Multi-IDM Claim Mapping

A CIAM app rarely has one identity provider. The same Spring resource server may accept tokens from Ping, Entra ID, and a partner's Keycloak — and every one of them buries roles and scopes in a different claim, with a different shape. The job of claim mapping is to melt those differences down into a single authority model your @PreAuthorize rules can rely on.

What is claim mapping — and why does each IDP put roles in a different place?

The JWT specification (RFC 7519) defines standard claims: sub, iss, aud, exp. It says nothing about where to put roles or scopes — each IDP decided their own. Ping Federate puts roles in a custom groups array. Entra ID puts app roles in roles and group membership in wids. Keycloak puts roles under realm_access.roles nested inside an object. Auth0 uses a namespaced claim like https://contoso.com/roles. If you write @PreAuthorize("hasRole('ADMIN')"), Spring Security needs to know which claim to look in to find "ADMIN". Without claim mapping configured, it defaults to scope claims only. Claim mapping is the configuration that says "for tokens from Ping, look in groups; for tokens from Entra, look in roles" and normalises them all into Spring Security authorities so your @PreAuthorize rules work regardless of which IDP issued the token.

Custom JwtAuthenticationConverter

@Bean JwtAuthenticationConverter converter() { var c = new JwtAuthenticationConverter(); c.setJwtGrantedAuthoritiesConverter(jwt -> { List<String> roles = new ArrayList<>(); roles.addAll(getFromClaim(jwt, "groups")); roles.addAll(getFromClaim(jwt, "roles")); roles.addAll(getNestedClaim(jwt, "realm_access", "roles")); return roles.stream().map(r -> new SimpleGrantedAuthority("ROLE_" + r)).toList(); }); return c; }. Maps all three IDPs into one authority list.

Multi-issuer validation

One resource server accepting tokens from multiple IDPs: configure multiple JwtDecoder beans and a JwtIssuerAuthenticationManagerResolver that picks the decoder based on the token's iss claim. Spring Security routes the JWT to the right decoder automatically. Each decoder validates signature against that IDP's JWKS and checks the iss claim. A token from Ping is validated by the Ping decoder; an Entra token by the Entra decoder.

Normalised authority model

After mapping, all roles become ROLE_CIAM_ADMIN, ROLE_USER_MANAGER regardless of which IDP they came from. Your @PreAuthorize rules are IDP-agnostic: @PreAuthorize("hasRole('CIAM_ADMIN')"). If Ping calls it "CIAM-Admin" and Entra calls it "CIAMAdmin", normalise in the converter: if (role.equalsIgnoreCase("ciam-admin") || role.equalsIgnoreCase("ciamadmin")) return "ROLE_CIAM_ADMIN". One mapping layer, zero changes to service code.

In CIAM: Your app accepts tokens from both Ping Federate (internal employees) and Entra ID (external partners). Ping tokens: "groups":["CIAM_ADMIN","USER_MANAGER"]. Entra tokens: "roles":["CIAMAdmin"]. The JwtIssuerAuthenticationManagerResolver routes by iss. The custom converter normalises both to ROLE_CIAM_ADMIN. Result: @PreAuthorize("hasRole('CIAM_ADMIN')") works for both Ping admins and Entra admins — your service code has no IDP-specific logic. When a third IDP is onboarded (e.g. a partner's Keycloak), add a third decoder and mapping case — zero service changes.

3. Accepting multiple issuers: route by iss

    

      

        
One issuer (the simple case)

        
# application.yml
spring.security.oauth2.resourceserver.jwt:
  issuer-uri: https://auth.pingone.com/<envId>/as

        
Spring auto-builds a JwtDecoder from the issuer's /.well-known + JWKS. Fine until a second IDM shows up.

      

      

        
Many issuers (multi-tenant)

        
var resolver = JwtIssuerAuthenticationManagerResolver
    .fromTrustedIssuers(
       "https://login.microsoftonline.com/<tenant>/v2.0",
       "https://auth.pingone.com/<envId>/as");

http.oauth2ResourceServer(o -> o
    .authenticationManagerResolver(resolver));

        
Each request is routed by its iss to the matching decoder/JWKS. Unknown issuer → rejected. Per-issuer you attach the right claim converter (next section).

      

    

  


  
  

    
4. The converter that does the melting

    

      
// turn THIS issuer's claims into Spring authorities
class EntraAuthoritiesConverter implements Converter<Jwt, Collection<GrantedAuthority>> {
  @Override public Collection<GrantedAuthority> convert(Jwt jwt) {
    var auths = new ArrayList<GrantedAuthority>();
    // scopes: Entra uses "scp" (space-delimited)
    for (String s : jwt.getClaimAsString("scp").split(" "))
      auths.add(new SimpleGrantedAuthority("SCOPE_" + s));
    // roles: Entra app roles live in "roles"; map to your canonical role names
    for (String r : jwt.getClaimAsStringList("roles"))
      auths.add(new SimpleGrantedAuthority("ROLE_" + ROLE_MAP.getOrDefault(r, r)));
    return auths;
  }
}

// wire it onto a JwtAuthenticationConverter (per issuer)
var conv = new JwtAuthenticationConverter();
conv.setJwtGrantedAuthoritiesConverter(new EntraAuthoritiesConverter());

      
Ping and Keycloak get their own converter (reading scope + p1.role / realm_access.roles) — but all three emit the same ROLE_*/SCOPE_* authorities, so nothing downstream needs to know which IDM the user came from.

      
↪ Those authorities are exactly what Method Security (@PreAuthorize) evaluates. Token validation basics: Spring · IDM Integration (OAuth2).

    

  


  
  

    
5. Pitfalls unique to multi-IDM

    

      
    
        
  • Entra group GUIDs. groups are object IDs like 8f3c…, not "Admins". Prefer app roles (the roles claim) or map GUID→role server-side. Large group sets also trigger an overage claim (you must call Graph to fetch them) — another reason to prefer app roles.
    • 
        
  • Validate aud per client. Routing by iss proves who minted the token; you still must check aud is your API, or you'll accept tokens meant for a different app in the same tenant.
    • 
        
  • Prefix discipline. Pick one convention (ROLE_ for roles, SCOPE_ for scopes) and apply it in every converter, or hasRole/hasAuthority checks silently miss.
    • 
        
  • Clock skew & key rotation. Each issuer rotates its JWKS independently; allow a little exp leeway and let Spring cache/refresh keys per issuer.
    • 
      

    

  


  
  

    
6. One-sentence recap

    

      
🔀 When one resource server trusts several IDMs, route each request to the right decoder by its iss (a JwtIssuerAuthenticationManagerResolver), then give each issuer a Converter<Jwt, Collection<GrantedAuthority>> that reads that IDM's scope claim (scp vs scope) and role claim (roles vs p1.role vs realm_access.roles) and emits one consistent ROLE_*/SCOPE_* model — so a single @PreAuthorize rule works no matter which provider signed the user in (just mind Entra's group GUIDs and always re-check aud).
