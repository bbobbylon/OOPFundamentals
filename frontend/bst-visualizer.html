Binary Search Tree — Balanced vs Degenerate

Smaller values go LEFT, larger go RIGHT. Balanced = O(log n). Sorted insert order? It becomes a linked list — O(n).

🧩 What is a Binary Search Tree — and why does the insertion order determine everything about its performance?

A Binary Search Tree (BST) is a binary tree that enforces one rule: for any node N, every value in N's LEFT subtree is smaller than N, and every value in N's RIGHT subtree is larger. This one invariant makes the tree searchable — at each node, you can eliminate half the remaining nodes by going left or right, giving O(log n) search for a balanced tree. Insert: start at root. If the new value is less than current node, go left; if greater, go right. Repeat until you find an empty spot — that's where the node goes. O(height). Search: same navigation. At each step, go left if target < current, right if target > current, return true if equal, return false if you hit null. O(height). In-order traversal: left → root → right. For a BST, this produces values in sorted ascending order — a useful property for producing sorted output without an extra sort pass. The critical insight: height determines everything. A balanced BST has height O(log n) — each level holds twice as many nodes as the previous, so n nodes fit in log₂(n) levels. O(log n) for all operations. A degenerate BST has height O(n) — if you insert values in sorted order (1, 2, 3, 4, 5...), every node goes to the right child of the previous one. The tree becomes a straight line — a linked list. Search degrades to O(n). Self-balancing BSTs (AVL trees, Red-Black trees) automatically restructure via rotations to maintain O(log n) height regardless of insertion order. Java's TreeMap and TreeSet are backed by a Red-Black tree — guaranteed O(log n) operations with sorted iteration. BST vs HashMap: HashMap gives O(1) get/put but no ordering. BST (TreeMap) gives O(log n) get/put with sorted iteration, floor(), ceiling(), range queries. Use TreeMap when you need sorted keys or range queries; use HashMap when order doesn't matter and you want pure speed.

BST node + search

class TreeNode { int val; TreeNode left, right; // left < val, right > val TreeNode(int v) { val = v; } } // Insert TreeNode insert(TreeNode node, int val) { if (node == null) return new TreeNode(val); // found the spot if (val < node.val) node.left = insert(node.left, val); else node.right = insert(node.right, val); return node; // O(height) } // Search boolean search(TreeNode node, int val) { if (node == null) return false; // ran off tree if (val == node.val) return true; // found it if (val < node.val) return search(node.left, val); // go left else return search(node.right, val); // go right } // In-order traversal (left→root→right) = sorted output

Java TreeMap — BST in practice

// TreeMap = Red-Black BST (self-balancing) // Guaranteed O(log n) for all operations // Keys are always in sorted order TreeMap<String, Integer> scoreBoard = new TreeMap<>(); scoreBoard.put("Alice", 95); scoreBoard.put("Bob", 87); scoreBoard.put("Carol", 91); // Keys always sorted: Alice, Bob, Carol scoreBoard.firstKey(); // "Alice" — O(log n) scoreBoard.lastKey(); // "Carol" — O(log n) // Range query: everyone with score "B" or "C" name scoreBoard.subMap("B", "D"); // Bob, Carol // Floor/ceiling (useful for range searches) scoreBoard.floorKey("Bz"); // "Bob" (largest key ≤ "Bz") scoreBoard.ceilingKey("Ca"); // "Carol" (smallest key ≥ "Ca") // WHEN to use TreeMap vs HashMap: // • Need sorted iteration → TreeMap // • Need floor/ceiling/range → TreeMap // • Just need fast get/put, no order → HashMap

In CIAM / Context: BSTs (via Java TreeMap) are directly useful in CIAM for: role-based access control lookups where roles need to be iterated in alphabetical/priority order, session management stores sorted by expiry timestamp (TreeMap<Long, Session> → efficiently find and evict the oldest sessions), audit log range queries (find all events between timestamp A and B in a sorted event store), and OAuth scope sorting/comparison (Ping AM sorts scopes lexicographically when constructing consent pages). The degenerate case is a real production risk — inserting OAuth client IDs in sequential order into a custom sorted container will silently become O(n); always use a library's balanced tree.

Balanced vs Degenerate — same 7 values, different insert order

Balanced — insert order [50, 30, 70, 20, 40, 60, 80]

Height = 3. Search for any value takes at most 3 hops. Cuts the remaining tree in half at each step.

Degenerate — insert order [10, 20, 30, 40, 50, 60, 70]

Height = 7. Every "left" pointer is null — it's just a linked list pointed at right. Search for 70 walks all 7 nodes.

The lesson: a plain BST is only fast if your insert order is roughly random. If your data comes in sorted (timestamps, auto-increment IDs, sorted file imports), you get the worst case. Production systems use self-balancing trees — AVL, Red-Black, B-trees — that rotate nodes after each insert to keep height ≈ log n.

Three traversal orders

In-order (Left, Root, Right)

Walks the tree in sorted order. This is the killer feature of BST: you can dump everything alphabetically/numerically just by traversing.

void inorder(Node n) {
    if (n == null) return;
    inorder(n.left);
    visit(n);
    inorder(n.right);
}

Used for: printing sorted output, range queries (give me all keys between A and B).

Pre-order (Root, Left, Right)

Visits the root before its children. Useful when you need to copy a tree or serialize it — you write the parent before you know about the children, but on replay the parent always exists when you need to attach a child.

void preorder(Node n) {
    if (n == null) return;
    visit(n);
    preorder(n.left);
    preorder(n.right);
}

Used for: tree copying, expression-tree prefix output, DOM serialization.

Post-order (Left, Right, Root)

Visits children before the parent. Useful when the parent depends on the children being done first — like deleting a tree (free the leaves first) or evaluating an expression tree (compute operands before applying the operator).

void postorder(Node n) {
    if (n == null) return;
    postorder(n.left);
    postorder(n.right);
    visit(n);
}

Used for: deleting a tree, expression-tree evaluation, dependency resolution.

Where you see trees in the real world

📂 File systems

Directory trees are literally trees. Every parent has children, every child has one parent. find does a recursive traversal.

🗄️ Database indexes

Postgres, MySQL, SQLite — all use B-trees (a flatter, disk-friendly cousin of BSTs) for most indexes. That's how WHERE id = 42 is fast on a billion-row table.

🌳 TreeMap / TreeSet

Java's TreeMap is a Red-Black tree. Use it when you need keys sorted, range queries (subMap, headMap), or "give me the next key after X".

🧬 DOM / XML / JSON

Every HTML page is a tree of nodes. document.querySelector walks that tree. Same goes for XML, JSON, AST — all tree-shaped.

🎮 Scene graphs & game AI

3D rendering uses scene trees (a car contains 4 wheels each containing tires...). Game AI uses decision trees and behavior trees.

📐 Expression trees

Calculators and compilers parse (2 + 3) * 4 into a tree where leaves are numbers and internal nodes are operators. Post-order traversal evaluates it.
