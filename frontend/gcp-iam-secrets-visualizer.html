IAM Policies, Service Accounts & Secret Manager

This is the CIAM-heaviest page in the GCP track: a service account is both an identity and a resource, Workload Identity Federation replaces downloaded JSON keys with short-lived tokens exchanged from CI/CD, and Secret Manager is where application secrets live with a full access audit trail.

🔐 What makes GCP identity different — and why is a service account both a "who" and a "what"?

Every IAM policy in GCP is a list of bindings — each one a {role, members[]} pair, optionally scoped by a CEL condition (e.g. only valid before an expiry time, or only from a given IP range) — attached to a resource, and every binding is inherited downward through the Organization → Folder → Project → Resource hierarchy as a union: there is no explicit per-resource Deny, so the only way to carve out an exception is an Organization Policy constraint at a higher level. A Service Account is the identity most workloads run as, but unlike a human user it is also a resource in its own right that can itself appear as a member in an IAM binding — which is what makes impersonation possible: if principal A is granted roles/iam.serviceAccountTokenCreator on service account B, A can mint short-lived tokens as B without ever holding B's credentials. Workload Identity Federation (WIF) takes this one step further for external systems like GitHub Actions: it exchanges a GitHub-issued OIDC token for a short-lived GCP access token via Security Token Service (STS), which then impersonates a service account — the entire flow needs zero long-lived keys, closing off the single most common real-world GCP credential leak (a downloaded service-account JSON key committed to a public repo). Secret Manager stores application secrets as versioned, encrypted blobs with per-version IAM bindings and immutable Cloud Audit Logs recording every access — never a plaintext env var and never a value baked into a container image.

  • IAM binding — {role, members[], optional CEL condition}, inherited downward and unioned, no explicit Deny.
  • Service account — an identity workloads run as, AND a resource that can be impersonated via a binding on itself.
  • Impersonation — roles/iam.serviceAccountTokenCreator lets principal A mint short-lived tokens as principal B.
  • Workload Identity Federation — external OIDC token → STS exchange → service account impersonation, zero downloaded keys.
  • Secret Manager — versioned, encrypted, IAM-gated secrets with a full Cloud Audit Log access trail.

The impersonation pattern

# grant impersonation rights gcloud iam service-accounts add-iam-policy-binding \   deploy-sa@proj.iam.gserviceaccount.com \   --member="user:bob@co.com" \   --role="roles/iam.serviceAccountTokenCreator" # then mint a short-lived token AS that SA gcloud auth print-access-token --impersonate-service-account=deploy-sa@proj.iam.gserviceaccount.com

AWS & Azure comparison

IAM bindings ≈ AWS IAM policies ≈ Azure RBAC role assignments, but GCP's model is the simplest of the three: pure allow-list union, no explicit Deny statement (AWS has explicit Deny; Azure has Deny assignments). Workload Identity Federation ≈ AWS IAM Roles for GitHub OIDC ≈ Azure Workload Identity Federation (same name, same idea) — all three converged on "exchange a CI-issued OIDC token for a cloud-native short-lived credential" as the answer to long-lived key sprawl. Secret Manager ≈ AWS Secrets Manager ≈ Azure Key Vault.

Spring Boot comparison

Fetching a database password from Secret Manager at startup via the Secret Manager Spring Boot starter (spring.cloud.gcp.secretmanager.secret-manager.enabled=true, then ${sm://db-password} in application.yml) is the exact same externalized-config pattern as pulling secrets from Vault or AWS Secrets Manager — the secret never lives in application.yml itself, only a reference to where it lives.

CIAM in production: This page is the direct GCP analogue of your day job's Ping/Entra federation work — Workload Identity Federation's OIDC-token-in, short-lived-token-out exchange via STS is structurally identical to any OIDC federation flow, and the service-account-as-both-identity-and-resource duality is the same mental model as a Ping service account or an Entra app registration that can itself be a principal in another resource's access policy.

The problem

You never created a service account for that VM. It has one anyway, and in an older project it is probably Editor.

"Allow full access to all Cloud APIs" plus a default service account nobody assigned

Create a VM and skip the service-account section, as almost everyone does the first time. The instance gets the project's default Compute Engine service account — PROJECT_NUMBER-compute@developer.gserviceaccount.com — which for years was granted the roles/editor basic role on the project automatically, at project creation. Google now ships an org policy constraint that switches that automatic grant off, and it is enforced by default for newly created organisations. Your existing projects did not retroactively change.

Then there is the second control, which is easy to read as a convenience setting. Access scopes are a legacy per-VM limit on what that service account's token may be used for, and the default set is deliberately narrow — read-only storage, write logs and metrics. Somebody hits a permission error, finds the advice "set access scopes to allow full access", and selects it. That replaces the narrow list with cloud-platform, which means "no scope restriction" — and now the only thing standing between code on that VM and the project is the IAM role, which is Editor. A dependency with a post-install script, or an SSRF in your own app, is project Editor too.

Keyless is a real improvement, and it is not the same thing as least privilege.

Create a dedicated service account per workload and attach it explicitly — never run on the default one ↓ a purpose-built identity can be given exactly the roles that workload needs, and revoked without affecting anything else Set scopes to cloud-platform deliberately and do the real restricting in IAM ↓ scopes are a blunt legacy layer; two half-controls that each look like the answer is how workloads end up with neither Then enforce constraints/iam.automaticIamGrantsForDefaultServiceAccounts and go strip Editor off the default accounts in the projects that predate it
Every workload runs as something. If you did not choose it, a default did — and defaults are set for the convenience of getting started, not for the shape of your production system. The useful audit question is not "who has access to this project?" but "what identity does each piece of running code carry, and who decided that?" Those are different questions, and only the second one finds a VM quietly holding Editor because nobody filled in an optional field.
Access scopes and IAM roles are two seatbelts, each of which people assume is the other one's job. Scopes are the legacy layer and cannot express anything fine-grained; IAM is the real control. Widen the first and forget the second, and nothing is holding you.
You

I never attached a service account to that instance. What is it even running as?

The default Compute Engine service account

Me. I was created with the project and attached because the field was left empty. In an older project I hold roles/editor, which I was granted automatically — not because anyone decided your VM needed it, but because that was the default at the time the project was made.

Access scopes

And I am the older, cruder limit that sits on top. I restrict which APIs a token from this VM may call, regardless of IAM. I cannot express "this bucket" or "read only this secret" — I work in whole APIs. Which is why setting me to cloud-platform is reasonable if IAM is doing the real work, and dangerous if you assumed I was.

The metadata server

Meanwhile I hand out that token to anything running on the instance that asks me, over plain HTTP on an internal address. I do require a Metadata-Flavor: Google header, which stops the laziest request forgery — but any code on the box, and any SSRF that can set a header, gets a working token.

The mechanism

Six steps from an unticked checkbox to project Editor.

  1. A project is created. Enabling Compute Engine creates the default service account, which in older projects is granted roles/editora grant nobody requested
  2. A VM is created with the service-account field left alone, so it runs as that default accountthe identity, by omission
  3. The app hits a permission error. The quickest fix in every forum answer is to widen the instance's access scopesthe plausible wrong turn
  4. Scopes become cloud-platform. The narrow API limit is gone, and IAM — Editor — is the only remaining boundaryboth controls now open
  5. Any process on the instance can ask the metadata server for a token and receive one that is Editor on the projectincluding code you did not write
  6. An SSRF in your own app is enough: make the app fetch the metadata URL with the required header, and read the token out of the responsea web bug becomes a cloud breach

Step 6 is why this belongs in an application developer's head and not only an infrastructure engineer's. Server-side request forgery is normally a medium-severity finding — "the app can be made to fetch a URL" — and on a cloud VM it is the step that converts a web vulnerability into cloud credentials. That conversion is the whole reason the metadata service grew defences (Google's required header, AWS's move to IMDSv2's session tokens): the bug being defended against is in your application, not in the platform. Reduce what the token is worth and an SSRF goes back to being an SSRF.

Only the first of those was the intent, and the setting cannot distinguish between them, because a VM-wide credential is available to everything on the VM by definition. That is the argument for a dedicated service account per workload in the strongest form: it is not tidiness, it is that the identity is shared by every line of code on that machine, wanted or not. The same reasoning is why Workload Identity Federation and per-pod identities exist — push the credential down to the smallest unit that has a distinct job.

A VM in a long-standing project was created without specifying a service account, and someone later set its access scopes to "allow full access to all Cloud APIs". No service-account key was ever downloaded, and the project's IAM bindings were reviewed last quarter. What is the exposure?

Short-lived and not downloadable are genuine improvements, and they defeat a whole class of leaked-key incidents. They do nothing about code already running on the instance, which can simply ask the metadata server for a fresh token whenever it wants one — and the token works from anywhere for its lifetime once it has been read.

Correct on both halves, and the fix is both halves too: give the workload its own service account with only the roles it needs, and remove roles/editor from the default account in every project that predates the org policy. Newer organisations get the safer default automatically — older projects keep whatever they were created with, and nothing goes back to fix them for you.

Where you have seen this before

Defaults are decisions. They are just decisions nobody remembers making.

IMDSv1 and the same attack on the other cloud

An SSRF fetching the EC2 metadata endpoint returned the instance role's credentials, which is how several well-known breaches escalated from a web bug to the account. IMDSv2 answered it with a required PUT-issued session token. Same lesson in two clouds: a credential reachable over HTTP from inside is reachable by any bug that can make an HTTP request.

SSRF is a credential vulnerability in the cloud

Kubernetes' default service account token, mounted into every pod

Unless you say otherwise, a pod gets a token for the namespace's default service account mounted into its filesystem. Usually harmless, occasionally not — and the fix is the same shape: automountServiceAccountToken: false, then a dedicated identity per workload that actually needs one.

mounted by default, reviewed by nobody

The database user your app connects as

It is almost always the one from the tutorial, it almost always owns the schema, and nobody revisits it once the connection works. Any SQL injection inherits every right that user has — which is why "what does my app connect as?" is worth asking about every dependency it talks to.

The whole page on a napkin: GCP IAM bindings are additive and inherited down the resource hierarchy with no explicit Deny in the allow policy, service accounts are identities you impersonate rather than log into, Workload Identity Federation removes downloaded keys entirely, and Secret Manager versions secrets behind IAM with full audit logging. The sentence worth adding: a VM with no service account specified runs as the default Compute Engine account, which in older projects is project Editor — give every workload its own identity and let IAM, not access scopes, do the limiting.

1. IAM bindings: union, inherited, no explicit Deny

# a binding with a CEL condition — expires automatically
gcloud projects add-iam-policy-binding proj-123 \
  --member="user:temp-contractor@co.com" \
  --role="roles/viewer" \
  --condition='expression=request.time < timestamp("2026-09-30T00:00:00Z"),title=temp-access'
There is no "Deny" binding in core IAM. If a folder grants Editor and a project grants nothing further, the effective permission at the project is still Editor — inherited bindings only ever add access, never subtract it. The only way to carve out a true exception is an Organization Policy constraint (a different system entirely) applied at or above the resource in question.

2. Workload Identity Federation: no downloaded keys, ever

# GitHub Actions step — no service-account key file anywhere
- uses: google-github-actions/auth@v2
  with:
    workload_identity_provider: 'projects/123/locations/global/workloadIdentityPools/gh-pool/providers/gh-provider'
    service_account: 'deploy-sa@proj.iam.gserviceaccount.com'
The GitHub OIDC token never directly grants GCP access. STS exchanges it for a short-lived GCP federated token, and a separate IAM binding (roles/iam.workloadIdentityUser, scoped to a specific repo/branch via an attribute condition) is what allows that federated identity to impersonate the target service account — two independent checks, either of which failing blocks the whole flow.

3. Secret Manager: versioned, IAM-gated, fully audited

# fetch the latest version — access is logged automatically
gcloud secrets versions access latest --secret=db-password

# Spring Boot: spring.cloud.gcp.secretmanager auto-resolves this
spring.datasource.password=${sm://db-password}
Every access is a Cloud Audit Log entry, with no opt-out. Unlike an environment variable — which is invisible after the fact — every single read of a Secret Manager value is permanently recorded: who, when, which version, from which resource. This audit trail is frequently the deciding factor in choosing Secret Manager over env vars for anything regulator-sensitive.
