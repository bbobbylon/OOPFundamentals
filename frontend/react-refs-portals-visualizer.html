Refs, forwardRef & Portals

Refs are React's escape hatch to the imperative world: a mutable box that survives renders without causing them. Plus forwarding a ref to a child's DOM node, exposing a controlled imperative API, and rendering outside your DOM subtree with portals.

🚪 What are Refs and Portals — and when do you break out of React's declarative model?

React is declarative, but sometimes you must reach into the DOM imperatively — focus an input, measure an element, drive an animation, wrap a non-React library. useRef is the escape hatch: a mutable {current} box that persists across renders without triggering one (state change → re-render; ref change → nothing). It holds DOM nodes (<input ref={myRef}>) or arbitrary values (timer IDs, sockets). forwardRef lets a parent reach a DOM node inside a child; useImperativeHandle exposes a custom API ({focus, reset}) instead of the raw node. Portals render a subtree into another DOM node — modals, tooltips, dropdowns that must escape overflow:hidden/z-index, while events still bubble through the React tree.

  • useRef = escape hatch — mutable box that persists without re-rendering.
  • Holds DOM nodes or values — focus/measure, timer IDs, sockets, prev props.
  • forwardRef/useImperativeHandle — pass a ref through, or expose a custom API.
  • Portals escape the DOM parent — modals/tooltips; events still bubble React-side.

DOM ref + forwardRef

// DOM ref: access the real input element function SearchBox() { const inputRef = useRef<HTMLInputElement>(null); // After component mounts, inputRef.current = <input> useEffect(() => { inputRef.current?.focus(); // focus on mount }, []); return <input ref={inputRef} type="search" />; } // forwardRef: let PARENT access an input inside SearchBox const SearchBox = forwardRef<HTMLInputElement, {}>((props, ref) => ( <input ref={ref} type="search" {...props} /> )); // Parent usage: function Page() { const searchRef = useRef<HTMLInputElement>(null); return ( <> <button onClick={() => searchRef.current?.focus()}>Focus Search</button> <SearchBox ref={searchRef} /> </> ); }

Portal for modals

// Modal component rendered in document.body // (outside the app's overflow:hidden container) function Modal({ title, onClose, children }: ModalProps) { // Prevent body scroll while modal open useEffect(() => { document.body.style.overflow = 'hidden'; return () => { document.body.style.overflow = ''; }; }, []); // createPortal: render into #portal-root, not parent div return createPortal( <div className="modal-overlay" onClick={onClose}> <div className="modal" onClick={e => e.stopPropagation()}> <h2>{title}</h2> {children} <button onClick={onClose}>Close</button> </div> </div>, document.getElementById('portal-root')! // target DOM node ); } // Events still bubble through React tree (not DOM tree!) // So a click in the modal bubbles to the component // that rendered <Modal />, not to document.body

Angular comparison

React ref → Angular equivalent. useRef<HTMLInputElement>(null) + ref={inputRef} → Angular's @ViewChild('searchInput') searchInput!: ElementRef<HTMLInputElement> + #searchInput in template. inputRef.current?.focus() → this.searchInput.nativeElement.focus(). forwardRef → Angular's @ViewChild in a parent reaching into a child's template ref. useImperativeHandle → Angular component exposing public methods that the parent calls via @ViewChild(ChildComponent). Portal → Angular CDK's Overlay service — renders content in an overlay container outside the component tree. Angular Material dialogs, tooltips, and bottom sheets all use CDK Overlay internally — the React Portal equivalent. The conceptual model is identical: render content that visually escapes the component's DOM position.

CIAM React app: A delete-user confirmation modal must render above fixed headers, overflow:hidden sidebars and stacked dropdowns — so createPortal(<ConfirmDeleteModal .../>, document.getElementById('portal-root')!), with its confirm button firing a deleteUserMutation.mutate(user.id). Focus management is the accessibility part: move focus to the first button on open (firstFocusableRef.current?.focus()) and back to the trigger on close (triggerRef.current?.focus()). A ref also measures the trigger (getBoundingClientRect()) so a tooltip portal can position relative to it.

1. Two jobs for useRef

JobExample
Access a DOM node<input ref={inputRef} /> → inputRef.current.focus()
Hold a mutable value across renders without re-renderinginterval IDs, previous values, "has mounted" flags, latest props
Mutating .current never triggers a re-render. That is the entire point — and the gotcha. A ref is for values the render output does not depend on. If the UI must reflect the value, it belongs in useState, not a ref. Also: don't read or write .current during render (it makes render impure) — do it in effects and event handlers.

2. Getting a ref to a child's DOM node

You can't put a ref on a custom component and expect a DOM node — components aren't DOM nodes. You must forward the ref to a real element inside.

≤ React 18: forwardRef

const Input = forwardRef((props, ref) => (
 <input ref={ref} {...props} />
));

React 19: ref is just a prop

function Input({ ref, ...props }) {
 return <input ref={ref} {...props} />;
} // no forwardRef needed
React 19 makes ref a normal prop for function components, so forwardRef is no longer required (and is being deprecated over time). You'll still see forwardRef everywhere in existing code and libraries — know both.

3. Portals keep the React tree, change the DOM tree

createPortal(
  <Modal />, // what to render
  document.getElementById('modal-root') // WHERE in the DOM
)
A portal renders into a different DOM node but stays in your React tree. So context still works, and synthetic events still bubble to the React parent — even though the DOM node lives under <body>. This escapes parent overflow:hidden and z-index stacking contexts that would otherwise clip a modal, dropdown, tooltip, or toast.
