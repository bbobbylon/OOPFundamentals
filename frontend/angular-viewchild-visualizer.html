Template Reference Variables, ViewChild & ContentChild

Template reference variables let you name elements in your template so you can pass them to event handlers or read them in your component class. ViewChild and ContentChild are the decorators (and their modern signal equivalents) that make template elements available as TypeScript properties.

🎯 What is ViewChild? When do you reach into the template from the component?

Data binding usually makes direct DOM access unnecessary — set a signal and the template updates. But sometimes you need the actual element or child component instance: to focus an input, call a method on a child, measure an element, or hand a real HTMLElement to a chart library. ViewChild gives you a property Angular populates with that reference. The critical timing rule: the element only exists after ngAfterViewInit — not in the constructor, not in ngOnInit.

  • Query by template-ref name ('searchInput'), a component class, or a directive class.
  • Decorator form @ViewChild(...) resolves after ngAfterViewInit (use { static: true } only for always-present elements).
  • Signal form viewChild(...) (17+) is reactive — undefined until ready, then updates as the element appears/disappears (e.g. inside @if); viewChild.required() asserts presence.
  • @ContentChild / contentChild() query projected content (from the consumer's template) and resolve after ngAfterContentInit.
  • Use it for imperative needs — focus, scroll, measure, integrate a JS lib — not as a substitute for binding.

@ViewChild — query an element

@ViewChild('searchInput') input!: ElementRef + template <input #searchInput>. In ngAfterViewInit: this.input.nativeElement.focus(). The ! is needed because Angular sets it asynchronously.

viewChild() signal (17+)

input = viewChild<ElementRef>('searchInput'). Read it as this.input()?.nativeElement.focus() — no ngAfterViewInit dance; the signal updates when the element appears or is removed.

ContentChild — projected content

@ContentChild queries elements the consumer projected via <ng-content> (not the component's own template). Resolves after ngAfterContentInit. For wrapper components — modal, card, accordion.

In CIAM:after the "Create User" dialog opens, auto-focus email with this.emailInput()?.nativeElement.focus(); call this.userForm()?.resetForm() on the child form after a successful save; pass a <div #chartHost> ref to a Chart.js init in ngAfterViewInit (it needs a real DOM node, not data).

or, static: true doesn't mean "get it sooner" — it means "get it once, before anything conditional exists"

A photograph taken once is not the same as a camera that's still recording.

You added static: true to fix a timing bug. The reference didn't arrive later. It stopped arriving at all.

I set static: true specifically so I'd have the reference earlier. Why is it undefined even in ngAfterViewInit, once the panel is open?
Because "early" and "ever" aren't the same promise. static: true resolves your query exactly once, before ngOnInit runs — using only whatever the template's static structure contains at that single moment. Your canvas sits behind @if (showPanel), and showPanel was false when the component was constructed, so the query looked, found nothing, and never looks again.
But the canvas IS in the DOM once showPanel flips true — why doesn't static: true just see it then?
static: true isn't watching anything. "Static" describes WHEN the query resolves, not WHETHER the thing it's looking for exists yet. It's a one-time snapshot taken at a fixed point before your template's conditional content has even been decided — it doesn't get a second look when the doors open later.
So is static: true just broken, then — should I stop using it?
No — for an element with no structural block above it, ever (a permanent toolbar, a fixed header), static: true is completely correct, and it resolves one hook earlier than the default. It only fails for an element that CAN vanish — a step-up MFA modal that slides open to its own content height is exactly that case: measuring it with static: true either finds nothing or snaps open at the wrong height for one visible frame, because the modal wasn't there yet at the one moment the query looked. The promise static makes was never about existence — only about timing.
Doesn't the signal viewChild() have the exact same "one moment" problem, just with nicer syntax?
No — this is the one place the two genuinely diverge. viewChild() has no fixed "when": it re-evaluates on every change-detection pass, so the instant your @if flips true, it flips from undefined to the real ElementRef on its own, with no lifecycle hook required at all.
Fine — I'll play it safe and always use the DEFAULT @ViewChild (no static) instead. Now I'm covered?
Safer, not safe. Default still resolves only ONCE — in ngAfterViewInit, just one hook later than static: true. If your conditional element still hasn't rendered by THAT moment either, you get the identical undefined, for a shorter window that's just as real. Default moves the snapshot later; it doesn't turn it into a live feed.
My console just prints "undefined" either way. How do I even tell which of the two traps I'm looking at?
You can't, from the log alone — a permanently-undefined static: true reference and a not-yet-resolved default reference are printed identically. The only way to know is to go check which query style produced it: one fixes itself on the very next render. The other never will.
static: true is a promise about WHEN a query resolves, not a promise about WHETHER the element exists. That's why it works for a permanently present nav bar but not a canvas behind an @if, why a signal-based viewChild() sidesteps this whole class of bug (it doesn't need a "when" — it reacts whenever the element shows up or disappears), and why "undefined, with no error" is the single most common symptom across all four of ViewChild's query styles.
Think of static: true as a photograph taken the instant the doors open, before anyone behind a velvet rope is let in. If the thing you're looking for was still behind that rope — behind an @if — at that exact moment, the photo simply doesn't have it in frame, and no amount of staring at that same photo later will make it appear, because nobody ever retakes it. The signal viewChild() is a security camera instead: it keeps recording, so it catches the moment the rope drops.

The mechanism

Four query styles. One question decides which one to reach for: can the element disappear?

  1. Angular reads your query — decorator or signal call — at class definition time and records what to look for: a template-ref name, a component type, a directive typethe "what," decided in code
  2. For static: true, Angular resolves it once, before ngOnInit, using only what the template's static structure contains right thena single snapshot, taken early
  3. For everything else, Angular waits until the full view — including embedded views from @if/@for — has been created, then resolves in ngAfterViewInitthe default, and the safe one
  4. An element inside a structural block that hasn't rendered yet comes back undefined — permanently for static: true, temporarily for everything elsesame symptom, opposite outcome
  5. Decorator queries never re-run after their one resolution point unless you manually subscribe to QueryList.changes — a viewChild() signal re-evaluates on every change-detection pass insteadthe entire reason the signal form exists
  6. ContentChild/contentChildren follow the identical rules one hook later — ngAfterContentInit — because projected content isn't attached until after your own view starts buildingsame trap, shifted one step right

Step 4 is the lesson. "Same symptom" is the trap: a permanently-undefined static: true reference and a not-yet-resolved default reference both just print undefined in a console log — indistinguishable at a glance. One of them fixes itself on the very next render. The other never will. You cannot tell which you're looking at without knowing which query style produced it, which is exactly why reaching for static: true "to be safe" is worse than just waiting for ngAfterViewInit.

Only one of these three options actually tracks an element that can appear and disappear — the other two answer a fixed "when," and a conditional element doesn't have a fixed when.

@ViewChildren(PanelComponent) panels!: QueryList<PanelComponent> is populated from an *ngFor. Inside ngAfterViewInit you run this.initialCount = this.panels.length. The user then adds three more panels through the *ngFor list. Later, do this.panels.length and this.initialCount reflect the new total?

There's no refresh step required — that's the entire point of a QueryList staying live: Angular updates it automatically whenever change detection notices the *ngFor added or removed elements. Nothing manual is needed for the QueryList itself; the miss here is somewhere else entirely.

A reasonable instinct — "live" sounds like it should spread to everything touched by it. But this.initialCount = this.panels.length just copies a plain number out, once. The QueryList object keeps updating after that line runs; the number you copied out of it that one time has no ongoing connection back to the list it came from.

Right. The QueryList instance is live — check this.panels.length again later and it reflects every panel currently in the DOM. initialCount is a snapshot: a plain number, copied out at one moment, with no ongoing connection back to the list it came from.

Questions from the back row

Is this an Angular-only quirk, or does it show up anywhere else?

It's older than Angular. React's useRef is null until after React commits the DOM, so you read it inside useEffect — never during the render function itself, the same "declared up front, populated after a specific later moment" split. A plain <script> tag calling document.getElementById before the element below it has parsed hits the identical wall with no framework and no lifecycle hook to lean on at all. Angular just formalizes a rule every DOM-touching system eventually needs.

Why does Angular even have ngAfterContentInit as a separate hook from ngAfterViewInit?

Because content projection and your own template are built in a specific order that matters: Angular has to finish instantiating whatever a consumer projected into your <ng-content> before it finishes building the rest of your own view around it, so ngAfterContentInit necessarily fires first. Collapsing them into one hook would mean you couldn't tell whether you were looking at projected content or your own template's children — exactly the distinction @ContentChild vs @ViewChild exists to preserve.

Can I mix the signal viewChild() and the classic @ViewChild decorator in the same component?

Nothing stops you, but there's rarely a reason to once you've adopted signal queries. The decorator needs the ngAfterViewInit dance and gives you undefined forever if you read it too early; the signal form needs neither and updates live. Angular ships both because a decade of existing code uses the decorator — new code should default to the signal form and reach for the decorator only where it has to interoperate with something still written the old way.

ViewChild AND ContentChild both return undefined for the same element. How do I know which one I should have used?

By where the markup was physically written. If it's inside your own component's template, it's a ViewChild. If the consumer of your component wrote it between your component's opening and closing tags and it arrives via <ng-content>, it's a ContentChild. Mixing them up returns undefined with no error either way, so the fastest diagnosis is to go look at which template the element was actually typed into.

Template reference variables — #myRef

Add a #name attribute to any element in a template to create a reference variable. Its meaning depends on what you put it on:

Element typeWhat #ref refers toExample
Plain HTML element The native HTMLElement (an ElementRef.nativeElement) <input #myInput> → myInput.value
Angular component The component class instance — all its public properties and methods <app-timer #timer> → timer.start()
Directive on element By default: the ElementRef. Export the directive with exportAs and use #ref="directiveName" to get the directive instance instead. <input #f="ngModel" [(ngModel)]="val"> → f.valid
<ng-template> A TemplateRef object you can use to render the template imperatively <ng-template #tpl> 
<!-- 1. Reference a plain input — use in template directly -->
<input #searchInput type="text" placeholder="Search..." />
<button (click)="onSearch(searchInput.value)">Search</button>

<!-- 2. Read a child component's instance  -->
<app-accordion #accordion></app-accordion>
<button (click)="accordion.closeAll()">Collapse All</button>

<!-- 3. Get the ngModel directive instance (not the element) -->
<input #emailField="ngModel" [(ngModel)]="email" name="email" required email />
<p *ngIf="emailField.invalid && emailField.touched">Enter a valid email</p>

<!-- 4. Reference an ng-template for ViewContainerRef usage -->
<ng-template #modalTemplate>
  <app-modal>...</app-modal>
</ng-template>

@ViewChild decorator — all four overloads

@ViewChild queries the component's own template (not projected content). You pass either a string matching a template reference variable name, or the class of the component/directive you want. Angular populates the decorated property after ngAfterViewInit. 

import { ViewChild, ElementRef, AfterViewInit } from '@angular/core';

export class DashboardComponent implements AfterViewInit {

  // 1. By template reference variable name (string)
  @ViewChild('chartCanvas') canvas!: ElementRef<HTMLCanvasElement>;

  // 2. By component class — gets the first instance of that component in the template
  @ViewChild(ChartComponent) chart!: ChartComponent;

  // 3. By directive class — gets the directive applied to any element in the template
  @ViewChild(ResizableDirective) resizable!: ResizableDirective;

  // 4. static: true — populate BEFORE ngOnInit (only for non-conditional elements)
  @ViewChild('header', { static: true }) header!: ElementRef;
  //  ^ This works in ngOnInit. But ONLY if <div #header> is NEVER inside *ngIf/*ngFor

  // Default: static: false — populate after view init, required for conditional elements
  @ViewChild('tooltip', { static: false }) tooltip?: ElementRef;
  //  ^ element might be inside *ngIf, so it's optional (?) and only available in ngAfterViewInit

  // 5. Get the injector's ElementRef — the host element of this component itself
  @ViewChild(ElementRef) hostEl!: ElementRef;

  ngAfterViewInit(): void {
    // All @ViewChild fields (except static:true) are populated HERE
    this.chart.setData([10, 20, 30]);
    this.canvas.nativeElement.getContext('2d');
  }
}

static: true vs static: false — when to use each

The static option controls when the query is resolved. The default (false) is almost always the right choice. Use true only in the narrow case where you need the reference available in ngOnInit and you're certain the element is not conditional.

static: false (default) — correct for most cases

<!-- element inside *ngIf — dynamic -->
<div *ngIf="showPanel">
  <app-panel #panel></app-panel>
</div>

// ✅ static: false → resolved after view init
@ViewChild('panel') panel?: AppPanelComponent;
// panel is undefined if showPanel is false
// panel is populated in ngAfterViewInit when showPanel is true

ngAfterViewInit() {
  if (this.panel) { this.panel.open(); }
}

static: true — only for always-present elements

<!-- element is ALWAYS in the template, no *ngIf -->
<app-navbar #nav></app-navbar>

// ✅ static: true → resolved before ngOnInit
@ViewChild('nav', { static: true }) nav!: NavbarComponent;

ngOnInit() {
  this.nav.setTitle('Dashboard');
  // Works! nav is available here because static: true
}

// ❌ DO NOT use static: true if the element could be inside *ngIf
// The query will silently return undefined and confuse you

@ViewChildren — QueryList of all matches

When you have multiple matching elements — typically created by *ngFor — use @ViewChildren (plural). It returns a QueryList<T>, not a plain array. A QueryList is a special Angular collection that stays live: when items are added or removed from the DOM, the QueryList updates automatically. It also emits on its .changes Observable. 

import { ViewChildren, QueryList } from '@angular/core';   // QueryList is a TYPE — the collection @ViewChildren populates

export class AccordionComponent implements AfterViewInit, OnDestroy {
  private destroy$ = new Subject<void>();   // the teardown signal for the changes subscription below

  // Gets ALL PanelComponent instances in the template
  @ViewChildren(PanelComponent) panels!: QueryList<PanelComponent>;

  ngAfterViewInit(): void {
    console.log(this.panels.length);         // number of panels
    console.log(this.panels.toArray());      // convert to regular array
    this.panels.first.expand();              // access first item directly
    this.panels.last.collapse();             // access last item directly

    // Subscribe to QueryList changes — fires when *ngFor adds/removes panels
    this.panels.changes
      .pipe(takeUntil(this.destroy$))   // unsubscribes automatically when destroy$ fires, in ngOnDestroy below
      .subscribe((updated: QueryList<PanelComponent>) => {
        console.log('Panels updated — new count:', updated.length);
        updated.forEach(p => p.recalculateSize());   // re-run per-panel logic against the FRESH list, not the stale one
      });
  }

  closeAll(): void {
    // forEach works just like on an array
    this.panels.forEach(p => p.collapse());
  }

  ngOnDestroy(): void { this.destroy$.next(); this.destroy$.complete(); }   // the standard takeUntil teardown pair
}

@ContentChild and @ContentChildren

@ContentChild queries content projected into the component via <ng-content> — not content defined in the component's own template. It works exactly like @ViewChild but targets projected content. Available from ngAfterContentInit onward (earlier than @ViewChild's ngAfterViewInit).

The component template (defines a slot)

<!-- card.component.html — the "host" component -->
<div class="card-wrapper">
  <div class="card-header">
    <!-- any content projected as #header goes here -->
    <ng-content select="[slot=header]"></ng-content>   <!-- only elements with a slot="header" attribute land here -->
  </div>
  <div class="card-body">
    <ng-content></ng-content>  <!-- default slot -->
  </div>
</div>

// card.component.ts — query the projected icon button
export class CardComponent implements AfterContentInit {   // a DIFFERENT lifecycle interface than AfterViewInit — content, not view
  @ContentChild(ActionButtonComponent)
  actionBtn!: ActionButtonComponent;   // finds it wherever the CALLER projected it — this component never defines it itself

  ngAfterContentInit() {
    // ✅ actionBtn is available HERE (content has been projected)
    this.actionBtn.setVariant('outline');   // calling a method on the PROJECTED component's own instance
  }
}

The parent template (projects content in)

<!-- parent.component.html -->
<app-card>

  <!-- This ActionButtonComponent is projected into <app-card> -->
  <!-- @ContentChild in CardComponent will find it -->
  <app-action-button slot="header">
    Edit
  </app-action-button>

  <!-- default slot content -->
  <p>Card body content here.</p>

</app-card>

// @ContentChildren — get ALL projected children of a type:
@ContentChildren(MenuItemComponent)
menuItems!: QueryList<MenuItemComponent>;

Signal-based queries (Angular 17+)

Angular 17 introduced signal versions of all four query APIs. Instead of decorated properties that are populated by lifecycle hooks, they return Signals that automatically update whenever the DOM changes. The big advantage: no lifecycle timing issues — you can safely read the signal anywhere, and it's always current.

Decorator-based (before Angular 17)

import { ViewChild, ViewChildren, QueryList } from '@angular/core';   // decorator + collection TYPE — the classic (pre-17) query imports

export class OldSearchBar implements AfterViewInit {   // the lifecycle interface is REQUIRED to safely read either query below
  @ViewChild('input') input!: ElementRef;   // the ! promises TS it will be set — but only AFTER ngAfterViewInit runs
  @ViewChildren(OptionComponent) options!: QueryList<OptionComponent>;

  ngAfterViewInit() {
    // Must wait for this hook. If you access input in ngOnInit — undefined.
    this.input.nativeElement.focus();
    this.options.forEach(o => o.recalc());   // same QueryList.forEach() the earlier accordion example used
  }
}

Signal-based (Angular 17+)

import { viewChild, viewChildren } from '@angular/core';   // lowercase FUNCTIONS — not the uppercase @Decorators from the left panel

export class NewSearchBar {   // no `implements AfterViewInit` needed at all
  // Signal<ElementRef | undefined> — no lifecycle hook needed
  input = viewChild<ElementRef>('input');
  // Signal<readonly OptionComponent[]>
  options = viewChildren(OptionComponent);

  focusInput() {
    // Read the signal — always current, works from ngOnInit onward
    this.input()?.nativeElement.focus();   // input is a FUNCTION call now — ?. guards the brief window before the view exists
  }

  recalcOptions() {
    // viewChildren returns a plain readonly array (not a QueryList)
    this.options().forEach(o => o.recalc());   // no .changes Observable to subscribe to — just re-read the signal whenever you need it
  }
}
// All four signal query APIs — mirroring the four decorator APIs
import { viewChild, viewChildren, contentChild, contentChildren } from '@angular/core';

export class MyComponent {
  // @ViewChild equivalent — Signal<T | undefined>
  chart = viewChild<ChartComponent>(ChartComponent);
  // required() throws if undefined instead of returning undefined
  header = viewChild.required<ElementRef>('header');

  // @ViewChildren equivalent — Signal<readonly T[]>
  tabs = viewChildren(TabComponent);

  // @ContentChild equivalent
  icon = contentChild(IconComponent);

  // @ContentChildren equivalent
  items = contentChildren(ListItemComponent);

  // Use them as computed values — no lifecycle hook needed
  tabCount = computed(() => this.tabs().length);
}

The signal APIs return plain arrays for viewChildren/contentChildren — not a QueryList. You don't need to subscribe to a .changes observable; the signal reactivity system handles updates automatically. Signal queries are the modern recommendation for new Angular 17+ code.

Common real-world patterns

Focus an input on component open

@Component({
  template: `<input #search type="text" />`   // #search is a template ref variable — the string ViewChild matches on below
})
export class SearchDialogComponent implements AfterViewInit {
  @ViewChild('search') search!: ElementRef<HTMLInputElement>;   // typed generic — nativeElement is a real HTMLInputElement, not a bare Element

  ngAfterViewInit() {
    // Auto-focus the input when dialog opens
    setTimeout(() => this.search.nativeElement.focus());
    // setTimeout defers past the current CD cycle — avoids ExpressionChangedError
  }
}

Call a method on a child component

@Component({
  template: `<app-video-player #player [src]="url"></app-video-player>
             <button (click)="player.pause()">Pause</button>`   // the template itself can also call player.pause() directly, no class method needed
})
export class VideoPageComponent implements AfterViewInit {
  @ViewChild('player') player!: VideoPlayerComponent;   // typed as the COMPONENT class — every public member is callable from TS too
  url = '/video/intro.mp4';

  skipToEnd() {
    // Call methods on the child directly via ViewChild
    this.player.seekTo(this.player.duration);   // reads a PROPERTY (duration) and calls a METHOD (seekTo) on the same child instance
  }
}

Measure DOM element dimensions

export class ResponsiveChartComponent implements AfterViewInit {
  @ViewChild('container') container!: ElementRef<HTMLDivElement>;
  width = 0;
  height = 0;

  ngAfterViewInit() {
    const rect = this.container.nativeElement.getBoundingClientRect();   // real layout numbers — only meaningful once the view exists
    this.width  = rect.width;
    this.height = rect.height;
    this.drawChart(this.width, this.height);   // the ONE-TIME initial draw

    // Keep re-measuring on resize
    const ro = new ResizeObserver(entries => {   // a native browser API — nothing Angular-specific about it
      this.width  = entries[0].contentRect.width;
      this.height = entries[0].contentRect.height;
    });
    ro.observe(this.container.nativeElement);   // watches the SAME element the ViewChild resolved above
  }
}

Access FormGroup via ContentChild

// A "card" wrapper that can read any form inside it
export class FormCardComponent implements AfterContentInit {
  @ContentChild(NgForm) form?: NgForm;   // optional (?) — a card might be used with no form projected into it at all

  ngAfterContentInit() {
    if (this.form) {   // guards against the "no form projected" case above
      // Subscribe to the projected form's validity changes
      this.form.statusChanges?.subscribe(status => {
        this.isValid = status === 'VALID';   // mirrors the CHILD form's status onto this wrapper component
      });
    }
  }
  isValid = false;
}

Common mistakes

Accessing @ViewChild in ngOnInit

Unless static: true, @ViewChild is undefined in ngOnInit. The view hasn't been built yet. Move DOM access to ngAfterViewInit.

Forgetting ? on conditional ViewChild

If the element could be inside *ngIf, declare the property with ? (optional): @ViewChild('x') x?: ElementRef. Otherwise TypeScript will complain and you'll get runtime errors when the condition is false.

Using QueryList as an array

QueryList is not an array — it doesn't have array methods like .map(). Use .toArray() to convert it, or use the signal viewChildren() which returns a real readonly array.

Not subscribing to QueryList.changes

If you do work in ngAfterViewInit based on the initial QueryList but then items get added/removed by *ngFor, your logic doesn't re-run. Subscribe to queryList.changes or switch to signal queries.

Modifying component state in ngAfterViewInit

Setting a component property in ngAfterViewInit that the template binds to causes ExpressionChangedAfterItHasBeenCheckedError. Wrap the change in setTimeout() or call cdr.detectChanges().

Mixing @ContentChild and @ViewChild up

@ViewChild queries the component's own template. @ContentChild queries content projected into it from the outside via <ng-content>. Using the wrong one returns undefined with no error message.
