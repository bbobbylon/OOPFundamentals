JWT Tokens — Anatomy & Validation

Every Entra ID auth flow produces JWT tokens. Learn to decode them, understand every claim, and know exactly how Spring Boot validates them.

1 — JWT Structure — Three Base64 Parts

A JWT is three base64url-encoded JSON objects joined by dots. Click each part to decode it:

Header — Algorithm & Key ID

alg
"RS256"
Signing algorithm: RSA + SHA-256. Asymmetric — Entra signs with its private key, Spring verifies with Entra's public key.
typ
"JWT"
Token type. Always JWT here.
kid
"-KYdh5..."
Key ID — which of Entra's public keys was used to sign this token. Spring fetches the matching key from the JWKS endpoint to verify.

Payload — Claims (the actual data)

aud
"api://c7a8e2f1..."
Audience — who this token is for. Must match your API's Client ID or App ID URI.
iss
"https://login.microsoftonline.com/{tenantId}/v2.0"
Issuer — who created this token. Spring validates this exactly.
exp
1717234567 (Unix timestamp)
Expiration time. Spring rejects expired tokens automatically.
iat
1717230967
Issued at time.
sub
"user-object-id-guid"
Subject — unique user identifier in this tenant. Stable across sessions.
oid
"user-object-id-guid"
Object ID — same as sub in most cases for Entra v2 tokens.
name
"Alice Johnson"
Display name from the user's profile.
preferred_username
"alice@company.com"
UPN — usually the email. Use for display, not as a stable identifier.
roles
["Admin", "ReadOnly"]
App roles assigned to this user. In Spring: APPROLE_Admin authority.
scp
"Users.Read Users.Write"
Scopes granted — what the app requested and the user consented to.
tid
"a1b2c3d4-e5f6..."
Tenant ID — which Entra directory this user belongs to.

Highlighted rows are the ones Spring Boot validates automatically when configured as a Resource Server.

Signature — Tamper Protection

The signature is computed as:

Base64UrlEncode( RSA_SHA256_Sign( privateKey, base64url(header) + "." + base64url(payload) ) )

Entra ID signs with its private key (which only Entra holds).
Spring Boot verifies with Entra's public key (fetched from the JWKS endpoint).

If any character in the header or payload is modified after signing, the signature check fails and Spring rejects the token with 401.

2 — How Spring Boot Validates an Incoming JWT

Click the check/fail icons to simulate what happens when each validation passes or fails:

✓
1. Extract JWT from Authorization header
Spring looks for Authorization: Bearer <token>. If missing: 401 Unauthorized.
✓
2. Parse and decode the three parts
Base64url-decode header and payload. Read the kid claim from the header to know which public key to use.
✓
3. Fetch public key from JWKS endpoint
Spring fetches https://login.microsoftonline.com/{tenant}/discovery/v2.0/keys and caches the result. Finds the key matching the kid. Keys are cached — not fetched on every request.
✓
4. Verify RSA signature
Cryptographically verifies the signature matches the header + payload using the public key. A tampered token fails here → 401.
✓
5. Validate issuer (iss claim)
Checks iss matches https://login.microsoftonline.com/{tenantId}/v2.0. Configured via issuer-uri in application.yml. Prevents accepting tokens from other tenants.
✓
6. Validate audience (aud claim)
Checks aud contains your API's Client ID or App ID URI. Prevents your token from being replayed against a different API. Configured via audiences property.
✓
7. Check expiration (exp claim)
Compares exp to current time. If expired: 401. Access tokens from Entra typically expire in 1 hour.
✓
8. Map claims to Spring Security authorities
App roles from roles claim → APPROLE_Admin authorities. Scopes from scp → SCOPE_Users.Read authorities. These are what @PreAuthorize checks against.

3 — Reading Claims in Spring Boot

// Access JWT claims in your controller @GetMapping("/api/me") public Map<String, Object> me(@AuthenticationPrincipal Jwt jwt) { String userId = jwt.getSubject(); String email = jwt.getClaimAsString("preferred_username"); List<String> roles = jwt.getClaimAsStringList("roles"); return Map.of("userId", userId, "email", email, "roles", roles); } // Protect endpoints by scope or app role @PreAuthorize("hasAuthority('SCOPE_Users.Read')") @GetMapping("/api/users") public List<User> getUsers() { ... } @PreAuthorize("hasAuthority('APPROLE_Admin')") @DeleteMapping("/api/users/{id}") public void deleteUser(@PathVariable Long id) { ... }

4 — Access Token vs ID Token vs Refresh Token

TokenPurposeAudienceLifespan
Access Token Authorize API calls. Sent in Authorization header. Your API (aud = API client ID) ~1 hour
ID Token Authenticate the user. Contains user profile info. For the frontend only. Your SPA (aud = Angular client ID) ~1 hour
Refresh Token Get new access/ID tokens without re-prompting the user. MSAL manages this silently. Entra token endpoint 24h–90 days (depends on policy)

Key rule: The Access Token goes to your API. The ID Token stays in the frontend (Angular) for displaying user info. Never send the ID Token to your API — Spring Boot validates aud, and the ID Token has the wrong audience.
