Python: Structural Pattern Matching

match/case (Python 3.10+) — not a switch, but structural destructuring: literal, capture, sequence, mapping, and class patterns, plus guards — and the capture gotcha that bites everyone.

🪢 match/case looks like a switch but is really destructuring + dispatch

Python 3.10's match/case is not a C-style switch — it's structural pattern matching. Each case is a pattern tested against the subject's shape that can destructure and bind values in one step; the first match wins, no fall-through, case _ is the default. Patterns include literals/OR (case 401 | 403:), sequence (case [first, *rest]:), mapping (case {"type": t}: — partial, extra keys OK), and class (case Point(x=0):), plus guards (case n if n > 0:). The infamous trap: a bare name captures everything — use a literal, dotted name, or guard to compare against a constant.

  • Shape matching, not value switch — destructure + bind in one step.
  • Pattern kinds: literal/OR, sequence, mapping, class — plus guards.
  • Mapping patterns are partial — extra keys are fine.
  • A bare name captures everything — use literals/dotted names/guards to compare.

Literal · OR · wildcard

match status: case 200: ok() case 401 | 403: denied() case int() if status >= 500: retry() case _: unknown() # default

Destructure dicts/objects

# map a token claim shape to roles match claims: case {"realm_access": {"roles": rs}}: return rs # keycloak case {"roles": rs}: return rs # entra case {"scp": scp}: return scp.split() # spring

vs switch / if-elif

C/Java switch: value equality + fall-through; no destructuring. match: shape matching + binding, no fall-through. if/elif: still better for simple value checks or complex boolean logic. Reach for match when you'd otherwise write nested isinstance + index/.get checks to pull a structure apart.

CIAM context: Mapping patterns cleanly normalize IdM claim shapes — one match over the token payload maps Keycloak's realm_access.roles, Entra's roles, and Spring's scp to your authority list. But heed the capture gotcha: case role: (a bare name) matches any token and binds it — a silent "allow everything." Compare against constants with literals, dotted enum names, or guards.

You already know the bare-name capture trap. This one is sneakier: it only shows up when your patterns are all perfectly correct literals.

The problem

Two case clauses, both spelled exactly right, no bare-name capture in sight — and the wrong one still wins, because Python compares some literals differently than others.

An MFA check that silently treats "verified" as "legacy"

Your IdP mostly sends mfa_verified as a real JSON boolean, but a legacy sync job still writes the field as the integer 1/0 from years ago. You handle both, oldest case first, the way you'd order any "specific to general" match:

match claims.get("mfa_verified"):
  case 1:
    log.info("legacy int flag")
  case True:
    log.info("modern boolean flag")

This looks harmless while both branches do the same thing — until someone adds a THIRD case above case True: for "legacy int, needs a re-sync warning," expecting it to only ever catch the literal integer. It also silently catches every modern boolean True, because case 1: tests subject == 1, and in Python True == 1. case True: below it never even runs for a boolean subject — case 1: already claimed it.

case 1: spelled correctly ✓ case True: spelled correctly ✓ which comparison operator each one secretly uses ⚠

Neither pattern is wrong. Their comparison rules just aren't the same rule.

Put the singleton patterns first, or check the type explicitly
List case True: / case False: / case None: before any numeric literal case ↓ is-based patterns matched first can't be shadowed by a later ==-based one Or guard the numeric case: case 1 if isinstance(subject, int) and not isinstance(subject, bool): ↓ makes the "actual integer, not a bool" requirement explicit instead of implicit Best: normalize the claim to one type (always bool) before it ever reaches match
Literal patterns don't all use the same comparison. Python's match statement uses is specifically for the three singleton patterns — None, True, False — and == for every other literal (numbers, strings). The is rule exists so that case True: can never be confused with numeric equality; it says nothing about protecting a numeric pattern from a boolean subject, because bool is a subclass of int in Python and True == 1 has always been true.
Think of case True: as a bouncer checking a photo ID, and case 1: as a bouncer just checking a number written on a wristband. True's wristband happens to say "1" — so the numeric bouncer waves it through without ever glancing at the photo the identity-based bouncer further down the line would have caught.
You

I put my int case above my bool case because ints felt more "specific." Why did the bool value get swallowed by the int case?

The match statement

case 1: isn't a singleton pattern, so I compare with ==. Your subject was True, and True == 1 — that's just how Python's bool works, it's a subclass of int. I matched, so I never even looked at your case True:.

You

But you use is for True elsewhere — why not protect me here too?

The match statement

The is rule protects case True: itself from matching an unrelated 1 — it guarantees that pattern only fires for the real singleton. It was never designed to stop a numeric pattern from matching a boolean subject; that's == doing exactly what == has always done in Python.

The mechanism

Watch the same subject hit the two case orderings and get two different outcomes.

  1. Subject is the boolean True (a real JSON boolean from a modern IdP)subject
  2. case 1: is not None/True/False, so Python tests True == 1== path
  3. bool is a subclass of int; True == 1 evaluates to Truematches
  4. First match wins — case 1:'s body runs, no fall-through to later casesfirst match wins
  5. case True: below is never reached for this subject at alldead for booleans
  6. Reorder so case True: comes first: Python tests True is True — matches immediately, correctly, every timethe fix

Step 3 is the only fact you need to memorize: bool being an int subclass isn't a match-statement quirk, it's ordinary Python that's been true since bool was added to the language — match just inherits it because ==-based literal patterns are, underneath, exactly the equality you already know.

case 1: listed first subject True arrives → True == 1, matches — wrong branch for a real boolean
case True: listed first subject True arrives → True is True, matches — correct
case True: listed first subject 1 arrives → 1 is True is False, falls through to case 1 — also correct

Putting the identity-based pattern first costs you nothing: an actual integer subject still correctly falls through to the numeric case, because is is stricter than ==, never looser. The only ordering that loses information is numeric-before-boolean.

Order isn't automatic here — patterns are still tried top to bottom exactly as written. There's no special reordering that promotes singleton patterns above numeric ones.

match never raises for two patterns that could both apply — it just takes the first one that matches and stops looking. No ambiguity error exists in the language.

Exactly — case 0: isn't a singleton pattern so it compares with ==, and False == 0 is True in Python. First match wins, so "zero" is returned and case False: is dead code for this input.

Where you have seen this before

"Two comparison rules living under one operator" trips people up well beyond match statements.

SQL's = TRUE vs a bit column

Databases that store booleans as TINYINT/BIT have the same collision — WHERE flag = 1 and WHERE flag = TRUE can silently mean the same query on some engines and different ones on others, for the identical "boolean is secretly a number" reason.

a boolean that's really a number underneath

JavaScript's == vs ===

1 == true is true in JS for the same underlying reason — a loose equality that coerces types — while 1 === true is false. Python's match doesn't have a "strict operator" toggle per case; the strictness is baked into which literal you wrote.

loose vs strict equality, same trap, no toggle in Python

Java's Integer.equals(Boolean) — always false, but for the opposite reason

Java refuses to let unrelated boxed types compare equal, which is the safety net Python's bool-is-an-int design deliberately doesn't have — the price of Python's convenience is exactly this kind of silent cross-type match.

the safety net one language has and the other trades away

1. Literal, OR & Wildcard

match command.split():
  case ["go", ("north" | "south") as dir]:
    move(dir)
  case ["quit" | "exit"]:
    stop()
  case _:
    unknown() # wildcard default

Literal patterns match by value (case 200:, case "GET":, case None:). The | combines alternatives (case 401 | 403:). case _: is the wildcard — matches anything, binds nothing, the default. There's no fall-through (no break needed) and the first matching case wins, so order from specific to general. as binds a sub-pattern's value (("north"|"south") as dir).

match is an expression-shaped statement, not exhaustive. If nothing matches and there's no case _, the block simply does nothing (no error) — so add a wildcard (or raise) when you expect total coverage. Unlike some languages, Python won't warn you about a missing case.

2. Capture & Sequence Patterns — and THE Gotcha

match point:
  case [0, 0]: # exact
    origin()
  case [x, y]: # binds x, y
    plot(x, y)
  case [first, *rest]: # star captures the tail
    head(first, rest)

# GOTCHA: a bare name ALWAYS matches + binds
case status: # NOT "== status"; matches everything!

A capture pattern binds the subject (or sub-part) to a name. Sequence patterns destructure lists/tuples positionally ([a, b]), with *rest grabbing the remainder. The trap: a bare lowercase name is always a capture, not a comparison — case status: matches any value and shadows whatever status meant before. To compare against an existing constant, use a dotted name (case HTTPStatus.OK:), a literal, or a guard (case s if s == status:).

This gotcha is a real security footgun. Writing case ADMIN: hoping to compare to a constant instead binds a variable named ADMIN and matches every input — a silent "allow all." Constants used in patterns must be dotted (enum/namespace) so Python treats them as value patterns, not captures.

3. Mapping Patterns

match event:
  case {"type": "login", "user": u}:
    audit_login(u)
  case {"type": "role_change", "to": role, **extra}:
    audit_role(role, extra)
  case {"type": t}:
    log_other(t)

Mapping patterns match dict keys and bind their values. They are a partial match: {"type": "login", "user": u} requires those keys but ignores any others (no need to list every field) — perfect for JSON/event payloads. **rest captures the remaining key/value pairs. Combine literal values (to match a discriminator like "type") with captures (to extract the data you need).

Mapping patterns are "open" by default — extra keys don't break the match. That's the opposite of sequence patterns, which match length exactly (use *rest to allow extra elements). This makes match ideal for evolving JSON where new fields appear over time.

4. Class Patterns & Guards

from dataclasses import dataclass
@dataclass
class User: name: str; role: str

match principal:
  case User(role="admin"): # type + attr value
    grant_all()
  case User(name=n) if n.startswith("svc-"): # guard
    service_account(n)
  case User():
    normal()

Class patterns match an instance's type and its attributes: User(role="admin") matches a User whose role equals "admin"; User(name=n) captures the attribute into n. Positional class patterns (Point(0, y)) need __match_args__ on the class (dataclasses define it automatically). A guard (if ...) adds an arbitrary condition the pattern must also satisfy — checked after the structural match.

Use match for structure, if/elif for plain conditions. When you're destructuring nested data or dispatching on type+shape (parsers, ASTs, event routers, claim mappers), match is dramatically clearer than nested isinstance/index checks. For a single value compared a few ways, or rich boolean logic, a plain if/elif (or a dict dispatch) is the better tool.
