tsconfig.json — Deep Dive: Every Compiler Option Explained

⚙️ What are advanced TypeScript compiler options — and how does the tsconfig extends chain keep Angular app, test, and library configs aligned?

Beyond the basics, TypeScript's compiler options contain powerful settings that determine how strictly types are checked, how modules are resolved, and how the compiled output behaves. Angular projects use a tsconfig extends chain: tsconfig.json (base workspace settings) is extended by tsconfig.app.json (adds include: ["src"] and Angular-specific options for the production build) and by tsconfig.spec.json (adds test file includes and Jasmine type definitions). Each child inherits ALL base options and can override or extend them. Type checking options: noUnusedLocals and noUnusedParameters — errors on variables or function parameters that are declared but never used. Catches dead code before it accumulates. noImplicitReturns — every code path in a function must explicitly return a value (no implicit undefined). noFallthroughCasesInSwitch — switch case fallthrough is an error (must have explicit break/return). Module resolution: "moduleResolution": "bundler" (Angular 17+ with esbuild) is the modern mode — it understands that a bundler (not Node's require()) will handle imports, enabling cleaner import syntax. "moduleResolution": "node16" requires explicit file extensions in imports (matches what Node.js 16+ actually needs). Project references: for monorepos, TypeScript project references ("references": [{ "path": "../my-lib" }]) let the compiler build and type-check multi-package projects incrementally — only rebuilding what changed. lib: declares what built-in type definitions are available. ["ES2022", "dom"] = ES2022 language features + browser DOM types. Add "dom.iterable" for NodeList.forEach(). "WebWorker" for Web Worker globals. Incremental compilation: "incremental": true + "tsBuildInfoFile" caches build information — subsequent compilations are much faster by only recompiling changed files.

tsconfig extends chain

// tsconfig.json (base — workspace-wide): { "compilerOptions": { "strict": true, ... } // No "include" — each child controls files } // tsconfig.app.json (for ng build): { "extends": "./tsconfig.json", // inherit base "compilerOptions": { "outDir": "./dist/out-tsc", "types": [] // no @types/jasmine in prod build }, "files": [ "src/main.ts" ], "include": ["src/**/*.d.ts"] } // tsconfig.spec.json (for ng test): { "extends": "./tsconfig.json", // inherit base "compilerOptions": { "outDir": "./dist/out-tsc", "types": ["jasmine"] // add Jasmine types }, "include": [ "src/**/*.spec.ts", // test files "src/**/*.d.ts" ] }

Key strict options

// What "strict": true enables: { "strict": true, // Includes all of these: "strictNullChecks": true, // null/undefined not assignable to other types "noImplicitAny": true, // Must declare type — 'any' must be explicit "strictFunctionTypes": true, // Function param types checked covariantly "strictBindCallApply": true, // .bind() .call() .apply() are type-checked "strictPropertyInitialization": true, // Class properties must be init in constructor // (or use ! assertion: user!: User) "noImplicitThis": true, // 'this' expressions must have known type // Additional (not in strict bundle): "noUnusedLocals": true, // Error on declared-but-never-used variables "noUnusedParameters": true, // Error on unused function parameters "noImplicitReturns": true // Every code path must explicitly return }

// moduleResolution controls how imports are resolved: // "bundler" (Angular 17+ / esbuild): "moduleResolution": "bundler" // For esbuild/webpack/Vite bundled apps // Allows: import { x } from 'rxjs' // Bundler handles actual file resolution // RECOMMENDED for Angular 17+ // "node16" (for Node.js apps): "moduleResolution": "node16" // Requires: import { x } from 'rxjs/index.js' // Explicit .js extension required // Matches Node 16+'s actual resolution // "node" (legacy): "moduleResolution": "node" // Old Node-style CJS resolution // Works but doesn't understand ESM package exports // Avoid for new projects // "classic" (very old): // TypeScript's own made-up resolution // Never use — only exists for old codebases // Angular-specific: // module + moduleResolution must be compatible: // module: "ES2022" → moduleResolution: "bundler"

In CIAM / Context: The CIAM app's tsconfig extends chain: base (strict=true, strictTemplates=true, noUnusedLocals, paths aliases) → app (includes src/main.ts, no jasmine types) → spec (includes *.spec.ts, adds jasmine + jest types). The spec tsconfig allows @ts-expect-error for mock objects that don't implement full interfaces. incremental=true in the CI pipeline caches .tsbuildinfo between runs, making type-checking 2-3x faster on repeat builds with small changes.

tsconfig Hierarchy — Extends Chains

Angular projects ship with three tsconfig files that form an extends chain. Each child file inherits all options from its parent and can override or add to them. This keeps compiler options DRY while letting different parts of the build have different settings.

tsconfig.json base
Root of the chain. Contains shared options: strict settings, module resolution, paths aliases, and decorator flags. The "files":[] and "include":[] are deliberately empty — it only supplies compiler options.
// tsconfig.json
{
  "compilerOptions": {
    "target": "ES2022",
    "module": "ES2022",
    "moduleResolution": "bundler",
    "strict": true,
    "noImplicitOverride": true,
    "noPropertyAccessFromIndexSignature": true,
    "experimentalDecorators": true,
    "useDefineForClassFields": false,
    "baseUrl": "",
    "paths": { "@app/*": ["src/app/*"], "@shared/*": ["src/shared/*"] }
  },
  "files": []  // intentionally empty — child configs include files
}
↓ extends
tsconfig.app.json Angular build
Extends the base. Used by ng build and ng serve. Includes application source files only (src/**/*.ts). Excludes test files.
// tsconfig.app.json
{
  "extends": "./tsconfig.json",
  "compilerOptions": {
    "outDir": "./out-tsc/app",
    "types": []           // no @types injected for app code
  },
  "files": [
    "src/main.ts"         // only entry points; Angular CLI finds the rest
  ],
  "exclude": ["src/**/*.spec.ts"]
}
↓ extends
tsconfig.spec.json test code
Extends the base. Used by ng test (Karma / Jest). Includes spec files. Adds @types for jasmine or jest so test globals (describe, it, expect) are recognised.
// tsconfig.spec.json
{
  "extends": "./tsconfig.json",
  "compilerOptions": {
    "outDir": "./out-tsc/spec",
    "types": ["jasmine"]    // or ["jest"] if using Jest
  },
  "include": [
    "src/**/*.spec.ts",
    "src/**/*.d.ts"
  ]
}

How "extends" merging works

Child options override parent options at the property level. Arrays are not merged — a child "types":["jasmine"] completely replaces any parent "types" value. Only object properties inside compilerOptions are merged key-by-key.

PropertyMerge behaviourExample
compilerOptions.*Child overrides parent key-by-keychild strict:false overrides parent strict:true
include / exclude / filesChild completely replaces parentparent include:[] has no effect when child sets it
referencesChild completely replaces parentusually only set on root tsconfig

Type Checking Options

These options control how strictly TypeScript checks your code. strict: true is the master switch that enables most of them simultaneously. Understanding each one individually lets you know exactly what protection you have.

strict: true recommended

Master switch. Equivalent to turning on: strictNullChecks, strictFunctionTypes, strictBindCallApply, strictPropertyInitialization, noImplicitAny, noImplicitThis, alwaysStrict, useUnknownInCatchVariables. Set this and forget — unless you need a specific escape hatch.

// Without strict — TypeScript is basically JavaScript with suggestions
function greet(name) {        // name is implicitly 'any'
  return "Hello, " + name.toUpperCase();
}
greet(null);                  // runtime crash — TypeScript said nothing

// With strict — caught at compile time
function greet(name: string): string {
  return "Hello, " + name.toUpperCase();
}
greet(null);   // Error: Argument of type 'null' is not assignable to parameter of type 'string'
strictNullChecks
default: true (with strict)type: boolean
null and undefined are their own types — they cannot be assigned to string, number, etc.

Without this, every type implicitly includes null and undefined — which is the source of the majority of runtime crashes in JS. With it, you must check for null before using a value.

// strictNullChecks: false
let s: string = null;     // OK — dangerous!
s.length;                 // runtime crash

// strictNullChecks: true
let s: string = null;     // Error!
let s: string | null = null; // OK — explicit
if (s !== null) s.length; // safe access
strictFunctionTypes
default: true (with strict)type: boolean
Enforces contravariance for function parameter types instead of bivariance.

Bivariance (the default without this flag) allows unsound assignments. Contravariance is the mathematically correct rule: a function accepting a base type can replace a function accepting a derived type, but not the reverse.

type Handler = (e: MouseEvent) => void;
type AnyHandler = (e: Event) => void;

// Without strictFunctionTypes (bivariant) — both are OK
const h: Handler = (e: Event) => {}; // allowed — but wrong!

// With strictFunctionTypes (contravariant)
const h: Handler = (e: MouseEvent) => {}; // OK
const h: AnyHandler = (e: MouseEvent) => {}; // Error — too specific
strictPropertyInitialization
default: true (with strict)type: boolean
Class properties must be assigned a value in the constructor (or be optional).
class User {
  name: string;          // Error: not initialized
  email!: string;        // OK — definite assignment assertion
  role: string = 'user'; // OK — initialized inline
  age: number | undefined; // OK — undefined is explicit

  constructor(name: string) {
    this.name = name;     // OK — assigned in constructor
  }
}

// Angular uses ! for @Input() and @ViewChild() which are set by Angular, not constructor
@Input() title!: string;
@ViewChild('canvas') canvas!: ElementRef;
noImplicitAny
default: true (with strict)type: boolean
Error when TypeScript can only infer 'any' for a value — force you to annotate it.
// noImplicitAny: false — silent any everywhere
function process(data) {    // data: any (implicit)
  return data.whatever;     // no error
}

// noImplicitAny: true — must be explicit
function process(data: unknown) { // explicit
  if (typeof data === 'object') { ... }
}
function process(data: any) { // explicit any is still allowed
  return data.whatever;
}
exactOptionalPropertyTypes
default: falsetype: boolean
Distinguishes "property absent" from "property explicitly set to undefined".
interface Config {
  theme?: 'dark' | 'light';
}

// Without exactOptionalPropertyTypes
const c: Config = { theme: undefined }; // OK — but theme is "absent"?

// With exactOptionalPropertyTypes: true
const c: Config = { theme: undefined }; // Error!
const c: Config = {};                    // OK — absent
const c: Config = { theme: 'dark' };   // OK — present
useUnknownInCatchVariables
default: true (with strict)type: boolean
catch(e) binds e as unknown instead of any — forces you to check the error type.
// Before (e is 'any' — dangerous)
try { ... } catch (e) {
  console.log(e.message);   // no error — e could be anything
}

// With useUnknownInCatchVariables: true
try { ... } catch (e) {
  console.log(e.message);   // Error: 'e' is of type 'unknown'
  if (e instanceof Error) {
    console.log(e.message); // OK — narrowed
  }
}
noImplicitOverride
default: falsetype: boolean
Methods in subclasses that override base class methods must use the 'override' keyword.
class Base {
  process() { ... }
}
class Child extends Base {
  process() { ... }          // Error: must use 'override'
  override process() { ... } // OK
  override missing() { ... } // Error: base has no 'missing'
}
noPropertyAccessFromIndexSignature
default: falsetype: boolean
Forces bracket notation when accessing properties that come from an index signature.
interface Dict { [key: string]: string; }

const d: Dict = { foo: 'bar' };
d.foo;         // Error: use bracket notation for index signatures
d['foo'];      // OK — makes the "dynamic" access explicit

Module Resolution Options

These options control how TypeScript resolves import statements to actual files on disk, and how it emits module code. Getting these right is especially important in Angular 17+ with esbuild.

moduleResolution — The Big Three

moduleResolution: "node"
legacy
Old CommonJS-based algorithm. Looks in node_modules, no ESM interop. Used by older projects.

Mimics Node.js pre-12 resolution. No support for package.json exports field, no .js extension handling for relative imports. Avoid in new projects.

// Works with "node":
import { x } from 'some-package'; // resolves index.js via "main" field
import { y } from './utils';      // tries utils.ts, utils/index.ts
moduleResolution: "node16"
ESM/CJS interop
Node.js 16+ algorithm with ESM support. Requires explicit .js extensions on relative imports.
// With "node16" you must write the .js extension (even for .ts files):
import { x } from './utils.js';  // correct — .js not .ts
import { y } from './utils';    // Error in node16 mode
moduleResolution: "bundler"
Angular 16+ / esbuild
Modern bundler-aware resolution. Supports package.json exports, no .js extension requirement. Best choice for Angular with esbuild or Vite.

Designed for tools like esbuild, Vite, and Webpack. Understands package.json exports map (sub-path exports, conditional exports). You write imports without extensions like in Node. Angular CLI 16+ sets this automatically.

// "bundler" — no extension required, exports map respected
import { x } from './utils';          // OK
import { y } from 'lodash/array';     // sub-path export
import data  from './data.json';      // with resolveJsonModule

esModuleInterop & allowSyntheticDefaultImports

esModuleInterop: true

Emits helper code that lets you use default-import syntax with CommonJS modules that don't have a proper default export. Automatically enables allowSyntheticDefaultImports.

// Without esModuleInterop (old way)
import * as path from 'path';

// With esModuleInterop (clean)
import path from 'path';
allowSyntheticDefaultImports: true

Type-checking only version — allows the default-import syntax at the TS level without emitting any runtime helper code. Use this when your bundler already handles the interop (like esbuild).

// allowSyntheticDefaultImports — TS is happy, bundler does the work
import React from 'react';   // OK at TS level
// No helper __esImportDefault emitted

Path Aliases — paths & baseUrl

Path aliases let you write clean, refactor-safe imports instead of brittle relative paths like ../../shared/utils.

// tsconfig.json
{
  "compilerOptions": {
    "baseUrl": "",          // must be set when using paths
    "paths": {
      "@app/*":    ["src/app/*"],
      "@shared/*": ["src/shared/*"],
      "@env/*":    ["src/environments/*"]
    }
  }
}
// Usage in code — clean, absolute-looking imports
import { UserService } from '@app/services/user.service';
import { formatDate }  from '@shared/utils/date';
Important — angular.json also needs this for esbuild: 
// angular.json → projects → app → architect → build → options
{
  "plugins": [
    {
      "plugin": "@ng-tools/esbuild-plugin-paths",
      "options": { "paths": { "@app/*": ["src/app/*"] } }
    }
  ]
}

TypeScript knows about paths at compile time. But esbuild runs separately and needs its own path alias configuration. For Angular 16+ with the application builder, use the built-in tsconfig paths support — the Angular CLI reads tsconfig paths and passes them to esbuild automatically.

resolveJsonModule

// tsconfig.json
{ "resolveJsonModule": true }

// Now valid TypeScript:
import config from './config.json';   // typed as the JSON's shape
import pkg    from '../package.json'; // access pkg.version etc.
console.log(pkg.version);              // string — fully typed

Output & Target Options

These control what JavaScript TypeScript emits and which built-in types are available to your code.

target — Compilation Target vs Browser Support

The target option tells TypeScript which JS syntax to downcompile (transform into older equivalent code). Syntax not supported by the target gets transformed; everything else is passed through as-is.

lib — Available Built-in Types

lib controls which TypeScript type definitions for built-in JavaScript APIs are included. If you use Promise but don't include "ES2015.Promise" in lib, TypeScript will error. The "ES2022" lib includes all stable APIs up to ES2022.

// Typical Angular app (tsconfig.json)
{
  "lib": ["ES2022", "DOM", "DOM.Iterable"]
}
// "ES2022" — Promise, Map, Set, Symbol, Array.from, String.replaceAll, etc.
// "DOM"    — window, document, HTMLElement, fetch, etc.
// "DOM.Iterable" — for...of on NodeList, HTMLCollection

Project References & Composite Builds

For large projects or monorepos, TypeScript's project references enable incremental compilation — only recompile changed packages. Angular workspaces with multiple apps or libraries use this automatically.

composite: true

Required on any tsconfig that is referenced by another. Enables three things:

  • Builds .tsbuildinfo file: stores the build fingerprint for fast incremental detection
  • Enforces declaration:true: referenced projects must emit type declarations
  • Requires explicit files/include: the set of input files must be deterministic
// tsconfig.lib.json (in a library project)
{
  "extends": "./tsconfig.json",
  "compilerOptions": {
    "composite": true,
    "declaration": true,
    "outDir": "./dist"
  },
  "include": ["src/**/*.ts"]
}

references — The Dependency Graph

In the root tsconfig.json (or the app tsconfig.app.json), list other tsconfigs this project depends on. TypeScript builds them first, in order, and uses their cached .d.ts output.

// Root tsconfig.json in a monorepo
{
  "files": [],
  "references": [
    { "path": "./packages/shared/tsconfig.lib.json" },
    { "path": "./packages/ui/tsconfig.lib.json" },
    { "path": "./apps/admin/tsconfig.app.json" }
  ]
}
// Build only what changed:
npx tsc --build            // builds all referenced projects in order
npx tsc --build --verbose  // shows what was rebuilt vs skipped
npx tsc --build --force   // force rebuild everything
npx tsc --build --clean   // delete all build artifacts

Angular Library Setup (ng-packagr)

When you run ng generate library my-lib, Angular creates a separate project with its own tsconfig.lib.json. The library is built with ng-packagr into the Angular Package Format (APF) — a structure with ESM and CJS outputs plus type declarations.

// projects/my-lib/tsconfig.lib.json (generated by Angular CLI)
{
  "extends": "../../tsconfig.json",
  "compilerOptions": {
    "outDir": "../../out-tsc/lib",
    "declaration": true,
    "declarationMap": true,
    "inlineSources": true
  },
  "exclude": ["**/*.spec.ts"]
}

Angular-Specific TypeScript Options

These three options are unique to Angular's decorator system. They exist because Angular's legacy decorators predate the TC39 standard proposal and have different semantics.

experimentalDecorators: true required by Angular legacy

Enables the Stage-2 TypeScript decorator syntax — the @Component, @Injectable, @Input, @Output, @ViewChild decorators Angular uses today. Without this, TypeScript rejects all decorator syntax.

// These decorators only work with experimentalDecorators: true
@Component({ selector: 'app-root', template: '...' })
export class AppComponent { ... }

@Injectable({ providedIn: 'root' })
export class UserService { ... }

emitDecoratorMetadata: true DI metadata

Emits runtime type metadata when decorators are present. Angular's Dependency Injection uses this to know the types of a constructor's parameters — so it can inject the right services automatically.

// Without emitDecoratorMetadata, Angular can't figure out what to inject:
@Injectable()
export class UserService {
  constructor(private http: HttpClient) {  // Angular needs to know "inject HttpClient"
  }
}
// With emitDecoratorMetadata, TypeScript emits:
// Reflect.metadata("design:paramtypes", [HttpClient])
// Angular's DI reads this metadata to resolve the dependency.
Note: Angular 14+ with inject() function doesn't need this — metadata is captured differently. Angular 17+ with standalone and signals-based DI is gradually moving away from metadata.

useDefineForClassFields: false decorator compat

TC39 class fields use Object.defineProperty semantics (define). Angular's legacy decorators were designed around TypeScript's older assign semantics. Setting this to false keeps the old behaviour Angular depends on.

// useDefineForClassFields: true (TC39 standard, ES2022 target)
class MyComponent {
  @Input() title = 'default';  // PROBLEM: defineProperty OVERWRITES decorator metadata
}

// useDefineForClassFields: false (Angular's requirement)
class MyComponent {
  @Input() title = 'default';  // OK: assign semantics, decorator runs correctly
}
Future: TC39 Stage 3 decorators use defineProperty and don't need these three flags. Angular will eventually support Stage 3 decorators and these options will become unnecessary. Angular 17+ can optionally use signal inputs (input()) instead of @Input() which avoids the issue entirely.
