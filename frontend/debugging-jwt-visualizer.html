Debugging JWTs — decode & diagnose

When auth misbehaves, the token usually holds the answer. A JWT is just three base64url chunks — header.payload.signature — so you can decode and read it instantly, without any key. But decoding is not validating: a resource server runs a checklist (algorithm, signature, exp, nbf, iss, aud), and the first check that fails is your bug.

🐛 What is a JWT — and how do you decode and debug a token that's failing validation?

JWT (JSON Web Token) is the standard format for stateless bearer tokens. When your Spring Boot resource server receives an HTTP request with Authorization: Bearer eyJ..., it must validate that token — and when it rejects it, you need to understand WHY. The good news: JWTs are not encrypted by default — they're base64url-encoded. You can decode them instantly in jwt.io or with echo 'eyJ...' | base64 -d. Structure: three parts separated by dots. Header: {"alg":"RS256","kid":"abc123","typ":"JWT"} — tells you the signing algorithm (RS256 = RSA + SHA-256, most common; HS256 = HMAC-SHA256) and the key ID (which signing key to look up in JWKS). Payload: the claims — sub (subject = user ID), iss (issuer = who issued this token: Ping's URL), aud (audience = who this token is for: your API's identifier), exp (expiration: Unix timestamp), nbf (not before: token not valid before this time), iat (issued at), plus custom claims like roles, email. Signature: base64url(RSASHA256(header + "." + payload, privateKey)) — validated with the public key from JWKS. Validation checklist (Spring Boot OAuth2 Resource Server does all of this): (1) Can signature be verified with JWKS public key? (2) Has exp passed? (3) Is nbf in the future? (4) Does iss match configured issuer? (5) Does aud contain expected audience? If ANY check fails → 401. The first failing check is your bug. When debugging: decode the token, check each claim manually against what Spring Security expects. Most common issues: exp in the past (clock skew or long-lived test token), iss mismatch (dev Ping URL vs prod URL), aud missing or wrong (API identifier not in token audiences).

Common JWT failures

401 in prod, works in dev: decode exp — token from dev has dev Ping issuer (ping-dev.co), prod Spring Security expects prod issuer (ping.co). → iss mismatch. 401 right after login: exp decoded → Unix timestamp 10 seconds ago. Clock skew between Ping server and your API server. → Allow clock skew: @Bean JwtDecoder jwtDecoder() { NimbusJwtDecoder d = ...; d.setClockSkew(Duration.ofSeconds(30)); return d; }. Signature validation fails despite correct token: wrong JWKS URL, or Ping rolled a new signing key and your app hasn't refreshed the JWKS cache yet. → Restart app or hit JWKS endpoint to verify keys. Claims missing from token: Ping scope configuration — roles claim only included if the OAuth scope requests it. → Check Ping token manager scope settings. Works in curl, fails in Angular: not a JWT issue — likely CORS (preflight OPTIONS blocks the request before JWT even sent) or the frontend is sending the wrong token (ID token vs access token).

Debugging CIAM JWTs: Workflow: user reports 401 on CIAM API. Step 1: grab the token from the browser Network tab (Authorization header) or ask the dev to console.log(token). Step 2: decode at jwt.io — check iss (matches Spring config?), exp (not expired?), aud (contains your API identifier?), roles (has expected roles?). Step 3: if all claims look correct, the signature might be invalid — verify the JWKS endpoint is accessible from the API server: curl https://ping.mycompany.com/.well-known/jwks.json | jq '.keys[] | select(.kid=="abc123")'. Step 4: enable logging.level.org.springframework.security=DEBUG in a test environment — Spring logs exactly which validation step failed: "JWT expired", "Invalid issuer", "Invalid audience". Step 5: check Entra vs Ping token format — Entra tokens have oid instead of sub, different issuer format (https://login.microsoftonline.com/{tenantId}/v2.0). Your custom JwtAuthenticationConverter must handle both.

1. Decode vs validate — don't confuse them

// three dot-separated base64url parts
eyJhbGciOiJSUzI1NiIsImtpZCI6ImsxIn0   . ← header  {alg, kid}
eyJzdWIiOiJhbGljZSIsImF1ZCI6ImR…     . ← payload {sub, aud, exp, …}
SflKxwRJSMeKKF2QT4fwpMeJf36POk6yJV…    ← signature (needs the key)

Decoding reads the header + payload (anyone can). Validating proves the token is genuine and current (only the server, with the key, can). Never trust claims from a token you haven't validated — and never paste a real production token into a random web decoder.

The problem

Every check on this page's checklist can pass on a token that should have stopped working twenty minutes ago.

Support disabled the account. The API kept serving her data for another 21 minutes.

09:05 — Alice signs in. Ping mints an access token with a 30-minute lifetime, so exp lands at 09:35. 09:14 — a support engineer disables her account in the admin console and, being thorough, also calls the issuer's revocation endpoint with her refresh token. 09:20 — Alice's still-open browser tab calls GET /api/accounts. Your Spring resource server answers 200, with her data in the body.

Nothing failed. Your decoder fetched the JWKS keys once, at startup, and cached them. On every request since, it verifies the signature against that cached public key, compares exp to the local clock, string-matches iss, and checks aud — all in process, all in microseconds, and without ever speaking to Ping again. That speed is the entire point of a self-contained token. The cost is that revocation happened somewhere your API never looks.

signature verifies ✓ exp is 09:35, it's 09:20 ✓ iss and aud both match ✓ the account behind the token no longer exists ⚠ nobody told the resource server ⚠

The checklist answers "was this token genuinely issued, and is it still inside its window?" It has never once answered "should this token still work?"

Shrink the window, then close it deliberately where it matters
Decide what your revocation gap actually is, out loud, and write it down ↓ it equals the access-token lifetime, exactly — a 60-minute TTL is a 60-minute gap, whatever the admin console says Cut the access-token TTL to 5-15 minutes and let refresh-token rotation do the re-checking ↓ the refresh call DOES hit the issuer, so a disabled account fails there — that round trip is where revocation lands For the endpoints where 15 minutes is too long, check state on purpose: a jti denylist in Redis, or token introspection (RFC 7662) on that route only ↓ you are choosing to pay a network hop for "delete this customer" and not for "load the dashboard" And subscribe to the issuer's logout/revocation signals — OIDC back-channel logout, or Entra's Continuous Access Evaluation — so the news reaches you instead of waiting for exp
A stateless token is a decision cached in the client's pocket, and cached decisions go stale. Validation proves the issuer said yes at issue time and that the deadline has not passed. It cannot prove the issuer would still say yes now, because nobody asked. Every property you love about JWTs — no session store, no per-request call to the IdP, horizontal scale for free — is the same property that makes revocation slow. You do not fix that by adding a seventh claim to the checklist. You fix it by choosing a token lifetime you can live with, and by paying for a real state check on the few operations that deserve one.

Tokens expire. They do not get recalled.

A validated JWT is a concert wristband, not the guest list. Security scans the band at the door — is it genuine, is it today's colour? Crossing someone off the list at the box office changes nothing for the person already wearing a band. You either print bands that expire sooner, or you put a radio in the bouncer's ear. The bouncer checks the wristband, not the list.

Your Spring resource server

Because I never asked you anything. I cached Ping's public keys, and since then every request has been six local checks on bytes the client handed me. I don't have a phone line to the IdP — that's what made me fast enough to run twelve instances behind a load balancer.

The revocation endpoint

I did my job. I killed the refresh token so no NEW access token can be minted from that grant. The one already in her browser isn't mine to reach into — it's a signed string that exists in a hundred places I've never seen.

The 30-minute exp claim

Which makes me the actual security control here, and I'm just a number someone typed into a config screen. Set me to 5 minutes and your worst case gets six times better without a single line of code.

The mechanism

Follow one token from mint to grave and watch exactly where the revocation news fails to arrive.

  1. 09:05 — Alice authenticates. Ping mints an access token (exp 09:35) plus a refresh token, and records the grant in its own storethe issuer is stateful; it remembers
  2. Your API's decoder fetches the JWKS public keys once and caches them. It will not call Ping again unless it meets an unknown kidthe last call to the IdP for 30 minutes
  3. 09:06-09:13 — 400 API requests. Each one: verify signature locally, compare exp to the local clock, match iss, check aud. Zero network callsthis is the feature, not the bug
  4. 09:14 — support disables the account and revokes the refresh token. Ping updates Ping's store. Your API is not a subscriber, is not polled, and is not notifiedthe news stops here
  5. 09:20 — Alice's tab calls GET /api/accounts. All six checks pass, because all six are about the token, and the token has not changed200 OK, correctly
  6. 09:35 — exp passes. Now she gets a 401. The SPA tries to refresh, Ping rejects the revoked grant, and only then does the disabled account become visible to your APIrevocation, delivered 21 minutes late by a clock

Step 4 is the whole lesson: it is the only step where something important happens and nothing happens in your process. There is no log line, no failed check, no red entry in the Network tab — the absence of an event is the event. Which is also why this bug never shows up in debugging: you are staring at a request that is behaving perfectly.

Minted (09:05) Ping signs it → a self-contained string, valid for 30 minutes, now living in the browser
Accepted (09:06-09:34) every request → six local checks, cached keys, no call to the issuer
Revoked at the issuer (09:14) admin disables the account → Ping's store changes; the token in the browser does not, and neither does your API's answer
Expired (09:35) exp passes → 401, refresh attempt, issuer finally consulted, revocation lands

Read the third state again. It is the only one where the token's status and the API's behaviour disagree, and it lasts exactly as long as whatever number you configured for the access-token lifetime. That number is not a performance tuning knob. It is the answer to "how long can a fired employee keep calling our API?", and it belongs in your threat model with the seriousness that implies.

Your Spring resource server is configured with issuer-uri pointing at Ping, and your audience validator is in place. At 09:14 an admin disables Alice's account and calls Ping's revocation endpoint with her refresh token. At 09:20 her open tab sends the access token she received at 09:05 (exp 09:35) to GET /api/accounts. What does your API return?

This is what the admin console's wording leads you to expect, and it is true of the refresh token — that grant really is dead, and no new access token can be minted from it. But revocation is a change of state at the issuer. The access token already sitting in Alice's browser is a signed string; there is no channel by which Ping reaches into it or into your process. Nothing about that string changed at 09:14.

Right — and importantly, your API is not misbehaving. It is answering the only question it was ever asked: is this token genuine and inside its window? Both are still true. The gap between "revoked" and "stops working" equals the access-token lifetime, which is why a 5-minute TTL plus refresh rotation is a real security control and a 12-hour TTL is a 12-hour window for anyone holding a copy. If a specific endpoint cannot tolerate even 5 minutes, that endpoint gets a deliberate state check — a jti denylist lookup or an introspection call — and pays the round trip on purpose.

Spring's JWT resource-server support does not call userinfo, or anything else, during request validation — the whole design is a local verification against cached JWKS keys, which is what lets a stateless API scale horizontally without a shared session store. (And 403 would be the wrong shape anyway: 403 means "I know who you are and you still can't", which implies a successfully authenticated principal.) If you want per-request issuer contact, you opt into it explicitly with token introspection — and you accept the latency you just bought.

Where you have seen this before

The same shape shows up any time a yes/no answer gets copied away from whoever owns the truth.

The session you replaced to get here

A server-side HttpSession has the opposite trade. Calling session.invalidate() — or Spring Security's SessionRegistry.expireNow() — takes effect on the very next request, because the truth lives in one store your app reads every time. That is precisely the lookup JWTs deleted for scale. Stateless auth did not make revocation harder by accident; revocation was the thing it traded away.

you sold instant revocation to buy the missing round trip

The S3 presigned URL you can't take back

You generate a presigned link, it leaks into a Slack channel, and you want it gone. There is no "unshare" button — the URL is a signature over parameters plus an expiry, verified without any lookup. Your options are wait for the expiry, or invalidate the signing credential and break every other URL signed with it. Same maths as a JWT, same reason: the check is offline.

anything signed and self-describing is un-revokable by design

CDN TTL and the purge you forgot to run

You fix the price on the product page, deploy, and customers see the old number for another hour because CloudFront is serving a cached object with time left on its TTL. The origin is correct; the edge is confidently serving a stale copy of a correct past answer. "Purge the cache" is exactly what back-channel logout and Continuous Access Evaluation are for tokens: an explicit push, because the puller was never going to ask again.

a short TTL is the cheap fix; a purge channel is the real one

4. Decode it yourself (safely)

    

      
# PowerShell — decode the payload (2nd segment), no key needed
$p = "<jwt>".Split(".")[1].Replace('-','+').Replace('_','/')
while ($p.Length % 4) { $p += "=" }
[Text.Encoding]::UTF8.GetString([Convert]::FromBase64String($p))

      
Read exp/aud/iss straight from the output. For signature/key issues you need the IDM's JWKS — but the decode alone resolves most "why 401?" questions. Don't paste production tokens into online decoders; they're bearer credentials.

5. Traps

    

      
    
        
  • Decoding ≠ trusting. The payload is readable by anyone; only a verified signature makes it trustworthy. Servers must validate, never just decode.
    • 
        
  • alg-confusion attacks. Accept only your expected algorithm; reject alg: none and don't let a token downgrade RS256→HS256. Spring's decoders pin this — don't loosen it.
    • 
        
  • aud can be a string or an array. Validate membership, not equality, and always check it (routing by iss alone isn't enough).
    • 
        
  • exp/nbf are seconds, not millis. Off-by-1000 and clock skew both masquerade as "expired/not-yet-valid".
    • 
      

    

  


  
  

    
6. One-sentence recap

    

      
🔍 A JWT is three base64url parts you can decode without a key to read exp/aud/iss instantly — but a resource server validates it through a checklist (alg → signature → exp → nbf → iss → aud), and the first failing check is your bug: expired → refresh, bad signature → key rotated/tampered (re-auth), wrong aud/iss → token minted for another API/tenant, alg: none → reject it — so decode the token (safely, never in a random web tool) and walk that list.
