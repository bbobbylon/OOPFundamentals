Routing — turning URLs into components

Angular Router maps a URL path to a component. Click a link → the URL changes → a different component renders in the <router-outlet>. No page reload, no server roundtrip. Add guards, lazy loading, and route data on top.

🧭 What is client-side routing? How is it different from clicking a link?

On a traditional site, clicking a link sends a new request to the server, which returns a whole new HTML page. An Angular Single-Page Application downloads the app once; after that, navigation happens entirely in JavaScript — the URL changes via the History API, Angular matches it to a route, and swaps which component renders inside a <router-outlet>. No full reload, no server round-trip for a new page.

  • You declare routes (a path → a component); Angular matches the current URL top-down and the first match wins.
  • <router-outlet> is the placeholder where the matched component renders; nested outlets give nested layouts.
  • routerLink navigates without a reload; :id path params and ?q= query params feed the component via ActivatedRoute.
  • Guards (canActivate, canMatch) run before a route activates — the hook for auth checks and redirects.
  • Lazy loading (loadComponent/loadChildren) defers a feature's code until its route is hit — a smaller initial bundle.

How a route maps

const routes = [

The problem

You put a guard on the admin route. The admin bundle showed up in the network tab anyway.

The redirect worked. The chunk had already arrived.

You lazy-load the admin module with loadChildren and gate it with canActivate: [authGuard], same as every other protected route in the app. A logged-out user clicks a stray /admin link and gets bounced to /login exactly like you'd expect — the guard clearly did its job. Weeks later, a security review opens the Network tab during that exact click and finds admin-routes.chunk.js sitting there, fully downloaded, before the redirect ever happens. Nothing in your test caught it, because your test checked "did I end up on the login page" — and you did.

canActivate answers "should this route activate" — a question the router can only ask after it has already fetched and loaded the code for the route it's asking about.

Put the gate before the download, not after it
canActivate: [authGuard] → canMatch: [authGuard], on the lazy route itself ↓ canMatch runs during route matching, before the router decides this route is even eligible to load — an ineligible route's loadChildren never executes Keep canActivate too, on the routes inside the loaded module ↓ canMatch stops a network request; canActivate is still what protects a route someone reaches by a different path once the module IS loaded Now "unauthorized" means the code never arrives, not just that it never renders
A guard can only gate what the router asks it about — and canActivate is asked after the code is already loaded. That's why canMatch exists as a separate hook instead of canActivate just being "good enough": lazy loading's whole promise is not shipping code a user shouldn't have yet, and the only guard positioned early enough in the pipeline to honor that promise is the one that runs before loadChildren is ever invoked.
Think of canActivate as a bouncer checking IDs at the door of a room, and canMatch as the one deciding whether to even build the room in the first place. The bouncer does a real job — nobody uninvited gets inside — but by the time he's standing there, the room, the furniture and the sound system have already been delivered and set up on the truck outside. If the thing you're protecting is "nobody should know this room exists," you needed the second one, not the first. The analogy stops mattering once the module is already loaded once — after that, either guard genuinely gates the same door, because there's no more delivery left to stop.
You

My guard is on the route. Why did the admin code still download for a logged-out user?

The Router

Because by the time I run canActivate, I've already recognized your route and resolved what to load for it — that resolution step is what triggers the import() for your lazy chunk. canActivate is one of the last things I check, not one of the first.

canMatch

I'm the one who runs early enough to matter here. I get asked "is this route even a candidate" before the router commits to loading anything for it — say no, and loadChildren never fires, so there's no import(), no network request, no chunk.

canActivate

Which leaves me doing the job I was actually built for — gating activation of routes that already loaded, for users who reached them a different way, or where there was never anything sensitive in the bundle to hide in the first place.

The mechanism

One extra letter of hook name, and the fetch either happens or it doesn't.

  1. A logged-out user clicks a link to /admin. The router begins recognizing the URL against the route tablenavigation starts
  2. If the /admin route entry has a canMatch guard, the router runs it right now, before treating /admin as a real candidate matchthe earliest checkpoint that exists
  3. canMatch returns false (or a redirecting UrlTree) → the router discards this route entirely. loadChildren for the admin routes is never calledno call, no chunk, no download
  4. If instead the route only has canActivate, matching succeeds immediately, and resolving that match triggers loadChildren's import('./admin/admin.routes') — a real network request, dispatched right nowthe download already happened
  5. Only after the chunk is loaded does the router run canActivate. It returns a redirecting UrlTree, the admin route never activates, and AdminComponent never rendersthis part is genuinely gated
  6. The user was correctly denied the page. They were not denied the download — DevTools' Network tab shows the request, and any code that runs at module-evaluation time has already runthe gap between "didn't see it" and "never received it"

Step 4 is the lesson. It's easy to read canActivate: [authGuard] on a lazy route and assume the guard is what's standing between an unauthorized user and the bundle — but activation is a later stage than loading. The guard that actually stands in front of loadChildren is canMatch, and it's the only one of the two that was designed with "don't fetch it at all" as its job, not "don't render it once you have."

/admin is configured with loadChildren: () => import('./admin/admin.routes') and canActivate: [authGuard] — no canMatch. A logged-out user's authGuard returns a UrlTree redirecting to /login. Which is true?

The natural read of "the guard blocked it" — and it's true for the activation half of that sentence, just not the loading half. canActivate is checked after the router has already resolved what to load for a matched route, so on a canActivate-only lazy route, resolving the match is exactly what triggers the import() — before the guard ever runs.

There's no such retry policy, and canActivate doesn't interact with module loading at all — it has no visibility into whether a chunk succeeded, failed, or was ever requested. It only ever answers one question, "can this already-resolved route activate," after the loading step is long finished.

Right — and this is exactly why canMatch exists as a separate hook rather than Angular just calling canActivate earlier. Activation and loading are different stages of the same navigation, and only one hook is positioned before both.

Where you've seen this before

"Don't even let the code reach the door" is a rule bigger than Angular's router.

A firewall rule vs. an app-level permission check

A firewall dropping a packet before it reaches your server is canMatch — the request never arrives, there's nothing to log, nothing to exploit at the app layer. An app-level if (!user.isAdmin) throw 403 is canActivate — the request landed, ran real code, and got rejected afterward. Both "work," but only one of them means the sensitive endpoint's existence and behavior were never exposed to something that shouldn't have reached it.

drop before the door ≠ reject after opening it

Code-splitting bundles by feature, then gating the split

This problem only exists because lazy loading works — loadChildren is Angular's wrapper around a dynamic import(), which the build turns into a genuinely separate chunk file fetched on demand. Any framework doing route-based code-splitting inherits the identical two-stage question: does the gate run before the chunk request, or after the chunk already arrived. React Router's lazily-loaded routes with a data-loader guard hit the same fork.

lazy loading + gating = the same two-stage question everywhere

Role-gating a CIAM admin console built as its own lazy chunk

An internal console splits /admin/** into its own bundle behind canMatch: [rolesGuard] reading the decoded JWT's roles — not just canActivate, specifically because that bundle imports things worth not exposing to every authenticated user: internal role names, feature flags for unreleased tooling, API paths for endpoints that shouldn't be discoverable from a webpack chunk. canActivate alone would still keep those strings sitting in a downloaded file for anyone who opened DevTools.

canMatch keeps the admin bundle's contents un-downloaded, not just unrendered
Questions from the back row

If canMatch is strictly earlier, is there ever a reason to use canActivate instead?

Constantly — most guards aren't protecting a lazy chunk at all. A route like /settings that's part of the main bundle has nothing to "not download"; there's no chunk to save, so canActivate's job (block activation, redirect) is the entire job. canMatch specifically earns its keep on lazy routes where the thing worth protecting is the bytes themselves, not just the rendered page — outside that case it's just an earlier hook doing the same conceptual check, with no download to prevent.

Can canMatch redirect the same way canActivate can, with a UrlTree?

Yes — both hooks accept the same return shape: true, false, or a UrlTree the router treats as "redirect here instead." The difference is timing, not capability. A canMatch returning a UrlTree means the router picks a different route before ever attempting to match /admin, which is also why canMatch is the right hook for role-based route splitting — same URL, different bundle loaded, decided before any loading happens.

What actually happens to the top-level code in a chunk that downloaded but never activated?

It already ran. A dynamic import() executes the module's top-level statements — imports, constant initialization, anything outside a component's lifecycle — the moment the module evaluates, which happens as part of loading it, independent of whether the router ever activates a component from it. Rendering is gated; module evaluation isn't. That's the sharp edge underneath this whole page: "the guard blocked it" is true of the component tree and not necessarily true of every line of code that shipped alongside it.

Defining routes

// app.routes.ts — central place where every route lives
import { Routes } from '@angular/router';

export const routes: Routes = [
  { path: '',         redirectTo: '/home', pathMatch: 'full' },
  { path: 'home',     component: HomeComponent },
  { path: 'users',    component: UserListComponent },
  { path: 'users/:id', component: UserDetailComponent },  // :id = param
  { path: 'admin',    component: AdminComponent,

  { path: '**',       component: NotFoundComponent }      // catch-all 404

Programmatic navigation — Router.navigate()

export class LoginComponent {
  private router = inject(Router);

  async onLogin() {
    await this.authService.login();
    this.router.navigate(['/dashboard']);          // absolute
  }

  openUser(id: string) {
    this.router.navigate(['/users', id]);   // each array element becomes one path SEGMENT — same as routerLink's array syntax
  }

  goWithQueryParams() {
    this.router.navigate(['/search'], {
      queryParams: { q: 'angular', page: 2 }   // a separate options object — never concatenated into the path array itself
    });   // → /search?q=angular&page=2
  }

  goBack() {
    this.router.navigate(['..']);   // relative — go up one segment
  }
}

Every call here takes an ARRAY, not a string — navigate(['/users', id]) builds the path from segments so a dynamic id never has to be string-concatenated (and risks a malformed URL) by hand.

Route params & query params — reading the URL

When the user is on /users/42?tab=settings, the :id param is 42 and the query param tab is settings. Read them via ActivatedRoute. 

export class UserDetailComponent {
  private route = inject(ActivatedRoute);

  // Snapshot — value at time of route activation. Good if it never changes.
  id = this.route.snapshot.paramMap.get('id');                // '42'
  tab = this.route.snapshot.queryParamMap.get('tab');          // 'settings'

  // Observable — fires every time the param changes WITHOUT recreating the component
  id$ = this.route.paramMap.pipe(map(p => p.get('id')));
}

The gotcha: navigating from /users/1 to /users/2 does NOT recreate UserDetailComponent — Angular reuses it for performance. snapshot would still show 1. Use paramMap observable when params can change without leaving the route.

Route guards — gate access to a route

Guards are functions Angular runs before navigating. Return true → allow. Return false or a UrlTree → block / redirect. (Class-based CanActivate still works but functional is the modern way.) 

// auth.guard.ts — functional guard (Angular 14.2+)
import { inject } from '@angular/core';
import { CanActivateFn, Router } from '@angular/router';

export const authGuard: CanActivateFn = () => {   // a plain arrow function — no class, no @Injectable
  const auth   = inject(AuthService);   // works here because Angular calls this from an injection context
  const router = inject(Router);

  if (auth.isLoggedIn()) return true;

  // Block AND redirect — return a UrlTree
  return router.createUrlTree(['/login']);   // returning a UrlTree redirects atomically — no separate navigate() call needed
};

// Wire it up in routes
{ path: 'admin', component: AdminComponent, canActivate: [authGuard] }   // an ARRAY — you can stack multiple guards here, all must pass

Lazy loading — load code only when needed

The biggest perf lever in Angular. Without lazy loading, every component, service, and library across your whole app ships in one JS bundle on first load. With it, route-specific code downloads only when the user actually navigates there. 

// ❌ Eager — admin code is in the main bundle even if user never goes to /admin
{ path: 'admin', component: AdminComponent }   // a static import — Angular has no choice but to bundle it eagerly

// ✅ Lazy — admin code is a separate chunk, downloaded on demand
{
  path: 'admin',
  loadComponent: () => import('./admin/admin.component').then(m => m.AdminComponent)   // dynamic import() — its own chunk, fetched only on navigation
}

// ✅ Lazy whole feature with its own sub-routes
{
  path: 'admin',
  loadChildren: () => import('./admin/admin.routes').then(m => m.adminRoutes)   // lazy-loads an ENTIRE routes array, not just one component
}

Route data & resolvers

// Static route data — for things like page titles, roles, breadcrumbs
{
  path: 'admin',
  component: AdminComponent,
  data: { title: 'Admin', role: 'admin', breadcrumb: 'Admin' }   // known in advance — no async work required
}

// Read it in the component
private route = inject(ActivatedRoute);
title = this.route.snapshot.data['title'];   // data: and a resolver's result live in the SAME snapshot.data object

// Resolver — fetch data BEFORE the route activates
export const userResolver: ResolveFn<User> = (route) => {
  const id = route.paramMap.get('id')!;   // reads the :id from the route being resolved, not the current one
  return inject(UserService).getById(id);   // an Observable — Angular waits for it to emit and complete
};

{ path: 'users/:id', component: UserDetailComponent,
  resolve: { user: userResolver } }   // the key ('user') is what snapshot.data['user'] below reads by

// Read it in the component
user = this.route.snapshot.data['user'];   // already loaded — no loading spinner needed

Resolvers block navigation until data is ready. Convenient, but for slow APIs they make the UI feel unresponsive. Often better to navigate immediately and show a loading skeleton inside the component.

Router events — react to navigation

export class AppComponent {
  private router = inject(Router);

  constructor() {
    this.router.events.pipe(   // emits MANY event types (NavigationStart, guards, resolvers...) — this stream carries all of them
      filter(e => e instanceof NavigationEnd)   // narrow down to just the ones that mean "navigation finished successfully"
    ).subscribe((e: NavigationEnd) => {
      console.log('navigated to', e.url);
      analytics.track('page_view', { url: e.url });   // the classic SPA analytics pattern — no full page load to hook a script onto
    });
  }
}

// All event types: NavigationStart, RoutesRecognized, GuardsCheckStart,
// ResolveStart, ActivationStart, NavigationEnd, NavigationCancel,
// NavigationError, Scroll. NavigationEnd is the one you'll use 99% of the time.

The 5 mistakes to avoid

❌ Using <a href="/foo">

Plain anchors trigger a full page reload — your app reinitializes from scratch. Use routerLink for all in-app links.

❌ Forgetting {exact: true}

routerLinkActive matches by prefix. /users would stay "active" on /users/42. Add [routerLinkActiveOptions]="{exact: true}" for nav items that should only highlight on an exact match.

❌ Reading params from snapshot when they can change

If users can navigate between /users/1 and /users/2 while staying in the same component, use paramMap observable, not snapshot.

❌ Putting auth state in the URL

Don't write /dashboard?auth_token=.... Tokens belong in headers / cookies / storage, never in URLs (they leak to logs, history, referer headers).

❌ Loading everything eagerly

A 5MB initial bundle = a 4-second first paint on a 3G phone. Lazy-load every feature route unless it's the homepage.

❌ Heavy work in guards

Guards run on every navigation. A slow guard = a slow app. Cache results, return Observables, and never make N synchronous network calls.

Mental model

URL = state

The URL is the source of truth for "what page are we on." Bookmark it, share it, refresh → same view. Router-state must be reflected in the URL.

One outlet per layout level

The root <router-outlet> shows the top-level routed component. Each nested layout has its own <router-outlet> for its children.

Guards = the bouncer

Stand at the door, check ID, let you in or send you to /login. They run BEFORE the component is even constructed.

Lazy load by feature

Each top-level feature (admin, settings, reports) is its own lazy chunk. Initial bundle stays small, page-load stays fast.

Functional guards — the modern pattern with inject()

Since Angular 14, guards are plain functions — no class, no decorator. They use inject() to pull in services and return boolean | UrlTree (or an Observable/Promise of either). A UrlTree redirects instead of just blocking.

canActivate — auth guard

// auth.guard.ts
export const authGuard: CanActivateFn = (route, state) => {   // state.url is the URL being navigated TO — captured below for the redirect back
  const auth = inject(AuthService);
  const router = inject(Router);

  if (auth.isAuthenticated()) {
    return true;
  }
  // redirect to /login, preserve return URL
  return router.createUrlTree(
    ['/login'],
    { queryParams: { returnUrl: state.url } }   // login page can read this and navigate back after a successful login
  );
};

// routes.ts
{ path: 'dashboard', component: DashboardComponent,
  canActivate: [authGuard] }

canMatch — role-based route splitting

// admin.guard.ts — never downloads the chunk
// unless the user is actually an admin
export const adminGuard: CanMatchFn = () => {   // a DIFFERENT function type than CanActivateFn above — runs at a different point
  const auth = inject(AuthService);
  const router = inject(Router);

  return auth.hasRole('admin')
    ? true
    : router.createUrlTree(['/forbidden']);
};

{ path: 'admin',
  canMatch: [adminGuard],       // ← blocks chunk download
  loadChildren: () => import('./admin/admin.routes')   // this import() is the exact thing canMatch:false prevents from ever running
    .then(m => m.adminRoutes) }

Route params as input() signals — withComponentInputBinding()

Enable withComponentInputBinding() in your router config and route params, query params, and resolve data are automatically injected into matching input() signals — no ActivatedRoute injection needed.

Before (classic inject approach)

export class UserDetailComponent {
  private route = inject(ActivatedRoute);   // this dependency disappears entirely on the "after" side
  userId = '';   // plain field — starts empty, populated asynchronously below

  ngOnInit() {   // needs a lifecycle hook just to wire up the subscription
    this.route.paramMap
      .pipe(map(p => p.get('id')!))
      .subscribe(id => this.userId = id);   // manual subscription — needs its own unsubscribe discipline elsewhere
  }
}

After (withComponentInputBinding)

// app.config.ts
provideRouter(routes, withComponentInputBinding())

// user-detail.component.ts
export class UserDetailComponent {
  // route param :id → this signal
  id = input.required<string>();

  // query param ?tab=... → this signal
  tab = input('overview');

  // resolve data → same name in resolve:{user}
  user = input<User>();
}

Why it matters: The component becomes testable without a router stub — just set the input directly. Route params become reactive signals: computed(() => this.id() + ' — detail') recalculates automatically when navigation changes the id.

CIAM pattern — OIDC redirect guard

A real CIAM auth guard does more than a null-check: it reads the stored session, verifies the access token is not expired, and if not — redirects to the IdP (Ping / Entra) for a fresh login. The return URL is preserved so users land back where they were.

// oidc-auth.guard.ts
export const oidcAuthGuard: CanActivateFn = (route, state) => {
  const auth = inject(OidcSecurityService);  // angular-auth-oidc-client
  const router = inject(Router);
  const config = inject(APP_CONFIG);

  return auth.isAuthenticated$.pipe(
    take(1),   // the guard's Observable must COMPLETE — take(1) guarantees that after one emission
    switchMap(({ isAuthenticated }) => {
      if (isAuthenticated) return of(true);   // the fast, common path — already has a valid session

      // store return url so callback can redirect back
      sessionStorage.setItem('returnUrl', state.url);   // survives the full-page redirect to the IdP and back — a JS variable wouldn't

      // kick off OIDC login redirect to IdP
      auth.authorize(config.oidcConfigId);   // navigates the WHOLE browser away to Ping/Entra — not an Angular route change
      return of(false);   // blocks this navigation attempt; the redirect above is already in flight
    })
  );
};

// routes.ts — protect all protected pages
{ path: '',
  canActivate: [oidcAuthGuard],   // applied at the PARENT — every child route below inherits this check
  children: [
    { path: 'dashboard', component: DashboardComponent },
    { path: 'profile',   component: ProfileComponent },
    { path: 'admin',
      canMatch: [adminGuard],   // a SECOND, more specific guard layered on top of the parent's auth check
      loadChildren: () => import('./admin/admin.routes').then(m => m.adminRoutes) },
  ]
}
CIAM architecture note: Guards are UX gates — they make the UI flow correctly. They are not the security boundary. The Spring Boot resource server validates the JWT on every protected API call independently. Never skip server-side token validation because the Angular guard looks correct.

🌱 New to routing? It's a map from URLs to screens.

A single-page app never reloads the page — so something has to decide which component to show for a given URL. That's the router. You give it a list of routes ("when the path is users, show UsersComponent"), drop a <router-outlet> where the matched component should appear, and link around with routerLink="/users" (or router.navigate(['/users']) from code). A :id in the path (users/:id) carries data in the URL, so a page is bookmarkable and shareable. That's the whole job: URL → component, with data in the path.

🧠 Expert corner — lazy chunks, guards, and the navigation lifecycle

  • Lazy loading is the perf win. loadComponent/loadChildren code-split a feature into its own bundle that downloads only when its route is hit — keep the initial bundle tiny.
  • Functional guards (canActivate, canMatch) are just functions that inject() services and return boolean | UrlTree. canMatch is powerful: it can make the same path resolve to different routes by role — and a failing canMatch means the lazy chunk is never even downloaded.
  • Resolvers prefetch data before activation so the component opens with data in hand (no flash of empty state).
  • The navigation is a stream. router.events emits NavigationStart → GuardsCheck → Resolve → NavigationEnd (or NavigationCancel/NavigationError) — wire a loading bar to it. withComponentInputBinding() binds route params straight to component input()s.
  • CIAM tie-in. A canMatch guard gates the admin feature so its code isn't shipped to non-admins; a canActivate redirects unauthenticated users to /login via a UrlTree. Remember: guards are UX — the Spring server is the real authorization gate. See Functional Guards and Route Guards & Claims.
