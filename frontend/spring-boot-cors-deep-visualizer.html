CORS & Preflight

Your Angular SPA at app.contoso.com calls your Spring API at api.contoso.com — different origins, so the browser's Same-Origin Policy kicks in and demands the server opt in via CORS headers. Get it wrong and the call dies with a cryptic status 0 while working fine in Postman. Here's exactly what the browser checks, and how Spring opts in.

🌐 What is CORS — and why does Postman work while the browser returns status 0?

Browsers enforce the Same-Origin Policy: JavaScript at https://app.contoso.com can only read responses from that same origin — a different subdomain like https://api.contoso.com counts as cross-origin. The browser blocks it, not the server, which is why Postman (no browser) gets the response and the browser silently hides it as "status 0 / network error" — never a clean 403. CORS is how the server says "it's fine for JavaScript from https://app.contoso.com to read my responses," via headers like Access-Control-Allow-Origin: https://app.contoso.com.

  • CORS is browser-enforced. The server already ran; the browser withholds the response from JS.
  • "status 0" = CORS/preflight, not an auth error — look at the OPTIONS request.
  • Preflight first. Auth header / JSON / PATCH/DELETE trigger an OPTIONS that must be permitted.
  • Never * with credentials. List exact origins in prod; the browser forbids wildcard + credentials.

Preflight requests

Non-simple requests (Authorization header, JSON body, PATCH/DELETE) send an OPTIONS preflight first; the server must return allowed origins/methods/headers before the real call fires. If Security rejects the preflight with 403, the real request never happens — Angular sees "status 0".

Spring CORS config

Per-controller @CrossOrigin(origins="https://app.contoso.com"), or global in the SecurityFilterChain via http.cors(...) with a CorsConfiguration setting allowed origins, methods (incl. OPTIONS), headers, and allowCredentials. Global wins for consistency.

Never * with credentials

Allow-Origin: * permits any origin, but the browser forbids the wildcard once allowCredentials=true (cookies/Authorization). List exact origins — http://localhost:4200 in dev, https://app.contoso.com in prod — never * on an authenticated CIAM API.

Debug "status 0" in CIAM: Open the Network tab, find the OPTIONS preflight, check its status — 200 means CORS is fine; 403 means Security rejected it before CORS ran (add .requestMatchers(HttpMethod.OPTIONS).permitAll()). Then verify the Access-Control-Allow-Origin header matches your Angular origin exactly — it's case-sensitive and the trailing slash matters.

The problem

Your preflight is green, your login returns 200, and Angular still can't find the token.

Login works, the body parses, and headers.get('Jwt-Token') is null

Your Spring login endpoint does the sensible thing: it puts the freshly minted JWT in a response header — Jwt-Token — instead of burying it in the JSON body. The CORS config looks complete: allowedOrigins("https://app.contoso.com"), allowedMethods("*"), allowedHeaders("*"), allowCredentials(true). The preflight OPTIONS comes back 204. The POST /login comes back 200. The body deserialises into your UserDTO perfectly.

Then you open the Network tab and there it is, plainly visible under Response Headers: Jwt-Token: eyJhbGciOiJIUzUxMiJ9…. And in the very next line of your code, res.headers.get('Jwt-Token') returns null. No CORS error in the console. No red request. Nothing failed. The browser simply received that header, decided your JavaScript wasn't allowed to see it, and said nothing about it. DevTools shows you the wire; your code gets a filtered view of the wire, and nobody tells you they differ.

preflight OPTIONS → 204 ✓ POST /login → 200 ✓ DevTools shows Jwt-Token on the response ✓ headers.get('Jwt-Token') → null ⚠

The assumption underneath: that allowedHeaders means "headers this API is allowed to use." It means the opposite direction — headers the browser is allowed to send you.

Name the header you want read back, on the response side
.allowedHeaders("Authorization", "Content-Type") ↓ that is the request direction — what the browser may put ON the call. It has no opinion about reading anything back. .exposedHeaders("Jwt-Token", "Location") ↓ now the actual response carries Access-Control-Expose-Headers: Jwt-Token, Location, and the browser un-hides exactly those two res.headers.get('Jwt-Token') returns the token — with no change to Angular, the endpoint, or the preflight
CORS filters the response your JavaScript receives, not just the request it is allowed to send. Out of every header on the wire, a cross-origin read exposes only seven by default — Cache-Control, Content-Language, Content-Length, Content-Type, Expires, Last-Modified, Pragma — and nothing else, ever, until Access-Control-Expose-Headers names it. That is why a paging API's X-Total-Count, a 201's Location, a 429's Retry-After and your auth header all go missing together the first time the SPA moves to its own subdomain. And the wildcard is not the easy way out: per the Fetch standard Access-Control-Expose-Headers: * is treated as a literal header name — not a wildcard — as soon as the request sends credentials, which is every authenticated CIAM call you make.
Think of the pharmacy pickup window. Your whole order is on the counter three feet away — you can see it, the label has your name on it — but you only get what the pharmacist slides through the slot. exposedHeaders is the list of what gets slid through the slot. Everything else stays on the counter, in full view, permanently out of reach.

The browser's CORS layer

Because DevTools is me showing you what arrived on the socket, and headers.get() is me showing your script what it's cleared to read. Those are two different lists. Cross-origin, your script gets seven safelisted response headers plus whatever the server explicitly names in Access-Control-Expose-Headers. Yours named nothing.

DefaultCorsProcessor, in Spring

Angular's HttpHeaders

The mechanism

One credentialed POST /login from app.contoso.com to api.contoso.com, start to finish.

  1. The Content-Type: application/json body makes this non-simple, so the browser sends an OPTIONS preflight firstpermission to send
  2. Spring answers the preflight with Allow-Origin, Allow-Methods, Allow-Headers and Allow-Credentials — every one of them about the request you are about to makenothing here is about reading
  3. The preflight passes, the real POST goes out with the cookie, and your controller runs and mints the JWTserver side is completely fine
  4. The 200 comes back carrying Content-Type, Date, Jwt-Token and half a dozen others. All of them physically arrive in the browser processthe wire has everything
  5. Before handing the response to your fetch/XHR, the browser builds a filtered header list: the seven CORS-safelisted names, plus anything listed in Access-Control-Expose-Headers on this responsethe invisible step
  6. That header wasn't sent, so Jwt-Token is dropped from the filtered list — silently, with a 200 status and a perfectly readable bodysuccess, minus the part you needed

Step 5 is the one nobody pictures. Every CORS diagram you have ever seen stops at "the preflight was approved, the request went through" — as if approval were a single yes/no gate at the front door. There is a second gate on the way out, it runs on the actual response and not the preflight, and it defaults to closed. Which is also why re-reading the OPTIONS response in DevTools for the hundredth time will never show you the problem: the fix has to land on the POST's own headers.

Read it inwards and the bug stops being mysterious. Nothing was lost between the first ring and the second — your server did its job and the network delivered it. The whole bug lives in the third ring, a list that starts with seven entries and grows only when you say so. Debugging from the outermost ring (curl, Postman, the Network tab) will always look healthy, because all three of those tools live in ring two.

Two things wrong here, and both are worth having straight. allowedHeaders only ever governs headers the browser may send on the request — adding a response header's name to it changes nothing about reading. And Spring doesn't leave you with a broken wildcard either: when allowedHeaders is "*", CorsConfiguration.checkHeaders() resolves it to the concrete header names the preflight actually asked for, so the response echoes real names rather than a literal *. Where you have seen this before

Three other places where the data arrived intact and the layer you read it through handed you nothing.

JWT claims vs. granted authorities

Your Entra access token carries a groups claim, you can paste it into jwt.io and see it, and hasAuthority("ROLE_ADMIN") still fails. Spring Security's default JwtGrantedAuthoritiesConverter reads scope/scp and prefixes each with SCOPE_ — it never looks at groups. The claim is present, decoded and validated; it just isn't in the list the authorization check reads from until you supply your own converter.

present in the token ≠ present in the authorities

HttpClient's default observe: 'body'

Even with exposedHeaders configured correctly, a plain http.post(url, body) hands you the deserialised body and throws the HttpResponse away. There is no .headers to ask. You need observe: 'response' before the question is even askable — a second, entirely client-side filter stacked on top of the browser's one.

two filters between the wire and your variable

HttpOnly on a session cookie

The server sets it, the browser stores it, and every subsequent request sends it back faithfully — and document.cookie returns an empty string. Same shape, opposite intent: here the invisibility is the entire point, because a cookie your JavaScript can read is a cookie an injected script can steal. It's the clearest proof that "on the wire" and "readable by my code" were never the same list.

1. Why CORS exists

The Same-Origin Policy stops a page from reading responses from a different origin — otherwise any site could call your bank's API using your logged-in cookies. An origin is scheme + host + port; change any one and it's "cross-origin".

SPA originAPI URLSame origin?
https://app.contoso.comhttps://app.contoso.com/api✓ yes (no CORS)
https://app.contoso.comhttps://api.contoso.com✗ different host
https://app.contoso.comhttp://app.contoso.com✗ different scheme
http://localhost:4200http://localhost:8080✗ different port (your dev setup!)

CORS = the server's way of saying "these other origins may read my responses." It's permission the API grants, enforced by the browser.

2. Simple requests vs preflighted requests

"Simple" → sent straight away

No preflight if all hold: method is GET/HEAD/POST, and only safelisted headers, and Content-Type is one of text/plain, multipart/form-data, application/x-www-form-urlencoded.

⚠️ A "simple" cross-origin POST still reaches and runs on the server — the browser just hides the response if CORS fails. (This is why CSRF protections matter.)

Anything else → preflight first

The browser sends an OPTIONS "preflight" to ask permission before the real request. Triggered by:

  • method PUT/DELETE/PATCH
  • Content-Type: application/json (your typical API call!)
  • an Authorization header or any custom X-* header

5. The credentials & wildcard gotcha

The single most common CORS failure with authenticated apps: you cannot combine Access-Control-Allow-Origin: * with credentials.

  • If the request sends cookies/auth (withCredentials), the server must echo the specific origin (Access-Control-Allow-Origin: https://app.contoso.com) — never *.
  • It must also return Access-Control-Allow-Credentials: true.
  • So allowedOrigins("*") + allowCredentials(true) is rejected by Spring at startup — use allowedOriginPatterns(...) instead, which echoes the matched origin.

Try it in the simulator: set withCredentials = on and allowedOrigins = * → blocked.

6. Configuring CORS in Spring

Global config (recommended)

@Configuration  // registers this class as a bean-definition source, wired in at startup
class CorsConfig implements WebMvcConfigurer {  // hooks into Spring MVC's OWN config interface
  @Override public void addCorsMappings(CorsRegistry r) {  // the one method this interface exposes for CORS
    r.addMapping("/api/**")  // applies to every path under /api, nothing else
     .allowedOrigins("https://app.contoso.com")  // one exact origin — never "*" alongside credentials
     .allowedMethods("GET","POST","PUT","DELETE")  // only these verbs clear preflight
     .allowedHeaders("*")  // any request header is let through
     .allowCredentials(true);   // → can't use allowedOrigins("*")
  }
}

@CrossOrigin on a controller/method works too, but per-endpoint config drifts — prefer one central place.

⚠️ With Spring Security, wire CORS in

@Bean
SecurityFilterChain chain(HttpSecurity http) throws Exception {
  http.cors(Customizer.withDefaults())  // ← enables CORS in the chain
      .authorizeHttpRequests(a -> a.anyRequest().authenticated());
  return http.build();
}

If you forget .cors(...), the Security filter chain rejects the preflight OPTIONS (no auth header on it!) with a 401 before your CORS config runs — the classic "CORS works without security, breaks with it".

7. CORS is enforced by the browser — only

  • Postman / curl / server-to-server calls ignore CORS entirely — there's no Origin enforcement outside a browser. "Works in Postman, fails in the app" = CORS, almost always.
  • A CORS failure surfaces in Angular as HttpErrorResponse with status: 0 and no body — the browser blocked it before your JS could read it.
  • The real diagnostic is the browser devtools console / Network tab, which names the missing Access-Control-* header.

↪ That status 0 is the same one covered in the API Error Handling deep-dive's "status-0 trap".

8. One-sentence recap

🌐 Because your SPA and API are different origins, the browser enforces the Same-Origin Policy and the API must opt in with CORS: non-simple calls (PUT/DELETE, application/json, Authorization) trigger a preflight OPTIONS that the server must answer with matching Access-Control-Allow-Origin/Methods/Headers (and Allow-Credentials: true + a specific origin — never * — when sending cookies); configure it once via WebMvcConfigurer, remember http.cors() when Security is on, and know that a CORS failure shows up as status 0 in the browser only.
