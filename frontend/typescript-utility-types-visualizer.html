Utility Types Deep Dive

Every built-in utility type, what it does, the one-liner that implements it, and when to reach for it. These are the LEGO bricks of type-level programming.

🛠️ What are utility types? Why do they matter?

You have a User with 10 fields. A "create" form needs all of them except the server-generated id; an "update" endpoint wants them all optional; a public profile must hide password. Instead of hand-writing three interfaces, TypeScript ships utility types that transform an existing type — Omit<User,'id'>, Partial<User>, Pick<User,'name'|'email'>. They're built into the standard library (no import), implemented with mapped + conditional types, and they re-derive automatically when the base type changes.

  • Transform, don't duplicate. Derive create/update/public shapes from one source type.
  • Shape modifiers: Partial, Required, Readonly.
  • Key selectors: Pick, Omit, Record.
  • Type extractors: ReturnType, Parameters, Awaited.

Shape modifiers

Partial<T> (all optional), Required<T> (all required), Readonly<T> (no mutation).

Key selectors

Pick<T, K> (keep these keys), Omit<T, K> (drop these), Record<K, V> (build a map type).

Type extractors

ReturnType<F> (a function's return), Parameters<F> (its args tuple), Awaited<P> (unwrap a Promise).

CIAM / Angular / Spring: Partial<UpdateUserRequest> for PATCH endpoints, Omit<TokenPayload, 'exp'> for token builders, Record<string, Permission> for role maps, and ReturnType<typeof service.getUser> to type service returns without repeating yourself.

Treat them as magic and the sharp edges stay invisible

Learn utility types as vocabulary — "Partial makes things optional, Omit removes a key" — and you have no way to predict what happens at the boundaries. So you type Omit<User, 'emial'>, the compiler says nothing, and you ship a type that omits absolutely nothing while claiming it did.

The definition

I map over keyof T — one level of keys — and add ? to each. I never look inside T[K]. So config.db is optional and every field inside db is exactly as required as it always was.

Omit

And read mine before you trust me. I take K extends keyof any, not K extends keyof T. Any string at all is a legal argument. Pick constrains its K; I do not.

The mechanism

Watch Partial<User> expand into the type it really is.

  1. You write Partial<User>looks built-in
  2. The compiler looks up an ordinary alias: type Partial<T> = { [K in keyof T]?: T[K] }it is just a file you can open
  3. keyof User becomes the union 'id' | 'name' | 'db' — one level of keys, nothing nestedthis is where "shallow" comes from
  4. Each key is re-emitted with ? added, and its value type T[K] copied through untouchedthe value type is never visited
  5. Result: { id?: number; name?: string; db?: DbConfig } — and DbConfig's own fields are as required as everexactly what the definition said

Nobody has to memorise "Partial is shallow." Step 3 makes it unavoidable: the mapped type iterates keyof T and copies T[K] through. There is no recursion in that line, so there is no recursion in the behaviour. The same reading tells you Readonly is shallow too, for the identical reason — and tells you how to write DeepPartial when you need one.

Which brings us back to the typo that compiles. Open the two definitions side by side: Pick<T, K extends keyof T> constrains K to keys that actually exist, so a misspelling is a compile error. Omit<T, K extends keyof any> constrains K to any property key at all, so Omit<User, 'emial'> is legal and quietly returns every field of User. It is deliberate — Omit has to work on union types where a key exists on only some members — but the cost is that the utility most people reach for to strip a password field will happily strip nothing at all. If that matters in your codebase, the one-liner type StrictOmit<T, K extends keyof T> = Omit<T, K> gets the check back, and it is a type alias, because that is all any of these ever were.

Questions from the back row

What is the actual difference between Record and an index signature?

Mostly that Record can take a finite key union. Record<string, User> is just { [k: string]: User } — but Record<'admin' | 'user', Policy> produces two required properties, so forgetting one is a compile error and adding a third role to the union breaks every map that has not been updated. That is the version worth using: exhaustiveness you get for free.

Why does Exclude behave strangely on a generic parameter?

Because conditional types distribute over naked type parameters: applied to a union, the condition is evaluated once per member and the results unioned back. That is what makes Exclude<'a'|'b'|'c', 'b'> work at all. It surprises people when they did not want it — wrapping both sides in a tuple, [T] extends [U], turns distribution off, which is the standard trick and looks like nonsense until you know this is what it is for.

Should I write my own utility types?

Yes, and it is far less exotic than it sounds — most useful ones are one line. type Nullable<T> = T | null, type Result<T> = { ok: true; value: T } | { ok: false; error: string }, a StrictOmit. Keep them in one types.ts and give them names from your domain. The bar is the same as for a helper function: if the shape appears three times, name it.

1. Why utility types matter

You almost never declare the "same" type twice in a well-typed codebase. A User exists once; UserUpdate is "every User field optional"; UserCreate is "every User field but the id". Utility types let you derive all those shapes from the single source of truth — so when User changes, every derived type follows.

type User = { id: string; name: string; email: string; admin: boolean };

type UserUpdate = Partial<User>;        // all fields optional
type UserCreate = Omit<User, 'id'>;       // drop the auto-assigned id
type UserPublic = Pick<User, 'id' | 'name'>; // safe-to-render fields
Mental model: utility types are functions at the type level. They take types in, give types out. The arguments go in <...> instead of (...) — that's the only real difference.

2. Object utilities

Partial<T> — every field optional

type Partial<T> = { [K in keyof T]?: T[K] };
type User      = { id: string; name: string; admin: boolean };
type UserPatch = Partial<User>;
// { id?: string; name?: string; admin?: boolean }

function update(id: string, patch: UserPatch) { /* PATCH /users/:id */ }
update('u_1', { name: 'Bob' }); // ✅ partial body OK

Use for: PATCH payloads, default-merging configs, optional override props.

Required<T> — every field mandatory

type Required<T> = { [K in keyof T]-?: T[K] };

The opposite of Partial. Note the -? — that's the "remove optionality" modifier in mapped types.

type Config         = { host?: string; port?: number; retries?: number };  // every field optional — the caller-facing shape
type ResolvedConfig = Required<Config>;  // the internal shape, after defaults are filled in
// { host: string; port: number; retries: number }

function withDefaults(cfg: Config): ResolvedConfig {  // accepts the loose shape, promises to return the strict one
  return { host: 'localhost', port: 80, retries: 3, ...cfg };  // defaults first, then cfg's own values override via spread order
}

Readonly<T> — every field immutable

type Readonly<T> = { readonly [K in keyof T]: T[K] };
type Frozen = Readonly<{ x: number; y: number }>;
const p: Frozen = { x: 1, y: 2 };
p.x = 3;  // ❌ Cannot assign to 'x' because it is a read-only property

Caveat: shallow only. Readonly<{ inner: { a: number } }> still lets you mutate p.inner.a. Build your own DeepReadonly with a recursive mapped type — see §9.

Pick<T, K> — keep only these keys

type Pick<T, K extends keyof T> = { [P in K]: T[P] };
type User       = { id: string; name: string; email: string; password: string };
type UserPublic = Pick<User, 'id' | 'name' | 'email'>;
// { id: string; name: string; email: string }   ← password excluded

Use for: safely exposing a subset of a domain type to the outside world (API responses, view models).

Omit<T, K> — drop these keys

type Omit<T, K extends keyof any> = Pick<T, Exclude<keyof T, K>>;

The inverse of Pick. Note K extends keyof any — Omit lets you pass keys that aren't in T without error (controversial design choice).

type User       = { id: string; name: string; password: string };
type CreateUser = Omit<User, 'id'>;
// { name: string; password: string }   ← id is generated server-side

type Bad = Omit<User, 'idd'>; // ⚠ no error! typo silently does nothing

Record<K, V> — object with known keys, uniform values

type Record<K extends keyof any, V> = { [P in K]: V };
type Role        = 'admin' | 'user' | 'guest';
type Permissions = Record<Role, string[]>;
// { admin: string[]; user: string[]; guest: string[] }

const perms: Permissions = {
  admin: ['read', 'write', 'delete'],
  user:  ['read', 'write'],
  guest: ['read'],
};
// Forgetting a role → compile error. Adding a new role to Role → compile error here too. ✨

// Wide-key form for "any string maps to a value":
type Dict = Record<string, number>; // same as { [k: string]: number }

3. Union utilities

Exclude<T, U> — remove members of U from union T

type Exclude<T, U> = T extends U ? never : T;
type Status = 'pending' | 'active' | 'banned';
type Live   = Exclude<Status, 'banned'>;
// 'pending' | 'active'

type NonString = Exclude<string | number | boolean, string>;
// number | boolean

Extract<T, U> — keep only members of T assignable to U

type Extract<T, U> = T extends U ? T : never;
type Mixed  = string | number | { id: string };
type Strs   = Extract<Mixed, string>;        // string
type Object = Extract<Mixed, { id: string }>; // { id: string }

NonNullable<T> — remove null and undefined

type NonNullable<T> = T & {}; // modern; older: Exclude<T, null | undefined>
type Maybe = string | null | undefined;
type Defined = NonNullable<Maybe>; // string

4. Function utilities

ReturnType<F> — what a function gives back

type ReturnType<F> = F extends (...a: any) => infer R ? R : never;
function getUser() {
  return { id: 'u_1', name: 'Bob', lastLogin: new Date() };
}

type User = ReturnType<typeof getUser>;
// { id: string; name: string; lastLogin: Date }

// Now User stays in sync with getUser's body — no manual duplication.

The typeof grabs the function's type; ReturnType extracts the return slot. This pattern is everywhere in real codebases — it's why you can stop hand-writing types that mirror a function's output.

Parameters<F> — tuple of argument types

type Parameters<F> = F extends (...a: infer P) => any ? P : never;
function register(name: string, age: number, admin = false) {}  // a default value makes "admin" optional in the extracted tuple below
type RegArgs = Parameters<typeof register>;  // same typeof + utility combo as ReturnType above
// [name: string, age: number, admin?: boolean]

// Useful for wrapping/decorating:
function withLog<F extends (...a: any[]) => any>(fn: F) {  // F is constrained to "any function", then narrowed to the real one passed in
  return (...args: Parameters<F>): ReturnType<F> => {  // the wrapper's signature is derived FROM fn — never re-typed by hand
    console.log('call', args);
    return fn(...args);  // spreads the tuple back out as individual arguments
  };
}

ConstructorParameters<C> & InstanceType<C>

type ConstructorParameters<C> = C extends new (...a: infer P) => any ? P : never;
type InstanceType<C> = C extends new (...a: any) => infer R ? R : never;
class Service { constructor(public url: string, public timeout: number) {} }  // a class, not a plain function — these two utilities read its constructor

type Args    = ConstructorParameters<typeof Service>; // [string, number]
type ServInst = InstanceType<typeof Service>;          // Service

function make<C extends new (...a: any[]) => any>(  // C is constrained to "any constructable class", same idea as Ctor<T> on the generics page
  C: C, ...args: ConstructorParameters<C>  // args must match whichever class C actually is — checked per call
): InstanceType<C> {  // the return type is derived from C too — a generic factory function
  return new C(...args);
}

ThisParameterType<F> & OmitThisParameter<F>

Niche but handy when you're typing decorators or proxies. Extract or strip the this annotation.

function click(this: HTMLElement, e: MouseEvent) { this.focus(); }
type ThisT  = ThisParameterType<typeof click>;   // HTMLElement
type Plain  = OmitThisParameter<typeof click>;   // (e: MouseEvent) => void

5. Async utilities

Awaited<T> — unwrap Promise (recursively!)

// recursive — peels nested promises until a non-promise type
type A = Awaited<Promise<string>>;                  // string
type B = Awaited<Promise<Promise<number>>>;        // number  ← recursive
type C = Awaited<boolean | Promise<boolean>>;     // boolean

// Real use: derive the resolved type of an async function
async function fetchUser() { return { id: 'u_1', name: 'Bob' }; }
type User = Awaited<ReturnType<typeof fetchUser>>;
// { id: string; name: string }

6. String utilities

Uppercase, Lowercase, Capitalize, Uncapitalize

Apply to string-literal types. Real use: building precise template-literal types and event-handler maps.

type Greeting = 'hello world';

type U  = Uppercase<Greeting>;   // 'HELLO WORLD'
type L  = Lowercase<'HELLO'>;       // 'hello'
type C  = Capitalize<'click'>;      // 'Click'
type Uc = Uncapitalize<'Click'>;    // 'click'

// Real use — turn event names into handler-prop names:
type Events  = 'click' | 'hover' | 'submit';
type Handlers = { [K in Events as `on${Capitalize<K>}`]: () => void };
// { onClick: () => void; onHover: () => void; onSubmit: () => void }

7. Combining utilities

The real power emerges when you chain them. A few patterns you'll meet constantly:

Update payload — every field optional, except id required

type User       = { id: string; name: string; email: string; admin: boolean };
type UserUpdate = Pick<User, 'id'> & Partial<Omit<User, 'id'>>;
// { id: string } & Partial<{ name; email; admin }>
// → id required, rest optional

function patch(u: UserUpdate) {}
patch({ id: 'u_1', name: 'Bob' }); // ✅
patch({ name: 'Bob' });            // ❌ id missing

Pick + Record — a typed map keyed by some subset

type User     = { id: string; name: string; email: string };
type Indexed  = Record<User['id'], User>;
// { [k: string]: User } — but keyed by the id field's type

Async + Return — derive the resolved type of an HTTP call

const getUser = async (id: string) => {  // an async arrow function — typeof still works on this, same as a named function
  const r = await fetch(`/users/${id}`);
  return r.json() as Promise<{ id: string; name: string }>;  // the cast tells TS what shape the JSON resolves to
};

type User = Awaited<ReturnType<typeof getUser>>;  // ReturnType gives Promise<{...}>, Awaited unwraps the Promise to get the final shape
// { id: string; name: string } — chain of three utilities

9. Build your own

Once you internalize keyof, mapped types, and conditional types, you can write any utility you need. A starter kit:

DeepReadonly — recursive freeze

type DeepReadonly<T> = {
  readonly [K in keyof T]: T[K] extends object ? DeepReadonly<T[K]> : T[K];
};

Mutable — strip readonly

type Mutable<T> = { -readonly [K in keyof T]: T[K] };

NullableFields — make every field T | null

type Nullable<T> = { [K in keyof T]: T[K] | null };

PickByValue — pick fields whose value is assignable to V

type PickByValue<T, V> = {  // unlike Pick, you filter by VALUE type here, not by naming keys explicitly
  [K in keyof T as T[K] extends V ? K : never]: T[K];  // "as ... : never" is the key-filtering trick — mapping a key to never drops it entirely
};

type User      = { id: number; name: string; admin: boolean; age: number };
type UserNums  = PickByValue<User, number>;  // keeps only the fields whose value type is number
// { id: number; age: number }

OmitNever — drop keys whose value resolved to never

type OmitNever<T> = { [K in keyof T as T[K] extends never ? never : K]: T[K] };

🌱 New to these? They're built-in "type functions" that reshape a type.

You define a User type once. Now you need "a User where everything is optional" (for an update form), or "just the id and name", or "User without the password". Instead of redefining the shape each time, TypeScript ships utility types that transform an existing type into a related one:

  • Partial<User> — every field optional;
  • Pick<User, 'id' | 'name'> — only those fields;
  • Omit<User, 'password'> — everything except;
  • Record<string, number> — an object used as a map.

Feed a type in, get a new type out — no copy-paste, and they stay in sync if User changes.

🧠 Expert corner — they're just mapped + conditional types

  • You could write them yourself. Partial<T> is literally {[K in keyof T]?: T[K]} — a mapped type. Knowing that lets you build custom ones (e.g. DeepPartial).
  • The wider toolbox: Required, Readonly, NonNullable, Parameters<F>, ReturnType<F>, Awaited<P>, InstanceType, plus the intrinsic string ones (Uppercase, Capitalize).
  • Compose them. Partial<Pick<User, 'name' | 'email'>> is a perfectly good PATCH-body type.
  • Derive types from values. ReturnType<typeof createUser> keeps a type glued to the function that produces it — refactor the function, the type follows.
  • CIAM tie-in. Omit<User, 'passwordHash'> is your safe response DTO; Partial<User> is the PATCH input. One source of truth, two safe shapes. Go deeper in Mapped Types.
