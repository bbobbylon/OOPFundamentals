Java Generics

Compile-time type safety, wildcards, bounded type parameters, PECS, and type erasure.

🔣 What are generics — and why does the compiler erase them at runtime?

Before Java 5, List list held anything and you cast on retrieval — risking ClassCastException at runtime. Generics add a type parameter (List<String>) so the compiler catches a wrong type before the code runs. But type erasure means generics exist only at compile time — at runtime List<String> and List<Integer> are both just List, which is why you can't do new T() or T.class. Wildcards (? extends/? super) and the PECS rule handle flexible read/write bounds.

  • Type parameters move errors to compile time — no more cast-and-pray.
  • Erasure: generics vanish at runtime — no new T(), T.class, or T[].
  • Bounds add capability — <T extends Comparable<T>> lets you call compareTo.
  • PECS — Producer extends, Consumer super.

Generic classes and methods

Generic class: class Pair<A, B> { A first; B second; }. Use: Pair<String, Integer> p = new Pair<>("hello", 42) (diamond inference). Generic method: <T extends Comparable<T>> T max(T a, T b) { return a.compareTo(b) > 0 ? a : b; }. The <T extends Comparable<T>> bounds T to types that can compare themselves. Without the bound: you can't call a.compareTo(b) — the compiler doesn't know T has that method. Multiple bounds: T extends Comparable<T> & Serializable.

Wildcards: ? extends / ? super

void printAll(List<? extends Number> list) — read items (as Number), can't add (type unknown). Called with: List<Integer>, List<Double>. void addNumbers(List<? super Integer> list) — can add Integers, can't read as anything useful. Called with: List<Integer>, List<Number>, List<Object>. PECS rule: Collections.copy(List<? super T> dest, List<? extends T> src) — src produces (extends), dest consumes (super). Unbounded: List<?> — can only read as Object, can't add anything (except null).

Type erasure consequences

Can't: new T(), new T[10], T.class, instanceof List<String>, overload two methods that differ only by generic type. Can: instanceof List<?>. To get the class of T at runtime: pass Class<T> clazz as a parameter. Jackson uses this approach: objectMapper.readValue(json, new TypeReference<List<User>>(){}) — the anonymous class captures the generic type at compile time (ParameterizedType), bypassing erasure. Spring's ParameterizedTypeReference does the same thing.

Spring Boot / CIAM: Spring Data returns Page<UserDto> — a generic Spring knows at compile time; deserializing it needs a TypeReference<Page<UserDto>> to survive erasure. The generic repository pattern UserRepository extends JpaRepository<User, Long> inherits findById(Long): Optional<User> for free, with Spring generating the implementation by reflection.

1. Why Generics?

Before Java 5 (Java 1.4 and earlier) every collection stored Object. You had to manually cast on the way out — and the compiler could not warn you if the types were wrong. The error only appeared at runtime as a ClassCastException. Generics were introduced in Java 5 to move that error to compile time.

BEFORE GENERICS (Java 1.4) — compiles, crashes at runtime
// Nothing stops mixing types ArrayList numbers = new ArrayList(); numbers.add(42); numbers.add(99); // Bug: someone adds a String to the "numbers" list numbers.add("oops"); // compiles fine! for (int i = 0; i < numbers.size(); i++) { // Must cast — and this BLOWS UP on "oops" Integer n = (Integer) numbers.get(i); // ^^^ ClassCastException at runtime! System.out.println(n * 2); }
AFTER GENERICS (Java 5+) — compiler catches the mistake
// Type parameter locks the list to Integer ArrayList<Integer> numbers = new ArrayList<>(); numbers.add(42); numbers.add(99); // Compiler ERROR — won't compile at all // numbers.add("oops"); // <-- type mismatch for (Integer n : numbers) { // No cast needed — type is already known System.out.println(n * 2); }
Key insight: Generics shift type errors from runtime (hard to debug) to compile time (immediate feedback). The compiler also inserts the necessary casts automatically, so your code is both safer and cleaner.

2. Generic Classes

A generic class declares one or more type parameters in angle brackets after the class name. Inside the class those parameters act exactly like real types.

T — Type (general purpose)
E — Element (collections)
K — Key (maps)
V — Value (maps)
N — Number
Box<T> — a single-item generic container
public class Box<T> { private T value; // T is the actual stored type at call site public Box(T value) { this.value = value; } public T getValue() { return value; } @Override public String toString() { return "Box[" + value + "]"; } } // Usage — T is replaced by the concrete type at each call site Box<String> strBox = new Box<>("Hello"); Box<Integer> intBox = new Box<>(42); String s = strBox.getValue(); // no cast needed Integer n = intBox.getValue(); // no cast needed System.out.println(strBox); // Box[Hello] System.out.println(intBox); // Box[42]
Pair<K, V> — two type parameters
public class Pair<K, V> { private final K key; private final V value; public Pair(K key, V value) { this.key = key; this.value = value; } public K getKey() { return key; } public V getValue() { return value; } @Override public String toString() { return "(" + key + ", " + value + ")"; } } // K = String, V = Integer Pair<String, Integer> score = new Pair<>("Alice", 95); System.out.println(score.getKey()); // Alice System.out.println(score.getValue()); // 95

3. Generic Methods

A generic method declares its own type parameter in <T> placed before the return type. This is independent of any type parameter on the class — static methods especially must declare their own.
max() — works with any Comparable type
// <T extends Comparable<T>> declares T AND constrains it public static <T extends Comparable<T>> T max(T a, T b) { return a.compareTo(b) >= 0 ? a : b; } // Compiler infers T from the arguments Integer biggerInt = max(10, 25); // T = Integer String laterString = max("apple", "mango"); // T = String Double biggerDouble = max(3.14, 2.71); // T = Double System.out.println(biggerInt); // 25 System.out.println(laterString); // mango System.out.println(biggerDouble); // 3.14
swap() — works with any object array
public static <T> void swap(T[] arr, int i, int j) { T temp = arr[i]; arr[i] = arr[j]; arr[j] = temp; } String[] words = {"cat", "dog", "fox"}; Integer[] nums = {1, 2, 3}; swap(words, 0, 2); // ["fox", "dog", "cat"] swap(nums, 0, 1); // [2, 1, 3]

4. Bounded Type Parameters

Bounds restrict which types can be used as arguments. An upper bound (extends) means "T must be this type or a subtype of it." This lets you call methods defined on the bound type.

Upper bound — <T extends Number>
// T must be Number, Integer, Double, Long, Float, etc. public static <T extends Number> double sum(List<T> list) { double total = 0; for (T item : list) { total += item.doubleValue(); // OK — Number defines doubleValue() } return total; } List<Integer> ints = List.of(1, 2, 3); List<Double> doubles = List.of(1.5, 2.5); System.out.println(sum(ints)); // 6.0 System.out.println(sum(doubles)); // 4.0 // sum(List.of("a","b")); // COMPILE ERROR — String is not a Number
Multiple bounds — T extends Comparable<T> & Serializable
// T must implement BOTH interfaces (class bound must come first) public static <T extends Comparable<T> & Serializable> T clampAndSerialize(T value, T min, T max) { if (value.compareTo(min) < 0) return min; if (value.compareTo(max) > 0) return max; return value; } // Integer is Comparable AND Serializable Integer clamped = clampAndSerialize(150, 0, 100); // 100

5. Wildcards Explained

Wildcards (?) appear in method parameters and variable types — not in class/method declarations. They express flexibility in what collection you are willing to accept.

List<?>

Unbounded wildcard — "a list of any type."

Useful when you only need to iterate and treat each element as Object.

READ: elements come out as Object ✓
WRITE: cannot add anything (except null) ✗
void printAll(List<?> list) { for (Object o : list) System.out.println(o); } // Works for List<String>, List<Integer>, etc.

List<? extends Number>

Upper-bounded wildcard — "a list of Number or any subtype."

You know elements are at least a Number, so you can call Number methods. But you can't add because you don't know the exact subtype.

READ: elements come out as Number ✓
WRITE: cannot add — could be List<Integer> or List<Double> ✗
double total(List<? extends Number> list) { double sum = 0; for (Number n : list) sum += n.doubleValue(); return sum; }

List<? super Integer>

Lower-bounded wildcard — "a list of Integer or any supertype."

Could be List<Integer>, List<Number>, or List<Object>. You can safely ADD integers. Reads give only Object.

WRITE: can add Integer (and subtypes) ✓
READ: elements come out as Object only ✗
void addIntegers(List<? super Integer> list) { list.add(1); list.add(2); list.add(3); // OK — any list that can hold Integer works }

6. The PECS Principle

PECS = Producer Extends, Consumer Super
Coined by Joshua Bloch in Effective Java.
If a collection produces items that you read out of it, use extends.
If a collection consumes items that you write into it, use super.

Producer (you READ from it)

List<? extends Animal> src
Produces Animal references
Can't add to it (unknown exact subtype)
Use extends
→

Consumer (you WRITE to it)

List<? super Dog> dst
Consumes Dog references
Reads give only Object
Use super
Canonical PECS example — Collections.copy()
// src produces T values → extends // dst consumes T values → super public static <T> void copy( List<? super T> dst, List<? extends T> src) { for (T item : src) // read from src (producer) dst.add(item); // write to dst (consumer) } List<Integer> ints = List.of(1, 2, 3); List<Number> nums = new ArrayList<>(); copy(nums, ints); // T = Integer; dst=List<Number> (super Integer) // src=List<Integer> (extends Integer)
Quiz — extends or super?

You're writing a method that reads elements from a List of Shape subtypes and draws each one.

Use extends: List<? extends Shape>
You only READ from the list (the list produces Shape values). You never add items, so you don't need super.

You're writing a method that adds Dog objects into a provided List.

Use super: List<? super Dog>
You WRITE into the list (the list consumes Dog values). The list could be List<Dog>, List<Animal>, or List<Object> — all accept a Dog.

You want a method that accepts any List and just prints its size().

Use unbounded wildcard: List<?>
You neither read the elements nor write to the list — you just call a method on the List itself. The unbounded wildcard is the most flexible choice.

7. Type Erasure

Generics in Java are a compile-time feature only. The compiler uses the type information to check your code, then erases it. At runtime, List<String> and List<Integer> are the same class: List. The compiler inserts casts where needed, invisibly.

What you write (generic source code)
List<String> names = new ArrayList<>(); names.add("Alice"); String first = names.get(0);
What the compiler actually emits (bytecode equivalent)
List names = new ArrayList(); // raw type names.add("Alice"); // compiler inserts the cast for you: String first = (String) names.get(0);

Heap pollution warning — because erasure discards type info, raw types let you lie to the compiler and produce a ClassCastException in surprising places:

List<String> strs = new ArrayList<>(); strs.add("Hello"); List raw = strs; // raw type — no warning at the assignment @SuppressWarnings("unchecked") List<Integer> ints = raw; // unchecked cast — heap pollution! ints.add(42); // adds an Integer into a "String" list // The ClassCastException happens here, not at add(): String s = strs.get(1); // BOOM — ClassCastException
What erasure prevents you from doing
// CANNOT — type info gone at runtime T obj = new T(); // COMPILE ERROR T[] arr = new T[10]; // COMPILE ERROR if (obj instanceof List<String>) { ... } // COMPILE ERROR // These two erase to the same signature → overload clash void process(List<String> list) { } // COMPILE ERROR void process(List<Integer> list) { } // same erasure! // CAN — instanceof without type param is fine if (obj instanceof List<?>) { ... } // OK

8. Comparable<T> and Comparator<T>

Comparable<T> — the class itself defines its "natural order." Implement it when there is one obvious, intrinsic way to sort.
Comparator<T> — an external strategy for a specific ordering criterion. Use it when you want multiple sort orders or can't modify the class.
Student implements Comparable<Student> — natural order by GPA
public class Student implements Comparable<Student> { private final String name; private final double gpa; public Student(String name, double gpa) { this.name = name; this.gpa = gpa; } @Override public int compareTo(Student other) { // Natural order: highest GPA first return Double.compare(other.gpa, this.gpa); } // getters omitted for brevity } List<Student> students = List.of( new Student("Alice", 3.9), new Student("Bob", 3.4), new Student("Carol", 3.7) ); Collections.sort(students); // uses compareTo — natural order // → [Alice(3.9), Carol(3.7), Bob(3.4)]
Comparator<Student> — custom order by name without touching the class
// Option 1: lambda expression Comparator<Student> byName = (a, b) -> a.getName().compareTo(b.getName()); // Option 2: method reference (cleaner) Comparator<Student> byName2 = Comparator.comparing(Student::getName); // Sort by name, then by GPA descending as tiebreaker Comparator<Student> byNameThenGpa = Comparator.comparing(Student::getName) .thenComparing(Comparator.comparingDouble(Student::getGpa).reversed()); students.sort(byName); // → [Alice, Bob, Carol] (alphabetical) students.sort(byNameThenGpa); // → [Alice(3.9), Bob(3.4), Carol(3.7)] (name asc, gpa desc)

9. Generic Interfaces

Repository<T, ID> — the pattern behind Spring Data JPA
// Generic interface: any entity type T with primary key type ID public interface Repository<T, ID> { void save(T entity); Optional<T> findById(ID id); List<T> findAll(); void deleteById(ID id); } // Concrete implementation for User entities public class UserRepository implements Repository<User, Long> { @Override public void save(User user) { /* persist */ } @Override public Optional<User> findById(Long id) { /* query */ return Optional.empty(); } // ... etc } // Spring Data's JpaRepository is exactly this pattern: public interface UserJpaRepo extends JpaRepository<User, Long> { // Spring generates the implementation — you get findAll(), save(), etc. for free }
Converter<S, T> — converting between types
public interface Converter<S, T> { T convert(S source); } // Convert a UserDto (data transfer object) to a User entity public class UserDtoToUser implements Converter<UserDto, User> { @Override public User convert(UserDto dto) { return new User(dto.getId(), dto.getName(), dto.getEmail()); } } // Spring's own ConversionService uses Converter<S,T> extensively

10. Common Pitfalls

Operation Allowed? Reason / Workaround
new T() NO T is erased at runtime — the JVM doesn't know what constructor to call. Pass a Class<T> clazz param and use clazz.getDeclaredConstructor().newInstance().
new T[10] NO Arrays carry runtime type info; generic arrays can't. Workaround: @SuppressWarnings("unchecked") T[] a = (T[]) new Object[10]; or use a List<T> instead.
instanceof T NO T is erased. Pass Class<T> clazz and use clazz.isInstance(obj).
instanceof List<String> NO Parameterized types cannot appear in instanceof. Use instanceof List<?> instead.
Generic exception class NO class MyException<T> extends Exception is not allowed. Exceptions are matched by type at runtime, which is erased for generics.
List<int> NO Primitives are not reference types. Use the wrapper: List<Integer>. Autoboxing handles the conversion automatically.
T as method param / return YES This is the primary use of generics. The type information exists at compile time where it matters.
Generic array with cast YES* @SuppressWarnings("unchecked") T[] a = (T[]) new Object[n]; — works but loses type safety. Prefer List<T>.
Class<T> as constructor param YES Pass the class token to regain runtime type info: new Repo<>(User.class). Used in frameworks for reflection.
Overload differing only in generic param NO void f(List<String> x) and void f(List<Integer> x) are the same signature after erasure. Use different method names.

🌱 New to generics? They're type-safety for containers.

List<String> means "a list that only holds Strings." The compiler then stops you from putting an Integer in, and you never have to cast when you take one out — it already knows it's a String. The <T> is a placeholder you fill in (with String, User, whatever). Before generics, collections held bare Object, so you cast everywhere and risked a runtime ClassCastException if you slipped. Generics move that whole class of bug from runtime to compile time — the errors show up while you type, not in production.

🧠 Expert corner — erasure, and the wildcard rule (PECS)

  • Type erasure. Generics are a compile-time feature — at runtime List<String> is just List. Consequences: no new T[], no T.class, and instanceof List<String> is illegal. Overloads that differ only by type argument collide (same erased signature).
  • Bounds. <T extends Comparable<T>> lets you call compareTo inside; the bound is what you can do with T.
  • Wildcards — remember PECS ("Producer Extends, Consumer Super"): use <? extends T> when you only read Ts out (a producer), <? super T> when you only put Ts in (a consumer). This is why Collections.copy(dest, src) is copy(List<? super T>, List<? extends T>).
  • Generic methods declare their own param: static <T> T first(List<T> xs) — inference fills T at the call site.
  • Raw types (List without <>) are legacy escape hatches — they switch off the checks; don't write new ones.
  • Real tie-in. JpaRepository<User, Long>, ResponseEntity<UserDto>, Optional<T> — the framework is generics all the way down.
