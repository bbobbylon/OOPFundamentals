1. Two strategies — pick based on data size

Client-side — load all, slice locally

Fetch the whole list once, then show a slice. Simple, instant page switches, sorting/filtering is free — but only viable for small datasets (hundreds, not millions).

export class UsersComponent {
  all = signal<User[]>([]);
  page = signal(0);
  size = signal(10);

  // the visible slice — recomputes automatically
  pageItems = computed(() => {
    const start = this.page() * this.size();
    return this.all().slice(start, start + this.size());
  });

  totalPages = computed(() =>
    Math.ceil(this.all().length / this.size())
  );
}

Server-side — fetch one page at a time

Ask the API for just the page you need. The server does the slicing. Scales to any size — this is what you'll use with real backends.

export class UsersComponent {
  private http = inject(HttpClient);
  items = signal<User[]>([]);
  totalElements = signal(0);

  load(page: number, size: number) {
    this.http.get<Page<User>>('/api/users', {
      params: { page, size, sort: 'name,asc' }
    }).subscribe(p => {
      this.items.set(p.content);
      this.totalElements.set(p.totalElements);
    });
  }
}

💡 HttpParams turns {page:2, size:10} into ?page=2&size=10 on the URL.

Client-sideServer-side
Initial loadWhole dataset (slow if big)One page (fast)
Page switchInstant (no network)Network request each time

Scales to millionsNoYes
Use whenSmall, static listsReal APIs, large/dynamic data

2. Two index models — page/size vs offset/limit

The math (and the off-by-one trap)

// page/size — Spring Data style (page is 0-based!)
page = 2, size = 10
→ items 20..29   // the 3rd page

// offset/limit — SQL / many REST APIs
offset = 20, limit = 10
→ items 20..29   // same window

// convert between them
offset = page * size;
page   = Math.floor(offset / size);

⚠ Spring pages are 0-indexed, but humans count pages from 1. Show page + 1 in the UI and subtract 1 when calling the API — a classic source of "page 1 shows page 2's data" bugs.

The Spring Page<T> response shape

When your backend returns Page<User> (Spring Data), the JSON looks like this — model it in TypeScript:

interface Page<T> {
  content: T[];          // the rows for THIS page
  totalElements: number;  // total across all pages
  totalPages: number;     // how many pages exist
  number: number;         // current page index (0-based)
  size: number;           // page size
  first: boolean;
  last: boolean;
  numberOfElements: number; // rows on this page
}
GET /api/users?page=0&size=10 → { content:[…], totalElements:248 }

4. The page-number array (with ellipsis)

Computing which numbers to show

You don't render 248 page buttons. Show the first, last, current, and neighbours — gap the rest with ….

// returns e.g. [1, '…', 4, 5, 6, '…', 25]
pageNumbers(current: number, total: number): (number|string)[] {
  const delta = 1;            // neighbours each side
  const range: number[] = [];
  for (let i = Math.max(1, current - delta);
       i <= Math.min(total, current + delta); i++) {
    range.push(i);
  }
  const withDots: (number|string)[] = [];
  if (range[0] > 1) withDots.push(1, range[0] > 2 ? '…' : 2);
  withDots.push(...range);
  if (range.at(-1)! < total)
    withDots.push(range.at(-1)!<total-1 ? '…':total-1, total);
  return withDots;
}

The template

<button (click)="go(page() - 1)"
        [disabled]="page() === 0">Prev</button>

@for (n of pageNumbers(); track $index) {
  @if (n === '…') {
    <span>…</span>
  } @else {
    <button (click)="go(+n - 1)"
            [class.active]="page() === +n - 1">
      {{ n }}
    </button>
  }
}

<button (click)="go(page() + 1)"
        [disabled]="page() === totalPages() - 1">Next</button>

Disable Prev on the first page and Next on the last — cheap guard against invalid requests.

5. The RxJS pattern — page$ → switchMap → results

Declarative paging with streams

Model the current page as a stream. switchMap cancels the previous request when you click quickly — no race conditions, no stale page landing after a newer one.

private page$ = new BehaviorSubject<number>(0);
private size$ = new BehaviorSubject<number>(10);

// re-fetch whenever page OR size changes
result$ = combineLatest([this.page$, this.size$]).pipe(
  debounceTime(0),          // coalesce rapid changes
  switchMap(([page, size]) =>
    this.http.get<Page<User>>('/api/users', {
      params: { page, size }
    })
  ),
  shareReplay(1)
);

go(p: number)   { this.page$.next(p); }
setSize(s: number) { this.page$.next(0); this.size$.next(s); }
<!-- template: async pipe, no manual subscribe -->
@if (result$ | async; as page) {
  @for (u of page.content; track u.id) { … }
  <app-pager [total]="page.totalPages" />
}

Why switchMap matters here

Click page 2, then quickly page 3. Two requests fire. Without cancellation, page 2's (slower) response could arrive last and overwrite page 3.

// ❌ mergeMap — both complete, order not guaranteed
//    page 2 response may land AFTER page 3

// ✓ switchMap — clicking page 3 CANCELS the
//   in-flight page 2 request. Only the latest wins.
click p2 → req2 … click p3 → ❌ cancel req2, req3 wins

💡 Also reset to page 0 whenever a filter or sort changes — otherwise you might ask for "page 9" of a filtered list that only has 2 pages and get an empty screen.

6. Infinite scroll — append instead of replace

Load the next page when you near the bottom

// IntersectionObserver on a sentinel element
@ViewChild('sentinel') sentinel!: ElementRef;
items = signal<User[]>([]);
page = 0; loading = false; done = false;

ngAfterViewInit() {
  const io = new IntersectionObserver(([entry]) => {
    if (entry.isIntersecting) this.loadMore();
  });
  io.observe(this.sentinel.nativeElement);
}

loadMore() {
  if (this.loading || this.done) return;
  this.loading = true;
  this.api.getPage(this.page++).subscribe(p => {
    this.items.update(cur => [...cur, ...p.content]); // APPEND
    this.done = p.last;
    this.loading = false;
  });
}

7. Virtual scrolling & URL state

CDK virtual scroll — render only visible rows @angular/cdk

Showing 10,000 rows in the DOM kills performance. cdk-virtual-scroll-viewport renders only the handful you can see and recycles them as you scroll.

// 1. install: npm i @angular/cdk
import { ScrollingModule } from '@angular/cdk/scrolling';

<!-- 2. template -->
<cdk-virtual-scroll-viewport itemSize="48"
                            class="viewport">
  <div *cdkVirtualFor="let u of users" class="row">
    {{ u.name }}
  </div>
</cdk-virtual-scroll-viewport>

/* .viewport { height: 400px; } */

Use virtual scroll for long client-side lists; combine with server paging for huge datasets.

Keep the page in the URL — shareable & back-button friendly

private route = inject(ActivatedRoute);
private router = inject(Router);

// read page from ?page=3 (drives the fetch)
page$ = this.route.queryParamMap.pipe(
  map(p => Number(p.get('page') ?? 1) - 1)
);

// write page to the URL (don't reload, just update)
go(page: number) {
  this.router.navigate([], {
    queryParams: { page: page + 1 },
    queryParamsHandling: 'merge'
  });
}

✓ Now /users?page=3 deep-links straight to page 3, refresh keeps your place, and the browser back button steps through pages.
