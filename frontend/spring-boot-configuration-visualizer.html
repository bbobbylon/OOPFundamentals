Configuration & Profiles

application.properties vs .yml, @Value, @ConfigurationProperties, and how profiles target dev/staging/prod environments.

⚙️ How does Spring Boot configuration work — and how do you manage dev/staging/prod values?

Spring Boot resolves config from many sources in priority order: command-line args (highest) → environment variables → application-{profile}.properties → application.properties (lowest), and the highest-priority source wins. So one codebase runs everywhere — you change the DB URL, the Ping issuer, or the log level by setting env vars in your deployment, not by editing code. @Value injects one property; @ConfigurationProperties binds a whole group into a typed class; profiles (application-dev.yml, application-prod.yml) layer environment-specific overrides on top of the base config.

  • Externalize, don't hard-code. Env vars override file properties, so one image promotes from dev to prod untouched.
  • Relaxed binding. PING_CLIENT_SECRET (env) maps to ping.client-secret (property) automatically.
  • Prefer @ConfigurationProperties for groups — typed, validatable with @Validated, fails fast on a missing value.
  • Secrets never live in the repo. Keep them in env vars / Key Vault / Secrets Manager and load at startup.

@Value vs @ConfigurationProperties

@Value("${ping.issuer-uri}") — one property inline, fine for 1-2 values. @ConfigurationProperties(prefix="ping") binds all ping.* into a class with issuerUri, clientId, scopes… Add @Validated + @NotBlank and the app refuses to start if a value is missing.

Profiles

Activate with SPRING_PROFILES_ACTIVE=prod. application-dev.yml = local datasource + Ping sandbox + DEBUG; application-prod.yml = prod datasource + real Ping + WARN. Profile files override application.yml. @Profile("dev") beans exist only in that profile.

Never commit secrets

Client secrets, DB passwords, and API keys go in env vars (K8s Secrets), Azure Key Vault / AWS Secrets Manager (loaded at startup), or a git-ignored .env — never application.properties. Spring reads env vars automatically via relaxed binding.

CIAM: @ConfigurationProperties(prefix="oidc") @Validated class OidcConfig with @NotBlank issuer/clientId/clientSecret fails fast if any OIDC value is missing. Dev points at the Ping sandbox, prod at login.contoso.com; a K8s secret OIDC_CLIENT_SECRET auto-binds to oidc.client-secret, and GET /actuator/env shows the effective value with the secret masked as ******.

3 — @Value vs @ConfigurationProperties

@Value — single values

@Service public class EmailService { @Value("${app.smtp.host}") private String host; @Value("${app.smtp.port:587}") // :587 = default private int port; @Value("${app.smtp.username}") private String username; }

Good for: one or two related values. Downside: scattered, harder to see all config for a feature, no auto-completion in some IDEs.

@ConfigurationProperties — groups

@ConfigurationProperties(prefix = "app.smtp") @Component public class SmtpProperties { private String host; private int port = 587; // default private String username; // getters + setters } // application.yml: // app.smtp.host=smtp.example.com // app.smtp.port=465 // app.smtp.username=noreply@example.com

Good for: groups of related config. Type-safe. IDE auto-completion. Validated with @Validated + JSR-303 annotations.

🌱 New here? Config is everything you don't hardcode.

Database URLs, ports, secrets, feature flags, the IDM issuer — none of that belongs baked into your code, because it differs per environment. Spring reads it from application.yml / application.properties (and environment variables) and hands it to your code. The win for a beginner: the same build runs on your laptop and in production just by feeding it different config — you change a value, not a class, and never rebuild to point at a different database. You read a single value with @Value("${server.port}"), or — better — bind a whole group of related settings to a typed class with @ConfigurationProperties.

🧠 Expert corner — precedence, profiles, and keeping secrets out

  • Know the precedence. Later sources override earlier: command-line args > OS env vars > profile-specific application-{profile}.yml > application.yml > defaults in code. This is what lets an env var override a baked-in default with no rebuild.
  • Profiles (application-prod.yml, @Profile("prod")) swap whole sets of config and even beans per environment. Activate with SPRING_PROFILES_ACTIVE=prod.
  • Prefer @ConfigurationProperties over scattered @Value. It binds a typed, validated, grouped object (with relaxed binding: MY_PROP env ↔ my.prop), which is far easier to test and refactor than dozens of string keys.
  • Never commit secrets. Keep passwords, client secrets, and signing material in environment variables, a secrets manager (Vault, AWS/Azure), or Spring Cloud Config — and reference them from the yml. A secret in git history is a leak forever.
  • CIAM tie-in. The resource-server issuer-uri and any client secrets come from env/config per environment (dev IDM vs prod IDM), never from the jar — so promoting a build between environments is purely a config change. See Profiles and Tokens, Keys & Signing.
