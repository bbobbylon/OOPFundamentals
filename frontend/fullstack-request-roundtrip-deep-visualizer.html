Full-Stack Request Round-Trip

This is the capstone: one authenticated GET /api/users, from an Angular button click all the way down to a database row and back to a rendered list — across every layer the other deep-dives cover in isolation. Watch the descent through the SPA, the hop across the network, the descent through Spring to the DB, and the response climbing back up. Then break it three ways.

🔁 What does a full authenticated API round-trip look like — and how do Angular, HTTP, Spring Security, JPA, and the database all work together on a single request?

The full-stack request involves at least 12 distinct steps across 6 layers, each handled by a different framework or protocol. When a user clicks a button in an Angular component: Step 1 — Angular component: a click event triggers a component method. The component calls an Angular service (via dependency injection). Step 2 — Angular service + MSAL interceptor: the service calls httpClient.get('/api/users'). Before the request leaves, Angular's HTTP interceptor chain runs. The MSAL interceptor (or angular-oauth2-oidc interceptor) checks localStorage for a valid JWT, and if one exists, adds Authorization: Bearer {token} to the request headers. If the token is expired, it silently refreshes it first. Step 3 — Browser + CORS preflight: the browser checks if the request is cross-origin (Angular at :4200, API at :8080). If so, it sends an OPTIONS preflight to check if the server allows this. Spring Boot's CORS config responds with the allowed origins/methods/headers. Step 4 — Network: the HTTP/HTTPS request travels across the network. TLS encrypts everything in transit. Step 5 — Spring Security filter chain: the request enters Spring Boot and passes through the SecurityFilterChain. JwtAuthenticationFilter extracts the Bearer token, validates the signature against the JWKS public key, checks iss/aud/exp claims, and creates a JwtAuthenticationToken stored in the SecurityContext. Step 6 — DispatcherServlet routing: Spring MVC routes the request to the matching @RestController method based on @RequestMapping. Step 7 — Controller: the controller method extracts path variables, request params, and @AuthenticationPrincipal Jwt. It validates input (@Valid) and delegates to a service. Step 8 — Service layer: @Transactional begins a transaction. Business logic runs. The service calls a JPA repository method. Step 9 — JPA/Hibernate: Hibernate generates SQL from the repository method name or @Query. Sends it to the DB. Step 10 — Database: SQL executes, returns rows. Hibernate maps rows to entity objects. Step 11 — Response serialization: entities are mapped to DTO/record objects, then Jackson serializes them to JSON. The HTTP response travels back to the browser. Step 12 — Angular response handling: the Observable emits, the component's subscriber runs, the template re-renders with the new data. Three ways it breaks: (1) 401 — token missing/expired/invalid signature; (2) 403 — token valid but missing required scope/role; (3) CORS error — missing Access-Control-Allow-Origin header on the response.

The 3 ways it breaks

// BREAK 1: 401 Unauthorized // Token expired, missing, or invalid signature // Angular: catch in HTTP interceptor, redirect to login or refresh // Debug: decode JWT at jwt.io, check exp claim // Check: jwk-set-uri is correct, kid matches JWKS // BREAK 2: 403 Forbidden // Token valid but missing required scope or role // Spring: @PreAuthorize("hasAuthority('SCOPE_users.read')") failed // Debug: decode JWT, check "scp" and "roles" claims // Fix: update token policy in IdP to include required scope // OR: update @PreAuthorize to match the actual claims // BREAK 3: CORS error // Browser blocks the response (SPA gets no data) // Symptoms: browser console shows "No 'Access-Control-Allow-Origin'" // Spring fix: // @CrossOrigin(origins = "https://app.example.com") on controller // OR: CorsConfigurationSource bean in SecurityConfig // Watch out: "Access-Control-Allow-Origin: *" doesn't work with // credentials (Authorization header) — must be specific origin // BREAK 4: CORS missing "Authorization" in allowedHeaders // The OPTIONS preflight response must allow the Authorization header // config.addAllowedHeader("Authorization"); // CRITICAL

In CIAM / Your Job: This end-to-end request flow is exactly what you build and debug every day. When something goes wrong (and it will — CORS, 401s, 403s, and JWT validation errors are the most common), trace the request layer by layer: (1) Check browser devtools Network tab — is the request being sent? Is the Authorization header present? What's the HTTP status code? (2) Check Spring Boot logs (DEBUG logging for Security) — did the JWT validate? Which step failed? (3) Decode the JWT at jwt.io — are the claims correct (right iss, aud, scp, roles, non-expired exp)? (4) Check JWKS endpoint is accessible from the Spring Boot server (not just from your browser). This systematic approach resolves 95% of auth issues without guessing.

or, readOnly=true is a promise to Hibernate — and Hibernate holds you to it

The problem

The endpoint returns 200. The user list is correct. The one field it's also supposed to update never moves.

getUsersByTenant() looks read-only, so nobody thought twice about what it also does

Section 1's own JPA snippet shows @Transactional(readOnly = true) on getUsersByTenant() — a real, correct optimization: Hibernate skips dirty-checking every loaded entity at commit, because a read-only method has nothing to check. Then someone adds one line inside that same .map(this::toDTO) step: touch user.setLastAccessedAt(now()) on each entity, to power a "last seen" column on an admin dashboard. The endpoint still returns 200. The user list in the response is still exactly right — reads work fine inside a read-only transaction. The one thing that silently never happens is the write: Hibernate set this transaction's flush mode to MANUAL the moment it saw readOnly = true, so the changed lastAccessedAt sits on the in-memory entity, gets discarded when the transaction ends, and never reaches a single row in the database. No exception. No log line. Just a dashboard column that reads "Last seen: never" for every user, forever.

GET /api/users → 200 OK ✓ user list in the response is completely correct ✓ @Transactional(readOnly = true) on a method that also writes ⚠ lastAccessedAt update never flushed, never persisted, no error ⚠

The wrong assumption underneath: that readOnly describes what a method mostly does — Hibernate reads it as an instruction to stop tracking changes at all, not a comment about your intent.

Decide what a method IS before you annotate it, then keep it that way
First move: split the read from the write — getUsersByTenant() stays readOnly = true; recordAccess(userId) gets its own writable @Transactional and is called separately ↓ each method's annotation now matches what it actually does, so Hibernate's optimization only ever applies where it's true Better: if the write genuinely belongs in the same transaction, drop readOnly entirely rather than "mostly" keeping it ↓ readOnly isn't a performance dial you can leave half-on — a transaction either needs dirty-checking or it doesn't The result: the audit write either happens every time, or the annotation stops lying about what the method does
readOnly = true doesn't just hint at the database — it turns off Hibernate's memory of what changed. Once a persistence context's flush mode is set to MANUAL, any entity field you mutate inside that transaction is changed in Java and nowhere else; nothing downstream ever asks "did anything change here?" because you told it, up front, the answer would always be no. That's the same read/write boundary the intro-mini's @Transactional(readOnly = true) comment calls "a hint to the DB" — it's a much bigger hint than it looks.
Think of readOnly = true as telling a stenographer to stop transcribing the meeting. They're still in the room. They can still watch you write on the whiteboard. They just stopped writing any of it down, because you told them at the door this was "just a briefing, nobody's deciding anything here." If someone quietly makes a real decision in minute forty, it happened, everyone in the room saw it — but the official record shows nothing, because the one person whose job was to record it was told in advance not to bother.
You

user.setLastAccessedAt(now()) runs right there in the method. I can see it in the debugger. Why is the database row unchanged?

Hibernate

I saw you set it too — the entity in memory has the new value, I'm not disputing that. But this transaction started with readOnly = true, and the first thing I do with that flag is set my flush mode to MANUAL. Dirty-checking costs time, and you told me not to bother, so at commit I don't compare anything to anything. Nothing to flush means nothing to send.

The transaction manager

And I closed the transaction clean — no rollback, no error. From where I sit, everything about this commit succeeded, because nothing was ever queued to fail.

Your admin dashboard

Which is why I've been showing "Last seen: never" for every user since the day this shipped — and returning a 200 the entire time. No health check was ever going to catch this. I was never broken. I was just reporting the truth about a write that never happened.

The mechanism

One flag changes what Hibernate is even willing to remember.

  1. The controller calls userService.getUsersByTenant(tenantId), annotated @Transactional(readOnly = true)the promise gets made here
  2. Spring opens a transaction and, seeing readOnly = true, sets Hibernate's session flush mode to MANUAL before a single query runsthis is the actual effect of the flag
  3. The repository loads User entities into the persistence context — each one a managed, dirty-checkable object, in principle"in principle" is about to matter
  4. The mapping step sets user.setLastAccessedAt(now()) on each entity while building DTOsa real mutation, on a real managed entity
  5. The method returns; Spring commits the transactionlooks completely normal
  6. Commit does not trigger a flush, because flush mode is MANUAL — Hibernate never compares the entities' current state to what it loaded, so it never notices lastAccessedAt changed at allthe write simply never gets asked about

Step 2 is the lesson. Nothing that happens afterward is Hibernate malfunctioning — steps 3 through 6 are a persistence context and a transaction manager doing exactly what MANUAL flush mode tells them to do. The mutation at step 4 is completely real in Java; it's just never compared against anything, because step 2 already switched off the only mechanism that would have noticed.

The mutation happens inside both rings — the entity is genuinely managed, genuinely changed, for the entire life of a genuinely open transaction. What's missing is inside the inner ring: the one mechanism that would normally ask "did anything change?" at commit time was switched off the moment readOnly = true was read. That makes this stranger than the classic detached-entity bug (a setter fired after the transaction already closed) — every box in this picture is technically still open when the write happens.

A service method is annotated @Transactional(readOnly = true). Inside it, userRepo.findById(id) loads a managed User, and the method calls user.setLastAccessedAt(now()) on it — still inside that same open transaction, before the method returns. Does the update reach the database?

This is exactly what would happen if the method weren't marked readOnly — a genuinely writable transaction absolutely would flush this change at commit. The one thing different here, worth checking before trusting "it's managed, so it'll flush": what flush mode did this specific transaction start in?

This is a real JPA bug — just not this one. An entity does detach the moment its owning transaction closes, which is exactly what happens if findById() opens its own short-lived transaction because the calling method has no @Transactional of its own. Here, the surrounding method IS @Transactional for its entire body, so the entity stays managed all the way through — the write is discarded for a completely different reason.

Right. The entity is managed, the transaction is genuinely still open, and the setter genuinely ran — none of that is in question. What's missing is the one step that would normally notice: flush mode MANUAL means Hibernate never runs its "did anything change?" comparison at commit, so a real, live, managed mutation gets thrown away for lack of anyone ever checking.

Where you've seen this before

A write that's real in exactly one place, and nowhere anyone actually looks.

Your own "last login" column, in production

CIAM systems live and die by exactly this kind of audit timestamp — last login, last MFA challenge, last password change, last consent acceptance. All of them get written from inside a request that's also doing a read (fetch the user, then stamp the access), which is exactly the shape that tempts someone into leaving a convenient readOnly = true on the outer method. A silently-stuck "last login" column isn't just an annoying dashboard bug in this world — auditors and compliance reports read that value.

audit timestamps live in exactly this shape of method

Mutating Redux/NgRx state instead of dispatching an action

Redux and NgRx have the mirror-image version of this bug: state.user.name = 'new' genuinely changes the object in memory, but nothing downstream ever finds out, because the whole framework is built around noticing a new state reference arriving through a dispatched action — not an in-place mutation. Same lesson: the write is real, but bypass the one mechanism that watches for change, and nothing downstream consumes it.

real mutation, unwatched by the framework

Write-behind caching — the write is "done" until you ask where

A write-behind cache marks a value updated immediately and defers the actual database write to a background flush, for speed — a deliberate, useful trade-off, right up until that background flush doesn't happen (a crash, a misconfigured worker) and the "saved" value only ever existed in memory. Same shape again: a write that's completely real in one place and never reaches the place everyone actually queries later.

real in memory, absent from disk
Questions from the back row

Why does Hibernate even offer a MANUAL flush mode? Seems dangerous.

Because dirty-checking every loaded entity at every commit is real, measurable overhead — comparing the current state of every managed object against a snapshot taken at load time, for potentially hundreds of rows, on every single read-only request. For a method that truly never writes, skipping that comparison is a legitimate, meaningful performance win. The danger isn't the flag; it's using it on a method that turns out not to be as read-only as its name suggests.

How would you actually catch this in code review, since nothing throws?

Read @Transactional(readOnly = true) as a hard constraint on everything the method calls, not just a label on the method itself — then trace every setter reachable from inside it, including ones buried in a mapper or a stream .map() call. In practice, the more reliable catch is automated: a test that asserts the database row actually changed after calling the method, not just that the method returned successfully. A 200 response proves the read worked; it says nothing about a write nobody asserted on.

Does readOnly = true do anything at the database level too, or is it purely a Hibernate-side flag?

It can go further than Hibernate, depending on your transaction manager and driver — some setups propagate it down to the JDBC connection itself as a read-only hint. Whether that actually gets enforced (some drivers or databases reject writes outright on a read-only connection; others treat it as an ignorable hint) varies enough by stack that you shouldn't rely on it as a safety net either way. The Hibernate-side flush skip is the one part of this you can always count on — that's the layer this whole bug lives in.

4. Three ways it breaks — and exactly where

CORS — never reaches your code

The browser blocks the response (or the preflight) before Spring's controller runs. You see a console CORS error, the server sees… nothing useful. Fix the allow-list, not the controller.

401 — who are you?

The security filter chain rejects a missing/expired token before the controller. The Angular interceptor catches it, runs a silent refresh, and retries once.

403 — you, but not allowed

Authenticated, but @PreAuthorize said no. The method body never runs. No refresh will help — it's an authorization gap, not an identity one.

🔄 One GET /api/users descends the Angular stack (component → HttpClient → interceptor adds the Bearer), crosses the network past CORS, descends the Spring stack (security filter chain validates the JWT → DispatcherServlet → @PreAuthorize → controller → service → repository → DB), then climbs back as entity → DTO → JSON to update a signal that re-renders the list — and the three classic failures live at distinct layers: CORS (before your code), 401 (filter chain, recoverable by refresh), and 403 (method security, not recoverable by refresh).
