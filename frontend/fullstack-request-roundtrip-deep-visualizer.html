4. Three ways it breaks — and exactly where

CORS — never reaches your code

The browser blocks the response (or the preflight) before Spring's controller runs. You see a console CORS error, the server sees… nothing useful. Fix the allow-list, not the controller.

401 — who are you?

The security filter chain rejects a missing/expired token before the controller. The Angular interceptor catches it, runs a silent refresh, and retries once.

403 — you, but not allowed

Authenticated, but @PreAuthorize said no. The method body never runs. No refresh will help — it's an authorization gap, not an identity one.

6. One-sentence recap

🔄 One GET /api/users descends the Angular stack (component → HttpClient → interceptor adds the Bearer), crosses the network past CORS, descends the Spring stack (security filter chain validates the JWT → DispatcherServlet → @PreAuthorize → controller → service → repository → DB), then climbs back as entity → DTO → JSON to update a signal that re-renders the list — and the three classic failures live at distinct layers: CORS (before your code), 401 (filter chain, recoverable by refresh), and 403 (method security, not recoverable by refresh).
