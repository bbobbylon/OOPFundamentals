The Template Method — Coffee & Tea

Chapter 8. Brewing coffee and steeping tea are almost the same recipe: boil water, brew/steep, pour, add condiments. The Coffee and Tea classes duplicate that whole sequence. Template Method puts the skeleton of the algorithm in a base method and lets subclasses fill in only the steps that differ.

🎯 What is the Template Method pattern — and why is it the pattern that controls who defines the algorithm?

The Template Method pattern defines the skeleton of an algorithm in the base class and defers some steps to subclasses — letting subclasses redefine certain steps of the algorithm without changing the algorithm's structure. The story: Coffee and Tea both do: (1) boil water, (2) brew/steep, (3) pour in cup, (4) add condiment. Steps 1 and 3 are identical. Steps 2 and 4 differ. Without Template Method: both classes duplicate steps 1 and 3. With Template Method: abstract class CaffeineBeverage { final void prepareRecipe() { boilWater(); brew(); pourInCup(); addCondiments(); } abstract void brew(); abstract void addCondiments(); void boilWater() { /* identical code */ } void pourInCup() { /* identical code */ } }. prepareRecipe() is final — subclasses cannot change the order of steps. Hooks: a non-abstract method with a default implementation that subclasses can override optionally. boolean customerWantsCondiments() { return true; } — Coffee overrides to ask the user; Tea just uses the default. The Hollywood Principle: "Don't call us, we'll call you" — the base class calls the subclass, not vice versa.

Hooks vs abstract methods

Abstract method: subclass MUST override — it's a required step. The base class declares it but cannot provide a default. Use when every subclass must provide its own implementation. Hook: subclass MAY override — it's optional. The base class provides a default (often empty or returning true). Use when the step is optional or when most subclasses will want the default. Examples in Spring: WebSecurityConfigurerAdapter.configure(HttpSecurity) — a hook with sensible defaults that you override to customise. OncePerRequestFilter.doFilterInternal() — abstract, you must implement. Template Method draws the line between "this must happen" and "this can be optionally customised".

Template Method in Spring Boot

JdbcTemplate.query(sql, rowMapper): the template method handles connection, PreparedStatement, execution, exception handling. You supply RowMapper.mapRow(ResultSet, int) — the varying step. AbstractEntityManagerFactoryBean.createNativeEntityManagerFactory(): Spring creates the JPA factory using Template Method — you configure, Spring calls your configuration in the right order. OncePerRequestFilter: doFilter() is the template (handles once-per-request guarantee), doFilterInternal() is your abstract step. Spring Batch: AbstractItemStreamItemReader — template for reading, you implement doRead().

Template Method vs Strategy

Both patterns isolate varying behaviour — but differently. Template Method: variation via inheritance. The varying steps are in subclasses. Algorithm skeleton in base class. "I control the algorithm; you fill in the blanks." Tighter coupling — subclass is tied to the base class's algorithm. Strategy: variation via composition. The algorithm is in a separate object. "You pick the algorithm; I delegate." Looser coupling — context doesn't care about the strategy's internals. Rule of thumb: use Template Method when you own the base class and can design the algorithm skeleton. Use Strategy when you want to plug different complete algorithms into an existing context.

In CIAM / Spring Boot: Custom JWT filter: abstract class BaseJwtFilter extends OncePerRequestFilter { final void doFilterInternal(HttpServletRequest req, ...) { String jwt = extractToken(req); // template step Claims claims = validateToken(jwt); // ABSTRACT - Ping vs Entra verif different UserPrincipal principal = buildPrincipal(claims); // ABSTRACT - Ping vs Entra claims differ SecurityContextHolder.getContext().setAuthentication(principal); filterChain.doFilter(req, resp); } abstract Claims validateToken(String jwt); abstract UserPrincipal buildPrincipal(Claims c); }. PingJwtFilter extends BaseJwtFilter validates against Ping JWKS. EntraJwtFilter extends BaseJwtFilter validates against Entra JWKS. The filter chain sequence (extract → validate → build principal → set context) is fixed in the base class. Only the IDP-specific steps differ.

Act 1 — two recipes, 80% identical

Coffee and Tea each have their own prepareRecipe() — and they're almost the same. Boiling water and pouring into a cup are identical; only the middle two steps differ.

Coffee

prepareRecipe() {
  boilWater();
  brewCoffeeGrinds();
  pourInCup();
  addSugarAndMilk();
}

Tea

prepareRecipe() {
  boilWater();
  steepTeaBag();
  pourInCup();
  addLemon();
}
Brain Power. boilWater() and pourInCup() are duplicated verbatim. "Brew the grinds / steep the bag" and "add sugar+milk / add lemon" are really the same two abstract steps — "brew" and "add condiments" — done differently. Generalize, and the duplication vanishes.

Act 2 — the template method

Put the skeleton in an abstract base class. prepareRecipe() is declared final — subclasses can't change the algorithm's shape, only fill in the abstract steps.

abstract class CaffeineBeverage {
  final void prepareRecipe() {     // the TEMPLATE METHOD — final
    boilWater();                  // fixed step
    brew();                       // abstract — subclass decides
    pourInCup();                 // fixed step
    addCondiments();              // abstract — subclass decides
  }
  abstract void brew();
  abstract void addCondiments();
  void boilWater()  { ... }       // shared, written ONCE
  void pourInCup() { ... }
}

Coffee implements brew() = run grinds, addCondiments() = sugar+milk. Tea implements brew() = steep, addCondiments() = lemon. The duplicated steps live in the base class, written once.

Act 3 — hooks: optional steps

A hook is a method with a default (often empty) body that subclasses may override to influence the algorithm. Here it lets a subclass skip condiments.

final void prepareRecipe() {
  boilWater();  brew();  pourInCup();
  if (customerWantsCondiments()) addCondiments();   // guarded by a hook
}
boolean customerWantsCondiments() { return true; }   // hook: default yes

Q: When do I make a step abstract vs a hook?

A: Abstract = the subclass must provide it (the algorithm can't run without it). Hook = the subclass may override it to tweak or opt out, but a sensible default exists. Use the minimum that the algorithm requires.

The principle this chapter hands you

Design Principle — The Hollywood PrincipleDon't call us, we'll call you.

Low-level subclasses don't call into the base class's algorithm — the base class's prepareRecipe() calls down into their brew() and addCondiments() when it's ready. Control lives at the top; subclasses just supply the pieces. This is exactly how a framework (or a lifecycle hook like Angular's ngOnInit) calls your code, not the reverse.

The Template Method Pattern, defined

The Template Method Pattern defines the skeleton of an algorithm in a method, deferring some steps to subclasses. Template Method lets subclasses redefine certain steps of an algorithm without changing the algorithm's structure.
You've used it. Arrays.sort() calls your compareTo(); HttpServlet calls your doGet()/doPost(); Spring's JdbcTemplate owns the connect/execute/close skeleton and calls your RowMapper. Strategy (which we met first) solves a similar problem with composition instead of inheritance — a family of whole algorithms vs. filling in steps of one.

Sort() — the Template Method you call every day

Arrays.sort() is a Template Method: it owns the sorting skeleton (TimSort algorithm) and calls your code for the one thing that varies — how to compare two elements.

// Arrays.sort() owns the skeleton. YOU fill in one step.
Arrays.sort(employees, (Employee a, Employee b) ->
  a.getSalary() - b.getSalary()   // ← the one deferred step
);
// HttpServlet.service() calls your doGet()/doPost()
// Spring's JdbcTemplate owns connect/execute/close — calls your RowMapper
// Angular's ngOnInit is called BY the framework — you don't call it
Design Principle — Encapsulate What VariesThe algorithm skeleton doesn't vary — boil→brew→pour, sort→compare→swap. Only the varying steps (brew, compare) belong in the subclass or callback. Marking the skeleton final means the invariant holds for every subclass or caller.

Template Method vs Strategy — inheritance vs composition

Both patterns solve "algorithm with variations" — but they use opposite mechanisms:

Template Method — inheritance

abstract class BeverageMaker {
  final void make() { boil(); brew(); pour(); }
  abstract void brew();  // subclass fills ONE step
}
class Tea extends BeverageMaker {
  void brew() { steep(); }
}

Base class defines the skeleton; subclasses fill in steps. One hierarchy, tighter coupling.

Strategy — composition

interface BrewStrategy { void brew(); }
class BeverageMaker {
  BrewStrategy strategy;  // whole algorithm is swappable
  void make() { boil(); strategy.brew(); pour(); }
}
// swap at runtime, no inheritance needed

Context holds the whole algorithm as a field. Looser coupling; swap behavior at runtime.

Q: Should I always prefer Strategy since GoF says "favor composition over inheritance"?

A: Not always. Template Method is simpler when the skeleton is truly fixed and only one or two steps vary. Strategy shines when the whole algorithm is swappable, or when you need to change behavior at runtime. Prefer composition by default, but don't refactor to Strategy just to avoid an abstract class — ask whether the runtime flexibility is actually needed.
