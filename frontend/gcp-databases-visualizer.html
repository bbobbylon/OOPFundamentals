Cloud SQL, Firestore & BigQuery — Relational, NoSQL & Analytics

GCP splits "database" into three purpose-built services instead of one general-purpose engine: Cloud SQL for transactional relational data, Firestore for real-time document NoSQL, and BigQuery for serverless analytics at any scale. Picking the right one — and connecting to it the secure way — is most of the job.

🗄️ What are Cloud SQL, Firestore & BigQuery — and why does "which database" become "which of these three"?

GCP doesn't offer one flexible database you bend to every workload — it offers three, each opinionated about a different shape of problem. Cloud SQL is a fully-managed Postgres/MySQL/SQL Server instance: the familiar relational world, with automated backups, patching, and high availability, reached securely through the Cloud SQL Auth Proxy — a small local process that authenticates using the caller's IAM identity and opens an encrypted mTLS tunnel to the instance, so the database itself never needs a public IP or an open firewall rule. Firestore is a document database built for apps, not reports: it stores JSON-like documents in hierarchical collections, and its headline feature is real-time listeners — call onSnapshot() once and your client keeps receiving live pushes every time the underlying data changes, no polling loop required. Unlike DynamoDB's default eventual consistency, Firestore reads are strongly consistent by default. BigQuery throws out the assumptions of both: no server to size, no indexes to tune, no connections to pool. It's a serverless, columnar data warehouse that you pay for by the byte scanned (or by reserved flat-rate slots) — and because a naive query can scan terabytes for a single dashboard chart, the two levers that actually control your bill are partitioning (splitting a table by date/ingestion time so a date-filtered query skips whole partitions) and clustering (sorting storage by a column so a filter on it skips most of the remaining blocks). GCP also has Cloud Spanner — a globally-distributed, horizontally-scalable relational database with external (TrueTime-backed) consistency — for the rare case that needs both SQL joins and planet-scale writes; neither AWS nor Azure has a direct equivalent.

  • Cloud SQL — managed Postgres/MySQL/SQL Server; connect via the Auth Proxy (IAM identity + short-lived cert, no public IP needed).
  • Firestore — document NoSQL, strongly consistent, hierarchical collections/subcollections, live onSnapshot() listeners push updates with no polling.
  • BigQuery — serverless columnar warehouse, no indexes; cost is driven by bytes scanned, controlled by partitioning + clustering.
  • Cloud Spanner — globally-distributed relational DB with external consistency; no direct AWS/Azure equivalent.
  • Pick by workload, not familiarity — transactional app data → Cloud SQL; real-time mobile/web sync → Firestore; analytics on billions of rows → BigQuery.

The CLI happy path

# Cloud SQL: create + connect via Auth Proxy gcloud sql instances create shop-db \ --database-version=POSTGRES_16 --tier=db-custom-2-8192 cloud-sql-proxy shop-project:us-central1:shop-db # BigQuery: query a partitioned table bq query --use_legacy_sql=false \ 'SELECT * FROM orders WHERE order_date = "2026-08-27"'

AWS & Azure comparison

Cloud SQL ≈ RDS / Azure SQL Database (managed relational). Firestore ≈ DynamoDB / Cosmos DB — but Firestore is strongly consistent by default where DynamoDB is eventually consistent by default, and its real-time listeners have no direct DynamoDB equivalent (Streams is pull-based, not a live subscription). BigQuery ≈ Redshift / Azure Synapse — but BigQuery is fully serverless (no cluster to provision) where Redshift/Synapse are provisioned clusters you size and pay for whether or not you're querying.

Spring Boot comparison

Cloud SQL via the Auth Proxy slots straight into your existing NamedParameterJdbcTemplate pattern — the proxy just changes how the JDBC URL resolves and authenticates, your repo/query/rowmapper code is unchanged. Firestore has no JDBC equivalent — it's a document SDK, closer in shape to a Mongo client than JdbcTemplate. BigQuery is typically queried from a batch/reporting service, not your request path — think a scheduled job using the BigQuery Java client, not a controller method.

CIAM in production: Cloud SQL's Auth Proxy pattern is a direct cousin of workload identity: your Spring service authenticates to the database using the same IAM identity Cloud IAM already trusts for everything else — no separate database credential to rotate or leak, no VPC firewall rule to maintain. Firestore's strong consistency + real-time listeners make it a natural fit for session/presence data (is this device still logged in, right now) where DynamoDB's eventual consistency would need extra plumbing to get the same guarantee.

1. Cloud SQL: connect through the Auth Proxy, not a public IP

# Grant the service account permission to connect (once)
gcloud projects add-iam-policy-binding shop-project \
--member="serviceAccount:orders-api@shop-project.iam.gserviceaccount.com" \
--role="roles/cloudsql.client"

# The proxy runs alongside the app (sidecar or local process)
cloud-sql-proxy shop-project:us-central1:shop-db --port 5432

# Spring just points at localhost — the proxy IS the tunnel
spring.datasource.url=jdbc:postgresql://localhost:5432/orders
The instance never needs a public IP, and there's no firewall rule to maintain. The Auth Proxy authenticates using the caller's IAM identity (a service account attached to your Cloud Run/GKE/Compute Engine workload), fetches a short-lived client certificate on your behalf, and opens an encrypted mTLS tunnel to the instance. Compare to RDS: a typical RDS setup relies on VPC security groups (network-level allow-listing); Cloud SQL's Auth Proxy relies on IAM (identity-level authorization) — the same trust model your API already uses for everything else, so there's one fewer credential type to rotate or leak.

2. Firestore: strong consistency + live listeners, no polling

// Subscribe once — the client keeps pushing updates
db.collection("orders").document("order-9001")
.addSnapshotListener((snapshot, error) -> {
// fires immediately, then again on every future write
Order o = snapshot.toObject(Order.class);
updateUi(o);
});
The listener is the whole feature. Most databases make you poll ("has anything changed?") or wire up a separate streams/CDC pipeline to get near-real-time updates. Firestore's addSnapshotListener/onSnapshot keeps an open connection and pushes the new document the instant it changes — the standard building block for live order-status screens, chat, or presence. And because Firestore reads are strongly consistent by default (unlike DynamoDB's default eventual consistency), a client that just wrote a document and then reads it back — even through a different code path — is guaranteed to see its own write.

3. BigQuery: no indexes — partitioning and clustering are the whole cost story

-- Table partitioned by DATE(order_date) at creation time
-- ✅ filters on the partition column → only that day's partition is scanned
SELECT * FROM orders WHERE order_date = "2026-08-27"

-- ❌ no filter on the partition column → scans every partition, every byte
SELECT * FROM orders WHERE customer_id = "cust-42"

-- clustering on customer_id speeds up the second query too,
-- by sorting storage blocks so matching rows cluster together
CREATE TABLE orders (…) PARTITION BY order_date CLUSTER BY customer_id
You are billed for bytes scanned, not rows returned. BigQuery has no B-tree indexes to tune — instead, columnar storage means a query only reads the columns it selects, and partitioning lets it skip entire partitions (whole days/months of data) before it even opens a file. Clustering then sorts the remaining data by a chosen column so a filter on it prunes further within each partition. A query that scans 2 TB instead of 20 GB isn't just slower — on on-demand pricing it's ~100× the dollar cost, which is why "did you filter on the partition column?" is the first question in any BigQuery cost review.
