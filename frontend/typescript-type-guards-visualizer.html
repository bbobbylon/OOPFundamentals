Type Guards & Assertions

The honesty contract you sign with the compiler. x is T, asserts x is T, and the new(-ish) satisfies operator — three different ways to tell TS something it can't figure out on its own, each with a different escape hatch and a different blast radius. Pairs with the Narrowing card.

What are type guards? When does TypeScript need your help?

TypeScript's automatic narrowing (via typeof, instanceof, in) covers most cases. But sometimes you have information TypeScript can't derive on its own. For example: you fetch a response from an API and want to verify it has the shape of a User — TypeScript has no way to check that at compile time because the data comes from the network at runtime. Type guards let you write that runtime check and teach TypeScript to trust it.

In CIAM / Angular work: Validating API responses (isUser(json) after http.get()), checking JWT payload shape before trusting claims, assertNever(action.type) in NgRx reducers to catch unhandled action types at compile time.

1. Why type guards exist

TypeScript's flow analysis can only narrow types based on syntax it recognizes — the operators in the Narrowing card: typeof, instanceof, in, equality, truthiness, discriminated unions. For anything else, you need to teach it what your code knows.

function isUser(x: unknown): boolean {
  return typeof x === 'object' && x !== null && 'id' in x;
}

function handle(x: unknown) {
  if (isUser(x)) {
    // x is still 'unknown' here — TS sees a boolean return, doesn't connect the dots
    x.id; // ✗ Type error
  }
}

The fix: tell TS that isUser isn't just returning a boolean — it's returning a type predicate.

2. Type predicates — x is T

A type predicate is a return type with three parts: parameterName is SomeType. When the function returns true, TS narrows the argument to SomeType in the calling code.

interface User { id: number; name: string; }

function isUser(x: unknown): x is User {
  return (
    typeof x === 'object' && x !== null &&
    'id' in x && typeof (x as any).id === 'number' &&
    'name' in x && typeof (x as any).name === 'string'
  );
}

function handle(x: unknown) {
  if (isUser(x)) {
    x.id;   // ✓ x is User
    x.name; // ✓
  }
}
Anatomy:
• The parameter name on the left of is must match a parameter on the function (or this for methods).
• The type on the right is what the parameter narrows to on the true branch.
• The else branch automatically gets the negation — TS narrows to Exclude<Original, T>. 
function isString(x: unknown): x is string { return typeof x === 'string'; }

function demo(v: string | number | null) {
  if (isString(v)) { v; // string }
  else             { v; // number | null  ← else branch narrows automatically }
}

3. The honesty contract

The compiler will trust your predicate without checking it. That's the whole point — but it also means a lying guard is a runtime time bomb that TS can't detect.

// Lying guard — compiles, runs, crashes
function isUserLying(x: unknown): x is User {
  return true; // ← TS believes you
}

function bad(x: unknown) {
  if (isUserLying(x)) {
    x.id.toFixed(); // ← may crash at runtime if x is not a User
  }
}
The escape hatch is built into the language. A user-defined type guard is a vouching mechanism — TS is asking "are you sure?", and the predicate body is your answer. Write predicates whose checks actually imply the narrowing, and treat them like security boundaries: review carefully, test edge cases, and avoid putting business logic next to them.

Returning a narrower type than the predicate claims

Type predicates use assignability. The predicate can claim a narrower type than what the runtime check would technically allow — that's fine — but if it claims a wider type than its checks justify, the calling code may misuse it.

// Overly narrow claim — strict but safe
function isPositiveInt(x: unknown): x is number {
  return typeof x === 'number' && Number.isInteger(x) && x > 0;
}
// You COULD claim "x is PositiveInt" with a branded type — but the type system has no way
// to enforce the runtime invariant. The brand is your reminder to readers.

4. Generic & reusable guards

The most useful guards are reusable across types. Two patterns:

Array element guard

function isNonEmpty<T>(arr: T[]): arr is [T, ...T[]] {
  return arr.length > 0;
}

function first<T>(arr: T[]): T | undefined {
  return isNonEmpty(arr) ? arr[0] : undefined;
  // inside the guard, arr is [T, ...T[]] — arr[0] is T, not T | undefined
}

Filtering with a guard — the typed .filter() idiom

function isDefined<T>(x: T | null | undefined): x is T {
  return x != null;
}

const values: (string | null)[] = ['a', null, 'b'];
const clean = values.filter(isDefined);
// inferred: string[]   ← without the guard, it'd still be (string | null)[]

This pattern is one of the most quietly load-bearing utilities in any TS codebase. Stick it in a utils/ file and use it everywhere.

Key-based guards on discriminated unions

type Shape =
  | { kind: 'circle'; r: number }
  | { kind: 'square'; side: number }
  | { kind: 'tri'; base: number; h: number };

function hasKind<K extends Shape['kind']>(
  s: Shape, k: K
): s is Extract<Shape, { kind: K }> {
  return s.kind === k;
}

function demo(s: Shape) {
  if (hasKind(s, 'circle')) s.r;     // ✓ s narrowed to circle variant
}

5. Assertion functions — three flavors

Assertion functions are guards that throw instead of returning. After the call, TS narrows the rest of the function as if the check passed — because if it didn't, you wouldn't still be here.

Flavor 1: asserts x is T — narrow a value

function assertIsString(x: unknown): asserts x is string {
  if (typeof x !== 'string') throw new Error('not a string');
}

function demo(v: unknown) {
  assertIsString(v);
  v.toUpperCase(); // ✓ v is string from here down
}

Flavor 2: asserts cond — narrow based on a boolean

function assert(cond: unknown, msg?: string): asserts cond {
  if (!cond) throw new Error(msg ?? 'assertion failed');
}

function demo(v: string | null) {
  assert(v !== null, 'v required');
  v.toUpperCase(); // ✓ v is string
}

Flavor 3: asserts x — equivalent to "x is truthy"

function assertExists<T>(x: T): asserts x {
  if (!x) throw new Error('missing');
}
// On the value side this is just a non-null assert with a different feel.
Assertion-function constraint: the function must have an explicit return type annotation. TS won't infer asserts — you have to write it. Forget it and TS will quietly treat the function as returning void without narrowing.

The narrowed-else trick

// Assertion functions don't have an else branch — control flow goes one way.
// For values that might fail without throwing, prefer a returning predicate.
// Use 'asserts' when failure is genuinely exceptional.

6. Typing Node's assert

If you've used assert from node:assert and noticed the variable narrows after the call — that's because @types/node ships exactly this signature. It's the same pattern; you can write your own framework-grade versions.

// From @types/node, lightly trimmed:
function assert(value: unknown, message?: string): asserts value;
function ok(value: unknown, message?: string): asserts value;

import assert from 'node:assert';

function demo(user?: { id: number }) {
  assert(user, 'user required');
  user.id; // ✓ user is { id: number }
}

7. The satisfies operator

Added in TS 4.9. The motivating problem: you want to check that a value conforms to a type, but keep the value's narrow inferred type for downstream use. as is too loose (it allows lying); a type annotation is too lossy (it widens). satisfies is the middle path.

type Palette = Record<string, string | [number, number, number]>;

const palette = {
  red:   [255, 0, 0],
  green: '#0f0',
  blue:  [0, 0, 255],
} satisfies Palette;

palette.red.length;        // ✓ TS knows red is the tuple — 3
palette.green.toUpperCase(); // ✓ TS knows green is a string
// Without 'satisfies', if you'd typed `const palette: Palette = ...`,
// red would be `string | [number,number,number]` and you'd need a narrow first.

And it still catches typos and missing/extra fields just like an annotation:

const bad = {
  red: 42,    // ✗ Type 'number' is not assignable to 'string | [number,number,number]'
} satisfies Palette;

8. satisfies vs as vs annotation

These three look similar at the call site and behave wildly differently. Mental model:

ToolChecks the value?Keeps the narrow type?Can lie?
const x: T = ...YesNo — widens to TNo
const x = ... as TOnly "overlap" checkNo — becomes TYes — that's its whole job
const x = ... satisfies TYesYes — full inferred shapeNo
type Cfg = { host: string; port: number; tags: string[] };

// Annotation — checks, but tags becomes string[] (you lose the literal length)
const a: Cfg = { host: 'x', port: 80, tags: ['a', 'b'] };
// a.tags  → string[]

// as — bypasses checks entirely
const b = {} as Cfg;        // ✗ at runtime: b.host is undefined, TS thinks it's a string

// satisfies — checks the shape, keeps the literal type
const c = { host: 'x', port: 80, tags: ['a', 'b'] } satisfies Cfg;
// c.tags  → string[]  (still widened, since no `as const`)

// satisfies + as const — checks AND keeps literal-literal type
const d = { host: 'x', port: 80, tags: ['a', 'b'] } as const satisfies Cfg;
// d.tags  → readonly ['a', 'b']

When to reach for each

  • const x: T = ... — when you genuinely want the variable's type to be T (e.g. the value is going to flow into a T-typed argument anyway).
  • x as T — last resort. You know something TS can't see, and you've accepted responsibility for being right.
  • x satisfies T — for config objects, lookup tables, fixture data: anything where you want both "check this matches the shape" and "let me index into specific keys with their narrow types".

10. Schema validators & the API boundary

The biggest practical use for type guards is at the boundary where untyped data comes in — HTTP responses, JSON.parse, localStorage, postMessage. The pattern:

interface User { id: number; email: string; }

function isUser(x: unknown): x is User {
  return (
    typeof x === 'object' && x !== null &&
    'id' in x && typeof x.id === 'number' &&
    'email' in x && typeof x.email === 'string'
  );
}

async function getUser(id: number): Promise<User> {
  const res = await fetch(`/api/users/${id}`);
  const data: unknown = await res.json();
  if (!isUser(data)) throw new Error('malformed user response');
  return data; // ✓ User
}

The "use a real schema library" caveat

Hand-rolled guards are fine for small APIs. For anything bigger, reach for Zod, Valibot, io-ts, or ArkType: you get one source of truth that produces both the runtime validator and the static type.

// Zod sketch — one schema, both runtime check and static type
import { z } from 'zod';

const UserSchema = z.object({
  id: z.number(),
  email: z.string().email(),
});

type User = z.infer<typeof UserSchema>;
// { id: number; email: string }

async function getUser(id: number): Promise<User> {
  const res = await fetch(`/api/users/${id}`);
  return UserSchema.parse(await res.json()); // throws on mismatch
}

11. Combining & composing guards

AND — narrow further

function isUser(x: unknown): x is User { /* ... */ }
function isAdmin(u: User): u is User & { role: 'admin' } {
  return (u as any).role === 'admin';
}

function demo(x: unknown) {
  if (isUser(x) && isAdmin(x)) {
    x.role; // ✓ 'admin'
  }
}

OR — widen the set of accepted shapes

function isStringOrNumber(x: unknown): x is string | number {
  return typeof x === 'string' || typeof x === 'number';
}

Higher-order: build a guard from another guard

function isArrayOf<T>(
  guard: (x: unknown) => x is T
): (x: unknown) => x is T[] {
  return (x): x is T[] => Array.isArray(x) && x.every(guard);
}

const isStringArray = isArrayOf(isString);
if (isStringArray(input)) input.join(', '); // ✓ string[]

12. Anti-patterns & common bugs

x as T compiles where x is totally wrongTS allows any cast where types overlap — and most things overlap with any or {}Use satisfies if you don't actually need to coerce; or cast through unknown as a signal

The "double-cast" smell

// If you find yourself writing this, something has gone wrong:
const x = (something as unknown) as User;

// The double-cast disables TS's overlap check. It's saying "shut up, compiler".
// Almost always: write a proper type guard or use a schema validator.
// The rare legitimate use: bridging two type universes (e.g., legacy untyped API).

The as any bomb

// any propagates outward and silently disables all checking downstream.
function getUser(): User {
  return (fetchData() as any).user;
  // Everything downstream is now "any". The type system is gone.
}

// Prefer 'unknown' + a guard. unknown forces the next step to validate.
function getUserSafe(): User {
  const data: unknown = fetchData();
  if (!isUser(data)) throw new Error('bad shape');
  return data;
}

Decision tree:
• At an API boundary (untyped → typed)? Type predicate or schema library.
• Defining a config / lookup object literal? satisfies.
• The type is wrong and you have proof? Refactor first; as only as a last resort, ideally with a comment explaining why.
• Need to crash on bad input? Assertion function — write it once, reuse everywhere.

🌱 New here? A type guard is a check the compiler trusts.

When a value could be several types, a type guard is the runtime check that proves which one it is — and TypeScript narrows the type accordingly inside that branch. The built-in ones you already know: typeof x === "string", x instanceof Date, "id" in obj, even a plain truthiness check (if (user)). Inside the if, the compiler now lets you use the methods/fields of the narrowed type and stops you from using the others. Guards are how you safely cross from "this is one of a few things" to "this is definitely that thing" — without casting.

🧠 Expert corner — predicates, assertions, and validating at the edge

  • User-defined type predicates. A function returning x is User packages a check and tells the compiler to trust its result: function isUser(x: unknown): x is User { ... }. Now if (isUser(v)) narrows v to User.
  • Assertion functions narrow for the rest of the scope: function assertUser(x): asserts x is User throws on failure, so code after the call treats x as User — great for "fail fast on bad input."
  • Discriminated-union tags are the cleanest guard: switch (shape.kind) narrows each branch with zero boilerplate (see Discriminated Unions).
  • Validate at the boundary. Data from fetch/JSON is unknown at runtime regardless of your types. Don't as it — run it through a real guard or a schema library (e.g. zod) so the type and the runtime value actually agree.
  • as and ! are unchecked escape hatches — they tell the compiler "trust me" with no runtime verification. Prefer a guard; reserve as for cases you've genuinely proven, with a comment.
  • CIAM tie-in. An isAuthenticated(state): state is AuthedState guard means state.user/state.token are only reachable after the check — no "user might be null here?" guesswork.
