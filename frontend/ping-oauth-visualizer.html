OAuth2 with PingFederate

PingFederate acts as an OAuth2 Authorization Server / OIDC Provider. Learn Auth Code + PKCE for Angular SPAs and Client Credentials for Spring Boot APIs.

🎟️ What is OAuth2 with PingFederate — and how does the wrong grant type become a real vulnerability?

OAuth2 lets Angular obtain a token proving "this user authorized these scopes" that Spring verifies without re-asking; PingFederate is the Authorization Server that issues, signs and introspects tokens (and ID tokens when an OIDC provider). The grant type must match the client: Authorization Code + PKCE for browser SPAs (code never in the URL, single-use, PKCE blocks interception), Client Credentials for machine-to-machine (no user, client_id+secret/cert). The implicit grant is deprecated (tokens in the URL). Three token types: access (your API validates), ID (frontend display), refresh (renews, never sent to the API). Ping can issue JWT (verify offline via JWKS) or opaque (introspect for instant revocation) tokens.

  • Ping = Authorization Server — issues/signs/introspects tokens.
  • Match grant to client — Auth Code + PKCE (SPA), Client Credentials (M2M).
  • Implicit is deprecated; access/ID/refresh tokens have distinct jobs.
  • JWT (offline JWKS) vs opaque (introspect) — pick for revocation needs.

In CIAM / Your Job: Core to your daily work — Angular uses Auth Code + PKCE through PingFederate (or PingOne), and your Spring APIs use spring-security-oauth2-resource-server with jwk-set-uri on Ping's JWKS to authenticate every call. The common bugs: aud mismatch (token issued for a different audience), scope not granted (missing from the client registration), and clock skew (a drifted server clock makes valid tokens look expired). Always check the decoded JWT at jwt.ms before debugging Spring config.

or, the authorization code is a single-use ticket, and Angular tore it in half

The problem

Login works. Then, for some users, it works and immediately un-works.

Brain Power

Before you scroll: your callback component reads ?code=… off the URL and exchanges it in ngOnInit. A guard redirect, a refresh, or a restored tab makes that component initialise a SECOND time, with the exact same code still sitting in the address bar. Does the second exchange just fail harmlessly, or does something worse happen to the session the first exchange already created?

Code on the URL callback route initialises → POST /as/token.oauth2 with the code and verifier
First exchange PingFederate accepts → access + refresh token returned, code marked used
Component initialises again code still on the URL → the same code is POSTed a second time
Second exchange reuse detected → invalid_grant, and the tokens from the first exchange may be revoked — back to the login page, and round again

Read the loop and notice where it closes: the failure sends the user back to the start, which mints a fresh code and can reproduce the whole cycle. That is why this so often shows up as a support ticket titled "it randomly logs me out" rather than a stack trace — in a CIAM shop, it clusters specifically around enterprise SSO users, whose browsers are the ones most likely to restore a suspended tab or run behind a proxy that double-fires the redirect. That is why this often presents as a redirect loop rather than as an error — the app never sits still long enough to show one. The state that has to change to break the loop is the URL, which is why clearing the code is the fix that ends it and a retry is the move that sustains it.

Redeem once, and make "once" a property of the code rather than of the component. Guard the exchange on the code itself — record the code you are redeeming and refuse to start a second exchange for the same value; a flag on the component only survives as long as the component does, and the whole problem is that a new one appeared. Strip the code from the URL the moment you read it, with a history replace rather than a navigation, so a refresh, a restored tab or a back button has nothing left to redeem. And let the library do it if you are using one — a certified OIDC client already handles this, and hand-rolling the callback is where this bug is almost always introduced.

A single-use credential means the second attempt is not a retry — it is an incident. Most of what your frontend talks to is idempotent enough that repeating a request is harmless, and every instinct you have built from HTTP says "just try again". Authorization codes are the opposite: reuse is the signature of a stolen code being replayed, so the authorization server is right to treat it as an attack and tear down everything it issued. Your job is to make sure the only reuse it ever sees is a real one.
The code is a cinema ticket, not a season pass. Handing it over twice does not get you a second seat — it gets you removed from the one you were already sitting in.
The mechanism

Six steps, and only one of them is a mistake.

  1. Angular sends the user to /as/authorization.oauth2 with the client id, scope, state and PKCE challengethe flow this page just walked
  2. PingFederate authenticates, then redirects back to /callback?code=…&state=…the ticket, on the doormat
  3. The callback component initialises, reads the code, and POSTs it with the verifier. Tokens come back and are storedlogin succeeded
  4. Something re-initialises the component — a guard redirect, a refresh, a restored tab — while the code is still in the URLthe actual defect
  5. The same code is POSTed again. PingFederate sees a reused code and returns invalid_grantcorrect server behaviour
  6. It also revokes the tokens issued from that code, so the session the user just got is dead — and your error handler sends them back to log inthe loop closes

Step 4 is the only thing here that is wrong, and it is not in your OAuth code at all — it is in how your router and your component lifecycle interact. That is the general lesson worth taking off this page: the OAuth flow is short, well specified and usually correct; the bugs live in the plumbing around it. Which is also why the fix belongs in the plumbing, and why "retry the exchange" — the reflex a failed HTTP call normally deserves — is precisely the wrong move here.

Your Angular callback component exchanges the authorization code in ngOnInit. A guard causes the route to re-enter, so the same code is POSTed to PingFederate twice. The first exchange already succeeded. What is the likely result?

Codes are deliberately not idempotent. Replaying one is the signature of an intercepted code, so caching and re-serving the response would hand an attacker exactly what single-use was designed to prevent. The instinct comes from the rest of HTTP, where retrying is usually safe — and it is the instinct to suspend at the token endpoint.

The verifier is not consumed; it is a value your app holds and can send as many times as it likes, and both of these requests carry the correct one. PKCE binds the redemption to the client that began the flow — which your second request also is. It defends against a different attacker entirely, which is why it does not help here.

Correct — and the revocation is the part that turns a harmless-looking failed request into a logout. Fix it by clearing the code from the URL as soon as you read it and guarding the exchange on the code value rather than on component state, so a second component instance finds nothing to redeem.

1 — OAuth2 Roles in the Ping Context

Authorization Server
PingFederate — issues access tokens, ID tokens, and refresh tokens. Validates client identity. Connects to user directories (AD/LDAP) to authenticate resource owners.
Resource Owner
The logged-in user — the person who owns the data and decides to grant access.
Client
The Angular SPA (or mobile app) requesting access on behalf of the user. Registered in PingFederate as an OAuth Client with a Client ID.
Resource Server
Your Spring Boot API — the service holding the protected data. Validates incoming access tokens by checking PingFederate's JWKS endpoint.
Scope
Permissions the client requests. Defined in PingFederate's OAuth client configuration. Examples: openid profile email api:read

Client Credentials is for service-to-service calls — batch jobs, microservices, CI pipelines. The token represents the application, not a user. Store the client_secret in a secrets manager (HashiCorp Vault, AWS Secrets Manager) — never in code.
