OAuth2 with PingFederate

PingFederate acts as an OAuth2 Authorization Server / OIDC Provider. Learn Auth Code + PKCE for Angular SPAs and Client Credentials for Spring Boot APIs.

1 — OAuth2 Roles in the Ping Context

Authorization Server
PingFederate — issues access tokens, ID tokens, and refresh tokens. Validates client identity. Connects to user directories (AD/LDAP) to authenticate resource owners.
Resource Owner
The logged-in user — the person who owns the data and decides to grant access.
Client
The Angular SPA (or mobile app) requesting access on behalf of the user. Registered in PingFederate as an OAuth Client with a Client ID.
Resource Server
Your Spring Boot API — the service holding the protected data. Validates incoming access tokens by checking PingFederate's JWKS endpoint.
Scope
Permissions the client requests. Defined in PingFederate's OAuth client configuration. Examples: openid profile email api:read

1
User clicks "Login" — Angular generates a cryptographic code_verifier and code_challenge (PKCE). Redirects browser to PingFederate authorization endpoint.
2
PingFederate shows login — Presents HTML login form (or delegates to AD, MFA, etc.). User authenticates.
3
Authorization code issued — PingFederate redirects back to Angular's redirect_uri with a short-lived code parameter.
4
Token exchange — Angular POSTs the code + code_verifier to PingFederate's token endpoint. No client secret needed (PKCE replaces it for SPAs).
5
Tokens returned — PingFederate returns access_token (JWT), id_token (OIDC), and refresh_token.
6
API call with token — Angular attaches the access_token to API requests: Authorization: Bearer <access_token>
7
Spring validates JWT — API verifies token signature against PingFederate's JWKS, checks iss/aud/exp claims, extracts user info. Returns protected data.

# Step 1: Service A requests access token (no user involved) POST https://pingfederate.company.com/as/token.oauth2 Content-Type: application/x-www-form-urlencoded grant_type=client_credentials &client_id=service-a-client-id &client_secret=service-a-secret &scope=api:read api:write # Step 2: PingFederate returns access token { "access_token": "eyJhbG...", "token_type": "Bearer", "expires_in": 3600 } # Step 3: Service A calls Service B GET https://service-b.internal/api/data Authorization: Bearer eyJhbG... # Service B validates the JWT against PingFederate's JWKS # No user involved — machine-to-machine auth

Client Credentials is for service-to-service calls — batch jobs, microservices, CI pipelines. The token represents the application, not a user. Store the client_secret in a secrets manager (HashiCorp Vault, AWS Secrets Manager) — never in code.

3 — Spring Boot Resource Server Config (PingFederate)

# application.yml — validate tokens issued by PingFederate spring: security: oauth2: resourceserver: jwt: # PingFederate OIDC Discovery — Spring auto-configures jwk-set-uri from here issuer-uri: https://pingfederate.company.com/ext/oauth/discovery # OR specify JWKS directly jwk-set-uri: https://pingfederate.company.com/ext/oauth/jwks # Validate audience claim matches your API's expected value: spring.security.oauth2.resourceserver.jwt.audiences: my-api-resource
