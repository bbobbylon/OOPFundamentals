Authentication Journeys & Trees

In Ping AM (formerly ForgeRock AM / OpenAM) you don't code login — you draw it. A journey is a tree of nodes; each node does one small thing and routes to an outcome. This declarative orchestration — "Intelligent Access" — is the single most important concept in a ForgeRock/Ping CIAM build. PingOne DaVinci is the same idea in the cloud.

🌳 What is a Ping AM authentication journey — and why does "drawing" login as a tree unlock more than code?

Ping AM models login not as code but as a declarative tree of small single-responsibility nodes wired by outcomes (Intelligent Access) — instead of if/else in a controller, you drag nodes onto a canvas and the engine traverses the graph at runtime. Each node has a type, design-time config, labelled outcomes, and access to NodeState — the shared bag of data threaded through the journey (username, auth level, device fingerprint, risk score). Nodes come in categories: collectors (gather input), decisions (branch on conditions), actions (send OTP, set auth level), and terminals (Success/Failure). Declarative beats code: adding MFA is drag-and-drop with zero redeploys, A/B testing runs two variants, and Scripted Decision nodes (Groovy/JS) cover anything pre-built nodes can't.

  • Login as a node tree, not code — drag-and-drop, engine traverses at runtime.
  • NodeState threads shared data (username, risk score, device) across nodes.
  • Collector / decision / action / terminal nodes wired by outcomes.
  • Zero-redeploy changes + Scripted Decision (Groovy/JS) for custom logic.

In CIAM / Your Job: Journeys are the central design artifact of every Ping AM deployment. You'll design them (which nodes, how wired), write Scripted Decision nodes in Groovy/JS for custom logic (call a fraud API, check account status, transform claims), debug failures (which node returned which outcome — AM audit logs capture every traversal), and drive the journey from Angular via its REST API. The problem

The MFA node never ran, the tree reached Success, and nothing anywhere logged an error.

A decision node asked about a value nobody had put in the bag yet — and "no" was wired to the easy branch

You add risk-based MFA exactly as advertised: a Risk Score node, then a Decision node reading the score from NodeState, with the high-risk outcome going to an OTP node and the low-risk outcome going straight to Success. Drag, drop, connect, save. No code, no deploy.

Then someone reorders the tree, or an upstream node fails softly, or a device-fingerprint collector returns nothing for a particular browser — and the risk key is simply absent from NodeState when the Decision node reads it. Absent is not high. So the node takes its low-risk outcome, skips the OTP entirely, and hands the user a session. The tree completed successfully. Every node did what it was told. The most dangerous outcome was the default one, and nothing in the canvas made that visible.

tree valid ✓ every node configured ✓ journey reached Success ✓ risk key: absent ⚠ MFA: silently skipped ⚠

Declarative did not remove the bug. It removed the stack trace.

Make the missing case explicit, and make the safe branch the default one
Wire the branch you want when data is MISSING, not just when it is present ↓ "no risk score" should mean "treat as risky", never "treat as fine" — absence is not evidence of safety Point every unhandled or fall-through outcome at Failure rather than letting it drift toward Success ↓ a journey should fail closed, the same way a firewall rule does Then test it like code: walk every path, including the ones where a collector returns nothing
A journey is a program whose variables are a shared untyped bag and whose control flow is drawn with arrows. That buys something real — anyone can add MFA without a deploy — and it costs something equally real: no compiler checks that the key a node reads is one an earlier node wrote, and no reviewer sees a diff. The lesson is not "avoid declarative." It is that declarative moves your errors from build time to run time, so the testing you skipped writing has to come back somewhere.
NodeState is a bag of global variables, and a journey is a program written entirely with them. Everything you were ever taught about globals applies unchanged: any node can write any key, nothing declares what it needs, and the bug is always the distance between where a value was set and where it was read.

NodeState

Because I am a map, and maps have absent keys. I am not typed, not declared, and not validated — any node may write any key at any point, and a node reading a key I do not have gets nothing back. I never throw. I have no opinion about whether the key should have been there.

The Decision node

And I only have the outcomes you drew. "High" and "low" were your two arrows, so an absent value has to come out of one of them — and it will be whichever you configured as the fall-through. I am doing precisely what the canvas says. The canvas just does not draw the third case.

The compiler you no longer have

Which is what I used to be for. In a coded login flow, reading an undeclared variable is a build error, and a reviewer sees the diff in a pull request. Here there is no build and the change was a mouse drag on a Tuesday. So the safety has to come from somewhere else: explicit absent-data branches, fail-closed defaults, and someone actually walking the paths.

The mechanism

Six steps, every one of them behaving correctly.

  1. The engine begins at the start node and walks the tree, carrying one NodeState for the whole journeyone shared bag, start to finish
  2. A collector or action node writes keys into it — username, auth level, device fingerprint, risk scorewrites are implicit, never declared
  3. A Decision node reads a key. Present and high → the MFA branch. Present and low → straight throughthe two cases you drew
  4. Absent → there is no third arrow, so it leaves by the fall-through you configured, which is almost always the permissive onethe case you did not draw
  5. Traversal continues to a terminal. Reaching Success issues a session, exactly as designedno error to log
  6. Your app receives a perfectly valid session with an auth level that never earned it — and cannot tell the differencewhere it becomes your problem

Step 6 is worth dwelling on, because it is where this stops being Ping's concern and becomes your API's. Downstream, the session or token carries an auth level, and your resource server trusts it — it has no view of which path through the tree produced it. This is the same shape as Conditional Access on the Entra side: a policy engine decides at authentication time and leaves only a claim behind, so if the claim can be produced by an unintended path, nothing later in the stack can detect that.

Two of these rows were designed and one was inherited. The fix is not cleverness, it is drawing the third row on purpose: give the node an explicit absent-data outcome, or put a node in front that fails the journey when a required key is missing. Once the third case is on the canvas it gets reviewed like the other two — and the whole problem here was that it was invisible, not that it was hard.

A Decision node branches on a risk score in NodeState: "high" routes to an OTP node, "low" routes straight to Success. On some browsers the upstream device-fingerprint node returns nothing, so the risk key is never written. What does the journey do for those users?

NodeState is an untyped map, and reading an absent key from a map yields nothing rather than raising. If it did throw, this would be a far better bug: loud, immediate, and impossible to ship. The whole difficulty is that it fails quietly and in the permissive direction.

There is no dependency graph to consult. Nodes do not declare which keys they read or write, which is exactly what makes the canvas so easy to rearrange — and exactly why the engine cannot know that one node's output was another node's input. Re-running a collector would also be unsafe in general, since collectors have side effects like prompting the user.

Correct, and the direction matters more than the mechanism: the unhandled case lands on the easy path, so a journey degrades toward less security rather than more. Draw the absent case explicitly and point it at the OTP node or at Failure — and while you are there, check every other outcome that currently falls through to Success.

Where you have seen this before

Low-code moves the bugs. It does not remove them.

A switch with no default, forty years of the same bug

Every language eventually grows exhaustiveness checking — sealed types, assertNever, a compiler warning on a missing case — because the unhandled branch is where bugs live. A node canvas has none of that: unhandled cases are drawn as nothing at all, which is the least visible possible representation.

the missing case is always the bug

Fail-open versus fail-closed, in every security control ever built

A firewall that cannot reach its policy server should drop traffic, not allow it. An auth tree that cannot evaluate risk should challenge, not wave through. The rule is identical and the reason is identical: the failure mode must be the safe one, because the failure mode is the one nobody tested.

absence of evidence is not evidence of safety

Why "no code" needs more testing, not less

No build, no compiler, no pull request, no diff, and a change ships the instant someone clicks save. Every safety net that normally catches a mistake between "I had an idea" and "production" has been removed in exchange for speed. That is a real trade with real upside — it just means the review has to be deliberate, because nothing will force it.

1. A journey is a tree of nodes

Each node reads and writes a shared bag of data called the NodeState (the journey's "shared state"), then returns an outcome that decides the next node. Collectors gather input, decisions branch, and terminal nodes end the tree in Success or Failure. Because it's a graph — not a script — product owners can reshape login (add MFA, social, risk) by dragging nodes, with zero redeploys.

  • Nodes — one responsibility each (collect a password, check a device, send a push).
  • Outcomes — the labelled exits of a node (True/False, Low/High) that wire to the next node.
  • NodeState — shared/transient/secure data threaded through every node (username, risk score, auth level…).
  • Auth Level — a number that climbs as stronger factors succeed; apps and policies can demand a minimum.

4. Auth levels & step-up

The auth level climbs with assurance

Password success might set level 1; passing MFA bumps it to 2; a passkey might be 3. The session carries that number.

// Scripted Decision / Set Session
nodeState.putShared("authLevel", 2);

Apps & policies demand a minimum

A "view balance" page may accept level 1; "wire money" requires level 2 → AM re-enters a journey mid-session (step-up) to raise it, without a full re-login.

// acr / auth-level on the OIDC request
acr_values="urn:...:2"

5. When config isn't enough: Scripted nodes

A Scripted Decision node runs your Groovy/JS against the NodeState — for logic the built-in nodes don't cover (custom risk, calling an external fraud API, shaping claims). It returns one of its declared outcomes.

// Scripted Decision — outcomes: ["low","high"]
var score = deviceProfile.risk();          // your logic
nodeState.putShared("riskScore", score);
if (score > 60) {
  action = Action.goTo("high").build();   // → step-up MFA branch
} else {
  action = Action.goTo("low").build();    // → skip MFA
}

Keep scripts thin — they're powerful but become un-versioned logic. Prefer built-in nodes; reach for scripts only at the edges.

6. The cloud equivalent: PingOne DaVinci

Self-managed ForgeRock AM uses authentication trees. The cloud — PingOne / PingOne Advanced Identity Cloud — uses DaVinci flows: the same draw-your-login idea, but drag-and-drop in a browser with prebuilt connectors (PingOne MFA, social IdPs, risk, fraud vendors, HTTP). Trees live next to your apps; DaVinci runs as a SaaS orchestration layer. The mental model transfers 1:1 — nodes, outcomes, shared flow state, branching.

7. Recap

🌳 A Ping/ForgeRock authentication journey is a tree of nodes that thread a shared NodeState and branch on outcomes — so login adapts per user and per risk (trusted device → frictionless; new device → step-up MFA; bad creds → fail) instead of following a fixed code path. Collectors gather, decisions branch, MFA/risk nodes raise the auth level, and apps/policies demand a minimum to force step-up. Scripted nodes cover the edges; PingOne DaVinci is the cloud twin.
