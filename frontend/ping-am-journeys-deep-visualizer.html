Authentication Journeys & Trees

In Ping AM (formerly ForgeRock AM / OpenAM) you don't code login — you draw it. A journey is a tree of nodes; each node does one small thing and routes to an outcome. This declarative orchestration — "Intelligent Access" — is the single most important concept in a ForgeRock/Ping CIAM build. PingOne DaVinci is the same idea in the cloud.

What is a Ping AM authentication journey — and why does "drawing" login as a tree of nodes unlock capabilities that code alone never could?

Ping AM (formerly ForgeRock Access Management / OpenAM) reimagines login not as code but as a declarative tree of small, single-responsibility nodes connected by outcomes. Instead of writing a Spring Boot controller with if/else branches for MFA, risk checks, and social login, you drag and drop nodes onto a canvas, wire their outcome ports to the next node, and the AM engine traverses the resulting graph at runtime. This is called Intelligent Access (the product feature name). Anatomy of a journey node: each node has a type (what it does), configuration (set once at design time), outcomes (the labelled exit ports — True/False, Low/Medium/High, or outcome-specific like "Email OTP Sent"), and access to the NodeState. NodeState is the shared bag of data threaded through every node in the journey — like a per-session context object. Nodes read previous nodes' outputs from it and write their own outputs into it. Username, authentication level, device fingerprint, risk score — all live in NodeState. Node categories: Collector nodes gather input (Username Collector, Password Collector, Device Profile Collector). Decision nodes branch on conditions (Has Session node, Device Match node, Risk Decision node — routes to Low/Medium/High based on the risk score from a risk engine). Action nodes perform operations (Send Email OTP, Create Persistent Cookie, Set Auth Level). Terminal nodes end the journey with Success or Failure. Why declarative beats code: adding MFA to an existing login journey is a drag-and-drop operation requiring zero redeploys. A/B testing two login flows means running two journey variants simultaneously. Compliance changes (add consent node for GDPR) are handled without touching application code. Business stakeholders can understand and modify the journey diagram. Scripted Decision nodes: for custom logic that pre-built nodes don't cover. Write Groovy or JavaScript that reads from NodeState, calls APIs, evaluates conditions, and sets an outcome. The script has access to the full journey context including headers, profile attributes, and HTTP actions.

NodeState — the shared journey context

// NodeState is Ping AM's per-journey session context // Persisted between nodes; survives redirects // Scripted Decision node (Groovy) reading NodeState: def username = nodeState.get("username") // set by Username Collector def riskScore = nodeState.get("riskScore") // set by Risk Decision node def deviceKnown = nodeState.get("deviceMatch") // set by Device node // Writing to NodeState: nodeState.putShared("customClaim", "value") nodeState.putTransient("otpCode", generatedOtp) nodeState.putEncrypted("sensitive", secretValue) // Three compartments: // putShared() → ends up in the ID/access token claims // (make it into the JWT for downstream use) // putTransient() → exists only for this journey's duration // (OTP codes, intermediate values) // putEncrypted() → stored encrypted (SSNs, raw passwords you verify but never expose) // Setting outcomes: if (riskScore < 30) action.goTo("Low") else if (riskScore < 70) action.goTo("Medium") else action.goTo("High") // The outcome string must exactly match the node's outcome ports!

In CIAM / Your Job: Authentication journeys are the central design artifact of every Ping AM / ForgeRock CIAM deployment. In your role, you'll design journeys (deciding which nodes to use and how to wire them), write Scripted Decision nodes in Groovy or JavaScript to handle custom business logic (call an internal fraud API, check account status, write custom claim transformations), debug journey failures (which node returned which outcome for a given user — AM's audit logs capture every node traversal), and integrate your Angular app with the journey's REST API. The NodeState inspector on this page shows you exactly what data flows between nodes — essential knowledge for writing effective Scripted Decision nodes and for debugging why a user is hitting the wrong outcome path.

1. A journey is a tree of nodes

Each node reads and writes a shared bag of data called the NodeState (the journey's "shared state"), then returns an outcome that decides the next node. Collectors gather input, decisions branch, and terminal nodes end the tree in Success or Failure. Because it's a graph — not a script — product owners can reshape login (add MFA, social, risk) by dragging nodes, with zero redeploys.

  • Nodes — one responsibility each (collect a password, check a device, send a push).
  • Outcomes — the labelled exits of a node (True/False, Low/High) that wire to the next node.
  • NodeState — shared/transient/secure data threaded through every node (username, risk score, auth level…).
  • Auth Level — a number that climbs as stronger factors succeed; apps and policies can demand a minimum.

4. Auth levels & step-up

The auth level climbs with assurance

Password success might set level 1; passing MFA bumps it to 2; a passkey might be 3. The session carries that number.

// Scripted Decision / Set Session
nodeState.putShared("authLevel", 2);

Apps & policies demand a minimum

A "view balance" page may accept level 1; "wire money" requires level 2 → AM re-enters a journey mid-session (step-up) to raise it, without a full re-login.

// acr / auth-level on the OIDC request
acr_values="urn:...:2"

5. When config isn't enough: Scripted nodes

A Scripted Decision node runs your Groovy/JS against the NodeState — for logic the built-in nodes don't cover (custom risk, calling an external fraud API, shaping claims). It returns one of its declared outcomes.

// Scripted Decision — outcomes: ["low","high"]
var score = deviceProfile.risk();          // your logic
nodeState.putShared("riskScore", score);
if (score > 60) {
  action = Action.goTo("high").build();   // → step-up MFA branch
} else {
  action = Action.goTo("low").build();    // → skip MFA
}

Keep scripts thin — they're powerful but become un-versioned logic. Prefer built-in nodes; reach for scripts only at the edges.

6. The cloud equivalent: PingOne DaVinci

Self-managed ForgeRock AM uses authentication trees. The cloud — PingOne / PingOne Advanced Identity Cloud — uses DaVinci flows: the same draw-your-login idea, but drag-and-drop in a browser with prebuilt connectors (PingOne MFA, social IdPs, risk, fraud vendors, HTTP). Trees live next to your apps; DaVinci runs as a SaaS orchestration layer. The mental model transfers 1:1 — nodes, outcomes, shared flow state, branching.

7. Recap

🌳 A Ping/ForgeRock authentication journey is a tree of nodes that thread a shared NodeState and branch on outcomes — so login adapts per user and per risk (trusted device → frictionless; new device → step-up MFA; bad creds → fail) instead of following a fixed code path. Collectors gather, decisions branch, MFA/risk nodes raise the auth level, and apps/policies demand a minimum to force step-up. Scripted nodes cover the edges; PingOne DaVinci is the cloud twin.
