Angular Workspace, Monorepo & Libraries

Multi-project workspaces, ng generate library, secondary entry points, path aliases, and publishing — all the scaffolding for sharing code at scale.

📚 What is an Angular workspace library — and when do you need one?

When several Angular apps share code (components, services, utilities), you can either copy-paste it (bad — copies diverge) or extract a library. One Angular workspace can hold multiple projects: apps (projects/my-app) and libraries (projects/my-lib). A library is a publishable package — it compiles on its own, has its own package.json, and any app can import it via a path alias (@company/auth) or from npm across repos. Unlike a shared folder, a library is built with the Angular Package Format, enabling tree-shaking and secondary entry points.

  • A workspace = one repo with multiple apps + libs sharing a single config and node_modules.
  • A library compiles separately (Angular Package Format) and is consumed via a path alias or npm.
  • Secondary entry points (@company/auth/guards) let consumers import only the slice they need.
  • Develop with ng build lib --watch + ng serve app; the app picks up lib changes via the alias.
  • Always import via the public entry point, never src directly — and build the lib before the app.

Creating and using a library

ng generate library @company/auth creates projects/company-auth/ with package.json, ng-package.json, public-api.ts, and a tsconfig path alias. In any app: import { AuthStore } from '@company/auth'. Build first: ng build @company/auth.

Secondary entry points

Split @company/auth into /core, /guards, /interceptors — consumers import only what they need and tree-shaking drops the rest. Each subpath gets its own ng-package.json with an entryFile.

Build watch mode

Two terminals: ng build @company/auth --watch + ng serve my-app; the app picks up lib changes via the alias. Prod/CI: build the lib, then the app, in order. Never import from src directly.

In CIAM:a platform team ships @company/ciam-angular — AuthStore, authInterceptor, authGuard/roleGuard, OidcCallbackComponent, hasRoleDirective — so every app gets CIAM in ~3 lines: providers: [provideAuth({ issuer, clientId }), provideHttpClient(withInterceptors([authInterceptor]))].

The problem

Nothing in your library is private until every import is forced through the front door.

Reach straight into the folder

You needed one date helper out of @corp/ui. It wasn't in index.ts, and you had a demo in forty minutes, so you typed import { fmt } from '../../../libs/ui/src/lib/internal/date.util'. It compiled. Tests passed. Nobody reviewed the import line.

../../../libs/ui/src/lib/internal/date.util compiles perfectly ✅ renamed a "private" file → 6 apps red ⚠ the "library" is now a folder with extra steps ⚠

Here's the sting: that file has no version, no changelog and no promise attached to it. You just conscripted an implementation detail into the public API of six applications — and no human being wrote that down anywhere.

One door, and let the tooling nail the windows shut
libs/auth/src/index.ts — the entire public surface, in one readable file ↓ because everything else under src/ is now unreachable by contract "@corp/auth": ["libs/auth/src/index.ts"] in tsconfig paths ↓ because the alias is the only spelling a consumer is able to type @nx/enforce-module-boundaries fails the lint on any deep import
index.ts is a contract; the path alias is the only thing that makes it enforceable. Without the alias, "private" is a naming convention — and a naming convention is a thing your teammates violate at 4:50pm on a Friday.
libs/auth/src/index.ts

Four things leave this building: AuthStore, authGuard, authInterceptor, and the AuthUser type. That is the whole list, and the list is the product.

Which is why I got rewritten twice last quarter — refresh races, then IndexedDB — and not one consuming team filed a ticket. They can't name me, so they can't depend on me.

The mechanism

Every consumer, one door, one file.

my-appadmin-app@corp/feature-profilea .spec.ts
from '@corp/auth' ↓ tsconfig paths resolves all four to the same file
libs/auth/src/index.tsthe entire public surface · 4 exports · everything else under src/ is private

This is the part everyone re-learns mid-refactor: the door is not the folder, it is the one file the alias points at. A deep relative import walks past this picture entirely — it never touches the alias, so every private file it brushed against silently joined your public API.

Buildable vs non-buildable is a question about the door, not about the room. A non-buildable library never produces a dist/ at all: the alias points straight at libs/auth/src/index.ts and the consuming app's compiler pulls that TypeScript in as though you had typed it into the app. Nothing to build first, nothing to go stale, fastest inner loop you will ever get. A buildable library compiles on its own through ng-packagr into dist/, and the alias points there instead — which is what you need the day something outside this repo consumes it: another repo, npm, a partner team. The trade is inner-loop speed for independence, and it is not free: buildable means ng build @corp/auth has to finish before any app can compile, which is the "why isn't my change showing up" hour every monorepo team loses exactly once. The index.ts contract is byte-for-byte identical either way. All that changes is what the alias resolves to.

@corp/auth exports only AuthStore from its index.ts; lib/internal/token-cache.ts is deliberately not exported. You rename a method on TokenCache and ship it as a patch release. Overnight, admin-app's build goes red. What actually happened?

Exactly. index.ts only makes a file private if the alias is the only way in. One ../../libs/auth/src/lib/internal/token-cache and semver becomes fiction — you changed something you never agreed was public, and the tool that would have caught it at review time is @nx/enforce-module-boundaries.

Semver describes the public API, and by your own intent TokenCache was never in it. Renaming a private method genuinely is a patch. The version number wasn't the problem; the import that walked around the contract was.

A stale dist/ gives you "module not found" or yesterday's behaviour, and it would break every consumer equally. This broke exactly one app, precisely when a private method was renamed — that is a fingerprint, not a coincidence.

Questions from the back row

Buildable or non-buildable — which do I actually pick?

Default to non-buildable and stay there as long as you can. You make a library buildable when someone outside this repo consumes it, or when a lib is slow enough that you want its output cached independently. Making everything buildable on day one buys you a build-order graph, a stale dist/, and a two-terminal --watch dance in exchange for benefits you don't have yet.

@corp/auth imports from @corp/profile, and @corp/profile imports from @corp/auth. It compiles. Is that fine?

It compiles today. It is also one of the very few design smells a tool can actually prove for you — nx graph draws the loop and the module boundary lint fails on it. A cycle means neither library can be built, tested, versioned or deleted on its own: you own one library wearing two folders. The fix is nearly always a third lib underneath both — @corp/auth-types holding the interface they're really fighting over — or pushing the sideways-reaching code down into the shared one.

Can't I just be disciplined and not deep-import?

You can. Your five teammates, the contractor who onboards Monday, and your own editor cannot — auto-import will cheerfully complete a symbol from ../../libs/ui/src/lib/internal/date.util the instant that symbol is reachable, and it does it without asking. That is why an alias plus a lint rule beats a convention plus a wiki page: one of them fails the pull request, the other one gets read once, on your first day.

2. Library Project Structure

A library project has a specific structure that ng-packagr understands. The key difference from an app: it has a public-api.ts barrel file and ng-package.json.

Library folder layout

public-api.ts — The Barrel File

// projects/my-lib/src/public-api.ts
// Everything exported here is part of the library's PUBLIC API
// Consumers import FROM these exports — never from internal paths

export * from './lib/my-lib.module';
export * from './lib/my-button/my-button.component';
export * from './lib/my-input/my-input.component';
export * from './lib/types/button.types';

// DO NOT export internal helpers, test utilities,
// or implementation details — those are private
// ❌ export * from './lib/internal/renderer.util';
Only export what consumers need. Internal utilities, test helpers, and implementation details should stay private. Exporting too much makes semver breaking changes harder to avoid.

3. Secondary Entry Points

Secondary entry points let consumers import just part of your library — enabling tree-shaking. Without them, importing one component forces the entire library into the bundle.

Creating secondary entry points

projects/my-lib/
src/ ← primary entry
public-api.ts
testing/ ← secondary entry
package.json ← required!
public-api.ts
src/
mock-button.component.ts
animations/ ← secondary entry
package.json
public-api.ts

Secondary entry package.json

// projects/my-lib/testing/package.json
// The "name" matches the import path
{
  "ngPackage": {}
}

// Consumer imports — tree-shakeable!
// Only my-lib/testing bundle is downloaded
import { MockButtonComponent }
  from '@myorg/my-lib/testing';

import { fadeInAnimation }
  from '@myorg/my-lib/animations';

// Angular Material does exactly this:
// @angular/material/button
// @angular/material/table  etc.
Angular Material uses secondary entry points for every component (@angular/material/button, @angular/material/table, etc.). This is why importing just a button doesn't pull the entire Material library into your bundle.

5. Consuming a Library in the Same Workspace

You don't need to publish to npm to use a library in the same workspace. TypeScript path aliases in tsconfig.json map the package name to the built output.

tsconfig.json — path aliases

// tsconfig.json (workspace root)
{
  "compilerOptions": {
    "paths": {  // each key is an import specifier, each value is where TS should actually resolve it
      "@myorg/my-lib": [  // the library's primary entry point — what a plain `import ... from '@myorg/my-lib'` resolves to
        "dist/my-lib"  // points at the BUILT output, not the source — you must build the lib before this resolves
      ],
      "@myorg/my-lib/testing": [  // a secondary entry point — its own importable sub-path, e.g. mock components
        "dist/my-lib/testing"
      ],
      "@myorg/my-lib/animations": [  // another secondary entry point — libraries can have as many as they need
        "dist/my-lib/animations"
      ]
    }
  }
}

Using the library in an app

// In any app in the workspace — imports like npm!
import { MyButtonComponent }  // the real component, from the library's primary entry point
  from '@myorg/my-lib';

import { MockButtonComponent }  // a lightweight test double, from the "testing" secondary entry point
  from '@myorg/my-lib/testing';

// In spec files:
import { MockButtonComponent }  // same import path — specs swap the real component for the mock, no wiring needed
  from '@myorg/my-lib/testing';
Build order matters. The consuming app imports from dist/my-lib, so you must run ng build my-lib before ng build my-app. Use ng build my-lib --watch during development so the dist updates on every change.

8. Versioning & Publishing

Semantic versioning rules

BumpWhenExample
MAJORBreaking public API change1.2.3 → 2.0.0
MINORNew feature, backward compatible1.2.3 → 1.3.0
PATCHBug fix, no API change1.2.3 → 1.2.4

Peer dependencies

// dist/my-lib/package.json
{
  "peerDependencies": {
    "@angular/common": "^17.0.0 || ^18.0.0 || ^19.0.0",
    "@angular/core":   "^17.0.0 || ^18.0.0 || ^19.0.0"
  }
  // DO NOT put angular in "dependencies"
  // That would bundle TWO copies of Angular!
}

Publish workflow

# 1. Build the library
ng build my-lib

# 2. Bump version (in dist/ package.json)
cd dist/my-lib
npm version patch   # or minor, major

# 3. Publish to npm
npm publish
# or: npm publish --access=public  (scoped pkgs)

# Automate with release-it or changesets:
npx release-it
npx changeset  # great for monorepos
Use changesets or release-it to automate version bumps, changelog generation, and publishing. Both support monorepos and integrate with GitHub Actions for fully automated releases.
