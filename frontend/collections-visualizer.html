Java Collections Deep Dive

Full ecosystem overview — hierarchy, implementations, performance, and how to choose the right collection.

📚 What is the Java Collections Framework — and how do you pick the right data structure?

The Java Collections Framework has three roots: List (ordered, dups — ArrayList/LinkedList), Set (no dups — HashSet/TreeSet), and Map (key→value — HashMap/TreeMap). The implementation drives performance: ArrayList is O(1) random access but O(n) mid-insert; HashMap is O(1) but unordered; TreeMap is O(log n) but sorted; LinkedHashMap is O(1) with insertion order. Declare to the interface (List<User>) so you can swap implementations freely.

  • Three roots: List, Set, Map — ordered/dups, unique, key→value.
  • Implementation = performance — pick by access pattern (random get, contains, sorted, ordered).
  • Declare the interface, not the class — List<User>, not ArrayList<User>.
  • Standard collections aren't thread-safe — use ConcurrentHashMap & friends.

List: ArrayList vs LinkedList

ArrayList: backed by an array. get(i): O(1). add(end): amortised O(1). add(middle): O(n) — shifts elements. contains: O(n) linear scan. Use for: almost everything — random access, iteration. LinkedList: doubly linked. add(front/end): O(1). get(i): O(n) — traverses. contains: O(n). Use as a Deque (double-ended queue) not as a List. LinkedList implements Deque: addFirst(), addLast(), pollFirst(), pollLast() all O(1). Rule: if you ever need get(index), use ArrayList.

Set and Map implementations

HashSet / HashMap: O(1) add/contains/get, no ordering. LinkedHashSet / LinkedHashMap: O(1), insertion order preserved — great for caches (LRU with removeEldestEntry). TreeSet / TreeMap: O(log n), sorted by natural order or Comparator. Extra ops: headMap(key), tailMap(key), subMap(from,to), firstKey(), lastKey(). EnumMap: O(1) with minimal memory — keys must be enum values. WeakHashMap: keys held weakly — GC can remove entries when key has no other references. Use for: metadata caches keyed by objects.

Thread-safe collections

Standard collections are NOT thread-safe. Options: Collections.synchronizedList(list) — wraps with synchronized methods (coarse lock — slow under contention). ConcurrentHashMap — fine-grained locking (segment-level), computeIfAbsent(key, k->new Value()) is atomic. CopyOnWriteArrayList — writes copy the entire array, reads lock-free; good for infrequent writes + many readers. BlockingQueue implementations (ArrayBlockingQueue, LinkedBlockingQueue): producer-consumer pattern, blocks on empty (take) or full (put). ConcurrentSkipListMap: thread-safe sorted map alternative to ConcurrentHashMap.

CIAM / Spring Boot: A shared userCache is a ConcurrentHashMap; search results are an ArrayList<UserDto> (random access, returned to Angular); a role set is a HashSet for O(1) contains("CIAM_ADMIN") permission checks; ordered+deduped audit entries use LinkedHashSet; and injected config lists are wrapped in Collections.unmodifiableList().

3. Map Implementations

HashMap

O(1) avg null key OK

Hash table backed. No order guarantee. Allows one null key and multiple null values. Load factor 0.75 triggers rehash.

Use this 90% of the time.

See HashMap internals visualizer →

LinkedHashMap

insertion order O(1) avg

Extends HashMap. Maintains a doubly-linked list of entries. Slightly higher memory. Supports access-order mode (useful for LRU caches).

// LRU cache (access-order, evict eldest) new LinkedHashMap<>(16, 0.75f, true) { protected boolean removeEldestEntry(Map.Entry e) { return size() > 100; } };

TreeMap

sorted keys O(log n)

Red-black tree. Keys sorted by natural order or Comparator. No null key. Implements NavigableMap: floorKey, ceilingKey, subMap, headMap, tailMap.

TreeMap<String, Integer> m = new TreeMap<>(); m.put("banana", 2); m.put("apple", 5); m.floorKey("cherry"); // "banana" m.subMap("a", "c"); // keys a..b

EnumMap

array-backed VERY fast

Keys must be enum values. Internally uses a plain array indexed by enum ordinal. No hashing overhead — fastest possible Map for enum keys.

enum Day { MON, TUE, WED } EnumMap<Day, String> schedule = new EnumMap<>(Day.class);

Hashtable (legacy)

synchronized no null key

Fully synchronized HashMap predecessor. No null keys or values. Slower than HashMap + synchronization wrappers. Never use in new code.

Use ConcurrentHashMap instead.

4. Set Implementations

HashSet

O(1) null OK

Backed by a HashMap (values are a dummy object). O(1) add/contains/remove. No ordering. At most one null element. Default choice for sets.

LinkedHashSet

insertion order O(1)

Backed by LinkedHashMap. Iterates in insertion order. Slightly more memory than HashSet. Use when order of first-seen elements matters.

TreeSet

sorted O(log n)

Backed by a TreeMap. Sorted by natural order or Comparator. No null. Implements NavigableSet: first(), last(), floor(e), ceiling(e), headSet(), tailSet().

Practical pattern: Check if all elements are unique

List<String> words = List.of("apple", "banana", "apple"); // allUnique = true iff no duplicates exist boolean allUnique = new HashSet<>(words).size() == words.size(); // HashSet discards duplicates, so if sizes differ — there were dupes System.out.println(allUnique); // false // Find duplicates Set<String> seen = new HashSet<>(); words.stream() .filter(w -> !seen.add(w)) // add() returns false if already present .collect(Collectors.toList()); // ["apple"]

TreeSet NavigableSet API

TreeSet<Integer> scores = new TreeSet<>(Set.of(10, 20, 30, 40)); scores.first(); // 10 — smallest scores.last(); // 40 — largest scores.floor(25); // 20 — largest element <= 25 scores.ceiling(25); // 30 — smallest element >= 25 scores.headSet(30); // [10, 20] — elements < 30 scores.tailSet(30); // [30, 40] — elements >= 30 scores.subSet(10, 30); // [10, 20] — 10 <= x < 30

5. Queue & Deque

ArrayDeque as Queue (FIFO)

Deque<String> q = new ArrayDeque<>(); q.addLast("first"); // enqueue q.addLast("second"); q.pollFirst(); // "first" — dequeue q.peekFirst(); // peek without removing

Head → [first, second] → Tail. pollFirst() removes from head.

ArrayDeque as Stack (LIFO)

Deque<String> stack = new ArrayDeque<>(); stack.push("a"); // addFirst stack.push("b"); // addFirst stack.pop(); // "b" — removeFirst stack.peek(); // "a" — peekFirst
Prefer ArrayDeque over legacy Stack class. Stack extends Vector and has unnecessary synchronization overhead.

PriorityQueue (min-heap)

// Min-heap (default) PriorityQueue<Integer> pq = new PriorityQueue<>(); pq.add(5); pq.add(1); pq.add(3); pq.poll(); // 1 — always minimum // Max-heap PriorityQueue<Integer> maxPq = new PriorityQueue<>(Comparator.reverseOrder()); maxPq.add(5); maxPq.add(1); maxPq.add(3); maxPq.poll(); // 5 — always maximum

PriorityQueue (Min-Heap) Animation

The heap property: every parent ≤ both children. peek() is O(1) — root is always minimum. poll() and add() are O(log n).

6. Collection Decision Tree

Answer each question to find the right collection for your use case.

Do you need to store key-value pairs?
Do you need unique elements (no duplicates)?
Do you need FIFO queue or LIFO stack behavior (insert/remove from ends)?
Do you mostly read by index, or frequently insert/delete in the middle?
Map sub-question: What ordering do you need?
Set sub-question: Do you need ordering?

HashMap<K, V>

O(1) average for get/put/remove. No ordering guarantee. Handles one null key. The right Map for the vast majority of use cases.

Map<String, Integer> counts = new HashMap<>(); counts.put("apple", 3); counts.getOrDefault("banana", 0); // 0 counts.merge("apple", 1, Integer::sum); // 4

LinkedHashMap<K, V>

Maintains insertion order (or access order for LRU). Slightly heavier than HashMap. Good for caches and ordered iteration.

Map<String, Integer> ordered = new LinkedHashMap<>(); ordered.put("c", 3); ordered.put("a", 1); // iterates c, a — insertion order preserved

TreeMap<K, V>

Red-black tree. Keys sorted ascending (or by Comparator). Use for range queries, navigation, or when sorted output is needed.

NavigableMap<String, Integer> m = new TreeMap<>(); m.put("b", 2); m.put("a", 1); m.put("c", 3); m.firstKey(); // "a" m.subMap("a", "c"); // {a=1, b=2}

EnumMap<K extends Enum, V>

Array-indexed by enum ordinal. Fastest possible Map when keys are a fixed enum. No boxing overhead.

enum Status { OPEN, IN_PROGRESS, DONE } Map<Status, List<Task>> board = new EnumMap<>(Status.class);

HashSet<E>

O(1) add/contains/remove. No ordering. Backed by HashMap internally. Best default Set.

Set<String> visited = new HashSet<>(); visited.add("home"); if (!visited.contains("shop")) { /* visit it */ }

LinkedHashSet<E>

Preserves insertion order with O(1) operations. Use when set members must be iterated in the order they were first added.

Set<String> tags = new LinkedHashSet<>(); tags.add("java"); tags.add("spring"); tags.add("java"); // iterates: java, spring (insertion order, no dup)

TreeSet<E>

Sorted set. O(log n). Supports floor/ceiling/headSet/tailSet for range queries. Good for leaderboards, sorted unique values.

TreeSet<Integer> ranks = new TreeSet<>(); ranks.addAll(List.of(5, 2, 8, 1)); ranks.first(); // 1 ranks.headSet(5); // [1, 2]

ArrayList<E>

Dynamic array. O(1) indexed access. O(1) amortized add to end. Best general-purpose List — use by default.

List<String> items = new ArrayList<>(); items.add("x"); items.get(0); // O(1) items.remove(0); // O(n) — shifts remaining

ArrayDeque<E> (or LinkedList)

For frequent head/tail inserts use ArrayDeque — it's faster than LinkedList for stack/queue operations with no pointer overhead. LinkedList is rarely the right answer.

// Prefer ArrayDeque for head/tail ops Deque<String> deque = new ArrayDeque<>(); deque.addFirst("a"); deque.addLast("b"); deque.pollFirst(); deque.pollLast();

ArrayDeque<E>

Resizable array deque. O(1) for add/remove at both ends. Use as a Queue (FIFO) or Stack (LIFO). Faster than LinkedList for these operations and preferred over the legacy Stack class.

// As Queue Queue<Integer> q = new ArrayDeque<>(); q.offer(1); q.offer(2); q.poll(); // 1 // As Stack Deque<Integer> s = new ArrayDeque<>(); s.push(1); s.push(2); s.pop(); // 2

7. Concurrent Collections

Standard collections are not thread-safe. The java.util.concurrent package provides high-performance concurrent alternatives.

ConcurrentHashMap

segment-locked

Thread-safe HashMap. Uses fine-grained locking (CAS + bin-level locks in Java 8+), so reads are mostly lock-free and writes only lock a small segment. Much faster than Collections.synchronizedMap() under contention.

ConcurrentHashMap<String, Integer> map = new ConcurrentHashMap<>(); map.computeIfAbsent("key", k -> 0); map.merge("key", 1, Integer::sum); // atomic

CopyOnWriteArrayList

copy-on-write

Every mutating operation (add, set, remove) creates a fresh copy of the backing array. Reads are completely lock-free. Expensive writes, cheap reads. Perfect for event listener lists, config lists read far more than written.

List<EventListener> listeners = new CopyOnWriteArrayList<>(); // Reads iterate the snapshot — never CME

BlockingQueue

producer-consumer

ArrayBlockingQueue (bounded) and LinkedBlockingQueue (optionally bounded). put() blocks when full, take() blocks when empty. Foundation of the producer-consumer pattern and thread pools.

BlockingQueue<Task> queue = new ArrayBlockingQueue<>(100); // Producer thread queue.put(task); // blocks if full // Consumer thread Task t = queue.take(); // blocks if empty
Never use in new code: Vector — synchronized ArrayList, replaced by CopyOnWriteArrayList. Hashtable — synchronized HashMap, replaced by ConcurrentHashMap. Stack — synchronized stack, replaced by ArrayDeque. These classes exist only for backward compatibility.

8. Fail-Fast vs Fail-Safe Iterators

Fail-Fast Iterator

Used by ArrayList, HashMap, HashSet, and most standard collections. Tracks a modCount on the collection. If modCount changes during iteration (any structural modification except through the iterator itself), throws ConcurrentModificationException immediately.

  • Best-effort — not guaranteed in all cases
  • Design purpose: detect bugs early
  • Fix: use iterator's own remove()

Fail-Safe Iterator

Used by CopyOnWriteArrayList, ConcurrentHashMap, and other concurrent collections. Iterates over a snapshot of the data at the time the iterator was created. No ConcurrentModificationException. May not reflect modifications made after iteration started.

  • Safe to use from multiple threads
  • Snapshot may be stale
  • Higher memory use (snapshot copy)

The ConcurrentModificationException bug — and the fix

// BUG: modifying list while iterating with for-each (uses iterator internally) List<String> list = new ArrayList<>(List.of("a", "b", "c")); for (String s : list) { if (s.equals("b")) list.remove(s); // throws ConcurrentModificationException! } // FIX 1: Use Iterator.remove() Iterator<String> it = list.iterator(); while (it.hasNext()) { if (it.next().equals("b")) it.remove(); // safe — uses same iterator } // FIX 2: removeIf (Java 8+) — cleanest list.removeIf(s -> s.equals("b")); // FIX 3: collect into new list list = list.stream() .filter(s -> !s.equals("b")) .collect(Collectors.toList());
The same issue applies to Maps: never call map.put() or map.remove() during a for (Map.Entry e : map.entrySet()) loop. Use map.entrySet().removeIf(...) or collect keys to remove in a separate pass.

9. Collections Utility Class

java.util.Collections provides static factory and algorithm methods for any Collection or List.

List<Integer> nums = new ArrayList<>(List.of(3, 1, 4, 1, 5)); // ── Algorithms ───────────────────────────────────── Collections.sort(nums); // [1, 1, 3, 4, 5] Collections.sort(nums, Comparator.reverseOrder()); // [5, 4, 3, 1, 1] Collections.binarySearch(nums, 3); // index (list must be sorted) Collections.reverse(nums); // reverses in place Collections.shuffle(nums); // random permutation Collections.min(nums); // 1 Collections.max(nums); // 5 Collections.frequency(nums, 1); // 2 Collections.disjoint(nums, List.of(9)); // true — no common elements Collections.fill(nums, 0); // replaces all elements Collections.copy(dest, src); // dest must be >= src size Collections.swap(nums, 0, 1); // swaps elements at indices Collections.rotate(nums, 2); // rotates by distance // ── Read-only views ───────────────────────────────── List<Integer> ro = Collections.unmodifiableList(nums); // UnsupportedOperationException on write Set<Integer> ros = Collections.unmodifiableSet(mySet); Map<String,Integer> rom = Collections.unmodifiableMap(myMap); // Note: unmodifiable ≠ immutable — the backing collection can still change! // For truly immutable, use List.of() / Set.of() / Map.of() (Java 9+) // ── Legacy synchronized wrappers (prefer concurrent classes) ─── List<Integer> sl = Collections.synchronizedList(new ArrayList<>()); Map<String,Integer> sm = Collections.synchronizedMap(new HashMap<>()); // Must manually synchronize when iterating! synchronized(sl) { for (Integer i : sl) { } } // ── Factory helpers ────────────────────────────────── List<String> empty = Collections.emptyList(); // immutable empty Set<String> es = Collections.emptySet(); Map<String,Integer> em = Collections.emptyMap(); List<String> one = Collections.singletonList("only"); List<String> fives = Collections.nCopies(5, "x"); // [x, x, x, x, x]
Collections.unmodifiableList() returns a view — if the backing list is modified, the view reflects the change. For a truly immutable list, use List.of() (Java 9+) or List.copyOf().

🌱 New here? Collections are Java's ready-made containers.

When you have a group of objects, you reach for a collection instead of juggling arrays by hand. Three cover almost everything, and you pick by what you need:

  • List (usually ArrayList) — ordered, indexable, allows duplicates. "A sequence of things."
  • Set (usually HashSet) — no duplicates. "A bag of unique things."
  • Map (usually HashMap) — look things up by a key. "A dictionary: key → value."

They're generic — List<String> only holds Strings — so they're type-safe and you never cast. Need order & index → List; uniqueness → Set; lookup by key → Map. That decision tree handles most of your day.

🧠 Expert corner — pick the implementation, and respect the contracts

  • Program to the interface. Declare List<T>/Map<K,V>, instantiate ArrayList/HashMap — so you can swap the implementation later.
  • Know the costs. ArrayList is O(1) random access but O(n) to insert in the middle; HashMap is O(1) average get/put; TreeMap/TreeSet keep keys sorted at O(log n); LinkedHashMap preserves insertion order.
  • equals/hashCode is a contract. HashMap/HashSet only work if keys implement both consistently — and you must never mutate a key after it's in the map (its bucket goes stale). Records give you correct ones for free.
  • Fail-fast iterators. Modifying a collection while iterating it throws ConcurrentModificationException — use the iterator's remove() or removeIf().
  • Immutability. List.of(...)/Map.of(...) create unmodifiable collections — great for constants and defensive returns.
  • Real tie-in. Claim→authority mapping is a Map<String, GrantedAuthority>; a request's roles are a Set<String> (uniqueness matters).
