Reading Stack Traces

A stack trace looks like a wall of noise, but it's a precise story: what went wrong, where it blew up, and how the program got there. The skill is filtering — skip the framework frames, find the first line you own, and (in Java) read the Caused by: chain to the bottom for the real culprit. Do that and most exceptions diagnose themselves.

🐛 What is a stack trace — and how do you read one to find the actual bug in 30 seconds?

A stack trace is the breadcrumb trail of method calls that were executing when an exception was thrown. It shows exactly: which exception was thrown, what the error message is, and the full chain of method calls (the call stack) from where it blew up back to where the original request started. Despite looking like a wall of text, it contains precise diagnostic information — if you know where to look. Structure: ExceptionType: message on the first line. Then a list of stack frames: at com.myco.Class.method(File.java:lineNumber). Each frame is one method call. The FIRST frame is where the exception was thrown. The LAST frame is where the request started (usually a servlet dispatcher or thread pool). Reading strategy: (1) Read the exception type + message — this tells you WHAT went wrong. NullPointerException, DataIntegrityViolationException: unique constraint violated, IllegalArgumentException: JWT expired. (2) Scan for the FIRST frame in YOUR code (com.myco.ciam..., not org.springframework..., not java.util...). This is where YOUR code triggered the problem. (3) Read the Caused by: chain — Java exceptions often wrap other exceptions. PingClientException wrapping HttpClientErrorException wrapping an underlying SSLHandshakeException. The INNERMOST Caused by: at the bottom is usually the root cause. Common patterns: NullPointerException at .getUser() — something you called a method on was null (check what's being returned). DataIntegrityViolationException — a DB constraint was violated (unique, not-null, foreign key). LazyInitializationException — Spring tried to load a JPA lazy collection outside of a transaction. ClassCastException — a value was assumed to be one type but was another (often in JSON deserialization). IDE navigation: In IntelliJ, stack frames in the log console are clickable hyperlinks — click AuthService.java:142 and IntelliJ opens that file at that line.

Common Spring exceptions

LazyInitializationException: "could not initialize proxy — no Session". JPA @ManyToMany loaded lazily, accessed outside transaction. Fix: @Transactional on service method, or use @EntityGraph to eager-fetch. DataIntegrityViolationException: "unique constraint violated: users.email". Concurrent insert of same email. Fix: ON CONFLICT DO NOTHING or catch exception. BeanCreationException: Spring startup failure — bad config, missing bean, circular dependency. Read the full Caused by chain — the root cause is at the bottom and usually readable: "UnsatisfiedDependencyException: No qualifying bean of type PingClient". Fix: missing @Component or wrong bean name. NoSuchMethodError: compile vs runtime version mismatch. A method exists in the version you compiled against but not in the runtime JAR. Fix: check Maven dependency tree for version conflicts. StackOverflowError: infinite recursion. Usually two Spring beans calling each other, or a Lombok @ToString/@EqualsAndHashCode on a bidirectional JPA relationship. Fix: break circular reference.

Reading CIAM stack traces: Spring Boot CIAM startup failure: BeanCreationException: Error creating bean 'securityConfig' → Unsatisfied dependency: No qualifying bean of type 'JwkSetUriJwtDecoderBuilderCustomizer' — Spring Security OAuth2 resource server can't find a required bean. Root cause: missing spring-security-oauth2-jose on the classpath (add to pom.xml). Runtime NullPointerException in provisioning: trace finds PingClient.java:142 — calling .getEmail() on a null UserInfo response. Root cause: Ping SCIM endpoint returned 204 (no body) for a user that was deleted mid-flow. Fix: add null check + handle "user not found" case. LazyInitializationException in admin endpoint: User.roles accessed outside transaction. Fix: @Transactional on the admin service method. 1. How to read one

  • Line 1 = the exception type + message. Often the most useful line — read it literally ("Cannot invoke getEmail() because user is null" ⇒ user was null).
  • The frames below = the call stack, most-recent first. The top is where it threw — but that's frequently framework code.
  • Find the first frame in YOUR package. That's where to put the breakpoint. (com.bob.devhub… / your src/, not org.springframework… / node_modules.)
  • Java: read Caused by: to the BOTTOM. The top exception is often a wrapper; the last caused-by is the root cause.

or, the production trace with zero frames — and why the bug that happens 40,000 times a day tells you less than the one that happens once

The problem

Everything on this page assumes you have a stack trace to read. Sometimes the JVM stops giving you one, on purpose, and never says so.

3am incident. The log says java.lang.NullPointerException and then nothing. No message, no at lines, no Caused by.

You know the drill by now: read line one, find the first frame you own, follow the Caused by chain to the bottom. Except there is no line two. One exception type, no message, not a single frame — and the same endpoint, same build, same JDK, throws a beautiful 40-frame trace with a Java 14+ helpful message when you hit it on your laptop. So you go hunting for the logging config that must be truncating it. There isn't one.

HotSpot did this. When a builtin exception — NullPointerException, ArithmeticException, ArrayIndexOutOfBoundsException, ClassCastException, ArrayStoreException — is thrown implicitly from the same compiled site often enough, the JIT recompiles that site to throw a preallocated instance instead of building a fresh one. Preallocated means shared, and a shared exception cannot carry your call stack or your message, so it carries none. The flag is -XX:+OmitStackTraceInFastThrow and it is on by default. Your laptop never reproduces it because your laptop never ran that line ten thousand times in a row.

logging config is fine ✓ the exception is real ✓ local run shows the full trace ✓ JIT swapped in a shared, stackless exception ⚠ the hotter the bug, the emptier the evidence ⚠

An optimisation that costs you nothing until the day it costs you the only artefact you had.

Recognise the signature before you blame the log pipeline: a builtin exception type, no message, zero frames, prod only, hot path only ↓ a truncating log encoder would cut frames off the end and do it to every exception — this one loses all of them, and only for the JVM's own implicit throws Search the log backwards to just after the last restart or deploy ↓ the earliest occurrences ran interpreted, before the JIT had any reason to optimise the site — those entries carry the complete trace you need, and nobody ever scrolls up that far If there is no early occurrence to find, redeploy with -XX:-OmitStackTraceInFastThrow and wait for the next one ↓ you are paying a small cost on the throw path only, in exchange for evidence — turn it back off once you have the trace if that path is genuinely hot Then treat the heat itself as the finding: a throw site the JIT bothered to optimise is an exception being used as control flow thousands of times a second
A stack trace is not a fact about the exception; it is a cost the runtime chose to pay. Filling one in means walking the stack and allocating an array of frames every single time — cheap once, expensive in a loop. So the JVM stops paying when the same implicit throw turns into a hot path, the same way a logging pipeline samples a repeated message and an error tracker collapses a million events into one row with a counter. Every layer between a failure and your eyes is allowed to decide that the ten-thousandth copy is not worth keeping. Which means the frequency of an error and the quality of your information about it can run in opposite directions — and the first occurrence, right after a restart, is very often the most informative one you will ever get.

The louder the bug, the quieter the evidence.

It is the smoke detector you pulled the battery out of because it went off every time you made toast. It still detects smoke perfectly. It has simply stopped telling you, on the grounds that you clearly already knew. The JVM mutes the alarm it has heard ten thousand times.

Who truncated my stack trace? There's an NPE here with no frames at all.

The JIT compiler

Nobody truncated it — there were never any frames. That line threw so often that I recompiled the method to reuse one preallocated exception object. It's shared by every throw at that site, so it can't carry anyone's particular stack or message.

Your laptop's JVM

Which is why I look innocent. You hit that endpoint four times; I ran it interpreted and built you a full trace each time. I was never under enough pressure to optimise anything.

The log file, 6 hours earlier

And I have what you want. The first dozen occurrences after last night's rollout are complete — type, message, every frame. You just stopped scrolling at the most recent one, like everybody does.

The mechanism

Watch one throw site cool, heat up, and lose its voice.

  1. Deploy at 21:00. Requests arrive; the method runs interpreted. A null slips through and throws an NPE the ordinary way — stack walked, frames allocated, helpful message attacheda perfect trace, logged and ignored
  2. Traffic climbs. The method crosses the JIT's threshold and gets compiled. The throw is still a real, fully-populated exceptionnothing lost yet
  3. The same implicit NPE keeps firing from the same compiled site, thousands of times. HotSpot notices the patternthis is the trigger — repetition, not time
  4. It recompiles to the fast-throw form: one preallocated exception object, reused for every occurrence at that site. Shared object, so no per-throw stack, no message-XX:+OmitStackTraceInFastThrow, on by default
  5. 03:00 — you're paged. Every entry in the last six hours is a bare java.lang.NullPointerException. You conclude the logging is brokenthe wrong suspect, confidently identified
  6. Meanwhile the complete traces are still sitting in the log from 21:00, and a restart would produce more of them — for a while, until the site heats up againthe evidence you have and never look at

Step 6 is the practical one. Everybody debugging a production exception scrolls to the latest occurrence, because recent means relevant. Here that instinct is exactly backwards: the newest entries are the emptiest, and the useful ones are the earliest after the last restart. It is worth knowing this before the night it matters, because at 3am "the log is broken" is a much easier story to believe than "the JVM optimised my diagnostics away".

Read the fan carefully: not one of those reactions is a bug, and not one of them is reported anywhere. The repetition is the input, and the loss of detail is the output — which is why this only ever bites you in production, on your busiest endpoint, during your worst incident. The bug you can reproduce locally is never the one that hits this.

A production log shows dozens of java.lang.NullPointerException entries with no message and not a single at frame. The same build, hit on your laptop, throws a full trace with a helpful "because user.email is null" message. Most likely explanation?

Worth ruling out, and the way to rule it out is the shape of the loss: a size-limited encoder truncates the tail of a long stack and would do it to any large event, including ones you throw yourself. What you have here is total — zero frames, no message — and it is happening only to exception types the JVM throws implicitly. That combination points at the runtime, not the pipeline.

Right, and the tell is exactly the prod/local split: your laptop never runs that line enough times for the JIT to bother. Recovery is cheap — scroll the log back to just after the last restart, where the early occurrences ran interpreted and carry complete traces. If the log doesn't go back that far, redeploy with -XX:-OmitStackTraceInFastThrow and catch the next one. Then take the heat seriously: a throw site HotSpot decided to optimise is an exception firing thousands of times a second, which is usually a bigger problem than the NPE itself.

Async really does cost you frames, and it is a genuine source of confusion on this page's territory — an exception thrown in a worker shows the worker's stack, and the submitting code's frames are simply not in it, because that stack no longer exists. But it costs you the caller's frames, not all of them: you would still see the task's own frames and the executor's. A trace with zero frames is a different phenomenon entirely.

Where you have seen this before

Three more layers that quietly decide the tenth thousand copy of something isn't worth keeping.

Sampling and dedup in your observability stack

Error trackers group identical events into one row with a counter, and log pipelines rate-limit or de-duplicate repeated messages to keep ingest costs sane. Useful — until the event you need to inspect individually is the one that fired a million times, and what survived is a count. Same trade the JVM makes, one layer up and with a billing motive.

aggregation is lossy exactly where volume is highest

Spring Security hides which half of the login failed — deliberately

AbstractUserDetailsAuthenticationProvider defaults hideUserNotFoundExceptions to true, so "no such user" is converted into the same generic BadCredentialsException as "wrong password". That's correct: telling a caller which one it was hands an attacker a user-enumeration oracle. But it also means your own logs lose the distinction, which is why login debugging feels blind. Flip it off in a non-production environment when you need the truth — never in the response to the client.

sometimes the detail is withheld on purpose, and rightly

(Unknown Source) instead of a line number

Compile without debug info and every frame in the trace reads (Unknown Source) — the class is fine, the method name is fine, and the LineNumberTable the trace needs was simply never emitted. Same shape as this page's source-map story in JavaScript: the build optimised away the metadata that makes a trace navigable, and the failure mode is silence rather than an error.

The new sentence: the JVM will stop writing that story at all once an implicit throw gets hot enough — so a message-less, frame-less builtin exception in production is not a broken log, it is a fast-throw, and the full trace is sitting in the same file shortly after the last restart. 3. Language-specific reading

Java

  • Top-down for the stack; bottom-most Caused by: for the root cause.
  • A generic wrapper (DataIntegrityViolationException) hides a specific root (duplicate key … unique constraint) — chase it down.
  • The (File.java:42) suffix is your clickable line number.
  • "…23 more" = frames identical to the enclosing trace; collapsed, not lost.

JavaScript / Angular

  • Skip zone.js & node_modules/@angular frames — find your .ts.
  • Source maps turn a minified main.js:1:99999 into your real file:line.
  • --- async --- markers stitch across await/promise hops — the cause may be above the boundary.
  • "Uncaught (in promise)" = a rejected promise nobody catch'd.

4. One-sentence recap

🪜 Read a stack trace as a story: line 1 is the exception + message (often the whole answer), the frames are the call stack most-recent-first, you skip the framework noise to the first frame you own (that's your breakpoint), and in Java you follow Caused by: to the bottom for the real root cause — using source maps to de-minify JS and the --- async --- markers to cross await boundaries.
