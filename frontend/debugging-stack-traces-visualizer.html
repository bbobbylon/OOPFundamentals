Reading Stack Traces

A stack trace looks like a wall of noise, but it's a precise story: what went wrong, where it blew up, and how the program got there. The skill is filtering — skip the framework frames, find the first line you own, and (in Java) read the Caused by: chain to the bottom for the real culprit. Do that and most exceptions diagnose themselves.

🐛 What is a stack trace — and how do you read one to find the actual bug in 30 seconds?

A stack trace is the breadcrumb trail of method calls that were executing when an exception was thrown. It shows exactly: which exception was thrown, what the error message is, and the full chain of method calls (the call stack) from where it blew up back to where the original request started. Despite looking like a wall of text, it contains precise diagnostic information — if you know where to look. Structure: ExceptionType: message on the first line. Then a list of stack frames: at com.myco.Class.method(File.java:lineNumber). Each frame is one method call. The FIRST frame is where the exception was thrown. The LAST frame is where the request started (usually a servlet dispatcher or thread pool). Reading strategy: (1) Read the exception type + message — this tells you WHAT went wrong. NullPointerException, DataIntegrityViolationException: unique constraint violated, IllegalArgumentException: JWT expired. (2) Scan for the FIRST frame in YOUR code (com.myco.ciam..., not org.springframework..., not java.util...). This is where YOUR code triggered the problem. (3) Read the Caused by: chain — Java exceptions often wrap other exceptions. PingClientException wrapping HttpClientErrorException wrapping an underlying SSLHandshakeException. The INNERMOST Caused by: at the bottom is usually the root cause. Common patterns: NullPointerException at .getUser() — something you called a method on was null (check what's being returned). DataIntegrityViolationException — a DB constraint was violated (unique, not-null, foreign key). LazyInitializationException — Spring tried to load a JPA lazy collection outside of a transaction. ClassCastException — a value was assumed to be one type but was another (often in JSON deserialization). IDE navigation: In IntelliJ, stack frames in the log console are clickable hyperlinks — click AuthService.java:142 and IntelliJ opens that file at that line.

Common Spring exceptions

LazyInitializationException: "could not initialize proxy — no Session". JPA @ManyToMany loaded lazily, accessed outside transaction. Fix: @Transactional on service method, or use @EntityGraph to eager-fetch. DataIntegrityViolationException: "unique constraint violated: users.email". Concurrent insert of same email. Fix: ON CONFLICT DO NOTHING or catch exception. BeanCreationException: Spring startup failure — bad config, missing bean, circular dependency. Read the full Caused by chain — the root cause is at the bottom and usually readable: "UnsatisfiedDependencyException: No qualifying bean of type PingClient". Fix: missing @Component or wrong bean name. NoSuchMethodError: compile vs runtime version mismatch. A method exists in the version you compiled against but not in the runtime JAR. Fix: check Maven dependency tree for version conflicts. StackOverflowError: infinite recursion. Usually two Spring beans calling each other, or a Lombok @ToString/@EqualsAndHashCode on a bidirectional JPA relationship. Fix: break circular reference.

Reading CIAM stack traces: Spring Boot CIAM startup failure: BeanCreationException: Error creating bean 'securityConfig' → Unsatisfied dependency: No qualifying bean of type 'JwkSetUriJwtDecoderBuilderCustomizer' — Spring Security OAuth2 resource server can't find a required bean. Root cause: missing spring-security-oauth2-jose on the classpath (add to pom.xml). Runtime NullPointerException in provisioning: trace finds PingClient.java:142 — calling .getEmail() on a null UserInfo response. Root cause: Ping SCIM endpoint returned 204 (no body) for a user that was deleted mid-flow. Fix: add null check + handle "user not found" case. LazyInitializationException in admin endpoint: User.roles accessed outside transaction. Fix: @Transactional on the admin service method. IntelliJ: hover over a log line in Run console, the clickable hyperlinks jump directly to the file:line. Kubernetes: kubectl logs ciam-auth-7d8c9f-xyz -f streams the Spring Boot log to your terminal — look for the exception in real time.

1. How to read one

  • Line 1 = the exception type + message. Often the most useful line — read it literally ("Cannot invoke getEmail() because user is null" ⇒ user was null).
  • The frames below = the call stack, most-recent first. The top is where it threw — but that's frequently framework code.
  • Find the first frame in YOUR package. That's where to put the breakpoint. (com.bob.devhub… / your src/, not org.springframework… / node_modules.)
  • Java: read Caused by: to the BOTTOM. The top exception is often a wrapper; the last caused-by is the root cause.

3. Language-specific reading

Java

  • Top-down for the stack; bottom-most Caused by: for the root cause.
  • A generic wrapper (DataIntegrityViolationException) hides a specific root (duplicate key … unique constraint) — chase it down.
  • The (File.java:42) suffix is your clickable line number.
  • "…23 more" = frames identical to the enclosing trace; collapsed, not lost.

JavaScript / Angular

  • Skip zone.js & node_modules/@angular frames — find your .ts.
  • Source maps turn a minified main.js:1:99999 into your real file:line.
  • --- async --- markers stitch across await/promise hops — the cause may be above the boundary.
  • "Uncaught (in promise)" = a rejected promise nobody catch'd.

4. One-sentence recap

🪜 Read a stack trace as a story: line 1 is the exception + message (often the whole answer), the frames are the call stack most-recent-first, you skip the framework noise to the first frame you own (that's your breakpoint), and in Java you follow Caused by: to the bottom for the real root cause — using source maps to de-minify JS and the --- async --- markers to cross await boundaries.
