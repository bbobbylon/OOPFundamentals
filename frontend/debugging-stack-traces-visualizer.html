Reading Stack Traces

A stack trace looks like a wall of noise, but it's a precise story: what went wrong, where it blew up, and how the program got there. The skill is filtering — skip the framework frames, find the first line you own, and (in Java) read the Caused by: chain to the bottom for the real culprit. Do that and most exceptions diagnose themselves.

1. How to read one

  • Line 1 = the exception type + message. Often the most useful line — read it literally ("Cannot invoke getEmail() because user is null" ⇒ user was null).
  • The frames below = the call stack, most-recent first. The top is where it threw — but that's frequently framework code.
  • Find the first frame in YOUR package. That's where to put the breakpoint. (com.bob.devhub… / your src/, not org.springframework… / node_modules.)
  • Java: read Caused by: to the BOTTOM. The top exception is often a wrapper; the last caused-by is the root cause.

3. Language-specific reading

Java

  • Top-down for the stack; bottom-most Caused by: for the root cause.
  • A generic wrapper (DataIntegrityViolationException) hides a specific root (duplicate key … unique constraint) — chase it down.
  • The (File.java:42) suffix is your clickable line number.
  • "…23 more" = frames identical to the enclosing trace; collapsed, not lost.

JavaScript / Angular

  • Skip zone.js & node_modules/@angular frames — find your .ts.
  • Source maps turn a minified main.js:1:99999 into your real file:line.
  • --- async --- markers stitch across await/promise hops — the cause may be above the boundary.
  • "Uncaught (in promise)" = a rejected promise nobody catch'd.

4. One-sentence recap

🪜 Read a stack trace as a story: line 1 is the exception + message (often the whole answer), the frames are the call stack most-recent-first, you skip the framework noise to the first frame you own (that's your breakpoint), and in Java you follow Caused by: to the bottom for the real root cause — using source maps to de-minify JS and the --- async --- markers to cross await boundaries.
