Express — Middleware, Routing & Error Handling

The "Flask of Node": a tiny, unopinionated layer over the HTTP server. Everything is middleware — a chain of (req, res, next) functions — and routing, parsing, auth, and errors are all just middleware in the right order.

🚂 What is Express — and why is "everything is middleware" the whole idea?

Express is the most widely used Node web framework — minimal and unopinionated. Its entire model is a middleware pipeline: an ordered list of functions, each (req, res, next). A request enters at the top and flows down; each middleware can read/modify req and res, then either call next() to pass control on, or end the request by sending a response. Body parsing (express.json()), logging, CORS, authentication, and your route handlers are all middleware — the only difference is order and whether they match a path/method. A route handler is just a middleware bound to a method + path (app.get("/users/:id", handler)). Error-handling middleware is special: it takes four args (err, req, res, next) and Express routes thrown/forwarded errors to it. Express gives you the pipeline and the router; you assemble everything else — which is its strength and its weakness.

  • Middleware = (req, res, next) — call next() or send a response.
  • Order matters — parsers/auth go before the routes that need them.
  • Routes are middleware bound to a method + path; :id → req.params.id.
  • Errors → the 4-arg handler (err, req, res, next), registered last.

An Express app, top to bottom

const app = express(); app.use(express.json()); // parse JSON body app.use(logger); // log every request app.use("/api", authMiddleware); // protect /api/* app.get("/api/users/:id", (req, res) => { const id = req.params.id; res.json({ id, name: "Alice" }); }); app.use(errorHandler); // 4-arg, registered LAST app.listen(3000);

Middleware & error handler

// auth middleware — calls next() or ends the request function authMiddleware(req, res, next) { const h = req.headers.authorization; if (!h?.startsWith("Bearer ")) return res.status(401).json({ error: "no token" }); req.user = verifyJwt(h.slice(7)); // attach to req next(); // pass control on } // error handler — FOUR args marks it special function errorHandler(err, req, res, next) { res.status(err.status || 500) .json({ error: err.message }); }

Spring Boot comparison

Express middleware ≈ the Servlet filter chain / Spring HandlerInterceptor. app.get("/users/:id", h) ≈ @GetMapping("/users/{id}"); req.params.id ≈ @PathVariable, req.query ≈ @RequestParam, req.body ≈ @RequestBody. express.json() ≈ Jackson's automatic body binding. The 4-arg errorHandler ≈ @RestControllerAdvice / @ExceptionHandler. The big difference: Spring auto-configures the chain and uses annotations + DI; Express makes you wire every piece explicitly with app.use(). Angular's HTTP interceptors are the same shape as Express middleware — intercept, modify, call next.

CIAM Express BFF: A typical layout — express.json(), then a request-id + logger, then cors() whitelisting the SPA origin, then a JWT authMiddleware on /api that verifies the Ping/Entra RS256 token and sets req.user = {sub, roles}. Route handlers gate on req.user.roles and return 403 if missing. A final 4-arg errorHandler turns any thrown error into a consistent JSON shape (RFC 7807-style) so the Angular client always parses errors the same way. Order is everything: put cors() before auth so the browser preflight is answered before the token check.

or, Express doesn't read your code — it counts your parameters

The problem

You added a default value to next. Now your error handler never runs.

The function still has four names in its parentheses

Someone got a next is not a function warning once, so the team's error handler got "defensively" rewritten as function errorHandler(err, req, res, next = () => {}). It shipped fine — nothing threw, the linter was happy, and the four-argument shape is right there in the signature. Weeks later a downstream service started timing out, and every failing request came back as Express's default HTML "Cannot GET" error page instead of your JSON envelope — as if the error handler had vanished. It hadn't been deleted. It had been unregistered by a single = () => {}.

four names between the parens ✓ no typos, no missing import ✓ next = () => {} default value ⚠ function length dropped from 4 to 3 ⚠

Express never reads your parameter NAMES. It reads how many of them count toward .length — and a default value stops the count.

Never give the error handler's next a default
function errorHandler(err, req, res, next = () => {}) ↓ a default value on ANY parameter stops Function.length from counting it, or anything after it Better: function errorHandler(err, req, res, next) ↓ four plain parameters, no defaults — .length is 4, and Express files it as the error handler again Failures return your JSON envelope again, not Express's default page
Express doesn't check your syntax — it counts arguments. The only thing that marks a middleware as an error handler is fn.length === 4: not a type, not a name, not where you registered it, just a plain integer JavaScript computes off the function's own parameter list. That single fact is why next "must" be the fourth parameter even though your handler rarely calls it, why a default value is dangerous on that exact signature, and why an error handler that looks completely right can still be invisible to Express.
Think of Express's dispatcher as a bouncer who checks party invitations by headcount only — never by reading a single name on the guest list. Four people walk up together, they're waved into the "error handling" room, no questions asked about who they are. Show up as three people and a stroller and the bouncer doesn't debate whether the stroller "kind of" counts — three is three. Where it stops being accurate: a real bouncer might still glance at faces. Express's headcount check is the entire rule, with no fallback and no second look.
The mechanism

One property decides your handler's whole job: fn.length. Express never looks at your source — it reads exactly one number off the function, once, at registration.

app.use(errorHandler) registers the layer→ Express reads fn.length once, at registration time→ next = () => {} on the 4th param drops fn.length from 4 to 3→ Express files the layer as regular middleware, not the error handler→ a real error finds no fn.length === 4 layer left to catch it
  1. You register middleware with app.use(fn). Express doesn't run it yet — it just stores the function in an ordered list of layersjust a list, so far
  2. For each stored layer, Express reads fn.length once — a built-in JS property computed from the parameter listthe whole test
  3. fn.length === 4 files a layer as an error handler; anything else files it as regular middleware, no matter the parameter namesthe branch
  4. A normal request only ever walks the regular-middleware layers, top to bottom, calling next() to advancethe happy path
  5. Something calls next(err), or an Express 5 handler's promise rejects. Express switches lanes: it now skips every regular layer, hunting only for the next layer with fn.length === 4the error path
  6. next = () => {} on your error handler is scored during step 2, before any request ever arrives — so the misfiling happens once, silently, at startup, and every request after that inherits itwhy nobody noticed sooner

Step 2 is the lesson. Express makes its most important routing decision — "is this an error handler?" — at REGISTRATION time, off a number it computes once and never rechecks against what the function actually does. Everything downstream, step 3's branch and step 5's error-path search, just trusts that one number. Get it wrong and the mistake stays invisible until the exact moment you need the error path.

This is the funnel with the bug already baked in: every layer on the stack — including the one written specifically to catch errors — scores 3. The search for a 4 comes up empty, so it funnels all the way down to Express's own generic handler: the one that renders the default HTML page you never wrote.

Two teammates each try to guard the error handler against a missing next. Handler A: function errorHandler(err, req, res, next = () => {}) { res.status(500).json({error: err.message}); }. Handler B: function errorHandler(err, req, res, next) { next = next || (() => {}); res.status(500).json({error: err.message}); }. Which one does Express still register as the error handler?

Tempting, because both handlers are visibly trying to guard against a missing next — and one of them really does break arity. But .length only inspects the declared parameter list up to the first default or rest parameter; whatever a function does inside its BODY — an if, a || fallback — is invisible to it. Handler B's parameter list is still four plain names with no default, so its length is still 4.

This gets the rule backwards. A default value on a parameter is exactly what stops the count — Handler A declares next = () => {}, so JavaScript stops counting at next and reports 3. Handler B's next = next || (() => {}) is a plain assignment statement inside the function body, not a parameter default, so it never touches .length at all.

Right. .length is computed once, from the parameter list only, up to the first parameter with a default or a rest parameter — the function body is never read. Handler A declares a default on next, so counting stops there and Express sees 3; it gets filed as regular middleware. Handler B declares four plain parameters and does its guarding in the body instead, so it still reports 4 and keeps its job.

Where you've seen this before

Three frameworks all read your function's signature to decide what it does — they just trust a different part of it.

Spring MVC does the same trick, more carefully

Spring picks how to invoke an @RequestMapping method by reflecting over its parameter list too — matching @PathVariable, @RequestBody, Principal, HttpServletResponse by type and annotation, not by position or count. Same underlying idea as Express — read the signature, decide the behavior — but Spring inspects types and annotations instead of one integer, so reordering a controller method's parameters doesn't silently reclassify what the method IS the way a stray default value does in Express.

signature-based dispatch, sturdier version

pytest fixtures: matched by name, not count

pytest inspects a test function's parameters too, but it trusts the NAMES: write def test_login(db_session, mock_idp): and pytest injects whichever fixtures are registered under those exact names. Get the count right but a name wrong and you get a loud "fixture not found" error — nothing like Express quietly rerouting your handler to the wrong internal list. Same goal, different part of the signature trusted, and that choice is what decides how loudly each framework fails you.

same idea, different part of the signature trusted

Your CIAM gateway's error handler, gone quiet

The intro's error handler formats every failure into one RFC-7807-style JSON envelope for the Angular client. Questions from the back row

Why would Express build something this important around a raw number instead of a special class or a naming convention?

Because Express predates a lot of what would make that convenient — no TypeScript in the original codebase, no decorators — while Function.prototype.length already existed as a free, zero-config way to introspect a function. It's pragmatic API design: cheap to implement, cheap to check, and it works right up until a parameter default silently changes the number it reads. The fix the ecosystem converged on isn't a language change; it's a house rule — never put a default value on an error handler's parameters.

Does this arity trick apply anywhere else in Express, or just error handlers?

It's specifically how error middleware is told apart from regular middleware — the one place in Express where argument COUNT changes what a function IS, not just what it receives. Regular middleware and route handlers don't have this trap: extra or defaulted parameters there just receive undefined or their default value, and nothing reads .length to reroute them. That's exactly what makes the error-handler case surprising — it's the one signature in the whole framework where arity is load-bearing.

How would I actually catch this before it reaches production?

Log your middleware stack's arities at startup — app._router.stack.map(l => l.handle.length) — and assert your error handler is the one 4 in that list. Or sidestep the whole class of bug: never put a default value or destructured parameter on an error handler's signature, full stop. The cheapest real safety net is a five-minute integration test that deliberately throws inside a route and asserts the response is your JSON shape, not Express's default HTML page.

1. The middleware signature

// every middleware has the same shape
function mw(req, res, next) {
  // 1. read/modify req & res
  req.startTime = Date.now();
  // 2. EITHER pass control on…
  next();
  // …OR end the request (don't call next):
  // res.status(401).json({ error: "unauthorized" });
}
app.use(mw); // runs for every request, in registration order
next() is the baton. Forget to call next() (and don't send a response) and the request hangs forever. Call next(err) with an argument and Express skips ahead to the error-handling middleware. That single convention drives the whole pipeline.

2. Routers split a big app into modules

// users.routes.js
const router = express.Router();
router.get("/", listUsers);
router.get("/:id", getUser);
router.post("/", createUser);
export default router;

// app.js — mount under a base path
app.use("/api/users", router); // GET /api/users/:id → getUser

A Router is a mini-pipeline you mount under a prefix — the Express equivalent of grouping endpoints in a @RequestMapping("/api/users") controller.

3. Async errors need forwarding

// ❌ in Express 4, a rejected promise is NOT caught automatically
app.get("/u/:id", async (req, res) => {
  const u = await db.find(req.params.id); // throws → unhandled
  res.json(u);
});

// ✅ wrap, or use Express 5 (auto-forwards rejections)
app.get("/u/:id", (req, res, next) =>
  db.find(req.params.id).then(u => res.json(u)).catch(next));
