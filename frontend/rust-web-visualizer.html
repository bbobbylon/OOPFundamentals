Rust Web — Axum, Tokio & Type-Driven Handlers

How Rust builds web services: Tokio (the async runtime) drives thousands of concurrent connections on a small thread pool, and Axum turns ordinary async fns into handlers — wiring requests to them through the type system with extractors. Fast, safe, and remarkably ergonomic.

🦀 What is the Rust web stack — and why async + types?

A Rust web server has two layers. Underneath is Tokio, an asynchronous runtime: instead of one OS thread per request (expensive), Tokio runs many futures (lazy state machines produced by async fn) on a small pool of worker threads. When a future hits .await on I/O that isn't ready, it yields the thread so another task can run, and the runtime resumes it later when the data arrives. That's how a handful of threads serve tens of thousands of concurrent connections. On top sits Axum (built on the tower middleware ecosystem and hyper). You write plain async fn handlers and register them on a Router (route("/users/:id", get(show))). The magic is extractors: each handler argument is a type that knows how to pull itself out of the request — Path(id): Path<u32> parses a URL segment, Json(body): Json<CreateUser> deserializes and validates the JSON body, State(db) injects shared state. If an extractor can't produce its value (bad JSON, missing param) it returns a rejection — a 400/422 — and your handler never runs. The return type implements IntoResponse, and a Result<Json<T>, AppError> maps cleanly onto status codes. The result: the compiler verifies your request wiring, and the same ownership/borrow guarantees from the language carry into a fearlessly-concurrent server.

  • Tokio — async runtime; futures yield on .await so few threads serve many connections.
  • Axum Router — map method + path → an async fn handler (on tower/hyper).
  • Extractors — typed handler args parse the request; failure → an automatic rejection.
  • IntoResponse + Result — return types become responses; errors map to status codes.

A router and a handler

let app = Router::new() .route("/users/:id", get(show)) .with_state(db); async fn show( State(db): State<Db>, // shared state Path(id): Path<u32>, // URL segment → u32 ) -> Result<Json<User>, AppError> { let u = db.find(id).await?; // ? propagates err Ok(Json(u)) // → 200 + JSON }

Spring Boot comparison

Tokio ≈ the Netty event loop / Spring WebFlux's reactor — non-blocking I/O on few threads. The Router ≈ @RequestMapping. Extractors are the killer feature: Path<u32> ≈ @PathVariable, Json<T> ≈ @RequestBody + @Valid, State<T> ≈ an injected bean — but type-checked, so a wiring mistake won't compile. tower middleware ≈ the servlet filter chain. IntoResponse ≈ ResponseEntity; Result<T, AppError> ≈ a @ControllerAdvice exception handler mapping errors to status codes.

CIAM with Axum: a JWT-verifying API gateway is a natural fit — a tower middleware (or a custom extractor like AuthUser) verifies the RS256 token against the IdP's JWKS and rejects with 401 before the handler runs; an extractor that checks a claim/scope can reject with 403. Because extraction is type-driven, a handler that needs an authenticated admin simply takes an AdminUser argument — if the request can't satisfy it, Axum returns the rejection and the handler body is unreachable (the compiler guarantees you handled it). Tokio's non-blocking I/O keeps token introspection and JWKS fetches off the worker threads, and Rust's no-GC determinism keeps auth-hot-path latency predictable.

or, the synchronous function call sitting quietly inside an async fn, waiting to freeze your whole server

The problem

Tokio only ever gets a chance to switch tasks at an .await point — write a function with no .await in it anywhere, and the runtime has no way to know you're even still running.

Your login endpoint's password check froze every other request on the server

A POST /login handler checks the password with bcrypt::verify(password, &stored_hash) — a plain, synchronous Rust function. There's no .await inside it because there's nothing to await: bcrypt's work is pure CPU (deliberately expensive hashing), not I/O. It compiles cleanly, uses the exact extractor pattern this page already showed you, and returns the right answer every time you test it.

Tokio's default runtime spins up one worker thread per CPU core — say 4, on a 4-core box. Four login attempts land at once, one task per worker thread. Every one of those threads now runs bcrypt::verify's hashing loop to completion — deliberately slow, around 250ms at a realistic cost factor — and none of them can do anything else until it finishes, because nothing in that call ever yields. A fifth request for something totally unrelated, GET /health, gets spawned as a task at the same moment — and there is no free worker thread anywhere to poll it on. It queues behind all four logins for the same 250ms, even though its own handler never touches bcrypt, a database, or anything slow at all.

handler signature and extractors ✓ bcrypt verifies the password correctly ✓ compiles clean, returns 200 with no errors ✓ the CPU-bound call never yields its thread ⚠

Async Rust doesn't preempt tasks the way an OS scheduler preempts threads — it cooperates. A task that never says .await never gives anyone else a turn.

Move CPU-bound work off Tokio's worker threads entirely
Wrap it in tokio::task::spawn_blocking ↓ this hands the closure to a SEPARATE thread pool built exactly for blocking work, so it can take as long as it needs without starving the async worker threads everything else depends on Await the JoinHandle it returns ↓ your handler still reads as ordinary async code — awaiting the spawned task IS a real yield point, so the worker thread is freed the instant the blocking pool takes over Reserve plain .await calls for real I/O — sqlx, reqwest, tokio::fs ↓ those already yield correctly, because their internals are built on Tokio's non-blocking I/O primitives; the fix only applies to work that's CPU-bound or wraps a blocking library, never to a database or network call made through an async driver
The one-sentence rule. Tokio's whole speed advantage — a handful of threads serving thousands of requests — depends on every task voluntarily yielding at an .await; one synchronous, CPU-heavy call inside an async fn breaks that promise for every other task sharing its thread, and the compiler has no way to warn you, because the code is perfectly valid Rust.
Picture a waiter who isn't allowed to leave a table until that table has completely finished eating — not to bring water, not to take a new order, nothing. One slow eater, and every other table just sits there, and it has nothing to do with how good a waiter they are.

The mechanism

Follow four login attempts landing at the same instant, and watch a fifth, completely unrelated request get stuck behind all of them.

  1. Server starts with Tokio's default runtime — 4 worker threads on a 4-core machinebaseline
  2. Four POST /login requests arrive within the same millisecond; Tokio spawns 4 tasks, one per worker threadfan-out
  3. Each task calls bcrypt::verify(password, hash) — synchronous, pure CPU, no .await inside itno yield point
  4. Every worker thread now runs bcrypt's hashing loop to completion; none can be reused until its ~250ms of CPU work finishesall 4 threads pinned
  5. A fifth request, GET /health, is spawned as a task — but there is no free worker thread anywhere to poll it onnowhere to run
  6. /health sits queued for the same ~250ms, even though its own handler never touches bcrypt, a database, or anything slowcollateral stall

Step 5 is the one that surprises people. There is nothing expensive or wrong about GET /health — it is being punished for a decision made inside a completely different handler. Tokio's cooperative model has no concept of "this task is more urgent" or "let the cheap one cut in line"; it only has "is a worker thread free right now," and for 250ms, the honest answer is no.

Three completely different-looking calls — a crypto function, a file read, a sort — collapse into the identical outcome, because the runtime doesn't care WHY a thread is busy, only THAT it is. Any synchronous, CPU-bound work dropped into an async fn produces this same funnel; the fix (spawn_blocking) is the same regardless of which one of these caused it.

Your Axum handler for POST /login calls the synchronous bcrypt::verify(password, hash) directly, with no .await anywhere in it. Four login requests arrive at the same instant on a server with 4 worker threads. A fifth, unrelated GET /health request arrives a moment later. What happens to it?

Tokio doesn't spin up a new thread on demand for an equal-priority task — it runs a fixed worker pool (commonly one thread per CPU core), and every one of those four was already claimed by a bcrypt call with no point at which to yield it back.

That would require preemption — the runtime forcibly interrupting a task mid-execution. Tokio doesn't do that; it's cooperative, meaning it can only switch tasks at a spot the running code itself marks with .await. A plain synchronous function call has no such spot.

Right. All four worker threads are occupied running bcrypt to completion, and since bcrypt::verify never awaits anything, Tokio never gets an opportunity to interrupt it. /health has nowhere to run until one of the four finishes.

Where you have seen this before

"A cooperative scheduler only switches where the code lets it" is the same trap in every event-loop-shaped runtime, not just Tokio.

Node's single-threaded event loop

A synchronous JSON.parse on a huge payload, or a tight uninterrupted for loop, blocks Node's ONE event-loop thread — every other pending request, timer, and promise callback on the entire process waits until that call returns. Same cooperative trap, just with one thread instead of a small pool of them.

the JS version, one thread instead of four

Spring WebFlux's own Reactor threads

This page's intro compares Tokio to WebFlux's reactor in general — here's the specific failure mode: calling a blocking JDBC driver, or Mono.block(), from inside a reactive pipeline running on Schedulers.parallel()'s small event-loop pool starves every other in-flight reactive stream sharing that thread, exactly like bcrypt starves Tokio's workers.

the JVM's reactive stack, hitting the identical wall

Android's "Application Not Responding"

Android's main/UI thread is a single cooperative loop that must keep processing input and redraw events. Run a heavy synchronous computation on it and the whole UI freezes — after about 5 seconds the OS itself throws up an ANR dialog. It's the same one-thread-does-too-much shape, just with a user staring at a frozen screen instead of a queued HTTP request.

1. async fn returns a future; .await drives it

async fn show(id: u32) -> User {
  let u = db.find(id).await; // yields the thread while the DB works
  u
}
// calling show(7) does NOTHING yet — it returns a Future (a lazy state machine).
// Tokio polls it; at .await it parks the task and runs others until I/O is ready.
Futures are lazy; the runtime drives them. An async fn compiles to a state machine that does nothing until polled. Tokio's executor polls many futures on a few threads; when one hits an .await that isn't ready, it returns Pending and the thread runs another task — cooperative, non-blocking concurrency. This is why a small thread pool serves enormous connection counts, the same reason Node's event loop or Spring WebFlux scale.

2. The router maps paths to handlers

let app = Router::new()
  .route("/users", get(list).post(create))
  .route("/users/:id", get(show))
  .layer(TraceLayer::new_for_http()) // tower middleware
  .with_state(db);

axum::serve(listener, app).await?;

A Router maps method + path to handler functions and stacks tower middleware via .layer(...) (tracing, auth, compression, timeouts) — the filter chain. .with_state(db) makes shared state available to every handler through the State extractor.

3. Errors are values — map them to responses

enum AppError { NotFound, Unauthorized, Db(sqlx::Error) }

impl IntoResponse for AppError {
  fn into_response(self) -> Response {
    let code = match self {
      AppError::NotFound => StatusCode::NOT_FOUND, // 404
      AppError::Unauthorized => StatusCode::UNAUTHORIZED, // 401
      AppError::Db(_) => StatusCode::INTERNAL_SERVER_ERROR,
    };
    (code, Json(json!({ "error": code.to_string() }))).into_response()
  }
}
One place to map errors to status. Because a handler returns Result<T, AppError> and AppError implements IntoResponse, the ? operator can bubble any error up, and Axum turns it into the right HTTP status — Rust's equivalent of a Spring @ControllerAdvice / @ExceptionHandler, but checked by the compiler.
