Transactions & ACID

Atomicity, Consistency, Isolation, Durability — and how PostgreSQL MVCC gives you isolation without blocking readers.

💳 What are ACID transactions — and why do they prevent catastrophic data corruption?

A transaction runs a group of statements as one unit — all commit, or any failure rolls everything back, which is vital where partial success corrupts (debit without credit, a user with no role). The ACID guarantees: Atomicity (all-or-nothing), Consistency (FK/NOT NULL/unique constraints hold at commit), Isolation (concurrent txns don't see each other's in-progress work), Durability (committed data survives crashes via the WAL). Postgres uses MVCC — a writer creates a new row version instead of locking readers, so reads and writes don't block. Isolation levels trade strictness for concurrency: READ COMMITTED (default) → REPEATABLE READ (snapshot at start) → SERIALIZABLE (as if sequential).

  • All-or-nothing — BEGIN…COMMIT/ROLLBACK; partial success is worse than failure.
  • ACID — atomicity, consistency, isolation, durability (WAL-backed).
  • MVCC — writers version rows instead of locking readers; no read/write blocking.
  • Isolation levels — READ COMMITTED → REPEATABLE READ → SERIALIZABLE.

Transaction syntax

-- Explicit transaction: BEGIN; INSERT INTO users (email, idp_type, created_at) VALUES ('bob@eg.com', 'PING', NOW()) RETURNING id INTO v_user_id; INSERT INTO user_roles (user_id, role_id) VALUES (v_user_id, (SELECT id FROM roles WHERE role_name = 'USER')); INSERT INTO audit_events (user_id, event_type) VALUES (v_user_id, 'USER_CREATED'); COMMIT; -- all 3 inserts committed atomically -- On error, ROLLBACK undoes everything: BEGIN; UPDATE users SET balance = balance - 100 WHERE id = 1; UPDATE users SET balance = balance + 100 WHERE id = 2; -- If any UPDATE fails: ROLLBACK; -- neither update applied -- SAVEPOINT for partial rollback: SAVEPOINT sp1; ... -- can ROLLBACK TO sp1 if needed

Isolation levels

-- READ COMMITTED (default PostgreSQL): -- Each statement sees only committed data -- But two reads in same tx may differ BEGIN; SELECT count FROM sessions WHERE user_id=1; -- another tx commits, adding a session SELECT count FROM sessions WHERE user_id=1; -- DIFFERENT value — non-repeatable read COMMIT; -- REPEATABLE READ: snapshot at tx start BEGIN ISOLATION LEVEL REPEATABLE READ; SELECT count FROM sessions WHERE user_id=1; -- another tx commits — we DON'T see it SELECT count FROM sessions WHERE user_id=1; -- SAME value guaranteed COMMIT; -- FOR UPDATE: pessimistic locking BEGIN; SELECT * FROM users WHERE id = 1 FOR UPDATE; -- locks row until COMMIT -- No other tx can update this row now UPDATE users SET active = false WHERE id = 1; COMMIT;

Spring @Transactional

Spring Boot wraps methods in transactions with @Transactional. SQL BEGIN/COMMIT are called automatically. @Transactional(rollbackFor = Exception.class) — by default, Spring only rolls back on RuntimeException; add rollbackFor to catch checked exceptions too. @Transactional(isolation = Isolation.REPEATABLE_READ) — maps to PostgreSQL REPEATABLE READ. @Transactional(propagation = REQUIRES_NEW) — starts a NEW transaction, even if one is already active (for audit logging that must commit regardless of outer tx outcome). @Transactional(readOnly = true) — hint to Hibernate to optimize (no dirty checking, PostgreSQL uses optimized read-only mode). Common mistake: calling a @Transactional method from WITHIN the same class — Spring's proxy AOP won't intercept it, so no transaction starts. Fix: inject the service into itself (@Autowired private UserService self) or restructure. Another mistake: @Transactional on private method — Spring AOP only proxies public methods.

CIAM transaction patterns: User provisioning must be atomic — create user + assign default role + write audit event, all in one @Transactional method so a failure leaves no orphaned user. A concurrent-login race (two OAuth callbacks for the same subject) is fixed by a unique constraint on (idp_type, external_id) + catching DataIntegrityViolationException — the second insert rolls back and you return the existing user. And role edits use optimistic locking (@Version): two admins editing the same user, one gets OptimisticLockException and retries.

The problem

You read a number, you thought about it, and by the time you wrote it back it was a rumour.

The balance check that both requests passed

Two withdrawals land in the same millisecond. Each opens a transaction, runs SELECT balance FROM accounts WHERE id = 7, and gets back 100. Each one does the subtraction in Java and writes the answer back: UPDATE accounts SET balance = 0 WHERE id = 7. Both commit. The balance went down by $100 and $200 walked out the door.

SELECT → 100both read 100 both write 0 ⚠$200 paid out ⚠

Nothing threw. No deadlock, no constraint violation, no stack trace, not even a warning line. The only evidence is a number that is $100 short, found three weeks later in a reconciliation report by someone who does not read Java.

Make the write depend on what you read
SELECT ... FOR UPDATE ↓ pessimistic — the row is yours until COMMIT, and request two waits in line for it UPDATE ... AND version=? ↓ optimistic — no lock, but a stale row now updates ZERO rows instead of the wrong one 0 rows → re-read → retry
A read is not a reservation. On the level your database is actually running, SELECT tells you what was true a microsecond ago — not what will still be true when your UPDATE lands. If a write depends on a value you read, you must lock that row or version it. "Be careful" is not the third option.

The mechanism

Four levels, and each one closes exactly one more door.

  1. READ UNCOMMITTED — you would be able to read rows another transaction has not committed yet: a dirty read. Postgres declines to implement it and quietly hands you the next level up.not real here
  2. READ COMMITTED — every statement takes a fresh snapshot, so two SELECTs inside one transaction may legally disagree, and rows that match your WHERE can appear out of nowhere.the default
  3. REPEATABLE READ — one snapshot for the whole transaction. Rows stop shifting under you and phantoms stay hidden — on Postgres. The ANSI standard still permits phantoms at this level, so the exam and your database will hand you different answers. Writing onto a row somebody else changed now fails with 40001.one snapshot
  4. SERIALIZABLE — Postgres tracks read/write dependencies between live transactions and aborts any result that no serial ordering could have produced.retry required

The part everyone re-learns: your database is sitting on row two. Row two is where the lost update lives.

Read that ladder again with the withdrawal in mind. On READ COMMITTED both transactions read 100, both write 0, both commit — no error, because neither statement ever asked whether the row had moved. Raise the same code to REPEATABLE READ and the second UPDATE does not silently win: it dies with could not serialize access due to concurrent update. That is better, and it is still an incident unless you wrote the retry. Isolation levels do not remove the conflict — they only change whether you find out about it. Notice the trap: the fix people reach for first (SET TRANSACTION ISOLATION LEVEL) is the one that needs the code path they were trying to avoid writing.

And an open transaction is never free. @Transactional is not a hint. At the proxy boundary Spring pulls a connection out of the pool, sends BEGIN, and pins that connection to your thread until the method returns — then COMMIT, or ROLLBACK if a RuntimeException escaped (a checked exception commits happily unless you spell out rollbackFor). So every line in that method is inside the transaction, including the 900 ms REST call to the IdP that someone added last sprint. The row lock you took on line three is still held on line forty. A transaction is a lease on one connection plus every lock you hold, and the clock starts at BEGIN, not at the UPDATE. Twenty threads doing that against a pool of ten is an outage that will be filed as a database problem when it is really a method that is too long.

Your refresh endpoint runs SELECT used FROM refresh_tokens WHERE token = ?, checks if (!used) in Java, then UPDATE refresh_tokens SET used = true WHERE id = ?. Two requests arrive with the same token at the same instant, on stock PostgreSQL settings. What happens?

Right — and nothing in that code looks wrong, which is the whole problem. READ COMMITTED lets both SELECTs see false; the two UPDATEs queue on the row lock and then both apply, because neither one asked whether it was still false. One single-use token, two live sessions.

The second UPDATE genuinely does wait on the row lock. But its SELECT already ran and already returned false — the if in your Java was decided before that lock existed. Waiting does not re-run the decision. Only FOR UPDATE on the read would have.

That is REPEATABLE READ or SERIALIZABLE behaviour. On the default READ COMMITTED, Postgres has nothing to object to: two transactions each updated a row they were allowed to update. You never told it these two were related.

Where you've seen this before

Three CIAM bugs that are all this bug wearing a different hat.

The single-use refresh token

Two browser tabs wake up and refresh at once. Both read the token as unused, both rotate. Now one revocation cleans up half the mess. Fix: take the row lock on the read — SELECT ... FOR UPDATE inside the same transaction — so the loser re-reads reality instead of a memory of it.

Three attempts left. Two POSTs land together, both read 3, both write 2. The attacker just spent two guesses and was charged for one. Fix: never let the arithmetic happen in Java — do it in the statement, and check the row count.

Questions from the back row

Why not just run SERIALIZABLE everywhere and stop thinking about it?

Because it does not delete the conflict, it converts it into a 40001 that arrives at runtime, under load, on the busiest endpoint — which is the exact moment you least want an untested code path. SERIALIZABLE without a retry loop is READ COMMITTED with extra outages. Write the retry first, then raise the level; that order is not negotiable.

FOR UPDATE or a version column — how do I pick?

Pessimistic (FOR UPDATE) when losing is likely and the transaction is short: the second request waits a few milliseconds and then reads the truth. Optimistic (@Version) when losing is surprising and you would rather not hold a lock across work you do not control. Optimistic still needs the retry — the version check tells you that you lost, it does not do anything about it.

Does @Transactional(readOnly = true) make any of this safer?

No — faster and more honest, not safer. Hibernate skips dirty checking and the connection refuses writes, which catches the day someone adds a save() to your report method. Your snapshot rules are exactly what they were: it is a performance and intent flag, not an isolation level.

3 — Deadlock Prevention




A deadlock occurs when TXN A waits for TXN B's lock, and TXN B waits for TXN A's lock — a cycle that can never resolve. PostgreSQL detects it in ~1 second and kills one transaction.


-- Prevention: always acquire locks in the same ORDER

-- BAD (can deadlock):
-- TXN A: UPDATE accounts WHERE id=1 THEN WHERE id=2
-- TXN B: UPDATE accounts WHERE id=2 THEN WHERE id=1

-- GOOD: always lock lower id first
SELECT * FROM accounts
  WHERE id IN (1, 2)
  ORDER BY id  -- lock in consistent order!
  FOR UPDATE;

-- Or use SELECT ... FOR UPDATE SKIP LOCKED (queue pattern)









4 — MVCC in Spring Boot Context




PostgreSQL MVCC means readers never block writers, writers never block readers. Each transaction sees a consistent snapshot. Old row versions are kept until VACUUM removes them.


// Spring: @Transactional creates a transaction boundary
@Transactional(readOnly = true)  // uses snapshot, no locks
public List<User> getUsers() {
  return userRepo.findAll();  // consistent snapshot at txn start
}

// Optimistic locking: detect conflicts without row-level locks
@Entity
public class Order {
  @Version  // Hibernate checks this on UPDATE
  private int version;  // incremented each update
  // UPDATE orders SET ... WHERE id=? AND version=?
  // If 0 rows updated → OptimisticLockException → retry
}
