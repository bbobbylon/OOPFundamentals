ASP.NET Core Auth — JWT Bearer, Policies & Claims

How ASP.NET Core proves who you are and what you may do: a two-step middleware pipeline — UseAuthentication() turns a Bearer token into a ClaimsPrincipal, then UseAuthorization() evaluates [Authorize] policies. Authentication failure is 401; authorization failure is 403.

🟣 What is auth in ASP.NET Core — and why are authentication and authorization two separate middlewares?

ASP.NET Core models auth as two ordered middlewares in the request pipeline. First app.UseAuthentication() runs the configured authentication handler — for an API that is the JWT Bearer handler (AddJwtBearer). It reads the Authorization: Bearer <token> header, validates the token's signature, issuer, audience and lifetime against the configured TokenValidationParameters, and on success builds a ClaimsPrincipal from the token's claims and assigns it to HttpContext.User. Crucially, authentication does not reject a request on its own — it just establishes identity (or leaves User unauthenticated). Then app.UseAuthorization() runs and evaluates the [Authorize] metadata on the matched endpoint: a bare [Authorize] requires any authenticated user, while [Authorize(Policy="AdminOnly")] or [Authorize(Roles="Admin")] requires a policy to be satisfied. Policies are named sets of requirements registered with AddAuthorization (e.g. RequireRole, RequireClaim("scope","users.delete"), or a custom AuthorizationHandler). The split is what produces the two distinct status codes: if there is no valid token the authentication handler issues a Challenge → 401 Unauthorized; if the token is valid but the principal fails the policy the authorization middleware issues a Forbid → 403 Forbidden. Because UseAuthentication must populate HttpContext.User before UseAuthorization can read it, their order in Program.cs is mandatory — swap them and every protected request silently fails.

  • Two middlewares — UseAuthentication() (who?) then UseAuthorization() (allowed?), in that order.
  • JWT Bearer handler — validates the token and builds a ClaimsPrincipal onto HttpContext.User.
  • [Authorize] + policies — declarative gates; policies bundle requirements (RequireRole, RequireClaim, custom handlers).
  • 401 vs 403 — Challenge (no/invalid token) is 401; Forbid (authenticated, policy unmet) is 403.

Configure + order the pipeline

builder.Services .AddAuthentication("Bearer") .AddJwtBearer(o => { o.Authority = entraTenantUrl; o.Audience = "api://my-api"; }); builder.Services.AddAuthorization(o => o.AddPolicy("AdminOnly", p => p.RequireRole("Admin"))); // order is mandatory: app.UseAuthentication(); app.UseAuthorization();

Protect an endpoint, read claims

app.MapGet("/me", (ClaimsPrincipal user) => Results.Ok(new { id = user.FindFirstValue("sub"), name = user.Identity!.Name })) .RequireAuthorization(); app.MapDelete("/users/{id}", Delete) .RequireAuthorization("AdminOnly");

Spring Boot comparison

AddJwtBearer ≈ Spring's OAuth2 resource server (oauth2ResourceServer().jwt()) + JwtDecoder. HttpContext.User (the ClaimsPrincipal) ≈ the SecurityContext's Authentication. [Authorize(Policy="AdminOnly")] ≈ @PreAuthorize("hasRole('ADMIN')"); a custom AuthorizationHandler ≈ a custom AccessDecisionVoter / SpEL expression. The UseAuthentication → UseAuthorization ordering is exactly Spring Security's filter-chain ordering. 401 Challenge ≈ AuthenticationEntryPoint; 403 Forbid ≈ AccessDeniedHandler.

CIAM with Entra ID: in a real Microsoft shop you don't hand-roll token validation — Microsoft.Identity.Web's AddMicrosoftIdentityWebApi(config) wires AddJwtBearer to your Entra tenant: it fetches the OIDC metadata + JWKS, validates the RS256 signature and the iss/aud, and maps Entra app roles (the roles claim) or group claims into the principal so [Authorize(Roles="...")] just works. That is the .NET counterpart to Spring's NimbusJwtDecoder.withJwkSetUri(...) + an authorities converter. For an SPA, the same BFF reasoning applies — keep tokens server-side behind an httpOnly cookie. Your 15-minute token is a 20-minute token, and nobody told you

The problem

You set ValidateLifetime = true, minted a 15-minute token, and it still works four minutes after it expired.

The token says exp 10:15:00. At 10:18:40 the endpoint returns 200.

You are hardening an API. Access tokens live 15 minutes; refresh handles the rest. Security asks you to prove that a stolen access token dies on schedule, so you grab a token at 10:00:00, watch the clock, and at 10:18:40 you replay it against GET /me.

You expect the 401 Challenge the page's scenario ③ shows. You get 200 OK, with the full ClaimsPrincipal. Every line of your config is correct: ValidateLifetime is true, the exp claim really is 10:15:00, the signature really is valid. What you never set is ClockSkew, and TokenValidationParameters.ClockSkew defaults to TimeSpan.FromMinutes(5) — DefaultClockSkew. The lifetime check is not exp < now. It is exp < now - skew. Your token is accepted right up to 10:20:00.

You did not configure a 15-minute token. You configured a 20-minute token with a 15-minute label on it.

Every JWT validator on earth accepts some clock drift between the issuer that stamped exp and the API reading it, because two machines never agree on the millisecond. The only question is how much, and who decided. In Microsoft.IdentityModel.Tokens the answer is five minutes and the decision was made in 2013 by someone who was not on your team. Step four is the whole lesson. The comparison is not "has this expired," it is "has this expired by more than the tolerance." Flip it around and the same subtraction explains the friendly half of skew: when your API's container clock drifts 20 seconds ahead of the IdP, a token minted one second ago would look like it came from the future and every login would fail — skew is why it does not. The default is not a bug. The default being five minutes, in a system where you also chose fifteen, is the bug.

10:00:00 → 10:15:00 · genuinely valid any request → 200, and everyone agrees it should be
10:15:00 → 10:20:00 · expired, still accepted same request → 200, because exp is not yet earlier than now - 5 min
after 10:20:00 · finally rejected same request → SecurityTokenExpiredException → Challenge → 401

Read the middle band out loud: for five whole minutes the token is expired and works. That band is where every "but we revoked it" incident report lives. It is also why a five-second access token is a fiction — with the default skew, the shortest token you can actually issue is five minutes and five seconds. If short lifetimes are the point of your design, the skew is not a footnote, it is the floor.

Your API uses AddJwtBearer with ValidateLifetime = true and nothing else about time configured. A token stamped exp 10:15:00 arrives at GET /me at 10:18:40, signature and audience both fine. What does the endpoint return?

That is what the flag's name promises, and it is what almost everyone answers. ValidateLifetime only decides whether the time check runs; ClockSkew decides where the line is. With the check on and the skew untouched at TimeSpan.FromMinutes(5), the comparison is exp < now - 5min → 10:15:00 < 10:13:40 → false → valid. You get the 401 at 10:20:01, not at 10:15:01.

403 cannot happen here, and knowing why is worth more than the question. 403 is a Forbid — it requires an authenticated principal that failed a policy. An expired token produces no principal at all, so the failure mode would be a Challenge (401), never a Forbid. A stale token is an identity problem, and identity problems are 401 by construction in ASP.NET Core.

Right, and the arithmetic is the point: the validator asks exp < now - ClockSkew, not exp < now. TokenValidationParameters.ClockSkew defaults to DefaultClockSkew, five minutes, so 10:15:00 is compared against 10:13:40 and passes. Set o.TokenValidationParameters.ClockSkew = TimeSpan.Zero when your issuer and API share an NTP source, and remember the same tolerance applies to nbf — a token that is not supposed to be valid until 10:25 is accepted at 10:20.

Where you have seen this before

Every system that compares two clocks builds in a fudge factor, and every one of them picked a different number.

Spring Security's resource server does the same thing with a different number

On the Java side of your stack, NimbusJwtDecoder validates timestamps through JwtTimestampValidator, whose default maximum clock skew is 60 seconds, not five minutes. Same design, same invisible extension of your token's life, one-fifth the size. If you run a .NET API and a Spring API against the same Entra tenant and the same token, they stop accepting it four minutes apart — and the one that looks "broken" is the correct one.

same token, two APIs, two expiry times

Your authenticator app's 30-second code lasts longer than 30 seconds

TOTP derives a code from a 30-second time step, and RFC 6238 tells verifiers to also accept the adjacent step so a user who types slowly is not punished. That is the same subtraction: the code is compared against a window of steps, not one instant. It is why the digits you typed as the ring finished refreshing were still accepted — and why a phished code stays useful to an attacker for longer than the countdown suggests.

a 30-second secret with a 60-second life

Kerberos is where the five minutes came from

Active Directory's "Maximum tolerance for computer clock synchronization" defaults to 5 minutes, and a domain-joined machine whose clock drifts past it simply stops authenticating. That policy is the ancestor of the number sitting in your TokenValidationParameters today. Knowing the lineage is the memory hook: five minutes is Windows' historical answer to "how far apart can two clocks be," inherited by a token library that has nothing to do with domain controllers.

an inherited default, not a chosen one
The whole page on a napkin: ASP.NET Core splits auth into two ordered middlewares — UseAuthentication turns a Bearer token into a ClaimsPrincipal on HttpContext.User, then UseAuthorization evaluates [Authorize] and its policies, which is why a missing identity is 401 and a failed policy is 403. And the one thing this block adds: ValidateLifetime does not check exp against now — it checks exp against now minus ClockSkew, which defaults to five minutes, so every token you issue lives five minutes longer than its label until you set ClockSkew yourself.

1. Configure the handler and order the pipeline

builder.Services.AddAuthentication(JwtBearerDefaults.AuthenticationScheme)
  .AddJwtBearer(options => {
    options.Authority = "https://login.microsoftonline.com/<tenant>/v2.0"; // Entra
    options.Audience = "api://my-api";
    options.TokenValidationParameters = new() {
      ValidateIssuer = true, ValidateAudience = true,
      ValidateLifetime = true, ValidateIssuerSigningKey = true
    };
  });
builder.Services.AddAuthorization(options => {
  options.AddPolicy("AdminOnly", p => p.RequireRole("Admin"));
  options.AddPolicy("CanDelete", p => p.RequireClaim("scope", "users.delete"));
});
var app = builder.Build();
app.UseAuthentication(); // 1) WHO are you? → sets HttpContext.User
app.UseAuthorization(); // 2) are you ALLOWED? → evaluates [Authorize]
Order is not optional. UseAuthentication populates HttpContext.User; UseAuthorization reads it. Register them in that order — reversed, the authorization middleware sees an anonymous principal and rejects everything. TokenValidationParameters is the security contract: turning off ValidateAudience or ValidateIssuer would let a token minted for another app sail through, so keep them all on.

2. Protect endpoints and read the principal

app.MapGet("/me", (ClaimsPrincipal user) =>
  Results.Ok(new {
    id = user.FindFirstValue("sub"),
    name = user.Identity!.Name,
    scopes = user.FindAll("scope").Select(c => c.Value)
  }))
  .RequireAuthorization(); // any authenticated user

app.MapDelete("/users/{id:int}", (int id) => Results.NoContent())
  .RequireAuthorization("AdminOnly"); // policy: must be in the Admin role
The ClaimsPrincipal is the populated identity. Because the JWT Bearer handler already set HttpContext.User, any endpoint can take ClaimsPrincipal user as a parameter (model binding injects HttpContext.User) and read claims with FindFirstValue/FindAll — no manual token parsing. RequireAuthorization() attaches the [Authorize] metadata; RequireAuthorization("AdminOnly") attaches the named policy. The endpoint body only runs once authorization passes.

3. Policies, attributes, and 401 vs 403

[ApiController]
[Authorize] // class-level: must be authenticated
public class UsersController : ControllerBase {
  [HttpDelete("{id}")]
  [Authorize(Policy = "CanDelete")] // method-level: needs the scope
  public IActionResult Delete(int id) => NoContent();
}
// No / invalid token → JwtBearerHandler.Challenge() → 401 Unauthorized
// Authenticated, policy unmet → authorization Forbid() → 403 Forbidden
401 and 403 come from different stages. When authentication can't establish an identity, the handler issues a Challenge — for JWT Bearer that is a bare 401 (with a WWW-Authenticate header). When an authenticated principal fails a policy, the authorization middleware issues a Forbid — 403. Sending 403 to an anonymous caller (or 401 to a known user who merely lacks a role) is the classic mix-up; ASP.NET keeps them separate by design because they happen in different middleware.
