TypeScript Async Patterns

Promises, async/await, all combinators, async iterables, error handling, and real-world patterns — with TypeScript types throughout

⏳ What is async JavaScript? Why do we need it?

JavaScript runs on a single thread, so if you wait for a network request before moving on, the whole page freezes — no clicks, no scrolls. Asynchronous programming lets JS start an operation, register what to do when it finishes, and keep working meanwhile. A Promise is the object for "a value that will exist later" — it's pending, then resolves (value) or rejects (error) — and async/await is sugar that makes Promise code read top-to-bottom while pausing only that function, never the thread.

  • Single thread ≠ blocking. Async keeps the UI responsive while I/O is in flight.
  • A Promise has three states — pending → resolved or rejected.
  • await pauses one function, not the thread; .then() chains the same machinery.
  • TypeScript types the result — Promise<User>, Awaited<T>, catch (e: unknown).

Promise vs async/await

fetch(url).then(r => r.json()).then(log) vs the sequential const r = await fetch(url); const data = await r.json(); — same behavior, the second reads like synchronous code.

TypeScript adds types

Promise<User> is a typed result; an async fn returns Promise<T>; Awaited<Promise<User>> = User; and catch (e: unknown) forces safe error handling.

Angular / Spring / CIAM: Angular HTTP returns RxJS Observables, but many APIs use Promises; auth flows are async — await oidc.getToken(), await http.get<User>(url). Spring WebFlux uses Reactor (same idea), and Promise.all() runs parallel auth checks.

The problem

Two awaits in a row is a decision, even when you didn't make one.

const user = await getUser(); const prefs = await getPrefs(); const flags = await getFlags();
await getUser() — profile call, independent of the other two300ms
await getPrefs() — starts only after getUser() finishes300ms
await getFlags() — starts only after getPrefs() finishes300ms
Total — one spinner, this long900ms
Nothing here says "wait for the profile before checking flags." await on its own line says it anyway — three independent calls, none needing the other two, forced into a queue by where the keyword sits on the page.
Sequential: 900ms

await, await, await — each call waits for the previous one to finish before it even starts. You did not write a bug; you wrote a schedule, by accident.

Promise.all: 300ms

const [user, prefs, flags] = await Promise.all([...]) — all three requests are already in flight before anything is awaited. One wait, for the slowest of the three, not the sum of all three.

A Promise starts the moment it's created — not when you await it→ build-await-build-await lets only one be in flight at a time→ each 300ms call waits for the previous one before starting→ 300 + 300 + 300 = 900ms of a user watching a spinner
await does not block the thread — it blocks THIS function. Everything else on the page keeps running. So the cost of an extra await is never "the browser froze"; it is "this one flow got longer", which is exactly why it hides.

Say what actually depends on what. Start all three at once so the calls are already in flight, then await Promise.all([...]) for one wait covering the slowest of them — 300ms total instead of 900ms. Build-then-await, not build-await-build-await. And remember Promise.all rejects the instant any one of them does, but it can't cancel the rest — they finish in the background, unwatched, which surprises people just as often as the sequential-await cost does.

The mechanism

Four combinators. One question picks between them.

N promiseswhat do you need back?
which combinator? →
ALL of them, or fail → Promise.all All outcomes, successes and failures → Promise.allSettled The first to SETTLE, win or lose → Promise.race The first to SUCCEED → Promise.any

all is fail-fast, allSettled never rejects (you get a {status, value|reason} per entry), race is the one you want for a timeout, and any ignores failures until everything has failed. Reaching for all when you meant allSettled is how one flaky optional call takes down a whole dashboard.

None of these cancel anything. A rejected Promise.all settles immediately, but the other requests are still in flight and will still resolve — into nothing. If you actually need to stop the work, that is AbortController's job, and it has to be threaded into the fetch call itself. TypeScript will not warn you about this; the types are identical either way.

Promise.all([a, b, c]) and b rejects after 50ms while a and c take 2s. What is true at t=100ms?

Nothing cancels a promise. There is no cancel in the Promise API at all — AbortController exists precisely because of that gap, and it has to be wired into the underlying fetch.

That is allSettled. all is fail-fast: the first rejection settles it immediately.

Right, and the second half is the part that bites. Your catch already ran, but a and c keep going and resolve into a result nobody is holding — which is why a "failed" request can still write to state or log an error seconds later.

Questions from the back row

Why didn't my try/catch catch that error?

Almost always because the throw happened in a promise you never awaited — a "floating" promise. try { doThing(); } catch {} without await catches nothing, because doThing() returns before it fails. The rejection surfaces later as an unhandled rejection with no stack you recognise. TypeScript's no-floating-promises lint rule exists for exactly this and is worth turning on.

Is await in a for loop always wrong?

No — it is wrong when the iterations are independent, and right when each one depends on the last, or when you are deliberately rate-limiting. Firing 5,000 requests with Promise.all is its own outage. The honest answer is "batch": chunk the list and Promise.all each chunk.

Does async make my function run on another thread?

Never. It marks the function as returning a Promise and lets it pause at await. All your JavaScript still runs on one thread — the concurrency comes from the browser doing the I/O elsewhere and handing you the result. If you want real parallelism for CPU work, that is a Web Worker, not async.

// TypeScript: Promise<T> — T is the resolved type
const p: Promise<number> = new Promise((resolve, reject) => {
  setTimeout(() => {
    if (Math.random() > 0.5) resolve(42);   // fulfilled: T=42
    else                    reject(new Error('failed')); // rejected
  }, 1000);
});

// .then(onFulfilled, onRejected) — chainable
p.then(n => n * 2)       // Promise<number>
  .then(n => n.toString()) // Promise<string>
  .catch(e => 'default')  // catches any earlier rejection
  .finally(() => cleanup()); // always runs

// Shorthand creators
Promise.resolve(42);      // already fulfilled: Promise<number>
Promise.reject(new Error('bad')); // already rejected

async / await — syntactic sugar over Promises

// The two are EXACTLY equivalent

// Promise chain style
function getUser(id: number): Promise<User> {
  return fetch(`/users/${id}`)
    .then(r => r.json())
    .then(data => data as User)
    .catch(e => { throw new Error('fetch failed'); });
}

// async/await style — reads like sync code
async function getUser(id: number): Promise<User> {
  try {
    const r = await fetch(`/users/${id}`);
    return await r.json() as User;
  } catch {
    throw new Error('fetch failed');
  }
}

// async function ALWAYS returns Promise<T>
async function four(): Promise<number> { return 4; }
// ↑ Same as: function four() { return Promise.resolve(4); }

// await unwraps the Promise — only inside async fn
const n = await four(); // n: number (4)

// Classic use: timeout wrapper

function withTimeout<T>(
  p: Promise<T>,
  ms: number
): Promise<T> {
  const timeout = new Promise<never>((_, reject) =>  // Promise<never> — this promise only ever rejects, never resolves
    setTimeout(() => reject(new Error(`Timeout after ${ms}ms`)), ms)
  );
  return Promise.race([p, timeout]);  // whichever settles first wins — the real promise, or the timeout rejecting
}

await withTimeout(fetchData(), 5000);  // wraps any promise with a 5-second deadline
// → resolves with data if < 5s, rejects with timeout if not

// ✓ Best for: timeout, fastest-server wins, cache vs network

Async Error Handling Patterns

The Result type — no-throw pattern

// Never throw async — return a discriminated union
type Result<T, E = Error> =  // same shape as the Result type on the generics page — T for success, E for failure
  | { ok: true;  value: T }
  | { ok: false; error: E };

async function safeGet<T>(
  url: string
): Promise<Result<T>> {  // notice: this NEVER rejects — every path returns a value
  try {
    const r = await fetch(url);
    if (!r.ok) throw new Error(`HTTP ${r.status}`);  // a non-2xx response doesn't reject fetch on its own, so this checks manually
    return { ok: true, value: await r.json() };  // success branch of the discriminated union
  } catch (e) {
    return { ok: false, error: e as Error };  // failure branch — the try/catch is caught HERE, never escapes to the caller
  }
}

// Usage — explicit branching, no surprise throws
const result = await safeGet<User>('/api/me');  // no try/catch needed at the call site — the function can't throw
if (result.ok) {
  console.log(result.value.name); // TS: User
} else {
  console.error(result.error.message);  // this branch is forced by the type — you can't accidentally skip error handling
}

Retry with exponential backoff

async function retry<T>(
  fn: () => Promise<T>,  // a thunk — deferred so retry() can call it more than once
  opts = { times: 3, baseMs: 500 }  // a default object, in case the caller doesn't pass options at all
): Promise<T> {
  let lastError: unknown;  // remembers the most recent failure, in case every attempt fails
  for (let i = 0; i < opts.times; i++) {
    try {
      return await fn();  // success — return immediately, no more attempts needed
    } catch (e) {
      lastError = e;
      if (i < opts.times - 1) {  // don't wait after the LAST attempt — just fall through and throw
        const delay = opts.baseMs * 2 ** i; // 500, 1000, 2000...
        await new Promise(r => setTimeout(r, delay));  // a common idiom for "await N milliseconds"
      }
    }
  }
  throw lastError;  // every attempt failed — re-throw the last error, rather than swallowing it
}

// Usage
const data = await retry(
  () => fetch('/flaky-api').then(r => r.json()),  // the thunk — not called yet, just handed to retry()
  { times: 4, baseMs: 300 }  // overrides the defaults: up to 4 attempts, 300/600/900ms delays
);

Async Iterables — for await...of

Creating & consuming async iterables

// AsyncGenerator — yields one value at a time, lazily
async function* paginate<T>(
  url: string
): AsyncGenerator<T[]> {
  let page = 1;
  while (true) {
    const res = await fetch(`${url}?page=${page}`);
    const data: { items: T[]; hasMore: boolean } =
      await res.json();
    yield data.items;                // pause, emit this page
    if (!data.hasMore) break;       // done!
    page++;
  }
}

// Consume with for await...of
for await (const page of paginate<User>('/api/users')) {
  page.forEach(user => renderUser(user));
  // Each page loads before the next fetch fires
}

// With break — stops fetching early
let found: User | undefined;
for await (const page of paginate<User>('/api/users')) {
  found = page.find(u => u.name === 'Bobby');
  if (found) break; // no more pages fetched!
}

Async iterable from EventTarget / stream

// Turn any event into an async iterable
async function* fromEvent<T>(
  target: EventTarget,
  event: string
): AsyncGenerator<T> {
  const queue: T[] = [];  // events that arrived faster than the consumer could read them
  let resolve: (() => void) | null = null;  // holds a pending "wake me up" callback while waiting for the next event

  target.addEventListener(event, (e) => {
    queue.push(e as T);  // buffer the event
    resolve?.(); resolve = null;  // if the generator was waiting, wake it up now
  });

  while (true) {
    if (queue.length) { yield queue.shift()!; }  // something's already buffered — emit it immediately
    else { await new Promise<void>(r => { resolve = r; }); }  // nothing yet — park here until the listener above resolves this promise
  }
}

// Consume clicks as an async stream
for await (const click of fromEvent<MouseEvent>(btn, 'click')) {  // same for-await syntax as the paginate() example above
  console.log('Clicked at', click.clientX, click.clientY);
}

// ReadableStream (Fetch API / Node streams)
const res = await fetch('/api/large-file');
const reader = res.body!.getReader();  // the "!" asserts body isn't null — reasonable after a successful fetch
const decoder = new TextDecoder();  // streams deliver raw bytes — this turns them into text
while (true) {
  const { done, value } = await reader.read();  // a different streaming API from AsyncGenerator, but the same manual loop shape
  if (done) break;
  processChunk(decoder.decode(value));  // process this chunk as soon as it arrives, without waiting for the whole file
}

TypeScript async types — Awaited<T>, return type inference, typed errors

Awaited<T> — unwrap the resolved type

// Awaited extracts the value type from a Promise
type A = Awaited<Promise<string>>;     // string
type B = Awaited<Promise<Promise<number>>>; // number (nested)
type C = Awaited<string>;               // string (no-op on non-Promise)

// Common use: extract the return type of an async fn
async function fetchUser(id: string) {
  const res = await fetch(`/api/users/${id}`);
  return res.json() as User;
}

// ReturnType gets the Promise; Awaited unwraps it
type UserResult = Awaited<ReturnType<typeof fetchUser>>;
// UserResult = User  ← not Promise<User>

// Useful in generics that accept async or sync callbacks
async function run<T>(fn: () => T | Promise<T>): Promise<T> {
  return await fn();  // Awaited<T> normalizes T in the caller
}

Typed errors in catch — unknown vs cast

// TypeScript: catch variable is always  unknown
try {
  await doSomething();
} catch (e) {  // "e" starts out completely untyped — TS won't let you call .message on it yet
  // e: unknown — must narrow before use
  if (e instanceof Error) {
    console.log(e.message); // ✓ narrow first
  }
}

// Custom error type for typed error handling
class ApiError extends Error {  // extends the real Error class, so instanceof Error still works too
  constructor(public status: number, message: string) {  // carries the HTTP status alongside the usual message
    super(message);
    this.name = 'ApiError';  // sets the error's displayed name, shown in stack traces
  }
}

// Error guard helper — use everywhere
function isApiError(e: unknown): e is ApiError {  // a named guard, same pattern as isUser on the narrowing page
  return e instanceof ApiError;
}

try { await api.getUser(); }
catch (e) {
  if (isApiError(e) && e.status === 401) {  // after isApiError(e), e.status is legal to read — TS narrowed it
    redirectToLogin();
  } else throw e; // re-throw unexpected errors
}

Promise.any() — first success wins

// any() resolves on first fulfilled promise
// only rejects if ALL reject (AggregateError)
// contrast: race() resolves/rejects on first settled
const fastest = await Promise.any([
  fetchFromCdn1(url),  // ← takes 200ms ✓ wins
  fetchFromCdn2(url),  // takes 400ms
  fetchFromOrigin(url) // takes 150ms but rejects
]);

// Type: typeof fastest  →  same as the element type
// AggregateError if all reject:
try { await Promise.any([Promise.reject(1), Promise.reject(2)]); }
catch (e) {
  if (e instanceof AggregateError) {
    console.log(e.errors); // [1, 2]
  }
}

Async generics — typed async pipelines

// Fully typed async transform pipeline
async function pipe<A, B, C>(
  value: A,
  step1: (a: A) => Promise<B>,
  step2: (b: B) => Promise<C>
): Promise<C> {
  return step2(await step1(value));
}

// Use: all types inferred
const result = await pipe(
  'user-123',
  id => fetchUser(id),   // string → Promise<User>
  u  => fetchProfile(u)  // User → Promise<Profile>
);
// result: Profile — fully inferred, no casts

Production Patterns

Concurrent limit (p-limit style)

// Run max N promises concurrently
async function mapWithLimit<T, R>(
  items: T[],
  fn: (item: T) => Promise<R>,  // the async work to run per item
  limit: number  // how many workers run at once — the whole point of this function
): Promise<R[]> {
  const results: R[] = [];  // pre-sized by index below, not built with push — order is preserved regardless of finish order
  let i = 0;  // shared "next item to claim" counter, read by every worker below

  async function worker() {  // one worker pulls items off the shared queue until none are left
    while (i < items.length) {
      const idx = i++;  // claim the next index — each worker gets a DIFFERENT idx since i is shared
      results[idx] = await fn(items[idx]);
    }
  }

  await Promise.all(
    Array.from({ length: limit }, worker)  // starts exactly "limit" workers running concurrently, all sharing the same queue
  );
  return results;
}

// Upload 100 files, max 5 at a time
const urls = await mapWithLimit(
  files, f => uploadFile(f), 5  // never more than 5 uploads in flight at once, regardless of how many files there are
);

AbortController — cancel in-flight requests

// Cancel a fetch when component unmounts (Angular)
@Component({...})
export class SearchComponent implements OnDestroy {
  private controller: AbortController | null = null;

  async search(q: string) {
    // Cancel previous request
    this.controller?.abort();
    this.controller = new AbortController();

    try {
      const res = await fetch(`/search?q=${q}`, {
        signal: this.controller.signal  // pass the signal
      });
      this.results = await res.json();
    } catch (e) {
      if ((e as DOMException).name === 'AbortError') return;
      throw e; // real error — rethrow
    }
  }

  ngOnDestroy() { this.controller?.abort(); }
}
