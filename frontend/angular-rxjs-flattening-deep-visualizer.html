RxJS Flattening: what actually flows

A "higher-order" observable is an observable whose values are themselves observables — e.g. each search keystroke maps to an HTTP request. The four flattening operators differ in exactly one decision: what to do when a new source value arrives while an inner observable is still running. That one choice is the whole ballgame. Watch the same input produce four different outputs.

What is "flattening"? Why do we need four different operators for it?

When you map() a stream value to an HTTP call, you get Observable<Observable<User[]>> — an "observable of observables." You can't .subscribe() to that usefully. You need to flatten it: automatically subscribe to each inner observable and merge its values into the outer stream. All four flattening operators do this — but they differ in one critical way: what happens when a new outer value arrives before the current inner observable completes?

switchMap — cancel the old one

New outer value arrives → cancel the in-flight inner observable, start a new one. Perfect for search autocomplete: you only want results for what the user is currently typing, not what they typed 300ms ago.

Use for: search, navigation, any "latest wins"
mergeMap — run all in parallel

New outer value → keep the old inner running AND start a new one. Results come in as each completes. Use for parallel operations where order doesn't matter and all results are needed.

Use for: parallel uploads, parallel API calls
concatMap — queue, one at a time

New outer value → queue it, wait for the current inner to complete first. Results come in order. Use when order matters and you can't afford to miss any value.

Use for: sequential saves, action queues
exhaustMap — ignore until done

New outer value → ignore it while inner is running. The first wins and others are dropped. Perfect for login buttons: if a login request is in flight, extra clicks are ignored — no double-login.

Use for: login, form submit, prevent double-click
CIAM decision guide: Login button click → exhaustMap (ignore double-clicks). User search box → switchMap (cancel old search). Uploading multiple files → mergeMap (parallel). Sequential API calls that must be in order → concatMap. Wrong choice = race conditions, duplicate requests, or lost data.

1. The projection returns an Observable

// the source: a form control's value stream (your "form data")
search = new FormControl('');

results$ = this.search.valueChanges.pipe(
  debounceTime(300),
  distinctUntilChanged(),
  switchMap(q => this.http.get<Result>('/search?q=' + q))   // ← returns Observable<Result>
);
// template:  <li *ngFor="let r of results$ | async">…</li>

The function you pass to switchMap doesn't return a value — it returns an Observable (the HTTP call). The operator subscribes to it for you and decides how to merge its output back into the stream. Swap switchMap for mergeMap/concatMap/exhaustMap and the behavior below changes completely.

4. Which one — and when

switchMap — “latest wins”

Type-ahead search, autocomplete, reacting to route param changes, re-fetching on filter change. Anything where a newer input makes the older request irrelevant. The safe default for reads.

mergeMap — “all in parallel”

Independent side-effects that can overlap: upload N files, fire-and-forget analytics, parallel lookups. Don't use for type-ahead — stale responses leak through.

concatMap — “in order, one at a time”

Order-sensitive writes: sequential PATCHes, a queue of commands that must not overlap. Correct ordering, at the cost of piled-up latency.

exhaustMap — “ignore the spam”

Login / submit / “refresh” buttons: ignore repeat clicks until the in-flight request finishes. Kills accidental double-submits dead.

5. Recap

🔀 A flattening operator subscribes to the Observable your projection returns and merges its output into the stream. They differ only in how they treat a new source value while an inner is still running: switchMap cancels the old (latest-wins — use for search), mergeMap runs all concurrently (parallel side-effects), concatMap queues in order (sequential writes), exhaustMap ignores the new (de-spam buttons). Same input, four very different output streams.
