JavaScript Fundamentals

Variables (var / let / const), primitive vs reference types, function forms and the "this" binding trap, lexical scope and closures — the mental model underneath every Angular component, React hook, and Node service in this Hub.

🟨 What is JavaScript, and why start here before Angular/React/TypeScript?

JavaScript is the language every browser runs natively, and — via Node.js — a common server language too. It is dynamically typed (a variable can hold any type, and that type can change), single-threaded with an event loop (one thing runs at a time, but async work like network calls doesn't block it), and it uses lexical scoping (where a variable is visible is decided by where it's written in the source, not by how the code happens to run). TypeScript adds a type-checking layer on top of exactly this language; Angular, React, and Node are all frameworks and runtimes built on it. If a concept here feels shaky, everything downstream — signals, hooks, RxJS, Express middleware — will feel shakier than it needs to. This page is the foundation the rest of the Web track (and TypeScript, Angular, React, Node) assumes you already have.

  • var / let / const — three ways to declare a variable, with real, breaking differences in scope.
  • Primitives copy by value, objects copy by reference — the single most common source of "how did that change?!" bugs.
  • Regular functions get a dynamic this (decided by how they're called); arrow functions inherit this lexically (decided by where they're written).
  • Closures — a function that remembers the scope it was created in, even after that scope's function has already returned.

The problem this solves

A for (var i...) loop with a setTimeout inside logs the same final number three times, not 0/1/2 — until you understand var vs let scoping, that bug looks like magic.

Core concepts here

Scope (where a name is visible), hoisting (declarations are processed before code runs), closures (functions that carry their birth-scope with them), and this (which object a function call is "on").

Where this shows up next

Angular signals and RxJS callbacks, React hooks' closure rules ("stale closure" bugs), Node's this inside Express route handlers, and every .then()/async callback you'll ever write.

Full-stack / CIAM angle: A debounced token-refresh function, an Angular interceptor that captures this.authService in a closure, a login form's submit handler needing the right this — every one of these is built on exactly the four ideas on this page. Get them solid here and half of "weird" frontend bugs stop being weird.

1. Variable Declarations — var, let, const

All three declare a variable, but they disagree on scope (where the name is visible) and reassignment (whether the binding can change). Modern JavaScript avoids var almost entirely.

var
function-scoped, hoisted & initialized to undefined
let
block-scoped, hoisted but in a "temporal dead zone" until declared
const
block-scoped, cannot be reassigned — but a const object is still mutable
Block scope
{ } — if/for/while bodies, not just functions
Function scope
only function bodies create a new scope for var
// const freezes the BINDING, not the object
const user = { name: 'Alice' };
user.name = 'Bob';      // ✅ fine — mutating the object
user = { name: 'Eve' };  // ✗ TypeError — reassigning the binding

// var leaks out of blocks
if (true) { var leaked = 1; }
console.log(leaked); // 1 — var ignored the if-block

if (true) { let trapped = 1; }
console.log(trapped); // ✗ ReferenceError — let respects the block
The classic interview trap: for (var i = 0; i < 3; i++) { setTimeout(() => console.log(i), 0); } logs 3, 3, 3, not 0, 1, 2 — because var i is one shared binding for the whole loop. Swap to let i and it logs 0, 1, 2, because let creates a fresh binding of i for every iteration. See scenario ① above, animated.

2. Types — Primitives, References, and == vs ===

JavaScript has 7 primitive types (string, number, boolean, null, undefined, symbol, bigint) and everything else — objects, arrays, functions — is a reference type. How they're copied on assignment is the single most important distinction in the language.

Primitives — copy by value

let a = 5;
let b = a;   // b gets its OWN copy of 5
b = 10;
console.log(a); // 5 — untouched

Objects — copy by reference

let obj1 = { x: 1 };
let obj2 = obj1; // obj2 points at the SAME object
obj2.x = 99;
console.log(obj1.x); // 99 — obj1 changed too!
// == coerces types before comparing; === does not (always prefer ===)
'5' == 5    // true  — '5' is coerced to a number first
'5' === 5   // false — different types, no coercion, not equal
null == undefined   // true  — special-cased loose equality
null === undefined  // false — different types
To copy an object instead of sharing a reference: { ...obj1 } (shallow) or structuredClone(obj1) (deep). This is exactly why Angular/React never mutate state objects directly — they replace them with a new reference so change detection can tell "did this actually change?" with a cheap reference comparison instead of a deep one.

3. Functions, Scope & Closures

Three ways to write a function — and one behavioral difference between them that matters more than syntax: what this means inside.

FormSyntaxthis behavior
Function declarationfunction f() {}Dynamic — determined by how f() is called
Function expressionconst f = function() {}Dynamic — same rule as a declaration
Arrow functionconst f = () => {}Lexical — inherited from where f was written, never rebound
const timer = {
  label: 'Countdown',
  start() {
    // ✗ regular function: setTimeout calls it plainly, so `this` is NOT timer
    setTimeout(function() { console.log(this.label); }, 100); // undefined

    // ✅ arrow function: `this` is inherited from start(), which IS timer
    setTimeout(() => console.log(this.label), 100); // 'Countdown'
  }
};
timer.start();

Closures: a function "remembers" the variables from the scope it was created in — even after that outer function has already returned and would normally be gone.

function makeCounter() {
  let count = 0;               // private — nothing outside can touch this directly
  return () => ++count;      // this arrow closes over `count`
}
const counterA = makeCounter();
const counterB = makeCounter();
counterA(); counterA();  // 1, 2 — counterA's own private count
counterB();              // 1 — a completely separate count, unaffected by counterA
The call stack, Web APIs (like setTimeout), and the callback queue are how JavaScript stays single-threaded but non-blocking: synchronous code always finishes running before any queued callback gets a turn — that's why a setTimeout(fn, 0) callback still runs after the rest of the current script.
