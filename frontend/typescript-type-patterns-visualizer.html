1. Branded / Nominal Types

TypeScript's structural type system means any two types with the same shape are interchangeable. This is usually helpful, but sometimes you want distinct identity. Consider user IDs and post IDs: both are strings, but you should never be able to pass a post ID where a user ID is expected. At runtime they're identical, but at the type level they're different.

The standard solution is branding: intersect the base type with a unique marker type. The marker is never actually present at runtime — it exists only in the type system to distinguish the types from each other.

// The problem — these are both just string at runtime
type UserId = string;
type PostId = string;

declare function getUser(id: UserId): User;

const postId: PostId = "post-123";
getUser(postId);  // ✓ — No error! Both are just string. This is the bug.
// The solution — brand the types
type UserId = string & { readonly __brand: 'UserId' };
type PostId = string & { readonly __brand: 'PostId' };

// 'Brand' utility — cleaner way to define branded types
type Brand<T, B> = T & { readonly __brand: B };
type UserId = Brand<string, 'UserId'>;
type PostId = Brand<string, 'PostId'>;
type Pixels = Brand<number, 'Pixels'>;
type Milliseconds = Brand<number, 'Milliseconds'>;

The brand function — the only place you cast

// The 'as' cast is ONLY done in the brand constructor functions
// Everywhere else in the codebase, the types flow naturally
const toUserId = (s: string): UserId => s as UserId;
const toPostId = (s: string): PostId => s as PostId;

// Usually combined with validation
function parseUserId(raw: string): UserId {
  if (!raw.startsWith('usr_')) throw new Error(`Invalid user ID: ${raw}`);
  return raw as UserId;
}

// Now the type system enforces correct usage
declare function getUser(id: UserId): User;
declare function getPost(id: PostId): Post;

const uid = toUserId("usr_42");
const pid = toPostId("post_7");

getUser(uid);   // ✓
getPost(pid);   // ✓
// getUser(pid);   // ✗ ERROR — Argument of type 'PostId' is not assignable to 'UserId'
// getPost("raw"); // ✗ ERROR — plain string is not assignable to PostId
Branded types work at zero runtime cost. The __brand property doesn't actually exist on the value — it's purely a type-level marker. No extra memory, no extra runtime checks. The type system enforces the invariant; at runtime it's still just a string or number.

2. Phantom Types & Builder Pattern (Type-State Pattern)

A phantom type is a generic type parameter that never appears in the actual runtime representation — it's used only to carry type-level information. Combined with a builder pattern, this lets you enforce that API operations happen in the correct order, checked at compile time.

The idea: each state of the builder is a different generic instantiation. Methods return a new type with an updated state marker. The final method (.build()) only exists on the type that represents the fully-configured state.

// Type-state: tracks what has been configured on the query builder
interface QueryState { table: boolean; columns: boolean; }

// The phantom type S is never stored — it's purely type-level metadata
class QueryBuilder<S extends QueryState = { table: false; columns: false }> {
  private _table = '';
  private _columns: string[] = [];
  private _where: string | undefined;

  from(table: string): QueryBuilder<{ table: true; columns: S['columns'] }> {
    this._table = table;
    return this as any;  // the cast is safe — we control this class
  }

  select(...cols: string[]): QueryBuilder<{ table: S['table']; columns: true }> {
    this._columns = cols;
    return this as any;
  }

  where(condition: string): this {
    this._where = condition;
    return this;
  }

  // build() only callable when BOTH table and columns are configured
  // S['table'] extends true AND S['columns'] extends true
  build(this: QueryBuilder<{ table: true; columns: true }>): string {
    const where = this._where ? ` WHERE ${this._where}` : '';
    return `SELECT ${this._columns.join(', ')} FROM ${this._table}${where}`;
  }
}

// Valid — both .from() and .select() called before .build()
const sql = new QueryBuilder()
  .from('users')
  .select('id', 'email')
  .where('age > 18')
  .build();  // ✓ "SELECT id, email FROM users WHERE age > 18"

// Invalid — .build() called without .from() or .select()
// new QueryBuilder().build();  // ✗ ERROR at compile time
// new QueryBuilder().from('users').build();  // ✗ ERROR — columns not set
Type state in the real world: this pattern appears in HTTP client builders, ORM query builders, test harness builders, and any API where steps must happen in order. The key insight: instead of throwing at runtime when .build() is called too early, you get a compile-time error. The invalid state is unrepresentable.

3. Result / Either Pattern

Exceptions are invisible to the type system. If a function might throw, TypeScript won't remind callers to handle the error — there's no throws equivalent. The Result pattern makes errors explicit in the return type: every function that can fail returns Result<T, E>, a discriminated union of success and failure.

// Core Result type — a discriminated union
type Result<T, E = Error> =
  | { ok: true;  value: T }
  | { ok: false; error: E };

// Constructor functions
const Ok  = <T>(value: T): Result<T, never> => ({ ok: true, value });
const Err = <E>(error: E): Result<never, E> => ({ ok: false, error });

// Functions that can fail return Result instead of throwing
function parseJson(input: string): Result<unknown, 'invalid-json'> {
  try {
    return Ok(JSON.parse(input));
  } catch {
    return Err('invalid-json');
  }
}

// Callers MUST handle both cases — the type system enforces this
const result = parseJson('{"id":1}');
if (result.ok) {
  console.log(result.value);  // only accessible inside ok:true branch
} else {
  console.error(result.error);  // only accessible inside ok:false branch
}

Chaining results — railway-oriented programming

// andThen: transform the success value; pass errors through unchanged
function andThen<T, U, E>(
  result: Result<T, E>,
  fn: (value: T) => Result<U, E>
): Result<U, E> {
  return result.ok ? fn(result.value) : result;
}

// mapOk: transform the value inside Ok without failing
function mapOk<T, U, E>(
  result: Result<T, E>,
  fn: (value: T) => U
): Result<U, E> {
  return result.ok ? Ok(fn(result.value)) : result;
}

// Method-chaining version (fluent API)
class ResultChain<T, E> {
  constructor(private result: Result<T, E>) {}

  andThen<U>(fn: (v: T) => ResultChain<U, E>): ResultChain<U, E> {
    return this.result.ok ? fn(this.result.value) : new ResultChain(this.result);
  }

  map<U>(fn: (v: T) => U): ResultChain<U, E> {
    return new ResultChain(this.result.ok ? Ok(fn(this.result.value)) : this.result);
  }

  unwrap(): Result<T, E> { return this.result; }
}

// Real usage — parse JSON → validate → extract field, errors handled at the end
const userResult = ResultChain.of(parseJson(rawInput))
  .andThen(data => validateUser(data))
  .map(user => user.email)
  .unwrap();

if (userResult.ok) {
  sendWelcomeEmail(userResult.value);  // userResult.value is string (email)
}

4. Recursive Types

TypeScript supports types that reference themselves. This is essential for modeling tree-like or nested data: JSON values, file system paths, nested config objects, AST nodes. The key requirement: the recursive part must be a property type, not the type alias itself directly — TypeScript needs a level of indirection to avoid infinite expansion.

JSON value — the canonical recursive type

// JSON can be: a primitive, an array of JSON, or an object of JSON values
type JSONValue =
  | string
  | number
  | boolean
  | null
  | JSONValue[]                       // recursive: array
  | { [key: string]: JSONValue };   // recursive: object

// Fully typed — TypeScript knows all valid JSON shapes
const user: JSONValue = {
  name: "Alice",
  scores: [1, 2, 3],
  meta: { active: true, tags: ["admin"] }
};
// user.undefined_key;  // ✓ — index sig allows it, returns JSONValue

DeepPartial — making all nested properties optional

type DeepPartial<T> = {
  [K in keyof T]?: T[K] extends object
    ? DeepPartial<T[K]>   // recurse into nested objects
    : T[K];               // primitive — use as-is
};

interface Config {
  server: { host: string; port: number; ssl: { cert: string; key: string }; };
  db: { url: string; poolSize: number; };
}

type PartialConfig = DeepPartial<Config>;
// {
//   server?: { host?: string; port?: number; ssl?: { cert?: string; key?: string } }
//   db?: { url?: string; poolSize?: number }
// }

Tree node type — the data structure

// Binary tree where each node holds a value of type T
type TreeNode<T> = {
  value: T;
  left?:  TreeNode<T>;  // recursive: left subtree
  right?: TreeNode<T>;  // recursive: right subtree
};

// Nested comments thread — each comment can have child replies
interface Comment {
  id: string;
  text: string;
  author: string;
  replies: Comment[];  // recursive: nested comments
}

// Path in a file system
type FSNode =
  | { kind: 'file';   name: string; size: number }
  | { kind: 'dir';    name: string; children: FSNode[] };  // recursive

5. Opaque Types and Type Aliases as Documentation

Type aliases aren't just abbreviations — they're documentation. A function that takes a Milliseconds parameter is much more self-documenting than one that takes a number. TypeScript encourages using type aliases aggressively to communicate intent.

// Without aliases — confusing signature
function retry(fn: () => Promise<void>, n: number, d: number): Promise<void>;

// With aliases — self-documenting
type Milliseconds = Brand<number, 'ms'>;
type RetryCount   = Brand<number, 'retries'>;

function retry(
  fn: () => Promise<void>,
  maxRetries: RetryCount,
  delayMs: Milliseconds
): Promise<void>;

// The call site makes the intent obvious
retry(fetchUser, 3 as RetryCount, 500 as Milliseconds);
// Can't accidentally swap the arguments — they're different types

Readonly inputs, Mutable internals

// Functions should accept Readonly inputs — never mutate what you're given
function processItems(items: Readonly<{ id: string; value: number }[]>): number[] {
  // items.push(...) would be a compile error — Readonly prevents mutation
  return items.map(i => i.value * 2);
}

// Internal mutable type — for when you need to build something up piece by piece
type Mutable<T> = { -readonly [K in keyof T]: T[K] };

function buildConfig(...): Readonly<Config> {
  const draft: Mutable<Config> = {} as Mutable<Config>;
  draft.host = 'localhost';  // mutable during construction
  draft.port = 3000;
  return Object.freeze(draft) as Readonly<Config>;  // freeze then return as immutable
}

6. Exhaustive Switches with never

One of TypeScript's most powerful patterns: use the never type to make the compiler enforce that every member of a union is handled. When you add a new variant to a discriminated union, every switch/if-else that doesn't handle it becomes a compile error.

type Shape =
  | { kind: 'circle';    radius: number }
  | { kind: 'rectangle'; width: number; height: number }
  | { kind: 'triangle';  base: number;  height: number };

// The assertNever helper — takes a value that should be 'never' at this point
function assertNever(x: never): never {
  throw new Error(`Unhandled case: ${JSON.stringify(x)}`);
}

function area(shape: Shape): number {
  switch (shape.kind) {
    case 'circle':
      return Math.PI * shape.radius ** 2;
    case 'rectangle':
      return shape.width * shape.height;
    case 'triangle':
      return 0.5 * shape.base * shape.height;
    default:
      // TypeScript narrows 'shape' to 'never' here — all cases handled
      return assertNever(shape);
  }
}

// Now add a new shape:
// | { kind: 'ellipse'; rx: number; ry: number }
// TypeScript IMMEDIATELY errors on area()'s default case:
// "Argument of type '{ kind: "ellipse"; rx: number; ry: number }' is not
//  assignable to parameter of type 'never'"
// You can't forget to handle the new case.
The superpower: without assertNever, TypeScript might warn about a missing case — or might not, depending on your strictness settings. With assertNever, it's a hard compile error no matter what. You've encoded the requirement "all cases must be handled" directly into the type system.

7. Strongly Typed Event Emitter

Standard Node.js EventEmitter is untyped — .on('click', (data) => any) gives you no type safety. A generic event emitter typed over an event map provides full type safety: the event name is checked as a key, and the callback receives the correct type for that event.

// EventMap: maps event names to their payload types
interface AppEventMap {
  userLogin:   { userId: string; timestamp: Date };
  userLogout:  { userId: string };
  pageView:    { path: string; referrer?: string };
  error:       Error;
}

// Typed event emitter — generic over the EventMap
class TypedEmitter<Events extends Record<string, unknown>> {
  private listeners = new Map<keyof Events, Function[]>();

  on<K extends keyof Events>(
    event: K,
    listener: (data: Events[K]) => void
  ): this {
    const arr = this.listeners.get(event) ?? [];
    this.listeners.set(event, [...arr, listener]);
    return this;
  }

  emit<K extends keyof Events>(event: K, data: Events[K]): void {
    this.listeners.get(event)?.forEach(fn => fn(data));
  }

  off<K extends keyof Events>(event: K, listener: (data: Events[K]) => void): this {
    const arr = this.listeners.get(event) ?? [];
    this.listeners.set(event, arr.filter(fn => fn !== listener));
    return this;
  }
}

// Usage — fully typed
const emitter = new TypedEmitter<AppEventMap>();

emitter.on('userLogin', ({ userId, timestamp }) => {
  // userId: string, timestamp: Date — no annotation needed
  console.log(`User ${userId} logged in at ${timestamp.toISOString()}`);
});

emitter.emit('userLogin', { userId: 'u1', timestamp: new Date() });
// emitter.on('unknown', ...);  // ✗ ERROR — 'unknown' not in AppEventMap
// emitter.emit('error', 'string');  // ✗ ERROR — payload must be Error
