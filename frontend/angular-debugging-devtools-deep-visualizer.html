Browser & Angular DevTools

Half of debugging speed is reaching for the right panel. The browser DevTools and the Angular DevTools extension each answer specific questions — Network for "is the call working?", Sources for breakpoints in your real TypeScript, the Angular Profiler for "why did this re-render?", the component explorer for live state. Match the symptom to the tool and you skip the flailing.

🛠️ Which devtools panel answers which question — a reference card

Most Angular debugging time is wasted in the wrong panel — hunting a missing HTTP header in Sources, or a slow component in Network. Each tool answers a specific category of question; matching the symptom to the right tool is the whole skill. This page maps symptoms → panels so you debug faster.

  • Network — is the call firing? what headers/body? is the Bearer token attached? what's the status?
  • Sources — breakpoints in your real .ts (via source maps); step through service methods.
  • Angular DevTools — the component tree (live @Input/@Output) + a CD profiler ("why is this rendering 50×/s?").
  • Console helpers — ng.getComponent($0), ng.getContext($0), ng.profiler.timeChangeDetection(), ng.applyChanges().
  • Pick the panel by symptom: data/headers → Network; logic → Sources; re-render storms → Angular DevTools profiler.

Browser DevTools — what for

Network: is the API call firing? headers? response body? is the token in Authorization? Sources: breakpoints in real .ts via source maps. Console: ng.getComponent($0) for the component behind the selected element.

Angular DevTools extension

Adds an "Angular" panel: Component Tree (browse the hierarchy, see @Input/@Output live) and Profiler (record a CD cycle, see which components were checked and how long). The tool for "why is this re-rendering constantly?"

Console commands

ng.getComponent($0) — instance for the selected element; ng.getContext($0) — template context in loops; ng.profiler.timeChangeDetection() — CD time over 500ms; ng.applyChanges(c) — force CD on a component.

Debugging the CIAM auth flow:1) Network → filter /api/ → confirm every request has Authorization: Bearer …; 2) on a 401, compare the token to its decode — expired? 3) Angular DevTools → find AuthStore → read user()/accessToken() live; 4) component not updating after login? breakpoint in AuthStore.setUser() to confirm signal.set() ran.

or, Angular DevTools isn't broken in production — Angular made sure there's nothing left for it to read

The problem

You open Angular DevTools on the staging build. The Components tab is empty. You assume the extension is broken.

You spent twenty minutes reinstalling an extension that was never broken

Staging (correctly) builds with the production configuration. You open the app, pop the Angular panel, and get an empty tree, or "could not find Angular on this page." Reasonable next moves: reinstall the extension, check its permissions, file a bug. None of that is the problem. A production build strips the exact debug metadata — component instance references, template locations, the internal registry Angular DevTools reads from — specifically because shipping it bloats the bundle and hands internals to anyone with a console open. The panel isn't malfunctioning. It's accurately reporting that the thing it needs was deliberately deleted.

The wrong assumption: a devtools panel showing nothing means the tool failed. Here it means the build succeeded at exactly what a production build is supposed to do.

Every devtools panel reads a different layer, and a production build only ships some of the layers. Network and Sources (with source maps) read things that exist no matter how the app was built — real HTTP traffic, real mapped code. Angular DevTools' Components and Profiler tabs read Angular's own internal debug registry, which is exactly the layer a production build is optimized to delete. Know which layer a symptom lives in and you know which panel — and which build — can even see it.
Think of a production Angular build like a magic show after the reveal — the mechanism has been struck from the stage. The trick still works exactly the same for the audience (your user), but the trapdoors, wires, and mirrors (debug metadata) are gone, because they're expensive to keep around and nobody in the audience needed to see them. Angular DevTools is the backstage tour. It only works when the wires are still there to show you.

Angular DevTools

No — I'm reading a registry Angular attaches to the page in dev mode. A production build doesn't attach it; there's nothing here for me to display, and I'm telling you that honestly instead of faking a tree.

The Network panel

I don't have that problem. I just watch real HTTP traffic leave and arrive — that happens the same way whether the JS behind it is a 2MB dev bundle or a 400KB minified one.

The Profiler tab

And I especially need dev mode — I'm not just reading state, I'm timing every change-detection cycle and attributing it to a component. That instrumentation is exactly the kind of thing a production build exists to strip out.

The mechanism

One vague bug report. Five panels. Only one of them can actually see the problem — and only on the right build.

  1. A bug report arrives — "the profile page looks wrong after logging in." Vague. First job: narrow which layer is brokenthe actual first step, and it isn't opening a panel yet
  2. Is the data wrong, or the display of correct data? Network answers this — inspect the real response bodyrules out half the codebase in one look
  3. API response is correct → the bug is in Angular's own code. Sources (breakpoints on your real .ts) or the component explorer (live signal values) take overdifferent tool, same layer: your logic
  4. State looks right too, but the wrong thing renders — or renders too often? That's the Profiler's job: record a cycle, see exactly which component was checked and whythe only panel that answers "why did THIS re-render"
  5. None of that works on a build with no dev metadata? You're not debugging wrong — you're debugging the wrong buildcircle back to step 0: which config is this?

Step 5 is the one worth remembering, because it's the step that gets skipped. Every panel here reads a specific layer — real network traffic, real mapped source, or Angular's internal debug registry — and only the last one disappears in production. A symptom that reproduced in dev but not in staging is almost never a build difference in your app; it's a build difference in what the tool can see.

Four honest guesses, and only the build you're actually running can rule any of them out. On a production build, the last two aren't guesses that failed — they're panels with nothing left to read.

A very reasonable guess — the Console feels like a completely different tool from the visual DevTools panel, so it's natural to assume it has its own separate access. It doesn't. ng.getComponent() and the Components tab are two different front ends reading the exact same underlying debug data Angular attaches in dev mode — strip that data and both go dark together.

Right. Whichever surface you ask through — the visual panel or a console one-liner — you're asking the same question of the same registry, and production doesn't populate it. This is also why "just use the console instead" isn't a real workaround for a production issue: reproduce it against a dev build locally, or lean on Network/Sources, which don't have this dependency.

Not browser-specific — these are plain global functions Angular itself attaches to the page in dev mode, callable from any console that can run JS against it (Chrome, Firefox, Edge). What gates them is the build configuration, not which browser's devtools happen to be open.

Where you've seen this before

React's own devtools hit the identical wall, a much older toolchain hit it first, and the panel you reach for first has a quieter cost.

React DevTools goes just as blind on a production build

The React DevTools extension's Components and Profiler tabs depend on the exact same category of thing — fiber debug metadata React's production build strips for the same bundle-size and internals-exposure reasons. Same framework-agnostic lesson under a different logo: a framework devtools extension is only ever as capable as the build it's pointed at.

A stripped binary and a missing -g flag

gdb on a release binary compiled without debug symbols shows raw addresses instead of variable names and line numbers — not because gdb is broken, but because the symbol table it reads was deliberately left out to shrink the binary. Angular DevTools versus a production bundle is the exact same trade, decades later, in a browser instead of a compiler.

no symbols in, nothing to read out

The Network tab that saves you also leaks the bearer token

The exact panel this page tells you to check first for a CIAM 401 — Network, filtered to /api/ — shows the raw Authorization: Bearer … header in plaintext for every request. That's essential for debugging, and also exactly why screen-sharing your DevTools on a support call, or attaching a HAR export to a ticket, is a real credential leak: anyone who can read that header can replay it until it expires. Redact or let the token expire before a network capture leaves your own machine.

Questions from the back row

If Angular DevTools needs dev mode, is it safe to just always ship a dev build so support and QA can debug in place?

No — a dev build skips minification and Ivy's production optimizations, and it ships the exact debug metadata (component internals, template source locations) you generally don't want sitting on a public origin. If a staging environment genuinely needs to be debuggable, give it its own build configuration with the flags you actually want, rather than quietly shipping the same artifact your real users get.

Does the Angular DevTools Profiler slow the app down while it's recording?

Yes, noticeably — timing and attributing every change-detection cycle to a specific component is real instrumentation overhead, the same tax every profiler pays (Chrome's own Performance panel, React's Profiler included). The absolute millisecond numbers you see while recording aren't what a real user experiences; what's trustworthy is the relative comparison — which component consumed the most time this cycle, and whether that number drops after your fix. Profile to find the outlier, not to get a production timing number.

What's ng.applyChanges() actually for?

It forces a change-detection run on one component instance from the console — which tells you whether you have a change-detection problem or a data problem. If forcing it fixes the stale value, the data was already right and CD just hadn't run yet; if nothing changes, the data itself is wrong. It's a console debugging tool only — like ng.getComponent(), it depends on dev-mode debug metadata, so there's nothing to call it against on a shipped production build, and it wouldn't do anything useful there even if you tried.

1. Two toolkits

  • Browser DevTools (built in): Network, Console, Sources (breakpoints + source maps), Elements, Performance, Memory.
  • Angular DevTools (extension): a Components explorer (inputs/outputs/state/signals/injected services) and a Profiler that records change-detection cycles and shows what triggered them and how long they took.

Angular DevTools needs a dev build (it reads Angular's debug metadata, stripped from production). Source maps likewise make Sources/Console show your TypeScript instead of the minified bundle.

3. Angular DevTools, specifically

Components explorer

  • Click any node in the component tree to see its @Inputs, state, and signals — and edit them live to test a hypothesis.
  • See the injected services and the resolved DI path.
  • $0 in the console = the selected element's component instance.

Profiler

  • Record an interaction → every change-detection cycle as bars.
  • See which components were checked and how long each took — and what triggered the cycle.
  • Spot needless checks (a missing OnPush, an over-firing @Input).

↪ What those CD cycles are: Angular · Change Detection Internals. The dev-only CD error: Debugging · ExpressionChangedAfterItHasBeenChecked.

4. Speed tricks

  • Preserve log (Network & Console) so a redirect/reload doesn't wipe the evidence.
  • Conditional & logpoint breakpoints in Sources — right-click the gutter; log without editing code (same idea as the Spring breakpoint zoo).
  • "Break on" DOM changes (Elements → right-click → Break on subtree modifications) to catch what mutates a node.
  • Throttle the network to reproduce slow-connection and cold-start behavior.
  • Source maps in prod: generate them but host them privately (or upload to your error tracker) so prod stack traces de-minify without shipping source to users.

5. One-sentence recap

🧰 Reach for the right panel: Network for API/CORS/payload bugs, Sources (+ source maps) to breakpoint real TypeScript, the Angular DevTools Profiler for "why did this re-render / what's slow", the Components explorer to inspect and live-edit a component's inputs/signals/state, Elements for CSS/specificity, and Memory snapshots to confirm a leak — remembering Angular DevTools and de-minified traces need dev builds / source maps.
