Declaration Files (.d.ts)

How TypeScript types JavaScript code it didn't write. The anatomy of .d.ts files, ambient declarations, module augmentation, and the full resolution strategy TypeScript uses to find your types.

📑 What are declaration files (.d.ts) — and how does TS know the types of JS npm packages?

Most npm packages are plain JavaScript with no type annotations — TypeScript still checks your usage of them through declaration files (.d.ts), which carry type information and no runtime code, like C header files. They arrive three ways: bundled with the package, from DefinitelyTyped (@types/*), or hand-written for legacy/global code. declare asserts something exists at runtime without defining it, and module augmentation extends existing types — e.g. adding a user property to Express's Request.

  • .d.ts = types only, no code. It describes JS shapes so TS can typecheck your imports.
  • Three sources: bundled types, @types/* (DefinitelyTyped), or your own ambient files.
  • declare asserts runtime existence — declare const ENV: … with no implementation.
  • Module augmentation extends existing types — add fields to Request/Window or a third-party class.

.d.ts anatomy

// userService.d.ts — types for a JS module export declare class UserService { constructor(config: { baseUrl: string }); getUser(id: number): Promise<{ id: number; name: string; email: string; }>; updateUser(id: number, data: Partial<{ name: string; email: string; }>): Promise<void>; } // Ambient value (no implementation) declare const API_VERSION: string; // Ambient namespace declare namespace Utils { function formatDate(d: Date): string; interface Config { timeout: number } }. No function bodies — just signatures. TypeScript uses this to typecheck your code that imports the module.

Module augmentation

// Extend Express Request with a user property // types/express/index.d.ts import { JwtPayload } from './jwt'; declare global { namespace Express { interface Request { user?: JwtPayload; tenantId?: string; } } } // Now req.user is typed everywhere in your Express app // Extend Window with custom properties declare global { interface Window { analyticsQueue: AnalyticsEvent[]; pingConfig: { clientId: string }; } }. Module augmentation must be inside a module file (has at least one import/export).

Type resolution order

When you write import { HttpClient } from '@angular/common/http', TypeScript finds types by: (1) Check node_modules/@angular/common/http/package.json for "types" or "typings" field → bundled .d.ts. (2) Check node_modules/@angular/common/http/index.d.ts. (3) Check node_modules/@types/@angular/common/http (rarely needed). tsconfig.json settings: "typeRoots": ["./node_modules/@types", "./src/types"] — look here for ambient type files. "types": ["node", "jest"] — only include these @types packages (not all of @types). "paths": { "@app/*": ["src/app/*"] } — path aliases for imports.

CIAM / Angular: If Ping's JS SDK ships no types, write src/types/ping-sdk.d.ts: declare module '@pingidentity/p1-services' { export interface PingUser { sub: string; email: string; roles: string[] }; export function getUser(token: string): Promise<PingUser>; }. Type env vars with declare namespace NodeJS { interface ProcessEnv { VITE_API_URL: string } }, and give the Angular environment a typed interface Environment imported everywhere instead of touching environment.ts directly.

The problem

A .d.ts file is TypeScript's word against nobody's — it's never checked against the real code.

verifyToken() says .valid, the SDK says .ok, and nothing ever compares them

legacy-auth-sdk is untyped, so someone on your team hand-writes a declaration for it: declare module 'legacy-auth-sdk' { export function verifyToken(token: string): { valid: boolean; userId: string }; }. Every caller across the codebase gets full autocomplete and writes if (result.valid) { ... }. It all compiles clean.

The SDK actually returns { ok: boolean; sub: string } — maybe it always did and the .d.ts was wrong from day one, maybe a minor version bump renamed the fields. TypeScript has no way to know either way: a .d.ts file isn't compiled against the JavaScript it describes, run against it, or diffed against it on install. It's simply believed.

every call site type-checks ✓ autocomplete shows .valid and .userId ✓ result.valid is undefined at runtime ⚠

You didn't lie to the compiler. Whoever wrote the .d.ts did, and the compiler had no way to check.

Verify the shape once, at the boundary
Put a real runtime check at the one place the SDK's output enters your code — a type guard, a schema, or at minimum an assertion in dev ↓ this is the only place anything ever actually looks at what the SDK returned If you must hand-write the .d.ts, pin it to the exact SDK version and re-verify it on every upgrade ↓ a .d.ts file doesn't fail CI when the real API drifts — you have to make something else fail instead Prefer an SDK-shipped or @types declaration over a hand-written one wherever one exists
A .d.ts file is an assertion, not a contract TypeScript can enforce. TypeScript type-checks your .ts files against the shapes described in a declaration file, but it never checks the declaration file against the JavaScript it claims to describe — there's no build step, no runtime probe, nothing. A hand-written or stale declaration can be confidently, silently wrong for years, and every caller downstream inherits that wrongness as verified fact.
A .d.ts file is a museum placard next to an empty display case — it tells you exactly what's supposed to be behind the glass, and nobody working there has checked lately whether it still is.

Follow one field name from a hand-written .d.ts to a boolean that's always false.

  1. legacy-auth-sdk.js actually returns { ok: true, sub: 'u_42' } from verifyToken()reality
  2. Your team hand-writes legacy-auth-sdk.d.ts declaring { valid: boolean; userId: string } insteaddeclaration
  3. tsc type-checks every caller against the .d.ts — never against the real SDK sourceone-way trust
  4. Every if (result.valid) compiles clean; TypeScript has no mechanism to compare the declaration to realityno verification
  5. At runtime, result.valid reads a property the returned object never had: undefinedruntime
  6. if (undefined) is always falsy — every caller's "success" path silently never runssilent failure

Step three is the crux. tsc's entire relationship with a .d.ts file is trust, not verification — there's no second pass anywhere that opens the actual SDK file and compares field names against what was declared.

1. What are .d.ts files?

A .d.ts file is a TypeScript file that contains only type information — no executable code, no expressions, no statements that would produce JavaScript output. They are pure declarations: "this JavaScript artifact has this shape."

When TypeScript compiles a .ts file, it can optionally emit a companion .d.ts alongside the compiled .js. The .d.ts contains all the exported type information from the original file, stripped of all implementation. This is how library authors ship type information with their packages.

// math.ts — source TypeScript file
export function add(a: number, b: number): number {
  return a + b;
}
export interface Vector2D { x: number; y: number; }

// math.js — the compiled output (TypeScript-free)
export function add(a, b) { return a + b; }

// math.d.ts — the generated declaration file (type-only)
export declare function add(a: number, b: number): number;
export interface Vector2D { x: number; y: number; }
Key insight: .d.ts files are to TypeScript what .h header files are to C/C++ — they describe the shape of a compiled artifact so that other code can use it with full type safety. The .js file is what actually runs; the .d.ts is what TypeScript reads.

2. Three sources of type definitions

When you import a package, TypeScript looks for types in three places, in order:

SourceHow it worksExample
Bundled with package The npm package itself ships .d.ts files. The package.json "types" field points to the entry declaration file. typescript, zod, rxjs
@types/package A separate @types/package package on npm, maintained by the community via DefinitelyTyped. Installed separately: npm i -D @types/node @types/node, @types/express, @types/lodash
Local ambient declarations A .d.ts file in your own project using declare module to add types for a completely untyped package. A vendor-types.d.ts in your src/ folder

3. Anatomy of a declaration file

Declaration files use the declare keyword throughout. The declare keyword tells TypeScript: "this thing exists at runtime — I'm just describing its shape, not defining it." Without declare, TypeScript would try to emit JavaScript for your type definitions.

// my-library.d.ts — A complete example of declaration file anatomy

// Module-level type alias — no 'declare' needed for pure type constructs
export type ID = string | number;

// Exported interface — describes an object shape
export interface Config {
  host: string;
  port?: number;           // optional property
  readonly version: string; // readonly property
}

// Exported function — uses 'declare' or just the export signature
export declare function connect(config: Config): Promise<void>;

// Function overloads — multiple signatures, no implementation
export declare function parse(input: string): Config;
export declare function parse(input: Buffer): Config;

// Exported class
export declare class Client {
  constructor(config: Config);
  send(data: unknown): Promise<void>;
  close(): void;
  readonly connected: boolean;
}

// Default export (if the library uses module.exports = something)
export default Client;

4. declare module — typing untyped packages

Some packages ship no types at all and have no @types package. TypeScript will give you an error: "Could not find a declaration file for module 'old-lib'." The solution is to add a local ambient declaration in any .d.ts file in your project.

// src/types/vendor.d.ts — ambient declarations for untyped packages

// Minimal: tell TypeScript to accept the import and give it 'any' type
declare module 'old-untyped-lib';

// Better: actually describe the shape
declare module 'legacy-formatter' {
  export interface FormatOptions {
    indent: number;
    quote: 'single' | 'double';
  }
  export function format(code: string, options?: FormatOptions): string;
  export const version: string;
}

// Non-JS imports — telling TS that importing a file gives you a string
declare module '*.svg' {
  const content: string;
  export default content;
}
declare module '*.css' {
  const styles: Record<string, string>;
  export default styles;
}
Wildcard module declarations (*.svg, *.css) are a common pattern in projects using Webpack or Vite. They let you import non-JS files without TypeScript complaining. The import gives you whatever type you declared — a string for SVG content, a Record for CSS modules.

5. Module augmentation — extending existing types

Module augmentation lets you add new declarations to an already-typed module without modifying the original .d.ts files. The classic use case: adding properties to Express's Request object when you've attached something via middleware.

// auth-middleware.ts — your middleware attaches a 'user' to every request
import { Request, Response, NextFunction } from 'express';

// This augments the 'express' module's types — no separate file needed
declare module 'express' {
  interface Request {
    user?: { id: string; email: string; role: 'admin' | 'user' };
    requestId: string;
  }
}

// Now in any route handler, req.user is typed!
export function authMiddleware(req: Request, res: Response, next: NextFunction) {
  req.user = { id: 'u1', email: 'a@b.com', role: 'admin' };
  req.requestId = crypto.randomUUID();
  next();
}

// In a route:
// app.get('/me', (req, res) => {
//   const { id, email } = req.user!;  // fully typed — no 'any'!
// })
How augmentation works: TypeScript merges declarations from multiple locations into a single namespace. When you declare module 'express' { interface Request { ... } }, TypeScript merges your new properties into the existing Request interface. This is called declaration merging, and it works for interfaces and namespaces (but not type aliases or classes).

Augmenting your own modules

// You can also augment your own modules — useful for plugin systems

// base.ts — core module that other modules can extend
export interface PluginRegistry {
  // plugins register themselves here via augmentation
}

// plugin-auth.ts — the plugin augments the registry
declare module './base' {
  interface PluginRegistry {
    auth: { login(): Promise<void>; logout(): void; }
  }
}

// plugin-analytics.ts
declare module './base' {
  interface PluginRegistry {
    analytics: { track(event: string): void; }
  }
}

// After importing both plugins, PluginRegistry has both 'auth' and 'analytics' fields

6. declare global — extending the global scope

Sometimes you need to add properties to the global scope — things that are available everywhere without any import. Examples: a __DEV__ flag injected by your build tool, custom properties added to Window by your app, or environment variable types.

// globals.d.ts — extends the global scope

// Add global variables (e.g., injected by Webpack/Vite)
declare const __DEV__: boolean;
declare const __VERSION__: string;
declare const __API_URL__: string;

// Extend the Window interface (global object in browsers)
declare global {
  interface Window {
    analytics: { track(event: string, props?: Record<string, unknown>): void; };
    __appState: Record<string, unknown>;
  }
}

// Extend process.env for Node.js projects
declare global {
  namespace NodeJS {
    interface ProcessEnv {
      NODE_ENV: 'development' | 'production' | 'test';
      DATABASE_URL: string;
      JWT_SECRET: string;
      PORT?: string;   // optional — may not be set
    }
  }
}

// Now process.env.DATABASE_URL is typed as string (not string|undefined)
// And process.env.UNKNOWN_VAR causes a TypeScript error

7. Ambient declarations — variables, functions, classes

Ambient declarations tell TypeScript about values that exist in the JavaScript runtime environment but are not imported from any module — they are just "there." This is common for legacy globals (jQuery's $), browser APIs that TypeScript doesn't know about yet, or values injected by your runtime environment.

// Ambient variable — exists globally (e.g., injected by a CDN script tag)
declare const jQuery: (selector: string) => JQueryResult;
declare const $: typeof jQuery;

// Ambient function — exists globally (e.g., platform API)
declare function require(path: string): any;
declare function importScripts(...urls: string[]): void;  // Web Worker global

// Ambient class — e.g., a global class provided by the environment
declare class NativeWebSocket {
  constructor(url: string, protocols?: string | string[]);
  send(data: string | ArrayBuffer | Blob): void;
  close(code?: number, reason?: string): void;
  readonly readyState: 0 | 1 | 2 | 3;
}

// Ambient enum — when an enum's values are available globally
declare enum Direction { Up, Down, Left, Right }

8. Triple-slash references

Triple-slash references are single-line comments at the top of a .ts or .d.ts file that serve as compiler directives. They were the original way to include type definitions before tsconfig.json's types array made them mostly unnecessary. You still encounter them in generated declaration files and in some edge cases.

/// <reference types="node" />
// Equivalent to having "@types/node" in tsconfig "types" array, but file-local
// Use when your .d.ts file needs @types/node but you don't want to force it globally

/// <reference path="../types/vendor.d.ts" />
// Includes a specific .d.ts file by path — rarely needed with tsconfig

/// <reference lib="dom" />
// Include a specific TypeScript lib file (dom, es2020, etc.) for this file only
When you still need triple-slash references: when writing a .d.ts file that will be published in an npm package and needs to reference other type definitions. The /// <reference types="..."> directive in a published .d.ts causes TypeScript to automatically install the referenced @types package when a user installs yours.

9. How TypeScript finds your declarations

When you write import { foo } from 'my-lib', TypeScript follows a specific resolution algorithm to find the type definitions. Understanding this prevents hours of debugging "Cannot find module" errors.

// Resolution is controlled by the "moduleResolution" tsconfig option
// Modern projects use "bundler" or "node16" — here's the general flow:

// For import from 'my-lib':
// 1. Check package.json "exports" field (if it exists)
//    → looks for a conditional export matching the current moduleResolution
// 2. Check package.json "types" field
//    → e.g., "types": "./dist/index.d.ts"
// 3. Check for index.d.ts in package root
// 4. Check node_modules/@types/my-lib/index.d.ts
// 5. If none found → error (or 'any' with noImplicitAny:false)

// package.json with full type support:
// {
//   "main": "./dist/index.js",
//   "types": "./dist/index.d.ts",
//   "exports": {
//     ".": {
//       "import": "./dist/index.mjs",
//       "require": "./dist/index.cjs",
//       "types": "./dist/index.d.ts"
//     }
//   }
// }

10. CommonJS, ESM, and UMD module formats

Different JavaScript module formats require different patterns in declaration files.

// CommonJS: module.exports = something
// old-lib/index.d.ts
declare function oldLib(x: string): string;
declare namespace oldLib {
  const version: string;
  function configure(opts: object): void;
}
export = oldLib;  // CommonJS default export syntax

// UMD: works as both global and CommonJS/AMD module
export as namespace MyLib;     // makes it available as window.MyLib globally
export declare function doThing(): void;

// ESM (modern): standard export statements
export declare function doThing(): void;
export declare class MyClass { /* ... */ }
export default MyClass;

11. Best practices

Use overloads for functions that behave differently based on input

// Without overloads — loose, imprecise
declare function createElement(tag: string): HTMLElement;

// With overloads — precise, each call site gets the right type
declare function createElement(tag: 'div'):    HTMLDivElement;
declare function createElement(tag: 'canvas'): HTMLCanvasElement;
declare function createElement(tag: 'input'):  HTMLInputElement;
declare function createElement(tag: string):   HTMLElement;
// The last overload is the fallback for unknown tags

// Generic declarations for flexible return types
declare function parse<T = unknown>(json: string): T;
// parse<User>('{"id":1}') gives you a User type — caller is responsible for correctness

12. DefinitelyTyped and @types

DefinitelyTyped is a massive GitHub repository containing community-maintained type definitions for thousands of JavaScript packages that don't ship their own types. Each package has its types published to npm as @types/package-name.

// Install type definitions for common packages
npm install --save-dev @types/node       # Node.js built-ins (fs, path, etc.)
npm install --save-dev @types/express    # Express.js
npm install --save-dev @types/react      # React (though React ships its own now)
npm install --save-dev @types/lodash     # Lodash utilities

// TypeScript automatically picks up @types/* packages —
// no tsconfig change needed (unless you've set "types" explicitly)

// tsconfig.json — control which @types are included
// {
//   "compilerOptions": {
//     "types": ["node", "jest"]   // only include these @types
//     // omit "types" to include all @types/* in node_modules
//   }
// }
