Rendering, Commit & Lifecycle

"Rendering" is React calling your function — not painting pixels. Watch the exact order: trigger → render (pure) → commit (DOM) → refs & layout effects (sync) → paint → passive effects. Plus the class lifecycle map and what StrictMode really does.

🔁 What is the React rendering lifecycle — and what does "render" actually mean vs "paint"?

"Rendering" means React calls your component and gets back an element tree — not writing to the DOM, not the user seeing anything. The lifecycle: trigger (mount, setState, context, parent), render (your pure function, possibly called twice in StrictMode), commit (diffs written to the DOM), layout effects (useLayoutEffect, synchronous before paint — measure the DOM here), paint (pixels appear — only now does the user see it), then passive effects (useEffect, async after paint — fetch, subscribe, analytics). StrictMode double-invokes render and effects in dev to surface impure renders and missing cleanups; in production it's zero-overhead.

  • Render ≠ paint — render builds the tree; paint is when pixels (and the user) update.
  • Render must be pure — React may call it twice in StrictMode/Concurrent.
  • useLayoutEffect before paint (measure), useEffect after paint (fetch/subscribe).
  • StrictMode double-invokes in dev — catches impure renders and missing cleanup.

Angular lifecycle comparison

React hook → Angular lifecycle equivalent. useEffect(fn, []) → ngOnInit() (runs once after first render/init). useEffect(fn, [dep]) → ngOnChanges(changes) + input changes (runs when dep changes). useEffect(() => { return cleanup; }, []) → ngOnDestroy() (cleanup on unmount). useLayoutEffect → ngAfterViewInit() (after view is initialized). useEffect(fn) (no deps, every render) → no Angular equivalent — Angular doesn't call code after every CD cycle by default. React StrictMode double-invocation → Angular's dev mode performs an extra CD check (ExpressionChangedAfterItHasBeenCheckedError) — both catch imperative bugs during development.

The problem

React tells you render must be pure. React also explicitly lets you call a state setter right there in the render body. Both are true — the trap is whose state you're setting.

The "harmless" refactor that ends in "Maximum update depth exceeded"

A Gallery resets its selection whenever a new items prop arrives, using React's own documented render-time pattern — no useEffect, just a guarded call inside the function body: if (items !== prevItems) { setPrevItems(items); setSelected(null) }. It works: one extra silent re-render, zero flash, no warning.

A teammate "simplifies" it by moving the comparison into a child, <FilterBar onItemsChanged={resetSelection} />, which calls the PARENT's setter conditionally during the CHILD's own render. Same shape of code, same guard — except now the console lights up with "Cannot update a component (Gallery) while rendering a different component (FilterBar)", and if the guard ever fails to stabilize, the app hard-locks with "Maximum update depth exceeded."

the guard condition is identical in both versions ✓ no useEffect either way, by design ✓ the setter now belongs to a DIFFERENT component than the one currently rendering ⚠

Same syntax, different owner — one is a sanctioned React escape hatch, the other is a race against your own render.

The fix: only adjust state you own, in the render that owns it
Move the comparison and the setters back inside Gallery itself ↓ React's exception only covers a component adjusting its OWN state mid-render If a child must react to a prop change, do it in the child's useEffect ↓ an effect runs after commit, so notifying a parent there can never race the parent's own render And keep the trick to one obviously-conditional line per component ↓ it's an escape hatch for "adjust state from props," not a general replacement for effects
Render-phase updates are scoped to the renderer, not the target. React only folds a setState call into the render currently unwinding when that state belongs to a component that is part of THIS SAME pass — itself, or an ancestor already re-rendering above it. A setter reached through a prop and called from a different component's render body is not part of that pass, so React can't silently absorb it — it has to warn you, and if nothing stops the update from recurring, it warns you forever.
Think of render-phase setState like editing a shared draft while it's still being written: fixing a typo in the paragraph you yourself are writing is invisible to everyone else — reaching over to edit a different section while its author is mid-sentence is how you get two people overwriting each other.
You

I called setSelected(null) right in the middle of the function body and nothing broke. I thought renders had to be pure?

React

They do — except for this one carve-out. You updated a piece of state that belongs to the component I'm CURRENTLY running. I just throw away this pass and call your function again immediately, before anyone commits or paints.

You

So I moved the identical call into a child's prop callback to save a render.

React

Now you're editing a DIFFERENT component's state while ITS render is what's running. I can't fold that into this pass — the best I can do is warn you, and if your guard doesn't hold, we do this forever.

The mechanism

Watch what React does the instant it sees a same-component setState mid-render.

  1. The Gallery function begins executing — this IS the render phaserender starts
  2. items !== prevItems is true — a new list arrivedguard passes
  3. setPrevItems(items) and setSelected(null) run, still before returnsame component
  4. React recognizes: this fiber is CURRENTLY rendering, and the update targets its own stateownership check
  5. React discards the JSX this pass would have returnedpass thrown away
  6. React calls Gallery again immediately — synchronously, before commit or paint — and this time the guard is falseinstant re-run

Step 6 is why this never causes a visible flash: the discarded first pass never reached commit, so the browser only ever paints the SECOND result. An effect-based reset, by contrast, would commit the stale render first and correct it a frame later — which is exactly why React documents this pattern as the more efficient option when you genuinely need it.

All three call sites look like "just calling a setter during render." React's response depends entirely on whose fiber is executing right now versus whose state the call targets — the syntax gives no hint of the difference, which is exactly why the child-callback version reads as "the same trick" right up until the console disagrees.

A SearchResults component resets page to 1 whenever query changes, using React's documented render-time pattern directly in its own function body (no useEffect). A teammate refactors so a child <Filters onQueryChanged={resetPage}> calls that same setter, still conditionally, but now from inside the CHILD's render. What changes the next time query updates?

It's not the same at runtime even though the guard logic is identical text — React tracks WHICH fiber is currently rendering, and "the same lines of code" moved to a different component is a different fiber, with a different rule applied to it.

Calling a function prop during render is completely normal (that's how you compute a derived value from a callback, for instance) — the problem here isn't "calling a function," it's specifically that the function sets state belonging to a component that isn't the one currently rendering.

Right — React's render-phase-update exception only covers a component updating state that's part of the CURRENT render pass. Reached from a child's render body, the parent's setter is out of scope for that pass, so React warns instead of silently folding it in — and a guard that never stabilizes turns the warning into an infinite loop.

Where you have seen this before

"You may touch your own turn, never someone else's mid-turn" shows up anywhere a system lets you self-correct but polices reaching sideways.

Angular's ExpressionChangedAfterItHasBeenCheckedError

Angular allows a binding to update within its own change-detection pass, but throws this dev-only error the moment a value changes AFTER Angular already checked it in this cycle — the same "you can adjust during your own pass, not after the fact from somewhere else" boundary.

a dev-only error whose entire job is to catch a timing/ownership violation

Redux's "may not dispatch while a reducer is executing"

Reducers are supposed to be pure, like render — and Redux explicitly throws if a reducer (even indirectly) triggers another dispatch back into the store mid-reduction, for the identical reason: you can't reach back into a pass that's still in progress.

purity rules always carve out one specific self-directed exception, never a general one

Oracle's "ORA-04091: table is mutating" trigger error

A BEFORE UPDATE trigger may freely modify the row it's currently processing, but querying or updating a DIFFERENT row of the same table mid-statement raises this exact "mutating table" error — touching your own in-flight record is fine, reaching sideways into the same working set is not.

the boundary is never "state," it's always "whose turn is it"
The whole page on a napkin: render is a pure function call, commit mutates the DOM, layout effects run synchronously before paint, passive effects run after, and StrictMode double-invokes all of it in dev to expose impurity and missing cleanup. New: React quietly forgives a component for calling its OWN setter mid-render (and instantly re-runs the pass before paint) — but the same call reaching sideways into a different component's state from inside someone else's render is not forgiven, and logs a warning that becomes an infinite loop if nothing stops it.

1. Three things trigger a render

TriggerDetail
Initial mountcreateRoot(el).render(<App/>) — the very first render
State / reducer updatesetState with a value that differs by Object.is from the current
Parent re-renderA parent rendering re-renders all children by default (unless React.memo bails out)
Context value changeEvery consumer of a changed context re-renders, memo or not
"Render" ≠ "paint". Rendering is React invoking your component function to get JSX. It happens often and is usually cheap. Only the commit phase touches the DOM, and only paints what actually changed. A component can render many times without a single DOM mutation.

2. The exact effect order on every commit

1. render() // your function runs (pure)
2. cleanup prev useLayoutEffect // if deps changed / unmount
3. mutate DOM // commit phase
4. attach refs
5. run useLayoutEffect // SYNC — blocks paint, can read layout
────────── browser paints ──────────
6. cleanup prev useEffect // if deps changed / unmount
7. run useEffect // ASYNC — after paint
useLayoutEffect vs useEffect: useLayoutEffect fires synchronously after DOM mutation but before the browser paints — use it only to read/measure layout and write it back synchronously (e.g. tooltip positioning) to avoid a visible flicker. useEffect fires after paint and is correct for everything else (fetching, subscriptions, logging). Overusing useLayoutEffect blocks painting.

4. StrictMode double-invokes — on purpose

In development, <StrictMode> deliberately runs renders twice and mounts effects twice (mount → unmount → mount). This is a bug detector, not a bug: if your render is impure or your effect lacks cleanup, the doubled run makes the problem obvious immediately rather than in production. Production runs each exactly once.

If something "runs twice" only in dev, it is StrictMode telling you the code is not resilient to being re-run. The fix is almost never to disable StrictMode — it is to make the render pure and give the effect a proper cleanup so mount → unmount → mount is a no-op.
