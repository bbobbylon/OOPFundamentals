Rendering, Commit & Lifecycle

"Rendering" is React calling your function — not painting pixels. Watch the exact order: trigger → render (pure) → commit (DOM) → refs & layout effects (sync) → paint → passive effects. Plus the class lifecycle map and what StrictMode really does.

🔁 What is the React rendering lifecycle — and what does "render" actually mean vs "paint"?

"Rendering" means React calls your component and gets back an element tree — not writing to the DOM, not the user seeing anything. The lifecycle: trigger (mount, setState, context, parent), render (your pure function, possibly called twice in StrictMode), commit (diffs written to the DOM), layout effects (useLayoutEffect, synchronous before paint — measure the DOM here), paint (pixels appear — only now does the user see it), then passive effects (useEffect, async after paint — fetch, subscribe, analytics). StrictMode double-invokes render and effects in dev to surface impure renders and missing cleanups; in production it's zero-overhead.

  • Render ≠ paint — render builds the tree; paint is when pixels (and the user) update.
  • Render must be pure — React may call it twice in StrictMode/Concurrent.
  • useLayoutEffect before paint (measure), useEffect after paint (fetch/subscribe).
  • StrictMode double-invokes in dev — catches impure renders and missing cleanup.

Render → Commit → Paint order

function UserDetail({ userId }: { userId: number }) { // RENDER PHASE — pure, no side effects const [user, setUser] = useState<UserDto | null>(null); console.log('render'); // may run 2x in dev // DOM not touched yet return <div id="user-detail">{user?.name ?? 'Loading…'}</div>; // ↑ React diffs this element tree // against the previous one } // COMMIT PHASE (after render): // React writes to DOM: div.textContent = 'Loading…' // LAYOUT EFFECT (after DOM write, before paint): useLayoutEffect(() => { // DOM is mutated; browser hasn't painted yet const height = document.getElementById('user-detail')?.offsetHeight; }, [user]); // BROWSER PAINT: user sees the UI // PASSIVE EFFECT (after paint): useEffect(() => { fetchUser(userId).then(setUser); }, [userId]);

Class lifecycle → Hooks map

// Class component lifecycle ↔ Hook equivalent componentDidMount() {} // ↔ useEffect(() => {...}, []) // empty deps = on mount componentDidUpdate(prevProps, prevState) {} // ↔ useEffect(() => {...}, [dep]) // specific dep // (runs on mount AND when dep changes) componentWillUnmount() {} // ↔ useEffect(() => { return () => { cleanup }; }, []) getDerivedStateFromProps(props, state) {} // ↔ useMemo or computed value from props getSnapshotBeforeUpdate() {} // ↔ useLayoutEffect (before paint) shouldComponentUpdate() {} // ↔ React.memo (shallow comparison) render() { return <JSX />; } // ↔ return value of function component

Angular lifecycle comparison

React hook → Angular lifecycle equivalent. useEffect(fn, []) → ngOnInit() (runs once after first render/init). useEffect(fn, [dep]) → ngOnChanges(changes) + input changes (runs when dep changes). useEffect(() => { return cleanup; }, []) → ngOnDestroy() (cleanup on unmount). useLayoutEffect → ngAfterViewInit() (after view is initialized). useEffect(fn) (no deps, every render) → no Angular equivalent — Angular doesn't call code after every CD cycle by default. React StrictMode double-invocation → Angular's dev mode performs an extra CD check (ExpressionChangedAfterItHasBeenCheckedError) — both catch imperative bugs during development.

CIAM React app: A user-detail page renders a skeleton (commit→paint), useEffect fetches /api/users/{id}, then setUser(data) triggers a second render that paints the real data. An auth check in useEffect(() => { if (!token) navigate('/login') }, [token]) runs after paint, so the page flashes — better to gate it in the router loader before render. A token-refresh interval (setInterval(refreshToken, 5*60*1000)) must return a cleanup that clearIntervals on unmount — the same memory-leak guard as Angular's ngOnDestroy() { this.subscription.unsubscribe() }.

1. Three things trigger a render

TriggerDetail
Initial mountcreateRoot(el).render(<App/>) — the very first render
State / reducer updatesetState with a value that differs by Object.is from the current
Parent re-renderA parent rendering re-renders all children by default (unless React.memo bails out)
Context value changeEvery consumer of a changed context re-renders, memo or not
"Render" ≠ "paint". Rendering is React invoking your component function to get JSX. It happens often and is usually cheap. Only the commit phase touches the DOM, and only paints what actually changed. A component can render many times without a single DOM mutation.

2. The exact effect order on every commit

1. render() // your function runs (pure)
2. cleanup prev useLayoutEffect // if deps changed / unmount
3. mutate DOM // commit phase
4. attach refs
5. run useLayoutEffect // SYNC — blocks paint, can read layout
────────── browser paints ──────────
6. cleanup prev useEffect // if deps changed / unmount
7. run useEffect // ASYNC — after paint
useLayoutEffect vs useEffect: useLayoutEffect fires synchronously after DOM mutation but before the browser paints — use it only to read/measure layout and write it back synchronously (e.g. tooltip positioning) to avoid a visible flicker. useEffect fires after paint and is correct for everything else (fetching, subscriptions, logging). Overusing useLayoutEffect blocks painting.

4. StrictMode double-invokes — on purpose

In development, <StrictMode> deliberately runs renders twice and mounts effects twice (mount → unmount → mount). This is a bug detector, not a bug: if your render is impure or your effect lacks cleanup, the doubled run makes the problem obvious immediately rather than in production. Production runs each exactly once.

If something "runs twice" only in dev, it is StrictMode telling you the code is not resilient to being re-run. The fix is almost never to disable StrictMode — it is to make the render pure and give the effect a proper cleanup so mount → unmount → mount is a no-op.
