1. Three things trigger a render

TriggerDetail
Initial mountcreateRoot(el).render(<App/>) — the very first render
State / reducer updatesetState with a value that differs by Object.is from the current
Parent re-renderA parent rendering re-renders all children by default (unless React.memo bails out)
Context value changeEvery consumer of a changed context re-renders, memo or not
"Render" ≠ "paint". Rendering is React invoking your component function to get JSX. It happens often and is usually cheap. Only the commit phase touches the DOM, and only paints what actually changed. A component can render many times without a single DOM mutation.

2. The exact effect order on every commit

1. render() // your function runs (pure)
2. cleanup prev useLayoutEffect // if deps changed / unmount
3. mutate DOM // commit phase
4. attach refs
5. run useLayoutEffect // SYNC — blocks paint, can read layout
────────── browser paints ──────────
6. cleanup prev useEffect // if deps changed / unmount
7. run useEffect // ASYNC — after paint
useLayoutEffect vs useEffect: useLayoutEffect fires synchronously after DOM mutation but before the browser paints — use it only to read/measure layout and write it back synchronously (e.g. tooltip positioning) to avoid a visible flicker. useEffect fires after paint and is correct for everything else (fetching, subscriptions, logging). Overusing useLayoutEffect blocks painting.

4. StrictMode double-invokes — on purpose

In development, <StrictMode> deliberately runs renders twice and mounts effects twice (mount → unmount → mount). This is a bug detector, not a bug: if your render is impure or your effect lacks cleanup, the doubled run makes the problem obvious immediately rather than in production. Production runs each exactly once.

If something "runs twice" only in dev, it is StrictMode telling you the code is not resilient to being re-run. The fix is almost never to disable StrictMode — it is to make the render pure and give the effect a proper cleanup so mount → unmount → mount is a no-op.
