Change Detection & Lifecycle

Change detection is how Angular keeps the DOM in sync with your component data. Done well, it's invisible. Done poorly, your app gets slow. Understanding it unlocks OnPush, signals, and "why is this re-rendering 800 times?"

The 30-second model

After ANY async event (click, HTTP response, timer, etc) Angular walks the component tree top-down and checks every binding: "is the value I rendered last time still the same?" If not, update the DOM. That's it. The rest is optimization. 

// Roughly what Angular does after every async event:
function tick(component) {
  for (const binding of component.bindings) {
    const newValue = evaluate(binding.expression);
    if (newValue !== binding.lastValue) {
      updateDOM(binding, newValue);
      binding.lastValue = newValue;
    }
  }
  for (const child of component.children) tick(child);   // recurse down
}

What triggers a check? — Zone.js, the magic glue

Zone.js is a library that monkey-patches every async browser API — setTimeout, addEventListener, Promise.then, fetch, etc. After any of them finishes, Angular's Zone calls tick() automatically. That's why you almost never call change detection manually.

Async sourceTriggers change detection?
DOM event (click, input, etc)✅ Yes
setTimeout / setInterval✅ Yes
Promise.then / async/await✅ Yes
HttpClient / fetch (via Zone-patched XHR/fetch)✅ Yes
RxJS Observables fed from any of the above✅ Yes (transitively)
WebSocket message (not Zone-patched)❌ No — you must call NgZone.run()
Third-party libs that use their own async (rare)❌ Maybe not — depends on the lib

Symptom of a missed trigger: "I update a value but the UI doesn't refresh until I click somewhere else." Fix: wrap the callback in this.ngZone.run(() => { ... }) or migrate that piece to signals.

Live demo — Default vs OnPush

Click tick (any async event). The 🟡 highlight = component was checked this cycle. Notice in Default mode everything is checked. In OnPush mode, only components whose inputs changed get checked — the rest are skipped (dashed). Same UI, way less work.

Components marked ⚡ use OnPush. In OnPush mode, a check only happens when: an @Input() reference changes, an event in its template fires, an async pipe emits, or you call markForCheck().

OnPush — the optimization that scales

Default strategy

@Component({
  selector: 'app-foo',
  template: `...`
  // changeDetection: ChangeDetectionStrategy.Default
})
export class FooComponent {}

After ANY async event, this component & all its descendants are checked. Safe. Slow at scale.

OnPush strategy

@Component({
  selector: 'app-foo',
  template: `...`,
  changeDetection: ChangeDetectionStrategy.OnPush
})
export class FooComponent {}

Skipped UNLESS: (a) input reference changes, (b) event in this template fires, (c) async pipe emits, (d) cdr.markForCheck().

The catch: if you mutate an Input object instead of replacing it, OnPush doesn't notice. Treat Inputs as immutable: this.users = [...this.users, newUser], NEVER this.users.push(newUser).

How to make OnPush re-check on demand

export class MyComponent {
  private cdr = inject(ChangeDetectorRef);

  onSomeNonZoneEvent() {
    // 1. Schedule a check next tick (the safe default)
    this.cdr.markForCheck();

    // 2. Detect changes RIGHT NOW (synchronous, expensive — rarely needed)
    this.cdr.detectChanges();

    // 3. Detach from CD entirely (for very high-frequency components)
    this.cdr.detach();
    this.cdr.reattach();   // turn it back on
  }
}

99% of the time, markForCheck() is what you want. detectChanges() can fire mid-cycle and trigger ExpressionChangedAfterItHasBeenCheckedError — see below.

The dreaded ExpressionChangedAfterItHasBeenCheckedError

Dev-mode only. Angular runs change detection twice in dev mode to catch a bug: a binding's value changed DURING the check itself. That means whatever the user sees might be one render behind. 

// ❌ Triggers the error — ngAfterViewInit modifies a value that was just rendered
@Component({ template: `{{ message }}` })
export class Buggy implements AfterViewInit {
  message = 'hello';
  ngAfterViewInit() {
    this.message = 'goodbye';       // CD already ran; this changes the rendered value
  }
}

// ✅ Fix 1: defer to next tick
ngAfterViewInit() {
  setTimeout(() => this.message = 'goodbye');
}

// ✅ Fix 2: signal/queueMicrotask/Promise.resolve().then(...)
// ✅ Fix 3: rewrite so the change happens BEFORE the view is checked (ngOnInit)

constructor
DI injects dependencies. Don't put logic here — too early.
created
ngOnChanges
Called when @Input values change. Receives a SimpleChanges object. Fires BEFORE ngOnInit on first render too.
on input change
ngOnInit
Once, after the first ngOnChanges. The right place for initialization: subscribe, fetch data, set up forms.
once
ngDoCheck
Every CD cycle. For custom change detection. Almost never needed — if you reach for this, consider OnPush instead.
every CD
ngAfterContentInit
After projected <ng-content> is initialized. Once.
once
ngAfterContentChecked
After every CD of projected content. Same caveats as DoCheck.
every CD
ngAfterViewInit
After this component's view (and its children's views) is initialized. Once. The right place for @ViewChild access and DOM measurements.
once
ngAfterViewChecked
After every CD of the view. Avoid heavy work — fires constantly.
every CD
ngOnDestroy
Cleanup. Unsubscribe Observables, clear timers, remove DOM listeners. Or use DestroyRef / takeUntilDestroyed().
once, at end

In practice you'll use 3: ngOnInit (setup), ngAfterViewInit (DOM access), ngOnDestroy (cleanup). The rest are escape hatches you'll rarely need.

The modern hook — DestroyRef (Angular 16+)

// ❌ Old way — implement OnDestroy
export class MyComponent implements OnDestroy {
  private sub = interval(1000).subscribe(...);
  ngOnDestroy() { this.sub.unsubscribe(); }
}

// ✅ New way — inject DestroyRef anywhere, no boilerplate hook
export class MyComponent {
  private destroyRef = inject(DestroyRef);
  sub = interval(1000).pipe(
    takeUntilDestroyed(this.destroyRef)
  ).subscribe(...);

  // or as a callback
  constructor() {
    this.destroyRef.onDestroy(() => console.log('gone'));
  }
}

Performance recipes

1. OnPush by default

New components → changeDetection: ChangeDetectionStrategy.OnPush. Massive savings, no behavioral change as long as you treat Inputs as immutable.

2. Use the async pipe

| async auto-calls markForCheck() on emission — your component re-renders without ANY zone trigger. Plays perfectly with OnPush.

3. trackBy on *ngFor

Without it, every array change rebuilds the WHOLE list of DOM nodes. With it, Angular reuses unchanged rows. 10× faster on big lists.

4. Pure pipes over methods

{{ items | sortByName }} caches the result. {{ sortByName(items) }} re-runs every CD cycle — that's potentially thousands of times per second.

5. runOutsideAngular for high-freq work

Animations, scroll handlers, drag-and-drop — wrap in ngZone.runOutsideAngular(...) so they don't trigger CD on every frame. Re-enter with ngZone.run(...) when you actually need to update state.

6. Go zoneless — signals

The endgame. Replace Zone.js entirely with fine-grained reactivity. Only the bindings that depend on a changed signal re-evaluate. Covered in the Signals visualizer.

Mental model

CD = check every binding

Angular doesn't magically know what changed. It re-evaluates every {{ x }}, [prop] and compares to last time. OnPush just skips whole subtrees.

Zone.js = the trigger

Any browser async event → Zone notifies Angular → CD runs. Without Zone, you'd be manually calling tick() all over the place (which is exactly what signals enable).

Immutability unlocks OnPush

OnPush checks Input references with ===. Mutating the same object/array = same reference = no check. Always replace, never mutate.

Lifecycle = phases of the same loop

Create → check → check → ... → destroy. The "every CD" hooks fire on every check; the "once" hooks fire at the start & end. Use the once hooks for setup & teardown.
