Change Detection & Lifecycle — Comprehensive Reference

How Angular knows what to re-render — Zone.js's monkey-patching, the dirty-check tree walk, OnPush's escape hatches, signals' fine-grained graph, and zoneless mode. The single concept that ties the whole framework together.

🔄 What is change detection? Why does Angular need it at all?

Your TypeScript class doesn't "know" the template exists. Set this.user.name = 'Alice' and nothing updates the DOM — the browser only re-renders what it's told to. Change detection is Angular's mechanism for asking "did anything change?" and re-rendering only what did. Angular 1.x re-checked every binding on every event (too slow); modern Angular has two strategies — the legacy Zone.js tree-walk and the modern signals approach that updates only the components which read a changed signal.

  • A change has to be detected — JS mutations don't notify the DOM, so Angular re-evaluates bindings and patches what differs.
  • Zone.js (default): patches async APIs; after any event it dirty-checks the whole component tree top-down. Automatic but broad.
  • OnPush: a component is skipped unless an @Input reference changes, an event fires in it, an async pipe emits, or markForCheck() runs.
  • Signals: reading user() records the dependency; user.set(x) updates exactly those views — no tree walk.
  • Zoneless (Angular 18+) drops Zone.js entirely — smaller bundle, no zone overhead; signals drive every update.

Default (Zone.js)

Zone.js patches setTimeout, promises, events, XHR. When one completes, Angular checks every component top-down — a "tree walk." Automatic, but one click can trigger hundreds of checks in a large app.

OnPush strategy

changeDetection: ChangeDetectionStrategy.OnPush skips a component unless an @Input reference changes, an event fires inside it, an async pipe emits, or markForCheck() is called. Most production components should be OnPush.

Signals (Angular 16+)

A template that reads user() registers that dependency. user.set(v) updates only the views that read user — no tree walk. With zoneless mode (18+), Zone.js isn't even loaded.

In CIAM:a user list polls every 5s. Without OnPush, every tick checks every component (nav, sidebar, modals, forms). With OnPush + signals (users.set(newList)), Angular re-renders only the table — in a ~300-component app, CD time per tick often drops from ~50ms to ~3ms.

The problem

You pushed a row onto the array. The table did not move.

Nothing threw, nothing is broken, and the new user really is in the array

You put ChangeDetectionStrategy.OnPush on the user table because the profiler told you to, and it worked — the app got fast. Then you added a row with this.users.push(newUser) and the table ignored you. No error. No warning. Log the array and the user is sitting right there. Reload and the row appears. So the data is fine and the template is fine, which leaves the one thing nobody thought to check: Angular never saw a change, because from where Angular stands, nothing changed.

The bug is not in your component. It is in the assumption that Angular is watching your objects.

Angular does not observe your data. It compares snapshots. Every binding you write is a value Angular stored last time and will compare against next time. That one sentence explains OnPush, ExpressionChangedAfterItHasBeenChecked, why push() is invisible, and why signals are a different thing rather than a faster version of the same thing — a signal tells Angular, so there is nothing left to compare.
Think of Zone.js as a smoke alarm, not a security camera. It can tell you something happened somewhere in the building. It cannot tell you which room, or what. So the only safe response is to walk every room and look. A signal is a camera in one room that calls you by name — which is why signals don't need a tree walk at all.

The mechanism

One click. Three hundred components asked. One of them had an answer.

  1. You click a button. Zone.js monkey-patched addEventListener at startup, so its wrapper is already around your handlera patch, not magic
  2. Your handler runs and finishes. Zone.js knows only that it finished — never what it touchedthe whole reason a tree walk exists
  3. Zone fires onMicrotaskEmpty, and Angular calls ApplicationRef.tick()the real entry point
  4. tick() walks the component tree from the root top-down, in declaration order, re-evaluating every binding and comparing it to the value stored last timethis is "dirty checking"
  5. Different → patch that one piece of DOM. Same → move on. An OnPush component is skipped outright unless something marked it dirtywhere your table went missing
  6. In dev mode Angular immediately runs the entire walk a second time and throws if any binding disagrees with the first passExpressionChangedAfterItHasBeenChecked lives here

Step 2 is the lesson, and everything else follows from it. Zone.js is not a change detector — it is a something-happened detector. Because it cannot say what changed, Angular's only safe move is to check everything. That single missing piece of information is why the default strategy costs what it costs, why OnPush exists to opt out of it, and why signals delete the problem instead of optimising it.

Every box gets asked; one had an answer. Swap the click for users.set(next) under signals and this fan collapses to a single arrow — the views that read users registered themselves, so there is nobody else left to ask.

A component is OnPush. Its @Input() users is bound to an array owned by the parent. The parent's click handler runs this.users.push(newUser). What does the child render?

A click does mark the component it fired in, and its ancestors, as dirty — that part is real. But it does not mark the OnPush child. When the walk reaches that child the deciding question is whether its inputs changed, and that test is Object.is(oldUsers, newUsers) on the array reference. Same object, so the child is skipped with the longer array sitting right there, unread.

Exactly — and notice what Angular never did: look inside the array. A deep compare of every input on every tick is precisely the cost OnPush exists to avoid, so it buys its speed with a reference test and trusts you to hand it a new reference. this.users = [...this.users, newUser] fixes it in one line.

There is no deferred queue. OnPush is not "later", it is "not at all" — the component is skipped on this tick and every tick after, until something marks it dirty: a new input reference, an event inside it, an async pipe emission, or an explicit markForCheck(). Absent one of those, the stale row survives indefinitely.

Where you've seen this before

Three frameworks, one idea: keep a copy, compare it later.

Hibernate's dirty checking — same trick, same words

When Spring Data loads an entity, Hibernate keeps a snapshot of every field. At flush it compares the live object against that snapshot and issues UPDATE only for what differs — which is why you never call save() on a managed entity and it persists anyway. Identical mechanism to Angular's binding compare, and it has the identical blind spot: mutate something the snapshot isn't tracking and the write silently never happens.

snapshot + compare = "dirty"

React's memo, and why that ecosystem chants "immutable"

React.memo skips a re-render when props are shallow-equal — the same reference test OnPush runs, under a different name. It is the entire reason React culture insists on [...arr, x] over arr.push(x). Same rule, different framework, and the exact same bug on the day you forget it.

OnPush ≈ React.memo

Your CIAM admin shell, polling every 5 seconds

A 300-component admin console polling a user list every 5s: on the default strategy that re-checks every binding in the app twelve times a minute — nav, sidebar, every open modal — to re-render one table that usually hasn't changed. OnPush plus users.set(next) narrows each tick to the table alone. That is the whole performance story, and it is a two-line change.

~50ms → ~3ms per tick
Questions from the back row

If signals are better, why is Zone.js still the default?

Because Zone.js asks nothing of you. Every this.x = y in a decade of existing Angular code keeps working, which is exactly what a framework with that much shipped code behind it has to guarantee. Zoneless is opt-in for the mirror-image reason: going zoneless means any state not behind a signal, an async pipe or an explicit markForCheck() stops updating — and it fails silently, the same way your pushed row did. New app: go zoneless from day one. Existing app: migrate component by component, OnPush first.

What actually is ExpressionChangedAfterItHasBeenChecked?

Step 6 above, catching you in the act. Angular checks once, then in dev mode checks again and compares the two passes. If a binding disagrees, something in your template changed state while being read — most often a getter that builds a new object on every call (get items() { return [...this.raw] } hands back a different array each time, so the two passes can never agree), or a child writing to a parent field inside ngAfterViewInit. It is dev-only, and it is telling you the truth: in production that value would simply have rendered one tick stale, with no warning at all.

Should every component just be OnPush, then?

Close to it — treat it as the default for new code. The price is that you have to be honest about mutation: new references in, or signals all the way down. Where it bites is a component reading a mutable service field directly; under OnPush that has to become a signal or an observable piped through async, because you have removed the only mechanism that was covering for it.

Why change detection exists at all

JavaScript is single-threaded. Your component's state changes — a property got a new value, an HTTP response came back, a button was clicked. Angular has no way to know unless someone tells it. "Change detection" is Angular's answer: a tree walk that compares every bound template expression to its previous value, and if anything changed, updates the DOM.

Three things to internalize first:

  • CD is not magic. It's a top-down walk that re-runs every binding in every component.
  • CD doesn't detect changes — it propagates them. Something else (Zone.js, signals, or a manual call) triggers a "check"; CD just runs the comparison.
  • Default CD checks everything. OnPush and signals are tools to check less.
The mental model: "Angular runs a check. The check walks the tree. Each component compares its current bound values to last cycle's snapshot. Differences become DOM updates." Everything in this file is a refinement of that one sentence.

The dirty-check algorithm

1
A trigger fires
Zone catches a click / timer / HTTP response / promise resolution, or a signal that the template reads is set, or someone calls cd.detectChanges() manually.
2
Angular schedules a tick
ApplicationRef.tick() is the actual top-level call. It walks every root view.
3
Tree walk, top-down, depth-first
For each component: re-run all template expressions, compare to the previous value, mark bindings that changed.
4
Apply DOM updates
For every changed binding, update the corresponding DOM property / attribute / text node.
5
In dev mode: assert stability
Re-run the check immediately. If any value changed AGAIN between the two passes → throw ExpressionChangedAfterItHasBeenCheckedError. Production skips this assertion.

The "comparison" itself is === (referential equality). That's why [items]="this.items.slice()" creates a new array each tick and floods OnPush children with updates — same content, different reference.

Zone.js — the monkey-patch story

Angular needs to know when something might have changed. There's no language-level "after async operation" hook in JavaScript. So Angular ships zone.js: a library that monkey-patches every async API in the browser so it can run a callback before and after them.

// Before Angular boots, zone.js does (roughly):
const originalSetTimeout = window.setTimeout;
window.setTimeout = function(fn, ms, ...args) {
  return originalSetTimeout(() => {
    // 1. tell the current zone "task starting"
    const result = fn(...args);
    // 2. tell the zone "task done" — this is what kicks off CD
    return result;
  }, ms);
};
// ...same for addEventListener, Promise.then, XMLHttpRequest, fetch, etc.

Angular installs a custom zone — NgZone — at bootstrap. Every time a patched async API completes, NgZone's onMicrotaskEmpty fires, which triggers ApplicationRef.tick().

This is why Angular feels "automatic": not because the framework is smart, but because zone.js has wrapped every browser async API. Click a button → tick. Promise resolves → tick. XHR returns → tick. You never write the trigger; zone does it for you.

tick() — the actual entry point

Every change detection cycle goes through ApplicationRef.tick(). Knowing this is useful for debugging — if you set a breakpoint there, you can see exactly what triggered a run.

// Roughly what happens, ignoring detail:
class ApplicationRef {
  tick() {
    for (const view of this._views) {
      view.detectChanges();   // recursive walk down THIS view's tree
    }
  }
}

// Zone tells ApplicationRef "tick now" via:
zone.onMicrotaskEmpty.subscribe(() => appRef.tick());

"Microtask empty" means the JavaScript event loop drained — every queued promise resolved, every event handler ran. That's why CD runs once per logical operation, not once per state change. A click handler that updates 5 fields = 1 tick, not 5.

Default strategy

Under ChangeDetectionStrategy.Default — the unchanged default — every tick walks every component in the tree, top-down. Doesn't matter where in the tree the change actually happened.

@Component({
  selector: 'app-thing',
  // implicit: changeDetection: ChangeDetectionStrategy.Default
  template: `{{ user.name }}`,
})
export class ThingComponent { ... }

This is safe (no scenario where the UI is "stale") but expensive (every component re-checks every tick).

For small apps it's fine. For lists of 1000+ rows or trees 5+ levels deep, you'll feel it — every keystroke checks the whole tree.

OnPush strategy

ChangeDetectionStrategy.OnPush tells Angular: "skip this component during the tree walk unless something explicitly marked it dirty."

@Component({
  selector: 'app-thing',
  changeDetection: ChangeDetectionStrategy.OnPush,
  template: `{{ user.name }}`,
})
export class ThingComponent { ... }

What marks an OnPush component dirty?

  1. An @Input() received a new reference (=== changed).
  2. A DOM event handler defined in this component's template fired.
  3. An async pipe in the template emitted a new value.
  4. A signal that the template reads got a new value (v16+).
  5. Manual: cdRef.markForCheck() or cdRef.detectChanges().
The OnPush trap: If you mutate an existing object (e.g. this.user.name = 'X') instead of replacing it, the reference is the same — OnPush will NOT see the change. Use immutable updates: this.user = { ...this.user, name: 'X' }.
// ❌ Mutating — OnPush doesn't notice
this.user.name = 'Bobby';

// ✅ Replacing — OnPush sees a new reference
this.user = { ...this.user, name: 'Bobby' };

ChangeDetectorRef — the manual API

Inject ChangeDetectorRef when you need to control CD manually. Four methods worth knowing:

MethodBehaviorUse when
markForCheck()Mark this view AND every ancestor as dirty. Next tick will check them.OnPush component whose internal state changed (not via Input/event/async)
detectChanges()Run CD on THIS view immediately (and its children).Sync update right now — usually inside a third-party callback that ran outside zone
detach()Remove this view from the CD tree entirely.Heavy components that you'll re-check manually on a timer
reattach()Put it back.Pair with detach
 
private cdr = inject(ChangeDetectorRef);

// Heavy widget — manually CD once per second
ngOnInit() {
  this.cdr.detach();
  interval(1000).pipe(takeUntilDestroyed()).subscribe(() => {
    this.cdr.detectChanges();
  });
}
markForCheck vs detectChanges: markForCheck says "please consider me dirty next tick" — no work happens now. detectChanges does the work right now, only on this view. Use markForCheck 95% of the time.

Signals — fine-grained reactivity (the new model)

Signals (v16+) change the model entirely. Instead of "check everything periodically and see what changed," each signal tracks which views read it during rendering. When you call signal.set(...), only those specific views are marked dirty.

import { signal, computed, effect } from '@angular/core';

export class CounterComponent {
  count = signal(0);
  doubled = computed(() => this.count() * 2);

  increment() {
    this.count.update(c => c + 1);
    // → only views that called this.count() during rendering are marked dirty
    // → no tree walk, no top-down check, no Zone needed
  }
}

Why this is a big deal

  • No tree walk. Update one signal → exactly the views that read it get checked.
  • No equality bugs. Signals only fire when the value actually changes (via === by default, or a custom equality function).
  • Composes by computed. Derived values are cached and lazy — they only re-evaluate when their dependencies actually changed.
  • OnPush-friendly by default. A signal in a template is more powerful than OnPush — and the two layer together perfectly.

Zoneless mode (stable v20.2, default in v21+)

If your whole app is on signals, you can drop zone.js entirely:

// main.ts
import { bootstrapApplication } from '@angular/platform-browser';
import { provideZonelessChangeDetection } from '@angular/core';

bootstrapApplication(AppComponent, {
  providers: [
    provideZonelessChangeDetection()
  ]
}).catch(console.error);

afterRender / afterNextRender (v16+) — measure the DOM safely

Need to read element sizes, scroll positions, focus an element, integrate a third-party canvas library? Doing that inside ngAfterViewInit often clashes with SSR (no DOM) and with the next CD cycle.

The fix:

import { afterNextRender, afterRender } from '@angular/core';

constructor() {
  // Runs ONCE, after the next render, browser-only
  afterNextRender(() => {
    const rect = this.canvasRef.nativeElement.getBoundingClientRect();
    this.chart = new Chart(this.canvasRef.nativeElement, ...);
  });

  // Runs after EVERY render — for ongoing measurements
  afterRender(() => {
    this.height.set(this.containerRef.nativeElement.offsetHeight);
  });
}

Both skip during SSR (no DOM exists). They're the right place for any code that touches window/document.

DestroyRef (v16+) — composable destroy

Before v16, "run X when this component dies" required implementing OnDestroy and pasting code into ngOnDestroy. Now:

private destroyRef = inject(DestroyRef);

someMethod() {
  const id = setInterval(...);
  this.destroyRef.onDestroy(() => clearInterval(id));
}

Multiple onDestroy callbacks compose. You can call this from a service, a directive, or anywhere with access to an injection context. No more single-method ngOnDestroy shoehorning everything together.

ExpressionChangedAfterItHasBeenCheckedError — the famous one

This dev-mode-only error is Angular telling you: "I checked your template, then I checked it again, and a value changed between the two passes. That means CD won't reach a stable state."

Common cause: updating state from a lifecycle hook that fires AFTER CD:

// ❌ ngAfterViewInit fires AFTER CD ran once. If you set state here,
// the next check sees a different value than the first.
ngAfterViewInit() {
  this.width = this.elRef.nativeElement.offsetWidth;   // → ECAHCB
}

// ✅ Fix 1 — defer to the next microtask
ngAfterViewInit() {
  queueMicrotask(() => this.width = this.elRef.nativeElement.offsetWidth);
}

// ✅ Fix 2 — afterNextRender (the modern way, also SSR-safe)
constructor() {
  afterNextRender(() => {
    this.width = this.elRef.nativeElement.offsetWidth;
  });
}

// ✅ Fix 3 — signals decouple reads from writes
width = signal(0);
constructor() {
  afterNextRender(() => this.width.set(this.elRef.nativeElement.offsetWidth));
}
The rule: never update bindings during or after CD has run for that cycle. Use afterNextRender for DOM measurement, signals for state, or schedule the update to the next tick.

runOutsideAngular — escape the loop

The inverse problem: you have CPU-hot code (mouse-move handler, scroll listener, requestAnimationFrame loop) that's triggering CD on every event. The fix is to run that code outside the Angular zone, so it doesn't trigger ticks. Then re-enter zone only when you have a meaningful update.

private zone = inject(NgZone);

ngOnInit() {
  this.zone.runOutsideAngular(() => {
    window.addEventListener('mousemove', e => {
      this.updateCanvas(e);   // 60fps repaints — NO CD per move

      if (somethingMeaningfulHappened(e)) {
        this.zone.run(() => this.message = 'updated');   // re-enter, trigger CD
      }
    });
  });
}

Classic use case: drag-and-drop libraries, charting libraries, requestAnimationFrame physics loops. Without runOutsideAngular, a 60fps loop = 60 ticks per second.

Performance guidelines

Default for the top, OnPush for hot leaves

You don't need OnPush everywhere. Use it on components that render large lists, deeply nested trees, or expensive bindings.

Use trackBy in @for / *ngFor

Without it, every array change re-creates every DOM node. With it, Angular reuses nodes whose key hasn't changed.

Use the async pipe

It marks OnPush components dirty on every emission AND auto-unsubscribes. Free correctness.

Cache template function calls

{{ heavyCompute() }} in a Default template runs every tick. Compute once into a field, or use a pure pipe.

Prefer signals for derived state

computed() only re-runs when its sources actually change — better than getter functions called from the template.

Use detach + manual detectChanges for animations

A component running a 60fps canvas animation can detach from CD entirely and re-check only on user events.

runOutsideAngular for event firehoses

mousemove, scroll, requestAnimationFrame. Re-enter only when something user-visible needs to change.

Profile before you OnPush-everything

Use Chrome devtools' performance tab + Angular DevTools' profiler. Most apps are fast enough on Default.

Mental model — final word

CD propagates, doesn't detect

Something else (Zone, signal, manual call) tells Angular to check. CD just walks the tree comparing old vs new.

Zone is a giant monkey-patch

Every async API in the browser is wrapped. That's why ticks happen "automatically" — but also why CD runs more than you think.

OnPush trades safety for speed

Skip checks unless explicitly marked dirty. Win: 10–100× fewer comparisons. Cost: you must replace, not mutate.

Signals are the destination

Fine-grained subscriptions. Only the views that read a signal get checked when it changes. No tree walk needed.

Lifecycle is for hookup, not state

Constructor → DI. ngOnInit → first fetch. afterViewInit → query @ViewChild. ngOnDestroy → cleanup. Anything else, prefer signals/effects.

If in doubt, profile

Use Angular DevTools' profiler. The actual hotspot is rarely where you'd guess. Don't optimize blind.

🌱 New here? It's how Angular keeps the screen matching your data.

You change a variable in your class — how does the screen update? That's change detection. After anything that could change data (a click, an HTTP response, a timer), Angular walks down the component tree, re-checks each binding, and updates the DOM wherever a value differs from last time. By default it checks everything on every such event, which is why "it just updates" feels automatic. You rarely think about it — until a big app gets slow, and then knowing how it works (and how to make it check less) is the difference.

🧠 Expert corner — Zone.js, OnPush, and the zoneless future

  • What triggers a check? By default, Zone.js monkey-patches async APIs (events, setTimeout, XHR/fetch, promises) and tells Angular "something happened, run change detection" — then it checks the whole tree top-down.
  • OnPush is the big lever. ChangeDetectionStrategy.OnPush tells Angular to skip a component (and its subtree) unless: an @Input/input() reference changed, an event fired inside it, an async pipe / bound signal emitted, or you call markForCheck(). On a deep tree this turns "check everything" into "check what changed."
  • OnPush rewards immutability. It compares input references, so mutating an array in place (arr.push()) won't be seen — create a new reference ([...arr, x]).
  • Signals make it fine-grained. A signal knows exactly which views read it, so it can mark just those dirty — enabling zoneless change detection (no Zone.js at all): the view updates because a signal it read changed, not because an async API was patched.
  • Manual control: ChangeDetectorRef — detectChanges(), markForCheck(), detach()/reattach() for hot paths.
  • CIAM tie-in. An OnPush <user-menu> that only re-renders when the auth signal changes — not on every unrelated event. Deeper: CD Internals · Zoneless.
