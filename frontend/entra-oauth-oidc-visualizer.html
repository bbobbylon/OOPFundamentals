OAuth2 & OIDC Flows

How your Angular app and Spring Boot API authenticate users through Microsoft Entra ID.

🔐 What is OAuth2 + OIDC with Entra ID — and how does Auth Code + PKCE get your Angular app a token safely?

Entra ID is the Authorization Server + OpenID Provider — it runs both OAuth2 (grant access) and OIDC (authenticate + profile). Your Angular SPA uses Authorization Code + PKCE (mandatory for public clients that can't keep a secret): Angular makes a code_verifier and sends its SHA256 code_challenge to /authorize, the user logs in at Entra (your app never sees the password), Entra returns a one-use code, and Angular exchanges code + verifier at /token — Entra checks SHA256(verifier) == challenge so a stolen code is useless. Out come the access, ID, and refresh tokens. MSAL (@azure/msal-angular) runs the whole flow, stores tokens, silently renews, and attaches Bearer headers; endpoints are tenant-specific under login.microsoftonline.com/{tid}.

  • Entra = OAuth2 + OIDC server — authorizes and authenticates.
  • Auth Code + PKCE — verifier/challenge makes a stolen code useless; no browser secret.
  • Three tokens — access (APIs), ID (profile), refresh (silent renew).
  • MSAL runs it — tenant-specific endpoints under login.microsoftonline.com/{tid}.

In CIAM / Your Job: The Entra flow is structurally identical to Ping — same Auth Code + PKCE, same JWT output — but config differs: tenant-specific endpoints (login.microsoftonline.com/{tid}), MSAL instead of angular-oauth2-oidc, and an aud of your API's api://{clientId}. The most common Spring bug: an issuer-uri without the /v2.0 suffix — v1.0 and v2.0 tokens have different issuers, so always use v2.0.

One Entra login at /token hands your app three tokens at once. Before you look at the picture below: which one is Spring's resource server actually supposed to see in the Bearer header — and if the interceptor grabbed a different one by mistake, would anything even notice?

So: the picture answers the Brain Power question — Spring's resource server should only ever see the access token, because its aud is api://your-api-id and its scp says what was granted. But "should" is doing the work in that sentence. The ID token is signed by the same tenant, published at the same JWKS, and carries the same iss — a resource server wired with nothing but issuer-uri checks exactly those three things, finds them all genuine, and waves the ID token through as if it were a credential. It is not a broken token. It is the right token in the wrong slot, and a verifier that never read the address on the envelope.

  1. Angular sends a code_challenge and a nonce to /authorize, asking for the API by its full api://<id>/read:users scope namethe scope decides the audience
  2. You authenticate at Entra. Your app never sees the password, and Entra hands back a one-time codethe redirect half
  3. Angular exchanges code + verifier at /token; Entra checks SHA256(verifier) == challenge, so a stolen code alone is worthlesswhat PKCE buys you
  4. Three tokens come back in the same response — the ID token's aud is your client id, the access token's aud is the APIthe fork in the road
  5. The interceptor attaches one of them as the Bearer header — and only an audiences check on the API decides whether the wrong pick even gets noticedwhere it breaks, if it breaks

Step 5 is the one to watch — everything before it mints two perfectly valid tokens, and it is the only step where a missing line of Spring config decides whether the wrong one gets through.

and here's the part nobody puts in the onboarding doc: in CIAM this isn't an Entra quirk — Ping hands your app the exact same two JWTs, so the same missing audiences line is the same hole at work, no matter whose logo is on the login screen.

An Angular app wires its interceptor to attach the ID token as the Bearer header, because it carries the user's name and email. The Spring resource server is configured with spring.security.oauth2.resourceserver.jwt.issuer-uri pointing at the same Entra tenant — and nothing else. What happens to the request?

Backwards: Spring cannot derive an expected audience from the issuer, because one tenant issues tokens for many different APIs, all sharing the same iss. Only you know which audience this particular service should answer to — which is exactly why audiences has to be configuration, not something the framework infers.

Correct, and this is the uncomfortable part: the request succeeds, so the mistake ships silently. Both tokens are ordinary JWTs signed by the same tenant keys with the same iss; the default validators on issuer-uri cover timestamps and issuer only. Set spring.security.oauth2.resourceserver.jwt.audiences to your API's identifier and both the ID token, and any access token minted for a different API in the same tenant, stop working.

They are the same format. An Entra v2.0 ID token is a JWT with a header, claims, and an RS256 signature — structurally identical to an access token for a custom API, which is exactly why this substitution goes unnoticed. What differs is the meaning of the claims inside: aud points at the client instead of the API, and there is no scp at all.

Think of the ID token as a wristband at the door and the access token as a drink ticket. The wristband proves the bouncer checked you — show it to the bartender and they should say "that's lovely, that isn't a drink ticket." A bar where the wristband buys drinks hasn't been generous; it has stopped counting.

1 — OAuth2 vs OpenID Connect (OIDC)

OAuth2 — Authorization

Question: "Can app X access resource Y on behalf of user Z?"

Returns an access token — a credential for calling APIs.

Example: "Grant my app permission to read your calendar."

OAuth2 alone does NOT tell you who the user is (just what they can access).

OIDC — Authentication (built on OAuth2)

Question: "Who is this user?"

Adds an ID token (JWT) to the OAuth2 response — contains user identity claims.

Example: "Log in with Microsoft" — the app knows who logged in.

In practice: use OIDC for login. Use the access token to call APIs.

2 — Authorization Code Flow with PKCE

The recommended flow for web apps and SPAs. PKCE (Proof Key for Code Exchange) prevents authorization code interception attacks. Click Next Step to walk through:

1

User Clicks "Sign In"

Angular app (using MSAL) generates a random code_verifier string and its code_challenge (SHA-256 hash of the verifier). Stores code_verifier in memory.

2

Redirect to Entra ID Login

Browser redirects to:
https://login.microsoftonline.com/{tenantId}/oauth2/v2.0/authorize?client_id=...&response_type=code&scope=openid+profile+api.read&redirect_uri=http://localhost:4200/callback&code_challenge=...&code_challenge_method=S256

3

User Authenticates (+ MFA if required)

Entra ID shows the login page. User enters username + password. If Conditional Access requires MFA → MFA challenge. If consent required → user sees permission dialog and accepts.

4

Entra Redirects Back with Authorization Code

Entra ID redirects browser to: http://localhost:4200/callback?code=ABC123...
The code is short-lived (60–90 seconds). It's NOT a token — it's a one-time code to exchange for tokens.

5

App Exchanges Code + Verifier for Tokens

Angular POSTs to the token endpoint:
POST https://login.microsoftonline.com/{tenantId}/oauth2/v2.0/token
Body: code=ABC123&code_verifier=ORIGINAL_VERIFIER&client_id=...&grant_type=authorization_code
PKCE: Entra verifies SHA256(verifier) = challenge sent in step 2.

6

Receive Tokens

Entra returns: access_token (for calling your API), id_token (identifies the user, decode to get name/email), refresh_token (get new access tokens silently).
MSAL stores tokens in memory / sessionStorage (never in localStorage — XSS risk).

7

Use Access Token to Call Spring Boot API

MSAL interceptor auto-attaches: Authorization: Bearer <access_token> to API calls.
Spring Boot validates the token's signature + expiry + audience using Entra's JWKS endpoint. No network call needed per request after initial JWKS fetch.

3 — Client Credentials Flow

For service-to-service calls — no user involved. A background job or microservice authenticates as itself.

POST https://login.microsoftonline.com/{tenantId}/oauth2/v2.0/token grant_type=client_credentials &client_id=YOUR_SERVICE_CLIENT_ID &client_secret=YOUR_SECRET (or use certificate assertion) &scope=api://TARGET_API_CLIENT_ID/.default Response: { "access_token": "eyJ0...", "token_type": "Bearer", "expires_in": 3600 // No refresh_token — just get a new one when this expires }
When to use: CI/CD pipelines calling deployment APIs, background jobs syncing data, microservice A calling microservice B's internal API.
Never use for user-facing apps — there's no user in this flow.

4 — Token Types & Lifetimes

Access Token

Credential for calling APIs. APIs validate its signature and extract scopes/roles. Never log this token — it's a secret. Short-lived to limit damage if leaked.

default: 1 hour

ID Token

Contains user identity: name, email, object ID. For the client app to display "Welcome, Bob!" Never send to an API — it's not meant for API auth (wrong audience).

default: 1 hour

Refresh Token

Used to silently get new access + ID tokens when they expire. Long-lived. Store securely. If compromised, revoke from Entra portal. Invalidated on password change or explicit sign-out.

default: 90 days rolling

Silent Token Refresh (MSAL handles this automatically)

1. Access token expires (or about to expire)
2. MSAL detects expiry, automatically calls token endpoint with grant_type=refresh_token
3. Gets a new access token silently — user sees nothing
4. If refresh token is also expired → user is redirected to login page
