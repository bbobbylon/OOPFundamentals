RxJS & Observables — Comprehensive Reference

RxJS is a library for handling streams of values over time. Angular leans on it everywhere — HttpClient, the Router, Reactive Forms, EventEmitter. This page is a full reference: every operator you'll touch, every pattern you'll need, and every trap that bites people.

🔀 What is RxJS? Why does Angular use it instead of just Promises?

A Promise represents a single future value — it resolves once and it's done. A stream represents many values over time: a user typing, a WebSocket's messages, a sequence of navigation events. RxJS (Reactive Extensions for JavaScript) is the library for working with those streams — creating, transforming, combining, and reacting to them. Its core type is the Observable, which (unlike a Promise) can emit many values, can be cancelled, and is lazy: it does nothing until something subscribes.

  • An Observable is a lazy stream — define it, then .subscribe() to start it. No subscriber means no work happens.
  • You shape the stream with operators inside .pipe(): map transforms each value, filter drops some, catchError recovers, switchMap cancels the previous inner stream.
  • It emits three kinds of notification: next (a value), error (terminates), complete (terminates cleanly).
  • Streams are cold (each subscriber gets its own run — e.g. an HTTP call) or hot/shared (one source feeding many listeners).
  • Every .subscribe() must be cleaned up or it leaks — prefer the async pipe or takeUntilDestroyed().

Anatomy: create → transform → subscribe

http.get<User[]>('/api/users')
.pipe(
  map(us => us.filter(u => u.active)),
  catchError(() => of([]))
)
.subscribe(us => this.users = us);

Where Angular hands you streams

  • HttpClient.get() → Observable<T>
  • Router.events → navigation stream
  • FormControl.valueChanges → input stream
  • ActivatedRoute.params → route params
  • EventEmitter extends Subject

Memory-leak trap

Every .subscribe() keeps the stream alive. If the component is destroyed and you didn't unsubscribe, the callback still fires — on a dead component. Fix: the async pipe (auto-unsubscribes), takeUntilDestroyed(), or unsubscribe in ngOnDestroy.

Core CIAM RxJS patterns:switchMap cancels a prior token-refresh when a new one starts (no double-refresh); catchError in the auth interceptor catches 401s and triggers silent refresh; the async pipe binds user$ in templates; combineLatest([user$, roles$]) merges auth state from several sources.

Promise vs Observable — the mental model

Promise — one value, eagerly fired

const p = fetch('/api/me');   // fires NOW

p.then(r => console.log(r));
p.then(r => console.log(r));
// fetch happened ONCE. Both .then callbacks get the same value.
// Once resolved: no cancel, no follow-up values.

Observable — 0..N values, lazy & cancelable

const o = this.http.get('/api/me');   // NOTHING happens yet

const s1 = o.subscribe(r => console.log(r));
const s2 = o.subscribe(r => console.log(r));
// Two subscribes = TWO HTTP requests. Code runs on .subscribe.

s1.unsubscribe();   // cancel — request gets aborted
PromiseObservable
ValuesExactly 1 (or 1 error)0, 1, or many over time
ExecutionEager — runs when createdLazy — runs on .subscribe()
CancelableNoYes — .unsubscribe()
Operators.then, .catch, .finally100+ via .pipe()
Multi-subscriberShared resultRe-runs by default (cold); share with shareReplay
Backpressuren/aYes — buffers, throttles, samples
CompositionChained .thenDeclarative pipelines

The anatomy of a subscription

obs$.subscribe({
  next:     value => console.log(value),   // 0..N times
  error:    err   => console.error(err),   // 0..1 time, terminal
  complete: ()    => console.log('done'),  // 0..1 time, terminal
});

// Shorthand — just pass next() as a function
obs$.subscribe(value => console.log(value));

// THE RULE: error and complete are TERMINAL.
// After either fires: no more values. Stream is dead.
// Resources (timers, HTTP requests, listeners) are cleaned up.

The full Observable contract

An Observable is just a function with a subscribe method that takes an Observer (an object with next/error/complete). It returns a Subscription object whose only useful method is unsubscribe().

const myObs$ = new Observable<number>(observer => {
  observer.next(1);
  observer.next(2);
  const id = setInterval(() => observer.next(Math.random()), 1000);

  // Return a teardown function — runs on unsubscribe OR completion
  return () => clearInterval(id);
});

const sub = myObs$.subscribe(v => console.log(v));
sub.unsubscribe();  // triggers the teardown

You rarely write Observables this way — RxJS gives you of, from, fromEvent, etc. But knowing this is what's underneath demystifies the whole library.

Creating Observables — the helpers

of(...values)creation

Emit a sequence of static values synchronously, then complete.

of(1, 2, 3).subscribe(console.log);   // 1, 2, 3, done
of({ name: 'Bobby' }).subscribe(...);    // 1 emission, done
from(iterable | promise | observable)creation

Convert anything iterable, a Promise, or another Observable-like into an Observable.

from([1, 2, 3]).subscribe(...);            // emits each item
from(fetch('/api/x')).subscribe(...);            // Promise → Observable
from('hi').subscribe(...);                    // 'h', 'i' (string is iterable)
fromEvent(target, event)creation

DOM/Node EventEmitter events as a stream. The unsubscribe removes the listener.

fromEvent(button, 'click').pipe(
  map(e => ({ x: e.clientX, y: e.clientY }))
).subscribe(console.log);
interval(ms) / timer(delay, period?)creation

Time-based emissions.

interval(1000).subscribe(t => ...);          // every 1s: 0, 1, 2...
timer(500).subscribe(...);                 // once, after 500ms
timer(500, 1000).subscribe(...);           // after 500ms, then every 1s
EMPTY / NEVER / throwErrorcreation

Edge-case constants useful in error handlers and tests.

EMPTY                          // completes immediately, emits nothing
NEVER                          // never emits, never completes
throwError(() => new Error('oops'))  // errors immediately
defer(factory)creation

Re-evaluate the factory per subscriber. Use when the inner value depends on subscription time (e.g. Date.now()) or when you want each subscriber to get a fresh Promise.

// Without defer — the Date is captured once
const stale$ = of(Date.now());

// With defer — each subscribe gets the CURRENT timestamp
const fresh$ = defer(() => of(Date.now()));
iif(condition, trueObs, falseObs)creation

Pick between two Observables at subscription time.

iif(() => user.isLoggedIn, authedData$, publicData$).subscribe(...);

distinctUntilChanged() / distinctUntilKeyChanged(key)filter

Drop consecutive duplicates. Saves wasted re-renders / re-fetches when an upstream value didn't actually change.

  map(v => v.email),
  distinctUntilChanged()           // only fire when email changed
).subscribe(emailValidator);
take(N) / takeLast(N) / takeWhile(pred) / takeUntil(notifier$)filter

Finish a stream early. takeUntil is the classic component-destroy pattern (though takeUntilDestroyed from @angular/core/rxjs-interop is the modern Angular 16+ way).

interval$.pipe( takeUntilDestroyed() )...                // modern (Angular 16+)

combineLatest([a$, b$, ...])combine

Emit when ANY input emits — combining the latest value from each. Waits for every input to emit at least once before the first output.

  map(([user, filter, order]) => buildView(user, filter, order))

forkJoin({ a: a$, b: b$ })combine

Wait for ALL inputs to complete, then emit the final value of each. RxJS's Promise.all. Only works on streams that complete — perfect for HTTP, terrible for Subjects.

forkJoin({
  user:    http.get('/api/user'),
  orders:  http.get('/api/orders'),
  prefs:   http.get('/api/prefs')
}).subscribe(({ user, orders, prefs }) => renderDashboard(user, orders, prefs));

withLatestFrom(other$)combine

Like combineLatest, but only the SOURCE drives emissions — the others are "passive" (we just grab their latest value).

saveButton$.pipe(
  withLatestFrom(form.valueChanges)
).subscribe(([_click, formValue]) => api.save(formValue));
// Triggered by click; doesn't re-fire on every keystroke.
merge(a$, b$, ...)combine

Interleave emissions from multiple streams — values come out as soon as they arrive, from any input.

merge(clicks$, keypresses$, swipes$).subscribe(allInputs => ...);
concat(a$, b$, ...)combine

Subscribe to a$, wait for it to complete, then subscribe to b$. Sequential, ordered, never overlapping.

concat(initialLoad$, polling$).subscribe(...);
// Run an initial fetch, then start polling.
zip(a$, b$, ...)combine

Wait for every input to emit its Nth value, then emit them paired. Stream pacing is the SLOWEST input.

zip(timestamps$, sensorReadings$)
  .pipe( map(([t, v]) => ({ t, v })) )
  .subscribe(plotPoint);

Operators — error handling

catchError(handler)error

Catch an error and return a replacement Observable. The stream continues if the replacement emits values.

http.get<User[]>('/api/users').pipe(
  catchError(err => {
    console.error(err);
    return of([]);                // fallback to empty list
  })
).subscribe(users => ...);

// Or RE-THROW to bubble up:
catchError(err => throwError(() => new FormattedError(err)))
retry(count) / retry({ count, delay })error

Resubscribe to the source up to count times on error. With delay, you get backoff for free.

http.get('/api/flaky').pipe(
  retry({
    count: 3,
    delay: (err, retryIndex) => timer(Math.pow(2, retryIndex) * 1000)
    // 1s, 2s, 4s — exponential backoff
  })
).subscribe(...);
timeout(ms)error

If the source doesn't emit within ms, error with TimeoutError.

http.get('/api/slow').pipe(
  timeout(5000),
  catchError(err => of({ error: 'took too long' }))
).subscribe(...);
finalize(fn)error

Run a teardown when the stream completes, errors, OR unsubscribes. The .finally() of RxJS.

loading.set(true);
http.get('/api/data').pipe(
  finalize(() => loading.set(false))   // always runs
).subscribe(...);

Operators — multicasting (cold → hot)

share() / shareReplay(N)multicast

Take a cold source (re-runs per subscriber) and share a single execution. shareReplay additionally caches the last N values for late subscribers.

// Without — three HTTP calls
user$ = http.get<User>('/api/me');

// With shareReplay — one HTTP call, cached value for all subscribers
user$ = http.get<User>('/api/me').pipe(
  shareReplay({ bufferSize: 1, refCount: true })
);

shareReplay options — the ones that actually matter

OptionEffectDefault
bufferSizeHow many past values to replay to new subscribersInfinity
refCount: trueUnsubscribe upstream when subscriber count → 0. Next subscriber refetches.false (cache leaks forever)
windowTimeHow long to keep cached values (ms)Infinity
The leak: shareReplay(1) alone keeps the source alive forever, even with zero subscribers. Always use shareReplay({ bufferSize: 1, refCount: true }) unless you genuinely want a forever-warm cache.

Operators — utility

tap(observer)util

Run a side effect without changing the stream. Your debugger and your logger.

source$.pipe(
  tap(v => console.log('before:', v)),
  map(x => x * 2),
  tap(v => console.log('after:', v))
).subscribe(save);
delay(ms)util

Push every emission forward in time by ms. Mostly useful in tests / demos.

of('hi').pipe( delay(1000) ).subscribe(console.log);
defaultIfEmpty(value) / throwIfEmpty()util

Emit a fallback if the source completes without producing anything.

http.get<User[]>('/api/users').pipe(
  filter(users => users.length > 0),
  defaultIfEmpty('no users found')
).subscribe(...);

The classic state-service pattern

export class CartService {
  private items$ = new BehaviorSubject<Item[]>([]);
  readonly items = this.items$.asObservable();        // expose read-only

  add(item: Item) {
    this.items$.next([...this.items$.value, item]);    // push new state
  }
  remove(id: string) {
    this.items$.next(this.items$.value.filter(i => i.id !== id));
  }
}

// Components consume it
items$ = this.cart.items;
// template: <div *ngFor="let i of items$ | async">{{ i.name }}</div>
Subject vs BehaviorSubject — pick wrong and you'll get null on first render. If a subscriber needs to see the current state immediately on mount, use BehaviorSubject. If it's a fire-and-forget event channel, use Subject.

The unsubscribe trap — memory leak time

A subscription that's not unsubscribed when its component dies = memory leak. The subscription keeps the component alive AND keeps firing callbacks on a dead component. Four ways to fix it:

// ❌ NAIVE — leaks if interval keeps firing after destroy
ngOnInit() {
  interval(1000).subscribe(t => this.tick = t);
}

// ✅ FIX 1 — async pipe (best when used in template)
tick$ = interval(1000);
// template:  {{ tick$ | async }}

// ✅ FIX 2 — takeUntilDestroyed() (Angular 16+, the modern way)
interval(1000).pipe(
  takeUntilDestroyed()                 // must be called in an injection context
).subscribe(t => this.tick = t);

// ✅ FIX 3 — destroy$ Subject (the classic, pre-v16)
private destroy$ = new Subject<void>();
ngOnInit() {
  interval(1000).pipe( takeUntil(this.destroy$) ).subscribe(...);
}
ngOnDestroy() {
  this.destroy$.next(); this.destroy$.complete();
}

// ✅ FIX 4 — toSignal() (best for components using signals everywhere)
tick = toSignal(interval(1000), { initialValue: 0 });
// auto-unsubscribes on destroy
Rule of thumb: if it's an HTTP call (single emission, auto-completes) — you're safe, no leak. If it's anything that emits multiple times (intervals, subjects, fromEvent, valueChanges, route params) — handle the unsubscribe.

RxJS ↔ Signals interop

Signals are great for synchronous state. Observables are great for async streams. Angular ships @angular/core/rxjs-interop to convert between them — use both, glue at the seam.

import { toSignal, toObservable } from '@angular/core/rxjs-interop';

// Observable → Signal (auto-unsubscribes on destroy)
user = toSignal(this.http.get<User>('/api/me'), { initialValue: null });

// Signal → Observable (emits on every signal change)
query = signal('');
results = toSignal(
  toObservable(this.query).pipe(
    debounceTime(300),
    switchMap(q => this.api.search(q))
  ),
  { initialValue: [] }
);

// In template:
// <input [ngModel]="query()" (ngModelChange)="query.set($event)">
// @for (r of results(); track r.id) {...}
The pattern: Keep user input + UI state in signals. Pipe through RxJS for async work (HTTP, debounce, retry). Convert back to a signal for the template. Best of both worlds, no leaks.

Testing RxJS with marble diagrams

RxJS ships a TestScheduler that runs streams in virtual time. You declare expectations as ASCII marble strings. Each character is 1 frame (1 millisecond by default).

import { TestScheduler } from 'rxjs/testing';

describe('debounceTime', () => {
  let scheduler: TestScheduler;
  beforeEach(() => {
    scheduler = new TestScheduler((actual, expected) => {
      expect(actual).toEqual(expected);
    });
  });

  it('collapses bursts', () => {
    scheduler.run(({ cold, expectObservable }) => {
      const source = cold('-a-b-c-----d-|');
      const expected =       '-------c----d|';   // 4-frame debounce
      expectObservable(source.pipe( debounceTime(4) )).toBe(expected);
    });
  });
});

Marble tests are the gold standard for testing operator pipelines — they describe behavior without resorting to real timers (which would slow tests to a crawl).

10 real-world RxJS recipes

1. Search-as-you-type with cancellation

When: user types into a search input and you want to query an API
search = toSignal(
  toObservable(this.query).pipe(
    filter(q => q.length >= 2),
    debounceTime(300),
    distinctUntilChanged(),
    switchMap(q => this.api.search(q).pipe(
      catchError(() => of([]))
    ))
  ), { initialValue: [] });

2. Polling — refetch every N seconds while page is visible

When: dashboards, real-time-ish data, no websocket
data$ = timer(0, 5000).pipe(             // emit immediately, then every 5s
  switchMap(() => this.http.get('/api/status')),
  retry({ count: 3, delay: 2000 }),
  shareReplay({ bufferSize: 1, refCount: true })
);

3. Exponential-backoff retry

When: a flaky upstream API that needs gradual back-off, not hammering
http.get('/api/flaky').pipe(
  retry({
    count: 5,
    delay: (err, retryIndex) => {
      const delayMs = Math.min(1000 * 2 ** retryIndex, 30_000);
      console.log(`retry #${retryIndex} in ${delayMs}ms`);
      return timer(delayMs);
    }
  })
);

4. Auto-save with debounce + concatMap (preserve order)

When: a text editor, "saves as you type"
form.valueChanges.pipe(
  debounceTime(500),
  distinctUntilChanged((a, b) => JSON.stringify(a) === JSON.stringify(b)),
  concatMap(value => this.api.save(value))     // queue: saves apply in order
).subscribe();

5. Don't double-submit a form

When: button that triggers an API call you don't want fired twice
submit$.pipe(
  exhaustMap(() => this.api.submitOrder())   // clicks during in-flight = ignored
).subscribe(result => ...);

6. WebSocket with reconnect

8. Optimistic update with rollback on error

When: like buttons, instant UI feedback
likePost(id: string) {
  const prev = this.posts$.value;
  this.posts$.next(prev.map(p => p.id === id ? { ...p, liked: true } : p));

  this.api.like(id).pipe(
    catchError(() => {
      this.posts$.next(prev);                  // rollback

  ).subscribe();
}

Operator decision tree

Q: What kind of operation?
→ Transform every value ......... map, scan → Drop some values ............... filter, distinctUntilChanged, skip, take → Rate-limit emissions ........... debounceTime, throttleTime, sampleTime → Map to an inner Observable Q: What if a new one arrives while old is running? → Cancel old, take new ......... switchMap <-- 90% case → Queue, run in order ............ concatMap → Run all in parallel ............ mergeMap → Ignore new while old runs ...... exhaustMap → Combine multiple streams Q: When do you want output? → Whenever ANY emits ............. combineLatest → Only when SOURCE emits ......... withLatestFrom → When ALL complete .............. forkJoin → Interleave all ................. merge → Sequentially ................... concat → Handle errors ................... catchError, retry, timeout → Cache a result .................. shareReplay({ bufferSize: 1, refCount: true }) → Cleanup on destroy .............. takeUntilDestroyed() (v16+) → Inject seed value ............... startWith → Side effect / debug ............. tap

Common bugs & gotchas

SymptomLikely causeFix
"HTTP request never fires" Never subscribed to the Observable Add .subscribe() or use | async in template
"Got results for the wrong query" Using mergeMap instead of switchMap Switch to switchMap for type-ahead
"Same HTTP call fired 5 times" Subscribed to a cold Observable 5 times Add shareReplay({ bufferSize: 1, refCount: true })
"Memory keeps growing" Manual .subscribe() with no teardown takeUntilDestroyed() or | async
"Nothing happens on first render" Using Subject, expected BehaviorSubject Use BehaviorSubject(initial) or startWith(initial)
"shareReplay never recomputes" Source was hot-cached forever Pass refCount: true, or invalidate via a trigger Subject
"Error in one inner Observable killed the whole stream" catchError in wrong place Put catchError INSIDE the mapping function so only that inner fails
"forkJoin never emits" One input never completes (Subject, interval) Use combineLatest instead, or take(1) on each input
"Nested .subscribe() pyramid" Mixing imperative with declarative Compose with switchMap; subscribe ONCE at the edge
"distinctUntilChanged not deduping objects" Reference equality vs value equality Pass a comparator: distinctUntilChanged((a, b) => a.id === b.id)
The #1 anti-pattern: .subscribe() inside another .subscribe(). If you do this, you can't unsubscribe properly, you lose error propagation, and you've recreated callback hell with extra steps. Always compose with switchMap/mergeMap/etc., subscribe once at the edge.

Mental model — final word

Observable = future stream of values

You're not handling "the value" — you're handling "every value that arrives over time". Think conveyor belt, not box.

Operators don't run immediately

.pipe(map, filter, ...) just builds a recipe. Nothing executes until something subscribes. This is "lazy".

Always have an exit strategy

Every multi-value subscription needs takeUntilDestroyed / | async / toSignal. Otherwise: memory leak.

Prefer composing over subscribing

If you find yourself .subscribe()-ing inside another .subscribe(), switch to switchMap. Subscribe ONCE at the edge.

Pick the right flatten operator

switch (cancel) · concat (queue) · merge (parallel) · exhaust (ignore). Most "weird async bugs" trace back to picking the wrong one.

Signals for state, RxJS for streams

Use signals for synchronous component state. Use RxJS when time, cancellation, or composition matters. Glue with toSignal/toObservable.

🌱 RxJS feels alien at first — here's the one idea under all of it.

A normal value is one thing, right now: const x = 5. An Observable is a stream of values, arriving over time — like keystrokes, mouse clicks, or HTTP responses. You can't just read it; you subscribe to be told each time a new value shows up.

The analogy that makes it click: an array is a list of values in space (all here at once); an Observable is a list of values in time (they trickle in). And just like you .map() and .filter() an array, you transform a stream with operators inside .pipe(...):

  • A stream emits values (zero or many), then either completes or errors — exactly one ending.
  • .subscribe(v => …) starts it and runs your callback per value. (Many Observables are cold: nothing happens until someone subscribes.)
  • .pipe(map(...), filter(...)) builds a new transformed stream without changing the original.
  • In templates the async pipe — {{ data$ | async }} — subscribes for you and unsubscribes when the component dies.

If you remember nothing else: Observable = values over time; operators reshape them; subscribe to receive them. The scary names (switchMap, debounceTime) are just specialized reshapers.

🧠 Expert corner — cold/hot, the flattening map, and not leaking

  • Cold vs hot is about where the producer lives. A cold Observable (e.g. HttpClient.get()) creates its producer per subscriber — two subscribers = two HTTP calls. A hot one (a Subject, a DOM event stream) shares one producer; late subscribers miss earlier values. share()/shareReplay() turn cold into hot (and shareReplay({ bufferSize:1, refCount:true }) is the usual cache-the-last-value recipe). See Multicasting.
  • The flattening operators are the heart of real apps. When each value triggers another Observable (a value → an HTTP call), you must choose how overlap is handled: switchMap cancels the previous inner (perfect for type-ahead search), concatMap queues in order (saves), mergeMap runs them in parallel, exhaustMap ignores new ones while one is running (login button spam). Most "weird async bugs" are the wrong choice here — walk them live in RxJS Flattening.
  • Unsubscribe or leak. A manual .subscribe() that outlives the component keeps running — and keeps a reference alive. Fix it with the async pipe (auto), takeUntilDestroyed() (v16+), or takeUntil(destroy$). HTTP requests complete on their own, but streams of events do not.
  • Error handling ends the stream. An unhandled error terminates the Observable — no more emissions. Use catchError to recover (return a fallback Observable), and mind placement: catchError inside a switchMap keeps the outer stream alive; outside it kills everything. retry/retryWhen for transient failures.
  • Subjects are the multi-tool. Subject (no initial value), BehaviorSubject (holds "current", great for state), ReplaySubject (replays N), AsyncSubject (only the last, on complete). A BehaviorSubject behind a service was the classic pre-signals state container.
  • Signals vs RxJS — not a rivalry. Use signals for synchronous component/UI state (no subscription, no leak); use RxJS when time, cancellation, or composition matter (debounced search, websockets, retry). Bridge with toSignal()/toObservable() — see the interop page. CIAM tie-in: a token-refresh pipeline (exhaustMap so concurrent 401s trigger one refresh, then replay) is pure RxJS; the resulting "is logged in" flag is a signal the navbar reads.
