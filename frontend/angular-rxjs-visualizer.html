RxJS & Observables

RxJS is a library for handling streams of values over time. Angular leans on it everywhere — HttpClient, the Router, Reactive Forms, EventEmitter. Learn ~10 operators and you can read any Angular codebase.

The mental model — Promise vs Observable

Promise — one value, eagerly fired

const p = fetch('/api/me');   // fires NOW

p.then(r => console.log(r));
p.then(r => console.log(r));
// fetch happened ONCE. Both .then callbacks get the same value.
// Once resolved, that's it — no way to cancel, no follow-up values.

Observable — 0..N values, lazy & cancelable

const o = this.http.get('/api/me');   // NOTHING happens yet

const sub1 = o.subscribe(r => console.log(r));
const sub2 = o.subscribe(r => console.log(r));
// Two subscribes = TWO HTTP requests. Lazy: code only runs on .subscribe.

sub1.unsubscribe();   // cancel — the request gets aborted
PromiseObservable
ValuesExactly 1 (or 1 error)0, 1, or many over time
ExecutionEager — runs when createdLazy — runs on .subscribe()
CancelableNoYes — .unsubscribe()
Operators.then, .catch only~100 operators via .pipe()
Multi-subscriberShared resultRe-runs by default (cold); use shareReplay to share

The anatomy of an Observable subscription

obs$.subscribe({
  next:     value => console.log(value),   // 0..N times — every emitted value
  error:    err   => console.error(err),   // 0..1 time — if something goes wrong
  complete: ()    => console.log('done'),  // 0..1 time — stream finished cleanly
});

// Shorthand — just pass next() as a function
obs$.subscribe(value => console.log(value));

// THE RULE: error and complete are TERMINAL.
// After either fires, no more values. The stream is finished.

5. switchMap — switch to a new inner Observable, cancel the old one

The most important of the "flatten" operators. When a new outer value arrives, cancel the in-flight inner Observable and start a new one. Perfect for "show results for the LATEST search, not whatever finishes first." 

searchBox$.pipe(
  switchMap(query => this.http.get(`/search?q=${query}`))
).subscribe(results => ...);

// Type "ang" → fires GET /search?q=ang
// Type "angu" before "ang" returns → CANCELS the /search?q=ang request
//                                  → fires GET /search?q=angu
// You always get the result for the latest query. No race conditions.
OperatorWhat it does when a new outer value arrivesUse for
switchMapCancel previous inner, start new oneSearch, navigation — only care about the latest
concatMapQueue — wait for previous to complete, then run nextSequential writes that mustn't overlap
mergeMapRun all in parallelFire-and-forget, where order doesn't matter
exhaustMapIgnore new outer while inner is running"Don't double-submit" button-click handlers

7. catchError — handle errors without breaking the stream

this.http.get('/api/users').pipe(
  catchError(err => {
    console.error(err);
    return of([]);            // fallback to empty list — stream continues
  })
).subscribe(users => ...);

// If you don't catchError, the error propagates to the .subscribe error handler
// and the stream is OVER. Pair catchError with `of(default)` to keep it alive.

8. take / takeUntil — finish a stream early

// take(N) — emit the first N values, then complete
clicks$.pipe( take(3) ).subscribe(...);   // only first 3 clicks

// takeUntil(notifier$) — stream until notifier emits, then complete
private destroy$ = new Subject<void>();

ngOnInit() {
  interval$.pipe( takeUntil(this.destroy$) ).subscribe(...);
}
ngOnDestroy() {
  this.destroy$.next();
  this.destroy$.complete();
}
// Classic "kill all subscriptions when component dies" pattern.

9. shareReplay — turn cold → hot, cache the last value

// Without shareReplay — every subscribe = new HTTP request
user$ = this.http.get<User>('/api/me');
// (used in 3 components → 3 network calls)

// With shareReplay — single request shared across all subscribers
user$ = this.http.get<User>('/api/me').pipe(
  shareReplay({ bufferSize: 1, refCount: true })
);
// First subscriber fires the request. Subsequent subscribers get the cached value.
// refCount: true → when subscriber count drops to 0, drop the cache so next subscriber refetches.

10. startWith / withLatestFrom — practical helpers

// startWith — emit a seed value before the source's first real emission
formChanges$.pipe( startWith(initialValue) ).subscribe(...);
// Great for "show something immediately, then update."

// withLatestFrom — combine, but only emit when SOURCE emits (other is "passive")
saveButton$.pipe(
  withLatestFrom(form.valueChanges)
).subscribe(([_click, formValue]) => api.save(formValue));
// Triggered by click; reads the latest form value without reacting to every keystroke.

Live demo — search as you type with debounce + switchMap

Type fast — see the debounce eat the in-between keystrokes. Each "API call" simulates a 600ms response. Notice switchMap cancels earlier requests so only the latest result shows up. 

fromEvent(searchInput, 'input').pipe(

Subjects — Observables you can emit into

Regular Observables emit on their own (timers, HTTP, etc). A Subject is BOTH an Observable AND an Observer — you can call .next(value) on it to push values manually. Use them for events, state holders, communication channels.

Subject typeBehaviorUse for
SubjectLate subscribers miss past values. Just a pipe.Events: button-clicks, "destroyed" notifier.
BehaviorSubject(initial)Has a "current value". New subscribers get it immediately.State: current user, selected tab, dark mode.
ReplaySubject(N)Buffers last N values; replays to new subscribers.Logs, recent activity.
AsyncSubjectOnly emits the FINAL value, on complete.Rare — basically a Promise replacement.
 
// The 90% case: BehaviorSubject for state
export class CartService {
  private items$ = new BehaviorSubject<Item[]>([]);    // initial = []

  readonly items = this.items$.asObservable();          // expose read-only

  add(item: Item) {
    this.items$.next([...this.items$.value, item]);     // push new state
  }
}

// Components consume it
items$ = this.cart.items;
<!-- template: -->
<div *ngFor="let i of items$ | async">{{ i.name }}</div>

Hot vs Cold Observables

❄️ Cold — produces values per subscriber

// http.get is COLD — re-fires for each subscribe
const users$ = this.http.get('/api/users');

users$.subscribe(...);   // HTTP request #1
users$.subscribe(...);   // HTTP request #2
users$.subscribe(...);   // HTTP request #3

🔥 Hot — produces once, shared by subscribers

// Subjects are HOT — single producer
const clicks$ = new Subject<Event>();

clicks$.subscribe(...);  // listener A
clicks$.subscribe(...);  // listener B — same events

// Make cold → hot with .pipe(shareReplay({...}))

The unsubscribe trap (memory leak time)

A subscription that's not unsubscribed when its component dies = a memory leak. The subscription keeps the component alive AND keeps firing callbacks on a dead component. Three ways to fix it: 

// ❌ NAIVE — leaks if interval keeps firing
ngOnInit() {
  interval(1000).subscribe(t => this.tick = t);
}

// ✅ FIX 1 — async pipe (best when used in template)
tick$ = interval(1000);
<!-- template: -->
{{ tick$ | async }}

// ✅ FIX 2 — takeUntilDestroyed() (Angular 16+, the modern way)
ngOnInit() {
  interval(1000).pipe(
    takeUntilDestroyed(this.destroyRef)
  ).subscribe(t => this.tick = t);
}
// inject DestroyRef in the field initializer; auto-unsubscribes on ngOnDestroy

// ✅ FIX 3 — destroy$ Subject (the classic, pre-v16)
private destroy$ = new Subject<void>();
ngOnInit() {
  interval(1000).pipe( takeUntil(this.destroy$) ).subscribe(...);
}
ngOnDestroy() {
  this.destroy$.next(); this.destroy$.complete();
}

Rule of thumb: if it's an HTTP call (single emission, auto-completes) — you're safe, no leak. If it's anything that emits multiple times (intervals, subjects, fromEvent, valueChanges, params) — handle the unsubscribe.

Creating Observables — the helpers

// of — emit static values, then complete
of(1, 2, 3).subscribe(console.log);              // 1, 2, 3, done

// from — convert array, Promise, iterable to Observable
from([1, 2, 3]).subscribe(console.log);
from(fetch('/x')).subscribe(...);                  // Promise → Observable

// fromEvent — DOM events as a stream
fromEvent(button, 'click').subscribe(...);

// interval / timer — time-based
interval(1000).subscribe(t => ...);                // every 1s: 0, 1, 2, ...
timer(500, 1000).subscribe(t => ...);             // after 500ms, then every 1s

// EMPTY — completes immediately (useful in catchError)
// NEVER — never emits, never completes
// throwError — emits an error
throwError(() => new Error('oops'));

How Angular uses Observables — the four big places

🌐 HttpClient

Every HTTP method returns Observable<T>. Don't forget to subscribe (or use | async in the template) — without it, the request never fires.

🧭 Router

route.params, queryParams, data, router.events — all Observables. React to URL changes as a stream.

📋 Reactive Forms

form.valueChanges and form.statusChanges emit on every keystroke. Compose with debounceTime, distinctUntilChanged.

📤 EventEmitter

@Output() uses EventEmitter under the hood — which extends Subject. So Angular's "events" are already RxJS streams.

Mental model

Observable = future stream of values

You're not handling "the value" — you're handling "every value that arrives over time". Think conveyor belt, not box.

Operators don't run immediately

.pipe(map, filter, ...) just builds a recipe. Nothing executes until something subscribes. This is "lazy".

Always have an exit strategy

Every multi-value subscription needs takeUntilDestroyed / | async / manual unsubscribe. Otherwise: memory leak.

Prefer composing over subscribing

If you find yourself .subscribe()-ing inside another .subscribe(), you're doing it wrong. Use switchMap / combineLatest to compose, subscribe only at the edge.
