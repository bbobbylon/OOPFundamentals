Node Auth — JWT, Sessions & Middleware

How a Node backend proves who you are and what you may do: a login route mints a signed JWT, an auth middleware verifies the Authorization: Bearer token on every protected request, and a guard checks scopes. Authentication (401) and authorization (403) are two distinct gates.

🔐 What is token auth in Node — and why is the JWT itself the session?

Auth answers two separate questions. Authentication — who are you? — happens once at /login: the server checks the password against a stored bcrypt hash, and on success mints a JWT (JSON Web Token) with jwt.sign(claims, key). A JWT is three base64url parts — header.payload.signature — where the payload carries claims (sub = the user id, scope/roles, exp = expiry) and the signature proves the server issued it. The client stores the token and sends it on every later request as Authorization: Bearer <token>. The key idea: the token is self-contained — the signature lets any server verify it with just the key, so the backend keeps no session state (it is stateless). That contrasts with classic server sessions, where login creates a row in a session store and the browser holds only an opaque connect.sid cookie that the server looks up each request. On every protected route an auth middleware — an ordinary (req, res, next) function in Express, or a CanActivate guard in NestJS — pulls the Bearer token, runs jwt.verify (checking the signature and exp), and on success attaches the principal to req.user and calls next(). If the token is missing, tampered, or expired it short-circuits with 401 Unauthorized and the handler never runs. Authorization — are you allowed? — is a second gate: even a perfectly valid token may lack the required scope, so a guard returns 403 Forbidden.

  • Login → sign — verify the bcrypt hash, then jwt.sign({sub,scope}, key, {expiresIn}) mints a signed token.
  • Bearer — the client returns it as Authorization: Bearer <token> on each request.
  • Verify middleware — jwt.verify checks signature + exp; sets req.user; bad token → 401.
  • 401 vs 403 — authentication failure (who?) is 401; authorization failure (allowed?) is 403.

CIAM in production: you rarely verify an HMAC secret you own. Instead the IdP (Microsoft Entra, Ping) signs tokens with RS256 (asymmetric) and publishes its public keys at a JWKS endpoint. Your API fetches and caches those keys, then verifies the signature plus iss (issuer), aud (audience) and exp — never holding a shared secret. That is exactly what Spring's NimbusJwtDecoder.withJwkSetUri(...) does. In a BFF (backend-for-frontend) the browser holds only an httpOnly session cookie and the BFF keeps the tokens server-side, relaying them to downstream APIs — so the access token never touches JavaScript (no XSS token theft). See spring-boot-security-filter-chain-deep and spring-boot-bff-token-relay-deep for the same flow on the Java side.

The problem

Your IdP's signing key is PUBLIC by design. That's supposed to be fine.

The one missing argument that turns a public key into a backdoor

Your API verifies Entra/Ping tokens with jwt.verify(token, publicKey) — no third argument. It works in every test you've written: real tokens, signed RS256 by the IdP, verify cleanly. Then a pentest report comes back with a forged admin token nobody signed. It wasn't cracked, guessed, or stolen — it's legitimate JSON, correctly formatted, verifying against the exact same public key your server already trusts. The key wasn't leaked. It was never secret to begin with — it's published at a JWKS URL on purpose, for anyone to read.

jwt.verify(token, publicKey) — no typo ✓ the public key really is public, on purpose ✓ no algorithms allowlist passed ⚠ attacker's header just says HS256 instead of RS256 ⚠

The bug isn't the public key. It's letting the token's OWN header decide how the server should check it.

Never let the token choose its own verification algorithm
jwt.verify(token, publicKey) ↓ the verifier blindly follows whatever alg the token's header claims Better: jwt.verify(token, publicKey, { algorithms: ['RS256'] }) ↓ the SERVER decides the algorithm; a token claiming HS256 is rejected before the key is touched A public key can never be smuggled in as someone else's HMAC secret
A verifier that lets the token say how it should be checked isn't verifying anything. jwt.verify without an explicit algorithms allowlist lets the attacker, not the server, choose the algorithm — and if that attacker can pick "treat this RSA public key as an HMAC secret instead," a value that was never meant to be secret becomes exactly that. The fix isn't a stronger key. It's refusing to let the token's own header cast a vote in its own verification.
Think of the RSA public key as a notary's stamp everyone is handed a photo of, on purpose — you're meant to be able to check a document against it. Algorithm confusion is a forger using that same photo as the ink for a completely different kind of signature — one your front desk happens to accept too, because nobody ever told it to accept only the notary's actual stamp. The photo was never stolen. Nobody told the front desk to reject the other kind of signature.
You

I verify every token against our IdP's public key. How did someone forge an admin token without ever touching a private key?

jwt.verify (unpinned)

You handed me a key and a token, and I did what the token's header told me: it said alg: HS256, so I treated your key argument as an HMAC secret and computed a matching signature. Nobody told me it was supposed to be an RSA public key used only for RS256. I just followed instructions — the token's instructions.

The attacker

And your public key was never a secret. It's published at a JWKS URL for anyone to fetch — that's the whole point of asymmetric signing. I downloaded it, used it as an HMAC key instead of an RSA key, and your verifier never questioned the switch.

jwt.verify (algorithms: ['RS256'] pinned)

This time you told me what to expect before I ever looked at the token. Its header says HS256; that's not on my allowlist, so I reject it before your key is used for anything. The token's own claims don't get a vote.

The mechanism

One missing argument is the entire difference between a verifier and a rubber stamp.

  1. Your IdP signs real tokens RS256, and publishes the matching PUBLIC key at a JWKS URL — by design, so any server can verify without ever holding a private keyworking as intended, so far
  2. Your server calls jwt.verify(token, publicKey) with no algorithms option — the verifier will accept whatever algorithm the TOKEN's own header claimsthe missing guardrail
  3. An attacker fetches that same public JWKS key — they're allowed to, it's public — and crafts a forged token with header alg: HS256 and any payload they like, say scope: ["admin"]no private key needed
  4. The attacker computes an HMAC-SHA256 signature over the token using the PUBLIC KEY STRING as the HMAC secret — possible only because that "secret" was never actually secretthe actual trick
  5. Your unpinned verifier reads the forged header, sees HS256, and — trusting the token — treats the public key you gave it as an HMAC secret too, computing the identical signatureit matches, because you handed it the same string
  6. Verification succeeds. The forged token is now indistinguishable, to your server, from one your IdP actually signedgame over, silently

Step 2 is the lesson. Every step after it is just the attacker correctly exploiting the one design choice your server made: letting the TOKEN decide the algorithm instead of the SERVER deciding it. Pin the algorithm and step 5 fails immediately — a header claiming HS256 gets rejected before your public key is used for anything at all.

jwt.verify(token, publicKey)no algorithms option — the TOKEN picks
↓ header says ↓
alg: RS256 — verify with the real public key alg: HS256 — verify the SAME key string as an HMAC secret instead

Both options are live at once, and the attacker gets to flip the switch — that's what "no algorithms allowlist" actually means. Pin algorithms: ['RS256'] and the second option is deleted before the token is even read; there is no switch left for anyone else to flip.

Your server runs jwt.verify(token, publicKey) with no algorithms option. An attacker who has never seen your private key sends a token whose header is {"alg":"HS256"} and whose signature is HMAC-SHA256(header + "." + payload, publicKey) — using your real, publicly-known RS256 public key as the HMAC secret. What happens?

A reasonable-sounding guess — RSA keys and HMAC secrets feel like different worlds. But HMAC doesn't know or care what a key "is"; it takes an arbitrary byte string. A PEM-formatted RSA public key is, at the byte level, just a string, and that string works perfectly well as an HMAC key. There's no format check standing in the way.

Right. Without an algorithms allowlist, the verifier lets the token's own header pick the algorithm. The header says HS256, so the key argument gets used as an HMAC secret — and because the attacker used that exact public key value to compute the HMAC themselves, the two signatures match. Nothing about this required the private key at any point.

This describes the FIX, mistaken for the default. Pinning algorithms: ['RS256'] is exactly what makes the server, not the token, decide the algorithm — but that has to be requested. Without it, nothing cross-checks "this looks like an RSA key" against "the header says HMAC"; the library just does what the header asks.

Where you've seen this before

Three systems, one root cause: letting the untrusted side pick how it gets checked.

TLS downgrade attacks: the same move, one layer down

POODLE, FREAK, and Logjam are all the identical idea at the transport layer: a TLS handshake lets both sides negotiate the cipher, and an attacker who can sit in the middle forces that negotiation down to a weaker algorithm the server still accepts for compatibility — then breaks the weak algorithm instead of the strong one. JWT algorithm confusion is the application-layer version: the "negotiation" is just an unauthenticated header field, and "still accepts for compatibility" is an unpinned algorithms list.

downgrade to a weaker algorithm, exploit that instead

Insecure deserialization: trusting the payload to describe itself

Java and Python's classic insecure-deserialization bugs (the 2015 ysoserial gadget chains, among others) share the same root cause: the incoming data includes a type descriptor, and the deserializer instantiates whatever the payload claims to be. Algorithm confusion is the same shape in miniature — the token includes an algorithm descriptor, and a naive verifier processes it as whatever the token claims. Both are fixed the same way: an explicit allowlist the RECEIVER controls, never a self-description the SENDER controls.

let the receiver decide the type, never the payload

Your Spring resource server has the safer default

Spring Security's NimbusJwtDecoder.withJwkSetUri(...) — the exact tool this page's own CIAM note points to — sidesteps this entire bug class structurally: it resolves the verification key from the token's kid against the JWKS endpoint and expects an RS256/ES256-family algorithm by configuration, so a forged HS256 token is rejected as an algorithm mismatch before any key material is even compared. Node's jsonwebtoken gives you the same safety, but only if you ask for it with an explicit algorithms array — Spring's happy path defaults you into the safe behavior; Node's makes you opt in.

Spring defaults you in; jsonwebtoken makes you opt in
Questions from the back row

Is this just a theoretical attack, or has it happened for real?

Very real — this is one of the most cited JWT vulnerability classes in application security, formally disclosed against multiple mainstream JWT libraries around 2015, and it keeps resurfacing in pentest reports for exactly the reason this page walks through: someone wrote jwt.verify(token, key) without the third argument, and it worked in every test, because every test used a real, correctly-signed token. The vulnerability only shows up when someone feeds it a token you didn't expect.

Why doesn't the library just refuse to use an RSA-shaped key as an HMAC secret automatically?

Because HMAC keys have no required shape at all — cryptographically, an HMAC secret is "any bytes," so there's nothing for the library to inspect that would flag a PEM string as wrong for that role. Detecting "this looks like a public key someone published, not a secret someone chose" is a heuristic, not a guarantee — which is exactly why the real fix is a different mechanism entirely: telling the verifier the acceptable algorithm ahead of time, so it never gets to the point of using the key at all.

Does switching to RS256 everywhere protect me even without pinning algorithms?

No — RS256 is what makes THIS attack possible, not what causes it. An HS256-only system can't be downgrade-attacked this exact way, because there's no public key to repurpose in the first place, but it has its own version of the same root problem: without a pinned algorithm, a token can still choose an algorithm you never intended to accept. The fix is never "pick the right algorithm" — it's "the server decides the algorithm, unconditionally, before it looks at anything the token claims."

1. Login: verify the password, then sign a token

import jwt from 'jsonwebtoken';
import bcrypt from 'bcrypt';

app.post('/login', async (req, res) => {
  const { email, password } = req.body;
  const user = await users.findByEmail(email);
  if (!user || !await bcrypt.compare(password, user.hash))
    return res.status(401).json({ error: 'invalid credentials' }); // never say WHICH was wrong

  const token = jwt.sign(
    { sub: user.id, scope: user.roles }, // the claims (payload)
    process.env.JWT_SECRET, // HMAC secret (or an RS256 private key)
    { expiresIn: '15m', issuer: 'auth.example.com' });
  res.json({ token });
});
The signed token IS the session. Once minted, the JWT carries everything a later request needs — the user id and scopes — and the signature proves authenticity. The server stores nothing, so any instance (behind a load balancer) can verify it without a shared session store. The trade-off: you cannot instantly revoke a stateless token, which is why access tokens are short-lived (here 15 min) and paired with a longer-lived refresh token. Note the deliberately vague "invalid credentials" — revealing whether the email existed would leak which accounts are real (user enumeration).

2. The auth middleware: verify Bearer on every protected route

function requireAuth(req, res, next) {
  const header = req.headers.authorization || '';
  const token = header.startsWith('Bearer ') ? header.slice(7) : null;
  if (!token) return res.status(401).json({ error: 'missing token' });
  try {
    const claims = jwt.verify(token, process.env.JWT_SECRET); // signature + exp
    req.user = { id: claims.sub, scope: claims.scope }; // attach the principal
    next(); // pass control to the handler
  } catch (e) {
    return res.status(401).json({ error: 'invalid or expired token' });
  }
}

app.get('/me', requireAuth, (req, res) => res.json(req.user));
One middleware guards many routes. Because Express runs middleware in order, listing requireAuth before the handler means an unauthenticated request is rejected with a 401 and next() is never called — the handler is unreachable. jwt.verify does the real work: it recomputes the signature with the key and rejects a tampered token, and it checks exp and throws TokenExpiredError for a stale one. Only on success does it attach req.user, the principal every downstream handler reads — the Node equivalent of Spring's SecurityContextHolder.

3. Authorization: a guard checks scope (NestJS)

@Injectable()
export class ScopesGuard implements CanActivate {
  constructor(private required: string) {}
  canActivate(ctx: ExecutionContext): boolean {
    const req = ctx.switchToHttp().getRequest();
    const scopes = req.user?.scope ?? []; // set by the JWT guard
    if (!scopes.includes(this.required))
      throw new ForbiddenException(); // → 403, not 401
    return true;
  }
}
// @UseGuards(JwtAuthGuard, new ScopesGuard('admin')) — authn THEN authz
401 and 403 are different failures. Authentication asks "do I know who you are?" — a missing or invalid token is 401 Unauthorized. Authorization asks "are you permitted to do this?" — a valid token whose scope lacks admin is 403 Forbidden. The guards run in order: JwtAuthGuard establishes identity (populating req.user), then ScopesGuard reads that identity to decide access. Conflating the two is a classic API bug — a 403 should never be sent for an unauthenticated caller, and a 401 should never be sent for a known user who simply lacks a role.
