Node Auth — JWT, Sessions & Middleware

How a Node backend proves who you are and what you may do: a login route mints a signed JWT, an auth middleware verifies the Authorization: Bearer token on every protected request, and a guard checks scopes. Authentication (401) and authorization (403) are two distinct gates.

🔐 What is token auth in Node — and why is the JWT itself the session?

Auth answers two separate questions. Authentication — who are you? — happens once at /login: the server checks the password against a stored bcrypt hash, and on success mints a JWT (JSON Web Token) with jwt.sign(claims, key). A JWT is three base64url parts — header.payload.signature — where the payload carries claims (sub = the user id, scope/roles, exp = expiry) and the signature proves the server issued it. The client stores the token and sends it on every later request as Authorization: Bearer <token>. The key idea: the token is self-contained — the signature lets any server verify it with just the key, so the backend keeps no session state (it is stateless). That contrasts with classic server sessions, where login creates a row in a session store and the browser holds only an opaque connect.sid cookie that the server looks up each request. On every protected route an auth middleware — an ordinary (req, res, next) function in Express, or a CanActivate guard in NestJS — pulls the Bearer token, runs jwt.verify (checking the signature and exp), and on success attaches the principal to req.user and calls next(). If the token is missing, tampered, or expired it short-circuits with 401 Unauthorized and the handler never runs. Authorization — are you allowed? — is a second gate: even a perfectly valid token may lack the required scope, so a guard returns 403 Forbidden.

  • Login → sign — verify the bcrypt hash, then jwt.sign({sub,scope}, key, {expiresIn}) mints a signed token.
  • Bearer — the client returns it as Authorization: Bearer <token> on each request.
  • Verify middleware — jwt.verify checks signature + exp; sets req.user; bad token → 401.
  • 401 vs 403 — authentication failure (who?) is 401; authorization failure (allowed?) is 403.

Spring Boot comparison

The requireAuth middleware ≈ Spring Security's BearerTokenAuthenticationFilter in the filter chain. jwt.verify ≈ a JwtDecoder (validates signature + exp/iss). Setting req.user ≈ populating the SecurityContext with an Authentication. A NestJS CanActivate guard with a scope check ≈ @PreAuthorize("hasAuthority('admin')") / method security. 401 vs 403 map to Spring's AuthenticationEntryPoint vs AccessDeniedHandler.

CIAM in production: you rarely verify an HMAC secret you own. Instead the IdP (Microsoft Entra, Ping) signs tokens with RS256 (asymmetric) and publishes its public keys at a JWKS endpoint. Your API fetches and caches those keys, then verifies the signature plus iss (issuer), aud (audience) and exp — never holding a shared secret. That is exactly what Spring's NimbusJwtDecoder.withJwkSetUri(...) does. In a BFF (backend-for-frontend) the browser holds only an httpOnly session cookie and the BFF keeps the tokens server-side, relaying them to downstream APIs — so the access token never touches JavaScript (no XSS token theft). See spring-boot-security-filter-chain-deep and spring-boot-bff-token-relay-deep for the same flow on the Java side.

1. Login: verify the password, then sign a token

import jwt from 'jsonwebtoken';
import bcrypt from 'bcrypt';

app.post('/login', async (req, res) => {
  const { email, password } = req.body;
  const user = await users.findByEmail(email);
  if (!user || !await bcrypt.compare(password, user.hash))
    return res.status(401).json({ error: 'invalid credentials' }); // never say WHICH was wrong

  const token = jwt.sign(
    { sub: user.id, scope: user.roles }, // the claims (payload)
    process.env.JWT_SECRET, // HMAC secret (or an RS256 private key)
    { expiresIn: '15m', issuer: 'auth.example.com' });
  res.json({ token });
});
The signed token IS the session. Once minted, the JWT carries everything a later request needs — the user id and scopes — and the signature proves authenticity. The server stores nothing, so any instance (behind a load balancer) can verify it without a shared session store. The trade-off: you cannot instantly revoke a stateless token, which is why access tokens are short-lived (here 15 min) and paired with a longer-lived refresh token. Note the deliberately vague "invalid credentials" — revealing whether the email existed would leak which accounts are real (user enumeration).

2. The auth middleware: verify Bearer on every protected route

function requireAuth(req, res, next) {
  const header = req.headers.authorization || '';
  const token = header.startsWith('Bearer ') ? header.slice(7) : null;
  if (!token) return res.status(401).json({ error: 'missing token' });
  try {
    const claims = jwt.verify(token, process.env.JWT_SECRET); // signature + exp
    req.user = { id: claims.sub, scope: claims.scope }; // attach the principal
    next(); // pass control to the handler
  } catch (e) {
    return res.status(401).json({ error: 'invalid or expired token' });
  }
}

app.get('/me', requireAuth, (req, res) => res.json(req.user));
One middleware guards many routes. Because Express runs middleware in order, listing requireAuth before the handler means an unauthenticated request is rejected with a 401 and next() is never called — the handler is unreachable. jwt.verify does the real work: it recomputes the signature with the key and rejects a tampered token, and it checks exp and throws TokenExpiredError for a stale one. Only on success does it attach req.user, the principal every downstream handler reads — the Node equivalent of Spring's SecurityContextHolder.

3. Authorization: a guard checks scope (NestJS)

@Injectable()
export class ScopesGuard implements CanActivate {
  constructor(private required: string) {}
  canActivate(ctx: ExecutionContext): boolean {
    const req = ctx.switchToHttp().getRequest();
    const scopes = req.user?.scope ?? []; // set by the JWT guard
    if (!scopes.includes(this.required))
      throw new ForbiddenException(); // → 403, not 401
    return true;
  }
}
// @UseGuards(JwtAuthGuard, new ScopesGuard('admin')) — authn THEN authz
401 and 403 are different failures. Authentication asks "do I know who you are?" — a missing or invalid token is 401 Unauthorized. Authorization asks "are you permitted to do this?" — a valid token whose scope lacks admin is 403 Forbidden. The guards run in order: JwtAuthGuard establishes identity (populating req.user), then ScopesGuard reads that identity to decide access. Conflating the two is a classic API bug — a 403 should never be sent for an unauthenticated caller, and a 401 should never be sent for a known user who simply lacks a role.
