OIDC Login — Authorization Code + PKCE

When your Angular SPA logs a user in through Entra ID or Ping, it uses the OpenID Connect Authorization Code flow with PKCE. The SPA never sees a password and never holds a client secret — it proves itself with a one-time cryptographic challenge instead. Here's every redirect and parameter, and why each one exists.

🔐 What is OIDC Authorization Code + PKCE — and why can't a SPA just send a password?

An Angular SPA can't safely hold a client secret — it's public JavaScript any user can inspect. The PKCE (Proof Key for Code Exchange) flow was built for exactly this: instead of a secret, the SPA generates a random code_verifier, hashes it into a code_challenge, sends the challenge up front, and later proves it had the original verifier. An attacker who intercepts the one-time code can't exchange it without the verifier — which never left the browser. The SPA never touches a username or password; it redirects the user to Entra ID / Ping to log in.

  • The SPA is a public client — no secret. PKCE replaces the secret with a per-login verifier/challenge pair.
  • 1 · Authorize: hash code_verifier → code_challenge, store the verifier, redirect to /authorize?…&code_challenge=…&code_challenge_method=S256.
  • 2 · Login at the IdP: the user authenticates on Entra/Ping's own page; the SPA sees none of it and gets back a one-time code.
  • 3 · Token exchange: POST the code + original code_verifier; the IdP re-hashes, compares, and returns the tokens.
  • Credentials and the secret never live in the SPA — that's the whole security win over a password grant.

Step 1 — Authorization request

SPA makes a random code_verifier (43–128 chars), hashes it to code_challenge = SHA256(verifier), stashes the verifier in sessionStorage, and redirects to /authorize?response_type=code&code_challenge=…&code_challenge_method=S256&scope=openid profile email.

Step 2 — User logs in at the IdP

Entra ID / Ping shows its own login page (the SPA sees none of it). On success it redirects back to redirect_uri?code=…. That code is short-lived (~60s), single-use, and useless without the verifier.

Step 3 — Token exchange

SPA POSTs to the token endpoint with grant_type=authorization_code&code=…&code_verifier=…. The IdP hashes the verifier, compares it to the stored challenge, and on match returns access + ID + refresh tokens.

In CIAM:your app registers a redirect_uri (e.g. https://app/auth/callback) in Entra/Ping. When the SPA's OidcCallbackComponent mounts there, it reads the code, pulls the code_verifier from sessionStorage, exchanges for tokens, keeps the access token in memory, and routes the user onward.

1. Why this exact flow for a browser app

A SPA is a public client: all its code ships to the browser, so it cannot keep a secret. The Authorization Code flow keeps tokens off the URL (they're fetched in a back-channel POST), and PKCE replaces the missing client secret with a per-login proof — so a stolen authorization code is useless to an attacker.

  • Authorization Code (not Implicit): tokens come from a POST to the token endpoint, never in a redirect fragment. Implicit flow is deprecated.
  • PKCE (Proof Key for Code Exchange): the app proves it's the same party that started the login.
  • OIDC adds an id_token on top of OAuth2 so you learn who the user is.

3. The parameters that keep it safe

ParameterOn which requestWhat it's for
code_challenge/authorizeSHA-256 of a secret code_verifier the app kept — the PKCE commitment
code_verifier/tokenrevealed only in the back-channel; the IDM hashes it and checks it matches the challenge
state/authorize → callbackCSRF guard — the app verifies the returned state equals what it sent
nonce/authorize → id_tokenreplay guard — the app checks the id_token.nonce matches
scope/authorizeopenid (required for OIDC) + profile email + your API scopes
redirect_uri/authorizemust exactly match one registered in the IDM app — limits where codes can land

The PKCE pair is the whole trick: the challenge goes out in a front-channel URL anyone can see; the verifier stays in the app and is revealed only in the back-channel token call. An attacker who steals the code can't redeem it without the verifier.

4. Two tokens, two jobs

id_token → authentication

A JWT about the user (sub, name, email, nonce). The SPA validates it (nonce, signature via JWKS, iss, aud, exp) and uses it to establish the logged-in session. It is not sent to your API.

access_token → authorization

The credential you attach as Authorization: Bearer … on API calls. Your Spring resource server validates this one — exactly the pipeline in the IDM deep-dive. (Plus a refresh_token to get new ones; next page.)

5. You don't hand-roll this — use a library

Entra ID → MSAL

// @azure/msal-angular + @azure/msal-browser
provideMsal({
  auth: {
    clientId: '<app-id>',
    authority: 'https://login.microsoftonline.com/<tenant>',
    redirectUri: '/auth/callback',
  },
});  // MSAL does PKCE, state, nonce, token cache, refresh

Ping / generic OIDC

// angular-oauth2-oidc (or oidc-client-ts)
this.oauth.configure({
  issuer: 'https://auth.pingone.com/<envId>/as',
  clientId: '<app-id>',
  redirectUri: location.origin + '/auth/callback',
  responseType: 'code',           // auth code
  scope: 'openid profile email api.read',
});
this.oauth.loadDiscoveryDocumentAndLogin();

Both discover endpoints from the IDM's /.well-known/openid-configuration, implement PKCE/state/nonce for you, validate the id_token, and cache tokens. Never implement the crypto or token parsing by hand.

6. One-sentence recap

🔓 An Angular SPA logs in with the OIDC Authorization Code + PKCE flow: it redirects to the IDM's /authorize with a code_challenge + state + nonce, the user authenticates, the IDM returns a one-time code to the registered redirect_uri, and the app back-channel POSTs that code plus the secret code_verifier to get an id_token (who you are) and an access_token (what you send your Spring API) — all handled by MSAL (Entra) or angular-oauth2-oidc (Ping), never by hand.
