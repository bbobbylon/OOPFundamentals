Java Strings

String immutability, the String Pool, StringBuilder, formatting, and every method you'll actually use.

📝 Why is String immutable in Java — and when does that matter?

In Java String is immutable — s.toUpperCase() returns a new string, it never mutates s. That buys three things: thread-safety (share freely), the string pool (literals are interned, so == on literals is true — but never trust it, use .equals()), and cached hash codes (great HashMap keys). The cost: concatenating in a loop (result = result + item) allocates each iteration — O(n²) — so use StringBuilder, String.join, or Collectors.joining.

  • Immutable = safe to share & cache — methods return new strings.
  • Compare with .equals(), never == — == tests identity, fooled by the pool.
  • Loop concatenation is O(n²) — use StringBuilder/String.join/joining.
  • Secrets prefer char[] — you can wipe an array; an immutable String lingers in memory.

StringBuilder vs String

Bad: String result = ""; for (String s : list) { result = result + s + ", "; } — creates a new String object every iteration; O(n²) total characters copied. Good: StringBuilder sb = new StringBuilder(); for (String s : list) { sb.append(s).append(", "); } String result = sb.toString() — O(n) amortised. Modern Java: String.join(", ", list) (returns joined string) or list.stream().collect(Collectors.joining(", ")). String.formatted("Hello %s, age %d", name, age) (Java 15+, same as String.format() but as an instance method). Text blocks (Java 15+): """ SELECT * FROM users WHERE active = true """.

Essential String methods

s.equals(other): content comparison (not ==). s.equalsIgnoreCase(other): case-insensitive. s.contains("sub"). s.startsWith("http"), endsWith(".json"). s.indexOf("x"): -1 if not found. s.substring(2,5): chars at indices 2,3,4. s.trim(): remove leading/trailing whitespace. s.strip(): Unicode-aware trim (Java 11+). s.isBlank(): true if null or whitespace-only (Java 11+). s.split(","): returns String[]. s.replace("old","new"): all occurrences. s.replaceAll(regex, replacement). s.toCharArray(). s.charAt(i). s.length(). s.isEmpty().

String security pitfalls

Strings are in the JVM heap and string pool — they can persist in memory long after you're done with them. For passwords and sensitive tokens: use char[] instead of String — you can clear a char array (Arrays.fill(charArray, '\0')) but can't clear a String (immutable). Java's Scanner.nextLine() and Spring's @Value return String for passwords anyway — but using char[] for the actual credential check reduces the window. In logging: log.debug("Processing user: " + user.getEmail()) — even if DEBUG is disabled, the string concatenation happens. Use log.debug("Processing user: {}", user.getEmail()) — SLF4j evaluates only if DEBUG is enabled.

CIAM / Spring Boot: JWTs are Strings — never log them above TRACE. Claim extraction (claims.get("email", String.class)) and correlation IDs (MDC.put("traceId", UUID.randomUUID().toString())) are all string ops. Build queries with parameters (PreparedStatement/JPA), never concatenation — "… WHERE email = '" + email + "'" is a SQL-injection hole.

Strings are immutable — every "change" creates a new object

String s = "hello"; // These create NEW String objects: String upper = s.toUpperCase(); // "HELLO" — s unchanged String longer = s + " world"; // new object String sub = s.substring(1, 3); // "el" System.out.println(s); // still "hello" // Reassignment changes the variable, not the object s = s.toUpperCase(); // s now points to "HELLO" // old "hello" object is eligible for GC

Why immutability?

✦ Thread-safe — no synchronization needed
✦ String Pool — safe to share references
✦ HashMap keys — hash code never changes
✦ Security — file paths, class names can't be mutated after validation
✦ Cache-friendly — hash is computed once

String vs char[] — for passwords, use char[] then wipe it

// Problem with String for passwords String password = "secret"; // "secret" lives in the String Pool — can't be wiped! // Even after password = null, object lingers until GC // Solution: char[] — can be explicitly zeroed char[] password = getPasswordChars(); try { authenticate(password); } finally { Arrays.fill(password, ' '); // zero out immediately }

StringBuilder — mutable string for building up content

// Why StringBuilder? // String concatenation in a loop is O(n²)! String result = ""; for (int i = 0; i < 1000; i++) { result += i; // creates 1000 String objects! } // StringBuilder: O(n) — single mutable buffer StringBuilder sb = new StringBuilder(); for (int i = 0; i < 1000; i++) { sb.append(i); } String result = sb.toString();
// StringBuilder methods — all return this (fluent) StringBuilder sb = new StringBuilder("Hello"); sb.append(" World"); // "Hello World" sb.insert(5, ","); // "Hello, World" sb.delete(5, 6); // "Hello World" sb.replace(6,11,"Java"); // "Hello Java" sb.reverse(); // "avaJ olleH" sb.deleteCharAt(0); // "vaJ olleH" // Length and capacity sb.length() // current content length sb.capacity() // internal buffer size (auto-grows) // StringBuffer — thread-safe version of StringBuilder // Use StringBuilder unless you share between threads

When the compiler optimizes String + automatically

// In Java 9+, the compiler uses StringConcatFactory // Single-line concatenation is already efficient: String s = first + " " + last + " age:" + age; // No manual StringBuilder needed // Use StringBuilder for: // - Loop-based building // - Conditional appending // - Building in multiple methods // String.join for simple delimiter joining String.join(", ", "Alice", "Bob", "Carol"); // "Alice, Bob, Carol" // Collectors.joining for streams names.stream().collect(Collectors.joining(", ", "[", "]")); // "[Alice, Bob, Carol]"

String Formatting — printf style and modern approaches

// String.format() — create formatted string String s = String.format( "%-10s age:%3d score:%.2f", "Alice", 30, 98.5 ); // "Alice age: 30 score:98.50" // System.out.printf — print formatted System.out.printf("Name: %s, Age: %d%n", name, age); // Common format specifiers: // %s — String (calls toString) // %d — int / long // %f — float / double // %.2f — 2 decimal places // %5d — right-aligned in 5 chars // %-5d — left-aligned in 5 chars // %05d — zero-padded // %n — platform newline // %b — boolean // %x — hex // %o — octal
// formatted() — Java 15+ instance method String msg = "Hello %s, you are %d" .formatted("Bob", 25); // String.format vs formatted — same result // formatted() is slightly cleaner // Locale-aware formatting String.format(Locale.US, "%.2f", 1234.5); // "1234.50" String.format(Locale.GERMAN, "%.2f", 1234.5); // "1234,50" (comma as decimal separator) // NumberFormat for currency NumberFormat.getCurrencyInstance().format(1234.5); // "$1,234.50" in US locale

Text Blocks — multi-line strings (Java 15+)

// Old way — escape-heavy String json = "{\n" + " \"name\": \"Alice\",\n" + " \"age\": 30\n" + "}"; // Text block — clean multi-line String json = """ { "name": "Alice", "age": 30 } """; // Opening """ must be followed by newline // Closing """ sets indentation baseline // Common leading whitespace is stripped
// Text blocks for HTML, SQL, JSON String html = """ <html> <body> <p>Hello, %s!</p> </body> </html> """.formatted("World"); String sql = """ SELECT u.name, o.total FROM users u JOIN orders o ON u.id = o.user_id WHERE u.active = true AND o.total > :minTotal ORDER BY o.created_at DESC """; // Escape sequences still work // \n \t \" still valid inside text block // \ at end of line = line continuation (no newline)
