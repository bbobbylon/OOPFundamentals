Signals ↔ RxJS — Living Together

Angular now has two reactive systems. They're not rivals — they're pull vs push, each best at different jobs. Here's when to use which, and how toSignal / toObservable bridge them at the seams of your app.

🔁 Signals vs RxJS — why you need both, and how they talk to each other

Angular ships two reactive primitives, and they're not replacements for each other — they solve different problems. Signals are pull-based synchronous state: a current value you can read any time, with Angular efficiently updating the DOM when it changes. Observables are push-based async streams: events and data arriving over time (HTTP, WebSocket, route events). Real apps have both, so the skill is moving data between them cleanly.

  • Signals = synchronous "what's the value now?" state — selected tab, loading flag, current user, role list.
  • Observables = asynchronous "values over time" — HTTP, WebSocket, debounced search, Router/FormControl streams.
  • toSignal(obs$) subscribes and wraps a stream as a signal — and auto-unsubscribes on destroy.
  • toObservable(sig) turns a signal into a stream so you can use it in a .pipe() chain.
  • toSignal() replaces a lot of async-pipe + BehaviorSubject boilerplate.

Use signals for UI state

Loading flag, selected tab, modal open/closed, current user, roles — anything the template reads synchronously. Works natively with @if / @for. e.g. who's logged in, which tab is active.

Use RxJS for async streams

HTTP, WebSockets, operator chains (debounce + switchMap + catchError), event buses, Router / valueChanges — all observable streams. e.g. HTTP, routing, search-as-you-type.

Bridge: toSignal / toObservable

toSignal(obs$) wraps a stream as a signal (auto-unsubscribes on destroy); toObservable(sig) turns a signal into a stream for .pipe(). toSignal() replaces async-pipe + BehaviorSubject.

In CIAM:const user = toSignal(authService.getUser$()) — the HTTP stream fetches the user and toSignal wraps it so the template reads user()?.name synchronously, no async pipe. Guards read user()?.roles; the interceptor reads the token via tokenService.token() — a signal, not a subscription.

1. Two reactive primitives, two shapes of "reactive"

The single most useful thing to internalize: a SIGNAL = pull always holds a current value you read synchronously; an OBSERVABLE = push is a stream that hands you values over time when it decides.

Signal (pull)Observable (push)
Has a value right now?✅ always — count() reads it❌ not until it emits
Time dimensionjust "current state"a stream of events over time
Starts when?eager, always livelazy — nothing runs until you subscribe
Teardownnone to managemust unsubscribe (leaks otherwise)
Operatorscomputed (derive)100+ (debounce, switchMap, retry…)
Glitch-free?✅ diamond deps resolve once⚠️ combineLatest can double-fire
Great forsynchronous UI stateasync events, time, coordination

Rule of thumb: state → signal, events/async → observable. Most components want signals for the template and RxJS for the plumbing that feeds them.

2. The two bridges

toSignal() — observable → signal

Subscribes for you and exposes the latest value as a signal. Angular auto-unsubscribes when the injection context (component) is destroyed — no ngOnDestroy, no async pipe needed.

private http = inject(HttpClient);

// stream → signal you can read synchronously
user = toSignal(
  this.http.get<User>('/api/me'),
  { initialValue: null }   // else type is User | undefined
);
// template:  {{ user()?.name }}

Reads like state, but it's really your HTTP stream. requireSync:true if the source emits synchronously (e.g. a BehaviorSubject).

toObservable() — signal → observable

Turns a signal into a stream so you can use RxJS operators on it. Under the hood it uses an effect to emit whenever the signal changes.

query = signal('');

results$ = toObservable(this.query).pipe(
  debounceTime(300),
  distinctUntilChanged(),
  switchMap(q => this.api.search(q))
);
// …and often back again:
results = toSignal(this.results$, { initialValue: [] });

This "signal → observable → operators → signal" round-trip is the canonical interop pattern. You'll build it live below.

4. effect() vs .subscribe()

effect() — reacts to signals

effect(() => {
  // re-runs whenever any signal READ here changes
  console.log('count is', this.count());
  localStorage.setItem('c', this.count());
});
  • Auto-tracks dependencies — no manual wiring.
  • Auto-cleans up on destroy.
  • For side effects only — don't set other signals in it (use computed to derive).

subscribe() — reacts to streams

this.socket$
  .pipe(takeUntilDestroyed())  // ← or you leak
  .subscribe(msg => this.handle(msg));
  • You manage teardown (takeUntilDestroyed(), async pipe, or manual unsubscribe).
  • Gives you the full operator pipeline before the callback.
  • Right when the timing/coordination is the hard part.

5. Which one do I reach for?

Reach for a SIGNAL when…

  • It's component/UI state: form values, toggles, selected row.
  • You want a value readable synchronously in the template or a method.
  • You're deriving from other state → computed.
  • You want zoneless-friendly, fine-grained updates.

Reach for RxJS when…

  • There's a time axis: debounce, throttle, intervals, retries.
  • You're cancelling/switching async work → switchMap.
  • You're combining multiple async sources with backpressure.
  • The source is a stream: WebSocket, SSE, router events.

In practice: do the async, time-based work in RxJS, then toSignal at the very edge so your template only ever touches simple, synchronous signals.

6. Interop gotchas

GotchaWhyFix
toSignal value is T | undefinedNo emission has arrived yetPass { initialValue }, or requireSync:true for sync sources
"can only be used within an injection context"toSignal/toObservable need DI context for cleanupCall them in a field initializer / constructor, or pass an injector
toSignal subscribes immediatelyIt's eager (unlike a template async pipe that waits for render)Fine usually; be aware it fires the HTTP at construction
Writing a signal inside effect warns/loopsEffects are for side effects, not deriving stateUse computed; or allowSignalWrites only if you must
Lost values between signal changesSignals only keep the latest — intermediate values are droppedIf you need every value, keep it an Observable until after the operators

7. One-sentence recap

🔁 Signals are pull-based always-current state (great for templates & computed); Observables are push-based streams over time (great for debounce/switchMap/cancellation) — use toObservable to run RxJS operators on a signal and toSignal to land the result back as synchronous state, doing the time-based work in RxJS and exposing only signals to your view.
