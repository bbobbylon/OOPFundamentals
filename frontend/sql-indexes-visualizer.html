Indexes & Query Plans

B-tree indexes, composite indexes, covering indexes — and how EXPLAIN shows you what the planner chose.

📇 What are database indexes — and why does one missing index turn a fast query into a multi-second scan?

Without an index a query does a sequential scan — every row, every time (10M comparisons on a 10M-row table). An index is a side structure that jumps straight to matching rows, like a book's index. The default B-tree serves equality, range, sort and prefix (LIKE 'foo%') — but not leading-wildcard LIKE '%foo' or LOWER(col) without a functional index. A composite index on (a, b) follows the leftmost-prefix rule (helps a or a,b, not b alone); a covering index answers a query from the index alone (index-only scan). EXPLAIN ANALYZE is the key tool — look for Seq Scan (often bad) vs Index Scan/Index Only Scan (good).

  • No index = sequential scan — every row; an index jumps to matches.
  • B-tree serves =/range/sort/prefix — not %foo or LOWER() (needs functional index).
  • Composite = leftmost-prefix; a covering index gives an index-only scan.
  • EXPLAIN ANALYZE — Seq Scan bad, Index Scan good; too many indexes slow writes.

Index types

-- B-tree (default): equality + range CREATE INDEX idx_users_email ON users (email); -- Unique index (also enforces uniqueness): CREATE UNIQUE INDEX idx_users_email_unique ON users (email); -- Composite index (leftmost prefix rule): CREATE INDEX idx_users_active_created ON users (active, created_at DESC); -- Helps: WHERE active = true ORDER BY created_at DESC -- Helps: WHERE active = true (uses first column) -- DOES NOT help: WHERE created_at > '2024-01-01' -- Partial index (only index relevant rows): CREATE INDEX idx_sessions_active ON sessions (expires_at) WHERE revoked = false; -- Much smaller index — only active sessions -- GIN index for JSONB: CREATE INDEX idx_audit_metadata ON audit_events USING GIN (metadata);

EXPLAIN ANALYZE

Full scan (actual rows=2000000 time=210ms) -> Bitmap Heap Scan on users -> Bitmap Index Scan on idx_users_active -- Fix: add index on sessions.user_id CREATE INDEX idx_sessions_user_id ON sessions (user_id); -- After index: -- Hash Right Join with Index Scan on sessions -- 210ms → 3ms

Index pitfalls

Function on indexed column: WHERE LOWER(email) = 'bob@eg.com' can't use index on email. Fix: create functional index: CREATE INDEX ON users (LOWER(email)) or store emails already lowercased. NULL behavior: B-tree indexes include NULL values — WHERE col IS NULL can use an index. LIKE with wildcard: LIKE '%foo' can't use B-tree (prefix unknown). LIKE 'foo%' CAN use B-tree. For arbitrary substring: use GIN + pg_trgm extension. Too many indexes slow writes: every INSERT/UPDATE/DELETE must update ALL indexes on the table. A table with 20 indexes has 20x the write overhead vs no indexes. Rule: index columns that appear in WHERE, JOIN ON, ORDER BY of slow queries. Don't pre-emptively index everything. JPA N+1: not an index issue but equally important — @ManyToMany without fetch = EAGER or JOIN FETCH causes N+1 queries: 1 query for users, then N queries for their roles. Fix: @Query("SELECT u FROM User u JOIN FETCH u.roles").

CIAM index strategy: Essentials — UNIQUE INDEX ON users (email) (login + uniqueness); UNIQUE INDEX ON users (idp_type, external_id) (lookup by Ping subject / Entra OID); INDEX ON sessions (user_id, expires_at) WHERE revoked = false (partial, active-session lookups); INDEX ON audit_events (user_id, created_at DESC) (recent-first history); INDEX ON user_roles (user_id) (role JOIN). Turn on spring.jpa.show-sql, run EXPLAIN ANALYZE on slow queries, and add an index wherever a Seq Scan hits a 1000+ row table with a selective WHERE.

1 — How B-tree Indexes Work




A B-tree index is a separate on-disk structure ordered by the indexed column(s). The tree is typically 3-4 levels deep for millions of rows — instead of scanning every page you traverse ~3 pages to find the target, then fetch the heap page.


-- Create an index
CREATE INDEX idx_users_email ON users (email);
CREATE UNIQUE INDEX idx_users_email_uniq ON users (email);

-- Partial index: only index active users (smaller, faster)
CREATE INDEX idx_active_users ON users (created_at)
  WHERE active = true;

-- Expression index: index on a computed value
CREATE INDEX idx_lower_email ON users (LOWER(email));
-- Now this uses the index:
SELECT * FROM users WHERE LOWER(email) = 'alice@ex.com';









2 — Composite Index Column Order




A composite index (a, b) is sorted by a first, then b within equal a values. The leading column rule: a query can only use the index if it filters on the leftmost column(s).


CREATE INDEX idx_orders_user_status ON orders (user_id, status);

-- USES the index (leading column user_id matches)
WHERE user_id = 42
WHERE user_id = 42 AND status = 'pending'

-- Does NOT use the index (skips leading column)
WHERE status = 'pending'   -- index scan on status alone? No.

-- Rule of thumb: put high-cardinality, equality columns first
-- Then range columns. user_id (equality) before status (range).









3 — Covering Index (Index-Only Scan)




If the index contains ALL columns the query needs (via INCLUDE), PostgreSQL does an index-only scan — no heap page fetch needed. This is dramatically faster for read-heavy workloads.


-- Without covering: index scan + heap fetch for email
CREATE INDEX idx_users_active ON users (active, created_at);

-- With covering: no heap fetch needed
CREATE INDEX idx_users_active_cov ON users (active, created_at)
  INCLUDE (id, email);  -- INCLUDE stores extra cols in leaf pages

-- This query now does an index-only scan:
SELECT id, email FROM users
WHERE active = true AND created_at > '2024-01-01';









4 — Reading EXPLAIN ANALYZE




EXPLAIN ANALYZE
SELECT * FROM users WHERE email = 'alice@ex.com';

-- With index:
-- Index Scan using idx_users_email on users  (cost=0.42..8.44 rows=1)
--   (actual time=0.032..0.034 rows=1 loops=1)
--   Index Cond: (email = 'alice@ex.com')
-- Planning Time: 0.1 ms
-- Execution Time: 0.1 ms

-- Without index:
-- Seq Scan on users  (cost=0.00..1842.00 rows=1 width=52)
--   (actual time=12.3..18.4 rows=1 loops=1)
--   Filter: (email = 'alice@ex.com')
--   Rows Removed by Filter: 99999
-- Execution Time: 18.5 ms
