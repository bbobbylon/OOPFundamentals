Indexes & Query Plans

B-tree indexes, composite indexes, covering indexes — and how EXPLAIN shows you what the planner chose.

📇 What are database indexes — and why does one missing index turn a fast query into a multi-second scan?

Without an index a query does a sequential scan — every row, every time (10M comparisons on a 10M-row table). An index is a side structure that jumps straight to matching rows, like a book's index. The default B-tree serves equality, range, sort and prefix (LIKE 'foo%') — but not leading-wildcard LIKE '%foo' or LOWER(col) without a functional index. A composite index on (a, b) follows the leftmost-prefix rule (helps a or a,b, not b alone); a covering index answers a query from the index alone (index-only scan). EXPLAIN ANALYZE is the key tool — look for Seq Scan (often bad) vs Index Scan/Index Only Scan (good).

  • No index = sequential scan — every row; an index jumps to matches.
  • B-tree serves =/range/sort/prefix — not %foo or LOWER() (needs functional index).
  • Composite = leftmost-prefix; a covering index gives an index-only scan.
  • EXPLAIN ANALYZE — Seq Scan bad, Index Scan good; too many indexes slow writes.

Index types

-- B-tree (default): equality + range CREATE INDEX idx_users_email ON users (email); -- Unique index (also enforces uniqueness): CREATE UNIQUE INDEX idx_users_email_unique ON users (email); -- Composite index (leftmost prefix rule): CREATE INDEX idx_users_active_created ON users (active, created_at DESC); -- Helps: WHERE active = true ORDER BY created_at DESC -- Helps: WHERE active = true (uses first column) -- DOES NOT help: WHERE created_at > '2024-01-01' -- Partial index (only index relevant rows): CREATE INDEX idx_sessions_active ON sessions (expires_at) WHERE revoked = false; -- Much smaller index — only active sessions -- GIN index for JSONB: CREATE INDEX idx_audit_metadata ON audit_events USING GIN (metadata);

EXPLAIN ANALYZE

EXPLAIN ANALYZE SELECT u.email, COUNT(s.id) as session_count FROM users u LEFT JOIN sessions s ON u.id = s.user_id WHERE u.active = true GROUP BY u.id, u.email; -- Output: HashAggregate (cost=... rows=1000) -> Hash Right Join (actual rows=50000 time=45ms) Hash Cond: (s.user_id = u.id) -> Seq Scan on sessions ← BAD! Full scan (actual rows=2000000 time=210ms) -> Bitmap Heap Scan on users -> Bitmap Index Scan on idx_users_active -- Fix: add index on sessions.user_id CREATE INDEX idx_sessions_user_id ON sessions (user_id); -- After index: -- Hash Right Join with Index Scan on sessions -- 210ms → 3ms

Index pitfalls

Function on indexed column: WHERE LOWER(email) = 'bob@eg.com' can't use index on email. Fix: create functional index: CREATE INDEX ON users (LOWER(email)) or store emails already lowercased. NULL behavior: B-tree indexes include NULL values — WHERE col IS NULL can use an index. LIKE with wildcard: LIKE '%foo' can't use B-tree (prefix unknown). LIKE 'foo%' CAN use B-tree. For arbitrary substring: use GIN + pg_trgm extension. Too many indexes slow writes: every INSERT/UPDATE/DELETE must update ALL indexes on the table. A table with 20 indexes has 20x the write overhead vs no indexes. Rule: index columns that appear in WHERE, JOIN ON, ORDER BY of slow queries. Don't pre-emptively index everything. JPA N+1: not an index issue but equally important — @ManyToMany without fetch = EAGER or JOIN FETCH causes N+1 queries: 1 query for users, then N queries for their roles. Fix: @Query("SELECT u FROM User u JOIN FETCH u.roles").

CIAM index strategy: Essentials — UNIQUE INDEX ON users (email) (login + uniqueness); UNIQUE INDEX ON users (idp_type, external_id) (lookup by Ping subject / Entra OID); INDEX ON sessions (user_id, expires_at) WHERE revoked = false (partial, active-session lookups); INDEX ON audit_events (user_id, created_at DESC) (recent-first history); INDEX ON user_roles (user_id) (role JOIN). Turn on spring.jpa.show-sql, run EXPLAIN ANALYZE on slow queries, and add an index wherever a Seq Scan hits a 1000+ row table with a selective WHERE.

The problem

Your login query reads ten million rows to find one.

The login lookup nobody indexed

SELECT id, password_hash FROM users WHERE email = ? — with no index on email, the database has exactly one strategy available: read the entire users table, compare every row, throw away all but one. On 10 million users that is roughly 12,500 eight-kilobyte pages dragged through memory per sign-in.

Seq Scan on users rows=10,000,000 Rows Removed by Filter: 9,999,999 ⚠ …and again on the next login ⚠

It passed code review, it passed the integration suite, it was instant in dev. Of course it was — dev had 4,000 users. The defect was never in the SQL. The defect was the row count, and the row count is the one thing your laptop never has.

Give the database a sorted side-copy and a pointer
CREATE INDEX idx_users_email ON users (email); ↓ every email now lives in a B-tree, in sorted order, next to the row's address root page → branch page → leaf page ↓ three binary searches, three page reads, no comparison wasted leaf holds the ctid → one heap fetch → your row ↓ 12,500 pages became 4 18 ms → 0.1 ms, and it stays 0.1 ms at 100 million rows
An index doesn't make your query faster. It makes your query read less. Everything else — B-trees, leftmost prefixes, covering indexes, EXPLAIN — is bookkeeping in service of that one sentence. And the payoff scales the wrong way round from your intuition: the bigger the table gets, the more the index wins, because a scan grows with the table and a tree grows with the logarithm of it. Ten times the users costs a seq scan ten times more work and costs the B-tree roughly one extra page.
The planner

email = ? on ten million rows. Scan is 12,500 pages; idx_users_email is about four. I did not agonise over this.

The B-tree

Because I keep every email sorted, and every leaf entry carries the physical address of its row. I am not the data. I am a signpost that happens to be alphabetised.

Every INSERT on this table

And I pay for all of it. One new user is one row written — plus one entry threaded into you, and into the other six indexes somebody added "just in case", and a page split when a leaf fills up. Reads are the party. Writes get the bill.

The mechanism

A composite index is a phone book: surname first, then first name.

  1. WHERE tenant_id = 7 — the leading column is pinned, so the tree can seekindex used
  2. … AND status = 'ACTIVE' — column 2, with column 1 still pinnedindex used, and now narrower
  3. … AND created_at > '2026-01-01' — column 3, a range on the tailthe whole index earns its keep
  4. WHERE status = 'ACTIVE' on its own — column 1 was skippedSeq Scan. The index is right there, and useless.

Here is the part everyone re-learns the hard way: you may drop columns off the right end of the list as often as you like, and you may never skip one on the left. (a, b, c) serves a, and a,b, and a,b,c — and does nothing whatsoever for b alone.

The phone book is the memory hook, so use it. It is sorted by surname, then first name. "Find every Nakamura" — you open it near the N's and you are done. "Find every Nakamura called Kenji" — same page, the Kenjis are already grouped together, because within one surname the book is sorted by first name. Now: "find everyone called Steve." You read the entire book, cover to cover, because a book sorted by (surname, first name) is simply not sorted by first name. Postgres is not being awkward when it picks a Seq Scan for WHERE status = 'ACTIVE' — it is telling you the truth about what sorted order it actually has. The order in CREATE INDEX is the order of the book, and you cannot read a book from the middle of a word.

The same logic explains the trap that eats an afternoon: WHERE UPPER(email) = ? with an index on email. Your index is a list sorted by the raw stored value — 'Alice@ex.com', 'bob@ex.com', 'Zoe@ex.com'. Apply UPPER() and that is a different sequence, one nobody ever sorted. The planner will only reach for an index whose expression matches your predicate exactly, so either index the expression itself — CREATE INDEX ON users (UPPER(email)) — or, better in CIAM, store the address already normalised at registration and stop calling the function at all. A function wrapped around an indexed column throws the index away silently: no error, no warning, just a query that got 200× slower on the day the table grew.

Login is SELECT id, password_hash FROM users WHERE LOWER(email) = ? and you already have CREATE INDEX ON users (email). EXPLAIN ANALYZE still reports a Seq Scan over 8 million rows. Which change actually gets you an index scan?

Right. The index has to be sorted by the exact thing you are comparing. Build it on LOWER(email) and the predicate matches the index expression, so the tree can seek again. The alternative — and the better answer in a CIAM system, where email comparison is case-insensitive anyway — is to normalise on the way in and drop LOWER() from the query entirely.

Fresh statistics help the planner choose well among the plans that exist. Here no index-scan plan exists at all: your index is sorted by email, and nothing in that WHERE clause is email — it is LOWER(email), a value the index has never seen.

You would be adding a second copy of an index this query already cannot use — no new reads served, and one more B-tree that every signup, every profile edit and every password reset now has to update. Pure cost.

Questions from the back row

So how many indexes is too many?

There is no number, but there is a measurement: SELECT indexrelname, idx_scan FROM pg_stat_user_indexes. Any index sitting at idx_scan = 0 after a full production week is a tax you pay on every single write, forever, for a read that never comes. Drop it (DROP INDEX CONCURRENTLY) and watch nothing break. The right instinct is not "index the columns" — it is "index the queries", and only the slow ones.

The index exists and EXPLAIN still says Seq Scan. Is Postgres broken?

Usually it is right and you are annoyed. An index scan is random I/O: seek the tree, then jump to a scattered heap page per match. If your predicate matches half the table, doing that four million times is genuinely slower than reading the table sequentially. Selectivity is the whole game — an index on a boolean active column where 95% of rows are true earns nothing. Same for tiny tables: scanning 200 rows beats traversing anything. It is worth suspecting the planner when estimated rows and actual rows differ by orders of magnitude — that is stale statistics, and ANALYZE is the fix.

Does the order I write the conditions in the WHERE clause matter?

No, and this is the most common mix-up on this whole page. WHERE status = 'ACTIVE' AND tenant_id = 7 and WHERE tenant_id = 7 AND status = 'ACTIVE' are the same query; the planner reorders predicates freely. The order that is load-bearing is the one inside CREATE INDEX (tenant_id, status) — that one is physical, written to disk, and changing it means building a new index.

What is a "covering" index actually covering?

Your SELECT list. Normally the index gets you a row address and then the database still fetches the heap page to read the columns. If every column the query needs is already in the index — as a key column, or bolted on with INCLUDE (id, email) — there is nothing left to fetch, and EXPLAIN says Index Only Scan. That is two I/Os per row collapsing into one. The catch: Postgres still checks the visibility map, so a table that has just been heavily updated and not yet vacuumed will quietly go back to touching the heap.

1 — How B-tree Indexes Work




A B-tree index is a separate on-disk structure ordered by the indexed column(s). The tree is typically 3-4 levels deep for millions of rows — instead of scanning every page you traverse ~3 pages to find the target, then fetch the heap page.


-- Create an index
CREATE INDEX idx_users_email ON users (email);
CREATE UNIQUE INDEX idx_users_email_uniq ON users (email);

-- Partial index: only index active users (smaller, faster)
CREATE INDEX idx_active_users ON users (created_at)
  WHERE active = true;

-- Expression index: index on a computed value
CREATE INDEX idx_lower_email ON users (LOWER(email));
-- Now this uses the index:
SELECT * FROM users WHERE LOWER(email) = 'alice@ex.com';









2 — Composite Index Column Order




A composite index (a, b) is sorted by a first, then b within equal a values. The leading column rule: a query can only use the index if it filters on the leftmost column(s).


CREATE INDEX idx_orders_user_status ON orders (user_id, status);

-- USES the index (leading column user_id matches)
WHERE user_id = 42
WHERE user_id = 42 AND status = 'pending'

-- Does NOT use the index (skips leading column)
WHERE status = 'pending'   -- index scan on status alone? No.

-- Rule of thumb: put high-cardinality, equality columns first
-- Then range columns. user_id (equality) before status (range).









3 — Covering Index (Index-Only Scan)




If the index contains ALL columns the query needs (via INCLUDE), PostgreSQL does an index-only scan — no heap page fetch needed. This is dramatically faster for read-heavy workloads.


-- Without covering: index scan + heap fetch for email
CREATE INDEX idx_users_active ON users (active, created_at);

-- With covering: no heap fetch needed
CREATE INDEX idx_users_active_cov ON users (active, created_at)
  INCLUDE (id, email);  -- INCLUDE stores extra cols in leaf pages

-- This query now does an index-only scan:
SELECT id, email FROM users
WHERE active = true AND created_at > '2024-01-01';
