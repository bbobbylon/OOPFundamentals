Async JavaScript — Callbacks, Promises, async/await & fetch()

JavaScript runs on ONE thread with ONE call stack — so how does it ever wait for a network request without freezing the page? This is the mental model that makes fetch(), Angular's HttpClient/RxJS Observables, and every async Spring Boot call your frontend makes actually make sense.

⏱️ What is "async JavaScript," and why does it matter?

JavaScript executes on a single thread — one call stack, one thing happening at a time. If a function took 3 seconds to run synchronously, your entire tab would freeze for 3 seconds: no scrolling, no clicks, no re-paints. Async JavaScript is how the language does long-running work — network requests, timers, file reads — without blocking that one thread. The browser hands slow work off to its own Web APIs, and JavaScript is notified later, through a queue, once the call stack is empty. Understanding callbacks → Promises → async/await is understanding three generations of the same idea: "run this code later, when the result is ready." This is not academic — it is exactly the model underneath every fetch() call to a login endpoint, every Angular HttpClient request, and every RxJS Observable you will ever write. Get the event loop right here, and Angular's async patterns stop feeling like magic.

  • One thread, one call stack — synchronous code always finishes before any async callback runs.
  • Callbacks → Promises → async/await is the same idea, getting more readable each generation.
  • Microtasks (Promises) always drain before the next macrotask (setTimeout) — a real ordering rule, not a detail.
  • fetch() only rejects on network failure — a 404 or 500 is still a "successful" fetch you must check yourself.

The problem it solves

Without async handling, waiting for a 300ms API response would freeze the whole browser tab for 300ms — no scrolling, no other JS running, nothing. Async lets the thread stay free while work happens elsewhere.

The three eras

Callbacks (pass a function to call later — nests badly) → Promises (an object representing a future value — chains with .then()) → async/await (Promises, but written to read top-to-bottom like sync code).

Angular / Spring tie-in

Angular's HttpClient returns RxJS Observables — a cousin of Promises built for streams of values over time. Every subscribe() call you'll write in Angular assumes you already understand this page.

CIAM angle: a login form's fetch('/api/auth/login', ...) call is a Promise from the moment you press submit to the moment a JWT comes back (or an error does) — and that Promise settling incorrectly-handled (ignoring response.ok, or forgetting await) is a real, common source of "login silently does nothing" bugs.

1. Callbacks: the original async pattern (and its problem)

Before Promises existed, "run this later" meant passing a function — a callback — to be invoked once the async work finished. It works, but nesting several in sequence produces the infamous "pyramid of doom":

login(username, password, (err, user) => { if (err) return handleError(err); fetchProfile(user.id, (err, profile) => { if (err) return handleError(err); fetchSettings(user.id, (err, settings) => { if (err) return handleError(err); render(user, profile, settings); }); }); });
Key insight: every level needs its own error check, indentation grows with every step, and there is no single place to catch a failure from ANY step. This exact pain — not aesthetics — is why Promises were added to the language in ES6.

2. Promises: one object, three states, chainable

A Promise represents a value that doesn't exist yet. It starts pending, then settles exactly once — either fulfilled (success) or rejected (failure) — and every listener attached with .then()/.catch() fires off that single settlement:

login(username, password) .then(user => fetchProfile(user.id)) .then(profile => fetchSettings(profile.userId)) .then(settings => render(settings)) .catch(err => handleError(err)); // ← ONE catch for the whole chain
Key insight: .then() flattens nesting into a linear chain, and .catch() at the end catches a rejection from any step in the chain — one error path instead of one per level.

3. async/await: Promises, written like synchronous code

async/await is syntactic sugar over Promises — nothing new happens at runtime, but the code reads top-to-bottom like ordinary synchronous code, and errors use ordinary try/catch:

async function loadDashboard(username, password) { try { const user = await login(username, password); const profile = await fetchProfile(user.id); const settings = await fetchSettings(user.id); render(user, profile, settings); } catch (err) { handleError(err); } } // an `async function` ALWAYS returns a Promise, even if you `return` a plain value
Key insight: await only pauses the function it's inside — not the whole program. The rest of the page keeps rendering and handling clicks while this function is "paused" waiting on a Promise.
