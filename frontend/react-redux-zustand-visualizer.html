React: Redux Toolkit & Zustand

The modern Redux (createSlice, configureStore, Immer, RTK Query) and the minimalist alternative (Zustand) — when you need a global store and how each one wires it up.

🗄️ Global state without prop-drilling — the two libraries you'll actually meet

For state shared across distant components you reach for a store. Redux Toolkit (RTK) is official, batteries-included Redux: createSlice defines state + reducers and auto-generates actions; reducers look mutating (state.value += 1) but Immer makes a correct immutable update; configureStore wires it with DevTools. Components read with useSelector (re-render only when the slice changes) and write with useDispatch — a strict, logged, one-way flow great for big apps. RTK Query adds caching data-fetching hooks. Zustand drops the ceremony: create((set) => ({...})) + useStore(s => s.count), no provider/actions/reducers, tiny bundle. Many apps pair TanStack Query (server state) with a small Zustand store for the client state left over.

  • RTK = createSlice + Immer — mutating-looking reducers, immutable result.
  • useSelector re-renders narrowly — only when the selected slice changes.
  • One-way logged flow — dispatch → reducer → state → selector → render.
  • Zustand = no ceremony; pair with TanStack Query for server state.

RTK slice

const auth = createSlice({ name: 'auth', initialState: { user: null, roles: [] }, reducers: { loggedIn(state, action) { state.user = action.payload.user // Immer state.roles = action.payload.roles }, loggedOut(state) { state.user = null }, }, }) export const { loggedIn, loggedOut } = auth.actions

Read & write

const roles = useSelector(s => s.auth.roles) const dispatch = useDispatch() dispatch(loggedIn({ user, roles })) // re-renders ONLY when s.auth.roles changes

Zustand (no boilerplate)

const useAuth = create((set) => ({ user: null, roles: [], login: (u, r) => set({ user: u, roles: r }), logout: () => set({ user: null }), })) // in a component — no Provider needed: const roles = useAuth(s => s.roles)

CIAM context: An authSlice holds the token, current user, and roles; a memoized selector selectIsAdmin = s => s.auth.roles.includes('ROLE_ADMIN') drives role-gated UI, and every login/logout is a logged action you can replay in DevTools. The admin users list belongs in RTK Query / TanStack Query with cache invalidation, not hand-managed in a slice. A lighter app covers the same auth state with one Zustand useAuth store at a fraction of the code.

1. createSlice — State + Reducers + Actions in One

const counter = createSlice({
  name: 'counter',
  initialState: { value: 0 },
  reducers: {
    increment(state) { state.value++ }, // Immer
    addBy(state, action) { state.value += action.payload }
  }
})
export const { increment, addBy } = counter.actions

One createSlice replaces the old action-types + action-creators + switch-reducer trio. It infers action creators from the reducer names. The "mutating" syntax is safe: RTK wraps reducers in Immer, which records your mutations on a draft and returns a brand-new immutable state — you get immutability without spread-operator gymnastics.

Immer's one rule: mutate the draft or return a new value — never both. state.x = 1 ✓; return {...state, x:1} ✓; doing both in one reducer throws. And don't mutate then return the same draft.

2. The One-Way Data Flow

const store = configureStore({ reducer: { counter: counter.reducer, auth: auth.reducer } })

// component:
const value = useSelector(s => s.counter.value) // subscribe
const dispatch = useDispatch()
<button onClick={() => dispatch(increment())}>+1</button>
// dispatch → reducer → new state → selector recomputes → re-render
useSelector re-renders when its selected value changes by reference (default ===). Returning a fresh object/array every time (s => ({a:s.a})) re-renders on every action — use a memoized selector (Reselect's createSelector) or select primitives. Wrap the app once in <Provider store={store}>.

3. RTK Query — Server State, Cached

const api = createApi({
  baseQuery: fetchBaseQuery({ baseUrl: '/api' }),
  tagTypes: ['User'],
  endpoints: (b) => ({
    getUsers: b.query({ query: () => '/admin/users', providesTags: ['User'] }),
    addUser: b.mutation({ query: u => ({url:'/users',method:'POST',body:u}), invalidatesTags:['User'] })
  })
})
const { data, isLoading } = api.useGetUsersQuery() // generated hook

createApi generates typed hooks with caching, deduping, loading/error flags, and tag-based invalidation: a mutation that invalidatesTags:['User'] auto-refetches any query that providesTags:['User']. It's RTK's answer to server-state — overlapping with TanStack Query. Pick one data layer; don't store server data in slices by hand.

Separate server state from client state. Server data (lists, entities) belongs in a caching layer (RTK Query / TanStack Query) that handles staleness and refetching. Slices/Zustand are for genuine client state (UI flags, the current user, a wizard step) that no server owns.

4. Zustand — Minimal Global State

const useAuth = create((set, get) => ({
  user: null, roles: [],
  login: (u, r) => set({ user: u, roles: r }),
  logout: () => set({ user: null, roles: [] }),
  isAdmin: () => get().roles.includes('ROLE_ADMIN'),
}))

// component — no Provider:
const roles = useAuth(s => s.roles) // selective subscribe

create returns a hook that is the store. Pass a selector to subscribe to just a slice (re-renders only when that slice changes). Actions are plain functions that call set. No provider, no reducers, no action constants — and it lives outside React, so non-component code can read/update it via useAuth.getState()/setState().
