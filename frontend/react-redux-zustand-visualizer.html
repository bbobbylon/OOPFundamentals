React: Redux Toolkit & Zustand

The modern Redux (createSlice, configureStore, Immer, RTK Query) and the minimalist alternative (Zustand) — when you need a global store and how each one wires it up.

🗄️ Global state without prop-drilling — the two libraries you'll actually meet

For state shared across distant components you reach for a store. Redux Toolkit (RTK) is official, batteries-included Redux: createSlice defines state + reducers and auto-generates actions; reducers look mutating (state.value += 1) but Immer makes a correct immutable update; configureStore wires it with DevTools. Components read with useSelector (re-render only when the slice changes) and write with useDispatch — a strict, logged, one-way flow great for big apps. RTK Query adds caching data-fetching hooks. Zustand drops the ceremony: create((set) => ({...})) + useStore(s => s.count), no provider/actions/reducers, tiny bundle. Many apps pair TanStack Query (server state) with a small Zustand store for the client state left over.

  • RTK = createSlice + Immer — mutating-looking reducers, immutable result.
  • useSelector re-renders narrowly — only when the selected slice changes.
  • One-way logged flow — dispatch → reducer → state → selector → render.
  • Zustand = no ceremony; pair with TanStack Query for server state.

RTK slice

const auth = createSlice({ name: 'auth', initialState: { user: null, roles: [] }, reducers: { loggedIn(state, action) { state.user = action.payload.user // Immer state.roles = action.payload.roles }, loggedOut(state) { state.user = null }, }, }) export const { loggedIn, loggedOut } = auth.actions

Read & write

const roles = useSelector(s => s.auth.roles) const dispatch = useDispatch() dispatch(loggedIn({ user, roles })) // re-renders ONLY when s.auth.roles changes

Zustand (no boilerplate)

const useAuth = create((set) => ({ user: null, roles: [], login: (u, r) => set({ user: u, roles: r }), logout: () => set({ user: null }), })) // in a component — no Provider needed: const roles = useAuth(s => s.roles)

CIAM context: An authSlice holds the token, current user, and roles; a memoized selector selectIsAdmin = s => s.auth.roles.includes('ROLE_ADMIN') drives role-gated UI, and every login/logout is a logged action you can replay in DevTools. The admin users list belongs in RTK Query / TanStack Query with cache invalidation, not hand-managed in a slice. A lighter app covers the same auth state with one Zustand useAuth store at a fraction of the code.

The problem

Your store is right. Your component is right. The page still ships two different answers to "is anyone logged in?" in one response.

The NavBar that flashes "Sign in" for a user who is already logged in

Take this page's own auth store, wrapped exactly as shown above: create(persist((set) => ({ user: null, ... }), { name: 'auth-storage' })), read inside NavBar with const name = useAuthStore(s => s.user?.name). As a client-only single-page app it's flawless — refresh the page, persist reads localStorage before React even renders, and NavBar shows the real name from the very first frame.

Add server-side rendering (Next.js, Remix, any setup that renders this same component on the server first) and the identical store, the identical component, breaks. On every load where a user is already logged in, the console logs "Hydration failed because the initial UI does not match what was rendered on the server," and NavBar visibly flashes "Sign in" for one frame before snapping to the real name.

the store's logic never changed ✓ the component's code never changed ✓ the SERVER rendering that component has never once seen this browser's localStorage ⚠

persist reads a browser API the server doesn't have — so "first render" quietly means two different things depending which machine is doing the rendering.

The fix: make the server and the client agree on frame one
Render the logged-out state unconditionally on the very first pass, everywhere ↓ a hydration flag starts false on both the server and the client's first render Only switch to the persisted value after that flag flips, inside an effect ↓ an effect never runs on the server, so the server's HTML and the client's FIRST render now describe the same "not hydrated yet" state Or reach for the persist middleware's own hydration API for tighter control ↓ skipHydration at store creation plus a manual rehydrate() call, with hasHydrated() / onFinishHydration() to know exactly when it's safe to show the real data
The server and the client don't share a "first render" — they share a name for two different ones. persist's localStorage-backed hydration is genuinely synchronous, so there's no timing race to lose on the client. The mismatch isn't a race at all: the server's render was built from information — the browser's localStorage — that a server process structurally cannot read. Fixing the timing on the client fixes nothing, because the client was never the side with the problem.
The server is painting your UI from a photograph it was handed at request time — the client is standing in the actual room. When the room has moved since the photo was taken, the client's first frame can never match the photograph, no matter how fast either side works.

It can't. I'm not comparing a fast client to a slow server — I'm comparing the server's HTML to the client's first render, and those two are correctly describing two different things. That's exactly what the hydration warning is for.

The mechanism

Follow one already-logged-in visitor's request all the way to the mismatch.

  1. A browser requests /dashboard; the request carries cookies and headers, never localStorageserver has no access
  2. The server renders NavBar using the Zustand store's plain initial state — user: nullserver render
  3. HTML ships to the browser with "Sign in" already baked into the markupHTML shipped
  4. The browser parses that HTML immediately — same "Sign in" text, first paintfirst paint matches HTML
  5. React boots on the client; persist synchronously reads localStorage and hydrates the store with the real user, before React's own hydration pass reconcilesstore hydrates
  6. React compares the DOM it now wants ("Priya") against the DOM the server actually sent ("Sign in") — mismatch, warning, client-side patchhydration mismatch

Step 5 is the one that's easy to misread: the STORE hydrating fast is exactly what causes the mismatch, not what fixes it. A slower store would have briefly matched the server's HTML by accident. The real fix is making the server and the client's first render describe the same state on purpose, not racing to see who reads localStorage first.

a request for /dashboard arrives at the server
server renders NavBar from the store's plain initial state — no localStorage exists here
HTML ships: "Sign in" — and the browser paints exactly that, first
the client boots, persist() reads the REAL localStorage synchronouslyReact now wants "Priya" on a DOM it already painted as "Sign in" — that gap is the whole warning

Every ring here is correct in isolation — the server correctly had no localStorage, the client correctly read the real one. The core is where those two separately-correct facts collide: nobody made a mistake, and React still has to reconcile two truths that were never going to match on their own.

Your Zustand auth store is wrapped in persist(...) exactly like this page's own example, and NavBar reads const name = useAuthStore(s => s.user?.name). It works perfectly as a client-only SPA. You then add server-side rendering (for example, migrating to Next.js), and now, on every load where a user is already logged in, the console logs "Hydration failed because the initial UI does not match what was rendered on the server," and NavBar briefly flashes "Sign in" before snapping to the real name. What's actually going on?

Not quite — for localStorage (synchronous storage), persist() hydrates before the client's first render every single time. There's no window where it sometimes wins and sometimes loses; the mismatch happens on every logged-in load, deterministically, because the server-side gap is structural, not timing-based.

Right — this isn't a speed problem on either side. The server process was never connected to this browser's localStorage, full stop, so "first render" means something different in each place by construction. Bridging that gap means deliberately rendering the same initial state on both sides until an effect — which never runs on the server — says it's safe to switch.

Keys help React match up siblings in a list — they're not what an SSR hydration check compares. This mismatch is a genuine state difference (null versus a real user) between the server's markup and the client's first render, unrelated to any missing key.

Where you have seen this before

Two processes correctly computing two different answers from two different views of the world shows up everywhere state gets copied across a boundary.

A .env.local file that only exists on one laptop

A CI server and a developer's machine can run the byte-for-byte identical source and still behave differently, because one of them was never going to see a config file the other one has — no bug in the code, just two environments with structurally different inputs.

same code, different available inputs, different correct-for-that-environment output

Per-instance caches behind a load balancer

Two requests to "the same" endpoint can return two different answers depending purely on which server behind the load balancer happens to catch them — each instance's in-memory cache is a perfectly valid view of the world that just isn't the same view the other instance has.

there's no single "first response" when two processes each compute their own

Optimistic UI in a chat app

The sender's own screen marks a message "Sent" immediately from local-only state, a full network round-trip before the server — and everyone else — actually agrees it arrived. For that gap, two different, equally sincere "current states" of the same message coexist.

the local view and the source-of-truth view are allowed to disagree for a while, on purpose

1. createSlice — State + Reducers + Actions in One

const counter = createSlice({
  name: 'counter',
  initialState: { value: 0 },
  reducers: {
    increment(state) { state.value++ }, // Immer
    addBy(state, action) { state.value += action.payload }
  }
})
export const { increment, addBy } = counter.actions

One createSlice replaces the old action-types + action-creators + switch-reducer trio. It infers action creators from the reducer names. The "mutating" syntax is safe: RTK wraps reducers in Immer, which records your mutations on a draft and returns a brand-new immutable state — you get immutability without spread-operator gymnastics.

Immer's one rule: mutate the draft or return a new value — never both. state.x = 1 ✓; return {...state, x:1} ✓; doing both in one reducer throws. And don't mutate then return the same draft.

2. The One-Way Data Flow

const store = configureStore({ reducer: { counter: counter.reducer, auth: auth.reducer } })

// component:
const value = useSelector(s => s.counter.value) // subscribe
const dispatch = useDispatch()
<button onClick={() => dispatch(increment())}>+1</button>
// dispatch → reducer → new state → selector recomputes → re-render
useSelector re-renders when its selected value changes by reference (default ===). Returning a fresh object/array every time (s => ({a:s.a})) re-renders on every action — use a memoized selector (Reselect's createSelector) or select primitives. Wrap the app once in <Provider store={store}>.

3. RTK Query — Server State, Cached

const api = createApi({
  baseQuery: fetchBaseQuery({ baseUrl: '/api' }),
  tagTypes: ['User'],
  endpoints: (b) => ({
    getUsers: b.query({ query: () => '/admin/users', providesTags: ['User'] }),
    addUser: b.mutation({ query: u => ({url:'/users',method:'POST',body:u}), invalidatesTags:['User'] })
  })
})
const { data, isLoading } = api.useGetUsersQuery() // generated hook

createApi generates typed hooks with caching, deduping, loading/error flags, and tag-based invalidation: a mutation that invalidatesTags:['User'] auto-refetches any query that providesTags:['User']. It's RTK's answer to server-state — overlapping with TanStack Query. Pick one data layer; don't store server data in slices by hand.

Separate server state from client state. Server data (lists, entities) belongs in a caching layer (RTK Query / TanStack Query) that handles staleness and refetching. Slices/Zustand are for genuine client state (UI flags, the current user, a wizard step) that no server owns.

4. Zustand — Minimal Global State

const useAuth = create((set, get) => ({
  user: null, roles: [],
  login: (u, r) => set({ user: u, roles: r }),
  logout: () => set({ user: null, roles: [] }),
  isAdmin: () => get().roles.includes('ROLE_ADMIN'),
}))

// component — no Provider:
const roles = useAuth(s => s.roles) // selective subscribe

create returns a hook that is the store. Pass a selector to subscribe to just a slice (re-renders only when that slice changes). Actions are plain functions that call set. No provider, no reducers, no action constants — and it lives outside React, so non-component code can read/update it via useAuth.getState()/setState().
