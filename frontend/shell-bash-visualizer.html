Bash Scripting

A Bash script is just a text file of commands the shell runs top to bottom — the same commands you'd type by hand, saved and repeatable. Add variables, conditionals, and loops and you have a real automation language. This page covers the shebang, the quoting rules that bite everyone, exit codes, and the control flow. (Bash is the default on Linux and macOS, and runs on Windows via WSL/Git Bash.)

What is Bash scripting — and what are the quoting rules, exit codes, and control flow patterns that separate working scripts from frustrating ones?

A Bash script is a text file containing shell commands that run top to bottom when executed. It's the same as typing commands interactively, except they're saved and repeatable. Scripts are used everywhere in DevOps: CI/CD pipelines, server provisioning, deployment automation, log rotation, backup jobs. Every ADO pipeline YAML step that runs script: is executing a Bash (or PowerShell) script. The shebang: the first line #!/bin/bash tells the OS which interpreter to use. Without it, the OS might use /bin/sh (Dash) which lacks Bash features. Always include it. Quoting rules (the biggest source of bugs): double quotes "..." — variable substitution happens, but spaces in values are preserved as a single string; single quotes '...' — nothing is substituted, everything is literal; no quotes — word splitting happens at spaces, which breaks file names with spaces and variable values with spaces. Rule of thumb: always quote variable references: "$var" not $var. Variables: name="Alice" (no spaces around =!), read with $name or ${name}. Special variables: $0 (script name), $1..$9 (positional parameters / arguments), $@ (all args), $# (arg count), $? (last exit code), $$ (current PID). Exit codes: 0 = success, non-zero = failure. This is the fundamental contract of Unix: programs communicate success/failure through exit codes. Scripts should use set -e (exit on any error) and set -u (exit on undefined variable) at the top to fail fast rather than silently proceeding with corrupt state. Control flow: if/elif/else test exit codes and conditions. for loops iterate over lists. while loops run until a condition changes. [ ... ] (test command) evaluates conditions: -f file (file exists), -d dir (directory exists), -z "$var" (var is empty), -n "$var" (var is non-empty), ==/!= (string comparison).

Script skeleton

#!/bin/bash set -euo pipefail # -e: exit on error # -u: exit if unset variable is used # -o pipefail: exit if any pipe command fails # Variables: ENV="${1:-dev}" # positional arg, default "dev" APP_NAME="my-ciam-app" DATE=$(date +%Y%m%d) # command substitution → runs date, captures output echo "Deploying ${APP_NAME} to ${ENV} on ${DATE}" # Conditions: if [ "$ENV" == "prod" ]; then echo "Production deploy — running extra checks" ./run-smoke-tests.sh || { echo "Smoke tests failed!"; exit 1; } elif [ "$ENV" == "staging" ]; then echo "Staging deploy" else echo "Dev deploy" fi # Functions: log() { echo "[$(date +%T)] $*" } log "Build started"

Quoting + common traps

# Quoting trap 1: spaces in values name="John Smith" echo $name # BUG: "John" and "Smith" are two args echo "$name" # CORRECT: "John Smith" is one arg # Quoting trap 2: file names with spaces for f in $(ls); do ... # BUG: breaks on "my file.txt" for f in *; do ... # CORRECT: glob expansion is safe # Arithmetic: count=5 count=$((count + 1)) # = 6 (use $(( )) for math) # String operations: path="/var/log/app.log" echo "{$path##*/}" # = "app.log" (strip longest prefix */…) echo "{$path%/*}" # = "/var/log" (strip shortest suffix /…) echo "{$path%.log}.txt" # = "/var/log/app.txt" (extension swap) # Arrays: files=("auth.log" "app.log" "error.log") for f in "{$files[@]}"; do # always quote array expansion echo "Processing $f" done

CI/CD script patterns

# Typical ADO/GitHub Actions pipeline step (Bash): #!/bin/bash set -euo pipefail # Read secrets from env vars (CI injects these): SPRING_CLIENT_SECRET="${OAUTH_CLIENT_SECRET:?'OAUTH_CLIENT_SECRET not set'}" # :? = if unset, print error and exit # Build: echo "Building Maven project..." mvn clean package -DskipTests -q echo "Build complete: exit $?" # Docker: IMAGE_TAG="myapp:$(git rev-parse --short HEAD)" docker build -t "$IMAGE_TAG" . docker push "$IMAGE_TAG" # Wait for service to be ready: for i in {1..30}; do if curl -sf http://localhost:8080/actuator/health; then echo "Service ready" break fi echo "Waiting... ($i/30)" sleep 2 done # Cleanup on exit (trap runs even if script fails): trap 'echo "Script exited with $?"' EXIT

In CIAM / Your Job: Bash scripts are the glue of every CI/CD pipeline in your CIAM stack. Your ADO pipelines run Bash steps to: build the Spring Boot JAR, build the Docker image, push to ACR/ECR, apply Kubernetes manifests, and run smoke tests. The most common Bash task in CIAM work: calling the OAuth2 token endpoint with curl in a script to get a token for automated testing. Always use set -euo pipefail — without it, a failed mvn build won't stop the docker push from running, and you'll deploy a broken image. Store secrets as pipeline environment variables (ADO Secret Variables, GitHub Secrets) and read them in Bash as $VARIABLE_NAME — never hardcode secrets in scripts.

1. Anatomy of a script

#!/usr/bin/env bash          # ① shebang: which interpreter runs this
set -euo pipefail              # ② strict mode (see the gotcha box)

name="${1:-world}"            # ③ $1 = first arg, default "world"
echo "Hello, $name!"

if [[ -f config.yaml ]]; then   # ④ test: does the file exist?
  echo "found config"
else
  echo "no config" >&2        # write to stderr
  exit 1                      # non-zero = failure
fi
Strict mode. set -e exits on the first failing command, set -u errors on an undefined variable (catches typos), and set -o pipefail makes a pipeline fail if any stage fails. Put set -euo pipefail at the top of every script — it turns silent bugs into loud, early failures.

2. Variables & the quoting rules everyone learns the hard way

Assigning & reading

name="Ada"        # NO spaces around =
echo "$name"      # Ada
files=$(ls)       # $(...) captures output
count=$((2 + 3))   # $((...)) does math

# name = "Ada"   ← WRONG: runs command `name`

Quote your variables. Always.

file="my report.txt"

rm $file     # ❌ deletes "my" AND "report.txt"!
rm "$file"   # ✓ one file, the right one

# unquoted = word-split on spaces + glob-expanded

Single quotes are literal ('$name' → $name); double quotes expand variables ("$name" → Ada). When in doubt, double-quote every expansion.

3. Exit codes — how the shell knows success

# Every command returns an exit code: 0 = success, non-zero = failure.
grep -q ERROR log.txt
echo $?          # 0 if "ERROR" was found, 1 if not

# Chain on success (&&) or failure (||):
mkdir build && cd build       # cd only if mkdir worked
ping -c1 host || echo "unreachable"   # fallback on failure

# That's also how `if` works — it tests an exit code, not a boolean.
if grep -q ERROR log.txt; then alert; fi

$? holds the exit code of the last command. if cmd; then … runs the then branch when cmd exits 0. There's no separate boolean type — the exit code is the truth value.

Loops & functions (scenario ④): for f in *.txt; do echo "$f"; done iterates over files; while read line; do …; done < file reads a file line by line; and a function is just greet() { echo "hi $1"; }. Bash is a full language — but for anything with real data structures, reach for Python instead.
