The Decorator Pattern

or, how Starbuzz Coffee learned to stop subclassing and start wrapping

Starbuzz's menu has a handful of beverages and a pile of condiments — milk, mocha, soy, whip. Model every combination as its own class and you get a class explosion: hundreds of rigid HouseBlendWithSoyAndMochaAndWhip-shaped classes. Decorator wraps a drink in condiment objects that each add their own cost, so any order gets built at runtime, one wrapper at a time.

The problem

Every new topping shouldn't mean a new class.

Subclass for every combo
HB+SoyHB+MochaDecaf+Whip HB+Soy+WhipDecaf+Soy+Mocha HB+Mocha+WhipDecaf+Mocha+Whip HB+Soy+Mocha+WhipDecaf+Soy+Whip

…and one more class for every new topping the menu adds.

Wrap at runtime instead
House Blend ↓ wrapped by + Soy ↓ wrapped by + Whip ↓ wrapped by + Mocha
Open/Closed Principle: classes should be open for extension but closed for modification. Every condiment is a new class added beside Beverage — nothing about HouseBlend ever changes.
Whip

I don't know what I'm wrapping. I just ask it for its cost and add ten cents to whatever it says.

HouseBlend

And I have no idea anyone is wrapping me. I charge $0.89 and go back to sleep.

Mocha

So the barista's code just sees… a Beverage. One Beverage. It has no idea it's actually four objects deep.

You build new Whip(new Mocha(new Espresso())). Whose cost() runs first?

Espresso's cost is the first to return, but not the first to be called. The call has to travel inward through the wrappers before anything comes back.

You call cost() on the outermost object, so Whip runs first — it immediately delegates inward to Mocha, which delegates to Espresso. Espresso returns 1.99, then each wrapper adds its delta on the way back out.

Nothing runs in parallel here. It's one call stack going in and unwinding out — which is exactly why the order is visible in the receipt.

The mechanism

Four objects, one method call.

cost() called ↘

+ Mocha · $1.29
+ Whip · $1.09
+ Soy · $0.99
House Blend$0.89

The call goes in through Mocha → Whip → Soy to reach the real coffee, then the total bubbles back out, gaining a charge at every layer: $0.89 → $0.99 → $1.09 → $1.29.

Key terms

Component

The shared type. Both the real object and every decorator implement it.

Concrete Component

The thing actually being wrapped — HouseBlend, Espresso, a real InputStream.

Decorator

Holds a Component, implements Component, delegates to it. That's the whole trick.

Concrete Decorator

Mocha, Whip, Soy. Each adds exactly one responsibility on top of the delegate call.

Questions from the back row

Doesn't this mean I now have a separate class for Soy, Whip, and Mocha? Isn't that more classes, not fewer?

Three small classes instead of hundreds of rigid ones. Each condiment class is reused across every beverage and every combination, instead of existing once per combination.

How does the outer object know how deep the wrapping goes?

It doesn't need to. Mocha only ever talks to "the Beverage I'm wrapping" — whether that's a raw Espresso or three more decorators deep is invisible to it.

Does Mocha(Whip(x)) differ from Whip(Mocha(x))?

The total cost comes out the same either way — it's just addition. But getDescription() prints condiments in wrap order, so the two produce different-looking receipts for the same drink.

Act 1 — the class explosion

First instinct: a Beverage subclass for every drink-plus-condiment combination. It does not scale — each new condiment doubles the class count, and a price change for milk means editing dozens of classes.

HouseBlend, HouseBlendWithMilk, HouseBlendWithMocha,
HouseBlendWithMilkAndMocha, HouseBlendWithSoyAndMochaAndWhip, …
// × every beverage × every condiment combination = chaos
Brain Power. Second instinct: add boolean hasMilk/hasMocha fields and cost() logic to the base Beverage class. Better count — but now a new condiment forces you to edit the base class, double-mocha is impossible, and a tea that can't take whip still inherits the field. You're modifying existing, tested code for every change. There's a principle for that…

Act 2 — wrap, don't subclass

A condiment is-a Beverage (so it fits anywhere a Beverage fits) and has-a Beverage (the thing it wraps). It delegates cost() to what it wraps, then adds its own price.

The component & base decorator

abstract class Beverage {   // the shared type ALL of it wears
  abstract double cost();      // every layer must answer this
}
// extends Beverage → IS-A (fits anywhere a drink fits)
abstract class CondimentDecorator extends Beverage {
  protected Beverage beverage;   // HAS-A the wrapped drink
}

A concrete decorator

class Mocha extends CondimentDecorator {
  // wrap time: remember what's one layer inward
  Mocha(Beverage b) { this.beverage = b; }
  double cost() {                    // called from outside-in…
    return beverage.cost() + 0.20;  // …ask inward, add my delta
  }
}

Act 3 — the order, in code

Beverage drink = new DarkRoast();           // 0.99
drink = new Mocha(drink);                    // + 0.20
drink = new Whip(drink);                     // + 0.10
System.out.println(drink.cost());           // 1.29

Q: The outer object's type is just Whip — doesn't the client lose track of what's inside?

A: It does, and that's fine. The client only ever calls cost() (and getDescription()) on a Beverage. It never needs to know the stack — that's the whole point of programming to the component type.

The principle this chapter hands you

Design Principle — Open/ClosedClasses should be open for extension, but closed for modification.

A new condiment is a new decorator class — you never reopen Beverage or the existing condiments. You extend behavior by wrapping, not by editing tested code. That's Open/Closed in its purest form.

The Decorator Pattern, defined

The Decorator Pattern attaches additional responsibilities to an object dynamically. Decorators provide a flexible alternative to subclassing for extending functionality.

A decorator mirrors the type of what it wraps (so it's interchangeable) and adds behavior before or after delegating. You can stack them in any order, any number of times — all decided at runtime.

You've already used Decorator (java.io is built on it)

Java I/O streams

InputStream in =                // client sees ONE type
  new BufferedInputStream(      // decorator: adds buffering
    new GZIPInputStream(        // decorator: adds unzip
      new FileInputStream("data.gz")));  // the real stream

Buffering and decompression are decorators wrapping the raw file stream — same shape as Whip(Mocha(DarkRoast)).

Spring & Angular

// Spring: BeanPostProcessor / AOP proxies wrap beans
// Angular: an HttpInterceptor wraps the next handler
intercept(req, next) {
  return next.handle(req.clone(...));  // add, then delegate
}

An Angular interceptor chain is decorators around the HTTP backend — each adds a header, then delegates to next.
