Act 1 — the class explosion

First instinct: a Beverage subclass for every drink-plus-condiment combination. It does not scale — each new condiment doubles the class count, and a price change for milk means editing dozens of classes.

HouseBlend, HouseBlendWithMilk, HouseBlendWithMocha,
HouseBlendWithMilkAndMocha, HouseBlendWithSoyAndMochaAndWhip, …
// × every beverage × every condiment combination = chaos
Brain Power. Second instinct: add boolean hasMilk/hasMocha fields and cost() logic to the base Beverage class. Better count — but now a new condiment forces you to edit the base class, double-mocha is impossible, and a tea that can't take whip still inherits the field. You're modifying existing, tested code for every change. There's a principle for that…

Act 2 — wrap, don't subclass

A condiment is-a Beverage (so it fits anywhere a Beverage fits) and has-a Beverage (the thing it wraps). It delegates cost() to what it wraps, then adds its own price.

The component & base decorator

abstract class Beverage {
  abstract double cost();
}
abstract class CondimentDecorator extends Beverage {
  protected Beverage beverage;   // HAS-A the wrapped drink
}

A concrete decorator

class Mocha extends CondimentDecorator {
  Mocha(Beverage b) { this.beverage = b; }
  double cost() {
    return beverage.cost() + 0.20;  // delegate + add
  }
}

Act 3 — the order, in code

Beverage drink = new DarkRoast();           // 0.99
drink = new Mocha(drink);                    // + 0.20
drink = new Whip(drink);                     // + 0.10
System.out.println(drink.cost());           // 1.29

Q: The outer object's type is just Whip — doesn't the client lose track of what's inside?

A: It does, and that's fine. The client only ever calls cost() (and getDescription()) on a Beverage. It never needs to know the stack — that's the whole point of programming to the component type.

The principle this chapter hands you

Design Principle — Open/ClosedClasses should be open for extension, but closed for modification.

A new condiment is a new decorator class — you never reopen Beverage or the existing condiments. You extend behavior by wrapping, not by editing tested code. That's Open/Closed in its purest form.

The Decorator Pattern, defined

The Decorator Pattern attaches additional responsibilities to an object dynamically. Decorators provide a flexible alternative to subclassing for extending functionality.

A decorator mirrors the type of what it wraps (so it's interchangeable) and adds behavior before or after delegating. You can stack them in any order, any number of times — all decided at runtime.

You've already used Decorator (java.io is built on it)

Java I/O streams

InputStream in =
  new BufferedInputStream(
    new GZIPInputStream(
      new FileInputStream("data.gz")));

Buffering and decompression are decorators wrapping the raw file stream — same shape as Whip(Mocha(DarkRoast)).

Spring & Angular

// Spring: BeanPostProcessor / AOP proxies wrap beans
// Angular: an HttpInterceptor wraps the next handler
intercept(req, next) {
  return next.handle(req.clone(...));  // add, then delegate
}

An Angular interceptor chain is decorators around the HTTP backend — each adds a header, then delegates to next.
