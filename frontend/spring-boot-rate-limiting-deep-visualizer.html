Rate Limiting & Account Lockout

Your /api/auth/login is a magnet for brute-force and credential-stuffing attacks — without a throttle, an attacker can try millions of passwords. Two related defenses: rate limiting (cap requests per window, return 429) and account lockout (too many failed logins → temporarily refuse). The trick is stopping attackers without handing them a way to lock out real users.

🚦 What is a credential-stuffing attack — and why does rate limiting stop it?

A brute-force attack tries millions of passwords against one account; credential stuffing takes a leaked username/password list from another breach and replays each pair against your login, banking on password reuse. Unthrottled, an attacker tries ~10,000/second. Rate limiting caps it — say 5 attempts per IP per minute, then 429 Too Many Requests with Retry-After: 60 — a 2,000× slowdown. Account lockout complements it (lock after 10 failures for one account), but it can be abused to deliberately lock real users out, so thresholds and unlock paths need care.

  • Throttle to defang stuffing. Capping attempts/min turns 10k/s into 5/min.
  • Limit by IP and username — IP catches single-source, username catches distributed attacks.
  • Limit early. Gateway/filter, never the service layer (you've already spent the DB lookup).
  • Lockout cuts both ways — design unlock so it can't become a DoS against real users.

Bucket4j / Resilience4j

Bucket4j token bucket: each IP gets 5 tokens, 1 per attempt, refilling 1/min; empty → 429. Redis-backed (Bandwidth.classic(5, Refill.greedy(...))) for multi-pod consistency. Resilience4j RateLimiter is annotation-based for method-level limits.

Account lockout

Track per-account in Redis: INCR login:failures:{userId} + EXPIRE …900; clear on success. At ≥10, return 429 without checking the password. Unlock by TTL or admin POST …/unlock. Alert if >100 accounts lock in 5 min (lockout-DoS).

The right layer

Best at the gateway/LB (blocked before any compute), then a Security filter early in the chain, then a plain filter for un-gatewayed endpoints — never the service layer. Tune per endpoint: login 5/min, password reset 3/hour, admin create 10/min.

CIAM: POST /api/auth/login limited by IP (5/min) and username (10/hour); log each failure with IP, masked username, and timestamp. If one username gets >10 failures in 5 min from different IPs, that's a stuffing pattern — notify the user "someone is trying to access your account." Also throttle POST /api/auth/password-reset (3/hour per email) to stop email flooding.

1. Two controls, different keys

Account lockoutconsecutive failed loginsusername/accounttemporary refuse (e.g. 423)

Rate limiting blunts volume; lockout blunts targeting one account. Use both — but lock carefully (see the trap below).

2. Interactive: a token-bucket rate limiter

bucket:

Each request spends a token. Empty bucket → 429 with a Retry-After. Tokens refill over time (here, +2 every 4s, cap 5) — so a steady, human pace is fine but a burst gets throttled. Hammer it to see the block.

3. How you'd build it

Token bucket (bucket4j)

var limit = Bandwidth.classic(5,
   Refill.greedy(5, Duration.ofMinutes(1)));
var bucket = Bucket.builder().addLimit(limit).build();

if (!bucket.tryConsume(1))
   return ResponseEntity.status(429)
       .header("Retry-After", "60").build();

Put it in a filter (or API gateway) keyed by client IP / API key, before the controller.

Distributed & lockout

  • One instance ≠ the limit. In-memory counters don't share across pods — back the bucket with Redis (bucket4j has a Redis store).
  • Lockout: count failures per account in the DB/cache; after N, refuse for M minutes; reset on success.
  • Gateway option: Spring Cloud Gateway's RequestRateLimiter filter (Redis) does it before your app.
  • Or let the IDM do it: Entra/Ping "smart lockout" if it owns the login.

4. The lockout trap (and better defenses)

  • Naive lockout is a DoS on your users. If "5 fails → lock account", an attacker can deliberately lock any victim out by failing on purpose. Don't lock purely on username.
  • Prefer graduated friction: throttle + exponential backoff per IP+account, then CAPTCHA, then short lockouts — not an instant hard lock.
  • Constant-time & vague: don't reveal "wrong password" vs "no such user", and keep timing even, or you leak which usernames exist.
  • Always return Retry-After on 429 so well-behaved clients back off correctly.

5. One-sentence recap

🚦 Protect auth endpoints with a rate limit (a token bucket — e.g. bucket4j in a filter — keyed by IP/API-key, returning 429 + Retry-After, backed by Redis when you run more than one instance) plus careful account lockout on failed logins — but avoid naive username-only locks (an attacker can weaponize them to DoS real users); prefer throttling + exponential backoff + CAPTCHA, keep responses vague and constant-time, and let the IDM's smart-lockout help when it owns login.
