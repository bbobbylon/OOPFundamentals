Java Variables & Types

Zero to confident: primitives, references, memory, casting, autoboxing, var, and scope.

What are Java variables and types — and why does understanding primitives vs references and stack vs heap prevent the most common Java bugs?

Java is a statically typed language — every variable has a declared type that is checked at compile time, before the program runs. This means the compiler catches type errors early (passing a String where an int is expected is a compile error, not a runtime crash). Java has two fundamental categories of types that behave completely differently. Primitive types (8 of them: boolean, byte, short, int, long, float, double, char) store their value directly in memory. When you write int x = 42; the number 42 lives directly in the variable's memory slot on the stack. Primitives are fast, have no overhead, and cannot be null. Reference types (everything else: String, arrays, all class instances) store a memory address (a pointer) that points to the actual object on the heap. When you write String s = "hello"; the variable s holds the address of where "hello" lives in heap memory. This is why you can pass a reference to a method and have the method modify the underlying object — but you can't change what the variable itself points to from inside the method (Java is "pass by value" where the value passed is the reference). Stack vs Heap: the stack holds local variables and method call frames — it's fast, has limited size (~1MB by default), and is automatically managed (variables are "popped off" when a method returns). The heap holds all objects — it's larger, slower, and managed by the garbage collector. Autoboxing: Java automatically converts between primitives and their wrapper class equivalents (int ↔ Integer, boolean ↔ Boolean) when context requires it. This is convenient but has traps: Integer a = 127; Integer b = 127; a == b is true (cached), but Integer a = 200; Integer b = 200; a == b is false (different objects! use .equals()). The var keyword (Java 10+) enables type inference — var list = new ArrayList<String>(); — the compiler infers the type at compile time. The type is still static; var just avoids repeating it. Use var when the type is obvious from the right side; avoid when it makes code harder to read.

Primitive vs Reference

// PRIMITIVES — value lives in the variable: int a = 5; // 5 is stored directly in 'a' int b = a; // b gets a COPY of 5 b = 10; // a is still 5 — they're independent // REFERENCES — variable holds an address: int[] arr1 = {1, 2, 3}; // arr1 → [address of array] int[] arr2 = arr1; // arr2 gets the SAME address arr2[0] = 99; // arr1[0] is now 99! (same object) // Why this matters for methods: void addOne(int x) { x = x + 1; } // does NOT change caller's int void addElement(List<String> list) { list.add("x"); } // DOES modify caller's list // Because: int copy is passed; list reference (same object) is passed // NULL: only references can be null (no value, no address): String s = null; // legal // s.length() // NullPointerException! must check != null first

Type casting + overflow

// WIDENING: safe, automatic (smaller → larger): int i = 100; long l = i; // auto-widened (int fits in long) double d = i; // auto-widened (100.0) // NARROWING: must be explicit, may lose data: double pi = 3.14159; int truncated = (int) pi; // = 3 (decimal part lost) // OVERFLOW: Java wraps around silently! int max = Integer.MAX_VALUE; // 2,147,483,647 int overflow = max + 1; // = -2,147,483,648 (wraps!) // This is a classic bug in old code (use long if values can exceed INT_MAX) // Autoboxing traps: Integer x = 127; Integer y = 127; System.out.println(x == y); // true (cached by JVM for -128..127) Integer a = 200; Integer b = 200; System.out.println(a == b); // false (different heap objects!) System.out.println(a.equals(b)); // true (always use equals for objects) // var inference (Java 10+): var users = new ArrayList<User>(); // compiler infers ArrayList<User>

Stack vs Heap memory

// Stack: per-thread, fast, limited, auto-cleaned // Each method call gets a "stack frame" // Frame holds: local variables + method parameters // When method returns: frame is destroyed (all locals gone) void calculate() { int result = 42; // 'result' lives in this stack frame } // stack frame popped, 'result' gone // Heap: shared between threads, GC-managed, large // All objects (new Foo(), new int[], "string literals"*) go here User user = new User("Alice"); // - 'user' variable: lives on the STACK (it's local) // - new User(...) object: lives on the HEAP // - user holds the HEAP ADDRESS of the User object // Stack overflow: too many nested calls (deep recursion without base case) // java.lang.StackOverflowError // OutOfMemoryError: heap full (too many large objects, memory leak) // Memory leak: objects still referenced but never used // GC can't collect objects that are still reachable // Common cause: static collections that grow forever

In CIAM / Your Job: Understanding primitives vs references is essential for debugging CIAM code. Common bugs: using == to compare String values (e.g., comparing OAuth grant types, scopes, or tenant IDs) instead of .equals() — strings are objects, so == compares addresses, not content. NullPointerExceptions on JWT claims: always check that claims map contains a key before calling .get("tid").toString(). In Spring Boot, @Transient fields vs @Column fields in JPA entities: transient fields are not persisted, so if you store a decoded JWT claim in a transient field, it won't be in the DB — by design. The var keyword greatly reduces verbosity in modern Spring Boot code (Java 17+).

Local variable error:
int x;
System.out.println(x); // COMPILE ERROR

"variable x might not have been initialized" — the compiler proves every path must assign before use.
Why different? Fields are initialized when the object is created. Locals only exist on the call stack and the compiler cannot safely give them a default.

Reference Types — the variable holds an address, not the object

// Creating objects on the heap String name = "Alice"; int[] scores = new int[5]; List<String> list = new ArrayList<>(); // Assigning refs copies the ADDRESS String a = "hello"; String b = a; // same object, not a copy Person p1 = new Person("Bob"); Person p2 = p1; p2.name = "Charlie"; // p1.name is now "Charlie" too!

◆ Enums — enum values are objects
◆ Records — Java 16+ immutable value objects

== vs .equals() — the most common Java gotcha

String a = new String("hello"); String b = new String("hello"); a == b // false — different heap addresses a.equals(b) // true — same characters // String Pool — literals are interned String c = "hello"; String d = "hello"; c == d // true — same pool object // Golden rule: ALWAYS use .equals() for Strings // Null-safe: Objects.equals(a, b)
// Same issue with Integer cache! Integer x = 127; Integer y = 127; x == y // true — cached range [-128, 127] Integer p = 128; Integer q = 128; p == q // false — outside cache, new objects // Always use: x.equals(y) // true Objects.equals(x, y) // null-safe Integer.compare(x, y) // for ordering

Pass-by-value of the reference — Java is NOT pass-by-reference

void tryChange(Person p, String s) { p.name = "New Name"; // mutates the heap object — caller SEES this p = new Person(); // reassigns LOCAL variable — caller does NOT see this s = "changed"; // reassigns LOCAL — String is also immutable anyway } Person alice = new Person("Alice"); String text = "original"; tryChange(alice, text); // alice.name == "New Name" (mutation visible) // text == "original" (reassignment not visible)

Autoboxing & Unboxing — automatic conversion between primitives and wrappers

Wrapper Classes

int ↔ Integer
long ↔ Long
double ↔ Double
boolean ↔ Boolean
char ↔ Character
byte ↔ Byte
// Autoboxing: primitive → wrapper (automatic) Integer x = 42; // Integer.valueOf(42) List<Integer> nums = new ArrayList<>(); nums.add(5); // autoboxed to Integer // Unboxing: wrapper → primitive (automatic) int sum = x + 10; // x.intValue() + 10 int y = nums.get(0); // unboxed from Integer // Danger: NullPointerException! Integer n = null; int val = n; // NPE — n.intValue() on null!

Performance Pitfall: unnecessary autoboxing in loops

// SLOW: autoboxes every iteration Long sum = 0L; for (long i = 0; i < 1_000_000; i++) { sum += i; // unbox sum, add, rebox } // Creates ~1M Long objects!
// FAST: stay primitive long sum = 0L; for (long i = 0; i < 1_000_000; i++) { sum += i; // pure primitive math } // No boxing, no GC pressure
Useful wrapper methods: Integer.parseInt("42"), Integer.toBinaryString(n), Integer.MAX_VALUE, Double.isNaN(d), Character.isDigit(c)

var — Local Variable Type Inference (Java 10+)

// var tells the compiler: "figure out the type from the right side" var name = "Alice"; // String var count = 42; // int var scores = new int[5]; // int[] var map = new HashMap<String, Integer>(); // HashMap<String,Integer> // var is NOT dynamic — it's still statically typed! var x = 5; x = "hello"; // COMPILE ERROR — x is int // Great for long generic types var entries = new ArrayList<Map.Entry<String, List<Integer>>>(); // vs: ArrayList<Map.Entry<String,List<Integer>>> entries = ... // Use in enhanced for loops for (var entry : map.entrySet()) { System.out.println(entry.getKey() + " = " + entry.getValue()); }

When to use var — and when NOT to

✓ Good uses

// Type obvious from right side var list = new ArrayList<String>(); var user = userService.findById(id); // Long generic type names var result = new HashMap<String, List<Map.Entry<Integer,Double>>>(); // try-with-resources try (var conn = db.getConnection()) { // ... }

✗ Avoid when unclear

// Type not obvious from right side var x = getResult(); // what type? var y = process(map); // reader must look it up // Cannot use with null var z = null; // COMPILE ERROR — no type to infer // Cannot use in method signatures var field = 5; // ERROR — only local vars // Cannot use for lambda params (use explicit type) var fn = (x, y) -> x + y; // ERROR

Variable Shadowing — inner variable hides outer

class Shadow { int x = 10; // instance field void method() { int x = 20; // local SHADOWS field System.out.println(x); // 20 System.out.println(this.x); // 10 (field) } void noShadow() { System.out.println(x); // 10 (field) } }
// Final variables — can't be reassigned final int MAX = 100; MAX = 200; // COMPILE ERROR // final reference — ref can't change // but object itself can still mutate final List<String> list = new ArrayList<>(); list.add("ok"); // fine list = new ArrayList<>(); // COMPILE ERROR // Effectively final (Java 8+) int count = 5; // never reassigned Runnable r = () -> System.out.println(count); // ok
