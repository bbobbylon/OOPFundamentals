The State Pattern — the Gumball Machine

Chapter 10. A gumball machine has four states — No Quarter, Has Quarter, Sold, Sold Out — and every action (insertQuarter, turnCrank, dispense) behaves differently in each. Coded with int constants and if/else, adding a "1-in-10 winner" state means editing every method. The State pattern makes each state a class.

Act 1 — the if/else gumball machine

The first version uses int state constants and branches on them inside every method:

final int SOLD_OUT=0, NO_QUARTER=1, HAS_QUARTER=2, SOLD=3;
int state = NO_QUARTER;

void insertQuarter() {
  if (state == HAS_QUARTER) ... ;
  else if (state == NO_QUARTER) ... ;
  else if (state == SOLD_OUT) ... ;
  else if (state == SOLD) ... ;      // the SAME 4-way if in EVERY method
}
// …repeat in turnCrank(), dispense() — duplicated, fragile…
Brain Power. Now the boss wants a "1-in-10 you win two gumballs" feature. That's a new state — and with this design you must add a WINNER constant and a new else if branch to every single method. State-dependent behavior scattered across methods is exactly the smell the State pattern removes.

Act 2 — make each state a class

Define a State interface with one method per action. Each concrete state implements all the actions for that state. The machine holds a reference to the current state and delegates.

The State interface & context

interface State {
  void insertQuarter();
  void turnCrank();
  void dispense();
}
class GumballMachine {
  State state = noQuarterState;
  void insertQuarter() { state.insertQuarter(); }  // delegate
}

A concrete state owns its behavior

class NoQuarterState implements State {
  public void insertQuarter() {
    print("You inserted a quarter");
    machine.setState(machine.getHasQuarterState());
  }
  public void turnCrank() { print("Pay first!"); }
}

Act 3 — the transition, animated

Each action delegates to the current state object, which performs the behavior and moves the machine to the next state. Buying a gumball walks NoQuarter → HasQuarter → Sold → NoQuarter.

machine.insertQuarter();   // NoQuarter → HasQuarter
machine.turnCrank();      // HasQuarter → Sold (then dispense)
// Sold.dispense() releases a gumball, then → NoQuarter (or SoldOut)

Q: Who decides the next state — the machine or the state object?

A: The state objects. Each state knows its own valid transitions and calls machine.setState(...). That localizes "what can happen next" to the one place that should own it — instead of a transition table scattered across if-branches.

The State Pattern, defined

The State Pattern allows an object to alter its behavior when its internal state changes. The object will appear to change its class.

"Appears to change its class" = the machine's behavior is entirely determined by which State object it currently delegates to. Swap the object, and insertQuarter() means something completely different — without a single if.

State vs Strategy — same diagram, different story

State and Strategy have an identical class diagram (a context delegating to an interface), but they tell different stories:

Strategy

The client chooses the algorithm and usually sets it once. The strategies don't know about each other.

State

The states change themselves at runtime as a result of actions, and each state knows the next. The transitions are the whole point.

You've used it. A workflow/order status (PENDING → PAID → SHIPPED), a TCP connection (Listen/Established/Closed), an Angular router or an XState/NgRx state machine — all "behavior changes with state." That's the whole Head First greatest-hits run: Strategy, Observer, Decorator, Factory, Singleton, Command, Adapter/Facade, Template Method, and State.

State in your stack

Order workflow — Spring entity

enum OrderStatus { PENDING, PAID, SHIPPED, DELIVERED }
// each action is a state transition
order.pay();    // PENDING → PAID
order.ship();   // PAID → SHIPPED
// invalid: order.ship() while PENDING → throw

Angular — XState / NgRx state machine

const machine = createMachine({
  initial: 'idle',
  states: {
    idle:    { on: { FETCH: 'loading' } },
    loading: { on: { DONE: 'success', FAIL: 'error' } },
    success: { ... }, error: { ... }
  }
});
Design Principle — Encapsulate What VariesState-dependent behavior is what varies. Put each state's behavior in its own class — NoQuarterState owns what "insertQuarter" means for that state. The if-else chain scattered that knowledge across every method; the State pattern localizes it.
You'll spot it everywhere. TCP connections (Listen → Established → CloseWait → Closed), browser routing, authentication flows (Unauthenticated → ChallengeSent → Authenticated), vending machines, video player controls. Anywhere "the same action does different things depending on the current mode" — that's the State pattern waiting to be named. XState encodes it explicitly for JS; Spring State Machine for Java.
