Vitest & .spec.ts

Angular's modern unit-test runner. What a .spec.ts file is, how Vitest runs it, and the features — watch mode, vi mocks, coverage, test.each, fake timers — that make you a faster, more confident developer. Pairs with the broader Testing (TestBed & Pyramid) page.

⚡ What is Vitest, and why does Angular use it now?

A unit test is a tiny program that runs one piece of your code and checks it did the right thing — automatically, in milliseconds, every time you save. A test runner is the tool that finds those tests, runs them, and reports pass/fail. For years Angular's runner was Karma + Jasmine (spin up a real browser, slow). Karma is now deprecated and removed; from Angular 20 the CLI ships first-party Vitest support, and v21 makes it the recommended runner. Vitest is built on Vite — the same lightning-fast dev server Angular already uses — so tests transform with esbuild, run in Node against a fake DOM (jsdom/happy-dom), and re-run only the file you touched. Same tests, a fraction of the time.

  • A test file is named thing.spec.ts and lives next to the code it tests (cart.service.ts → cart.service.spec.ts).
  • Inside: describe() groups tests, it()/test() is one test, expect() makes an assertion. Vitest's API is Jest-compatible, so this reads like Jasmine.
  • Run ng test (Angular's builder drives Vitest) or npx vitest directly. Leave it running — watch mode re-runs on every save.
  • Mock collaborators with vi.fn(), vi.spyOn(), vi.mock(). Angular's TestBed still works unchanged — it's runner-agnostic.
  • Features that level you up: --coverage shows untested lines, test.each table-drives cases, vi.useFakeTimers() controls time, --ui gives a dashboard.

The shape of a spec

import { describe, it, expect } from 'vitest'; describe('CartService', () => { it('adds an item', () => { expect(...).toBe(...) }) }). Group → case → assertion. That's 90% of testing.

Why it's fast

No browser boot. Vite transforms TS with esbuild and caches it; a fake DOM runs in Node worker threads; on save only the changed module graph re-runs. Suites that took 30 s on Karma finish in low single-digit seconds.

Why it makes you better

Fast feedback = you actually run tests while coding. --coverage reveals blind spots, mocks force you to design seams, and writing the test first (TDD) clarifies the API before you build it.

In CIAM:unit-test authGuard by calling it with a mocked AuthStore and asserting it returns a UrlTree to /login; mock the token API with vi.fn().mockResolvedValue(...); use vi.useFakeTimers() to fast-forward a token's expiry and prove the refresh interceptor fires — all in milliseconds, no real clock, no real network.

The problem

The test passed alone. It failed the moment you ran the whole file.

toHaveBeenCalledTimes(1) was true — an hour ago, in a different test

You write it('tracks a purchase', () => { checkout(); expect(track).toHaveBeenCalledTimes(1); }) against a vi.mock('./analytics') spy, run just that one test with a name filter, and it's green. You run the whole spec file and it fails: Expected 1, received 3. Nothing about your assertion changed and checkout() genuinely only calls track() once. You add a log line, and it shows exactly one call — from this test. So the count from this test is right and the assertion is honest, which leaves only one place left to look: the count didn't reset when the last test ended.

checkout() calls track() exactly once, every time ✓ the assertion in this test is written correctly ✓ the same mock instance carried calls from earlier tests ⚠ nothing reset its call history between tests ⚠

vi.fn() isn't reborn for every it() block — the same fake function, and its whole call history, survives for as long as the module stays loaded, unless something explicitly clears it.

Make "start clean" the default, not a habit you remember
Add clearMocks: true to vitest.config.ts ↓ Vitest clears every mock's call history before each test runs — automatically, no per-file boilerplate Or, file by file: vi.clearAllMocks() in an afterEach ↓ same effect, opted into deliberately where a global setting would be too blunt Either way, "this test's count" stops meaning "every count since the file started"
A mock remembers everything until something tells it to forget. vi.fn() isn't scoped to the it() block it's called in — it's a plain object living as long as the module that created it, quietly accumulating .mock.calls across every test that touches it, which is exactly why toHaveBeenCalledTimes is the assertion most likely to lie to you the moment a suite grows past one test.
Think of vi.fn() as a notebook you hand a coworker to log every time someone knocks on their door. If you never tell them to start a fresh page, "how many knocks today" and "how many knocks since I gave you this notebook" quietly become the same question — and the second one is almost never the one your test meant to ask. clearMocks: true is telling them to tear out the page before every single visitor.
You

My test only calls track() once. Why does the assertion say 3?

The mock

Because I don't know what "this test" means — I'm not aware it() blocks even exist. I'm just a function object with an array on it, .mock.calls, and every time anyone calls me, I push onto it. Nobody emptied that array between your last three tests, so by the time you asked, it had three entries on it, not one.

Vitest

And to be fair to the mock, I don't clear it for you either — not unless you ask. clearMocks is a config flag that defaults to false, precisely because sometimes a suite wants to assert something across multiple it() blocks on purpose, and I can't tell your intentional case apart from your accidental one without you saying which this is.

The mechanism

Three tests, one un-cleared spy, and the count just keeps climbing.

  1. vi.mock('./analytics') runs once, hoisted above the imports, and creates one track spy shared by the whole fileone object, not one per test
  2. Test 1 calls checkout(), which calls track('purchase'). track.mock.calls now holds one entrythis is the array actually growing
  3. Test 1's expect(track).toHaveBeenCalledTimes(1) reads that array's length: 1. Correct, and it passestrue, for now
  4. Test 2 begins. Nothing ran between tests to reset track, so its .mock.calls array still holds test 1's entrythe array didn't know a new test started
  5. Test 2 also calls checkout(), pushing a second entry. Its own toHaveBeenCalledTimes(1) now reads a length of 2 and fails — for an assertion that, read on its own, looks completely correctthe bug shows up in the wrong test
  6. clearMocks: true inserts a call equivalent to vi.clearAllMocks() before every single test in the run, resetting .mock.calls to empty right before test 2 (and every test after it) even startsthe fix runs before the failure ever has a chance to happen

Step 4 is the lesson. The failure surfaces in test 2, which makes test 2 look broken — but test 2's code and assertion are both fine in isolation; the missing piece is something that should have happened between test 1 ending and test 2 starting, and didn't. That's the tell for this entire category of bug: when a test only fails as part of a suite, and only in a particular run order, look for state living somewhere the test itself never touches.

track.mock.calls = [] — file just loadedtest 1 runs checkout()→one call recorded
track.mock.calls.length === 1 — test 1's expect passestest 1 ends — nothing clears the spy→the array survives into test 2
test 2 runs checkout() against the same spya second call pushes onto the same array→length is now 2
track.mock.calls.length === 2 — test 2's expect(…toHaveBeenCalledTimes(1)) failsadd clearMocks: true→back to the top, array emptied before every test

The loop only closes with clearMocks. Without it, every test after the first one inherits a call count that has nothing to do with what that test actually did — which is why this bug reads as flaky or order-dependent instead of what it actually is: one shared object, never reset, quietly counting since the file started.

A spec file has vi.mock('./analytics') at the top and no clearMocks setting anywhere. Test A calls checkout() once and asserts toHaveBeenCalledTimes(1) — it passes. Test B never calls checkout() at all, but still asserts expect(track).toHaveBeenCalledTimes(0). If test A runs before test B, what happens to test B's assertion?

This is the assumption that feels obviously true — of course a test only counts what happens inside it — and it's exactly backwards for an un-cleared mock. toHaveBeenCalledTimes doesn't know which test it's running in; it just reads the length of an array that's been accumulating since the file loaded.

Right, and this is the uncomfortable version of the bug: a test with correct code and a correct assertion fails because of something an entirely different test did. Nothing here is wrong with test B — the missing piece is a reset that was supposed to happen between the two tests and didn't.

There's no such per-test isolation for a mock's call history — vi.mock('./analytics') sets up the fake once, hoisted above the imports, and every test in the file shares that same spy unless something explicitly clears it. Module-level isolation is not the same thing as call-history isolation.

Where you've seen this before

Shared mutable state outliving the thing that's supposed to own it — you've debugged this exact shape before.

A static field in a JUnit test class

The same bug, same fix, one stack down: a static List<String> calls field on a JUnit test class persists across every @Test method unless a @BeforeEach resets it — and exactly like clearMocks, most teams don't discover the leak until test order changes (a new CI runner, alphabetical vs. declaration order) and a previously-green suite starts failing for no code reason at all.

static test state ⇒ the exact same leak, different language

An in-memory rate limiter that forgets to reset between test requests

A rate-limiting middleware backed by an in-memory map behaves perfectly in production (one process, real time passing) and lies in a test suite that fires ten requests back-to-back without resetting the map — request 6 gets throttled not because the limiter is wrong, but because nine earlier tests already "used up" their share of a counter nobody cleared.

same failure: shared counter, no reset between runs

A CIAM token-refresh interceptor suite sharing one mocked HttpClient

Testing a CIAM app's refresh-token interceptor often mocks HttpClient once at the top of the file and fires several requests across several it() blocks to check retry behavior. Skip clearMocks here and a later test's "was the refresh endpoint called exactly once" assertion silently counts refresh calls from an earlier test's expired-token scenario too — a false failure that looks like a broken interceptor and is actually just an uncleared spy, on the one kind of test where a wrong answer is easiest to believe.

auth-flow tests are exactly where an uncleared mock hides best
Questions from the back row

If clearMocks: true is basically free, is there ever a reason not to set it globally?

Rarely, and it's worth setting as the default in almost every new project — but it's not entirely free. clearMocks resets call history and instances; it does not restore an implementation you overrode with mockImplementation, and it won't undo a vi.spyOn back to the original method (that needs restoreMocks: true instead). If a suite relies on a mock keeping its custom return value across tests in the same file — rare, and usually itself a design smell — turning on clearMocks globally will surface that dependency as new failures, which is normally a good thing to find.

What's the actual difference between clearMocks, resetMocks, and restoreMocks?

Each one undoes progressively more. clearMocks wipes .mock.calls/.mock.results — just the history — and leaves any mockReturnValue/mockImplementation in place. resetMocks does that and also removes any configured implementation, so a vi.fn() goes back to returning undefined. restoreMocks goes furthest: for a vi.spyOn() specifically, it puts the original, real method back, undoing the spy entirely. Reach for clearMocks for the call-count bug on this page; reach for restoreMocks when a spy on a real method needs to stop being a spy between tests.

Does this same bug exist for TestBed-based component tests, or only for vi.mock()?

The same root cause — a fake object whose state outlives a single test — can show up there too, if a provider fake ({ provide: UserApi, useValue: api }) is built once outside a beforeEach and reused across tests instead of rebuilt fresh inside one. The usual convention of calling TestBed.configureTestingModule() inside beforeEach mostly protects you by rebuilding the whole testing module — and any vi.fn() you construct fresh inside it — for every single test, which is the same fix as clearMocks, just achieved by rebuilding the object instead of resetting it.

Why the switch? Karma → Jasmine → Vitest

Karma (2013–)

Ran tests in a real browser via a websocket. Reliable but heavy: boot Chrome, recompile the whole app, ~seconds of startup before a single test runs.

Karma deprecated (v16, 2023)

The Karma project was retired. Angular began searching for a modern runner and shipped guidance to migrate to Jest or Web Test Runner.

Vitest experimental (v20, 2025)

The Angular CLI added a first-party @angular/build:unit-test builder that runs your existing .spec.ts files on Vitest — no browser, Vite-fast.

Vitest recommended (v21, 2025)

Vitest becomes the recommended default for new workspaces. Jasmine syntax still runs (Vitest is Jest-compatible), so most specs move over untouched.

Do you have to rewrite your tests? Mostly no. describe / it / expect / beforeEach are identical. The main edits are spies (jasmine.createSpyObj → vi.fn()) and fake timers (jasmine.clock() → vi.useFakeTimers()). See the migration table below.

1. The anatomy of a .spec.ts file

Every test file is the same four moving parts. Learn these and you can read any spec in any codebase.

// cart.service.spec.ts   ← named after cart.service.ts, sits right beside it
import { describe, it, expect, beforeEach } from 'vitest';   // (or enable globals in config)
import { CartService } from './cart.service';

describe('CartService', () => {           // ① a SUITE: groups related tests
  let service: CartService;

  beforeEach(() => {                        // ② runs before EACH it() → fresh state
    service = new CartService();
  });

  it('starts empty', () => {                // ③ a TEST CASE: one behaviour
    expect(service.items()).toEqual([]);   // ④ an ASSERTION: the actual check
  });

  it('adds an item', () => {
    service.add({ id: 1, name: 'Laptop' });
    expect(service.items()).toHaveLength(1);
    expect(service.items()[0].name).toBe('Laptop');
  });
});
PartKeywordJob
① Suitedescribe(name, fn)Groups tests and shows a heading in the report. Can nest.
② HookbeforeEach / afterEachSetup/teardown that runs around every test so cases can't leak state into each other.
③ Caseit(name, fn) / test(...)One behaviour. Name it as a sentence: "it adds an item".
④ Assertionexpect(actual).matcher(expected)The check. If it throws, the test fails. Aim for one concept per test.
The 3 A's: Arrange (set up), Act (do the thing), Assert (check). Every good test is those three lines in that order.

3. Mocking with vi — fakes you fully control

A unit test isolates one thing. Everything it talks to — services, HTTP, timers — you replace with a fake so the test is fast and deterministic. Vitest's mocking lives on the vi object.

import { describe, it, expect, vi } from 'vitest';

// vi.fn() — a fake function that records calls and returns what you tell it
const save = vi.fn().mockReturnValue(true);
save({ id: 1 });
expect(save).toHaveBeenCalledWith({ id: 1 });   // ✓ it recorded the argument
expect(save).toHaveBeenCalledTimes(1);

// vi.spyOn() — wrap a REAL method: observe it, or override its return
const spy = vi.spyOn(api, 'getUser').mockResolvedValue({ id: 1, name: 'Ada' });

// async returns:
vi.fn().mockResolvedValue(x);   // Promise that resolves to x
vi.fn().mockRejectedValue(err); // Promise that rejects
vi.fn().mockReturnValueOnce(a).mockReturnValueOnce(b); // different value each call

Mock an entire module with vi.mock()

// Replace a whole import so the real module never runs
vi.mock('./analytics', () => ({  // the factory's return value REPLACES the module's real exports
  track: vi.fn()          // every track() call is now a no-op spy
}));

import { track } from './analytics';  // resolves to the MOCKED version — vi.mock() is hoisted above this import

it('logs a purchase', () => {
  checkout();
  expect(track).toHaveBeenCalledWith('purchase');
});
ToolUse it when
vi.fn()You need a standalone fake callback/function to pass in and assert on.
vi.spyOn(obj, 'm')You want to watch (or stub) a method on a real object without replacing the whole object.
vi.mock('./mod')You want an entire imported module faked (hoisted to the top of the file — Vitest lifts it above imports).
vi.clearAllMocks()Reset call history between tests (or set clearMocks: true in config to do it automatically).

4. Component tests — TestBed runs under Vitest too

The runner changed; Angular's DI test harness did not. TestBed builds a mini Angular module, ComponentFixture renders the component, and you assert on the real DOM — exactly as before, just faster.

import { describe, it, expect, beforeEach, vi } from 'vitest';
import { TestBed, ComponentFixture } from '@angular/core/testing';  // the same DI test harness as before — only the runner changed
import { UserCardComponent } from './user-card.component';
import { UserApi } from './user.api';

describe('UserCardComponent', () => {
  let fixture: ComponentFixture<UserCardComponent>;  // typed handle to the rendered component + its real DOM
  const api = { getUser: vi.fn() };            // a fake UserApi

  beforeEach(async () => {
    api.getUser.mockReturnValue(of({ id: 1, name: 'Ada' }));
    await TestBed.configureTestingModule({
      imports: [UserCardComponent],                // standalone → import it
      providers: [{ provide: UserApi, useValue: api }] // swap real for fake
    }).compileComponents();
    fixture = TestBed.createComponent(UserCardComponent);  // instantiates the component — change detection has NOT run yet
  });

  it('renders the user name', () => {
    fixture.detectChanges();                       // ← run change detection / ngOnInit
    const el = fixture.nativeElement.querySelector('.name');  // a real DOM query — asserts on what the user would actually see
    expect(el.textContent).toContain('Ada');
  });
});
The #1 gotcha survives the switch: forgetting fixture.detectChanges(). Angular does not auto-run change detection in tests, so without it the DOM is stale and your assertion checks nothing. Call it after Arrange and after every Act.

5. The features that make you a better developer

👀 Watch mode

Leave vitest running. Save a file → only the affected tests re-run, in well under a second. Fast feedback is the whole game: you test while you code, not after.

📊 Coverage

--coverage shows which lines/branches ran. Not a score to game — a map of your blind spots. Chase confidence on critical paths, not 100% on getters.

🔁 test.each

Table-drive a case across many inputs. One test body, many rows — great for validators and pure functions. No copy-paste.

⏰ Fake timers

vi.useFakeTimers() + vi.advanceTimersByTime(300) makes debounce, polling, and token expiry instant and deterministic — no real waiting.

🖥️ --ui dashboard

A browser panel to filter tests, watch the module graph, and inspect failures. Great while learning what a suite covers.

📸 Snapshots

toMatchSnapshot() records output and flags future changes. Powerful but rots if over-used — reserve for stable, structured output.

🎯 only / skip / todo

it.only focuses one test while debugging; it.skip parks a flaky one; it.todo is an executable TODO list for tests you still owe.

🧵 In-source testing

Vitest can run tests written inside the source file itself (guarded by import.meta.vitest) — handy for tiny pure helpers.

test.each — one test, a table of cases

describe('isStrongPassword', () => {
  it.each([  // each object in this array becomes its OWN separate, independently-reported test
    { pw: 'short',          ok: false },
    { pw: 'nouppercase1!',  ok: false },
    { pw: 'Strong1!pass',   ok: true  },
  ])('"$pw" → $ok', ({ pw, ok }) => {  // $pw/$ok are interpolated from each row into that test's name
    expect(isStrongPassword(pw)).toBe(ok);
  });
});
// Reports THREE named tests. Add a row → add a case. Zero duplication.

vi.useFakeTimers() — control time itself

import { vi, it, expect, beforeEach, afterEach } from 'vitest';

beforeEach(() => vi.useFakeTimers());   // swap in a virtual clock
afterEach(()  => vi.useRealTimers());  // always restore it

it('debounces search by 300ms', () => {
  const spy = vi.fn();
  const search = debounce(spy, 300);

  search('a'); search('ab'); search('abc');
  expect(spy).not.toHaveBeenCalled();      // still waiting…

  vi.advanceTimersByTime(300);            // fast-forward the clock
  expect(spy).toHaveBeenCalledOnce();
  expect(spy).toHaveBeenCalledWith('abc');   // only the last value
});
Angular async, the Angular way: for zone-based async inside components you can still use fakeAsync/tick() from @angular/core/testing. For plain functions and services, Vitest's vi.useFakeTimers() is simpler. Both make time deterministic — pick the one that fits the code under test.

7. Config — where the settings live

Two paths. With the Angular CLI builder you barely touch config; standalone Vitest uses a vitest.config.ts.

Angular CLI builder (angular.json)

// angular.json — the "test" target uses the unit-test builder
"test": {
  "builder": "@angular/build:unit-test",  // the new builder name — replaces the old Karma-based one
  "options": {
    "runner": "vitest",  // explicitly opts into Vitest as the underlying runner
    "tsConfig": "tsconfig.spec.json",
    "buildTarget": "::development"
  }
}
// Then: ng test  → builds the app + runs every *.spec.ts on Vitest

Standalone Vitest config

// vitest.config.ts
import { defineConfig } from 'vitest/config';

export default defineConfig({
  test: {
    globals: true,              // use describe/it/expect without importing
    environment: 'jsdom',        // a fake DOM in Node (or 'happy-dom')
    setupFiles: ['src/test-setup.ts'], // runs once before the suite
    coverage: { provider: 'v8', reporter: ['text', 'html'] },
    clearMocks: true            // reset vi.fn() history between tests
  }
});
OptionWhy you set it
globals: trueSkip importing describe/it/expect in every file (add "types": ["vitest/globals"] to tsconfig).
environment: 'jsdom'Gives Node a fake document/window so DOM code runs headlessly. happy-dom is a faster alternative.
setupFilesOne-time global setup (e.g. Angular's TestBed zone/init, custom matchers).
clearMocksAuto-reset spy call history between tests so cases stay independent.

The mental model: a .spec.ts is Arrange → Act → Assert. Vitest finds it, transforms it with Vite (fast), runs it against a fake DOM, and re-runs it the instant you save.
