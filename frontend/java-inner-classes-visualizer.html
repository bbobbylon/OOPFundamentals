Java Inner Classes & Anonymous Classes — Zero to Hero

The four types of nested classes — when to use each, how they relate to their enclosing scope, and when lambdas replaced them.

What are the four types of nested classes — and why do static nested classes hold a reference to the outer class?

Java has four kinds of classes-inside-classes. Static nested class: declared with static, has no access to instance members of the outer class (no implicit this). Used for: helper types that are logically part of the outer class (e.g., User.Builder, Response.Error). Inner class (non-static): holds an implicit reference to the outer class instance. Can access outer class instance members. Downside: the outer instance is kept alive as long as the inner exists — a memory leak risk. Local class: defined inside a method, can capture effectively-final local variables. Rarely used today. Anonymous class: a one-time class definition used as an expression — new Runnable() { public void run() { ... } }. Widely replaced by lambdas in Java 8+. The memory leak pattern: holding a non-static anonymous class (e.g., an event listener) in a long-lived object — it holds a reference to the outer object, preventing GC. Modern solution: use lambdas (which don't have this hidden reference problem) or static inner classes.

Builder pattern as static nested class

class User { private final String name; private final String email; private User(Builder b) { this.name=b.name; this.email=b.email; } static class Builder { private String name, email; public Builder name(String n) { this.name=n; return this; } public Builder email(String e) { this.email=e; return this; } public User build() { return new User(this); } } }. Usage: new User.Builder().name("Bobby").email("b@b.com").build(). Static because it doesn't need the outer instance. Lombok's @Builder generates this pattern for you.

Anonymous class → lambda migration

Before (anonymous class): executor.submit(new Callable<String>() { @Override public String call() { return fetchData(); } }). After (lambda): executor.submit(() -> fetchData()). Before: list.sort(new Comparator<User>() { @Override public int compare(User a, User b) { return a.getName().compareTo(b.getName()); } }). After: list.sort(Comparator.comparing(User::getName)). Anonymous classes are still needed when: implementing an interface with multiple methods, accessing the this reference of the anonymous class itself (lambda's this = enclosing class).

Memory leak with inner class

Classic Android/UI leak: class Activity { void onCreate() { new AsyncTask() { // anonymous inner class doInBackground() { // holds reference to Activity this$ } }.execute(); } }. If the activity is destroyed but the task is still running, the anonymous class holds an implicit reference to the Activity — preventing GC. The Activity (and its views) leak. Fix: static inner class + WeakReference to the activity. Or use lambdas which don't implicitly capture this. In Spring Boot, this is less common (singleton beans don't get destroyed), but watch for inner-class Runnable/Callable instances holding references to request-scoped objects.

In CIAM / Spring Boot: Static nested classes for DTOs: class UserResponse { String name; List<RoleDto> roles; static class RoleDto { String name; String description; } } — cleanly scoped. Anonymous class for TypeReference (bypassing generics type erasure): new TypeReference<List<UserDto>>() {} — the anonymous class captures the generic type at compile time so Jackson can deserialise the list correctly. This is one of the few remaining legitimate uses of anonymous classes in modern Java — lambdas can't do this because they don't create subclass instances.

The four types — a quick map

Java supports four distinct flavors of nested classes. The key axis is whether they have an implicit reference to an outer class instance. Static nested classes do not. Inner, local, and anonymous classes do (unless they are in a static context). That reference is what enables them to access outer fields — and it's what causes memory leaks when misused.

1. Static Nested Class
Declared with static keyword inside a class. Acts like a regular top-level class but is namespaced inside the outer class. No implicit outer reference. Preferred for helper types.
2. Inner Class (non-static)
Declared without static. Every instance holds a hidden reference to the outer class instance. Can access outer instance fields directly. Cannot have static members (except constants).
3. Local Class
Declared inside a method body. Can capture effectively final local variables from the enclosing method. Rarely used in modern Java — usually replaced by lambdas or inner classes.
4. Anonymous Class
Declared and instantiated in one expression. Implements an interface or extends a class with no name. Was the standard way to write callbacks pre-Java 8. Largely replaced by lambdas, but still needed in some cases.
class Outer { int x = 10; // 1. Static nested class static class StaticNested { void hello() { System.out.println("static nested"); } } // 2. Inner class (non-static) class Inner { void hello() { System.out.println("outer.x = " + x); } } void doStuff() { int y = 20; // effectively final // 3. Local class class Local { void hello() { System.out.println("y = " + y); } } new Local().hello(); // 4. Anonymous class Runnable r = new Runnable() { public void run() { System.out.println("anon, x = " + x + ", y = " + y); } }; r.run(); } public static void main(String[] args) { Outer o = new Outer(); Outer.StaticNested sn = new Outer.StaticNested(); // no outer needed Outer.Inner in = o.new Inner(); // needs outer instance } }

Static nested class — namespaced helper with no outer reference

A static nested class is essentially a top-level class that lives in another class's namespace. It can access the outer class's private static members (a useful privilege), but it has no access to outer instance fields because there is no outer instance. You instantiate it with new Outer.Nested() — no Outer instance needed.

public class Graph { private int[][] adjacency; // Static nested class — closely related to Graph but // doesn't need a Graph instance to exist public static class Edge { final int from, to, weight; Edge(int from, int to, int weight) { this.from = from; this.to = to; this.weight = weight; } @Override public String toString() { return from + " → " + to + " (w=" + weight + ")"; } } // Graph can create Edges public List<Edge> getEdges() { List<Edge> edges = new ArrayList<>(); // ... populate ... return edges; } } // Using it — no Graph instance needed for Edge Graph.Edge e = new Graph.Edge(0, 1, 5); System.out.println(e); // 0 → 1 (w=5) // Outer class private statics ARE accessible: public class Config { private static final int MAX_RETRIES = 3; public static class RetryPolicy { public int maxRetries() { return MAX_RETRIES; } // ✓ OK } }
When to use: Use a static nested class when the nested type is a helper or value type that is conceptually related to the outer class (like Map.Entry) but doesn't need to operate on a specific outer-class instance. It is the default choice for nested classes — prefer it over non-static unless you specifically need outer-instance access.

Map.Entry — the standard library's canonical static nested class

// java.util.Map.Entry is a static nested interface public interface Map<K, V> { // ... map methods ... interface Entry<K, V> { // implicitly static in interface K getKey(); V getValue(); V setValue(V value); } } // Usage Map<String, Integer> scores = Map.of("Alice", 95, "Bob", 88); for (Map.Entry<String, Integer> entry : scores.entrySet()) { System.out.printf("%s scored %d%n", entry.getKey(), entry.getValue()); }

Non-static inner class — holds a hidden reference to outer instance

A non-static inner class is different from a static nested class in one crucial way: every inner class instance carries a hidden field this$0 that points to the outer class instance that created it. This is what gives the inner class access to outer instance fields — it literally holds a reference. The outer instance is said to "enclose" the inner instance. You cannot create an inner class instance without an outer instance.

public class BankAccount { private double balance; private final String owner; BankAccount(String owner, double initialBalance) { this.owner = owner; this.balance = initialBalance; } // Inner class — accesses outer's private fields directly public class Transaction { private final double amount; private final String type; Transaction(String type, double amount) { this.type = type; this.amount = amount; } public void execute() { // Directly accesses BankAccount.this.balance if (type.equals("DEPOSIT")) balance += amount; else if (type.equals("WITHDRAW")) balance -= amount; System.out.printf("[%s] %s: %.2f — balance: %.2f%n", owner, type, amount, balance); } } public Transaction createDeposit(double amt) { return new Transaction("DEPOSIT", amt); } } // Must create through an outer instance BankAccount acc = new BankAccount("Alice", 1000.0); BankAccount.Transaction t1 = acc.createDeposit(500.0); BankAccount.Transaction t2 = acc.new Transaction("WITHDRAW", 200.0); t1.execute(); // [Alice] DEPOSIT: 500.00 — balance: 1500.00 t2.execute(); // [Alice] WITHDRAW: 200.00 — balance: 1300.00

Memory leak: Transaction holds this$0 → the BankAccount instance. If a Transaction is stored in a static field, a cache, or a long-lived collection, the entire BankAccount can never be garbage collected, even if nothing else references it. This is one of the most common Java memory leaks. Fix: use a static nested class (which has no outer reference) or explicitly pass the needed outer data as constructor parameters.

Local class — defined inside a method body

A local class is declared inside a method (or a block). It can implement interfaces, extend classes, have multiple methods, and even have its own constructors. It can access effectively final local variables from the enclosing method — "effectively final" means the variable is never reassigned after initialization, even without the final keyword (Java 8+). Unlike anonymous classes, it has a name, so it can be instantiated multiple times inside the method.

public class TextProcessor { public List<String> processLines(List<String> lines, String prefix) { // 'prefix' is effectively final — never reassigned int lineCount = 0; // effectively final (only set here) // Local class — full class definition inside the method class LineFormatter { private final String content; LineFormatter(String content) { this.content = content; } String format(int lineNum) { // Captures 'prefix' from enclosing method return String.format("%s[%03d] %s", prefix, lineNum, content.trim()); } boolean isEmpty() { return content.isBlank(); } } List<String> result = new ArrayList<>(); for (String line : lines) { LineFormatter lf = new LineFormatter(line); // instantiate by name if (!lf.isEmpty()) { result.add(lf.format(++lineCount)); } } return result; } } // Output: ["LOG[001] First line", "LOG[002] Second line", ...]
Effectively final: If you try to reassign prefix after the local class is defined, the compiler will error: "Local variable prefix defined in an enclosing scope must be final or effectively final." This rule exists because the local class may outlive the method call — it captures a copy of the variable's value, not a live reference to the stack slot.

When local classes still make sense over lambdas

// Lambda: great for single-method interfaces (functional interfaces) Runnable r = () -> System.out.println("simple task"); // But local class is needed when: // 1. You need multiple methods in the implementation // 2. The class needs its own state / constructor // 3. You're implementing a non-functional interface (multiple abstract methods) // 4. You need to instantiate it more than once with different constructor args class TimedTask implements Runnable { private final String name; private final long startedAt = System.currentTimeMillis(); TimedTask(String name) { this.name = name; } public void run() { long elapsed = System.currentTimeMillis() - startedAt; System.out.printf("%s finished in %dms%n", name, elapsed); } long getStartTime() { return startedAt; } // extra method — no lambda } TimedTask t1 = new TimedTask("task-A"); TimedTask t2 = new TimedTask("task-B"); executor.submit(t1); executor.submit(t2);

Anonymous class — one-shot implementation with no name

An anonymous class is declared and instantiated in a single new expression. It either extends a class or implements an interface (not both). It has no name — you cannot refer to it by type anywhere else. Anonymous classes can have instance initializers but not explicit constructors (the only constructor it gets is the implicit one that matches the supertype's constructor it calls).

// Implementing an interface anonymously Comparator<String> byLength = new Comparator<String>() { @Override public int compare(String a, String b) { return Integer.compare(a.length(), b.length()); } }; // Extending a class anonymously Thread t = new Thread("worker") { @Override public void run() { System.out.println("Running: " + getName()); } }; // Anonymous class with instance initializer Map<String, Integer> map = new HashMap<String, Integer>() {{ put("one", 1); // outer {} = anonymous class body put("two", 2); // inner {} = instance initializer block put("three", 3); }}; // Note: "double brace initialization" creates an inner class that // holds a reference to the enclosing instance — avoid in production!

When anonymous classes still beat lambdas

// 1. Implementing a non-functional interface (2+ abstract methods) MouseAdapter handler = new MouseAdapter() { @Override public void mouseClicked(MouseEvent e) { ... } @Override public void mousePressed(MouseEvent e) { ... } // Lambda cannot do this — only one abstract method allowed }; // 2. Need to hold per-instance state Iterator<Integer> fib = new Iterator<Integer>() { int a = 0, b = 1; // state fields public boolean hasNext() { return true; } public Integer next() { int t = a; a = b; b = t + b; return t; } }; // A lambda cannot have mutable state (well — not without tricks) // 3. Need to override multiple methods from an abstract class AbstractAction saveAction = new AbstractAction("Save") { { putValue(ACCELERATOR_KEY, KeyStroke.getKeyStroke("ctrl S")); } public void actionPerformed(ActionEvent e) { document.save(); } };

Evolution: anonymous Runnable → local class → lambda

Java 1.1 — Anonymous class (pre-8)
Thread t = new Thread(new Runnable() { @Override public void run() { System.out.println("Hello from thread"); } }); t.start();
Java 1.1 — Named local class (slightly better readability)
class HelloTask implements Runnable { public void run() { System.out.println("Hello from thread"); } } new Thread(new HelloTask()).start();
Java 8 — Lambda (concise, no boilerplate)
new Thread(() -> System.out.println("Hello from thread")).start();
Java 8 — Method reference (most readable when task is a named method)
new Thread(MyClass::sayHello).start(); // Or with Executors (the modern way) ExecutorService exec = Executors.newSingleThreadExecutor(); exec.submit(MyClass::sayHello); exec.submit(() -> System.out.println("Hello from thread"));
When to keep anonymous class over lambda
// Use anonymous class when you need multiple methods: Comparator<Person> comp = new Comparator<Person>() { @Override public int compare(Person a, Person b) { ... } // Maybe we override equals() too for documentation @Override public String toString() { return "PersonByName"; } }; // Lambda: only works for single-abstract-method interfaces Comparator<Person> comp2 = (Person a, Person b) -> a.name().compareTo(b.name());

Builder pattern with static nested class — the canonical Java Builder

The Builder pattern uses a static nested class because the Builder needs to access the outer class's private constructor, but it doesn't need an existing outer instance to create a new one. The outer constructor is private, so only the nested Builder can call it. This enforces that the only way to build the object is through the builder.

1
Start builder: Person.builder() creates a new Person.Builder with all fields null/default.
Builder{name=null, age=null, email=null, phone=null}
2
Set name: .name("Alice") — sets the name field and returns this (the builder).
Builder{name="Alice", age=null, email=null, phone=null}
3
Set age: .age(30) — chained call, still the same builder instance.
Builder{name="Alice", age=30, email=null, phone=null}
4
Set email: .email("alice@example.com")
Builder{name="Alice", age=30, email="alice@example.com", phone=null}
5
Build: .build() validates required fields, then calls new Person(this) — the outer class's private constructor which reads all fields from the builder.
Person{name="Alice", age=30, email="alice@example.com", phone=null} ← immutable

The full Builder code

public final class Person { private final String name; private final int age; private final String email; private final String phone; // optional // Private — only Builder can call this private Person(Builder b) { this.name = b.name; this.age = b.age; this.email = b.email; this.phone = b.phone; } public static Builder builder() { return new Builder(); } // Getters... public String getName() { return name; } public int getAge() { return age; } public String getEmail() { return email; } // Static nested Builder — no outer instance needed public static class Builder { private String name; private int age; private String email; private String phone; public Builder name(String v) { name = v; return this; } public Builder age(int v) { age = v; return this; } public Builder email(String v) { email = v; return this; } public Builder phone(String v) { phone = v; return this; } public Person build() { if (name == null || name.isBlank()) throw new IllegalStateException("name is required"); if (age <= 0) throw new IllegalStateException("age must be positive"); return new Person(this); // calls Person's private constructor } } } // Usage — fluent, readable, immutable result Person p = Person.builder() .name("Alice") .age(30) .email("alice@example.com") .build();

Decision guide — which type to use?

static nested
The nested type is a helper, value type, or utility that is conceptually related to the outer class but does not need to operate on an outer instance. This is the default choice. Examples: Map.Entry, Person.Builder, Graph.Edge.
inner (non-static)
The nested type needs to directly access outer instance state as part of its core purpose, and you want the tight coupling to be explicit. Iterator implementations over outer collections are the classic example. Be cautious of memory leaks.
local class
You need a named class that is only used within one method, needs its own constructor or multiple methods, and should be invisible outside that method. Rare in modern Java.
anonymous class
One-shot implementation of a non-functional interface (multiple abstract methods), or you need per-instance state/multiple methods, but only need one instance. More common in legacy code and Swing/AWT.
lambda
Implementing a functional interface (single abstract method) and you don't need to name the type or add state. This covers the vast majority of modern use cases: Comparator, Runnable, event handlers, stream operations.
