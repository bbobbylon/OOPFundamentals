Spring Boot Application Events

Decouple your components with the publish-subscribe pattern. Events let one part of your app notify others without direct dependencies.

📣 What is the pub/sub pattern — and why does Spring use it for decoupling services?

Without events, creating a user forces UserService to know about — and call — EmailService, AuditService, ProvisioningService, and more; every new side effect edits UserService again, growing an unbounded "god service." Spring Application Events reverse that dependency: UserService publishes a UserCreatedEvent and knows nothing about who handles it, while each consumer independently listens via @EventListener. Adding a handler means adding a listener — the publisher is never touched.

  • Publisher and subscribers don't know each other — that's the whole decoupling win.
  • Listeners are synchronous by default; add @Async to run off the publishing thread.
  • Use AFTER_COMMIT for side effects so a rolled-back transaction never emails or webhooks.
  • In-process only. For cross-service or durable delivery, reach for Kafka/RabbitMQ instead.

Publish & listen

Event: record UserCreatedEvent(User user, String actor){}. Publish via injected ApplicationEventPublisher.publishEvent(...). Consume with @EventListener void onUserCreated(UserCreatedEvent e){...} — same thread unless you add @Async.

Transactional events

@TransactionalEventListener(phase=AFTER_COMMIT) fires only after the tx commits — essential for outbox-style work so a welcome email never goes out for a rolled-back user. Plain @EventListener may fire before commit.

Spring events vs Kafka/RabbitMQ

Spring events are in-JVM, share the transaction, and vanish if the app crashes (not durable). Use them inside one service for audits, notifications, cache eviction. Use Kafka/RabbitMQ for cross-service, guaranteed-delivery, high-throughput flows.

CIAM: UserCreatedEvent, UserLockedEvent, RoleAssignedEvent, PasswordResetRequestedEvent. createUser() publishes UserCreatedEvent; a @TransactionalEventListener(AFTER_COMMIT) sends the welcome email and an @Async @EventListener writes the audit entry — three listeners today, and a fourth changes nothing in UserService.

The problem

Three listeners, one event, one throws. How many actually ran?

auditOrderCreation() throws, and updateInventory() just… never happens

OrderEventHandlers — the class from Section 3 — registers three listeners for OrderCreatedEvent that matter here: auditOrderCreation() at @Order(1), updateInventory() at @Order(2), and sendConfirmationEmail(), which carries no @Order at all. Order #4521 comes in. auditLog.record("ORDER_CREATED", 4521) hits a connection pool that's momentarily exhausted and throws. Nothing about that should touch inventory or email — separate methods, separate concerns, the entire pitch of pub/sub is that they don't know about each other. And yet: no inventory reservation. No confirmation email. No error logged for either one — because neither one was ever called. The order exists. The warehouse has no idea it exists.

OrderCreatedEvent published ✓ auditOrderCreation() @Order(1) — throws updateInventory() @Order(2) — never invoked sendConfirmationEmail() (unordered) — never invoked

Not two bugs. One exception, and a dispatch loop that had nowhere else to go.

Give the loop somewhere to go besides up
Define your own bean named applicationEventMulticaster ↓ that exact name is what Spring looks for before it falls back to creating its own SimpleApplicationEventMulticaster Call setErrorHandler(ex -> log.error("listener failed", ex)) on it ↓ now invokeListener() wraps each call in try/catch and hands the throwable to your handler instead of rethrowing it auditOrderCreation() can still throw on connection-pool exhaustion — updateInventory() and sendConfirmationEmail() run anyway
Pub/sub decouples who publishes from who's listening. By default, it does not decouple one listener's exception from the next listener's turn. @Order gives you a sequence. It was never a promise that the sequence survives contact with a thrown exception.
Think of a synchronous @EventListener chain as a bucket brigade, not a group text. A group text reaches every phone on its own — one dead phone doesn't touch the others. A bucket brigade hands the same bucket down a line of people, one at a time; drop it at position one, and positions two and three never even see it, fire or no fire.
You

auditOrderCreation() failed on order #4521 last night. Why didn't the warehouse get its inventory update anyway? Those are two completely unrelated listeners.

publishEvent()

Unrelated to each other, sure. Not unrelated to me. I don't run either one myself — I hand your event to the multicaster and wait for it to hand control back. Last night, it didn't hand control back. It handed me an exception instead.

SimpleApplicationEventMulticaster

I run every listener registered for one event in a single loop, in @Order sequence, one at a time, on whatever thread called me. Nobody told me what to do when one throws, so my default is the obvious one: I stop, and I let it throw right back at whoever's iterating me.

updateInventory()

And I was next in that loop. I wasn't skipped with a warning. I wasn't called at all. There's a difference — last night it was the difference between a missing shipment and a logged one.

The mechanism

One publishEvent() call. One loop. Follow it to the exact line that decides this.

  1. createOrder() calls publisher.publishEvent(new OrderCreatedEvent(4521, …)) — one line, no try/catch around ityour code
  2. AbstractApplicationEventMulticaster resolves every listener registered for OrderCreatedEvent and sorts them — @Order value ascending, unordered listeners default to Ordered.LOWEST_PRECEDENCE and sort lasthappens once, at dispatch
  3. SimpleApplicationEventMulticaster walks that sorted list in a plain for-loop, on the calling thread, one listener at a time — unless a given listener is @Async, in which case only that one gets handed to an executorthis loop is the whole story
  4. For each listener, invokeListener() checks whether a custom ErrorHandler bean was ever configured. Out of the box: nothe missing safety net
  5. auditOrderCreation() throws. With no ErrorHandler, invokeListener() doesn't catch it — it climbs straight out of multicastEvent(), and the for-loop dies mid-iterationthe loop stops, it doesn't continue
  6. Everything later in that sorted list — updateInventory(), sendConfirmationEmail(), however many more you add next year — is simply never reached. publishEvent() then rethrows the same exception back to createOrder()collateral, not a bug report

Step 4 is the whole lesson. There's a real hook for making this loop fault-tolerant — Spring built it in — and out of the box, nobody wires it. That's not a bug in Spring; a shared, ordered, synchronous loop with no error handler is exactly what @Order asked for. The mistake is assuming @Order also bought you isolation. It bought you sequence.

OrderCreatedEventpublished once, from one line of code
multicastEvent() walks its sorted listener list ↓
auditOrderCreation() @Order(1) — throws no ErrorHandler configured — the loop dies right here updateInventory() @Order(2) — never reached sendConfirmationEmail() unordered — never reached

Swap in a custom applicationEventMulticaster with an ErrorHandler and this fan doesn't change shape — every listener still gets a turn, in the same order. What changes is that a thrown exception stops being a roadblock and becomes just… a logged line, with the loop already past it.

OrderEventHandlers registers auditOrderCreation() at @Order(1), updateInventory() at @Order(2), and sendConfirmationEmail() with no @Order at all — all three listening for OrderCreatedEvent, all synchronous, no custom ErrorHandler configured anywhere. On order #4521, auditOrderCreation() throws. Which of the three actually ran?

Exactly. Spring's default SimpleApplicationEventMulticaster runs listeners for one event in a single synchronous for-loop, sorted by @Order, on the calling thread. With no ErrorHandler configured — the out-of-the-box state — invokeListener() doesn't catch what auditOrderCreation() throws; it lets it climb out, and the loop dies right there. updateInventory() and sendConfirmationEmail() don't fail. They're never called.

This is the trap the whole page sets up for you: pub/sub decouples the publisher from needing to know its listeners. It says nothing about decoupling the listeners from each other. They share one loop, one thread, one @Order sequence — "independent" describes who calls them, not what happens when one of them throws.

Missing @Order doesn't mean "skipped" — it means Ordered.LOWEST_PRECEDENCE, dead last in line, but still in line. If auditOrderCreation() hadn't thrown, sendConfirmationEmail() would have run fine, just after the other two. What actually determines who runs isn't whether a listener has an @Order — it's whether the loop is still alive by the time it's their turn.

Where you've seen this before

Three places you've already trusted a chain to keep going — and one where you helped build it.

Array.prototype.forEach — same trap, same fix

orders.forEach(o => processOrder(o)) runs the same way: one synchronous loop, and a thrown exception inside one callback stops the iteration cold — everything after it in the array never gets processed. Promise.allSettled() exists specifically because forEach/for...of give you zero isolation between iterations; it runs every promise to completion and hands you a result per item, failures included.

forEach() ≈ the multicaster's loop

Spring Security's own FilterChain — the pattern you use every day

You've spent five pages watching a Spring Security filter chain: each filter calls chain.doFilter(request, response) to hand off to the next one. A filter that throws instead of calling that method stops the chain exactly the way auditOrderCreation() does — everything registered after it, including filters with nothing to do with whatever went wrong, never runs. Same shape: an ordered, synchronous, shared loop with no isolation baked in.

FilterChain.doFilter() ≈ multicastEvent()'s loop

Your own SCIM sync, one listener behind an audit log

Say RoleAssignedEvent — already on this page's own CIAM list — fires two synchronous listeners: auditRoleChange() at @Order(1), then syncRoleToEntra() at @Order(2) pushing the new role to Entra via Graph API. Let the audit call throw — a timeout, a transient 500 — and the Entra sync never fires. Nothing logs "SCIM sync skipped." The user just quietly keeps the wrong permissions in the downstream IdP until someone notices.

one throw, one silently un-synced identity
Questions from the back row

Doesn't @Async fix this too, the same way @TransactionalEventListener's AFTER_COMMIT does?

Differently, but yes for isolation specifically. An @Async listener is handed to an executor — executor.execute(...) — and that call returns immediately, before the listener body ever runs; the throw, if any, happens later, on a pool thread, completely outside the synchronous for-loop. It can't block or skip siblings dispatched in the same pass. The tradeoff: nobody who called publishEvent() will ever see that exception either, unless you separately register an AsyncUncaughtExceptionHandler — a silent failure of a different kind.

So should every listener just be @Async, if I don't want one failure to cancel the others?

If strict cross-listener ordering doesn't matter to you, that's the cleanest fix — each one gets its own dispatch call, so there's no shared loop left to break. Reach for the custom ErrorHandler instead when you need to stay synchronous on purpose: because a later listener's timing genuinely depends on an earlier one finishing first, or because you're relying on @TransactionalEventListener's phase to fire before the method returns.

Does this apply to @TransactionalEventListener the same way?

Same multicaster, same loop, same rule. Register two @TransactionalEventListener(AFTER_COMMIT) methods for one event, and if the first one (by @Order) throws, the second one in that phase is skipped exactly like updateInventory() was. The phase only decides when the loop runs, relative to the transaction — not what happens once something inside it throws.

1. The Publish-Subscribe Pattern

The event system lets components communicate without knowing about each other. A publisher fires an event; one or more listeners handle it. The publisher doesn't know or care how many listeners exist or what they do.

Spring's event system is synchronous by default — all listeners run in the publisher's thread before publishEvent() returns. Use @Async to make a listener non-blocking.

2. Creating and Publishing Custom Events

Option A — POJO event (Spring 4.2+, preferred)

// No superclass needed since Spring 4.2 public class OrderCreatedEvent { private final Long orderId; private final String customerEmail; private final BigDecimal amount; // constructor, getters... } @Service public class OrderService { private final ApplicationEventPublisher events; public OrderService(ApplicationEventPublisher e) { this.events = e; // injected by Spring } public Order createOrder(CreateOrderRequest req) { Order order = orderRepo.save(new Order(req)); events.publishEvent( new OrderCreatedEvent( order.getId(), req.getEmail(), req.getTotal() ) ); return order; } }

Option B — Extend ApplicationEvent (legacy)

// Old-style — source is the publisher object public class UserRegisteredEvent extends ApplicationEvent { private final String username; public UserRegisteredEvent( Object source, String username) { super(source); this.username = username; } public String getUsername() { return username; } } // Older listener style — interface based @Component public class WelcomeEmailSender implements ApplicationListener<UserRegisteredEvent> { @Override public void onApplicationEvent( UserRegisteredEvent event) { sendWelcomeEmail(event.getUsername()); } }
Prefer POJOs + @EventListener over ApplicationEvent. Less boilerplate and cleaner separation.

3. @EventListener — Ordering, Conditions, Async

@Component public class OrderEventHandlers { // Basic listener — method name doesn't matter @EventListener public void sendConfirmationEmail(OrderCreatedEvent event) { emailService.send(event.getCustomerEmail(), "Order confirmed #" + event.getOrderId()); } // @Order controls execution order among listeners for the same event // Lower numbers run first. Default is Ordered.LOWEST_PRECEDENCE. @EventListener @Order(1) // runs first public void auditOrderCreation(OrderCreatedEvent event) { auditLog.record("ORDER_CREATED", event.getOrderId()); } @EventListener @Order(2) // runs second public void updateInventory(OrderCreatedEvent event) { inventoryService.reserve(event.getOrderId()); } // Conditional — SpEL condition on the event itself // Listener only fires if amount > 1000 @EventListener(condition = "#event.amount > 1000") public void flagHighValueOrder(OrderCreatedEvent event) { fraudDetection.flag(event.getOrderId()); } // Async — runs in a separate thread, non-blocking // Requires @EnableAsync on a @Configuration class @EventListener @Async public void sendSmsNotification(OrderCreatedEvent event) { // runs in thread pool, doesn't block createOrder() smsService.send(event.getCustomerPhone(), "Your order is confirmed!"); } // Listen to multiple event types @EventListener({OrderCreatedEvent.class, OrderShippedEvent.class}) public void logOrderActivity(Object event) { log.info("Order activity: {}", event.getClass().getSimpleName()); } // Return a value to publish another event (event chaining) @EventListener public InvoiceEvent onOrderCreated(OrderCreatedEvent event) { // return value auto-published as a new event! return new InvoiceEvent(event.getOrderId(), event.getAmount()); } }

4. @TransactionalEventListener — Fire After DB Commit

A critical problem: if you publish an event inside a @Transactional method and a listener queries the DB, the data might not be committed yet. @TransactionalEventListener lets you control exactly when in the transaction lifecycle a listener fires.

The problem with regular @EventListener

@Service public class OrderService { @Transactional public Order createOrder(req) { Order order = repo.save(req); // Event fires NOW — inside tx! // If listener queries the DB, it // might not see the new order yet // because it hasn't committed. events.publishEvent( new OrderCreatedEvent(order)); return order; // tx commits HERE } }

The fix — @TransactionalEventListener

@Component public class OrderEventHandlers { // Default phase: AFTER_COMMIT @TransactionalEventListener public void onOrderCommitted( OrderCreatedEvent event) { // Data is in DB when this runs ✓ emailService.send(event.getEmail()); } @TransactionalEventListener( phase = TransactionPhase.BEFORE_COMMIT ) public void validateBeforeCommit( OrderCreatedEvent event) { // Can throw to roll back the tx fraudService.validate(event); } @TransactionalEventListener( phase = TransactionPhase.AFTER_ROLLBACK ) public void cleanupOnRollback( OrderCreatedEvent event) { // Compensating action on failure cache.evict(event.getOrderId()); } }

TransactionPhase enum

BEFORE_COMMIT
Fires just before the transaction commits. Can throw to cause rollback. Rarely needed.
AFTER_COMMIT ← default
Fires after successful commit. DB data guaranteed visible. Use this for notifications, outbox patterns, cache updates.
AFTER_ROLLBACK
Fires after the transaction rolls back. Use for cleanup/compensating actions (e.g. release a lock you acquired).
AFTER_COMPLETION
Fires regardless of commit or rollback. Use for cleanup that must always happen (e.g. close a resource).
Warning: @TransactionalEventListener only fires if there is an active transaction. If the event is published outside a @Transactional method, the listener is silently skipped (AFTER_COMMIT phase, no active tx = nothing to commit). Add fallbackExecution = true to also fire when there's no tx.

5. Built-in Spring Boot Lifecycle Events

Spring Boot publishes its own events during application startup and shutdown. Listen to these to run initialization code at the right moment.

ApplicationStartingEvent
Fires at the very start, before anything is created. Logging not yet available. Rarely useful.
ApplicationEnvironmentPreparedEvent
Environment is ready, context not yet created. Useful for programmatic property source manipulation.
ApplicationContextInitializedEvent
ApplicationContext created and initialized, but beans not loaded yet.
ApplicationPreparedEvent
Bean definitions loaded, auto-configuration applied, but beans not instantiated yet.
ContextRefreshedEvent
All beans are created and wired. Context is ready. Good for post-startup initialization. Also fires on context refresh (rare).
ApplicationStartedEvent
App started, before CommandLineRunner / ApplicationRunner execute. Context is fully refreshed.
ApplicationReadyEvent ← most useful
Best place for post-startup logic. CommandLineRunners are done. App is accepting traffic. Cache warm-up, subscribe to queues here.
ApplicationFailedEvent
Application failed to start. Use for cleanup / alert notification on startup failure.

Listening to lifecycle events

@Component public class CacheWarmup { // Best practice: use ApplicationReadyEvent for startup work @EventListener(ApplicationReadyEvent.class) public void warmUpCache() { log.info("App ready — warming up cache"); productCacheService.loadAll(); } } // You can also use CommandLineRunner or ApplicationRunner // They run AFTER context refresh, BEFORE ApplicationReadyEvent @Component @Order(1) public class DataSeeder implements CommandLineRunner { @Override public void run(String... args) { // runs at startup, receives CLI args } }
