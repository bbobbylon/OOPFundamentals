Reactive Forms & Validation (auth)

A registration form is the most validation-heavy screen in a CIAM app — and a great teacher. The client mirrors the server's rules so users fail fast, adds cross-field (password match) and async (username taken) checks the server alone can't give instantly, and gracefully maps the server's real errors back onto fields. The form below is live — type in it.

✅ Why validate a CIAM form in BOTH Angular AND Spring — and why differently?

Angular validation is UX: it tells the user "your email is invalid" instantly, with no server round-trip. Spring validation is security: it enforces the real business rules and can't be bypassed. You need both — client-side is fast and responsive, but any HTTP client (Postman, a script) can skip the Angular form and hit the API directly. So Spring re-validates the same rules with @Valid + Bean Validation, and Angular must gracefully display whatever errors the server returns for things it didn't catch.

  • Client validation = instant feedback; server validation = the actual enforcement. Never ship only the first.
  • Built-in validators (required, email, minLength, pattern) chain on a control; check with control.hasError('...').
  • Cross-field rules (password === confirm) live on the parent FormGroup, not a single control.
  • Async validators (is this email taken?) return an Observable and should debounce so they don't fire per keystroke.
  • Map server errors back onto the right field with control.setErrors({ serverError: '…' }) so the message lands where the user looks.

Built-in validators

Validators.required, Validators.email, Validators.minLength(8), Validators.pattern(/…/) — chain as an array: new FormControl('', [Validators.required, Validators.email]). Check control.hasError('email').

Cross-field validator

Passwords must match — neither field knows the other, so attach to the group: new FormGroup({ pw, confirm }, { validators: passwordsMatch }). It reads both and returns null or { passwordsMismatch: true }; show via form.hasError('passwordsMismatch').

Async validator — username taken?

Returns Observable<ValidationErrors|null>: call GET /api/users/exists?email=… → null or { emailTaken: true }. Debounce with timer(400).pipe(switchMap(...)); Angular shows a pending state while it waits.

In CIAM:a registration form — email (required + format + async "taken?"), password (required + minLength(12) + complexity pattern), confirmPassword (cross-field match). On submit it POSTs to Spring; if Spring returns 400 with {"errors":{"email":"already registered"}}, Angular does form.get('email').setErrors({ serverError: 'already registered' }) to surface it on the right field.

The problem

You wired the submit button to form.invalid. Someone still managed to click it too early.

The button re-enabled itself while a check was still in flight

You bind [disabled]="registerForm.invalid". Every rule looks right — required, email pattern, password length, the cross-field match — and by hand the form behaves exactly how you'd expect: type garbage, button stays off; fix the fields, button lights up. Then on a slower connection someone types a username, and in the half-second before the "taken?" check answers, they click submit and it goes through. Nothing about your validators is wrong. The bug is that invalid was never the question you needed to ask.

required / email / minLength pass ✓ confirm matches password ✓ form.invalid === false mid-check ⚠ the async verdict hasn't arrived yet ⚠

The assumption underneath: "invalid" and "not yet known to be valid" feel like the same thing. Angular tracks them as two different statuses, and only one of them disables anything by default.

Gate on the third status too, not just the second one
[disabled]="registerForm.invalid" ↓ this only ever looks at two of Angular's three settled outcomes [disabled]="registerForm.invalid || registerForm.pending" ↓ pending now blocks the click for exactly the window an async validator is running The click becomes impossible until every validator — sync and async — has actually answered
Valid isn't the opposite of invalid — pending is a third status, and it means "don't know yet." That one sentence is why gating a submit button on invalid alone under-protects the moment you add an async validator, why the async check needs debouncing instead of firing on every keystroke, and why the server re-runs the same rule anyway: nothing the client reports is a promise, only a prediction with a network delay attached.
Think of an async validator as a bouncer radioing the front desk to confirm your name is on the list. You're standing right at the door while that call happens — not let in, but not turned away either, just... pending. The door only stays locked if someone tells it to stay shut during the radio call; otherwise you can just walk through while dispatch is still talking.

The mechanism

Type one character in the username box. Four different things start timing themselves.

  1. The keystroke updates the FormControl's value immediatelysynchronous, always
  2. Every sync validator on that control re-runs right away — required, minLength(3), maxLength(50) — no network, no delaythe fast, free pass
  3. Only if every sync validator passes does Angular even call the async validator function at alla failed sync check skips async entirely
  4. Calling that function already flips the control's status to PENDING — before the debounce timer inside it has elapsed, before any request existsPENDING starts before the request does
  5. Once the pause fires, the HTTP call actually goes out, and the control stays PENDING for the whole round tripthis window is where an under-guarded submit button leaks
  6. The Observable emits null or {taken:true}, the control resolves to VALID or INVALID, and the FormGroup's own status is recomputed from every child — never storedthe parent has no status of its own

Step 4 is the one to remember. PENDING begins the instant Angular decides to run the async check — not when a network request actually leaves the browser. That gap between "validation is running" and "a request is in flight" is exactly why debounce lives inside the validator instead of on the input event, and exactly why checking pending, not just invalid, is the only way to make a submit button trustworthy.

Three of these settle in the same tick, synchronously, for free. The fourth is the one holding the whole group's status at PENDING until a server round-trip finishes — the box a disabled-submit check has to include, or it isn't really guarding anything.

A field has Validators.required and the async usernameAvailable validator. The user types a username; the async validator's timer(400) hasn't elapsed yet, so no HTTP request has been created. Is the submit button — gated on invalid || pending — disabled right now?

A completely reasonable read of the word "pending" — surely nothing is pending until something is actually happening over the network. But Angular's status model doesn't wait for the Observable to do anything observable. The moment it calls your async validator function and gets an Observable back, the control is marked PENDING, full stop. The timer(400) just delays what happens inside that already-pending window.

Right — and this is the detail that makes || pending load-bearing rather than decorative. The 400ms isn't a delay before pending starts, it's a delay while pending, baked into the validator's own pipe. From the FormGroup's point of view, the async check began the instant it was asked to run.

updateOn: 'blur' changes when Angular re-runs validators — on blur instead of on every keystroke — not what PENDING means once a validator does run. Set it and you'll see fewer PENDING windows, not different behavior inside the ones you get. It's a real setting in this exact form (line 9 of the code walk above) — just answering a different question than the one being asked here.

Where you've seen this before

A three-state form model, a database that doesn't care what the browser thought, and the identity provider that has the last word.

React Hook Form's isValidating — the same third state, a different name

Every serious form library reinvents this exact state machine, because "not yet erroring" and "confirmed fine" genuinely cannot collapse into one boolean once a check leaves the browser. React Hook Form exposes formState.isValidating for precisely this reason. Guard a submit button on isValid alone over there and you've written the identical bug in different syntax.

PENDING ≈ isValidating

A SQL UNIQUE constraint doesn't care what your SELECT said a moment ago

The async validator's GET only proves the username was free when that query ran — not when the server's INSERT commits a few hundred milliseconds later. Two people registering the same name inside that window both pass the check. The only thing that's actually authoritative is a UNIQUE index on the column and a handled constraint violation; everything upstream of that, your Angular form included, is a courtesy.

the SELECT stops being true the instant two people race it

Self-registration against Ping or Entra hits this window twice

A sign-up screen that checks email or username availability against Ping's directory (or via Microsoft Graph for Entra) races the same PENDING window — and then meets it again one layer up. The directory itself re-validates uniqueness and any server-side password policy at the moment of the actual write, and can reject a submission your Angular form and your own API both already approved. Two layers said "looks fine"; only the last one actually decided.

the directory write is the only real yes
Questions from the back row

If the server re-validates everything anyway, why bother with async client validation at all?

Because the alternative is a full round trip and a page of red text after the user has already filled out the whole form and hit submit. The async validator's entire job is UX: catch the common case — this username is obviously taken — in the few hundred milliseconds while they're still looking at that one field, so the only surprises left at submit are the ones that genuinely require a write to detect, like the UNIQUE-constraint race above. It's an optimization for the common path, never a substitute for the server's own check.

Why does the async validator need debouncing — won't Angular only call it once the value "settles"?

No — by default a FormControl re-validates on every value change, which for a text input means every keystroke. Undebounced, typing a 10-character username can fire up to 10 requests, most already stale by the time they land — and because responses can arrive out of order, a slow early response can overwrite a fast later one and show the wrong verdict. timer(400).pipe(switchMap(...)) fixes both problems: it waits for a pause, and switchMap cancels the previous in-flight request the moment a new one starts.

Should I ever trust form.valid alone to gate a submit button?

Only on a form with zero async validators — and even then, only for UX, never as an actual security boundary. The moment you add one async check, valid and invalid stop being a complete pair, because PENDING exists, so invalid alone under-disables. And no matter what the client reports, the request that actually creates the account is validated again server-side — the client's status is a UI convenience, not a gate anyone downstream is relying on.

1. Mirror the server, then add what it can't

This app's RegisterRequest validates: username @Size(3,50), email @Email, password @Size(min=8). The client copies those for instant feedback — then adds two it can't do synchronously:

  • Cross-field — "confirm password" must equal "password" (a group-level validator).
  • Async — "is this username taken?" (a debounced call to the API → pending → valid/taken).

2. Interactive: a live registration form

3. The form

form = this.fb.group({
  username: ['', [Validators.required, Validators.minLength(3), Validators.maxLength(50)],
                [this.usernameAvailable]],          // async validator (3rd arg)
  email:    ['', [Validators.required, Validators.email]],
  password: ['', [Validators.required, Validators.minLength(8)]],
  confirm:  ['', [Validators.required]],
}, { validators: matchFields('password', 'confirm') });  // group-level

// debounced async validator
usernameAvailable = (c: AbstractControl) => this.api.check(c.value).pipe(
  map(taken => taken ? { taken: true } : null));

4. Showing errors well (and mapping the server's)

  • Only after interaction. Show a control's error when it's touched/dirty, not on first paint — don't yell at an empty form.
  • Disable submit while form.invalid || form.pending (pending = async still running). Show a spinner during pending.
  • Map server errors back. A 400 with field errors or this app's 409 "username taken" → control.setErrors({ server: msg }) so it lands on the right field, not a toast.
  • Don't fully duplicate the server. Mirror cheap rules for UX; the server stays authoritative (it re-validates every request). Some rules (uniqueness, business logic) are server-only.
  • Accessibility: aria-invalid + link the message with aria-describedby.

5. One-sentence recap

📝 Build the auth form as a typed FormGroup whose validators mirror the server (required/min/max/email) for instant feedback, add a group-level validator for password-match and a debounced async validator for username availability, keep submit disabled while invalid || pending, show errors only after touched, and map the server's real 400/409 errors back onto the offending control with setErrors — all while remembering the server stays authoritative.
