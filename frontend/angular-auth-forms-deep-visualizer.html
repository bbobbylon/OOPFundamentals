Reactive Forms & Validation (auth)

A registration form is the most validation-heavy screen in a CIAM app — and a great teacher. The client mirrors the server's rules so users fail fast, adds cross-field (password match) and async (username taken) checks the server alone can't give instantly, and gracefully maps the server's real errors back onto fields. The form below is live — type in it.

1. Mirror the server, then add what it can't

This app's RegisterRequest validates: username @Size(3,50), email @Email, password @Size(min=8). The client copies those for instant feedback — then adds two it can't do synchronously:

  • Cross-field — "confirm password" must equal "password" (a group-level validator).
  • Async — "is this username taken?" (a debounced call to the API → pending → valid/taken).

2. Interactive: a live registration form

Submit stays disabled until the whole group is valid and the async check resolves. Type admin as the username to see the async "taken" error; submit with username bob to see a server 409 mapped back onto the field.

3. The form

form = this.fb.group({
  username: ['', [Validators.required, Validators.minLength(3), Validators.maxLength(50)],
                [this.usernameAvailable]],          // async validator (3rd arg)
  email:    ['', [Validators.required, Validators.email]],
  password: ['', [Validators.required, Validators.minLength(8)]],
  confirm:  ['', [Validators.required]],
}, { validators: matchFields('password', 'confirm') });  // group-level

// debounced async validator
usernameAvailable = (c: AbstractControl) => this.api.check(c.value).pipe(
  map(taken => taken ? { taken: true } : null));

4. Showing errors well (and mapping the server's)

  • Only after interaction. Show a control's error when it's touched/dirty, not on first paint — don't yell at an empty form.
  • Disable submit while form.invalid || form.pending (pending = async still running). Show a spinner during pending.
  • Map server errors back. A 400 with field errors or this app's 409 "username taken" → control.setErrors({ server: msg }) so it lands on the right field, not a toast.
  • Don't fully duplicate the server. Mirror cheap rules for UX; the server stays authoritative (it re-validates every request). Some rules (uniqueness, business logic) are server-only.
  • Accessibility: aria-invalid + link the message with aria-describedby.

↪ The backend rules: Spring · Validation + REST API Design (ProblemDetail). The failure round-trip: Angular · Error Handling (E2E).

5. One-sentence recap

📝 Build the auth form as a typed FormGroup whose validators mirror the server (required/min/max/email) for instant feedback, add a group-level validator for password-match and a debounced async validator for username availability, keep submit disabled while invalid || pending, show errors only after touched, and map the server's real 400/409 errors back onto the offending control with setErrors — all while remembering the server stays authoritative.
