Pagination & Filtering

Every production REST API returns large lists — you need to page them and filter them. Spring Data makes both trivially easy with Pageable, Page<T>, and Specification.

📄 Why do APIs paginate — and what does the Spring Page<T> response look like to Angular?

A user system with 50,000 users can't return them all from GET /api/users — it would take seconds, burn ~50MB, and crash the browser rendering 50,000 rows. Pagination returns one page (say 20) plus metadata about the whole set (total count, current page, size, has-next). Angular reads the metadata to draw a paginator and requests ?page=1&size=20 on "Next." Spring Data's Pageable auto-reads page/size/sort, and Page<T> wraps the rows with all that metadata — no manual offset/limit math.

  • Never return an unbounded list. Bound it and report the total separately.
  • Pageable is automatic. Add the param and Spring binds page/size/sort for you.
  • Cap the page size. max-page-size stops a ?size=100000 DoS.
  • Offset vs cursor. Offset is simple but slow at large offsets; cursors (nextLink) scale for big or external datasets.

Page<T> JSON shape

{ "content":[…], "totalElements":50000, "totalPages":2500, "number":0, "size":20, "first":true, "last":false }. Angular uses content for rows, totalElements for the total, number for the current page, and first/last to disable prev/next.

Controller + repository

@GetMapping Page<UserResponse> getUsers(Pageable p) reads ?page=0&size=20&sort=email,asc; the repo's findAll(Pageable) does the rest. @PageableDefault(size=20) sets defaults; spring.data.web.pageable.max-page-size=100 caps abuse.

Cursor vs offset

Offset (LIMIT 20 OFFSET 1000) is native but scans 1020 rows to return 20. Cursor pagination passes a stable marker (last ID/timestamp) — ?after=… — and stays fast at scale. IDM APIs use it (@odata.nextLink, nextPageToken).

CIAM: Your internal DB uses Spring offset paging (Page<UserDto>). The Entra ID Graph API is cursor-based — GET /v1.0/users?$top=20 returns an @odata.nextLink; Angular stores it in a signal<string|null> and "Previous" means caching prior pages client-side. Ping Directory returns an x-first-result-cookie. Know which model the API you're calling uses.

1 — Why You Can't Just Return a List

Without pagination — broken at scale
GET /api/products

→ SELECT * FROM product;
→ loads 250,000 rows into memory
→ serializes entire result to JSON
→ sends ~40 MB over the wire

Result: OutOfMemoryError, 30 s timeouts, frustrated users
With pagination — production-ready
GET /api/products?page=0&size=20&sort=name,asc

→ SELECT * FROM product ORDER BY name LIMIT 20 OFFSET 0
→ loads exactly 20 rows
→ returns structured Page response
→ ~4 KB over the wire

Result: fast, predictable, client knows total pages

2 — The Page<T> Response — What Spring Returns

Click any field to see what it means:

Page<ProductDto> — JSON response body
"content":
[…]
The actual items for this page — an array of your DTO objects. Length ≤ page size.
"totalElements":
247
Total number of matching rows in the database (across ALL pages). The client uses this to say "247 products found".
"totalPages":
13
ceil(totalElements / pageSize) — how many pages exist. The client renders the page selector from this number.
"number":
0
The current page index — zero-based. Page 1 in the UI = number 0 in the API. This is a common off-by-one trap.
"size":
20
How many items were requested per page. May differ from content.length on the last page if fewer items remain.
"first":
true
true if this is the first page (number == 0). Lets the client disable the "Previous" button without computing it.
"last":
false
true if this is the final page. Lets the client disable the "Next" button.
"empty":
false
true if content is empty (totalElements == 0 or page number exceeds last page). Useful for "No results" UI states.

3 — Repository & Controller Wiring

Adding pagination to an existing repository method takes one line — add Pageable as a parameter:

// ProductRepository.java — extend JpaRepository (already includes PagingAndSortingRepository) public interface ProductRepository extends JpaRepository<Product, Long> { // No pagination — DON'T use in production for large tables List<Product> findAll(); // With pagination — Spring Data builds the LIMIT/OFFSET SQL automatically Page<Product> findAll(Pageable pageable); // Filtering + pagination together Page<Product> findByCategoryAndPriceLessThanEqual(String category, BigDecimal maxPrice, Pageable pageable); }
// ProductController.java — Spring resolves Pageable from query parameters automatically @RestController @RequestMapping("/api/products") public class ProductController { @GetMapping public Page<ProductDto> list( @PageableDefault(size = 20, sort = "name") // defaults if client sends no params Pageable pageable) { return productRepo.findAll(pageable) .map(productMapper::toDto); // map Entity → DTO before sending } } // Client calls: // GET /api/products → page=0, size=20, sort=name,asc (defaults) // GET /api/products?page=2&size=10 → page 2, 10 items per page // GET /api/products?sort=price,desc → sort by price descending // GET /api/products?sort=name,asc&size=5 → sort by name, 5 per page

5 — Simple Filtering with @RequestParam

For a small, fixed set of known filters, just take @RequestParam values and use derived query methods or JPQL:

@GetMapping public Page<ProductDto> list( @RequestParam(required = false) String category, @RequestParam(required = false) BigDecimal maxPrice, @RequestParam(required = false) Boolean inStock, @PageableDefault(size = 20) Pageable pageable) { // Build query dynamically only when the param was supplied if (category != null && maxPrice != null) { return repo.findByCategoryAndPriceLessThanEqual(category, maxPrice, pageable) .map(mapper::toDto); } if (category != null) { return repo.findByCategory(category, pageable).map(mapper::toDto); } return repo.findAll(pageable).map(mapper::toDto); } // GET /api/products?category=Electronics&page=0&size=10 // GET /api/products?category=Books&maxPrice=25.00&sort=price,asc
Limitation: this approach creates an explosion of findBy… methods as filters grow. With 5+ optional filters use Specification instead (Section 6).

6 — Dynamic Filtering with JPA Specification

A Specification<T> wraps a single JPA Criteria predicate. You compose them at runtime — only applying the ones the client actually requested:

// Step 1 — repository must extend JpaSpecificationExecutor public interface ProductRepository extends JpaRepository<Product, Long>, JpaSpecificationExecutor<Product> {} // adds findAll(Specification, Pageable) // Step 2 — a helper class of reusable Specification factories public class ProductSpecs { public static Specification<Product> hasCategory(String category) { return (root, query, cb) -> cb.equal(root.get("category"), category); } public static Specification<Product> priceLessThanOrEqual(BigDecimal max) { return (root, query, cb) -> cb.lessThanOrEqualTo(root.get("price"), max); } public static Specification<Product> nameContains(String keyword) { return (root, query, cb) -> cb.like(cb.lower(root.get("name")), "%" + keyword.toLowerCase() + "%"); } public static Specification<Product> inStock() { return (root, query, cb) -> cb.greaterThan(root.get("stockQuantity"), 0); } } // Step 3 — compose only the specs the client actually sent @GetMapping public Page<ProductDto> search( @RequestParam(required = false) String category, @RequestParam(required = false) BigDecimal maxPrice, @RequestParam(required = false) String keyword, @RequestParam(required = false) Boolean inStock, @PageableDefault(size = 20) Pageable pageable) { Specification<Product> spec = Specification.where(null); // start with "match all" if (category != null) spec = spec.and(ProductSpecs.hasCategory(category)); if (maxPrice != null) spec = spec.and(ProductSpecs.priceLessThanOrEqual(maxPrice)); if (keyword != null) spec = spec.and(ProductSpecs.nameContains(keyword)); if (Boolean.TRUE.equals(inStock)) spec = spec.and(ProductSpecs.inStock()); return repo.findAll(spec, pageable).map(mapper::toDto); // Spring generates: SELECT * FROM product WHERE ... LIMIT ? OFFSET ? // Hibernate counts: SELECT COUNT(*) FROM product WHERE ... (for totalElements) }
