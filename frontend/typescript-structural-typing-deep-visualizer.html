Structural Typing — "If it walks like a duck…"

The single biggest mental shift coming from Java/C#. TypeScript decides type compatibility by shape, not by name. Two classes that never heard of each other are interchangeable if their members line up. Here's exactly how that works — and when you'd want to opt out.

🦆 What is structural typing — and why is it the biggest mental shift coming from Java?

Coming from Java/C#, this is the biggest shift: their compatibility is nominal (types match only via explicit extends/implements), but TypeScript is structural — two types are compatible if they have the same shape, regardless of declaration or hierarchy. Point and Vector with the same fields are interchangeable, and an object is assignable to a type if it has at least the required properties (extras are fine). When you actually want to prevent mixing same-shaped types (a UserId vs a RoleId), opt back into nominal with a brand: type UserId = number & { __brand: 'UserId' }.

  • Shape beats name. Same properties → compatible, no implements needed (duck typing).
  • More-specific is assignable to less-specific — extra properties are allowed, missing ones aren't.
  • Brand types opt back into nominal — a phantom field keeps UserId and RoleId distinct.
  • Functions are structural too — parameters are contravariant, return types covariant.

Structural compatibility

// No explicit relationship needed class PingUser { sub: string; email: string; ping_roles: string[]; } interface Identifiable { sub: string } const ping = new PingUser(); const ident: Identifiable = ping; // OK — PingUser has 'sub' // More specific is assignable to less specific: interface User { id: number; name: string; email: string } interface Named { name: string } const user: User = { id: 1, name: 'Bob', email: 'b@b.com' }; const named: Named = user; // OK — User has 'name' // NOT the other way: const n: Named = { name: 'Bob' }; const u: User = n; // Error: missing 'id' and 'email'

Brand types (nominal-like)

// Without brands — IDs mix silently type UserId = number; type RoleId = number; function assignRole(userId: UserId, roleId: RoleId) {} assignRole(roleId, userId); // No error — both just number! // With brands — phantom type prevents mixing type UserId = number & { readonly __brand: 'UserId' }; type RoleId = number & { readonly __brand: 'RoleId' }; const toUserId = (n: number): UserId => n as UserId; const toRoleId = (n: number): RoleId => n as RoleId; function assignRole(userId: UserId, roleId: RoleId) {} const uid = toUserId(42); const rid = toRoleId(7); assignRole(uid, rid); // OK assignRole(rid, uid); // Error! assignRole(42, 7); // Error — not branded

Functions are structural too

// Function types: structural compatibility type Handler = (e: MouseEvent) => void; // OK: parameter type compatible const h: Handler = (e: Event) => {}; // MouseEvent extends Event — parameter contravariance // h is assigned a function that accepts the wider Event // When called with MouseEvent, it's passed a MouseEvent // which is assignable to Event — safe // NOT OK: const h2: Handler = (e: WheelEvent) => {}; // WheelEvent is MORE specific than MouseEvent // Caller might pass a plain MouseEvent // but h2 uses WheelEvent properties — unsafe // Return type: covariant (more specific is OK) type Getter = () => Animal; const g: Getter = () => new Dog(); // OK — Dog is Animal

CIAM / Angular + Spring: Structural typing makes Ping/Entra responses assignable to UserDto when their shapes match — no adapter needed. Brand the tokens (type PingToken = string & { __brand: 'PingToken' }) to stop a Ping token being passed where an Entra token is expected. Any class with a matching getUser satisfies interface UserProvider without implements — which is why Angular services rarely implement interfaces — but DI tokens use InjectionToken to add nominal identity.

1. The headline: shape beats name

TypeScript structural

interface Point { x: number; y: number; }

class Vector { constructor(public x: number,
                       public y: number) {} }

const p: Point = new Vector(1, 2); // ✅ OK!
// Vector never said "implements Point".
// It just HAS x:number and y:number, so it fits.

Compatibility is computed from members. The declared name is irrelevant.

Java nominal — for contrast

interface Point { double getX(); double getY(); }

class Vector { double x, y; } // same shape

Point p = new Vector(); // ❌ COMPILE ERROR
// Vector is not a Point unless it explicitly
// declares: class Vector implements Point

Java checks the name/declared hierarchy. Same shape isn't enough — you must opt in with implements.

💡 Why TS chose this: JavaScript is duck-typed at runtime — objects are just bags of properties, no class needed. A structural type system describes that honestly: it can type a plain { x, y } literal, a class instance, or a function's return value uniformly, because it only ever asks "does this value have the right shape?"

3. Width subtyping — why "extra properties are fine"

A value with more properties is assignable to a type that asks for fewer. This is "width subtyping": Point3D is a subtype of Point2D because every Point2D (x, y) lives inside every Point3D (x, y, z).

type Point2D = { x: number; y: number };
type Point3D = { x: number; y: number; z: number };

const p3: Point3D = { x:1, y:2, z:3 };
const p2: Point2D = p3;  // ✅ extra z is ignored
const bad: Point3D = p2; // ❌ p2 has no z

More properties = more specific = assignable to the looser type. Fewer properties can't satisfy a type that demands more. (It's the same direction as "a Dog is an Animal, but an Animal isn't necessarily a Dog.")

4. The one exception: excess property checks

Object literals get extra scrutiny

If structural typing always ignored extras, typos would slip through. So when you assign a fresh object literal directly, TS flags properties the target doesn't know about.

type Opts = { width: number; color?: string };

// direct literal → excess prop check kicks in:
const a: Opts = { width:5, colour:'red' };
// ❌ 'colour' not in Opts — did you mean 'color'?

…but only for fresh literals

Assign through a variable first and the excess check is gone — it's back to plain structural rules (the extra is just ignored).

const raw = { width:5, colour:'red' };
const b: Opts = raw; // ✅ no excess check; extra ignored

// escape hatch when you DO want extras on a literal:
type Opts2 = { width: number; [k: string]: unknown };

It's a deliberately shallow safety net for the most common typo case — not a real nominal check.

5. Opting OUT: making a type nominal

Branded types — the idiomatic escape hatch

Sometimes structural is too loose: a UserId and an OrderId are both string, so TS lets you mix them up. Add a phantom "brand" so they stop being interchangeable.

type UserId  = string & { readonly __brand: 'UserId' };
type OrderId = string & { readonly __brand: 'OrderId' };

const asUserId = (s: string) => s as UserId;

function ban(id: UserId) { … }
ban(orderId); // ❌ OrderId is not UserId — caught!

The brand exists only at compile time (it's never really there at runtime). It forces values through your asUserId "constructor," giving you nominal safety on primitives.

A private field also brands a class

Classes with a private (or #) member become effectively nominal — only instances of that exact class are compatible, because the private is unique to it.

class Token { private _t = 0; }
class Other { private _t = 0; }

let x: Token = new Other(); // ❌ private origins differ

Same shape, but the private makes them incompatible — the closest TS gets to Java's nominal classes by default.

6. What structural typing buys you (and costs you)

7. One-sentence recap

🦆 TypeScript is structurally typed: a value fits a type if it has all the members that type requires (extras ignored — that's width subtyping), so unrelated classes/literals of the same shape are interchangeable — the opposite of Java's nominal "must implements it" rule — with excess-property checks on fresh literals as a typo guard, and branded types / private fields as the escape hatch when you need name-based identity.
