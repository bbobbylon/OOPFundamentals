The Factory Pattern — the Pizza Store

Chapter 4. orderPizza() always does the same dance — prepare, bake, cut, box — but the line new CheesePizza() ties it to concrete classes. Every new pizza means editing that method. The Factory patterns pull object creation out so the order process stays closed to change while the menu stays open to extension.

🎯 What is the Factory pattern — and what is the difference between Factory Method and Abstract Factory?

The problem: orderPizza() contains if (type.equals("cheese")) pizza = new CheesePizza(). Adding a new pizza type means editing orderPizza() — a violation of the Open/Closed Principle. Simple Factory: extract the creation into a separate class: PizzaFactory.createPizza(type). Not technically a GoF pattern, but a common simplification. Factory Method: define an interface for creating an object, but let subclasses decide which class to instantiate. PizzaStore has abstract createPizza(type). NYPizzaStore creates NY-style pizzas; ChicagoPizzaStore creates Chicago-style. The orderPizza() method stays in the base class — only creation is delegated. Abstract Factory: provides an interface for creating families of related objects. PizzaIngredientFactory creates dough, sauce, cheese, veggies together — all from the same regional style. NY factory creates NY ingredients; Chicago factory creates Chicago ingredients — no mixing.

Factory Method structure

abstract class PizzaStore { // Template Method Pizza orderPizza(String type) { Pizza p = createPizza(type); // Factory Method p.prepare(); p.bake(); p.cut(); p.box(); return p; } abstract Pizza createPizza(String type); // subclass decides } class NYPizzaStore extends PizzaStore { Pizza createPizza(String type) { return switch(type) { case "cheese" -> new NYStyleCheesePizza(); default -> throw new IllegalArgumentException(); }; } }. Factory Method and Template Method work together here.

Factory in Spring Boot

Spring's BeanFactory is the Abstract Factory — it creates objects (beans) of different types based on configuration. ApplicationContext.getBean(UserService.class) — the factory creates and returns the bean. @Configuration classes are Factory Method classes: each @Bean method is a factory method that creates a specific bean. Spring's DataSource: DataSourceBuilder.create().type(HikariDataSource.class).url(url).build() — builder pattern (related to Factory). Spring Security's AuthenticationManagerBuilder creates authentication infrastructure — Abstract Factory for auth components.

DIP: Depend on Abstractions

Factory patterns teach the Dependency Inversion Principle (DIP): high-level modules (PizzaStore) should not depend on low-level modules (CheesePizza) — both should depend on abstractions (Pizza). orderPizza() works with Pizza (interface) — it never touches NYStyleCheesePizza. The factory is the only place that knows concrete classes. "New" is the enemy of DIP — every new ConcreteClass() creates a dependency. Factories centralise all new calls. In Spring: you never write new UserService() — Spring's factory does it, injecting the right dependencies.

In CIAM / Spring Boot: IDP client factory: interface IdpClientFactory { IdpClient create(IdpType type); }. @Component class DefaultIdpClientFactory implements IdpClientFactory { IdpClient create(IdpType type) { return switch(type) { case PING -> pingClient; case ENTRA -> entraClient; }; } }. The service asks the factory: IdpClient client = factory.create(user.getIdpType()). Adding Keycloak: add the case to the factory, nothing else changes. Abstract Factory for multi-tenant: TenantClientFactory returns the right set of clients (auth, directory, provisioning) for a given tenant's IDP configuration — clients always come as a consistent family.

Act 1 — "new" is the enemy of "closed for modification"

When you new up a concrete class, you bind to it. Here orderPizza() mixes a stable process with a volatile decision:

Pizza orderPizza(String type) {
  Pizza pizza;
  if (type.equals("cheese")) pizza = new CheesePizza();
  else if (type.equals("veggie")) pizza = new VeggiePizza();
  // … edit this block for EVERY menu change …
  pizza.prepare(); pizza.bake(); pizza.cut(); pizza.box();  // stable
  return pizza;
}
Brain Power. Notice two speeds in one method: the prepare/bake/cut/box steps almost never change, but the if/else creation block changes constantly. That's the aspect that varies — and you already know the move: pull it out and encapsulate it.

Act 2 — the Simple Factory (an idiom, not a pattern)

Move the creation into its own object. orderPizza() stops changing; only the factory does.

class SimplePizzaFactory {
  Pizza createPizza(String type) {
    if (type.equals("cheese")) return new CheesePizza();
    // … the volatile decision now lives HERE, in one place …
  }
}
// orderPizza() just asks the factory:
Pizza pizza = factory.createPizza(type);  // no "new" in the store

Useful, but it doesn't let each franchise make pizzas its own way. For that, push creation into subclasses.

Act 3 — the Factory Method

Make createPizza() an abstract method on the store. The base PizzaStore owns the unchanging orderPizza() template; subclasses decide which Pizza to instantiate.

The creator declares the factory method

abstract class PizzaStore {
  Pizza orderPizza(String t) {
    Pizza p = createPizza(t);   // the factory method
    p.prepare(); p.bake(); p.cut(); p.box();
    return p;
  }
  abstract Pizza createPizza(String t);  // subclasses decide
}

Each subclass picks the product

class NYPizzaStore extends PizzaStore {
  Pizza createPizza(String t) {
    return new NYStyleCheesePizza();
  }
}
class ChicagoPizzaStore extends PizzaStore {
  Pizza createPizza(String t) {
    return new ChicagoStyleCheesePizza();
  }
}

Q: orderPizza() calls createPizza(), but createPizza() is abstract here — how does it know what to make?

A: Polymorphism. orderPizza() runs on an instance of a subclass, so createPizza() resolves to that subclass's override at runtime. The base class is written in terms of an abstract product it never names directly.

Act 4 — Abstract Factory (families of ingredients)

NY and Chicago don't just make different pizzas — they use different ingredient families (thin vs deep dough, marinara vs plum tomatoes). An Abstract Factory is one object that creates a whole matching family.

interface PizzaIngredientFactory {
  Dough createDough();  Sauce createSauce();  Cheese createCheese();
}
class NYIngredientFactory implements PizzaIngredientFactory {
  Dough createDough()  { return new ThinCrustDough(); }
  Sauce createSauce()  { return new MarinaraSauce(); }
}

Factory Method vs Abstract Factory: Factory Method uses inheritance (a subclass overrides one creation method for one product). Abstract Factory uses composition (one object hands you a whole family of related products). Both decouple your code from concrete classes.

The principle this chapter hands you

Design Principle — Dependency InversionDepend upon abstractions. Do not depend upon concrete classes.

High-level orderPizza() shouldn't depend on low-level NYStyleCheesePizza. With the factory method, both depend on the abstraction Pizza — the dependency is "inverted." This is exactly how Spring's container hands you interfaces, not new-ed implementations.

The Factory Method Pattern, defined

The Factory Method Pattern defines an interface for creating an object, but lets subclasses decide which class to instantiate. Factory Method lets a class defer instantiation to subclasses.
You've used it. Calendar.getInstance(), NumberFormat.getInstance(), Spring's BeanFactory, an Angular provider's useFactory — all "ask something else to create the right object for you." Next in the track: Singleton (Chocolate Boiler) and Command (Remote Control).
