Azure Cosmos DB — Partitions, RUs & Consistency

Cosmos DB is Azure's globally distributed NoSQL database. Three ideas explain almost everything about it: data is spread across physical partitions by a partition key you choose, every operation is billed in Request Units (RUs), and reads choose a point on the consistency spectrum from strong to eventual.

🪐 What is Cosmos DB — and why do the partition key and RUs decide everything?

Cosmos DB stores JSON items in containers (inside databases, inside a Cosmos account), and it scales horizontally the only way any database can: by sharding. When you create a container you name one property — say /customerId — as the partition key. Every item's key value is hashed to decide which logical partition it belongs to, and logical partitions are packed onto physical partitions (the actual machines, each capped at ~50 GB and 10,000 RU/s). This single choice is destiny: a query that filters on the partition key goes to one partition (fast, cheap); a query that doesn't must fan out to all of them (slow, expensive). Cost is measured in Request Units — a currency that folds CPU, IO, and memory into one number. A 1 KB point-read costs ~1 RU; a write ~5 RU; a cross-partition query can cost hundreds. You provision throughput as RU/s (manual or autoscale, per container or shared per database) or pay per operation (serverless) — and when you exceed it, Cosmos doesn't slow down, it throttles: HTTP 429 with a Retry-After header. Finally, because Cosmos replicates every partition (4 replicas in-region, plus any regions you add), reads must pick a consistency level: strong (always the latest, higher latency, no multi-region writes), bounded staleness, session (the default — read your own writes within your session), consistent prefix, or eventual (fastest, may read stale). The change feed — an ordered log of inserts/updates per partition — is the integration workhorse: Azure Functions subscribe to it to build materialized views, caches, and event pipelines.

  • Account → database → container → item — the container is the scaling unit; the partition key is set at container creation and is immutable.
  • Partition key = the shard router — filter on it: 1 partition. Don't: fan-out query across all. High cardinality + even spread + used in every query = good key.
  • RU = the currency — ~1 RU per 1 KB point read, ~5 per write. Exceed provisioned RU/s → 429 TooManyRequests + Retry-After (SDK retries automatically).
  • Consistency spectrum — strong · bounded staleness · session (default) · consistent prefix · eventual. Weaker = faster reads + lower RU cost.
  • Change feed — per-partition ordered stream of changes; the standard trigger for Functions-based projections and integrations.

AWS comparison

Cosmos DB ≈ DynamoDB. Partition key ≈ partition key (Dynamo adds a sort key; Cosmos uses id within the partition). RU/s ≈ RCU/WCU. 429 ≈ ProvisionedThroughputExceededException. Change feed ≈ DynamoDB Streams. Big differences: Cosmos speaks rich SQL-ish queries + multiple APIs (SQL/Core, Mongo, Cassandra, Gremlin, Table), and multi-region writes with five consistency levels vs Dynamo's global tables (eventual only).

Spring Boot comparison

Mental model shift from your JDBC pattern: there are no joins across items and no ACID across partitions — you model for the query, often embedding what you'd normalize in SQL (an order embeds its line items). CosmosClient ≈ your NamedParameterJdbcTemplate; a point read (readItem(id, partitionKey)) ≈ findById — and it is the cheapest thing you can do (~1 RU). Spring Data Cosmos exists, but the raw SDK teaches the cost model honestly.

CIAM in production: Cosmos is a natural fit for identity-adjacent data — sessions, user profiles, consent records — because /userId (the token's sub/oid claim) is a textbook partition key: high cardinality, evenly spread, and present in every query your API makes on behalf of that user. Point-read the profile by (id, userId) for ~1 RU per request. or, the ORDER BY that ran fine for months and throws a 400 the day someone adds a tiebreaker column

The problem

Cosmos indexes every property automatically — this page already told you that — but automatic indexing only covers sorting by ONE property at a time.

Your dashboard query 400s the moment a second sort column ships

A dashboard query has run in production for months: SELECT * FROM o WHERE o.status = "OPEN" ORDER BY o.orderDate. It works because a single-property ORDER BY is covered by the automatic per-property range index every container gets by default — nothing special was ever configured for it, and nothing needed to be.

Then product asks for a completely reasonable tiebreaker: when two orders share a date, sort by customerId too. The change looks trivial — ORDER BY o.orderDate, o.customerId — same table, same properties, already both indexed individually. Cosmos's own indexing-policy documentation says otherwise: an ORDER BY across two or more properties requires an explicit composite index defined in the container's indexing policy. The automatic range index that silently handled the single-column sort does not extend to multi-column sorts — that's a separate, opt-in feature. Without a composite index covering exactly (orderDate, customerId), the query doesn't get slower or cost more RUs. It fails outright with a 400 Bad Request, before it ever reaches a single partition.

single-column ORDER BY worked fine for months ✓ query syntax is completely valid ✓ the WHERE clause on status is untouched ✓ no composite index defined for (orderDate, customerId) ⚠

This isn't a performance cliff like the cross-partition fan-out earlier on this page — that query still runs, just expensively. A missing composite index is a hard stop: the query doesn't run at all.

The one-sentence rule. Cosmos's default indexing policy quietly stops covering you the instant an ORDER BY touches a second property — composite indexes are opt-in, no matter how automatically-indexed the container otherwise appears to be.
Cosmos indexing every property by default feels like a restaurant that seats a table of one or two the moment you walk in. Ask for a table sorted two ways at once, and you find out that specific arrangement needed a reservation nobody made.
You

My ORDER BY on orderDate alone has worked in production for months. I added customerId as a tiebreaker and now every request 400s. I didn't touch the WHERE clause at all.

Cosmos

Sorting by one property is covered by the range index every property gets automatically. Sorting by two or more is a different feature — a composite index — and nobody defined one for (orderDate, customerId).

You

But it's still just an ORDER BY. Why does one more column change anything?

Cosmos

Because ordering by two properties at once needs the values pre-combined into a single sortable structure ahead of time — that doesn't happen unless you ask for it. I'd rather fail loudly right now than quietly ignore your second sort key.

The mechanism

Follow the exact same query as it gains one column and loses the ability to run at all.

  1. Container orders/ ships with the default indexing policy — every property auto-indexed with its own range indexdefault policy
  2. SELECT ... WHERE o.status='OPEN' ORDER BY o.orderDate runs fine — a single-property sort uses that automatic range index directlysingle-column ok
  3. A new requirement adds a tiebreaker: ORDER BY o.orderDate, o.customerIdtwo columns
  4. The query engine looks for a composite index covering exactly (orderDate, customerId), in that order, inside the indexing policy — and finds nonelookup fails
  5. Cosmos rejects the query outright with a 400 Bad Request, before touching a single partition400
  6. Adding a composite index for that exact property pair — and waiting for re-indexing on a large container — is the only fix; no query rewrite avoids itfix

Steps 4 and 5 are where this diverges from every other Cosmos gotcha on this page. A cross-partition fan-out still RUNS — it just costs more RUs, as scenario ② showed. A missing composite index doesn't degrade at all: the query engine checks for it before the query ever reaches a partition, and refuses outright the moment it isn't there.

The slot resolves on something that has nothing to do with data volume or your consistency setting — it's a single yes/no fact about the indexing policy, checked before the query planner even chooses a partition to visit.

A container uses the default indexing policy (every property auto-indexed). SELECT * FROM o WHERE o.status='OPEN' ORDER BY o.orderDate has run successfully for months. A developer changes it to ORDER BY o.orderDate, o.customerId to break ties, with no other change to the container. What happens?

Multi-property ORDER BY isn't just slower under the default policy — it's unsupported by the automatic per-property range index entirely. There's no degraded-but-working path here.

Cosmos doesn't silently guess at an order for the second column or return partially-sorted results — it refuses to run the query at all rather than return something that doesn't actually honor the ORDER BY clause as written.

Right. The default indexing policy's automatic range indexes cover a single-property sort only. The instant an ORDER BY spans two or more properties, Cosmos requires a composite index defined for that exact property list and direction — without it, the query is rejected outright with a 400, before it ever reaches a partition.

Where you have seen this before

"The simple case is automatic, the compound case needs an explicit opt-in" shows up everywhere a query engine sits on top of an index.

A relational database sorting on the "wrong" index

PostgreSQL or MySQL has the same underlying problem — a single-column index on status doesn't efficiently serve ORDER BY orderDate, customerId either — but the consequence is different in kind: the planner falls back to an in-memory or on-disk sort and the query still returns, just slower. Cosmos's hard refusal is the more unusual choice, not the missing-index problem itself.

the same missing index, a gentler failure mode elsewhere

Elasticsearch sorting on a field without doc_values

Elasticsearch indexes text fields for searching by default, but sorting requires doc_values to be enabled for that field — a separate, opt-in structure. Try to sort on a field that lacks it and Elasticsearch doesn't degrade gracefully; it throws a search-phase execution exception outright, the same hard-stop shape as Cosmos's missing composite index.

a different search engine, the identical hard-stop shape

MongoDB's in-memory sort limit

Sort a MongoDB query on an unindexed field and it works fine — right up until the working set crosses the server's in-memory sort limit, at which point MongoDB throws an outright error ("Sort exceeded memory limit") instead of quietly spilling to disk, unless allowDiskUse was explicitly requested ahead of time. An assumption that held at small scale becomes a hard failure with zero code change, the same way Cosmos's single-column sort stopped covering a second column.

an implicit limit that only announces itself by failing

1. The partition key decides the shape of every query

-- container: orders, partition key /customerId
-- ✅ single-partition: the pk is in the filter → routed to ONE partition
SELECT * FROM orders o WHERE o.customerId = "cust-42" AND o.status = "OPEN"

-- ❌ cross-partition: no pk in the filter → fans out to EVERY partition
SELECT * FROM orders o WHERE o.status = "OPEN"

-- 🏆 point read: id + pk, no query engine at all (~1 RU)
container.readItem("order-9001", new PartitionKey("cust-42"), Order.class)
Choose the key for the questions you ask, not the data you have. The three tests: high cardinality (many distinct values — /customerId yes, /country no), even distribution (no single customer is 90% of traffic — a celebrity-user or /date key creates a hot partition that throttles while others idle), and appears in your dominant queries. A logical partition is also capped at 20 GB — all items sharing one key value must fit. When one property can't satisfy both reads and writes, use a synthetic key (e.g. customerId + "-" + month) or duplicate data into a second container via change feed — storage is cheap, RUs are not.

2. The consistency spectrum: what a read is allowed to see

LevelGuaranteeRead RULatencyPick when
Strongalways the latest committed write, globally2× (quorum)highestfinancial balances; single-region or paired reads
Bounded stalenesslag ≤ K versions or T seconds, ordered2×highglobally ordered feeds that tolerate a known lag
Session (default)your session reads its own writes1×lowalmost everything user-facing — the sweet spot
Consistent prefixnever out-of-order, may be behind1×lowordered event consumers that tolerate lag
Eventualno ordering promise, converges eventually1×lowestlike counts, telemetry, anything approximate
Session consistency is the default for a reason. It gives each client the thing users actually notice — read-your-own-writes (save profile → refresh → see it) — at half the RU cost of strong, by threading a session token through the SDK's requests. Strong doubles read cost because it reads a replica quorum, and it rules out multi-region writes. Exam phrasing decoder: "monotonic reads, read-your-writes, within one session" → session; "lag bounded by K versions or T time" → bounded staleness; "cheapest, order irrelevant" → eventual.

3. Throughput: provisioned vs autoscale vs serverless

# manual: fixed 400 RU/s (the minimum) — cheap, throttles above it
az cosmosdb sql container create … --throughput 400

# autoscale: floats between 10% and the max you set
az cosmosdb sql container create … --max-throughput 4000

# serverless (account-level choice): pay per RU consumed, no floor
az cosmosdb create -n cosmos-shop --capabilities EnableServerless
Match the billing mode to the traffic shape. Steady, predictable load → manual provisioned (cheapest per RU). Spiky but daily traffic → autoscale (billed on the highest RU/s each hour, scales 10×). Infrequent or dev/test → serverless (zero idle cost, per-operation billing, 1M RU/s cap per container). Throughput can be set per-container (isolated) or shared across a database (containers compete). And burn into memory: hitting the limit is not an error state — 429 + x-ms-retry-after-ms is Cosmos telling you the price of your success; the SDK retries it automatically up to 9 times before you ever see an exception.
