Template Literal Types

String literal types that interpolate other types. `hello ${T}` on the type side — used to build typed event names, parse routes at compile time, derive keys from other keys, and produce surprisingly strict string APIs.

🔤 What are template literal types — and how do they build type-safe event names and paths?

Template literal types are JavaScript's backtick strings lifted to the type level: `on${T}` builds a new string-literal type from a type. The real power is union distribution — `on${'Click'|'Change'}` expands to 'onClick' | 'onChange', so you can generate whole unions of strings from other unions. Pair them with the intrinsic Capitalize/Uppercase/Lowercase helpers, keyof, and mapped-type key remapping to derive event names, CSS classes, and typed route paths — even parse strings with infer, all at compile time.

  • Backtick strings at the type level — interpolate types into a string-literal type.
  • Unions distribute & multiply — `${A}${B}` yields every combination.
  • Intrinsic helpers transform — Capitalize, Uppercase, Lowercase.
  • infer parses strings — extract route params like :userId from a path type.

Union distribution

// Combining unions type Entity = 'User' | 'Role' | 'Group'; type Action = 'Created' | 'Updated' | 'Deleted'; type AuditEvent = `${Entity}${Action}`; // = 'UserCreated' | 'UserUpdated' | 'UserDeleted' // | 'RoleCreated' | 'RoleUpdated' | 'RoleDeleted' // | 'GroupCreated' | 'GroupUpdated' | 'GroupDeleted' // 9 strings from 3 × 3 = auto-generated // Event handler names type EventName = 'click' | 'change'; type Handler = `on${Capitalize<EventName>}`; // = 'onClick' | 'onChange' // CSS utility classes type Color = 'red' | 'blue' | 'green'; type Shade = '100' | '200' | '300'; type ColorClass = `bg-${Color}-${Shade}`; // = 'bg-red-100' | 'bg-red-200' | ... (9 classes)

Derive keys from keys

// Generate getter methods from property names type Getters<T> = { [K in keyof T as `get${Capitalize<string & K>}`]: () => T[K]; }; type UserGetters = Getters<{ name: string; id: number }>; // = { getName: () => string; getId: () => number } // Generate setter types type Setters<T> = { [K in keyof T as `set${Capitalize<string & K>}`]: (v: T[K]) => void; }; // Generate signal names type Signals<T> = { [K in keyof T as `${string & K}Changed`]: EventEmitter<T[K]>; }. The template literal acts as a key transformer in the mapped type's as clause.

The problem

You typed 'onClick' by hand. So did three other files.

Two strings, one fact, zero enforcement

Your event is called click. Your handler key is called onClick. Every human on the team knows the second is the first with four characters bolted on — and nothing in the language knows that. Rename the event to press and the compiler says nothing, because 'onClick' is still a perfectly respectable string.

'click''onClick''onclick' ⚠ 'on_click' ⚠handler never fires ⚠

The bug isn't the typo. The bug is that the rule connecting the two strings lived in your head instead of in the type, so nobody could check it.

Write the rule down and let tsc apply it
type Ev = 'click' | 'change' | 'focus' ↓ because the handler name is a function of the event name, not a second fact type Handler = `on${Capitalize<Ev>}` ↓ and the compiler recomputes it on every single build, for free 'onClick' | 'onChange' | 'onFocus'
A template literal type is string concatenation that runs at compile time. If two strings in your codebase are related by a rule, write the rule once — the compiler keeps the second string in sync forever, and ships zero bytes doing it.

The mechanism

One template goes in. Every combination comes out.

`${Idp}:${Event}`one template, two unions
distributes over every member of every union ↓
'ping:login' 'ping:logout' 'entra:login' 'entra:logout' 'okta:login' 'okta:logout' …and 9,994 more once the unions hit 100 × 100

The part everyone re-learns the hard way: a union inside ${…} is not a slot, it is a loop. Two unions is a nested loop. Six literals cost you nothing; ten thousand cost you an editor that stops to think on every keystroke.

The four intrinsics — Uppercase, Lowercase, Capitalize, Uncapitalize — are the only built-in string functions the type system has, and they are implemented in the compiler itself, not in lib.d.ts. They distribute the same way: Capitalize<'a'|'b'> is 'A'|'B', member by member. In real code you will almost always write Capitalize<K & string>, because keyof T hands you string | number | symbol and a template refuses to interpolate a symbol. Cardinality is the cost model: multiply the size of every union in the template and that's how many types your editor is now holding in memory. Under a few hundred, invisible. Over ten thousand, you will feel it in autocomplete — and TypeScript hard-stops you around 100,000.

Your CIAM audit type is type Audit = `${Idp}:${Ev}` with Idp = 'ping'|'entra'|'okta' and Ev = 'login'|'logout'. A teammate widens Idp to plain string so a new provider can be onboarded without a code change. What does logAudit(e: Audit) now accept?

Widening threw the three literals away. There is nothing left to check the provider half against — 'okra:login' compiles now.

Questions from the back row

Does a 10,000-member union cost my users anything?

Not a byte. tsc checks types and then deletes them — a template literal type has no runtime representation at all. The bill is paid entirely by your editor and your CI: slower autocomplete, slower type-check, a fatter .tsbuildinfo. Users get the same JavaScript either way.

Why does Capitalize<K> explode when K comes from keyof T?

Because keyof T is string | number | symbol, and a template can only interpolate stringables — a symbol is not one. K & string fixes it, and it is an intersection, not a cast: each union member is intersected with string, the symbol members become never, and never drops out of a union on its own.

When should I not reach for this?

When the string space is open. If the value arrives from a config file, a database row, or a user, no template type can enumerate it — you end up writing `${string}-${string}`, which is an expensive way to spell string. Type-level parsing also has a recursion ceiling near 50–100 levels; a runtime validator doesn't, and it can read the actual value.

1. Syntax — strings at the type level

A template literal type looks like a JS template string, but it produces a type. You can interpolate other types, and the compiler will compute the resulting string literal type.

type Greeting = `hello, ${string}`;
// Any string that starts with "hello, " satisfies this.

type Name = 'world';
type G = `hello, ${Name}`;
// 'hello, world'  — fully literal

const g1: Greeting = 'hello, ts';     // ok
const g2: Greeting = 'hi, ts';        // ✗ Type error

The thing inside ${...} can be any type that's "stringable": a string literal, a union of string literals, the wide string type, number, bigint, or boolean.

type A = `x-${number}`;      // 'x-0' | 'x-1' | 'x-2' | ... (all of them — number is wide)
type B = `x-${1 | 2 | 3}`;    // 'x-1' | 'x-2' | 'x-3'   (literal union)
type C = `is-${boolean}`;     // 'is-true' | 'is-false'

2. Union distribution in templates

When you put a union inside ${...}, the template distributes over each member, then unions the results. Multiple unions in one template produce the cartesian product.

type Color = 'red' | 'green' | 'blue';
type Size  = 'sm' | 'lg';

type CssClass = `${Color}-${Size}`;
// 'red-sm' | 'red-lg' | 'green-sm' | 'green-lg' | 'blue-sm' | 'blue-lg'
// 3 colors × 2 sizes = 6 literal members
Combinatorial explosion: a template with three 10-member unions produces a 1000-member union. TS will warn around 100 000 members. Useful, but keep the cardinality reasonable — if you find yourself reaching for product-of-unions to model many enums, a generic factory function is often a better fit.

You can also union outside the template:

type Edge = 'top' | 'bottom' | 'left' | 'right';
type Margin = `margin-${Edge}` | `m${Edge[0]}`;
// 'margin-top' | ... | 'mt' | 'mb' | 'ml' | 'mr'

3. The four built-in case helpers

TypeScript ships four intrinsic types that mutate string literals at the type level. They're the only "built-in functions" in the type system that operate on strings.

TypeEffect on 'hello'
Uppercase<S>'HELLO'
Lowercase<S>'hello'
Capitalize<S>'Hello'
Uncapitalize<S>'hello'
type A = Uppercase<'event'>;            // 'EVENT'
type B = Capitalize<'click'>;           // 'Click'
type C = `on${Capitalize<'click' | 'change'>}`;
// 'onClick' | 'onChange'

They work member-by-member on unions and propagate through nested templates. You can also use them to derive an uppercase enum from a lowercase one:

type Method = 'get' | 'post' | 'delete';
type HttpVerb = Uppercase<Method>;
// 'GET' | 'POST' | 'DELETE'

4. With mapped types: rename keys

The combination that made template literal types essential: { [K in keyof T as ...]: ... } with a template inside the as clause. See the Mapped Types page for the full story — the pattern in short:

type Getters<T> = {  // mapped type: loop over every key in T and build a new property for each one
  [K in keyof T as `get${Capitalize<K & string>}`]: () => T[K];  // "as" renames the key to get+Capitalized(K); the value type becomes a no-arg function returning the original T[K]
};  // closes the mapped-type body — the whole thing is still just a type alias

type Person = { name: string; age: number };  // a plain object type to feed into Getters
type G = Getters<Person>;  // instantiate the mapped type — TS expands it eagerly, key by key
// { getName: () => string; getAge: () => number }

The K & string intersection is doing the same job as it does everywhere: keyof T is string | number | symbol, but template literals only allow string. Intersecting filters down to just the string-named keys.

Same trick for prefixes — typed Redux/NgRx action types:

type Prefixed<P extends string, T> = {  // P is the prefix string, T is the object whose keys get prefixed
  [K in keyof T as `${P}/${K & string}`]: T[K];  // same "as" trick as Getters — but the value type passes through unchanged, only the key is templated
};

type TodoActions = Prefixed<'todos', {  // P = 'todos'; the second arg is an inline object literal type used as T
  add: { text: string };  // becomes key 'todos/add'
  remove: { id: number };  // becomes key 'todos/remove'
}>;
// { 'todos/add': { text: string }; 'todos/remove': { id: number } }

5. Parsing with infer

The truly magical bit: you can put infer X inside a template literal and TS will pattern-match the input string, capturing whatever fills the placeholder.

// Capture the part after the colon
type AfterColon<S> = S extends `${string}:${infer R}` ? R : never;

type A = AfterColon<'user:bob'>;         // 'bob'
type B = AfterColon<'no-colon'>;        // never

You can capture multiple pieces in one template. TS reads left-to-right, greedily matching:

type SplitOnDot<S> =
  S extends `${infer A}.${infer B}` ? [A, B] : [S];

type X = SplitOnDot<'one.two'>;     // ['one', 'two']
type Y = SplitOnDot<'one.two.three'>; // ['one', 'two.three']  ← greedy on the LEFT capture
type Z = SplitOnDot<'one'>;         // ['one']
Matching is structural: the literal parts of the template (the bits outside ${...}) must appear in the input string. Inferred placeholders soak up everything between literals. Combined with recursion, this is enough to write a real lexer at the type level.

6. Route params — the worked example

This is the canonical demo because it's both useful and shows the full toolkit (infer, recursion, union assembly) in one tight type.

type RouteParams<S extends string> =  // S is the route string, e.g. '/users/:id/posts/:postId'
  S extends `${string}:${infer Param}/${infer Rest}`  // does S contain a ':param/' followed by more path? capture the param name and everything after it
    ? Param | RouteParams<`/${Rest}`>  // yes: this param is one hit, and recurse on the remaining "/Rest" to find the others (union grows)
    : S extends `${string}:${infer Param}`  // no more '/' after it — check if there's still exactly one trailing param
      ? Param  // the last param in the chain, base case of the recursion
      : never;  // no ':' left at all — no params found on this branch

type A = RouteParams<'/users/:id'>;
// 'id'

type B = RouteParams<'/users/:id/posts/:postId'>;  // two params — recursion fires once, unioning 'id' with the recursive call's result
// 'id' | 'postId'

type C = RouteParams<'/static'>;  // no ':' anywhere in the string
// never  — no params

Once you have the param union, you can build a typed link() helper:

function link<R extends string>(
  route: R,
  params: Record<RouteParams<R>, string>
): string { /* ... */ }

link('/users/:id/posts/:postId', { id: '42', postId: '7' });   // ✓
link('/users/:id/posts/:postId', { id: '42' });                  // ✗ missing postId
link('/users/:id', { id: '42', foo: 'x' });                       // ✗ extra key

7. Numeric coercion in templates

Since TS 4.8 you can pattern-match a numeric value inside a template-literal capture by adding extends number. This converts the captured string into a numeric literal type.

type ParseInt<S> = S extends `${infer N extends number}` ? N : never;

type A = ParseInt<'42'>;      // 42 (number)
type B = ParseInt<'-7'>;      // -7
type C = ParseInt<'abc'>;     // never — doesn't parse as number

Works for boolean and bigint too:

type ParseBool<S> = S extends `${infer B extends boolean}` ? B : never;
type X = ParseBool<'true'>;  // true

8. Recursive string transforms

Combine template literal parsing with recursive conditional types, and you can write surprisingly real transforms.

SnakeCase → camelCase

type SnakeToCamel<S> =  // S is the snake_case string to transform
  S extends `${infer Head}_${infer Tail}`  // does S contain an underscore? capture everything before it as Head and everything after as Tail
    ? `${Head}${Capitalize<SnakeToCamel<Tail>>}`  // yes: keep Head as-is, then recursively camelCase Tail and Capitalize the result (so "first_name" → "First" + "Name")
    : S;  // no underscore left — this segment is already camelCase-ready, return it unchanged

type A = SnakeToCamel<'user_first_name'>;  // three underscore-separated words to fold together
// 'userFirstName'

Split — produce a tuple of segments

type Split<S extends string, D extends string> =  // S is the string to cut up, D is the delimiter
  S extends `${infer Head}${D}${infer Tail}`  // does S contain D at all? capture what's before it as Head and everything after as Tail
    ? [Head, ...Split<Tail, D>]  // yes: Head is one segment, spread the recursive split of Tail onto a tuple after it
    : [S];  // no D left in S — the whole remaining string is the last (or only) segment

type A = Split<'a.b.c.d', '.'>; // ['a', 'b', 'c', 'd']

Join — the inverse

type Join<T extends string[], D extends string> =  // T is the tuple of strings, D is the glue between them — the inverse of Split
  T extends [infer H extends string, ...infer R extends string[]]  // destructure T into its first element H and the rest of the tuple R (a tuple pattern, not a template one)
    ? R extends [] ? H : `${H}${D}${Join<R, D>}`  // if R is now empty, H is the last piece — stop; otherwise glue H, D, and the recursive join of R together
    : '';  // T didn't match the [H, ...R] shape — that only happens when T is [], so the result is the empty string

type A = Join<['a', 'b', 'c'], '-'>; // 'a-b-c'
TS will yell at deep recursion. Around 50–100 levels you'll see "Type instantiation is excessively deep and possibly infinite". For practical recursive parsing keep inputs bounded — and consider whether the type-level work is really paying for itself versus a runtime check.

10. Real-world patterns

CSS-in-TS — typed property names

type Side = 'top' | 'right' | 'bottom' | 'left';
type Spacing = `margin-${Side}` | `padding-${Side}`;
// 'margin-top' | 'margin-right' | ... | 'padding-left'

function setSpacing(prop: Spacing, value: string) { /* ... */ }
setSpacing('margin-left', '8px');  // ✓
setSpacing('margin-xxx', '8px');   // ✗ Type error

Type-safe SQL fragment (sketch)

type SelectStmt<S> =  // S is a whole SQL-ish SELECT string to pick apart at the type level
  S extends `SELECT ${infer Cols} FROM ${infer Table}`  // does S start with "SELECT ", have a "FROM " later, and end with a table name? capture the columns text and the table name
    ? { columns: Split<Cols, ', '>; table: Table }  // yes: reuse the Split helper from section 8 to turn "id, name" into the tuple ['id', 'name']
    : never;  // doesn't match the SELECT ... FROM ... shape at all

type Q = SelectStmt<'SELECT id, name FROM users'>;  // Cols captures 'id, name', Table captures 'users'
// { columns: ['id', 'name']; table: 'users' }

Lodash-style "get" with dot paths (preview)

type DeepGet<T, P> =
  P extends `${infer K}.${infer R}`
    ? K extends keyof T ? DeepGet<T[K], R> : never
    : P extends keyof T ? T[P] : never;

type User = { profile: { name: string; age: number }; id: number };
type A = DeepGet<User, 'profile.name'>;  // string
type B = DeepGet<User, 'id'>;           // number
type C = DeepGet<User, 'nope'>;         // never

Angular & NgRx — typed action / selector names

// Prefix every action with a feature name
type FeatureActions<F extends string, A> = {
  [K in keyof A as `[${F}] ${K & string}`]: A[K];
};

type UserActions = FeatureActions<'User', {
  Load: void;
  LoadSuccess: { users: string[] };
}>;
// {
//   '[User] Load': void;
//   '[User] LoadSuccess': { users: string[] };
