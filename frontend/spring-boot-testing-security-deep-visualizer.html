Testing Secured Endpoints

Security is exactly the code you most want tested — and the easiest to forget, because the happy path passes whether or not the guard works. spring-security-test lets you fake an authenticated caller in a slice test, so you can assert the two things that matter: the right caller gets 200, and the wrong one gets 401 or 403. The negative tests are the whole point.

Why do security tests need @WithMockUser / JWT mocks — and what exactly are you testing?

The most common gap in API testing: the tests cover "what does the endpoint return when it works?" but not "what happens when an unauthorized user calls it?" A @WebMvcTest slice test starts the MVC layer (controllers, filters, security config) but not the full application context. Without a mock user, every request is anonymous and is rejected with 401 — but that means your test of the controller's logic never actually runs. spring-security-test provides two ways to fake authentication: @WithMockUser(roles="ADMIN") for simple role-based tests, and SecurityMockMvcRequestPostProcessors.jwt() for JWT-specific claim tests. The critical tests you must write: (1) authenticated user with correct role gets 200, (2) authenticated user with wrong role gets 403, (3) unauthenticated gets 401. If all three pass, your security config is correct.

@WithMockUser

@Test @WithMockUser(username="admin", roles={"ADMIN"}) void adminCanDeleteUser() throws Exception { mockMvc.perform(delete("/api/users/42")).andExpect(status().isNoContent()); }. @Test @WithMockUser(roles={"USER"}) void userCannotDeleteUser() throws Exception { mockMvc.perform(delete("/api/users/42")).andExpect(status().isForbidden()); }. @Test void anonymousCannotAccess() throws Exception { mockMvc.perform(get("/api/users")).andExpect(status().isUnauthorized()); }.

JWT mock for claim-based tests

mockMvc.perform(get("/api/users").with(jwt().jwt(b -> b.claim("ciam_roles", List.of("CIAM_ADMIN")).claim("sub","user-42").claim("iss","https://ping.contoso.com")))).andExpect(status().isOk()). The jwt() post-processor creates a mock JwtAuthenticationToken with the specified claims — no real JWT is needed, no real IDP is called. Tests the claim-mapping code in your JwtAuthenticationConverter. Critical for multi-IDM setups: test that Ping-style claims AND Entra-style claims both produce the correct authorities.

Method security tests

@ExtendWith(SpringExtension.class) @SpringBootTest class UserServiceSecurityTest { @Autowired UserService service; @Test @WithMockUser(roles="USER") void regularUserCannotAssignAdminRole() { assertThrows(AccessDeniedException.class, () -> service.assignRole(42L, ADMIN_ROLE_ID)); } @Test @WithMockUser(roles="CIAM_ADMIN") void ciamAdminCanAssignAnyRole() { assertDoesNotThrow(() -> service.assignRole(42L, ADMIN_ROLE_ID)); } }. Tests the @PreAuthorize directly on service methods.

In CIAM: Write a security test for every role-protected endpoint. Template: "USER_MANAGER can search users (200), USER_MANAGER cannot delete users (403), CIAM_ADMIN can delete users (200/204), anonymous cannot do anything (401)." For claim mapping: "Ping-style token with groups=[CIAM_ADMIN] produces ROLE_CIAM_ADMIN authority (200 on admin endpoint)" AND "Entra-style token with roles=[CIAMAdmin] also produces ROLE_CIAM_ADMIN authority (200)." These tests ensure a broken claim-mapping config is caught in CI before production.

1. Fake the caller, assert the gate

Use a real security filter chain in the test (import your SecurityConfig), then attach a fake authentication with a request post-processor or @WithMockUser. You're testing your authorization rules, not the IDM — so you don't need a real token.

Anonymous → 401 everywhere. Authenticated-but-not-admin → 200 on progress, 403 on admin. The point of the test suite is to prove both the allow and the deny.

3. The test

@WebMvcTest(AdminController.class)
@Import(SecurityConfig.class)          // use the REAL filter chain, not a stubbed one
class AdminControllerTest {
  @Autowired MockMvc mvc;
  @MockitoBean UserService users;     // collaborators are mocked in a @WebMvcTest

  @Test void anonymous_is_401() throws Exception {
    mvc.perform(delete("/api/admin/users/1"))
       .andExpect(status().isUnauthorized());        // 401
  }
  @Test void nonAdmin_is_403() throws Exception {
    mvc.perform(delete("/api/admin/users/1").with(jwt()))
       .andExpect(status().isForbidden());           // 403
  }
  @Test void admin_is_200() throws Exception {
    mvc.perform(delete("/api/admin/users/1")
          .with(jwt().authorities(new SimpleGrantedAuthority("ROLE_ADMIN")))
          .with(csrf()))                             // csrf() if your config needs it
       .andExpect(status().isOk());
  }
}

Post-processors: jwt() (resource-server), user("x").roles("ADMIN"), csrf(). Annotation form: @WithMockUser / @WithMockUser(authorities="SCOPE_users.read").

4. Traps

  • Forgetting @Import(SecurityConfig) in a @WebMvcTest → Boot applies a default chain, so your real rules aren't tested (everything may pass or 401 wrongly).
  • Only testing the happy path. A guard that never denies is broken and green. Always add the 401 and 403 cases.
  • Missing csrf() on POST/PUT/DELETE when CSRF is enabled (cookie/session mode) → a spurious 403. (This app is stateless+JWT, so CSRF is off — see the CSRF page.)
  • roles("ADMIN") adds the ROLE_ prefix; authorities("ROLE_ADMIN") does not. Match what hasRole/hasAuthority expects.
  • Method security needs the bean. To test @PreAuthorize on a service directly, use @SpringBootTest (or import the method-security config) so the proxy exists.

5. One-sentence recap

🧪 Test security with spring-security-test: stand up the real filter chain (@WebMvcTest + @Import(SecurityConfig)), fake the caller with a request post-processor (.with(jwt()…), user().roles(), csrf()) or @WithMockUser, and assert all three outcomes — anonymous → 401, authenticated-but-unauthorized → 403, authorized → 200 — because the deny cases are what actually prove the guard works.
