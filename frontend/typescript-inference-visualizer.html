Type Inference, Widening & as const

Why TypeScript infers the types it does — and how to control it. The daily-confusion topic, made clear.

1. Inference — TypeScript types things for you

You rarely annotate everything. TS infers a type from the value on the right of =, from a function's return, and from surrounding context. The skill is knowing what it infers — because it isn't always what you'd write by hand.

let count = 5;            // inferred: number
let name = 'Bobby';       // inferred: string  (NOT 'Bobby')
const pi = 3.14;          // inferred: 3.14   (the literal!)
const tags = ['a', 'b'];   // inferred: string[]
const user = { id: 1 };    // inferred: { id: number }

function double(n: number) {
  return n * 2;            // return type inferred: number
}

Notice line 2 vs 3: let name = 'Bobby' is string, but const pi = 3.14 is the literal 3.14. That difference is widening — the heart of this page.

2. Literal widening — let vs const

Why let widens but const doesn't

A const can never be reassigned, so its type is the exact literal. A let can be reassigned, so TS widens the literal to its general type (so you can later assign other strings/numbers).

const a = 'GET';   // type: 'GET'   (literal)
let   b = 'GET';   // type: string  (widened)

b = 'POST';       // ✓ fine — b is string

// this matters when calling typed functions:
function request(method: 'GET' | 'POST') {}

request(a);         // ✓ a is 'GET'
request(b);         // ✗ string not assignable to 'GET'|'POST'

This is the "string is not assignable to 'GET' | 'POST'" error that confuses everyone. The fix: keep it const, annotate the type, or use as const.

3. Objects & arrays widen too

Object properties are mutable → widened

const config = {
  method: 'GET',     // widened to string
  retries: 3,        // widened to number
};
// type: { method: string; retries: number }

// even though config is const, its PROPERTIES
// can be reassigned, so they widen:
config.method = 'POST';  // ✓ allowed

// so this fails:
request(config.method);  // ✗ string not 'GET'|'POST'
{ method: 'GET' } widens to → { method: string }

as const freezes everything to literals

const config = {
  method: 'GET',
  retries: 3,
} as const;
// type: {
//   readonly method: 'GET';
//   readonly retries: 3;
// }

request(config.method);  // ✓ now it's 'GET'
config.method = 'POST';  // ✗ readonly — can't assign

// arrays become readonly tuples:
const point = [3, 4] as const;
// type: readonly [3, 4]   (not number[])

✓ as const = "treat this literal as deeply immutable and as narrow as possible."

4. satisfies — validate without widening v4.9+

The problem satisfies solves

You want two things at once: (1) check an object matches a type, but (2) keep the narrow inferred types of its values. A plain annotation gives you (1) but loses (2).

type Config = Record<string, string | number>;

// annotation — checked, but values WIDENED
const a: Config = { host: 'localhost', port: 8080 };
a.port.toFixed();   // ✗ port is string|number, no toFixed

// satisfies — checked AND keeps narrow types
const b = { host: 'localhost', port: 8080 }
  satisfies Config;
b.port.toFixed();   // ✓ TS knows port is number
b.host.toUpperCase(); // ✓ host is string

5. Contextual typing — inference flows inward

TS infers callback params from where they're used

You don't annotate e or item below — TS knows their types from the surrounding API. This is inference flowing into the function from context.

// e is inferred as MouseEvent — from addEventListener
button.addEventListener('click', (e) => {
  e.clientX;   // ✓ no annotation needed
});

// n is inferred as number — from number[]
[1, 2, 3].map((n) => n * 2);

// item is inferred as User — from User[]
users.filter((item) => item.active);

💡 If you ever see a callback param typed as any, contextual typing failed — usually the surrounding type was any or untyped.

Return-type inference vs explicit

// inferred return — convenient
function makeUser(name: string) {
  return { name, createdAt: Date.now() };
}
// inferred: { name: string; createdAt: number }

// explicit return — a contract you enforce
function makeUser2(name: string): User {
  return { name, createdAt: Date.now() };
  // ✗ errors HERE if shape is wrong, not at call site
}

Rule of thumb: let TS infer local returns; annotate public/exported functions so the contract is explicit and errors point at the source.
