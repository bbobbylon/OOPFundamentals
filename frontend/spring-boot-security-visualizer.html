Spring Security

The filter chain, authentication vs authorization, and securing REST APIs with JWT Bearer tokens.

🛡️ What does Spring Security actually do? Why is 401 different from 403?

Without Spring Security, every HTTP request reaches your controller — anyone could call DELETE /api/users/42 with no token. Spring Security inserts a filter chain that runs before your controller: an ordered set of filters that inspect the request, decide whether it's allowed, and either pass it through or reject it. Two distinct questions get answered — authentication (who are you?) and authorization (are you allowed?) — and they map to two different failure codes.

  • Authentication = identity. Validate the JWT, verify its signature against the IDM's public keys, check expiry → build an Authentication.
  • Authorization = permission. Does your roles claim include ADMIN? Enforced per-endpoint with @PreAuthorize.
  • 401 ≠ 403. 401 = not authenticated (no/bad token); 403 = authenticated but not allowed (valid token, wrong role).
  • Configured once. A SecurityFilterChain bean declares the rules; every request flows through the chain automatically.

Authentication vs Authorization

Authentication — who are you? (validate the JWT, verify the signature, check expiry). Authorization — are you allowed? (does your role include ADMIN?). 401 = no/bad token. 403 = valid token, wrong role.

JWT Bearer flow

1. Angular sends Authorization: Bearer <JWT>. 2. Spring extracts & validates it. 3. Claims → Authentication in the SecurityContext. 4. @PreAuthorize("hasRole('ADMIN')") checks the claims. 5. 200 (allowed) or 403 (wrong role).

CIAM security chain: Your Angular app gets a JWT from Entra ID / Ping after OIDC login. The Spring API validates that JWT's signature against the IDM's JWKS endpoint, extracts the roles claim, and uses @PreAuthorize on each endpoint to enforce who can do what — configured once.

The mechanism

Six rules on the list. The request only ever meets one of them.

  1. The request already carries whatever Authentication earlier filters built — a real principal, or the anonymous one if no token was offeredauthentication already decided
  2. AuthorizationFilter walks your authorizeHttpRequests(...) entries in the exact order you wrote themnot sorted, not weighted
  3. For each entry, it tests the request's path against that entry's matcher patternAnt-style paths, e.g. /api/admin/**
  4. The first pattern that matches wins. Evaluation stops there — pass or failthis is the whole bug
  5. That one rule's check runs: permitAll() always passes, hasRole/hasAuthority checks the authorities on the Authenticationpass → controller, fail → AccessDeniedException
  6. Every entry below the matching one is never evaluated for this request — including one that names the path far more preciselydead code that still compiles

Step 4 is the lesson, and the other five are bookkeeping around it. There is no ranking pass, no "most specific wins" tiebreaker, no second look — the moment a pattern matches, Spring stops reading. Everything else in this block, the health-check bug included, is a consequence of that one sentence.

Your chain has, in this exact order: .requestMatchers("/api/**").permitAll(), then .requestMatchers("/api/reports/**").hasAuthority("SCOPE_reports.read"), then .anyRequest().authenticated(). A request with no Authorization header hits GET /api/reports/quarterly. What comes back?

A completely reasonable guess — "the more specific rule wins" is how CSS selectors, Java overload resolution, and plenty of other systems actually behave. But authorizeHttpRequests has no concept of "more specific." It never compares your two patterns against each other; it just asks each one, in order, "does this match?" — and /api/** already said yes three lines earlier. The reports rule never runs, so it can't produce a 403.

Right — and this isn't Spring being lenient, it's the documented contract: matchers evaluate in declaration order and the first match wins, full stop. That's why git blame on the reports rule usually comes back clean — the rule was never wrong, it's just unreachable from where it sits.

There's no such floor. permitAll() means exactly what it says — zero authentication required, not "authentication optional." If unauthenticated traffic should still be rejected for some other reason, that has to be written as its own rule; as written, this one guarantees the controller runs.

Where you've seen this before

Ordered rule lists show up everywhere security gets enforced. They all share this exact trap.

Firewall rules — the original "first match wins"

An iptables chain or an AWS security group's rule list works on the identical principle: rules are walked top to bottom, and the first one that matches the packet decides its fate. A wide-open ACCEPT rule placed above a narrow DENY rule doesn't get overruled by the more specific rule underneath it — the DENY rule just never runs. Same bug, thirty years older.

first match wins, not best match

CSS taught you the opposite instinct — that's why this one bites

A CSS engine ranks selectors by specificity first and only falls back to source order to break a tie between equally specific rules — so .admin-badge beats a plain div selector even if the div rule is written last. Years of that habit is exactly what makes authorizeHttpRequests feel broken the first time it bites: there is no specificity ranking here at all, only position.

specificity vs. position — different rulebooks entirely

In CIAM: the gateway sitting in front of this exact service

A real CIAM deployment usually puts a gateway in front of a Spring resource server like this one — Spring Cloud Gateway, an API management layer, an ALB's listener rules. Every one of them matches incoming routes in a defined order and stops at the first predicate that fits, for the same reason authorizeHttpRequests does. Add a broad new route to send more traffic through a new pipeline, and it can quietly swallow a narrower route that used to handle that traffic — with no error at the gateway, the app, or the deploy pipeline.

the bug moves up a layer, the rule stays identical
Questions from the back row

If order matters this much, why doesn't Spring just sort my rules from most specific to least specific automatically?

Because it would have to understand your intent to do that safely, and Ant-style path patterns don't carry enough information for that. Is /api/admin/** "more specific" than /api/*/reports? For some URLs yes, for others no — there's no total ordering that works for every pair of patterns. Rather than guess, Spring makes you the one who decides, and the price of that control is that the order you write is the order that runs.

Why did a request with no Authorization header at all come back 401, when it failed a hasRole check — isn't that supposed to be a 403?

This is the one exception to "AccessDeniedException means 403." By default Spring still builds an Authentication for a request with no token — an anonymous one, via AnonymousAuthenticationFilter — so hasRole('ADMIN') fails it the normal way. But ExceptionTranslationFilter checks whether the failing Authentication is anonymous, and if it is, it doesn't hand back 403 — it invokes the same AuthenticationEntryPoint a flat-out authentication failure uses. The logic: you were never given a chance to prove who you are, so "forbidden" is the wrong message — "authenticate first" is the honest one. Send a real but insufficiently-privileged token instead and you get an actual 403, no translation involved.

Does @PreAuthorize have the same ordering problem?

No ordering problem — there's no list to order, just one SpEL expression evaluated for that one method call. But it has a sharper trap of its own: it only runs when the call arrives through Spring's proxy. Call the annotated method from another method on the same bean (this.deleteUser(id)) instead of going through an injected dependency, and the proxy is never in the path — the annotation is silently skipped. No exception, no log line, the code just runs as if @PreAuthorize weren't there.

2 — Authentication vs Authorization

Authentication — "Who are you?"

Verifying identity. Checking credentials: username+password, JWT signature, OAuth2 token.

Result: a Authentication object in SecurityContextHolder containing the principal (who they are) and their authorities (what they can do).

Failure → 401 Unauthorized

Authorization — "What can you do?"

Checking if an authenticated principal has permission to perform an action on a resource.

Roles (ROLE_ADMIN, ROLE_USER) or scopes (SCOPE_api.read) are granted authorities checked against your access rules.

Failure → 403 Forbidden

3 — JWT Bearer Token Flow

Click Next Step to walk through the stateless JWT authentication flow:

1

User Logs In

Client POSTs to /auth/login (your auth server or Entra ID) with credentials. Spring Security authenticates them.

2

Server Issues JWT

Server creates a JWT: header.payload.signature. Signs it with a private key. Payload contains: user ID, roles/scopes, exp (expiry), iss (issuer). Returns it to the client.

3

Client Stores JWT

Angular stores the token in memory (safest) or sessionStorage. Never store JWTs in localStorage — vulnerable to XSS attacks that can steal tokens.

4

Client Sends JWT in Every Request

Every API call includes: Authorization: Bearer eyJhbGciOiJSUzI1NiJ9.eyJ1c2VyIjoiYm9i.... An Angular HTTP interceptor (or MSAL interceptor) does this automatically.

5

Server Validates JWT Locally

Spring Security's BearerTokenAuthenticationFilter extracts the token. Validates signature using the public key (from JWKS endpoint — cached). Checks exp not past, iss matches config. No database call. No network call.

6

Access Granted

Security context populated with user's identity and roles/scopes. Request proceeds to the controller. Controller can access: @AuthenticationPrincipal Jwt jwt to read claims.

🌱 New to this? Security is a checkpoint before your code runs.

Before a request ever reaches your controller, Spring Security runs it through a chain of filters that asks two questions, in order: who are you? (authentication) and are you allowed to do this? (authorization). If you sent no/bad credentials, you get 401 Unauthorized ("I don't know who you are"). If you're known but lack the right role, you get 403 Forbidden ("I know you, but no"). You wire all of this up in one SecurityFilterChain bean — and by default everything is locked down until you open it. That's the whole mental model: a checkpoint that runs before your code, deciding 200 vs 401 vs 403.

🧠 Expert corner — two gates, JWTs, and the SecurityContext

  • There are two authorization gates, not one. authorizeHttpRequests(...) matches URLs (first-match wins, so order matters) and runs early in the chain; @PreAuthorize runs at the method with full SpEL and access to arguments (#id == authentication.name). URL rules are the coarse net; method security is the fine, per-object gate.
  • JWT resource server. Point it at an issuer-uri and Spring fetches the IDM's public keys (JWKS), validates every token locally per request (signature, issuer, audience, expiry) — no call to the IDM. See Tokens, Keys & Signing.
  • Claims → authorities. A JwtAuthenticationConverter maps token claims (roles/scopes) to GrantedAuthority (ROLE_* / SCOPE_*); accept several IDMs at once with JwtIssuerAuthenticationManagerResolver.
  • The SecurityContextHolder holds the current Authentication in a ThreadLocal — that's how @PreAuthorize and authentication.name see "the current user" anywhere in the call.
  • Stateless vs session & CSRF. A bearer-token API is stateless (no server session) — and CSRF protection is only needed for cookie-based auth, so it's commonly disabled for pure JWT-header APIs (enable it for the BFF/cookie path). Go deeper: the filter chain · @PreAuthorize.
