Infrastructure as Code — Terraform

Provision cloud infrastructure from versioned config instead of clicking in a console. You declare the desired state in HCL; Terraform diffs it against recorded state and the real cloud, then applies only the changes needed to converge.

🏗️ What is Infrastructure as Code — and why "plan then apply"?

Infrastructure as Code (IaC) means your servers, networks, databases, and DNS are defined in version-controlled files, not created by hand in a web console. Terraform is the most common cloud-agnostic IaC tool, and it is declarative: you describe the desired end state — "an App Service, a Postgres database, a Key Vault" — and Terraform figures out the create/update/delete actions to get there. You write HCL (HashiCorp Configuration Language) declaring resources, each belonging to a provider (the azurerm, aws, or google plugin that knows that cloud's API). The workflow has three commands. terraform init downloads the providers and sets up the backend. terraform plan is the safety feature: Terraform reads the current state file (its record of what it manages), refreshes it against the real cloud, compares both to your HCL, and prints an exact diff — what it will create (+), change (~), or destroy (-) — without touching anything. terraform apply then executes that plan, calling provider APIs and recording the results back into state. The state file is the linchpin: it maps each HCL resource to a real cloud object (by id), so Terraform knows the difference between "create new" and "update existing." It also detects drift — when someone changes infrastructure manually, the next plan shows the divergence so you can reconcile. The result is infrastructure that is reviewable in a pull request, reproducible across environments, and auditable in git history.

  • Declarative — describe the desired state; Terraform computes the actions to reach it.
  • Providers + resources — a provider (azurerm/aws) exposes resource types you declare in HCL.
  • plan = a diff — desired (HCL) vs recorded (state) vs real (cloud) → +/~/-, no changes made.
  • State — maps each resource to a real cloud object; enables updates, deletes, and drift detection.

A resource (HCL)

resource "azurerm_resource_group" "rg" { name = "ciam-prod" location = "eastus" } resource "azurerm_key_vault" "kv" { name = "ciam-secrets" resource_group_name = azurerm_resource_group.rg.name }

The workflow

terraform init # get providers terraform plan # show the diff + 2 to add ~ 0 to change - 0 to destroy terraform apply # execute the plan

Your day-job comparison

Terraform is the cloud-agnostic cousin of Azure Bicep / ARM (this repo uses Bicep for Azure Container Apps) and AWS CloudFormation. The plan diff ≈ ARM "what-if" / a CloudFormation change set. State ≈ what the resource provider tracks internally, but Terraform makes it an explicit, shared file. One Terraform codebase can target Azure and AWS with different providers — handy for a multi-cloud CIAM footprint.

CIAM / provisioning: the infrastructure a CIAM app needs — an App Service/Container App, a managed database, a Key Vault for client secrets and signing keys, DNS, and the app registration's redirect URIs — is exactly what you want in code: reviewed in a PR, identical across dev/stage/prod, and rebuildable after a disaster. Store the state file remotely (an Azure Storage container or S3 bucket with locking) so a team shares one source of truth, and never commit secrets — reference them from Key Vault. This pairs with the CI/CD page: a pipeline typically runs terraform plan on a PR and terraform apply on merge behind an approval gate.

The problem

Terraform doesn't track a resource by what it IS in the cloud — it tracks it by the exact string you happened to type as its name in your HCL file.

You renamed one resource block for readability. Terraform deleted your production Key Vault to do it.

The Key Vault from this page's own code walkthrough has been live for a year, holding your IdP's client secrets and JWT signing keys: resource "azurerm_key_vault" "kv" { name = "ciam-secrets" ... }. A new engineer does a readability pass and renames the local identifier — "kv" becomes "secrets_vault" — leaving every argument inside the block untouched. It feels like a no-op, so obviously safe that they skip running plan before opening the PR.

Terraform's state maps by address — azurerm_key_vault.kv — never by the vault's actual Azure resource id, and certainly not by "what this HCL block conceptually represents." The next plan finds azurerm_key_vault.kv in state with no matching block left in the HCL (- destroy), and azurerm_key_vault.secrets_vault in the HCL with no entry in state (+ create) — two completely unrelated resources, as far as Terraform is concerned, even though every argument inside them is byte-for-byte identical. The reviewer skims a diff that reads like a rename and approves it. apply runs both actions: the real, live vault is deleted, then a brand-new, empty one is created under the new address. Every client secret and signing key that lived in the old vault is gone. Every JWT the old signing key backs becomes unverifiable the instant the key disappears.

the name argument is unchanged ✓ sku_name and every other setting are unchanged ✓ the PR diff reads like a cosmetic rename ✓ Terraform sees two unrelated resources, not one renamed one ⚠

State doesn't know what a Key Vault is FOR. It only knows the string azurerm_key_vault.kv used to map to an id, and nothing in your HCL claims that string anymore.

Tell Terraform a rename is a rename — don't let it guess
Add a moved block (Terraform 1.5+) ↓ moved { from = azurerm_key_vault.kv; to = azurerm_key_vault.secrets_vault } tells Terraform explicitly "this is the same object under a new address" — plan then shows a clean no-op instead of a destroy+create Or run terraform state mv before you ever touch the HCL name ↓ this re-points the EXISTING state entry to the new address directly, so the moment your renamed HCL runs a plan, it already matches — the pre-1.5 way of doing exactly what moved now automates Run plan on every change — even a "pure" rename — and actually read the -/+ lines ↓ a destroy+create is right there in plan output; the failure here was never in Terraform, it was in deciding a rename was too trivial to preview
The one-sentence rule. Terraform's state maps a fixed string — the resource's address in your HCL — to a real object's identity; the moment that string changes with no explicit migration, Terraform has no way to know you meant "rename" instead of "delete this one, and, unrelated, also make a new one that happens to look similar."
It's like changing the name plate on your office door and having the building's directory delete your entire office and build a brand-new empty one under the new name — instead of just updating the label on the door you're already sitting behind.

The state file

Obviously to you. I don't read intent — I match addresses. Tell me it's the same thing with a moved block or state mv, and I'll treat it as the same thing. Otherwise I take your HCL exactly as literally as it's written.

The mechanism

Follow one resource through a plan that looks like nothing, and turns out to be everything.

  1. State holds one entry: azurerm_key_vault.kv → a real Azure id, currently holding live secretsbefore the rename
  2. Engineer renames the HCL block's local name to secrets_vault — every argument inside stays identicalpure refactor
  3. terraform plan compares state's addresses against the new HCL's addressesaddress comparison
  4. azurerm_key_vault.kv is in state with no matching HCL block anymore → planned for destroyorphaned in state
  5. azurerm_key_vault.secrets_vault is in HCL with no entry in state → planned for createunmatched in HCL
  6. apply runs both actions: the live vault (and everything in it) is deleted, then an empty one is created under the new addressdata gone

Step 3 is the entire mechanism, and there's no bug in it anywhere — plan is doing exactly its documented job, matching state addresses against HCL addresses. The mistake happened one step earlier, in step 2, the instant a human treated a rename as too small to need an explicit moved block or an actual plan review. Terraform never had the information needed to know the two blocks were "the same resource, renamed" — that information only ever existed in the engineer's head.

renaming a resource's local namemoving a resource into a modulechanging a for_each key
the old address vanishes from HCL, matching nothing in the new config ↓
Terraform plans a destroy for something that never logically went awayonly its address in the file changed — three different refactors, the identical mechanism

All three of these are ordinary, well-intentioned edits that Terraform's own documentation specifically calls out as needing a moved block — because all three change a resource's address without changing the resource itself. The fix is identical regardless of which refactor caused it: tell Terraform explicitly that the old address and the new address name the same object, instead of leaving it to infer that from arguments it never compares.

An engineer renames a Terraform resource's local name — resource "azurerm_key_vault" "kv" becomes resource "azurerm_key_vault" "secrets_vault" — changing nothing else inside the block. No moved block or terraform state mv is used. What does the next terraform plan show?

Right. State keys are addresses — type plus local name — not a hash of the block's arguments. kv disappearing and secrets_vault appearing with no state entry look, to Terraform, like an unrelated deletion and an unrelated creation, even though a human can plainly see they're the same vault.

Terraform never compares the contents of an orphaned state entry against the contents of an unmatched HCL block to guess they're related — it only matches on address. Identical arguments inside two differently-addressed blocks are, to Terraform, a coincidence, not a signal of anything.

A resource address with no matching state entry is an entirely ordinary situation — it's exactly what a brand-new resource looks like on its very first plan. Terraform has no way to tell "this is new" apart from "this used to have a different name" without you telling it explicitly.

Where you have seen this before

"Identity is tracked by a fragile label, not by what the thing actually is" breaks the same way in every tool that has to key on a name.

Natural keys used as foreign keys

A schema that foreign-keys on a "natural" value — a username, an email — instead of a surrogate numeric id breaks the moment that natural value legitimately changes: every row referencing the old username now points at nothing. Database design guidance has recommended surrogate keys for exactly this reason for decades — the underlying entity's identity shouldn't be tied to a value that's allowed to change.

the same fragile-key trap, one layer down in the schema

Renaming a Kubernetes Deployment

Changing a Deployment's metadata.name isn't a rename to the Kubernetes API — it's a brand-new object. The old Deployment (and its ReplicaSets and Pods) gets torn down or orphaned, and a new Deployment starts fresh, because the API server has no concept of "this is the same workload, just relabeled."

a different orchestrator, the identical delete-and-recreate trap

AWS CloudFormation logical IDs

This page's own intro compares Terraform to CloudFormation — here's where they share a scar: CloudFormation tracks resources by the logical ID you give them in the template, and renaming that logical ID plans a DeleteResource plus a separate CreateResource, the exact same shape of accident, in the sibling tool this page already put side by side with Terraform.

The whole page on a napkin: Terraform reads your HCL as the desired end state, diffs it in a dry-run plan against state and the live cloud, and apply executes only the create/update/destroy actions needed to converge — with the state file mapping each resource's address to its real cloud id. The one new sentence this block adds: that map is keyed on the address you happen to type in your HCL, not on what the resource actually is, so a pure rename with no explicit moved block or state mv looks to Terraform exactly like deleting one resource and creating an unrelated new one — and it will do precisely that.

1. Declare resources in HCL

terraform {
  required_providers { azurerm = { source = "hashicorp/azurerm" } }
  backend "azurerm" { ... } # remote state (shared, locked)
}
resource "azurerm_resource_group" "rg" {
  name = "ciam-prod"
  location = "eastus"
}
resource "azurerm_key_vault" "kv" {
  name = "ciam-secrets"
  resource_group_name = azurerm_resource_group.rg.name # implicit dependency
  location = azurerm_resource_group.rg.location
}
References build a dependency graph. Each resource block is resource "<type>" "<local-name>". When the Key Vault reads azurerm_resource_group.rg.name, Terraform learns the vault depends on the resource group and orders creation automatically — no manual sequencing. The backend block stores state remotely (here in Azure Storage) with locking, so a whole team plans and applies against one shared source of truth instead of local files that drift apart.

2. State maps config to real resources

# terraform.tfstate (simplified) — Terraform's record of reality
{
  "azurerm_resource_group.rg": { id: "/subscriptions/.../ciam-prod" },
  "azurerm_key_vault.kv": { id: "/subscriptions/.../vaults/ciam-secrets",
                      sku_name: "standard" }
}
State is how Terraform knows "create" from "update." Each managed resource is recorded with its real cloud id. Without state, Terraform couldn't tell whether your azurerm_key_vault.kv already exists — it would try to recreate it every run. With state, it maps the HCL name to the existing object and computes only the delta. State can hold sensitive values, which is why it lives in a locked remote backend with access control, never in git.

3. plan is a three-way diff

$ terraform plan
  + azurerm_resource_group.rg # in HCL, not in state → CREATE
  ~ azurerm_key_vault.kv # sku_name "standard" → "premium" → UPDATE
  - azurerm_storage_account.old # in state, removed from HCL → DESTROY

Plan: 1 to add, 1 to change, 1 to destroy.
plan compares three things: HCL (desired), state (recorded), and the live cloud (refreshed). A resource in your config but not in state is a create (+); one in both whose attributes differ is an update (~); one in state but deleted from config is a destroy (-). Crucially, plan changes nothing — it's a dry run you review (and gate in CI) before apply executes exactly that set of actions. This preview is Terraform's core safety property.
