Debugging RxJS Pipelines

Almost every RxJS bug is one of five: nothing emits, it emits too much, a stale response wins a race, it leaks, or one error kills it forever. And the root cause is nearly always the same short list — cold-vs-hot, the wrong flattening operator, or a subscription you never managed. A single tap() in the pipe usually reveals which.

🐛 The 5 RxJS bugs — and the one technique that reveals all of them

RxJS pipelines are invisible by default — you call .pipe() and either see a result or don't. The hard part isn't writing the pipeline; it's knowing where in the pipe the problem is and why. The universal tool is tap(): drop it anywhere to log values without changing them — .pipe(tap(v => console.log('before', v)), switchMap(...), tap(v => console.log('after', v))). If the "before" tap logs but "after" doesn't, you've found the operator swallowing values. One operator at a time.

  • Nothing emits: you forgot .subscribe()/async, or a filter/distinctUntilChanged is eating values.
  • Race condition: using mergeMap/concatMap for search instead of switchMap (cancel-the-old).
  • Error kills the stream: an uncaught error completes the Observable — guard inner streams with catchError.
  • Memory leak: a forgotten .subscribe() stays alive after destroy — use the async pipe / takeUntilDestroyed().
  • The technique: bracket each operator with tap() and walk downstream until the values stop.

Bug 1: nothing emits

Cold Observable never subscribed (forgot .subscribe()/async pipe); a filter() that's never true; distinctUntilChanged() treating values as equal by reference. tap() before it shows what's actually arriving.

Bug 2: race condition

Type fast → 3 requests → response 2 lands after response 3 → stale data wins. Caused by mergeMap/concatMap where you wanted switchMap (cancels in-flight). tap(v => console.log(Date.now(), v)) reveals the ordering.

Bug 3: error kills the stream

An uncaught error completes the Observable — later emissions never arrive (a search that 404s stops forever). Fix: switchMap(() => api.search().pipe(catchError(() => of([])))) — recover the inner stream without killing the outer.

Debug workflow:1) tap(v => console.log('A', v)) at the source; 2) another after the first operator; 3) keep adding downstream until values stop — that's the broken operator. For leaks: Chrome DevTools → Memory → heap snapshots before/after navigation; lingering subscription objects mean you didn't unsubscribe.

Silence isn't a diagnosis — it's the absence of one. A next-only tap() can only ever tell you what arrived; it says nothing about what left. Filtering a value out, erroring, and completing all look identical from a next-only tap's point of view: no line printed. The bisection technique this page teaches — sandwiching a suspect operator in taps — only tells you WHERE a stream stops. It can't tell you WHY unless you're also listening for error and complete, which none of the taps in this page's own examples do.
Think of a next-only tap() as a doorbell camera that only records people walking in. If nobody ever walks back out, that camera has nothing to show you about why — maybe they left through a window (an error), maybe they're genuinely still inside (still pending), maybe they were never let in at all (filtered before they arrived). All three look identical to a camera that only watches the front door. Watching the back door and the windows too — tap's error and complete handlers — is the only way to tell them apart.

The mechanism

tap(fn) is shorthand for one third of an observer. The other two thirds still run — silently, past the version of you that's watching.

  1. You write tap(v => console.log(v)) — RxJS treats the single function you passed as the next handler onlythe shorthand's whole limitation starts here
  2. A value flows in; your function runs, logs it, and tap forwards it downstream unchangedthis half works exactly as expected
  3. The operator right after your tap throws inside its own callback — a map() calling something that crashes, sayan ordinary, common failure
  4. RxJS converts that thrown exception into an error() notification and propagates it downstream, exactly like any Observable errorthis part is invisible unless you're watching for it
  5. Your next tap downstream receives that error() call — but you never gave it an error handler, so nothing gets logged. It still propagates onward exactly as it shouldsilence, not swallowing
  6. You read the console, see no new lines, and reach for the most common explanation you've seen produce this exact symptom before — a filterthe misdiagnosis is a reasonable one

Step 5 is the lesson. tap() without an error handler doesn't hide the error — it just doesn't announce it, and forwards it on exactly like it's supposed to. The bug in your debugging session isn't RxJS misbehaving; it's a diagnostic tool you built with only one of its three ears turned on.

Two of the three channels a tap() could report on are switched off by default. The bisection technique still narrows down WHERE a stream stops — it just can't tell you WHY unless you wire the other two switches yourself.

Your bisected pipe: tap(v => console.log('1:', v)), map(v => JSON.parse(v)), tap(v => console.log('2:', v)) — both taps use the single-function shorthand, no error handlers. You feed it the string "not valid json". What does the console show?

JSON.parse doesn't fail quietly — invalid JSON throws a SyntaxError every single time; it never just hands back undefined. That behavior would actually make this bug easier to spot, since a visible (if wrong) value would show up in the log. The real behavior is quieter than that.

Tap 1 sits BEFORE map() in the pipe, so it always sees and logs the raw input first — the failure doesn't happen until JSON.parse actually runs, one step later. Nothing about a downstream failure can reach back and stop an upstream tap from having already fired.

Where you've seen this before

Instrumentation that only watches the happy path always looks healthy right up until it doesn't.

Java's ExecutorService.submit() — the exception nobody called .get() to see

Submit a Callable to an ExecutorService and an exception thrown inside it doesn't print, doesn't crash anything, doesn't appear anywhere — it sits captured inside the returned Future until something calls .get() on it, which re-throws it as an ExecutionException. Fire-and-forget the Future the way most code does, and the failure is exactly as silent as an error hitting a next-only tap.

uninspected Future ≈ next-only tap

A dashboard with request count, but no error-rate alarm

A service graphing requests-per-second can look perfectly healthy while its error rate climbs from 1% to 40%, because a failed request still counts as "a request" on that graph. Nobody's ignoring the outage — the dashboard was simply never wired to a channel that would show it, exactly like a tap watching next() while errors sail past underneath it.

count graph without an error-rate graph ≈ tap without error handler

Your CIAM token-refresh interceptor — the same blind spot, higher stakes

An interceptor watching only the happy path of a refreshToken$ pipeline sees every refresh that worked and gets no chance to see the one that didn't. A Ping or Entra outage mid-refresh looks, from the console, identical to "nothing happened yet" — when what actually happened is every authenticated request after it is now failing for a reason nobody logged.

silent refresh failure ≈ silent map() failure
Questions from the back row

Isn't it extra work to always write tap({next, error, complete}) instead of the one-liner?

For a tap() you're leaving in the code long-term, use the shorthand — most passthrough logging genuinely only cares about values. But for a tap() you added specifically to answer "why did this stop," the whole point is ruling out possibilities, and a next-only tap rules out nothing about errors or completion. Write the three-handler version for exactly as long as you're actively debugging, then delete it — the extra typing is smaller than the twenty minutes it just saved you.

If an error happened, wouldn't I see it somewhere — like an uncaught exception?

Only if nothing downstream ever catches it. If there's a catchError further along the pipe — even one that quietly returns EMPTY, exactly like this page's own examples do — it recovers the stream cleanly, and there is no uncaught exception anywhere. The failure is handled so thoroughly that the only trace of it was ever going to be a tap() that happened to be listening for it.

Does this same blind spot apply to complete(), or just error()?

Both, and complete() is arguably sneakier, because it isn't even a failure. A source that completes early — a take(1) upstream, or an Observable that's just naturally finite — stops your downstream taps from logging again, ever, with nothing that looks like a bug at all. A next-only tap can't distinguish "this will emit again later" from "this is over"; for that you need the complete handler too.

1. The one-line debugger: tap

this.search$.pipe(
  tap(q => console.log('1 input ', q)),
  debounceTime(300),
  tap(q => console.log('2 debounced', q)),
  switchMap(q => this.api.search(q).pipe(
     tap(r => console.log('3 result  ', r)))),
)

Drop a numbered tap between each operator and watch the console: the last number that logs is where the stream stops. Did nothing log at all? Nothing subscribed. Logs once per click but you expected one stream? Cold-observable re-subscription.

3. The flattening operator is a top bug source

OperatorInner streamsUse for
switchMapcancels the previous when a new one arrivessearch / type-ahead / navigation (only the latest matters)
mergeMapruns all concurrently, keeps every resultindependent parallel work (⚠ races on search)
concatMapqueues, one at a time, in orderordered writes (e.g. sequential saves)
exhaustMapignores new while one is in flightsubmit buttons (drop double-clicks)

"Old result clobbers new" on a search box is almost always mergeMap where you wanted switchMap. "Double submit" is mergeMap where you wanted exhaustMap.

4. Cold vs hot, and cleaning up

  • Cold = per-subscriber. An HttpClient call is cold — every subscribe re-runs the request. Three async pipes on the same observable = three HTTP calls. Multicast with shareReplay({ bufferSize: 1, refCount: true }).
  • Prefer the async pipe in templates — it subscribes and (crucially) unsubscribes for you, killing most leaks.
  • Manual subscribes must be cleaned up — takeUntilDestroyed() (inject context) or unsubscribe in ngOnDestroy. A leaked subscribe keeps firing — and keeps the component in memory.
  • Errors are terminal. An unhandled error completes the stream; place catchError inside the switchMap so a failed request doesn't kill the outer search stream.

5. One-sentence recap

🔌 Debug an RxJS stream by dropping numbered tap()s between operators (the last one that logs is where it stops), then map the symptom to its usual cause: no emissions = nothing subscribed (use the async pipe), duplicate calls = cold re-subscription (shareReplay), stale race = mergeMap where you needed switchMap, leak = an unmanaged subscribe (takeUntilDestroyed/async pipe), and dies on error = missing catchError (put it inside the inner map).
