Debugging RxJS Pipelines

Almost every RxJS bug is one of five: nothing emits, it emits too much, a stale response wins a race, it leaks, or one error kills it forever. And the root cause is nearly always the same short list — cold-vs-hot, the wrong flattening operator, or a subscription you never managed. A single tap() in the pipe usually reveals which.

🐛 The 5 RxJS bugs — and the one technique that reveals all of them

RxJS pipelines are invisible by default — you call .pipe() and either see a result or don't. The hard part isn't writing the pipeline; it's knowing where in the pipe the problem is and why. The universal tool is tap(): drop it anywhere to log values without changing them — .pipe(tap(v => console.log('before', v)), switchMap(...), tap(v => console.log('after', v))). If the "before" tap logs but "after" doesn't, you've found the operator swallowing values. One operator at a time.

  • Nothing emits: you forgot .subscribe()/async, or a filter/distinctUntilChanged is eating values.
  • Race condition: using mergeMap/concatMap for search instead of switchMap (cancel-the-old).
  • Error kills the stream: an uncaught error completes the Observable — guard inner streams with catchError.
  • Memory leak: a forgotten .subscribe() stays alive after destroy — use the async pipe / takeUntilDestroyed().
  • The technique: bracket each operator with tap() and walk downstream until the values stop.

Bug 1: nothing emits

Cold Observable never subscribed (forgot .subscribe()/async pipe); a filter() that's never true; distinctUntilChanged() treating values as equal by reference. tap() before it shows what's actually arriving.

Bug 2: race condition

Type fast → 3 requests → response 2 lands after response 3 → stale data wins. Caused by mergeMap/concatMap where you wanted switchMap (cancels in-flight). tap(v => console.log(Date.now(), v)) reveals the ordering.

Bug 3: error kills the stream

An uncaught error completes the Observable — later emissions never arrive (a search that 404s stops forever). Fix: switchMap(() => api.search().pipe(catchError(() => of([])))) — recover the inner stream without killing the outer.

Debug workflow:1) tap(v => console.log('A', v)) at the source; 2) another after the first operator; 3) keep adding downstream until values stop — that's the broken operator. For leaks: Chrome DevTools → Memory → heap snapshots before/after navigation; lingering subscription objects mean you didn't unsubscribe.

1. The one-line debugger: tap

this.search$.pipe(
  tap(q => console.log('1 input ', q)),
  debounceTime(300),
  tap(q => console.log('2 debounced', q)),
  switchMap(q => this.api.search(q).pipe(
     tap(r => console.log('3 result  ', r)))),
)

Drop a numbered tap between each operator and watch the console: the last number that logs is where the stream stops. Did nothing log at all? Nothing subscribed. Logs once per click but you expected one stream? Cold-observable re-subscription.

3. The flattening operator is a top bug source

OperatorInner streamsUse for
switchMapcancels the previous when a new one arrivessearch / type-ahead / navigation (only the latest matters)
mergeMapruns all concurrently, keeps every resultindependent parallel work (⚠ races on search)
concatMapqueues, one at a time, in orderordered writes (e.g. sequential saves)
exhaustMapignores new while one is in flightsubmit buttons (drop double-clicks)

"Old result clobbers new" on a search box is almost always mergeMap where you wanted switchMap. "Double submit" is mergeMap where you wanted exhaustMap.

4. Cold vs hot, and cleaning up

  • Cold = per-subscriber. An HttpClient call is cold — every subscribe re-runs the request. Three async pipes on the same observable = three HTTP calls. Multicast with shareReplay({ bufferSize: 1, refCount: true }).
  • Prefer the async pipe in templates — it subscribes and (crucially) unsubscribes for you, killing most leaks.
  • Manual subscribes must be cleaned up — takeUntilDestroyed() (inject context) or unsubscribe in ngOnDestroy. A leaked subscribe keeps firing — and keeps the component in memory.
  • Errors are terminal. An unhandled error completes the stream; place catchError inside the switchMap so a failed request doesn't kill the outer search stream.

5. One-sentence recap

🔌 Debug an RxJS stream by dropping numbered tap()s between operators (the last one that logs is where it stops), then map the symptom to its usual cause: no emissions = nothing subscribed (use the async pipe), duplicate calls = cold re-subscription (shareReplay), stale race = mergeMap where you needed switchMap, leak = an unmanaged subscribe (takeUntilDestroyed/async pipe), and dies on error = missing catchError (put it inside the inner map).
