package.json

package.json Anatomy

Every field in a typical full-stack project's package.json. Hover a line in VS Code and the TypeScript language server gives you inline docs — but this page explains the why.

// package.json — Angular + Node full-stack project
{
  /* ── Identity ─────────────────────────────────────── */
  "name": "my-app",              // npm registry id; lowercase, no spaces
  "version": "1.0.0",           // MAJOR.MINOR.PATCH (SemVer)
  "description": "...",         // shown on npmjs.com search results
  "author": "Your Name <you@example.com>",
  "license": "MIT",
  "private": true,              // prevents accidental `npm publish`
  "repository": {
    "type": "git",
    "url": "https://github.com/you/my-app.git"
  },

  /* ── Scripts ──────────────────────────────────────── */
  "scripts": {
    "start":   "ng serve",           // `npm start` (shorthand — no "run")
    "build":   "ng build",
    "test":    "ng test",
    "lint":    "ng lint",
    "prebuild":"npm run lint",      // `pre` prefix runs BEFORE `build`
    "e2e":     "playwright test"
  },

  /* ── Runtime dependencies (shipped to users) ─────── */
  "dependencies": {
    "@angular/core":    "^17.3.0",  // ^ = compatible minor/patch updates
    "@angular/common":  "^17.3.0",
    "rxjs":             "~7.8.0",   // ~ = patch updates only
    "tslib":            "^2.6.2",
    "zone.js":          "~0.14.4"
  },

  /* ── Dev dependencies (build toolchain, not shipped) */
  "devDependencies": {
    "@angular/cli":         "^17.3.0",
    "@angular-devkit/build-angular": "^17.3.0",
    "typescript":           "~5.4.2",
    "jest":                 "^29.7.0",
    "@types/node":          "^20.0.0"
  },

  /* ── Peer dependencies (library authors only) ─────── */
  "peerDependencies": {
    "@angular/core": ">=16.0.0 <18.0.0"
    // Tells consumers: "I need Angular, bring your own"
  },

  /* ── Engine requirements ─────────────────────────── */
  "engines": {
    "node": ">=20.0.0",          // warns (or errors with engineStrict) if mismatch
    "npm":  ">=10.0.0"
  },

  /* ── Package type (ESM vs CommonJS) ──────────────── */
  "type": "module",              // "module"=ESM, "commonjs"=CJS (default)

  /* ── Angular workspace config pointer ────────────── */
  "browserslist": [
    "last 2 Chrome versions",
    "last 2 Firefox versions",
    "last 2 Edge versions"
  ]
}

Field quick-reference

FieldPurpose
nameRegistry identifier — npm install <name>
versionSemVer string; bumped with npm version patch/minor/major
privateBlocks npm publish — always set for app repos
mainCJS entry point (Node.js require)
moduleESM entry point (bundlers use this)
exportsModern conditional entry points (overrides main/module)
filesAllowlist of files included in the published package
enginesNode/npm version requirements
type"module" or "commonjs" — how .js files are interpreted
browserslistTarget browsers — shared with Babel/PostCSS/esbuild

Dependency types

FieldInstalled when…Shipped?
dependenciesAlways (npm install)yes
devDependenciesLocal dev only; skipped with --productionno
peerDependenciesMust be installed by consumer; npm 7+ auto-installsconsumer
optionalDependenciesInstall attempted; failure is not fatalmaybe
bundledDependenciesPacked into .tgz on publish; rarely usedpacked

Rule of thumb: test frameworks, linters, type declarations → devDependencies. Anything your users' code imports at runtime → dependencies.

npm Scripts

The scripts object is a tiny task runner built into npm. Run any script with npm run <name> (or npm start / npm test for the two special names).

Lifecycle hooks — pre & post

npm automatically runs pre<script> before and post<script> after any named script. Ordering is guaranteed.

"scripts": {
  // Runs in order: prelint → lint → postlint
  "prelint":  "echo 'Checking code...'",
  "lint":     "eslint src --ext .ts",
  "postlint": "echo 'Done'",

  // Runs in order: prebuild → build → postbuild
  "prebuild": "npm run lint && npm run test -- --watchAll=false",
  "build":    "ng build --configuration production",
  "postbuild":"node scripts/copy-assets.js"
}

Common Angular project scripts

start
ng serve
Dev server with HMR on localhost:4200. Run with npm start.
build
ng build --configuration production
Production build with tree-shaking, minification, and AOT compilation into dist/.
test
ng test
Runs Karma/Jest unit tests. Run with npm test.
lint
ng lint
ESLint over your TypeScript source. Angular CLI configures ESLint via @angular-eslint.
e2e
playwright test
End-to-end tests. Playwright is the modern choice over Protractor (deprecated Angular v13).
analyze
ng build --stats-json && webpack-bundle-analyzer dist/my-app/browser/stats.json
Generate a visual bundle analysis to find large dependencies. Requires webpack-bundle-analyzer dev dep.

Passing arguments to scripts

# Pass extra args after -- (double dash)
npm run test -- --watchAll=false --coverage
npm run build -- --configuration staging

# Compose scripts with && (sequential) or || (fallback)
"build:all": "npm run build:client && npm run build:server"

# Run in parallel — use a cross-platform tool like concurrently
"dev": "concurrently \"ng serve\" \"node server.js\""

Environment variables in scripts

# Works on Mac/Linux — not Windows CMD
"start:staging": "NODE_ENV=staging ng serve"

# Cross-platform: use cross-env package
"start:staging": "cross-env NODE_ENV=staging ng serve"

# Angular uses fileReplacements in angular.json, not NODE_ENV
# See the angular.json visualizer for environment switching

devDependencies vs dependencies — the decision rule

→ dependencies

  • Packages your app imports at runtime
  • @angular/core, rxjs, tslib
  • Any utility the built JS bundle references
  • Server-side packages (Express, Fastify)

→ devDependencies

  • Tools used only during development / CI
  • @angular/cli, typescript, jest
  • ESLint, Prettier, Husky (git hooks)
  • @types/* — type declarations
  • Webpack, Vite — bundlers the user never sees

peerDependencies — for library authors

// In a library like @my-org/ui-kit:
"peerDependencies": {
  "@angular/core": ">=17.0.0 <20.0.0",
  "@angular/common": ">=17.0.0 <20.0.0"
},
"peerDependenciesMeta": {
  "@angular/animations": { "optional": true }  // mark optional peers
}

The peer says: "I need Angular in the host app — I won't bundle my own copy." npm 7+ auto-installs peers unless there's a conflict. npm 6 and earlier only warned.

Checking for outdated / vulnerable packages

# See which packages have newer versions
npm outdated

# Audit for known security vulnerabilities
npm audit
npm audit fix           # auto-fix safe patches
npm audit fix --force   # unsafe — may break API

# Update all to latest allowed by SemVer range in package.json
npm update

# Upgrade beyond your range (use a tool)
npx npm-check-updates -u   # rewrites package.json ranges
npm install                # then install

SemVer — Semantic Versioning

Every npm version string follows MAJOR.MINOR.PATCH[-prerelease][+build]. The range prefixes in package.json control which future versions npm will install.

The three parts

1.4.2-beta.1
↑ ↑ ↑  └── pre-release label (optional)
│ │ └──── PATCH — bug fixes, no API change
│ └────── MINOR — new backward-compatible features
└──────── MAJOR — breaking changes

Range syntax — what each prefix installs

Installed package is currently 1.4.2. The range in package.json allows:

^1.4.2caret → ≥1.4.2 <2.0.0 (MINOR+PATCH ok)
1.4.21.4.91.5.01.9.92.0.00.9.0
~1.4.2tilde → ≥1.4.2 <1.5.0 (PATCH only)
1.4.21.4.91.5.02.0.0
1.4.2exact pin → only this version
1.4.21.4.31.5.0
>=1.4.0range → any ≥ 1.4.0
1.4.01.5.02.0.01.3.9
*wildcard → any version (dangerous)
1.4.22.0.0100.0.0
1.xx-range → ≥1.0.0 <2.0.0
1.0.01.9.92.0.0

Pre-release versions

"rxjs": "^8.0.0-alpha.1"   // only if exact alpha or higher alpha
"rxjs": "^8.0.0"            // pre-releases excluded by default

# Install a specific tag
npm install rxjs@next     // latest with "next" dist-tag
npm install rxjs@beta
npm install rxjs@latest   // default; stable only

Version bumping with npm version

# Bump version + create git tag automatically
npm version patch   // 1.4.2 → 1.4.3
npm version minor   // 1.4.2 → 1.5.0
npm version major   // 1.4.2 → 2.0.0
npm version prerelease --preid=beta  // 1.4.2 → 1.4.3-beta.0

package-lock.json & npm ci

The lockfile records the exact resolved version of every installed package (and every package those packages depend on). It's the reproducibility guarantee.

package-lock.json structure

{
  "name": "my-app",
  "version": "1.0.0",
  "lockfileVersion": 3,   // v3 since npm 7
  "requires": true,
  "packages": {
    "": {                    // root (your project)
      "name": "my-app",
      "version": "1.0.0",
      "dependencies": { "rxjs": "~7.8.0" },
      "devDependencies": { "typescript": "~5.4.0" }
    },
    "node_modules/rxjs": {
      "version": "7.8.1",      // EXACT resolved version
      "resolved": "https://registry.npmjs.org/rxjs/-/rxjs-7.8.1.tgz",
      "integrity": "sha512-...", // SHA-512 hash — tamper detection
      "dependencies": {
        "tslib": "^2.1.0"
      }
    }
  }
}

npm install vs npm ci — when to use which

npm install

  • Reads package.json ranges
  • Updates lockfile if needed
  • Can install newer compatible versions
  • Merges with existing node_modules
  • Use: local development

npm ci

  • Reads package-lock.json exactly
  • Never modifies the lockfile
  • Deletes node_modules first (clean install)
  • Fails if lockfile is out of sync
  • Use: CI / CD pipelines, Docker builds

Commit the lockfile — always

# ✓ Add to git — ensures reproducible installs for the whole team
git add package-lock.json

# Never add node_modules to git
echo "node_modules/" >> .gitignore

Why integrity hashes matter

Each entry has a sha512-... integrity field. When npm ci downloads a package it verifies the hash against what's in the lockfile — catching supply-chain attacks where a registry package is swapped after the lockfile was committed.

yarn.lock / pnpm-lock.yaml

Yarn and pnpm use their own lockfile formats, but the concept is identical:
  - yarn.lock          (Yarn 1, Yarn Berry)
  - pnpm-lock.yaml     (pnpm — hard links node_modules, saves disk)
  - bun.lockb          (Bun — binary format)

Never mix package managers in one project — delete and reinstall if switching.

ESM, CommonJS & the exports field

Modern JavaScript has two module systems that coexist awkwardly. Understanding these fields prevents the dreaded "require() of ES Module" error.

CJS vs ESM at a glance

CommonJS (CJS)

const fs = require('fs')
module.exports = { myFn }
  • Node.js default (no "type" field)
  • Synchronous — cannot top-level await
  • Files: .js, .cjs
  • Dynamic: require(variable) works

ESM (ECMAScript Modules)

import fs from 'fs'
export { myFn }
  • Enabled with "type": "module"
  • Supports top-level await
  • Files: .js, .mjs
  • Static — imports resolved at parse time

The exports field — modern dual-package

"exports": {
  ".": {                        // main export (import 'my-lib')
    "import": "./dist/esm/index.js",  // ESM consumers
    "require": "./dist/cjs/index.js", // CJS consumers
    "types": "./dist/index.d.ts"       // TypeScript
  },
  "./utils": {                  // sub-path export (import 'my-lib/utils')
    "import": "./dist/esm/utils.js",
    "require": "./dist/cjs/utils.js"
  }
}

// "exports" takes priority over "main" / "module" in Node 12+ and bundlers
// Keep "main" and "module" for older toolchains as fallback:
"main":   "./dist/cjs/index.js",
"module": "./dist/esm/index.js",
"types":  "./dist/index.d.ts"

Angular apps don't need exports — libraries do

// Angular app → "type": "commonjs" or omit (Angular CLI handles ESM internally)
// Angular library (ng-packagr) → ng-packagr sets exports automatically

// To publish an Angular library:
ng generate library my-lib
ng build my-lib --configuration production
cd dist/my-lib
npm publish

.mjsESM regardless of "type"
