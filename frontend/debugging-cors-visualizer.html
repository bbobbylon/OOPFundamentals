Debugging CORS Failures

A CORS error feels like the server rejected you — but it didn't. CORS is enforced by the browser: the server usually answered fine, and the browser threw the response away because a header didn't authorize your origin to read it. That one fact ("works in curl/Postman, fails in the browser") is the key to debugging every CORS error fast.

What is CORS — and why does the "works in Postman, fails in browser" pattern happen?

CORS (Cross-Origin Resource Sharing) is a browser security mechanism that restricts JavaScript from making HTTP requests to a different origin than the page it's running on. Origin = protocol + hostname + port. https://app.mycompany.com is a different origin from https://api.mycompany.com (different hostname). http://localhost:4200 is different from http://localhost:8080 (different port). When your Angular app at http://localhost:4200 makes an HttpClient.get('http://localhost:8080/api/users') call, the browser intercepts it — "this is a cross-origin request." The browser's CORS mechanism: first sends a preflight request (HTTP OPTIONS to the server, with Origin, Access-Control-Request-Method, Access-Control-Request-Headers headers). If the server responds with the right CORS headers (Access-Control-Allow-Origin: http://localhost:4200, Access-Control-Allow-Methods: GET,POST,PUT,DELETE), the browser proceeds with the actual request. If not — browser blocks the response and shows the CORS error in the console. Why Postman works: Postman is NOT a browser. It doesn't enforce CORS. It sends the request directly and shows the response. Same with curl. The CORS check is entirely browser-side. The server doesn't even know a CORS error occurred — it returned a normal response, the browser discarded it. Spring Boot CORS config: add @CrossOrigin on a controller (simple, per-endpoint) or configure global CORS in SecurityFilterChain (correct for Spring Security apps). The critical rule: CORS config MUST come before Spring Security's authentication filter — configure it via http.cors() and a CorsConfigurationSource bean. Credentials (cookies + auth headers): if your Angular app sends withCredentials: true, the server must respond with Access-Control-Allow-Credentials: true AND Access-Control-Allow-Origin must be the EXACT origin (not * — wildcards don't work with credentials).

Spring Boot CORS config

// Spring Security + CORS (correct approach): @Bean CorsConfigurationSource corsConfigSource() { CorsConfiguration config = new CorsConfiguration(); config.setAllowedOrigins(List.of( "http://localhost:4200", // local dev "https://app.mycompany.com" // production )); config.setAllowedMethods(List.of("GET","POST","PUT","DELETE","OPTIONS")); config.setAllowedHeaders(List.of("Authorization","Content-Type","X-Request-ID")); config.setAllowCredentials(true); // for cookies/auth config.setMaxAge(3600L); // preflight cache UrlBasedCorsConfigurationSource source = new UrlBasedCorsConfigurationSource(); source.registerCorsConfiguration("/**", config); return source; } @Bean SecurityFilterChain chain(HttpSecurity http) { return http .cors(cors -> cors.configurationSource(corsConfigSource())) .csrf(csrf -> csrf.disable()) // for REST APIs .oauth2ResourceServer(...) .build(); }

CIAM CORS debugging: Angular CIAM app at https://app.mycompany.com calling Spring Boot at https://api.mycompany.com — cross-origin. CORS must be configured on Spring Boot. The most common CIAM CORS mistake: adding @CrossOrigin on controllers BUT having Spring Security reject the preflight OPTIONS request before the controller even sees it (401 on OPTIONS because no auth header). Fix: configure CORS in SecurityFilterChain with http.cors() which adds a CORS filter BEFORE the auth filter. The second most common mistake: Access-Control-Allow-Origin: * (wildcard) but Angular sends withCredentials: true — browsers block this combination. Fix: use exact origin: config.setAllowedOrigins(List.of("https://app.mycompany.com")). Ping redirect CORS: when Ping redirects to https://app.mycompany.com/callback after login, the redirect itself isn't a CORS request (it's a browser navigation). But if the callback page makes an API call to Spring Boot to exchange the code — that IS CORS. Ensure the Spring Boot /oauth2/code/exchange endpoint has CORS configured.

1. First, reframe what you're seeing

  • It's a browser policy, not an auth failure. A CORS error is not a 401/403. The request may have returned 200 server-side; the browser blocked your JS from reading it.
  • curl/Postman ignore CORS. If it works there but fails in the browser, it's almost always CORS — those tools don't enforce the same-origin policy.
  • Look for the OPTIONS first. Non-simple requests send a preflight OPTIONS before the real call. Half of CORS bugs are the preflight failing, not the actual request.

3. The debugging workflow

  • 1. Open the Network tab and find the OPTIONS row (filter by the path). Is it there? What status? Does its response carry Access-Control-Allow-Origin?
  • 2. Reproduce the preflight from the CLI and read the headers directly:
# does the server echo your origin on the preflight?
curl -i -X OPTIONS https://your-api/api/auth/login \
  -H "Origin: https://yourname.github.io" \
  -H "Access-Control-Request-Method: POST"
  • 3. Compare the Origin byte-for-byte with the allow-list — scheme, host, and no trailing slash.

4. Where this app decides CORS

// SecurityConfig — the allow-list + the OPTIONS escape hatch
config.setAllowedOrigins(allowedOrigins);          // from CORS_ALLOWED_ORIGINS
config.setAllowedMethods(List.of("GET","POST","PUT","DELETE","OPTIONS"));
config.setAllowCredentials(true);                 // ⇒ origins must be explicit, never '*'

http.authorizeHttpRequests(a -> a
   .requestMatchers(HttpMethod.OPTIONS, "/**").permitAll()  // preflights pass
   …);

So in this codebase a CORS fix is almost always: add the origin to CORS_ALLOWED_ORIGINS (exact match), and make sure OPTIONS is permitAll so the preflight isn't eaten by the auth filter.

5. Traps

  • Chasing a 401 that's really CORS. If the preflight 401s, the browser reports a CORS error, not an auth error. Fix the OPTIONS handling, not your token.
  • * + credentials is illegal. With allowCredentials(true) you must echo a specific origin; the wildcard is rejected by the browser.
  • Trailing slash / scheme. https://app.io/ ≠ https://app.io, and http ≠ https. Exact match only.
  • Stale preflight cache. Browsers cache preflights (Access-Control-Max-Age); hard-reload or wait it out after a config change.

6. One-sentence recap

🌐 A CORS error is the browser refusing to let your JS read a response (not the server rejecting you) — so debug it by finding the OPTIONS preflight in the Network tab (or reproducing it with curl -X OPTIONS), checking whether the response carries an Access-Control-Allow-Origin that exactly matches your origin, confirming the preflight isn't 401/403'd by auth, and never pairing * with credentials — in this app that's the CORS_ALLOWED_ORIGINS list plus permitAll on OPTIONS.
