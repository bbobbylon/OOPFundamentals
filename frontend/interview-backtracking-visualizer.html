Backtracking & Recursion — Subsets, Permutations & Tree Search

The universal pattern: make a choice, recurse, undo. Mastering this unlocks Subsets, Permutations, Combinations, N-Queens, Word Search, and Sudoku.

🧩 What is backtracking — and how does "make a choice, recurse, undo the choice" solve combinatorial problems that seem impossibly complex?

Backtracking is a recursive problem-solving technique for finding all (or the best) solutions to a problem by incrementally building candidates and abandoning ("backtracking") a candidate as soon as it's determined that the candidate cannot lead to a valid solution. It's the systematic exploration of all possibilities with pruning. The universal backtracking template: (1) If we've reached a valid complete solution, add it to results. (2) Otherwise, for each available choice at the current decision point: make the choice (modify state), recurse (explore all solutions that start with this choice), undo the choice (restore state to what it was before). The "undo" step is what makes backtracking possible — by restoring state after each choice, we can explore sibling branches cleanly. When to use backtracking: when the problem asks you to find ALL valid combinations/permutations/subsets; when no greedy or DP approach applies; when the brute force decision tree has clear pruning opportunities (you can tell early that a partial solution can't lead to a valid complete solution). Subsets: for each element, make a binary choice: include or exclude. Result: 2ⁿ subsets. At each recursion level, either include arr[i] (add to current set) or skip it. Permutations: for n items, there are n! orderings. Use a "used" boolean array — at each position, pick any unused element, mark it used, recurse, unmark. Combinations: like permutations but order doesn't matter. Use a start index to avoid revisiting elements already used earlier in the path. N-Queens: place N queens on an N×N board so none attack each other. For each row, try placing a queen in each column — if no existing queen attacks this position (check column, diagonal, anti-diagonal with O(1) hash sets), place and recurse to the next row. If placement fails for all columns, backtrack. Pruning: the key to making backtracking practical. Skip invalid choices early: if remaining sum < 0 in a subset-sum problem, prune. If a queen attacks another queen, skip that column. Good pruning can reduce exponential time to manageable for the input sizes seen in interviews.

Universal backtracking template

// Universal backtracking: make-recurse-undo void backtrack(List<List<Integer>> result, List<Integer> current, int[] nums, int start) { result.add(new ArrayList<>(current)); // ADD TO RESULT // (for combinations/subsets: add current state as a valid result) // (for permutations/N-queens: only add when current is complete) for (int i = start; i < nums.length; i++) { // PRUNING: skip if this choice can't lead to valid solution // e.g., if (nums[i] > remaining) break; (if sorted) current.add(nums[i]); // MAKE CHOICE backtrack(result, current, nums, i + 1); // RECURSE current.remove(current.size()-1); // UNDO CHOICE (backtrack!) } } // Call: backtrack(result, new ArrayList<>(), nums, 0); // The "current.remove()" is THE backtracking step // Without it, state bleeds between branches → wrong answers

Permutations

// Permutations of [1,2,3]: [1,2,3],[1,3,2],[2,1,3],... // n! total — O(n! * n) time void permute(int[] nums, boolean[] used, List<Integer> current, List<List<Integer>> result) { if (current.size() == nums.length) { // COMPLETE permutation result.add(new ArrayList<>(current)); return; } for (int i = 0; i < nums.length; i++) { if (used[i]) continue; // skip already-used elements used[i] = true; // MARK as used current.add(nums[i]); // MAKE CHOICE permute(nums, used, current, result); // RECURSE current.remove(current.size()-1); // UNDO used[i] = false; // UNMARK } } // Alternative: swap-based permutations (in-place, less intuitive) // Swap nums[start] with nums[i], recurse(start+1), swap back

N-Queens (pruning)

// N-Queens: place n queens so none attack each other // Pruning: use O(1) sets for column/diagonal tracking int solutions = 0; Set<Integer> cols=new HashSet<>(); Set<Integer> diag=new HashSet<>(); // row-col is constant on \ diagonal Set<Integer> antiDiag=new HashSet<>(); // row+col is constant on / diagonal void solveNQueens(int row, int n) { if (row == n) { solutions++; return; } // all queens placed for (int col = 0; col < n; col++) { int d = row - col; int ad = row + col; if (cols.contains(col) || diag.contains(d) || antiDiag.contains(ad)) continue; // PRUNE: queen attacks ← skip this column cols.add(col); diag.add(d); antiDiag.add(ad); // PLACE queen solveNQueens(row + 1, n); // RECURSE: next row cols.remove(col); diag.remove(d); antiDiag.remove(ad); // UNDO } }

Interview / Context: Backtracking problems are some of the most challenging in technical interviews because candidates try to solve them analytically instead of mechanically applying the template. The correct approach: recognize the problem as backtracking (find all valid X, or explore all combinations), write the universal template, identify the base case (what makes a solution complete?), identify what choices are available at each step, and identify the pruning condition. In CIAM context, backtracking reasoning appears in policy evaluation — "find all valid permission combinations that satisfy this access request" — and in test generation for auth flow coverage (generate all valid journey path combinations through a Ping AM tree of N nodes).

The problem

"Visited" is two different ideas wearing one word, and the DFS skeleton above cannot tell you which one you meant.

Word Search restores the cell. Number of Islands must not. Same code.

Pattern 5 further down this page — grid search — does exactly this: mark the cell '#', recurse into the four neighbours, then board[r][c] = temp to restore it. That restore is essential. If a path through this cell fails, the cell has to become available again, because a different path may legitimately need it. Leave it marked and you get false negatives: the word is in the grid and exist returns false.

Now write Number of Islands. Scan every cell; when you find unvisited land, increment the count and flood-fill the whole island as visited. The recursion is the same four-direction DFS, so the instinct is to reuse the template — restore included. Restore it and every single land cell is counted as its own island, because the outer scan reaches the next cell and finds it unvisited again. A 3×3 block of land reports 9 islands. No exception, no infinite loop, just a number that is wrong in a way that looks like an off-by-something.

Neither version is a bug in the DFS. The two problems need opposite answers to a question the code never asks out loud: is "visited" a property of the current path, which must be undone when the path is abandoned, or a property of the whole search, which must never be undone? The template in the card above answers the first. Flood fill needs the second, and the difference is one line that reads like boilerplate.

the DFS traversal is correct ✓ bounds checks are correct ✓ the marking is correct ✓ the unmarking is copied from a different problem ⚠ every cell becomes its own island ⚠

Backtracking undoes choices. Flood fill does not make choices — it makes a claim, and claims do not get taken back.

Say which "visited" you mean, in the code
Searching for a path (Word Search, N-Queens, rat-in-a-maze): visited is per-path — mark on the way in, restore on the way out ↓ a cell rejected by one path has to be offered to the next, because the thing you are enumerating is paths, and two paths may share a cell Partitioning or covering the grid (Number of Islands, flood fill, region colouring): visited is global — mark once and never restore ↓ there is no branching to undo; every cell belongs to exactly one region, and the whole point is that the second visit must not happen And name the variable after which one it is: onPath versus seen ↓ visited is the word that hides the distinction, and a reviewer cannot check a restore line against an intention nobody wrote down
Backtracking's "undo" is not a cleanup step — it is the statement that the choice was tentative. Undo something that was never a choice and you have unmade a fact. That is the whole distinction: in Word Search, using a cell is a bet on one path among many; in flood fill, marking a cell says "this cell has been accounted for", which is true forever. Both are called visited, both are a boolean in a grid, and only one of them is reversible.
Undo means "I might not have meant that". In flood fill you did mean it, permanently — so the restore line is not a safety measure, it is a retraction of something true.
You

It's the same four-direction DFS on the same grid. Why would the visited handling differ?

Word Search

Because I am enumerating paths, and a cell can be on many of them. When a path through a cell fails, that cell is innocent — the failure was about the path, not the cell. If I do not restore it, I have punished every future path for one dead end.

Number of Islands

And I am partitioning the grid. Every land cell belongs to exactly one island, and once I have assigned it, that is settled. There is nothing tentative to undo, so a restore does not "clean up" after me — it deletes the only record that I was ever there.

Cycle detection in a directed graph

Worth adding that I need both at once, which is why I get taught with three colours. White is unvisited, grey is on the current path, black is finished. An edge to grey is a cycle; an edge to black is just a re-encounter. Collapse grey and black into one visited set and I either miss cycles or invent them.

The mechanism

Six steps on a 2×2 grid of all land, counted with the restore line left in.

  1. The outer scan reaches (0,0), finds land, and increments the count to 1correct so far
  2. The flood fill marks (0,0), then (0,1), (1,1), (1,0) — the whole island, correctly identifiedthe traversal works
  3. Each call returns, and on the way out each one restores its cell to land — the template's last linethe copied line
  4. The fill finishes having marked everything and then unmarked everything. The grid is byte-for-byte what it wasas if nothing happened
  5. The outer scan moves to (0,1), finds land and no mark, and increments the count to 2the same island, again
  6. Four cells, four islands. The answer should be 1, and the code has done a great deal of correct work to produce 4no error, just wrong

Step 4 is the one to hold onto, because it describes a whole family of bugs: an operation that does its work and then perfectly erases the evidence of having done it. Nothing you can inspect afterwards shows what went wrong — dump the grid at the end and it is pristine, which looks like the algorithm never ran rather than like it ran and undid itself. When state is both created and destroyed inside one call, a debugger at the boundaries sees nothing; you have to log inside the recursion, or reason about it, and reasoning is what the two names onPath and seen would have made easy.

the restore line on the way outboard[r][c] = temp; — keep it, or delete it?
depends entirely on what you are enumerating →
Word Search — keep it: paths share cells, and a failed path must not consume the grid Number of Islands / flood fill — delete it: each cell belongs to one region, decided once Shortest path in a grid (BFS) — delete it: the first time you reach a cell is already the shortest way there Counting all paths from corner to corner — keep it: you are enumerating paths again, not covering cells

Read the four rows by what they enumerate rather than by what they look like, and the rule falls out with no memorisation: enumerate paths and visited is per-path; cover or partition cells and visited is global. The BFS row is worth a second look, because it is global for a slightly different reason — not "each cell belongs to one region" but "the first arrival is optimal, so any later one is redundant". That is the same argument Dijkstra makes when it finalises a node, and it is why adding a restore line to a shortest-path search does not merely slow it down; it re-opens nodes whose answers were already settled.

You reuse the Word Search DFS from Pattern 5 — including the board[r][c] = temp restore on the way out — to count islands in a 2×2 grid where all four cells are land. What does it return?

The fill really does reach all four cells in the first pass — that part works perfectly. The problem is what the grid looks like afterwards: restored to its original state, so the outer scan has no way to know those cells were already accounted for, and it counts each of them again.

A cell is restored only after its own recursion has fully returned, so while the DFS is inside a cell's subtree that cell is still marked — stepping back into it is blocked. The recursion terminates normally, which is exactly why this is hard to notice: there is no hang and no stack overflow, just a wrong number.

Correct. Delete the restore line for flood fill: marking a cell there is a permanent statement that it has been accounted for, not a tentative choice. Keep it for Word Search, where a cell rejected by one path must stay available to the next.

Where you have seen this before

Every search has to distinguish "I am currently trying this" from "this is settled".

Memoization on a backtracking function

Caching results by position is valid only if the answer depends on nothing but that position. Cache a Word Search subcall keyed on (r, c, idx) and you will return an answer computed while a different set of cells was marked — the cached value was never a property of the key alone. Same distinction: settled versus currently-being-tried.

cache only what the key fully determines

A transaction versus a committed write

Uncommitted changes are per-transaction and get rolled back; committed ones are global and do not. Reading another transaction's uncommitted state is called a dirty read precisely because it treats a tentative fact as a settled one — the database version of unmarking at the wrong time.

tentative until commit, then not

Idempotency keys on a retried request

A retry needs to know whether the previous attempt settled anything. Without a durable record the retry re-does the work; with one that is cleared too eagerly, it re-does it anyway. Any "have I done this already?" flag has a scope, and getting the scope wrong is not a bug in the flag.

the flag's scope is the design
The whole page on a napkin: one template — choose, recurse, undo — covers subsets, permutations, combinations, string partitioning and grid search; snapshot the path when you record a solution, skip duplicate siblings with i > start on sorted input, and prune early. The sentence worth adding: the undo line belongs to per-path state only — keep it when you are enumerating paths, delete it when you are covering cells, and name the variable onPath or seen so the choice is visible.

The Universal Backtracking Template

// The pattern that solves ~20 common interview problems List<List<Integer>> results = new ArrayList<>(); void backtrack(List<Integer> current, int start) { // ── 1. BASE CASE (leaf of decision tree) if (isSolution(current)) { results.add(new ArrayList<>(current)); // snapshot! return; // or continue for more solutions } // ── 2. ITERATE over choices for (int i = start; i < choices.length; i++) { // ── 3. PRUNE bad choices early if (invalid(i)) continue; // ── 4. MAKE the choice current.add(choices[i]); // ── 5. RECURSE with updated state backtrack(current, i + 1); // or i for reuse // ── 6. UNDO the choice (BACKTRACK!) current.remove(current.size() - 1); // This is the "undo" that makes it backtracking } }

The Key Insight

Why "undo"? Because we explore the decision tree depth-first. After exploring one branch fully, we remove our last choice and try the next option at this level.

Without the undo step, current keeps accumulating — it's just recursion, not backtracking.

Mental model: Imagine walking a maze. You mark your path. When you hit a dead end, you erase your marks as you backtrack.
Common bug: results.add(current) — you're adding the reference! As backtracking undoes choices, the list empties. Always new ArrayList<>(current) to snapshot.

When to Use Backtracking

Pattern Recognition

Problem asks for all solutions / combinations / permutations
Exponential search space (2^n or n!)
"Generate all..." or "Find all valid..."
Constraint satisfaction (N-Queens, Sudoku)

Complexity

Subsets: O(2^n) solutions
Permutations: O(n!) solutions
Combinations(n,k): O(C(n,k))
Pruning dramatically reduces actual work

vs Recursion

Pure recursion: find ONE answer, no undo
Backtracking: find ALL answers, undo choices
Memoization (DP): cache subproblems

Pattern 1 — Subsets (Power Set) 2^n solutions

Iterative approach (cleaner)

// nums=[1,2,3] → 8 subsets public List<List<Integer>> subsets(int[] nums) { List<List<Integer>> res = new ArrayList<>(); res.add(new ArrayList<>()); // always include empty set for (int num : nums) { int size = res.size(); for (int i = 0; i < size; i++) { List<Integer> sub = new ArrayList<>(res.get(i)); sub.add(num); // add num to every existing subset res.add(sub); } } return res; // Each element: include or exclude → doubles the set }
// Backtracking approach (matches template exactly) public List<List<Integer>> subsets(int[] nums) { List<List<Integer>> res = new ArrayList<>(); backtrack(nums, 0, new ArrayList<>(), res); return res; } void backtrack(int[] nums, int start, List<Integer> cur, List<List<Integer>> res) { res.add(new ArrayList<>(cur)); // add at every node! for (int i = start; i < nums.length; i++) { cur.add(nums[i]); // include backtrack(nums, i+1, cur, res); // recurse cur.remove(cur.size()-1); // exclude (undo) } }

Subsets II — With Duplicates

// nums=[1,2,2] → no duplicate subsets void backtrack(int[] nums, int start, List<Integer> cur, List<List<Integer>> res) { res.add(new ArrayList<>(cur)); for (int i = start; i < nums.length; i++) { // Skip duplicate SIBLINGS (not children) // i > start: only skip at same level of tree if (i > start && nums[i] == nums[i-1]) continue; cur.add(nums[i]); backtrack(nums, i+1, cur, res); cur.remove(cur.size()-1); } } // MUST sort array first: Arrays.sort(nums) // Duplicate skip: i>start (not i>0) is crucial! // i>0 would skip valid subsets that start mid-array
Critical distinction: i > start not i > 0 — we only skip duplicate elements at the same level (siblings in the decision tree), not when starting a fresh recursion.

Pattern 2 — Permutations n! solutions

Standard Template

// nums=[1,2,3] → 6 permutations public List<List<Integer>> permute(int[] nums) { List<List<Integer>> res = new ArrayList<>(); backtrack(nums, new boolean[nums.length], new ArrayList<>(), res); return res; } void backtrack(int[] nums, boolean[] used, List<Integer> cur, List<List<Integer>> res) { if (cur.size() == nums.length) { res.add(new ArrayList<>(cur)); return; } for (int i = 0; i < nums.length; i++) { if (used[i]) continue; // skip already used used[i] = true; cur.add(nums[i]); backtrack(nums, used, cur, res); cur.remove(cur.size()-1); used[i] = false; // undo! } }

Permutations II — With Duplicates

// nums=[1,1,2] → [1,1,2],[1,2,1],[2,1,1] void backtrack(int[] nums, boolean[] used, List<Integer> cur, List<List<Integer>> res) { if (cur.size() == nums.length) { res.add(new ArrayList<>(cur)); return; } for (int i = 0; i < nums.length; i++) { if (used[i]) continue; // Skip duplicate: same value as previous sibling // !used[i-1]: prev sibling was un-used (backtracked) if (i > 0 && nums[i] == nums[i-1] && !used[i-1]) continue; used[i] = true; cur.add(nums[i]); backtrack(nums, used, cur, res); cur.remove(cur.size()-1); used[i] = false; } } // Sort nums first! Arrays.sort(nums)
!used[i-1] means: the previous duplicate was already backtracked (un-used), so we're at the same position in the sibling sequence — skip to avoid duplicating results.

Pattern 3 — Combinations & Combination Sum Common

Combination Sum (unlimited use)

// candidates=[2,3,6,7], target=7 // → [[2,2,3],[7]] public List<List<Integer>> combinationSum( int[] candidates, int target) { Arrays.sort(candidates); // sort for early pruning List<List<Integer>> res = new ArrayList<>(); backtrack(candidates, target, 0, new ArrayList<>(), res); return res; } void backtrack(int[] c, int remain, int start, List<Integer> cur, List<List<Integer>> res) { if (remain == 0) { res.add(new ArrayList<>(cur)); return; } for (int i = start; i < c.length; i++) { if (c[i] > remain) break; // prune! sorted so all larger cur.add(c[i]); backtrack(c, remain-c[i], i, cur, res); // i not i+1 (reuse!) cur.remove(cur.size()-1); } }

Combination Sum II (one use, no dup results)

// candidates=[10,1,2,7,6,1,5], target=8 // → [[1,1,6],[1,2,5],[1,7],[2,6]] void backtrack(int[] c, int remain, int start, List<Integer> cur, List<List<Integer>> res) { if (remain == 0) { res.add(new ArrayList<>(cur)); return; } for (int i = start; i < c.length; i++) { if (c[i] > remain) break; // Skip duplicate siblings (not children) if (i > start && c[i] == c[i-1]) continue; cur.add(c[i]); backtrack(c, remain-c[i], i+1, cur, res); // i+1 (no reuse) cur.remove(cur.size()-1); } } // MUST sort: Arrays.sort(candidates)
Reuse vs no-reuse: Pass i to allow reuse (same element multiple times), pass i+1 to prevent reuse. The duplicate-skip line i > start && c[i] == c[i-1] prevents generating duplicate result sets.

Choose K from N — Combinations

// n=4, k=2 → [[1,2],[1,3],[1,4],[2,3],[2,4],[3,4]] public List<List<Integer>> combine(int n, int k) { List<List<Integer>> res = new ArrayList<>(); backtrack(n, k, 1, new ArrayList<>(), res); return res; } void backtrack(int n, int k, int start, List<Integer> cur, List<List<Integer>> res) { if (cur.size() == k) { res.add(new ArrayList<>(cur)); return; } // Pruning: need (k - cur.size()) more elements // Remaining elements from i to n = (n - i + 1) // Only proceed if (n - i + 1) >= k - cur.size() for (int i = start; i <= n - (k - cur.size()) + 1; i++) { cur.add(i); backtrack(n, k, i+1, cur, res); cur.remove(cur.size()-1); } } // Pruning formula: i <= n - (k - cur.size()) + 1 // Without pruning: i <= n. Pruning skips impossible branches.

Pattern 4 — String Building / Grammar Medium

Palindrome Partitioning

// s="aab" → [["a","a","b"],["aa","b"]] public List<List<String>> partition(String s) { List<List<String>> res = new ArrayList<>(); backtrack(s, 0, new ArrayList<>(), res); return res; } void backtrack(String s, int start, List<String> cur, List<List<String>> res) { if (start == s.length()) { res.add(new ArrayList<>(cur)); return; } for (int end = start + 1; end <= s.length(); end++) { String prefix = s.substring(start, end); if (!isPalindrome(prefix)) continue; // prune! cur.add(prefix); backtrack(s, end, cur, res); // recurse on suffix cur.remove(cur.size()-1); } } boolean isPalindrome(String s) { int l = 0, r = s.length()-1; while (l < r) if (s.charAt(l++) != s.charAt(r--)) return false; return true; }

Letter Case Permutation

// s="a1b2" → ["a1b2","a1B2","A1b2","A1B2"] public List<String> letterCasePermutation(String s) { List<String> res = new ArrayList<>(); backtrack(s.toCharArray(), 0, res); return res; } void backtrack(char[] chars, int i, List<String> res) { if (i == chars.length) { res.add(new String(chars)); return; } backtrack(chars, i+1, res); // keep as-is if (Character.isLetter(chars[i])) { // Toggle case and branch chars[i] ^= 32; // XOR 32 toggles case bit backtrack(chars, i+1, res); chars[i] ^= 32; // undo toggle } }
XOR 32 trick: ASCII uppercase letters have bit 5 = 0, lowercase have bit 5 = 1. XOR with 32 (bit 5) toggles the case. 'a' ^ 32 = 'A', 'A' ^ 32 = 'a'. Elegant and fast.

Pattern 5 — Grid Search (DFS + Backtrack) Medium–Hard

Word Search

// Find if word exists in grid public boolean exist(char[][] board, String word) { int rows = board.length, cols = board[0].length; for (int r = 0; r < rows; r++) for (int c = 0; c < cols; c++) if (dfs(board, word, r, c, 0)) return true; return false; } boolean dfs(char[][] board, String word, int r, int c, int idx) { if (idx == word.length()) return true; if (r < 0 || r >= board.length || c < 0 || c >= board[0].length) return false; if (board[r][c] != word.charAt(idx)) return false; if (board[r][c] == '#') return false; // already visited char temp = board[r][c]; board[r][c] = '#'; // mark visited IN-PLACE boolean found = dfs(board, word, r+1, c, idx+1) || dfs(board, word, r-1, c, idx+1) || dfs(board, word, r, c+1, idx+1) || dfs(board, word, r, c-1, idx+1); board[r][c] = temp; // UNMARK (backtrack!) return found; }

N-Queens

// Place N queens so none attack each other Set<Integer> cols = new HashSet<>(); Set<Integer> diag1 = new HashSet<>(); // (r-c) Set<Integer> diag2 = new HashSet<>(); // (r+c) void backtrack(int row, int n, int[] queens) { if (row == n) { addSolution(queens, n); return; } for (int col = 0; col < n; col++) { if (cols.contains(col) || diag1.contains(row-col) || diag2.contains(row+col)) continue; // conflict cols.add(col); diag1.add(row-col); diag2.add(row+col); queens[row] = col; backtrack(row+1, n, queens); cols.remove(col); diag1.remove(row-col); diag2.remove(row+col); } } // Key insight: r-c is constant on same "/" diagonal // r+c is constant on same "\" diagonal
