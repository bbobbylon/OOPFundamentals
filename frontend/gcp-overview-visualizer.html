GCP Overview — Projects, Resource Hierarchy & IAM

Every GCP resource lives inside a strict hierarchy — organization → folder → project → resource — and access is governed by Cloud IAM policy bindings that attach anywhere in that hierarchy and inherit downward, with APIs that must be explicitly enabled per project before you can use them.

☁️ What is the GCP resource model — and why does the project matter more than anything else?

GCP organizes everything into a hierarchy that is shallower and stranger than it looks at first glance. At the top, an Organization represents the company (tied to a Google Workspace or Cloud Identity domain). Below it, Folders are optional and nestable — teams use them to mirror business units or environments (folder/prod, folder/dev). The load-bearing unit is the Project: it is simultaneously the billing boundary, the API-enablement boundary, and the default IAM scope for most day-to-day work — and unlike Azure's resource group, a project has three separate identifiers (a human-readable name, a globally-unique Project ID you'll type constantly, and an immutable Project Number GCP assigns internally). Below the project sit the actual resources — a VM, a bucket, a Cloud SQL instance. Access is controlled by Cloud IAM: a policy is a set of bindings, each pairing a role (a bundle of permissions) with one or more members (principals), optionally narrowed by a condition (a CEL expression — time-bound, resource-attribute-based). Bindings attach at any level of the hierarchy and are inherited downward as a union: a role granted at the folder flows to every project and resource beneath it. Unlike AWS's Service Control Policies, IAM here has no explicit per-resource Deny — the closest analog, Organization Policies, is a separate constraint system layered on top. Finally, every resource type belongs to a Google API that must be explicitly enabled on a project before you can create anything of that type — try to create a Compute Engine VM in a fresh project and you'll hit SERVICE_DISABLED before you hit any IAM check at all.

  • Hierarchy — organization → folder (optional, nestable) → project (billing + IAM + API scope) → resource.
  • Three project identifiers — display name, globally-unique Project ID, immutable Project Number.
  • IAM bindings — {role, members[], optional CEL condition}, attach anywhere, inherit downward as a union.
  • No explicit Deny — only Organization Policy constraints restrict what an ancestor granted.
  • APIs are per-project and opt-in — gcloud services enable before a resource type can be created.

The CLI happy path

# login → get an identity token gcloud auth login # create the project, point the CLI at it gcloud projects create shop-prod-91a2 --name="Shop Prod" gcloud config set project shop-prod-91a2 # enable the API before using it gcloud services enable compute.googleapis.com

AWS & Azure comparison

Project ≈ an AWS account or an Azure subscription (billing boundary). Folder ≈ AWS Organizations OU ≈ Azure management group. GCP has no exact twin for Azure's resource group — a project already owns lifecycle and billing together, so there's no extra logical folder underneath it. IAM bindings-with-inheritance ≈ Azure RBAC role assignments at a scope; the big divergence from AWS is GCP's total lack of an explicit Deny statement — AWS SCPs have no real GCP equivalent, Organization Policies are the nearest cousin.

Spring Boot comparison

Cloud Resource Manager + IAM behaves like a REST backend's gateway: authenticate first (an identity token, exactly like your JwtDecoder), then authorize (IAM policy evaluation ≈ @PreAuthorize, but evaluated across an inherited hierarchy of scopes instead of one method), then check the API is even enabled — a step with no real Spring analog, closer to a feature flag gating an entire controller.

CIAM in production: A Service Account is GCP's workload identity — it can authenticate to APIs the same way a user does, and its short-lived OAuth token comes from the instance/container metadata server, never a downloaded key file if you set it up right. In CI/CD, prefer Workload Identity Federation over a downloaded Service Account JSON key: the pipeline runner presents its own OIDC token (GitHub Actions, GitLab, another cloud), GCP's STS exchanges it for a short-lived access token, and no long-lived credential is ever stored as a secret. The problem

You wrote tight IAM bindings for every human on the team — then created a VM without thinking about identity at all, and that VM can now edit almost anything in the project.

gcloud compute instances create with no --service-account flag

You provision shop-batch-vm the fast way: gcloud compute instances create shop-batch-vm --zone=us-central1-a --machine-type=e2-medium. No --service-account flag, no --scopes flag — you just needed a VM to run a nightly script.

GKE, Cloud Run, and Cloud Functions all make you think about identity explicitly; a bare Compute Engine VM doesn't. Skip the flag and the VM attaches to the project's default Compute Engine service account — PROJECT_NUMBER-compute@developer.gserviceaccount.com — an account that exists in every project automatically, and that has historically shipped bound to the broad, legacy Editor role at the project level unless someone has already gone in and stripped it down. Anyone who can SSH into that VM, or trigger an SSRF bug in whatever's running on it, can hit the metadata server and mint an OAuth token scoped to whatever that default account can do — which, if nobody locked it down, is most of the project.

The one-sentence rule. Every workload identity — a VM, a service account, a pod — should be able to do only what that specific workload needs, and GCP will happily hand out a much broader default than that if you never make the explicit choice; the absence of a decision is itself a decision, and it's usually the wrong one.
No --service-account flag doesn't mean no identity — it means the loudest, broadest identity in the project by default. Silence isn't neutral here; it's Editor.

The mechanism

Here's what actually decides a VM's identity, and it happens before you ever touch IAM.

  1. gcloud compute instances create runs with no --service-account givenno flag
  2. Compute Engine falls back to the project's default Compute Engine service accountfallback
  3. That account is attached as the VM's metadata-server identityattach
  4. IAM bindings on that service account — set once, maybe years ago — now apply to anything running on the VMinherited grant
  5. Any process on the VM can call the metadata server and receive a live OAuth token for that identitytoken available
  6. No code change, no explicit grant — the VM's blast radius equals the default SA's role, whatever that turned out to beblast radius

Step 2 is the one nobody sees happen. There's no prompt, no warning, no diff to review — the fallback is silent, so the VM's real permissions are whatever was bound to that default account long before this VM ever existed.

1. The hierarchy: where a resource lives decides billing, policy, and access

# the hierarchy, top to bottom
Organization contoso.com # tied to a Workspace/Cloud Identity domain
└─ Folder Production # optional, nestable, mirrors org structure
   └─ Project shop-prod-91a2 (billing + API scope + default IAM scope)
      ├─ compute.googleapis.com/instances shop-api-vm
      ├─ storage.googleapis.com/buckets shop-uploads
      └─ sqladmin.googleapis.com/instances shop-db
The project is doing double duty Azure splits across two levels. Where Azure separates the subscription (billing) from the resource group (lifecycle), GCP folds both into the project — it is the billing account, the default IAM scope, and the API-enablement boundary all at once. That is also why "one project per environment" (not one project for everything) is the standard convention: it keeps billing, quotas, and blast radius cleanly separated between shop-dev and shop-prod.

2. IAM bindings: role + members + optional condition, inherited downward

# grant a role at the PROJECT scope
gcloud projects add-iam-policy-binding shop-prod-91a2 \
  --member="user:ada@contoso.com" \
  --role="roles/compute.instanceAdmin.v1"

# the same bind, but time-boxed with a CEL condition
gcloud projects add-iam-policy-binding shop-prod-91a2 \
  --member="user:contractor@contoso.com" \
  --role="roles/storage.objectViewer" \
  --condition="expression=request.time < timestamp('2026-09-01T00:00:00Z'),title=expires-sept"
Roles come in three flavors. Basic roles (Owner/Editor/Viewer) are broad and legacy — avoid them in production. Predefined roles are service-scoped and specific (roles/compute.instanceAdmin.v1). Custom roles let you hand-pick permissions at the project or org level. Whatever role you bind, it inherits downward: a binding at the folder flows to every project and resource beneath it, and a project-level binding unions with anything inherited from above — GCP IAM has no way to subtract a permission an ancestor granted, only Organization Policy constraints can restrict what's allowed regardless of IAM.

3. API enablement: the gate before IAM even gets asked

# list what's enabled, then enable what you need
gcloud services list --enabled
gcloud services enable compute.googleapis.com run.googleapis.com sqladmin.googleapis.com

# Application Default Credentials — local dev vs. attached identity
gcloud auth application-default login # local dev: your user creds
# on Compute Engine/Cloud Run/GKE: the attached Service Account is used automatically
A disabled API fails before RBAC ever runs. Every resource type belongs to a specific Google API, and that API is off by default on a brand-new project. Try to create a Compute Engine VM without enabling compute.googleapis.com first and you get SERVICE_DISABLED — a distinct failure mode from an IAM denial, and one that trips up almost everyone's first `gcloud` session. Application Default Credentials (ADC) is the resolution order the client libraries use to find identity: an explicit key file, then gcloud auth application-default login for local dev, then the attached Service Account's metadata-server token when running on GCP compute.
