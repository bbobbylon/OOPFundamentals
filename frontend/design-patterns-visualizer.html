Design Patterns — Reusable Solutions to Recurring Problems

From the Gang of Four book. These aren't rules — they're names for shapes you'll see in real codebases. Recognize them and you'll read code 10× faster.

Singleton creational

Ensure a class has exactly one instance and provide a global access point to it.
Code
public class AppSettings {
    private static final AppSettings INSTANCE = new AppSettings();

    private AppSettings() { ... }            // private — no one else can `new` it

    public static AppSettings get() {       // the only door in
        return INSTANCE;
    }

    public String getApiKey() { ... }
}

// Modern Java: enum singleton — thread-safe by JVM, no boilerplate
public enum AppSettings {
    INSTANCE;
    public String getApiKey() { ... }
}
Where it shows up

java.lang.Runtime

Runtime.getRuntime() — one JVM, one runtime

Loggers

SLF4J/Log4j loggers cached per class

Spring beans

Default scope IS singleton — the container owns it

Connection pools

HikariCP — one pool, shared across the app

✓ Use when

  • The object owns a resource that should exist exactly once (config, pool, cache)
  • Multiple instances would actively cause bugs

✗ Avoid when

  • You just want "global access" — that's not the same as "needs to be one"
  • You'd benefit from dependency injection (most cases)
  • You need easy mocking in tests — singletons are sticky

Factory creational

Delegate object creation to a method or class — callers ask for "a shape of type CIRCLE", not new Circle().
Code
interface Shape { void draw(); }
class Circle implements Shape { ... }
class Square implements Shape { ... }

public class ShapeFactory {
    public static Shape create(String type) {
        return switch (type) {
            case "circle" -> new Circle();
            case "square" -> new Square();
            default       -> throw new IllegalArgumentException(type);
        };
    }
}

// caller — doesn't import Circle/Square at all
Shape s = ShapeFactory.create("circle");
s.draw();
Variations
// Static factory method on the type itself (often the best version)
List<String> l = List.of("a", "b");
Optional<User> o = Optional.ofNullable(maybeUser);
LocalDate d = LocalDate.parse("2026-05-21");

// Abstract factory — when you produce families of related objects
GuiFactory mac = new MacFactory();
mac.createButton(); mac.createMenu();
Where it shows up

Integer.valueOf(int)

May return a cached instance — you don't know, that's the point

List.of, Map.of

Static factories on collections

Calendar.getInstance()

Returns a calendar for the right locale

SLF4J LoggerFactory

You ask for a logger; the factory wires up the backend

✓ Use when

  • Choosing the concrete class depends on config, input, or platform
  • You want a named constructor (Money.usd(10) reads better than new Money(10, USD))
  • Construction is non-trivial and you want to centralize it

✗ Avoid when

  • You only have one class — new Thing() is fine
  • You'd just be hiding a single new for ceremony

Builder creational

Construct complex objects step-by-step with a fluent API, avoiding constructors that take 14 arguments.
❌ Telescoping constructor — unreadable
new Pizza("large", true, false, true, false,
          true, "thin", false, "tomato");
// What is true #3 again? Is it olives? Onions?
✅ Builder — reads itself
Pizza pizza = Pizza.builder()
    .size("large")
    .crust("thin")
    .sauce("tomato")
    .addCheese()
    .addPepperoni()
    .addOlives()
    .build();
Skeleton
public class Pizza {
    private final String size, crust, sauce;
    private final Set<String> toppings;
    // private constructor — only the builder calls it
    private Pizza(Builder b) { /* copy fields */ }

    public static Builder builder() { return new Builder(); }

    public static class Builder {
        private String size, crust, sauce = "tomato";
        private Set<String> toppings = new HashSet<>();
        public Builder size(String s)   { this.size = s; return this; }
        public Builder crust(String c)  { this.crust = c; return this; }
        public Builder addOlives()      { toppings.add("olives"); return this; }
        public Pizza build()             { return new Pizza(this); }
    }
}
Where it shows up

StringBuilder

new StringBuilder().append("a").append("b").toString()

Stream.Builder

Build a stream item-by-item

HttpRequest.newBuilder()

Java's modern HTTP client

Lombok @Builder

Annotation auto-generates the whole thing

✓ Use when

  • Class has many constructor parameters (especially optional ones)
  • You want sensible defaults that callers can override
  • You want the resulting object to be immutable

✗ Avoid when

  • The class has 2-3 fields — a constructor or record is simpler
  • Construction order matters and the builder allows wrong sequences

Observer behavioral

Define a one-to-many dependency: when the subject changes, all its observers are notified automatically.
Code
interface Observer { void onNews(String headline); }

class NewsAgency {
    private final List<Observer> subs = new ArrayList<>();

    public void subscribe(Observer o)   { subs.add(o); }
    public void unsubscribe(Observer o) { subs.remove(o); }

    public void publish(String headline) {
        for (Observer o : subs) o.onNews(headline);
    }
}

// callers — these subscribers don't know about each other
NewsAgency agency = new NewsAgency();
agency.subscribe(headline -> System.out.println("📺 TV: " + headline));
agency.subscribe(headline -> System.out.println("📱 App: " + headline));
agency.publish("Java 25 released!");  // fires both observers
Where it shows up

UI event listeners

button.addClickListener(e -> ...)

Spring ApplicationEvent

Publish/subscribe within a Spring app

RxJava / Project Reactor

Observable streams of events

Kafka / RabbitMQ

Same shape, but observers are remote services

MVC view updates

Model changes → views re-render

WebSockets

Server pushes events to subscribed clients

✓ Use when

  • One thing happens, many things need to react — and they shouldn't know each other
  • The set of listeners changes at runtime
  • You want event-driven decoupling

✗ Watch out for

  • Memory leaks — observers that never unsubscribe (use weak references in long-lived subjects)
  • Order dependencies — observer A relies on observer B having run first = fragile
  • Surprise cascades — one event triggers events triggers events…

Strategy behavioral

Define a family of algorithms, encapsulate each one, make them interchangeable. The client picks which one to use.
Code
interface PaymentStrategy { void pay(int cents); }

class CreditCardPay implements PaymentStrategy { ... }
class PayPalPay     implements PaymentStrategy { ... }
class CryptoPay     implements PaymentStrategy { ... }

class Checkout {
    private final PaymentStrategy strategy;
    // constructor takes whichever one we're using today
    public Checkout(PaymentStrategy s) { this.strategy = s; }

    public void complete(Cart cart) {
        strategy.pay(cart.totalCents());     // dispatches to whichever impl
    }
}

// In modern Java, the strategy is often just a lambda
Checkout c = new Checkout(cents -> stripe.charge(cents));
Where it shows up

Collections.sort(list, comparator)

Comparator IS the strategy

Spring's @Qualifier

Inject ONE of several strategies by name

Compression algorithms

GZIP, BZIP2, ZSTD all implement Compressor

Authentication providers

OAuth, LDAP, SAML — all implement Authenticator

Thread pool RejectedExecutionHandler

What to do when the pool is full

Caching eviction policies

LRU, LFU, FIFO — pick one at config time

✓ Use when

  • You have a family of algorithms and the caller picks which
  • You want to swap behavior at runtime, not compile time
  • You're replacing a big if/switch on type

✗ Avoid when

  • You have exactly one algorithm and no realistic chance of more
  • The interface adds ceremony without bringing flexibility

Other patterns worth recognizing

Adapter structural

Wrap one interface so it looks like another (USB-C → USB-A)

Decorator structural

Wrap an object to add behavior (BufferedInputStream wraps FileInputStream)

Facade structural

One simple interface in front of a complex subsystem

Proxy structural

Stand-in object — lazy loading, access control, remote calls

Composite structural

Tree of objects treated uniformly (UI components contain components)

Iterator behavioral

Step through a collection without exposing its internals

Command behavioral

Wrap a request as an object — undo, queues, macros

Template Method behavioral

Parent defines the skeleton; children fill specific steps

State behavioral

Object's behavior changes when its internal state changes

Chain of Responsibility behavioral

Servlet filters, middleware — pass request through a chain until someone handles it
