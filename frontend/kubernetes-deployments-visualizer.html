1 — Deployment Manifest




A Deployment declares desired replicas and a pod template. It owns a ReplicaSet which ensures the right number of pods are always running.


apiVersion: apps/v1
kind: Deployment
metadata:
  name: api-server
spec:
  replicas: 3
  selector:
    matchLabels: { app: api-server }
  strategy:
    type: RollingUpdate
    rollingUpdate:
      maxSurge: 1        # extra pods during update
      maxUnavailable: 0   # never go below replicas
  template:
    metadata:
      labels: { app: api-server }
    spec:
      containers:
      - name: app
        image: myregistry/api-server:1.0
        livenessProbe:
          httpGet: { path: /actuator/health/liveness, port: 8080 }
          initialDelaySeconds: 30
        readinessProbe:
          httpGet: { path: /actuator/health/readiness, port: 8080 }









2 — Rolling Update Strategy




A rolling update creates a new ReplicaSet and gradually shifts replicas from old to new. With maxSurge:1, maxUnavailable:0 and replicas:3, you always have 3 healthy pods and at most 4 total during the update.


# trigger a rollout
kubectl set image deployment/api-server app=myregistry/api-server:2.0

# watch progress
kubectl rollout status deployment/api-server

# history
kubectl rollout history deployment/api-server
# REVISION  CHANGE-CAUSE
# 1         initial deploy
# 2         image update to 2.0









3 — Probes: Liveness vs Readiness






ProbeFailure actionUse for


livenessProbeRestart containerDetect deadlock / hung process


readinessProbeRemove from Service endpointsWarm-up, temporary unavailability


startupProbeRestart if not ready within failureThresholdSlow-starting apps (protects liveness during startup)




For Spring Boot: expose /actuator/health/liveness and /actuator/health/readiness by adding the Kubernetes actuator group in application.yml.









4 — Horizontal Pod Autoscaler (HPA)




apiVersion: autoscaling/v2
kind: HorizontalPodAutoscaler
metadata:
  name: api-server-hpa
spec:
  scaleTargetRef:
    apiVersion: apps/v1
    kind: Deployment
    name: api-server
  minReplicas: 2
  maxReplicas: 10
  metrics:
  - type: Resource
    resource:
      name: cpu
      target:
        type: Utilization
        averageUtilization: 70  # scale up if avg CPU > 70%


HPA requires metrics-server in the cluster. For KEDA (event-driven autoscaling on queue depth, Redis key count, etc.) replace HPA with a ScaledObject.
