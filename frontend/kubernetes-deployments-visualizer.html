Deployments & Scaling

Deployments manage ReplicaSets so your pods survive crashes, updates, and traffic spikes. See Deployment Strategies for blue-green, canary, feature-flag, and GitOps alternatives to the rolling update this page covers.

🚢 What is a Deployment — and how is it different from just running a Pod directly?

A Deployment manages pods for you — you never run pods directly in prod. The chain is Deployment → ReplicaSet → Pods, and it exists for rolling updates: change the image and K8s spins up a new ReplicaSet while draining the old one for zero-downtime, rolling back instantly if health checks fail. Key fields: replicas, selector (must match pod labels), template (the pod spec), and strategy (RollingUpdate with maxSurge/maxUnavailable). A HorizontalPodAutoscaler scales replicas on CPU/metrics, and kubectl rollout undo reverts to the previous ReplicaSet. Stateless apps use Deployments; stateful ones (Ping, DBs) use StatefulSets, and scheduled work uses CronJobs.

  • Deployment → ReplicaSet → Pods — never run bare pods in prod.
  • Rolling updates, zero-downtime — new RS up as old drains; instant rollback.
  • maxSurge/maxUnavailable tune the rollout; HPA scales on CPU/metrics.
  • Stateless → Deployment; stateful (Ping/DB) → StatefulSet; scheduled → CronJob.

Deployment vs other controllers

Deployment: stateless apps. Multiple replicas all identical — each pod could be any "instance" of the app. Your Spring Boot CIAM service. StatefulSet: stateful apps needing stable identity. Pods get stable network names: ping-0, ping-1, ping-2. Ordered startup/shutdown. Persistent volume per pod. Use for: Ping Identity server cluster, database (PostgreSQL), distributed cache (Redis Cluster). DaemonSet: one pod per node. Use for: log collector (Fluentd), monitoring agent (Prometheus node exporter), network plugin. Job: runs to completion, then stops. Use for: database migration, report generation, data export. CronJob: Job on a schedule. Use for: nightly CIAM user sync, token cleanup, audit log rotation. Common mistake: using Deployment for a database — use StatefulSet instead so pods have stable identities and persistent storage.

CIAM deployment strategy: Run the auth service as a Deployment with maxUnavailable: 0 + maxSurge: 1 — zero-downtime is critical since any gap means users can't log in. HPA (minReplicas: 2, maxReplicas: 20 at 70% CPU) absorbs the 9 AM login spike and scales back by night. Use CronJobs for nightly Entra sync, expired-session cleanup, and token-blacklist pruning. And a readinessProbe is required — K8s only routes traffic after /actuator/health/readiness confirms the app and DB connections are up.

1 — Deployment Manifest




A Deployment declares desired replicas and a pod template. It owns a ReplicaSet which ensures the right number of pods are always running.


apiVersion: apps/v1
kind: Deployment
metadata:
  name: api-server
spec:
  replicas: 3
  selector:
    matchLabels: { app: api-server }
  strategy:
    type: RollingUpdate
    rollingUpdate:
      maxSurge: 1        # extra pods during update
      maxUnavailable: 0   # never go below replicas
  template:
    metadata:
      labels: { app: api-server }
    spec:
      containers:
      - name: app
        image: myregistry/api-server:1.0
        livenessProbe:
          httpGet: { path: /actuator/health/liveness, port: 8080 }
          initialDelaySeconds: 30
        readinessProbe:
          httpGet: { path: /actuator/health/readiness, port: 8080 }









2 — Rolling Update Strategy




A rolling update creates a new ReplicaSet and gradually shifts replicas from old to new. With maxSurge:1, maxUnavailable:0 and replicas:3, you always have 3 healthy pods and at most 4 total during the update.


# trigger a rollout
kubectl set image deployment/api-server app=myregistry/api-server:2.0

# watch progress
kubectl rollout status deployment/api-server

# history
kubectl rollout history deployment/api-server
# REVISION  CHANGE-CAUSE
# 1         initial deploy
# 2         image update to 2.0

4 — Horizontal Pod Autoscaler (HPA)




apiVersion: autoscaling/v2
kind: HorizontalPodAutoscaler
metadata:
  name: api-server-hpa
spec:
  scaleTargetRef:
    apiVersion: apps/v1
    kind: Deployment
    name: api-server
  minReplicas: 2
  maxReplicas: 10
  metrics:
  - type: Resource
    resource:
      name: cpu
      target:
        type: Utilization
        averageUtilization: 70  # scale up if avg CPU > 70%


HPA requires metrics-server in the cluster. For KEDA (event-driven autoscaling on queue depth, Redis key count, etc.) replace HPA with a ScaledObject.
