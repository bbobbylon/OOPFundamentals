Deployments & Scaling

Deployments manage ReplicaSets so your pods survive crashes, updates, and traffic spikes. See Deployment Strategies for blue-green, canary, feature-flag, and GitOps alternatives to the rolling update this page covers.

🚢 What is a Deployment — and how is it different from just running a Pod directly?

A Deployment manages pods for you — you never run pods directly in prod. The chain is Deployment → ReplicaSet → Pods, and it exists for rolling updates: change the image and K8s spins up a new ReplicaSet while draining the old one for zero-downtime, rolling back instantly if health checks fail. Key fields: replicas, selector (must match pod labels), template (the pod spec), and strategy (RollingUpdate with maxSurge/maxUnavailable). A HorizontalPodAutoscaler scales replicas on CPU/metrics, and kubectl rollout undo reverts to the previous ReplicaSet. Stateless apps use Deployments; stateful ones (Ping, DBs) use StatefulSets, and scheduled work uses CronJobs.

  • Deployment → ReplicaSet → Pods — never run bare pods in prod.
  • Rolling updates, zero-downtime — new RS up as old drains; instant rollback.
  • maxSurge/maxUnavailable tune the rollout; HPA scales on CPU/metrics.
  • Stateless → Deployment; stateful (Ping/DB) → StatefulSet; scheduled → CronJob.

Deployment vs other controllers

Deployment: stateless apps. Multiple replicas all identical — each pod could be any "instance" of the app. Your Spring Boot CIAM service. StatefulSet: stateful apps needing stable identity. Pods get stable network names: ping-0, ping-1, ping-2. Ordered startup/shutdown. Persistent volume per pod. Use for: Ping Identity server cluster, database (PostgreSQL), distributed cache (Redis Cluster). DaemonSet: one pod per node. Use for: log collector (Fluentd), monitoring agent (Prometheus node exporter), network plugin. Job: runs to completion, then stops. Use for: database migration, report generation, data export. CronJob: Job on a schedule. Use for: nightly CIAM user sync, token cleanup, audit log rotation. Common mistake: using Deployment for a database — use StatefulSet instead so pods have stable identities and persistent storage.

CIAM deployment strategy: Run the auth service as a Deployment with maxUnavailable: 0 + maxSurge: 1 — zero-downtime is critical since any gap means users can't log in. HPA (minReplicas: 2, maxReplicas: 20 at 70% CPU) absorbs the 9 AM login spike and scales back by night. Use CronJobs for nightly Entra sync, expired-session cleanup, and token-blacklist pruning. And a readinessProbe is required — K8s only routes traffic after /actuator/health/readiness confirms the app and DB connections are up.

or, why "successfully rolled out" and "users can log in" can be two different claims

The problem

Your rollout finishes clean — deployment "ciam-auth" successfully rolled out — and for the next fifteen seconds, real login requests get connection refused.

The rollout that succeeds and fails at the same time

The manifest defines a livenessProbe hitting /actuator/health/liveness — that feels like the important one, the one that catches a hung process. Nobody added a readinessProbe.

Kubernetes' own documented default: a container with no readinessProbe is considered Ready the instant it reaches the Running state — no check performed at all. The moment the new pod's process starts, the Service adds its IP to the Endpoints and real traffic starts arriving, even though your Spring Boot app is still loading its context and hasn't opened a database connection yet. The rolling update proceeds exactly on schedule from Kubernetes' point of view — new pods are "Ready," so old ones get terminated right on cue — and kubectl rollout status watches that same signal, reporting success the instant the last new pod was marked Ready, not when it could actually answer a request.

livenessProbe defined, deadlock detection covered ✓ kubectl rollout status says success ✓ real requests during the window get refused ⚠

Every command in your runbook did exactly what it claimed. The manifest just never told Kubernetes what "ready" was supposed to mean.

Fix: define a readinessProbe that checks the real thing
Add a readinessProbe pointing at /actuator/health/readiness — the Spring Boot group that only returns 200 once the app context and its dependency checks (DB, downstream IdP) are actually up ↓ this is the one signal Kubernetes trusts to decide "add this pod to the Service" — nothing else gates that decision Set an honest initialDelaySeconds/periodSeconds for the app's real startup time, so the first check doesn't fire before there's anything worth checking ↓ a probe that starts a little too early just delays the rollout slightly — nowhere near as bad as skipping it entirely And watch kubectl rollout status in one terminal while hitting the Service with real (or synthetic) traffic in another, so you can see the gap close instead of assuming it's gone
The one-sentence rule. Readiness answers one specific question — can this pod usefully receive traffic right now — and Kubernetes' default answer, with no probe configured, is an unconditional yes the instant the container starts. A livenessProbe answers a completely different question (should this container be restarted) and never gates traffic at all. Defining only the one that feels important leaves the traffic-gating question answered by a default that assumes every app is instantly ready — vanishingly rare for anything running on a JVM with a connection pool to warm up.
Kubernetes doesn't wait to be convinced a pod is ready — it assumes yes until you build something that can say no. Skip the readinessProbe and you've hired a bouncer who waves everyone in the second they appear at the door, before checking whether they're actually on the list.

The mechanism

Here's the exact sequence Kubernetes follows for a Deployment with no readinessProbe.

  1. The new ReplicaSet starts a pod; its container image is pulled and the process launchescontainer starts
  2. Kubelet checks: is a readinessProbe defined for this container?the check
  3. There isn't one — so the documented default applies: Ready = Success, immediatelyno probe = auto-ready
  4. The pod's Ready condition flips true; the Service controller adds its IP to the Endpoints objectadded to Service
  5. Real traffic starts arriving at a pod whose Spring Boot context is still loadingtoo early
  6. The Deployment controller sees enough Ready replicas and terminates an old pod; kubectl rollout status reports successrollout "completes"

Step 3 is the entire bug, and it's not a corner case — it's Kubernetes' documented, intentional default. The system isn't guessing wrong; it's doing exactly what an absent readinessProbe tells it to do, which is assume the best.

Deployment — watches rollout status
ReplicaSet — counted "done" once replicas are Ready
Pod — container is Running
Ready = Success (the default, with no probe)everything above is quietly trusting this one assumption

Every layer here is telling the truth about what it watches — the Deployment really is counting Ready replicas, the ReplicaSet really is tracking Pod conditions. The gap lives at the very center: "Ready," with nothing else configured, means nothing more than "the container process exists."

A Deployment's pod template has a livenessProbe hitting /actuator/health/liveness but no readinessProbe at all. During a rolling update, kubectl rollout status reports success in under ten seconds, but real login requests fail for the next fifteen. What's actually going on?

Nothing in this scenario points at restarts — a livenessProbe firing would show up as repeated container restarts in kubectl get pods, and the rollout still completed cleanly. Liveness governs restarts, not traffic routing.

Right — with no readinessProbe, "Ready" defaults to true the moment the container starts, so the Service routes to it long before the app inside can actually answer a request.

kubectl rollout status genuinely does wait for the Ready condition, not just a bare replica count — that's the whole point of the command. The sneaky part is that the Ready condition it's watching was, in this case, configured to mean nothing more than "the process exists."

Where you have seen this before

A platform assumes success by default until something tells it otherwise — and the assumption quietly outlives the moment it stopped being true.

Spring Boot's /actuator/health without a custom indicator

/actuator/health reports UP based only on the health indicators actually wired in. If you never add one for your downstream identity provider, the endpoint can say UP while that dependency is completely unreachable — "UP" is the default for anything nobody built a check for.

unchecked and healthy look identical from outside

TypeScript trusting a return type instead of the actual runtime path

A function typed Promise<User> that internally does array.find(...) can legitimately resolve undefined at runtime — .find()'s real type is User | undefined. The compiler trusts the annotation everywhere downstream, not what the code can actually produce, and the mismatch surfaces as a crash three functions later.

the type system assumed; the runtime disagreed

An Auto Scaling Group's default health check is EC2-only

By default, an AWS Auto Scaling Group's health check type is EC2 — it only confirms the virtual machine is reachable, not that the application on it works. An instance can pass that check while the app itself is completely wedged, and ASG won't replace it until you explicitly switch the health check type to ELB, which actually asks the load balancer.

"the machine is up" and "the app works" are different questions

1 — Deployment Manifest




A Deployment declares desired replicas and a pod template. It owns a ReplicaSet which ensures the right number of pods are always running.


apiVersion: apps/v1
kind: Deployment
metadata:
  name: api-server
spec:
  replicas: 3
  selector:
    matchLabels: { app: api-server }
  strategy:
    type: RollingUpdate
    rollingUpdate:
      maxSurge: 1        # extra pods during update
      maxUnavailable: 0   # never go below replicas
  template:
    metadata:
      labels: { app: api-server }
    spec:
      containers:
      - name: app
        image: myregistry/api-server:1.0
        livenessProbe:
          httpGet: { path: /actuator/health/liveness, port: 8080 }
          initialDelaySeconds: 30
        readinessProbe:
          httpGet: { path: /actuator/health/readiness, port: 8080 }









2 — Rolling Update Strategy




A rolling update creates a new ReplicaSet and gradually shifts replicas from old to new. With maxSurge:1, maxUnavailable:0 and replicas:3, you always have 3 healthy pods and at most 4 total during the update.


# trigger a rollout
kubectl set image deployment/api-server app=myregistry/api-server:2.0

# watch progress
kubectl rollout status deployment/api-server

# history
kubectl rollout history deployment/api-server
# REVISION  CHANGE-CAUSE
# 1         initial deploy
# 2         image update to 2.0









3 — Probes: Liveness vs Readiness






ProbeFailure actionUse for


livenessProbeRestart containerDetect deadlock / hung process


readinessProbeRemove from Service endpointsWarm-up, temporary unavailability


startupProbeRestart if not ready within failureThresholdSlow-starting apps (protects liveness during startup)




For Spring Boot: expose /actuator/health/liveness and /actuator/health/readiness by adding the Kubernetes actuator group in application.yml.









4 — Horizontal Pod Autoscaler (HPA)




apiVersion: autoscaling/v2
kind: HorizontalPodAutoscaler
metadata:
  name: api-server-hpa
spec:
  scaleTargetRef:
    apiVersion: apps/v1
    kind: Deployment
    name: api-server
  minReplicas: 2
  maxReplicas: 10
  metrics:
  - type: Resource
    resource:
      name: cpu
      target:
        type: Utilization
        averageUtilization: 70  # scale up if avg CPU > 70%


HPA requires metrics-server in the cluster. For KEDA (event-driven autoscaling on queue depth, Redis key count, etc.) replace HPA with a ScaledObject.
