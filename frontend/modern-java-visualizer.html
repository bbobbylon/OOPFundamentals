Modern Java (14–21)

Records, Sealed Classes, Pattern Matching, Text Blocks, Virtual Threads — and everything in between.

☕ What did Java 14–21 actually change — and which features matter for Spring Boot?

Java sped up: 14–21 shipped high-impact features. Records (16) give immutable data classes in one line; sealed classes (17) close a hierarchy for exhaustive checks; pattern matching for switch (21) tests types and binds variables with guards; text blocks (15) are multiline strings without escaping; and virtual threads (21) are lightweight threads that scale to millions, so blocking I/O no longer ties up an OS thread — transforming Spring Boot throughput with spring.threads.virtual.enabled=true.

  • Records — immutable DTOs in one line; Jackson-ready in Spring Boot 3.
  • Sealed + pattern switch — exhaustive handling; a new subtype breaks the build.
  • Text blocks — readable multiline SQL/JSON without escaping.
  • Virtual threads — millions of cheap threads; blocking I/O unmounts instead of blocking.

Records as DTOs

record UserDto(Long id, String name, String email, List<String> roles) {}. Generated: id(), name(), etc. (not getId() — records use plain accessors). equals()/hashCode() based on all components. toString(): UserDto[id=42, name=Bobby, ...]. Compact constructor for validation: record Email(String value) { Email { if (!value.contains("@")) throw new IllegalArgumentException(); } }. Jackson works with records automatically (Spring Boot 3). Lombok's @Value is now largely replaced by records. Records can implement interfaces but can't extend classes.

Sealed classes + exhaustive switch

sealed interface AuthEvent permits LoginSuccess, LoginFailure, TokenExpired {}. Subclasses must be in same package/file, must extend/implement the sealed type. Now: String message = switch (event) { case LoginSuccess s -> "Welcome " + s.userId(); case LoginFailure f -> "Failed: " + f.reason(); case TokenExpired t -> "Token expired at " + t.at(); }. Compiler verifies all permits are handled — add a new event type = compile error until you add its case. No more missed cases. DDD (Domain-Driven Design) value objects as sealed records.

Virtual Threads (Java 21)

Platform (OS) threads: ~1MB stack, ~10,000 max practical limit. Blocking I/O = thread blocked. Virtual threads: ~few KB, millions possible. Blocking I/O = virtual thread unmounted from OS thread (which can serve another virtual thread). Same code, no reactive programming required. Spring Boot 3.2+: spring.threads.virtual.enabled=true switches Tomcat, scheduled tasks, @Async all to virtual threads. Result: a Spring Boot service that previously saturated at 200 concurrent requests can now handle 10,000+ with the same code. Caveat: thread-pinning (synchronized blocks holding native resources) prevents unmounting — avoid synchronized with virtual threads.

CIAM / Spring Boot: All response DTOs become records (record UserResponse(Long id, String displayName, …, Instant createdAt) {}, no Lombok); auth events become a sealed interface so the handler's switch is exhaustive; multiline SQL in specifications uses text blocks. Enable virtual threads in staging and confirm the HikariCP pool size — not threads — becomes the bottleneck, then scale the pool.

2 — Text Blocks (Java 15)

No more escape-character nightmares. Text blocks use """ triple-quote delimiters and preserve indentation automatically.

BEFORE — String literal hell
// JSON string String json = "{\\n" + " \\\"name\\\": \\\"Alice\\\",\\n" + " \\\"age\\\": 30\\n" + "}"; // HTML template String html = "<html>\\n" + " <body>\\n" + " <h1>Hello</h1>\\n" + " </body>\\n" + "</html>";
AFTER — Text blocks
// JSON string — clean! String json = """ { "name": "Alice", "age": 30 } """; // HTML template — readable! String html = """ <html> <body> <h1>Hello</h1> </body> </html> """;
Real examples

SQL query

String sql = """ SELECT u.id, u.name, o.total FROM users u JOIN orders o ON u.id = o.user_id WHERE u.active = TRUE AND o.total > 100 ORDER BY o.total DESC """;

Special escape sequences

// \ at end of line = line continuation // (no newline in the string) String s = """ This is a very long \ single line """; // Result: "This is a very long single line\n" // \s forces a trailing space String t = """ hello \s world """; // "hello " (3 spaces preserved)

Opening """

Must be followed by a newline. You cannot put content on the same line as the opening """.

Indentation Stripping

The position of the closing """ controls how much leading whitespace is stripped from every line.

Quotes inside

Single and double quotes don't need escaping. Only """ itself would need it (rare).

Still a String

Text blocks are compile-time constants. Same type as String, same methods, same pool interning.

3 — Switch Expressions (Java 14)

The old switch statement had fall-through bugs and couldn't return a value. Switch expressions fix both problems and add compiler-enforced exhaustiveness.

OLD — switch statement (dangerous)
// Fall-through bug waiting to happen String type; switch (day) { case MONDAY: case TUESDAY: case WEDNESDAY: case THURSDAY: case FRIDAY: type = "Weekday"; break; // forget this → falls through! case SATURDAY: case SUNDAY: type = "Weekend"; break; default: type = "Unknown"; } // Verbose. No return value. Error-prone.
NEW — switch expression (clean)
// Arrow syntax: no fall-through, returns value String type = switch (day) { case MONDAY, TUESDAY, WEDNESDAY, THURSDAY, FRIDAY -> "Weekday"; case SATURDAY, SUNDAY -> "Weekend"; }; // Compiler error if a Day enum value is missed! // No break needed. No fall-through possible. // yield for multi-statement cases String msg = switch (day) { case MONDAY -> "Start of the week"; case FRIDAY -> { System.out.println("TGIF!"); yield "End of work week"; } default -> "Midweek"; };

Arrow syntax (->)

No fall-through. Each arm is isolated. Multiple labels separated by commas.

It's an Expression

The whole switch returns a value. Assign it, pass it to a method, or return it directly.

Exhaustiveness

When switching over an enum, compiler errors if any value is not handled. No silent bugs.

yield keyword

Used inside a { } block arm to produce the value. Like return but for one switch arm.

4 — Records (Java 16)

Records are concise, immutable data carriers. One line replaces a full class with constructor, getters, equals, hashCode, and toString.

OLD — Plain data class (50+ lines)
public final class Point { private final int x; private final int y; public Point(int x, int y) { this.x = x; this.y = y; } public int getX() { return x; } public int getY() { return y; } @Override public boolean equals(Object o) { ... } @Override public int hashCode() { ... } @Override public String toString() { ... } } // 30-50 lines of boilerplate
NEW — Record (1 line!)
// Everything above — in one line: public record Point(int x, int y) {} // Auto-generated by compiler: // - canonical constructor Point(int x, int y) // - accessors: x() and y() (NOT getX/getY!) // - equals() comparing all components // - hashCode() based on all components // - toString() → "Point[x=3, y=4]" Point p = new Point(3, 4); p.x(); // 3 (accessor, not getX!) p.y(); // 4 p.toString(); // "Point[x=3, y=4]"
Advanced record features

Compact constructor (validation)

public record Point(int x, int y) { // Compact constructor — no parameter list! // Runs before assignment, great for validation public Point { if (x < 0 || y < 0) throw new IllegalArgumentException( "Coordinates must be non-negative"); } // Custom methods are fine public double distanceTo(Point other) { int dx = this.x - other.x(); int dy = this.y - other.y(); return Math.sqrt(dx*dx + dy*dy); } }

Records with generics & constraints

// Generic record public record Pair<A, B>(A first, B second) {} Pair<String, Integer> p = new Pair<>("hello", 42); p.first(); // "hello" p.second(); // 42 // Records are: // ✓ implicitly final (can't be extended) // ✓ implicitly extend java.lang.Record // ✓ all fields are private final // ✗ can't extend other classes // ✓ can implement interfaces // ✓ can have static members public record Range(int min, int max) implements Comparable<Range> { ... }

5 — Sealed Classes (Java 17)

Sealed classes restrict which other classes can extend or implement them. The compiler knows the complete, closed set of subtypes — enabling exhaustive pattern matching.

sealed interface Shape
permits Circle, Rectangle, Triangle
final class Circle
radius: double
final
sealed class Rectangle
permits Square
sealed (further restricted)
final class Square
final
non-sealed class Triangle
w, h, base: double
non-sealed (open again)
// The sealed interface — declares permitted subtypes public sealed interface Shape permits Circle, Rectangle, Triangle {} // Each permitted subclass must be final, sealed, or non-sealed public final record Circle(double radius) implements Shape {} public sealed class Rectangle implements Shape permits Square { public Rectangle(double width, double height) { ... } } public final class Square extends Rectangle { public Square(double side) { super(side, side); } } // non-sealed = opens hierarchy back up (escape hatch) public non-sealed class Triangle implements Shape { public Triangle(double base, double height) { ... } }

vs abstract class

Abstract classes are open — anyone in any package can extend them. Sealed classes restrict extension to a named set.

vs interface

Interfaces are open by default — anyone can implement. Sealed interfaces restrict implementors to the permits list.

Why it matters

Compiler knows ALL possible subtypes. Pattern matching over a sealed type can be exhaustive — no default needed.

Same compilation unit

If all permitted subclasses are in the same file, the permits clause is optional — compiler infers it.

6 — Pattern Matching for instanceof (Java 16)

Eliminates the redundant cast after an instanceof check. The binding variable is scoped to where it's known to be the right type.

OLD — Check then cast (redundant)
// You already checked it's a String... // ...but you still have to cast manually. if (obj instanceof String) { String s = (String) obj; // redundant! System.out.println(s.toUpperCase()); } // Even worse with multiple types: if (shape instanceof Circle) { Circle c = (Circle) shape; return Math.PI * c.radius() * c.radius(); } else if (shape instanceof Rectangle) { Rectangle r = (Rectangle) shape; return r.width() * r.height(); }
NEW — Pattern matching (binding variable)
// Type check + binding in one step if (obj instanceof String s) { // s is already a String here — no cast! System.out.println(s.toUpperCase()); } // Works great with && (guarded pattern) if (obj instanceof String s && s.length() > 5) { System.out.println("Long string: " + s); } // Multi-type dispatch, no redundant casts: if (shape instanceof Circle c) { return Math.PI * c.radius() * c.radius(); } else if (shape instanceof Rectangle r) { return r.width() * r.height(); }
Scope rule: The binding variable s is in scope only where the compiler can prove the pattern matched. On the true branch of if (obj instanceof String s), s is available. In a negated check — if (!(obj instanceof String s)) return; — s is available after the if block (flow typing).

7 — Pattern Matching for switch (Java 21)

The crown jewel of Modern Java. Combines switch expressions with type patterns, guarded patterns, and sealed-class exhaustiveness checking.

OLD — if-else chain (verbose, error-prone)
double area(Shape shape) { if (shape instanceof Circle c) { return Math.PI * c.radius() * c.radius(); } else if (shape instanceof Rectangle r) { return r.width() * r.height(); } else if (shape instanceof Triangle t) { return 0.5 * t.base() * t.height(); } throw new IllegalArgumentException( "Unknown shape"); // manual "exhaustiveness" }
NEW — Pattern switch (elegant, exhaustive)
double area(Shape shape) { return switch (shape) { // Type patterns: bind and use directly case Circle c -> Math.PI * c.radius() * c.radius(); case Rectangle r -> r.width() * r.height(); case Triangle t -> 0.5 * t.base() * t.height(); // No default needed! Shape is sealed. // Compiler GUARANTEES exhaustiveness. }; }

More pattern types — all in one switch:

String describe(Shape shape) { return switch (shape) { // Guarded pattern: type match + condition case Circle c when c.radius() == 0 -> "Degenerate circle (point)"; case Circle c -> "Circle r=" + c.radius(); // Rectangle with a guard case Rectangle r when r.width() == r.height() -> "Square! side=" + r.width(); case Rectangle r -> "Rectangle " + r.width() + "×" + r.height(); case Triangle t -> "Triangle base=" + t.base(); }; } // You can also handle null explicitly String label(Object obj) { return switch (obj) { case null -> "(nothing)"; case Integer i -> "int: " + i; case String s -> "string: " + s; default -> "other: " + obj.getClass().getSimpleName(); }; }
Order matters for guarded patterns. More-specific cases must come before less-specific ones. case Circle c when c.radius() == 0 must precede case Circle c — the compiler enforces this.

8 — Virtual Threads / Project Loom (Java 21)

Platform threads map 1:1 to OS threads — expensive, limited. Virtual threads are JVM-managed and cost nearly nothing. You can run millions of them.

Platform Threads — OS Threads (expensive)
Each dot = 1 OS thread (~1 MB stack). Limited by OS.
Virtual Threads — JVM-managed (cheap)
Each dot = 1 virtual thread (~few KB). Parked when blocking.

How to create virtual threads:

// Java 21 — three ways to create virtual threads // 1. Simple one-off Thread vt = Thread.ofVirtual() .name("my-virtual-thread") .start(() -> doWork()); // 2. Executor — one virtual thread per task (preferred for many tasks) try (var exec = Executors.newVirtualThreadPerTaskExecutor()) { for (int i = 0; i < 100_000; i++) { exec.submit(() -> callDatabase()); // 100k virtual threads: fine! } } // auto-closes, waits for all tasks // 3. Spring Boot 3.2+ — one property enables it app-wide // application.properties: spring.threads.virtual.enabled=true // All @RequestMapping handler threads become virtual threads automatically!
Platform thread blocks
// A blocking call like JDBC or REST: // Platform thread blocks → OS thread // sits idle, wasting 1MB stack memory. // With 1000 concurrent requests you need // 1000 OS threads → server struggles. String data = httpClient.GET("/api/users"); // Thread is BLOCKED here for 50ms... // OS thread burning stack space.
Virtual thread parks (zero waste)
// Same blocking call with virtual threads: // Virtual thread blocks → JVM detects it // → parks the virtual thread (heap memory) // → OS thread (carrier) picks up other work // With 1000 requests: only a handful of // OS threads needed. Server handles millions. String data = httpClient.GET("/api/users"); // Virtual thread PARKS here. 0 OS thread cost! // Carrier thread runs other virtual threads.
Spring Boot tip: With spring.threads.virtual.enabled=true, every HTTP request handler runs on a virtual thread. Blocking JDBC calls, RestTemplate calls, and file I/O are all fine — no reactive programming needed. Virtual threads are designed to make blocking code scale.

9 — Sequenced Collections (Java 21)

A new SequencedCollection interface standardises first/last access across all ordered collections. No more list.get(list.size() - 1) or ((LinkedList) deque).peekLast() hacks.

BEFORE — inconsistent across types
List<String> list = new ArrayList<>(); // First element list.get(0); // Last element — ugly! list.get(list.size() - 1); // Deque — completely different API deque.peekFirst(); deque.peekLast(); // LinkedHashSet — no first/last at all! // You'd have to iterate... set.iterator().next(); // first (bad)
AFTER — SequencedCollection (uniform)
// Same methods on List, Deque, LinkedHashSet collection.getFirst(); // first element collection.getLast(); // last element collection.addFirst(item); // prepend collection.addLast(item); // append collection.removeFirst(); // remove & return first collection.removeLast(); // remove & return last // Reversed view — no copy, O(1) List<String> reversed = list.reversed(); // LinkedHashSet, Deque — same reversed() method!
ArrayList (SequencedCollection)

New interface hierarchy

SequencedCollection extends Collection. SequencedSet extends it. SequencedMap is a parallel for maps.

Retrofitted

All existing ordered collections — List, Deque, LinkedHashSet, LinkedHashMap — now implement these interfaces.

reversed() view

Returns a reversed view, not a copy. Mutations to the view are reflected in the original and vice versa.

SequencedMap

Adds firstEntry(), lastEntry(), reversed() to LinkedHashMap and TreeMap.
