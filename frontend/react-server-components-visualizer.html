Server Components & Actions

Server Components run on the server, ship zero JavaScript, and talk to your database directly. Client Components ('use client') handle interactivity. Server Actions ('use server') are server functions you call from the client. The modern full-stack React model.

🖥️ What are React Server Components — and how is this different from just SSR?

Traditional SSR renders to HTML on the server, then ships the same JS to hydrate — every component's bundle reaches the browser. React Server Components are different: they run only on the server, produce a serialized UI payload (not HTML), can query the DB / read env vars directly (no API layer), and ship zero JS — no hydration. Client Components ('use client') run on server then browser, use hooks/events/state, and do ship JS. Composition is one-way: server can render client (and pass it as children), not the reverse. Server Actions ('use server') are server functions called from client code — lightweight RPC for mutations, no REST endpoint needed. Angular has no RSC equivalent (it's always client-rendered or pre-rendered).

  • Server Components ship 0 JS — run only on the server, query the DB directly.
  • Client Components ('use client') add hooks/events/state and ship JS.
  • One-way composition — server renders client; client takes server as children.
  • Server Actions = RPC mutations — no REST endpoint; Angular has no RSC analog.

Server Component (no JS shipped)

// app/users/page.tsx (Server Component by default in Next.js) // No 'use client' → runs on server only // ↓ Direct DB query — no API needed import { db } from '@/lib/db'; export default async function UsersPage() { // Can await directly (no useEffect needed) const users = await db.user.findMany({ where: { active: true }, include: { roles: true } }); // Zero JS shipped for this component // Browser only receives HTML + RSC payload return ( <main> <h1>Users</h1> {users.map(u => ( <!-- Client Component receives data as props --> <UserRow key={u.id} user={u} /> ))} </main> ); }

Client Component + Server Action

// UserRow.tsx — Client Component (needs onClick) 'use client'; // ← marks as Client Component export function UserRow({ user }: { user: UserDto }) { const [expanded, setExpanded] = useState(false); // Can use hooks because it's a Client Component return ( <div onClick={() => setExpanded(!expanded)}> {user.name} {expanded && <UserRoles userId={user.id} />} </div> ); } // actions/deleteUser.ts — Server Action 'use server'; export async function deleteUser(userId: number) { await db.user.delete({ where: { id: userId } }); revalidatePath('/users'); // refresh users page } // Call from Client Component — no REST API needed: <button onClick={() => deleteUser(user.id)}>Delete</button>

RSC vs Angular / Spring Boot

React Server Components → what does this look like in your CIAM stack? Server Component querying the DB directly ≈ a Spring Boot @RestController method — both run server-side and have access to the database. Client Component ≈ an Angular component (runs in the browser, handles interaction). Server Action ≈ a Spring Boot @PostMapping endpoint called by the Angular service — but with zero boilerplate (no DTO, no service layer, no HTTP path). The key difference: RSC eliminates the "API layer" for read operations and Server Actions simplify mutations. In enterprise CIAM apps (Spring Boot + Angular), you have a clear separation: Spring Boot is your server, Angular is your client — they communicate via a REST API. RSC collapses this separation in a Next.js-only stack. For your Spring Boot + Angular CIAM work, RSC knowledge helps you understand what the browser is doing and contrast with Next.js patterns.

CIAM relevance: A Next.js App Router admin panel can use a Server Component for the user list — query Ping/Entra via a server-side SDK with no token exposed to the browser — and a Server Action for role assignment ('use server'; async function assignRole(userId, role) { await pingClient.addRole(userId, role); revalidatePath('/users/' + userId) }) called straight from a button. Auth reads the session from cookies server-side, no Bearer header. Your Spring+Angular path (Angular → Bearer → Spring validates JWT → Ping) is 3 hops; RSC + Server Actions collapse it into one server-side call, and API keys / DB creds never leave the server.

1. Server vs Client Components

RunsOn the server, at request/build timeOn the server (SSR) and the client (hydration)
Ships JS to browser?No — zero client bundleYes — its code is in the client bundle
Can use hooks/state/effects?No (useState/useEffect are unavailable)Yes
Can access DB / fs / secrets?Yes — directly, with awaitNo (it runs in the browser too)
Event handlers (onClick)?NoYes
This requires a framework. RSC needs a bundler + server integration — Next.js App Router, or React Router/Remix. You can't drop Server Components into a plain Vite SPA. The directives 'use client' and 'use server' are compiler instructions, placed at the top of a file (or function, for actions).

2. The composition rule

A Server Component can import and render a Client Component. A Client Component cannot import a Server Component — but it can receive one as children (or any prop). So you "interleave" by passing server-rendered content into a client shell.

// ❌ Client importing Server — not allowed
// ✅ Server renders Client, passing a Server child through:
<ClientTabs>
  <ServerProductList /> // rendered on the server, slotted into the client shell
</ClientTabs>
Props crossing the boundary must be serializable. A Server Component passing props to a Client Component can send strings, numbers, arrays, plain objects, and JSX — but not functions (except Server Actions), class instances, Dates with methods, or symbols. The props are serialized into the RSC payload to reach the client.

3. Server Actions

// actions.ts
'use server';
export async function createTodo(formData) {
  await db.todo.create({ text: formData.get('text') });
  revalidatePath('/todos'); // refresh the server-rendered data
}

// in a component: <form action={createTodo}>…</form>
Progressive enhancement: a <form action={serverAction}> works even before JavaScript loads — the browser posts the form, the server runs the action. Once hydrated, React intercepts and runs it without a full page reload. Pair with useActionState (result + pending state), useFormStatus (submit button spinner), and useOptimistic (instant UI).
