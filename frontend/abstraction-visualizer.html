Abstraction — Show the What, Hide the How

An interface says "objects of this type can do X". The implementation can be anything. Your code calls X without knowing or caring.

🎭 What is abstraction? Why write code to an interface instead of to a class?

Abstraction is hiding the "how" and exposing only the "what." A PaymentService interface says "you can processPayment(amount)" — not whether that hits Stripe, writes to a DB, or is mocked in a test. Callers don't know or care, so you can swap implementations without touching any calling code. That's the Dependency Inversion Principle: high-level code depends on abstractions, not concretions.

  • Hide the how, expose the what — the interface is the contract.
  • Interface = pure contract; abstract class = partial implementation — "can-do X" vs "IS-A with shared code."
  • Swap implementations freely — real in prod, mock in tests, zero caller changes.
  • This is Dependency Inversion — depend on abstractions, not concrete classes.

Interface vs abstract class

Interface — pure contract, no state (until default methods); use for "can-do X". Abstract class — partial implementation, some abstract + some concrete; use for "IS-A" with shared code.

Why it matters for testing

If OrderService depends on a PaymentGateway interface, inject real Stripe in prod and a MockPaymentGateway in tests — zero code changes. That's Dependency Inversion in practice.

Spring / CIAM: Spring's UserDetailsService is an interface — implement it to tell Spring how to look up a user, and Spring Security calls loadUserByUsername() without knowing if it hits a database, LDAP, or an in-memory store. Swap the implementation and Security behaves identically.

Think of the steering wheel in your car. You turn left → the car goes left. You don't know if it's hydraulic, electric, or steer-by-wire. The wheel is the interface; the rest is hidden. Swap the engine, swap the brakes, swap the entire drivetrain — as long as the wheel still turns left and right, you can drive any car.

One interface, many implementations

All three of these devices implement Drivable — the same three methods. Click Drive all and watch the loop. Same code path, three completely different behaviors. 

interface Drivable {
    void start();
    void drive(int miles);
    void stop();
}

// One method works for ALL three (and any future Drivable, like an ebike or a tractor)
public void commute(Drivable vehicle) {
    vehicle.start();
    vehicle.drive(25);
    vehicle.stop();
}

Inheritance Multiple — a class can implement many Single — you only extend one parent
State (fields) Only public static final constants Can have instance fields with state
Constructors No Yes — called by subclass super(...)
Method bodies Allowed since Java 8 — default and static methods Always allowed
Best for Pure contracts: "can do X" (Comparable, Runnable, Serializable) Shared baseline: classes that mostly act the same but customize a few points
Default for new code Start here. Easier to mix, easier to mock, easier to evolve. Use when you have real shared state or non-trivial template behavior

The "template method" pattern — abstract class shines here

When most of an algorithm is shared but a few steps vary, an abstract class is perfect. The parent has the structure; the children fill in the holes. 

abstract class DataExporter {
    // The shared algorithm — same for every subclass
    public final void export(List<Row> rows) {
        openConnection();
        writeHeader();
        for (Row r : rows) writeRow(r);
        writeFooter();
        closeConnection();
    }

    // Steps the subclass fills in
    protected abstract void writeHeader();
    protected abstract void writeRow(Row r);
    protected abstract void writeFooter();
}

class CsvExporter extends DataExporter { ... }
class JsonExporter extends DataExporter { ... }
class XmlExporter extends DataExporter { ... }

Abstraction in everyday Java

📋 List, Map, Set

Your method takes a List<T>. The caller passes an ArrayList, LinkedList, or CopyOnWriteArrayList. Your code has no idea — and doesn't need to.

🗄️ JDBC

Connection, Statement, ResultSet are interfaces. Postgres, MySQL, Oracle each ship a driver implementing them. Your DAO code is the same against any of them.

🔌 Spring Data repositories

You declare interface UserRepository extends JpaRepository<User, Long>. Spring generates the implementation at runtime. You only ever see the interface.

🌐 java.io streams

InputStream is abstract. FileInputStream, ByteArrayInputStream, GZIPInputStream, SocketInputStream — all the same to read().

🧪 Mockito

Testing depends on abstraction. Mockito.mock(UserService.class) works because UserService is an interface (or has a no-arg ctor). Hard-coded dependencies = untestable code.

⚡ Comparator / Comparable

list.sort(Comparator.comparing(User::name)). sort doesn't know how to compare your objects — you abstract that into a Comparator.

The deeper meaning — managing complexity

Encapsulation hides data. Abstraction hides complexity. When you write file.write(bytes), you don't think about:

  • How the OS schedules the write
  • How the filesystem allocates blocks
  • Whether it's an SSD or HDD or NFS mount
  • The exact syscall the JVM ends up making

Every layer hides the one below it. That's the only reason a single human can program a modern system — you'd never get anything done if you had to hold all of it in your head. Good abstractions are leak-proof: you can use them without understanding what's underneath.

Bad abstractions — the leaky kind

🩹 Half-finished interface

An interface where some methods throw UnsupportedOperationException. Now callers have to know which implementations support which methods — the abstraction has leaked. (Collections.unmodifiableList is a known offender.)

🩹 Implementation in the name

HashMapBasedUserRepository. The whole point of abstraction is that callers shouldn't care it's a HashMap. Name the interface for the role, not the implementation.

🩹 Configuration cascade

To use the "simple" API, you must first configure 12 things. The abstraction is hiding complexity behind setup complexity. Good APIs work with sensible defaults.

🩹 One implementation, ever

An interface with exactly one implementation, no plan for more, no tests using a fake. That's not abstraction — it's ceremony. Inline it.

🌱 New to abstraction? Hide the "how," show the "what."

Abstraction means describing what something can do without exposing how it does it. An interface like interface PaymentProcessor { void charge(amount); } names a capability — "this can charge a payment" — without saying whether it's Stripe, PayPal, or a test fake. Callers depend on the idea, not the details, so any implementation can slot in. For a beginner the win is simplicity: the rest of your code says processor.charge(...) and doesn't care which provider is behind it. Swap the implementation and nothing else changes.

🧠 Expert corner — interface vs abstract class, and DIP

  • Interface vs abstract class. An interface is a pure contract (a class can implement many); an abstract class can hold partial implementation and state but you can extend only one. Reach for an interface by default; an abstract class when subclasses genuinely share code/fields.
  • Interfaces can carry default methods — shared behavior without forcing every implementer to rewrite it (how the JDK evolved Collection without breaking everyone).
  • "Program to an interface, not an implementation" is the Dependency Inversion Principle: high-level code depends on abstractions, low-level details implement them. This is exactly what makes dependency injection, mocking, and the Strategy pattern possible.
  • Functional interfaces + lambdas. A single-method interface (Runnable, Comparator) can be implemented inline with a lambda — abstraction without a named class.
  • Don't over-abstract (the gotcha above): an interface with one implementation and no test fake is just ceremony. Add the seam when a second implementation or a test actually needs it.
  • Real-world tie-in. A Spring UserRepository interface — you declare it, Spring Data generates the implementation; in tests you inject a fake. You coded to the abstraction and never wrote the SQL.
