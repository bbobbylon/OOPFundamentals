The Observer Pattern — the Weather Station

Chapter 2. You're building a weather station: a WeatherData object gets new measurements, and several display widgets must update the instant it does. Wire them together directly and you'll be editing the WeatherData class every time someone adds a display. The Observer pattern is how the newspaper-and-subscriber idea fixes that — and it's the same idea under RxJS, Angular outputs, and DOM events.

🎯 What is the Observer pattern — and how is it the same idea as RxJS, Angular @Output, and DOM events?

The Observer pattern defines a one-to-many dependency: when one object (the Subject) changes state, all its dependents (the Observers) are notified automatically. Without it: WeatherData calls currentConditionsDisplay.update(), statisticsDisplay.update(), forecastDisplay.update() directly — it's coupled to every display. Adding a new display means modifying WeatherData. The Observer pattern inverts this: displays register themselves with WeatherData.registerObserver(this). When weather changes: WeatherData.notifyObservers() — it calls update() on every registered observer. Adding a new display: create it, register it, done — WeatherData unchanged. This is the newspaper subscription model: the paper publishes; subscribers get notified. This exact pattern is: DOM addEventListener() (Subject = DOM element, Observer = listener), RxJS Observable.subscribe(), Angular @Output() EventEmitter (parent subscribes to child events), Spring's @EventListener, Java's PropertyChangeSupport.

The Java structure

interface Observer { void update(float temp, float humidity, float pressure); } interface Subject { void registerObserver(Observer o); void removeObserver(Observer o); void notifyObservers(); } class WeatherData implements Subject { List<Observer> observers = new ArrayList<>(); float temp; void setMeasurements(float t, float h, float p) { this.temp=t; notifyObservers(); } void notifyObservers() { observers.forEach(o -> o.update(temp,humidity,pressure)); } } class CurrentConditionsDisplay implements Observer { public void update(float t, float h, float p) { // refresh display } }

Pull vs Push

Push: Subject pushes all data to Observers in update(temp, humidity, pressure). Observer must accept all data even if it only needs temperature. Pull: Subject passes itself: update(WeatherData data). Observer calls data.getTemperature() — gets only what it needs. Head First advocates pull as cleaner. RxJS uses push: the Observable pushes values to the subscriber. Java's built-in java.util.Observable (deprecated in Java 9): push with setChanged() + notifyObservers(). Modern Java: use Flow.Publisher/Subscriber or just the listener pattern with lambdas.

Loose coupling principle

This pattern teaches the OO principle: "strive for loosely coupled designs between objects that interact." WeatherData knows observers implement the Observer interface — nothing else. It doesn't know their class names. Adding or removing observers doesn't touch the Subject. Observers can be added or removed at runtime (dynamic subscription). Subject and Observer can vary independently — change WeatherData's internals without touching any display. Change the displays without touching WeatherData. This is the core of event-driven programming: producers don't know consumers.

In CIAM / Spring Boot: Spring's Observer implementation: @EventListener. UserService publishes UserCreatedEvent. EmailService listens: @EventListener void onUserCreated(UserCreatedEvent e) { sendWelcomeEmail(e.getUser()); }. AuditService listens: @EventListener void onUserCreated(UserCreatedEvent e) { auditLog.record(e); }. MetricsService listens. Three observers, zero coupling to UserService. Add a new observer (Slack notification) = add one @EventListener, nothing changes in UserService. Angular: @Output() userCreated = new EventEmitter<User>() — parent subscribes with (userCreated)="onUserCreated($event)". Same Observer pattern, different syntax.

Act 1 — the hard-wired weather station

The naive measurementsChanged() reaches into each concrete display and pushes values directly:

void measurementsChanged() {
  float t = getTemperature(), h = getHumidity(), p = getPressure();
  currentDisplay.update(t, h, p);      // concrete reference
  statsDisplay.update(t, h, p);        // concrete reference
  forecastDisplay.update(t, h, p);     // concrete reference
}
Brain Power. Spot the problems. (1) We code to concrete display classes, not an interface. (2) Every new display means editing this method — we can't add or remove displays at runtime. (3) The one part that varies (the set of displays) isn't encapsulated. That last one should sound familiar from the Strategy chapter.

Act 2 — newspapers & subscribers

Observer works like a newspaper subscription. A publisher (the Subject) keeps a list of subscribers (Observers). Subscribers can join or cancel anytime, and the publisher doesn't know or care who they are — only that they implement "I can receive an update."

The two interfaces

interface Subject {
  void registerObserver(Observer o);
  void removeObserver(Observer o);
  void notifyObservers();
}
interface Observer {
  void update(float t, float h, float p);
}

The Subject keeps the list

class WeatherData implements Subject {
  private List<Observer> observers = new ArrayList<>();

  public void registerObserver(Observer o) { observers.add(o); }
  public void removeObserver(Observer o)   { observers.remove(o); }

  public void notifyObservers() {
    for (Observer o : observers) o.update(t, h, p);
  }
}

Act 3 — the Observer design in motion

A display registers itself in its constructor, then just waits to be told. When a new reading arrives, the Subject loops its list and calls update() on each — that's the fan-out the hero animates in scene ③.

class CurrentConditionsDisplay implements Observer {
  public CurrentConditionsDisplay(Subject weather) {
    weather.registerObserver(this);   // "subscribe me"
  }
  public void update(float t, float h, float p) {
    this.temperature = t; display();        // react to the push
  }
}

// WeatherData now just does:
void measurementsChanged() { notifyObservers(); }   // that's it

Q: Can an observer rely on the values arriving in a particular order, or on being notified before another observer?

A: No — and that's the point. Observers must be independent. If display B assumes display A ran first, you've smuggled coupling back in. Treat each update() as if it's the only one.

The principle this chapter hands you

Design PrincipleStrive for loosely coupled designs between objects that interact.

The Subject knows only that its observers implement the Observer interface — never their concrete classes. You can add new display types, or remove them at runtime, without changing the Subject. Loose coupling means the two sides can change independently: exactly the flexibility the hard-wired version lacked.

The Observer Pattern, defined

The Observer Pattern defines a one-to-many dependency between objects so that when one object changes state, all of its dependents are notified and updated automatically.

one-to-many = one WeatherData, many displays; changes state = new measurements; notified automatically = the notifyObservers() loop. Push (Subject sends the data) vs pull (observers ask the Subject for what they need) are both valid — pull scales better when observers want different slices.
