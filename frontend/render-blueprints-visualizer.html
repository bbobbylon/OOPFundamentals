Render Blueprints — your whole environment, in one file

or, how to stop rebuilding production from memory at eleven at night

📋 What is a Blueprint, and why would you write YAML for something the dashboard already does?

A Blueprint is a file called render.yaml at the root of your repo that declares every service, database and environment variable your app needs. Render reads it and makes reality match. This is the same idea as Terraform or a Kubernetes manifest — infrastructure as code — scoped down to one platform. The dashboard is faster for the first deploy; the file is the only version that survives you forgetting what you clicked.

  • Declarative, not imperative. You describe the end state; Render works out the steps to get there.
  • It's in git. Which means infrastructure changes get reviewed in a pull request, like code.
  • Services wire themselves together. fromDatabase and fromService inject real values at deploy time, so no credential is ever typed into the file.
  • Preview environments. One line, and every pull request gets its own full stack — its own API, its own database, its own URL.

The dashboard is not a bad tool — it's an unrecorded one

Clicking through the UI works perfectly. The problem is six months later, when you need a second environment and the only record of how the first one was configured is in your memory. A Blueprint makes "how is production set up?" a file you can read, diff and review.

Secrets belong in the file — but only their names

The trick that makes this safe: you declare that a variable exists without giving its value. sync: false means "I'll set this in the dashboard", generateValue: true means "invent one and never show me". The file is a complete description of your environment that is still safe to make public.

Spring / CIAM: this is exactly the shape your identity config wants. The IdP-issued client secret is sync: false — it came from Ping or Entra and only a human can supply it. A JWT signing key is generateValue: true — nobody should ever see it, including you. And the database password is fromDatabase, so it is never a value anyone types at all.

The idea

A Blueprint moves your environment out of a dashboard you click and into a file you review.

A Blueprint is a single render.yaml at the root of your repo. It declares the services you want, the databases they use, and the environment variables that connect them — and when you push it, Render makes reality match the file. Nothing is remembered, nothing is folklore, and "how is staging different from prod?" becomes a git diff instead of an archaeology project.

You already have a page on this idea: Terraform. The difference is scope, and scope explains everything else. Terraform can provision anything, anywhere — which is exactly why it needs providers, a state file, and a plan/apply ceremony to reconcile what it believes with what exists. A Blueprint provisions one platform. No providers, because there's one. No state file, because Render is the state. Forty lines instead of four hundred, and you give up every cloud but this one.

You

git push — 40 lines of render.yaml

Render

Created devhub-api (web, docker), devhub-mailer (worker), devhub-nightly (cron, 0 3 * * *) and a Postgres called devhub-db. SPRING_DATASOURCE_URL wired from the database. JWT_SECRET generated — I won't show it to you either. ENTRA_CLIENT_SECRET left blank: that one's yours to type.

If it isn't in the file, it isn't real.

That's the discipline the whole page is asking for, and it has teeth in both directions. A value you set by hand in the dashboard is a value nobody else can see, nobody reviewed, and nothing recreates — and the next Blueprint sync will happily overwrite it if it conflicts with the file. Meanwhile a resource you delete from the file does not disappear: syncing a Blueprint never deletes an existing resource. The file adds and updates. It does not subtract. Both halves of that sentence have surprised somebody at 6pm on a Friday, and scenario ④ below is that Friday.

The Blueprint is the source of truth render.yaml is committed, reviewed, merged → Render syncs reality to match it
Production breaks at 11pm and you fix it in the dashboard bump the instance count, add a missing env var → the site recovers, and you go to bed
Now the file and reality disagree — this is drift nothing warns you; both are individually correct → the gap is invisible until something reads the file again
The next sync resurrects the old value a teammate merges an unrelated one-line change → your 11pm fix is silently undone
So you close the loop: put the fix in the file the dashboard edit was the emergency; the commit is the fix → back to the top, and the file is true again

The loop only bites at step 4, which is why it catches people — the damage is done at step 2 but does not appear until someone unrelated pushes something unrelated. That is also the tell for diagnosing it: a setting that reverts itself for no reason, on a deploy that did not touch it, is drift being corrected exactly as designed. The dashboard edit is a defibrillator, not a treatment plan.

Anatomy of a render.yaml

Four top-level keys. Click each — the second one surprises people, because it isn't under the first.

services — everything that runs

A list, where each entry has a type: web (the only one that gets a public URL), pserv (a private service, reachable only from your other services), worker (a process with no port and no URL — queue consumers, mail senders), cron (needs a schedule: expression), and keyvalue (a Redis-compatible store). Choosing worker instead of web for something with no HTTP interface is not just tidiness: a worker is never asked for a port, so it can't fail the port check you met on the last page.

databases — its own key, not a service

Postgres lives at the top level in databases:, not inside services:, and this trips people up every time. Each entry takes a name (what Render calls it), a databaseName (what Postgres calls it), a user, a plan and a region. Match that region to your services or they can't use the fast private connection string at all.

envVarGroups — say it once, use it everywhere

A named bundle of environment variables that any number of services can pull in with - fromGroup: shared-config. The moment you have a web service and a worker that need the same six values, this is the difference between one edit and two — and between two services that agree and two that drift apart silently.

previews — a whole stack per pull request

previews: { generation: automatic } and every PR gets its own copy of every service and its own database, at its own URL. manual means opt-in per PR; off disables it. Pair it with expireAfterDays so they tidy themselves up, and with previewValue on individual variables to point a preview at a sandbox API key rather than the real one.

envVars — the interesting part

Four shapes, and only the first one contains a literal value. value: is a plain setting. fromDatabase: pulls a property off a database you declared. fromService: pulls one off another service. generateValue: true makes Render invent a random 256-bit value that nobody, including you, ever types. And sync: false puts the key in the file while leaving the value out — Render asks you for it once. Between the last two, a correct render.yaml can be public and still hold no secrets.

Your app needs the client secret for your Entra (Azure AD) app registration. It must be in the environment, it must never be in git, and Render must not invent it — the value is issued by the identity provider. Which wiring?

There is no shell here doing interpolation on your behalf — Render reads the file as written, so this either becomes a literal string or nothing at all. Worse, the habit it teaches is "secrets pass through the file", which is the thing we're avoiding.

Right tool, wrong secret. generateValue is perfect when you get to choose the value and nobody needs to know it — a JWT signing key, a session secret. Here the value is issued by the IdP: a random one Render invented would simply be wrong, and your OAuth flow would fail at token exchange.

Exactly. sync: false is the "declared but not defined" wiring: the file records that this service requires ENTRA_CLIENT_SECRET, which is genuinely useful documentation, while the value is entered once in the dashboard and never travels through git. Anyone recreating this environment gets told what's missing instead of finding out from a 401.

The reference

The keys worth memorising, and the ones worth looking up.

The service types
type: webThe only type with a public URL. Needs a port; gets a health check.
type: pservA private service — reachable from your other services, not from the internet.
type: workerA process with no port and no URL. Queue consumers, mailers, importers.
type: cronRuns on a schedule: and exits. The right home for a nightly job.
type: keyvalueA Redis-compatible store (older blueprints spell it redis).
runtime:node · python · ruby · go · rust · elixir · docker · image · static. Replaces the deprecated env:.
The four shapes of an env var
value: prodA literal. Fine for settings, never for secrets.
fromDatabase: {name, property}Pull connectionString, host, user, password or connectionPoolString off a database you declared.
fromService: {type, name, property}One service finds another: host, port, hostport. No hardcoded URLs.
generateValue: trueRender invents a random 256-bit value. Nobody types it; nobody leaks it.
sync: falseThe key is declared, the value is not. You supply it once in the dashboard.
fromGroup: shared-configPull in a whole envVarGroups entry.
Sync behaviour — the rules that bite
Auto SyncOn by default: a push that modifies the file triggers a sync. Turn it off to sync deliberately.
never deletes"Syncing a Blueprint never deletes an existing resource." Removing it from the file is not enough — delete it in the dashboard.
overwrites conflictsA dashboard edit that conflicts with the file is overwritten on the next sync.
recreatesDelete a resource in the dashboard but leave it in the file, and the next sync brings it back.

Friday, 6pm. Production is misbehaving, so you bump MAX_POOL_SIZE from 10 to 40 directly in the Render dashboard. It works. You go home without touching render.yaml, which still says 10.

Predict before you pick: on Monday, someone pushes an unrelated change to the Blueprint. What is the pool size?

This is the intuition to unlearn, and it's a reasonable one — most config systems do let the more specific layer win. Render's Blueprint isn't a layer under the dashboard, it's a declaration of what should be true.

10, and nobody gets told. The docs are blunt about it: if dashboard changes "conflict with configuration defined in the Blueprint, they're overwritten the next time you sync". Friday's fix was real, it worked, and it was never written down — so the next sync quietly reverts production to a value chosen before the problem existed. The habit that prevents this: if the emergency fix is worth keeping, it's worth a one-line pull request before you close the laptop.

There is a review step — a sync shows you the list of changes it's about to apply before you click Deploy Blueprint. But it shows what the file will do, not a merge conflict to resolve, and on a busy Monday "40 → 10" scrolls past in a list of changes you were expecting to see.

Put it together

Turn a clicked-together environment into a file — predict each output before you reveal it.

Start from what exists, not from a blank file

You don't have to write the first draft. Render can generate a Blueprint from services you already created by hand — which also produces an honest inventory of every value currently living only in a dashboard.

$ git add render.yaml && git commit -m "describe the environment" && git push
==> Blueprint file detected: render.yaml
==> Changes to apply:
      + create   web      devhub-api
      + create   worker   devhub-mailer
      + create   cron     devhub-nightly   (0 3 * * *)
      + create   postgres devhub-db
      ~ 1 environment variable requires a value: ENTRA_CLIENT_SECRET
read the plan output as a diff, not a log. Render is telling you what it is about to change — and this is the one moment before it happens where a wrong region or a missed sync: false is still free to fix.
Wire the database in without ever seeing the URL

The connection string contains a password. Typing it anywhere — a file, a dashboard, a Slack message to yourself — is a copy you now have to protect. Reference it instead.

envVars:
  - key: SPRING_DATASOURCE_URL
    fromDatabase:
      name: devhub-db
      property: connectionString
# in the running container:
$ echo $SPRING_DATASOURCE_URL
postgresql://devhub:••••••••@dpg-cs4k2h••••-a/devhub

# rotate the database password and this value follows automatically —
# there is no second copy to forget about.
the payoff is the •••• — that value exists in the container and has never existed in your repo, your terminal history, or your clipboard. Rotate the password and it follows, because there is no second copy to update.
Let a pull request build the whole stack

Two lines. The reviewer stops reading a diff and imagining the result, and starts clicking a URL where the result is running — with its own database, so they can break whatever they like.

previews:
  generation: automatic
  expireAfterDays: 7
==> Pull request #214 opened
==> Creating preview environment pr-214
      web      devhub-api-pr-214    https://devhub-api-pr-214.onrender.com
      worker   devhub-mailer-pr-214
      postgres devhub-db-pr-214     (a fresh, empty database)
      IS_PULL_REQUEST=true
==> Expires in 7 days
generation: automatic is the line that does it. expireAfterDays is the line that keeps it from quietly costing you money — a preview per PR with no expiry is how you end up paying for thirty dead environments.
Prove the "never deletes" rule to yourself, once

This is the rule most likely to bite you, so spend two minutes confirming it on something disposable rather than discovering it on something that matters.

$ git rm --cached nothing   # (just delete the devhub-mailer block from render.yaml)
$ git commit -am "remove the mailer" && git push
==> Changes to apply:
      (no deletions — syncing a Blueprint never deletes a resource)

# devhub-mailer is still running, still costing money, and is now
# invisible to anyone reading render.yaml. Delete it in the dashboard.
the lesson is what is missing from the plan: no delete. Removing a block from the file removes it from the file and nothing else. The service keeps running, keeps billing, and is now invisible to anyone reading the Blueprint.
The CIAM version of this page: your app registration's client secret, your signing key and your database password are three different kinds of secret, and the Blueprint has a different answer for each. The IdP issues the client secret → sync: false, because only the identity provider can tell you the value. You choose the signing key → generateValue: true, because a random 256-bit value nobody has ever typed is strictly better than one a human invented. Render issues the database credential → fromDatabase, so rotating it updates every consumer at once and leaves no stale copy behind. Three secrets, three wirings, and a render.yaml that could be made public without a single one of them leaking.
There are no dumb questions

So is this Terraform, or should I be using Terraform with it?

It's the same idea at a much smaller scope, and for a Render-only stack you should use the Blueprint and stop there. The tell is the state file. Terraform must keep its own record of what it created, because it talks to a dozen providers that don't agree on anything and can't be asked "what did I ask you for?" — hence plan, apply, state locking, and the entire genre of state-corruption stories. A Blueprint needs none of that: there's one platform, it knows what it's running, so Render is the state. Reach for Terraform when your infrastructure genuinely spans providers — a Render service plus an S3 bucket plus a Cloudflare record — and accept the ceremony as the price of that reach.

Where does a preview environment's database come from — is it a copy of production?

No, and this is the part to be clear-eyed about: it's a fresh, empty database of the same shape. That's the right default (you do not want a pull request from a contractor pointed at real customer rows), but it means a preview is only as useful as its seed data. The fix is to make seeding part of the deploy rather than a thing you do by hand: a preDeployCommand that runs your schema, plus a seed step guarded by IS_PULL_REQUEST so it only loads fixtures in previews. Do that once and every future PR gets a working app instead of an empty one — do it never, and previews quietly stop being used because "they're always broken".

If the file never deletes anything, how do I actually get rid of a service?

In the dashboard, by hand, and it's deliberate — an infrastructure tool that could delete your production database because someone resolved a merge conflict badly would be a worse tool. But the asymmetry has a sharp edge worth knowing: deleting a resource in the dashboard while it's still in the file doesn't work either. The next sync sees a resource the file requires and no resource existing, and helpfully recreates it. People hit this while cost-cutting, delete three services, and find them all running again after the next unrelated push. The order that works is: remove it from the file, push, then delete it in the dashboard.
