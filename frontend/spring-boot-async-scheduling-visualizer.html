Async & Scheduling

Run work off the calling thread with @Async, and execute recurring tasks automatically with @Scheduled — two essential patterns in every enterprise Spring Boot app.

⏱️ When does a REST endpoint do work asynchronously — and when does work run on a schedule?

By default every HTTP request is handled synchronously: the thread that receives it does all the work and returns the response. Fine for a fast DB query — a problem for slow work (sending email, calling an external API, building a report), because the HTTP thread blocks, the client waits, and your thread pool fills up under load. @Async moves a method onto a separate thread pool so the caller (and the HTTP response) returns immediately. @Scheduled is for work that isn't triggered by a request at all — it runs on a timer ("every night at 2am, clean up expired tokens"; "every 5 minutes, sync users from the IDM").

  • @Async = offload now. Free the HTTP thread; the task finishes later on a TaskExecutor.
  • @Scheduled = run on a clock. cron, fixedRate, or fixedDelay — no request needed.
  • Both are proxy-based — a self-call (this.method()) bypasses the proxy and runs inline/synchronously.
  • Multi-pod needs a lock. Every pod fires the same @Scheduled job; gate it with ShedLock so only one runs.

@Async — fire and forget

Annotate the method, enable with @EnableAsync. Spring runs it on a TaskExecutor; the caller returns immediately. Return CompletableFuture<T> when the caller needs the result. Gotcha: a same-class this.method() call bypasses the proxy and runs synchronously.

@Scheduled — timer work

cron="0 0 2 * * *" (2am daily), fixedRate=300_000 (every 5 min regardless of duration), fixedDelay=300_000 (5 min after the previous run ends). Enable with @EnableScheduling. In K8s with 3 pods all 3 fire — use ShedLock/Batch so one wins.

Custom thread pool

Define a ThreadPoolTaskExecutor bean with core/max/queue sizes and a thread-name prefix. Without it Spring's default pool is effectively unbounded — dangerous under load. Named threads also show up clearly in thread dumps.

CIAM: After POST /api/users, @Async sendActivationEmail(user) lets the 201 return to Angular instantly while the email sends in the background. @Scheduled(cron="0 0 3 * * *") deletes refresh tokens where expiresAt < now(); @Scheduled(fixedRate=600_000) syncs Entra ID group memberships every 10 min — guarded by @SchedulerLock(name="tokenCleanup", lockAtMostFor="10m").

The problem

The annotation is right there on the method. It just... doesn't run async anymore.

POST /api/users used to return in 40ms. After a refactor, it takes 800ms — and @Async is still on the method

Someone tidies up UserService and moves sendActivationEmailAsync() into the same class as createUser(), for locality. createUser() now calls this.sendActivationEmailAsync(user) directly instead of going through a separately injected bean. The method still has @Async on it. It still compiles. It still looks completely correct in review — the annotation is right there. But the HTTP thread now blocks on the entire email send, because the call never passes through the proxy that's actually responsible for the "run this later, on another thread" behavior.

@Async annotation still present ✓ method signature unchanged ✓ code compiles and passes review ✓ called via this. inside the same class ⚠ request thread blocks on the full send ⚠

The wrong assumption: that the annotation itself does the work, rather than the proxy Spring wraps around external calls to it.

Never call a @Async/@Scheduled method on yourself — route it through a bean
Notice the method being called with this. from inside the same class ↓ a self-call never passes through the Spring-generated proxy that redirects the call to a thread pool Move the method to its own small service (or self-inject with @Lazy) and call it through THAT reference ↓ calling through an injected reference forces the call through the proxy — the only place @Async's logic actually lives The annotation and the actual behavior finally agree again
An annotation on a method is a request to the proxy, not a property of the method itself. @Async and @Scheduled both work because Spring wraps your bean in a proxy at startup; call the method through that proxy — from outside the class, via an injected reference — and the extra behavior runs. Call it as a bare this. reference from inside the same class, and you've walked around the proxy entirely: the plain, un-annotated method body just runs, on the calling thread, as if the annotation were never written.
Think of @Async as a note taped to a receptionist's desk, not a rule burned into the method itself: "always put this caller on hold and have someone call them back." Instructions like that only get followed by whoever answers the phone at reception. Walk directly into a coworker's office and ask them yourself, and there's no receptionist there to intercept anything. It stops being a perfect analogy in one place: a blocked intercom fails loudly and obviously — a self-call doesn't fail at all, it succeeds instantly and quietly, in exactly the wrong way.
You

@Async is right there on the method. Why did this call run synchronously?

The proxy

Because you never went through me. I'm the object Spring actually registered in the container — I'm the one who knows how to hand this off to a thread pool.

this.

And I'm not the proxy. I'm a raw reference to the real object, sitting right next to the method I'm calling — so I called it directly, the plain way, with zero interception.

Spring's container

I only ever get a chance to substitute the proxy in when something asks me for the bean — through constructor or field injection. A this. call never asks me anything.

The mechanism

The proxy only exists between beans. Inside one class, there's no gap left to intercept.

  1. At startup, Spring sees @Async on a method and builds a proxy wrapping the real beanone proxy per bean, built once
  2. Every OTHER bean that gets UserService injected receives a reference to that proxy, not the raw objectinjection is where the substitution happens
  3. An external caller (a controller) calls sendActivationEmailAsync(user) on the injected referencethis is the call that gets intercepted
  4. The proxy submits the real method to a TaskExecutor and returns immediately, before the method body runsthe caller's thread is free at this exact point
  5. Inside UserService, createUser() calls this.sendActivationEmailAsync(user) directlybypasses the proxy entirely — it's a raw reference
  6. The plain method body executes right there, on the calling thread, exactly as if @Async didn't existno exception, no warning — just the wrong behavior

Step 5 is the lesson. Every other step happens through the proxy, which is the only place @Async's thread-hopping logic actually lives. A this. call from inside the same class reaches the real object directly, never touching the proxy, so there's genuinely nothing there to intercept it. This isn't a bug Spring forgot to handle — it's a direct consequence of how Java's dynamic proxies work: they can only intercept calls that arrive from outside the object.

A call that arrives from outside — through the ring — gets intercepted and redirected to a thread pool. A call placed from inside the ring, at the core, using this., never crosses that boundary at all. Same object, same method, same annotation — the only thing that changed is which side of the ring the call started from.

UserService.createUser() calls this.sendActivationEmailAsync(user), and sendActivationEmailAsync is annotated @Async. What actually happens when createUser() runs?

A very natural reading of what an annotation "should" do — attach a behavior to a method, period, regardless of who's calling. That's true for annotations the compiler or reflection process at the call site. @Async isn't one of those; it only does anything through a proxy, and a this. call never reaches the proxy.

Right — and the dangerous part is that nothing fails loudly here. No exception, no log line, no startup warning. The method returns a value (or void) exactly like an ordinary synchronous call, which is exactly what lets this bug survive code review and only surface later as "the endpoint got slower."

This assumes Spring does more static analysis of your code than it actually performs. Detecting a self-call would require inspecting every method body's bytecode at startup for internal invocations — Spring's proxy-based AOP doesn't do that. The proxy gets built correctly; it's simply never invoked for this particular call path, and nothing flags that.

Where you've seen this before

"Only the wrapper gets intercepted" is older than Spring, and shows up anywhere a proxy sits in front of the real thing.

JavaScript's own Proxy object

const p = new Proxy(target, handler) only intercepts operations performed on p. Code that holds a reference to the raw target and calls it directly skips every trap in handler, silently — the exact same shape as a this. call skipping Spring's AOP proxy. Same word, same underlying idea, two unrelated runtimes.

only the wrapper reference gets intercepted

The GoF Proxy/Decorator pattern, by design

Every design-pattern book's Proxy and Decorator patterns work only if callers hold a reference to the wrapper, not the wrapped object. Spring's @Async proxy isn't a special case invented for annotations — it's a textbook application of a pattern that has this exact requirement built in, whether or not any annotation is involved.

callers must hold the wrapper, not the core

Calling a downstream service directly instead of through the gateway

A microservice that calls another service's internal pod address directly, instead of routing through the API gateway or BFF, skips whatever that gateway does on every request — token validation, rate limiting, logging. Same failure shape as the self-call bug: the cross-cutting behavior lives in something you can walk around, not in the destination method itself.

bypass the gateway, skip everything it does
Questions from the back row

Is there any way to make a self-call still go through the proxy?

Yes — the standard fixes all boil down to "call it from outside." Cleanest: move the method to its own small service and inject that. Workable but a little unusual: self-inject with @Autowired @Lazy private UserService self; and call self.sendActivationEmailAsync(user) — @Lazy avoids a circular-dependency failure at startup. Least preferred: grab the live proxy at runtime with AopContext.currentProxy(), which needs exposeProxy=true and directly couples your code to Spring AOP internals.

Does @Transactional have the exact same self-call problem?

Yes — identical mechanism, identical failure. @Transactional, @Async, @Scheduled, @Cacheable, and method-security's @PreAuthorize are all implemented as Spring AOP advice wrapped in a proxy around the bean, so all of them share this exact self-invocation blind spot. A transaction that silently doesn't commit the way you expected from a self-called method is this same bug, wearing a different annotation.

Why doesn't Spring just detect this at compile time and fail the build?

Because that would require a fundamentally different mechanism than the one Spring uses. Proxy-based AOP is built at runtime, around whichever object got registered as the bean — Spring never rewrites your class's bytecode to intercept internal calls. AspectJ compile-time or load-time weaving does handle self-invocation correctly, precisely because it modifies bytecode directly instead of wrapping the object — it's a heavier, opt-in tool because it trades away this simplicity on purpose.

1 — @Async — Running Work in a Background Thread

Without @Async, slow operations (email, PDF generation, external API calls) block the HTTP thread — the client waits. With @Async, Spring runs the method in a thread pool and returns immediately:

Without @Async — HTTP thread blocked
// HTTP thread waits 2+ seconds for email @PostMapping("/register") public ResponseEntity<?> register(@RequestBody UserDto dto) { userService.createUser(dto); emailService.sendWelcome(dto.email()); // ← blocks 2s return ResponseEntity.ok("registered"); // client waits 2+ seconds for a welcome email! }
With @Async — returns in <10ms
@Async // runs on thread pool, not HTTP thread public void sendWelcome(String email) { // runs in background — may take 2 seconds smtpClient.send(email, "Welcome!"); } // Controller returns immediately emailService.sendWelcome(dto.email()); return ResponseEntity.accepted().build();
Enable @Async: add @EnableAsync to your @SpringBootApplication or a @Configuration class. Without it, @Async annotations are silently ignored.

2 — Thread Pool Configuration

The default Spring @Async executor is a single unbounded thread (SimpleAsyncTaskExecutor) — fine for demos, bad in production. Always configure a proper thread pool:

@Configuration @EnableAsync public class AsyncConfig implements AsyncConfigurer { @Override public Executor getAsyncExecutor() { ThreadPoolTaskExecutor exec = new ThreadPoolTaskExecutor(); exec.setCorePoolSize(4); // threads kept alive even when idle exec.setMaxPoolSize(20); // max threads under peak load exec.setQueueCapacity(100); // tasks queued when all core threads busy exec.setThreadNamePrefix("async-"); // visible in thread dumps exec.setRejectedExecutionHandler(new CallerRunsPolicy()); // back-pressure: caller runs if queue full exec.initialize(); return exec; } @Override public AsyncUncaughtExceptionHandler getAsyncUncaughtExceptionHandler() { return (ex, method, params) -> log.error("Async error in {}: {}", method.getName(), ex.getMessage(), ex); // IMPORTANT: @Async void methods swallow exceptions by default — handle them here } }
SettingRule of thumb
corePoolSizeNumber of CPU cores × 2 for IO-bound tasks (email, HTTP); = CPU cores for CPU-bound
maxPoolSizeMax burst capacity — threads beyond core are created when queue is full
queueCapacityBuffer for burst — set to 0 to scale threads immediately (SynchronousQueue behaviour)
RejectedExecutionHandlerCallerRunsPolicy = back-pressure (caller waits); AbortPolicy = throws exception

3 — Returning CompletableFuture from @Async

When you need the result of an async operation (not fire-and-forget), return CompletableFuture<T>. You can then join multiple async tasks in parallel:

@Async public CompletableFuture<PriceQuote> fetchQuote(String supplierId) { PriceQuote quote = supplierApi.getQuote(supplierId); // ~500ms per supplier return CompletableFuture.completedFuture(quote); } // In the service — fire all 3 requests SIMULTANEOUSLY, wait for all to finish public BestQuote findBestPrice(String productId) { CompletableFuture<PriceQuote> q1 = pricingService.fetchQuote("supplier-A"); CompletableFuture<PriceQuote> q2 = pricingService.fetchQuote("supplier-B"); CompletableFuture<PriceQuote> q3 = pricingService.fetchQuote("supplier-C"); // Wait for ALL (parallel execution — ~500ms total instead of ~1500ms) CompletableFuture.allOf(q1, q2, q3).join(); return Stream.of(q1, q2, q3) .map(CompletableFuture::join) .min(Comparator.comparing(PriceQuote::price)) .orElseThrow(); }

5 — @Scheduled — Recurring Background Tasks

Enable scheduling: add @EnableScheduling to your app or config class. Without it, all @Scheduled annotations are silently ignored.

fixedRate

Run every N ms, measured from START of last execution

fixedDelay

Wait N ms after the END of last execution, then run again

cron

Run at specific times using a cron expression
