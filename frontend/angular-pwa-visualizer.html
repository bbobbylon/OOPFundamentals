1. What Is a Progressive Web App?

Installable

Browser prompts "Add to Home Screen." App launches in its own window without the browser chrome. Appears in the OS app drawer.

📱

Offline-Capable

Service worker intercepts fetch requests. Serves cached app shell and assets when there is no network. Shows an offline fallback page for uncached content.

✈️

Push-Enabled

Service worker can receive push messages from your server even when the app is not open. Uses the Web Push protocol with VAPID keys.

🔔
A PWA is not an app store app — it is a regular web app that opts into additional browser capabilities via a service worker and a web app manifest. No special build tools beyond ng add @angular/pwa are required.

Service worker registration

// app.config.ts — added by the schematic
import { provideServiceWorker }
  from '@angular/service-worker';

export const appConfig: ApplicationConfig = {
  providers: [
    provideRouter(routes),
    provideServiceWorker(
      'ngsw-worker.js',  // generated at build time
      {
        enabled: !isDevMode(),  // disabled in dev
        registrationStrategy:
          'registerWhenStable:30000'
          // wait until app is stable, max 30s
      }
    )
  ]
};
Dev mode: Service workers are disabled during ng serve. To test them, build the app (ng build) and serve the dist/ folder with a local HTTP server: npx http-server dist/my-app/browser -p 8080.

4. Service Worker Lifecycle

The service worker goes through four phases. Understanding this explains the "update is ready" prompt and why a hard refresh sometimes doesn't pick up a new version.

install
install event fires
Service worker script is parsed. The install event fires. Angular's NGSW pre-caches the app shell: index.html, main.js, styles.css. While pre-caching, the SW is "installing".
waiting
waiting to activate
If an OLD service worker is already controlling the page, the NEW one waits. The old SW continues serving requests. This is why "update available" prompts exist — NGSW won't silently swap while the user is using the app.
activate
activate event fires
Old tabs are closed / page reloaded. The new SW takes control. The activate event fires. Old caches from the previous version are deleted here.
fetch
fetch events intercepted
Every network request from the page passes through the service worker's fetch handler. NGSW decides: serve from cache (performance strategy) or network first (freshness strategy), based on ngsw-config.json.

5. ngsw-config.json Deep Dive

This file is the brain of NGSW. It defines which files are cached, how long, and with which strategy.

// ngsw-config.json
{
  "$schema": "./node_modules/@angular/service-worker/config/schema.json",
  "index": "/index.html",

  "assetGroups": [
    {
      "name": "app-shell",              // cached at install time
      "installMode": "prefetch",   // downloaded eagerly
      "updateMode": "prefetch",
      "resources": {
        "files": [
          "/favicon.ico",
          "/index.html",
          "/manifest.webmanifest",
          "/*.css",
          "/*.js"
        ]
      }
    },
    {
      "name": "assets",                 // images, fonts — cached lazily
      "installMode": "lazy",        // downloaded when first requested
      "updateMode": "prefetch",
      "resources": {
        "files": ["/assets/**", "/*.(eot|svg|cur|jpg|png|webp)"]
      }
    }
  ],

  "dataGroups": [
    {
      "name": "api-freshness",          // network-first: fresh data
      "urls": ["/api/**"],
      "cacheConfig": {
        "strategy": "freshness",     // try network first
        "maxSize": 100,             // max cached entries
        "maxAge": "3d",             // expire after 3 days
        "timeout": "10s"            // fallback to cache if network slow
      }
    },
    {
      "name": "api-performance",        // cache-first: fast reads
      "urls": ["/api/config/**"],
      "cacheConfig": {
        "strategy": "performance",  // serve from cache if present
        "maxSize": 10,
        "maxAge": "1h"
      }
    }
  ],

  "navigationUrls": [
    "/**",           // all navigation requests → index.html
    "!/**/*.*",      // except files with extensions
    "!/**/__*"       // except test/internal paths
  ]
}

assetGroups — Static Files

Used for app shell files (index.html, JS bundles, CSS) and static assets (images, fonts). Angular hashes these files at build time — when a hash changes, NGSW knows to re-download that file.

installModeBehavior
prefetchDownloaded during SW install — app shell always available offline
lazyDownloaded only when first requested — avoids large install-time cost

dataGroups — API Calls

Used for HTTP API calls. Unlike assetGroups, data is not versioned by hash — it uses TTL (maxAge) and a max entry count instead.

strategyBehavior
freshnessNetwork first → fall back to cache. Best for mutable data.
performanceCache first → fall back to network. Best for read-heavy, slowly changing data.

7. SwUpdate Service — App Updates

Detect and apply updates

@Injectable({ providedIn: 'root' })
export class AppUpdateService {
  private swUpdate =
    inject(SwUpdate);
  private snackBar =
    inject(MatSnackBar);

  constructor() {
    if (!this.swUpdate.isEnabled) return;

    this.swUpdate.versionUpdates
      .pipe(filter(e =>
        e.type === 'VERSION_READY'
      ))
      .subscribe(() => {
        const ref = this.snackBar
          .open('Update available',
               'Reload');
        ref.onAction()
          .subscribe(() => {
            this.swUpdate
              .activateUpdate()
              .then(() =>
                location.reload()
              );
          });
      });
  }
}

versionUpdates event types

Event typeMeaning
VERSION_DETECTEDNew version found on server, starting download
VERSION_READYNew version downloaded, waiting to activate
VERSION_INSTALLATION_FAILEDDownload failed — network error or corrupt files
NO_NEW_VERSION_DETECTEDChecked server, current version is up to date

Manually check for updates

// Call this periodically if desired
async checkForUpdate() {
  try {
    const updateFound =
      await this.swUpdate
        .checkForUpdate();
    console.log(updateFound
      ? 'Update found'
      : 'Already latest');
  } catch (err) {
    console.error('Check failed', err);
  }
}

8. SwPush Service — Push Notifications

Subscribe to push

@Injectable({ providedIn: 'root' })
export class PushService {
  private swPush = inject(SwPush);

  async subscribeToPush() {
    const sub =
      await this.swPush
        .requestSubscription({
          serverPublicKey:
            VAPID_PUBLIC_KEY
          // Generate with:
          // npx web-push generate-vapid-keys
        });

    // Send to your backend
    await this.http
      .post('/api/push/subscribe', sub)
      .toPromise();
  }

  listenForMessages() {
    this.swPush.messages
      .subscribe((msg: any) => {
        console.log('Push received', msg);
      });
  }
}

Push notification flow

  1. Generate VAPID keys: npx web-push generate-vapid-keys
  2. Frontend calls swPush.requestSubscription() with the public key
  3. Browser shows permission prompt to the user
  4. On allow: browser creates a PushSubscription object (endpoint + keys)
  5. Frontend sends the subscription object to your backend via HTTP
  6. Backend stores the subscription in a database
  7. When you want to push: backend calls the endpoint in the subscription using the Web Push protocol + private VAPID key
  8. Browser wakes up the service worker, which fires a push event
  9. NGSW shows a notification — even if the app is closed
Push notifications require HTTPS in production. They also require explicit user permission — never ask for permission on first page load, wait until the user has seen value in your app.

10. Lighthouse PWA Audit

Lighthouse checks a specific set of criteria for "installable" and "PWA optimized." All must pass for a 100 PWA score.

Installability checks

  • HTTPS (or localhost)
  • Service worker registered and active
  • Web app manifest with required fields
  • Manifest has at least one icon ≥144x144 with purpose: any
  • start_url responds while offline

PWA optimized checks

  • theme-color meta tag in HTML
  • Viewport meta tag configured
  • Redirect HTTP to HTTPS
  • Custom splash screen (manifest background_color + icons)
  • Maskable icon present

11. Offline Fallback Page

When the user is offline and requests a URL that is NOT in the cache, serve a custom offline fallback page instead of the browser's default error.

Create src/offline.html

<!-- src/offline.html -->
<!doctype html>
<html>
<head>
  <title>Offline</title>
  <meta name="theme-color" content="#dd0031">
</head>
<body>
  <h1>You're offline</h1>
  <p>Check your connection and try again.</p>
  <button onclick="location.reload()">Retry</button>
</body>
</html>

Add to ngsw-config.json

// In the app-shell assetGroup:
{
  "name": "app-shell",
  "installMode": "prefetch",
  "resources": {
    "files": [
      "/index.html",
      "/offline.html",  // add this
      "/*.css",
      "/*.js"
    ]
  }
}

// Update navigationUrls to route offline
// navigations to offline.html:
"navigationUrls": [
  "/**",
  "!/**/*.*",
  "!/**/__*"
]
NGSW automatically serves index.html for all navigation requests that match navigationUrls. For navigations that miss the cache while offline, the browser shows a network error — serve offline.html via a custom SW fetch handler if you need a custom page.
