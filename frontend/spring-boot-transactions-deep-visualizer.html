@Transactional — Propagation & Isolation

The two settings everyone gets wrong. What "a transaction inside a transaction" really does, why a caught exception can still doom your commit, and exactly what each isolation level protects you from.

1. First: how @Transactional even works (the proxy)

It's a proxy wrapping your bean

Spring doesn't change your method. It wraps your @Service in a proxy. Calls go through the proxy, which opens a transaction, calls your real method, then commits or rolls back.

// what the proxy effectively does:
Object invoke(method, args) {
  tx = txManager.getTransaction(); // BEGIN
  try {
    result = method.invoke(target, args); // your code
    txManager.commit(tx);              // COMMIT
  } catch (RuntimeException e) {
    txManager.rollback(tx);            // ROLLBACK
    throw e;
  }
  return result;
}

⚠️ The self-invocation gotcha

Because the magic lives in the proxy, calling a transactional method from within the same class (this.x()) bypasses the proxy — the annotation is silently ignored.

@Service
class OrderService {
  place() {
    this.audit(); // ❌ direct call — NO new tx!
  }
  @Transactional(propagation = REQUIRES_NEW)
  void audit() { … } // REQUIRES_NEW ignored here
}

Fixes: move audit() to another bean (call that), self-inject the proxy, or use TransactionTemplate. Also: only public methods are advised by default.

3. The takeaways from that simulator

    

      

        
REQUIRED + caught exception = the silent killer

        
When inner joins the outer's transaction (REQUIRED) and throws, Spring marks the shared transaction rollback-only. Even if the outer catches the exception and tries to commit, Spring refuses and throws:

        
UnexpectedRollbackException:
  Transaction silently rolled back because
  it has been marked as rollback-only

        
Lesson: catching an exception does not "save" a write if it happened in the same physical transaction. You need REQUIRES_NEW or NESTED for the inner work to survive independently.

6. Rollback rules — the other thing that surprises people

    

      

        
By default, only unchecked exceptions roll back

        
Spring rolls back on RuntimeException and Error — but commits on a checked Exception. This trips everyone up at least once.

        
@Transactional
void transfer() throws IOException {
  repo.debit();
  throw new IOException(); // ✅ COMMITS the debit!
}

      

      

        
Override it explicitly

        
// roll back on a checked exception too:
@Transactional(rollbackFor = IOException.class)

// or: don't roll back on a specific runtime one:
@Transactional(noRollbackFor = ValidationException.class)

// read-only hint (lets the DB/JPA optimize):
@Transactional(readOnly = true)

        
Mark query-only service methods readOnly = true — Hibernate skips dirty checking and the driver/DB can optimize.

8. One-sentence recap

    

      
🔐 @Transactional is a proxy that begins a transaction and commits or rolls back around your method — propagation decides whether a nested call joins (REQUIRED), runs independently (REQUIRES_NEW), or uses a savepoint (NESTED); isolation decides which concurrent-read anomalies you're protected from; rollback happens on runtime exceptions only unless you say rollbackFor — and none of it applies when you call the method on this.
