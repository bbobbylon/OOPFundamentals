Provisioning & Identity Lifecycle

PingIDM (formerly ForgeRock Identity Management) automates the full identity lifecycle — from hire to terminate — across all enterprise systems.

What is PingIDM provisioning — and how does SCIM automate the full identity lifecycle across every connected system simultaneously?

PingIDM (formerly ForgeRock Identity Management / OpenIDM) is the lifecycle engine of the Ping platform. While PingAM handles authentication (proving who you are right now), PingIDM handles the entire span of an identity's existence in the organization: how accounts are created, how they change over time, and how they are securely deprovisioned. Without automated provisioning, these are manual processes — IT tickets, spreadsheets, and inevitably orphaned accounts that become security vulnerabilities. The Joiner-Mover-Leaver model: Joiner = new hire event from HR (SAP, Workday, BambooHR) triggers account creation in AD, PingDS, Salesforce, GitHub, etc. Mover = role or department change triggers entitlement updates across all connected systems. Leaver = termination triggers immediate deprovisioning in the correct order (revoke tokens first, then disable accounts). The "Leaver" step is the security-critical one — orphaned accounts are the #1 source of insider threat and audit findings. Managed Objects: PingIDM stores identities as JSON objects in its repository (typically PostgreSQL). A managed user object contains all the attributes about a person: profile data, account status, roles, linked accounts. All CRUD operations go through the managed object layer. Connectors: the integration glue. PingIDM ships connectors for AD/LDAP, Salesforce, ServiceNow, Google Workspace, AWS IAM, and dozens more. Each connector maps IDM attributes to the target system's schema. Custom connectors can be built with the Connector Framework. SCIM (System for Cross-domain Identity Management): the REST API standard for user provisioning (RFC 7643/7644). PingIDM exposes a /scim endpoint for apps to provision users (POST /scim/Users), update them (PATCH), and deprovision (DELETE). This is the same protocol cloud apps use — Salesforce, GitHub, Slack all accept SCIM provisioning. Sync and Reconciliation: live sync catches changes in real time (AD event listener); reconciliation is a scheduled bulk comparison to catch drift (if an account was manually created in AD that IDM doesn't know about, reconciliation finds and handles it). The mapping drives what IDM does when it finds a new, changed, or deleted object in the source.

SCIM API calls

// PingIDM exposes SCIM 2.0 at /openidm/scim // CREATE user (Joiner): POST /openidm/scim/Users Authorization: Bearer <admin-token> Content-Type: application/json { "schemas": ["urn:ietf:params:scim:schemas:core:2.0:User"], "userName": "bobby.oliver@example.com", "name": {"givenName":"Bobby","familyName":"Oliver"}, "emails": [{"value":"bobby@example.com","primary":true}], "active": true } // IDM creates: managed user → AD account → Salesforce user // UPDATE role (Mover): PATCH /openidm/scim/Users/{id} { "Operations": [ {"op":"replace","path":"department","value":"Engineering"} ] } // IDM: updates AD group memberships + Salesforce profile // DELETE (Leaver): DELETE /openidm/scim/Users/{id} // IDM: revoke tokens → disable AD → disable Salesforce → audit log

Mapping + connector config

// IDM sync mapping (JSON config in conf/sync.json): { "mappings": [{ "name": "systemHRDB_managedUser", // mapping name "source": "system/HRDB/employees", // Workday connector "target": "managed/user", // IDM managed user "properties": [ // attribute mapping: source field → target field { "source": "employeeId", "target": "employeeNumber" }, { "source": "email", "target": "mail" }, { "source": "department", "target": "department", // transform script (Groovy/JavaScript): "transform": "source.department?.toLowerCase()" }, { "source": "status", "target": "accountStatus", "condition": { "type": "text/javascript", "source": "source.status === 'ACTIVE'" } } ], // what to do when HR source has UNLINK (employee terminated): "onUnlink": [{ "name": "DISABLE"}], // what to do on source DELETE: "onSourceMissing": [{ "name": "DELETE"}] }] }

Reconciliation + live sync

// TWO mechanisms to keep IDM in sync with source systems: // 1. LIVE SYNC (event-driven, near real-time): // IDM polls source connector for changes since last run // Best for: catching changes quickly (within minutes) // Config: POST /openidm/recon?_action=performAction // Or scheduled: {"type":"cron","schedule":"0 */5 * * * ?"} // every 5 min // 2. RECONCILIATION (bulk, periodic): // Full comparison: all source objects vs all target objects // Catches: manually created accounts, drift, orphans // Situations handled: // SOURCE → TARGET (new in source, not in target) → CREATE // CONFIRMED (exists in both, compare attributes) → UPDATE if changed // TARGET → SOURCE (in target, not in source) → UNLINK/DELETE // AMBIGUOUS (one source matches multiple targets) → alert // Trigger reconciliation via REST: POST /openidm/recon?_action=recon {"mapping":"systemHRDB_managedUser"} // Returns a reconciliation ID; check status: GET /openidm/recon/{reconId}

In CIAM / Your Job: PingIDM provisioning is core to your CIAM work. Your application receives SCIM events from PingIDM when users are created, updated, or deprovisioned — your Spring Boot service must handle these webhooks correctly (idempotently, in the right order). The hardest part is the "Leaver" flow: you must guarantee that deprovisioning operations happen atomically — if your Spring Boot service fails to receive the SCIM DELETE (network partition), IDM's retry mechanism will retry until acknowledged. Test the unhappy path explicitly. The most common audit failure is orphaned accounts — document your reconciliation schedule and what happens when source-missing is detected.

Hire / Onboard — PingIDM automates:

  • Source: HR system (Workday, SAP) fires a "new hire" event
  • PingIDM triggers a provisioning workflow
  • Creates account in Active Directory (username, password, group memberships)
  • Creates account in PingDirectory (LDAP)
  • Provisions Microsoft 365 mailbox and Teams
  • Grants default role-based application access based on department/title
  • Sends welcome email with credentials / onboarding link
  • Target systems updated via SCIM, REST, or native connectors

Access Request — Self-service portal:

  • User opens PingIDM self-service portal
  • Searches for and requests access to specific applications or groups
  • PingIDM routes the request to approval workflow (manager, resource owner)
  • Approver approves/denies via email link or portal
  • On approval: PingIDM automatically provisions the access in target systems
  • Audit log entry created for compliance (who approved, when, what)

Role Change (Transfer / Promotion):

  • HR system updates employee record (department change, new title)
  • PingIDM detects change via reconciliation or event-based sync
  • Evaluates new role against access policies
  • Revokes previous role's access that no longer applies
  • Grants new role's access across all connected systems
  • Enforces Separation of Duties — prevents conflicting access combinations

Access Review / Recertification:

  • Scheduled campaign (quarterly, annual) or triggered by compliance requirement
  • PingIDM generates access review tasks for each manager
  • Manager reviews: does this user still need this access?
  • Certify (keep) or revoke each entitlement
  • Revoked items automatically removed from target systems
  • Completion tracked — non-respondent accounts can be auto-revoked or escalated

Termination — Immediate or scheduled deprovision:

  • HR terminates employee → PingIDM event fires
  • Immediate: all Active Directory accounts disabled + Entra ID accounts blocked
  • Microsoft 365 license reclaimed within hours
  • All application accounts disabled or deleted across connected systems
  • Active sessions revoked (PingFederate, PingAccess)
  • VPN, physical badge access — notified or automated via connectors
  • Data retention: mailbox, files preserved for legal hold if required

3 — PingIDM Connectors

Connectors are adapters that translate PingIDM operations into each target system's API or protocol. Click to learn more:

Active Directory / LDAP

Connector: LDAP / AD Connector
Creates/disables users, manages group memberships via LDAP protocol. Bidirectional sync — changes in AD can flow back to PingIDM. The most common enterprise connector.

Entra ID (Azure AD)

Connector: Graph API Connector
Provisions users and groups to Microsoft Entra ID via Microsoft Graph REST API. Used when your org uses both PingIDM for lifecycle management and Entra ID for cloud authentication.

Salesforce

Connector: Salesforce Connector
Creates/deactivates Salesforce users, assigns profiles and permission sets. Uses Salesforce REST/SOAP APIs or SCIM endpoint.

Database (JDBC)

Connector: Database Table Connector
Reads/writes user records directly to a database table. Used when your target application stores users in an RDBMS (MySQL, PostgreSQL, Oracle) without an API.

REST / Generic HTTP

Connector: Scripted REST Connector
Calls any REST API using Groovy scripts. Use for custom internal applications or SaaS systems without a pre-built connector. Flexible but requires scripting.

CSV / Flat File

Connector: CSV File Connector
Reads from or writes to CSV files. Used for batch HR exports (daily Workday CSV dump), legacy system integration, or simple one-way provisioning.

4 — Reconciliation: Keeping Systems in Sync

Reconciliation scans the source (HR system) and target (Active Directory) and resolves discrepancies. Run on a schedule (nightly) or on-demand:

Situation FoundReconciliation Action
Source: Alice exists. Target: Alice missing.CREATE — provision Alice in the target system.
Source: Alice's email changed. Target: old email.UPDATE — sync the change to the target.
Source: Alice terminated. Target: Alice active.DISABLE/DELETE — deprovision Alice in the target.
Source: Alice missing. Target: Alice exists.Policy-based: IGNORE, report, or delete orphaned account.
Source and Target match.LINK — confirm the mapping is correct, no action needed.
