Directives — Structural & Attribute

Directives are how Angular extends HTML. Structural directives change the DOM tree (add/remove elements). Attribute directives change appearance or behavior of an existing element. Master *ngIf, *ngFor, ngClass, ngStyle and you can build most UIs.

🧭 What are directives? Structural vs attribute — the key difference

A directive is a class that adds behaviour to an element in the DOM. Angular has three flavours: components (directives with a template) and two template-only kinds. Structural directives change the DOM structure — they add, remove, or replace elements (the * prefix, or the modern @if/@for). Attribute directives change the look or behaviour of an element that's already there, without touching the tree (ngClass, ngStyle, a custom [appHighlight]).

  • *ngIf="false" (or @if) means the element does not exist in the DOM — its child component is destroyed, ngOnDestroy runs, change detection skips it, form controls deregister.
  • That's fundamentally different from CSS display:none, where the element still exists, keeps its state, and is merely invisible.
  • The * is sugar: *ngIf="x" desugars to an <ng-template [ngIf]="x"> that Angular stamps in only when the condition holds.
  • Modern Angular (17+): prefer built-in @if / @for / @switch — no imports, better type-narrowing, faster.
  • Always provide track (old trackBy) in a loop so Angular reuses DOM nodes and only the changed rows re-render.

Structural — changes the DOM

Add / remove / replace elements. @if (user) { … } @else { … }, @for (u of users; track u.id) { … }, @switch. Legacy: *ngIf, *ngFor, *ngSwitch. The element's very existence is conditional — render it, or it isn't in the DOM at all.

Attribute — modifies an element

Change appearance or behaviour in place. [ngClass]="{ active: isOn }", [ngStyle]="{ color: c }", and custom ones like an [appHighlight] that sets a background on hover via @HostListener. No nodes are added or removed.

In CIAM / Angular:@if (auth.hasRole('CIAM_ADMIN')) makes the "Delete user" button truly absent for non-admins (not just hidden — so there's no handler to exploit). A custom *appHasRole structural directive reuses that gate across every template — but it's UX only; the real authorization is still Spring @PreAuthorize on the server.

*ngIf — conditionally render

Live demo

isLoggedIn = false
Please log in to continue.

The code

// .ts
isLoggedIn = false;
toggle() { this.isLoggedIn = !this.isLoggedIn; }

<!-- .html — old syntax -->
<div *ngIf="isLoggedIn">
  Welcome back!
</div>
<div *ngIf="!isLoggedIn">
  Please log in.
</div>

<!-- with else block -->
<div *ngIf="isLoggedIn; else loginBlock">
  Welcome!
</div>
<ng-template #loginBlock>
  Please log in.
</ng-template>

Key insight: when *ngIf is false, the element is not in the DOM at all — not just hidden. That's different from [hidden] or display: none, which keep the element but hide it. For expensive components, *ngIf saves you the cost of even creating them.

*ngFor — loop over a collection

Live demo — a todo list

The code

// .ts
todos = [
  { id: 1, text: 'Learn directives', done: false },
  { id: 2, text: 'Build a todo app', done: true }
];

<!-- .html -->
<div *ngFor="let t of todos; let i = index; trackBy: trackById">
  {{ i + 1 }}. {{ t.text }}
</div>

// Local vars you can grab:
//   let i = index    // 0-based position
//   let first = first, let last = last
//   let even = even, let odd = odd

// trackBy — CRITICAL for performance
trackById(index, item) { return item.id; }

Always add trackBy for lists that change. Without it, Angular re-creates every DOM node when the array reference changes. With trackBy returning a stable id, Angular only touches the items that actually changed — orders of magnitude faster for big lists.

ngClass & ngStyle — dynamic styling

Live demo — change priority

This box's color, scale & weight are bound to priority.

The code

// .ts
priority: 'low' | 'med' | 'high' = 'med';

<!-- ngClass — toggle classes by object -->
<div [ngClass]="{
    'bg-green': priority === 'low',
    'bg-amber': priority === 'med',
    'bg-red':   priority === 'high'
  }">...</div>

<!-- ngStyle — inline styles from an object -->
<div [ngStyle]="{
    'transform': priority === 'high' ? 'scale(1.05)' : 'scale(1)',
    'font-weight': priority === 'high' ? 700 : 400
  }">...</div>

<!-- shorthand — single class / style -->
<div [class.active]="isActive"></div>
<div [style.color]="errorColor"></div>

[ngSwitch] — when *ngIf gets messy

<!-- Instead of three *ngIfs -->
<div [ngSwitch]="user.role">
  <admin-dashboard *ngSwitchCase="'admin'" />
  <editor-dashboard *ngSwitchCase="'editor'" />
  <viewer-dashboard *ngSwitchCase="'viewer'" />
  <guest-dashboard *ngSwitchDefault />
</div>

🆕 New control flow (Angular 17+) — @if, @for, @switch

Angular 17 added a brand-new template syntax. Built into the compiler — no CommonModule import needed, faster, with proper else if and an empty block for loops. The old *ngIf / *ngFor still work but new code should use this.

Old way (still works)

<div *ngIf="loading">Loading...</div>
<div *ngIf="!loading && users.length">
  <div *ngFor="let u of users">
    {{ u.name }}
  </div>
</div>
<div *ngIf="!loading && !users.length">
  No users found.
</div>

New way — cleaner & faster

@if (loading) {
  <div>Loading...</div>
} @else if (users.length) {
  @for (u of users; track u.id) {
    <div>{{ u.name }}</div>
  } @empty {
    <div>No users found.</div>
  }
} @else {
  <div>Something went wrong.</div>
}

Note: track is required in @for (not optional like in *ngFor's trackBy). The new @empty block fires when the collection is empty — no more separate *ngIf for that case.

@switch — the new control flow's switch

@switch (user.role) {
  @case ('admin')  { <admin-dashboard /> }
  @case ('editor') { <editor-dashboard /> }
  @case ('viewer') { <viewer-dashboard /> }
  @default           { <guest-dashboard /> }
}

@defer — lazy-load parts of a template

Brand new in Angular 17 — drop a piece of UI into a @defer block and Angular will lazy-load that component's code only when the trigger fires. Huge win for initial bundle size. 

@defer (on viewport) {                       // when scrolled into view
  <heavy-chart [data]="data" />
} @placeholder {                              // shown until trigger
  <div>Chart will load when you scroll...</div>
} @loading (minimum 500ms) {                  // shown while loading
  <spinner />
} @error {                                     // shown if load fails
  <div>Failed to load chart.</div>
}

// Other triggers:
//   on idle     — when browser is idle
//   on hover    — pointer hovers an element
//   on interaction — first click/keydown
//   on timer(2s)    — after a delay
//   when condition  — when a condition is true

Why is there an asterisk before *ngIf and *ngFor?

The * is sugar. *ngIf="cond" tells Angular: "wrap this element in an <ng-template> and apply the ngIf directive to it." This is the desugared form: 

<!-- What you write -->
<div *ngIf="isLoggedIn">Hello</div>

<!-- What it desugars to -->
<ng-template [ngIf]="isLoggedIn">
  <div>Hello</div>
</ng-template>

Why this matters: only ONE structural directive per element. <div *ngIf="x" *ngFor="..."> is illegal. Wrap in a <ng-container> (a wrapper that doesn't add a DOM element) or use @if / @for which can nest freely.

<ng-container> — group without an extra DOM element

<!-- Want *ngIf around a group of elements without adding a wrapper div -->
<ng-container *ngIf="user">
  <h3>{{ user.name }}</h3>
  <p>{{ user.email }}</p>
</ng-container>

<!-- Or to stack two structural directives -->
<ng-container *ngFor="let u of users">
  <div *ngIf="u.active">{{ u.name }}</div>
</ng-container>

Renders nothing itself — just a logical grouping. Useful for keeping the DOM clean and for stacking structural directives.

Custom attribute directive — the one you'll write

A directive is a class with the @Directive decorator. The classic example: highlight a paragraph yellow on hover. 

// highlight.directive.ts
import { Directive, ElementRef, HostListener, Input } from '@angular/core';

@Directive({
  selector: '[appHighlight]',           // match elements with this attribute
  standalone: true
})
export class HighlightDirective {
  @Input('appHighlight') color = 'yellow';

  constructor(private el: ElementRef) {}

  @HostListener('mouseenter') onEnter() {
    this.el.nativeElement.style.backgroundColor = this.color;
  }
  @HostListener('mouseleave') onLeave() {
    this.el.nativeElement.style.backgroundColor = '';
  }
}

<!-- usage -->
<p appHighlight>default yellow on hover</p>
<p [appHighlight]="'lightblue'">custom color</p>

@HostListener listens for events on the element the directive is attached to. ElementRef gives you the raw DOM node — useful, but prefer Renderer2 for SSR safety in real apps.

hostDirectives — compose behaviors like mix-ins (Angular 15+)

hostDirectives lets a component (or directive) apply other directives to itself without a wrapper element. It's the Angular answer to multiple inheritance for DOM behaviors — each directive stays focused and reusable.

Reusable behavior directives

// click-trackable.directive.ts
@Directive({ selector: '[appClickTrack]', standalone: true })
export class ClickTrackDirective {
  @Input() appClickTrack = ''; // event name
  @HostListener('click') track() {
    analytics.event(this.appClickTrack);
  }
}

// tooltip.directive.ts
@Directive({ selector: '[appTooltip]', standalone: true })
export class TooltipDirective {
  @Input() appTooltip = '';
  // shows/hides a tooltip on the host
}

Applied via hostDirectives

@Component({
  selector: 'app-cta-button',
  standalone: true,
  template: `<ng-content />`,
  // both behaviors live on <app-cta-button>
  hostDirectives: [
    {
      directive: ClickTrackDirective,
      inputs: ['appClickTrack']   // forward the input
    },
    {
      directive: TooltipDirective,
      inputs: ['appTooltip']
    }
  ]
})
export class CtaButtonComponent {}

<!-- usage: both directives apply -->
<app-cta-button
  appClickTrack="signup_click"
  appTooltip="Create account">
  Sign up
</app-cta-button>

The button doesn't extend these classes — it hosts them. Each directive is independent, testable alone, and can be mixed onto any component. Angular Material uses this pattern extensively for CDK behaviors (focusable, hoverable, etc.).

Custom structural directive — writing your own *appUnless

Structural directives add or remove DOM elements by working with a TemplateRef (the block of HTML to clone) and a ViewContainerRef (where to stamp it). The * prefix is sugar that desugars to a microsyntax.

How * desugars

<!-- what you write -->
<p *ngIf="condition">hello</p>

<!-- what Angular sees -->
<ng-template [ngIf]="condition">
  <p>hello</p>
</ng-template>

<!-- key: the * wraps the element in an
     ng-template and passes the expression
     as an @Input to the directive -->

Writing *appUnless

@Directive({
  selector: '[appUnless]', standalone: true
})
export class UnlessDirective {
  private hasView = false;
  constructor(
    private tpl: TemplateRef<any>,
    private vc: ViewContainerRef
  ) {}

  @Input() set appUnless(cond: boolean) {
    if (!cond && !this.hasView) {
      this.vc.createEmbeddedView(this.tpl);
      this.hasView = true;
    } else if (cond && this.hasView) {
      this.vc.clear();
      this.hasView = false;
    }
  }
}
<!-- usage -->
<p *appUnless="isLoggedIn">Please log in.</p>

When to write one: usually you don't — @if / @for cover almost everything. But if you need custom iteration (a paginated list, infinite scroll, drag-reorder), a structural directive is the right abstraction: it controls exactly which views exist in the DOM at any moment.

Mental model — three kinds of directives

🧱 Components

Directives with a template. The kind you write 95% of the time. @Component extends @Directive.

🌲 Structural directives

Change the DOM tree: add, remove, or move elements. Always prefixed with *. *ngIf, *ngFor, *ngSwitchCase — and the new @if, @for, @switch replace them.

🎨 Attribute directives

Change the appearance or behavior of an existing element. [ngClass], [ngStyle], [ngModel], or any you write yourself.

🌱 New to directives? It's "behavior you stick on an element."

A directive is a bit of behavior you attach to an HTML element by writing it like an attribute. There are three flavors, and you've already used all of them:

  • Components — a directive that also has a template. (Yes, a component is a directive with a view.)
  • Structural — they add or remove elements: *ngIf, *ngFor, and the modern @if/@for. The * is your hint that the DOM is being restructured.
  • Attribute — they change an existing element: [ngClass], [ngStyle], or one you write like [appHighlight].

So "directive" isn't an exotic thing — it's the umbrella word for "the stuff you put on an element to make it do something."

🧠 Expert corner — desugaring, the new control flow, and writing your own

  • The * is sugar for <ng-template>. *ngIf="x" desugars to <ng-template [ngIf]="x"> — that's why a structural directive can hold (and re-create) a chunk of DOM.
  • Built-in control flow (v17+) largely replaces the legacy directives. @if/@for/@switch are block syntax baked into the compiler — better type-narrowing, no CommonModule import, and faster. @for requires a track expression (the new, mandatory trackBy).
  • A custom attribute directive is @Directive({selector:'[appHighlight]'}) + ElementRef/Renderer2 to touch the host, with @HostListener/@HostBinding for events and bound properties.
  • Directive composition (hostDirectives) lets a component apply directives to its own host — reuse behavior without inheritance.
  • Selectors are CSS selectors. [appHighlight], button[appBusy], .card — the same matching engine the browser uses.
  • CIAM tie-in. A structural *appHasRole="'admin'" directive removes UI a user can't use — convenient UX, but remember it's only hiding; the Spring server is the real gate. See Custom Directives and Built-in Control Flow.
