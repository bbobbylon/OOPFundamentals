Cloud Storage — Buckets, Storage Classes & Signed URLs

A bucket is a globally-unique-named container holding objects at a chosen location and storage class. Access is granted through IAM roles (uniform, recommended) or delegated with signed URLs — time-boxed, cryptographically-signed links that need no GCP credentials to use.

🪣 What is Cloud Storage — and why do storage classes, signed URLs, and Uniform access matter?

Cloud Storage is GCP's object store — the service behind user uploads, backups, static websites, ML training data, and audit exports. The hierarchy is flat: a bucket (globally-unique name, assigned a location at creation — region, dual-region, or multi-region, which drives both latency and price) holds objects identified by a key that can contain / for a folder-like illusion, exactly like every other object store. Two decisions dominate real usage and the ACE exam. First, how do callers get in? The modern, recommended default is Uniform bucket-level access — IAM roles evaluated at the bucket (or with conditions, a path prefix) with no legacy per-object ACLs to reason about. When a caller has no GCP identity at all — a browser uploading a photo, a partner system fetching a file — you mint a signed URL: a time-limited, cryptographically-signed link generated via a service account's signing key (through the IAM Credentials API's signBlob, no private key file needed on modern setups). Second, what does storage cost? Every object sits in a storage class: Standard (frequent access, no minimum stay), Nearline (30-day minimum, monthly access pattern), Coldline (90-day minimum, quarterly access), and Archive (365-day minimum, yearly access, cheapest to hold). Deleting or downgrading before a class's minimum stay triggers an early-deletion charge — Object Lifecycle Management rules move or delete objects automatically by age or condition, which is how "keep for 7 years" retention becomes infrastructure instead of a spreadsheet reminder.

  • Bucket → object — the bucket name is global (DNS-visible); the location is fixed at creation and cannot be changed later.
  • Two doors — IAM role (best, identity-bound) or a signed URL (delegated, expiring, no identity required to use).
  • Storage classes trade cost vs minimum stay — Standard (none) → Nearline (30d) → Coldline (90d) → Archive (365d); all stay online (unlike AWS Glacier's offline tiers), only price and early-deletion fees change.
  • Lifecycle rules automate tiering — age or condition-based rules transition or delete objects; this is the exam's favorite cost question.
  • Public Access Prevention is the guardrail — blocks allUsers/allAuthenticatedUsers grants outright, even if someone tries to add them via IAM.

The CLI happy path

# bucket with uniform access, region us-central1 gcloud storage buckets create \ gs://ciam-invoices-prod \ --location=us-central1 \ --uniform-bucket-level-access # upload with your gcloud identity gcloud storage cp 2026-06.pdf \ gs://ciam-invoices-prod/invoices/

AWS comparison

Cloud Storage ≈ S3. Buckets are globally unique flat namespaces in both. Storage classes ≈ S3 storage classes (Standard≈Standard, Nearline≈Standard-IA, Coldline≈Glacier, Archive≈Glacier Deep Archive) — but GCP classes stay online the whole time; only AWS Glacier goes fully offline. Signed URLs ≈ presigned URLs (near-identical mechanism). Uniform bucket-level access ≈ disabling ACLs + relying on bucket policy/IAM only.

Spring Boot comparison

The SDK pattern mirrors a repository: Storage client (≈ NamedParameterJdbcTemplate — one per project) → BlobId/BlobInfo (≈ a row's key + metadata) → storage.create()/storage.signUrl() (≈ insert/select). GoogleCredentials.getApplicationDefault() plays the role your JWT filter plays in reverse: it acquires a token (the VM/Cloud Run/GKE service account locally via ADC, or your gcloud auth on a laptop) instead of validating one.

CIAM in production: the standard pattern for user file uploads in an identity-aware app: the SPA never gets a service account key. Your Spring API validates the user's JWT, authorizes, then calls the IAM Credentials API's signBlob using the API's own runtime service account to mint a V4 signed URL scoped to exactly one object with a 10-minute expiry, and hands the URL to the browser. The signature is tied to the signing service account's identity, so access is revocable by removing that service account's role — no shared secret, no downloaded JSON key anywhere. That is the API→form upload recipe on the recipes pages, done the GCP way.

The problem

Uniform bucket-level access is the setting this very page calls the best practice — and turning it on quietly starts a clock most teams never notice is running.

You followed the recommended default, and 91 days later you can't undo it

A team creates gs://ciam-invoices-prod with --uniform-bucket-level-access, exactly the way the CLI happy path above shows it — because it's the modern, recommended default, and there's no reason to think twice about a security improvement. Six months later, an old on-prem batch job from a partner integration needs read access to exactly one object. That job only understands per-object ACLs; it was written years before Uniform access existed and nobody is rewriting it this quarter.

Cloud Storage gives you a genuine 90-day grace window after enabling Uniform bucket-level access, during which the bucket privately keeps its old ACL state and gcloud storage buckets update --no-uniform-bucket-level-access is a real, working command. But once those 90 days pass, Google's own documentation is explicit: you can no longer disable Uniform bucket-level access on that bucket. Ever. The bucket that "just needed a modern access setting" can no longer support per-object ACLs, permanently — and the fix isn't flipping the setting back, it's standing up a brand-new bucket and migrating every object into it.

The one-sentence rule. A setting documented as "the modern default" can still be a one-way door with a countdown attached — read the reversibility window before you flip it, not after a legacy caller needs the thing it removed.

The mechanism

Follow one bucket from the day the setting is flipped to the day a legacy caller discovers the door has already closed.

  1. Bucket created with --uniform-bucket-level-access — day 0 of the reversibility windowday 0
  2. For 90 days, the bucket privately keeps its pre-existing object ACL state, in case you switch backgrace period
  3. During the window, gcloud storage buckets update --no-uniform-bucket-level-access is a real, working commandreversible
  4. Day 91 arrives with no action taken — Cloud Storage permanently discards the tracked ACL state for this bucketwindow closes
  5. A legacy consumer that only speaks per-object ACLs requests access on day 180new requirement
  6. The same --no-uniform-bucket-level-access command that would have worked on day 60 now fails outright — the bucket is permanently Uniformpermanent

Step 4 is the point of no return, and it happens with zero signal. No email, no console banner, nothing about the bucket's behavior changes that day — it keeps serving requests exactly as it did on day 89. The only thing that's different is a decision you no longer get to make.

Day 0: Uniform bucket-level access enabled — the recommended default
Days 1–90: grace period — the bucket still privately remembers its old ACLs, and switching back still works
Day 91 onward: ACL state is permanently discardedFine-grained access can never be re-enabled on this bucket again — a new bucket and a full object migration is the only fix left

Reading these rings from the outside in is reading a clock, not a hierarchy: the outer ring is where every bucket starts, the middle ring is the only stretch where the decision is still yours, and the core is where it becomes permanent — quietly, with nothing about the bucket itself visibly changing.

There's no autoreset and no cycle here — this is a one-way transition, not a timer that loops back around. Past day 90, the bucket is permanently Uniform, indefinitely, with no expiration on that state.

Where you have seen this before

"Framed as a default, actually a one-way door" is a shape that shows up anywhere a platform quietly trades reversibility for simplicity.

AWS S3 Object Lock in Compliance mode

Enable Object Lock in Compliance mode on an S3 bucket and the retention it imposes cannot be shortened or removed by any principal — not even the AWS account root user — for the entire retention period. GCP's Uniform access at least offers a 90-day grace window; S3 Compliance mode is the same one-way-door shape with no window at all.

an even harsher version of the identical trade

A mobile app's bundle identifier

Choosing com.acme.app as an iOS or Android package identifier feels like any other config value during setup — until the app is published. After the first store submission, that identifier is permanent; changing it means shipping what both platforms treat as an entirely new app, losing reviews, install counts, and update continuity.

a setting chosen early, locked in by a later event outside the setting itself

A Certificate Transparency log entry

The moment a TLS certificate is issued, it's published into a public, append-only Certificate Transparency log — and it stays there forever, even after the certificate is revoked five minutes later for having the wrong name on it. Revocation undoes the certificate's validity; nothing undoes the log entry.

revocation fixes the danger, not the permanent record

1. Storage classes: the price ladder every object sits on

ClassStorage costAccess costMinimum stayAvailabilityUse for
Standardhighestlowest—online, ms latencyactive data, files being served now
Nearlinelowerhigher30 daysonline, ms latencymonthly backups, recent invoices
Coldlinelower stillhigher still90 daysonline, ms latencyquarterly-access data, disaster recovery copies
Archivelowesthighest365 daysonline, ms latencycompliance retention, "keep 7 years" data
Every class stays online — that's the exam trap, and it's the opposite of AWS. Unlike AWS Glacier (which goes fully offline and needs hours to rehydrate), GCP's Archive class is still readable in milliseconds — you just pay the highest per-GB retrieval fee and eat an early-deletion charge if you touch it before the 365-day minimum. There is no "rehydration wait" step in GCP Cloud Storage. Any question implying an object "must be restored before reading" is describing AWS Glacier, not GCP Archive.

2. The two doors, ranked

# 1️⃣ BEST — IAM role bound to a principal (no secrets at all)
gcloud storage buckets add-iam-policy-binding gs://ciam-invoices-prod \
  --member="serviceAccount:api-runtime@ciam-prod.iam.gserviceaccount.com" \
  --role="roles/storage.objectViewer"

# 2️⃣ DELEGATED — V4 signed URL: scoped, expiring, revocable via the signer's role
gcloud storage sign-url gs://ciam-invoices-prod/invoices/2026-06.pdf \
  --impersonate-service-account=api-runtime@ciam-prod.iam.gserviceaccount.com \
  --duration=10m --http-verb=GET

# AVOID — downloaded JSON service-account keys: a static, non-expiring secret
# prefer Workload Identity Federation / attached service accounts instead
Signed URLs are signed by a service account's identity, not a bucket secret. A V4 signed URL is produced by calling the IAM Credentials API's signBlob using whichever service account is impersonated — on Cloud Run/GKE/Compute Engine that's the attached runtime service account via Application Default Credentials, so no private key file ever touches disk. Revoke the signing service account's roles/iam.serviceAccountTokenCreator or its storage role and every URL it signed stops working going forward. If the exam says "revoke delegated access without rotating a key" → remove the IAM binding, not a key.

3. Lifecycle management: tiering on autopilot

// lifecycle config — JSON applied to the bucket
{ "rule": [
  { "action": { "type": "SetStorageClass", "storageClass": "NEARLINE" },
    "condition": { "age": 30, "matchesPrefix": ["invoices/"] } },
  { "action": { "type": "SetStorageClass", "storageClass": "ARCHIVE" },
    "condition": { "age": 180, "matchesPrefix": ["invoices/"] } },
  { "action": { "type": "Delete" },
    "condition": { "age": 2555, "matchesPrefix": ["invoices/"] } }
] }
Rules evaluate roughly once a day — not instantly. Conditions can match on age, createdBefore, matchesPrefix/matchesSuffix, numNewerVersions, and isLive (great for pruning noncurrent versions). Combined with Object Versioning (soft-delete-style retention of noncurrent versions), this is the full data-protection story: versioning catches accidents, lifecycle keeps the bill down. 2555 days = the classic 7-year compliance retention, same number you'd write for an AWS S3 lifecycle rule.
