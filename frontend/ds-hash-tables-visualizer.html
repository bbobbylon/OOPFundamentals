🧩 What is a hash table — and how does it achieve O(1) average-case lookup despite having no inherent ordering?

A hash table (HashMap in Java, dict in Python, object/Map in JavaScript) is the most important data structure after arrays. It maps arbitrary keys to values and (on average) retrieves them in O(1) — regardless of how many entries it holds. The mechanism: a hash function converts a key into an integer (the hash code), then a modulo operation maps it to an array index (a bucket). bucketIndex = hashCode(key) % capacity. The value is stored at that index. To retrieve: compute the same hash, go to the same bucket, and find the value. Hash collisions: two different keys may produce the same bucket index. This WILL happen (by the birthday paradox, with high probability once you have many entries). Two solutions: Chaining — each bucket holds a linked list of entries. Collision: append to the list. Worst case: all keys hash to one bucket → O(n) lookup (degenerate case). Average case with good hash function + reasonable load factor: O(1). Open addressing — when a collision occurs, probe for the next empty slot (linear probing: try index+1, index+2, ...; quadratic probing: try index+1², index+2²; double hashing: second hash function). Requires no extra memory for lists. Better cache performance (data stays in the same array). Load factor: ratio of entries to buckets. Java HashMap's default load factor is 0.75 — when 75% of buckets are filled, the table doubles in size and rehashes all entries. Higher load factor = less memory, more collisions. Lower = more memory, fewer collisions. Java HashMap internals: uses chaining, but since Java 8, when a bucket's chain exceeds 8 entries, it converts the chain to a balanced BST (TreeMap-like) — worst case lookup degrades from O(n) to O(log n) instead.

What Is a Hash Table?

A hash table maps keys to values in O(1) average time by computing the storage index directly from the key. No searching needed — the position is calculated, not found.

The Big Idea

// Three steps every hash table does:
① HASH key → integer "hello" → 99162322
② MOD integer % capacity 99162322 % 16 = 2
③ STORE array[index] = value array[2] = "world"

What Makes a Collision?

Two different keys produce the same index after the MOD step. By the pigeonhole principle, if you have more keys than buckets you must have collisions. Even with fewer keys, random hashing gives a ~63% chance of collision by the Birthday Paradox at 50% load.

Why Worst Case O(n)?

If all n keys hash to bucket 0, lookup requires scanning all n nodes in bucket 0's chain — linear search. This is why hash function quality matters enormously.

Birthday Paradox: In a table of capacity n, you only need √n insertions before collision probability exceeds 50%. With n=365 days, only 23 people needed for >50% birthday match.

Java's hashCode() Contract

// The Object hashCode() contract (you must follow this when overriding): // 1. If a.equals(b) then a.hashCode() == b.hashCode() [consistency] // 2. The reverse is NOT required (hash collisions are allowed) // 3. hashCode() must be consistent within one JVM run // BAD: Only overrides equals — violates contract! class BadPoint { int x, y; public boolean equals(Object o) { return ... } // but no hashCode! // Two equal BadPoints will land in DIFFERENT HashMap buckets → broken } // GOOD: Both overridden consistently class Point { int x, y; @Override public int hashCode() { return Objects.hash(x, y); // delegates to Arrays.hashCode([x,y]) } @Override public boolean equals(Object o) { if (!(o instanceof Point p)) return false; return x == p.x && y == p.y; } } // Records auto-generate both correctly: record Point(int x, int y) {} // hashCode + equals auto-generated

String hashCode() — How Java Does It

// Java's String.hashCode() formula: // s[0]*31^(n-1) + s[1]*31^(n-2) + ... + s[n-1] // Uses 31 because: prime, odd, fits in int, JIT optimizes // 31 * i == (i << 5) - i ← compiler uses this shift trick int hash = 0; for (char c : "hello".toCharArray()) { hash = 31 * hash + c; } // hash = 99162322 // PROBLEM: Similar strings cluster // "FB".hashCode() == "Ea".hashCode() == 2236 // → HashMap applies a "spread" function on top

HashMap's Spread Step

// Java HashMap doesn't use hashCode() directly! // It applies an additional mixing step: static final int hash(Object key) { int h; return (key == null) ? 0 : (h = key.hashCode()) ^ (h >>> 16); } // XOR the high bits into the low bits. // Why? Capacity is always a power of 2, so // index = hash & (capacity-1) only uses LOW bits. // Without spreading, high-bit variation is lost. // Final bucket index: int index = hash & (n - 1); // n = power-of-2 capacity

Hash DoS Attack & Defense

Hash Flooding (HashDoS): An attacker submits keys that all hash to the same bucket, degrading O(1) to O(n) per operation. Servers parsing HTTP headers or JSON are vulnerable if using user input as HashMap keys.
// Vulnerable: predictable hashCode // In Java pre-7u6, String hashCode was // deterministic across JVM runs. // Attacker could craft N strings with // same hash → O(n²) HashMap operations // Example attack vectors: // HTTP POST with 100k params all hashing to 0 // JSON object with colliding keys
// Defenses: // 1. Java 7u6+: hash seed randomized per-JVM-run // 2. Java 8+: treeify buckets at length ≥ 8 // (O(log n) even when all in one bucket) // 3. SipHash: keyed hash, attacker can't predict // (used by Python, Ruby, Rust since ~2012) // 4. Limit user-controlled key count // 5. Use LinkedHashMap or TreeMap for // untrusted key sets

Separate Chaining — The Classic Approach

Each bucket holds a linked list (or tree) of all entries that hash to that index. Collisions are handled by appending to the chain. Lookup scans the chain for a key match.

How Chaining Works

// PUT("cat", 1): hash("cat") % 8 = 2
bucket[2] → ["cat":1] → null

// PUT("act", 2): hash("act") % 8 = 2 ← collision!
bucket[2] → ["act":2] → ["cat":1] → null

// GET("cat"): hash % 8 = 2, scan chain
check "act" ✗ → check "cat" ✓ return 1

Implementation Sketch

class ChainingHashMap<K,V> { Node[] buckets; int capacity, size; int index(K key) { return (key.hashCode() & 0x7FFFFFFF) % capacity; } void put(K key, V val) { int i = index(key); for (Node n = buckets[i]; n != null; n = n.next) if (n.key.equals(key)) { n.val = val; return; } buckets[i] = new Node(key, val, buckets[i]); size++; if ((double) size / capacity > 0.75) resize(); } V get(K key) { Node n = buckets[index(key)]; while (n != null) { if (n.key.equals(key)) return n.val; n = n.next; } return null; } }

Chaining: Pros & Cons

Advantages

  • Simple to implement
  • Load factor can exceed 1.0 (chains grow)
  • Deletion is straightforward (unlink node)
  • Order within a chain preserves insertion order
  • Resistant to clustering (primary/secondary)
  • Easy to convert chain → tree (Java's treeify)

Disadvantages

  • Extra memory per node (next pointer)
  • Poor cache locality (linked list nodes scattered in heap)
  • Long chains degrade to O(n) linear scan
  • Memory overhead: 16–24 bytes per Node object on JVM
Java 8+ mitigates the last point: when a chain reaches 8 nodes, it converts to a Red-Black Tree — O(log n) worst case per bucket.

Open Addressing — No External Chains

All entries live inside the array. On collision, probe for the next open slot using a deterministic sequence. Better cache performance; load factor must stay below 1.0.

Linear Probing

probe(i) = (h + i) % n // 0, 1, 2, 3, 4... ✓ Best cache locality ✗ Primary clustering

Occupied slots clump together → long runs to skip over, hurting average probe length.

Quadratic Probing

probe(i) = (h + i²) % n // 0, 1, 4, 9, 16... ✓ Reduces primary clusters ✗ Secondary clustering ✗ May not visit all slots

Works reliably only when capacity is prime or power-of-2 with specific coefficients.

Double Hashing

probe(i) = (h1 + i*h2) % n // step size from 2nd hash ✓ No clustering ✓ Near-random distribution ✗ 2 hash computations ✗ Poor cache locality

Best theoretical performance; used in Python's dict (simplified variant).

Rehashing (Resize)

When load exceeds threshold, allocate a larger array and reinsert all entries. Java HashMap doubles capacity (always power of 2). This is O(n) but happens infrequently → O(1) amortized.

// Java HashMap resize (simplified): void resize() { int newCapacity = capacity * 2; // always doubles Node[] newBuckets = new Node[newCapacity]; // Rehash all entries into new positions for (Node head : buckets) { Node node = head; while (node != null) { Node next = node.next; // Smart trick: new index is either i or i+oldCapacity int newIdx = (node.hash & newCapacity) == 0 ? node.hash & (newCapacity - 1) // same bucket : (node.hash & (newCapacity - 1)); // or bucket + oldCap // Insert at head of new bucket node.next = newBuckets[newIdx]; newBuckets[newIdx] = node; node = next; } } buckets = newBuckets; capacity = newCapacity; } // Key insight: since capacity doubles (power of 2), // we only check one new bit of the hash → split is O(1) per entry
Pre-sizing advice: If you know you'll insert N entries, initialize with new HashMap<>(N * 4 / 3 + 1) to avoid rehashing. The constructor takes initial capacity, not max entries. With default 0.75 threshold: capacity needed = N / 0.75 ≈ N × 1.34.

Amortized Analysis of Rehashing

// Each doubling: copy all n existing entries once. // Total copies over n insertions starting from cap=1: // 1 + 2 + 4 + 8 + ... + n/2 = n - 1 ≈ n // So n insertions → ~2n total copy operations // → O(1) amortized per insertion ✓ // Rehash thresholds in Java: // Default initial capacity: 16 // Default load factor: 0.75 // Resize at: 12 entries (16 × 0.75) // → new capacity: 32, threshold: 24 // → new capacity: 64, threshold: 48 // → ...

Tuning HashMap

// Use when: high-memory-ok, minimize collision new HashMap<>(16, 0.5f); // low LF, fewer collisions // Use when: memory-constrained, many entries new HashMap<>(16, 0.9f); // high LF, more collisions // Pre-size for known count (avoids rehashing): int n = 1000; new HashMap<>(Math.max(16, (n * 4 / 3) + 1)); // Guava utility (does the math for you): // Maps.newHashMapWithExpectedSize(n)

Java 8+ HashMap Internals

Java's HashMap is a carefully engineered chaining hash table with three critical optimizations: power-of-2 sizing (fast modulo), spread hashing (better distribution), and treeification (DoS defense).

Treeification — Java 8's Key Innovation:

When a single bucket's linked list reaches 8+ nodes AND the table has ≥ 64 total buckets, that chain converts from a LinkedList of Node to a TreeMap of TreeNode (Red-Black Tree). This guarantees O(log n) worst-case per bucket instead of O(n). If entries fall below 6 nodes (after remove), it converts back to a linked list.
// HashMap.Node (linked list node): static class Node<K,V> { final int hash; // cached hash(key) — avoids recompute on resize final K key; V value; Node<K,V> next; // linked list chain } // HashMap.TreeNode (Red-Black tree node, extends Node): static final class TreeNode<K,V> extends LinkedHashMap.Entry<K,V> { TreeNode<K,V> parent, left, right, prev; boolean red; // color for Red-Black invariant } // Constants that control treeification: static final int TREEIFY_THRESHOLD = 8; // chain → tree static final int UNTREEIFY_THRESHOLD = 6; // tree → chain static final int MIN_TREEIFY_CAPACITY = 64; // table must be ≥64 first

HashMap: Full put() Walkthrough

// Simplified put(K key, V value) — following Java 8 source: V put(K key, V value) { // Step 1: Compute spread hash int hash = (key == null) ? 0 : key.hashCode() ^ (key.hashCode() >>> 16); // Step 2: Lazy-initialize table on first put if (table == null) resize(); // Step 3: Find bucket index (fast bitwise AND — works because cap is power of 2) int i = hash & (table.length - 1); Node<K,V> p = table[i]; // Step 4: Handle empty bucket if (p == null) { table[i] = new Node(hash, key, value, null); } else { // Step 5a: Bucket is a tree → delegate to tree insert if (p instanceof TreeNode) e = ((TreeNode) p).putTreeVal(this, table, hash, key, value); // Step 5b: Bucket is a linked list → walk it else { for (Node<K,V> e = p;; e = e.next) { if (e.next == null) { e.next = new Node(hash, key, value, null); // append if (binCount >= TREEIFY_THRESHOLD - 1) treeifyBin(table, hash); break; } if (e.hash == hash && e.key.equals(key)) { e.value = value; return /* old value */; // key exists: update } } } } // Step 6: Update size, maybe resize if (++size > threshold) resize(); }

LinkedHashMap & TreeMap

LinkedHashMap — Insertion-Order Iterator

// LinkedHashMap = HashMap + doubly-linked list // that threads through all entries in insertion order Map<String, Integer> lhm = new LinkedHashMap<>(); lhm.put("banana", 2); lhm.put("apple", 1); lhm.put("cherry", 3); // Iteration: banana, apple, cherry (insertion order) // Access-order mode → LRU Cache! Map<K,V> lru = new LinkedHashMap<>(16, 0.75f, true) { protected boolean removeEldestEntry(Map.Entry<K,V> e) { return size() > MAX_SIZE; } };

TreeMap — Sorted Order, O(log n)

// TreeMap = Red-Black tree. Keys must be Comparable // or you supply a Comparator. TreeMap<String, Integer> tm = new TreeMap<>(); tm.put("banana", 2); tm.put("apple", 1); tm.put("cherry", 3); // Iteration: apple, banana, cherry (alphabetical) // Unique NavigableMap operations: tm.firstKey(); // "apple" tm.headMap("cherry"); // {apple=1, banana=2} tm.floorKey("b"); // "banana" (≤ "b") tm.ceilingKey("b"); // "banana" (≥ "b")

Common HashMap Pitfalls

Mutable Key Disaster

List<Integer> key = new ArrayList<>(List.of(1, 2)); Map<List<Integer>, String> map = new HashMap<>(); map.put(key, "hello"); key.add(3); // mutate the key! map.get(key); // returns null — key's hash changed! // Entry is still in map, but in the WRONG bucket now // Use immutable keys (String, Integer, record, etc.)

getOrDefault / computeIfAbsent

// Counting words — verbose old way: if (!map.containsKey(word)) map.put(word, 0); map.put(word, map.get(word) + 1); // 2 lookups! // Modern: merge() — atomic count map.merge(word, 1, Integer::sum); // Grouping: computeIfAbsent map.computeIfAbsent(key, k -> new ArrayList<>()).add(val); // Safe default: map.getOrDefault(key, "N/A");

Iteration While Modifying

// ConcurrentModificationException! for (String key : map.keySet()) if (shouldRemove(key)) map.remove(key); // ✗ // Correct: use removeIf on entrySet map.entrySet().removeIf(e -> shouldRemove(e.getKey())); // Or iterate over copy of keys new ArrayList<>(map.keySet()).forEach(k -> { if (shouldRemove(k)) map.remove(k); });

null Keys & Values

// HashMap: allows ONE null key and multiple null values map.put(null, "value"); // OK map.put("key", null); // OK // Hashtable: no null keys or values // ConcurrentHashMap: no null keys or values // TreeMap: no null keys (Comparable.compareTo would NPE) // Dangerous pattern: map.get("key") == null; // ambiguous: key absent OR value is null map.containsKey("key"); // unambiguous check
