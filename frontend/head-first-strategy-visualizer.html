Act 1 — inheritance looked great (for about a week)

Joe's company makes SimUDuck, a duck-pond simulator. The original design is textbook OO: a Duck superclass, and every duck extends it.

abstract class Duck {
  void quack() { System.out.println("Quack"); }   // all ducks share this
  void swim()  { System.out.println("All ducks float"); }
  abstract void display();                       // each duck looks different
}

class MallardDuck extends Duck {
  void display() { System.out.println("I'm a green-headed mallard"); }
}

Clean. Reusable. Everyone's happy. Then the executives want the ducks to fly for the next shareholder demo…

Act 2 — "just add fly() to the superclass" (the rubber duck incident)

Easy, thinks Joe — add fly() to Duck and every duck inherits it for free.

abstract class Duck {
  void quack() { ... }
  void fly()   { System.out.println("I'm flying!"); }  // ← added to the base class
}

The demo goes great… until rubber ducks start flying across the screen. Because RubberDuck extends Duck, it inherited fly() too.

Brain Power. Joe's reflex is to override fly() in RubberDuck to do nothing (and quack() to squeak). What happens when the company adds a DecoyDuck (a wooden decoy — no fly, no quack)? And the next 20 duck types? Every new subclass forces you to remember which inherited methods to cancel. A localized change to the superclass rippled into a maintenance nightmare.
class RubberDuck extends Duck {
  void fly() { /* override to do nothing — ugh */ }
  void quack() { System.out.println("Squeak"); }
}

Act 3 — "interfaces, then!" (also not the answer)

Next idea: pull fly() and quack() out into Flyable and Quackable interfaces. Only ducks that should fly implement Flyable.

interface Flyable   { void fly(); }
interface Quackable { void quack(); }

class MallardDuck extends Duck implements Flyable, Quackable { ... }
class RedheadDuck extends Duck implements Flyable, Quackable { ... }

It fixes the rubber-duck bug — but it's worse. Interfaces have no implementation, so every flying duck reimplements fly() by hand. Change how flying works and you edit it in 48 classes. You destroyed code reuse to get flexibility.

Q: So inheritance gives reuse but no flexibility, and interfaces give flexibility but no reuse?

A: Exactly. That's the tension the Strategy pattern resolves. The trick is to stop asking "what IS-A duck" and start asking "what VARIES between ducks" — and pull that out.

Act 4 — encapsulate what varies

What varies across ducks? Flying and quacking. So pull each into its own family of behavior classes behind an interface — and give Duck a reference to one of each.

The behavior families

interface FlyBehavior { void fly(); }

class FlyWithWings implements FlyBehavior {
  public void fly() {
    System.out.println("I'm flying with wings!");
  }
}
class FlyNoWay implements FlyBehavior {
  public void fly() { /* can't fly */ }
}

Duck HAS-A behavior (composition)

abstract class Duck {
  FlyBehavior flyBehavior;     // HAS-A, not IS-A
  QuackBehavior quackBehavior;

  void performFly() {
    flyBehavior.fly();          // DELEGATE — don't do it yourself
  }
  // swap behavior at runtime:
  void setFlyBehavior(FlyBehavior fb) {
    this.flyBehavior = fb;
  }
}

Now a MallardDuck sets flyBehavior = new FlyWithWings(); a RubberDuck sets new FlyNoWay(). Adding a rocket-powered duck is a new behavior class, not a change to Duck. And because of setFlyBehavior(), you can change a duck's flight at runtime — which is exactly what the hero above shows in scene ④.

The three principles this chapter hands you

Design Principle #1Identify the aspects that vary and separate them from what stays the same.
Design Principle #2Program to an interface (a supertype), not an implementation.
Design Principle #3Favor composition (“HAS-A”) over inheritance (“IS-A”).

"Program to an interface" really means "program to a supertype" — the declared type is an interface/abstract class, so the actual object can be any implementation, decided at runtime. That's the whole reason flyBehavior.fly() can mean different things for different ducks.

The Strategy Pattern, defined

The Strategy Pattern defines a family of algorithms, encapsulates each one, and makes them interchangeable. Strategy lets the algorithm vary independently from the clients that use it.

Map it back to the ducks: the family of algorithms = FlyBehavior implementations; encapsulated = each is its own class; interchangeable = setFlyBehavior(); vary independently of the client = you change flying without touching Duck or any duck subclass.

You've already used Strategy (you just didn't call it that)

java.util.Comparator

list.sort(Comparator.comparing(User::getName));
list.sort(byAgeThenName);

The sort algorithm is fixed; the comparison strategy is the swappable object you pass in.

Spring & Angular, everywhere

// Spring: pick an algorithm by injecting a bean
PasswordEncoder enc = new BCryptPasswordEncoder();
// Angular: a ValidatorFn IS a strategy
control = new FormControl('', Validators.email);

PasswordEncoder, ValidatorFn, an RxJS operator you pass to pipe() — all "a family of interchangeable algorithms behind one interface."
