JSX & the Virtual DOM

JSX is not HTML and the Virtual DOM is not the DOM. Watch a tag travel from source → Babel → a plain React.createElement object → an in-memory element tree → real browser nodes.

🧬 What is JSX — and what is the Virtual DOM actually doing at every step?

JSX is compile-time sugar — there's no JSX in the browser. A build tool turns <Button onClick={save}>Save</Button> into _jsx(Button, { onClick: save, children: "Save" }) (the React 17+ transform, so no more import React per file). The result is a plain React element object — cheap data: { type, props, key, ref }. The Virtual DOM is the tree of those objects; rendering a component returns a new tree, React reconciles it against the previous one, and the differences become real DOM operations in the commit phase. The point isn't that DOM calls are slow per se — it's batching and minimizing them to avoid expensive reflows and repaints.

  • JSX is compile-time only — transforms to _jsx(...) before the browser sees it.
  • React element = plain object — { type, props, key, ref }, cheap to create.
  • Reconciliation diffs trees — new vs previous element tree.
  • Commit phase applies the minimal DOM ops, avoiding reflows/repaints.

JSX transform pipeline

// Step 1: You write JSX const el = ( <div className="card"> <UserAvatar src={user.avatarUrl} /> <span>{user.name}</span> </div> ); // Step 2: Babel/SWC compiles JSX away const el = _jsx('div', { className: 'card', children: [ _jsx(UserAvatar, { src: user.avatarUrl }), _jsx('span', { children: user.name }) ] }); // Step 3: Runtime creates element objects // { type: 'div', props: { className: 'card', // children: [ { type: UserAvatar, ... }, // { type: 'span', ... } ] } }

JSX rules

One root element: JSX must return a single root. Use <React.Fragment> or <></> to avoid adding a real DOM wrapper. className not class: class is a JS reserved word. camelCase events: onClick not onclick. Self-close empty tags: <Input /> not <Input>. Expressions in {}: any JS expression inside curly braces; statements (if, for) need to be moved outside or replaced with ternaries / .map(). Components start uppercase: lowercase = native DOM tag (<div>). Uppercase = React component (<UserRow>). Angular equivalent of JSX: Angular templates (.html files) compiled by the Angular compiler to TypeScript instruction sequences. Both are compile-time transformations of a declarative template into imperative DOM instructions.

Angular comparison: Angular's compiler turns a template into TypeScript that calls Ivy instruction functions directly — no virtual DOM. React diffs the whole subtree then commits; Angular knows exactly which bindings to re-execute (more surgical, but needs compile-time static analysis of templates). Zone.js (or Signals) drives Angular's change detection. Different tradeoffs, same end result: a real DOM matching current state.

The mechanism

Watch what actually happens to that key field between your spread and the element React builds.

  1. <UserRow {...user} /> compiles to _jsx(UserRow, {...user}) under the automatic runtimecompile time
  2. No literal key= attribute exists in the JSX source, so Babel has nothing to pull out as a separate argumentno literal key
  3. At runtime, _jsx's config object is user itself — id, key, name, role, all present as plain propertiesruntime object
  4. React's element-construction code checks that config object for a key property directly, finds one, and lifts it onto the element's own .key — same as createElement has always donestill extracted
  5. Because this lookup happens on an object React didn't expect key to arrive through, it also fires the console warningflagged
  6. The element ships with a real, working key today — and a paper trail marking the pattern for removalworks, but marked

Step 4 is the surprising one: the automatic JSX runtime isn't a stricter gatekeeper than the classic transform here — it runs the identical "does this config have a key" check createElement has always run. The new thing in React 18.3 isn't the extraction; it's the warning bolted onto it.

Where you have seen this before

Something that still runs perfectly today while carrying its own retirement notice is a much older shape than this one warning.

HTML's <marquee> and <font> tags

Every browser still renders them exactly as it did in 1998 — nothing about them is broken — yet both were stripped from the HTML spec years ago, kept alive only by browsers' promise never to break the old web. "Still works" and "still sanctioned" come apart here exactly like they do for a spread key.

a working feature and a supported feature are two different guarantees

Java's Thread.stop()

Deprecated since Java 1.2, complete with a javadoc warning that it's "inherently unsafe" — and still a real, callable method decades later, still doing exactly what it always did, right up until whichever JDK version finally turns it into a hard error.

a deprecation window can outlast several major versions before the wall arrives

A cloud SDK's sunset-dated API version

Calls through an old AWS/Azure/GCP SDK major version keep returning real, correct data for years after the "please migrate" banner appears in your console — until the provider's published sunset date arrives and the exact same code starts failing outright, all at once.

1. JSX is sugar for function calls

JSX is not part of JavaScript — your browser never sees it. A compiler (Babel, or the TypeScript/SWC/esbuild equivalents) rewrites every tag into a createElement call at build time. What ships to the browser is plain JavaScript.

You write (JSX)

const el = (
  <button className="btn" onClick={save}>
    Save {count}
  </button>
);

Classic transform compiles to

const el = React.createElement(
  "button",
  { className: "btn", onClick: save },
  "Save ", count
);
New JSX transform (React 17+): Babel now emits import {jsx as _jsx} from "react/jsx-runtime" and calls _jsx("button", {className, onClick, children}) instead of React.createElement. That is why modern code no longer needs import React from 'react' just to use JSX — the compiler injects the runtime import for you.

2. A React element is a plain object — not a DOM node

createElement does not touch the DOM. It returns a frozen, immutable description: { $$typeof, type, key, ref, props }. Rendering that object is React's job, in a separate step.

{
  $$typeof: Symbol(react.element), // guards against JSON-injection XSS
  type: "button", // string = host (DOM) tag
  key: null, ref: null,
  props: { className: "btn", onClick: fn, children: ["Save ", 3] }
}
type valueMeansHow React renders it
"div", "button" (lowercase string)Host componentCreates the matching DOM element
Counter (function/Capitalized)Your componentCalls the function to get more elements
Symbol(react.fragment)Fragment <>…</>Renders children with no wrapper node
Why capitalization matters: <button> compiles to createElement("button", …) (a string → DOM tag) but <Button> compiles to createElement(Button, …) (a reference to your function). Lowercase a component name and React tries to create a literal <mycomponent> DOM tag — silent breakage.

3. The Virtual DOM diff

The Virtual DOM is a lightweight tree of these element objects kept in memory. On each render React builds a new tree, compares it to the previous one (reconciliation), and computes the minimal set of real DOM mutations. Touching the real DOM is slow; comparing JS objects is fast.

The Virtual DOM is a means, not magic. It does not make React "faster than the DOM" — direct DOM updates are always faster than diffing. What it buys you is a declarative model: you describe the UI for the current state and React figures out the patches, so you never hand-write el.textContent = … imperatively.
