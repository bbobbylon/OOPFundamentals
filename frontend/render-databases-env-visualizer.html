Render — Postgres, env vars and the 30-day clock

or, two connection strings for one database, and the free tier that starts a timer the moment you click create

🗄️ What does "managed Postgres" actually give you, and why are there two connection strings?

A managed database is a real PostgreSQL server that somebody else patches, backs up and keeps running. You get a hostname and a password; you don't get a machine to log into. Render hands you two ways to reach it, and picking the wrong one is the single most common configuration mistake on the platform: the internal address only resolves from inside Render's private network, and the external one is reachable from anywhere on the internet.

  • Internal for your app, external for your laptop. Internal never leaves the private network — faster and not exposed.
  • Same region, or no private network. A service in Oregon cannot use a Frankfurt database's internal address.
  • A free database expires 30 days after it is created — not after 30 idle days. The clock starts at creation and does not stop.
  • Connections are a budget. Every instance of every service multiplies its pool size against one fixed max_connections.

An environment variable is not a secret store

It is good enough for most things and it is what you'll use. But know what it is: readable by anyone with dashboard access, visible to every process in the container, and easy to print into a log by accident. Group it, scope it, and never log the whole environment in an error handler.

Build time and run time are different worlds

Your build runs on one machine; your app runs on another. A variable available to one is not automatically available to the other, and a value baked into a front-end bundle at build time is shipped to every visitor's browser. That distinction is where "the secret is right there in the dashboard, why is it null?" comes from.

Spring / CIAM: Spring Boot will not accept Render's connection string as-is. The platform hands you a libpq-style URL; JDBC wants jdbc:postgresql://host/db with the username and password as separate properties. So you pull host, database, user and password individually and assemble the URL yourself — which is also why Hikari's pool size becomes something you have to think about rather than something you inherit.

Your service queries its database in single-digit milliseconds. A second service — same account, same code, same connection string, different region — can't reach it at all. Nothing is misconfigured, no firewall rule is missing, and the string is byte-for-byte identical. What is actually different?

The idea

One database, two doors — and picking the wrong one is a latency bug, not an error message.

Every Render Postgres hands you two connection strings for the same database, and they are not interchangeable.

  • The Internal Database URL travels over Render's private network. It is fast, it never touches the public internet, and it works from your other Render services on one condition: the same account and the same region. Render's own advice is blunt — "use the internal URL wherever possible."
  • The External Database URL goes over the public internet, encrypted with Render-managed TLS. It works from anywhere: your laptop, a GitHub Action, a colleague's machine, a service you put in the wrong region nine months ago. It is slower, and it is reachable by anyone holding the string.

That is the answer to the question above. Two services, one region apart, and only one of them has a private network path to the database.

A free Postgres expires 30 days after it is created.

Not thirty days of inactivity. Thirty days from creation, whether you use it every hour or never touch it again. Render gives you a 14-day grace period to upgrade before the database is deleted, and if you miss that, it goes — with the data in it.

This is the single most expensive surprise on the platform, because it is silent, it is slow, and it lands on exactly the wrong thing: the portfolio project you built in March and linked on your CV in May. The web service is still there. The URL still resolves. The app comes up and every page that needs data is broken. Keep-alive pingers do nothing about it — they keep the service awake, and this clock was never about traffic.

This is the arithmetic nobody does until it fails. Hikari's default pool is 10, and that default is per process — so scaling your API from one instance to three did not add a third of the load, it tripled the connection demand. Add a worker service and an open psql window and you are at 41 against a ceiling of 40. The error arrives as FATAL: sorry, too many clients already, on the healthiest-looking service you own, at whatever moment the last connection was requested — which is to say, not necessarily in the service that caused it.

Anatomy of a connection string

Click each part — the host is the only one that differs between the two URLs, and it changes everything.

the scheme — and a JDBC papercut

Render gives you a URL starting postgresql:// (or the older postgres://). Most drivers are happy with it. The JVM is not: JDBC wants jdbc:postgresql://…, and it does not accept a username and password embedded in the URL the way libpq does. So a Spring Boot app usually splits the value into spring.datasource.url, .username and .password rather than pasting the string in whole. That mismatch — a perfectly valid URL that the JDBC driver refuses — is one of the most common first-hour failures for a Java service here.

the user

The role Render created with the database. In a Blueprint it's the user: field, and it comes back out through fromDatabase with property: user — which is exactly how you feed spring.datasource.username without ever typing it.

the password — the reason you never copy this string

It's right there in the URL, in plain text. Every place you paste it is a place you now have to protect and remember to update: a .env file, a Slack message to yourself, a screenshot in a ticket. Reference it, don't copy it — fromDatabase in your Blueprint means one authoritative copy, and rotating the credential updates every consumer at once instead of leaving stale copies to fail later.

the host — the entire difference between the two URLs

This is the only part that changes. The internal URL uses a bare hostname with no public domain on it — it resolves only inside Render's private network, from services in the same account and region. The external URL is the same name with a region-qualified render.com domain appended, resolvable from anywhere and protected by TLS instead of by network isolation. Same database, same credentials, two completely different security and latency stories — and nothing in your app's config hints at which one you handed it.

the database name

The Postgres database itself — the Blueprint's databaseName:, as opposed to name:, which is what Render calls the resource in its own dashboard. Two names for two different layers, and the one fromDatabase refers to is the Render one.

A GitHub Action needs to run a schema migration against your Render Postgres before a release. Which connection string does it use?

Correct, and the reason is worth stating precisely: the internal hostname doesn't resolve outside Render's private network, so a GitHub runner can't even look it up — you get a DNS failure, not a permissions error. Anything running off-platform (your laptop, CI, a colleague) uses the external URL, over TLS. And if it's a Render service doing the migrating, the better answer is a preDeployCommand, which runs on the private network and needs no external exposure at all.

It is faster — but speed isn't the constraint here. The internal hostname is only resolvable from inside Render's private network, and a GitHub-hosted runner is not on it. The job would fail at name resolution before it ever tried to authenticate.

Same database, yes — but not the same reachability. The internal URL works only from the same account and region inside Render; the external one works from anywhere. Treating them as interchangeable is how a service ends up quietly routing every query over the public internet.

Give JDBC the pieces, not the URL

Render's connectionString is a libpq-style URL with credentials inside it, and the JDBC driver won't take it. Pull the parts separately and assemble the one shape the JVM actually accepts.

envVars:
  - key: DB_HOST
    fromDatabase: { name: devhub-db, property: host }
  - key: DB_NAME
    fromDatabase: { name: devhub-db, property: database }
  - key: SPRING_DATASOURCE_USERNAME
    fromDatabase: { name: devhub-db, property: user }
  - key: SPRING_DATASOURCE_PASSWORD
    fromDatabase: { name: devhub-db, property: password }
  - key: SPRING_DATASOURCE_URL
    value: jdbc:postgresql://${DB_HOST}/${DB_NAME}

HikariPool-1 - Start completed.

# no password anywhere in the repo, and rotating it in Render
# updates all four values at once.
four separate fromDatabase pulls exist for one reason: JDBC will not parse the string Render gives you. Take the pieces and assemble jdbc:postgresql://${DB_HOST}/${DB_NAME} yourself, and pass user and password as their own properties.
Check which door you came in through

Nothing in your config announces whether you're on the private network or crossing the public internet — but the hostname tells you, and so does the latency.

$ echo $DB_HOST
$ psql "$DATABASE_URL" -c '\timing' -c 'select 1'
# internal (same region) — a bare hostname, no public domain:
dpg-cs4k2h9r0ff-a
Time: 1.284 ms

# external (from your laptop) — region-qualified public domain:
dpg-cs4k2h9r0ff-a.oregon-postgres.render.com
Time: 84.402 ms
the hostname is the tell, and so is the timing — 1ms against 84ms. A bare hostname means you are on the private network; a .oregon-postgres.render.com suffix means your traffic went out to the internet and came back.
Do the connection maths before Postgres does it for you

Every plan caps concurrent connections, and a connection pool is a reservation, not a request — Hikari opens up to its maximum and keeps them. Multiply before you deploy the third service.

$ psql "$DATABASE_URL" -c 'show max_connections;'
$ psql "$DATABASE_URL" -c 'select count(*) from pg_stat_activity;'

Find out when the clock runs out — today, not in October

If the database is free, it has an expiry date that was set the moment you created it. Look it up now, put it in your calendar, and decide deliberately whether this project deserves a paid database or an export.

$ pg_dump "$EXTERNAL_DATABASE_URL" > devhub-$(date +%F).sql
# Free database created 2026-03-04
#   expires   2026-04-03   (30 days after CREATION, not last use)
#   grace     +14 days to upgrade, then deleted with its data

# a dump costs you one command and turns "it vanished"
# into "I restored it".
the word to notice is CREATION. This is not an idle timer you can reset by using the database — it started when you clicked create and it does not stop. Write the date down now; a pg_dump is one command.
The CIAM version of this page: notice that the internal URL is protected by where it is and the external URL by what it proves — network isolation versus TLS and credentials. That's the same choice you make between a private service on an internal network and a public API behind OAuth, and the same reason "it's on the internal network" is a boundary, not an authorisation. Anything reachable from the internet needs to prove who it is on every request; anything reachable only from inside still needs to, the day someone adds a service you didn't expect. Use the private path because it's faster and smaller-surface — never as a substitute for authentication.
There are no dumb questions

If the internal URL is better, why does the external one exist at all?

Because plenty of legitimate things aren't on Render. Your local machine running a migration, a GitHub Action doing a release, a BI tool, a colleague reproducing a bug, pg_dump taking the backup you'll be glad about later — none of those can resolve an internal hostname, because it isn't in public DNS. The external URL is the door for all of them, which is exactly why it deserves respect: it is reachable from anywhere in the world by anyone holding the string. Use internal for service-to-service traffic, use external deliberately and briefly, and treat the external string as the credential it is.

What's the actual difference between a connection pool and the pooled connection string?

They solve the same shortage at different layers, and knowing which one you need is the whole trick. Your pool — HikariCP in Spring Boot — lives inside one instance and stops that instance from opening a new TCP connection per request. The pooled connection string lives in front of the database and multiplexes many client connections onto a smaller number of real ones. If a single service is exhausting the database, tune your own pool. If the sum of your services exceeds the database's limit — three services × ten connections each, plus previews, plus the psql window you left open — no per-service tuning fixes it, and connectionPoolString is the right answer. The tell is the error: too many clients already comes from Postgres, not from your app, so the shortage is on the database side of the wire.

My free database expired. Is the data really gone?

After the grace period, yes — and this is the part to internalise before it happens rather than after. The 30 days start at creation and the 14-day grace period is your window to upgrade; miss both and the database is deleted along with what was in it. Two habits make it a non-event. First, a pg_dump to a file you actually keep, which is one command and can be a monthly calendar reminder. Second, be honest about which projects are demos and which are real: a demo can be re-seeded from a script in your repo, and if it can't, it isn't a demo — it's a production database with no backups and no plan, which is a much more uncomfortable sentence and exactly the right one to say out loud.
