Python: Packaging & Environments

From an isolated venv to a published wheel: virtual environments, pip & dependency locking, the modern pyproject.toml, and building/publishing distributions the supply-chain-safe way.

🚚 How Python code becomes an installable, reproducible artifact

Real projects never pip install into the system Python. First a virtual environment (python -m venv .venv) isolates dependencies per project; pip installs from PyPI, but production needs pinning and locking (exact versions + hashes via pip-compile/uv/Poetry) so every machine installs byte-identical deps. Metadata and dependencies live in one standardized pyproject.toml (replacing setup.py/requirements.txt). python -m build produces an sdist and a wheel, and you publish with twine — ideally via trusted publishing (OIDC) over long-lived tokens.

  • One venv per project — isolate deps; no system-Python pollution.
  • Pin + lock with hashes — byte-identical, reproducible installs.
  • pyproject.toml is the standard — metadata + deps + build backend in one file.
  • Build a wheel, publish via OIDC — short-lived CI tokens, not long-lived secrets.

Isolate, install, lock

python -m venv .venv source .venv/bin/activate # Win: .venv\Scripts\activate pip install -e . # editable install pip-compile -o requirements.lock # pin + hash

One config file

[project] name = "authlib" version = "1.2.0" dependencies = ["httpx>=0.27", "pyjwt"] [build-system] requires = ["hatchling"] build-backend = "hatchling.build"

vs Maven / npm

Java: pom.xml + the local ~/.m2 repo isolate per-project deps; a JAR ≈ a wheel. npm: package.json + package-lock.json ≈ pyproject.toml + a lockfile; node_modules ≈ a venv. Python just made these standard later, so older tutorials show the pre-pyproject world.

CIAM context: Auth code is where supply-chain integrity matters most. Lock with hashes so a compromised upstream can't slip a malicious version into your token-validation path; one venv per service contains a vulnerable dependency; host internal auth libraries on a private index; and publish via trusted publishing (OIDC) rather than a long-lived PyPI token. Zero-trust for your dependencies, not just user sessions.

1. Virtual Environments — Isolation First

# create + activate an isolated environment
python -m venv .venv
source .venv/bin/activate # macOS/Linux
.venv\Scripts\activate # Windows

# now pip installs land in .venv, not system Python
pip install httpx
which python # → .../.venv/bin/python
deactivate

A virtual environment is a self-contained directory with its own interpreter link and site-packages. Activating it puts that environment's python/pip first on your PATH, so installs are scoped to the project. This prevents version conflicts between projects and keeps the system Python clean. Add .venv/ to .gitignore — you commit the spec (lockfile), not the installed bytes.

Tooling is converging on faster wrappers. uv venv creates environments in milliseconds; pipx installs CLI apps each in their own isolated venv; Poetry/hatch manage one per project automatically. They all produce the same kind of isolated environment — the concept is what matters.

2. pip & Dependency Locking

GoalCommand / fileNotes
install a packagepip install httpxgrabs the latest compatible — non-deterministic
install your project (dev)pip install -e .editable: code changes apply without reinstall
declared depspyproject.toml [project] dependenciesloose ranges, e.g. httpx>=0.27
locked depsrequirements.lock (pip-compile / uv lock)exact versions + hashes → reproducible
install from lockpip install -r requirements.lock--require-hashes rejects tampered packages
Declare loosely, install from a lock. Your pyproject.toml states intent (httpx>=0.27); a lockfile records the exact resolved graph with hashes for reproducible, auditable installs. CI installs from the lock so production matches dev byte-for-byte; you regenerate the lock deliberately when you want upgrades. Hash-pinning is your defense against a compromised upstream silently swapping a release.

3. pyproject.toml — The Modern Standard

[build-system] # PEP 517/518: how to build
requires = ["hatchling"]
build-backend = "hatchling.build"

[project] # PEP 621: metadata
name = "authlib"
version = "1.2.0"
requires-python = ">=3.11"
dependencies = ["httpx>=0.27", "pyjwt"]

[project.optional-dependencies]
dev = ["pytest", "ruff"]

[project.scripts]
authlib = "authlib.cli:main" # console entry point

One declarative file replaces setup.py + setup.cfg + requirements.txt. [build-system] names the build backend (hatchling, setuptools, flit, pdm…), making builds tool-agnostic. [project] holds standardized metadata and dependencies; optional-dependencies defines extras (pip install authlib[dev]); [project.scripts] generates CLI entry points. Linters/formatters (ruff, mypy) read their config from here too — a single source of truth.

Declarative beats executable config. The old setup.py ran arbitrary Python at build time (slow, unsafe to introspect). pyproject.toml is pure data a tool can parse without executing it — which is also why supply-chain scanners and IDEs can reliably read your project's metadata.

4. Build & Publish

python -m build # → dist/
# authlib-1.2.0.tar.gz (sdist, source)
# authlib-1.2.0-py3-none-any.whl (wheel)

twine check dist/*
twine upload --repository testpypi dist/* # dry run
twine upload dist/* # PyPI

# better: trusted publishing (OIDC) from CI —
# no long-lived token stored anywhere

python -m build produces two artifacts: an sdist (source tarball, built on install) and a wheel (pre-built zip that installs without a build step — faster and the default for consumers). twine uploads them to PyPI, TestPyPI, or a private index. The modern best practice is trusted publishing: GitHub Actions exchanges a short-lived OIDC token with PyPI, so no permanent API token lives in your secrets.

Wheel vs sdist, and why OIDC publishing matters. A wheel is already built for an ABI/platform tag, so pip just unzips it; an sdist must be compiled on the user's machine. Ship both. And because a leaked PyPI token lets an attacker publish a poisoned release of your auth library, trusted publishing (ephemeral OIDC credentials) removes that standing secret entirely — the supply-chain analog of short-lived user sessions.
