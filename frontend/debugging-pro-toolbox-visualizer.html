Debug Like a Pro — The Professional Toolbox

"Add a print statement" and "step through it in the debugger" stop scaling once a bug lives in 10,000 loop iterations, a race between two threads, or a request that fails three services away from where you're looking. This page is the toolbox professionals reach for once those two moves aren't enough — not the scientific method itself (see The Debugging Method) and not the log-vs-debugger choice (see Log vs Debugger). This is what you do once you've picked your tool and need to actually use it well.

🧰 What's actually in the professional toolbox?

git bisect automates the commit-history half of bisecting: instead of eyeballing 50 commits, you tell git one known-good and one known-bad commit, and it checks out the midpoint for you, over and over, narrowing a 50-commit range to the exact culprit in about 6 tests (log₂50). Conditional breakpoints and watch expressions are what separate "I have a debugger open" from using one efficiently: an unconditional breakpoint inside a 10,000-iteration loop stops 10,000 times, but a condition like order.getId().equals("ORD-9821") makes the debugger silently evaluate and skip every iteration except the one that matters — you land exactly at the failure with a full variable inspector, instead of clicking "continue" 9,999 times. A logpoint is the same idea aimed at production-shaped problems: it's a breakpoint that logs an expression and keeps running instead of halting — you get the visibility of a print statement without redeploying code to add one. Structured logging with correlation IDs is how you debug a request you can't attach a debugger to at all: one ID, generated at the edge and threaded through every service and log line that request touches, turns "grep three separate log files and guess which lines belong together" into "grep one ID." Profilers, heap dumps, and thread dumps answer the questions a debugger can't: not "what is this variable right now" but "what has every thread been doing for the last 30 seconds" or "what's actually holding onto memory." And when none of that's enough on your own, asking for help well — a tight repro, expected vs. actual, what you've already ruled out — is still a debugging skill, not an admission of failure.

  • git bisect — binary-searches commit history automatically; you just answer good/bad at each checkout.
  • Conditional breakpoints & watches — stop only when a condition is true, or only when a watched value changes; the debugger does the filtering, not you clicking through.
  • Logpoints — log an expression without halting execution; production-safe visibility without a redeploy.
  • Correlation IDs — one ID threaded through every service a request touches, so distributed logs become searchable as one story.
  • Dumps & profilers — thread dumps catch deadlocks and hangs; heap dumps and profilers catch leaks and slowness that no single breakpoint would ever land on.

A conditional breakpoint is a filter, not a pause button

The debugger still evaluates the condition on every hit — it just doesn't stop unless it's true. That evaluation has a real cost in a hot loop, which is why IDEs let you combine a condition with a hit count ("break on the 47th hit") when you already know roughly where the bad iteration lives.

A logpoint doesn't touch your source file

Because it's set in the debugger/IDE, not compiled into the code, you can add and remove logpoints in a running process without a redeploy — the closest thing to "adding a print statement" that's actually safe to do against production.

A thread dump is free — you don't need a profiler running

jstack <pid> or Spring's /actuator/threaddump gives you an instant snapshot of every thread's exact stack, with zero setup cost — it's the first thing to reach for the moment an app hangs instead of crashes.

The CIAM parallel: a login request in this codebase crosses at least three log-owning layers — Angular's HTTP interceptor, the Spring filter chain (CustomAuthFilter, then the identity provider call), and the JDBC repo layer underneath it. Without a correlation ID, a failed login shows up as three unrelated-looking log lines in three places. With one — generated the moment the request hits Angular and threaded through every hop, including the outbound call to Ping or Entra — grep correlationId=a1b2c3 reconstructs the whole request's path in one shot. A few things worth knowing

  • Bisecting a whole test suite instead of the failing test wastes cycles — point git bisect run at the narrowest command that reproduces the regression (one test class, not the whole suite), since it's going to run that command ~log₂(N) times.
  • A watch expression that's expensive to evaluate slows the whole debug session — prefer watching a field over a method call with side effects; some debuggers re-run the expression on every single step, not just at breakpoints.
  • A good bug report is itself a debugging tool — writing "expected X, got Y, here's the minimal repro, I've already ruled out A and B" forces the same rigor as forming a hypothesis, and often surfaces the answer before anyone else reads it.
  • A thread dump only catches what's true at that instant — a deadlock (threads permanently stuck) shows up reliably in one dump; a transient contention issue may need several dumps a few seconds apart to see the pattern.
