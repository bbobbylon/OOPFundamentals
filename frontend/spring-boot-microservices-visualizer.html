Microservices Architecture Patterns with Spring Boot

Design distributed systems that scale independently, deploy separately, and fail gracefully. Understand the patterns before reaching for the tools.

🧩 What are microservices — and why are they harder than a monolith even when they help?

A monolith is one deployable unit — a single Spring Boot app for users, orders, payments, and notifications. It's simple to build and debug, but you scale and deploy all of it together. Microservices split it into independently deployable services that scale, deploy, and evolve on their own. The cost is real: in-process calls become HTTP calls, bringing network latency, partial failures, distributed transactions, service discovery, and roughly 10× the infrastructure. The rule: start with a monolith and extract a service only for a concrete reason — e.g. the payments team ships 20×/day and the user team weekly, and coupling them slows both.

  • Independence is the benefit; the distributed system is the bill.
  • Default to a monolith. Split on a real constraint (team cadence, divergent scaling), not fashion.
  • Resilience patterns are mandatory once calls cross the network — gateway, discovery, circuit breaker, saga.
  • Service-to-service auth is Client Credentials — never forward a user's token between services.

Key patterns

API Gateway (one entry: routing, auth, rate limit), Service Discovery (Eureka / K8s DNS), Circuit Breaker (Resilience4j fallback), Saga (local transactions + compensations), and Event-Driven (Kafka/RabbitMQ instead of sync HTTP).

Auth across services

Either the gateway validates the JWT once and downstream services trust it, or each service validates independently (more secure, a little slower). For service-to-service calls use Client Credentials machine tokens — never forward the user's token (different scope, no user context leaked).

When NOT to

Avoid with a 1–3 dev team, an early product with weekly-changing requirements, no DevOps automation, or no distributed-systems experience. Worth it for large teams with independent releases, very different scaling needs, firm domain boundaries, and strong K8s automation.

CIAM: At scale: AuthService (OIDC, token issuance), UserService (CRUD/search), AuditService (write-heavy, own DB), NotificationService (email/SMS). The gateway validates the JWT once; services call each other with Client Credentials; AuditService subscribes to Kafka topics rather than being called directly. But for a 3-person team, one monolith with auth/users/audit packages is simpler and just as maintainable.

or, "talking to another service" and "acting as the user" are two different questions — microservices make you answer both, every time

The problem

Your OrderService → AuditService call worked in every test. Then a scheduled job tried to log an event, and there was no user around to blame it on.

It worked for months — right up until nothing HTTP triggered the call

OrderService forwards the caller's JWT to AuditService on every write, because that token is already sitting in the request thread and forwarding it is one line: .header("Authorization", incomingAuthHeader). Every controller-triggered call passes it along, every test goes through an authenticated HTTP request first, so every test is green. Then someone adds a nightly reconciliation job — a plain @Scheduled method, no incoming request, no JWT anywhere to forward — and it also needs to write an audit event. AuditService starts rejecting it with 401s that make no sense, because there genuinely is no token to forward, and nobody ever built a second path.

every controller-triggered call worked ✓ unit tests all green ✓ no JWT exists outside a request thread ⚠ AuditService has never had to authenticate "the system itself" ⚠

The wrong assumption: that AuditService's caller is always "a user, via a request." Writing an audit row isn't done on the user's authority — it's the system doing system things.

Ask which authority the call actually needs — before picking a token
Call is on behalf of the logged-in user's own data → forward or relay their JWT ↓ e.g. OrderService asking UserService for the current user's own profile Call is the system acting, regardless of trigger → Client Credentials, a service-level token ↓ e.g. an audit write, an IdP sync, a scheduled job with no user in the picture at all Now the scheduled job and the HTTP-triggered call authenticate identically
Every service call answers two separate questions: who's calling, and on whose authority. Forwarding the user's JWT answers both with "the user" — correct when that's literally true (they asked for their own data), wrong the moment the call is really the system acting, because then there's no user authority to invoke and, eventually, nothing sitting in a thread to forward at all.
Think of it like a company mailroom clerk. Ask the clerk to send your personal package and they sign for it as you — your name goes on the slip, because you're the one who asked. When the company itself needs to ship its routine invoices every night, the clerk signs as the company, not as whichever employee happened to be nearby — because no particular employee asked for it. Try to ship the nightly invoices under some random employee's name and the signature makes no sense to whoever receives it. That's the scheduled job with a forwarded token that doesn't exist.
You

OrderService already has the user's JWT sitting right there in the request. Why not just pass it along to AuditService?

OrderService

Because I only have that JWT while I'm inside an actual HTTP request. The moment something calls me without one — a scheduled job, a Kafka listener — I have nothing left to forward, and I still owe AuditService that write.

AuditService

And from where I sit, I can't tell "a legitimate system write" from "someone forged a header" unless I know which kind of authority I'm supposed to trust. I need to trust Client Credentials tokens for service-to-service calls as a rule — not just on the days a user happens to be attached.

The Client Credentials grant

That's what I'm for. I don't represent a user at all — I represent OrderService itself, with its own client ID and its own scopes. I exist and I'm valid whether a human triggered this request or a cron job did.

The mechanism

One call path for a click. One call path for a cron job. Same authentication code either way.

  1. A request reaches OrderService — either from a user (HTTP, JWT present) or from nothing external at all (a @Scheduled trigger, no JWT)two very different starting points
  2. OrderService decides which authority the downstream call actually needs — "on behalf of this user," or "the system, regardless of trigger"the real design decision
  3. If it's on behalf of the user: relay the validated JWT, scoped to exactly what that call needstoken relay — legitimate, not a shortcut
  4. If it's the system acting: request a Client Credentials token using OrderService's own client ID and secret against the IdP's token endpointno user in this token at all
  5. AuditService validates whichever token shows up the same way every time — signature, issuer, audience, scope — never by checking "is a user attached"AuditService doesn't need to know which path it came from
  6. The scheduled job and the HTTP-triggered call now hit the exact same authenticated endpoint, because both requested the token KIND that actually matched what they were doingthe fix that makes the bug impossible, not just handled

Step 2 is the lesson. Deciding which authority a given call needs is a design decision made once, up front — not something answered by "whatever token happens to be lying around in the thread." Retrofitting it later usually means finding every place a JWT got casually forwarded and asking, one call at a time, whether it was ever really on the user's authority to begin with.

OrderService needs to call AuditServicesame HTTP client, same endpoint, every time
whose authority is this call really on? →
Forward the user's JWT — this call is on behalf of one specific logged-in user Request a Client Credentials token — this call is the system itself, no user involved Trust the call because it came from inside the private network — no token at all

AuditService's endpoint doesn't change based on which of these gets picked — same URL, same verb. What changes is which token lands in the Authorization header, and that's the whole decision: does this specific call carry a user's authority, or the system's? The third option is the one the CodeWalk below calls out as unsafe for anything multi-tenant — "inside the network" isn't an identity, so there's nothing left to check against.

NotificationService needs to send a password-reset email. The flow starts at a public, unauthenticated POST /api/password-reset on the gateway — there's no logged-in user, so no user JWT exists anywhere in this request. How should the call from AuthService to NotificationService authenticate?

Right — there's no user to act on behalf of, so don't invent one. Client Credentials represents AuthService itself, which is exactly the authority this call actually has.

Tempting because it's the least code — but a service token and a user token mean different things to whatever validates them downstream. If NotificationService, or anything auditing its calls, ever assumes a token in that slot represents a specific human, blending the two breaks that assumption silently instead of failing loudly.

This reads like consistency, but it manufactures an identity that never existed. There was no logged-in user in this flow — pretending there was one just to keep the code path uniform makes the audit trail lie about who did what, which is worse than the two paths looking slightly different.

Where you've seen this before

Three systems, one split: is this the user's authority, or the system's own?

AWS IAM instance roles vs. a user's own credentials

An EC2 instance or Lambda function assumes an IAM role to call other AWS services — completely separate from any IAM user's personal credentials, on purpose. The instance's authority exists independent of any person, the same way OrderService's Client Credentials token does.

instance role ≈ client credentials

A Unix cron job running as its own service account

A 3am cron job doesn't run "as you," even on a box you personally set it up on — it runs as a dedicated service account, precisely so it keeps working (and keeps its blast radius contained) whether or not you're logged in, and doesn't silently exercise your personal permissions.

service account ≈ client credentials

CIAM: the IdP's own logs tell service traffic apart from user traffic

When a service authenticates via Ping's or Entra's client_credentials grant, the client ID that shows up in the IdP's own audit log for that call is the service's registered client — not any user. That's what makes "which service called which, and when" something you can actually query later, independent of whatever user traffic was happening at the same moment.

separate client ID = separate audit trail
Questions from the back row

Doesn't Client Credentials mean OrderService can now call anything, with no restriction at all?

No — Client Credentials tokens carry scopes just like user tokens do, just scoped to what that service is registered to do rather than to a person. OrderService's client registration in Ping or Entra should only be granted what it actually needs (say, audit:write), not blanket access. The whole point of giving each service its own client ID is being able to restrict, rotate, or revoke one service's access without touching any other service, or any user.

If a circuit breaker trips because AuditService is down, does OrderService's request fail too?

That depends entirely on whether the fallbackMethod treats the audit write as critical or best-effort. For most systems it shouldn't be critical — the fallback should queue the event (locally, or onto a durable topic) and let OrderService's own response to the customer succeed anyway. Failing someone's checkout because the audit trail is temporarily unreachable is usually the wrong trade-off, and that's a business decision the fallback method encodes — Resilience4j doesn't decide it for you.

Does a Saga's compensating transaction need its own authority story too?

Yes, and it's easy to miss. A compensating call like inventoryClient.releaseReservation(orderId) is the system undoing its own earlier action — not a user asking for anything — so it authenticates the same way a scheduled job or an audit write does, with the service's own Client Credentials. Never with whatever user token started the original saga, which may well have expired by the time the compensation actually runs.

1. Monolith vs Microservices — When to Split

Monolith — Start Here

PRO Simple deployment — one artifact, one process
PRO Simple debugging — one stack trace, one log stream
PRO Easy transactions — one DB, ACID everywhere
CON Scale entire app to scale one bottleneck component
CON Single team owns all — merge conflicts at scale
CON One bad deployment can break everything
Martin Fowler's rule: "Don't start with microservices." Build a modular monolith first. Extract services when you have clear bounded context boundaries and the scaling/team need is real.

Microservices — When Justified

PRO Scale only the bottleneck — payment service needs 10x, auth needs 1x
PRO Team autonomy — each team owns/deploys their service independently
PRO Technology diversity — Python ML model alongside Java API
CON Network calls fail — you need circuit breakers, retries, timeouts
CON Distributed transactions are hard — no ACID across services
CON Operational complexity — N services, N deployments, distributed traces

DDD Decomposition — Bounded Contexts

E-Commerce Domain
├── UserService (identity, authentication)
├── ProductService (catalog, inventory)
├── OrderService (cart, checkout, orders)
├── PaymentService (billing, refunds)
└── NotificationService (email, SMS)
Each context = separate DB = no shared tables

2. Service-to-Service Communication

Synchronous — OpenFeign

<!-- pom.xml --> <dependency> <groupId>org.springframework.cloud</groupId> <artifactId>spring-cloud-starter-openfeign</artifactId> </dependency> // Enable on main class or config @EnableFeignClients // Declare interface — Spring generates HTTP client @FeignClient( name = "inventory-service", url = "${inventory-service.url}", // from config fallback = InventoryFallback.class // Circuit breaker ) public interface InventoryClient { @GetMapping("/api/inventory/{sku}") InventoryResponse checkStock( @PathVariable String sku); @PostMapping("/api/inventory/reserve") ReservationResponse reserve( @RequestBody ReserveRequest req); } // Fallback implementation @Component class InventoryFallback implements InventoryClient { public InventoryResponse checkStock(String sku) { return InventoryResponse.unavailable(); } }

Synchronous with RestClient (Spring 6.1+)

@Bean public RestClient inventoryClient() { return RestClient.builder() .baseUrl("${inventory-service.url}") .defaultHeader("Accept", "application/json") .build(); } // Usage in service InventoryResponse stock = restClient .get() .uri("/api/inventory/{sku}", sku) .retrieve() .body(InventoryResponse.class);

Asynchronous — Events / Messages

// With Kafka (resilient, decoupled) @Component public class OrderEventPublisher { @Autowired private KafkaTemplate<String, OrderCreatedEvent> kafka; public void publishOrderCreated(Order order) { kafka.send("orders.created", order.getId().toString(), new OrderCreatedEvent(order)); } } // Inventory service listens to Kafka topic @Component public class InventoryEventConsumer { @KafkaListener(topics = "orders.created", groupId = "inventory-service") public void onOrderCreated( @Payload OrderCreatedEvent event) { inventoryService.reserve(event.getOrderId(), event.getItems()); } } // application.yml spring: kafka: bootstrap-servers: kafka:9092 consumer: group-id: inventory-service auto-offset-reset: earliest
Sync (Feign/RestClient): Immediate response needed, simpler, but caller blocks and target failures cascade.
Async (Kafka/RabbitMQ): Better resilience, loose coupling, but eventual consistency and harder debugging.

API Gateway handles cross-cutting concerns: JWT validation, rate limiting, request logging, CORS, SSL termination — so microservices don't each have to implement them.

4. Saga Pattern — Distributed Transactions

No 2PC (Two-Phase Commit) in microservices — it creates tight coupling and is fragile. The Saga pattern handles distributed transactions through a series of local transactions, each with a compensating transaction that can undo the work.

Choreography Saga

No central coordinator. Each service publishes events; the next service reacts. Simpler but harder to track.

// OrderService @Transactional public Order createOrder(CreateOrderRequest req) { Order order = repo.save(new Order(req, "PENDING")); events.publish(new OrderCreatedEvent(order)); return order; } // InventoryService reacts @KafkaListener(topics = "orders.created") void onOrderCreated(OrderCreatedEvent e) { try { inventoryService.reserve(e.getItems()); kafka.send("inventory.reserved", e.getOrderId()); } catch (OutOfStockException ex) { // Compensating event — tells Order to cancel kafka.send("inventory.reservation.failed", e.getOrderId()); } } // OrderService compensates @KafkaListener(topics = "inventory.reservation.failed") void onReservationFailed(String orderId) { orderRepo.updateStatus(orderId, "CANCELLED"); kafka.send("orders.cancelled", orderId); }

Orchestration Saga

Central orchestrator (a Spring bean or state machine) calls services in order, tracks state, handles failures.

@Component public class CreateOrderSaga { public void execute(Long orderId) { try { // Step 1 inventoryClient.reserve(orderId); // Step 2 paymentClient.charge(orderId); // Step 3 orderRepo.updateStatus(orderId, "CONFIRMED"); } catch (PaymentFailedException e) { // Compensate step 1 — release reservation inventoryClient.releaseReservation(orderId); orderRepo.updateStatus(orderId, "CANCELLED"); } } }

6. CQRS & Event Sourcing

CQRS — Command Query Responsibility Segregation

Separate the write model (Commands) from the read model (Queries). Writes go to a normalized DB; reads come from a denormalized projection optimized for queries.

// Command side — normalized domain model @RestController @RequestMapping("/api/orders") public class OrderCommandController { @PostMapping public ResponseEntity<?> createOrder( @RequestBody CreateOrderCommand cmd) { commandBus.send(cmd); // write to SQL DB return ResponseEntity.accepted().build(); } } // Query side — denormalized read model (e.g. MongoDB/Redis) @RestController @RequestMapping("/api/orders/view") public class OrderQueryController { @GetMapping public List<OrderSummaryView> list(...) { // Query from pre-built view, no JOINs needed return orderViewRepo.findAll(...); } }

Event Sourcing

Instead of storing current state, store every event that happened. Rebuild state by replaying events. Perfect audit trail.

// Events are the source of truth record OrderCreated(UUID id, String customer, ...) {} record ItemAdded(UUID orderId, String sku, int qty) {} record OrderConfirmed(UUID orderId) {} record OrderCancelled(UUID orderId, String reason) {} // Event store — append-only table // CREATE TABLE events ( // id BIGSERIAL, stream_id UUID, // type VARCHAR, payload JSONB, // occurred_at TIMESTAMPTZ // ); // Rebuild order state by replaying events public Order load(UUID orderId) { List<Event> events = eventStore.load(orderId); Order order = new Order(); events.forEach(order::apply); // fold over events return order; } // Benefits: full audit trail, temporal queries, // rebuild any projection from history, time-travel
Event Sourcing adds significant complexity. Use it only when audit trail, temporal queries, or event-driven projections justify the trade-off. Most apps don't need it.
