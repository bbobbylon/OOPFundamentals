Spring Boot Profiles — Deep Dive

One codebase, many environments. Profiles let you switch datasources, feature flags, logging levels, and entire beans without touching source code.

What do Spring profiles let you do beyond just switching database URLs?

Spring profiles are broader than most developers realise. Yes, you can switch datasources and config values between dev/staging/prod. But profiles also control which beans are loaded: @Profile("dev") @Bean MockEmailService emailService() — in dev, emails go to the mock (printed to console); in prod, @Profile("!dev") @Bean SmtpEmailService emailService() actually sends. This eliminates the classic "accidentally sent real emails to production users from a dev environment" incident. Profiles also control which test configurations load, which external service mocks are active, and which feature flags are enabled. Profile groups (Spring 2.4+) let you activate multiple profiles at once: spring.profiles.group.staging=db-staging,feature-flags-staging,metrics — activate "staging" and all three are activated.

Profile activation

Set active profile: spring.profiles.active=prod in application.yml (but override with env var is better). Env var: SPRING_PROFILES_ACTIVE=prod (K8s: set in pod spec). Command line: java -jar app.jar --spring.profiles.active=prod. Multiple profiles: SPRING_PROFILES_ACTIVE=prod,metrics — both are active. application-prod.yml is loaded and merged with (overriding) application.yml. Default profile: when no profile is active, @Profile("default") beans load.

@Profile on beans

@Profile("!prod") — active in any non-production profile. @Profile("dev | test") — active in dev OR test. @Profile("prod & !eu") — active in prod but not when eu profile is also active. Use on: @Bean methods in config classes, @Component/@Service/@Repository classes, @Configuration classes to conditionally load an entire config block. If two beans implement the same interface, only the one matching the active profile loads.

Test profiles

@SpringBootTest @ActiveProfiles("test") — loads application-test.yml (H2 in-memory DB, mock external services, fast startup). @TestPropertySource for individual test overrides. Never run tests against the dev or prod database — use a test profile with H2 or a Testcontainers-managed PostgreSQL. Profile: test should also disable Flyway migration (use spring.flyway.enabled=false in test profile and use spring.jpa.hibernate.ddl-auto=create-drop instead).

In CIAM: Profiles: dev (H2, mock Ping, mock email, DEBUG logging), test (H2, Testcontainers for Redis, mock Ping via WireMock), staging (real PostgreSQL, Ping sandbox, real SMTP to a staging inbox, INFO logging), prod (real PostgreSQL, real Ping Federate, real SMTP, WARN logging, Actuator on internal port only). @Profile("!prod") @Bean WireMockPingServer pingMock() — in dev/test, HTTP calls to Ping go to WireMock instead. Add @Profile("prod") to the real Ping OAuth2 client bean. Never send real tokens to a prod IDP from a dev environment.

1. What Problems Do Profiles Solve?

Every non-trivial application runs in multiple environments: local development, CI, staging, and production. Each environment needs different config — a local H2 database vs a production PostgreSQL cluster, debug logging vs warn-only, mocked external APIs vs real ones. Without profiles you'd need separate builds or dangerous environment-detection hacks in code.

Spring Boot auto-discovers profile-specific config files. No code change needed — just set the active profile and the right config is applied automatically.

2. Profile Configuration Files

Spring Boot loads configuration files in a specific order. Later sources override earlier ones for the same property key.

File naming convention

# Always loaded (default values) src/main/resources/ application.yml # base config application-dev.yml # loaded when profile=dev application-staging.yml # loaded when profile=staging application-prod.yml # loaded when profile=prod application-test.yml # loaded when profile=test

application.yml (base)

spring: application: name: my-service datasource: url: jdbc:h2:mem:testdb # default username: sa jpa: show-sql: false server: port: 8080 logging: level: root: INFO

application-dev.yml (overrides)

spring: datasource: url: jdbc:h2:mem:devdb username: dev_user jpa: show-sql: true # override! hibernate: ddl-auto: create-drop logging: level: root: DEBUG # override! com.myapp: TRACE

application-prod.yml (overrides)

spring: datasource: url: ${DB_URL} # from env vars username: ${DB_USER} password: ${DB_PASS} hikari: maximum-pool-size: 20 jpa: hibernate: ddl-auto: validate # NEVER create! logging: level: root: WARN

4. How to Activate a Profile

In application.yml

spring: profiles: active: dev # multiple: dev,metrics
Don't hard-code profiles in application.yml for staging/prod — use environment variables or CI/CD tooling instead. This is fine for dev defaults.

Environment variable

# Linux/Mac export SPRING_PROFILES_ACTIVE=prod # Windows PowerShell $env:SPRING_PROFILES_ACTIVE = "prod" # Docker / Kubernetes env: - name: SPRING_PROFILES_ACTIVE value: "prod,metrics"

Command-line argument

java -jar app.jar \ --spring.profiles.active=prod # Maven Spring Boot plugin mvn spring-boot:run \ -Dspring-boot.run.profiles=dev

In tests — @ActiveProfiles

@SpringBootTest @ActiveProfiles("test") class UserServiceIntegrationTest { @Autowired private UserService userService; @Test void shouldSaveUser() { // uses application-test.yml config // typically H2 + test data } }

Profile Groups (Spring Boot 2.4+)

spring: profiles: group: production: prod,metrics,tracing ci: test,mocks # Activating "production" auto-activates: # prod + metrics + tracing profiles # Great for consistent multi-profile combos
Profile groups are a clean way to name environment tiers. Your CI sets SPRING_PROFILES_ACTIVE=ci and gets test + mocks automatically.

Programmatic check

@Component class StartupLogger { @Autowired private Environment env; @PostConstruct void log() { String[] profiles = env.getActiveProfiles(); log.info("Active: {}", profiles); } }

5. @Profile on Beans — Interactive Demo

Annotating a @Component or @Bean method with @Profile tells Spring to only register it when the named profile is active. The ApplicationContext simply won't contain the bean otherwise.

// Interface — same API regardless of environment public interface NotificationService { void send(String message); } // Only loaded in dev — prints to console @Profile("dev") @Service public class ConsoleNotificationService implements NotificationService { public void send(String msg) { log.info("[DEV] {}", msg); } } // Only loaded in prod — sends real email via SES @Profile("prod") @Service public class SesNotificationService implements NotificationService { public void send(String msg) { sesClient.send(...); } } // Negation — loaded in everything EXCEPT prod @Profile("!prod") @Component public class DevDataSeeder { ... } // Multiple profiles — loaded if dev OR staging is active @Profile({"dev", "staging"}) @Bean public DataSource localDataSource() { ... }

6. @Conditional Annotations — Fine-Grained Bean Conditions

@Profile is a simple profile name check. Spring provides richer conditionals that check properties, presence of beans or classes, and arbitrary SpEL expressions.

@ConditionalOnProperty
Bean is created only when a specific property has a given value (or just exists).
@ConditionalOnProperty(name="feature.cache.enabled", havingValue="true", matchIfMissing=false)
@ConditionalOnMissingBean
Bean is created only if no bean of the specified type is already registered. Used by auto-configuration to provide defaults that users can override.
@ConditionalOnMissingBean(CacheManager.class)
@ConditionalOnBean
Bean is created only if a bean of the specified type IS already registered. Useful for "if the user configured X, also configure Y".
@ConditionalOnBean(DataSource.class)
@ConditionalOnClass
Bean is created only if a specific class is on the classpath. This is how Spring Boot auto-configurations work — check if the starter dependency is present.
@ConditionalOnClass(RedisConnectionFactory.class)
@ConditionalOnMissingClass
Opposite of @ConditionalOnClass — bean loaded when a class is NOT on the classpath. Use for fallback implementations.
@ConditionalOnExpression
SpEL expression must evaluate to true. Most powerful but also most fragile — use sparingly.
@ConditionalOnExpression("'${app.mode}' == 'batch' and ${feature.enabled:false}")
@ConditionalOnWebApplication
Only active in a web application context (not in a CLI runner or batch job).
Type attribute: SERVLET, REACTIVE, or ANY

Auto-Configuration pattern — how Spring Boot uses these:

@Configuration @ConditionalOnClass({ DataSource.class, EmbeddedDatabaseType.class }) @ConditionalOnMissingBean(type = "io.r2dbc.spi.ConnectionFactory") @EnableConfigurationProperties(DataSourceProperties.class) public class DataSourceAutoConfiguration { @Bean @ConditionalOnMissingBean(DataSource.class) // user can override! public DataSource dataSource(DataSourceProperties props) { return props.initializeDataSourceBuilder().build(); } }
This is the "convention over configuration" magic. Spring Boot auto-configures a DataSource only if: (a) DataSource.class is on the classpath, and (b) you haven't defined your own DataSource bean.

7. Testing with Profiles

application-test.yml

spring: datasource: url: jdbc:h2:mem:testdb driver-class-name: org.h2.Driver jpa: hibernate: ddl-auto: create-drop show-sql: true flyway: enabled: false # use DDL auto instead external-api: url: http://localhost:${wiremock.port}

Test-specific @Configuration

@TestConfiguration // not picked up by main app public class TestEmailConfig { @Bean @Primary // overrides the real bean public EmailService mockEmailService() { return mock(EmailService.class); } }

Integration test with profile

@SpringBootTest(webEnvironment = RANDOM_PORT) @ActiveProfiles("test") @Import(TestEmailConfig.class) class OrderControllerIT { @Autowired private TestRestTemplate restTemplate; @Test void createOrder_returns201() { var req = new CreateOrderRequest("item1"); var resp = restTemplate.postForEntity( "/api/orders", req, OrderResponse.class); assertThat(resp.getStatusCode()) .isEqualTo(HttpStatus.CREATED); } }

Slice test — no full context

@DataJpaTest // auto-uses H2 + test profile @ActiveProfiles("test") class UserRepositoryTest { @Autowired private UserRepository repo; @Test void findByEmail_returnsUser() { repo.save(new User("alice@example.com")); assertThat(repo.findByEmail("alice@example.com")) .isPresent(); } }
@TestConfiguration vs @Configuration: @TestConfiguration beans are only available in tests. @Configuration in the main source tree is always loaded. Never use @SpringBootApplication in a test config class — it triggers a full component scan.
