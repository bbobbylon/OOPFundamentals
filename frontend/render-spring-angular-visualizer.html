Spring Boot + Angular on Render

or, two services, one origin, and a CORS problem you can delete instead of configuring

🧩 Why does a Spring Boot + Angular app become two Render services, and what joins them back together?

Because the two halves want opposite things. Angular compiles to static files — they want a CDN, and there is nothing to keep running. Spring Boot is a process that must stay alive — it wants a container, a port and a health check. Deploy each as what it is and you get the best of both: a front end that is free and always instant, and a backend you can size independently. The cost is that you now have two hostnames, and by default the browser treats those as two different origins — which is where CORS comes from.

  • Angular → runtime: static. Built once, served from a CDN. No port, no health check, nothing that can fall asleep.
  • Spring Boot → runtime: docker. Render has no native Java runtime, so you write the Dockerfile — and get to pin the exact JDK.
  • One rewrite rule deletes CORS. Point /api/* at the API's URL and every call becomes same-origin.
  • Order matters. The catch-all /* rule must come last, or it swallows your API calls and answers them with HTML.

What "same origin" means, exactly

Scheme + host + port, all three matching. devhub.onrender.com and devhub-api.onrender.com differ in the host, so they are separate origins — the browser does not care that both are yours. A rewrite works because it happens on the server: the browser only ever asked for a path on the site it was already on.

Rewrite vs redirect — the difference is everything

A rewrite quietly serves the destination's content at the original path; the address bar never changes and the browser learns nothing. A redirect tells the browser to go fetch it from the other host itself — which puts you right back to two origins and every CORS rule you were trying to avoid.

Spring / CIAM: collapsing to one origin makes session cookies first-party, so SameSite=Lax works and third-party-cookie blocking stops being your problem. The catch is the OIDC redirect_uri: it must be the address the browser is at, not the API's own hostname — and behind a rewrite, Spring will build the wrong one unless you set server.forward-headers-strategy=framework.

Your API is at devhub-api.onrender.com. Your Angular app is at devhub.onrender.com. Two different origins, so every call gets a preflight, a CORS configuration, an allowCredentials decision and a cookie policy you have to think about. What if the browser simply never found out there were two services?

The idea

Deploy them as two services, and then hide the seam with one routing rule.

The natural shape for this stack on Render is two services and a database, and the two services are deliberately unalike:

  • Angular becomes a static site — runtime: static. Render builds it once, then serves the result from a CDN with HTTP/2 and Brotli. There is no container, no port, nothing to health check, and nothing that can fall asleep. Static sites are free.
  • Spring Boot becomes a Docker web service — runtime: docker, because Render has no native Java runtime. You write a multi-stage Dockerfile, which turns out to be an advantage: you pin the exact JDK, and you ship a JRE-sized image rather than a build-toolchain-sized one.

Then the good part. A static site's rewrite rule can point at a full public URL, not just a path inside itself. Send /api/* to the API's URL and the browser only ever talks to one origin — so there is no cross-origin request, therefore no preflight, therefore no CORS configuration to get wrong. You don't configure the problem away; you arrange for it not to exist.

Worth sitting with, because most tutorials teach the other path: deploy two origins, then spend an afternoon on @CrossOrigin, allowedOrigins, allowCredentials, and the special rule that you may not combine allowCredentials(true) with a wildcard origin. All of that is real and all of it is avoidable here. The one-line rewrite makes your API a path on your own site, and every cross-origin rule stops applying — including the third-party-cookie behaviour that quietly breaks session auth in browsers that block them.

  1. Angular asks for /api/users — a path, not a URLthe call this only works if your environment file says apiUrl: '/api'; name the API's host and you have two origins again
  2. the browser checks the origin — same page, same hostno preflight no OPTIONS round trip, no Origin header, no CORS rules apply at all
  3. Render matches the request against your routes, top downfirst match wins a real file at that path always wins first — which is why your JS bundles are unaffected
  4. /api/* matches, so the request is rewritten to the API's URLthe trick server-side, so the address bar never changes and the browser never learns another host exists
  5. Spring answers — but now sees a proxy, not the clientthe cost the real scheme, host and IP arrive in X-Forwarded-*; set forward-headers-strategy=framework to read them
  6. anything that did not match falls through to /* → index.htmlthe payoff so deep links and refreshes work — and this rule must be LAST, or step 4 never happens

Step 3 is the whole page in one line. Put the catch-all first and /* matches /api/users too, so the CDN answers your API call with your index page — 200 OK, plausible headers, and <!doctype html> where the JSON should be. The error you would get is "Unexpected token '<'", which reads like a backend bug and is not one.

Anatomy of the static site half

Four settings — and the fourth one is only correct because of where it sits in the list.

the build command

npm ci && npm run build. Use ci rather than install: it installs exactly what package-lock.json says and fails if the lockfile and package.json disagree, which is precisely the behaviour you want on a build machine. Anything a production build needs must be in dependencies or devDependencies — the build runs somewhere else, so "it works on my machine" carries no weight at all.

the publish directory — where Angular 17+ moved the goalposts

The folder that actually gets uploaded. For a modern Angular app using the application builder, that is dist/<project>/browser — note the browser subfolder, which did not exist before Angular 17 and is the single most common wrong answer here. Point at dist/<project> instead and Render happily publishes a directory whose only contents are a browser folder and possibly a server one, giving you a 404 at the root and no error anywhere. Check the real path with ls dist/* after a local build rather than trusting a tutorial written for Angular 15.

the rule that deletes CORS

type: rewrite, source: /api/*, destination: https://devhub-api.onrender.com/api/*. A rewrite serves the destination's content at the original path — the browser's address bar never changes and the browser never learns another host was involved. That is the whole trick: a request to /api/users is same-origin, so there is no preflight and no Origin check. (A redirect would do the opposite — it tells the browser to go to the other host itself, which reintroduces every cross-origin rule you were trying to avoid.)

the rule that fixes deep links

type: rewrite, source: /*, destination: /index.html. Angular's router is a client-side illusion: there is no file at /users/42, so a refresh or a pasted link asks the CDN for a file that does not exist. This rule answers every unmatched path with index.html and lets the router take it from there. And it is safe for your assets because Render does not apply a rule when a real file exists at that path — your JS, CSS and images are served as themselves.

the order — and why /* must be last

/* matches everything, including /api/users. Put it first and it swallows your API rule: every API call would be answered with the HTML of your index page, and your Angular code would report a JSON parse error while the network tab cheerfully shows 200 OK. Specific rules first, the catch-all last — the same top-down discipline as a Spring Security filter chain, where a broad /** matcher above a specific one makes the specific one dead code.

Your Angular app works when you click through it from the home page. But refreshing on /users/42, or opening that link directly, returns a 404 from Render.

If the route were misconfigured, clicking through wouldn't work either — and it does. That's the diagnostic: in-app navigation working while direct navigation fails means the problem is upstream of Angular, in whatever answered the HTTP request.

Exactly. Client-side routing is a fiction maintained by JavaScript that is already running. On a fresh load the browser genuinely asks the CDN for /users/42, there is no such file, and you get a 404 before a single line of Angular executes. The rewrite says "for anything you can't find, serve index.html" — Angular boots, reads the URL, and shows the right view. Your assets are unaffected, because Render skips the rule when a real file exists at the path.

A sleeping API produces a slow page or an error inside a working app — the shell still loads, because the shell comes from the CDN and the CDN never sleeps. A 404 on the document itself happens before any API call is made.

Find out where Angular actually put the build

Don't guess this from a tutorial. Build locally once and look, because the answer changed at Angular 17 and a wrong publish path produces a 404 with no error message anywhere to explain it.

$ npm run build && ls dist/devhub-web
browser/          ← this is what you publish
3rdpartylicenses.txt

$ ls dist/devhub-web/browser
index.html  main-K3F2P9QX.js  polyfills-B7NHCXTY.js  styles-8WQ2ZKMN.css

# staticPublishPath: dist/devhub-web/browser
the answer is the browser/ line. Publish dist/devhub-web and you ship a directory containing a folder — a 404 at the root, with a build log that says everything succeeded, because it did.
Make the JVM respect the container it lives in

A small instance and a JVM that sizes its heap from the wrong number is the classic "it just dies under load" on a platform. Modern JVMs are container-aware, but the percentage is worth setting explicitly so the number is visible in your Dockerfile instead of implied.

FROM eclipse-temurin:21-jre
ENV JAVA_TOOL_OPTIONS="-XX:MaxRAMPercentage=75"
$ java -XX:MaxRAMPercentage=75 -XX:+PrintFlagsFinal -version | grep MaxHeapSize
   size_t MaxHeapSize = 402653184    ← 384 MB of a 512 MB instance

# leaves headroom for metaspace, thread stacks and the OS.
# Give the JVM 100% and the kernel OOM-kills you instead.
MaxRAMPercentage is the line that keeps you alive on a small instance. Give the JVM the whole 512 MB and the kernel OOM-kills the container — which shows up as a service that restarts under load with an application log that ends mid-sentence.
Point the front end at a path, not at a host

This is the change that makes the rewrite work. If your environment file names the API host, you have two origins again no matter what your routes say.

// environment.prod.ts — a PATH, not a URL
export const environment = {
  production: true,
  apiUrl: '/api'      // ← not 'https://devhub-api.onrender.com/api'
};
$ curl -s -D- https://devhub.onrender.com/api/health | head -4
HTTP/2 200
content-type: application/json

# same origin as the page — no Origin header was sent,
# no preflight happened, and no CORS config exists anywhere.
apiUrl: '/api' is the entire trick. Name the API's hostname here and you are back to two origins no matter how the routes are written — the rewrite can only hide a seam the browser never asked about.
Prove the seam is invisible — and then find the one place it isn't

Compare a preflight against the two deployments. Then look at what the API thinks its own address is, because that is the one thing a rewrite genuinely changes.

$ curl -s -o /dev/null -w '%{http_code}\n' -X OPTIONS \
    -H 'Origin: https://devhub.onrender.com' \
    -H 'Access-Control-Request-Method: GET' \
    https://devhub.onrender.com/api/users
# no preflight is ever sent by the browser — same origin.
# but the API is now behind a proxy, so tell Spring to trust it:
#   server.forward-headers-strategy=framework
# without it, any absolute URL Spring builds (a redirect, a
# Location header, an OIDC redirect_uri) names the INTERNAL
# host and the browser follows it straight off your site.
forward-headers-strategy is the price of the rewrite. Without it Spring builds absolute URLs from the internal host, so redirects and the OIDC redirect_uri point somewhere the browser cannot follow.
The CIAM version of this page: collapsing to one origin changes your auth options for the better. Same-origin means a session cookie is a first-party cookie, so SameSite=Lax works and none of the third-party-cookie blocking that breaks cross-origin session auth applies to you. If you use bearer tokens instead, the interceptor gets simpler too — one origin means no "should I attach the token to this host?" branch, which is exactly the branch that leaks a token to the wrong domain. The one to watch is the redirect URI. Your OIDC redirect_uri must be the address the browser is at (https://devhub.onrender.com/...), never the API's own hostname — and that is precisely the value Spring will get wrong behind a proxy unless forward-headers-strategy is set. A redirect URI mismatch is a hard failure at the identity provider, so this is worth getting right before you wire the login.
There are no dumb questions

Why not just serve the Angular build from Spring Boot's static/ folder and have one service?

You can, and for a small internal tool it's genuinely fine — one deploy, one origin for free, nothing to route. But you give up three things worth having. The CDN: your JS and CSS would be served by your Tomcat threads from one region instead of from an edge close to the user. The sleep asymmetry inverts — with everything behind one service, a spun-down free instance means even the login page takes a minute, where the split keeps the shell instant. And you couple the deploys: a CSS tweak now rebuilds and restarts your API. The single-service version is the right call when the front end is small and secondary; the split is the right call when the front end is the product.

Doesn't the /api/* rewrite add a hop and slow everything down?

It adds one, and it is nearly always worth it. Weigh it against what it removes: a CORS preflight is an entire extra round trip before the real request on any call that isn't simple — which is every request with an Authorization header, so, all of yours. You're trading one server-side hop between Render's own edge and your service for one browser-side round trip across the internet, and the browser one is both slower and repeated. The real cost of the rewrite is different and worth naming: your API now sees the proxy, not the client, so client IP, scheme and host all arrive in X-Forwarded-* headers. Set server.forward-headers-strategy=framework and Spring reads them; leave it and you'll build http:// URLs on an https:// site and wonder why rate limiting sees every request coming from one address.

My first Docker deploy took eleven minutes. Is that normal?

The first one, yes — it downloaded a Maven image, resolved your entire dependency tree and compiled everything. The second one shouldn't, and if it does, your Dockerfile is defeating the layer cache. The rule is to order instructions from least-changing to most-changing: copy pom.xml alone and resolve dependencies as one layer, then copy src and build. Do it that way and a code-only change reuses the dependency layer and takes a fraction of the time. Do it the obvious way — COPY . . before anything else — and every one-character change invalidates every layer after it, so you re-download the internet on each push. Same instructions, same result, wildly different build times, and the only difference is the order.
