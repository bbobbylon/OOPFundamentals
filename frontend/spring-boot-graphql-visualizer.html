GraphQL — One Endpoint, Client-Specified Shape

Every REST page in this hub — REST API, REST API Design — teaches a URL-per-resource model where the server decides the response shape. GraphQL inverts that: one endpoint, and the client specifies exactly which fields it wants, nested arbitrarily deep, in a single request.

🕸️ What problem does GraphQL actually solve that REST doesn't?

A REST endpoint returns a fixed shape decided at the server — GET /api/users/42 always returns the same fields, whether the caller needs all eighteen of them or just two. That mismatch has a name on each side: over-fetching (the response includes fields the client throws away) and under-fetching (the response is missing a nested relation, so the client fires a second — or third — request to stitch the full picture together). GraphQL solves both with one mechanism: a single /graphql endpoint accepts a query describing exactly which fields the client wants, including nested relations, and the server walks that query — field by field, through a graph of resolver functions — to assemble precisely that shape in one response. The cost of that flexibility is real: a naive resolver graph re-fetches related data once per parent row (the classic N+1 problem), and a schema with no field-level authorization can let an authenticated-but-unauthorized caller simply ask for a sensitive field REST would never have exposed at that URL in the first place.

  • One endpoint, not one-per-resource — POST /graphql for everything; the query body determines the shape, not the URL.
  • Resolvers are per-field, not per-endpoint — each field in the schema (User.name, User.orders, Order.shippingAddress) has its own function, called only if the client asked for it.
  • The N+1 problem is GraphQL's signature performance trap — a list of 50 items, each resolving one related field naively, means 51 database round trips instead of 2.
  • A permissive schema is a security surface — "the caller is authenticated" is not the same question as "the caller may see THIS field, on THIS record."

Schema-first: the contract is strongly typed

A GraphQL schema (SDL) declares every type and field up front — type User { id: ID! name: String! orders: [Order!]! } — and the server rejects any query asking for a field that doesn't exist. This is closer to OpenAPI/Swagger's contract-first spirit than to REST's typically looser response shapes.

This app's REST convention, contrasted

Every controller in this scaffold returns ResponseEntity<HttpResponse> — one fixed envelope per endpoint. GraphQL has no equivalent "envelope" convention to design; the response shape IS the query, echoed back with data instead of field names.

CIAM angle — field-level authorization is easy to forget

REST's one-URL-per-resource shape means an authorization check at the controller (@PreAuthorize) naturally guards everything that endpoint returns. GraphQL's flexible field selection means a resolver for a sensitive field (User.ssn, User.internalNotes) needs its own authorization check — "authenticated" and "authorized to see this specific field on this specific record" are different questions, and scenario 5 below shows exactly how that gap gets exploited.

1. REST vs GraphQL, side by side

AxisRESTGraphQL
EndpointsOne URL per resource — GET /api/users/42, GET /api/users/42/ordersOne endpoint — POST /graphql — for every query and mutation
Response shapeFixed per endpoint, decided by the serverDecided per-request by the client's query
Over/under-fetchingCommon — either extra unused fields, or extra round trips for nested dataSolved by construction — the client asks for exactly the shape it needs, nested, in one request
CachingHTTP caching (ETags, Cache-Control) works natively per URLHarder — every query can have a different shape, so URL-level HTTP caching doesn't apply the same way
Performance riskN round trips for nested data (under-fetching)N+1 database queries inside ONE request if resolvers aren't batched
Neither is strictly better — REST's fixed shapes make HTTP caching and simple mental models easy; GraphQL's flexible shapes make mobile clients and complex nested UIs far more efficient over the network, at the cost of new server-side problems (N+1, field-level auth) that REST's URL-per-resource model didn't have in the same form.

2. Over-fetching: REST returns the whole row; GraphQL returns exactly what was asked

✗ REST — fixed shape, client discards the rest

GET /api/users/42
// server has no idea the client only wants 2 fields —
// it always returns the full DTO
{
  "id": 42, "name": "...", "email": "...",
  "address": {...}, "phone": "...", "createdAt": "...",
  // ...12 more fields the mobile client will discard
}

✓ GraphQL — the query IS the shape

query {
  user(id: "42") {
    name
    avatarUrl
  }
}
// resolver only fetches/returns these 2 fields —
// nothing else is even computed
The server literally does less work for the GraphQL request — since each field has its own resolver, a field the client didn't ask for is never resolved, never queried, never serialized. REST's DTO, by contrast, is assembled in full regardless of what the caller actually needed.

3. The N+1 problem: GraphQL's signature performance trap

✗ Naive resolver — one query per row

// SchemaMapping on Order.customer, called ONCE PER ORDER
@SchemaMapping(typeName = "Order", field = "customer")
public Customer customer(Order order) {
  return customerRepo.findById(order.getCustomerId());
  // 50 orders → 1 query for orders + 50 queries here = 51 total
}

✓ Batched resolver — one query for ALL rows

// BatchMapping — Spring for GraphQL collects every order
// in this tick and calls this ONCE with the whole batch
@BatchMapping(typeName = "Order", field = "customer")
public Map<Order, Customer> customers(List<Order> orders) {
  return customerRepo.findAllByIdIn(orderCustomerIds(orders));
  // 50 orders → 1 query for orders + 1 batched query = 2 total
}
Spring for GraphQL's @BatchMapping is the idiomatic fix for exactly the problem the standalone DataLoader pattern (common in Node/Apollo servers) also solves: collect every pending request for a field during one execution tick, then satisfy them all with a single WHERE id IN (...) query instead of N individual ones.

4. One-sentence recap

🕸️ GraphQL trades REST's fixed, per-endpoint response shape for a client-specified one — solving over/under-fetching by construction — but that flexibility introduces two traps of its own: the N+1 problem (fixed with @BatchMapping/DataLoader) and a field-level authorization gap that REST's URL-per-resource model doesn't have in the same shape.
