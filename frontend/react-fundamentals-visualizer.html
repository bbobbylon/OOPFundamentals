React Fundamentals

JSX compilation, the Virtual DOM, the Fiber reconciler, commit phase DOM mutations, and why React batches updates — the mental model for everything else in React.

⚛️ What is React — and what are JSX, the Virtual DOM, and Fiber actually doing?

React is a JavaScript library for UIs: you declare what the UI should look like for some data, and React handles how to mutate the real DOM. JSX is the syntax — <Button onClick={fn}>Save</Button> compiles to React.createElement(...), a plain object describing the element. The Virtual DOM is the in-memory tree of those objects; on a state change React builds a new tree, diffs it against the old, and applies only the differences (cheap JS comparison vs expensive DOM work). Fiber (React 16+) is the reconciler — a linked list of work units React can pause and resume, enabling concurrent rendering. And React 18 batches all state updates into one re-render.

  • Declarative — describe the UI for the data; React does the DOM ops.
  • JSX → createElement — plain element objects, not HTML.
  • Virtual DOM diff — new tree vs old, apply only the differences.
  • Fiber + batching — interruptible rendering; one re-render per update batch.

JSX → JS

// What you write (JSX): const el = ( <div className="container"> <h1>Hello, {name}</h1> <Button onClick={save}>Save</Button> </div> ); // What Babel compiles it to: const el = React.createElement('div', { className: 'container' }, React.createElement('h1', null, 'Hello, ', name), React.createElement(Button, { onClick: save }, 'Save') ); // The result: a plain JS object // { type: 'div', props: { className: 'container', // children: [{ type: 'h1', ... }, { type: Button, ... }] } }

Virtual DOM diffing

// User clicks "Save" → setState called // React builds NEW element tree // Diffs against PREVIOUS tree // Previous: <button disabled={false}>Save</button> // New: <button disabled={true}>Saving…</button> // Diff: props.disabled changed, children text changed // DOM update: only TWO attribute mutations // → button.disabled = true // → button.textContent = 'Saving…' // (not: destroy button, create new button) // Key prop in lists: // <UserRow key={user.id} user={user} /> // key tells React "this is the same item" // even after list reorder — prevents remounting

React vs Angular

React: a library (just UI layer). No built-in routing, forms, HTTP, state management — you pick your own ecosystem. Very flexible, larger ecosystem. JSX mixes HTML and logic. Change detection: explicit state changes only. Bundle: ~40KB min+gzip. Angular: a framework (opinionated full stack). Built-in router, forms, HTTP, DI, change detection. Less flexible but less decision fatigue. Templates separate from TypeScript. Change detection: Zone.js or Signals. Bundle: ~75KB+ but tree-shaken well. CIAM context: most enterprise apps you'll work on use Angular (with Spring Boot). React knowledge matters for understanding modern web patterns and for components/libraries that publish in React.

React batches the update into one render and the Virtual DOM diff touches only changed rows (keyed by user ID). Angular's equivalent is *ngFor="...; trackBy: trackById" — track-by is React's key.

1. JSX is Syntactic Sugar for createElement()

You write:

const el = (
  <Button onClick={handleClick}>
    <span>Click me</span>
  </Button>
);

Babel compiles to:

const el = React.createElement(
  Button,
  { onClick: handleClick },
  React.createElement("span", null, "Click me")
);
Key insight: JSX is not HTML and it is not special syntax. It is a JS expression that compiles to function calls. You can use it anywhere in JS: inside if blocks, ternaries, arrays. The compiler (Babel or TypeScript) transforms it before the browser ever sees it.

2. The Fiber Architecture

React 16+ uses Fiber — a rewritten reconciler where each React element maps to a "fiber" node (a plain JS object). Fibers form a linked list, not a tree, enabling React to pause, prioritize, and resume rendering work.

Fiber node shape

// Each fiber is roughly:
{
  type: Button,        // component or string
  key: null,
  stateNode: domNode, // for host components
  child: fiber,       // first child
  sibling: fiber,     // next sibling
  return: fiber,      // parent (not "parent"!)
  memoizedState: ..., // hooks state
  flags: 0b010101,   // effect tags
}

Two-phase rendering

Render phase (interruptible): build a new fiber tree ("work in progress"). Pure — no side effects. React can pause mid-way for higher-priority work (Concurrent Mode).

Commit phase (synchronous): walk the effect list and apply DOM changes, call useLayoutEffect, then useEffect. Cannot be interrupted — the DOM must reach a consistent state.

3. Keys in Lists

Keys let React match old and new list items across re-renders. Without keys, React falls back to position-based matching — causing unnecessary DOM mutations and broken state.

❌ Index as key

// items = [{id:1,"Alice"},{id:2,"Bob"}]
{items.map((item, i) =>
  <Item key={i} name={item.name} />
)}
// Remove "Alice" — Bob gets key=0
// React thinks Bob is Alice, patches name
// State/animations on Alice leak into Bob

✅ Stable unique key

// items = [{id:1,"Alice"},{id:2,"Bob"}]
{items.map(item =>
  <Item key={item.id} name={item.name} />
)}
// Remove "Alice" (id=1) — Bob still key=2
// React removes Alice's fiber, keeps Bob's
// No state leaking, minimal DOM ops

or, "which row is this" and "what was at this position" are two different questions — a key answers whichever one you ask it

Keying a list. Two doors.

Same .map(), same six characters of code, one prop away from each other. Both of these are the right answer somewhere in your codebase today.

key={index}

React is told "the element at position 0 is the same element it was last render" — full stop, regardless of what data it's now displaying.

Choose it when the list is append-only and never reorders, filters, or deletes from the middle — a static nav menu, a fixed set of tabs, a log that only ever grows at the end. Position and identity are genuinely the same thing here, so the index IS a stable id, for free, with zero extra bytes in your data.

What it costs you: the promise has to hold for the LIFETIME of the component, not just today. The moment a sort control, a delete button, or a filter gets added next sprint, "same position" stops meaning "same row" — and every uncontrolled input, expanded/collapsed toggle, or in-flight CSS transition riding on that node silently attaches itself to the wrong record.

key={user.id}

React is told "the element belonging to id 7 is the same element it was last render" — independent of where it currently sits in the array.

Choose it the moment the list can reorder, filter, or have an item removed from anywhere but the end — a sortable table, a searchable list, anything with a delete button. Deleting a row now destroys THAT row's node and leaves every survivor's state, DOM node, and uncontrolled input value exactly where it belongs.

What it costs you: a real, stable, unique identifier has to exist on the data in the first place. A server-generated id is free; a client-only draft item that hasn't been saved yet needs one manufactured (a UUID, a counter) before it can be listed at all.

Neither door is the mistake. The mistake is not noticing there was a choice — reaching for whichever key was shortest to type, and finding out the day someone adds a delete button which one you actually needed.
The condition that decides it: can this list's SHAPE change? Not "does it look static today", not "which key is less code to write" — can an item ever be inserted, removed, or reordered anywhere but the very end. If the answer is no, position and identity are the same fact and the index is a legitimate, free id. If the answer is yes, a key is your claim about identity and React trusts it completely — label the same position twice and it will faithfully carry a stranger's state onto it. The reason the wrong door is so easy to walk through is that key={index} is always available and always compiles, so the choice never announces itself as a choice until a list you called "static" stops being one.
Index keys say "row 2 is row 2 forever." Delete row 1, and the thing that used to be row 2 is now row 1 — but its typing, its scroll position and its state stayed at row 2, because nothing ever told React the identity moved.
The mechanism

Six steps, and the array is correct at every single one of them.

  1. Three rows render as users.map((u, i) => <Row key={i} user={u} />), each containing an uncontrolled <input defaultValue={u.name} />keys 0, 1, 2
  2. The user types "Zara" into the first input. That string now lives in the DOM node, not in any React stateReact is not tracking it
  3. The first user is deleted. The array is now correct and two items longthe data is right
  4. React compares old keys [0,1,2] with new keys [0,1]: two matches and one removal — and it removes the node for key 2, the last onethe wrong node destroyed
  5. The node that held "Zara" is matched to key 0 again and reused, with props updated to the second userreused, not rebuilt
  6. defaultValue is only read on mount, so the input still shows "Zara" — under the second user's rowright props, wrong screen

Step 4 is the one worth sitting with: React deleted the last node, not the one you deleted, and from Door 1's own rules that is exactly right — three keys became two, so one has to go, and the missing key is 2. Every node that survived kept the identity you assigned it. This is what it means to say that reconciliation is driven by keys rather than by content: React is not comparing your data, it is comparing your labels, and it will faithfully carry state across any two things you labelled the same. This is Door 1 used where the list actually needed Door 2 — not a bug in either door.

The common thread is that all four are state React does not own and therefore cannot move for you: it lives in the DOM node or in the component instance, and both of those are exactly what a key decides the fate of. That is also why this is so hard to catch in tests — a render test asserts on output derived from props, and every prop here is correct. The things that break are the things nothing in your test can see, which makes the key itself, rather than the symptom, the thing to review whenever a list's shape stops being fixed.

Three rows render with key={index}, each containing an uncontrolled <input defaultValue={user.name} />. You type "Zara" into the first input, then delete the first user from the array. What appears on screen?

This is what would happen with a controlled input, whose value comes from props on every render — which is why switching to controlled makes the symptom disappear. defaultValue is read once, at mount, and nothing here mounted: the node was reused.

React only destroys nodes whose keys are gone from the new list. The keys here went from [0,1,2] to [0,1], so exactly one node is destroyed — the one keyed 2, which is the last row rather than the deleted one. Rebuilding everything is precisely the work keys exist to avoid.

Correct, and note what is not wrong: the array, every prop, and the React tree in DevTools. Key by user.id and React matches rows the way you mean it, destroying the node that belongs to the deleted user and leaving the others untouched.

Where you have seen this before

Anything that reuses objects by position needs a real identity, or position becomes the identity.

Angular's @for and track

The same problem, named more explicitly: track is a required expression in the new control flow, and tracking by index has the same consequence — DOM nodes reused across records, with form control state following the position rather than the record. Two frameworks, one unavoidable question.

every list diff needs an identity

A recycled row in a mobile list view

RecyclerView and UITableView reuse cell objects as you scroll, and the classic bug is a cell showing the previous row's image or checkbox because the reuse path did not reset every field. Same mechanism made explicit: reuse is the optimisation, and resetting is your job.

reuse is the feature; reset is the work

Pagination keyed by offset

LIMIT 20 OFFSET 40 identifies rows by position in a result set, so an insert between two requests shifts everything and a user sees one record twice and another never. Cursor pagination fixes it by keying on a stable value. Position is only an identity while nothing moves.

offsets shift; cursors do not
The whole page on a napkin: JSX compiles to createElement calls, the Fiber reconciler diffs the resulting tree in a render phase and applies the differences in a commit phase, and keys tell it which children are which. The sentence worth adding: index and identity are the same fact only while a list's shape never changes — the moment it can reorder, filter, or lose an item from the middle, they diverge, and a key is your claim about which one React should trust.
