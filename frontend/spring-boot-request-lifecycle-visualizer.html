The Spring MVC Request Lifecycle

Follow one HTTP request all the way through Spring Boot — from the Tomcat socket to the JSON response — and see exactly where your code plugs in

What happens between "TCP packet arrives" and "JSON response sent" in Spring Boot?

Most Spring Boot developers know how to write a @RestController method, but have little visibility into what surrounds that method call. Understanding the request lifecycle explains: why your @Transactional annotation starts a transaction before your controller runs (it doesn't — it starts in the service), why @ExceptionHandler can catch exceptions from the controller but not from filters, why adding a Filter executes before Spring Security, and where exactly to put custom code that needs to run on every request (correlation IDs, timing, request logging). The path: TCP socket → Tomcat thread → Servlet Filter chain → Spring Security filter chain → DispatcherServlet → HandlerMapping → Interceptors → Controller method → Service (with transaction, cache, async) → Response serialisation → back up the same stack.

The layers in order

1. Tomcat: accepts TCP, creates a thread, parses HTTP. 2. Servlet Filters (javax.servlet.Filter): run before Spring — CORS, rate limiting, request logging. 3. Spring Security Filter Chain: JWT validation, session management, authentication. 4. DispatcherServlet: routes to the correct handler. 5. HandlerInterceptors (preHandle): before controller. 6. Controller: @RequestMapping method — argument resolution, binding, validation. 7. Service: @Transactional, @Cacheable, @Async. 8. ResponseBody: Jackson serialises return value to JSON. 9. HandlerInterceptors (postHandle, afterCompletion). 10. Response sent to Tomcat → TCP response.

Where to put custom cross-cutting code

Servlet Filter: MDC correlation ID, request/response logging (full URL, duration), rate limiting. Runs before Spring Security. Spring Security filter: auth token extraction, JWT validation. HandlerInterceptor: audit logging (has access to handler method metadata), permission checks based on controller method. @ControllerAdvice @ExceptionHandler: centralised error handling — catches exceptions from controllers and services, but NOT from filters.

Exceptions at each layer

Exception in a Servlet Filter: not caught by @ControllerAdvice — you must handle it in the filter with try/catch and write the response directly. Exception in Spring Security: handled by AuthenticationEntryPoint (401) or AccessDeniedHandler (403). Exception in controller/service: caught by @ControllerAdvice @ExceptionHandler — returns structured ProblemDetail. This is why a serialisation exception during response writing can't be caught by your @ExceptionHandler — the response has already started.

In CIAM: Request lifecycle for PATCH /api/users/42: Filter adds correlationId to MDC → Spring Security extracts Bearer JWT, validates it, puts JwtAuthenticationToken in SecurityContext → DispatcherServlet routes to UserController.updateUser(42, body) → @PreAuthorize("hasRole('USER_MANAGER')") checked by AOP proxy → UserService.updateUser() runs in @Transactional context → Hibernate updates user → transaction commits → Jackson serialises UserResponse → @AfterReturning audit logs the change → 200 OK sent. Understanding this order tells you exactly where to add the audit log: not in the filter (no controller info), not in the controller (no DB confirmation), but in the service or an AOP aspect.

1. The journey at a glance

When a request hits GET /api/orders/42, it passes through a fixed pipeline. The DispatcherServlet is the traffic cop in the middle — it receives every request and orchestrates finding your controller, binding the arguments, and serializing the result.

4. How method arguments get filled in

Argument resolvers map the request to params

You never parse the request yourself. HandlerMethodArgumentResolvers read each parameter's annotation and pull the value from the right place.

@GetMapping("/api/orders/{id}")
OrderDto getOrder(
    @PathVariable Long id,        // ← from the URL path
    @RequestParam boolean full,   // ← from ?full=true
    @RequestHeader String auth,   // ← from a header
    @RequestBody Filter filter)  // ← JSON body → object
{ … }
AnnotationPulled from
@PathVariableURL template (/{id})
@RequestParamquery string / form
@RequestBodyrequest body (JSON → object via Jackson)
@RequestHeaderHTTP headers

Response: the return value becomes JSON

On the way out, an HttpMessageConverter (Jackson for JSON) serializes whatever you return into the response body — the mirror image of @RequestBody.

// you return a plain object…
return new OrderDto(42, "shipped");

// …Jackson writes:
// HTTP/1.1 200 OK
// Content-Type: application/json
// { "id": 42, "status": "shipped" }

@RestController = @Controller + @ResponseBody, which is what tells Spring to write the return value as the body (instead of resolving it to a view/template).

5. The error path — exceptions get their own lane

An exception short-circuits the pipeline

If your controller or service throws, the DispatcherServlet stops and hands the exception to a resolver chain, which looks for a matching @ExceptionHandler.

controller throws → HandlerExceptionResolver → @ExceptionHandler → error JSON

Centralize it with @ControllerAdvice

@RestControllerAdvice // applies to ALL controllers
class GlobalExceptionHandler {

  @ExceptionHandler(OrderNotFoundException.class)
  @ResponseStatus(HttpStatus.NOT_FOUND)
  ErrorDto handleNotFound(OrderNotFoundException e) {
    return new ErrorDto("ORDER_NOT_FOUND", e.getMessage());
  }

  @ExceptionHandler(MethodArgumentNotValidException.class)
  @ResponseStatus(HttpStatus.BAD_REQUEST)
  ErrorDto handleValidation(...) { … }
}

One class turns thrown exceptions into clean, consistent error responses across your whole API.

6. The one-sentence mental model

📨 Tomcat hands the raw request to a chain of filters, which pass it to the DispatcherServlet, which uses handler mapping to find your controller method, argument resolvers to fill its parameters, runs your service/repository logic, then uses a message converter to turn the return value into JSON — and if anything throws, an exception handler takes over.
