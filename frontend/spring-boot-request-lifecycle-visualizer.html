The Spring MVC Request Lifecycle

Follow one HTTP request all the way through Spring Boot — from the Tomcat socket to the JSON response — and see exactly where your code plugs in

🔄 What happens between "TCP packet arrives" and "JSON response sent"?

Most developers can write a @RestController method but can't see what surrounds the call. The lifecycle explains the rest: why @Transactional starts in the service (not the controller), why @ExceptionHandler catches controller/service errors but not filter errors, why a custom Filter runs before Spring Security, and exactly where cross-cutting code (correlation IDs, timing, request logging) belongs. The path: TCP socket → Tomcat thread → Servlet filter chain → Spring Security filter chain → DispatcherServlet → HandlerMapping → interceptors → controller → service (transaction/cache/async) → response serialization → back up the same stack.

  • It's a stack you descend then ascend. Every layer wraps the next and unwinds on the way out.
  • Order decides power. Filters run before Security; interceptors see the handler method; the service owns the transaction.
  • @ExceptionHandler has a blind spot — it can't catch what fails in a filter or during response writing.
  • Place cross-cutting code by what it needs: filter (no handler info), interceptor (handler metadata), service/aspect (DB confirmation).

The layers in order

Tomcat (TCP + HTTP parse) → Servlet filters (CORS, rate limit, logging) → Spring Security chain (JWT, auth) → DispatcherServlet (routing) → interceptor preHandle → controller (binding/validation) → service (@Transactional/@Cacheable) → Jackson serialization → postHandle/afterCompletion → response.

Where custom code goes

Servlet filter: MDC correlation ID, request logging, rate limiting (before Security). Security filter: token extraction/validation. HandlerInterceptor: audit + permission checks with handler metadata. @ControllerAdvice: central error handling for controllers/services — but not filters.

Exceptions per layer

A filter exception isn't caught by @ControllerAdvice — handle it inline and write the response. Security failures go to AuthenticationEntryPoint (401) / AccessDeniedHandler (403). Controller/service errors hit @ExceptionHandler → ProblemDetail. A serialization error mid-write can't be caught — the response already started.

CIAM: PATCH /api/users/42: filter sets correlationId → Security validates the Bearer JWT into the SecurityContext → DispatcherServlet routes to updateUser → @PreAuthorize("hasRole('USER_MANAGER')") via the AOP proxy → @Transactional service updates + commits → Jackson serializes UserResponse → an @AfterReturning aspect audits the change → 200. The order tells you the audit log belongs in the service/aspect — not the filter (no controller info) or controller (no DB confirmation).

or, an @PreAuthorize check isn't a property of the method — it's a property of how you called it

The problem

The annotation is right there on the method. The security check never ran anyway.

promoteToAdmin() is locked down — bulkPromote() walks right past the lock

This page's own CIAM callout shows @PreAuthorize("hasRole('USER_MANAGER')") guarding a user-management endpoint, enforced "via the AOP proxy." Now picture the natural next feature request: a bulk version, so an admin can promote fifty users in one call instead of fifty round-trips. The obvious way to write it lives on the same @Service class, right next to the method it calls:

public List<UserDto> bulkPromote(List<Long> ids) { return ids.stream().map(this::promoteToAdmin).toList(); }

It compiles clean. Code review has nothing to flag — promoteToAdmin is still annotated, right there, completely unmodified. Call it one id at a time through the controller and a non-manager still gets a 403, exactly like before. But call bulkPromote instead, and every id in the list gets promoted — no exception, no log line, regardless of who's calling it.

POST /users/7/promote (single) → 403 for a non-manager ✓ @PreAuthorize("hasRole('USER_MANAGER')") still sitting on the method ✓ bulkPromote() reaches it via this::promoteToAdmin ⚠ POST /users/bulk-promote → 200, all promoted, any caller ⚠

The wrong assumption underneath: that @PreAuthorize is a property of the method, checked no matter how you arrive at it — like a Java access modifier. It's actually a property of the call path.

Make every call to an annotated method leave the object and come back through Spring
First move: never write this.promoteToAdmin(id) — or a bare method reference to it — from inside the same class; call it through an injected reference to a DIFFERENT bean instead ↓ a call between two beans is forced through the container, which means through the proxy Better: move bulkPromote() onto a separate UserAdminService that depends on UserService, so the loop can only ever reach promoteToAdmin() from outside ↓ the class boundary makes the correct call path the only call path — nobody has to remember the rule The result: every promotion, single or bulk, is checked by the exact same guard
An annotation on a method is a promise the proxy keeps — not the method. @PreAuthorize, @Transactional, and @Cacheable all work the identical way: Spring wraps the bean in a proxy, and only the proxy carries the check. That's exactly why this page's own diagram routes @PreAuthorize "via the AOP proxy" as a distinct hop instead of folding it into the method itself, and exactly why @Transactional has to "start in the service, not the controller" — both only run at all because the call arrived from outside, through Spring's front door.
Think of the proxy as a receptionist who checks ID badges at the lobby door of a secure office. Everyone who walks in through that door gets carded — that's the @PreAuthorize check. But if you already work in the building and duck through an internal connecting door straight into the next office, you never pass the lobby at all. The receptionist isn't malfunctioning, and the policy posted at the front desk was never wrong — you simply didn't use the door it's watching.
You

I put @PreAuthorize("hasRole('USER_MANAGER')") directly on promoteToAdmin(). How did a caller with zero admin permissions promote fifty users through bulkPromote()?

Spring's proxy

They never called MY promoteToAdmin(). I only exist wrapped around the bean the container hands out through @Autowired. The instant bulkPromote() reaches promoteToAdmin through the bare this reference, that call goes straight to the real object I'm wrapped around — it never reaches me, so I never get a chance to check anything.

The real UserService object, underneath

And from in here, I don't even know a proxy exists. this has meant "me, directly" since the day Java was designed — nothing about an ordinary method call inside my own class was ever going to detour through some object wrapped around me.

Your security review

Which is exactly why this one is so easy to miss: the annotation is real, the code compiles clean, and a review reading top-to-bottom sees a properly-guarded method. The missing piece isn't in the code you're looking at — it's in which door the call used to get there.

The mechanism

One word decides whether the check even gets a chance to run: this.

  1. At startup, Spring sees @PreAuthorize (or @Transactional, @Cacheable) on a bean method and builds a dynamic proxy around that bean a CGLIB subclass, typically, in a Spring Boot app
  2. Every external caller — the controller, another @Service, a test running the real context — receives that PROXY, not the raw object, whenever it @Autowireds the beanthe only object the container ever hands out
  3. A call arriving through the proxy passes the interceptor chain first: @PreAuthorize evaluates, then — only if it passes — the real method runs the advice runs before the body sees the call
  4. A call written as this.promoteToAdmin(id) — or this::promoteToAdmin — from inside the bean's own code reaches the bare, unwrapped instance the proxy is privately wrapping, with nothing in betweenthe lesson
  5. The real method body executes identically either way — from inside itself, it has no way to tell which path the call tooksame bytecode, either way
  6. Nothing throws, nothing logs, nothing fails to compile — the annotation simply never gets consulted for that particular callsilent by construction

Step 4 is the lesson. Steps 1, 3, and 5 describe a proxy and a bean doing exactly what they were built to do — there's no bug in Spring here. The only thing that decided whether @PreAuthorize ran was which reference the call was made against: the proxy Spring built at startup, or the plain object sitting behind it that every method inside that same class already holds as this.

The ring isn't a step the call can choose to skip — it's the only place the check exists at all. A call from the controller has to cross the ring to reach the core, so @PreAuthorize runs. A call written as this.promoteToAdmin(id) inside bulkPromote() is already standing in the core the moment it happens — there was never a ring around it to cross.

UserService has promoteToAdmin(Long id) annotated @PreAuthorize("hasRole('USER_MANAGER')"), and a second method, bulkPromote(List<Long> ids), implemented as ids.stream().map(this::promoteToAdmin).toList() — with no annotation of its own. A user with no roles at all calls the bulk-promote endpoint with a list of 50 ids. What happens?

Right — and the dangerous part is exactly how quiet it is. this::promoteToAdmin resolves to the bare, unproxied object sitting inside the wrapper Spring built at startup. The security interceptor lives on the proxy, not inside the compiled method body, so a call that never reaches the proxy never reaches the check either — every promotion in the list goes through.

This is exactly how a Java access modifier like private behaves — enforced no matter how you get there — so it's a completely reasonable guess. @PreAuthorize doesn't work that way: it's enforced by a proxy sitting in front of the object, not a check compiled into the method itself. A call that never passes through that proxy never triggers the check, which is exactly what a self-invoked call is.

Method references aren't special-cased here — ids.stream().map(this::promoteToAdmin) behaves exactly like writing for (Long id : ids) this.promoteToAdmin(id) in a loop. Either way the call is made against the bare this reference to the same instance, so either way it bypasses the proxy. The bug isn't the :: syntax — it's that the call never leaves the object to come back in through Spring's front door.

Where you've seen this before

A guard that only watches one door — and every framework built on proxies has exactly one door.

The same bulk-endpoint refactor, in a real CIAM admin panel

Session revocation, forced MFA re-enrollment, role changes pushed down from Ping or Entra — these are exactly the @PreAuthorize-guarded, one-user-at-a-time endpoints that get a "bulk" sibling the moment support asks to fix ten accounts at once. Writing that sibling as a loop that calls the single-item service method through this reproduces this exact bug on the highest-stakes endpoints in the app — the ones a pentest report finds first.

admin bulk-actions are where this bug is most expensive

ASP.NET Core's EF Core lazy-loading proxies

EF Core's lazy-loading proxies are a dynamically generated subclass wrapped around your entity — the same shape as CGLIB. They only intercept a virtual navigation property read through the proxy reference from outside; code inside the entity's own method that touches the backing field directly never triggers the proxy, and the "lazily loaded" data silently isn't there.

same shape: a subclass proxy, only watching external calls

Redux/NgRx middleware that never sees a direct function call

Logging middleware, auth-gating middleware, and analytics middleware all sit between store.dispatch() and the reducer — they only run when an action is actually dispatched. Call a reducer or an action-creator's inner function directly instead of dispatching it, and the entire middleware chain is skipped, silently, exactly like skipping Spring's proxy.

the interceptor only watches its one designated front door
Questions from the back row

Does this affect @Transactional too, or is @PreAuthorize special?

Identically — @Transactional is implemented the same way, as advice on the same kind of proxy. A self-invoked call to a @Transactional method runs inside whatever transaction (or lack of one) was already active in the calling method, silently, instead of opening its own. Same mechanism, same blind spot, different symptom — a data-consistency bug instead of a security bypass.

Why doesn't Spring just detect this and refuse to start, or make it work?

There's a real fix — AspectJ compile-time or load-time weaving bakes the advice directly into the method's bytecode instead of wrapping the bean in a proxy, so a self-invoked call runs the advice too. Spring Boot doesn't default to it because weaving is heavier to set up and harder to debug than a proxy. Automatic detection is hard for the same reason a compiler can't flag it: this.promoteToAdmin(id) is completely ordinary, valid Java — the missing check is a runtime fact about which object answered the call, not a syntax error.

How do I actually catch this before it ships?

Grep for any call to a method in the same class that carries @Transactional, @PreAuthorize, @Cacheable, or @Async — a bare call or a this:: reference to one of those from inside the class is the smell. More reliably, write an integration test that goes through the real Spring context and calls the PUBLIC entry point with a principal that should be denied, then asserts a 403. A unit test that mocks the security context and calls the method directly will pass either way — it never puts the proxy in the loop at all.

4. How method arguments get filled in

Argument resolvers map the request to params

You never parse the request yourself. HandlerMethodArgumentResolvers read each parameter's annotation and pull the value from the right place.

@GetMapping("/api/orders/{id}")
OrderDto getOrder(
    @PathVariable Long id,        // ← from the URL path
    @RequestParam boolean full,   // ← from ?full=true
    @RequestHeader String auth,   // ← from a header
    @RequestBody Filter filter)  // ← JSON body → object
{ … }
AnnotationPulled from
@PathVariableURL template (/{id})
@RequestParamquery string / form
@RequestBodyrequest body (JSON → object via Jackson)
@RequestHeaderHTTP headers

Response: the return value becomes JSON

On the way out, an HttpMessageConverter (Jackson for JSON) serializes whatever you return into the response body — the mirror image of @RequestBody.

// you return a plain object…
return new OrderDto(42, "shipped");

// …Jackson writes:
// HTTP/1.1 200 OK
// Content-Type: application/json
// { "id": 42, "status": "shipped" }

@RestController = @Controller + @ResponseBody, which is what tells Spring to write the return value as the body (instead of resolving it to a view/template).

5. The error path — exceptions get their own lane

An exception short-circuits the pipeline

If your controller or service throws, the DispatcherServlet stops and hands the exception to a resolver chain, which looks for a matching @ExceptionHandler.

controller throws → HandlerExceptionResolver → @ExceptionHandler → error JSON

Centralize it with @ControllerAdvice

@RestControllerAdvice // applies to ALL controllers
class GlobalExceptionHandler {

  @ExceptionHandler(OrderNotFoundException.class)
  @ResponseStatus(HttpStatus.NOT_FOUND)
  ErrorDto handleNotFound(OrderNotFoundException e) {
    return new ErrorDto("ORDER_NOT_FOUND", e.getMessage());
  }

  @ExceptionHandler(MethodArgumentNotValidException.class)
  @ResponseStatus(HttpStatus.BAD_REQUEST)
  ErrorDto handleValidation(...) { … }
}

One class turns thrown exceptions into clean, consistent error responses across your whole API.

6. The one-sentence mental model

📨 Tomcat hands the raw request to a chain of filters, which pass it to the DispatcherServlet, which uses handler mapping to find your controller method, argument resolvers to fill its parameters, runs your service/repository logic, then uses a message converter to turn the return value into JSON — and if anything throws, an exception handler takes over.
