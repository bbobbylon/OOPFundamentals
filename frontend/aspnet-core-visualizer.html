ASP.NET Core — Pipeline, DI & Endpoints

Microsoft's answer to Spring Boot, and culturally its closest cousin: a built-in DI container, a middleware request pipeline, attribute-routed controllers (or minimal APIs), model binding, and policy-based authorization. If you like Spring's structure, you will feel at home here.

🌐 What is ASP.NET Core — and why is it the closest thing to Spring Boot?

ASP.NET Core is Microsoft's cross-platform web framework. Like Spring Boot, it is built on a dependency-injection container (first-class, not a library bolted on) and a middleware pipeline — an ordered chain of components each request flows through (app.UseRouting(), UseAuthentication(), UseAuthorization(), then the endpoint). You register services in builder.Services with a lifetime — Singleton / Scoped / Transient (Scoped = once per request, the JPA-session analogue) — and they are constructor-injected into your controllers, exactly like Spring beans. You write endpoints either as attribute-routed controllers ([ApiController], [HttpGet("{id}")] ≈ @RestController/@GetMapping) or as terse minimal APIs (app.MapGet("/users/{id}", handler)). Model binding maps the route, query, and JSON body to your method parameters ([FromBody] ≈ @RequestBody), and policy/role-based authorization with [Authorize] ≈ @PreAuthorize. The structure transfers from Spring almost one-to-one.

  • Middleware pipeline — ordered app.Use…(); order is the behaviour (auth before endpoints).
  • Built-in DI — AddSingleton/AddScoped/AddTransient, constructor injection like beans.
  • Controllers or minimal APIs — [HttpGet("{id}")] ≈ @GetMapping; MapGet(...) for terse routes.
  • Model binding + [Authorize] ≈ @RequestBody/@PathVariable + @PreAuthorize.

Program.cs — build & run

var builder = WebApplication.CreateBuilder(args); // register services (the DI container) builder.Services.AddScoped<IUserService, UserService>(); builder.Services.AddControllers(); builder.Services.AddAuthentication("Bearer").AddJwtBearer(); var app = builder.Build(); // the middleware pipeline — ORDER MATTERS app.UseRouting(); app.UseAuthentication(); // who are you? app.UseAuthorization(); // are you allowed? app.MapControllers(); app.Run();

Controller + DI + binding

[ApiController] [Route("api/users")] // ≈ @RequestMapping public class UsersController : ControllerBase { private readonly IUserService _svc; // constructor injection — like @Autowired public UsersController(IUserService svc) => _svc = svc; [HttpGet("{id}")] // ≈ @GetMapping("/{id}") public async Task<IActionResult> Get(int id) { var u = await _svc.FindAsync(id); return u is null ? NotFound() : Ok(u); } }

Spring Boot comparison

builder.Services.AddScoped<T> ≈ a Spring @Service bean (Scoped ≈ request scope). The middleware pipeline ≈ the Servlet filter chain / Spring Security filter chain. [ApiController]/[HttpGet] ≈ @RestController/@GetMapping; [FromBody]/[FromRoute]/[FromQuery] ≈ @RequestBody/@PathVariable/@RequestParam. [Authorize(Policy="Admin")] ≈ @PreAuthorize("hasRole('ADMIN')"). Ok(obj)/NotFound() ≈ ResponseEntity.ok()/notFound(). appsettings.json ≈ application.yml; the Options pattern ≈ @ConfigurationProperties. EF Core ≈ Spring Data JPA. Even the philosophy — convention + DI + auto-wiring — matches.

CIAM ASP.NET service: A .NET resource server validating Ping/Entra tokens uses AddAuthentication().AddJwtBearer() with Authority set to the IdP (it auto-fetches the JWKS and validates RS256/iss/aud), then [Authorize(Policy = "CiamAdmin")] on actions for role/claim checks (≈ @PreAuthorize). UseAuthentication() must come before UseAuthorization() in the pipeline — get the order wrong and every request is anonymous. Microsoft's own Entra integration (Microsoft.Identity.Web) layers cleanly on top.

2. Service lifetimes

builder.Services.AddSingleton<ICache>(); // one instance for the whole app
builder.Services.AddScoped<IUserService>(); // one per HTTP request (≈ JPA session)
builder.Services.AddTransient<IEmailer>(); // a new one every time it's injected
The captive-dependency trap. Never inject a Scoped service into a Singleton — the singleton captures one request's instance forever (stale DbContext, leaked state). ASP.NET Core's scope validator throws on this in development. The Scoped lifetime is the one a Spring developer should reach for by default.

3. Minimal APIs vs controllers

// minimal API — terse, great for small services
app.MapGet("/users/{id}", async (int id, IUserService svc) =>
  await svc.FindAsync(id) is { } u ? Results.Ok(u) : Results.NotFound());

// services are injected straight into the handler parameters

Minimal APIs put routing, binding, and DI in one lambda — ideal for microservices. Controllers add structure (filters, model validation attributes, conventions) and scale better for large APIs. Both share the same pipeline, DI, and binding.
