GKE & Artifact Registry — Managed Kubernetes on GCP

GKE (Google Kubernetes Engine) runs a fully-managed Kubernetes control plane, with Autopilot managing nodes for you and Standard giving you node-pool control; Artifact Registry stores the images, and Workload Identity lets a pod call GCP APIs with zero downloaded keys.

☸️ Autopilot vs Standard, and why Workload Identity replaces the downloaded JSON key

GKE is Google's managed Kubernetes offering, and the control plane — the API server, etcd, the scheduler — is always fully managed by Google, regardless of mode; you never see a control-plane node or patch it yourself. The real decision is Autopilot vs Standard. Autopilot hands Google the nodes too: you submit a Deployment with resource requests, and GKE provisions exactly the right-sized capacity behind the scenes, bills you per pod (not per node), and hardens defaults (no privileged containers, no hostPath by default) automatically. Standard gives you node pools — groups of nodes sharing a machine type and config, each independently autoscalable via the Cluster Autoscaler — so you can, say, run a cheap Spot-VM pool for batch jobs alongside an on-demand pool for latency-sensitive services, at the cost of choosing machine types and watching for pending pods yourself. Images come from Artifact Registry, the successor to Container Registry (gcr.io): regional repositories, IAM-gated push/pull, and built-in vulnerability scanning. The identity story is the part worth slowing down for: a pod's default credentials used to mean baking a downloaded service-account JSON key into a Secret — a long-lived, exfiltratable credential. Workload Identity replaces that: you bind a Kubernetes ServiceAccount (KSA) to a Google Cloud IAM ServiceAccount (GSA), and GKE's metadata proxy transparently exchanges the pod's identity for a short-lived GCP access token on every request — no key file exists anywhere, ever.

  • Control plane — always Google-managed in both modes; you never patch or scale it yourself.
  • Autopilot — pay per pod, Google sizes and provisions nodes automatically, secure defaults baked in.
  • Standard — you own node pools (machine type, count, Spot vs on-demand); Cluster Autoscaler scales each pool independently.
  • Artifact Registry — regional, IAM-gated image repos with vulnerability scanning; successor to gcr.io.
  • Workload Identity — binds a KSA to a GSA so pods get short-lived tokens instead of a downloaded JSON key.

Deploy + bind identity

# Autopilot cluster, zero node config gcloud container clusters create-auto shop-cluster \   --region us-central1 # bind KSA → GSA, no key file involved gcloud iam service-accounts add-iam-policy-binding \   gsa-storage-reader@shop.iam.gserviceaccount.com \   --role roles/iam.workloadIdentityUser \   --member "serviceAccount:shop.svc.id.goog[default/ksa-storage-reader]"

AWS & Azure comparison

GKE ≈ EKS (AWS) / AKS (Azure) — all three run managed Kubernetes control planes. Artifact Registry ≈ ECR / ACR. Autopilot's per-pod billing has no exact AWS/Azure twin — the closest is Fargate-on-EKS, which right-sizes per-pod too but still requires you to define a Fargate profile. Workload Identity ≈ IRSA (IAM Roles for Service Accounts, AWS) ≈ Azure's pod-level Workload Identity (same name, same idea) — all three exist because "download a long-lived key into the cluster" was never an acceptable answer. See aws-ecs-visualizer.html and azure-containers-visualizer.html for the sibling services.

Spring Boot comparison

Your multi-stage backend/Dockerfile still produces the same image; only where it runs changes. On GKE, Boot's /actuator/health feeds the pod's readiness and liveness probes directly, config comes from a ConfigMap/Secret mounted or injected as env vars, and if the app needs Cloud Storage or BigQuery, Workload Identity means the Google Cloud Java SDK just picks up ambient credentials — no GOOGLE_APPLICATION_CREDENTIALS key file to manage, mirroring how the CIAM app already avoids storing IdP secrets in code.

CIAM in production: Workload Identity is the whole ballgame here — a pod that needs to read a secret from Secret Manager or write an audit event to BigQuery authenticates as itself, via a token the metadata server issues and rotates automatically, never as a static key sitting in a Kubernetes Secret that someone could kubectl get secret -o yaml and exfiltrate. Combined with Artifact Registry's IAM-gated pulls (node service accounts hold artifactregistry.reader, nothing more), the entire path from "image built" to "pod calling a GCP API" never touches a long-lived credential.

1. Autopilot vs Standard: who owns the nodes

# Autopilot — no node pool to define, billed per pod request
gcloud container clusters create-auto shop-cluster --region us-central1

# Standard — you define node pools explicitly
gcloud container clusters create shop-cluster --region us-central1 \
  --num-nodes 3 --machine-type e2-standard-4
gcloud container node-pools create spot-batch --cluster shop-cluster \
  --spot --machine-type e2-standard-4 --enable-autoscaling \
  --min-nodes 0 --max-nodes 10
The control plane is never the decision. Google runs the API server and etcd for you in both modes — upgrades, HA, patching are Google's problem either way. The actual choice is who sizes and pays for the nodes: Autopilot reads your pod's resources.requests and provisions exactly that much capacity, billed per pod-second — great for teams that don't want to think about machine types. Standard's node pools let you mix a cheap Spot pool (up to ~60-91% cheaper, can be reclaimed with ~30s notice) for interruption-tolerant batch work alongside an on-demand pool for your API — a cost lever Autopilot doesn't expose.

2. Artifact Registry: IAM-gated, scanned image storage

# create a regional Docker repository
gcloud artifacts repositories create shop-images \
  --repository-format=docker --location=us-central1

# build, tag, push (same docker CLI, GCP-namespaced tag)
docker build -t us-central1-docker.pkg.dev/shop-proj/shop-images/api:v2 .
docker push us-central1-docker.pkg.dev/shop-proj/shop-images/api:v2

# grant a node's service account pull-only access
gcloud artifacts repositories add-iam-policy-binding shop-images \
  --location=us-central1 \
  --member="serviceAccount:gke-node-sa@shop-proj.iam.gserviceaccount.com" \
  --role="roles/artifactregistry.reader"
Regional, not global, and reader-only by default. Artifact Registry repos live in a specific region (co-locate with your cluster to cut pull latency and cross-region egress), and the standard pattern grants the GKE node service account only artifactregistry.reader — it can pull images, never push or delete. Vulnerability scanning runs automatically on push, surfacing known CVEs in your base image before a pod ever starts.

3. Workload Identity: no more downloaded keys

# 1. create a Kubernetes ServiceAccount
kubectl create serviceaccount ksa-storage-reader

# 2. bind the KSA to a GCP ServiceAccount (GSA) — the trust relationship
gcloud iam service-accounts add-iam-policy-binding \
  gsa-storage-reader@shop-proj.iam.gserviceaccount.com \
  --role roles/iam.workloadIdentityUser \
  --member "serviceAccount:shop-proj.svc.id.goog[default/ksa-storage-reader]"

# 3. annotate the KSA to point at the GSA
kubectl annotate serviceaccount ksa-storage-reader \
  iam.gke.io/gcp-service-account=gsa-storage-reader@shop-proj.iam.gserviceaccount.com
The pod never sees a key — it sees a token that expires. Once a pod uses ksa-storage-reader, any GCP client library call it makes is transparently intercepted by GKE's metadata proxy, which exchanges the pod's Kubernetes identity for a short-lived (typically 1-hour) GCP access token scoped to whatever roles the GSA holds. Compare that to the old pattern — mount a service-account JSON key as a Secret — where the credential is long-lived, visible to anyone with kubectl get secret access, and has to be manually rotated. Workload Identity removes the key file from existence entirely.
