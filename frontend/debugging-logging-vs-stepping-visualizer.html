Log vs Debugger

A breakpoint and a log line are different instruments, and reaching for the wrong one wastes time. A debugger is unbeatable for rich state at a known line you can reproduce locally. Logging wins when you can't pause — production, concurrency, async, "where does it even break?". Knowing which to grab (and how to log so the logs actually help) is a core skill.

🐛 What is the difference between a debugger and logging — and when should you reach for each?

The choice between a breakpoint and a log line isn't about preference — it's about the shape of the problem. Reaching for the wrong tool costs you significant time. A debugger (breakpoint) is the right tool when: the bug is locally reproducible, you know approximately where in the code the problem is, and you need to inspect rich object state — you want to see the entire UserService object, the full JWT claims map, the database connection state at that exact moment. IntelliJ's debugger lets you hover over any variable and see its entire structure. You can evaluate arbitrary expressions in the Debug Console. Step through line by line. The limitation: a debugger freezes the running thread. This changes timing characteristics — concurrency bugs (race conditions, deadlocks) often disappear when you add a breakpoint because the pause alters the thread interleaving. Logging wins when: you're debugging production (you cannot pause real users), the bug is timing/concurrency-related (logging doesn't freeze threads), you don't know where the bug is (add logs at multiple checkpoints, run, grep the output), or you need to trace across multiple requests or time windows. Structured logging: don't just log strings — log key-value pairs that can be queried. log.info("user_login user_id={} outcome={} latency_ms={}", userId, outcome, elapsed). In production, these feed into Splunk, Azure Monitor, or ELK where you filter by user_id=12345 across all logs. Log levels matter: ERROR for unrecoverable failures that need immediate attention; WARN for recoverable anomalies; INFO for key business events (login, token issued, user created); DEBUG for detailed flow tracing (request/response details, method entry/exit). In production, run at INFO. When debugging an issue, temporarily bump a package to DEBUG: logging.level.com.myco.ciam.auth=DEBUG in Spring's application.properties. Logpoints (IntelliJ feature): a non-pausing breakpoint that just logs an expression — useful middle ground that instruments code without modifying it and runs at full speed without affecting timing.

The problem

You stopped to look at one variable for four minutes, and every clock outside that thread kept running.

You resumed, and the exception you got was one you created by looking

The bug is reproducible locally, you know the line, and you need rich state — so the debugger is the right instrument and this page told you so. You breakpoint inside a @Transactional service method, expand the user object, read the claims map, evaluate a couple of expressions. Four minutes, tops. You hit resume.

And the run window fills with things that were not your bug. A SQLTransientConnectionException: Connection is not available, request timed out after 30000ms from a completely different request. A lock-wait timeout on the row you were sitting on. A broken pipe writing the response, because the browser gave up two hundred and forty seconds ago and closed the socket. Your pause suspended your thread. The connection pool's 30-second acquire timeout, the database's lock-wait timeout, the HTTP client's read timeout and the user's patience were all still counting the whole time — and in Spring the transaction, the leased connection and the row lock were all held open by the thread you froze.

Decide what your pause will break before you take it
Ask what this line is holding: a transaction, a pooled connection, a lock, a single-use token, an open response stream ↓ anything with a deadline attached is a thing your breakpoint will expire, and you'll read the wreckage as evidence about the bug Change the breakpoint's suspend policy from All threads to just this one ↓ IntelliJ suspends every thread by default, which also stops the heartbeats, schedulers and health endpoints that other systems are watching — and yes, suspending one thread instead of all of them changes the interleaving you're observing, so know which trade you took When the question is "what is this value" rather than "what happens next", use a non-suspending logpoint instead ↓ same information, no pause, no expired anything — this is the middle instrument this page's table is really pointing at And when you must take a long pause, raise the relevant timeouts in your local profile first, so the noise after you resume is not mistaken for the bug
A debugger gives you a stopped picture of a system that never stopped. The pause is local to one thread in one process; the rest of the world — pools, locks, sockets, schedulers, token lifetimes, orchestrators, the person refreshing the page — keeps its own time and keeps counting. Everything you observe after a long pause is therefore a mixture of your bug and the damage the pause did, and those two are indistinguishable in a log. This is the same family as the timing problem this page already warns about, pointed the other way: a breakpoint doesn't only hide concurrency bugs by changing the interleaving, it manufactures failures that could never happen at full speed.

Your thread stopped. Nothing else did.

Pressing pause on your player does not pause the match. The ball keeps moving, the whistle goes, and when you press play you're behind and everyone else has moved on. A breakpoint is a pause button on your seat, not on the game.

The mechanism

One pause, four independent clocks, and none of them is yours.

  1. Request arrives. Spring opens a transaction, which leases a connection from a pool of ten and holds it for the whole methodthe resource you're about to sit on
  2. Your breakpoint hits at t+0.2s. With IntelliJ's default policy, every thread in the JVM suspends — not just this oneincluding schedulers and health endpoints
  3. t+30s — another request needs a connection, waits, and dies with Connection is not available, request timed out. First casualty, and it isn't even your requestpool starvation, entirely self-inflicted
  4. t+50s — a second session waiting on the row you locked hits the database's lock-wait timeout and gets rolled backthe DB cannot tell a debugger from a hang
  5. t+60s — the browser's read timeout expires and the socket closes. Whatever you were about to observe has no audience leftthe response is now undeliverable
  6. t+240s — you resume. The method finishes correctly, then the write fails with a broken pipe, and your console is full of exceptions that describe your pause rather than your bugfour minutes of looking, zero minutes of evidence

Step 6 is the expensive one, because those exceptions are plausible. Pool starvation and lock-wait timeouts are exactly the kind of thing you'd expect a real production bug to look like, so it is very easy to spend the next hour investigating an incident you caused by holding still. The rule that saves the hour: any exception that appears after a long pause is suspect until you've reproduced it without the pause.

the user's browser — read timeout counting

Read it from the inside out and you have your pre-flight checklist. The core is the cheapest thing on the screen and the outermost ring is the one with a human attached, but every layer between them has an independent deadline, and your breakpoint suspends exactly one thing: the code in the middle. Before any pause longer than a few seconds, ask which of these rings your line is currently inside.

You breakpoint inside a @Transactional method, spend four minutes in the Variables panel, and resume. The console then shows SQLTransientConnectionException: Connection is not available, request timed out after 30000ms — thrown on a different request thread — and the browser tab that started your request shows nothing at all. What have you learned about the bug you sat down to fix?

Right, and the useful habit is to treat everything after a long pause as contaminated. Both symptoms are artefacts: a pooled connection is held for the life of the transaction, and the transaction lives as long as your suspended thread, so a pool of ten connections effectively became a pool of nine for four minutes while everything else kept to its configured timeouts. Reproduce at full speed — a logpoint, or a curl with timing — before you believe any of it.

Resizing a pool to accommodate a debugging session is how a local workaround becomes a production config. Worse, it hides the signal: connection-acquisition timeouts are one of the better early warnings you get about long-running transactions, and raising the pool size until they stop is the equivalent of pulling the fuse. The number was fine; one borrower was asleep.

A real connection leak looks superficially identical, which is exactly why this distractor is dangerous — and the difference is reproducibility. A leak starves the pool again on the next run, with no breakpoint involved, and it shows up in Hikari's own leak-detection warning (leakDetectionThreshold). A debugger pause starves it only while you're paused. Run it once without the breakpoint before you go looking for a missing close().

Where you have seen this before

Three other deadlines that expire while you sit on a line and read.

The authorization code that died while you inspected it

Debugging the OAuth callback is the classic. Ping redirects back with ?code=…, you breakpoint in the handler to inspect it, and by the time you resume the exchange fails with invalid_grant. Authorization codes are single-use and deliberately short-lived — RFC 6749 recommends a maximum of ten minutes, and real IdPs commonly use a minute or less. You then spend an hour re-checking your client secret and redirect URI, both of which were always correct.

the credential expired inside the debugger

The liveness probe that restarted the pod you were attached to

Remote-debugging a service in Kubernetes with an all-threads suspend policy means the health endpoint stops answering. The kubelet's liveness probe fails its threshold, the pod is restarted, and your debug session dies mid-inspection — looking, from the outside, exactly like a flaky connection. A thread-only suspend policy keeps the heartbeat alive, which is one of the more practical reasons to change that default.

a suspended JVM reads as an unhealthy one

The lease that moved on without you

Distributed locks and leader-election leases are held for a fixed duration and renewed by a heartbeat — Redis with an expiry, a Kubernetes lease object, a ZooKeeper ephemeral node. Suspend the thread that renews it and the lease lapses; another instance takes over, and your process resumes confidently doing work it is no longer entitled to do. Same shape as the connection pool, with a much worse blast radius.

you resume holding a lock you no longer own

3. Log so the logs actually help

  • Log decisions, not decoration. The inputs, the branch taken, and state before/after a transform — not "got here".
  • Make it greppable. Stable prefixes + a correlation id per request (MDC) so you can pull one request's whole story across threads.
  • Binary-search with logs. Don't know where it breaks? Log at a few boundaries, see which half misbehaves, then add logs (or a breakpoint) there. (Same bisection as the Debugging Method.)
  • Right level, structured. DEBUG for flow you can switch on live, INFO for lifecycle; emit key=value/JSON so a log tool can filter.
  • Never log secrets. Tokens, passwords, PII — a debug line that dumps a JWT is a breach.

4. One-sentence recap

🧭 Reach for a debugger when you can reproduce locally and need rich state at a known line, and for logging when you can't pause — production, concurrency/timing (a debugger's pause hides the race), async (frames don't span the hop — use correlation ids), or "where does it break?" (log at boundaries to bisect, then debug the narrowed spot) — and log decisions + ids at the right level, structured and greppable, never secrets.
