SSR & Hydration

Server-Side Rendering, full hydration (v16+), event replay (v18+), incremental hydration (v19+). What actually happens between request and interactive.

🖥️ What is Angular SSR and Hydration — and when does server-rendering actually help?

SSR (Server-Side Rendering) runs your Angular app on a Node server and ships complete HTML, so users (and crawlers) see content before any JavaScript loads — unlike Client-Side Rendering, where the browser gets an empty shell first. Hydration is the follow-up: after the HTML arrives, Angular boots and reuses the server-rendered DOM instead of throwing it away and rebuilding (which would flicker and double the work). It's the right tool for public, SEO-sensitive, fast-FCP pages — and usually overkill for an authenticated dashboard.

  • Why SSR: SEO (crawlers see real HTML), better Core Web Vitals/FCP, and correct social-share previews.
  • Hydration (provideClientHydration(), v16+) reuses the server DOM; v17 adds event replay (buffer clicks until hydrated); v19 adds incremental hydration.
  • Transfer state: the server serializes its fetched data into the HTML so the browser doesn't re-fetch it.
  • Guard browser APIs: window/document/localStorage don't exist on the server — wrap them in isPlatformBrowser().
  • Trade-off: SSR needs a Node server and more care; CSR runs on any static host and is fine behind auth.

The problem

The server said "Good evening". The browser said "Good afternoon". Angular believed the browser and threw the server’s work away.

A component that renders something different every time it runs

Your public login page greets people by time of day: {{ greeting() }}, built from new Date().getHours(). Node runs it in UTC at 19:00 and writes "Good evening" into the HTML. Two hundred milliseconds later the browser in Denver boots, runs the same component, gets "Good afternoon" — and the two do not match.

new Date().getHours() Math.random() window.innerWidth < 768 ⚠ NG0500 in the console ⚠ a cookie the server never got ⚠

Here is the part that should scare you: nothing turns red for the user. Angular throws that whole subtree away and re-renders it in the browser, exactly like the pre-v16 days. The page still ends up correct. You just bought a Node server, a second build target and an on-call rotation — to ship CSR with extra steps.

Render the same thing twice — or don't render it on the server at all
The server's HTML and the client's first render must agree, node for node ↓ so anything that differs per run has no business in an SSR template isPlatformBrowser(inject(PLATFORM_ID)) — branch honestly instead of crashing ↓ and for the code that genuinely needs a live DOM afterNextRender(() => …) — browser only, after the DOM is really there ↓ and for a region that can never agree, stop pretending @defer (hydrate never) { … } — server HTML forever, zero JS shipped
Hydration is the browser agreeing with the server. Disagree once — one text node, one @if that flipped — and Angular sides with the browser: it destroys the server's DOM for that subtree and re-renders it. SSR isn't a speed feature you switch on. It's a promise that your components are deterministic, and every mismatch is you breaking it.
The Node server

I ran your component and produced HTML. There is no window in here, no document, no localStorage — I'm a process, not a browser. I don't have a screen to measure or a user to have cookies.

The browser

I painted your HTML in 300 ms and it looked wonderful. Then main.js arrived, I ran the same component, and I got a different answer than you did.

Angular hydration

Then I can't reuse that DOM. NG0500, subtree destroyed, re-rendered from scratch. Sorry about the flicker — and about the layout shift you'll see in the Core Web Vitals report next Tuesday.

The mechanism

Seven steps, and every one of them gates the next.

  1. A request arrives. Node runs your Angular app against a synthetic DOM — a data structure that looks enough like a document to render intono browser exists anywhere in this process
  2. Components construct, HttpClient fetches on the server, and Angular waits for the app to go stable before it serializes anythinga setInterval that never settles hangs the whole response
  3. Angular writes out the HTML plus ngh markers plus <script id="ng-state"> holding the data it just fetchedngh is the map from DOM node back to component
  4. The HTML hits the wire, the browser paints, FCP is done. The user can read the pagevisible — and completely dead
  5. main.js downloads, parses, compiles and bootstraps on the main threadevery click in this gap is lost unless withEventReplay() caught it
  6. Hydration walks the DOM you already have, matches ngh markers to component instances, and attaches listenerszero DOM writes — that is the entire point
  7. Any node that doesn't match what the client would have rendered → NG0500, subtree destroyed, re-renderedthis is where SSR quietly refunds itself

Steps 4 → 6 are the window everybody forgets: the page looks finished and isn't. That gap is measured in seconds on cold 4G, and it is the single reason withEventReplay() exists.

Now the question that trips up everyone the first week: why is window undefined on the server? Because window is not part of JavaScript — it's part of the browser. Node ships the language, not the DOM. Angular renders SSR into its own minimal document implementation, so document exists in a limited form inside Angular's rendering, but window, localStorage, navigator and matchMedia simply are not there, and touching one at field-initializer or constructor time is a ReferenceError that takes the whole response down with a 500. That's why there are two different tools and they are not interchangeable: isPlatformBrowser() answers "am I allowed to touch this?" anywhere, while afterNextRender() answers "run this later, in the browser, once the DOM is actually committed" — it never runs on the server, and it's excluded from the stability wait, so a timer inside it can't hang your SSR response. Measuring an element, initialising a charting library, reading scroll position, booting an analytics SDK: all afterNextRender. Guard reads, defer DOM work — and never, ever fake a window global on the server to make the error go away.

Your public registration page is SSR'd for SEO. A banner reads @if (window.innerWidth < 768) { … } — guarded with isPlatformBrowser, so nothing crashes. The server, having no viewport, renders the desktop banner; every phone then renders the mobile one. Lighthouse still shows a fast FCP and no errors reach your users. What did you actually ship?

This is the comfortable assumption, and it's the wrong one. Hydration is not a diffing pass — Angular never compares the server DOM against a freshly computed one to patch the delta. It trusts the markup and attaches to it. The moment the shape it expects isn't the shape that's there, the only safe move is to throw the subtree out.

Right — and the cruelty is that it works. The user sees correct content, your error tracker sees an NG0500 nobody triages, and the money you spent on a Node render tier bought a first paint that gets repainted. Viewport is a browser fact; render one layout on the server and let CSS media queries do the responsive work, or push the whole banner behind @defer (hydrate on viewport).

That's the failure you'd get without the guard — and it would be the better outcome, honestly, because a 500 in staging gets fixed on Tuesday. The guard converted a loud crash into a silent mismatch, which is exactly why "I wrapped it in isPlatformBrowser" is not the same as "I fixed it".

Questions from the back row

Can't I just polyfill window on the server and stop guarding everything?

You can — domino and jsdom exist, and plenty of codebases do it. It's a trap with a very long fuse. A fake window has no layout engine, no real viewport, no user's storage and a user agent that means nothing. So your code stops crashing and starts taking the browser branch with wrong answers — which the real browser then contradicts. You've traded a loud ReferenceError for a silent hydration mismatch on every page. Guard, don't fake.

Isn't afterNextRender just ngAfterViewInit with a new name?

No, and the difference is precisely the one that matters here: ngAfterViewInit runs on the server too, during SSR. Put document.querySelector(…).getBoundingClientRect() in it and you'll find out on the first render. afterNextRender callbacks never run on the server at all, and they run after the DOM is committed rather than merely after the view is created — plus they're outside SSR's stability wait, so a timer in there can't hang the response.

How do I even see a hydration mismatch? Nothing looks broken.

That's the whole problem. Look for the NG0500–NG0507 family in the browser console on a dev build (production strips the message and leaves you a bare code), and watch for a component whose constructor runs twice. The visual tell is a flicker or layout shift at the exact moment main.js finishes — which is invisible on localhost, where hydration lands 40 ms after paint. Throttle to slow 4G and it becomes impossible to miss.

Why SSR exists at all

    
A traditional Angular SPA ships a near-empty <app-root></app-root> and lets the browser download megabytes of JS before anything appears. SSR renders the page on the server first, so the user sees content immediately — then JS arrives and "hydrates" the DOM so it becomes interactive.

Setting it up

    
One command adds SSR to any existing Angular app (v17+):

    
# From the project root
ng add @angular/ssr

    
That single command edits angular.json, adds a server.ts entry point, creates a Node Express server, enables hydration in app.config.ts, and updates the build to produce both browser and server bundles.


    
What changes in app.config.ts

    
import { ApplicationConfig } from '@angular/core';
import { provideRouter } from '@angular/router';
import { provideClientHydration, withEventReplay, withIncrementalHydration } from '@angular/platform-browser';

export const appConfig: ApplicationConfig = {
  providers: [
    provideRouter(routes),
    provideClientHydration(
      withEventReplay(),         // v18+ replay clicks that happened before hydration
      withIncrementalHydration() // v19+ defer hydration per @defer block
    )
  ]
};

What is hydration, actually?

    
The server already rendered the DOM. Hydration is the process where Angular walks the existing DOM, matches it to its component tree, and attaches event listeners + signal bindings without re-creating elements. Before v16, Angular destroyed and re-rendered every node — causing a visible "flicker" and tossing the server's work.


    
Full hydration (v16+ default): Angular reuses the server-rendered DOM. No flicker. No double-rendering. Faster TTI (Time To Interactive) and lower CLS (Cumulative Layout Shift).


    
How Angular matches server DOM to client components

    
During SSR, Angular adds ngh attributes — hydration metadata that tells the client which DOM element belongs to which component instance.


    

      

        <app-product ngh="0">

          <h1 ngh="0|c1">Wireless Headphones</h1>

          <button ngh="0|c2">Add to cart</button>

        </app-product>

        <script id="ng-state" type="application/json">

          { "TransferState": { "product-42": {...} } }

        </script>
      

    

    
Without these markers Angular wouldn't know which DOM node corresponds to which component, so it would have to destroy and re-render — exactly the old behavior we're trying to avoid.


    
    
TransferState — don't re-fetch what the server already fetched

    
If your server fetched /api/product/42 to render the page, you don't want the browser to fetch it again after hydration. TransferState serializes data into the HTML so the client can reuse it.


    
The shortcut: httpResource / HttpClient with withFetch()

    
// app.config.ts — automatic state transfer
provideHttpClient(
  withFetch(),                 // uses fetch under the hood
  withInterceptors([...])
)
provideClientHydration(
  withHttpTransferCacheOptions({ includePostRequests: false })
)

    
With withFetch() + withHttpTransferCacheOptions(), GET requests made during SSR are auto-cached, serialized into the page, and replayed instantly on the client — no extra code in your services.


    
The manual API (when you need it)

    
import { inject, makeStateKey, TransferState } from '@angular/core';

const PRODUCT_KEY = makeStateKey<Product>('product-42');

export class ProductService {
  private state = inject(TransferState);
  private http  = inject(HttpClient);

  getProduct(): Observable<Product> {
    const cached = this.state.get(PRODUCT_KEY, null);
    if (cached) return of(cached);   // browser: reuse SSR result

    return this.http.get<Product>('/api/product/42').pipe(
      tap(p => this.state.set(PRODUCT_KEY, p)) // server: stash for client
    );
  }
}


    
    
Event replay (v18+)

    
The bundle is still downloading. The page is visible. The user clicks "Add to cart". What happens?

    
Without event replay: the click is lost. The button looks ready but doesn't do anything. Frustrating.

    
With withEventReplay(): Angular installs a tiny pre-hydration listener that queues events. After hydration runs, those events are dispatched to the now-bound handlers — like the click never happened too early.

Incremental hydration (v19+) — only hydrate what you need

    
Full hydration still runs JS for the entire page on load. For long pages this is wasteful — the user might never scroll to the footer. Incremental hydration uses @defer blocks to delay hydration per region: each block only downloads + hydrates when its trigger fires.


    
<!-- product.html — server renders all of this, but JS only loads on demand -->
@defer (hydrate on viewport) {
  <app-reviews />          // hydrates when scrolled into view
}

@defer (hydrate on interaction) {
  <app-recommendations />   // hydrates on first hover/click
}

@defer (hydrate on idle) {
  <app-footer />           // hydrates when the main thread is idle
}

@defer (hydrate never) {
  <app-static-banner />    // static HTML forever, no JS shipped
}

Prerendering specific routes (SSG mode)

    
Most marketing/blog/docs sites don't need a Node server. Tell Angular which routes to render at build time and serve the resulting HTML from a CDN.

    
// app.routes.server.ts (v19+)
import { RenderMode, ServerRoute } from '@angular/ssr';

export const serverRoutes: ServerRoute[] = [
  { path: '',            renderMode: RenderMode.Prerender },
  { path: 'about',       renderMode: RenderMode.Prerender },
  { path: 'blog/:slug',  renderMode: RenderMode.Prerender,
    getPrerenderParams: async () => (await fetch('/api/posts'))
      .json().then(posts => posts.map(p => ({ slug: p.slug })))
  },
  { path: 'dashboard/**', renderMode: RenderMode.Client },   // CSR for auth'd
  { path: '**',           renderMode: RenderMode.Server },    // SSR fallback
];

    
v19 introduced per-route render modes — the same app can mix Prerender, Server, and Client per route, picking the right tradeoff for each page.


    
    
The classic SSR pitfalls


    

      
!

      

        
ReferenceError: window is not defined

        
Node has no window, document, or localStorage. Guard with isPlatformBrowser(inject(PLATFORM_ID)) or move that code into afterNextRender(() => ...) which only runs in the browser.

      

    


    

      
!

      

        
setTimeout / setInterval never finish

        
SSR waits for "stability" before serializing HTML. A timer that never completes blocks the response. Use afterNextRender for browser-only timers, or wrap in runOutsideAngular.

      

    


    

      
!

      

        
Hydration mismatch errors (NG0500–NG0507)

        
Server HTML must match what Angular re-renders on the client. Common cause: rendering Date.now(), Math.random(), or DOM-manipulation that runs differently in Node vs browser. Make those values stable, or wrap in @defer (hydrate never).

      

    


    

      
!

      

        
Cookies and auth headers missing on server

        
SSR fetches happen from Node, not the browser — they don't carry the user's cookies automatically. Use an HTTP interceptor that forwards REQUEST headers when running on the server (inject REQUEST from @angular/ssr).

      

    


    

      
!

      

        
CSS-in-JS / styling libraries that need DOM

        
Some libraries measure elements or attach styles via document at import time. They'll crash SSR. Either replace them with Angular's styles / signals, or dynamically import() them inside afterNextRender.
