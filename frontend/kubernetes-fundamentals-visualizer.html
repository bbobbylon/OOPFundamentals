Kubernetes Fundamentals

Pods, nodes, clusters, kubectl — how K8s schedules and runs your containers.

☸️ What is Kubernetes — and why do modern cloud-native apps need it?

Kubernetes (K8s) is a container orchestrator (from Google, CNCF 2014) that decides which machine runs which container, restarts crashed ones, scales on traffic, and routes traffic to healthy instances. The core objects: a Pod is the smallest unit (one+ containers sharing network/storage, ephemeral); a Node is a worker machine; the Control Plane is the brain (API Server, Scheduler, Controller Manager, etcd). The central idea is desired state: you declare what you want ("3 replicas of this image") and K8s continuously reconciles actual to match — restart a crashed pod, reschedule a dead node's pods. You drive it all through kubectl against the API Server (apply/get/logs/exec).

  • Container orchestrator — schedules, restarts, scales, routes traffic.
  • Pod / Node / Control Plane — smallest unit, worker, brain (API+Scheduler+etcd).
  • Desired-state reconciliation — declare it; K8s keeps actual matching.
  • kubectl → API Server — apply/get/logs/exec.

Cluster architecture

Control Plane components: API Server — HTTPS endpoint all tools and controllers communicate with. etcd — distributed key-value store, stores all cluster state. If etcd goes down, the cluster is read-only. Scheduler — watches for unscheduled pods, picks a node based on resource requests, affinity rules, taints/tolerations. Controller Manager — runs control loops: ReplicaSet controller (maintains desired replica count), Node controller (marks nodes as unhealthy), Job controller, etc. Worker Node components: kubelet — agent on each node, talks to API server, ensures containers in pods are running. kube-proxy — network rules (iptables/ipvs) for Service IP routing. Container Runtime — containerd or CRI-O (Docker was deprecated as runtime in K8s 1.24). Namespace: virtual cluster within a cluster — isolates resources. kubectl create ns ciam-prod.

In a CIAM deployment: Your Spring CIAM app runs in pods across nodes. kubectl apply -f ciam-deployment.yaml lets the scheduler place pods on nodes with capacity; a crashed pod (OOMKilled, startup failure) is replaced immediately by the ReplicaSet controller, and a failed node's pods reschedule to healthy ones — no manual intervention. Namespaces separate ciam-dev/staging/prod with their own RBAC and quotas, and your Ping server runs as a StatefulSet (stable identity for clustering).

or, the redeploy that redeployed nothing at all

The problem

You rebuilt the image, pushed it back to the same :latest tag, ran the exact kubectl apply -f you always run — and the running pod is still serving yesterday's bug.

The fix that never left the registry

The manifest says image: myregistry/ciam-auth:latest. You fix a bug, docker build, docker push myregistry/ciam-auth:latest, then run kubectl apply -f ciam-auth-pod.yaml — the same command that's "deployed" every time before.

kubectl apply is declarative against the text of the manifest, not the contents of your registry. It diffs the file you just handed it against the kubectl.kubernetes.io/last-applied-configuration annotation already recorded on the live object. The file says image: myregistry/ciam-auth:latest — exactly what it said the last hundred times you ran this. There is no textual difference. Kubernetes issues zero API changes, the kubelet is never told to do anything, and the container running right now is still whatever it pulled the last time something actually forced a pull.

the new image really is in the registry ✓ kubectl apply exited 0, no errors ✓ the running container is still yesterday's code ⚠

kubectl didn't lie to you — from where it's standing, you asked for the exact same thing you already had.

Fix: give the manifest something to actually diff on
Tag images by content, not a floating label — a git SHA or build number (ciam-auth:a91f3c2), so every real change produces a new string in the manifest ↓ kubectl apply diffs text; a new tag is a real text change, so this time it actually issues a patch If you must keep :latest, force the issue yourself — kubectl rollout restart deployment/ciam-auth, or delete the pod, so the kubelet re-pulls ↓ this bypasses the manifest diff entirely and asks the kubelet to fetch again directly — and it only helps if imagePullPolicy is Always And set imagePullPolicy explicitly instead of relying on the tag-based default — Always for a tag that moves, IfNotPresent only for one that genuinely never does
The one-sentence rule. kubectl apply reconciles the cluster's recorded desired state against the text of the file you hand it — it has no way to know what's sitting in your container registry, and it never checks. Pairing a mutable tag like :latest with a habit of "re-push the image, then apply the same unchanged file" guarantees the one command you're running never actually changes anything, because from Kubernetes' point of view, nothing did.
kubectl apply reads your manifest like a grocery list, not a fridge inspection. If the list says "milk" both times, it doesn't matter that you swapped in a different carton at the store — nobody's going back to buy anything.
You

I pushed a new image to the same :latest tag and ran kubectl apply. Why is the old bug still live?

kubectl

Because your file says the same thing it said yesterday. I compare what you hand me to what I last recorded — I've never once looked inside your registry.

So :latest doesn't mean "always the newest one" to you?

kubectl

Not to me. It's four ASCII characters in a string field. If that string doesn't change, neither does anything I control.

The mechanism

Here's exactly what kubectl apply checks before it does anything at all.

  1. You run kubectl apply -f ciam-auth-pod.yamlthe command
  2. kubectl reads the live object's kubectl.kubernetes.io/last-applied-configuration annotationrecorded state
  3. It compares that recorded text against the file you just handed it, field by fieldthe diff
  4. image: myregistry/ciam-auth:latest appears in both — character for character identicalno change found
  5. No patch is generated for that field, or for any field, if nothing else in the file changed eitherzero-length patch
  6. The API server receives nothing to update; the kubelet is never told to do anything; the running container keeps runningsilent no-op

Step 3 is doing exactly its job — a real, byte-level diff. The bug isn't in the diff; it's in expecting that diff to somehow know about a registry push that never touched the one thing it's allowed to look at: the text of your manifest.

kubectl apply decides whether anything needs to changeyou just pushed a new image to the same :latest tag
what it actually compares →
the digest of the image currently running in the pod what's newly sitting in the container registry the literal text already stored in kubectl.kubernetes.io/last-applied-configuration

Kubernetes never asks the registry a single question during kubectl apply — the only thing being compared is text you already gave it before, against text you're giving it now. A registry push doesn't touch either side of that comparison.

Nothing here points to an auth failure — kubectl apply genuinely exits 0 because it found no difference to apply, not because something silently broke.

Where you have seen this before

A reconciliation system that trusts the declared text in front of it, and has no way to see the reality that text is supposed to describe.

Terraform plan showing "no changes" over real drift

terraform plan diffs your .tf files against its own state file — not against whatever is actually running in AWS. Someone edits a security group by hand in the console, or a referenced "latest" AMI gets rebuilt upstream, and Terraform can report a clean plan anyway, because nothing in the text it tracks actually changed.

the state file, not the cloud, is the thing being compared

CloudFront still serving the old file from the same key

You overwrite an object in S3 at the exact same key, but CloudFront keeps serving the cached response until its TTL expires or you run an explicit invalidation. The CDN's decision was never "is the origin content different" — it's "do I already have something cached for this key."

same URL, new bytes, stale answer until told otherwise

Angular OnPush missing a mutated array

A component with ChangeDetectionStrategy.OnPush only re-renders when an @Input's reference changes. Call this.items.push(x) instead of assigning a new array, and the reference is identical to before — Angular's change detector compares references, not contents, so the new item never appears on screen.

the comparison was shallow on purpose, and the data changed somewhere it doesn't look
The whole page on a napkin: Kubernetes is a reconciliation loop — pods, nodes, the control plane, kubectl, namespaces, and lifecycle phases, all built around "declare the desired state and K8s makes it real." The new sentence this block adds: "desired state" means the literal text you handed it last, not whatever now exists in your registry — so kubectl apply is a genuine no-op whenever that text hasn't changed, no matter what you just pushed.

2 — Pods




A Pod wraps one or more containers that share the same network namespace (same IP) and can share volumes. Pods are ephemeral — they don't reschedule themselves. That's what Deployments are for.


# minimal pod manifest
apiVersion: v1
kind: Pod
metadata:
  name: demo
  labels:
    app: demo
spec:
  containers:
  - name: app
    image: myregistry/demo:1.0
    ports:
    - containerPort: 8080
    resources:
      requests: { cpu: "100m", memory: "256Mi" }
      limits:  { cpu: "500m", memory: "512Mi" }


100m CPU = 0.1 core. Always set both requests and limits — requests drive scheduling; limits prevent a bad pod from starving others.

4 — Namespaces & Resource Quotas




Namespaces are virtual clusters within a physical cluster. They scope names, RBAC policies, and resource quotas. Use them to isolate environments (dev/staging) or teams.


# create a namespace
kubectl create namespace team-alpha

# ResourceQuota limits total consumption
apiVersion: v1
kind: ResourceQuota
metadata:
  name: team-alpha-quota
  namespace: team-alpha
spec:
  hard:
    pods: "20"
    requests.cpu: "4"
    requests.memory: 8Gi


Four built-in namespaces: default (your apps if unspecified), kube-system (K8s internals), kube-public (readable by all), kube-node-lease (node heartbeats).









5 — Pod Lifecycle






PhaseMeaning


PendingAccepted by API server; waiting for scheduler or image pull


RunningAt least one container running; others may still be starting


SucceededAll containers exited 0 (Job pods)


FailedAt least one container exited non-zero and won't restart


UnknownNode communication lost; pod state unreadable




Restart policies: Always (default, good for servers), OnFailure (Jobs), Never (run-once tasks). CrashLoopBackOff = container keeps crashing; K8s backs off exponentially (10s → 20s → 40s… max 5min).
