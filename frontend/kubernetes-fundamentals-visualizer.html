Kubernetes Fundamentals

Pods, nodes, clusters, kubectl — how K8s schedules and runs your containers.

What is Kubernetes — and why do modern cloud-native apps need it?

Kubernetes (abbreviated K8s, because there are 8 letters between "K" and "s") is an open-source container orchestration platform originally built at Google and donated to the CNCF in 2014. In plain English: Kubernetes is the system that decides which machine runs which container, restarts containers when they crash, scales them up when traffic spikes, and routes network traffic to healthy instances. Without Kubernetes (or something like it), you would manually deploy containers to specific servers — if a server dies, your app is down. The core objects: A Pod is the smallest deployable unit — one or more tightly-coupled containers that share a network namespace and storage. Pods are ephemeral — they come and go. A Node is a worker machine (VM or bare metal) where pods run. The Control Plane is the brain: the API Server (all kubectl commands go here), the Scheduler (assigns pods to nodes), the Controller Manager (runs controllers that reconcile desired vs actual state), and etcd (the distributed key-value store that holds all cluster state). Desired state is the core concept: you declare what you want ("3 replicas of my auth service, using this image") and Kubernetes continuously reconciles actual state to match desired state. If a pod crashes, Kubernetes restarts it. If a node fails, Kubernetes reschedules its pods elsewhere. kubectl is the CLI for talking to the API Server: kubectl apply -f manifest.yaml (declare desired state), kubectl get pods (list pods), kubectl logs (view logs), kubectl exec -it pod-name -- sh (shell into a pod).

kubectl essentials

# Apply a manifest (create or update): kubectl apply -f deployment.yaml # List resources: kubectl get pods -n ciam-namespace kubectl get nodes -o wide kubectl get all # everything # Inspect: kubectl describe pod <name> # events + config kubectl logs <pod> -f # follow logs kubectl logs <pod> -c <container> # multi-container # Debug: kubectl exec -it <pod> -- sh # shell into pod kubectl port-forward pod/<name> 8080:8080 # Delete: kubectl delete pod <name> # Kubernetes restarts it! kubectl delete -f deployment.yaml # Contexts (switch clusters): kubectl config use-context dev-cluster

Cluster architecture

Control Plane components: API Server — HTTPS endpoint all tools and controllers communicate with. etcd — distributed key-value store, stores all cluster state. If etcd goes down, the cluster is read-only. Scheduler — watches for unscheduled pods, picks a node based on resource requests, affinity rules, taints/tolerations. Controller Manager — runs control loops: ReplicaSet controller (maintains desired replica count), Node controller (marks nodes as unhealthy), Job controller, etc. Worker Node components: kubelet — agent on each node, talks to API server, ensures containers in pods are running. kube-proxy — network rules (iptables/ipvs) for Service IP routing. Container Runtime — containerd or CRI-O (Docker was deprecated as runtime in K8s 1.24). Namespace: virtual cluster within a cluster — isolates resources. kubectl create ns ciam-prod.

In a CIAM deployment: Your CIAM Spring Boot app running on Kubernetes runs in pods across multiple nodes. When you do kubectl apply -f ciam-deployment.yaml, the scheduler places pods on nodes with enough CPU/memory. If a pod crashes (OOMKilled, Spring startup failure), the kubelet detects this, reports to the control plane, and the ReplicaSet controller creates a new pod immediately. If a node fails (Azure VM deallocation, AWS spot interruption), all pods on that node are rescheduled to healthy nodes — zero manual intervention. Kubernetes namespaces separate environments: ciam-dev, ciam-staging, ciam-prod — each with their own RBAC roles (who can deploy to prod) and resource quotas (prod gets more CPU). Your Ping Identity server might run as a StatefulSet (stable network identity required for clustering).

2 — Pods




A Pod wraps one or more containers that share the same network namespace (same IP) and can share volumes. Pods are ephemeral — they don't reschedule themselves. That's what Deployments are for.


# minimal pod manifest
apiVersion: v1
kind: Pod
metadata:
  name: demo
  labels:
    app: demo
spec:
  containers:
  - name: app
    image: myregistry/demo:1.0
    ports:
    - containerPort: 8080
    resources:
      requests: { cpu: "100m", memory: "256Mi" }
      limits:  { cpu: "500m", memory: "512Mi" }


100m CPU = 0.1 core. Always set both requests and limits — requests drive scheduling; limits prevent a bad pod from starving others.









3 — kubectl Essentials




# context & cluster
kubectl config get-contexts
kubectl config use-context my-cluster

# apply manifests (declarative)
kubectl apply -f deployment.yaml
kubectl apply -f ./k8s/          # whole directory

# inspect
kubectl get pods -n my-namespace
kubectl get pods -A              # all namespaces
kubectl describe pod demo-abc
kubectl logs demo-abc -f         # stream logs
kubectl exec -it demo-abc -- /bin/sh

# debug
kubectl get events --sort-by=.metadata.creationTimestamp
kubectl top pods                 # requires metrics-server









4 — Namespaces & Resource Quotas




Namespaces are virtual clusters within a physical cluster. They scope names, RBAC policies, and resource quotas. Use them to isolate environments (dev/staging) or teams.


# create a namespace
kubectl create namespace team-alpha

# ResourceQuota limits total consumption
apiVersion: v1
kind: ResourceQuota
metadata:
  name: team-alpha-quota
  namespace: team-alpha
spec:
  hard:
    pods: "20"
    requests.cpu: "4"
    requests.memory: 8Gi


Four built-in namespaces: default (your apps if unspecified), kube-system (K8s internals), kube-public (readable by all), kube-node-lease (node heartbeats).









5 — Pod Lifecycle






PhaseMeaning


PendingAccepted by API server; waiting for scheduler or image pull


RunningAt least one container running; others may still be starting


SucceededAll containers exited 0 (Job pods)


FailedAt least one container exited non-zero and won't restart


UnknownNode communication lost; pod state unreadable




Restart policies: Always (default, good for servers), OnFailure (Jobs), Never (run-once tasks). CrashLoopBackOff = container keeps crashing; K8s backs off exponentially (10s → 20s → 40s… max 5min).
