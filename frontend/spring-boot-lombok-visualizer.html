Lombok & Code Generation

Lombok generates boilerplate at compile time via Annotation Processing Tool (APT) — getters, setters, builders, equals/hashCode, constructors, and @Slf4j logging. Zero runtime overhead, but know the gotchas.

🧰 What is Lombok — and what boilerplate does it eliminate from Java classes?

Java makes you write the same boilerplate on every class — getters, setters, equals()/hashCode()/toString(), constructors. A 10-field class is 30+ lines that carry zero information. Lombok removes it with annotations processed at compile time (its annotation processor generates the bytecode for those methods). Your source keeps just the fields and business logic; the boilerplate is present in the compiled class but invisible in the file — with zero runtime overhead, since Lombok ships no runtime classes. The catch: a few annotations interact badly with JPA, Jackson, and Spring, and knowing which saves hours of mysterious bugs.

  • Compile-time codegen, not reflection. No runtime dependency, no performance cost.
  • @Data is the all-in-one — Getter + Setter + ToString + EqualsAndHashCode + RequiredArgsConstructor.
  • Don't put @Data on entities. It drags lazy fields into equals/hashCode and omits the no-args constructor JPA needs.
  • @Builder breaks Jackson unless paired with @Jacksonized (or use a record).

Most-used annotations

@Getter/@Setter, @ToString, @EqualsAndHashCode (can exclude fields), the three constructor annotations, @Data (combines them), @Builder (fluent builder), and @Slf4j (injects a log).

@Data + @Entity gotcha

Two traps on a JPA @Entity: @EqualsAndHashCode pulls in lazy collections → LazyInitializationException outside a transaction, and the generated @RequiredArgsConstructor clashes with JPA's no-args requirement. Use @Getter/@Setter/@NoArgsConstructor separately instead.

@Builder + Jackson gotcha

@Builder drops the default constructor Jackson needs. Fix with @Builder @AllArgsConstructor @NoArgsConstructor, or just add @Jacksonized (Lombok 1.18.14+). For deserialize-only DTOs, prefer Java records — immutable and Jackson-friendly with no extra annotations.

CIAM: Response DTO as @Builder @Jacksonized record UserResponse(Long id, String email, …); request DTO as @Data @Builder @AllArgsConstructor @NoArgsConstructor class CreateUserRequest; entity as @Getter @Setter @NoArgsConstructor @Entity class User (never @Data); services use @Slf4j for log.info("Creating user: {}", email).

or, @Data's hashCode changes the moment JPA assigns an id — and a HashSet never finds out

The problem

The entity went into the Set. save() ran fine. The Set now insists it has never seen it.

A saved entity that its own HashSet can't find

@Data @Entity class Tag { @Id @GeneratedValue Long id; String name; }. Then: Tag t = new Tag(); t.setName("URGENT"); Set<Tag> tags = new HashSet<>(); tags.add(t); tagRepository.save(t); — save() assigns t.id = 501 in place, mutating the very same object. @Data generated a hashCode() from every field, id included. At tags.add(t), id was still null, so the HashSet computed a hash from (id=null, name="URGENT") and dropped t into the bucket that hash pointed to. save() then changes id to 501 on that same object — and t's hashCode, computed fresh, is now a completely different number. tags.contains(t) comes back false.

@Data on the entity ✓ tags.add(t) succeeds ✓ tagRepository.save(t) succeeds, id assigned ✓ t's hashCode is now a different value than when it was inserted ⚠ tags.contains(t) — false ⚠

A HashSet doesn't store objects by identity. It stores them by whatever hashCode() answered at insertion time — and never asks again.

Never hash a field that's designed to change
  1. Never let a JPA-generated @Id drive equals()/hashCode()the fix
  2. @EqualsAndHashCode(onlyExplicitlyIncluded = true) + @EqualsAndHashCode.Include on a stable business key — or none at alloption 1
  3. Or base identity on a natural key set once, at construction, that never changes afterwardoption 2
  4. With no natural key: fall back to comparing ids only when both are non-null — never let @Data auto-include a mutable, initially-null fieldoption 3
A HashSet computes an object's bucket ONCE, at insertion, using whatever hashCode() returns at that moment. If any field hashCode() depends on can change afterward — and a JPA @GeneratedValue id changes from null to a real value the instant it's persisted — the object's bucket and its hashCode silently disagree forever after. @Data doesn't know which of your fields are stable and which aren't; it includes all of them, unconditionally.
Think of a HashSet's bucket like a coat-check ticket written from "what the coat looks like right now." You hand over a coat with no buttons yet — the ticket says "plain wool coat, bucket 14." While it's hanging there, someone sews buttons onto your actual coat (your id gets assigned). Come back and ask "do you have my coat with buttons?" — the attendant checks bucket 12, the one "coat with buttons" tickets go to, finds nothing, and says no. Your coat never moved. It's still hanging in bucket 14, buttons and all. The ticket just stopped matching the coat the moment the coat changed.
You

I added it to the Set before save(), and contains() says it's not there. But I can see it right there if I iterate the Set with a for loop!

HashSet

Because iterating doesn't ask me to compute anything — I just walk every bucket and hand you whatever's inside. contains() is the one that trusts hashCode() to tell it WHICH bucket to even look in. I asked your object for its hash the moment you called add() — I never asked again.

You

Fine — so ask it again. Why not just recompute the hash on every lookup?

HashSet

Because that would mean rehashing every element on every single operation, and the entire reason anyone reaches for me is O(1) lookups. My contract is "trust the hash from insertion time." That's not a bug — every hash table in every language makes that same deal.

You

Then this is on @Data — it generated hashCode() from every field, id included.

Lombok's @Data

I did exactly what you told me to: include every field in equality and hashing. I have no idea id is special — that it starts null and gets silently overwritten by something else, seconds later. You never told me to exclude it.

You

Then it's Hibernate's fault. It's the one mutating the id in place after I already added t to the Set.

Hibernate

I did exactly what @GeneratedValue promises: assign the database-generated id back onto your managed entity the moment the INSERT flushes, so you don't have to reload it. Mutating the same object in place is the entire point — swapping in a new object would break every reference you're already holding. Nobody told me a HashSet was quietly depending on that object's hashCode staying frozen.

You

So all three of you did your job perfectly, and I still lost the entity.

HashSet

That's the whole lesson. None of us is wrong. None of us even knows the other two exist. You're the only one holding all three assumptions at once — and the only one who can keep them from colliding.

The mechanism

Every step behaves exactly as documented. The bug lives entirely in the combination.

  1. new Tag() is created — id is null, since @GeneratedValue only fires on insertid = null right now
  2. tags.add(t) — HashSet calls t.hashCode(), computed from (id=null, name="URGENT"), and stores t in the bucket that hash maps tothe bucket is chosen ONCE, right here
  3. tagRepository.save(t) flushes an INSERT — Hibernate mutates the SAME object's id field in place, from null to 501same reference, new field value
  4. t.hashCode(), if called now, returns a completely different value — because id is now part of the computation and it changedthe object's own hash just moved
  5. tags.contains(t) calls t.hashCode() again, gets the NEW value, and looks in the bucket THAT hash maps tothe wrong bucket for where t actually lives
  6. That bucket doesn't have t in it — t is still sitting in the bucket chosen back in step 2. contains() returns falselost, but not gone

Step 3 is the moment the trap is set, but step 2 is the actual design flaw: hashCode() was computed and trusted to stay valid for as long as the object lives in that Set — and @Data built a hashCode() out of a field, id, that's specifically designed to change exactly once, right after insertion.

The Tag entity t — one single object in memorynever replaced, never copied
asked for its hashCode at two different moments ↓
Moment 1 (tags.add(t)): hashCode from id=null → HashSet stores t in bucket(H1) save() assigns id=501 — nothing about the Set's internal buckets moves Moment 2 (tags.contains(t)): hashCode from id=501 → a different bucket entirely bucket(H2) is empty — contains() reports false, even though t still sits safely in bucket(H1)

Same object, same reference, two different hashCode answers a few milliseconds apart — and a HashSet has no mechanism for reconciling the two.

@Data @Entity class Tag { @Id @GeneratedValue Long id; String name; }. Tag t = new Tag(); t.setName("URGENT"); Set<Tag> tags = new HashSet<>(); tags.add(t); tagRepository.save(t); — save() assigns t.id = 501 in place, on the same object. What does tags.contains(t) return right after that, and why?

HashSet never re-hashes anything automatically — it has no way to know a field changed, and no mechanism that runs on mutation. It computed a bucket once, at add(), and has trusted that answer ever since.

Hibernate's persistence-context identity map does guarantee the SAME row loaded twice returns the SAME Java object reference — but that's a completely separate mechanism from java.util.HashSet, which has no idea a JPA transaction or session even exists. There's no fallback like this.

Exactly — t never moved. contains() just went looking in the wrong bucket, because it trusts whatever hashCode() answers RIGHT NOW, and that answer changed the instant id was assigned. The object is still in the set; it's simply unreachable through the one method that's supposed to find it quickly.

Questions from the back row

Doesn't @EqualsAndHashCode.Include let me just leave id out entirely?

Yes — that's exactly the fix for entities with no natural key: base equality on nothing but the class itself (or a truly immutable business key set at construction) until the entity has an id, then compare by id only once it's assigned and never mutated again. It's more code than @Data's one-liner — which is exactly why @Data is the wrong tool for an entity in the first place.

If I only ever call save() before adding anything to a Set, does this go away?

Yes, in this specific case, because id would already be assigned before hashCode() ever gets computed for the add(). But that just relocates the landmine — the same bug reappears the moment ANY code path adds a transient, unsaved entity to a Set or Map key before persisting it, and nothing in the type system stops that from happening somewhere else in a large codebase.

Is this a Lombok bug, a JPA bug, or a HashSet bug?

None of them, individually — each behaves exactly as documented. Lombok does exactly what @Data promises (include every field). JPA does exactly what @GeneratedValue promises (assign the id on insert, mutating the same object). HashSet does exactly what its contract promises (trust hashCode() at insertion, never recompute). The bug lives entirely in the combination — none of the three components was ever told about the other two's assumptions.

2. @Data vs @Value vs record

// @Data: mutable DTO (has setters)
@Data
public class UserDto {
  private String name;
  private String email;
  private String role;
}

// @Value: immutable value object (no setters)
@Value
public class Money {
  BigDecimal amount;
  String currency;
}// all fields are private final automatically
// Java 16+ record: built-in immutable VO
public record Money(BigDecimal amount, String currency) {}
// generated: constructor, getters (amount()), equals, hashCode, toString
// no Lombok needed

// When to choose what:
// JPA entity → @Entity + @Data (AVOID @Value — JPA needs setters/no-arg ctor)
// Mutable DTO → @Data
// Immutable DTO → record (Java 16+) or @Value
// Complex build → @Builder

Java 16+ records replace most @Value uses. Records are a language feature — no annotation processor needed, first-class support in Spring, and no Lombok plugin required in IDEs. Prefer records for immutable DTOs in modern Spring Boot projects.

3. @RequiredArgsConstructor for Spring Injection

// Lombok generates the constructor Spring uses for DI
@Service
@RequiredArgsConstructor // generates: UserService(UserRepo r, MailService m)
public class UserService {
  private final UserRepository userRepository;
  private final MailService mailService;
  
  // NO @Autowired needed — Spring injects via constructor
}
// Without Lombok — verbose boilerplate
@Service
public class UserService {
  private final UserRepository userRepository;
  private final MailService mailService;
  
  @Autowired
  public UserService(UserRepository ur, MailService ms) {
    this.userRepository = ur;
    this.mailService = ms;
  }
}
Constructor injection is recommended over @Autowired fields. @RequiredArgsConstructor generates the correct constructor for all final fields. Spring automatically uses the single constructor — no @Autowired needed. This pattern is the Spring Boot best practice for dependency injection.
