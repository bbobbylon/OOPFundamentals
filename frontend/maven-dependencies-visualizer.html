Dependency Scopes

What each scope includes on which classpath and what ends up in the final JAR. Click any scope for examples.

What are Maven dependency scopes — and why does scope determine what ends up in your final JAR?

Every Maven dependency has a scope that controls three things: (1) which classpath the dependency is on (compile, test, runtime), (2) whether it's included in the final artifact (JAR/WAR), and (3) whether it's transitive (passed on to modules that depend on this module). Getting scope wrong can cause runtime failures (ClassNotFoundException) or bloated JARs. compile (default if not specified): available in compile classpath, test classpath, and runtime classpath. Included in the fat JAR. Example: spring-boot-starter-web — you write code against Spring MVC annotations, so you need it at compile time AND it needs to run. runtime: NOT available at compile time (you can't import its classes in your code), but IS available at runtime and included in the JAR. Example: JDBC drivers — you never directly import org.postgresql.Driver in your code (you use javax.sql.DataSource which is in JDK), but the driver must be on the classpath at runtime so JDBC can load it. test: only available during test compilation and execution. NOT included in the final JAR. Example: JUnit, Mockito, WireMock, AssertJ. Your production users don't need JUnit — removing it from the JAR saves space and reduces attack surface. provided: available at compile time (you CAN import it), but NOT included in the JAR because the runtime environment provides it. Example: Tomcat Servlet API — when deploying a WAR to an external Tomcat, Tomcat already has the Servlet API; including it in the WAR would cause conflict. For Spring Boot fat JARs (embedded Tomcat), use compile instead. Lombok uses provided because the annotation processor runs at compile time only. system: like provided but you specify the JAR path explicitly. Avoid — tightly couples to local filesystem. import: only in <dependencyManagement> — imports a BOM (Bill of Materials) for version management.

Scope examples

<dependencies> <!-- compile (default): in JAR + compile CP --> <dependency> <groupId>org.springframework.boot</groupId> <artifactId>spring-boot-starter-web</artifactId> </dependency> <!-- runtime: in JAR but NOT compile CP --> <dependency> <groupId>org.postgresql</groupId> <artifactId>postgresql</artifactId> <scope>runtime</scope> </dependency> <!-- test: only in test CP, NOT in JAR --> <dependency> <groupId>com.github.tomakehurst</groupId> <artifactId>wiremock-jre8</artifactId> <scope>test</scope> </dependency> <!-- provided: compile CP but NOT in JAR --> <dependency> <groupId>org.projectlombok</groupId> <artifactId>lombok</artifactId> <scope>provided</scope> </dependency> </dependencies>

Dependency conflicts

# Diagnose dependency tree: mvn dependency:tree # Find specific artifact + who depends on it: mvn dependency:tree -Dincludes=com.fasterxml.jackson.core:jackson-databind # Example conflict output: # [INFO] +- org.springframework.boot:spring-boot-starter-web:jar:3.3.0 # \- com.fasterxml.jackson.core:jackson-databind:jar:2.17.0:compile # [INFO] +- io.jsonwebtoken:jjwt-impl:jar:0.12.5 # \- com.fasterxml.jackson.core:jackson-databind:jar:2.15.0:compile (omitted for conflict) # → Spring Boot wins (closest dep) # Force a version if needed: <dependency> <groupId>com.fasterxml.jackson.core</groupId> <artifactId>jackson-databind</artifactId> <version>2.17.0</version> ← explicit override </dependency>

BOMs + version management

<!-- BOM (Bill of Materials): version catalog --> <dependencyManagement> <dependencies> <!-- Spring Cloud BOM: manages all Spring Cloud versions --> <dependency> <groupId>org.springframework.cloud</groupId> <artifactId>spring-cloud-dependencies</artifactId> <version>2023.0.1</version> <type>pom</type> <scope>import</scope> </dependency> </dependencies> </dependencyManagement> <!-- Now you can use Spring Cloud deps without version: --> <dependency> <groupId>org.springframework.cloud</groupId> <artifactId>spring-cloud-starter-openfeign</artifactId> <!-- version managed by BOM! --> </dependency>

CIAM dependency management: Common CIAM pom.xml scope decisions: postgresql → runtime (JDBC driver, never import directly), spring-boot-starter-test → test (JUnit + Mockito), wiremock → test (mock Ping/Entra HTTP APIs in tests), lombok → provided (annotation processor, not needed at runtime), spring-security-oauth2-jose → compile (JWT parsing code), spring-boot-starter-oauth2-resource-server → compile (you configure it via @EnableResourceServer). Spring Boot parent manages: Jackson (JSON), SLF4J/Logback (logging), HikariCP (connection pool), Hibernate (JPA), Tomcat (embedded server), Spring Security versions — all consistent. mvn dependency:analyze — finds declared but unused dependencies (can remove scope) and used but undeclared (transitive deps you rely on, should declare explicitly). Run before version upgrades to clean up.

2 — Transitive Dependencies

Maven downloads the full dependency graph, not just what you declare:

Your Project
→ depends on (compile)
spring-boot-starter-web
→ depends on (compile)
spring-webmvc
→ depends on (compile)
spring-context
✓ You get spring-context
Your Project
→ depends on (compile)
Library A
→ depends on (test)
JUnit 5
✗ You do NOT get JUnit

Rule: test-scoped and provided-scoped transitive dependencies are NOT passed down. compile-scoped ones are. Use mvn dependency:tree to see the full graph and diagnose version conflicts.

3 — Dependency Exclusions

Remove an unwanted transitive dependency — common when switching logging implementations:

<!-- spring-boot-starter-web pulls in logback-classic by default --> <!-- To use log4j2 instead, exclude logback and add log4j2 --> <dependency> <groupId>org.springframework.boot</groupId> <artifactId>spring-boot-starter-web</artifactId> <exclusions> <exclusion> <groupId>ch.qos.logback</groupId> <artifactId>logback-classic</artifactId> </exclusion> </exclusions> </dependency> <dependency> <groupId>org.springframework.boot</groupId> <artifactId>spring-boot-starter-log4j2</artifactId> </dependency>

4 — Reading mvn dependency:tree

Run this to see the full dependency graph and debug version conflicts:

$ mvn dependency:tree [INFO] com.example:my-app:jar:1.0.0-SNAPSHOT [INFO] +- org.springframework.boot:spring-boot-starter-web:jar:3.3.0:compile [INFO] | +- org.springframework.boot:spring-boot-starter:jar:3.3.0:compile [INFO] | | +- org.springframework.boot:spring-boot:jar:3.3.0:compile [INFO] | | \- ch.qos.logback:logback-classic:jar:1.4.14:compile ← you might want to exclude this [INFO] | +- com.fasterxml.jackson.core:jackson-databind:jar:2.17.0:compile [INFO] +- org.postgresql:postgresql:jar:42.7.3:runtime ← runtime scope, not compile [INFO] \- org.springframework.boot:spring-boot-starter-test:jar:3.3.0:test [INFO] +- org.junit.jupiter:junit-jupiter:jar:5.10.2:test [INFO] \- org.mockito:mockito-core:jar:5.11.0:test

The tree shows: each dependency's scope (compile/runtime/test), version resolution (who won when multiple versions are in play), and the full transitive chain. Essential for debugging "NoClassDefFoundError" and version conflicts.
