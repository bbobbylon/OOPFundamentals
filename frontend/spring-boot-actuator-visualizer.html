Actuator & Observability

Spring Boot Actuator exposes production-ready endpoints for health checks, metrics, and diagnostics. Essential for Docker, Kubernetes, and cloud deployments.

🩺 What is Spring Boot Actuator — and why does every production app need it?

In production, how do you know the app is healthy, whether the DB pool is exhausted, or what value a config property actually resolved to? Read logs — or hit an Actuator endpoint and get the answer instantly. Spring Boot Actuator adds HTTP endpoints under /actuator that expose operational metadata: health, environment, loaded beans, request mappings, thread dumps, and metrics. Kubernetes and load balancers poll /actuator/health as readiness/liveness probes — 200 UP means route traffic here, anything else means restart or drain the pod. Without it, ops is flying blind.

  • It's your app's instrument panel — health, metrics, env, mappings, loggers, all over HTTP.
  • K8s depends on it. Readiness gates traffic; liveness triggers restarts.
  • Lock it down. Only health/info are public by default; secure the rest behind a role.
  • Extensible. A custom HealthIndicator adds dependency checks (e.g. "is Ping reachable?").

Key endpoints

/health (UP/DOWN + components), /env (effective property values), /beans, /mappings, /metrics/{name} (heap, request counts, pool usage), and /loggers/{name} — read and change a log level at runtime with no redeploy.

What to expose

Only health and info are public by default. Opt others in via management.endpoints.web.exposure.include, then require an ACTUATOR_ADMIN role. Never expose /env publicly — it lists every property (values masked, names not).

Custom health indicators

Implement HealthIndicator: a PingHealthIndicator returns Health.down().withDetail("reason","Ping unreachable") when the IDM is down. It shows up under /health, and K8s stops routing to the pod until it recovers.

CIAM: GET /actuator/health/readiness includes DB, Redis (session store), and Ping checks — if Ping is down, readiness goes DOWN and K8s stops routing new auth requests to that pod while in-session users continue elsewhere. /health/liveness only asks "is the JVM alive?" And flipping com.company.ciam.security to DEBUG via /loggers reveals every JWT validation step without a restart.

or, health isn't one number — it's two different questions with two different consequences

The problem

Ping has a five-minute blip. Kubernetes decides your app itself is broken, and restarts it. Six times.

The pods keep restarting, and the JVM was never the thing that was actually down

A K8s manifest wires livenessProbe to plain /actuator/health instead of /actuator/health/liveness — it "worked in testing," because in testing every downstream dependency was always up. In production, Ping has a brief outage. The Ping HealthIndicator reports DOWN, the aggregate health rolls up to DOWN, the liveness probe fails three times in a row, and kubelet kills the container. The new pod boots, checks health, Ping is still down, health is still DOWN — and it gets killed again. Real users on that pod get dropped, repeatedly, on top of an outage that was never the JVM's fault in the first place.

JVM never crashed or hung ✓ request-handling threads healthy the whole time ✓ liveness wired to full /actuator/health, not /liveness ⚠ a downstream Ping outage now restarts the pod repeatedly ⚠

The wrong assumption: that "health" is one number, so pointing both probes at the same endpoint is a harmless simplification.

Point readiness at your dependencies, and liveness at nothing but the JVM
Readiness probe → /actuator/health/readiness, including DB, Redis, Ping ↓ readiness saying DOWN just removes the pod from the load balancer's rotation — cheap, reversible, no restart Liveness probe → /actuator/health/liveness specifically — JVM-only, zero downstream calls ↓ a liveness failure means "kill and restart," which only fixes what restarting can actually fix — a deadlock, a leak, a stuck process Ping going down now drains traffic from the pod instead of destroying and rebuilding it every 10 seconds
Readiness and liveness ask different questions, and only one of them should ever depend on something outside your JVM. Readiness asks "can this pod usefully serve traffic right now" — a downstream dependency being down is a completely legitimate reason to say no. Liveness asks "is this specific process broken in a way only a restart can fix" — a third-party outage is never that, no matter how badly it drags down the aggregate. Wire liveness to anything that touches Ping, the database, or any other external system, and "something else is having a bad day" quietly becomes "let's make our own app worse too."
Think of readiness as a "kitchen accepting new orders" sign, and liveness as "is anyone in the kitchen still breathing." Run out of one ingredient and you flip the sign for that dish — nobody calls an ambulance. Only someone collapsing on the floor calls the ambulance — that's the restart. It stops holding up in one place: no real restaurant has an automated system that mistakes "we're out of an ingredient" for "call an ambulance" — but that's exactly the mix-up a liveness probe pointed at the wrong health group makes, over and over, every ten seconds.

The mechanism

Two probes, two completely different consequences, for the exact same word: "down."

  1. K8s calls GET /actuator/health/readiness on an intervalanswers: route new traffic here, or not
  2. The readiness indicator aggregates DB, Redis, and the Ping HealthIndicatordownstream dependencies belong here, on purpose
  3. Ping times out; its indicator reports DOWN; readiness rolls up to DOWNcorrect and useful — pull this pod out of rotation
  4. Separately, K8s calls GET /actuator/health/liveness on its own intervala different endpoint, a different question entirely
  5. Liveness checks only JVM-level signals — it never calls Ping, or anything else externalno downstream calls belong here, ever
  6. Liveness stays UP through the whole outage; readiness alone flips DOWN and backtraffic drains and returns; nothing restarts

Step 5 is the lesson. Liveness is deliberately, structurally shallow — Spring Boot's own liveness group checks nothing but whether the application context itself is up, by default. Add a downstream dependency check to liveness and you've turned "restart this container" into the response for "a system I don't control had a bad five minutes," and no amount of restarting fixes that. Readiness is the only one of the two probes actually built to carry that kind of external information.

aggregates ↓ asks every registered indicator
DB HealthIndicatorRedis HealthIndicatordisk space indicator Ping HealthIndicator ← the one that just went DOWN

Readiness isn't one check — it's a fan-out. Every registered indicator gets asked, and the aggregate is DOWN the moment even one of them is. That's exactly why a single flaky dependency, Ping here, can take a perfectly healthy pod out of rotation all by itself — correct behavior for readiness, and precisely the wrong behavior to hand to liveness.

Ping goes down for 90 seconds. Liveness is correctly wired to /actuator/health/liveness, readiness to /actuator/health/readiness. What happens to a pod that was already up and serving traffic?

Right — and worth noticing: in-flight requests that pod is already handling aren't forcibly killed either. Readiness failing only affects whether new traffic gets routed there; it doesn't reach back and terminate work already in progress.

This is exactly the outcome from the broken wiring in the problem section above — a completely reasonable guess if you don't yet know Kubernetes only restarts a container because of a failed liveness probe specifically, never because of readiness. With the two probes correctly split, a downstream outage has no path left to trigger a restart at all.

Actuator endpoints are indeed "just HTTP responses" in isolation, so this is a fair guess in a vacuum. What makes them consequential is that Kubernetes is explicitly configured to poll them and take automated action — route or don't-route, restart or don't-restart — based on the status code and body they return.

Where you've seen this before

"Stop routing here" and "destroy and rebuild this" are two different remedies — every platform that automates recovery ends up splitting them.

AWS: ALB target health vs. Auto Scaling instance health

An ALB target group can mark one instance unhealthy and simply stop sending it traffic — the instance keeps running, completely untouched. A separate, stricter Auto Scaling health check is what actually terminates and replaces an instance. Same two-tier split as readiness/liveness, wearing AWS's names for the two tiers instead of Kubernetes's.

stop routing ≠ terminate and replace

Resilience4j's circuit breaker, OPEN state

A circuit breaker trips OPEN when a downstream call keeps failing, and stops sending it traffic — without restarting or rebuilding anything on the calling side. That's readiness's exact job, just implemented per-call instead of per-pod: isolate a failing dependency without treating your own healthy process as the thing that's broken.

isolate the failure, don't restart yourself

Feeding Ping's own status page into your readiness, on purpose

Some CIAM teams go one step further and have their readiness indicator watch Ping/Entra's own published status feed directly, instead of waiting for a live auth call to time out first — flipping readiness DOWN proactively the moment the IdP reports an incident, before a single real user request has to fail to discover it.

readiness can react before the first real failure
Questions from the back row

Why have two separate probes at all — why not one endpoint that just means "everything's fine"?

Because "fine" isn't one fact — it's at least two, with completely different fixes. A downstream dependency being down calls for "stop sending traffic here" (readiness). A JVM that's deadlocked or has leaked itself into oblivion calls for "kill and restart it" (liveness). Collapse them into one endpoint and you force Kubernetes to apply a single remedy to both situations — and for a downstream outage, the only remedy it has (restart) does nothing useful. It just adds a restart's worth of extra disruption on top of a problem restarting can't touch.

Does Spring Boot split these into separate health groups automatically, or is it manual?

You opt in — set management.endpoint.health.probes.enabled=true (on by default once Spring detects it's running on Kubernetes, but worth setting explicitly). That exposes /actuator/health/liveness and /actuator/health/readiness as separate groups. A custom indicator like PingHealthIndicator joins the readiness group by default — you'd have to deliberately reassign one into the liveness group, which is almost never the right call.

If liveness never checks the database, how does connection-pool exhaustion ever get caught?

Through readiness — and that's the correct place for it. A fully exhausted pool means this pod genuinely can't serve DB-backed requests right now, so readiness correctly goes DOWN and traffic routes elsewhere while the pool (or the underlying DB issue) recovers. Restarting the JVM doesn't inherently un-exhaust a pool if the root cause is the database itself being slow — routing that through liveness risks the exact same restart-storm failure as the Ping example above, for the same underlying reason.

HTTP/1.1 200 OK { "app": { "name": "my-spring-app", "version": "1.2.0", "description": "Customer API service" }, "build": { "artifact": "my-spring-app", "time": "2024-06-01T14:30:00Z" }, "git": { "commit": { "id": "a3c2683", "time": "2024-06-01T12:00:00Z" }, "branch": "main" } }
Configure in application.yml under info: for static data. Add spring-boot-maven-plugin build-info goal and git-commit-id-maven-plugin for build/git data automatically injected at build time.
GET
/actuator/loggers
List log levels — change them at runtime
GET /actuator/loggers/com.example.service { "configuredLevel": "INFO", "effectiveLevel": "INFO" } --- Change a log level at runtime (no restart needed) --- POST /actuator/loggers/com.example.service Content-Type: application/json { "configuredLevel": "DEBUG" }
Huge operational win: bump a specific logger to DEBUG in production for 10 minutes to diagnose an issue, then reset to INFO — zero restarts, zero downtime. Requires management.endpoints.web.exposure.include: loggers.
GET
/actuator/env
Active properties and their sources
HTTP/1.1 200 OK { "activeProfiles": ["prod"], "propertySources": [ { "name": "Config resource 'application-prod.yml'", "properties": { "spring.datasource.url": { "value": "jdbc:postgresql://prod-db:5432/mydb", "origin": "URL [file:./application-prod.yml]:3:9" } } } ] }
Shows the effective configuration and which file each property came from. Essential for debugging "why is my app using the wrong config?" mysteries.

Sensitive properties are automatically masked (password, secret, key, token).
POST
/actuator/shutdown
Gracefully shut down the application
HTTP/1.1 200 OK { "message": "Shutting down, bye..." }
Disabled by default for safety. Enable only if needed: management.endpoint.shutdown.enabled: true

Always secure the management port with Spring Security or place it behind an internal network — these endpoints reveal sensitive operational details and (in the case of shutdown) can kill your app.
