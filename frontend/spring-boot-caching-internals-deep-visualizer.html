Caching Internals

@Cacheable looks like a one-line speedup, but underneath it's a proxy doing cache-aside: check a store by a generated key, return the hit, or run your method on a miss and store the result. Knowing the key rules, the @CachePut/@CacheEvict companions, and the (familiar) proxy gotcha is the difference between a cache that helps and one that serves stale data.

How does @Cacheable actually work — and what are the three ways it silently fails?

@Cacheable("users") on a method tells Spring: before running the method, check the cache named "users" for a value stored under a key derived from the method arguments. If there's a hit, return the cached value — the method body never runs. If there's a miss, run the method body, store the return value in the cache under that key, then return it. This is the cache-aside pattern. Spring implements it via an AOP proxy — the same mechanism as @Transactional and @Async. And it has the same proxy gotcha: if you call a @Cacheable method from within the same class, you bypass the proxy and the caching never happens. The three common failures: self-invocation, wrong key expression, and forgetting to evict the cache after an update.

Key generation

Default: Spring uses all method parameters as the key. @Cacheable("users") User getUser(Long id) → key is id. @Cacheable("users") List<User> getUsersByRole(String role, boolean active) → key is SimpleKey[role, active]. Custom key: @Cacheable(value="users", key="#id") or key="#user.id". Condition: condition="#id > 0" — only cache for positive IDs. Unless: unless="#result == null" — don't cache null results.

@CachePut and @CacheEvict

@CachePut("users") — always runs the method AND updates the cache. Use on update methods: @CachePut(value="users", key="#user.id") User updateUser(User user). After update, the cache has fresh data. @CacheEvict("users") — deletes a cache entry. On delete: @CacheEvict(value="users", key="#id") void deleteUser(Long id). allEntries=true — clear the entire "users" cache (use after bulk operations).

The stale data trap

Forgot @CacheEvict on the delete endpoint. User deleted from DB. getUser(42) still returns the deleted user from cache. Client is confused. Fix: pair every mutating operation with cache eviction. Or set a short TTL: @Bean CacheManager cacheManager() { RedisCacheConfiguration cfg = RedisCacheConfiguration.defaultCacheConfig().entryTtl(Duration.ofMinutes(5)); ... }. TTL is a safety net, not a substitute for explicit eviction.

In CIAM: @Cacheable(value="user-roles", key="#userId") on Set<String> getUserRoles(Long userId) — role lookups are frequent and cheap to cache. @CacheEvict(value="user-roles", key="#userId") on updateUserRoles(Long userId, ...). Cache the JWKS (public keys for JWT validation) — it's fetched from Ping/Entra on every token validation. @Cacheable(value="jwks") with 10-minute TTL prevents hammering the IDP's JWKS endpoint. Self-invocation gotcha: if getRoles() and updateRoles() are in the same service class and updateRoles calls getRoles internally — the eviction and re-fetch bypass the proxy.

1. What @Cacheable does — cache-aside, via a proxy

The annotation

@EnableCaching            // turn it on (once)
@Configuration class CacheConfig {}

@Service
class UserService {
  @Cacheable("users")              // cache name
  public User getUser(Long id) {
    // only runs on a MISS (the "slow" part)
    return repo.findById(id).orElseThrow();
  }
}

What the proxy does on each call

call→ proxy→ key in cache?
  • Hit: return the stored value — your method never runs.
  • Miss: run the method, store the result under the key, return it.

This is "cache-aside" (lazy population). Because it's a proxy, the same rule as @Transactional/@Async holds: it only engages on calls through the bean, never on self-invocation.

3. The three core annotations

AnnotationRuns the method?Effect on the cacheUse for
@Cacheableonly on a missstores the result; serves it on later callsexpensive reads
@CachePutalwaysruns, then overwrites the entry with the new resultupdates that should refresh the cache
@CacheEvictalways (by default)removes the key (or allEntries=true clears the cache)deletes / invalidation

Don't put @Cacheable on a method that mutates — it won't run on a hit, so your write silently disappears. Reads = @Cacheable; writes = @CachePut or @CacheEvict.

4. How the key is generated

Default: SimpleKeyGenerator

  • No args → SimpleKey.EMPTY (one shared entry).
  • One arg → the arg itself is the key (our id).
  • Many args → a SimpleKey(arg1, arg2, …).

⚠️ Keys must have correct equals/hashCode. Two args that collide, or a mutable key, will cross-serve or never hit.

Take control with SpEL

@Cacheable(value="users", key="#id")
@Cacheable(value="users", key="#user.id")
@Cacheable(value="users",
   key="#root.methodName + ':' + #id")

// only cache some calls / some results
@Cacheable(value="users",
   condition="#id > 0",        // before (on args)
   unless="#result == null")   // after (on result)

Or supply a keyGenerator bean for a project-wide strategy.

5. Two traps: self-invocation & the cache stampede

Self-invocation (yet again)

@Service class UserService {
  public User load(Long id){
    return getUser(id);  // ⛔ "this" — proxy skipped
  }
  @Cacheable("users") public User getUser(Long id){…}
}

The internal call bypasses the proxy → no caching at all. Call through an injected reference instead.

↪ Same proxy rule as the @Async and Transactions deep-dives.

Stampede → sync = true

@Cacheable(value="users", sync=true)
public User getUser(Long id){…}

On a cold key, many concurrent requests all miss at once and all run the expensive method — a "cache stampede". sync=true lets one thread compute while the others wait for that result.

Trade-off: sync serializes that key and can't combine with unless/multiple caches.

6. The provider abstraction & TTL

Your annotations target Spring's CacheManager/Cache SPI — the actual store is pluggable. Crucially, @Cacheable has no TTL or size attribute; expiry and eviction are configured on the provider.

ProviderGood forTTL / eviction
ConcurrentMapCacheManagerthe default / dev — a plain Mapnone — grows unbounded, no TTL
Caffeinefast in-process (single app)expireAfterWrite, maximumSize
Redisshared across instances (distributed)entryTtl(...) per cache
 
# Caffeine via properties
spring.cache.type: caffeine
spring.cache.caffeine.spec: maximumSize=10000,expireAfterWrite=5m

So "my cache never expires" is almost always the ConcurrentMapCacheManager default — switch to Caffeine or Redis the moment you need TTL or bounded size.

7. One-sentence recap

🗃️ @Cacheable (with @EnableCaching) is a proxy doing cache-aside — return the value for the generated key on a hit, run the method and store it on a miss — paired with @CachePut (always run, refresh) and @CacheEvict (invalidate); keys come from the args via SimpleKeyGenerator or your SpEL key=, self-invocation bypasses it (same proxy rule), sync=true guards against stampedes, and TTL/size live on the provider (Caffeine/Redis), not the annotation.
