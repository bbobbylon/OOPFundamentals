Angular Lazy Loading, Preloading & @defer

Cut initial bundle size with route-level lazy loading, intelligent preloading strategies, and the @defer block for template-level deferral.

📦 What is lazy loading — and why does it matter for startup time?

By default Angular bundles every component, pipe, and service into one JavaScript file the browser must download, parse, and run before anything shows — in a big CIAM app that can be 2–5 MB. Lazy loading splits it into chunks, one per route or feature: visit /login and only the login chunk loads; the admin module's 500 KB only downloads when someone navigates to /admin. The payoff is a 70–90% smaller initial download, much faster first paint, and better Core Web Vitals.

  • Lazy-load a single standalone component with loadComponent, or a whole feature's routes with loadChildren.
  • The CLI automatically emits each lazy route as its own chunk at build time — no manual config.
  • Preloading fills the gap: fetch likely-next chunks in the background after first paint (PreloadAllModules, Quicklink, or a custom strategy).
  • @defer blocks do the same idea at the template level — lazy-load a heavy widget on viewport/interaction.
  • Analyze chunks (--stats-json + a bundle analyzer) to catch a library bundled into several chunks instead of the shared one.

Route-level lazy loading

{ path: 'admin', loadComponent: () => import('./admin/admin.component').then(m => m.AdminComponent) }, or loadChildren: () => import('./admin/routes').then(m => m.ADMIN_ROUTES) for a feature. Each becomes its own chunk.

Preloading strategies

PreloadAllModules loads all lazy chunks after first paint; NoPreloading (default) is on-demand only; Quicklink preloads routes whose links are in view; or implement PreloadingStrategy with a per-route data: { preload: true } flag.

Bundle analysis

ng build --stats-json then webpack-bundle-analyzer / source-map-explorer. Typical finds: a date lib pulled into 3 chunks (move to root), a full icon set in the admin chunk (tree-shake), Material duplicated (put it in the shared bundle).

In CIAM:loadComponent(() => import('./login')) (small, fast), loadChildren(() => import('./user-management/routes')) (list/detail/create), loadChildren(() => import('./admin/routes')) (heavy audit log + charts only ~5% of users see). With Quicklink, once the user logs in the user-management chunk preloads silently in the background.

The problem

You did not delete the work. You moved it — and you can move it to a worse moment.

"Split everything. Smaller main.js is always better."

So you loadComponent the login page too. The build log is beautiful: main.js drops from 212 KB to 190 KB. Then a support ticket arrives from someone on 4G saying the login form takes longer to appear than it used to. It does. You inserted a second network round trip into the one page 100% of your users see first, and that round trip cannot even start until main.js has finished parsing and bootstrapping.

main.js −22 KB 🎉 +1 serial round trip ⚠ 4G RTT ≈ 300 ms ⚠ 100% of sessions pay it ⚠ saved 22 KB · cost 340 ms ⚠

You optimised the number in the build output. The number the user feels went up.

Split by who needs it and when, never by what looks big
eager: the shell + the route the user lands on ↓ because 100% of sessions need it, so a round trip here is pure added latency lazy: the routes a minority ever reach ↓ because 95% of users should not download the audit dashboard to log in preloaded: the lazy routes the majority reach next ↓ because the fetch happens while they're typing a password, not after they click @defer: heavy widgets inside a page — charts, editors, QR generators
Lazy loading does not make your app faster. It makes the first paint faster by rescheduling work. Total bytes barely move. The only question worth asking about a chunk is when does this user need it — never how big is it.

The mechanism

Seven steps, strictly in order, and nothing renders until the last one.

  1. User clicks the link — the router matches { path: 'admin', loadChildren: … }still zero network activity
  2. The arrow function finally runs: import('./admin/admin.routes')this is the moment the fetch is born
  3. GET /chunk-admin.a1b2c3.jsthe round trip you bought — ~40 ms on a warm desktop, ~300 ms on cold 4G
  4. The browser parses, compiles and evaluates the chunk on the main threada big chunk costs CPU here too, not just bandwidth
  5. canActivate runs — it lives inside the chunk, so it could not have run any earliercanMatch is the guard that runs BEFORE the fetch
  6. Resolvers settle, then AdminDashboardComponent is constructedfirst pixels are still not on screen
  7. …and ngOnInit fires its first API callround trip number two, and this one you always had

Steps 2 through 4 are the bill for lazy loading, and they are serial — the fetch cannot begin until the router evaluates the route, and the router does not exist until main.js has booted. Nobody notices that chain on a route reached at second 30 of a session. Put it on the landing route and every session in your product got slower to save a rounding error in a build log.

The fix is not "stop splitting" — it is "split, then prefetch". Preloading keeps the small first paint and buys back the instant navigation: after the initial navigation settles, the router quietly fetches lazy chunks at low priority while the user is reading, typing, or doing nothing at all. PreloadAllModules fetches every one of them; a custom PreloadingStrategy reading data.preload fetches only the routes you know come next; Quicklink fetches only the ones whose links are on screen. Same bytes, radically different clock. The one thing preloading can never do is win a race against the route the user is already navigating to — which is exactly why the landing route stays eager.

Your CIAM app's /login route is loadComponent-ed, main.js is down to 190 KB, and Lighthouse adores you. Real users on 4G report the login form now takes longer to appear than it did before the split. What actually happened?

Chunk size isn't the cost here; the round trip is. A 22 KB chunk and a 220 KB chunk over the same cold 4G connection differ by a few dozen milliseconds — connection setup plus the request/response cycle spent the other 300. And "merge it back" via a bundler knob is the right instinct pointed at the wrong dial: just make the route eager.

Right. import() does not run until the router evaluates the route, and the router does not run until main.js has parsed and bootstrapped. You turned one download into two sequential downloads on the critical path — and unlike /admin, everybody logs in, so nobody escapes the bill.

Tempting, and it's the fix for the route after this one. But preloading starts after the initial navigation completes — it exists to fetch routes you haven't gone to yet. It can never beat a navigation already in flight. Make /login eager and preload /dashboard instead.

Questions from the back row

If PreloadAllModules downloads everything anyway, what did splitting actually buy me?

Order and priority. The same bytes arrive, but after the app is interactive and at low priority — the user is already typing into the login form while the admin chunk trickles in behind them. Time-to-interactive is set by what blocks the first paint, not by total transfer. And the user who logs out after 30 seconds never paid for the chunks that hadn't arrived yet.

Should I @defer everything below the fold?

No. Every @defer block buys you a placeholder, a loading state, a possible layout shift and a network request. Below-the-fold markup costs almost nothing to render and gains nothing from deferral. Defer things with a library behind them — a chart, a rich-text editor, a map, a QR generator. If the deferred thing is 4 KB of your own HTML, you added machinery and latency to save nothing.

My lazy route works locally and throws ChunkLoadError in production. Why?

Almost always a deploy that happened while a user had the old index.html open. Their tab still asks for chunk-admin.a1b2c3.js; the new build hashed it to something else and the CDN 404s. Handle it on both ends: an @error block for @defer, a router error handler that reloads the page on ChunkLoadError, and keep the previous build's chunks live for a release or two.

1. Why Lazy Loading Matters

Every byte of JavaScript the browser downloads must be parsed and compiled before your app is interactive. Lazy loading splits your app into chunks — the browser only downloads what the current page actually needs.

Eager (no lazy)

All code in one main.js. User visiting the login page downloads admin panel, user dashboard, analytics, and settings code they'll never see.

1.4 MB
initial bundle (gzipped)

Route Lazy Loading

Each route is a separate chunk. Login page only downloads main.js + login chunk. Admin downloads lazily when the user navigates there.

Lazy + @defer

Routes lazy load AND heavy widgets within pages defer until needed. Chart library only loads when the charts section enters the viewport.

2. Route-Level Lazy Loading

loadChildren() — Feature Routes File

// app.routes.ts
export const routes: Routes = [
  { path: '', component: HomeComponent },

  // Lazy feature — downloads admin.chunk.js
  // only when user navigates to /admin
  {
    path: 'admin',
    loadChildren: () =>  // the arrow function is what makes it LAZY — nothing runs until the router needs it
      import('./admin/admin.routes')
        .then(r => r.ADMIN_ROUTES)
  },

  // With route-level providers
  {
    path: 'store',
    loadChildren: () =>
      import('./store/store.routes')
        .then(r => r.STORE_ROUTES),
    providers: [CartService]  // scoped to store
  }
];

loadComponent() — Single Component

// For standalone components — no routes file needed
const routes: Routes = [
  {
    path: 'profile',
    loadComponent: () =>  // loads ONE component directly — skips the whole-module indirection loadChildren needs
      import('./profile/profile.component')
        .then(c => c.ProfileComponent)  // the import resolves to a MODULE object — pick the named export off it
  },
  {
    path: 'settings',
    loadComponent: () =>  // same pattern — each route gets its own separately-downloaded chunk
      import('./settings/settings.component')
        .then(c => c.SettingsComponent)
  }
];

// Even shorter — if default export:
{
  path: 'about',
  loadComponent: () => import('./about.component')  // no .then needed — the default export IS what loadComponent expects
}

3. Preloading Strategies

Preloading downloads lazy chunks in the background after the initial page is interactive. The user already has the chunk cached when they navigate — feels instant.

StrategyBehaviorBest For
NoPreloadingNever preload — chunks download on demandData-saver users, low-bandwidth sites
PreloadAllModulesEagerly preload every lazy chunk after bootstrapSmall apps where all routes likely to be visited
Custom strategyPreload only routes with data.preload: trueLarge apps — preload critical paths only
QuicklinkStrategyPreload routes whose links are visible on screenApps with heavy navigation menus

Built-in: PreloadAllModules

import { PreloadAllModules } from '@angular/router';

provideRouter(routes,
  withPreloading(PreloadAllModules)
)

Custom Preloading Strategy

@Injectable({ providedIn: 'root' })
export class SelectivePreloadStrategy
  implements PreloadingStrategy {  // the router calls preload() on this class for EVERY lazy route, one at a time

  preload(route: Route,  // route is the CONFIG object — its "data.preload" flag is read below
          load: () => Observable<any>
  ): Observable<any> {
    return route.data?.['preload']
      ? load()  // calling load() actually triggers the download; EMPTY means "skip it"
      : EMPTY;
  }
}

// Mark critical routes:
{ path: 'dashboard', data: { preload: true },
  loadChildren: ... }

4. @defer Block — Template-Level Deferral

@defer is a template syntax for lazy loading a chunk of UI. It uses IntersectionObserver, IdleCallback, and other browser APIs natively — no manual setup needed.

Anatomy of a @defer Block

@defer (on viewport) {
  <!-- Heavy chart component — only downloaded when scrolled into view -->
  <app-analytics-chart [data]="chartData" />
}
@placeholder {
  <!-- Shown immediately, before the deferred content loads -->
  <div class="chart-skeleton"></div>
}
@loading (minimum 300ms; after 100ms) {
  <!-- Shown while the JS chunk is downloading -->
  <!-- minimum: show for at least 300ms (prevents flash) -->
  <!-- after: only show if loading takes longer than 100ms -->
  <app-spinner />
}
@error {
  <!-- Shown if the chunk fails to download -->
  <p>Failed to load chart.</p>
}

All Trigger Types

on idle

Load when browser has no pending work. Uses requestIdleCallback.

on viewport

Load when element enters the visible viewport. Uses IntersectionObserver.

on interaction

Load on first click or focus event on the placeholder.

on hover

Load when the user hovers over the placeholder element.

on timer(2000)

Load after a fixed delay (ms). Simple time-based approach.

when condition

Load when an expression/signal becomes truthy. Most flexible.

Select a trigger above to see how @defer responds to it.

Prefetch vs Defer

// @defer with prefetch — downloads the JS early, renders later
@defer (on viewport; prefetch on idle) {
  <app-heavy-widget />
}
// prefetch on idle: JS chunk downloads when browser is idle
// on viewport: component is RENDERED only when scrolled into view
// The chunk is already in cache, so render is instantaneous
