The gcloud CLI

or, the third dialect of the same sentence — and the one login everybody forgets

>_

You already read the AWS and Azure pages. Google's CLI speaks the same group → verb grammar, so most of it is free. So why does everyone's first day with gcloud end in "Could not automatically determine credentials"?

The idea

Same sentence, third dialect — plus a context you switch by name.

gcloud organizes Google Cloud exactly the way az organizes Azure: a group (what kind of thing), sometimes a subgroup, then a verb. gcloud run deploy, gcloud secrets versions access, gcloud iam service-accounts create. If you can read one, you can read all three clouds. What makes gcloud its own lesson is the two places it deliberately diverges: it keeps named configurations — a whole context (account + project + region) you switch by name — and it makes you log in twice, once for you and once for your code.

You

gcloud config list

gcloud

account = bobby@example.com, project = devhub-prod, region = us-central1. Your active configuration is: [work]. Type carefully.

Two logins, not one.

Say it before you read another line, because it is the single most common way a perfectly-configured machine still refuses to run your app. gcloud auth login gets credentials for you — the human typing commands. gcloud auth application-default login gets credentials for your code — the Java or Node client library running on the same laptop. They are two different files. Doing the first and expecting the second to work is the rite of passage.

Motivation

Why learn a third CLI when you already know two?

01
Two thirds is already free

Group → verb → flags is identical to az. What you actually have to learn is the delta, and this page is only the delta.

02
Configurations beat profiles

AWS switches a key file. Azure switches a subscription. gcloud switches account and project and region in one named move — the cleanest client-hopping story of the three.

03
Identity is the whole product

IAM bindings, service accounts, OIDC tokens, workload-identity federation — your CIAM day job, expressed as one-liners you can put in a pipeline.

04
Interviews ask for all three

"Have you worked multi-cloud?" is much easier to answer honestly once you can compare --query, --filter and --format from memory.

Anatomy of a gcloud command

Click each part — the differences from az hide in the last two.

the program

gcloud fronts nearly all of Google Cloud, and it holds a login session (tokens under ~/.config/gcloud) rather than a static key file — the same model as az, not AWS's keys-in-a-file. Two siblings survive for historical reasons: bq for BigQuery and kubectl for Kubernetes. gsutil is the one that got absorbed — storage is gcloud storage now.

the group

run is the kind of thing you're acting on. Groups nest just like Azure's: gcloud iam service-accounts, gcloud secrets versions, gcloud compute instances. Every level answers --help with what lives inside it, so you can explore the whole product from the terminal.

the verb

create, list, describe, delete, update. Note describe, not show — that one word is the most common muscle-memory slip when you move over from az. Same idea: describe is one item in full, list is all of them.

the name — positional

devhub-api just sits there with no flag in front of it. Azure wants --name devhub-api; gcloud takes the name positionally in most commands. Small thing, constant papercut, worth naming out loud once so you stop re-typing --name.

the project

The project is Google's container for everything: it is the billing boundary and the IAM boundary and the resource folder, all at once. (Azure splits those across subscription + tenant + resource group.) Almost every command needs one, so you usually set it once — gcloud config set project devhub-prod — and stop typing the flag.

Check the context before you touch anything

Deploying to the wrong project is the gcloud equivalent of pushing to the wrong remote. config list prints all of it, including which named configuration is answering.

Deploy the folder you're standing in

No Dockerfile needed — buildpacks detect the language, build a container, push it, and start a service. --format trims the wall of output down to the one line you wanted.

$ gcloud run deploy devhub-api --source . --region us-central1
Building using Buildpacks and deploying container to Cloud Run service [devhub-api]

Service [devhub-api] revision [devhub-api-00001-xkq] has been deployed
and is serving 100 percent of traffic.

It's private by default — so prove who you are

A plain curl gets a 403, because you never passed --allow-unauthenticated. The fix isn't a password: it's an ID token, minted from the credentials you already have.

$ curl -s -o /dev/null -w '%{http_code}\n' https://devhub-api-83f1kd9m-uc.a.run.app
403

$ curl -H "Authorization: Bearer $(gcloud auth print-identity-token)" \
       https://devhub-api-83f1kd9m-uc.a.run.app
{"status":"UP","service":"devhub-api"}
Give the deploy bot one role, then prove it only has one

Granting is easy and everybody does it. Auditing is the part that gets skipped — and it's one command, so there's no excuse.

$ gcloud projects add-iam-policy-binding devhub-prod \
    --member="serviceAccount:deploy-bot@devhub-prod.iam.gserviceaccount.com" \
    --role="roles/run.admin"
Updated IAM policy for project [devhub-prod].

$ gcloud projects get-iam-policy devhub-prod \
    --flatten="bindings[].members" \
    --filter="bindings.members:deploy-bot@devhub-prod.iam.gserviceaccount.com" \
    --format="table(bindings.role)"
ROLE
roles/run.admin
In your CIAM job, this page is the job: a service account is just a non-human principal, an IAM binding is just a grant, and gcloud auth print-identity-token hands you the same kind of OIDC ID token your Spring Security resource server validates every day. The one worth internalising: an access token answers "what may I do", an ID token answers "who am I". Google gives you a command for each — print-access-token and print-identity-token — which makes the distinction concrete in a way no diagram quite manages.
There are no dumb questions

Two logins really is the design? That feels like a bug.

It's deliberate, and once you see why it's hard to unsee. Your code shouldn't behave differently depending on whether a human happens to be logged into a CLI on the same machine — it should look for credentials in one well-known place and find the same shape of thing everywhere it runs. That place is ADC (Application Default Credentials), and libraries search it in a fixed order: GOOGLE_APPLICATION_CREDENTIALS if set → the file written by gcloud auth application-default login → the metadata server, when running on Google Cloud. That last hop is the payoff: deployed on Cloud Run, your code gets the service account's credentials automatically and the ADC file is never involved. Same code, no branch, no key.

Project, folder, organization — which one am I "in"?

The project, essentially always. It's the unit that holds resources, collects the bill, and carries the IAM policy — Azure splits those three jobs across a subscription, a resource group, and a tenant, while Google fuses them. Folders and the organization sit above it purely so policy can be inherited downward, which is why a permission you can't find in the project may have been granted three levels up. Watch the ID: devhub-prod is the globally-unique project ID that commands take; the numeric project number and the human-friendly display name are different things and they're the reason half of all "project not found" errors happen.

Is --format the same as the --query I learned for AWS?

No — and this is the trap, because AWS and Azure are the same as each other. Both of those use JMESPath, so --query is one skill for two clouds. Google went its own way with two separate flags: --format shapes the output (--format=json, --format="table(name, status)", --format="value(status.url)") and --filter chooses the rows (--filter="status:ACTIVE"). The split is arguably cleaner than cramming both into one expression — but pasting a JMESPath string into gcloud will only ever produce a syntax error. Memory hook: two clouds query, the third one formats and filters.
