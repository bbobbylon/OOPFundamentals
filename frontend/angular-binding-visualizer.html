Data Binding — the 4 flavors

Binding is how the component class and the template stay in sync. Four syntaxes, three directions of data flow. Memorize the punctuation and you've got 90% of Angular templates figured out.

🔗 What is data binding? How do the class and template talk?

Your component class has a property — username = 'Alice' — and your template has an element that should show it. Data binding is Angular's mechanism for keeping the two in sync automatically: change the property and the DOM updates; the user types or clicks and your class hears about it. Without it you'd be hand-writing element.textContent = this.username on every change. The punctuation around a binding tells you which direction the data flows.

  • Interpolation {{ value }} — class → template, rendered as text. It's just shorthand for property-binding to textContent.
  • Property binding [src]="url" — class → a DOM property or a component @Input (any type, not only strings).
  • Event binding (click)="save()" — template → class; a DOM event (or an @Output) calls your method.
  • Two-way [(ngModel)]="x" — the "banana in a box" — is exactly [ngModel] + (ngModelChange) combined.
  • Bindings re-evaluate during change detection, so the view always reflects current class state — no manual DOM poking, no getElementById.

The 4 binding syntaxes

  • {{ value }} — class → template (text)
  • [property]="expr" — class → DOM/input
  • (event)="fn()" — DOM/output → class
  • [(ngModel)]="prop" — two-way

Bracket trick: [ ] in, ( ) out

[src]="imgUrl" — data flows IN to the DOM property. (click)="save()" — an event comes OUT to the class. [(value)]="x" — both at once: [value] + (valueChange). Square = input, round = output, banana-in-a-box = both.

In CIAM / Angular forms:[disabled]="!form.valid" gates the login button until the form is valid, (submit)="onLogin()" fires the OIDC flow, {{ user.displayName }} shows who's signed in, and [class.active]="isSelected" drives conditional CSS.

Square brackets IN. Round brackets OUT. Banana-in-a-box: both.

Read [(ngModel)] out loud as "banana in a box" — that's the official Angular nickname. If you can see the 🍌 in a 📦, you can never forget which syntax is two-way binding.

The problem

The HTML says value="Alice". The input says "Bobby". Both are correct.

Attributes and properties share a name and are not the same thing

An HTML attribute is what you wrote in the markup — it is the initial value, and it never changes on its own. A DOM property is live state on the JavaScript object. Type in the box and input.value updates while the attribute still reads "Alice" forever. Angular binds to the property, which is why inspecting the HTML in devtools can show you something that has not been true for ten minutes.

devtools shows value="Alice" ⚠ the field shows "Bobby" ⚠ neither is a bug ⚠ [attr.x] and [x] differ ⚠

Half an hour goes into debugging a discrepancy that is just two different things wearing one name.

Bind to the property; reach for attr. only when there isn't one
[disabled]="!form.valid" — a DOM property, live, re-evaluated ↓ this is what you want almost always [attr.colspan]="n" — for things with NO matching property ↓ colspan, aria-*, data-*, and most SVG attributes disabled="{{ x }}" — an attribute holding a string. Rarely what you meant
Angular binds to DOM properties, not HTML attributes. The markup you typed set an initial value; the property is the living one. When a binding "does nothing", the first question is whether the thing you named is a property at all.

disabled="{{ isBusy }}" should disable the button when isBusy is false. It never re-enables.

The browser

You set the attribute to the string "false". For boolean attributes like disabled, my rule is presence, not value — a non-empty string means disabled. The word "false" disables it just as firmly as "true".

Angular

Write [disabled]="isBusy" instead and I set the property to the actual boolean. Square brackets mean "evaluate this as an expression", not "interpolate it into a string".

The mechanism

What one property binding does on every change detection pass.

  1. Angular evaluates the expression inside [disabled]="!form.valid"every cycle, not once
  2. It compares the result to the value from the previous cycle — and does nothing if unchangedthis is the whole optimisation
  3. If it changed, it assigns to the DOM property: el.disabled = truea JS assignment, not markup
  4. The HTML attribute is never touched — which is why devtools still shows what you originally wrotethe discrepancy, explained
  5. [attr.x] takes the other path entirely: setAttribute, and null removes itthe escape hatch for attribute-only things

Step 1 is worth pausing on, because it is the cost nobody budgets for: a binding is a subscription, not an assignment. That expression is re-evaluated on every change detection cycle for the life of the component — so [title]="buildTooltip(user)" calls that function on every cycle, forever. Bind to a field or a computed() signal, not to a function call, unless the function is genuinely trivial.

And the direction mnemonic above is really a statement about who owns the value. [x] means the parent owns it and the child reads it. (x) means the child owns the event and the parent listens. [(x)] is not a third mechanism at all — it is pure sugar that expands to [x]="v" plus (xChange)="v = $event", which is exactly why the output must be named <input>Change for banana-in-a-box to work on your own component. There is no two-way binding in Angular; there is a one-way binding and an event, written together.

You write <button disabled="{{ isBusy }}"> and isBusy is false. What happens?

No coercion happens. Interpolation always produces a string, and the string "false" is perfectly non-empty. This is the assumption that makes the bug so hard to see when you are reading your own template.

It compiles cleanly — the syntax is legal, it just does something other than what you meant. Angular cannot know your intent, which is why this stays silent until someone notices the button never re-enables.

Right, and it is the browser's rule rather than Angular's: for a boolean attribute, presence disables. disabled="false", disabled="no" and disabled="" all disable. Use [disabled]="isBusy" so the actual boolean reaches the property.

Where you've seen this before

Three more places the same distinction bites.

[attr.aria-label], not [aria-label]

ARIA is attribute-only — there is no el.ariaLabel on older targets — so a plain property binding silently does nothing. The accessibility attribute you carefully added never reaches the DOM, and nothing warns you.

aria and data need attr.

[class.x] and [style.x]

Special-cased for the same reason: class and style are not plain properties you can assign a string to safely. The dedicated syntaxes let Angular merge with whatever else is writing to them.

merged, not overwritten

Questions from the back row

Why does $event sometimes have .target.value and sometimes not?

Because $event is whatever was emitted. On a native element it is the real DOM event, so the value lives at $event.target.value — and TypeScript will type target as EventTarget | null, which is why that line so often needs a cast. On your own component it is whatever you passed to emitter.emit(...), typed exactly as you declared it. Same syntax, two very different payloads.

What is NG0100 really telling me?

ExpressionChangedAfterItHasBeenCheckedError means a bound value changed after Angular checked it, within the same cycle — usually because a lifecycle hook or a getter mutated state during rendering. It is dev-mode only, and that is not leniency: in production the check does not run, so the screen would simply show the stale value with no warning at all. Treat it as a real bug being reported early, and fix the write rather than deferring it with setTimeout.

Do signal inputs change any of this?

The template syntax is identical — the parent still writes [count]="n" — but the child now declares count = input<number>(0) and reads this.count(). The gain is that reading it registers a dependency, so a computed() derived from it updates automatically and the component works under zoneless change detection. model() is the two-way version, and it generates the Change output for you, which removes the one naming rule people always forget.

// .ts

3. Event binding

(domEvent)="handler($event)"

Run a class method when the DOM fires an event. Direction: DOM → TS.

clicks: 0

<!-- expands to: -->

The most common gotchas

⚠️ Attribute vs property

HTML attributes initialize the DOM property. Once rendered, attribute and property can drift. [src] binds the PROPERTY (what the browser actually uses); writing src="{{url}}" binds the attribute. Always prefer [] for dynamic values.

⚠️ ngModel needs FormsModule

If [(ngModel)]="text" doesn't compile, you forgot to import FormsModule in your component's imports: []. Reactive forms use a different module entirely.

⚠️ Don't put logic in templates

Templates re-evaluate on every change-detection cycle. {{ heavyCompute() }} runs constantly. Compute in ngOnInit or use a computed() signal / memoized getter.

⚠️ The $event variable

Inside an event binding, $event is the DOM event (or the emitted value if it's a custom component event). Pass it: (click)="handle($event)". Without it, methods receive undefined.

Bonus: key modifiers — common shortcut

<!-- Run save() only when Enter is pressed -->
<input (keyup.enter)="save()">

<!-- Ctrl+S, Escape, etc -->
<textarea (keyup.control.s)="save()"></textarea>
<div (keydown.escape)="close()">...</div>

Beats reading $event.key === 'Enter' every time. Modifiers: .shift, .control, .alt, .meta (cmd/win key), .enter, .escape, .tab, .space.

Template reference variables — grab the DOM directly

<!-- #nameBox creates a reference to this input -->
<input #nameBox placeholder="your name">
<button (click)="greet(nameBox.value)">say hi</button>
<p>Length: {{ nameBox.value.length }}</p>

Useful for one-off "I just need this input's value when the user clicks save" — saves you wiring up [(ngModel)] and a class property. Reference variables can also point at a directive instance: #form="ngForm".

Mental model — when to reach for which

Display a value

Use {{ }} for text content. Use [prop] for anything else (src, href, disabled, value, etc).

React to user input

Use (event). Add $event if you need the event object.

Form input that the class also writes to

Use [(ngModel)] for template-driven simplicity, or pair [value]+(input) manually for full control.

One-off DOM access

Use #ref template variable. No class property needed.

🌱 Totally new? Binding is just "keep the screen and the data in sync."

Your component class holds data (a name, a count, whether a button's disabled). Your template is the HTML on screen. Binding is the wiring that keeps the two matching so you never write document.getElementById(...) by hand. There are four shapes, and the punctuation tells you the direction:

  • {{ name }} — interpolation. "Print this value here." Class → screen.
  • [disabled]="isBusy" — property binding (square brackets). "Set this element's property from the class." Class → screen. Think of [ ] as an arrow pointing into the element.
  • (click)="save()" — event binding (parentheses). "When this happens, call my method." Screen → class. The ( ) is a little catcher's mitt facing out.
  • [(ngModel)]="email" — two-way (the "banana in a box"). Both directions at once: type in the box and the class updates; change the class and the box updates.

That's the whole mental model: [ ] sends data in, ( ) listens for events out, {{ }} prints, [( )] does both. Everything else is detail.

Signal-based inputs — input(), output(), model() (Angular 17+)

Angular 17 introduced a new, signal-native way to declare inputs and outputs — no decorators needed. The classic decorator API still works, but new code should prefer the functional API.

input() — required and optional

// Optional input with default
export class PillComponent {
  label = input<string>('default');
  // label is a Signal<string>
  display = computed(() => this.label().toUpperCase());
}

// Required input — must be provided
userId = input.required<string>();
// userId(): string — always defined

// Aliased input
value = input<number>(0, { alias: 'count' });
// parent writes [count]="n" — class reads this.value()

output() and model() — two-way signals

// output() — replaces @Output + EventEmitter
export class ButtonComponent {
  clicked = output<string>();

  handleClick() {
    this.clicked.emit('clicked!');
  }
}

// model() — two-way bindable signal
// replaces @Input + @Output + xChange pattern
export class ToggleComponent {
  checked = model(false);
  // parent: [(checked)]="isOn"
  // inside: this.checked.set(!this.checked())
}
parent template
<app-pill [label]="'Angular'"></app-pill>
<app-toggle [(checked)]="isDarkMode"></app-toggle>
<app-button (clicked)="onClicked($event)"></app-button>
<!-- All three use the same [ ] / ( ) / [( )] syntax you already know -->

Key advantage: input() values are signals — you can computed() off them without ngOnChanges. No more "was my input updated?" ceremony.

The async pipe — subscribing directly in the template

The async pipe subscribes to an Observable (or Promise) and unwraps the latest value — and automatically unsubscribes when the component is destroyed. It is the safest way to consume RxJS streams in a template.

Basic usage

<!-- null until the first emission -->
<p>{{ users$ | async | json }}</p>

<!-- unwrap + iterate -->
<li *ngFor="let u of users$ | async">
  {{ u.name }}
</li>

The as alias — avoid double subscription

<!-- without as: users$ is subscribed TWICE -->
<div *ngIf="users$ | async">
  {{ (users$ | async)?.length }}
</div>

<!-- with as: one subscription, one value -->
<div *ngIf="users$ | async as users">
  <li *ngFor="let u of users">{{ u.name }}</li>
  Total: {{ users.length }}
</div>
Angular 17+ @if control flow
<!-- Modern equivalent — @if + async + as -->
@if (users$ | async; as users) {
  @for (u of users; track u.id) {
    <li>{{ u.name }}</li>
  }
}
<!-- no extra wrapper div needed -->

CIAM pattern: currentUser$ | async as user — bind the user object from your auth service into the template once, then access user.displayName, user.roles etc. without subscribing multiple times.

Host bindings — styling the component's own element

By default, a component's template is the content inside its element. Host bindings let the component bind properties and listen for events on its own root element — no wrapper div needed.

Decorator style (classic)

export class CardComponent {
  @HostBinding('class.highlighted')
  isHighlighted = false;

  @HostBinding('attr.role')
  role = 'article';

  @HostListener('click')
  onClick() {
    this.isHighlighted = !this.isHighlighted;
  }
}

host: {} metadata style (preferred)

@Component({
  selector: 'app-card',
  template: `...`,
  host: {
    // static attr
    'role': 'article',
    // dynamic class bound to a field
    '[class.highlighted]': 'isHighlighted',
    // event listener
    '(click)': 'onClick()',
    // bind aria attribute to a signal
    '[attr.aria-disabled]': 'disabled()',
  }
})

Why use it: A button component that is a <button> element (not a <div> that wraps one) uses host binding for [disabled] and [attr.type], getting real browser behavior (keyboard nav, form submit) for free. This is how Angular Material components are built.

🧠 Expert corner — attribute vs property, and how a binding actually re-runs

  • [prop] binds the DOM property, not the HTML attribute. Attributes are the initial string in the markup; properties are the live values on the DOM object. That's why [disabled]="false" correctly enables the control (boolean property) while the raw attribute disabled="false" would still disable it. When no property exists (ARIA, SVG, colspan), reach for [attr.aria-label], [class.active], [style.width.px].
  • A binding is an expression Angular re-evaluates during change detection. Each {{ }}/[ ] is checked when its component is checked; if the result differs from last time (by reference), the DOM is updated. This is why a [value]="getThing()" that returns a new object every call thrashes — and why a method call in a template runs on every CD pass.
  • Keep template expressions cheap and pure. No side effects, no heavy computation, no new objects each call. Precompute in the class (or a computed() signal); bind to the field. This is the single biggest template-perf lever before OnPush.
  • The dreaded ExpressionChangedAfterItHasBeenChecked error happens when a binding's value changes during the very CD pass that's reading it (often a parent reacting to a child's ngAfterViewInit). It's Angular protecting you from an inconsistent frame — see that diagnoser.
  • [(x)] is pure sugar. [(ngModel)]="email" desugars to [ngModel]="email" (ngModelChange)="email = $event". Any property x with a matching xChange output becomes two-way bindable — that's how model() signals expose two-way inputs.
  • CIAM tie-in. A login form binds [disabled]="form.invalid || submitting()" on the submit button and (ngSubmit)="login()" on the form; the username field is [(ngModel)] or a reactive control. The button's enabled state is derived from form validity — bind it, don't toggle it imperatively.
