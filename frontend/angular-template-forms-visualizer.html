Template-Driven Forms

How Angular's FormsModule turns plain HTML inputs into tracked, validated, stateful form fields — with nothing but directives and two-way binding.

📝 What are Template-Driven Forms? How do they differ from Reactive Forms?

Template-driven forms define the model in the HTML using directives like ngModel, ngForm, and validation attributes (required, minlength). Angular reads them and builds the FormGroup/FormControl structure for you behind the scenes; you interact through template reference variables (#form="ngForm") rather than class properties. The trade: less boilerplate for simple forms, but harder to test, no TypeScript type safety, and awkward async validators.

  • The form model lives in the template, built implicitly from ngModel — the opposite of Reactive Forms (model in the class).
  • [(ngModel)]="user.email" two-way-binds a field; Angular tracks it as an NgModel directive instance.
  • #form="ngForm" exposes the whole form — check form.valid/form.dirty, gate submit with [disabled]="!form.valid".
  • Great for simple, throwaway forms (search bars, login, settings); avoid for cross-field validation, dynamic arrays, or testable logic.
  • For anything complex (CIAM user management, bulk ops), reach for Reactive Forms and its explicit, typed model.

[(ngModel)] — two-way binding

[(ngModel)]="user.email" — the banana-in-a-box. [ngModel] is one-way in, (ngModelChange) is the output; together they're two-way. Angular tracks each field as an NgModel instance.

Template ref + ngForm

<form #myForm="ngForm" (ngSubmit)="onSubmit(myForm)"> gives you the form's NgForm instance — read myForm.valid/.dirty, or do [disabled]="!myForm.valid" on the submit button.

When to use template-driven

Simple search filters, login forms, quick settings — anywhere you don't need cross-field validation, dynamic field arrays, or unit-testable form logic. For anything complex, prefer Reactive Forms.

In CIAM:a simple user-list search bar — [(ngModel)]="searchTerm" with a (ngModelChange) that fires loadUsers(searchTerm) — is quick to wire up. But the real create-user form (roles, MFA, an async username-uniqueness validator that calls the API) should switch to Reactive Forms.

The problem

Your signup form greeted every visitor with three red errors before they typed a single character.

The validator is right. Showing it immediately is the bug

A required email field, and you show its error with *ngIf="email.invalid". It compiles, and it feels correct in your head — invalid should show an error, that's the whole point of a validator. Except the field renders invalid because it starts empty, so the message is sitting there the instant the page loads, aimed at a visitor who hasn't done anything wrong yet. The field's state genuinely is invalid — Angular isn't lying to you. Nobody thought to check whether "invalid" and "worth showing" are actually the same condition.

required validator working ✓ *ngIf="email.invalid" correctly wired ✓ field starts empty → starts invalid ⚠ invalid !== touched-by-the-user ⚠

Angular is faithfully reporting a fact you didn't ask a useful question about. "Is this control invalid" and "has this user done anything wrong yet" are two different questions, and the CSS classes give you both — you just reacted to the wrong one.

Gate the message on dirty || touched, not on invalid alone
*ngIf="email.invalid && (email.dirty || email.touched)" ↓ the message now appears only once the user has actually interacted with the field Better: style off Angular's own classes — .ng-invalid.ng-touched { border-color: red } ↓ CSS reads the exact state Angular already tracks; nothing to keep in sync by hand And a fresh form looks clean, exactly the way a fresh form should
Validity and blame are two different questions, and Angular tracks them separately on purpose. valid/invalid says whether the data is acceptable right now. pristine/dirty and untouched/touched say whether the user has done anything yet. That split is the entire reason ng-invalid alone is the wrong class to react to, why the standard pattern is always ng-invalid.ng-touched, and why a form can be simultaneously "invalid" and "showing no errors at all" — which is correct, not buggy.
Think of validity like a fire alarm, and touched like whether anyone's actually been in the building. Invalid means the alarm condition is true; touched means someone was present to have caused it. An empty required field on a fresh page is an alarm going off in an empty building — technically true, completely unhelpful to report.

So invalid on its own was never a "something's wrong, tell the user" signal. Only ever half of one. Pair it with dirty or touched and it becomes one.

The mechanism

Six classes, three pairs, and Angular flips exactly one pair per kind of event.

  1. On creation, NgModel starts every control ng-pristine and ng-untouched, and ng-valid or ng-invalid depending on the initial value against its validatorsday one, before any input
  2. A keystroke fires ng-dirty — permanently, for that control, until a programmatic reset — and re-runs every validator against the new valuedirty never reverts to pristine on its own
  3. Validators re-run synchronously on every value change and flip ng-valid/ng-invalid to matchthis pair can flip back and forth all day
  4. A blur event fires ng-touched — also permanent until reset — independent of whether the value changed at allyou can be touched and still pristine
  5. Angular writes all of this as literal class="…" attributes on the <input>, which is why plain CSS selectors like .ng-invalid.ng-touched work with zero JavaScriptno framework magic needed to style it
  6. #form="ngForm" aggregates every child control: the form is dirty if ANY control is dirty, touched if ANY control is touched, but valid only if EVERY control is validAND for valid, OR for the rest

Step 6 is the one people trip on. dirty and touched bubble up as OR — one changed field is enough to call the whole form dirty — but valid bubbles up as AND, because a form isn't submittable until every field agrees. Mixing those two aggregation rules up is exactly how a submit button ends up enabled, or stuck disabled, for a reason nobody can see in the template.

Pristine · Untouched type() → Dirty · Untouched  ·  blur() → Pristine · Touched
Dirty · Untouched blur() → Dirty · Touched
Pristine · Touched type() → Dirty · Touched
Dirty · Touched further typing/blurring → stays put  ·  form.reset() → every control back to Pristine · Untouched, at once

reset() is the only way back to the start — no amount of typing or blurring ever un-dirties or un-touches a control on its own, which is exactly why "Pristine · Touched" is a real, reachable state and not an edge case.

A required email field starts empty. The user clicks into it, types nothing, and clicks away without typing a single character. Which classes does Angular apply?

It's tempting because "the user did something" feels dirty-worthy — but Angular's dirty flag tracks the value, not the interaction. The value here never changed (it started empty and stayed empty), so dirty never fires. Only typing a character — even one, then deleting it — sets dirty.

Half right: pristine is correct, because the value genuinely never changed. But untouched is wrong — touched tracks focus-then-blur, completely independent of whether the value moved at all. Focusing in and blurring out is enough on its own to set it.

Exactly — and this is the combination beginners forget exists. Pristine + touched + invalid is a real, common state: the required field the user looked at, decided not to fill in yet, and moved past. It's why the standard error guard is dirty || touched, not dirty alone — touched alone gets you here too.

Where you've seen this before

Three places, the identical split between "wrong" and "worth mentioning."

HTML5's own :invalid and :user-invalid

Native browser validation ships almost the exact same split: :invalid fires the moment a required field is empty, while the newer :user-invalid pseudo-class only fires after the user has interacted with it — because browser vendors hit the identical "don't yell at a fresh page" problem years before Angular modeled it as ng-touched.

:invalid vs :user-invalid ≈ ng-invalid vs ng-touched

Reactive Forms' identical pair, different spelling

Reactive Forms track the exact same four states on every FormControl — pristine/dirty, untouched/touched — just read as control.touched in TypeScript instead of a CSS class in the template. Switch approaches and the mental model doesn't change at all; only where you read it does.

control.touched ≈ .ng-touched

Your CIAM registration form's MFA phone field

An optional MFA phone number, required only once "enable MFA" is checked — QA filed it as a bug because the field rendered red the instant the page loaded, before the checkbox was even touched. Same root cause: the error was gated on invalid instead of invalid && (dirty || touched). One condition, fixed in the same commit.

Questions from the back row

Why doesn't Angular just wait to mark a field invalid until it's touched?

Because invalid and touched answer different questions, and something downstream might need the honest one right away — a submit button's [disabled]="!form.valid" has to know the real validity the instant you land on the page, not a politely-delayed version of it, or you could submit a form that's actually still empty. Angular gives you both signals and trusts your template to combine them for display; collapsing them into one flag would make that honest use case impossible.

Does touched ever go back to false without calling reset()?

No — not on that control, not automatically. Focus-then-blur permanently flips a control to touched, exactly like a value change permanently flips it to dirty. The only built-in way back is markAsUntouched()/markAsPristine(), or the blunt instrument, form.reset(), which resets every control in the form at once. There's no "un-blur" operation.

Is #form="ngForm" the same object every change detection cycle?

Yes — it's a live reference to the same NgForm directive instance for the lifetime of the form, which is why [disabled]="!loginForm.valid" works without you ever calling markForCheck() yourself: you're reading a property off a stable object, and Angular's own change detection re-evaluates that binding on every tick like any other. The instance only changes if the <form> element itself is destroyed and recreated — inside an *ngIf toggling off and on, for instance.

Template-Driven vs Reactive Forms — when to use each

Angular ships two completely different approaches to forms. Pick one per form — you can mix across forms in the same app, but don't mix within a single form.

FactorTemplate-DrivenReactive
Setup complexityLow — just add FormsModuleMedium — must build FormGroup in class
Data flowTwo-way binding [(ngModel)]Explicit via patchValue / valueChanges
Validation logicHTML attributes in templateValidator functions in class
Unit testabilityHard (needs DOM / TestBed)Easy (pure TS, no DOM needed)
Dynamic fieldsVerbose — needs ngModelGroupEasy — FormArray
RxJS integrationManual subscriptionNative — valueChanges is an Observable
Best forSimple login / contact formsComplex, dynamic, or wizard forms
Angular versionAll versions (classic approach)Angular 2+ (preferred modern approach)
Rule of thumb: fewer than 5 fields with no conditional logic? Template-driven is faster. Any dynamic fields, cross-field validation, or unit tests? Go reactive.

Mental model — the core difference

Template-Driven: template is the source of truth

The form model is derived from the DOM. Angular reads your [(ngModel)] directives and builds an internal NgForm / NgModel automatically.

<!-- The template IS the model -->
<input [(ngModel)]="user.name"
       name="name"
       required
       minlength="2">

Reactive: class is the source of truth

The form model is built in the component class. The template binds to it. The model exists before the DOM does.

// The CLASS defines the model
form = new FormGroup({
  name: new FormControl('', [
    Validators.required,
    Validators.minLength(2)
  ])
});

Setup & ngModel two-way binding

1. Import FormsModule

// app.component.ts (standalone)
import { FormsModule } from '@angular/forms';

@Component({
  standalone: true,
  imports: [FormsModule],   // ← must import this
  template: `...`
})
Without FormsModule in imports, Angular ignores ngModel entirely — no error, just silent no-op. Always check imports first when ngModel doesn't work.

2. Two-way binding with [(ngModel)]

<!-- template -->
<input
  [(ngModel)]="username"
  name="username"    <!-- REQUIRED inside <form> -->
  placeholder="Enter username"
>
<p>Hello, {{ username }}!</p>
// component class
export class AppComponent {
  username = '';
  // No other code needed!
  // [(ngModel)] = [ngModel] + (ngModelChange)
  // = property binding + event binding
}

    Submit
  </button>

Submitting the form & reading its value

// component.ts
export class LoginComponent {
  formData = { email: '', password: '' };

  onSubmit(form: NgForm) {
    if (form.invalid) return;

    console.log('Form value:', form.value);
    // { email: 'user@example.com', password: 'abc12345' }

    console.log('Bound model:', this.formData);
    // Same thing — both are in sync via [(ngModel)]

    form.reset();  // clears values AND resets all state flags to pristine/untouched
  }
}

Advanced Patterns

1. Cross-field validation — custom validator directive

Template-driven forms can't access two fields simultaneously in a single validator. Wrap both fields in an ngModelGroup and apply a custom directive to the group.

// password-match.directive.ts
@Directive({
  selector: '[passwordMatch]',
  providers: [{
    provide: NG_VALIDATORS,
    useExisting: PasswordMatchDirective,
    multi: true
  }]
})
export class PasswordMatchDirective
    implements Validator {
  validate(group: AbstractControl) {
    const pw  = group.get('password');
    const cpw = group.get('confirm');
    return pw?.value !== cpw?.value
      ? { mismatch: true }
      : null;
  }
}
<!-- Template usage -->
<div ngModelGroup="passwords"
     passwordMatch
     #pwGroup="ngModelGroup">

  <input name="password"
         [(ngModel)]="pw"
         required>

  <input name="confirm"
         [(ngModel)]="cpw"
         required>

  <div *ngIf="pwGroup.errors?.['mismatch']">
    Passwords do not match
  </div>
</div>

2. Dynamic forms with *ngFor + ngModelGroup

// component.ts
addresses = [{ street: '', city: '' }];
addAddress() { this.addresses.push({ street: '', city: '' }); }

<!-- template -->
<div *ngFor="let addr of addresses; let i = index"
     ngModelGroup="address-{{ i }}">
  <input name="street" [(ngModel)]="addr.street" required>
  <input name="city"   [(ngModel)]="addr.city"   required>
</div>
<button (click)="addAddress()">+ Add address</button>
Note: dynamic forms get awkward quickly in template-driven mode — each dynamic group needs a unique ngModelGroup name built from index. For anything beyond 2–3 dynamic fields, switch to Reactive Forms with FormArray.

3. Select, checkbox & radio with ngModel

<!-- Select -->
<select name="role" [(ngModel)]="user.role">
  <option value="admin">Admin</option>
  <option value="editor">Editor</option>
</select>

<!-- Checkbox -->
<input type="checkbox" name="agree"
       [(ngModel)]="user.agreed">

<!-- Radio group -->
<input type="radio" name="size"
       value="small" [(ngModel)]="user.size"> Small
<input type="radio" name="size"
       value="large" [(ngModel)]="user.size"> Large

Same form — Template-Driven vs Reactive

A simple login form (email + password, required, email validator, submit) built both ways.

Template-Driven — component class

import { Component } from '@angular/core';
import { FormsModule, NgForm } from '@angular/forms';

@Component({
  standalone: true,
  imports: [FormsModule],
  templateUrl: './login.component.html'
})
export class LoginComponent {
  formData = { email: '', password: '' };

  onSubmit(f: NgForm) {
    if (f.invalid) return;
    console.log(f.value); // { email, password }
    f.reset();
  }
}

Reactive — component class

import { Component } from '@angular/core';
import { ReactiveFormsModule, FormGroup,
         FormControl, Validators } from '@angular/forms';

@Component({
  standalone: true,
  imports: [ReactiveFormsModule],
  templateUrl: './login.component.html'
})
export class LoginComponent {
  form = new FormGroup({
    email: new FormControl('',
      [Validators.required, Validators.email]),
    password: new FormControl('',
      [Validators.required, Validators.minLength(8)])
  });

  onSubmit() {
    if (this.form.invalid) return;
    console.log(this.form.value);
    this.form.reset();
  }
}

Verdict

Template-Driven wins for:

  • Quick forms (2–4 fields)
  • Prototyping
  • Developers who think in HTML
  • When you want the HTML to be self-documenting

Reactive wins for:

  • Dynamic field counts
  • Complex validation logic
  • Unit testing validators
  • Streaming valueChanges with RxJS

Both share:

  • Same CSS state classes
  • valid, invalid, errors API
  • reset() method
  • (ngSubmit) event
