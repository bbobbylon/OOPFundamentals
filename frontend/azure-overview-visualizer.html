Azure Overview — Subscriptions, Resource Groups & ARM

Every Azure resource lives inside a strict hierarchy — management group → subscription → resource group → resource — and every create/update/delete goes through one front door: Azure Resource Manager (ARM), which authenticates you with Entra ID, checks RBAC, and then routes to the right resource provider.

🌩️ What is the Azure resource model — and why does every action flow through ARM?

Azure organizes everything you deploy into a four-level hierarchy. At the top, management groups let an enterprise apply policy across many subscriptions. A subscription is the billing and quota boundary — resources inside it show up on that subscription's invoice. A resource group (RG) is a logical folder whose members share a lifecycle: delete the group and everything inside it is deleted too, which is why teams usually put one application environment (say, rg-shop-prod) in one group. Finally a resource is the actual thing — a web app, a storage account, a database. What makes Azure coherent is that every management operation, whether it comes from the portal, the az CLI, PowerShell, an SDK, or a CI/CD pipeline, hits the same REST front door: Azure Resource Manager. ARM authenticates the caller (the token comes from Microsoft Entra ID), evaluates role-based access control (do you hold a role like Contributor at this scope?), applies Azure Policy, and only then forwards the request to the resource provider (Microsoft.Web for App Service, Microsoft.Storage for storage…). That is the control plane. Reading a blob or querying a database is the data plane — it talks to the resource's own endpoint and is secured separately. Because ARM is declarative underneath, you can also hand it a whole desired state as a Bicep/ARM template and let it work out what to create, update, or leave alone — the same idempotent model as Terraform.

  • Hierarchy — management group → subscription (billing) → resource group (lifecycle) → resource.
  • One front door — portal, CLI, SDKs, and pipelines all call ARM's REST API; there is no side entrance.
  • Control vs data plane — ARM manages resources (create/configure/delete); the data plane is the resource's own endpoint (read a blob, query a DB).
  • RBAC at a scope — a role (Reader/Contributor/Owner or granular built-ins) is assigned at MG/sub/RG/resource scope and inherits downward.
  • Declarative option — Bicep/ARM templates describe the end state; ARM diffs and converges, so re-deploying is safe.

The CLI happy path

# login → get an Entra token az login # a folder for the app env az group create -n rg-shop-prod -l eastus2 # a resource inside it az storage account create \ -n stshopprod -g rg-shop-prod \ --sku Standard_LRS

AWS comparison

Subscription ≈ an AWS account (billing boundary). Management group ≈ AWS Organizations OU. Resource group has no exact AWS twin — tags + CloudFormation stacks come closest, but Azure RGs are mandatory and lifecycle-owning. ARM ≈ the AWS control plane APIs + CloudFormation in one; Bicep ≈ CloudFormation templates/CDK. Azure RBAC ≈ IAM policies, but role assignments attach to a scope in the hierarchy rather than to JSON policy documents.

Spring Boot comparison

ARM behaves like a well-designed REST backend you already know: one gateway, authentication first (Bearer token from Entra, exactly like your JwtDecoder), then authorization (RBAC evaluation ≈ @PreAuthorize at a scope), then routing to the right controller (resource provider). A 401 means the token failed; a 403 means the token was fine but no role assignment covers the action — the same two gates as Spring Security.

CIAM in production: Azure's control plane is itself a big OAuth2 resource server — az login runs an OIDC flow against Microsoft Entra ID and every ARM call carries Authorization: Bearer <access token> with audience https://management.azure.com. Your day-job pattern (Entra token → API validates → roles decide) is exactly how Azure manages itself. In CI/CD, prefer workload identity federation / managed identities over client secrets — the pipeline exchanges its own identity for an Entra token, so no credential ever sits in a variable. 1. The hierarchy: where a resource lives decides billing, policy, and access

# the four levels, top to bottom
Management Group contoso-root # policy umbrella across subscriptions
└─ Subscription shop-prod (billing + quotas)
   └─ Resource Group rg-shop-prod (one app env, one lifecycle)
      ├─ Microsoft.Web/sites shop-api # App Service
      ├─ Microsoft.Storage/storageAccounts stshopprod
      └─ Microsoft.DocumentDB/databaseAccounts cosmos-shop
Resource groups own lifecycle, not networking. A resource group is a logical container: its members can live in different regions, and resources in different groups can still talk to each other. What the group really gives you is a single unit for deploy together, secure together, delete together — one az group delete tears down the whole environment. That is also why mixing prod and dev resources in one group is the classic beginner mistake: RBAC scopes and deletes hit everything inside.

2. Control plane vs data plane — two doors, two tokens

# CONTROL PLANE — manage the resource (goes through ARM)
PUT https://management.azure.com/subscriptions/…/resourceGroups/rg-shop-prod/
    providers/Microsoft.Storage/storageAccounts/stshopprod?api-version=2023-01-01
Authorization: Bearer <token for audience management.azure.com>

# DATA PLANE — use the resource (talks to the resource endpoint)
GET https://stshopprod.blob.core.windows.net/invoices/2026-06.pdf
Authorization: Bearer <token for audience storage.azure.com> # or a SAS
Different audiences, different roles. Holding Contributor on a storage account lets you reconfigure it (control plane) but does not by itself let you read blobs — data-plane access needs a data role like Storage Blob Data Reader, a SAS, or an account key. AZ-204 loves this distinction, and it bites in real life: your app's managed identity can "own" the account yet still get 403 on GET /blob until a data role is assigned.

3. Declarative deployments: Bicep in, converged state out

// main.bicep — describe the END STATE, not the steps
param location string = resourceGroup().location

resource store 'Microsoft.Storage/storageAccounts@2023-01-01' = {
  name: 'stshopprod'
  location: location
  sku: { name: 'Standard_LRS' }
  kind: 'StorageV2'
  properties: { minimumTlsVersion: 'TLS1_2' }
}

# deploy it — safe to run twice (idempotent)
az deployment group create -g rg-shop-prod --template-file main.bicep
Idempotent by design. ARM compares the template against what exists: missing resources are created, drifted properties are updated, matching ones are untouched. Re-running a deployment is therefore a no-op, which is what makes templates safe in CI/CD. The default incremental mode never deletes extra resources; complete mode removes anything in the group that the template omits — powerful and dangerous. Bicep compiles to ARM JSON; it is the same engine Terraform's azurerm provider ultimately calls. See devops-iac-terraform-visualizer.html for the plan/apply mental model.
