Flask — Routing, Contexts & Blueprints

A microframework: Flask gives you routing, a request object, and templating — and gets out of the way. You add an ORM, validation, and auth as extensions. Small, explicit, and the easiest Python web framework to reason about end to end.

🍶 What is Flask — and what does "microframework" mean in practice?

Flask is a microframework: it ships a small, sharp core — URL routing (via Werkzeug), a request/response model, Jinja2 templating, and a development server — and deliberately leaves the rest to you. There is no built-in ORM, no admin, no forms layer; you compose those from extensions (Flask-SQLAlchemy, Flask-Migrate, Flask-Login). A view is just a function decorated with @app.route("/path") that returns a string, a tuple, or jsonify(...). Flask sits on WSGI (the Python web-server interface), and its cleverest idea is context locals: the global-looking request, g, and current_app objects are actually per-request/per-app proxies pushed onto a stack, so your code reads like it uses globals while staying correctly isolated per request. Larger apps are split into blueprints — reusable groups of routes mounted under a prefix. Flask is the framework to reach for when you want full control and minimal magic — the "Flask of Node" is Express, and the comparison is apt in both directions.

  • Microframework — routing + request + templating; everything else is an extension.
  • Views are functions — @app.route decorates a function that returns a response.
  • Context locals — request/g/current_app are per-request proxies, not real globals.
  • Blueprints split a big app into mountable, reusable route groups.

A whole app in a few lines

from flask import Flask, request, jsonify app = Flask(__name__) @app.route("/users/<int:id>") # dynamic converter def get_user(id): return jsonify({"id": id, "name": "Alice"}) @app.route("/users", methods=["POST"]) def create(): data = request.get_json() # parsed body return jsonify(data), 201 app.run(port=5000)

Hooks & a blueprint

# request lifecycle hooks @app.before_request def require_auth(): g.user = verify_jwt(request.headers.get("Authorization")) # a blueprint = a mountable group of routes bp = Blueprint("api", __name__, url_prefix="/api") @bp.route("/me") def me(): return jsonify(g.user) app.register_blueprint(bp) # mounts at /api/me

Spring Boot / Express comparison

Flask ≈ Express in Python: minimal, explicit, function/decorator routes. @app.route ≈ Express app.get ≈ Spring @GetMapping. before_request/after_request ≈ Express middleware ≈ a Servlet filter. Blueprints ≈ Express Router ≈ grouping under @RequestMapping("/api"). g (per-request scratch space) ≈ request attributes / SecurityContextHolder. Versus Spring Boot / Django, Flask gives you less out of the box on purpose — you wire SQLAlchemy, Marshmallow (validation), and Flask-Login yourself. More control, more assembly.

CIAM with Flask: A lean token-validating microservice fits Flask well. A @app.before_request hook reads the Authorization header, verifies the Ping/Entra RS256 JWT (via PyJWT + a JWKS client), and stashes the claims on g.user; each view reads g.user.roles and aborts with 403 if a role is missing (≈ @PreAuthorize). Because g is a per-request context local, there is no cross-request bleed even though it looks global. Blueprints keep the auth routes, the resource routes, and health checks cleanly separated.

1. Returning responses

# a view can return several shapes; Flask coerces them to a Response
return "<h1>Hello</h1>" # str → 200 text/html
return jsonify(user) # dict/list → JSON
return jsonify(user), 201 # (body, status)
return jsonify(err), 400, {"X-Trace": id} # (body, status, headers)
abort(404) # raise an HTTP error
Flask is explicit. There is no automatic body deserialization into a typed object or automatic validation — you call request.get_json() and validate yourself (or add Marshmallow/Pydantic). That is the microframework trade: less magic, total clarity about what happens. Compare Express's res.json() and Spring's automatic @RequestBody binding.

2. The application factory

# the recommended pattern: build the app inside a function
def create_app(config):
  app = Flask(__name__)
  app.config.from_object(config)
  db.init_app(app) # bind extensions
  app.register_blueprint(api_bp) # mount routes
  return app

The factory lets you create independent app instances (e.g. one per test) with different config — the Flask equivalent of Spring's profiles + a fresh ApplicationContext per test.

3. WSGI underneath

# Flask is a WSGI app; in production a WSGI server runs it
gunicorn "app:create_app()" --workers 4
# each worker is a process; concurrency = workers × threads.
