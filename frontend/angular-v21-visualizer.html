Angular 21

Everything new in Angular 21 — signals evolution, resource API, HMR, incremental hydration, and more

✨ What changed in Angular 21 — and is it worth upgrading?

Angular 21 continues the signals evolution. The headline is the stable resource() API — a signals-based way to declare async loading that replaces the common effect(() => fetchData(id())) pattern, with built-in isLoading()/error()/reload states you bind to directly. Style HMR is stable (edit a .scss and the browser updates instantly without losing component state), and incremental hydration lets SSR pages hydrate components on demand rather than all at once — a big Time-to-Interactive win.

  • resource() models async data as signals — auto-cancels the old request when its input signal changes (like switchMap, no pipe).
  • Bind to res.value(), res.isLoading(), res.error(); call res.reload() — no manual loading/error signals.
  • linkedSignal() is a writable signal that resets when a source changes — removes a class of effect() + set() code.
  • afterRenderEffect() runs after the DOM updates — safe for measurements (heights, scroll, canvas).
  • Incremental hydration + style HMR are quality-of-life wins for SSR apps and dev speed.

resource() API

userResource = resource({ request: () => ({ id: this.userId() }), loader: ({ request }) => this.userApi.getUser(request.id) }). Read value()/isLoading()/error(); reload(). When userId() changes it cancels the old request and starts a new one — switchMap without the RxJS pipe.

linkedSignal()

selectedUserId = linkedSignal(() => this.users()[0]?.id ?? null) — starts at the first user's id but can be overridden, and resets when users() changes. Replaces an effect() that watched the source and manually called set().

afterRenderEffect()

Like effect() but guaranteed to run after the DOM updated — safe to read measurements. afterRenderEffect(() => this.chart.resize(this.chartEl.nativeElement.clientWidth)). Replaces the timing-unsafe effect() DOM-poke.

In CIAM:resource() replaces the "load user on route-param change" pattern — userId = toSignal(route.paramMap.pipe(map(p => p.get('id')!))) + a resource() loader — and the template is @if (res.isLoading()) { … } @else if (res.error()) { … } @else { show user }. No manual loading/error signals, no switchMap, no subscriptions.

or, eight features that are all the same feature

The problem

Read a release note as a list and you memorise eight things. Read it as a story and you learn one.

What everyone was actually writing

Before this release, "load data when the id changes" had no primitive, so people reached for effect() — and effect() is a fire-and-forget side channel, not a value.

effect(() => fetch(id())) a race on fast id changes ⚠ isLoading tracked by hand ⚠ error state tracked by hand ⚠ no cancellation ⚠

Every team wrote this, every team wrote the same four bugs into it, and none of it was visible in the type system.

The whole release, in one sentence
effect() was being used to ASSIGN reactive state ↓ so give that job a real primitive resource() — async state as a declared value ↓ and the "reset when the input changes" case too linkedSignal() — writable state derived from a source ↓ and forms, which were the same pattern in ceremony signal forms — the value IS the model
Every headline feature in v21 exists to take a job away from effect(). Once you see that, the release is not eight things to learn — it is one correction applied in four places, and you can predict what v22 will do next.
effect()

I was never meant to compute values. I was for talking to things outside Angular — a chart library, localStorage, the document title.

resource()

Right, and "fetch when this changes" is a value with three states. Now it says so: value(), isLoading(), error(), and I cancel the stale request for you.

linkedSignal()

And I'm for the case computed() could never do — derived, but the user can still overwrite it, and it resets when the source changes. That was an effect with a bug in it on every team I've met.

The mechanism

Four primitives. One question tells them apart.

Some reactive statewho owns the value?
which primitive? →
Pure derivation, read-only → computed() Derived BUT writable, resets on source change → linkedSignal() Comes from async work → resource() / rxResource() Not a value at all — a side effect → effect()

The tell is ownership. If something outside your component owns the value (a server, a user's override), computed() cannot express it — and reaching for effect() to patch that gap is exactly the habit these APIs retire.

The other half of the release is about not shipping work you don't need yet. Incremental hydration going GA means a server-rendered page can stay static HTML until a component is actually needed, and style HMR means the dev loop stops paying for a rebuild to change a colour. Different surface, same instinct as the signals work: stop doing eagerly what you can declare and defer.

A CIAM admin screen must set document.title to the selected tenant's name whenever the selection changes. Which primitive?

Right, and it is worth noticing this is the one case that is still effect()'s job. Talking to something Angular does not own — the document, a chart library, localStorage — is precisely what it was designed for. The v21 APIs take away the jobs it was being MISUSED for, not the one it is right for.

computed() produces a value you read; it does not push anything anywhere. Nothing would ever set the title, and a computed that is never read does not even evaluate.

resource() is for state loaded ASYNCHRONOUSLY from somewhere. There is no request here — just a write to the DOM.

Where you've seen this before

The same correction, in three other places.

React's useEffect → use()

The identical arc: everyone fetched in useEffect, wrote the same race and loading-flag bugs, and the framework eventually gave async data a real primitive.

useEffect(fetch) ⚠

Your existing RxJS code

rxResource() is the bridge: keep the observable pipeline you already trust, get signal ergonomics at the component boundary. You do not have to pick a side.

rxResource({ loader })

Spring's @Async and CompletableFuture

Same lesson on the backend: "kick off work and mutate a field later" became "return a value that represents the pending work". Declaring beats orchestrating.

a value, not a callback
Questions from the back row

Do I have to rewrite my effect() calls?

No — and most of them are probably fine. The ones worth revisiting are those that assign to a signal or kick off a fetch; those are the bug-prone shape these APIs replace. An effect that writes to the DOM, logs, or syncs localStorage is doing exactly its job and should stay.

Is "Developer Preview" safe to use at work?

It means the API may still change between minors without a deprecation cycle. Fine for a spike or an internal tool; risky for the CIAM login flow you cannot afford to re-test on a Tuesday. The useful move is to try it somewhere small so the eventual migration is informed rather than a surprise.

Does going zoneless mean I must convert everything to signals first?

No, but it means every source of change has to be one Angular can actually see — a signal, an event binding, or an explicit markForCheck. Code that quietly relied on Zone.js noticing a setTimeout is what breaks, and that is the real migration work rather than the signal syntax itself.

resource() & rxResource() — Stable in v21

resource() — Promise-based

Declare async data dependencies reactively. Automatically re-fetches when signal inputs change.

import { resource, signal } from '@angular/core';

@Component({...})
export class UserProfileComponent {
  userId = input<number>();

  // Automatically re-fetches when userId() changes
  userResource = resource({
    request: () => ({ id: this.userId() }),
    loader: async ({ request }) => {
      const res = await fetch(`/api/users/${request.id}`);
      return res.json();
    }
  });

  // Reactive state — no manual loading flags needed
  isLoading = this.userResource.isLoading;  // Signal<boolean>
  user      = this.userResource.value;     // Signal<User | undefined>
  error     = this.userResource.error;     // Signal<unknown>
}
<!-- Template -->
@if (userResource.isLoading()) {
  <p>Loading...</p>
} @else if (userResource.error()) {
  <p>Error: {{ userResource.error() }}</p>
} @else {
  <h2>{{ userResource.value()?.name }}</h2>
}

rxResource() — Observable-based

Same API as resource() but accepts an Observable loader — perfect for HttpClient.

import { rxResource } from '@angular/core/rxjs-interop';
import { HttpClient } from '@angular/common/http';

@Component({...})
export class ProductsComponent {
  private http = inject(HttpClient);
  category = signal('electronics');

  products = rxResource({
    request: () => this.category(),
    loader: ({ request: cat }) =>
      this.http.get<Product[]>(`/api/products?cat=${cat}`)
  });
}

linkedSignal() — Stable in v21

Writable Derived Signal

A signal that derives its initial value from another signal, but can also be written to manually. Resets when the source changes.

import { linkedSignal, signal } from '@angular/core';

export class CountryCitySelector {
  country = signal('USA');
  cities  = signal({ USA: ['NYC', 'LA'], France: ['Paris', 'Lyon'] });

  // Resets to first city when country changes
  selectedCity = linkedSignal(() =>
    this.cities()[this.country()][0]
  );

  changeCountry(c: string) {
    this.country.set(c);
    // selectedCity auto-resets to first city of new country
  }

  selectCity(city: string) {
    this.selectedCity.set(city); // manual write still works
  }
}

vs computed() vs signal()

signal()
Standalone writable. No automatic derivation. You set it manually always.
computed()
Read-only derived value. Cannot be set. Always tracks source.
linkedSignal()
Writable + derived. Can be set manually but resets when source changes.

Hot Module Replacement (HMR) — Default in v21 dev

Instant Style & Template Updates

In Angular 21, ng serve uses HMR by default. Template and style changes reflect instantly — no full reload, component state preserved.

# v20 and earlier — full page reload on changes
ng serve

# v21 — HMR is on by default for templates + styles
ng serve

# Disable if needed
ng serve --no-hmr

# angular.json — fine-grained control
"serve": {
  "options": {
    "hmr": true,
    "hmrWarning": false
  }
}
Templates ✓ Styles ✓ Component logic ✓ Providers — full reload

Effect on Developer Workflow

Save CSS/SCSS change
Styles swap in <100ms. No state lost.
Save template change
Component re-renders with current signal/input values intact.
Save component .ts change
Component class logic updated; full re-render of that component only.
Change a provider / DI token
Full page reload required (can't hot-swap DI graph).

Incremental Hydration — GA in v21

Hydrate Only What's Needed

The SSR page ships static HTML. Angular hydrates (attaches JS) to components progressively — on viewport entry, on interaction, or on a timer.

// app.config.ts — enable incremental hydration
export const appConfig: ApplicationConfig = {
  providers: [
    provideClientHydration(
      withIncrementalHydration()
    )
  ]
};
<!-- Template — use @defer triggers -->
<!-- Hydrate when scrolled into view -->
@defer (hydrate on viewport) {
  <app-product-card .../>
}

<!-- Hydrate on first interaction -->
@defer (hydrate on interaction) {
  <app-comments .../>
}

<!-- Hydrate after 5 seconds -->
@defer (hydrate on timer(5000)) {
  <app-newsletter-cta .../>
}

Signal-based Forms — Developer Preview in v21

Reactive Forms with Signals

import { FormControl } from '@angular/forms';

@Component({...})
export class LoginForm {
  username = new FormControl('');
  password = new FormControl('');

  // v21: .value is now a Signal!
  usernameVal = this.username.value;   // Signal<string>
  isValid     = this.username.valid;   // Signal<boolean>
  errors      = this.username.errors;  // Signal<ValidationErrors | null>

  // Computed from signals — no more valueChanges pipe
  canSubmit = computed(() =>
    this.isValid() && this.password.valid()
  );
}
<!-- Template — reads signals directly -->
<input [formControl]="username">
@if (username.errors()?.['required']) {
  <p>Required</p>
}
<button [disabled]="!canSubmit()">Login</button>

Before vs After

v20 (Observable)
v21 (Signal)
// v20 — Observable-based, manual subscription
export class MyForm implements OnInit, OnDestroy {
  ctrl = new FormControl('');
  val = '';
  sub!: Subscription;

  ngOnInit() {
    this.sub = this.ctrl.valueChanges
      .pipe(debounceTime(300))
      .subscribe(v => this.val = v);
  }
  ngOnDestroy() { this.sub.unsubscribe(); }
}
// v21 — Signal-based, no subscriptions
export class MyForm {
  ctrl = new FormControl('');

  // Signals — automatically tracked
  val = this.ctrl.value;  // Signal<string>

  // No OnInit, no OnDestroy, no subscription!
}

effect() Improvements — v21

Cleanup Callbacks

import { effect, signal } from '@angular/core';

export class TimerComponent {
  interval = signal(1000);

  constructor() {
    effect((onCleanup) => {
      const id = setInterval(() => {
        console.log('tick');
      }, this.interval());

      // Cleanup called before each re-run & on destroy
      onCleanup(() => clearInterval(id));
    });
  }
}

allowSignalWrites — Stable

export class TrackerComponent {
  count   = signal(0);
  doubled = signal(0);

  constructor() {
    effect(() => {
      // v21: writing to signals inside effect is stable
      this.doubled.set(this.count() * 2);
    });
    // No more { allowSignalWrites: true } option needed!
  }
}
