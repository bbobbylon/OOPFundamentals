🏁 What is a race condition — and why can one thread see a stale value from another?

A race condition is when threads touch shared mutable state and the result depends on timing — counter++ is really read-add-write, so two threads can both read 5 and both write 6 (a lost update). CPU caches make it worse: a write in one core's cache may not be visible to another. The Java Memory Model defines visibility: synchronized gives mutual exclusion and visibility, while volatile gives visibility only — not enough for read-modify-write.

  • counter++ isn't atomic — read-modify-write races to a lost update.
  • synchronized = exclusion + visibility; volatile = visibility only.
  • Prefer lock-free atomics — AtomicInteger/LongAdder over a lock for counters.
  • Avoid deadlock — acquire locks in a fixed order; never block on I/O while holding one.

synchronized vs AtomicInteger

synchronized(lock) { counter++; }: safe but slow under contention (threads queue up). Better for simple counters: AtomicInteger counter = new AtomicInteger(0); counter.incrementAndGet() — uses CPU-level compare-and-swap (CAS), no lock. AtomicLong, AtomicReference, AtomicBoolean available. LongAdder: even faster for high-contention counters (maintains multiple cells, combines for sum). Use case: metrics counting, request ID generators, sequence numbers. Never use volatile int counter; counter++ — volatile doesn't make compound ops atomic.

Locks and ReentrantLock

ReentrantLock lock = new ReentrantLock(); lock.lock(); try { // critical section } finally { lock.unlock(); }. Advantages over synchronized: tryLock (don't block if can't acquire), timed lock, fairness (longest waiting thread gets lock first), interruptible lock wait. ReadWriteLock: multiple readers OR one writer, never both. StampedLock: optimistic read (no lock, validate at end — fast if no write), upgrade to full lock if validation fails. Use when: read-heavy, write-rare scenarios. Never hold a lock during blocking I/O.

Deadlock and how to prevent it

Deadlock: Thread A holds Lock 1, waiting for Lock 2. Thread B holds Lock 2, waiting for Lock 1. Both wait forever. Prevention: always acquire locks in the same order. tryLock(timeout): back off if can't acquire both locks in time. Detection: take a thread dump (jstack <pid>) — shows "waiting to lock" chains. Live in Spring Boot: /actuator/threaddump endpoint. Never call external code (HTTP calls, DB queries) while holding a lock — it might block for seconds, holding the lock for all threads. Keep synchronized blocks minimal.

Spring Boot / CIAM: Tomcat runs ~200 request threads, all sharing your @Bean singletons — so any singleton with mutable state (a cache Map, a counter) must be thread-safe (ConcurrentHashMap, AtomicInteger). SecurityContextHolder is ThreadLocal, which is exactly why @Async loses the security context (new thread, empty ThreadLocal) — fix with a DelegatingSecurityContextExecutor.

or, the bug that passes every test you write for it

The problem

counter++ is not one thing. It is three.

Two threads, 10,000 increments each

You expect 20,000. You get 13,847. Run it again: 17,902. Again: 20,000 — and that last one is the dangerous result, because it is the one your test run gets.

read counter → 5 other thread reads 5 too ⚠ both add 1 → 6 both write 6 two increments, one result

Nothing threw. Nothing logged. The number is just quietly wrong, and it is wrong by a different amount every time — which is why "it worked on my machine" is not a joke here, it is the literal failure mode.

Two separate problems, two separate fixes
ATOMICITY — can another thread interleave? ↓ fixed by synchronized, a Lock, or AtomicInteger VISIBILITY — will another thread even SEE my write? ↓ fixed by volatile, or by the same synchronized Both, or you have fixed half a bug
Atomicity and visibility are different problems. volatile buys you visibility and nothing else. synchronized buys you both. Almost every confidently-wrong concurrency fix on the internet is someone applying the first one to a problem that needed the second.
Thread A

I read counter. It's 5.

Thread B

Same. 5. The scheduler put me here between your read and your write — that gap is not an edge case, it is most of the instruction.

Your CPU cache

And even after A writes 6, I might hold it in a core-local cache for a while. B can keep reading 5 long after A "finished". That is the half nobody debugs.

The mechanism

Where the other thread gets in.

  1. READ the field into a registergetfield — thread B can be scheduled right here
  2. ADD oneiadd — and here
  3. WRITE it backputfield — B's write is now overwritten by yours

Three bytecodes, two gaps. A lost update needs the scheduler to land in one of those gaps, which on a loaded server happens constantly and on your laptop during a unit test happens rarely — the exact inversion you do not want.

The reason this survives code review is that the broken version looks like one statement, and Java gives you no syntax that distinguishes "one statement" from "one atomic operation". AtomicInteger.incrementAndGet() is the same three steps done as a single CPU compare-and-swap; the value is that the atomicity is now visible in the code you read.

Two threads run counter++ 10,000 times each on a shared field. You mark the field volatile. Is the count now correct?

Right. You have fixed the half of the problem you did not have. Both threads now reliably read a fresh 5, both add 1, both write 6 — the lost update is untouched. Use AtomicInteger, or synchronized, which covers both.

This is the single most common concurrency misconception. volatile guarantees that a write is seen by other threads — it says nothing about whether another thread can interleave between your read and your write.

Sharing the instance is what creates the race in the first place, not what fixes it. Two threads on two different objects would have no problem at all.

Questions from the back row

My tests pass. Doesn't that mean it's fine?

It means the scheduler did not land in the gap during your run. A race is a probability, not a branch, and a unit test on an idle laptop is close to the best case. Raise the odds deliberately: many threads, many iterations, and assert the total. The page's 10,000× section below does exactly that, and it is the only kind of test that has anything to say here.

If I use ConcurrentHashMap, am I done?

Only for single operations. if (!map.containsKey(k)) map.put(k, v) is two thread-safe calls with a race between them — another thread can insert in that gap. That is what putIfAbsent and computeIfAbsent are for: they make the check and the act one operation.

Why is synchronizing on a String literal a bad idea?

Because interned literals are shared across the whole JVM, so unrelated code that happens to lock on the same text is now serialised with yours — and can deadlock with you. Same for boxed Integer values in the cache range. Lock on a private final Object you own.

1. The setup

Two threads each call counter.increment() a thousand times. Both threads target the same Counter object. After both finish, the counter should equal 2,000.

But value = value + 1 isn't atomic. It's three steps: (1) read value, (2) add 1, (3) write back. If thread A reads while thread B is mid-update, A's "+1" overwrites B's "+1" and one update is lost forever.

3. The three ways to fix it

synchronized

Java's built-in mutex. One thread inside the block at a time.
public synchronized void increment() {
    value = value + 1;
}

The lock lives on this. Simple but coarse — entire method blocks other callers.

AtomicInteger

Lock-free. Uses CPU compare-and-swap instructions.
private AtomicInteger value = new AtomicInteger();
value.incrementAndGet();

Faster than synchronized for simple counters. java.util.concurrent.atomic has the whole family.

ReentrantLock

Like synchronized, but with more control (try-lock, timeouts, fairness).
private final ReentrantLock lock = new ReentrantLock();
lock.lock();
try { value++; }
finally { lock.unlock(); }

Immutable data

No shared mutable state = nothing to coordinate.
// Money is immutable — adding makes a NEW one
Money total = a.plus(b);   // no lock needed

Often the cleanest "fix": redesign so threads don't share mutable state in the first place.

The other concurrency landmines (briefly)

  • Deadlock: Thread A holds lock X and waits for lock Y. Thread B holds Y and waits for X. Both stuck forever. Fix: always acquire locks in the same order.
  • Livelock: Threads keep responding to each other but make no progress (like two people in a hallway dancing left/right). Fix: random backoff.
  • Starvation: One thread keeps losing to others and never gets the lock. Fix: fair locks (new ReentrantLock(true)).
  • Memory visibility: Without proper synchronization, one thread's writes may never become visible to other threads (CPU caches!). The volatile keyword and synchronized blocks fix this.
  • Best practice: use ExecutorService instead of raw Thread, and prefer the java.util.concurrent collections (ConcurrentHashMap, BlockingQueue) over hand-rolling synchronization.
