Concurrency — Race Conditions, Live

Two threads. One shared counter. Watch the bug appear, then watch the fix work.

1. The setup

Two threads each call counter.increment() a thousand times. Both threads target the same Counter object. After both finish, the counter should equal 2,000.

But value = value + 1 isn't atomic. It's three steps: (1) read value, (2) add 1, (3) write back. If thread A reads while thread B is mid-update, A's "+1" overwrites B's "+1" and one update is lost forever.

3. The three ways to fix it

synchronized

Java's built-in mutex. One thread inside the block at a time.
public synchronized void increment() {
    value = value + 1;
}

The lock lives on this. Simple but coarse — entire method blocks other callers.

AtomicInteger

Lock-free. Uses CPU compare-and-swap instructions.
private AtomicInteger value = new AtomicInteger();
value.incrementAndGet();

Faster than synchronized for simple counters. java.util.concurrent.atomic has the whole family.

ReentrantLock

Like synchronized, but with more control (try-lock, timeouts, fairness).
private final ReentrantLock lock = new ReentrantLock();
lock.lock();
try { value++; }
finally { lock.unlock(); }

Immutable data

No shared mutable state = nothing to coordinate.
// Money is immutable — adding makes a NEW one
Money total = a.plus(b);   // no lock needed

Often the cleanest "fix": redesign so threads don't share mutable state in the first place.

The other concurrency landmines (briefly)

  • Deadlock: Thread A holds lock X and waits for lock Y. Thread B holds Y and waits for X. Both stuck forever. Fix: always acquire locks in the same order.
  • Livelock: Threads keep responding to each other but make no progress (like two people in a hallway dancing left/right). Fix: random backoff.
  • Starvation: One thread keeps losing to others and never gets the lock. Fix: fair locks (new ReentrantLock(true)).
  • Memory visibility: Without proper synchronization, one thread's writes may never become visible to other threads (CPU caches!). The volatile keyword and synchronized blocks fix this.
  • Best practice: use ExecutorService instead of raw Thread, and prefer the java.util.concurrent collections (ConcurrentHashMap, BlockingQueue) over hand-rolling synchronization.
