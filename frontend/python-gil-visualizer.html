Python: The GIL, Threads & Processes

Why one lock means Python threads don't parallelize CPU work — and how to choose between threading (I/O), multiprocessing (CPU), and asyncio (massive I/O concurrency).

The GIL: one lock that shapes every Python concurrency decision

The Global Interpreter Lock (GIL) is a single mutex inside CPython that allows only one thread to execute Python bytecode at a time. It exists because CPython's memory management (reference counting) isn't thread-safe — the GIL makes refcount updates atomic without per-object locks, which keeps single-threaded code fast and C extensions simple. The consequence: spinning up multiple threads for a CPU-bound task gives no speedup — they take turns holding the GIL, so you get concurrency, not parallelism. But threads are still excellent for I/O-bound work, because the GIL is released during blocking I/O (file/socket reads, time.sleep) and inside many C extensions — so while one thread waits on the network, another runs. For true CPU parallelism you use multiprocessing: separate processes, each with its own interpreter and its own GIL, running on different cores — at the cost of no shared memory (data is pickled across an IPC boundary) and heavier startup. For thousands of concurrent I/O operations on one thread, asyncio uses a cooperative event loop (async/await) — no thread overhead, no GIL contention, but only for code written to await. The rule of thumb: I/O-bound → threads or asyncio; CPU-bound → processes. And the landscape is shifting: free-threaded Python (PEP 703, the experimental 3.13t build) removes the GIL, making threads truly parallel for CPU work — but it's opt-in and still maturing.

CPU-bound: threads DON'T help

# 4 threads crunching numbers: # ~same wall-time as 1 (GIL serializes them) with ThreadPoolExecutor(4) as ex: ex.map(crunch, data) # no speedup # 4 PROCESSES: ~4x on 4 cores with ProcessPoolExecutor(4) as ex: ex.map(crunch, data) # true parallelism

I/O-bound: threads DO help

# 50 URLs fetched concurrently: # GIL released during each socket wait with ThreadPoolExecutor(50) as ex: results = ex.map(fetch, urls) # ~50x faster than sequential # (or use asyncio for 1000s of them)

vs Java/Go concurrency

Java/Go: threads/goroutines run truly in parallel across cores — no global lock. Python: the GIL serializes bytecode, so CPU parallelism requires multiple processes. This is Python's most-criticized design choice. The flip side: a far simpler C-extension story and no data races on individual operations. Free-threaded 3.13t finally offers a no-GIL path, closing the gap.

In a CIAM context: An auth service is mostly I/O — JWKS fetches, DB lookups, IdP calls — so asyncio (FastAPI) or a thread pool scales it beautifully despite the GIL. But password hashing (bcrypt/argon2) is deliberately CPU-bound: running it directly on the asyncio event loop blocks every other request. Offload it — await loop.run_in_executor(process_pool, hash_pw, pw) — so the CPU work runs in a separate process and the event loop stays responsive. Knowing which half of your workload is I/O vs CPU is the whole game.

1. What the GIL Is (and Why It Exists)

# The GIL: one thread runs bytecode at a time.
# CPython refcounting isn't thread-safe, so the
# GIL serializes the interpreter instead of
# locking every object.

# Result for CPU work across 4 threads:
# they ROUND-ROBIN the GIL → ~1x, not 4x

The GIL is an implementation detail of CPython (Jython/IronPython/PyPy differ). It protects the interpreter's internal state — chiefly reference counts — so a single global lock replaces millions of tiny per-object locks. That makes single-threaded code fast and C extensions easy to write, but it means two threads can't run Python bytecode simultaneously. It's a throughput trade-off baked deep into the runtime.

The GIL is released periodically and during I/O. CPython hands off the GIL every few milliseconds (so threads share time) and, crucially, drops it during blocking I/O and inside many C extensions (NumPy heavy math, etc.). That's exactly why threads do accelerate I/O-bound and native-heavy workloads — the GIL is held only while interpreting Python bytecode.

2. threading — for I/O-Bound Work

from concurrent.futures import ThreadPoolExecutor

# 50 network fetches, concurrently
with ThreadPoolExecutor(max_workers=50) as ex:
  results = list(ex.map(fetch, urls))
# while one thread waits on a socket,
# the GIL is free for another → big speedup

Threads shine when the bottleneck is waiting — HTTP calls, DB queries, disk. Each blocking call releases the GIL, so other threads make progress. Use ThreadPoolExecutor (or threading.Thread) and you get real concurrency for I/O. But two threads can still interleave on a non-atomic operation, so shared mutable state needs a threading.Lock — the GIL protects the interpreter, not your invariants.

The GIL is not a substitute for your own locks. counter += 1 across threads can still lose updates (it's read-modify-write, and the GIL can switch mid-operation). Protect shared mutable state with threading.Lock or use atomic structures like queue.Queue. The GIL prevents interpreter corruption, not application-level races.

3. multiprocessing — for CPU-Bound Work

from concurrent.futures import ProcessPoolExecutor

# CPU crunching across all cores
with ProcessPoolExecutor() as ex:
  results = list(ex.map(crunch, chunks))
# each process has its OWN interpreter + GIL
# args/results are PICKLED across the boundary

Separate processes each get their own Python interpreter and GIL, so they truly run in parallel across cores — the only stdlib way to parallelize pure-Python CPU work. The cost: no shared memory (arguments and return values are pickled and copied over an IPC pipe), heavier startup, and anything you send must be picklable. Best for coarse-grained chunks where compute dwarfs the serialization overhead.

Process overhead means granularity matters. Sending tiny tasks to a process pool can be slower than running them in one process, because pickling + IPC + process startup dominate. Batch work into larger chunks (chunksize), and prefer it for genuinely heavy jobs (image processing, model inference, big numeric loops).

4. Choosing: asyncio vs Threads vs Processes

WorkloadUseWhy
Many slow I/O calls (100s–1000s)asyncioone thread, an event loop, no per-task thread cost; needs await-able libs
Moderate I/O, blocking librariesthreadingGIL released during I/O; works with sync libraries you can't rewrite
CPU-bound (math, parsing, crypto)multiprocessingseparate GILs → real multicore parallelism
CPU-bound, cutting edgefree-threaded 3.13tPEP 703 removes the GIL — threads parallelize CPU work (experimental, opt-in)
Mix them when a workload is mixed. An async server (I/O) that must do occasional heavy CPU work offloads it: await loop.run_in_executor(process_pool, cpu_fn, arg) runs the CPU job in a process without blocking the event loop. The art is identifying which parts are I/O-bound and which are CPU-bound, then routing each to the right primitive.
