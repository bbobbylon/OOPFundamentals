Modules & import type

TypeScript files live in two universes at once: the type universe (compile-time) and the value universe (runtime). Modules connect them — and import type is the toggle that decides what survives the trip to JavaScript.

1. The two universes

Every TS file participates in two parallel worlds:

  • The type universe — used by the compiler to check correctness. Erased before the code runs.
  • The value universe — actual functions, classes, variables. Survives compilation and ends up in your JS bundle.

Some declarations live in only one. interface and type live only in the type universe. let, function, and const live only in the value universe. class, enum, and namespace exist in both — a class declaration produces a runtime constructor and a type with the same name.

// Type universe only — vanishes at runtime
interface User { id: number; }
type UserId = User['id'];

// Value universe only — appears in the JS output
const ADMIN_ID = 1;
function greet(name: string) { return `hi ${name}`; }

// Both — the class is a runtime constructor AND a type
class Repo { findUser(id: number) { /* ... */ } }
const r: Repo = new Repo(); // Repo used as a type (left) AND a value (right)
Why this matters for modules: when you import something, the compiler has to decide whether to emit a real runtime import in the output JS — or whether the imported name is type-only and the entire import line should disappear.

2. ESM in TypeScript

Modern TS code uses ECMAScript module syntax — the same import / export you'd use in plain JS:

// user.ts — exports
export interface User { id: number; email: string; }
export function findUser(id: number): User | undefined { /* ... */ }
export const SYSTEM_USER: User = { id: 0, email: 'root@x' };
export default class UserRepo { /* ... */ }

// app.ts — imports
import UserRepo, { User, findUser, SYSTEM_USER } from './user';

The compiler resolves the path, type-checks the import, and (if it emits a runtime import) writes it to the output. Same forms also work:

import * as userMod from './user';        // namespace import
import { findUser as find } from './user'; // renamed import
import './styles.css';                    // side-effect-only
await import('./lazy');                     // dynamic — returns a Promise

3. import type & export type

An import type statement imports something for type checking only. The line is guaranteed to be erased from the JS output, even if the imported name happens to also be a value.

// Without 'type' — TS decides whether to emit based on usage:
import { User } from './user';
const u: User = /* ... */; // only used as a type — TS likely erases the import

// With 'type' — the intent is explicit, never emitted as a runtime import:
import type { User } from './user';
const u: User = /* ... */;
// Guaranteed: this line disappears from the JS output.

Same on the export side:

// Re-export a type without dragging in any runtime dependency
export type { User } from './user';

Why this matters in practice

  1. Smaller bundles. A type-only import that the bundler can't prove is type-only may show up as a real import in the output, pulling the dep along. import type tells everyone in the toolchain "don't bother".
  2. Avoiding circular import errors. If two modules need each other's types but not each other's runtime, swapping one direction to import type breaks the cycle without splitting the file.
  3. Isomorphic/server-side code. Sharing types from a server-only module into the browser bundle is safe with import type — the line vanishes.

4. Inline type-only specifiers

Since TS 4.5, you can mark individual specifiers as type-only within an otherwise-runtime import — useful when one file exports both kinds and you need both:

import { type User, findUser, SYSTEM_USER } from './user';
// User is erased; findUser and SYSTEM_USER are kept as runtime imports.

// Works for exports too:
export { type UserId, findUser } from './user';

This is the form most codebases standardize on — it's the least disruptive and gives you per-name control without splitting imports.

5. verbatimModuleSyntax

A compiler flag (TS 5.0+) that makes the rules unambiguous: TS will not delete or rewrite import/export syntax for you. If you wrote import {X}, it will be emitted as-is — even if X is type-only. So you'd better have written import type {X}.

// tsconfig.json
{
  "compilerOptions": {
    "verbatimModuleSyntax": true
  }
}

With it enabled:

// ✗ Error: 'User' is a type and must be imported using a type-only import
import { User } from './user';
const u: User = /* ... */;

// ✓ Correct under verbatim
import { type User } from './user';
const u: User = /* ... */;
Recommendation: turn on verbatimModuleSyntax for new projects. It removes a whole class of "why did this import vanish/persist?" confusion, and your editor will auto-add the type keyword for you. The cost is fixing existing imports — usually a one-time codemod.

7. Module resolution modes

How TS finds './user' on disk. Set with "moduleResolution" in tsconfig.json. Modes are coupled to the "module" setting.

ModeWhen to useNotes
"node" (a.k.a. "node10")Legacy Node.js / CommonJSOld algorithm — no exports field support, no extension required
"node16" / "nodenext"Native ESM in Node.jsRequires explicit .js extensions in imports, supports package.json exports field, distinguishes .cts/.mts
"bundler"Vite, Webpack, esbuild, BunModern. Like Node ESM but doesn't require .js extensions. Use for app code targeting a bundler

{
  "compilerOptions": {
    "module": "esnext",
    "moduleResolution": "bundler",
    "verbatimModuleSyntax": true
  }
}

// Library targeting Node.js native ESM
{
  "compilerOptions": {
    "module": "nodenext",
    "moduleResolution": "nodenext"
  }
}

8. Path aliases — baseUrl & paths

The fix for import { foo } from '../../../../utils/foo'. Configure once in tsconfig.json:

{
  "compilerOptions": {
    "baseUrl": ".",
    "paths": {
      "@app/*":    ["src/*"],
      "@utils/*":  ["src/utils/*"],
      "@shared":    ["../shared/src/index.ts"]
    }
  }
}
// Now:
import { formatDate } from '@utils/date';       // instead of '../../../utils/date'
import type { User } from '@app/types/user';
Important: paths is a type-checker-only feature. TS understands the alias but does not rewrite it in the emit. At runtime, your bundler (Vite, Webpack, Jest, esbuild) also needs to know the alias. Most bundlers have a plugin (vite-tsconfig-paths, tsconfig-paths-webpack-plugin) that reads tsconfig and configures itself. If you skip the bundler config, the build fails at runtime.

9. The .js extension surprise

Under "moduleResolution": "nodenext" (or "node16"), Node.js's native ESM rules apply: imports must include the explicit extension, and that extension must be .js — even though the source file is .ts.

// In foo.ts, importing from bar.ts:
import { bar } from './bar.js';  // ← .js, not .ts

This trips up everyone the first time. The reasoning: TS compiles bar.ts → bar.js, and the import in the emitted JS will be ./bar.js. The TS compiler doesn't rewrite the specifier, so the spec you write at compile time must be the spec that works at runtime.

Under "moduleResolution": "bundler", you can omit the extension (and most apps do). The bundler resolves on its own. If you write to publish a library that consumers will use directly in Node, prefer nodenext and write .js.

The .cts / .mts escape valves

TS recognizes these the way Node recognizes .cjs / .mjs: .cts is always CommonJS, .mts is always ESM, regardless of the surrounding package.json's "type" field. Handy in mixed projects (a single CJS config file inside an ESM package, for instance).

10. Barrel files (and their cost)

A barrel is a module that re-exports from a bunch of others — index.ts files that aggregate a folder.

// utils/index.ts
export { formatDate } from './date';
export { formatMoney } from './money';
export { slugify } from './string';
export type { Currency } from './money';

// consumers can write:
import { formatDate, formatMoney } from './utils';

The cost: any consumer that touches the barrel pulls in every module the barrel re-exports — for type checking, and (if the bundler doesn't tree-shake perfectly) sometimes for runtime too. In big monorepos this is a real performance issue: editing a tiny utility can trigger rebuilds across the codebase.

Practical advice:
• Barrels for types only (using export type) are essentially free.
• Barrels for runtime values: fine for small libraries, watch out in big apps. Many teams ban deep barrels and require explicit per-file imports.
• Modern tools (Vite, Turbopack) tree-shake well, but TS type-checking time scales with what the barrel transitively reaches.

11. Ambient modules & declare module

Sometimes you import something that isn't a real TS module — a CSS file, an image, an untyped npm package. You declare the shape ambient-style so TS lets the import compile:

// src/types/globals.d.ts
declare module '*.css' {
  const classes: { readonly [key: string]: string };
  export default classes;
}

declare module 'untyped-lib' {
  export function doThing(x: unknown): number;
}

The full story — including type augmentation, declare global, and writing real declaration files — is in the Declaration Files card (Expert tier). For now: ambient module declarations let you tell TS "trust me, this import works at runtime; here's its shape".

The dual-class trap

// A class is both a type AND a value.
import type { Repo } from './repo';

function demo(r: Repo) {       // ✓ used as a type — works
  const x = new Repo();      // ✗ used as a value — fails at runtime
}

// Fix: drop the 'type' keyword. Or split:
import { Repo } from './repo';        // runtime + type, both worlds
