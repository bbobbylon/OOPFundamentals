XSS & SQL Injection — Attacking (and Defending) User Input

Two of the OWASP Top 10's most common findings, both caused by the exact same mistake: untrusted input lands in a context that has its own grammar — HTML, JavaScript, or SQL — without being escaped or parameterized first, so the interpreter can't tell attacker data from attacker code.

💉 What makes an "injection" attack, and why is it always the same root cause?

Every injection attack — XSS in the browser, SQL injection in the database, command injection in a shell — follows one pattern: attacker-controlled text is concatenated into a string that an interpreter (the HTML parser, the SQL engine, the OS shell) is about to read as syntax, without first marking where the data ends and the syntax begins. <script> in an HTML response becomes a real tag. A stray ' in a SQL string becomes the end of a literal and the start of new SQL. The fix is always the same shape too: never build the target string by concatenation — use context-aware output encoding for HTML, and parameter binding for SQL, so the interpreter is structurally incapable of treating your data as its own syntax.

  • Same bug, three targets: HTML/JS (XSS), SQL (SQLi), OS commands (command injection) — the interpreter can't distinguish data from code.
  • Reflected vs Stored vs DOM-based XSS differ only in where the unescaped input round-trips through.
  • Encoding must match the context — HTML-encoding a value that lands inside a <script> block doesn't help; there's no single universal "sanitize" function.
  • Parameterized queries don't "escape" SQL — they never let attacker input become SQL text at all.

Angular's default posture

Angular auto-escapes everything bound via interpolation ({{ value }}) and property binding — it's XSS-safe by default. The danger zone is anything that opts back into raw HTML: [innerHTML], bypassSecurityTrustHtml(), or hand-rolled DOM writes like el.innerHTML = ….

This app's own SQL pattern

Every repo in the scaffold's JDBC layer uses NamedParameterJdbcTemplate with a MapSqlParameterSource — :email, never string concatenation. That isn't a style choice; it's the thing that makes SQL injection structurally impossible against these queries.

Defense in depth

Output encoding / parameterization is the primary fix, but layer on a Content-Security-Policy header (blocks inline <script> even if one slips through) and httpOnly cookies (limits what a successful XSS can actually steal).

CIAM: Session/auth cookies should always be HttpOnly (JS can't read them, so XSS can't exfiltrate them directly) and Secure+SameSite. A Bearer JWT kept in localStorage instead of a cookie sidesteps CSRF (see the CSRF page) but is fully readable by any XSS on the page — which is exactly why an app that stores tokens in JS memory/localStorage has to take XSS defense even more seriously, not less.

The problem

Two strings went in. One string came out. That is the whole bug.

The mechanism

Watch the exact instant data turns into grammar.

  1. you hold two separate things: a query template and a value typed into a formright now the boundary between them still exists
  2. you join them with + into one flat stringthe boundary is gone, and nothing downstream can rebuild it
  3. that string reaches a parser — SQL engine, HTML parser, shell, LDAP, templatea parser's entire job is to find grammar in text
  4. the ' stops being a character and becomes a tokenit does exactly what you asked; it cannot read your mind
  5. everything after that token is parsed as code, and runslogin bypass, stolen session, dropped table — pick your parser

Look at which step a real fix deletes. Not step 4 — you cannot teach a parser to guess which characters you meant. Not step 5 — by then it is already executing. Every genuine defence kills step 2.

One disease, five parsers. SQL injection, XSS, command injection, LDAP injection and server-side template injection are not five bug classes to memorise for an exam — they are one bug held against five different grammars. Which parser you happen to be feeding decides only the blast radius, never the cause, and never the shape of the fix: bind parameters for SQL, textContent or {{ }} for HTML, an argument array for ProcessBuilder instead of a shell line. Three different APIs, one identical move. If a fix's name contains the word "escape" or "filter", it is a speed bump, not a wall. Which is exactly what a WAF is: it reads your traffic as text and guesses, because it does not know your grammar either.

Your Angular console keeps its session in an HttpOnly; Secure; SameSite=Strict cookie — textbook CIAM. A stored XSS lands in a profile bio an admin views. The attacker's script cannot read document.cookie. So what?

Right, and this is the part that gets skipped: XSS does not need to steal the session, because it is the session. It can change the recovery email, enrol its own MFA factor, mint an API key, or approve its own consent screen — all from inside the victim's tab, all perfectly authenticated. "We use HttpOnly" is an answer to cookie theft. It is not an answer to XSS.

HttpOnly stops the cookie being read. It does nothing about it being used. The script is running on your origin, so the browser attaches that cookie to every request the script makes — helpfully, and by design.

No — HttpOnly hides the cookie from every script, same-origin ones included. That is the one thing it does well, and it is still not enough here.

Questions from the back row

We have a WAF in front of everything. Doesn't that cover this?

It buys you hours during a zero-day and it eats the drive-by scanners, which is real value — keep it. But it inspects your traffic as text and guesses, because it doesn't know your grammar any better than your regex did: SeLeCt, double URL-encoding and inline /**/ comments have been beating those rules for twenty years. And for DOM-based XSS the WAF sees literally nothing — the payload lives after the #, which the browser never sends. Defence in depth, never the fix.

Then why not sanitize once on input and be done?

Because at input time you don't yet know which parser the value will meet. The same display name is harmless in a <p>, lethal inside a <script> block, and needs a completely different encoding again in a URL or a CSV a colleague opens in Excel. Sanitizing on input means guessing every future context, and it corrupts your data permanently while doing it. Store what the user actually typed; encode at the moment you write it somewhere, when you finally know where "somewhere" is.

So bind everything and I'm safe?

Almost. A bind parameter can only replace a value, never an identifier — ORDER BY :col and a parameterised table name simply do not work, because the plan is built before the value shows up. That's a feature, and it's also the one hole left: for a sortable admin grid you need a hard allowlist, a switch mapping the string "name" to the literal column u.display_name. Not an escape function. A list of the columns that exist.

1. Reflected vs Stored vs DOM-based XSS

TypeWhere the payload livesWho's affectedNeeds server involvement?
ReflectedThe URL/request itself (query param, form field) — echoed straight back into the responseOnly the victim who clicks the crafted linkYes — server reflects it, unescaped
StoredSaved server-side (a comment, profile bio, ticket description) — rendered to every viewerEvery visitor who views the poisoned page — no click requiredYes — server persists and later re-serves it, unescaped
DOM-basedNever touches the server at all — client-side JS reads location.hash/search and writes it straight into the DOMOnly the victim who opens the crafted linkNo — purely client-side; server-side output encoding can't fix this
Stored is the worst of the three — one successful write compromises every future viewer with zero further attacker effort. DOM-based is the sneakiest — it can pass every server-side security review, because the vulnerable code never sends the tainted string to the server at all.

2. XSS defense: encode for the context you're writing into

There's no single universal "sanitize" function — the correct escaping depends entirely on where the value is being written.

ContextExample sinkCorrect encoding
HTML body text<p>Hello, {name}</p>HTML-entity encode & < > " '
HTML attribute<img alt="{name}">HTML-attribute encode (also handles " breaking out of the quote)
Inside a <script> blockvar name = "{name}";JS-string encode — HTML-encoding does not stop "; alert(1); //
URL / query param<a href="/search?q={q}">encodeURIComponent — different rules than HTML encoding

✗ Angular — opts back into risk

// [innerHTML] renders raw HTML — attacker XSS runs
<div [innerHTML]="comment.body"></div>

// bypassSecurityTrustHtml explicitly disables Angular's sanitizer
this.safeHtml = this.sanitizer
  .bypassSecurityTrustHtml(comment.body);

✓ Angular — default, safe

// Interpolation is ALWAYS auto-escaped by Angular
<div>{{ comment.body }}</div>
// A literal <script> renders as visible, inert text

↪ Add a Content-Security-Policy header as a second layer — even if an encoding bug slips through, script-src 'self' blocks inline/attacker-hosted scripts from executing.

3. SQL injection: string concatenation vs. parameter binding

✗ Vulnerable — concatenated SQL

String sql =
  "SELECT * FROM users WHERE email = '"
  + email + "'";
stmt.execute(sql);
// email = "' OR '1'='1' --"
// query becomes: ...WHERE email = '' OR '1'='1' --'
// always true → returns the FIRST row, often an admin

✓ This app's actual pattern

// UserQuery.java — a named-param constant
public static final String SELECT_BY_EMAIL =
  "SELECT * FROM users WHERE email = :email";

// UserRepoImpl.java
MapSqlParameterSource params =
  new MapSqlParameterSource("email", email);
jdbc.queryForObject(SELECT_BY_EMAIL, params, rowMapper);
NamedParameterJdbcTemplate doesn't "escape" the input — it never lets the input become SQL text at all. The driver sends the query text and the parameter value to the database separately; the DB engine treats :email's value as a literal, full stop, no matter what characters it contains. That's a structural guarantee, not a best-effort filter — which is exactly why this scaffold's whole JDBC layer (see repo/repoimpl/ across every aggregate) is built on it by default.

4. One-sentence recap

💉 Injection — XSS, SQL injection, and their relatives — is always the same bug: untrusted input reaches an interpreter that has its own grammar without being escaped for that exact context or bound as a literal parameter; the fix is never a single "sanitize everything" function, it's context-aware output encoding in the browser (Angular's default interpolation, a Content-Security-Policy) and parameter binding, never concatenation, in the database.
