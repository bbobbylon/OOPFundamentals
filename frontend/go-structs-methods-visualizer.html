Go Structs & Methods

Structs, value vs pointer receivers, embedding (composition over inheritance), and how method sets decide which types satisfy an interface.

🏗️ Go has no classes — so how do structs, methods, and interfaces replace them?

Go drops the class and composes three smaller ideas. A struct is a typed bag of fields and a value type (assigning copies every field). A method is a function with a receiver declared outside the struct: a value receiver ((u User)) gets a copy and can't mutate; a pointer receiver ((u *User)) mutates the caller and avoids copying. There's no inheritance — reuse comes from embedding, where an inner struct's fields and methods are promoted (composition, not "is-a"). And an interface is satisfied implicitly by method set. The classic gotcha: a pointer-receiver method is in the method set of *T only — so a plain value can fail to satisfy an interface its pointer would.

  • Struct = value type — assigning/passing copies every field.
  • Value vs pointer receiver — copy & read-only vs mutate the caller.
  • Embed, don't inherit — promoted fields/methods; composition over "is-a".
  • Pointer methods are on *T only — a value may miss the interface.

Struct + methods

type User struct { ID int Name string Email string } // value receiver — read-only, gets a copy func (u User) FullName() string { return u.Name } // pointer receiver — mutates the original func (u *User) Rename(n string) { u.Name = n }

Value vs pointer receiver

u := User{Name: "Bobby"} u.FullName() // copy — fine u.Rename("Alice") // Go auto-takes &u // → u.Name is now "Alice" // but in a slice/map the copy bites: users := []User{{Name:"A"}} for _, x := range users { x.Rename("Z") // x is a COPY } // users[0].Name still "A"! // fix: for i := range users { users[i].Rename("Z") }

Embedding vs Java inheritance

Java: class Admin extends User — "is-a", tight coupling, one parent. Go: embed for "has-a + promotion": type Admin struct { User; CanDelete bool }. Now admin.Name and admin.FullName() work (promoted from User), but Admin is not a User — it just has one. Embed many types; promote many method sets. Override by declaring a same-named method on Admin. This is "composition over inheritance" enforced by the language.

CIAM context: A token validator models cleanly with embedding: type Claims struct { jwt.RegisteredClaims; Roles []string `json:"roles"` } embeds the library's standard claims (promoting their Valid()) and adds your CIAM Roles; a func (c *Claims) HasRole(r string) bool pointer receiver reads cleanly. Unlike Spring's class CustomClaims extends DefaultClaims, Go's embedding is composition you can mix freely (embed RegisteredClaims and an Audit mixin) with no single-inheritance ceiling.

1. Structs Are Value Types With Field Tags

// definition + the three literal styles
type User struct {
  ID int `json:"id"`
  Name string `json:"name"`
  Email string `json:"email,omitempty"`
}

a := User{ID: 1, Name: "Bobby"} // named (preferred)
b := User{1, "Bobby", ""} // positional (fragile)
var c User // zero: {0, "", ""}

Prefer named literals — positional breaks silently when fields are reordered or added. Struct tags (the backtick string after a field) are metadata read via reflection: encoding/json uses json:"..." for (de)serialization, and ORMs/validators use their own tags. omitempty drops zero-valued fields from JSON output.

A struct comparison just works if all fields are comparable: a == b compares field by field. But a struct containing a slice, map, or function is not comparable and == won't compile — use reflect.DeepEqual or a hand-written equality.

2. Value vs Pointer Receivers

Value receiver func (u User)Pointer receiver func (u *User)
Operates on a copy — cannot mutate the caller's structOperates on the original — can mutate fields
Copies the whole struct on every call (cheap for small structs)Copies only the pointer (cheap for large structs)
Use for read-only methods on small values (String(), getters)Use to mutate, or when the struct is large, or holds a sync.Mutex
Consistency rule: if any method needs a pointer receiver, give all methods on that type pointer receivers. Mixing them makes the method set confusing and can break interface satisfaction (Section 4).

3. Embedding = Composition With Promotion

// Admin embeds User (no field name)
type Admin struct {
  User // embedded
  CanDelete bool
}

ad := Admin{User: User{Name: "Eve"}}
ad.Name // "Eve" — promoted field
ad.FullName() // promoted method
ad.User.Name // explicit path still works

Promotion lifts the embedded type's exported fields and methods to the outer struct. Override by declaring a same-named method on Admin — yours wins, and you can still call ad.User.FullName() for the inner one. Go resolves the shallowest name; an ambiguous promotion (two embeds with the same field) is a compile error you must disambiguate explicitly.

Embedding an interface is just as common: type ReadWriter interface { io.Reader; io.Writer } composes two interfaces into one. Same mechanism, type-level.

4. Method Sets Decide Interface Satisfaction

The classic compile error: if Save() has a pointer receiver and Storer requires Save(), then var s Storer = User{} fails ("User does not implement Storer (method Save has pointer receiver)") while var s Storer = &User{} compiles. Interfaces hold whatever you assign — assign the pointer.
