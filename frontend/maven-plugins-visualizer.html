🧩 What are Maven plugins — and why is every Maven action a plugin goal?

Maven itself does almost nothing — a framework. The real work (compile, test, package, deploy) is done by plugins, JARs of Mojos that each implement a goal (compiler:compile, surefire:test, spring-boot:repackage); goals either bind to a phase or run standalone. The key Spring Boot ones: maven-compiler-plugin (Java version + annotation processors for Lombok/MapStruct), maven-surefire-plugin (unit tests, *Test.java), maven-failsafe-plugin (integration tests, *IT.java, in the verify phase), and spring-boot-maven-plugin (repackage makes the fat JAR, run launches in dev). Utility plugins add Flyway migrations, JaCoCo coverage, and version checks.

  • Maven = framework; plugins do the work — each goal is a Mojo.
  • Goals bind to phases or run standalone — compiler:compile, spring-boot:repackage.
  • compiler / surefire / failsafe / spring-boot — version+APT, unit, IT, fat JAR.
  • Utility plugins — Flyway, JaCoCo coverage, versions check.

or, why your coverage badge has been lying to you since March

The problem

You fix an OOM-killed test run, the build stays green, and coverage quietly drops to zero — with no error anywhere.

The coverage gate that always passes because it measures nothing

Your CI box keeps OOM-killing the test JVM, so you add a fix straight to maven-surefire-plugin: <argLine>-Xmx1536m</argLine> in its <configuration>. Tests stop crashing. mvn verify goes green. Nobody looks twice.

jacoco-maven-plugin's prepare-agent execution runs earlier in the build and writes a -javaagent:...jacocoagent.jar=... string into that same argLine property, specifically so surefire will fork its test JVM wrapped in the coverage agent. Maven doesn't merge two values written to one property — whichever plugin's configuration surefire actually reads wins outright. Your literal string replaces JaCoCo's, the forked JVM never loads the agent, target/jacoco.exec still gets written (almost empty), and target/site/jacoco/index.html quietly reports coverage near 0%.

Java version pinned to 21 ✓ surefire pinned to 3.x for JUnit 5 ✓ a literal <argLine> instead of ${argLine} ⚠

The build is green because nothing failed — it just stopped measuring anything.

Always chain argLine through the placeholder
Confirm prepare-agent runs before surefire ↓ its default phase is initialize, well before test — if it hasn't run yet there's no argLine to inherit at all Write your own argLine as ${argLine} plus your flags, never a bare literal ↓ ${argLine} pulls in whatever prepare-agent already set — that's concatenation, not replacement, so the agent and your heap flag both survive And re-check the actual HTML report, not just the build's exit code
Configuration that looks additive can be silently replacing. Any Maven property one plugin writes and another reads — argLine, skip, testFailureIgnore — is really a shared variable, not a merged list. The last plugin to set it wins unless you deliberately reference the old value. Treat it exactly like overwriting a shared global in code, because that is exactly what it is.
Sticky note: ${argLine} isn't decoration — it's the only thing standing between "green build" and "nothing was ever measured."
You

I only added a heap flag to surefire. Why did our coverage badge drop to 2%?

jacoco-maven-plugin

I set the javaagent flag into argLine back during initialize, specifically so surefire would launch your tests wrapped in me.

maven-surefire-plugin

I forked the test JVM with whatever argLine held at that moment. Yours was the last write — I don't know or care who wrote before you.

The argLine property

There's only one of me. I don't merge — I hold exactly one string, and I hand it to whoever asks last.

The mechanism

Trace who actually owns the argLine property, in order, across one mvn verify run.

  1. initialize phase beginsphase
  2. jacoco-maven-plugin:prepare-agent runs, writes -javaagent:...=target/jacoco.exec into the argLine propertysets argLine
  3. compile, test-compile phases run normally, untouchedphase
  4. test phase begins; surefire reads its own <configuration><argLine>reads config
  5. if that value is a literal string with no ${argLine}, it's what forks the JVM — JaCoCo's agent flag is simply goneoverwrite
  6. verify phase runs jacoco:report against a near-empty jacoco.exec and writes a near-zero report — nothing threw, so the build stays greensilent

Step 5 is the entire bug. Maven never prints "argLine was replaced" — as far as its plugin engine is concerned, you configured surefire's argLine correctly. It has no idea a second plugin wanted a say in that same property.

JaCoCo's javaagent flag silently vanishescoverage reports near-zero, build stays green

Three unrelated reasons to touch argLine, one identical failure. The fix isn't "never touch argLine" — it's that argLine is a single shared slot, and every plugin writing to it needs to know it isn't the only writer.

Your team adds <argLine>-Xmx2g</argLine> to maven-surefire-plugin to stop OOM-killed test runs. mvn verify is green and the JaCoCo HTML report exists. What's actually wrong?

Right. The literal argLine replaced the property JaCoCo's prepare-agent had already set. Surefire forked a completely un-instrumented JVM; the report is real, it's just reporting almost nothing.

A passing build and an existing report only prove jacoco:report ran and surefire didn't crash — neither step verifies the exec file has real samples in it. Green means "nothing threw," not "coverage was measured."

The coverage agent doesn't have a separate memory budget that -Xmx could exceed — it just instruments bytecode as classes load. It isn't failing at all here; it's simply absent from the JVM that ran your tests.

Where you have seen this before

"Last write wins on a shared slot" shows up anywhere config from two sources lands in the same place.

Spring Boot profile YAML

application-prod.yml setting a list property doesn't merge with the base application.yml's list for that same key — it replaces it wholesale. Scalars override cleanly; lists don't append, they vanish and get swapped.

one shared slot, last writer wins

Angular DI tokens without multi: true

Register a second provider for HTTP_INTERCEPTORS and forget multi: true, and Angular doesn't append it to the interceptor chain — it silently replaces the earlier provider for that token. No error, just one interceptor that mysteriously stopped firing.

same trap, no error either time

JwtAuthenticationConverter in Spring Security

Call setJwtGrantedAuthoritiesConverter to pull custom claims into authorities, and you fully replace the default converter that reads the scope/scp claim — your users keep their custom roles and silently lose every scope-based authority unless you re-add it yourself.

explicit merge or silent loss

1 — Goals vs Phases: The Core Distinction

Phase

A named slot in the build lifecycle — an abstract step like "compile" or "test". Phases run in fixed order.

When you run mvn package, Maven executes every phase up to and including package.

Goal

The actual unit of work — a specific task a plugin knows how to do. Goals are bound to phases.

Format: plugin:goal — e.g., compiler:compile, surefire:test.

Key rule: You can run a goal directly (mvn compiler:compile) or run a phase (mvn compile) — which triggers all goals bound to that phase. Running a phase also runs all preceding phases.

3 — Key Plugins Explained

maven-compiler-plugin
compile phase
Compiles .java → .class with your Java version
Goals: compiler:compile compiler:testCompile

Spring Boot's parent POM pre-configures this to use the java.version property you set in <properties>.

To customize (e.g., enable preview features): 
<plugin>
  <artifactId>maven-compiler-plugin</artifactId>
  <configuration>
    <release>21</release>
    <compilerArgs>
      <arg>--enable-preview</arg>
    </compilerArgs>
  </configuration>
</plugin>
maven-surefire-plugin
test phase
Discovers and runs JUnit 5 tests
Goals: surefire:test

Discovers test classes by convention: *Test.java, *Tests.java, *TestCase.java.

Skip tests: mvn package -DskipTests (skip execution) or -Dmaven.test.skip=true (skip compilation too).

Reports: target/surefire-reports/*.xml — picked up by CI systems (GitHub Actions, Jenkins) to show test results.

For JUnit 5 to work, Spring Boot's parent POM pins surefire to version 3.x which has JUnit Platform support built in.
spring-boot-maven-plugin
package phase
Creates the executable fat JAR
Goals: spring-boot:repackage spring-boot:run spring-boot:build-image

spring-boot:repackage: runs after jar:jar. Takes the thin JAR and wraps it into an executable fat JAR containing all dependencies in a nested BOOT-INF/lib/ layout.

spring-boot:run: run the app directly without building a JAR. Uses the classpath directly — fast for development.

spring-boot:build-image: builds a Docker image using Cloud Native Buildpacks. No Dockerfile needed.

mvn spring-boot:run -Dspring-boot.run.profiles=dev — activate a profile.
maven-resources-plugin
process-resources
Copies src/main/resources into target/classes
Goals: resources:resources resources:testResources

Copies src/main/resources/ to target/classes/ so application.properties is on the classpath at runtime.

Resource filtering: if enabled, replaces ${project.version} placeholders in resource files with actual Maven property values. Useful for injecting the build version into application.properties.

Spring Boot's parent enables filtering for application*.yml and application*.properties by default.
maven-jar-plugin
package phase
Builds the initial thin JAR
Goals: jar:jar

Creates the initial target/app.jar containing only your compiled classes and resources — no dependencies.

This runs before spring-boot-maven-plugin's repackage goal. The repackage step then replaces/wraps this thin JAR.

You rarely configure this directly in a Spring Boot project — the defaults work fine.
maven-failsafe-plugin
integration-test phase
Runs integration tests separately from unit tests
Goals: failsafe:integration-test failsafe:verify

Discovers tests named *IT.java, *ITCase.java, *IntegrationTest.java.

Key difference from surefire: failsafe does not fail the build during the integration-test phase. It collects failures and only fails at the verify phase — giving post-integration teardown steps a chance to run.

Use this for @SpringBootTest tests that need a full server or database — keeps them out of the fast unit test suite.

4 — Configuring a Plugin in pom.xml

Anatomy of a plugin declaration — every element explained:

<build> <plugins> <plugin> <!-- Coordinates identify the plugin artifact --> <groupId>org.apache.maven.plugins</groupId> <artifactId>maven-surefire-plugin</artifactId> <version>3.2.5</version> <!-- optional if inherited from parent --> <!-- <configuration> sets plugin-specific options --> <configuration> <excludes> <exclude>**/*IntegrationTest.java</exclude> </excludes> </configuration> <!-- <executions> binds goals to lifecycle phases --> <executions> <execution> <id>default-test</id> <phase>test</phase> <goals> <goal>test</goal> </goals> </execution> </executions> </plugin> </plugins> </build>
