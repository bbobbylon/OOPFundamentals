⚙️ What is Python's function and parameter system — and what is the mutable-default trap?

Python functions are first-class objects. There are four parameter kinds, and order matters: positional, *args (extra positionals → tuple), keyword-only (after *), and **kwargs (extra keywords → dict). The famous trap: default arguments evaluate once at definition, so def f(items=[]) shares one list across all calls — fix with items=None then build inside. Name lookup follows LEGB (Local → Enclosing → Global → Built-in), and closures let inner functions capture enclosing variables.

  • Four parameter kinds — positional, *args, keyword-only, **kwargs.
  • Mutable defaults are shared — defined once; use a None sentinel + build inside.
  • LEGB resolves names — Local → Enclosing → Global → Built-in.
  • Closures capture enclosing scope — inner functions remember outer variables.

Mutable default trap

# ❌ THE FAMOUS BUG: def add_role(user, roles=[]): roles.append(user['role']) return roles # Default [] created ONCE at function definition add_role({'role': 'ADMIN'}) # ['ADMIN'] ← ok add_role({'role': 'READER'}) # ['ADMIN', 'READER'] ← BUG! # Both calls share the SAME list object! # ✓ FIX: use None as sentinel def add_role(user, roles=None): if roles is None: roles = [] # new list each call roles.append(user['role']) return roles # Same trap exists for dicts and other mutables: def f(cache={}): ... # ← shared dict, BUG def f(options=[]): ... # ← shared list, BUG

The problem

You handed a helper your list. It handed you back a different list.

"Python is pass-by-value." "No — pass-by-reference."

Both camps ship bugs. Believe by value and you will not expect a helper's roles.append('ADMIN') to reach the caller — it does, and a session object you never meant to touch just grew an admin role. Believe by reference and you will expect roles = [] inside the function to blank the caller's list — it doesn't, and your "clear it out" helper does nothing at all, quietly, forever.

roles.append(r) — caller SEES it roles = [] — caller sees nothing ⚠ n += 1 on an int — invisible ⚠ no copy was ever made

Each of those two wrong models is right exactly half the time. That is worse than being wrong all the time — it means the model survives code review, twice, and then fails in the one place nobody was looking.

One rule, instead of two half-rules
def f(p): … then f(a) ↓ the call literally performs the assignment p = a p and a are now two names for ONE object ↓ rebinding p moves the name p and nothing else mutating the object changes what every name sees ↓ therefore rebind = invisible outside · mutate = visible outside
Python passes arguments by assignment. Not by value, not by reference — f(a) runs p = a. That one sentence explains both halves of every argument surprise on this page, including the mutable-default trap in scenario ④.
Your caller

I passed perms. I own that list. Nothing in there had better change.

The parameter

I am not a copy of your list. I am a second sticky note with the same address written on it. When I call .append(), I am writing on your list.

An int argument

I get the identical treatment — you just can't tell, because I ship no method that alters me. Every "change" to me quietly builds a new int and moves a name.

The mechanism

Two names, one object, zero copies.

The part everyone re-learns at 2am: id(p) == id(perms) is true inside the function. Writing p = [] builds a brand-new object and repoints one sticky note — it cannot move the others, because nothing in Python can reach out and repoint a name it does not own.

Mutable and immutable are not two rules — they are one rule meeting two kinds of object. int, str, tuple and frozenset ship no method that alters them, so the only thing that can ever happen to them is a rebind, and a rebind is invisible outside — which is why they look pass-by-value. list, dict, set and every class you write hand you append, update, attribute assignment — so they look pass-by-reference. The rule never changed. The objects did.

This is also what the / and * markers are buying you, and it is not pedantry. Everything before / is positional-only, so its name is not part of your API — rename data to payload at 4pm on a Friday and not one caller breaks. That is exactly why the built-in is len(obj) and never len(seq=obj). Everything after a bare * is keyword-only, so the call site is forced to say what it means — create_user(first_name='Bob', idp_type='PING') cannot silently transpose two adjacent strings the way create_user('Bob', 'PING') can, and a first name swapped with an IdP type is the kind of bug a customer finds for you.

A cleanup helper runs exactly two lines against the list it was handed: roles.remove('ADMIN'), then roles = []. You call it with perms = ['ADMIN', 'READER']. What does print(perms) show afterwards?

That is the line everyone expects to win, and it is the one that does nothing. roles = [] builds a new empty list and points the local name at it. The caller's name never moved.

Right — and both halves of the rule fire in two consecutive lines. remove mutates the one shared object, so the caller sees it. roles = [] only rebinds a local name that evaporates on return, so the caller sees nothing. Mutate visible, rebind invisible.

No copy is made anywhere — the call ran roles = perms. That is precisely why line one was able to reach out and shorten your list.

Questions from the back row

Fine — so how do I actually pass a copy?

One level deep: list(roles), roles[:], dict(attrs). Nested: copy.deepcopy(x). But know what a shallow copy really gives you — a new list holding the same dicts, so copy[0]['sub'] = 'x' still lands on the original. The better answer is usually to stop mutating the caller's argument at all: take it, build a new value, return it. A function that both mutates its argument and returns something is a function your colleagues will use wrong.

If closures capture like this, why do my lambdas built in a loop all print the same number?

Because a closure captures the variable, not the object the variable held at the time. Each lambda: i holds a cell pointing at i itself, and that cell is read when you call the lambda — which is after the loop finished, when i is sitting on its final value. The fix lambda i=i: i works because default arguments are evaluated once, at def time, on that iteration. Read that twice: the very same "defaults evaluate at definition" rule that hands you the mutable-default bug is the rule you use to fix the loop-closure bug. One rule, one famous trap, one famous cure.

What is a decorator, minus the magic?

A function that takes a function and returns a function. @log above a def is just f = log(f) — which is only possible because functions are ordinary objects you can bind to a name. The wrapper takes *args, **kwargs and forwards them so it can wrap anything. Skip @functools.wraps(func) and the returned object honestly reports itself: __name__ becomes 'wrapper', the docstring is gone, and inspect.signature shows (*args, **kwargs). So every log line reads "Calling wrapper", your generated docs go blank, and any framework that registers routes by __name__ now sees two endpoints both called wrapper and refuses to start. One line buys all of that back.

1. The four kinds of parameters — and the / and * markers

A function signature can mix all of these. The order is fixed: positional-only, then normal, then *args, then keyword-only, then **kwargs.

# pos_only / normal *args kw_only **kwargs
def f(a, b, /, c, d, *args, e, f=0, **kwargs):
    pass

# a, b : positional-ONLY  — must be passed by position (the / enforces it)
# c, d : normal           — by position OR keyword
# *args: extra positionals collected into a tuple
# e    : keyword-ONLY     — after *, must be passed by name
# f    : keyword-only with a default
# **kwargs: extra keywords collected into a dict

Calling it

f(1, 2, 3, 4, 5, 6, e=7, x=8)
# a=1 b=2 c=3 d=4
# args=(5, 6)   ← extra positionals
# e=7  f=0      ← e by keyword, f default
# kwargs={'x': 8} ← extra keyword

Unpacking at the call site

nums = [1, 2, 3]
opts = {'e': 7}
f(*nums, 4, **opts)
# * spreads a list into positionals
# ** spreads a dict into keywords
# the SAME * / ** symbols, mirror image

2. LEGB — how a name is resolved

When you read a variable, Python searches four scopes in order and stops at the first hit.

L
Local
this function's body
E
Enclosing
any outer function
G
Global
the module
B
Built-in
len, print, range…
x = "global"

def outer():
    x = "enclosing"
    def inner():
        # reads x → not Local, found in Enclosing
        print(x)        # "enclosing"
    inner()

# To WRITE an outer name, declare intent:
def counter():
    global x        # rebind the module-level x
def make():
    n = 0
    def step():
        nonlocal n     # rebind the enclosing n (a closure)
        n += 1; return n
    return step
Brain Power. Assignment creates a local name by default. So n += 1 inside a nested function without nonlocal raises UnboundLocalError — Python sees the assignment, marks n local, then you read it before it's set. global/nonlocal are how you say "no, I mean that outer one."

3. Closures — functions that remember

A closure captures variables, not values

def multiplier(factor):
    def mul(x):
        return x * factor   # captures `factor`
    return mul

double = multiplier(2)
triple = multiplier(3)
print(double(10), triple(10))  # 20 30
# each closure keeps its own `factor`

The classic loop-closure surprise

fns = [lambda: i for i in range(3)]
print([f() for f in fns])  # [2, 2, 2] !
# all 3 captured the SAME i (now 2)

# Fix: bind per-iteration via a default arg
fns = [lambda i=i: i for i in range(3)]
print([f() for f in fns])  # [0, 1, 2]

Try both snippets in the Python Playground — the surprise is real, and seeing [2, 2, 2] print is the fastest way to never forget it.

The mutable-default trap (scenario ④): def f(x, acc=[]) creates the list once, when the def runs — not per call. Every call without acc shares that one list, so it "remembers" across calls. The fix is the sentinel pattern: def f(x, acc=None): acc = acc or [].
