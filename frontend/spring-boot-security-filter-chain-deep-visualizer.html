The Security Filter Chain

Spring Security isn't magic sprinkled on your controllers — it's an ordered chain of servlet filters that every request passes through before it reaches the DispatcherServlet. Knowing the order, and which filter does what, is how you finally understand why a request gets 401 vs 403, and where your custom filter belongs.

1. It's one big filter chain, in front of your app

A single DelegatingFilterProxy hands off to Spring's FilterChainProxy, which runs your SecurityFilterChain — a list of filters in a fixed, meaningful order. Each filter does one job and calls the next. Only if the request survives all of them does it reach your controller.

request→ authenticate→ authorize→ DispatcherServlet → @Controller

Two ideas drive everything: authentication ("who are you?") happens early; authorization ("are you allowed?") happens last, right before your code. The split is exactly why 401 and 403 are different filters' jobs.

2. The cast: SecurityContext, Authentication, and the decision point

SecurityContext + Authentication

The SecurityContextHolder holds the current Authentication (principal + granted authorities) for the request thread. An authn filter sets it; everything downstream reads it.

ExceptionTranslationFilter

The translator. It catches AuthenticationException → 401 (start authentication) and AccessDeniedException → 403. It makes no decisions itself.

AuthorizationFilter

The decider (last filter). It evaluates your authorizeHttpRequests rules against the Authentication. Denied → it throws AccessDeniedException (which the translator above catches).

4. So where is 401 vs 403 decided?

Both come from the same event — AuthorizationFilter throwing AccessDeniedException — but the ExceptionTranslationFilter chooses the status based on whether the principal is authenticated:

Principal at the denyTranslator doesStatus
anonymous / not authenticatedcalls the AuthenticationEntryPoint (e.g. send WWW-Authenticate)401 Unauthorized
authenticated, but lacks the authoritycalls the AccessDeniedHandler403 Forbidden

5. How authentication actually resolves

Filter → Manager → Provider

Authn Filter→ AuthenticationManager→ AuthenticationProvider

The authn filter builds an unauthenticated Authentication token and hands it to the AuthenticationManager (usually ProviderManager), which tries each AuthenticationProvider until one authenticates it — then the result is stored in the SecurityContext.

Defining the chain

@Bean
SecurityFilterChain chain(HttpSecurity http) throws Exception {
  http
    .authorizeHttpRequests(a -> a
       .requestMatchers("/api/admin/**").hasRole("ADMIN")
       .requestMatchers("/public/**").permitAll()
       .anyRequest().authenticated())
    .oauth2ResourceServer(o -> o.jwt(Customizer.withDefaults()));
  return http.build();
}

6. Adding your own filter (in the right place)

Order matters: a filter that reads the Authentication must run after the authn filter; one that sets up context must run before. Use addFilterBefore / addFilterAfter and extend OncePerRequestFilter.

http.addFilterBefore(new RequestIdFilter(),
                    BearerTokenAuthenticationFilter.class);

class RequestIdFilter extends OncePerRequestFilter {
  @Override protected void doFilterInternal(
      HttpServletRequest req, HttpServletResponse res, FilterChain chain)
      throws ServletException, IOException {
    MDC.put("reqId", UUID.randomUUID().toString());
    try { chain.doFilter(req, res); }      // MUST call the next filter
    finally { MDC.clear(); }
  }
}

Two classic mistakes: forgetting to call chain.doFilter(...) (the request silently stalls), and placing an auth-reading filter before authentication has run (the SecurityContext is still empty).

7. One-sentence recap

🛡️ Spring Security is an ordered servlet-filter chain in front of your DispatcherServlet: early filters authenticate (set the Authentication in the SecurityContext), the last AuthorizationFilter decides access and throws AccessDeniedException when it denies, and the ExceptionTranslationFilter translates that into 401 (anonymous → authenticate) or 403 (authenticated but unauthorized) — so to place a custom filter, you just slot it before/after the relevant stage with addFilterBefore/After.
