🧩 What is Java OOP — and how do the four pillars (Encapsulation, Inheritance, Polymorphism, Abstraction) combine with SOLID principles to make large codebases maintainable?

Object-Oriented Programming (OOP) organizes code around objects — units that combine state (fields) and behavior (methods). Java is a class-based OOP language: every object is an instance of a class, and classes form hierarchies. The four pillars each address a specific software engineering concern. Encapsulation: hide internal state and only expose controlled access via methods. Fields are private; getters/setters (or more commonly, business methods) provide controlled access. Reason: prevents external code from putting the object in an invalid state; lets you change the internal representation without breaking callers. In Java: private fields + public methods + final to prevent subclass overrides of critical methods. Inheritance: a subclass extends a parent class, inheriting its fields and methods and optionally overriding them. Enables code reuse and establishes "is-a" relationships. Java uses single inheritance (one parent class, multiple interfaces). Key rule: override with @Override (compiler checks you're actually overriding, not accidentally overloading). Polymorphism: the same method call behaves differently based on the actual runtime type of the object. Compile-time polymorphism = method overloading (same name, different parameters). Runtime polymorphism = method overriding (a subclass method is called on a parent type reference). This is what makes List<Animal> work for both Dogs and Cats — calling animal.speak() calls the correct subclass's speak() at runtime via dynamic dispatch. Abstraction: define WHAT a type can do (the interface/abstract class) without specifying HOW. Callers depend on the abstraction, not the implementation. List<String> list = new ArrayList<>() — you interact with the List abstraction; switching to LinkedList later requires zero changes to calling code. SOLID principles: five design rules that lead to maintainable OOP code. S: Single Responsibility (each class has one reason to change). O: Open/Closed (open for extension, closed for modification — add behavior via new classes, not by editing existing ones). L: Liskov Substitution (subclasses must be substitutable for their parent without breaking correctness). I: Interface Segregation (prefer many small interfaces over one large "fat" interface). D: Dependency Inversion (depend on abstractions, not concretions — inject dependencies, don't instantiate them). Spring Boot's entire design is built on SOLID — DI is D, @Service/@Repository separation is S, interface-based service design is I.

4 Pillars examples

// ENCAPSULATION: hide state, expose behavior class BankAccount { private double balance; // hidden public void deposit(double amount) { if (amount <= 0) throw new IllegalArgumentException(...); this.balance += amount; // controlled access } } // INHERITANCE: is-a relationship class Animal { void speak() { ... } } class Dog extends Animal { @Override void speak() { System.out.println("Woof"); } } // POLYMORPHISM: same interface, different behavior at runtime List<Animal> animals = List.of(new Dog(), new Cat()); animals.forEach(Animal::speak); // Dog: Woof, Cat: Meow // JVM calls the correct speak() based on ACTUAL type // ABSTRACTION: depend on interface, not class interface PaymentProcessor { void process(Payment p); } class StripeProcessor implements PaymentProcessor { ... } class PayPalProcessor implements PaymentProcessor { ... } // Caller: PaymentProcessor pp = ... // inject either

abstract class vs interface

// Interview favorite: abstract class vs interface — when to use each? // ABSTRACT CLASS: // ✅ Want to provide default method implementations // ✅ Share state (fields) across subclasses // ✅ "Template Method" pattern: define algorithm skeleton // in abstract class, subclasses implement specific steps // ❌ Subclass can only extend ONE abstract class // Example: abstract class BaseAuthHandler { abstract void authenticate(); // subclasses must implement final void handleRequest() { // template: can't override log("Request received"); authenticate(); // calls subclass implementation log("Auth complete"); } } // INTERFACE: // ✅ Defining a contract without any implementation // ✅ A class can implement MULTIPLE interfaces // ✅ Since Java 8: default methods for backward compat // ❌ No state (no non-static fields — only constants) // Example: UserRepository, PaymentProcessor, Serializable // Rule of thumb: use interface when you can (prefer composition)

Interview / Context: Java OOP is fundamental to your Spring Boot work and heavily tested in both junior and senior interviews. The most common interview questions: "What is the difference between abstract class and interface?" (above), "What is the difference between overriding and overloading?" (runtime vs compile-time polymorphism), "How does Spring implement dependency injection?" (constructor/setter/field injection — prefer constructor injection for testability and required dependencies), "What is the Liskov Substitution Principle and can you give an example of violating it?" (a Rectangle subclass whose setWidth() also changes height to maintain square invariant violates LSP — callers of Rectangle expect independent width/height). SOLID principles are also asked in behavioral/design questions at senior levels.

The Four Pillars of OOP Click Each Card

Click a pillar to expand detailed explanation, code, and interview tips.

🔒 Encapsulation
Bundle data + behavior, hide internals — click to expand

Restrict direct access to an object's fields. Expose only what is necessary via public methods. Validation logic lives inside the class, protecting invariants.

public class BankAccount { private double balance; // private field public double getBalance() { return balance; } public void deposit(double amount) { if (amount <= 0) throw new IllegalArgumentException( "Amount must be positive"); balance += amount; } // No public setBalance() — protected! }
Interview answer: Encapsulation = data hiding + access control. Prevents invalid state, lets you change implementation without breaking callers, and improves testability.
🠺 Inheritance
Extend existing classes, reuse behavior — click to expand

A subclass inherits fields and methods from its superclass. Java: single class inheritance (extends), multiple interface inheritance (implements).

public class Animal { protected String name; public void speak() { System.out.println(name + " makes a sound"); } } public class Dog extends Animal { @Override public void speak() { System.out.println(name + ": Woof!"); } } // super() calls parent constructor // super.method() calls parent version
Prefer Composition over Inheritance when behavior should vary at runtime, or when you need behaviors from multiple sources.
🍮 Polymorphism
One interface, many implementations — click to expand

Runtime polymorphism (method overriding) — JVM decides at runtime which method to call based on the actual object type. Compile-time polymorphism (method overloading) — compiler picks based on parameter types.

// Runtime: dynamic dispatch Animal a = new Dog(); a.speak(); // calls Dog.speak() at runtime! // Compile-time: overloading public int add(int a, int b) {...} public double add(double a, double b) {...} public String add(String a, String b) {...} // Polymorphism powers the strategy pattern: List<Animal> zoo = List.of(new Dog(), new Cat()); zoo.forEach(Animal::speak);
🌌 Abstraction
Hide complexity, expose only essentials — click to expand

Focus on what an object does, not how. Achieved via abstract classes and interfaces.

// Abstract class: partial implementation public abstract class Shape { abstract double area(); abstract double perimeter(); public void describe() { // shared System.out.printf( "Area=%.2f%n", area()); } } // Interface: pure contract public interface Drawable { void draw(); default void drawInColor(String color) { System.out.println("Color: "+color); draw(); } }

Interface — Capability Contract

@FunctionalInterface public interface Transformer<T, R> { R transform(T input); // lambdas can implement this! } Transformer<String, Integer> len = s -> s.length(); // Java 8+ default method interface Printable { void print(); default void printBordered() { System.out.println("---"); print(); System.out.println("---"); } }

Abstract Class — Template Method

public abstract class DataProcessor { private final String source; public DataProcessor(String s) { this.source = s; // has constructor! } // Template method: defines algorithm public final void process() { var data = readData(); var out = transform(data); writeOutput(out); } protected abstract List<String> readData(); protected abstract List<String> transform( List<String> data); protected void writeOutput( List<String> data) { data.forEach(System.out::println); } }
Decision rule: Interface = capability that unrelated classes can share (Serializable, Runnable, Comparable). Abstract Class = base for a family of closely related classes that share state and partial behavior with customizable hooks.

Design Patterns — Interview Essentials

Singleton — Thread-Safe

// Best: enum singleton (thread-safe, serializable) public enum Singleton { INSTANCE; public void doSomething() { ... } } // Classic: double-checked locking public class Config { private static volatile Config instance; private Config() {} public static Config getInstance() { if (instance == null) { synchronized (Config.class) { if (instance == null) instance = new Config(); } } return instance; } } // volatile = visibility, synchronized = atomicity

Factory Pattern

// Simple Factory public class ShapeFactory { public static Shape create(String type) { return switch (type.toLowerCase()) { case "circle" -> new Circle(); case "rectangle" -> new Rectangle(); default -> throw new IllegalArgumentException(type); }; } } // Abstract Factory: family of related objects public interface UIFactory { Button createButton(); Dialog createDialog(); } // WindowsUIFactory, MacUIFactory implement it // Ensures all components from same OS family

Builder Pattern

public class Pizza { private final String size; private final boolean cheese, pepperoni; private Pizza(Builder b) { size=b.size; cheese=b.cheese; pepperoni=b.pepperoni; } public static class Builder { private String size; private boolean cheese, pepperoni; public Builder size(String s) { size=s; return this; } public Builder cheese() { cheese=true; return this; } public Builder pepperoni() { pepperoni=true; return this; } public Pizza build() { return new Pizza(this); } } } // Usage: Pizza p = new Pizza.Builder() .size("large").cheese().pepperoni().build();

Observer Pattern

public interface Observer { void update(String event, Object data); } public class EventBus { private final Map<String, List<Observer>> subs = new HashMap<>(); public void subscribe(String ev, Observer o) { subs.computeIfAbsent(ev, k -> new ArrayList<>()).add(o); } public void publish(String ev, Object d) { subs.getOrDefault(ev, List.of()) .forEach(o -> o.update(ev, d)); } } // Spring: @EventListener, ApplicationEventPublisher // Used in GUI frameworks, reactive systems
Strategy Pattern (also common): Comparator IS the strategy pattern. Collections.sort(list, comparator) — the sort accepts any sorting strategy at runtime.

SOLID Principles

S — Single Responsibility Principle

A class should have only one reason to change. Separate concerns into distinct classes.

// BAD: too many responsibilities class UserService { void saveUser(User u) { /* DB logic */ } void sendEmail(User u) { /* Email */ } String generateReport() { /* Report */ } } // GOOD: each class has one job class UserRepository { void save(User u) {} } class EmailService { void send(User u) {} } class ReportGenerator { String generate() {} }

O — Open/Closed Principle

Open for extension, closed for modification. Add new behavior by creating new classes.

// GOOD: new discount = new class, no modification interface DiscountPolicy { double apply(double price); } class StudentDiscount implements DiscountPolicy { public double apply(double p){ return p*0.9; } } class VIPDiscount implements DiscountPolicy { public double apply(double p){ return p*0.7; } }

L — Liskov Substitution Principle

Subtypes must be usable wherever their base type is used, without breaking behavior. The classic violation: Square extends Rectangle.

// VIOLATION: Square breaks Rectangle contract // Rectangle says setWidth/setHeight are independent class Square extends Rectangle { public void setWidth(int w) { super.setWidth(w); super.setHeight(w); // breaks contract! } } // Fix: use a common interface instead interface Shape { int area(); } class Rectangle implements Shape { ... } class Square implements Shape { ... }

I — Interface Segregation Principle

Don't force clients to depend on methods they don't use. Split fat interfaces into smaller, focused ones.

// BAD: Robot must implement eat() and sleep() interface Worker { void work(); void eat(); void sleep(); } // GOOD: segregated interfaces interface Workable { void work(); } interface Feedable { void eat(); } interface Sleepable { void sleep();} class Human implements Workable,Feedable,Sleepable{} class Robot implements Workable {}

D — Dependency Inversion Principle

High-level modules should not depend on low-level modules. Both depend on abstractions. Foundation of Spring IoC/DI.

// BAD: high-level depends on concrete low-level class class OrderService { private MySQLOrderRepo repo = new MySQLOrderRepo(); // tightly coupled! } // GOOD: inject the abstraction interface OrderRepository { void save(Order o); Optional<Order> findById(long id); } class OrderService { private final OrderRepository repo; OrderService(OrderRepository repo) { this.repo = repo; // injected! } } // Spring: @Autowired OrderRepository repo; // Swap MySQL with MongoDB: zero changes to OrderService

equals() / hashCode() Contract Must Know

The Contract Rules

Reflexive: x.equals(x) is always true.
Symmetric: x.equals(y) implies y.equals(x).
Transitive: x.equals(y) and y.equals(z) implies x.equals(z).
Consistent: Multiple calls return same result (no side effects).
Null-safe: x.equals(null) always returns false.

hashCode contract: If x.equals(y) then x.hashCode() == y.hashCode() MUST hold.
Unequal objects CAN have the same hashCode (collision is allowed).
Critical mistake: Override equals() but forget hashCode(). Objects break in HashMap and HashSet — two "equal" objects hash to different buckets and can never be found.

Correct Implementation

public class Point { private final int x, y; @Override public boolean equals(Object obj) { if (this == obj) return true; if (!(obj instanceof Point)) return false; Point o = (Point) obj; return x == o.x && y == o.y; } @Override public int hashCode() { return Objects.hash(x, y); // Java 7+ // classic: 31 * x + y } } // Java 16+ records auto-generate everything: public record Point(int x, int y) {} // equals, hashCode, toString all generated!

Why 31 as the hash multiplier?

The classic hashCode recipe: result = 31 * result + fieldHash. The number 31 is an odd prime. Even multipliers risk losing information on overflow (shifts out bits). The JVM optimizes 31*x as (x << 5) - x (one shift + subtract). 31 also distributes hash values well across the hash table buckets in practice.

String Immutability, Pool & StringBuilder

String Pool

String a = "hello"; // pool reference String b = "hello"; // same pool reference! String c = new String("hello"); // heap object a == b; // true - same pool object a == c; // false - c is new heap object a.equals(c); // true - same content // intern() forces pool placement String d = c.intern(); a == d; // true - back in pool // Why immutable? // 1. String pool is safe only if strings can't change // 2. hashCode can be cached (strings as map keys) // 3. Thread-safe - share freely without sync // 4. Security - filenames, URLs can't be modified

StringBuilder vs String

// BAD: creates n intermediate String objects! String s = ""; for (int i = 0; i < 1000; i++) s += i; // O(n^2) total // GOOD: mutable buffer, one object StringBuilder sb = new StringBuilder(); for (int i = 0; i < 1000; i++) sb.append(i); // O(n) total String result = sb.toString(); // StringBuffer = StringBuilder + synchronized // Use StringBuffer ONLY if multiple threads write // Useful StringBuilder methods: sb.insert(0, "prefix"); sb.delete(2, 5); sb.reverse(); sb.charAt(3); sb.setCharAt(3, 'X');
Interview tip: Modern JVM compilers optimize simple String concatenation in loops using StringBuilder. But the optimization only applies to simple cases. Always use StringBuilder explicitly for complex loop concatenations.

List — When to Choose

  • ArrayList — O(1) get, O(n) insert middle. 99% of use cases
  • LinkedList — O(1) add/remove ends. Implements Deque. Poor cache
  • Vector/Stack — Synchronized ArrayList/stack. Legacy — prefer ArrayDeque for stack

Set — When to Choose

  • HashSet — O(1) contains/add. No order
  • LinkedHashSet — O(1) + preserves insertion order
  • TreeSet — O(log n) sorted. Use for range queries: floor/ceiling

Map — When to Choose

  • HashMap — O(1). General purpose. No order
  • LinkedHashMap — O(1) + insertion order. LRU Cache base
  • TreeMap — O(log n) sorted keys. Range queries
