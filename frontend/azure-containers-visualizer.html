Azure Containers — ACR, ACI & Container Apps

The Azure container ladder: ACR stores (and can build) your images, ACI runs a container in seconds with zero orchestration, and Container Apps adds revisions, ingress, and KEDA event-driven scale — Kubernetes power without operating Kubernetes.

📦 Which container service when — and what do revisions and KEDA actually do?

Azure gives you a ladder of container services, and AZ-204 mostly tests whether you can pick the right rung. The base is Azure Container Registry (ACR) — a private Docker registry with a twist: az acr build uploads your source and builds the image in the cloud (no local Docker daemon needed), and ACR Tasks can rebuild automatically when a base image gets patched. Azure Container Instances (ACI) is the simplest runtime: give it an image, get a running container (or a container group — several containers sharing localhost and volumes, like a one-off pod) with per-second billing and no VMs to manage. It is perfect for batch jobs, build agents, and burst capacity, but it has no load balancing, no autoscale, and no rolling deploys. That is what Azure Container Apps (ACA) adds: it runs your containers on managed Kubernetes + KEDA under the hood, giving you HTTPS ingress, revisions (every deploy creates an immutable snapshot; you can split traffic 90/10 between old and new for canary releases), scale rules from HTTP concurrency or event sources (queue depth, Kafka lag), and true scale to zero. Full AKS (Azure Kubernetes Service) remains the answer only when you need raw Kubernetes APIs, custom operators, DaemonSets, or a service mesh you control — with the operational burden that implies. The decision heuristic: registry → ACR always; quick single container → ACI; microservices/APIs/event workers → Container Apps; "we need actual Kubernetes" → AKS.

  • ACR — private registry + cloud-side az acr build + Tasks (rebuild on base-image update); auth via managed identity, not passwords.
  • ACI — a container (or container group) in seconds, per-second billing; no orchestration, no autoscale, no rolling deploys.
  • Container Apps — managed K8s+KEDA underneath: ingress, revisions with traffic splitting, scale rules incl. scale-to-zero.
  • Revision — an immutable snapshot of image+config per deploy; canary = weight traffic across revisions, rollback = shift weight back.
  • AKS — full Kubernetes when you need its API surface; you own upgrades, node pools, and the complexity (see the K8s track).

Source → cloud build → running app

# build IN ACR (no local docker) az acr build -r acrshop \ -t shop-api:v2 . # run it as a Container App az containerapp update -n shop-api \ -g rg-shop \ --image acrshop.azurecr.io/shop-api:v2

AWS comparison

ACR ≈ ECR (plus in-cloud builds ≈ CodeBuild folded in). ACI ≈ Fargate run-task — serverless containers without a service definition. Container Apps ≈ App Runner (HTTP apps) plus ECS-on-Fargate's scaling, with KEDA event scalers that AWS has no direct twin for. AKS ≈ EKS. The project's own deploy uses this ladder — see deploy/azure/containerapp.bicep and aws-ecs-visualizer.html for the AWS side.

Spring Boot comparison

Your multi-stage backend/Dockerfile already produces the image; the only question is where it runs. On Container Apps, Boot's /actuator/health maps to startup/liveness/readiness probes, env vars come from ACA secrets/config, and a queue-depth KEDA rule can scale your @RabbitListener worker from 0 to N — the listener code is identical, the fleet size becomes the platform's job.

CIAM in production: the registry pull is an identity problem: give the Container App (or AKS kubelet) a managed identity with the AcrPull role instead of admin username/password — the image pull is then authorized by Entra, auditable, and secret-free. Same story for the app reaching Key Vault or Service Bus at runtime. In your ADO pipelines, az acr build + workload identity federation means the whole build-push-deploy chain runs without a single stored credential.

1. ACR: the registry that also builds

# create the registry (Basic/Standard/Premium tiers)
az acr create -n acrshop -g rg-shop --sku Standard

# build IN the cloud from local source — no docker daemon needed
az acr build --registry acrshop --image shop-api:v2 .

# an ACR Task: rebuild automatically when the base image is patched
az acr task create -n rebuild-on-base --registry acrshop \
  --image shop-api:{{'{{'}}.Run.ID{{'}}'}} --file Dockerfile \
  --context https://github.com/bob/shop.git --base-image-trigger-enabled true
az acr build is the CI shortcut. It tars your build context, uploads it, and runs the Docker build on ACR's own compute — your laptop or pipeline agent never needs Docker installed. The base-image trigger is the exam-favorite feature: when eclipse-temurin:21-jre publishes a security patch, the Task rebuilds your image automatically, so you inherit fixes instead of shipping stale layers. Authentication for pulls should be a managed identity with AcrPull — the "admin user" toggle is for demos only.

2. Picking the runtime: ACI vs Container Apps vs AKS

# ACI — one container, running in ~10s, per-second billing
az container create -g rg-shop -n nightly-report \
  --image acrshop.azurecr.io/report-job:v1 --restart-policy Never \
  --assign-identity --cpu 2 --memory 4

# Container Apps — ingress + revisions + scale rules
az containerapp create -n shop-api -g rg-shop \
  --environment env-shop --image acrshop.azurecr.io/shop-api:v1 \
  --ingress external --target-port 8080 \
  --min-replicas 0 --max-replicas 10
Match the workload, not the hype. ACI: run-to-completion jobs, build agents, "give me a shell in the VNet now" — no scaling or routing, and a container group is the multi-container unit (sidecar + app sharing localhost). Container Apps: HTTP APIs and event-driven workers that want revisions, TLS ingress, and scale-to-zero. AKS: you need CRDs, operators, Helm charts you control, or cluster-level agents. AZ-204 phrases it as "minimum management effort" — that phrase almost always points at ACI (single container) or Container Apps (microservices).

3. Revisions: immutable deploys and traffic splitting

# deploy v2 → creates revision shop-api--v2 alongside v1
az containerapp update -n shop-api -g rg-shop --image acrshop.azurecr.io/shop-api:v2

# canary: 90% of traffic to v1, 10% to v2
az containerapp ingress traffic set -n shop-api -g rg-shop \
  --revision-weight shop-api--v1=90 shop-api--v2=10

# confident? shift fully; regret? shift back — v1 never stopped existing
az containerapp ingress traffic set -n shop-api -g rg-shop \
  --revision-weight shop-api--v2=100
A revision is a snapshot, not a deployment event. Image + env vars + scale rules are frozen into an immutable, named revision on every "revision-scope" change. In multiple-revision mode old and new run side by side and the ingress splits traffic by weight — the same blue/green idea as App Service slots (azure-app-service-visualizer.html), but with percentage canaries instead of an all-at-once swap. Rollback is a weight change, which is why it takes seconds.
