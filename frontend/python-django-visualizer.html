Django — MVT, the ORM & the Request Cycle

"Batteries included": Django ships an ORM, an admin panel, auth, forms, and migrations out of the box. Its shape is Model-View-Template, a request flows through a middleware stack to a view, and the ORM turns Python into SQL — great for content-heavy apps and fast delivery.

🟩 What is Django — and what does "batteries included" actually give you?

Django is Python's high-level, opinionated web framework. Where Flask hands you a microframework and lets you assemble the rest, Django ships the whole stack: a powerful ORM, an auto-generated admin panel, auth, forms, migrations, templating, and security middleware — all conventionally wired. Its architecture is MVT (Model-View-Template), which is just MVC with different names: the Model is your data (ORM classes), the View is the function/class that handles a request (what most frameworks call a controller), and the Template renders HTML. A request flows through the URLconf (regex/path routing) and a middleware stack (security, sessions, auth, CSRF) to the view, which queries models via the ORM and returns an HttpResponse — often a rendered template, or JSON via Django REST Framework. The ORM's QuerySet is lazy: you build it up and it hits the database only when evaluated. Django optimizes for getting a robust, secure, content-driven app shipped fast.

  • MVT = Model (ORM) · View (the handler) · Template (HTML) — MVC renamed.
  • Batteries included — ORM, admin, auth, forms, migrations, CSRF out of the box.
  • Request cycle — URLconf → middleware stack → view → response.
  • Lazy QuerySets — composed in Python, executed as SQL only when evaluated.

Spring Boot comparison

Django's view ≈ a Spring @Controller handler. The URLconf ≈ @RequestMapping routing. The ORM ≈ Spring Data JPA/Hibernate — objects.filter() ≈ a derived query, select_related ≈ JOIN FETCH, and the N+1 problem is identical. Middleware ≈ the Servlet filter chain. Migrations ≈ Flyway/Liquibase but generated from models. Django REST Framework serializers ≈ Spring DTOs + Jackson + Bean Validation. The big philosophical difference: Django bundles the admin, auth, and ORM as one opinionated whole, where Spring Boot composes starters.

CIAM with Django: Django's bundled auth (sessions, users, permissions) suits a server-rendered portal, but for a token-based API you reach for Django REST Framework with a JWT auth class that validates the Ping/Entra bearer token, plus permission classes (≈ @PreAuthorize) gating viewsets. The middleware stack is where session/CSRF protection lives for the browser-facing parts; the DRF authentication/permission layer is where bearer-token APIs are secured. The auto admin is a fast way to build internal identity-ops tooling (manage users, inspect consents) with near-zero code.

1. MVT is MVC, renamed

# Django's names vs the classic MVC names
Model → the data layer (ORM classes) # same as MVC Model
View → the request handler (your function) # MVC's CONTROLLER
Template → the HTML renderer # MVC's VIEW
# Django calls the framework itself "the controller" that wires it together.
Don't let the naming trip you. A Django "view" is what Spring calls a controller method — it receives the request and returns a response. The "template" is the HTML view. So MVT maps cleanly to a Spring @Controller returning a Thymeleaf template (server-rendered) or a @RestController returning JSON (via DRF).

2. Class-based views & DRF

# Django REST Framework — a full CRUD API in a few lines
class ArticleSerializer(serializers.ModelSerializer):
  class Meta: model = Article; fields = ["id", "title", "body"]

class ArticleViewSet(viewsets.ModelViewSet):
  queryset = Article.objects.all()
  serializer_class = ArticleSerializer
  permission_classes = [IsAuthenticated] # ≈ @PreAuthorize

A ModelViewSet auto-generates list/create/retrieve/update/delete endpoints. The serializer validates input and shapes output — Django's answer to a DTO + Bean Validation + Jackson.
