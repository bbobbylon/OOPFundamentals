React: Testing (RTL + Vitest)

Testing components the way users use them: render, query by accessible role, interact with userEvent, assert on the DOM, and mock the network with MSW — on the Vitest runner.

🧪 Test behavior, not implementation — the React Testing Library philosophy

React Testing Library follows one rule: "the more your tests resemble how the software is used, the more confidence they give." So you render to a real DOM (jsdom), query it like a user/screen-reader would (by accessible role, label, or text — not CSS classes), interact via userEvent (real event sequences), and assert on the document. Three query families: getBy* (throws — must exist now), queryBy* (null — assert absence), findBy* (retrying promise — appears after async). Prefer getByRole (doubles as an a11y check) over test IDs. Vitest is the Vite-native, Jest-compatible runner; MSW intercepts requests at the network layer so real fetch code runs against a fake API. Result: tests that survive refactors and catch real regressions.

  • Render → query → interact → assert — exercise what the user sees.
  • Query by role/label/text — not classes; getByRole is also an a11y check.
  • getBy/queryBy/findBy — exists now / asserts absence / async-appears.
  • Vitest + MSW — Jest-compatible runner; network-layer mocking, real fetch runs.

A complete test

import { render, screen } from '@testing-library/react' import userEvent from '@testing-library/user-event' test('submits the form', async () => { render(<LoginForm onSubmit={fn} />) await userEvent.type( screen.getByLabelText(/username/i), 'demo') await userEvent.click( screen.getByRole('button', {name:/sign in/i})) expect(fn).toHaveBeenCalledWith( { username:'demo', ... }) })

getBy / queryBy / findBy

// must exist NOW (throws if missing): screen.getByRole('button') // assert ABSENCE (returns null): expect(screen.queryByText('Error')) .not.toBeInTheDocument() // appears LATER (retries, async): await screen.findByText('Welcome')

RTL vs Enzyme / Angular TestBed

Enzyme (legacy): wrapper.state(), .instance() — couples tests to internals. RTL: query the rendered DOM by role/text — refactor-proof. Angular: TestBed.configureTestingModule + fixture.debugElement; Angular Testing Library wraps it with the same RTL philosophy. Same idea everywhere: assert on output, not implementation.

CIAM context: Test the login form by typing credentials and clicking submit, then asserting the token was stored / the user redirected — the real journey. For role-gated UI, render as an admin and assert getByRole('link', {name:/users/i}) exists, then render as a normal user and assert queryBy…not.toBeInTheDocument(). Use MSW to stub POST /api/auth/login so the component's real fetch runs without a backend — and add a 401 handler to cover the error path.

1. Render & Query Like a User

import { render, screen } from '@testing-library/react'

render(<Greeting name="Bobby" />)

// query the rendered DOM by accessible role/text
screen.getByRole('heading', { name: /hello, bobby/i })
screen.getByText(/welcome/i)

render mounts the component into jsdom; screen queries that document. Prefer queries a user/AT can perceive — role (button, heading, link, textbox), then label, then visible text. Using getByRole is a free accessibility assertion: if the element has no role (a clickable <div>), the query fails and tells you the component isn't accessible.

Query priority (highest first): getByRole → getByLabelText (forms) → getByPlaceholderText → getByText → … → getByTestId (last resort). Reaching for data-testid first is a smell — it means the test (and often the UI) is bypassing the accessibility tree.

2. getBy / queryBy / findBy

FamilyFoundNot foundUse for
getBy*elementthrowssomething that must be present now
queryBy*elementnullasserting absence (not.toBeInTheDocument())
findBy*Promise→elementrejects after timeoutappears after an async update (await it)
*AllBy*arrayper familymultiple matches (lists)
Match the family to intent. Using getBy to check absence throws instead of failing cleanly — use queryBy. Using getBy for something async fails because it doesn't wait — use findBy (it polls until the element appears or times out, wrapping the change in act for you).

3. userEvent (not fireEvent)

import userEvent from '@testing-library/user-event'

test('login', async () => {
  const user = userEvent.setup()
  render(<LoginForm />)
  await user.type(screen.getByLabelText(/user/i), 'demo')
  await user.click(screen.getByRole('button'))
})

userEvent (v14+) simulates a real interaction — a click is pointerdown → focus → pointerup → click; typing fires keydown/keyup per character and respects disabled/readonly. It's async (always await). The older fireEvent.click dispatches a single synthetic event and skips the realistic sequence — fine for low-level cases, but userEvent catches bugs fireEvent misses (e.g. a disabled button that shouldn't click).

The "not wrapped in act(...)" warning means a state update happened outside React's awareness — almost always a missing await on a userEvent or findBy. Await them and it disappears; you rarely need to call act() yourself.

4. Mocking: Modules, Functions & the Network (MSW)

// Vitest: mock a function / module
const onSubmit = vi.fn()
vi.mock('./analytics', () => ({ track: vi.fn() }))

// MSW: intercept the real network call
server.use(
  http.post('/api/auth/login', () =>
    HttpResponse.json({ token: 'fake.jwt', roles: ['ROLE_USER'] }))
)
// the component's real fetch() runs against this fake
ToolUse
vi.fn()a spy/stub — assert toHaveBeenCalledWith(...) (e.g. an onSubmit prop)
vi.mock('module')replace a whole module (analytics, a hook, a service)
MSW (setupServer)intercept HTTP at the network layer — don't stub fetch by hand
@testing-library/jest-dommatchers: toBeInTheDocument, toHaveValue, toBeDisabled, toHaveTextContent
Prefer MSW over mocking fetch. Hand-stubbing global.fetch couples the test to how the component calls the network. MSW intercepts the actual request, so the component's real data layer (TanStack Query, an interceptor, retries) runs unchanged — you test the integration, and the same handlers can power local dev and Storybook. Vitest needs environment: 'jsdom' and a setup file that imports jest-dom + starts the MSW server.
