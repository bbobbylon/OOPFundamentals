PHP Fundamentals & the Request Model

PHP's defining trait is shared-nothing: every request starts a fresh script with a clean slate and tears it all down at the end. That model — plus modern PHP 8's types, and Composer's PSR-4 autoloading — is what makes Laravel tick.

🐘 What makes PHP different — and why does "shared-nothing" matter?

PHP powers a huge share of the web (WordPress, Laravel, much of the LAMP stack). Its defining characteristic is the shared-nothing, request-per-script execution model: unlike a long-running Node or Java process, each HTTP request spins up a fresh PHP execution, runs your code from a clean global state, sends the response, and throws everything away. There are no leftover variables between requests — which makes PHP famously easy to reason about and hard to leak memory in, at the cost of re-bootstrapping per request (mitigated by opcode caching and modern long-lived runtimes like Swoole/FrankenPHP). Modern PHP 8 is a different language from its reputation: it has scalar and union type declarations, enums, readonly properties, named arguments, constructor property promotion, attributes (annotations), the nullsafe operator, and a JIT. PHP's one quirky workhorse is the array — an ordered hash map that serves as both list and dictionary. Code is organized with namespaces and loaded by Composer via PSR-4 autoloading (class name → file path), the same dependency-management role as Maven/npm.

  • Shared-nothing — fresh state per request; nothing persists between requests in-process.
  • Modern PHP 8 — typed properties, enums, readonly, attributes, JIT — not the PHP of 2010.
  • Arrays are ordered maps — list and dictionary in one structure.
  • Composer + PSR-4 — dependency manager + class autoloading (≈ Maven/npm).

Java / Spring comparison

The shared-nothing model is the opposite of a Spring app's long-lived JVM with singleton beans — PHP rebuilds the world per request, so "application state" lives in a cache/DB, not in memory. Composer ≈ Maven (with composer.json ≈ pom.xml) and PSR-4 ≈ the package→folder convention. PHP 8 attributes (#[Route("/x")]) ≈ Java annotations. Typed properties + enums + readonly bring PHP close to Java's type discipline. Namespaces ≈ packages. The big mental shift: there is no persistent in-process container — each request is a clean boot.

CIAM with PHP: Shared-nothing is actually friendly to stateless JWT auth — there is no in-memory session to manage, so each request independently verifies the Ping/Entra bearer token and builds the user context from scratch (the token IS the state). Laravel's middleware verifies the JWT per request and attaches the user; because nothing persists between requests, there is no risk of identity bleed across requests. State that must survive (sessions, rate-limit counters) goes to Redis or the database, exactly where a stateless model wants it.

The problem

You cache the logged-in user in a static property so you don't have to pass it through six function calls. On php-fpm that's completely harmless. On Laravel Octane, it just handed User B a piece of User A's identity.

Your "obviously safe" static cache leaks one user into another user's request

On classic php-fpm you write a tiny helper: class AuthContext { private static ?User $current = null; public static function set(User $u): void { self::$current = $u; } public static function user(): ?User { return self::$current; } }. Middleware verifies the JWT, calls AuthContext::set($user) once, and the rest of the request reads AuthContext::user() from anywhere — controllers, views, logging — without threading it through every function. Section 1 above says "no state survives a request." A static property is memory, and memory gets freed at teardown. This looks obviously safe.

JWT verification logic ✓ middleware order ✓ assumption that a static property can't outlive a request ⚠

"Shared-nothing" describes php-fpm's process model, not a guarantee the PHP language enforces — swap the runtime and the guarantee goes with it.

Worker handles Request A JWT verified → AuthContext::$current = User A
Request A completes response sent → php-fpm destroys the process · Octane keeps the worker alive, memory intact
Same worker handles Request B next request lands here → php-fpm: fresh AuthContext (null) · Octane: AuthContext still = User A

The first transition looks identical on both runtimes — a request comes in, state gets set. The second transition is where they diverge, and it's completely invisible from inside the request that triggers it: nothing in Request A's code path knows or cares whether its process is about to die or keep going.

14:02:00.000 — Request A lands on a warm Octane worker; middleware verifies User A's JWT ↓ 8ms later, still inside the same request 14:02:00.008 — AuthContext::set($userA) runs — the static property now holds User A ↓ the rest of Request A reads it correctly, then the response goes out 14:02:00.031 — Request A's response is sent. On php-fpm this worker dies HERE — on Octane it just keeps running, AuthContext::$current still set to User A ↓ 2ms later, a different user entirely 14:02:00.033 — Request B lands on that SAME warm worker, from User B — but a logging middleware reads AuthContext::user() before Request B's own set() call has run yet ↓ 2ms later still 14:02:00.035 — Request B's own set($userB) finally executes and overwrites the property — too late for the log line that already ran under User A's identity, for User B's request

Rung three is the one to stare at. It is not "sometimes wrong" — it is deterministically correct for every request on php-fpm and deterministically leaky for the handful of milliseconds between two requests landing on the same warm Octane worker. That window is real, it is small, and it is exactly the kind of gap a local dev box never has a second request to fall into.

Read rungs two and four together. Same class, same static property, same line of code — the only variable is which runtime is holding the process when the next request happens to land.
Never let per-request identity live in a static or global
  1. Pass request-scoped values explicitly, not through staticsrebuilt every request
  2. Use your framework's request-scoped container if it has one — Laravel's service container can bind an object as request-scoped instead of process-scopedOctane-aware binding
  3. Test under the real worker runtime before trusting shared-nothing at all — this class of bug is invisible on a local php-fpm dev box, and only shows up once two users' requests can land on the same warm workertest under Octane
The one-sentence rule. "Shared-nothing" is a promise your deployment model makes, not one the PHP language enforces — a static property is just memory, and memory survives for exactly as long as the process holding it does, whether that's php-fpm's one-process-per-request or Swoole's one-process-for-thousands.
A hotel room stripped and remade after every guest is "shared-nothing" by policy, not by any law of physics — leave a note under the mattress and the next guest finds it too, the moment housekeeping stops doing its job between stays.

1. The request-per-script lifecycle

// each request, in a worker process (php-fpm):
1. request arrives → a worker picks it up
2. bootstrap: parse/compile (or hit the opcache), init superglobals
3. run your script from a CLEAN global state
4. build & send the response
5. tear down: free ALL memory; nothing carries to the next request
No state survives a request. A static variable, a global, a loaded config — all gone when the request ends. This is why PHP rarely leaks and is easy to reason about, but also why "warm up once, reuse forever" patterns (in-memory caches, connection pools) need an external store (Redis) or a long-lived runtime (Swoole, FrankenPHP). The opcode cache (OPcache) keeps the compiled code so only your data is rebuilt per request.

2. Type declarations (PHP 8)

function discount(float $price, int $pct): float {
  return $price * (1 - $pct / 100);
}

function find(int $id): ?User { ... } // nullable return
function id(int|string $v): string { ... } // union type

PHP is dynamically typed but lets you declare types on parameters, returns, and properties. With declare(strict_types=1) they are enforced strictly — passing the wrong type throws a TypeError, much like Java.
