Java Records & Sealed Classes

Deep Dive into Java 16-21 features: records eliminate boilerplate, sealed classes restrict inheritance, and pattern matching ties them together.

🧾 What are Java records and sealed classes — and how do they kill DTO boilerplate and close hierarchies?

Records (Java 16) kill data-class boilerplate: record User(String name, String email) {} auto-generates the constructor, final fields, accessors, equals/hashCode (by value), and toString — immutable by design, ideal for DTOs, request/response bodies, and event payloads. Sealed classes (Java 17) close an open hierarchy: sealed interface Shape permits Circle, Rectangle {} tells the compiler the complete subtype set, which enables exhaustive pattern-matching switches (Java 21) with no default — add a new permitted type and every switch that misses it fails to compile. Together they're Java's algebraic data types.

  • Records = immutable data in one line — constructor, accessors, value equals/hashCode, toString.
  • Compact constructors validate/normalize — e.g. email = email.toLowerCase().
  • Sealed = a closed subtype set — the compiler knows every permitted type.
  • Sealed + switch = exhaustive — no default; a new subtype breaks the build until handled.
  • Records aren't entities — JPA needs mutability + a no-arg constructor; use records for the DTO layer.

Records — DTO in one line

// Before records: ~20 lines of boilerplate // After records: record UserDTO(String name, String email, List<String> roles) { // Compact constructor for validation: public UserDTO { // no parameter list → canonical params are in scope Objects.requireNonNull(name, "name required"); email = email.toLowerCase(); // can transform components } // Custom method: boolean hasRole(String role) { return roles.contains(role); } } // Automatically generated by the compiler: // - constructor: new UserDTO("Alice", "alice@x.com", List.of("ADMIN")) // - accessors: dto.name(), dto.email(), dto.roles() // - equals(): compares name + email + roles // - hashCode(): combines name + email + roles // - toString(): UserDTO[name=Alice, email=alice@x.com, roles=[ADMIN]] // With Jackson: @JsonSerializable — works out of the box // With Spring: use as @RequestBody or @ResponseBody directly // Records implement equals/hashCode by VALUE not identity

Sealed + pattern matching

// Sealed hierarchy: sealed interface AuthEvent permits LoginSuccess, LoginFailure, TokenExpired, PasswordReset {} record LoginSuccess(String userId, String sessionId) implements AuthEvent {} record LoginFailure(String userId, String reason, int attempts) implements AuthEvent {} record TokenExpired(String tokenId, Instant expiredAt) implements AuthEvent {} record PasswordReset(String userId, Instant resetAt) implements AuthEvent {} // Exhaustive switch (Java 21) — compiler verifies ALL cases covered: String describe(AuthEvent event) { return switch (event) { case LoginSuccess s -> "User " + s.userId() + " logged in"; case LoginFailure f -> "Failed: " + f.reason() + " (attempts: " + f.attempts() + ")"; case TokenExpired t -> "Token " + t.tokenId() + " expired at " + t.expiredAt(); case PasswordReset r -> "Password reset for " + r.userId(); // No default needed — compiler knows AuthEvent is sealed // Add a new permitted subclass → compile error here until handled }; }

Spring Boot + records

// Spring Boot REST with records (clean, modern): record CreateUserRequest(String username, String email, String role) {} record UserResponse(Long id, String username, String email) {} @PostMapping("/users") public ResponseEntity<UserResponse> createUser( @RequestBody @Valid CreateUserRequest req) { User saved = userService.create(req); return ResponseEntity.ok(new UserResponse(saved.getId(), saved.getUsername(), saved.getEmail())); } // Spring @ConfigurationProperties with records (Java 17+): @ConfigurationProperties(prefix = "app.oidc") record OidcConfig(String issuerUri, String clientId, String clientSecret) {} // Binds: app.oidc.issuer-uri, app.oidc.client-id, app.oidc.client-secret // JPA: records can't be @Entity (JPA needs mutable + no-arg constructor) // Use records for the DTO layer ONLY; use regular classes for @Entity

What problem do Records solve?

A huge fraction of Java classes are simple data carriers — objects whose only job is to hold some named values and be passed around. Before Java 16, every such class required a mountain of boilerplate that obscured the actual intent.

Before records — 40 lines of ceremony
public final class Point { private final int x; private final int y; public Point(int x, int y) { this.x = x; this.y = y; } public int x() { return x; } public int y() { return y; } @Override public boolean equals(Object o) { if (this == o) return true; if (!(o instanceof Point)) return false; Point p = (Point) o; return x == p.x && y == p.y; } @Override public int hashCode() { return Objects.hash(x, y); } @Override public String toString() { return "Point[x=" + x + ", y=" + y + "]"; } }
→
With a record — 1 line
public record Point(int x, int y) {} // That's it. Java auto-generates everything. // The compiler produces: // • constructor(int x, int y) // • int x() — component accessor // • int y() — component accessor // • equals() — compares all components // • hashCode() — based on all components // • toString() → "Point[x=1, y=2]" // Usage — identical to the verbose version Point p = new Point(3, 4); p.x() // 3 p.y() // 4 p.toString() // "Point[x=3, y=4]"
Records are transparent data carriers. Their API is their components — everything is derived from the component list. This makes them ideal for DTOs (Data Transfer Objects), query results, configuration bundles, event payloads, and map keys.

Records are implicitly final — inheritance rules

// Records are implicitly final — you cannot extend a record public record Point(int x, int y) {} class Point3D extends Point {} // COMPILE ERROR — records are final // Records CANNOT extend other classes (already extend java.lang.Record) record Foo(int x) extends SomeClass {} // COMPILE ERROR // Records CAN implement interfaces interface Shape { double area(); } record Circle(double radius) implements Shape { @Override public double area() { return Math.PI * radius * radius; } } // Records can implement multiple interfaces record Order(String id, BigDecimal total) implements Comparable<Order>, Serializable { @Override public int compareTo(Order o) { return total.compareTo(o.total); } }

Three kinds of constructors in records

1. Canonical Constructor — matches the component list exactly
record Range(int min, int max) { // Explicit canonical constructor — same params as the record header Range(int min, int max) { if (min > max) throw new IllegalArgumentException("min > max"); this.min = min; this.max = max; } } // You manually assign this.min and this.max
2. Compact Constructor — cleanest for validation (Java 16+)
record Range(int min, int max) { // Compact constructor — no parameter list, no this.x = x assignments // The compiler inserts the assignments AFTER your code runs Range { if (min > max) throw new IllegalArgumentException("min > max"); min = Math.max(min, 0); // can normalise the parameters here // this.min = min; — automatically injected by compiler here } } // Preferred for validation and normalisation
3. Custom Constructor — must delegate to the canonical constructor
record Range(int min, int max) { // Convenience constructor — different parameter list Range(int size) { this(0, size); // must call the canonical constructor first } } var r = new Range(10); // Range[min=0, max=10]

Compact constructor — normalisation and defensive copies

// Compact constructor is ideal for making defensive copies of mutable components record DataPoint(String name, int[] values) { DataPoint { Objects.requireNonNull(name, "name must not be null"); if (name.isBlank()) throw new IllegalArgumentException("name is blank"); values = values.clone(); // defensive copy — record is not fully immutable otherwise // this.values = values.clone() — compiler inserts this.values = values at the end } } int[] raw = {1, 2, 3}; DataPoint dp = new DataPoint("sensor1", raw); raw[0] = 99; // does NOT affect dp.values() — copy was made dp.values()[0] // still 1
Records are "shallowly immutable" by default. The component references cannot be reassigned (the fields are final), but if the component is a mutable object (array, List, Date), the object itself can be mutated. Use defensive copies in the compact constructor to achieve true immutability.

Adding custom methods to records

record Money(BigDecimal amount, Currency currency) { // Compact constructor for validation Money { Objects.requireNonNull(amount); Objects.requireNonNull(currency); if (amount.compareTo(BigDecimal.ZERO) < 0) throw new IllegalArgumentException("Amount cannot be negative"); } // Static factory — cleaner API than new static Money of(double amount, String currency) { return new Money(BigDecimal.valueOf(amount), Currency.getInstance(currency)); } // Instance methods — add computed behaviour Money add(Money other) { if (!currency.equals(other.currency)) throw new IllegalArgumentException("Currency mismatch"); return new Money(amount.add(other.amount), currency); // return new record } Money multiply(double factor) { return new Money(amount.multiply(BigDecimal.valueOf(factor)), currency); } boolean isZero() { return amount.compareTo(BigDecimal.ZERO) == 0; } // Override the auto-generated toString @Override public String toString() { return currency + " " + amount.toPlainString(); } } Money.of(10.00, "USD").add(Money.of(5.50, "USD")); // USD 15.50

Local records (Java 16+) and generic records

// Local record — declared inside a method void processStats(List<Integer> values) { record Stats(int min, int max, double avg) {} // only visible in this method IntSummaryStatistics s = values.stream().mapToInt(Integer::intValue).summaryStatistics(); Stats stats = new Stats(s.getMin(), s.getMax(), s.getAverage()); System.out.println(stats); // Stats[min=1, max=10, avg=5.5] } // Generic record — type parameter in the component list record Pair<A, B>(A first, B second) { static <X,Y> Pair<X,Y> of(X x, Y y) { return new Pair<>(x, y); } Pair<B,A> swapped() { return new Pair<>(second, first); } } Pair<String,Integer> p = Pair.of("hello", 42); p.first() // "hello" p.swapped() // Pair[first=42, second=hello]

Records vs Lombok @Data — when to use which

Java Records
record User(String name, int age) {} // Pros: // + Part of the language — no annotation processing // + Works with reflection/serialization transparently // + JVM-native: pattern matching, instanceof // + Immutable by design // + Supported in all Java 16+ tooling natively // + No extra build dependency // Cons: // - No setters (immutable only) // - No inheritance // - Accessors named x() not getX() // - No @Builder out of the box
Lombok @Data
@Data public class User { private String name; private int age; } // Pros: // + Generates getters AND setters // + @Builder for builder pattern // + Works with existing frameworks expecting // getX() naming (e.g. older Jackson configs) // + Can extend other classes // + Mutable by default // Cons: // - Annotation processor — build tooling overhead // - IDE needs Lombok plugin // - Mutability often leads to bugs // - Pattern matching doesn't recognise it
Decision guide:
Use records when: the object is a pure data carrier, immutability is desired, you're writing new Java 16+ code, or you want pattern matching support.
Use Lombok when: you need mutable state with setters, you're in an older codebase, you need @Builder, or frameworks require getX() naming.
Use neither when: the class has real behaviour — then proper OOP with explicit methods is clearer.

Sealed Classes (Java 17) — restricting inheritance

A sealed class (or interface) declares the complete, exhaustive set of its permitted subclasses. No other class can extend or implement it. This makes the compiler aware of every possible subtype, enabling exhaustiveness checks in pattern matching.

// Sealed class hierarchy for geometric shapes public sealed class Shape permits Circle, Rectangle, Triangle {} // Every permitted subclass must be in the same package (or named module) // and must use one of: final, sealed, or non-sealed public final class Circle extends Shape { private final double radius; // ... final means no further extension } public sealed class Rectangle extends Shape permits Square { // Rectangle is itself sealed — restricts further private final double width, height; } public final class Square extends Rectangle { ... } public non-sealed class Triangle extends Shape { // non-sealed: anyone can extend Triangle // "I know there are subtypes I don't control — that's intentional" }
Why would you use non-sealed? When you control part of the hierarchy (sealed) but want to allow extension at a specific point. Example: sealed HttpResponse permits SuccessResponse, ErrorResponse, where non-sealed ErrorResponse allows library users to create domain-specific error types.

Sealed interfaces — for algebraic data types

// Sealed interfaces work exactly like sealed classes // Records are an excellent fit for the leaf nodes public sealed interface JsonValue permits JsonNull, JsonBool, JsonNumber, JsonString, JsonArray, JsonObject {} public record JsonNull() implements JsonValue {} public record JsonBool(boolean value) implements JsonValue {} public record JsonNumber(double value) implements JsonValue {} public record JsonString(String value) implements JsonValue {} public record JsonArray(List<JsonValue> elements) implements JsonValue {} public record JsonObject(Map<String,JsonValue> map) implements JsonValue {} // Every possible JSON value type is now captured in a type-safe hierarchy

The sealed → permits → final/sealed/non-sealed chain

// Rule: every permitted subclass must declare exactly one of these modifiers: // 1. final — no further subclassing (most common) public final class Circle extends Shape {} // 2. sealed — extends hierarchy but still controls who can extend it public sealed class Quadrilateral extends Shape permits Square, Rectangle, Trapezoid {} // 3. non-sealed — opens the hierarchy back up public non-sealed class CustomShape extends Shape {} class Hexagon extends CustomShape {} // allowed class Octagon extends CustomShape {} // allowed // Record classes are implicitly final — perfect leaf nodes for sealed hierarchies public record Circle(double radius) implements Shape {} // final implicitly
The permits clause is optional when subclasses are in the same source file. The compiler can infer the permitted subtypes if they are all defined in the same .java file as the sealed class. In separate files, the permits clause is required.

Same-file inference — permits can be omitted

// Shape.java — all subtypes in one file, no permits needed sealed interface Expr {} // no permits — inferred from below record Num(int value) implements Expr {} record Add(Expr left, Expr right) implements Expr {} record Mul(Expr left, Expr right) implements Expr {} record Neg(Expr expr) implements Expr {} // Evaluate expression tree static int eval(Expr e) { return switch (e) { case Num(var v) -> v; case Add(var l, var r) -> eval(l) + eval(r); case Mul(var l, var r) -> eval(l) * eval(r); case Neg(var expr) -> -eval(expr); }; // No default needed — compiler knows all cases }

Pattern Matching for switch — exhaustiveness with sealed types

Pattern matching for switch (Java 21, finalized) combined with sealed types is where these features pay off most. The compiler can verify that all sealed subtypes are handled — no default needed, and forgetting a case is a compile error.

// Sealed Shape hierarchy sealed interface Shape permits Circle, Rectangle, Triangle {} record Circle(double radius) implements Shape {} record Rectangle(double w, double h) implements Shape {} record Triangle(double base, double h) implements Shape {} // Pattern matching switch — exhaustive static double area(Shape shape) { return switch (shape) { case Circle c -> Math.PI * c.radius() * c.radius(); case Rectangle r -> r.w() * r.h(); case Triangle t -> 0.5 * t.base() * t.h(); // No default needed! Compiler verifies all sealed subtypes are covered. // If you add a new permitted type, THIS CODE WON'T COMPILE until you add a case. }; } // Deconstruction patterns (Java 21) — unpack record components directly static String describe(Shape shape) { return switch (shape) { case Circle(double r) -> "Circle with radius " + r; case Rectangle(double w, double h) -> w + "x" + h + " rectangle"; case Triangle(double b, double h) -> "Triangle base=" + b + " h=" + h; }; }
Guard patterns (when clause): You can add conditions to a case: case Circle c when c.radius() > 0 → .... Guards allow fine-grained matching without nesting if statements.

Guarded patterns and null handling

// Guarded patterns — add a when clause to refine a case static String classify(Shape shape) { return switch (shape) { case Circle c when c.radius() < 1 -> "tiny circle"; case Circle c when c.radius() < 10 -> "small circle"; case Circle c -> "large circle"; case Rectangle r when r.w() == r.h() -> "square (special rectangle)"; case Rectangle r -> "rectangle"; case Triangle t -> "triangle"; }; } // Null handling in pattern switch (Java 21) static String safe(Shape shape) { return switch (shape) { case null -> "no shape"; // explicit null case case Circle c -> "circle"; case Rectangle r -> "rectangle"; case Triangle t -> "triangle"; }; }

Real-world sealed class: Result<T> — typed error handling

// A type-safe Result type — no exceptions for expected failures public sealed interface Result<T> permits Result.Success, Result.Failure { record Success<T>(T value) implements Result<T> {} record Failure<T>(String error, Throwable cause) implements Result<T> { Failure(String error) { this(error, null); } } static <T> Result<T> of(Supplier<T> supplier) { try { return new Success<>(supplier.get()); } catch (Exception e) { return new Failure<>(e.getMessage(), e); } } } // Usage — caller must handle both cases Result<User> result = Result.of(() -> userRepo.findById(id)); switch (result) { case Result.Success<User>(var user) -> render(user); case Result.Failure<User>(var err, var cause) -> showError(err); } // exhaustive — no default needed

Real-world: HTTP response modeling

public sealed interface ApiResponse<T> permits ApiResponse.Ok, ApiResponse.NotFound, ApiResponse.Unauthorized, ApiResponse.ServerError { record Ok<T>(T body) implements ApiResponse<T> {} record NotFound<T>(String resource) implements ApiResponse<T> {} record Unauthorized<T>(String realm) implements ApiResponse<T> {} record ServerError<T>(Throwable cause) implements ApiResponse<T> {} } // Dispatch — clean, exhaustive, compiler-verified static ResponseEntity<?> toHttp(ApiResponse<?> resp) { return switch (resp) { case ApiResponse.Ok(var b) -> ResponseEntity.ok(b); case ApiResponse.NotFound(var r) -> ResponseEntity.notFound().build(); case ApiResponse.Unauthorized(var realm) -> ResponseEntity.status(401).build(); case ApiResponse.ServerError(var e) -> ResponseEntity.internalServerError().build(); }; }

Data-oriented programming: Records + Sealed + Pattern Matching

These three features are designed to work together. This is Java's answer to algebraic data types and functional-style data modeling.

// The trio in action: a simple arithmetic expression evaluator // 1. SEALED — define the closed set of node types sealed interface Expr permits Literal, Variable, Add, Mul, Neg, IfPos {} // 2. RECORDS — each node is an immutable data carrier record Literal(double value) implements Expr {} record Variable(String name) implements Expr {} record Add(Expr left, Expr right) implements Expr {} record Mul(Expr left, Expr right) implements Expr {} record Neg(Expr expr) implements Expr {} record IfPos(Expr cond, Expr then, Expr orElse) implements Expr {} // 3. PATTERN MATCHING — process the tree exhaustively static double eval(Expr e, Map<String, Double> vars) { return switch (e) { case Literal(var v) -> v; case Variable(var n) -> vars.getOrDefault(n, 0.0); case Add(var l, var r) -> eval(l, vars) + eval(r, vars); case Mul(var l, var r) -> eval(l, vars) * eval(r, vars); case Neg(var ex) -> -eval(ex, vars); case IfPos(var c, var t, var f) -> eval(c, vars) > 0 ? eval(t, vars) : eval(f, vars); }; } // Build the expression: (x + 2) * -y Expr expr = new Mul(new Add(new Variable("x"), new Literal(2)), new Neg(new Variable("y"))); eval(expr, Map.of("x", 3.0, "y", 4.0)); // (3+2) * -4 = -20.0
The key insight: Each "operation" (eval, print, simplify, optimize) is one function with a pattern switch. Adding a new operation is a one-function change. Compare with the classic OOP Visitor pattern — the same expressiveness with a fraction of the code.

🌱 New here? A record is a one-line immutable data class.

When a class exists just to hold data, writing the constructor, getters, equals, hashCode, and toString by hand is tedious and error-prone. A record generates all of it from one line: record Point(int x, int y) {} gives you new Point(1,2), accessors x()/y(), value-based equality, and a readable toString — and the object is immutable. Use records for plain data carriers: DTOs, value objects, coordinates, results. A sealed type is the companion idea: sealed interface Shape permits Circle, Square says "these are the only shapes," so the set of subtypes is closed and known to the compiler.

🧠 Expert corner — algebraic data types & exhaustive switches

  • Records are final & immutable; their components are the canonical state. Add a compact canonical constructor to validate or normalize (if (x < 0) throw ...). They can implement interfaces, just not extend classes.
  • Free correct equals/hashCode make records excellent Map keys and Set elements — no more "I forgot to override hashCode" bugs.
  • Sealed + records = algebraic data types. Model a closed set of variants as records under a sealed interface — the idiomatic Java way to express "one of these shapes."
  • Exhaustive switches. Pattern-matching switch over a sealed type needs no default — and if you add a new permitted subtype later, every switch that forgot it becomes a compile error. The compiler maintains your branches.
  • CIAM tie-in. Model an auth result as sealed interface AuthResult permits Success, MfaRequired, Denied with records for each — callers must handle every case, and impossible states can't be constructed. (The TypeScript mirror is a discriminated union.)
