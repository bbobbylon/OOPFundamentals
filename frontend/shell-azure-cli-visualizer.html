The Azure CLI

or, az: the two letters between you and your whole Entra tenant

>_

The Azure portal has a thousand blades. What if the ten things you actually do were each one typed line — including the Entra app registrations you manage at work?

The idea

Groups of groups of commands — say the resource, then the verb.

az organizes Microsoft's entire cloud as a sentence: az webapp create, az keyvault secret show, az ad app list — a group (what kind of thing), sometimes a subgroup, then a verb (what to do to it). Once that grammar clicks, you can guess commands you've never seen: storage account? Probably az storage account create. It is. Unlike the portal, every one of these lines can live in a script, a pipeline, or your shell history — which is where repeatable work belongs.

You

az account show

Azure

You're bobby@…, in the DevHub-Prod subscription, tenant contoso.onmicrosoft.com. Careful in here.

Anatomy of an az command

Group, verb, and the two parameters nearly everything needs.

the program

az fronts every Azure service and your Entra tenant. It holds a login session (tokens in ~/.azure), so unlike AWS's keys-in-a-file model, you sign in like a person and the tokens refresh themselves.

the group

webapp is the kind of resource. Groups nest: az keyvault secret, az ad app, az storage account. Each level answers --help with what's inside it.

the verb

create, list, show, delete, update — the same five verbs across almost every group. show is one item, list is all of them: the pair you'll type most.

the name

--name (short -n) identifies which resource. For webapps it must be globally unique — it becomes devhub-api.azurewebsites.net.

the resource group

--resource-group (short -g) is the folder every Azure resource lives in — billing, permissions, and deletion happen at this level. Tired of typing it? az config set defaults.group=rg-devhub makes it implicit.

You need details of ONE Entra app registration. Which line?

show is the "one item, in full" verb, across every group — az ad app is the group for app registrations, so group + verb reads like the sentence you meant.

list is the "all of them" verb. It can filter, but the idiomatic one-item command is show.

There's no entra group (the Entra rebrand kept the CLI's historical ad prefix), and az's read-one verb is show, not get.

The reference

The commands that cover a working week.

Session & subscriptions
az loginBrowser (or device-code) sign-in; tokens cached in ~/.azure.
az account showWho am I, which subscription, which tenant — the az whoami.
az account set -s <sub>Switch subscriptions. Everything after targets the new one.
Resources
az group createMake the folder first — every resource needs a group.
az webapp upCreate plan + app + deploy your code, one command.
az webapp log tailLive application logs in your terminal — Azure's tail -f.
az group delete -n rg-xDeletes the group and everything in it. The cleanup — and the footgun.
Identity (your CIAM day job)
az ad app listEvery app registration in the tenant.
az ad sp showA service principal — the app's identity in the tenant.
az keyvault secret showRead a secret at deploy time — never hardcode it.
az role assignment listWho can do what, on what scope. RBAC, enumerated.

A teammate ran one cleanup command and the whole staging environment vanished. Which was it?

That removes one web app — painful, but the databases, storage, and vault in the environment would still exist.

account set just switches which subscription later commands target. It destroys nothing.

A resource group is the container for an entire environment — deleting it takes every resource inside with it, and --yes skips the confirmation. Powerful for teardown, catastrophic on the wrong name.

Put it together

Audit an OAuth client like it's Tuesday — predict each output before you reveal it.

Confirm the tenant

Identity work in the wrong tenant is a bad day. account show tells you which directory your commands will hit.

$ az account show --query "{sub:name, tenant:tenantId}" -o table
Sub          Tenant
-----------  ------------------------------------
DevHub-Prod  72f988bf-86f1-41af-91ab-2d7cd011db47
Find the app registration

Filter server-side with --filter (OData) instead of pulling the whole tenant's app list and grepping it.

$ az ad app list --filter "displayName eq 'devhub-web'" --query "[].{name:displayName, appId:appId}" -o table
Name        AppId
----------  ------------------------------------
devhub-web  a1b2c3d4-e5f6-7890-abcd-ef1234567890
Check its redirect URIs

The classic OAuth bug: the app is redirecting somewhere that isn't registered. One show settles it.

$ az ad app show --id a1b2c3d4-e5f6-7890-abcd-ef1234567890 --query "web.redirectUris"
[
  "https://devhub.example.com/auth/callback",
  "http://localhost:4200/auth/callback"
]
Rotate the client secret — without ever seeing the old one

Reset issues a fresh credential; the response is the only time Azure will show it, so pipe it straight into Key Vault, not into your scrollback.

$ az ad app credential reset --id a1b2c3d4-… --display-name rotated-2026-09 --query password -o tsv |
    xargs -I{} az keyvault secret set --vault-name kv-devhub --name web-client-secret --value {}
{
  "name": "web-client-secret",
  "attributes": { "enabled": true, "updated": "2026-09-01T09:31:04Z" }
}
In your CIAM job, this page is the job: the tenant you administer through Entra blades answers to az ad. Redirect-URI checks, secret rotation into Key Vault, listing which service principals hold a Graph permission (az ad sp list --query …), and the ADO pipeline's AzureCLI@2 task all run exactly the commands above — with the pipeline signing in as a service principal (az login --service-principal) instead of a person.
There are no dumb questions

How does a pipeline run az login? It can't open a browser.

It doesn't log in as a person. Pipelines authenticate as a service principal — az login --service-principal -u <appId> -p <secret> --tenant <id> — or better, with OIDC workload-identity federation, where ADO/GitHub proves its identity to Entra directly and no secret exists at all. On an Azure VM, az login --identity uses the machine's managed identity: zero credentials anywhere.

Subscription vs tenant — which am I "in"?

Both, always. The tenant is the Entra directory — users, groups, app registrations live there. A subscription is a billing container for resources, and it trusts one tenant. az ad commands hit the tenant; az webapp-style commands hit the current subscription. az account show prints both, which is why it's the debugging first move.

Is az's --query the same as the AWS one?

Yes — both are JMESPath, identical syntax. Learn it once, filter both clouds. The az twist worth knowing: az ad app list also has --filter, which is OData and runs server-side in Microsoft Graph — use it to avoid downloading a 5,000-app tenant list just to find one app.
