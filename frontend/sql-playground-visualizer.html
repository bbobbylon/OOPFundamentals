SQL Playground

A real SQLite database, running entirely in your browser. This page loads sql.js (the actual SQLite C engine compiled to WebAssembly), seeds two tables, and runs your queries for real — same parser, same query planner, same error messages you'd get from sqlite3 on a server. Write SQL, press ▶ Run.

🗄️ What is this — and what is SQL doing?

SQL (Structured Query Language) is how you talk to a relational database. You describe what rows you want — SELECT name FROM users WHERE role = 'ADMIN' — and the engine's query planner decides how to fetch them (which index, which join order). This page runs a genuine SQLite engine compiled to WebAssembly, so everything you type is really parsed, planned, and executed against live, seeded data — the same behaviour and the same error messages you'd get from a server.

  • Data lives in tables — rows with typed columns. Here: users (id, name, email, role…) and orders, which has a user_id foreign key pointing back to a user.
  • SELECT reads; INSERT / UPDATE / DELETE write; JOIN … ON stitches two tables together along that shared key.
  • WHERE filters individual rows; GROUP BY + COUNT/SUM/AVG roll them up into summaries; HAVING then filters those groups.
  • SQL is declarative — you state the result you want and the planner picks the access path. Hit Explain to watch it choose a full-table SCAN vs an index SEARCH.
  • Nothing is uploaded — the database lives in-memory in this browser tab. Reset DB restores the seed whenever you want a clean slate.

The clauses you'll use

  • SELECT … FROM — pick columns + table
  • WHERE — filter rows
  • JOIN … ON — combine tables
  • GROUP BY + COUNT/SUM
  • ORDER BY · LIMIT

How SQLite runs it

  1. Parse the SQL text
  2. Plan: which index / table scan?
  3. Open a cursor, walk rows
  4. Filter, group, sort
  5. Return the result set
Why it matters for CIAM:your Spring Boot app's JPA/Hibernate layer ultimately emits SQL exactly like this — SELECT * FROM users WHERE email = ? on login, a JOIN to load a user's roles, and the ? placeholder that stops SQL injection. Knowing the SQL underneath makes the ORM stop being magic.

Why this is genuinely SQLite — and why that matters

It's the real engine

sql.js is SQLite's own C source compiled to WebAssembly. The same B-tree storage, the same query planner, the same no such column / UNIQUE constraint failed errors you'd hit on a server.

Declarative, not step-by-step

You never write a loop. You state the shape of the answer and the planner chooses the access path. EXPLAIN QUERY PLAN (the Explain button) reveals that choice — a full SCAN vs an index SEARCH.

The bridge to JPA

Every userRepository.findByEmail(...) becomes SQL like this. Seeing the JOIN and the ? bind parameter here is what makes Hibernate, N+1 queries, and parameterized statements click. See the Spring Data JPA page.
