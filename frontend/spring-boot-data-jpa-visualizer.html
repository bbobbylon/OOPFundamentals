2 — Entity Annotations

@Entity @Table(name = "users") public class User { @Id @GeneratedValue(strategy = GenerationType.IDENTITY) // AUTO_INCREMENT private Long id; @Column(name = "first_name", nullable = false, length = 50) private String firstName; @Column(unique = true) private String email; @OneToMany(mappedBy = "user", cascade = CascadeType.ALL, fetch = FetchType.LAZY) private List<Order> orders; @ManyToOne @JoinColumn(name = "department_id") private Department department; // Getters/setters or use @Data from Lombok }
@Entity — marks class as a JPA entity (maps to a table).
@Table(name="users") — overrides default table name (default = class name).
@Id — marks the primary key field.
@GeneratedValue — auto-generate ID. IDENTITY = database auto-increment.
@Column — customize column: name, nullable, length, unique.
@OneToMany — one User has many Orders. LAZY = don't load Orders until accessed (default, good).
@ManyToOne — many Users belong to one Department.
@JoinColumn — the foreign key column name.

4 — The N+1 Problem & Fix

🌱 New to JPA? Talk to the database without writing SQL.

You mark a class @Entity — now it maps to a database table, and its fields map to columns. Then you declare an interface: interface UserRepository extends JpaRepository<User, Long> — and without writing any implementation you instantly get save, findById, findAll, delete. Even better, you can name a method like findByEmail(String email) and Spring writes the query from the method name. So for the everyday cases you work entirely with objects and method calls; JPA generates the SQL underneath. (You can still drop to real SQL when you need to.)

🧠 Expert corner — the persistence context, and the N+1 trap

  • The persistence context tracks your entities. Inside a @Transactional method, loaded entities are "managed" — change a field and JPA dirty-checks and flushes an UPDATE automatically; you don't call save() for an already-loaded entity.
  • Derived queries vs @Query. Method-name queries (findByEmailAndActiveTrue) are great until they get long — then switch to @Query with JPQL (or native SQL).
  • The N+1 problem is the classic perf bug. Lazily accessing a collection inside a loop fires one query per row. Fix with JOIN FETCH or an entity graph (this page's demo shows it live). See N+1 & Fetch Strategies.
  • LAZY vs EAGER. Default associations to LAZY and fetch what you need explicitly — EAGER everywhere quietly drags the whole graph into memory.
  • Don't expose entities. Map to DTOs (or use projections) so lazy associations and internal fields never leak across the API boundary — and you avoid LazyInitializationException after the transaction closes.
  • CIAM tie-in. A User entity with a passwordHash must never be returned raw — project to a safe DTO. Pagination via Pageable → Page<T> keeps big tables fast.
