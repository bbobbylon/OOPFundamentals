Spring Data JPA

Map Java classes to database tables with annotations, then query without writing SQL using repository methods.

🗄️ What is JPA? Why not just write SQL?

JPA (Java Persistence API) is the Java standard for Object-Relational Mapping — it bridges Java objects and database rows so you don't hand-write SQL strings, manually map ResultSet columns to fields, or maintain INSERT/UPDATE statements per entity. You annotate a class with @Entity and it handles the SQL. Spring Data JPA goes further: declare a repository interface that extends JpaRepository<User, Long> and Spring generates the implementation at startup — method names like findByEmail or findByRoleAndActiveTrue are parsed straight into SELECT queries, so you write zero SQL for the common cases.

  • @Entity maps a class to a table — fields become columns and @Id @GeneratedValue marks the primary key.
  • Repositories are derived, not written — Spring reads the method name and builds the query (findByRole → WHERE role = ?).
  • The persistence context tracks entities — change a managed entity's field inside a transaction and Hibernate auto-flushes the UPDATE (dirty checking).
  • Lazy vs eager loading is the #1 trap — touching a lazy collection once per row produces the N+1 query explosion.

Entity + Repository

  String email; String role;

An entity is only as "live" as the transaction that loaded it. That one sentence is why findById() + setRole() with no @Transactional silently does nothing, why @Transactional(readOnly = true) sits on every generated repository method whether you asked for it or not, and why calling save() explicitly on a detached object works while mutating it in place does not — save() hands you back a fresh, managed copy; the object you already had never rejoins anything.
Think of a managed entity as a hotel room while you're still checked in. Housekeeping (the persistence context) notices every rearranged lamp and updates the ledger for you automatically — but only while your key card (the transaction) is still active. Check out, and you can keep holding that key and rearranging furniture in your head all you like; nobody is writing any of it down anymore. Where it breaks down: checking into a fresh room with the same room number (a new findById() for the same id) doesn't restore your old rearrangements — it hands you brand-new furniture, pulled straight from the database.

The mechanism

Every repository method opens a door. Most close it before you're back in your own code.

  1. You call userRepo.findByRole("ADMIN") — an interface method with no implementation you ever wrotenot magic, generated
  2. At startup, Spring Data parsed that method name into a query — findByRole → WHERE role = :role — and checked it against User's fields. Misspell it and the app refuses to startfails at boot, not at call time
  3. SimpleJpaRepository wraps the generated method in @Transactional(readOnly = true)the part nobody notices
  4. Hibernate opens a persistence context, runs the SQL, and maps each row to a User — each one is now managedmanaged = tracked
  5. If no wider transaction was already running, that transaction — and the persistence context with it — commits and closes the instant the method returnsthis is the trap
  6. The User you're holding is still perfectly usable Java — it's just detached. Mutating it is legal; persisting it is not, until something reopens a sessiondirty checking needs a live session

Step 3 is the lesson, and everything else follows from it. You never asked for a transaction, but SimpleJpaRepository put one around your call anyway — one scoped to exactly that method. That single default explains why a non-transactional service "loses" writes, why wrapping your own method in @Transactional fixes it (yours becomes the one that's already running, so the repository joins it instead of opening a new one), and why the fetch strategies on the next page all live or die by the same boundary.

Where you've seen this before

Three systems, one boundary: tracked only while a resource stays open.

EF Core's DbContext — the .NET twin of this exact bug

Entity Framework Core tracks entities per DbContext instance, and in ASP.NET that context is usually request-scoped. Load an entity, let the request end (the context disposes), and a background job holding a reference to that entity is holding a detached POCO — calling SaveChanges() on a different context does nothing for it unless you explicitly Attach() and mark it modified. Same idea, same silence, different runtime.

DbContext scope ≈ persistence context scope

Raw JDBC's ResultSet — the version that at least yells at you

Keep a ResultSet reference after its Connection closes and call rs.getString() and you get a loud SQLException: ResultSet is closed. JPA sits one layer above JDBC and hides that connection entirely — which is exactly why its version of "the resource already closed" fails silently instead. The convenience that makes JPA pleasant to use is the same convenience that hides this bug.

JDBC fails loud; JPA fails quiet

Questions from the back row

Why doesn't Spring just keep one big transaction open for my whole service method automatically?

It does — you just have to ask. Put @Transactional on your own service method and its propagation defaults to REQUIRED: if a transaction is already running, join it; if not, start one. When your method is the one that's already running, findById()'s own @Transactional joins yours instead of opening a second one — Spring doesn't nest real transactions here, it just notices one is already open and reuses it. That's the actual fix, not a workaround: put the boundary where the read and the write both need to live.

If I call save() on the detached u, does that fix it?

Yes, but only if you use what it hands back. save() on an entity that already has an id runs an EntityManager.merge() under the hood: it copies your object's field values onto a freshly loaded, newly managed instance in a new persistence context and returns that instance. repository.save(u) and then continuing to use the original u is a classic near-miss — the merge worked, you're just still holding the wrong object.

Does @Transactional(readOnly = true) actually stop me from writing?

No — it's a hint, not a lock. It tells Hibernate to skip the dirty-checking flush at commit (a real performance win on read paths) and some JDBC drivers use it to set the connection read-only at the database level, but neither is guaranteed across every driver. Don't rely on it as a safety rail against accidental writes; rely on it for speed on methods that genuinely never write.

2 — Entity Annotations

@Entity @Table(name = "users") public class User { @Id @GeneratedValue(strategy = GenerationType.IDENTITY) // AUTO_INCREMENT private Long id; @Column(name = "first_name", nullable = false, length = 50) private String firstName; @Column(unique = true) private String email; @OneToMany(mappedBy = "user", cascade = CascadeType.ALL, fetch = FetchType.LAZY) private List<Order> orders; @ManyToOne @JoinColumn(name = "department_id") private Department department; // Getters/setters or use @Data from Lombok }
@Entity — marks class as a JPA entity (maps to a table).
@Table(name="users") — overrides default table name (default = class name).
@Id — marks the primary key field.
@GeneratedValue — auto-generate ID. IDENTITY = database auto-increment.
@Column — customize column: name, nullable, length, unique.
@OneToMany — one User has many Orders. LAZY = don't load Orders until accessed (default, good).
@ManyToOne — many Users belong to one Department.
@JoinColumn — the foreign key column name.

🌱 New to JPA? Talk to the database without writing SQL.

You mark a class @Entity — now it maps to a database table, and its fields map to columns. Then you declare an interface: interface UserRepository extends JpaRepository<User, Long> — and without writing any implementation you instantly get save, findById, findAll, delete. Even better, you can name a method like findByEmail(String email) and Spring writes the query from the method name. So for the everyday cases you work entirely with objects and method calls; JPA generates the SQL underneath. (You can still drop to real SQL when you need to.)

🧠 Expert corner — the persistence context, and the N+1 trap

  • The persistence context tracks your entities. Inside a @Transactional method, loaded entities are "managed" — change a field and JPA dirty-checks and flushes an UPDATE automatically; you don't call save() for an already-loaded entity.
  • Derived queries vs @Query. Method-name queries (findByEmailAndActiveTrue) are great until they get long — then switch to @Query with JPQL (or native SQL).
  • The N+1 problem is the classic perf bug. Lazily accessing a collection inside a loop fires one query per row. Fix with JOIN FETCH or an entity graph (this page's demo shows it live). See N+1 & Fetch Strategies.
  • LAZY vs EAGER. Default associations to LAZY and fetch what you need explicitly — EAGER everywhere quietly drags the whole graph into memory.
  • Don't expose entities. Map to DTOs (or use projections) so lazy associations and internal fields never leak across the API boundary — and you avoid LazyInitializationException after the transaction closes.
  • CIAM tie-in. A User entity with a passwordHash must never be returned raw — project to a safe DTO. Pagination via Pageable → Page<T> keeps big tables fast.
