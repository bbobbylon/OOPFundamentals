NestJS — Spring Boot, but TypeScript

If you know Spring, you already know NestJS: decorators, a DI container, modules, controllers, services, guards, interceptors, pipes, and exception filters. It is deliberately the Spring experience on Node — the framework a Spring developer feels at home in.

🐱 What is NestJS — and why does it feel exactly like Spring Boot?

NestJS is an opinionated, batteries-included Node framework written in TypeScript, built around the same ideas as Spring Boot: decorators (Nest's annotations), a dependency-injection container, and a layered structure of modules → controllers → providers (services). You declare a @Module (≈ a Spring @Configuration/component-scan boundary), put HTTP endpoints in @Controller classes (≈ @RestController), and business logic in @Injectable() providers (≈ @Service) that Nest constructs and injects for you. Every request flows through an ordered pipeline — middleware → guards → interceptors (pre) → pipes → the route handler → interceptors (post) → exception filters — which maps almost one-to-one onto Spring's filter chain, @PreAuthorize, AOP around-advice, argument resolvers/validation, and @ControllerAdvice. By default Nest runs on Express (you can swap in Fastify). The payoff: a Spring developer is productive on day one, on the same language as their Angular frontend.

  • DI container — constructor injection of @Injectable() providers, like Spring beans.
  • Module / Controller / Provider ≈ @Configuration / @RestController / @Service.
  • Guards / Interceptors / Pipes / Filters ≈ @PreAuthorize / AOP / validation / @ControllerAdvice.
  • Decorator-driven — @Get(':id'), @Param(), @Body() read like Spring MVC.

@Injectable() export class UsersService { findOne(id: string) { return this.repo.find(id); } } @Controller("users") // ≈ @RestController + @RequestMapping export class UsersController { // constructor injection — Nest supplies the singleton constructor(private users: UsersService) {} @Get(":id") // ≈ @GetMapping("/{id}") findOne(@Param("id") id: string) { return this.users.findOne(id); // serialized to JSON } }

The mental model transfers wholesale from the day job.

or, one request-scoped provider can make your whole app request-scoped

The problem

You scoped ONE service to the request. Now your whole app rebuilds itself, every single request.

Nobody touched the controllers. The controllers changed anyway.

You add a small TenantContextService — @Injectable({ scope: Scope.REQUEST }) — because it needs to read the tenant id off the live REQUEST object, something a singleton can never see (a singleton is built once, long before any request exists). It's a good, small, focused class. You inject it into AuditLogger, because every write path already logs through AuditLogger. Load testing afterward shows p99 latency up and CPU per request up, even though you didn't touch a single controller or route handler. AuditLogger is used almost everywhere — and everywhere it's used just quietly stopped being a singleton too.

TenantContextService: one small class ✓ no controller code changed ✓ AuditLogger now Scope.REQUEST too ⚠ everything that injects AuditLogger, also REQUEST ⚠

Scope isn't a property of the class you wrote. It's contagious — it travels up every constructor that depends on it.

Keep request-scoped providers at the leaves, not the root
TenantContextService (REQUEST) injected into AuditLogger (used everywhere) ↓ scope bubbles up through every constructor parameter that depends on it Better: give AuditLogger the tenant id as a plain argument, not a request-scoped dependency ↓ AuditLogger and everything above it goes back to being a singleton, built once Only the one genuinely per-request slice pays the per-request cost
Scope isn't a label on a class — it's a property of the whole dependency chain leading to it. A provider that injects a REQUEST-scoped dependency becomes request-scoped itself, automatically, with no decorator of your own — and so does everything that depends on THAT provider. Nest calls this "bubbling up." It's why one small class chosen for a good reason (reading the live request) can quietly undo the "build once" benefit of the DI container for a much bigger slice of the app than the one class someone actually scoped.
Think of provider scope as a food allergy in a shared kitchen, not a label on one dish. If one ingredient at the shared prep station has to be made fresh for every customer's order, every dish that touches that station now has to be made fresh too — even the ones that never changed their own recipe. Where it stops being accurate: a real kitchen can wall off one station. Nest's DI graph has no wall to put between a request-scoped dependency and everything built on top of it.
You

I only changed one small service. Why is my whole app slower under load?

TenantContextService

Because I asked for something a singleton can never have: the live REQUEST object. Nest can't hand out one instance of me and reuse it forever — there's a new request every few milliseconds. So Nest marks me Scope.REQUEST and builds a fresh me, every time.

AuditLogger

And I depend on him now. Nest can't hand out one long-lived instance of ME either — if it did, I'd be holding onto whichever request happened to build me first, forever. So Nest quietly scopes me to REQUEST too. I didn't ask for this. Nobody put Scope.REQUEST on my class.

Every controller that injects AuditLogger

Same story, one level up. The bubbling doesn't stop until it runs out of things that depend on him. That's a large slice of the app's controller layer, rebuilt from scratch, on every single request — for the sake of one class that needed to read a tenant id.

The mechanism

One Scope.REQUEST provider, and the container stops asking "do I already have one of these?"

  1. TenantContextService is declared @Injectable({ scope: Scope.REQUEST }) because it injects the REQUEST token to read a headerthe only class anyone touched
  2. Nest's container sees a provider depends on something REQUEST-scoped, and marks the DEPENDENT provider REQUEST-scoped too — automatically, with no decorator you wrotebubbling, step one
  3. AuditLogger injects TenantContextService, so AuditLogger becomes REQUEST-scoped as wellbubbling, step two
  4. Every controller and service that injects AuditLogger — in a real app, most of them — becomes REQUEST-scoped in turn, transitively, with no ceiling on how far it spreadsthe part nobody sized
  5. A request arrives. Nest can no longer reuse the app's long-lived singleton graph for any of these providers — it builds a fresh sub-tree of them, from scratch, for this one request onlythe actual cost
  6. The request finishes; that entire sub-tree is thrown away and garbage-collected. The next request pays the full construction cost again, from zeroand again, and again

Step 2 is the lesson. Nest doesn't ask you to opt in to the slow path for every affected class — the container computes it FOR you, silently, by walking the dependency graph. That's good API design for correctness (a stale singleton holding one request's data forever would be a much worse bug) and bad news for performance, because "everything that transitively depends on this" is usually much bigger than the one class someone meant to scope.

One REQUEST-scoped class at the root of the fan is all it takes. Nothing downstream opted in — each box just happened to depend on something that depends on something that needed the live request, and that's contagious in exactly one direction: upward, toward the root.

TenantContextService is Scope.REQUEST and injects LoggerService (a plain singleton) to log the resolved tenant. BillingService is also a plain singleton, and it injects LoggerService too — but never touches TenantContextService. InvoiceController injects both BillingService and TenantContextService. After Nest resolves scopes, what is LoggerService, and what is BillingService?

Right. Scope bubbles in exactly one direction: toward whatever INJECTS a request-scoped provider, never toward what that provider itself depends on. TenantContextService injects LoggerService — that's TenantContextService depending on a plain singleton, which changes nothing about LoggerService. BillingService never injects TenantContextService at all, so it's untouched even though InvoiceController — which does inject TenantContextService, and therefore does turn REQUEST-scoped — happens to hold a reference to it too.

Tempting, because it matches the earlier AuditLogger story: one request-scoped class did spread to a whole neighborhood there. The difference is direction. In that example, everything downstream INJECTED the request-scoped provider, directly or transitively. Here, LoggerService is a dependency OF the request-scoped provider, not a dependent — nothing forces it to change. And BillingService never injects TenantContextService at all, so there's no edge for the scope to travel across.

Half right, in that a request-scoped provider IS involved — but backwards on which side moves. Scope only bubbles toward a CONSUMER of a request-scoped provider, never down to something that provider merely uses. TenantContextService consumes LoggerService, not the other way around, so LoggerService has no reason to change scope.

Where you've seen this before

Three frameworks, one question: what happens when something that lives for one request meets something built to live forever?

Spring's request-scoped beans have the identical trap

Spring Boot has the same feature under @Scope("request"), and the same warning: inject a request-scoped bean straight into a singleton and Spring throws a BeanCreationException at startup, because the singleton is built once and the request-scoped bean doesn't exist yet at that point. Spring's fix is a scoped proxy (proxyMode = ScopedProxyMode.TARGET_CLASS) — a stand-in the singleton can hold forever, which resolves the real request-scoped bean fresh on every call. Nest generates the equivalent machinery for you automatically, which is exactly why the cost is so easy to miss until a load test finds it.

scoped proxy ≈ Nest's automatic Scope.REQUEST rebuilding

Flask's g / Python's contextvars: no graph to bubble through

Flask and FastAPI solve "give me something scoped to this one request" differently: a g object or a contextvars.ContextVar that any function can read during that request, with no dependency-injection graph for the scope to propagate through. You lose Nest's clean constructor-injection testability, but you also lose the entire bubbling problem, because nothing was ever declared to be "built once" in the first place.

request-local storage, no DI graph to bubble through

Your CIAM resource server, under a login storm

A Nest resource server validating Ping/Entra tokens often wants a small CurrentUserService that reads request.user (set by a guard) so business services don't each reach into the raw request. Mark that convenience service Scope.REQUEST and inject it into something broadly shared — a PermissionsService every controller uses for role checks — and the entire authorization layer of the API stops being built once at startup. Under a Monday-morning SSO login storm, that's real, measurable latency added to code every single request already has to run.

one convenience service, the whole authz layer rebuilt per request
Questions from the back row

If request-scoped providers are this costly, why do they exist at all?

Because sometimes you genuinely need per-request state inside the DI graph — a CurrentUserService wrapping request.user, or a multi-tenant app resolving a tenant-specific database connection before any business logic runs. The alternative — reaching into a raw request object by hand everywhere — is worse for testability. Nest's answer isn't "never use it," it's "use it as close to the leaves of the dependency graph as you can," because everything above it inherits the cost.

Does the same bubbling happen with Scope.TRANSIENT?

No, and that's the detail people mix up. Scope.TRANSIENT means a fresh instance per CONSUMER — each class that injects it gets its own private copy — but it doesn't force a consumer to change ITS OWN scope. A transient provider can be injected into a singleton just fine, because a new transient instance is simply handed to that singleton once, at construction, and reused for the singleton's whole lifetime. Only Scope.REQUEST bubbles, because only REQUEST scope is tied to something — an HTTP request — that a singleton fundamentally cannot outlive.

How would I even notice this happening in my own app?

Nest logs each provider's scope with verbose startup logging, but the more reliable signal is a load test: request-scoped bubbling shows up as CPU and memory that scale with request VOLUME even when the actual work per request hasn't changed, plus GC pressure from constantly discarding rebuilt sub-graphs. The structural check is manual: grep for Scope.REQUEST, then trace every class that injects that provider, and every class that injects THOSE — if the list reaches your controllers, you've found your blast radius.

2. Validation pipe + DTO

// create-user.dto.ts — class-validator decorators ≈ Bean Validation
export class CreateUserDto {
  @IsEmail() email: string;
  @MinLength(8) password: string;
  @IsOptional() @IsInt() age?: number;
}

@Post()
create(@Body() dto: CreateUserDto) { // ValidationPipe runs first
  // reaches here only if dto is valid; else 400 auto-returned
  return this.users.create(dto);
}
Enable it globally: app.useGlobalPipes(new ValidationPipe({ whitelist: true })) strips unknown properties and rejects invalid bodies with a 400 — exactly like putting @Valid on every @RequestBody plus a global @ExceptionHandler(MethodArgumentNotValidException) in Spring.

3. The execution order

// Inbound:
Middleware → Guards → Interceptors(before) → Pipes → Route Handler
// Outbound:
Route Handler → Interceptors(after) → Response
// On throw, at any point:
→ Exception Filters → error response

Guards decide if the request proceeds (auth). Interceptors wrap the handler (timing, response shaping, caching). Pipes transform/validate the bound arguments. Filters catch thrown exceptions. Each can be scoped global, per-controller, or per-route.
