Deployment Strategies — Blue-Green, Canary, Feature Flags & GitOps

Kubernetes Deployments and ECS both cover rolling deployment — the default, gradually replace old pods/tasks with new ones. This page covers the alternatives teams reach for when rolling isn't safe enough, fast enough, or decoupled enough from the release itself: blue-green, canary, feature flags, and GitOps.

🚦 If rolling deployment already works, why does anything else exist?

A rolling deployment replaces old instances with new ones a few at a time — safe, zero-downtime, and the right default for most services. But it has real limits: during the rollout, both versions run simultaneously and there's no fast, total "undo" — rolling back means rolling forward again, pod by pod, which takes just as long as the deploy did. It also can't answer three separate questions rolling deployment conflates into one: "is the new version safe?" (best answered by testing it on a small slice of real traffic first — canary), "can I switch back to the old version instantly if something's wrong?" (best answered by keeping the old version fully running and just flipping a router — blue-green), and "do I need to redeploy at all to turn a feature on or off?" (answered by decoupling deploy from release entirely — feature flags). A fourth idea, GitOps, changes a different axis: not how traffic shifts, but where the desired state lives — a git repo, continuously reconciled by a controller, instead of a human running kubectl apply by hand.

  • Blue-green trades cost for instant rollback — two full environments running at once, but switching back is one router flip, not a redeploy.
  • Canary trades speed for safety — a small % of real traffic validates the new version before it gets the rest, with an automatic abort if metrics degrade.
  • Feature flags decouple deploy from release — the code can be in production, dark, for days before anyone flips it on for anyone.
  • GitOps changes WHO applies the change — a controller continuously reconciles the cluster to match git, so a deploy is a merged PR, not a manual command.

These compose, they don't compete

A real pipeline often uses all four together: GitOps as the delivery mechanism, canary as the traffic-shifting policy the GitOps controller executes, with a feature flag as an extra kill switch, inside a blue-green environment pair for the riskiest changes.

This app's own rolling default, contrasted

The Kubernetes Deployments page's RollingUpdate strategy (maxSurge/maxUnavailable) is what actually ships when you run kubectl apply against this app's manifests — the strategies below are alternative traffic-shifting policies layered on top of, or instead of, that same rolling substrate.

CIAM angle — a canary or flag rollout for auth changes needs its own care

Rolling out a change to token validation, claim mapping, or a security filter gradually means two different auth code paths are live in production at once — a session issued by the old version must still validate against the new one (and vice versa) for the whole rollout window, or users get logged out mid-rollout for reasons that have nothing to do with their own session expiring.

1. The four strategies, side by side

StrategyWhat changesRollback speedInfra costBest for
Rolling (the default, not detailed here)Old instances replaced graduallySlow — roll forward againLow — one environmentRoutine, low-risk deploys

Rollback speed is the real differentiator. Rolling deployment's biggest weakness isn't safety — it's that "undo" takes as long as "redo." Blue-green, canary, and feature flags all exist primarily to make rollback near-instant, each at a different cost (idle infra, gradual exposure, or a toggle service) and a different point in the pipeline (infra, traffic, or code).

2. Blue-green: two full environments, one router flip

✗ Rolling — rollback means redeploying

// kubectl rollout undo

Kubernetes replaces pods with the previous ReplicaSet's spec — one at a time, the same speed as the original rollout. A bad deploy discovered at 100% traffic can mean minutes of degraded service while it unwinds.

✓ Blue-green — rollback is a router config change

# both "blue" (live) and "green" (idle) are FULL, running
# environments the whole time — switching is just this:
kubectl patch service app \
  -p '{"spec":{"selector":{"env":"green"}}}'

Both environments are already fully deployed and warm before the switch — flipping back is the same one-line change, in the other direction, taking effect for new connections immediately.

3. Canary vs blue-green: gradual exposure vs instant switch

AxisBlue-greenCanary
Traffic shiftAll-at-once, at the moment of cutoverGradual — a % at a time, expanding as confidence grows
Blast radius if wrong100% of users, immediately — but instantly reversibleJust the canary %, and it can be caught before expanding further
Real-traffic validationNone before the switch — smoke tests onlyReal production traffic validates the new version incrementally
Infra during rollout2x — both environments fully provisioned~1x + a small canary slice
Canary catches problems blue-green can't — a bug that only shows up under real production traffic patterns (a specific query shape, a rare user segment, load-dependent behavior) will hit 100% of users the instant a blue-green switch happens, but only a small % of users during a canary's early stage, where automated monitoring can catch it and abort before it ever reaches everyone.

4. One-sentence recap

🚦 Blue-green buys an instant rollback at 2x infra cost, canary buys real-traffic validation with automatic abort, feature flags decouple "it's deployed" from "it's on," and GitOps changes who applies the change at all — a git-reconciling controller instead of a human running commands by hand.
