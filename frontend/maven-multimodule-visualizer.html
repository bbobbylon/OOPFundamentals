Multi-Module Projects

Real Spring Boot applications split into multiple Maven modules for separation of concerns. Learn the parent-child POM structure, reactor builds, and inter-module dependencies.

1 — Why Split Into Modules?

❌ Single Module (grows painful)

  • Everything in one JAR — hard to reuse
  • Domain model + web layer + DB in one src/
  • Full rebuild required to test any change
  • Can't deploy parts independently
  • Circular import risk grows over time

✓ Multi-Module (enterprise standard)

  • domain module: shared model reused by all modules
  • Clear architectural boundaries enforced by compiler
  • Only changed modules rebuild (faster CI)
  • api module can depend on domain without web code
  • Promotes clean layered architecture

2 — Typical Structure — Click Each Module

📦 my-company-app/ Parent POM (packaging: pom)
├── 📁 domain/ JAR — no deps
domain — pure Java. Contains your entities, value objects, enums, and domain interfaces. No Spring, no JPA annotations if you're going hexagonal.

Depends on: nothing (or only utility libraries). Everything else depends on this.

com.example.domain.User, com.example.domain.Order etc.
├── 📁 infrastructure/ JAR — Spring Data, JPA
infrastructure — persistence layer. JPA entities (if separate from domain), Spring Data repositories, database configuration.

Depends on: domain module. Has spring-boot-starter-data-jpa and the DB driver.

com.example.infrastructure.UserJpaRepository, com.example.infrastructure.UserEntity
├── 📁 api/ JAR — REST controllers
api — web layer. Controllers, DTOs, exception handlers, request/response mappers.

Depends on: domain and infrastructure modules. Has spring-boot-starter-web.

Cannot accidentally import from domain → infrastructure direction because module boundaries enforce it at compile time.
└── 📁 app/ Executable FAT JAR
app — the Spring Boot launcher. Contains @SpringBootApplication main class, application.yml, and wires all other modules together.

Depends on: all other modules. Has spring-boot-maven-plugin configured here (not in parent) — only this module produces the fat JAR.

Running mvn package from the root builds all modules in dependency order and creates app/target/app.jar.

3 — The Parent POM

The root pom.xml has packaging: pom and lists all child modules. It's also the right place to centralize dependency versions via <dependencyManagement>:

<project> <groupId>com.example</groupId> <artifactId>my-company-app</artifactId> <version>1.0.0-SNAPSHOT</version> <packaging>pom</packaging> <!-- MUST be "pom" for parent/aggregator --> <parent> <groupId>org.springframework.boot</groupId> <artifactId>spring-boot-starter-parent</artifactId> <version>3.3.0</version> </parent> <!-- List all child modules --> <modules> <module>domain</module> <module>infrastructure</module> <module>api</module> <module>app</module> </modules> <!-- Centralize versions here — child modules declare without version --> <dependencyManagement> <dependencies> <dependency> <groupId>com.example</groupId> <artifactId>domain</artifactId> <version>${project.version}</version> </dependency> </dependencies> </dependencyManagement> </project>

4 — Inter-Module Dependencies

The api module's pom.xml references domain as a dependency just like an external library:

<!-- api/pom.xml --> <project> <parent> <groupId>com.example</groupId> <artifactId>my-company-app</artifactId> <!-- the parent aggregator --> <version>1.0.0-SNAPSHOT</version> </parent> <artifactId>api</artifactId> <dependencies> <!-- Reference sibling module — no version because parent manages it --> <dependency> <groupId>com.example</groupId> <artifactId>domain</artifactId> </dependency> <dependency> <groupId>org.springframework.boot</groupId> <artifactId>spring-boot-starter-web</artifactId> </dependency> </dependencies> </project>

Dependency direction (arrows = "depends on"):

app
→
api
→
infrastructure
→
domain

domain depends on nothing. Everything else depends on domain. The compiler enforces this — domain cannot import from api.

5 — The Maven Reactor

Running mvn package from the root triggers the Reactor — Maven's multi-module build engine. It calculates the correct build order from dependency relationships:

[INFO] Scanning for projects... [INFO] ------------------------------------------------------------------------ [INFO] Reactor Build Order: [INFO] [INFO] my-company-app [pom] <-- parent first [INFO] domain [jar] <-- no deps, built first [INFO] infrastructure [jar] <-- needs domain [INFO] api [jar] <-- needs domain + infrastructure [INFO] app [jar] <-- needs all, built last [INFO] [INFO] ----------------------------------------------------------------------- [INFO] BUILD SUCCESS [INFO] ----------------------------------------------------------------------- [INFO] Total time: 12.4s (Wall Clock)
CommandWhat it does
mvn package (from root)Builds ALL modules in reactor order
mvn package -pl apiBuild only the api module (and its dependencies)
mvn package -pl api -am-am: Also build modules that api depends on (domain, infrastructure)
mvn package -pl api -amd-amd: Also build modules that depend on api downstream
mvn install (from root)Install all modules to ~/.m2 — needed for CI where other builds reference them
