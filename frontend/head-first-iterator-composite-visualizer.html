Iterator & Composite — the Objectville Menus

Chapter 9. The Objectville Diner (an ArrayList) and the Pancake House (an Array) merge. The waitress now has to loop over two different collection types two different ways. Iterator gives every collection one common way to be walked. Then, when menus start containing sub-menus, Composite lets the waitress treat a single item and a whole menu-tree exactly the same.

What are Iterator and Composite — and how do they solve the "two different menus" problem together?

Iterator provides a way to access elements of a collection sequentially without exposing its underlying representation. The problem: the Diner uses an ArrayList<MenuItem>; the Pancake House uses a MenuItem[] array. The waitress loops: for (int i=0; i<pancakeMenu.getItems().length; i++) { ... } AND Iterator it = dinerMenu.createIterator(); while(it.hasNext()) { ... } — two different loop patterns. With Iterator: both menus implement createIterator() returning an Iterator<MenuItem>. The waitress has one loop: while(it.hasNext()) { MenuItem item = it.next(); print(item); }. SRP bonus: the collection manages its own structure; the Iterator manages traversal. Composite takes it further: menus containing sub-menus. A MenuComponent interface has print(). MenuItem (leaf) prints itself. Menu (composite) has a list of MenuComponents — it calls print() on each child, which may itself be a Menu. The composite walks the tree recursively. The client treats leaf and composite the same: just call component.print(). Composite = tree structures where you want to treat individual objects and compositions of objects uniformly.

Iterator structure

interface Iterator<T> { boolean hasNext(); T next(); } class ArrayMenuIterator implements Iterator<MenuItem> { MenuItem[] items; int pos = 0; boolean hasNext() { return pos < items.length; } MenuItem next() { return items[pos++]; } } class Menu { Iterator<MenuItem> createIterator() { return new ArrayMenuIterator(items); } }. Java's java.util.Iterator is this exact interface. All Java collections implement Iterable<T> (one method: iterator()), allowing the enhanced for-each: for (MenuItem item : menu) — syntactic sugar over Iterator.hasNext()/next().

Composite structure

abstract class MenuComponent { void print() { throw new UnsupportedOperationException(); } void add(MenuComponent c) { throw new UnsupportedOperationException(); } } class MenuItem extends MenuComponent { String name; double price; void print() { System.out.println(name + ": $" + price); } } class Menu extends MenuComponent { List<MenuComponent> children = new ArrayList<>(); void add(MenuComponent c) { children.add(c); } void print() { children.forEach(MenuComponent::print); } // recursive }. Usage: Menu allMenus = new Menu("ALL"); Menu dinnerMenu = new Menu("DINNER"); dinnerMenu.add(new MenuItem("Burger", 8.99)); allMenus.add(dinnerMenu); allMenus.print() — walks entire tree.

In Spring and Angular

Iterator in Spring: JPA Specification pattern with Criteria API — compose predicates like iterating through search criteria. Spring Batch: ItemReader is Iterator — read() returns the next item or null. MultiResourceItemReader: composite reader that wraps multiple readers. Composite in Angular: The component tree IS a Composite — a component can contain other components. Angular's ComponentRef tree is a Composite where each node can be a leaf (simple component) or a composite (component with children). Navigation menus in Angular apps: menu items and sub-menus, both rendered via the same template recursion.

In CIAM / Spring Boot: Iterator: paginated Ping Directory API — class PingDirectoryIterator implements Iterator<UserDto> { int page=0; List<UserDto> buffer=[]; boolean hasNext() { if (!buffer.isEmpty()) return true; buffer = pingClient.getUsers(page++, 100); return !buffer.isEmpty(); } UserDto next() { return buffer.remove(0); } }. The caller uses a simple while-loop; the pagination is hidden inside the Iterator. Composite: permission tree — abstract class Permission { abstract boolean check(UserPrincipal u); } class SimplePermission extends Permission { ... } class AndPermission extends Permission { List<Permission> children; boolean check(u) { return children.stream().allMatch(p -> p.check(u)); } }. Compose: new AndPermission(ROLE_ADMIN, new OrPermission(TENANT_A, TENANT_B)).

Act 1 — two menus, two ways to loop

The merger hands the waitress two menus backed by different collections. To print everything, she writes two loops — one per implementation:

// Pancake House — backed by an ArrayList
ArrayList<MenuItem> items = pancakeMenu.getMenuItems();
for (int i = 0; i < items.size(); i++) { ... items.get(i) ... }

// Diner — backed by a plain Array
MenuItem[] items = dinerMenu.getMenuItems();
for (int i = 0; i < items.length; i++) { ... items[i] ... }   // different loop!
Brain Power. The waitress is now coupled to both concrete collection types. Add a third menu (a HashMap?) and she needs a third loop. The implementation of "how this collection stores its items" has leaked into her code. We need to hand her one way to step through any collection.

Act 2 — one Iterator interface

Each menu exposes a createIterator() that returns an Iterator — a tiny interface with hasNext() and next(). The waitress only ever talks to Iterator.

The common interface

interface Iterator {
  boolean hasNext();
  Object next();
}
// each menu returns its own implementation
Iterator createIterator();

One loop, every menu

void printMenu(Iterator it) {
  while (it.hasNext()) {
    MenuItem item = (MenuItem) it.next();
    print(item.getName());
  }
}
// works for ArrayList, Array, HashMap, anything
Design PrincipleA class should have only ONE reason to change
Single Responsibility — managing a collection and iterating it are two jobs. Iterator takes the second one off the collection.

Q: Java already has java.util.Iterator and Iterable — do I write my own?

A: Almost never. Implement Iterable<T> (return a java.util.Iterator<T>) and you get the enhanced for-loop (for (var x : menu)) and Streams for free. The pattern is so useful it's baked into the language — that's the point of learning it.

The Iterator Pattern, defined

The Iterator Pattern provides a way to access the elements of an aggregate object sequentially without exposing its underlying representation.

"Without exposing its representation" = the client never knows (or cares) whether it's an array, a list, or a tree. That decoupling is what let us delete the second loop.

Act 3 — menus within menus (Composite)

Now the chef wants a dessert sub-menu nested inside the dinner menu. A menu can now contain menu items AND other menus. Iterator alone can't express a tree. Composite gives leaves and branches a single shared type.

One component type for both

abstract class MenuComponent {
  void add(MenuComponent c) { ... }   // composite-only
  void print() { ... }              // both implement
}
class MenuItem extends MenuComponent { ... }  // leaf
class Menu extends MenuComponent { ... }      // composite

print() recurses the tree

// Menu (composite)
void print() {
  print(name);
  for (MenuComponent c : children)
    c.print();   // leaf prints itself; menu recurses
}
The trade-off (be honest). Composite deliberately puts add()/remove() on the base type, even though a leaf MenuItem can't hold children. That breaks Single Responsibility a little — in exchange for transparency (the client treats everything as a MenuComponent and never type-checks). Head First calls this out: it's a conscious tug-of-war between safety and uniformity, and Composite chooses uniformity.

The Composite Pattern, defined

The Composite Pattern allows you to compose objects into tree structures to represent part-whole hierarchies. Composite lets clients treat individual objects and compositions of objects uniformly.

"Uniformly" is the payoff: component.print() works whether component is one item or a menu of menus of items. And an Iterator can walk a Composite — the two patterns team up.

You've used these — everywhere

Iterator in the wild

Every for (var x : list), every Java Stream, JavaScript's for...of + generators, Python's __iter__/__next__, an Angular @for over a collection — all the Iterator pattern, standardized into the language.

Composite in the wild

The DOM tree (a node is an element or a document fragment, same API), Angular/React component trees, a filesystem (file vs directory), Swing/JavaFX containers, an AST in a compiler. Anywhere "a thing or a group of things, treated the same."
