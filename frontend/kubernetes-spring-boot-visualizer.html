Spring Boot on Kubernetes

Container image, health probes, graceful shutdown, and resource limits — the K8s-native Spring Boot playbook.

🩺 How do you run Spring Boot on Kubernetes — and what does K8s-native actually mean?

Running Spring Boot on K8s means integrating with the container lifecycle. Build the image with spring-boot:build-image (Buildpacks) or a multi-stage Dockerfile on a minimal JRE, using layered JARs for cache-friendly builds. The big integration is health probes: a startupProbe gives a slow Spring app time before liveness checks begin; a readinessProbe (/actuator/health/readiness) gates traffic until ready; a livenessProbe (/actuator/health/liveness) restarts a deadlocked pod. On SIGTERM, Spring 2.3+ does graceful shutdown (server.shutdown=graceful, drains in-flight up to 30s). Always set requests/limits — the container-aware JVM (UseContainerSupport) sizes heap from the cgroup limit.

  • Build with Buildpacks / multi-stage JRE — layered JARs for cache.
  • Three probes — startup (slow boot), readiness (gate traffic), liveness (restart).
  • Graceful shutdown on SIGTERM — drain in-flight up to 30s.
  • requests/limits + UseContainerSupport — cgroup-sized heap, no OOMKill.

JVM + K8s gotchas

JVM heap sizing: without container awareness, JVM reads the node's total RAM (e.g., 16 GB) and sets heap to 4 GB — but your pod limit is 1 GB → OOMKilled immediately. Fix: Java 10+ with -XX:+UseContainerSupport (default) reads cgroup limit (1 GB) and sizes heap accordingly (~256 MB). Or explicitly: -Xmx512m. Slow startup probe: Spring Boot with lots of beans, DB migrations (Flyway), and @PostConstruct initialization can take 20-60 seconds to start. Without a startupProbe, K8s may kill the pod for "failing liveness" before it's even started. Set startupProbe.failureThreshold: 60, periodSeconds: 5 = 300s max startup window. PodDisruptionBudget: ensures at least N pods are always up during node maintenance: kind: PodDisruptionBudget; spec: { minAvailable: 2; selector: { matchLabels: { app: ciam-auth }}}. During kubectl drain node, K8s respects this and won't evict more pods than allowed.

CIAM Spring Boot on K8s: Typical sizing: requests {512Mi, 500m}, limits {1Gi, 2}. With Flyway migrations, the startupProbe allows ~5 minutes (Spring 10-30s + Flyway 30-60s). The readinessProbe polls /actuator/health/readiness, and a custom PingHealthIndicator marks the app down when Ping is unreachable so traffic routes elsewhere. A PDB minAvailable: 2 + Deployment maxUnavailable: 0 keeps 2+ pods serving auth throughout an upgrade — zero downtime.

The problem


Kubernetes killed your pod because your app was doing its job.




  
Both probes pointed at /actuator/health

  
A JVM takes 30 seconds to warm up. The liveness probe starts checking at 10, gets no
  answer, and concludes the app is dead — so it restarts it. Which takes 30 seconds.

  

    livenessProbe: /actuator/health
    readinessProbe: /actuator/health
    initialDelaySeconds: 10 ⚠
    CrashLoopBackOff ⚠
    a boot loop that never converges ⚠
  

  
The app was never broken. The probe was asking the wrong question, and a
  slow DB connection at startup is enough to trigger it forever.






  
Two different questions, two different endpoints

  

    liveness — "are you ALIVE?"  → /actuator/health/liveness
    ↓ if no: RESTART the pod. This is a big hammer.
    readiness — "can you take TRAFFIC?" → /actuator/health/readiness
    ↓ if no: remove from the Service. Pod keeps running.
    startup — "have you finished booting?" → protects a slow JVM from both
  






  Liveness failing restarts you. Readiness failing just takes you out of the load
  balancer. Point liveness at anything that can be temporarily unhappy — a database, a
  downstream API — and a brief outage in a dependency becomes a restart storm across every
  replica you own.





  

    The readiness probe
    
Your DB connection pool is exhausted. I will stop sending you requests until it
    recovers. You keep running.

  

  

    The liveness probe
    
And if I were checking the same thing, I would have killed you instead — losing your
    in-flight requests and your warm JIT, and making the pool problem worse for everyone
    else.

  

  

    The startup probe
    
Which is why I exist: I hold the other two off entirely until the JVM has actually
    finished booting.

  





The mechanism


Shutdown is a conversation, and the order matters.




  
    
    
  1. you kubectl delete — or a rollout replaces the podt=0
    2. 
    
  2. the pod is marked Terminating and REMOVED from the Service endpointsstop new traffic
    3. 
    
  3. SIGTERM is sent to PID 1 — Spring begins graceful shutdownSIGTERM
    4. 
    
  4. in-flight requests finish, up to spring.lifecycle.timeout-per-shutdown-phasedrain
    5. 
    
  5. after terminationGracePeriodSeconds (default 30) — SIGKILL, no mercySIGKILL
    6. 
  

  
Steps 2 and 3 race. Endpoint removal propagates through kube-proxy on
  every node asynchronously, so requests can still arrive for a second or two AFTER SIGTERM.
  That is why a preStop sleep of a few seconds is standard practice — it is not
  superstition, it is waiting for the cluster to catch up with a decision it already made.





The JVM's other Kubernetes surprise is memory. Set a container memory limit and
forget the heap, and the JVM sizes itself against what it thinks the machine has — then the
kernel OOM-kills the container with exit code 137 and no Java stack trace, because the JVM
never saw it coming. Modern JVMs are container-aware
(-XX:MaxRAMPercentage=75), but the limit still has to leave room for
metaspace, thread stacks and native buffers, which live outside the heap. A pod that dies at
137 with no exception in the log is almost always this.




  
Your CIAM API's database goes down for 40 seconds. Liveness and readiness both
  point at /actuator/health, which reports the DB. What happens?

  
  
  
  
That is what happens if only READINESS reports the DB — which is
  the configuration you want. Here liveness reports it too.

  
Readiness failing does remove the pods from the Service, so
  traffic stops rather than erroring. But that is not the end of it, because liveness is
  failing at the same time.

  
Right, and it is the worst outcome. Liveness failing means
  RESTART, so every replica is killed and restarted — each one taking 30 seconds to boot into
  a database that is still down, and failing again. A dependency outage became a full outage
  of your own service. Liveness must only test the process itself.

Questions from the back row



  
Do I need a startup probe if I already set initialDelaySeconds?

  
A startup probe is better, because a delay is a guess you have to make twice —
  too short and you restart a healthy boot, too long and a genuinely hung process sits there
  unnoticed. A startup probe polls until success and only then hands over to liveness, so slow
  boots are tolerated without making liveness sluggish forever after.





  
Why does my container exit 137 with nothing in the log?

  
137 is 128+9 — SIGKILL, and almost always the kernel OOM killer. The JVM does
  not get to write a stack trace because it is not asked. Check whether heap plus metaspace
  plus thread stacks plus native memory fits inside the container limit, not just the heap.
  It is the single most common "Spring works locally, dies in the cluster" cause.





  
Are requests really lost during a rolling update?

  
They can be, and it is usually this: the app stops accepting connections the
  instant SIGTERM lands, while endpoint removal is still propagating. Graceful shutdown plus a
  short preStop sleep closes the window. If you see a handful of 502s on every
  deploy and nowhere else, that is what you are looking at.

1 — Dockerfile for Spring Boot




# Multi-stage: build with Maven, run with JRE only
FROM eclipse-temurin:21-jdk-alpine AS build
WORKDIR /app
COPY pom.xml .
COPY src ./src
RUN mvn package -DskipTests

FROM eclipse-temurin:21-jre-alpine
WORKDIR /app
# Extract layers (Spring Boot layertools) for better caching
COPY --from=build /app/target/app.jar app.jar
RUN java -Djarmode=layertools -jar app.jar extract

# Run as non-root (security best practice)
RUN addgroup -S appgroup && adduser -S appuser -G appgroup
USER appuser

EXPOSE 8080
ENTRYPOINT ["java", "-jar", "app.jar"]


For faster K8s startup use Spring Boot Layer Jars or GraalVM native images (near-instant startup, 10× less memory). Layer jars improve Docker cache reuse — dependencies rarely change, so they cache well.









2 — Health Probes via Spring Actuator




# application.yml
management:
  endpoint.health.probes.enabled: true
  health.livenessstate.enabled: true
  health.readinessstate.enabled: true

# Kubernetes deployment spec
livenessProbe:
  httpGet:
    path: /actuator/health/liveness
    port: 8080
  initialDelaySeconds: 60   # give Spring time to boot
  periodSeconds: 10
  failureThreshold: 3       # restart after 3 fails
readinessProbe:
  httpGet:
    path: /actuator/health/readiness
    port: 8080
  initialDelaySeconds: 30
  periodSeconds: 5









3 — Graceful Shutdown




When K8s sends SIGTERM to terminate a pod it waits terminationGracePeriodSeconds (default 30s) before SIGKILL. Spring Boot 2.3+ supports graceful shutdown out of the box.


# application.yml
server:
  shutdown: graceful    # drain in-flight requests first
spring.lifecycle:
  timeout-per-shutdown-phase: 25s  # leave 5s buffer for SIGKILL

# preStop hook ensures the pod is removed from Service endpoints
# BEFORE SIGTERM arrives (avoids a 503 race condition)
lifecycle:
  preStop:
    exec:
      command: ["/bin/sh", "-c", "sleep 5"]
