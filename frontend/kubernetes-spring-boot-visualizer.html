Spring Boot on Kubernetes

Container image, health probes, graceful shutdown, and resource limits — the K8s-native Spring Boot playbook.

How do you run Spring Boot on Kubernetes — and what does K8s-native actually mean?

Running Spring Boot on Kubernetes requires understanding how Kubernetes manages container lifecycle — and Spring Boot has specific features designed to integrate with that lifecycle. Container image: Spring Boot 2.3+ supports building Docker images directly: mvn spring-boot:build-image (uses Cloud Native Buildpacks, no Dockerfile needed) or a multi-stage Dockerfile. Use a minimal JRE base image (eclipse-temurin:21-jre-alpine) not a full JDK. Use layered JARs (SPRING_LAYERED_JARS=true) so unchanged library layers are cached in Docker — faster builds. Health probes: Kubernetes checks three probes. startupProbe: is the app done starting? K8s doesn't check liveness until startupProbe passes — critical for slow-starting Spring Boot apps (10-30 seconds). readinessProbe: is the app ready to receive traffic? If readiness fails, pod is removed from Service endpoints — no traffic until ready. Maps to Spring Boot Actuator /actuator/health/readiness. livenessProbe: is the app alive (not deadlocked)? If liveness fails, Kubernetes KILLS and restarts the pod. Maps to /actuator/health/liveness. Graceful shutdown: when Kubernetes stops a pod (rolling update, scale-down), it sends SIGTERM. Spring Boot 2.3+ handles SIGTERM: stops accepting new requests (server.shutdown=graceful), drains in-flight requests (up to spring.lifecycle.timeout-per-shutdown-phase=30s), then exits. Kubernetes sends SIGKILL 30s after SIGTERM if not exited — set terminationGracePeriodSeconds: 60 on the pod. Resource limits: always set requests (what the scheduler uses to find a node) and limits (hard cap). Spring Boot JVM: container-aware GC (-XX:+UseContainerSupport, default in Java 10+) reads cgroup memory limits and sizes heap accordingly.

JVM + K8s gotchas

JVM heap sizing: without container awareness, JVM reads the node's total RAM (e.g., 16 GB) and sets heap to 4 GB — but your pod limit is 1 GB → OOMKilled immediately. Fix: Java 10+ with -XX:+UseContainerSupport (default) reads cgroup limit (1 GB) and sizes heap accordingly (~256 MB). Or explicitly: -Xmx512m. Slow startup probe: Spring Boot with lots of beans, DB migrations (Flyway), and @PostConstruct initialization can take 20-60 seconds to start. Without a startupProbe, K8s may kill the pod for "failing liveness" before it's even started. Set startupProbe.failureThreshold: 60, periodSeconds: 5 = 300s max startup window. PodDisruptionBudget: ensures at least N pods are always up during node maintenance: kind: PodDisruptionBudget; spec: { minAvailable: 2; selector: { matchLabels: { app: ciam-auth }}}. During kubectl drain node, K8s respects this and won't evict more pods than allowed.

CIAM Spring Boot on K8s: Your CIAM auth service typical setup: requests: { memory: 512Mi, cpu: 500m }, limits: { memory: 1Gi, cpu: 2 }. Spring Boot with Flyway DB migrations: startupProbe allows 5 minutes (Spring takes 10-30s, Flyway might take 30-60s on large DB). readinessProbe polls /actuator/health/readiness — Spring marks the app NOT ready if the DB connection pool is saturated (custom HealthIndicator checks Ping connectivity): @Component public class PingHealthIndicator implements HealthIndicator { public Health health() { try { pingClient.ping(); return Health.up().build(); } catch (Exception e) { return Health.down().withDetail("ping", e.getMessage()).build(); } } }. Rolling update with minAvailable: 2 (PDB) + maxUnavailable: 0 (Deployment strategy): zero downtime, always 2+ pods serving auth traffic during upgrade.

1 — Dockerfile for Spring Boot




# Multi-stage: build with Maven, run with JRE only
FROM eclipse-temurin:21-jdk-alpine AS build
WORKDIR /app
COPY pom.xml .
COPY src ./src
RUN mvn package -DskipTests

FROM eclipse-temurin:21-jre-alpine
WORKDIR /app
# Extract layers (Spring Boot layertools) for better caching
COPY --from=build /app/target/app.jar app.jar
RUN java -Djarmode=layertools -jar app.jar extract

# Run as non-root (security best practice)
RUN addgroup -S appgroup && adduser -S appuser -G appgroup
USER appuser

EXPOSE 8080
ENTRYPOINT ["java", "-jar", "app.jar"]


For faster K8s startup use Spring Boot Layer Jars or GraalVM native images (near-instant startup, 10× less memory). Layer jars improve Docker cache reuse — dependencies rarely change, so they cache well.









2 — Health Probes via Spring Actuator




# application.yml
management:
  endpoint.health.probes.enabled: true
  health.livenessstate.enabled: true
  health.readinessstate.enabled: true

# Kubernetes deployment spec
livenessProbe:
  httpGet:
    path: /actuator/health/liveness
    port: 8080
  initialDelaySeconds: 60   # give Spring time to boot
  periodSeconds: 10
  failureThreshold: 3       # restart after 3 fails
readinessProbe:
  httpGet:
    path: /actuator/health/readiness
    port: 8080
  initialDelaySeconds: 30
  periodSeconds: 5









3 — Graceful Shutdown




When K8s sends SIGTERM to terminate a pod it waits terminationGracePeriodSeconds (default 30s) before SIGKILL. Spring Boot 2.3+ supports graceful shutdown out of the box.


# application.yml
server:
  shutdown: graceful    # drain in-flight requests first
spring.lifecycle:
  timeout-per-shutdown-phase: 25s  # leave 5s buffer for SIGKILL

# preStop hook ensures the pod is removed from Service endpoints
# BEFORE SIGTERM arrives (avoids a 503 race condition)
lifecycle:
  preStop:
    exec:
      command: ["/bin/sh", "-c", "sleep 5"]
