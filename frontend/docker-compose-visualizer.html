Docker Compose

Define and run multi-container applications with a single YAML file. Essential for local development with Spring Boot + PostgreSQL + Redis.

🎼 What is Docker Compose — and why does it replace manual docker run for multi-container apps?

Running an app locally means several containers — your Spring app, Postgres, Redis, maybe a Ping server — each a long docker run. Docker Compose declares them all in one compose.yaml: docker compose up starts everything, down removes it. Each service has an image/build, ports, environment, volumes and depends_on. Service discovery is by name (Spring reaches Postgres at jdbc:postgresql://postgres:5432), and a healthcheck + condition: service_healthy makes Compose wait until a dependency is actually ready, not just started. It's the local-dev cousin of Kubernetes — but not for production (no HA, multi-host, or self-healing).

  • One compose.yaml for many containers — up/down the whole stack.
  • Services discover by name — postgres:5432 from the app.
  • Healthcheck + service_healthy waits for ready, not just started.
  • Local-dev cousin of K8s — not for production (no HA/self-healing).

Full compose.yaml

services: postgres: image: postgres:16-alpine environment: POSTGRES_DB: ciam POSTGRES_USER: ciam_user POSTGRES_PASSWORD: secret volumes: - pg-data:/var/lib/postgresql/data healthcheck: test: ["CMD-SHELL", "pg_isready -U ciam_user"] interval: 5s retries: 5 ciam-auth: build: . # build from Dockerfile ports: - "8080:8080" environment: SPRING_DATASOURCE_URL: jdbc:postgresql://postgres:5432/ciam SPRING_DATASOURCE_USERNAME: ciam_user SPRING_DATASOURCE_PASSWORD: secret PING_BASE_URL: http://ping-server:9031 depends_on: postgres: condition: service_healthy # wait for healthcheck volumes: pg-data: # named volume, persists between restarts

Essential commands

# Start all services (detached): docker compose up -d # Start with rebuilding image: docker compose up -d --build # View logs (all services): docker compose logs -f # View logs (one service): docker compose logs ciam-auth -f # List running services: docker compose ps # Execute command in service: docker compose exec ciam-auth sh docker compose exec postgres psql -U ciam_user ciam # Stop and remove containers + networks: docker compose down # Also remove volumes (WARNING: destroys data!): docker compose down -v # Restart single service: docker compose restart ciam-auth # Scale a service: docker compose up -d --scale ciam-auth=3

Compose vs K8s

Docker Compose → Kubernetes equivalent. services: → Pods / Deployments. image: → spec.containers[].image. ports: - "8080:8080" → Service NodePort/LoadBalancer. environment: → ConfigMap + Secret env vars. volumes: - pg-data:/data → PersistentVolumeClaim. depends_on: → init containers or readinessProbe. healthcheck: → livenessProbe / readinessProbe. docker compose up → kubectl apply -f manifests/ or helm install. docker compose down → kubectl delete -f manifests/. Compose is for local development (single host). Kubernetes is for production (multi-host, HA, autoscaling). Many teams use Compose for local dev and Kubernetes for production — the mental model translates well. Compose is NOT suitable for production (no HA, no multi-host, no self-healing). Compose V2 (current): docker compose (no hyphen) is built into Docker Desktop. Old V1 was docker-compose (hyphen, separate Python binary).

CIAM local dev stack: A full compose.yaml: postgres + redis + ciam-auth (your Spring app) + ping-server + keycloak/mock-oauth for testing Entra flows. Spring reads DB creds from env vars (same names as the K8s Secret keys — Compose uses plaintext, prod uses real secrets), and depends_on: postgres: condition: service_healthy stops Flyway running before Postgres accepts connections. For remote debugging, an override adds JAVA_TOOL_OPTIONS: "-agentlib:jdwp=...,address=*:5005" and exposes 5005 — attach IntelliJ and set breakpoints.

1 — What Compose Solves

❌ Without Compose (4 commands, order matters)

docker network create app-net docker volume create pgdata docker run -d --name postgres \ --network app-net \ -v pgdata:/var/lib/postgresql/data \ -e POSTGRES_PASSWORD=secret postgres:16 docker run -d --name api \ --network app-net -p 8080:8080 \ -e DB_URL=jdbc:postgresql://postgres:5432/db \ myapp:latest

✓ With Compose (1 command)

docker compose up -d # That's it. All services start in # the right order with correct network # and volumes automatically. docker compose down

2 — Annotated docker-compose.yml — Click Each Section

# docker-compose.yml (or compose.yaml) services: # required top-level key
services — the top-level key. Each named child is a service (= one container). Docker Compose v3+ dropped the "version:" header — just start with "services:" in modern Compose files.
postgres: image: postgres:16 environment: POSTGRES_DB: mydb POSTGRES_USER: app POSTGRES_PASSWORD: secret volumes: - pgdata:/var/lib/postgresql/data healthcheck: test: ["CMD-SHELL", "pg_isready -U app"] interval: 5s timeout: 3s retries: 5
postgres service:
• image: pull from Docker Hub if not cached locally
• environment: sets env vars inside the container
• volumes: pgdata (named volume) mounted at PostgreSQL's data directory — data survives docker compose down
• healthcheck: Compose waits for this to pass before marking the service "healthy". Other services that depends_on: postgres: condition: service_healthy won't start until pg_isready returns OK.
api: build: context: . dockerfile: Dockerfile ports: - "8080:8080" - "8081:8081" # actuator environment: SPRING_DATASOURCE_URL: jdbc:postgresql://postgres:5432/mydb SPRING_DATASOURCE_USERNAME: app SPRING_DATASOURCE_PASSWORD: secret SPRING_PROFILES_ACTIVE: docker depends_on: postgres: condition: service_healthy
api service:
• build: context: . — build the image from the Dockerfile in the current directory instead of pulling a pre-built one
• ports: map host → container. Two ports: app (8080) and Spring Boot Actuator (8081)
• environment: Spring Boot picks up SPRING_DATASOURCE_URL — overrides application.properties. "postgres" resolves to the postgres container via Compose DNS.
• depends_on: condition: service_healthy — waits until the postgres healthcheck passes before starting. Prevents "Connection refused" on startup.
redis: image: redis:7-alpine command: redis-server --requirepass redissecret
redis service:
• image: redis:7-alpine — alpine variant is much smaller (~30MB vs ~120MB)
• command: overrides the container's default CMD. Here we add a password requirement.
volumes: pgdata: # declare named volume
volumes — top-level declaration of named volumes. Docker creates and manages these. They survive docker compose down but are removed by docker compose down -v.

Referenced in service volumes: section as pgdata:/path/in/container.
networks: default: driver: bridge
networks — Compose automatically creates a default network for all services. You can omit this block entirely and it still works. Define custom networks for fine-grained isolation (e.g., front-tier and back-tier networks).

4 — Essential docker compose Commands

CommandWhat it does
docker compose upCreate and start all services (foreground — logs stream to terminal)
docker compose up -dStart in detached (background) mode
docker compose up --buildForce rebuild images before starting (picks up Dockerfile changes)
docker compose downStop and remove containers and networks (volumes preserved)
docker compose down -vAlso remove named volumes — wipes database data
docker compose logs -f apiStream logs from the api service
docker compose psList services and their status
docker compose exec api /bin/shOpen shell in running api container
docker compose restart apiRestart a single service without affecting others
docker compose pullPull latest versions of all images
docker compose configValidate and display the resolved compose configuration
