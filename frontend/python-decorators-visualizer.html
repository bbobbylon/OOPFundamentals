Python Decorators

A decorator is just a function that takes a function and returns a (usually wrapped) function. The @ syntax is pure sugar. Once you see that @deco above def f means f = deco(f), every decorator — timing, caching, auth checks, retries, Flask routes — stops being magic. Press ▶ and watch the rewrap happen.

🎀 What is a Python decorator — and how does the @ syntax actually work?

A decorator is a callable that takes a function (or class) and returns a modified version — @deco is pure sugar for f = deco(f). Once that clicks, every decorator is transparent: FastAPI's @app.get, @lru_cache, @dataclass are all just functions returning a (usually wrapped) function. The wrapper pattern adds behavior before/after the call; functools.wraps preserves the original's name/docstring. To pass args (@require_role('ADMIN')) you write a three-level factory → decorator → wrapper. It's the same idea as Spring's @Transactional/@Cacheable AOP — minus the bytecode proxies.

  • @deco = f = deco(f) — that's the whole secret.
  • The wrapper adds cross-cutting behavior — auth, caching, timing, retry.
  • functools.wraps keeps name/docstring — or tracebacks all say "wrapper".
  • Args need a factory — factory → decorator → wrapper (three levels).

Decorator = f = deco(f)

import functools, time def timer(func): # func = the decorated function @functools.wraps(func) # preserve name/docs def wrapper(*args, **kwargs): start = time.perf_counter() result = func(*args, **kwargs) # call original elapsed = time.perf_counter() - start print(f'{func.__name__} took {elapsed:.3f}s') return result return wrapper # return the wrapper # @timer is sugar for: # def sync_users(): ... # sync_users = timer(sync_users) ← same thing @timer def sync_users(): time.sleep(0.5) return {'synced': 100} sync_users() # prints: sync_users took 0.500s sync_users.__name__ # 'sync_users' (not 'wrapper')

or, the decorator that crashes on an integer that appears nowhere in your code

The problem

You wrote @retry(3) exactly the way this page just taught. retry itself was still the old two-layer shape — and Python never once tells you that's the actual problem.

TypeError: 'int' object is not callable — on a decorator, at the @ line

Someone half-refactored a plain decorator into a configurable one and stopped partway: def retry(func): @functools.wraps(func) def wrapper(*a, **k): ...; return wrapper — still only two layers, still expecting func directly. They apply it as @retry(3) above def transfer_funds(): ..., meaning to allow three attempts.

The crash lands immediately, at the @retry(3) line, before transfer_funds even finishes being defined: TypeError: 'int' object is not callable. Nowhere in this file does anyone write 3(...). The traceback points inside wrapper, at a variable called func — and func, somehow, is 3.

@retry(3) parses fine ✓ — valid Python syntax retry(3) runs fine and returns a real function ✓ that function is then CALLED with transfer_funds as its argument ⚠

transfer_funds never gets a chance to exist as a decorated function. The name is never bound, the module fails to import, and the only clue is an integer that was supposed to mean "three attempts."

Add the missing layer — or drop the parentheses that promise one
Give retry a real outer layer: def retry(times): def decorator(func): def wrapper(*a,**k): ...; return wrapper; return decorator ↓ now retry(3) returns decorator, and decorator(func) is what finally receives transfer_funds — three calls deep, on purpose Or, if no configuration is actually needed, drop the parentheses: @retry, not @retry() ↓ this matches what a plain two-layer decorator's contract actually promises: "hand me the function directly" Read every `@expr` as "call expr, then call the result on the function below it" — no exceptions
@expr above a def desugars to exactly one thing: f = expr(f). There is no special decoration machinery beyond that single rule. If expr is retry(3), Python evaluates retry(3) first — one ordinary function call, which can succeed even when the whole setup is wrong — and then calls whatever THAT returned on f. Two calls happen, always, whether or not the code you wrote was designed for two.
A decorator factory is a vending machine: you put in 3, it hands you a decorator. A plain decorator is a turnstile: you put the function itself through it. Wire the turnstile up behind the vending machine's coin slot, and the coin — 3 — is what walks through the turnstile instead of your function.

The @ syntax

Because typing retry(3) alone only builds wrapper — it never hands wrapper anything to call. @retry(3) does both in one breath: build wrapper, then immediately call it on transfer_funds. That second call is decoration itself, and it's the one that breaks.

The mechanism

Watch the two calls hiding inside one line of syntax.

  1. Python sees @retry(3) directly above def transfer_funds(): ...syntax
  2. It evaluates retry(3) first — an ordinary call, with func bound to 3 inside retrycall #1
  3. @functools.wraps(3) decorates a fresh wrapper closure — no error; wraps silently skips attributes an int doesn't havesilently fine
  4. retry(3) returns that wrapper, a real function closing over func = 3returns a REAL function
  5. Python now calls that returned function on the actual target: wrapper(transfer_funds)call #2 — this IS decoration
  6. Inside wrapper, func(*a, **k) runs as 3(transfer_funds) → TypeErrorcrash

Step 5 is the one nobody visualizes. @expr is not "apply some decoration magic" — it is two chained function calls, and the second one is where the actual function you wrote gets passed in. Everything before that point can succeed perfectly, including a factory that was never a factory, because call #1 doesn't know or care what call #2 is about to hand it.

what really happens →
retry(3) treated as "skip configuration, just decorate" retry(3) returns wrapper, then wrapper(transfer_funds) runs a clear TypeError naming retry() and the missing layer

The middle option is the only one Python ever runs — there is no special-casing for "oh, this decorator wasn't built as a factory, let me adjust." The error you get names int, not retry, because by the time anything crashes, retry has already finished running successfully and handed off to wrapper.

A teammate pastes in an old plain decorator, def audited(func): ...; return wrapper — no configuration argument anywhere — and applies it as @audited(), with empty parentheses, above def transfer_funds(): .... What happens?

Right. @audited() means "call audited() first" — zero arguments — and a plain decorator declared as def audited(func): requires exactly one. It fails immediately, for the missing-argument mirror image of the @retry(3) story: wrong SHAPE either way, just missing instead of extra this time.

Parentheses always mean "call this," never "ignore this." Empty parentheses are still a call — with zero arguments — and audited was never written to accept zero.

This fails at decoration time, the same moment @retry(3) failed — not later, and not when transfer_funds is called. transfer_funds never successfully becomes a name at all.

Where you have seen this before

"Call the wrapper, then call what it gives you" is not special to Python's @ syntax — plenty of ecosystems build a two-call handshake and plenty of engineers skip one of the calls.

A Java annotation with the wrong element shape

@Retryable(times = 3) requires an annotation type that actually declares a times element — get the shape wrong and javac refuses to compile. Java catches this mismatch before the program ever runs; Python's version of the same mistake only surfaces the moment the decorator line executes.

javac ✓ catches it at compile timePython ⚠ catches it at import/decoration time

TypeScript's @Input() vs @Input

Angular's own decorators follow the identical two-call shape: @Input() calls a factory that returns the real decorator, then applies it to the property. Forgetting the parentheses on a factory-style decorator, or adding them to a plain one, is the same class of mistake in a different syntax.

@Input() — factory, needs the call@Input — would be the plain form, if Angular offered one

Express middleware: app.use(cors) vs app.use(cors())

cors is a factory — cors() returns the actual middleware function. Pass the factory itself to app.use without calling it, and Express happily wires up the wrong thing, running the factory as if it were middleware instead of the configured handler it was supposed to produce.

cors() ✓ the configured middlewarecors ⚠ the unconfigured factory itself
The whole page on a napkin: a decorator is a callable that takes a function and returns a replacement, @name is sugar for name = decorator(name), and an argument-taking decorator needs a third nested layer to make that math work. The one new sentence this block adds: because @expr is always two calls chained together, a decorator built for the wrong number of layers doesn't fail with a helpful message about layers — it fails wherever the second call happens to land, blaming whatever object was standing in for your function at that moment.

1. The anatomy — three nested layers

import functools, time

def timed(func):                 # ① takes the original function
    @functools.wraps(func)      # ③ copy __name__, __doc__, signature
    def wrapper(*args, **kwargs):  # ② accepts ANY call
        start = time.perf_counter()
        result = func(*args, **kwargs)   # call the real one
        dur = time.perf_counter() - start
        print(f"{func.__name__} took {dur*1000:.2f}ms")
        return result
    return wrapper                  # hand back the replacement

@timed
def work(n):
    return sum(range(n))
Brain Power. Why does wrapper take *args, **kwargs instead of the same parameters as work? Because a good decorator is generic — it should wrap any function regardless of its signature. Capturing with *args, **kwargs and re-spreading them forwards the call transparently.

2. @functools.wraps — keep the identity

Without @wraps — identity lost

work.__name__   # 'wrapper' 😦
work.__doc__    # None
# help(), tracebacks, and debuggers
# now all say "wrapper"

With @wraps — identity preserved

work.__name__   # 'work' ✓
work.__doc__    # the real docstring
work.__wrapped__ # the original fn
# @wraps copies the metadata over

Always use @functools.wraps(func) on your wrapper. It's one line and it stops your decorator from making every function look like wrapper in stack traces.

3. Decorators that take arguments — one more layer

def retry(times):              # ① the FACTORY — takes the arg
    def decorator(func):        # ② the real decorator
        @functools.wraps(func)
        def wrapper(*a, **k):    # ③ the wrapper
            for i in range(times):
                try: return func(*a, **k)
                except Exception:
                    if i == times - 1: raise
        return wrapper
    return decorator

@retry(3)                     # retry(3) RETURNS a decorator, then it's applied
def flaky(): ...

@retry(3) means: call retry(3) first (it returns decorator), then apply that to flaky. That's why an argument-taking decorator needs three nested functions instead of two.

Stacking (scenario ④): decorators apply bottom-up but execute top-down. @a over @b over def f builds a(b(f)) — so b wraps f first, then a wraps that. At call time you enter a's wrapper first. Order matters: @app.route over @login_required is not the same as the reverse.
