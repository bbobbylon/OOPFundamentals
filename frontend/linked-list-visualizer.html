Linked List — Nodes & Pointers

Each node holds a value and a pointer to the next node. The last one points to null.

🧩 What is a Linked List — and how do pointer-chained nodes enable O(1) insertions that arrays can never match?

A Linked List is a linear data structure made of nodes — each node holds a data value and a pointer (reference) to the next node. The last node's next pointer is null. Unlike an array, linked list nodes are scattered anywhere in memory; they are connected only by these next pointers, not by physical adjacency. This one structural difference creates an entirely different trade-off profile compared to arrays. O(1) insertion and deletion at known positions: to insert a node between nodes A and C (with B going in the middle), you only update two pointers: A.next = B and B.next = C. No elements need to shift. To delete node B: A.next = B.next (and handle B's memory). This is why Java's LinkedList can add/remove at the front or middle instantly — no array shuffling. O(n) access by index: to find the 5th element, you must start at the head and follow 5 next pointers. There is no mathematical formula to jump directly to position 5 like an array (where element[5] = base_address + 5 × element_size). Types: Singly linked (next pointer only — forward traversal only). Doubly linked (both next AND prev pointers — bidirectional traversal, O(1) delete of any node if you have a reference to it). Circular (tail.next = head — useful for round-robin scheduling, music playlist loops). Key algorithms: Reverse a linked list (three-pointer technique: prev/curr/next — O(n), O(1) space). Detect a cycle (Floyd's algorithm: fast pointer moves 2 nodes, slow pointer moves 1 — if they meet, there's a cycle). Find middle (fast/slow pointer — when fast reaches end, slow is at middle). When to use vs ArrayList: LinkedList wins when you insert/delete at the front or middle frequently and don't need random access. ArrayList wins for everything else — it has better cache performance (contiguous memory), O(1) random access, and lower per-element overhead (no pointer storage). Java's LinkedList implements both List and Deque; as a Deque it's useful for double-ended queues where you add/remove from both ends.

Reverse linked list (in-place)

// Reverse: 1→2→3→4→null becomes 4→3→2→1→null // Three pointers: prev, curr, next // O(n) time, O(1) space — classic interview problem ListNode reverse(ListNode head) { ListNode prev = null; // the reversed part (starts empty) ListNode curr = head; // current node being processed while (curr != null) { ListNode next = curr.next; // SAVE next before overwriting curr.next = prev; // reverse the pointer prev = curr; // advance prev curr = next; // advance curr } return prev; // prev is now the new head } // Step trace for 1→2→3: // init: prev=null, curr=1 // iter1: next=2, 1.next=null, prev=1, curr=2 // iter2: next=3, 2.next=1, prev=2, curr=3 // iter3: next=null,3.next=2, prev=3, curr=null // return 3 (new head): 3→2→1→null ✓

Floyd's cycle detection

// Floyd's algorithm: detect cycle in O(n) time, O(1) space // Idea: fast pointer moves 2 steps, slow 1 step // If cycle exists: fast "laps" slow → they meet inside cycle // If no cycle: fast reaches null boolean hasCycle(ListNode head) { ListNode slow = head; // moves 1 node per step ListNode fast = head; // moves 2 nodes per step while (fast != null && fast.next != null) { slow = slow.next; // advance 1 fast = fast.next.next; // advance 2 if (slow == fast) return true; // CYCLE: they met } return false; // fast hit null → no cycle } // Extension: find cycle START // After meeting, reset slow to head // Move both one step at a time → they meet at cycle start // Math proof: distance from head to cycle start // equals distance from meeting point to cycle start

ArrayList vs LinkedList

// ArrayList: backed by contiguous array // get(i) = O(1) — index = base + i*size (direct) // add(tail) = O(1) amortized (doubles when full) // add(middle) = O(n) — must shift all elements right // remove(i) = O(n) — must shift elements left // Cache-friendly: contiguous memory = CPU prefetcher works well // LinkedList: scattered nodes with pointers // get(i) = O(n) — must walk from head // addFirst() = O(1) — just update head pointer // addLast() = O(1) — just update tail pointer // add(middle) = O(n) to find + O(1) to link = O(n) // NOT cache-friendly: nodes scattered in heap // CHOOSE LinkedList WHEN: // ✅ Frequent addFirst/removeFirst (queue, deque, LRU) // ✅ Implementing a stack (addFirst/removeFirst) // CHOOSE ArrayList WHEN: // ✅ Random access by index (99% of List usage) // ✅ Iteration (cache-friendlier = faster in practice)

In CIAM / Context: Linked lists underpin several Spring and CIAM patterns: Spring's filter chain (SecurityFilterChain) is literally a linked list of filters — each filter calls chain.doFilter() to invoke the next filter. Spring's ApplicationContext uses linked-list-like bean post-processor chains. OAuth authorization code flows maintain a linked history of redirect steps. Java's LinkedList used as a Deque is the standard implementation for LRU cache eviction queues — you add new entries at the tail and remove expired entries from the head in O(1). Floyd's cycle detection is relevant to detecting circular bean dependencies in Spring (which would cause an infinite loop during context startup).

The decisive race — addFirst() on each

Both structures store the same numbers. Click addFirst(0) to insert at index 0 on both. Watch what happens. The linked list rewires one pointer. The ArrayList shifts every existing element one slot to the right.

LinkedList — O(1) at head

operations: 0

ArrayList — O(n) shifting

operations: 0

At n = 1,000,000, the LinkedList still does ~1 operation. The ArrayList does ~1,000,000 shifts. That's the difference between <1µs and ~10ms.

The flip side — get(index) is where ArrayList wins

ArrayList stores everything in a contiguous block of memory. list.get(500_000) is just memory[base + 500_000 * sizeof(ref)] — one calculation, one fetch. LinkedList has to walk 500,000 next pointers from the head. Worse, the nodes are scattered across the heap, so each step is a cache miss. This is why LinkedList is rarely the right answer in modern Java — even when the algorithm "should" favor it, ArrayList's cache friendliness usually wins.

Where you actually use a linked list

📝 LRU caches (with HashMap)

A doubly linked list + HashMap is the textbook LRU cache. The list gives you O(1) reorder-to-front-on-access; the map gives you O(1) lookup. Java's LinkedHashMap is this exact data structure.

🎵 Music / video playlists

"Next track" and "previous track" are pointer hops on a doubly linked list. Inserting a song mid-queue is O(1) once you have the surrounding nodes — no shifting.

↩️ Undo / redo stacks

Each operation links to the previous and next state. Going back is one hop. Editors, photoshop, IDEs all use linked structures for undo history.

🧵 Process schedulers

OS run queues are often linked lists. Moving a process between queues is just pointer surgery — no copying, no shifting. Speed matters in kernel code.

🧠 Adjacency lists for graphs

Each vertex stores a linked list of edges. Easy to add/remove edges, easy to iterate neighbors. (We use this in the graph visualizer.)

🔗 Hash collision chains

HashMap buckets are linked lists (then trees once they get long). That's how chaining works under the hood. You don't see them, but you use them constantly.

The Java code

// A textbook singly linked list node.
class Node<T> {
    T value;
    Node<T> next;

    Node(T value) { this.value = value; }
}

public class MyLinkedList<T> {
    private Node<T> head;
    private int size = 0;

    // O(1) — just rewire the head pointer
    public void addFirst(T value) {
        Node<T> node = new Node<>(value);
        node.next = head;
        head = node;
        size++;
    }

    // O(n) — must walk to the tail to find where to attach
    public void add(T value) {
        Node<T> node = new Node<>(value);
        if (head == null) { head = node; size++; return; }
        Node<T> cur = head;
        while (cur.next != null) cur = cur.next;
        cur.next = node;
        size++;
    }

    // O(n) — index lookups are slow on linked lists
    public T get(int i) {
        Node<T> cur = head;
        for (int k = 0; k < i; k++) cur = cur.next;
        return cur.value;
    }
}
