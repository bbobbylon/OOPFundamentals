Bean Lifecycle & Dependency Injection

Spring manages every @Component bean — creating it, injecting its dependencies, running lifecycle callbacks, and eventually destroying it. Understanding this deeply prevents a whole class of subtle bugs.

1 — Bean Scopes — How Many Instances Spring Creates

Click each scope to understand when Spring creates a new instance vs reuses an existing one:

@Scope("singleton") — DEFAULT

One instance per ApplicationContext — shared by everyone

@Scope("prototype")

New instance every time the bean is requested

@RequestScope

One instance per HTTP request — destroyed when response is sent

@SessionScope

One instance per HTTP session — lives as long as the user's session
Scope mismatch bug: injecting a prototype or request scope bean into a singleton captures a single instance forever — the short-lived bean never refreshes. Fix: inject ObjectProvider<T> or use @Lookup.

4 — Resolving Ambiguity: @Qualifier & @Primary

When multiple beans implement the same interface, Spring doesn't know which to inject. Use @Primary as the default or @Qualifier to be explicit:

// Two implementations of the same interface @Service("smtpNotifier") public class SmtpNotificationService implements NotificationService { ... } @Service("smsNotifier") @Primary // used by default when no @Qualifier present public class SmsNotificationService implements NotificationService { ... } // Injecting the @Primary bean (no qualifier needed) private final NotificationService notifier; // → SmsNotificationService // Injecting a specific implementation explicitly @Qualifier("smtpNotifier") private final NotificationService emailNotifier; // → SmtpNotificationService // Injecting ALL implementations as a list private final List<NotificationService> allNotifiers; // → [smtp, sms]

5 — Circular Dependency

What Spring sees (unsolvable with constructor injection)
OrderService
requires ↓
↓ needs ↓
PaymentService
requires ↓
↑ needs ↑
BeanCurrentlyInCreationException on startup
Three ways to break the cycle
// Fix 1: @Lazy — defer one dependency public OrderService(@Lazy PaymentService ps) { this.ps = ps; // ps is a proxy, resolved lazily } // Fix 2: setter injection (field injection also works // but constructor injection is preferred) @Autowired public void setPayment(PaymentService ps) { this.ps = ps; } // Fix 3 (best): redesign — extract shared // logic to a third, dependency-free bean @Service public class PaymentValidator { ... } // Both OrderService and PaymentService // depend on PaymentValidator — no cycle

6 — Conditional Beans — @Conditional & @Profile

// @Profile — only register bean for certain profiles @Service @Profile("!production") // active in dev & test, NOT in prod public class MockEmailService implements EmailService { public void send(String to, String body) { log.info("MOCK email to {}", to); } } @Service @Profile("production") public class SmtpEmailService implements EmailService { ... } // @ConditionalOnProperty — enable feature via config flag @Service @ConditionalOnProperty(name = "app.analytics.enabled", havingValue = "true") public class AnalyticsService { ... } // Set app.analytics.enabled=true in application.yml to activate // @ConditionalOnMissingBean — provide a default only if no custom bean exists @Bean @ConditionalOnMissingBean(CacheManager.class) public CacheManager defaultCacheManager() { return new ConcurrentMapCacheManager("default"); } // Auto-configuration uses this pattern everywhere — // your @Bean definition overrides the Spring Boot default

7 — Quick Reference

AnnotationPurposeWhen to use
@Component / @Service / @Repository / @ControllerRegister a class as a Spring beanAll are equivalent for bean creation; use semantic names for clarity
@AutowiredMark injection point (constructor, field, setter)Optional on single-constructor classes since Spring 4.3
@PrimaryDefault bean when multiple matchWhen you want a fallback without naming it everywhere
@Qualifier("name")Inject a specific bean by nameWhen you need explicit control over which impl is injected
@LazyDelay bean creation until first useHeavy beans not needed at startup; breaking circular dependencies
@PostConstructRuns after all dependencies are injectedInitialization logic that needs injected dependencies
@PreDestroyRuns before bean is removed from contextResource cleanup: closing connections, flushing caches
@Scope("prototype")New instance per injection pointStateful beans, builders, objects that must not be shared
@ConditionalOnPropertyRegister bean only if property is setFeature flags, optional integrations
@Profile("dev")Register bean only for given profilesDev-only mocks, environment-specific implementations
