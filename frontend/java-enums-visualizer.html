Java Enums — Zero to Hero

From simple constants to full-blown type-safe state machines — everything the enum keyword can do.

📇 What is a Java enum — and why is it far more powerful than a set of constants?

Before enums (Java 5) you'd use static final int constants — no type safety (nothing stops 99), no methods, no iteration. A Java enum fixes all of it: enum UserStatus { ACTIVE, SUSPENDED, LOCKED } is compiler-checked, with values() and valueOf(). And enums are full classes — they can carry fields, constructors, and methods (OK(200)), each variant is a singleton, and abstract-method enums implement the State/Strategy pattern without subclasses.

  • Type-safe named constants — the compiler rejects anything but a declared variant.
  • Enums are classes — fields, constructors, methods; each variant is a singleton.
  • Abstract-method enums = State/Strategy without subclasses.
  • Persist by name(), never ordinal() — reordering variants must not break stored rows.

Enums with fields and methods

enum Planet { MERCURY(3.303e+23, 2.4397e6), EARTH(5.976e+24, 6.37814e6); final double mass, radius; Planet(double m, double r) { this.mass=m; this.radius=r; } double surfaceGravity() { return 6.67300E-11*mass/(radius*radius); } }. Each variant carries data and can compute derived values. This turns enums into rich value objects. Planet.EARTH.surfaceGravity(). EnumSet: EnumSet.of(ACTIVE, PENDING) — bit-vector backed, extremely efficient. EnumMap: EnumMap<UserStatus, List<User>> — ordinal-indexed, faster than HashMap for enum keys.

Enum state machine pattern

enum OrderState { PENDING { @Override public OrderState next() { return PROCESSING; } }, PROCESSING { @Override public OrderState next() { return SHIPPED; } }, SHIPPED { @Override public OrderState next() { return DELIVERED; } }, DELIVERED { @Override public OrderState next() { throw new IllegalStateException("Already delivered"); } }; public abstract OrderState next(); }. Usage: order.state = order.state.next(). Each state knows its own transition rules — no giant switch statement in service code.

Enum serialization and JSON

Jackson serialises enum to its name by default: ACTIVE → "ACTIVE". To serialise as a different value: @JsonValue String toJson() { return name().toLowerCase(); } → "active". To deserialise: @JsonCreator static UserStatus from(String s) { return valueOf(s.toUpperCase()); }. In Spring: @GetMapping("/users?status={status}") — Spring automatically converts the string query param to the enum via valueOf(). Add @JsonProperty per variant for full control. Never rely on enum ordinal() for persistence — it changes if you reorder variants. Use name() or a dedicated code field.

CIAM / Spring Boot: Store enum UserStatus as @Enumerated(EnumType.STRING) (never ORDINAL — reordering corrupts rows); GET /api/users?status=ACTIVE auto-converts. enum IdpType { PING, ENTRA, KEYCLOAK } drives switch-expression routing, EnumSet.of(...) backs fast dashboard filters, and @JsonValue + @JsonCreator map snake_case API names.

What is an enum? Class constants with type safety

Before enums (Java 5), developers used integer constants for things like days or directions. The problem: nothing stopped you from passing an invalid integer where a day was expected. Enums solve this by making each constant its own type-safe object, so the compiler rejects nonsense values at compile time.

Pre-enum: int constants (bad)

// Nothing prevents calling this wrong: static final int MON = 0; static final int TUE = 1; // ... void scheduleMeeting(int day) { ... } scheduleMeeting(99); // compiles! logic error scheduleMeeting(SUIT_HEARTS); // also compiles!

With enum (good)

enum Day { MON, TUE, WED, THU, FRI, SAT, SUN } void scheduleMeeting(Day day) { ... } scheduleMeeting(Day.MON); // correct scheduleMeeting(99); // COMPILE ERROR scheduleMeeting(Suit.HEARTS); // COMPILE ERROR
Key fact: Every Java enum implicitly extends java.lang.Enum<E> and is implicitly final (unless it has abstract methods). Each constant is a public static final instance of the enum class itself. There is exactly one instance per constant — created when the class loads — making enum constants singletons by nature.

Implicit methods: values(), ordinal(), name(), valueOf()

enum Day { MON, TUE, WED, THU, FRI, SAT, SUN } // values() — returns all constants in declaration order for (Day d : Day.values()) { System.out.printf("%s ordinal=%d%n", d.name(), d.ordinal()); } // MON ordinal=0, TUE ordinal=1, … SUN ordinal=6 // name() — the string name as declared Day.WED.name() // "WED" // ordinal() — 0-based position (fragile! see Pitfalls tab) Day.FRI.ordinal() // 4 // valueOf() — parse from string Day d = Day.valueOf("SAT"); // Day.SAT Day.valueOf("SATURDAY"); // throws IllegalArgumentException // Comparison: == works (enums are singletons) Day.MON == Day.MON // true (reference equality is safe) Day.MON.equals(Day.MON) // also true, but == preferred
ordinal() anti-pattern: Never store or persist ordinal() values. If you insert a new constant between existing ones, all ordinals shift and your stored integers become wrong. Use a code field instead (see Fields & Methods tab).

Enums with fields, constructors, and methods — the Planet example

An enum constant is an object. Like any object it can carry data in fields and expose behaviour through methods. The constructor is called once per constant, when the class loads. Constructors are always implicitly private — you can never call new Planet() from outside.

enum Planet { // Each constant calls the constructor MERCURY(3.303e+23, 2.4397e6), VENUS (4.869e+24, 6.0518e6), EARTH (5.976e+24, 6.37814e6), MARS (6.421e+23, 3.3972e6); private final double mass; // kilograms private final double radius; // meters // Constructor — always private (implicit) Planet(double mass, double radius) { this.mass = mass; this.radius = radius; } static final double G = 6.67300E-11; double surfaceGravity() { return G * mass / (radius * radius); } double surfaceWeight(double otherMass) { return otherMass * surfaceGravity(); } } // Usage double earthWeight = 75.0; double mass = earthWeight / Planet.EARTH.surfaceGravity(); for (Planet p : Planet.values()) { System.out.printf("Weight on %s = %.2f%n", p, p.surfaceWeight(mass)); }

Adding behaviour: getters, toString, and custom logic

enum Coin { PENNY(1), NICKEL(5), DIME(10), QUARTER(25); private final int cents; Coin(int cents) { this.cents = cents; } public int getCents() { return cents; } @Override public String toString() { return name().charAt(0) + name().substring(1).toLowerCase() + " (" + cents + "¢)"; } } System.out.println(Coin.QUARTER); // Quarter (25¢) int total = Arrays.stream(Coin.values()) .mapToInt(Coin::getCents) .sum(); // 41

Enums with abstract methods — per-constant behaviour

An enum can declare an abstract method, which forces every single constant to provide its own implementation. This is like having a mini polymorphism system entirely within the enum — no inheritance hierarchy required. The enum class itself becomes abstract, but you never see that externally.

enum Operation { PLUS("+") { @Override public double apply(double x, double y) { return x + y; } }, MINUS("-") { @Override public double apply(double x, double y) { return x - y; } }, TIMES("*") { @Override public double apply(double x, double y) { return x * y; } }, DIVIDE("/") { @Override public double apply(double x, double y) { return x / y; } }; private final String symbol; Operation(String symbol) { this.symbol = symbol; } // Abstract — each constant MUST override this public abstract double apply(double x, double y); @Override public String toString() { return symbol; } } // Elegant dispatch — no if/else, no external switch for (Operation op : Operation.values()) { System.out.printf("%.1f %s %.1f = %.1f%n", 4.0, op, 2.0, op.apply(4,2)); } // 4.0 + 2.0 = 6.0 // 4.0 - 2.0 = 2.0 // 4.0 * 2.0 = 8.0 // 4.0 / 2.0 = 2.0
Why is this powerful? Each constant carries its own logic, not just data. When you add a new constant (e.g. MODULO), the compiler forces you to implement apply(). Compare this to a switch in external code, which silently falls through to a default if you forget a case.

Interface implementation — another way to add per-constant behaviour

interface Describable { String describe(); } enum Season implements Describable { SPRING { public String describe() { return "Warm and rainy"; } }, SUMMER { public String describe() { return "Hot and sunny"; } }, AUTUMN { public String describe() { return "Cool, leaves fall"; } }, WINTER { public String describe() { return "Cold and dark"; } }; } // Enums can also implement interfaces with default method bodies // so not every constant needs to override — only those that differ

EnumSet — blazingly fast sets for enums

EnumSet is a specialized Set implementation that stores enum constants as a bit vector — a single long if the enum has 64 or fewer constants. Each bit corresponds to an ordinal position. Set operations (add, contains, remove, retainAll) become pure bitwise operations: AND, OR, XOR. This makes EnumSet dramatically faster than HashSet for enums, while also using far less memory.

import java.util.EnumSet; enum Day { MON, TUE, WED, THU, FRI, SAT, SUN } // Factory methods (no public constructor) EnumSet<Day> weekdays = EnumSet.range(Day.MON, Day.FRI); EnumSet<Day> weekend = EnumSet.of(Day.SAT, Day.SUN); EnumSet<Day> all = EnumSet.allOf(Day.class); EnumSet<Day> none = EnumSet.noneOf(Day.class); // Complement (complement of weekdays = weekend) EnumSet<Day> comp = EnumSet.complementOf(weekdays); // comp = {SAT, SUN} // Iteration is in declaration order — always predictable weekdays.contains(Day.WED); // true weekdays.add(Day.SAT); // adds Saturday to weekdays set
Rule of thumb: whenever you need a Set of enum constants, use EnumSet. It implements the full Set<E> interface, so you can swap it in anywhere a Set is accepted. The only caveat: it cannot hold null.

EnumMap — ordered, fast map keyed by enum constants

import java.util.EnumMap; EnumMap<Day, List<String>> schedule = new EnumMap<>(Day.class); schedule.put(Day.MON, List.of("Standup", "Code review")); schedule.put(Day.WED, List.of("Architecture review")); schedule.put(Day.FRI, List.of("Retrospective")); // Internally backed by an array indexed by ordinal — O(1) everything // Iterates in declaration order (MON → SUN) schedule.forEach((day, events) -> System.out.println(day + ": " + events)); // Great for config tables: EnumMap<HttpMethod, Handler> routes = new EnumMap<>(HttpMethod.class); routes.put(HttpMethod.GET, this::handleGet); routes.put(HttpMethod.POST, this::handlePost);

Classic switch statement on an enum

The enum's name (not the full qualified path) is used in case labels — the compiler already knows the type from the switch expression. Note the common pitfall: forgetting a break causes fall-through to the next case.

enum Season { SPRING, SUMMER, AUTUMN, WINTER } Season s = Season.WINTER; switch (s) { case SPRING: case SUMMER: System.out.println("Warm: " + s); break; case AUTUMN: System.out.println("Cool: " + s); break; case WINTER: System.out.println("Cold: " + s); break; default: throw new AssertionError("Unknown season: " + s); } // Output: Cold: WINTER

Modern switch expression (Java 14+) — exhaustive, no fall-through

Switch expressions use -> (arrow) syntax. They are expressions (they return a value), they have no fall-through by design, and when switching on an enum the compiler can check exhaustiveness — if you add a new enum constant, the code stops compiling until you handle it.

// Switch expression — returns a value String description = switch (s) { case SPRING -> "Flowers blooming"; case SUMMER -> "Beach weather"; case AUTUMN -> "Leaves turning"; case WINTER -> "Snow and frost"; // No default needed — all 4 constants covered // Add MONSOON to enum → this file won't compile! }; // Multi-line arm with yield int months = switch (s) { case SPRING, SUMMER, AUTUMN, WINTER -> { System.out.println("Processing: " + s); yield 3; // yield instead of return inside switch expr } }; // Pattern matching in switch (Java 21) Object obj = Season.SUMMER; String msg = switch (obj) { case Season season when season == Season.SUMMER -> "It's summer!"; case Season season -> "Another season: " + season; case null -> "null"; default -> "Not a season"; };
Tip: Prefer switch expressions over switch statements for assignments. The exhaustiveness checking alone prevents entire classes of "forgot to handle the new case" bugs — a huge win when the enum is in a shared library and evolves over time.

Enum as a state machine — Order lifecycle

Enums are a natural fit for state machines. Each constant represents a state; the enum can hold transition logic (which states are reachable from here), guard predicates (can we enter this state?), and entry actions (what happens when we arrive?). The OrderStatus enum code

enum OrderStatus { PENDING { @Override public OrderStatus next() { return PROCESSING; } public boolean canCancel() { return true; } public String label() { return "Order received, awaiting payment"; } }, PROCESSING { @Override public OrderStatus next() { return SHIPPED; } public boolean canCancel() { return true; } public String label() { return "Payment confirmed, packing items"; } }, SHIPPED { @Override public OrderStatus next() { return DELIVERED; } public boolean canCancel() { return false; } // too late! public String label() { return "In transit with courier"; } }, DELIVERED { @Override public OrderStatus next() { throw new IllegalStateException("Terminal"); } public boolean canCancel() { return false; } public String label() { return "Delivered to customer"; } }, CANCELLED { @Override public OrderStatus next() { throw new IllegalStateException("Terminal"); } public boolean canCancel() { return false; } public String label() { return "Order was cancelled"; } }; public abstract OrderStatus next(); public abstract boolean canCancel(); public abstract String label(); }

Singleton pattern with enum — the best way

Josh Bloch (Effective Java) recommends a single-element enum as the best way to implement a Singleton. It is thread-safe (the JVM guarantees class initialization is atomic), serialization-safe (Java serialization never creates a second instance of an enum constant), and reflection-safe (you cannot call the constructor via reflection — the JVM blocks it).

// The cleanest singleton in Java enum AppConfig { INSTANCE; // one constant = one instance private final Properties props; AppConfig() { props = new Properties(); props.load(AppConfig.class.getResourceAsStream("/app.properties")); } public String get(String key) { return props.getProperty(key); } public void set(String key, String val) { props.setProperty(key, val); } } // Usage String host = AppConfig.INSTANCE.get("db.host"); // Try to break it — all fail: // Serialization: readObject() returns the existing constant // Reflection: constructor.newInstance() throws IllegalArgumentException // Clone: Enum.clone() always throws CloneNotSupportedException

== vs equals() on enums — why both work

// Both are correct for enums Day d = Day.MON; d == Day.MON // true ✓ d.equals(Day.MON) // true ✓ // WHY? Enum constants are singletons. // There is exactly one Day.MON object ever. // equals() on Enum is final and delegates to == // == is preferred because: // 1. NullPointerException safe // 2. Checked at compile time (type mismatch) // 3. Marginally faster (no virtual dispatch) Day maybeNull = null; maybeNull == Day.MON // false — no NPE maybeNull.equals(Day.MON) // NullPointerException!
// Compile-time protection with == Day d = Day.MON; Suit s = Suit.HEARTS; d == s // COMPILE ERROR — incompatible types // prevents logical bugs d.equals(s) // compiles (both are Object) // returns false at runtime — no error // but the bug goes undetected // Summary // Use == for enum comparisons // Use .equals() when working with wildcards // or when the type is Enum<?>

The ordinal() anti-pattern

Fragile — never do this

enum Priority { LOW, MEDIUM, HIGH } // Store ordinal in DB: db.save("priority", p.ordinal()); // 0,1,2 // Later someone adds CRITICAL: enum Priority { LOW, CRITICAL, MEDIUM, HIGH } // ↑ inserted here! // ordinals shift: LOW=0 CRITICAL=1 // MEDIUM=2 HIGH=3 // All stored values are now WRONG

Stable — use a dedicated field

enum Priority { LOW(1), MEDIUM(2), HIGH(3), CRITICAL(10); // explicit code private final int code; Priority(int code) { this.code = code; } public int getCode() { return code; } public static Priority fromCode(int c) { for (Priority p : values()) if (p.code == c) return p; throw new IllegalArgumentException(""+c); } }
Rule: ordinal() is only for internal use by EnumSet/EnumMap as an array index. Never store it, serialize it, or use it as a meaningful value in your domain logic.
