package.json — Advanced: Scripts, Workspaces, Exports & More

⚙️ What are advanced npm scripts — and how do workspaces, exports maps, and lockfiles power professional Angular projects?

Once you go beyond basic npm install and npm run build, package.json reveals a rich set of advanced features that power monorepo setups, library distribution, and CI optimization. Advanced scripts: npm scripts support automatic pre/post hooks — prebuild runs automatically before build, postbuild runs after. Use them for: code generation, lint enforcement before build, version bumping, test runs before publish. Scripts can chain commands with && (run B only if A succeeds), || (run B if A fails), or ; (always run B). For parallel execution: npm-run-all --parallel start:api start:ui. npm workspaces: a monorepo feature that lets you manage multiple packages in one repository. "workspaces": ["packages/*", "apps/*"] tells npm to hoist shared dependencies to the root node_modules. Running npm install at the root installs all workspace packages. Running npm run build --workspace=apps/ciam-portal targets a specific workspace. This replaces many uses of Lerna/Turborepo for simple monorepos. exports field: for library packages, the "exports" field precisely controls what consumers can import. Instead of exposing the entire package, you define entry points: "exports": { ".": "./dist/index.js", "./testing": "./dist/testing.js" }. Consumers can do import from 'my-lib' or import from 'my-lib/testing' but NOT arbitrary deep imports. Dependency management: overrides field lets you force a specific version of a transitive dependency (critical for security patches without waiting for upstream). peerDependencies declares what the host project must provide — Angular libraries use this to require specific Angular versions. optionalDependencies are installed if possible but won't fail the install if missing (native modules that may not compile on all platforms).

Pre/post hooks + chaining

Advanced Scripts

npm scripts are more powerful than they look. Beyond simple wrappers, they support pre/post hooks, cross-platform environment variables, parallel execution, and lifecycle events that npm itself fires automatically.

npm Lifecycle Hooks npm auto-fires these

npm fires certain script names automatically when specific commands are run. You don't call these — npm does.

preinstallnpm install (before)Check Node version, set env variables
postinstallnpm install (after)Build native modules, patch files, run setup
preparenpm install + npm publish (before packing)Build the project — runs even for git dependencies

Pre/Post Hooks for Any Custom Script

Prefix any script name with pre or post and npm will automatically run it before or after the main script. No configuration needed — it's purely naming convention.

// package.json
{
  "scripts": {
    "prebuild":  "rimraf dist",               // runs before "build"
    "build":     "ng build --configuration=production",
    "postbuild": "node scripts/copy-assets.mjs", // runs after "build"

    "pretest":   "ng lint",                   // lint before tests
    "test":      "ng test --watch=false",
    "posttest":  "node scripts/upload-coverage.mjs"
  }
}

cross-env — OS-Agnostic Environment Variables

On Windows, setting environment variables in scripts uses set VAR=value; on macOS/Linux it's VAR=value. cross-env normalises this so your scripts work everywhere.

// Without cross-env — breaks on Windows:
"build:prod": "NODE_ENV=production ng build"  // fails on cmd.exe

// With cross-env (install: npm i -D cross-env):
"build:prod": "cross-env NODE_ENV=production ng build"  // works everywhere
"build:staging": "cross-env NODE_ENV=staging API_URL=https://staging.api.com ng build"

concurrently & npm-run-all

concurrently parallel

// Run Angular dev server + mock API in parallel
"dev": "concurrently \"ng serve\" \"json-server --watch db.json --port 3000\""

// With labels and colors
"dev": "concurrently -n \"ng,api\" -c \"cyan,yellow\" \"ng serve\" \"json-server db.json\""

npm-run-all parallel or sequential

// run-p = run in parallel
"dev": "run-p serve:* watch:*"

// run-s = run in sequence
"ci": "run-s clean build test"

// Glob patterns for script groups
"build:*"  // matches build:app, build:lib, build:docs

$npm_package_version in Scripts

npm exposes all package.json fields as environment variables with the $npm_package_ prefix. The most useful is the version number — use it to tag Docker images or generate release notes.

// package.json
{
  "version": "2.1.4",
  "scripts": {
    "docker:build": "docker build -t myapp:$npm_package_version .",
    "release":      "echo Releasing v$npm_package_version"
  }
}
// On Windows with cross-env use %npm_package_version%

Workspaces — Monorepo Setup

Workspaces let you manage multiple packages in a single repository with a shared node_modules. npm, Yarn, and pnpm all support workspaces with slightly different configs.

npm Workspaces npm 7+

// Root package.json
{
  "name": "my-monorepo",
  "private": true,
  "workspaces": [
    "packages/*",  // every folder in packages/ is a workspace
    "apps/*"        // every folder in apps/ is a workspace
  ]
}

What npm workspaces do for you:

  • Hoisting: all dependencies installed into root node_modules/ — each package share the same copy
  • Symlinks: workspace packages symlinked into root node_modules/@mycompany/shared
  • Single lock file: one package-lock.json at the root covers all packages
  • Cross-package scripts: npm run build -w packages/shared runs in a specific workspace
// Running commands across workspaces
npm run build --workspaces                  // build every workspace
npm run build -w packages/shared            // build only shared
npm install lodash -w apps/web-app          // install lodash into web-app only
npm install --workspace=apps/admin express // long form

Local Package References

// apps/web-app/package.json — reference a local workspace package
{
  "dependencies": {
    "@mycompany/shared": "workspace:*",  // pnpm syntax — always latest local
    "@mycompany/ui":     "*"              // npm/yarn — any version (resolves local)
  }
}

npm will symlink node_modules/@mycompany/shared to the actual workspace folder. No need to publish to npm registry during development.

pnpm Workspaces Stricter isolation

pnpm uses a separate pnpm-workspace.yaml file instead of package.json. It also enforces strict isolation — packages can only access what they explicitly declare in their own package.json, preventing phantom dependency bugs.

# pnpm-workspace.yaml (root of repo)
packages:
  - 'packages/*'
  - 'apps/*'
  - '!**/__tests__/**'   # exclude test helper packages
// Package cross-reference in pnpm
{
  "dependencies": {
    "@mycompany/shared": "workspace:^1.0.0",  // specific version constraint
    "@mycompany/ui":     "workspace:*"           // latest workspace version
  }
}

Package Exports Map

The "exports" field is the modern, precise way to control what consumers can import from your npm package. It supersedes the old "main" and "module" fields.

Why "exports" Matters

  • Encapsulation: Consumers can only import what you explicitly export. Deep paths like import x from 'mylib/src/internals' are blocked.
  • Conditional exports: Serve ESM to ESM consumers, CJS to CommonJS consumers — from the same package.
  • Sub-path exports: Expose named entry points like import utils from 'mylib/utils'.

Export Patterns

Simple — single entry point

"exports": "./dist/index.js"

// Consumer:
import { x } from 'mylib';       // OK
import { y } from 'mylib/utils'; // Error: not exported

Conditional — ESM + CJS + types

"exports": {
  ".": {
    "import":  "./dist/index.esm.js",
    "require": "./dist/index.cjs.js",
    "types":   "./dist/index.d.ts"
  }
}

Sub-path exports — multiple entry points

// package.json
{
  "exports": {
    ".": {
      "import": "./dist/index.esm.js",
      "require": "./dist/index.cjs.js",
      "types": "./dist/index.d.ts"
    },
    "./utils": {
      "import": "./dist/utils.esm.js",
      "require": "./dist/utils.cjs.js",
      "types": "./dist/utils.d.ts"
    },
    "./package.json": "./package.json"  // always expose this
  }
}
// Consumer can use:
import { x }     from 'mylib';          // OK — main entry
import { formatDate } from 'mylib/utils'; // OK — sub-path
import { secret } from 'mylib/src/internal'; // Error: not in exports map

"main" / "module" / "types" vs "exports"

FieldSupported byUse caseStatus
"main"All Node.js versions, old bundlersCommonJS entry pointLegacy — use "exports"
"module"Bundlers only (Webpack, Rollup)ESM entry point for tree-shakingLegacy — use "exports"."import"

Dependency Management

overrides — Fix Transitive Dependency Vulnerabilities npm 8.3+

When a package deep in your dependency tree has a security vulnerability, you can force all occurrences to use a safe version — without waiting for the intermediate packages to update.

// package.json — force all transitive uses of lodash to 4.17.21
{
  "overrides": {
    "lodash": "4.17.21",

    // Only override lodash when depended on by specific-package
    "specific-package": {
      "lodash": "4.17.21"
    },

    // Override a package's dependency on another package
    "package-with-old-dep": {
      "vulnerable-dep": "^3.0.0"
    }
  }
}
// Yarn equivalent (in package.json):
"resolutions": {
  "lodash": "4.17.21",
  "**/webpack": "5.88.0"   // glob-based path — any nested webpack
}

peerDependencies

peerDependencies declares what the consuming project must provide. Libraries use this to avoid bundling their host framework. Angular component libraries declare @angular/core as a peer dep — not a regular dep.

// @mycompany/ng-components/package.json (library)
{
  "peerDependencies": {
    "@angular/core": ">=17.0.0",  // consumer must have Angular 17+
    "@angular/common": ">=17.0.0"
  },
  "peerDependenciesMeta": {
    "@angular/animations": {
      "optional": true   // only needed if using animated components
    }
  }
}

If the consumer doesn't have Angular 17+ installed, npm will print a warning (npm 7+) or error (with engine-strict). The library is NOT bundled with Angular — it uses the host app's copy.

.npmrc Configuration

.npmrc is the npm config file. It can live in your project root (project-level), your home directory (user-level), or be set globally. Project-level settings take precedence.

Common .npmrc settings

# .npmrc (project root)

# Registry — use your company's private registry
registry=https://registry.npmjs.org/
@mycompany:registry=https://npm.mycompany.com/

# Auth token for private registry (use env var — never commit the actual token)
//registry.npmjs.org/:_authToken=${NPM_TOKEN}
//npm.mycompany.com/:_authToken=${MYCOMPANY_NPM_TOKEN}

# Pin exact versions — no ^ or ~ in package.json when you npm install
save-exact=true

# Fail if engines field doesn't match current Node/npm version
engine-strict=true

# Legacy peer deps — suppress peer dep conflicts (useful in mixed-version projects)
legacy-peer-deps=true

# Use a local node_modules cache
cache=/tmp/npm-cache

# Don't generate package-lock.json (not recommended for apps)
package-lock=false

Per-scope registry config

You can route specific npm scopes (like @mycompany) to a private registry while everything else goes to the public registry. This is the standard pattern for enterprise teams.

# Route @mycompany packages to private Artifactory/Nexus/Verdaccio registry
@mycompany:registry=https://artifactory.example.com/npm/
//artifactory.example.com/npm/:_authToken=${ARTIFACTORY_TOKEN}

# Route @ngx-* packages through the public registry
@ngx-*:registry=https://registry.npmjs.org/

engines — Enforce Node/npm Version

// package.json
{
  "engines": {
    "node": ">=20.0.0",   // require Node 20+
    "npm":  ">=10.0.0"    // require npm 10+
  }
}

# .npmrc — make this a hard error (not just a warning)
engine-strict=true

package-lock.json Deep Dive

The lock file is a complete snapshot of your dependency tree — every package, every transitive dependency, pinned to an exact version with a cryptographic hash. It is the source of truth for reproducible installs.

lockfileVersion History

Versionnpm VersionNotes
1npm 5–6Flat structure, packages listed once. Old format.
2npm 7+Dual format — contains both v1 and v3 data. Backward compatible.
3npm 7+ (default)Nested tree structure. Smaller file. Requires npm 7+ to read.

Anatomy of a lock file entry

// package-lock.json (v3 format excerpt)
{
  "lockfileVersion": 3,
  "packages": {
    "node_modules/lodash": {
      "version": "4.17.21",                      // exact version pinned
      "resolved": "https://registry.npmjs.org/lodash/-/lodash-4.17.21.tgz",
      "integrity": "sha512-v2kDEe...",             // SHA-512 hash of the tarball
      "license": "MIT"
    },
    "node_modules/@angular/core": {
      "version": "17.3.0",
      "resolved": "https://registry.npmjs.org/@angular/core/-/core-17.3.0.tgz",
      "integrity": "sha512-abc...",
      "peerDependencies": {
        "rxjs": "^7.4.0",
        "tslib": "^2.3.0",
        "zone.js": "~0.14.2"
      }
    }
  }
}

The integrity field is a Subresource Integrity (SRI) hash. When npm downloads the package, it hashes the tarball and compares to this value. If they don't match, the install fails — protecting against supply chain attacks.

npm install vs npm ci

npm install

  • Reads package.json for requirements
  • Resolves version ranges (^ ~)
  • Updates package-lock.json if ranges allow
  • Creates node_modules if missing
  • Slow — checks all resolution rules
  • Use on developer machines

npm ci CI/CD

  • Reads package-lock.json (not package.json)
  • Installs exact pinned versions only
  • Fails if lock file is out of sync with package.json
  • Deletes node_modules and reinstalls clean
  • Fast — no version resolution needed
  • Use in CI/CD pipelines, Docker builds
Best practice: Always commit package-lock.json for applications. Never commit it for libraries (consumers get their own resolution). Use npm ci in every CI/CD pipeline for deterministic, faster builds.

Publishing Configuration

Preventing Accidental Publishing

// "private": true prevents npm publish — always set for apps
{
  "private": true,
  "name": "my-angular-app"
}
// npm publish now exits with: "This package has been marked as private"

"files" — Whitelist What Gets Published

Instead of a .npmignore blacklist (easy to forget), use "files" to whitelist exactly what goes into the published package. Everything else is excluded by default.

// Library package.json
{
  "files": [
    "dist/",          // compiled output
    "README.md",      // documentation
    "CHANGELOG.md"    // version history
  ]
  // Excluded automatically: node_modules, src, test, .git, .env, tsconfig.json
}

// Verify what will be published without actually publishing:
npm pack --dry-run

publishConfig

// Override registry/access for publishing (different from development)
{
  "publishConfig": {
    "registry": "https://registry.npmjs.org/",
    "access": "public"    // scoped packages default to "restricted" — make them public
  }
}

// For private registry publish:
{
  "publishConfig": {
    "registry": "https://artifactory.example.com/npm/",
    "tag": "latest"
  }
}

"sideEffects" — Enable Tree Shaking

Tells bundlers (Webpack, esbuild, Rollup) that your package is side-effect free — importing a file that isn't used won't cause any observable change. This lets bundlers safely remove unused exports from the bundle.

// Pure library — nothing is side-effectful
{ "sideEffects": false }

// Library with CSS that must be kept even if "unused"
{ "sideEffects": ["*.css", "*.scss"] }

// A file that modifies global state (polyfill, etc.)
{ "sideEffects": ["./src/polyfills.js"] }
Warning: If you set "sideEffects": false but your library imports CSS (Angular components often do), the bundler may incorrectly tree-shake out those styles. Test your published library before setting this.
