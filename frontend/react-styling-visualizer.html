React: Styling

Tailwind utility-first, CSS Modules scoping, CSS-in-JS (styled-components/Emotion) and the zero-runtime shift, plus theming with design tokens — how to style React and what to pick.

🎨 Five ways to style React — and why the industry shifted toward Tailwind & zero-runtime

React is unopinionated about CSS, so approaches coexist. Tailwind is utility-first — compose tiny classes in className with md:/hover:/dark: variants; a JIT compiler ships only what you use. CSS Modules keep real .css but scope class names locally (hashed) with zero runtime. CSS-in-JS (styled-components/Emotion) co-locates props-driven styles in JS, but classic libs inject at runtime — costing bundle size and clashing with Server Components. That tension drove zero-runtime (vanilla-extract, Linaria, Panda): typed co-located styles compiled to static CSS at build time. Under all of them, design tokens (CSS custom properties) are the single source of truth, making dark mode a variable swap. Consensus: Tailwind for most apps, CSS Modules if you prefer real CSS, zero-runtime CSS-in-JS in an RSC world.

  • Tailwind = utility-first — JIT ships only used classes; RSC-friendly (just classes).
  • CSS Modules = scoped real CSS — hashed names, zero runtime, no cascade clashes.
  • CSS-in-JS co-locates props-driven styles; classic runtime fights Server Components.
  • Zero-runtime + design tokens — build-time static CSS; dark mode = swap variables.

Tailwind (mapped to your tokens) is the fast default and is RSC-friendly because it's just classes. If you adopt styled-components in an App Router app, prefer a zero-runtime option (vanilla-extract/Panda) — classic runtime CSS-in-JS fights Server Components.

Or: how a perfectly correct styled-component quietly resets on every keystroke.

The problem

You wrapped a <mark> in styled.mark so its color could depend on a prop — and now that highlight's fade-in animation restarts every time the user types in the search box next to it.

The highlight that never finishes fading in

Inside SearchBar's function body you write const Highlight = styled.mark`color:${p=>p.$active?'#f0b':'#9ab'};`; — right there, because $active is only known inside SearchBar. Every keystroke updates query state, SearchBar re-renders, and the highlight reappears mid-fade instead of finishing it.

The generated CSS text is byte-for-byte identical to last render's. That's not the problem. styled.mark`...` is a function CALL, and every time SearchBar's body runs, that call runs again — producing a brand-new component function, with a brand-new identity, that just happens to render the same styles. React's reconciler compares component types by reference, not by the markup or CSS they'd produce, so a new reference at the same tree position means: unmount the old DOM node, mount a new one.

className hashing ✓ CSS text unchanged ✓ the styled() call site ⚠

The style survives the render. The DOM node underneath it doesn't.

Hoist the styled() call out of render
Move const Highlight = styled.mark`...` to module scope, above the component ↓ styled() now runs once, at import time, producing one component type for the life of the module Feed it a transient prop instead of a new template per render: <Highlight $active={active}> ↓ the CSS still varies by value, but through the SAME function reference every render — one type, reconciled, not replaced If a style truly has no fixed shape, keep the component static and flip a CSS variable or class instead ↓ variables update the paint without ever touching what component type is mounted
The one-sentence rule. Call styled() (or css) at module scope, never inside a component's function body — a component that's defined once and reused is what gives React a stable type to reconcile against; one defined fresh every render is a stranger every render.
Rename it in your head: styled.div`...` doesn't hand you a style, it hands you a component definition — the same category of thing as a class statement. You'd never write a new class inside another component's render function and expect the old class's instances to survive. Calling styled() mid-render is that exact mistake wearing a template-literal costume.

You

React's reconciler

I don't diff CSS strings. I compare component types by reference. Two function objects with identical bodies are still two different types to me — one gets unmounted, one gets mounted.

The mechanism

Watch what actually happens between one keystroke and the next.

  1. You type a character into the search boxstate update
  2. setQuery fires, SearchBar re-rendersrender #2
  3. The styled.mark`...` line inside the function body executes againnew call
  4. styled-components returns a fresh component function — a different reference than render #1'snew type
  5. React diffs the tree and sees the OLD <mark> type at this position replaced by a NEW typereconcile
  6. React unmounts the old DOM node (killing its transition and any focus) and mounts a fresh oneremount

Step 4 is the one that fools people: the CSS coming out of that call is identical to last render's, so nothing about the visible style "changed." But styled.mark`...` doesn't return CSS — it returns a component, and calling the same-looking code twice still produces two different function objects. Same output, different reference, and reference is all React checks.

a keystroke updates local statea parent re-rendersa context value changes
any re-render re-executes styled.mark`...` ↓
A brand-new component typeidentical CSS text, different function reference — React remounts the DOM node under it

It doesn't matter what triggered the re-render — a keystroke, a parent, a context change. The instant that styled() call executes again inside a function body, you get a new type. Hoist it out and none of those triggers matter anymore, because the line never runs a second time.

Your team writes const Card = styled.div`padding:${p=>p.$pad}px;` inside a <Dashboard> component so $pad can vary. A websocket tick re-renders Dashboard every 2 seconds, and every card inside it flashes, losing hover and focus state. What's the actual cause?

The cost here isn't CSS math — the generated CSS text is often byte-identical between renders. The real cost is that React treats each render's Card as an entirely new component to mount, never an existing one to update.

Exactly — the value returned by styled.div is a fresh function reference every time that line executes, so React can't tell this render's Card is "the same" node as last render's.

Batching frequency doesn't create or destroy component types. Even a websocket update ticking once a minute would trigger the same remount if Card were defined inside the render body — the problem is where the call lives, not how often it fires.

Where you have seen this before

"Looks the same, but the framework can't tell" shows up everywhere identity matters more than appearance.

Angular *ngFor without trackBy

Angular tears down and rebuilds every DOM node in a loop when it can't tell "this item" at render N is "the same item" at render N+1 — the identical trap as styled-components being unable to tell two calls apart. A trackBy function (here, hoisting styled() out of render) is what hands the framework a stable identity to diff against instead of guessing from position.

no stable identity → full rebuild, not a diff

Java: == on boxed integers outside the cache

Two Integer objects both holding 200 print identically, but Integer.valueOf(200) == Integer.valueOf(200) is false — the JVM only guarantees reference equality for the cached -128..127 range. React's reconciler is running the same kind of reference check on component types: "looks the same" was never "is the same."

identity (==) vs equality (.equals) — same trap, different language

Hibernate/JPA entities across two sessions

Load the same row via two separate Sessions and you get two distinct Java objects representing one database record — same primary key, different object identity. Code that compares them with == (instead of the entity's equals()) silently breaks, the same way code that assumes "same-looking styled() call" means "same component" silently breaks.

same data, different reference — check equality, not identity

The one new sentence this block adds: wherever you land, a styled() call is a component definition, not a style — call it once at module scope, or every render silently remounts whatever it wraps.

1. The Landscape

ApproachScopingRuntimeBest for
Plain CSS / globalnone (cascade)nonetiny apps; collisions at scale
Tailwindutilities (no naming)none (build JIT)most apps — speed + consistency, RSC-friendly
CSS Moduleslocal (hashed)noneteams who want real CSS, scoped
CSS-in-JS (runtime)local (generated)yeshighly dynamic styles; not ideal with RSC
Zero-runtime CSS-in-JSlocalnone (build)JS-authored styles in an RSC world
The trend is "author ergonomically, ship static CSS." Tailwind, CSS Modules, and zero-runtime CSS-in-JS all emit plain CSS at build time (no runtime style engine). Classic runtime CSS-in-JS lost favor because the runtime adds bundle + work and doesn't fit Server Components — which is why Tailwind became the default for new Next.js apps.

2. Tailwind — Utility-First

<button className="rounded-lg px-4 py-2 bg-indigo-600 text-white
  hover:bg-indigo-500 focus:ring-2 disabled:opacity-50
  md:px-6 dark:bg-indigo-500">Sign in</button>

// extract a repeated pattern when needed:
.btn { @apply rounded-lg px-4 py-2 bg-indigo-600 text-white; }

You compose pre-defined utilities directly in markup, with variants for responsive (md:), state (hover:/focus:/disabled:), and theme (dark:). The JIT compiler scans your files and emits only the utilities you used, so production CSS stays small. Values come from a constrained theme scale (spacing, colors), which enforces consistency. For a repeated combo, @apply (or a component) factors it out; clsx/tailwind-merge handle conditional classes.

The trade: "ugly" markup for speed + consistency. Long className strings are the common complaint — but you stop naming things, stop context-switching to a CSS file, and the design-token scale keeps spacing/color consistent across a team. Map Tailwind's theme to your design tokens so utilities and custom CSS agree.

3. CSS Modules & CSS-in-JS

// CSS Modules — real CSS, locally scoped
import s from './Card.module.css'
<div className={s.card}>…</div> // → Card_card__x7z2

// CSS-in-JS — co-located, props-driven
const Badge = styled.span`
  color: ${p => p.$admin ? '#f0b' : '#9ab'};
`;

CSS Modules hash each class so styles are local by default — no global collisions, zero runtime, and you write ordinary CSS (with composes for reuse). CSS-in-JS (styled-components, Emotion) co-locates styles with the component and makes them dynamic from props, which is its superpower — but classic libraries generate and inject styles at runtime (bundle + per-render cost) and need special setup with SSR/RSC.

Runtime CSS-in-JS vs React Server Components. A Server Component can't run a client-side style runtime, so styled-components/Emotion need a workaround (or a Client Component boundary) in the App Router. The fix is zero-runtime CSS-in-JS — vanilla-extract, Linaria, Panda CSS — which compiles your TypeScript-authored styles to static CSS at build time: same co-location and type-safety, no runtime, RSC-safe.

4. Design Tokens & Theming

/* tokens as CSS custom properties — one source of truth */
:root { --color-primary: #6366f1; --space-2: 8px; --radius: 8px; }
[data-theme="dark"] { --color-primary: #818cf8; --bg: #0b1426; }

/* everything references the tokens */
.btn { background: var(--color-primary); border-radius: var(--radius); }
// dark mode = flip one attribute on <html data-theme="dark">
Tokens decouple "what it looks like" from "where it's used." Define color/spacing/typography once as CSS variables; every styling method (Tailwind theme, CSS Modules, CSS-in-JS) reads them. Theming and dark mode become a single variable swap (toggle data-theme on the root) instead of editing hundreds of rules — and because CSS variables cascade and are dynamic, the switch is instant with no re-render. This is exactly how the design system you're reading (devhub.css) themes each track via one track-* body class.
