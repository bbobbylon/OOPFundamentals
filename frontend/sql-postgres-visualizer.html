PostgreSQL Deep Dive

JSONB, full-text search, VACUUM, connection pooling — PostgreSQL-specific power features for production apps.

🐘 What makes PostgreSQL different — and why do production applications use these advanced features?

PostgreSQL goes far beyond standard SQL. JSONB stores semi-structured data in a binary, GIN-indexable form you can query by nested field (metadata->>'ip') — "schemaless within SQL" for audit logs and event payloads. Built-in full-text search (tsvector/tsquery) beats LIKE '%x%' with stemming and relevance ranking. Because MVCC leaves dead row versions, VACUUM (and autovacuum) reclaims space and refreshes planner stats. Postgres is process-per-connection (~5-10MB each), so a pooler like PgBouncer multiplexes many app connections onto few real ones, and pg_stat_statements surfaces your slowest queries in production.

  • JSONB — binary, GIN-indexable semi-structured data; query nested fields.
  • Full-text search (tsvector/tsquery) — stemming + ranking, beats LIKE.
  • VACUUM reclaims MVCC dead tuples and refreshes planner stats.
  • PgBouncer pools connections; pg_stat_statements finds slow queries.

-- Audit events with JSONB metadata: CREATE TABLE audit_events ( id BIGSERIAL PRIMARY KEY, user_id BIGINT, event_type TEXT NOT NULL, created_at TIMESTAMPTZ DEFAULT NOW(), metadata JSONB ); -- Insert: INSERT INTO audit_events VALUES ( DEFAULT, 42, 'LOGIN', NOW(), '{"ip":"10.0.0.1","idp":"PING","mfa":true,"device":"Chrome/Windows"}' ); -- Query JSONB fields: SELECT metadata->>'ip' AS ip, -- text metadata->'mfa' AS mfa_bool -- JSON FROM audit_events WHERE metadata->>'idp' = 'PING' AND (metadata->'mfa')::boolean = true; -- GIN index for fast JSONB queries: CREATE INDEX ON audit_events USING GIN (metadata);

Full-text search + VACUUM

-- Full-text search on user display names: ALTER TABLE users ADD COLUMN search_vector tsvector GENERATED ALWAYS AS ( to_tsvector('english', COALESCE(display_name,'') || ' ' || COALESCE(email,'')) ) STORED; CREATE INDEX ON users USING GIN (search_vector); -- Search: SELECT email, display_name, ts_rank(search_vector, query) AS rank FROM users, plainto_tsquery('english', 'bobby oliver') AS query WHERE search_vector @@ query ORDER BY rank DESC; -- VACUUM (run manually if autovacuum lagging): VACUUM ANALYZE users; -- reclaim + update stats VACUUM FULL users; -- compact table (locks!) -- Monitor dead tuples: SELECT n_dead_tup, n_live_tup FROM pg_stat_user_tables WHERE relname='users';

or, why PostgreSQL has never once updated a row in its life

The problem

The table is 40GB. It holds 2GB of rows.

Four symptoms, one cause nobody mentioned

You get told to watch bloat, run VACUUM, avoid long transactions, and never SELECT count(*) on a big table — four unrelated-sounding rules. They are one rule. Postgres does not overwrite a row when you UPDATE it: it writes a new version and marks the old one dead. Every row you have ever updated is still physically on disk until something sweeps it.

50k live rows 8.2M dead tuples ⚠ disk 40GB, data 2GB ⚠ index scans reading tombstones ⚠

Nothing deleted them, nothing is broken, and the row count on your dashboard has not moved in a week.

Once you know it is versions, the rules stop being arbitrary
UPDATE = INSERT a new version + tombstone the old one ↓ so a hot table grows even when the row count is flat VACUUM is the sweeper that makes dead space reusable ↓ but it can only remove versions no open transaction could still see So a long transaction anywhere pins the garbage everywhere
Postgres never updates a row — it writes a new version and tombstones the old one. That one sentence is the cause of dead tuples, table bloat, why VACUUM exists, why count(*) has to walk the table, and why one forgotten open transaction can bloat a table it never touched.
You

I updated one column on one row. Surely that is a small write.

Postgres

I wrote a complete new copy of the row and left the old one in place with a "died at transaction 9,412" stamp. I have to — a transaction that started before yours is still entitled to see the old value.

VACUUM

And I am the one who reclaims it, later. I remove versions that no currently open transaction could possibly see. Which means the oldest open transaction in the whole database decides how much I am allowed to clean.

The mechanism

Follow one UPDATE all the way to reusable disk space.

  1. You run UPDATE orders SET status='PAID' WHERE id=42one row, one column
  2. Postgres writes an entirely new tuple with the new value, and stamps the old one with the transaction that killed itboth versions now exist on disk
  3. Readers pick a version using their snapshot — an older transaction still sees the old one, which is why readers never block writersthis is what MVCC buys you
  4. Every index entry pointing at the row must also be updated — unless the new version fits on the same page and no indexed column changed (a HOT update)why fillfactor matters on hot tables
  5. VACUUM later marks dead versions reusable — but only those older than the oldest transaction still open anywhere in the databasethe horizon that ruins afternoons

Step 5 is the one that surprises people, and it is the one that pages you. Autovacuum can be running perfectly, on schedule, on a table under heavy update load — and reclaim nothing, because a reporting query on a completely different table has been holding a snapshot open for three hours. The bloat is not an autovacuum failure. It is autovacuum being told it is not allowed.

And this is also why VACUUM FULL is not the bigger hammer it looks like. Plain VACUUM marks dead space reusable in place and takes no disruptive lock, so the file does not shrink but the space stops growing. VACUUM FULL rewrites the entire table into a new file to actually return disk to the OS — and takes an ACCESS EXCLUSIVE lock for the whole rewrite, which blocks every read and every write on that table until it finishes. On a 40GB table at 2am that is a maintenance window; run it reflexively during business hours and you have converted a disk-usage problem into an outage. When you genuinely need the space back without the lock, that is what pg_repack is for.

Your reporting service holds one transaction open for three hours running a long analytical query over audit_events. Meanwhile the sessions table — a different table entirely — takes heavy UPDATE traffic. Autovacuum is healthy and running on schedule. What happens to sessions?

The tables are unrelated; the snapshot horizon is not. It is computed across every backend in the database, because vacuum cannot know which rows that long transaction is about to look at. Table isolation gives you no protection here at all.

Worker slots are a real constraint (autovacuum_max_workers) but they are not this. Autovacuum will visit sessions right on schedule, scan it, and remove almost nothing — the work happens, the reclaim does not.

Right, and it is the failure mode worth memorising. The oldest open transaction anywhere in the database sets the horizon, and vacuum may only reclaim versions that died before it. Watch it directly with SELECT max(age(backend_xmin)) FROM pg_stat_activity, and defend against the common cause — a connection parked idle in transaction — with idle_in_transaction_session_timeout.

Where you've seen this before

Three things that stop being separate facts once you know this one.

Why count(*) is slow

There is no single true row count to read — visibility is per version, per snapshot. So an exact count walks the table. When "roughly how many" will do, reltuples from pg_class is free.

the count depends on who is asking

A garbage-collected heap

Exactly the same bargain, in a different runtime: allocation is cheap and something has to sweep later, so the pathology is not "slow allocation" but "the sweeper could not keep up." A long-lived reference pins garbage in a JVM the same way a long transaction pins tuples here.

allocate fast, collect later

A CIAM sessions table

The worst possible shape for this: small row count, enormous update rate — every token refresh rewrites a row. Row count stays flat, disk climbs. Give it aggressive per-table autovacuum settings rather than relying on the 20% global default.

autovacuum_vacuum_scale_factor = 0.01
Questions from the back row

If dead tuples are the problem, why not vacuum constantly?

Autovacuum essentially does, throttled on purpose — it reads pages and writes them back, so running it flat out competes with your workload for I/O. The defaults are tuned for a table that changes slowly, which is why the useful move is almost never "vacuum more globally" and almost always "set a lower autovacuum_vacuum_scale_factor on the three tables that actually churn." The 20% default on a 50-million-row table means waiting for ten million dead tuples before it starts.

What is transaction ID wraparound, and should I care?

Transaction IDs are 32-bit and wrap around. Postgres has to freeze old rows before that happens or they would appear to be from the future and become invisible — so if vacuum is blocked long enough, the database will eventually refuse new writes to protect itself. You will almost certainly never hit it; the reason to know it is that it is the same root cause wearing a scarier hat. Anything that stops vacuum for long enough gets here eventually, so age(datfrozenxid) is worth a monitor.

Does JSONB make bloat worse?

It can, and for a reason worth knowing: there is no partial update of a JSONB document. Changing one key rewrites the whole value, and if it is large enough it also rewrites its TOAST entries. A 40KB audit payload updated on every event is a lot of dead bytes per change. Store payloads you append and read; be wary of JSONB columns you repeatedly mutate — those wanted to be real columns.

1 — JSONB




-- Store flexible metadata without separate tables
ALTER TABLE users ADD COLUMN metadata JSONB;

-- Insert
UPDATE users SET metadata = '{"plan":"pro","features":["sso","audit"],"score":95}'
WHERE id = 1;

-- Query operators
metadata -> 'plan'           -- JSON value (returns JSON)
metadata ->> 'plan'          -- text value (returns text)
metadata @> '{"plan":"pro"}'  -- containment (GIN-indexable!)
metadata ? 'features'        -- key exists
metadata #>> '{features,0}'   -- first element of features array

-- GIN index for fast containment queries
CREATE INDEX idx_users_metadata ON users USING gin(metadata);

-- Now this is fast (index scan, not seq scan)
SELECT * FROM users WHERE metadata @> '{"plan":"pro"}';









2 — Full-Text Search




-- tsvector: pre-parsed document representation
ALTER TABLE articles ADD COLUMN search_vec tsvector
  GENERATED ALWAYS AS (
    to_tsvector('english', coalesce(title, '') || ' ' || coalesce(body, ''))
  ) STORED;

CREATE INDEX idx_articles_fts ON articles USING gin(search_vec);

-- tsquery: search expression
SELECT title, ts_rank(search_vec, query) AS rank
FROM articles, to_tsquery('english', 'spring & boot & security') AS query
WHERE search_vec @@ query
ORDER BY rank DESC
LIMIT 10;









3 — Connection Pooling with PgBouncer




PostgreSQL creates a heavyweight process per connection (~5MB). At 1000 concurrent users, that's 5GB just for connection processes. PgBouncer multiplexes many app connections onto few database connections.


# pgbouncer.ini
[databases]
mydb = host=localhost port=5432 dbname=mydb

[pgbouncer]
listen_port = 6432
pool_mode = transaction   # best for Spring Boot
max_client_conn = 1000    # app connections to PgBouncer
default_pool_size = 20    # actual connections to PostgreSQL


In Spring Boot: connect to PgBouncer on port 6432 instead of PostgreSQL on 5432. Set spring.datasource.hikari.maximum-pool-size to match default_pool_size.









4 — VACUUM & Table Bloat




-- Check table bloat
SELECT relname, n_dead_tup, n_live_tup,
       ROUND(n_dead_tup::numeric / NULLIF(n_live_tup,0) * 100, 2) AS dead_pct,
       last_autovacuum
FROM pg_stat_user_tables
WHERE relname = 'orders';

-- Manual VACUUM options
VACUUM orders;            -- reclaim dead tuples (non-locking)
VACUUM FULL orders;       -- rewrite table (exclusive lock!)
VACUUM ANALYZE orders;   -- vacuum + refresh statistics

-- autovacuum tuning for high-update tables
ALTER TABLE orders SET (
  autovacuum_vacuum_scale_factor = 0.01,   -- 1% (default 20%)
  autovacuum_analyze_scale_factor = 0.005
);
