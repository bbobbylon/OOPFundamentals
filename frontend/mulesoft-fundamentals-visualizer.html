MuleSoft — Flows, the Mule Event & DataWeave

How a Mule application processes a request: a flow is triggered by a source and runs an ordered chain of event processors. A single Mule Event (message + variables) travels through them, reshaped along the way by DataWeave — Mule's transformation language.

🔌 What is a Mule flow — and why does one "event" travel through it?

A MuleSoft application built in Anypoint Studio is a set of flows. A flow begins with a source (a trigger — most often an HTTP Listener, but also a scheduler, a queue listener, etc.) followed by an ordered chain of event processors. When the source fires, the runtime creates one Mule Event and passes it processor-to-processor, like a pipeline. The event carries a Message — which has a payload (the body) and attributes (metadata: HTTP method, headers, query params, URI params) — plus variables (vars) you set along the way. Crucially the event is the single source of truth moving down the flow: each processor reads it and may replace the payload. Connectors are the processors that talk to the outside world — an HTTP Listener/Requester, a Database SELECT, Salesforce, a queue — each exposing typed operations. The star is DataWeave (%dw 2.0), Mule's functional transformation language: a Transform Message processor takes the current payload (and vars/attributes) as input and produces a new payload in any format — output application/json, XML, CSV, Java. Finally, error handling is structural: a try scope or flow-level error handler catches a failure and routes it to on-error-propagate (re-throw, stop the flow) or on-error-continue (recover and keep going). The whole model is low-code and visual — you wire processors on a canvas — but underneath it's an event flowing through a deterministic pipeline.

  • Flow = source + processors — a trigger (HTTP Listener…) then an ordered processor chain.
  • Mule Event — one event travels the flow: payload + attributes (the Message) + vars.
  • Connectors — processors that reach external systems (HTTP, DB, Salesforce…) via typed operations.
  • DataWeave — %dw 2.0 transforms the payload to any format (output application/json --- {…}).

A flow (XML config)

<flow name="getUser"> <http:listener path="/users/{id}"/> <db:select .../> // connector <ee:transform> // DataWeave ... </ee:transform> </flow>

A DataWeave transform

%dw 2.0 output application/json --- { id: payload.user_id, name: payload.first ++ " " ++ payload.last, scopes: payload.roles map "ROLE_" ++ $ }

Spring Boot comparison

A flow ≈ a controller method + the processing pipeline behind it. The HTTP Listener ≈ @GetMapping; connectors ≈ injected clients/repositories (a db:select ≈ a Spring Data query, a http:request ≈ a RestClient call). DataWeave ≈ a MapStruct/Jackson mapping but as a first-class language. The Mule Event ≈ the request/response context threaded through filters. on-error-propagate/continue ≈ @ControllerAdvice deciding whether to rethrow or recover. MuleSoft trades code for a visual, reuse-first integration model.

CIAM / integration: MuleSoft usually sits as the integration tier between channel apps and systems of record — including identity. A flow can call an IdP's token or userinfo endpoint via the HTTP Connector, normalize claims with DataWeave, and aggregate user data from several systems behind one API. Token validation itself is best done at the Anypoint API Gateway with a JWT/OAuth2 policy (see the API-Led page) rather than hand-coded in a flow — the same edge-validation idea as a Spring resource server or the gateway in the node-auth / aspnet-auth pages.

1. A flow: a source followed by processors

<flow name="getUser">
  <http:listener config-ref="api" path="/users/{id}"/> <!-- source: triggers the flow -->
  <set-variable variableName="userId" value="#[attributes.uriParams.id]"/>
  <db:select config-ref="db"> <!-- connector operation -->
    <db:sql>SELECT * FROM users WHERE id = :id</db:sql>
    <db:input-parameters>#[{ id: vars.userId }]</db:input-parameters>
  </db:select>
  <ee:transform> <!-- DataWeave: DB row → API JSON --> ... </ee:transform>
</flow>
A flow is an ordered pipeline. The source (http:listener) creates the Mule Event when a request arrives; each processor below runs in order on that same event. #[...] is a DataWeave expression embedded inline — attributes.uriParams.id reads the URL segment, vars.userId reads a variable you set. The last processor's output becomes the HTTP response payload. Reorder the processors and you reorder the logic — there is no hidden control flow.

2. The Mule Event: message (payload + attributes) + variables

# the event as it moves down the flow
event = {
  message: {
    payload: { user_id: 42, first: "Ada", last: "Lovelace" }, // the body
    attributes: { method: "GET", uriParams: { id: "42" }, headers: {...} } // metadata
  },
  vars: { userId: "42", correlationId: "a1b2" } // your flow-scoped variables
}
One event, threaded through every processor. The payload is what most processors read and rewrite; attributes are read-only metadata about how the message arrived (great for routing/auth); vars are your scratch space that survives across processors but not across flows (unless you pass them). A connector or Transform Message typically replaces the payload while leaving attributes and vars intact — which is why you stash the id in a var before a DB call overwrites the payload with rows.

3. DataWeave: transform the payload to any shape

%dw 2.0
output application/json
---
{
  id: payload.user_id,
  name: payload.first ++ " " ++ payload.last,
  scopes: payload.roles map ("ROLE_" ++ $), // map over an array
  active: payload.status == "A"
}
DataWeave is a pure, functional mapping language. Everything after --- is one expression that produces the output document. The header declares the output format (switch application/json to application/xml and the same map emits XML). Operators like map, filter, groupBy, and ++ reshape data declaratively; $ is the current item in a lambda. This is the heart of MuleSoft's value proposition — connect any system to any other by transforming between their data shapes without imperative glue code.
