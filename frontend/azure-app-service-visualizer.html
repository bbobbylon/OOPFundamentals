Azure App Service — Plans, Slots & Scaling

Azure's PaaS web host: you bring code (a Spring Boot jar, a Node app, a container), an App Service plan supplies the VMs, deployment slots give you zero-downtime releases via swap, and autoscale rules add or remove instances behind a shared front end.

🚀 What is App Service — and why do plans, slots, and settings each solve a different problem?

App Service is platform-as-a-service: Azure owns the OS, patching, load balancer, and TLS; you own the application. Three concepts carry the whole model. First, the App Service plan is the compute you pay for — a set of VM instances of a chosen tier (Free/Basic for dev, Standard/Premium for prod). Apps run on a plan, and several apps can share one plan (they share its CPU and memory, which is a cost win and a noisy-neighbour risk). Scale settings belong to the plan, not the app. Second, deployment slots (Standard tier and up) are live clones of your app with their own hostname and their own configuration: you deploy to a staging slot, warm it up and smoke-test it against real infrastructure, then swap — Azure repoints the front-end routing so staging becomes production instantly, with the old prod still alive in the other slot for one-click rollback. Third, app settings are configuration injected as environment variables at runtime — connection strings, feature flags, SPRING_PROFILES_ACTIVE — so the same build artifact runs in every environment (the twelve-factor rule). Settings can be marked slot-sticky so a staging database string never follows a swap into prod, and they can be Key Vault references so the secret itself never sits in App Service at all. Changing a setting restarts the app — Azure re-creates the process with the new environment.

  • Plan = the servers — tier + instance count; apps share the plan's VMs; scaling is per-plan.
  • Slot = a parallel deployment — deploy to staging, warm up, swap hostnames for zero-downtime release + instant rollback.
  • Settings = env vars — same artifact, per-environment config; slot-sticky settings stay behind on swap; Key Vault references keep secrets out.
  • Autoscale — rules on metrics (CPU > 70% for 10 min → +1 instance) with min/max bounds and cool-downs, set on the plan.
  • Kudu / deploy engines — zip deploy, GitHub Actions, or container pull; az webapp deploy is the modern one-liner.

Deploy a Spring Boot jar

mvn package az webapp create -n shop-api -g rg-shop \ --plan plan-shop --runtime "JAVA:21-java21" az webapp config appsettings set \ --settings SPRING_PROFILES_ACTIVE=prod az webapp deploy --src-path target/api.jar \ --type jar -n shop-api -g rg-shop

AWS comparison

App Service ≈ Elastic Beanstalk / App Runner (managed platform over EC2). The App Service plan ≈ the EB environment's instance fleet. Deployment slots ≈ blue/green via EB environment swap or CodeDeploy traffic shifting — but slots are first-class and instant. App settings ≈ EB environment properties; autoscale rules ≈ an Auto Scaling group's target-tracking policies. See aws-ecs-visualizer.html for the container-side contrast.

Spring Boot comparison

App settings land as environment variables, which Spring's relaxed binding maps onto properties: SPRING_DATASOURCE_URL → spring.datasource.url. So the artifact you built once picks up per-slot config with zero code — exactly your application-prod.yml-via-env pattern. The slot swap's warm-up ping is where Boot's /actuator/health readiness probe earns its keep: swap only routes traffic once the staging instance answers healthy.

CIAM in production: give the web app a managed identity (one toggle) and it can fetch secrets from Key Vault or call your APIs with an Entra token — no client secret in any app setting. App Service can also do Easy Auth: a built-in auth layer that validates Entra ID tokens before requests reach your code, handy for internal tools. For your Spring APIs you will usually keep validation in the app (resource server + JWKS, as in spring-boot-idm-oauth2-deep-visualizer.html), but knowing the platform can do it is an AZ-204 staple.

1. Plans and tiers: apps run on a plan, and the plan is what scales

# the plan = the fleet of VMs; apps share it
az appservice plan create -n plan-shop -g rg-shop \
  --sku P1v3 --is-linux # Premium v3, Linux workers

# two apps on the SAME plan share its CPU/RAM
az webapp create -n shop-api -g rg-shop --plan plan-shop --runtime "JAVA:21-java21"
az webapp create -n shop-jobs -g rg-shop --plan plan-shop --runtime "JAVA:21-java21"

# scaling belongs to the PLAN, not the app
az appservice plan update -n plan-shop -g rg-shop --number-of-workers 3
Tier picks your features, not just your horsepower. Free/Shared are for experiments (no custom domain SLA, no always-on). Basic adds manual scale. Standard unlocks deployment slots and autoscale; Premium adds more slots, faster workers, and VNet integration. AZ-204 asks this as "which minimum tier gives you X?" — slots → Standard, and remember every app on the plan scales together because the instances are shared.

2. Slot swap: deploy next to prod, then repoint the router

# create a staging slot (Standard+), deploy the new build INTO it
az webapp deployment slot create -n shop-api -g rg-shop --slot staging
az webapp deploy --src-path target/api-v2.jar --type jar \
  -n shop-api -g rg-shop --slot staging

# smoke-test at the slot hostname, then swap
curl https://shop-api-staging.azurewebsites.net/actuator/health
az webapp deployment slot swap -n shop-api -g rg-shop \
  --slot staging --target-slot production
A swap moves routing, not files. Both slots keep running; Azure warms the staging workers (applies the prod slot's sticky settings, pings the site until it answers), then swaps the front-end pointers. Users never see a cold start, and the previous prod build is still running in the staging slot — rollback is just swapping back. Settings marked slot-sticky (deployment slot setting) stay with the slot, so staging keeps its test database even after it becomes prod code.

3. Configuration: env vars in, Key Vault references for secrets

# plain setting → env var (restarts the app)
az webapp config appsettings set -n shop-api -g rg-shop --settings \
  SPRING_PROFILES_ACTIVE=prod \
  WELCOME_BANNER="Shop API v2"

# secret stays in Key Vault; App Service resolves it at startup
az webapp config appsettings set -n shop-api -g rg-shop --settings \
  DB_PASSWORD="@Microsoft.KeyVault(SecretUri=https://kv-shop.vault.azure.net/secrets/db-password/)"

# Spring reads them like any env var
spring.datasource.password=${DB_PASSWORD}
Changing a setting bounces the process. App settings are injected as environment variables when the worker process starts, so every change triggers a restart — schedule config changes like deployments. The @Microsoft.KeyVault(…) reference syntax makes App Service (using its managed identity) fetch the secret from Key Vault and expose only the value to your process: the portal shows the reference, never the secret, and rotation happens in one place. Details in azure-keyvault-identity-visualizer.html.
