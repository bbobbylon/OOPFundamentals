Functions Deep — Overloads, Signatures & this

The Functions page introduces parameter types, optionals, and predicate returns. This companion goes one level down: how the compiler resolves an overloaded call, the difference between call and construct signatures, and how this gets a type even though it isn't a real parameter.

What are function overloads in TypeScript — and when do you need them instead of just a union parameter?

TypeScript function overloads let you declare multiple signatures for one function — each signature describing a specific combination of parameter types and corresponding return type. You write N overload signatures (header-only, no body), then one implementation signature (with a body, using the union of all types). The compiler uses the overload signatures for type-checking callers; the implementation signature is hidden from callers. Why use overloads instead of just string | number as the parameter type? Because the relationship between inputs and outputs can differ: function getUser(id: number): UserDto and function getUser(email: string): UserDto[] — by ID returns one user; by email might return multiple. A union parameter id: number | string with return type UserDto | UserDto[] doesn't capture this relationship. With overloads, the caller gets precisely UserDto when passing a number, and precisely UserDto[] when passing a string. Overload resolution: TypeScript checks overload signatures in order, top to bottom, returning the first one that matches. The implementation signature must be compatible with all overloads. Call signatures in types: types and interfaces can describe callable objects: interface Formatter { (value: string): string; (value: number): string } — a type for an object that can be called as a function with two different signatures.

Overload structure

// Overload signatures (no body) function findUser(id: number): UserDto; function findUser(email: string): UserDto[]; function findUser(criteria: { dept: string }): UserDto[]; // Implementation signature (body required) function findUser(arg: number | string | { dept: string }): UserDto | UserDto[] { if (typeof arg === 'number') { return db.findById(arg); } else if (typeof arg === 'string') { return db.findByEmail(arg); } else { return db.findByDept(arg.dept); } } const user: UserDto = findUser(42); // precise type const users: UserDto[] = findUser('bob@co.com'); // precise type

this parameter

// TypeScript allows typing 'this' explicitly // (it's erased at compile time — not a real parameter) interface Element { addEventListener(type: string, handler: (this: Element, e: Event) => void): void; } // Class method 'this' type class UserComponent { user = { name: 'Bobby' }; showUser(this: UserComponent): void { console.log(this.user.name); // OK } } const comp = new UserComponent(); const fn = comp.showUser; fn(); // Error: 'this' context is undefined — // TypeScript catches the detachment bug comp.showUser(); // OK. this typing prevents the classic "lost context" JavaScript bug — calling a method as a callback without binding.

Overloads vs generics

Use generics when the return type is the same shape as the input (just parameterised by T): function first<T>(arr: T[]): T | undefined. Use overloads when different input types produce different shapes of output (not just different T values): function coerce(v: string): number; function coerce(v: number): string — the outputs are genuinely different types. Also use overloads for: optional parameter combinations where the types change based on what's present; method overloads in classes; describing third-party library call patterns. Avoid overloads for simple cases — generic constraints or union parameters are usually cleaner and easier to maintain.

In CIAM / Angular: HTTP service overloads: getUserClaims(token: string): Observable<JwtClaims> for Ping (returns the full claims object); getUserClaims(oid: string, tenantId: string): Observable<EntraClaims> for Entra (needs both OID and tenant). Implementation internally routes: function getUserClaims(tokenOrOid: string, tenantId?: string). Angular event handlers typed with this: class method passed to RxJS operators — this.userService.getUsers().pipe(tap(this.onUsersLoaded.bind(this))). The onUsersLoaded(this: UserListComponent, users: UserDto[]) {} signature ensures if someone calls it without binding they get a compile error, not a silent this.someProperty of undefined runtime crash.

1. One function, many faces

The shape of an overload

You write overload signatures (what callers see) followed by one implementation signature (the body that actually runs). The implementation signature is not callable from outside — it only has to be broad enough to satisfy every overload.

// 3 overload signatures — what the caller picks from
function format(x: string): string;
function format(x: number): string;
function format(x: Date): string;

// implementation signature — NOT callable directly
function format(x: unknown): string {
  if (x instanceof Date) return x.toISOString();
  return String(x);
}

The implementation signature is invisible

A common surprise: even though the body accepts unknown, callers can only use the three overloads above it. format(true) is an error — boolean matches none of the public signatures.

format("hi");        // ✅ → string
format(42);          // ✅ → string
format(new Date()); // ✅ → string

format(true);
// ❌ No overload matches this call.
//    The unknown impl sig is private to the body.

Rule: the implementation signature constrains the body, the overload signatures constrain the callers. They are two different contracts.

2. Interactive — watch overload resolution pick a signature

Resolution is top-to-bottom, first match wins. Pick an argument, then step the compiler down the overload list. It tests each signature in source order and stops at the first one the argument is assignable to.

3. Order matters — put specific signatures first

❌ General first shadows specific

Because the first match wins, a broad signature placed early swallows every call before the specific ones are even tried.

function get(x: any): any;        // 🟥 too broad, too early
function get(x: string): string;
function get(x: unknown) { return x; }

const r = get("hi"); // r: any  ← string overload never reached

✅ Specific first, fallback last

List narrow signatures first; let the broad one catch the rest.

function get(x: string): string;
function get(x: number): number;
function get(x: unknown): unknown;   // fallback
function get(x: unknown) { return x; }

const r = get("hi"); // r: string ✅

4. Overloads vs. the alternatives

Overloads exist to preserve the correlation between an input type and its output type. A plain union return throws that correlation away. Often a generic or a conditional return type expresses the same thing more cleanly.

TechniqueWhat it saysReach for it when…
union param(x: string|number): string|number — caller can't tell which output goes with which inputinput and output are genuinely independent
overloadsEach input type maps to a fixed output type; arities/param-counts can differ tooa small fixed set of input→output pairs, or different argument counts
generic<T>(x: T): T — output tracks the exact input the caller passedoutput is "the same as" or derived from the input
conditional(x: T): T extends string ? A : Boutput type is computed from the input type by a rule

The classic trap a union return hides

// 🟥 union signature — correlation lost
function wrap(x: string | number): string[] | number[] { /* … */ }
const a = wrap("x");   // a: string[] | number[]  ← you "know" it's string[], TS doesn't
a.push(1);          // no error — TS can't rule it out 😬

// ✅ overloads keep input↔output tied together
function wrap(x: string): string[];
function wrap(x: number): number[];
function wrap(x: string | number) { return [x]; }
const b = wrap("x");   // b: string[] ✅

5. Call signatures & construct signatures

Typing a value that is callable

An interface with a bare (args): ret member describes a callable value. Add named properties and you have a hybrid type — a function that also carries data (think $ in jQuery, or a memoized fn with a .cache).

interface Greeter {
  (name: string): string;   // call signature
  lang: string;             // + a property
}

const g: Greeter = (n) => `hi ${n}`;
g.lang = "en";            // ✅ callable AND has data

Typing something you call with new

Prefix with new for a construct signature — the type of a class/constructor itself, so you can pass "a class" as a value (factories, DI).

interface Ctor {
  new (id: string): Service;  // construct signature
}

function make(C: Ctor, id: string) {
  return new C(id);          // ✅ TS knows C is newable
}
make(UserService, "u1");

An interface can hold both a call and a construct signature (e.g. NumberConstructor — you can call Number(x) or new Number(x)).

6. Typing this — the parameter that isn't one

this isn't a real argument, but you can declare its type as a fake first parameter. It's erased at compile time — purely a hint so the compiler checks how the function is called. With strict + noImplicitThis, a free function that uses this without declaring it is an error.

interface Card { title: string; }

// 'this' typed as a fake first param — disappears in the JS output
function render(this: Card, prefix: string) {
  return prefix + this.title;   // this: Card
}

const c: Card = { title: "Hi" };
render.call(c, "› ");  // ✅ this bound to a Card
render("› ");        // ❌ 'this' context of type void is not assignable to Card

Polymorphic this — fluent builders

Return type this means "whatever subclass I'm called on" — so chained calls keep the subclass type instead of collapsing to the base.

class Query {
  where(c: string): this { /*…*/ return this; }
}
class UserQuery extends Query {
  active(): this { return this; }
}
new UserQuery().where("x").active();
// ✅ .where() returns UserQuery, so .active() still exists

Extracting / stripping this

Two utility types operate on the this parameter:

type T = ThisParameterType<typeof render>;
// T = Card

type Free = OmitThisParameter<typeof render>;
// Free = (prefix: string) => string   (this removed)

Handy when you .bind() a method and want the resulting standalone function's type.

7. Pitfalls

  • Arrow functions can't be overloaded. Overload signatures need function declarations or object-method syntax — you can't stack signatures on a const f = () => ….
  • The implementation signature isn't a public overload. Forgetting this, people widen the impl to any and wonder why f(true) still errors — callers never see the impl.
  • Overloads don't auto-distribute over unions. Calling an overloaded fn with a string | number value won't try both overloads — it looks for one signature that accepts the whole union. Add a union overload or use a generic.
  • Lost this on detached methods. const f = obj.method; f() drops the binding. The this-param type catches it; fix with an arrow field or .bind(obj).
  • Arrow methods can't type this as a param — an arrow has no own this; it captures the enclosing one. That's usually what you want in a class field callback.

8. One-sentence recap

An overloaded function shows callers a list of overload signatures that the compiler tries top-to-bottom, first match wins (so order specific→general), while a separate implementation signature — invisible to callers — types the body; reach for generics or conditional returns when output is derived from input, use call/construct signatures to type callable and newable values, and type this as an erased fake first parameter (with ThisParameterType/OmitThisParameter to read or strip it).
