Testing in Spring Boot

Unit tests, slice tests, and integration tests with JUnit 5, Mockito, and Spring's test slices.

🧪 What are the three testing layers in Spring Boot — and when do you use each?

Spring Boot testing comes in three layers of increasing fidelity and cost. Unit tests (JUnit 5 + Mockito) exercise one class with no Spring context — mock the dependencies, run in milliseconds, cover business logic and branches. Slice tests (@WebMvcTest, @DataJpaTest, @JsonTest) boot only one layer of the context — the web layer or the JPA layer — in seconds. Integration tests (@SpringBootTest) start the whole context against a real test database (Testcontainers) in tens of seconds for true end-to-end coverage. Rule of thumb: roughly 70% unit, 20% slice, 10% integration.

  • Match the layer to the risk. Logic → unit; serialization/security → slice; full flow → integration.
  • Faster tests run more often. Unit on every save, integration in CI.
  • @MockBean swaps a bean in a slice; @Mock/@InjectMocks wire a pure unit test.
  • Prefer Testcontainers over H2 for repository tests — same SQL dialect as prod Postgres.

Unit test (Mockito)

@ExtendWith(MockitoExtension.class) with @Mock UserRepository + @InjectMocks UserService. given(repo.findById(42L)).willReturn(...), assert the result, and assert it throws when empty. No Spring, no DB — instant.

@WebMvcTest slice

@WebMvcTest(UserController.class) with MockMvc + @MockBean UserService. @WithMockUser(roles="ADMIN") then mockMvc.perform(get(...)).andExpect(status().isOk()) — tests routing, JSON, validation, and security only.

@DataJpaTest + Testcontainers

H2 is fast but its dialect drifts from Postgres. Better: @DataJpaTest @AutoConfigureTestDatabase(replace=NONE) @Testcontainers with a PostgreSQLContainer — real Postgres in Docker, started once per class, so Specifications, indexes, and Flyway run for real.

CIAM: Unit-test every service branch; slice-test every controller for "right role → 200" and "wrong role → 403"; @DataJpaTest + Testcontainers for user-search specifications against 50 seed rows; one @SpringBootTest end-to-end for the critical flow — create user → assign role → fetch → assert role. Focus on the hard logic and the security boundary, not coverage for its own sake.

1 — The Testing Pyramid

Click each layer to understand what it tests and which Spring annotations drive it:

E2E / Integration Tests
Few — slow — high confidence
@SpringBootTest — boots the full application context. Closest to production. Slow (seconds).

@SpringBootTest(webEnvironment = RANDOM_PORT) + TestRestTemplate or WebTestClient

Use for: happy-path API flows, database round-trips, security filter chains end-to-end. Write a handful — not hundreds.
Slice Tests
Some — medium speed — targeted
@WebMvcTest — only web layer (controllers, filters, serialization). No database.
@DataJpaTest — only JPA layer (repositories, entities). Uses H2 in-memory by default.
@JsonTest — only Jackson serialization/deserialization.

These start fast because they load a partial application context — only the beans relevant to that slice.

Use for: controller input validation, JSON shaping, custom query methods, repository behavior.
Unit Tests
Many — milliseconds — isolated
Plain JUnit 5 + Mockito — no Spring context at all. Instantiate the class under test directly.

@ExtendWith(MockitoExtension.class) enables @Mock / @InjectMocks.

Use for: service logic, validation methods, pure business rules — anything that doesn't need the framework to run. These should be the majority of your tests (cheap to write, milliseconds to run).

2 — Key Test Annotations

@SpringBootTest

Full context integration test
Loads the entire ApplicationContext — every bean, every configuration.

webEnvironment options:
• MOCK (default) — MockMvc-based, no real port
• RANDOM_PORT — real embedded Tomcat, random port
• DEFINED_PORT — real Tomcat on configured port

Slowest of all test types. Use sparingly for end-to-end flows.

@WebMvcTest

Controller slice — no DB
Only loads web layer beans: @Controller, @RestController, @ControllerAdvice, filters, Jackson converters.

Service and repository beans are NOT loaded — you must mock them:
@MockBean UserService userService;

Inject MockMvc to send fake HTTP requests and assert responses.

@DataJpaTest

Repository slice — H2 in-memory
Only loads JPA-related beans: @Repository, EntityManager, DataSource (H2), Flyway/Liquibase (if present).

Each test runs in a transaction that rolls back automatically — so tests don't pollute each other.

Injects TestEntityManager to set up test data without calling your repository.

@MockBean

Spring-managed mock
Adds a Mockito mock into the Spring ApplicationContext. Any bean that depends on it gets the mock injected.

Used in slice tests to replace beans that aren't loaded by the slice.

Different from @Mock — that's a plain Mockito mock used in pure unit tests with no Spring context.

@ExtendWith(Mockito)

Pure unit test with mocks
@ExtendWith(MockitoExtension.class) — activates Mockito annotations without Spring.

@Mock — creates a mock of the type.
@InjectMocks — creates the class under test and injects mocks into it.

Fastest possible tests. No application context startup overhead at all.

@TestConfiguration

Override beans for tests
Defines test-only Spring beans that override production beans in the test context.

Use when you want a real (but lighter-weight) implementation instead of a Mockito mock — e.g., an in-memory implementation of a port/interface.

Annotate a static inner class or a separate class and import it with @Import.

🌱 New to testing? It's code that checks your code, automatically.

A test creates your object, exercises it, and asserts the result is what you expect — and the build runs all of them and fails if any break. So instead of manually clicking through the app after every change, you get an instant safety net. The simplest kind: new up a class (with fake versions of its dependencies), call a method, and assert the output. Spring Boot also lets you spin up part of the app (just the web layer, just the database layer) or the whole thing when you need a more realistic test. You write @Test methods; the build does the rest.

🧠 Expert corner — the pyramid, slices, and mocking

  • Follow the test pyramid. Lots of fast unit tests (plain JUnit + Mockito, no Spring context — milliseconds), fewer slice/integration tests, very few full end-to-end. Speed is a feature; a slow suite stops getting run.
  • Use the right slice. @WebMvcTest loads just one controller + MockMvc (mock the service with @MockBean); @DataJpaTest loads just repositories against a test DB; @SpringBootTest loads the whole context — powerful but slow, so reserve it.
  • Mock collaborators, test one unit. Mockito.when(repo.findById(1)).thenReturn(...) isolates the class under test; @MockBean swaps a bean inside a Spring slice.
  • Real infra with Testcontainers — spin up a real Postgres in Docker for integration tests instead of H2, so "works in tests" matches prod.
  • Assert behavior, not implementation (AssertJ's fluent assertThat(...) reads well). Brittle tests that mirror internals slow you down.
  • CIAM tie-in. A @WebMvcTest with a mock JWT (@WithMockUser / a stub JwtDecoder) lets you assert that an endpoint returns 200 for the right authority and 401/403 otherwise — without a real IDM.
