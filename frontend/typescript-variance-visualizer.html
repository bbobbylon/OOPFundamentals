Variance & Assignability

Why () => Dog is assignable to () => Animal, but Array<Dog> is not assignable to Array<Animal>. The hidden rules that govern every type error you've ever seen.

What is variance? Why does TypeScript care about it?

Variance is the rule that decides when one type is assignable to another. You know Dog extends Animal. But does Promise<Dog> extend Promise<Animal>? Does (dog: Dog) => void extend (animal: Animal) => void? The answer depends on where the type parameter is used — as an output (return value) or an input (parameter). Getting this wrong leads to runtime type errors that TypeScript cannot catch.

Covariant (output) — follows subtyping
type Producer<T> = () => T;
// Producer<Dog> assignable to Producer<Animal>
// ✓ A fn that returns Dog satisfies
// "give me something that returns Animal"
Invariant (mutable) — strict both ways
const dogs: Array<Dog> = [];
const animals: Array<Animal> = dogs; // ✗
// If allowed: animals.push(new Cat())
// dogs[0] is now a Cat — runtime crash!
Why you'll hit this: Variance errors appear when you try to assign an Observable<AdminUser> to Observable<User>, pass a callback typed for a subtype where a broader type is expected, or use method shorthand in interfaces (which TypeScript allows but is technically unsafe — bivariant).

1. What "assignable" means

At its core, TypeScript is about one question asked millions of times during compilation: can a value of type A be used where type B is expected? If yes, we say "A is assignable to B." This is also written as "A extends B" in conditional type syntax.

Concretely: if you have a variable typed as B, and you try to put a value of type A into it, TypeScript will allow this only if A is assignable to B. Every type annotation, every function call argument, every return statement — TypeScript is checking assignability.

let x: string;
x = "hello";        // ✓ string is assignable to string
x = 42;            // ✗ number is NOT assignable to string

let y: string | number;
y = "hello";        // ✓ string is assignable to string | number
y = 42;            // ✓ number is assignable to string | number

let z: unknown;
z = "anything";    // ✓ everything is assignable to unknown
z = 42;            // ✓
z = null;          // ✓

let w: never;      // nothing is assignable TO never; never is assignable to everything
The type hierarchy: never sits at the bottom (subtype of everything), unknown sits at the top (supertype of everything). any is special — it's simultaneously assignable to and from everything, bypassing the type system. The useful types — string, number, objects — live in between.

Assignability is the foundation of subtyping

When we say "A is a subtype of B," we mean exactly that A is assignable to B. A has at least everything B has, possibly more. A is more specific. A is "at least as good as" B for any purpose B is used for.

2. Structural typing — shape, not name

TypeScript uses structural typing. This is fundamentally different from languages like Java or C# which use nominal typing. In nominal typing, two types are only compatible if they explicitly declare that relationship (via extends or implements). In structural typing, two types are compatible if they have the same shape — the same properties and methods — regardless of their names.

// Nominal typing (not TypeScript): these are incompatible because different names
// class Cat { name: string }; class Dog { name: string }; — Cat ≠ Dog

// Structural typing (TypeScript): these ARE compatible because same shape
interface Cat { name: string; }
interface Dog { name: string; }

let cat: Cat = { name: "Whiskers" };
let dog: Dog = cat;   // ✓ — same shape, perfectly fine in TypeScript

// A class with all the right properties is assignable to an interface
class Point { constructor(public x: number, public y: number) {} }
interface Coord { x: number; y: number; }
const pt: Coord = new Point(1, 2);  // ✓ — Point has x and y, that's all Coord needs
Important: Structural typing means you can't use the type system to distinguish between types that have the same shape. Two different IDs — both string — are interchangeable. This is exactly the problem that Branded Types (see the patterns page) solve.

3. Subtype hierarchy and width subtyping

With structural typing, a type with more properties is a subtype of a type with fewer properties. This is called width subtyping. An object with extra fields can always fill in for one with fewer — the receiver only needs certain fields to exist, and the extra ones don't hurt.

Animal
{ name: string }
↑
extends (adds bark)
Dog
{ name, bark() }
↑
extends (adds color)
Labrador
{ name, bark(), color }
interface Animal { name: string; }
interface Dog extends Animal { bark(): void; }
interface Labrador extends Dog { color: string; }

const lab: Labrador = {
  name: "Buddy", color: "yellow",
  bark() { console.log("woof"); }
};

let d: Dog = lab;     // ✓ Labrador extends Dog
let a: Animal = lab;  // ✓ Labrador extends Animal
let l: Labrador = d;  // ✗ Dog doesn't have 'color'

The arrow in the diagram points upward toward the supertype. Assignability flows upward: a Labrador can be assigned to a Dog variable, and to an Animal variable, because it has everything those types need. Going the other direction — assigning an Animal to a Labrador variable — fails because the Animal might not have bark or color.

4. Covariance — return types

Covariance means: if type A is a subtype of B, then F<A> is a subtype of F<B>. The relationship is preserved in the same direction.

Return types of functions are covariant. If Dog extends Animal, then () => Dog is assignable to () => Animal.

type GetAnimal = () => Animal;
type GetDog    = () => Dog;

// GetDog is assignable to GetAnimal — covariant return
const getDog: GetDog = () => ({ name: "Rex", bark() {} });
const getAnimal: GetAnimal = getDog;  // ✓

// Why is this safe? If you call getAnimal(), you expect an Animal back.
// getDog() returns a Dog, which IS an Animal — it has everything Animal has.
// The caller is perfectly happy with the result.
The mental model: a function that produces a more specific result can always stand in for one that produces a less specific result. The caller asks for an Animal and gets a Dog — the Dog has everything an Animal needs, so the caller is satisfied. Covariance: subtype relationships are preserved in the output position.

5. Contravariance — parameter types

Contravariance means: if A is a subtype of B, then F<B> is a subtype of F<A>. The relationship is flipped in the input position.

Parameter types of functions are contravariant. If Dog extends Animal, then (animal: Animal) => void is assignable to (dog: Dog) => void — NOT the other way around.

type HandleAnimal = (animal: Animal) => void;
type HandleDog    = (dog: Dog)    => void;

// HandleAnimal is assignable TO HandleDog — the WIDER parameter is assignable to the NARROWER
const petAnimal: HandleAnimal = (a) => { console.log(a.name); };
const petDog: HandleDog    = petAnimal; // ✓ — counter-intuitive but correct!

// NOT assignable the other way:
const makeDogSit: HandleDog = (d) => { d.bark(); };
// const makeAnimalSit: HandleAnimal = makeDogSit; // ✗ ERROR
// Why? makeDogSit calls .bark() — but a plain Animal has no .bark()!
The mental model: a function that can handle any Animal can certainly handle a Dog (a Dog is an Animal). But a function that specifically handles Dogs — maybe calling .bark() — cannot handle any Animal, because the Animal might not be a Dog. Contravariance: subtype relationships are flipped in the input position.

6. Bivariance — the old method behavior

Before TypeScript 2.6 and the strictFunctionTypes flag, TypeScript treated all function parameters as bivariant: both covariant and contravariant assignments were allowed. This was a deliberate unsoundness to make common patterns easier to write, but it allowed runtime crashes.

// Bivariance (what TypeScript used to allow for ALL function params)
type HandleDog = (d: Dog) => void;

// Both of these would be allowed in bivariant mode:
const h1: HandleDog = (a: Animal) => {};  // contravariant — correct direction
const h2: HandleDog = (l: Labrador) => { l.color.toUpperCase(); }; // ✗ unsafe!

// h2 called with a non-Labrador Dog would crash at runtime
// (accessing .color on a plain Dog that has no .color property)

Bivariance existed as a pragmatic compromise. Array methods like Array.forEach(callback) need their callback parameter to be flexible. Strict contravariance would make many common patterns require casts. With strictFunctionTypes, TypeScript enforces correct contravariance — but only for function type expressions, not method shorthands.

7. strictFunctionTypes — arrows vs methods

This is one of TypeScript's quirkiest design decisions. The strictFunctionTypes flag enables correct contravariant checking for function types written with the => arrow syntax. However, it deliberately does not apply to function parameters written in method shorthand. Why? Because enforcing it on method shorthands would break too many real-world patterns, especially in DOM typings and class hierarchies.

// With strictFunctionTypes: true

// ARROW function type — contravariance IS enforced
type F1 = (x: Animal) => void;    // function type (arrow)
type F2 = (x: Dog)    => void;

declare let f1: F1;
let f2: F2 = f1;  // ✓ — Animal handler can be used as Dog handler (contravariant)
let f1b: F1 = f2; // ✗ ERROR — Dog handler cannot be used as Animal handler

// METHOD shorthand — bivariance still applies even with strictFunctionTypes!
interface M1 { handle(x: Animal): void; }   // method shorthand
interface M2 { handle(x: Dog): void; }

declare let m1: M1;
let m2: M2 = m1;  // ✓ (contravariant — fine)
let m1b: M1 = m2; // ✓ (covariant — allowed because METHOD shorthand = bivariant)

8. Invariance — mutable generics

Invariance means: even if A is a subtype of B, F<A> is not assignable to F<B> or vice versa. No relationship at all. Mutable generic containers in TypeScript are invariant.

Array<Dog> is NOT assignable to Array<Animal>, even though Dog extends Animal. This surprises many developers who come from covariant array languages like Java.

declare let dogs:    Array<Dog>;
declare let animals: Array<Animal>;

// animals = dogs;  // ✗ Type 'Dog[]' is not assignable to type 'Animal[]'
// Why? Because if it were allowed, you could do this:

// animals = dogs;              // pretend this works
// animals.push({ name: "Cat" }); // Animal without bark() — valid for Animal[]
// dogs[dogs.length - 1].bark(); // 💥 runtime crash — that Animal has no .bark()

// The mutable push() creates the problem. If we could only READ, it would be safe.
The push() problem: if you could assign Dog[] to Animal[], then via the Animal[] reference you could push a non-Dog animal into what is actually a Dog[]. The next time code reads from the Dog array and calls .bark() on the thing you pushed, it crashes. Invariance prevents this entire class of bugs.

9. Covariant generics via readonly

When you remove the ability to write into a container, you remove the push() problem. readonly Array<Dog> IS assignable to readonly Array<Animal>. You can only read from it, and reading a Dog where an Animal is expected is always safe (a Dog satisfies the Animal contract).

declare let dogs:          readonly Dog[];
declare let readonlyAnimals: readonly Animal[];

readonlyAnimals = dogs;  // ✓ — safe! No write operations on readonly.

// The same principle with ReadonlyArray, Readonly<T>, and readonly tuple types
type ReadonlyPair<T> = readonly [T, T];
declare let dogPair:    ReadonlyPair<Dog>;
declare let animalPair: ReadonlyPair<Animal>;
animalPair = dogPair;  // ✓

// ReadonlyMap, ReadonlySet from lib follow the same pattern
declare let dogSet:    ReadonlySet<Dog>;
declare let animalSet: ReadonlySet<Animal>;
animalSet = dogSet;  // ✓

10. The in/out variance annotations (TypeScript 4.7)

TypeScript 4.7 added explicit variance annotations. Before this, TypeScript had to infer variance from the structure of the generic, which was expensive for complex types and sometimes wrong. The out T annotation declares "T only appears in output positions (covariant)" and in T declares "T only appears in input positions (contravariant)."

// Without annotations — TypeScript infers variance from usage
interface Producer<T> {
  produce(): T;  // T in return position → inferred covariant
}

// With explicit annotation — faster compilation, clearer intent
interface Producer<out T> {  // 'out' = covariant
  produce(): T;
}

interface Consumer<in T> {  // 'in' = contravariant
  consume(value: T): void;
}

interface Transformer<in In, out Out> {  // in+out = bivariant-ish, but explicit
  transform(value: In): Out;
}
When to use variance annotations: primarily for library authors working on complex generic types where TypeScript's inference is slow or incorrect. For most application code, TypeScript infers variance correctly and annotations are optional. The annotations also serve as documentation — telling readers exactly how a type parameter is used. 
// TypeScript enforces that your annotation matches actual usage
interface Broken<out T> {
  produce(): T;
  // consume(x: T): void;  // ✗ ERROR — 'out T' but T appears in input position
}

11. Practical implications

Why you can't pass string[] to (string | number)[]

function addMixed(arr: (string | number)[]): void {
  arr.push(42);  // valid — 42 is a number, which is string|number
}

const strings: string[] = ["a", "b"];
// addMixed(strings);  // ✗ ERROR — would push 42 into a string[], corrupting it

// Note: string[] IS assignable to readonly (string|number)[] — that's safe
function readMixed(arr: readonly (string | number)[]): void {
  console.log(arr[0]); // only reading — safe
}
readMixed(strings);  // ✓

Function overloads and variance in practice

// Event handlers — contravariance of callbacks
type EventHandler<T> = (event: T) => void;

interface MouseEvent { x: number; y: number; }
interface ClickEvent extends MouseEvent { button: number; }

// A handler for any MouseEvent can handle a ClickEvent (contravariant)
declare const mouseHandler: EventHandler<MouseEvent>;
const clickHandler: EventHandler<ClickEvent> = mouseHandler;  // ✓

// Promise is covariant in its resolved type (read-only by nature)
declare const dogPromise: Promise<Dog>;
const animalPromise: Promise<Animal> = dogPromise;  // ✓

12. Excess property checking

There's one important exception to pure structural typing: excess property checking. When you assign a fresh object literal directly to a type, TypeScript checks for properties that the target type doesn't declare. This is a special rule — it doesn't apply to variables, only to literals used inline.

interface Config { host: string; port: number; }

// Excess property check — applies to fresh literal
const c1: Config = { host: "localhost", port: 3000, debug: true };
// ✗ Object literal may only specify known properties ('debug' doesn't exist in Config)

// No excess property check — variable assignment goes through structural typing
const obj = { host: "localhost", port: 3000, debug: true };
const c2: Config = obj;  // ✓ — obj has a wider type, assignable structurally

// Same for function arguments with inline literals vs variables
function connect(cfg: Config) { /* ... */ }
connect({ host: "localhost", port: 3000, timeout: 5000 }); // ✗ excess property check
connect(obj);  // ✓ — variable, no excess check
Why does this exist? Excess property checking catches a very common class of typo: writing { colour: "red" } when the type expects color. Without this rule, the extra property would silently be ignored, and you'd wonder why your color setting doesn't work. The rule applies to fresh literals because they are almost certainly intended only for this target type — there's no other reason you'd write a literal with a field that the target doesn't use.
