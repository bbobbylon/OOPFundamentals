API Error Handling — End to End

A failing API call is a journey: Spring throws, an @RestControllerAdvice turns it into a ProblemDetail, it crosses the wire as a status code + JSON, Angular wraps it in an HttpErrorResponse, your catchError inspects it, and something shows up for the user. Handle each hop deliberately and errors become a feature, not a surprise.

🚨 What happens when an API call fails — and who handles it?

Every API call can fail at four levels, each with a different owner. Network: the request never arrived (status: 0). Spring: the server returned 4xx/5xx, with @RestControllerAdvice shaping the body. Interceptor: catches 401 (silent refresh) or 503 (retry). Component: whatever wasn't handled upstream lands here — show a toast, an error state, or a retry. Not handling errors means blank screens and no feedback — one of the most common UX bugs in Angular apps.

  • Decide where each error is owned: transport, server, interceptor, or component — and don't double-handle.
  • Angular wraps every HTTP failure in HttpErrorResponse; status: 0 means it never reached the server.
  • In a service, catchError recovers what it can (e.g. 404 → empty list) and re-throws the rest for the component.
  • Spring 6 returns RFC 9457 ProblemDetail — read err.error.detail and field errors to map back onto form controls.
  • A global ErrorHandler is the safety net: log anything unhandled to telemetry so users never see a silent failure.

HttpErrorResponse

Angular wraps HTTP errors as HttpErrorResponse — { status, statusText, error, url }. Check err.status === 404; body via err.error?.detail; a network error is err.status === 0 && err.error instanceof ProgressEvent.

catchError in services

http.get('/api/users').pipe(catchError(err => err.status === 404 ? of([]) : throwError(() => err))). Recover what you can; re-throw what the component should handle. Never swallow errors silently.

Spring ProblemDetail (RFC 9457)

Spring 6+ returns { type, title, status, detail, instance }. Angular reads err.error.detail for the message, err.error.status for the code, and field-level invalid-params to map onto form controls.

In CIAM:interceptor: 401 → silent refresh, 503 → retry with backoff (max 3). Service: 404 on fetch → not-found page; 409 (email conflict) → structured error. Component: 400 → read err.error['invalid-params'] and form.get(field).setErrors({ serverError }) per field. A global ErrorHandler logs anything unhandled to telemetry.

1. Two kinds of failure (and they look different)

The server answered — with an error status

4xx (you) or 5xx (them). There's a real HTTP response with a status code and usually a ProblemDetail body. In Angular this is an HttpErrorResponse where error holds the parsed body and status is 4xx/5xx.

There was no answer at all

DNS failure, connection refused, timeout — or CORS blocking the response. Angular still gives you an HttpErrorResponse, but status === 0 and error is a raw ProgressEvent, not JSON. There's nothing to parse.

Telling these apart is the whole game: status > 0 → read the ProblemDetail; status === 0 → it never reached (or never returned from) the server.

3. The Angular error surface: HttpErrorResponse

What you actually catch

// the failing call
this.http.get<User>(`/api/v1/users/${'{'}id{'}'}`).pipe(
  catchError((err: HttpErrorResponse) => {
    if (err.status === 0) {
      // network / CORS — err.error is a ProgressEvent
      return throwError(() => new ApiError('OFFLINE'));
    }
    // server ProblemDetail lives in err.error
    const pd = err.error as ProblemDetail;
    return throwError(() => new ApiError(pd.title, err.status, pd));
  })
);

Typed models for both sides

// mirror Spring's RFC 7807 body
interface ProblemDetail {
  type: string; title: string;
  status: number; detail?: string;
  instance?: string;
  errors?: { field: string; message: string }[];
}
class ApiError {
  constructor(
    readonly message: string,
    readonly status = 0,
    readonly problem?: ProblemDetail) {}
}

4. Centralize it: one error interceptor

Don't write catchError in every component. Put cross-cutting rules (401 → login, 5xx → toast, retries) in a functional interceptor; let components handle only the errors specific to them (a 409 on a form).

export const errorInterceptor: HttpInterceptorFn = (req, next) =>
  next(req).pipe(
    retry({ count: 2, delay: retryBackoff }),       // only idempotent GETs, see §6
    catchError((err: HttpErrorResponse) => {
      const auth = inject(AuthService), toast = inject(ToastService);
      if (err.status === 401) auth.redirectToLogin();
      else if (err.status === 0)   toast.error("Can't reach the server");
      else if (err.status >= 500) toast.error('Something went wrong');
      return throwError(() => err);   // re-throw so components can still react
    })
  );

// register once
provideHttpClient(withInterceptors([authInterceptor, errorInterceptor]));

401 vs 403: only 401 should bounce the user to log in — a 403 means they're known but unauthorized, so logging in again changes nothing.

6. The status === 0 trap & retrying safely

Status 0 usually means CORS

When a call "fails for no reason" with status 0 and an empty error, it's most often a CORS rejection — the response came back but the browser refused to expose it. It works in Postman/curl (no CORS there) but not the SPA.

↪ Debug it with the Spring · CORS & Preflight deep-dive.

Retry only what's safe

function retryBackoff(err: HttpErrorResponse, i: number) {
  // don't retry 4xx (your fault) — only 0 / 5xx,
  // and only idempotent methods (GET/PUT/DELETE)
  if (err.status !== 0 && err.status < 500)
    return throwError(() => err);
  return timer(2 ** i * 300);   // 300ms, 600ms, …
}

Retrying a POST can double-create — see idempotency on the API-design page.

7. One-sentence recap

🧯 An API error travels Spring exception → @RestControllerAdvice → ProblemDetail → status code + JSON → Angular HttpErrorResponse → catchError → UI; read the ProblemDetail from err.error when status > 0 (and remember status === 0 means network/CORS with no body), centralize cross-cutting rules (401→login, 5xx→toast, safe retries) in an error interceptor while components handle their own 400/409, and map every status to a deliberate UX.
