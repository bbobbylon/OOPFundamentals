1 — Why Normalize?




Normalization removes data anomalies:




AnomalyProblemExample


Update anomalySame fact stored in multiple rows → easy to go inconsistentCity name stored on every order → update in 1000 places


Insert anomalyCan't add a fact without adding unrelated dataCan't add a product without an order


Delete anomalyDeleting a row loses unrelated factsDelete last order → lose customer record











2 — Normal Forms






FormRuleViolation


1NFAtomic values, no repeating groups, primary keyColumn "phones" stores "555-1234, 555-5678"


2NFNo partial dependencies (non-key col depends on PART of composite PK)Composite PK (order_id, product_id) but product_name depends only on product_id


3NFNo transitive dependencies (non-key col depends on another non-key col)zipcode → city (city depends on zipcode, not on PK)


BCNFEvery determinant is a candidate keyRare edge case; 3NF is sufficient for most applications











3 — Denormalization Trade-offs




-- 3NF: address stored in a separate table (correct but slow reads)
SELECT o.id, u.email, a.city, a.state
FROM orders o
JOIN users u ON u.id = o.user_id
JOIN addresses a ON a.id = o.address_id;

-- Denormalized: copy city/state into orders for fast reads
-- Trade-off: fast reads, but UPDATE address doesn't update orders
SELECT id, city, state FROM orders;


Denormalization is a deliberate choice for performance — common in data warehouses, reporting tables, and cached summary rows. Document it clearly. Use triggers or application logic to keep denormalized data consistent.
