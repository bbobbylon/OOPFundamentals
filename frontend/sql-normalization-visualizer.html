Database Normalization

1NF → 2NF → 3NF: eliminate redundancy and anomalies. Know when to denormalize for performance.

📐 What is database normalization — and why does it prevent data anomalies?

Normalization organizes tables to kill redundancy and the anomalies it causes — update (change a city in one of many rows and they diverge), delete (lose data when the last row goes), insert (can't store a user before an order). 1NF: atomic values, a key, no repeating groups. 2NF: 1NF + no partial dependency on part of a composite key. 3NF: 2NF + no transitive dependency (a non-key depending on another non-key). BCNF tightens 3NF for overlapping candidate keys. The counterweight is denormalization — normalization adds JOINs, so for read-heavy reporting a materialized view or a cached column is a fair trade.

  • Kills update/delete/insert anomalies — one fact stored once.
  • 1NF atomic · 2NF no partial dep · 3NF no transitive dep (BCNF tightens it).
  • Decompose into related tables — JOIN to recombine.
  • Denormalize deliberately — materialized views / cached columns for read-heavy paths.

1NF → 2NF → 3NF

-- Violates 1NF (arrays, no atomic values): user_id | roles | email 1 | ADMIN,VIEWER | a@eg.com ← NOT 1NF -- 1NF fix: one role per row user_roles(user_id, role_name) -- Violates 2NF (partial dependency): order_items(order_id, product_id, qty, product_name) ← NOT 2NF -- product_name depends only on product_id -- 2NF fix: separate table order_items(order_id, product_id, qty) products(product_id, product_name, price) -- Violates 3NF (transitive dependency): users(id, email, dept_id, dept_name) ← NOT 3NF -- dept_name → dept_id → id (transitive) -- 3NF fix: separate table users(id, email, dept_id) departments(dept_id, dept_name) -- Fully normalized CIAM schema: users(id, email, idp_type, external_id) roles(id, role_name, description) user_roles(user_id, role_id, assigned_at)

When to denormalize

-- Normalized: need 3 JOINs for user+roles: SELECT u.email, r.role_name FROM users u JOIN user_roles ur ON u.id = ur.user_id JOIN roles r ON ur.role_id = r.id WHERE u.id = 42; -- Denormalized (cached roles as JSONB): -- Add to users: roles_cache JSONB -- {"roles":["CIAM_ADMIN","USER"],"cached_at":"..."} SELECT email, roles_cache->>'roles' FROM users WHERE id = 42; -- Faster (no JOINs) but must invalidate -- cache on role change! -- Materialized view (best of both): CREATE MATERIALIZED VIEW user_with_roles AS SELECT u.id, u.email, array_agg(r.role_name) AS roles FROM users u JOIN user_roles ur ON u.id = ur.user_id JOIN roles r ON ur.role_id = r.id GROUP BY u.id, u.email; -- Refresh: REFRESH MATERIALIZED VIEW user_with_roles;

JPA entity design

Normalized SQL schema → JPA entity design. 1NF (no arrays in columns) → @OneToMany / @ManyToMany relationship: @ManyToMany @JoinTable(name="user_roles") Set<Role> roles;. 2NF (separate products table) → separate @Entity class Product + @ManyToOne Product product on OrderItem. 3NF (separate department table) → @ManyToOne @JoinColumn(name="dept_id") Department department; (never store dept_name directly on User entity). JPA's @Embedded / @Embeddable: for value types that don't need their own table (Address, Money amount+currency) — stores multiple columns in the parent table but maps as a separate Java class. @OneToMany(cascade = ALL): when you save the parent, child rows are automatically inserted/updated/deleted — maps to referential integrity in SQL. orphanRemoval = true: removing a child entity from the collection also DELETEs it from DB.

CIAM schema normalization: A bad schema — users(id, email, role1, role2, role3, ping_id, entra_id, ...) — violates 1NF (role columns/arrays) and 2NF (IDP info mixed in). Normalized: users → user_idp_links(user_id, idp_type, external_id) → user_roles → roles. Now adding Okta is just a row with idp_type='OKTA' (no schema change), a new role needs no new column, and cross-IDP role queries are a clean JOIN. Strategic denormalization: sessions stores user_email redundantly to skip a JOIN on every validation — fine since email rarely changes; document the decision in a schema comment.

or, the table that passes every normal form and still lies to you

The problem

1NF: atomic. 2NF: no partial dependency. 3NF: no transitive dependency. Every box checked. The anomaly is still there.

Adding one role means inserting four rows

A user can hold several independent roles (ADMIN, VIEWER, BILLING) and can be enrolled in several independent MFA factors (TOTP, WEBAUTHN, SMS) — two facts about the same user that have nothing to do with each other. Someone models both in one junction table: user_role_mfa(user_id, role, mfa_factor), primary key on all three columns.

Run it through the checklist: 1NF — every column atomic, yes. 2NF — no partial dependency, because there's no non-key column at all to depend on part of the key. 3NF — no transitive dependency, same reason; BCNF — the only candidate key is the whole row, so it trivially holds. The table is fully normalized by every rule this page teaches. And yet: user 42 has 2 roles and 2 MFA factors, so representing "these are simply the facts about user 42" correctly requires four rows — one for every role/factor combination — because leaving any combination out reads as "role X only applies via factor Y," which was never true.

1NF/2NF/3NF/BCNF all pass ✓ single composite primary key ✓ adding a 3rd role means inserting 2 more rows just to keep the cross-product honest ⚠

This is a real, documented anomaly with its own name and its own normal form: 3NF and BCNF only ever talk about functional dependencies. This table's problem is a multi-valued dependency — two independent one-to-many facts crammed into one table — and only 4NF checks for that.

Split independent multi-valued facts into their own tables
Ask: are these two attributes actually independent of each other? ↓ roles and MFA factors both depend on user_id, but never on EACH OTHER — that's the definition of a multi-valued dependency worth splitting Give each one its own two-column table ↓ user_roles(user_id, role) and user_mfa_factors(user_id, mfa_factor) — 2 + 2 = 4 rows total instead of the 2 × 2 = 4-row cross-product that grows multiplicatively as either list grows Recombine with a JOIN only when you actually need both facts together ↓ the two tables were never related to each other in the first place — a JOIN across them was always an artificial cross-product, not a real relationship
The one-sentence rule. 3NF and BCNF only rule out one non-key column determining another — they say nothing about two independent one-to-many facts sharing a table, so a table with a spotless 3NF/BCNF checklist can still force you to fake a relationship between two things that were never related.
1NF asks "is each cell atomic?" 3NF asks "does every non-key column depend on nothing but the key?" 4NF asks a completely different question: "are two of these facts independent of each other, even though they share the same key?" — and nothing before 4NF ever asks it.
You

This table is in BCNF. Why do I still have to insert four rows to add one role?

The user_role_mfa table

Because you're storing two independent one-to-many facts as if they were one three-way relationship. I have no way to say "user 42 has role BILLING" without also picking an MFA factor to pair it with.

You

But roles and MFA factors have nothing to do with each other!

A multi-valued dependency

Exactly — and that's precisely the shape 4NF exists to catch. 3NF never checks for it, because there's no non-key column here for one column to transitively depend on.

The mechanism

Walk through what "add role BILLING for user 42" actually requires in each design.

  1. User 42 currently has roles {ADMIN, VIEWER} and MFA factors {TOTP, WEBAUTHN}starting state
  2. In the combined table, that's 4 existing rows: every role × every factorcross-product
  3. You need to add role BILLING for user 42 — nothing to do with their MFA factorsthe change
  4. To keep the table honest, you must insert (BILLING, TOTP) AND (BILLING, WEBAUTHN) — two rows for one factforced duplication
  5. Forget the second row and the table now implies "BILLING only applies via TOTP," which is falsesilent lie
  6. In the split design, the same change is one row in user_roles — user_mfa_factors is untouched, because it was never relatedthe fix

Step 4 is the anomaly in miniature: a single, simple fact ("user 42 also has role BILLING") that should cost one row costs two, purely because of a table design decision made before anyone tried to add a role. Multiply that by however many MFA factors a real system supports and the duplication compounds every time either list grows.

user 42 gains one new role: BILLINGa fact with nothing to do with MFA factors
who has to react in the combined table ↓
the roles this user holds every existing MFA-factor row — each one needs a BILLING-paired duplicate nothing in a properly split schema

In the split design, adding a role is a subject reacting alone — one insert, one table, done. In the combined design, the fan-out is real: every row in the OTHER independent fact has to react too, just to keep the cross-product from silently implying a relationship that was never true.

A table user_role_mfa(user_id, role, mfa_factor) has a composite primary key on all three columns and passes every 1NF/2NF/3NF/BCNF check with no non-key columns at all. A user has 3 roles and 2 MFA factors, both independent facts. How many rows does correctly representing that user require?

Right. Because the table forces every role to pair with every factor, 3 roles × 2 factors means 6 rows for what is really just 5 independent facts (3 roles + 2 factors) about one user — that gap between "6 rows stored" and "5 facts that are true" is the multi-valued-dependency anomaly, invisible to 3NF and BCNF alike.

That's the row count in the CORRECTLY split design — two separate tables, one row per fact. In the single combined table this question describes, you don't get to choose 5 rows; the composite key forces every combination to exist or the missing ones read as false negatives.

BCNF only ever reasons about functional dependencies — one column determining another. It has no concept of two independent multi-valued facts sharing a key, which is exactly why a spotless BCNF table can still have this anomaly. That's what 4NF exists to catch, and this page's normal-form ladder stops one rung short of it.

Where you have seen this before

"Passing every check on the list doesn't mean the list covered everything" recurs constantly.

A CIAM permissions table with the same shape

A table like user_permission_scope(user_id, permission, tenant_scope) has the identical trap if permissions and tenant scopes are actually independent per-user facts — granting a new permission forces you to re-pair it with every scope the user already has, or the table implies the permission only applies in some scopes when it should apply in all of them.

Passing unit tests that never covered the real bug

A test suite with 100% line coverage on a function can still miss an entire category of bug — coverage answers "was this line executed," never "was every INDEPENDENT combination of inputs considered." 4NF is the database version of a coverage metric people forget exists.

a green checklist measures what it was built to measure, nothing more

OWASP's own list versus "secure"

Passing every item on the OWASP Top 10 checklist doesn't mean an application has no vulnerabilities — it means the specific categories that list enumerates were addressed. 3NF/BCNF are the OWASP Top 10 of schema design: necessary, well-known, and not the complete list of things that can go wrong.

a named, numbered standard is still a subset of "actually correct"

3 — Denormalization Trade-offs




-- 3NF: address stored in a separate table (correct but slow reads)
SELECT o.id, u.email, a.city, a.state
FROM orders o
JOIN users u ON u.id = o.user_id
JOIN addresses a ON a.id = o.address_id;

-- Denormalized: copy city/state into orders for fast reads
-- Trade-off: fast reads, but UPDATE address doesn't update orders
SELECT id, city, state FROM orders;


Denormalization is a deliberate choice for performance — common in data warehouses, reporting tables, and cached summary rows. Document it clearly. Use triggers or application logic to keep denormalized data consistent.
