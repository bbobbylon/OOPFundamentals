Database Normalization

1NF → 2NF → 3NF: eliminate redundancy and anomalies. Know when to denormalize for performance.

What is database normalization — and why does it prevent data anomalies?

Normalization is the process of organizing a database to reduce data redundancy and prevent update anomalies. An anomaly is a situation where you can end up with inconsistent data. Consider a single table: UserOrders(user_id, user_email, user_city, order_id, product). If a user changes their city, you must update EVERY row with their orders — miss one and the data is inconsistent (update anomaly). If you delete their last order, you lose their city data too (delete anomaly). If you want to store a new user before they've ordered anything, you can't (insert anomaly). Normalization solves this by decomposing tables. 1NF (First Normal Form): each column contains atomic (single) values — no arrays, no comma-separated lists in a cell. Each row is unique (has a primary key). No repeating column groups (not: product1, product2, product3 as columns — instead, separate rows). 2NF (Second Normal Form): must be in 1NF + no partial dependency — every non-key column must depend on the ENTIRE primary key (only relevant when the primary key is composite). Example: in OrderItems(order_id, product_id, product_name) — product_name depends only on product_id, not the full composite key. Fix: separate Products table. 3NF (Third Normal Form): must be in 2NF + no transitive dependency — no non-key column depends on another non-key column. Example: Users(id, zip_code, city) — city depends on zip_code, not on id. Fix: separate ZipCodes table. BCNF (Boyce-Codd NF): stronger version of 3NF, handles edge cases with multiple overlapping candidate keys. When to denormalize: normalization adds JOINs, which add query complexity and (sometimes) performance cost. For read-heavy reporting tables or materialized views, strategic denormalization (storing pre-computed/redundant data) is acceptable.

1NF → 2NF → 3NF

-- Violates 1NF (arrays, no atomic values): user_id | roles | email 1 | ADMIN,VIEWER | a@eg.com ← NOT 1NF -- 1NF fix: one role per row user_roles(user_id, role_name) -- Violates 2NF (partial dependency): order_items(order_id, product_id, qty, product_name) ← NOT 2NF -- product_name depends only on product_id -- 2NF fix: separate table order_items(order_id, product_id, qty) products(product_id, product_name, price) -- Violates 3NF (transitive dependency): users(id, email, dept_id, dept_name) ← NOT 3NF -- dept_name → dept_id → id (transitive) -- 3NF fix: separate table users(id, email, dept_id) departments(dept_id, dept_name) -- Fully normalized CIAM schema: users(id, email, idp_type, external_id) roles(id, role_name, description) user_roles(user_id, role_id, assigned_at)

When to denormalize

-- Normalized: need 3 JOINs for user+roles: SELECT u.email, r.role_name FROM users u JOIN user_roles ur ON u.id = ur.user_id JOIN roles r ON ur.role_id = r.id WHERE u.id = 42; -- Denormalized (cached roles as JSONB): -- Add to users: roles_cache JSONB -- {"roles":["CIAM_ADMIN","USER"],"cached_at":"..."} SELECT email, roles_cache->>'roles' FROM users WHERE id = 42; -- Faster (no JOINs) but must invalidate -- cache on role change! -- Materialized view (best of both): CREATE MATERIALIZED VIEW user_with_roles AS SELECT u.id, u.email, array_agg(r.role_name) AS roles FROM users u JOIN user_roles ur ON u.id = ur.user_id JOIN roles r ON ur.role_id = r.id GROUP BY u.id, u.email; -- Refresh: REFRESH MATERIALIZED VIEW user_with_roles;

JPA entity design

Normalized SQL schema → JPA entity design. 1NF (no arrays in columns) → @OneToMany / @ManyToMany relationship: @ManyToMany @JoinTable(name="user_roles") Set<Role> roles;. 2NF (separate products table) → separate @Entity class Product + @ManyToOne Product product on OrderItem. 3NF (separate department table) → @ManyToOne @JoinColumn(name="dept_id") Department department; (never store dept_name directly on User entity). JPA's @Embedded / @Embeddable: for value types that don't need their own table (Address, Money amount+currency) — stores multiple columns in the parent table but maps as a separate Java class. @OneToMany(cascade = ALL): when you save the parent, child rows are automatically inserted/updated/deleted — maps to referential integrity in SQL. orphanRemoval = true: removing a child entity from the collection also DELETEs it from DB.

CIAM schema normalization: A poorly designed CIAM schema might have: users(id, email, role1, role2, role3, ping_id, entra_id, ping_groups, entra_groups) — violates 1NF (multiple role columns, arrays), 2NF (all IDP info mixed). Fully normalized: users(id, email, created_at) → user_idp_links(user_id, idp_type, external_id, display_name) → user_roles(user_id, role_id) → roles(id, role_name). Benefits: adding a third IDP (Okta) requires no schema change — just a new row in user_idp_links with idp_type='OKTA'. Adding a fourth role doesn't require a new column. Querying all of a user's roles across all IDPs is a clean JOIN. Strategic denormalization: the sessions table stores user_email redundantly (to avoid a JOIN on every session validation check) — acceptable because email rarely changes and the performance win is significant. Document denormalization decisions in schema comments.

3 — Denormalization Trade-offs




-- 3NF: address stored in a separate table (correct but slow reads)
SELECT o.id, u.email, a.city, a.state
FROM orders o
JOIN users u ON u.id = o.user_id
JOIN addresses a ON a.id = o.address_id;

-- Denormalized: copy city/state into orders for fast reads
-- Trade-off: fast reads, but UPDATE address doesn't update orders
SELECT id, city, state FROM orders;


Denormalization is a deliberate choice for performance — common in data warehouses, reporting tables, and cached summary rows. Document it clearly. Use triggers or application logic to keep denormalized data consistent.
