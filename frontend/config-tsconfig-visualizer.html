tsconfig.json

What is tsconfig.json — and how does it control what TypeScript catches and what JavaScript is emitted?

tsconfig.json is the TypeScript compiler's configuration file. Every TypeScript project has at least one, and Angular projects typically have three in an extends chain: tsconfig.json (base, workspace-wide), tsconfig.app.json (for the app build), and tsconfig.spec.json (for tests). The TypeScript compiler (tsc) reads this file to know: what files to include/exclude, what target JavaScript to emit, how strict to be with type checking, how to resolve modules, and how to handle Angular's special decorators. compilerOptions is the most important section. target: what JavaScript version to emit. Angular 17+ targets ES2022 — modern browsers all support it, and it enables the best optimizations. Don't target ES5 anymore — Angular dropped IE11 support. strict: the single most valuable TypeScript setting. Enables: noImplicitAny (can't use variables without type), strictNullChecks (null and undefined are NOT assignable to non-null types), strictPropertyInitialization (class properties must be initialized), and more. Without strict mode, TypeScript is just JavaScript with occasional types. With strict mode, TypeScript catches entire classes of bugs at compile time that would otherwise surface as runtime errors. module and moduleResolution: controls how TypeScript resolves import from 'rxjs'. For Angular: "module": "ES2022" and "moduleResolution": "bundler" (Angular 17+) or "node16". paths: alias imports — @app/* maps to src/app/*. Enables import { AuthService } from '@app/core/services/auth.service' instead of ugly relative paths. experimentalDecorators: must be true for Angular's class decorators (@Component, @Injectable). Angular 17+ is moving toward standards-based decorators but still requires this for now.

Angular tsconfig.json

{ "compileOnSave": false, "compilerOptions": { "baseUrl": "./", "outDir": "./dist/out-tsc", "strict": true, // ← the most important flag "noImplicitOverride": true, // explicit 'override' keyword "noPropertyAccessFromIndexSignature": true, "noImplicitReturns": true, // all code paths must return "noFallthroughCasesInSwitch": true, "skipLibCheck": true, "esModuleInterop": false, "sourceMap": true, "declaration": false, "downlevelIteration": true, "experimentalDecorators": true, "moduleResolution": "bundler", "module": "ES2022", "useDefineForClassFields": false, "lib": ["ES2022", "dom"] }, "angularCompilerOptions": { "enableI18nLegacyMessageIdFormat": false, "strictInjectionParameters": true, "strictInputAccessModifiers": true, "strictTemplates": true // ← type-check templates } }

strict mode (what it catches)

// WITHOUT strict mode: function getUserEmail(user) { return user.email.toLowerCase(); // ↑ No error if user is null — crashes at runtime } // WITH strict mode (noImplicitAny + strictNullChecks): function getUserEmail(user: User | null): string { // TypeScript ERROR: // Object is possibly null (user may be null) return user.email.toLowerCase(); // Must handle null: return user?.email?.toLowerCase() ?? ''; // Or: if (!user) throw new Error('User is required'); return user.email.toLowerCase(); // ← safe now } // strictTemplates (Angular-specific): // Catches type errors IN HTML templates: // <p>{{ user.emaill }}</p> // ↑ ERROR: Property 'emaill' does not exist on User // (typo caught at build time, not runtime)

paths aliases

// tsconfig.json: { "compilerOptions": { "baseUrl": ".", "paths": { "@app/*": ["src/app/*"], "@env/*": ["src/environments/*"], "@shared/*": ["src/app/shared/*"], "@core/*": ["src/app/core/*"] } } } // BEFORE (ugly relative imports): import { AuthService } from '../../../core/services/auth.service'; // AFTER (clean alias imports): import { AuthService } from '@core/services/auth.service'; import { User } from '@shared/models/user.model'; // angular.json must also declare paths // (for the CLI build to resolve them): // Usually configured via tsconfig — CLI reads it // IMPORTANT: // Jest config also needs moduleNameMapper to match // TS paths (otherwise tests fail to resolve imports)

In CIAM / Context: The CIAM Angular app uses strict: true + strictTemplates: true — all type errors including template binding mismatches are caught at build time, never at runtime. Path aliases: @core/* maps to services (AuthService, TokenService), @shared/* maps to shared components and models (User, Role, TokenResponse). This means 300+ files import cleanly without counting ../../ relative hops. All of this runs in the AOT compilation step in the CI pipeline before any test or build artifact.

tsconfig.json Anatomy

TypeScript's compiler configuration file. Every Angular, Node, and modern front-end project has one. The root object has three keys: compilerOptions, include/exclude, and references.

{
  /* ── Extend a base config (optional) ──────────────────── */
  "extends": "./tsconfig.json",     // merge parent, then override below

  /* ── Compiler Options ─────────────────────────────────── */
  "compilerOptions": {

    /* Type checking */
    "strict": true,                // enables all strict* flags at once
    "noImplicitAny": true,         // error on implicit `any`
    "strictNullChecks": true,      // null/undefined are not assignable to everything
    "strictFunctionTypes": true,   // check function parameter types contravariantly
    "noUnusedLocals": true,        // error on unused variables
    "noUnusedParameters": true,    // error on unused function parameters
    "noImplicitReturns": true,     // all code paths must return a value
    "noFallthroughCasesInSwitch": true,

    /* Output target */
    "target": "ES2022",           // emitted JavaScript version
    "lib": ["ES2022", "DOM", "DOM.Iterable"],  // type defs available
    "useDefineForClassFields": true, // TC39 class fields semantics

    /* Module system */
    "module": "ES2022",           // output module format
    "moduleResolution": "bundler",// how imports are resolved
    "esModuleInterop": true,      // allow `import fs from 'fs'` for CJS
    "allowSyntheticDefaultImports": true,

    /* Paths */
    "baseUrl": ".",               // root for non-relative imports
    "paths": {
      "@app/*": ["src/app/*"],
      "@env/*": ["src/environments/*"]
    },

    /* Decorators (Angular needs these) */
    "experimentalDecorators": true,
    "emitDecoratorMetadata": true, // needed for Angular DI reflection

    /* Source maps */
    "sourceMap": true,
    "inlineSources": true,        // embed .ts source in .js.map

    /* Output directory */
    "outDir": "./dist/out-tsc",
    "declaration": true,          // emit .d.ts files (for libraries)
    "declarationMap": true,       // .d.ts.map for go-to-definition

    /* Interop */
    "skipLibCheck": true,         // skip type-check of .d.ts files
    "forceConsistentCasingInFileNames": true
  },

  /* ── Files to include / exclude ──────────────────────── */
  "include": ["src/**/*.ts"],
  "exclude": ["node_modules", "dist", "**/*.spec.ts"]
}

Strict Mode — All the Flags

Setting "strict": true is shorthand for enabling all of the flags below simultaneously. You can override individual ones after setting strict.

"strict": true,    // equivalent to all of these:

"strictNullChecks":         true,
"noImplicitAny":            true,
"strictFunctionTypes":      true,
"strictBindCallApply":      true,
"strictPropertyInitialization": true,
"noImplicitThis":           true,
"alwaysStrict":             true,
"useUnknownInCatchVariables": true
strictNullChecks
null and undefined are their own types. You must check before using.
let x: string = null; // ✗ error let x: string | null = null; // ✓ ok if (x !== null) x.toUpperCase();
noImplicitAny
Parameters without a type annotation that TypeScript can't infer become errors.
function greet(name) { ... } // ✗ implicit any function greet(name: string) {} // ✓
strictFunctionTypes
Function parameters are checked contravariantly — prevents unsound callbacks.
type Handler = (x: Animal) => void; const h: Handler = (x: Dog) => x.bark(); // ✗ // Dog is more specific — ok for methods, error for functions
strictPropertyInitialization
Class properties declared in a class body must be assigned in the constructor.
class User { name: string; } // ✗ class User { name!: string; } // ✓ (definite assignment) class User { name = ''; } // ✓ (initializer)
useUnknownInCatchVariables
catch (e) gives e the type unknown instead of any — forces type narrowing.
try { ... } catch (e) { e.message; // ✗ unknown has no .message if (e instanceof Error) e.message; // ✓ }
noImplicitThis
Error when `this` has type any (e.g., function() { this.x } with no context).
const fn = function() { this.x; } // ✗ `this` is any const fn = () => this.x; // ✓ arrow inherits outer this
noUnusedLocals
Variables declared but never read are compile errors. (Not in strict — add separately.)
const unused = 5; // ✗ 'unused' is declared but never read const _unused = 5; // ✓ prefix _ to suppress
noImplicitReturns
All code paths in a non-void function must return a value.
function f(x: boolean): number { if (x) return 1; // ✗ missing return on else path } function f(x: boolean): number { return x ? 1 : 0; // ✓ }

Opt out of individual strict flags

"strict": true,
// Turn off one flag you can't fix yet:
"strictPropertyInitialization": false,
// Common for legacy Angular code using @Input() without initializers

Module & moduleResolution

Two orthogonal settings that are often confused. module controls what the emitted JavaScript looks like; moduleResolution controls how TypeScript finds imported files.

module — output format

ValueEmits
CommonJSrequire() / module.exports
ESNextimport / export (passthrough)
ES2022import / export (specific syntax)
NodeNextCJS or ESM based on file extension
SystemSystemJS loader format
NoneNo module output (scripts only)

moduleResolution — lookup algorithm

ValueUse when
nodeLegacy Node.js / webpack 4
node16 / nodenextNative Node.js ESM
bundler AngularVite, esbuild, webpack 5 — most flexible
classicVery old TS — avoid

moduleResolution: "bundler" — what it allows

// With "bundler", these all work:
import { x } from './utils';       // no extension needed (bundler adds it)
import { y } from './utils.js';    // explicit .js extension also ok
import data from './data.json';   // JSON imports
import styles from './app.css';   // CSS modules (if bundler supports)

The lib array — global type definitions

"lib": ["ES2022", "DOM", "DOM.Iterable"]

// ES2022  → Array.at(), structuredClone(), Object.hasOwn(), Error.cause
// DOM     → document, window, HTMLElement, fetch, localStorage
// DOM.Iterable → allows iteration over NodeList, HTMLCollection

// For Node.js servers (no DOM):
"lib": ["ES2022"]
// Install @types/node for process, __dirname, Buffer etc.

target vs lib — not the same thing

target: "ES2022"

Controls which JavaScript syntax TypeScript emits. If you target ES5, async/await is compiled to state machines. If you target ES2022, async/await emits as-is.

lib: ["ES2022", "DOM"]

Controls which type definitions are in scope for your code. You can target ES5 but still use Promise types by including ES6 in lib — just make sure there's a polyfill at runtime.

useDefineForClassFields

// Controls how class fields are compiled:

// useDefineForClassFields: true (TC39 spec — Angular 15+)
class Foo {
  x = 1;    // compiles to: Object.defineProperty(this, "x", { value: 1, ... })
}

// useDefineForClassFields: false (TypeScript legacy)
class Foo {
  x = 1;    // compiles to: this.x = 1;
}

// Angular 15+ requires true. Angular 14 had a known issue with decorators + true.

paths & baseUrl — Import Aliases

Instead of ../../../core/auth.service, configure aliases like @core/auth.service.

Configuration

"compilerOptions": {
  "baseUrl": ".",              // project root (where tsconfig.json lives)
  "paths": {
    // "@alias/*" → ["path/from/baseUrl/*"]
    "@app/*":  ["src/app/*"],
    "@core/*": ["src/app/core/*"],
    "@env/*":  ["src/environments/*"],
    "@shared/*":["src/app/shared/*"],

    // Multiple fallbacks (tried left to right)
    "my-lib":  ["src/lib/index.ts", "node_modules/my-lib"]
  }
}

Using the aliases

// Before (relative, fragile when moving files):
import { UserService } from '../../../core/services/user.service';

// After (alias, works regardless of file location):
import { UserService } from '@core/services/user.service';

Angular also needs aliases in angular.json

// tsconfig.json tells TypeScript — but the build tool also needs to know
// Angular CLI (esbuild) reads tsconfig paths automatically ✓
// If using Jest, add moduleNameMapper in jest.config.ts:
moduleNameMapper: {
  '^@app/(.*)$': '<rootDir>/src/app/$1',
  '^@core/(.*)$': '<rootDir>/src/app/core/$1'
}

rootDir and outDir

"rootDir": "src",    // root of TypeScript source files
"outDir":  "dist",   // mirrors src/ structure in dist/

// src/app/user.ts    → dist/app/user.js
// src/main.ts        → dist/main.js

Project References & Composite Projects

For monorepos or projects with separate app + library layers. References enable incremental builds — only recompile what changed.

Structure

my-monorepo/
├── tsconfig.json           // root (no compiling, just references)
├── packages/
│   ├── ui-lib/
│   │   ├── tsconfig.json   // "composite": true required
│   │   └── src/
│   └── admin-app/
│       ├── tsconfig.json   // references ui-lib
│       └── src/

Root tsconfig (solution file)

{
  "files": [],               // don't compile root itself
  "references": [
    { "path": "packages/ui-lib" },
    { "path": "packages/admin-app" }
  ]
}

Library tsconfig — must be composite

{
  "compilerOptions": {
    "composite": true,       // enables incremental builds + .d.ts emit
    "declaration": true,     // required when composite is true
    "declarationMap": true,  // go-to-definition works across packages
    "outDir": "dist"
  },
  "include": ["src"]
}

App tsconfig — references the library

{
  "compilerOptions": {
    "paths": { "@ui-lib/*": ["../ui-lib/src/*"] }
  },
  "references": [
    { "path": "../ui-lib" }   // tsc builds ui-lib first if needed
  ]
}

Building with references

# Build all projects in dependency order
tsc --build             // alias: tsc -b

# Build and watch incrementally
tsc --build --watch

# Force rebuild all
tsc --build --force

# Clean build outputs
tsc --build --clean

Angular workspace — tsconfig.app.json splits

my-ng-app/
├── tsconfig.json           // base: shared options for all
├── tsconfig.app.json       // extends base; includes src/main.ts only
└── tsconfig.spec.json      // extends base; includes *.spec.ts

Angular's tsconfig Pattern

A new Angular project has three tsconfig files that extend each other. Understanding the hierarchy prevents "works in app, errors in test" surprises.

tsconfig.json — shared base

{
  "compileOnSave": false,
  "compilerOptions": {
    "baseUrl": ".",
    "outDir": "./dist/out-tsc",
    "strict": true,
    "noImplicitOverride": true,
    "noPropertyAccessFromIndexSignature": true,
    "noImplicitReturns": true,
    "noFallthroughCasesInSwitch": true,
    "skipLibCheck": true,
    "esModuleInterop": true,
    "sourceMap": true,
    "declaration": false,
    "experimentalDecorators": true,
    "moduleResolution": "bundler",
    "target": "ES2022",
    "module": "ES2022",
    "lib": ["ES2022", "dom"],
    "useDefineForClassFields": false  // Angular 17 default for decorators compat
  }
}

tsconfig.app.json — production app only

{
  "extends": "./tsconfig.json",
  "compilerOptions": {
    "outDir": "./dist/out-tsc",
    "types": []             // no @types/* in app bundle (keeps it clean)
  },
  "files": [
    "src/main.ts"           // entry point only — Angular resolves the graph
  ],
  "include": [
    "src/**/*.d.ts"         // include local .d.ts ambient declarations
  ]
}

tsconfig.spec.json — unit tests

{
  "extends": "./tsconfig.json",
  "compilerOptions": {
    "outDir": "./dist/out-tsc",
    "types": ["jasmine"]     // or ["jest"] if using Jest
  },
  "include": [
    "src/**/*.spec.ts",      // test files
    "src/**/*.d.ts"
  ]
}
