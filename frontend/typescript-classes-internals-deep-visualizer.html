Classes Deep — #private vs private, Param Props & this Types

The Classes page shows the surface syntax. This companion goes to the runtime: what TypeScript erases, what actually enforces privacy, how parameter properties desugar, and how a class can stay type-safe across subclasses with this types.

🏛️ What makes TypeScript class internals different from Java — and what does TS actually erase?

TypeScript classes are syntactic sugar over JavaScript prototypes, and much of what TypeScript adds is erased at compile time — knowing what survives and what vanishes is critical for debugging. private is compile-time only (a plain public property at runtime, visible in JSON.stringify and DevTools), whereas #private fields are truly private (a WeakMap the engine enforces). Parameter properties collapse declare-and-assign into the constructor signature, and a this return type keeps method chaining type-safe across subclasses.

  • private is erased; #private is real. Use # for secrets — private leaks at runtime and in JSON.
  • Parameter properties — constructor(private repo: Repo) declares + assigns in one line (idiomatic Angular DI).
  • this return type enables chaining across subclasses — each call returns the actual subtype.
  • Most annotations vanish at runtime. TS adds compile-time safety, not runtime enforcement.

private vs #private

class UserTS { private password: string; // TS only — erased #secret: string; // truly private at runtime constructor(pw: string, sec: string) { this.password = pw; this.#secret = sec; } } const u = new UserTS('p@ss', 'secret123'); // TypeScript error: u.password; // Error: property is private u.#secret; // Error: private identifier // But at RUNTIME in JS: (u as any).password; // 'p@ss' — accessible! (u as any).#secret; // SyntaxError — truly blocked // In JSON: JSON.stringify(u); // {"password":"p@ss"} — leaks!. Conclusion: use #private for sensitive fields (passwords, tokens) since TypeScript's private offers no runtime protection.

Parameter properties

// Without parameter properties (verbose) class UserService { private readonly userRepo: UserRepository; private readonly jwtService: JwtService; constructor(userRepo: UserRepository, jwt: JwtService) { this.userRepo = userRepo; this.jwtService = jwt; } } // With parameter properties (idiomatic Angular/TS) class UserService { constructor( private readonly userRepo: UserRepository, private readonly jwtService: JwtService ) {} } // EXACT same compiled output — just half the lines // Both are equally valid in Angular @Injectable classes

this types for chaining

class QueryBuilder { protected filters: string[] = []; where(condition: string): this { this.filters.push(condition); return this; // 'this' = actual subtype } } class UserQueryBuilder extends QueryBuilder { activeOnly(): this { return this.where('active = true'); } } const q = new UserQueryBuilder() .where('name LIKE ?') // returns UserQueryBuilder .activeOnly() // returns UserQueryBuilder .where('email IS NOT NULL'); // still UserQueryBuilder // Without 'this' return type: .where() returns QueryBuilder // and .activeOnly() would be a compile error

CIAM / Angular: Angular services use parameter properties everywhere — @Injectable() class UserService { constructor(private http: HttpClient, private auth: AuthService) {} } — DI reads the parameter types from compiler metadata. Never keep a token in TS private (it leaks); use #token or an httpOnly cookie. A chainable query builder with this returns — new UserSearchQuery().where(filter).sortBy('name').limit(20) — stays fully typed across every call.

or, one function object for ten thousand objects — until you type an arrow

The problem

Your method never belonged to your object.

The callback that lost its object

You wrote an idle-timeout warning, wired it up with setTimeout(this.warn, 60_000), and tsc said nothing at all. Sixty seconds later production throws Cannot read properties of undefined (reading 'banner').

Here is the thing nobody tells you: this.warn did not read a property off your instance. Your instance has no warn. The lookup missed, walked up to SessionTimer.prototype, found one bare function sitting there, and handed it to you with nothing attached. The dot was supplying the object. You copied the function and threw the dot away.

warn is not on the instance lookup walks the prototype called with no receiver ⚠ tsc compiles it clean ⚠

The bug is not that this changed. It is that this was never stored anywhere — it is handed in fresh on every single call, by whatever sits to the left of the dot.

Three fixes, three different bills
warn = () => this.banner.show() ↓ a field, not a method — one NEW closure per instance, but it survives being torn off this.warn = this.warn.bind(this) ↓ same per-instance bill, and the prototype method still exists underneath for super setTimeout(() => this.warn(), 60_000) ↓ costs nothing per object — the dot is still there, at the call site, where it belongs
A method is not part of your object. this is whatever sits to the left of the dot, decided fresh at every call. Which is why detaching a method detaches its object too — and why the fix is never "bind harder", it is "keep the dot".

This is the part everyone re-learns: an arrow class property turns this picture upside down. warn = () => … is a field, so it is created inside the constructor — ten thousand timers, ten thousand closures, and the prototype holding nothing at all.

Writing class creates two objects, not one. There is the constructor function SessionTimer, and there is the plain object hanging off its .prototype. Instance methods are installed on the prototype object; fields (including parameter properties, and including arrow properties) are assigned onto each instance in the constructor; and static members are stuck on the constructor function itself — which is exactly why SessionTimer.MAX_IDLE works and timer.MAX_IDLE is undefined. extends then wires both chains: Object.getPrototypeOf(Child.prototype) is Parent.prototype so instances find inherited methods, and Object.getPrototypeOf(Child) is Parent — that second link is the only reason statics are inherited at all.

A grid renders 5,000 Row components. You change onSelect() { … } to onSelect = () => { … } so it can be passed straight to a child. What did that cost you?

They are not the same declaration. onSelect() {} is a method definition and is installed on Row.prototype exactly once, when the class body evaluates. onSelect = () => {} is a field initializer — it runs in the constructor, on every instance, forever.

Right — one closure per row, each capturing its own this. That capture is precisely what lets it survive being torn off and handed to a child, and it is precisely what you are paying for. On 5,000 rows it is usually fine. On a list you rebuild sixty times a second it is 300,000 function objects a second for the garbage collector.

There is no lazy, lookup-time binding in JavaScript. bind() and arrow class fields both produce a real, new function object, eagerly, at construction time.

Questions from the back row

If warn is shared by all 10,000 timers, how does this.email inside it ever see my email?

Because the function is shared but the receiver is not. timer.warn() is two operations glued together: look warn up along the prototype chain, then invoke it with this set to timer. One function body, ten thousand different this values, one per call. Split those two operations — const f = timer.warn; f(); — and the lookup still succeeds perfectly. You simply supplied no receiver on the second half.

What does super.warn() actually compile to?

Roughly Object.getPrototypeOf(LoudTimer.prototype).warn.call(this). Two halves matter. The lookup starts at the prototype of the object where the method was defined — its [[HomeObject]], captured once when the class body evaluated, not re-derived from this. The call then forces this back to the current instance, so the parent's code still operates on your object. That split is why super survives deep inheritance, and why copying a method out of one class onto some other object quietly breaks it: the home object came along for the ride and it still points at the old chain.

So should I stop using arrow class fields?

No — use them exactly where the function genuinely gets torn off: a handler you pass by reference, a callback handed to a library, anything that has to survive destructuring. Use a normal method everywhere else. Rule of thumb: if the only call site is this.thing(), it belongs on the prototype. And the real cost is not the memory — it is that a field is not on the prototype, so a subclass cannot super.warn() it and a test spy cannot patch it once for every instance.

▶ #private vs private — where enforcement actually happens

TypeScript's private is erased at compile time — it's invisible at runtime. The ECMAScript # prefix uses a WeakMap enforced by the JS engine, which means it survives a cast to any.

1. The big one: private is a compile-time lie; #private is real

TS private — erased

private/protected/public are TypeScript-only. They're checked by the compiler and then completely erased — at runtime the field is an ordinary, fully-readable property.

class Session {
  private token = "s3cr3t";
}
const s = new Session();
s.token;            // ❌ compile error
(s as any).token;   // ✅ "s3cr3t" at runtime 😱
JSON.stringify(s); // {"token":"s3cr3t"} — it leaks

JS #private — enforced

#name is a real JavaScript private field. It's invisible outside the class at runtime too — not enumerable, not in JSON.stringify, and accessing it from outside is a hard SyntaxError.

class Session {
  #token = "s3cr3t";
}
const s = new Session();
s.#token;           // ❌ SyntaxError (even in plain JS)
(s as any).#token; // can't — # isn't dynamic
JSON.stringify(s); // {} — truly hidden ✅

3. Both keywords also make the class nominal

TypeScript is normally structural — same shape ⇒ interchangeable. But a class with a private or # member becomes effectively nominal: only instances of that exact declaration are assignable, because the private member is unique to it.

class Apple { private seeds = 5; }
class Pear  { private seeds = 5; }   // identical shape

let a: Apple = new Pear();    // ❌ private 'seeds' come from different declarations

// #private brands even harder — the brand check is a runtime operator:
class Box {
  #brand!: void;
  static is(x: unknown): x is Box { return #brand in (x as any); }
}

This is the cleanest way to get Java-style "must be exactly this type" identity out of a structural system — see also branded primitives on the Structural-typing page.

4. Parameter properties — the constructor shorthand

What you write

Put an access modifier (or readonly) on a constructor parameter and TS declares the field and assigns it for you. This is everywhere in Angular services (injected deps).

class UserService {
  constructor(
    private http: HttpClient,  // the modifier IS the whole declaration — no separate field line needed anywhere
    readonly base: string,
  ) {}
  load() { return this.http.get(this.base); }  // this.http/this.base already exist as real fields
}

What it desugars to

class UserService {
  private http: HttpClient;
  readonly base: string;
  constructor(http: HttpClient, base: string) {
    this.http = http;   // generated
    this.base = base;   // generated
  }
}

A parameter with no modifier stays an ordinary local param — no field is created. The modifier is the trigger.

5. abstract classes & implements vs extends

abstract — a base you can't new

abstract class Shape {
  abstract area(): number;   // no body — subclass must supply
  describe() { return `area=${this.area()}`; } // can have real methods + state
}
new Shape();              // ❌ cannot instantiate an abstract class
class Circle extends Shape { area() { return 3.14; } }

Unlike an interface (pure shape, erased), an abstract class can carry implementation and state — pick it when subclasses share code, not just a contract.

implements is a check, not a link

implements only verifies the class structurally matches an interface — it copies nothing and adds no runtime relationship. extends actually inherits members.

interface Logger { log(m: string): void; }

class Console2 implements Logger {
  log(m: string) { console.log(m); }   // must provide it yourself
}
// 'implements' gives you NO inherited code — only a compile-time conformance check.

6. this types — surviving subclassing

Polymorphic this return

Returning this (not the class name) keeps fluent chains typed as the actual subclass, so subclass methods stay reachable mid-chain.

class Builder {
  set(k: string): this { return this; }  // returning the TYPE "this" (not "Builder") is what makes it work for any subclass
}
class FormBuilder extends Builder {
  validate(): this { return this; }
}
new FormBuilder().set("a").validate();
// ✅ set() returns FormBuilder, not Builder → .validate() exists

this is T guards

A method can narrow this to a subtype, so a check unlocks the richer API on the same object.

class Node2 {
  isLeaf(): this is Leaf { return "value" in this; }
}
class Leaf extends Node2 { value = 1; }

if (n.isLeaf()) n.value;  // ✅ n narrowed to Leaf

7. Pitfalls

  • 🔐 Never put secrets in a private field. Tokens, keys, PII in a private property are fully readable at runtime and land in JSON.stringify, logs, and devtools. Use #private (or just don't keep them on the object) — directly relevant to CIAM token handling.
  • Lost this in callbacks. onClick={this.handle} or setTimeout(this.tick) drops the binding. Fix with an arrow class field (handle = () => {…}) which captures this at construction.
  • Field init order with useDefineForClassFields. Modern targets define fields with [[Define]] semantics; a field initializer can't see a value a subclass constructor sets later, and class fields run after super(). Watch initialization that depends on a base-class side effect.
  • #private can't be accessed dynamically. No obj[#x], no reflection — that's the point, but it means you can't enumerate or proxy them.
  • implements ≠ inheritance. It won't give you the interface's (nonexistent) implementation — you must write every member. For shared code, extends a base class.

8. One-sentence recap

private is a compile-time-only modifier that's erased (so secrets in it leak at runtime — use #private, a genuinely hidden JS field), both make a class effectively nominal; parameter properties declare-and-assign a field from a constructor arg; abstract classes carry code+state you can't new while implements is a pure structural check with no inheritance; and this return types + this is T guards keep classes type-safe across subclassing.
