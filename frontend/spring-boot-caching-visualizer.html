Caching

Avoid repeating expensive work — database queries, HTTP calls, heavy computations — by storing the result the first time and returning it instantly on subsequent calls.

What is caching — and what are the risks of doing it wrong?

Caching is storing the result of an expensive operation (a DB query, an HTTP call, a computation) so that subsequent requests for the same result can be served instantly from memory instead of repeating the work. A user lookup that takes 5ms from the DB takes 0.01ms from an in-memory cache. But caching introduces a new problem: stale data. The cached value represents what was true when it was stored. If the underlying data changes (user's role is updated) and the cache isn't updated, callers get the old value. Good caching answers three questions: (1) What should I cache? (read-heavy, rarely changing). (2) How long should I keep it (TTL)? (3) When must I evict it (invalidation — when the underlying data changes)? Cache everything without a plan and you'll serve stale user permissions to callers who should see updated data.

Spring caching annotations

@Cacheable("name") — check cache before running, store result on miss. @CachePut("name") — always run AND update the cache (use on update methods). @CacheEvict("name") — delete cache entry (use on delete/modify methods). @Caching — combine multiple cache annotations on one method. Enable with @EnableCaching on your config class. Works with any CacheManager: in-memory, Redis, Caffeine.

Cache backends

ConcurrentHashMap (default): in-memory, per-JVM instance. Fine for single-instance dev; in K8s with 3 pods, each pod has its own cache — updates on pod 1 aren't visible on pod 2. Redis: shared across all pods, persistent, TTL support, eviction policies. Production default for horizontal scaling. Caffeine: in-memory with eviction policies (size-based, time-based) — better than ConcurrentHashMap for single-instance use.

What to cache vs. what not to

Cache: JWKS keys (fetched per token validation, changes rarely), user role lookups (frequent, changes rarely), reference data (country list, role definitions). Don't cache: individual user profile (changes frequently, staleness risk), sensitive PII (audit trail broken if served from cache), anything that must be real-time (account balance, session status). Staleness window must be acceptable for the data: 10 minutes for roles? OK. 10 minutes for "is user locked out?" — dangerous.

In CIAM: Redis cache in all pods: @Cacheable(value="user-roles", key="#userId"). When an admin updates a user's roles: @CacheEvict(value="user-roles", key="#userId") — all pods will now fetch fresh roles from DB on next request. JWKS cache: @Cacheable(value="jwks", key="'global'") with 10-minute TTL — if Ping rotates its signing keys, the cache auto-expires within 10 minutes and the new keys are fetched. Don't cache the access token validation result — you'd cache "user is authorized" even after they're deprovisioned.

1 — Why Cache? The Latency Problem

Typical latencies for fetching the same product by ID — with and without cache:

Cache MISS (first call — must query database)
Network + DB query + JPA deserialization ≈ 8–40ms
Cache HIT (subsequent calls — return from memory)
≈ 0.1ms
Without caching — every call hits the database
GET /api/products/42 × 1000 times
→ 1000 SQL SELECT queries
→ 1000 × 20ms = 20 seconds of DB time
→ DB connection pool exhausted under load
With @Cacheable — DB called once per key
GET /api/products/42 × 1000 times
→ 1 SQL SELECT (first call)
→ 999 cache hits ≈ 0.1ms each
→ DB load reduced by ~99%

3 — Cache Keys & Conditions

// Default key = all method parameters combined // Override with SpEL expressions via 'key' attribute @Cacheable(value = "products", key = "#id") public Product findById(Long id) { return repo.findById(id).orElseThrow(); } // Compound key — cache per user AND status combination @Cacheable(value = "orders", key = "#userId + '_' + #status") public List<Order> findOrders(Long userId, String status) { ... } // condition — only cache if result is non-null AND price > 0 @Cacheable(value = "products", key = "#id", condition = "#id != null", unless = "#result == null or #result.price <= 0") public Product findById(Long id) { ... } // 'condition' evaluated BEFORE the call (on args) // 'unless' evaluated AFTER the call (on #result) — don't cache null/empty results // @Caching — combine multiple annotations on one method @Caching(evict = { @CacheEvict(value = "products", key = "#product.id"), @CacheEvict(value = "productSummaries", allEntries = true) }) public Product update(Product product) { return repo.save(product); }

5 — Setup: Enabling Caching in Spring Boot

Step 1 — Add @EnableCaching
@SpringBootApplication @EnableCaching // activates cache proxy public class App { public static void main(...) }
Step 2 — Default: ConcurrentHashMap (dev only)
// No config needed — Spring uses a simple // ConcurrentHashMap-backed cache. // Items NEVER expire. Fine for demos, // NOT for production — use Caffeine or Redis.

6 — Production Cache: Caffeine (In-Process)

Caffeine is a high-performance in-memory cache for single-node deployments. Add spring-boot-starter-cache + caffeine dependency:

# pom.xml <dependency> <groupId>org.springframework.boot</groupId> <artifactId>spring-boot-starter-cache</artifactId> </dependency> <dependency> <groupId>com.github.ben-manes.caffeine</groupId> <artifactId>caffeine</artifactId> </dependency>
# application.yml — per-cache configuration spring: cache: type: caffeine caffeine: spec: maximumSize=500,expireAfterWrite=10m cache-names: - products - users
// Or configure programmatically for per-cache settings @Configuration public class CacheConfig { @Bean public CacheManager cacheManager() { CaffeineCacheManager manager = new CaffeineCacheManager(); manager.registerCustomCache("products", Caffeine.newBuilder() .maximumSize(500) .expireAfterWrite(Duration.ofMinutes(10)) .recordStats() // enables hit/miss metrics .build()); manager.registerCustomCache("users", Caffeine.newBuilder() .maximumSize(1000) .expireAfterAccess(Duration.ofMinutes(30)) .build()); return manager; } }

7 — Distributed Cache: Redis (Multi-Node)

Use Redis when you have multiple app instances (containers, pods) that need to share the same cache. Add spring-boot-starter-data-redis:

# application.yml spring: data: redis: host: localhost port: 6379 cache: type: redis redis: time-to-live: 10m cache-null-values: false # don't cache null results
// Per-cache TTL via RedisCacheManagerBuilderCustomizer @Bean public RedisCacheManagerBuilderCustomizer redisCacheCustomizer() { return builder -> builder .withCacheConfiguration("products", RedisCacheConfiguration.defaultCacheConfig() .entryTtl(Duration.ofMinutes(10)) .disableCachingNullValues()) .withCacheConfiguration("sessions", RedisCacheConfiguration.defaultCacheConfig() .entryTtl(Duration.ofHours(1))); } // Objects stored in Redis MUST be serializable // Use Jackson serialization (stores as JSON — human-readable in Redis CLI): @Bean public RedisSerializer<Object> redisValueSerializer(ObjectMapper mapper) { return new GenericJackson2JsonRedisSerializer(mapper); }

8 — Gotchas That Will Bite You

GotchaWhat happensFix
Self-invocationCalling @Cacheable from the same class bypasses the proxy — cache never populatedSame fix as @Transactional: extract to a separate Spring bean
Caching null results@Cacheable caches null by default — next call returns null even if data appearedunless="#result == null" or spring.cache.redis.cache-null-values=false
Mutable return valueMultiple callers share the same cached object reference — one mutates it, all see the changeReturn defensive copies or use immutable DTOs / records
Cache stampedeMany concurrent requests all miss at the same time → all hit the DB simultaneouslyUse Caffeine's refreshAfterWrite or a lock (SynchronizedCacheDecorator)
Not serializable for RedisNotSerializableException at runtime for complex objectsAdd implements Serializable, or use Jackson JSON serializer
@CacheEvict on wrong tierEvicting by key but forgot the key includes method args — wrong entry stays cachedLog cache keys in dev; use allEntries=true when uncertain
