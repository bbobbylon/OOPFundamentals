JVM Memory — Heap, Stack & GC

Primitives and object references live on the stack. The actual objects live on the heap. The garbage collector reclaims unreachable heap objects in generations.

🧠 What is the JVM heap vs stack — and how does garbage collection know what to free?

The JVM manages two regions. The stack is per-thread: each method call pushes a frame holding locals and references, popped when the method returns. The heap is shared: every new allocates there, and a stack variable holds a reference to the heap object. When nothing references a heap object it becomes eligible for garbage collection — you never call free(). The GC is generational (young collected often, old rarely), and you "leak" in Java by holding references longer than needed.

  • Stack = per-thread locals/references; heap = shared objects.
  • GC frees the unreachable — no manual free(); generational young/old.
  • You can still leak — static collections, underegistered listeners, ThreadLocals in pools.
  • Pick the GC for the job — G1 (default), ZGC for sub-ms pauses.

Stack vs heap in code

void method() { int x = 5; // x is on the stack (primitive value) String name = "Bobby"; // name reference on stack, "Bobby" object on heap User user = new User(); // user reference on stack, User object on heap } // method returns: x, name, user references popped from stack // but the User object stays on heap until GC (if no other references). Primitives (int, long, boolean, double): value stored directly in stack frame. Objects: reference (pointer address) stored in stack, actual object in heap.

GC algorithms

G1GC (default Java 9+): balanced throughput and latency, good for heap >4GB. Heap divided into equal-sized regions — collects the most garbage first (Garbage First). ZGC (Java 15+, production): pause times <1ms regardless of heap size — ideal for low-latency systems. Shenandoah: similar to ZGC. Minor GC: young generation, runs frequently, fast (~ms). Major/Full GC: old generation, runs rarely, can pause for seconds (avoid in prod). -Xms512m -Xmx2g: initial and max heap. -XX:+UseZGC: switch to ZGC.

Memory leaks in Java

Java has GC but you can still "leak" — by keeping references alive longer than needed. Common leaks: (1) Static collections that grow: static List cache = new ArrayList() — grows forever, never GC'd. (2) Event listeners not deregistered — inner class holds outer class reference. (3) Thread-local leaks: ThreadLocal.set(largeObject) in a thread pool thread without remove() — the object lives for the thread's lifetime. (4) Hibernate N+1: 1000 lazy-loaded queries fill heap. Detect: /actuator/metrics/jvm.memory.used, heap dump via jmap -dump:file=heap.hprof <pid>, analyze with VisualVM.

Spring Boot / CIAM: 200 Tomcat threads × a ~512KB stack each ≈ 100MB of stack before heap, so cap server.tomcat.threads.max on small instances. SecurityContextHolder's ThreadLocal is cleared per request by SecurityContextPersistenceFilter; virtual threads change stack management (small, resizable, millions possible). Monitor /actuator/metrics/jvm.memory.used?tag=area:heap and alert above 80% of max for 5 minutes.

Generational GC — why it works

The weak generational hypothesis: most objects die young. Loop variables, intermediate results, request-scoped beans — they live for microseconds. So the JVM splits the heap into:

  • Young Gen (Eden + Survivor spaces) — where new allocations land. GC here is fast because most objects are already dead.
  • Old Gen — objects that survived a few young GCs get "promoted" here. GC is rare but expensive (stop-the-world).
  • Metaspace — class metadata, static fields, interned strings. Outside the regular heap. Native memory.

Minor GC = collect Young only — fast, frequent. Major / Full GC = collect Old + sometimes everything — slow, rare.

The garbage collectors you can choose

G1 (default since Java 9)

Splits heap into ~2000 regions, prioritizes those with most garbage. Predictable pause times. Default for most apps.

-XX:+UseG1GC

ZGC

Pause times <10ms even on multi-TB heaps. Concurrent — does most work alongside your app. Use for low-latency services.

-XX:+UseZGC

Shenandoah

Similar goals to ZGC, different implementation. Red Hat's. Concurrent compaction.

-XX:+UseShenandoahGC

Parallel GC

Throughput-focused — pause longer, do more work per pause. Good for batch jobs that don't care about latency.

-XX:+UseParallelGC

Serial GC

Single-threaded. Tiny apps, embedded, or containers with one core.

-XX:+UseSerialGC

Epsilon (no-op GC)

Allocates but never collects. For load tests, ultra-short-lived programs, JVM hacking. App crashes when heap fills.

-XX:+UseEpsilonGC

Memory errors you'll meet

💥 OutOfMemoryError: Java heap space

The heap is genuinely full. Real leak (objects referenced forever), too-small -Xmx, or just need more memory.

Fix: heap dump + analyze with VisualVM / Eclipse MAT.

💥 OutOfMemoryError: GC overhead limit exceeded

JVM spent >98% of recent time in GC and reclaimed <2%. App is thrashing — you're about to OOM anyway.

💥 OutOfMemoryError: Metaspace

Loading too many classes (dynamic class generation gone wild — Spring + lots of proxies). Bump -XX:MaxMetaspaceSize.

💥 StackOverflowError

Infinite recursion (or just very deep). Each call pushes a stack frame; stack is finite.

Fix: add a base case, or convert to iteration.

Reference types (advanced)

Java has four kinds of references that change how GC treats the object: 

// Strong — the normal kind. Object lives as long as some strong ref points to it.
String s = new String("hi");

// Soft — GC keeps if it can; collects only when about to OOM. Use for caches.
SoftReference<LargeImage> cached = new SoftReference<>(image);

// Weak — GC collects on next pass even if memory is fine. Use for canonicalizing maps.
WeakReference<User> ref = new WeakReference<>(user);

// Phantom — never returns the object; only signals "it has been collected".
// Used for resource cleanup beyond what finalizers can do.

WeakHashMap uses weak keys — entries vanish automatically when the key is GC'd. Useful for caches keyed on objects you don't fully control the lifetime of.
