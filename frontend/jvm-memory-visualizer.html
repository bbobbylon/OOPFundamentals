JVM Memory — Heap, Stack & GC

Primitives and object references live on the stack. The actual objects live on the heap. The garbage collector reclaims unreachable heap objects in generations.

🧠 What is the JVM heap vs stack — and how does garbage collection know what to free?

The JVM manages two regions. The stack is per-thread: each method call pushes a frame holding locals and references, popped when the method returns. The heap is shared: every new allocates there, and a stack variable holds a reference to the heap object. When nothing references a heap object it becomes eligible for garbage collection — you never call free(). The GC is generational (young collected often, old rarely), and you "leak" in Java by holding references longer than needed.

  • Stack = per-thread locals/references; heap = shared objects.
  • GC frees the unreachable — no manual free(); generational young/old.
  • You can still leak — static collections, underegistered listeners, ThreadLocals in pools.
  • Pick the GC for the job — G1 (default), ZGC for sub-ms pauses.

Stack vs heap in code

void method() { int x = 5; // x is on the stack (primitive value) String name = "Bobby"; // name reference on stack, "Bobby" object on heap User user = new User(); // user reference on stack, User object on heap } // method returns: x, name, user references popped from stack // but the User object stays on heap until GC (if no other references). Primitives (int, long, boolean, double): value stored directly in stack frame. Objects: reference (pointer address) stored in stack, actual object in heap.

GC algorithms

G1GC (default Java 9+): balanced throughput and latency, good for heap >4GB. Heap divided into equal-sized regions — collects the most garbage first (Garbage First). ZGC (Java 15+, production): pause times <1ms regardless of heap size — ideal for low-latency systems. Shenandoah: similar to ZGC. Minor GC: young generation, runs frequently, fast (~ms). Major/Full GC: old generation, runs rarely, can pause for seconds (avoid in prod). -Xms512m -Xmx2g: initial and max heap. -XX:+UseZGC: switch to ZGC.

Memory leaks in Java

Java has GC but you can still "leak" — by keeping references alive longer than needed. Common leaks: (1) Static collections that grow: static List cache = new ArrayList() — grows forever, never GC'd. (2) Event listeners not deregistered — inner class holds outer class reference. (3) Thread-local leaks: ThreadLocal.set(largeObject) in a thread pool thread without remove() — the object lives for the thread's lifetime. (4) Hibernate N+1: 1000 lazy-loaded queries fill heap. Detect: /actuator/metrics/jvm.memory.used, heap dump via jmap -dump:file=heap.hprof <pid>, analyze with VisualVM.

Spring Boot / CIAM: 200 Tomcat threads × a ~512KB stack each ≈ 100MB of stack before heap, so cap server.tomcat.threads.max on small instances. SecurityContextHolder's ThreadLocal is cleared per request by SecurityContextPersistenceFilter; virtual threads change stack management (small, resizable, millions possible). Monitor /actuator/metrics/jvm.memory.used?tag=area:heap and alert above 80% of max for 5 minutes.

Generational GC — why it works

or, exit code 137 — the out-of-memory that produces no OutOfMemoryError

The problem

The OOM panels above list four ways the JVM tells you it ran out of memory. This is the fifth way, and the JVM does not get to tell you anything.

-Xmx bounds the heap. The container limit bounds the process.

The pod has a 1 GB memory limit, so you set -Xmx1g and reason that the JVM now cannot exceed it. Then the pod dies with exit code 137 — 128 plus signal 9, the kernel's OOM killer — and there is no stack trace, no OutOfMemoryError, and no heap dump, because -XX:+HeapDumpOnOutOfMemoryError only fires on a Java error and no Java error occurred. The process was shot.

The reason is that -Xmx caps one region and the kernel counts all of them. Everything else the JVM allocates is native memory outside the heap, and a modern JDK's own defaults show how much room that is: ReservedCodeCacheSize = 251658240 — 240 MB for JIT-compiled code. MaxMetaspaceSize = 18446744073709551615, which is the JVM's way of writing "no limit at all". Thread stacks at roughly 1 MB each, so a 200-thread pool is another 200 MB that -Xmx never counted. And MaxDirectMemorySize = 0, meaning "default", and the default is equal to the maximum heap — so a Netty or NIO-heavy service can hold about 2 × -Xmx before either limit complains.

Add them up and -Xmx1g in a 1 GB container is not conservative, it is an overcommit. The heap graph looks perfectly healthy right up to the kill, because the heap genuinely was healthy — that is the part that makes this so hard to diagnose. You are staring at the one region that was not the problem, and the region that was has no JVM metric on your dashboard at all.

the heap never filled ✓ GC pause times were fine ✓ no OutOfMemoryError anywhere ✓ native memory is outside -Xmx ⚠ the kernel kills, so there is no Java event ⚠

MaxRAMPercentage defaults to 25 for a reason. The other 75% is not spare — it is the rest of the JVM.

Size the process, then give the heap a share of it
Set -XX:MaxRAMPercentage, not -Xmx, in a container ↓ a percentage is computed from the cgroup limit the JVM actually reads, so it survives a change to the pod's limit; a hard-coded -Xmx silently becomes wrong the moment somebody edits the manifest, and nothing connects the two numbers Leave real headroom — 25% to 50% depending on how much native memory the app uses ↓ a plain REST service with a small thread pool can take 75%; anything doing NIO, Netty, gRPC, compression, image work or a native driver is holding direct buffers, and those come out of the same 100% And when it still gets killed, turn on Native Memory Tracking rather than guessing ↓ -XX:NativeMemoryTracking=summary plus jcmd <pid> VM.native_memory summary breaks the process down by category — heap, class, thread, code, GC, internal — which is the only view that shows the region that is actually growing
Every limit belongs to something, and the thing your limit belongs to is rarely the thing being killed. -Xmx is a promise to the garbage collector about one region; the cgroup limit is a promise the kernel makes about the whole process; and the gap between them is where metaspace, thread stacks, code cache, direct buffers and the JVM's own C++ live. This is the same reasoning error as a connection-pool size that ignores the database's own connection cap, or a rate limit set per instance while the quota is per account: two numbers that look like they measure the same thing, measured at different boundaries.
Exit 137 with no stack trace is not a JVM error — it is the kernel. If you are looking for an OutOfMemoryError, you will not find one, because nothing in Java ran after the signal.
You

The limit is 1 GB and -Xmx is 1 GB. What else is there?

The JVM

Metaspace, the code cache, one stack per thread, direct byte buffers, GC bookkeeping and my own native code. None of that is heap, so none of it is inside -Xmx. I will happily use every byte you gave the heap and all of those, because you told me the heap could have a gigabyte.

The kernel

And I do not know what a heap is. I count resident pages for the cgroup. When the total crosses the limit I send SIGKILL, which cannot be caught, handled or logged — that is what makes it a reliable last resort, and why you get 137 and nothing else.

Your dashboard

Worth admitting my part: I graph heap used, GC pauses and allocation rate, because those are the metrics the JVM exposes by default. Native memory is not one of them. My graphs were flat and green, which is true and completely beside the point.

The mechanism

Six steps from a reasonable-looking Dockerfile to a restart loop with no error in it.

  1. The pod's limit is set to 1 GB, and JAVA_OPTS is given -Xmx1g to match itlooks careful
  2. Startup: the heap reserves its space, metaspace loads the classes, and the JIT begins filling a code cache with 240 MB reservednone of it counted by -Xmx
  3. Traffic arrives. The thread pool grows to 200, and each thread takes about 1 MB of stack — another 200 MB of native memorystill no heap pressure
  4. The HTTP client allocates direct byte buffers. Their default cap is the max heap, so nothing in the JVM objectsa second gigabyte, permitted
  5. Resident memory crosses 1 GB. The kernel sends SIGKILL, which cannot be caught — no shutdown hook, no dump, no log linethe process ends mid-instruction
  6. The pod restarts. The dashboard shows heap at 40%, GC healthy, and a container that keeps dying for no visible reasongreen graphs, dead service

Step 5 is worth understanding precisely, because it explains every missing artefact at once. SIGKILL is the one signal a process cannot install a handler for — so the JVM's shutdown hooks do not run, the heap dump on OOM does not fire, the final log lines never flush, and even the exit code has to be reconstructed by the supervisor as 128 + 9. Every diagnostic you would normally reach for is implemented as "code that runs when something goes wrong", and here nothing ran at all. That is why the fix has to be preventative — headroom and Native Memory Tracking before the fact — rather than forensic. There will be no evidence to examine afterwards, by design.

what the container limit actually contains ↘

the Java heapthe only ring -Xmx bounds — and the only one on your dashboard

Drawn this way the mistake becomes obvious in a sentence: you set a limit on the innermost ring and assumed it constrained the outermost one. The picture also tells you which lever to pull for each symptom — a rising heap with growing GC time is a Java memory leak and a heap dump will find it; flat heap with rising RSS is native, and only jcmd VM.native_memory will. And it explains why -Xms equal to -Xmx is good advice in a container for a different reason than people usually give: not just to avoid resize pauses, but so the heap's full claim is visible at startup rather than arriving later, on top of everything else that has grown since.

Where you have seen this before

A limit set on the part, enforced on the whole.

A connection pool larger than the database allows

Ten instances with a pool of 50 each is 500 connections against a server configured for 200. Each instance's setting is reasonable and the aggregate is not — same arithmetic error, one boundary out.

per-instance ≠ per-system

A disk quota measured before compression

The application counts the bytes it wrote; the filesystem counts blocks, including the ones a sparse file never used and the ones a snapshot still pins. "Used" is defined by whoever enforces the limit, never by whoever produced the data.

the enforcer defines the unit

A request timeout that does not cover retries

A 2-second timeout with three retries and backoff is a 10-second wait for the caller, and the caller's own timeout was set against the first number. Whenever two limits look like they measure the same thing, find out which one has a kernel — or a customer — behind it.

budget the whole, not the step
The whole page on a napkin: stack is per-thread and holds frames and references; heap is shared and holds objects, split into young and old generations so that most collections only have to touch the short-lived part; the collector you pick trades pause time against throughput. The sentence worth adding: -Xmx bounds the heap, not the process — metaspace, the code cache, ~1 MB per thread stack and direct buffers (whose default cap equals the heap) all live outside it, so in a container set -XX:MaxRAMPercentage and expect exit 137 rather than an OutOfMemoryError when you get it wrong.

The weak generational hypothesis: most objects die young. Loop variables, intermediate results, request-scoped beans — they live for microseconds. So the JVM splits the heap into:

  • Young Gen (Eden + Survivor spaces) — where new allocations land. GC here is fast because most objects are already dead.
  • Old Gen — objects that survived a few young GCs get "promoted" here. GC is rare but expensive (stop-the-world).
  • Metaspace — class metadata, static fields, interned strings. Outside the regular heap. Native memory.

Minor GC = collect Young only — fast, frequent. Major / Full GC = collect Old + sometimes everything — slow, rare.

The garbage collectors you can choose

G1 (default since Java 9)

Splits heap into ~2000 regions, prioritizes those with most garbage. Predictable pause times. Default for most apps.

-XX:+UseG1GC

ZGC

Pause times <10ms even on multi-TB heaps. Concurrent — does most work alongside your app. Use for low-latency services.

-XX:+UseZGC

Shenandoah

Similar goals to ZGC, different implementation. Red Hat's. Concurrent compaction.

-XX:+UseShenandoahGC

Parallel GC

Throughput-focused — pause longer, do more work per pause. Good for batch jobs that don't care about latency.

-XX:+UseParallelGC

Serial GC

Single-threaded. Tiny apps, embedded, or containers with one core.

-XX:+UseSerialGC

Epsilon (no-op GC)

Allocates but never collects. For load tests, ultra-short-lived programs, JVM hacking. App crashes when heap fills.

-XX:+UseEpsilonGC

Memory errors you'll meet

💥 OutOfMemoryError: Java heap space

The heap is genuinely full. Real leak (objects referenced forever), too-small -Xmx, or just need more memory.

Fix: heap dump + analyze with VisualVM / Eclipse MAT.

💥 OutOfMemoryError: GC overhead limit exceeded

JVM spent >98% of recent time in GC and reclaimed <2%. App is thrashing — you're about to OOM anyway.

💥 OutOfMemoryError: Metaspace

Loading too many classes (dynamic class generation gone wild — Spring + lots of proxies). Bump -XX:MaxMetaspaceSize.

💥 StackOverflowError

Infinite recursion (or just very deep). Each call pushes a stack frame; stack is finite.

Fix: add a base case, or convert to iteration.

Reference types (advanced)

Java has four kinds of references that change how GC treats the object: 

// Strong — the normal kind. Object lives as long as some strong ref points to it.
String s = new String("hi");

// Soft — GC keeps if it can; collects only when about to OOM. Use for caches.
SoftReference<LargeImage> cached = new SoftReference<>(image);

// Weak — GC collects on next pass even if memory is fine. Use for canonicalizing maps.
WeakReference<User> ref = new WeakReference<>(user);

// Phantom — never returns the object; only signals "it has been collected".
// Used for resource cleanup beyond what finalizers can do.

WeakHashMap uses weak keys — entries vanish automatically when the key is GC'd. Useful for caches keyed on objects you don't fully control the lifetime of.
