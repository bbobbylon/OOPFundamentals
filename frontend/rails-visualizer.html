Ruby on Rails — Lifecycle, Active Record & MVC

The framework that made Ruby famous: convention over configuration, a Rack middleware stack, a router, MVC controllers, and Active Record — an expressive ORM where the model is the query API. Wildly productive for CRUD-shaped web apps and APIs.

🛤️ What is Rails — and why is it so productive?

Ruby on Rails is a full-stack web framework built on one big idea: convention over configuration. If you follow its naming conventions (a User model maps to a users table, a UsersController serves /users), Rails wires almost everything for you — no XML, no annotations, very little boilerplate. A request enters through Rack (Ruby's web-server interface, ≈ the servlet API), passes through a middleware stack (≈ a filter chain — sessions, cookies, CSRF, logging), reaches the router (config/routes.rb), which dispatches to a controller action. The controller talks to the database through Active Record — an Active Record pattern ORM where the model both represents a row and is the query interface (User.where(active: true), user.save), with first-class associations (has_many :orders). It then renders a view (an ERB/HTML template) or returns JSON for an API. before_action filters run cross-cutting logic like authentication; strong parameters whitelist incoming attributes to prevent mass-assignment attacks; and migrations evolve the schema in versioned Ruby files. The whole stack favors a short, readable happy path — at the cost of "magic" you must learn, and the Active-Record coupling of models to persistence.

  • Lifecycle — Rack → middleware stack → router → controller action → view/JSON.
  • Active Record — the model is the row and the query API; associations are built in.
  • Convention over configuration — naming wires models↔tables↔controllers↔routes.
  • before_action + strong params — auth filters and mass-assignment protection.

Spring Boot comparison

The Rack middleware stack ≈ the Servlet/Security filter chain. routes.rb → controller ≈ @RequestMapping → @RestController; resources :users generates REST routes you would hand-write in Spring. Active Record is the Active-Record pattern (model = persistence), where Spring Data/JPA uses Data Mapper (entity + repository). includes(:orders) ≈ JOIN FETCH — same N+1 trap. before_action ≈ a Spring interceptor / @PreAuthorize; strong params ≈ binding to a DTO. Migrations ≈ Flyway. Convention-over-config replaces most of Spring's explicit wiring.

CIAM with Rails: Rails apps usually authenticate with Devise (sessions) or, for an API behind Ping/Entra, a before_action that verifies the RS256 JWT against the provider's JWKS and sets current_user — Rails' equivalent of a Spring Security filter. Authorization is a gem like Pundit/CanCanCan (policies ≈ @PreAuthorize): a missing token → 401, an allowed-but-forbidden action → 403. Strong parameters stop mass-assignment (a client can't set admin: true by smuggling it in the body). Active Record associations make a consent/role model expressive — current_user.consents.where(granted: true) — and includes avoids N+1 across scopes. The shared-nothing request model means each request re-verifies the token, which suits stateless JWT APIs.

The problem

You call something that sounds like the bulk version of save, and every validation and callback you were counting on simply never runs.

Your before_save email-normalizer never sees the bulk update

Say User has before_save :downcase_email and validates :email, uniqueness: true. A support script needs to reset 200 legacy accounts to a placeholder address before a migration: User.where(status: "legacy").update_all(email: "reset@example.com"). It reads like the natural bulk cousin of calling .save on each record — same model, same column, just faster.

Rails' own documentation is blunt about what update_all actually is: it does not instantiate the models involved, and it does not run any callbacks or validations. It compiles your call into one raw SQL statement and sends it straight to the database. delete_all and insert_all/upsert_all make the identical trade for deletes and creates. There is no User object anywhere in this path for before_save to be a hook on, and no validation runs to notice that setting the same literal email on 200 rows is about to violate the uniqueness rule those rows would enforce one at a time. All 200 rows get the exact same email, silently.

where() scoped the right rows ✓ column name spelled correctly ✓ all 200 rows really did update ✓ before_save and the uniqueness validation never ran ⚠

update_all did exactly what its name says: it updated all of them, in bulk, by skipping every hook that turns save into more than a raw UPDATE.

update_all doesn't skip your callbacks to spite you — it skips them because it never builds an object for them to run on.

I called update_all on 200 legacy users. Why didn't before_save lowercase their emails, and why didn't the uniqueness check stop me from giving them all the same address?
Because update_all never builds a User object for any of the matched rows. It compiles your call into one raw UPDATE statement and sends it straight to the database. before_save is a hook on User#save; update_all doesn't call save, not even once.
But "update_all" sounds like it's just the bulk version of "update."
The name is the trap. Plain update loads each record, runs its validations and callbacks, and saves it — one row at a time. update_all skips all three of those steps on purpose; that's the entire reason it's fast.
So is this a bug in Rails?
No — it's documented, deliberate behavior. Rails' own docs say update_all/delete_all do not instantiate the models involved and do not trigger Active Record callbacks or validations. The speed comes precisely from skipping the object layer.
Does the same trade apply to inserts too, not just updates?
Yes. insert_all and upsert_all make the identical trade on creates — no callbacks, no validations, straight SQL. "Bulk" in Active Record always means "no object layer," across update_all, delete_all, insert_all, and upsert_all alike.
How do I get the speed AND keep my validations/callbacks?
Iterate explicitly: User.where(...).find_each(&:save!) is slower, but every before_save/validates/after_commit fires exactly like it would for one record. Or run the side effect yourself, once, right after the bulk statement — a single reindex call instead of 200 individual ones.
What's the actual tell that a method skips the object layer, before I read the source?
Any Active Record method documented as compiling straight to one SQL statement across many rows — update_all, delete_all, insert_all, upsert_all — skips it. If the method's own docs don't mention loading records into memory, assume no callbacks run.
The one-sentence rule. Active Record's callbacks and validations are code attached to instances of your model class — any method documented as writing straight to the table, without building those instances, has nothing for that code to run on.
update_all is Rails being completely honest about a table, not a model. It just isn't the sentence most people are expecting to hear.
The mechanism

Follow the call from your script down to the database, and watch exactly where the object layer disappears.

  1. You write User.where(status: "legacy").update_all(email: "reset@example.com")call
  2. Rails compiles this into ONE SQL statement: UPDATE users SET email='reset@example.com' WHERE status='legacy'compiled
  3. That statement is sent straight to the database — no User objects are ever instantiated for the matching rowsno objects
  4. Because there is no object, there is nothing for validates to check and nothing for before_save/after_commit to fire fromno hooks
  5. The database reports back rows affected — 200 — which is exactly what update_all returns to your scriptrows_affected
  6. All 200 rows now share the identical email, and not one of them ran the callback or validation your model relies on elsewheresilent gap

Steps 3 and 4 are the whole story. Callbacks and validations are code that lives on instances of your model class — update_all never creates an instance, so there is no object for before_save to be a hook ON and nothing for validates to inspect. It isn't skipping your safeguards; there was never anything for them to attach to in the first place.

Three completely different guarantees — a data-normalizing callback, a uniqueness rule, a search-index sync — all trace back to the exact same root cause. They don't fail independently and they don't fail loudly; they simply never had a model instance to run on, because that's what "bulk" means in Active Record.

1. Active Record is the Active-Record pattern

# the model IS the query interface and the row
user = User.find(42) # SELECT … WHERE id=42 LIMIT 1
user.email = "new@x.com"
user.save # UPDATE … (only changed columns)

User.where(active: true)
    .order(:name)
    .includes(:orders) # eager load (no N+1)
Active Record vs Data Mapper. A Rails model both is a row and is the query API — user.save persists itself, User.where(...) queries. Spring Data/JPA splits these: an entity holds data, a repository persists it. Active Record is terser for CRUD; Data Mapper separates concerns for complex domains. The N+1 trap is identical — use includes (Rails) / JOIN FETCH (JPA) to eager-load.

2. Convention over configuration

# ONE line generates 7 RESTful routes
resources :articles

# GET /articles → ArticlesController#index
# GET /articles/:id → #show
# POST /articles → #create
# PATCH /articles/:id → #update
# DELETE /articles/:id → #destroy (+ new, edit)

Naming is configuration. An Article model maps to the articles table; ArticlesController serves /articles; app/views/articles/show.html.erb is the show template. Follow the conventions and Rails wires the rest — the opposite of Spring's explicit annotations.

3. Migrations evolve the schema
