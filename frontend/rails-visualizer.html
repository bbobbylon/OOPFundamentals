Ruby on Rails — Lifecycle, Active Record & MVC

The framework that made Ruby famous: convention over configuration, a Rack middleware stack, a router, MVC controllers, and Active Record — an expressive ORM where the model is the query API. Wildly productive for CRUD-shaped web apps and APIs.

🛤️ What is Rails — and why is it so productive?

Ruby on Rails is a full-stack web framework built on one big idea: convention over configuration. If you follow its naming conventions (a User model maps to a users table, a UsersController serves /users), Rails wires almost everything for you — no XML, no annotations, very little boilerplate. A request enters through Rack (Ruby's web-server interface, ≈ the servlet API), passes through a middleware stack (≈ a filter chain — sessions, cookies, CSRF, logging), reaches the router (config/routes.rb), which dispatches to a controller action. The controller talks to the database through Active Record — an Active Record pattern ORM where the model both represents a row and is the query interface (User.where(active: true), user.save), with first-class associations (has_many :orders). It then renders a view (an ERB/HTML template) or returns JSON for an API. before_action filters run cross-cutting logic like authentication; strong parameters whitelist incoming attributes to prevent mass-assignment attacks; and migrations evolve the schema in versioned Ruby files. The whole stack favors a short, readable happy path — at the cost of "magic" you must learn, and the Active-Record coupling of models to persistence.

  • Lifecycle — Rack → middleware stack → router → controller action → view/JSON.
  • Active Record — the model is the row and the query API; associations are built in.
  • Convention over configuration — naming wires models↔tables↔controllers↔routes.
  • before_action + strong params — auth filters and mass-assignment protection.

Route → controller → Active Record

# config/routes.rb resources :users # 7 RESTful routes # app/controllers/users_controller.rb class UsersController < ApplicationController before_action :authenticate! def show user = User.includes(:orders).find(params[:id]) render json: user # → 200 JSON end end # app/models/user.rb class User < ApplicationRecord has_many :orders end

Validations & strong params

# model validations → 422 if invalid class User < ApplicationRecord validates :email, presence: true, uniqueness: true end # controller: whitelist params (no mass-assign) def user_params params.require(:user).permit(:email, :name) end User.create!(user_params) # INSERT or raise

Spring Boot comparison

The Rack middleware stack ≈ the Servlet/Security filter chain. routes.rb → controller ≈ @RequestMapping → @RestController; resources :users generates REST routes you would hand-write in Spring. Active Record is the Active-Record pattern (model = persistence), where Spring Data/JPA uses Data Mapper (entity + repository). includes(:orders) ≈ JOIN FETCH — same N+1 trap. before_action ≈ a Spring interceptor / @PreAuthorize; strong params ≈ binding to a DTO. Migrations ≈ Flyway. Convention-over-config replaces most of Spring's explicit wiring.

CIAM with Rails: Rails apps usually authenticate with Devise (sessions) or, for an API behind Ping/Entra, a before_action that verifies the RS256 JWT against the provider's JWKS and sets current_user — Rails' equivalent of a Spring Security filter. Authorization is a gem like Pundit/CanCanCan (policies ≈ @PreAuthorize): a missing token → 401, an allowed-but-forbidden action → 403. Strong parameters stop mass-assignment (a client can't set admin: true by smuggling it in the body). Active Record associations make a consent/role model expressive — current_user.consents.where(granted: true) — and includes avoids N+1 across scopes. The shared-nothing request model means each request re-verifies the token, which suits stateless JWT APIs.

1. Active Record is the Active-Record pattern

# the model IS the query interface and the row
user = User.find(42) # SELECT … WHERE id=42 LIMIT 1
user.email = "new@x.com"
user.save # UPDATE … (only changed columns)

User.where(active: true)
    .order(:name)
    .includes(:orders) # eager load (no N+1)
Active Record vs Data Mapper. A Rails model both is a row and is the query API — user.save persists itself, User.where(...) queries. Spring Data/JPA splits these: an entity holds data, a repository persists it. Active Record is terser for CRUD; Data Mapper separates concerns for complex domains. The N+1 trap is identical — use includes (Rails) / JOIN FETCH (JPA) to eager-load.

2. Convention over configuration

# ONE line generates 7 RESTful routes
resources :articles

# GET /articles → ArticlesController#index
# GET /articles/:id → #show
# POST /articles → #create
# PATCH /articles/:id → #update
# DELETE /articles/:id → #destroy (+ new, edit)

Naming is configuration. An Article model maps to the articles table; ArticlesController serves /articles; app/views/articles/show.html.erb is the show template. Follow the conventions and Rails wires the rest — the opposite of Spring's explicit annotations.

3. Migrations evolve the schema

$ rails g model Article title:string body:text # scaffold a migration

class CreateArticles < ActiveRecord::Migration[7.1]
  def change
    create_table :articles do |t|
      t.string :title
      t.text :body
      t.timestamps
    end
  end
end
$ rails db:migrate # apply it
