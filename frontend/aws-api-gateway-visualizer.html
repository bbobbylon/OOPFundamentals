API Gateway

The front door for a serverless API: it terminates HTTPS, decides who's allowed in before your code ever runs, reshapes the request, and can throttle a caller into a 429 — all without a line of your application code executing.

🚪 What does API Gateway actually sit in front of, and why does that order of operations matter?

API Gateway is a managed front door: it accepts HTTPS requests, and before your backend compute (usually Lambda) ever sees one, it can authenticate the caller, validate and transform the request, enforce a rate limit, and only then invoke your function. There are two API types: a REST API is the older, more feature-rich type — request/response mapping templates, API keys, usage plans, request validation, WAF integration; an HTTP API is newer, cheaper, and lower-latency, with a narrower feature set built for the common case (JWT authorizers, simple proxy integration). The most common backend pattern is Lambda proxy integration: instead of API Gateway parsing and reshaping the request into a custom shape, it hands your Lambda the entire raw HTTP request (headers, query string, body) as one JSON event, and expects a specific JSON shape back (statusCode, headers, body) — simple, but it means your function owns all the parsing. Authentication happens via an authorizer: a Lambda authorizer runs your own code (e.g. validate a JWT, check a claim) and returns an IAM policy document that API Gateway caches and enforces; a built-in JWT authorizer does the same for a standard OIDC/JWT issuer without you writing any code. Either way, a request that fails authorization never reaches your backend compute at all — the deny happens at the gateway.

  • REST API vs HTTP API — REST API: mapping templates, API keys, WAF; HTTP API: cheaper, lower latency, built-in JWT authorizers, narrower feature set.
  • Lambda proxy integration — the whole HTTP request becomes one JSON event; your function returns statusCode + headers + body, not a custom shape.
  • Authorizers gate BEFORE compute — a Lambda or JWT authorizer runs first and returns allow/deny; a denied request never invokes your backend function at all.
  • Throttling is per-account and per-key — usage plans + API keys let you rate-limit individual callers independently of your overall account-level burst/steady-state limits.

The authorizer result is cached

A Lambda authorizer's IAM policy is cached (by default 5 minutes, keyed on the token) — the SAME token won't re-invoke your authorizer function on every request, which matters for both cost and latency.

REST API mapping templates transform, proxy doesn't

Without Lambda proxy integration, a REST API's Velocity Template Language (VTL) mapping template reshapes the request before your function sees it — powerful, but a second place logic can silently diverge from your code.

429 is a gateway decision, not a backend one

When a usage-plan rate limit is exceeded, API Gateway returns 429 itself — your Lambda is never invoked, never billed, and never even aware the request happened.

The CIAM parallel: a Lambda authorizer that validates a Bearer JWT and returns an IAM policy is doing exactly what this codebase's own CustomAuthFilter does inside the Spring Boot security filter chain — parsing and verifying a signed JWT before a request reaches a controller. The difference is where it runs: CustomAuthFilter runs inside the same JVM as the app; a Lambda authorizer runs as a separate, independently-scaled function in front of API Gateway, so an auth failure never even spins up your backend compute.

A few things worth knowing

  • The authorizer's response shape matters — a Lambda authorizer must return a well-formed IAM policy document (`Effect: Allow/Deny` on a specific `Resource` ARN); a malformed response is treated as an authorizer error (500), not a deny.
  • Throttling has two levels — an account-level default (steady-state + burst, region-wide) and an optional per-API-key usage plan on top of it; a usage plan can be stricter than the account default but never looser.
  • Proxy integration pushes parsing into your code — this is simpler to reason about than mapping templates, but it means path parameters, query strings, and headers all need to be parsed inside your Lambda handler rather than being pre-shaped for you.
