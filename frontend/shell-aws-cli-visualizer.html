The AWS CLI

or, the whole AWS console in one command you can put in a pipeline

>_

Every click in the AWS console is an API call. What if you could make those calls yourself — scripted, repeatable, and exactly the same every time?

The idea

The console is a GUI over an API. The CLI is the API, undisguised.

Everything AWS does — create a bucket, launch a server, read a secret — is an HTTPS API call. The web console just builds those calls for you behind buttons. aws, the command-line client, builds the same calls from what you type: it signs each request with your credentials (SigV4), sends it to the service endpoint, and prints the JSON that comes back. Which means anything you can click, you can script — and anything you script, a CI/CD pipeline can run at 3 a.m. without you.

Motivation

Four reasons the CLI beats the console at real work.

01
Pipelines speak CLI

Every ADO / GitHub Actions deploy step that touches AWS is an aws command in a YAML file. There is no "click the console" step in CI.

02
Repeatable, reviewable

A script of ten commands can be code-reviewed, versioned, and re-run identically. Ten console clicks can't — and next month you won't remember which ten.

03
Bulk operations

Delete 400 old snapshots from the console and you'll be clicking all afternoon. One CLI loop does it in seconds.

04
The truth, in JSON

The console summarizes; the CLI returns the raw API response. When you're debugging "why is this 403ing", the raw response is the one that tells you.

Anatomy of an aws command

Program, service, operation, arguments, flags. Tap each piece.

the program

aws is one binary that fronts every AWS service — 300+ of them. It reads your credentials, builds the API request, signs it, and prints the response.

the service

s3 picks which service's API you're calling. Swap it for ec2, lambda, sts, iam, secretsmanager… — the command shape stays the same, which is why learning one service teaches you all of them.

the operation

cp is what to do — here, copy a file to a bucket. Run aws s3 help and every operation the service supports is listed with docs.

the arguments

Source and destination. s3://bucket/key is S3's addressing scheme — like a URL, but for objects in a bucket. Order matters: from → to, same as cp in Bash.

the flags

--profile prod says which identity to sign the request as (profiles live in ~/.aws/credentials). Other regulars: --region, --output table, --query for filtering.

You run aws lambda list-functions --output table. Which part decides which API gets called?

--output only changes how the response is printed (json / table / text). The request is identical with or without it.

Service (lambda) plus operation (list-functions) maps directly onto the Lambda API's ListFunctions call. Everything after that is arguments and presentation.

Credentials decide who is asking, never what is asked. The binary is the same for all 300+ services.

The reference

The dozen commands that cover most days.

Identity & setup
aws configureInteractive setup — writes key, secret, region to ~/.aws.
aws sts get-caller-identity"Who am I?" — the first command to run when anything 403s.
aws configure list-profilesEvery named identity you have. Use one with --profile.
S3 — files & artifacts
aws s3 lsList buckets — or a bucket's contents with s3://name.
aws s3 cp app.zip s3://b/Upload / download. --recursive for whole folders.
aws s3 sync ./dist s3://b/Copy only what changed — the deploy workhorse.
aws s3 presign s3://b/fA time-limited download URL you can hand to anyone.
Seeing clearly
--query "..."JMESPath filter — pull just the fields you want from the JSON.
--output tableHuman-readable grid instead of JSON. text for scripts.
aws <svc> helpEvery operation, every flag, offline. No doc-site tab needed.
--dry-run(EC2 & friends) "Would this be allowed?" without doing it.

A deploy script must re-upload only the files that changed in ./dist. Which command?

cp --recursive copies everything, every time — correct result, wasteful deploy that gets slower as the site grows.

mv would delete your local build after uploading — not what a deploy wants.

sync diffs source against destination (size + timestamp) and transfers only the changes — it's the standard static-site deploy command.

Put it together

Ship a build artifact and hand out a download link — predict each output before you reveal it.

Prove who you are first

Before touching anything, confirm which identity the CLI will sign requests as — the wrong profile here means the rest lands in the wrong account.

$ aws sts get-caller-identity
{
    "UserId":  "AIDAEXAMPLE7SAMPLE",
    "Account": "111122223333",
    "Arn":     "arn:aws:iam::111122223333:user/bobby-dev"
}
Upload the artifact

cp streams the file up and prints a confirmation. The s3:// address is bucket, then key (the object's name).

$ aws s3 cp build/app-1.4.2.zip s3://devhub-artifacts/releases/
upload: build/app-1.4.2.zip to s3://devhub-artifacts/releases/app-1.4.2.zip
Verify it landed

ls on the prefix. --human-readable turns 5872640 into something your eyes can parse.

$ aws s3 ls s3://devhub-artifacts/releases/ --human-readable
2026-09-01 09:14:22    5.6 MiB app-1.4.2.zip
Hand out a link that expires

The bucket stays private. presign mints a URL carrying a signature that's only valid for --expires-in seconds — after an hour, it's a 403.

$ aws s3 presign s3://devhub-artifacts/releases/app-1.4.2.zip --expires-in 3600
https://devhub-artifacts.s3.amazonaws.com/releases/app-1.4.2.zip?X-Amz-Algorithm=AWS4-HMAC-SHA256&X-Amz-Expires=3600&X-Amz-Signature=9f2c…
In your CIAM job: the pipeline steps that push your Spring Boot image and Angular bundle to AWS are exactly these commands in ADO YAML. aws sts get-caller-identity is the first move whenever a pipeline 403s (nine times out of ten it's signing as the wrong role), and aws secretsmanager get-secret-value --secret-id prod/oauth/client-secret --query SecretString --output text is how a deploy fetches the OAuth client secret without it ever living in the repo.
There are no dumb questions

Where do my keys actually live after aws configure?

Two plain-text files: ~/.aws/credentials (the keys, per profile) and ~/.aws/config (region and output defaults). That's also why you never run aws configure on a shared box — anyone who can read your home directory is you, as far as AWS can tell. CI pipelines skip the files entirely and inject credentials as environment variables or, better, assume a role.

Is aws s3 different from aws s3api?

Same service, two dialects. s3 gives friendly file-manager verbs (cp, sync, ls) with niceties like recursion and progress. s3api is the raw API, one call per command (put-object, list-objects-v2) — you reach for it when you need an exact API feature the friendly layer doesn't expose, like object versions or ACL details.

Why did my command work in the console region but return nothing in the CLI?

Region mismatch — the #1 beginner trap. The console remembers the region you picked in its top-right dropdown; the CLI uses whatever ~/.aws/config says (or --region). An EC2 instance in us-west-2 is invisible to aws ec2 describe-instances pointed at us-east-1 — no error, just an empty list.
