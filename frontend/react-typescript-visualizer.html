TypeScript with React

Typing the React surface: props (incl. children and extending native elements), hooks (useState/useRef/useReducer/context), event handlers, and generic components — plus the inference that lets you write fewer annotations than you'd think.

What does TypeScript add to React — and where does it actually catch bugs?

TypeScript makes React code dramatically safer and more maintainable. Without TypeScript, React props are plain JavaScript objects — you discover missing or wrong props at runtime (bugs in production). With TypeScript: the compiler catches wrong props at write time. The React-specific typing surface covers six areas. Props interfaces: every component has a typed props interface. TypeScript catches: missing required props, wrong prop types, extra props that don't exist. children: typed as React.ReactNode (anything renderable) or React.ReactElement (a single element). Event handlers: React.MouseEvent<HTMLButtonElement>, React.ChangeEvent<HTMLInputElement> — typed with the specific element type so e.target.value is always string. Hooks: useState<UserDto | null>(null) — the generic type constrains what you can pass to the setter. useRef<HTMLInputElement>(null) — types ref.current as the input element. useReducer with discriminated union actions: TypeScript guarantees the switch exhaustively handles every action type. Context: React.createContext<AuthContextType | null>(null) — consumers get the full type from useContext without any casting. Generic components: a Select<T> component that takes options: T[] and onChange: (value: T) => void — the T flows through without the component needing to know what T is. This mirrors TypeScript generics in Spring Boot DTOs — same concept, different layer.

// useState with type argument const [user, setUser] = useState<UserDto | null>(null); // TypeScript infers: setUser: (value: UserDto | null) => void // setUser(42) ← compile error // setUser(null) ← ok // useRef with DOM element type const inputRef = useRef<HTMLInputElement>(null); inputRef.current?.focus(); // optional chain: current can be null // Event handlers — type the event AND element const handleChange = (e: React.ChangeEvent<HTMLInputElement>) => { setQuery(e.target.value); // e.target.value: string ✓ }; const handleSubmit = (e: React.FormEvent<HTMLFormElement>) => { e.preventDefault(); submitForm(); }; const handleClick = (e: React.MouseEvent<HTMLButtonElement>) => { e.currentTarget.disabled = true; };

In a CIAM React app: Share TypeScript types between your Spring Boot API and React frontend. Spring Boot: record CreateUserRequest(String firstName, String lastName, @Email String email, @NotNull IdpType idpType) {}. React: interface CreateUserDto { firstName: string; lastName: string; email: string; idpType: 'PING' | 'ENTRA'; } — the same shape. Tools like openapi-typescript can auto-generate these types from your Spring Boot OpenAPI spec (springdoc-openapi), keeping them in sync automatically. TypeScript also catches runtime-prone mistakes: user?.roles.includes('CIAM_ADMIN') — without TypeScript you'd write user.roles.includes(...) and crash when user is null. Context typing: const auth = useContext(AuthCtx); — if AuthCtx is typed as AuthContextType | null, TypeScript forces you to null-check before accessing auth.user. The same discipline as Spring's @NonNull or Kotlin's null safety.

3. The React.FC debate

Prefer a plain function with a typed props parameter over React.FC. React.FC historically forced an implicit children prop (even for components that take none), complicates generics, and adds little. The community-recommended style is function Comp(props: Props) {} or const Comp = (props: Props) => {} and declare children explicitly when you want it.
