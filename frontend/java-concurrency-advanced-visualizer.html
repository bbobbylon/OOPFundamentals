🧵 What is an ExecutorService — and why is CompletableFuture the modern way to compose async?

A new Thread() per task is wasteful (~1ms to create, ~1MB each). ExecutorService manages a pool of reusable threads — Executors.newFixedThreadPool(10) — and you submit() tasks that return a Future whose get() blocks. CompletableFuture (Java 8) is the modern, non-blocking, composable replacement: supplyAsync(...).thenApply(...).thenAccept(...) chains stages, thenCombine merges two, allOf(...).join() waits for many, and exceptionally handles errors — Java's Promise chain, and what Spring's @Async uses underneath.

  • Pool threads, don't create per task — an ExecutorService reuses a fixed/cached pool.
  • Future.get() blocks; CompletableFuture composes — chain stages without blocking.
  • Fan out, then join — thenCombine/allOf make total time ≈ the slowest call.
  • SecurityContext is ThreadLocal — it doesn't follow work to a pool thread; propagate it.

Thread pool types

newFixedThreadPool(n): exactly n threads. Submit more tasks than n → they queue. Good for CPU-bound tasks: n = number of CPU cores. newCachedThreadPool(): creates threads as needed, reuses idle ones after 60s. Good for many short-lived tasks. newSingleThreadExecutor(): one thread, tasks execute in order. Good for serialised background processing. newScheduledThreadPool(n): schedule with delay or fixed rate. Spring Boot uses: a task executor bean for @Async — configure with ThreadPoolTaskExecutor (not the bare-bones Executors factory).

CompletableFuture patterns

Load two things in parallel: CompletableFuture<User> u = supplyAsync(() -> repo.findUser(id)); CompletableFuture<List<Role>> r = supplyAsync(() -> repo.findRoles(id)); u.thenCombine(r, (user, roles) -> new UserWithRoles(user, roles)).join(). Timeout: cf.orTimeout(5, SECONDS). Complete with value: cf.completeOnTimeout(default, 5, SECONDS). Compose: thenCompose(fn) when fn returns a CompletableFuture (like flatMap for futures). Error: handle((result, ex) -> ex != null ? fallback : result).

SecurityContext in async threads

Spring Security stores the authenticated user in SecurityContextHolder — a ThreadLocal. When @Async runs on a different thread, the ThreadLocal is empty. Fix: capture before submitting: SecurityContext ctx = SecurityContextHolder.getContext(); CompletableFuture.runAsync(() -> { SecurityContextHolder.setContext(ctx); doAsyncWork(); SecurityContextHolder.clearContext(); }). Or configure Spring's DelegatingSecurityContextExecutorService to propagate automatically. With virtual threads (Java 21): each virtual thread gets its own ThreadLocal copy — less of an issue.

CIAM / Spring Boot: Build a profile page by fetching user, roles, and audit in parallel — three supplyAsync(...) futures joined with allOf(...).join() so total time is the slowest call, not the sum. With @Async CompletableFuture<Void> sendWelcomeEmail(user) the call is fire-and-forget: the pool queues it and the caller returns immediately.

ExecutorService — managed thread pools

// Fixed pool — N threads, excess tasks queue ExecutorService pool = Executors.newFixedThreadPool(4); // Submit Runnable (fire and forget) pool.execute(() -> doWork()); // Submit Callable (returns Future) Future<Integer> future = pool.submit(() -> computeAnswer()); // Get result — blocks until done int result = future.get(); // blocking int r2 = future.get(5, TimeUnit.SECONDS); // with timeout // Cancel if not started future.cancel(true); // true = interrupt if running // Shutdown — reject new tasks, wait for running pool.shutdown(); pool.awaitTermination(30, TimeUnit.SECONDS);
// Common pool types // Single thread — guarantees task order ExecutorService single = Executors.newSingleThreadExecutor(); // Cached — creates threads on demand, reuses idle ExecutorService cached = Executors.newCachedThreadPool(); // Scheduled — run after delay or periodically ScheduledExecutorService sched = Executors.newScheduledThreadPool(2); sched.schedule(() -> doIt(), 5, TimeUnit.SECONDS); sched.scheduleAtFixedRate(task, 0, 1, TimeUnit.MINUTES); // Custom pool with full control new ThreadPoolExecutor( 2, // corePoolSize 10, // maximumPoolSize 60L, TimeUnit.SECONDS, // keepAliveTime new ArrayBlockingQueue<>(100) // queue );

invokeAll & invokeAny — batch submission

ExecutorService pool = Executors.newFixedThreadPool(4); List<Callable<Integer>> tasks = List.of( () -> fetchPrice("AAPL"), () -> fetchPrice("GOOG"), () -> fetchPrice("AMZN") ); // invokeAll — waits for ALL to complete List<Future<Integer>> results = pool.invokeAll(tasks); results.stream().map(f -> { try { return f.get(); } catch(...) { ... } }).forEach(System.out::println); // invokeAny — returns first successful result int first = pool.invokeAny(tasks); // Cancels remaining tasks automatically

Combining CompletableFutures

// thenCombine — combine two independent CFs CompletableFuture<User> userCF = getUser(id); CompletableFuture<Account> acctCF = getAccount(id); var combined = userCF.thenCombine(acctCF, (user, acct) -> buildSummary(user, acct)); // thenCompose — chain dependent CFs (flatMap) CompletableFuture<Order> orderCF = getUser(userId) // CF<User> .thenCompose(user -> getOrders(user)) // CF<List<Order>> .thenCompose(orders -> process(orders)); // CF<Order>
// anyOf — first to complete wins CompletableFuture.anyOf( fetchFromPrimary(), fetchFromReplica(), fetchFromCache() ).thenAccept(result -> show(result)); // Error handling cf.handle((result, ex) -> { if (ex != null) { log.error("Failed", ex); return defaultValue; } return result; }); // Custom executor CompletableFuture.supplyAsync( () -> heavyWork(), myThreadPool) // don't use common pool .thenApply(this::process);

Thread-safe Collections — no external synchronization needed

// ConcurrentHashMap — segmented locking, very fast ConcurrentHashMap<String, Integer> map = new ConcurrentHashMap<>(); // Atomic compound operations map.putIfAbsent("key", 0); map.computeIfAbsent("key", k -> loadFromDB(k)); map.merge("count", 1, Integer::sum); // atomic counter // vs synchronized HashMap (much slower) Map<String,Integer> sync = Collections.synchronizedMap(new HashMap<>()); // Every operation locks the entire map
// CopyOnWriteArrayList — optimized for read-heavy CopyOnWriteArrayList<String> list = new CopyOnWriteArrayList<>(); // Writes copy the entire array — expensive! // Reads never block — good for event listeners // BlockingQueue — producer-consumer pattern BlockingQueue<Task> queue = new LinkedBlockingQueue<>(100); // bounded // Producer queue.put(task); // blocks if full queue.offer(task, 5, TimeUnit.SECONDS); // timeout // Consumer Task t = queue.take(); // blocks if empty Task t2 = queue.poll(5, TimeUnit.SECONDS);

Concurrent collection cheat sheet

ConcurrentHashMap
High-concurrency key-value. putIfAbsent, computeIfAbsent. Use for shared caches.
ConcurrentLinkedQueue
Non-blocking FIFO queue. Lock-free. Good for task submission.
LinkedBlockingQueue
Blocking producer-consumer queue. Bounded = backpressure.
CopyOnWriteArrayList
Read-heavy lists. Event listeners, observers. Expensive writes.
ConcurrentSkipListMap
Sorted concurrent map. TreeMap equivalent with thread safety.
PriorityBlockingQueue
Blocking priority queue. Tasks processed by priority.

Atomic Variables — lock-free thread-safe operations

// AtomicInteger / AtomicLong / AtomicBoolean AtomicInteger counter = new AtomicInteger(0); counter.incrementAndGet() // ++i equivalent counter.getAndIncrement() // i++ equivalent counter.addAndGet(5) // add 5, return new value counter.get() // read current counter.set(100) // write // compareAndSet (CAS) — the core primitive boolean success = counter.compareAndSet( 5, // expected current value 10 // new value — only set if current == 5 ); // updateAndGet — apply lambda atomically counter.updateAndGet(x -> x * 2);
// AtomicReference — any object type AtomicReference<User> currentUser = new AtomicReference<>(); currentUser.set(new User("Alice")); User u = currentUser.get(); // Atomic array AtomicIntegerArray arr = new AtomicIntegerArray(10); arr.incrementAndGet(3); // index 3 // LongAdder — better for high contention counters LongAdder hits = new LongAdder(); hits.increment(); // in many threads long total = hits.sum(); // aggregate at end // Faster than AtomicLong under high contention

ReentrantLock, ReadWriteLock & Semaphore

// ReentrantLock — more flexible than synchronized ReentrantLock lock = new ReentrantLock(); lock.lock(); try { criticalSection(); } finally { lock.unlock(); // ALWAYS in finally } // tryLock — non-blocking attempt if (lock.tryLock(100, TimeUnit.MILLISECONDS)) { try { ... } finally { lock.unlock(); } } else { // lock not acquired — fallback } // Condition variables Condition notEmpty = lock.newCondition(); notEmpty.await(); // release lock, wait notEmpty.signal(); // wake one waiter
// ReadWriteLock — many readers OR one writer ReadWriteLock rwLock = new ReentrantReadWriteLock(); // Multiple threads can read simultaneously rwLock.readLock().lock(); try { readData(); } finally { rwLock.readLock().unlock(); } // Only one thread can write (blocks readers too) rwLock.writeLock().lock(); try { writeData(); } finally { rwLock.writeLock().unlock(); } // Semaphore — limit concurrent access Semaphore sem = new Semaphore(5); // 5 permits sem.acquire(); // get a permit (blocks if none) try { accessResource(); } finally { sem.release(); // return permit } // Used for: DB connection pools, rate limiting

Virtual Threads (Java 21 LTS) — millions of lightweight threads

// Platform thread — expensive, ~1MB stack Thread pt = new Thread(() -> doWork()); pt.start(); // OS-managed: ~10K max practical limit // Virtual thread — cheap, JVM-managed Thread vt = Thread.ofVirtual() .start(() -> doWork()); // Scheduled on ForkJoinPool carrier threads // Unmounts during blocking I/O — no OS thread wasted // Create millions try (var executor = Executors.newVirtualThreadPerTaskExecutor()) { for (int i = 0; i < 1_000_000; i++) { executor.submit(() -> doWork()); } } // all complete before here
// Virtual threads shine for I/O-bound work // (REST calls, DB queries, file reads) // Before: need async/reactive to scale Flux.fromIterable(urls) .flatMap(url -> webClient.get(url)) .subscribe(this::process); // With virtual threads: simple blocking code scales! urls.parallelStream() .forEach(url -> { String body = httpClient.get(url); // blocking process(body); }); // JVM unmounts during .get() — another VT runs // Spring Boot 3.2+ auto-uses virtual threads // spring.threads.virtual.enabled=true
Virtual thread gotchas: Don't pool virtual threads (defeat the purpose). Avoid synchronized blocks that hold platform threads during I/O — use ReentrantLock instead. ThreadLocal can cause memory issues at scale — use ScopedValue (JEP 446).
