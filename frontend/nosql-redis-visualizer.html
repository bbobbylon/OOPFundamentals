Redis — In-Memory Key-Value Store, Caching & Pub/Sub

Every page in this track so far has been a relational store — rows, foreign keys, joins, ACID transactions. Redis is the opposite end of the spectrum: an in-memory, single-threaded key-value engine that trades durability and query flexibility for raw speed and a handful of purpose-built data structures. It's not a replacement for Postgres — it's the thing you put in front of Postgres.

⚡ What makes Redis fast, and what does that speed cost you?

Redis keeps its entire dataset in RAM and processes commands on a single thread — no locks, no lock contention, because only one command ever executes at a time. That single fact explains almost everything about Redis: it's why INCR is perfectly atomic with zero extra code, why it's blazingly fast (RAM access, no disk seek, no query planner), and why a single slow command (a giant KEYS * scan) blocks every other client until it finishes. The cost of that speed is durability and structure: RAM is volatile, so Redis persists to disk asynchronously (RDB snapshots or an AOF write-log) rather than synchronously like a relational commit — a crash can lose the last few seconds of writes unless you tune persistence aggressively. And there's no schema, no joins, no foreign keys — just keys mapped to one of a handful of data structures, each with its own purpose-built command set.

  • In-memory + single-threaded — RAM speed, and every command is atomic by construction, with no explicit locking.
  • Five core data structures — string, hash, list, set, and sorted set — each solving a different shape of problem, not a generic document store.
  • TTL is a first-class citizen — any key can expire automatically; this is what makes Redis a natural fit for caches, sessions, and rate limits.
  • Persistence is a trade-off you tune, not a guarantee you get for free — RDB snapshots (fast restarts, can lose minutes) vs. AOF (near-durable, slower).

String

The simplest structure — a value up to 512MB. Used for cached blobs, counters (INCR), and simple flags.

Hash

A field→value map inside one key — like caching a whole object (user:42 → {name, email, plan}) without one key per field.

List

An ordered, linked sequence — LPUSH/RPOP make it a natural queue or a capped "recent activity" feed.

Set

Unordered, unique members — fast membership checks (SISMEMBER) and set algebra (intersect/union) like "users who liked both posts."

Sorted Set

Members ranked by a score — ZADD/ZRANGE power leaderboards and priority queues with O(log N) inserts.

This app's cache-aside pattern

Spring's @Cacheable (see Caching) is cache-aside implemented for you: check the cache, and only call through to the annotated method — hitting the real repository/database — on a miss. This page shows the same pattern one layer lower, with the raw RedisTemplate calls @Cacheable is doing under the hood.

Not a transactional system of record

Redis has no foreign keys and no multi-table ACID transactions the way Postgres does (see Transactions & ACID) — MULTI/EXEC queues commands atomically but doesn't roll back on a mid-transaction application error the way SQL does. Keep the source of truth in the relational database; use Redis to make reading it fast.

CIAM angle

Two of the most common Redis uses in an identity platform are exactly the two demoed below: rate-limiting login attempts (an atomic INCR + EXPIRE counter per user/IP, immune to race conditions because Redis is single-threaded) and session/refresh-token storage with a TTL that mirrors the token's own expiry, so an expired session simply evaporates instead of needing a cleanup job.

"I promised 5000 milliseconds — not forever."

Redis is holding a countdown, Worker A is frozen mid-charge, and Worker B is about to walk in and take what looks like an empty seat.

Worker A

I called SET lock:order-991 token-A NX PX 5000. Nobody else can be touching order 991 right now.

Redis

I gave you that key for 5000 milliseconds, and not one millisecond more. I never promised your code would be done by then.

Worker A

I'm not done. I'm still waiting on the payment gateway to answer — that usually takes 200ms, not 5000.

Redis

"Usually" isn't in my contract. At millisecond 5000 I ran exactly what PX 5000 told me to run: DEL lock:order-991.

Worker B

The key was gone when I looked, so I set it again with token-B. Every rule I know says that makes it mine.

Worker A

Nothing has told me to stop. I'm still holding what I think is the only lock on this order.

Brain Power

Redis kept its word. Worker A kept doing exactly what it was told. Worker B followed the rules to the letter. Three parties, zero mistakes — so who actually caused the double charge?

Redis

Don't look at me. I don't track who's "still working" — I only track keys and milliseconds. That's the entire interface.

Worker A

Don't look at me either. There's no callback that fires when a lock I'm holding gets taken away. I find out the same way you'd notice your parking spot is gone: too late.

Worker B

And I did nothing wrong — SET NX told me the space was free, so I took it. That's the entire point of NX.

You

You're all right, and order 991 got charged twice anyway. The bug was never any one of you — it's that nobody agreed on what "I still hold the lock" means at the one moment it actually mattered.

The one-sentence rule. A lock's TTL only measures elapsed time, never the health of whoever is holding it, so anywhere "only one worker acts" is a hard correctness requirement — money, inventory, a single write — needs a second, independent check made at the moment of the actual effect, not just at the moment the lock was acquired. Give every acquisition a fencing token that only ever increases, and make the protected write itself reject anything lower than the highest token it has already accepted. At work, this is the same reasoning behind re-checking a session at the point of the actual write instead of trusting that a token valid at request-start is still valid 400ms later — in CIAM, an access token that expires mid-request is this exact bug wearing a different hat.

Swap the GC pause for a slow disk write or a dropped network packet and the story replays identically — the specific stall never mattered. What mattered is that nothing re-verified "am I still the lock holder?" at the one moment it counted: right before the charge actually fired.

Your worker locks an order with SET lock:order-991 token-A NX PX 5000, then a GC pause freezes it for 6 seconds mid-charge. What does Redis actually do to that lock while your worker is stalled?

Redis has no "give it more time" behavior built into PX — the value you pass is the exact TTL, full stop. The only way to extend it is a watchdog explicitly renewing the key yourself, like Redisson's lock does.

Right. Redis's countdown is attached to the key, not to any notion of the client's liveness — it has no idea your worker is mid-GC, mid-network-call, or dead. At 5000ms the key is gone, full stop.

Redis doesn't track per-connection heartbeats for key expiry — that's a mental model borrowed from something like a TCP keepalive, and it doesn't apply here. The TTL countdown runs purely off the clock, deaf to whatever the client is doing.

Think of the TTL as a parking meter, not a bouncer at a door. A meter running out doesn't tow your car — it just makes the spot legally available to someone else. Two cars can be "parked" in the same spot at once, and nobody finds out until they both try to leave.

1. Redis vs. a relational database — different jobs, not competitors

AxisRedisPostgreSQL / relational
StorageRAM (optionally persisted to disk async)Disk, with a buffer cache — durable by default on commit
SchemaNone — keys map to one of ~5 data structure typesStrict — tables, columns, types, constraints, foreign keys
QueriesDirect key lookups + structure-specific commands (no joins)Arbitrary SELECT/JOIN/aggregate queries via a query planner
ConsistencySingle-threaded → naturally atomic per command; no cross-key ACID transactionsFull ACID — multi-row, multi-table transactions with rollback
Typical roleCache, session store, rate limiter, real-time leaderboard, pub/sub busSystem of record — the data that must never be silently lost
The rule of thumb: if losing this data on a crash would be a real problem, it belongs in Postgres, not (only) Redis. Redis excels precisely where speed matters more than durability — a cache can always be repopulated from the database it's fronting; the database itself cannot be "repopulated" from anywhere.

2. Cache-aside: check the cache, fall through to the database on a miss

✗ No cache — every read hits the database

public UserProfile getProfile(Long userId) {
  // every single call round-trips to Postgres,
  // even though this profile rarely changes
  return userRepo.findById(userId);
}

✓ Cache-aside with RedisTemplate

public UserProfile getProfile(Long userId) {
  String key = "user:profile:" + userId;  // one unique key per user — never collides across users
  UserProfile cached = (UserProfile) redis.opsForValue().get(key);  // simple GET; cast since it returns Object
  if (cached != null) return cached; // hit — no DB call

  UserProfile fresh = userRepo.findById(userId); // miss
  redis.opsForValue().set(key, fresh, Duration.ofMinutes(15));  // writes it back — the TTL makes the key self-expire, no cleanup job needed
  return fresh;
}
The TTL (Duration.ofMinutes(15)) is doing double duty — it bounds how stale the cached copy can get AND it means there's no cache-invalidation cleanup job to write or forget; a key that's never explicitly deleted still self-removes.

3. Atomic counters: why INCR is race-free and a naive read-then-write isn't

✗ Race condition — read, modify, write as three steps

int attempts = (int) redis.opsForValue().get(key); // read: 4
attempts++;                                          // modify: 5 (in app memory)
redis.opsForValue().set(key, attempts);              // write: 5
// two concurrent login attempts can both read 4, both write 5 —
// one increment is silently lost, rate limit under-counts

✓ Atomic — one command, no window for a race

Long attempts = redis.opsForValue().increment(key); // INCR
if (attempts == 1) redis.expire(key, Duration.ofMinutes(15));
if (attempts > 5) throw new TooManyAttemptsException();
// Redis's single-threaded execution means INCR is indivisible —
// every concurrent caller gets a distinct, correct count
INCR is atomic because Redis never interleaves two commands — there's no gap between "read the value" and "write the incremented value" for another client's command to slip into, because there's only one thread executing commands at all. This is the same structural guarantee this hub's rate limiting page relies on, applied at the storage layer instead of the application layer.

4. One-sentence recap

⚡ Redis trades durability and query flexibility for RAM speed and single-threaded atomicity — use it as a cache-aside layer in front of the real database, an atomic counter for rate limits, a TTL-backed session store, or a pub/sub bus, but never as the only copy of data you can't afford to lose.
