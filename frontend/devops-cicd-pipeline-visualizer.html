CI/CD Pipelines — Build, Test, Deploy

How a code push becomes a running deployment automatically: a pipeline checks out the code, builds it, runs tests, packages an artifact, and deploys it through environments — with gates between stages. Modeled here on GitHub Actions. Once the artifact is deployed, see Deployment Strategies for how traffic actually shifts to it — blue-green, canary, feature flags, or GitOps — and From git push to Production for the full end-to-end capstone.

♾️ What is CI/CD — and why automate the path from commit to production?

Continuous Integration (CI) means every push is automatically built and tested, so integration bugs surface in minutes instead of at a painful end-of-sprint merge. Continuous Delivery/Deployment (CD) extends that: a build that passes is automatically packaged and rolled out to environments — Delivery stops at a manual approval before production, while Deployment goes all the way with no human gate. A pipeline is the ordered set of stages that makes this happen: checkout the commit, build (compile / bundle), test (unit, integration, lint), package an immutable artifact (a jar, a container image), then deploy that exact artifact to staging and on to production. In GitHub Actions the pipeline is a workflow (a YAML file in .github/workflows/) triggered by an event (on: push, pull_request, a tag, a schedule, or manual workflow_dispatch). A workflow has jobs that run on runners (fresh VMs/containers); each job is a series of steps — shell commands or reusable actions (actions/checkout, setup-java…). Jobs run in parallel unless one needs another, and a non-zero exit fails the pipeline so nothing downstream runs — a red test blocks the deploy. Environments add protection: a deploy job can target an environment with required reviewers (a manual gate) and scoped secrets. The guiding principles: build once, deploy the same artifact everywhere, keep pipelines fast, and make every run reproducible from a clean runner.

  • CI — every push is auto-built & tested; broken integrations surface immediately.
  • CD — passing builds auto-deploy; Delivery gates at prod, Deployment does not.
  • Pipeline stages — checkout → build → test → package artifact → deploy (staging → prod).
  • Actions model — workflow → jobs (on runners) → steps; needs orders jobs, a failure halts downstream.

A workflow (YAML)

on: { push: { branches: [main] } } jobs: build: runs-on: ubuntu-latest steps: - uses: actions/checkout@v4 - run: mvn -B verify - uses: actions/upload-artifact@v4 with: { path: target/*.jar }

A gated deploy job

deploy-prod: needs: build environment: name: production # required url: https://app... # reviewers steps: - run: ./deploy.sh $IMAGE

The problem

Two jobs in the same workflow file read like two functions in the same program. They aren't — they're two different machines, and nothing you set on one exists on the other unless you say so on purpose.

Your deploy job shipped an empty version string to production

Your build job computes a version from git describe --tags and saves it with echo "VERSION=1.4.1" >> $GITHUB_ENV. A later step in that same job echoes $VERSION to confirm it worked — and it does, printing 1.4.1 right there in the log. Confident it's wired up, your deploy job declares needs: build and runs ./deploy.sh ${{ env.VERSION }}, assuming that since deploy waits for build, it can also see whatever build set.

It can't. $GITHUB_ENV is documented to persist "for the remainder of the job" — scoped to that one job's steps, because they all run on the same runner VM. The deploy job is a completely separate runner, one that never heard the build job's echo at all. ${{ env.VERSION }} resolves to an empty string. The run: step doesn't fail — the shell just expands ./deploy.sh with no argument, and if deploy.sh quietly falls back to whatever's already checked out (or a "latest" tag) when its argument is blank, the workflow finishes green while shipping the wrong build.

needs: build tells GitHub Actions when to run the deploy job. It says nothing at all about what that job can see.

Hand values across jobs with outputs, never environment variables
Give the value-producing step an id: ↓ e.g. id: ver — this is what lets anything reference steps.ver.outputs.value afterward Declare outputs: on the job itself ↓ outputs: { version: ${{ steps.ver.outputs.value }} } — this is what actually makes the value visible OUTSIDE that job, to anything that lists needs: build Read it downstream as needs.build.outputs.version ↓ this crosses the job boundary the way a plain env var or $GITHUB_ENV never does — GitHub Actions itself records the output as part of the workflow run, not the runner
The one-sentence rule. A GitHub Actions job is a separate machine, not a separate function call — anything that has to survive from one job into the next needs an explicit outputs: / needs.<job>.outputs hand-off (or a real uploaded artifact), never a shell or environment variable, because there is no shared process, filesystem, or environment between two jobs even when one needs the other.
needs: build is a start signal, not a memory share. It's like phoning a coworker in a different building and telling them "go" — they still can't see anything sitting on your desk just because you told them when to start.

The mechanism

Watch the exact same value, 1.4.1, take two different paths out of the build job — one that dies at the runner's edge, one that survives it.

  1. Build job, step id: ver: echo "value=1.4.1" >> $GITHUB_OUTPUTstep output
  2. Build job, a later step in the SAME job: echo "VERSION=1.4.1" >> $GITHUB_ENV — just to comparejob env
  3. Build job finishes; its runner VM is torn down — disk, process tree, every env var it ever set, all gonerunner destroyed
  4. Deploy job starts once needs: build is satisfied — on a brand-new runner that has never heard of $VERSIONfresh runner
  5. ${{ env.VERSION }} resolves to empty in deploy — but ${{ needs.build.outputs.version }} resolves to 1.4.1the fork
  6. Deploy runs ./deploy.sh 1.4.1 using the output reference and ships the right build; the env-var reference, left in, would have shipped nothingcorrect hand-off

Step 5 is the fork in the road, and the reason it goes two different ways is where the value is stored. A job output is recorded by GitHub Actions itself, as part of the workflow run's own state — it survives the runner being destroyed because it was never IN the runner to begin with. An environment variable lives only inside a runner's process tree, and when that VM is torn down at the end of the job, so is everything $GITHUB_ENV ever wrote.

Read the diagram as a warning too: the third option, a silent fallback, is exactly how a blank $VERSION turns into "deployed something, just not the thing you meant" instead of a loud, obvious failure.

Your build job runs echo "VERSION=1.4.1" >> $GITHUB_ENV, and a later step in that same job echoes $VERSION successfully. Your deploy job (needs: build) then runs ./deploy.sh ${{ env.VERSION }}. What actually gets deployed?

That's the intuitive assumption, but needs: only controls ordering and success/failure gating between jobs — it creates no shared environment. Each job is a separate runner with its own process tree, and a $GITHUB_ENV write never leaves the process tree it was made in.

Right. $GITHUB_ENV is scoped to "the rest of the current job" by design — it survives across steps because they share one runner, but a second job boots a brand-new runner that never saw that write. The fix is a declared job output, read as needs.build.outputs.<name>, which GitHub Actions itself carries across the boundary instead of the runner.

GitHub Actions doesn't validate at parse time whether an env var actually holds a value — ${{ env.VERSION }} is syntactically fine and simply evaluates to an empty string at runtime. The workflow starts, runs, and reports success while silently deploying the wrong thing.

Where you have seen this before

"State doesn't cross a process boundary just because you told it to wait its turn" shows up the moment any pipeline splits work across more than one machine.

Azure DevOps stage-to-stage variables

Setting a variable with ##vso[task.setvariable]myVar=1.4.1 in one job only reaches later steps of that SAME job by default — to read it from a different stage you must mark it isOutput=true and reference it explicitly as dependencies.<StageName>.outputs['<JobName>.<StepName>.myVar']. It's the identical hand-off requirement, in ADO's own syntax.

same rule, the tool this page already compares itself to

Docker multi-stage builds

An ENV set in one FROM ... AS builder stage of a Dockerfile does not exist in a later FROM node:20 stage — each stage starts from its declared base image with none of the previous stage's environment, and only files explicitly pulled across with COPY --from=builder make the trip.

the same isolation, one layer down in the build system

A child process's export never reaches its parent shell

Run a script that does export FOO=bar from your terminal, and FOO is gone the moment that script's process exits — a child process inherits its parent's environment one-way, downward, and can never hand a new variable back up. It's the same underlying operating-system rule GitHub Actions' job isolation is built on top of.

1. The pipeline stages

push → checkout → build → test → package (artifact) → deploy staging → [gate] → deploy prod

# Each stage must pass for the next to run. A non-zero exit code fails the run.
# "Build once": the SAME artifact promoted from staging to prod — never rebuilt.
One immutable artifact, promoted forward. The build stage produces a versioned artifact (a jar or container image) once; every later environment deploys that exact bytes-for-bytes artifact. Rebuilding per environment is the classic anti-pattern — it lets staging and prod diverge. Stages are sequential by dependency: a failure anywhere short-circuits the rest, so a broken test can never reach production.

2. A GitHub Actions workflow

name: ci
on: { push: { branches: [main] }, pull_request: {} } # triggers
jobs:
  build:
    runs-on: ubuntu-latest # a fresh runner VM
    steps:
      - uses: actions/checkout@v4 # a reusable action
      - uses: actions/setup-java@v4
        with: { java-version: '21', distribution: temurin }
      - run: mvn -B verify # compile + test; nonzero exit = fail
      - uses: actions/upload-artifact@v4
        with: { name: app, path: target/*.jar }
Workflow → jobs → steps, on ephemeral runners. The workflow triggers on on: events. Each job gets a clean runner (so builds are reproducible — nothing leaks between runs). Steps are either run: shell commands or uses: reusable actions from the marketplace. The upload-artifact step persists the build output so later jobs (or your records) can grab it. Any step exiting non-zero fails the job and, by default, the run.

3. Environments & gates

  deploy-prod:
    needs: build # waits for build to succeed
    environment:
      name: production # requires the env's reviewers to approve
      url: https://app.example.com
    steps:
      - uses: actions/download-artifact@v4
        with: { name: app }
      - run: ./deploy.sh # secrets injected from the env scope
        env: { TOKEN: ${{ secrets.DEPLOY_TOKEN }} }
Gates turn Delivery into safe Deployment. needs: build orders the jobs; a protected environment can require reviewers to click approve before the job runs, and it scopes secrets so production credentials are only available to production deploys. This is the difference between Continuous Delivery (a human approves the prod step) and Continuous Deployment (no gate — every green build ships). Secrets are referenced as ${{ secrets.X }} and never printed, keeping credentials out of the repo.
