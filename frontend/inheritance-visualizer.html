Inheritance — The IS-A Relationship

A class hierarchy: parent at the top, children inherit its fields and methods, and can override or extend them.

What is inheritance? Why does it exist in OOP?

Suppose you're building a system with Dog, Cat, and Bird classes. All three have a name, an age, and can eat(). Without inheritance, you'd copy those fields and that method into all three classes — then fix bugs in all three separately. Inheritance lets you put shared code in a parent class (Animal) and have all three extend it: class Dog extends Animal. Dog gets everything Animal has for free.

What "extends" gives you
  • All parent fields (state)
  • All parent methods (behavior)
  • Ability to override methods (@Override)
  • Access to parent via super
The IS-A rule

Only use inheritance when the relationship is genuinely "IS-A": Dog IS-A Animal ✓. Not for "has-a" or "uses-a" — those use composition instead. Misusing inheritance leads to brittle hierarchies that are hard to change.

In Spring Boot: Spring's AbstractSecurityFilterChain, JdbcTemplate, ResponseEntityExceptionHandler — all abstract parents you extend to customize behavior while keeping the framework's scaffolding. The Template Method design pattern (from Spring internals) is built entirely on inheritance.

4. Key concepts visualized

    

      

        
IS-A relationship

        
"Dog IS-A Animal" — a Dog has every property an Animal has, plus more. So a method that accepts Animal will also accept a Dog.

      

      

        
extends keyword

        
class Dog extends Animal means "Dog inherits from Animal." Dog gets all of Animal's non-private fields and methods automatically.

      

      

        
super(...) call

        
The first line of a subclass constructor is usually super(name, age) — that's how the parent's constructor initializes its own fields.

      

      

        
@Override

        
An annotation that says "I'm intentionally replacing my parent's version of this method." If the parent doesn't actually have it (typo!), the compiler errors. Cheap safety net.

      

      

        
protected access

        
Like private, but subclasses CAN see it. Fields a parent class wants its children to use directly should be protected, not private.

      

      

        
Single inheritance

        
Java only lets you extend ONE class. (For multiple capabilities, use multiple interfaces.) This avoids the "diamond problem" that plagues C++.

      

    


    
5. When inheritance is the wrong tool

    

      

        Inheritance models "is-a" relationships. Use it when the subclass really IS a special kind of the parent. But:
      

      
    
        
  • Don't use inheritance just to share code — that often creates fragile hierarchies. Prefer composition (a class HAS-A another class as a field).
    • 
        
  • Don't make a subclass that breaks the parent's contract (Liskov violation). If Square extends Rectangle means a Rectangle whose setWidth also changes height, code expecting a Rectangle will misbehave.
    • 
        
  • Do use it when subclasses are genuine variants with shared, stable behavior (e.g., FileInputStream extends InputStream).

🌱 New to inheritance? It's one class building on another.

    

      
When Dog extends Animal, the Dog class gets all of Animal's fields and methods for free, and can add its own or replace (override) ones. It models an "is-a" relationship: a Dog is an Animal. Two payoffs: you don't rewrite shared behavior, and code written to accept an Animal automatically works with a Dog (that's polymorphism riding on inheritance). The keyword is extends; super(...) calls the parent's constructor, and super.method() calls the parent's version of a method.

    

    
🧠 Expert corner — the rules, and "favor composition"

    

      
    
        
  • Single inheritance. A class has exactly one parent (everything ultimately extends Object). Need multiple types? That's what interfaces are for.
    • 
        
  • Constructors chain. A subclass constructor calls super(...) first (implicitly the no-arg super() if you don't) — the parent is fully built before the child.
    • 
        
  • Override rules: mark with @Override (catches typos), you may return a covariant subtype, you can't reduce visibility, and final/static/private methods can't be overridden. protected exposes members to subclasses.
    • 
        
  • Favor composition over inheritance. Inheriting just to reuse code creates a fragile base class — a parent change can silently break children. Prefer HAS-A (hold the other class as a field) over IS-A unless it's a true subtype.
    • 
        
  • Respect Liskov. A subclass must be usable anywhere the parent is. The infamous Square extends Rectangle breaks this — code that sets width expecting height unchanged misbehaves.
    • 
        
  • Real-world tie-in. You inherit from framework base classes constantly — extends OncePerRequestFilter for a Spring security filter, extends RuntimeException for a custom error. Library inheritance is stable and intended; deep app-class hierarchies usually aren't.
