Advanced Queries

CTEs, window functions, and CASE — the tools that turn complex reporting into readable SQL.

🪟 What are CTEs and window functions — and when do you need them instead of basic SELECT?

Basic SELECT/JOIN/GROUP BY covers CRUD, but reporting needs more. A CTE (WITH name AS (...)) is a named subquery that makes long queries readable, and a recursive CTE walks hierarchies (org charts, role/permission trees). Window functions (FUNC() OVER (PARTITION BY … ORDER BY …)) compute ROW_NUMBER/RANK/LAG/running totals without collapsing rows — unlike GROUP BY, you keep each row and its computed value. CASE WHEN is if/else inside a query, and subqueries nest a SELECT — but a correlated one runs per outer row, so prefer a JOIN where you can.

  • CTEs name subqueries — readable; recursive CTEs walk hierarchies.
  • Window functions don't collapse rows — ROW_NUMBER/LAG/running totals.
  • PARTITION BY = GROUP BY for windows; CASE WHEN = inline if/else.
  • Prefer JOIN over correlated subqueries (which run once per outer row).

CTEs

-- CTE: new users this month vs last WITH this_month AS ( SELECT id FROM users WHERE created_at >= date_trunc('month', NOW()) ), last_month AS ( SELECT id FROM users WHERE created_at >= date_trunc('month', NOW() - INTERVAL '1 month') AND created_at < date_trunc('month', NOW()) ), growth AS ( SELECT (SELECT COUNT(*) FROM this_month) AS new_this, (SELECT COUNT(*) FROM last_month) AS new_last ) SELECT *, ROUND(100.0 * (new_this - new_last) / NULLIF(new_last, 0), 1) AS growth_pct FROM growth; -- Recursive CTE: role hierarchy WITH RECURSIVE role_tree AS ( SELECT id, name, parent_id, 0 AS depth FROM roles WHERE parent_id IS NULL UNION ALL SELECT r.id, r.name, r.parent_id, rt.depth+1 FROM roles r JOIN role_tree rt ON r.parent_id = rt.id ) SELECT * FROM role_tree ORDER BY depth;

Window functions

-- ROW_NUMBER: rank users by login count SELECT email, login_count, ROW_NUMBER() OVER ( ORDER BY login_count DESC ) AS rank, ROW_NUMBER() OVER ( PARTITION BY idp_type -- rank within each IDP ORDER BY login_count DESC ) AS rank_within_idp FROM user_login_stats; -- Running total of new users: SELECT DATE(created_at) AS day, COUNT(*) AS new_users, SUM(COUNT(*)) OVER ( -- running total ORDER BY DATE(created_at) ) AS cumulative_total FROM users GROUP BY DATE(created_at); -- LAG: compare to previous day SELECT day, new_users, LAG(new_users) OVER (ORDER BY day) AS prev_day, new_users - LAG(new_users) OVER (ORDER BY day) AS delta FROM daily_stats;

CASE + subqueries

-- CASE: classify users SELECT email, CASE WHEN last_login > NOW() - INTERVAL '7d' THEN 'Active' WHEN last_login > NOW() - INTERVAL '30d' THEN 'Returning' WHEN last_login > NOW() - INTERVAL '90d' THEN 'At risk' WHEN last_login IS NULL THEN 'Never logged in' ELSE 'Churned' END AS user_status FROM users; -- FILTER (PostgreSQL extension): SELECT COUNT(*) AS total_users, COUNT(*) FILTER (WHERE idp_type='PING') AS ping_users, COUNT(*) FILTER (WHERE idp_type='ENTRA') AS entra_users, COUNT(*) FILTER (WHERE active=false) AS inactive FROM users;

CIAM reporting queries: "Suspicious login patterns" = CTE recent_logins ⨝ failed_attempts; "daily growth by IDP" = GROUP BY day+idp_type with a window running total (Ping vs Entra velocity); "top 10 active users per role" = ROW_NUMBER() OVER (PARTITION BY role ORDER BY login_count DESC) then rank <= 10; "active last month but churned" = last_month EXCEPT this_month; "median session length" = PERCENTILE_CONT(0.5) WITHIN GROUP. Run these as native @Query (or JOOQ) when JPA can't express them cleanly.

1 — Common Table Expressions (CTEs)




-- CTE: name a subquery for readability and reuse
WITH
  active_users AS (
    SELECT id, email FROM users WHERE active = true
  ),
  user_totals AS (
    SELECT au.id, COUNT(o.id) AS order_count, SUM(o.amount) AS total
    FROM active_users au
    LEFT JOIN orders o ON o.user_id = au.id
    GROUP BY au.id
  )
SELECT email, order_count, total
FROM active_users
JOIN user_totals USING (id)
WHERE order_count > 5
ORDER BY total DESC;


CTEs improve readability and allow reuse of the same subquery multiple times. In PostgreSQL 12+, the planner inlines CTEs by default — use MATERIALIZED to force a temp table if you want the old behavior.









2 — Window Functions




Window functions compute a result across rows related to the current row WITHOUT collapsing them (unlike GROUP BY). They use an OVER() clause.


SELECT
  email,
  amount,
  -- Ranking within each user
  ROW_NUMBER() OVER(PARTITION BY user_id ORDER BY amount DESC) AS rn,
  -- Running total per user
  SUM(amount) OVER(PARTITION BY user_id ORDER BY created_at) AS running_total,
  -- Previous row in the same partition
  LAG(amount) OVER(PARTITION BY user_id ORDER BY created_at) AS prev_amount
FROM orders;




FunctionWhat it computes


ROW_NUMBER()Unique sequential number — no ties


RANK()Rank with gaps for ties (1,1,3)


DENSE_RANK()Rank without gaps for ties (1,1,2)


LAG(col, n)Value from n rows before in partition


LEAD(col, n)Value from n rows after in partition


NTILE(n)Divide rows into n buckets (quartiles etc)











3 — Recursive CTE




Recursive CTEs traverse hierarchical data (org charts, file trees, category hierarchies) without knowing the depth in advance.


-- Org chart: find all reports under manager id=1
WITH RECURSIVE org_tree AS (
  -- Anchor: the root
  SELECT id, name, manager_id, 1 AS depth
  FROM employees WHERE id = 1

  UNION ALL

  -- Recursive part: join on previous result
  SELECT e.id, e.name, e.manager_id, ot.depth + 1
  FROM employees e
  JOIN org_tree ot ON e.manager_id = ot.id
)
SELECT REPEAT('  ', depth-1) || name AS name_indented, depth
FROM org_tree;









4 — CASE Expression




-- CASE for computed columns
SELECT
  order_id,
  amount,
  CASE
    WHEN amount < 50   THEN 'small'
    WHEN amount < 200  THEN 'medium'
    ELSE                    'large'
  END AS size_tier
FROM orders;

-- CASE for pivot (rows → columns)
SELECT
  user_id,
  SUM(CASE WHEN status = 'pending'   THEN 1 ELSE 0 END) AS pending_count,
  SUM(CASE WHEN status = 'completed' THEN 1 ELSE 0 END) AS completed_count
FROM orders
GROUP BY user_id;
