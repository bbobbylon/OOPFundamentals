Azure Blob Storage — Tiers, SAS & Lifecycle

A storage account exposes a data-plane endpoint (https://<account>.blob.core.windows.net) where blobs live in containers. Access is granted three ways — Entra ID + RBAC data roles, SAS tokens, or account keys — and each blob sits in an access tier (hot / cool / cold / archive) that trades storage price against read cost.

🗂️ What is Blob Storage — and why do tiers, SAS, and data roles matter?

Blob ("binary large object") Storage is Azure's object store — the service you reach for whenever an app needs to keep files: user uploads, invoices, images, logs, backups, static websites. The hierarchy is flat and simple: a storage account (the ARM resource with a globally unique name) contains containers (like top-level folders), which contain blobs (the files, optionally with /-separated virtual paths). Two design decisions dominate real usage and the AZ-204 exam. First, how do callers get in? The modern answer is an Entra ID token plus a data-plane RBAC role like Storage Blob Data Reader — remember from the overview page that Contributor (a control-plane role) does not read blobs. When you must hand access to someone without an Entra identity — a browser downloading a file, a partner system — you mint a SAS (shared access signature): a signed URL that encodes permissions, expiry, and scope. Second, what does storage cost? Every blob has an access tier: hot (frequent access, highest storage price, cheapest reads), cool (30-day minimum, cheaper storage, pricier reads), cold (90-day), and archive (offline — hours to rehydrate, pennies to keep). Lifecycle management policies move blobs down the ladder automatically ("after 30 days without access → cool; after 180 → archive; after 7 years → delete"), which is how compliance retention gets implemented without anyone remembering to do it.

  • Account → container → blob — the account name is global (it is a DNS name); containers gate access policy; blobs are the objects.
  • Three doors — Entra token + data RBAC role (best), SAS URL (delegated, expiring), account key (root password — avoid, rotate).
  • Tiers trade storage vs access cost — hot ⇄ cool ⇄ cold are instant; archive is offline and needs rehydration (up to ~15h standard).
  • Lifecycle rules automate tiering — conditions on age/last-access move or delete blobs; this is the exam's favorite cost question.
  • Redundancy is per account — LRS (3 copies, one datacenter) → ZRS (3 zones) → GRS/GZRS (+ paired region, optional read access RA-).

The CLI happy path

# container in an existing account az storage container create \ --account-name stshopprod \ -n invoices --auth-mode login # upload with your Entra token az storage blob upload \ --account-name stshopprod \ -c invoices -f 2026-06.pdf \ --auth-mode login

AWS comparison

Blob Storage ≈ S3. Storage account ≈ nothing exact — S3 buckets are global-flat, Azure nests containers inside an account. Tiers ≈ S3 storage classes (hot≈Standard, cool≈Standard-IA, archive≈Glacier). SAS ≈ presigned URLs (SAS is richer: stored access policies, account-level scope). Lifecycle policies ≈ S3 lifecycle rules. Storage Blob Data Reader ≈ an IAM policy allowing s3:GetObject.

Spring Boot comparison

The SDK pattern mirrors a repository: BlobServiceClient (≈ NamedParameterJdbcTemplate — one per account) → BlobContainerClient (≈ a repo scoped to a table) → BlobClient (≈ one row). DefaultAzureCredential plays the role your JWT filter plays in reverse: it acquires the Bearer token (managed identity in Azure, your az login locally) instead of validating one.

CIAM in production: the standard pattern for user file uploads in an identity-aware app: the SPA never gets the account key. Your Spring API validates the user's JWT, authorizes, then either streams through the API or — for big files — mints a user-delegation SAS scoped to exactly one blob with a 10-minute expiry and hands the URL to the browser. The SAS is signed with a key derived from the API's own Entra token (its managed identity), so it is revocable by revoking the identity's role — no shared secret anywhere. That is the API→form upload recipe on the recipes pages, done the Azure way.

Archive is offline — that is the exam trap. Hot, cool, and cold blobs are all readable in milliseconds; only their price per GB and per read differs. An archive blob cannot be read at all until you rehydrate it — either Set Blob Tier back to hot/cool (standard priority up to ~15 hours, high priority under 1 hour for <10 GB) or Copy Blob to a new online blob. Deleting or re-tiering before a tier's minimum stay incurs an early-deletion charge. Any question that says "rarely accessed but must be available immediately" is asking for cool/cold, never archive.

2. The three doors, ranked

# 1️⃣ BEST — Entra ID + data-plane RBAC (no secrets at all)
az role assignment create --assignee <app-mi-object-id> \
  --role "Storage Blob Data Contributor" \
  --scope …/storageAccounts/stshopprod

# 2️⃣ DELEGATED — user-delegation SAS: scoped, expiring, revocable
az storage blob generate-sas --auth-mode login --as-user \
  --account-name stshopprod -c invoices -n 2026-06.pdf \
  --permissions r --expiry 2026-07-03T12:10Z

# 3️⃣ AVOID — account key: full-account root password
az storage account keys list -n stshopprod # rotate if it ever leaks
SAS comes in three kinds — know which signs with what. A user-delegation SAS is signed with a key obtained via Entra ID (best: no account key involved, honors RBAC, max 7-day validity). A service SAS and an account SAS are signed with the account key — anyone holding the key can mint them forever, and rotating the key instantly kills every SAS it signed. Tie service SAS to a stored access policy on the container so you can revoke the policy without rotating keys. If the exam says "revoke access without rotating keys" → stored access policy or user-delegation SAS.

3. Lifecycle management: tiering on autopilot

// lifecycle policy — JSON on the storage account
{ "rules": [{ "name": "invoices-retention", "enabled": true,
  "definition": {
    "filters": { "blobTypes": ["blockBlob"], "prefixMatch": ["invoices/"] },
    "actions": { "baseBlob": {
      "tierToCool": { "daysAfterModificationGreaterThan": 30 },
      "tierToArchive": { "daysAfterModificationGreaterThan": 180 },
      "delete": { "daysAfterModificationGreaterThan": 2555 }
    } } } }] }
Policies run roughly once a day — not instantly. Lifecycle rules evaluate age conditions (daysAfterModificationGreaterThan, or daysAfterLastAccessTimeGreaterThan if access tracking is enabled) and can tier, delete, or manage snapshots/versions. Combined with blob soft delete + versioning, this is the full data-protection story: soft delete catches accidents (a deleted blob is recoverable for N days), versioning keeps history, lifecycle keeps the bill down. 2555 days = the classic 7-year compliance retention.
