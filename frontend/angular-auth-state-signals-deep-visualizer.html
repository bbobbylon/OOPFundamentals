Auth State with Signals

Every screen needs to know the same things: who's logged in, are they authenticated, what can they do. Scatter that across components and it drifts. The modern Angular answer is one signal-based store: a user signal plus computed derivations (isAuthenticated, roles), and everything — guards, the bearer interceptor, and the UI — reads from it and updates automatically.

1. One store, derived state

@Injectable({ providedIn: 'root' })
export class AuthStore {
  private _user = signal<User | null>(null);

  readonly user            = this._user.asReadonly();
  readonly isAuthenticated = computed(() => this._user() !== null);
  readonly roles           = computed(() => this._user()?.roles ?? []);

  hasRole(r: string) { return this.roles().includes(r); }
  login(u: User) { this._user.set(u); }
  logout()       { this._user.set(null); }
}

Expose read-only signals; mutate only through methods. Consumers never hold their own copy — they read auth.isAuthenticated() and re-render when it changes.

Guard & interceptor

4. Initializing & persisting

  • Hydrate on startup from the (validated) token, not from a stored user object — the token is the source of truth. Decode it, set _user; if it's expired, silent-refresh first.
  • Don't trust persisted state. A user in localStorage can be edited to {role:'admin'}; the server still enforces real authority on every call. The store is UX.
  • RxJS interop when you need it: toObservable(auth.user) to drive a stream, or toSignal() to fold an HTTP login response into the store.
  • Logout clears the signal and ends the IDM session (see the token page) so the next login doesn't silently re-auth.

5. One-sentence recap

🧠 Keep auth in one signal store — a private user signal exposed read-only, with computed isAuthenticated/roles/hasRole() — so guards, the bearer interceptor, and the template all read the same reactive source and update automatically on login()/logout(); hydrate it from the validated token (not a persisted user object) on startup, and remember it's UX only — the server still enforces real authority.
