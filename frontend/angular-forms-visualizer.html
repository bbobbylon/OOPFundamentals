Reactive Forms — Comprehensive Reference

Reactive forms model the form in the component class — typed, testable, observable, and predictable. This page is the full reference: every control type, every validator pattern, every state, and the custom-control pattern most devs never learn.

📝 What are Reactive Forms? Why not just use <input> directly?

A plain <input> keeps its value in the DOM — to read it you reach into the DOM, and there's no clean way to validate, track dirty/touched state, or debounce typing. Reactive Forms move the whole form model into the component class as a FormGroup of typed FormControls. You read form.value, react to form.valueChanges (an Observable), and attach validators as pure functions — all fully TypeScript-typed since Angular 14.

  • The form lives in the class, not the template — so it's testable, typed, and you can build/validate it programmatically.
  • FormControl = one field; FormGroup = a set of named controls; FormArray = a dynamic, growable list of controls.
  • Validators are functions (Validators.required, custom, or cross-field) producing an errors object; group.valid is true only if every control is.
  • State flags drive UX: pristine/dirty (changed?) and untouched/touched (blurred?) — show errors only once dirty || touched.
  • valueChanges + debounceTime() powers autosave/typeahead; getRawValue() includes disabled controls on submit.

FormControl — one field

new FormControl('', [Validators.required, Validators.email]) wraps one input. It exposes .value, .valid, .dirty, .touched, .errors, and a .valueChanges Observable. The generic (FormControl<string>) types .value.

FormGroup — a whole form

new FormGroup({ email: …, password: … }). group.value is { email, password }; group.valid is true only if ALL controls are valid. Submit with getRawValue() to include disabled controls.

Control states

pristine = never changed, dirty = user typed; untouched = never blurred, touched = focused then blurred. Show validation errors only when dirty || touched so fields don't go red before the user types.

In CIAM:a registration form is a FormGroup of email, displayName, roles (a FormArray) and mfaEnabled. Submit POSTs getRawValue() to /api/users; valueChanges.pipe(debounceTime(300)) autosaves a draft; a cross-field validator makes sure password + confirm match before submit is allowed.

The problem

The role field was right there on screen. It never made it to the server.

form.value silently drops every disabled control — not just skips it, omits the key entirely

You built a user-edit form. Non-admins can't change their own role, so you disable the control for them: this.form.get('role').disable(). The field still renders — greyed out, showing "USER" — exactly the UX you wanted. On submit you send this.form.value to the API. The PATCH lands with no role key at all — not role: null, not role: "", the property simply isn't in the object. Depending on how your backend treats an absent field, that ranges from harmless to a genuine data-integrity bug on a request that happened to reuse this same form component.

the field renders correctly, greyed out ✓ the value onscreen matches the server ✓ form.value silently excludes disabled controls ⚠ the key isn't sent as null — it's just absent ⚠

Angular isn't hiding a bug here. .value doing exactly this is documented — just documented in a place most people read after they've already shipped the form.

Use getRawValue() when disabled fields must be in the payload
this.form.getRawValue() instead of this.form.value on submit ↓ getRawValue() includes every control regardless of disabled state Or, if the value genuinely shouldn't be sent either, leave form.value as-is ↓ disabled isn't always "still relevant, just locked" — sometimes it's really "not this form's business" Decide which one you meant, per field, instead of discovering it in a bug report
disable() doesn't remove a control from the form — it removes it from .value. Every other API still sees a disabled control: it's still in form.controls, it still has a value you can read with getRawValue() or the control's own .value, it's just excluded from the aggregate .value and skipped by validation. That one exclusion rule is the entire reason getRawValue() exists, and forgetting it is the single most common way a Reactive Form quietly loses data on submit.
Think of a disabled control like an employee on leave, still on the org chart. Ask .value for the department roster and it only counts people currently clocked in — technically accurate, and exactly why payroll (getRawValue()) has to check the full roster, on-leave employees included, or somebody's paycheck goes missing.

The mechanism

One flag, checked at exactly one point: when .value gets assembled.

  1. FormControl.disable() sets the control's status to DISABLED and marks it excluded from its parent's aggregationthe only thing disable() actually flips
  2. The control keeps its current value internally — disable() doesn't clear it, blank it, or detach it from the DOM bindingwhich is why it still renders correctly
  3. A disabled control is skipped by validation entirely — not "always valid," genuinely not checked — so a disabled required field never blocks form.valida second, separate consequence of the same flag
  4. Reading form.value walks the control tree and builds an object from ENABLED controls only, recursively — a disabled child of an enabled FormGroup is dropped right therethe exact moment the key disappears
  5. getRawValue() walks the identical tree but builds the object from every control regardless of statussame tree, different filter
  6. valueChanges also only fires from an enabled control's own edits — calling disable()/enable() itself doesn't emit on valueChanges, only on statusChangesa second place this same flag quietly changes behavior

Step 4 is the one line of implementation that explains the whole page's worth of confusion. There's no separate "submission mode" Angular switches into — .value is always the enabled-only view, every time you read it, which is why the disabled field's data was never briefly there and then removed. It was never in .value to begin with.

Two controls make it into .value; the disabled one doesn't, even though it's sitting in the exact same FormGroup with a real value of its own. Swap the read for getRawValue() and all three appear — same tree, the only thing that changed is which method walked it.

A FormGroup has email (enabled) and role (disabled, current value 'ADMIN'). You call form.get('role').enable() immediately before reading form.value on the very next line. What does form.value contain?

There's no change-detection delay here — FormControl status changes are plain synchronous method calls, not something queued for a future render. If enable() already ran on the line above, .value already reflects it by the time you read it.

Right — enable() and disable() take effect immediately and synchronously. .value is computed fresh every time you read it by walking the current control tree, so there's no lag between flipping a control's status and that change showing up in the very next .value read, even one line later.

enable() and disable() only ever change a control's status, never its value. The control held 'ADMIN' before the call and holds 'ADMIN' after it — that's actually the whole reason getRawValue() is useful in the first place: the value was preserved the entire time it was disabled, not cleared.

Where you've seen this before

Silent, documented exclusion shows up everywhere data gets filtered on the way out.

SQL's WHERE clause, silently dropping rows

A query filtered on status = 'active' doesn't complain that inactive rows exist — it just never shows them, and a report built from that query looks complete until someone asks where the archived accounts went. .value filtering out disabled controls is the identical shape: correct, silent exclusion that only becomes a bug once someone downstream assumed "the result" meant "everything."

a silent WHERE clause, not a bug

JSON.stringify skipping undefined values

JSON.stringify({ a: 1, b: undefined }) produces '{"a":1}' — no b key at all, the same silent-omission shape as a disabled control missing from .value. Both are documented, correct behavior that still catches people expecting "the object" to mean "every property I set."

undefined keys vanish; disabled controls vanish

A locked MFA-enforcement toggle, for real

An org-policy screen where "require MFA" is locked ON for admin roles by policy — shown checked and greyed out. A save handler built on form.value silently drops that field from the PATCH, and if the backend treats a missing field as "leave whatever's there," this specific case is harmless by luck. Change the backend's semantics to "missing means false" even once, and a locked-on security setting silently turns itself off on save.

luck, not correctness, is doing the work here
Questions from the back row

If disabled controls are skipped by validation, can a form with an invalid disabled field still be form.valid?

Yes — consistent with everything else disable() does, not a separate bug. A disabled control's status becomes DISABLED, not VALID or INVALID, and the parent FormGroup's aggregate validity only looks at ENABLED children. A required field showing empty and disabled won't block submission — which is exactly why the "good card" pattern matters: decide deliberately whether a locked field should also be exempt from validation, because Angular will exempt it whether you decided that or not.

Does setValue() work on a disabled control?

Yes, and this surprises people in the other direction — setValue() and patchValue() both still write to a disabled control's internal value; disabled only affects the .value/.valid aggregation, not whether the control can be programmatically updated. It's specifically user input that the disabled state blocks, via the native element's own [disabled] binding; your TypeScript can read and write a disabled control freely.

Is there a way to include SOME disabled controls in .value but not others?

Not through .value/getRawValue() directly — that split is all-or-nothing per form. The common pattern is building the submit payload by hand instead of trusting either helper blindly: spread form.value, then explicitly add back the specific disabled fields you need with form.get('role').value. A few extra lines, but it makes the intent — "this one is deliberately included" — visible in the code instead of riding on which helper method you happened to call.

FormControl — the atom

Every input you bind to a form is backed by one FormControl. The control holds the value AND the metadata (valid, dirty, touched, errors).

import { FormControl, Validators } from '@angular/forms';

const email = new FormControl('', [Validators.required, Validators.email]);

// READ
email.value;          // current value
email.valid;          // boolean
email.invalid;        // boolean — convenience inverse
email.errors;         // { required: true } | { email: true } | null
email.touched;        // user has blurred it at least once
email.dirty;          // user has modified the value
email.pristine;       // !dirty
email.pending;        // async validator running
email.status;         // 'VALID' | 'INVALID' | 'PENDING' | 'DISABLED'

// WRITE
email.setValue('a@b.com');
email.patchValue('a@b.com');
email.markAsTouched();
email.markAsDirty();
email.reset();             // back to initial: value=null, untouched, pristine
email.disable(); email.enable();

// SUBSCRIBE
email.valueChanges.subscribe(v => console.log('now:', v));
email.statusChanges.subscribe(s => console.log('status:', s));

FormGroup — composing controls

A FormGroup bundles named controls into one object. Its value is the object of child values; its validity is the AND of children.

import { inject } from '@angular/core';
import { FormBuilder, Validators } from '@angular/forms';

export class SignupComponent {
  private fb = inject(FormBuilder);   // factory for group()/control()/array() below

  form = this.fb.group({            // each key becomes a named FormControl — the object's SHAPE is the form's shape
    email:    ['', [Validators.required, Validators.email]],
    password: ['', [Validators.required, Validators.minLength(8)]],
    age:      [null, [Validators.required, Validators.min(13)]],
  });

  onSubmit() {
    if (this.form.invalid) {
      this.form.markAllAsTouched();   // show errors that weren't blurred
      return;                        // bail out — nothing gets submitted while invalid
    }
    this.api.signup(this.form.getRawValue());  // includes disabled fields
  }
}

This class never touches the DOM — the whole form (fields, validators, submit logic) is testable object graph before a single template exists. The template below is just a thin binding to it.

The template side

<form [formGroup]="form" (ngSubmit)="onSubmit()">  <!-- links this <form> to the class's `form` property -->
  <input formControlName="email" placeholder="email">  <!-- must match a key in fb.group({...}) exactly -->
  @if (form.controls.email.touched && form.controls.email.invalid) {  <!-- read the SAME control the input is bound to -->
    <small>Please enter a valid email</small>
  }
  <button [disabled]="form.invalid">Sign up</button>  <!-- the GROUP's validity, not any one field -->
</form>

Accessing children

form.controls.email           // the FormControl instance (typed!)
form.get('email')              // same, by path string
form.get('address.zip')        // dot notation for nested groups
form.value                    // { email, password, age }
form.getRawValue()             // INCLUDES disabled fields (form.value skips them)

FormArray — dynamic forms

When the number of fields is dynamic (a list of phone numbers, line items, tags), use FormArray. You add/remove controls at runtime.

import { FormArray, FormControl, FormGroup } from '@angular/forms';

phones = new FormArray([                // a LIST of controls, not a set of named ones — index is the key
  new FormControl('', Validators.pattern(/^\d{10}$/)),   // starts with exactly one row
]);

addPhone() {
  this.phones.push(new FormControl('', Validators.pattern(/^\d{10}$/)));  // appends a new control at runtime
}
removePhone(i: number) {
  this.phones.removeAt(i);            // by index, not by value
}
clearPhones() {
  this.phones.clear();               // removes every control, array stays — not the same as reassigning it
}

Every method here mutates phones in place (push/removeAt/clear) instead of assigning a new array — that's what the "Gotcha" below the third block is warning you never to break.

Template — formArrayName + index binding

<div formArrayName="phones">          <!-- wires this block to the FormArray named "phones" -->
  @for (phone of phones.controls; track $index) {   // iterate the CONTROLS, track by position — there's no stable id
    <input [formControlName]="$index" placeholder="10 digits">  <!-- the control's NAME is its array index -->
    <button type="button" (click)="removePhone($index)">×</button>
  }
</div>
<button type="button" (click)="addPhone()">Add phone</button>  <!-- type="button" is required — plain "submit" would fire the form's ngSubmit -->

FormArray of FormGroups — line items, addresses, etc.

items = this.fb.array([               // same array, but each ELEMENT is a whole group now
  this.fb.group({ name: [''], qty: [1], price: [0] }),
]);

addItem() {
  this.items.push(this.fb.group({   // push a brand new group, not a bare control
    name:  ['', Validators.required],
    qty:   [1,  [Validators.required, Validators.min(1)]],
    price: [0,  [Validators.required, Validators.min(0)]],
  }));
}

A FormArray doesn't care WHAT it holds — plain controls (phones, above) or whole groups (line items, here). The template just needs one more formGroupName="$index" wrapper per row to reach into each group's own fields.

Gotcha: Don't replace the entire array reference (this.form.setControl('items', newArray)). Use push / removeAt / clear so subscribers don't lose their references.

Typed forms (Angular 14+)

Pre-v14 forms were typed as any — a usability disaster. Now every control infers its type from the initial value or from an explicit generic.

const form = new FormGroup({
  email:    new FormControl('', { nonNullable: true }),
  age:      new FormControl<number | null>(null),
});

form.value;                  // { email?: string, age?: number | null }
form.getRawValue();          // { email: string, age: number | null }
form.controls.email.value;   // string (because nonNullable)
form.controls.age.value;     // number | null

The shortcut: NonNullableFormBuilder

private fb = inject(NonNullableFormBuilder);
// All controls created via this fb are { nonNullable: true } by default.

form = this.fb.group({
  email:    ['', Validators.required],   // type: FormControl<string>
  password: ['', Validators.required],
});

type Signup = typeof this.form.value;
// → { email: string, password: string } — perfect, no null pollution
Use NonNullableFormBuilder as your default. The only time you want a nullable control is when "no value yet" is genuinely distinct from "" — like an optional age field.

FormBuilder shorthand

FormBuilder is just sugar over new FormControl/FormGroup/FormArray — same result, less typing.

Without FormBuilder

form = new FormGroup({          // every control spelled out with `new`
  email: new FormControl('',
    [Validators.required, Validators.email]),
  password: new FormControl('',
    [Validators.required, Validators.minLength(8)]),
});

With FormBuilder

form = this.fb.group({           // same result — fb infers FormControl from each array
  email:    ['', [Validators.required, Validators.email]],
  password: ['', [Validators.required, Validators.minLength(8)]],
});

Read the two side by side: every new FormControl(value, validators) on the left became a plain [value, validators] array on the right. fb.group() just unpacks that array shape for you.

The array form is [initialValue, syncValidators, asyncValidators].

type ValidatorFn = (control: AbstractControl) => ValidationErrors | null;

Custom synchronous validators

A validator is a function: takes the control, returns null (valid) or an error object (invalid).

// 1. Simple: no parameters
export const noSpaces: ValidatorFn = (ctrl) => {
  return /\s/.test(ctrl.value) ? { noSpaces: true } : null;
};

// 2. Parameterized: outer function returns the validator
export function forbiddenName(forbidden: RegExp): ValidatorFn {
  return (ctrl) => {
    return forbidden.test(ctrl.value)
      ? { forbiddenName: { value: ctrl.value } }
      : null;
  };
}

// 3. Wire it up
username = this.fb.control('', [
  Validators.required,
  noSpaces,
  forbiddenName(/^(admin|root)$/),
]);

// 4. Display
// @if (username.errors?.forbiddenName) {
//   "{{ username.errors.forbiddenName.value }} is reserved" }
The convention: return { errorName: extraInfo }. The key becomes how you look it up (control.errors?.errorName); the value can carry context for the message.

Async validators

For checks that need the network — username availability, address verification — use AsyncValidatorFn. The control's status goes to PENDING until the validator emits/resolves.

type AsyncValidatorFn = (ctrl: AbstractControl) =>    // same shape as ValidatorFn, but returns...
  Promise<ValidationErrors | null> | Observable<ValidationErrors | null>;  // ...a Promise/Observable of the result, not the result itself

export function usernameAvailable(api: UserApi): AsyncValidatorFn {   // same "outer function returns the validator" shape as sync custom validators
  return (ctrl) => api.isAvailable(ctrl.value).pipe(
    debounceTime(300),                                // don't hammer the API
    distinctUntilChanged(),                              // skip a redundant call if the value didn't actually change
    switchMap(ok => of(ok ? null : { taken: true })),  // translate the API's boolean into null | error-object
    first()                                          // IMPORTANT — must complete
  );
}

// Wire it up — async validators go in the THIRD slot
username: ['', [Validators.required], [usernameAvailable(this.userApi)]]  // [value, sync[], async[]] — three positions, not two

The control's status walks VALID → PENDING → VALID/INVALID for exactly as long as this observable takes to complete — which is why first() a few lines up isn't optional: without it, status gets stuck on PENDING forever.

Display the pending state

@if (form.controls.username.pending) {
  <small>Checking availability…</small>
} @else if (form.controls.username.errors?.taken) {
  <small>That username is taken</small>
}
Two non-obvious rules:
1. Async validators only run AFTER all sync validators pass. So if required fails, no network call. (Saves you.)
2. The async validator MUST complete (emit then end). Use first() or take(1) — without them the control stays PENDING forever.

Cross-field validators (group-level)

When a rule depends on more than one field — "password matches confirmation", "end date is after start date" — attach the validator to the FormGroup, not a single control.

export function passwordMatch(group: AbstractControl): ValidationErrors | null {  // takes a GROUP, not a control
  const pw  = group.get('password')?.value;   // reach into siblings via the group it's attached to
  const cpw = group.get('confirm')?.value;
  return pw === cpw ? null : { mismatch: true };  // the error lands on the GROUP, not on either field
}

form = this.fb.group({
  password: ['', [Validators.required, Validators.minLength(8)]],
  confirm:  ['', Validators.required],
}, { validators: [passwordMatch] });   // group-level option — 2nd argument to fb.group(), not inside either field's array

The validator is registered as the FormGroup's own second-argument option, not tucked inside password or confirm's validator array — that placement is what lets it read both fields at once.

Display the error in the template

@if (form.errors?.mismatch && form.controls.confirm.touched) {
  <small>Passwords don't match</small>
}

Group-level errors live on the group: form.errors, not control.errors. The form itself becomes invalid until they're cleared.

Conditional validation

Add or remove validators based on another control's value. Always call updateValueAndValidity() after changing validators — otherwise the new rules don't run until the next change.

// "If user picks 'Other', the explanation field is required"
this.form.controls.reason.valueChanges.pipe(   // watch ONE control to conditionally validate ANOTHER
  takeUntilDestroyed()                    // auto-unsubscribe when the component is destroyed
).subscribe(reason => {
  const explanation = this.form.controls.explanation;
  if (reason === 'other') {
    explanation.setValidators([Validators.required, Validators.minLength(10)]);  // REPLACES whatever validators it had
  } else {
    explanation.clearValidators();     // back to no validators at all
  }
  explanation.updateValueAndValidity();   // MUST be called
});

// Add a single validator without replacing the existing ones
ctrl.addValidators([Validators.required]);   // ADDS to the existing list — setValidators() above would have wiped it
ctrl.removeValidators([Validators.required]);   // removes just this one, leaves the rest
ctrl.hasValidator(Validators.required);   // check

setValidators and addValidators read almost the same but do opposite things: one REPLACES the whole list, the other appends to it. Reach for addValidators/removeValidators whenever some validators (like required here) should always stay regardless of what else changes.

Error display strategies — when to show errors

"Show every error from the moment the form renders" is hostile. There are four common strategies — pick one and apply it consistently.

touched && invalid
Show after the user has blurred the field at least once. The most common choice.
dirty && invalid
Show as soon as the user has typed something. Better for hot validation like password strength.
submitted && invalid
Hold all errors until the form is submitted. Common in long-form questionnaires.
(touched || submitted) && invalid
Hybrid: per-field on blur, but everything lights up on submit. The friendliest default.

Track submitted via the directive

// Component
@ViewChild(FormGroupDirective) formDir!: FormGroupDirective;   // the directive [formGroup] creates — .submitted lives here, not on the FormGroup itself
shouldShow(name: string) {                 // one helper, called per field from the template
  const c = this.form.get(name);
  return c?.invalid && (c.touched || this.formDir?.submitted);  // the hybrid strategy from the table above, as code
}

valueChanges & statusChanges — forms as Observables

Every AbstractControl exposes two streams:

  • valueChanges — emits the new value on every change
  • statusChanges — emits 'VALID' / 'INVALID' / 'PENDING' / 'DISABLED'
// Auto-save when the form is valid and changes settle
this.form.valueChanges.pipe(       // a plain Observable — every RxJS operator you know already works here
  debounceTime(500),                      // wait for typing to pause, don't save every keystroke
  distinctUntilChanged((a, b) => JSON.stringify(a) === JSON.stringify(b)),  // skip a no-op save if nothing really changed
  filter(() => this.form.valid),      // never save an invalid draft
  switchMap(value => this.api.save(value)),  // switchMap cancels an in-flight save if the user keeps typing
  takeUntilDestroyed()                    // unsubscribe automatically when the component goes away
).subscribe();

This is the whole payoff of forms being Observables: five stock RxJS operators turn every field into an autosaving draft, with no manual timers and no manual subscription bookkeeping beyond takeUntilDestroyed().

Gotcha: valueChanges emits on every set, including patchValue calls. To skip emission, pass { emitEvent: false }:
ctrl.patchValue(val, { emitEvent: false }) — useful when you're syncing the form from external state and don't want to ping-pong.

Disabled controls — the trap

// ❌ The classic warning everyone has hit
// Template:
<input formControlName="x" [disabled]="!canEdit">
// Console:
// "It looks like you're using the disabled attribute with a reactive form directive..."

// ✅ Disable in the TypeScript, not the template
if (!this.canEdit) {
  this.form.controls.x.disable();
} else {
  this.form.controls.x.enable();
}

A disabled control is excluded from form.value, form.valid, and validators. Use form.getRawValue() if you need its value anyway.

updateOn: 'change' / 'blur' / 'submit'

By default, Angular runs validators and emits valueChanges on every keystroke. For expensive validators or large forms, defer to blur or submit.

// Per-control
email = new FormControl('', { updateOn: 'blur' });

// Per-group — applies to all children unless they opt out
form = this.fb.group({ ... }, { updateOn: 'submit' });

ControlValueAccessor — building custom form controls

Want to use your own <app-rating-stars> or <app-date-picker> with formControlName? Implement ControlValueAccessor. Four methods, that's the whole contract.

import {
  ControlValueAccessor, NG_VALUE_ACCESSOR
} from '@angular/forms';

@Component({
  selector: 'app-stars',
  standalone: true,
  providers: [{
    provide:     NG_VALUE_ACCESSOR,
    useExisting: forwardRef(() => StarsComponent),
    multi:       true
  }],
  template: `
    @for (i of [1,2,3,4,5]; track i) {
      <span (click)="select(i)" [class.on]="i <= value">★</span>
    }
  `
})
export class StarsComponent implements ControlValueAccessor {
  value = 0;
  disabled = false;

  private onChange = (_: number) => {};   // placeholder until the form registers its real callback
  private onTouched = () => {};

  // 1. Forms → component
  writeValue(value: number): void { this.value = value ?? 0; }  // called by Angular on setValue/patchValue/reset — never call it yourself

  // 2. Component → forms (call when user changes value)
  registerOnChange(fn: (v: number) => void): void { this.onChange = fn; }  // Angular hands you ITS callback — you store it

  // 3. Component → forms (call to mark as touched, usually on blur)
  registerOnTouched(fn: () => void): void { this.onTouched = fn; }  // same idea, for the touched flag

  // 4. Forms → component (toggle interactivity)
  setDisabledState(isDisabled: boolean): void { this.disabled = isDisabled; }  // fires when ctrl.disable()/.enable() is called

  select(n: number) {
    if (this.disabled) return;   // respect the form's disabled state even though this is a plain click handler
    this.value = n;
    this.onChange(n);     // notify the form!
    this.onTouched();
  }
}

// Now it works with Reactive Forms transparently:
// <app-stars formControlName="rating" />

Four methods, two directions: writeValue is the only one the FORM calls into the component; registerOnChange/registerOnTouched just hand over two callbacks that YOUR component calls later, whenever the user actually interacts. Nothing here talks to a FormControl directly — that's the whole point.

Why CVA matters: any component that implements it becomes a first-class form control. You can use formControlName on it. Validators, valueChanges, all of it just works. This is how Material/PrimeNG/etc. build their input components.

Nested FormGroups

Sometimes a sub-section of a form is logically grouped (an address, a billing block). Nest a FormGroup inside the parent.

form = this.fb.group({
  name: ['', Validators.required],
  address: this.fb.group({          // a group AS a field — this is the entire technique
    street: ['', Validators.required],
    city:   ['', Validators.required],
    zip:    ['', [Validators.required, Validators.pattern(/^\d{5}$/)]],
  }),
});

// Template — formGroupName on the wrapper
<div formGroupName="address">       <!-- points at the nested group's KEY, not a class or id -->
  <input formControlName="street">   <!-- resolved relative to formGroupName above, not the root form -->
  <input formControlName="city">
  <input formControlName="zip">
</div>

// Access nested
form.get('address.zip')          // dot-path string — one call, no chained .get()s
form.value.address?.zip              // or plain property access on the value object — same shape either way

Nesting is recursive by construction: address is itself a full FormGroup with its own validity, its own value, its own errors — the parent form's overall validity is just the AND of every leaf, however deep.

Reactive Forms + Signals

Forms predate signals, but the two compose beautifully via toSignal.

import { toSignal } from '@angular/core/rxjs-interop';

formValue = toSignal(this.form.valueChanges, {
  initialValue: this.form.value
});

isValid = toSignal(this.form.statusChanges.pipe(
  map(s => s === 'VALID')
), { initialValue: this.form.valid });

// Computed derived state — fully reactive
canSubmit = computed(() => this.isValid() && !this.submitting());

// Template:
// <button [disabled]="!canSubmit()">Save</button>

A new generation of "Signal Forms" is being designed for Angular — keep an eye on the RFC. Until it lands, Reactive Forms + toSignal is the right pattern.

Testing forms — the killer feature

Because the form lives in the component class, you can test it without rendering anything.

describe('SignupForm validation', () => {
  let form: FormGroup;

  beforeEach(() => {              // fresh form before every test — no shared/leaking state
    const fb = new FormBuilder();   // plain `new`, not injected — there's no DI container running here
    form = fb.group({
      email:    ['', [Validators.required, Validators.email]],
      password: ['', [Validators.required, Validators.minLength(8)]],
    });
  });

  it('rejects bad email', () => {
    form.controls.email.setValue('nope');      // drive the control directly — no typing simulation needed
    expect(form.controls.email.errors).toEqual({ email: true });  // assert on the SAME errors object the template would read
  });

  it('is invalid until both fields are valid', () => {
    form.patchValue({ email: 'a@b.com', password: 'short' });  // email ok, password too short
    expect(form.invalid).toBeTrue();      // group is invalid because ONE child still fails
    form.patchValue({ password: 'longenough' });   // fix just the failing field
    expect(form.valid).toBeTrue();       // now every child passes, so the group does too
  });
});

Notice there's no TestBed.createComponent, no fixture.detectChanges(), no querying the DOM for an input to type into — because the form's validation logic lives entirely in the class, testing it is just testing a plain object.

No TestBed, no fixtures, no DOM. Pure logic tests for validation rules.

Mental model — final word

The form is data, not DOM

The FormGroup lives in your class. The template just renders + binds to it. You can build, validate, test, save — all without ever rendering.

Validators are pure functions

(ctrl) => error | null. That's the whole contract. No magic, no framework hooks. Easy to write, easy to test, easy to compose.

Errors are objects, not strings

An error object's KEY is the lookup; the VALUE carries context for the message. { required: true }, { minLength: { requiredLength: 8, actualLength: 4 } }.

State has many dimensions

valid/invalid · pristine/dirty · touched/untouched · pending · disabled. They're independent — touched ≠ dirty ≠ invalid. Display rules combine them.

valueChanges is a stream

Compose it with RxJS — debounce, distinctUntilChanged, switchMap. This is where Reactive Forms shines vs template-driven.

Custom controls = CVA

Anything you build that implements ControlValueAccessor becomes first-class. Star ratings, date pickers, color pickers — all standard formControlName targets.

🌱 New to reactive forms? The form lives in your class, not the template.

A "reactive" form means you model it as objects in your TypeScript: a FormControl for each field, grouped in a FormGroup. You create them in the class, connect them to the HTML with [formGroup] and formControlName="email", and then you can read form.value and form.valid at any time, from code. Validation is just functions you attach (Validators.required, Validators.email). The payoff for a beginner: the form is data you own and can inspect — no hunting through the DOM — which makes it easy to test, pre-fill, enable/disable, and build dynamically.

🧠 Expert corner — typed forms, valueChanges, and the validator types

  • Reactive vs template-driven. Reactive = explicit, synchronous, unit-testable (the model is in code). Template-driven ([(ngModel)]) is simpler but async and harder to test. Prefer reactive for anything non-trivial.
  • Typed forms (v14+). new FormControl('', {nonNullable:true}) gives FormControl<string> — form.value is fully typed, and nonNullable stops the surprise null after reset(). Build them tersely with inject(FormBuilder).
  • valueChanges/statusChanges are Observables. That's the gateway to live behavior: form.get('q').valueChanges.pipe(debounceTime(300), switchMap(search)) for a type-ahead.
  • Validators come in three kinds: sync (Validators.required), async (return an Observable/Promise — e.g. "is this username taken?"), and cross-field (a validator on the FormGroup comparing two controls, like password-confirm).
  • FormArray models a dynamic, add/remove list of controls (line items, phone numbers). updateOn:'blur'|'submit' tunes when validation runs.
  • CIAM tie-in. A login/registration form: Validators for shape, a custom async validator hitting the API for "email already registered", and a submit button bound to [disabled]="form.invalid || submitting()". See Reactive Forms (Auth).
