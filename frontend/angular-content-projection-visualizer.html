Content Projection

How Angular lets consumers inject their own HTML into a component — from basic <ng-content> slots to dynamic templates and runtime component rendering.

🧱 What is content projection? Why is it the key to reusable UI?

Picture an <app-modal> that can show any content — a delete confirmation, a user form, a JSON viewer — without knowing in advance what that content is. Content projection lets the consumer drop their own HTML into named "slots" via <ng-content>: the component defines where content goes, the caller decides what. It's exactly how Angular Material's mat-card, mat-dialog, and mat-tab stay reusable.

  • A single <ng-content> renders whatever the consumer puts between the component's tags.
  • <ng-content select="[slot]"> creates named slots — project by attribute, element, or class into specific spots.
  • The component owns the chrome (border, padding, layout); the consumer owns the content — so one component serves many uses without forking.
  • For row/column renderers, an <ng-template> + *ngTemplateOutlet passes a typed context the consumer reads (let-user).
  • Projected content keeps the consumer's injector & lifecycle — it isn't a child of the component it lands in.

Single slot

Component: <div class="card"><ng-content></ng-content></div>. Consumer: <app-card><h2>Title</h2><p>Body</p></app-card>. Everything between the tags lands inside the card.

Named slots (select=)

<ng-content select="[modal-header]"> picks <h2 modal-header>…</h2>; another slot takes [modal-body]. Select by attribute, element, or class; unmatched content falls into a plain <ng-content> fallback.

ng-template + TemplateRef

@Input() cellTemplate?: TemplateRef<{ $implicit: User }>, rendered via *ngTemplateOutlet="cellTemplate; context: { $implicit: row }". The consumer supplies <ng-template let-user>…</ng-template> — full, type-safe control over each cell.

In CIAM:a shared <app-confirm-dialog> with [dialog-title]/[dialog-body]/[dialog-actions] slots serves "Delete User" and "Revoke Token" with the same chrome, different payloads. A user table takes an [actionColumn] template — admin pages project Edit+Delete, read-only pages project View — one table, zero forks.

What is Content Projection?

      

        Content projection (also called transclusion in Angular 1 days) lets a child component reserve a placeholder — a slot — that its parent fills in with arbitrary HTML at usage time.
        The child defines the shell (layout, behaviour, styles), the parent provides the content.
      

      

        
Parent
provides content

        
→

        
<app-card>
shell component

        
→

        
<ng-content>
slot / hole

      

      

        Core idea: without content projection you'd need a different component (or a giant @Input() receiving raw HTML) for every variation. With it, one reusable shell handles unlimited variations.
      

      

        

          
Without projection

          
You'd pass strings or HTML via @Input, or duplicate the card component for each content variation — brittle and non-composable.

        

        

          
With projection

          
One <app-card> shell. Consumers put anything between its tags — text, images, other components — and it just shows up in the slot.

        

        

          
Real examples

          
Modal dialogs, card layouts, tab panels, accordions, drawer sidebars, table rows — every "wrapper" UI pattern uses projection.

Single-slot: <ng-content>

      

        The simplest form: one <ng-content> tag inside the child's template acts as a single hole. Everything between the child's opening and closing tags in the parent gets projected there.
      

      

        

          
Child component template (shell)

          
<!-- app-card.component.html -->
<div class="card">
  <div class="card-wrapper">

    <!-- 👇 the "hole" — parent fills this -->
    <ng-content></ng-content>

  </div>
</div>

        

        

          
Parent usage

          
<!-- app.component.html -->
<app-card>
  <!-- ↓ this is projected into <ng-content> -->
  <h2>Order Summary</h2>
  <p>3 items · $42.00</p>
  <button>Checkout</button>
</app-card>

        

      

      

        Key rule: the projected content is created in the parent's context. Its bindings, change detection, and styles all belong to the parent — not the card shell. The shell just positions it.
      

    


    
    

      
Fallback (default) content

      
Put content inside the <ng-content> tags. It renders only when the parent projects nothing.

      
<ng-content>
  <!-- shown only when parent passes nothing -->
  <p class="empty-state">No content provided yet.</p>
</ng-content>

      

        Angular 18+: fallback content inside <ng-content> is now officially supported. In earlier versions it was silently ignored — use @if on a wrapper div instead.

Multi-slot projection: named selectors

      

        Add a select attribute to each <ng-content> to target specific elements. The selector is a CSS-style selector — attribute, class, element type, or combination.
      

      

        

          
Child template — 3 named slots

          
<div class="card">

  <!-- slot 1: match [slot="header"] attr -->
  <header>
    <ng-content select="[slot=header]">
    </ng-content>
  </header>

  <!-- slot 2: match any element -->
  <section class="body">
    <ng-content></ng-content>
  </section>

  <!-- slot 3: match .footer class -->
  <footer>
    <ng-content select=".footer">
    </ng-content>
  </footer>

</div>

        

        

          
Parent usage

          
<app-card>

  <!-- goes to slot 1 (matches [slot=header]) -->
  <h2 slot="header">
    Order Summary
  </h2>

  <!-- goes to slot 2 (the catch-all) -->
  <p>3 items · $42.00</p>
  <p>Ships in 2 days</p>

  <!-- goes to slot 3 (matches .footer) -->
  <button class="footer">
    Checkout
  </button>

</app-card>

        

      


      
      
Selector reference

      

        
select= valueMatchesExample parent HTML

        
          
[slot=header]Elements with slot="header" attribute<h2 slot="header">...</h2>

          
.footerElements with class="footer"<div class="footer">...</div>

          
app-iconThe <app-icon> element<app-icon name="star"></app-icon>

          
[header]Elements with a header attribute (any value)<span header>Title</span>

          
(none)Everything that didn't match a named slotCatch-all — always put last

        
      


      

        Order matters: Angular processes slots top to bottom. The catch-all <ng-content> with no select grabs everything the named slots didn't claim. Put it last.

ng-container — the invisible wrapper

      

        <ng-container> is a logical grouping element that produces zero DOM output. Angular removes it from the rendered HTML entirely — only its children appear. It exists purely to apply structural directives or group elements without polluting the DOM.
      

      

        

          
Problem: wrapping with <div>

          
<ul>
  <div *ngIf="show">  <!-- invalid! -->
    <li>Item A</li>
    <li>Item B</li>
  </div>
</ul>

          
Renders a <div> inside <ul> — invalid HTML. Also breaks CSS selectors that rely on direct li children.

        

        

          
Solution: <ng-container>

          
<ul>
  <ng-container *ngIf="show">
    <li>Item A</li>
    <li>Item B</li>
  </ng-container>
</ul>

          
Renders only the <li> elements when show=true. Zero wrapper in the DOM. Valid HTML.

        

      

    


    

      
Common use-cases

      

        

          
1. Multiple directives on one element

          
You can't put two structural directives on the same element. Wrap one in ng-container.

          
<!-- ERROR: two structural directives -->
<li *ngFor="let x of items"
    *ngIf="x.active">{{ x.name }}</li>

<!-- CORRECT: wrap outer in ng-container -->
<ng-container *ngFor="let x of items">
  <li *ngIf="x.active">{{ x.name }}</li>
</ng-container>

        

        

          
2. ngSwitch grouping

          
<ng-container [ngSwitch]="role">
  <app-admin    *ngSwitchCase="'admin'">
  </app-admin>
  <app-editor   *ngSwitchCase="'editor'">
  </app-editor>
  <app-viewer   *ngSwitchDefault>
  </app-viewer>
</ng-container>

        

        

          
3. ngTemplateOutlet host (see tab 5)

          
<ng-container
  [ngTemplateOutlet]="myTpl"
  [ngTemplateOutletContext]="{ $implicit: row }">
</ng-container>

          
No extra DOM element — the template stamps directly.

        

        

          
4. @if / @for (new control flow)

          
With Angular 17+ built-in control flow, ng-container is less needed — @if and @for don't add DOM nodes. But it's still useful for named slots.

          
<!-- ng-container as projection target -->
<app-tabs>
  <ng-container slot="tab1">
    <h3>First tab content</h3>
  </ng-container>
</app-tabs>

ngTemplateOutlet — stamping templates dynamically

      

        ngTemplateOutlet stamps an <ng-template> reference into the DOM. You can pass a template as an @Input() to a child component — the child decides where and when to render it. This is Angular's version of the "render prop" pattern from React.
      

      

        

          
1. Define a template with <ng-template>

          
<!-- parent template -->
<ng-template #myTpl let-item>
  <div class="custom-row">
    <strong>{{ item.name }}</strong>
    <span>{{ item.price | currency }}</span>
  </div>
</ng-template>

<!-- pass template to the child -->
<app-list
  [items]="products"
  [rowTemplate]="myTpl">
</app-list>

        

        

          
2. Child stamps it with ngTemplateOutlet

          
<!-- app-list.component.html -->
<ul>
  <li *ngFor="let item of items">
    <ng-container
      [ngTemplateOutlet]="rowTemplate"
      [ngTemplateOutletContext]="{ $implicit: item }">
    </ng-container>
  </li>
</ul>

<!-- app-list.component.ts -->
import { TemplateRef } from '@angular/core';
@Input() rowTemplate!: TemplateRef<any>;

        

      

      

        Context & $implicit: the context object passed via [ngTemplateOutletContext] is available in the template via let-varname. The special key $implicit binds to a bare let-item without a key.
      

    


    

      
Context variables — passing data back UP

      
<!-- Parent defines template that receives data FROM the child -->
<ng-template #myTpl
             let-row                   <!-- $implicit -->
             let-index="index"          <!-- named key -->
             let-total="total">         <!-- named key -->
  Row {{ index + 1 }} of {{ total }}: {{ row.label }}
</ng-template>

<!-- Child provides all the context variables -->
<ng-container
  [ngTemplateOutlet]="rowTemplate"
  [ngTemplateOutletContext]="{ $implicit: row, index: i, total: items.length }">
</ng-container>

      

        This is the render-prop pattern: the parent decides the markup, the child provides the data. Powerful for generic list, table, and tree components.

ngComponentOutlet — runtime component rendering

      

        ngComponentOutlet renders a component class at runtime — you pass the class reference and Angular instantiates it on the fly. No selector needed in the template. Used for plugin systems, dynamic widget dashboards, and form-builder UIs.
      

      
// parent.component.ts
import { NgComponentOutlet } from '@angular/common';
import { AlertComponent, BannerComponent, CardComponent } from './widgets';

@Component({
  standalone: true,
  imports: [NgComponentOutlet],
  template: `
    <ng-container [ngComponentOutlet]="activeWidget" />
    <button (click)="rotate()">Next widget</button>
  `
})
export class DashboardComponent {
  widgets = [AlertComponent, BannerComponent, CardComponent];
  idx = signal(0);
  activeWidget = computed(() => this.widgets[this.idx()]);
  rotate() { this.idx.update(i => (i + 1) % this.widgets.length); }
}


      
Passing inputs with ngComponentOutletInputs (Angular 16+)

      
<ng-container
  [ngComponentOutlet]="activeWidget"
  [ngComponentOutletInputs]="{ title: 'Hello', severity: 'warn' }">
</ng-container>

      

        Before Angular 16, you needed ViewContainerRef + createComponent() to pass inputs. Now ngComponentOutletInputs handles it declaratively.

ContentChild & ContentChildren

      

        @ContentChild and @ContentChildren let a parent component query projected content — the children that were slotted into its <ng-content>. This is different from @ViewChild, which queries elements in the component's own template.
      

      

        

          
@ContentChild — one match

          
// tab-group.component.ts
import { ContentChild, AfterContentInit } from '@angular/core';

@Component({ selector: 'app-tab-group', ... })
export class TabGroupComponent
    implements AfterContentInit {

  // queries the first projected TabLabelComponent
  @ContentChild(TabLabelComponent)
  label!: TabLabelComponent;

  ngAfterContentInit() {
    // safe to access projected content here
    console.log(this.label.text);
  }
}

        

        

          
@ContentChildren — all matches

          
import { ContentChildren, QueryList } from '@angular/core';

@Component({ selector: 'app-tab-group', ... })
export class TabGroupComponent
    implements AfterContentInit {

  // queries ALL projected TabComponent instances
  @ContentChildren(TabComponent)
  tabs!: QueryList<TabComponent>;

  ngAfterContentInit() {
    // QueryList is iterable and has changes$ observable
    this.tabs.forEach(tab => tab.init());

    this.tabs.changes.subscribe(() => {
      console.log('tabs changed', this.tabs.length);
    });
  }
}

        

      

    


    

      
ViewChild vs ContentChild — the critical difference

      

        
DecoratorSearches in...Available fromUse for

        
          
@ViewChildComponent's own templatengAfterViewInitDOM refs, child components defined in THIS template

          
@ContentChildProjected content (what parent passed in)ngAfterContentInitComponents/directives projected via <ng-content>

          
@ViewChildrenComponent's own template (all matches)ngAfterViewInitLists of child components/directives

          
@ContentChildrenProjected content (all matches)ngAfterContentInitDynamic lists like tabs, accordion panels

        
      


      
Real-world: building a tab group

      
// tab.component.ts — the projected child
@Component({
  selector: 'app-tab',
  standalone: true,
  template: `<ng-content *ngIf="active"></ng-content>`
})
export class TabComponent {
  @Input() label = '';
  active = false;
}

// tab-group.component.ts — the shell that queries them
@Component({
  selector: 'app-tab-group',
  standalone: true,
  template: `
    <nav>
      <button *ngFor="let t of tabs" (click)="activate(t)">{{ t.label }}</button>
    </nav>
    <ng-content></ng-content>
  `
})
export class TabGroupComponent implements AfterContentInit {
  @ContentChildren(TabComponent) tabs!: QueryList<TabComponent>;

  ngAfterContentInit() {
    this.tabs.first.active = true; // activate first tab
  }
  activate(tab: TabComponent) {
    this.tabs.forEach(t => t.active = false);
    tab.active = true;
  }
}

// Usage in parent
<app-tab-group>
  <app-tab label="Overview">Overview content here</app-tab>
  <app-tab label="Details">Details content here</app-tab>
</app-tab-group>

    


    

      
Signal-based queries (Angular 17.2+)

      
// Modern signal-based equivalent
import { contentChild, contentChildren } from '@angular/core';

export class TabGroupComponent {
  // Returns a Signal<TabComponent | undefined>
  firstTab = contentChild(TabComponent);

  // Returns a Signal<readonly TabComponent[]>
  allTabs = contentChildren(TabComponent);

  // No ngAfterContentInit needed — signals are always current
  activeLabel = computed(() => this.firstTab()?.label ?? 'none');
}

      

        Signal queries don't need lifecycle hooks. The signal value updates automatically when projected content changes, and it works with computed() and effect().
      

    

  


  
  

    

      
Common Gotchas & Best Practices


      
1. OnPush and projected content

      

        Problem: if the shell component uses ChangeDetectionStrategy.OnPush, projected content is still checked — but in the parent's change detection cycle, not the shell's. The shell only re-checks when its own inputs change. This can cause projected bindings to appear stale.
      

      
@Component({
  changeDetection: ChangeDetectionStrategy.OnPush,
  template: `<ng-content></ng-content>`
})
export class ShellComponent {}

// Parent template
<app-shell>
  {{ parentService.liveData }}  <!-- ✅ updates via PARENT's CD, not shell's -->
</app-shell>

      
The projected content's change detection belongs to the parent. OnPush on the shell doesn't block parent CD from updating it.


      
2. CSS encapsulation and ::ng-deep

      

        ::ng-deep is deprecated (but still widely used). It punches through Angular's view encapsulation to style projected content from inside the shell. Avoid it — prefer passing CSS classes via @Input() or using ViewEncapsulation.None on the shell.
      

      

        

          
Avoid: ::ng-deep

          
/* shell.component.css */
::ng-deep .projected-title {
  color: red;  /* leaks globally! */
}

        

        

          
Prefer: pass a class input

          
// shell.component.ts
@Input() titleClass = '';

<!-- template -->
<div [class]="titleClass">
  <ng-content select="[title]"></ng-content>
</div>

        

      


      
3. Content projection is not re-projected

      

        If component A projects into B, and B has its own <ng-content> pointing outward to C — that doesn't work automatically. Each <ng-content> is a one-hop slot. To re-project, you'd need B to explicitly use ngTemplateOutlet or restructure the components.
      


      
4. Projected content instantiates in the parent

      
// ParentComponent template:
<app-card>
  <expensive-widget [data]="bigDataset"></expensive-widget>
</app-card>

// ExpensiveWidget is always created — even if app-card hides ng-content with *ngIf.
// Use ngTemplateOutlet + @defer if you need lazy instantiation.

      
The projected content is created when the parent is created — regardless of whether the shell's <ng-content> is hidden. If you need truly lazy projection, pass a template reference and use ngTemplateOutlet inside an @defer block.
