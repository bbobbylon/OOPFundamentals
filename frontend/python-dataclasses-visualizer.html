Python: Dataclasses

The @dataclass decorator generates __init__/__repr__/__eq__ for you — plus field() defaults, frozen immutability, ordering, and how it compares to NamedTuple, TypedDict, and Pydantic.

📦 Stop hand-writing __init__ and __repr__ — let @dataclass generate them

A dataclass (from dataclasses import dataclass) turns a class of type-annotated attributes into a full value object by generating the boilerplate: __init__, a readable __repr__, and a field-by-field __eq__. Defaults work normally, but a mutable default (roles: list = []) is a deliberate error — use field(default_factory=list) for a fresh list per instance. Options add power: frozen=True (immutable + hashable), order=True, slots=True. Dataclasses don't validate types at runtime — for untrusted API input you reach for Pydantic.

  • Generates __init__/__repr__/__eq__ from annotated fields.
  • Mutable defaults are an error — use field(default_factory=list).
  • frozen=True = immutable + hashable (dict key / set member); __post_init__ validates.
  • It doesn't validate types — that's Pydantic's job at the API boundary.

Before vs after

# by hand: class User: def __init__(self, id, email): self.id = id; self.email = email def __repr__(self): ... def __eq__(self, o): ... # with dataclass: @dataclass class User: id: int email: str # __init__/__repr__/__eq__ generated

The mutable-default trap

@dataclass class Acct: roles: list = [] # ❌ ValueError! @dataclass class Acct: roles: list[str] = field( default_factory=list) # ✅ fresh list # default_factory runs per instance

dataclass vs Java record

Java: record User(int id, String email) {} — immutable, final, generates ctor/equals/hashCode/accessors. Python: @dataclass(frozen=True) is the closest equivalent (immutable + hashable). A mutable @dataclass is more like a Lombok @Data POJO. Neither validates types at runtime — that's Pydantic's job (≈ Bean Validation / @Valid).

CIAM context: Model an internal Principal or decoded AccessToken as a @dataclass(frozen=True) — immutable (no layer mutates identity mid-request) and hashable (cache it, set-member it) — with field(default_factory=list) for roles and __post_init__ to check exp. But the inbound token payload and request bodies should be Pydantic models, since those need real runtime validation of untrusted input.

1. @dataclass Generates the Boilerplate

from dataclasses import dataclass

@dataclass
class User:
  id: int
  email: str
  active: bool = True # default like a param

u = User(1, "a@b.com")
u # User(id=1, email='a@b.com', active=True)
u == User(1, "a@b.com") # True (field-by-field __eq__)

The decorator reads the class's type annotations and synthesizes __init__ (params in declaration order), __repr__ (the nice User(...) form), and __eq__ (compares all fields). Fields with defaults must follow fields without — same rule as function parameters. The annotations are not enforced at runtime: User("oops", 2) happily constructs — annotations are hints for tools like mypy, not validators.

A bare annotation defines a field; assigning a value defines a default. id: int is a required field; active: bool = True is an optional one. A class-level assignment without an annotation (x = 5) is NOT a field — it's an ordinary class attribute the dataclass ignores.

2. field(): Defaults, Factories, and __post_init__

from dataclasses import dataclass, field

@dataclass
class Account:
  email: str
  roles: list[str] = field(default_factory=list)
  id: str = field(init=False, default="")
  def __post_init__(self):
    self.id = sha(self.email) # derived field
    if "@" not in self.email: raise ValueError

default_factory runs once per instance, the correct way to give each object its own mutable default (list/dict/set). field(init=False) keeps a field out of __init__ (you set it in __post_init__); repr=False/compare=False exclude a field from those dunders (e.g. hide a secret from repr). __post_init__ runs right after the generated __init__ — the place for validation and computed fields.

The mutable-default error is a feature. roles: list = [] raises ValueError: mutable default at class-definition time — dataclasses refuse it precisely because a shared default list (the infamous mutable-default-argument bug) would silently leak state across instances. default_factory=list is the enforced, correct alternative.

3. frozen (Immutable + Hashable) and order

@dataclass(frozen=True, order=True)
class Point:
  x: int
  y: int

p = Point(1, 2)
p.x = 9 # FrozenInstanceError
{p} # works — frozen ⇒ hashable
Point(1,2) < Point(1,3) # True (order ⇒ __lt__…)

frozen=True makes assignment raise FrozenInstanceError and auto-generates __hash__, so instances can be dict keys or set members (a mutable dataclass is unhashable by default). order=True generates __lt__/__le__/__gt__/__ge__ that compare fields as a tuple, in order. slots=True (3.10+) adds __slots__ — less memory, faster attribute access, but no new attributes and some multiple-inheritance caveats.

"Modify" a frozen instance with dataclasses.replace: p2 = replace(p, y=5) returns a new instance with one field changed — the immutable-update pattern (like a copy-with). Combined with frozen=True, this gives you safe, shareable value objects.

4. Pick the Right Tool

UseWhen
@dataclassinternal mutable value object; you control the inputs; no runtime validation needed
@dataclass(frozen=True)immutable, hashable value object (cache keys, set members, shared identity)
NamedTuplelightweight immutable record that's also a tuple (indexable, unpackable)
TypedDicttype hints for a plain dict shape (JSON-ish data, no instance/methods)
Pydantic BaseModeluntrusted input at an API/IdP boundary — runtime validation + coercion + JSON
The decision hinges on validation. Dataclasses (and NamedTuple/TypedDict) trust their annotations — they never check types at runtime. The moment data crosses a trust boundary (an HTTP body, a token from an IdP, a config file), use Pydantic so a wrong type or missing field is a clean validation error, not a deep-in-the-code crash later.
