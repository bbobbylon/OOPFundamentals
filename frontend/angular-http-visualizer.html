HTTP & Interceptors

How Angular talks to APIs — HttpClient, the interceptor pipeline (auth, logging, caching, error handling), and the patterns every real app needs.

🌐 What is HttpClient? Why not just use fetch()?

You could use the browser's native fetch() in Angular and it would work — but HttpClient gives you three things fetch doesn't. It returns a typed Observable<T> (so you get RxJS operators, cancellation, and subscription management for free); it runs every request through an interceptor pipeline where you inject cross-cutting behaviour (auth headers, retries, logging, caching) in one place; and it's trivially testable with HttpTestingController.

  • http.get<User[]>('/api/users') returns a cold Observable — nothing fires until you subscribe (or the async pipe does it for you).
  • Interceptors are middleware: a request flows down the chain (each may clone & modify it), hits the network, and the response flows back up in reverse.
  • Because it's an Observable you compose it — retry(), catchError(), switchMap(), timeout() — and cancel it by unsubscribing.
  • Type the response with <T> and Angular hands back a typed object; pair it with generated OpenAPI models to kill drift.
  • Test with HttpTestingController: assert the outgoing request, flush a fake response, no real network needed.

What interceptors do

  • Add Authorization: Bearer …
  • Log request timing / status
  • Retry on 5xx / network error
  • Cache GET responses
  • 401 → refresh token → retry

The interceptor pipeline

A request flows DOWN through every interceptor (each can modify it), then hits the network; the response flows back UP in reverse. Each calls next(req) to pass it along, or short-circuits (e.g. a cache hit) by returning its own response.

Core CIAM pattern:one authInterceptor adds the Bearer token to every API request, detects a 401, calls refreshTokens(), and retries the original request with the new token — transparently. No component code knows any of this happens.

or, retrying a request doesn't rewind you through the interceptors that built it

The problem

The refresh call succeeded. The retry still failed with 401.

auth.refreshTokens() returns 200 with a brand-new token. The very next request still gets rejected

A CIAM app's error interceptor tries to handle a 401 reactively, right where it happens, instead of only redirecting to login: export const errorInterceptor: HttpInterceptorFn = (req, next) => { const auth = inject(AuthService); return next(req).pipe(catchError(err => { if (err.status === 401) { return auth.refreshTokens().pipe(switchMap(() => next(req))); } return throwError(() => err); })); }; — this looks reasonable: catch the 401, refresh, retry with next(req). In the network tab, auth.refreshTokens() genuinely returns a fresh access token with a 200. The very next request — the retry — gets a second 401. Not a fluke: it gets one every single time, because req is the exact same HttpRequest object that arrived at this interceptor already carrying the OLD Authorization header, cloned in by authInterceptor upstream, long before the token expired. Retrying with next(req) doesn't ask authInterceptor to run again and re-clone with the new token — it just resends the identical frozen object, stale header and all.

auth.refreshTokens() → 200 ✓ new token stored ✓ retry sent ✓ retry status: 401 ⚠

The refresh worked. The retry never saw it — because the retry was never given the chance to.

If you retry from inside an interceptor, YOU own re-attaching the new token — next() won't do it for you
switchMap(() => next(req)) — retries with whatever req already was ↓ req was cloned ONCE, upstream, before the failure; calling next() again doesn't reach back up and re-clone it Better: clone again, with the token refreshTokens() just handed you ↓ switchMap(newToken => next(req.clone({ setHeaders: { Authorization: `Bearer ${newToken}` } }))) Now the retry is a genuinely different request, not a resend of the one that just failed
next(req) never re-runs anything upstream of the interceptor that calls it. An interceptor chain is built once and walked top-to-bottom on the way in; calling next() a second time — from inside a catchError, a retry(), or anywhere else — only resends whatever request object you hand it. It does not rewind execution back to authInterceptor, and it does not magically pick up state that changed after the request was originally cloned. If you want a different request on retry, you have to build one yourself.
Think of the request object as a sealed envelope, not a live phone line back to whoever wrote the letter. authInterceptor sealed it once, with whatever token was current at that moment inside. Handing that exact envelope to a second courier — which is all next(req) ever does — doesn't change what's inside it, no matter how many couriers you hand it to or how many times you ask. Getting different contents into the envelope means someone has to seal a new one.
You

I refreshed the token right before retrying. Why did the retry get a 401 too?

next(req)

Because you handed me the same req you already had — the one authInterceptor cloned with the OLD token, back before any of this happened. I don't inspect what's inside it. I don't compare it to what a fresh request would look like. I just send it.

You

So the refresh call was pointless?

next(req)

No — it got you a good token, sitting in the auth service right now. It just never made it into this request, because nothing told me to clone a new one. Refreshing the token and attaching the token are two different jobs, and you only did the first one.

The mechanism

One request object, cloned once, retried unchanged.

  1. The component calls http.get('/api/orders'). HttpClient builds a fresh HttpRequest and walks it through the interceptor chain, starting at authInterceptorthe only time the chain runs top-to-bottom
  2. authInterceptor reads the current token and calls req.clone({ setHeaders: { Authorization: 'Bearer <old-token>' } }) — this produces ONE new, immutable request object. Call it reqAreqA now exists, frozen, forever
  3. reqA reaches errorInterceptor via next(reqA), goes to the network, and comes back 401 — the token expired between page load and this callthe failure that triggers everything below
  4. catchError runs auth.refreshTokens(), which succeeds and stores a new token somewhere the AuthService can read — but nobody has asked for a new HttpRequest yetthe token is fixed; the request object isn't
  5. switchMap(() => next(reqA)) fires — reqA, the exact same object from step 2, old Authorization header baked in, unchangedthis is the bug: reqA, not a new clone
  6. The server checks the Authorization header it actually received — still the expired one — and returns 401 again. authInterceptor is never called a second time to fix it, because nothing re-entered the chain from the topfixable only by cloning again, explicitly, right here

Step 5 is the whole lesson. "Retry" sounds like it means "try again, freshly" — but every retry pattern on this page, from a component-level retry() to a catchError inside an interceptor, only ever resends an object that already exists. If nothing about that object has changed, neither has the outcome.

REQUEST SENT (reqA, old token) server checks the Authorization header, finds it expired → 401 RECEIVED
401 RECEIVED catchError runs auth.refreshTokens() → TOKEN REFRESHED
TOKEN REFRESHED (new token stored — but reqA still exists, unchanged) switchMap(() => next(reqA)) resends the SAME object → REQUEST RESENT
REQUEST RESENT (still reqA, still the old token) server checks the header again, finds the same expired value → back to 401 RECEIVED

Without a guard, this cycle repeats — refreshing a token successfully every time and still failing every time, because the one thing never happening is a NEW clone of the request. Break the cycle at the marked step: next(req.clone({ setHeaders: { Authorization: ... } })), not next(req).

An interceptor runs: return next(req).pipe(retry(2), catchError(err => { if (err.status === 401) { return auth.refreshTokens().pipe(switchMap(() => next(req))); } return throwError(() => err); })); The first call gets a 401. refreshTokens() succeeds and the AuthService now holds a valid new token. What does the retried request's Authorization header actually contain?

Exactly. req is a specific, already-built HttpRequest object — its headers were fixed the moment an upstream interceptor cloned it, long before this 401 happened. next(req) just resends that object; it has no way to reach back and ask for a different one, no matter what AuthService holds now.

Tempting — it feels like "wait for the refresh, then use the new state" should work, and switchMap genuinely does wait for refreshTokens() to complete first. But waiting for the token to update somewhere else doesn't change what's already baked into req's headers. AuthService holding a new token and req carrying an old one are two separate facts, and only one of them got updated here.

There's no such stripping behavior — RxJS operators don't inspect or rebuild HttpRequest objects. req.clone() is the only thing that ever changes a request's headers, and this code never calls it a second time. Whatever headers req had going in are exactly what it has coming back out.

Where you've seen this before

Three systems, one shape: "retry" replays an object instead of rebuilding one.

Axios interceptors hit the identical wall

Axios's response-interceptor pattern for 401-refresh-retry is one of the most repeated "why is this looping" questions in that ecosystem: error.config — the original Axios request config — carries the same stale Authorization header unless you explicitly overwrite error.config.headers.Authorization before calling axios(error.config) again. Different library, identical trap: the retry vehicle is the OLD request, not a new one, unless you touch it yourself.

error.config ≈ Angular's req

Your browser's own "confirm form resubmission" warning

Refresh a page you reached via POST and the browser offers to resend the exact same request — same body, same headers, same CSRF token — because that's literally all a "resend" ever means at the HTTP layer: replaying a byte-for-byte identical request. If the session or CSRF token has rotated since, the resend fails for the same reason a stale-token retry does: nothing rebuilds the request, it just gets sent again.

"resend" always means the SAME bytes

Your silent-refresh interceptor, the day the IdP rotates signing keys

A Ping/Entra silent-refresh flow that retries a failed call the way the buggy version above does won't just fail once — it fails on every retry, for every user, the instant tokens issued before a signing-key rotation stop validating. The refresh call itself succeeds every time (it's hitting a healthy IdP with valid credentials); the retried API call fails every time, because it's still carrying a token minted under the old key. Support sees "intermittent 401s that a refresh doesn't fix" — the fix is never on the refresh side; it's always in whether the retried request was actually rebuilt.

refresh succeeds, retry still dies
Questions from the back row

Doesn't RxJS's retry() solve this automatically?

No — retry() only resubscribes to the Observable it's piped onto. If that Observable is next(req) called with a fixed req, every resubscription sends that same req again. retry() is great for "the network blipped, try the identical call again" (a 503, a timeout) — it was never designed to rebuild the request in between attempts.

So where should 401-refresh-and-retry actually live?

Either proactively, before the request ever goes out — check expiry, refresh if needed, then clone with whatever token you end up with, the pattern this page's own CIAM interceptor uses — or reactively in catchError, as long as you explicitly req.clone() with the new token before calling next() again. Either is fine. Calling next(req) unchanged is the only version that's broken.

How would this actually surface in production, versus in a quick manual test?

You might not catch it manually at all — if you test by refreshing the page, you get a brand-new authInterceptor pass with a valid token and everything looks fine. It only shows up for a session that's been open long enough for the original token to expire mid-session, which is exactly the case automated refresh-and-retry exists to handle — so the bug hides until the one moment it's supposed to matter.

1. The basics — HttpClient

Inject HttpClient, call get / post / put / delete — you get back an Observable. Always subscribe (or use the async pipe).

// app.config.ts — register HttpClient at the app root
import { provideHttpClient } from '@angular/common/http';

export const appConfig: ApplicationConfig = {
  providers: [
    provideHttpClient()                          // modern standalone API (v15+)
  ]
};
// user.service.ts
import { HttpClient } from '@angular/common/http';
import { Observable } from 'rxjs';   // every HttpClient method RETURNS one of these — it's the type below, not a class you construct

interface User { id: number; name: string; email: string; }   // the shape every method below is typed against

@Injectable({ providedIn: 'root' })
export class UserService {
  private http = inject(HttpClient);   // the functional inject() — no constructor needed
  private base = '/api/users';   // one URL constant, reused by every method below instead of repeated string literals

  // Type the response — HttpClient is generic
  getAll(): Observable<User[]> {
    return this.http.get<User[]>(this.base);   // the <User[]> tells TS what shape .subscribe(users => ...) will receive — it does NOT validate the response at runtime
  }

  getOne(id: number): Observable<User> {
    return this.http.get<User>(`${this.base}/${id}`);   // template literal builds "/api/users/{id}"
  }

  create(user: Partial<User>): Observable<User> {   // Partial<User> — caller need not supply every field (no id yet, e.g.)
    return this.http.post<User>(this.base, user);   // 2nd arg = body, auto-JSON
  }

  update(id: number, user: Partial<User>): Observable<User> {
    return this.http.put<User>(`${this.base}/${id}`, user);   // same URL-building pattern as getOne, body goes second
  }

  remove(id: number): Observable<void> {   // void — a delete has no meaningful response body to type
    return this.http.delete<void>(`${this.base}/${id}`);
  }
}

None of these five methods do anything until something calls .subscribe() on them — Angular's HttpClient observables are cold. Call getAll() and never subscribe, and Angular never even opens the HTTP connection. The three calling patterns right below this block are exactly the three ways to make that subscription happen.

// Calling from a component — three ways

// 1) Subscribe manually (verbose, must unsubscribe)
this.userService.getAll().subscribe(users => this.users = users);

// 2) async pipe in template (recommended — auto-unsubscribes)
users$ = this.userService.getAll();
// template: @for (u of users$ | async; track u.id) { ... }

// 3) Signals (v16+) — convert Observable to signal
import { toSignal } from '@angular/core/rxjs-interop';
users = toSignal(this.userService.getAll(), { initialValue: [] });
// template: @for (u of users(); track u.id) { ... }

2. Query params & custom headers

import { HttpParams, HttpHeaders } from '@angular/common/http';

search(q: string, page: number) {
  // HttpParams is IMMUTABLE — each .set() returns a new instance
  const params = new HttpParams()
    .set('q', q)   // this call does NOT mutate params — it returns a NEW HttpParams you must chain off
    .set('page', page);
  // → ?q=foo&page=2 (auto-URL-encoded)

  const headers = new HttpHeaders({
    'X-Trace-Id': crypto.randomUUID(),   // a fresh id per request — handy for correlating logs across services
    'Accept-Language': 'en-US'
  });

  return this.http.get<SearchResult>('/api/search', { params, headers });   // both ride in the SAME options object as the 2nd argument
}

// Shortcut: pass params/headers as plain objects (v15+)
this.http.get('/api/search', { params: { q, page } });   // HttpClient builds the HttpParams for you — less ceremony for the common case

3. Interceptors — functional (v15+, modern)

Interceptors are functions (req, next) => next(req). They can:

  • Modify the request before it leaves (add headers, change URL)
  • Short-circuit it (return a cached response without hitting the network)
  • Tap the response (logging, analytics)
  • Handle errors (retry, redirect to login, show a toast)
// auth.interceptor.ts
import { HttpInterceptorFn } from '@angular/common/http';   // a TYPE — describes the (req, next) => Observable shape below
import { inject } from '@angular/core';   // needed because a plain function has no constructor to DI into

export const authInterceptor: HttpInterceptorFn = (req, next) => {   // req = the outgoing request, next = call this to continue the chain
  const auth = inject(AuthService);   // works here because Angular calls this function inside an injection context
  const token = auth.getToken();

  // Skip for login endpoint, or for public routes
  if (!token || req.url.includes('/auth/login')) {
    return next(req);   // pass the ORIGINAL request through unchanged
  }

  // Clone the request — requests are immutable
  const authReq = req.clone({   // req itself can never be mutated — clone() makes a modified copy
    setHeaders: { Authorization: `Bearer ${token}` }
  });
  return next(authReq);   // pass the CLONED, now-authorized request onward instead
};
// logging.interceptor.ts — tap on response, time the request
import { tap, finalize } from 'rxjs';

export const loggingInterceptor: HttpInterceptorFn = (req, next) => {
  const start = performance.now();   // captured BEFORE the request is sent
  console.log(`→ ${req.method} ${req.url}`);

  return next(req).pipe(
    finalize(() => {   // finalize runs on success AND error, unlike tap's next-only callback
      const ms = (performance.now() - start).toFixed(0);   // elapsed time, now that the response (or error) has arrived
      console.log(`← ${req.method} ${req.url} (${ms}ms)`);
    })
  );
};
// cache.interceptor.ts — return cached response for GETs
import { HttpResponse } from '@angular/common/http';
import { of, tap } from 'rxjs';

const cache = new Map<string, HttpResponse<any>>();   // module-level — lives for the app's lifetime, shared by every call

export const cacheInterceptor: HttpInterceptorFn = (req, next) => {
  if (req.method !== 'GET') return next(req);   // only cache GETs

  const cached = cache.get(req.urlWithParams);   // urlWithParams — different query strings are DIFFERENT cache keys
  if (cached) return of(cached.clone());        // short-circuit! next() is never called — no network request happens

  return next(req).pipe(
    tap(event => {   // tap observes without transforming — the response still flows through unchanged
      if (event instanceof HttpResponse) {   // HttpClient emits several event TYPES when observe:'events'; this filters to the final response
        cache.set(req.urlWithParams, event.clone());   // store a copy so the NEXT matching request hits the branch above
      }
    })
  );
};
// error.interceptor.ts — retry on 5xx, redirect to login on 401
import { catchError, retry, throwError, timer } from 'rxjs';
import { HttpErrorResponse } from '@angular/common/http';

export const errorInterceptor: HttpInterceptorFn = (req, next) => {
  const router = inject(Router);
  const toast  = inject(ToastService);

  return next(req).pipe(
    retry({
      count: 3,   // up to 3 additional attempts before giving up
      delay: (err, retryCount) => {   // a FUNCTION, not a fixed number — lets retry logic decide per-error
        // Only retry network/5xx, exponential backoff
        if (err.status >= 500 || err.status === 0) {   // status 0 = the request never reached the server (network down, CORS, etc.)
          return timer(Math.pow(2, retryCount) * 300);   // returning a timer() observable is retry's signal to WAIT then re-subscribe
        }
        return throwError(() => err);   // any other status (4xx) — give up immediately, don't retry a bad request
      }
    }),
    catchError((err: HttpErrorResponse) => {   // runs once retry has exhausted its attempts (or didn't retry at all)
      if (err.status === 401) router.navigate(['/login']);
      else if (err.status === 403) toast.error('Forbidden');
      else toast.error(`Error ${err.status}: ${err.message}`);
      return throwError(() => err);                // re-throw so component can react
    })
  );
};

Notice the ORDER inside .pipe(): retry runs first and catchError last. catchError only ever sees an error that retry gave up on — it's the final backstop, not a competing handler.

// Register them — ORDER MATTERS. Outer interceptors wrap inner ones.
// Request flows top → bottom. Response flows bottom → top.
import { provideHttpClient, withInterceptors } from '@angular/common/http';

provideHttpClient(
  withInterceptors([
    authInterceptor,      // 1st: add token
    loggingInterceptor,   // 2nd: log timing (sees the auth'd request)
    cacheInterceptor,     // 3rd: check cache
    errorInterceptor      // last: retry / catch (closest to network)
  ])
)
Order tip: put auth early (so all subsequent interceptors see the token) and error/retry last (so retries get a fresh token each attempt). Cache should usually sit between auth and error.

4. Class-based interceptors (legacy, pre-v15)

You'll still see these in older codebases. Same logic, more boilerplate.

@Injectable()
export class AuthInterceptor implements HttpInterceptor {
  intercept(req: HttpRequest<any>, next: HttpHandler) {
    // same as functional, but `this` is a class instance
    return next.handle(req.clone({ /* ... */ }));
  }
}

// register via DI multi-provider:
{ provide: HTTP_INTERCEPTORS, useClass: AuthInterceptor, multi: true }

For new code, use functional. For old code, leave it alone — both work side-by-side via withInterceptorsFromDi().

5. Common patterns

Loading spinner

An interceptor increments a counter on request start, decrements on end. A signal exposes isLoading; a global spinner reads it.

Request deduplication

If three components ask for the same URL in the same tick, share one HTTP call. Use shareReplay(1) in your service.

Stale-while-revalidate

Return cached value immediately, then fetch fresh in the background and update. Pair with a BehaviorSubject.

Cancellation

Use switchMap on user input — when a new value arrives, the in-flight request is auto-cancelled.

Optimistic updates

Update local state immediately, fire the request, roll back on error. Pairs nicely with NgRx + Effects.

File uploads

Use FormData as the body; subscribe with reportProgress: true + observe: 'events' for upload progress.

7. HttpContext — talk to interceptors per-request

Sometimes one request needs different interceptor behavior (skip auth, skip cache, etc.). Use HttpContextToken.

// tokens.ts
export const SKIP_AUTH = new HttpContextToken<boolean>(() => false);
export const CACHE_TTL_MS = new HttpContextToken<number>(() => 60000);

// auth.interceptor.ts
if (req.context.get(SKIP_AUTH)) return next(req);

// caller — opt out of auth for this one call
this.http.get('/api/public', {
  context: new HttpContext().set(SKIP_AUTH, true)
});

Anti-patterns

❌ Don't✅ Do
Mutate req directlyreq.clone({ ... }) — requests are immutable
Forget to subscribeObservables are cold — nothing fires until subscribed (or piped through | async)
Subscribe in template + serviceOne source of truth — users$ in service, | async in template
Catch errors only at call siteUse an error interceptor for global handling (toasts, redirects); catch locally only for component-specific recovery
Put business logic in interceptorsInterceptors are cross-cutting (auth, log, cache). Business logic belongs in services.
Forget to unsubscribeUse | async, toSignal, or takeUntilDestroyed() (v16+)
The mental model: HttpClient is just an Observable factory. Interceptors are a pipeline of (req, next) => Observable<event> functions wrapped around it. Auth, logging, cache, retry, error mapping — all live in interceptors so your services stay clean.

8. Error handling — retry, global interceptor, typed errors

Retry with exponential backoff

import { retry, timer } from 'rxjs';

// Retry up to 3 times, delay 1s/2s/4s
this.http.get<User[]>('/api/users').pipe(
  retry({
    count: 3,
    delay: (err, attempt) =>   // attempt starts at 1, so pow(2,1)=2s... wait: 2^1*1000=2s, 2^2*1000=4s — doubles each time
      timer(Math.pow(2, attempt) * 1000)
  })
).subscribe(...);   // this is CALL-SITE retry — only affects this one request

// In an interceptor: retry transient errors only
return next(req).pipe(
  retry({
    count: 2,
    delay: (err) => {   // this version applies GLOBALLY, to every request through the pipeline
      if (err instanceof HttpErrorResponse
          && err.status >= 500) {
        return timer(1000); // retry server errors
      }
      throw err; // don't retry 4xx
    }
  })
);

Same retry({ delay }) shape, two different SCOPES: the top snippet opts one component's one call into backoff; the bottom snippet, living in an interceptor, applies it to every request that flows through the app — decide per call vs. decide once, globally.

Global error interceptor — toasts + 401 redirect

export const errorInterceptor: HttpInterceptorFn =
  (req, next) =>
    next(req).pipe(
      catchError((err: HttpErrorResponse) => {   // catches ANY failed request from ANY service in the app
        const toast = inject(ToastService);   // injected inside the callback — still a valid injection context here
        const router = inject(Router);

        switch (err.status) {   // one place that decides what EVERY HTTP failure in the app looks like to the user
          case 0:   // status 0 — no response at all (offline, CORS blocked, DNS failure)
            toast.error('Network error'); break;
          case 401:
            // token expired — silent refresh handles it
            // or redirect if refresh also fails
            router.navigate(['/login']); break;
          case 403:   // authenticated but not ALLOWED — different from 401 (not authenticated at all)
            toast.error('Permission denied'); break;
          case 503:
            toast.error('Service unavailable'); break;
          default:   // anything not explicitly handled above still gets SOME feedback, never silently swallowed
            toast.error(err.message);
        }
        return throwError(() => err);   // still re-throws — this interceptor NOTIFIES the user, it doesn't decide the call succeeded
      })
    );
Rule: Handle component-specific recovery (show an empty state, hide a spinner) at the call site with catchError. Handle cross-cutting responses (toast, redirect, logging) in the error interceptor. Don't duplicate both.

9. CIAM bearer token interceptor — full implementation

In a CIAM app (Ping / Entra) the one job of an HTTP interceptor is to attach the access token as a Bearer header to every protected API call, skip it for public routes, and kick off silent refresh when the token is expired. The functional interceptor pattern makes this clean:

// auth.interceptor.ts
export const authInterceptor: HttpInterceptorFn = (req, next) => {
  const auth   = inject(AuthService);
  const skipAuth = req.context.get(SKIP_AUTH); // public endpoints opt out

  if (skipAuth || !req.url.startsWith('/api')) {   // the path-prefix check the security note below warns you to keep tight
    return next(req);         // public route — no token
  }

  const token = auth.getAccessToken(); // reads from memory/cookie

  if (auth.isTokenExpired(token)) {   // checked BEFORE sending — cheaper than waiting for a 401 to come back
    // token expired — refresh first, then retry with new token
    return auth.refreshTokens().pipe(
      switchMap(newToken => next(addBearer(req, newToken))),   // only proceed with the ORIGINAL request once refresh resolves
      catchError(() => {
        auth.logout();                  // refresh failed → force login
        return throwError(() => new Error('Session expired'));
      })
    );
  }

  return next(addBearer(req, token));   // the common case — token is valid, attach and go
};

// helper — clone request with Authorization header (requests are immutable)
function addBearer(req: HttpRequest<unknown>, token: string) {   // a plain function, not exported — private to this file
  return req.clone({
    setHeaders: { Authorization: `Bearer ${token}` }
  });
}

// register it (app.config.ts)
provideHttpClient(withInterceptors([authInterceptor, errorInterceptor]))   // auth runs first, then error handling — a 401 from a mid-flight token still gets caught
Security note: The interceptor attaches the token to /api/* calls. Verify the path prefix matches your API base URL — never send the Bearer header to third-party URLs or CDN calls (the token would leak). Use HttpContextToken for precise opt-in/opt-out on individual requests.

10. httpResource() — Angular 19 signal-based HTTP

httpResource() is Angular 19's signal-native HTTP primitive. It wraps an HTTP GET into a Resource — a signal that carries value(), isLoading(), error(), and status() — no subscribe(), no async pipe needed.

Basic usage

import { httpResource } from '@angular/core';   // note the source — a core primitive, not from @angular/common/http

export class UserListComponent {
  // GET /api/users — auto-fetches on init
  users = httpResource<User[]>(   // no inject(HttpClient), no .subscribe() — the resource IS the field
    '/api/users'
  );
}

<!-- template -->
@if (users.isLoading()) { <app-spinner/> }   <!-- isLoading() is a SIGNAL call, re-evaluated automatically as the fetch progresses -->
@if (users.error()) { <p>Error loading</p> }   <!-- error() holds whatever the failed fetch threw, or undefined -->
@for (u of users.value() ?? []; track u.id) {   // value() starts as undefined before the first response — ?? [] avoids a crash
  <li>{{ u.name }}</li>
}

Three signal calls — isLoading(), error(), value() — replace what used to be three separate pieces of state you'd track by hand (a boolean, a caught error, an array) every time you wired up a manual subscribe().

Reactive URL — refetches when signal changes

export class UserDetailComponent {
  // route param as signal (withComponentInputBinding)
  id = input.required<string>();

  // re-fetches whenever id() changes
  user = httpResource<User>(() =>
    `/api/users/${this.id()}`
  );

  // derived signal from the resource
  displayName = computed(() =>
    this.user.value()?.name ?? 'Loading…'
  );
}

// Status values: 'idle'|'loading'|
//               'refreshing'|'resolved'|'error'
if (user.status() === 'resolved') { ... }
When to use httpResource() vs HttpClient directly: Use httpResource() for "load data, display it, re-load when params change" — the 80% case. Use HttpClient directly when you need POST/PUT/DELETE, cancellation with switchMap, retry logic, or file upload progress.

🌱 New to this? Talking to a server in three lines.

To get data from a backend, you inject(HttpClient) and call http.get('/api/users'). The catch for newcomers: it doesn't return the data directly — it returns an Observable, because the response arrives later, over the network. You subscribe to receive it (or, in a template, use the async pipe and Angular subscribes for you). The HTTP verbs map straight across: get reads, post creates, put/patch update, delete removes. So the whole basics: pick the verb, call it, and handle the result when it arrives.

🧠 Expert corner — cold requests, interceptors, and typed responses

  • HttpClient Observables are cold. Nothing happens until you subscribe — and subscribing twice fires the request twice. The async pipe subscribes once; shareReplay caches a shared result.
  • Interceptors are the cross-cutting layer. Register functional interceptors with withInterceptors([...]) to attach the auth header, retry, log, or transform errors for every request in one place. This is where the bearer token gets added — not in each call.
  • Type your responses. http.get<User[]>('/api/users') flows the type through; pair it with an OpenAPI-generated client so the contract can't drift.
  • HttpParams/HttpHeaders are immutable — .set() returns a new instance; assign it back.
  • Errors arrive as HttpErrorResponse on the error channel — handle with catchError; switchMap gives you free cancellation of stale requests (type-ahead). For load-and-display, httpResource() (v19+) wraps it declaratively as a signal.
  • CIAM tie-in. An auth interceptor adds Authorization: Bearer … and, on a 401, kicks off a silent refresh and retries the request. See HTTP Interceptors, Error Handling, and Tokens & Refresh.
