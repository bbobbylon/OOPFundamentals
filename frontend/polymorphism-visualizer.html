Polymorphism — One Name, Many Behaviors

Call .area() or .makeSound() through a parent-type reference, and Java dispatches to the actual subclass at runtime.

What is polymorphism? Why is it the most powerful OOP concept?

Polymorphism means "one name, many behaviors." You write code against a parent type (Shape shape), and at runtime, the JVM calls the actual subclass's method — whether that's Circle.area() or Rectangle.area(). You don't need an if/else per type. New shapes can be added without changing the code that uses them. This is the "Open/Closed Principle" — open for extension, closed for modification.

Without polymorphism (fragile)
if (shape instanceof Circle) circleArea();
else if (shape instanceof Rect) rectArea();
// add Triangle → update every if/else
With polymorphism (extensible)
for (Shape s : shapes) {'{'}
s.area(); // JVM dispatches at runtime
{'}'}
// add Triangle → just add the class
In Spring / CIAM: Spring Security's AuthenticationProvider interface: Spring tries each registered provider (JwtAuthenticationProvider, DaoAuthenticationProvider) via the same .authenticate() call — polymorphism at work. Adding a new IDM (Entra ID, Ping) = add a new AuthenticationProvider, no existing code changes.

How dynamic dispatch actually works (the vtable)

Every class with virtual methods has a hidden table — the vtable — that maps method names to the actual code to run. Each object has a pointer to its class's vtable. When you call animal.makeSound(), the JVM looks up makeSound in the object's vtable. That's how the SAME line of code dispatches to different implementations for different objects. Cost: one extra pointer hop per call. Cheap, and the JIT often inlines it away.

The killer use case — write once, work with anything

This is the real reason polymorphism exists. Code written against an interface works with every implementation — present and future. Your method doesn't care which list it got; it just calls .add() and trusts the object to do the right thing. 

// One method. Three valid call sites. Zero copy-paste.
public void save(List<String> items) {
    for (String item : items) repository.store(item);
}

save(new ArrayList<>());        // works
save(new LinkedList<>());       // works
save(new CopyOnWriteArrayList<>()); // works — even one that didn't exist when we wrote `save`

"Program to an interface, not an implementation" — the most quoted line from the Gang of Four design patterns book. That's polymorphism in plain English.

Real-world patterns powered by polymorphism

🎮 Strategy pattern

Sorting takes a Comparator<T>. Spring's RestTemplate takes a HttpMessageConverter. Different algorithms, same interface, swappable at runtime.

🧰 JDBC drivers

Connection, Statement, ResultSet are interfaces. Postgres, MySQL, SQLite each implement them. Your code looks the same against all three.

📦 Spring beans

Inject PaymentProcessor. Spring picks Stripe or PayPal at startup. Your controller doesn't know or care — it just calls .charge().

🖼️ UI toolkits

Component.paint(Graphics g). Button overrides it. Label overrides it. The framework just loops and calls .paint() on every component.

📁 java.io streams

InputStream has 20+ subclasses: file, network, byte array, GZIP, encrypted. Code that reads bytes works with any of them.

🧪 Test doubles

Real service in production, fake in tests — both implement the same interface. That's why testable code is interface-shaped.

Gotchas to avoid

🚫 Overloading by inheritance — not polymorphic

If you write void log(Object o) and void log(String s), the compiler picks based on the DECLARED type, not the actual type. log((Object) "hi") calls the Object version even though it's really a String.

void log(Object o) { ... }
void log(String s) { ... }
Object x = "hi";
log(x);  // calls log(Object) — surprise!

🚫 Calling overridable methods from a constructor

If a parent constructor calls a method that the child overrides, the child's version runs before the child's own fields are initialized. Classic NullPointerException source.

🚫 Returning a more general type than you need

If your method returns ArrayList instead of List, callers lock themselves to that implementation. Return the most general useful type.

🚫 Forgetting @Override

Without it, a typo in the method name silently creates a NEW method instead of overriding. The parent's version still runs. Always annotate.

Recap: OVERRIDING (runtime, via inheritance) — the JVM looks at the actual object type to choose the method. OVERLOADING (compile-time) — the compiler looks at the argument types to choose the method. Both share the idea of "one name, many forms," but they happen at different times. The first is the reason OOP scales; the second is mostly syntactic sugar.

🌱 New to "polymorphism"? It just means "many forms."

Say you have an Animal type with a speak() method, and Dog and Cat both extend it. Polymorphism is this: you hold the value as the general type — Animal a = new Dog() — call a.speak(), and the actual object decides which version runs ("Woof", not the generic default). Why is that a big deal? Because you can write code against Animal once — a list of animals, a method that takes an Animal — and it works for every animal that exists today or that you add tomorrow, without changing that code. One name, many behind-the-scenes forms.

🧠 Expert corner — dynamic dispatch, and what is not polymorphic

  • Overriding is resolved at runtime by the object's actual type, via a per-class method table (vtable): the JVM looks up speak() on the real Dog. This dynamic dispatch is the engine of OOP.
  • Overloading is resolved at compile time by the static types of the arguments — the compiler picks print(int) vs print(String) before the program runs. Same name, but a totally different mechanism from overriding.
  • Fields are NOT polymorphic. A field access uses the reference type, not the object type — Animal a = new Dog(); a.name reads Animal's field. Only methods dispatch dynamically. A classic interview trap.
  • You can't override static, private, or final methods (static methods are hidden, not overridden — resolved by reference type). Always add @Override so the compiler catches a signature typo that would silently create a new method instead.
  • Covariant returns let an override narrow the return type (Dog reproduce() overriding Animal reproduce()).
  • The principle behind it: Liskov Substitution — a subtype must be usable anywhere its supertype is expected. Real-world tie-in: a PaymentProcessor interface with StripeProcessor/PayPalProcessor implementations chosen at runtime — one call site, swappable behavior. That's polymorphism powering the Strategy pattern.
