gRPC & Protocol Buffers — Spring's Binary, Contract-First RPC

REST (REST API) sends JSON over HTTP/1.1 and GraphQL (GraphQL) lets the client shape a JSON response — both are text-based and both assume a request gets exactly one response. gRPC is a third option: a binary wire format, a strongly-typed contract compiled into real code, and — uniquely among the three — native support for a server or client (or both) sending a stream of messages instead of just one.

📡 What problem does gRPC solve that REST and GraphQL don't?

REST and GraphQL both serialize every message as JSON text — human-readable, but verbose (field names repeated in every payload) and slow to parse at scale. gRPC compiles a .proto file — a language-neutral Interface Definition Language (IDL) describing every message and service method — into real client and server code in whatever language you're using, including Java. Messages are serialized as Protocol Buffers: a compact binary format where each field is a number, not a repeated string key, making payloads far smaller and faster to parse than the equivalent JSON. And because gRPC runs on HTTP/2 instead of HTTP/1.1, a single TCP connection can multiplex many concurrent request/response exchanges — including streams, where a client or server keeps sending messages over the same call instead of just one round trip. That combination — a strict compiled contract, a compact binary wire format, and native streaming — makes gRPC the default choice for internal, polyglot, service-to-service communication (microservice A in Java calling microservice B in Go), where REST's human-readability and GraphQL's client-shaped queries matter less than raw throughput and a contract the compiler enforces.

  • The contract is code, not documentation — a .proto file is compiled into typed stubs; there's no way to call a method with the wrong argument types the way a hand-typed REST request body can drift from its DTO.
  • Binary beats JSON on the wire — protobuf fields are numbered, not spelled out per-message, so payloads are typically 3-10x smaller than the equivalent JSON, and parsing is a fixed binary read instead of a text scan.
  • Streaming is native, not bolted on — unary (1 request → 1 response), server-streaming, client-streaming, and bidirectional-streaming are all first-class RPC types in the .proto definition itself.
  • Browsers can't speak raw gRPC — it depends on HTTP/2 trailers a browser's fetch/XHR can't read, so a public browser-facing API needs a grpc-web proxy layer, or should just be REST/GraphQL instead.

grpc-spring-boot-starter: the idiomatic wiring

The community grpc-spring-boot-starter lets a service implementation be a plain @GrpcService bean extending the generated base class — Spring Boot auto-starts a gRPC server alongside (or instead of) the usual Tomcat/Netty HTTP server, on its own port (default 9090).

This app's REST convention, contrasted

Every controller in this scaffold returns ResponseEntity<HttpResponse> — a hand-written envelope. gRPC has no equivalent to design: the response message's shape is whatever the .proto file declares, generated into a typed Java class the compiler checks for you.

CIAM angle — auth travels as metadata, not a header

REST and GraphQL both carry a JWT in the HTTP Authorization header. gRPC has no HTTP headers in the traditional sense — it carries key/value pairs called metadata alongside each call, and a ServerInterceptor (Spring's GrpcGlobalServerInterceptor) reads and validates it before the service method runs — the same filter-before-controller shape as Spring Security's filter chain, just for a different transport. These aren't ranked — they're shaped for different callers. A public-facing SPA talks REST or GraphQL because a browser can call them directly with no extra tooling. Service-to-service calls inside a cluster — where every caller is a language-agnostic backend, not a browser — are exactly where gRPC's binary speed and native streaming pay off.

2. The contract: one .proto file, generated code on both sides

✗ REST — the contract lives in documentation, not the compiler

// OpenAPI describes this, but nothing stops a client
// from sending the wrong field name or type — it's
// only caught at runtime, by @Valid, if at all
POST /api/orders
{ "customerId": "42", "items": [...] }

✓ gRPC — the contract IS code, on both ends

service OrderService {
  rpc CreateOrder(CreateOrderRequest)
      returns (Order);
}
message CreateOrderRequest {
  int64 customer_id = 1;
  repeated OrderItem items = 2;
}
// protoc generates a typed OrderServiceGrpc.Stub
// AND a matching server base class — from ONE file
The numbers after each field (= 1, = 2) are the wire-format field tags — protobuf serializes by number, not by writing the field name into every message, which is a large part of why the binary payload is so much smaller than the equivalent JSON.

3. The four RPC shapes — only one of these exists in REST

RPC type.proto signatureReal-world use
Unaryrpc GetOrder(OrderId) returns (Order);Exactly like a REST GET — one request, one response. Most gRPC calls are this shape.
Server streamingrpc WatchPriceUpdates(Ticker) returns (stream PriceUpdate);One request opens a channel the server keeps pushing messages into — live price ticks, log tailing, progress updates.
Client streamingrpc UploadChunks(stream Chunk) returns (UploadResult);The client sends many messages over one call, server responds once at the end — large file upload, batched sensor telemetry.
Bidirectional streamingrpc Chat(stream ChatMsg) returns (stream ChatMsg);Both sides send whenever they want, independently, over the same open call — chat, live collaborative editing, real-time metrics duplex.
REST can only ever express the first row natively. A "streaming" REST API is really long-polling, Server-Sent Events, or a separate WebSocket bolted on — gRPC gets all four shapes from one protocol, because HTTP/2 already supports multiple concurrent, long-lived, independently-flowing streams over a single TCP connection.

4. One-sentence recap

📡 gRPC trades REST's human-readable JSON and GraphQL's client-shaped queries for a compiler-enforced binary contract and native streaming — the right default for internal, polyglot, high-throughput service-to-service calls, not for a public browser-facing API.
