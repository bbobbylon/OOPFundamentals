System Design — Scaling From 1 to 1 Million Users

Every "scale" decision is really about cost, latency, and consistency trade-offs. This page walks the same app through 5 architectures, then breaks down the building blocks you can mix & match.

🏛️ What is system design — and why do "it works fine locally" and "it collapsed under 10,000 users" happen with the same code, and how do you design systems that survive the transition?

System design is the process of defining the architecture of a software system to meet functional requirements (what it does) and non-functional requirements (how well it does it: scale, latency, availability, consistency, cost). The core insight is that every architectural decision is a trade-off — there is no free lunch. Faster reads mean eventual consistency. High availability means tolerating partial failures. Global scale means dealing with network partitions. The CAP theorem formalizes this: a distributed system can guarantee at most 2 of 3 properties: Consistency (every read sees the most recent write), Availability (every request gets a response), Partition Tolerance (works despite network failures between nodes). In practice, networks can always partition — so you choose CP (consistent but may be unavailable during partition: banking, CIAM) or AP (available but may return stale data during partition: social media, caching). Scaling strategies: Vertical scaling (scale up) = buy a bigger server. Simple but has a hard ceiling and creates a single point of failure. Horizontal scaling (scale out) = add more servers behind a load balancer. More complex (need stateless services or sticky sessions) but practically unlimited and fault-tolerant. Key building blocks: Load Balancer (distributes requests across servers; makes horizontal scaling possible); Cache (Redis/Memcached — stores frequently-read data in memory so the database isn't hit every request; L1/L2 cache vs distributed cache); Database replication (primary writes, replica reads — scales read throughput); Database sharding (split data across multiple DBs by key, e.g., user_id % 10 — scales write throughput and storage); CDN (Content Delivery Network — caches static assets at global edge nodes near users); Message Queue (Kafka/RabbitMQ — decouples producers from consumers, enables async processing, handles traffic spikes); Microservices (split monolith into independent services, each with its own database — enables independent scaling and deployment, but adds distributed system complexity). The 5-architecture progression: Single Server → Separate DB → Load Balancer + Replicas → Add Cache → CDN + Microservices. Each step solves a specific bottleneck and introduces new complexity. The skill is knowing which bottleneck you actually have before adding infrastructure. SQL vs NoSQL: SQL (PostgreSQL, MySQL) — ACID transactions, structured data, complex joins, scales reads well with replicas but writes are harder to shard. NoSQL (MongoDB, DynamoDB, Cassandra) — flexible schema, horizontal write scaling, no joins, eventual consistency. Choose SQL unless you have specific scale or flexibility requirements for NoSQL.

Stateless services = horizontal scale

// Stateless: server stores NO session data // Any request can go to ANY server instance // This is what makes load balancing / horizontal scale work // STATEFUL (bad for scale): HttpSession session = request.getSession(); session.setAttribute("userId", userId); // stored in-memory // If request 2 goes to server B, it has no session! // Fix: sticky sessions (bad) or session replication (complex) // STATELESS with JWT (scales perfectly): // Client stores the JWT; sends it on every request // Server validates JWT signature (no DB lookup needed!) // Any server can validate any JWT → truly stateless @GetMapping("/profile") public User profile(@AuthenticationPrincipal Jwt jwt) { // JWT carries userId/roles in claims — no session lookup String userId = jwt.getSubject(); return userService.findById(userId); } // Cache layer (Redis): @Cacheable("userProfiles") // Spring Cache annotation public User getUser(String id) { return userRepo.findById(id).orElseThrow(); // Redis serves repeated calls; DB only hit on cache miss }

CAP theorem + DB choice

// CAP Theorem: Consistency, Availability, Partition-Tolerance // Networks can always partition → pick CP or AP // CP systems (Consistent + Partition Tolerant): // PostgreSQL, MySQL, HBase // During network partition: return error rather than stale data // Use when: banking, auth, CIAM (wrong role = security hole) // AP systems (Available + Partition Tolerant): // Cassandra, DynamoDB, CouchDB // During network partition: return possibly stale data // Use when: user feeds, analytics, caching // Read replicas (scale reads): // Primary DB: handles all WRITES // Read replicas: copies of primary, handle READS // Replication lag: replicas may be milliseconds behind // Most Spring Boot config: // @Transactional(readOnly=true) → routes to read replica // Database index → turns O(n) table scan → O(log n): // CREATE INDEX idx_users_email ON users(email); // Without index: find email = scan all 1M rows // With index: binary search tree in B-tree structure // Always index: foreign keys, columns in WHERE clauses, // columns in ORDER BY, columns in JOIN ON

In CIAM / Your Job: CIAM systems are some of the most demanding to scale — they're in the critical path of every user interaction. Key design decisions in CIAM: (1) JWT over sessions — stateless JWT tokens let any backend instance validate any token without shared session state, enabling horizontal scaling of your Spring Boot services; (2) Redis for token blacklisting — when a user revokes a token, store the JTI (JWT ID) in Redis with a TTL matching the token's remaining lifetime; this works across all instances without a DB hit; (3) Load balancer with health checks — your Spring Boot Actuator /health endpoint should return 503 if the DB or required downstream service (Ping, Entra) is unreachable, so the load balancer stops routing to it; (4) Read replica for audit queries — CIAM generates massive audit logs; route audit report queries to a read replica to protect the write primary; (5) CAP choice = CP — CIAM must be consistent (wrong permissions = security breach), so prefer PostgreSQL over eventual-consistency NoSQL for user/role/permission data. Your Azure and AWS infrastructure aligns with this: Azure AD for identity, Azure Cache for Redis for token caching, and Azure Load Balancer for the Spring Boot tier.

Stage 1 — single server: app + database both on one box. Cheap, simple, perfect for an MVP or side project. The moment that box dies, the service is down. Adding hardware to one box ("vertical scaling") works until it doesn't — there's a ceiling and an expensive curve.

Load balancers — the front door

📍 What it does

One public address that distributes incoming requests across many backend instances. The clients never know there are 50 servers behind it.

🎲 Algorithms

  • Round-robin: next server in line. Simple, dumb, works.
  • Least-connections: the server with the fewest in-flight requests. Good for long-lived connections.
  • Consistent hashing: hash(client IP) → server. Same client always lands on the same backend — useful for sticky sessions or local caching.

🏥 Health checks

The LB pings each backend every few seconds (e.g., GET /healthz). If a server fails 3 in a row, it's pulled from rotation. This is most of why "high availability" actually works.

🌐 L4 vs L7

Layer 4 (TCP, e.g. AWS NLB): fast, dumb, just shuffles packets. Layer 7 (HTTP, e.g. nginx, ALB): can inspect headers, route by URL path, do SSL termination, rate-limit. Slower but smarter.

Caching — the #1 lever for latency

Most data is read 100× more than it's written. A cache stores the answer to "what's user 42's profile?" in memory so you skip the DB round-trip. Result: 10-100× faster reads.

Memorize the orders of magnitude. "Hit Redis instead of DB" is a 10× win. "Hit RAM instead of Redis" is another 5000×.

🔄 Cache-aside (lazy)

App checks cache first. Miss? Load from DB, write to cache, return. Most common pattern. Apps own the cache logic.

v = cache.get(key)
if v is None:
    v = db.query(key)
    cache.set(key, v, ttl=300)
return v

✍️ Write-through

App writes to cache, cache writes to DB. Cache always has fresh data; writes are slower.

⏳ Write-behind

App writes to cache instantly; cache flushes to DB later async. Fastest writes — but cache crashes can lose data.

♻️ Eviction policies

  • LRU (least recently used) — default, works for most.
  • LFU (least frequently used) — better for "hot" items.
  • TTL — just expire after N seconds. Pair with one of the above.

Sharding & replication

📑 Replication

One primary handles writes; one or more replicas stream the changes and serve reads.

Wins: read throughput, fault tolerance (promote replica if primary dies).

Cost: replication lag — replica might be 50ms behind. Reading-your-own-writes can show stale data.

🔀 Sharding (partitioning)

Split data across N databases by some shard key. e.g. users 0-25% → shard A, 25-50% → B, etc.

Wins: horizontal write scale, smaller indexes per shard.

Cost: queries that span shards become expensive. Re-sharding is painful. Pick the key wisely.

🔑 Picking a shard key

You want uniform distribution (no hot shards) and queries that target one shard. user_id is often good; created_at is usually bad (all today's writes hit one shard).

🎯 Consistent hashing

Maps keys to shards in a way that adding/removing a shard only moves 1/N of the keys, not all of them. Standard trick for cache clusters & sharded KV stores.

Message queues — async work

A queue (Kafka, RabbitMQ, SQS) sits between two services so the producer doesn't have to wait for the consumer. Crucial whenever the user shouldn't wait for slow work (email, video encode, billing webhook). 

// ❌ Synchronous — user waits for everything
api.checkout(cart):
    charge_credit_card(cart)         // 800ms
    send_receipt_email(cart)         // 400ms
    update_warehouse_inventory(cart) // 500ms
    push_to_analytics(cart)          // 200ms
    return "OK"                   // total: 1.9 seconds

// ✅ Async with queue — user waits only for the critical bit
api.checkout(cart):
    charge_credit_card(cart)               // 800ms (must be sync — payment confirms or fails)
    queue.publish("order.created", cart)  // 5ms — workers pick this up
    return "OK"                         // total: 805ms — perceived 2× faster

// Workers run independently, retry on failure, scale separately
worker_email.consume("order.created", send_receipt)
worker_stock.consume("order.created", update_inventory)
worker_analytics.consume("order.created", push_to_analytics)

Bonus: if the email service is down, messages pile up in the queue and process when it recovers. The user's checkout still succeeded. This is what "decoupled" really means in practice.

Kafka

Distributed log. Messages stay around for days. Multiple consumers can replay. Best for event streams, analytics, audit logs, multi-team broadcast.

RabbitMQ

Classic task queue. Routes messages by exchange/topic. Per-message ack & retry. Best for "do this work somewhere."

SQS / Pub-Sub

Managed cloud queue. No servers to run. Lower throughput than Kafka, but you don't operate it. Default choice on AWS/GCP.

CAP theorem — pick 2 of 3 (during a network partition)

In a distributed system, when the network splits (and it WILL), you must choose: Consistency (every read sees the latest write) or Availability (every request gets a response). You don't get to skip — Partition tolerance is mandatory in any real distributed system.

ChoiceBehavior during partitionExamples
CP — Consistency + Partition Refuse writes on the minority side; readers might get errors. Data stays correct. Postgres (with sync replication), MongoDB (default), HBase, Zookeeper, etcd.
AP — Availability + Partition Accept writes everywhere, reconcile later. Readers may see stale or conflicting values. Cassandra, DynamoDB, Couchbase, most DNS, S3 (within a region).
CA — Consistency + Availability Only possible if you assume the network never fails. Doesn't really exist at scale. Single-node databases. Theoretical.

Real rule of thumb: banking → CP (a wrong balance is worse than a down ATM). Social feed → AP (a slightly stale like-count is fine, an unavailable feed isn't).

Rate limiting — protecting your API

// Token bucket — most common algorithm
// Each user has a "bucket" with N tokens. Each request takes 1 token.
// Bucket refills at R tokens/second. Empty bucket → request rejected.

def allow(user_id):
    bucket = redis.hgetall(f"rl:{user_id}")
    now = time.time()
    elapsed = now - bucket['last']
    tokens = min(MAX_TOKENS, bucket['tokens'] + elapsed * REFILL_RATE)
    if tokens < 1:
        return False  # HTTP 429 Too Many Requests
    tokens -= 1
    redis.hset(f"rl:{user_id}", tokens=tokens, last=now)
    return True

Where to enforce: at the API gateway / LB if possible — keeps abusive traffic away from your app servers. Other algorithms: leaky bucket (smooths bursts), fixed window (simpler but worse boundary behavior), sliding window log (most accurate, most memory).

CDN — push content close to users

What it solves

A user in Sydney hits your image in Virginia → ~250ms round-trip. With a CDN, the image is cached on a node in Sydney → ~10ms. Huge perceived-speed win.

What goes on a CDN

Static assets: images, JS, CSS, fonts, videos, downloads. Anything cacheable for hours and identical for every user. Don't put per-user pages there unless you're careful with cache keys.

Cache headers matter

Cache-Control: public, max-age=31536000, immutable

For versioned assets (e.g. app.a4f9c.js). Change the hash to bust the cache — never edit a deployed file's contents.

Edge functions

Modern CDNs (Cloudflare, Vercel, Fastly) let you run code at the edge — A/B routing, auth checks, image resizing — closer to the user than your origin.

Monolith vs Microservices

🧱 Monolith

  • One codebase, one deploy, one DB.
  • ✅ Easy to develop, debug, run locally.
  • ✅ Refactoring across modules is a one-PR job.
  • ❌ At >~50 engineers, deploys queue up.
  • ❌ One bad commit can take down everything.

🧩 Microservices

  • Many small services, each owns its DB, deploys independently.
  • ✅ Teams ship without coordinating.
  • ✅ Scale & choose tech per service.
  • ❌ Distributed bugs (network, timing, partial failure) become normal.
  • ❌ Massive ops cost — observability, deploy infra, service mesh.

📐 Start monolith

Almost every team that started with microservices regrets it. Build a clean modular monolith. Carve out a service ONLY when a real boundary appears: different scaling needs, different team owner, different reliability requirements.

🔌 If you do split

Split by business capability (Orders, Inventory, Billing) — NOT by technical layer (Controllers, Services, DAOs). Each service owns its data; other services talk to it only via its API, never its DB.
