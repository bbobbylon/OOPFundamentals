unknown, any & never — the Top & Bottom of the Type System

Every type system has a top type (holds anything) and a bottom type (holds nothing). In TypeScript that's unknown and never — plus any, the deliberate escape hatch that opts out of the whole thing. Get these three right and the rest of the type system snaps into focus.

1. Three special types, one picture

TypeRoleThe one-liner
unknown TOPholds any value, safely"I don't know the type yet — make me check before I use it."
anyopts out of checking"Stop type-checking this. Trust me." (often a mistake)
never BOTTOMholds no value"This can't happen / this never produces a value."

unknown and any can both hold anything — the difference is what you're allowed to do with them afterwards. never is the opposite: nothing can be one.

4. never in the wild — it's more useful than it looks

Exhaustiveness checking

function area(s: Shape) {
  switch (s.kind) {
    case "circle": return …;
    case "square": return …;
    default:
      const _x: never = s; // ✅ all cases handled
      return _x;          // add a Shape → compile error here
  }
}

If you add a new variant to Shape, s is no longer never in default, and the assignment fails — the compiler reminds you to handle it.

Functions that never return

// throws → never finishes normally
function fail(m: string): never {
  throw new Error(m);
}
// infinite loop → also never
function loop(): never { while (true) {} }

A never return tells the compiler "control flow stops here," which improves narrowing after a call to it.

It vanishes from unions

type T = string | never;   // = string
// which is why Exclude works:
type R = Exclude<"a"|"b", "b">; // "a"

never is the identity element of unions — adding it changes nothing, so filtered-out members collapse away.

Impossible states

// make a bad combination unrepresentable:
type Resp =
  | { ok: true;  data: User; error?: never }
  | { ok: false; error: string; data?: never };

error?: never means "you literally cannot put an error on a success" — the type makes the illegal state uncompilable.

5. Rules of thumb

  • At any boundary where data arrives untyped (JSON.parse, fetch().json(), catch (e), libraries), prefer unknown over any — then validate/narrow once, and you're safe everywhere downstream.
  • Treat any as a code smell. Each one is a hole where runtime crashes leak through. Enable noImplicitAny; in catch, use useUnknownInCatchVariables (default in strict).
  • Reach for never deliberately: exhaustiveness checks and "make illegal states unrepresentable." If a value is typed never unexpectedly, you over-narrowed (e.g. intersected incompatible types).
  • Mnemonic: unknown = "any, but you must look before you leap"; any = "I turned the lights off"; never = "this branch is unreachable."

6. One-sentence recap

🔼 unknown is the top type — anything is assignable to it, but you must narrow before using it (safe); any disables checking in both directions (unsafe — avoid it); and never is the bottom type — assignable to everything but produced by nothing, which powers exhaustiveness checks, never-returning functions, and "impossible state" modeling.
