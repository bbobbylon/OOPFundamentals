Python: Advanced Typing

Generics with TypeVar, structural typing with Protocol, precise @overload signatures, decorator-preserving ParamSpec, and Self — the type system beyond basic hints.

🧬 Static types that hold their shape — generics, structural typing, and friends

Python's type hints are checked by external tools (mypy/pyright) and erased at runtime — they catch bugs without affecting execution. The advanced toolkit makes them generic and precise: a TypeVar preserves the exact type (def first(xs: list[T]) -> T) instead of widening to Any; a Protocol gives structural typing (static duck typing — a class fits if it has the right methods, no inheritance); @overload declares precise per-call-shape signatures; and ParamSpec forwards a callable's whole parameter list so a decorator keeps the wrapped signature. Python 3.12 adds native def first[T](...) syntax.

  • Types are a static layer — checked by mypy/pyright, erased at runtime.
  • TypeVar/Generic preserve types — no widening to Any.
  • Protocol = structural typing — fit by shape, no implements.
  • @overload & ParamSpec add precision — per-shape returns; signature-preserving decorators.

Generics preserve the type

from typing import TypeVar, Generic T = TypeVar("T") def first(xs: list[T]) -> T: return xs[0] first([1,2,3]) # inferred int first(["a","b"]) # inferred str class Stack(Generic[T]): def push(self, x: T) -> None: ... def pop(self) -> T: ... # 3.12 syntax: def first[T](xs: list[T]) -> T

Protocol = structural typing

from typing import Protocol class Validator(Protocol): def validate(self, token: str) -> Claims: ... # ANY class with that method satisfies it — # no `class X(Validator)` needed def check(v: Validator, t: str): return v.validate(t)

vs Java/TypeScript

Java: generics <T> with bounds (<T extends X>); interfaces are nominal (must implements). TypeScript: <T> generics + structural interfaces (like Protocol) + overloads. Python: TypeVar generics, structural Protocols, @overload — but all erased (no runtime enforcement). Closer to TS's "types are a static layer" than Java's runtime generics.

CIAM context: A TokenValidator Protocol (validate(token) -> Claims) lets your code depend on the shape, not a concrete Entra/Ping/Keycloak class. @overload types get_user(id) as User | None but get_user(id, required=True) as User; a @require_role decorator typed with ParamSpec keeps the wrapped view's signature; and Self makes a fluent PolicyBuilder.allow(...).deny(...) return the right subclass.

Everything on this page is erased at runtime — the one line above already told you that. This block is about the ONE typing construct whose syntax actively hides how total that erasure is.

The problem

You wrap a raw string in what looks exactly like a constructor call, expecting at least a whisper of validation. You get the identical, unsanitized string back, wearing a costume mypy can see and nothing else can.

A "validated" user ID that was never checked at all

You want to stop accidentally passing a raw group_id where a user_id is expected — both are just strings, so you reach for NewType, and the call syntax looks reassuring:

from typing import NewType
UserId = NewType("UserId", str)

def load_profile(uid: UserId) -> Profile: ...

raw = request.headers["X-User-Id"]  # attacker-controlled
uid = UserId(raw)  # "constructing" a validated UserId... right?
load_profile(uid)

UserId(raw) reads exactly like instantiating a class — parentheses, a type name, an argument. It performs precisely zero validation, zero sanitization, and zero wrapping. uid is raw, the exact same string object, and type(uid) is str — not UserId, because UserId was never a class to begin with. Any assumption downstream that "if it's a UserId, it's already been checked" is false at runtime, even though mypy will happily agree with you that it's safe.

You didn't skip a validation step. NewType never had one to give you.

NewType never creates an object — it returns the argument, unchanged. The typing docs describe it exactly this way: calling the thing NewType() returns is "a callable that returns its argument when called" — no new instance, no wrapper, no overhead beyond a plain function call. It exists purely so a type checker can refuse to let a GroupId flow into a function expecting a UserId, even though at runtime they are both just str, indistinguishable by any check you could write.
A NewType is a name tag stuck onto a value, not a background check performed on it. Writing "HELLO, I AM A VALIDATED USER ID" on a sticky note and slapping it onto a string doesn't validate the string — and neither does calling UserId(raw).
You

I called UserId(raw) — shouldn't that at least check it looks like a UUID?

NewType's runtime implementation

I don't check anything. When you call me, I return exactly what you handed me, same object, same type. My entire job happens at type-checking time, in mypy's head — at runtime I might as well not exist.

You

Then why does calling you look exactly like constructing an instance of a class?

NewType's runtime implementation

Because that syntax is what makes mypy's static story readable — "wrap this raw value as the distinct type" reads naturally as a constructor call. Nobody designed that resemblance to also promise you runtime safety; it's a static-analysis convenience that happens to look like one.

The mechanism

Follow exactly what happens, line by line, when UserId(raw) executes.

  1. UserId = NewType("UserId", str) creates a lightweight callable, not a classdefinition
  2. mypy privately notes: "UserId is a distinct type, but at runtime it IS a str"static-only fact
  3. UserId(raw) calls that callable with raw as the argumentthe call
  4. The callable's entire body is "return the argument" — no branching, no checks, no wrappingno-op
  5. The returned object is raw itself — same id(), same type(), same contentidentical object
  6. Every "is this validated?" question you might ask at runtime gets the same answer it would have for the unwrapped string, because there is no wrapperno distinction survives

Step 4 is the whole lesson: there's no code path inside NewType's generated callable that could validate anything even if it wanted to. It isn't skipping a check — a check was never part of the design.

Every other option on this board is what a "constructor" would normally do — validate, or at least allocate something new. NewType does neither; the slot that looks like "validated wrapper" resolves to "no-op passthrough," and only a type checker ever notices the difference.

GroupId = NewType("GroupId", str); g = GroupId("not-a-real-uuid-at-all"). At runtime, type(g) is:

Correct. NewType's callable just hands back its argument. There's no subclass, no wrapper — g is the exact same str object "not-a-real-uuid-at-all" already was.

There's no subclass created at all, real or otherwise — that's precisely the misconception the constructor-like syntax invites. If you need an actual subclass with runtime identity, you'd write one yourself.

mypy's inferences never reach into the running program — type hints carry zero runtime behavior in standard Python, NewType included. There is no mechanism for a static inference to change what type() reports.

1. TypeVar & Generics

from typing import TypeVar, Generic
T = TypeVar("T")
N = TypeVar("N", bound="Comparable") # upper bound

def first(xs: list[T]) -> T: return xs[0] # T preserved

class Stack(Generic[T]):
  def push(self, x: T) -> None: ...
  def pop(self) -> T: ...
# 3.12: def first[T](xs: list[T]) -> T ; class Stack[T]

A TypeVar links inputs and outputs: first(list[T]) -> T tells the checker the return matches the element type, so first([1,2]) is int, not Any. bound=X says "T must be X or a subtype" (so you can call X's methods on it); a constrained TypeVar("S", str, bytes) restricts T to those exact types. Generic[T] makes a reusable container class. Python 3.12+ has native syntax (def f[T](...)) that drops the separate TypeVar declaration.

Without a TypeVar, you lose the type. def first(xs: list) -> object (or Any) forces callers to cast or gives up checking. The TypeVar is what makes generic code both reusable and precise — the difference between "a list of something" and "a list of T, returning T."

2. Protocol — Structural ("Static Duck") Typing

from typing import Protocol, runtime_checkable

class SupportsValidate(Protocol):
  def validate(self, token: str) -> Claims: ...

# EntraValidator/PingValidator satisfy it WITHOUT subclassing,
# just by having validate(self, str) -> Claims
def check(v: SupportsValidate, t: str) -> Claims:
  return v.validate(t)

A Protocol defines a required shape; any class with matching members satisfies it — no explicit inheritance. This is statically-checked duck typing: your function depends on "anything that can validate," decoupling it from concrete classes (and third-party types you can't subclass). Add @runtime_checkable to allow isinstance(x, SupportsValidate) (checks method names only, not signatures).

Protocol (structural) vs ABC (nominal). An abc.ABC requires you to register/inherit (class X(MyABC)) — nominal typing. A Protocol matches by structure, so even a class you don't control conforms automatically. Use Protocols for "I need something that behaves like…", ABCs when you want an explicit, enforced base class with shared implementation.

3. @overload — Precise Per-Call Return Types

from typing import overload, Literal

@overload
def get_user(id: int) -> User | None: ...
@overload
def get_user(id: int, required: Literal[True]) -> User: ...

def get_user(id, required=False): # the ONE real impl
  u = repo.find(id)
  if required and u is None: raise NotFound
  return u

@overload declares multiple type-only signatures above one implementation. The checker picks the matching overload per call: get_user(1) is User | None, but get_user(1, required=True) is User — so callers don't need a redundant None check. The overloaded stubs have empty bodies (...); only the final, un-decorated function runs. Literal[True] is what lets the boolean argument's value select the return type.

Overloads are for the type checker only. At runtime there's a single function — the overload stubs are erased. They eliminate a class of bugs (forgetting a None check, casting) by encoding "this argument changes the return type" precisely, which a single union signature can't express.

4. ParamSpec & Self

from typing import ParamSpec, TypeVar, Callable
P = ParamSpec("P"); R = TypeVar("R")

def require_role(fn: Callable[P, R]) -> Callable[P, R]:
  @wraps(fn)
  def inner(*a: P.args, **k: P.kwargs) -> R:
    check(); return fn(*a, **k)
  return inner # wrapped fn keeps its EXACT signature

ParamSpec (P) captures a callable's full parameter list so a decorator can forward it unchanged — Callable[P, R] -> Callable[P, R] means "returns a function with the same params and return type." Without it, decorators erase the signature to (*args, **kwargs) -> Any and callers lose autocomplete/checking. Concatenate lets a decorator add/remove a leading arg. Self types methods that return their own instance (fluent builders, def clone(self) -> Self) so subclasses get the right type back.

These are all erased at runtime. mypy/pyright read them; the interpreter ignores them (apart from storing __annotations__). So they cost nothing at runtime and never change behavior — they're a static contract. Run a checker in CI to actually get the safety; without it, the hints are just documentation.
