Services & Networking

Services give pods a stable DNS name and load-balance traffic. Ingress routes HTTP from outside the cluster.

🚦 What are Kubernetes Services — and how does traffic actually reach your pods?

Pods are ephemeral — new IPs each restart — so you can't hardcode a pod IP. A Service gives a set of pods (selected by label) a stable ClusterIP and DNS name, load-balancing across healthy ones (kube-proxy routes via iptables/ipvs). Types: ClusterIP (in-cluster only, the default), NodePort (a static port on every node), LoadBalancer (a cloud LB with a public IP, one per service), ExternalName (alias to external DNS). An Ingress is a smarter HTTP router in front of many Services — TLS termination, host/path routing, rate limiting — far cheaper than a LoadBalancer each. CoreDNS gives every Service <name>.<namespace>.svc.cluster.local.

  • Service = stable IP/DNS for ephemeral pods — label-selected, load-balanced.
  • ClusterIP / NodePort / LoadBalancer / ExternalName — in-cluster → public.
  • Ingress fronts many Services — TLS + host/path routing, cheaper than per-service LBs.
  • CoreDNS — name.namespace.svc.cluster.local; NetworkPolicy = pod firewall.

NetworkPolicy security

By default, all pods in a cluster can talk to all other pods — no network isolation. NetworkPolicy adds firewall rules at the pod level. Deny all traffic first, then allow only what's needed: apiVersion: networking.k8s.io/v1; kind: NetworkPolicy; spec: { podSelector: { matchLabels: { app: ciam-auth }}; policyTypes: [Ingress, Egress]; ingress: [{ from: [{ podSelector: { matchLabels: { app: api-gateway }}}], ports: [{ port: 8080 }] }]; egress: [{ to: [{ podSelector: { matchLabels: { app: postgres }}}], ports: [{ port: 5432 }] }] }. This says: ciam-auth pods can ONLY receive traffic from api-gateway pods on port 8080, and can ONLY send traffic to postgres pods on port 5432. Everything else blocked. Essential for CIAM: prevents compromised services from communicating laterally to identity stores.

CIAM networking topology: External traffic flows Internet → AWS ALB / Azure App Gateway → Ingress controller → host/path routing → ClusterIP Services → pods. Ping is a ClusterIP ping-gateway.ciam-prod:9031, the auth service ciam-auth:8080, the Angular nginx ciam-frontend:80, with TLS terminating once at the Ingress. A NetworkPolicy lets ciam-auth pods accept only from the Ingress controller — blocking lateral calls from a compromised microservice to your user-management endpoints.

The problem

You scaled to ten replicas. Your gRPC traffic still all goes to one pod.

"Load balanced" turns out to mean something narrower than you thought

A Service load-balances connections, not requests. It picks a pod when the TCP connection is established and then that connection is pinned there for its whole life. For REST over short-lived HTTP/1.1 connections that is invisible. For anything that holds a connection open — gRPC, HTTP/2, a WebSocket, a JDBC pool — you made one choice, once, and every request afterwards rides it.

kubectl scale --replicas=10 ✓ endpoints: 10 healthy ✓ pod-3 CPU 95% ⚠ the other nine idle ⚠

Every dashboard says the Service is healthy and balanced. It is. It balanced the two connections you opened, perfectly, across two pods.

Once you know what a Service physically is, the fix is obvious
A Service is packet-rewriting rules, not a proxy process ↓ so the pod is chosen at connect time, in the kernel, once Long-lived connections therefore need a client that re-balances ↓ periodic reconnect, or a client that opens one connection per endpoint Give it the endpoints: a headless Service (clusterIP: None) returns pod IPs
A ClusterIP is not an address anything owns. No process listens on it, no interface has it, and nothing will answer if you ping it. It is a value in an iptables rule on every node, and the rule swaps it for a real pod IP as the packet leaves. That is the whole of it.
DNS resolves the Service name to a ClusterIP→ your app opens a TCP connection to that fake address→ an iptables/IPVS rule on this node fires→ the rule picks ONE endpoint and rewrites the destination — conntrack records it→ every later packet on this connection follows conntrack to that same pod
Station four is the liar — not because it's wrong, but because it looks like ongoing load balancing and is actually a single decision made once, at connect time. Every station before and after it runs exactly as advertised: DNS really does resolve, the rule really does forward, conntrack really does track. The chain never balances a REQUEST anywhere in it — only a connection, exactly once, at station four.
The mechanism

Follow one packet from your pod to a real pod IP.

  1. Your app resolves ciam-auth.ciam-prod.svc.cluster.local — CoreDNS returns the ClusterIP, e.g. 10.96.14.7a real DNS answer for a fake address
  2. Your app opens a TCP connection to 10.96.14.7:8080. Nothing anywhere is listening on itno process, no interface, no host
  3. Leaving the pod, the packet hits an iptables (or IPVS) rule on this node that kube-proxy programmed from the Endpoints listevery node has the full ruleset
  4. The rule picks one endpoint at random and rewrites the destination to that pod's real IP — and conntrack records the choicechosen ONCE, at connect time
  5. Every subsequent packet on this connection follows the conntrack entry to the same pod, until the connection closesthis is the pinning

Step 4 is the one that explains the pager. The random choice happens on the first packet of a new connection and nowhere else, so "balanced" means balanced across connections. Ten HTTP/1.1 requests open ten connections and spread nicely; ten thousand gRPC calls over one HTTP/2 connection are ten thousand requests to a single pod. Nothing is misconfigured — you are reading the word "load balancer" as more than the rule does.

And this is why so much Kubernetes debugging is looking at Endpoints rather than the Service. A Service is only a label selector plus a port map; the actual list of pod IPs lives in the Endpoints (or EndpointSlice) object that the controller keeps in sync. So kubectl get endpoints ciam-auth is the question worth asking first — an empty list means the selector matches nothing (a typo'd label, or pods that are running but not Ready, because failing a readiness probe removes a pod from Endpoints and that is exactly what readiness is for). The Service will look perfectly healthy the entire time, because from its side there is nothing to be unhealthy about.

Your Spring service holds a gRPC connection to ciam-auth, which has 3 replicas behind a normal ClusterIP Service. You scale it to 10. Where does traffic go?

The rules genuinely are reprogrammed — new connections will see all 10. But conntrack already has an entry for your established connection, and rewriting the rules does not rewrite existing flows. New connections balance; yours is not a new connection.

There is no per-connection endpoint set to keep. The choice was a single destination, made once, recorded in conntrack — not a list narrowed to three.

Right, and it is the shape of the whole problem. The pod was chosen on the first packet and pinned by conntrack; scaling changes nothing about a flow already established. Fixes, in order of bluntness: set a max connection age or idle timeout so clients reconnect periodically; use a headless Service so the client sees every pod IP and balances itself; or put a real L7 proxy in the path (a service mesh, or gRPC's own round_robin policy over a headless Service) — which balances requests rather than connections, because it actually parses them.

Where you've seen this before

Three places connection pinning shows up wearing a different name.

A JDBC connection pool

HikariCP holds ten connections open for the life of the pod. Point it at a ClusterIP in front of read replicas and those ten connections pick their replicas once, at startup, and hold them — so a rolling restart of the database tier rebalances your app and nothing else does.

pooled means pinned

WebSockets and SSE

Same physics, and the reason sticky sessions stop being a choice: the connection is the session. Any state the server keeps for it must be in Redis rather than in that pod's memory, because you cannot move the connection.

the connection is the session

A readiness probe you thought was cosmetic

Readiness is precisely the switch that adds and removes a pod from Endpoints — which is the list kube-proxy programs from. Liveness restarts a pod; readiness decides whether the Service will ever send it anything.

readiness = "in the rules or not"
Questions from the back row

Then what is Ingress, if a Service is already "load balancing"?

A different layer doing a genuinely different job. A Service works at L4 — it moves packets and never looks inside them. An Ingress controller is a real proxy process (nginx, Envoy, Traefik) that terminates the connection, parses HTTP, and can therefore route by host and path, terminate TLS once, and balance per request rather than per connection. That last point is the one that matters here: an L7 proxy in the path is a real fix for the gRPC problem, because it is the only thing in the chain that can see where one request ends and the next begins.

Why can I reach a Service by name from one namespace but not another?

Because the short name is resolved through a DNS search path that puts your own namespace first. ciam-auth from inside ciam-prod becomes ciam-auth.ciam-prod.svc.cluster.local; from default it tries ciam-auth.default… and finds nothing. Use the two-label form ciam-auth.ciam-prod across namespaces. And note a NetworkPolicy can produce the same symptom from a completely different cause — DNS resolving fine and the connection hanging — so check which one you are actually looking at before you start editing manifests.

Is NodePort ever the right answer?

Rarely on a cloud cluster, and it is worth knowing it is always there: a LoadBalancer Service is a NodePort Service with a cloud load balancer pointed at it, and a NodePort is a ClusterIP with a high-numbered port opened on every node. They stack. Its honest uses are bare metal without a cloud LB, and local development. For several HTTP services, one Ingress in front of ClusterIPs beats a cloud load balancer per Service on both cost and TLS management.

2 — ClusterIP Service Manifest

kind: Service
metadata:
  name: api-server-svc
  namespace: default
spec:
  selector:
    app: api-server    # matches Deployment pod labels
  ports:
  - port: 80           # service port (what callers use)
    targetPort: 8080   # pod port (what Spring Boot listens on)
  type: ClusterIP      # default — internal only

# Other pods call it by DNS:

3 — Ingress




An Ingress is an L7 HTTP router. It requires an Ingress Controller (nginx, Traefik, AWS ALB…) to be installed. Multiple services share one cloud load balancer.


apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: app-ingress
  annotations:
    nginx.ingress.kubernetes.io/rewrite-target: /
spec:
  tls:
  - hosts: [api.myapp.com]
    secretName: tls-cert
  rules:
  - host: api.myapp.com
    http:
      paths:
      - path: /api
        pathType: Prefix
        backend:
          service:
            name: api-server-svc
            port: { number: 80 }









4 — Network Policies




By default, all pods can talk to all pods. NetworkPolicies restrict ingress/egress at the pod level (requires a CNI that enforces them, e.g. Calico or Cilium).


# Allow only the frontend to call the api-server
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: allow-frontend-only
spec:
  podSelector:
    matchLabels: { app: api-server }
  ingress:
  - from:
    - podSelector:
        matchLabels: { app: frontend }
    ports:
    - { port: 8080 }
