React: Accessibility (a11y)

Semantic HTML first, accessible names, keyboard & focus management, ARIA used sparingly, and how to test it — building React UIs everyone can use.

♿ Accessibility is mostly "use the right HTML" — not a pile of ARIA

Accessibility (a11y) means people using a keyboard, screen reader, magnifier, or voice control can operate your UI. The biggest lever is the simplest: semantic HTML. A real <button>, <a href>, <label> or heading brings an implicit role, keyboard behavior and focusability for free — a clickable <div onClick> ("div soup") brings none. Every control needs an accessible name, full keyboard support (Tab + Enter/Space, visible focus, no traps), and deliberate focus management on route/modal changes. ARIA only fills the gaps HTML can't — don't use ARIA if a native element does the job. Lint with eslint-plugin-jsx-a11y and test with axe; accessible components are also the testable ones.

  • Semantic HTML first — role, keyboard, focus come free with the right element.
  • Accessible name on every control — text, <label htmlFor>, aria-label, or alt.
  • Keyboard + focus management — reachable, operable, no traps; move focus on modal/route change.
  • ARIA last — aria-live/aria-modal only where HTML falls short; bad ARIA > none.

div soup vs semantic

// ❌ invisible to AT, no keyboard <div className="btn" onClick={save}> Save </div> // ✅ role, focus, Enter/Space — all free <button onClick={save}>Save</button> // ✅ a real label ties text to the input <label htmlFor="email">Email</label> <input id="email" type="email" />

Focus + live region

// announce async errors to screen readers <div role="alert" aria-live="assertive"> {error} </div> // move focus to the error on submit fail useEffect(() => { if (error) errRef.current?.focus() }, [error])

Why it pays off

Accessible UIs are legally required in many contexts (WCAG / ADA / EN 301 549), help SEO (semantic structure), and are easier to test (RTL queries by role/name). The same getByRole('button', {name:/save/i}) that a screen reader uses to find your button is the query your test uses — accessibility and testability are the same discipline.

CIAM context: A login form must be fully operable by keyboard and screen reader — real <label>s on every field, a <button type="submit">, the "invalid credentials" message in an aria-live="assertive" region, and focus moved to that error on failure. The admin area is a real <nav> of links; a "delete user" confirmation is a role="dialog" aria-modal that traps focus and returns it on close. Auth flows are exactly where users can't afford to get stuck.

1. Semantic HTML First

Instead of…Use…You get for free
<div onClick><button>role=button, focusable, Enter/Space, disabled
<div onClick> (navigation)<a href>role=link, focus, Enter, open-in-new-tab
<div className="title"><h1>…<h6>document outline screen readers navigate by
placeholder-as-label<label htmlFor>announced name, bigger click target, persists
If you must make a non-semantic element interactive, you owe it the full kit: role, tabIndex={0}, and key handlers for Enter/Space — which is exactly the boilerplate a real <button> gives you. So just use the button. (In React, htmlFor is the JSX spelling of the for attribute.)

2. Keyboard & Focus Management

// move focus into a dialog on open, restore on close
useEffect(() => {
  const prev = document.activeElement
  dialogRef.current?.focus()
  return () => prev?.focus() // restore
}, [])

// skip link for keyboard users
<a href="#main" className="skip-link">Skip to content</a>

Everything operable by mouse must work by keyboard: reachable via Tab (logical order = DOM order — avoid positive tabIndex), activated by Enter/Space, with a visible focus ring (never outline:none without a replacement). On a route change or modal open, move focus deliberately (to the heading/dialog) and trap it inside a modal; restore it to the trigger on close. A "skip to content" link spares keyboard users from tabbing through the whole nav.

SPAs break focus on navigation. A client-side route change swaps content but leaves focus on the old (now-gone) element and doesn't announce the new page. Move focus to the new page's <h1> (or a route announcer with aria-live) so screen-reader users know they navigated.

3. ARIA — Only When HTML Can't

ARIAUse
aria-label / aria-labelledbyname an element with no visible text (an icon button) or point to its label
aria-live="polite|assertive"announce async updates (toasts, validation errors, "saved")
aria-expanded / aria-controlsdisclosure/menu toggles — state the open/closed state
role="dialog" + aria-modal="true"modal dialogs (pair with focus trap + Esc to close)
First rule of ARIA: don't use ARIA. A native <button> beats <div role="button" tabIndex=0> every time. Incorrect ARIA actively misleads screen readers (worse than none) — e.g. aria-hidden="true" on a focusable element creates a "phantom" stop. Use ARIA to supplement semantics (live regions, expanded state), not to recreate elements HTML already provides.

4. Testing Accessibility

// lint: catches many issues as you type
// eslint-plugin-jsx-a11y → flags <img> without alt, click-without-key, etc.

// runtime audit in a test
import { axe } from 'jest-axe'
const { container } = render(<LoginForm />)
expect(await axe(container)).toHaveNoViolations()

// RTL queries BY ROLE = an implicit a11y check
screen.getByRole('button', { name: /sign in/i })
Automated tools catch ~30–50%; the rest needs a human. eslint-plugin-jsx-a11y + axe catch missing alt text, low contrast, bad roles, and label gaps. They cannot judge whether focus order is logical, whether a live region announces at the right time, or whether the experience makes sense — so also tab through with the keyboard and try a screen reader (VoiceOver/NVDA) on critical flows.
