Reconciliation & Fiber

A fiber is a unit of work and a node in a linked-list tree. Watch React walk the tree (beginWork down, completeWork up), diff against the previous tree, and commit only the deltas — interruptibly.

🧵 What is Fiber — and why did React rewrite its entire reconciler around it?

The pre-16 "Stack Reconciler" walked the tree recursively and synchronously — once started it couldn't pause, so a 200ms reconcile froze the browser for 200ms. Fiber (React 16+) made it iterative: a Fiber node is a JS object for one element with child/sibling/return pointers, forming a linked-list tree React can walk in a loop. The payoff is that React can yield control between work units — abandon a low-priority render to handle a click, then resume. Two phases: the render phase (interruptible) builds an effects list; the commit phase (synchronous) applies all DOM mutations at once. Concurrent features (startTransition, useDeferredValue, Suspense streaming) all ride on this interruptibility.

  • Old reconciler couldn't pause — a big sync render blocked the browser.
  • Fiber = linked-list tree — child/sibling/return, walked iteratively.
  • Yields between work units — high-priority input interrupts low-priority render.
  • Render phase interruptible, commit phase atomic — concurrent features ride on it.

// Render phase traversal (simplified): // 1. beginWork(fiber): process this fiber // For function component: call the function // For class component: call render() // For host element ('div'): process props // Returns child fiber (go deeper) // 2. Double buffering

React maintains TWO fiber trees at all times. current: the tree currently rendered on screen (committed). workInProgress: the tree being built for the next render. Each fiber has an alternate pointer to its counterpart in the other tree. During reconciliation, React walks and mutates the workInProgress tree. When commit happens, the root's current pointer flips to point to the workInProgress tree — which becomes the new current. The old current becomes the next workInProgress (memory reuse). This is why React can abandon a workInProgress render midway (due to a higher-priority update) without corrupting the visible UI — the current tree is untouched until the commit phase flips the pointer.

Why it matters for CIAM: On a 1000+ row user table with live filter/sort, Fiber's interruptible rendering keeps the search input responsive while the filtered list reconciles in the background via startTransition — the input is high-priority, the filter low-priority. Without it, filtering 10k users would freeze the box for hundreds of ms. Angular has no interruptibility by default (Zone.js runs synchronous CD); Signals + OnPush reduce work but don't make it interruptible. Truly incremental rendering is a Fiber-specific capability.

1. What is a Fiber?

A fiber is a JavaScript object that is two things at once: a node in the component tree and a unit of work the scheduler can pause and resume. React 16 replaced the old recursive "stack reconciler" (which could not be interrupted) with this linked-list structure precisely so rendering could be broken into chunks.

FiberNode = {
  type, key, // what & identity (from the element)
  stateNode, // the real DOM node OR class instance
  child, sibling, return, // tree as a linked list (no recursion)
  pendingProps, memoizedProps,// next vs last props
  memoizedState, // the hooks linked list lives here
  flags, // Placement | Update | Deletion …
  lanes, // priority of pending work
  alternate // link to the OTHER tree (double buffering)
}
child / sibling / return, not children[]: The tree is a singly-linked list. React walks child to go down, sibling to go across, and return to go back up — so it can stop mid-walk, save its place, and resume later. A recursive function call stack cannot be paused; a pointer can.

2. Double buffering: current vs workInProgress

React keeps two fiber trees. current is what is on screen. When an update comes in, React builds a workInProgress tree, reusing fibers from current via the alternate pointer. When the WIP tree is finished and committed, React simply swaps the pointers — WIP becomes current in one atomic step.

Why two trees? The screen always shows a complete, consistent tree (current). React can build, throw away, and rebuild the workInProgress tree as many times as it likes (e.g. when a higher-priority update interrupts) without the user ever seeing a half-rendered UI. This is what makes concurrent rendering safe.

3. The O(n) diffing heuristics

A general tree-diff is O(n³). React gets it to O(n) with two assumptions:

SituationWhat React does
Same type at same position (div→div)Keep the DOM node, update only changed attributes; recurse into children
Different type (div→span, or <A/>→<B/>)Tear down the entire old subtree (unmount, lose state), build the new one from scratch
List childrenMatch by key; same key = same instance moved, no key = match by index
"Different type ⇒ throw away the subtree" has teeth. Conditionally rendering {edit ? <input/> : <input/>} where the two branches are different component types unmounts and remounts — losing focus, scroll, and all local state. Keep the type stable and toggle a prop instead.

4. Two phases — and why it matters

Render / reconcile phase

Interruptible. React calls your components, diffs, builds the WIP tree, and records flags. No DOM is touched. Can be paused, aborted, or restarted — so it must be pure (no side effects). This is why StrictMode double-invokes renders in dev: to surface impurity.

Commit phase

Synchronous, not interruptible. React walks the effect list and applies mutations to the real DOM, attaches refs, then runs layout effects. Fast and atomic so the user never sees a torn UI. useEffect callbacks are flushed shortly after, asynchronously.
