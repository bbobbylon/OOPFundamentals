@Async & Thread Pools

@Async moves a method off the calling thread onto a thread pool — fire-and-forget, or returning a CompletableFuture. The catch: thread pools fill in an order that surprises almost everyone, and (like @Transactional) @Async rides on a proxy, so calling it from the same class does nothing. Let's make both concrete.

🧵 How does a thread pool actually work — and why does it fill in a counter-intuitive order?

A thread pool is a fixed set of worker threads created once and reused, avoiding per-task thread creation. Three knobs govern it: corePoolSize (always alive), maxPoolSize (the ceiling), and queueCapacity (tasks waiting before new threads spawn). The surprise: Spring only adds threads beyond core after the queue is full. With core=5, max=20, queue=100, submitting 25 tasks runs 5 and queues 20 — no new threads. Extra threads appear only past 105 tasks, and you hit all 20 at 200. People expect threads to scale before the queue; it's the opposite.

  • Queue fills before the pool grows. core → queue → up to max → reject.
  • @Async is proxy-based — a self-call runs synchronously and silently.
  • CompletableFuture composes async work without blocking the submitting thread.
  • SecurityContext is ThreadLocal — it doesn't follow work onto a new thread.

Self-invocation proxy gotcha

@Async runs through an AOP proxy. An external userService.sendEmail() is intercepted and runs async; an internal this.sendEmail() bypasses the proxy and runs synchronously. Fix by self-injecting (@Lazy @Autowired UserService self) or extracting another @Service.

CompletableFuture chaining

@Async CompletableFuture<UserDto> loadUser(id), then future.thenApply(...).thenAccept(...). Run several together with CompletableFuture.allOf(f1,f2,f3).thenRun(...) — the whole pipeline is non-blocking; the main thread submits and moves on.

SecurityContext in async

SecurityContext lives in ThreadLocal, so on an @Async thread getContext() is empty (user null). Fix with MODE_INHERITABLETHREADLOCAL or a DelegatingSecurityContextExecutor wrapping your task executor.

CIAM: The ThreadLocal bug is real — an @Async sendAuditEvent() that reads SecurityContextHolder.getContext().getAuthentication().getName() NPEs in prod. Capture the principal before dispatching: String actor = authentication.getName(); executor.execute(() -> auditService.record(actor, …)) — pass the value in, don't read ThreadLocal on the new thread.

1. What @Async actually does

Offload to a pool

@EnableAsync          // turn the feature on (once)
@Configuration
class AsyncConfig {}

@Service
class ReportService {
  @Async
  public void emailReport(Long id) { … }   // fire-and-forget

  @Async
  public CompletableFuture<Report> build(Long id) {
    return CompletableFuture.completedFuture(slowBuild(id));
  }
}

The caller returns immediately; the work runs on a pool thread. The return type must be void or a Future/CompletableFuture — anything else can't be made async.

How the call is intercepted

caller→ proxy→ submit to executor→ pool thread runs it

Spring wraps the bean in a proxy. When you call emailReport(), the proxy submits a task to a TaskExecutor and returns. The real method runs later, on a borrowed thread.

Because it's a proxy, the same two rules as @Transactional apply: it only works through an injected reference, and self-invocation is invisible (next section).

2. The self-invocation gotcha (same as @Transactional)

@Service
class ReportService {
  public void run() {
    emailReport(1L);   // ⛔ plain "this" call
  }
  @Async public void emailReport(Long id) { … }
}

Runs synchronously on the caller's thread — the proxy was bypassed, so @Async never engaged.

@Service
class Caller {
  private final ReportService svc;  // injected
  public void run() {
    svc.emailReport(1L);  // ✅ via the proxy
  }
}

The call goes through the injected proxy, so the task is submitted to the pool. (Or self-inject, or use AopContext.currentProxy().)

4. The order that surprises everyone

Intuition says "fill core threads, then grow to max threads, then queue". It's the opposite. A ThreadPoolExecutor only creates threads beyond core once the queue is full:

1. fill core threads→ 2. fill the queue→ 3. grow to max threads→ 4. reject

The trap: set a huge queueCapacity (e.g. Integer.MAX_VALUE, the default for a plain unbounded queue) and step 2 never finishes — so steps 3 & 4 never happen and maxPoolSize is ignored. Your pool quietly stays at core size while work piles up in memory. Bound the queue if you want max threads to ever kick in.

5. Configuring the executor

A tuned ThreadPoolTaskExecutor

@Bean
ThreadPoolTaskExecutor taskExecutor() {
  var ex = new ThreadPoolTaskExecutor();
  ex.setCorePoolSize(2);
  ex.setQueueCapacity(4);     // bounded!
  ex.setMaxPoolSize(4);
  ex.setKeepAliveSeconds(60);  // reap idle overflow threads
  ex.setRejectedExecutionHandler(
      new ThreadPoolExecutor.CallerRunsPolicy());
  ex.setThreadNamePrefix("async-");
  ex.initialize();
  return ex;
}

Name a specific executor on the annotation: @Async("taskExecutor").

Defaults & virtual threads

  • Boot auto-configures an applicationTaskExecutor; tune it with spring.task.execution.pool.* properties (core-size, queue-capacity, max-size).
  • Rejection handlers: AbortPolicy (throws TaskRejectedException — the default), CallerRunsPolicy (runs it on the caller = built-in backpressure), DiscardPolicy, DiscardOldestPolicy.
  • Virtual threads (Boot 3.2+/4): set spring.threads.virtual.enabled=true and @Async runs each task on a fresh virtual thread — no pool sizing to agonize over for I/O-bound work.

6. Where do exceptions go?

Return typeWhat happens to a thrown exceptionHow to handle it
voidSwallowed — the caller already moved on, so it can't see itRegister an AsyncUncaughtExceptionHandler via AsyncConfigurer
CompletableFuture<T>Captured inside the future.exceptionally(...) / .handle(...), or it throws on .get()
 
@Configuration @EnableAsync
class AsyncConfig implements AsyncConfigurer {
  @Override public AsyncUncaughtExceptionHandler getAsyncUncaughtExceptionHandler() {
    return (ex, method, params) -> log.error("async {} failed", method.getName(), ex);
  }
}

Rule of thumb: if you care about the result or the failure, return a CompletableFuture. Reserve void for true fire-and-forget where a logged error is enough.

7. One-sentence recap

⚙️ @Async (with @EnableAsync) submits a void/CompletableFuture method to a TaskExecutor via a proxy (so self-invocation is a no-op, just like @Transactional), and the pool fills in the counter-intuitive order core → queue → max → reject — meaning an unbounded queue makes maxPoolSize dead code — so bound the queue, pick a RejectedExecutionHandler (CallerRunsPolicy for backpressure), and return a CompletableFuture whenever you need the result or the exception.
