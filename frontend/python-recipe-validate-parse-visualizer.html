Recipe — Validate & Parse Request Data

The backend side of "form data": let Pydantic turn an untyped JSON request into a parsed, typed, validated object — or an automatic 422 with precise field errors. In FastAPI, declaring a model parameter is the parsing + validation.

🐍 The pattern: declare a model → FastAPI parses, coerces & validates for you

On the server you never want to touch raw, untyped request data. The recipe: define a Pydantic BaseModel with typed fields, then declare it as a parameter of your FastAPI path operation — and the framework does the rest. When a request arrives, FastAPI reads the JSON body and hands it to the model, which performs three jobs at once. (1) Parse: it builds a real Python object from the dict. (2) Coerce: Pydantic intelligently converts compatible types — "30" → int 30, an ISO string → a datetime, "true" → bool — so you get clean, typed values instead of strings everywhere. (3) Validate: it enforces the field types and any constraints you declared — EmailStr, conint(gt=0), min_length, Field(pattern=...), plus custom @field_validator / @model_validator functions (e.g. "password and confirm must match"). If everything passes, your handler receives a fully-typed model instance and can trust every field. If anything fails, Pydantic raises a ValidationError that FastAPI turns into a 422 Unprocessable Entity whose body lists each problem with its location (loc), a human message (msg), and an error type — so the client can show the error on the exact field. The same model also documents the endpoint in the auto-generated OpenAPI/Swagger schema. The big idea: parsing and validation are one declarative step — you describe the shape, and bad data can't reach your business logic.

  • Declare — a Pydantic BaseModel with typed fields + constraints (EmailStr, Field(gt=0)…).
  • Parse + coerce — FastAPI feeds the JSON to the model; compatible types convert ("30"→int, ISO→datetime).
  • Validate — field + custom (@field_validator/@model_validator) rules run automatically.
  • Fail = 422 — a ValidationError becomes a structured 422 (loc/msg/type) per field.

The model

class SignUp(BaseModel): name: str = Field(min_length=1) email: EmailStr age: int = Field(gt=0, lt=120) joined: datetime # ISO str → datetime

The endpoint

@app.post("/signup") def signup(body: SignUp): # body is already parsed, # coerced & validated return { "id": save(body) }

Spring comparison

A Pydantic model parameter ≈ Spring's @Valid @RequestBody UserDTO. EmailStr/Field(gt=0) ≈ @Email/@Positive bean-validation annotations. @field_validator ≈ a custom ConstraintValidator. The auto 422 ≈ Spring's MethodArgumentNotValidException → 400 (often shaped via @ControllerAdvice + RFC 7807). Both make "the type IS the contract".

In your CIAM app: this is the FastAPI registration / profile / token-exchange handler. The Pydantic model is your input contract — it parses and validates before any logic runs, so an attacker can't slip a malformed or oversized payload past you. Use EmailStr, constrained ints/strings, and @model_validator for cross-field rules (password == confirm). The 422 body maps cleanly back onto the frontend form (the angular-recipe-api-form / react-recipe-api-form pages consume exactly this shape). Never echo secrets in errors, and remember validation is the gate even though the SPA also validates for UX.

or, the profile update that returned 200 and changed nothing

The problem

Every field validated. The response was a clean 200. And the value you sent never got saved — because Pydantic never even saw it.

A typo'd JSON key that nobody, and nothing, complained about

Your Angular profile form does a PATCH /me with { "nickName": "Bobby" }. The camelCase in the frontend TypeScript interface doesn't quite match the field you declared on the backend model, which is lowercase nickname: str | None = None. FastAPI hands the body to Pydantic. Validation passes. The handler runs. The client gets 200 OK.

The nickname never changes, because Pydantic's BaseModel ignores fields it doesn't recognize by default — model_config = ConfigDict(extra="ignore") is the out-of-the-box behavior. nickName gets silently dropped as an unknown extra field. nickname — the field the model actually declared — was never in the request at all, so it just keeps its default of None. Nothing failed. Nothing was even validated wrong. The update was simply a no-op that looked, from the outside, exactly like success.

the 422 machinery ✓ every declared field's constraints ✓ the field the client actually sent ⚠

Validation only ever inspects the fields your model KNOWS about. A typo doesn't fail validation — it just never enters the conversation.

Make an unrecognized field a hard error
Set model_config = ConfigDict(extra="forbid") on request models ↓ now nickName triggers its own 422 ("extra_forbidden") instead of vanishing — the typo surfaces on the very first request Keep extra="ignore" only where you mean it — e.g. models you feed a raw upstream JSON payload ↓ ignoring genuinely-optional passthrough fields is a real use case; the mistake is leaving it as the silent default on every INPUT model without deciding Round-trip the response: return the field you just wrote, not just {"ok": true} ↓ an endpoint that echoes back {"nickname": None} makes the no-op visible on the client's very next render, instead of hiding behind a bare success flag
"Validated" only covers what was declared, not what was sent. A Pydantic model is a whitelist, not a mirror of the request body. Extra keys aren't wrong by the model's rules — they're invisible to them. Silence from the validator means "everything I was told to check passed," never "everything you sent arrived."
A Pydantic model with default extra="ignore" is a bouncer checking IDs at a door with no guest list posted — anyone whose name isn't on the list doesn't get turned away loudly, they just don't get let in, and nobody at the door says a word about it.

The mechanism

Trace the same {"nickName": "Bobby"} body through three different model configurations.

  1. FastAPI reads the JSON body: {"nickName": "Bobby"}receive
  2. Pydantic walks the model's declared fields, looking for a match for each — case-sensitively, no fuzzy matchingmatch fields
  3. nickname (declared) has no corresponding key in the body → its default, None, is useddefault fills in
  4. nickName (sent) has no corresponding declared field → it is an "extra" keyextra key
  5. With the default extra="ignore", that extra key is discarded without commentdiscard
  6. The resulting object — nickname=None — passes every constraint it has, because it never had any on an absent optional fieldvalid, and wrong

Step 3 and step 4 are the same event seen from two directions: one declared field quietly falls back to its default, one sent field quietly gets thrown away. Neither half of that trade is visible anywhere in the response.

extra = "ignore" (the default) unrecognized key arrives → silently dropped, 200 OK
extra = "forbid" unrecognized key arrives → 422, error type "extra_forbidden"
extra = "allow" unrecognized key arrives → kept on model.model_extra, still 200

All three configurations are one word apart in your code and produce three completely different outcomes for the identical typo'd request. Nothing on the wire changes — only which of these three quiet policies your model happens to be running under.

A PATCH /me handler uses class UpdateProfile(BaseModel): bio: str | None = None with Pydantic's defaults. The client sends {"Bio": "Full-stack CIAM engineer"} (capital B, a frontend typo). What does the server do?

Pydantic's default field matching is case-sensitive — Bio and bio are different keys to it, full stop. There's no near-miss detection or casing tolerance built in without you adding it yourself (e.g. a custom alias generator).

Coercion converts compatible VALUES to a field's declared type ("30" → 30) — it never renames or matches KEYS for you. Casing is part of the key, and key matching is exact unless you configure aliases.

This is exactly what happens, and it's the trap: nothing about this request fails, because nothing about it violates any rule the model was given. The bug is in what the model was never told to check.

Where you have seen this before

"A silent default filled in where a real value should have been" isn't specific to Pydantic — it's what happens anywhere a schema tolerates the unknown by default.

Jackson's default deserialization in Spring

By default, Jackson (the JSON library behind @RequestBody) also ignores unknown properties unless you set FAIL_ON_UNKNOWN_PROPERTIES or annotate the DTO with @JsonIgnoreProperties(ignoreUnknown = false). A Spring UserDTO and a FastAPI UpdateProfile model make the identical silent choice unless you flip the identical switch.

unknown-field tolerance is an opt-out default in both ecosystems

An OIDC ID token with an unrecognized custom claim

A Ping/Entra ID token can carry a custom claim your client library's model doesn't map — a strict parser drops it into an "extra claims" bag or ignores it outright, same as extra="ignore". If your authorization logic checked the WRONG claim name, you get exactly this bug: a token that "validated fine" while the actual permission it needed to see never got read.

a claim you meant to read but never named right is a claim you never read

SQL's UPDATE ... SET with a misspelled column alias

An ORM or hand-written query that silently no-ops on a column name it can't map — rather than erroring — leaves a row looking successfully written while the value never moved. Same shape: the write path reports success because nothing it checked was wrong; what was wrong was never inside anything it checked.

success reported by a system only ever means "everything I checked was fine"
The whole page on a napkin: declare a Pydantic model, let FastAPI parse + coerce + validate the request body against it, and a failure becomes a structured 422 with loc/msg/type per field before your handler ever runs. The one new sentence this block adds: that safety net only catches fields the model actually declared — an unrecognized key isn't a validation failure, it's outside the net entirely, and Pydantic drops it without a sound unless you explicitly set extra="forbid".

1. Declare the model — parsing & coercion are free

from pydantic import BaseModel, EmailStr, Field
from datetime import datetime

class SignUp(BaseModel):
  name: str = Field(min_length=1, max_length=80)
  email: EmailStr # validates address format
  age: int = Field(gt=0, lt=120) # "30" → 30, then bounds-checked
  joined: datetime # "2026-06-18T10:00:00Z" → datetime
  active: bool = True # default if omitted
The type annotation is the parser and the validator. Pydantic reads each field's type and coerces compatible inputs: a numeric string becomes an int, an ISO-8601 string becomes a datetime, "true"/1 become bool. Field(...) attaches constraints (length, numeric bounds), and special types like EmailStr bring their own validation. Defaults make a field optional. You declared what good data looks like once — no manual int(request["age"]) with a try/except in sight.

2. Use it in the endpoint — the body arrives validated

from fastapi import FastAPI
app = FastAPI()

@app.post("/signup")
def signup(body: SignUp): # declaring the type triggers parse+validate
  # if we get here, every field is present, typed and within bounds
  user_id = save_user(body.name, body.email, body.age)
  return {"id": user_id, "joined": body.joined.isoformat()}
Declaring body: SignUp is the whole integration. FastAPI sees the type hint, pulls the JSON body, and runs it through the model before your function executes. Inside the handler you work with a typed object (body.age is an int, body.joined is a datetime) and never re-check anything — invalid requests never reach this code. The same model also feeds the auto-generated OpenAPI docs, so the contract, the validation, and the docs can't drift apart.

3. Cross-field rules with a validator

from pydantic import field_validator, model_validator

class SignUp(BaseModel):
  password: str = Field(min_length=12)
  confirm: str

  @field_validator("password")
  @classmethod
  def not_common(cls, v):
    if v.lower() in COMMON: raise ValueError("too common")
    return v

  @model_validator(mode="after")
  def passwords_match(self):
    if self.password != self.confirm: raise ValueError("passwords differ")
    return self
Custom rules live on the model, close to the data. A @field_validator validates one field (reject a common password); a @model_validator(mode="after") sees the whole object, so it can compare fields (password == confirm). Raising ValueError inside either is automatically collected into the same 422 with the right loc. This keeps validation declarative and co-located with the schema instead of scattered through the handler — and it composes with the field constraints from step 1.
