Go: Testing

Table-driven tests and subtests, the testing.T API, benchmarks, fuzzing, and the race detector — Go's batteries-included test toolchain, no framework required.

🔬 How does Go test without JUnit, Mockito, or an assertion library?

Testing is in the stdlib and the go test command — no framework. Tests live in *_test.go as func TestXxx(t *testing.T). The dominant idiom is the table-driven test: a slice of case structs each run as a named subtest via t.Run — isolated, filterable with -run. There's deliberately no assertion library: t.Errorf records and continues, t.Fatalf records and stops. Benchmarks (BenchmarkXxx) loop b.N times with the framework tuning N; fuzzing (FuzzXxx, Go 1.18+) mutates seeded inputs to hunt crashes and saves failing cases as regressions. The race detector (go test -race) catches data races at runtime, and -cover/t.Parallel()/t.Cleanup round it out — mocking is usually a hand-written struct satisfying an interface.

  • Table-driven + subtests — case slice, t.Run, filter with -run.
  • No assertion lib — t.Errorf continues, t.Fatalf stops; mocks are plain structs.
  • Benchmarks + fuzzing built in — b.N tuning, mutated inputs saved as regressions.
  • -race + -cover — race detector and coverage in the same command.

Table-driven + subtests

func TestAbs(t *testing.T) { cases := []struct{ name string; in, want int }{ {"pos", 3, 3}, {"neg", -3, 3}, {"zero", 0, 0}, } for _, tc := range cases { t.Run(tc.name, func(t *testing.T) { if got := Abs(tc.in); got != tc.want { t.Errorf("Abs(%d)=%d want %d", tc.in, got, tc.want) } }) } }

Benchmark

func BenchmarkAbs(b *testing.B) { for i := 0; i < b.N; i++ { Abs(-42) } } // go test -bench=. -benchmem // BenchmarkAbs-8 1000000000 0.31 ns/op 0 B/op 0 allocs/op // b.N is chosen by the framework // until the result is stable

Go testing vs JUnit

JUnit: annotations (@Test, @BeforeEach), an assertion lib (assertEquals), Mockito for mocks, JMH for benchmarks — all separate dependencies. Go: convention over annotation (TestXxx), failures via plain if got != want { t.Errorf() }, benchmarks and fuzzing built into the same go test, and the race detector is a compiler flag. Mocking is usually just a hand-written struct that satisfies an interface — no framework. Less magic, fewer dependencies, one command.

CIAM context: Table-driven tests fit an IdM authority mapper perfectly — each case is {name, idmClaims, wantAuthorities} across entra/ping/keycloak/spring shapes, one table proving the whole normalization. Run go test -race on the token cache to prove concurrent reads + refreshes are safe (a data race in a cache is a security bug). And fuzz the JWT/base64 parser so a malformed token returns an error instead of panicking and taking down the auth service.

Or: your cleanup runs before the tests it's supposed to clean up after.

The problem

You did everything the table-driven pattern teaches. Your parallel subtests still fail against a resource that's already gone.

defer db.Close() fires while the parallel subtests are still queued, not finished

TestUserQueries opens a test database, defer db.Close()s it right after (textbook Go), then loops over cases calling t.Run(tc.name, func(t *testing.T){ t.Parallel(); /* query db */ }). Every subtest looks correct. With one case, it passes every time.

Add a few more cases and it gets flaky: some subtests fail with "sql: database is closed." The moment ANY subtest calls t.Parallel(), Go pauses it right there and returns control to the for loop immediately — it does not wait for the subtest to finish. The loop finishes fast, TestUserQueries's own body returns, and its defer db.Close() fires — all before any of the paused parallel subtests have resumed past their t.Parallel() call and actually touched db.

table-driven pattern ✓ defer right after setup ✓ defer's timing relative to t.Parallel() ⚠

t.Parallel() doesn't just mark a test "run me concurrently" — it hands control straight back to whatever called t.Run, right now, before the subtest body below it has executed a single further line.

Scope the cleanup to outlive the parallel subtests, not the loop
Wrap the whole table in one outer t.Run("group", func(t *testing.T) {...}) ↓ the outer Run call blocks until every parallel child it contains has actually finished — unlike the bare test function Put the loop of parallel t.Run calls INSIDE that group closure ↓ now TestUserQueries's own defer only fires after the group (and its parallel children) are truly done Or use t.Cleanup registered per-subtest instead of one defer in the parent
A parallel subtest pauses at t.Parallel(); it does not block its caller there. The t.Run call that launched it returns almost immediately once the child hits t.Parallel(). Everything after that — including the rest of the loop, and any code in the enclosing test function after the loop, including its defers when the function returns — runs BEFORE the parallel subtest's remaining body does.
Think of t.Parallel() as a subtest saying "hold my seat, I'll be right back" and then stepping out of line entirely — the line (your loop) keeps moving without them. If the parent function was holding a resource meant to be released "once everyone's done," releasing it the moment the line is empty is way too early; the people who stepped out haven't come back yet.
You

I put defer right after I opened the resource — isn't that the idiomatic, safe pattern?

Go's testing package

It's exactly right for a defer whose owner is the function it's declared in — I run it the instant that function's body returns, no matter what's still pending elsewhere.

You

But my subtests are "still pending elsewhere" when that happens?

Go's testing package

Correct — a parallel subtest paused at t.Parallel() belongs to a later phase I run after the non-parallel work at this level finishes, including your enclosing function returning. Your defer doesn't know that phase exists. It just sees its function end.

The mechanism

Trace one table test from "defer scheduled" to "subtests actually run" and watch where the gap opens up.

  1. TestUserQueries opens db; defer db.Close() is registereddefer armed
  2. for _, tc := range cases { t.Run(tc.name, func(t *testing.T){ t.Parallel(); ... }) }loop starts
  3. Each subtest hits t.Parallel() almost immediately and pauses — control returns to the loop right awaypause, don't block
  4. The for loop finishes fast; TestUserQueries's body has nothing left to runparent body ends
  5. TestUserQueries returns → its deferred db.Close() executes NOWdefer fires
  6. Only after that does the test framework resume the paused subtests — some now query a closed dbtoo late

The gap is between steps 3 and 6: everything a subtest does after t.Parallel() is deferred to a later phase the framework controls, but step 5's defer doesn't know that phase is coming — it only knows TestUserQueries's function body just returned.

TestUserQueries's function body returnsright after queuing 5 paused parallel subtests
everything that fires at that instant ↓
"--- PASS: TestUserQueries" is NOT yet printed the deferred db.Close() runs — right now the next top-level test function may start

The surprising reactor is the middle one. Nothing about "TestUserQueries returned" sounds like it should mean "and now its subtests' shared database is gone" — but that's exactly what a plain defer in the parent gives you.

TestFoo does db := openTestDB(); defer db.Close(), then loops calling t.Run(tc.name, func(t *testing.T){ t.Parallel(); useDB(t, db) }) for 5 cases. Which best describes the actual execution order?

That's the order everyone expects from reading top-to-bottom — and it's exactly backwards for parallel subtests. t.Run does not wait for a t.Parallel() child to finish before returning to the loop.

t.Parallel() pauses the subtest and hands control back to the loop immediately. Once the loop (and the rest of TestFoo) finishes, TestFoo returns and its defer fires — before the paused subtests resume and actually call useDB. That race is what makes this flaky rather than reliably broken: it depends on scheduling.

t.Parallel() has nothing to do with defer semantics, and it's never ignored — it always pauses the calling subtest and queues it to run concurrently with its siblings once the parent's non-parallel work is done.

Where you have seen this before

"The cleanup fired at the wrong scope" is really an ownership bug wearing a testing-framework costume.

JUnit's @AfterAll with untracked async work

A JUnit @AfterAll that closes a shared resource runs once all test methods in the class finish — but if a test kicks off async work JUnit can't see (a raw thread, an unjoined future), @AfterAll can fire while that work is still touching the resource. Same ownership mismatch.

the framework's "done" doesn't cover work it can't see

try-with-resources closing before an async callback runs

try (var conn = pool.getConnection()) { conn.queryAsync(cb); } closes conn the instant the try block exits — if cb runs later on another thread, it's holding a reference to an already-closed connection. Same defer-vs-async shape.

synchronous cleanup syntax, asynchronous actual work

A React useEffect cleanup racing a fetch

useEffect(() => { fetch(url).then(setData); return () => { cancelled = true } }, []) — the cleanup can run (component unmounts) before the fetch resolves, and without checking a cancellation flag you call setState on an unmounted component.

the cleanup's timing is decided by the framework, not the code's visual order

The one new sentence this block adds: a defer in the enclosing test function fires the moment that function's body returns, which — thanks to how t.Parallel() pauses and re-queues a subtest — happens before its parallel children resume, so shared-resource cleanup belongs in t.Cleanup or an outer grouping t.Run, never a bare parent-level defer.

1. Table-Driven Tests & Subtests

cases := []struct {
  name string
  in, want int
}{
  {"pos", 3, 3},
  {"neg", -3, 3},
}
for _, tc := range cases {
  t.Run(tc.name, func(t *testing.T) {
    if got := Abs(tc.in); got != tc.want {
      t.Errorf("Abs(%d)=%d want %d", tc.in, got, tc.want)
    }
  })
}

Each case becomes a named subtest: go test -run TestAbs/neg runs just one. Subtests isolate failures (one bad case does not hide the others), give clear names in output, and can call t.Parallel() to run concurrently. Adding a case is one line — which is why this pattern scales to dozens of inputs without copy-pasted test functions.

Parallel subtest gotcha (pre-Go 1.22): capturing the loop variable tc inside a t.Parallel() subtest used to need tc := tc shadowing, or every subtest saw the last case. Go 1.22+ gives each iteration its own variable, so the footgun is gone — but you'll still see tc := tc in older code.

2. The testing.T API

CallEffect
t.Errorf(...) / t.Error(...)mark the test failed, keep running (collect multiple failures)
t.Fatalf(...) / t.Fatal(...)mark failed and stop this test now (use when continuing is pointless)
t.Helper()mark a function as a test helper so failures report the caller's line
t.Cleanup(fn)register teardown that runs when the test (and its subtests) finish
func TestMain(m *testing.M)package-wide setup/teardown around m.Run() (spin up a DB, then os.Exit)
t.Fatal must be called from the test's own goroutine. Calling it inside a spawned goroutine does not stop the test correctly — send the error back over a channel and t.Fatal on the main test goroutine instead.

3. Benchmarks

func BenchmarkParse(b *testing.B) {
  data := buildInput() // setup not timed…
  b.ResetTimer() // …because we reset here
  for i := 0; i < b.N; i++ {
    Parse(data)
  }
}
// go test -bench=. -benchmem

The framework runs the loop, increasing b.N until timing is statistically stable, then reports ns/op. b.ResetTimer() excludes setup; b.ReportAllocs() (or -benchmem) adds B/op and allocs/op — often more telling than raw speed. Compare two runs with benchstat to see if a change is real signal or noise.

Stop the compiler from optimizing your benchmark away: assign the result to a package-level sink (var Sink int; ... Sink = Parse(data)). If nothing uses the return value, the optimizer may delete the call and you'll "benchmark" nothing — a deceptively fast 0.3 ns/op.

4. Fuzzing, the Race Detector & Coverage

func FuzzParseJWT(f *testing.F) {
  f.Add("a.b.c") // seed corpus
  f.Fuzz(func(t *testing.T, raw string) {
    _, _ = ParseJWT(raw) // must not panic on ANY input
  })
}
// go test -fuzz=FuzzParseJWT → mutates inputs; saves crashers to testdata/fuzz/
// go test -race → flags concurrent unsynchronized memory access
// go test -cover → % statements covered (-coverprofile for HTML)
ToolCatches
-fuzzinputs that panic or break a round-trip/invariant; a failing input is saved as a permanent seed
-racedata races (two goroutines touch the same memory, one writing, without synchronization)
-coverstatement coverage; -coverprofile=c.out && go tool cover -html=c.out for a visual map
The race detector finds real races, not all races. It only reports a race it actually observes at runtime, so run it against tests that exercise real concurrency (-race in CI is standard). A clean -race run is strong evidence, not a proof of absence.
