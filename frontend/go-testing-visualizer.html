Go: Testing

Table-driven tests and subtests, the testing.T API, benchmarks, fuzzing, and the race detector — Go's batteries-included test toolchain, no framework required.

How does Go test without JUnit, Mockito, or an assertion library?

Testing is part of Go's standard library and the go test command — no framework to add. Tests live next to the code in *_test.go files; a test is func TestXxx(t *testing.T). The dominant idiom is the table-driven test: a slice of case structs, each executed as a named subtest via t.Run(name, func(t *testing.T){...}) — isolated, individually filterable with -run, and reportable on their own. There is deliberately no assertion library in the stdlib: you call t.Errorf to record a failure and keep going, or t.Fatalf to record and stop that test. (testify is popular but optional.) Benchmarks are func BenchmarkXxx(b *testing.B) that loop b.N times — the framework tunes N until the timing is stable, and -benchmem reports allocations. Fuzzing (Go 1.18+) is func FuzzXxx(f *testing.F): you seed a corpus with f.Add and the engine mutates inputs to hunt for crashes or broken invariants, saving any failing input to testdata/fuzz so it becomes a permanent regression test. And the race detector (go test -race) instruments memory access to catch data races at runtime. Coverage comes from -cover; t.Parallel() runs tests concurrently; t.Cleanup and TestMain handle teardown/setup.

Table-driven + subtests

func TestAbs(t *testing.T) { cases := []struct{ name string; in, want int }{ {"pos", 3, 3}, {"neg", -3, 3}, {"zero", 0, 0}, } for _, tc := range cases { t.Run(tc.name, func(t *testing.T) { if got := Abs(tc.in); got != tc.want { t.Errorf("Abs(%d)=%d want %d", tc.in, got, tc.want) } }) } }

Benchmark

func BenchmarkAbs(b *testing.B) { for i := 0; i < b.N; i++ { Abs(-42) } } // go test -bench=. -benchmem // BenchmarkAbs-8 1000000000 0.31 ns/op 0 B/op 0 allocs/op // b.N is chosen by the framework // until the result is stable

Go testing vs JUnit

JUnit: annotations (@Test, @BeforeEach), an assertion lib (assertEquals), Mockito for mocks, JMH for benchmarks — all separate dependencies. Go: convention over annotation (TestXxx), failures via plain if got != want { t.Errorf() }, benchmarks and fuzzing built into the same go test, and the race detector is a compiler flag. Mocking is usually just a hand-written struct that satisfies an interface — no framework. Less magic, fewer dependencies, one command.

In a CIAM context: Table-driven tests are perfect for an IdM authority mapper: each case is {name, idmClaims, wantAuthorities} across entra / ping / keycloak / spring shapes — one table proves the whole normalization. Run go test -race on a token cache to prove concurrent reads and refreshes are safe (a data race in a cache is a security bug). And fuzz the JWT/base64 parser — f.Fuzz(func(t, raw []byte){ parseJWT(raw) }) — to ensure a malformed token returns an error instead of panicking and taking down the auth service.

1. Table-Driven Tests & Subtests

cases := []struct {
  name string
  in, want int
}{
  {"pos", 3, 3},
  {"neg", -3, 3},
}
for _, tc := range cases {
  t.Run(tc.name, func(t *testing.T) {
    if got := Abs(tc.in); got != tc.want {
      t.Errorf("Abs(%d)=%d want %d", tc.in, got, tc.want)
    }
  })
}

Each case becomes a named subtest: go test -run TestAbs/neg runs just one. Subtests isolate failures (one bad case does not hide the others), give clear names in output, and can call t.Parallel() to run concurrently. Adding a case is one line — which is why this pattern scales to dozens of inputs without copy-pasted test functions.

Parallel subtest gotcha (pre-Go 1.22): capturing the loop variable tc inside a t.Parallel() subtest used to need tc := tc shadowing, or every subtest saw the last case. Go 1.22+ gives each iteration its own variable, so the footgun is gone — but you'll still see tc := tc in older code.

2. The testing.T API

CallEffect
t.Errorf(...) / t.Error(...)mark the test failed, keep running (collect multiple failures)
t.Fatalf(...) / t.Fatal(...)mark failed and stop this test now (use when continuing is pointless)
t.Helper()mark a function as a test helper so failures report the caller's line
t.Cleanup(fn)register teardown that runs when the test (and its subtests) finish
func TestMain(m *testing.M)package-wide setup/teardown around m.Run() (spin up a DB, then os.Exit)
t.Fatal must be called from the test's own goroutine. Calling it inside a spawned goroutine does not stop the test correctly — send the error back over a channel and t.Fatal on the main test goroutine instead.

3. Benchmarks

func BenchmarkParse(b *testing.B) {
  data := buildInput() // setup not timed…
  b.ResetTimer() // …because we reset here
  for i := 0; i < b.N; i++ {
    Parse(data)
  }
}
// go test -bench=. -benchmem

The framework runs the loop, increasing b.N until timing is statistically stable, then reports ns/op. b.ResetTimer() excludes setup; b.ReportAllocs() (or -benchmem) adds B/op and allocs/op — often more telling than raw speed. Compare two runs with benchstat to see if a change is real signal or noise.

Stop the compiler from optimizing your benchmark away: assign the result to a package-level sink (var Sink int; ... Sink = Parse(data)). If nothing uses the return value, the optimizer may delete the call and you'll "benchmark" nothing — a deceptively fast 0.3 ns/op.

4. Fuzzing, the Race Detector & Coverage

func FuzzParseJWT(f *testing.F) {
  f.Add("a.b.c") // seed corpus
  f.Fuzz(func(t *testing.T, raw string) {
    _, _ = ParseJWT(raw) // must not panic on ANY input
  })
}
// go test -fuzz=FuzzParseJWT → mutates inputs; saves crashers to testdata/fuzz/
// go test -race → flags concurrent unsynchronized memory access
// go test -cover → % statements covered (-coverprofile for HTML)
ToolCatches
-fuzzinputs that panic or break a round-trip/invariant; a failing input is saved as a permanent seed
-racedata races (two goroutines touch the same memory, one writing, without synchronization)
-coverstatement coverage; -coverprofile=c.out && go tool cover -html=c.out for a visual map
The race detector finds real races, not all races. It only reports a race it actually observes at runtime, so run it against tests that exercise real concurrency (-race in CI is standard). A clean -race run is strong evidence, not a proof of absence.
