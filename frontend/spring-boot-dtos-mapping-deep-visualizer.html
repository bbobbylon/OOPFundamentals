DTOs & Mapping

A DTO (Data Transfer Object) is the shape you put on the wire — deliberately separate from your @Entity, which is the shape in your database. Conflating the two is the single most common way Spring apps leak data, throw lazy-loading errors, and become impossible to evolve. Here's why you map, and how.

🔁 Why do you need DTOs — why not just return the @Entity from the controller?

Returning a @Entity straight from a @RestController is the classic beginner mistake. The entity is your DB mapping: it exposes every column, every @OneToMany relation, every internal field. Suddenly passwordHash is in the JSON, serializing a lazy roles collection throws LazyInitializationException (the transaction already ended), and renaming a DB column silently changes the API and breaks Angular. A DTO (Data Transfer Object) is a separate class that says exactly what goes on the wire — no more, no less — and entity ↔ DTO mapping is the translation layer between your persistence model and your API contract.

  • The entity is for the DB; the DTO is for the client. Keep the two contracts independent.
  • Three failures of entity-as-DTO: data leakage, lazy-loading exceptions, schema/API coupling.
  • Map explicitly or with MapStruct — compile-time codegen, zero runtime cost.
  • Separate request and response DTOs so a client can't set fields like id it shouldn't.

Three problems it causes

1. Data leakage — passwordHash, internal flags, FK IDs in the response. 2. LazyInitializationException — Jackson serializes a LAZY collection after the tx closed. 3. Coupling — a DB rename changes the API field and breaks Angular. DTOs decouple all three.

Manual vs MapStruct

Manual: new UserDto(u.getId(), u.getEmail(), u.getRoles().stream().map(Role::getName).toList()) — explicit but repetitive. MapStruct: @Mapper interface UserMapper { UserDto toDto(User u); } and Spring generates the impl at compile time (nested objects, conversions, no runtime cost).

Request vs response DTOs

CreateUserRequest has email/displayName/roles but no id; UserResponse has id/status/createdAt but no passwordHash; UpdateUserRequest only the editable fields. Separate classes kill the "client sets id" bug.

CIAM: UserResponse { Long id; String email; List<String> roleNames; UserStatus status; LocalDateTime createdAt; String createdBy; } — no passwordHash, no FK IDs. CreateUserRequest { @Email String email; @NotBlank String displayName; List<UUID> roleIds; }. The DTO layer also exposes computed fields like boolean locked = lockoutUntil != null && lockoutUntil.isAfter(now()) — two entity fields presented to Angular as one boolean.

1. The entity is for the database. The DTO is for the client.

Your JPA @Entity is shaped by your schema: every column, every relation, every internal flag. The JSON your API returns should be shaped by your contract: only what the client needs, named the way the client expects. Returning the entity directly couples those two — and they pull in opposite directions.

@Entity User (DB row)— map —> UserResponse (JSON)→ client

The mapping layer is a firewall: it decides exactly what crosses the boundary, in both directions.

3. Three concrete ways a raw entity bites you

① Accidental field leaks

Add a passwordHash or ssn column next year and — because the controller serializes the whole entity — it silently appears in every API response. A DTO only ever contains fields you wrote down on purpose.

② Lazy-loading blow-ups

Serializing a LAZY relation after the transaction closed throws LazyInitializationException. Make it EAGER + bidirectional and Jackson recurses user→orders→user→… forever (or you N+1 the DB). A DTO flattens it to orderCount.

③ You can't evolve it

Rename a column and you break every client. The entity now serves two masters — DB migrations and the public contract. A DTO decouples them: rename the column, keep the JSON field, map between.

4. Request vs Response DTOs — and why records are perfect

Request DTO — what you accept

// Immutable, validated, NO server-set fields
// (no id, no createdAt, no isAdmin!)
public record CreateUserRequest(
    @NotBlank String username,
    @Email String email,
    @Size(min = 8) String password
) {}

@PostMapping("/api/v1/users")
UserResponse create(@Valid @RequestBody CreateUserRequest req){
  var saved = repo.save(req.toEntity(encoder));
  return UserResponse.from(saved);
}

A request DTO is an allow-list of inputs. The client literally cannot set isAdmin — the field doesn't exist on the way in. This kills mass-assignment / over-posting bugs.

Response DTO — what you return

// Only safe fields, renamed/flattened
public record UserResponse(
    Long id,
    String username,
    String email,
    String memberSince,
    int orderCount
) {
  // static factory = the mapping
  static UserResponse from(User u){
    return new UserResponse(
      u.getId(), u.getUsername(), u.getEmail(),
      u.getCreatedAt().getYear()+"",
      u.getOrders().size());   // flatten, no leak
  }
}

Records give you immutability, a canonical constructor, and equals/hashCode/toString for free — the ideal DTO. Request and response are separate types: they have different fields and different lifecycles.

5. Three ways to do the mapping

Static factory simplest

UserResponse.from(user)

A hand-written from(entity) on the DTO. Zero dependencies, fully explicit, trivial to read. Great default until the mappings get numerous.

MapStruct at scale

@Mapper(componentModel="spring")
interface UserMapper {
  UserResponse toDto(User u);
}

Generates the boilerplate at compile time (no reflection). Inject the mapper. Pays off when you have many DTOs; matches fields by name, configure the rest.

JPQL projection fastest

@Query("""
  select new com..UserResponse(
    u.id, u.username, u.email)
  from User u"")
List<UserResponse> findAllAsDto();

The DB returns the DTO directly — only the selected columns are read, no entity is ever materialized. Best for read-heavy list endpoints. (Spring Data interface projections do the same.)

Rule of thumb: start with a static from() factory. Reach for MapStruct when the number of mappings becomes tedious. Use a JPQL/interface projection when a read endpoint is hot and you want to avoid loading whole entities. All three keep the entity off the wire — that's the part that matters.

6. One DTO per use-case > one fat DTO

It's tempting to make a single UserDto and reuse it everywhere. Resist it — different endpoints need different shapes, and a shared DTO drifts toward exposing everything to everyone.

Use-caseDTOShape
Create userCreateUserRequestusername, email, password  in
Update profileUpdateProfileRequestemail only  in
User in a listUserSummaryid, username  out
User detail pageUserResponseid, username, email, memberSince, orderCount  out
Admin viewAdminUserView+ isAdmin, failedLoginCount  out, secured

Small, single-purpose DTOs are self-documenting and safe: each one's field list is the contract for that endpoint. Need to expose more to admins? That's a different DTO behind a different authorization rule — not a field you forgot to hide.

7. One-sentence recap

🧱 A DTO is the deliberate, client-facing shape of your data — keep it separate from the @Entity so you never leak sensitive fields, never serialize a lazy relation, and can evolve your schema and your API independently: use records for request & response DTOs, @Valid the requests, map with a static from() / MapStruct / JPQL projection, and prefer one DTO per use-case over one fat shared one.
