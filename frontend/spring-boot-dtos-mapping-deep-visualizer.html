DTOs & Mapping

A DTO (Data Transfer Object) is the shape you put on the wire — deliberately separate from your @Entity, which is the shape in your database. Conflating the two is the single most common way Spring apps leak data, throw lazy-loading errors, and become impossible to evolve. Here's why you map, and how.

🔁 Why do you need DTOs — why not just return the @Entity from the controller?

Returning a @Entity straight from a @RestController is the classic beginner mistake. The entity is your DB mapping: it exposes every column, every @OneToMany relation, every internal field. Suddenly passwordHash is in the JSON, serializing a lazy roles collection throws LazyInitializationException (the transaction already ended), and renaming a DB column silently changes the API and breaks Angular. A DTO (Data Transfer Object) is a separate class that says exactly what goes on the wire — no more, no less — and entity ↔ DTO mapping is the translation layer between your persistence model and your API contract.

  • The entity is for the DB; the DTO is for the client. Keep the two contracts independent.
  • Three failures of entity-as-DTO: data leakage, lazy-loading exceptions, schema/API coupling.
  • Map explicitly or with MapStruct — compile-time codegen, zero runtime cost.
  • Separate request and response DTOs so a client can't set fields like id it shouldn't.

Three problems it causes

1. Data leakage — passwordHash, internal flags, FK IDs in the response. 2. LazyInitializationException — Jackson serializes a LAZY collection after the tx closed. 3. Coupling — a DB rename changes the API field and breaks Angular. DTOs decouple all three.

Manual vs MapStruct

Manual: new UserDto(u.getId(), u.getEmail(), u.getRoles().stream().map(Role::getName).toList()) — explicit but repetitive. MapStruct: @Mapper interface UserMapper { UserDto toDto(User u); } and Spring generates the impl at compile time (nested objects, conversions, no runtime cost).

Request vs response DTOs

CreateUserRequest has email/displayName/roles but no id; UserResponse has id/status/createdAt but no passwordHash; UpdateUserRequest only the editable fields. Separate classes kill the "client sets id" bug.

CIAM: UserResponse { Long id; String email; List<String> roleNames; UserStatus status; LocalDateTime createdAt; String createdBy; } — no passwordHash, no FK IDs. CreateUserRequest { @Email String email; @NotBlank String displayName; List<UUID> roleIds; }. The DTO layer also exposes computed fields like boolean locked = lockoutUntil != null && lockoutUntil.isAfter(now()) — two entity fields presented to Angular as one boolean.

or, MapStruct's build-time safety net catches missing fields — never wrong ones

The problem

The build succeeded. The mapper was generated cleanly. The response still leaks an internal-only value.

UserResponse.status comes back looking suspiciously like an internal enum name

User.status holds internal lifecycle codes — ACTIVE, LOCKED_FRAUD, PENDING_DELETION — never meant to leave the server. Independently, someone adds a field to UserResponse also called status, intending it to mean something simple and client-safe. @Mapper(componentModel = "spring") interface UserMapper { UserResponse toDto(User u); } builds clean — no @Mapping lines needed, zero warnings, the exact "unmapped field caught at build time" safety story this page just told you. Ship it, and GET /users/42 for a locked account returns "status": "LOCKED_FRAUD" straight to the client.

build passed, zero MapStruct warnings ✓ @Mapper generated cleanly ✓ both sides happen to be named "status" ⚠ one means internal lifecycle, the other was meant to mean something else entirely ⚠

MapStruct's build-time check answers "did every target field get SOMETHING." It never asks whether it got the RIGHT thing.

MapStruct proves completeness, not correctness. Its build-time policy answers exactly one question: does every target property have a source property with the same name? It has no idea what either field means. Two fields can share a name by pure coincidence — one entity's internal lifecycle code, one DTO's intended public status — and MapStruct wires them together exactly as confidently as it wires two fields that were always meant to travel together.
Think of MapStruct's name matching as a mail-sorting robot that reads only the label on the front of the envelope. Two departments both label outgoing mail "STATUS UPDATE" — one means building maintenance, the other means a personnel file — and the robot cheerfully delivers each to whichever inbox is ALSO labeled "STATUS UPDATE," with total confidence, because the labels matched perfectly. The robot never once opened either envelope to check what was inside.

The mechanism

MapStruct's whole safety story is "nothing gets left unmapped." It says nothing about whether what got mapped should have been.

  1. User.status holds an internal lifecycle code — values include LOCKED_FRAUD, never meant to leave the serveran entity-only concept
  2. A UserResponse record independently gains a field also named status, meant to mean something client-safesame name, different job
  3. MapStruct's annotation processor matches target properties to source properties by name — status to statusthe entire matching algorithm
  4. Both names resolve, so it silently generates userResponse.setStatus(user.getStatus()) — no @Mapping line, no warninga SUCCESS from MapStruct's point of view
  5. The unmapped-property check — the safety net the page above relies on — never fires, because nothing is unmappedthe safety net can't see this failure case
  6. GET /users/42 returns "status": "LOCKED_FRAUD" straight to the client, in a totally green buildthe leak the compiler was never asked to catch

Step 3 is the lesson. MapStruct's matching algorithm has exactly one signal available to it: the property name. It has no way to know that two classes meant two completely different things by status — that knowledge exists only in a human's head, and it only becomes real the moment someone writes an explicit @Mapping (or renames one of the two fields) to say so out loud.

Where you've seen this before

Three systems, one trap: matching by name isn't the same as matching by meaning.

.NET's AutoMapper — the same convention, the same blind spot

AutoMapper's default convention wires two classes' properties together by name, exactly like MapStruct, and its AssertConfigurationIsValid() catches unmapped members at startup — exactly the same completeness check. It has the identical gap: two same-named properties with different intended meanings pass that validation with total confidence, because validation never inspects meaning, only presence.

AssertConfigurationIsValid() ≈ unmappedTargetPolicy

ETL pipelines matching CSV headers

A data pipeline importing a partner's CSV maps columns by header name — their amount column means cents, yours means dollars. Matched, loaded, off by 100x, silently, because the loader's whole job was "does a column named amount exist," never "does it mean what we mean." Same coincidence, no code generation anywhere in sight.

header-name matching ≈ property-name matching

Your CIAM SCIM provisioning sync

An identity provider's SCIM payload has an active boolean meaning "enabled in the IdP." Your own User.active was quietly repurposed months ago to mean "has completed onboarding." A sync mapper wired by field name flips onboarding status every time the IdP toggles a completely unrelated concept — the exact same collision, now silently corrupting account state instead of leaking a string.

SCIM active ≠ your active, same name
Questions from the back row

Can I configure MapStruct to actually catch this?

Not the semantic mismatch itself — no tool can know what you meant by a name. What you can do is shrink the coincidence surface: keep a naming convention that makes internal-only entity fields visually distinct, and treat any newly-added same-named field pair as something a code reviewer explicitly confirms rather than assumes. unmappedTargetPolicy = ERROR still earns its keep for the OTHER failure mode — it just isn't this one.

Would a manual static from() factory have caught this instead?

Only as well as the person writing it. A hand-written mapper has no build-time unmapped-field check at all — but it also lacks this specific blind spot, because whoever writes new UserResponse(u.getId(), transform(u.getStatus()), …) has to look at u.getStatus() at least once and consciously decide what to do with it, even if they decide wrong. You trade completeness (MapStruct) for forced attention (manual) — nothing here gives you both for free.

Does an explicit @Mapping with ignore=true plus a manual setter fix this properly?

Yes — that's exactly the right shape. Telling MapStruct "don't auto-wire this one," then setting the client-safe value yourself (directly or via an @AfterMapping method), turns an invisible coincidence into a visible, intentional line inside the mapper interface. The fix was never smarter tooling — it's making the decision visible to the next person who reads the mapper.

1. The entity is for the database. The DTO is for the client.

Your JPA @Entity is shaped by your schema: every column, every relation, every internal flag. The JSON your API returns should be shaped by your contract: only what the client needs, named the way the client expects. Returning the entity directly couples those two — and they pull in opposite directions.

@Entity User (DB row)— map —> UserResponse (JSON)→ client

The mapping layer is a firewall: it decides exactly what crosses the boundary, in both directions.

3. Three concrete ways a raw entity bites you

① Accidental field leaks

Add a passwordHash or ssn column next year and — because the controller serializes the whole entity — it silently appears in every API response. A DTO only ever contains fields you wrote down on purpose.

② Lazy-loading blow-ups

Serializing a LAZY relation after the transaction closed throws LazyInitializationException. Make it EAGER + bidirectional and Jackson recurses user→orders→user→… forever (or you N+1 the DB). A DTO flattens it to orderCount.

③ You can't evolve it

Rename a column and you break every client. The entity now serves two masters — DB migrations and the public contract. A DTO decouples them: rename the column, keep the JSON field, map between.

4. Request vs Response DTOs — and why records are perfect

Request DTO — what you accept

// Immutable, validated, NO server-set fields
// (no id, no createdAt, no isAdmin!)
public record CreateUserRequest(  // a record's fields ARE the constructor params — no getter/setter boilerplate
    @NotBlank String username,
    @Email String email,
    @Size(min = 8) String password
) {}

@PostMapping("/api/v1/users")
UserResponse create(@Valid @RequestBody CreateUserRequest req){
  var saved = repo.save(req.toEntity(encoder));  // converts DTO → entity here, hashing the password before it's ever saved
  return UserResponse.from(saved);
}

A request DTO is an allow-list of inputs. The client literally cannot set isAdmin — the field doesn't exist on the way in. This kills mass-assignment / over-posting bugs.

Response DTO — what you return

// Only safe fields, renamed/flattened
public record UserResponse(  // a completely different shape than the entity — no password field even exists to leak
    Long id,
    String username,
    String email,
    String memberSince,
    int orderCount
) {
  // static factory = the mapping
  static UserResponse from(User u){
    return new UserResponse(
      u.getId(), u.getUsername(), u.getEmail(),
      u.getCreatedAt().getYear()+"",
      u.getOrders().size());   // flatten, no leak
  }
}

Records give you immutability, a canonical constructor, and equals/hashCode/toString for free — the ideal DTO. Request and response are separate types: they have different fields and different lifecycles.

5. Three ways to do the mapping

Static factory simplest

UserResponse.from(user)

A hand-written from(entity) on the DTO. Zero dependencies, fully explicit, trivial to read. Great default until the mappings get numerous.

MapStruct at scale

@Mapper(componentModel="spring")
interface UserMapper {
  UserResponse toDto(User u);
}

Generates the boilerplate at compile time (no reflection). Inject the mapper. Pays off when you have many DTOs; matches fields by name, configure the rest.

JPQL projection fastest

@Query("""
  select new com..UserResponse(
    u.id, u.username, u.email)
  from User u"")
List<UserResponse> findAllAsDto();

The DB returns the DTO directly — only the selected columns are read, no entity is ever materialized. Best for read-heavy list endpoints. (Spring Data interface projections do the same.)

Rule of thumb: start with a static from() factory. Reach for MapStruct when the number of mappings becomes tedious. Use a JPQL/interface projection when a read endpoint is hot and you want to avoid loading whole entities. All three keep the entity off the wire — that's the part that matters.

6. One DTO per use-case > one fat DTO

It's tempting to make a single UserDto and reuse it everywhere. Resist it — different endpoints need different shapes, and a shared DTO drifts toward exposing everything to everyone.

Use-caseDTOShape
Create userCreateUserRequestusername, email, password  in
Update profileUpdateProfileRequestemail only  in
User in a listUserSummaryid, username  out
User detail pageUserResponseid, username, email, memberSince, orderCount  out
Admin viewAdminUserView+ isAdmin, failedLoginCount  out, secured

Small, single-purpose DTOs are self-documenting and safe: each one's field list is the contract for that endpoint. Need to expose more to admins? That's a different DTO behind a different authorization rule — not a field you forgot to hide.

7. One-sentence recap

🧱 A DTO is the deliberate, client-facing shape of your data — keep it separate from the @Entity so you never leak sensitive fields, never serialize a lazy relation, and can evolve your schema and your API independently: use records for request & response DTOs, @Valid the requests, map with a static from() / MapStruct / JPQL projection, and prefer one DTO per use-case over one fat shared one.
