IDM Integration — OAuth2 / OIDC

When your Spring service talks to an Identity Manager (Entra ID, Ping, Okta, Keycloak, Auth0), you almost never write authentication code. The IDM issues a signed JWT; your job is to validate it and map its claims to authorities. This page traces exactly what Spring checks on every request, where 401 differs from 403, and which OAuth2 flow to pick.

What does Spring Security actually do when a JWT arrives — step by step?

When Angular sends Authorization: Bearer eyJhbGci... to your Spring endpoint, Spring Security performs these checks automatically: (1) Extract the JWT from the header. (2) Verify the signature using the JWKS fetched from the IDP's /.well-known/jwks.json endpoint — if the signature is invalid, reject immediately. (3) Check the exp claim — if the token is expired, reject. (4) Check the iss claim matches the configured issuer URI. (5) Check the aud claim if configured. (6) Map the claims to Spring Security GrantedAuthority objects (roles/scopes). (7) Put the JwtAuthenticationToken in the SecurityContext. Your controller never sees steps 1-7 — they happen in the filter chain before the request reaches your code. If any check fails: 401. If all pass but the user doesn't have the required role: 403.

Minimal Spring config

In application.yml: spring.security.oauth2.resourceserver.jwt.issuer-uri: https://login.contoso.com. That's it. Spring auto-fetches JWKS, validates every JWT, and puts the authentication in the security context. To require authentication for all endpoints: http.authorizeHttpRequests(auth -> auth.anyRequest().authenticated()). To require specific roles: auth.requestMatchers("/api/admin/**").hasRole("SYSTEM_ADMIN").

Claims → authorities mapping

By default, Spring maps the scope claim to SCOPE_read, SCOPE_write authorities. Ping/Entra put roles in different claims: Ping in groups, Entra in roles. Custom mapping: @Bean JwtAuthenticationConverter jwtConverter() { var c = new JwtGrantedAuthoritiesConverter(); c.setAuthoritiesClaimName("groups"); c.setAuthorityPrefix("ROLE_"); return c; }. Now @PreAuthorize("hasRole('CIAM_ADMIN')") checks the groups claim for "CIAM_ADMIN".

Which OAuth2 flow to pick

Authorization Code + PKCE: user-facing login (Angular SPA + Ping/Entra). Produces ID token + access token + refresh token. Client Credentials: machine-to-machine (Spring backend calling the IDM admin API or another microservice). No user involved. App authenticates with client ID + secret, gets an access token. Token Exchange: advanced — your service receives a user token and needs to call a downstream service on behalf of that user (OBO flow in Entra). Use the right flow; mixing them is a security mistake.

In CIAM: Issuer: https://federation.contoso.com (Ping Federate). JWT claims: sub (user ID), email, ciam_roles (custom claim: ["CIAM_ADMIN", "USER_MANAGER"]). Map: setAuthoritiesClaimName("ciam_roles"); setAuthorityPrefix("ROLE_"). Then: @PreAuthorize("hasRole('CIAM_ADMIN')") works. 401 vs 403: missing/invalid token → Spring returns 401 before reaching the controller. Valid token, wrong role → @PreAuthorize throws AccessDeniedException → Spring returns 403. Angular's interceptor catches 401 and triggers re-login; catches 403 and shows "Access Denied" toast.

1. The golden rule: the IDM mints tokens, you only validate them

You don't store passwords, you don't issue tokens, and you never hand-parse a JWT with string splitting. The IDM is the authority; your service is a resource server that trusts tokens it can cryptographically verify came from that IDM and haven't been tampered with or expired.

User / Service— authenticates → IDM (Entra/Ping/Okta)— signed JWT → Client— Bearer token → Your Spring API

The whole trust model rests on the IDM's signature and a small set of claim checks. Spring Security does all of it for you from one config line — but you should know each step it runs.

2. Resource-server config — the one line that turns it on

application.yml

spring:
  security:
    oauth2:
      resourceserver:
        jwt:
          # Spring auto-discovers JWKS + issuer from here
          issuer-uri: https://login.microsoftonline.com/<tenant>/v2.0
// build.gradle / pom.xml
spring-boot-starter-oauth2-resource-server

From issuer-uri, Spring fetches the OIDC discovery doc, finds the jwks_uri, caches the signing keys, and wires a JwtDecoder that validates signature + issuer + expiry on every request. That's the baseline.

SecurityFilterChain

@Bean
SecurityFilterChain api(HttpSecurity http) throws Exception {
  http
    .authorizeHttpRequests(a -> a
       .requestMatchers("/api/**").authenticated()
       .anyRequest().permitAll())
    .oauth2ResourceServer(o -> o
       .jwt(Customizer.withDefaults()));
  return http.build();
}

Now every /api/** call must carry Authorization: Bearer <jwt>. Add @PreAuthorize on methods for role/scope checks (section 5). Audience validation isn't on by default — add it (section 5).

4. 401 vs 403 — the distinction that trips everyone up

401 Unauthorized = "I don't know who you are"

The authentication failed: no token, malformed token, bad signature, wrong issuer, wrong audience, or expired. The identity itself isn't established.

  • Spring's BearerTokenAuthenticationFilter / JwtDecoder rejects it.
  • Response carries a WWW-Authenticate header.
  • Fix: get a valid, unexpired token for the right audience.

403 Forbidden = "I know you, but no"

The token is valid and authenticated — but the principal lacks the required scope/role/authority for this endpoint. Authorization failed, not authentication.

  • The AuthorizationFilter / @PreAuthorize denies it.
  • Refreshing the token won't help — you need the right claim.
  • Fix: grant the user the role/scope in the IDM.

One-line test: if a fresh, correct token would fix it → it was a 401. If even a brand-new token fails the same way → it's a 403 (the identity simply isn't allowed).

5. Claim mapping → authorities (and every IDM does it differently)

By default Spring maps the scope/scp claim to SCOPE_* authorities. To authorize on roles/groups, you tell a JwtAuthenticationConverter where your IDM puts them — because they all put them somewhere different.

@Bean
JwtAuthenticationConverter jwtAuthConverter() {
  JwtGrantedAuthoritiesConverter scopes = new JwtGrantedAuthoritiesConverter(); // SCOPE_*
  JwtAuthenticationConverter conv = new JwtAuthenticationConverter();
  conv.setJwtGrantedAuthoritiesConverter(jwt -> {
    var auths = new ArrayList<GrantedAuthority>(scopes.convert(jwt));
    List<String> roles = jwt.getClaimAsStringList("roles");   // Entra app roles
    if (roles != null) roles.forEach(r ->
        auths.add(new SimpleGrantedAuthority("ROLE_" + r)));
    return auths;
  });
  return conv;
}

// then on the endpoint:
@PreAuthorize("hasAuthority('ROLE_devhub.write')")
@PostMapping("/api/v1/articles") ...

Where each IDM hides roles/groups

Oktagroups (mapped)groupsscproles usually modeled as groups; configure the claim in the auth server
Keycloakrealm_access.rolesgroupsscopenested claim + resource_access.<client>.roles — needs a custom extractor
Pingconfigurablegrp/groupsscopeclaim names are policy-defined — confirm with the IDM team

This table is why "it worked against Keycloak but breaks on Entra" — the validation is identical, only the claim location changed. Adjust the converter, not the security model.

7. The client side — calling a protected API service-to-service

Register the client (M2M)

spring:
  security:
    oauth2:
      client:
        registration:
          idm:
            client-id: svc-devhub
            client-secret: ${IDM_SECRET}
            authorization-grant-type: client_credentials
            scope: api.read
        provider:
          idm:
            token-uri: https://.../oauth2/v2.0/token

Add spring-boot-starter-oauth2-client. No user, no browser — the service authenticates with its own client-id/secret.

Attach the token automatically

@Bean
RestClient idmClient(OAuth2AuthorizedClientManager mgr) {
  var interceptor = new OAuth2ClientHttpRequestInterceptor(mgr);
  interceptor.setClientRegistrationIdResolver(req -> "idm");
  return RestClient.builder()
      .requestInterceptor(interceptor)
      .build();                // every call now carries a fresh Bearer token
}

The OAuth2AuthorizedClientManager obtains, caches, and refreshes the access token for you. You just call the downstream API — the token is attached and renewed transparently.

8. One-sentence recap

🔑 Your Spring service is a resource server: from one issuer-uri it auto-validates each Bearer JWT's signature → issuer → audience → expiry (any failure = 401), maps the IDM's roles/groups/scope claim to authorities via a JwtAuthenticationConverter (missing authority = 403), and — for outbound calls — uses the oauth2-client starter with the right grant (Authorization Code for users, Client Credentials for M2M, Token Relay through a gateway); you never mint or hand-parse tokens.
