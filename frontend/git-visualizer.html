Git — Commits, Branches & Merges

Git is a graph of snapshots. Branches are sticky notes pointing at commits. HEAD is a sticky note pointing at a branch. That's the whole mental model.

The four areas a file can live in

Edit a file → it's in working dir. git add moves it to staging. git commit snapshots staging into repo. git push sends it to remote. git status shows you exactly where everything sits.

Merge vs Rebase — the religious war

🔀 git merge

Creates a merge commit with two parents. History shows exactly what happened — branch existed, then joined.

✅ Pros: non-destructive, preserves true history, safe on shared branches.

❌ Cons: history becomes a tangle of diamonds, can be hard to read on busy projects.

git checkout main
git merge feature   // merge commit if diverged

📏 git rebase

Replays your commits on top of another branch. Result: linear history that looks like you wrote your work after main's latest commit.

✅ Pros: clean linear history, easy to read & bisect, no merge-commit noise.

❌ Cons: rewrites history (new commit hashes) — NEVER rebase commits you've already pushed and others have pulled.

git checkout feature
git rebase main      // replay feature commits on top of main

⚖️ Common rule

Rebase locally, merge publicly. Use rebase to keep your private feature branch tidy before opening a PR. Use merge (or squash-merge) to land the PR into main.

If you're alone on a branch — rebase freely. If anyone else has pulled it — don't rewrite it without coordination.

🥇 Squash merge

The PR-button compromise. Takes your 12 messy "WIP" commits and squashes them into ONE clean commit on main. Best of both: messy private branch, tidy public history.

git merge --squash feature
git commit -m "feat: add login"

The everyday workflow (PR flow)

// 1. Get the latest main
git checkout main
git pull

// 2. Branch off for your work
git checkout -b feature/login    // shortcut for branch + checkout

// 3. Make changes, then stage & commit
git status                       // what changed?
git diff                         // what exactly changed?
git add src/Login.java           // stage specific files (avoid `git add .`)
git commit -m "feat: add login form validation"

// 4. Push your branch to remote
git push -u origin feature/login  // -u sets upstream so later `git push` works alone

// 5. Open a PR on GitHub. After review, click "Squash & merge".
// 6. Clean up locally
git checkout main
git pull
git branch -d feature/login      // delete merged branch

"Oh no" — the recovery cheatsheet

I did thisHow to undo itNotes
Edited a file, want to throw away the changes git restore file.txt Older Git: git checkout -- file.txt. Destructive — work is gone.
Staged a file by mistake git restore --staged file.txt Unstages but keeps your edits. Older Git: git reset HEAD file.txt.
Committed but forgot to add a file (and haven't pushed yet) git add forgot.txt && git commit --amend --no-edit Replaces the last commit. NEVER amend a pushed commit unless you're the only one on the branch.
Bad commit message on last commit git commit --amend -m "new message" Same warning — local only.
Want to undo the last commit but keep the changes git reset --soft HEAD~1 Commit goes away, changes return to staging. Safe — nothing is lost.
Want to undo last commit AND throw away changes git reset --hard HEAD~1 DESTRUCTIVE. Files are gone. Use --soft unless you're sure.
Need to undo a commit that's already pushed git revert <sha> Creates a NEW commit that inverts the old one. Safe for shared branches — no history rewrite.
Started work on wrong branch, haven't committed git stash && git checkout right-branch && git stash pop Stash = temporary shelf for uncommitted work.
I have no idea what I did, can I get my old commit back? git reflog LIFESAVER. Shows every place HEAD has been for ~90 days. Find the SHA, then git reset --hard <sha>.
Want to grab ONE commit from another branch git cherry-pick <sha> Copies that single commit onto your current branch.

Merge conflicts — what they actually are

A conflict happens when both branches changed the same lines of the same file. Git can't pick a winner, so it stops and asks you. The file is marked with conflict markers: 

// hello.js — after `git merge feature`
function greet(name) {
<<<<<<< HEAD                              // ← your version (main)
    return `Hello, ${name}!`;
=======                                    // ← divider
    return `Hi there, ${name}!`;
>>>>>>> feature                            // ← their version
}

To resolve: open the file, delete the markers, leave the code you want (often a blend of both), then git add hello.js and git commit (or git merge --continue). Use git status to see which files still have conflicts.

⚠️ If you DO commit a secret: changing the file isn't enough — the secret lives in git history forever. Rotate the secret immediately (assume it's compromised), then use git filter-repo or BFG Repo-Cleaner to scrub it from history, and force-push (after coordinating with the team).

Mental model — the only things you need to remember

1. Commits are snapshots

Not "diffs" — full snapshots of every tracked file at that moment, plus a pointer to the parent commit(s). Storage is deduplicated so it's actually efficient.

2. Branches are pointers

A branch is just a tiny file containing one commit SHA. main → abc123. Creating a branch is instant — Git just writes a new pointer.

3. HEAD points at your current branch

HEAD → main → abc123. git checkout feature just moves HEAD. git commit moves whatever branch HEAD points at.

4. Nothing is ever truly lost (for ~90 days)

Even git reset --hard leaves the orphaned commit in git reflog. As long as you committed at least once, it's recoverable. Don't panic — reflog first.
