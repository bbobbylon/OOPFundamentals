Tokens, Keys & Signing

The word "key" gets overloaded into mush — secret keys, signing keys, session keys, API keys, client secrets, TLS keys. This page untangles all of them, then shows the one that matters most for JWTs: how a token gets signed and verified, why a resource server can trust a token without ever calling the IDM, and how Ping (or Entra) rotates keys without breaking anyone.

What are signing keys, JWKS, and key rotation — and why can your Spring Boot API verify a JWT without calling Ping or Entra on every request?

The "key" problem: auth systems use at least 5 types of "keys" that are completely different things. (1) Client secret: a password-like shared secret used by a client application (Angular SPA or Spring Boot service) to authenticate itself to the identity provider. Used in Client Credentials flow (machine-to-machine). Never put in browser code — only on the server. (2) JWT signing key pair: the identity provider (Ping/Entra) signs each JWT with its RSA or EC private key. The corresponding public key is published at the JWKS endpoint. Anyone can verify a token's signature using the public key — without needing the private key or calling the IdP. (3) TLS certificate: used for HTTPS. The server's private key encrypts the TLS handshake; the browser verifies the certificate was signed by a trusted CA. Nothing to do with JWTs. (4) Session key: a symmetric key negotiated during TLS to encrypt the connection. Ephemeral — changes with every connection. (5) API key: a long random string used for simple API authentication (like a shared password). Not a cryptographic key per se — just a secret string in a header. No built-in expiry or signature. How JWT signing works (RS256): (1) IdP creates the JWT header+payload. (2) IdP computes SHA256(header + "." + payload) and RSA-encrypts it with its private key → this is the signature. (3) IdP sends header.payload.signature to the client. (4) Spring Boot receives the JWT and fetches the JWKS (public keys) from the IdP's JWKS URI once at startup, then caches them. (5) For each request, Spring Boot RSA-verifies the signature using the cached public key → fast, no network call. (6) If signature valid, check iss, aud, exp claims. Key rotation: the IdP periodically creates a new RSA key pair and publishes the new public key in the JWKS (keeping the old one for a grace period). Tokens signed with the old key still include the old kid (key ID) in the header — Spring Security fetches the JWKS again when it sees an unknown kid. This is why you should never hardcode kid values — always look up by kid from the JWKS.

JWT anatomy — the 3 parts

// A JWT = 3 base64url-encoded parts joined with "." // HEADER.PAYLOAD.SIGNATURE // HEADER (decoded): {"alg":"RS256","kid":"07kz","typ":"JWT"} // alg: signing algorithm (RS256 = RSA + SHA256) // kid: Key ID — which key from JWKS to use for verification // typ: token type // PAYLOAD (decoded): { "iss": "https://am.example.com/oauth2", // WHO issued this token "sub": "user-abc-123", // WHO is this token about "aud": "api://my-spring-boot-api", // WHO should accept this "exp": 1718000000, // WHEN does it expire (Unix ts) "iat": 1717996400, // WHEN was it issued "scp": "users.read users.write", // WHAT scopes were granted "roles": ["ADMIN"], // WHAT app roles "tid": "tenant-456" // WHICH tenant } // SIGNATURE: // base64url(RSA_sign(SHA256(header + "." + payload), privateKey)) // Verifiable by anyone with the public key from JWKS

Key type cheat sheet

// CLIENT SECRET // What: password for your client app to auth to IdP // Where: Azure App Registration → Certificates & secrets; Ping admin console // Use: Client Credentials flow (M2M); token endpoint ONLY // NEVER: put in Angular/browser code; commit to git // RSA SIGNING KEY PAIR (JWT) // Private key: IdP only — signs JWTs // Public key: in JWKS — anyone can fetch; used to verify // Rotation: every 24-90 days (IdP manages automatically in PingOne/Entra) // TLS CERTIFICATE // What: proves server identity + enables encrypted HTTPS // Issued by: CA (Let's Encrypt, DigiCert, etc.) // Expiry: typically 90 days (Let's Encrypt) to 1 year // WATCH OUT: expired TLS cert breaks ALL traffic (not just auth) // API KEY // What: long random string used as a simple credential // How: X-API-Key: sk-1234567890abcdef header // Cons: no built-in expiry, no scope, no user context // Use: external service integrations, webhook validation // NEVER: as primary auth for user-facing APIs

In CIAM / Your Job: You will rotate signing keys in production. The procedure: (1) generate new key pair in Ping AM or Entra (both have admin UI for this); (2) publish new public key to JWKS — the old key stays published during the grace period; (3) new tokens will use the new private key (new kid); (4) existing tokens signed with the old key still validate until they expire; (5) after all old tokens expire (typically 1-2 hours), remove the old public key from JWKS. Spring Boot handles this automatically via the kid lookup mechanism. What breaks: if your jwk-set-uri cache TTL is too long, Spring Boot won't pick up the new key fast enough. The fix: configure spring.security.oauth2.resourceserver.jwt.jwk-set-cache-timeout=5m.

1. "Key" disambiguated — the whole nine yards

Every one of these is called a "key" or "secret" by someone. Here's what each actually is, and which layer it lives in.

The one that confuses everyone. A signed JWT (JWS) is not encrypted — it's Base64, fully readable by anyone (try it in the playground). The signature proves integrity (nobody changed it) and authenticity (the IDM issued it), not secrecy. So never put anything sensitive in a JWT payload. If you truly need a secret in a token, that's JWE (encrypted), which is rare for access tokens.

2. Symmetric vs asymmetric — who can forge?

HS256 — one shared secret

# sign AND verify use the SAME secret
sig = HMAC_SHA256(secret, header.payload)

# ✅ fine: one app signs & verifies its own tokens
# ❌ bad at scale: every verifier needs the secret,
#    and the secret can also FORGE tokens

RS256 — a key pair

# IDM signs with its PRIVATE key (kept secret)
sig = RSA_sign(privateKey, header.payload)

# APIs verify with the PUBLIC key (published)
ok  = RSA_verify(publicKey, header.payload, sig)
# public key can verify but CANNOT forge ✅

This is why real IDMs (PingFederate, PingOne, Entra) use asymmetric RS256/ES256: they hand out the public key freely so any number of resource servers can verify tokens, while only the IDM can mint them. With HS256 you'd have to share the forging secret with every API — a non-starter.

3. How your API trusts a token without calling the IDM

A Spring resource server validates the signature locally using the IDM's public keys — fetched once from the JWKS endpoint and cached.

# application.yml — point Spring at the issuer; it discovers the JWKS
spring:
  security:
    oauth2:
      resourceserver:
        jwt:
          issuer-uri: https://auth.pingone.com/{envId}/as
          # Spring auto-fetches /as/jwks from the issuer's metadata,
          # caches the public keys, and verifies every token locally.
GET /as/jwks → { "keys": [{ "kty": "RSA", "use": "sig", "kid": "07kz", "n": "0vx7ag…(public modulus)…", "e": "AQAB", "alg": "RS256" }] }

The token's header kid: "07kz" selects the matching JWKS key. No network call to the IDM per request — validation is a local signature check (issuer, audience, expiry, and signature). That's what makes JWT-based auth scale.

🧑‍💻
Browser / SPA
Holds the access token (memory) + maybe a session cookie. With a BFF, holds only an httpOnly cookie.

Gateway / BFF
Terminates TLS (TLS session keys). May swap a cookie ↔ bearer token (token relay).
TLS keys · relay
🍃
Spring resource server
Verifies the JWT signature with the IDM's public key (JWKS, cached). Maps claims → authorities → @PreAuthorize.
public key · claims
🔐
IDM (PingFederate / PingOne / Entra)
Holds the private signing key, issues & signs tokens, publishes the public key, rotates keys.
private signing key
🗄️
Downstream service
Receives a relayed token (on-behalf-of) or the app acts as itself with a client secret.
relayed token · client secret
Key rotation (scenario ③): IDMs rotate signing keys on a schedule. They publish the new public key in the JWKS before switching, so verifiers that re-fetch on an unknown kid pick it up seamlessly. This is why you should never hard-code a public key — always resolve it by kid from the live JWKS. A token signed with a retired key fails once the key drops out of the JWKS.
