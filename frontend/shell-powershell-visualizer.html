PowerShell

PowerShell looks like Bash but works on a completely different principle: it pipes objects, not text. When you write Get-Process | Where-Object CPU -gt 100, real .NET objects with typed properties flow through the pipe — no parsing, no fragile awk/cut on columns. That one idea reshapes everything. (PowerShell is cross-platform — Windows, Linux, macOS.)

⌨️ What is PowerShell — and why does "objects through the pipe instead of text" completely change how you write automation scripts on Windows?

PowerShell is a task automation shell and scripting language built on .NET. It runs on Windows (built-in since Win7), Linux, and macOS (PowerShell 7+). The key insight that makes PowerShell different from every other shell: the pipeline carries .NET objects, not text strings. In Bash, when you pipe output through commands, you're passing text — and parsing text is fragile (spaces in values, column alignment varies, locale-dependent formatting). In PowerShell, Get-Process returns a collection of System.Diagnostics.Process objects with real typed properties (CPU, Memory, Name, Id) — and you interact with those properties directly. Verb-Noun cmdlets: all PowerShell commands (cmdlets) follow a strict Verb-Noun naming convention. This makes them discoverable — once you know the verb (Get, Set, New, Remove, Start, Stop, Invoke, Test, Write) you can guess the cmdlet. Get-ChildItem, New-Item, Remove-Item, Set-Content, Invoke-WebRequest. Aliases exist for familiarity (ls, cd, cat, dir) but the full names are canonical. Key differences from Bash: (1) Comparison operators are -eq, -ne, -lt, -gt, -le, -ge (not ==, !=, <, >, etc.) — using == and < in PowerShell does something different! (2) Variables start with $ (like $name, $env:PATH). (3) Strings use double-quote for interpolation ("Hello $name") and single-quote for literals ('literal $name'). (4) Pipeline operators && and || are only in PS7+ (use ; or if($LASTEXITCODE -ne 0)) in PS5. (5) -ErrorAction SilentlyContinue suppresses errors but doesn't guarantee $? is true. PowerShell for Windows CIAM automation: PowerShell excels at: calling Azure REST APIs (AzureAD/Graph modules), configuring IIS, managing Windows Server services, scripting Active Directory operations (Get-ADUser, New-ADUser), interacting with the Windows event log, and running ADO pipeline steps on Windows agents.

Object pipeline in action

# OBJECTS through the pipe (not text): Get-Process # Returns: System.Diagnostics.Process[] objects # With properties: Id, Name, CPU, WorkingSet, etc. Get-Process | Where-Object {$_.CPU -gt 100} # filter by property Get-Process | Sort-Object CPU -Descending # sort by property Get-Process | Select-Object Name,CPU,Id # pick which properties Get-Process | Select-Object -First 5 # take top 5 # Compared to Bash (parsing text): # ps aux | awk '$3 > 100 {print $11}' ← fragile, column-dependent # Filter with Where-Object (alias: ?): Get-ChildItem *.log | Where-Object Length -gt 1MB # files over 1MB # Select and export: Get-Process | Select-Object Name,CPU | Export-Csv "procs.csv" Get-Process | ConvertTo-Json | Set-Content "procs.json" # Measure (like wc): Get-ChildItem . -Recurse | Measure-Object Length -Sum # Sum, Average, Count, Min, Max all available

Variables + control flow

# Variables: $name = "Alice" # string $count = 42 # int $list = @("a", "b", "c") # array $map = @{name="Alice"; age=30} # hashtable # String interpolation: "Hello $name, you are $($map.age)" # double-quote: expands vars 'Hello $name' # single-quote: literal (no expansion) # Conditions (use -eq not ==): if ($count -gt 10) { Write-Host "Large count" } elseif ($count -eq 0) { Write-Host "Zero" } else { Write-Host "Small" } # Loops: foreach ($item in $list) { Write-Host $item } 1..10 | ForEach-Object { Write-Host "Item $_" } # Error handling: try { Invoke-RestMethod "https://api.example.com/token" } catch { Write-Error "Request failed: $($_.Exception.Message)" exit 1 }

or, the two truth-tellers that don't actually agree with each other

The problem

You wrote if ($?) { Write-Host "Deploy succeeded" } right after a command that genuinely worked — and it printed the failure branch instead.

The push that "failed" by succeeding loudly

A deploy step runs git push origin main, then checks if ($?) { Write-Host "Pushed" } else { Write-Error "Push failed" }. The branch really does land on the remote. The exit code really is 0. The script prints "Push failed" anyway.

Git writes its progress output — "Enumerating objects…", "To github.com:…" — to stderr, not stdout. That's just how git talks; it always has. For a native executable, Windows PowerShell doesn't build $? from the numeric exit code — it sets $? to $false the moment the process writes anything at all to stderr. Git's routine chatter gets read as an error.

git push actually succeeded ✓ the exit code really was 0 ✓ $? still says False ⚠

You'll swear the deploy failed while staring at the commit you just pushed, sitting right there on GitHub.

Fix: check $LASTEXITCODE for native commands, not $?
After any native .exe — not a cmdlet — read $LASTEXITCODE instead of $? ↓ $LASTEXITCODE is the actual numeric exit code the process returned; 0 really does mean success Reserve $? for cmdlets and PowerShell functions, where it tracks real terminating errors ↓ cmdlets set $? from their own success state, not from stray text on a stream And if a script mixes both worlds, write if ($LASTEXITCODE -ne 0) { … } right after every native call, not a bare if ($?)
The one-sentence rule. $? and $LASTEXITCODE answer two different questions. For a cmdlet, $? reliably means "did this terminate without error." For a native executable in Windows PowerShell, $? means "did anything show up on stderr" — a completely different, noisier question — while $LASTEXITCODE is the one plain number the process actually returned. Treating them as interchangeable is how a clean deploy gets logged as a failure.
$? is the office rumor mill — if a native program so much as mentions something on the stderr grapevine, $? repeats it as bad news. $LASTEXITCODE is the paycheck: one plain number, and it's the only one of the two that the program itself actually controls.

The mechanism

Here's the order of events, every time a native .exe runs inside a PowerShell script.

  1. git.exe runs and writes its progress text to stderr — normal git behavior, success or failurestderr write
  2. git.exe finishes and hands the OS a real exit code — 0, because the push workedthe real result
  3. PowerShell stores that 0 in $LASTEXITCODE$LASTEXITCODE set
  4. Separately, PowerShell asks: did anything get written to the error stream during this command?a different question
  5. Yes — git's routine progress text counted, even though none of it was an errorfalse positive
  6. $? is set to False based on that stderr write, completely independent of the 0 already sitting in $LASTEXITCODEdisagreement

Steps 3 and 6 run off the exact same command and land on opposite verdicts. That's not a bug you introduced — it's how Windows PowerShell has always evaluated a native command's success, and it's exactly why $LASTEXITCODE exists as a second, more literal answer.

what reacts to that stderr write ↓
$LASTEXITCODE — stays 0, unaffected $? — flips to False the branch on the remote — unaffected, it's really there

Only one of these three things is even watching stderr. The exit code and the real state of the remote branch don't care that git printed anything there — $? is the one signal in the whole script that gets rattled by it.

A PowerShell CI step runs git push origin main, then if ($?) { Write-Host "OK" } else { throw "push failed" }. The branch really is updated on the remote, but the script throws "push failed" anyway. What's the real cause?

Git's exit code genuinely is 0 here — there's no bug in git. The "failure" people blame on git is really about how Windows PowerShell reads native-command success, not what git returned.

Where you have seen this before

Two signals from the same event, and only one of them is telling you what you actually want to know.

A token endpoint that returns HTTP 200 with an error body

Some identity providers respond to a failed grant with a plain 200 OK and {"error":"invalid_grant"} in the body, instead of a 4xx status. Code that only checks response.StatusCode == 200 reports success on a request that actually failed — the transport-layer signal and the application-layer signal disagree, exactly like $? and $LASTEXITCODE.

the wrong layer answered the question

AWS async APIs returning 0 the instant the request is accepted

aws ecs update-service exits 0 as soon as AWS accepts the request to start a new deployment — not once that deployment actually finishes and stabilizes. A script that checks the exit code and moves on can report a clean deploy minutes before the real rollout even starts failing.

"accepted" and "succeeded" are not the same claim

A test suite that passes because it never ran

A typo in a test-file glob means Maven Surefire or Jest discovers zero test files. Zero tests ran, zero tests failed, so the runner exits 0 — a fully green build with no actual test coverage that day. The exit code was honest about "no failures"; it was never asked "did anything real happen."

green isn't the same claim as tested

1. Cmdlets are Verb-Noun — and that's a feature

Get-ChildItem      # list (alias: ls, dir, gci)
Get-Content log.txt
Set-Location C:\proj  # cd
Stop-Process -Name node
New-Item -ItemType Directory build
Why Verb-Noun helps. The verbs are a fixed, approved set (Get, Set, New, Remove, Start, Stop…). So once you know a noun exists, you can guess the cmdlet — and Get-Command -Verb Get lists everything you can read. Discoverability is built into the naming. The short aliases (ls, cat, cd) exist for interactive comfort, but scripts should use the full names for clarity.

2. The big idea: objects vs text

Bash — everything is text

# to get process names using >100% CPU,
# you parse columns by position:
ps aux | awk '$3 > 100 { print $11 }'
# fragile: depends on column order,
# spacing, locale, header rows…

PowerShell — real objects

# ask for the property by NAME:
Get-Process |
  Where-Object CPU -gt 100 |
  Select-Object Name, CPU
# no parsing — CPU is a typed number

In Bash, every command's output is a blob of text that the next command must re-parse. In PowerShell, Get-Process emits Process objects; Where-Object reads the real CPU property (a number you can compare with -gt); Select-Object picks fields. Nothing is ever parsed from columns.

3. Reference: operators & common cmdlets

Comparisons are words, not symbols

-eq  -ne        # equal / not equal
-gt  -ge -lt -le # greater / less
-like  -match    # wildcard / regex
-contains -in    # membership
# (because > and < mean redirection!)

The pipeline workhorses

Where-Object   # filter (alias: ?)
Select-Object  # pick/compute properties
ForEach-Object # act on each (alias: %)
Sort-Object    # sort by property
Measure-Object # count/sum/avg
Variables & environment (scenario ④): a variable is $name = "Ada"; environment variables live in the $env: drive — $env:PATH, $env:USERPROFILE. Error handling is try { } catch { } like a real language, and $? / $LASTEXITCODE report success. Because PowerShell objects have methods, you can do (Get-Date).AddDays(7) right in the pipeline.
