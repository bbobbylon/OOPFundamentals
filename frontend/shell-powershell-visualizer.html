PowerShell

PowerShell looks like Bash but works on a completely different principle: it pipes objects, not text. When you write Get-Process | Where-Object CPU -gt 100, real .NET objects with typed properties flow through the pipe — no parsing, no fragile awk/cut on columns. That one idea reshapes everything. (PowerShell is cross-platform — Windows, Linux, macOS.)

What is PowerShell — and why does "objects through the pipe instead of text" completely change how you write automation scripts on Windows?

PowerShell is a task automation shell and scripting language built on .NET. It runs on Windows (built-in since Win7), Linux, and macOS (PowerShell 7+). The key insight that makes PowerShell different from every other shell: the pipeline carries .NET objects, not text strings. In Bash, when you pipe output through commands, you're passing text — and parsing text is fragile (spaces in values, column alignment varies, locale-dependent formatting). In PowerShell, Get-Process returns a collection of System.Diagnostics.Process objects with real typed properties (CPU, Memory, Name, Id) — and you interact with those properties directly. Verb-Noun cmdlets: all PowerShell commands (cmdlets) follow a strict Verb-Noun naming convention. This makes them discoverable — once you know the verb (Get, Set, New, Remove, Start, Stop, Invoke, Test, Write) you can guess the cmdlet. Get-ChildItem, New-Item, Remove-Item, Set-Content, Invoke-WebRequest. Aliases exist for familiarity (ls, cd, cat, dir) but the full names are canonical. Key differences from Bash: (1) Comparison operators are -eq, -ne, -lt, -gt, -le, -ge (not ==, !=, <, >, etc.) — using == and < in PowerShell does something different! (2) Variables start with $ (like $name, $env:PATH). (3) Strings use double-quote for interpolation ("Hello $name") and single-quote for literals ('literal $name'). (4) Pipeline operators && and || are only in PS7+ (use ; or if($LASTEXITCODE -ne 0)) in PS5. (5) -ErrorAction SilentlyContinue suppresses errors but doesn't guarantee $? is true. PowerShell for Windows CIAM automation: PowerShell excels at: calling Azure REST APIs (AzureAD/Graph modules), configuring IIS, managing Windows Server services, scripting Active Directory operations (Get-ADUser, New-ADUser), interacting with the Windows event log, and running ADO pipeline steps on Windows agents.

Object pipeline in action

# OBJECTS through the pipe (not text): Get-Process # Returns: System.Diagnostics.Process[] objects # With properties: Id, Name, CPU, WorkingSet, etc. Get-Process | Where-Object {$_.CPU -gt 100} # filter by property Get-Process | Sort-Object CPU -Descending # sort by property Get-Process | Select-Object Name,CPU,Id # pick which properties Get-Process | Select-Object -First 5 # take top 5 # Compared to Bash (parsing text): # ps aux | awk '$3 > 100 {print $11}' ← fragile, column-dependent # Filter with Where-Object (alias: ?): Get-ChildItem *.log | Where-Object Length -gt 1MB # files over 1MB # Select and export: Get-Process | Select-Object Name,CPU | Export-Csv "procs.csv" Get-Process | ConvertTo-Json | Set-Content "procs.json" # Measure (like wc): Get-ChildItem . -Recurse | Measure-Object Length -Sum # Sum, Average, Count, Min, Max all available

Variables + control flow

# Variables: $name = "Alice" # string $count = 42 # int $list = @("a", "b", "c") # array $map = @{name="Alice"; age=30} # hashtable # String interpolation: "Hello $name, you are $($map.age)" # double-quote: expands vars 'Hello $name' # single-quote: literal (no expansion) # Conditions (use -eq not ==): if ($count -gt 10) { Write-Host "Large count" } elseif ($count -eq 0) { Write-Host "Zero" } else { Write-Host "Small" } # Loops: foreach ($item in $list) { Write-Host $item } 1..10 | ForEach-Object { Write-Host "Item $_" } # Error handling: try { Invoke-RestMethod "https://api.example.com/token" } catch { Write-Error "Request failed: $($_.Exception.Message)" exit 1 }

Invoke-RestMethod for APIs

# Call REST APIs and work with JSON results natively: # Get OAuth2 token via Client Credentials: $body = @{ grant_type = "client_credentials" client_id = $env:CLIENT_ID client_secret = $env:CLIENT_SECRET scope = "api://my-api/.default" } $response = Invoke-RestMethod ` -Uri "https://login.microsoftonline.com/$env:TENANT_ID/oauth2/v2.0/token" ` -Method POST ` -Body $body $token = $response.access_token # $response is a PSCustomObject — access properties directly: Write-Host "Expires in: $($response.expires_in) seconds" # Use token to call your API: $users = Invoke-RestMethod ` -Uri "https://api.example.com/api/users" ` -Headers @{Authorization = "Bearer $token"} # $users is now a PowerShell array of user objects # Filter immediately: $admins = $users | Where-Object {$_.roles -contains "ADMIN"}

In CIAM / Your Job: PowerShell is essential for Windows-based CIAM automation. You use it in ADO pipelines that run on Windows agents; to call the Microsoft Graph API and Entra ID REST APIs for user management automation; to script Active Directory operations for hybrid identity scenarios; and to manage Azure resources (App Registrations, Key Vaults, App Service). The Invoke-RestMethod cmdlet is particularly useful — it calls REST APIs and auto-parses JSON responses into PowerShell objects, so you can immediately filter and manipulate the results. Common CIAM PowerShell task: bulk update users in Entra via the Microsoft Graph API — Get-MgUser (from the Microsoft.Graph module), filter, update, Update-MgUser.

1. Cmdlets are Verb-Noun — and that's a feature

Get-ChildItem      # list (alias: ls, dir, gci)
Get-Content log.txt
Set-Location C:\proj  # cd
Stop-Process -Name node
New-Item -ItemType Directory build
Why Verb-Noun helps. The verbs are a fixed, approved set (Get, Set, New, Remove, Start, Stop…). So once you know a noun exists, you can guess the cmdlet — and Get-Command -Verb Get lists everything you can read. Discoverability is built into the naming. The short aliases (ls, cat, cd) exist for interactive comfort, but scripts should use the full names for clarity.

2. The big idea: objects vs text

Bash — everything is text

# to get process names using >100% CPU,
# you parse columns by position:
ps aux | awk '$3 > 100 { print $11 }'
# fragile: depends on column order,
# spacing, locale, header rows…

PowerShell — real objects

# ask for the property by NAME:
Get-Process |
  Where-Object CPU -gt 100 |
  Select-Object Name, CPU
# no parsing — CPU is a typed number

In Bash, every command's output is a blob of text that the next command must re-parse. In PowerShell, Get-Process emits Process objects; Where-Object reads the real CPU property (a number you can compare with -gt); Select-Object picks fields. Nothing is ever parsed from columns.

3. Reference: operators & common cmdlets

Comparisons are words, not symbols

-eq  -ne        # equal / not equal
-gt  -ge -lt -le # greater / less
-like  -match    # wildcard / regex
-contains -in    # membership
# (because > and < mean redirection!)

The pipeline workhorses

Where-Object   # filter (alias: ?)
Select-Object  # pick/compute properties
ForEach-Object # act on each (alias: %)
Sort-Object    # sort by property
Measure-Object # count/sum/avg
Variables & environment (scenario ④): a variable is $name = "Ada"; environment variables live in the $env: drive — $env:PATH, $env:USERPROFILE. Error handling is try { } catch { } like a real language, and $? / $LASTEXITCODE report success. Because PowerShell objects have methods, you can do (Get-Date).AddDays(7) right in the pipeline.
