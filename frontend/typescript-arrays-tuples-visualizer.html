Arrays, Tuples & Readonly

JS has one collection type — arrays. TS has many flavors: arrays, fixed tuples, variadic tuples, labeled tuples, readonly arrays, frozen literals via as const. Pick the right one and the compiler does the rest.

1. Two ways to write an array type

const a: number[] = [1, 2, 3];
const b: Array<number> = [1, 2, 3];
// Identical types. Use whichever reads better.

// The bracket form gets clunky once you have unions:
const c: (string | number)[] = ['a', 1];
const d: Array<string | number> = ['a', 1]; // often clearer

An array's element type says "every value at every index is T". Empty arrays without an annotation start as any[] (or never[] under strict mode), so it's worth declaring the type up front.

2. Reading vs writing elements

By default, TS does not consider out-of-bounds access an error. arr[999] is typed as T, even if the array is empty. Turn on noUncheckedIndexedAccess in tsconfig.json and indexing returns T | undefined — much safer.

const xs: number[] = [];

// Without noUncheckedIndexedAccess:
xs[0].toFixed(2);  // ✅ compiles, 💥 throws at runtime

// With noUncheckedIndexedAccess: true
xs[0].toFixed(2);  // ❌ Object is possibly 'undefined'
xs[0]?.toFixed(2); // ✅
Strongly recommended: enable noUncheckedIndexedAccess. It catches a huge class of "undefined is not a function" bugs that the basic strict flags miss. It does require sprinkling ?. or guards, but that's the point.

3. Tuples — fixed length, mixed types

A tuple is an array with a known length and a known type at each position. Square-bracket syntax with the position types inside:

type Pair = [string, number];

const p: Pair = ['age', 30];
p[0];           // string
p[1];           // number
p[2];           // ❌ length is 2 — index out of range
p.length;       // 2 (literal type)
"age"[0] string
30[1] number

Tuples are great for "always-paired" data — coordinates, key/value, result+error.

type Point  = [x: number, y: number];
type Entry  = [key: string, value: unknown];
type Result<T> = [data: T, error: null] | [data: null, error: Error];

4. Labeled tuples

Add names in front of each type. Pure documentation at runtime — but TS shows the labels in tooltips and signature hints, making call sites much clearer.

function rangeUnlabeled(start: number, end: number): [number, number] {
  return [start, end];
}
// Hover the return → just [number, number]. Which is start? which is end?

function rangeLabeled(start: number, end: number): [start: number, end: number] {
  return [start, end];
}
// Hover the return → [start: number, end: number]. Self-documenting.
Labels are all-or-nothing. [start: number, number] is a syntax error — either every position has a label, or none does.

5. Optional tuple elements

Trailing positions can be optional with ?. Their type becomes T | undefined.

type Range = [start: number, end: number, step?: number];

const r1: Range = [0, 10];           // ✅
const r2: Range = [0, 10, 2];        // ✅
const r3: Range = [0];               // ❌ end is required

r1.length; // 2 | 3 — TS tracks the possibilities
startnumber
endnumber
step?number?

6. Rest in tuples (variadic)

A spread inside a tuple type lets one position hold "any number of values of this type". Combined with concrete positions, you get variadic tuple types — the basis of most modern TS magic in functions.

// "first is a string, then any number of numbers"
type StringThenNums = [string, ...number[]];

const a: StringThenNums = ['sum', 1, 2, 3];
const b: StringThenNums = ['sum'];

// Rest can be anywhere — beginning, middle, or end
type SurroundedByNums = [number, ...string[], number];
const c: SurroundedByNums = [0, 'a', 'b', 'c', 100];

The killer app: forwarding arguments

// Generic rest tuple captures the entire signature
function defer<A extends unknown[], R>(
  ms: number,
  fn: (...args: A) => R,
  ...args: A
): void {
  setTimeout(() => fn(...args), ms);
}

defer(100, (name: string, n: number) => console.log(name, n), 'Bob', 42);
// ✅ TS validates 'Bob' and 42 match the function's signature

defer(100, (name: string, n: number) => {}, 'Bob');
// ❌ Expected 2 args for fn, got 1 trailing arg to defer

7. readonly arrays

Add readonly in front of an array or tuple type. The compiler then refuses any mutating method — push, pop, splice, index assignment.

const nums: readonly number[] = [1, 2, 3];
nums.push(4);       // ❌ Property 'push' does not exist on 'readonly number[]'
nums[0] = 99;       // ❌ Index signature is read-only

// Equivalent ReadonlyArray form:
const nums2: ReadonlyArray<number> = [1, 2, 3];

// And for tuples:
type RPair = readonly [string, number];
const p: RPair = ['a', 1];
p[0] = 'b';          // ❌
Compile-time only. readonly erases at runtime — the array is still a mutable JS array, and JS code with no types can change it. For runtime immutability, use Object.freeze (shallow) or a library like Immer.

readonly is one-way assignable

const mut: number[]           = [1, 2, 3];
const ro:  readonly number[]  = mut;  // ✅ "I promise not to mutate"

const ro2: readonly number[]  = [1];
const mut2: number[]          = ro2; // ❌ Would let caller mutate a readonly

Why APIs should accept readonly T[]

// 🥺 Stricter than needed — only mutable arrays can be passed
function sum(nums: number[]): number {
  return nums.reduce((a, b) => a + b, 0);
}

// 😎 Accepts both readonly & mutable, signals intent
function sumRO(nums: readonly number[]): number {
  return nums.reduce((a, b) => a + b, 0);
}

8. as const

The "freeze this literal" operator. Applied to an expression, it does three things:

  • Strings/numbers/booleans become their literal type instead of widening
  • Arrays become readonly tuples (not T[])
  • Objects become readonly with literal property types
const a = [1, 2, 3];
// a: number[]

const b = [1, 2, 3] as const;
// b: readonly [1, 2, 3]   ← literal AND readonly AND tuple

const c = { theme: 'dark', fontSize: 14 };
// c: { theme: string; fontSize: number }

const d = { theme: 'dark', fontSize: 14 } as const;
// d: { readonly theme: 'dark'; readonly fontSize: 14 }

Why this matters: deriving a string-union type

const SIZES = ['small', 'medium', 'large'] as const;
// SIZES: readonly ['small', 'medium', 'large']

type Size = typeof SIZES[number];
// 'small' | 'medium' | 'large'

function setSize(s: Size) { /* ... */ }

setSize('medium'); // ✅
setSize('huge');   // ❌

One source of truth. Add 'xlarge' to the array and the type updates automatically — no separate union to maintain.

10. Array methods & type changes

Most array methods preserve the element type. A few change it — note the return types.

MethodReturns
map((x: T) => U)U[] (potentially new type)
filterT[] by default — narrowed only with a type predicate
filter((x): x is U => ...)U[]
findT | undefined
findIndexnumber (returns -1 if not found — TS can't express that)
reduce((acc, x) => ..., initial)Type of the initial value (usually annotate to help inference)
flatMapU[]
concat(arr)(T | U)[] when given a different-element array

The filter trap

const mixed: (string | null)[] = ['a', null, 'b'];

// ❌ Result is still (string | null)[] — TS doesn't know x => x !== null narrows
const strs1 = mixed.filter(x => x !== null);

// ✅ Predicate makes the narrowing explicit
const strs2 = mixed.filter((x): x is string => x !== null);
// strs2: string[]

The reduce initial-value trap

// Without initial value — return type matches array
[1, 2, 3].reduce((acc, n) => acc + n); // number

// With a different-type initial — annotate, or TS narrows to the initial's type
[1, 2, 3].reduce((acc, n) => ({ ...acc, [n]: true }), {} as Record<number, boolean>);

11. Element-type unions vs tuples

These look similar but mean different things:

TypeMeaningExample value
(string | number)[]Array of any length, each item is either string OR number['a', 1, 'b', 2]
[string, number]Tuple — exactly 2 elements, first is string, second is number['a', 1]
[string | number, string | number]2 elements, each independently either['a', 'b'] or [1, 2]
readonly [string, number]Same as tuple, but immutable['a', 1] as const
