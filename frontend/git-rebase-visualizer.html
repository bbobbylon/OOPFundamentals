Rebase & Advanced Git

Rebase vs merge, interactive rebase, the golden rule, and force-with-lease. The tools senior developers use daily.

🔀 What is git rebase — and when should you use it instead of merge?

Rebase and merge both integrate changes from one branch to another — but they rewrite history differently. Merge: creates a new "merge commit" that has two parents — it records the fact that two branches came together. The history is non-linear but honest — you can see exactly when and where branches diverged and merged. Rebase: moves (replays) your commits onto a new base. git rebase main on your feature branch: takes all your commits, temporarily removes them, advances your branch pointer to match main, then re-applies your commits one by one on top. Result: a linear history — it looks like you branched from the CURRENT tip of main, not the old tip. Your commit SHAs CHANGE (new commits are created). The Golden Rule of Rebase: NEVER rebase commits that have been pushed to a shared remote branch (that others have pulled). Rebase rewrites history — if someone else has based work on your old commits and you rebase, their history and your history diverge catastrophically. Safe to rebase: commits only on YOUR local feature branch. Interactive rebase: git rebase -i HEAD~5 — rewrite the last 5 commits interactively. Options per commit: pick (keep), squash/fixup (combine with previous commit — great for "fix typo" commits), reword (change message), edit (stop to amend), drop (delete commit). Use before opening a PR to clean up your commit history: squash 12 "wip" commits into 1 meaningful commit. force-with-lease: git push --force-with-lease — safer than --force. Force push is needed after rebase (history changed). --force blindly overwrites remote. --force-with-lease checks that the remote branch hasn't been updated by someone else since you last fetched — refuses to push if it has. Always use --force-with-lease, never bare --force.

CIAM Git rebase practices: ADO squash-merge on PR completion: all feature branch commits squash into one clean commit on main. This means every commit on main = one PR = one feature/fix — extremely clean history for blame and bisect. Before squash-merge, use git rebase -i to clean up WIP commits and write a good commit message (it becomes the squash commit message). ADO "rebase and fast-forward": alternative to squash — replays commits from feature branch linearly onto main without a merge commit. Good for features with carefully crafted individual commits (like the walkthrough pages where each page is its own commit). --force-with-lease hook: set up a git hook that prevents bare --force: git config --global alias.force-push "push --force-with-lease". Interactive rebase of last 3 commits to fix up a pending PR: add a missed test, update the PR — git commit --fixup=HEAD~1 then git rebase -i --autosquash HEAD~3.

The problem

You tidied four commits. Your colleague's next git pull conflicted in 555 files.

"Moved" is the wrong verb, and it costs somebody an afternoon

Rebase does not pick your commits up and set them down elsewhere. It replays them — building a brand new commit for each one, with a new hash, a new parent, and a new timestamp. The originals still exist, orphaned. So after a force-push, anyone who already fetched the old ones has history that no longer exists upstream, and git tries to reconcile two versions of the same work.

4 commits "moved" ✓ 4 brand new hashes ⚠ their branch still has the old 4 ⚠ every file conflicts ⚠

Nobody's work was lost and nothing is corrupt. Git is faithfully merging two histories that contain the same changes twice.

Rebase what nobody has; merge what everybody has
Your own unpushed work → rebase freely, it is yours alone ↓ nobody can be holding the commits you are about to replace A branch someone else has pulled → merge, or ask first ↓ a merge commit adds history instead of replacing it, so their clone stays valid And when you must force, use --force-with-lease
A rebase is a copy, not a move. Every rebased commit is a different commit — new hash, same changes. Once you have that, the golden rule stops being a rule to memorise and becomes the obvious consequence: never replace commits other people are standing on.
You

I only reordered my own commits. I did not change anyone else's work.

Git

You did not change their work — you replaced the commits it was built on. Their branch points at a1b2c3; upstream now has f9e8d7 with identical content and a different identity. To me those are two unrelated commits that happen to touch the same lines.

The reflog

And nothing is gone. I still have every hash you had checked out for the last 90 days, including the one you think you destroyed. git reflog, find it, branch from it.

The mechanism

Watch one commit get replayed and re-identified.

  1. Git finds the commits on your branch that are not on the new basethe ones to replay
  2. It checks out the new base and applies the first commit's changes — not the commit itselfa diff, re-applied
  3. It writes a NEW commit. Different parent → different hash, always: the hash is computed from the content and the parentthis is why the id changes
  4. Repeat down the list. The original commits stay on disk, unreferenced, reachable only through the reflogorphaned, not deleted
  5. Your branch now points at the new chain — which is why the push is rejected, and why forcing it replaces history for everyonethe rejection is a warning, not a bug

Step 3 is the entire lesson. A commit's hash covers its parent, so changing a commit's parent necessarily changes its identity — there is no way to replay a commit and keep its id, and no flag that would give you one. Which also means the push rejection at step 5 is git telling you the truth: you are not adding to the remote branch, you are proposing to replace it.

So when you genuinely must force, force with a seatbelt. Plain --force says "make the remote match me, whatever is there." --force-with-lease says "make the remote match me only if it is still where I last saw it" — so if a colleague pushed while you were rebasing, the push is rejected instead of silently deleting their commit. It costs nothing and it is strictly better; the only reason people type --force is that it is shorter. Worth an alias, and worth knowing that --force-with-lease is weakened by a bare git fetch beforehand, since fetching updates the "last saw it" reference the safety check compares against.

You rebase a shared feature branch and force-push. A colleague who had already pulled the old commits runs git pull. What do they get?

Git compares commits by hash, not by content. The rebased copies have different hashes, so nothing is recognised as already-applied — that is exactly the assumption that makes this outcome surprising.

A pull does not refuse. It fetches the new commits, sees that neither branch is an ancestor of the other, and does what it is designed to do with divergent histories: merge them. The refusal happens on push, to you, before any of this.

Right, and the size is the part people underestimate. Every file your rebased commits touched now has two independent sets of changes claiming the same lines. Their fix is git fetch && git reset --hard origin/<branch> — after pushing any local work somewhere safe first, because that reset discards it.

Questions from the back row

I rebased and lost a commit. Is it really gone?

Almost certainly not. git reflog lists every position HEAD has held — including the one before the rebase — and those objects survive about 90 days before garbage collection. Find the hash, then git branch rescue <hash> to give it a name again. The reflog is local and per-clone, which is worth knowing in both directions: it will save you on your own machine, and it cannot save you from something that only ever existed on someone else's.

When is interactive rebase actually worth it?

Before a pull request, on your own unpushed commits, to turn "wip", "fix typo", "actually fix it" into commits a reviewer can read one at a time. squash folds a commit into the one above, fixup does the same and discards its message, and reword edits a message without touching content. The value is entirely for the reviewer, so the test is simple: would someone reading this history one commit at a time understand the change? If yes, leave it alone.

Rebase or merge to bring in the latest main?

If nobody else has your branch, rebase — you get a linear history and your commits sit on top of current main. If anyone else has pulled it, merge: a merge commit adds to history rather than replacing it, so their clone stays valid and no force-push is needed. The "merge commits are ugly" argument is real and it is worth far less than not breaking a colleague's checkout.

2 — The Golden Rule of Rebase

⚠ Never rebase commits that exist on a remote shared branch

When you rebase, Git creates new commits with new SHA hashes. If you've already pushed those commits and teammates have pulled them, their history now diverges from yours.

Force-pushing to fix it overwrites their work. This causes lost commits, confusing merge conflicts, and lost trust.

Safe rebase: only rebase commits on your local feature branch that haven't been pushed yet — or if you're the sole person on that branch.

When in doubt: use git merge. It's always safe. Rebase is a tool for cleaning up your own work before sharing it.

4 — git push --force-with-lease

git push --force ✗

# DANGEROUS: overwrites whatever # is on the remote — even if a # teammate pushed new commits. $ git push --force origin feature # You just deleted Alice's commit. # She will never forgive you.

git push --force-with-lease ✓

# SAFE: checks that the remote # matches what you last fetched. # Fails if someone else pushed. $ git push --force-with-lease origin feature # If Alice pushed: rejected! # Pull first, resolve, try again.

When to use force push at all: after an interactive rebase on your own feature branch (before others have based work on it), or after amending the last commit. Always use --force-with-lease, never plain --force.

6 — git reflog: Your Safety Net

Rebase gone wrong? git reflog shows every position your HEAD has been in. You can always recover:

# After a rebase that went badly wrong $ git reflog HEAD@{0} abc1234 rebase (finish): returning to refs/heads/feature HEAD@{1} def5678 rebase (pick): Add login endpoint HEAD@{2} 9a8b7c6 commit: Add login endpoint <-- this was before the rebase HEAD@{3} 4d3e2f1 checkout: moving to feature # To undo the entire rebase and go back to before it started: $ git reset --hard HEAD@{2} # You're back. Reflog saves everything for ~30 days.
