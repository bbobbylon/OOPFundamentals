Route Guards & Claim-based UI

Once the user is logged in and you hold their tokens, two questions remain: which routes may they open, and which UI should they even see? Angular answers both by reading the user's claims (roles / scopes from the validated token) in functional route guards and template gates. The catch — and the most important slide here — is that none of this is security. It's UX. The real gate is your Spring API.

🛡️ What are route guards — and why are they NOT security?

A route guard is a function that runs before Angular activates a route and returns true (allow) or a UrlTree (redirect). It stops an unauthenticated user from seeing /admin — but that's UI-only protection. Anyone can open DevTools, paste a token, or patch the JavaScript to skip the guard. The real authorization decision must happen in your Spring API, which validates the JWT signature, audience, expiry, and role claims on every request, no matter what the client does.

  • Guards are UX: they keep honest users out of pages they can't use and redirect them cleanly — not a security boundary.
  • canActivate gates a route; canActivateChild covers all children; canMatch (14+) stops the route matching at all (lazy chunk never downloads).
  • Return a UrlTree to redirect (preferred over a manual router.navigate() inside the guard).
  • Template gating (@if (isAdmin())) hides UI for the wrong role — same rule: UX only, the server still checks.
  • Guards typically read computed signals off the auth store (isAuthenticated(), hasRole('ADMIN')).

canActivate guard

canActivate: [authGuard]. The function gets ActivatedRouteSnapshot + RouterStateSnapshot and returns true, false, or a UrlTree. Reads roles from authService.roles().

Role-based template gating

@if (isAdmin()) { <button>Delete User</button> } hides UI for users without the role (computed(() => user()?.roles.includes('ADMIN'))). UX, not security — the DELETE endpoint must check server-side too.

canActivateChild / canMatch

canActivateChild guards all of a route's children with one declaration. canMatch (14+) stops the route matching entirely — the lazy chunk isn't even downloaded when it returns false.

In CIAM:an auth guard redirects unauthenticated users to /login; a role guard sends non-admins to /403 — both read computed signals off the user signal. Independently, Spring enforces @PreAuthorize("hasRole('ADMIN')") on every endpoint. Both must pass; only the server one is the real gate.

A route guard can only hide a door. It has no way to check whether that door was ever locked. That's why a guard passing every manual test in the browser proves nothing about the API underneath it, why "anyone can skip the guard in DevTools" is really a special case of a bigger truth — the guard and the server-side check are two completely independent systems that happen to agree by convention, not by anything that enforces it — and why the real failure above wasn't forgetting the guard. It was trusting that a working guard implied a working check on the other side.
Think of the guard as the "Employees Only" sign on a door, and @PreAuthorize as the lock. The sign works perfectly on everyone who reads signs and respects them. It does nothing whatsoever to someone who just tries the handle. And a missing lock is obvious the moment anyone checks it by hand — a missing @PreAuthorize is invisible until someone specifically goes and tries the handle, because every honest visitor who saw the sign never touched it at all.

The mechanism

One decision, enforced twice, by two systems that have never met.

  1. Angular's router calls your canActivate function with the route snapshot, before it builds the componentruns entirely in the browser
  2. The guard reads a signal off your in-memory auth store — no network call, just a claim already sitting in JSfast, and trivially editable
  3. true lets navigation continue; a UrlTree redirects — either way, this decision never leaves the tab it ran inthe browser is the only witness
  4. Separately, whenever the component calls the API, that HTTP request carries the JWT in an Authorization headerthe only thing that crosses the network
  5. Spring's filter chain validates that token's signature, expiry, and audience — completely unaware Angular ever ran a guard, because it never askedzero shared state with steps 1–3
  6. @PreAuthorize checks the role claim inside the now-validated token — if this annotation is missing, nothing upstream of it, guard included, can compensatethe only check that was ever real

Step 5 is the lesson — "completely unaware Angular ever ran a guard" is the whole page in one clause. Steps 1–3 and steps 4–6 aren't two halves of one system; they're two entirely separate systems that happen to reach the same conclusion when both sides are implemented correctly, and only one of the two is checking anything an attacker can't simply skip.

Four ways in, one check that actually runs for all of them. The Angular guard only ever intercepts the first path — the other three walk straight past it, because they never asked Angular anything in the first place.

An admin route uses canMatch: [roleGuard('admin')] instead of canActivate, specifically so the lazy admin bundle never downloads for non-admins. Does that choice add any protection for the /api/admin/users data the admin screen displays, compared to using canActivate?

Right. canMatch only ever decides what Angular renders in this one browser tab — it has zero jurisdiction over an HTTP endpoint sitting at a fixed URL. Anyone with a valid bearer token can call /api/admin/users directly, with curl, a mobile app, or a completely different frontend that has never heard of your canMatch guard. The bundle not downloading changes what a browser shows; it changes nothing about what the server accepts.

It sounds right — no code to build the request, no request. But REST endpoints don't require a specific frontend to exist; they answer whatever well-formed HTTP request carries a valid token, built by curl, Postman, or a five-line script, none of which need your Angular bundle at all. Not having ready-made client code is a convenience you removed, not a security boundary you added.

Tempting, because it would be a genuinely useful feature if it existed — but a bearer token is just a signed claim about who the user is and what they're allowed to do. Nothing in the OAuth2/OIDC token format ties a token's validity to which frontend route happened to render it. A validated token works against any endpoint whose @PreAuthorize check it satisfies, full stop.

Where you've seen this before

Three layers of software, the same rule every time: the client cannot be trusted to police itself.

HTML's own required/pattern attributes — the simplest version of this idea

A <input required pattern="…"> blocks a form submission in the browser — and does absolutely nothing to a POST built by hand with curl. Every framework's "client validation isn't real validation" rule is this same lesson, one layer below Angular: the check has to be repeated on the server, or it was never a check at all.

required attribute ≈ a route guard

Mobile jailbreak / root detection

An app that hides a feature when it detects a jailbroken device is doing UX, not security — a patched binary skips the check in minutes, the same way a patched Angular bundle skips a guard. Real protection against a compromised device needs server-side attestation, not a client-side flag the client itself can lie about.

jailbreak check ≈ a client-side guard

It's already inside your OIDC tokens, one layer up

The same split exists inside the token pair itself: the id_token is for your app's UI — who is this, what's their name — and should never be sent to an API. The access_token is the only thing a resource server should ever trust for authorization. Angular's guard vs. Spring's @PreAuthorize is the identical distinction one layer higher: display information versus enforcement information, and mixing them up in either place is the same mistake.

id_token:UI :: access_token:API
Questions from the back row

If guards can always be bypassed, why bother writing them at all?

Because nearly every user is honest, and for them a guard is the difference between a confusing stack trace and a clean redirect to /login that remembers where they were headed. It also saves real cost: canMatch means a non-admin's browser never downloads the admin bundle at all — fewer bytes over the wire, less compiled code sitting in their tab to poke at. "Not security" doesn't mean "not worth building." It means "not a substitute for the check that actually is security."

Does canActivate vs canMatch matter for something that genuinely needs to feel invisible, like a beta feature?

Yes — this is the one place the distinction has real teeth beyond UX polish. canActivate still lets a curious user confirm the route exists (a 403 redirect proves something is there). canMatch makes the router treat the URL as unmatched entirely, and the lazy bundle is never shipped to that browser, so nobody without the flag can even find the feature inside the compiled JS. Still not "security" in the token-validation sense — but for hiding a feature's existence rather than its data, canMatch does something canActivate genuinely can't.

The intro says a guard reads a signal "no network call." Does that make it stale if a role changes mid-session?

Yes, and that's one more reason it can't be the real gate. A guard checking a signal is checking whatever this tab currently believes, updated only when something refreshes it — typically a token refresh or re-login. Revoke an admin's role server-side mid-session and their Angular guard keeps saying yes until their token naturally expires or the app happens to refetch the user, even though their very next API call would already get a 403 from Spring. The client check isn't just skippable — it can also be looking at genuinely outdated information through no fault of its own code.

1. Functional guards: a function that returns true or a redirect

A guard runs before a route activates. Modern Angular (v15+) guards are just functions that inject() what they need and return true, false, or a UrlTree (a redirect). No classes, no providers.

export const authGuard: CanActivateFn = (route, state) => {  // a plain function, typed against Angular's CanActivateFn shape
  const auth = inject(AuthService);  // inject() works here because Angular calls guards inside an injection context
  const router = inject(Router);
  if (auth.isAuthenticated()) return true;  // true = let the navigation proceed
  // not logged in → go to /login, remember where they were headed
  return router.createUrlTree(['/login'], { queryParams: { returnUrl: state.url } });  // a UrlTree return value redirects instead of just blocking
};

// a parameterized guard — a factory that returns a CanActivateFn
export const roleGuard = (role: string): CanActivateFn => () => {  // roleGuard('admin') is what you actually pass in canActivate/canMatch arrays
  const auth = inject(AuthService), router = inject(Router);
  return auth.hasRole(role) ? true : router.parseUrl('/forbidden');  // "role" is captured by the closure — configured once, reused every navigation
};

Return true → navigation proceeds. Return a UrlTree → Angular cancels this navigation and redirects there instead. Return false → navigation is just blocked (you usually want a redirect, not a dead end). Guards may also return a Promise/Observable of those, so they can await an async check.

3. The guard family — and where each one fires

GuardQuestion it answersWhen it runs
CanActivateMay this user open this route?after the route is matched, before the component renders
CanMatchDoes this route even apply to this user?during matching — if false the route is skipped (and a lazy chunk is not fetched); the router falls through to the next matching route
CanActivateChildMay they open a child route?before activating any child of the route
CanDeactivateMay they leave (e.g. unsaved form)?on navigating away from the component
resolvePre-load data before activationafter guards pass, before render

CanActivate vs CanMatch: use canActivate to block (and redirect) — the user knows the page exists but can't enter. Use canMatch to make a route invisible: the lazy bundle never downloads and the URL can resolve to a different route entirely. Great for not even shipping admin code to non-admins.

export const routes: Routes = [
  { path: 'dashboard', canActivate: [authGuard],  // route exists and the user can SEE it fail — just gets redirected
    loadComponent: () => import('./dashboard') },
  { path: 'admin', canMatch: [authGuard, roleGuard('admin')],  // an array — ALL guards must pass, evaluated in order
    loadComponent: () => import('./admin') },   // chunk not fetched unless guards pass
  { path: '**', redirectTo: 'not-found' },  // catch-all — matches anything not matched above
];

4. Claim-based UI: hide what they can't use

A structural directive

@Directive({ selector: '[appHasRole]' })  // the [] means attribute selector — matches *appHasRole in a template
export class HasRoleDirective {
  private tpl = inject(TemplateRef<unknown>);  // the <ng-template> the * syntax sugar wraps — not rendered by default
  private vcr = inject(ViewContainerRef);  // the spot in the DOM where this directive sits — where we insert/remove views
  private auth = inject(AuthService);
  @Input() set appHasRole(role: string) {  // a setter, not a plain field — runs every time the bound value changes
    this.vcr.clear();  // wipe out whatever view is there before re-deciding — avoids stacking duplicates
    if (this.auth.hasRole(role))
      this.vcr.createEmbeddedView(this.tpl);  // only NOW does the template actually render into the page
  }
}

In the template

<!-- modern control flow -->
@if (auth.hasRole('admin')) {  // built into the template syntax — no directive import needed, calls the component's own method
  <a routerLink="/admin">Admin console</a>
}

<!-- …or the directive -->
<button *appHasRole="'admin'">  // the outer "" is the Angular binding, the inner '' makes 'admin' a string literal, not a property lookup
  Delete user
</button>

hasRole() reads the claims the IDM put in the validated token — the same id_token/access_token from login. Back it with a signal so the UI re-renders when the user (or their roles) change.

5. ⚠️ Guards are UX, not security — the server is the gate

A route guard runs in the browser, on code the user fully controls. Anyone can open devtools, skip the guard, or just curl your API with the bearer token directly. Hiding a button does not protect the endpoint behind it. Client checks only improve the experience — they stop honest users from wandering into 403s.

The actual authorization decision must happen on the resource server, which re-validates the token and re-checks authorities on every single request:

@PreAuthorize("hasAuthority('SCOPE_admin')")   // re-checked on EVERY call
@GetMapping("/api/admin/users")
List<User> all() { … }

The pairing: the Angular guard keeps non-admins out of the admin screen; Spring's @PreAuthorize (after the security filter chain validates the JWT) keeps everyone out of the admin data. Build both — and never trust the client one.

↪ Server-side enforcement: Spring · Security Filter Chain + Spring · IDM Integration (OAuth2/OIDC).

6. One-sentence recap

🛡️ Functional route guards (CanActivateFn / CanMatchFn) inject() an AuthService and return true or a UrlTree redirect to keep users out of routes their claims don't allow — canActivate blocks & redirects, canMatch hides the route and skips the lazy bundle — and the same claims drive claim-based UI (an @if or *appHasRole gate), but remember all of it is UX only: the real authorization gate is your Spring API re-checking the token with @PreAuthorize on every call.
