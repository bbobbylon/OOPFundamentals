Angular CLI & Project Structure

The Angular CLI is an opinionated command-line toolchain that scaffolds, builds, tests, and ships Angular apps. Instead of wiring up Webpack, TypeScript, and test runners yourself, you get a single ng command that handles all of it with sane defaults you can customize.

What the CLI does — and why it exists

Before the CLI, Angular developers had to manually configure Webpack, TypeScript compilation, Karma/Jasmine, Protractor, live-reload dev servers, production minification, asset pipelines, and tree-shaking — every project. The Angular team noticed that 80% of this config was identical across all projects, so they extracted it into a shareable, versionable tool called the CLI. The CLI manages a concept called schematics — blueprints for generating code — and builders — tasks for building, testing, and serving. When you run ng generate component, the CLI executes a schematic. When you run ng build, it executes a builder (esbuild or webpack under the hood). This means the entire build toolchain can be updated by upgrading one npm package.

Without CLI — manual setup

# Without CLI you manually configure:
webpack.config.js        ~200 lines
tsconfig.json            custom
karma.conf.js            custom
jest.config.js           or this
polyfills.ts             manual
src/main.ts              bootstrap code
src/styles.css           global styles entry
# And every time Angular releases a new version,
# you update all of this by hand.

With CLI — one command

$ npm install -g @angular/cli
$ ng new my-app
$ cd my-app
$ ng serve

# That's it. You get:
✔ TypeScript compilation
✔ Live reload dev server
✔ Unit test runner (Karma + Jasmine)
✔ Production build with tree-shaking
✔ Angular version migrations (ng update)
✔ Code generation (ng generate)

Installation & first steps

The CLI is a global npm package. Install it once per machine. After installation, the ng command is available everywhere in your terminal. You should have Node.js 18+ and npm 9+ installed first. 

# 1. Install the CLI globally
$ npm install -g @angular/cli

# 2. Verify the installation — shows CLI version, Node version, Angular package versions
$ ng version

Key CLI commands reference

  

    

      
CommandWhat it doesKey flags

      
        

          ng serve
          Start a live-reload dev server on localhost:4200. Recompiles on every save. Uses esbuild for very fast rebuilds.
          --port 3000, --ssl, --proxy-config proxy.conf.json, --configuration staging
        

        

          ng build
          Compile and bundle the app into the dist/ folder. Default configuration is "development"; use --configuration=production for release.
          --configuration=production, --output-hashing=all, --stats-json
        

        

          ng generate
          Scaffold a new file (component, service, pipe, etc.) using a schematic. Automatically creates the file and updates imports/declarations where needed.
          component, service, pipe, directive, guard, interceptor, module, enum, interface, class, resolver
        

        

          ng test
          Run unit tests with Karma + Jasmine (or Jest if configured). Watches for changes by default.
          --watch=false, --code-coverage, --browsers=ChromeHeadless
        

        

          ng lint
          Run ESLint (or TSLint in older projects) over the codebase.
          --fix — auto-fix fixable issues
        

        

          ng add
          Add a library to the project using its Angular schematic. Better than plain npm install because the schematic also configures angular.json, imports modules, and adds polyfills.
          ng add @angular/material, ng add @ngrx/store
        

        

          ng update
          Migrate the app to a newer Angular version. Runs migration schematics that automatically update code that the new version changed.
          ng update @angular/core @angular/cli
        

        

          ng e2e
          Run end-to-end tests. Requires an e2e testing package (Cypress, Playwright) to be added first via ng add.
          Depends on your e2e runner

angular.json deep dive

  

    

      angular.json is the CLI's master config file. It tells the CLI how to build, test, and serve your app. The structure is: projects → architect → targets (build/test/serve/…) → configurations (production/staging/…).
    

    
// angular.json — annotated skeleton
{
  "version": 1,
  "projects": {
    "my-app": {
      "projectType": "application",
      "root": "",            // project root (workspace root for the main app)
      "sourceRoot": "src",
      "architect": {
        "build": {
          "builder": "@angular-devkit/build-angular:application",  // esbuild builder
          "options": {
            "outputPath": "dist/my-app",
            "index": "src/index.html",
            "browser": "src/main.ts",      // entry point
            "polyfills": ["zone.js"],
            "tsConfig": "tsconfig.app.json",
            "assets": ["src/favicon.ico", "src/assets"],
            "styles": ["src/styles.css"],
            "scripts": []
          },
          "configurations": {
            "production": {
              "budgets": [                          // build fails if bundles exceed these sizes
                { "type": "initial", "maximumWarning": "500kb", "maximumError": "1mb" },
                { "type": "anyComponentStyle", "maximumWarning": "2kb" }
              ],
              "outputHashing": "all",              // adds content hash to filenames for cache-busting
              "fileReplacements": [              // swap environment files per config
                {
                  "replace": "src/environments/environment.ts",
                  "with": "src/environments/environment.production.ts"
                }
              ]
            },
            "staging": {
              "fileReplacements": [
                {
                  "replace": "src/environments/environment.ts",
                  "with": "src/environments/environment.staging.ts"
                }
              ]
            }
          }
        },
        "serve": {
          "builder": "@angular-devkit/build-angular:dev-server",
          "configurations": {
            "production": { "buildTarget": "my-app:build:production" },
            "development": { "buildTarget": "my-app:build:development" }
          }
        },
        "test": {
          "builder": "@angular-devkit/build-angular:karma",
          "options": { "tsConfig": "tsconfig.spec.json" }
        }
      }
    }
  }
}

  


  
  
Proxy config — forwarding API calls in dev

  

    

      In development, your Angular app runs on localhost:4200 but your API might be on localhost:3000. Browsers block cross-origin requests by default. The CLI dev server can proxy specific URL prefixes to another host — so /api/users on your Angular app silently becomes http://localhost:3000/api/users on the backend. No CORS headers needed in dev.
    

    

      

        
proxy.conf.json

        
{
  "/api": {
    "target": "http://localhost:3000",
    "secure": false,            // allow self-signed certs
    "changeOrigin": true       // rewrite origin header
  },
  "/auth": {
    "target": "https://auth.example.com",
    "secure": true,
    "pathRewrite": {
      "^/auth": ""              // strip /auth prefix before forwarding
    }
  }
}

      

      

        
Wire it up in angular.json

        
// In angular.json → serve → options:
{
  "serve": {
    "builder": "...dev-server",
    "options": {
      "proxyConfig": "proxy.conf.json"
    }
  }
}

// OR pass it on the CLI:
$ ng serve --proxy-config proxy.conf.json

// Angular app code just hits /api/users —
// the proxy quietly forwards to localhost:3000
inject(HttpClient).get('/api/users')

      

    

  


  
  
Environments — replacing files per build configuration

  

    

      You often need different API URLs, feature flags, or analytics keys for dev vs staging vs production. Angular's environment system lets you maintain one environment file per target and the CLI swaps the correct one in at build time via the fileReplacements setting in angular.json. Your app code always imports from ./environments/environment — the CLI decides which physical file that resolves to.
    

    

      

        
src/environments/environment.ts (dev)

        
export const environment = {
  production: false,
  apiUrl: 'http://localhost:3000',
  featureFlags: {
    newDashboard: true,  // enabled in dev for testing
    betaSearch: true
  }
};

      

      

        
src/environments/environment.production.ts

        
export const environment = {
  production: true,
  apiUrl: 'https://api.example.com',
  featureFlags: {
    newDashboard: false, // disabled in prod
    betaSearch: false
  }
};

      

    

    
// In your service — always import from environment.ts
import { environment } from '../environments/environment';

@Injectable({ providedIn: 'root' })
export class ApiService {
  private http = inject(HttpClient);
  private baseUrl = environment.apiUrl;   // 'localhost:3000' in dev, real URL in prod
  getUsers() { return this.http.get(`${this.baseUrl}/users`); }
}

// ng build → uses environment.ts (dev values)
// ng build --configuration=production → fileReplacement swaps in environment.production.ts

  


  
  
Build output — what's in the dist/ folder

  

    

      After ng build --configuration=production, the dist/my-app/browser/ folder contains everything needed to deploy a static SPA. Every file has a content hash in its name — so browsers can aggressively cache them, and after a new deployment they automatically download the new version (because the hash changed).
    

    

      
FileContentsCache strategy

      
        
index.htmlThe single HTML page. References all the JS and CSS bundles by their hashed names. The only file your server needs to serve for ALL routes (with a rewrite rule).No-cache or short TTL — this must always be fresh

        
main-[hash].jsYour application code — all your components, services, pipes, and directives compiled and tree-shaken. The biggest bundle.Immutable / 1 year — hash changes on every release

        
polyfills-[hash].jsBrowser compatibility shims (zone.js). Rarely changes between builds.Immutable / 1 year

        
styles-[hash].cssAll global CSS (from styles array in angular.json) concatenated into one file.Immutable / 1 year

        
chunk-[hash].jsLazy-loaded route chunks. Angular splits each lazy route into its own bundle so users only download code for routes they visit.Immutable / 1 year

        
assets/Copied verbatim from src/assets/. Images, fonts, JSON config files.Varies — set individually per asset type

        
favicon.icoBrowser tab icon.Short TTL

      
    

    
# Example production build output
$ ng build --configuration=production

  main-ABCD1234.js                   187 KB  (gzipped: ~52 KB)
  polyfills-EFGH5678.js              33 KB

Standalone (Angular 17+) vs NgModule project structure

  

    

      Angular 17 made standalone components the default. The key structural difference is: standalone projects have an app.config.ts file that acts as the application's provider list, while NgModule projects have an app.module.ts file that declares components and imports feature modules. Both are fully supported; standalone is the modern recommendation.
    

    

      

        
Standalone (default since Angular 17)

        
// src/main.ts
bootstrapApplication(AppComponent, appConfig);

// src/app/app.config.ts — the app's provider list
export const appConfig: ApplicationConfig = {
  providers: [
    provideRouter(routes),
    provideHttpClient(),
    provideAnimationsAsync()
  ]
};

// src/app/app.component.ts — standalone: true
@Component({
  selector: 'app-root',
  standalone: true,
  imports: [RouterOutlet],   // self-contained — no module needed
  templateUrl: './app.component.html'
})
export class AppComponent {}

      

      

        
NgModule (older / migrated apps)

        
// src/main.ts
platformBrowserDynamic().bootstrapModule(AppModule);

// src/app/app.module.ts — declarations + imports
@NgModule({
  declarations: [
    AppComponent,         // must declare every component here
    NavbarComponent,
    HomeComponent
  ],
  imports: [
    BrowserModule,
    RouterModule.forRoot(routes),
    HttpClientModule
  ],
  bootstrap: [AppComponent]
})
export class AppModule {}

// src/app/app.component.ts — no standalone flag
@Component({
  selector: 'app-root',
  templateUrl: './app.component.html'
})
export class AppComponent {}

      

    

  


  
  
TypeScript config files

  

    

      

        
tsconfig.json

        
Base config for the whole workspace. Sets compiler options like target, strict, experimentalDecorators. The other two extend this via "extends".

      

      

        
tsconfig.app.json

        
Extends the base. Targets only src/main.ts and application source. Excludes test files. Used by ng build.

      

      

        
tsconfig.spec.json

        
Extends the base. Includes test files (*.spec.ts). Used by ng test (Karma) or Jest. Often has slightly looser settings than the app config.

      

    

    
// tsconfig.json — important Angular-specific settings
{
  "compilerOptions": {
    "target": "ES2022",
    "lib": ["ES2022", "dom"],
    "strict": true,                       // enables strict type checking — keep this on!
    "experimentalDecorators": true,        // needed for @Component, @Injectable, etc.
    "useDefineForClassFields": false,      // Angular-specific — needed for decorators to work
    "moduleResolution": "bundler",         // modern — lets esbuild resolve modules
    "paths": {                             // optional: create short import aliases
      "@app/*": ["src/app/*"],
      "@env/*": ["src/environments/*"]
    }
  }
}

  


  
  
Common mistakes

  

    

      
Editing node_modules/

      
Never modify files in node_modules/. It's regenerated on every npm install and isn't tracked by git. If you need to patch a package, use patch-package.

    

    

      
Committing angular.json builder version mismatches

      
When teammates run different CLI versions, the generated angular.json builder strings can conflict. Always run ng update before upgrading Angular and commit the result as a team.

    

    

      
Hardcoding API URLs in component code

      
API URLs belong in environment files. Components should never contain 'https://api.example.com' directly — use the environment object or an InjectionToken so you can swap them per build configuration.

    

    

      
Missing the proxy config in serve options

      
If you only pass --proxy-config on the CLI, it doesn't persist for teammates. Add "proxyConfig" to the serve.options section in angular.json so everyone gets it automatically.

    

    

      
Budget limits causing build failures

      
If ng build --configuration=production fails with a "bundle budget exceeded" error, the fix is usually not to raise the budget — it's to lazy-load more routes or import fewer libraries. The budget is a guard, not an obstacle.

    

    

      
Mixing standalone and NgModule styles

      
In a standalone project, adding declarations to a non-existent AppModule does nothing. Standalone components import their dependencies directly in the component's imports array, not via a module.
