NgRx SignalStore

Signals-first state management — withState, withComputed, withMethods, withHooks, and withEntities. All the structure of NgRx with a fraction of the boilerplate.

📦 What is NgRx SignalStore — and how is it different from classic NgRx?

Classic NgRx makes you write Actions, Reducers, Selectors, and Effects in separate files — a lot of ceremony for simple state. NgRx SignalStore (17+) is the same team's signals-based alternative: you compose state, computed values, and methods in one place with signalStore(). Everything is exposed as signals — no store.select(), no async pipe — you just read store.users() in the template. It's the middle ground between "a service holding a signal" and full NgRx.

  • Composable "features": withState, withComputed, withMethods, withEntities, withHooks — mix what you need.
  • State is signals; update immutably with patchState(store, { … }) (partial, type-checked).
  • withComputed derives cached values; withMethods holds the actions (async, or rxMethod for streams).
  • withEntities<T>() gives a normalized id→entity collection with setAllEntities/addEntity/updateEntity/removeEntity.
  • No actions/reducers/effects boilerplate — but you lose NgRx's centralized action log / time-travel (a deliberate trade).

withState — signal state

signalStore(withState({ users: [] as User[], loading: false })). Each key is a signal: store.users(), store.loading(). Update with patchState(store, { loading: true }). Types are inferred from the initial value.

withComputed + withMethods

withComputed(s => ({ admins: computed(() => s.users().filter(u => u.role === 'ADMIN')) })) and withMethods(s => ({ load: async () => { patchState(s, { loading: true }); … } })). Call store.load().

withEntities — normalized lists

withEntities<User>() adds an id→entity map + ids array, with setAllEntities(), addEntity(), updateEntity({ id, changes }), removeEntity(id). store.entities() returns the array — no manual array juggling.

In CIAM:a UserManagementStore = signalStore(withEntities<User>(), withState({ page: 0, size: 20 }), withComputed(…adminCount…), withMethods((s, api = inject(UserApi)) => ({ loadPage: async p => { const res = await api.getUsers(p, s.size()); patchState(s, { page: p }); setAllEntities(res.users); } }))) — paged, entity-normalized, all signals.

NgRx SignalStore — NgRx's answer to the boilerplate complaint

Traditional NgRx (Actions/Reducers/Effects/Selectors) is powerful but verbose. For many features, developers reach for a simple service-with-subject pattern because NgRx feels like too much. SignalStore bridges the gap: you get the benefits of a structured, testable, DevTools-connected state container without dispatching action objects or writing reducer switch cases. State is exposed as Angular Signals — reactive, fine-grained, and zero-zone-dependency.

Traditional NgRx — what you write for a counter

// counter.actions.ts
const increment = createAction('[Counter] Increment');
const decrement = createAction('[Counter] Decrement');
const reset     = createAction('[Counter] Reset');

// counter.reducer.ts
const initialState = { count: 0 };
const counterReducer = createReducer(
  initialState,
  on(increment, s => ({ ...s, count: s.count + 1 })),
  on(decrement, s => ({ ...s, count: s.count - 1 })),
  on(reset,     s => ({ ...s, count: 0 }))
);

// counter.selectors.ts
const selectCount =
  createSelector(featureSelector, s => s.count);
const selectDoubled =
  createSelector(selectCount, n => n * 2);

// component
this.store.dispatch(increment());
count$ = this.store.select(selectCount);
~30+ lines across 3+ files. Every change requires creating an action, updating a reducer, possibly a selector.

SignalStore — the same counter

// counter.store.ts
export const CounterStore =
  signalStore(
    withState({ count: 0 }),

    withComputed(({ count }) => ({
      doubled: computed(() => count() * 2)
    })),

    withMethods((store) => ({
      increment() {
        patchState(store, s =>
          ({ count: s.count + 1 })
        );
      },
      decrement() {
        patchState(store, s =>
          ({ count: s.count - 1 })
        );
      },
      reset() { patchState(store, { count: 0 }); }
    }))
  );

// component
store.increment();
count = store.count();      // it's a Signal!
doubled = store.doubled(); // computed signal
One file. Call methods directly. Read state as signals. No actions, no dispatch, no selectors for basic access.
SignalStore is NOT a replacement for all NgRx. For complex cross-feature state, time-travel debugging with Redux DevTools, or team-scale apps where action traceability matters, traditional NgRx Store + Effects is still the right tool. SignalStore is NgRx's answer for local/feature state — the cases where ComponentStore or a service-with-signals used to be the go-to.

Core API — the four withX functions

A SignalStore is created by composing four building blocks. Each withX function extends the store's type — TypeScript sees the full merged API as one object.

withState — initial state becomes signals

import { signalStore, withState, patchState }
  from '@ngrx/signals';

// Defining state shape:
type UserState = {
  user:    User | null;
  loading: boolean;
  error:   string | null;
};

const initialState: UserState = {
  user: null, loading: false, error: null
};

export const UserStore = signalStore(
  withState(initialState)
  // ↑ creates: store.user()     → Signal<User|null>
  //           store.loading()  → Signal<boolean>
  //           store.error()    → Signal<string|null>
);

withComputed — derived state from signals

withComputed(({ user, loading, error }) => ({
  // Receives the state signals as destructured params
  isLoggedIn: computed(() => user() !== null),
  displayName: computed(() =>
    user()?.name ?? 'Guest'
  ),
  hasError: computed(() => error() !== null),
  status: computed(() => {
    if (loading()) return 'loading';
    if (error())   return 'error';
    if (user())    return 'loaded';
    return 'empty';
  })
}))
// These are standard Angular computed() signals — lazily evaluated,
// automatically tracked, update only when inputs change.

withMethods — actions that mutate state

withMethods((store) => {
  const userSvc = inject(UserService);  // inject() works here!

  return {
    // Sync method — direct patchState
    clearError() {
      patchState(store, { error: null });
    },

    // Async method — uses rxMethod for Observable piping
    loadUser: rxMethod<string>(
      pipe(
        tap(() => patchState(store, { loading: true, error: null })),
        switchMap(id => userSvc.getById(id).pipe(
          tapResponse({
            next:  user  => patchState(store, { user, loading: false }),
            error: err   => patchState(store, { error: err.message, loading: false })
          })
        ))
      )
    )
  };
})

withHooks — lifecycle integration

withHooks({
  onInit(store) {
    // Runs when the store is first created (service injection)
    // Perfect for kicking off initial data loads
    store.loadUser(inject(AuthService).userId());
  },
  onDestroy(store) {
    // Runs when the store's scope is destroyed
    // (useful when provided at component level)
  }
})

patchState vs setState

// patchState — merges partial state (most common)
patchState(store, { loading: false });
// Only 'loading' changes. user and error are preserved.

// patchState with updater function (use current values)
patchState(store, s => ({ count: s.count + 1 }));

// setState — replaces the entire state (dangerous, use rarely)
// Available from @ngrx/signals/testing for full state replacement

Providing the store — global vs component-scoped

// Global (singleton, available everywhere)
export const TodoStore = signalStore(
  { providedIn: 'root' },   // ← option object before withX calls
  withState({ todos: [] }),
  withMethods(...)
);

// Component-scoped (each component instance gets its own store)
@Component({
  providers: [TodoStore]    // ← provide in component providers
})
export class TodoListComponent {
  store = inject(TodoStore);

  // Access state as signals — no async pipe needed!
  todos   = this.store.todos();
  loading = this.store.loading();
}

withEntities() — built-in CRUD collection management

withEntities() from @ngrx/signals/entities adds a normalized entity map to the store. Internally it stores a Record<string|number, T> (fast lookup) plus an ordered array of IDs. It ships with updater functions for all common CRUD operations — you never manually slice arrays. 

import { signalStore, withState, withMethods, patchState }
  from '@ngrx/signals';
import {
  withEntities,
  addEntity, updateEntity, removeEntity, setAllEntities,
  selectAllEntities, selectEntity
} from '@ngrx/signals/entities';

type Todo = { id: number; title: string; done: boolean };

export const TodoStore = signalStore(
  { providedIn: 'root' },

  withEntities<Todo>(),
  // ↑ Adds to the store:
  //   store.entities()        → Signal<Todo[]> (all entities, ordered)
  //   store.entityMap()       → Signal<Record<number,Todo>> (fast id lookup)
  //   store.ids()             → Signal<number[]> (ordered ids)
  //   selectEntity(store, id) → computed signal for one entity

  withState({ loading: false, filter: 'all' as 'all'|'active'|'done' }),

  withComputed(({ entities, filter }) => ({
    filteredTodos: computed(() => {
      const f = filter(), all = entities();
      if (f === 'active') return all.filter(t => !t.done);
      if (f === 'done')   return all.filter(t =>  t.done);
      return all;
    }),
    totalCount:  computed(() => entities().length),
    doneCount:   computed(() => entities().filter(t => t.done).length),
    activeCount: computed(() => entities().filter(t => !t.done).length),
  })),

  withMethods((store) => {
    const http = inject(HttpClient);
    let nextId = 1;

    return {
      addTodo(title: string) {
        patchState(store,
          addEntity({ id: nextId++, title, done: false })
        );
      },
      toggleTodo(id: number) {
        const todo = store.entityMap()[id];
        patchState(store,
          updateEntity({ id, changes: { done: !todo.done } })
        );
      },
      removeTodo(id: number) {
        patchState(store, removeEntity(id));
      },
      loadTodos: rxMethod<void>(
        pipe(
          switchMap(() => http.get<Todo[]>('/api/todos')),
          tap(todos => patchState(store, setAllEntities(todos)))
        )
      ),
      setFilter(filter: 'all'|'active'|'done') {
        patchState(store, { filter });
      }
    };
  }),

  withHooks({
    onInit(store) { store.loadTodos(); }
  })
);

Entity updater functions reference

FunctionUsageEffect
addEntity(entity)patchState(store, addEntity({ id:1, name:'x' }))Adds one entity; replaces if id already exists
addEntities(entities)patchState(store, addEntities([...]))Adds many; merges into existing map
setEntity(entity)patchState(store, setEntity({...}))Upsert — add or replace by id
setAllEntities(entities)patchState(store, setAllEntities([...]))Replaces entire collection
updateEntity({id, changes})patchState(store, updateEntity({ id:1, changes:{ done:true } }))Partial update — merges changes
updateEntities({ids, changes})patchState(store, updateEntities({ ids:[1,2], changes:{done:true} }))Bulk partial update
removeEntity(id)patchState(store, removeEntity(1))Removes by id
removeEntities(ids)patchState(store, removeEntities([1,2,3]))Bulk remove
removeAllEntities()patchState(store, removeAllEntities())Clears entire collection
Custom entity id key: by default, withEntities expects an id field. To use a different key: withEntities<Product>({ idKey: 'productId' }). The idKey must be of type string or number.

Comparison — all four Angular state options

Angular has four main approaches to state management. There is no universally "best" choice — the right pick depends on feature scope, team size, and whether you need features like time-travel debugging.

Criterion Service + Signals NgRx ComponentStore NgRx SignalStore NgRx Store (classic)
Boilerplate None Low Low High
Reactivity model Signals RxJS Observables Signals (primary) RxJS Observables
Redux DevTools No Basic (with plugin) Yes (plugin available) Full time-travel
Action traceability None Effect events Method names Full action log
Entity collection Manual Manual withEntities() @ngrx/entity
Cross-feature state Service shared via DI Not intended for it providedIn:'root' First-class
Testing Plain class test TestBed with helpers TestBed, getState() MockStore, marbles
Best for Isolated, small state Component-level state with effects Feature state, entity lists, medium apps Large apps, many teams, debugging needs

Decision flowchart

Is this state used only within a single component?
  → Yes: use signals in the component class — no separate store needed
  → No: continue below

Is this state shared across the whole app (global)?
  → Yes + needs time-travel/action log: use NgRx Store
  → Yes + moderate complexity: use SignalStore with providedIn:'root'
  → No: continue below

Is this a per-feature or per-route store?
  → Has entity collections: use SignalStore + withEntities()
  → Simple, no entities: use Service with signals or SignalStore
  → Needs complex async with RxJS: use ComponentStore
SignalStore + Effects: you can still use NgRx Effects alongside SignalStore for complex side effects — they operate at the Store (classic) level. SignalStore does not replace Effects; it replaces the boilerplate for simple mutations and local state. In large apps, both coexist: classic NgRx Store for cross-cutting global state, SignalStore for feature-specific state.
