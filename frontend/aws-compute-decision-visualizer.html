Choosing Compute: EC2 vs Lambda vs ECS/Fargate vs EKS

Same workload, four different compute models. Watch how one spiky-traffic image-resize API behaves differently depending on which compute service is under it — the code barely changes, but the operational and cost story is completely different each time.

🧭 "Just deploy it" isn't a real answer — which compute service?

AWS gives you (at least) four ways to run the same piece of code, and they sit on a spectrum from most control / most ops burden to least control / least ops burden. EC2 is a virtual machine you fully manage — you pick the OS, patch it, and an Auto Scaling Group adds or removes whole instances to match load; capacity is provisioned ahead of demand, so you're always paying for some idle baseline. Lambda is the opposite extreme — you upload a function, AWS runs it per-invocation, and it scales from zero to thousands of concurrent executions without you provisioning anything; you pay per invocation/duration, not for idle time, but each cold execution environment has to initialize first (a cold start), and there's a hard ceiling on execution time (15 minutes) and memory. ECS/Fargate sits in the middle — you package the app as a container, Fargate runs it without you managing any EC2 host underneath, and scaling adds/removes tasks (containers) rather than whole VMs or per-invocation functions; cold start is container-level (faster than an EC2 boot, slower than Lambda). EKS is Kubernetes on AWS — the most portable and flexible (the same manifests could run on any cloud's Kubernetes), but it stacks two scaling loops on top of each other (pods via the Horizontal Pod Autoscaler, and the underlying nodes via the Cluster Autoscaler) and you own real operational complexity (upgrades, networking, RBAC) that the other three abstract away. There's no universally-right answer — the right one depends on how spiky the traffic is, how long a single unit of work takes, and how much operational surface area your team wants to own.

  • EC2 — full control, provisioned capacity, slowest to scale (whole-VM boot), you pay for idle baseline 24/7.
  • Lambda — zero to thousands of concurrent executions near-instantly, pay only per invocation, but a cold start per fresh execution environment and hard 15-minute/memory ceilings.
  • ECS/Fargate — container-level scaling with no servers to manage, a middle ground on both cold-start speed and cost model.
  • EKS — most portable and flexible, but two stacked scaling loops (pods + nodes) and real cluster-ops overhead.

"Spiky" is the deciding word

A steady, predictable load favors EC2 (provision once, pay a flat known rate). A spiky, unpredictable load favors Lambda or Fargate, which only cost money while actually doing work.

Cold start is not one number

EC2's "cold start" is a full OS boot (~60-120s). ECS/Fargate's is a container pull + start (~30-60s). Lambda's is per-execution-environment (~200ms-2s depending on runtime and package size) — three very different meanings of the same word.

Execution time ceilings force the choice

Lambda hard-caps a single invocation at 15 minutes. A batch image-processing job that can run for hours simply can't live on Lambda at all — that alone rules it out regardless of cost or scaling preferences.

CIAM / production shape: a Spring Boot CIAM API with steady, predictable authentication traffic is usually a poor fit for Lambda (the JVM's cold start is one of the heaviest of any runtime) and a good fit for ECS/Fargate or EC2 behind an ALB — see the load balancing visualizer for how that pairs with an Auto Scaling Group. A spiky, bursty side task like this page's image-resize example is the opposite case: exactly the shape Lambda was built for.

A few things worth knowing

  • These aren't mutually exclusive — a real system often mixes them: a Spring Boot API on ECS/Fargate for the steady request path, with a Lambda triggered by an S3 upload event to actually perform this page's image-resize job.
  • Lambda's memory setting also sets CPU — increasing MemorySize proportionally increases the CPU allocated to the function, which can make a CPU-bound job like image resizing finish faster even though you "only" asked for more memory.
  • EKS's two scaling loops can fight each other — the Horizontal Pod Autoscaler can decide to add pods faster than the Cluster Autoscaler can add nodes to host them, leaving pods stuck "Pending" until node capacity catches up.
