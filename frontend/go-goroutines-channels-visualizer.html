Goroutines & Channels

Goroutines (lightweight, M:N scheduled), channels (typed message passing), select (non-blocking channel ops), and the sync package (Mutex, WaitGroup).

🔀 What are goroutines and channels — and how do they differ from Java threads?

Go's concurrency rests on two primitives. Goroutines are lightweight concurrent functions — go fn() starts one on a few KB of scheduler-managed stack (not an OS thread); creation is ~2μs/~4KB vs Java's ~1ms/~1MB, so a goroutine-per-request handles 100k concurrent with a fraction of the overhead. Channels are typed conduits between goroutines (unbuffered blocks until received; buffered blocks when full) — the philosophy is "don't communicate by sharing memory; share memory by communicating." select waits on several channel ops at once (timeouts via time.After, cancel via ctx.Done(), non-blocking via default). When shared memory IS right, the sync package has Mutex/RWMutex/WaitGroup/Once.

  • Goroutines are cheap — ~2μs/4KB vs threads' ~1ms/1MB; one per request.
  • Channels pass data — unbuffered syncs; buffered decouples; share by communicating.
  • select multiplexes channels — timeout, cancel, non-blocking default.
  • sync for shared memory — Mutex/WaitGroup/Once when channels don't fit.

Goroutines + WaitGroup

func fetchAllUsers(client *IdpClient, ids []int) []User { results := make([]User, len(ids)) var wg sync.WaitGroup var mu sync.Mutex for i, id := range ids { wg.Add(1) go func(idx, userID int) { defer wg.Done() user, err := client.GetUser(userID) if err != nil { return } mu.Lock() results[idx] = user mu.Unlock() }(i, id) // Each iteration starts a goroutine } wg.Wait() // block until all goroutines done return results } // 100 goroutines fetching concurrently // vs 100 sequential HTTP calls

Java thread comparison

Go goroutine → Java equivalent. go fn() → Thread t = new Thread(fn); t.start() or CompletableFuture.runAsync(fn). But goroutines are ~1000x cheaper (2μs vs 1ms, 4KB vs 1MB). sync.WaitGroup → CountDownLatch. sync.Mutex → synchronized block or ReentrantLock. chan int → BlockingQueue<Integer> (unbuffered ≈ SynchronousQueue, buffered ≈ LinkedBlockingQueue(100)). select { case <-ctx.Done() } → Java virtual threads (Project Loom) or reactive Spring WebFlux. Go's model: channels enforce ownership transfer — when you send data through a channel, the receiver owns it, reducing race conditions. Spring Boot with virtual threads (Java 21+) approaches Go's concurrency model but with more overhead.

CIAM Go service: A bulk user-export service fans out one goroutine per page fetch and a WaitGroup collects results into a channel (go func() { wg.Wait(); close(results) }()). An event pipeline has one goroutine reading Ping webhook events and another processing, with a buffered channel between. On SIGTERM, cancel() closes ctx.Done() and every watching goroutine stops cleanly. The Spring equivalent — @Async + CompletableFuture.allOf() — is more boilerplate and lower throughput.

Or: the channel bug that never panics, never logs, and never ends.

The problem

A nil map screams the moment you touch it. A nil channel just waits. Forever. Silently.

A goroutine that vanishes without a single log line

A struct has a chan Result field that's supposed to be set by a constructor, NewWorker() — but one code path builds the struct directly with &Worker{} (a quick unit-test helper, or a config branch that forgot the make). The field is left at its zero value: nil.

The worker goroutine reaches result := <-w.resultsCh. Nothing panics. Nothing errors. The goroutine just parks there — permanently. runtime.NumGoroutine() creeps up by one, forever, and if it's the last goroutine waiting with nothing left to run, the whole program freezes with fatal error: all goroutines are asleep - deadlock! instead of a stack trace pointing at the real bug.

compiles ✓ no panic on startup ✓ the channel was never make()'d ⚠

A nil slice is safe to read. A nil map panics on write. A nil channel does neither — it just blocks, on send AND receive, forever.

Treat "nil channel" as a checklist item, not a runtime surprise
Initialize every channel field in the constructor, never leave it at the zero value ↓ make(chan T) (or , n) is what turns "blocks forever" into "blocks until someone sends" In tests, construct through the real constructor, not a bare struct literal ↓ &Worker{} silently skips every make() call the real constructor would have run And if a goroutine looks stuck, check runtime.NumGoroutine() — a nil channel leaves no other trace
nil channel operations block forever — on purpose. This isn't a missing nil-check the runtime forgot to add. A nil channel blocking forever is specified, deliberate Go behavior, because a select can use it as an off switch: assign ch = nil to a case's channel variable and that case can never be chosen again, without an extra boolean flag anywhere.
A nil channel is a phone line that was never connected — you can pick up the receiver and "wait" as long as you like, but there's no dial tone, no busy signal, no error. Contrast that with a nil MAP, which is more like a filing cabinet with no drawers: try to file something and it screams immediately. Same nil-ness, two completely different reactions.
You

If sending to a nil channel is basically a bug, why doesn't Go just panic like it does for a nil map?

The Go runtime

Because sometimes you WANT a channel operation to never fire. I let you set a channel variable to nil specifically so a select case attached to it goes silent — permanently — without an if enabled around every case.

You

So how do I tell "nil on purpose" from "nil by mistake — forgot to make() it"?

The Go runtime

I can't — that part's on you. I treat both identically: block forever. If you meant to disable a case, great. If you forgot a make(), you've built the exact same thing, and it looks like a hang, not a crash.

The mechanism

Watch a select loop deliberately nil out a channel to turn a case off — the same rule that hides the bug is also the intended feature.

  1. doneCh starts non-nil, wired to a real closing signal channelcase armed
  2. select { case <-doneCh: cleanup(); doneCh = nil } — case fires oncefires once
  3. doneCh = nil is the last line in that case body — deliberatedisable on purpose
  4. Next loop iteration: select evaluates case <-doneCh againre-evaluated
  5. doneCh is nil now, so that case is never ready — select simply skips it, foreversilently skipped
  6. The other cases in the same select keep working normally — only this one is switched offsurgical disable

Step 5 is exactly the same rule that caused the bug above — "a nil channel is never ready" — except here it's load-bearing: it's the one line of Go idiom that turns off a single select case without a boolean guard cluttering every branch.

nil (zero value) send or receive attempted → blocks forever, no panic
open (after make) send within capacity → proceeds immediately
closed another send attempted → panics: send on closed channel

Three channel states, three completely different reactions to the same "send" operation: silence forever, success, or a panic. Nowhere does the type system tell you which state a chan Result variable is in — that's tracked entirely at runtime, by you.

type Worker struct { out chan int }. A test builds one with w := &Worker{} (skipping the real constructor) and starts go func(){ w.out <- compute() }(). No make was ever called on out. What happens?

A nil channel is never ready for communication, in either direction. The send doesn't error — it just never proceeds, because there's no channel behind out for it to hand the value to. The goroutine leaks unless something recovers it.

That's the nil MAP rule, not the nil channel rule — writing to a nil map panics, but sending on a nil channel is defined to block forever instead, precisely so it can be used to disable a select case on purpose.

Nothing "discards" the value quietly — the send statement itself never completes, so the line right after it (and the rest of that goroutine) never executes either. It's stuck, not skipped.

an unfulfilled contract just waits, it doesn't complain

A Spring @Async method with no configured executor

Misconfigure the executor and an @Async call can silently queue and never run, rather than failing loudly at the call site — the caller expecting a background task to fire has no direct signal that it didn't.

1. The M:N Scheduler

Go multiplexes M goroutines onto N OS threads (M:N scheduling). A goroutine starts with ~2KB stack (vs ~1MB for OS threads) and grows dynamically. The Go runtime parks goroutines on blocking operations and runs other goroutines — no OS context switch needed.

"Do not communicate by sharing memory; share memory by communicating." — Go proverb. Channels are the idiomatic way to pass data between goroutines. Use sync.Mutex only when you need shared state that multiple goroutines read/write (like a cache).

2. Channel Types

Unbuffered (synchronous)

ch := make(chan int) // capacity = 0
go func() { ch <- 42 }() // blocks until receiver ready
v := <-ch // blocks until sender sends
// Both sides meet at the channel — like a handoff

Buffered (asynchronous)

ch := make(chan int, 3) // capacity = 3
ch <- 1 // no block (buffer has space)
ch <- 2 // no block
ch <- 3 // no block (full now)
ch <- 4 // BLOCKS — buffer full

close() signals no more sends

close(ch) // only sender should close
v, ok := <-ch // ok=false when closed + empty
for v := range ch { ... } // range exits on close

Direction types

func producer(ch chan<- int) {} // send-only
func consumer(ch <-chan int) {} // receive-only
// Direction-typed channels enforce correct usage

3. Context for Cancellation

ctx, cancel := context.WithTimeout(context.Background(), 5*time.Second)
defer cancel() // ALWAYS defer cancel to prevent goroutine leak

go func() {
  select {
  case result := <-workCh:
    fmt.Println(result)
  case <-ctx.Done():
    fmt.Println("timeout:", ctx.Err())
  }
}()
Always defer cancel(). Not calling cancel() leaks the context goroutine and timer. Context is the standard Go mechanism for deadline propagation — pass ctx as the first argument to any function that does I/O, and check ctx.Err() or ctx.Done() in long loops.
