1. The M:N Scheduler

Go multiplexes M goroutines onto N OS threads (M:N scheduling). A goroutine starts with ~2KB stack (vs ~1MB for OS threads) and grows dynamically. The Go runtime parks goroutines on blocking operations and runs other goroutines — no OS context switch needed.

"Do not communicate by sharing memory; share memory by communicating." — Go proverb. Channels are the idiomatic way to pass data between goroutines. Use sync.Mutex only when you need shared state that multiple goroutines read/write (like a cache).

2. Channel Types

Unbuffered (synchronous)

ch := make(chan int) // capacity = 0
go func() { ch <- 42 }() // blocks until receiver ready
v := <-ch // blocks until sender sends
// Both sides meet at the channel — like a handoff

Buffered (asynchronous)

ch := make(chan int, 3) // capacity = 3
ch <- 1 // no block (buffer has space)
ch <- 2 // no block
ch <- 3 // no block (full now)
ch <- 4 // BLOCKS — buffer full

close() signals no more sends

close(ch) // only sender should close
v, ok := <-ch // ok=false when closed + empty
for v := range ch { ... } // range exits on close

Direction types

func producer(ch chan<- int) {} // send-only
func consumer(ch <-chan int) {} // receive-only
// Direction-typed channels enforce correct usage

3. Context for Cancellation

ctx, cancel := context.WithTimeout(context.Background(), 5*time.Second)
defer cancel() // ALWAYS defer cancel to prevent goroutine leak

go func() {
  select {
  case result := <-workCh:
    fmt.Println(result)
  case <-ctx.Done():
    fmt.Println("timeout:", ctx.Err())
  }
}()
Always defer cancel(). Not calling cancel() leaks the context goroutine and timer. Context is the standard Go mechanism for deadline propagation — pass ctx as the first argument to any function that does I/O, and check ctx.Err() or ctx.Done() in long loops.
