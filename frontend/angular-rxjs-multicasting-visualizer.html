RxJS Multicasting

share, shareReplay, publish, multicast — turning cold Observables hot and controlling subscriptions

The Problem: Cold Observables Duplicate Work

Cold Observable — each subscriber gets its own execution

A cold Observable creates a new producer for every subscriber. Two subscribers = two HTTP requests.

const data$ = this.http.get('/api/data');

// Subscriber A
data$.subscribe(v => console.log('A:', v)); // → HTTP request #1

// Subscriber B (same observable — different request!)
data$.subscribe(v => console.log('B:', v)); // → HTTP request #2 ❌
Cold observable — watch the request count
Subscriber A
Subscriber B
HTTP Requests: 0

Hot Observable — all subscribers share one execution

Multicasting shares a single producer across all subscribers. Two subscribers = one HTTP request.

const data$ = this.http.get('/api/data')
  .pipe(shareReplay(1)); // ← multicast!

// Subscriber A
data$.subscribe(v => console.log('A:', v)); // → HTTP request #1

// Subscriber B (gets same emission!)
data$.subscribe(v => console.log('B:', v)); // → no new request ✓
Hot/shared observable — same request, both get it
Subscriber A
Subscriber B
HTTP Requests: 0

The Four Multicasting Operators

share() — ref-counted multicast

Shares one subscription. Unsubscribes when last subscriber leaves. Re-subscribes (cold restart!) when next subscriber arrives.

import { share } from 'rxjs/operators';

const clicks$ = fromEvent(btn, 'click').pipe(
  share()
);

// Both subscribers hear the same click events
clicks$.subscribe(e => updateCounter());
clicks$.subscribe(e => logEvent());

// When BOTH unsubscribe → source unsubscribes
// When next subscriber comes → source re-subscribes
✓ Deduplicates subscriptions
✓ Automatically tears down (ref counting)
✗ Late subscribers miss past emissions
✗ Restarts source if all unsub then resub

Best for: Event streams, websockets, user actions — anything ongoing where late arrival is OK

shareReplay(n) — replay for late subscribers

Like share() but replays the last n emissions to any late subscriber. The most common choice for HTTP caching.

import { shareReplay } from 'rxjs/operators';

const config$ = this.http.get('/config').pipe(
  shareReplay(1)   // cache the 1 latest response
);

// First subscriber triggers the request
config$.subscribe(c => this.setupA(c));

// Second subscriber 500ms later — gets cached value instantly!
timer(500).pipe(switchMap(() => config$))
  .subscribe(c => this.setupB(c));

// ⚠️ shareReplay default: refCount: false
// → source stays subscribed even with 0 subscribers
// → use { bufferSize: 1, refCount: true } to auto-teardown
shareReplay({ bufferSize: 1, refCount: true })
✓ Late subscribers get cached value immediately
✓ HTTP request fires only once (perfect for config/user data)
⚠ Default refCount:false keeps source alive forever
⚠ Can cause memory leaks without refCount:true

Best for: HTTP requests you want cached (config, user profile, feature flags)

publish() + refCount() — the manual way

publish() returns a ConnectableObservable. You control when the source subscription starts. refCount() makes it auto-manage.

import { publish, refCount } from 'rxjs/operators';

const source$ = interval(1000).pipe(
  publish(),   // wrap in Subject (multicast)
  refCount()   // auto-connect when first sub arrives
);
// ↑ equivalent to share()

// Manual connect (no refCount)
const connected$ = interval(1000).pipe(publish());
const conn = connected$.connect(); // starts NOW, before any subscriber
connected$.subscribe(...);
conn.unsubscribe(); // stop it manually

Best for: Cases where you need to control the start time of the source (e.g., start emitting before any UI is mounted)

multicast(Subject) — choose your Subject type

Like publish() but you pick the Subject. Use ReplaySubject to replay N values (same effect as shareReplay).

import { multicast, refCount, ReplaySubject } from 'rxjs';

const shared$ = source$.pipe(
  multicast(() => new ReplaySubject(3)),
  refCount()
);
// Late subscribers get last 3 values

// With Subject (no replay) = share()
multicast(new Subject()).pipe(refCount());

// With BehaviorSubject (always has a value)
multicast(new BehaviorSubject(0)).pipe(refCount());

Best for: Custom replay strategies, or when you need BehaviorSubject semantics on an arbitrary Observable

Which Multicasting Operator to Use?

Operator Late subscriber gets? Source teardown? Source restart on resub? Best use case
share() Nothing — joins live Yes (ref counted) Yes — cold restart Ongoing event streams
shareReplay(1) Last value immediately No (default). Use refCount:true No — keeps value cached HTTP caching, config, user data
shareReplay({bufferSize:1, refCount:true}) Last value immediately Yes Yes — re-fetches after all unsub Cacheable HTTP with auto-cleanup
publish() + refCount() Nothing Yes Yes Same as share() — explicit form
multicast(ReplaySubject) + refCount() Last N values Yes Yes Custom buffer strategies

Real-World Pattern: HTTP Caching Service

The Pattern

@Injectable({ providedIn: 'root' })
export class UserService {
  private http = inject(HttpClient);

  // Shared, cached Observable — one request total
  readonly currentUser$ = this.http
    .get<User>('/api/me')
    .pipe(
      shareReplay({ bufferSize: 1, refCount: true })
    );

  // Force a refresh (e.g., after profile update)
  private refresh$ = new Subject<void>();

  readonly user$ = this.refresh$.pipe(
    startWith(undefined),
    switchMap(() =>
      this.http.get<User>('/api/me')
    ),
    shareReplay(1)
  );

  refresh() { this.refresh$.next(); }
}

Component usage

@Component({
  template: `
    <!-- Both components share ONE HTTP request -->
    <app-header [user]="user$ | async" />
    <app-profile [user]="user$ | async" />

    <!-- Or with signals interop -->
    {{ user() | json }}
  `
})
export class AppComponent {
  private userSvc = inject(UserService);

  // async pipe → auto-unsubscribes on destroy
  user$ = this.userSvc.user$;

  // Or convert to signal (Angular 17+)
  user = toSignal(this.userSvc.user$);
}

The share() Cold-Restart Gotcha

Problem — everyone unsubscribes, then someone resubscribes

const data$ = this.http.get('/api/data').pipe(
  share()
);

// Route A loads — subscribes
const subA = data$.subscribe(d => useIt(d));
// Route A destroys — unsubscribes
subA.unsubscribe();
// ref count hits 0 → source is torn down

// Route B loads — subscribes to "same" observable
// But source restarted → NEW HTTP request ❌
const subB = data$.subscribe(d => useIt(d));

Fix: Use shareReplay(1) for HTTP — it keeps the cached value even after all unsubscribes (when refCount:false, the default).

Solution — shareReplay keeps the cache alive

const data$ = this.http.get('/api/data').pipe(
  shareReplay(1)
  // refCount defaults to FALSE
  // → subscription never tears down
  // → cache persists for the lifetime of the service
);

// Route A → subscribes, gets data, unsubscribes
// Route B → subscribes, gets CACHED data instantly ✓
// No new HTTP request fired

// If you DO want teardown (e.g., short-lived data):
shareReplay({ bufferSize: 1, refCount: true })
Non-auth HTTP data (config, constants)
shareReplay(1) — live forever, fine
Auth-sensitive user data
shareReplay({bufferSize:1, refCount:true}) — teardown on logout
Live event streams (websocket, SSE)
share() — auto-connects/disconnects with subscribers
