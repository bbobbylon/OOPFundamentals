Python: Context Managers

The with statement and the __enter__/__exit__ protocol, the @contextmanager generator shortcut, the contextlib toolbox, and async with — guaranteed, deterministic cleanup.

🚪 Why with f as open(...) is more than syntax sugar

A context manager pairs setup with teardown so a resource is released no matter how the block exits — including on an exception. with drives a two-method protocol: __enter__ runs on entry (its return value binds to as), and __exit__ runs on exit always. So with open(path) as f: beats a bare open — deterministic close, no try/finally to remember. The Pythonic way to write one is @contextlib.contextmanager on a generator (setup before yield, teardown after, in try/finally), and async with drives the async variant for DB sessions and HTTP clients.

  • Setup/teardown guaranteed — __exit__ runs on normal exit, return, or exception.
  • with replaces try/finally — deterministic resource lifetime.
  • @contextmanager = a generator — yield once, teardown in finally.
  • async with for async resources — DB sessions, HTTP clients.

with vs try/finally

# verbose, easy to forget: f = open(path) try: data = f.read() finally: f.close() # context manager — close is guaranteed: with open(path) as f: data = f.read() # f.close() runs on exit, even on error

@contextmanager generator

from contextlib import contextmanager @contextmanager def timer(label): start = time.perf_counter() # enter try: yield # body runs here finally: dur = time.perf_counter() - start print(f"{label}: {dur:.3f}s") # exit with timer("query"): run_query()

vs Java try-with-resources

Java: try (var f = new FileReader(p)) { ... } auto-closes anything implementing AutoCloseable (close()). Python: with drives __enter__/__exit__ — same guarantee, but __exit__ also sees the exception and can suppress it, and @contextmanager lets you write one as a generator. Python's protocol is a bit more powerful (the manager can react to how the block ended).

CIAM context: Context managers release exactly what a request acquires — a DB transaction (with conn.begin(): commits or rolls back), a distributed lock, a tracing span. Write an @contextmanager for a temporary elevated-auth scope that always reverts in the finally so privilege can't leak. In async handlers, async with httpx.AsyncClient() as c: and async with session.begin(): close/commit deterministically.

Or: the context manager that works perfectly the first time you use it, and only the first time.

The problem

You built a transaction context manager with @contextmanager, it passed code review, it passed its first test — and the second with block using the exact same object blows up with a RuntimeError that mentions a generator.

Reuse the instance, break the second call

You write the transaction helper correctly — try/finally around the yield and everything: @contextmanager def transaction(conn): tx = conn.begin(); try: yield tx; tx.commit(); except Exception: tx.rollback(); raise. Then, because building it once seems efficient, you save the result and reuse it: tx_cm = transaction(conn) at module scope, then with tx_cm: do_work_a() in one function and with tx_cm: do_work_b() in another.

The first with tx_cm works fine. The second raises RuntimeError: generator didn't yield. @contextmanager wraps a generator — calling transaction(conn) creates the generator object, and a generator can only run through its body once. The first with block drives it from start to (just past) yield and it's now exhausted. Calling __enter__ a second time on that same exhausted generator has nowhere left to go.

try/finally around yield ✓ correct commit/rollback logic ✓ reusing the SAME cm instance ⚠

A class-based context manager can often be reused across with blocks. A generator-based one, from @contextmanager, almost never can.

Call the factory function again for every with
Never store the RESULT of calling a @contextmanager function — store the function itself ↓ transaction the function is reusable forever; transaction(conn) the generator is not Call it fresh at each with site: with transaction(conn): do_work_a() ... with transaction(conn): do_work_b() ↓ each call produces a brand-new generator, so each with block gets one full, unused run through __enter__/__exit__ If you truly need one object reusable across many with blocks, write a class with __enter__/__exit__ that resets its own state each time ↓ a class instance's methods can run any number of times; a generator's body cannot
The one-sentence rule. A @contextmanager-decorated function must be called again for every with block — the object it returns is a one-shot generator, not a reusable context manager, no matter how correct the commit/rollback logic inside it looks.
Think of @contextmanager like a firework, not a lightbulb. A lightbulb (a class-based context manager, written carefully) can be switched on and off repeatedly. A firework goes off once — light the SAME one twice and nothing happens the second time except a loud complaint, because there's no fuse left to relight.
You

The commit/rollback logic is identical to what worked a minute ago. Why does the second with block fail?

The generator object, personified

Because I'm not the function — I'm one specific RUN of it. You already drove me from my first line to my yield and back. I have no more code left to execute; there's nothing after "resume" to give you.

You

But I only wrote transaction(conn) once — I thought that was the reusable part.

The transaction function

I'M the reusable part — call me again and I'll happily hand you a brand-new generator every time. What you saved in tx_cm was the ONE-TIME OUTPUT of calling me, not me.

The mechanism

Follow tx_cm from creation through its second, doomed with.

  1. tx_cm = transaction(conn) creates ONE generator object, saved in a variablecreated once
  2. First with tx_cm: calls tx_cm.__enter__(), which does next(gen), running up to yield txenter #1
  3. Block body runs; exiting the with calls __exit__, which resumes the generator past yield to tx.commit()exit #1 — generator returns
  4. The generator has now run off the end of its function body — it's exhausted, permanentlyexhausted
  5. Second with tx_cm: calls __enter__() again → next(gen) on an already-finished generatorenter #2
  6. next() on an exhausted generator has nothing to run; contextlib surfaces this as RuntimeError: generator didn't yieldRuntimeError

Step 4 is invisible from the outside — nothing in the code, the variable name, or the successful first with block tells you the object is now dead weight. A class instance would just sit there, ready to be entered again; a generator quietly becomes unusable the moment it finishes running, and Python won't warn you until the next attempt.

The with statement's protocol is identical either way — call __enter__, run the body, call __exit__ — but what sits behind that protocol determines whether a second call succeeds. A generator-backed context manager can only ever answer "yes" to that question once.

A teammate refactors a database helper to db_lock = file_lock("db.lock") at module import time (where file_lock is decorated with @contextmanager), so every function can just do with db_lock: ... without re-creating it. The app works in dev (one request at a time) and breaks in production on the second concurrent request. Why?

OS-level file lock semantics aren't the issue here — the code never even gets that far a second time, because the Python-level generator wrapping it is already exhausted before a second lock attempt happens.

Right — file_lock("db.lock") was called exactly once, at import time, producing one generator. The first request's with db_lock drives it to completion; every subsequent request's with db_lock tries to re-enter an already-finished generator and gets RuntimeError: generator didn't yield.

Module-level variables imported correctly are visible everywhere that imports the module — that's not the failure here. The failure is what kind of object db_lock is, not whether other files can see it.

Where you have seen this before

"Works once, silently dead after that" is a whole category of Python — and software — bugs.

Python: reusing an exhausted iterator

it = iter(some_list); list(it); list(it) — the second list(it) returns [], not the same items again, because an iterator (which a generator also is) tracks its own position and can't rewind. The generator-based context manager is this same "already consumed, nothing left" behaviour wearing a with-statement costume.

an iterator/generator remembers where it stopped — permanently

Java: reading an InputStream twice

An InputStream (from an HTTP response body, a socket, a file) can typically be read start-to-finish exactly once — call .read() again after reaching EOF and you get -1 or nothing, not the data replayed. Wrapping it in a "reusable" helper doesn't change that the underlying stream is a one-pass resource, same as the generator underneath @contextmanager.

a stream position, once past the end, doesn't reset itself

JavaScript: awaiting a Promise that's already settled twice, expecting it to re-run

A Promise executes its work once, the moment it's created, and every subsequent .then() just replays the already-computed result — it never re-runs the underlying async function. Someone expecting "calling .then() again reruns the fetch" is making the exact same "one object, one run" mistake as reusing a context-manager generator.

the work already happened; you're just re-reading its outcome
The whole page on a napkin: with guarantees __enter__/__exit__ run in pairs on every exit path, __exit__ sees the exception (and a truthy return swallows it), and @contextmanager turns a try/finally-wrapped generator into that same protocol with far less boilerplate. The one new sentence this block adds: the generator @contextmanager hands you is single-use — save the CALL, not the result, or the second with block gets a RuntimeError instead of your teardown logic.

1. The with Statement & __enter__/__exit__

class Resource:
  def __enter__(self):
    print("acquire")
    return self # bound to `as`
  def __exit__(self, et, ev, tb):
    print("release") # always runs

with Resource() as r:
  use(r)
# acquire → use → release

with calls __enter__ (binding its return to the as name), runs the body, then calls __exit__ on the way out — guaranteed. The guarantee holds for every exit path: the body completing, a return/break, or an exception propagating. That determinism is why files, locks, DB sessions, and sockets all ship as context managers — you can't forget to release them.

__enter__ often returns self, but not always. open() returns the file object; a DB engine's connect() returns a connection. Whatever __enter__ returns is what as binds — so a context manager can hand you a different object than the manager itself.

2. __exit__ Sees the Exception

def __exit__(self, exc_type, exc, tb):
  self.cleanup()
  if exc_type is KeyError:
    return True # SUPPRESS the exception
  # return None/False ⇒ exception propagates

When the block raises, __exit__ receives (exc_type, exc, tb) — otherwise all three are None. Returning a truthy value swallows the exception (the with block then completes normally); returning None/falsy lets it propagate after cleanup. Suppressing is the exception, not the rule — the common case is "clean up, then let the error fly." Reserve suppression for cases like contextlib.suppress(FileNotFoundError).

Don't accidentally swallow errors. A bare return True (or returning a value you didn't intend as a flag) hides every exception raised in the block — a brutal debugging trap. If you don't mean to suppress, return nothing.

3. @contextmanager — Write One as a Generator

from contextlib import contextmanager

@contextmanager
def transaction(conn):
  tx = conn.begin() # __enter__
  try:
    yield tx # value for `as`; body runs
    tx.commit()
  except Exception:
    tx.rollback(); raise

with transaction(conn) as tx: ...

Decorating a generator with @contextmanager turns "code before yield" into __enter__ and "code after yield" into __exit__ — far less boilerplate than a class. Wrap the yield in try/finally (or try/except) so teardown runs even when the body raises; an exception in the block is re-raised at the yield line, which is why commit-on-success / rollback-on-error reads so naturally.

Without try/finally, your teardown is not guaranteed. If the body raises and your generator has plain "setup; yield; teardown", the exception skips the teardown. The finally (or an except ...: raise) is what makes @contextmanager as safe as a hand-written __exit__.
