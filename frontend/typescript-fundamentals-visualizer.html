Why TypeScript

TypeScript is JavaScript with a structural type system that runs at compile-time only. Strip the types out and you have plain JS. The runtime has zero awareness — every check happens before the code runs.

Plain JS — bugs found at runtime

function format(user) {
  return user.name.toUpperCase();
}

format(null);  // TypeError at runtime
format({ nme: 'Bob' });  // silently breaks (typo)
format(42);  // TypeError at runtime

TypeScript — bugs found at compile-time

function format(user: { name: string }) {
  return user.name.toUpperCase();
}

format(null);  // Error: Argument of type 'null' not assignable
format({ nme: 'Bob' });  // Error: 'nme' does not exist on type
format(42);  // Error: not assignable to '{ name: string }'
Structural typing: two types are compatible if their shapes match — no need to inherit or implement. { name: string } matches anything that has a string name, regardless of class hierarchy.

Primitives & literal types

let x: string  = 'hello';
let n: number  = 42;            // no int/float distinction
let b: boolean = true;
let u: undefined = undefined;
let nul: null   = null;
let big: bigint = 9007199254740992n;
let sym: symbol = Symbol('id');

Literal types — the value is the type

// A type whose only valid value is the literal "red"
type Red = 'red';
const c: Red = 'red';   // ok
const d: Red = 'blue';  // Type '"blue"' is not assignable to type '"red"'

// Most useful as a union — a finite set of allowed values
type HttpMethod = 'GET' | 'POST' | 'PUT' | 'DELETE';
type Status = 200 | 404 | 500;
type Direction = 'up' | 'down' | 'left' | 'right';

Widening & const

let   a = 'hello';   // inferred: string  (widens)
const b = 'hello';   // inferred: 'hello' (literal — doesn't widen)

const cfg = { method: 'GET' };
// cfg.method is inferred as `string`, not 'GET'

const cfg2 = { method: 'GET' } as const;
// cfg2.method is inferred as 'GET' — `as const` freezes the whole object literally

Arrays & tuples

// Two equivalent syntaxes for arrays
let a: number[]       = [1, 2, 3];
let b: Array<number> = [1, 2, 3];

// readonly — prevents push/pop/splice/etc.
let r: readonly number[] = [1, 2, 3];
r.push(4);  // Property 'push' does not exist on type 'readonly number[]'

// Tuples — fixed-length, position-typed
let point: [number, number] = [10, 20];
let named: [x: number, y: number] = [10, 20];   // labeled tuples
let res:   [string, number, boolean?] = ['ok', 200];  // optional element
let rest:  [string, ...number[]] = ['header', 1, 2, 3];

Object shapes

// Inline shape
function greet(u: { name: string; age: number }) { ... }

// Optional property — ?:
type User = {
  name: string;
  age?: number;          // can be missing
  readonly id: string;     // can't be reassigned
};

// Index signature — "any string key maps to..."
type Dict = {
  [key: string]: number;
};
const d: Dict = { a: 1, b: 2 };

// Record<K, V> — the type-safe dictionary, prefer this
const scores: Record<string, number> = { alice: 10, bob: 20 };
const flags:  Record<'dark' | 'beta', boolean> = { dark: true, beta: false };

Unions & intersections

Union — "this OR that"

type Id = string | number;
function print(id: Id) {
  // id.toUpperCase() — might be a number, no .toUpperCase
  if (typeof id === 'string') {
    // here id is narrowed to string — full string API available
    id.toUpperCase();
  }
}

Intersection — "this AND that"

type Named    = { name: string };
type Aged     = { age:  number };
type Person   = Named & Aged;

const p: Person = { name: 'Bobby', age: 30 };   // must satisfy both
Counterintuitive: the intersection of two object types is the type with BOTH sets of properties (more demanding), not fewer. Think: a Person is everything a Named is AND everything an Aged is.

Enums (and what to use instead)

// Numeric enum — values default to 0, 1, 2, ...
enum Direction { Up, Down, Left, Right }
const d = Direction.Up;   // value: 0

// String enum — explicit string values
enum Role {
  Admin = 'admin',
  User  = 'user',
}
Most teams avoid enums today. Reasons: they generate runtime code (a small JS object emitted), don't play well with tree-shaking, and have surprising assignability rules. Prefer the literal-union pattern:
type Role = 'admin' | 'user';     // pure type, zero runtime cost
const ROLES = ['admin', 'user'] as const;
type Role2 = typeof ROLES[number];   // 'admin' | 'user' — derived from the array

Functions

// Explicit param + return types
function add(a: number, b: number): number { return a + b; }

// Inferred return type (preferred — let TS figure it out)
function double(x: number) { return x * 2; }   // : number inferred

// Optional, default, and rest params
function greet(name: string, greeting = 'hi', title?: string) { ... }
function log(...parts: string[]) { ... }

// Arrow function as a type — useful for callbacks
type Handler = (event: MouseEvent) => void;
const onClick: Handler = (e) => console.log(e.target);

// Function overloads — multiple signatures, one implementation
function parse(x: string): Date;
function parse(x: number): Date;
function parse(x: string | number): Date {
  return new Date(x);
}

void vs undefined

type Foo = () => void;
// `void` as a return type means "I don't care what's returned — ignore it"
const arr: Foo[] = [];
arr.push(() => 42);   // OK — the 42 is just discarded

type Bar = () => undefined;
// `undefined` as return type means "you MUST return undefined"

type vs interface

Both name a shape. 95% of the time, either works. The differences matter for advanced cases.

interfacetype
Names a shape✅✅
Extends / implementsinterface A extends B {}type A = B & {...}
Declaration merging (same name redefines/merges)✅❌ (duplicate identifier error)
Union types❌✅ type X = A | B
Mapped types❌✅ type X = { [K in keyof T]: ... }
Conditional types❌✅ type X = T extends U ? A : B
Template literals / utility types❌✅
Tuples❌✅

The practical rule

Am I describing an object shape (or class shape)? → Yes → interface (cleaner, can be augmented later, better error messages) Am I building a union, mapped type, conditional type, or anything algebraic? → Yes → type Am I picking between them with no other constraints? → Default → type for short aliases, interface for big shapes (especially public APIs)

TypeScript watches your control flow. Inside an if branch, it narrows types automatically based on the check you wrote. These are the major narrowing patterns:

function describe(x: string | number | Date) {
  if (typeof x === 'string') {
    return x.toUpperCase();         // x: string
  }
  if (x instanceof Date) {
    return x.toISOString();         // x: Date
  }
  return x.toFixed(2);                // x: number (only thing left)
}

User-defined type guards

When TypeScript can't narrow on its own (custom shapes, runtime checks against object structure), write your own type guard. A function whose return type is x is T.

type Cat = { type: 'cat'; meow(): void };
type Dog = { type: 'dog'; bark(): void };

// The magic is the return type: `pet is Cat`
function isCat(pet: Cat | Dog): pet is Cat {
  return pet.type === 'cat';
}

function speak(pet: Cat | Dog) {
  if (isCat(pet)) {
    pet.meow();    // narrowed to Cat
  } else {
    pet.bark();    // narrowed to Dog
  }
}

Assertion functions — the asserts keyword

// Assertions throw if the check fails — and narrow if it doesn't
function assertString(v: unknown): asserts v is string {
  if (typeof v !== 'string') throw new Error('not a string');
}

function use(x: unknown) {
  assertString(x);
  x.toUpperCase();   // narrowed to string after the assert
}

Discriminated unions — the killer pattern

When you have a union of similar object shapes, add a common literal field that distinguishes them. TypeScript narrows on it automatically.

// Shape with a 'kind' discriminator
type Shape =
  | { kind: 'circle';    radius: number }
  | { kind: 'square';    side:   number }
  | { kind: 'rect';      width:  number; height: number };

function area(s: Shape): number {
  switch (s.kind) {
    case 'circle': return Math.PI * s.radius ** 2;       // s: Circle
    case 'square': return s.side ** 2;                  // s: Square
    case 'rect':   return s.width * s.height;             // s: Rect
  }
}

A signature like type Result<T> = { ok: true; value: T } | { ok: false; error: string } is the standard "Result" pattern — replaces try/catch with type-safe branches.

Exhaustiveness checking — the never trick

When you switch on a discriminated union, you want a compile error if you ever add a new case and forget to handle it. The never type makes this work.

function area(s: Shape): number {
  switch (s.kind) {
    case 'circle': return Math.PI * s.radius ** 2;
    case 'square': return s.side ** 2;
    case 'rect':   return s.width * s.height;
    default: {
      const _exhaustive: never = s;
      throw new Error(`Unhandled shape: ${(s as any).kind}`);
    }
  }
}

// Now if someone adds { kind: 'triangle', ... } to Shape and forgets a case:
// Type 'Triangle' is not assignable to type 'never'.
This is the most valuable TS pattern. Adding a new variant to a union becomes a compiler-driven refactor — TS lists every switch that needs updating.

Generics — types that take type parameters

A generic is a function or type that takes a type parameter, like Array<T>, Promise<T>, Map<K, V>. It lets you write code that works for any type without losing type safety.

The classic motivator

// ❌ Loses type info — return type is `any`
function firstAny(arr: any[]): any {
  return arr[0];
}
const x = firstAny([1, 2, 3]);   // x: any — no autocomplete, no safety

// ✅ Generic — return type is whatever T is
function first<T>(arr: T[]): T | undefined {
  return arr[0];
}
const y = first([1, 2, 3]);      // y: number | undefined
const z = first(['a', 'b']);     // z: string | undefined

Multiple type parameters

function pair<A, B>(a: A, b: B): [A, B] {
  return [a, b];
}
const p = pair('hello', 42);   // p: [string, number]

Generic type alias

type Box<T> = { value: T };
type Result<T, E = Error> =
  | { ok: true;  value: T }
  | { ok: false; error: E };

const success: Result<number> = { ok: true, value: 42 };

Generic constraints & defaults

Constraint — "T must extend this shape"

// Without a constraint, .length is an error — T might not have it
function longest<T extends { length: number }>(a: T, b: T): T {
  return a.length >= b.length ? a : b;
}

longest([1, 2], [3, 4, 5]);   // OK — arrays have length
longest(10, 20);                  // Error — numbers have no .length

Default — "fall back to this if not specified"

type ApiResponse<T = unknown> = {
  status: number;
  data:   T;
};

const r1: ApiResponse          = { status: 200, data: '?' };  // T = unknown
const r2: ApiResponse<User>    = { status: 200, data: { name: 'B' } };

keyof as a constraint — type-safe property accessor

function get<T, K extends keyof T>(obj: T, key: K): T[K] {
  return obj[key];
}

const u = { name: 'B', age: 30 };
get(u, 'name');   // type: string
get(u, 'age');    // type: number
get(u, 'nope');   // Argument of type '"nope"' is not assignable to keyof T

Generic functions in practice

// Generic Promise wrapper — preserves the inner type
async function fetchJson<T>(url: string): Promise<T> {
  const r = await fetch(url);
  return r.json() as T;
}
const user = await fetchJson<User>('/api/me');   // user: User

// Generic map — preserves the value type
function mapValues<T, U>(
  obj: Record<string, T>,
  fn:  (v: T) => U
): Record<string, U> {
  return Object.fromEntries(
    Object.entries(obj).map(([k, v]) => [k, fn(v)])
  );
}

// Generic class — a typed event emitter
class EventBus<Events extends Record<string, any>> {
  private listeners = {} as {
    [K in keyof Events]?: ((p: Events[K]) => void)[]
  };

  on<K extends keyof Events>(k: K, fn: (p: Events[K]) => void) {
    (this.listeners[k] ??= []).push(fn);
  }
  emit<K extends keyof Events>(k: K, payload: Events[K]) {
    this.listeners[k]?.forEach(fn => fn(payload));
  }
}

const bus = new EventBus<{ login: User; logout: void }>();
bus.on('login', u => console.log(u.name));   // u: User
bus.emit('login', { name: 'B' });               // payload is checked
bus.emit('login', 42);                         // Error

infer & conditional types

A conditional type picks one of two branches based on a type relationship: T extends U ? A : B. infer lets you extract a piece of a type from inside such a check.

// Pick a branch based on a type relationship
type IsString<T> = T extends string ? true : false;
type A = IsString<'hi'>;   // true
type B = IsString<42>;     // false

// Extract the resolved type of a Promise — infer the inner type
type Awaited<T> = T extends Promise<infer U> ? U : T;
type C = Awaited<Promise<string>>;   // string

// Extract the return type of a function
type MyReturnType<F> = F extends (...a: any[]) => infer R ? R : never;
type D = MyReturnType<() => number>;   // number

// Extract the parameter types
type MyParams<F> = F extends (...a: infer P) => any ? P : never;
type E = MyParams<(a: string, b: number) => void>;   // [string, number]

TypeScript's standard library already has ReturnType<F>, Parameters<F>, Awaited<T> as built-ins. They use exactly this infer pattern internally.

// Real-world combo example
type User = { id: string; name: string; email: string; password: string; };

// What an API returns (no password)
type SafeUser = Omit<User, 'password'>;

// What a PATCH request body looks like (everything optional except id)
type UserPatch = Partial<SafeUser> & { id: string };

// A read-only display version
type UserView = Readonly<SafeUser>;

Mapped types — transform every property

// "For each key K in T, give me { K: ... }"
type MyPartial<T> = {
  [K in keyof T]?: T[K];
};

// Add / remove modifiers with + and -
type Mutable<T> = {
  -readonly [K in keyof T]: T[K];      // strip readonly
};
type MyRequired<T> = {
  [K in keyof T]-?: T[K];            // strip optional
};

// Key remapping with `as` — rename keys, even filter them out
type Getters<T> = {
  [K in keyof T as `get${Capitalize<K & string>}`]: () => T[K];
};

type User = { name: string; age: number };
type UserGetters = Getters<User>;
// = { getName(): string; getAge(): number }

Template literal types — string types as code

// Compose new string types from others
type Color = 'red' | 'blue';
type Shade = 'light' | 'dark';
type CompoundColor = `${Shade}-${Color}`;
// = 'light-red' | 'light-blue' | 'dark-red' | 'dark-blue'

// Pattern matching on strings
type EventName<T extends string> = `on${Capitalize<T>}`;
type Hooks = EventName<'click' | 'hover'>;   // 'onClick' | 'onHover'

// Parse the structure of a string
type Split<S extends string, D extends string> =
  S extends `${infer H}${D}${infer T}`
    ? [H, ...Split<T, D>]
    : [S];
type Parts = Split<'a/b/c', '/'>;   // ['a', 'b', 'c']

Template literal types power library APIs like CSS-in-JS object keys, GraphQL query typings, and route-parameter extraction in frameworks like Hono.

keyof / typeof / indexed access

// keyof — union of an object type's keys
type User = { name: string; age: number };
type UserKey = keyof User;   // 'name' | 'age'

// typeof (at type level) — get the type of a value
const config = { theme: 'dark', version: 3 } as const;
type Config = typeof config;
// { readonly theme: 'dark'; readonly version: 3 }

// Indexed access — lookup a property's type
type UserName = User['name'];          // string
type UserValue = User[keyof User];   // string | number

// Combined — get array element type
const colors = ['red', 'blue', 'green'] as const;
type Color = typeof colors[number];   // 'red' | 'blue' | 'green'

Type assertions & satisfies

Type assertion — as

// "Trust me, I know better than the inference"
const el = document.getElementById('x') as HTMLInputElement;
const id = x as unknown as UserId;   // double-assert when types don't overlap
Use sparingly. Type assertions silence the compiler — if you're wrong, you get the same runtime bug TS was supposed to prevent. Prefer narrowing (type guards, control flow) where possible.

satisfies — validate without widening

// Without satisfies — `palette.red` is typed as `string`, info lost
const palette: Record<string, string> = {
  red:   '#ff0000',
  green: [0, 255, 0],   // Error — not assignable to string
};

// With satisfies — check the shape AND keep the precise inferred types
const palette2 = {
  red:   '#ff0000',
  green: [0, 255, 0],
} satisfies Record<string, string | number[]>;

palette2.red.toUpperCase();    // OK — red is precisely string
palette2.green.map(n => n + 1);   // OK — green is precisely number[]
satisfies = "type-check this against X, but keep its precise inferred type." Use it for config objects, route maps, theme palettes — anything where you want validation AND autocomplete on specific keys.

unknown vs any vs never

// any — opt out of type checking. Avoid.
let a: any = JSON.parse(input);
a.anyMethodAtAll();   // no error at compile time, blows up at runtime

// unknown — safe alternative. Forces you to narrow.
let u: unknown = JSON.parse(input);
u.anything();                 // Object is of type 'unknown'
if (typeof u === 'string') {
  u.toUpperCase();          // OK — narrowed
}

// never — the empty set. Used in exhaustive checks and in unreachable code.
function throwIt(m: string): never { throw new Error(m); }

Modules & ESM

// Named exports
export const PI = 3.14;
export function add(a: number, b: number) { ... }
export type User = { ... };

// Default export
export default function main() { ... }

// Import
import { PI, add, type User } from './math';
import main           from './main';
import * as M       from './math';

// Type-only imports (don't generate runtime code)
import type { User } from './types';
import { type User, parseUser } from './user';

// Re-export
export { add, PI } from './math';
export * from './math';

Why import type: ensures the import is erased at compile time. Critical when the module has side effects you don't want to trigger, or when you're worried about bundle size.

Declaration files (.d.ts)

A .d.ts file declares types without implementing them. They tell TypeScript about JS code (your own or third-party).

// types.d.ts — typing a JS module
declare module 'legacy-lib' {
  export function parse(x: string): object;
}

// Augmenting globals
declare global {
  interface Window {
    myCustomProp?: string;
  }
}

// Module augmentation (extend a 3rd-party module's types)
declare module 'express' {
  interface Request {
    user?: User;
  }
}

@types/* packages from DefinitelyTyped are bundles of .d.ts files for popular JS libraries.

Mental model — final word

Types are a compile-time language

Run TS through the compiler → JS comes out, types are gone. The whole type system exists to make the build fail before you ship a bug.

Structural, not nominal

Two types match if their shapes match. No need to inherit/implement. Different classes with the same fields are compatible.

Narrow, don't assert

Use typeof/instanceof/discriminators/guards. Reach for as only when you genuinely know better than TS.

Derive, don't duplicate

typeof + as const + utility types let you build a type from a value. Single source of truth, no drift.

Strict pays off

Every check strict: true adds catches a class of real bugs. Use it. Add noUncheckedIndexedAccess for the next level.

The type system is Turing-complete

You can compute almost anything at the type level. Use this power for library APIs; resist it in everyday code (slow builds, unreadable types).

🌱 Brand-new? TypeScript is JavaScript with a spell-checker for data.

Plain JavaScript lets you do "5" * user.naem and only blows up when it runs (and naem is silently undefined). TypeScript lets you write down what a value is — name: string, age: number — and then checks every use against that as you type, catching the typo and the wrong-type bug before you ever run the code. The magic part for beginners: those types are erased when it compiles to JavaScript, so there's zero runtime cost — they exist purely to help you and your editor (autocomplete, safe rename, inline errors). And you don't annotate everything: TypeScript infers most types for you. Try it live in the TypeScript Playground.

🧠 Expert corner — structural, inferred, and erased

  • Typing is structural, not nominal. Two types are compatible if their shapes match — names don't matter. An object with the right properties satisfies an interface without ever declaring it implements it (see Structural Typing).
  • Inference does the heavy lifting. let x = 3 is number; const s = "hi" is the literal "hi". as const freezes a whole object into deeply-readonly literal types — great for config and discriminated unions.
  • Types are erased — never trust them at runtime. There's no reflection on a TS type after compile. To branch on a value's shape at runtime you need real JS checks (typeof, in, a user-defined type guard) — that's narrowing.
  • Turn on strict and prefer unknown to any. strictNullChecks alone eliminates a huge class of "cannot read property of undefined" bugs; any disables the checker for that value, while unknown forces you to narrow before use.
  • The compiler is just a checker + transpiler. It reports type errors and emits plain JS — it does not change runtime behavior (a type error still emits by default). Third-party JS gets typed via .d.ts declaration files.
  • CIAM tie-in. Type your API DTOs and, ideally, generate them from Spring's OpenAPI spec so the frontend and backend contract can't silently drift — see OpenAPI → Typed Client.
