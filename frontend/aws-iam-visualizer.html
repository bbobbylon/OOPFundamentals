IAM — Identity & Access Management

IAM controls who can do what in your AWS account. Every API call is checked against IAM policies. Getting this right is the foundation of AWS security.

1 — Core IAM Concepts

Root Account

God mode — use sparingly
The email you used to create the AWS account. Has unlimited power and cannot be restricted.

Best practice: enable MFA, create an admin IAM user for daily use, never use root for day-to-day work. Store root credentials securely.

IAM User

A person or service with permanent credentials
Has an Access Key ID + Secret Access Key for programmatic access, or username/password for console access.

Use for humans (developers, admins) and legacy service accounts. For modern applications, prefer IAM Roles over long-lived user credentials.

IAM Group

Attach policies to multiple users at once
Groups make permission management scalable. Create groups: Developers, DBAdmins, ReadOnly. Attach policies to the group. Add users to groups.

Users inherit all permissions from their groups. A user can belong to multiple groups.

IAM Role

Temporary credentials — no long-lived secrets
A Role is assumed by an entity (EC2 instance, Lambda, ECS task, another AWS account). Provides temporary credentials that rotate automatically.

EC2 Instance Profile: attach a role to an EC2 instance so your Spring Boot app can call S3, RDS, etc. without hard-coding credentials. This is the AWS best practice.

IAM Policy

JSON document defining permissions
A JSON document with Statements that allow or deny specific Actions on Resources.

AWS Managed: pre-built by AWS (e.g., AmazonS3ReadOnlyAccess)
Customer Managed: you create and maintain them
Inline: embedded directly in a user/group/role (avoid — hard to manage)

Policies are attached to identities (users, groups, roles).

Trust Policy

Who can assume this role
Every Role has a Trust Policy (who can assume it) and Permission Policies (what they can do once assumed).

Example Trust Policy: "EC2 service can assume this role." This is what makes Instance Profiles work — EC2 is trusted to assume the role and provide temporary credentials to the instance.

2 — IAM Policy Anatomy

{ "Version": "2012-10-17", // always this value — required "Statement": [ { "Sid": "AllowS3ReadOnBucket", // optional statement ID "Effect": "Allow", // "Allow" or "Deny" "Action": [ "s3:GetObject", // specific actions (service:Operation) "s3:ListBucket" ], "Resource": [ "arn:aws:s3:::my-company-assets", // the bucket itself "arn:aws:s3:::my-company-assets/*" // all objects in bucket ], "Condition": { // optional extra conditions "StringEquals": { "s3:prefix": ["uploads/", "public/"] } } } ] }

ARN format: arn:partition:service:region:account-id:resource-type/resource-id
Use * as wildcard in Action (s3:*) or Resource. Never use Action: "*" and Resource: "*" together — that's full admin access.

3 — Policy Evaluation Logic

When an API call is made, IAM evaluates all applicable policies in this order:

1. Explicit Deny — any policy denies this action?
→ DENY (final, no override)
2. Service Control Policy (Org SCPs) — if using AWS Organizations
→ DENY if not allowed
3. Resource-based Policy — bucket policy, KMS key policy grants access?
→ ALLOW if yes
4. Identity-based Policy — attached user/role policy allows?
→ ALLOW if yes
5. Implicit Deny — no explicit allow found
→ DENY (default)

Key rule: Default is DENY. You must explicitly Allow. An Explicit Deny always wins over any Allow.

4 — Spring Boot with IAM Roles (Instance Profile)

❌ Hard-coded credentials (never do this)

cloud: aws: credentials: access-key: AKIA... secret-key: abc123 # Credentials in code / config files # = security incident waiting to happen

✓ IAM Role via Instance Profile

# No credentials in code at all! # Attach IAM Role to EC2/ECS task: cloud: aws: region: static: us-east-1 # AWS SDK auto-discovers credentials # from instance metadata endpoint

The AWS SDK for Java uses a Credential Provider Chain — checks environment variables → system properties → instance metadata → ECS task role → in order. On EC2 and ECS, the instance/task role credentials are automatically available with no configuration.

5 — IAM Security Best Practices

PracticeWhy
Enable MFA on root accountRoot has unlimited power — a compromised root account is catastrophic
Least privilegeGive only the permissions needed. Start with deny-all, add only what's required.
Use IAM Roles for applicationsTemporary credentials rotate automatically — no secrets to rotate or leak
Never share access keysCreate individual IAM users. Shared keys make auditing impossible.
Rotate access keys regularlyFor any long-lived key that must exist, rotate every 90 days
Use IAM Access AnalyzerDetects overly permissive policies and public resource exposure
Enable CloudTrailEvery IAM API call is logged — essential for security investigations
Tag IAM resourcesEnvironment, owner, project tags make cost allocation and audits manageable
