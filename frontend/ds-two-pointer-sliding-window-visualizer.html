Two Pointers & Sliding Window

Two related tricks for scanning an array or string in one pass instead of nested loops — turning an O(n²) brute force into O(n) by moving indices smartly instead of re-checking every pair.

👉👈 Why do these two patterns keep showing up in the same breath?

Both patterns replace a nested loop with a small number of indices that move through the data exactly once, and both rely on the same underlying trick: throwing away information you can prove you'll never need again. Two pointers usually means two indices moving toward each other from opposite ends of a sorted array — sortedness is what makes convergence valid, because it guarantees that moving the left pointer only ever increases the sum you're tracking, and moving the right pointer only ever decreases it, so you can reason about which one to move without checking every combination. Sliding window means two indices moving in the same direction — a left and right boundary around a contiguous run of an array or string — where the right pointer expands the window to include new elements and the left pointer contracts it to drop elements once some condition is violated (a fixed size is exceeded, or a character starts repeating). Both patterns get their O(n) speed from the same guarantee: every index is added to the window and removed from it at most once across the whole scan, so the total work is linear even though it "looks like" two nested loops (an outer expand and an inner shrink).

  • Opposite-direction (converging) — left starts at 0, right starts at n-1, they move toward each other; requires sorted input; classic uses: Two Sum, 3Sum, Container With Most Water.
  • Same-direction, fixed window — a window of constant size k slides one element at a time; each slide does O(1) work (drop the outgoing element, add the incoming one) instead of re-summing the whole window.
  • Same-direction, variable window — the window grows by expanding the right edge and shrinks by advancing the left edge whenever an invariant breaks (too many duplicates, sum too large); the answer is usually the best window size seen during the whole scan.
  • The tell in an interview — "sorted array, find a pair/triple" almost always means converging two-pointer; "longest/shortest contiguous substring or subarray satisfying X" almost always means sliding window.

Why it beats nested loops

A brute-force pair search checks all n² combinations. Two pointers checks each element a constant number of times total — not because it's "smarter" about which pairs to skip, but because sortedness makes an entire class of pairs provably irrelevant the moment you move a pointer.

Sortedness is not optional

Converging two-pointer only works because the array is sorted. Run it on an unsorted array and moving "left" doesn't reliably increase the sum — the whole correctness argument depends on that one precondition.

The window's invariant is the whole trick

Every sliding-window problem reduces to: what condition must the window satisfy, and what's the cheapest way to update that condition when one element enters and one leaves? Get that update O(1) and the whole algorithm is O(n).

Where this shows up in real backend work: a fixed-size sliding window is literally the mechanism behind a fixed-window rate limiter (count requests in the current N-second bucket, slide the bucket forward, evict requests that age out) — the same drop-one/add-one update this page walks through for a max-subarray-sum window is what keeps a rate limiter's per-request check O(1) instead of re-scanning a request log. Keyset (cursor-based) pagination is the same converging-pointer idea turned sideways: instead of two indices scanning one array, you're tracking "how far the client has consumed" as a monotonically advancing boundary through a sorted result set, which is exactly why keyset pagination requires a stable sort order the same way two-pointer requires a sorted array.

The generic sliding-window template

Scenarios ③ and ④ are both instances of the same shape — only the invariant and what triggers a shrink change:

int left = 0; for (int right = 0; right < arr.length; right++) { // 1. expand: fold arr[right] INTO the window's running state addToWindow(arr[right]); // 2. shrink: while the window breaks its invariant, drop from the left while (windowIsInvalid()) { removeFromWindow(arr[left]); left++; } // 3. update the answer using the CURRENT valid window [left, right] answer = combine(answer, right - left + 1); }

A fixed window (scenario ③) never actually needs the while shrink loop — once the window hits size k, every expand is paired with exactly one shrink, so left and right stay exactly k apart. A variable window (scenario ④) is where the shrink loop earns its keep: it can run zero, one, or several times per expand, which is exactly the "duplicate found, shrink until it's gone" behavior in that scenario's walk below.

A few things worth knowing

  • The "why" behind moving the shorter wall (Container With Most Water) — width can only ever shrink as the pointers converge, so the only way area can increase is if the limiting height increases; moving the taller wall can never raise the limiting height (it's still capped by the shorter one), so it's a guaranteed-useless move. Moving the shorter wall is the only move that has any chance of improving on the current best.
  • Amortized O(n), not O(1) per step — the shrink while loop can look like it makes the whole thing O(n²) in the worst case, but because left only ever moves forward and can move at most n times total across the entire scan (never resets backward), the total work across all shrinks is bounded by n — this is the same amortized-analysis argument used for dynamic array resizing.
  • Three pointers, not two — 3Sum is the same converging two-pointer idea with an added outer loop: fix one element, then two-pointer the rest of the (still sorted) array for the remaining pair. It's O(n²) overall (n outer iterations × O(n) inner two-pointer scan), still better than the O(n³) brute force of checking every triple.
