RBAC & Authorization Deep Dive

Role-Based Access Control (RBAC), JWT claim design for roles/permissions, Spring Boot @PreAuthorize with SpEL, Attribute-Based Access Control (ABAC), and multi-tenant RBAC — the complete CIAM authorization picture.

🛡️ What is RBAC — and why does role-based authz live partly in the JWT, partly in the API, partly in the IdP?

Authorization ("can this user do THIS to THAT?") comes after authentication. RBAC assigns users roles (ADMIN/USER/READER) which carry permissions — managed per-role, not per-user. At login, roles are embedded in the JWT (the roles/groups claim) so the API reads them with no DB call; Spring maps scp/roles/groups/tid claims to GrantedAuthority for @PreAuthorize. ABAC extends RBAC with attribute rules (user.dept == doc.dept) — most CIAM apps use RBAC for coarse endpoint access and ABAC for fine-grained row access. Multi-tenant RBAC scopes roles per tenant via tid — always cross-check a resource's tenant against the JWT's tid so a role in tenant A never reaches tenant B's data.

  • AuthZ ≠ AuthN — what you can do vs who you are.
  • RBAC = roles carry permissions — embedded in JWT claims, read without a DB call.
  • Spring maps claims → GrantedAuthority for @PreAuthorize; ABAC for row-level.
  • Multi-tenant: scope by tid — never let tenant A's role touch tenant B.

JWT roles → Spring authorities

// JWT from Ping/Entra might have: // { "sub": "user-123", "roles": ["ADMIN", "USER"], "scp": "read write", "tid": "t-456" } // Spring custom converter maps claims → GrantedAuthority: @Bean JwtAuthenticationConverter jwtAuthenticationConverter() { var c = new JwtAuthenticationConverter(); c.setJwtGrantedAuthoritiesConverter(jwt -> { List<GrantedAuthority> auths = new ArrayList<>(); // Map "scp" → "SCOPE_read", "SCOPE_write": List<String> scopes = jwt.getClaimAsStringList("scp"); if (scopes != null) scopes.stream().map(s -> "SCOPE_"+s) .map(SimpleGrantedAuthority::new).forEach(auths::add); // Map "roles" → "ROLE_ADMIN", "ROLE_USER": List<String> roles = jwt.getClaimAsStringList("roles"); if (roles != null) roles.stream().map(r -> "ROLE_"+r) .map(SimpleGrantedAuthority::new).forEach(auths::add); return auths; }); return c; } // @PreAuthorize("hasRole('ADMIN')") → checks for "ROLE_ADMIN" authority // @PreAuthorize("hasAuthority('SCOPE_write')") → checks for "SCOPE_write"

@PreAuthorize SpEL patterns

// Basic role/scope guards: @PreAuthorize("hasRole('ADMIN')") public void adminAction() {} @PreAuthorize("hasAuthority('SCOPE_users.write')") public void writeUser() {} // Multiple conditions (AND): @PreAuthorize("hasRole('USER') and hasAuthority('SCOPE_profile.read')") public UserProfile getProfile() {} // Access method parameters in SpEL: @PreAuthorize("#userId == authentication.principal.subject or hasRole('ADMIN')") public User getUser(String userId) {} // ^ Only admins can get other users; normal users can only get themselves // @PostAuthorize — check AFTER method runs (filter result): @PostAuthorize("returnObject.tenantId == authentication.principal.getClaim('tid')") public Document getDocument(String docId) {} // ^ Ensures returned document belongs to caller's tenant // @PreFilter / @PostFilter — filter collections: @PostFilter("filterObject.ownerId == authentication.name") public List<Item> getItems() {}

Multi-tenant data isolation

// Critical: ALWAYS enforce tenant isolation at the data layer // Never rely on routing alone — tenants share the DB // Extract tenant from JWT in service methods: @Service public class DocumentService { // Pattern 1: Extract from SecurityContext private String getCurrentTenantId() { var jwt = (Jwt) SecurityContextHolder.getContext() .getAuthentication().getPrincipal(); return jwt.getClaimAsString("tid"); } // Always include tenantId in ALL data queries: public Page<Document> getDocuments(Pageable pageable) { String tenantId = getCurrentTenantId(); return documentRepo.findByTenantId(tenantId, pageable); // If tenantId missing → return empty or throw 403 } public Document getDocument(String docId) { String tenantId = getCurrentTenantId(); return documentRepo.findByIdAndTenantId(docId, tenantId) .orElseThrow(() -> new AccessDeniedException("Not found")); // ↑ Returns 403 even if doc exists — tenant can't know another tenant's IDs } }

In CIAM / Your Job: Ping AM injects group/role memberships into the JWT via token-policy claim transforms; Entra app-role assignments (App Registration → App roles) land in the roles claim. Your Spring APIs read these and enforce with @PreAuthorize. The security rule: never trust client-sent claims — only the IdP-signed JWT. And the Entra tid claim is your multi-tenant isolation key — verify the tenant on every resource access.

The problem

Everything above is about getting roles into the token. Nobody warned you how hard they are to get back out.

The offboarding ticket said "access removed 09:00." The audit log says they deleted a user at 09:47.

An engineer leaves the team. At 09:00 someone removes their ADMIN role in Entra — correctly, immediately, in the right tenant. The directory is now the truth: this person is a plain user. Everyone signs off on the ticket.

But the token in their browser was minted at 08:55, and it says "roles":["ADMIN"]. It is signed by the IdP. Its exp is 09:55. Its tid is right. Your API does exactly what this page taught it to do — reads the claim, maps it to ROLE_ADMIN, hands it to @PreAuthorize — and at 09:47 it allows a delete, because nothing in that request is false. The token is not stale in any sense your verifier can express. It is a correct statement about 08:55.

directory says USER ✓ token says ADMIN ⚠ signature valid ✓ exp 09:55 — not yet ✓ 55 minutes of ghost admin ⚠

The speed that makes JWT authorization worth using — no DB call, no IdP call — is the exact same property that makes revocation slow.

You cannot un-issue a token. You can only shorten the window, or ask again.
Shorten the access token: 60 min → 5-15 min, with silent refresh ↓ the refresh is where the IdP gets to re-check the directory, so the blast radius becomes one token lifetime For genuinely destructive operations, ask the IdP: token introspection, or re-read the role from your own store ↓ you have paid one network call to buy back real-time truth, on the 1% of endpoints that deserve it And keep a deny-list of revoked jti/sub values that the filter checks, for "remove this person NOW"
A role claim is a photograph of your directory at the moment the token was minted — not a live view of it. Every property you like about JWT authorization follows from that sentence: it is fast because the photograph is in your hand, it scales because nobody has to call the IdP, and it is stale because photographs do not update. Revocation is not a feature you forgot to turn on. It is the bill for the speed.
A token is a printed boarding pass, not a live database query. The airline can cancel your seat in their system the instant you shout at the gate agent — and the paper in your pocket still says BOARDING, SEAT 14C, because it was true when it printed. Which is precisely why boarding passes expire in hours, not months.

I removed the role. Why is my API still letting them in?

Entra / Ping

I updated my directory the moment you asked. What I cannot do is reach into tokens I already signed and edit them — they are not stored anywhere I control, they are strings in other people's browsers. All I can promise is that the next token I mint reflects the change. That is what the refresh is for.

The access token

And I am not lying. I never claimed to describe the present. I claimed that at iat, this subject held these roles, and I put an exp on myself specifically so nobody would mistake me for a permanent statement.

Your API

So I have one real decision to make, and it is not technical: how long am I willing to be wrong about someone's role? Answer sixty minutes and I skip every lookup. Answer zero and I call the IdP on every request and give back everything JWTs bought me. Almost every real system answers "a few minutes, except for the endpoints that scare me."

The mechanism

Nothing here malfunctions. That is what makes it hard to spot in review.

Token minted user signs in, IdP reads the directory → roles embedded as a claim, signed, exp set — the photograph is taken
Directory changes a role is added or removed in Entra/Ping → already-issued tokens are not edited — there is nothing signed that can be rewritten
Token expires exp is reached, silent refresh fires → the IdP re-reads the directory and mints a token that finally agrees with it

This loop re-runs on every sign-in, not just the one that goes wrong — most of the time nobody notices because nobody's role changes mid-token. The gap only becomes visible on the one sign-in where step two lands between steps one and three, and the size of that gap is exactly your access-token lifetime. That is the dial you are actually choosing when you pick "60 minutes" as a default.

08:55 — user signs in. The IdP reads the directory, sees ADMIN, and mints a token carrying roles:["ADMIN"], exp 09:55 ↓ 5 minutes later 09:00 — you remove the ADMIN role in the directory. The directory changes. No token anywhere changes, because the IdP does not hold any of them ↓ 47 minutes into a token that is still perfectly valid, a request arrives 09:47 — DELETE /api/users/42 arrives. The resource server verifies the signature against JWKS, offline, exactly as designed — no IdP call is made ↓ the claim-to-authority converter has nothing else to consult 09:47 — roles:["ADMIN"] out of the token becomes ROLE_ADMIN. @PreAuthorize("hasRole('ADMIN')") evaluates true. The delete runs ↓ 8 minutes later, the photograph finally develops 09:55 — the token expires. The silent refresh asks the IdP, which re-reads the directory and mints a token that finally says USER

Read that ladder again looking for the bug. There isn't one — every rung did its job, and the only variable you actually control is the distance between the first rung and the last. That is why "how long is our access token?" is a security question and not a performance one, and why the answer for a CIAM app is usually minutes. It is also why role changes and offboarding are different problems: shrinking the window is enough for "they moved teams", and not enough for "they were dismissed" — that one needs the deny-list, because waiting even five minutes is a policy decision somebody has to sign.

The fan-out is the part people miss in an incident review: there is rarely one token. Every device and every session that authenticated before 09:00 is holding its own independent photograph, each with its own expiry, and none of them are enumerable from the IdP's side. Revoking the refresh token stops new ones being minted — which is the real offboarding lever — but it does nothing to the access tokens already in flight.

You remove a user's ADMIN role in Entra at 09:00. Their SPA is holding an access token issued at 08:55 that contains "roles":["ADMIN"] and expires at 09:55. At 09:15 they call DELETE /api/users/42, guarded by @PreAuthorize("hasRole('ADMIN')") on a standard resource-server setup. What happens?

This is the mental model that makes the bug invisible, because it is what "remove the role" feels like it should do. But a resource server deliberately does not call the IdP per request — that round trip is the cost JWT authorization exists to avoid. hasRole('ADMIN') evaluates against the Authentication's authorities, and on this setup those came from one place: the claim inside the token.

Correct — and notice that nothing anywhere is broken. The signature is valid, exp has not passed, tid matches, and the claim accurately records the directory as it stood at 08:55. The exposure lasts until the token expires and the refresh forces the IdP to look again, which is exactly why access-token lifetime is a security control: a 60-minute token buys a 60-minute window, a 10-minute token buys ten.

Signatures have no relationship to directory state. The signature proves the IdP minted these bytes and nobody edited them since — a fact about the past that stays true forever, no matter what you change afterwards. There is also nothing to invalidate: the IdP never stored this token, so there is no record of it to mark dead. That is precisely the gap a jti deny-list fills, by making your own side remember.

The token wasn't wrong. It was just old — and old is the one thing a signature can't detect.

1. RBAC vs ABAC vs ReBAC

ModelDecision based onBest forExample
RBAC — Role-BasedUser's assigned rolesEnterprise: defined job functionsRole=ADMIN can delete users; Role=VIEWER read only
ABAC — Attribute-BasedSubject + resource + environment attributesFine-grained: ownership, context, timeUser can edit document IF user.dept == doc.dept AND time is business hours
ReBAC — Relationship-BasedGraph relationship between user and resourceSocial/collaborative: "can edit if owner or team member"Google Zanzibar (Docs, Drive): viewer:doc → user:alice
PBAC — Policy-BasedDeclarative policy rules (OPA/Rego)Complex org: cross-cutting policies, auditOPA evaluates JSON policy: allow if user has MFA and clearance level >= 3
Most CIAM apps use RBAC + a pinch of ABAC. RBAC handles coarse-grained access (which features/endpoints). ABAC handles fine-grained access within an endpoint (can you edit THIS record, not just records in general). Spring Security natively supports both via @PreAuthorize SpEL.

2. JWT Claims Design for RBAC

Minimal RBAC claims (roles in token)

{
  "sub": "alice@example.com",
  "name": "Alice Smith",
  "roles": ["ROLE_ADMIN", "ROLE_USER"],
  "permissions": ["users:read", "users:write", "reports:read"],
  "iss": "https://auth.example.com",
  "aud": "api.example.com",
  "exp": 1900000000,
  "iat": 1718000000
}

Multi-tenant claims

{
  "sub": "alice@acme.com",
  "tenant_id": "acme-corp",
  "tenant_roles": {
    "acme-corp": ["ROLE_ORG_ADMIN"],
    "partner-co": ["ROLE_VIEWER"]
  },
  "dept": "engineering",
  "clearance": 3
}

Token size matters — JWTs travel in every request header. Keep roles in the token for coarse-grained RBAC. For fine-grained ABAC, look up permissions per request from a fast cache (Redis), not the token.

3. Spring Security + JWT Configuration

// 1. SecurityFilterChain — JWT resource server config
@Bean
public SecurityFilterChain filterChain(HttpSecurity http) throws Exception {
  http
    .csrf(csrf -> csrf.disable())
    .sessionManagement(sm -> sm.sessionCreationPolicy(SessionCreationPolicy.STATELESS))
    .authorizeHttpRequests(auth -> auth
      .requestMatchers("/public/**").permitAll()
      .anyRequest().authenticated()
    )
    .oauth2ResourceServer(rs -> rs
      .jwt(jwt -> jwt
        .decoder(NimbusJwtDecoder.withJwkSetUri(jwkSetUri).build())
        .jwtAuthenticationConverter(jwtAuthConverter())
      )
    );
  return http.build();
}

// 2. Custom converter: map JWT roles → Spring GrantedAuthority
@Bean
JwtAuthenticationConverter jwtAuthConverter() {
  JwtGrantedAuthoritiesConverter conv = new JwtGrantedAuthoritiesConverter();
  conv.setAuthoritiesClaimName("roles"); // read "roles" claim
  conv.setAuthorityPrefix(""); // do not prefix ROLE_ again
  JwtAuthenticationConverter jwtConv = new JwtAuthenticationConverter();
  jwtConv.setJwtGrantedAuthoritiesConverter(conv);
  return jwtConv;
}
The JWT authentication converter is the bridge between your JWT claims and Spring Security's GrantedAuthority. Your token has "roles": ["ROLE_ADMIN"]. The converter reads those and creates GrantedAuthority objects that @PreAuthorize SpEL can evaluate. Get this wrong and all @PreAuthorize checks fail silently (403 even for valid tokens).
