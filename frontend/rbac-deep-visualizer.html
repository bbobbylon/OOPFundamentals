RBAC & Authorization Deep Dive

Role-Based Access Control (RBAC), JWT claim design for roles/permissions, Spring Boot @PreAuthorize with SpEL, Attribute-Based Access Control (ABAC), and multi-tenant RBAC — the complete CIAM authorization picture.

🛡️ What is RBAC — and why does role-based authz live partly in the JWT, partly in the API, partly in the IdP?

Authorization ("can this user do THIS to THAT?") comes after authentication. RBAC assigns users roles (ADMIN/USER/READER) which carry permissions — managed per-role, not per-user. At login, roles are embedded in the JWT (the roles/groups claim) so the API reads them with no DB call; Spring maps scp/roles/groups/tid claims to GrantedAuthority for @PreAuthorize. ABAC extends RBAC with attribute rules (user.dept == doc.dept) — most CIAM apps use RBAC for coarse endpoint access and ABAC for fine-grained row access. Multi-tenant RBAC scopes roles per tenant via tid — always cross-check a resource's tenant against the JWT's tid so a role in tenant A never reaches tenant B's data.

  • AuthZ ≠ AuthN — what you can do vs who you are.
  • RBAC = roles carry permissions — embedded in JWT claims, read without a DB call.
  • Spring maps claims → GrantedAuthority for @PreAuthorize; ABAC for row-level.
  • Multi-tenant: scope by tid — never let tenant A's role touch tenant B.

JWT roles → Spring authorities

// JWT from Ping/Entra might have: // { "sub": "user-123", "roles": ["ADMIN", "USER"], "scp": "read write", "tid": "t-456" } // Spring custom converter maps claims → GrantedAuthority: @Bean JwtAuthenticationConverter jwtAuthenticationConverter() { var c = new JwtAuthenticationConverter(); c.setJwtGrantedAuthoritiesConverter(jwt -> { List<GrantedAuthority> auths = new ArrayList<>(); // Map "scp" → "SCOPE_read", "SCOPE_write": List<String> scopes = jwt.getClaimAsStringList("scp"); if (scopes != null) scopes.stream().map(s -> "SCOPE_"+s) .map(SimpleGrantedAuthority::new).forEach(auths::add); // Map "roles" → "ROLE_ADMIN", "ROLE_USER": List<String> roles = jwt.getClaimAsStringList("roles"); if (roles != null) roles.stream().map(r -> "ROLE_"+r) .map(SimpleGrantedAuthority::new).forEach(auths::add); return auths; }); return c; } // @PreAuthorize("hasRole('ADMIN')") → checks for "ROLE_ADMIN" authority // @PreAuthorize("hasAuthority('SCOPE_write')") → checks for "SCOPE_write"

@PreAuthorize SpEL patterns

// Basic role/scope guards: @PreAuthorize("hasRole('ADMIN')") public void adminAction() {} @PreAuthorize("hasAuthority('SCOPE_users.write')") public void writeUser() {} // Multiple conditions (AND): @PreAuthorize("hasRole('USER') and hasAuthority('SCOPE_profile.read')") public UserProfile getProfile() {} // Access method parameters in SpEL: @PreAuthorize("#userId == authentication.principal.subject or hasRole('ADMIN')") public User getUser(String userId) {} // ^ Only admins can get other users; normal users can only get themselves // @PostAuthorize — check AFTER method runs (filter result): @PostAuthorize("returnObject.tenantId == authentication.principal.getClaim('tid')") public Document getDocument(String docId) {} // ^ Ensures returned document belongs to caller's tenant // @PreFilter / @PostFilter — filter collections: @PostFilter("filterObject.ownerId == authentication.name") public List<Item> getItems() {}

Multi-tenant data isolation

// Critical: ALWAYS enforce tenant isolation at the data layer // Never rely on routing alone — tenants share the DB // Extract tenant from JWT in service methods: @Service public class DocumentService { // Pattern 1: Extract from SecurityContext private String getCurrentTenantId() { var jwt = (Jwt) SecurityContextHolder.getContext() .getAuthentication().getPrincipal(); return jwt.getClaimAsString("tid"); } // Always include tenantId in ALL data queries: public Page<Document> getDocuments(Pageable pageable) { String tenantId = getCurrentTenantId(); return documentRepo.findByTenantId(tenantId, pageable); // If tenantId missing → return empty or throw 403 } public Document getDocument(String docId) { String tenantId = getCurrentTenantId(); return documentRepo.findByIdAndTenantId(docId, tenantId) .orElseThrow(() -> new AccessDeniedException("Not found")); // ↑ Returns 403 even if doc exists — tenant can't know another tenant's IDs } }

In CIAM / Your Job: Ping AM injects group/role memberships into the JWT via token-policy claim transforms; Entra app-role assignments (App Registration → App roles) land in the roles claim. Your Spring APIs read these and enforce with @PreAuthorize. The security rule: never trust client-sent claims — only the IdP-signed JWT. And the Entra tid claim is your multi-tenant isolation key — verify the tenant on every resource access.

1. RBAC vs ABAC vs ReBAC

ModelDecision based onBest forExample
RBAC — Role-BasedUser's assigned rolesEnterprise: defined job functionsRole=ADMIN can delete users; Role=VIEWER read only
ABAC — Attribute-BasedSubject + resource + environment attributesFine-grained: ownership, context, timeUser can edit document IF user.dept == doc.dept AND time is business hours
ReBAC — Relationship-BasedGraph relationship between user and resourceSocial/collaborative: "can edit if owner or team member"Google Zanzibar (Docs, Drive): viewer:doc → user:alice
PBAC — Policy-BasedDeclarative policy rules (OPA/Rego)Complex org: cross-cutting policies, auditOPA evaluates JSON policy: allow if user has MFA and clearance level >= 3
Most CIAM apps use RBAC + a pinch of ABAC. RBAC handles coarse-grained access (which features/endpoints). ABAC handles fine-grained access within an endpoint (can you edit THIS record, not just records in general). Spring Security natively supports both via @PreAuthorize SpEL.

2. JWT Claims Design for RBAC

Minimal RBAC claims (roles in token)

{
  "sub": "alice@example.com",
  "name": "Alice Smith",
  "roles": ["ROLE_ADMIN", "ROLE_USER"],
  "permissions": ["users:read", "users:write", "reports:read"],
  "iss": "https://auth.example.com",
  "aud": "api.example.com",
  "exp": 1900000000,
  "iat": 1718000000
}

Multi-tenant claims

{
  "sub": "alice@acme.com",
  "tenant_id": "acme-corp",
  "tenant_roles": {
    "acme-corp": ["ROLE_ORG_ADMIN"],
    "partner-co": ["ROLE_VIEWER"]
  },
  "dept": "engineering",
  "clearance": 3
}

Token size matters — JWTs travel in every request header. Keep roles in the token for coarse-grained RBAC. For fine-grained ABAC, look up permissions per request from a fast cache (Redis), not the token.

3. Spring Security + JWT Configuration

// 1. SecurityFilterChain — JWT resource server config
@Bean
public SecurityFilterChain filterChain(HttpSecurity http) throws Exception {
  http
    .csrf(csrf -> csrf.disable())
    .sessionManagement(sm -> sm.sessionCreationPolicy(SessionCreationPolicy.STATELESS))
    .authorizeHttpRequests(auth -> auth
      .requestMatchers("/public/**").permitAll()
      .anyRequest().authenticated()
    )
    .oauth2ResourceServer(rs -> rs
      .jwt(jwt -> jwt
        .decoder(NimbusJwtDecoder.withJwkSetUri(jwkSetUri).build())
        .jwtAuthenticationConverter(jwtAuthConverter())
      )
    );
  return http.build();
}

// 2. Custom converter: map JWT roles → Spring GrantedAuthority
@Bean
JwtAuthenticationConverter jwtAuthConverter() {
  JwtGrantedAuthoritiesConverter conv = new JwtGrantedAuthoritiesConverter();
  conv.setAuthoritiesClaimName("roles"); // read "roles" claim
  conv.setAuthorityPrefix(""); // do not prefix ROLE_ again
  JwtAuthenticationConverter jwtConv = new JwtAuthenticationConverter();
  jwtConv.setJwtGrantedAuthoritiesConverter(conv);
  return jwtConv;
}
The JWT authentication converter is the bridge between your JWT claims and Spring Security's GrantedAuthority. Your token has "roles": ["ROLE_ADMIN"]. The converter reads those and creates GrantedAuthority objects that @PreAuthorize SpEL can evaluate. Get this wrong and all @PreAuthorize checks fail silently (403 even for valid tokens).
