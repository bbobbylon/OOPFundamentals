Server-Side Refresh Tokens & Rotation

A refresh token is long-lived and powerful — steal one and you mint access tokens indefinitely. The server-side defense is three rules: store them hashed, rotate on every use (each refresh returns a new one and burns the old), and detect reuse — if a token that was already spent shows up again, that's theft, so you revoke the whole family. Rotation alone doesn't stop a thief; reuse-detection is what closes the window.

Why is a refresh token so dangerous — and what are the three server-side defenses?

An access token is short-lived (15 minutes) — if stolen, the attacker has a narrow window. A refresh token is long-lived (days or weeks) and can generate new access tokens indefinitely. If an attacker steals a refresh token, they own the account — they can keep generating access tokens forever, even after the user changes their password (the refresh token is still valid unless explicitly revoked). The three server-side defenses: (1) Store hashed — never store the raw refresh token in the DB. Store SHA-256(token). If the DB is leaked, attackers can't use the hashes. (2) Rotate — on every refresh, issue a new refresh token and immediately invalidate the old one. (3) Detect reuse — if an already-spent refresh token arrives, someone is replaying a stolen token. Revoke the entire token family (all sessions for that user). This is the key insight: rotation alone doesn't help if the attacker uses the token before you do. Reuse detection catches that.

Token family model

DB schema: refresh_tokens (id, family_id, token_hash, user_id, issued_at, expires_at, revoked). All tokens for one login session share the same family_id. Rotate: mark old token revoked=true, insert new token with same family_id. Reuse detected: incoming token hash found in DB with revoked=true → revoke ALL tokens where family_id = old.family_id → force user to log in again. Alert: log the reuse attempt with IP and user ID.

Storage rules

Access token: memory only (Angular's in-memory variable or signal — not localStorage). Never store access tokens in localStorage or sessionStorage (XSS risk). Refresh token: httpOnly, Secure, SameSite=Strict cookie only. JavaScript cannot read it. The browser attaches it automatically to POST /api/auth/refresh. Or (BFF pattern): the BFF stores the refresh token server-side (Redis), browser only holds a session cookie. Never store refresh tokens in JS-readable storage.

Spring Security JWT refresh flow

POST /api/auth/refresh (refresh token in httpOnly cookie). 1) Read cookie. 2) Hash it: SHA-256(cookie). 3) Lookup in DB by hash. 4) If not found: 401. 5) If found but revoked=true: reuse detected → revoke family → 401 + logout. 6) If valid and not expired: issue new access JWT, rotate refresh token (new cookie set, old marked revoked). 7) Return {"accessToken":"..."} in JSON body. Angular stores the new access token in memory.

In CIAM: When user changes password: revoke ALL their refresh tokens (all families). When admin deactivates user: revoke all tokens immediately — the user's current access token lasts max 15 minutes, then they can't refresh. When reuse is detected: log to security audit log ("Refresh token reuse detected for user X from IP Y — all sessions revoked"), send the user an email "Your account was logged out from all devices due to a suspicious login attempt." The email is a security signal — the user might not know they were compromised.

1. The three rules

  • Hash at rest. Store a hash of the refresh token (like a password), never the raw value — a DB leak then yields nothing usable.
  • Rotate on use. Every grant_type=refresh_token issues a new refresh token and marks the presented one used. A stolen token is good only until the next legit refresh.
  • Detect reuse → revoke the family. If an already-used (or unknown) token is presented, someone has a copy. Invalidate every token in that login's family and force re-auth.

2. Interactive: rotation & reuse-detection

3. What you store

@Entity class RefreshToken {
  String id;            // this token's id
  String familyId;      // the login session (rotation chain)
  String tokenHash;     // SHA-256 of the raw token — never the raw value
  String userId;
  Instant expiresAt;    // absolute (and/or sliding) expiry
  boolean used;         // flipped true on rotation
}

// on refresh: look up by hash → if missing OR used → REUSE → revoke whole familyId
//            else → mark used, issue a new token in the same family

Rotation makes the chain single-use end-to-end; the familyId lets one detected reuse nuke every descendant in that session.

4. Where it lives

  • The IDM usually owns this. Entra/Ping issue & rotate refresh tokens for you — prefer that over rolling your own. You build it yourself mainly for a custom auth server or a BFF holding tokens server-side.
  • Never in the browser's localStorage. A refresh token in JS is an XSS jackpot. Keep it in an httpOnly cookie via a BFF, or don't expose it to the SPA at all.
  • Absolute + sliding expiry. Cap the total session lifetime (absolute) even as activity slides the window — so a quiet stolen token still dies.
  • Revocation on logout deletes the family; "log out everywhere" deletes all families for the user.

5. One-sentence recap

🔁 Store refresh tokens hashed, rotate them on every use (new token issued, old marked used, tracked by a familyId), and detect reuse — a spent or unknown token reappearing means it was stolen, so revoke the entire family and force re-auth — because rotation alone only shrinks the theft window while reuse-detection is what actually catches the thief; prefer the IDM's built-in rotation, keep the token in an httpOnly cookie / BFF (never localStorage), and bound it with absolute + sliding expiry.
