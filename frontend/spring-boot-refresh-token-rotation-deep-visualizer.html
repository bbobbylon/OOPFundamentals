Server-Side Refresh Tokens & Rotation

A refresh token is long-lived and powerful — steal one and you mint access tokens indefinitely. The server-side defense is three rules: store them hashed, rotate on every use (each refresh returns a new one and burns the old), and detect reuse — if a token that was already spent shows up again, that's theft, so you revoke the whole family. Rotation alone doesn't stop a thief; reuse-detection is what closes the window.

🔄 Why is a refresh token so dangerous — and what are the three server-side defenses?

An access token is short-lived (~15 min), so a theft has a narrow window. A refresh token is long-lived and mints new access tokens indefinitely — steal one and the attacker owns the account, even after a password change, unless it's explicitly revoked. Three defenses: store hashed (keep only SHA-256(token) so a DB leak is useless), rotate (issue a new refresh token and invalidate the old one on every use), and detect reuse (a spent token replayed means it was stolen → revoke the whole token family). The key insight: rotation alone fails if the attacker spends the token first — reuse detection is what catches that.

  • Refresh tokens are the crown jewels — long-lived and self-renewing.
  • Hash at rest. A leaked DB of SHA-256 hashes can't be replayed.
  • Rotate every use so any token is single-use.
  • Reuse = breach. A replayed spent token revokes the entire family and forces re-login.

Token family model

refresh_tokens(id, family_id, token_hash, user_id, issued_at, expires_at, revoked). One session shares a family_id; rotation marks the old revoked=true and inserts a new one. A hit on a revoked=true hash = reuse → revoke the whole family_id and log it with IP + user.

Storage rules

Access token: in memory only (a signal/variable, never localStorage). Refresh token: httpOnly, Secure, SameSite=Strict cookie the browser auto-attaches to /api/auth/refresh — or, in BFF, kept server-side in Redis. Never in JS-readable storage.

Spring refresh flow

POST /api/auth/refresh: read cookie → hash → DB lookup. Not found → 401; found but revoked → reuse → revoke family + 401; valid → issue a new access JWT, rotate the refresh token (new cookie, old revoked), return {"accessToken":"…"} for Angular to hold in memory.

CIAM: On password change, revoke all of a user's refresh tokens (every family); on admin deactivation, revoke immediately — their access token dies within 15 min and can't refresh. On reuse, write a security-audit line ("reuse detected for user X from IP Y — all sessions revoked") and email "you were logged out of all devices due to a suspicious attempt" — that email may be the user's first sign they were compromised.

1. The three rules

  • Hash at rest. Store a hash of the refresh token (like a password), never the raw value — a DB leak then yields nothing usable.
  • Rotate on use. Every grant_type=refresh_token issues a new refresh token and marks the presented one used. A stolen token is good only until the next legit refresh.
  • Detect reuse → revoke the family. If an already-used (or unknown) token is presented, someone has a copy. Invalidate every token in that login's family and force re-auth.

2. Interactive: rotation & reuse-detection

family: active attacker holds a copy of RT#1

Try: legit refresh (RT#1→RT#2), then attacker replays RT#1 → it's already used → reuse detected → the whole family is revoked (both parties must re-login — the safe outcome). Or let the attacker replay first to see why rotation needs detection.

3. What you store

@Entity class RefreshToken {
  String id;            // this token's id
  String familyId;      // the login session (rotation chain)
  String tokenHash;     // SHA-256 of the raw token — never the raw value
  String userId;
  Instant expiresAt;    // absolute (and/or sliding) expiry
  boolean used;         // flipped true on rotation
}

// on refresh: look up by hash → if missing OR used → REUSE → revoke whole familyId
//            else → mark used, issue a new token in the same family

Rotation makes the chain single-use end-to-end; the familyId lets one detected reuse nuke every descendant in that session.

4. Where it lives

  • The IDM usually owns this. Entra/Ping issue & rotate refresh tokens for you — prefer that over rolling your own. You build it yourself mainly for a custom auth server or a BFF holding tokens server-side.
  • Never in the browser's localStorage. A refresh token in JS is an XSS jackpot. Keep it in an httpOnly cookie via a BFF, or don't expose it to the SPA at all.
  • Absolute + sliding expiry. Cap the total session lifetime (absolute) even as activity slides the window — so a quiet stolen token still dies.
  • Revocation on logout deletes the family; "log out everywhere" deletes all families for the user.

↪ The browser side of the same flow: Angular · Access Tokens & Silent Refresh. Keeping tokens off the SPA: Spring · BFF & Token Relay.

5. One-sentence recap

🔁 Store refresh tokens hashed, rotate them on every use (new token issued, old marked used, tracked by a familyId), and detect reuse — a spent or unknown token reappearing means it was stolen, so revoke the entire family and force re-auth — because rotation alone only shrinks the theft window while reuse-detection is what actually catches the thief; prefer the IDM's built-in rotation, keep the token in an httpOnly cookie / BFF (never localStorage), and bound it with absolute + sliding expiry.
