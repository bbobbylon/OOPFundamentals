Graphs — BFS, DFS & Shortest Paths

Same graph, different exploration strategies. Watch the order they discover nodes — and watch BFS find the shortest path.

🧩 What is BFS vs DFS — and when does each algorithm find what you're looking for?

A graph is a set of nodes (vertices) connected by edges. Unlike arrays or trees, graphs have no inherent start or ordering — you must traverse them to discover what's connected. The two fundamental traversal algorithms, BFS and DFS, explore the same graph but in completely different orders, which makes them optimal for different problems. BFS (Breadth-First Search): explore all neighbors of the current node before going deeper. Uses a queue (FIFO). The algorithm: enqueue start node and mark visited, then loop: dequeue a node, process it, enqueue all unvisited neighbors. Because it explores level by level (all nodes at distance 1, then all at distance 2...), BFS naturally finds the shortest path (fewest edges) between two nodes in an unweighted graph. The first time BFS reaches the destination is guaranteed to be the shortest route. DFS (Depth-First Search): go as deep as possible along one path before backtracking. Uses a stack (or recursion, which uses the call stack implicitly). The algorithm: push start node, loop: pop a node, if not visited mark it and push all neighbors. DFS goes one direction as far as it can before trying another direction. DFS is NOT guaranteed to find the shortest path — it may find a path, but not necessarily the shortest one. What each is good for: BFS → shortest path in unweighted graphs, level-order traversal, "find nearest X" problems. DFS → cycle detection, topological sort, connected components, maze solving, detecting reachability, backtracking problems. Time complexity: both O(V + E) — V vertices + E edges. Every vertex is visited once, every edge is traversed once. Space complexity: BFS stores up to O(V) nodes in the queue (wide levels). DFS stores O(depth) nodes in the stack — in the worst case (linear chain) that's O(V), but in practice much less for balanced graphs.

BFS — queue-based

// BFS: explore level by level // Data structure: QUEUE (FIFO) // Finds SHORTEST PATH in unweighted graph void bfs(Map<Integer,List<Integer>> graph, int start) { Set<Integer> visited = new HashSet<>(); Queue<Integer> queue = new LinkedList<>(); queue.offer(start); visited.add(start); while (!queue.isEmpty()) { int node = queue.poll(); // dequeue FIFO System.out.print(node + " "); // process for (int neighbor : graph.getOrDefault(node, List.of())) { if (!visited.contains(neighbor)) { visited.add(neighbor); // mark BEFORE enqueue! queue.offer(neighbor); // enqueue for later } } } } // Explore order: A,B,C,D,E... (distance 1 then 2 then 3)

DFS — recursive

// DFS: go deep first, then backtrack // Data structure: STACK or RECURSION // Good for: cycles, components, topological sort void dfs(Map<Integer,List<Integer>> graph, int node, Set<Integer> visited) { if (visited.contains(node)) return; // already seen visited.add(node); System.out.print(node + " "); // process BEFORE recursing for (int neighbor : graph.getOrDefault(node, List.of())) { dfs(graph, neighbor, visited); // recurse DEEP immediately } // backtrack: returns here after exhausting this path } // Call: dfs(graph, startNode, new HashSet<>()); // Explore order: A,B,E,F,C,D... (goes deep first) // NOT shortest path — just SOME path

BFS vs DFS decision table

// USE BFS WHEN: // ✅ Need shortest path (fewest edges) // ✅ Find nearest neighbor/element // ✅ Level-by-level processing // ✅ Find all nodes within distance K // Example: word ladder (BFS = min transformations) // USE DFS WHEN: // ✅ Detect cycles in a graph // ✅ Find all paths (not just shortest) // ✅ Topological sort (DFS-based version) // ✅ Check if path EXISTS (not min length) // ✅ Backtracking (mazes, N-queens, permutations) // ✅ Connected components (island counting) // Example: number of islands (DFS marks whole island) // BOTH work for: // • Graph connectivity (is A reachable from B?) // • Traversal of all nodes // Performance is the same: O(V+E) for both

In CIAM / Context: BFS and DFS are used throughout CIAM systems. BFS finds the shortest delegation chain in a role hierarchy (ADMIN → MANAGER → USER — minimum hops to reach a target permission). DFS detects circular role/group inheritance (e.g., Group A includes Group B includes Group A — Ping AM's group resolver would loop forever without cycle detection). Spring's ApplicationContext dependency resolution uses DFS-like traversal to resolve bean dependencies. Angular's module dependency graph is checked for circular imports using DFS cycle detection. OAuth authorization code flows can be modeled as a graph where BFS answers "what is the minimum number of redirect steps to reach the callback URI?"

The problem

Recursive DFS is textbook-correct, O(V+E), and it will still crash your JVM on a real graph — and nothing in your own code is what throws the error.

It worked on 200 test nodes. It died on a partner's sync job.

Say you write a recursive DFS cycle-checker that runs before a role-import job commits — the exact recursive shape from the intro card above, one call per node, recursing into every unvisited neighbor. It's reviewed, it's tested against your 200-node fixture graph, it ships.

Then a partner's nightly SCIM sync uploads a role hierarchy where a generator bug points every role's "parent" at the row directly above it — no branching, just ROLE_1 → ROLE_2 → ROLE_3 → … → ROLE_80000, one straight 80,000-node chain. Your DFS starts walking it, one recursive call per role. Somewhere in the low tens of thousands of open frames, the thread's call stack runs out of room and the JVM throws StackOverflowError — not from a line you wrote, from the act of calling a function inside a function 80,000 times without any of them returning yet.

adjacency list ✓ visited set ✓ cycle logic ✓ recursion depth == chain length ⚠

Every line of the algorithm is right. The bug is that you asked the call stack to hold 80,000 open frames at the same time.

Get the traversal off the JVM's call stack
Rewrite the recursion as an explicit stack ↓ you push/pop your own array on the heap instead of the JVM's fixed-size thread stack — heap scales to gigabytes, the default thread stack does not Or raise -Xss for that one worker thread, if you must keep the recursion ↓ buys headroom today, but bakes in a new, higher, still-silent ceiling — someone imports 500,000 roles next quarter and it dies again And cap the traversal depth before you ship either version ↓ a depth cap turns a silent JVM crash into an ordinary, catchable "graph too deep, rejecting import" error you can hand back to whoever generated the bad file
The one-sentence rule. Recursive DFS is only as deep as your input lets it be, and nothing about "traverse the graph" promises the input stays shallow. Treat call-stack depth as a finite resource, the same way you'd treat memory or open file handles — especially anywhere DFS runs on a graph built from data someone else controls.
A stack frame doesn't know it's traversing a graph. It just knows a function called a function called a function. 80,000 nested calls in, and the JVM never once asks whether you meant it.
You

My DFS is O(V+E). Why did it just crash on a graph that's smaller than graphs I've BFS'd through fine?

The call stack

Because BFS never asked me to hold anything. Its queue lives on your heap. I'm a fixed slice of memory the OS carved out for this one thread before your first line even ran.

You

So the shape of the graph — chain versus branching tree — decides whether I crash?

The call stack

Recursion depth is the longest unbroken chain of open calls, not the node count. A wide, bushy graph with 80,000 nodes and depth 12 never troubles me. A straight chain with the same node count fills me up completely.

The mechanism

Follow one recursive call as it goes 80,000 nodes deep, and watch exactly where the stack runs out.

  1. dfs(ROLE_1) is called from the import job's main loop — frame #1 is pushed onto the thread's call stackdepth 1
  2. dfs(ROLE_1)'s loop calls dfs(ROLE_2) for its one neighbor — frame #2 is pushed, frame #1 stays open, waiting on frame #2 to returndepth 2
  3. The pattern repeats: dfs(ROLE_3) pushes frame #3 — now two frames above it are still open, still waitingdepth 3
  4. By roughly ROLE_9,987 the thread's reserved stack memory is essentially full — because not one of those 9,987 calls has returned yetnear limit
  5. dfs(ROLE_9,988) tries to push one more frame and there is nowhere left to put itoverflow
  6. StackOverflowError is thrown from inside the JVM, unwinding all 9,987 open frames at once — the import job dies mid-transactioncrash

Look at steps 2 through 4: none of the earlier frames had returned. Recursive DFS doesn't finish a node and move on — it pauses on a node, dives into its neighbor, and only unwinds once every deeper call has finished. BFS never does this: BFS fully finishes one node, discards its stack frame, and only then looks at the next one in its queue. That's the whole difference between "depth held open" and "depth already released."

They funnel into the exact same failure because none of them care what kind of data they're modeling: DFS's recursion only sees "how long is the chain," and a chain is a chain whether you call it a role hierarchy, a linked list, or a dependency line.

Your recursive cycle-detection DFS works fine on every graph in your test suite (largest is 200 nodes, several branches deep). A partner's nightly sync produces a role-inheritance graph that's a single unbranched chain of 80,000 nodes. What actually happens when the cycle check runs against it?

O(V+E) describes total work across the whole run — it says nothing about how much of that work has to be in flight at once. Recursion depth is a separate resource, one open stack frame per call that hasn't returned yet, and big-O never prices it in.

Right — and here's the sharper detail: StackOverflowError extends Error, not Exception. A catch (Exception e) around the whole import job won't catch it. The crash isn't just unexpected, it slips past the exact safety net most teams reach for by habit.

It doesn't fail quietly — the crash is loud, it's just thrown from a place your own try/catch isn't watching. A silent wrong answer would actually be a different (and in some ways scarier) bug than the one that happens here.

Where you have seen this before

"Unbounded recursion on attacker- or partner-controlled input" is a whole category of bug, and graphs are only one costume it wears.

Jackson deserializing your Spring controller's request body

A deeply nested JSON payload — thousands of nested arrays, not necessarily large in bytes — drives a recursive-descent JSON parser one stack frame per nesting level, the same way a deep graph drives DFS. It's exactly why Jackson 2.15 added StreamReadConstraints with a default max nesting depth: to turn that StackOverflowError into an ordinary, catchable JsonParseException before it ever reaches your controller.

same shape: recursion depth tied to untrusted input, not to data size

SAML assertions in identity systems

SAML assertions are XML, and XML has been parsed recursively for decades. Deeply nested XML elements are a documented denial-of-service vector for exactly this reason — a small, deliberately deep document can exhaust a naive parser's stack the same way a deliberately deep graph exhausts DFS's. It's why hardened XML parsers cap element nesting depth as part of the same threat model as entity-expansion bombs.

identity's own version of the depth attack

Recursive-descent expression parsers

A hand-written parser for a calculator or config language hits the identical wall on deeply nested parentheses — ((((((…)))))) a few thousand deep — because parseExpression() calling parseExpression() calling parseExpression() overflows before it evaluates a single number.

the classic compilers-class version of this exact bug

BFS vs DFS — when to use which

🌊 BFS — Breadth-First

Data structure: queue (FIFO)

Visits the start, then all distance-1 neighbors, then all distance-2 neighbors. Explores in layers, like ripples on a pond.

  • Shortest path on unweighted graphs ✅
  • "Friends of friends" recommendations
  • Web crawlers (level-by-level)
  • Solving puzzles with fewest moves
  • Network broadcast / flood fill

🌲 DFS — Depth-First

Data structure: stack (LIFO) or recursion

Dives down a single path as far as it can, then backtracks. Uses less memory than BFS on wide graphs, more on deep graphs.

  • Topological sort (build / dependency order)
  • Cycle detection
  • Connected component analysis
  • Solving mazes (path exists?)
  • Generating & pruning game trees

Beyond BFS: weighted graphs & Dijkstra

BFS assumes every edge has the same cost (1 hop). Most real-world graphs have weights: roads have miles, networks have latency, flights have prices. For those, BFS gives the wrong answer — taking 5 short edges might cost less than 1 long edge.

The fix is Dijkstra's algorithm — BFS but with a priority queue (min-heap) instead of a regular queue. Always pop the node with the smallest known distance, relax its neighbors, repeat. Result: shortest path on a weighted graph with non-negative edges, in O((V + E) log V). 

// Dijkstra is BFS with a priority queue. Pseudocode:
dist[start] = 0;
pq.add(start, 0);
while (!pq.isEmpty()) {
    Node u = pq.popMinDist();
    for (Edge e : adj[u]) {
        int newDist = dist[u] + e.weight;
        if (newDist < dist[e.to]) {
            dist[e.to] = newDist;
            prev[e.to] = u;
            pq.add(e.to, newDist);
        }
    }
}

When edges can be negative (e.g. arbitrage in finance), use Bellman-Ford. When you have a heuristic (e.g. straight-line distance on a map), use A* — it explores fewer nodes by always preferring directions that look like progress toward the goal.

Where you see graphs in production

🗺️ Maps & routing

Google Maps, Waze, Uber. Roads = edges, intersections = nodes, weights = travel time. Uses Dijkstra / A* / contraction hierarchies.

👥 Social graphs

"People you may know", LinkedIn 2nd-degree connections, Twitter following graph. BFS to find friends-of-friends within N hops.

🌐 The internet itself

Routers are nodes, links are edges. BGP and OSPF are shortest-path algorithms running on the global network 24/7.

📦 Build systems & package managers

Maven, npm, Cargo: dependencies form a DAG. Topological sort (a DFS variant) gives you the order to compile / install in.

🧠 Knowledge & recommendation graphs

Netflix, Spotify, Amazon all use graph traversals over user-item-tag graphs to recommend. Wikipedia link structure is a giant graph too.

🧬 Compilers

Control-flow graphs, call graphs, register interference graphs — half of compiler theory is graph algorithms in a trench coat.

Adjacency list (how the graph is actually stored)

// Adjacency list: each vertex points to a list of its neighbors.
// Memory: O(V + E). Best when edges are sparse — the usual case.
Map<String, List<String>> adj = new HashMap<>();
adj.put("A", List.of("B", "C"));
adj.put("B", List.of("A", "D"));
// ...

// Textbook BFS
public List<String> bfs(String start) {
    Queue<String> queue = new ArrayDeque<>();
    Set<String> visited = new HashSet<>();
    List<String> order = new ArrayList<>();
    queue.add(start); visited.add(start);
    while (!queue.isEmpty()) {
        String cur = queue.poll();
        order.add(cur);
        for (String n : adj.getOrDefault(cur, List.of())) {
            if (visited.add(n)) queue.add(n);
        }
    }
    return order;
}
