REST Controllers

Building HTTP APIs with @RestController — the annotations, the request/response cycle, and the status codes that matter. For the alternative to one-URL-per-resource — a single endpoint where the client specifies the response shape — see GraphQL.

🌐 What is a REST API? What does @RestController do?

@RestController turns a plain Java class into HTTP endpoints your Angular app (or any client) calls over the network. The client sends a request like GET /api/users/42; Spring matches the URL to a method, runs it, and serializes whatever you return into a JSON response. You annotate the class and its methods — Spring handles the routing, parameter binding, JSON conversion, and status codes for you.

  • A REST API is a set of URLs + HTTP verbs (GET read · POST create · PUT replace · DELETE remove) acting on resources.
  • @RestController marks the class; @GetMapping("/users") / @PostMapping map a URL + verb to one specific method.
  • Inputs are bound for you: @PathVariable pulls values out of the URL, @RequestBody deserializes the JSON body into a DTO object.
  • Your return value is auto-serialized to JSON; the outcome maps to a status code — 200 ok · 201 created · 404 missing · 400 bad input.
  • Cross-cutting concerns (auth, validation, error shape) live in the filter chain and @ControllerAdvice, not repeated inside every method.

The key annotations

  • @RestController — marks the class
  • @GetMapping("/users") — maps GET
  • @PostMapping / @PutMapping / @DeleteMapping
  • @PathVariable Long id — from the URL
  • @RequestBody User dto — from JSON

What happens to a request

  1. Arrives at Tomcat
  2. Security filter chain (auth check)
  3. DispatcherServlet finds the method
  4. Method runs → calls your service
  5. Result serialized to JSON
  6. Response sent (200 / 201 / 404…)

The problem

The @ExceptionHandler is written correctly, tested, and sitting right there in the codebase. A production 500 happens anyway.

An expired JWT never even reaches your clean 401

Your @RestControllerAdvice has @ExceptionHandler(ExpiredJwtException.class) returning a tidy ProblemDetail with a 401. It works great in every test you wrote — each one calls the service method directly, or hits an endpoint with an already-valid token and a separately-mocked expiry check. In production, an actual expired Bearer token comes in, and the client gets Tomcat's raw HTML error page instead of your JSON. Nothing about the @ExceptionHandler is wrong. It simply never runs.

@ControllerAdvice catches exceptions thrown while a handler is being invoked. A filter throws before a handler is even picked — a different pipeline stage entirely.

@ControllerAdvice catches exceptions thrown while DispatcherServlet is invoking a handler — not exceptions thrown before a handler was ever chosen. Anything upstream of routing — a security filter, the servlet container itself — is a different failure domain, with its own handlers. Moving, renaming, or duplicating your @ExceptionHandler methods fixes nothing here, because the problem was never the handler. It was which stage of the pipeline threw.
Think of DispatcherServlet's exception machinery as a receptionist who only starts helping once you've checked in at the front desk — once a handler method has been picked for you. @ControllerAdvice is that receptionist's rulebook for what to say when a checked-in visitor has a problem. Your JwtAuthFilter is the security guard standing OUTSIDE, checking badges before anyone reaches the front desk at all. If the guard rejects your badge, you're turned away right there in the parking lot — the receptionist never even learns you existed. Nobody wrote that rulebook with parking-lot problems in mind.

The mechanism

@ControllerAdvice's safety net is real. It's also only stretched across one specific room.

  1. Angular sends GET /api/users/me with a Bearer token that expired four minutes agothe request leaves the browser
  2. Tomcat's filter chain runs first — JwtAuthFilter.doFilterInternal() parses the token, before Spring MVC exists for this request at allpre-routing
  3. The JWT library throws ExpiredJwtException from inside the filter — no handler has been chosen yet, because routing hasn't happenedDispatcherServlet not yet invoked
  4. The exception propagates straight up through the filter chain toward Tomcat — Spring's HandlerExceptionResolver chain, the thing @ControllerAdvice plugs into, was never enteredthe safety net that never got a chance
  5. Tomcat falls back to its own default error handling — a generic HTML error page, not your JSON ProblemDetaila different error-rendering pipeline entirely
  6. Your @RestControllerAdvice method, sitting right there in the codebase, never runs — not because it's broken, but because this request never entered its territorycorrect code, wrong assumption about reach

Step 3 is the whole lesson. @ControllerAdvice is wired into DispatcherServlet's HandlerExceptionResolver chain, and that chain only exists for a request that made it far enough to have a handler picked. A filter-chain exception happens at a pipeline stage @ControllerAdvice was never attached to — no amount of adding, editing, or reordering @ExceptionHandler methods reaches backward into a stage that already finished throwing.

ExpiredJwtException is thrown in the OUTER ring — one layer before the inner ring's machinery even exists for this request. It never gets a chance to walk inward and find your @ExceptionHandler; it goes straight up and out, to Tomcat.

Your @RestControllerAdvice has @ExceptionHandler(ExpiredJwtException.class) returning a clean 401 with a JSON ProblemDetail body. A request arrives with an expired Bearer token; your custom JwtAuthFilter (registered addFilterBefore(..., UsernamePasswordAuthenticationFilter.class)) parses it and throws, with no try/catch of its own. What does the client actually receive?

Exactly — @ControllerAdvice hooks into DispatcherServlet's HandlerExceptionResolver chain, which only exists once a handler has been chosen for the request. A filter runs before that point, so an uncaught exception there propagates straight up to the servlet container, which renders its own generic error response — not the JSON you wrote.

The natural assumption — @RestControllerAdvice really does catch this exact exception type beautifully, but only when it's thrown from inside a controller or service call that DispatcherServlet is actively invoking. A filter runs at an earlier pipeline stage that @ControllerAdvice was never attached to, so the method never fires here.

Spring Security doesn't silently swallow filter exceptions — left uncaught, they propagate. (You CAN configure an AuthenticationEntryPoint to handle exactly this case cleanly — but that's a separate, dedicated extension point, not @ControllerAdvice, and it doesn't happen automatically.)

Where you've seen this before

Three frameworks, one boundary: exception-handling machinery only sees what actually flows through it.

ASP.NET Core's exception middleware

The same boundary shows up as pipeline order. UseExceptionHandler only catches exceptions thrown by middleware registered AFTER it. An exception thrown by authentication middleware registered earlier in Program.cs sails right past it, straight to the server's own default response — same "was I downstream of the throw" question, different framework's syntax for asking it.

middleware order ≈ filter-vs-DispatcherServlet order

Express's (err, req, res, next) handler

Express's error-handling middleware only catches what actually reaches it through the normal next() chain — a synchronous throw inside a route, or an explicit next(err). An exception thrown inside something wired before your error handler, or inside an async callback that never calls next(err), never arrives — the process just crashes or hangs instead. Same shape: the catching machinery only sees traffic that's routed through it.

next(err) chain ≈ HandlerExceptionResolver chain

Your CIAM's federated-login filter

A filter validating a Ping- or Entra-issued token during OAuth2 login throws on a bad signature or a failed introspection call — same blind spot, same stage as the JWT filter above, invisible to @ControllerAdvice for the exact same reason. The fix has to live in an AuthenticationFailureHandler or AuthenticationEntryPoint, because that's the extension point actually wired into that stage of the pipeline.

federated login filter ≈ JwtAuthFilter
Questions from the back row

So @ControllerAdvice is basically useless for security exceptions?

Not useless — the wrong tool for THIS stage. It's exactly right for exceptions your controller or service layer throws (not-found, validation, business-rule violations) — everything downstream of routing. For anything a filter throws (JWT parsing, token introspection), Spring Security has dedicated hooks — AuthenticationEntryPoint for 401s, AccessDeniedHandler for 403s — that run at the filter stage itself.

Could I just move the JWT validation somewhere @ExceptionHandler-friendly, like a service call from inside a controller?

You could validate a token's CLAIMS inside a service and get @ControllerAdvice back for that part — but the authentication decision (is this even a request I should route at all?) has to happen before routing, by design. You don't want DispatcherServlet binding a body or invoking a controller for a request you're about to reject anyway. That's exactly why authentication belongs in a filter in the first place.

How do I get consistent JSON error shapes across both stages, then?

Write your AuthenticationEntryPoint / AccessDeniedHandler to build the SAME ProblemDetail shape your @ExceptionHandler methods build — same fields, same structure — just from a different entry point. Two separate mechanisms, one shared response format; the client never has to know which stage rejected the request.

2 — Controller Anatomy — Click Any Annotation

@RestController

Marks class as HTTP handler + auto-serializes return values to JSON

@RequestMapping

Base URL prefix for all methods in the class

@GetMapping

Handles GET requests. Maps a URL to a method

@PostMapping

Handles POST requests. Used for creating resources

@PathVariable

Extracts a variable from the URL path

@RequestBody

Deserializes the JSON request body into a Java object

ResponseEntity

Wrapper that lets you control status code + headers

@RequestParam

Reads query string parameters like ?page=2&size=10

@RestController @RequestMapping("/api/users") public class UserController { private final UserService service; @GetMapping("/{id}") public ResponseEntity<User> getUser(@PathVariable Long id) { return service.findById(id) .map(ResponseEntity::ok) .orElse(ResponseEntity.notFound().build()); } @PostMapping public ResponseEntity<User> createUser(@RequestBody User user) { User saved = service.save(user); return ResponseEntity.status(201).body(saved); } @GetMapping public List<User> listUsers( @RequestParam(defaultValue = "0") int page, @RequestParam(defaultValue = "20") int size) { return service.findAll(page, size); } }

3 — HTTP Status Codes That Matter

Click a status code to see when to use it and the common mistake.

200
OK
Successful GET, PUT, DELETE. Return the resource or updated object. ⚠️ Don't use for resource creation — that's 201.
201
Created
Successful POST that created a new resource. Return the created object and set Location header to the new resource URL.
204
No Content
Successful DELETE (or PUT with no response body). No response body. ⚠️ Don't return 200 with an empty body — use 204.
400
Bad Request
The client sent malformed data (invalid JSON, missing required field). Return a body explaining what's wrong. Include validation errors.
401
Unauthorized
Not authenticated. Client must provide credentials (login first, get a token). ⚠️ Confusingly named — it means unauthenticated, not unauthorized.
403
Forbidden
Authenticated but not authorized. The user IS logged in but doesn't have permission for this action/resource. Don't expose why — just refuse.
404
Not Found
Resource doesn't exist. Return 404 (not 200 with null). ⚠️ Also use 404 instead of 403 when you want to hide a resource's existence from unauthorized users.
409
Conflict
Request conflicts with current state. Classic use: trying to create a user with an email that already exists. Return the conflicting resource info.
500
Internal Server Error
Something broke server-side. Log the full exception server-side but return a generic message to the client — never expose stack traces externally.

4 — Raw Servlet vs Spring MVC

The same GET /users/{id} endpoint — written the old way vs the Spring way:

❌ Raw HttpServlet
protected void doGet( HttpServletRequest req, HttpServletResponse res) throws IOException { String path = req.getPathInfo(); // Parse ID from "/42" manually Long id = Long.parseLong(path.substring(1)); User u = db.find(id); if (u == null) { res.setStatus(404); return; } res.setContentType("application/json"); // Serialize to JSON manually String json = "{\\"id\\":" + u.getId() +"}"; res.getWriter().write(json); }
✅ Spring @RestController
@GetMapping("/{id}") public ResponseEntity<User> getUser(@PathVariable Long id) { return service.findById(id) .map(ResponseEntity::ok) .orElse(ResponseEntity .notFound().build()); } // - No parsing URLs manually // - No JSON serialization (Jackson) // - No response headers // - No try/catch boilerplate // - Spring handles all of it
