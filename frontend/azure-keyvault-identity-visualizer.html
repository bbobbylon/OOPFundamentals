Azure Key Vault & Managed Identities — Secrets Without Secrets

The bootstrap problem — "the app needs a credential to fetch its credentials" — is solved by managed identities: Azure itself vouches for your compute, Entra mints it tokens, and Key Vault (secrets, keys, certificates) plus App Configuration (settings, feature flags) become readable with no stored credential anywhere.

🔐 What are Key Vault and managed identities — and how do they end the "password in a config file" era?

Every app has secrets: database passwords, API keys, signing certificates. The naive fix — put them in application.yml or environment variables — just moves the leak. Azure Key Vault is the hardened home for them, holding three object types: secrets (arbitrary strings like connection strings, versioned, soft-deletable), keys (RSA/EC cryptographic keys that never leave the vault — you send data in, the vault signs/encrypts/unwraps and sends results out, optionally backed by HSMs), and certificates (managed TLS certs with auto-renewal). But a vault only relocates the bootstrap problem: what credential does the app present to the vault? The answer is a managed identity (MI) — a service principal that Azure creates and binds to your compute resource (App Service, Function, VM, Container App). No password or certificate exists for it anywhere; instead, code running on that resource asks a local, non-routable metadata endpoint (IMDS, 169.254.169.254) for a token, and because only workloads on that VM/instance can reach that endpoint, Entra trusts the request and mints a token for the identity. System-assigned MIs live and die with one resource; user-assigned MIs are standalone resources you can share across several apps. Grant the MI a Key Vault RBAC role like Key Vault Secrets User, and the chain completes: compute proves itself to Entra, Entra vouches to the vault, the vault releases the secret — zero stored credentials end-to-end. Azure App Configuration rounds out the story for non-secret settings and feature flags, with Key Vault references so one config store presents both.

  • Key Vault holds 3 types — secrets (strings, versioned), keys (crypto ops in-vault, HSM option), certificates (auto-renewing TLS).
  • Managed identity = no credential at all — Azure binds a service principal to compute; IMDS hands tokens only to code on that resource.
  • System-assigned vs user-assigned — one-resource lifecycle vs standalone/shared. User-assigned survives resource deletion and pre-provisions RBAC.
  • Two authz models on the vault — modern Azure RBAC roles (use this: Key Vault Secrets User) vs legacy access policies. Pick one per vault.
  • Protection rails — soft delete (recoverable window, on by default) + purge protection (nothing can permanently destroy early); App Config for settings/flags with KV references for the secret ones.

The CLI happy path

# vault + a secret az keyvault create -n kv-shop-prod \ -g rg-shop-prod --enable-rbac-authorization az keyvault secret set --vault-name kv-shop-prod \ -n db-password --value 'S3cr3t!' # give the app's MI read access az webapp identity assign -n shop-api -g rg-shop-prod az role assignment create --role "Key Vault Secrets User" \ --assignee <mi-principal-id> --scope <vault-id>

AWS comparison

Key Vault ≈ Secrets Manager + KMS + ACM rolled into one resource. Managed identity ≈ an EC2 instance role / IRSA — same trick, the platform injects credentials via a metadata endpoint (AWS IMDS at the same 169.254.169.254 address!). App Configuration ≈ AppConfig / Parameter Store. Key Vault soft delete ≈ Secrets Manager's 7–30 day recovery window.

Spring Boot comparison

With spring-cloud-azure-starter-keyvault-secrets, the vault becomes a PropertySource: secret db-password simply is ${db-password} in your config, resolved at startup through the MI. Your .env.example + "config from environment variables" convention survives intact — the values just stop living on disk. Feature flags via App Config ≈ a hot-reloadable @ConfigurationProperties that someone else can flip in the portal.

CIAM in production: this page is your day job's trust fabric. The JWT signing keys your APIs validate against, the client secrets for Ping/Entra OAuth apps, the mTLS certs between services — all belong in Key Vault, fetched by managed identity. Better still: workloads that sign (issuing tokens, webhooks) should use Key Vault keys so the private key never exists in app memory — the vault signs on the app's behalf, and key rotation is a vault operation with zero deploys. Federated CI/CD (GitHub/ADO workload identity) is the same pattern one level up: even the pipeline holds no secret.

1. The identity chain: how compute proves itself with no credential

# what DefaultAzureCredential does inside an App Service — you never write this
GET http://169.254.169.254/metadata/identity/oauth2/token
  ?resource=https://vault.azure.net&api-version=2019-08-01
Metadata: true

# IMDS answers with an Entra token for the resource's managed identity
{ "access_token": "eyJ0eXAi…", "expires_in": "86400",
  "resource": "https://vault.azure.net", "token_type": "Bearer" }
The trust anchor is network locality. 169.254.169.254 is a link-local address that only code running on that compute instance can reach — it never routes across the internet or even the VNet. Azure's fabric knows which resource the call came from, so no proof-of-possession secret is needed. That is the entire trick: possession of the runtime environment is the credential. It also defines the threat model — anything achieving code execution on the box (SSRF reaching IMDS, a malicious dependency) can mint tokens, which is why MIs still get least-privilege roles, not Owner.

2. System-assigned vs user-assigned — pick by lifecycle

System-assignedUser-assigned
Lifecyclecreated/deleted with the resourcestandalone ARM resource, independent life
Sharingexactly one resourceattachable to many resources
RBAC preponly after the resource existspre-provision roles before any compute exists
Blue/green & scale-out fleetsevery instance re-needs role grantsone identity, N apps — grants survive redeploys
Default choiceone app, simple caseIaC pipelines, app fleets, slot swaps
Exam decoder: "identity must survive resource deletion / be shared across multiple apps / be granted permissions before deployment" → user-assigned. "Simplest option, tied to one resource" → system-assigned. Also know the two vault authorization models: Azure RBAC (recommended — normal role assignments like Key Vault Secrets User, Key Vault Crypto User, scoped as low as one vault) versus legacy access policies (per-vault ACLs granting get/list/set per object type). New vaults should use --enable-rbac-authorization.

3. Soft delete, purge protection, and the day someone deletes prod's vault

# soft delete is ON by default (90-day retention). Purge protection is opt-in — and one-way.
az keyvault update -n kv-shop-prod --enable-purge-protection true

# someone deletes a secret — it is recoverable, not gone
az keyvault secret delete --vault-name kv-shop-prod -n db-password
az keyvault secret recover --vault-name kv-shop-prod -n db-password

# with purge protection: even 'purge' is refused until retention expires
az keyvault secret purge --vault-name kv-shop-prod -n db-password
# ERROR: Operation "purge" is not allowed (purge protection enabled)
Soft delete makes deletion a two-phase act: a deleted secret/key/vault enters a recoverable state for 7–90 days, and purge (permanent destruction) is a separate, separately-permissioned operation. Purge protection goes further: purge is flatly refused until retention lapses — and once enabled it cannot be turned off, which is exactly what you want against ransomware that deletes-then-purges the keys your backups are encrypted with. Enable it on every production vault; the exam flags any answer where encryption keys can be irrecoverably destroyed.
