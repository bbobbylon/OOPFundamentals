Angular Zoneless Mode (v19+)

🚫 What is Zoneless Mode — and why is Zone.js the source of Angular's CD overhead?

Traditional Angular uses Zone.js — it monkey-patches every async API (setTimeout, promises, events, fetch…) and, after any of them completes, tells Angular "something might have changed — run change detection." Angular then walks the whole component tree checking every binding; 200 rows = 200 checks even if one changed. Zoneless mode (18+ stable, 17 experimental) removes Zone.js: components re-render only when you explicitly signal a change — via signals (signal()/computed()) or markForCheck() — so Angular re-renders precisely the templates that read what changed. That's fine-grained reactivity: smaller bundle, lower CPU, faster paint.

  • With Zone.js, one event → ApplicationRef.tick() → a full top-down tree check (100 components = 100 checks).
  • Zoneless: a signal.set() schedules a microtask and re-renders only the components that read that signal.
  • Enable with provideZonelessChangeDetection() (v20+, stable in v20.2) and drop zone.js from polyfills — on v21+ it is already the default and you add nothing.
  • Migrate gradually: OnPush everywhere → signal inputs + signal()/computed() state → enable zoneless.
  • RxJS still works — wrap streams with toSignal(obs$); Material and Router are zoneless-compatible in 18+.

Zone.js vs Zoneless

Zone.js: click → handler → tick() → walk the whole tree (100 components = 100 checks), plus the Zone.js bundle. Zoneless: click → handler → signal.set() → re-render only the components that read that signal (3 readers = 3 checks); the rest untouched, no Zone.js bundle.

Signals in zoneless

Template reads {{ userCount() }}; the class has userCount = signal(0) and adminCount = computed(() => users().filter(u => u.isAdmin).length). this.users.set(list) re-renders only the templates that read users()/adminCount().

Migration path

1) OnPush on all components; 2) replace @Input with input(), state with signal(), derived with computed(); 3) enable zoneless. RxJS components: wrap with toSignal(observable$). Material + Router already work in 18+.

In CIAM / Angular:a 500-row user table — with Zone.js + default CD, every click checks all 500 rows; with signals + zoneless, each row reads isSelected = computed(() => selectedId() === user().id) and clicking calls selectedUserId.set(id) → only the deselected + selected rows re-render, 498 untouched. A isRefreshing = signal(false) re-renders just the header during token refresh.

The problem

Angular has never known what you changed — so for a decade it re-checked everything, just in case.

The mechanism

Nothing renders until something says so.

  1. something notifies the scheduler — a signal read by a template changes, an async pipe emits, a template (click) fires, or you call markForCheck()the trigger
  2. that view and every ancestor up to the root get flagged dirtydirty path
  3. the scheduler queues one pass on a microtask — fifty writes in a loop still buy you exactly onecoalesced
  4. tick() walks from the root, but only refreshes views sitting on a dirty paththe pass
  5. changed bindings are written to the DOM; the other 196 components are never even readpaint

Step 1 is the migration. this.user.name = 'Ada' is a perfectly legal assignment that notifies nobody: no signal, no event binding, no error, no warning. Steps 2–5 never happen, so the value is right in memory and wrong on the screen.

OnPush was zoneless with training wheels, and nobody noticed. An OnPush component already said "re-check me only when an input reference changed, an event fired inside my template, or someone called markForCheck()" — which is, item for item, the zoneless notification list. The difference is that zone.js kept starting the pass anyway, so a component you had wired wrong still got swept up eventually and you never learned it was broken. Delete zone.js and that safety net goes with it: if your app is already OnPush-clean, going zoneless is a one-line provider swap; if it isn't, it's a bug hunt with no stack trace and no failing test. Which is exactly why the migration order is OnPush first, signals second, and provideZonelessChangeDetection() last — not the other way round.

You've gone zoneless. In a (click) handler you write this.label = 'Saved' and the screen updates — great. So you move that exact line into setTimeout(() => this.label = 'Saved', 1000). A second later, what do you see?

The assignment is identical; what differs is who told Angular. The click worked because Angular's own template listener notified the scheduler — what you wrote inside the handler was irrelevant. Inside setTimeout there is no listener and no zone.js patch, so nobody notifies anybody.

Right — and this is the migration bug every single team hits. label genuinely is 'Saved', the DOM still shows the old text, and the console is spotless. Make the write itself the notification: label = signal(''), then this.label.set('Saved').

NG0100 is the opposite failure — a value changing after a pass already read it. Here no pass runs at all, which is exactly why this is so nasty: a thrown error would have been a kindness.

Questions from the back row

I went zoneless and my plain this.count++ in a click handler still updates the view. Did I imagine the whole problem?

No — you got lucky, structurally. Angular registers the listener for every template (click), and that listener notifies the scheduler on its own. A pass runs, re-reads your template, and finds the new number. Move the same line into a setTimeout, a WebSocket onmessage, or a third-party promise, and there is no notifier at all. The click was doing you a favour you cannot rely on.

So are signals actually mandatory in zoneless mode?

No. Anything on the notification list works: an async pipe emitting, a template or host event listener firing, ChangeDetectorRef.markForCheck(), ComponentRef.setInput(). Signals just mean you can never forget to notify, because the write and the notification are the same keystroke. A mutated plain object is the one thing on nobody's list.

Zoneless is on. Do I still bother setting OnPush everywhere?

Yes. Zoneless removes the trigger, not the traversal. When some other part of the app schedules a pass, tick() still walks from the root, and a Default-strategy component in its path is checked every single time. OnPush is what makes the walk skip you. That is also why v19+ scaffolds new components as OnPush and stops pretending it's an optimisation.

What is Zone.js — and why is it being removed?

  
Zone.js is a library that monkey-patches every async browser API — setTimeout, Promise.then, addEventListener, fetch, and more — to intercept when an async operation completes. Angular uses this as a trigger to run change detection across the entire component tree.


  

    

      
Zone.js patch layer

      
Monkey-patches setTimeout, Promise, fetch, addEventListener. Creates an execution "zone" that fires notifications when tasks enter/exit.

    

    

      
NgZone (Angular)

      
Angular's wrapper around the NgZone. Listens for onMicrotaskEmpty — fires after every microtask queue flush. This is when CD triggers.

    

    

      
Change Detection loop

      
Angular walks the entire component tree top-down, comparing current values to previous snapshot. Renders updated bindings to DOM.

    

    

      
The cost

      
Runs on EVERY async event — a mousemove, a setInterval tick, any Promise. Large trees = expensive checks. Plus ~56KB bundle just for zone.js.

    

  


  
The problem with Zone.js

  

    

      
What Zone.js triggers CD on

      
    
        
  • Every click, keyup, mousemove
    • 
        
  • Every setTimeout / setInterval
    • 
        
  • Every Promise resolution
    • 
        
  • Every HTTP response
    • 
        
  • Every WebSocket message
    • 
        
  • Any third-party library async code
    • 
      

      
Angular literally cannot tell if the event changed anything. It always checks.

    

    

      
What Zoneless triggers CD on

      
    
        
  • Signal writes ONLY
    • 
        
  • Nothing else causes a check
    • 
        
  • Angular knows exactly WHICH signals changed
    • 
        
  • Only components that read those signals re-render
    • 
        
  • No surprise checks from third-party timers
    • 
        
  • Predictable, auditable render graph
    • 
      

    

  


  

    Zone.js bundle cost: zone.js itself is ~56KB (minified+gzipped: ~18KB). More importantly, it parses and patches the entire async API surface at startup — adding latency even on fast devices. Every Angular app has paid this cost since v2. Zoneless eliminates it entirely.

// The old world (zone-based) — triggered on anything async:
setTimeout(() => {
  // Zone.js intercepts this. When it finishes, Angular runs CD.
  // Even if you didn't change any component state. Wasteful.
  console.log('hello');
}, 1000);

// The new world (zoneless) — only signals trigger CD:
setTimeout(() => {
  // Angular does NOT intercept this. No CD runs.
  // If you need state to update, write to a signal:
  this.message.set('updated!');  // THIS triggers CD, only for components reading it
}, 1000);







  
Setting up Zoneless mode

  
Three changes are needed to go fully zoneless in an existing Angular project.


  
Step 1 — Replace the zone provider in app.config.ts

  

    
// app.config.ts — Angular 19+
import { ApplicationConfig, provideZonelessChangeDetection } from '@angular/core';
import { provideRouter } from '@angular/router';

export const appConfig: ApplicationConfig = {
  providers: [
    // ❌ Remove this:
    // provideZoneChangeDetection({ eventCoalescing: true }),

    // ✅ Add this instead:
    provideZonelessChangeDetection(),

    provideRouter(routes),
  ]
};

    

      The name changed, and the old one is gone. Angular 18 and 19 called this provideExperimentalZonelessChangeDetection(). v20 renamed it to provideZonelessChangeDetection() and marked it stable in v20.2. They do not both exist any more — the experimental name was deprecated in v20 and removed, so copying it out of a 2024 blog post gives you TS2305: Module '@angular/core' has no exported member. And on v21+ you need neither: zoneless is the default, so the only provider you might reach for is provideZoneChangeDetection(), to go back.

Step 4 — Set ChangeDetectionStrategy.OnPush on every component

  

    
In zoneless mode, OnPush is effectively the default — components only re-check when their signals change. But you should explicitly set it for clarity and for lint rules.

    
import { Component, ChangeDetectionStrategy, signal } from '@angular/core';

@Component({
  selector: 'app-counter',
  standalone: true,
  changeDetection: ChangeDetectionStrategy.OnPush,   // ← required for zoneless
  template: `
    <button (click)="increment()">+</button>
    <span>{{ count() }}</span>
  `
})
export class CounterComponent {
  count = signal(0);
  increment() { this.count.update(n => n + 1); }
}

    

      In Angular 19+, new projects scaffold with OnPush as the default when you choose zoneless. The CLI sets this automatically. For existing projects, use ng update plus the schematics to migrate automatically.

The three primitives that replace zone ticks

  

    
PrimitiveRoleTriggers re-render when

    
      
signal(initialValue)Writable state source.set() or .update() changes the value

// Complete zoneless component — signal drives everything
@Component({
  selector: 'app-user-card',
  standalone: true,
  changeDetection: ChangeDetectionStrategy.OnPush,
  template: `
    <div class="card">
      <h2>{{ user().name }}</h2>
      <p>Score: {{ formattedScore() }}</p>
      <p [class.active]="isActive()">{{ statusLabel() }}</p>
      <button (click)="addPoint()">+1 Point</button>
    </div>
  `
})
export class UserCardComponent {
  // Signal input (v17+)
  user = input.required<User>();

  // Local writable state
  bonusPoints = signal(0);

  // Derived — recomputes when user() or bonusPoints() changes
  totalScore  = computed(() => this.user().score + this.bonusPoints());
  formattedScore = computed(() => this.totalScore().toLocaleString());
  isActive    = computed(() => this.totalScore() > 1000);
  statusLabel = computed(() => this.isActive() ? 'Active' : 'Inactive');

  addPoint() { this.bonusPoints.update(n => n + 1); }
  // When addPoint() runs: bonusPoints changes → totalScore recomputes → formattedScore
  // recomputes → isActive recomputes → statusLabel recomputes → Angular
  // schedules a re-render ONLY for this component. NavBar? Untouched.
}

Third-party library compatibility

  

    The main migration risk. Libraries that use timers, Promises, or callbacks internally to update state may stop working correctly in zoneless mode. Common offenders: drag-drop libraries, rich text editors, chart libraries, date pickers that use native inputs.
  


  
// Pattern for wrapping third-party library callbacks:
import { NgZone, inject } from '@angular/core';

export class ChartComponent {
  private ngZone = inject(NgZone);
  selection = signal<DataPoint | null>(null);

  ngAfterViewInit() {
    // Third-party chart lib uses its own callbacks
    this.chart = new Chart(canvas, {
      onClick: (dataPoint) => {
        // Run inside Angular zone, OR write to signal:
        this.ngZone.run(() => {
          this.selection.set(dataPoint);  // signal write triggers CD
        });
        // OR just write to signal (runs ngZone.run internally in v19+):
        // this.selection.set(dataPoint);
      }
    });
  }
}


  

    Angular 19 improvement: in v19, signal writes automatically schedule a CD check even outside NgZone. So in many cases, you can simply write to a signal in a third-party callback without ngZone.run(). The old wrapper is only needed if the library itself needs to detect that CD has run (rare).
  


  
Testing in zoneless mode

  

    
// TestBed setup for zoneless components
import { TestBed } from '@angular/core/testing';
import { provideZonelessChangeDetection } from '@angular/core';

describe('CounterComponent', () => {
  beforeEach(async () => {
    await TestBed.configureTestingModule({
      imports: [CounterComponent],

    }).compileComponents();
  });

  it('increments on click', async () => {
    const fixture = TestBed.createComponent(CounterComponent);
    fixture.detectChanges();
    const btn = fixture.nativeElement.querySelector('button');
    btn.click();
    await fixture.whenStable();  // ← waits for CD to settle
    fixture.detectChanges();
    expect(fixture.nativeElement.querySelector('span').textContent).toBe('1');
  });
});
