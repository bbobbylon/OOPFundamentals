Collaboration & Pull Requests

The full PR workflow, resolving merge conflicts, git stash for context switching, and cherry-pick for surgical moves.

1 — Pull Request Workflow

Click Next Step to walk through a full PR lifecycle:

1

Create Feature Branch

git checkout -b feature/user-auth main
Branch from the latest main, never from a stale local copy. Pull first: git pull origin main

2

Make Commits

Write the feature in small, focused commits. Each commit should compile and pass tests.
git add src/auth/ && git commit -m "feat: add JWT authentication filter"

3

Push Branch

git push -u origin feature/user-auth
-u sets the upstream, so future git push / git pull know which remote branch to use.

4

Open Pull Request

On GitHub/GitLab: click "New Pull Request". Write a clear description: what changed, why, how to test, screenshots if UI.
Link to the issue: Closes #42 in the description auto-closes the issue on merge.

5

Code Review

Reviewers comment, ask questions, request changes. You push additional commits to the SAME branch to address feedback — they automatically appear in the PR.
Respond to every comment: resolve it or discuss until aligned.

6

CI Passes, PR Approved

CI runs tests, linting, security scans. All green ✓. At least one reviewer approves.
Most teams require: 1-2 approvals + all CI checks green before merging.

7

Merge & Clean Up

Choose merge strategy: Squash and merge (one clean commit on main), Rebase and merge (linear history), or Merge commit (preserves branch history).
Delete the feature branch — GitHub has a "Delete branch" button. Clean up locally: git branch -d feature/user-auth

2 — Resolving Merge Conflicts

Both Alice and Bob edited the same function. Git marks the conflict — you decide what to keep:

❌ Conflicted file
<<<<<<< HEAD (yours) public String getGreeting(String name) { return "Hello, " + name + "!"; } ======= public String getGreeting(String name, Locale locale) { return i18n.getMessage("greeting", name, locale); } >>>>>>> feature/i18n (theirs)
✅ Resolved file
// Kept their signature (i18n support) // Added null-safe locale fallback from our branch public String getGreeting(String name, Locale locale) { if (locale == null) locale = Locale.ENGLISH; return i18n.getMessage("greeting", name, locale); }
# After editing the file to resolve the conflict: git add src/service/GreetingService.java git commit -m "fix: resolve merge conflict in getGreeting" # Or if in the middle of a merge: git merge --continue
Conflict resolution tips:
• Use a proper merge tool (VS Code, IntelliJ, vimdiff: git mergetool)
• Understand BOTH changes before deciding — don't just pick yours blindly
• After resolving: test before committing. Conflicts can break logic even when the syntax is fixed
• git merge --abort if you want to start over

3 — git stash — Context Switching

Urgent bug comes in while you're halfway through a feature. Stash your work-in-progress:

Working Directory

● UserService.java (modified)
● UserDto.java (modified)
✓ Clean

git stash list

empty

Current Branch

feature/user-auth
git stash # save WIP, restore clean working tree git stash push -m "WIP: user auth feature" # stash with a label git stash list # see all stashes: stash@{0}, stash@{1}... git stash pop # restore latest stash + remove it from stash list git stash apply stash@{1} # apply a specific stash (keeps it in list) git stash drop stash@{0} # delete a stash entry

4 — git cherry-pick

What it does

Takes one specific commit from any branch and applies its changes to your current branch. Creates a new commit with the same changes (different hash).

Use for: "That security fix was committed to the feature branch — get it onto main without merging the whole feature."

git cherry-pick abc1234
git cherry-pick abc1234 def5678 (multiple commits)
git cherry-pick feature/auth~3..feature/auth (range)

When NOT to use it

• When you want ALL changes from a branch — use merge instead
• For long chains of commits — merge or rebase is cleaner
• When commits have complex interdependencies — cherry-pick only applies the diff, missing context can cause failures

Watch out: cherry-picking the same change multiple times (once via cherry-pick, once via merge) can create duplicate commits or conflicts.

# Scenario: fix committed to feature branch, need it on main urgently git log feature/user-auth --oneline abc1234 fix: prevent SQL injection in user search ← want this def5678 feat: add user search endpoint ghi9012 feat: add user auth middleware git checkout main git cherry-pick abc1234 [main a1b2c3d] fix: prevent SQL injection in user search # New commit a1b2c3d on main with same changes as abc1234
