Collaboration & Pull Requests

The full PR workflow, resolving merge conflicts, git stash for context switching, and cherry-pick for surgical moves.

🔀 What is the Pull Request workflow — and how do merge conflicts actually work?

Collaboration in Git centers on the Pull Request (PR) — the mechanism for proposing changes, getting feedback, and integrating code safely. A PR is NOT a Git concept — it's a platform feature (GitHub, Azure DevOps, GitLab). But it's the core unit of team collaboration. PR lifecycle: create feature branch → commit changes → push branch → open PR (comparing feature branch to main) → automated CI runs tests → reviewers leave comments → author addresses feedback → approvals collected → merge. In ADO (Azure DevOps): branch policies enforce this — required reviewers, CI build required, work item linked. Merge conflict: happens when TWO branches modified the SAME lines in the same file in different ways. Git can't decide which version is correct — so it puts BOTH versions in the file with conflict markers and asks you to decide. <<<< HEAD = your current branch's version. ==== = divider. >>>> feature/branch = incoming branch's version. Resolution: edit the file to the correct final state (keeping relevant parts of both, or one over the other), then git add + git commit. git stash: a temporary shelf for uncommitted changes. Switch to fix a bug, stash your in-progress work: git stash push -m "wip: entra provisioning". Come back later: git stash pop. Multiple stashes: git stash list, git stash apply stash@{1}. cherry-pick: take a specific commit from one branch and apply it to another. Use case: a hotfix was committed to a feature branch — you need that fix on main NOW without merging the entire feature branch. git cherry-pick a72dd56 — applies commit a72dd56 to the current branch. Creates a new commit with the same changes but a different SHA. Code review best practices: small PRs (<400 lines changed) are reviewed faster and more carefully. Big PRs get rubber-stamped because reviewers can't hold the context. PR description: what does it do, why, how to test it.

Merge conflict resolution

# Create conflict: two branches modify same line # main has: return pingClient.getUser(id); # feature has: return entraClient.getUser(id); git switch main git merge feature/entra-auth # CONFLICT (content): src/AuthService.java # File now contains: <<<<<<< HEAD return pingClient.getUser(id); ======= return entraClient.getUser(id); >>>>>>> feature/entra-auth # Resolve (keep both with routing logic): IdpClient client = user.idpType().equals("PING") ? pingClient : entraClient; return client.getUser(id); git add src/AuthService.java git commit # merge commit created # IntelliJ merge tool: much nicer UI # 3-pane view: yours | merged | theirs

CIAM team collaboration: PR template in ADO (.azuredevops/pull_request_template.md): sections for "What changed", "Why", "Testing done", "Screenshots (for UI changes)", "Checklist (security review, migration tested, feature flag)". Conflict prevention: pull from main frequently (git pull --rebase origin main on your feature branch) — small frequent merges avoid big conflicts. When conflicts DO happen in generated code (like Flyway migration scripts numbered V001__init.sql, V002__add_sessions.sql): two devs both created V003. Resolution: one renumbers to V004. Team convention: coordinate migration numbers in a team channel. Large feature in progress (weeks)? Use feature flags — merge to main behind a disabled flag, enable it when ready. Avoids long-lived branches. ADO work item linking: every PR linked to a work item (story/bug) in the board — traceability from business requirement → code change → deployment.

or, why git branch -d calls your already-merged branch a liar

The problem

GitHub's badge says "Merged." Git looks at the same branch and refuses to believe it.

"not fully merged" — on a branch that's already merged

You open a PR for feature/session-refresh, it gets reviewed, and you click "Squash and merge" on GitHub. The badge flips purple: Merged. You do exactly what the cleanup step on this page teaches — git checkout main && git pull && git branch -d feature/session-refresh.

Git refuses: error: The branch 'feature/session-refresh' is not fully merged. Nothing is actually wrong. The code is on main, right now, verifiably, and Git is still insisting it isn't merged.

PR shows Merged on GitHub ✓ git pull on main brought down the new code ✓ the feature branch's own commit history was never touched ⚠

-d checks whether your branch's TIP COMMIT is an ancestor of main — a squash merge never makes that true, no matter how completely the code landed.

Know which delete you actually mean
Confirm on GitHub/ADO that the PR genuinely landed ↓ the "Merged" badge is the platform's record, not Git's — the two track different facts Use git branch -D (capital D), deliberately, once you've confirmed that ↓ capital -D skips the ancestry check entirely — you're telling Git "this looks unmerged to you, delete it anyway" Never reach for capital -D as a reflex ↓ on a branch that was merged normally (not squashed), a refused lowercase -d is a real warning that commits would be lost — capital D throws that warning away too
The one-sentence rule. git branch -d never asks GitHub or ADO whether your PR merged — it asks Git's own commit graph whether your branch's tip is an ancestor of the branch you're standing on, and a squash merge manufactures a brand-new commit that is never an ancestor of anything, so the safe delete fails on every squash-merged branch, permanently, by design.
Squash merge keeps your CODE but throws away the one thing git branch -d actually checks — whether your branch's own history is an ancestor of main. After a squash, it never is.
You

GitHub says this branch merged twenty minutes ago. Why won't git delete it?

Git's branch tracker, personified

Because I don't read GitHub's UI. I check one thing: is your branch's last commit an ancestor of main? A squash merge gave main a brand-new commit — a repackaged copy of your diff, not your commits. As far as I'm concerned, your branch was never absorbed.

You

So every squash-merged branch is going to make you say this?

Git's branch tracker, personified

Every single one. It isn't a bug you tripped over — it's the standing rule for any team that squash-merges.

The mechanism

Follow one PR from "approved" to "phantom unmerged branch" and watch exactly where the ancestry breaks.

  1. You commit six times on feature/session-refresh, each with its own SHA6 commits
  2. The PR opens comparing that branch against main, gets reviewed, gets approvedapproved
  3. You click "Squash and merge" — GitHub takes the combined diff of all six commitssquash
  4. GitHub creates ONE new commit on main, whose only parent is main's old tip — none of your six commits are its ancestorsnew SHA, no lineage
  5. git pull on main brings that one new commit down — the code is now present and correctcode arrived
  6. git branch -d feature/session-refresh walks the ancestry graph looking for your branch's tip among main's ancestors, finds nothing, and refusesthe refusal

Sit with step 4 — it's where everything downstream gets decided, and it's invisible from where you're standing. GitHub shows you a diff, not a graph, so you see the content matches your branch and reasonably assume Git will agree. But Git's later ancestry check was never comparing content — it only cares whether your exact commits, by SHA, are reachable from main. Squash-and-merge guarantees they never will be, on this branch or any other one your team ever squashes.

everything that reacts ↓
PR badge flips to "Merged" (purple) teammates' next git pull origin main shows the new code your local branch's ancestry in Git's object graph — completely unchanged, still not reachable from main

Two of these three reactions are about what people and tools OBSERVE happened. The third is about what Git can PROVE happened by walking commit parents — and a squash merge never gives it anything to walk. That gap is the entire gotcha in one picture.

Your team squash-merges every PR. You just ran git checkout main && git pull && git branch -d feature/rate-limiting right after GitHub marked the PR "Merged," and Git refused with "not fully merged." What's actually true here?

Correct. Squash merge structurally guarantees your branch's tip is never an ancestor of main, so -d's ancestry check fails every time — regardless of whether the code shipped cleanly, which here it did.

A failed git pull reports its own distinct error (network, conflict, diverged history) — it doesn't quietly leave you on stale code without telling you. This refusal comes from a completely different check, run entirely locally against the commit graph.

GitHub's "Merged" badge reliably reflects what happened on the platform side. The mismatch here isn't GitHub lying — it's Git's local ancestry bookkeeping using a different definition of "merged" than the one your eyes are reading on the PR page.

Where you have seen this before

"Two systems agree something happened, but only one of them can actually prove it by walking its own records" shows up far outside Git.

ADO auto-closing a linked work item

Azure DevOps closes a linked work item the instant a PR completes — but if that merge sits behind a disabled feature flag waiting for next week's deployment window, the work item says "Closed" days before a single real CIAM user has the code running against them. One system's bookkeeping outran the other's actual state.

"marked done" and "actually true" are tracked by two different systems

Soft-deleted rows without a filter

Your app sets deleted_at on a row and calls it deleted. A reporting query that forgot to add WHERE deleted_at IS NULL still finds it, joins on it, and counts it. The application's definition of "gone" and the database's definition of "still a row" disagree until every single consumer applies the same rule.

"deleted" by convention, not deleted by the thing doing the checking

DNS propagation after a record change

You update a DNS record and your own machine resolves the new IP instantly. A user on another continent hits a resolver that cached the old answer and will keep serving it for the record's full TTL. The authoritative source is updated; every downstream cache is still checking its own stale copy of the truth.

"changed at the source" and "reflected everywhere that checks" are not the same moment

The one new sentence this block adds: git branch -d checks a commit-ancestry fact in Git's own graph, not a platform's "Merged" badge — squash merge breaks that check on every branch it touches, forever, and the fix is a deliberate -D, not doubt about whether your code is safe.

1 — Pull Request Workflow

Click Next Step to walk through a full PR lifecycle:

1

Create Feature Branch

git checkout -b feature/user-auth main
Branch from the latest main, never from a stale local copy. Pull first: git pull origin main

2

Make Commits

Write the feature in small, focused commits. Each commit should compile and pass tests.
git add src/auth/ && git commit -m "feat: add JWT authentication filter"

3

Push Branch

git push -u origin feature/user-auth
-u sets the upstream, so future git push / git pull know which remote branch to use.

4

Open Pull Request

On GitHub/GitLab: click "New Pull Request". Write a clear description: what changed, why, how to test, screenshots if UI.
Link to the issue: Closes #42 in the description auto-closes the issue on merge.

5

Code Review

Reviewers comment, ask questions, request changes. You push additional commits to the SAME branch to address feedback — they automatically appear in the PR.
Respond to every comment: resolve it or discuss until aligned.

6

CI Passes, PR Approved

CI runs tests, linting, security scans. All green ✓. At least one reviewer approves.
Most teams require: 1-2 approvals + all CI checks green before merging.

7

Merge & Clean Up

Choose merge strategy: Squash and merge (one clean commit on main), Rebase and merge (linear history), or Merge commit (preserves branch history).
Delete the feature branch — GitHub has a "Delete branch" button. Clean up locally: git branch -d feature/user-auth

2 — Resolving Merge Conflicts

Both Alice and Bob edited the same function. Git marks the conflict — you decide what to keep:

❌ Conflicted file
<<<<<<< HEAD (yours) public String getGreeting(String name) { return "Hello, " + name + "!"; } ======= public String getGreeting(String name, Locale locale) { return i18n.getMessage("greeting", name, locale); } >>>>>>> feature/i18n (theirs)
✅ Resolved file
// Kept their signature (i18n support) // Added null-safe locale fallback from our branch public String getGreeting(String name, Locale locale) { if (locale == null) locale = Locale.ENGLISH; return i18n.getMessage("greeting", name, locale); }
# After editing the file to resolve the conflict: git add src/service/GreetingService.java git commit -m "fix: resolve merge conflict in getGreeting" # Or if in the middle of a merge: git merge --continue
Conflict resolution tips:
• Use a proper merge tool (VS Code, IntelliJ, vimdiff: git mergetool)
• Understand BOTH changes before deciding — don't just pick yours blindly
• After resolving: test before committing. Conflicts can break logic even when the syntax is fixed
• git merge --abort if you want to start over

4 — git cherry-pick

What it does

Takes one specific commit from any branch and applies its changes to your current branch. Creates a new commit with the same changes (different hash).

Use for: "That security fix was committed to the feature branch — get it onto main without merging the whole feature."

git cherry-pick abc1234
git cherry-pick abc1234 def5678 (multiple commits)
git cherry-pick feature/auth~3..feature/auth (range)

When NOT to use it

• When you want ALL changes from a branch — use merge instead
• For long chains of commits — merge or rebase is cleaner
• When commits have complex interdependencies — cherry-pick only applies the diff, missing context can cause failures

Watch out: cherry-picking the same change multiple times (once via cherry-pick, once via merge) can create duplicate commits or conflicts.

# Scenario: fix committed to feature branch, need it on main urgently git log feature/user-auth --oneline abc1234 fix: prevent SQL injection in user search ← want this def5678 feat: add user search endpoint ghi9012 feat: add user auth middleware git checkout main git cherry-pick abc1234 [main a1b2c3d] fix: prevent SQL injection in user search # New commit a1b2c3d on main with same changes as abc1234
