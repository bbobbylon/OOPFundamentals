AI Coding Assistants — The Landscape

Copilot, Cursor, Windsurf, Claude Code, Aider, Amazon Q, JetBrains AI — dozens of names, but they all sit somewhere on just two axes: how much they see, and how much they're trusted to do without asking.

🗺️ What separates these tools from each other?

Every AI coding tool on the market today is a thin harness wrapped around a small number of the same underlying language models — the differences you actually feel as a developer come almost entirely from two independent design choices the harness makes, not from the model itself. The first axis is context: does the tool see only the current file and open tabs, or does it actively search the whole repository — via embeddings, via live grep/read tool calls, or both — to find the files a change actually needs? The second axis is autonomy: does it merely suggest text for a human to accept keystroke-by-keystroke, does it propose a multi-file diff that stops for review, or does it hold the pen itself — editing files, running the build, reading the failure, and iterating — before ever coming back to a human? Plotting any given tool on these two axes explains almost everything about how it feels to use: a narrow-context, low-autonomy tool (classic autocomplete) is fast and safe but blind to anything outside the current file; a wide-context, high-autonomy tool (a terminal-native coding agent) can restructure a feature across a dozen files and prove it still passes tests, but it needs real guardrails — plan-mode gates, hooks, permission scopes — precisely because its blast radius is so much larger.

  • Context axis — open-file-only → explicit @-references → whole-repo semantic index → live tool calls (grep/read) that see the actual current file, not a stale embedding.
  • Autonomy axis — ghost-text suggestion → chat you paste from → agent that edits and stops at a diff → agent that edits, runs the build/tests itself, and iterates until it's green.
  • Same models, different harnesses — the reasoning model behind an IDE's inline suggestions is often a close relative of the one behind its "agent mode"; the harness (what it's allowed to see and do) is what changes.
  • Editor-embedded vs CLI-native — IDE-integrated tools (Copilot, Cursor, Windsurf) live inside your editor's UI; terminal-native agents (Claude Code, Aider) run as a CLI process with no GUI of their own, which is exactly what lets them run arbitrary shell commands as a first-class tool.

Higher autonomy ≠ better

A one-line typo fix is faster with inline autocomplete than with a full agent loop. Autonomy is a dial to match to the task's size and risk, not a ladder where higher is always the goal.

Context quality beats context size

A semantic index built once can drift stale as files change; a tool that greps and reads the live file at request time always sees the current truth, even if it "sees less" of the repo per request.

The instructions-file convention is converging

.github/copilot-instructions.md, CLAUDE.md, and .cursor/rules all do the same job for their own tool. AGENTS.md is the emerging attempt at one file several tools read.

Choosing a tool for CIAM work: a task like "add a permission-gated endpoint that follows this repo's ResponseEntity<HttpResponse> + NamedParameterJdbcTemplate conventions" is exactly the kind of multi-file, convention-heavy change where context and autonomy both matter — a narrow-context autocomplete tool won't know the pattern exists three files away, and a low-autonomy chat tool leaves you to wire four files together by hand. It's also exactly the kind of change worth a plan-first, verify-before-reporting agent rather than one that edits and walks away.

or, the one library an AI coding assistant is most likely to get wrong: the AI SDK itself

The problem

Ask an AI assistant for code that calls itself — an LLM API — and there's a real chance it hands you syntax that was correct the day its training data was frozen and has been broken since.

openai.ChatCompletion.create() — perfectly correct, several years ago

You ask an AI coding assistant to "write a Python function that calls the OpenAI chat API." It responds instantly and fluently with import openai; openai.ChatCompletion.create(model="gpt-3.5-turbo", messages=[...]) — clean syntax, sensible parameter names, no hedging.

openai-python v1.0 (released November 2023) restructured the whole library around a client object — the correct call became client = OpenAI(); client.chat.completions.create(...). Any environment with the current package installed raises AttributeError: module 'openai' has no attribute 'ChatCompletion' on that exact snippet. The assistant wasn't guessing badly — it was reciting the correct answer for a library version that no longer exists in most active projects.

the code is syntactically valid Python ✓ it matches real documentation — from before a specific release date ✓ it throws AttributeError on any currently-installed openai package ⚠

The model wasn't wrong about anything it learned — it just learned before the library changed underneath it.

Treat the assistant's library knowledge as dated, not authoritative
Tell the assistant which major version you're on (openai==1.x) instead of leaving it to guess ↓ a version number is a fact it can condition on, even if its internal knowledge of that version is thin Paste in the actual current method signature or a doc snippet when the API is young or fast-moving ↓ grounding beats memory — a live snippet you provide overrides guessed syntax from training data every time Run the code and read the real error before assuming either the model or the library is "wrong" ↓ an AttributeError naming a renamed method is a strong, specific signal, not a mystery
The one-sentence rule. A model's knowledge of any library is frozen at its training cutoff, so for fast-moving SDKs — and AI SDKs are some of the fastest-moving software on earth right now — the syntax it recites most confidently is exactly as likely to be stale as the syntax it hedges on, because fluency was never a signal of recency.
An AI assistant answering a library question isn't checking a live manual — it's reciting the most likely-looking thing from a fixed moment in the past. Confidence and currency are two completely different axes.

The mechanism

Walk through why a training-cutoff freeze turns into confidently wrong code, using the real openai v1.0 migration as the timeline.

  1. The model's training data is collected up to some cutoff datethe freeze
  2. At that point, openai.ChatCompletion.create() is the current, heavily-documented patterntrue at the time
  3. The model learns this pattern as extremely high-probability, boring-correct codehigh confidence
  4. openai-python ships v1.0 — a deliberate breaking change to a client-object APIthe world moves
  5. The model's weights don't change; it keeps completing the old pattern with the same fluency as beforefrozen knowledge
  6. Every fluent repetition of the old pattern is now silently wrong on any current installconfidence outlives correctness

The step that matters most is #5 — nothing about HOW confidently the model writes the old pattern changes after the library does. Fluency was never wired to "this is still true today"; it only ever measured "this matched my training data extremely well." A model has no built-in mechanism to notice the world moved on without being told.

All three causes funnel to the identical symptom because from inside the model's completion process, "the pattern I learned" and "the pattern that's still correct today" are indistinguishable — there's no internal flag that lights up differently for a renamed method versus a newly-required parameter. They all just look like the next most likely tokens.

An AI assistant confidently writes openai.ChatCompletion.create(...) for you. You run it against a freshly-installed openai package and get AttributeError: module 'openai' has no attribute 'ChatCompletion'. What does this error most likely tell you?

ChatCompletion.create() was real, extensively documented syntax — it just belonged to a version of the library that predates the v1.0 rewrite. This isn't a fabricated API, it's a stale one.

Correct. openai-python v1.0 (Nov 2023) restructured the whole library around a client object, retiring the old top-level openai.ChatCompletion interface — a model trained before that release recites the old, once-correct pattern with full confidence.

A clean, well-documented AttributeError naming a specific missing attribute is a strong signal of an API that changed, not a broken install — reinstalling the same current version would reproduce the identical error.

Where you have seen this before

Confidently repeating something that used to be true is a failure mode that shows up anywhere knowledge gets frozen at one point in time.

A cached IdP metadata document after a certificate rotation

Ping or Entra federation metadata (signing certs, endpoints) gets fetched once and cached; if the identity provider rotates its signing certificate and your service keeps trusting the cached copy, token validation keeps "confidently" succeeding right up until it confidently fails — the cache doesn't know it's stale until something forces a refetch.

the compressed lesson: a cache doesn't know the source of truth moved on

A tutorial's @EnableGlobalMethodSecurity after Spring Security 6 renamed it

Spring Security 6 replaced @EnableGlobalMethodSecurity with @EnableMethodSecurity. Code written against the old annotation still compiles and reads exactly as confidently as the current one — the compiler only complains once you're actually on the newer major version, same as the assistant only turning out wrong once you run its code.

the compressed lesson: old-but-fluent syntax can survive right up until the version boundary you didn't check

A browser serving a stale CSS file after a deploy

The browser has no idea the server shipped new styles; it keeps confidently rendering the old, once-correct file until a cache-bust or hard refresh forces it to notice the world moved on.

the compressed lesson: nothing forces a stale copy to re-check itself without an explicit signal

A few things worth knowing

  • Embeddings can go stale — a repo-aware IDE agent's semantic index is usually built (or incrementally updated) on a schedule; if you just renamed a method in another editor tab it hasn't reindexed yet, it can propose a call to a name that no longer exists. A live grep/read loop doesn't have this failure mode because it re-reads the file at request time.
  • "Agent mode" isn't one thing — an IDE agent that stops at a diff and a CLI agent that runs your test suite before replying are both marketed as "agentic," but only one of them has actually verified its own claim before you see it.
  • The steering file matters more as autonomy rises — an inline suggestion that ignores your conventions costs you one keystroke to reject; a CLI agent that ignores them can produce a dozen wrong files before you notice, which is exactly why CLAUDE.md / copilot-instructions.md / AGENTS.md become load-bearing at the high-autonomy end of this spectrum.
