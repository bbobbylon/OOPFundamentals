TypeScript Decorators — Legacy & TC39 Stage 3

Decorators are annotations that wrap or modify classes, methods, properties, and parameters. TypeScript supports two incompatible decorator systems: the legacy experimentalDecorators system (used by Angular, NestJS, TypeORM) and the newer TC39 Stage 3 system (TypeScript 5.0+, the JavaScript standard path).

🎀 What is a decorator? What problem does it solve?

A decorator is a function that wraps another piece of code — a class, method, or property — and adds behavior without modifying the original. Instead of repeating the same logging, retry, or validation in every method, you write it once and apply it with a single @ annotation — the same idea as Python decorators or Java annotations + AOP.

  • Cross-cutting behavior, applied declaratively. Write once, attach with @.
  • Targets classes, methods, properties, parameters — each has a different signature.
  • Two incompatible systems exist — legacy (experimentalDecorators) vs TC39 Stage 3; never mix them.
  • Order matters: factories evaluate top→down, decorators apply bottom→up.

Without vs with a decorator

// repeated everywhere:
async getUser(){ try { return await api.get('/user') } catch { /*retry 3x*/ } }
becomes @Retry(3) async getUser(){ return await api.get('/user') } — the retry lives in one place.

Two decorator systems

The legacy system (experimentalDecorators: true) is what Angular, NestJS, and TypeORM use today; the TC39 Stage 3 system (TS 5.0+) is the future standard. They look alike but have totally different signatures — never mix them.

Angular / NestJS / CIAM: @Component, @Injectable, @Input, @HostListener, and NestJS @Get/@Post are all legacy decorators — Angular reads them as metadata for DI and the template compiler. Execution order (evaluate top→down, apply bottom→up) explains why @Component fires last.

The problem

You cannot debug a spell.

Treating @ as magic the compiler does

Most people read @Injectable() the way they read public — a keyword, part of the language, handled by something that knows better. Then one day the build config changes, or a colleague swaps a constructor type for an interface, and DI stops working with an error that names a class you never wrote.

NullInjectorError: No provider for Object ⚠ "it worked before I upgraded TypeScript" ⚠ Decorators are not valid here ⚠ @Injectable() has empty parens… why? ⚠ works in one file, dies in the next ⚠

Every one of those is the same bug: you have no runtime model, so you cannot predict what the annotation actually did. And it did something very ordinary.

The mechanism

Constructor injection is a six-link chain, and every link can be unplugged.

  1. tsconfig: "experimentalDecorators": truewithout it the @ is a syntax error, not a feature
  2. tsconfig: "emitDecoratorMetadata": truethe compiler now writes types into the output
  3. TS emits design:paramtypes = [HttpClient, TokenStore]the note on the side — real runtime values
  4. import 'reflect-metadata' once at the app entrysupplies Reflect.getMetadata; nothing stores it otherwise
  5. the @Injectable() decorator runs at import timeregisters the class as injectable
  6. the injector reads the array and resolves each type to a providerthis is the whole of "DI magic"

The part everyone re-learns the hard way is step 3. It can only emit a type that still exists at runtime — a class. Type a constructor parameter as a TypeScript interface and it erases to nothing, so the compiler writes Object in its place, and the injector goes looking for a provider for Object. Your file looks perfect. The error names a type you never typed.

This is also the cleanest way to understand the two decorator systems. The legacy system exists because TypeScript shipped decorators years before JavaScript standardised them, and its whole DI story leans on that compiler-emitted metadata plus parameter decorators like @Inject(TOKEN). TC39 Stage 3 decorators have no parameter decorators at all — a decorator there gets (value, context) and writes to context.metadata instead, and the compiler emits no types for it. That is not a regression; it is the standard refusing to make the type system observable at runtime. It is also why modern Angular pushes you toward the inject() function and explicit InjectionTokens: those need no metadata emit, so they survive the move.

A teammate refactors constructor(private http: HttpClient) into constructor(private http: HttpPort), where HttpPort is a TypeScript interface, and registers a provider for it. It compiles with zero errors. What happens at runtime?

Right — and this is the single most confusing DI failure in Angular and NestJS. emitDecoratorMetadata can only emit values that survive to runtime, so an erased interface becomes the literal Object constructor. The injector dutifully hunts for a provider for Object, finds none, and names a type you never wrote. The fixes: an InjectionToken plus @Inject(HTTP_PORT), or an abstract class instead of an interface — an abstract class is a real runtime value, so it can be both a type and a DI token.

There is no interface name left to record. Interfaces are a compile-time-only construct: after emit, HttpPort does not exist in the JavaScript at all, so there is nothing for the compiler to write down and nothing for the injector to match against.

Erasure happens in the compiler, so JIT and AOT read exactly the same design:paramtypes array. This one fails identically in both — which is at least merciful.

Questions from the back row

Why does @Injectable() have empty parentheses if it takes no arguments?

Because it is a factory, and the parens are the call that produces the decorator. @Injectable without them would hand the class straight to Injectable as if it were the decorator function — wrong shape, and in a framework that also accepts options you get a confusing failure rather than a clean one. Rule of thumb: if the docs ever show it taking a config object, it is a factory, so it always needs the parens.

Can I use a legacy decorator and a TC39 decorator in the same project?

Not in the same compilation. experimentalDecorators is a program-wide switch: while it is on, every @ in your code is the legacy three-argument kind, no matter how modern the library. The signatures are not compatible, so a TC39-style (value, context) decorator called the legacy way receives a prototype where it expected a function and fails somewhere far from the cause. Migrate a whole tsconfig at a time, never a file.

Does the decorator run on every call to the method?

No — and this is the contrast worth burning in. The decorator body runs once, when the module is imported, before your app has rendered a pixel. The function it installed runs on every single call — every keystroke, every HTTP round trip, every one of the ten thousand invocations after. Expensive setup belongs in the decorator; anything you put in the wrapper you are paying for forever.

1. What are decorators?

A decorator is a function that receives information about the thing it decorates (a class, method, property, or parameter) and can inspect it, wrap it, or replace it. Syntactically, decorators use the @ prefix and appear immediately before the declaration they annotate.

@sealed
class BankAccount {
  @log
  deposit(@validate amount: number): void {
    this.balance += amount;
  }

  @readonly
  private balance = 0;
}

// @sealed   → class decorator
// @log      → method decorator
// @validate → parameter decorator
// @readonly → property decorator

Decorators are particularly powerful because they run at class definition time, not per-call. The decoration happens once when the module loads. Each decorator can add behavior, metadata, or validation without the class itself knowing about it — a form of Aspect-Oriented Programming (AOP).

To use decorators in TypeScript today: for legacy decorators add "experimentalDecorators": true to tsconfig. For TC39 Stage 3, just use TypeScript 5.0+ without the experimental flag. The two systems cannot be mixed in the same file.

3. Legacy: class decorator

A class decorator is called with the class constructor as its only argument. It can return a new constructor to replace the class, or return nothing (modify in place).

// tsconfig: "experimentalDecorators": true

// Simple class decorator — seals the class so no new
// properties can be added to it or its prototype.
function sealed(target: Function): void {
  Object.seal(target);
  Object.seal(target.prototype);
}

@sealed
class Config {
  version = "1.0";
}
// Config.newProp = "x";  // runtime error: object is sealed

// Class decorator that REPLACES the class (returns new constructor)
function singleton<T extends { new(...args: any[][]): {} }>(Ctor: T) {
  let instance: InstanceType<T>;
  return class extends Ctor {
    constructor(...args: any[]) {
      if (!instance) { super(...args); instance = this as any; }
      return instance;
    }
  };
}

@singleton
class AppState {
  count = 0;
}
const a = new AppState(), b = new AppState();
console.log(a === b); // true — same instance every time

4. Legacy: method decorator

A method decorator receives three arguments: the class prototype (or constructor for statics), the method name, and the PropertyDescriptor. Modifying the descriptor's value replaces the method.

function log(
  target:     any,
  key:        string,
  descriptor: PropertyDescriptor
): PropertyDescriptor {
  const original = descriptor.value;
  descriptor.value = function(this: any, ...args: any[]) {
    console.log(`→ calling ${key}(${JSON.stringify(args)})`);
    const result = original.apply(this, args);
    console.log(`← ${key} returned ${JSON.stringify(result)}`);
    return result;
  };
  return descriptor;
}

class Calculator {
  @log
  add(a: number, b: number): number {
    return a + b;
  }
}

const calc = new Calculator();
calc.add(2, 3);
// → calling add([2,3])
// ← add returned 5
Key insight: the decorator runs at class definition time (when the module loads), not at each method call. It replaces the method's descriptor.value with a wrapper function. The wrapper then runs at call time. This is the Decorator pattern from GoF, applied at the language level.

5. Legacy: property decorator

A property decorator receives the prototype and the property name. Unlike method decorators, it has no PropertyDescriptor — you cannot directly intercept the value. The typical workaround is to define a getter/setter dynamically or store metadata for a later accessor.

// Property decorators cannot get/set the initial value,
// but they can define getters/setters on the prototype.
function readonly(target: any, key: string): void {
  Object.defineProperty(target, key, {
    writable: false,
    configurable: false
  });
}

class Config {
  @readonly
  appName = "MyApp";
}
const cfg = new Config();
// cfg.appName = "Other"; // runtime TypeError in strict mode

// More common: use property decorators to RECORD metadata,
// then read it in the class decorator or a factory function.
function column(name: string) {
  return (target: any, key: string) => {
    const existing = Reflect.getMetadata('columns', target) ?? [];
    Reflect.defineMetadata('columns', [...existing, { key, name }], target);
  };
}

class User {
  @column('user_id')
  id: number;

  @column('display_name')
  name: string;
  // TypeORM and class-transformer work like this
}

6. Legacy: parameter decorator

Parameter decorators receive the prototype, method name, and parameter index. They cannot change the parameter — they are metadata recorders. NestJS's @Body(), @Param(), and @Query() are built on parameter decorators plus reflect-metadata.

function required(target: any, key: string, idx: number): void {
  const existing: number[] = Reflect.getMetadata('required', target, key) ?? [];
  Reflect.defineMetadata('required', [...existing, idx], target, key);
}

function validate(target: any, key: string, desc: PropertyDescriptor) {
  const orig = desc.value;
  desc.value = function(...args: any[]) {
    const reqs: number[] = Reflect.getMetadata('required', target, key) ?? [];
    reqs.forEach(i => {
      if (args[i] == null) throw new Error(`Param ${i} is required`);
    });
    return orig.apply(this, args);
  };
}

class UserService {
  @validate
  create(@required name: string, email?: string): string {
    return `Created ${name}`;
  }
}

const svc = new UserService();
svc.create("Alice");   // ✅
svc.create(null as any); // ❌ runtime: "Param 0 is required"

7. Decorator factories — decorators that accept arguments

When you write @log you pass a decorator function directly. When you write @log('debug') you call a decorator factory — a function that returns a decorator. The factory runs at class-definition time; the returned decorator is what actually decorates the target.

// Basic decorator (no args)
function log(target: any, key: string, desc: PropertyDescriptor) { ... }
@log  // Called with (target, key, desc)

// Decorator factory (accepts args, returns a decorator)
function log(level: 'debug' | 'info' | 'error') {
  return function(target: any, key: string, desc: PropertyDescriptor) {
    const orig = desc.value;
    desc.value = function(...args: any[]) {
      console[level](`[${level.toUpperCase()}] calling ${key}`);
      return orig.apply(this, args);
    };
  };
}

class Service {
  @log('debug')    // factory called first, returns decorator
  fetchData(): void { ... }

  @log('error')
  save(): void { ... }
}

9. reflect-metadata — storing decorator metadata

The reflect-metadata polyfill adds Reflect.defineMetadata and Reflect.getMetadata to the global Reflect object. This is how Angular and NestJS's DI containers know what types to inject — they store metadata at class-definition time (via decorators) and read it at injection time.

// npm install reflect-metadata
// import 'reflect-metadata'; // once, at app entry point
// tsconfig: "emitDecoratorMetadata": true

function Injectable(target: Function): void {
  // TypeScript emits design:paramtypes when emitDecoratorMetadata is on.
  // It's an array of the constructor's parameter types (as constructors).
  const types = Reflect.getMetadata('design:paramtypes', target);
  console.log(types); // e.g. [UserRepository, LogService]
  // DI container uses this to know what to inject
}

@Injectable
class UserService {
  constructor(
    private repo: UserRepository,
    private log:  LogService
  ) {}
  // At runtime, @Injectable reads [UserRepository, LogService]
  // and the DI container resolves each one automatically.
}

// Custom metadata
Reflect.defineMetadata('role', 'admin', UserService.prototype, 'deleteUser');
const role = Reflect.getMetadata('role', UserService.prototype, 'deleteUser');
// → 'admin'

10. TC39 Stage 3 decorators (TypeScript 5.0+)

The TC39 Stage 3 decorator proposal is the JavaScript standard path. TypeScript 5.0 implemented it. The key change is the API: instead of (target, key, descriptor), a decorator receives (value, context) where context is a rich object describing what is being decorated. This is cleaner and does not require reflect-metadata.

// TypeScript 5.0+ — no experimentalDecorators flag needed

// Method decorator (TC39)
function log<T extends (this: any, ...args: any[]) => any>(
  value: T,
  context: ClassMethodDecoratorContext
): T {
  return function(this: any, ...args: any[]) {
    console.log(`→ ${String(context.name)} called with`, args);
    const result = value.apply(this, args);
    console.log(`← ${String(context.name)} returned`, result);
    return result;
  } as T;
}

// Class decorator (TC39)
function sealed<T extends abstract new(...args: any[]) => {}>(
  value: T,
  context: ClassDecoratorContext
): T {
  context.addInitializer(function() {
    Object.seal(this);
    Object.seal((this as any).prototype);
  });
  return value;
}

// Accessor decorator (TC39) — new 'accessor' keyword
function validate(
  value: ClassAccessorDecoratorTarget<unknown, number>,
  context: ClassAccessorDecoratorContext
): ClassAccessorDecoratorResult<unknown, number> {
  return {
    set(v: number) {
      if (v < 0) throw new Error("Value must be non-negative");
      value.set.call(this, v);
    }
  };
}

@sealed
class Product {
  @validate
  accessor price = 0; // 'accessor' keyword enables accessor decorators

  @log
  getInfo(): string { return `Price: ${this.price}`; }
}

11. Real-world decorator examples

Angular's @Component — under the hood

// Simplified Angular @Component implementation
function Component(metadata: {
  selector: string;
  template: string;
  styles?: string[];
}) {
  return function(target: Function) {
    // Angular stores the metadata for the component compiler
    Reflect.defineMetadata('annotations', metadata, target);
    // Angular's JIT compiler reads this when bootstrapping
  };
}

@Component({
  selector: 'app-root',
  template: '<h1>Hello</h1>'
})
class AppComponent {
  title = 'My App';
}

NestJS @Controller and @Get — under the hood

// Simplified NestJS routing decorators
function Controller(prefix: string = '') {
  return (target: Function) => {
    Reflect.defineMetadata('prefix', prefix, target);
  };
}

function Get(path: string = '') {
  return (target: any, key: string, desc: PropertyDescriptor) => {
    const routes = Reflect.getMetadata('routes', target) ?? [];
    routes.push({ path, method: 'GET', handler: key });
    Reflect.defineMetadata('routes', routes, target);
  };
}

@Controller('/users')
class UserController {
  @Get('/')
  findAll(): string[] { return []; }

  @Get('/:id')
  findOne(): string { return ""; }
}
// NestJS reads the metadata and registers Express/Fastify routes

12. @Memoize — interactive cache demo

Memoization is one of the cleanest decorator use cases: wrap a method so that calling it with the same arguments returns the cached result instead of recomputing. Click the buttons below to call a simulated slow function and watch cache hits accumulate.

The @Memoize decorator

function Memoize(
  target: any,
  key: string,
  desc: PropertyDescriptor
) {
  const cache = new Map<string, any>();
  const orig = desc.value;
  desc.value = function(...args: any[]) {
    const k = JSON.stringify(args);
    if (cache.has(k)) {
      return cache.get(k); // cache hit
    }
    const v = orig.apply(this, args);
    cache.set(k, v);
    return v;            // cache miss
  };
}

13. Legacy vs TC39 side-by-side — same @log decorator

Here is the same logging decorator written in both systems so you can compare the API differences directly.

LEGACY experimentalDecorators

// tsconfig: "experimentalDecorators": true

function log(
  target:     any,
  methodName: string,
  descriptor: PropertyDescriptor
): PropertyDescriptor {
  const original = descriptor.value;

  descriptor.value = function(
    this: any,
    ...args: any[]
  ) {
    console.log(
      `→ ${methodName}(${args})`
    );
    const result = original.apply(this, args);
    console.log(`← ${methodName} =${result}`);
    return result;
  };

  return descriptor;
}

class MyService {
  @log
  greet(name: string): string {
    return `Hello, ${name}`;
  }
}

TC39 TypeScript 5.0+

// No special tsconfig flag needed

function log<T extends (
  this: any,
  ...args: any[]
) => any>(
  value:   T,
  context: ClassMethodDecoratorContext
): T {
  const methodName = String(context.name);

  return function(
    this: any,
    ...args: any[]
  ) {
    console.log(
      `→ ${methodName}(${args})`
    );
    const result = value.apply(this, args);
    console.log(`← ${methodName} =${result}`);
    return result;
  } as T;
}

class MyService {
  @log
  greet(name: string): string {
    return `Hello, ${name}`;
  }
}
