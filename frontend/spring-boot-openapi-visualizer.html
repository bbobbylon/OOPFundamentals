1 — Why OpenAPI? The Stale Docs Problem

Traditional API documentation lives in a wiki or Word document. The moment the code changes, the docs are wrong — and no-one knows until a frontend developer spends an hour debugging a 422 response.

Without OpenAPI — manual docs
Developer updates the endpoint
→ Forgets to update the Confluence page
→ Frontend calls old parameter name
→ 400 Bad Request with no explanation
→ 2-hour debugging session
→ "The docs were wrong" — again

Docs are always one commit behind code
With OpenAPI / Springdoc — code IS the docs
Developer updates the endpoint
→ Springdoc regenerates the spec on startup
→ Swagger UI shows the new contract instantly
→ Frontend team uses the live UI to test it
→ Client SDKs can be regenerated in CI

Docs are always exactly in sync with code
Three things OpenAPI gives you for free:
✓ Swagger UI — interactive browser UI to explore and call your API without Postman
✓ /v3/api-docs — machine-readable OpenAPI 3.x JSON/YAML that any tool can consume
✓ Client code generation — openapi-generator creates TypeScript, Python, Go, etc. SDK clients from your spec

2 — Adding Springdoc (One Dependency)

Add a single dependency to pom.xml. No other configuration is required to get Swagger UI running:

<!-- pom.xml — add inside <dependencies> --> <dependency> <groupId>org.springdoc</groupId> <artifactId>springdoc-openapi-starter-webmvc-ui</artifactId> <version>2.6.0</version> </dependency> <!-- That's it. Spring Boot auto-configuration does the rest. No @EnableOpenApi, no WebMvcConfigurer changes needed. -->
What gets auto-created on startup:
http://localhost:8080/swagger-ui.html
→ redirects to /swagger-ui/index.html — the interactive browser UI
http://localhost:8080/v3/api-docs
→ the full OpenAPI 3 spec as JSON
http://localhost:8080/v3/api-docs.yaml
→ same spec as YAML (easier to read / diff in git)
Optional application.yml customisation:
# application.yml springdoc: api-docs: path: /v3/api-docs # default, change if you need /api/docs swagger-ui: path: /swagger-ui.html # default entry-point operations-sorter: method # sort by GET/POST/PUT/DELETE in the UI tags-sorter: alpha # sort tag groups alphabetically try-it-out-enabled: true # expand "Try it out" by default show-actuator: false # hide /actuator endpoints from the spec

3 — Zero-Config: Auto-Detected Endpoints

Springdoc scans every @RestController in your application context and includes all public mapped methods in the spec automatically. No annotation needed on the controller itself.

// UserController.java — no Springdoc annotation needed at all @RestController @RequestMapping("/api/v1/users") public class UserController { @GetMapping // → GET /api/v1/users public List<UserResponse> findAll() { ... } @GetMapping("/{id}") // → GET /api/v1/users/{id} public UserResponse findById(@PathVariable Long id) { ... } @PostMapping // → POST /api/v1/users public ResponseEntity<UserResponse> create(@RequestBody CreateUserRequest req) { ... } @DeleteMapping("/{id}") // → DELETE /api/v1/users/{id} public ResponseEntity<Void> delete(@PathVariable Long id) { ... } } // All 4 endpoints appear in Swagger UI immediately after adding the dependency.
Swagger UI shows — auto-detected from the controller above:
GET /api/v1/users findAll
GET /api/v1/users/{id} findById
POST /api/v1/users create
DELETE /api/v1/users/{id} delete

4 — Annotation Reference

Click any annotation to see its attributes, purpose, and a code example. These annotations live in the io.swagger.v3.oas.annotations package.

@Operation
Documents a single endpoint — summary, description, tags, operationId
@Parameter
Documents a method parameter — path, query, or header variable
@ApiResponse
Documents a specific HTTP status code and its response body schema
@Schema
Enriches a DTO field or class with description, example, and constraints
@Tag
Groups endpoints into a named section in Swagger UI — class-level
@SecurityRequirement
Declares that an endpoint requires a named security scheme (JWT, API key…)

5 — @Schema on DTO Fields

Adding @Schema to DTO fields makes Swagger UI show real example values and descriptions in the "Request body" section — so frontend developers know exactly what to send.

CreateUserRequest.java
@Schema(description = "Request body for creating a new user account") public record CreateUserRequest( @Schema( description = "Full display name of the user", example = "Alice Johnson", requiredMode = Schema.RequiredMode.REQUIRED, minLength = 2, maxLength = 100 ) @NotBlank String name, @Schema( description = "Valid email address — used as login credential", example = "alice@example.com", requiredMode = Schema.RequiredMode.REQUIRED, format = "email" ) @Email @NotBlank String email, @Schema( description = "Password — min 8 chars, must include a digit", example = "Secret123!", requiredMode = Schema.RequiredMode.REQUIRED, minLength = 8 ) @Size(min = 8) String password, @Schema( description = "User role — defaults to USER if omitted", example = "USER", allowableValues = {"USER", "ADMIN", "MODERATOR"}, defaultValue = "USER" ) String role ) {}
How Swagger UI renders it
Request body schema
name* string (2..100)
Full display name of the user
Example: "Alice Johnson"
email* string (email)
Valid email address — used as login credential
Example: "alice@example.com"
password* string (min: 8)
Password — min 8 chars, must include a digit
Example: "Secret123!"
role string (enum)
Allowed: USER, ADMIN, MODERATOR
Default: "USER"

6 — JWT Security Scheme Configuration

Register a bearerAuth security scheme so Swagger UI shows an "Authorize" button where users can paste their JWT token. Then apply it globally to all endpoints (or per-endpoint with @SecurityRequirement).

@Configuration public class OpenApiConfig { @Bean public OpenAPI openAPI() { return new OpenAPI() .info(new Info() .title("User Management API") .description("REST API for managing users and roles") .version("1.0.0") .contact(new Contact().name("Platform Team").email("api@example.com")) .license(new License().name("Apache 2.0").url("https://www.apache.org/licenses/LICENSE-2.0"))) // 1. Register the security scheme under the name "bearerAuth" .components(new Components() .addSecuritySchemes("bearerAuth", new SecurityScheme() .name("bearerAuth") .type(SecurityScheme.Type.HTTP) .scheme("bearer") .bearerFormat("JWT") // shown as hint in Swagger UI .description("Paste your JWT token (without the 'Bearer ' prefix)"))) // 2. Apply globally — every endpoint requires the JWT .addSecurityItem(new SecurityRequirement().addList("bearerAuth")); } }
Override per-endpoint: no auth needed
// Public endpoint — override the global requirement @Operation(summary = "Register a new account", security = {}) // empty = no auth required @PostMapping("/register") public ResponseEntity<UserResponse> register( @RequestBody CreateUserRequest req) { ... }
Add auth on a specific endpoint
// Explicit — useful when global security is OFF @Operation(summary = "Get current user profile") @SecurityRequirement(name = "bearerAuth") @GetMapping("/me") public UserResponse me( @AuthenticationPrincipal UserDetails user) { ... }
After adding the scheme, Swagger UI shows a padlock icon on secured endpoints and an Authorize button at the top right where users paste: eyJhbGciOiJIUzI1NiIs...

7 — GroupedOpenApi: Multiple API Versions / Audiences

GroupedOpenApi lets you split your API into named groups that appear as a dropdown in Swagger UI. Common use cases: public vs. admin endpoints, or v1 vs. v2 paths.

@Configuration public class OpenApiGroupConfig { // Group 1 — Public API: only /api/v1/** paths visible to end users @Bean public GroupedOpenApi publicApi() { return GroupedOpenApi.builder() .group("public-api") // dropdown label in Swagger UI .displayName("Public API (v1)") .pathsToMatch("/api/v1/**") .pathsToExclude("/api/v1/admin/**") // hide admin sub-paths .build(); } // Group 2 — Admin API: internal management endpoints @Bean public GroupedOpenApi adminApi() { return GroupedOpenApi.builder() .group("admin-api") .displayName("Admin API (internal)") .pathsToMatch("/api/v1/admin/**", "/internal/**") .build(); } // Group 3 — v2 API: new version running alongside v1 @Bean public GroupedOpenApi v2Api() { return GroupedOpenApi.builder() .group("v2-api") .displayName("API v2 (beta)") .pathsToMatch("/api/v2/**") .build(); } }
Swagger UI dropdown (top right) — generated from the beans above:
▼ Public API (v1)
▼ Admin API (internal)
▼ API v2 (beta)
Each group hits a different api-docs URL: /v3/api-docs/public-api, /v3/api-docs/admin-api, etc.

9 — Best Practices Checklist

Practice Why it matters How to do it
Always set operationId openapi-generator uses it as the method name in generated SDKs. Without it you get ugly auto-names like getUsersUsingGET1. @Operation(operationId = "listUsers")
Use @Tag for grouping Groups related endpoints into collapsible sections in Swagger UI. Without tags, everything is in one flat list. @Tag(name="Users", description="...") on the controller class
Document error responses Frontend devs need to know what 400, 401, 404, and 500 look like so they can handle them. Silent omission leads to "I didn't know it could return that." @ApiResponse(responseCode="404", ...) — add for every error your endpoint can return
Version paths as /api/v1/ Allows you to introduce breaking changes in /api/v2/ without affecting existing clients. GroupedOpenApi can then surface each version separately. @RequestMapping("/api/v1/users") — never /users without a version
Hide internal endpoints Actuator, internal health checks, and debugging endpoints should not appear in the public API spec. @Hidden on the controller or method — removes it from the spec entirely
Use @Parameter for query params Without it, Springdoc infers the type but gives no description, example, or required flag — leaving consumers guessing. @Parameter(description="...", example="active", required=false)
Set example on @Schema fields Swagger UI pre-fills the "Try it out" body with your examples. Makes manual testing instant and shows intent clearly. @Schema(example="alice@example.com") on each DTO field
Commit the YAML spec to git Lets teams diff API changes in pull requests — a breaking change to a response body is visible in the PR diff, not discovered by accident. Generate in CI: mvn springdoc:generate then commit openapi.yaml
