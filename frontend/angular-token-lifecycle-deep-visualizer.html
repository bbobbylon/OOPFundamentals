Access Tokens & Silent Refresh

After login your SPA holds three tokens with three jobs. The access token is deliberately short-lived — so the real work is attaching it to every API call, silently refreshing it before (or right after) it expires, and storing it without handing it to an attacker. Here's the full lifecycle, hands-on.

🎫 What are the three tokens — and what does each one actually do?

After an OIDC login your SPA receives up to three tokens from the IdP (Entra ID / Ping), each with a different job and lifetime. Mixing them up causes real bugs: sending the ID token to your API, stashing the refresh token in localStorage where XSS can grab it, or calling an API with an already-expired access token. Knowing which token goes where — and where each may be stored — is the core of frontend auth.

  • ID token = "who you are" (for the client only — show the name in the nav). Never send it to the API.
  • Access token = "what you may do" — the only token your API sees, as Authorization: Bearer …. Short-lived (15–60 min).
  • Refresh token = "get a new access token" — sent to the IdP, not your API; long-lived and the highest-value target.
  • Storage matters: access token in memory; refresh token in an httpOnly cookie (never JS-readable storage).
  • Refresh before expiry on a timer, and let a 401 interceptor recover if a call still races an expired token.

ID token — who are you?

A JWT identifying the user — sub, name, email, iat, exp. For the client only (display the name); never send it to the API. Purpose: client identity, not authorization.

Access token — prove your rights

A short-lived JWT (15–60 min) sent as Authorization: Bearer … on every API call. Spring validates signature + expiry + audience and reads roles/scp. Store in memory, never localStorage.

Refresh token — new access token

A long-lived opaque token (hours–days) sent to the IdP to mint a new access token silently — no re-login. If stolen it's persistent access. httpOnly cookie only, never JS-accessible storage.

In CIAM:an Angular service keeps the access token in memory (private token = signal<string|null>(null)); the auth interceptor reads tokenService.token() and injects it. ~90s before expiry a timer fires silentRefresh() against the IdP; if a call still hits an expired token, the 401 interceptor refreshes and retries.

The problem

One flaky wifi moment. Six parallel API calls. The user gets logged out of everything — including the tab that "won."

The interceptor did exactly what section 3's code shows — and it torched the session

A dashboard fires six parallel calls on load: orders, invoices, profile, notifications, settings, team. The access token expired forty seconds ago, so all six land a 401 within milliseconds of each other. Each interceptor instance independently does what the code block above says to do — catches its own 401, calls auth.refresh() — because nothing is coordinating between them. All six POST to /token almost simultaneously. The IdP processes the first arrival, rotates the refresh token, and hands back a new access token. The second arrival — already in flight before the rotated cookie even existed — presents the refresh token that was just spent. Rotation's reuse-detection can't tell "my own app racing itself" from "an attacker replaying a stolen token," so it revokes the entire token family. The tab that "won" the race gets logged out too, on its very next call, mid keystroke, with an unsaved form.

access token expired right on schedule ✓ refresh rotation configured correctly ✓ 6 requests raced the same expired token ⚠ IdP saw a reused refresh token → revoked the whole family ⚠

The wrong assumption underneath: that "on 401, refresh and retry" is safe to write inside every interceptor invocation independently — when a rotating refresh token is a single-use ticket, and "single" includes your own other requests.

Make every 401 wait for one refresh, instead of starting its own
First move: auth.refresh() gets called fresh from every 401 handler, unmodified ↓ N concurrent 401s make N concurrent refresh calls, and rotation only forgives the first one Better: share one in-flight refresh with shareReplay(1) (or exhaustMap) ↓ five of the six 401s now just wait for the one real call to resolve, then retry with its result The result: exactly one rotation per expiry, no matter how many requests noticed at once
A rotating refresh token is a single-use ticket — and "single" includes your own other requests. The token endpoint has no way to know that two 401s calling refresh() a millisecond apart both came from your app in good faith off the same expired access token; from where it sits, that is indistinguishable from an attacker replaying a stolen one, so it makes the only safe call available — revoke first, ask never. Coordinating refresh into one shared call isn't an optimization. It's the only way to stop your own concurrency from looking like an attack.
Think of a rotating refresh token as a train ticket that's punched and voided the instant it's used, with a fresh one issued in its place. If you and your own travel companion each hand the same ticket to two different conductors on two different cars, seconds apart, the second conductor doesn't know you're together — they just see a ticket that was already punched a moment ago, three cars down. Both of you get put off at the next stop. The ticket didn't fail. Nobody told the two conductors to check with each other first.

The mechanism

Six requests notice the same expired token. Only one of them is allowed to matter.

  1. Six components each hold a subscription that fires on page load; the access token expired 40ms ago, so all six get a 401the setup, not the bug yet
  2. Each interceptor instance independently catches its own 401 and calls auth.refresh() — nothing is shared between themthis line is the whole problem
  3. All six POST to /token with grant_type=refresh_token within milliseconds of each othera stampede, not a queue
  4. The IdP processes the first arrival: rotates the refresh token, issues a new access token, and marks the old refresh token spentexactly one legitimate winner
  5. The second arrival presents the now-spent refresh token — not stale by choice, just by timing, since the browser hadn't received the rotated one yet when it was senta race, not a mistake
  6. The IdP can't tell "my own app racing itself" from "an attacker replaying a stolen token," so reuse-detection revokes the entire token family — winner includedthe whole session dies to stop a theft that never happened

Step 2 is the lesson. Nothing from step 3 onward is a bug — that's rotation and reuse-detection doing exactly their job, correctly treating a reused refresh token as a threat. The only broken line in the whole sequence is step 2, where five refresh calls get made that never needed to exist. Fix step 2 — coordinate every 401 onto one shared refresh — and steps 3 through 6 simply never happen the bad way, because there is only ever one request at the token endpoint per expiry.

This is the fixed shape: six 401s, one refresh. Without shareReplay(1) (or an equivalent "is a refresh already in flight" check), this diagram doesn't exist — each caller draws its own arrow straight to /token, six separate POSTs land within milliseconds, and rotation's reuse-detection reads that as an attack instead of a coincidence. The fix isn't smarter reuse-detection on the IdP's side — it's right to be suspicious. The fix is never giving it a reason to be.

Tab A and Tab B are the same app in the same browser, sharing one httpOnly refresh-token cookie. Both tabs' access tokens expire within the same second. Tab A's refresh request reaches the IdP first and wins — RT#1 rotates to RT#2. Forty milliseconds later, Tab B's refresh request — dispatched before it ever saw the new cookie — arrives presenting RT#1, which the IdP now considers reused. What happens to Tab A?

This is the intuitive read — Tab A did everything right and "won." But reuse detection doesn't score a race; it tracks a lineage. The IdP saw RT#1 used twice, and RT#2 is a child of that same lineage, so revoking "the token that got reused" necessarily means revoking everything descended from it too — including Tab A's brand-new one.

There's no soft-failure middle state here. Refresh token rotation with reuse detection is designed to fail loudly and completely the instant reuse is seen, because the threat model is a real attacker replaying a stolen token — and a real attacker doesn't get a grace period. It revokes the family outright rather than quietly degrading.

Right, and it's the counterintuitive part: "winning" the race doesn't protect you, because the IdP isn't scoring a race — it's watching for one refresh token ever being redeemed twice, and RT#1 was. Once that lineage is flagged, RT#2 goes down with it, whether or not the tab holding it did anything wrong. The only real fix is preventing two refreshes off the same token from ever being sent in the first place.

Where you've seen this before

"Second writer loses, unconditionally" shows up everywhere state gets versioned.

This exact ticket, in your own Entra ID / Ping tenant

Both Entra ID and PingFederate support — and for SPAs, expect — refresh token rotation with reuse detection exactly like this. The failure mode isn't theoretical: it's the standard reason a support ticket reads "the app randomly logged me out of everything" right after a flaky network moment triggered several parallel retries. The fix lives entirely in your Angular interceptor, not in the IdP config — the server-side behavior here is correct and non-negotiable.

fix the client, not the IdP

Hibernate's @Version column — the same "second writer loses" rule

Optimistic locking works identically: a row carries a version number, an UPDATE only succeeds if the version you read still matches, and the loser doesn't get a merge — they get an OptimisticLockException and have to start over. A rotating refresh token is a version column with exactly one allowed writer: the first successful use bumps it, and anyone still holding the old value is unconditionally wrong, not partially wrong.

stale version ≈ reused refresh token

Why "sign out everywhere" exists as a button at all

Mass session revocation after a password change runs on the same instinct: once there's any signal that something in a session's lineage might be compromised, the safe response is to revoke the whole lineage, not just the device that looked suspicious. A replayed refresh token and a stolen password get the same answer — kill the family, make everyone log in fresh, and let the legitimate owner take the ten-second hit.

when in doubt, revoke the whole lineage
Questions from the back row

Why does the IdP punish the winner too? That feels unfair.

Because from the IdP's side there's no way to know which of the two requests was "the real one" and which was the replay — both presented a technically valid, correctly-issued refresh token. Punishing only "the second one to arrive" would mean an attacker who's simply faster than the legitimate client gets to keep the session while the real user gets logged out — exactly backwards. Revoking the whole lineage is the only response that doesn't require guessing who the attacker is.

Should we just turn off refresh token rotation to avoid the false positive?

No — that trades a survivable annoyance for an unsurvivable one. Rotation with reuse detection is what makes a stolen refresh token worthless after its first replay; without it, a leaked refresh token stays valid for its entire lifetime — hours or days — with nobody able to tell it was ever stolen. The false-positive rate for legitimate concurrent refreshes is a client-side coordination bug you can actually fix with shareReplay(1); a silently valid stolen token for days is not fixable after the fact.

Our app doesn't fire six requests on load. Are we safe?

Check two other places before assuming that. Multiple browser tabs of the same app share one httpOnly cookie — a completely normal thing users do — and a slow network can trigger an automatic client-level retry while the original request is still technically in flight. Either one reproduces the exact same race with a single logical request, not six. "We only make one API call" doesn't mean "we only ever have one refresh in flight."

Short access-token lifetimes limit the blast radius if one leaks; the refresh token quietly tops you up. Only send the access token to your own API — never to the IDM, a CDN, or a third-party.

3. Attaching the token: the bearer interceptor

export const authInterceptor: HttpInterceptorFn = (req, next) => {
  const auth = inject(AuthService);
  // only attach to YOUR api — never leak the token to other origins
  const token = auth.accessToken();
  const apiReq = token && req.url.startsWith(environment.apiBase)
    ? req.clone({ setHeaders: { Authorization: `Bearer ${'{'}token{'}'}` } })
    : req;

  return next(apiReq).pipe(
    catchError((e: HttpErrorResponse) =>
      e.status === 401
        ? auth.refresh().pipe(switchMap(t =>          // got a new access_token…
            next(apiReq.clone({ setHeaders: { Authorization: `Bearer ${'{'}t{'}'}` } }))))  // …retry once
        : throwError(() => e))
  );
};

A real app also guards against a refresh stampede (many 401s at once): share one in-flight refresh so they all wait for a single new token. MSAL / angular-oauth2-oidc handle this for you.

4. How "silent" refresh works

Refresh-token grant (today's default for SPAs)

Exchange the refresh_token for a new access_token in the background. SPAs should use refresh-token rotation: each refresh returns a new refresh token and invalidates the old one — so a stolen refresh token is quickly useless.

The older hidden-iframe trick

Before rotating refresh tokens were safe for SPAs, apps did a silent prompt=none auth in a hidden iframe using the IDM session cookie. Third-party-cookie blocking has largely killed this; prefer rotated refresh tokens (or a BFF).

5. Where do you store the tokens?

StorageXSS exposureSurvives reload?Verdict
in-memory (signal/var)low — gone on reloadno (silent re-auth on load)safest for the access token
localStoragehigh — any XSS can read ityesconvenient but risky; common target
httpOnly cookie (BFF)none — JS can't read ityesbest, but needs a backend + CSRF defense

Rule: keep the access token in memory and re-acquire it silently on reload. If you need true persistence and high security, move tokens to an httpOnly cookie via a BFF (backend-for-frontend) so the browser JS never touches them.

6. Logging out properly

  • Clear local tokens (memory + any storage) so the app forgets the session.
  • Hit the IDM's end-session / logout endpoint so the IDM's own SSO session ends — otherwise the next login silently re-authenticates and the user "can't log out".
  • Optionally revoke the refresh token at the IDM.
logout() {
  this.auth.clearTokens();
  location.href = `${'{'}issuer{'}'}/logout?id_token_hint=…&post_logout_redirect_uri=…`;
}

7. One-sentence recap

⏱️ Your SPA holds an id_token (who), a short-lived access_token (attached as Bearer to your API only), and a refresh_token (to get new access tokens) — so a bearer interceptor adds the token and, on a 401, runs a (single, shared) silent refresh with a rotating refresh token and retries; keep the access token in memory (or in an httpOnly cookie via a BFF), never localStorage if you can help it, and on logout clear tokens and end the IDM session.
