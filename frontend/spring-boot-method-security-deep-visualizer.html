Method Security — @PreAuthorize & friends

The security filter chain answers "is this request authenticated, and may it reach this URL?" Method security answers the finer question right at the service layer: "may this user, with these claims, run this method — on this data?" It's authorization expressed as an annotation, evaluated by a Spring AOP proxy just before your method body runs.

🔏 Why isn't URL-pattern security enough — when do you need @PreAuthorize on methods?

URL security (.requestMatchers("/api/admin/**").hasRole("ADMIN")) is coarse-grained: "only admins reach /admin." But CIAM rules are often finer — "a USER_MANAGER can list users but only PATCH users in their own department" — which can't be a URL pattern because it depends on the method arguments and the caller's claims together. @PreAuthorize puts that logic on the service method: Spring evaluates a SpEL expression against the current Authentication before the method runs, returning 403 if false. @PostAuthorize can even check the returned object after the fact.

  • Two layers: URL rules for broad gates, method annotations for per-object logic.
  • SpEL sees the args + the principal — #userId == authentication.name or hasRole('ADMIN').
  • Post-checks & filters — @PostAuthorize on the return, @Pre/@PostFilter on collections.
  • Annotate the service layer. It's proxy-based, so self-invocation skips the check.

SpEL expressions

hasRole('ADMIN'), hasAnyRole('ADMIN','USER_MANAGER'), isAuthenticated(), #userId == authentication.name or hasRole('ADMIN') (own profile or admin), and delegation: @permissionService.canManageUser(#userId, authentication) for complex policy.

@PostAuthorize & @PostFilter

@PostAuthorize("returnObject.status != 'DELETED' or hasRole('ADMIN')") checks the result when visibility depends on the object itself. @PostFilter strips items from a returned collection; @PreFilter trims the input collection before the method runs.

Enable method security

@EnableMethodSecurity (Spring Security 6, replaces @EnableGlobalMethodSecurity) turns on @PreAuthorize/@PostAuthorize/@Pre/@PostFilter/@Secured. It's AOP-proxy based — a self-call bypasses it — so annotate the service layer, not repositories or controllers.

CIAM: @PreAuthorize("hasAnyRole('SYSTEM_ADMIN','USER_MANAGER')") on searchUsers(); @PreAuthorize("hasRole('SYSTEM_ADMIN') or #userId == authentication.name") on getUser(userId) (admins see all, users see themselves); @PreAuthorize("@ciamPermissions.canAssignRole(#roleId, authentication)") on assignRole(...) for an IdM policy check. Angular guards are UX — this is the real gate.

1. Two layers of authorization

By the time a method-security check runs, the filter chain has already authenticated the JWT and populated the SecurityContext with the user's authorities. Method security is a second, finer gate — defense in depth, closer to the data, able to see method arguments and even the return value.

HTTP / filter chain (authorizeHttpRequests)URL + verbthe request401 if unauthenticated, 403 if URL-forbidden
Method (@PreAuthorize)per method + argumentsprincipal, args, return value403 AccessDeniedException

3. The expression toolkit

AnnotationRunsTypical expression
@PreAuthorizebefore the methodhasRole('ADMIN'), hasAuthority('SCOPE_users.read'), #id == authentication.name
@PostAuthorizeafter — can inspect resultreturnObject.owner == authentication.name
@PreFilterfilters a collection argumentfilterObject.ownerId == authentication.name
@PostFilterfilters the returned collectionhasRole('ADMIN') or filterObject.public
@Secured / @RolesAllowedbefore — role list only@Secured("ROLE_ADMIN") · no SpEL

hasRole vs hasAuthority: hasRole('ADMIN') is sugar for hasAuthority('ROLE_ADMIN') — it adds the ROLE_ prefix for you. JWT scopes arrive as SCOPE_ authorities, so check those with hasAuthority('SCOPE_…'). (You decide how token claims map to authorities — see Multi-IDM Claim Mapping.)

4. Reading the principal & arguments

The annotation

@Service
public class UserService {

  @PreAuthorize("hasAuthority('SCOPE_users.read')")
  public List<User> getUsers() { … }

  // ownership: callers may only read their own profile
  @PreAuthorize("#id == authentication.name or hasRole('ADMIN')")
  public User getProfile(@P("id") String id) { … }
}

The principal in the controller

@GetMapping("/api/me")
Me me(@AuthenticationPrincipal Jwt jwt) {
  return new Me(
    jwt.getSubject(),              // "sub"
    jwt.getClaimAsString("email"),
    jwt.getClaimAsStringList("roles"));
}

SpEL names: authentication, principal, #argName (enable arg names or use @P), returnObject, hasRole, hasAuthority, permitAll.

5. The gotchas that bite

  • It's an AOP proxy. @PreAuthorize only fires when the call goes through the proxy (an injected bean). A self-invocation (this.getUsers() from another method in the same class) bypasses the check entirely.
  • Proxies need overridable methods. On private / final / static methods the annotation is silently ignored (CGLIB can't proxy them).
  • 401 vs 403. No/invalid token → the filter chain rejects with 401 before your method. A valid token lacking the authority → method security throws 403. Don't confuse "who are you?" with "you're not allowed."
  • Don't rely on the client. An Angular route guard hiding a button is UX; this annotation is the enforcement. Both, always.
  • @PostAuthorize runs the method first — fine for reads, dangerous if the method has side effects you don't want unauthorized callers to trigger.

6. One-sentence recap

🔐 With @EnableMethodSecurity, a Spring AOP proxy evaluates a SpEL expression in @PreAuthorize (or @PostAuthorize) just before (or after) your service method — using the authenticated principal, its ROLE_/SCOPE_ authorities, and the method arguments — and throws a 403 AccessDeniedException when it's false; it's the server-side enforcement behind any client check, but remember it only fires through the proxy (self-invocation and private/final methods slip past it).
