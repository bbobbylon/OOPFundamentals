Resilience4j — Circuit Breaker, Retry & Rate Limiter

When a remote service fails, your entire application should not. Resilience4j gives you battle-tested fault-tolerance patterns as simple annotations.

1 — The Cascading Failure Problem

Without fault tolerance, one slow service can bring down your entire system. Watch what happens when the Inventory Service becomes slow or unresponsive.

API Gateway
Healthy — handling requests
→
Order Service
Healthy — calling Inventory
→
Inventory Service
🟢 Normal (200ms)

Why this matters: Each request to Order Service holds a thread open while waiting for Inventory. When Inventory hangs, Order's thread pool fills up. New requests queue. Then API Gateway's threads fill up waiting for Order. In 30–60 seconds: total outage from one slow dependency.

2 — Resilience4j Modules

Six composable patterns. Click any card to learn more.

@CircuitBreaker
Prevents calling a failing service. Opens after too many failures, then auto-heals.
Tracks success/failure rate in a sliding window. Once failures exceed the threshold, the circuit opens and all calls immediately return a fallback response — no more waiting for timeouts. After a cooldown, it enters HALF-OPEN to test if the service recovered.
@Retry
Retries failed calls automatically with configurable backoff delays.
Catches specific exceptions and retries the call up to maxAttempts times. Supports exponential backoff, jitter, and an ignore-list for exceptions that should not trigger a retry (e.g. validation errors).
@RateLimiter
Limits how many calls can pass through per time window using a token bucket.
Refills N tokens every limitRefreshPeriod. Each call costs one token. If no tokens are available and timeoutDuration is 0, the call immediately throws RequestNotPermitted. Useful for protecting downstream services or enforcing SLAs.
@Bulkhead
Limits concurrent calls to isolate slow services and prevent thread-pool exhaustion.
Two implementations: Semaphore (limits concurrent calls in the same thread pool — lightweight) and ThreadPool (gives each service its own isolated pool — stronger isolation but more overhead). Prevents one slow service from starving others.
@TimeLimiter
Adds a timeout to async (CompletableFuture) calls. Cancels and falls back if too slow.
Works with @Async and CompletableFuture. If the async call doesn't complete within timeoutDuration, it's cancelled and the fallback method is invoked. Requires AOP.
Fallback
The last resort — a method that returns a safe default when all else fails.
Defined via fallbackMethod on any Resilience4j annotation. Must have the same return type and parameters as the primary method, plus a Throwable parameter. Used by all patterns as the final safety net.

3 — Circuit Breaker: Three-State Machine

The circuit breaker is a state machine. Understanding all three states is the key to using it correctly.

🟡 HALF-OPEN probing
Let N test calls through. Decide based on their outcome.
CLOSED — Normal Operation
Calls flow normally. Each result (success or failure) is recorded in a sliding window. When the failure rate in that window exceeds failureRateThreshold, the circuit trips to OPEN.
OPEN — Fast Fail Mode
Zero calls reach the downstream service. Every call gets an immediate CallNotPermittedException and your fallback runs. This stops thread exhaustion and gives the service time to recover.

5 — @CircuitBreaker Annotation & Configuration

Java — annotated service method
@Service public class OrderService { @CircuitBreaker( name = "inventoryService", fallbackMethod = "inventoryFallback" ) public StockResponse checkStock(String productId) { // calls the external Inventory service return inventoryClient.getStock(productId); } // Must have same params + Throwable private StockResponse inventoryFallback( String productId, Throwable t) { log.warn("Circuit open — returning cached data"); return StockResponse.cached(productId); } }
application.yml — full config block
resilience4j: circuitbreaker: instances: inventoryService: # sliding window: last 5 calls slidingWindowSize: 5 slidingWindowType: COUNT_BASED # trip if ≥ 60% fail failureRateThreshold: 60 # also trip on slow calls (> 2s) slowCallRateThreshold: 80 slowCallDurationThreshold: 2000 # wait 10s before trying again waitDurationInOpenState: 10000 # let 3 test calls through in HALF-OPEN permittedNumberOfCallsInHalfOpenState: 3 # need at least 5 calls before measuring minimumNumberOfCalls: 5 registerHealthIndicator: true
The fallback method receives the same arguments as the original method plus a Throwable. Return type must match exactly. It handles all failure scenarios: circuit open, timeout, exception.

6 — @Retry with Exponential Backoff

Annotated method
@Retry( name = "inventoryService", fallbackMethod = "retryFallback" ) public StockResponse checkStock(String id) { return inventoryClient.getStock(id); } private StockResponse retryFallback( String id, Exception e) { return StockResponse.empty(); }
application.yml
resilience4j: retry: instances: inventoryService: maxAttempts: 3 waitDuration: 500ms enableExponentialBackoff: true exponentialBackoffMultiplier: 2 # exceptions that trigger retry: retryExceptions: - java.io.IOException - org.springframework.web.client .HttpServerErrorException # exceptions that DON'T retry: ignoreExceptions: - com.example.NotFoundException - javax.validation.ConstraintViolation

7 — @RateLimiter — Token Bucket

A token bucket holds N tokens. Each API call costs one token. When empty, calls are blocked or rejected immediately. The bucket refills every period.

Java
@RateLimiter( name = "inventoryService", fallbackMethod = "rateLimitFallback" ) public StockResponse checkStock(String id) { return inventoryClient.getStock(id); } private StockResponse rateLimitFallback( String id, RequestNotPermitted e) { return StockResponse.rateLimited(); }
application.yml
resilience4j: ratelimiter: instances: inventoryService: # 10 calls per second allowed limitForPeriod: 10 limitRefreshPeriod: 1s # 0 = fail immediately if no token timeoutDuration: 0

9 — @TimeLimiter — Async Timeouts

@TimeLimiter works with CompletableFuture and @Async. If the async operation doesn't complete within the configured duration, it is cancelled and the fallback runs.

Java — requires @Async + CompletableFuture
@Service public class InventoryService { @TimeLimiter( name = "inventoryService", fallbackMethod = "timeLimitFallback" ) @Async // required! public CompletableFuture<StockResponse> checkStockAsync(String id) { return CompletableFuture.supplyAsync( () -> inventoryClient.getStock(id) ); } private CompletableFuture<StockResponse> timeLimitFallback( String id, TimeoutException e) { return CompletableFuture.completedFuture( StockResponse.timeout() ); } }
application.yml
resilience4j: timelimiter: instances: inventoryService: # cancel if not done in 2s timeoutDuration: 2s # actually cancel the future cancelRunningFuture: true

@EnableAsync must be on your @Configuration class, and you need a configured ThreadPoolTaskExecutor bean for @TimeLimiter to work correctly.

10 — Combining Patterns

Annotations can be stacked. They execute inside-out — the innermost annotation wraps the actual call first.

outermost wrapper
→ wraps →
Retry

→ wraps →
TimeLimiter

→ wraps →
Actual Call
the real method
@CircuitBreaker(name = "inventoryService", fallbackMethod = "fallback") @Retry(name = "inventoryService") @TimeLimiter(name = "inventoryService") @Async public CompletableFuture<StockResponse> checkStock(String id) { return CompletableFuture.supplyAsync(() -> inventoryClient.getStock(id)); } // Single fallback handles ALL failure scenarios private CompletableFuture<StockResponse> fallback(String id, Exception ex) { log.error("All resilience patterns failed for {}: {}", id, ex.getMessage()); return CompletableFuture.completedFuture(StockResponse.unavailable(id)); }
1. TimeLimiter executes first
Wraps the actual call. If it doesn't return within 2s, throws TimeoutException and cancels the future.
2. Retry wraps TimeLimiter
If TimeLimiter throws, Retry waits and tries again — up to maxAttempts times with backoff.
3. CircuitBreaker wraps Retry
If retries keep failing, the circuit breaker trips and future calls skip Retry+TimeLimiter entirely — going straight to fallback.
All three instances share the name "inventoryService" so they read from the same yml config block. Each module has its own key under that name.

11 — Maven Dependencies

<!-- pom.xml --> <!-- 1. Core Resilience4j Spring Boot 3 starter --> <dependency> <groupId>io.github.resilience4j</groupId> <artifactId>resilience4j-spring-boot3</artifactId> <version>2.2.0</version> </dependency> <!-- 2. AOP — REQUIRED for annotations (@CircuitBreaker, @Retry, etc.) --> <dependency> <groupId>org.springframework.boot</groupId> <artifactId>spring-boot-starter-aop</artifactId> </dependency> <!-- 3. Reactive/WebFlux support (only if using WebFlux) --> <dependency> <groupId>io.github.resilience4j</groupId> <artifactId>resilience4j-reactor</artifactId> <version>2.2.0</version> </dependency>
AOP is mandatory. Without spring-boot-starter-aop, the annotations do nothing — they are silently ignored and your methods run unprotected. This is the most common setup mistake.
For Spring Boot 2.x
Use resilience4j-spring-boot2 instead of spring-boot3.
Actuator Integration
Add spring-boot-starter-actuator + set registerHealthIndicator: true to expose circuit breaker state via /actuator/health.
