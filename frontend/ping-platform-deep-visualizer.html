The Ping / ForgeRock Identity Platform

Ping Identity acquired ForgeRock in 2023; the product names converged onto a Ping prefix. A CIAM build rests on four engines — AM (access), IDM (lifecycle), DS (the store), and IG (the gateway) — running either self-managed or as the PingOne cloud. Knowing which box does what is half the job in an interview and on the job.

What is the Ping / ForgeRock platform — and how do the four engines divide responsibilities so each concern is handled by exactly one system?

The Ping / ForgeRock platform follows a strict separation of concerns: each engine has a single, well-defined responsibility. This architecture prevents the most common CIAM antipattern — embedding identity logic directly in application code — by centralizing every identity operation behind a purpose-built system. Understanding this division is essential for both system design and incident response. PingAM (Access Management): the authentication and authorization engine. Handles: Who is this user? (authentication journeys/trees). Are they allowed? (policy engine, XACML policies). Issue a token that proves it? (OAuth2/OIDC/SAML). PingAM is the "security checkpoint" — it's consulted on every login, every token issuance, and every authorization policy evaluation. Everything downstream trusts PingAM's tokens because PingAM's signing keys are the trust anchor. PingIDM (Identity Management): the lifecycle engine. Handles: Create, update, and delete user accounts (Joiner-Mover-Leaver). Sync identities between systems (HR → AD → PingDS → SaaS apps). Self-service (registration, profile update, password reset). PingIDM doesn't authenticate users — it manages the accounts that PingAM will later authenticate. PingDS (Directory Services): the identity store. A hardened LDAP/REST directory purpose-built for CIAM scale: hundreds of millions of entries, sub-millisecond reads, multi-master replication across data centers, and fine-grained access control. PingDS is the system of record — the authoritative source of user profile data. Both PingAM and PingIDM read/write PingDS. PingGateway (Identity Gateway): the enforcement proxy. Sits in front of APIs and applications, intercepts requests, validates tokens against PingAM, and either passes them through or rejects them. Enforces policy at the edge without requiring the downstream application to be "identity-aware." Also retrofits SSO onto legacy apps via header injection. Integration pattern: a user login touches all four: Gateway intercepts the login request → AM authenticates the user via a journey → AM issues tokens using claims from DS → IDM ensures the account is current and provisioned. An API call: Gateway intercepts → validates token with AM → AM checks policy → permits access.

In CIAM / Your Job: Knowing "which box does what" prevents the most common CIAM design mistakes. Examples from the real world: putting authorization logic in Spring Boot instead of AM's policy engine (breaks when policy changes require a redeploy); calling PingDS directly from Angular instead of going through AM's /userinfo endpoint (bypasses AM's access control layer); storing user profile data in your application database instead of PingDS (creates a shadow identity store that drifts from the canonical store). The platform's design intent is that your application knows nothing about identity — it only sees validated tokens and enforced policies delivered by the Ping stack.

1. The four engines

🔐 PingAM — Access Management

The front door. Authentication journeys/trees, SSO sessions, OAuth2/OIDC & SAML, MFA, adaptive risk, and the policy engine (who can access what). Formerly ForgeRock AM / OpenAM.

🔄 PingIDM — Identity Management

The lifecycle engine. Registration & self-service, managed objects, connectors (AD, Salesforce, Workday), sync & reconciliation, workflow. Formerly ForgeRock IDM / OpenIDM.

🗄️ PingDS — Directory Services

The identity store — a hardened LDAP directory built for hundreds of millions of consumer identities with replication & low latency. Often the system of record. Formerly ForgeRock DS / OpenDJ.

🚪 PingGateway — Identity Gateway

The enforcement point. A reverse proxy that fronts apps/APIs, validates tokens, enforces AM policy, and retrofits SSO onto legacy apps that can't speak OIDC. Formerly ForgeRock IG / OpenIG.

Rule of thumb: AM decides who you are & what you may do, IDM manages the account over time, DS stores it, and IG enforces it at the edge.

3. Self-managed vs the PingOne cloud

Self-managed

You run AM/IDM/DS/IG on your own infra (VMs/k8s). Maximum control & customization; you own upgrades, scaling, HA. The classic ForgeRock stack.

PingOne (cloud)

SaaS CIAM — PingOne services (MFA, Risk, Verify, DaVinci) consumed via APIs. No infra to run. PingOne Advanced Identity Cloud is the managed ForgeRock stack as a service.

DaVinci (orchestration)

The cloud's no-code flow builder — the DaVinci equivalent of AM's journeys, wiring connectors (social, MFA, fraud, HTTP) into a login/registration flow.

6. Recap

🏗️ A Ping/ForgeRock CIAM platform = PingAM (authenticate, SSO, OAuth/OIDC, journeys, policy) + PingIDM (registration, lifecycle, provisioning, reconciliation) + PingDS (the high-scale identity store) + PingGateway (edge enforcement for legacy/APIs) — run self-managed or as PingOne cloud, with DaVinci as the cloud's journey builder. AM decides, IDM manages, DS stores, IG enforces.
