🧩 What are structural vs behavioral design patterns — and where do you see them in Spring Boot?

Structural patterns describe how classes and objects are composed; behavioral patterns describe how they communicate and share responsibility. The big ones you already use in Spring: Builder (step-by-step construction — User.builder()…build()), Adapter (wrap an incompatible interface), Facade (hide a subsystem behind one call), Proxy (control access — how @Transactional/@Cacheable work), Command (a request as an object — undo/redo, queues), and Template Method (a base-class algorithm skeleton — Spring Batch's ItemProcessor).

  • Structural = composition; behavioral = communication.
  • Builder is everywhere — ResponseEntity, RestClient.builder(), Lombok @Builder.
  • Proxy powers Spring AOP — @Transactional/@Cacheable wrap your bean (self-calls bypass it).
  • Adapter + Facade tame multi-IdP — adapters normalize Ping/Entra to one interface.

Builder in Spring Boot

Builder pattern everywhere: HttpRequest.newBuilder(uri).GET().header("Auth","Bearer "+t).build(). ResponseEntity.ok().body(dto). UriComponentsBuilder.fromPath("/api/users/{id}").build(userId). RestClient.builder().baseUrl(url).defaultHeader("Accept","application/json").build(). Lombok @Builder: User.builder().name("Bobby").email("b@b.com").roles(List.of(ADMIN)).build(). MockMvc: mockMvc.perform(get("/api/users").header("Authorization","Bearer "+jwt)).andExpect(status().isOk()). Builder is the most used pattern in modern Java — you're using it constantly without realising.

Proxy in Spring AOP

Spring wraps your service in a CGLIB proxy: userService.createUser() actually calls the proxy first. The proxy adds @Transactional behaviour (begin tx → call real method → commit/rollback), @Cacheable (check cache → skip real call if hit → store result). This is transparent to callers — they just call userService.createUser(). How to detect: userService.getClass().getName() returns UserService$SpringCGLIB$0 (proxied) instead of UserService (not proxied). Self-invocation bypasses the proxy: this.createUser() skips the proxy's transaction management.

Adapter + Facade for IDPs

Adapter: Ping returns users as PingUserResource with getEntryDN(); your app needs UserDto with getId(). PingUserAdapter implements UserProvider { UserDto adapt(PingUserResource r) { return new UserDto(r.getEntryDN(), ...); } }. Entra has a different format — EntraUserAdapter adapts Microsoft Graph's com.microsoft.graph.models.User. Both adapters implement the same interface, so your service layer never sees the IDP-specific types. Facade: IdmFacade { UserDto getUser(String id) { return userIdpRouter.route(id).getUser(id); } }.

CIAM / Spring Boot: A Command pattern backs the audit log — AssignRoleCommand implements UserCommand { execute(); undo(); } stored in a CommandHistory enables role-assignment rollback. Template Method shows up in Spring Batch (extend AbstractItemStreamItemReader, implement doRead()) and Spring Security's AbstractSecurityInterceptor (beforeInvocation → proceed → afterInvocation).

Structural vs Behavioral — the distinction

Structural patterns describe how classes and objects are composed into larger structures. They use inheritance and composition to form new functionality from existing pieces. Key question: "How are these objects connected?"

Examples here: Adapter (connecting incompatible interfaces), Facade (hiding subsystem complexity), Composite (tree structures), Proxy (wrapping with extra behaviour).
Behavioral patterns describe how objects communicate and distribute responsibility. They characterize control flow and the ways objects interact. Key question: "Who does what and when?"

Examples here: Command (requests as objects with undo), Template Method (algorithm skeleton with overridable steps).

Builder — the telescoping constructor problem

BEFORE — telescoping constructors
class HttpRequest { // Which fields are required? Which optional? // What does the 3rd boolean mean? HttpRequest(String url) { ... } HttpRequest(String url, String method) { ... } HttpRequest(String url, String method, int timeout) { ... } HttpRequest(String url, String method, int timeout, boolean followRedirects) { ... } // ... 8 more constructors } // Call site — completely unreadable: new HttpRequest("https://api.example.com", "POST", 5000, true, false, null);
AFTER — Builder pattern
HttpRequest req = HttpRequest.newBuilder() .url("https://api.example.com") .method("POST") .timeout(5, TimeUnit.SECONDS) .header("Content-Type", "application/json") .followRedirects(true) .build(); // validates required fields // Self-documenting. Each setter is clearly named. // build() can throw if required fields missing.

Builder implementation — the static inner class pattern

public final class HttpRequest { // Immutable fields — set only by Builder private final String url; private final String method; private final int timeoutMs; private final Map<String,String> headers; private final boolean followRedirects; // Private constructor — ONLY the Builder can call it private HttpRequest(Builder b) { this.url = b.url; this.method = b.method; this.timeoutMs = b.timeoutMs; this.headers = Map.copyOf(b.headers); this.followRedirects = b.followRedirects; } public static Builder newBuilder() { return new Builder(); } public static class Builder { private String url; // required private String method = "GET"; // default private int timeoutMs = 30_000; // default private Map<String,String> headers = new HashMap<>(); private boolean followRedirects = true; // default // Each setter returns 'this' for chaining public Builder url(String url) { this.url = url; return this; } public Builder method(String m) { this.method = m; return this; } public Builder timeout(int ms) { this.timeoutMs = ms; return this; } public Builder header(String k, String v) { headers.put(k, v); return this; } public Builder followRedirects(boolean f) { this.followRedirects = f; return this; } public HttpRequest build() { if (url == null || url.isBlank()) throw new IllegalStateException("url is required"); return new HttpRequest(this); } } }

Adapter — make incompatible interfaces work together

Analogy: A travel power adapter lets your laptop plug (US type) work in a European socket. The adapter doesn't change either interface — it translates between them. In code, you have a target interface (what your code expects) and an adaptee (what you have). The Adapter class wraps the adaptee and implements the target interface.

Object Adapter — wrap the adaptee

The legacy / third-party class you have
// Old XML logger — can't modify this class XmlLogger { void writeXml(String tag, String msg) { System.out.printf("<%s>%s</%s>\n", tag, msg, tag); } } // New interface your system uses interface Logger { void log(String level, String message); }
The Adapter bridges them
class XmlLoggerAdapter implements Logger { private final XmlLogger adaptee; public XmlLoggerAdapter(XmlLogger xl) { this.adaptee = xl; } @Override public void log(String level, String message) { adaptee.writeXml(level, message); } } // Usage — caller only sees Logger Logger l = new XmlLoggerAdapter(new XmlLogger()); l.log("INFO", "App started");

Real-world adapter examples in the JDK

// Arrays.asList() adapts T[] (array) to List<T> String[] arr = {"a", "b", "c"}; List<String> list = Arrays.asList(arr); // adapter: array → List interface // Collections.enumeration() adapts Iterator to old Enumeration Enumeration<String> en = Collections.enumeration(list); // InputStreamReader adapts InputStream (bytes) to Reader (chars) Reader reader = new InputStreamReader(socket.getInputStream(), StandardCharsets.UTF_8); // Runnable → Callable adapter (Executors.callable()) Runnable r = () -> doWork(); Callable<Void> c = Executors.callable(r);
When to use Adapter: You're integrating a third-party library, migrating a codebase to a new interface, or bridging two subsystems that evolved independently. You should NOT need to modify either the adaptee or the target interface.

Facade — simplify access to a complex subsystem

Analogy: A car's dashboard is a facade. You don't interact with the fuel injectors, the alternator, the ignition coil — you turn a key (or press a button). The facade exposes one simple interface and hides the subsystem internals from you.

Home Theater Facade example

WITHOUT Facade — caller must coordinate everything
// Every caller does this 8-step dance: amplifier.on(); amplifier.setDvd(dvdPlayer); amplifier.setSurroundSound(); amplifier.setVolume(5); projector.on(); projector.setInput(dvdPlayer); projector.setWideScreenMode(); dvdPlayer.on(); dvdPlayer.play(movie); lights.dim(10); screen.down(); popcornMaker.on(); // And you have to remember the exact order...
WITH HomeTheaterFacade
class HomeTheaterFacade { private Amplifier amp; private Projector proj; private DvdPlayer dvd; private Lights lights; // ... other subsystems public void watchMovie(String movie) { amp.on(); amp.setVolume(5); proj.on(); proj.setWideScreenMode(); dvd.on(); dvd.play(movie); lights.dim(10); // all the complexity hidden here } public void endMovie() { /* reverse everything */ } } // Caller: theater.watchMovie("Inception"); // done!

Facade in Java frameworks

// SLF4J — facade over Log4j, Logback, java.util.logging // Your code always calls the same Logger interface: Logger log = LoggerFactory.getLogger(MyClass.class); log.info("Service started"); // SLF4J routes to whichever impl is on the classpath at runtime // Spring's JdbcTemplate — facade over JDBC // Without JdbcTemplate you need: // connection = dataSource.getConnection() // preparedStatement = connection.prepareStatement(...) // resultSet = stmt.executeQuery() // while (rs.next()) { ... } // rs.close(); stmt.close(); conn.close() <-- easy to forget! // With JdbcTemplate (facade): List<Employee> staff = jdbc.query( "SELECT * FROM employees WHERE dept = ?", rowMapper, "Engineering"); // Connection lifecycle, exception translation all handled for you
Facade vs Adapter: An Adapter changes an existing interface into a different existing interface. A Facade defines a new simplified interface that didn't exist before. Facade is about reducing complexity; Adapter is about compatibility.

Composite — treat leaf and container uniformly

// Common interface for both File and Directory interface FileSystemItem { String getName(); long getSize(); // File: bytes; Directory: sum of children void print(String indent); } // Leaf — no children class File implements FileSystemItem { private final String name; private final long size; @Override public long getSize() { return size; } @Override public void print(String indent) { System.out.println(indent + "[F] " + name + " (" + size + "b)"); } } // Composite — has children, delegates to them class Directory implements FileSystemItem { private final String name; private final List<FileSystemItem> children = new ArrayList<>(); public void add(FileSystemItem item) { children.add(item); } @Override public long getSize() { return children.stream().mapToLong(FileSystemItem::getSize).sum(); // recursion — a dir delegates to children, which may themselves be dirs } @Override public void print(String indent) { System.out.println(indent + "[D] " + name + " (" + getSize() + "b)"); children.forEach(c -> c.print(indent + " ")); } } // Client code works identically on a single File or an entire Directory tree: void printTotal(FileSystemItem item) { item.print(""); System.out.println("Total: " + item.getSize() + " bytes"); // Doesn't care if item is a File or a Directory — same interface }

File system tree visualizer

This tree is a Composite. Every node implements the same FileSystemItem interface. Size of each directory is the sum of all its children.

Other Composite examples

// Swing / JavaFX UI: Component (leaf) and Container (composite) // Container.paint() calls paint() on all children recursively // HTML DOM: Element can be a leaf (text) or a container (div with children) // java.awt.Component hierarchy: // Component (abstract — leaf and composite share interface) // ← Button, Label (leaf) // ← Container // ← Panel, JPanel, JFrame (composite) // Expression trees in compilers: // Expression (interface) // ← Literal(42) — leaf // ← Add(left, right) — composite of two Expressions // ← Multiply(left, right) — composite // eval() is implemented by each: Literal returns 42, Add returns left.eval()+right.eval()

Proxy — a surrogate that controls access

The Proxy implements the same interface as the real object, so clients can't tell the difference. The proxy intercepts calls and can add behavior before or after delegating to the real object — or refuse to delegate at all.

Four proxy variants

Virtual Proxy — lazy initialization
// Heavy object — don't create until needed class ImageProxy implements Image { private RealImage realImage; private final String filename; public ImageProxy(String f) { this.filename = f; } @Override public void display() { if (realImage == null) realImage = new RealImage(filename); // load once realImage.display(); } }
Caching Proxy
class CachingServiceProxy implements Service { private final Service real; private final Map<String,Result> cache = new HashMap<>(); @Override public Result query(String key) { return cache.computeIfAbsent(key, real::query); } }
Protection Proxy
class SecureDocProxy implements Document { private final Document real; private final User user; @Override public String read() { if (!user.hasRole("DOC_READER")) throw new SecurityException("Access denied"); return real.read(); } }
Logging Proxy
class LoggingProxy implements Service { private final Service real; @Override public Result query(String k) { log.info("query({}) called", k); Result r = real.query(k); log.info("query({}) returned {}", k, r); return r; } }
Spring AOP (Aspect-Oriented Programming) uses dynamic JDK proxies or CGLIB byte-code proxies under the hood. Every @Transactional, @Cacheable, @Secured annotation works by wrapping your bean in a proxy that intercepts method calls — exactly the Proxy pattern at framework scale.

Command — encapsulate a request as a first-class object

// Command interface — all requests look the same interface Command { void execute(); void undo(); } // Concrete command — wraps a receiver and its arguments class InsertTextCommand implements Command { private final TextEditor editor; private final int pos; private final String text; public InsertTextCommand(TextEditor e, int pos, String text) { this.editor = e; this.pos = pos; this.text = text; } @Override public void execute() { editor.insertAt(pos, text); } @Override public void undo() { editor.deleteAt(pos, text.length()); } } // Invoker — stores history, enables undo class CommandHistory { private final Deque<Command> history = new ArrayDeque<>(); public void execute(Command cmd) { cmd.execute(); history.push(cmd); } public void undo() { if (!history.isEmpty()) history.pop().undo(); } }

Command pattern beyond undo — other real uses

// Task queue — commands are queued and executed later BlockingQueue<Command> queue = new LinkedBlockingQueue<>(); queue.offer(() -> sendEmail(to, subject, body)); // lambda as Command queue.offer(() -> updateDatabase(record)); // Worker thread drains queue: while(true) { queue.take().execute(); } // Transaction script — all or nothing class TransferCommand implements Command { void execute() { debit(from, amount); credit(to, amount); } void undo() { credit(from, amount); debit(to, amount); } } // Runnable and Callable are the Command pattern! // executor.submit(task) — task IS the command, executor IS the invoker Runnable r = () -> processFile(file); executor.submit(r);

Template Method — fix the algorithm skeleton, vary the steps

// Abstract base class defines the template method and abstract hooks abstract class Game { // THE TEMPLATE METHOD — final: subclasses cannot change the sequence public final void play() { initialize(); // step 1 — abstract, must override while (!isDone()) { // step 2 — hook method (has default behaviour) makeMove(); // step 3 — abstract, must override } printResult(); // step 4 — concrete with default, may override } protected abstract void initialize(); // hook — no default protected abstract void makeMove(); // hook — no default protected boolean isDone() { return false; } // hook — has a default protected void printResult() { System.out.println("Game over"); } // default ok } class Chess extends Game { private int moves = 0; @Override protected void initialize() { System.out.println("Chess board set up"); } @Override protected void makeMove() { moves++; System.out.println("Move " + moves); } @Override protected boolean isDone() { return moves >= 3; } } class TicTacToe extends Game { // Different initialization, different move logic — same play() sequence } // Usage: both play the same sequence, different implementation new Chess().play(); new TicTacToe().play();

Template Method in the JDK

// AbstractList — provides iterator(), indexOf(), contains() based on get() and size() abstract class AbstractList<E> extends AbstractCollection<E> { // Template methods defined in terms of the abstract methods below: public Iterator<E> iterator() { /* uses get(i) and size() */ } public int indexOf(Object o) { /* uses get(i) and size() */ } // Hooks — subclasses implement these two: public abstract E get(int index); public abstract int size(); } // HttpServlet — doGet() / doPost() are template hooks public class MyServlet extends HttpServlet { @Override protected void doGet(HttpServletRequest req, HttpServletResponse resp) { // HttpServlet.service() calls doGet() for GET requests — template method resp.getWriter().write("Hello"); } } // Comparable.compareTo() used as a hook inside Collections.sort() // InputStream — read(byte[]) is implemented in terms of abstract read()
Template Method vs Strategy: Both let you vary part of an algorithm. Template Method uses inheritance — the variation is in a subclass method. Strategy uses composition — the variation is a separate object passed in. Prefer Strategy when you want to change behavior at runtime or avoid deep inheritance hierarchies.
