AWS Load Balancing & Auto Scaling

Two AWS services that only make sense as a pair: a load balancer decides which healthy instance gets each request, and an Auto Scaling Group decides how many instances exist in the first place — each one feeding the other a signal.

⚖️ How do a load balancer and Auto Scaling actually cooperate?

An Application Load Balancer (ALB) operates at layer 7 (HTTP/HTTPS) — it can route by path (/api/* to one target group, /admin/* to another), by hostname, and it terminates TLS. A Network Load Balancer (NLB) operates at layer 4 (raw TCP/UDP) — it doesn't look inside the request at all, which makes it faster and able to handle millions of requests per second, but it can't do path-based routing; use it for non-HTTP protocols or when you need a static IP per AZ. Both route traffic to a target group — a named pool of registered targets (EC2 instances, IPs, or Lambda functions) that the load balancer continuously health-checks on a schedule (e.g. GET /actuator/health every 30s). A target that fails enough consecutive checks is marked unhealthy and the load balancer simply stops sending it traffic — no restart, no scaling event, just removal from rotation until it recovers. Auto Scaling Groups (ASGs) are the other half: they watch a metric (usually CPUUtilization via CloudWatch) against a scaling policy — target tracking ("keep average CPU near 50%"), step scaling (bigger jumps for bigger breaches), or scheduled (before a known traffic spike) — and launch or terminate instances from a launch template to match. The two systems are wired together by one detail worth internalizing: when an ASG launches a new instance, it doesn't send it traffic immediately — it waits for the ALB's target group to report the instance as healthy first. Scaling and load balancing are two independent control loops that only work together because health checks are the signal connecting them.

  • ALB vs NLB — ALB routes on HTTP content (path/host, layer 7); NLB moves raw TCP/UDP (layer 4) at much higher throughput with no content awareness.
  • Target group + health check — a named pool of targets; failed health checks silently remove a target from rotation, no restart or scaling triggered by that alone.
  • Scaling policies — target tracking (hold a metric near a setpoint), step scaling (tiered response to breach size), scheduled (pre-provision for known spikes).
  • The handoff — a newly launched instance only receives traffic once it passes the target group's own health check — launching and being "in service" are two different moments.

ALB vs NLB, when to pick which

Default to ALB for a Spring Boot REST API — path-based routing and TLS termination are usually worth more than NLB's raw throughput. Reach for NLB only for non-HTTP TCP services or when you need a fixed IP per AZ that some client can't work around.

Health checks are silent

An unhealthy target isn't restarted or replaced by the load balancer itself — it's just excluded from routing. Replacing it is the ASG's job, driven by a separate EC2-status or ELB-health check of its own.

Scale-out is not instant

Launch → boot → user-data script → app startup → pass health check is a real pipeline with real latency (often 1-3 minutes for a JVM app) — target tracking has to account for that lag or it will over-scale while waiting.

CIAM / production shape: a Spring Boot CIAM API sits in a target group behind an ALB, health-checked on /actuator/health (which should itself check the DB connection pool, not just "the JVM is up"). The ASG's target-tracking policy on CPU keeps capacity matched to OAuth/token-validation load; because JWT validation is CPU-bound (signature verification) rather than I/O-bound, CPU-based scaling tracks real load well here — a service that was mostly waiting on a slow downstream call would need a different metric (e.g. request count per target) instead.

A few things worth knowing

  • Health check ≠ liveness check — a well-designed /actuator/health endpoint should reflect whether the instance can actually serve traffic (DB reachable, downstream deps OK), not just "the process is running." A JVM that's up but can't reach its database should fail the check.
  • Deregistration delay — when a target is removed (scale-in or manual), the ALB keeps draining in-flight requests to it for a configurable window (default 300s) before fully cutting it off, so scale-in doesn't drop active requests.
  • Scaling policies compose — it's common to run a target-tracking policy for steady-state plus a scheduled policy to pre-scale before a known traffic pattern (e.g. a batch job that hits the API every morning at 6am).
