AWS Load Balancing & Auto Scaling

Two AWS services that only make sense as a pair: a load balancer decides which healthy instance gets each request, and an Auto Scaling Group decides how many instances exist in the first place — each one feeding the other a signal.

⚖️ How do a load balancer and Auto Scaling actually cooperate?

An Application Load Balancer (ALB) operates at layer 7 (HTTP/HTTPS) — it can route by path (/api/* to one target group, /admin/* to another), by hostname, and it terminates TLS. A Network Load Balancer (NLB) operates at layer 4 (raw TCP/UDP) — it doesn't look inside the request at all, which makes it faster and able to handle millions of requests per second, but it can't do path-based routing; use it for non-HTTP protocols or when you need a static IP per AZ. Both route traffic to a target group — a named pool of registered targets (EC2 instances, IPs, or Lambda functions) that the load balancer continuously health-checks on a schedule (e.g. GET /actuator/health every 30s). A target that fails enough consecutive checks is marked unhealthy and the load balancer simply stops sending it traffic — no restart, no scaling event, just removal from rotation until it recovers. Auto Scaling Groups (ASGs) are the other half: they watch a metric (usually CPUUtilization via CloudWatch) against a scaling policy — target tracking ("keep average CPU near 50%"), step scaling (bigger jumps for bigger breaches), or scheduled (before a known traffic spike) — and launch or terminate instances from a launch template to match. The two systems are wired together by one detail worth internalizing: when an ASG launches a new instance, it doesn't send it traffic immediately — it waits for the ALB's target group to report the instance as healthy first. Scaling and load balancing are two independent control loops that only work together because health checks are the signal connecting them.

  • ALB vs NLB — ALB routes on HTTP content (path/host, layer 7); NLB moves raw TCP/UDP (layer 4) at much higher throughput with no content awareness.
  • Target group + health check — a named pool of targets; failed health checks silently remove a target from rotation, no restart or scaling triggered by that alone.
  • Scaling policies — target tracking (hold a metric near a setpoint), step scaling (tiered response to breach size), scheduled (pre-provision for known spikes).
  • The handoff — a newly launched instance only receives traffic once it passes the target group's own health check — launching and being "in service" are two different moments.

ALB vs NLB, when to pick which

Default to ALB for a Spring Boot REST API — path-based routing and TLS termination are usually worth more than NLB's raw throughput. Reach for NLB only for non-HTTP TCP services or when you need a fixed IP per AZ that some client can't work around.

Health checks are silent

An unhealthy target isn't restarted or replaced by the load balancer itself — it's just excluded from routing. Replacing it is the ASG's job, driven by a separate EC2-status or ELB-health check of its own.

Scale-out is not instant

Launch → boot → user-data script → app startup → pass health check is a real pipeline with real latency (often 1-3 minutes for a JVM app) — target tracking has to account for that lag or it will over-scale while waiting.

CIAM / production shape: a Spring Boot CIAM API sits in a target group behind an ALB, health-checked on /actuator/health (which should itself check the DB connection pool, not just "the JVM is up"). The ASG's target-tracking policy on CPU keeps capacity matched to OAuth/token-validation load; because JWT validation is CPU-bound (signature verification) rather than I/O-bound, CPU-based scaling tracks real load well here — a service that was mostly waiting on a slow downstream call would need a different metric (e.g. request count per target) instead.

The problem

Nothing ever errors. Nothing ever pages on its own. Your on-call just stares at a CPU graph that makes no sense.

One task at 95% CPU, three idling under 15%, and total traffic hasn't moved

Your CIAM API is stateless by design — every request carries its own JWT, validated fresh, no server-side session anywhere. Someone enables ALB sticky sessions on the target group anyway, "cheap insurance," 7-day cookie duration, and moves on. Load tests look fine. Nothing in code changed. Nothing in the deploy pipeline changed.

Three weeks later, on-call gets paged for a target-tracking scale-out that doesn't make sense: one ECS task is pinned at 95% CPU, its three siblings are idling under 15%, and total request volume across the service hasn't spiked at all. The autoscaling math is watching the average, so it just quietly adds a task to fix a problem that was never about total load — it was about where that load was landing.

JWT signature verification ✓ health checks passing on every task ✓ target-tracking policy doing its job ✓ the thing that is not ⚠ a routing decision nobody thought was a routing decision

Every layer you'd normally suspect is innocent. The layer that's guilty is the one setting that looked too boring to be load-bearing.

Turn stickiness off for anything that's actually stateless
Check whether anything server-side actually needs affinity ↓ a JWT-validated API has no session to protect — stickiness has nothing to do and only downside left to give If you're not sure, look at per-target request count in CloudWatch before you flip it ↓ a real skew across otherwise-identical targets confirms the theory instead of guessing under pressure And if one specific caller genuinely needs affinity, scope it narrowly ↓ a short duration, or an application cookie your own code issues and controls, beats a blanket multi-day default applied to every client alike
Stickiness pins the connection, not the authentication. A JWT re-proves who the caller is on every single request, which is exactly why a stateless API never needed a pinned target in the first place. Turning stickiness on doesn't make a stateless service safer — it just hands one lucky (or unlucky) target a client it can never hand back until the cookie says so.
A sticky note is supposed to hold one page in place. It was never supposed to hold one-seventh of your entire traffic in place for a week at a time — but that's exactly what a 7-day duration on your heaviest caller's cookie does.

The mechanism

Walk it forward one request at a time and the trap builds itself.

  1. A client sends its very first request — no AWSALB cookie present yet.no cookie
  2. The ALB's normal algorithm (round robin, or least-outstanding-requests) picks a target for this one request — say, Task B.normal routing
  3. Because stickiness is enabled on the target group, the ALB now generates an AWSALB cookie encoding Task B's identity, encrypts it, sets it to expire in 7 days, and returns it with the response.cookie issued
  4. Every later request from that same client presents the cookie. The ALB decodes it and forwards straight to Task B — the load-balancing algorithm from step 2 is never consulted again for this client.bypasses the algorithm
  5. This particular client happens to be your busiest machine caller — a token-introspection consumer making thousands of requests a minute — and none of that traffic gets rebalanced for the full 7 days, because nothing about this looks wrong from the ALB's side.quiet accumulation
  6. Target-tracking autoscaling watches average CPU across the whole target group. Three idle siblings pull that average down, so the one metric that would explain the problem is never the one anything is alarming on.the blind spot

Step 4 is the whole story in one sentence: stickiness doesn't bias the load-balancing algorithm toward fairness, it replaces it entirely for every client holding a valid cookie. A perfectly reasonable per-request algorithm and a perfectly reasonable per-client memory combine into something neither one would do alone.

First contact — no cookie round robin picks a target → Task B gets this client, ALB issues an AWSALB cookie naming Task B
Every request after — cookie present stickiness enabled, 7-day duration → all of this client's traffic pinned to Task B, load-balancing algorithm skipped entirely
Task B deregistered — deploy or scale-in cookie now names a target that no longer exists → ALB quietly picks a new target and re-signs the cookie — no error, no alert, no client-visible failure
New pin forms — same client, same habits next request carries the new cookie → whichever task it landed on this time becomes the next hot spot

That third state is the part worth sitting with. AWS designed the failover to be graceful on purpose — a deregistered or unhealthy target just gets silently swapped out, cookie and all. That's good engineering for the failure it's solving, and it's exactly why this gotcha never shows up as an error rate anyone would notice. The imbalance just relocates to a new task and keeps going.

Your CIAM API validates a fresh JWT on every request — there is no server-side session anywhere in the design. Someone enables ALB sticky sessions on it anyway, 7-day cookie duration, "cheap insurance." Three weeks later on-call gets paged: one ECS task is pinned at 95% CPU while its three siblings idle under 15%, with no spike in total request volume across the service. What is actually going on?

Exactly. Duration-based stickiness (the AWSALB cookie) pins a client to whichever target it first landed on, for however long you configured — up to 7 days. It has nothing to do with load, health, or fairness; it's a lookup table with one row per cookie. A single chatty machine client sending thousands of requests a minute, every one carrying that same cookie, lands every one of them on the same task, because the ALB is honoring the cookie instead of re-running its load-balancing algorithm.

JIT warm-up is real, but it resolves itself within the first couple of minutes of a task's life, not three weeks in — and it wouldn't explain why the SAME task stays hot indefinitely while identically-deployed siblings stay idle the whole time.

Health check interval is a target-group-level attribute applied identically to every target behind it — one task can't be checked more often than its siblings, and a lightweight GET every 30 seconds doesn't move CPU by 80 points regardless.

Where you have seen this before

Pinning-by-accident is not an AWS-specific idea — it's what happens anywhere a cache outlives the thing it's caching.

A gRPC client that resolved once and never let go

A thick client that looks up one backend address at startup and keeps a persistent connection alive for the life of the process is making the same trade: great latency, right up until that one backend becomes the only one anybody is actually hitting.

resolve once, pay for it for the process's whole lifetime

A naive consistent-hash ring with no load awareness

Hashing a key to a node is a clean idea right up until one key is far hotter than the rest — the ring doesn't know that, so it keeps sending every request for that key to the same unlucky node no matter how many nodes you add to the cluster.

the algorithm is fair per-key, not fair per-node

A DNS record with a huge TTL outliving the box it points to

The server behind it can be long gone; the cache doesn't know that until its own clock runs out. The bug was never in the DNS system — it was in a duration someone set once and then forgot was still ticking.

the failure mode is the cache's duration, not the resource it describes
The whole page on a napkin: an ALB and an ASG are two independent control loops that only cooperate through health checks — the ALB decides who's healthy enough to receive traffic, the ASG decides how many targets should exist at all. The one new sentence this block adds: a "harmless" load-balancer checkbox like sticky sessions can quietly defeat that whole cooperation by welding one client's traffic to one target for days at a time, and because the failover is graceful by design, the only symptom you'll ever see is a CPU graph that looks like a mystery.

A few things worth knowing

  • Health check ≠ liveness check — a well-designed /actuator/health endpoint should reflect whether the instance can actually serve traffic (DB reachable, downstream deps OK), not just "the process is running." A JVM that's up but can't reach its database should fail the check.
  • Deregistration delay — when a target is removed (scale-in or manual), the ALB keeps draining in-flight requests to it for a configurable window (default 300s) before fully cutting it off, so scale-in doesn't drop active requests.
  • Scaling policies compose — it's common to run a target-tracking policy for steady-state plus a scheduled policy to pre-scale before a known traffic pattern (e.g. a batch job that hits the API every morning at 6am).
