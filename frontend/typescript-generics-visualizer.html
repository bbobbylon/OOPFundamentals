Generics Foundations

How to write functions, classes, and types that work for any shape — without giving up type safety. Generics are TS's superpower; once they click, half the standard library makes sense.

🧬 What are generics? Why do they exist?

Say you need a function that returns the first element of an array. Hard-code it for number[] and it's useless for strings; use any and you throw away all type information. Generics solve this with a type parameter — a placeholder filled in per call: function first<T>(arr: T[]): T { return arr[0] }. TypeScript infers T from the argument (first([1,2,3]) → number), so the result is exactly T, never any — one function, infinite types, full safety.

  • A type parameter is a placeholder filled per call — usually inferred, rarely written.
  • Generics preserve type info where any discards it.
  • You already use them everywhere — Array<T>, Promise<T>, Observable<T>, Map<K,V>.
  • Constraints restrict T — <T extends { id: string }> requires an id.

You already use generics

Array<string> (generic array), Promise<User> (async result), Observable<User[]> (RxJS stream), Map<string, Session> (generic map).

Constraints restrict T

function getId<T extends { id: string }>(obj: T): string { return obj.id } — T must have an .id; anything else is a compile error.

Angular / Spring / CIAM: Angular's HttpClient.get<User[]>(url) is a generic call — you tell it the response type. ApiResponse<T> wrappers, FormControl<string>, Signal<User>, and JWT-payload generics are all daily Angular work.

1. Why generics exist

Without generics, you face an ugly tradeoff: write the same function ten times for ten types, or use any and lose type checking entirely. Generics let one function describe its relationship between input and output, and TS fills in the actual types per call.

😬 Without generics

function firstString(xs: string[]): string {
  return xs[0];
}
function firstNumber(xs: number[]): number {
  return xs[0];
}
// ...and one per type, forever.

// or use any:
function first(xs: any[]): any {
  return xs[0]; // no type safety at all
}

✨ With generics

function first<T>(xs: T[]): T {
  return xs[0];
}

first([1, 2, 3]);     // T = number → returns number
first(['a', 'b', 'c']); // T = string → returns string
first([true]);          // T = boolean → returns boolean
Read <T> as "for any type T". A function with <T> in its signature is a family of functions — one per type the caller plugs in. TS picks the right one for each call site.

2. Your first generic function

// The angle brackets <T> introduce a type parameter named T.
// You can use any letter — T, U, K, V are conventional.
// For clarity in big APIs, use full words: <Item>, <Key>.

function identity<T>(x: T): T {
  return x;
}

// Explicit type argument:
identity<string>('hi');  // returns string

// Inferred (the usual case):
identity(42);            // T = number — TS figured it out from the argument

An identity function looks trivial, but the type signature already encodes a strong promise: "whatever you give me, you'll get back the same type". (x: any) => any says nothing — it could return anything. <T>(x: T) => T says everything.

3. Type-argument inference

You almost never pass type arguments explicitly. TS works them out from the regular arguments at the call site.

Live: see TS infer T for each call

function map<A, B>(xs: A[], f: (x: A) => B): B[] {
  return xs.map(f);
}

map([1, 2, 3], x => x.toString());
// A = number (from the array)
// B = string (from the callback's return type)
// result: string[]
Inference is contextual: TS sees the array's element type, then carries it into the callback. That's why the x parameter doesn't need an annotation — TS already knows it's number.

4. Multiple type parameters

Functions often relate two or more types. List them in the angle brackets, separated by commas.

function pair<A, B>(a: A, b: B): [A, B] {
  return [a, b];
}

pair('hello', 42);  // [string, number]
pair(true, [1, 2]);  // [boolean, number[]]

function zip<A, B>(as: A[], bs: B[]): [A, B][] {
  return as.map((a, i) => [a, bs[i]]);
}

zip([1, 2], ['a', 'b']);
// [number, string][]

5. Constraints with extends

Sometimes "any T" is too loose — you need T to at least have a .length, or be an object, or be a string. Constrain it with extends:

function longest<T extends { length: number }>(a: T, b: T): T {
  return a.length >= b.length ? a : b;
}

longest('hello', 'hi');          // ✅ string has .length
longest([1, 2, 3], [1]);          // ✅ arrays have .length
longest(10, 20);                  // ❌ number has no .length
"extends" doesn't mean inheritance. Read it as "assignable to". T extends { length: number } means "T must be a type whose values are assignable to { length: number }" — i.e. they have at least that field. It's structural, not nominal.

Constraining to a key of an object

function get<T, K extends keyof T>(obj: T, key: K): T[K] {
  return obj[key];
}

const user = { id: 1, name: 'Bob', admin: true };
get(user, 'name');    // returns string
get(user, 'admin');   // returns boolean
get(user, 'email');   // ❌ "email" doesn't exist on user

This is the keyof + indexed-access combo — the foundation of Pick, Record, and most utility types.

6. Default type parameters

Like default function arguments, but at the type level. Used heavily by library APIs so the common case requires no <...>.

type ApiResponse<T = unknown> = {
  status: number;
  data: T;
};

const a: ApiResponse = { status: 200, data: { whatever: true } };
// a.data: unknown — must narrow before use

const b: ApiResponse<User> = { status: 200, data: { id: 1, name: 'Bob' } };
// b.data: User

Defaults can reference earlier parameters, just like JS:

type Result<T, E = Error> =
  | { ok: true;  value: T }
  | { ok: false; error: E };

type Saved  = Result<User>;            // E defaults to Error
type Parsed = Result<User, SyntaxError>;

7. keyof & indexed access

Two operators that together let you reach inside an object type:

OperatorMeansExampleResult
keyof TUnion of T's keyskeyof { a: 1; b: 2 }'a' | 'b'
T[K]The type of T's K property{ a: string }['a']string
T[keyof T]Union of T's value types{ a: string; b: number }[keyof T]string | number
T[number]Element type of a tuple/array['a', 'b', 'c'][number]'a' | 'b' | 'c'
type User = { id: number; name: string; admin: boolean };

type UserKey   = keyof User;        // 'id' | 'name' | 'admin'
type UserName  = User['name'];      // string
type UserField = User[keyof User]; // number | string | boolean

8. Generic classes

Put the type parameter on the class. Every instance is parameterized for the lifetime of that instance.

class Stack<T> {
  private items: T[] = [];
  push(x: T): void { this.items.push(x); }
  pop(): T | undefined { return this.items.pop(); }
  peek(): T | undefined { return this.items[this.items.length - 1]; }
  get size(): number { return this.items.length; }
}

const ns = new Stack<number>();
ns.push(1);          // ✅
ns.push('two');      // ❌ Argument of type 'string' is not assignable
ns.pop();             // number | undefined

// Inference also works for constructors when there's a parameter:
class Box<T> { constructor(public value: T) {} }
const b = new Box('hi'); // Box<string>
Static members can't use class type parameters. The type parameter belongs to the instance; statics are per-class. If you need a generic factory, make it a generic method or a free function.

9. Generic interfaces & types

Same syntax as functions and classes — angle brackets after the name.

interface Repository<T> {
  findById(id: string): Promise<T | null>;
  save(item: T): Promise<T>;
  delete(id: string): Promise<void>;
  list(): Promise<T[]>;
}

class UserRepo implements Repository<User> {
  async findById(id: string): Promise<User | null> { /* ... */ }
  // ...rest of methods, fully typed for User
}

// type aliases work the same way:
type Dict<V> = { [key: string]: V };
type Pair<A, B> = [A, B];

10. Live demo: typed EventBus

Generics shine in pub/sub APIs. Each event name has its own payload type — emit and on are type-safe per event.

type EventMap = {
  login:    { userId: string; at: Date };
  logout:   { userId: string };
  purchase: { sku: string; amount: number };
};

class EventBus<M> {
  private handlers: { [K in keyof M]?: ((p: M[K]) => void)[] } = {};

  on<K extends keyof M>(event: K, fn: (p: M[K]) => void): void {
    (this.handlers[event] ??= []).push(fn);
  }

  emit<K extends keyof M>(event: K, payload: M[K]): void {
    this.handlers[event]?.forEach(fn => fn(payload));
  }
}

const bus = new EventBus<EventMap>();

bus.on('login', p => console.log(p.userId, p.at)); // p is typed!
bus.emit('login', { userId: 'u1', at: new Date() });

bus.emit('login', { sku: 'x', amount: 9 }); // ❌ wrong shape
bus.on('banana', () => {});                  // ❌ no such event

11. Generic functions in practice

Three patterns that show up constantly.

Pluck — extract a field from each item

function pluck<T, K extends keyof T>(xs: T[], key: K): T[K][] {
  return xs.map(x => x[key]);
}

const users = [{ id: 1, name: 'A' }, { id: 2, name: 'B' }];
pluck(users, 'id');   // number[]
pluck(users, 'name'); // string[]
pluck(users, 'age');  // ❌

GroupBy — partition by a key function

function groupBy<T, K extends PropertyKey>(
  xs: T[],
  key: (x: T) => K
): Record<K, T[]> {
  return xs.reduce((acc, x) => {
    const k = key(x);
    (acc[k] ??= []).push(x);
    return acc;
  }, {} as Record<K, T[]>);
}

groupBy([1, 2, 3, 4], n => n % 2 === 0 ? 'even' : 'odd');
// Record<'even' | 'odd', number[]>

Once — memoize a parameterless function

function once<T>(fn: () => T): () => T {
  let called = false;
  let value: T;
  return () => {
    if (!called) { value = fn(); called = true; }
    return value;
  };
}

const getConfig = once(() => ({ apiUrl: '/api', timeout: 5000 }));
getConfig(); // runs the body
getConfig(); // cached — same object back, still fully typed

12. Where you can't put generics

Generic on…Allowed?
function declarations / expressions✅
arrow functions (with workaround for JSX — see note)✅
class declarations✅
methods (each method can introduce its own)✅
interfaces & type aliases✅
static class members❌ can't use the class's type parameter (own ones OK)
enum members❌
JSX inline: <T>(x: T) => x in a .tsx file⚠ ambiguous with JSX — use <T,> or <T extends unknown>
// JSX-safe generic arrow:
const identity = <T,>(x: T): T => x;
// or:
const identity2 = <T extends unknown>(x: T): T => x;

13. Common bugs

Generic resolves to unknown or {} TS had nothing to infer from — the type parameter never appears in any argument Pass an argument that uses T, or make the call explicit: fn<User>()
"Type 'X' does not satisfy the constraint" The type you passed doesn't meet the extends clause Either loosen the constraint or pass a compatible type
Inference gets a literal instead of widened type (or vice versa) TS widens type arguments by default; you may need as const fn(['a', 'b'] as const) to preserve literals
Generic class but every instance ends up any Constructor has no argument that mentions T Pass the type explicitly: new Box<User>()
"Cannot find name T" Used T outside the scope it was declared Generics are scoped to the function/class/type they're declared on
Generic method on a generic class: parameter shadowed Method declares <T> matching the class's <T> name Use a different letter on the method (<U>)
JSX file: const f = <T>(x: T) => x won't parse TSX thinks <T> is a tag <T,> or <T extends unknown>

The "infer T from this argument" trap

// ❌ Surprising — TS infers T as 'string', not 'red' | 'blue'
function pickFrom<T>(xs: T[]): T { return xs[0]; }
const r = pickFrom(['red', 'blue']); // r: string

// ✅ Two fixes — your choice depending on intent:
const r1 = pickFrom(['red', 'blue'] as const); // r1: 'red' | 'blue'
const r2 = pickFrom<'red' | 'blue'>(['red', 'blue']);

Sequence for designing a generic API: (1) write the concrete, non-generic version first; (2) circle the types that should vary per caller — those become <T>, <K>; (3) check that inference works at the call site without explicit type args; (4) add extends only if you actually call methods/properties on the parameter inside. Premature constraints kill flexibility.

🌱 New to generics? Think "a blank you fill in with a type."

A function takes value parameters in ( ). A generic takes a type parameter in < >. That's the whole idea. Box<T> is "a box of some type T"; Box<string> is a box of strings. The classic: function first<T>(arr: T[]): T — pass an array of strings, you get a string back; pass numbers, you get a number. Without generics you'd have to either give up and use any (losing all safety) or copy the function once per type. Generics let one piece of code stay type-safe across every type a caller throws at it.

🧠 Expert corner — inference, constraints, and not over-constraining

  • Let inference do the work. You almost never write first<number>([1,2]) — TypeScript infers T from the argument. Explicit type args are a smell unless inference genuinely can't see it.
  • Constrain only when you must. <T extends {length:number}> lets you read .length inside — but adding extends you don't need just narrows what callers can pass. Start unconstrained.
  • Defaults & multiple params. <T = string> gives a fallback; Map<K, V> carries two. Generics work on functions, classes, interfaces, and type aliases alike.
  • They're the foundation of the type system. Conditional types (T extends U ? X : Y), mapped types ({[K in keyof T]}), and the utility types are all generics underneath — see Conditional / Mapped types.
  • CIAM tie-in. A typed ApiResponse<T> or Page<T> that mirrors Spring's Page<T> gives you end-to-end typed pagination — one generic, every endpoint.
