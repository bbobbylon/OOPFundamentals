angular.json — Deep Dive: Builders, Budgets & Build Optimization

⚙️ What is angular.json's build target — and why do builders, budgets, and optimization flags determine what ships to users?

The angular.json build target is the most important section in the file — it controls what JavaScript bundles the Angular CLI produces, how large they can be, and how aggressively they're optimized. Angular 17+ uses esbuild (via the @angular-devkit/build-angular:application builder) by default, replacing the older Webpack-based builder. esbuild is 10-100x faster than Webpack. The optimization object controls: minification (removes whitespace, renames variables to single letters), tree-shaking (eliminates unused code), font inlining, and CSS optimization. Output hashing: "outputHashing": "all" adds a content hash to every output filename (main.a1b2c3d4.js). This enables aggressive browser caching — the filename only changes when content changes, so returning users don't re-download unchanged bundles. Budgets are the most underused feature: you define maximum sizes for the entire application and individual components. If a bundle exceeds the budget, the build FAILS with an error. This is a CI/CD guardrail — prevents bundle size regressions silently shipping to production. File replacements: each configuration (production, staging, development) can swap environment files at build time. The source code always imports environment.ts, but the build substitutes environment.prod.ts when building for production. Builders: builders are plugins — you can write custom builders or use community ones (Storybook, Tailwind CSS, custom Webpack). The builder string identifies the npm package and exported builder class: @angular-devkit/build-angular:application = package @angular-devkit/build-angular, builder export application.

Budgets (size limits)

// angular.json: budgets in production config "budgets": [ { "type": "initial", // entire initial bundle "maximumWarning": "500kB", // warn at 500KB "maximumError": "1MB" // fail build at 1MB }, { "type": "anyComponentStyle", "maximumWarning": "2kB", // per-component CSS "maximumError": "4kB" } ] // If exceeded: // ERROR: budget exceeded: initial exceeded by 234kB // Build FAILS — prevents silent regression // Good defaults for CIAM app: // initial: warn 250kB, error 500kB // lazy chunk: warn 100kB, error 200kB // Auth bundle is small — keep it fast // (users hit login page on first visit, // no prior cache, must load cold)

Optimization flags

// Optimization object (production config): "optimization": { "scripts": true, // minify + tree-shake JS "styles": { "minify": true, // minify CSS "inlineCritical": true // inline critical CSS }, "fonts": { "inline": true // inline fonts (no separate request) } } // Output hashing (cache busting): "outputHashing": "all" // Output: main.a1b2c3d4.js (hash changes with content) // CloudFront caches: max-age=31536000 (1 year!) // When code changes: new hash, new URL, cache miss // Unchanged files: same hash, still cached // Source maps in production: "sourceMap": { "scripts": false, // no source maps (smaller) "styles": false, "hidden": false // hidden=true → maps not } // served but exist on disk

Builders: what they actually do

The ADO CI pipeline fails on budget violations, preventing bundle bloat from silently reaching users. Top-Level Structure

angular.json is the workspace configuration file for the Angular CLI. It defines every project in your workspace, what builder runs each target, and what options that builder receives. Every ng command reads this file to know what to do.

// angular.json — skeleton
{
  "$schema": "./node_modules/@angular/cli/lib/config/schema.json",
  "version": 1,
  "newProjectRoot": "projects",   // where ng generate creates new projects
  "projects": {
    "my-app": {                     // project name — used with --project flag
      "projectType": "application",  // "application" | "library"
      "root": "",                    // path from workspace root
      "sourceRoot": "src",           // where source files live
      "prefix": "app",              // component selector prefix: app-
      "architect": {               // build targets ↓
        "build": { ... },
        "serve": { ... },
        "test":  { ... },
        "lint":  { ... },
        "extract-i18n": { ... }
      }
    }
  }
}

Architect Target Structure

Every target under architect follows the same three-part structure: a builder (who does the work), options (always applied), and configurations (named overrides).

"build": {
  "builder": "@angular/build:application",   // esbuild-based builder (Angular 17+)
  "defaultConfiguration": "production",     // ng build runs this config
  "options": {                               // ALWAYS applied
    "browser": "src/main.ts",
    "tsConfig": "tsconfig.app.json",
    "polyfills": ["zone.js"],
    "styles": ["src/styles.scss"],
    "assets": ["public"]
  },
  "configurations": {
    "production": {                          // ng build (default)
      "optimization": true,
      "sourceMap": false,
      "budgets": [...]
    },
    "development": {                         // ng build --configuration=development
      "optimization": false,
      "sourceMap": true,
      "namedChunks": true
    }
  }
}

Build Target Options — @angular/build:application

The options block contains the base configuration always applied regardless of configuration. The most important options for the new esbuild-based application builder:

"options": {
  // Entry point and compiler config
  "browser":   "src/main.ts",           // main entry point for browser bundle
  "tsConfig":  "tsconfig.app.json",     // TypeScript compiler config
  "polyfills": ["zone.js"],             // [] for zoneless Angular 18+

  // Static assets — copies to dist/browser/ as-is
  "assets": [
    "public",                          // shorthand for {glob:"**/*", input:"public"}
    "src/favicon.ico",                 // individual file
    {
      "glob": "**/*",
      "input": "src/assets/",          // source directory
      "output": "assets/"             // destination in dist/browser/
    }
  ],

  // Global styles (injected into index.html as <link> or inlined)
  "styles": ["src/styles.scss"],

  // Global scripts (added to index.html as <script defer>)
  "scripts": [],

  // Server-Side Rendering config (SSR)
  "server":  "src/app/app.config.server.ts",
  "ssr": { "entry": "server.ts" },
  "prerender": true   // Static Site Generation — pre-render all routes
}

assets — What Gets Copied to dist/

The assets array copies files verbatim into the output directory. They are NOT processed by the bundler — they're just copied. Use for images, fonts, JSON config files, and any static file your app needs to serve.

"assets": [
  "public",                 // shorthand: copies public/** to dist/browser/**
  "src/favicon.ico",        // single file to dist/browser/favicon.ico
  {
    "glob":   "**/*.svg",   // match pattern
    "input":  "src/icons/", // source directory
    "output": "icons/"      // destination in dist/browser/
  },
  {
    "glob":   "*.json",
    "input":  "src/assets/",
    "output": "assets/"
  }
]

SSR & Prerender Options

Server-Side Rendering (SSR)

"server": "src/app/app.config.server.ts",
"ssr": {
  "entry": "server.ts"   // Express/Node server
}

Adds a Node.js server bundle that renders the Angular app on the server and sends HTML. Requires provideClientHydration() in app.config.ts.

Static Site Generation (SSG)

"prerender": true
// or with options:
"prerender": {
  "routesFile": "routes.txt"
}

Pre-generates HTML for every route at build time. Fastest serving — no Node server needed. Routes discovered via Router or a routes file.

Optimization Flags

The optimization option controls how aggressively the build tools minify and optimize your output. When set to true, all sub-options are enabled. You can use an object to control each independently.

// production configuration
"optimization": {
  "scripts": true,        // Terser: minify + mangle + tree-shake JS
  "styles": {
    "minify": true,        // Lightning CSS: compress CSS
    "inlineCritical": true  // Extract above-the-fold CSS into <style> tag
  },
  "fonts": {
    "inline": true         // Inline Google Fonts @font-face in HTML
  }
}
optimization.scripts: true
Runs JavaScript through Terser (minifier) and esbuild's tree-shaker. Removes unused exports, mangles variable names, strips whitespace. Can reduce JS bundle by 40-60% compared to development build.
optimization.styles.minify: true
Minifies CSS using Lightning CSS (Angular 17+, replacing clean-css). Removes whitespace, optimises shorthand properties, deduplicates rules. Typically 20-30% smaller CSS files.
optimization.styles.inlineCritical: true
Analyses which CSS rules apply to above-the-fold content and inlines them in a <style> tag in index.html. External stylesheet loads asynchronously. Eliminates render-blocking CSS and dramatically improves LCP (Largest Contentful Paint).
optimization.fonts.inline: true
Downloads Google Fonts CSS and inlines it directly in index.html at build time. Removes a render-blocking network request to fonts.googleapis.com. Has no effect if you don't use Google Fonts.

Output Hashing

Hash suffixes in filenames enable long-lived browser caching. If the file content changes, the hash changes, the filename changes, and browsers download the new version. If content hasn't changed, browsers serve from cache.

"outputHashing": "all"    // production — hash all output files
"outputHashing": "none"   // development — no hash, easier debugging

// "all" produces filenames like:
// main.7f3a9b2c.js    — different hash per content change
// styles.e4d2a1f9.css
// chunk-VENDORS.a8c2b4e.js
ValueHashed files
"none"No files hashed — use in development
"all"All JS, CSS, and media files — recommended for production
"bundles"Only JS and CSS (not media files like images)
"media"Only media files

Source Maps

// development — full source maps for debugging
"sourceMap": true

// production — granular control
"sourceMap": {
  "scripts": false,  // no JS source maps in prod (security + size)
  "styles": false,   // no CSS source maps in prod
  "vendor": false,   // no maps for node_modules code
  "hidden": true    // maps exist on server, not referenced in bundle (for Sentry)
}

hidden: true generates source maps but doesn't add the //# sourceMappingURL comment to the output. Use with error monitoring services (Sentry, Datadog) that consume source maps server-side.

Other Build Flags

namedChunks
true (dev): lazy-loaded chunks get human-readable names like admin-admin-routes.js. false (prod): shorter hashed names like chunk-3a2b.js. Debug-friendly in dev, smaller in prod.
extractLicenses
When true, extracts all third-party library licenses into a 3rdpartylicenses.txt file in the output directory. Required by many enterprise legal teams. Enabled by default in production.
statsJson
Emits a stats.json file containing the complete bundle analysis. Feed it to Webpack Bundle Analyzer or npx source-map-explorer to visualize what's in your bundle.

Build Budgets

Budgets are size thresholds for your build output. When exceeded, Angular CLI prints a warning or fails the build (depending on the threshold type). They enforce performance discipline — preventing bundle size regressions.

"budgets": [
  {
    "type": "initial",              // total initial load (HTML + CSS + JS)
    "maximumWarning": "500kb",    // yellow warning in CLI output
    "maximumError": "1mb"         // red error — build "fails"
  },
  {
    "type": "anyComponentStyle",    // per-component SCSS/CSS file
    "maximumWarning": "2kb",
    "maximumError": "4kb"
  },
  {
    "type": "allScript",            // all JS files combined
    "maximumWarning": "2mb",
    "maximumError": "4mb"
  }
]

Budget Types Reference

typeWhat it measuresRecommended WarningRecommended Error

anyComponentStyleEach individual component's inline/separate CSS2kb4kb

What Happens When a Budget is Exceeded

maximumWarning exceeded

CLI prints a yellow warning message. Build succeeds. Good for gradual tightening — set warn first, tighten over sprints.

maximumError exceeded

CLI prints a red error. Build fails with exit code 1. CI/CD pipeline fails. Forces the team to fix the regression before merging.

File Replacements

File replacements are Angular's mechanism for swapping one file for another at build time. They are applied only in the configuration where they're declared — typically production, not development.

// In the "production" configuration:
"fileReplacements": [
  {
    "replace": "src/environments/environment.ts",
    "with":    "src/environments/environment.prod.ts"
  }
]

When Angular builds with --configuration=production, any import { environment } from '../environments/environment' in your code is resolved to environment.prod.ts instead of environment.ts. The swap happens silently — your code doesn't change.

Environment Files Content

environment.ts (dev)

export const environment = {
  production: false,
  apiUrl: 'http://localhost:8080/api',
  featureNewDashboard: true,
  logLevel: 'debug'
};

environment.prod.ts

export const environment = {
  production: true,
  apiUrl: 'https://api.myapp.com/api',
  featureNewDashboard: false,
  logLevel: 'error'
};

Any File Can Be Replaced

The environment files are just the most common use case. You can replace any TypeScript file — a service, a config module, a constants file. Real-world examples:

// Replace a mock service with the real one in production
{ "replace": "src/app/services/analytics.service.ts",
  "with":    "src/app/services/analytics.service.prod.ts" }

// Different app title per environment
{ "replace": "src/app/app.title.ts",
  "with":    "src/app/app.title.staging.ts" }

// Replace Angular's devtools module
{ "replace": "src/app/dev-tools.ts",
  "with":    "src/app/dev-tools.noop.ts" }

Multiple Configurations

You can define as many configurations as you need — not just production and development. Use --configuration=staging to activate them.

"configurations": {
  "production": {
    "fileReplacements": [{ "replace": "src/environments/environment.ts", "with": "src/environments/environment.prod.ts" }]
  },
  "staging": {
    "fileReplacements": [{ "replace": "src/environments/environment.ts", "with": "src/environments/environment.staging.ts" }],
    "optimization": true,
    "sourceMap": { "hidden": true }
  }
}

// Commands:
ng build                            // uses defaultConfiguration ("production")
ng build --configuration=staging    // staging config
ng build --configuration=development

Serve Target & Test Target

Serve Target Configuration

"serve": {
  "builder": "@angular/build:dev-server",
  "options": {
    "buildTarget": "my-app:build",       // which build target to serve
    "port": 4200,
    "host": "localhost",
    "open": false,                     // auto-open browser
    "hmr": true,                      // Hot Module Replacement (default in v17+)
    "proxyConfig": "proxy.conf.json"  // API proxy config
  }
}

Proxy Config — Forwarding API Calls

During development, your Angular app runs on localhost:4200 but your API is on localhost:8080. Direct calls fail due to CORS. The proxy forwards matching requests to the backend transparently.

// proxy.conf.json
{
  "/api": {
    "target":       "http://localhost:8080",
    "secure":       false,      // ignore self-signed SSL certs
    "changeOrigin": true,       // rewrite Host header to target
    "logLevel":     "debug"     // log proxied requests
  },
  "/auth": {
    "target": "http://auth.localhost:9000",
    "changeOrigin": true
  }
}

Now this.http.get('/api/users') in Angular is transparently forwarded to http://localhost:8080/api/users. No CORS issues, no URL changes needed between dev and prod.

Multiple Projects & Libraries

Adding a Library

// Generate a library — adds it to angular.json projects
ng generate library my-ui-lib

// angular.json — the library project entry
"my-ui-lib": {
  "projectType": "library",
  "root": "projects/my-ui-lib",
  "sourceRoot": "projects/my-ui-lib/src",
  "prefix": "lib",
  "architect": {
    "build": {
      "builder": "@angular-devkit/build-angular:ng-packagr",
      "options": {
        "project": "projects/my-ui-lib/ng-package.json",
        "tsConfig": "projects/my-ui-lib/tsconfig.lib.json"
      },
      "configurations": {
        "production": { "tsConfig": "projects/my-ui-lib/tsconfig.lib.prod.json" }
      }
    }
  }
}

ng-packagr — Angular Package Format (APF)

ng-packagr compiles your library into the Angular Package Format — the format npm-published Angular libraries must use. APF outputs:

  • FESM2022 (Flattened ESM 2022) — single-file ESM bundle, best for tree-shaking
  • ESM2022 — individual ESM files
  • type declarations (.d.ts files) — TypeScript types for consumers
// ng-package.json (in your library root)
{
  "lib": {
    "entryFile": "src/public-api.ts"  // the public barrel export file
  },
  "assets": ["./theming/**"],        // SCSS theming files to include
  "deleteDestPath": false            // don't delete dist between builds
}
// Build the library:
ng build my-ui-lib --configuration=production
// Output: dist/my-ui-lib/ (ready to publish to npm)

// Use the locally-built library in the app:
// tsconfig.json paths: { "@mycompany/ui": ["dist/my-ui-lib"] }
