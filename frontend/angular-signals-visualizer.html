Signals & Modern Angular

Signals are Angular's new reactive primitive (v16 stable, default-everything in v17+). They replace Zone.js, RxJS-for-state, and most of the change-detection complexity with something simpler: a value that knows who depends on it.

⚡ What are signals? What was wrong with the old way?

A signal is a value wrapped in a function — count = signal(0). Read it as count() and Angular records that whoever read it (a template, a computed) now depends on it; write it with count.set(1) and Angular notifies exactly those dependents to re-render. That's a precise dependency graph — the opposite of the old Zone.js model, which patched every async API and re-checked every component on any event.

  • The old way (Zone.js): monkey-patched setTimeout, promises, events and XHR, so any async could have changed anything — forcing Angular to dirty-check the whole component tree.
  • Signals: reading one subscribes the current consumer; writing one marks just those consumers dirty. No global sweep, no NgZone.
  • computed(() => …) derives a value that caches and only recomputes when a signal it actually read changes.
  • effect(() => …) runs side effects (logging, localStorage) automatically whenever its tracked signals change.
  • Equality matters: a set() to the same value (by Object.is) notifies nobody. Use signals for component state, RxJS for streams over time.

Three primitives

  • signal(v) — writable value
  • computed(() => …) — derived, cached
  • effect(() => …) — side effects

Signal vs Observable

  • Signal: always has a current value
  • Observable: a stream of events over time
  • Signals → component state
  • RxJS → HTTP, WebSocket, complex async

The 30-second pitch

A signal is a wrapper around a value. Read it like a function: count(). Write to it with count.set(5). Anything that reads a signal — a template, a computed, an effect — automatically depends on it. When the signal changes, ONLY those dependents re-run. That's it.

The old way (Zone + CD checks everything)

export class Counter {
  count = 0;
  double() { return this.count * 2; }   // runs every CD cycle
  bump() { this.count++; }
}
// Click bump → Zone fires → Angular walks entire tree
// checking EVERY binding to see what changed.

The signal way (only what depends re-runs)

export class Counter {
  count  = signal(0);
  double = computed(() => this.count() * 2);   // memoized

  bump() { this.count.update(c => c + 1); }
}
// Click bump → count signal changes → Angular re-runs
// ONLY the bindings that read count (or double).

The three primitives

import { signal, computed, effect } from '@angular/core';

// 1️⃣ signal — a writable reactive value
const count = signal(0);
count();                          // READ: call it like a function → 0
count.set(5);                     // WRITE: replace value
count.update(c => c + 1);          // WRITE: derive from current

// 2️⃣ computed — a derived signal, memoized, recomputes lazily
const double = computed(() => count() * 2);
double();                         // READ: 10
// — Only re-runs when count changes AND something reads double.
// — If count changes twice without being read, double computes ONCE.

// 3️⃣ effect — runs side effects when any signal it reads changes
effect(() => {
  console.log('count is now', count());
});
// — Runs immediately once, then re-runs every time count changes.
// — Auto-cleans up when its owning component is destroyed.

Reading rules — the magic isn't magic

Dependency tracking works by recording which signals were called during a computed or effect's execution. Conditional reads work — if you don't call a signal this run, you don't depend on it. 

const mode = signal('metric');
const kg   = signal(75);
const lbs  = signal(165);

const weight = computed(() =>
  mode() === 'metric' ? kg() : lbs()
);
// When mode === 'metric', weight depends on (mode, kg) — changing lbs does NOTHING.
// When mode === 'imperial', weight depends on (mode, lbs) — changing kg does NOTHING.
// Angular re-tracks dependencies on every recompute.

Read-only views — protect your state

// Service exposes a writable signal internally, read-only externally
@Injectable({ providedIn: 'root' })
export class CounterService {
  private _count = signal(0);
  readonly count = this._count.asReadonly();   // no .set / .update

  increment() { this._count.update(c => c + 1); }
}

// Consumers can only read
counter.count();           // ✓ read
counter.count.set(99);     // ✗ TypeScript error — no .set on a Signal<T>

Effects — the rules

export class UserProfile {
  user = signal(null);

  constructor() {                 // effects must be created in an injection context
    effect(() => {
      const u = this.user();
      if (u) document.title = `Profile — ${u.name}`;
    });
  }
}

// — Runs once immediately, then every time `user` signal changes.
// — Auto-cleans up when the component is destroyed.
// — DO NOT call .set() on a signal INSIDE an effect — it errors by default
//   (would create infinite loops). If you must, pass { allowSignalWrites: true }.

Effects are for side effects: writing to localStorage, updating document.title, calling an analytics library, syncing to a non-signal API. Don't use them to derive state — that's what computed is for.

Advanced: untracked() — read without creating a dependency

Sometimes you need to read a signal's current value inside a computed() or effect() without registering that signal as a dependency — so the computation does not re-run when that signal changes. That's what untracked() does.

Without untracked — double dependency

// Both price AND taxRate trigger re-run
total = computed(() => {
  return this.price() * this.taxRate();
  //              ^^^ tracked  ^^^ also tracked
});

// Fine here. But what if taxRate changes
// 60× per second for a live chart and
// you only want to re-run on price changes?

With untracked — single dependency

import { untracked } from '@angular/core';

// Only price creates a dependency
total = computed(() => {
  const price = this.price();          // tracked
  const tax   = untracked(() =>
    this.taxRate()                        // not tracked
  );
  return price * tax;
});
// Re-runs on price change, reads the
// latest taxRate value without subscribing

effect() cleanup function

If your effect opens a resource (WebSocket, setTimeout, event listener), return a cleanup function — Angular calls it before the next run and on destroy.

effect((onCleanup) => {
  const userId = this.userId(); // tracked
  const socket = new WebSocket(`wss://api/user/${userId}/events`);
  socket.onmessage = (e) => console.log(e.data);

  // Angular calls this before the next run or on destroy
  onCleanup(() => socket.close());
});
// When userId changes → old socket closed → new socket opened
// When component destroyed → socket closed automatically

CIAM tie-in: Open a server-sent events (SSE) connection for the current user ID, automatically reconnect when the user switches (impersonation), and close cleanly on logout — all in one effect with a cleanup function.

Signals in templates — the cleanest binding ever

@Component({
  selector: 'app-counter',
  template: `
    <p>count: {{ count() }}</p>       
    <p>double: {{ double() }}</p>

    @if (count() > 10) {              
      <p>That's a lot.</p>
    }

    <button (click)="bump()">+1</button>
  `
})
export class Counter {
  count  = signal(0);
  double = computed(() => this.count() * 2);

  bump() { this.count.update(c => c + 1); }
}

// No async pipe. No subscriptions. No OnPush needed.
// Angular sees `count()` in the template, knows that binding depends on it,
// and re-renders ONLY that binding when count changes.

RxJS interop — they play nicely

import { toSignal, toObservable } from '@angular/core/rxjs-interop';

// Observable → Signal (initial value required if stream is async)
const user = toSignal(this.http.get<User>('/api/me'), { initialValue: null });
// In template: {{ user()?.name }}  — no async pipe needed.

// Signal → Observable (for legacy code that wants Observables)
const count = signal(0);
const count$ = toObservable(count);
count$.subscribe(v => console.log(v));

Migration path: you don't have to rewrite everything. Wrap your existing Observables with toSignal() at the component boundary and you get all of signals' benefits in templates while your data layer stays RxJS.

The signal-based inputs & outputs (Angular 17.1+)

// ❌ Old decorator-based @Input/@Output
@Input() name = '';
@Output() saved = new EventEmitter<User>();

// ✅ New signal-based — input() & output() functions
import { input, output, model } from '@angular/core';

name  = input('');                              // Signal<string>
name  = input.required<string>();                  // required input
saved = output<User>();                          // output
value = model('');                             // two-way bindable! [(value)] just works

// Read in component & template
// template:  {{ name() }}     — call it like any signal
// emit:      this.saved.emit(user)
// model:     this.value.set('hello')   — both reads & writes

The new control flow (revisited)

We covered @if, @for, @switch, @defer in the Directives visualizer — they pair perfectly with signals because they're also designed for fine-grained reactivity. Quick recap: 

@if (user(); as u) {                       // signal in @if — auto-tracked
  <p>Welcome, {{ u.name }}!</p>
} @else {
  <p>Please log in.</p>
}

@for (item of items(); track item.id) {     // track is REQUIRED
  <item-card [item]="item" />
} @empty {
  <p>No items yet.</p>
}

@defer (on viewport) {                     // lazy-load on scroll
  <heavy-chart [data]="data()" />
} @loading { <spinner /> }

Migration playbook — one component at a time

1. Convert plain fields to signals

// before
count = 0;
// after
count = signal(0);
// in template: {{ count() }}

2. Replace getters with computed

// before
get double() { return this.count * 2; }
// after
double = computed(() => this.count() * 2);

3. Wrap Observables with toSignal()

users = toSignal(
  this.http.get<User[]>('/api/users'),
  { initialValue: [] }
);

4. Drop OnPush boilerplate

Signal-driven templates already give you OnPush-level performance without the strategy declaration or immutability rules. OnPush is still safe to add, but no longer required for fine-grained updates.

Mental model

1. A signal is a value with a doorbell

When the value changes, it rings the doorbell, and anything that "subscribed" by reading it gets notified.

2. Computed = lazy + memoized

Won't run until someone reads it. Once read, caches until a dependency changes. Multiple reads after change run it once.

3. Effect = the side-effect outlet

For things the UI tree can't express: localStorage, document.title, analytics. Not for deriving state.

4. Signals + new control flow = the future

A v17+ app using signal() in services, input()/output() in components, and @if/@for in templates is the modern Angular default. Faster, simpler, and zoneless-ready.

🌱 First time hearing "signal"? It's a value that announces when it changed.

Here's the problem signals solve. A plain variable can change and the screen has no idea — you'd have to manually remember to update everything that depended on it. A signal fixes that by wrapping the value in a tiny box that keeps track of who's watching.

  • You read it by calling it like a function: count().
  • You change it with count.set(5) or count.update(n => n + 1).
  • The magic: anything that read the signal (a template, a computed, an effect) is remembered — so when the value changes, exactly those things re-run, and nothing else.

There are just three pieces to learn:

  • signal(initial) — a value you can read and write.
  • computed(() => …) — a value derived from other signals; it recalculates itself automatically (e.g. total = computed(() => price() * qty())).
  • effect(() => …) — run a side-effect (save to localStorage, set the page title) whenever a signal it reads changes.

That's it. No subscriptions to remember to clean up, no manual "when this changes, update that." You describe the relationships once and Angular keeps them in sync.

🧠 Expert corner — the reactive graph, precisely

  • Pull-based, lazy, and memoized. A computed() does not eagerly recompute when a dependency changes — it just marks itself dirty, and only recomputes on the next read, caching the result. Read it ten times without a change and the body runs zero extra times.
  • Glitch-free consistency. Signals form a dependency graph that's resolved so a computed never exposes a half-updated intermediate value — the inconsistency that naive "A updates B updates C" observer chains are famous for.
  • The equality gate. A signal won't notify dependents if the new value is Object.is-equal to the old one. For value objects, pass a custom { equal } so a structurally-identical object doesn't trigger needless recomputation (or, conversely, so a mutated-in-place object does).
  • Dynamic dependency tracking. A computed depends only on the signals it actually read on its last run. Put a signal read behind an if and it leaves the dependency set when that branch isn't taken — dependencies are discovered, not declared.
  • Effects: timing & discipline. Effects run after change detection, are batched (many sync writes → one run), execute in an injection context, and auto-clean-up when their context is destroyed. Don't set signals inside an effect to derive state — that's what computed is for; reaching for allowSignalWrites is usually a design smell.
  • RxJS interop & zoneless. toSignal()/toObservable() bridge the two worlds (see Signals ↔ RxJS Interop). Signals are also what make zoneless change detection work — the view updates because a signal it read changed, not because Zone.js monkey-patched a setTimeout.
  • CIAM tie-in. authState = signal<User|null>(null); isAdmin = computed(() => authState()?.roles.includes('admin') ?? false); the navbar template reads isAdmin() and flips the instant the user logs in or out — no manual subscription, no async pipe, no leak.
