The one question a dependency array actually asks

Every "why did this effect rerun" mystery collapses to one check: is this the SAME object as last render, or a new box holding the same stuff?

Primitives compare by value — a number, a string, a boolean. 25 === 25 is true no matter how many times you typed the literal 25. Put one of these in a dependency array and "unchanged" means exactly what you think it means.

roleFilter (a string) pageSize (a number) isOpen (a boolean)

Objects and arrays compare by reference — two literals with identical contents are still two different boxes. { a: 1 } === { a: 1 } is false, every single time, forever. Put one of these in a dependency array and "unchanged" means "the exact same box in memory," not "the same stuff inside it."

{ roleFilter: 'admin', pageSize: 25 } — a fresh literal on every render [user1, user2] — a fresh array on every render a function defined inline — a fresh closure on every render

A custom hook's internal useEffect only knows what you put in its dependency array. Depend on the whole options object and you've asked "same box?" — and every caller who writes useUserSearch(query, { roleFilter, pageSize }) inline hands you a brand-new box on every render, guaranteed, even when roleFilter and pageSize never actually change.

Picture a locker that resets its combination the instant anyone hands it a new box, without ever checking what's inside the box. Hand it the identical contents in a freshly-taped box and it still resets — it was never reading the contents, only noticing "this is a different box than last time." Object.is checks the box, never the contents.
The same mixup, one ecosystem over: a Redux mapStateToProps that returns { user: state.user, cartCount: state.cart.items.length } builds a fresh object on every dispatch, so a connected component re-renders on every action in the store — whether or not user or cartCount actually changed. Same rule, different library: a fresh box always reads as "changed," even when nothing inside it moved.
A custom hook's internal effect is only as stable as the values it actually depends on — and if that's a whole object or array parameter, every caller who passes an inline literal breaks it, invisibly. Depend on the primitive fields you actually read, not the container those fields happen to arrive in. The instability lives inside a file the caller never opens, which is exactly what makes it a custom-hook problem and not just a useEffect problem.

🧩 What are custom hooks — and what's the difference between sharing logic vs sharing state?

A custom hook is just a function named use… that calls other hooks — no API, no registration, no base class; the prefix tells React and the linter to apply the rules of hooks. The key insight: custom hooks share logic, not state. Two components calling useUserData(id) get two independent state instances — the opposite of Angular's providedIn:'root' singleton. To actually share state, put the hook inside a Context provider. They replace the old render-props/HOC gymnastics for reusing stateful logic. Common ones: useLocalStorage, useFetch, useDebounce, useClickOutside — every mature codebase keeps a src/hooks/ folder.

  • Just a use… function that calls hooks — convention, not special API.
  • Shares logic, not state — each call gets its own independent state.
  • To share state, wrap in Context — unlike an Angular root singleton.
  • Replaces render-props / HOCs — useFetch/useDebounce/useClickOutside in src/hooks/.

useDebounce

// Custom hook: extracts debounce logic function useDebounce<T>(value: T, delayMs: number): T { const [debouncedValue, setDebouncedValue] = useState<T>(value); useEffect(() => { // Set a timer: update debouncedValue after delay const timer = setTimeout(() => { setDebouncedValue(value); }, delayMs); // Cleanup: if value changes before timer fires, // cancel the timer and start a new one return () => clearTimeout(timer); }, [value, delayMs]); return debouncedValue; } // Usage: function SearchBox() { const [query, setQuery] = useState(''); const debouncedQuery = useDebounce(query, 300); // Only fires API call 300ms after typing stops useEffect(() => { search(debouncedQuery); }, [debouncedQuery]); }

useFetch (data + loading + error)

function useFetch<T>(url: string) { const [data, setData] = useState<T | null>(null); const [loading, setLoading] = useState(true); const [error, setError] = useState<string | null>(null); useEffect(() => { setLoading(true); setError(null); const ctrl = new AbortController(); fetch(url, { signal: ctrl.signal, headers: authHeader() }) .then(r => { if (!r.ok) throw new Error(\`HTTP ${r.status}\`); return r.json() as Promise<T>; }) .then(d => { setData(d); setLoading(false); }) .catch(e => { if (e.name !== 'AbortError') { setError(e.message); setLoading(false); } }); return () => ctrl.abort(); }, [url]); return { data, loading, error }; } // Usage: const { data: user, loading, error } = useFetch<UserDto>(\`/api/users/${id}\`);

Angular comparison

React custom hook → Angular equivalent. useFetch<T>(url) → Angular service method returning Observable: getUser(id: number): Observable<UserDto>. useDebounce(query, 300) → RxJS debounceTime(300) operator in a pipe. useLocalStorage('token', '') → Angular service using localStorage.getItem/setItem. useClickOutside(ref, handler) → Angular directive @HostListener('document:click'). Key difference: a custom hook creates NEW state per component call. An Angular service method shares one service instance (singleton). To replicate "per-component state" in Angular, you'd use a component-scoped provider: @Component({ providers: [UserService] }) — creates a new UserService instance for this component and its children only, destroyed with the component.

CIAM React app: A CIAM hooks library: useAuth() (current user/token/logout), usePermission('CIAM_ADMIN') (role check), useUserSearch(query) (debounced /api/users?q= with loading/error), usePagination(size) (cursor state), useIdpClient(idpType) (right Ping/Entra client). Each is independently testable with renderHook(() => usePermission('CIAM_ADMIN'), { wrapper: AuthProvider }) — mirroring Angular's TestBed.inject(PermissionService).

1. The whole definition

There is no special API. A custom hook is a JavaScript function that (1) is named useSomething and (2) calls at least one other hook. That is it.

function useToggle(initial = false) {
  const [on, setOn] = useState(initial);
  const toggle = useCallback(() => setOn(o => !o), []);
  return [on, toggle]; // shape it like useState
}
// usage: const [isOpen, toggleOpen] = useToggle();
The use prefix is not cosmetic. The eslint-plugin-react-hooks linter uses it to know a function follows the Rules of Hooks — so it can verify hooks are only called at the top level and from components/other hooks. Name a hook getToggle and the linter stops protecting it; name a non-hook useThing and it falsely demands hook rules.

2. Why extract a custom hook?

Remove duplicationThe same fetch+loading+error dance in five components → useQuery

Isolate non-React systemsWrap a subscription / browser API behind a tidy hook interface
Make logic testableTest the hook in isolation (e.g. with @testing-library/react renderHook)
Don't over-extract. A custom hook earns its keep when logic is reused or genuinely complex. Wrapping a single useState in a hook for one caller just adds indirection. Extract when you feel the duplication or want to name the behavior.

3. Three patterns worth memorizing

useDebounce

function useDebounce(value, ms) {
 const [d, setD] = useState(value);
 useEffect(() => {
  const t = setTimeout(() => setD(value), ms);
  return () => clearTimeout(t);
 }, [value, ms]);
 return d;
}

useInterval (latest-ref)

function useInterval(cb, delay) {
 const ref = useRef(cb);
 useEffect(() => { ref.current = cb });
 useEffect(() => {
  const id = setInterval(() => ref.current(), delay);
  return () => clearInterval(id);
 }, [delay]);
}
