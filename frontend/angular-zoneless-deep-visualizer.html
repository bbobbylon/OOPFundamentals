Zoneless Change Detection

Removing zone.js doesn't change how Angular checks the tree — it changes what wakes it up. Instead of a Zone patching every async API, the framework now schedules change detection from its own explicit notifications. Here's the new model, and the one habit you must change.

What is Zoneless Angular — and why does removing zone.js matter?

Zone.js is a 12KB library that patches every async browser API to notify Angular "something may have changed, check the whole tree." It's magic — but costly: it adds 12KB to every app, it fires on every async completion (even ones that don't affect the UI), and it makes Angular apps hard to use with non-Angular async patterns (Web Workers, third-party libraries with their own async). Zoneless mode (Angular 18+, stable in 19+) removes Zone.js entirely. Angular only runs change detection when it explicitly needs to — when a signal changes, when an event handler explicitly triggers a check, or when ChangeDetectorRef.markForCheck() is called. The result: 12KB smaller bundle, faster startup, and better interop with native async patterns.

Enabling zoneless

In app.config.ts: provideExperimentalZonelessChangeDetection(). Remove zone.js from polyfills in angular.json. That's it. Now Angular only runs CD when: a signal updates, an @HostListener/(click) event fires, markForCheck() is called, or AsyncPipe emits. If your code mutates plain objects without signals, those changes will NOT update the UI.

The one habit you must change

In zone mode: this.users = newList works because Zone.js catches the event that set it and triggers CD. In zoneless mode: this.users = newList does nothing — no signal updated, no CD triggered. You must use signals: this.users.set(newList). If you can't use a signal, call this.cdr.markForCheck() after the change.

Signals + zoneless = the future

Signals tell Angular exactly what changed (no tree walk). Zoneless tells Angular when to check (only on explicit notification). Together: Angular only touches the components that read a changed signal, only when that signal changes. This is the most efficient possible change detection — no wasted work at all. New Angular projects should target this architecture.

In CIAM: Enable zoneless in a new CIAM app: provideExperimentalZonelessChangeDetection(). The auth store, user list, and all state must use signals. Third-party libraries that rely on Zone.js notifications must be checked: Angular Material is zoneless-compatible; some older charting libraries are not. Migration: start with signals, then enable zoneless — it will immediately surface any place you were relying on Zone.js's magic notifications.

1. From "patch everything" to "notify explicitly"

With Zone.js (the old default)

Zone monkey-patches ~40 async APIs. Any of them firing — even an unrelated setTimeout — tells Angular "something might have changed, run a tick."

any async API fires→ Zone: onMicrotaskEmpty→ tick()

Convenient (mutate any field and it "just updates"), but wasteful — ticks fire for things that changed nothing, and it ships ~13KB plus messy stack traces.

Zoneless (the future default)

No patching. A ChangeDetectionScheduler runs a tick only when the framework is explicitly notified that a view is dirty.

signal / markForCheck / event→ scheduler.notify()→ coalesced tick()

The notifications are coalesced (microtask/rAF) so many changes in one turn = one tick. Smaller, faster, predictable — and it pushes you toward signals.

2. What actually notifies the scheduler

In zoneless mode, change detection is scheduled by exactly these framework events — nothing else:

  • A signal read in a template changes (it calls markForCheck on its consumers).
  • ChangeDetectorRef.markForCheck() — directly, or via the async pipe on every emission.
  • A template event listener fires ((click), (input), …).
  • ComponentRef.setInput(), or a view being attached/created.
  • afterRender / afterNextRender hooks are pending.

What's NOT here: a bare setTimeout, Promise.then, fetch, addEventListener, or a 3rd-party callback that mutates a plain field. Under Zone those triggered a tick; under zoneless they don't — unless they go through one of the above.

4. Turning it on

Provider + drop zone.js

// main.ts
bootstrapApplication(App, {
  providers: [
    provideZonelessChangeDetection(),
  ],
});
// angular.json — remove the polyfill
// "polyfills": ["zone.js"]  ← delete this

Stable in v20 (was provideExperimentalZonelessChangeDetection in v18–19). Removing the polyfill is what actually drops the ~13KB.

Make components zoneless-ready first

  • Use signals for state, computed for derived values.
  • Use the async pipe for observables (it calls markForCheck).
  • Set components to OnPush — zoneless assumes you notify, which is exactly the OnPush contract.
  • Replace "mutate a field in a callback" with a signal write.

A clean OnPush + signals app is usually already zoneless-compatible.

6. Why bother — the payoff

  • Smaller & faster: ~13KB gone, faster startup, fewer needless ticks (no CD for unrelated timers).
  • Cleaner stack traces & debugging: no Zone frames wrapping every async call.
  • Predictable: CD runs when you change state, not as a side effect of any async work anywhere.
  • Better interop: 3rd-party async code no longer accidentally triggers app-wide change detection.
  • Future-aligned: it's the direction Angular is heading; signals are the idiomatic state primitive.

7. One-sentence recap

⚡ Zoneless drops zone.js and lets a ChangeDetectionScheduler run a (coalesced) tick only when the framework is explicitly notified — by a signal change, markForCheck/async pipe, a template event, or setInput — so the tree-walk is identical but bare setTimeout/Promise/fetch field mutations no longer update the view: use signals.
