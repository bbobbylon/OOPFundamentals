Zoneless Change Detection

Removing zone.js doesn't change how Angular checks the tree — it changes what wakes it up. Instead of a Zone patching every async API, the framework now schedules change detection from its own explicit notifications. Here's the new model, and the one habit you must change.

🚫 What is Zoneless Angular — and why does removing Zone.js matter?

Zone.js is a ~12 KB library that patches every async browser API to tell Angular "something may have changed — check the whole tree." It's magic, but costly: extra bundle weight, it fires on every async completion (even ones that don't touch the UI), and it complicates interop with non-Angular async (Web Workers, third-party libs). Zoneless mode (Angular 18+, stable in 19+) removes it — Angular runs change detection only when it explicitly needs to: a signal changed, an event handler triggered a check, or markForCheck() was called. Result: smaller bundle, faster startup, cleaner async interop.

  • Zone.js = automatic-but-broad CD; zoneless = explicit-and-precise CD driven by signals.
  • Enable with provideZonelessChangeDetection() and drop zone.js from polyfills — and on v21+ you need neither, because zoneless is the default there.
  • The one habit to change: plain mutation (this.users = newList) no longer updates the UI — use signal.set().
  • If you can't use a signal, call cdr.markForCheck() after the change; the async pipe and events still trigger CD.
  • Signals + zoneless = the most efficient possible CD — only the components reading a changed signal re-render, only when it changes.

Enabling zoneless

In app.config.ts: provideZonelessChangeDetection(); remove zone.js from polyfills. Now CD runs only on a signal update, an event, markForCheck(), or an async-pipe emission. Plain object mutations won't update the UI.

The one habit you must change

In zone mode this.users = newList works because Zone.js caught the event. In zoneless it does nothing — no signal updated, no CD. Use this.users.set(newList), or call cdr.markForCheck() if you can't use a signal.

Signals + zoneless = the future

Signals say what changed (no tree walk); zoneless says when to check (only on notification). Together, Angular touches only the components that read a changed signal, only when it changes. New projects should target this.

In CIAM:enable zoneless in a new app with provideZonelessChangeDetection() (on v21+ it is already on) — the auth store, user list, and all state must be signals. Vet third-party libs (Material is compatible; some old charting libs aren't). Migrate signals first, then flip zoneless — it instantly surfaces anywhere you relied on Zone.js's magic.

The problem

The migration got declared "done." One row-heavy component never got the memo.

Six weeks after "zoneless migration complete," one component is still eating 90% of every tick — for a signal it's never even read.

A team ships provideZonelessChangeDetection(), converts every service to signals, and marks every component OnPush — except AuditLogTable, a 4,000-row grid nobody touched during the migration because "it still worked." Elsewhere, a presence widget writes a heartbeat signal from a WebSocket callback every 2 seconds — a tiny, completely unrelated update. CPU profiling shows AuditLogTable re-evaluating all 4,000 rows' bindings twice a second, forever, for a signal it doesn't inject and has never read in its template.

The wrong assumption: that removing zone.js makes every component's checks cheap. It only makes ticks rarer. A Default-strategy component still pays full price on every tick that happens to run — whoever, or whatever, caused it.

You

We went zoneless months ago. Why is AuditLogTable still re-rendering every two seconds?

The scheduler

A tick runs whenever anything notifies me — right now that's the presence widget's heartbeat signal, once every 2 seconds. I don't inspect who's related to what. I just run the walk.

AuditLogTable (Default strategy)

And nobody ever told me I'm allowed to sit a tick out. Default strategy means: whenever a walk reaches me, check me — full stop. That rule didn't change when zone.js left the building.

OnPush, once added

Give me the annotation and I'll finally have a dirty flag to check. Now the scheduler's heartbeat-triggered walk reaches me, sees nothing of mine fired, and moves on without opening a single row.

The mechanism

One unrelated signal write. One unconditional casualty, until it gets the annotation.

  1. App is zoneless, and every component is OnPush — except AuditLogTable, missed during migrationone straggler is all it takes
  2. A WebSocket callback writes PresenceWidget's heartbeat signal, once every 2 secondsa real, legitimate, tiny notification
  3. The scheduler coalesces it and schedules exactly one tickzoneless is doing its job perfectly here
  4. The tick walks from the root down. OnPush siblings with no dirty flag get pruned, same as alwaysthis part is genuinely cheap
  5. AuditLogTable has no OnPush annotation, so Default strategy applies: checked unconditionally, every tick, regardless of why the tick firedthe walk doesn't ask "are you related?" — only "are you OnPush and clean?"
  6. 4,000 rows' worth of bindings re-evaluate, twice a second, forever — until someone adds the one annotationthe fix is one line, once you know to look for it

Step 5 is the whole lesson. Removing zone.js changed how a tick gets started — nothing about it changed how a Default-strategy component behaves once a tick is already under way. That component was always going to be checked on every tick, in Zone-based Angular or zoneless Angular alike; zoneless just made the ticks themselves rarer.

Three components see the exact same tick. Two of them get a strategy-based say in whether they're touched. The third was never asked.

A zoneless app is fully migrated to OnPush except one legacy component, AuditLogTable, which nobody got around to annotating. A completely unrelated signal write somewhere else in the app triggers a tick. Does AuditLogTable get checked on that tick?

Signals ARE fine-grained about marking things dirty — but only for components that have a dirty flag to set in the first place. That's an OnPush concept. AuditLogTable has no strategy telling it to wait for a specific dependency, so there's nothing for the signal to "not match" — it gets swept into every tick regardless.

This borrows a rule from the wrong story — that's how a detach()'d branch behaves (unreachable regardless of dirt), not how Default strategy behaves. A tick's walk isn't gated by relation to the trigger; the walk always covers the whole live tree, checking every Default component it reaches and every OnPush component its dirty flag allows through.

Right. The walk doesn't ask why the tick started or who's related to the trigger — it only asks, per component, "OnPush and clean, or not?" A component with no strategy annotation always fails that question in the expensive direction.

Where you've seen this before

Making an alarm ring less often never makes what happens after it rings any cheaper.

A cron job with no WHERE clause

Switching a job from running every minute to running every hour cuts the number of runs by 98% — and does nothing at all for a run that still executes SELECT * FROM orders with no index and no filter. Fewer wake-ups; identical, still-terrible cost per wake-up.

rarer trigger ≠ cheaper work

A React child with no memo()

Batching state updates (React 18's automatic batching, or your own debounce) makes a parent re-render less often — great. A child that was never wrapped in React.memo still fully re-renders every single time its parent does, on every one of those now-rarer renders, whether or not its own props changed at all.

unmemoized child ≈ Default-strategy component

Your CIAM admin dashboard's audit-log table

An admin console moves session-status from 5-second polling to a WebSocket push — a real win, ticks now fire only when something genuinely changes. But the audit-log table was built before the OnPush convention took hold and nobody circled back. Result: every presence ping from every other logged-in admin fully re-renders a 4,000-row log table that has nothing to do with anyone's presence — the win from switching off polling quietly gets eaten by the one component that never opted in to being skippable.

fixed the frequency, not the strategy
Questions from the back row

So does OnPush matter MORE in a zoneless app, or the same amount?

More, in practice — under Zone.js, ticks were already so frequent that one more wasted Default-strategy check barely registered. Under zoneless, ticks are supposed to be rare and meaningful, which makes one component that's checked on literally all of them stand out far more in a profiler. The bug was always there; zoneless just makes it visible.

If every component in the app is OnPush, does the "who gets checked" question even come up?

Only in the trivial sense — every component now asks "am I dirty?" before doing any work, so the answer is always exactly the components whose own triggers fired. That's the whole point of pairing zoneless with universal OnPush: the walk itself has nothing left to do at any clean node.

How would I actually catch a component like this before it ships?

A profiler flame graph over a few seconds of idle-ish app time is the fastest tell — a component re-rendering at a steady interval that matches some OTHER feature's polling or socket cadence, with none of its own inputs changing, is almost always a missing OnPush. Grepping the codebase for components with no changeDetection: line at all works too, just slower.

1. From "patch everything" to "notify explicitly"

With Zone.js (the old default)

Zone monkey-patches ~40 async APIs. Any of them firing — even an unrelated setTimeout — tells Angular "something might have changed, run a tick."

any async API fires→ Zone: onMicrotaskEmpty→ tick()

Convenient (mutate any field and it "just updates"), but wasteful — ticks fire for things that changed nothing, and it ships ~13KB plus messy stack traces.

Zoneless (the future default)

No patching. A ChangeDetectionScheduler runs a tick only when the framework is explicitly notified that a view is dirty.

signal / markForCheck / event→ scheduler.notify()→ coalesced tick()

The notifications are coalesced (microtask/rAF) so many changes in one turn = one tick. Smaller, faster, predictable — and it pushes you toward signals.

2. What actually notifies the scheduler

In zoneless mode, change detection is scheduled by exactly these framework events — nothing else:

  • A signal read in a template changes (it calls markForCheck on its consumers).
  • ChangeDetectorRef.markForCheck() — directly, or via the async pipe on every emission.
  • A template event listener fires ((click), (input), …).
  • ComponentRef.setInput(), or a view being attached/created.
  • afterRender / afterNextRender hooks are pending.

What's NOT here: a bare setTimeout, Promise.then, fetch, addEventListener, or a 3rd-party callback that mutates a plain field. Under Zone those triggered a tick; under zoneless they don't — unless they go through one of the above.

4. Turning it on

Provider + drop zone.js

// main.ts
bootstrapApplication(App, {  // standalone bootstrap — no NgModule, no zone.js required
  providers: [  // app-wide DI providers
    provideZonelessChangeDetection(),  // CD now runs off signal writes + events, never zone patching
  ],
});
// angular.json — remove the polyfill
// "polyfills": ["zone.js"]  ← delete this

Stable since v20.2, renamed from provideExperimentalZonelessChangeDetection (the v18–19 experimental name, now gone). On v21+ zoneless is the default — you don’t add this provider at all, and it is provideZoneChangeDetection() that opts you back into Zone.js. Removing the polyfill is what actually drops the ~13KB.

Make components zoneless-ready first

  • Use signals for state, computed for derived values.
  • Use the async pipe for observables (it calls markForCheck).
  • Set components to OnPush — zoneless assumes you notify, which is exactly the OnPush contract.
  • Replace "mutate a field in a callback" with a signal write.

A clean OnPush + signals app is usually already zoneless-compatible.

6. Why bother — the payoff

  • Smaller & faster: ~13KB gone, faster startup, fewer needless ticks (no CD for unrelated timers).
  • Cleaner stack traces & debugging: no Zone frames wrapping every async call.
  • Predictable: CD runs when you change state, not as a side effect of any async work anywhere.
  • Better interop: 3rd-party async code no longer accidentally triggers app-wide change detection.
  • Future-aligned: it's the direction Angular is heading; signals are the idiomatic state primitive.

7. One-sentence recap

⚡ Zoneless drops zone.js and lets a ChangeDetectionScheduler run a (coalesced) tick only when the framework is explicitly notified — by a signal change, markForCheck/async pipe, a template event, or setInput — so the tree-walk is identical but bare setTimeout/Promise/fetch field mutations no longer update the view: use signals.
