Microsoft Entra ID Overview

The identity platform behind Microsoft 365, Azure, and thousands of enterprise apps — formerly known as Azure Active Directory (Azure AD).

🏢 What is Microsoft Entra ID — and how is it the identity backbone for Microsoft cloud + thousands of apps?

Microsoft Entra ID (formerly Azure AD) is the identity layer behind Microsoft 365, Azure, and thousands of SaaS apps — so if a company runs M365, its identities already live here, making Entra the natural CIAM choice. The directory stores users, groups, service principals and managed identities (each an immutable Object ID, queryable via Microsoft Graph). It's multi-tenant (your org = one tenant ID) and speaks OAuth2/OIDC/SAML. Entra Connect syncs on-prem AD users/groups/password-hashes to the cloud (hybrid identity), and Conditional Access is the policy engine — "require MFA off-network", "block risky sign-ins" — evaluated at every sign-in with no app code, the Entra analogue of a Ping authentication journey.

  • Identity behind M365 + Azure — natural CIAM when the org is Microsoft-invested.
  • Directory of users/groups/SPs — immutable Object IDs, queried via Graph.
  • Entra Connect hybrid-syncs on-prem AD (users/groups/password hashes).
  • Conditional Access = code-free sign-in policy (≈ Ping journeys).

Entra key concepts

// Tenant: your org's Entra environment // Tenant ID: xxxxxxxx-xxxx-xxxx-xxxx-xxxxxxxxxxxx (GUID) // Domain: contoso.onmicrosoft.com (or custom: contoso.com) // Key objects in the Entra directory: // User: a person's identity // ObjectId: immutable GUID (never changes) // UPN: bobby@contoso.com (like an email address) // DisplayName: "Bobby Oliver" // Group: collection of users for role assignment // App Registration: your application's identity in Entra // ApplicationId (client_id): used in OAuth2 flows // ObjectId: Entra's internal ID for the app object // Service Principal: the app's runtime identity in a tenant // (App Registration = the template; SP = the instance) // Managed Identity: for Azure resources (no credentials) // Microsoft Graph API (query the directory): GET https://graph.microsoft.com/v1.0/users Authorization: Bearer <access_token_with_User.Read.All_scope> // Returns all users in your tenant

Entra Connect hybrid sync

// Most enterprises: on-prem AD DS + Entra ID (hybrid) // Entra Connect syncs: users, groups, passwords // On-prem AD: // CN=Bobby Oliver,OU=Users,DC=contoso,DC=local // sAMAccountName: bobbyo // mail: bobby@contoso.com // memberOf: CN=Engineering,OU=Groups,... // Entra Connect syncs to Entra ID: // User object in Entra: // onPremisesImmutableId: base64(objectGUID) ← tie between systems // onPremisesSamAccountName: bobbyo // onPremisesDistinguishedName: CN=Bobby Oliver,OU=... // groups: [Engineering] ← synced group memberships // passwordHash: synced (Password Hash Sync) // Sync latency: ~30 min for user/group changes // Password sync: near real-time (2-4 min) // Result: users log in to Microsoft 365 / Azure / your Entra app // with the same AD password — no separate cloud password

Conditional Access policies

// Conditional Access: "if X, then require Y" // Evaluated at sign-in — no app code changes needed // Example policies: // 1. Require MFA for all non-compliant devices: // IF user accesses any app // AND device is NOT Intune-compliant // THEN require MFA // 2. Block risky sign-ins: // IF Entra Identity Protection risk = High // THEN block access // 3. Require specific auth strength for admin apps: // IF user accesses "CIAMAdmin" app // AND user is in "CIAM_Admins" group // THEN require phishing-resistant MFA (FIDO2 only) // 4. Restrict to compliant locations: // IF accessing from outside corporate IP range // AND NOT trusted named location // THEN require MFA // Your app gets a claim in the ID token: // "acr": "mfaDone" → MFA was completed // "amr": ["mfa","pwd","hwk"] → auth methods used

In CIAM / Your Job: Entra is the other major CIAM platform alongside Ping — and they often coexist (Ping federates into Entra or vice versa); your Angular app may auth through Entra (MSAL) while other APIs take Ping tokens. Entra Connect sync means a user you see in your admin tool is the Entra projection of an on-prem AD account. Use the immutable objectId/onPremisesImmutableId as the stable cross-system key — never UPN or email, which can change.

1 — Core Concepts

Click each concept to expand the full explanation:

Tenant

One organization's isolated directory
A tenant is a dedicated, isolated instance of Entra ID for one organization. Your company "Acme Corp" has exactly one tenant. Each tenant has a globally unique Tenant ID (a GUID like a1b2c3d4-...). Even if two companies use Entra ID, they are completely isolated from each other.

Directory

Container of identities and registrations
The directory inside your tenant holds all your users, groups, app registrations, and service principals. Think of it as a database of everything identity-related in your organization. One tenant = one directory.

User

A person's identity in the directory
A user object has: userPrincipalName (like an email: bob@company.com), objectId (unique GUID), display name, group memberships, MFA methods, and account status. Users can be Members (your employees) or Guests (from another tenant — B2B collaboration).

Group

Collection of users for permission assignment
Groups let you assign permissions to many users at once. Two types: Security groups (control access to resources), Microsoft 365 groups (collaboration: shared mailbox, Teams, SharePoint). Add a user to a group → they inherit all its permissions.

Service Principal

An application's identity in the directory
When an application (not a human) needs to authenticate to Entra ID or access resources, it needs a service principal — the app's identity object in the directory. Created automatically when you register an app or when an Enterprise App is added.

Managed Identity

Auto-managed credentials for Azure resources
Azure resources (VMs, App Services, Functions) can have a System-Assigned Managed Identity. Azure manages the credential automatically — no secrets to store, rotate, or leak. The resource authenticates to Entra ID using its managed identity. Always prefer this over client secrets for Azure-hosted apps.

Key insight: Entra ID never touches your database or your API directly. It issues JWT tokens. Your Angular app passes the token to your Spring Boot API. Spring Boot validates the token's signature using Entra ID's public keys (JWKS endpoint) — no network call to Entra required at request time.
