The Command Line

or, how to drive any computer on Earth with twelve little words

>_

What is the command line — and why does every developer, sooner or later, end up living in it?

The idea

It's not a tool. It's a conversation.

The shell prints a prompt, you type a command, it runs and prints the result, then it prompts again. That's the whole loop. No menus, no wizards — just you and the machine, taking turns. On Linux and macOS your conversation partner is usually Bash (or Zsh); on Windows it's PowerShell, with CMD as the legacy old-timer. Master about a dozen commands — move around, look at files, create and delete things, and ask for help — and you can drive any machine you can log into.

Motivation

GUIs are for using computers. The CLI is for commanding them.

01
Automation

Anything you can type, you can script. A click can't be replayed at 3 a.m. by a CI pipeline — a command can, ten thousand times, identically.

02
Remote servers

SSH into a production box and there is no desktop waiting for you. The terminal isn't the power-user option there — it's the only option.

03
The tools live here

Docker, Kubernetes, git, Maven, and the cloud CLIs (aws, az, gcloud) are command-line first. The GUIs, where they exist, are wrappers.

04
Speed

Once the commands are muscle memory, you'll navigate, search, and rename faster than any file browser — because your hands never leave the keyboard.

Anatomy of a command

Command, flags, argument. Tap each piece.

the command

ls is the program to run — here, "list directory contents". The shell finds it by searching the folders in your PATH environment variable, in order, and runs the first match.

the flags

-la is two flags squashed together: -l = long format (permissions, size, date) and -a = all files, including hidden dotfiles like .git and .env. Short flags use one dash (-l), long ones use two (--help).

the argument

/var/log is what to act on — which directory to list. Leave it off and the command uses your current working directory. Most commands take zero, one, or many arguments after the flags.

And the prompt itself is telling you four things before you type a single letter:

dev@devhub:~/projects$ ls
dev — who you are (the user) devhub — which machine ~/projects — where you are (cwd) $ — ready for input (# = root)

In grep -rn "jwt" src/ — which part is the argument?

grep is the command — the program being run, not the thing acted on.

-rn is two flags (recursive + line numbers). Flags tune how the command behaves.

Arguments are what the command operates on: the pattern "jwt" and the directory src/. Command → flags → arguments, every time.

Paths

Every file has two names: where it is, and how to get there from here.

The four ways to point at a place

# absolute — from the root, unambiguous
cd /usr/local/bin       # Linux/mac
cd C:\Windows\System32  # Windows

# relative — from where you are now
cd projects/app

# shortcuts
cd ..      # up one
cd ../..   # up two
cd ~       # home directory
cd -       # previous directory (bash)

Special path tokens

.     # this directory
..    # parent directory
~     # your home (/home/dev, C:\Users\dev)
/     # filesystem root (Linux/mac)
C:\   # a drive root (Windows)

# run a script in THIS folder:
./deploy.sh   # the ./ says "right here"

Slashes differ: Linux/mac use /, Windows traditionally uses \ (though PowerShell accepts / too). That single difference trips up most cross-platform scripts.

Your cwd is ~/projects. What does cat ../photos/cat.jpg open?

.. means "parent": from ~/projects it steps up to ~ (that's /home/dev), then photos/cat.jpg descends. Sibling folders are one .. apart.

The path does start at the cwd — but its first hop is .., which leaves projects before descending into photos.

Relative paths can go anywhere: every .. climbs one level, all the way to the root if you chain enough of them.

Exit codes

Every command leaves a note on the way out.

When a command finishes it hands the shell one number, the exit code. You'll rarely look at it while typing — but scripts and CI/CD pipelines read it after every single command, and one non-zero fails the whole build.

0 = success vs. anything else = error 
ls /var/log         # runs fine → exit code 0
echo $?             # $? holds the LAST command's exit code (Bash)
                    # PowerShell's version is $LASTEXITCODE

mvn test && docker build .   # && = run the 2nd ONLY if the 1st exited 0
mvn test || echo "failed!"   # || = run the 2nd ONLY if the 1st failed

In a CI pipeline, mvn test exits with code 1. What happens to mvn test && docker build .?

That's what ; does (run regardless). && is conditional — it checks the exit code first.

&& means "and then, if that worked". Exit 1 ≠ 0, so the chain stops — which is exactly why broken tests block broken images from shipping.

Shells never retry on their own. Exit 1 simply short-circuits the && chain.

Put it together

Hunt down the file eating the server's disk — predict each output before you reveal it.

Where am I?

Never run anything destructive before you know your cwd. pwd is the "you are here" pin on the map.

$ pwd
/home/dev
Go where the logs live

An absolute path (leading /) works no matter where you started. The prompt's path segment updates to confirm the move.

$ cd /var/log
dev@devhub:/var/log$
Look around — with sizes

-l gives the long listing, and -h makes sizes human-readable (2.1G instead of 2254857830).

$ ls -lh
-rw-r--r-- 1 root root 2.1G Sep  1 09:14 app.log
-rw-r--r-- 1 root root  12K Sep  1 09:14 auth.log
drwxr-xr-x 2 root root 4.0K Aug 30 03:11 nginx/
Confirm it's the only monster

find searches from here (.) for anything over 100 MB — including inside subfolders that ls alone wouldn't show.

$ find . -type f -size +100M
./app.log
Peek before you act

tail shows the file's last lines — enough to see what is flooding the log before you truncate or rotate it. Piping into grep would filter it further.

$ tail -3 app.log
DEBUG TokenFilter — validating JWT (attempt 448121)
DEBUG TokenFilter — validating JWT (attempt 448122)
DEBUG TokenFilter — validating JWT (attempt 448123)
In your CIAM job, this exact loop is a Tuesday: SSH into the box, cd to the logs, tail -f auth.log | grep FAILED to watch failed logins live, grep -rn "client_secret" . in a security audit, and curl -i -X POST …/oauth2/token to test the token endpoint without touching the UI. ADO and GitHub Actions pipeline steps are nothing but these commands in a YAML file.
Getting unstuck (scenario ④ above): every command can explain itself. Bash: man ls or ls --help. PowerShell: Get-Help Get-ChildItem -Examples. CMD: help dir or dir /?. And which cmd (Bash) / Get-Command (PowerShell) / where cmd (CMD) tells you which program actually runs.
There are no dumb questions

Do I really have to memorize all these flags?

No — nobody does. You memorize the twelve command names and ask the command itself for the rest: --help for a quick list, man for the full story. Knowing that help exists beats knowing every flag.

I deleted a file with rm. Where's the recycle bin?

There isn't one. rm is immediate and permanent — that's why the scenario ③ animation flags it red. Before any rm -r, run pwd and ls first so you're certain what you're pointing at.

Bash or PowerShell — which should I actually learn?

Bash first: it's what servers, containers, and CI runners speak. But don't fear PowerShell — its aliases (ls, cat, cd) accept your Bash muscle memory, and on Windows it's the native power tool. CMD you only need to read, for old scripts.
