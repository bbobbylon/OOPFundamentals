CLI Basics

The command line is just a conversation: the shell prints a prompt, you type a command, it runs and prints the result, then prompts again. Master a dozen commands — move around, look at files, create and delete things, and ask for help — and you can drive any machine. This page shows them in Bash, PowerShell, and CMD together.

What is the command line — and why does every developer eventually need to know at least 12 commands that work on any machine?

The command-line interface (CLI) is a text-based way to interact with an operating system and its programs. Instead of clicking icons in a GUI, you type commands that the shell interprets and executes. The shell is the program that accepts your commands, figures out which program to run, runs it, and shows you the output. On Linux/macOS the default shell is usually Bash or Zsh. On Windows, PowerShell is the modern shell, with CMD (cmd.exe) being the legacy option. Why learn the CLI: (1) Many tools only have a CLI — most CI/CD pipelines, Docker, Kubernetes, cloud CLIs (az, aws, gcloud), and deployment scripts are CLI-based. (2) Automation — if you can do something in the CLI, you can script it. Click-based UIs can't be scripted. (3) Remote access — when you SSH into a server, there's no GUI; you only have a CLI. (4) Speed — experienced developers navigate and manipulate files faster in the CLI than in any file browser. The anatomy of a CLI command: a command is typically: [command] [flags/options] [arguments]. Example: ls -la /var/log — ls is the command (list directory contents), -la is flags (-l=long format, -a=include hidden files), /var/log is the argument (which directory). Flags are usually -x (short) or --long-form. The 12 commands you must know: navigation: pwd (where am I?), ls/dir (what's here?), cd (change directory); file operations: cat/type (show file contents), mkdir (create directory), rm/del (delete), cp/copy (copy), mv/move (rename/move); power tools: grep/Select-String (search in files), find/Get-ChildItem (find files), pipes (| — chain commands), man/--help (read the manual). Exit codes: every command exits with a numeric code. 0 = success. Any non-zero = error. In scripts and CI/CD, exit codes chain commands: command1 && command2 (run command2 ONLY if command1 succeeded). CI/CD pipelines fail the build if any command exits with non-zero.

Navigation + file ops (Bash)

pwd # print working directory (where am I?) ls -la # list files: -l=long, -a=all (including hidden) cd /var/log # change to absolute path cd .. # go up one level cd ~/projects # ~ = your home directory # Create and delete: mkdir -p a/b/c # create nested dirs (-p = parents, no error if exists) rm -rf ./build # remove directory and all contents (DANGER: no undo!) touch file.txt # create empty file (or update timestamp) cp -r src/ dest/ # copy directory (-r = recursive) mv old.txt new.txt # rename/move a file # View contents: cat file.txt # print entire file to terminal less file.txt # page through large file (q to quit) head -20 file.txt # first 20 lines tail -f app.log # follow log file in real-time (Ctrl+C to stop) wc -l file.txt # count lines # Find and search: find . -name "*.java" -type f # find all Java files under current dir grep -rn "jwt" src/ # search for "jwt" in all files, show line nums

Pipes, redirection, exit codes

# Pipes: output of one command → input of next ls -l | grep ".java" # list only .java files cat app.log | grep ERROR | head -10 # first 10 error lines ps aux | grep "spring" | wc -l # count Spring processes # Redirection: echo "hello" > file.txt # write stdout to file (overwrites) echo "world" >> file.txt # append stdout to file mvn test 2>errors.txt # redirect stderr to file mvn test >out.txt 2>&1 # redirect both stdout and stderr # Exit codes (CRITICAL for CI/CD): ls /var/log; echo "exit: $?" # echo last exit code ($? in Bash) # Bash: $? PowerShell: $LASTEXITCODE # Chain commands: mvn clean install && docker build . # build THEN docker (if mvn succeeds) mvn test || echo "Tests failed!" # if mvn fails, print message # Environment variables: export JAVA_HOME=/usr/lib/jvm/java-17 # set (Bash) $env:JAVA_HOME = "C:\Java\17" # set (PowerShell) echo $JAVA_HOME # read (Bash) echo $env:JAVA_HOME # read (PowerShell)

In CIAM / Your Job: CLI skills are used daily in CIAM work: SSH into servers to check logs or restart services; run az or aws CLI commands to manage cloud resources; write ADO/GitHub Actions pipeline steps (which are just Bash or PowerShell commands); run curl to test OAuth2 endpoints directly (e.g., hit the token endpoint, inspect the response headers); use grep to search Spring Boot logs for JWT validation errors or CORS issues; use find to locate config files on a server. The most useful for CIAM debugging: curl -i -X POST https://am.example.com/oauth2/token -d "grant_type=client_credentials&client_id=...&client_secret=..." — tests your auth flow without involving the UI.

2. Paths — absolute, relative, and the shortcuts

The four ways to point at a place

# absolute — from the root, unambiguous
cd /usr/local/bin       # Linux/mac
cd C:\Windows\System32  # Windows

# relative — from where you are now
cd projects/app

# shortcuts
cd ..      # up one
cd ../..   # up two
cd ~       # home directory
cd -       # previous directory (bash)

Special path tokens

.     # this directory
..    # parent directory
~     # your home (/home/dev, C:\Users\dev)
/     # filesystem root (Linux/mac)
C:\   # a drive root (Windows)

# run a script in THIS folder:
./deploy.sh   # the ./ says "right here"

Slashes differ: Linux/mac use /, Windows traditionally uses \ (though PowerShell accepts / too). That single difference trips up most cross-platform scripts.

Getting unstuck (scenario ④): every command can explain itself. Bash: man ls or ls --help. PowerShell: Get-Help Get-ChildItem -Examples. CMD: help dir or dir /?. And which cmd (Bash) / Get-Command (PowerShell) / where cmd (CMD) tells you which program actually runs.
