Spring Boot Auto-Configuration — the "Magic," Demystified

You add a dependency and suddenly a DataSource, a JSON serializer, and an embedded web server all exist — with zero config. Here's exactly how Boot decides what to wire, and why it politely backs off the moment you define your own.

🪄 How does Spring Boot wire a DataSource, a server, and JSON support from just a dependency?

Classic Spring needed 100+ lines of XML/Java config to wire a database, a web server, and JSON. Auto-configuration replaced that: each starter ships @AutoConfiguration classes (listed in …AutoConfiguration.imports) that Spring evaluates against conditions — @ConditionalOnClass, @ConditionalOnMissingBean, @ConditionalOnProperty — and only the beans whose conditions pass get created. It "politely backs off" because every auto-bean is @ConditionalOnMissingBean: define your own DataSource and Spring's default steps aside.

  • Classpath + conditions drive wiring. Add a starter, the right beans appear.
  • Your beans win. @ConditionalOnMissingBean means your definition overrides the default.
  • It's debuggable via the Conditions Evaluation Report and /actuator/conditions.
  • @SpringBootApplication is three annotations — config + enable-auto-config + component-scan.

Conditions that control wiring

@ConditionalOnClass(HikariDataSource.class) (only if on classpath), @ConditionalOnMissingBean(DataSource.class) (only if you didn't define one), @ConditionalOnProperty("spring.datasource.url") (only if set). All conditions on a class must pass — that's how one starter adds exactly the right beans.

Debugging auto-config

Run with --debug or logging.level.org.springframework.boot.autoconfigure=DEBUG for the Conditions Evaluation Report — every class with which conditions matched and why ("@ConditionalOnClass did not find …"). /actuator/conditions shows it live.

@SpringBootApplication

A composed annotation: @SpringBootConfiguration + @EnableAutoConfiguration (trigger the scan) + @ComponentScan (this package down). SpringApplication.run(App.class, args) bootstraps the whole context.

CIAM: Adding spring-boot-starter-oauth2-resource-server auto-configures a SecurityFilterChain that validates JWTs plus a JwtDecoder that fetches your issuer's JWKS. Define your own SecurityFilterChain bean and Spring's backs off — which also explains the "why is Security blocking everything?" mystery: the default chain requires auth on every endpoint until you customize it.

1. The chain that starts it all

One annotation kicks everything off. @SpringBootApplication is a meta-annotation bundling three things:

@SpringBootApplication  // = these three:
@SpringBootConfiguration   // this class is a @Configuration source
@ComponentScan             // find your @Component/@Service/... beans
@EnableAutoConfiguration    // ← the magic lives here
@EnableAutoConfiguration→ reads AutoConfiguration.imports→ ~150 candidate @AutoConfiguration classes→ evaluate @Conditional→ winners contribute beans

Each starter JAR ships a file META-INF/spring/org.springframework.boot.autoconfigure.AutoConfiguration.imports (the old spring.factories) listing its auto-config classes. Boot loads them all as candidates — then filters by conditions. Convention over configuration = "sensible defaults you can always override."

3. What you just saw — the two killer conditions

@ConditionalOnClass — "react to the classpath"

The bean is created only if a given class is present. This is how adding a JAR "turns a feature on." No JAR, no auto-config — silently.

@AutoConfiguration
@ConditionalOnClass(DataSource.class)
class DataSourceAutoConfiguration {
  @Bean
  @ConditionalOnMissingBean
  DataSource dataSource(...) { … }
}

@ConditionalOnMissingBean — "back off if you did it yourself"

This is why auto-config never fights you. If you declare a DataSource @Bean, Boot's default does not register — yours wins. Override by simply existing.

// your @Configuration:
@Bean
DataSource dataSource() {
  return myCustomPool(); // Boot steps aside
}

Toggle "I declared my own DataSource @Bean" in the demo and watch DataSourceAutoConfiguration back off.

4. The full family of @Conditional annotations

AnnotationActivates the bean only when…
@ConditionalOnClassa class is on the classpath
@ConditionalOnMissingClassa class is absent
@ConditionalOnBeananother bean already exists in the context
@ConditionalOnMissingBeanno such bean exists yet (the "back off" one)
@ConditionalOnPropertya property has a given value (e.g. ...enabled=true)
@ConditionalOnWebApplicationit's a servlet/reactive web app
@ConditionalOnResourcea resource file is present
@ConditionalOnExpressiona SpEL expression is true
@Conditional(MyCondition.class)your own Condition implementation returns true

All of these build on the core @Conditional mechanism. Ordering matters too — @AutoConfiguration(after=…) and @AutoConfigureBefore/After sequence them so "missing bean" checks happen after your config is processed.

5. Debugging it: the conditions report & opting out

See every decision: --debug

Run with --debug (or debug=true) and Boot prints a CONDITIONS EVALUATION REPORT: every positive and negative match, with the reason.

Positive matches:
  DataSourceAutoConfiguration matched:
    - @ConditionalOnClass found 'javax.sql.DataSource'

Negative matches:
  GsonAutoConfiguration:
    - @ConditionalOnClass did NOT find 'com.google.gson.Gson'

Turn one off

// annotation form:
@SpringBootApplication(exclude = {
  DataSourceAutoConfiguration.class
})

# or in application.properties:
spring.autoconfigure.exclude=\
  org...DataSourceAutoConfiguration

Common when you want to configure something fully by hand, or a starter pulled in a feature you don't want (e.g. security's default login page).

6. Write your own auto-configuration (how starters work)

A "starter" is just a JAR with auto-config classes + that imports file. To make your own library auto-configure itself:

// 1. the auto-config class
@AutoConfiguration
@ConditionalOnClass(GreetingService.class)
@EnableConfigurationProperties(GreetingProps.class)
class GreetingAutoConfiguration {
  @Bean
  @ConditionalOnMissingBean
  GreetingService greetingService(GreetingProps p) {
    return new GreetingService(p.getPrefix());
  }
}
// 2. register it — src/main/resources/META-INF/spring/
//    org.springframework.boot.autoconfigure.AutoConfiguration.imports
com.acme.greeting.GreetingAutoConfiguration

Now anyone who adds your JAR gets a GreetingService bean for free, configurable via greeting.prefix=… — and can still override it with their own @Bean. That's the entire starter pattern.

7. One-sentence recap

🪄 @EnableAutoConfiguration loads ~150 candidate @AutoConfiguration classes listed in each starter's AutoConfiguration.imports, evaluates each one's @Conditional guards against your classpath, beans, and properties, and registers the beans for the ones that pass — using @ConditionalOnMissingBean so it always defers to anything you defined yourself.
