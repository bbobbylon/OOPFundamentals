Exceptions — Stack Unwinding & Recovery

When something goes wrong, Java throws an exception and rewinds the call stack frame by frame until something catches it. Watch it happen.

What is an exception — and why does Java unwind the call stack to find a handler?

When Java encounters an error (null dereference, array out-of-bounds, division by zero, file not found), it creates an Exception object and throws it. The JVM then looks at the current method's code for a catch block that handles that exception type. If there isn't one, it goes up to the calling method. Then the method that called that. This continues up the call stack until a handler is found — or the stack is exhausted and the JVM prints a stack trace and terminates the thread. There are three kinds: Checked exceptions (IOException, SQLException) — the compiler forces you to handle or declare them, because they represent recoverable conditions. Unchecked exceptions (RuntimeException subclasses: NullPointerException, IllegalArgumentException) — represent programming bugs; you're not required to catch them. Errors (OutOfMemoryError, StackOverflowError) — JVM-level failures; don't catch these. The finally block always runs — even if an exception is thrown, even if a return is hit — making it the right place for cleanup code.

try-catch-finally anatomy

try { String s = null; s.length(); // NullPointerException thrown here } catch (NullPointerException e) { System.out.println("caught: " + e.getMessage()); } catch (RuntimeException e) { // more general — catches any RuntimeException not caught above } finally { // always runs — even if an exception is thrown or not caught // use for: closing connections, releasing locks }. Multiple catch blocks: more specific exceptions first — a RuntimeException catch before NullPointerException catch would be a compile error.

Custom exceptions

Extend RuntimeException for unchecked (no forced handling): class UserNotFoundException extends RuntimeException { private final Long userId; public UserNotFoundException(Long id) { super("User not found: " + id); this.userId = id; } public Long getUserId() { return userId; } }. Extend Exception for checked. Include context data (userId, etc.) so callers can log or handle with detail. Naming convention: always end in Exception.

try-with-resources

try (BufferedReader br = new BufferedReader(new FileReader(path))) { return br.readLine(); }. The resource (AutoCloseable) is automatically closed when the try block exits — whether normally or with an exception. No need for finally { br.close() }. Can declare multiple resources: try (Connection c = ds.getConnection(); PreparedStatement ps = c.prepareStatement(sql)) — both closed in reverse order. Essential for: file handles, DB connections, HTTP clients.

In CIAM / Spring Boot: Custom exceptions map to HTTP status codes: UserNotFoundException extends RuntimeException → Spring's @ExceptionHandler returns 404. UnauthorizedException → 401. ForbiddenException → 403. ValidationException → 400. The @ControllerAdvice is one central place that catches all these and converts them to ProblemDetail JSON responses. Never let raw NullPointerException reach the HTTP response — it's a 500 that leaks stack traces to clients.

The exception hierarchy

Throwable
├── Error    // JVM is dying — don't catch
│ ├── OutOfMemoryError   // heap exhausted
│ └── StackOverflowError   // infinite recursion
└── Exception
    ├── IOException   // CHECKED — compiler forces you to handle
    │ ├── FileNotFoundException
    │ └── SocketTimeoutException
    ├── SQLException
    └── RuntimeException   // UNCHECKED — compiler ignores
        ├── NullPointerException
        ├── IllegalArgumentException
        ├── IllegalStateException
        ├── ArrayIndexOutOfBoundsException
        └── ClassCastException

Checked vs unchecked is a famous Java debate. Checked exceptions force callers to handle them (compile error otherwise) — great for recoverable problems like network failures. Unchecked are usually programming bugs (null check missed, bad arg). Most modern Java leans unchecked; lambdas/streams don't play well with checked.

The full anatomy: try / catch / finally / try-with-resources

try {                                     // 1. risky code
    var data = Files.readString(path);
    return parser.parse(data);
} catch (FileNotFoundException e) {       // 2. specific first
    log.warn("missing {}", path);
    return Defaults.EMPTY;
} catch (IOException | ParseException e) {  // 3. multi-catch — same handling
    throw new AppException("failed to load " + path, e);  // chain the cause
} finally {                                // 4. always runs — cleanup
    log.debug("load attempt finished");
}

// Better — try-with-resources auto-closes anything AutoCloseable
try (var in = Files.newBufferedReader(path)) {
    return parser.parse(in);
} catch (IOException e) {
    throw new AppException("failed", e);
}
// `in` is closed even if parser throws — no leaked file handle

Custom exceptions — your domain has its own failures

// Domain-specific exception with extra context
public class InsufficientFundsException extends RuntimeException {
    private final BigDecimal requested, balance;

    public InsufficientFundsException(BigDecimal requested, BigDecimal balance) {
        super("need " + requested + ", have " + balance);
        this.requested = requested;
        this.balance = balance;
    }
    // getters — callers can render a useful error to the user
}

// usage
if (amount.compareTo(balance) > 0)
    throw new InsufficientFundsException(amount, balance);

The rules of the trade

✅ Catch specific, not generic

Catching Exception or worse Throwable hides bugs. Catch what you can actually handle; let everything else bubble up.

✅ Chain the cause

When wrapping an exception, always pass the original: throw new MyException(msg, e). The stack trace becomes "caused by:" — debugging gold.

✅ Throw early, validate at the boundary

Reject bad input at the front door (controller, public method) — deep code should be able to assume its inputs are valid.

✅ Use try-with-resources for anything AutoCloseable

Streams, readers, JDBC connections, sockets. The compiler enforces close-even-on-exception.

🚫 Don't use exceptions for control flow

Throwing is expensive (the JVM captures the whole stack). If "user not found" is normal, return Optional — don't throw UserNotFound.

🚫 Don't swallow exceptions

catch (Exception e) { } = invisible bugs forever. Log it, rethrow it, or handle it. Never nothing.

🚫 Don't catch and lose the cause

throw new MyException("bad") drops the original stack. Always pass e too.

🚫 Don't return null from a method that could fail

Return an Optional<T> instead. Callers can't ignore Optional; they can ignore null.

Read it bottom-up. The bottom is where the call started; the top is where the explosion happened. "Caused by:" sections show wrapped exceptions in chronological order.

🌱 New to exceptions? It's how Java says "something went wrong."

When code can't continue normally, instead of returning a fake value it throws an exception, and execution jumps to the nearest matching handler. You wrap risky code in try { ... } catch (SomeException e) { ... } — the catch runs only if that error happened — and an optional finally { ... } runs cleanup no matter what. If nothing catches it, the exception travels up the call stack and Java prints a stack trace. The point: your normal "happy path" code stays clean, and error handling lives in its own clearly-marked place.

🧠 Expert corner — checked vs unchecked, chaining, and not swallowing

  • Three families. Checked (extends Exception, e.g. IOException) — the compiler forces you to handle or declare them. Unchecked (extends RuntimeException, e.g. NullPointerException) — programming errors, no declaration required. Error (e.g. OutOfMemoryError) — don't catch.
  • Catch specific before general. List narrower types first; a broad catch (Exception e) above them makes the specific ones unreachable. Never write an empty catch — swallowing an exception hides the bug.
  • Preserve the cause when re-throwing. throw new ServiceException("loading user", e) keeps the original as "Caused by:" — losing e throws away the real stack trace.
  • try-with-resources auto-closes anything AutoCloseable (files, connections) even on exception — replaces fragile finally { close(); }.
  • Define your own by subclassing RuntimeException (or a domain base) so callers can catch your errors precisely.
  • CIAM/real tie-in. In Spring you map exceptions to HTTP responses with @ControllerAdvice / @ExceptionHandler returning a ProblemDetail — a NotFoundException becomes a clean 404 instead of a stack trace leaking to the client. See Validation & ProblemDetail.
