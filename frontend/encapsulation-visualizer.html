Encapsulation — Hide the State, Expose the Behavior

or, why a public field is a promise you can never take back

Make fields private. Force callers through methods that can validate, log, or reject. Watch the difference between a raw struct and a real object.

The problem

A public field is part of your API forever.

Everything public

Every caller can read and write every field, so every field is now a contract you cannot change without breaking someone.

account.balance = -500 order.total = 0 user.role = "ADMIN" ⚠ no validation anywhere

The object cannot defend its own invariants, because nothing has to go through it.

A wall, with doors you chose
private double balance ↓ the only way in deposit(amount) — validates, then changes ↓ the only way out getBalance() — returns a copy of the truth
Encapsulation is not "add getters and setters". A setter for every private field is a public field with extra steps. The point is to expose behaviour — deposit(), not setBalance() — so the object stays the only thing that can put itself in a bad state.

Java's four levels, from the inside out. private — this class only. (default, no keyword) — this package, which is the one people forget exists. protected — this package plus subclasses anywhere. public — everyone, forever. Start at private and widen only when something concrete forces you to; widening is easy, narrowing breaks callers.

Questions from the back row

So getters and setters are bad?

Setters are the suspicious half. A getter is often fine — code has to read state. A setter for every field means the object has no rules about its own data, which is the thing encapsulation was supposed to provide.

Isn't immutability simpler than all this?

Usually, yes — and it is the strongest form of this idea. If nothing can change after construction, there is no bad state to defend against, no defensive copy to remember, and the object is thread-safe for free. Reach for it first.

🔒 What is encapsulation? Why make fields private?

Encapsulation means a class keeps its data private and only lets the outside world touch it through methods that can enforce rules. A public balance field lets anyone write account.balance = -999999 — no validation, no logging, no control. Put it behind a deposit()/withdraw() method and the class can reject bad input, log every change, and guarantee its own invariants ("balance never goes negative").

  • Make fields private; expose behaviour through methods (getters/setters, or richer operations) that validate before they mutate.
  • You own the contract: callers depend on your method signatures, never on your internal fields.
  • That lets you change the internals freely — swap int for BigDecimal, add caching — without breaking a single caller.
  • It protects invariants: the rules that must always hold (a non-negative balance, a valid email) live in one guarded place.
  • It's one of the four pillars of OOP — the foundation that inheritance, polymorphism, and abstraction build on.

✗ No encapsulation

  • public int balance;
  • account.balance = -1000; — allowed!
  • no validation, no logging, no control

✓ With encapsulation

  • private int balance;
  • void deposit(int amt) { … }
  • if (amt <= 0) throw … — guarded
In Spring Boot:beans use private fields + constructor injection; JPA entities use private fields + getters so Hibernate manages state; DTOs use private fields + @NotNull/@Size so invalid data never reaches the service layer.

Every change runs through deposit / withdraw, which enforce the rules.
class GoodAccount {
    private final String owner;     // can't be changed after construction
    private double balance;            // no public setter, intentionally
    private final LocalDate opens;  // same idea — immutable, and no setter exists at all

    public void deposit(double amt) {
        if (amt <= 0) throw new IllegalArgumentException("amount must be positive");  // the rule a public field could never enforce
        balance += amt;
    }
    public void withdraw(double amt) {
        if (amt <= 0) throw new IllegalArgumentException();
        if (amt > balance) throw new InsufficientFundsException();  // can never overdraw — impossible with a public field
        balance -= amt;
    }
    public double getBalance() { return balance; }  // read-only getter
}

What encapsulation actually buys you

🛡️ Invariants stay true

A class invariant is a rule that's always supposed to hold — like "balance ≥ 0" or "email contains an @". With public fields, callers can break that rule the moment your back is turned. With private fields and validating setters, the rule is enforced for the lifetime of the object.

🔁 You can change the implementation later

Today balance is a double. Tomorrow you decide it should be a BigDecimal with currency, or stored remotely in a database. With encapsulation, only the methods change — every caller keeps working.

📋 One place to log / validate / cache

"Log every withdrawal over $10k for fraud team" — easy. Add it to withdraw. With public fields, you'd have to find every place anyone touched the balance.

🧵 Thread-safety lives in the methods

Synchronize deposit and withdraw once — done. You can't synchronize a public field; every reader and writer has to remember to lock manually. Easy to forget.

🧪 Testability

Tests interact with the public surface, not the internals. You can refactor the guts of a class freely as long as the methods keep their contract. That's how big codebases stay maintainable.

🔍 Debugging is finite

"Who set the balance to -2 billion?" With public fields, the answer is "anyone in the codebase." With private fields, it's "one of three methods" — and you can put a breakpoint in each of them.

Java's four access levels — when to use each

ModifierVisible fromDefault forUse when
private Same class only Fields, helpers Default for everything. Fields, internal helpers, anything you'd be embarrassed for a caller to see.
(default) Same package (no modifier) Package-private. Useful for tightly-coupled helper classes that ship together but aren't part of the public API.
protected Same package + subclasses Template-method hooks You're building a framework and want subclasses to override or extend specific points. Otherwise: avoid.
public Everywhere Methods, constants You've thought hard about the contract. This is the API; once people use it, it's nearly impossible to change.

Rule of thumb: start with private and only widen when you have a concrete reason. Loosening access later is easy; tightening it is a breaking change.

The dangerous trap — getters that leak mutable state

Making fields private isn't enough if your getter hands back the internal object. The caller can then mutate your "private" data through the back door. 

class Order {
    private List<Item> items = new ArrayList<>();

    // ❌ Broken — caller gets the actual list and can mutate it
    public List<Item> getItems() { return items; }
}

Order o = new Order();
o.getItems().clear();   // just wiped a "private" field!

// ✅ Fix 1 — return an unmodifiable view
public List<Item> getItems() { return Collections.unmodifiableList(items); }

// ✅ Fix 2 — return a defensive copy
public List<Item> getItems() { return new ArrayList<>(items); }

// ✅ Fix 3 — expose behaviors, not the list
public void addItem(Item i) { items.add(i); }
public int itemCount() { return items.size(); }

Immutability — the ultimate encapsulation

An immutable object can't change after construction. That makes it inherently thread-safe, safe to cache, safe to use as a HashMap key. Java records give you this with one line. 

// Pre-Java-14: lots of boilerplate
public final class Money {
    private final BigDecimal amount;
    private final String currency;
    public Money(BigDecimal amount, String currency) {
        this.amount = amount; this.currency = currency;
    }
    // + getters, equals, hashCode, toString...
}

// Java 14+: one line, equivalent
public record Money(BigDecimal amount, String currency) {}
