HTTP & REST — How the Web Actually Talks

Every API call is a HTTP request and a HTTP response. Method, path, headers, body — server sends back status, headers, body. Once you know the shape, the rest is patterns.

🌐 What is HTTP and REST — and why is every piece of your stack (Angular HttpClient, Spring Boot @RestController, OAuth2 token exchange, CORS) built on top of these same 6 concepts?

HTTP (HyperText Transfer Protocol) is the language of the web — every request your Angular app makes and every response your Spring Boot backend sends uses it. Understanding HTTP deeply means you can debug anything: 401s, CORS errors, token expiry, slow API calls, missing data. A request has four parts: Method (what to do: GET/POST/PUT/PATCH/DELETE), Path (which resource: /api/users/42), Headers (metadata: Authorization, Content-Type, Accept, CORS headers), and Body (the data: JSON payload on POST/PUT). A response has: Status Code (2xx success, 3xx redirect, 4xx client error, 5xx server error) and body. HTTP Methods in REST: GET = read (no body, idempotent, safe); POST = create (body required, not idempotent); PUT = full update/replace (body required, idempotent); PATCH = partial update (body with just changed fields); DELETE = remove (no body, idempotent). Idempotent means calling it multiple times gives the same result as calling once — important for retry logic. Status codes you must know: 200 OK, 201 Created, 204 No Content (successful DELETE or PUT with no response body), 301/302 Redirect, 400 Bad Request (invalid input), 401 Unauthorized (no valid token), 403 Forbidden (valid token but insufficient permission), 404 Not Found, 405 Method Not Allowed, 409 Conflict (duplicate resource), 422 Unprocessable Entity (validation failed), 429 Too Many Requests, 500 Internal Server Error, 503 Service Unavailable. REST (Representational State Transfer) is an architectural style that uses HTTP for APIs. REST principles: resources are nouns (not verbs) in the URL; HTTP method expresses the action; responses are stateless (server stores nothing about the client between requests); use standard status codes; version your API (v1/v2 in path or header). Key headers: Authorization (Bearer {token} for OAuth2 JWT); Content-Type: application/json (tells server how to parse body); Accept: application/json (tells server what format to return); CORS headers (Access-Control-Allow-Origin, etc. — set by server to permit cross-origin browser requests). OAuth2 and HTTP: OAuth2 token exchange is just HTTP POST requests. The Angular HttpClient sends an Authorization: Bearer header on every protected request, the Spring SecurityFilterChain extracts and validates that JWT, and returns 401 if it's missing or expired, 403 if the user lacks the required role/scope.

Status codes + CORS

// Status code decision flow: // Request valid + resource exists → 200 OK // Resource created → 201 Created (return Location header) // No response body (DELETE, PUT updating) → 204 No Content // Invalid input / missing required field → 400 Bad Request // No/expired token → 401 Unauthorized // Valid token, wrong role/scope → 403 Forbidden // Wrong URL → 404 Not Found // Validation failed (@Valid) → 422 Unprocessable Entity // Server crash → 500 Internal Server Error // CORS (Cross-Origin Resource Sharing): // Browser blocks Angular (localhost:4200) calling Spring Boot (localhost:8080) // unless the SERVER explicitly allows it via response headers: // Access-Control-Allow-Origin: http://localhost:4200 // Access-Control-Allow-Methods: GET, POST, PUT, DELETE, PATCH // Access-Control-Allow-Headers: Authorization, Content-Type // Spring Boot: configure CORS globally: @Bean CorsConfigurationSource corsConfig() { var c = new CorsConfiguration(); c.setAllowedOrigins(List.of("http://localhost:4200")); c.setAllowedMethods(List.of("*")); c.setAllowedHeaders(List.of("*")); var s = new UrlBasedCorsConfigurationSource(); s.registerCorsConfiguration("/**", c); return s; }

In CIAM / Your Job: HTTP/REST is the foundation of every CIAM integration. The OAuth2 Authorization Code Flow is a series of HTTP redirects and token exchange POSTs. When Ping or Entra issues a token, your Angular app attaches it as Authorization: Bearer {token} on every HTTP call. Your Spring Boot SecurityFilterChain validates that header on every request — returning 401 if expired, 403 if the token lacks the required scope. CORS configuration is mandatory: Angular on port 4200 talking to Spring Boot on 8080 will be blocked by the browser until Spring explicitly allows it. The 401 vs 403 distinction matters critically in CIAM: 401 = "I don't know who you are, please authenticate"; 403 = "I know who you are but you're not allowed here, don't bother re-authenticating." Getting these wrong confuses both users and client applications. In Ping IDM, every connector operation is an HTTP call; understanding REST means you can write custom Scripted REST connectors.

The problem

The methods table above hedges PATCH with one word — "usually." This is the block where "usually" turns into an outage.

A retried PATCH doubles a number that decides whether someone gets locked out

Your CIAM login endpoint tracks failed attempts with PATCH /api/users/42/login-attempts, body {"op": "increment"} — the service does attempts = attempts + 1 server-side. The methods table calls PATCH "usually idempotent," so your API gateway's retry policy treats it exactly like PUT and DELETE: safe to resend automatically if the client never got a response.

A flaky mobile connection loses one response in transit — the server genuinely incremented attempts to 3, but the acknowledgment never reached the client. Following its idempotent-retry policy, the gateway resends the identical PATCH. The server has no idea this is a repeat; it increments attempts to 4. One real failed login attempt just became two, and the account locks out a full attempt earlier than it should have.

the request timed out ✓ the retry followed policy ✓ what "idempotent" means for THIS body ⚠

PUT's idempotency comes from HOW it's written — send the whole final state. PATCH's idempotency, if it exists at all, depends entirely on what operation the body describes.

Ask what the PATCH body actually says before trusting the method name
Distinguish "set" from "adjust" in every PATCH body you write ↓ {"attempts": 4} — set the field to a known final value — is idempotent, since resending it twice leaves attempts at 4 either way; {"op":"increment"} — adjust relative to current state — is not, since resending applies the adjustment twice Give non-idempotent requests an idempotency key, not a blind retry policy ↓ the client generates one ID per logical operation and sends it as a header; the server remembers keys it has already processed and returns the ORIGINAL result on a duplicate, instead of re-executing the write Default retries to the genuinely safe methods; opt PATCH in per-endpoint ↓ a gateway that blanket-retries "GET, PUT, DELETE, and PATCH because the table says usually" needs that "usually" audited endpoint by endpoint, not assumed once for the whole verb
Idempotency is a property of the request, not the verb. PUT is idempotent because the convention behind it is to always send the complete final state — applying the same destination twice leaves you in the same place. PATCH carries no such universal convention: it's idempotent only when its body describes a destination too, and not when it describes an adjustment relative to whatever the current state happens to be.
PUT promises a destination: "end up looking like THIS" — landing there twice changes nothing. A delta-style PATCH promises a direction instead: "move one step this way" — and taking two steps is never the same as taking one.

I always carry the whole final state. Apply me twice and you land in the exact same place both times — that's where my idempotency actually comes from.

This particular PATCH body

I carry an instruction, not a destination — "add one." Apply me twice and you've added two. Nothing about the word PATCH ever promised otherwise.

An idempotency key

I'm the fix for exactly this. Tag the request once, and the server can recognize a resend and hand back the original answer instead of doing the work twice.

The mechanism

Follow one lost response from a genuine server-side write to a doubled counter.

  1. Client sends PATCH /users/42/login-attempts with body {"op":"increment"} after a failed logina delta, not a destination
  2. Server receives it, increments attempts from 2 to 3, and starts sending back 200 OKthe write already happened
  3. The response is lost on a flaky mobile connection before the client ever sees itthe client hears only silence
  4. The client times out and, trusting "PATCH is usually idempotent," resends the identical requestfollowing the retry policy
  5. The server has no memory of the first attempt — it increments attempts from 3 to 4no idea this is a repeat
  6. One real failed login is now recorded as two — one attempt closer to a lockout the user didn't actually earnthe retry caused this, not the user

Step 3 is the crux, and it's worth naming directly: a timeout tells the client nothing about whether the server received and acted on the request. "No response" and "no effect" are two completely different facts, and a retry policy that conflates them is the actual root cause here — not the PATCH body, and not the flaky network.

Same HTTP method, same URL, same retry policy — completely different real-world safety, decided entirely by what's inside the body. A retry policy that keys off the method name alone is reading the label on the box, not what's actually packed inside it.

Your API gateway automatically retries any GET, PUT, or DELETE that times out without a response, on the theory that those methods are always idempotent. A teammate proposes adding PATCH to that same auto-retry list, citing the methods table's "PATCH is idempotent" entry. What's the actual risk?

The spec doesn't actually guarantee this the way it guarantees PUT and DELETE — RFC 5789 explicitly leaves PATCH's exact semantics to whatever the specific API defines. Treating it as automatically safe is precisely the assumption that produces double-increments.

There's no such universal requirement — most servers happily accept and process a duplicate PATCH with no conflict response at all, which is exactly the problem: nothing built into HTTP stops the second one from silently re-applying.

Right. A method name is not a safety guarantee — it's the body's semantics that decide whether a retry is harmless or harmful, and a gateway retry policy keyed only on the verb has no way to see the difference.

Where you have seen this before

"Retrying it did the thing twice" is one of the oldest bugs in distributed systems.

Payment APIs and idempotency keys

Stripe and every major payment API popularized the idempotency-key pattern for exactly this reason: retrying a "charge $50" request without one can charge the customer twice if the first charge actually succeeded and only its response got lost. The fix is identical to the PATCH fix — tag the operation once, let the server recognize a resend.

the textbook version of the exact same bug

SQL's relative vs absolute UPDATE

UPDATE accounts SET balance = balance - 10 run twice subtracts 20; UPDATE accounts SET balance = 90 run twice still leaves it at 90. Same database, same table, same statement style — the only difference is whether the SQL describes a destination or a delta, one layer beneath the API that wraps it.

the identical distinction, one layer down the stack

Kafka's at-least-once delivery

A message broker that redelivers any message it didn't get an acknowledgment for in time will hand a consumer the same message twice. A consumer whose side effect is "increment a counter" or "send an email" duplicates that effect on redelivery — the entire reason "idempotent consumer" is a standing requirement in event-driven architecture, not just a nice-to-have.

at-least-once delivery, at-most-once safety, only if the consumer earns it

The HTTP methods (verbs)

VerbMeaningHas body?Safe?Idempotent?Cacheable?
GET Read a resource No ✅ — never modifies state ✅ ✅
POST Create a new resource (or trigger an action) Yes ❌ — modifies state ❌ — calling twice creates two ❌
PUT Replace a resource at a known URL Yes ❌ ✅ — same result every time ❌
PATCH Partial update — change some fields Yes ❌ Usually ✅ (depends on impl) ❌
DELETE Remove a resource Usually no ❌ ✅ — gone is gone (404 second time is fine) ❌

Idempotency matters because clients retry on network failures. If POST creates a user, retrying creates two. PUT/DELETE retries are safe. Production APIs solve POST idempotency with idempotency keys — a header the server uses to dedupe retries.

What makes an API "RESTful"

📦 Resources, not actions

The URL is a noun. Don't write /getUser?id=42; write GET /users/42. The verb is the HTTP method, not the path.

🆔 Stable, hierarchical URLs

Collections plural, item singular: /users → /users/42 → /users/42/orders → /users/42/orders/7.

🧱 Statelessness

Every request carries everything needed (auth token, parameters). The server doesn't remember you between calls. That's why REST scales — any server can answer.

🤝 Use the right status code

Don't return 200 with {"error": "..."}. Return 4xx for client problems, 5xx for server problems. Clients and proxies and monitoring all depend on it.

📜 Versioning

Breaking changes need a new version: /v1/users → /v2/users, or via header Accept: application/vnd.example.v2+json.

📃 Pagination & filtering via query string

GET /users?status=active&page=3&size=20. Return total count and next/prev URLs in the body or as Link: header.

The Java side — Spring REST in 30 seconds

@RestController
@RequestMapping("/api/users")
class UserController {
    private final UserRepository repo;
    // constructor injection omitted

    @GetMapping                                           // GET /api/users
    public List<User> list() { return repo.findAll(); }

    @GetMapping("/{id}")                                  // GET /api/users/42
    public User get(@PathVariable Long id) {
        return repo.findById(id)
            .orElseThrow(() -> new NotFoundException(id));
    }

    @PostMapping                                          // POST /api/users
    @ResponseStatus(HttpStatus.CREATED)                   // 201, not 200
    public User create(@RequestBody @Valid NewUser body) {
        return repo.save(body.toEntity());
    }

    @DeleteMapping("/{id}")                               // DELETE /api/users/42
    @ResponseStatus(HttpStatus.NO_CONTENT)                // 204, no body
    public void delete(@PathVariable Long id) { repo.deleteById(id); }
}
