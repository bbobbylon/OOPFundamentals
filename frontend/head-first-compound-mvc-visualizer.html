Compound Patterns & MVC — the DJ Beat Controller

Chapter 12 — the finale. A compound pattern is several patterns working together to solve a recurring problem. The most famous one is MVC. Strip away the buzzword and MVC is just three patterns you already know, teaming up: the View observes the Model (Observer), the View delegates user actions to a Controller (Strategy), and the View's UI is a tree of widgets (Composite).

🎯 What is MVC — and which patterns from earlier chapters are actually powering it?

MVC stands for Model-View-Controller — the most widely used architectural compound pattern. Head First reveals it's not a new pattern at all: it's three patterns you already know, combined. Model: holds the data and business logic. Notifies views when it changes. It's the Observable (Subject) from Chapter 2. Views register as Observers. View: displays the data. Gets notified by the Model and re-renders. It's also a Composite — built from a tree of sub-views and widgets, each of which may itself be a composite. The View also delegates user actions to the Controller — this is the Strategy pattern: you can swap the Controller (the strategy) without changing the View. Controller: receives user input from the View, translates it into model updates. It's the Strategy object — plug in a different Controller and the View behaves differently without changing its own code. The compound pattern is the insight: you can recognise MVC in any framework (Spring MVC, Angular, React) by identifying which part is the Observable, which is the Strategy, which is the Composite.

MVC request loop

The request loop in MVC: (1) User clicks "Save" in the View. (2) View calls controller.save(formData) — Strategy delegation. (3) Controller validates, calls model.update(data). (4) Model persists and calls notifyObservers() — Observer notification. (5) View receives update() call (it's an Observer). (6) View calls model.getState() and re-renders. The Controller never touches the View directly; the Model never knows which View is looking at it; the View never persists data. This separation of concerns is the core value of MVC. Every framework claims MVC; not all implement the full Observer loop.

Spring MVC decomposed

Model: @Service and @Repository classes (business logic + DB). View: Thymeleaf templates, or the JSON payload returned to Angular. Controller: @RestController — receives HTTP request, calls service, returns response. Observer: Spring's @EventListener — services publish events, other services observe. Strategy: HandlerMapping strategies map requests to handlers; MessageConverter strategies convert Java → JSON/XML. Composite: FilterChain is a Composite — each filter may delegate to child filters. The DispatcherServlet is the front controller — entry point for the entire MVC framework.

Angular MVC decomposed

Model: Angular @Injectable services + RxJS BehaviorSubject or Signals — hold state, emit changes. View: Angular component templates — observe the model via async pipe (subscribes to Observable) or computed() signals. The component tree is a Composite (components containing components). Controller: Angular component class — handles user events ((click)="save()"), calls services. Strategy: the component swaps its behaviour by injecting a different service. Observer: BehaviorSubject.subscribe() / Signals effect() — view reacts to model changes. Angular Router: the Controller deciding which View component to render based on the URL.

In CIAM / Spring Boot + Angular: Full CIAM MVC loop: (1) Admin clicks "Assign Role" in Angular (View). (2) UserDetailComponent calls userService.assignRole(userId, roleId) (Controller delegates to Model). (3) Angular UserService POSTs to /api/users/42/roles. (4) Spring UserController calls userServiceBean.assignRole(42, roleId). (5) UserService updates DB, publishes RoleAssignedEvent (Observable notifies). (6) AuditService observes (@EventListener) and logs. (7) Spring returns 200 JSON. (8) Angular UserService emits updated user to BehaviorSubject (Model notifies Observers). (9) UserDetailComponent re-renders roles list (View observes Model). Observer + Strategy + Composite — all three, all the way through the stack.

The three roles — Model, View, Controller

🥁 Model

The data + business rules (the BeatModel: BPM, play/stop). Knows nothing about the UI. Notifies observers when it changes.

🖥️ View

The presentation. Observes the model and redraws on change. Sends user gestures to the controller — never touches model logic itself.

🎛️ Controller

Takes user input from the view and turns it into model operations. The "strategy" that defines how the view behaves.

Brain Power. Why split View and Controller at all — they both deal with the UI? Because separating "how it looks" (View) from "what user actions mean" (Controller) lets you swap behavior without touching the display. Give the same View a different Controller and the buttons do different things. That swap-ability is the Strategy pattern hiding inside MVC.

The flow, in code

View delegates to the Controller (Strategy)

// user clicks "increase BPM" in the View
public void onIncreaseClicked() {
  controller.increaseBPM();   // delegate, don't decide
}

Model notifies; View pulls (Observer)

// Controller asked the Model to change…
model.setBPM(model.getBPM() + 1);
// …Model then tells every observer
notifyObservers();   // View.update() re-reads + redraws
The MVC loopView → Controller → Model → notify → View
A clean cycle: input flows one way, change-notifications flow back the other.

Why the Controller is a Strategy

The View is configured with a Controller object. Swap it and the same on-screen controls behave entirely differently — the View doesn't change at all.

DJView view = new DJView(beatController, beatModel);   // DJ behavior
// later, reuse the SAME view with a different strategy:
view.setController(new HeartRateController(heartModel));   // now it's a heart monitor

Q: Isn't this just "separation of concerns"? Why call it patterns?

A: Separation of concerns is the goal; the patterns are how you achieve it cleanly. Observer decouples Model from View; Strategy decouples View from behavior; Composite organizes the UI. Naming them lets you recognize the same machinery in any framework you'll ever touch.

MVC = three patterns you already know

Observer

Model is the Subject; Views are observers. The model pushes change-notifications without knowing which views exist. Model ↔ View decoupled.

Strategy

The View's Controller is a pluggable strategy for handling input. Swap it to change behavior. View ↔ behavior decoupled.

Composite

The View's GUI is a tree of windows/panels/buttons, refreshed uniformly. The UI is a Composite.

This is the whole point of the book. Patterns aren't isolated tricks — they combine. Once you see Observer + Strategy + Composite inside MVC, you'll spot the same trio inside every UI framework, and you'll be able to name what's happening instead of guessing.

MVC today — you live in it

Angular / React

A component template is the View; a service/store/signal is the Model (and Observer is literally RxJS/Signals pushing changes to the view); event handlers + the component class play Controller. The component tree is a Composite. Modern variants call it MVVM/MVU, but it's the same trio.

Spring MVC

The name is on the box. @Controller handles the request, the Model map carries data, a template (Thymeleaf/JSON) is the View. The DispatcherServlet is the front controller wiring it together.
