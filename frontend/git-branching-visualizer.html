Branching Strategies

GitFlow, GitHub Flow, and trunk-based development — what each looks like and when to use which.

🔀 What are branching strategies — and which one should your team use?

A branching strategy is a set of rules that defines how your team uses Git branches — when to create branches, how to name them, when to merge, and what branches represent the "truth" of production code. Without a strategy, teams end up with long-lived branches that diverge badly, painful merges, and uncertainty about what's actually deployed. Three main strategies dominate: GitFlow: uses two permanent branches (main = production, develop = integration) plus temporary feature, release, and hotfix branches. When to use: teams that have scheduled releases (version 1.0 ships on the 15th of every month), need to maintain multiple production versions simultaneously, or have strict QA gates between environments. Critique: complex, lots of merging back and forth, long-lived branches cause merge hell. GitHub Flow: just one permanent branch (main = always deployable) plus short-lived feature branches. Feature branch → PR → merge to main → deploy immediately. When to use: continuous deployment (every merge to main deploys to production), small-to-medium teams, SaaS products. Simple and fast. Assumption: your tests are comprehensive enough that main is always deployable. Trunk-Based Development: everyone commits to main (or merges feature branches within a day). Feature flags hide incomplete features in production. Extreme version of GitHub Flow. When to use: highly mature teams with comprehensive test coverage, full CI/CD automation, feature flag infrastructure. Google, Facebook, and high-velocity tech companies use this. Azure DevOps (ADO) supports all three natively. Branch policies enforce: required reviewers, CI must pass, no direct push to main. Pull Requests are the merge mechanism regardless of strategy. Key insight: all three strategies ultimately serve the same goal — keeping main releasable at all times and integrating changes frequently to reduce merge conflicts.

GitFlow commands

# GitFlow branch structure: main ← production code develop ← integration branch feature/X ← new features (from develop) release/1.3.0 ← pre-release stabilization hotfix/session-bug ← prod bug fix (from main) # Start feature: git checkout develop git checkout -b feature/ciam-mfa ... make commits ... git checkout develop git merge --no-ff feature/ciam-mfa git branch -d feature/ciam-mfa # Create release: git checkout -b release/1.3.0 develop ... bug fixes only ... git checkout main; git merge --no-ff release/1.3.0 git tag -a v1.3.0 -m "Release 1.3.0" git checkout develop; git merge --no-ff release/1.3.0 # Hotfix: git checkout -b hotfix/session-crash main ... fix ... git checkout main; git merge --no-ff hotfix/session-crash git checkout develop; git merge --no-ff hotfix/session-crash

GitHub Flow (simple)

# GitHub Flow — just two rules: # 1. main is ALWAYS deployable # 2. Feature branches are short-lived (days, not weeks) # Workflow: git switch main git pull origin main git switch -c feature/add-entra-provisioning # ... make small, focused commits ... git commit -m "feat: add Entra user creation endpoint" git push origin feature/add-entra-provisioning # Create PR → review → CI passes → merge # main deploys automatically via CI/CD pipeline # Naming conventions: feature/ ← new features fix/ ← bug fixes chore/ ← maintenance, deps docs/ ← documentation only # ADO branch protection: # main: require PR, require 1 reviewer # require CI to pass, no direct push

Comparison + choice

When to use each: GitFlow: you release versioned software (installed apps, APIs with versioned endpoints, enterprise software with quarterly releases). You maintain multiple versions (v1 support + v2 dev). Complexity is worth it for clear release boundaries. GitHub Flow: SaaS/web app deploying continuously. One production version. Small feature PRs. Works great with ADO pipelines that deploy on merge to main. Most CIAM web services fit here. Trunk-based: mature team with great test coverage + feature flags. Everyone commits to main (with short feature branches <1 day). Requires: good test suite, feature flag system (LaunchDarkly, Azure Feature Management), automated deployment. Reality: most teams use something between GitHub Flow and GitFlow. Common CIAM pattern: main (prod) + environment branches (dev, staging) that pipelines auto-deploy to + feature branches from main. Merging: feature → main (PR) → automated promote to dev → manual promote to staging → manual promote to prod.

CIAM branching strategy: GitHub Flow with environment promotion: main branch protected (PR + CI required). ADO pipeline: merge to main → deploy to dev automatically. Release to staging: manual trigger in ADO pipeline → same image, different K8s namespace + config. Release to prod: another manual trigger (requires sign-off). Branch naming: feature/ciam-entra-provisioning, fix/ping-token-expiry-race, chore/upgrade-spring-boot-3.3. PR rules: title must follow Conventional Commits (feat:, fix:, chore:), squash-merge into main (clean linear history), ADO work item linked. Hotfix flow: branch directly from the commit tagged as the current prod deployment, fix, PR to main, cherry-pick or redeploy. Long-lived branches to avoid: don't maintain separate dev/staging/`prod branches that diverge — use the same branch (main) deployed with different configs. Branch divergence = painful merges = risk of prod incidents.

1 — Three Strategies

main
develop
feature/*
release/*
hotfix/*
GitFlow uses two long-lived branches: main (always production-ready, tagged for releases) and develop (integration branch for features).

feature/* branches from develop, merged back to develop when done.
release/* branches from develop when ready to release, merged to main + tagged + merged back to develop.
hotfix/* branches from main for emergency production fixes, merged to main + tagged + merged back to develop.

Best for: teams with scheduled releases (quarterly, monthly). Complex but explicit.
main (always deployable)
feature branches (short-lived)
GitHub Flow is radically simpler: one long-lived branch (main, always deployable) and short-lived feature branches.

Workflow: branch from main → commit → open PR → review → merge to main → deploy immediately.

No develop branch. No release branch. Every merge to main is a production deployment (or triggers one via CI/CD).

Best for: teams that deploy continuously. Requires good CI/CD and feature flags for incomplete work.
main/trunk (the only long-lived branch)
short-lived feature branches (≤ 2 days)
Trunk-Based Development: all developers commit to one branch (main/trunk), directly or via very short-lived feature branches (max 1–2 days).

Feature flags decouple deployment from release. Incomplete features are deployed but hidden behind a flag. When ready, enable the flag without a deploy.

Requires: solid CI/CD (every commit runs tests), high test coverage, feature flag infrastructure.

Best for: experienced teams with mature CI/CD. Google, Facebook, and Netflix use this model.

3 — Common Branch Commands

git checkout -b feature/user-auth # create + switch to new branch git branch # list all local branches git branch -a # list local + remote branches git push -u origin feature/user-auth # push and track remote git checkout main && git pull # update main before merging git merge feature/user-auth # merge feature into current branch git branch -d feature/user-auth # delete local branch (after merge) git push origin --delete feature/user-auth # delete remote branch
