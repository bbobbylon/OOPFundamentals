VMs vs Containers

What Docker actually is, why containers beat VMs for app delivery, and the core concepts every developer needs.

What is Docker — and why did containers replace VMs for application delivery?

Before Docker, deploying a Java application meant: install the JDK on the server, configure environment variables, install dependencies, configure the OS — and hope the server matches your dev machine. "Works on my machine" was the universal frustration. Docker solves this with containers: a way to package your application AND all its dependencies (JRE, libraries, config files) into a single portable unit that runs identically everywhere. VMs vs containers: a Virtual Machine virtualizes the entire hardware, running a full OS kernel per VM — heavy (GB of disk, minutes to start, hundreds of MB RAM overhead). A container shares the host OS kernel — it's just an isolated process with its own filesystem, network, and PID namespace. No separate OS, no hypervisor. A container starts in milliseconds, uses ~10-50 MB overhead vs a VM's 500 MB+. Docker image: a read-only blueprint for a container. Built layer by layer — each Dockerfile instruction adds a layer. Layers are cached: if you change only your app code (line 10 of the Dockerfile) and layers 1-9 (base OS, dependencies) are unchanged, Docker reuses the cached layers. Docker container: a running instance of an image. Images are like Java classes; containers are like Java objects. You can run 5 containers from the same image. Docker Hub / registry: a repository of images. docker pull eclipse-temurin:21-jre-alpine downloads the official Java 21 JRE image. Your company runs a private registry (AWS ECR, Azure Container Registry, Harbor) for internal images. Docker daemon: the background process (dockerd) that manages images and containers. Docker CLI sends commands to the daemon via a Unix socket. The daemon talks to registries to push/pull images.

VM vs container

Virtual Machine: hypervisor (VMware/Hyper-V/KVM) → Guest OS (full Linux/Windows kernel) → App. Each VM: 500MB-2GB RAM for OS alone, 30-120s startup, 10-50 GB disk per VM. Container: host OS kernel → Docker → isolated processes using kernel namespaces + cgroups. Each container: 10-50 MB overhead, 100ms-2s startup, 10-200 MB image. What containers actually are: Linux namespaces (pid, net, mnt, uts, ipc, user) + cgroups (limit CPU/memory/IO) + a read-only layered filesystem (OverlayFS). The container "thinks" it has its own filesystem and network — it's actually using kernel features for isolation. No virtualization, no hypervisor. Docker on Windows/Mac runs a lightweight Linux VM because containers need a Linux kernel — Docker Desktop manages this transparently.

Layers + caching

# Image layers (each instruction = a layer): FROM eclipse-temurin:21-jre-alpine # Layer 1: ~190MB WORKDIR /app # Layer 2: tiny COPY target/app.jar app.jar # Layer 3: ~50MB EXPOSE 8080 # metadata ENTRYPOINT ["java","-jar","app.jar"] # metadata # docker build -t myapp:1.0 . # Step 1/5: FROM eclipse-temurin... # CACHED (already pulled) ← no re-download # Step 2/5: WORKDIR /app # CACHED ← no re-run # Step 3/5: COPY target/app.jar # [changed file] ← RE-BUILD # Step 4/5, 5/5: EXPOSE / ENTRYPOINT # RE-BUILD (everything after change) # BAD: COPY pom.xml + src + mvn = no layer caching # GOOD: COPY pom.xml → mvn deps → COPY src → compile

Docker in your CIAM stack: Your CIAM Spring Boot application runs in a Docker container in production. The image contains: JRE 21 (base layer, ~190 MB), Spring Boot fat JAR with all dependencies (your app layer, ~50 MB). ADO CI pipeline: mvn package → docker build -t myregistry.azurecr.io/ciam-auth:$(Build.BuildId) . → docker push → Kubernetes pulls this image and runs it. The container reads Ping client secrets from Kubernetes Secrets (mounted as env vars). CIAM Ping Identity server itself runs in a Docker container (official Ping Docker images on Docker Hub). Docker Compose for local dev: one YAML file spins up ciam-auth + postgres + redis — no manual database install. When you docker-compose up, all three start in the right order with the right networking.

1 — The Problem Docker Solves

😱 "It works on my machine!"

Developer runs app on Windows with Java 21. CI server runs on Ubuntu with Java 17. Production runs on RHEL with Java 21 but different library versions. App behaves differently everywhere. Hours lost debugging environment differences.

Docker's answer: package the app and all its dependencies — the runtime, the libraries, the config — into a single image. Run that image anywhere Docker is installed and it behaves identically.

The image becomes the unit of deployment. Not a JAR file that assumes Java is installed. Not a ZIP with a README about prerequisites. A complete, self-contained runtime.

3 — Images vs Containers

Image (the blueprint)

A read-only, layered snapshot. Like a class in OOP — it defines what a container will look like. Stored in a registry (Docker Hub, ECR, etc.). Created by docker build.

Container (the running instance)

A running process created from an image. Like an object from a class — the same image can run as 1 or 100 containers simultaneously. Created by docker run.

Image layers — each instruction in a Dockerfile creates a new layer. Unchanged layers are cached:

Layer 1: eclipse-temurin:21-jre-alpine
Base OS + Java Runtime · 190MB · pulled from Docker Hub · CACHED after first pull
Layer 2: WORKDIR /app
Sets working directory · tiny · CACHED unless Dockerfile changes
Layer 3: COPY target/app.jar app.jar
Your application JAR · 20-60MB · RE-BUILT only when source changes
ℹ️ Layers below unchanged layers are reused from cache. This is why you put slow steps (dependencies) early and fast-changing steps (source code) last in your Dockerfile.
