VMs vs Containers

What Docker actually is, why containers beat VMs for app delivery, and the core concepts every developer needs.

🐳 What is Docker — and why did containers replace VMs for application delivery?

Before Docker, deploying meant installing the JDK, deps and config on each server and hoping it matched dev — "works on my machine." Docker packages your app + all its dependencies into a portable container. Unlike a VM (a full guest OS per instance, GB of disk, slow boot), a container shares the host kernel — just an isolated process (namespaces + cgroups + a layered filesystem), ~10-50MB overhead, millisecond start. An image is a read-only layered blueprint (cached layer by layer); a container is a running instance (image:container :: class:object), and you can run many from one image. A registry (Docker Hub, ECR, ACR) stores images, and the daemon (dockerd) builds and runs them.

  • Solves "works on my machine" — app + deps packaged together.
  • Container shares the host kernel — namespaces + cgroups, not a full VM.
  • Image = read-only layered blueprint; container = running instance (class:object).
  • Registry stores images; the dockerd daemon builds and runs them.

VM vs container

Virtual Machine: hypervisor (VMware/Hyper-V/KVM) → Guest OS (full Linux/Windows kernel) → App. Each VM: 500MB-2GB RAM for OS alone, 30-120s startup, 10-50 GB disk per VM. Container: host OS kernel → Docker → isolated processes using kernel namespaces + cgroups. Each container: 10-50 MB overhead, 100ms-2s startup, 10-200 MB image. What containers actually are: Linux namespaces (pid, net, mnt, uts, ipc, user) + cgroups (limit CPU/memory/IO) + a read-only layered filesystem (OverlayFS). The container "thinks" it has its own filesystem and network — it's actually using kernel features for isolation. No virtualization, no hypervisor. Docker on Windows/Mac runs a lightweight Linux VM because containers need a Linux kernel — Docker Desktop manages this transparently.

1 — The Problem Docker Solves

😱 "It works on my machine!"

Developer runs app on Windows with Java 21. CI server runs on Ubuntu with Java 17. Production runs on RHEL with Java 21 but different library versions. App behaves differently everywhere. Hours lost debugging environment differences.

Docker's answer: package the app and all its dependencies — the runtime, the libraries, the config — into a single image. Run that image anywhere Docker is installed and it behaves identically.

The image becomes the unit of deployment. Not a JAR file that assumes Java is installed. Not a ZIP with a README about prerequisites. A complete, self-contained runtime.

3 — Images vs Containers

Image (the blueprint)

A read-only, layered snapshot. Like a class in OOP — it defines what a container will look like. Stored in a registry (Docker Hub, ECR, etc.). Created by docker build.

Container (the running instance)

A running process created from an image. Like an object from a class — the same image can run as 1 or 100 containers simultaneously. Created by docker run.

Image layers — each instruction in a Dockerfile creates a new layer. Unchanged layers are cached:

Layer 1: eclipse-temurin:21-jre-alpine
Base OS + Java Runtime · 190MB · pulled from Docker Hub · CACHED after first pull
Layer 2: WORKDIR /app
Sets working directory · tiny · CACHED unless Dockerfile changes
Layer 3: COPY target/app.jar app.jar
Your application JAR · 20-60MB · RE-BUILT only when source changes
ℹ️ Layers below unchanged layers are reused from cache. This is why you put slow steps (dependencies) early and fast-changing steps (source code) last in your Dockerfile.
