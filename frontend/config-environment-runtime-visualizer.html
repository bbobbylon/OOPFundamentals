Environment & Runtime Config

⚙️ What is environment and runtime config in Angular — and when should a value be baked into the build vs loaded at startup?

Angular applications need configuration: API base URLs, feature flags, OAuth issuer URLs, tenant IDs. The critical question is when the value is injected — at build time (baked into the JavaScript bundle) or at runtime (loaded via HTTP at startup, before the app renders). Build-time configuration: uses Angular's environment files (src/environments/environment.ts replaced by environment.prod.ts at build via angular.json file replacements). The value is a compile-time constant inside the JavaScript bundle. Pros: zero extra HTTP request, instantly available. Cons: every environment needs a separate build — you can't use one binary across dev/staging/prod. Runtime configuration: the built app fetches a config file (e.g., assets/config.json from a URL or environment-specific path) during startup, before the root component renders. Uses APP_INITIALIZER to block rendering until the fetch completes. Pros: ONE build artifact can be deployed to dev/staging/prod by pointing it at different config endpoints. Cons: one extra HTTP request on startup, config loading can fail. Recommendation for CIAM: use runtime config for environment-specific values that change per deployment (API URL, Ping issuer URL, feature flags). This enables the "build once, deploy many" pattern: the CI pipeline builds the Angular app once, and the Kubernetes/ECS deployment injects the config via environment-specific ConfigMaps/Secrets or a /api/config endpoint. Build-time constants are fine for values that truly never change per environment (copyright year, app version). InjectionToken: whether build-time or runtime, expose config via InjectionTokens rather than importing environment.ts directly — makes testing and code reuse much easier.

Build-time env files

// src/environments/environment.ts (dev): export const environment = { production: false, apiUrl: 'http://localhost:8080', pingIssuer: 'https://ping-dev.myco.com', pingClientId: 'dev-ciam-spa' }; // src/environments/environment.prod.ts: export const environment = { production: true, apiUrl: 'https://api.myco.com', pingIssuer: 'https://ping.myco.com', pingClientId: 'prod-ciam-spa' }; // angular.json swaps at build: // ng build --configuration production // → environment.prod.ts replaces environment.ts // ⚠️ Problem: separate build per env // If prod build is bad, staging build doesn't help // "Build once, deploy everywhere" → use runtime config

Runtime config (APP_INITIALIZER)

// src/app/core/config.service.ts @Injectable({ providedIn: 'root' }) export class ConfigService { private config: AppConfig | null = null; constructor(private http: HttpClient) {} load(): Promise<void> { return firstValueFrom( this.http.get<AppConfig>('/assets/config.json').pipe( tap(cfg => this.config = cfg) ) ); } get apiUrl(): string { return this.config!.apiUrl; } } // app.config.ts: { provide: APP_INITIALIZER, useFactory: (cfg: ConfigService) => () => cfg.load(), deps: [ConfigService], multi: true } // App renders ONLY after config is loaded // config.json served by nginx or fetched from /api/config

InjectionToken (type-safe config)

// Define a typed token: export interface AppConfig { apiUrl: string; pingIssuer: string; pingClientId: string; featureFlags: { mfaEnabled: boolean }; } export const APP_CONFIG = new InjectionToken<AppConfig>('APP_CONFIG'); // Register (either build-time or runtime): { provide: APP_CONFIG, useFactory: (cfg: ConfigService) => cfg.getConfig(), deps: [ConfigService] } // Consume anywhere (functional injection): @Injectable({ providedIn: 'root' }) export class PingAuthService { private config = inject(APP_CONFIG); buildAuthUrl(): string { return `${this.config.pingIssuer}/as/authorization.oauth2`; } } // Testing: TestBed.configureTestingModule({ providers: [{ provide: APP_CONFIG, useValue: testConfig }] });

In CIAM / Context: The CIAM Angular app uses runtime config: one build artifact, /assets/config.json served by nginx/S3 per environment. The config contains Ping issuer URL, API base URL, and feature flags. APP_INITIALIZER loads it before any component renders. The ConfigService exposes an InjectionToken so services can inject APP_CONFIG rather than importing environment.ts — making unit tests clean (inject testConfig, no mocking of imports).

Two families of configuration: build-time vs runtime

Angular projects can inject configuration at two distinct points. Choosing the right one matters for deployment flexibility, CI/CD pipelines, and security.

Build-time configuration

Values are baked into the JavaScript bundle during ng build. The bundle contains the values — you cannot change them without rebuilding.

  • Mechanism: environment.ts + fileReplacements in angular.json
  • Best for: flags that differ by environment (API URLs that are fixed per deployment, feature flags, log levels)
  • Not for: secrets (they end up in the bundle), values that change at deploy time

Runtime configuration

Values are loaded from a separate file or API after the browser downloads the app but before any component renders.

  • Mechanism: APP_INITIALIZER + HttpClient fetch of config.json
  • Best for: values that differ per deployment environment without a rebuild (multi-tenant, Docker env vars, ops-controlled)
  • Not for: secrets (still in the browser), truly large configs (adds load time)

Animated flow: the startup sequence

1

Browser downloads main bundle (JS)

Contains your app code. If using build-time config, the environment.prod.ts values are already inlined here.

2

bootstrapApplication() runs APP_INITIALIZERs

Angular waits for every APP_INITIALIZER to complete before rendering anything. Runtime config loading happens here.

3

App renders — config is ready

By the time the first component template runs, both build-time and runtime config values are available.

4

Components inject config via inject(TOKEN)

Components and services use inject(ENVIRONMENT) or inject(ConfigService) to read values — fully typed.

The golden rule: use build-time config for things that are set by developers at deploy time and don't change between deployments. Use runtime config for things that operations teams configure per-environment without rebuilding.

Build-time configuration — environment.ts + fileReplacements

The classic Angular pattern. Two (or more) environment files, swapped at build time by the Angular CLI.

The two files

src/environments/environment.ts (development)
// Default — used by ng serve / ng build (no config)
export const environment = {
  production: false,
  apiUrl: 'http://localhost:3000/api',
  featureFlags: {
    darkMode: true,
    betaEditor: true,
  },
  logLevel: 'debug',
};
src/environments/environment.prod.ts (production)
// Used when --configuration production
export const environment = {
  production: true,
  apiUrl: 'https://api.myapp.com',
  featureFlags: {
    darkMode: true,
    betaEditor: false,
  },
  logLevel: 'error',
};

How fileReplacements works in angular.json

// angular.json — inside projects.my-app.architect.build
{
  "configurations": {
    "production": {
      "fileReplacements": [
        {
          "replace": "src/environments/environment.ts",
          "with":    "src/environments/environment.prod.ts"
        }
      ],
      "optimization": true,
      "outputHashing": "all"
    },
    "staging": {
      "fileReplacements": [
        {
          "replace": "src/environments/environment.ts",
          "with":    "src/environments/environment.staging.ts"
        }
      ]
    }
  }
}
What fileReplacements does: when building with --configuration production, esbuild (or webpack) simply resolves every import of ./environments/environment to environment.prod.ts instead. The original file never gets bundled. The result: different values baked in based on build target.

Simulating the build swap

Using the environment in code

// Any service or component — just import
import { environment } from '../environments/environment';

@Injectable({ providedIn: 'root' })
export class ApiService {
  private base = environment.apiUrl;           // inlined at build time

  getUsers() {
    return this.http.get<User[]>(`${this.base}/users`);
  }
}

// Feature flag usage
@Component({
  template: `@if (betaEditorEnabled) { <beta-editor/> }`
})
export class EditorPage {
  betaEditorEnabled = environment.featureFlags.betaEditor;
}
Critical limitation: the values are baked into the JS bundle. A bad API URL requires a new build and deploy. If you ship containers and want the API URL to come from a Kubernetes ConfigMap or Docker environment variable, you cannot use this pattern — you need runtime config.

Runtime configuration — APP_INITIALIZER + config.json

Load a JSON file before the app renders. The ops team can change the JSON file on the server without rebuilding the Angular app.

The files involved

public/config.json (deployed separately, NOT bundled)
{
  "apiUrl": "https://api.myapp.com",
  "authDomain": "auth.myapp.com",
  "maxUploadMb": 50,
  "featureFlags": {
    "darkMode": true,
    "analyticsEnabled": false
  }
}
config.service.ts
import { Injectable } from '@angular/core';
import { HttpClient } from '@angular/common/http';
import { firstValueFrom } from 'rxjs';

interface AppConfig {
  apiUrl: string;
  authDomain: string;
  maxUploadMb: number;
  featureFlags: { darkMode: boolean; analyticsEnabled: boolean; };
}

@Injectable({ providedIn: 'root' })
export class ConfigService {
  private config!: AppConfig;

  load(): Promise<void> {
    return firstValueFrom(
      this.http.get<AppConfig>('/config.json')
    ).then(cfg => { this.config = cfg; });
  }

  get<K extends keyof AppConfig>(key: K): AppConfig[K] {
    return this.config[key];
  }

  constructor(private http: HttpClient) {}
}
app.config.ts — register the initializer
import { ApplicationConfig, APP_INITIALIZER } from '@angular/core';
import { provideHttpClient } from '@angular/common/http';
import { ConfigService } from './config.service';

export const appConfig: ApplicationConfig = {
  providers: [
    provideHttpClient(),
    {
      provide: APP_INITIALIZER,
      useFactory: (cs: ConfigService) => () => cs.load(),
      deps: [ConfigService],
      multi: true   // required — allows multiple initializers
    }
  ]
};

Using the config in components

import { inject } from '@angular/core';
import { ConfigService } from './config.service';

@Component({ /* ... */ })
export class UploadComponent {
  private config = inject(ConfigService);

  maxFileSizeMb = this.config.get('maxUploadMb');   // typed: number
  apiBase       = this.config.get('apiUrl');          // typed: string

  // By the time this component exists, APP_INITIALIZER has run,
  // so config is guaranteed to be populated.
}

Alternative: using fetch() without HttpClient

If you want to avoid the HttpClient dependency for just the config load (simpler), use the browser's native fetch() directly in the initializer factory.

// Without ConfigService — inline in app.config.ts
let _config: AppConfig;

{
  provide: APP_INITIALIZER,
  useFactory: () => () =>
    fetch('/config.json')
      .then(r => r.json())
      .then(cfg => { _config = cfg; }),
  multi: true
},
{ provide: APP_CONFIG, useFactory: () => _config }

ENVIRONMENT InjectionToken pattern

Instead of importing the environment object directly, wrap it in an InjectionToken. This makes components testable (you can provide different values in tests) and avoids direct file coupling.

environment.token.ts — define the token
import { InjectionToken } from '@angular/core';
import { environment } from './environment';

// Define a TypeScript interface for the shape
export interface Environment {
  production: boolean;
  apiUrl: string;
  logLevel: 'debug' | 'info' | 'error';
}

// Create the token — the type parameter provides compile-time safety
export const ENVIRONMENT = new InjectionToken<Environment>(
  'environment',
  {
    providedIn: 'root',
    factory: () => environment   // default factory — uses the imported environment
  }
);
In a component or service
import { inject } from '@angular/core';
import { ENVIRONMENT } from './environment.token';

@Component({ /* ... */ })
export class ApiService {
  private env = inject(ENVIRONMENT);    // typed as Environment

  getUsers() {
    return this.http.get(`${this.env.apiUrl}/users`);
  }
}
In tests — override the token
TestBed.configureTestingModule({
  providers: [
    {
      provide: ENVIRONMENT,
      useValue: {
        production: false,
        apiUrl: 'http://localhost:3000',
        logLevel: 'debug',
      } satisfies Environment   // TypeScript ensures the shape matches
    }
  ]
});
Why this is better than direct import: components that import environment directly are untestable without mocking the module. With an InjectionToken, tests provide any value they need via the DI system — no module mocking required.

Combining build-time + runtime with the token pattern

// You can merge both: start with environment.ts (build-time),
// then override with runtime values in APP_INITIALIZER.

@Injectable({ providedIn: 'root' })
export class ConfigService {
  private config = inject(ENVIRONMENT);  // starts with build-time values

  load(): Promise<void> {
    return fetch('/config.json')
      .then(r => r.json())
      .then(override => {
        // Deep merge: runtime values override build-time defaults
        Object.assign(this.config, override);
      });
  }
}

Full ConfigService pattern — typed runtime config

A production-grade pattern combining runtime loading, type safety, nested key access, and a fallback to build-time defaults.

app-config.interface.ts — strong typing
export interface AppConfig {
  api: {
    baseUrl: string;
    timeout: number;
    retries: number;
  };
  auth: {
    domain: string;
    clientId: string;
    audience: string;
  };
  features: Record<string, boolean>;
  logging: {
    level: 'debug' | 'info' | 'warn' | 'error';
    endpoint?: string;
  };
}

export const DEFAULT_CONFIG: AppConfig = {
  api: { baseUrl: '/api', timeout: 30000, retries: 3 },
  auth: { domain: '', clientId: '', audience: '' },
  features: {},
  logging: { level: 'info' },
};
config.service.ts — full implementation
@Injectable({ providedIn: 'root' })
export class ConfigService {
  private config: AppConfig = { ...DEFAULT_CONFIG };
  private loaded = false;
  private http = inject(HttpClient);

  load(): Promise<void> {
    return firstValueFrom(
      this.http.get<Partial<AppConfig>>('/config.json').pipe(
        catchError(() => of({}))  // falls back to defaults if file missing
      )
    ).then(partial => {
      // Deep merge runtime config over defaults
      this.config = this.deepMerge(DEFAULT_CONFIG, partial);
      this.loaded = true;
    });
  }

  // Typed path access: config.get('api.baseUrl') → string
  get(path: string): unknown {
    return path.split('.').reduce((o: any, k) => o?.[k], this.config);
  }

  getSection<K extends keyof AppConfig>(key: K): AppConfig[K] {
    return this.config[key];
  }

  isFeatureEnabled(flag: string): boolean {
    return this.config.features[flag] ?? false;
  }

  private deepMerge(base: any, override: any): any {
    const result = { ...base };
    for (const key of Object.keys(override)) {
      result[key] = (typeof override[key] === 'object' && !Array.isArray(override[key]))
        ? this.deepMerge(base[key] ?? {}, override[key])
        : override[key];
    }
    return result;
  }
}

Strategy When set Who controls it Requires rebuild Suitable for
environment.ts + fileReplacements Build time (ng build) Developer / CI pipeline Yes Per-environment API URLs, feature flags set at deploy time

window.__env__ — server-side injection pattern

<!-- index.html — server writes env vars here before sending the response -->
<script>
  window.__env__ = {
    API_URL: 'https://api-prod.myapp.com',  // ← injected by Node.js/Nginx
    AUTH_DOMAIN: 'auth.myapp.com'
  };
</script>
<script src="main.js"></script>
// Angular — read from window at runtime
export const APP_CONFIG = new InjectionToken<AppConfig>('appConfig', {
  providedIn: 'root',
  factory: () => (window as any).__env__ ?? DEFAULT_CONFIG
});
window.__env__ caveat: window.__env__ is not available during SSR (server-side rendering). If you use Angular SSR, use APP_INITIALIZER with HttpClient instead — it works in both browser and server contexts.

Yes — use window.__env__ injected into index.html. Zero extra HTTP request.
No — continue to Q3.
