Comparable vs Comparator

Sorting objects in Java — natural order, custom order, Comparator chains, TreeMap, PriorityQueue, and the overflow gotcha.

↕️ What is the difference between Comparable and Comparator — and when do you use each?

Comparable defines a class's natural order — the class implements compareTo, and Collections.sort, TreeSet, TreeMap, and PriorityQueue use it. Comparator is an external, pluggable ordering for when you need several sort orders or can't modify the class (Comparator.comparing(User::getEmail)). Both return negative/zero/positive for before/equal/after — but write Integer.compare(a, b), never a - b (it overflows), and keep compareTo consistent with equals or TreeSet will silently drop "equal" elements.

  • Comparable = natural order on the class; Comparator = external, swappable order.
  • Sorted collections rely on it — TreeSet/TreeMap/PriorityQueue.
  • Never a - b — it overflows; use Integer.compare(a, b).
  • Keep compareTo consistent with equals or TreeSet treats unequal items as duplicates.

Comparator chaining (Java 8+)

Comparator.comparing(User::getLastName).thenComparing(User::getFirstName).thenComparing(User::getId). Sort by lastName, then firstName for ties, then id for further ties. Reverse: .reversed(). Null handling: Comparator.nullsFirst(Comparator.naturalOrder()) — nulls sort before non-nulls. nullsLast() — nulls sort after. Primitive comparators: Comparator.comparingInt(User::getAge), comparingLong, comparingDouble — avoid boxing. Natural order: Comparator.naturalOrder() (requires Comparable). Reverse natural: Comparator.reverseOrder().

TreeMap, PriorityQueue & sorted collections

TreeMap<User, Value>: keys sorted by User's compareTo (or provide a Comparator to constructor). new TreeMap<>(Comparator.comparing(User::getName)). PriorityQueue<Task>: always dequeues the smallest element (min-heap). new PriorityQueue<>(Comparator.comparingInt(Task::getPriority).reversed()) for max-priority-first. TreeSet<User>: sorted set — elements sorted by Comparable/Comparator. Warning: if two elements compare as equal (compareTo returns 0), TreeSet treats them as the same element and won't add the second — even if equals() says they're different.

Sorted streams

users.stream().sorted(Comparator.comparing(User::getLastName).thenComparing(User::getFirstName)).toList(). Stream's sorted() uses TimSort — stable (preserves relative order of equal elements), O(n log n). min(comparator) / max(comparator): find extremes. Collections.sort(list, comparator): sort in place. list.sort(comparator): instance method, same thing. Arrays.sort(array, comparator): for arrays. Records implement Comparable using their canonical constructor parameters if you add implements Comparable<User>.

CIAM / Spring Boot: User search results sort consistently with sorted(Comparator.comparing(UserDto::getDisplayName, String.CASE_INSENSITIVE_ORDER)); a real-time dashboard uses a PriorityQueue<AuditEntry> by timestamp; role precedence is roles.stream().min(Comparator.comparingInt(Role::getPrecedenceLevel)).orElseThrow(); and Spring Batch reads via a sorted cursor for deterministic order.

Why you can't just call Collections.sort() on custom objects

// You have a list of Employee objects: List<Employee> staff = List.of( new Employee("Zara", "Engineering", 95000), new Employee("Alice", "Marketing", 72000), new Employee("Bob", "Engineering", 88000) ); // This compiles, but throws at runtime! Collections.sort(staff); // ClassCastException: Employee cannot be cast to Comparable // Java doesn't know HOW to compare Employee objects. // Should it sort by name? Salary? Department? Age? // YOU must tell it — via Comparable or Comparator.
Two solutions:
1. Comparable<T> — implement it inside the Employee class itself. Defines the natural order. You need to own/modify the class.
2. Comparator<T> — define ordering logic outside the class. Pass it to sort methods. Doesn't require touching the original class. Can have as many comparators as you want.

The sorting contract — what sort() actually does

// Java's sort algorithms (TimSort) only need one thing from you: // a way to determine if object A is less than, equal to, or greater than object B. // This is expressed as an integer: int result = compare(a, b); // result < 0 → a comes before b (a is "less than" b) // result == 0 → a and b are equal in this ordering // result > 0 → a comes after b (a is "greater than" b) // Convention: return -1, 0, or 1 — but any negative/zero/positive works. // TimSort is stable: elements with result==0 keep their original relative order.

Implementing Comparable<T> — the natural order

public class Employee implements Comparable<Employee> { private final String name; private final String department; private final double salary; // constructor, getters omitted for brevity @Override public int compareTo(Employee other) { // Natural order: sort alphabetically by name return this.name.compareTo(other.name); // String.compareTo() itself implements Comparable, so we delegate to it } } // Now Collections.sort() works without any extra arguments: Collections.sort(staff); // sorts by name A→Z (natural order) staff.sort(Comparator.naturalOrder()); // same thing, explicit

The three-part contract Comparable must honour

1. Antisymmetry
// If a.compareTo(b) < 0 // then b.compareTo(a) > 0 // (flip the pair, flip the sign) a.compareTo(b) == -b.compareTo(a) // as a sign: sgn(a.compareTo(b)) == -sgn(b.compareTo(a))
2. Transitivity
// If a < b and b < c, then a < c // Java's sort algorithms DEPEND on this. // Violating it causes unpredictable, non-reproducible sort order.
3. Totality
// For every pair (a, b), compareTo must return a result. // Can't throw for some pairs but not others. // a.compareTo(a) must equal 0 (reflexive).
Consistency with equals() — highly recommended
// "Strongly recommended" by the Java docs: // a.compareTo(b) == 0 ⟺ a.equals(b) // If you violate this, TreeSet and TreeMap behave // strangely because they use compareTo() for equality, // not equals(). TreeSet<BigDecimal> set = new TreeSet<>(); set.add(new BigDecimal("1.0")); set.add(new BigDecimal("1.00")); // size() == 1 ← compareTo() treats them equal (same numeric value) // but equals() would say they're different (different scale) // This is BigDecimal's famous inconsistency!
Multi-field natural order
@Override public int compareTo(Employee other) { // Primary: department int c = this.department.compareTo(other.department); if (c != 0) return c; // Tiebreak: name return this.name.compareTo(other.name); }

Implementing Comparator<T> — separate ordering logic

Anonymous class (pre-Java 8)
Comparator<Employee> bySalary = new Comparator<Employee>() { @Override public int compare(Employee a, Employee b) { return Double.compare(a.getSalary(), b.getSalary()); } };
Lambda (Java 8+)
Comparator<Employee> bySalary = (a, b) -> Double.compare(a.getSalary(), b.getSalary()); // Even cleaner with Comparator.comparing(): Comparator<Employee> bySalary = Comparator.comparingDouble(Employee::getSalary);
Comparator.comparing(keyExtractor) — pass a method reference or lambda that extracts a Comparable key (like a String or int). Java infers the rest. This is by far the most readable style for modern Java.

Comparator factory methods — the full toolkit

// Comparator.comparing() — extract a Comparable key Comparator<Employee> byName = Comparator.comparing(Employee::getName); Comparator<Employee> byDept = Comparator.comparing(Employee::getDepartment); // Comparator.comparingInt / comparingLong / comparingDouble — avoid boxing Comparator<Employee> bySal = Comparator.comparingDouble(Employee::getSalary); Comparator<String> byLen = Comparator.comparingInt(String::length); // .reversed() — flip the order Comparator<Employee> salDesc = bySal.reversed(); // .thenComparing() — tiebreaker Comparator<Employee> byDeptThenSal = byDept.thenComparing(bySal); // .nullsFirst() / .nullsLast() — handle nulls without NPE Comparator<Employee> nullSafe = Comparator.nullsLast(Comparator.comparing(Employee::getName)); // Comparator.naturalOrder() / reverseOrder() Comparator<String> aToZ = Comparator.naturalOrder(); Comparator<String> zToA = Comparator.reverseOrder();

Multi-key sort — chaining thenComparing()

// Sort employees: by department A→Z, then by salary high→low, then by name A→Z Comparator<Employee> multiSort = Comparator.comparing(Employee::getDepartment) // primary .thenComparingDouble(Employee::getSalary).reversed() // secondary (desc) .thenComparing(Employee::getName); // tertiary // Wait — .reversed() flips ALL keys built so far, not just the last one! // Better to wrap just the salary part: Comparator<Employee> multiSort = Comparator.comparing(Employee::getDepartment) .thenComparing( Comparator.comparingDouble(Employee::getSalary).reversed() ) .thenComparing(Employee::getName);
Caution: .reversed() on a chained comparator reverses the entire chain built so far, not just the last key. If you want salary descending but keep other keys ascending, wrap the salary comparator separately before passing it to .thenComparing().

Sorting with Streams — .sorted()

// Stream.sorted() with no args requires elements to implement Comparable List<String> sorted = names.stream() .sorted() // natural order (String is Comparable) .collect(Collectors.toList()); // Stream.sorted(Comparator) — explicit ordering List<Employee> result = staff.stream() .sorted(Comparator.comparing(Employee::getDepartment) .thenComparingDouble(Employee::getSalary) .reversed()) .collect(Collectors.toList()); // Inline — perfectly valid for one-off sorts staff.stream() .sorted((a, b) -> a.getName().compareToIgnoreCase(b.getName())) .forEach(System.out::println);

TreeMap and TreeSet — sorted by Comparator, not insertion order

// TreeMap keeps keys sorted. Default: natural order (keys must be Comparable) TreeMap<String, Integer> scores = new TreeMap<>(); // alphabetical by key scores.put("Zara", 95); scores.put("Alice", 72); scores.put("Bob", 88); // Iteration order: Alice, Bob, Zara — not insertion order // TreeMap with custom Comparator — e.g. reverse alphabetical: TreeMap<String, Integer> reversed = new TreeMap<>(Comparator.reverseOrder()); reversed.put("Zara", 95); // iteration: Zara, Bob, Alice // TreeSet — same idea, just keys (like a sorted Set) TreeSet<Employee> byName = new TreeSet<>(Comparator.comparing(Employee::getName)); byName.add(new Employee("Zara", ...)); byName.add(new Employee("Alice", ...)); // Always sorted: Alice → ... → Zara // TreeMap navigation methods — very useful! scores.firstKey() // "Alice" scores.lastKey() // "Zara" scores.headMap("C") // keys < "C" : {Alice} scores.tailMap("C") // keys >= "C" : {Zara} scores.subMap("A", "D") // keys in ["A","D") scores.floorKey("Bo") // greatest key <= "Bo" : "Bob" → wait, <= "Bo" = "Alice"
Key rule: TreeMap/TreeSet use compareTo() (or your Comparator's compare()) to determine equality — not equals(). Two objects that compare as equal will be treated as the same key, even if equals() says they're different.

PriorityQueue — heap ordering with Comparator

// Default PriorityQueue: natural order, min-heap (smallest first) PriorityQueue<Integer> minHeap = new PriorityQueue<>(); minHeap.offer(30); minHeap.offer(10); minHeap.offer(20); minHeap.poll(); // 10 — smallest // Max-heap: reverse order PriorityQueue<Integer> maxHeap = new PriorityQueue<>(Comparator.reverseOrder()); maxHeap.offer(30); maxHeap.offer(10); maxHeap.offer(20); maxHeap.poll(); // 30 — largest // Custom PQ — e.g. highest salary first PriorityQueue<Employee> topEarners = new PriorityQueue<>( Comparator.comparingDouble(Employee::getSalary).reversed() ); topEarners.offer(alice); topEarners.offer(bob); topEarners.offer(carol); topEarners.poll().getName(); // carol — highest salary

The integer overflow gotcha — NEVER use subtraction

WRONG — subtle overflow bug
Comparator<Integer> broken = (a, b) -> a - b; // DANGER! // Works fine for small values, but: int a = Integer.MIN_VALUE; // -2147483648 int b = 1; a - b; // OVERFLOWS → positive! // The comparator now says MIN_VALUE > 1 // Completely wrong — corrupts sort order
CORRECT — use Integer.compare()
Comparator<Integer> correct = (a, b) -> Integer.compare(a, b); // safe // Or with Comparator.comparingInt: Comparator<Integer> correct2 = Comparator.comparingInt(x -> x); // For doubles: Double.compare(a, b) // For longs: Long.compare(a, b) // For String: a.compareTo(b) — already correct // For booleans: Boolean.compare(a, b)

When to use Comparable vs Comparator

SituationUseWhy
You own the class and there's one obvious "natural" order Comparable Cleanest. Works with TreeSet, TreeMap, Collections.sort() with no extra args.
You need multiple sort orders (by name AND by salary) Comparator Define separate Comparator constants for each. Combine with thenComparing().
Sorting a class you don't own (e.g. third-party API) Comparator Can't modify the source. Pass a Comparator to the sort method.
Sorting in a different context (reverse, case-insensitive) Comparator Comparator.reverseOrder(), String.CASE_INSENSITIVE_ORDER
Value objects like Money, Score, Version Comparable A natural order exists and is unambiguous. Consistent with equals().

Null safety — compareTo() vs nullsFirst/nullsLast

// compareTo() throws NullPointerException if either object is null. // Never pass null to a Comparator unless you've handled it. // Safe: Comparator.nullsFirst / nullsLast wraps any Comparator Comparator<String> safe = Comparator.nullsFirst(Comparator.naturalOrder()); safe.compare(null, "Alice"); // -1 (null sorts before Alice) safe.compare("Alice", null); // +1 safe.compare(null, null); // 0 // With field extractor that might be null: Comparator<Employee> byOptTitle = Comparator.comparing(Employee::getTitle, Comparator.nullsLast(Comparator.naturalOrder()));
