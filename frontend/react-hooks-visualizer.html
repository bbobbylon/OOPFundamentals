React Hooks Deep Dive

useState, useEffect, useRef, useMemo, useCallback — how each hook works under the hood, when to use each, and the rules that make them work.

🪝 What are React Hooks — and why did they replace class components?

Hooks (React 16.8) let function components "hook into" state and lifecycle, retiring class components and their this-binding, logic-sharing, and tangled-lifecycle problems. The core set: useState holds a value and re-renders on change; useEffect runs side effects after render with an optional cleanup, gated by a dependency array; useRef is a mutable {current} box that persists without re-rendering (DOM refs, timers, previous values); useMemo caches an expensive computation; useCallback caches a function reference so memoized children don't re-render. Two rules: only call hooks at the top level (never in loops/conditions), and only from components or other hooks — React matches each call to its state slot by call order.

  • useState re-renders on change; useEffect runs effects + cleanup by deps.
  • useRef persists a mutable box without re-rendering — DOM, timers, prev values.
  • useMemo/useCallback cache a value / a function ref to skip needless work.
  • Rules of hooks — top level only; React pairs each call to its slot by order.

useState internals

// Each useState gets a slot in Fiber's state list function Counter() { // Slot 0: { value: 0, queue: [] } const [count, setCount] = useState(0); // Slot 1: { value: false, queue: [] } const [loading, setLoading] = useState(false); // React knows slot 0 = count, slot 1 = loading // by CALL ORDER — not by variable name // That's why hooks can't be inside if/for: // if (condition) const [x, setX] = useState(0); ← BAD // Call order would change based on condition // Functional update (safe for batched updates): const increment = () => setCount(prev => prev + 1); }

useRef for DOM + mutable values

function SearchInput() { const inputRef = useRef<HTMLInputElement>(null); const searchCount = useRef(0); // mutable counter, no re-render const focusInput = () => { inputRef.current?.focus(); // DOM access } const handleSearch = () => { searchCount.current++; // mutate without re-render console.log('Search #' + searchCount.current); } return <input ref={inputRef} onKeyDown={handleSearch} />; } // Common useRef pattern: store timerId const timerId = useRef<NodeJS.Timeout>(); clearTimeout(timerId.current); timerId.current = setTimeout(() => {}, 300);

useMemo vs useCallback

// useMemo: cache a COMPUTED VALUE const sortedUsers = useMemo( () => [...users].sort((a, b) => a.name.localeCompare(b.name)), [users] // recompute only when users changes ); // useCallback: cache a FUNCTION REFERENCE const handleDelete = useCallback( (userId: number) => { dispatch({ type: 'DELETE', payload: userId }); }, [dispatch] // stable function ref if dispatch is stable ); // Pass handleDelete to a memoised child: // <UserList users={users} onDelete={handleDelete} /> // Without useCallback: new function ref every render // = child's memo check always fails = always re-renders

Angular equivalent: useState ≈ signal(); useEffect ≈ ngOnInit/ngOnDestroy/effect() (the cleanup return = teardown); useRef(DOM) ≈ @ViewChild(..., {read: ElementRef}); useMemo ≈ computed(); useCallback ≈ stable class methods. Key difference: Angular drives change detection via Zone.js/Signals, while React needs an explicit setState to re-render — mutating a plain variable never updates the UI.

or, the hook that "fixes" state one render too late

The problem

You reset a piece of state with a perfectly reasonable-looking useEffect — and for one whole frame, the screen shows you a lie.

The highlighted comment belongs to the WRONG post

A comment thread component keeps const [selectedId, setSelectedId] = useState(null). When the user switches posts, you want the selection to clear, so you write the hook every tutorial teaches you to reach for: useEffect(() => { setSelectedId(null); }, [postId]); — clean, declarative, and it does eventually clear the selection.

But "eventually" is the trap. React already renders and paints the NEW post's comments with the OLD selectedId still attached, because the effect cannot run until AFTER that render is already on screen. For one real frame, comment #4 from post 12 shows highlighted inside post 7's list — and if your render code does comments.find(c => c.id === selectedId).author without a guard, that frame throws instead of just looking wrong.

the effect's dependency array ✓ the state shape itself ✓ the timing of WHEN it runs ⚠

Every line is correct. The bug is entirely about WHEN "correct" arrives.

Reset the state during render, not after it
Track the previous prop value in a plain useState — no ref needed ↓ const [prevPostId, setPrevPostId] = useState(postId); is just a normal state slot, used only as a comparison Compare it WHILE rendering, and call setState right there if it changed ↓ if (postId !== prevPostId) { setPrevPostId(postId); setSelectedId(null); } — yes, calling setState mid-render is allowed for exactly this case And stop reaching for useEffect just to mirror a prop into state
An effect is a message you send after the show already started. useEffect runs after React commits and the browser paints — it exists for things outside React (subscriptions, DOM APIs, logging), not for keeping one piece of state in sync with a prop that's already available during render. When state depends purely on props you already have, computing or resetting it inline isn't a hack — React's own documentation recommends it, because it collapses two renders (and one visibly wrong frame) into one.
A sticky note for the whiteboard: an effect is a text message — it arrives after the fact. If you need the answer before you hang up the phone, say it out loud during the call instead. Setting state during render is saying it during the call; a useEffect reset is the text message that shows up after you've already hung up.
You

But I was always told never to call setState while rendering — isn't that how you get infinite loops?

The React docs

Only if you call it unconditionally. Guard it with a comparison against a value from the previous render — like prevPostId above — and it fires at most once per real prop change, same as an effect, just one render sooner.

You

So is useEffect just... wrong for this?

useEffect

Not wrong — late. I'm for synchronizing with something OUTSIDE React: a WebSocket, document.title, an interval. Resetting a piece of YOUR OWN state because a prop changed doesn't need me at all.

The mechanism

Walk through why the effect version costs you an entire extra render — and why that extra render is visible, not theoretical.

  1. postId changes from 12 to 7 — the parent re-renders this componentrender #1 starts
  2. The component body runs top to bottom; selectedId is still whatever it was under post 12stale state
  3. React commits render #1 to the DOM and the browser paints itframe on screen
  4. The user SEES post 7's comments with post 12's selection still highlighted — this frame is real, not theoreticalvisible bug
  5. Only now does useEffect fire (post-paint) and call setSelectedId(null)effect runs
  6. React schedules and commits render #2 — now it's correct, one full frame later than the user's eyesrender #2

Step 4 is the one to stare at. It isn't a rare race condition — it happens on every single prop change, every time, because "run after commit" is useEffect's entire contract, not an implementation detail you can tune away. The fix in the good card skips straight from step 1 to a corrected step 3 by doing the comparison inline, so there is only ever ONE render, and it's already right.

Render #1 — mismatched postId: 12 → 7 → new comments + OLD selectedId
Paint — stale frame visible browser commits the DOM → wrong highlight, or a crash if unguarded
Render #2 — corrected useEffect fires post-paint → setSelectedId(null), now right

Three states, one avoidable middle one. The "good" fix collapses this into a single render by doing the comparison during the FIRST render instead of reacting to it afterward — the middle state, the one the user actually sees, simply never exists.

There's one prop here and one render pass — React doesn't split a single prop update into two DOM passes that drift apart. That describes a mechanism React doesn't have; the real gap is between commit and the effect that follows it.

Exactly — the render with the new user and the still-old draftName is a real, painted frame, because useEffect only runs after commit. Comparing user.id to a value stored from the previous render and resetting draftName inline, during that same render, removes the gap entirely.

Where you have seen this before

"Compute it now instead of reacting to it later" shows up everywhere state can lag behind its source.

Database triggers vs. computed columns

An AFTER INSERT trigger that backfills a derived column runs in a second transaction after the row is already visible to some readers; a GENERATED ALWAYS AS column is correct the instant the row commits, because it's computed inline instead of reacted to afterward.

reacting after the fact always leaves a visible gap

Angular's ngOnChanges vs. a getter

Resetting a field inside ngOnChanges runs on the NEXT change-detection pass; deriving the same value with a plain getter, or a computed() signal, is correct on the same pass — the Angular version of "during render, not after."

same one-tick lag, same fix, different framework

Cache invalidation webhooks

A webhook that busts a CDN cache after a save means the very first reader after that save can still get the stale response — there's a window. Writing through the cache synchronously during the save closes that window entirely.

"eventually consistent" always has a visible instant of "not yet"

1. The Hooks Linked List

React stores hook state in a linked list on the fiber node. Each call to a hook (useState, useEffect, useRef…) reads the NEXT slot in that list. This is why the Rules of Hooks exist: call order must be the same every render so React reads the right slot.

Rule: Never call hooks inside conditionals, loops, or nested functions. If hook call 1 is skipped on render 2, every subsequent hook reads the wrong slot — React cannot detect this at runtime until the values are observably wrong.

2. useEffect Dependency Array

No deps array

useEffect(() => {
  fetchData(); // runs after EVERY render
});

Runs after every commit. Rarely what you want — usually causes infinite loops if fetchData sets state.

Empty deps array []

useEffect(() => {
  const sub = ws.subscribe();
  return () => sub.unsubscribe();
}, []);
// mount only, cleanup on unmount

Runs once after mount. Cleanup runs on unmount. Correct for one-time subscriptions.

Specific deps

useEffect(() => {
  document.title = `User: ${userId}`;
}, [userId]);
// runs when userId changes

Runs when any dep changes (Object.is comparison). The linter rule exhaustive-deps helps you list everything.

⚠️ Stale closure trap

useEffect(() => {
  // count here is ALWAYS 0
  setInterval(() => console.log(count), 1000);
}, []); // count not in deps

The closure captures count=0. Adding count to deps fixes the value but restarts the interval every render. Use useRef to hold the latest value without re-running the effect.

3. useMemo vs useCallback

useMemo — cache a VALUE

const filtered = useMemo(
  () => items.filter(x => x.active),
  [items]
);
// filtered only recomputed when items changes

Use when the computation is genuinely expensive (large sort, heavy parse). useMemo is a hint, not a guarantee — React may evict cached values.

useCallback — cache a FUNCTION

const handleClick = useCallback(
  () => dispatch({ type: 'INC' }),
  [dispatch]
);
// same fn reference while dispatch is stable

useCallback(fn, deps) ≡ useMemo(() => fn, deps). Use when passing a callback to a memoized child component (React.memo) so it does not re-render on every parent render.

When NOT to memoize: Premature memoization adds overhead (dep comparison) without benefit. Profile first. Most components render fast enough that memoization makes no measurable difference. Only reach for useMemo/useCallback when you can demonstrate a render perf problem, or when a child is wrapped in React.memo.
