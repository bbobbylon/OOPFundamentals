Component Communication

Data flows DOWN via @Input(). Events bubble UP via @Output(). That's the contract. For anything else (siblings, deep trees), reach for a shared service.

🔁 What is component communication? Why the strict rules on data flow?

An Angular app is a tree of components — a UserListComponent holding UserCardComponents, each with a "Delete" button. Angular enforces one-way data flow: data flows down (parent → child via inputs), events flow up (child → parent via outputs). That unidirectional rule makes bugs traceable — you always know where a value came from and what changed it. Components that aren't parent/child don't talk directly; they share a service.

  • @Input() / input() — the parent pushes a value down: <app-user-card [user]="selected">.
  • @Output() / output() — the child emits an event up: this.deleted.emit(id), handled by (deleted)="remove($event)".
  • Siblings (no parent/child link) communicate through a shared service holding a signal or BehaviorSubject.
  • Signal inputs (input<T>()) give fine-grained updates — only the components that read them re-render, not the whole tree.
  • Keep state in the parent or a service; avoid child-to-child coupling — that's what makes apps hard to reason about.

@Input down, @Output up

Child: @Input() user!: UserDto; + @Output() deleted = new EventEmitter<number>(); → delete() { this.deleted.emit(this.user.id); }. Parent: <app-user-card [user]="u" (deleted)="remove($event)"> — $event is the emitted id.

Shared service for siblings

An @Injectable({ providedIn: 'root' }) holds the shared state — selected = signal<UserDto|null>(null) (or a BehaviorSubject). One sibling writes (select(u)), the other reads — no direct coupling.

Signals (Angular 17+)

user = input<UserDto>(), name = computed(() => user()?.firstName), deleted = output<number>(). Signal inputs track exactly who depends on them, so a change updates only the affected card — a real win for big lists vs full change detection.

In CIAM / Angular:a user-management page keeps the selected user + list in the parent, passes the user down via [user], and listens for (roleAssigned) up. A sibling search box emits (searchChanged). Cross-cutting auth state lives in a shared AuthService.currentUser$ every component reads — no component-to-component coupling.

The code behind the demo

Parent

@Component({
  selector: 'parent-component',
  standalone: true,
  imports: [ChildComponent, FormsModule],
  template: `
    <input [(ngModel)]="name">
    <p>votes received: {{ votes }}</p>

    <child-component
      [name]="name"                      <!-- DOWN -->
      (voted)="onVote($event)"           <!-- UP -->
    />
  `
})
export class ParentComponent {
  name  = 'Bobby';
  votes = 0;

  onVote(amount: number) {
    this.votes += amount;
  }
}

Child

@Component({
  selector: 'child-component',
  standalone: true,
  template: `
    <p>Hello, {{ name }}!</p>
    <button (click)="vote()">send vote up</button>
  `
})
export class ChildComponent {
  @Input() name = '';          // receives from parent
  @Output() voted =
    new EventEmitter<number>();   // emits to parent

  vote() {
    this.voted.emit(1);          // → parent's onVote(1)
  }
}

@Input — required, defaults, transforms, renames

// Plain input — optional, has a default
@Input() count = 0;

// Required — Angular errors at compile time if parent doesn't pass it (v16+)
@Input({ required: true }) userId!: string;

// Transform — coerce the incoming value (v16.1+)
@Input({ transform: booleanAttribute }) disabled = false;
@Input({ transform: numberAttribute }) age = 0;
// Now <child disabled> (attribute present = true) works correctly.

// Alias — public name differs from internal field
@Input('user-name') name = '';
// Parent: <child user-name="Bobby"/>  Child uses: this.name

@Output — EventEmitter is just a Subject

// Type the emitted payload
@Output() saved   = new EventEmitter<User>();
@Output() deleted = new EventEmitter<string>();   // emits the id
@Output() closed  = new EventEmitter<void>();    // no payload

// Fire them
this.saved.emit(updatedUser);
this.deleted.emit(id);
this.closed.emit();

<!-- Parent listens; $event is whatever child emitted -->
<user-form
  (saved)="onSave($event)"
  (deleted)="onDelete($event)"
  (closed)="closeDialog()"
/>

Naming convention: outputs are past-tense verbs (saved, closed, deleted) — they announce something happened. Avoid onClick / onSave — those are listeners, not events.

Two-way binding with custom outputs — the [(banana)] pattern

Angular has a magic naming rule: if you have @Input() x AND @Output() xChange, parents can use [(x)]="value" to two-way bind to it. That's all [(ngModel)] is. 

// child: counter.component.ts
@Input()  count = 0;
@Output() countChange = new EventEmitter<number>();

bump(delta: number) {
  this.count += delta;
  this.countChange.emit(this.count);
}

<!-- parent -->
<counter [(count)]="myCount"/>

<!-- equivalent to: -->
<counter [count]="myCount" (countChange)="myCount = $event"/>

Modern signal-based API — input(), output(), model()

Angular v17.3+ replaces the decorator forms with functions that return signals. New code should prefer these — they fit naturally into the signal world (no ngOnChanges needed, fewer typing footguns, computed inputs work for free). 

// === Old decorator form ===
export class ChildComponent {
  @Input() name = '';
  @Input({ required: true }) userId!: string;
  @Input({ transform: booleanAttribute }) disabled = false;
  @Output() saved = new EventEmitter<User>();
}

// === New signal form ===
export class ChildComponent {
  name     = input('');                                  // InputSignal<string>
  userId   = input.required<string>();                     // no default, must be provided
  disabled = input(false, { transform: booleanAttribute });
  saved    = output<User>();                            // OutputEmitterRef<User>

  greeting = computed(() => `Hi, ${this.name()}!`);   // reads signal()

  save() { this.saved.emit(buildUser(this.userId())); }
}

Signal inputs are read as functions

this.name is the signal itself; this.name() is the value. Templates: {{ name() }}. Putting them in computed or effect means the dependency tracking is automatic — no ngOnChanges for derived state.

Two-way with model()

// child: counter.component.ts
export class Counter {
  count = model(0);                       // ModelSignal<number> — input + matching output

  bump(delta: number) {
    this.count.update(c => c + delta);   // auto-emits the new value
  }
}

<!-- parent — just [(name)] works, no countChange to wire up -->
<counter [(count)]="myCount"/>

Migrating from EventEmitter

// The new output() does NOT extend EventEmitter — no .pipe(), .subscribe(), etc.
// If you need observable behavior, bridge it:
import { outputFromObservable, outputToObservable } from '@angular/core/rxjs-interop';

// Expose an existing Observable as an output:
saved = outputFromObservable(this.savedSubject$);

// Consume an output as an Observable:
const obs$ = outputToObservable(child.saved);

Modern queries — viewChild(), contentChild()

The signal-based replacement for @ViewChild / @ContentChild. Reads as a signal, so template usage and computed() derivations Just Work. No more ngAfterViewInit juggling. 

// === Old ===
@ViewChild('input') input!: ElementRef<HTMLInputElement>;
ngAfterViewInit() { this.input.nativeElement.focus(); }

// === New ===
input = viewChild<ElementRef<HTMLInputElement>>('input');
// Required form — errors at runtime if not found:
input = viewChild.required('input');

ngAfterViewInit() {
  this.input()?.nativeElement.focus();   // signal call → ElementRef | undefined
}

// Many at once
items = viewChildren(ItemComponent);            // Signal<readonly ItemComponent[]>
total = computed(() => this.items().reduce((s, i) => s + i.price, 0));

When parent ↔ child isn't enough

@Input/@Output work great for one level. Pushing data through 5 levels via "prop drilling" is misery. And siblings can't talk to each other directly at all. Solutions:

SituationBest toolWhy
Parent ↔ direct child@Input / @OutputExplicit contract, easy to read.
Through 2-3 levels@Input down, @Output upStill acceptable. Annoying but clear.
Deep tree (4+ levels)Shared serviceAvoid prop drilling. Service holds state, components subscribe.
Sibling ↔ siblingShared serviceThey have no direct relationship. A common parent + service.
Cross-route state (cart, auth, etc)providedIn: 'root' serviceSingleton, survives route changes.
Form-like inputs to a sub-treeService provided at the parent componentScoped instance shared with descendants.

Shared service pattern — sibling communication

// chat.service.ts — the "channel" between siblings
@Injectable({ providedIn: 'root' })
export class ChatService {
  private messages$ = new BehaviorSubject<string[]>([]);

  send(msg: string) {
    this.messages$.next([...this.messages$.value, msg]);
  }
  stream() {
    return this.messages$.asObservable();
  }
}

// sender.component.ts — sibling A
export class SenderComponent {
  private chat = inject(ChatService);

  send() { this.chat.send('hello'); }
}

// receiver.component.ts — sibling B (anywhere in the tree)
export class ReceiverComponent {
  private chat = inject(ChatService);
  messages$ = this.chat.stream();      // auto-subscribe with | async
}

<!-- receiver template -->
<div *ngFor="let m of messages$ | async">{{ m }}</div>

Other ways to reach across components

📍 @ViewChild — grab a child instance

Sometimes you need the actual child component object (to call a method like child.reset()). Use @ViewChild.

@ViewChild(ChildComponent) child!: ChildComponent;

reset() { this.child.reset(); }

Available after ngAfterViewInit. Avoid for normal data flow — it tightly couples parent to child.

📍 @ViewChildren — many children

Returns a QueryList of all matching child components. Iterate with .toArray() or .forEach().

@ViewChildren(ItemComponent) items!: QueryList<ItemComponent>;

📍 @ContentChild / @ContentChildren

Same idea, but for projected content (children passed via <ng-content>). Comes from the using template, not your own.

📍 Template reference + parent

The lightest option: a child exposed via #ref in the parent template. Good for one-off calls without TypeScript boilerplate.

<child #c/>
<button (click)="c.reset()">reset</button>

Content projection — <ng-content>

A way to let the parent hand markup INTO the child's template. Crucial for reusable wrappers (cards, modals, layouts) where the wrapping is constant but the inside changes. 

// card.component.ts
@Component({
  selector: 'app-card',
  standalone: true,
  template: `
    <div class="card">
      <header><ng-content select="[card-title]"/></header>
      <main><ng-content/></main>                  <!-- default slot -->
      <footer><ng-content select="[card-actions]"/></footer>
    </div>
  `
})
export class CardComponent {}

<!-- usage -->
<app-card>
  <h3 card-title>My Card</h3>
  <p>This goes in the default slot.</p>
  <button card-actions>Save</button>
</app-card>

The select="..." attribute is a CSS selector — pick by tag, class, or attribute. Order of <ng-content> elements in the child controls where each piece is rendered.

Passing templates between components — TemplateRef & ngTemplateOutlet

Sometimes a child needs to render markup that the parent supplies at specific spots — table cell renderers, dropdown item templates, custom empty states. Pass a TemplateRef as a regular @Input and render it with *ngTemplateOutlet. Far more flexible than content projection when the same template is reused or needs context. 

// list.component.ts — accepts an optional itemTemplate
@Component({
  selector: 'app-list',
  standalone: true,
  imports: [CommonModule],
  template: `
    @for (item of items(); track item.id) {
      <div class="row">
        <ng-container *ngTemplateOutlet="
          itemTemplate() ?? defaultTpl;
          context: { $implicit: item, index: $index }
        "></ng-container>
      </div>
    }
    <ng-template #defaultTpl let-item>{{ item.name }}</ng-template>
  `
})
export class ListComponent<T> {
  items = input.required<T[]>();
  itemTemplate = input<TemplateRef<{ $implicit: T; index: number }> | null>(null);
}

<!-- parent decides how each row looks -->
<app-list [items]="users" [itemTemplate]="row"/>

<ng-template #row let-user let-i="index">
  <strong>#{{ i }} {{ user.name }}</strong> — {{ user.email }}
</ng-template>

let-user binds the template variable to $implicit from the context object. Named contexts (let-i="index") bind to any named property you pass.

The flow rules — memorize these

Data flows DOWN

Parent owns data → passes it to child via @Input. Children should be "dumb" where possible — render what they're given.

Events bubble UP

Child says "something happened" → parent decides what to do. Children should never mutate Input data; emit an Output instead.

Siblings talk via parent OR service

Either lift state to the common parent (small scope) or share through a service (large scope or distant siblings).

Don't mutate @Input objects

If a child mutates this.user.name, it bypasses the parent. Treat Inputs as read-only. Emit an Output and let the parent update.

🌱 New here? Components talk in two directions: down and up.

When components are parent and child, there are exactly two channels:

  • Down — the parent passes data to the child with an input ([name]="title" ↔ name = input<string>()).
  • Up — the child notifies the parent with an output event ((liked)="onLike()" ↔ liked = output<void>() + liked.emit()).

For components that aren't parent/child, they can't use inputs/outputs — instead they share a service (both inject it; one writes, the other reads). So the rule of thumb: parent↔child → inputs/outputs; anywhere-to-anywhere → a shared service.

🧠 Expert corner — avoid prop-drilling, prefer a shared signal

  • Inputs/outputs are signal-based now (v17+): input(), output(), and model() for two-way ([(value)]). The decorator forms still work.
  • Don't prop-drill. Threading the same data through five layers of inputs is a smell — lift it into a shared service holding a signal (or a signal store) that any component injects and reads. The service is the mediator.
  • Don't mutate @Input objects (the gotcha above): treat inputs as read-only, emit an output, and let the owner update — otherwise you bypass change detection and confuse data ownership.
  • @ViewChild to call a child method is a last resort — it couples parent to child internals. Prefer data flow over reaching in.
  • Content projection (<ng-content>) is another "communication" tool: the parent supplies markup the child renders in place.
  • CIAM tie-in. A single AuthService exposing an authState signal is read by the navbar, guards, and any feature component — no input chains, one source of truth. See Services & DI and Signals.
