Functional Guards & Resolvers

Angular 15+ route guards and resolvers — functional style, inject(), canMatch, canDeactivate, and resolver-to-input binding. No class boilerplate required.

🛡️ What are functional guards & resolvers — and why did Angular drop classes?

Before Angular 15, a route guard was a class implementing an interface like CanActivate — needing @Injectable(), boilerplate, and registration. Angular 15 replaced them with plain functions: a guard is now just (route, state) => boolean | UrlTree | Observable<…>. Any matching function works — no class, no interface, no registration — and you call inject() inside it to reach services. That makes guards trivially composable and unit-testable: call the function with a mock route, no TestBed.

  • A guard returns true (allow), false (block), or a UrlTree (redirect — preferred over a manual router.navigate()).
  • It can return those asynchronously as an Observable/Promise — e.g. waiting on an auth check.
  • canActivate gates entry; canDeactivate guards exit (unsaved changes); canMatch pre-filters which route even matches.
  • Resolvers (ResolveFn) pre-fetch data so the component renders after the API returns — no in-component loading state.
  • Compose by listing several: canActivate: [authGuard, roleGuard('ADMIN')] — all must pass.

canActivate function

export const authGuard: CanActivateFn = () => inject(AuthStore).isAuthenticated() ? true : inject(Router).createUrlTree(['/login']); Use it as canActivate: [authGuard].

canDeactivate — unsaved changes

canDeactivate: [(c: UserFormComponent) => !c.hasUnsavedChanges() || confirm('Discard changes?')]. Runs when navigating away; return false to keep the user on the page.

Resolvers — data before render

export const userResolver: ResolveFn<User> = (route) => inject(UserApi).getUser(route.params['id']); Route: resolve: { user: userResolver }; the component reads it via input binding. The page renders only once the data is in.

In CIAM:authGuard redirects to /login when unauthenticated; roleGuard('ADMIN') redirects to /403; userResolver fetches the user before the detail page renders; an unsavedChangesGuard confirms before leaving a dirty edit form. Chain: canActivate: [authGuard, roleGuard('ADMIN')] — but remember the server is still the real gate.

The evolution: class guards → functional guards

Angular v14 introduced functional guards — plain arrow functions instead of injectable classes. Angular v15 deprecated the class-based interfaces (CanActivate, CanDeactivate, etc.). Today the functional form is the official, recommended style. The key wins: no boilerplate class, no decorator, and inject() works directly inside the function body thanks to Angular's injection context.

Old: class-based (deprecated v15)

@Injectable({ providedIn: 'root' })
export class AuthGuard
    implements CanActivate {

  constructor(
    private auth: AuthService,
    private router: Router
  ) {}

  canActivate(
    route: ActivatedRouteSnapshot,
    state: RouterStateSnapshot
  ): boolean | UrlTree {
    return this.auth.isLoggedIn()
      ? true
      : this.router
          .createUrlTree(['/login']);
  }
}
18 lines. Needs @Injectable, implements, constructor injection, this. everywhere.

New: functional (Angular 14+, current best practice)

// auth.guard.ts
import { inject } from '@angular/core';
import { CanActivateFn, Router }
  from '@angular/router';

export const authGuard: CanActivateFn =
  (route, state) => {
    const auth   = inject(AuthService);
    const router = inject(Router);

    return auth.isLoggedIn()
      ? true
      : router.createUrlTree(['/login'],{
          queryParams: { ret: state.url }
        });
  };
11 lines. A plain const — no class, no decorator, no implements.
Why inject() works inside guard functions: Angular's router calls guards from within an injection context. That means inject() can resolve tokens just like a constructor parameter — but only during the initial synchronous invocation of the guard function, not inside callbacks or async chains.

canActivate — authenticate before entering a route

The most-used guard. It runs after URL matching and before the component is created. Returning a UrlTree is the modern way to redirect — it's cleaner than calling router.navigate() imperatively because the router handles it as part of the same navigation event (no extra NavigationStart/End cycle). 

// auth.guard.ts — complete example
import { inject } from '@angular/core';
import { CanActivateFn, Router } from '@angular/router';
import { map } from 'rxjs/operators';

// ── Synchronous guard (fast, no HTTP call needed) ──────────────────
export const authGuard: CanActivateFn = (route, state) => {
  const auth   = inject(AuthService);
  const router = inject(Router);

  if (auth.isLoggedIn()) {              // isLoggedIn() reads a signal
    return true;                        // ✅ allow navigation
  }
  return router.createUrlTree(['/login'], {
    queryParams: { returnUrl: state.url }  // preserve intended URL
  });                                      // ↑ UrlTree = redirect
};

// ── Async guard (verify token with the backend) ────────────────────
export const asyncAuthGuard: CanActivateFn = (route, state) => {
  const auth   = inject(AuthService);
  const router = inject(Router);

  return auth.verifyToken().pipe(         // Observable<boolean>
    map(valid =>
      valid ? true
            : router.createUrlTree(['/login'], {
                queryParams: { returnUrl: state.url }
              })
    )
  );
};

// ── Composing multiple guards (AND logic) ──────────────────────────
export const adminGuard: CanActivateFn = () => {
  const auth = inject(AuthService);
  return auth.hasRole('admin')
    ? true
    : inject(Router).createUrlTree(['/forbidden']);
};
// app.routes.ts — applying guards
export const routes: Routes = [
  { path: '',        component: HomeComponent },
  { path: 'login',   component: LoginComponent },

  // Single guard
  { path: 'dashboard',
    canActivate: [authGuard],
    component: DashboardComponent },

  // Multiple guards — ALL must return true (evaluated in order)
  { path: 'admin',
    canActivate: [authGuard, adminGuard],
    component: AdminComponent },

  // canActivateChild — one guard protects ALL children
  { path: 'settings',
    canActivateChild: [authGuard],
    children: [
      { path: 'profile',  component: ProfileComponent },
      { path: 'security', component: SecurityComponent },
      { path: 'billing',  component: BillingComponent }
    ] }
];
UrlTree vs router.navigate(): returning a UrlTree from a guard is the preferred redirect mechanism. It's handled atomically — there is no second navigation event. Calling router.navigate() imperatively inside a guard causes a second, separate navigation which can interfere with loading indicators and event streams.

Async guard — verifying a JWT with the backend

A common pattern: the token is in memory (or a cookie) but you want a quick ping to /api/me to confirm it's still valid before showing sensitive data.

export const strictAuthGuard: CanActivateFn = (route, state) => {
  const http    = inject(HttpClient);
  const router  = inject(Router);

  return http.get<{ ok: boolean }>('/api/me').pipe(
    map(resp => resp.ok ? true
                         : router.createUrlTree(['/login'])),
    catchError(() => of(router.createUrlTree(['/login'])))
    // ↑ on network error, also redirect — never leave user stuck
  );
};
// Angular subscribes automatically, waits for the first emission,
// then proceeds or redirects. The Observable must complete!

canDeactivate — guard the exit door

canDeactivate fires when the user tries to navigate away from the current route — either via a router link, programmatic navigation, or the browser back button (in-app only). The guard receives a reference to the current component instance, so it can ask the component whether it's safe to leave.

The guard signature

// Type definition
type CanDeactivateFn<T> = (
  component:    T,                       // the component about to be left
  currentRoute: ActivatedRouteSnapshot,
  currentState: RouterStateSnapshot,
  nextState:    RouterStateSnapshot     // where we're going
) => MaybeAsync<GuardResult>;         // boolean | UrlTree | Observable | Promise

Pattern A — interface on the component (most reusable)

// can-leave.interface.ts
export interface CanLeave {
  canLeave(): boolean | Observable<boolean>;
}

// can-leave.guard.ts — one guard for ALL components that implement CanLeave
export const canLeaveGuard: CanDeactivateFn<CanLeave> =
  (component) => component.canLeave();

// edit-form.component.ts
export class EditFormComponent implements CanLeave {
  isDirty = signal(false);

  canLeave(): boolean | Observable<boolean> {
    if (!this.isDirty()) return true;
    return this.confirmDialog
      .open('Unsaved changes — leave anyway?')
      .afterClosed();  // Observable<boolean>
  }
}

// app.routes.ts
{ path: 'profile/edit', component: EditFormComponent,
  canDeactivate: [canLeaveGuard] }

Pattern B — inline, no separate guard file

// Inline functional guard in the route definition
{ path: 'editor', component: EditorComponent,
  canDeactivate: [
    (comp: EditorComponent) =>
      comp.isSaved || confirm('Leave without saving?')
  ]
}

Works with signal-based components

// Signal-based component — canDeactivate reads a signal
export class DocumentEditorComponent {
  private content    = signal('');
  private savedState = signal('');

  // computed: true when current content differs from last save
  hasUnsavedChanges = computed(() =>
    this.content() !== this.savedState()
  );

  canLeave(): boolean {
    return !this.hasUnsavedChanges() ||
      confirm('You have unsaved changes. Leave?');
  }
}
Browser back / tab close limitation: canDeactivate only intercepts Angular router navigations. It does NOT fire when the user closes the browser tab or navigates to an external URL. For those cases, listen to the DOM's window.beforeunload event separately. A common pattern: @HostListener('window:beforeunload', ['$event']) onBeforeUnload(e) { if (this.isDirty()) e.returnValue = ''; }

canMatch — guard before route matching

canMatch is the successor to the deprecated canLoad. It runs during URL matching — before Angular even decides if a route should be used — and therefore can completely prevent a lazy-loaded chunk from ever being downloaded. This is the key difference from canActivate: canActivate runs after a route is already matched and matched chunks already fetched; canMatch runs during matching so a false result means the route is skipped entirely.

canMatch vs canActivate — the critical difference

BehaviorcanActivatecanMatch
Runs whenAfter route selected, before component initDuring route selection — can skip route entirely
If it returns falseBlocks navigation; shows nothingAngular tries the next route with the same path
Lazy chunk downloadAlready downloaded by the time guard runsChunk never downloaded if guard returns false
Multiple routes at same pathNot possible — first match winsYes — canMatch controls which one wins
ReplacesWas always the auth guard slotReplaces deprecated canLoad

Feature flag routing — two components, one path

// feature-flag.guard.ts
export function featureFlag(flagName: string): CanMatchFn {
  return () => inject(FeatureFlagService).isEnabled(flagName);
}

// app.routes.ts
export const routes: Routes = [
  // If new-checkout flag is ON → match this route (v2 component)
  { path: 'checkout',
    canMatch: [featureFlag('new-checkout')],
    loadComponent: () => import('./checkout-v2.component') },

  // Fallback — used when first route's canMatch returns false
  { path: 'checkout',
    component: CheckoutLegacyComponent }
];
// Angular evaluates routes top-to-bottom. If canMatch=false, it skips to the next.

Role-based lazy loading — block the chunk download

export const routes: Routes = [
  // Non-admins never download this chunk — canMatch blocks it
  { path: 'admin',
    canMatch: [() => inject(AuthService).hasRole('admin')],
    loadChildren: () =>
      import('./admin/admin.routes').then(m => m.adminRoutes)
  },
  // Admin tried /admin without permission → canMatch false → falls to wildcard
  { path: '**', component: NotFoundComponent }
];

Migrating from canLoad → canMatch

// Before (deprecated)
{ path: 'reports',
  canLoad: [authGuard],           // ← deprecated
  loadChildren: () => import('./reports/routes') }

// After (current)
{ path: 'reports',
  canMatch: [authGuard],          // ← same guard function works
  loadChildren: () => import('./reports/routes') }

// CanActivateFn and CanMatchFn are compatible — same function works in both
A/B testing with canMatch: serve two completely different component implementations to different user segments — without routing conflicts, without feature-flag conditionals scattered in templates, and without the control group ever downloading the variant's code.

Resolvers — pre-fetch data before activating

A resolver runs after all guards pass but before the component is instantiated. Angular subscribes to the returned Observable and waits for it to emit and complete before proceeding. The emitted value lands in route.snapshot.data. The component is guaranteed to have the data on its very first render — no loading spinner needed inside the component itself. 

// product.resolver.ts — functional resolver
import { inject } from '@angular/core';
import { ResolveFn } from '@angular/router';

export const productResolver: ResolveFn<Product> =
  (route, state) => {
    const ps = inject(ProductService);
    const id = route.paramMap.get('id')!;
    return ps.getById(id);             // Observable<Product>
    // Angular awaits first emission + completion, then activates
  };

// app.routes.ts
{ path: 'products/:id',
  component: ProductDetailComponent,
  resolve: { product: productResolver } }

// product-detail.component.ts
export class ProductDetailComponent {
  private route = inject(ActivatedRoute);

  // Synchronous access — data is ready before ngOnInit
  product = this.route.snapshot.data['product'] as Product;

  // Or as an observable (useful if the route can be re-used in place)
  product$ = this.route.data.pipe(map(d => d['product'] as Product));
}

Multiple resolvers — they run in parallel

{ path: 'products/:id',
  component: ProductDetailComponent,
  resolve: {
    product:  productResolver,    // ┐ all three fire simultaneously
    reviews:  reviewsResolver,    // │ Angular waits for ALL to complete
    related:  relatedResolver,    // ┘ before the component activates
  }
}

// Access in component
product  = this.route.snapshot.data['product'];
reviews  = this.route.snapshot.data['reviews'];
related  = this.route.snapshot.data['related'];

withComponentInputBinding() — Angular 16+

Enable this router feature and resolved data, route params, and query params are automatically injected into matching @Input properties — no ActivatedRoute injection needed in the component.

// app.config.ts
export const appConfig: ApplicationConfig = {
  providers: [
    provideRouter(routes,
      withComponentInputBinding()   // ← enable the binding
    )
  ]
};

// product-detail.component.ts — no ActivatedRoute needed!
export class ProductDetailComponent {
  // route param :id flows into this @Input
  @Input() id!: string;

  // resolved data (key 'product') flows into this @Input
  @Input() product!: Product;

  // query param ?tab=reviews flows into this @Input
  @Input() tab?: string;
}
// Angular 17.3+: use input() signal function instead of @Input decorator
// id = input<string>();  product = input<Product>();

Static route metadata with data:

// Static metadata on the route — no async, no service
{ path: 'about', component: AboutComponent,
  data: { title: 'About Us', icon: 'info', breadcrumb: 'About' }
}

// Reading it — available immediately as snapshot data
const title = inject(ActivatedRoute).snapshot.data['title'];

// Common pattern: title service in AppComponent
router.events.pipe(filter(e => e instanceof NavigationEnd))
  .subscribe(() => {
    const route = router.routerState.root.firstChild;
    title.setTitle(route?.snapshot.data['title'] ?? 'My App');
  });
Resolver must complete, not just emit: if your Observable never completes (e.g., a BehaviorSubject directly), Angular will wait forever. Use take(1) to ensure completion: return myService.items$.pipe(take(1));

Testing functional guards — dramatically simpler

One of the big wins of functional guards: they are just functions. You can call them directly with mock arguments in a unit test without any Angular TestBed setup — though TestBed is still needed to properly test inject() calls.

Testing a synchronous guard

// auth.guard.spec.ts
describe('authGuard', () => {
  let authService: AuthService;
  let router:      Router;

  beforeEach(() => {
    TestBed.configureTestingModule({
      providers: [
        provideRouter([]),
        { provide: AuthService,
          useValue: { isLoggedIn: jest.fn() } }
      ]
    });
    authService = TestBed.inject(AuthService);
    router      = TestBed.inject(Router);
  });

  it('allows navigation when logged in', () => {
    (authService.isLoggedIn as jest.Mock).mockReturnValue(true);

    // Run the guard inside the injection context
    const result = TestBed.runInInjectionContext(() =>
      authGuard(mockRoute(), mockState())
    );

    expect(result).toBe(true);
  });

  it('redirects to /login when not logged in', () => {
    (authService.isLoggedIn as jest.Mock).mockReturnValue(false);

    const result = TestBed.runInInjectionContext(() =>
      authGuard(mockRoute(), mockState('/dashboard'))
    );

    expect(result).toBeInstanceOf(UrlTree);
    expect(router.serializeUrl(result as UrlTree))
      .toContain('/login');
  });
});

Testing an async guard

it('waits for async auth check', fakeAsync(() => {
  const authService = TestBed.inject(AuthService);
  jest.spyOn(authService, 'verifyToken')
    .mockReturnValue(of(true));

  let result: boolean | UrlTree | null = null;

  TestBed.runInInjectionContext(() =>
    (asyncAuthGuard(mockRoute(), mockState()) as Observable<any>)
      .subscribe(v => result = v)
  );
  tick();

  expect(result).toBe(true);
}));
TestBed.runInInjectionContext() — this is the key helper for testing functional guards and resolvers. It establishes an injection context so inject() works inside the function, exactly as it would when called by the real router.

Testing canDeactivate

it('blocks navigation when form is dirty', () => {
  const mockComponent = {
    canLeave: () => false   // simulating isDirty = true
  };

  const result = canLeaveGuard(
    mockComponent,
    mockRoute(), mockState(), mockState('/home')
  );

  expect(result).toBe(false);
});
// No TestBed needed — canLeaveGuard just calls component.canLeave()
