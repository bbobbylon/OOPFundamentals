Helm Charts

Helm is the package manager for Kubernetes. Charts template your manifests so you can deploy the same app to dev, staging, and prod with different values.

⛵ What is Helm — and why do Kubernetes manifests need a package manager?

A K8s app has 10-20 manifests (Deployment, Service, Ingress, ConfigMap, …) that differ per environment — without tooling that's 60 files to keep in sync. Helm is a templating engine + package manager: a Chart is Go-templated YAML ({{ .Values.replicaCount }}) plus a values.yaml of defaults, and helm install … -f prod-values.yaml renders and applies it. Commands track revisions: install, upgrade (apply with history), rollback, uninstall. A release is a named install, so the same chart runs as ciam-dev and ciam-prod with different values. Artifact Hub hosts pre-built charts (nginx-ingress, cert-manager). Most teams pair Helm (packaging) with ArgoCD (GitOps).

  • One chart, per-env values — no 60-file YAML duplication.
  • Go-templated YAML + values.yaml — {{ .Values.x }}.
  • Revision-tracked — install/upgrade/rollback; a release = a named install.
  • Pre-built charts on Artifact Hub; pair with ArgoCD for GitOps.

Chart structure + template

# Chart.yaml name: ciam-auth version: 1.2.3 appVersion: "1.2.3" # values.yaml (defaults) replicaCount: 2 image: repository: myregistry/ciam-auth tag: "1.2.3" resources: limits: { memory: 1Gi, cpu: "2" } requests: { memory: 512Mi, cpu: 500m } pingBaseUrl: "https://ping-dev.company.com" # templates/deployment.yaml spec: replicas: {{ .Values.replicaCount }} template: spec: containers: - name: ciam-auth image: "{{ .Values.image.repository }}:{{ .Values.image.tag }}" resources: {{- toYaml .Values.resources | nindent 12 }} env: - name: PING_BASE_URL value: {{ .Values.pingBaseUrl | quote }}

Multi-env values

# dev-values.yaml replicaCount: 1 resources: limits: { memory: 512Mi, cpu: "1" } requests: { memory: 256Mi, cpu: 250m } pingBaseUrl: "https://ping-dev.company.com" # prod-values.yaml replicaCount: 6 resources: limits: { memory: 2Gi, cpu: "4" } requests: { memory: 1Gi, cpu: "1" } pingBaseUrl: "https://ping-prod.company.com" # Deploy to each environment: helm install ciam-auth ./ciam-chart \ --namespace ciam-dev \ --values dev-values.yaml helm upgrade ciam-auth ./ciam-chart \ --namespace ciam-prod \ --values prod-values.yaml \ --set image.tag=1.3.0 # override one value # Check what would be applied: helm template ./ciam-chart -f prod-values.yaml # Rollback: helm rollback ciam-auth 2 -n ciam-prod

Helm vs Kustomize vs ArgoCD

Helm: Go templates + package manager. Best for: complex apps with many configurable values, third-party chart reuse (install nginx-ingress with one command). Con: template syntax is complex, hard to validate, "the YAML explosion gets worse". Kustomize: overlay-based, no templates. base/ directory has plain YAML, overlays/dev/ patches specific fields. Simpler than Helm, built into kubectl apply -k. Best for: straightforward config differences between environments. ArgoCD: GitOps operator. Watches a git repo, automatically syncs any changes to the cluster — if someone manually changes a K8s resource, ArgoCD drifts it back to match git. Supports both Helm and Kustomize. Reality: most teams use Helm for packaging + ArgoCD for GitOps. Pipeline: push code → CI builds image → CI updates image.tag in Helm values file → ArgoCD detects git change → ArgoCD runs helm upgrade → new pods rolling out. ADO Pipeline integration: helm upgrade --install step in your ADO YAML pipeline.

CIAM Helm chart: One chart bundles the Deployment, Service, Ingress (TLS + path routing), ConfigMap (per-env Ping URLs), ServiceAccount + RBAC, HPA, and a PodDisruptionBudget (minAvailable: 2). Dev values set replicaCount: 1/512Mi/DEBUG; prod sets 6/2Gi/INFO. The ADO pipeline runs helm upgrade --install ciam-auth ./helm/ciam-auth --values values-$(environment).yaml --set image.tag=$(Build.BuildId) — the BuildId tag rolls out a versioned image per build, with helm rollback if smoke tests fail.

or, how to ship four hundred lines of YAML that nobody has ever read

The exhibit

This is the one artifact that actually matters, and it's the one almost nobody looks at before it ships.

# $ helm template ./ciam-chart -f values-prod.yaml --set replicaCout=6
# ↓ this text is ALL the cluster will ever see — not the chart, not your intent
apiVersion: apps/v1
kind: Deployment
metadata:
  name: ciam-auth
spec:
  replicas: 2
  template:
    spec:
      containers:
        - name: ciam-auth
          image: registry/ciam-auth:2.3.1
replicas: 2 — the values.yaml default, not the six you meant to ship. --set replicaCout=6 has a typo Helm never flags: it just merges a brand-new key that no template reads, and the real replicaCount falls through to its default untouched.
There is no warning line above this YAML, no STATUS: unknown-key, nothing. helm upgrade --install prints STATUS: deployed for this exact output — Helm did precisely what you told it, key for key.
Notice what is NOT in this file: Chart.yaml, values.yaml, any {{ }}, any trace that a template engine ever ran. The cluster has never heard of Helm — this is the entire interface between the two.
Helm is a text templating engine wearing a package manager's coat. Templates plus merged values go in, plain Kubernetes YAML comes out, and that is all the cluster ever sees. Nothing in etcd has heard of a chart, a value or a {{ if }}.
The mechanism

Render, then apply. Only one of those two verbs touches Kubernetes.

  1. Helm loads Chart.yaml, values.yaml and everything under templates/still just files on your laptop
  2. Values merge: chart defaults, then a parent chart's values, then each -f file in order, then --setlast one wins, and says nothing
  3. Go's text/template runs over every template filetext in, text out — it cannot see your cluster
  4. The rendered text is finally parsed as YAMLa bad {{- becomes an error HERE
  5. The manifests go to the API server as an ordinary applybyte for byte, what kubectl would send
  6. Helm stores the rendered manifests in a Secret in that namespace, one per revision — sh.helm.release.v1.ciam-auth.v3the release lives IN the cluster
  7. helm rollback re-applies the text out of an older Secretwhich is why it is fast, and dumb

Steps 1 to 4 never contact Kubernetes. That is the entire point of helm template: it stops at step 4 and prints. Everyone re-learns this the day they try to debug a template by deploying it.

Step 6 is the one that surprises people. Helm has no database and no memory of its own — a release is a gzipped blob of rendered YAML sitting in a Secret in the release's namespace, which is why helm history is just a listing of those Secrets, why helm rollback works from any laptop with kubeconfig, and why deleting the namespace deletes your rollback history along with it. It is also why hand-editing a live resource is a time bomb: Helm's stored copy still says what the chart said, and the next upgrade will quietly settle the argument in the chart's favour.

During an incident you ran kubectl scale --replicas=6 on the CIAM auth Deployment. A week later a colleague runs helm upgrade with the same values file, only to ship a new image.tag. What happens to your six pods?

That was Helm 2, and it is exactly the assumption that gets people. A two-way patch compared old manifest to new manifest, saw replicas: 2 in both, and left your hand-scaled 6 alone.

Right. Helm 3 builds a three-way strategic merge patch: old manifest, live state, new manifest. It notices live (6) disagrees with what it last applied (2), decides that was not its doing, and puts it back. Your incident fix survived a whole week and then died to an unrelated image bump — which is the argument for putting the 6 in the values file the same afternoon you typed it.

Helm does not block on drift; nothing warns you. It reconciles silently, which is precisely why this one hurts.

Questions from the back row

If helm install renders the templates anyway, why bother with helm template?

Because install renders and applies in one breath, and you only get to review one of those. helm template stops after rendering and prints to stdout, so it fits in a pipe, a diff, a CI job or a PR comment — no cluster, no credentials, no consequences. Its one blind spot: it does not know the live state, so for "what will actually change" reach for helm diff upgrade or helm upgrade --dry-run, which do talk to the API server.

Why did adding a newline break my chart? What is {{- for?

Go templating emits every character you did not explicitly remove, and YAML is a whitespace-significant language reading the result. {{- chomps the whitespace before the action, including the newline; -}} chomps what comes after. So {{- if .Values.ingress.enabled }} on its own line disappears cleanly, while {{ if ... }} leaves a blank line that a range inside a list will happily indent into nonsense. Related trap: {{ toYaml .Values.resources | nindent 12 }} uses nindent, which adds a newline first — use indent there and you weld the map onto the key above it.

Do I still need Tiller, or a Helm server, to make rollback work?

No — Helm 3 deleted Tiller entirely. The client is the whole product: it renders locally, applies with your kubeconfig and your RBAC, and writes the result into a Secret. Two consequences worth remembering: Helm can do exactly what you are allowed to do and nothing more, and only the last --history-max revisions (default 10) are kept, so revision 1 is not waiting for you forever.

1 — Chart Structure




my-api/
├── Chart.yaml        # chart metadata (name, version, appVersion)
├── values.yaml       # default values
├── values-prod.yaml  # environment overrides
└── templates/
    ├── deployment.yaml
    ├── service.yaml
    ├── ingress.yaml
    ├── configmap.yaml
    └── _helpers.tpl  # reusable named templates


Templates use Go's text/template syntax. Values are injected via {{ .Values.key }}. The _helpers.tpl defines reusable snippets like the full app name and common labels.









2 — Deployment Template




# templates/deployment.yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: {{ include "my-api.fullname" . }}
  labels: {{ include "my-api.labels" . | nindent 4 }}
spec:
  replicas: {{ .Values.replicaCount }}
  template:
    spec:
      containers:
      - name: {{ .Chart.Name }}
        image: "{{ .Values.image.repository }}:{{ .Values.image.tag }}"
        env:
        {{- range .Values.extraEnv }}
        - name: {{ .name }}
          value: "{{ .value }}"
        {{- end }}









3 — values.yaml & Overrides




# values.yaml (defaults)
replicaCount: 2
image:
  repository: myregistry/api-server
  tag: latest
service.port: 80
ingress.enabled: false

# values-prod.yaml (overrides)
replicaCount: 5
image.tag: 2.1.0
ingress.enabled: true
ingress.host: api.mycompany.com
---
# Install for production:
helm upgrade --install api-server ./my-api \
  -f values-prod.yaml \
  --set image.tag=2.1.0 \
  --namespace prod









4 — Helm Release Lifecycle




# Install
helm install api-server ./my-api -n prod

# Upgrade (rolling update + versioned release)
helm upgrade api-server ./my-api -f values-prod.yaml -n prod

# Check status
helm status api-server -n prod
helm history api-server -n prod
# REVISION  STATUS     DESCRIPTION
# 1         deployed   Install complete
# 2         deployed   Upgrade complete
# 3         failed     Upgrade failed

# Rollback
helm rollback api-server 2 -n prod   # go back to revision 2

# Uninstall
helm uninstall api-server -n prod    # deletes ALL chart resources
