Python Fundamentals

The CPython execution model, the object system, LEGB scope, reference counting, and function call frames — the mental model every Python developer needs.

🐍 What is Python — and what does CPython actually do with your code?

Python is high-level, dynamically typed, and "interpreted" — but CPython actually compiles your source to bytecode (.pyc) and runs it in the Python Virtual Machine. Everything is an object (ints, strings, functions, classes) with an identity, a type, and a value. Name lookup follows LEGB, memory is managed by reference counting (plus a cyclic collector), and the GIL lets only one thread run bytecode at a time — so threads don't parallelize CPU work (use multiprocessing/asyncio).

  • Compiled to bytecode, run on the PVM — "interpreted" is a simplification.
  • Everything is an object — identity, type, value; functions included.
  • Ref-counting + cyclic GC free memory automatically.
  • The GIL serializes bytecode — threads ≠ CPU parallelism (use multiprocessing/asyncio).

or, the function argument that remembers every call it has ever seen

The problem

You wrote a friendly default. Python built it once, on move-in day, and never again.

def provision_user(name, roles=[]): looked completely reasonable

A seed script provisions two accounts back to back: alice = provision_user('Alice'), then bob = provision_user('Bob'). Neither call passes roles — that's the whole point of a default, so you don't have to.

bob['roles'] comes back as ['BASE_USER', 'BASE_USER']. Two entries. For a brand-new user who has never touched roles.append() in his own call. alice['roles'] is bob['roles'] — they are not two similar lists, they are the exact same object, and Alice's call left a mark on it that Bob inherited.

roles=[] reads like "a new empty list, every call" ⚠ the def line runs ONCE, at import time ✓ [] on that line is built ONCE, right then ✓

Nobody passed a list between the two calls. Nobody imported anything shared. The bug is the default argument itself, quietly acting as global state with a local-looking name.

Default to None, build the real value inside the function
Change the signature to roles=None ↓ None is immutable — reusing the exact same None forever is completely safe, unlike reusing a list Add one line at the top of the body: if roles is None: roles = [] ↓ this line runs fresh on EVERY call, so each caller who skips the argument gets a brand-new list Never mutate a parameter's default value in place — build the real one inside the function
Default argument values are evaluated exactly once — when the def statement runs, not each time the function is called. A def is a single executable statement, same as an assignment. Python runs it top to bottom one time to build the function object, and whatever roles=[] evaluates to at that moment is stored on the function forever, in provision_user.__defaults__, ready to be handed out — the same object — to every future call that doesn't supply its own.
A mutable default argument is a whiteboard bolted to the office wall on move-in day — not a fresh notepad torn off for each visitor. Every visitor who doesn't bring their own paper writes on that same whiteboard, and every mark they leave is still there for the next person who walks in.
You

I never passed Alice's list into Bob's call. How did her data get there?

roles=[]

You never passed me anywhere, either. I was built once, when Python read your def line, and I have been the same list ever since. Every call that skips the argument gets handed me, not a copy.

You

So the bug isn't in the function body at all?

provision_user.__defaults__

Correct — look at me between calls and you'll see it happen. I'm a tuple sitting on the function object, and my list keeps growing every time somebody appends to roles without noticing I'm the same list as last time.

The mechanism

Watch the timeline: one line runs once, then every call quietly reuses what it built.

  1. Python executes the def provision_user(...) statement — once, at import timeonce
  2. It evaluates [] right there and stores that list object on the function__defaults__
  3. provision_user('Alice') runs — no roles passed, so it borrows the stored listsame id()
  4. roles.append('BASE_USER') mutates that shared object in placemutation
  5. The mutated list is still sitting in __defaults__ after the function returnspersists
  6. provision_user('Bob') borrows the same list — now already one entry deepleaks forward

Step 2 is the one line everyone misreads. [] does not mean "an empty list, freshly built, every time this function is entered" — it means "build this list once, right now, while I'm defining the function." Every later call is just handed a reference to that one object. Nothing about calling a function normally re-runs its own signature.

def f(items=[])def g(cache={})def h(seen=set())
all three build ONE mutable object at def time ↓
one shared list/dict/setreused by every call that skips the argument, forever

It is never really "the list bug" — it is the same rule hitting three different literals. [], {}, and set() all build a real, mutable object the moment the def runs, and all three get silently shared the same way. None, 0, "", and () never show this bug, not because they're special-cased, but because nothing can mutate them in place to leave evidence behind.

provision_user('Alice') runs, then provision_user('Bob') runs, both leaving roles=[] on its default. What does bob['roles'] contain right after?

Right. There is exactly one list object behind roles=[], built when def ran. Alice's call appended to it; Bob's call borrowed that same, now-not-empty list and appended again.

That's the assumption every other mainstream language would reward you for making — a fresh default per call. Python's default is built once, at definition time, and reused by reference on every call that omits the argument.

No exception anywhere. That is what makes this bug expensive: it never crashes, it just quietly hands the wrong data to the next caller, and the code review looks completely normal.

1. The CPython Execution Pipeline

When you run python script.py, Python compiles your source to bytecode then executes it in the CPython VM — all in one process.

Source
.py text read by tokenizer
Tokens
keywords, names, literals, ops

Abstract Syntax Tree via ast module
Bytecode
.pyc file, LOAD_FAST / CALL etc.
CPython VM
frame stack, eval loop
# See the bytecode yourself:
import dis
def add(a, b):
    return a + b
dis.dis(add)
# LOAD_FAST 'a', LOAD_FAST 'b', BINARY_OP '+', RETURN_VALUE
The .pyc files in __pycache__/ are the compiled bytecode. Python skips recompilation if the source hash matches — it's a performance optimization, not security.

2. Everything Is an Object

In CPython, every Python value is a PyObject* — a C struct on the heap with a type pointer and reference count. Integers, strings, functions, classes — all objects.

Object anatomy

# Every object has:
id(x)       # memory address (CPython)
type(x)     # type object pointer
x.__class__  # same as type(x)

# Even "primitives" are objects
isinstance(42, int)   # True
isinstance("hi", str)  # True
(42).__add__(1)       # 43

Variable = name binding, not storage

# Variables are names in a namespace dict
a = 42     # 'a' → PyObject* for int(42)
b = a      # 'b' → same PyObject*, refcount+1
a = 100   # 'a' → new object; b still → 42

# Mutable objects CAN be mutated in-place
lst = [1,2]
ref = lst       # same list object
lst.append(3)  # ref sees [1,2,3] too!

3. Reference Counting & the GC

CPython tracks how many names/containers point to each object. When the count hits zero, memory is freed immediately — no GC pause for most objects.

+1assignment x = obj
+1stored in list/dict
+1passed as arg
-1del x or name rebound
-1scope exits
0freed immediately
import sys
x = object()
print(sys.getrefcount(x))  # 2 (x + getrefcount arg)
y = x
print(sys.getrefcount(x))  # 3
del y
print(sys.getrefcount(x))  # back to 2
Reference cycles (A → B → A) leak under pure refcounting. Python adds a cyclic GC (gc module) that runs periodically to collect these — but for most code, the synchronous refcount frees memory immediately.

4. LEGB Scope Rule

When Python looks up a name, it checks four scopes in order. The first match wins — no "variable hoisting" like JavaScript.

L — LocalVariables assigned inside the current functiondef f(): x = 1
E — EnclosingLocals of any enclosing (outer) function — closures live heredef outer(): x = 2; def inner(): use x
G — GlobalModule-level names; global x lets you assign to themx = 3 at module top
B — Builtinbuiltins module: len, print, range, True…print, len, type …
# Gotcha: assignment makes it Local
x = "global"
def f():
    print(x)  # UnboundLocalError! Python sees the assignment
    x = "local"  # below and marks x as local for the whole fn

# Fix: read-only reference (no assignment) or use global/nonlocal
def g():
    global x  # now g can assign to module-level x
    x = "changed"
