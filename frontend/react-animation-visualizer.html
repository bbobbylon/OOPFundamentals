React: Animation (Framer Motion)

motion components, variants & orchestration, gestures, automatic layout animations, and exit animations with AnimatePresence — declarative, spring-based motion for React.

🎬 Declarative animation: describe the target, let the library tween there

Framer Motion (now Motion) is the de-facto React animation library. Instead of stepping values over time, you render a motion element and declare initial (from), animate (to), and transition (how) — it animates the diff, defaulting to natural spring physics. Variants name reusable states so a parent can orchestrate children (staggerChildren); gestures (whileHover/whileTap/drag) and automatic layout animation (the layout prop, shared layoutId for magic-move) are first-class; and <AnimatePresence> animates exits. The rule: motion should communicate, stay subtle, and respect prefers-reduced-motion.

  • Declare the target, the library tweens — initial/animate/transition, spring by default.
  • Variants orchestrate children — name states, staggerChildren to cascade.
  • Layout + gestures are built in — layout/layoutId magic-move, whileHover/drag.
  • Exits via AnimatePresence; always respect prefers-reduced-motion.

initial / animate / transition

<motion.div initial={{ opacity: 0, y: 8 }} animate={{ opacity: 1, y: 0 }} transition={{ type: 'spring', stiffness: 300, damping: 30 }}> Welcome </motion.div>

Variants + stagger

const list = { visible: { transition: { staggerChildren: 0.05 } } } } const item = { hidden:{opacity:0}, visible:{opacity:1} } <motion.ul variants={list} initial="hidden" animate="visible"> {rows.map(r => <motion.li variants={item} .../>)} </motion.ul>

vs CSS transitions / Angular animations

CSS: great for simple hover/transition; awkward for orchestration, interruptible springs, and exit animations. Angular: @angular/animations (trigger/state/transition DSL). Motion: declarative props, real spring physics, gesture + layout + exit handled for you, and animations are interruptible (re-target mid-flight). For complex, stateful UI motion, it's far less code than hand-rolled CSS/JS.

CIAM context: Motion should clarify auth flows, not decorate them — fade/slide a login error in (a tiny shake draws the eye), stagger the admin user list as it loads, and animate a confirmation modal in/out with AnimatePresence so it doesn't pop. layoutId morphs a user row into its detail panel so context is kept, and non-essential motion is gated behind useReducedMotion() — accessibility first.

1. motion Components: initial / animate / transition

import { motion } from 'motion/react'

<motion.div
  initial={{ opacity: 0, y: 8 }}
  animate={{ opacity: 1, y: 0 }}
  transition={{ type: 'spring', stiffness: 300, damping: 30 }}
>
  Welcome back
</motion.div>

Swap any element for its motion.* version and declare states. initial is where it starts (set initial={false} to skip the mount animation), animate is the target — change it and the library tweens there, interrupting any in-flight animation smoothly. The default transition is a spring (feels organic); a tween (duration + ease) gives exact timing. Animate transforms (x,y,scale,rotate) and opacity for GPU-friendly 60fps; avoid animating layout-triggering props like width unless you use the layout prop.

Springs are interruptible and velocity-aware. If a value re-targets mid-animation, the spring carries its current velocity into the new motion — no jarring restart. That's why drag-and-release or rapidly-toggled UI feels right with springs and stuttery with fixed-duration tweens.

2. Variants — Named States & Orchestration

const list = { visible: { transition: { staggerChildren: 0.05 } } }
const item = { hidden: { opacity: 0, y: 6 }, visible: { opacity: 1, y: 0 } }

<motion.ul variants={list} initial="hidden" animate="visible">
  {users.map(u => <motion.li key={u.id} variants={item}>{u.email}</motion.li>)}
</motion.ul>

Variants are named target objects you reference by string. A parent's variant name propagates to children that define the same name, so you animate a whole tree with one prop change — and orchestrate with staggerChildren, delayChildren, or when:'beforeChildren'. This keeps animation logic declarative and out of your render JSX, and makes cascading list reveals trivial.

Variants reduce prop noise and enable orchestration you can't do inline. Without them you'd repeat initial/animate on every child and have no way to stagger. With them, the parent says "go visible" and the children cascade — the idiomatic way to animate lists, menus, and multi-step reveals.

3. Gestures

PropAnimates while…
whileHover={{ scale: 1.05 }}pointer is over the element
whileTap={{ scale: 0.95 }}pressed (pointer/touch down)
whileFocus={{ ... }}the element has keyboard focus (great for a11y)
drag / dragConstraintsbeing dragged (bounded by constraints; momentum on release)
Gesture props animate to a state for the gesture's duration, then back — no event handlers, no manual state. They compose with animate and variants. whileFocus matters for accessibility: a keyboard user sees the same affordance a mouse user gets on hover. drag gives you draggable UI (sliders, cards, sheets) with constraints and inertia for free.

4. Layout Animations & AnimatePresence

// auto-animate any layout change (reorder, resize, expand)
<motion.div layout>…</motion.div>

// "magic move" the same element between two places
<motion.div layoutId="card-42" /> // thumbnail ⇄ detail

// animate OUT on unmount
<AnimatePresence>
  {open && <motion.div exit={{ opacity: 0 }} />}
</AnimatePresence>

The layout prop makes an element smoothly animate whenever its position or size changes between renders (a list reorders, a panel expands) — Motion measures before/after and tweens the difference (FLIP). A shared layoutId across two mounted elements animates one into the other ("magic move"). And since React unmounts instantly, AnimatePresence defers removal until the child's exit animation completes — the only way to animate something leaving.

Respect motion preferences. Wrap non-essential motion in useReducedMotion() (or a CSS @media (prefers-reduced-motion: reduce)) and fall back to instant/opacity-only changes. Large movement can cause nausea/vestibular issues — honoring the OS setting is an accessibility requirement, not a nicety. And keep it subtle: motion that distracts from an auth flow is worse than none.
