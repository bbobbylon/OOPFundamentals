NoSQL Document & Wide-Column Stores — MongoDB & DynamoDB

Two more NoSQL shapes beyond Redis's key-value model: MongoDB's document store (JSON-like documents, embedded nesting) and DynamoDB's wide-column / key-value store (partition + sort keys, access-pattern-first design). Both trade the relational track's normalization and ad-hoc joins for something else — read speed at scale, in exchange for modeling your data around how you'll query it, not just what it logically is.

📦 Why do these stores ask you to model around your queries, not your entities?

Every page in the SQL & Databases track teaches you to normalize first and let the query planner figure out how to join it all back together at read time — that's the relational bet: pay a small join cost per query, in exchange for storing each fact exactly once. Document and wide-column stores make the opposite bet, because at their scale a join across machines is either impossible or ruinously slow. MongoDB lets you embed related data directly inside a parent document (an order with its line items nested right inside it) so a single document read gets you everything, no join required. DynamoDB goes further: every table has a partition key that deterministically decides which physical machine holds an item, so a "query" is really "which partition key do I already know the answer needs to live on" — decided at design time, not query time. The shared lesson: in both models, you design the schema around how the app will read the data, and figure out the entities second.

  • Embedding vs referencing (MongoDB) — embed data that's always read together; reference (store an id) data that's large, shared, or independently updated.
  • Partition key = physical placement (DynamoDB) — a poorly chosen key sends all traffic to one partition ("hot partition"); a good one spreads load evenly by design.
  • Schema-on-read, not schema-on-write — the database won't stop you from writing inconsistent documents; the application's read code is what has to cope with variation.
  • Denormalization is a deliberate trade — duplicating data (e.g. a username on every comment) avoids a join on read, at the cost of updating N copies on write.

Access patterns come first, not last

The single biggest mindset shift from relational design: with DynamoDB especially, you list every query your application will ever need to run before designing the table — because unlike Postgres, you can't bolt on a new query pattern later without redesigning keys or adding an index up front.

Consistency is often a per-request choice

DynamoDB lets each read choose eventually consistent (cheaper, default, might return slightly stale data right after a write elsewhere) or strongly consistent (costs more capacity, always reflects the latest write). MongoDB's replica-set reads have an analogous readConcern/readPreference spectrum.

CIAM angle

A user activity/audit-log feed is a natural document-store fit — each event is self-contained, rarely needs a join, and the write pattern (append-only, high volume) suits both MongoDB collections and a DynamoDB table keyed by userId (partition) + timestamp (sort), letting you fetch "this user's recent activity, newest first" in one efficient query with zero joins.

or, the "read together" rule that grows itself right past a hard limit

The problem

You followed the embedding rule exactly as written — reviews are read together with the product, so you embedded them — and eighteen months later every write to that product document starts failing.

The reviews array MongoDB eventually refuses to save

A product launches with three reviews, embedded right inside the product document the way the rule above says to: reviews: [ {...}, {...}, {...} ]. Every product read comes back with all its reviews in the same query — no second round trip. Textbook embedding win.

Fourteen months and forty thousand reviews later, productService.addReview() starts throwing BSONObj size: 16793601 is invalid. Size must be between 0 and 16793600 (16MB). Nobody touched the code. The document just grew, one $push at a time, until it hit MongoDB's hard per-document ceiling — and MongoDB doesn't warn you at 15 MB, it refuses the write outright at 16.

the embedding decision at launch ✓ every individual $push that added one review ✓ an array with no cap on how large it can grow ⚠

Embed what's read together — but only if it also has a natural, small ceiling on how large it can get.

Cap the embed, reference the overflow
Embed only a bounded slice — say, the 5 most recent or most-helpful reviews ↓ the product document now has a size ceiling that has nothing to do with how many reviews actually exist Move every review into its own reviews collection, referenced by productId ↓ the full history still exists and is fully queryable — it's just no longer forced to travel with the product on every single read And if the UI truly needs the full list on one screen, page it with its own query instead of growing one document forever
The one-sentence rule. Embedding is a bet that the embedded data has a natural size ceiling — a user's five most-recent logins, an order's line items at checkout — and any array whose size is really a function of "how long has this record existed" or "how popular has it become" will eventually outgrow that bet, right at the moment the record is successful enough for it to matter.
MongoDB's own docs call this the Massive Array anti-pattern. The fix isn't a bigger limit — it's admitting the array was never really "read together" data. It was a growing list wearing an embedded field's clothing.
You

The embedding rule said "store what's read together." Reviews are always read with the product. Why is that suddenly a problem?

MongoDB

I never promised a document could grow forever. Sixteen megabytes is a hard ceiling I enforce on every document, embedded arrays included — I don't care how sensible the relationship looked back when it had three items.

You

Couldn't you have warned me sooner — at 10 MB, say?

MongoDB

I do log large-document warnings in the slow-query log well before the limit. Nobody reads slow-query logs for a document that's still fast to read. The write only becomes visibly wrong the day it's finally too big.

The mechanism

Here's how one array field turns a perfectly healthy collection into a landmine, one $push at a time.

  1. Product ships with reviews: [] — empty, nowhere near any limitday one
  2. Every db.products.updateOne({_id}, {$push:{reviews: newReview}}) appends one more subdocumentevery review
  3. The document's on-disk size grows by roughly one review's size, every single timelinear growth
  4. MongoDB rewrites the WHOLE document on disk for every update, because a BSON document isn't a growable append-only logfull rewrite cost
  5. Long before 16 MB, both writes and reads get slower — more bytes to read, rewrite, and replicate per operationthe slow decline
  6. At 16,793,600 bytes, the next $push is rejected outright — not slow, just refusedthe hard wall

Step four is the one people miss: this isn't only a size-limit story, it's a performance story that started long before the limit. Every write to an oversized document re-serializes the entire thing — a 12 MB document with one new review costs vastly more than a 2 KB document with one new review, even though the actual new data is identical in both cases.

Read it from the outside in: a single document, containing a single array field, containing every review this product has ever received — three layers of "this seemed fine at first" wrapped around one immovable number. Nothing about the schema looked wrong at layer one; the danger was always in what layer two was allowed to become.

A users collection embeds each user's full login history as an array — loginHistory: [ {ip, ts}, ... ] — appended to on every sign-in with $push. After two years of daily logins, writes to long-tenured accounts take noticeably longer than writes to brand-new accounts, well before anyone hits an actual error. Why?

Right. A BSON document is not a growable log file — updating it means writing the whole thing back to disk, and to every replica. A two-year-old user with 700 logins embedded pays for rewriting all 700 on login #701; a brand-new user pays almost nothing for login #1.

MongoDB doesn't rebuild indexes because a single document grew — index maintenance is per-write and scoped to the indexed fields that changed, not to overall document size. This invents a mechanism that isn't real.

$push appends; it does not deduplicate, and there is no background process quietly trimming arrays to respect the 16 MB cap. Once you're near the limit, MongoDB simply rejects the next write — it never tries to rescue you first.

Where you have seen this before

An unbounded array quietly living inside a fixed-size container is a shape you'll recognize outside MongoDB too.

A JWT that embeds every role a user has ever been granted

A Spring Security Authorization: Bearer <jwt> embeds the caller's authorities as a claim so downstream services can skip a database round trip — the same "read together" bet as an embedded MongoDB array. Give an employee years of team reassignments without ever pruning stale roles, and the claims array grows until the encoded token blows past a reverse proxy's or load balancer's total request-header limit, and requests start failing with 431 Request Header Fields Too Large before your own controller code ever runs.

an identity token is still just an embedded array wearing a different file format

Kafka's max message size rejecting an oversized event

An event that embeds a growing list — every line item ever added to a long-lived cart, say — eventually crosses the broker's configured maximum message size and the producer gets a RecordTooLargeException. Same shape: a value that was "read together" data at first, denied outright once it outgrew its container's ceiling.

the container enforces a hard limit; it doesn't negotiate

PostgreSQL TOASTing an oversized jsonb column

A jsonb column holding a growing embedded array eventually gets TOASTed — Postgres's mechanism for storing oversized values out-of-line — and every update to that row still has to read and rewrite the whole TOASTed value, the identical "rewrite everything for one small change" cost that made the MongoDB document slow.

relational databases hit the same wall, just with a different name for it

The one new sentence this block adds: "read together" is not the same promise as "bounded in size," and an array with no natural ceiling will eventually outgrow the very document it was embedded to speed up.

1. MongoDB vs DynamoDB vs relational — three different bets

AxisMongoDB (document)DynamoDB (wide-column/KV)PostgreSQL (relational)
Unit of storageA JSON-like document (BSON) in a collectionAn item (map of attributes) in a tableA row in a table
SchemaFlexible — documents in one collection can differOnly the key schema is fixed; other attributes are flexibleStrict — every row conforms to the table definition
Relating dataEmbed nested data, or reference by _idDenormalize into the item, or model as composite sort keysForeign keys + JOIN at query time
Query flexibilityRich ad-hoc queries + aggregation pipelineMust query by key (or a defined index) — no ad-hoc joinsArbitrary SELECT/JOIN/aggregate via a query planner
Scaling modelHorizontal via sharding on a shard keyHorizontal by design — partition key IS the shardVertical first; horizontal (partitioning/replicas) is added complexity
DynamoDB is the strictest of the three about access patterns — MongoDB still lets you run an unindexed ad-hoc query (slowly); DynamoDB fundamentally can't answer a query that doesn't match a key or index at all. That constraint is the price of its predictable, scale-independent performance.

2. Embedding vs referencing — MongoDB's core modeling decision

✗ Over-normalized — a join-shaped habit in a store with no joins

// orders collection
{ _id: "ord_1", userId: "u42", total: 49.99 }
// lineItems collection — separate round trip needed
{ orderId: "ord_1", sku: "WIDGET", qty: 2 }
{ orderId: "ord_1", sku: "GADGET", qty: 1 }
// reading one order now needs 2 queries + app-side stitching

✓ Embedded — data that's always read together, stored together

// orders collection — one document, one read
{
  _id: "ord_1", userId: "u42", total: 49.99,
  lineItems: [
    { sku: "WIDGET", qty: 2 },
    { sku: "GADGET", qty: 1 }
  ]
}
The rule of thumb: embed what's read together and owned together; reference what's large, shared across parents, or updated independently. A product catalog entry referenced BY an order's line item (rather than embedded) is the right call — the product itself is shared across thousands of orders and changes independently of any one of them.

3. Partition key design — the decision you can't easily undo later

✗ Hot partition — low-cardinality key

// Partition key: orderStatus
// Every "PENDING" order lands on the SAME partition
PK="PENDING" → 40,000 items, one physical partition
PK="SHIPPED" → 2,000,000 items, one physical partition
// throughput for the whole table is capped by ONE partition's limit

✓ Even spread — high-cardinality key

// Partition key: orderId (unique per order)
// Sort key: createdAt (enables range queries per-order if needed)
PK="ord_88213" → 1 item, its own partition slice
PK="ord_88214" → 1 item, its own partition slice
// traffic spreads evenly across all of DynamoDB's partitions
DynamoDB spreads data across partitions by hashing the partition key — a key with only a handful of distinct values (a status enum, a boolean, a tenant flag on a single-tenant-heavy system) means only a handful of partitions ever get used, no matter how much you scale the table. High-cardinality keys (an order id, a user id) let DynamoDB actually spread the load the way it's designed to.

4. One-sentence recap

📦 Document and wide-column stores trade the relational track's normalize-then-join model for designing the schema around known access patterns — embed what MongoDB reads together, choose DynamoDB partition keys for even spread, and accept denormalization's write-fanout cost in exchange for join-free, horizontally scalable reads.
