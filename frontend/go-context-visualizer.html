Go: the context Package

Cancellation, deadlines, and request-scoped values threaded through a call tree — how Go propagates "stop now" across goroutines without leaking them.

🔗 What problem does context solve — and why is it the first parameter everywhere?

A context.Context carries three things across API boundaries and goroutines: a cancellation signal, a deadline/timeout, and request-scoped values. Every context derives from a root (context.Background()/TODO()) via WithCancel/WithTimeout/WithValue, forming a tree. The mechanic: ctx.Done() returns a channel that closes on cancel or deadline, and ctx.Err() says why; blocking work selects on it to bail the moment the caller gives up. Cancellation flows down — cancel a parent and every descendant's Done() closes, tearing down all the goroutines a request spawned. By convention ctx is the first parameter, never stored in a struct, and you always defer cancel().

  • Carries cancel + deadline + values across goroutines and API calls.
  • ctx.Done() closes on cancel/timeout; select on it to abandon work.
  • Cancellation flows down the tree — one request tears down its whole subtree.
  • First param, never stored; always defer cancel() to free resources.

Timeout + the Done() select

ctx, cancel := context.WithTimeout( parent, 2*time.Second) defer cancel() // ALWAYS select { case res := <-doWork(ctx): return res, nil case <-ctx.Done(): // fired at 2s return nil, ctx.Err() // → context.DeadlineExceeded }

WithValue for request scope

type ctxKey string const userKey ctxKey = "user" // in middleware after auth: ctx = context.WithValue(ctx, userKey, principal) // deep in a service: u, ok := ctx.Value(userKey).(*User) // typed key avoids collisions; // request-scoped data ONLY

Go context vs Java/Spring

Java: cancellation is Thread.interrupt() + checking isInterrupted(), timeouts live on each client (HttpClient.timeout), and request data hides in ThreadLocal (SecurityContextHolder). Go unifies all three in one explicit value you thread through every call. It is more verbose (ctx in every signature) but there is no hidden thread-local magic — you can always see exactly what carries cancellation and request data, which makes goroutine leaks and forgotten timeouts visible at the call site.

CIAM context: An auth gateway threads one ctx from the inbound request through token validation → JWKS fetch → user-lookup query. A 3s WithTimeout stops a slow IdP piling up goroutines; if the client disconnects, ctx.Done() closes and the in-flight DB query is cancelled — no wasted work. The principal and a trace ID ride along via WithValue, reaching every layer without a thread-local — the Go equivalent of a Spring request scope + @Transactional(timeout=3), made explicit.

1. The Constructors

FunctionReturnsUse for
context.Background()empty root contextmain, init, tests — the top of the tree
context.TODO()empty root contextplaceholder when you don't yet have one to plumb
WithCancel(parent)(ctx, cancel)manual cancellation you trigger
WithTimeout(parent, d)(ctx, cancel)cancel automatically after duration d
WithDeadline(parent, t)(ctx, cancel)cancel automatically at an absolute time t
WithValue(parent, k, v)ctxattach one request-scoped key/value
Every WithCancel/Timeout/Deadline returns a cancel func you MUST call — defer cancel() right after. Not calling it leaks the context (and a timer, for timeouts) until the parent is cancelled. go vet flags the lost cancel.

2. Done() + Err(): Making Work Cancel-Aware

// a worker that respects cancellation
func worker(ctx context.Context) error {
  for {
    select {
    case <-ctx.Done():
      return ctx.Err() // Canceled / DeadlineExceeded
    case job := <-jobs:
      process(job)
    }
  }
}

ctx.Done() is a channel that is closed (not sent to) on cancellation — a closed channel makes every receive return immediately, so every goroutine watching it unblocks at once. After Done() fires, ctx.Err() is non-nil: context.Canceled (someone called cancel) or context.DeadlineExceeded (time ran out). Standard-library calls like db.QueryContext(ctx, ...) and http.NewRequestWithContext already do this select for you.

3. WithValue — Sparingly, and With a Typed Key

DoDon't
request-scoped data: trace/request IDs, the authenticated principal, a localeoptional function parameters — pass those explicitly as arguments
use an unexported custom key type (type ctxKey string) to avoid collisionsuse a bare string key — two packages can clash on "user"
type-assert on read: v, ok := ctx.Value(k).(*User)store mutable state or dependencies (loggers, DB handles) — inject those
WithValue is untyped (any), so a wrong key or type silently returns nil. Wrap it: func UserFrom(ctx) (*User, bool) as the single typed accessor keeps the rest of the code honest.

4. Cancellation Propagates Down the Tree

Each WithX child links to its parent. Cancelling a context closes its Done() and the Done() of every context derived from it — recursively. A child also cancels if its parent does, or if its own deadline hits first (whichever comes first).

// one request → many derived children → one cancel tears it all down
reqCtx, cancel := context.WithTimeout(r.Context(), 5*time.Second)
defer cancel()

g, gctx := errgroup.WithContext(reqCtx) // derives gctx
g.Go(func() error { return fetchProfile(gctx, id) })
g.Go(func() error { return fetchRoles(gctx, id) })
err := g.Wait() // if either fails, gctx cancels the other
golang.org/x/sync/errgroup is the idiomatic way to run parallel context-aware sub-calls: the first error cancels the shared context, so the siblings stop immediately instead of finishing work nobody will use.
