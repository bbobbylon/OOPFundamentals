Synthetic Events

onClick is not a DOM listener on your button. React attaches one listener at the root and replays a cross-browser SyntheticEvent through the fiber tree. Watch the delegation, the capture/bubble phases, and the passive-listener traps.

🖱️ What is React's event system — and why is onClick not really a DOM event listener?

<button onClick> does NOT attach a listener to that button. React attaches a single listener to the root container; every event bubbles there, and React walks the fiber tree from the target up, running matching handlers in capture-then-bubble order — event delegation. Your handler receives a SyntheticEvent, a cross-browser wrapper where target/preventDefault/stopPropagation behave consistently. Gotcha: stopPropagation() only stops the React fiber tree, not the native event reaching root — use nativeEvent.stopImmediatePropagation() for that. And React 17+ attaches many listeners as passive, so to preventDefault on scroll/touch you need a direct DOM listener via useEffect.

  • One root listener, not per element — events delegate up to the createRoot container.
  • React walks the fiber tree — capture phase down, bubble phase up.
  • SyntheticEvent normalizes browsers; nativeEvent is the real one underneath.
  • stopPropagation() is React-tree-only; passive listeners block preventDefault on scroll/touch.

The problem

You followed this page's own fix for onWheel — a native addEventListener via a ref — and now two setState calls in that handler behave differently than your onClick handlers ever did.

The fix from section 4 that quietly un-batches your updates

Section 4 above told you the truth: React marks onWheel/onTouchMove as passive, so preventDefault() inside them does nothing — the sanctioned fix is a real addEventListener('wheel', handler, {passive:false}) on a ref, bypassing React's synthetic system entirely. You do exactly that, and inside your native handler you call setZoom(z => z+1) and setDirty(true) back to back.

On React 17, that handler runs OUTSIDE React's batching — those two setState calls trigger two separate synchronous re-renders, back to back, on every wheel tick. Only setState calls made INSIDE a React-attached synthetic event handler were batched in 17; anything from a native listener, a setTimeout, or a promise .then() got one render per call. Your delegated onClick handlers were always fine — it's specifically the escape hatch this page told you to reach for that loses batching.

The one-sentence rule. Before React 18, "batched" effectively meant "inside a handler React itself attached"; React 18's automatic batching changes the rule to "any setState call, from any origin, batches into one render unless you explicitly opt out with flushSync" — which matters the moment you write a native listener, a setTimeout callback, or a .then(), all of which this very page walks you through.
Batching before 18 had a WHITELIST — React's own synthetic handlers. Batching in 18 has a BLACKLIST — flushSync, and nothing else. If your mental model is still "only onClick batches," React 18 already proved you wrong; you just haven't hit the native handler that shows it yet.

Where you have seen this before

Coalescing many small operations into one flush is a trick every performance-minded system reaches for eventually.

Angular Signals' batched effect scheduling

Writing to several Angular signals synchronously in one tick doesn't re-run every dependent effect or re-render the template once per set() — Angular schedules the flush to happen once, after the current work finishes. Same shape as React's automatic batching, solved for a different reactivity model.

many synchronous writes, one scheduled flush

Disk write buffering

An OS buffers many small writes in memory and flushes them to disk together instead of hitting the disk on every single write() call — trading a little latency for far less overhead. React's batching makes the identical trade at the render layer: hold several state updates for one tick, then flush them as a single render.

many small writes → one flush

TCP's Nagle's algorithm

TCP can buffer several small outgoing writes and send them as one packet instead of a packet per write() call, trading a tiny delay for far less network overhead. React's batching makes the same trade: several state updates become one visible re-render instead of several half-finished ones.

1. There is no listener on your element

When you write <button onClick={fn}>, React does not call button.addEventListener('click', fn). It records fn against the button's fiber and attaches a single click listener at the React root container. Every click in the app bubbles up to that one listener, where React figures out which fibers should receive a synthetic event.

React versionWhere the delegated listeners live
≤ 16document (one set of listeners for the whole page)
17+the root DOM container you passed to createRoot — so multiple React versions and portals can coexist cleanly
Why delegate? One listener per event type instead of thousands. A 10,000-row table with an onClick on every row costs React zero extra native listeners — it is still just the one at the root. It also means dynamically added elements work instantly with no listener wiring.

2. Capture and bubble, simulated on the fiber tree

React reconstructs the W3C event flow on its own tree. For onClickCapture it walks root → target; for onClick it walks target → root. e.stopPropagation() halts the React traversal.

<div onClickCapture={a} onClick={d}> // a (capture, 1st) … d (bubble, 4th)
  <button onClickCapture={b} onClick={c}> // b (capture, 2nd) … c (bubble, 3rd)
    Click
  </button>
</div>
// order: a → b → c → d (capture down, then bubble up)

3. SyntheticEvent fields

MemberWhat it gives you
e.targetthe DOM element the event originated on
e.currentTargetthe element whose handler is running (changes as it propagates)
e.preventDefault()cancel the default action (form submit, link navigation)
e.stopPropagation()stop the synthetic event from reaching parent handlers
e.nativeEventthe underlying real browser event, if you need it
Event pooling is gone (React 17+). React 16 reused one SyntheticEvent object and nulled its fields after the handler returned, so reading e.target in an async callback required e.persist(). React 17 removed pooling — you can safely keep and read the event asynchronously now. If you see e.persist() in a tutorial, it is legacy.

TrapReality & fix

onScroll does not bubble (17+)Put onScroll directly on the scrolling element, not an ancestor
onFocus/onBlur do bubble in ReactReact implements them on focusin/focusout, unlike raw DOM focus/blur
