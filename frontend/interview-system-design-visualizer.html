System Design — Interview Frameworks & Patterns

Master the step-by-step framework for system design interviews. Common system walkthroughs, trade-off tables, and structured answers to the top 10 questions.

🏛️ What is system design — and how do you structure a 45-minute interview to cover requirements, scale, components, and trade-offs without being cut short?

System design interviews evaluate your ability to architect large-scale distributed systems. Unlike coding interviews (specific problems with correct answers), system design is open-ended — there's no single right answer, and interviewers are assessing your breadth of knowledge, your ability to navigate trade-offs, and whether you communicate like a senior engineer. The most common failure mode: diving into implementation details too early, before establishing requirements and scale. The STAR framework for system design: Scope (clarify requirements), Traffic estimation (scale calculation), Architecture (high-level components), Refinement (deep dives on bottlenecks and trade-offs). Step 1 — Requirements clarification (5 min): functional requirements (what does the system do?), non-functional requirements (scale, availability, latency, consistency), and constraints (read-heavy or write-heavy? global or regional?). Always ask before designing. Step 2 — Scale estimation (5 min): Daily Active Users × requests/user/day = requests/day. Divide by 86,400 = QPS (queries per second). Multiply by average data per request = storage growth per day. These numbers drive every architectural decision. 1M DAU × 10 requests = 10M req/day = ~115 QPS (single server can handle). 100M DAU = 11,574 QPS (needs horizontal scaling, load balancing, distributed cache). Step 3 — High-level architecture (15 min): draw the key components (clients, load balancer, application servers, database, cache, message queue, CDN). Show data flow. For stateless application servers: any server can handle any request → horizontal scaling. For databases: start with a single relational DB (PostgreSQL), then discuss when and why to shard, replicate, or add NoSQL. Key trade-offs to know cold: SQL vs NoSQL (strong consistency vs eventual, relational vs document/key-value). Horizontal vs vertical scaling. Cache-aside vs write-through vs write-behind. Strong consistency vs high availability (CAP theorem: you can't have both during a network partition). Synchronous vs asynchronous (HTTP request/response vs message queue for decoupling). CDN for static assets. Redis for distributed cache + session store. Kafka for event streaming at scale. Step 4 — Deep dives (15-20 min): pick the 2-3 most interesting/risky components and go deeper. For a URL shortener: how does the ID generation work at scale? (Snowflake ID, hash + Base62). For a social media feed: how is the feed ranked and served? (pre-computed fan-out vs pull-on-read). For a payment system: how is idempotency guaranteed? (idempotency key in request, stored in Redis).

The 6-Step System Design Framework Use Every Time

Interviewers evaluate your process as much as your solution. Always follow this order. Spend ~2-3 minutes per step.

STAR Method for System Design Answers

S — Situation (Requirements)

Clarify functional and non-functional requirements. Ask: "Who uses this? What's the scale? Any SLA requirements?" Don't assume — ask first.

T — Task (Capacity Estimation)

Estimate DAU, QPS, storage, bandwidth. Use round numbers: 1M DAU × 10 requests/day = ~100 QPS. Show math to the interviewer.

A — Action (Design & Components)

Draw the architecture: clients, LB, API gateway, services, databases, cache, CDN. Explain each component's role. Start simple, then scale.

R — Result (Trade-offs & Scaling)

Discuss trade-offs explicitly: consistency vs availability, cost vs performance. Propose how to handle hotspots, failures, and future scale.

URL Shortener — Full Walkthrough Classic Interview

Requirements

Functional:
• POST /shorten → short URL
• GET /{code} → 301/302 redirect
• Custom aliases (optional)
• Expiry dates (optional)

Non-Functional:
• 100M URLs/day writes, 10B reads/day
• Read:Write = 100:1
• <10ms redirect latency
• URLs never change once created
• 5 year retention

Capacity Estimation

Writes: 100M/day ÷ 86,400s = ~1,160 QPS
Reads: 10B/day ÷ 86,400s = ~115,000 QPS
Storage (5yr): 100M × 365 × 5 = 182B URLs
Per URL ~500 bytes: ~91 TB
Bandwidth: 115K × 500B = 57.5 MB/s read

Short Code Generation

Base62 encoding of a unique ID:
Characters: [a-z A-Z 0-9] = 62 chars
6 chars: 62⁵ = 56B combinations → enough for 182B URLs
7 chars: 62⁶ = 3.5T → safer margin
String BASE62 = "abcdefghijklmnopqrstuvwxyzABCDEFGHIJKLMNOPQRSTUVWXYZ0123456789"; String encode(long num) { StringBuilder sb = new StringBuilder(); while (num > 0) { sb.append(BASE62.charAt((int)(num % 62))); num /= 62; } return sb.reverse().toString(); } // ID from distributed ID gen (Snowflake) // Snowflake: 64-bit = timestamp+datacenter+seq
Collision risk with hashing: If you hash the URL (MD5/SHA), you get 128-bit hash, take first 7 chars. Risk: hash collision for two different URLs. Solution: check DB; if collision, append counter and retry.

Twitter Feed (News Feed) — Walkthrough

The Core Problem

When a user opens Twitter, they see tweets from accounts they follow, ordered by time (or relevance). The challenge: a celebrity may have 10M followers. When they tweet, how do you update 10M feeds?

Approach 1: Fan-out on Write (Push)

When user A posts, immediately write to all follower feeds in cache. Feed reads are O(1) — just read the pre-built feed. Problem: celebrity with 10M followers = 10M cache writes per tweet (write amplification).

Best for: Regular users. Fast reads, slow writes. Predictable read latency.

Approach 2: Fan-out on Read (Pull)

When user B opens their feed, fetch tweets from all accounts they follow and merge them. Problem: if B follows 500 accounts, that's 500 DB reads per feed load (read amplification).

Best for: Celebrities or inactive users. No write overhead, but slow reads under load.

Hybrid Approach (Twitter's actual approach)

Strategy:
1. Regular users (<100K followers): fan-out on write to followers' feed caches.
2. Celebrities (100K+ followers): fan-out on read when their followers open the feed.
3. When rendering feed: merge pre-built feed + real-time fetch of celebrity tweets.

Result: 99% of users get instant reads (push). Celebrity tweets are merged in at read time (pull). No write avalanche from celebrity posts.

Rate Limiter — Algorithms & Design

Token Bucket Algorithm

A bucket holds tokens. Tokens refill at a fixed rate. Each request consumes one token. If bucket is empty, reject the request. Allows bursts up to bucket capacity.

class TokenBucket { private double tokens; private double capacity; private double refillRate; // per second private long lastRefill; synchronized boolean allow() { refill(); if (tokens >= 1) { tokens--; return true; // allow } return false; // rate limit } private void refill() { long now = System.currentTimeMillis(); double elapsed = (now - lastRefill) / 1000.0; tokens = Math.min(capacity, tokens + elapsed * refillRate); lastRefill = now; } }

Sliding Window Log Algorithm

Store a log of request timestamps. For each request, remove old timestamps outside the window, count remaining — if below limit, allow. Most accurate but memory-intensive.

// Redis implementation (atomic Lua script) ZADD {key} {now} {now} // add timestamp ZREMRANGEBYSCORE {key} 0 // remove old {now - windowMs} count = ZCARD {key} // count in window EXPIRE {key} {windowSeconds} if count > limit: return 429 Too Many Requests else: return 200 OK
Distributed rate limiter: Store state in Redis (centralized). All API gateway nodes share the same Redis, ensuring consistent limits across the fleet. Use Redis Lua scripts for atomicity.

CAP Theorem

A distributed system can guarantee at most two of these three properties simultaneously: Consistency, Availability, Partition Tolerance. Since network partitions always happen in real systems, you must choose: CP or AP.

C — Consistency

Every read receives the most recent write (or an error). All nodes see the same data at the same time. Example: a bank balance — every read must reflect all prior writes.

MongoDB (strong)
HBase
ZooKeeper

A — Availability

Every request receives a response (possibly stale). The system is always up, even if some nodes are unreachable. Example: a social media feed can show slightly stale data but must always respond.

Cassandra
DynamoDB
CouchDB

P — Partition Tolerance

The system continues to operate even when network messages between nodes are lost. In modern distributed systems, P is non-negotiable. So the real choice is between C and A when a partition occurs.

PACELC extends CAP: Even without a partition, you must choose between Latency and Consistency. Cassandra: PA/EL. MySQL: PC/EC.

Key System Design Concepts

Caching Strategies

Cache-Aside (Lazy Loading): App checks cache first; on miss, reads DB and populates cache. Simple, tolerates cache failure. Cold start problem.

Write-Through: Write to cache and DB simultaneously. No stale data. Extra write latency.

Write-Behind (Write-Back): Write to cache, async flush to DB. Fast writes, risk of data loss on cache crash.

Read-Through: Cache sits between app and DB; cache fetches on miss. App always talks to cache.

CDN

CDN (Content Delivery Network) caches static assets at edge servers close to users. Reduces latency (300ms → 10ms) and offloads origin servers. Cache-Control headers control TTL. Used for: images, JS/CSS, video, API responses with long TTL.

Load Balancing

Round Robin: Cycle through servers equally. Simple, no state needed.
Least Connections: Route to server with fewest active connections. Good for varying request times.
IP Hash: Hash client IP → consistent server. Useful for sticky sessions.
Weighted: Assign weights to servers based on capacity.

Database Sharding

Horizontal partitioning: split data across multiple DB instances (shards). Each shard holds a subset of data. Shard key determines which shard holds a record. Challenges: cross-shard joins, resharding (consistent hashing helps), hotspot shards. Famous patterns: by user ID, by geography, by hash.

Message Queues & Microservices Patterns

Message Queue Use Cases

  • Decouple producers from consumers
  • Handle traffic spikes (buffer)
  • Async processing (email, notifications)
  • Fan-out (one event, many consumers)
  • Retry failed tasks
  • Kafka, RabbitMQ, SQS, Pub/Sub

Circuit Breaker

When a downstream service fails repeatedly, the circuit "opens" and short-circuits calls — returning cached/default response immediately instead of waiting for timeout. After a cooldown, it "half-opens" to test recovery. Prevents cascading failures.

Service Discovery

In microservices, instances come and go. Service registry (Consul, Eureka, etcd) tracks live instances. Clients query registry to find endpoints. Client-side discovery: client picks from registry. Server-side: LB queries registry.
