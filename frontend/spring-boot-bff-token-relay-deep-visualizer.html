BFF & Token Relay

The Angular auth pages keep tokens in the browser — convenient, but any XSS can read them. A Backend-for-Frontend flips that: a small server owns the tokens, the browser holds only an httpOnly session cookie it can't read, and the BFF relays the access token onto every downstream call. You trade a bit of server state for tokens that JavaScript can never touch.

What is the BFF pattern — and why do high-security CIAM apps use it instead of storing tokens in the browser?

The standard Angular OIDC flow stores tokens in sessionStorage or localStorage. This is convenient but has a critical weakness: any JavaScript running on the page — including injected malicious scripts (XSS) — can read localStorage and steal the access token. The Backend-for-Frontend (BFF) pattern removes tokens from the browser entirely. A small server sits between Angular and the API. Angular authenticates with the BFF, the BFF completes the OIDC flow and stores the tokens server-side (in Redis or an encrypted session), then sets an httpOnly session cookie in the browser. httpOnly means JavaScript literally cannot read the cookie — document.cookie won't show it. Every Angular API call goes through the BFF (same origin, so the cookie is sent automatically), the BFF reads the stored access token and relays it to the downstream API. XSS attack: steals the httpOnly cookie (impossible with JS) or the access token (never in the browser). The tradeoff: the BFF is a new server component to build, deploy, and scale.

The flow

1. Angular → GET /bff/login → BFF redirects to Ping/Entra OIDC. 2. User authenticates at IDP. 3. IDP → callback to BFF with code. 4. BFF exchanges code for tokens, stores them in Redis session. 5. BFF sets Set-Cookie: SESSION=abc; httpOnly; Secure; SameSite=Lax. 6. Angular calls GET /bff/api/users (cookie sent automatically). 7. BFF reads token from Redis, adds Authorization: Bearer ..., proxies to api:8080/api/users. 8. Response returned to Angular.

CSRF with BFF

When you use cookies (BFF pattern), you must re-enable CSRF protection — the very attack that was safe to ignore with bearer tokens is now possible again. Use Spring Security's CSRF token in a readable cookie: CookieCsrfTokenRepository.withHttpOnlyFalse() — sets a readable XSRF-TOKEN cookie that Angular reads and sends back as X-XSRF-TOKEN header. Angular's HttpClient does this automatically if configured.

BFF implementations

Spring Boot + Spring Cloud Gateway as BFF: spring-boot-starter-oauth2-client handles the OIDC flow, TokenRelay= filter adds the Bearer token to proxied requests. Alternative: Spring Authorization Server's BFF support (Spring 6.4+). Lightweight alternative: use a dedicated BFF library like the OAuth2 Proxy or the Spring Security BFF reference implementation. The pattern is the same regardless of tool.

When to use BFF vs. bearer tokens: Bearer tokens in Angular sessionStorage: fine for internal tools, low-risk apps, or when you control all content on the page (no third-party scripts). BFF with httpOnly cookies: required for high-security apps handling PII, financial data, or regulated identity data. If your CIAM app is customer-facing and handles sensitive identity data, BFF is the right architecture. The extra BFF server complexity is justified by eliminating token theft via XSS.

1. Why move the tokens off the browser

In a public SPA the access/refresh tokens live in JS (memory or localStorage). That's the single biggest XSS prize: one injected script and the attacker has a working bearer token. A BFF removes the prize — tokens sit in a server-side session, and the browser gets only an opaque, httpOnly cookie.

3. How a Spring BFF is built

The BFF is the OAuth2 client

# the BFF runs the Auth Code flow & keeps tokens in the session
spring.security.oauth2.client:
  registration.idm:
    client-id: devhub-bff
    client-secret: ${BFF_SECRET}      # confidential!
    authorization-grant-type: authorization_code
    scope: openid, profile, api.read
  provider.idm.issuer-uri: https://auth…/as

Browser ↔ BFF is a normal cookie session (oauth2Login()). The SPA never sees a token.

Relay the access token downstream

// Spring Cloud Gateway: one filter does it
spring.cloud.gateway.routes:
  - id: api
    uri: https://api.internal
    predicates: [ Path=/api/** ]
    filters: [ TokenRelay ]   // ← adds Bearer

Or do it by hand with OAuth2AuthorizedClientManager + a RestClient interceptor — exactly the on-behalf-of pattern from the @HttpExchange page.

4. The trade-off you're accepting

  • CSRF is back. Cookies are sent automatically by the browser, so a BFF needs CSRF protection again (Spring's CookieCsrfTokenRepository + a double-submit token, and SameSite=Lax/Strict on the session cookie). The token-in-header SPA didn't need this.
  • Server state. You now hold sessions — sticky sessions or a shared store (Spring Session + Redis) once you run more than one instance.
  • Still validate at the resource server. The BFF relays a real access token; the API behind it must still validate the JWT and run @PreAuthorize. The BFF protects the tokens, not the API.
  • When to choose it: high-value/regulated apps (finance, health, CIAM admin consoles) where "no tokens in the browser" is worth the session machinery. A plain SPA with rotating refresh tokens is fine for lower-risk apps.

5. Where it sits in the round-trip

Browser (Angular)        BFF (Spring)              Resource server
  │  cookie: SESSION  ──▶   │  looks up tokens         │
  │  (httpOnly)             │  Authorization: Bearer ──▶  validates JWT
  │  ◀── JSON ──────────────│  ◀──────────────── 200 ──│  @PreAuthorize
  no token in JS ✓          tokens live here           enforces access

The browser talks cookies to the BFF; the BFF talks bearer tokens to the API. Two trust boundaries, and the token never crosses into JavaScript.

6. One-sentence recap

🛡️ A Backend-for-Frontend makes a confidential Spring app the OAuth2 client: the browser holds only an httpOnly session cookie (unreadable by JS, so XSS can't steal a token), the BFF keeps the access/refresh tokens server-side and relays the access token as a Bearer onto each downstream call (Spring Cloud Gateway's TokenRelay filter or OAuth2AuthorizedClientManager) — you pay for it with CSRF defense + session state, and the resource server still validates the JWT and enforces @PreAuthorize on every request.
