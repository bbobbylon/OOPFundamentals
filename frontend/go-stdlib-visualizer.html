Go: Standard Library Tour

The four packages you'll touch in almost every Go program: encoding/json, the io.Reader/Writer abstraction, time, and strings/strconv/fmt.

🧰 Why Go's standard library lets most services ship with almost no dependencies

Go's stdlib is unusually complete — a production HTTP/JSON service often needs zero third-party libs. Four packages do most of it. encoding/json marshals/unmarshals via json:"..." struct tags (only exported fields). io defines two tiny interfaces — Reader and Writer — that files, sockets, HTTP bodies, gzip and crypto all implement, so io.Copy(dst, src) streams reader→writer in constant memory like Unix pipes. time gives time.Time, the type-safe time.Duration (2 * time.Second), and the famous reference-date layout (2006-01-02 15:04:05). And strings/strconv/fmt handle text (strings.Builder, number⇄string, %v/%+v/%q/%T). Master these four and you can build most backends framework-free.

  • encoding/json — tag-driven marshal/unmarshal; exported fields only.
  • io.Reader/Writer compose everything — io.Copy streams in constant memory.
  • time — type-safe Duration; the 2006-01-02 reference-date layout.
  • strings/strconv/fmt — builder, conversions, formatting verbs.

Or: the "obviously correct" error-check order that eats your last chunk of data.

The problem

Go trains you to check err before you touch anything else. For io.Reader, that habit throws away real bytes.

The response body that's always missing its last few bytes

You stream a webhook payload with the pattern every other Go error check taught you: n, err := r.Read(buf); if err != nil { return err }; process(buf[:n]). It works in every manual test — small payloads, local files, no surprises.

In production, against a real network stream, some responses come back truncated by exactly the last chunk. The cause: io.Reader.Read is documented to sometimes return n > 0 bytes AND a non-nil error (often io.EOF) from the SAME call — the final read of a stream can carry both "here are your last 12 bytes" and "and there's nothing after them" at once. Checking err != nil first and returning immediately means process(buf[:n]) never runs for that final, valid chunk.

error-first checking ✓ everywhere else in Go works against small local files ✓ the LAST Read() call of a stream ⚠

io.Reader's own doc comment says it outright: "callers should always process the n > 0 bytes returned before considering the error err." Not sometimes — always.

Process n before you branch on err
Always run process(buf[:n]) first, unconditionally, whenever n > 0 ↓ those bytes are valid and yours whether or not err is also set THEN check err — io.EOF means "stop looping," any other error means "something broke" ↓ EOF is not a failure, it's the stream's normal "no more data" signal Or skip hand-rolled loops entirely — io.ReadAll / io.Copy already get this order right
Read() is the one common Go API where err != nil does not mean "ignore everything else in this return." Most idiomatic Go functions promise zero-value results when they error, which is exactly why if err != nil { return err } is safe almost everywhere. io.Reader is the documented exception: a non-nil error can arrive bundled with real, valid, non-zero data in the very same call.
Most Go functions are "all or nothing": error means the other return values are garbage, ignore them. io.Reader is "some, then done": it can hand you real bytes and its resignation letter in the same envelope. Read the letter after you've counted the bytes, not instead of counting them.

io.Reader

For almost every function, yes — please keep doing that everywhere else. I'm the documented exception: my own doc comment tells implementers they're allowed to return n > 0 and a non-nil error together, and tells callers to handle n first.

You

Why would you even do that instead of returning the error cleanly on the next call?

io.Reader

Because the underlying data often ends exactly at a chunk boundary — the same read that hits the end of the file or socket is frequently the read that also returns the last few bytes. Splitting that into two separate calls would just move the same complexity somewhere else.

The mechanism

Trace one Read() call against a stream that ends exactly here.

  1. buf := make([]byte, 4096); n, err := r.Read(buf) — reading a chunked HTTP bodycall Read
  2. The underlying socket has exactly 12 bytes left, then closes12 bytes remain
  3. Read copies those 12 bytes into buf and sets n = 12n = 12
  4. Read also detects end-of-stream on this same call and sets err = io.EOFerr = io.EOF, same call
  5. if err != nil { return err } fires here — before buf[:12] is ever touchedearly return
  6. Those 12 real bytes are gone: never processed, never logged, no error mentions themsilently dropped

Steps 3 and 4 happening on the SAME call is the entire mechanism — there's no separate "final data" call and "EOF" call to reorder around. Both facts arrive together, in one (n, err) pair, and it's on the caller to unpack them in the right order.

reading a gzip-compressed responsea TCP socket closing mid-chunka chunked HTTP body's final segment
Read() returns n > 0 and a non-nil err together ↓
the last chunk silently vanishesone root cause, three unrelated-looking bug reports

Three bug reports that look nothing alike in a ticket queue — "gzip output is truncated," "the last websocket frame is missing," "file upload is 12 bytes short" — often trace back to this exact same one-line mistake at three different call sites.

n, err := r.Read(buf) returns n = 8 and err = io.EOF in the same call, on a stream with exactly 8 bytes left. Following io.Reader's own documented guidance, what should the caller do?

This is exactly what the io.Reader doc comment recommends: process the n bytes you got, unconditionally, then look at err — and io.EOF specifically means the stream ended cleanly, a signal to stop looping, not an error to bubble up.

err != nil does NOT mean "the data is garbage" for Read() the way it does for almost every other Go function — that's precisely the trap. And io.EOF is the normal, expected end-of-stream signal, not a failure worth reporting as one.

There is no "real" final chunk waiting in a later call — those 8 bytes ARE the final chunk, delivered together with the EOF signal in this exact call. Calling Read() again on an already-exhausted reader typically just returns (0, io.EOF) with nothing new.

Where you have seen this before

"The last item and the end-signal arrive in the same message" shows up anywhere something streams to completion.

Java's InputStream.read() splits it into two calls

Java's InputStream keeps "last real bytes" and "end of stream" as two separate calls — a read returning the final bytes, then a LATER read returning -1. Go collapsing them into one call is a genuine design difference, and porting Java-shaped stream-reading habits into Go reproduces exactly this bug.

the two ecosystems split this differently — check which one you're in

SQL cursors: the last fetch and "no more rows"

Some database drivers signal "this is the last row" as a flag alongside the row itself, rather than as a separate empty fetch — code that checks "are there more rows?" before reading the current one can skip the final row the same way.

end-of-data bundled with the last real item, not sent separately

A Kafka consumer's last record in a poll batch

A poll() call can return a batch where the final record coincides with the consumer reaching the end of an assigned partition — code that checks "is this partition done?" before processing every record in the batch can drop that last one, the same shape as ignoring Read()'s n on an EOF call.

batch-plus-status-flag APIs hide this same ordering trap

1. encoding/json

type User struct {
  ID int `json:"id"`
  Email string `json:"email"`
  Roles []string `json:"roles,omitempty"`
  pw string // unexported → never marshaled
}
b, _ := json.Marshal(u) // struct → []byte
var u2 User
err := json.Unmarshal(b, &u2) // []byte → struct (pass &)

Marshal/Unmarshal are tag-driven. omitempty drops zero values; json:"-" excludes a field entirely; unexported fields are invisible to JSON. Unknown JSON keys are silently ignored on decode (use Decoder.DisallowUnknownFields() to reject them). For huge or streaming payloads, use json.NewDecoder(r).Decode(&v) / json.NewEncoder(w).Encode(v) on an io.Reader/Writer instead of buffering.

Decoding into any turns every number into float64. json.Unmarshal(b, &m) where m is map[string]any gives you float64 for 42 — so a JWT exp read this way needs int64(v.(float64)). Decode into a typed struct to avoid the surprise.

2. io.Reader / io.Writer — Compose Like Pipes

InterfaceMethodImplemented by
io.ReaderRead(p []byte) (n int, err error)files, net.Conn, http body, strings.Reader, bytes.Buffer, gzip.Reader…
io.WriterWrite(p []byte) (n int, err error)files, http.ResponseWriter, bytes.Buffer, gzip.Writer, hash.Hash…
io.Copy(dst, src) streams any Reader into any Writer in constant memory, and decorators wrap each other: gzip.NewReader(bufio.NewReader(file)), io.MultiWriter(w1, w2) (tee), io.TeeReader. Read returns io.EOF at the end — that's a normal signal, not a failure. This tiny-interface design is why the whole stdlib plugs together.

3. time — Time, Duration, and the Reference Layout

now := time.Now()
d := 2 * time.Second // Duration is typed ns
later := now.Add(d)
elapsed := time.Since(start) // uses monotonic clock

// format/parse by the reference date:
// Mon Jan 2 15:04:05 MST 2006
s := now.Format("2006-01-02T15:04:05Z07:00") // = time.RFC3339
t, err := time.Parse(time.RFC3339, s)

A Duration is a typed int64 of nanoseconds, so arithmetic is unit-safe (5 * time.Minute). Formatting uses the magic reference time 01/02 03:04:05PM '06 -0700 — you write the layout as if formatting that exact date. Prefer the predefined layouts (time.RFC3339). For timeouts pair with context.WithTimeout; for periodic work use time.NewTicker (and Stop() it).

Measure elapsed time with time.Since, not by subtracting wall clocks. time.Now() carries a monotonic reading that's immune to NTP adjustments and DST; time.Since(start) uses it, so a clock jump can't produce a negative or wrong duration.
