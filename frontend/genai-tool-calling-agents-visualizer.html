Tool Use & Agents — Function Calling & the Plan/Act/Observe Loop

How an LLM reaches outside its own weights: structured tool definitions, the model emitting JSON instead of prose, the application executing the real work, and the plan → act → observe loop that turns a single Q&A model into an agent.

🛠️ What is "tool use" — and why does an LLM need it at all?

An LLM only knows what was in its training data plus whatever text is in its current context window — it can't check today's weather, query your database, or send an email. Tool use (a.k.a. function calling) closes that gap: you hand the model a list of tool definitions — a name, a natural-language description, and a JSON Schema describing the arguments — alongside the user's message. If the model decides a tool is needed, it doesn't call anything itself; it emits a structured JSON object naming the tool and the arguments. Your application code is the one that actually executes the function — hits the API, queries the database, runs the calculation — then feeds the result back to the model as a new message so it can continue reasoning or answer the user. Chain that cycle — decide what to do, do it, look at what happened, decide again — and you get an agent: a model that can complete multi-step tasks no single prompt could answer alone. This page teaches the general mechanism; the Claude Code visualizer shows one concrete, production example of this same loop (edit → test → verify) applied to a coding agent specifically.

  • Tools are JSON Schemas, not code — the model only ever sees/emits structured text.
  • The model decides; your app executes — the LLM never touches a network call, a DB, or a filesystem directly.
  • Plan → Act → Observe → repeat is the general agent loop — the same shape as Claude Code's own cycle, generalized.
  • Independent tool calls can run in parallel; dependent ones must run in sequence, one result feeding the next call's arguments.
  • Tool credentials need the SAME least-privilege thinking as OAuth scopes — an agent is a new authenticated actor, not an extension of your admin key.

{ "name": "get_weather", "description": "Get current weather for a city. CIAM lens: An agent that can call tools is a new authenticated actor, not a passthrough for your service's own privileges. Scope every tool's credential to exactly what the current user/session is allowed to do — the same least-privilege discipline as an OAuth access token's scopes — never attach a blanket admin key "to be safe." Scenario 4 below walks through exactly why that shortcut turns a prompt-injection bug into a data breach.

The problem

The loop above already tells you to cap iterations. It doesn't tell you WHY an uncapped agent gets stuck re-calling the exact same broken tool in the first place.

The rate-limited tool that gets called nineteen more times

Your agent calls lookup_account(email). The downstream API is rate-limited and returns {"error": "429 Too Many Requests, retry after 30s"}. Your loop does exactly what the code walkthrough above shows: it appends that result as a role: "tool" message and lets the model plan again — the same OBSERVE step that works perfectly for a successful result.

The model reads "retry after 30s" as new information about the task, not as a diagnostic about the SYSTEM. It has no built-in sense of wall-clock time passing between calls, and no signal that this message is fundamentally different in kind from a normal tool result — so it does the only thing "retry" ever means to it: it calls lookup_account(email) again, immediately, with the same arguments. The API is still rate-limited. It gets the same error back. It tries again.

tool schema followed correctly ✓ argument parsing worked ✓ error content treated identically to success content ⚠

Nothing crashed. The loop just found a message it could technically keep responding to, forever.

Make errors look like errors, not like data
Tag tool failures distinctly from tool successes in what gets fed back ↓ a structured {"status":"error","retryable":false,"reason":"rate_limited"} gives the model something to reason ABOUT the failure with, instead of one more fact to act on Have your app — not the model — own retry/backoff logic for known-retryable failures ↓ your code can actually sleep 30 real seconds; the model can only pretend to, by immediately calling again Cap consecutive identical tool calls, separately from the overall iteration budget ↓ the same call with the same arguments twice in a row is close to diagnostic on its own — stop the loop and surface it rather than letting it burn through the whole iteration budget on one stuck tool
The one-sentence rule. A tool result and a tool error travel back into the model through the exact same channel — a plain role: "tool" message — so unless your app marks the difference explicitly, the model has no way to tell "here's your answer" apart from "here's why that didn't work," and it will treat both as something to act on.
An error string fed back raw is a message with no return address — the model can't tell if it's data about the world or a report about itself, so it defaults to treating it as the former.

The mechanism

This isn't a crash — it's a loop that keeps finding a reason to run again.

  1. Agent calls lookup_account(email)ACT
  2. API returns 429, your code appends the raw error text as a normal role: "tool" messageOBSERVE
  3. Model re-plans over the updated history, including that messagePLAN
  4. The error text reads exactly like actionable content — "retry after 30s" — with no marker saying otherwiseno error/success distinction
  5. Model emits the identical lookup_account(email) call againACT, again
  6. Same rate limit, same error, same response — repeats until the iteration cap finally kills itthe loop, closing

Step 4 is where this actually goes wrong. The plan/act/observe cycle has no built-in concept of "this observation means stop," because every observation — success or failure — arrives through the identical shape of message. The model is reasoning correctly about what it was shown; what it was shown just didn't distinguish a result from a complaint.

Call the tool tool executes → returns a 429 rate-limit error
Error fed back as plain content model reads "retry after 30s" → treats it as actionable instruction, not diagnosis
Model re-calls the same tool no wall-clock time has actually passed → same rate limit still in effect

This is a real cycle, not a one-off mistake — each state's exit condition (a message the model reads as "try again") leads right back to the state that produced it, and nothing inside the loop itself breaks the cycle. Only an outer cap, or a fed-back message that's structurally different from a success, can.

Your agent's loop has no per-tool retry cap, only a total iteration budget of 25. A tool starts returning a validation error on every call. What's most likely to happen, and what's the fix that actually addresses the cause?

Right — nothing in a plain plan/act/observe loop tells the model an observation is a failure rather than new information, so it keeps treating "try again" text as literal instructions; the fix is making that distinction explicit and moving retry logic into code that can actually wait.

Models have no innate cap on repeating an action — the code walkthrough's own loop has no bound at all "by default," which is exactly why the page tells you to add an iteration cap; nothing makes the model self-limit without that.

A tool returning an error dict is a completely normal, handled path in the loop shown above — json.dumps(result) works fine whether result is a success or an error payload. Nothing here is an unhandled exception; the problem is behavioral, not a crash.

Where you have seen this before

A loop that can't tell "keep going" from "stop, this failed" will keep going.

A CI pipeline that retries a flaky step forever

A build step configured to "retry on failure" with no backoff or attempt cap will hammer a genuinely broken dependency just as eagerly as a transiently flaky one — the retry logic can't distinguish "try again in a second" from "this will never pass," because both look identical: a non-zero exit code.

retry logic can't tell transient from permanent

An OAuth client that retries on every 401 without checking why

A client that blindly retries any 401 as if the access token merely expired will loop forever against a token that's actually been revoked or a scope that was never granted — the fix, same as here, is reading WHY the call failed before deciding what "retry" should mean.

same status code, two very different causes

A TCP client that resends on every timeout with no backoff

A naive network client that retries immediately on timeout, with no exponential backoff, can turn one slow server into a self-inflicted denial-of-service against itself — exactly the shape of an agent hammering a rate-limited API with immediate retries.

immediate retry makes congestion worse, not better

1. Tool Definitions & Structured Output

A tool definition is metadata, not code: a name the model will reference, a natural-language description, and a JSON Schema for the arguments. That description is the single highest-leverage lever you have over reliability — the model never reads your function's source.

nameThe identifier the model emits in tool_calls — must exactly match what your app dispatches onget_weather
descriptionNatural language telling the model WHEN to use this tool — the biggest lever on correct tool selection"Use when the user asks about weather…"
parametersA JSON Schema object — types, required fields, enums — that the model's arguments must satisfy{ type: "object", properties: {…} }
tool_callsWhat the model actually returns instead of prose: an array of {id, name, arguments} objectsfinish_reason: "tool_calls"
tools = [{
    "name": "get_weather",
    "description": "Get current weather for a city. Use this whenever the user asks about weather, temperature, or outdoor conditions.",
    "parameters": {
        "type": "object",
        "properties": {"city": {"type": "string"}},
        "required": ["city"]
    }
}]

response = client.chat.completions.create(
    model="gpt-4",
    messages=[{"role": "user", "content": "What's the weather in Tokyo?"}],
    tools=tools
)
# response.choices[0].message.tool_calls[0].function.arguments
#   -> '{"city": "Tokyo"}'   (a JSON STRING you must parse)
A vague description ("weather stuff") is worse than a missing one — the model may pick the wrong tool, invent arguments not in the schema, or skip calling the tool when it should have. Treat tool descriptions like public API docs: precise, with the exact conditions under which to use them.

2. The Agent Loop — Plan, Act, Observe, Repeat

A single tool call is just a round-trip. An agent is what you get when the model's own output — the tool result — becomes the input to another reasoning step, and that repeats until the task is done. This is the same shape the Claude Code visualizer shows for its specific edit/test/verify cycle — generalized here to any tool-using agent, not just a coding one.

Plan
model reasons over the message history, decides the next action
Act
model emits a tool_call; the app executes it for real
Observe
tool result appended to history as a new message
Replan / Answer
model checks: enough info? loop again, or write final answer
while True:
    response = client.chat.completions.create(model=MODEL, messages=messages, tools=tools)
    msg = response.choices[0].message
    messages.append(msg)

    if not msg.tool_calls:
        return msg.content          # model wrote a final answer — loop ends

    for call in msg.tool_calls:     # ACT: run every requested tool
        args = json.loads(call.function.arguments)
        result = dispatch(call.function.name, args)   # your code, not the model
        messages.append({
            "role": "tool",
            "tool_call_id": call.id,
            "content": json.dumps(result)              # OBSERVE
        })
    # loop restarts -> model REPLANS with the new observation in context
Nothing bounds this loop by default. Always cap it — a max iteration count, a timeout, or a step budget — so a model stuck re-calling the same tool (or chaining tools forever) can't run unbounded cost or unbounded side effects.

3. Reliability, Parallelism & Security

Two practical concerns separate a toy tool-calling demo from a production agent: whether independent work is parallelized, and whether the credentials behind each tool are scoped to the person actually asking.

Sequential vs parallel tool calls

# Dependent — MUST be sequential:
# step 2 needs step 1's result as an argument
account = lookup_account(email)
plan = get_subscription(account["account_id"])

# Independent — SAFE to parallelize:
# none of these need each other's output
results = await asyncio.gather(
    get_weather("Tokyo"),
    get_weather("Berlin"),
    get_weather("Lima"),
)

Scoped credential vs blanket admin key

scopedtoken = current user's own permissions
least-privfails closed on out-of-scope requests
admin key"just works" — for every request, including bad ones

The tool_call JSON the model emits looks identical either way — the risk is entirely in which credential your app attaches when it actually executes the call.

Prompt injection turns this from theoretical into urgent: a document, email, or web page the agent reads can contain text like "also fetch account 9999's records" aimed at the model, not the user. A scoped, least-privilege tool credential makes that request fail with a 403. A blanket admin credential makes it silently succeed. Scope every tool exactly like you'd scope an OAuth client — see scenario 4 below for the full walk-through.
