CloudWatch — Monitoring & Observability

CloudWatch is AWS's observability platform. It collects metrics from all AWS services, ingests application logs, triggers alarms, and visualizes everything in dashboards — the control panel for your production system.

📊 What is CloudWatch — and how do you use it to monitor, alert on, and debug a Spring Boot CIAM service in production?

CloudWatch is AWS's observability platform — every service emits metrics, your apps push logs, alarms fire on thresholds, dashboards pull it together. Its four pillars: Metrics (time-series — ECS CPU, ALB 5XX, RDS connections, plus custom ones like login_success_count); Logs (Fargate ships stdout via the awslogs driver into Log Groups/Streams, queried with Logs Insights); Alarms (OK / ALARM / INSUFFICIENT_DATA → SNS to email/Slack/PagerDuty or trigger auto-scaling; composite alarms cut noise); and Dashboards. Metric filters turn log patterns into metrics ("ERROR count > 50/min → page"), and Container Insights adds per-task CPU/memory/IO.

  • CloudWatch = observability — metrics, logs, alarms, dashboards in one place.
  • Logs Insights — query language over Fargate stdout (Log Groups/Streams).
  • Alarms → SNS — page on threshold breaches; composite alarms reduce noise.
  • Metric filters + Container Insights — log patterns → metrics; per-task stats.

Custom metrics from Spring Boot

// Push custom metrics from Spring Boot // using AWS EMF (Embedded Metric Format): // Just log a special JSON — no SDK needed! // Add dependency: // aws-embedded-metrics @Service @Slf4j public class AuthMetrics { // EMF: log JSON → CloudWatch metric public void recordLoginAttempt(String outcome, String provider, long latencyMs) { // CloudWatch EMF structured log: log.info(JSONObject.quote({ "_aws": { "Namespace": "CIAM/Auth", "Metrics": [{"Name":"LoginLatency","Unit":"Milliseconds"}] }, "LoginLatency": latencyMs, "Outcome": outcome, // dimension "Provider": provider // dimension })); } } // → CloudWatch auto-creates metric: // Namespace: CIAM/Auth // MetricName: LoginLatency // Dimensions: Outcome=success, Provider=ping

Alarm: alert on error rate

# CloudWatch Alarm for CIAM error rate: # 1. Create metric filter on log group: aws logs put-metric-filter \ --log-group-name /ciam/auth-service \ --filter-name ErrorCount \ --filter-pattern '"ERROR"' \ --metric-transformations \ metricName=ErrorCount,metricNamespace=CIAM,metricValue=1 # 2. Create alarm on that metric: aws cloudwatch put-metric-alarm \ --alarm-name "CIAM-High-Error-Rate" \ --metric-name ErrorCount \ --namespace CIAM \ --statistic Sum \ --period 60 \ --evaluation-periods 2 \ --threshold 50 \ --comparison-operator GreaterThanThreshold \ --alarm-actions arn:aws:sns:us-east-1:ACCT:ciam-pagerduty # → If errors > 50 per minute for 2 consecutive minutes: # → SNS notifies PagerDuty → on-call engineer paged

Logs Insights queries

# CloudWatch Logs Insights query language: # Find JWT validation failures for a user: fields @timestamp, @message | filter @message like "jwt_validation_failed" | filter @message like "user=bob@company.com" | sort @timestamp desc | limit 50 # Top 10 slowest endpoints in last hour: fields @timestamp, endpoint, latency_ms | filter latency_ms > 500 | stats count() as count, avg(latency_ms) as p50 by endpoint | sort count desc | limit 10 # Error spike analysis: fields @timestamp, errorType, userId | filter level = "ERROR" | stats count() as errorCount by errorType, bin(5m) | sort errorCount desc # Latency percentiles: stats pct(latency_ms, 50) as p50, pct(latency_ms, 95) as p95, pct(latency_ms, 99) as p99 by bin(1h)

In CIAM / Context: The CIAM production dashboard shows login success/failure rate per minute, JWT validation errors, Ping OAuth latency, ECS task CPU/memory, RDS connection count and ALB 5xx rate. Alarms page on-call when error rate > 5% for 5 minutes, Ping p99 > 3s, or RDS connections > 80% of max — and Logs Insights pinpoints a specific user's auth failures during incident investigation.

2 — CloudWatch Alarms

Alarms watch a metric and trigger actions (SNS notification, Auto Scaling, EC2 action) when a threshold is crossed. Three states: OK, ALARM, INSUFFICIENT_DATA:

4 — Spring Boot Actuator → CloudWatch

<!-- pom.xml — Micrometer CloudWatch registry --> <dependency> <groupId>io.micrometer</groupId> <artifactId>micrometer-registry-cloudwatch2</artifactId> </dependency> # application.yml — push Actuator metrics to CloudWatch management: metrics: export: cloudwatch: namespace: MyApp/Production step: 1m # publish every minute endpoints: web: exposure: include: health,metrics,info,loggers # This sends JVM metrics (heap, GC, threads), HTTP metrics (requests, # latency by endpoint), HikariCP pool metrics, and your custom # @Timed / Counter metrics to CloudWatch automatically. // Custom metric in Spring Boot @Service public class OrderService { private final Counter orderCounter; public OrderService(MeterRegistry registry) { orderCounter = Counter.builder("orders.placed") .tag("region", "us-east-1") .register(registry); } public Order placeOrder(OrderRequest req) { Order order = processOrder(req); orderCounter.increment(); // shows up in CloudWatch return order; } }

5 — CloudWatch Pillars

📊 Metrics

  • Time-series numeric data
  • Free: AWS service metrics (EC2, RDS, ALB)
  • Paid: custom metrics from your app
  • Resolution: 1-second (high res) or 1-minute standard
  • Retention: 15 months

📋 Logs

  • Log Groups → Log Streams
  • Log Insights for querying
  • Metric Filters — turn log patterns into metrics (e.g., count ERROR lines)
  • Retention: configurable (1 day to never)
  • Export to S3 for long-term storage

🔔 Alarms

  • Watch any metric or math expression
  • Actions: SNS, Auto Scaling, EC2 actions, Lambda
  • Composite alarms: combine multiple alarms
  • Anomaly Detection: ML baseline
  • Set up billing alarm at $1 to catch surprises

📈 Dashboards

  • Cross-account and cross-region dashboards
  • Widget types: line, number, gauge, logs, alarms
  • Share dashboards with public URL
  • $3/dashboard/month (first 3 free)
  • Define as JSON or CloudFormation

6 — Observability Ecosystem

ServiceRole
CloudWatch LogsCentralized log storage and search. All ECS/EC2/Lambda logs flow here via log agents or awslogs driver.
CloudWatch MetricsNumeric time-series from AWS services + custom app metrics via Micrometer.
X-RayDistributed tracing. See the full call chain: ALB → Spring Boot → RDS → S3. Identifies slow downstream calls. Add aws-xray-sdk to your app.
CloudTrailAudit log of every AWS API call (who called what, when, from where). Essential for security investigations. Enabled by default; configure S3 delivery for retention.
EventBridgeEvent bus. Route CloudWatch Alarms → Slack, Lambda, SNS. Also schedule Lambda functions (replaces cron-on-EC2).
CloudWatch Container InsightsPre-built dashboards for ECS/EKS — CPU, memory, network per task. Enable per cluster.
AWS ConfigTracks resource configuration changes over time. Compliance rules: "Is every S3 bucket encrypted?" Alerts on drift from desired state.
AWS Health DashboardAWS-wide service status + your account's scheduled maintenance. Subscribe to events for proactive notification of impacted resources.
