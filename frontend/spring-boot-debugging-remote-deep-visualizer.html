Remote Debugging & Breakpoints

When the bug only happens in the container (or only with real data), you attach your IDE's debugger to the running JVM over JDWP — then use the right kind of breakpoint so you stop on the one call that matters instead of hammering "Resume" ten thousand times. Knowing the breakpoint zoo is half of debugging speed.

🐞 What is remote debugging — and how do you attach your IDE to a running container?

Some bugs only appear in the real environment — different env vars, different staging data, a timing issue that won't reproduce locally. Remote debugging connects IntelliJ or VS Code to a JVM running anywhere (a Docker container, a K8s pod, a remote server) without changing the running code. The JVM exposes a debug port via JDWP (Java Debug Wire Protocol); your IDE attaches and can pause, inspect variables, evaluate expressions, and step through in real time. You still need the source locally and it must match exactly what's running — but execution happens remotely.

  • Attach, don't redeploy. JDWP exposes a port; the IDE drives the remote JVM live.
  • Source must match the build exactly, or breakpoints land on the wrong lines.
  • Conditional/exception breakpoints are the time-savers on busy endpoints.
  • Never enable JDWP in prod — unauthenticated, it's full RCE + secret disclosure.

Enabling JDWP

JVM arg -agentlib:jdwp=transport=dt_socket,server=y,suspend=n,address=*:5005. In Docker add it to JAVA_OPTS and expose 5005; in K8s patch the deployment and kubectl port-forward … 5005:5005. Then IntelliJ → Remote JVM Debug → localhost:5005.

Breakpoint types

Conditional (userId.equals("42")) pauses only for the case you care about. Exception breakpoints stop on a thrown type without guessing the line. Field watchpoints fire on read/write. Method breakpoints stop on entry/exit (slower).

Never in production

Default JDWP has no auth — anyone reaching the port can pause the JVM, read every variable (secrets, tokens, DB passwords), and run arbitrary code. Dev/staging only, behind network policy. suspend=y is worse — it blocks startup until a debugger connects.

CIAM: A JWT 401 reproduces on staging but not locally. Enable JDWP in the staging Compose (JAVA_OPTS="-agentlib:jdwp=…address=*:5005"), port-forward, set a conditional exception breakpoint on JwtException so IntelliJ pauses exactly when parsing fails, and inspect the raw token in the frame — truncated? wrong encoding? — instead of guessing from logs.

The problem

You paused one thread to read one variable. Forty seconds later the pod was gone and you blamed the VPN.

The orchestrator restarted the pod while you were reading a variable

Staging only. You patch the deployment with -agentlib:jdwp=transport=dt_socket,server=y,suspend=n,address=*:5005, kubectl port-forward the port, and IntelliJ attaches on the first try. You drop a line breakpoint in TokenController.refresh(), fire the request, and it stops exactly where you wanted. You expand the frame, read the claims map, start typing an expression into Evaluate…

…and the IDE says Disconnected. The terminal running port-forward has exited. kubectl logs shows a fresh Spring banner. You reattach, it happens again, and by the third time you're convinced the cluster network is flaky. It isn't. Your breakpoint suspended every thread in the JVM — that's the default, not something you chose — so the kubelet's httpGet liveness probe against /actuator/health got no answer three times in a row and did precisely what you configured it to do: restart the container.

JDWP flags correct ✓ port-forward established ✓ breakpoint hit on the right line ✓ nothing in the JVM can answer the health probe ⚠

The assumption underneath: that pausing is something that happens to your request. It happens to the process, and the process has other people depending on it.

Suspend one thread, and give the probe room to be wrong
Right-click the breakpoint → Suspend: Thread (not All) ↓ the Tomcat worker holding your request stops; the acceptor, the scheduler and Actuator keep running, so /actuator/health still answers 200 while you read the frame On the debug deployment only, loosen the probe — failureThreshold 30, or drop the liveness probe entirely ↓ a pod you are actively debugging does not need to be auto-healed; you are the healing And prefer a logpoint when you only want to see a value — it prints and never suspends anything at all
A breakpoint is a full stop for the whole JVM unless you tell it otherwise, and every watchdog pointed at that JVM reads a full stop as death. IntelliJ creates line breakpoints with a suspend policy of All, which is the right default on your laptop and the wrong one inside an orchestrated container: the kubelet's default probe budget is roughly periodSeconds: 10 × failureThreshold: 3, so you have about thirty seconds of thinking time before something decides your app has hung and replaces it. Nothing about this is unique to Kubernetes — an ECS health check, an ALB target group, or a plain docker-compose healthcheck block all behave the same way. The debugger is not being interrupted by an unrelated failure; the debugger is the failure, as far as every health check can tell.
Pausing a JVM feels like pausing a video. It's closer to putting a patient under while they are still wired to a monitor whose only job is to call a code blue the second the trace goes flat. Your breakpoint is the flatline — a health check cannot tell "paused" from "dead".
You

I set one breakpoint on one line. Why did the whole pod restart?

The breakpoint's suspend policy

Because I'm set to All, and I always have been — it's the default on every line breakpoint you create. I don't stop your request, I stop the JVM: your worker thread, the other forty worker threads, the scheduler, the Actuator endpoints, the lot. Flip me to Thread and only the one frame you care about freezes.

The kubelet

From out here you look identical to a deadlock. I asked /actuator/health three times, ten seconds apart, and got nothing inside my one-second timeout each time. Restarting a hung container is my entire job description. Nobody told me a human was reading a variable.

Postgres

And while you were frozen mid-@Transactional, I was still holding the row lock you took. Your other two replicas were very much awake and queuing behind it. The debugger stopped one JVM; it didn't stop the system.

The mechanism

Thirty seconds, second by second, from "breakpoint hit" to "Disconnected".

  1. kubectl port-forward pod/api-7d9f 5005:5005, IDE attaches. With suspend=n the attach itself changes nothing — the app serves traffic exactly as beforet = 0s, all healthy
  2. You add a plain line breakpoint. Its suspend policy is All, inherited from the IDE default rather than chosenthe setting you never saw
  3. A refresh request reaches the line. The JDWP agent stops every thread: your worker, the Tomcat acceptor, the scheduled tasks, and the threads that would serve /actuator/healtht = 0s, whole JVM stopped
  4. The kubelet's next probe gets no response inside timeoutSeconds: 1. Failure one. Ten seconds later, failure two. Ten after that, failure three — failureThreshold reachedt = 10s, 20s, 30s
  5. All that time your frozen thread is inside a transaction holding a row lock, and your other replicas — awake, healthy, serving users — are piling up behind itthe part that hurts other people
  6. The kubelet restarts the container. The JVM dies, the JDWP socket closes, port-forward exits because its pod is gone, and the IDE reports a network problem it did not havet = 30s, "Disconnected"

Step 4 is where the clock you didn't know about runs out, and it's worth knowing the shape of that clock precisely: it is periodSeconds × failureThreshold, nothing to do with the debugger, and it is the same budget whether the JVM is paused, deadlocked, or in a twenty-second stop-the-world GC pause. Which is also the tell in reverse — if a probe's tcpSocket check keeps passing while its httpGet fails, that is never a network issue, it's the kernel accepting connections that no application thread is alive to answer.

Read the three inputs and notice none of them is a bug. Each is a piece of infrastructure doing exactly the job you asked it to do, triggered by a silence you created on purpose. That's why "the connection keeps dropping" is such a misleading way to describe this — the connection is the last domino, and fixing it means changing the silence (suspend one thread) or changing who is listening for it (relax the probe on the debug deployment), never the IDE.

You attach to a staging pod, stop on a line breakpoint in TokenController.refresh(), and spend about forty seconds inspecting the frame. The IDE disconnects and kubectl logs shows a fresh Spring Boot banner. What actually happened?

JDWP has no idle timeout — that's the point of a debugger, and a suspended JVM can sit suspended for hours quite happily. The agent only goes away when the process does. If your session dies on a schedule, something outside the JVM is running that schedule, and the very useful diagnostic is that the interval will be suspiciously round: thirty seconds, ninety seconds, five minutes. Debuggers don't have round numbers; health checks do.

Two things to untangle. First, a line breakpoint's default suspend policy in IntelliJ is All, not Thread — suspending just the one thread is the thing you have to opt into, and it's the fix here. Second, Kubernetes has no concept of a slow HTTP request; it never watches your traffic. It only knows what its probes tell it, which is why a slow endpoint is invisible to the kubelet and an unanswered probe is fatal.

Right, and the arithmetic gives you the whole story: periodSeconds: 10 × failureThreshold: 3 is about thirty seconds of thinking time, which is roughly how long it takes to expand a JWT claims map and type an expression. Set that breakpoint's suspend policy to Thread and the freeze narrows to the one worker holding your request, leaving the rest of the JVM free to keep answering probes. On a dedicated debug deployment, raise failureThreshold or remove the liveness probe outright — and while you're paused, remember the transaction you're sitting inside is still holding its locks against every other replica.

A twenty-second stop-the-world GC pause

An undersized heap, a full GC, and the JVM stops answering for long enough to blow the same probe budget — so the pod restarts, starts cold with an empty cache, takes a fresh wave of traffic, and GCs again. The restart loop looks like a crash loop and there is no crash anywhere in it. Identical mechanism to your breakpoint, minus the human.

1. Attach to a running JVM (JDWP)

# start the app with the debug agent listening on 5005
java -agentlib:jdwp=transport=dt_socket,server=y,suspend=n,address=*:5005 -jar app.jar

# then in your IDE: Run → Attach to Process / Remote JVM → host:5005
  • suspend=n — app starts normally, you attach whenever. suspend=y — the JVM waits for the debugger before main, so you can debug startup / bean init.
  • Docker: add the same flag (e.g. JAVA_TOOL_OPTIONS) and publish the port: docker run -p 5005:5005 ….
  • Cloud: tunnel the port (don't expose JDWP publicly — it's unauthenticated remote code execution).

2. Interactive: pick the right breakpoint for the job

A plain line breakpoint is the blunt instrument. The conditional and logpoint variants are what make debugging a loop or a hot path actually bearable.

3. The breakpoint zoo

TypeStops whenBest for
Lineexecution reaches the linethe default; pair with a condition
Conditionalline reached and expression is trueone specific id / iteration
Logpointnever pauses — just logsprint-debugging without code edits
Hit-countafter N hitsskip the healthy early calls
Exceptiona given exception is thrownfind an exception's origin
Field watcha field is read/written"who mutated this?"

All of these evaluate expressions in the current frame — inspect variables, call methods, even change a value. Hot-swap can redefine method bodies live (but not add fields/methods).

4. When NOT to reach for the debugger

  • Heisenbugs & timing/concurrency: pausing one thread changes the timing — the race vanishes. Use logging/thread dumps instead.
  • Production: stepping freezes the JVM (and any suspend stalls real users). Prefer Actuator + live log levels and a thread/heap dump.
  • Async / reactive: stack frames don't span the async hop — a breakpoint shows a worker thread with no caller context. Logpoints + correlation ids beat it.

5. One-sentence recap

🪲 Attach your IDE to a running (even containerized) JVM with JDWP (-agentlib:jdwp=…,address=*:5005; suspend=y to debug startup, never expose the port publicly), then reach past the blunt line breakpoint for a conditional one (stop on the single case), a logpoint (log without pausing), hit-count, exception, or field-watch breakpoint — and step away from the debugger entirely for concurrency, async, and production, where it distorts timing or freezes users.
