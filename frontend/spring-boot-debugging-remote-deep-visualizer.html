Remote Debugging & Breakpoints

When the bug only happens in the container (or only with real data), you attach your IDE's debugger to the running JVM over JDWP — then use the right kind of breakpoint so you stop on the one call that matters instead of hammering "Resume" ten thousand times. Knowing the breakpoint zoo is half of debugging speed.

1. Attach to a running JVM (JDWP)

# start the app with the debug agent listening on 5005
java -agentlib:jdwp=transport=dt_socket,server=y,suspend=n,address=*:5005 -jar app.jar

# then in your IDE: Run → Attach to Process / Remote JVM → host:5005
  • suspend=n — app starts normally, you attach whenever. suspend=y — the JVM waits for the debugger before main, so you can debug startup / bean init.
  • Docker: add the same flag (e.g. JAVA_TOOL_OPTIONS) and publish the port: docker run -p 5005:5005 ….
  • Cloud: tunnel the port (don't expose JDWP publicly — it's unauthenticated remote code execution).

2. Interactive: pick the right breakpoint for the job

A plain line breakpoint is the blunt instrument. The conditional and logpoint variants are what make debugging a loop or a hot path actually bearable.

3. The breakpoint zoo

TypeStops whenBest for
Lineexecution reaches the linethe default; pair with a condition
Conditionalline reached and expression is trueone specific id / iteration
Logpointnever pauses — just logsprint-debugging without code edits
Hit-countafter N hitsskip the healthy early calls
Exceptiona given exception is thrownfind an exception's origin
Field watcha field is read/written"who mutated this?"

All of these evaluate expressions in the current frame — inspect variables, call methods, even change a value. Hot-swap can redefine method bodies live (but not add fields/methods).

4. When NOT to reach for the debugger

  • Heisenbugs & timing/concurrency: pausing one thread changes the timing — the race vanishes. Use logging/thread dumps instead.
  • Production: stepping freezes the JVM (and any suspend stalls real users). Prefer Actuator + live log levels and a thread/heap dump.
  • Async / reactive: stack frames don't span the async hop — a breakpoint shows a worker thread with no caller context. Logpoints + correlation ids beat it.

5. One-sentence recap

🪲 Attach your IDE to a running (even containerized) JVM with JDWP (-agentlib:jdwp=…,address=*:5005; suspend=y to debug startup, never expose the port publicly), then reach past the blunt line breakpoint for a conditional one (stop on the single case), a logpoint (log without pausing), hit-count, exception, or field-watch breakpoint — and step away from the debugger entirely for concurrency, async, and production, where it distorts timing or freezes users.
