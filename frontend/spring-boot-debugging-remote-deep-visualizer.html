Remote Debugging & Breakpoints

When the bug only happens in the container (or only with real data), you attach your IDE's debugger to the running JVM over JDWP — then use the right kind of breakpoint so you stop on the one call that matters instead of hammering "Resume" ten thousand times. Knowing the breakpoint zoo is half of debugging speed.

What is remote debugging — and how do you attach your IDE to a running Docker container?

Some bugs only appear in the real environment: the container has different env vars, the staging database has different data, or the bug involves a timing issue that doesn't reproduce locally. Remote debugging lets you connect IntelliJ or VS Code's debugger to a JVM running anywhere — a Docker container, a Kubernetes pod, a remote server — without touching the running process's code. The JVM exposes a debugging port via JDWP (Java Debug Wire Protocol). Your IDE connects to that port and can pause execution, inspect variables, evaluate expressions, and step through code, all in real time. You still need the source code locally, and the source must match exactly what's running — but the execution happens in the remote environment.

How to enable JDWP

JVM arg: -agentlib:jdwp=transport=dt_socket,server=y,suspend=n,address=*:5005. In Docker: add to JAVA_OPTS env var and expose port 5005. In K8s: patch the deployment to add the JVM arg and forward the port: kubectl port-forward pod/my-app-xxx 5005:5005. Then in IntelliJ: Run → Edit Configurations → + → Remote JVM Debug → host: localhost, port: 5005 → Debug.

Breakpoint types that save time

Conditional breakpoint: right-click the breakpoint → Condition → userId.equals("42") — only pauses for user 42, not all 10,000 other requests. Exception breakpoint: pauses on any thrown exception of a specific type — no need to guess which line throws. Field watchpoint: pauses when a field is read or written. Method breakpoint: pauses on entry/exit of a specific method (slower than line breakpoints). Without conditional breakpoints, high-traffic endpoints pause on every request.

Never enable JDWP in production

JDWP with no authentication (the default) lets anyone who can reach that port pause the JVM, read all variables (including secrets, tokens, DB passwords), execute arbitrary code, and completely stop the application. Enable only in dev/staging, with network policies that prevent external access to port 5005. suspend=y is even more dangerous — it pauses the JVM on startup and waits for a debugger, meaning the app is completely unavailable until you connect.

In CIAM: JWT validation 401 happens on staging but not locally. 1) Enable JDWP in the staging Docker Compose: JAVA_OPTS="-agentlib:jdwp=transport=dt_socket,server=y,suspend=n,address=*:5005". 2) Port-forward from your machine: docker compose exec api sh -c "curl localhost:5005". 3) Set a conditional exception breakpoint on JwtException — IntelliJ pauses exactly when the JWT fails to parse. 4) Inspect the token string — is it truncated? Wrong encoding? You can see the raw value in the debugger frame.

1. Attach to a running JVM (JDWP)

# start the app with the debug agent listening on 5005
java -agentlib:jdwp=transport=dt_socket,server=y,suspend=n,address=*:5005 -jar app.jar

# then in your IDE: Run → Attach to Process / Remote JVM → host:5005
  • suspend=n — app starts normally, you attach whenever. suspend=y — the JVM waits for the debugger before main, so you can debug startup / bean init.
  • Docker: add the same flag (e.g. JAVA_TOOL_OPTIONS) and publish the port: docker run -p 5005:5005 ….
  • Cloud: tunnel the port (don't expose JDWP publicly — it's unauthenticated remote code execution).

2. Interactive: pick the right breakpoint for the job

A plain line breakpoint is the blunt instrument. The conditional and logpoint variants are what make debugging a loop or a hot path actually bearable.

3. The breakpoint zoo

TypeStops whenBest for
Lineexecution reaches the linethe default; pair with a condition
Conditionalline reached and expression is trueone specific id / iteration
Logpointnever pauses — just logsprint-debugging without code edits
Hit-countafter N hitsskip the healthy early calls
Exceptiona given exception is thrownfind an exception's origin
Field watcha field is read/written"who mutated this?"

All of these evaluate expressions in the current frame — inspect variables, call methods, even change a value. Hot-swap can redefine method bodies live (but not add fields/methods).

4. When NOT to reach for the debugger

  • Heisenbugs & timing/concurrency: pausing one thread changes the timing — the race vanishes. Use logging/thread dumps instead.
  • Production: stepping freezes the JVM (and any suspend stalls real users). Prefer Actuator + live log levels and a thread/heap dump.
  • Async / reactive: stack frames don't span the async hop — a breakpoint shows a worker thread with no caller context. Logpoints + correlation ids beat it.

5. One-sentence recap

🪲 Attach your IDE to a running (even containerized) JVM with JDWP (-agentlib:jdwp=…,address=*:5005; suspend=y to debug startup, never expose the port publicly), then reach past the blunt line breakpoint for a conditional one (stop on the single case), a logpoint (log without pausing), hit-count, exception, or field-watch breakpoint — and step away from the debugger entirely for concurrency, async, and production, where it distorts timing or freezes users.
