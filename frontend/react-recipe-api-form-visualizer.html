Recipe — Fetch an API & Drive a Controlled Form

The React version of the everyday edit screen: fetch a record in an effect, hold it in state, render controlled inputs (value + onChange), then submit it back — with validation and server-error handling. Plain React, no form library.

⚛️ The pattern: useEffect fetch → state → controlled inputs → POST

In React the form's data lives in state, and the DOM is just a reflection of it. (1) Load: a useEffect(() => {...}, []) runs once after mount and fetches the record; you await res.json() and call setForm(user) to seed state. (2) Control: each input is controlled — its value={form.email} comes from state and its onChange writes back with setForm(f => ({...f, email: e.target.value})). This makes React the single source of truth: what you see is always exactly what's in state, never stale DOM. (3) Validate: validation is usually derived — you compute errors from the current form on each render (e.g. !form.email.includes('@')), show messages, and disable submit when there are any. (4) Submit: a handleSubmit calls e.preventDefault() (so the browser doesn't full-page reload), then fetch(url, {method:'PUT', body: JSON.stringify(form)}); you check res.ok, and on a server rejection (e.g. 409 email taken) you set an error into state so the message renders by the field. The mental model is the opposite of jQuery: you never read inputs to get values — the values are already in state because every keystroke put them there. (In real apps you'd often reach for React Hook Form or TanStack Query to cut boilerplate, but knowing the raw pattern is what makes those libraries make sense.)

  • Load — useEffect(..., []) fetches once; setForm seeds state from the response.
  • Control — each input is value={form.x} + onChange → state is the single source of truth.
  • Validate — derive errors from form each render; disable submit when any exist.
  • Submit — preventDefault → fetch PUT → check res.ok; map a 4xx into error state.

Load into state

const [form, setForm] = useState({ name: '', email: '' }); useEffect(() => { fetch('/api/users/42') .then(r => r.json()) .then(setForm); }, []);

A controlled input

<input value={form.email} onChange={e => setForm(f => ({ ...f, email: e.target.value }))} /> {errors.email && <small>{errors.email}</small>}

Angular comparison

React state ≈ Angular's FormGroup value, but you wire each input (no formControlName). useEffect+fetch ≈ ngOnInit+HttpClient. Derived errors ≈ Angular validators (but recomputed each render rather than held on a control). res.ok/status handling ≈ the HttpClient error callback. React is more manual but more explicit; libraries like React Hook Form close the gap.

In your CIAM app: the React profile/registration form. Seed it from /api/profile, keep every field in state, and PUT it back. The same rule applies as everywhere: the client validation is UX only — the server (and IdP) is the real gate, so always handle the !res.ok path and surface a server 409/400 on the right field. For the access token, send it in the Authorization header of the fetch (or via a wrapper/interceptor); see the node-auth and aspnet-auth pages for the API side, and the password-complexity recipe for the password field.

1. Load the record into state

function ProfileForm() {
  const [form, setForm] = useState({ name: '', email: '' });
  const [errors, setErrors] = useState({});
  const [saved, setSaved] = useState(false);

  useEffect(() => { // runs once after mount
    fetch('/api/users/42')
      .then(r => r.json())
      .then(setForm); // seed state with the user
  }, []); // [] = only on mount
State is the form. useState holds the editable data, and useEffect(..., []) with an empty dependency array runs the fetch exactly once after the component mounts. Passing setForm directly to .then replaces the whole state object with the response. From here on, the inputs read from form — React, not the DOM, owns the values. (A production version would also handle loading and error states for the fetch itself.)

2. Controlled inputs & derived validation

const errors = { // derived from state every render
  email: !form.email.includes('@') ? 'Enter a valid email' : null,
  name: !form.name ? 'Name is required' : null,
};
const isValid = !errors.email && !errors.name;

<input value={form.email}
      onChange={e => setForm(f => ({ ...f, email: e.target.value }))} />
{errors.email && <small className="err">{errors.email}</small>}
Controlled = value flows from state, changes flow back. value={form.email} means the input always displays state; onChange updates state with a functional update (f => ({...f, email})) so you never mutate the previous object. Validation is just a value derived from form on each render — no separate validator objects to keep in sync. The error renders with the {cond && <small/>} idiom, and isValid gates the submit button.

3. Submit & handle the server's answer

async function handleSubmit(e) {
  e.preventDefault(); // stop the browser's full-page reload
  if (!isValid) return;
  const res = await fetch('/api/users/42', {
    method: 'PUT',
    headers: { 'Content-Type': 'application/json' },
    body: JSON.stringify(form), // state → JSON body
  });
  if (res.ok) setSaved(true);
  else if (res.status === 409) // email already taken
    setErrors({ email: 'That email is already in use' });
}
fetch doesn't throw on 4xx/5xx — you must check res.ok. Unlike Angular's HttpClient, fetch only rejects on network failure; a 409 still resolves, so you branch on res.ok / res.status yourself. preventDefault() is essential — without it a native form submit reloads the page and you lose all state. On a 409 you write the server's verdict into errors state, and because the component re-renders, the message appears under the email field. State in, JSON out, server's answer back into state.
