Backtracking

A search technique for problems where you build a solution one choice at a time and sometimes have to undo a choice once it's proven to lead nowhere — choose → explore → un-choose → prune.

🧭 What makes this different from plain recursion?

Plain recursion (see Recursion) breaks a problem into smaller versions of itself and trusts each call to return a correct answer. Backtracking is recursion with one extra discipline: it explores a tree of choices depth-first, and every time it makes a choice, it plans to undo that choice the moment it's known the branch below it can't work — either because the recursive call comes back empty, or because a quick check proves the branch is doomed before even recursing into it (that check is called pruning). The pattern always has the same four moves: choose (commit to one option and mutate the shared state), explore (recurse into the next decision with that choice in place), un-choose (undo the mutation once the recursive call returns, so the state is clean for the next option), and prune (skip a choice entirely — without ever recursing into it — the instant a check proves it can't lead anywhere). Every classic backtracking problem — subsets, permutations, N-Queens, Sudoku, combination sum — is the exact same four-move skeleton wrapped around a different "is this choice still valid?" check.

  • Choose — commit to one option and record it in shared, mutable state (a path list, a board array, a "used" set).
  • Explore — recurse one level deeper with that choice already in place.
  • Un-choose — the moment the recursive call returns, undo the mutation from "choose" so a sibling option sees a clean slate.
  • Prune — when a check proves a choice can't possibly lead to a valid solution, skip it without ever recursing — this is what keeps the search from degenerating into brute force.

Un-choose is the whole trick

Delete the un-choose line from any backtracking solver and it silently breaks — every sibling branch would see the previous branch's leftover state (a queen still "on the board," a value still marked "used") instead of a clean slate.

Pruning is what makes it fast

Without a check like isSafe() or "remaining < 0," backtracking degenerates into generating every possible arrangement and validating each one at the end — pruning cuts off entire doomed subtrees before wasting any work exploring them.

It's still exponential, just smaller

Backtracking doesn't change the worst-case complexity class — N-Queens is still O(n!) in the worst case — it just prunes the constant factor down by skipping the astronomically large fraction of arrangements that fail early and obviously.

Where this shows up in real backend work: a package manager resolving compatible dependency versions (npm, Maven) is backtracking search — choose a version for library A, explore by trying to satisfy library B's constraints against it, and if nothing satisfies B, un-choose A's version and try the next one. Role/permission conflict resolution in an RBAC system is the same shape: tentatively grant a role, check it doesn't violate a separation-of-duties rule, and back out if it does. Anywhere you see "try an assignment, validate it against everything committed so far, undo and try the next one if it fails," that's backtracking, even if nobody calls it that.

A few things worth knowing

  • Two different flavors of "check" — N-Queens prunes on a constraint violation (does this square attack an existing queen?); Combination Sum prunes on a numeric bound (has the running total already gone negative?). The choose/explore/un-choose skeleton is identical either way — only the check changes.
  • Where the state lives matters — these examples mutate one shared array/list (a path, a "used" set, a board) rather than copying it at every level, because copying an array at every node of an exponential tree is itself exponential extra work. Mutate-then-undo is what keeps the memory overhead down to the depth of the recursion, not the size of the tree.
  • Memoization is the wrong tool here — Recursion's memoization trick (cache a return value by input) doesn't apply to most backtracking problems, because the "input" at each node is the entire path taken to get there, which is different every time — there's nothing to look up.
