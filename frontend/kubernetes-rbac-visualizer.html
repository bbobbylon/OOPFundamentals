RBAC & Service Accounts

Who is allowed to do what, to which resources, in which namespace — Kubernetes' own IAM.

🔐 What is RBAC — and why did a "view" Role once hand out your Secrets?

Every request that reaches the Kubernetes API server — your kubectl, a Deployment controller, a CSI driver, your own pod calling the API — is checked against Role-Based Access Control before anything happens. A Role is a namespaced allow-list: a set of verbs (get, list, watch, create, update, patch, delete) on resources (pods, secrets, deployments). A RoleBinding attaches that Role to a subject — a ServiceAccount, a User, or a Group — inside one namespace. Need the same shape cluster-wide? ClusterRole + ClusterRoleBinding is the identical model with no namespace field at all. This is the actual security boundary the previous lesson pointed at: a Secret's base64 encoding stops nobody, but RBAC is what decides who may ever run kubectl get secret in the first place.

  • Role = a namespaced allow-list: verbs on resources. Grants nothing by itself.
  • RoleBinding attaches a Role to a subject, in ONE namespace — the only thing that connects identity to permission.
  • ClusterRole + ClusterRoleBinding = same shape, but reaches every namespace (present and future).
  • Every pod runs as a ServiceAccount — default unless you say otherwise, and default should never be granted anything.

Role + RoleBinding (namespaced)

apiVersion: rbac.authorization.k8s.io/v1 kind: Role metadata: name: ciam-app-role namespace: ciam-prod rules: - apiGroups: [""] resources: ["secrets"] resourceNames: ["ciam-secrets"] verbs: ["get"] --- apiVersion: rbac.authorization.k8s.io/v1 kind: RoleBinding metadata: name: ciam-app-binding namespace: ciam-prod subjects: - kind: ServiceAccount name: ciam-app namespace: ciam-prod roleRef: kind: Role name: ciam-app-role apiGroup: rbac.authorization.k8s.io

ClusterRole + ClusterRoleBinding (cluster-wide)

apiVersion: rbac.authorization.k8s.io/v1 kind: ClusterRole metadata: name: secret-reader rules: - apiGroups: [""] resources: ["secretproviderclasses"] verbs: ["get","list","watch"] --- apiVersion: rbac.authorization.k8s.io/v1 kind: ClusterRoleBinding metadata: name: secret-reader-binding subjects: - kind: ServiceAccount name: csi-secrets-driver namespace: kube-system roleRef: kind: ClusterRole name: secret-reader apiGroup: rbac.authorization.k8s.io # no "namespace:" field anywhere above — # that absence IS the cluster-wide reach

Audit a permission before you deploy

# does ciam-app's ServiceAccount # have this permission right now? kubectl auth can-i get secrets \ --as=system:serviceaccount:ciam-prod:ciam-app \ -n ciam-prod # → yes / no — the REAL authorizer, # not a simulation, zero side effects # what CAN this identity do, full list: kubectl auth can-i --list \ --as=system:serviceaccount:ciam-prod:ciam-app \ -n ciam-prod

CIAM's own RBAC shape: The Secrets Store CSI driver's ServiceAccount needs a ClusterRole — it fetches SecretProviderClass objects across every namespace, not just one. Your ciam-app ServiceAccount needs the opposite: a Role scoped to ciam-prod alone, with resourceNames narrowing it to the one Secret it actually reads. Grant the CSI driver's breadth to your own app's ServiceAccount by mistake — copy-pasting a platform team's ClusterRoleBinding is the single most common way this happens — and every namespace on the cluster can now read ciam-secrets.

The problem

RBAC errors look exactly like broken YAML, and the fastest fix is always the worst one.

"I gave the pipeline's ServiceAccount cluster-admin — the demo was in ten minutes"

Your GitHub Actions runner authenticates to the cluster as a ServiceAccount, tries to helm upgrade, and gets Error: secrets is forbidden. Ten minutes before a demo, the fix that compiles fastest is kubectl create clusterrolebinding ci-admin --clusterrole=cluster-admin --serviceaccount=ci:pipeline. The demo works. Nobody removes it, because nothing ever breaks again to remind you it exists:

cluster-admin = every verb, every resource, every namespace ⚠ a leaked CI token is now a leaked cluster ⚠ the token sits in a GitHub Actions secret, readable by any workflow in the repo ⚠ the actual missing permission was one line: get on one Secret ⚠

And the sting: six months later a dependency-confusion attack compromises one npm package the pipeline installs, and it doesn't just poison a build — it has cluster-admin, so it deletes every Secret in every namespace on its way out.

Three real dials, and RBAC only has these
Verb scope — get/list/watch is not create/update/patch/delete ↓ because "can this identity ever change something" is a different question from "can it read" Resource scope — resourceNames narrows "all secrets" to "this one secret" ↓ because most identities need exactly one Secret, not the collection Namespace scope — Role stays in one namespace; ClusterRole reaches all of them
RBAC is deny-by-default and additive-only — there is no "deny" rule, only the presence or absence of an allow. If two RoleBindings disagree, the more permissive one silently wins. "Tightening" one binding while a broader one still exists changes nothing at all.
Role

I'm just a list: these verbs, on these resources, in this namespace. I grant nothing to anyone by myself — I'm not even attached to an identity yet.

RoleBinding

That's me. I'm the wire between a Role and a ServiceAccount. Delete me and the Role is just YAML sitting in etcd, doing nothing — a very common "why doesn't this work" dead end.

ServiceAccount

And I'm the identity your pod authenticates as — auto-mounted, auto-rotated token, no human's kubeconfig involved. If nobody names me in the pod spec, I'm default, and default should own precisely zero RoleBindings.

The mechanism

Follow one API request from your terminal to a yes/no, and watch exactly where identity ends and authorization begins.

  1. you (or a pod) present a client cert or a ServiceAccount tokenauthentication
  2. the API server resolves that to an identity — a User, or system:serviceaccount:ns:namewho
  3. every Role/ClusterRole bound to that identity is checked for one matching ruleauthorization
  4. ANY single matching rule, in ANY binding, is enough — there is no override, no priorityunion, not ranking
  5. no rule matches → 403 Forbidden, with no hint about which binding was missingdeny by silence

Step 4 is the one that surprises people who know Spring Security or IAM policy evaluation, where an explicit deny can beat an allow. Kubernetes RBAC has no deny rules at all — only allows. A narrow Role you wrote carefully today does nothing to shrink a broad ClusterRole someone bound to the same ServiceAccount last year; both are simply unioned.

The 403 tells you nothing about why. It does not name the missing verb, the missing resource, or which of your bindings almost worked. Two tools close that gap without deploying anything: kubectl auth can-i <verb> <resource> --as=<identity> -n <namespace> asks the real authorizer a yes/no question with zero side effects, and kubectl auth can-i --list --as=<identity> dumps everything that identity can do. Both use --as impersonation, which itself needs an impersonate RBAC grant on your own account — so the audit tool is gated by the same system it audits.

ciam-app's ServiceAccount has one RoleBinding, to a Role granting get, list, watch on configmaps in ciam-prod. It calls the API to get a secret in that same namespace. What happens?

Namespace is one of three things that must match, not the only one. This Role's rule names configmaps — a completely different resource type from secrets in the same API group. Being in the right namespace buys nothing if the resource itself was never listed.

Right. A rule matches only when verb, resource, AND (if present) resourceNames all line up. This Role's only rule lists configmaps; secrets never appears anywhere in it, so the request has no matching rule in any binding and comes back 403 Forbidden.

There's no such implicit naming convention — RBAC never infers a resource name from the identity that's asking. A rule either lists the resource type at all (and optionally narrows it with an explicit resourceNames), or it grants nothing for that resource, full stop.

Where you've seen this before

Same shape, three different rooms you already work in.

@PreAuthorize("hasRole('ADMIN')")

Identical model at method scope: a subject (the authenticated principal), a permission check (does it hold the required authority), deny-by-default if the check fails. One annotation guards one endpoint the same way one RoleBinding guards one verb — and just like RBAC, stacking two @PreAuthorize rules from different base classes unions rather than overrides.

subject + checkdeny by default

Entra app roles & Ping OAuth scopes

An Entra app role assigned to a service principal, or a Ping OAuth scope granted to a client, is the CIAM-shaped version of a RoleBinding: it's the record of "this identity may do this" that a resource server checks on every request. The token carries the claim; RBAC checks the binding live against etcd — different storage, same question being asked.

role → claimchecked per-request

AWS IAM policy + a trust policy

An IAM policy's Action/Resource pair is a Role's verbs/resources wearing a different name, and a trust policy binding a role to a principal is a RoleBinding. Workload Identity / IRSA is the literal bridge: it lets a Kubernetes ServiceAccount assume a cloud IAM role, so the two systems' authorization checks chain instead of duplicating credentials.

Questions from the back row

Why does a pod need a ServiceAccount at all — why not just "the pod"?

Because every call a pod makes to the Kubernetes API — and plenty of platform components do this constantly — needs an identity to authenticate as. A ServiceAccount gives it one: an auto-mounted, auto-rotated token Kubernetes manages for you, so a Deployment controller, a CSI driver, or your own app's code can call the API without a human's kubeconfig anywhere near it. Leave it unspecified and the pod gets default — which is why default should never hold a RoleBinding.

Can I check a permission without actually trying the request for real?

Yes — kubectl auth can-i get secrets --as=system:serviceaccount:ciam-prod:ciam-app -n ciam-prod impersonates that identity for exactly one authorization check and answers yes/no with zero side effects. It runs the same authorizer a real request would hit, so the answer is exactly what production would do — not a guess, not a simulation of one.

I just replaced a broad RoleBinding with a narrower one — did I just tighten access?

Only if the broad one is gone, not just replaced in your mental model. RBAC unions every binding pointing at an identity; deleting one binding while a second, more permissive one still exists changes nothing that second binding already covers. Confirm with kubectl get rolebindings,clusterrolebindings -A -o json | grep -B4 ciam-app before declaring victory — can-i --list on the identity is the faster version of the same check.

1 — ServiceAccount

kind: ServiceAccount

  name: ciam-app
  namespace: ciam-prod

spec:
  serviceAccountName: ciam-app   # omit this and you get "default"









2 — Role + RoleBinding (namespaced)




apiVersion: rbac.authorization.k8s.io/v1
kind: Role
metadata:
  name: ciam-app-role
  namespace: ciam-prod
rules:
- apiGroups: [""]
  resources: ["secrets"]
  resourceNames: ["ciam-secrets"]   # only THIS one, not all secrets
  verbs: ["get"]
---
apiVersion: rbac.authorization.k8s.io/v1
kind: RoleBinding
metadata:
  name: ciam-app-binding
  namespace: ciam-prod
subjects:
- kind: ServiceAccount
  name: ciam-app
  namespace: ciam-prod
roleRef: { kind: Role, name: ciam-app-role, apiGroup: rbac.authorization.k8s.io }


⚠ resourceNames only narrows verbs that target one named object —
get, update, patch, delete. It does nothing for
list or watch, which always operate on the whole collection.









3 — ClusterRole + ClusterRoleBinding (cluster-wide)




apiVersion: rbac.authorization.k8s.io/v1
kind: ClusterRole
metadata:
  name: secretproviderclasses-reader   # no "namespace:" field — it can't have one
rules:
- apiGroups: ["secrets-store.csi.x-k8s.io"]
  resources: ["secretproviderclasses"]
  verbs: ["get", "list", "watch"]
---
apiVersion: rbac.authorization.k8s.io/v1
kind: ClusterRoleBinding
metadata:
  name: secretproviderclasses-reader-binding
subjects:
- kind: ServiceAccount
  name: csi-secrets-driver
  namespace: kube-system
roleRef: { kind: ClusterRole, name: secretproviderclasses-reader, apiGroup: rbac.authorization.k8s.io }


⚠ A ClusterRole can also be bound with a plain RoleBinding instead of a
ClusterRoleBinding — that reuses a shared permission SET (like the built-in view/
edit/admin roles) while still scoping it to one namespace. The binding
type controls the reach, not the role type.









4 — Workload identity + auditing a permission




# ServiceAccount annotated for Azure AD Workload Identity —
# no client secret stored in the cluster at all
apiVersion: v1
kind: ServiceAccount
metadata:
  name: ciam-app
  namespace: ciam-prod
  annotations:
    azure.workload.identity/client-id: "<managed-identity-client-id>"
  labels:
    azure.workload.identity/use: "true"

# check a permission WITHOUT deploying anything:
kubectl auth can-i get secrets \
  --as=system:serviceaccount:ciam-prod:ciam-app \
  -n ciam-prod
# → yes | no   (the real authorizer, zero side effects)

kubectl auth can-i --list \
  --as=system:serviceaccount:ciam-prod:ciam-app -n ciam-prod


Workload Identity answers "who is this pod to Azure" — it says nothing about "what may this
pod do inside the cluster". You still need the Role from section 2 for that; the two checks are
independent and both must pass.
