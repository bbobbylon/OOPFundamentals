Azure Functions — Triggers, Bindings & Hosting Plans

Serverless compute: your code is a function with a trigger (what starts it) and bindings (declarative in/out data), the Functions host wires both, and the hosting plan decides scale — Consumption scales to zero (and cold starts), Premium keeps warm instances.

⚡ What are Azure Functions — and why do triggers, bindings, and the plan matter more than the code?

A function app flips the web-server mental model: instead of a process that waits for requests, you write small functions that the platform invokes when an event happens. The trigger defines that event — an HTTP request, a message landing on a queue, a blob being uploaded, a timer firing, a Cosmos DB change-feed entry — and every function has exactly one. Bindings remove the plumbing on either side: an input binding hands your function data it would otherwise fetch (a blob's contents, a Cosmos document), and an output binding takes your return value and delivers it (enqueue a message, write a row) — declared in attributes or function.json, with no SDK code in your function body. Around your functions runs the Functions host: it listens to trigger sources, deserializes payloads into your parameters, executes your code, and handles retries — a queue message that keeps failing is moved to a poison queue after five attempts rather than looping forever. What you pay and how you scale is the hosting plan: the Consumption plan bills per execution and scales to zero — free while idle, but the first request after idleness pays a cold start while a worker is allocated and the runtime boots. The Premium plan keeps pre-warmed workers (no cold start, VNet access) for a base fee, and a Dedicated (App Service) plan runs functions on VMs you already own. For multi-step workflows, Durable Functions adds orchestrations that survive restarts by replaying recorded history — fan-out/fan-in, chaining, human-approval timeouts — without you persisting state by hand.

  • Trigger — the one event that invokes the function: HTTP, queue, timer, blob, Event Grid, Cosmos change feed.
  • Bindings — declarative inputs/outputs (read this blob, write that queue message); the host does the SDK work.
  • Host + retries — the runtime listens, deserializes, executes; failing queue messages retry ×5 then go to the poison queue.
  • Plans — Consumption: per-execution, scale-to-zero, cold starts; Premium: pre-warmed + VNet; Dedicated: your App Service plan.
  • Durable Functions — stateful orchestrations via event-sourced replay: chaining, fan-out/fan-in, timers, external events.

A queue-triggered function (Java)

@FunctionName("resizeImage") public void run( @QueueTrigger(name="msg", queueName="uploads") String msg, @BlobInput(name="in", path="raw/{queueTrigger}") byte[] img, @BlobOutput(name="out", path="thumbs/{queueTrigger}") OutputBinding<byte[]> thumb) { thumb.setValue(resize(img)); }

AWS comparison

Functions ≈ AWS Lambda (see aws-lambda-visualizer.html). Consumption plan ≈ Lambda's default pay-per-invoke; Premium ≈ provisioned concurrency; poison queue ≈ a DLQ on the event source. The big difference is bindings — Lambda has event sources but no declarative output bindings; you call the SDK yourself. Durable Functions ≈ AWS Step Functions, but expressed in code (replayed orchestrator) rather than a JSON state machine.

Spring Boot comparison

A queue trigger ≈ a @RabbitListener/@KafkaListener method — the framework listens, deserializes, and invokes; you never write the polling loop. Bindings ≈ Spring's parameter injection: declare what you need in the signature and the container supplies it. The difference is operational: your Boot app is a always-on process on servers you size; a Consumption function app is zero processes until an event arrives, and the platform sizes it per event volume.

CIAM in production: HTTP-triggered functions have platform authLevel keys (function/admin) — fine for internal webhooks, wrong for user-facing APIs. For real callers, validate an Entra ID Bearer token exactly as your Spring resource server does (JWKS, iss/aud), either in code or by fronting the function with API Management / Easy Auth. And when a function needs to reach Key Vault, Storage, or your APIs, give the function app a managed identity — connection strings in app settings are the legacy path, identity-based connections are the AZ-204 answer.

1. Triggers and bindings: declare the plumbing, write only the logic

// HTTP in → validate → queue message out. No queue SDK anywhere.
@FunctionName("placeOrder")
public HttpResponseMessage run(
  @HttpTrigger(name = "req", methods = {HttpMethod.POST},
    authLevel = AuthorizationLevel.FUNCTION, route = "orders")
    HttpRequestMessage<Order> req,
  @QueueOutput(name = "out", queueName = "orders",
    connection = "OrdersStorage") OutputBinding<Order> queue) {

  Order o = req.getBody();
  if (o.items().isEmpty()) return req.createResponseBuilder(HttpStatus.BAD_REQUEST).build();
  queue.setValue(o); // ← the output binding delivers it
  return req.createResponseBuilder(HttpStatus.ACCEPTED).build(); // 202
}
Bindings are configuration, not code. @QueueOutput names a queue and a connection setting (not a connection string literal — the value lives in app settings, ideally identity-based). Your function body just calls setValue; the host serializes and enqueues after your code returns. Swapping the destination (queue → Service Bus → Cosmos) changes the annotation, not the logic. This decoupling — accept fast with 202, process later off the queue — is the canonical serverless web pattern.

2. Hosting plans: what "serverless" costs and when it is cold

# Consumption — pay per execution, scale to ZERO (cold starts)
az functionapp create -n fn-shop -g rg-shop --consumption-plan-location eastus2 \
  --runtime java --functions-version 4 --storage-account stshopfn

# Premium — pre-warmed workers, no cold start, VNet integration
az functionapp plan create -n plan-fn-prem -g rg-shop --sku EP1 --min-instances 1

# Dedicated — run functions on an existing App Service plan (always on)
az functionapp create -n fn-shop -g rg-shop --plan plan-shop …
The plan is the AZ-204 decision point. Consumption: cheapest for bursty/low traffic, 5–10 min max execution (configurable to a cap), cold starts of a few seconds (worse for JVM apps). Premium: pre-warmed instances kill the cold start, unlimited-ish duration, VNet access to private resources — you pay for at least one warm worker. Dedicated: reuse the App Service plan you already run, enable Always On. The exam pattern: "no cold starts + access a private database" → Premium; "cheapest for a nightly job" → Consumption + timer trigger.

3. Durable Functions: workflows that survive restarts by replay

// orchestrator — describes the workflow; it will be REPLAYED, so it must be deterministic
@FunctionName("processCatalog")
public String orchestrate(@DurableOrchestrationTrigger(name="ctx") TaskOrchestrationContext ctx) {
  List<String> files = ctx.callActivity("listFiles", String.class).await();

  // FAN-OUT: one activity per file, all in parallel
  List<Task<Integer>> work = files.stream()
    .map(f -> ctx.callActivity("processFile", f, Integer.class)).toList();

  // FAN-IN: wait for all, aggregate
  List<Integer> counts = ctx.allOf(work).await();
  return "processed " + counts.stream().mapToInt(Integer::intValue).sum();
}
The orchestrator replays; activities do the work. Durable Functions checkpoints every await into a storage-backed history. If the host recycles mid-workflow, the orchestrator re-runs from the top, but completed activities return their recorded results instantly instead of re-executing — that is why orchestrator code must be deterministic (no DateTime.now(), no random, no I/O; those belong in activities). Patterns to name for the exam: function chaining, fan-out/fan-in, async HTTP APIs (202 + status polling URL), human interaction with durable timers.
