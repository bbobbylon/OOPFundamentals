Debugging Spring Proxies

You added @Transactional and the rollback still didn't happen. @Async ran on the same thread. @Cacheable never cached. The annotation is right — but Spring applies it through a proxy, and the proxy only intercepts calls that come through it. Self-invocation and non-overridable methods slip past, and the advice silently does nothing. This is the single most common "but I added the annotation!" bug.

🪞 What is a Spring AOP proxy — and why does a same-class call break @Transactional?

@Transactional, @Async, and @Cacheable don't modify your class — Spring wraps it in a proxy that sits in front of the bean. When another object calls in through the injected proxy, the proxy applies the advice (start a transaction, submit to the pool, check the cache) and then calls your method. The catch: the proxy only intercepts calls from outside. A this.anotherMethod() call goes straight to the real object and skips the proxy entirely, so the annotation on that method is ignored. It's not a bug — it's how Java dispatch works; internal calls never pass through the proxy.

  • Advice lives on the proxy, not your class. External calls get it; internal ones don't.
  • Self-invocation silently no-ops the annotation — no transaction, no async, no cache, no error.
  • Best fix: extract to another bean so the call crosses a proxy boundary.
  • final breaks CGLIB. A final method/class can't be subclassed, so it can't be proxied.

The self-invocation trap

createUserAndSendEmail() calling this.createUser() (@Transactional) and this.sendWelcomeEmail() (@Async) fires neither — no transaction, runs on the caller's thread, no error. It just silently does the wrong thing.

The fixes

Best: extract to a separate service so the call goes through the proxy. Self-inject: @Lazy @Autowired UserService self then self.createUser(...). AspectJ: load-time weaving bakes advice into bytecode (complex). Extraction is almost always right.

The final method trap

CGLIB proxies subclass your bean, so a final method can't be wrapped — @Transactional final void … is silently ignored, and a final class can't be proxied at all. Remove final from anything needing proxy annotations.

Debug proxy issues: In the debugger, inspect the injected field — a class name like UserService$$SpringCGLIB$$0 means it's a proxy; plain UserService means Spring couldn't proxy it (maybe final). For transactions, set logging.level.org.springframework.transaction=DEBUG and look for "Getting transaction for [class.method]". No such log on an annotated method = the proxy is being bypassed.

1. Why an annotation can silently no-op

Spring wraps your @Service bean in a proxy (CGLIB subclass by default). Everyone who injects the bean gets the proxy, and the proxy is what runs the @Transactional/@Async/@Cacheable/@PreAuthorize advice before delegating to your real method.

caller ──▶ UserService$$SpringCGLIB (proxy: runs advice) ──▶ UserService (your code)

The catch: inside your real object, this is the raw bean, not the proxy. So a call from one method to another in the same class (this.other()) never touches the proxy — and the advice is skipped.

Only the call that arrives through the injected proxy gets advised. The other three reach your method directly and the advice never runs — no error, just silence.

3. The proxy rules

SituationProxied?Why
External call via injected bean✓ advisedthe reference is the proxy
Self-invocation this.method()✗ bypassedthis is the raw object, not the proxy
private method✗ bypassedCGLIB can't override private methods
final method / class✗ bypassedCGLIB subclasses; can't override final
static method✗ bypassednot an instance method — nothing to override

Default proxying is CGLIB (subclass). That's why final/private/static escape it. JDK dynamic proxies (interface-based) have the same self-invocation limit.

4. The fixes

Go through the proxy

// 1) move the annotated method to ANOTHER bean
billing.charge(order);   // injected → proxied ✓

// 2) or self-inject the proxy (same class)
@Autowired OrderService self;
self.charge(order);      // via proxy ✓

Make it proxyable

  • Annotated methods must be public and non-final, on a non-final class.
  • Don't call them from the same class. If you must, use the self-inject trick or AopContext.currentProxy().
  • @Async & @Transactional can't combine on a self-call — split the responsibilities into separate beans.

5. How to confirm it at runtime

  • @Transactional: set logging.level.org.springframework.transaction=DEBUG — no "Creating new transaction" line means it didn't fire. (Or watch for writes that should have rolled back but didn't.)
  • @Async: log Thread.currentThread().getName() — if it's the caller's thread (http-nio-…), not a pool thread (task-…), it ran synchronously.
  • @Cacheable: the method body runs every time (add a log line) → the cache is being bypassed.
  • Inspect the bean: in a breakpoint, the injected type shows as …$$SpringCGLIB$$… when it's actually proxied.

6. One-sentence recap

🧩 Spring's @Transactional/@Async/@Cacheable/@PreAuthorize advice runs in a proxy that only intercepts calls arriving through the injected bean — so self-invocation (this.method()) and private/final/static methods bypass it and the annotation silently does nothing; fix it by calling through another bean (or a self-injected proxy / AopContext.currentProxy()) and keeping annotated methods public & non-final, and confirm with transaction/thread logging.
