Java Concurrency — Interview Deep Dive

Thread lifecycle, synchronization primitives, the Executor framework, CompletableFuture, common concurrency bugs, and the Java Memory Model.

What is Java concurrency — and how do threads, synchronization, and the Java Memory Model explain why multi-threaded bugs are so hard to reproduce?

Java concurrency is the ability to run multiple threads simultaneously within the same JVM process, sharing memory (heap) but each having its own stack and program counter. Concurrency enables parallelism (doing multiple things at once on multiple CPU cores) and responsiveness (keeping the UI thread free while background work runs). But shared mutable state creates hazards that are notoriously difficult to reproduce and debug: race conditions, deadlocks, and visibility issues. Thread lifecycle: NEW (created, not started) → RUNNABLE (ready to run or running) → BLOCKED (waiting for a monitor lock) → WAITING (waiting indefinitely for another thread) → TIMED_WAITING (waiting with a timeout) → TERMINATED (finished). Threads transition between states based on scheduling, lock acquisition, and calls to sleep/wait/notify. Synchronization: the synchronized keyword acquires a monitor lock (intrinsic lock) on an object. Only one thread can hold a monitor lock at a time — others block. Synchronized methods lock on this; synchronized static methods lock on the class object. Use synchronized blocks (with an explicit lock object) for finer-grained control. volatile: guarantees visibility (writes are immediately visible to all threads) but NOT atomicity. volatile int count++ is still a race condition (read-modify-write is three operations). Use AtomicInteger for atomic increment. The Java Memory Model (JMM): defines when writes by one thread become visible to another. Without synchronization, the JVM is free to cache variables in CPU registers or reorder instructions — another thread may see a stale value. The JMM guarantees a "happens-before" relationship: if action A happens-before action B, A's results are visible to B. Synchronized blocks, volatile writes/reads, and thread start/join establish happens-before. Executor framework: managing raw threads is error-prone. Use ExecutorService: Executors.newFixedThreadPool(n) creates a pool of n threads and queues tasks. submit() returns a Future (for getting results), execute() for fire-and-forget. Always shutdown() the executor when done. CompletableFuture: non-blocking async composition. Chain operations: thenApply() (transform result), thenAccept() (consume result), exceptionally() (handle errors), thenCompose() (flatMap — chain futures). Used extensively in Spring Boot's async request handling and WebFlux.

Race condition + synchronized fix

// BROKEN: race condition class Counter { private int count = 0; // count++ is READ→ADD→WRITE: 3 operations, not atomic! // Two threads can both read 0, both add 1, both write 1 // Final value: 1, not 2 public void increment() { count++; } } // FIX 1: synchronized (mutex lock) class Counter { private int count = 0; public synchronized void increment() { count++; // only 1 thread at a time can execute this } } // FIX 2: AtomicInteger (lock-free, hardware CAS instruction) class Counter { private final AtomicInteger count = new AtomicInteger(0); public void increment() { count.incrementAndGet(); // atomic compare-and-swap } // Faster than synchronized for single-variable counters }

Deadlock + ThreadPoolExecutor

// DEADLOCK: thread A waits for lock B (held by thread B) // while thread B waits for lock A (held by thread A) // Both blocked forever // Classic deadlock: // Thread 1: synchronized(lockA) { synchronized(lockB) {...} } // Thread 2: synchronized(lockB) { synchronized(lockA) {...} } // Fix: always acquire locks in the SAME order // ThreadPoolExecutor (explicit config): ExecutorService pool = new ThreadPoolExecutor( 4, // corePoolSize: min threads alive 8, // maximumPoolSize: max threads 60L, TimeUnit.SECONDS, // idle thread keepalive new LinkedBlockingQueue<>(100), // task queue (bounded!) Executors.defaultThreadFactory(), new ThreadPoolExecutor.CallerRunsPolicy() // if full: caller runs task ); pool.submit(() -> processTokenValidation(token)); // ALWAYS shutdown when done: pool.shutdown(); // graceful: finish queued tasks pool.awaitTermination(30, TimeUnit.SECONDS);

Interview / Context: Java concurrency is a heavily tested interview topic and directly relevant to your Spring Boot work. Spring Boot's Tomcat server handles each HTTP request in a separate thread from the thread pool — your Spring components must be thread-safe. @RestController beans are singletons; if they have mutable instance fields, they're shared across all request threads and prone to race conditions. Spring's ThreadLocal-based SecurityContext is the solution for storing the current user's identity — it's stored per-thread, not shared. CompletableFuture is used in Spring Boot's @Async methods and in WebClient (non-blocking HTTP calls to Ping/Entra). In interviews, deadlock and race condition questions are almost always answered with synchronized/AtomicInteger/volatile — know which tool fixes which bug.

Creating Threads — Three Ways

1. Extend Thread

class MyThread extends Thread { @Override public void run() { System.out.println( "Running in: " + Thread.currentThread() .getName()); } } new MyThread().start();
Avoid: wastes the single inheritance slot.

2. Implement Runnable

Runnable task = () -> { System.out.println( "Task running"); }; // Wrap in Thread new Thread(task).start(); // Better: use Executor ExecutorService ex = Executors .newFixedThreadPool(4); ex.submit(task);
Preferred: separates task from execution mechanism.

3. Callable + Future

Callable<Integer> task = () -> 42 * 2; Future<Integer> f = ex.submit(task); // Blocks until result ready int result = f.get(); // 84 // Non-blocking check: if (f.isDone()) { int r = f.get(); } // Cancel: f.cancel(true);
Use when you need a return value or exception from a thread.

synchronized — Mutual Exclusion

How synchronized works

Every Java object has an intrinsic monitor lock. A synchronized method or block acquires the lock on entry and releases it on exit (even if an exception is thrown).

public class Counter { private int count = 0; // synchronized method: lock is 'this' public synchronized void increment() { count++; } // synchronized block: more granular lock public void incrementBlock() { synchronized (this) { count++; } // other code runs without lock } // static synchronized: lock is Class object public static synchronized void staticMethod() { // lock on Counter.class, not 'this' } }

Race Condition Demo

// WITHOUT sync: race condition! int count = 0; // Thread 1: reads count (0), adds 1 → writes 1 // Thread 2: reads count (0), adds 1 → writes 1 // Result: 1 (expected 2!) // count++ is NOT atomic — it's 3 ops: // 1. read count from memory // 2. add 1 // 3. write back to memory // Another thread can interleave between any step! // Fix 1: synchronized synchronized(lock) { count++; } // Fix 2: AtomicInteger AtomicInteger atomicCount = new AtomicInteger(0); atomicCount.incrementAndGet(); // atomic!
Common misconception: synchronized on a method locks the object, not the method. Two synchronized methods on the same object CAN'T run concurrently from different threads. But a synchronized and a non-synchronized method CAN run concurrently.

volatile — Visibility Guarantee

// Without volatile: thread may cache the value boolean running = true; // Thread 1 (reader): while (running) { // may never see 'false'! // JVM may cache 'running' in register } // Thread 2 (writer): running = false; // Thread 1 may not see this // With volatile: always read from main memory volatile boolean running = true; // Writes are immediately visible to all threads // Prevents instruction reordering around it
volatile does NOT provide atomicity! volatile int count; count++ is still a race condition because ++ is read-modify-write, three operations. Use AtomicInteger for atomic increment.

When volatile is sufficient

// Suitable: flag checked by one thread, set by another private volatile boolean shutdown = false; public void run() { while (!shutdown) { doWork(); } } public void stop() { shutdown = true; } // Suitable: publishing an immutable object private volatile Config config; // safe publication public void update(Config c) { this.config = c; } public Config getConfig() { return config; } // NOT suitable: compound operations like check-then-act // if (count == 0) count = 1; -- still a race! // Use synchronized or AtomicInteger.compareAndSet()

Atomic Classes — Lock-Free Thread Safety

AtomicInteger, AtomicLong, AtomicReference

AtomicInteger counter = new AtomicInteger(0); counter.get(); // read counter.set(10); // write counter.incrementAndGet(); // ++count (returns new) counter.getAndIncrement(); // count++ (returns old) counter.addAndGet(5); // += 5 // CAS: Compare-And-Swap (hardware instruction) // "if current value == expected, set to update" boolean ok = counter.compareAndSet( 10, // expected 15); // update // Returns true if swap happened // AtomicReference for objects AtomicReference<Config> ref = new AtomicReference<>(initialConfig); ref.compareAndSet(old, newConfig);

ReentrantLock — Explicit Locking

Lock lock = new ReentrantLock(); // Always unlock in finally! lock.lock(); try { // critical section sharedResource.modify(); } finally { lock.unlock(); // ALWAYS release } // tryLock: non-blocking attempt if (lock.tryLock(100, TimeUnit.MILLISECONDS)) { try { /* ... */ } finally { lock.unlock(); } } // ReentrantReadWriteLock: multiple readers or one writer ReadWriteLock rwLock = new ReentrantReadWriteLock(); rwLock.readLock().lock(); // multiple OK simultaneously rwLock.writeLock().lock(); // exclusive
synchronized vs ReentrantLock: ReentrantLock adds: tryLock (non-blocking), lockInterruptibly (can be interrupted while waiting), fairness option (longest-waiting thread goes first), multiple Condition variables.

ConcurrentHashMap — Thread-Safe Map

// Hashtable: all methods synchronized — slow // Collections.synchronizedMap: lock on every call // ConcurrentHashMap: segment-level locking, O(1) ConcurrentHashMap<String,Integer> map = new ConcurrentHashMap<>(); // Atomic compound operations: map.putIfAbsent("key", 1); map.computeIfAbsent("key", k -> expensiveCompute(k)); map.merge("key", 1, Integer::sum); // Java 8+: forEach, reduce are parallel map.forEach(1, (k, v) -> process(k, v));
// CopyOnWriteArrayList: great for read-heavy // Writes create a fresh copy of the array List<String> cowList = new CopyOnWriteArrayList<>(); // Iteration never throws ConcurrentModificationException // Iterator sees snapshot at time of creation // LinkedBlockingQueue: thread-safe producer-consumer BlockingQueue<Task> queue = new LinkedBlockingQueue<>(100); queue.put(task); // blocks if full queue.take(); // blocks if empty queue.offer(task); // non-blocking, returns false

Executor Framework Modern Java Concurrency

ThreadPoolExecutor

// Executors factory methods ExecutorService fixed = Executors.newFixedThreadPool(4); ExecutorService cached = Executors.newCachedThreadPool(); ExecutorService single = Executors.newSingleThreadExecutor(); ScheduledExecutorService sched = Executors.newScheduledThreadPool(2); // Full control: ThreadPoolExecutor ExecutorService pool = new ThreadPoolExecutor( 4, // corePoolSize 16, // maximumPoolSize 60L, // keepAliveTime TimeUnit.SECONDS, new LinkedBlockingQueue<>(100), new ThreadPoolExecutor.CallerRunsPolicy() // rejection policy: run in caller's thread );

Proper Shutdown & Future

ExecutorService pool = Executors.newFixedThreadPool(4); // submit Callable, get Future Future<String> future = pool.submit(() -> { Thread.sleep(1000); return "result"; }); try { // blocks up to 2 seconds String val = future.get( 2, TimeUnit.SECONDS); } catch (TimeoutException e) { future.cancel(true); // interrupt } // Always shut down the pool! pool.shutdown(); // no new tasks, finish existing if (!pool.awaitTermination(5, TimeUnit.SECONDS)) { pool.shutdownNow(); // interrupt running threads }
Memory leak: Always shut down ExecutorService when done. If you don't, threads may run forever and prevent JVM shutdown.

Scheduled Executor

ScheduledExecutorService sched = Executors.newScheduledThreadPool(2); // Run once after 5 seconds delay sched.schedule(() -> sendReport(), 5, TimeUnit.SECONDS); // Run every 10 seconds (fixed rate — starts from previous start) sched.scheduleAtFixedRate( () -> pollMetrics(), 0, 10, TimeUnit.SECONDS); // Run 10 seconds after previous finishes (fixed delay) sched.scheduleWithFixedDelay( () -> cleanup(), 0, 10, TimeUnit.SECONDS);

CompletableFuture Java 8+

CompletableFuture is a Future that you can complete manually, chain operations on, and combine with other futures. It replaces callback hell with fluent pipelines.

Basic Usage & Chaining

// Start async task (uses ForkJoinPool by default) CompletableFuture<String> cf = CompletableFuture.supplyAsync(() -> { return fetchFromDB(); // runs in background }); // Chain: transform result cf.thenApply(data -> data.toUpperCase()) // map .thenApply(upper -> upper + "!") .thenAccept(result -> // consume System.out.println(result)) .exceptionally(ex -> { // error handler System.err.println(ex.getMessage()); return null; }); // thenApply vs thenCompose: // thenApply(f) → f returns T (like map) // thenCompose(f) → f returns CF<T> (like flatMap) cf.thenCompose(data -> asyncProcess(data)); // avoids CompletableFuture<CompletableFuture<T>>

Combining Multiple Futures

CompletableFuture<User> userFuture = CompletableFuture.supplyAsync(() -> getUser(1)); CompletableFuture<Order> orderFuture = CompletableFuture.supplyAsync(() -> getOrder(1)); // thenCombine: when BOTH complete CompletableFuture<String> combined = userFuture.thenCombine(orderFuture, (user, order) -> user.name + ": " + order.id); // allOf: wait for ALL to complete CompletableFuture.allOf(userFuture, orderFuture) .thenRun(() -> System.out.println("Both done!")); // anyOf: first to complete wins CompletableFuture.anyOf(primary, fallback) .thenAccept(result -> use(result)); // Custom thread pool (avoid using default ForkJoinPool) Executor pool = Executors.newFixedThreadPool(8); CompletableFuture.supplyAsync(() -> work(), pool);
thenApplyAsync vs thenApply: Async variants execute the callback in the thread pool, not in the completing thread. Use async when the callback is expensive. Non-async runs in whichever thread completed the future (could be the calling thread or a pool thread).

Concurrency Problems Must Diagnose

Deadlock

Thread A holds lock 1 and waits for lock 2. Thread B holds lock 2 and waits for lock 1. Neither can proceed.

// Classic deadlock pattern Object lock1 = new Object(); Object lock2 = new Object(); // Thread A synchronized(lock1) { Thread.sleep(100); synchronized(lock2) { // WAITS for lock2 doWork(); } } // Thread B (runs concurrently) synchronized(lock2) { Thread.sleep(100); synchronized(lock1) { // WAITS for lock1 doWork(); // DEADLOCK! } } // Fix: always acquire locks in same order // Thread A AND Thread B: lock1 then lock2

Detecting & Preventing Deadlocks

// Prevention strategies: // 1. Lock ordering — always same sequence // 2. tryLock with timeout if (!lock1.tryLock(100, TimeUnit.MS)) { return; // give up, retry later } // 3. Use higher-level abstractions // (ConcurrentHashMap, etc.) — no manual locking // Detection: jstack or JConsole shows threads // "waiting to lock <0x...> held by thread-1" // jstack PID | grep -A 20 "BLOCKED" // Thread dump key words: // "waiting to lock" = BLOCKED on synchronized // "parking to wait for" = waiting on lock.lock() // "Found 1 deadlock" = jstack finds it for you

Starvation

// Thread never gets CPU time // because high-priority threads keep winning // With unfair ReentrantLock (default): // High-priority threads may cut the queue // Fix: fair locking (may reduce throughput) Lock fairLock = new ReentrantLock(true); // fair=true // Longest-waiting thread gets the lock next // Also: avoid low thread priority // Thread t = new Thread(task); // t.setPriority(Thread.MIN_PRIORITY) → starves!

Java Memory Model (JMM)

Happens-Before Relationship

The JMM defines visibility rules: if action A happens-before action B, then A's effects are visible to B. Without happens-before, the JVM can reorder instructions for optimization.

// Happens-before rules: // 1. Thread start: all actions before t.start() // happen-before any action in thread t // 2. Monitor lock: unlock HB lock by any thread synchronized(lock) { data = 42; } // unlock // ... later ... synchronized(lock) { use(data); } // lock sees 42 // 3. volatile write HB volatile read volatile int v; v = 10; // write — HB // ... other thread ... int x = v; // read sees 10 // 4. Thread join: all actions in t HB after t.join() thread.join(); // this thread now sees all of t's work // 5. Transitivity: A HB B, B HB C → A HB C
