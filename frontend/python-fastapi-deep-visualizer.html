FastAPI Deep Dive

FastAPI routes, Pydantic validation, dependency injection, OAuth2 Bearer auth, background tasks, and how it maps to Spring Boot concepts you already know.

🚀 What is FastAPI — and how does it compare to Spring Boot?

FastAPI is Python's closest equivalent to Spring Boot — a modern async REST framework on Starlette + Pydantic that auto-generates OpenAPI docs. Routes are decorated async functions; path/query/body/header params are declared as function parameters and validated automatically. Request bodies are typed Pydantic models (a 422 with field errors on failure = @Valid + Bean Validation). It has built-in DI via Depends(...) (inject a DB session or the current user from a JWT), background tasks (≈ @Async), and Swagger at /docs with zero config.

  • Python's Spring Boot — async routes, validation, DI, OpenAPI out of the box.
  • Pydantic validates request bodies — typed models, automatic 422s (≈ @Valid).
  • Depends(...) is the DI system — inject DB sessions, the current user from a JWT.
  • /docs Swagger is free — built from your models and routes.

The problem

You wrote async def because it sounded faster. It was the dangerous one.

One blocking line, and the whole server stops answering

An async def endpoint runs directly on the event loop — a single thread that every concurrent request in the process shares. Put one blocking call in it (requests.get, a sync SQLAlchemy query, time.sleep, a bcrypt hash) and nothing else runs for the whole of it. Not the other requests. Not the health check. Nothing.

1 slow endpoint ⚠ p99 on EVERY route climbs ⚠ /health times out ⚠ k8s restarts a healthy pod ⚠

The endpoint you broke gets slower. Every endpoint you did not touch gets slower with it, which is why this is so hard to find from a dashboard.

FastAPI already handles this — if you let it
Plain def → FastAPI runs it in a threadpool, off the loop ↓ so blocking code in a def endpoint is SAFE, and this is the boring default async def → runs on the loop, and must never block ↓ so everything inside it has to be awaitable, all the way down Need both? await run_in_threadpool(fn) or an async driver
async def is not "the fast one" — it is the one with a rule. The rule is that nothing inside it may block, and the punishment for breaking it is paid by every other request in the process, not by yours. If your handler calls blocking code, plain def is both simpler and faster in practice.

The mechanism

Every concurrent request in this process funnels through one thread.

POST /usersGET /users/42webhook from PingGET /health…every other request…
↓ all served by a single event loop thread, interleaved only at each await
the event loopone thread · progresses only when the current coroutine yields

This is the trade the whole model rests on, and it is a good one: one thread can juggle thousands of connections because each coroutine gives the loop back at every await. But "gives it back" is the entire deal — a coroutine that runs two seconds of blocking work never yields, so for those two seconds the loop is not juggling anything. It is running your function. Concurrency here is cooperative, and one uncooperative handler is enough.

async def + blocking call
async def get_user(id): return db.query(...) — runs on the loop, blocks it for the whole query. Ten concurrent requests take ten times as long each, and every unrelated route waits behind them.
Plain def + the same blocking call
def get_user(id): return db.query(...) — FastAPI runs it in a worker thread. The loop stays free, the other routes keep answering, and you changed one keyword. Removing async made it faster.

And the same rule applies to dependencies, which is where it hides best. A Depends() function is inspected exactly like a path operation: declare it def and FastAPI runs it in the threadpool, declare it async def and it runs on the loop. So a shared get_current_user dependency that does a blocking token-introspection call, written async def because everything else was, blocks the loop on every authenticated request in the app — while the endpoints themselves look completely innocent. When you cannot change the call, wrap it: await run_in_threadpool(introspect, token) from starlette.concurrency, or await asyncio.to_thread(...).

Two endpoints do the identical blocking 2-second database call. One is def read_a(), the other is async def read_b(). Ten concurrent requests hit each. What happens?

Right, and the direction surprises almost everyone. FastAPI inspects your signature: plain def gets moved to a threadpool (40 workers by default), so ten 2-second calls overlap and finish in about two seconds. The async def version runs on the loop, and since the call never awaits, the ten queue up to roughly twenty seconds — and every other route in the process queues behind them.

The call takes 2 seconds in both cases; what differs is what else can happen during it. That is the whole question. Where the work runs decides whether it overlaps with anything, and here it decides a 10× difference.

Interleaving requires the coroutine to yield, which only happens at an await. A blocking driver call has no await in it, so there is no point at which the loop can switch — async without an awaitable underneath buys you nothing and costs you the threadpool.

Questions from the back row

How do I tell whether a library call blocks?

The signature is the tell: if you are not writing await in front of it, it is blocking. requests blocks and httpx.AsyncClient does not; psycopg2 blocks, asyncpg does not; SQLAlchemy blocks unless you are on its async engine and awaiting. If the async ecosystem has no version of what you need — a C library, an SDK with no async client — that is a perfectly good reason to write a plain def endpoint and let the threadpool earn its keep.

What are BackgroundTasks actually good for, then?

Returning to the client before the slow work finishes — a Ping sync, a welcome email. But be clear about what they are not: they run in the same process, after the response, on the loop or the threadpool by the same def/async def rule. So they still consume this server's capacity, and if the pod is killed mid-task the work is simply gone with no retry. Fine for best-effort side effects; use Celery or a real queue for anything that must actually happen.

Does a Pydantic model actually validate at runtime, or is it types like TypeScript?

It genuinely validates, and this is the sharpest difference from every TypeScript page in this hub. A Pydantic model is a real runtime check that parses, coerces and rejects — closer to Spring's @Valid on a DTO than to a TS interface. So an endpoint typed user: UserCreate is guaranteed a valid UserCreate inside the body, and a bad payload was already rejected with a 422 you did not write. That is a promise the TypeScript equivalent cannot make.

1. FastAPI vs Spring Boot — the Same Idea

🌿 Spring Boot (Java)
@RestController  // registers this class as a Spring MVC controller bean
@RequestMapping("/users")
public class UserController {
  @Autowired
  private UserService svc;  // field injection — works, but constructor injection is preferred

  @PostMapping
  @ResponseStatus(CREATED)
  public UserDto create(  // return type IS the response body — Jackson serializes it automatically
    @Valid @RequestBody CreateUserReq req) {
    return svc.create(req);  // business logic lives in the service, not the controller
  }
}
🐍 FastAPI (Python)
from fastapi import FastAPI, Depends
from pydantic import BaseModel

app = FastAPI()

class CreateUser(BaseModel):  # BaseModel gives validation + serialization for free — no separate DTO class needed
    name: str
    email: str

@app.post("/users", status_code=201)
async def create_user(  # async — FastAPI runs this on the event loop, not a blocked worker thread
    body: CreateUser,
    db: Session = Depends(get_db)  # Depends() is FastAPI's DI — same idea as Spring's @Autowired
):
    return svc.create(body, db)  # body is ALREADY validated — Pydantic did it on the way in

Both frameworks: route → inject dependencies → validate input → call service → return response. FastAPI uses Python type hints where Spring uses annotations.

2. Pydantic Models = Spring's @Valid + DTO in One

from pydantic import BaseModel, EmailStr, Field
from typing import Optional

class CreateUser(BaseModel):
    name: str = Field(min_length=2, max_length=50)
    email: EmailStr
    age: Optional[int] = None

# Pydantic VALIDATES and COERCES on construction:
user = CreateUser(name="Alice", email="alice@example.com", age="30")
# age="30" (string) → coerced to int 30
user.age  # 30 (int), not "30" (str)

3. Dependency Injection — Depends()

from fastapi import Depends, HTTPException, status
from fastapi.security import OAuth2PasswordBearer

oauth2_scheme = OAuth2PasswordBearer(tokenUrl="token")

async def get_current_user(token: str = Depends(oauth2_scheme)):
    user = verify_jwt(token)
    if not user:
        raise HTTPException(status_code=401)
    return user

async def require_admin(user = Depends(get_current_user)):
    if "admin" not in user.roles:
        raise HTTPException(status_code=403)
    return user
