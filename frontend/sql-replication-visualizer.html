Replication & High Availability

WAL streaming, sync vs async replicas, read-routing lag, and what actually happens when the primary dies.

🔁 What does "replicated" actually guarantee — and what does it quietly not?

PostgreSQL replication works by streaming the WAL (Write-Ahead Log) — the same durability log used for crash recovery — from a primary to one or more standby servers, which continuously replay it. Asynchronous replication (the default) lets the primary commit and acknowledge the client the instant its own WAL write is durable, without waiting for any replica — fast, but a replica can lag behind by anywhere from milliseconds to seconds, and a read routed to a lagging replica can return data that's already stale on the primary. Synchronous replication flips that trade: the primary blocks the COMMIT until at least one named replica confirms it has received (and optionally flushed) the WAL — zero data loss if the primary dies a moment later, at the cost of every write now paying a network round-trip to the replica. Failover — promoting a replica to primary when the original dies — is where the two modes diverge hardest: an async replica can be promoted while still missing the last few WAL bytes the old primary generated (silent data loss), while a synchronous replica is guaranteed current as of the last acknowledged commit.

  • WAL streaming — the crash-recovery log doubles as the replication stream; a replica is "just" a server that never stops replaying WAL.
  • Async (default) — primary doesn't wait for replicas; fast writes, but replicas (and reads routed to them) can be stale.
  • Sync — primary blocks COMMIT until a named replica acks; zero data loss on failover, higher write latency.
  • Failover risk is asymmetric — promoting an async replica can lose the last few committed transactions; a sync replica can't.

Setting up streaming replication

# primary: postgresql.conf wal_level = replica max_wal_senders = 10 wal_keep_size = 1GB # primary: pg_hba.conf — allow the replica to connect host replication repl_user 10.0.2.0/24 scram-sha-256 # on the replica, after a base backup: # postgresql.conf hot_standby = on primary_conninfo = 'host=10.0.1.5 port=5432 user=repl_user' -- check replication status on the primary: SELECT client_addr, state, sent_lsn, replay_lsn, write_lag, flush_lag, replay_lag FROM pg_stat_replication;

Synchronous replication

# primary: postgresql.conf synchronous_standby_names = 'replica-1' synchronous_commit = on -- primary now blocks COMMIT until replica-1 -- confirms it received (and by default flushed) -- the WAL for that transaction -- per-transaction override (Spring can set this -- via a native query for critical writes only): SET LOCAL synchronous_commit = remote_apply; -- levels, cheapest to strictest: -- off < local < remote_write < on < remote_apply

Read-replica routing in Spring Boot

// two DataSources: primary (writes) + replica (reads) @Transactional(readOnly = true) public List<Order> listOrders() { // routed to the replica DataSource return orderRepo.findAll(); } @Transactional public Order placeOrder(Order o) { // routed to the primary DataSource return orderRepo.save(o); } // AbstractRoutingDataSource picks primary vs replica // based on TransactionSynchronizationManager // .isCurrentTransactionReadOnly()

Replication in a CIAM stack: route the admin user-search UI's reads to a replica (it's read-heavy and tolerates a second of staleness), but route "read your own write" paths — a user updating their own profile and immediately re-fetching it — straight to the primary, or the app will render its own stale write back to the user. Refresh-token validation and login-event writes should never go to a replica at all. If you run synchronous replication for refresh_tokens, promoting a replica during an outage guarantees you don't silently resurrect an already-rotated token.

2 — Read-Replica Lag Is Not a Bug, It's the Trade




A replica isn't "eventually consistent" by accident — it's the whole point of async replication. replay_lag in pg_stat_replication tells you how far behind, in real time, the replica currently is.


-- on the primary: how far behind is each replica right now?
SELECT client_addr, replay_lag, sync_state
FROM pg_stat_replication;

--  client_addr | replay_lag | sync_state
--  10.0.2.11   | 00:00:00.04 | async     -- 40ms behind, normal
--  10.0.2.12   | 00:00:04.80 | async     -- 4.8s behind — investigate!

-- app-side guard: don't trust a replica that's fallen too far behind
SELECT extract(epoch FROM now() - pg_last_xact_replay_timestamp());









3 — Failover: Promoting a Standby




-- manual promotion (or automated via Patroni / pg_auto_failover)
$ pg_ctl promote -D /var/lib/postgresql/data

-- what promotion actually does:
-- 1. replica stops replaying WAL from the old primary
-- 2. replica starts accepting writes as the new primary
-- 3. any WAL the old primary generated but never shipped is GONE
--    (unless synchronous_commit guaranteed it was already there)


This is why "we have a replica" is not the same claim as "we have zero-data-loss failover" — the second claim depends entirely on which synchronous_commit level was in effect for the transactions that mattered.









4 — Spring Boot: Routing Reads to a Replica




@Configuration
public class RoutingDataSourceConfig {
  @Bean
  public DataSource routingDataSource(
      DataSource primaryDs, DataSource replicaDs) {
    var routing = new AbstractRoutingDataSource() {
      @Override
      protected Object determineCurrentLookupKey() {
        boolean readOnly = TransactionSynchronizationManager
            .isCurrentTransactionReadOnly();
        return readOnly ? "replica" : "primary";
      }
    };
    routing.setTargetDataSources(Map.of(
        "primary", primaryDs, "replica", replicaDs));
    routing.setDefaultTargetDataSource(primaryDs);
    return routing;
  }
}
