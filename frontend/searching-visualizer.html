Searching — Linear vs Binary

Two ways to find an item. The difference scales from "a little faster" to "millions of times faster" as data grows.

🧩 What is linear vs binary search — and why does the O(log n) vs O(n) difference matter catastrophically at scale?

Searching is the act of finding a specific element in a collection. How efficiently you search depends entirely on what you know about the data's structure. Linear Search: scan every element from start to finish until you find the target or exhaust the list. No prerequisites — works on any array (sorted or unsorted, numbers or strings). Time complexity: O(n) — in the worst case (element not present or at the end), you check all n elements. For 1,000,000 elements, that's up to 1,000,000 comparisons. Binary Search: requires the array to be sorted. Works by repeatedly halving the search space. Start with the full range [lo, hi]. Compute mid = (lo + hi) / 2. If arr[mid] == target, done. If arr[mid] > target, the answer must be in the left half — set hi = mid - 1. If arr[mid] < target, it must be in the right half — set lo = mid + 1. Repeat. Each iteration eliminates HALF the remaining elements. Time complexity: O(log₂ n) — for 1,000,000 elements, at most 20 comparisons. For 1,000,000,000 elements, at most 30 comparisons. The math: why log n is so powerful: log₂(1,000,000) ≈ 20. Linear search: 1,000,000 steps. Binary search: 20 steps. That's a 50,000× speedup — not "a little faster" but "fundamentally different class of algorithm." The requirement: sorted data. Binary search only works on sorted arrays. If data arrives unsorted, you can sort once in O(n log n) and then binary search repeatedly — if you need many searches, the upfront sort cost pays off. Java provides Arrays.binarySearch() and Collections.binarySearch() for this. Key implementation pitfall: mid = (lo + hi) / 2 can overflow for large lo and hi (both close to Integer.MAX_VALUE). Always use mid = lo + (hi - lo) / 2 — this is identical mathematically but never overflows. Variations: "find first occurrence," "find last occurrence," "find insertion position" (where would this element go if inserted?) — all variations of binary search by slightly tweaking the comparison logic.

Linear search — O(n)

// Linear search: works on ANY array (sorted or not) // Worst case: scan every element → O(n) int linearSearch(int[] arr, int target) { for (int i = 0; i < arr.length; i++) { if (arr[i] == target) { return i; // found at index i } } return -1; // not found } // Performance comparison: // n=10: linear=10 binary=4 comparisons // n=1,000: linear=1000 binary=10 // n=1,000,000: linear=1M binary=20 // n=1,000,000,000: linear=1B binary=30 // Use linear when: // • Data is unsorted and you won't sort it // • n is tiny (<50 elements) // • You need the first element matching a complex condition

Binary search — O(log n)

// Binary search: REQUIRES SORTED array // Each step eliminates HALF the remaining elements int binarySearch(int[] arr, int target) { int lo = 0, hi = arr.length - 1; while (lo <= hi) { int mid = lo + (hi - lo) / 2; // SAFE: avoids overflow if (arr[mid] == target) { return mid; // FOUND } else if (arr[mid] < target) { lo = mid + 1; // target is in RIGHT half } else { hi = mid - 1; // target is in LEFT half } } return -1; // not found } // Trace: arr=[1,3,5,7,9,11,13], target=7 // iter1: lo=0,hi=6, mid=3, arr[3]=7 → FOUND at index 3! // (only 1 comparison for 7-element array in this case)

Binary search variations

// Java built-in (returns index or -(insertionPoint)-1): int idx = Arrays.binarySearch(sortedArr, target); // Find FIRST occurrence of target (duplicates): int firstOccurrence(int[] arr, int target) { int lo=0, hi=arr.length-1, result=-1; while (lo <= hi) { int mid = lo + (hi-lo)/2; if (arr[mid] == target) { result = mid; // found one, but keep searching LEFT hi = mid - 1; // look for earlier occurrence } else if (arr[mid] < target) lo = mid+1; else hi = mid-1; } return result; } // Find insertion point (where would target go?): // Use lo after loop completes: // while (lo <= hi) { ... } // return lo; // position to insert to maintain sorted order // (This is Java Arrays.binarySearch negative result = -(lo)-1)

In CIAM / Context: Binary search is fundamental to CIAM at scale. Token validation often involves checking against a sorted allowlist/denylist — O(log n) vs O(n) matters when you're validating millions of tokens per hour. Sorted OAuth scope arrays use binary search to check if a requested scope is in the granted scope list. Entra ID's RBAC permission evaluation sorts permission strings and uses binary search. Database B-Tree indexes (used by every PostgreSQL table backing your CIAM user store) are binary-search trees applied to disk blocks — the reason "add an index" transforms a query from O(n) full-table-scan to O(log n). Understanding this makes you a much better SQL query planner.

2. The two algorithms in detail

Linear Search

Time: O(n) · Space: O(1)

Just walk through the array, comparing each element to the target.

When you should use it
  • Array is unsorted (no choice)
  • Array is small (under ~50 elements, the constant factor wins)
  • You only search a few times (sorting first would cost more)
Java implementation
int linearSearch(int[] arr, int target) {
    for (int i = 0; i < arr.length; i++) {
        if (arr[i] == target) return i;
    }
    return -1;
}

Binary Search

Time: O(log n) · Space: O(1) (iterative)

Check the middle; if too small, search the right half. If too big, the left half. Repeat.

When you should use it
  • Array is sorted (required!)
  • Array is large (the speedup is massive)
  • You search the same array many times (worth pre-sorting)
  • Looking up a name in a phone book / dictionary entry
Java implementation
int binarySearch(int[] arr, int target) {
    int low = 0, high = arr.length - 1;
    while (low <= high) {
        int mid = (low + high) / 2;
        if (arr[mid] == target) return mid;
        if (arr[mid] < target) low = mid + 1;
        else                  high = mid - 1;
    }
    return -1;
}

4. The catch — the sorting cost

Binary search assumes the array is sorted. Sorting itself is O(n log n) — far slower than a single linear search. So when does sorting pay off?

  • Search once? Just use linear. Sorting + binary = O(n log n + log n) ≫ O(n).
  • Search many times? Sort once, then every search is O(log n). The cost amortizes.
  • Data already structured? Use a HashMap for O(1), or a TreeMap for O(log n) + ordering.
  • In Java: Arrays.binarySearch(arr, target) for sorted arrays; Collections.binarySearch(list, target) for sorted Lists.
