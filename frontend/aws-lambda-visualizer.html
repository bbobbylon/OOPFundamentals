Lambda — Serverless Functions

Lambda runs code without provisioning servers. You write a function, Lambda handles everything else — capacity, scaling, patching, and availability. Pay only for execution time: 1M requests free per month forever.

⚡ What is AWS Lambda — and when does serverless make more sense than an always-on Spring Boot ECS service?

Lambda is serverless compute: you supply a function, AWS handles containers, scaling 0→thousands, patching and availability, and you pay only for the milliseconds your code runs. A warm start reuses a loaded container (10-100ms); a cold start spins up a fresh one — painful for Java + Spring (JVM + context init = 3-10s). Mitigate with Provisioned Concurrency (keep N warm), SnapStart (restore a post-init JVM snapshot, ~10× faster), or lighter frameworks (Quarkus/Micronaut). Limits: 15-min timeout, 10GB memory, 250MB package. It's event-driven (S3, SQS, EventBridge, API Gateway). Rule of thumb: Lambda for bursty, short, event-driven jobs; ECS for always-on heavy Spring Boot services.

  • Lambda = serverless functions — scales 0→thousands, pay per millisecond.
  • Cold vs warm start — Java + Spring cold start is 3-10s; warm is 10-100ms.
  • Fix cold starts — Provisioned Concurrency, SnapStart, or Quarkus/Micronaut.
  • Lambda vs ECS — bursty event-driven jobs vs always-on heavy services.

// Lambda function handler (Java): public class UserExportHandler implements RequestHandler<S3Event, String> { // Static init runs ONCE per container (warm) // or on each cold start private static final S3Client s3 = S3Client.builder() .region(Region.US_EAST_1) .build(); // Handler invoked per event @Override public String handleRequest(S3Event event, Context ctx) { String bucket = event.getRecords().get(0) .getS3().getBucket().getName(); String key = event.getRecords().get(0) .getS3().getObject().getKey(); // Process uploaded CSV of users to provision S3Object obj = s3.getObject( GetObjectRequest.builder() .bucket(bucket).key(key).build()); // ... parse CSV, call Ping to provision users return "Processed " + key; } } // Triggered: S3 PUT event on uploads/ prefix

Lambda vs ECS: when to use each

# Use LAMBDA when: ✓ Event-driven (S3 trigger, SQS consumer, cron) ✓ Bursty traffic (0 to thousands in seconds) ✓ Short-lived (seconds, not minutes) ✓ Cost-sensitive (pay per ms, not per hour) ✓ Light code (Python/Node glue scripts) # CIAM Lambda use cases: - Nightly user export to S3 (EventBridge cron) - Process bulk user import CSV (S3 trigger) - Send welcome email after registration (SQS) - Rotate Ping client secrets on schedule - Webhook receiver from Ping (low frequency) # Use ECS FARGATE when: ✓ Always-on Spring Boot API ✓ Heavy Spring context (slow cold start) ✓ Persistent connections (WebSocket, gRPC) ✓ Consistent traffic (Reserved cost less) ✓ Stateful session handling # CIAM ECS use cases: - Main auth service (/login, /token, /userinfo) - Admin API (user management CRUD) - OAuth 2.0 authorization server - Real-time audit log streaming service

In CIAM / Context: The core auth API (login, token exchange, userinfo) runs on ECS Fargate — always-on, fast, Spring Boot. Lambda handles async/batch jobs: nightly user export, bulk provisioning from CSV, welcome emails, scheduled Ping client-secret rotation. These fit Lambda because they're infrequent, short and cost-sensitive — and the 15-minute timeout is plenty for a 10,000-user CSV import.

1 — Cold Start vs Warm Start

The biggest Lambda concern for Java. On first invocation (or after idle), Lambda must initialize everything before running your code:

Cold Start (Java — can be 2–10 seconds)
🥶 Runtime Init
JVM startup, class loading
~1–5s for Java
⚙️ Handler Init
static initializers,
Spring context (~1–3s)
✓ Handler
your code
~50–200ms
Warm Start (subsequent invocations)
✓ Handler Execution Only — ~50–200ms
Lambda reuses the existing execution environment — no init overhead
Strategies to reduce Java cold starts:
  • Provisioned Concurrency — pre-warm N instances (pay for idle time)
  • Smaller deployment package — fewer classes to load
  • GraalVM native image — compile to native binary, no JVM startup
  • Avoid Spring Boot in Lambda — use plain handler or Micronaut/Quarkus
  • SnapStart — AWS snapshots the initialized JVM (Java 21+ runtime)
  • Increase memory — more memory = more CPU = faster init

2 — Common Lambda Triggers

🌐

API Gateway

HTTP REST/WebSocket API
HTTP requests invoke a Lambda. API Gateway handles auth (Cognito/IAM), rate limiting, CORS. Best for serverless REST APIs. Latency: add ~10–30ms API GW overhead.
🗂️

S3 Events

Object created / deleted
Lambda fires when a file is uploaded to S3. Use cases: image resizing (thumbnail generation), CSV parsing, triggering ETL pipelines. Invoked asynchronously.
⏰

EventBridge (Cron)

Scheduled events
Run Lambda on a schedule (cron or rate expression). Example: "every day at 2 AM, generate a report." Replaces scheduled jobs without servers. Cron uses UTC.
📨

SQS Queue

Message queue consumer
Lambda polls SQS and invokes your function with batches of messages (up to 10,000). Auto-scales. On failure, messages go to DLQ. Great for async processing.
📡

SNS Topic

Push notifications / fan-out
SNS pushes messages to Lambda immediately (no polling). Fan-out: one SNS message can trigger multiple Lambda functions. Use for event-driven architectures.
🗃️

DynamoDB Streams

DB change events
Lambda reacts to inserts/updates/deletes in a DynamoDB table. Use for: cache invalidation, audit logging, syncing data to Elasticsearch, real-time aggregations.
🔒

Cognito Triggers

Auth lifecycle hooks
Hook into Cognito user pool events: pre-signup validation, post-confirmation setup, pre-token-generation (add custom claims to JWTs), custom authentication challenge.
🔁

Function URL / ALB

Direct HTTPS endpoint
Function URLs give your Lambda a dedicated HTTPS endpoint without API Gateway. ALB can also invoke Lambda as a target — good for integrating with existing ALB routing rules.

3 — Java Lambda Handler

// pom.xml dependency <dependency> <groupId>com.amazonaws</groupId> <artifactId>aws-lambda-java-core</artifactId> <version>1.2.3</version> </dependency> <dependency> <groupId>com.amazonaws</groupId> <artifactId>aws-lambda-java-events</artifactId> <version>3.11.0</version> </dependency> // Simple Java handler (no Spring Boot — avoids cold start) public class ReportGeneratorHandler implements RequestHandler<ScheduledEvent, String> { // Static initializer runs once per container (warm start reuses this) private static final S3Client s3 = S3Client.create(); @Override public String handleRequest(ScheduledEvent event, Context context) { context.getLogger().log("Generating daily report at: " + event.getTime()); byte[] reportBytes = generateReport(); s3.putObject(PutObjectRequest.builder() .bucket("reports-bucket") .key("daily/report-" + LocalDate.now() + ".pdf") .build(), RequestBody.fromBytes(reportBytes)); return "Report generated successfully"; } } // Handler string in Lambda config: "com.example.ReportGeneratorHandler" // Trigger: EventBridge cron(0 2 * * ? *) — every day at 2:00 AM UTC

// API Gateway proxy handler — receives HTTP event public class ApiHandler implements RequestHandler<APIGatewayProxyRequestEvent, APIGatewayProxyResponseEvent> { private static final ObjectMapper mapper = new ObjectMapper(); @Override public APIGatewayProxyResponseEvent handleRequest( APIGatewayProxyRequestEvent input, Context ctx) { String path = input.getPath(); // "/users/123" String method = input.getHttpMethod(); // "GET" String body = input.getBody(); // request JSON body try { UserDto user = userService.findById(path.split("/")[2]); return new APIGatewayProxyResponseEvent() .withStatusCode(200) .withHeader("Content-Type", "application/json") .withBody(mapper.writeValueAsString(user)); } catch (NotFoundException e) { return new APIGatewayProxyResponseEvent().withStatusCode(404) .withBody("{\"error\":\"User not found\"}"); } } }

5 — Lambda Configuration Reference

SettingDescription
Memory128 MB–10 GB. CPU scales linearly with memory — more memory = more CPU = faster execution AND faster cold start. Start with 512 MB for Java.
TimeoutMax 15 minutes. API Gateway has a 29-second hard limit — Lambda behind API GW must finish in 29s. Set timeout = 29s for API-facing functions.
ConcurrencyDefault 1000 concurrent executions per region (soft limit). Each in-flight request = 1 concurrent execution. One Lambda instance handles one request at a time.
Reserved ConcurrencyGuarantee a minimum and cap a maximum number of concurrent executions for a specific function. Prevents one noisy function from consuming all concurrency.
Provisioned ConcurrencyPre-initialize N execution environments. Eliminates cold starts. You pay for provisioned capacity even when idle. Use for latency-critical endpoints.
LayersZip files containing shared code/libraries. Attach up to 5 layers per function. Example: a shared "utils" layer, a custom JRE layer.
Environment VarsKey-value pairs injected at runtime. Encrypted at rest with KMS. Store config like DB URLs, API keys, feature flags.
IAM Execution RoleLambda assumes this role to call AWS services. Define least-privilege permissions — only what the function needs. S3 functions need s3:PutObject, etc.
VPC ConfigPlace Lambda in your VPC to access private resources (RDS, ElastiCache). Adds 100–200ms to cold start (ENI provisioning). Use VPC Endpoints to avoid NAT Gateway costs.
SnapStart (Java)Snapshots the initialized JVM after init phase. Subsequent cold starts restore from snapshot — reduces Java cold start from ~5s to ~1s. Java 21 runtime only.
