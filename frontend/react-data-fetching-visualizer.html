Data Fetching & TanStack Query

Server state is not client state — it's async, shared, cached, and can go stale behind your back. TanStack Query (React Query) manages it: caching, deduping, stale-while-revalidate, background refetch, and mutations with optimistic updates.

🛰️ What is server state — and why does TanStack Query replace manual useEffect fetching?

There are two kinds of state: client state (data you own — inputs, toggles) and server state (remote data you don't own — it goes stale, needs caching, syncing, sharing). TanStack Query handles server state: useQuery fetches and caches by key, dedupes (two components, one request), and returns {data, isLoading, isError}. It's stale-while-revalidate (instant cache, background refetch), useMutation handles writes with invalidateQueries to refresh, and optimistic updates make UIs feel instant. Manual useEffect+fetch+useState reimplements only 20% of it — use TanStack Query for any server data.

  • Server state ≠ client state — it goes stale and needs caching/sync/sharing.
  • useQuery caches by key & dedupes — many consumers, one request.
  • Stale-while-revalidate — instant cached data, background refetch.
  • useMutation + invalidateQueries writes then refreshes; optimistic updates feel instant.

useQuery basics

// Setup: wrap app with QueryClientProvider const queryClient = new QueryClient({ defaultOptions: { queries: { staleTime: 60_000 } } // 1min }); <QueryClientProvider client={queryClient}> <App /> </QueryClientProvider> // Fetch users function UserList() { const { data: users, isLoading, isError, error, isFetching } = useQuery({ queryKey: ['users'], // cache key queryFn: () => fetch('/api/users', { headers: authHeader() }) .then(r => r.json() as Promise<UserDto[]>), staleTime: 30_000, // consider fresh for 30s gcTime: 5 * 60_000, // keep in cache 5 min after unmount }); if (isLoading) return <Spinner />; if (isError) return <p>Error: {error.message}</p>; return <ul>{users!.map(u => <UserRow key={u.id} user={u} />)}</ul>; }

Angular HttpClient comparison

TanStack Query feature → Angular equivalent. useQuery(['users'], fetchFn) → this.http.get<UserDto[]>('/api/users') (no caching — refetches every subscription). staleTime / caching → no built-in equivalent in Angular — you'd implement with shareReplay(1) + manual invalidation. isFetching background indicator → manually track with a BehaviorSubject. invalidateQueries → no built-in; you'd call the service method again. useMutation onSuccess → tap/switchMap in an RxJS pipe. TanStack Query brings significant value over raw HttpClient for real-world apps: automatic deduplication, background refresh, stale detection, optimistic updates. Angular's HTTP Interceptors handle auth headers centrally — equivalent to React's authHeader() function passed to fetch.

CIAM React app: Each resource gets a query key — ['users'], ['users', userId], ['users', userId, 'roles']. enabled: !!userId defers a parameterized query until the id is known; useInfiniteQuery with getNextPageParam handles cursor pagination; prefetchQuery on hover warms the cache before navigation; and a role mutation invalidates ['users', userId, 'roles'] on success.

The problem

Open the Network tab on a component that just mounts and fetches, and in development you see the SAME request fire twice.

The "duplicate" request that a teammate's fix makes worse

You write the textbook version: useEffect(() => { fetch('/api/users/42').then(r => r.json()).then(setForm) }, []). In production this fires once, like the docs say. In development, the Network tab shows it fire TWICE, back to back, for the exact same URL.

A teammate "fixes" it by deleting <React.StrictMode> from main.jsx. The duplicate call vanishes — case closed, right? Except nothing about your code changed; you just turned off the one tool that was warning you your effect isn't safe to run twice. StrictMode intentionally mounts, simulates an unmount (running your cleanup), then remounts — specifically so effects with missing or wrong cleanup get caught in DEVELOPMENT, before something else in production (a route re-visit, a parent re-key, a remount you didn't plan for) legitimately remounts the same component and fires the same uncancelled request for real.

the URL is correct ✓ the data that comes back is correct ✓ no AbortController to cancel the first, now-orphaned request ⚠

Removing StrictMode doesn't fix your effect. It just removes the thing that was telling you it was broken.

Give the effect a cleanup, and let StrictMode keep testing you
Put StrictMode back — treat the double-fire as free test coverage ↓ it's the cheapest remount test you'll get: if your effect survives React deliberately abusing it, it survives a real remount in production Add cancellation — an AbortController per effect run, aborted in the cleanup ↓ the first call's response is now discarded instead of racing to call setForm after the component has already moved on And step three: or just use TanStack Query — useQuery already dedupes and cancels this correctly (see section 1 above)
The one-sentence rule. React 18's StrictMode deliberately mounts, cleans up, and remounts every component once in development specifically to expose effects that assume "mount" only ever happens once — a raw fetch in useEffect with no AbortController is exactly that assumption, and disabling StrictMode only hides the symptom you were supposed to go fix.
StrictMode's double-invoke is a fire drill, not a fire. "Fixing" a fire drill by disabling the fire alarm doesn't make the building safer — it just means nobody hears about the next real fire until it's already spreading.

The mechanism

Trace what StrictMode actually does to your effect, in order.

  1. Component mounts — React runs your effect, fetch #1 goes outmount 1
  2. StrictMode immediately simulates an unmount — your effect's cleanup runs, if you wrote onesimulated unmount
  3. No cleanup means fetch #1 is still in flight, uncancelled, with nothing tracking it anymoreorphaned
  4. StrictMode remounts the component — React runs your effect again, fetch #2 goes outmount 2
  5. Both fetch #1 and fetch #2 are now racing toward the SAME setForm calltwo in flight
  6. Whichever resolves LAST wins and overwrites state — usually #2, but not guaranteedthe real bug

Step 6 is why this matters beyond a noisy Network tab: two in-flight requests racing to call the same setForm is exactly the stale-response race this page already teaches you to fix with AbortController — StrictMode just gives you a free, guaranteed reproduction of it every time you load the page in development, instead of only on a slow network in production.

Mount render → effect runs, fetch #1 starts
Simulated unmount StrictMode, dev only → cleanup runs (or doesn't exist)
Remount React re-renders → effect runs again, fetch #2 starts

This loop runs exactly once, only in development, only inside StrictMode — but it's rehearsing something that happens for real in production every time a component with this effect remounts: a route you navigate back to, a list item whose key changes, a parent that briefly unmounts its child. StrictMode just moved that rehearsal to your machine today instead of a user's machine in three weeks.

A component fetches a user record in a plain useEffect with no cleanup and no AbortController. In development (StrictMode on) the Network tab shows two identical requests on every mount. A teammate removes StrictMode and the second request disappears. Is the fetch effect now correct?

Exactly — the fetch still has no cancellation. It will still race itself the next time this component legitimately remounts in production (a route re-entry, a changed key, a flickering parent); you've only removed your early warning system.

StrictMode's double-invoke exists to catch far more than fetch races — missing cleanups on subscriptions, timers, and event listeners all show the same symptom. And "the duplicate call is gone" isn't the same as "the effect is safe" — it means the test stopped running, not that the code passed it.

TanStack Query is exactly the fix — but only if you're actually using useQuery. A plain useEffect plus fetch, which is what's described here, gets none of that deduplication or cancellation for free; you'd have to add it yourself with an AbortController.

Where you have seen this before

Deliberately breaking an assumption on purpose, safely, before reality breaks it for you, is a pattern that shows up everywhere.

Angular's takeUntilDestroyed()

An Angular HttpClient subscription that never unsubscribes has the exact same failure mode: a component that gets destroyed and recreated (inside an *ngIf toggle, or a route re-entry) leaves an old subscription alive, racing a new one to update state that no longer belongs to it. takeUntilDestroyed() is Angular's version of the cleanup this page is asking for.

orphaned subscription racing a fresh one

Idempotency keys in payment APIs

A payment gateway expects clients to retry failed requests, which means the SAME logical operation can arrive twice — servers handle it with an idempotency key so a retried "charge $50" doesn't charge twice. StrictMode is forcing your COMPONENT to prove it can survive being invoked twice for the "same" mount — the same discipline, a different layer.

designed to survive being called twice, on purpose

Chaos engineering

Deliberately killing production instances in a controlled way proves the rest of the system tolerates a real failure before an uncontrolled one happens. StrictMode's double-invoke is chaos engineering in miniature: React deliberately breaks the "mount happens once" assumption in dev, on your machine, before an uncontrolled version breaks it for a user.

break it on purpose, safely, before reality does

1. Server state vs client state

Client state (useState)Server state (TanStack Query)
You own it; it's always up to dateYou don't own it; it can change on the server
SynchronousAsynchronous (fetch, latency, errors)
Local to a component/treeShared by many components; should be deduped + cached
e.g. "is this dropdown open?"e.g. "the list of users from /api/users"
The insight that sells the library: the loading/error/caching/refetch/dedup/retry logic you hand-write around every useEffect fetch is the same logic every time. TanStack Query is that logic, done correctly once. You write a queryKey and a queryFn; it handles the rest.

2. The core API

const { data, isPending, isError, error, isFetching } = useQuery({
  queryKey: ['user', userId], // cache identity (serializable)
  queryFn: () => fetchUser(userId), // returns a promise
  staleTime: 60_000, // fresh for 60s → no refetch
});
Option / flagMeaning
staleTimeHow long data is "fresh"; while fresh, no refetch happens (default 0 = instantly stale)
gcTime (was cacheTime)How long inactive (unused) cache is kept before garbage collection (default 5 min)
isPending vs isFetchingisPending = no data yet; isFetching = a request is in flight (incl. background refetch)

3. Stale-while-revalidate

When a query has cached (but stale) data, TanStack Query shows the cached data instantly and refetches in the background. The user never stares at a spinner for data they've already seen — the screen updates only if the new data differs.

This is why React Query apps feel fast. Navigate away and back, and the list is there immediately (from cache) while a quiet background refetch keeps it correct. Compare to raw useEffect, where every mount starts from a blank loading state.
