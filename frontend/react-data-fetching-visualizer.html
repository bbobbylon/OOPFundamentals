Data Fetching & TanStack Query

Server state is not client state — it's async, shared, cached, and can go stale behind your back. TanStack Query (React Query) manages it: caching, deduping, stale-while-revalidate, background refetch, and mutations with optimistic updates.

1. Server state vs client state

Client state (useState)Server state (TanStack Query)
You own it; it's always up to dateYou don't own it; it can change on the server
SynchronousAsynchronous (fetch, latency, errors)
Local to a component/treeShared by many components; should be deduped + cached
e.g. "is this dropdown open?"e.g. "the list of users from /api/users"
The insight that sells the library: the loading/error/caching/refetch/dedup/retry logic you hand-write around every useEffect fetch is the same logic every time. TanStack Query is that logic, done correctly once. You write a queryKey and a queryFn; it handles the rest.

2. The core API

const { data, isPending, isError, error, isFetching } = useQuery({
  queryKey: ['user', userId], // cache identity (serializable)
  queryFn: () => fetchUser(userId), // returns a promise
  staleTime: 60_000, // fresh for 60s → no refetch
});
Option / flagMeaning
staleTimeHow long data is "fresh"; while fresh, no refetch happens (default 0 = instantly stale)
gcTime (was cacheTime)How long inactive (unused) cache is kept before garbage collection (default 5 min)
isPending vs isFetchingisPending = no data yet; isFetching = a request is in flight (incl. background refetch)

3. Stale-while-revalidate

When a query has cached (but stale) data, TanStack Query shows the cached data instantly and refetches in the background. The user never stares at a spinner for data they've already seen — the screen updates only if the new data differs.

This is why React Query apps feel fast. Navigate away and back, and the list is there immediately (from cache) while a quiet background refetch keeps it correct. Compare to raw useEffect, where every mount starts from a blank loading state.
