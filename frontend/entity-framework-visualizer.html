Entity Framework Core — DbContext, LINQ→SQL & Tracking

EF Core is .NET's ORM and the direct cousin of Spring Data JPA / Hibernate: a DbContext is the unit of work, LINQ queries translate to SQL, change tracking generates your UPDATEs, and migrations evolve the schema from your model — with the same N+1 trap to avoid.

🗄️ What is EF Core — and how is it Spring Data JPA in C#?

Entity Framework Core is the standard object-relational mapper for .NET. A DbContext is your session and unit of work (≈ a JPA EntityManager / Hibernate Session): it exposes DbSet<T> collections (≈ JPA repositories) and tracks the entities you load. You query with LINQ, and EF translates the whole expression tree into a single SQL statement run in the database — _db.Users.Where(u => u.Age > 18).ToListAsync() becomes a parameterized SELECT … WHERE. Because the context tracks loaded entities, you simply mutate a property and call SaveChangesAsync(); EF compares snapshots, generates the minimal UPDATE/INSERT/DELETE, and runs them in one transaction (the unit-of-work pattern). Relationships load eagerly via Include() or lazily — and lazy loading inside a loop is the famous N+1 query problem, exactly as in Hibernate. Schema changes are code-first migrations: change the model, scaffold a migration, apply it. If you know JPA, you know EF Core.

  • DbContext = session + unit of work (≈ EntityManager); DbSet<T> ≈ a repository.
  • LINQ → one SQL statement — filtering/sorting/paging happen in the database.
  • Change tracking — mutate + SaveChanges() generates the minimal UPDATE.
  • N+1 trap — fix with Include() / projection, just like Hibernate fetch joins.

Query + update

// LINQ → SQL, executed in the DB var adults = await _db.Users .Where(u => u.Age >= 18) .OrderBy(u => u.Name) .ToListAsync(); // change tracking does the UPDATE for you var u = await _db.Users.FindAsync(42); u.Email = "new@x.com"; // just mutate await _db.SaveChangesAsync(); // → UPDATE Users SET Email=@p WHERE Id=42

DbContext & entities

public class AppDb : DbContext { public DbSet<User> Users => Set<User>(); public DbSet<Order> Orders => Set<Order>(); } public class User { public int Id { get; set; } // PK by convention public string Email { get; set; } = ""; public List<Order> Orders { get; set; } = []; // nav prop } // registered Scoped: AddDbContext<AppDb>(...)

Spring Data JPA comparison

DbContext ≈ EntityManager + the persistence context. DbSet<User> ≈ a JpaRepository<User,Long>. LINQ ≈ JPQL/Criteria, but strongly typed and IDE-checked. SaveChangesAsync() ≈ flush/commit with dirty checking. .Include(u => u.Orders) ≈ JOIN FETCH / @EntityGraph. The N+1 problem is identical. Migrations ≈ Flyway/Liquibase but generated from your entity model (code-first). AddDbContext registers it Scoped — one context per request, like an @PersistenceContext.

CIAM data layer: A user/consent store on EF Core reads naturally: _db.Users.Include(u => u.Consents).FirstOrDefaultAsync(u => u.Subject == sub) pulls a user and their consents in one query keyed by the token sub. The Scoped DbContext means every repository in a request shares one unit of work, so a multi-step consent update commits atomically in SaveChangesAsync(). Watch the N+1 trap when listing users with their roles — project to a DTO or Include the roles, or you fire one query per user.

You made two slow queries run at the same time. EF Core threw an exception instead of saying thank you.

The problem

Task.WhenAll on one DbContext does not halve your latency — it fails the request outright, and the error message blames threads you never created.

"A second operation was started on this context instance before a previous operation completed."

Your dashboard endpoint makes three independent reads: a user count, an order count, and the last ten audit rows. They take 120 ms each and they do not depend on each other, so you do the obvious thing and overlap them: await Task.WhenAll(usersTask, ordersTask, auditTask), with each task a _db.Something.CountAsync(). Three hundred and sixty milliseconds should become a hundred and twenty.

Instead the endpoint throws InvalidOperationException on the second query. AddDbContext registers the context Scoped — one instance for the whole request — so all three tasks are talking to the same DbContext, which owns one connection and one change tracker and was never built to hold two conversations at once. The message says "usually caused by different threads," which sends everybody hunting for a thread bug. There is no thread bug. EF's concurrency detector fires on overlapping operations, so a single thread that starts a second query before awaiting the first trips it just as reliably.

the three queries are genuinely independent ✓ Task.WhenAll is the right tool for independent work ✓ they all share one Scoped DbContext ⚠

The unit of work you love for SaveChanges is the same object that refuses to be used twice at once.

Give each parallel branch its own context, or stop parallelising
First ask whether you need the overlap at all — three sequential awaits on one context are correct and boring ↓ most "parallel" ORM code saves a few milliseconds and costs a production incident If you do want real concurrency, register AddDbContextFactory<AppDb>() and create a context inside each task ↓ await using var db = await factory.CreateDbContextAsync(); — a fresh context, its own connection, its own tracker Never let a fire-and-forget continuation touch the request's context — that request's scope may already be disposed ↓ same class of bug, later timing, worse error: ObjectDisposedException instead of a clean failure And leave the thread-safety checks on; turning them off removes the exception, not the race
One DbContext holds one conversation at a time. It is a unit of work, a change tracker, an identity map and a database connection wrapped in one object, and every one of those parts assumes operations happen in sequence. EF Core guards this with a concurrency detector that throws the moment a second operation begins while one is still in flight. That guard is keyed to overlapping work, not to thread identity, which is why a perfectly single-threaded Task.WhenAll triggers it. Concurrency in EF Core is spelled "more contexts," never "more tasks on one context."
A DbContext is a single-lane bridge, not a motorway. Task.WhenAll is you waving three lorries on at once. The bridge does not widen — the barrier comes down, and the sign it flashes says "must be other drivers," which is why you spend an hour looking for other drivers.
You

Three independent reads, awaited together. Why is that a second operation?

The Scoped DbContext

Because there is one of me. AddDbContext gives the whole request a single instance — your three tasks did not get three contexts, they got three references to me.

The concurrency detector

I do not compare thread IDs. I set a flag when an operation starts and clear it when it finishes. Your second query found the flag already set, so I threw before anything could corrupt the change tracker.

IDbContextFactory

Ask me inside each task and everyone gets their own context, their own connection and their own tracker. Then Task.WhenAll does exactly what you expected the first time.

The mechanism

Follow the three tasks from the DI scope to the exception, in the order the runtime actually does it.

  1. The request opens a DI scope; AddDbContext resolves one AppDb for everything in itone instance
  2. Your handler calls _db.Users.CountAsync() — it starts executing and returns a Task<int> you have not awaited yetin flight
  3. The concurrency detector marks the context busy for the duration of that operationflag set
  4. The very next line calls _db.Orders.CountAsync() on the same instance, while the first is still openoverlap
  5. The detector sees the flag already set and throws InvalidOperationException — before any SQL is sentthrow
  6. Task.WhenAll surfaces the faulted task; your dashboard returns 500 and the log points at threads500

Step four is where the damage is done, and notice it happens before any await. An async method runs synchronously until its first real suspension, so calling a second query one line later is not "later" in any sense the context cares about — the first operation has not completed. This is also why the bug is timing-shaped: with two very fast queries the first sometimes finishes before the second starts, the request succeeds in dev, and the exception waits for the day the database is slow. Intermittent is the worst kind of correct.

Read it bottom-up the next time this message lands in your logs: the exception never tells you which line opened the first operation, only where the second one collided with it. All three shapes above are really the same shape — an operation that is still running when the next one begins — and the middle one is the sneakiest, because a missing await inside a foreach compiles, returns a Task nobody watches, and usually only overlaps once the loop gets long enough.

In one request handler, with the standard builder.Services.AddDbContext<AppDb>(...) registration, you write await Task.WhenAll(_db.Users.CountAsync(), _db.Orders.CountAsync());. Both queries are read-only. What happens?

Connection pooling is real, but it is a level below where this breaks. A DbContext holds its connection and will not acquire a second one to serve itself; the limit is the context, not the pool. And read-only does not help — the detector guards every operation, because materializing results touches shared state inside the context regardless of whether you plan to save anything.

Where you have seen this before

Every persistence session you have ever used is single-conversation; the ones that look concurrent are handing out copies.

Hibernate's Session is not thread-safe either

On the Spring side the rule is identical: a JPA EntityManager and the Hibernate Session behind it are single-threaded objects, and the transaction is bound to the thread by TransactionSynchronizationManager. Kick off CompletableFutures inside a @Transactional method and the child threads do not merely share the session unsafely — they cannot see the transaction at all. The .NET answer is a context factory; the Java answer is a new EntityManager per thread, which is the same answer wearing different syntax.

a session belongs to one thread's work

The ADO.NET layer underneath says the same thing, louder

Drop below EF to raw SqlConnection and try to run a second command while a SqlDataReader is still open, and SQL Server tells you there is already an open data reader associated with this command — unless you explicitly enable MultipleActiveResultSets, which is off by default. That is the physical reason the bridge has one lane: one connection, one active result stream. EF's exception is the polite version of a constraint that exists all the way down at the wire protocol.

one connection, one active reader

node-postgres: Client versus Pool

A single pg.Client can run exactly one query at a time; hand the same client to two overlapping handlers and the queries queue or misbehave, which is precisely why the library ships a Pool and the docs push you to it. Different language, different ORM, same architecture: the object that represents a connection is not the object you parallelise. When you want concurrency, you ask something for another one.

parallelism comes from more clients, not more calls

1. Tracking vs no-tracking

// tracked (default) — entities are watched for changes
var u = await _db.Users.FindAsync(42);
u.Email = "x@y.com"; await _db.SaveChangesAsync(); // auto UPDATE

// no-tracking — read-only, faster, no snapshots kept
var list = await _db.Users.AsNoTracking()
  .Where(u => u.Active).ToListAsync(); // for GET endpoints
Use AsNoTracking() for read-only queries. Tracking keeps a snapshot of every loaded entity so SaveChanges can diff them — useful for updates, wasteful for a read-only list endpoint. No-tracking skips the snapshots: less memory, faster. It is the EF equivalent of a read-only JPA query.

2. The N+1 problem and its fix

// ❌ N+1: 1 query for users, then 1 per user for their orders
var users = await _db.Users.ToListAsync(); // 1 query
foreach (var u in users)
  Console.WriteLine(u.Orders.Count); // +1 query each (lazy)

// ✅ eager-load with Include → ONE query (a JOIN)
var users = await _db.Users
  .Include(u => u.Orders).ToListAsync(); // 1 query total

100 users → 101 queries vs 1. The exact same trap as Hibernate lazy loading. Fix with Include() (a JOIN), or project only the columns you need with Select().
