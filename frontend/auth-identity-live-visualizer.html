🔐 What is this — and why does it matter?

Every secured app answers two questions on every request: "who are you?" (authentication) and "are you allowed?" (authorization). The answer travels in a JWT — a signed token the browser attaches to each call. This page runs that whole loop against a live backend so you can see it, not just read about it.

  • Log in — the server checks your password and hands back a signed token containing your roles.
  • Call a protected endpoint — the browser sends Authorization: Bearer <token>.
  • The server verifies the signature, reads the roles out of the token, and lets @PreAuthorize decide.
  • You get 200 (allowed), 401 (not authenticated), or 403 (authenticated but not permitted).

The request's journey

  1. Login → password check
  2. Server signs a JWT with roles
  3. Browser sends Bearer token
  4. Security filter chain verifies
  5. @PreAuthorize decides

Token flavors

  • First-party (HS256) — your own backend signs it
  • OIDC (RS256) — an external IdP signs it (Entra / Ping / Keycloak)
  • Same authorization outcome, different plumbing
Why it matters for CIAM:this is the exact shape of a CIAM app — a SPA, an identity provider that mints tokens, and a resource server that trusts them. Toggling first-party vs OIDC here mirrors comparing your own login against Entra/Ping-issued tokens in production.

or, 401 means "try again" and 403 means "don't bother" — and your interceptor needs to know the difference

The problem

The refresh worked perfectly. The request failed anyway. Then it did it again.

A retry loop that burns refresh tokens to re-ask a question that was never about the token

The three status codes above look like a severity scale — 401 bad, 403 worse — so a lot of interceptors get written to treat "any auth failure" the same way: run a silent refresh, retry once, and if it fails again, log the user out. It is a reasonable-looking five lines and it is wrong in both directions.

A user with a perfectly valid token but no ROLE_ADMIN calls a protected endpoint and gets 403. The interceptor sees a failure, refreshes, retries — and receives exactly the same 403, because the server never had any doubt about who they were. Nothing about a new token changes an authorization decision. Best case you have wasted a round trip and a token rotation. Worst case the retry logic loops, or the "log them out after two failures" rule fires and ejects a legitimate user for clicking a button they were never allowed to click.

token valid ✓ signature, exp fine ✓ identity known ✓ refresh: pointless ⚠ same 403, plus a logout ⚠

The two codes answer two different questions. Collapse them into one branch and you have a client that cannot tell "prove who you are" from "you are not allowed."

Branch on the code, because the code is the instruction
401 → the server does not know you. Refresh silently, retry once, and only then send them to log in ↓ this is the one case where retrying is meaningful, because a fresh token really can change the answer 403 → the server knows you and said no. Do not refresh, do not retry — show a real message ↓ "You need the Admin role for this" beats a spinner followed by a mysterious logout And on the server: return 404 rather than 403 when the 403 itself would reveal that something exists
401 is a question about identity; 403 is a verdict about permission. One invites you to come back with better credentials, the other tells you that credentials were never the problem. That is why they are separate codes rather than degrees of the same one — and why the status code is not just a result but an instruction to the client about what to do next. Getting it wrong does not only mislead a developer reading logs; it makes your frontend behave incorrectly.
401 is "I can't hear you, say that again." 403 is "I heard you perfectly. No." Repeating yourself is the right response to exactly one of those, and doing it to the other is how a conversation becomes an argument.
You

They both mean the request failed. Why does the distinction matter to my code?

401 Unauthorized

Because I am a misnomer — I actually mean unauthenticated. No token, an expired one, a bad signature: I cannot tell who you are. I am the one code where retrying with something better genuinely helps, which is why I come with a WWW-Authenticate header telling you how to try.

403 Forbidden

And I am the opposite. I know precisely who you are — your token is valid and I read it. The answer is still no, and it will be no for every identical request you make until somebody changes your roles. There is nothing to retry. Treating me as a transient failure is how clients end up in loops.

404 Not Found

And occasionally you should send me instead of 403 — on a private resource, "forbidden" confirms the thing exists, which is sometimes the only fact the attacker was after. It is why a private repository you cannot see returns "not found" rather than "not allowed." Same instinct as never revealing whether an account exists at the login page.

The mechanism

Where each code is decided — and they are decided in different places.

  1. Request arrives with Authorization: Bearer …. The security filter chain runs before any controllernothing of yours has executed yet
  2. No token, expired, or a bad signature → the entry point returns 401. Your controller is never reached, and never learns a request happenedauthentication failed
  3. Token valid → an Authentication is built, its claims mapped to authorities, and the request continuesidentity established
  4. @PreAuthorize evaluates. Denied → the access-denied handler returns 403, and the method body still never runsauthorization failed
  5. Allowed → your code finally runs, and any 404 from here is a genuine "no such row"the only layer that sees your data
  6. Except where you deliberately convert a 403 into a 404 to avoid confirming that the resource existsa decision, not an accident

Steps 2 and 4 are handled by two different components — an authentication entry point and an access-denied handler — which is the clearest possible signal that these are not two flavours of one failure. It also explains a detail that confuses people in the logs: a 403 proves your token was valid, so seeing 403s is evidence authentication is working. If you are debugging a login problem and you see 403, stop looking at the token; the token was fine.

Rows three and four return the identical code for opposite reasons, and that is the point: from outside, a resource you may not see should be indistinguishable from one that is not there. Inside, log them differently — the caller learns nothing, and the on-call engineer reading the logs at 2am learns everything.

Your Angular interceptor catches auth failures, runs a silent token refresh, and retries the request once. A logged-in user whose token is valid but who lacks ROLE_ADMIN calls DELETE /api/users/42. What does the interceptor achieve?

A refresh reissues a token for the same user, so unless somebody granted them the ADMIN role in the seconds between the two calls, the new token carries the same authorities as the old one. The old token was not expired in the first place — that is what makes this a 403 rather than a 401. Retrying repeats an identical question and receives an identical answer.

Correct, and this is why the interceptor must branch on the status code rather than on "did it fail". Refresh-and-retry belongs under 401, where a better credential genuinely can change the outcome. Under 403 the right move is to surface a real message — "you need the Admin role" — because the user can act on that, and a spinner followed by a silent logout is the worst possible translation of "no".

A 403 has no effect on the session at all: the token remains valid, unexpired and usable for every endpoint the user is allowed to call. Sessions end when a token expires or is explicitly revoked, never as a side effect of one denied request. Wiring a logout to 403 means a single misclick on an admin-only button signs a legitimate user out — which is a bug your users will report as "it randomly logs me out."

Where you have seen this before

Every protocol eventually needs "try again" and "stop trying" to be different words.

4xx versus 5xx, and what a retry policy is really keyed on

The whole reason HTTP splits client errors from server errors is so a caller knows whether repeating the request could possibly help. A 500 or 503 may succeed on retry; a 400 never will, however many times you send it. 401 and 403 are that same split applied one level deeper, inside the auth failures.

retryable vs terminal, all the way down

Checked versus unchecked exceptions, arguing the same point in Java

The intent behind the distinction was exactly this: some failures a caller can do something about, and some it cannot. Catching everything in one catch (Exception e) and retrying is the server-side twin of an interceptor that treats 401 and 403 identically — losing the one piece of information that told you what to do.

a failure type is advice, not just a label

Why the names are backwards, and why it is worth knowing

401 is named "Unauthorized" but means unauthenticated; 403 "Forbidden" is the real authorization failure. The names were fixed before the vocabulary settled, and they now mislead every newcomer in the same direction. Worth saying out loud once in a code review, because the mix-up survives entirely on nobody mentioning it.

What you just saw

The token carries the authority

After login, decode the token (middle box on the right): the roles claim is right there in the payload. The server doesn't hit the database to authorize — it reads the roles out of the signed token. That's why a JWT is "stateless auth": the proof of who you are and what you may do travels with every request.

401 vs 403 — a crucial difference

401 Unauthorized = the server doesn't know who you are (no token, or an expired/forged one). 403 Forbidden = it knows exactly who you are, but your roles don't grant this resource. Run demo → Admin area for a real 403, then admin → Admin area for a real 200 — same endpoint, decision flips on one role.

HS256 vs RS256. First-party mode mints an HS256 token your backend signs and verifies with one shared secret. OIDC mode mints an RS256 token signed with a private key and verified with the matching public key from the backend's /oauth2/jwks — the exact pattern a resource server uses to trust Entra / Ping.
