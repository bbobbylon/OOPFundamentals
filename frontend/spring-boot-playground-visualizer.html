How the gauntlet decides

Filter chain → URL security (before the controller)

The SecurityFilterChain runs first. It authenticates the Bearer token, then authorizeHttpRequests matches the URL against ordered rules (first match wins): no auth where required → 401; authenticated but missing the role → 403. This happens before any controller code.

Dispatcher → @PreAuthorize (at the method)

If URL security passes, the DispatcherServlet finds a handler — none → 404. Then method security (@PreAuthorize) is a second gate evaluated per method and its arguments → 403 if it fails. Only then does the controller run → 200.

Two independent authorization gates (URL rules + method security), two ways to get a 403. See the Security Filter Chain and Method Security deep-dives.

Recap

🍃 A request runs a gauntlet: authenticate the token → URL authorization (authorizeHttpRequests, first match wins) → dispatch to a handler (none → 404) → method security (@PreAuthorize) → controller → 200. Missing authentication is 401; present-but-insufficient is 403 — and there are two places that 403 can come from. Change the caller's authorities and watch the same request flip between 200, 403, and 404.
