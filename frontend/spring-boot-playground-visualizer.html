🌱 What is this — and what gauntlet does a request run?

Every request into a secured Spring Boot app passes through a fixed pipeline before your controller method ever sees it. This page renders that exact pipeline as a sequence of checkpoints, so you can watch which checkpoint stops a request — and why — instead of just getting a status code with no explanation.

  • Security filter chain — runs first, on every request. Checks the JWT signature and extracts the caller's authorities before anything else happens.
  • URL authorization — matches the request path against configured rules (e.g. /admin/** requires ROLE_ADMIN) — this is a coarse, path-based gate.
  • DispatcherServlet — Spring MVC's front controller; routes the (now-authenticated) request to the matching @RestController method.
  • @PreAuthorize — a fine-grained, method-level check (e.g. hasAuthority('DELETE:USER')) evaluated right before the method body runs.
  • Any checkpoint can reject the request — a rejection at the filter chain looks different (401) from one at @PreAuthorize (403), even though both mean "denied."

The gauntlet, in order

  1. Security filter chain (JWT)
  2. URL authorization (path rules)
  3. DispatcherServlet (routing)
  4. @PreAuthorize (method rule)
  5. Your controller method runs

Reading the verdict

  • 200 — passed every checkpoint
  • 401 — no/invalid token (filter chain)
  • 403 — authenticated but not permitted
  • 404 — no matching route at all
Why it matters for CIAM:this is the precise chain a CIAM app's authority strings travel through — knowing whether a rejected request died at the filter chain (401, bad/missing token) or at @PreAuthorize (403, valid token but wrong role) is the first diagnostic question in any real access-denied bug.

The problem

Your token is valid. The URL matched an allowed pattern. Postman still shows a 403, and you're out of ideas.

Everything you know how to check says this request should work

You configured authorizeHttpRequests so /api/** requires authentication, and it does — the token's signature checks out, it isn't expired, and the path matches. So you assume authorization is done and move on to debugging something else. It isn't done. There's a second, independent gate sitting on the controller method itself, and it's asking a completely different question than the one you just answered.

JWT signature valid ✓ path matches /api/** ✓ filter chain lets it through ✓ @PreAuthorize on the method itself ⚠

The wrong assumption: that "the URL rule allowed it" and "this caller is authorized" are the same fact.

Every checkpoint has to say yes; any single one saying no is enough to stop the request. That's why this page walks a request through four separate gates instead of one boolean "authorized?" — the filter chain, URL authorization, the dispatcher, and @PreAuthorize each know a different, narrower slice of the answer. The status code tells you which one fired: 401 means the filter chain never let the caller in the door; 403 means they got in and a later gate, almost always @PreAuthorize, said no anyway; 404 means nobody even asked, because the route doesn't exist.
Think of it like an office building. The badge reader at the front door is the filter chain — it only confirms you're a real employee. The floor directory is URL authorization — it says "this floor is Sales," a broad, path-shaped rule. The lock on one specific office door is @PreAuthorize — having a working badge and standing on the right floor still doesn't mean you have a key to that door. It stops being a perfect analogy at the front desk: a real security guard checks your badge once, but Spring re-checks a version of "who are you" at more than one layer on purpose, because each layer is answering a narrower question than the last.

The mechanism

Four gates, one request — and the instant one of them says no, nothing downstream even runs.

  1. The raw request arrives, with or without a Bearer token in the Authorization headernothing decoded yet
  2. The security filter chain validates the JWT's signature and expiry, and builds an Authenticationfails here → 401, nothing else runs
  3. authorizeHttpRequests matches the path against configured rulescoarse, path-only — doesn't know which method will run
  4. DispatcherServlet resolves the path to one specific @RestController methodno match → 404, a routing problem, not a security one
  5. @PreAuthorize evaluates its SpEL expression against the now-known callerfails here → 403 — the token was fine, the authority wasn't
  6. The controller method body finally executeseverything before this line was a gate, not the work

Step 5 is the lesson. Steps 2 through 4 only prove you're a legitimate caller allowed somewhere near this general area of the API — none of them know anything about the specific method you're calling. @PreAuthorize is the only checkpoint that reads the expression written for this method, which is why a 403 here is more informative than it feels: every general check passed, and there's exactly one narrow, deliberate rule left to go read.

It doesn't matter whether the caller is anonymous, a logged-in employee, or an admin — every request enters the identical four-stage pipeline, in the identical order, every single time. What differs is only where a particular caller's request happens to fail, if it fails at all. The pipeline itself never branches by who's asking.

A caller sends a completely valid JWT — good signature, not expired — but the token's authorities don't include the one @PreAuthorize requires. What status code comes back, and did the controller method's body ever run?

Right. 403 means "authenticated but forbidden" — the caller proved who they are, and @PreAuthorize still said no. One thing worth noticing: that annotation runs as AOP advice wrapping the call, so the method body never gets a chance to execute even its first line — there's no partial side effect to clean up.

A very reasonable read of the word "Unauthorized" — it's genuinely a confusing name, and even the HTTP spec's authors have said it should have been called "Unauthenticated." But Spring reserves 401 specifically for "the filter chain doesn't know who you are" — missing or invalid credentials. A caller who's fully authenticated but simply lacks a permission gets 403, one gate later.

This is the exact assumption the page above is built to break: that clearing the filter chain is the whole security story. It isn't — it's one of four independent gates, and @PreAuthorize is a separate, later check that the filter chain has no visibility into at all.

Where you've seen this before

"Broad rule, then a narrower one layered on top" isn't a Spring idea — it shows up anywhere permissions get checked twice, on purpose.

Kubernetes: RBAC, then admission control

RBAC answers a coarse question first — can this service account delete pods at all, generally? An admission webhook runs after RBAC already said yes, and can still reject the exact same request based on details RBAC never looks at, like what's actually inside the pod spec. Same two-layer shape: broad-and-early, then narrow-and-late.

RBAC = URL authorization · admission control = @PreAuthorize

AWS IAM: identity policy vs. resource policy

Your Lambda's IAM role can grant s3:GetObject broadly, and the call still fails if the S3 bucket's own resource policy independently denies it. Two policies, evaluated at two different layers, and both have to agree — exactly the "every checkpoint has to say yes" principle above, just wearing AWS's vocabulary instead of Spring's.

two independent policies, both must allow

Ping / Entra: token scopes vs. your app's own role check

The identity provider only promises the token carries a broad scope like api.read — it has no idea your app has a concept of "can only edit your own profile." That finer rule lives entirely in your Spring app's @PreAuthorize expressions, evaluated well after the IdP's job is already done.

the IdP hands you a scope, not a decision
Questions from the back row

If URL authorization already lets the request through, isn't checking @PreAuthorize too just redundant?

No — they check different things at different granularity, not the same thing twice. URL rules operate on the path before Spring even knows which Java method will run, so they can only express broad ownership: "logged-in users can reach /api/**." @PreAuthorize runs once the specific method — and often specific arguments, like #userId — is known, so it can express things a path pattern structurally cannot, such as "only if this path's id matches your own." They're two different questions, and both are cheap enough that skipping either buys you nothing.

Why does this page ever show a 404 instead of a 401 or 403 — doesn't security get checked first?

Because 404 isn't a security outcome at all — it's DispatcherServlet failing to find a matching @RequestMapping, which happens after the filter chain and URL authorization have already let the request through (or never had a specific rule to apply in the first place). Hit a genuinely nonexistent endpoint with a perfectly valid token and you still get 404, because there was never a method for @PreAuthorize to evaluate in the first place.

Could Spring check @PreAuthorize before URL authorization, if you wanted it to?

No, and not for configuration reasons — for structural ones. The filter chain, URL authorization included, is a servlet Filter, which by definition runs before the servlet (DispatcherServlet) that figures out which controller method applies. @PreAuthorize is AOP advice wrapped around that specific method call, so it literally cannot evaluate before Spring knows which method is being invoked. The order isn't a style choice; it's forced by what each mechanism is built on top of.

How the gauntlet decides

Filter chain → URL security (before the controller)

The SecurityFilterChain runs first. It authenticates the Bearer token, then authorizeHttpRequests matches the URL against ordered rules (first match wins): no auth where required → 401; authenticated but missing the role → 403. This happens before any controller code.

Dispatcher → @PreAuthorize (at the method)

If URL security passes, the DispatcherServlet finds a handler — none → 404. Then method security (@PreAuthorize) is a second gate evaluated per method and its arguments → 403 if it fails. Only then does the controller run → 200.

Two independent authorization gates (URL rules + method security), two ways to get a 403. See the Security Filter Chain and Method Security deep-dives.

Recap

🍃 A request runs a gauntlet: authenticate the token → URL authorization (authorizeHttpRequests, first match wins) → dispatch to a handler (none → 404) → method security (@PreAuthorize) → controller → 200. Missing authentication is 401; present-but-insufficient is 403 — and there are two places that 403 can come from. Change the caller's authorities and watch the same request flip between 200, 403, and 404.
