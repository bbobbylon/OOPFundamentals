Spring Batch — Jobs, Steps & Chunk Processing

Process millions of records reliably. Spring Batch handles retry, skip, partitioning, restartability and job history automatically.

1. Why Batch Processing?

ETL Pipelines
Extract from source DB → Transform data → Load into data warehouse. Nightly sync of 5M rows.
Scheduled Reports
Month-end billing run, generate invoices for 100K customers, send email per customer.
Data Migration
Migrate from legacy DB to new schema. Must be resumable — can't redo 2M rows if it crashes at row 1.9M.

Spring Batch solves batch-specific concerns: efficient bulk I/O, transactional integrity per chunk, job restartability from the last checkpoint, skip/retry policies for bad data, and parallelism via partitioning.

Building a Job with Spring Batch 5 (Spring Boot 3+)

// Spring Boot 3+ auto-configures JobRepository. No @EnableBatchProcessing needed. @Configuration public class ImportJobConfig { @Bean public Job importCustomerJob( JobRepository jobRepo, Step validateStep, Step processStep) { return new JobBuilder("importCustomerJob", jobRepo) .start(validateStep) .next(processStep) .build(); } @Bean public Step processStep( JobRepository jobRepo, PlatformTransactionManager txMgr, ItemReader<CustomerCsvRow> reader, ItemProcessor<CustomerCsvRow, Customer> processor, ItemWriter<Customer> writer) { return new StepBuilder("processStep", jobRepo) .<CustomerCsvRow, Customer>chunk(100, txMgr) // commit-interval = 100 .reader(reader) .processor(processor) .writer(writer) .faultTolerant() .skip(MalformedEmailException.class) .skipLimit(50) // skip up to 50 bad items .retry(DeadlockLoserException.class) .retryLimit(3) // retry up to 3x on deadlock .build(); } }

4. JobParameters & JobRepository

JobParameters

Parameters uniquely identify a JobInstance. Spring Batch prevents re-running a completed job with the same parameters (idempotency). Add a timestamp or UUID to re-run the same logical job.

// Launching a job programmatically @Service public class BatchLauncher { @Autowired private JobLauncher jobLauncher; @Autowired private Job importCustomerJob; public void launch() throws Exception { JobParameters params = new JobParametersBuilder() .addString("inputFile", "customers-2024-06.csv") .addLong("runId", System.currentTimeMillis()) .toJobParameters(); JobExecution exec = jobLauncher.run(importCustomerJob, params); log.info("Status: {}", exec.getStatus()); } } // Or use @Scheduled @Scheduled(cron = "0 0 2 * * *") // 2am daily public void runNightlyBatch() { launch(); }

JobRepository Tables

Spring Batch creates 6 meta-data tables. Stores every execution for restart and audit.

BATCH_JOB_INSTANCE
One row per unique job+params combo. ID, job_name, job_key
BATCH_JOB_EXECUTION
One row per run attempt. status, start_time, end_time, exit_code
BATCH_STEP_EXECUTION
One row per step per run. read_count, write_count, skip_count, commit_count
BATCH_JOB_EXECUTION_CONTEXT
ExecutionContext serialized — survives restart, shares data between steps

JobExecution Statuses

STARTING STARTED COMPLETED FAILED STOPPED ABANDONED
FAILED jobs can be restarted from the last successful chunk. COMPLETED jobs cannot be restarted with the same parameters — use a new runId parameter.

5. ItemReader Implementations

FlatFileItemReader (CSV)

@Bean public FlatFileItemReader<CustomerCsvRow> csvReader() { return new FlatFileItemReaderBuilder<CustomerCsvRow>() .name("customerCsvReader") .resource(new ClassPathResource("customers.csv")) .delimited() .names("id", "email", "amount") .targetType(CustomerCsvRow.class) .linesToSkip(1) // skip header .build(); }

JdbcCursorItemReader

@Bean public JdbcCursorItemReader<Order> orderReader( DataSource ds) { return new JdbcCursorItemReaderBuilder<Order>() .name("orderReader") .dataSource(ds) .sql("SELECT * FROM orders WHERE status='PENDING'") .rowMapper(new BeanPropertyRowMapper<>( Order.class)) .build(); // Streams via DB cursor — memory efficient // No full result set loaded into RAM }

JpaPagingItemReader

@Bean public JpaPagingItemReader<Product> productReader( EntityManagerFactory emf) { return new JpaPagingItemReaderBuilder<Product>() .name("productReader") .entityManagerFactory(emf) .queryString("SELECT p FROM Product p WHERE p.active=true") .pageSize(100) // page size = chunk size .build(); // Pages through JPA — safe for large sets // Flush/clear EntityManager between pages }

ExecutionContext — step data sharing

// In Step 1 listener — save data for Step 2 @Component public class Step1Listener implements StepExecutionListener { @Override public ExitStatus afterStep(StepExecution stepExec) { ExecutionContext jobCtx = stepExec.getJobExecution() .getExecutionContext(); jobCtx.putInt("recordCount", stepExec.getWriteCount()); return ExitStatus.COMPLETED; } } // In Step 2 — read what Step 1 stored @BeforeStep public void beforeStep(StepExecution stepExec) { ExecutionContext jobCtx = stepExec.getJobExecution().getExecutionContext(); int count = jobCtx.getInt("recordCount"); }

6. Skip Policy, Retry & Partitioning

Skip and Retry

// On the StepBuilder: .faultTolerant() .skip(MalformedEmailException.class) .skip(DataIntegrityViolationException.class) .skipLimit(100) // fail job after 100 skips .noSkip(FatalBizException.class) // never skip .retry(DeadlockLoserDataAccessException.class) .retry(OptimisticLockingFailureException.class) .retryLimit(3) // retry up to 3 times per item // Custom skip policy class .skipPolicy(new AlwaysSkipItemSkipPolicy()) // Listeners for monitoring .listener(new ItemReadListener<>() { ... }) .listener(new SkipListener<>() { public void onSkipInWrite(T item, Throwable t) { log.warn("Skipped: {}", item); deadLetterRepo.save(item, t.getMessage()); } })

Partitioning — Parallel Processing

Split the input data into N partitions and process each in parallel. Manager step coordinates, worker steps execute.

@Bean public Step partitionedStep( JobRepository jobRepo, Step workerStep, Partitioner partitioner) { return new StepBuilder("partitionedStep", jobRepo) .partitioner("workerStep", partitioner) .step(workerStep) .gridSize(4) // 4 parallel partitions .taskExecutor(new SimpleAsyncTaskExecutor()) .build(); } // Partitioner splits input into execution contexts @Component public class RangePartitioner implements Partitioner { @Override public Map<String, ExecutionContext> partition( int gridSize) { // Divide rows 1..1000000 into gridSize ranges // Each worker gets: minId, maxId return IntStream.range(0, gridSize) .mapToObj(i -> { var ctx = new ExecutionContext(); ctx.putInt("minId", i * 250000 + 1); ctx.putInt("maxId", (i+1) * 250000); return ctx; })...; } }
