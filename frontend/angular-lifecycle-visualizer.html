Angular Component Lifecycle Hooks

Angular manages your components from creation to destruction. At each important moment in that lifecycle, it calls a method on your component — a lifecycle hook. Knowing when each hook fires, what's available in it, and what cleanup to do in the last one is essential for writing correct, leak-free Angular applications.

All hooks at a glance — call order

These hooks are called in this exact order. To use a hook, implement the corresponding interface (OnInit, OnDestroy, etc.) and define the method. You only need to implement the hooks you actually use — the others are simply not called if the method doesn't exist.

ngOnChanges — the SimpleChanges object

ngOnChanges is the only hook that receives a parameter: a SimpleChanges object. It maps each changed input property name to a SimpleChange that tells you the previous value, the current value, and whether this is the first time it changed. 

import { Component, Input, OnChanges, SimpleChanges } from '@angular/core';

@Component({ selector: 'app-user-card', standalone: true, template: `...` })
export class UserCardComponent implements OnChanges {
  @Input() userId!: number;
  @Input() role!: string;

  ngOnChanges(changes: SimpleChanges): void {
    // 'changes' is a dictionary: key = input property name
    if (changes['userId']) {
      const change = changes['userId'];
      console.log('previousValue:', change.previousValue);  // old value
      console.log('currentValue:',  change.currentValue);   // new value
      console.log('firstChange:',   change.firstChange);    // true only the first time

      // Only reload data if userId actually changed (and it's not the first undefined→value)
      if (!change.firstChange) {
        this.loadUser(change.currentValue);
      }
    }

    // You can check ALL changed inputs at once
    Object.keys(changes).forEach(key => {
      console.log(`${key} changed from ${changes[key].previousValue} to ${changes[key].currentValue}`);
    });
  }

  loadUser(id: number) { /* fetch user data */ }
}

// SimpleChange structure (for reference):
interface SimpleChange {
  previousValue: any;    // value before the change
  currentValue: any;     // value after the change
  firstChange: boolean;  // true on the very first call
  isFirstChange(): boolean;  // same as firstChange, method form
}

Important: ngOnChanges only fires when Angular detects a change via change detection — meaning the value passed from the parent must be a new reference for objects/arrays (Angular uses reference equality, not deep equality, by default). If you mutate an array and pass the same reference, ngOnChanges will NOT fire. Use immutable patterns: spread to create new arrays/objects.

ngOnInit — where initialization logic belongs

ngOnInit is the most-used hook. It fires exactly once, after Angular has set all the component's @Input() bindings for the first time. This is the right place to:

Use ngOnInit for

  • Making HTTP requests to load data
  • Subscribing to route params or query strings
  • Setting up form controls with initial values
  • Starting timers or intervals
  • Anything that depends on @Input() values being available

Do NOT use constructor for

  • HTTP calls — inputs aren't set yet
  • DOM manipulation — no template yet
  • Accessing @Input() values — they're all undefined
  • Any logic that could throw — Angular can't catch constructor errors cleanly
@Component({ selector: 'app-product-detail', standalone: true, template: `...` })
export class ProductDetailComponent implements OnInit, OnDestroy {
  private http = inject(HttpClient);
  private route = inject(ActivatedRoute);

  product: Product | null = null;

  constructor() {
    // ✅ ONLY dependency injection here. Nothing else.
    // @Inputs are NOT available yet — this.route snapshot params would be undefined
  }

  ngOnInit(): void {
    // ✅ Here, all @Inputs are set. Router params are available.
    const id = this.route.snapshot.params['id'];
    this.http.get<Product>(`/api/products/${id}`)
      .subscribe(p => this.product = p);
  }
}

ngAfterViewInit — the ViewChild timing rule

This is one of Angular's most common gotchas. @ViewChild queries are populated AFTER the view is built — meaning in ngOnInit() they are still undefined. They become available in ngAfterViewInit(). Understanding this rule prevents a whole class of "cannot read property of undefined" errors.

Wrong — accessing ViewChild in ngOnInit

export class SearchComponent {
  @ViewChild('searchInput') input!: ElementRef;

  ngOnInit() {
    // ❌ input is UNDEFINED here — view not built yet
    this.input.nativeElement.focus();
    // TypeError: Cannot read properties of undefined
  }
}

Correct — accessing ViewChild in ngAfterViewInit

export class SearchComponent {
  @ViewChild('searchInput') input!: ElementRef;

  ngAfterViewInit() {
    // ✅ View is built — input is now populated
    this.input.nativeElement.focus();
  }
}

// Template:
<input #searchInput type="text" />

The one exception: @ViewChild('ref', { static: true }) is populated before ngOnInit. Use static: true only when the element is always in the template (not wrapped in *ngIf or *ngFor). For anything dynamic, stick with the default static: false and use it in ngAfterViewInit.

ngOnDestroy — cleanup checklist

Memory leaks in Angular almost always stem from forgetting to clean up in ngOnDestroy. When a component is destroyed (navigated away from, removed from the DOM, *ngIf set to false), Angular calls this hook. If you subscribed to an Observable, started a timer, or attached an event listener, you must clean it up here.

The memory leak — no cleanup

export class DashboardComponent {
  private refresh = inject(RefreshService);
  counts: number[] = [];

  ngOnInit() {
    // 🔴 LEAK: subscription is never cancelled.
    // Even after this component is destroyed,
    // the Observable keeps pushing values and
    // this callback keeps running on a dead object.
    this.refresh.tick$.subscribe(n => {
      this.counts.push(n);
    });
  }
  // No ngOnDestroy — subscription lives forever.
}

Fixed — unsubscribe in ngOnDestroy

export class DashboardComponent implements OnDestroy {
  private refresh = inject(RefreshService);
  private sub!: Subscription;
  counts: number[] = [];

  ngOnInit() {
    this.sub = this.refresh.tick$.subscribe(n => {
      this.counts.push(n);
    });
  }

  ngOnDestroy() {
    this.sub.unsubscribe();  // ✅ Clean exit
  }
}
// Complete cleanup checklist for ngOnDestroy
ngOnDestroy(): void {
  // 1. Unsubscribe from Observables
  this.subscription.unsubscribe();

  // 2. Cancel setInterval / setTimeout
  clearInterval(this.intervalId);
  clearTimeout(this.timeoutId);

  // 3. Remove native DOM event listeners
  document.removeEventListener('keydown', this.keyHandler);

  // 4. Complete Subject streams
  this.destroy$.next();
  this.destroy$.complete();

  // 5. Disconnect observers
  this.resizeObserver.disconnect();
  this.intersectionObs.disconnect();
}

export class NotificationComponent implements OnInit {
  private ws = inject(WebSocketService);
  notifications: string[] = [];

  ngOnInit() {
    // 🔴 When this component is destroyed (e.g. user navigates away),
    // this subscription remains active. The WebSocket keeps pushing,
    // the array keeps growing, and the GC cannot collect this component.
    this.ws.messages$.subscribe(msg => {
      this.notifications.push(msg);
    });
  }
  // No ngOnDestroy — the subscription is an orphan forever.
}
export class NotificationComponent implements OnInit, OnDestroy {
  private ws = inject(WebSocketService);
  private destroy$ = new Subject<void>();
  notifications: string[] = [];

  ngOnInit() {
    this.ws.messages$
      .pipe(takeUntil(this.destroy$))   // ✅ unsubscribe when destroy$ emits
      .subscribe(msg => {
        this.notifications.push(msg);
      });
  }

  ngOnDestroy() {
    this.destroy$.next();     // triggers takeUntil to complete
    this.destroy$.complete();
  }
}
// Works but requires boilerplate: the destroy$ Subject + the ngOnDestroy method.
import { takeUntilDestroyed } from '@angular/core/rxjs-interop';  // Angular 16+

export class NotificationComponent implements OnInit {
  private ws = inject(WebSocketService);
  // If called outside a constructor/field, you must pass destroyRef manually.
  // In a field initializer or constructor, Angular injects it automatically.
  notifications: string[] = [];

  ngOnInit() {
    this.ws.messages$
      .pipe(takeUntilDestroyed(inject(DestroyRef)))  // Angular 16+ shorthand
      .subscribe(msg => {
        this.notifications.push(msg);
      });
  }
  // No ngOnDestroy needed. takeUntilDestroyed handles it automatically.
}

// Even cleaner — set up the subscription in a field initializer:
export class NotificationComponent {
  private ws = inject(WebSocketService);
  notifications: string[] = [];

  // takeUntilDestroyed() with no args works here because we're in the injection context
  _ = this.ws.messages$
    .pipe(takeUntilDestroyed())
    .subscribe(msg => this.notifications.push(msg));
}
import { DestroyRef } from '@angular/core';  // Angular 16+

export class NotificationComponent {
  private ws = inject(WebSocketService);
  private destroyRef = inject(DestroyRef);

  constructor() {
    // Run any cleanup function when the component is destroyed
    this.destroyRef.onDestroy(() => {
      clearInterval(this.timerHandle);
      document.removeEventListener('keydown', this.handler);
    });
  }
  // This is the escape hatch for non-Observable cleanup. For Observables, prefer
  // takeUntilDestroyed(). For native timers and event listeners, DestroyRef.onDestroy()
  // keeps the cleanup co-located with the setup code instead of in a separate method.
}

Parent vs child hook order — the full sequence

Angular processes the component tree depth-first during initialization, but completes each level's view hooks in a bottom-up pass. This means the child's view is fully initialized before the parent's view init hook fires. 

// Full hook order for <app-parent> containing <app-child>:

// --- INIT PHASE ---
Parent: constructor()
Parent: ngOnChanges()         // parent's own @Inputs set
Parent: ngOnInit()
Parent: ngDoCheck()
Parent: ngAfterContentInit()
Parent: ngAfterContentChecked()

  Child: constructor()
  Child: ngOnChanges()          // child's @Inputs set (passed from parent)
  Child: ngOnInit()
  Child: ngDoCheck()
  Child: ngAfterContentInit()
  Child: ngAfterContentChecked()
  Child: ngAfterViewInit()       // child's view is complete
  Child: ngAfterViewChecked()

Parent: ngAfterViewInit()       // NOW parent's view is complete (child is part of it)
Parent: ngAfterViewChecked()

// --- DESTROY PHASE (when component is removed) ---
Child: ngOnDestroy()             // child destroyed first
Parent: ngOnDestroy()            // parent destroyed after all children

Signal-based lifecycle (Angular 17+)

Angular 17 introduced two new lifecycle functions that work outside of class-based components and are signal-aware. They replace some common ngAfterViewInit patterns, particularly for SSR-safe DOM access.

afterNextRender() — run once, next render

import { afterNextRender } from '@angular/core';

export class ChartComponent {
  private el = inject(ElementRef);

  constructor() {
    afterNextRender(() => {
      // ✅ Runs after the FIRST time the view is rendered in the browser.
      // Safe for SSR — it never runs on the server.
      // Perfect for third-party DOM libraries (Chart.js, D3, etc.)
      initChartLibrary(this.el.nativeElement);
    });
  }
}

afterRender() — run after every render

import { afterRender } from '@angular/core';

export class AutoScrollComponent {
  private el = inject(ElementRef);

  constructor() {
    afterRender(() => {
      // Runs after every render cycle — use sparingly.
      // Good for measuring DOM and reacting to size changes
      // without a ResizeObserver. Angular will call this
      // after every change detection pass that causes re-render.
      const height = this.el.nativeElement.scrollHeight;
      this.el.nativeElement.scrollTop = height;
    });
  }
}

ExpressionChangedAfterItHasBeenCheckedError

This is Angular's most infamous error. It happens when you change a value that the template has already rendered during the same change detection cycle. Angular in dev mode does a second pass to verify nothing changed — if something did change, it throws this error to warn you.

Causes the error

export class NavComponent {
  title = 'Home';

  ngAfterViewInit() {
    // ❌ Changes the title AFTER Angular rendered it.
    // Dev mode's second pass sees the value changed
    // → ExpressionChangedAfterItHasBeenCheckedError
    this.title = 'Dashboard';
  }
}

Fix: defer to next tick

export class NavComponent {
  private cdr = inject(ChangeDetectorRef);
  title = 'Home';

  ngAfterViewInit() {
    setTimeout(() => {
      // ✅ Deferred — runs after current CD cycle
      this.title = 'Dashboard';
    });

    // OR manually trigger another CD pass:
    this.cdr.detectChanges();
  }
}

The real fix is usually to rethink the design: if you're modifying state in ngAfterViewInit, you probably have a circular data dependency. Try moving the state mutation to ngOnInit (if the data doesn't depend on the view), or use a signal (which defers updates automatically).

ngDoCheck — custom change detection

ngDoCheck runs on every change detection cycle — even when nothing in this component changed. Because Angular's default change detection can't detect mutations inside objects or arrays (only reference changes), ngDoCheck lets you write your own logic to check for deeper changes. Use it very sparingly — it fires constantly. 

export class DeepListComponent implements DoCheck {
  @Input() items: Item[] = [];  // passed by reference — ngOnChanges won't fire on mutations
  private prevLength = 0;
  private differ = inject(IterableDiffers).find([]).create();

  ngDoCheck(): void {
    // Angular provides IterableDiffers and KeyValueDiffers for this purpose.
    // They track changes efficiently inside arrays/objects.
    const changes = this.differ.diff(this.items);
    if (changes) {
      changes.forEachAddedItem(r => console.log('Added:', r.item));
      changes.forEachRemovedItem(r => console.log('Removed:', r.item));
    }

    // ⚠ ngDoCheck fires very frequently. Avoid heavy computation here.
    // The Angular team added this for special cases (like the NgFor directive itself).
    // For most use cases, prefer immutable patterns + ngOnChanges.
  }
}
