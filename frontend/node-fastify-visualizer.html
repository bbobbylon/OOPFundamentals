Fastify — Schemas, Hooks & Plugins

Express, but faster and schema-first. You declare a JSON Schema per route; Fastify uses it to validate the input and compile a blazing-fast serializer for the output. Lifecycle hooks and an encapsulated plugin system round it out.

⚡ What is Fastify — and how does a schema make it fast and safe?

Fastify is a modern Node web framework focused on low overhead and developer experience. Its headline idea is schema-based everything: each route can declare a JSON Schema for its params, query, body, headers, and response. Fastify uses that schema two ways — it validates incoming data (rejecting bad requests with a 400 before your handler runs) and it compiles a specialized serializer (via fast-json-stringify) that turns your response object into JSON far faster than generic JSON.stringify, because the shape is known ahead of time. Requests flow through an explicit lifecycle of hooks (onRequest → preValidation → preHandler → handler → preSerialization → onSend → onResponse), each a place to plug in auth, logging, or transforms. Code is organized as plugins — encapsulated, composable units registered with fastify.register(), each with its own scope. It is the framework you pick when Express feels too unstructured and too slow.

  • Schema-first — one JSON Schema validates input and compiles the output serializer.
  • Lifecycle hooks — named extension points around every request.
  • Plugins + encapsulation — register() scopes decorators/hooks to a subtree.
  • Fast by design — schema-compiled serialization, low per-request overhead.

A schema-validated route

fastify.post("/users", { schema: { body: { type: "object", required: ["email"], properties: { email: { type: "string", format: "email" }, age: { type: "integer", minimum: 0 }, }, }, response: { 201: { type: "object", properties: { id: { type: "integer" } } } }, }, }, async (req, reply) => { const id = await createUser(req.body); // body is valid reply.code(201).send({ id }); });

Hooks & a plugin

// a hook: runs for every request in this scope fastify.addHook("onRequest", async (req, reply) => { req.startTime = process.hrtime.bigint(); }); // a plugin: an encapsulated, composable unit async function authPlugin(fastify, opts) { fastify.decorateRequest("user", null); fastify.addHook("preHandler", verifyJwt); } fastify.register(authPlugin); // scoped to its subtree

Spring Boot comparison

Fastify's per-route schema ≈ a Spring DTO + @Valid Bean Validation, but it also covers the response shape (like declaring your serialization view). Its hooks ≈ Servlet filters / HandlerInterceptor at named points. Plugins + encapsulation ≈ Spring's modular configuration and bean scoping — a registered plugin's decorators/hooks are visible only to that subtree, like a child ApplicationContext. reply.code(201).send(obj) ≈ ResponseEntity.status(201).body(obj). The schema-compiled serializer has no Spring analogue — it is a Fastify performance trick that trades a little startup compilation for much faster JSON output.

CIAM Fastify gateway: Fastify's speed suits a high-throughput token-validating gateway. An authPlugin decorates the request with a user property and adds a preHandler hook that verifies the Ping/Entra RS256 JWT (via @fastify/jwt + a JWKS fetcher) — encapsulation means only the routes under that plugin require auth. Per-route response schemas guarantee the gateway never accidentally leaks an internal field, because the compiled serializer only emits the properties the schema declares. That schema-as-allowlist behavior is a genuine security win over hand-rolled res.json().

The problem

Bring your Express habits to Fastify and almost all of them just work. This one fails without a sound.

The not-found branch that ships a 200 anyway

You port a lookup-by-id handler from Express to Fastify. The natural not-found guard goes in first: if (!user) { reply.code(404).send({ error: 'user not found' }); }, then the happy path: return { ok: true, user };. It looks complete — the 404 case is handled, the success case returns a value the way every Fastify example tells you to. Then a teammate notices the log filling up with "Reply was already sent" warnings, one per missing user, and nobody can explain where a second .send() call is hiding. There isn't one. There's a return statement.

reply.code(404).send(...) really does run ✓ the client really was told "not found", once ✓ no return inside the if block ⚠ the function's last line runs anyway, every time ⚠

In Express, this exact missing-return mistake crashes immediately and loudly (a second res.json() throws). In Fastify it doesn't crash at all — which is worse, because nothing tells you it happened.

Treat every manual reply.send() as an early exit
reply.code(404).send(...) inside the if block, nothing after it ↓ the async function still runs to its last line and returns a value Fastify will try to use as a payload return reply.code(404).send(...); — one statement, sends AND exits ↓ send() itself returns the reply object, so returning its result both stops the function here and satisfies "return something" Exactly one payload ever reaches Fastify's send logic, no matter which branch ran
return and reply.send() are the same action, not two different ones. An async Fastify handler's return value exists for exactly one reason: to become the argument to an implicit reply.send() call Fastify makes on your behalf once your function resolves. Call reply.send() yourself and then also return a value, and you haven't sent two responses — you've supplied one argument to send() twice, and the second supply is discarded. The CodeWalk above already shows the safe shape: reply.code(201).send({ id }) as the handler's very last line, with nothing after it to compete.
Think of reply as a letter you're allowed to seal and hand to the mail carrier exactly once. reply.send(x) is sealing envelope X and handing it over. return y from an async handler is Fastify sealing envelope Y and handing it to the carrier on your behalf, right after your function finishes — but the carrier already left with X. Y doesn't get glued to the back of X, and it doesn't knock X out of the truck. Y just never leaves the building. Where the analogy stops: the mail carrier wouldn't say anything. Fastify does — a log line naming the exact route — which is the only reason you'd ever notice this happened.

The mechanism

Six words explain the entire bug: the function keeps running after send().

  1. Fastify calls your async (req, reply) => {...} handler and awaits whatever it returns, no matter what happens inside italways awaited, no exceptions
  2. db.findUser(id) resolves to null — the user genuinely doesn't exista completely normal, expected outcome
  3. if (!user) { reply.code(404).send({error:'user not found'}); } runs — a real HTTP response is written to the socket, right nowthis part works exactly as intended
  4. There's no return inside that if block, so control falls through to the next line anywaythe missing word
  5. return { ok: true, user }; executes — the async function resolves with a defined, non-empty valuea second candidate payload now exists
  6. Fastify checks reply.sent before using a handler's return value as a payload — it's already true, so the returned value is discarded and a warning is logged instead of a second responsediscarded, not queued, not appended

Step 4 is the entire lesson — and it is the exact same missing word that causes the classic Express bug (a second res.json() call throwing ERR_HTTP_HEADERS_SENT). Fastify's implicit "return becomes send()" convenience is what changes the FAILURE MODE, not the root cause: the second attempt at a payload is now a quiet return statement instead of a loud second function call, so the identical mistake stops crashing and starts hiding.

this request's replycan be sent exactly once
↓ whichever reaches it first wins ↓
reply.code(404).send(...) — fires synchronously, inside the if block return { ok: true, user } — arrives after, discarded with a warning

Both of these are genuine attempts to supply a payload — Fastify doesn't know which one the developer "meant." It just enforces the only rule that makes sense for an HTTP response: first one to actually call send() (directly, or via a return Fastify sends for you) wins, and nothing else about that reply can be changed afterward.

A request arrives for a user id that doesn't exist, so db.findUser resolves to null. reply.code(404).send({ error: 'user not found' }) runs inside the if (!user) block — with no return after it — so control falls through to the handler's last line, return { ok: true, user };. What does the client actually receive?

Right. reply.code(404).send(...) already wrote a real response to the socket, synchronously, before the function's last line ever runs. By the time return { ok: true, user } resolves the handler's promise, reply.sent is already true — Fastify sees a return value with nowhere to go, discards it, and logs the mismatch instead of attempting a second write.

A reasonable guess if you think of return as always having the final word, like a function's normal output. But in a Fastify handler, return is only ever a REQUEST to send a payload — and requests made after the reply is already sent don't get honored. The 404 fired first and the response can't be reopened to add a different body afterward.

Tempting if you're thinking of this like writing to an already-closed stream, which does throw. But nothing here attempts a genuine second write to the socket — Fastify checks reply.sent BEFORE trying to use the returned value, so it never reaches code that would throw. The mismatch is caught and neutralized, not crashed on.

Where you've seen this before

Three different platforms, the same rule: a response can be supplied once, and the runtime enforces it differently every time.

Spring: writing after the response is committed

A Spring @RestController method that returns a ResponseEntity<T> is making the exact same kind of promise a Fastify return makes — "here is the body, send it for me." If that method ALSO manually writes to the raw HttpServletResponse before returning, the response becomes committed, and the servlet container throws IllegalStateException the moment anything tries to touch its status or headers again. Same root rule as this page — respond once — enforced with a hard exception instead of Fastify's soft warning.

committed response + a second write = IllegalStateException

A native Promise ignores this problem entirely

Every JavaScript Promise already has a rule for this, one you've used without thinking about it: once a Promise executor calls resolve() or reject(), every later call to either one is a guaranteed, silent no-op per the language spec — no warning, no error, nothing. Fastify's reply is stricter than a raw Promise (it at least logs the conflict); the underlying shape — first settlement wins, the rest are discarded — is identical.

settle a Promise twice and the second call just vanishes

Raw Node http: the crash Fastify is deliberately avoiding

Underneath both Express and Fastify sits the same http.ServerResponse, and calling res.end() (or setting a header) after a response is already sent throws ERR_HTTP_HEADERS_SENT — loudly, immediately. Fastify's reply.sent check exists specifically to intercept a return-value conflict BEFORE it reaches that raw, crashing code path — which is exactly why this bug produces a log warning in Fastify instead of taking the process down.

same underlying rule; Fastify catches it one layer higher, on purpose
Questions from the back row

If I never call reply.send() myself and always just return a value, am I completely safe from this?

Yes. If a handler purely computes a value and returns it — no manual .send() call anywhere in its body — there is only ever one candidate payload, so there's nothing for it to conflict with. The risk is specific to handlers that need to call reply.send() manually inside a branch (almost always an early-exit guard clause, like this page's 404 check) and then keep executing code after that branch.

What's the actual difference between return reply; and just calling reply.send() with nothing after it?

Functionally, very little — both tell Fastify "don't touch this again." A bare return; at the end of the branch resolves the function with undefined, which Fastify has nothing to do with once a reply is already sent. return reply; (or the equivalent one-liner, return reply.code(404).send(...), since send() itself returns reply) is the form Fastify's own docs show, mostly because it reads as an explicit "I handled this" rather than relying on a reader noticing an empty return a few lines below a .send() call.

Would a test catch this before it shipped?

Only if the test asserts on the response BODY, not just the status code. In this exact bug, reply.code(404) ran before .send(), so the status code is still correctly 404 — a test that only checks res.statusCode === 404 passes cleanly with this bug sitting right there in the code. It takes a body assertion, or someone actually reading the "Reply was already sent" log line, to surface it.

1. The request lifecycle (hook order)

onRequest // earliest — auth/rate-limit before parsing
preParsing
preValidation // before schema validation
[ schema validation runs here ]
preHandler // last gate before your handler
[ your handler runs ]
preSerialization // transform the payload before JSON
onSend // final tweak of the outgoing response
onResponse // after sent — logging/metrics
Hooks are the extension points. Put authentication in onRequest (cheapest, before body parsing); put authorization in preHandler (after validation, when you know the request shape is good); put metrics in onResponse. Each maps to a precise moment in the pipeline.

2. Encapsulation: the plugin tree

// decorators & hooks are scoped to where they're registered
fastify.register(async (api) => {
  api.addHook("preHandler", verifyJwt); // only inside this scope
  api.get("/me", meHandler); // protected
}, { prefix: "/api" });

fastify.get("/health", healthHandler); // NOT protected (outside scope)

A plugin gets its own encapsulated context — hooks and decorate() additions are visible only to it and its children, not siblings. Use fastify-plugin to deliberately break encapsulation and share globally.

3. Why the response schema matters

// Without a response schema: generic JSON.stringify, leaks everything
reply.send(user); // { id, email, passwordHash, internalFlags } 😱

// With a response schema: compiled serializer emits ONLY declared props
schema: { response: { 200: { type: "object",
  properties: { id: { type: "integer" }, email: { type: "string" } } } }
reply.send(user); // → { id, email } — passwordHash never serialized
