App Registration

App Registration is how you tell Entra ID your application exists. Every app that uses Entra ID for auth must be registered. Learn what each setting means.

📋 What is Entra App Registration — and why does every setting shape what Angular can request and Spring can accept?

An App Registration tells Entra an app exists and how it may authenticate — without one, no app can get tokens. The full-stack pattern needs two: one for the Angular SPA (the client) and one for the Spring API (the resource). Each has a Client ID (GUID) and exact-match Redirect URIs (no wildcards — blocks redirect-to-attacker attacks); SPAs use PKCE instead of a secret, servers use a client secret or (better) a certificate. The key distinction is delegated permissions (the app acts on behalf of a signed-in user) vs application permissions (the app acts as itself, admin-consent required). And the API registration exposes scopes (read:users) the Angular app requests — the chain that ends in Spring verifying the scope.

  • Two registrations — Angular (client) + Spring API (resource).
  • Client ID + exact Redirect URIs — no wildcards; SPAs use PKCE, not a secret.
  • Delegated vs application perms — on behalf of a user vs as the app (admin consent).
  • API exposes scopes Angular requests → Spring verifies the scope.

Two registrations required

// Registration 1: Angular SPA (the CLIENT) Name: "CIAM Angular App" Platform: Single-page application (SPA) Redirect URIs: https://app.example.com/callback ← production http://localhost:4200/callback ← development Application ID: aaaa-bbbb-cccc-dddd ← this is your client_id Client Secret: NONE (SPA = public client, uses PKCE) Delegated Permissions: Microsoft Graph: openid, profile, email (for OIDC) api://spring-api/read:users ← your API's scope // Registration 2: Spring Boot API (the RESOURCE) Name: "CIAM Spring Boot API" Platform: Web (not SPA — this is a server app) Application ID URI: api://eeee-ffff-gggg-hhhh Exposed Scopes: api://eeee-ffff-gggg-hhhh/read:users ← Angular requests this api://eeee-ffff-gggg-hhhh/write:users App Roles: CIAM.Admin, Reader // Spring Boot application.yml: spring.security.oauth2.resourceserver.jwt: issuer-uri: https://login.microsoftonline.com/<tenantId>/v2.0

Delegated vs Application perms

// DELEGATED: acts on behalf of a user // • User must be signed in // • Token sub = the user (not the app) // • Permission = intersection of app + user rights // • Requires user consent (or admin pre-consent) // // Examples: // User.Read → read your own profile // User.ReadBasic.All → read other users' basic profiles // api://api-id/read:users → your custom delegated scope // REQUEST DELEGATED: scope in /authorize request // scope=openid profile api://api-id/read:users // APPLICATION: acts as the app itself (no user) // • No user involved — background daemon/service // • Token sub = the application (service principal) // • Requires ADMIN CONSENT (powerful — bypasses user) // // Examples: // User.Read.All → read ALL users in tenant // Directory.Read.All → read entire directory // REQUEST APPLICATION: client credentials flow // scope=api://api-id/.default (no user delegation) // Use admin consent screen or: // az ad app permission admin-consent --id <clientId>

Certificate vs secret + App Roles

// Authentication method for the API registration: // CLIENT SECRET (avoid in production): // - Generated in Azure Portal (or via CLI) // - String like "abc~defGHIJK123..." // - Expires in 6 months, 1 year, or 2 years // - Risk: stored in config files, may appear in logs // - Use only for development // CLIENT CERTIFICATE (production standard): // - Upload public key cert to app registration // - Keep private key in Azure Key Vault // - Stronger: even if cert is seen, can't authenticate without private key // - MSAL: .withCertificate(cert, privateKey) // MANAGED IDENTITY (best for Azure-hosted apps): // - Azure handles identity — no credentials at all // - Works for: Azure VMs, Container Apps, AKS pods // - Use DefaultAzureCredential() in SDK → auto uses Managed Identity // APP ROLES (for RBAC in your Spring Boot API): // Define in app registration → Manifest tab: // { "appRoles": [{"value":"CIAM.Admin","displayName":"Admin"}] } // Assign roles to users in Enterprise Applications tab // → role appears in JWT's "roles" array claim

In CIAM / Your Job: App Registration is where CIAM integration most often breaks. Common mistakes: (1) wrong platform type — registering Angular as "Web" not "SPA" makes Entra demand a client_secret SPAs can't store; (2) a missing redirect URI (localhost:4200/callback) fails every local token; (3) wrong scope format — request api://spring-clientid/read:users, not bare read:users; (4) no admin consent for application permissions → your daemon gets a 403 on User.Read.All. Check Enterprise Applications → Permissions to see what's actually consented.

1 — What an App Registration Is

An App Registration is an identity configuration stored in Entra ID. It defines:

  • Who the app is — Client ID, Tenant ID
  • How it authenticates — client secret or certificate
  • What it exposes — scopes/permissions
  • Where users return after login — redirect URIs
  • What it can access — API permissions
Two types of apps:
Single-Tenant
Only users in your organization can sign in. Use for internal tools.
Multi-Tenant
Any Microsoft Entra user can sign in. Use for SaaS apps or products you sell to other companies.

Expose an API — Scopes

Define what permissions other apps can request to call YOUR API. Your Angular frontend will request these scopes.

Application ID URI: api://c7a8e2f1-3b40-4d91-a821-9f1234567890
api://c7a8e...9890/Users.Read
Admin and user consent: Read user data from the API. State: Enabled.
api://c7a8e...9890/Users.Write
Admin consent only: Write user data via the API. State: Enabled.

API Permissions — What this app can access

These are the permissions YOUR app requests from other APIs (Microsoft Graph, your own APIs, third-party APIs).

API / PermissionTypeStatus
Microsoft Graph / User.ReadDelegatedGranted
Microsoft Graph / openidDelegatedGranted
Microsoft Graph / profileDelegatedGranted
My API / Users.ReadDelegatedGranted

Delegated = acts on behalf of the signed-in user. Application = acts as the app itself (no user). Admin grant = admin pre-approved for all users in tenant.

App Roles — Custom Authorization Roles

Define roles that users or groups can be assigned to. These appear as claims in the JWT token your Spring Boot API validates.

Admin
Full access. Value: Admin. Allowed member types: Users/Groups.
ReadOnly
Read-only access. Value: ReadOnly. Allowed member types: Users/Groups.

In Spring Boot: @PreAuthorize("hasAuthority('APPROLE_Admin')") — Entra app roles appear prefixed with APPROLE_.

3 — Wiring It Into Spring Boot

After registering your API app in Entra, add these settings to application.yml:

# application.yml — Spring Boot API (Resource Server) spring: security: oauth2: resourceserver: jwt: # Entra ID JWKS endpoint — Spring validates incoming JWTs here jwk-set-uri: https://login.microsoftonline.com/{tenant-id}/discovery/v2.0/keys # Optional: validate the aud (audience) claim matches YOUR app audiences: api://c7a8e2f1-3b40-4d91-a821-9f1234567890 # If using spring-security-oauth2 autoconfiguration instead: spring: security: oauth2: resourceserver: jwt: issuer-uri: https://login.microsoftonline.com/{tenant-id}/v2.0

4 — Wiring It Into Angular (MSAL)

// environment.ts — Angular SPA export const environment = { production: false, apiUrl: 'http://localhost:8080', msalConfig: { auth: { clientId: 'c7a8e2f1-3b40-4d91-a821-9f1234567890', // from App Registration Overview authority: 'https://login.microsoftonline.com/a1b2c3d4-e5f6-7890-abcd-ef1234567890', redirectUri: 'http://localhost:4200' // must match Authentication blade } }, apiScopes: ['api://c7a8e2f1-3b40-4d91-a821-9f1234567890/Users.Read'] };
