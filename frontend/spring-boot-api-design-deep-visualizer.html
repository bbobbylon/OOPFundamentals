REST API Design & ProblemDetail

A REST API is a contract made of nouns (resources), verbs (HTTP methods), and status codes. Get those three right and the API is predictable — a client can guess the next endpoint. This page is the canonical cheat-sheet: which method, which path, which status, which body — and how Spring's built-in ProblemDetail standardizes your errors.

1. Resources are nouns. The action is the HTTP verb.

❌ Verbs in the path (RPC-style)

POST /createUser
POST /getUserById
POST /updateUserEmail
POST /deleteUser?id=42
POST /listActiveUsers

Every call is a verb glued onto a path, usually all POST. The HTTP method carries no meaning; you can't cache, can't guess, can't reason about safety/idempotency.

✅ Nouns + the right verb

POST   /api/v1/users
GET    /api/v1/users/42
PATCH  /api/v1/users/42
DELETE /api/v1/users/42
GET    /api/v1/users?status=active

One resource (/users), the method says what to do. Plural nouns, hierarchy for relations (/users/42/orders), filters as query params — never verbs in the path.

200 vs 201 vs 204: 201 means "I created a thing, here's where it lives" (Location). 204 means "done, nothing to send back" (deletes, some updates). 400 vs 422: 400 = malformed/unparseable; 422 = well-formed JSON that fails business validation (both are common — pick one and be consistent).

4. Lists: pagination, sorting, filtering

The request — params, not paths

GET /api/v1/users
      ?page=0      # zero-based page index
      &size=20     # items per page
      &sort=username,asc
      &status=active  # a filter
@GetMapping("/api/v1/users")
Page<UserSummary> list(
   @RequestParam(required=false) String status,
   Pageable pageable) {            // Spring binds page/size/sort
  return service.search(status, pageable);
}

The response — a Page<T> envelope

{
  "content": [ { "id":42, "username":"bjorn" }, … ],
  "page": {
    "size": 20,
    "number": 0,
    "totalElements": 137,
    "totalPages": 7
  }
}

The client gets the slice plus the metadata it needs to render "page 1 of 7". Never return an unbounded list — pagination is a correctness and safety concern, not a nicety. (Boot 3.3+ uses this stable page-nested shape.)

5. RFC 7807 ProblemDetail — one error shape for the whole API

Don't invent a custom error JSON. Spring Boot 3+/4 ships ProblemDetail (RFC 7807 / 9457): a standard body with type, title, status, detail, instance — plus any custom properties you add. Return it from a central @ControllerAdvice and every error in your API looks the same.

@RestControllerAdvice
class ApiExceptionHandler {

  @ExceptionHandler(UserNotFoundException.class)
  ProblemDetail notFound(UserNotFoundException ex) {
    ProblemDetail pd = ProblemDetail
        .forStatusAndDetail(HttpStatus.NOT_FOUND, ex.getMessage());
    pd.setType(URI.create("https://api.example.com/problems/user-not-found"));
    pd.setProperty("userId", ex.getId());   // extra fields are allowed
    return pd;
  }
}
// Content-Type: application/problem+json
{
  "type": "https://api.example.com/problems/user-not-found",
  "title": "Not Found",
  "status": 404,
  "detail": "User 999 was not found",
  "instance": "/api/v1/users/999",
  "userId": 999
}

Bonus: validation failures and Spring's own MVC errors already become ProblemDetail when you extend ResponseEntityExceptionHandler (and set spring.mvc.problemdetails.enabled=true for the built-ins).

6. Safety & idempotency — what a method promises

MethodSafe?
(no state change)		Idempotent?
(N calls = 1 call)		Why it matters
GET✓ yes✓ yescacheable; a client may retry/prefetch freely
POST✗ no✗ noretry after a timeout may create a duplicate — use an idempotency key if that's a risk
PUT✗ no✓ yesfull replace — sending it twice lands the same final state
PATCH✗ nodependsidempotent if the patch is absolute values; not if it's "increment by 1"
DELETE✗ no✓ yesdeleting an already-gone resource is still "gone" (often 204/404)

This is why POST creates and PUT replaces: a network retry of a PUT is harmless, a retry of a POST might double-charge a customer.

7. Versioning — plan for v2 from day one

URI versioning most common

GET /api/v1/users/42
GET /api/v2/users/42   # new shape

Obvious, easy to route and cache, trivial to test in a browser. The version is right there in the URL. Downside: it's technically a "different resource" per purist REST — in practice, nobody cares.

Header / media-type versioning

GET /api/users/42
Accept: application/vnd.acme.user.v2+json

Keeps URLs clean and "pure", but it's invisible, harder to test by hand, and easy for clients to forget. Use it when you need fine-grained content negotiation; otherwise URI versioning wins on simplicity.

Whichever you pick: never break v1 in place. Additive changes (new optional fields) don't need a version; removing/renaming fields or changing types does. DTOs (previous page) are what make this possible — a v2 DTO maps from the same entity.

8. One-sentence recap

🧭 Model resources as plural nouns and let the HTTP method be the verb; return the canonical status (201+Location on create, 204 on delete, 200 on read), page large lists into a Page<T>, standardize every error as an RFC 7807 ProblemDetail from a central @RestControllerAdvice, respect idempotency (PUT replaces, POST creates), and version the API (/v1) so you can evolve it without breaking clients.
