Spring Boot + Docker

Production-ready Dockerfiles for Spring Boot applications — multi-stage builds, layer optimization, and Docker Compose for local development.

1 — Production Dockerfile — Click Each Stage

# =================================================== # STAGE 1: Build stage (Maven + JDK — large, temp) # =================================================== FROM eclipse-temurin:21-jdk-alpine AS build
Multi-stage build stage 1 — uses the full JDK (includes compiler, javac). This stage does the heavy lifting: compiles and packages the app.

eclipse-temurin is the community OpenJDK image (successor to AdoptOpenJDK). alpine variant is smaller. AS build names this stage so stage 2 can reference it.
WORKDIR /workspace
Sets the working directory for all subsequent instructions. Created if it doesn't exist. Avoids long absolute paths in later commands.
# Copy pom.xml BEFORE source — layer cache trick COPY pom.xml . RUN mvn dependency:resolve -B # download deps (cached layer)
Layer caching optimization — copy pom.xml first and download dependencies in a separate layer. Maven dependencies rarely change, so this layer is cached on most builds.

If you copied all source code first, any code change would invalidate the deps layer and re-download everything. This order means only source changes trigger the build layer — deps layer stays cached.
COPY src ./src RUN mvn package -DskipTests # build the fat JAR
Now copy the source and build. Tests are skipped here because integration tests need a running DB — run them separately in CI before this Docker build step.

Output: /workspace/target/app.jar — the Spring Boot fat JAR.
# =================================================== # STAGE 2: Runtime stage (JRE only — small) # =================================================== FROM eclipse-temurin:21-jre-alpine
Multi-stage build stage 2 — fresh, minimal image. Only the JRE (Java Runtime Environment) — no compiler, no Maven, no source code.

Final image is typically 150–250 MB vs 500+ MB for a JDK image. Multi-stage is the standard production pattern — stage 1's contents are discarded.
# Security: run as non-root user RUN addgroup -S spring && adduser -S spring -G spring USER spring:spring
Security best practice — never run the JVM as root inside a container. If an attacker exploits a vulnerability and escapes the container, root in the container becomes root on the host.

Create a system user with no home directory and no password, then switch to it. Spring Boot runs fine as a non-root user.
COPY --from=build /workspace/target/*.jar app.jar
--from=build copies the JAR from the build stage into this runtime stage. The build tools, Maven cache, and source code stay in stage 1 and never enter the final image.
EXPOSE 8080 8081
Documents that the container listens on 8080 (app) and 8081 (Spring Boot Actuator). Does NOT publish to the host — that requires -p 8080:8080 at runtime. It's documentation + a hint to Docker tools.
ENTRYPOINT ["java", "-jar", "/app.jar"]
The command that runs when the container starts. Using exec form (JSON array) is required for proper signal handling — Docker can send SIGTERM directly to the Java process, allowing graceful shutdown.

Shell form ENTRYPOINT java -jar /app.jar wraps in /bin/sh, which intercepts signals — Spring Boot won't get SIGTERM and can't shut down gracefully.

3 — JVM Flags for Containers

❌ JVM without container awareness

# Container has 512MB memory limit # JVM sees HOST memory (e.g. 16GB) # Default heap = 25% of host = 4GB! # Container OOMKilled immediately. docker run -m 512m myapp:latest

✓ Container-aware JVM (Java 8u191+, Java 11+)

# UseContainerSupport is default in Java 11+ # JVM reads cgroup memory limits # Heap = 25% of container memory = 128MB docker run -m 512m \ -e JAVA_TOOL_OPTIONS="-XX:MaxRAMPercentage=75" \ myapp:latest # 75% of 512MB = 384MB heap # Works reliably in Docker/ECS/Kubernetes
JVM FlagPurpose
-XX:+UseContainerSupportDefault ON in Java 11+. Read cgroup CPU/memory limits instead of host values.
-XX:MaxRAMPercentage=75Heap = 75% of container memory limit. Use instead of -Xmx in containers.
-XX:+UseG1GCG1 garbage collector — good default for most Spring Boot apps.
-Dspring.profiles.active=prodActivate a Spring profile from the JVM without env var.
-Dfile.encoding=UTF-8Prevent character encoding surprises in containers with minimal locales.

4 — Alternative: Spring Boot Buildpacks (No Dockerfile)

Spring Boot 2.3+ can build Docker images without a Dockerfile using Cloud Native Buildpacks:

# Build and tag the image using the Spring Boot Maven plugin mvn spring-boot:build-image -Dspring-boot.build-image.imageName=myapp:1.0 # The plugin: # 1. Detects the runtime (Java/JVM) # 2. Applies Paketo buildpacks to create optimized layers # 3. Creates a container-aware image with sensible JVM defaults # 4. No Dockerfile to maintain # Pros: no Dockerfile, auto-updates base image, follows best practices # Cons: less control, slower than a tuned multi-stage Dockerfile, large base image
