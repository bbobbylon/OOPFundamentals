Spring Boot + Docker

Production-ready Dockerfiles for Spring Boot applications — multi-stage builds, layer optimization, and Docker Compose for local development.

🍃 How do you properly containerize a Spring Boot application for production?

Containerizing Spring Boot well means understanding the JVM in Docker, image size, and build speed. A naive apt install java + COPY fat.jar is a 1GB image with 60s builds; done right it's ~220MB with 5s CI rebuilds. The multi-stage Dockerfile compiles in a JDK stage then copies only the jar into a minimal JRE stage. Layer caching copies pom.xml + dependency:go-offline first (cached) and src/ last, so source changes skip the dependency download. JVM container flags matter: Java 10+ reads cgroup limits (-XX:+UseContainerSupport), and -XX:MaxRAMPercentage=75 sizes the heap to the container. Add Actuator liveness/readiness probes for Kubernetes, or skip the Dockerfile entirely with Buildpacks (mvn spring-boot:build-image).

  • Multi-stage build — JDK compiles, JRE ships the jar (~220MB not 1GB).
  • Layer caching — deps before source so rebuilds skip the download.
  • Container-aware JVM — UseContainerSupport + MaxRAMPercentage=75.
  • Actuator liveness/readiness probes; Buildpacks/Jib skip the Dockerfile.

Optimized Dockerfile

# BUILD stage: has JDK + Maven FROM eclipse-temurin:21-jdk-alpine AS build WORKDIR /build # 1. Copy pom only → download deps (cached) COPY pom.xml . RUN mvn dependency:go-offline -q # 2. Copy source → compile (cache miss here) COPY src ./src RUN mvn package -DskipTests -q # RUN stage: minimal JRE only FROM eclipse-temurin:21-jre-alpine AS run WORKDIR /app # Security: non-root RUN addgroup -S spring && adduser -S spring -G spring USER spring COPY --from=build /build/target/*.jar app.jar EXPOSE 8080 ENTRYPOINT ["java", "-XX:MaxRAMPercentage=75", "-XX:+ExitOnOutOfMemoryError", "-Dspring.config.location=classpath:/,/config/", "-jar", "app.jar"]

Build options comparison

Option 1: Multi-stage Dockerfile (this page). Full control, explicit, debuggable. Pro: you choose every layer. Con: maintain Dockerfile manually, security scanning needed. Option 2: Cloud Native Buildpacks. mvn spring-boot:build-image -Dspring-boot.build-image.imageName=myregistry/ciam:1.0. No Dockerfile. Buildpacks auto-detect Spring Boot, choose Bellsoft Liberica JRE, create optimized layered image. Pro: no Dockerfile to maintain, security patches auto-applied in base layers. Con: less control, longer first build. Option 3: Jib (Google). Maven plugin that builds OCI images without Docker daemon. mvn jib:build. Pushes directly to registry. Pro: no Docker needed in CI, fast incremental builds. Con: less flexible for non-standard setups. Layered JAR: Spring Boot splits the fat JAR into layers (deps / spring-boot-loader / snapshot-deps / app). Each layer is a Docker layer — only your app code layer changes between builds. Dramatically reduces pushed bytes to registry.

CIAM Spring Boot + Docker production: ADO pipeline: compile → test → docker build -t …azurecr.io/ciam-auth:$(Build.BuildId) → push → Helm upgrade — the BuildId tag gives exact traceability. -XX:MaxRAMPercentage=75 with a 1Gi limit gives a ~768MB heap, and -XX:+ExitOnOutOfMemoryError exits cleanly so K8s restarts the pod (faster than a hung JVM). Use JSON logging (LogstashEncoder) for Azure Monitor, and a custom PingHealthIndicator so readiness fails when Ping is down and traffic routes to healthy pods.

The problem

You copy the HEALTHCHECK line straight off this page, the app answers every request correctly, and the orchestrator still keeps killing it.

ECS cycles a healthy task every 90 seconds

You build the Dockerfile from Section 1 exactly as written. docker build succeeds. docker run starts. You hit http://localhost:8080/actuator/health from your own laptop and get back {"status":"UP"}. Everything about the app says it's fine.

Then ECS marks the task UNHEALTHY, drains it, and starts a replacement — which also goes UNHEALTHY 90 seconds later. The app in the logs never crashes. Nothing in Spring Boot ever throws. The HEALTHCHECK just keeps failing, forever, on a service that works.

image builds ✓ app responds 200 from your laptop ✓ HEALTHCHECK itself ⚠

The HEALTHCHECK command doesn't run on your laptop. It runs inside the container, using whatever binaries THAT image happens to ship.

Check what the base image actually contains, don't assume it
Run the base image alone and ask it for the tool ↓ docker run --rm eclipse-temurin:21-jre-alpine which curl prints nothing and exits 1 — curl was never there Swap to a binary the image already ships, or add the one you need ↓ Alpine's BusyBox ships wget by default — wget --no-verbose --tries=1 --spider http://localhost:8080/actuator/health || exit 1 needs nothing extra; alternatively RUN apk add --no-cache curl if you'd rather keep curl syntax Rebuild and watch the actual STATUS column, not just the app logs ↓ docker ps should read "(healthy)" within one interval; ECS's task health in the console flips the same way — the app was never the problem
A HEALTHCHECK is a program, and it runs where the container runs. It doesn't inherit your laptop's shell, your laptop's PATH, or the tools your normal terminal happens to have installed. If the base image is minimal — and JRE-alpine images are minimal on purpose, to stay small — every binary the HEALTHCHECK calls has to actually be sitting inside that same image, or the check fails before it ever reaches your code.
Alpine ships a kitchen with no can-opener. curl is not part of the base — wget (via BusyBox) is. A recipe written for a fully-stocked Debian kitchen fails quietly in this one, and nothing in the failure message mentions your Spring Boot app at all.

The mechanism

Walk the exact HEALTHCHECK line from Section 1 through what actually executes at runtime.

  1. Runtime stage builds FROM eclipse-temurin:21-jre-alpineno curl package
  2. Dockerfile bakes in HEALTHCHECK CMD curl -f http://localhost:8080/actuator/healthstored, not checked
  3. Container starts; Tomcat binds 8080; Actuator answers real HTTP requests with 200app is genuinely fine
  4. Every interval, Docker execs that CMD string INSIDE the container's own namespacenot from the host
  5. The shell resolves curl: no such binary — exits 127, not connection-refused127, not 200
  6. After 3 straight failures the container flips to unhealthy; ECS drains and replaces the taskorchestrator reacts to the check, not the app

Step 5 is the one to sit with: exit code 127 means "command not found," which is a completely different failure than the app returning an error. Docker's healthcheck log shows you the raw output if you run docker inspect --format='{{json .State.Health}}' <container> — it will literally say curl: not found if you know to look. Most people don't look; they just see "unhealthy" and start debugging the wrong layer of the stack.

curl wget (via BusyBox) netcat

Three tools you might reach for out of habit; only one is actually in the image without adding a package. BusyBox — the tiny multi-call binary Alpine bundles for basic shell utilities — includes a stripped-down wget by default. curl and netcat both need an explicit apk add. The fix isn't "use a smarter command," it's knowing which of the three slots is actually filled before you write the HEALTHCHECK line.

This page's Dockerfile builds clean, and curl http://podip:8080/actuator/health from your own machine returns {"status":"UP"}. ECS still cycles the task as UNHEALTHY every 90 seconds. What's the most likely cause?

Right. The CMD in a HEALTHCHECK runs inside the container's own filesystem and shell, and this exact base image doesn't ship curl. It exits 127 ("not found") on every single attempt — a failure that has nothing to do with Spring Boot. Swap to wget --spider (already present via BusyBox) or add curl with apk add, and the same signal starts working.

A real failure mode, but it doesn't match the symptoms here: if Actuator itself were returning 503, your own curl from your laptop would fail too. It didn't — it returned UP — which means the app is genuinely healthy and the check mechanism itself is what's broken.

Deregistration delay controls how long a task keeps draining traffic before ECS removes it from rotation — it has no bearing on whether the container's own internal HEALTHCHECK command can even execute. That setting matters elsewhere, just not here.

Where you have seen this before

"The base image doesn't ship the tool you assumed" is one of the most common ways a container quietly breaks.

Distroless images for hardened identity services

Security-conscious teams running CIAM workloads often go further than Alpine and use a distroless base — no shell at all, not even BusyBox. A HEALTHCHECK's CMD instruction needs a shell to interpret it, so it fails outright, not just when curl is missing. Teams that ship distroless bake a tiny static binary (like Go's grpc_health_probe) into the image at build time instead of relying on any shell tool.

fewer tools in the image = fewer assumptions you're allowed to make

Alpine Node images and native modules

npm install on a package with a native addon needs python3, make, and a C compiler to run node-gyp. A slim node:alpine image doesn't ship a build toolchain any more than the JRE-alpine image ships curl — the install fails with a compiler error that looks nothing like "missing package."

the same shape of bug, one layer earlier in the pipeline

ASP.NET's runtime-only image

mcr.microsoft.com/dotnet/aspnet deliberately ships no dotnet CLI — only what's needed to run an already-built app. A healthcheck script or entrypoint written and tested against the full sdk image works in dev and silently breaks the moment someone "optimizes" production to the runtime-only tag.

smaller image, fewer tools, same trap

1 — Production Dockerfile — Click Each Stage

# =================================================== # STAGE 1: Build stage (Maven + JDK — large, temp) # =================================================== FROM eclipse-temurin:21-jdk-alpine AS build
Multi-stage build stage 1 — uses the full JDK (includes compiler, javac). This stage does the heavy lifting: compiles and packages the app.

eclipse-temurin is the community OpenJDK image (successor to AdoptOpenJDK). alpine variant is smaller. AS build names this stage so stage 2 can reference it.
WORKDIR /workspace
Sets the working directory for all subsequent instructions. Created if it doesn't exist. Avoids long absolute paths in later commands.
# Copy pom.xml BEFORE source — layer cache trick COPY pom.xml . RUN mvn dependency:resolve -B # download deps (cached layer)
Layer caching optimization — copy pom.xml first and download dependencies in a separate layer. Maven dependencies rarely change, so this layer is cached on most builds.

If you copied all source code first, any code change would invalidate the deps layer and re-download everything. This order means only source changes trigger the build layer — deps layer stays cached.
COPY src ./src RUN mvn package -DskipTests # build the fat JAR
Now copy the source and build. Tests are skipped here because integration tests need a running DB — run them separately in CI before this Docker build step.

Output: /workspace/target/app.jar — the Spring Boot fat JAR.
# =================================================== # STAGE 2: Runtime stage (JRE only — small) # =================================================== FROM eclipse-temurin:21-jre-alpine
Multi-stage build stage 2 — fresh, minimal image. Only the JRE (Java Runtime Environment) — no compiler, no Maven, no source code.

Final image is typically 150–250 MB vs 500+ MB for a JDK image. Multi-stage is the standard production pattern — stage 1's contents are discarded.
# Security: run as non-root user RUN addgroup -S spring && adduser -S spring -G spring USER spring:spring
Security best practice — never run the JVM as root inside a container. If an attacker exploits a vulnerability and escapes the container, root in the container becomes root on the host.

Create a system user with no home directory and no password, then switch to it. Spring Boot runs fine as a non-root user.
COPY --from=build /workspace/target/*.jar app.jar
--from=build copies the JAR from the build stage into this runtime stage. The build tools, Maven cache, and source code stay in stage 1 and never enter the final image.
EXPOSE 8080 8081
Documents that the container listens on 8080 (app) and 8081 (Spring Boot Actuator). Does NOT publish to the host — that requires -p 8080:8080 at runtime. It's documentation + a hint to Docker tools.
ENTRYPOINT ["java", "-jar", "/app.jar"]
The command that runs when the container starts. Using exec form (JSON array) is required for proper signal handling — Docker can send SIGTERM directly to the Java process, allowing graceful shutdown.

Shell form ENTRYPOINT java -jar /app.jar wraps in /bin/sh, which intercepts signals — Spring Boot won't get SIGTERM and can't shut down gracefully.

3 — JVM Flags for Containers

❌ JVM without container awareness

# Container has 512MB memory limit # JVM sees HOST memory (e.g. 16GB) # Default heap = 25% of host = 4GB! # Container OOMKilled immediately. docker run -m 512m myapp:latest

✓ Container-aware JVM (Java 8u191+, Java 11+)

# UseContainerSupport is default in Java 11+ # JVM reads cgroup memory limits # Heap = 25% of container memory = 128MB docker run -m 512m \ -e JAVA_TOOL_OPTIONS="-XX:MaxRAMPercentage=75" \ myapp:latest # 75% of 512MB = 384MB heap # Works reliably in Docker/ECS/Kubernetes
JVM FlagPurpose
-XX:+UseContainerSupportDefault ON in Java 11+. Read cgroup CPU/memory limits instead of host values.
-XX:MaxRAMPercentage=75Heap = 75% of container memory limit. Use instead of -Xmx in containers.
-XX:+UseG1GCG1 garbage collector — good default for most Spring Boot apps.
-Dspring.profiles.active=prodActivate a Spring profile from the JVM without env var.
-Dfile.encoding=UTF-8Prevent character encoding surprises in containers with minimal locales.

4 — Alternative: Spring Boot Buildpacks (No Dockerfile)

Spring Boot 2.3+ can build Docker images without a Dockerfile using Cloud Native Buildpacks:

# Build and tag the image using the Spring Boot Maven plugin mvn spring-boot:build-image -Dspring-boot.build-image.imageName=myapp:1.0 # The plugin: # 1. Detects the runtime (Java/JVM) # 2. Applies Paketo buildpacks to create optimized layers # 3. Creates a container-aware image with sensible JVM defaults # 4. No Dockerfile to maintain # Pros: no Dockerfile, auto-updates base image, follows best practices # Cons: less control, slower than a tuned multi-stage Dockerfile, large base image
