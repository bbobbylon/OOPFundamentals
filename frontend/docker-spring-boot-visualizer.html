Spring Boot + Docker

Production-ready Dockerfiles for Spring Boot applications — multi-stage builds, layer optimization, and Docker Compose for local development.

How do you properly containerize a Spring Boot application for production?

Containerizing a Spring Boot application correctly requires understanding JVM behavior inside Docker, optimizing image size and build speed, and configuring Spring Boot for the container lifecycle. A naive FROM ubuntu; RUN apt install java; COPY fat.jar produces a 1 GB image with 60-second build times. The right approach produces a 220 MB image with 5-second CI builds after the first run. Multi-stage Dockerfile: the production pattern. Stage 1 (AS build) has the JDK and Maven/Gradle — it compiles your code. Stage 2 starts from a minimal JRE base and copies ONLY the compiled artifact from Stage 1. The final image has no JDK, no source code, no Maven binary — just the JRE and your JAR. Layer caching: the biggest CI speed-up. Dependencies in pom.xml change rarely; your source code changes on every commit. Copy pom.xml and run mvn dependency:go-offline FIRST — this layer is cached. Then copy src/ — cache miss only here. Result: rebuilds after source changes skip the ~3-minute dependency download. JVM container flags: old JVMs (pre-Java 10) didn't understand cgroups memory limits — a container with -m 1g would read the HOST's 16 GB RAM and allocate a 4 GB heap → immediate OOMKill. Java 10+ with -XX:+UseContainerSupport (default) reads the cgroup memory limit and sets the heap accordingly. Use -XX:MaxRAMPercentage=75 to allocate 75% of container memory to heap. Spring Boot Actuator probes: Kubernetes needs liveness and readiness endpoints. Spring Boot Actuator provides: /actuator/health/liveness (is the JVM alive?), /actuator/health/readiness (is the app ready to serve traffic?). Enable with management.endpoint.health.probes.enabled=true. Buildpacks: mvn spring-boot:build-image — no Dockerfile needed. Cloud Native Buildpacks auto-detect your Spring Boot app, choose the right base image, and build an optimized OCI image. Fewer security decisions to make manually.

Optimized Dockerfile

# BUILD stage: has JDK + Maven FROM eclipse-temurin:21-jdk-alpine AS build WORKDIR /build # 1. Copy pom only → download deps (cached) COPY pom.xml . RUN mvn dependency:go-offline -q # 2. Copy source → compile (cache miss here) COPY src ./src RUN mvn package -DskipTests -q # RUN stage: minimal JRE only FROM eclipse-temurin:21-jre-alpine AS run WORKDIR /app # Security: non-root RUN addgroup -S spring && adduser -S spring -G spring USER spring COPY --from=build /build/target/*.jar app.jar EXPOSE 8080 ENTRYPOINT ["java", "-XX:MaxRAMPercentage=75", "-XX:+ExitOnOutOfMemoryError", "-Dspring.config.location=classpath:/,/config/", "-jar", "app.jar"]

Spring Boot config for K8s

# application.yaml (K8s profile): server: shutdown: graceful # drain requests on SIGTERM spring: lifecycle: timeout-per-shutdown-phase: 30s management: endpoint: health: probes: enabled: true # /liveness + /readiness health: livenessState: enabled: true readinessState: enabled: true endpoints: web: exposure: include: health,info,metrics,prometheus logging: pattern: console: "%d{ISO8601} [%thread] %-5level %logger{36} - %msg%n" # JSON logging for Kubernetes log aggregation: # Use logback-spring.xml with LogstashEncoder # or logstash-logback-encoder library

Build options comparison

Option 1: Multi-stage Dockerfile (this page). Full control, explicit, debuggable. Pro: you choose every layer. Con: maintain Dockerfile manually, security scanning needed. Option 2: Cloud Native Buildpacks. mvn spring-boot:build-image -Dspring-boot.build-image.imageName=myregistry/ciam:1.0. No Dockerfile. Buildpacks auto-detect Spring Boot, choose Bellsoft Liberica JRE, create optimized layered image. Pro: no Dockerfile to maintain, security patches auto-applied in base layers. Con: less control, longer first build. Option 3: Jib (Google). Maven plugin that builds OCI images without Docker daemon. mvn jib:build. Pushes directly to registry. Pro: no Docker needed in CI, fast incremental builds. Con: less flexible for non-standard setups. Layered JAR: Spring Boot splits the fat JAR into layers (deps / spring-boot-loader / snapshot-deps / app). Each layer is a Docker layer — only your app code layer changes between builds. Dramatically reduces pushed bytes to registry.

CIAM Spring Boot + Docker production: ADO pipeline: compile → test → docker build -t $(acrLoginServer)/ciam-auth:$(Build.BuildId) . → docker push → Helm upgrade (or ArgoCD sync). Image tag = ADO BuildId = exact build traceability. -XX:MaxRAMPercentage=75 with K8s memory limit 1Gi: heap ~768 MB — sizing for Spring Boot with several services + JPA + connection pool. -XX:+ExitOnOutOfMemoryError: instead of JVM hanging in OOM state, it exits cleanly → K8s restarts the pod → faster recovery than a hung JVM. JSON logging in K8s: logback-spring.xml with LogstashEncoder (from logstash-logback-encoder) outputs structured JSON → Azure Monitor or Elasticsearch can parse and query log fields. Readiness endpoint: adds a custom HealthIndicator for Ping connectivity (@Component class PingHealthIndicator implements HealthIndicator) — if Ping is down, readiness fails → K8s stops sending traffic → load balancer routes to healthy pods.

1 — Production Dockerfile — Click Each Stage

# =================================================== # STAGE 1: Build stage (Maven + JDK — large, temp) # =================================================== FROM eclipse-temurin:21-jdk-alpine AS build
Multi-stage build stage 1 — uses the full JDK (includes compiler, javac). This stage does the heavy lifting: compiles and packages the app.

eclipse-temurin is the community OpenJDK image (successor to AdoptOpenJDK). alpine variant is smaller. AS build names this stage so stage 2 can reference it.
WORKDIR /workspace
Sets the working directory for all subsequent instructions. Created if it doesn't exist. Avoids long absolute paths in later commands.
# Copy pom.xml BEFORE source — layer cache trick COPY pom.xml . RUN mvn dependency:resolve -B # download deps (cached layer)
Layer caching optimization — copy pom.xml first and download dependencies in a separate layer. Maven dependencies rarely change, so this layer is cached on most builds.

If you copied all source code first, any code change would invalidate the deps layer and re-download everything. This order means only source changes trigger the build layer — deps layer stays cached.
COPY src ./src RUN mvn package -DskipTests # build the fat JAR
Now copy the source and build. Tests are skipped here because integration tests need a running DB — run them separately in CI before this Docker build step.

Output: /workspace/target/app.jar — the Spring Boot fat JAR.
# =================================================== # STAGE 2: Runtime stage (JRE only — small) # =================================================== FROM eclipse-temurin:21-jre-alpine
Multi-stage build stage 2 — fresh, minimal image. Only the JRE (Java Runtime Environment) — no compiler, no Maven, no source code.

Final image is typically 150–250 MB vs 500+ MB for a JDK image. Multi-stage is the standard production pattern — stage 1's contents are discarded.
# Security: run as non-root user RUN addgroup -S spring && adduser -S spring -G spring USER spring:spring
Security best practice — never run the JVM as root inside a container. If an attacker exploits a vulnerability and escapes the container, root in the container becomes root on the host.

Create a system user with no home directory and no password, then switch to it. Spring Boot runs fine as a non-root user.
COPY --from=build /workspace/target/*.jar app.jar
--from=build copies the JAR from the build stage into this runtime stage. The build tools, Maven cache, and source code stay in stage 1 and never enter the final image.
EXPOSE 8080 8081
Documents that the container listens on 8080 (app) and 8081 (Spring Boot Actuator). Does NOT publish to the host — that requires -p 8080:8080 at runtime. It's documentation + a hint to Docker tools.
ENTRYPOINT ["java", "-jar", "/app.jar"]
The command that runs when the container starts. Using exec form (JSON array) is required for proper signal handling — Docker can send SIGTERM directly to the Java process, allowing graceful shutdown.

Shell form ENTRYPOINT java -jar /app.jar wraps in /bin/sh, which intercepts signals — Spring Boot won't get SIGTERM and can't shut down gracefully.

3 — JVM Flags for Containers

❌ JVM without container awareness

# Container has 512MB memory limit # JVM sees HOST memory (e.g. 16GB) # Default heap = 25% of host = 4GB! # Container OOMKilled immediately. docker run -m 512m myapp:latest

✓ Container-aware JVM (Java 8u191+, Java 11+)

# UseContainerSupport is default in Java 11+ # JVM reads cgroup memory limits # Heap = 25% of container memory = 128MB docker run -m 512m \ -e JAVA_TOOL_OPTIONS="-XX:MaxRAMPercentage=75" \ myapp:latest # 75% of 512MB = 384MB heap # Works reliably in Docker/ECS/Kubernetes
JVM FlagPurpose
-XX:+UseContainerSupportDefault ON in Java 11+. Read cgroup CPU/memory limits instead of host values.
-XX:MaxRAMPercentage=75Heap = 75% of container memory limit. Use instead of -Xmx in containers.
-XX:+UseG1GCG1 garbage collector — good default for most Spring Boot apps.
-Dspring.profiles.active=prodActivate a Spring profile from the JVM without env var.
-Dfile.encoding=UTF-8Prevent character encoding surprises in containers with minimal locales.

4 — Alternative: Spring Boot Buildpacks (No Dockerfile)

Spring Boot 2.3+ can build Docker images without a Dockerfile using Cloud Native Buildpacks:

# Build and tag the image using the Spring Boot Maven plugin mvn spring-boot:build-image -Dspring-boot.build-image.imageName=myapp:1.0 # The plugin: # 1. Detects the runtime (Java/JVM) # 2. Applies Paketo buildpacks to create optimized layers # 3. Creates a container-aware image with sensible JVM defaults # 4. No Dockerfile to maintain # Pros: no Dockerfile, auto-updates base image, follows best practices # Cons: less control, slower than a tuned multi-stage Dockerfile, large base image
