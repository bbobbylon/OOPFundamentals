HTML Fundamentals

or, why the tag you choose is an accessibility decision

Document structure, semantic elements, forms, and accessibility — the literal skeleton every page on the web (including every page in this Dev Hub) is built from. This is the true zero-starting-point for Angular, React, and every other frontend track here.

The problem

A div can look like a button and be useless as one.

The div that pretends

Styled to look identical. Works with a mouse. Invisible to a keyboard and to a screen reader.

<div class="btn" onclick> no Tab focus ⚠no Enter / Space ⚠ announced as "group" ⚠no :disabled ⚠

To match a real <button> you would add tabindex, key handlers, a role and ARIA state — reimplementing what one tag gave you free.

Use the element that means it
<button> ↓ focusable, in tab order Enter and Space activate it ↓ announced by its role "Save, button" — and :disabled actually works
Semantics are behaviour, not decoration. The right element brings keyboard support, a role, and state for free. Everything you skip has to be rebuilt by hand — and usually isn't.
A screen reader

I navigate by landmarks and headings. Give me <nav>, <main>, <h1> and I can jump. Give me forty divs and I read from the top, every time.

A keyboard user

And I need Tab to reach it. If it isn't focusable, it doesn't exist for me — however good it looks.

Your future self

Plus <label for> makes the text click the input, and grouped radios only work if they share a name. Nobody remembers that at 5pm.

The mechanism

A document is a tree, and the tree is the meaning.

Headings are structure, not size. Screen-reader users pull up a list of headings to navigate, so h1 → h3 with no h2 leaves a hole in that outline. Pick the level for its place in the document and set the size in CSS — which is exactly how the Head First kit's .hf-say works: it looks like a headline without pretending to be one.

You need a clickable thing. It must work with the keyboard and be announced properly. Cheapest correct route?

Mouse-only. No focus, no Enter/Space, no role, no disabled state — four separate things to reimplement.

Closer, and still incomplete: role and tabindex give you focus and announcement, but you must still wire Enter AND Space yourself, and manage aria-disabled by hand. You have rebuilt a button, worse.

Questions from the back row

Does semantic HTML actually matter for SEO, or is that a myth?

It matters, but accessibility is the stronger reason. A crawler and a screen reader want the same thing — a document whose structure is legible without seeing it. Build for the second and you get the first.

When SHOULD I use a div?

When you need a box purely for layout or styling and it carries no meaning. That is most of them, and it is fine. The rule is not "avoid divs" — it is "don't use a div where a meaningful element exists".

Is ARIA the fix when I can't use the right element?

It's the fallback, not the fix. The first rule of ARIA is not to use ARIA if a native element will do — because ARIA only changes what is announced, never what actually works. It cannot make something focusable or make Space activate it.

🧱 What is HTML — and why does "semantic" markup matter?

HTML (HyperText Markup Language) is not a programming language — it's a markup language that describes the structure and meaning of content on a page: "this is a heading," "this is a paragraph," "this is a form the user fills in." The browser reads your HTML file top to bottom and builds an in-memory tree called the DOM (Document Object Model) — every tag becomes a node in that tree, and everything you'll later do with CSS (styling) or JavaScript (behavior) works by finding and manipulating those DOM nodes. Writing semantic HTML — using <nav> instead of <div class="nav">, <button> instead of a clickable <div> — isn't a style preference: screen readers, search engines, and browsers all read the tag names themselves to understand what's on the page, and a <div> tells them nothing.

  • HTML describes structure and meaning, not appearance (that's CSS) or behavior (that's JavaScript).
  • The browser parses HTML into the DOM — a tree of nodes that CSS and JS both operate on.
  • Semantic elements are read by machines — screen readers navigate by landmark (<nav>, <main>), search engines weight <h1> and <article> content differently than a generic <div>.
  • Forms are the web's original data-entry primitive — every login page, search box, and checkout flow is still built on <form>, <input>, and <label>, even inside a modern SPA.

The document skeleton

<!doctype html> <html lang="en"> <head> <meta charset="utf-8"> <meta name="viewport" content="width=device-width, initial-scale=1"> <title>My Page</title> <link rel="stylesheet" href="style.css"> </head> <body> <!-- everything visible goes here --> </body> </html>

Semantic vs div-soup

<!-- Bad: means nothing to a screen reader --> <div class="header">...</div> <div class="nav">...</div> <div class="main">...</div> <!-- Good: a landmark list is auto-generated --> <header>...</header> <nav>...</nav> <main>...</main> <footer>...</footer>

Forms — the original data entry

<form action="/login" method="post"> <label for="em">Email</label> <input id="em" type="email" required> <label for="pw">Password</label> <input id="pw" type="password" required> <button type="submit">Log in</button> </form>

CIAM / real-world tie-in: Every login form you've ever used — Ping, Entra, Auth0, this app's own register/login screens — is fundamentally a <form> with labeled <input>s. HTML5's required and type="email" give instant UX feedback, but they run entirely in the browser and can be bypassed with dev tools or a raw HTTP client — so every field validated on the client (here, or in Angular Reactive Forms, or React) must be re-validated server-side too (this app's Spring Boot backend does this with @Valid — see the Validation page). Client validation is a UX courtesy; server validation is the actual security boundary.

1. The Document Skeleton

Every HTML file starts with the same four pieces. This is literally the first few lines of every page in this Dev Hub, including this one.

<!doctype html>
tells the browser "use modern standards mode," not quirks mode from the 1990s
<html lang="en">
root element; lang attribute tells screen readers which pronunciation rules to use
<head>
metadata: title, charset, viewport, stylesheet links — nothing here is rendered directly
<body>
everything visible: text, images, forms, the whole rendered page
<!doctype html> <html lang="en"> <head> <meta charset="utf-8" /> <meta name="viewport" content="width=device-width, initial-scale=1" /> <title>My Page</title> </head> <body> <!-- everything visible goes here --> </body> </html>
Key insight: the browser parses this file as a stream, top to bottom, building the DOM tree incrementally — it doesn't wait for the whole file to download before starting. That's why <link rel="stylesheet"> tags go in <head> (block rendering until CSS is known) but <script> tags are often placed at the end of <body> (so they don't block content from appearing first) — this exact tradeoff is covered in depth on the upcoming Browser Rendering & Critical Path page.

2. Semantic Elements — Structure That Means Something

A generic <div> carries zero meaning. Semantic elements describe the ROLE of the content, which browsers, screen readers, and search engines all read directly.

Landmark elements

<header>site logo, title, top nav</header> <nav>primary navigation links</nav> <main><!-- exactly ONE per page --> <article>self-contained content</article> <section>thematic grouping</section> <aside>tangential content</aside> </main> <footer>copyright, links</footer>

Why it's not cosmetic

A screen reader user can jump straight to <main> or list every <nav> region without reading the whole page. Search engine crawlers weight text inside <article>/<h1> higher than the same text inside an unlabeled <div>. Browser devtools' Accessibility Tree — the thing screen readers actually consume — is built directly from these tag names, not from CSS classes.

Heading rule: exactly one <h1> per page (the page's main subject), and don't skip levels (an <h4> should never directly follow an <h2>) — screen reader users often navigate a page by jumping between headings, and a broken hierarchy is disorienting the same way a broken outline would be.

3. Forms, Validation & Accessibility

Forms are how the web collects input — and they carry two responsibilities that are easy to get wrong: binding labels to inputs correctly, and treating client-side validation as UX, not security.

<form action="/login" method="post"> <label for="email">Email</label> <input id="email" name="email" type="email" required /> <label for="pw">Password</label> <input id="pw" name="password" type="password" required minlength="8" /> <button type="submit">Log in</button> </form>
label[for] ↔ input[id]clicking the label focuses the input; screen readers announce the label when the input receives focus — without this pairing, neither happens
alt text on imagesread aloud by screen readers, shown as fallback text if the image 404s — never optional, and an empty alt="" is correct for purely decorative images
semantic landmarks > ARIAprefer <nav>/<button> over div+aria-role — "no ARIA is better than bad ARIA" (W3C's own guidance)
keyboard navigabilityevery interactive element must be reachable and operable via Tab/Enter/Space alone — a div with an onclick handler is invisible to keyboard users unless you add tabindex + a key handler
Key insight: HTML5's required, type="email", and pattern attributes stop an obviously-invalid submission before any network request fires — good for instant feedback. But they run entirely in the user's browser, which the user fully controls: opening devtools and removing required, or firing a raw fetch()/curl request directly at /login, bypasses all of it instantly. The server (this app's Spring Boot backend, via @Valid and Bean Validation annotations) MUST independently re-validate every field — client validation is a courtesy, server validation is the actual boundary.
