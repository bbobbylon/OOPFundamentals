Big O Notation — A Complete Tour

How algorithms scale, with real-world examples, code, and a time-at-scale reality check.

🧩 What is Big O notation — and why does it tell you whether your code will still work when the data grows 100× or 1000×?

Big O notation describes how the runtime (or memory usage) of an algorithm grows relative to its input size. It answers the question: "if the input doubles, how much longer does this take?" This is critical because a solution that works perfectly for 100 users might completely fail for 100,000 users — and Big O tells you which solutions will scale and which won't, before you even run the code. O(1) — constant time: runtime doesn't depend on input size at all. Array access by index (arr[42]), HashMap get/put, stack push/pop. These are the fastest possible operations. 1 item or 1 million items — same time. O(log n) — logarithmic time: runtime grows by 1 step each time input doubles. Binary search: n=1000 needs ~10 steps; n=1,000,000 needs ~20 steps. This is the "halving" pattern — each step eliminates half the remaining possibilities. BST search, heap operations, binary search in sorted array. Excellent for large datasets. O(n) — linear time: runtime grows proportionally with input. Single loop over n elements — 2× input = 2× time. Finding an element in an unsorted array, counting occurrences, printing all items. This is the baseline you should aim for or beat. O(n log n) — linearithmic time: slightly worse than linear. The best possible time for comparison-based sorting algorithms (Merge Sort, Quick Sort average, Heap Sort). Sorting n=1000 takes ~10,000 steps; sorting n=1,000,000 takes ~20,000,000 steps. Acceptable for most sorting needs. O(n²) — quadratic time: runtime grows with the square of input. Nested loops over the same collection — n=1000 → 1,000,000 operations; n=10,000 → 100,000,000 operations. This is where performance problems appear. Bubble Sort, Selection Sort, checking all pairs. Avoid on large datasets. O(2ⁿ) — exponential time: doubles with each additional input element. n=30 → ~1,000,000,000 operations. Only feasible for very small inputs. Recursive Fibonacci without memoization, some brute-force backtracking. Solve with dynamic programming (memoization). Big O rules: (1) drop constants — O(2n) = O(n); (2) drop lower-order terms — O(n² + n) = O(n²); (3) analyze the worst case by default; (4) for nested loops, multiply complexities — a loop of n inside a loop of n = O(n²).

Complexity code examples

// O(1) — same time regardless of input: int getFirst(int[] arr) { return arr[0]; } map.get("key"); // HashMap lookup // O(log n) — halves remaining each step: int binarySearch(int[] arr, int target) { int lo=0, hi=arr.length-1; while (lo <= hi) { int mid = lo + (hi-lo)/2; // avoids int overflow if (arr[mid]==target) return mid; else if (arr[mid]<target) lo=mid+1; else hi=mid-1; } return -1; } // O(n) — one pass through input: int sum(int[] arr) { int total=0; for (int x : arr) total+=x; // n operations return total; } // O(n²) — nested loops over same data: boolean hasDuplicates(int[] arr) { for (int i=0; i<arr.length; i++) // n iterations for (int j=i+1; j<arr.length; j++) // n iterations each if (arr[i]==arr[j]) return true; return false; // O(n²) total // Better: use a HashSet → O(n) }

Space complexity

// Space complexity: how much EXTRA memory does it use? // (not counting the input itself — "auxiliary space") // O(1) space: int sum(int[] arr) { int total = 0; // only one extra variable, regardless of n for (int x : arr) total += x; return total; } // O(n) space: List<Integer> doubled(int[] arr) { List<Integer> result = new ArrayList<>(); // grows with n for (int x : arr) result.add(x * 2); return result; } // O(log n) space (recursive binary search — call stack depth): int bsearch(int[] a, int t, int lo, int hi) { if (lo>hi) return -1; int mid=lo+(hi-lo)/2; if (a[mid]==t) return mid; if (a[mid]<t) return bsearch(a,t,mid+1,hi); // log n depth return bsearch(a,t,lo,mid-1); } // O(n) space (DFS recursion depth = n worst case): // e.g. factorial(n) calls factorial(n-1) ... factorial(1) // n stack frames at once = O(n) space // Time vs Space trade-off: // HashSet turns O(n²) duplicate check into O(n) time // Cost: O(n) extra space (the HashSet)

Real-world scaling table

// n=1,000 users, 1GHz CPU (10⁹ ops/sec): // O(1) → 0.000001ms (always instant) // O(log n) → 0.00001ms (log₂1000 ≈ 10 ops) // O(n) → 0.001ms (1,000 ops) // O(n lg n)→ 0.01ms (10,000 ops) // O(n²) → 1ms (1,000,000 ops) // O(2ⁿ) → 10^293 years (impossible!) // n=1,000,000 users (1M — real CIAM scale): // O(1) → 0.000001ms (still instant) // O(log n) → 0.00002ms (log₂1M ≈ 20 ops) // O(n) → 1ms (1M ops) // O(n lg n)→ 20ms (20M ops) // O(n²) → 1000 SECONDS (= 17 minutes!) // Key insight: // At 1M scale, O(n²) is unusable // O(n log n) is the practical limit for in-memory ops // Database indexes make O(n) queries → O(log n) on disk // HashMap makes O(n) "find in list" → O(1) // This is why "use a HashMap" solves so many performance problems

In CIAM / Your Job: Big O thinking applies to every layer of your CIAM stack. In Spring Boot: checking if a user has a permission by iterating a List is O(n) — use a Set for O(1). Fetching users one-by-one in a loop is O(n) DB queries (N+1 problem) — use a JOIN FETCH for O(1) queries. In Angular: filtering a large user list with .filter() on every change detection cycle is O(n) per tick — pipe it through a memoized pure pipe so it only runs when the data changes. In Ping IDM: a reconciliation that checks each user against all existing accounts is O(n×m) — add an index or use LDAP search with filters. At CIAM scale (millions of users), the difference between O(n) and O(log n) is the difference between a query that takes 0.001ms and one that takes 1ms — 1000× slower, noticeable at scale.

2. Each complexity — where you'll see it in the real world

O(1) — Constant Time

"the time doesn't depend on input size"

The fastest possible. No matter how big the input gets, the work stays the same.

Real-world examples
  • Looking up a value in a HashMap by key
  • Accessing array element by index: arr[42]
  • Pushing onto a stack, enqueuing into a queue (with right structures)
  • Checking if a number is even (n % 2 == 0)
  • Returning the first element of a list
Java that produces this
// O(1) — just one array lookup, no matter how big arr is.
int first = arr[0];
int age = ageMap.get("Bobby");

O(log n) — Logarithmic Time

"each step halves the work remaining"

The signature of "divide and conquer." For n = 1,000,000, that's only ~20 steps. Almost as good as O(1) in practice.

Real-world examples
  • Binary search on a sorted array
  • Looking up a name in a phone book (or actual dictionary)
  • Search/insert in a balanced BST, TreeMap, TreeSet
  • Finding a file in a sorted directory listing
  • Counting digits in a number: Math.log10(n)
Java that produces this
// Each iteration cuts the range in half.
while (low <= high) {
    int mid = (low + high) / 2;
    if (arr[mid] == target) return mid;
    if (arr[mid] < target) low = mid + 1;
    else                  high = mid - 1;
}

O(n) — Linear Time

"work scales with input size"

You touch every element exactly once. Double the input = double the time. Almost always acceptable.

Real-world examples
  • Linear search through an unsorted list
  • Finding the max/min of a list
  • Summing all the elements in an array
  • Reading every line in a file
  • Counting characters in a string
  • ArrayList.contains(x) (it has to scan)
Java that produces this
// Visit every element exactly once.
int max = arr[0];
for (int i = 1; i < arr.length; i++) {
    if (arr[i] > max) max = arr[i];
}

O(n log n) — Linearithmic Time

"the speed limit for comparison-based sorting"

A bit worse than linear, but practically very fast. The best general-purpose sorts all live here.

Real-world examples
  • Merge sort, Quick sort (average), Heap sort
  • Arrays.sort(), Collections.sort()
  • Java's Stream.sorted()
  • Building a balanced BST from n elements
  • Many divide-and-conquer algorithms
Java that produces this
// Recursive split (log n levels) × linear merge (n work per level)
void mergeSort(int[] a, int low, int high) {
    if (low >= high) return;
    int mid = (low + high) / 2;
    mergeSort(a, low, mid);
    mergeSort(a, mid + 1, high);
    merge(a, low, mid, high);
}

O(n²) — Quadratic Time

"nested loops over the same data"

The first complexity that genuinely hurts at scale. Double n = 4× the work. A million items takes a trillion ops.

Real-world examples
  • Bubble sort, Selection sort, Insertion sort
  • Finding all duplicate pairs in a list (naive)
  • Comparing every user with every other user
  • Brute-force "check every pair" algorithms
  • Building a multiplication table
Java that produces this
// Nested loop, each O(n) — total O(n × n) = O(n²)
for (int i = 0; i < arr.length; i++) {
    for (int j = i + 1; j < arr.length; j++) {
        if (arr[i] == arr[j]) return true;
    }
}

O(2ⁿ) — Exponential Time

"each +1 in input DOUBLES the work"

Catastrophic at scale. n = 50 already takes longer than the age of the universe. Often a sign you need a smarter algorithm.

Real-world examples
  • Naive recursive Fibonacci (without memoization)
  • Generating all subsets of a set ("power set")
  • Traveling Salesman brute-force
  • The "Boolean satisfiability" problem (SAT)
  • Solving NxN sudoku by trying everything
Java that produces this
// Each call branches into TWO more calls. 2^n total.
int fib(int n) {
    if (n < 2) return n;
    return fib(n - 1) + fib(n - 2);
}

The big takeaways

  • For small n (under ~1000), the difference barely matters. A bubble sort on 100 items is fine.
  • For large n, the complexity class is everything. O(n²) on a million items = grab a coffee. O(n log n) = blink.
  • Algorithm choice beats micro-optimization by orders of magnitude. A clever O(n log n) Python script outruns a hand-tuned O(n²) C program when n is big enough.
  • If you hit O(2ⁿ), you're probably doing something brute-force. There's usually a smarter approach (memoization, dynamic programming, math).
