2. Each complexity — where you'll see it in the real world

O(1) — Constant Time

"the time doesn't depend on input size"

The fastest possible. No matter how big the input gets, the work stays the same.

Real-world examples
  • Looking up a value in a HashMap by key
  • Accessing array element by index: arr[42]
  • Pushing onto a stack, enqueuing into a queue (with right structures)
  • Checking if a number is even (n % 2 == 0)
  • Returning the first element of a list
Java that produces this
// O(1) — just one array lookup, no matter how big arr is.
int first = arr[0];
int age = ageMap.get("Bobby");

O(log n) — Logarithmic Time

"each step halves the work remaining"

The signature of "divide and conquer." For n = 1,000,000, that's only ~20 steps. Almost as good as O(1) in practice.

Real-world examples
  • Binary search on a sorted array
  • Looking up a name in a phone book (or actual dictionary)
  • Search/insert in a balanced BST, TreeMap, TreeSet
  • Finding a file in a sorted directory listing
  • Counting digits in a number: Math.log10(n)
Java that produces this
// Each iteration cuts the range in half.
while (low <= high) {
    int mid = (low + high) / 2;
    if (arr[mid] == target) return mid;
    if (arr[mid] < target) low = mid + 1;
    else                  high = mid - 1;
}

O(n) — Linear Time

"work scales with input size"

You touch every element exactly once. Double the input = double the time. Almost always acceptable.

Real-world examples
  • Linear search through an unsorted list
  • Finding the max/min of a list
  • Summing all the elements in an array
  • Reading every line in a file
  • Counting characters in a string
  • ArrayList.contains(x) (it has to scan)
Java that produces this
// Visit every element exactly once.
int max = arr[0];
for (int i = 1; i < arr.length; i++) {
    if (arr[i] > max) max = arr[i];
}

O(n log n) — Linearithmic Time

"the speed limit for comparison-based sorting"

A bit worse than linear, but practically very fast. The best general-purpose sorts all live here.

Real-world examples
  • Merge sort, Quick sort (average), Heap sort
  • Arrays.sort(), Collections.sort()
  • Java's Stream.sorted()
  • Building a balanced BST from n elements
  • Many divide-and-conquer algorithms
Java that produces this
// Recursive split (log n levels) × linear merge (n work per level)
void mergeSort(int[] a, int low, int high) {
    if (low >= high) return;
    int mid = (low + high) / 2;
    mergeSort(a, low, mid);
    mergeSort(a, mid + 1, high);
    merge(a, low, mid, high);
}

O(n²) — Quadratic Time

"nested loops over the same data"

The first complexity that genuinely hurts at scale. Double n = 4× the work. A million items takes a trillion ops.

Real-world examples
  • Bubble sort, Selection sort, Insertion sort
  • Finding all duplicate pairs in a list (naive)
  • Comparing every user with every other user
  • Brute-force "check every pair" algorithms
  • Building a multiplication table
Java that produces this
// Nested loop, each O(n) — total O(n × n) = O(n²)
for (int i = 0; i < arr.length; i++) {
    for (int j = i + 1; j < arr.length; j++) {
        if (arr[i] == arr[j]) return true;
    }
}

O(2ⁿ) — Exponential Time

"each +1 in input DOUBLES the work"

Catastrophic at scale. n = 50 already takes longer than the age of the universe. Often a sign you need a smarter algorithm.

Real-world examples
  • Naive recursive Fibonacci (without memoization)
  • Generating all subsets of a set ("power set")
  • Traveling Salesman brute-force
  • The "Boolean satisfiability" problem (SAT)
  • Solving NxN sudoku by trying everything
Java that produces this
// Each call branches into TWO more calls. 2^n total.
int fib(int n) {
    if (n < 2) return n;
    return fib(n - 1) + fib(n - 2);
}

The big takeaways

  • For small n (under ~1000), the difference barely matters. A bubble sort on 100 items is fine.
  • For large n, the complexity class is everything. O(n²) on a million items = grab a coffee. O(n log n) = blink.
  • Algorithm choice beats micro-optimization by orders of magnitude. A clever O(n log n) Python script outruns a hand-tuned O(n²) C program when n is big enough.
  • If you hit O(2ⁿ), you're probably doing something brute-force. There's usually a smarter approach (memoization, dynamic programming, math).
