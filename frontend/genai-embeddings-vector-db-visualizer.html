Embeddings & Vector Databases

How text becomes a vector, how "closeness" in that vector space captures meaning, and how vector databases make similarity search fast at scale — the retrieval backbone under every RAG system.

🧭 What is a text embedding, and why does an LLM app need a vector database?

An embedding model converts a piece of text into a fixed-length list of numbers — a vector — such that texts with similar meaning land close together in that high-dimensional space, even if they share no words in common ("puppy" and "dog" end up near each other; "puppy" and "spreadsheet" do not). This is the foundation of semantic search: instead of matching keywords, you compare vectors with cosine similarity. A vector database (Pinecone, Weaviate, Chroma, or the pgvector extension on plain Postgres) stores millions of these vectors and uses an approximate nearest-neighbor (ANN) index like HNSW to find the closest ones in milliseconds instead of scanning every row.

  • Embedding = meaning as coordinates — similar meaning, nearby vectors.
  • Cosine similarity measures the angle between two vectors, ignoring magnitude.
  • Vector DBs index embeddings for fast approximate nearest-neighbor search at scale.
  • Same model in, same model out — mixing embedding models breaks the whole space.

Turning text into a vector

B) / (|A| * |B|) # Result range: -1 (opposite) .. 1 (identical direction) import numpy as np def cosine_sim(a, b): return np.dot(a, b) / (np.linalg.norm(a) * np.linalg.norm(b)) cosine_sim(embed("forgot password"), embed("reset my password")) # 0.88 cosine_sim(embed("forgot password"), embed("quarterly earnings")) # 0.06 # Cosine ignores vector LENGTH — only direction (meaning) matters

pgvector: a vector DB inside Postgres

CREATE EXTENSION IF NOT EXISTS vector; CREATE TABLE doc_embeddings ( id BIGSERIAL PRIMARY KEY, content TEXT NOT NULL, embedding VECTOR(384) NOT NULL ); -- HNSW index for fast approximate search CREATE INDEX ON doc_embeddings USING hnsw (embedding vector_cosine_ops); -- <=> is pgvector's cosine-distance operator SELECT content FROM doc_embeddings ORDER BY embedding <=> '[0.02,-0.11,...]' LIMIT 5;

CIAM tie-in: pgvector means you don't need a separate vector-DB service — the same Postgres instance backing your users table can hold a support_ticket_embeddings table for semantic ticket search, or embed OAuth scope descriptions so a "what does read:profile mean?" search works in plain English. The problem

You swap the exact same cosine_sim function above for a raw dot product because it's one fewer division per comparison — and suddenly an off-topic document starts beating the actually-relevant one to the top of every search.

Two candidates, one query — real computed scores, not invented ones
Candidate A — 15° off-topic direction, norm 1.0 — dot product score0.9659
Candidate B — 50° off-topic direction, norm 1.6 — dot product score1.0285
Raw dot product's winnerB — the WRONG one
Same two vectors, same query, worked with Python's math module to four decimal places. B is 3.3× further off-topic than A (50° vs 15°) and still wins — because raw dot product never divides by anything; a bigger vector always gets a bigger number, direction or no direction.
Dot product: 1.0285 vs 0.9659

No division by the norms, so B's 1.6× length inflates its score past A's — the ranking now answers "which vector is longer AND roughly pointing the right way," not "which is closest."

Cosine similarity: 0.9659 vs 0.6428

The exact same two vectors, divided by their own norms first. Direction only. A — genuinely closer to the query — wins by a wide, correct margin.

cosine_sim() divides by norm(a)×norm(b) on every comparison→ a profiler flags that division as the hot line→ division removed, or the vector DB's index type switched to inner-product→ every comparison is now a raw dot product→ vector magnitude becomes a silent, unrequested second vote

Not every embedding model guarantees unit-length output — some do (OpenAI's text-embedding-3 models are documented as pre-normalized), but plenty of open-source sentence-transformer models are not, unless you explicitly call a normalize step. Once vector lengths vary across your corpus, magnitude rides along in every ranking whether you wanted it there or not.

Decide on purpose whether magnitude should count. If you want cosine similarity, normalize the vectors to unit length ONCE, at write time — do it when you store the embedding, not on every query, and a plain dot product at search time then IS cosine similarity, correctly and cheaply. If you switch a vector DB's metric type, re-check what it assumes: an "inner product" index and a "cosine" index are not interchangeable performance knobs, they answer a different question against the exact same stored vectors. And never assume a third-party embedding model normalizes for you — check the docs, or just measure norm(vec) across a sample.

The one-sentence rule. Cosine similarity divides out magnitude on purpose so that only direction — meaning — decides the ranking; drop that division and you've reintroduced magnitude as a silent, unintended tiebreaker.
Picture two arrows pointing in nearly the exact same direction — same meaning, same "topic" — but one is drawn twice as long. Cosine similarity says they're both about equally close, because it only reads the angle. Raw dot product says the longer one wins, because it also reads the ruler.
The mechanism

Follow the exact same two candidate vectors through both formulas and watch where they stop agreeing.

  1. Query vector Q embedded once, held fixed for both comparisonsquery
  2. Candidate A: points in almost the same direction as Q, but its norm is 1.0on-topic, short
  3. Candidate B: points in a noticeably worse direction than Q, but its norm is 1.6off-topic, long
  4. Cosine similarity divides both dot products by their own norms — direction only — Candidate A ranks highercosine ranking
  5. Raw dot product skips that division — Candidate B's larger norm inflates its score past A'sdot-product ranking
  6. Same two vectors, same "closest match" question, two different winners depending only on which formula asked itflipped result

Step 5 is where it goes wrong, and step 6 is why nobody notices right away: nothing crashed, nothing errored, the query returned A RESULT — just not the one direction alone would have picked.

the corpus is re-indexed with a raw dot-product (inner-product) metric instead of cosinea "just as accurate, faster to query" swap
everything that reacts ↓
short, focused queries the one document whose embedding happens to have the largest norm in the corpus typical medium-length documents

Most of the corpus barely notices the swap — their vector lengths are close enough that direction still dominates. It's the one outlier vector with an unusually large norm that reacts: it now outranks genuinely closer matches on nearly every query, for a reason that has nothing to do with what it's about.

Your team swaps a cosine-similarity vector search for a raw dot-product index because it queries faster. After the swap, some clearly off-topic documents start outranking clearly relevant ones on the same queries. What changed?

Right — cosine similarity divides out magnitude specifically so only direction (meaning) decides the ranking. A raw dot product doesn't do that division, so a vector with a larger norm can win purely on size, regardless of how well it actually matches.

Nothing in this scenario touched the embedding model — the same vectors, computed the same way, are simply being compared with a different formula. The model isn't the variable here.

ANN's approximate recall trade-off (already covered above) causes occasional near-misses at random — it doesn't produce a consistent, explainable bias toward specific documents the way an unnormalized magnitude does.

The whole page on a napkin: a text embedding turns a string into a fixed-length vector so that semantically similar inputs land close together, cosine similarity finds the nearest ones by comparing direction, and a vector database adds an approximate-nearest-neighbor index so that search stays fast past thousands of vectors — but the whole index only works if you never mix embeddings from two different models. The one new sentence this block adds: cosine similarity only equals a raw dot product when every vector has the same length, so swapping to a raw dot-product metric for speed silently lets vector magnitude — not meaning — start deciding the ranking.

1. What Is a Text Embedding?

An embedding model is a neural network (usually a transformer encoder) trained so that semantically similar inputs produce numerically similar output vectors. The vector's individual numbers aren't human-readable — what matters is relative position in the space.

"reset my password"
Tokenize

Encoder
transformer layers
Pooling
mean/CLS token → 1 vector
Output
e.g. 384 or 1536 floats
from sentence_transformers import SentenceTransformer
model = SentenceTransformer('all-MiniLM-L6-v2')  # 384-dim, fast, local

vec = model.encode("reset my password")
len(vec)  # 384 — same length no matter the input length
# "reset my password" and "forgot password" land close together
# "reset my password" and "quarterly earnings report" land far apart
Dimensionality is a tradeoff: smaller vectors (384) are cheaper to store and search but capture less nuance; larger vectors (1536+, like OpenAI's text-embedding-3-large) capture more meaning at higher storage/compute cost.

2. Cosine Similarity & Nearest-Neighbor Search

To find "what's semantically closest to this query," compare the query vector against every candidate vector using cosine similarity — the cosine of the angle between them. It ignores vector magnitude, so it measures direction (meaning) only.

"forgot password"
0.88
"can't log in"
0.71
"update billing address"
0.22
"quarterly earnings"

import numpy as np
def cosine_sim(a, b):  # the actual formula — one call per pair of vectors compared
    return np.dot(a, b) / (np.linalg.norm(a) * np.linalg.norm(b))  # dot product ÷ magnitudes = the cosine of the angle

# Brute force: compare against every row — O(n), fine under ~100k vectors
scores = [(doc_id, cosine_sim(query_vec, v)) for doc_id, v in all_vectors]  # runs the formula above against EVERY stored vector
scores.sort(key=lambda x: x[1], reverse=True)  # sorts by the score (2nd tuple item), most similar first
Brute-force comparison is O(n) per query — fine for thousands of vectors, too slow for millions. That's what a vector database's ANN index solves.

3. Vector Databases in Practice

A vector database stores embeddings alongside metadata and builds an approximate nearest-neighbor (ANN) index — commonly HNSW (Hierarchical Navigable Small World graphs) — trading a small amount of recall for orders-of-magnitude faster search.

# Ingestion pipeline: chunk → embed → store
def ingest(conn, doc_text, chunk_size=500):
    chunks = split_into_chunks(doc_text, chunk_size)  # overlap ~10-20%
    for chunk in chunks:
        vec = model.encode(chunk).tolist()
        conn.execute(
            "INSERT INTO doc_embeddings (content, embedding) VALUES (%s, %s)",
            (chunk, vec)
        )

# Query pipeline: embed the query with the SAME model, then search
def search(conn, query, k=5):
    qvec = model.encode(query).tolist()
    return conn.execute(
        "SELECT content FROM doc_embeddings ORDER BY embedding <=> %s LIMIT %s",
        (qvec, k)
    ).fetchall()
The #1 real-world bug: embedding your documents with one model (say, 1536-dim text-embedding-3-small) and later embedding queries with a different model or dimension. Vector spaces from different models aren't compatible — best case you get a dimension-mismatch error, worst case it silently returns nonsense "matches" because the numbers happen to align by coincidence. Always pin one embedding model per index and re-embed everything if you ever change it.
