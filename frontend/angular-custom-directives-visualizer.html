Angular Custom Directives — Attribute, Structural & Composition

Build your own directives to extend HTML elements with behavior — from hover effects to custom *ngIf clones to composing CDK behaviors.

🧩 What is a custom directive? When do you need one instead of a component?

A component has a template — it renders HTML. A directive has no template — it attaches to an existing element and adds behaviour without changing its look or creating new DOM. Reach for one when you want to extend any element: a hover effect on any button, auto-focus on any input, a permission gate on any element, drag on any container. The behaviour then applies with a single attribute: <button appRipple>, <input appAutoFocus>, <div [appPermission]="'ADMIN'">.

  • Attribute directive: no template, just behaviour on the host — read it via inject(ElementRef) and react with @HostListener / @HostBinding.
  • Structural directive: adds/removes DOM using a TemplateRef + ViewContainerRef (the * syntax) — e.g. a role gate.
  • Directives are reusable across any element — that's why they beat copy-pasting the same behaviour into many components.
  • The directive composition API (15+) lets a component apply hostDirectives (CDK drag, tooltip…) with no wrapper markup.
  • Like everything in Angular, a directive can inject() services — so a permission directive can read your AuthStore.

Attribute directive

@Directive({ selector: '[appHighlight]' }) with private el = inject(ElementRef) and @HostListener('mouseenter') onEnter() { this.el.nativeElement.style.background = 'yellow'; }. Use: <p appHighlight>. No template, no new DOM.

Structural directive

Controls structure — adds/removes elements. Built-ins: *ngIf, *ngFor. Custom: a [appHasRole] setter that does vcr.createEmbeddedView(tmpl) or vcr.clear(). Use: <button *appHasRole="'ADMIN'">Delete</button>.

Directive composition API

Apply directives to a component without touching its template: @Component({ hostDirectives: [CdkDrag, TooltipDirective] }). The component gains drag + tooltip behaviour, optionally re-exposing their inputs. Angular 15+.

In CIAM:an *appHasRole directive hides any element the user's token lacks the role for (<button *appHasRole="'USER_ADMIN'">Delete</button>) — write once, use everywhere; an appAutoFocus focuses the first field of any form; an appClickOutside closes any dropdown on an outside click.

A component is a directive that happens to have a template. That is not an analogy — in Angular's own type definitions Component extends Directive. So every skill you already have transfers whole: inject(), ngOnInit, input(), outputs, host bindings, DI scoping. A directive is the component you already know, minus the one field that makes markup.

The mechanism

One character of sugar. Five things happen because of it.

  1. you type <button *appHasRole="'ADMIN'">Delete</button>one asterisk — that is the entire sugar
  2. the compiler rewrites it as <ng-template [appHasRole]="'ADMIN'"><button>Delete</button></ng-template>your button now lives inside a template, and templates render nothing
  3. Angular constructs your directive on that ng-template, injecting a TemplateRef (the un-stamped button) and a ViewContainerRef (the comment node marking where it would go)this is why the two-argument constructor is not optional ceremony
  4. your input setter runs — set appHasRole(role)the only line in the chain that is your logic
  5. vcr.createEmbeddedView(tpl) stamps the button into the DOM — or vcr.clear() and the DOM never had itnot display:none. There is no element.

The part everyone re-learns the hard way: TemplateRef and ViewContainerRef are not boilerplate you can skip — they are the two halves of the sugar. Delete the *, write the <ng-template> by hand, and the identical directive still works. That is all the compiler did for you.

Now the host. @HostListener('mouseenter') and host: { '(mouseenter)': 'onEnter()' } compile to the same listener — the difference is where the wiring lives. The decorators scatter it across your methods and hand the compiler a string it can only check at runtime; the host object collects every binding and listener in one place beside the selector, which is why the current Angular style guide points you there for new code. Either way, be very careful which event you listen to: @HostListener('mouseenter') fires when someone hovers one element, while @HostListener('document:mousemove') fires on every pixel of every mouse movement anywhere in the app — once per instance of your directive. Put that directive on the 500 rows of your user-admin table and a single twitch of the mouse calls your handler five hundred times. Same decorator, same two words changed, four orders of magnitude apart.

Your *appHasRole="'USER_ADMIN'" directive removes the Delete button from the DOM for a support agent who lacks the role. She opens DevTools. What is actually stopping the delete?

Right — and this is the one thing to carry out of this page. *appHasRole is UX: it stops an agent being offered a button that would 403 anyway. Removing is genuinely better than hiding (a display:none button is one CSS toggle away from clickable, and screen readers may still announce it), but both live on the attacker's side of the wire. The authorization decision has to happen where she cannot edit the code — @PreAuthorize on the controller.

The button was never the thing that deletes a user — the HTTP call is. Removing the element removes the affordance, not the capability. And she doesn't even need DevTools: the JavaScript bundle you shipped to her browser already contains the URL, the method and the payload shape.

Angular has no idea what your click handler does. There is no re-check: the setter ran once when its input changed and the directive has not thought about the role since.

Questions from the back row

Why is the selector in square brackets?

Because a directive selector is a CSS selector — Angular runs it against your templates at compile time. [appHighlight] is the CSS attribute selector, so it matches any element carrying that attribute. Which means you can be far pickier than most people ever try: button[appConfirm]:not([disabled]) matches only enabled buttons, input[type=password][appStrength] only password fields, and [appHasRole] plus [appHasRoleElse] in one selector demands both attributes. The flip side: a bare button selector would silently attach your directive to every button in the application — which is exactly why the convention is a prefixed attribute.

Attribute or structural — how do I decide?

Ask one question: do I want this element to exist, or to behave differently? Existence is structural (TemplateRef + ViewContainerRef); behaviour is an attribute directive on the host. A useful smell: if an attribute directive of yours is setting [hidden] or style.display, you wanted a structural one — you are leaving the element, its bindings and its child components alive and running just to paint over them.

Can one element carry two structural directives?

No, and the compiler tells you so. Two directives both claiming to be the one that stamps out the template is genuinely ambiguous — who owns the ViewContainerRef? The fix is to give each its own element: <ng-container *appHasRole="'ADMIN'"> wrapping <li *ngFor="let u of users">. ng-container is free — it leaves nothing in the rendered DOM.

1. Directive vs Component — When to Write Each

Rule of thumb: if you need to output HTML, write a component. If you need to change how an existing element behaves or looks, write a directive.

  


  
  
2. Attribute Directive — @HostListener & @HostBinding

  

    
import { Directive, HostListener, HostBinding, Input, ElementRef, Renderer2 }
  from '@angular/core';

@Directive({
  selector: '[appHighlight]',   // ATTRIBUTE selector — no element created, only attaches to a host
  standalone: true
})
export class HighlightDirective {
  // @Input() can be same name as selector — used as both attribute and input
  @Input('appHighlight') highlightColor = 'rgba(221,0,49,0.3)';   // the string in [appHighlight]="..." lands here

  // @HostBinding binds to a property on the host element
  @HostBinding('style.backgroundColor') bgColor = '';   // setting this field SETS the host's inline style
  @HostBinding('class.active') isActive = false;      // same idea, toggles a CSS class instead

  // @HostListener listens to events on the host element
  @HostListener('mouseenter')         // no target = the HOST element this directive is attached to
  onMouseEnter() {
    this.bgColor = this.highlightColor;   // writing this field is what makes the style change appear
    this.isActive = true;
  }

  @HostListener('mouseleave')
  onMouseLeave() {
    this.bgColor = '';            // empty string clears the inline style entirely
    this.isActive = false;
  }

  // Listen to document-level events
  @HostListener('document:keydown.escape')   // the "document:" prefix redirects the listener off the host entirely
  onEscapeKey() {
    this.bgColor = '';
    this.isActive = false;
  }
}

// Usage:
<button appHighlight="rgba(74,222,128,0.3)">Hover me</button>   // custom color via the @Input alias
<p appHighlight>Default red highlight</p>                        // bare attribute — falls back to the field's default value

    
Nothing in this class ever calls document.querySelector or
    touches the DOM directly — @HostBinding and @HostListener are a
    two-way contract with the element the directive is attached to: write a bound field, Angular
    updates the DOM; a bound event fires, Angular calls your method. The directive never needs to
    know WHICH element it's on.


    
ElementRef vs Renderer2

    

      

        
Avoid writes ElementRef

        
// Reading is fine:
const el = inject(ElementRef);
const width = el.nativeElement.offsetWidth;   // read-only queries never touch a server-rendered page

// Writing directly — AVOID
// Breaks SSR, XSS risk:
el.nativeElement.style.color = 'red'; // bad

      

      

        
Preferred Renderer2

        
const renderer = inject(Renderer2);   // the abstraction layer between your code and the real DOM
const el = inject(ElementRef);       // still need this — it names WHICH element to change

renderer.setStyle(el.nativeElement, 'color', 'red');   // same effect as the "bad" line above, platform-safe
renderer.addClass(el.nativeElement, 'active');
renderer.setAttribute(el.nativeElement, 'aria-label', '...');
renderer.createElement('div');          // even NEW elements go through Renderer2, never document.createElement

      

    

    
Every renderer.* call mirrors a native DOM API 1:1
    (setStyle ≈ .style.x =, createElement ≈
    document.createElement) — the only difference is Renderer2 can also target a
    non-browser platform (server-side rendering, a web worker), where el.nativeElement
    might not even be a real DOM node.

3. Structural Directives — *appIf & *appFor Clones

  

    

      The * prefix is syntactic sugar. *appIf="condition" desugars to <ng-template [appIf]="condition">. Your directive receives a TemplateRef and a ViewContainerRef.
    


    
Custom *appIf — Step by Step

    
import { Directive, Input, TemplateRef, ViewContainerRef } from '@angular/core';

@Directive({
  selector: '[appIf]',          // matches the desugared [appIf] binding, not a *appIf string
  standalone: true
})
export class AppIfDirective {
  private hasView = false;    // tracks state so re-running with the SAME condition is a no-op

  constructor(
    private readonly templateRef: TemplateRef<any>,    // the <ng-template> content — a recipe, not rendered yet
    private readonly viewContainer: ViewContainerRef   // WHERE in the DOM stamped views get inserted
  ) {}

  @Input() set appIf(condition: boolean) {   // a SETTER — runs every time the bound expression changes
    if (condition && !this.hasView) {
      this.viewContainer.createEmbeddedView(this.templateRef);   // stamps the template into the DOM, right here
      this.hasView = true;
    } else if (!condition && this.hasView) {
      this.viewContainer.clear();    // removes the view entirely — not hidden with CSS, actually destroyed
      this.hasView = false;
    }
  }
}

// Usage: <div *appIf="showPanel">...</div>
// Desugars to: <ng-template [appIf]="showPanel"><div>...</div></ng-template>

    
The * prefix from the intro above is now concrete: the
    template compiler rewrites *appIf="x" into the <ng-template
    [appIf]="x"> form shown on the last line, which is why the directive's constructor gets
    a TemplateRef at all — there was never a real <div> to attach to,
    only a template describing one.


    
Custom *appFor with Context Variables

    
@Directive({
  selector: '[appFor][appForOf]',   // TWO selectors, both required — appFor from *appFor, appForOf from "of items"
  standalone: true
})
export class AppForDirective<T> {   // generic — works with an array of any type, fully typed
  constructor(
    private readonly templateRef: TemplateRef<any>,
    private readonly viewContainer: ViewContainerRef
  ) {}

  @Input() set appForOf(items: T[]) {   // re-runs the WHOLE render whenever the array reference changes
    this.viewContainer.clear();     // unlike *appIf, this one throws everything away and rebuilds every time
    items.forEach((item, index) => {
      this.viewContainer.createEmbeddedView(this.templateRef, {   // second arg is the CONTEXT object for this one row
        // $implicit = value of `let item of items`
        $implicit: item,
        index: index,
        first: index === 0,
        last: index === items.length - 1,
        even: index % 2 === 0,
        odd: index % 2 !== 0
      });
    });
  }
}

// Usage:
<li *appFor="let user of users; let i=index; let last=last">
  {{i+1}}. {{user.name}} {{last ? '(last)' : ''}}
</li>

    
Every let x=y in the usage comment is a key from the context
    object above — let i=index binds to the index key,
    let last=last to the last key. This is the SAME
    ngTemplateOutletContext mechanism content projection's ngTemplateOutlet
    used, just driven by a structural directive instead of an explicit outlet.

4. Directive Composition API (Angular 15+)

  

    

      hostDirectives in the @Directive or @Component decorator lets you compose multiple directives on a single element without the user having to apply them manually.
    


    
import { CdkDrag, CdkDragHandle } from '@angular/cdk/drag-drop';   // third-party directives — never modified, just composed
import { Focusable } from './focusable.directive';

// A "DraggableCard" component that bundles 3 behaviors
@Component({
  selector: 'app-draggable-card',
  standalone: true,
  hostDirectives: [        // each entry is applied to THIS component's own host element
    // Apply CdkDrag — expose some inputs/outputs to consumers
    {
      directive: CdkDrag,
      inputs: ['cdkDragData'],           // expose as input
      outputs: ['cdkDragEnded: dragEnded'] // expose/rename output
    },
    CdkDragHandle,  // applied as-is, no exposed inputs
    Focusable
  ],
  template: `<ng-content />`
})
export class DraggableCardComponent {}   // no logic of its own — this class exists to BUNDLE the three directives

// Usage — CdkDrag behavior comes for free:
<app-draggable-card [cdkDragData]="item" (dragEnded)="onDrop($event)">   // looks like plain component I/O, resolves to CdkDrag underneath
  Card content here
</app-draggable-card>

    
The consumer at the bottom never writes cdkDrag,
    cdkDragHandle, or imports anything from @angular/cdk — the
    inputs:/outputs: renames in hostDirectives are the ONLY
    thing standing between "three directives applied manually" and "one component that just works."


    

      

        
Benefits

        
    
          
  • Encapsulate behavior bundles in reusable directives
    • 
          
  • Users don't need to know which CDK directives are being used
    • 
          
  • Selectively expose/rename inputs and outputs
    • 
          
  • Works with both components and directives
    • 
        

      

      

        
Constraints

        
    
          
  • Host directives run before the host component
    • 
          
  • Cannot host-compose standalone: false directives
    • 
          
  • Host directives share the same DI context
    • 
          
  • Only explicitly listed inputs/outputs are forwarded
    • 
        

      

    


    
Building a Reusable Tooltip Directive via Composition

    
// tooltip.directive.ts — standalone, composed from smaller pieces
@Directive({          // hostDirectives works on @Directive too, not just @Component
  selector: '[appTooltip]',
  standalone: true,
  hostDirectives: [
    { directive: HoverDirective, outputs: ['hovered'] },   // small, single-purpose directives —
    { directive: FocusDirective, outputs: ['focused'] }    // each does ONE thing, composed here into a bigger behavior
  ]
})
export class TooltipDirective {
  @Input() appTooltip = '';
  // HoverDirective and FocusDirective are applied automatically
  // This directive just handles rendering the tooltip overlay
}

    
This is the composition pattern in miniature: instead of one directive
    that knows about hovering AND focus AND rendering, three small directives each own one concern,
    and hostDirectives is the glue — no inheritance, no mixins, just a declarative list.

  


  
  
5. Input Signals on Directives (Angular 17.1+)

  

    

      

        
Old: @Input() decorator

        
@Directive({ selector: '[appBadge]', standalone: true })
export class BadgeDirective {
  @Input() appBadge = '';      // a plain field — reading it never tells Angular WHEN it changed
  @Input() badgeColor = 'red';

  // Can't use in template without ngOnChanges
}

      

      

        
New: input() signal function

        
import { input } from '@angular/core';

@Directive({ selector: '[appBadge]', standalone: true })
export class BadgeDirective {
  appBadge = input<string>('');   // no @Input decorator — the function IS the declaration
  badgeColor = input('red');          // type is inferred from the default value here

  // Full signal reactivity — use in computed(),
  // effect(), or template directly
  label = computed(() =>          // re-runs automatically whenever appBadge() changes
    this.appBadge().toUpperCase()   // CALL it like a function to read the current value
  );
}

      

    

    
The property name is identical on both sides
    (appBadge) — what changed is that it went from a plain field you can only READ to a
    signal-returning FUNCTION you call, which is exactly what lets computed() track it
    and re-run only when it actually changes.
