Images & Containers

Images are blueprints. Containers are running instances. Understand layers, the container lifecycle, and the essential commands.

What is the difference between a Docker image and a container — and how does the container lifecycle work?

The most fundamental Docker concept: image vs container. An image is a read-only, immutable template — a stack of filesystem layers. Think of it as a Java class definition, or an OOP blueprint. The image never changes. A container is a running instance of an image — Docker creates a writable layer on top of the image's read-only layers. The container can write files (logs, temp files) to its writable layer. Those writes disappear when the container is deleted. Like a Java object instantiated from a class — the class (image) is unchanged, the object (container) has its own state. Image layers: Docker images are made of layers — each Dockerfile instruction that modifies the filesystem creates a new layer. Layers are content-addressed (SHA256) and shared: if two images share the same base layer (e.g., both use eclipse-temurin:21-jre-alpine), that layer is stored ONCE on disk. This is why your second docker pull is instant — the layer already exists. Container lifecycle: Created → Running → Paused → Stopped → Removed. docker create: allocates the writable layer, doesn't start process. docker start: runs the ENTRYPOINT/CMD. docker stop: sends SIGTERM, waits, then SIGKILL (graceful shutdown). docker kill: sends SIGKILL immediately. docker rm: removes the container and its writable layer (image unchanged). Port mapping: -p 8080:8080 means host-port:container-port. The container process listens on container-port 8080; Docker forwards external traffic from host-port 8080 into it. Volume vs bind mount: -v /host/path:/container/path (bind mount — maps host directory into container) vs -v myvolume:/data (named volume — Docker manages storage location). Use volumes for persistent data (DB data dir), bind mounts for development (hot-reload of source).

Essential commands

# Build image from Dockerfile: docker build -t myapp:1.0 . # Pull from registry: docker pull eclipse-temurin:21-jre-alpine # Run (create + start): docker run -d \ # detached mode -p 8080:8080 \ # port mapping -e SPRING_PROFILES_ACTIVE=prod \ --name ciam-auth \ # named container myregistry/ciam:1.0 # Execute command in running container: docker exec -it ciam-auth sh docker exec ciam-auth env # see env vars # Logs: docker logs ciam-auth -f # follow docker logs ciam-auth --tail 100 # Inspect: docker inspect ciam-auth # full JSON config docker stats # CPU/memory live

Layers + writable layer

# Image = read-only layers (stack): # [Layer 4] ENTRYPOINT java -jar app.jar # [Layer 3] COPY app.jar /app/app.jar ← your code # [Layer 2] WORKDIR /app # [Layer 1] FROM eclipse-temurin:21-jre ← shared base # Container = image layers + writable layer: # [Writable] /tmp/spring.log, /tmp/cache ← container-specific # [Layer 3] app.jar (read-only copy) # [Layer 2-1] (shared with all containers) # Copy-on-write: when container writes to # /app/config.yaml (from layer 3), Docker # copies it to writable layer first. # Layer 3 (image) is UNCHANGED. # docker rm removes writable layer: docker rm ciam-auth # writable layer gone # Image still exists — run again: docker run myregistry/ciam:1.0 # fresh container

Volumes for persistence

# Named volume (Docker manages storage): docker volume create pg-data docker run -d \ -v pg-data:/var/lib/postgresql/data \ postgres:16 # /var/lib/postgresql/data persists # between container restarts/recreations # Bind mount (host dir in container): docker run -d \ -v $(pwd)/src:/app/src:ro \ myapp:dev # :ro = read-only in container # Useful for live reload in dev # List volumes: docker volume ls # View volume data: docker run --rm -v pg-data:/data \ alpine ls /data # inspect volume contents # Remove unused volumes: docker volume prune # reclaim disk space

CIAM container management: Your daily Docker workflow: docker logs ciam-auth -f (follow logs while testing), docker exec -it ciam-auth sh (shell in to check env vars, test curl to Ping), docker stats (monitor memory — JVM footprint in container). Container best practices for Spring Boot: run as non-root user (USER 1000 in Dockerfile), set JVM container memory flags (-XX:MaxRAMPercentage=75), set -XX:+ExitOnOutOfMemoryError so the JVM exits (instead of hanging) when OOM happens — Docker/K8s then restarts it. Image tag strategy: never use :latest in production — use :$(git rev-parse --short HEAD) or :$(Build.BuildId) so you always know exactly which commit is running. docker inspect ciam-auth | jq '.[0].Config.Env' — verify that secrets are coming through as env vars (sanitize output before sharing!).

1 — A Docker Image is a Stack of Read-Only Layers

Each instruction in a Dockerfile creates a layer. Layers are cached and shared across images. Click any layer:

Container Layer
your running container writes here
READ-WRITE
Thin writable layer — created fresh when a container starts. Anything your app writes (log files, temp data) goes here.

Ephemeral: destroyed when the container is removed. Use volumes or bind mounts to persist data across restarts.
COPY . /app
your application code
READ-ONLY
Copies your compiled JAR (or source) into the image. This layer changes every build — place it as late as possible so earlier layers can be cached.
RUN mvn package
build output
READ-ONLY
Results of running a build command. In Spring Boot, you'd typically build the JAR outside Docker (in CI) and just COPY the built artifact — avoids downloading Maven dependencies every build.
COPY pom.xml + deps
maven dependencies
READ-ONLY
Dependencies layer — only re-downloaded when pom.xml changes. Cache invalidation works top-down: if this layer hits cache, everything below also hits cache → fast builds.
FROM eclipse-temurin:21-jre
base OS + JRE (~200 MB)
READ-ONLY
The base image. Pulled once from Docker Hub and cached locally. eclipse-temurin is the community successor to AdoptOpenJDK — the standard JDK/JRE image for production Spring Boot containers.

Use -jre (not -jdk) in production — the JDK is larger and includes development tools you don't need at runtime.
Key caching rule: Docker processes layers top-to-bottom. The first changed layer invalidates all layers below it.

Optimal order:
1. Base image (never changes)
2. Dependencies (change rarely)
3. App code (changes often)

This way, most builds only rebuild the app-code layer — the heavy deps layer stays cached.

3 — Essential docker Commands

Images

$ docker build -t myapp:1.0 . Build image tagged myapp:1.0 $ docker images REPOSITORY TAG IMAGE ID SIZE myapp 1.0 a1b2c3d4e5f6 280MB $ docker pull eclipse-temurin:21-jre Download image from Docker Hub $ docker push myrepo/myapp:1.0 Push to a registry $ docker rmi myapp:1.0 Remove image (must stop containers first) $ docker image prune Remove all dangling (untagged) images

Containers

$ docker run -d -p 8080:8080 myapp:1.0 -d: detached (background) -p host:container port mapping $ docker ps CONTAINER ID IMAGE STATUS PORTS f1e2d3c4b5a6 myapp:1.0 Up 2m 0.0.0.0:8080->8080/tcp $ docker logs -f f1e2d3c4b5a6 Stream container logs (-f = follow) $ docker exec -it f1e2 /bin/sh Open interactive shell inside container $ docker stop f1e2 && docker rm f1e2 Stop then remove container $ docker run --rm myapp:1.0 --rm: auto-remove when stopped

4 — Volumes: Persisting Data

Container writable layers are ephemeral — removed with docker rm. Use volumes for data that must survive:

Named Volume (preferred for DBs)

# Docker manages the storage location docker run -d \ -v pgdata:/var/lib/postgresql/data \ postgres:16 # pgdata persists across container restarts # and docker rm (unless volume is deleted) docker volume ls docker volume rm pgdata

Bind Mount (dev: live code reload)

# Maps a host directory into the container docker run -d \ -v /home/user/app:/workspace \ myapp:dev # Changes on host are immediately visible # inside the container — useful for dev # hot-reload workflows
