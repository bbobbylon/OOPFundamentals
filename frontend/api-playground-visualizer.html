API Playground

A real HTTP client, right here in the page. Every Send fires an actual fetch() from your browser — no mocks. Build a request, fire it, and read the live status, timing, headers, and body. It's a pocket Postman that also explains what just happened: cross-origin or same-origin, whether a CORS preflight fired, and why a request sometimes fails before it ever reaches the server.

⚡ Works two ways: open it standalone or in the hub to call public APIs, or run the hub locally (http://localhost) to call the DevHub Spring backend on :8081 and watch a real login round-trip. On the deployed HTTPS site, http://localhost calls are blocked as mixed content — that's expected, and the playground will tell you so.

2 — Reading the status code

The first digit is the whole story. The colour of the big number above matches this table.

2xx
Success. 200 OK, 201 Created, 204 No Content.
3xx
Redirect. 301/302 moved, 304 Not Modified (cached).
4xx
You. 400 bad request, 401 unauthenticated, 403 forbidden, 404 not found, 429 rate-limited.
5xx
Them. 500 server error, 502/503 upstream down. Retrying may help.

401 vs 403 is the classic mix-up — 401 = "I don't know who you are" (fix the token), 403 = "I know you, but no" (fix permissions). Walk it in Auth: 401 vs 403.

3 — Why a request fails before it returns

CORS — the browser blocks it

A cross-origin call is allowed to leave, but the browser hides the response unless the server sends Access-Control-Allow-Origin. The fetch then throws a TypeError: Failed to fetch — not a 4xx/5xx, because no readable response ever arrived. Hit the “CORS error” preset above to make it happen on purpose, then see CORS Failures.

Mixed content — HTTPS → HTTP

A page served over https:// may not call http:// URLs — the browser blocks it outright. That's why the localhost:8081 presets only work when you run the hub locally over http. Same symptom (failed fetch), different cause — the explainer panel tells the two apart.

A readable error with a status number means your request reached the server. A thrown Failed to fetch with no status means it didn't — that's a browser-side gate (CORS, mixed content, DNS, offline), and the network tab won't show a normal response.

4 — Call your own backend

Run the hub locally (http://localhost:5500/app) with the Spring backend up on :8081, then use the local presets to run the real auth round-trip:

  1. GET /actuator/health → {"status":"UP"} (no auth — proves it's reachable).
  2. POST /api/auth/register or /login → copy the token from the body.
  3. Paste it into the Bearer box, then GET /api/progress → your data. Remove the token → 401.

That's the exact chain the hero pages animate, run for real against a live Spring resource server. The token is a real JWT — drop it into JWTs: decode & diagnose to inspect its claims.

5 — Recap

🧪 This is a real HTTP client: every Send is a live fetch(), and the response — status, timing, headers, body — is the actual one. The status code's first digit says who's responsible (4xx you, 5xx them); a thrown Failed to fetch with no status means the browser blocked it before the server could answer (CORS or mixed content). Add a Bearer token to authenticate, point it at the local DevHub backend, and you've run the whole CIAM round-trip by hand.
