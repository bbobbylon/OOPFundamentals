Reading the status code

The first digit is the whole story. The colour of the big number above matches this table.

2xx
Success. 200 OK · 201 Created · 204 No Content (empty body).
3xx
Redirect. 301/302 moved · 304 Not Modified (client cache hit).
4xx
You. 400 bad body · 401 no/bad token · 403 lacks permission · 404 not found · 429 rate-limited.
5xx
Them. 500 server error · 502/503 upstream down. Retrying may help.

401 vs 403 is the classic mix-up — 401 = "I don't know who you are" (fix the token), 403 = "I know you, but no" (fix the scope or role). Walk the full chain in Auth: 401 vs 403.

Why a request fails before it returns

CORS — the browser blocks it

A cross-origin call is allowed to leave your browser, but the browser hides the response unless the server returns Access-Control-Allow-Origin. The fetch throws a TypeError: Failed to fetch — not a 4xx/5xx. No readable status arrived. Hit the "CORS error" preset to trigger it on purpose.

Mixed content — HTTPS → HTTP

A page on https:// may not call http:// URLs — the browser blocks it before the request leaves. Same symptom as CORS (thrown error, no status), different cause. The explainer panel distinguishes the two automatically.

A readable error with a status number means the request reached the server. A thrown Failed to fetch with no status means the browser stopped it — CORS, mixed content, DNS failure, or host offline.

JWT inspector — how to use it

Paste any JWT into Auth → Bearer

The inspector decodes it instantly without any network call. It shows the algorithm (HS256, RS256…), all standard claims (iss, sub, aud, scope, roles), and a live expiry countdown — green while valid, red when expired. Non-standard claims appear at the bottom.

Security note: the inspector only base64-decodes the header and payload. It does not verify the signature. Always verify signatures server-side.

Sending authenticated requests

While a token is in the Bearer box, every request automatically adds Authorization: Bearer <token>. To test 401: send to a protected endpoint, then clear the token and send again. To test 403: use a token whose roles/scope claim lacks the required value.

Get a live JWT from the local login preset, drop it in Bearer, then hit local /api/progress to run the real auth round-trip against the DevHub Spring backend.

The diff view

After two or more requests, the Diff tab compares the current response body to the previous one. For JSON: it does a key-level semantic comparison — green = added key, red = removed key, yellow = changed value. For plain text: it does a line-level diff. Use it to verify that a PATCH actually changed what you expected, or to see exactly which fields differ between two API versions.

Call your own backend

Run the hub locally (http://localhost:5500/app) with the Spring backend up on :8081, then use the local presets:

  1. GET /actuator/health → {"status":"UP"} — proves the backend is reachable (no auth needed).
  2. POST /api/auth/login → copy the token field from the JSON response body.
  3. Switch to the Auth tab, paste the token → watch it decode. Every claim is shown.
  4. Send GET /api/progress — you're in. Clear the token → instant 401.

That's the exact chain the hero pages animate — run for real. Drop the token into JWTs: decode & diagnose for the full Spring-side validation walk.
