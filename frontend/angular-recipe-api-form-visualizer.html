Recipe — Fetch an API & Drive a Reactive Form

The single most common screen you build: load a record from an API, bind it into an editable form, validate as the user types, then submit the changes back — and handle the server's response. Done the Angular way with HttpClient + Reactive Forms.

🅰️ The pattern: GET → patch the form → validate → PUT

An "edit" screen is a four-step round trip, and Angular gives you a clean tool for each step. (1) Load: in ngOnInit you call http.get<User>('/api/users/42'), which returns an Observable you subscribe to (or read via the async pipe). (2) Bind: you create a FormGroup with a FormControl per field, then call form.patchValue(user) to drop the fetched data into the controls — the template's [formGroup] + formControlName bindings make the inputs show it instantly. (3) Validate: each control carries validators (Validators.required, Validators.email, custom ones); as the user types, the control's valid/errors/touched state updates reactively, so you can show messages and disable the submit button with [disabled]="form.invalid". (4) Submit: on submit you take form.value (a plain object), send it with http.put('/api/users/42', form.value), and handle the result — on success show a confirmation, and on a server error (say a 409 because the email is taken) map that error back onto the specific control with form.get('email').setErrors({taken:true}). The whole flow is reactive and unidirectional: data flows API → form → template, and edits flow template → form → API. No manual DOM reading, no document.getElementById — the FormGroup is the single source of truth.

  • Load — http.get<User>(url) returns an Observable; subscribe in ngOnInit.
  • Bind — build a FormGroup, then form.patchValue(user); template uses formControlName.
  • Validate — validators set each control's valid/errors/touched; gate submit on form.invalid.
  • Submit — http.put(url, form.value); map a server 4xx back onto a control via setErrors.

The component

form = this.fb.group({ name: ['', Validators.required], email: ['', [Validators.required, Validators.email]] }); ngOnInit() { this.http.get<User>(url) .subscribe(u => this.form.patchValue(u)); }

The template

<form [formGroup]="form" (ngSubmit)="save()"> <input formControlName="email"> @if (email.touched && email.invalid) { <small>Enter a valid email</small> } <button [disabled]="form.invalid"> Save</button> </form>

The server side

The form talks to a REST endpoint — e.g. a Spring @GetMapping("/users/{id}") returning the DTO and a @PutMapping taking @Valid @RequestBody UserDTO. Server validation (@Email, a unique-email check) is the real gate; the Angular validators are UX. A 409/400 from the server gets mapped back onto the matching control. See spring-boot-validation + spring-boot-rest-api.

In your CIAM app: this is the profile-edit and registration screen. Pre-fill the form from /api/profile, let the user edit, and PUT it back — mapping server-side rules (email already registered, weak password, claim constraints) onto the form so the message lands on the right field. Never trust the client validators alone: they are there so the user gets instant feedback, but the Spring @Valid layer (and the IdP) is what actually enforces the rules. Pair this with the angular-auth-forms-deep (login/registration forms) and the password-complexity recipe.

1. Build the form & load the data

export class ProfileComponent implements OnInit {
  form = this.fb.group({
    name: ['', Validators.required],
    email: ['', [Validators.required, Validators.email]],
  });
  constructor(private fb: FormBuilder, private http: HttpClient) {}

  ngOnInit() {
    this.http.get<User>('/api/users/42') // Observable<User>
      .subscribe(user => this.form.patchValue(user)); // drop data into the controls
  }
}
The FormGroup is the single source of truth. You declare the shape and rules once with FormBuilder, then patchValue fills it from the API response — patchValue (vs setValue) is forgiving of missing/extra keys, so a DTO with a few unrelated fields won't throw. Because get returns an Observable, the fetch is async and cancellable; subscribing in ngOnInit kicks it off when the component mounts. The template never reads the DOM — it binds to the form.

2. Bind & validate in the template

<form [formGroup]="form" (ngSubmit)="save()">
  <input formControlName="email" type="email">
  @if (form.controls.email.touched && form.controls.email.invalid) {
    <small class="err">Enter a valid email</small>
  }
  <button type="submit" [disabled]="form.invalid">Save</button>
</form>
Validation state is reactive and per-control. formControlName="email" wires the input to the control both ways. Each control exposes valid, invalid, errors (e.g. {email:true}), touched, and dirty — update as the user types. Showing the error only when touched && invalid avoids yelling at the user before they've interacted. Binding [disabled]="form.invalid" means the submit button can't fire until every validator passes — the first line of defense (UX), not the last (the server).

3. Submit & map server errors back to fields

save() {
  if (this.form.invalid) return; // guard: never submit invalid
  this.http.put('/api/users/42', this.form.value) // form.value = { name, email }
    .subscribe({
      next: () => this.saved = true,
      error: (e: HttpErrorResponse) => {
        if (e.status === 409) // email already taken
          this.form.get('email')!.setErrors({ taken: true });
      },
    });
}
The server has the final say — feed its verdict back into the form. form.value serializes straight to JSON for the PUT body. The subscribe object splits next (success) from error. When the API rejects with a 409 (unique-email violation it alone can check), you push that onto the exact control with setErrors({taken:true}) so your template shows the message under the email field — the user sees a precise, local error instead of a generic toast. Client validators are courtesy; the server's response is truth.
