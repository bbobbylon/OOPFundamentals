pom.xml

pom.xml Anatomy

The Project Object Model — Maven's build descriptor. One file defines your project's identity, dependencies, build lifecycle, and plugins. Spring Boot projects extend a parent POM that pre-configures almost everything.

<!-- pom.xml — Spring Boot 3.x + Java 21 -->
<project xmlns="http://maven.apache.org/POM/4.0.0">
  <modelVersion>4.0.0</modelVersion>

  <!-- ── Parent POM: inherits Spring Boot's dependency management ──── -->
  <parent>
    <groupId>org.springframework.boot</groupId>
    <artifactId>spring-boot-starter-parent</artifactId>
    <version>3.2.5</version>
    <relativePath/> <!-- always look in Maven Central -->
  </parent>

  <!-- ── Project coordinates (GAV) ──────────────────────────────────── -->
  <groupId>com.example</groupId>
  <artifactId>my-api</artifactId>
  <version>0.1.0-SNAPSHOT</version>
  <packaging>jar</packaging> <!-- jar | war | pom -->

  <!-- ── Properties ─────────────────────────────────────────────────── -->
  <properties>
    <java.version>21</java.version>     <!-- read by spring-boot-starter-parent -->
    <mapstruct.version>1.5.5.Final</mapstruct.version>
  </properties>

  <!-- ── Dependencies ───────────────────────────────────────────────── -->
  <dependencies>

    <!-- compile scope (default) -->
    <dependency>
      <groupId>org.springframework.boot</groupId>
      <artifactId>spring-boot-starter-web</artifactId>
      <!-- no <version> needed — parent BOM manages it -->
    </dependency>

    <dependency>
      <groupId>org.springframework.boot</groupId>
      <artifactId>spring-boot-starter-data-jpa</artifactId>
    </dependency>

    <!-- runtime scope -- needed at runtime, not compile time -->
    <dependency>
      <groupId>org.postgresql</groupId>
      <artifactId>postgresql</artifactId>
      <scope>runtime</scope>
    </dependency>

    <!-- test scope -- only on test classpath -->
    <dependency>
      <groupId>org.springframework.boot</groupId>
      <artifactId>spring-boot-starter-test</artifactId>
      <scope>test</scope>
    </dependency>

    <!-- provided scope -- servlet container provides it at runtime -->
    <dependency>
      <groupId>jakarta.servlet</groupId>
      <artifactId>jakarta.servlet-api</artifactId>
      <scope>provided</scope>
    </dependency>

  </dependencies>

  <!-- ── Build ───────────────────────────────────────────────────────── -->
  <build>
    <plugins>
      <plugin>
        <groupId>org.springframework.boot</groupId>
        <artifactId>spring-boot-maven-plugin</artifactId>
        <configuration>
          <excludes>
            <exclude>
              <groupId>org.projectlombok</groupId>
              <artifactId>lombok</artifactId>
            </exclude>
          </excludes>
        </configuration>
      </plugin>
    </plugins>
  </build>

</project>

GAV Coordinates

Every Maven artifact is uniquely identified by three coordinates: GroupId, ArtifactId, Version. Together they form a path in the local Maven repository (~/.m2/repository).

The three parts

com.example : my-api : 1.2.3-SNAPSHOT 
<groupId>com.example</groupId>
<!-- Your org's reverse domain name. Convention: com.company.project -->

<artifactId>my-api</artifactId>
<!-- Unique name of THIS module/jar within the group. Lowercase, hyphens. -->

<version>1.2.3-SNAPSHOT</version>
<!-- -SNAPSHOT means "in development". Released = no SNAPSHOT suffix. -->

Where it lives on disk

~/.m2/repository/
  com/
    example/
      my-api/
        1.2.3-SNAPSHOT/
          my-api-1.2.3-SNAPSHOT.jar
          my-api-1.2.3-SNAPSHOT.pom

Path formula: groupId(. → /) / artifactId / version / artifactId-version.jar

SNAPSHOT vs Release versions

SNAPSHOT (1.2.3-SNAPSHOT)

  • In-development — changes between builds
  • Maven re-downloads on every build (if configured)
  • Never deploy SNAPSHOTs to production
  • Stored in snapshot repository (Nexus/Artifactory)
  • Timestamp-stamped on deploy: 1.2.3-20240601.123456-1.jar

Release (1.2.3)

  • Immutable — once deployed, never overwrite
  • Maven downloads once and caches permanently
  • Stored in release repository
  • Use mvn release:prepare + mvn release:perform
  • Maven Central only accepts releases

packaging — what Maven builds

packagingOutputUse case
jar (default)executable or library .jarSpring Boot apps, libraries
war.war for deployment to servlet containersLegacy Tomcat/WildFly deployment
pomNo binary — just the POM itselfParent/aggregator POMs in multi-module

Common Maven commands

# lifecycle phases (each runs all prior phases)
mvn compile       → compile src/main/java
mvn test          → compile + run src/test/java
mvn package       → test + package into target/my-api-1.0.jar
mvn install       → package + install to ~/.m2/repository
mvn deploy        → install + upload to remote repository
mvn clean         → delete target/ directory
mvn clean package → clean then package (safest)

# Spring Boot specific
mvn spring-boot:run       → run the app without packaging
mvn spring-boot:build-image → build OCI container image

Dependency Scopes

Scope controls two things: which classpath a dependency appears on, and whether it's included in the final packaged artifact.

ScopeCompile classpathTest classpathRuntime classpathPackaged in JAR
compile ✓✓✓✓ (default)
test ✗✓✗✗
runtime ✗✓✓✓
provided ✓✓✗✗
import Special — only for <type>pom</type> in dependencyManagement. Imports a BOM.

compile (default)

<dependency>
  <groupId>org.springframework.boot</groupId>
  <artifactId>spring-boot-starter-web</artifactId>
  <!-- no scope = compile, packaged into your jar -->
</dependency>

test

<dependency>
  <groupId>org.springframework.boot</groupId>
  <artifactId>spring-boot-starter-test</artifactId>
  <scope>test</scope>
  <!-- JUnit 5, Mockito, AssertJ -- only for tests, not in production jar -->
</dependency>

runtime

<dependency>
  <groupId>org.postgresql</groupId>
  <artifactId>postgresql</artifactId>
  <scope>runtime</scope>
  <!-- JDBC driver: no compile-time API, loaded via DataSource at runtime -->
</dependency>

provided

<dependency>
  <groupId>org.projectlombok</groupId>
  <artifactId>lombok</artifactId>
  <optional>true</optional>  <!-- don't inherit to transitive dependents -->
</dependency>
<!-- Lombok is an annotation processor — only needed at compile time.
     Not needed in the final jar. "provided" keeps it off the runtime classpath. -->

Excluding transitive dependencies

<dependency>
  <groupId>org.springframework.boot</groupId>
  <artifactId>spring-boot-starter-web</artifactId>
  <exclusions>
    <exclusion>
      <!-- Replace Tomcat with Jetty: exclude Tomcat first -->
      <groupId>org.springframework.boot</groupId>
      <artifactId>spring-boot-starter-tomcat</artifactId>
    </exclusion>
  </exclusions>
</dependency>
<dependency>
  <groupId>org.springframework.boot</groupId>
  <artifactId>spring-boot-starter-jetty</artifactId>
</dependency>

Parent POM & Bill of Materials

Spring Boot's parent POM is a Bill of Materials (BOM) that pre-configures hundreds of compatible dependency versions so you don't have to manage them manually.

What spring-boot-starter-parent gives you

  • Managed versions — Spring Framework, Jackson, Hibernate, JUnit, etc. All tested to work together.
  • Plugin defaults — maven-compiler-plugin source/target, spring-boot-maven-plugin, maven-surefire-plugin.
  • Resource filtering — @project.version@ in application.properties gets replaced at build time.
  • Encoding — UTF-8 source and resource encoding set globally.
<parent>
  <groupId>org.springframework.boot</groupId>
  <artifactId>spring-boot-starter-parent</artifactId>
  <version>3.2.5</version>
  <relativePath/>  <!-- always fetch from Maven Central (not local) -->
</parent>

Overriding a managed version

<properties>
  <!-- Override a specific version managed by the parent -->
  <jackson-bom.version>2.17.0</jackson-bom.version>
  <hibernate.version>6.4.4.Final</hibernate.version>
</properties>

Using a BOM without parent (when you have your own parent)

<dependencyManagement>
  <dependencies>
    <dependency>
      <groupId>org.springframework.boot</groupId>
      <artifactId>spring-boot-dependencies</artifactId>
      <version>3.2.5</version>
      <type>pom</type>
      <scope>import</scope>   <!-- import scope = pull in BOM's dependencyManagement -->
    </dependency>
  </dependencies>
</dependencyManagement>

With this in place, you can declare Spring Boot starters without version numbers — Maven resolves them from the BOM.

Maven Plugins

Plugins bind to lifecycle phases and do the actual work. The Spring Boot parent pre-configures the most important ones; you only need to configure deviations.

maven-compiler-plugin

<plugin>
  <groupId>org.apache.maven.plugins</groupId>
  <artifactId>maven-compiler-plugin</artifactId>
  <configuration>
    <source>21</source>    <!-- set via java.version property in parent -->
    <target>21</target>
    <annotationProcessorPaths>
      <!-- Lombok annotation processor -->
      <path>
        <groupId>org.projectlombok</groupId>
        <artifactId>lombok</artifactId>
      </path>
      <!-- MapStruct annotation processor -->
      <path>
        <groupId>org.mapstruct</groupId>
        <artifactId>mapstruct-processor</artifactId>
        <version>${mapstruct.version}</version>
      </path>
    </annotationProcessorPaths>
  </configuration>
</plugin>

spring-boot-maven-plugin

<plugin>
  <groupId>org.springframework.boot</groupId>
  <artifactId>spring-boot-maven-plugin</artifactId>
  <configuration>
    <mainClass>com.example.MyApiApplication</mainClass>
    <!-- Build layered jar (better Docker caching) -->
    <layers>
      <enabled>true</enabled>
    </layers>
    <!-- Build OCI image via mvn spring-boot:build-image -->
    <image>
      <name>my-registry/my-api:${project.version}</name>
    </image>
  </configuration>
</plugin>

<!-- Goal: mvn spring-boot:run   → starts the app from source
     Goal: mvn package            → produces target/my-api-1.0.jar (fat jar)
     Goal: mvn spring-boot:build-image → Buildpacks OCI image -->

maven-surefire-plugin (unit tests)

<plugin>
  <groupId>org.apache.maven.plugins</groupId>
  <artifactId>maven-surefire-plugin</artifactId>
  <configuration>
    <!-- Run tests in parallel (Java 21 virtual threads) -->
    <parallel>methods</parallel>
    <threadCount>4</threadCount>
    <!-- Exclude slow integration tests (run with failsafe instead) -->
    <excludes>
      <exclude>**/*IT.java</exclude>
    </excludes>
  </configuration>
</plugin>

Multi-module Projects

Split a monolithic project into several Maven modules — each with its own pom.xml — that Maven builds in dependency order.

Directory structure

my-project/                    ← root module (aggregator)
├── pom.xml                    ← parent POM, packaging=pom
├── my-project-api/            ← shared DTOs / interfaces
│   └── pom.xml
├── my-project-service/        ← business logic
│   └── pom.xml
└── my-project-web/            ← Spring Boot app, depends on service
    └── pom.xml

Root POM (aggregator + parent)

<project>
  <groupId>com.example</groupId>
  <artifactId>my-project</artifactId>
  <version>1.0.0-SNAPSHOT</version>
  <packaging>pom</packaging>   <!-- aggregator: no jar output -->

  <modules>                    <!-- Maven builds these in dependency order -->
    <module>my-project-api</module>
    <module>my-project-service</module>
    <module>my-project-web</module>
  </modules>

  <dependencyManagement>      <!-- centralize versions for all child modules -->
    <dependencies>
      <dependency>
        <groupId>com.example</groupId>
        <artifactId>my-project-api</artifactId>
        <version>${project.version}</version>
      </dependency>
    </dependencies>
  </dependencyManagement>
</project>

Child module POM

<project>
  <parent>
    <groupId>com.example</groupId>
    <artifactId>my-project</artifactId>    <!-- parent = root module -->
    <version>1.0.0-SNAPSHOT</version>
  </parent>

  <!-- inherit groupId and version from parent -->
  <artifactId>my-project-service</artifactId>

  <dependencies>
    <dependency>
      <groupId>com.example</groupId>
      <artifactId>my-project-api</artifactId>
      <!-- no version -- managed by root's dependencyManagement -->
    </dependency>
  </dependencies>
</project>

Building a multi-module project

# Build all modules (from root)
mvn clean install

# Build only one module and its dependencies
mvn install -pl my-project-web -am
# -pl = project list, -am = also make (build dependencies)

# Skip a module
mvn install -pl !my-project-service

# Run tests for one module only
mvn test -pl my-project-service
