Cloud Run & Cloud Functions — Serverless Containers & Functions

Two flavors of "no servers to manage": Cloud Run runs any container behind a request-driven autoscaler with real concurrency per instance, and Cloud Functions (2nd gen) is event-driven glue code that is actually Cloud Run underneath. Both scale to zero and both bill per request/CPU-time, not per idle hour.

🏃 What are Cloud Run and Cloud Functions — and why does "concurrency" separate GCP serverless from Lambda?

Cloud Run takes any container that listens on $PORT and runs it with zero infrastructure to manage: no cluster, no nodes, no Kubernetes YAML. It autoscales on incoming requests, scales to zero when idle (no traffic, no bill), and every deploy creates a new immutable revision — traffic can be split by percentage across revisions, which is the entire canary/blue-green mechanism, no separate load balancer resource required. The detail that actually differentiates it from AWS Lambda: one Cloud Run instance can serve many concurrent requests (default 80, tunable), because a whole container — not one function invocation — is the unit of scaling. Lambda gives one execution environment per in-flight request; Cloud Run gives you a running process that can multiplex, the same way a normal web server does. Cloud Functions (2nd gen) is the event-driven sibling: HTTP, Pub/Sub, Cloud Storage, Firestore, or any Eventarc-routed audit-logged event can invoke a function — and under the hood, 2nd-gen Functions are Cloud Run services with Eventarc wiring in front, not a separate compute product. Both share the same cold-start story: scaling from zero (or adding a new instance under burst) pays container/runtime init, mitigated with a min-instances setting that keeps N instances permanently warm at a standing cost. Invocation is IAM-gated by default (roles/run.invoker); --allow-unauthenticated is the explicit opt-out for public endpoints.

  • Cloud Run — any container, request-driven autoscaling, scale-to-zero, immutable revisions + traffic splitting.
  • Concurrency — one instance serves many requests at once (default 80) — the key difference from Lambda's one-per-instance model.
  • Cloud Functions (2nd gen) — event-driven (HTTP/Pub/Sub/Storage/Eventarc), built on Cloud Run + Eventarc under the hood.
  • Cold starts — container/runtime init on scale from zero; min-instances keeps warm instances at a standing cost.
  • IAM invocation control — roles/run.invoker gates who can call a service; --allow-unauthenticated opts out.

AWS comparison

Cloud Run ≈ AWS Fargate (any container, no cluster to run) crossed with Lambda (scale-to-zero, pay-per-use) — but Lambda has no concurrency-per-instance knob; one invocation = one environment, full stop. Cloud Functions ≈ Lambda's event-trigger model (S3/SQS/EventBridge ≈ Storage/Pub/Sub/Eventarc), except 2nd-gen Functions are literally Cloud Run services, not a distinct runtime.

Azure comparison

Cloud Run ≈ Azure Container Apps — both are "just run a container, we'll scale it" with revision-based traffic splitting. Cloud Functions ≈ Azure Functions — triggers and bindings vs. Eventarc-routed events, same scale-to-zero-with-cold-start tradeoff, same Premium/min-instances fix.

Spring Boot comparison

A Spring Boot app packaged as a container and deployed to Cloud Run needs zero code changes — it is still a normal servlet container handling many requests per JVM, which is exactly what Cloud Run's concurrency model expects. A Pub/Sub-triggered Cloud Function is the rough equivalent of a @RabbitListener/@KafkaListener method, except the "always-on listener process" is replaced by "spin up on message, shut down when idle."

CIAM in production: Cloud Run's default IAM-gated invocation (roles/run.invoker) means a service is private-by-default — the same posture as requiring a valid Bearer token on a Spring resource server, just enforced one layer lower, before your code even runs. For a public-facing API, front it with API Gateway or Cloud Armor and validate an OIDC/JWT token in your own middleware exactly as you would on Angular → Spring; for service-to-service calls (a Cloud Function invoking a private Cloud Run API), attach a service account to the caller and let IAM do the identity check with zero shared secrets.

or, the receipt email that "ran" for six minutes and never sent

The problem

You return the response, then keep working in the background the way you would on any normal server — except Cloud Run just quietly took away almost all of your CPU.

The "respond now, email after" handler that stops emailing

Your handler does the real work, sends the response, then — to keep the response fast — fires off unawaited calls to log an analytics event and send a receipt email: res.send(order); logAnalyticsEvent(order); sendReceiptEmail(order);, both async and deliberately not awaited so the client isn't kept waiting. Locally, and in a load test where traffic never stops, this looks completely fine — the event lands and the email sends, all within a second or two after the response.

In production, on a service that gets occasional, spaced-out traffic, the receipt emails stop arriving. Nothing throws an error. What actually happened: the instant res.send() returns, Cloud Run's default CPU allocation mode treats the request as finished and throttles that instance's CPU down toward zero — because from the platform's point of view, if no request is in flight, the instance has nothing left to compute. Your background email call is still technically alive, but it's getting a sliver of CPU, if any, until the next real request happens to wake the instance back up — which might be seconds, minutes, or never before the instance is recycled.

the response returning correctly and fast ✓ the analytics/email calls succeeding under constant load-test traffic ✓ any work started after the response, on a quiet service ⚠

Cloud Run only guarantees your code CPU time while it's actively serving a request — after that, by default, you're not promised to keep running at all.

Await it, hand it off, or explicitly pay for always-on CPU
Await the background work before responding, if it truly must run ↓ the extra latency is honest cost the client actually experiences, instead of invisible work that might never finish Or hand it off to Cloud Tasks / Pub/Sub and let a follow-up invocation process it ↓ that follow-up invocation is its own real, billed request, so it gets full CPU allocation for its entire duration And if you genuinely need code running between requests — a connection-pool warmer, a background poller — set CPU allocation to "always allocated" and pay the standing cost on purpose
The one-sentence rule. "The response was sent" is not the same event as "the request is over" from your code's point of view, but under Cloud Run's default CPU-allocation setting it is exactly the same event from the platform's point of view — so any work you start after responding is racing a throttle you can't see happen.
Default Cloud Run CPU allocation behaves like a taxi meter that stops the second the passenger gets out. The driver hasn't vanished — but nobody's paying to move the car, so don't expect it to arrive anywhere.

The Cloud Run instance

Your load test kept requests arriving constantly, so I never got a chance to throttle down between them. A quiet production service gives me plenty of idle gaps — exactly when your unattended background code gets starved.

The mechanism

Here's the exact moment the rug gets pulled out from under "fire and forget" code.

  1. A request arrives at a Cloud Run instancerequest start
  2. CPU is fully allocated to the instance for the duration of the requestfull CPU
  3. Your handler calls res.send(order) — the response leaves for the clientresponse sent
  4. By default ("CPU allocated only during requests"), Cloud Run considers the request complete and begins throttling the instance's CPUthe switch flips
  5. Any code still executing — an unawaited promise, a background thread — now competes for a tiny CPU allowancestarved code
  6. If no new request arrives before Cloud Run scales the instance down, that background work is abandoned mid-execution, silentlythe disappearance

Step four is the crux: this isn't a bug, it's a documented, deliberate cost-saving default. Cloud Run allocates (and bills for) CPU around request-processing time, and code that outlives the request is, by definition, outside that window unless you explicitly tell Cloud Run otherwise.

Serving a request request arrives → CPU fully allocated, your handler runs at full native speed
Response already sent res.send() returns → CPU is throttled toward zero, by default
"Background" work still executing your unawaited async call → starved of CPU cycles, it may take minutes or simply freeze mid-task

Read the cycle clockwise: full CPU only exists inside the top state. Anything your code tries to do after crossing into "response already sent" is gambling on how quickly the throttle bites, and whether another request happens to rescue it before that.

A Cloud Run service handles a webhook: it validates the payload, responds 200 OK immediately so the caller doesn't retry, then spends roughly 4 more seconds doing image processing in the background before uploading the result to Cloud Storage. In staging, with constant test traffic, it always finishes. In production, with sporadic real traffic, the processed image is frequently missing. What actually fixes this?

Right — CPU throttling after the response is the real cause, so the fix has to either keep the work inside the request (await it) or make the follow-up work its own real, billed request via Cloud Tasks or Pub/Sub, which gets full CPU allocation for its own duration.

Memory and CPU are configured together on Cloud Run, but a larger memory allocation doesn't change WHEN CPU is throttled — it only changes how much CPU you get while it IS allocated. This never touches the actual cause.

Keeping a connection open doesn't change Cloud Run's CPU allocation policy — throttling is about whether a request is actively being processed, not about the transport protocol. WebSockets bring their own entirely separate considerations on Cloud Run.

Where you have seen this before

"The container is still running" and "the container is still allowed to do work" turning out to be two different promises shows up outside Cloud Run too.

Spring's @Async "send the welcome email" after registration

Fire an @Async method to send a welcome email right after a registration endpoint returns 201 Created, and you're making the identical bet Cloud Run's default CPU mode punishes: that the environment keeps running your code after the response has already left. Spring's own documentation is explicit that @Async tasks run against whichever executor you configure, and that executor's lifecycle — including its behavior on shutdown — is something you own, not something Spring quietly guarantees away for you.

"fire and forget" always means someone else now owns "forget"

AWS Lambda freezing the execution environment after the response

AWS's own Lambda documentation warns that background work started before a handler returns can be frozen mid-flight the instant the response is sent, and may only resume — if it resumes at all — the next time that same execution environment happens to be reused for an unrelated invocation. Same "response sent ≠ work finished" assumption, enforced even more abruptly than Cloud Run's throttle.

the platform reclaims the environment on its own schedule, not yours

A beforeunload analytics call the browser never finishes sending

Fire a plain fetch() to log an analytics event as a user navigates away, and the browser can tear the page down — cancelling the in-flight request — before it completes. This exact failure mode is why navigator.sendBeacon() exists: a purpose-built API for handing a small payload to the browser to deliver after the page that fired it is already gone.

the runtime you were relying on can disappear before your callback does
The whole page on a napkin: Cloud Run and Cloud Functions turn "any container" or "any event handler" into a request/event-driven, autoscaling, scale-to-zero service, with revisions and traffic splitting standing in for a separate load balancer and canary system. The one new sentence this block adds: scaling to zero when idle and throttling CPU between requests are the same underlying mechanism, so any work your code starts after the response leaves is running on borrowed time you never actually asked to borrow.

1. Cloud Run: any container, request-driven autoscaling

# Build (or bring your own image) and deploy — no cluster, no YAML
gcloud run deploy orders-api \
  --source . \
  --region us-central1 \
  --concurrency 80 \
  --min-instances 0 --max-instances 20 \
  --no-allow-unauthenticated

# Grant a service account permission to invoke it
gcloud run services add-iam-policy-binding orders-api \
  --member="serviceAccount:checkout-sa@proj.iam.gserviceaccount.com" \
  --role="roles/run.invoker"
Concurrency is the headline difference from Lambda. --concurrency 80 means one running container instance can serve up to 80 simultaneous requests — a Spring Boot app with a normal thread pool just works. Lambda's model gives one execution environment per in-flight request; Cloud Run gives you a process that multiplexes, so a traffic spike that Lambda would answer by spinning up hundreds of new (possibly cold) environments, Cloud Run can often absorb with the instances it already has warm.

2. Revisions & traffic splitting: the built-in canary mechanism

# Every deploy is a new, immutable revision. Split traffic by percentage:
gcloud run services update-traffic orders-api \
  --to-revisions=orders-api-00042-xyz=90,orders-api-00043-abc=10

# Happy with the canary? Shift to 100% — no new deploy needed
gcloud run services update-traffic orders-api --to-latest
No separate load balancer resource required. Traffic weighting is a built-in ingress feature of Cloud Run itself — revisions are live, independently addressable deploy targets, and shifting the split (or rolling back to 100% on the old revision) is a metadata change, not a redeploy. This is the same shape as Azure Container Apps' revision traffic weights and the canary pattern taught on devops-deployment-strategies-visualizer.html.

3. Cloud Functions (2nd gen): event-driven, built on Cloud Run + Eventarc

# A Pub/Sub-triggered function — deployed like a function, running like a Cloud Run service
gcloud functions deploy resize-thumbnail \
  --gen2 \
  --runtime=java21 \
  --trigger-topic=image-uploads \
  --memory=512Mi \
  --min-instances=0
2nd-gen Functions are Cloud Run underneath. Deploying a function with --gen2 provisions a Cloud Run service plus an Eventarc trigger that routes the Pub/Sub (or Storage, Firestore, or any audit-logged) event to it — the "function" framing is a thinner developer experience layered over the same runtime and scaling engine as scenario 1. That is why min-instances, concurrency, and revision traffic splitting all apply to gen2 Functions too, features 1st-gen Functions never had.
