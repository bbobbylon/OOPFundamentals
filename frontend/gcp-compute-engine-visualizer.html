Compute Engine — VMs, Instance Templates & Managed Instance Groups

Compute Engine is GCP's virtual machine layer: pick a machine type family, define an instance template once, and let a Managed Instance Group turn that template into a fleet that autoscales, self-heals, and rolls out updates without you touching a single VM by hand.

🖥️ What is Compute Engine — and why does the Instance Template + MIG combination matter more than any single VM?

A single Compute Engine instance is a VM — you pick a machine type from a family: E2 (cost-optimized, shared-core up through standard sizes), N2/N2D (balanced general purpose), C2/C2D (compute-optimized, consistent high clock speed), and M-series (memory-optimized, huge RAM). On its own a VM is exactly as manual to operate as any server you've ever SSH'd into — the leverage comes from an Instance Template: an immutable, versioned bundle of machine type, boot disk image, startup script, network tags, and attached service account, which becomes the single source of truth for what "one instance of this app" looks like. A Managed Instance Group (MIG) takes that template and turns it into a fleet: it autoscales on target CPU, load-balancing capacity, or a custom Cloud Monitoring metric; it runs health checks and auto-heals by recreating any instance that fails them; and it performs rolling updates — controlled by max-surge and max-unavailable — to roll a new template version out gradually, with an optional canary phase using a second template. MIGs can be zonal (fast, single failure domain) or regional (spread across zones for HA). For cost, Spot VMs undercut standard pricing by up to 60–91% with no fixed 24-hour cap, at the price of a 30-second termination notice delivered via a shutdown-script hook — ideal for fault-tolerant, checkpointable batch work, never for a stateful primary database. Every instance also talks to a local metadata server (http://metadata.google.internal) that serves both the startup script's parameters and, critically, the attached service account's short-lived OAuth token — the same mechanism the rest of GCP's compute products use for keyless identity.

  • Machine families — E2 (cost), N2/N2D (balanced), C2/C2D (compute), M-series (memory).
  • Instance Template — an immutable, versioned VM config: machine type, image, startup script, tags, service account.
  • Managed Instance Group — autoscaling (CPU/LB/custom metric) + health-check auto-heal + rolling updates from a template.
  • Spot VMs — up to 60–91% cheaper, 30-second termination notice, no fixed max lifetime unlike old preemptible VMs.
  • Metadata server — serves startup-script params and the attached service account's OAuth token; no embedded credentials.

The CLI happy path

# define the template once gcloud compute instance-templates create orders-tpl-v3 \   --machine-type=e2-medium \   --image-family=debian-12 --image-project=debian-cloud \   --service-account=orders-sa@proj.iam.gserviceaccount.com # turn it into a self-managing fleet gcloud compute instance-groups managed create orders-mig \   --template=orders-tpl-v3 --size=3 --zone=us-central1-a

AWS & Azure comparison

Instance Template + MIG ≈ AWS Launch Template + Auto Scaling Group ≈ Azure VMSS (Virtual Machine Scale Set) — the same three-part pattern (template, autoscaler, health-driven replacement) under three different names. Spot VMs ≈ AWS Spot Instances ≈ Azure Spot VMs, all trading a short eviction notice for a steep discount. Machine families map roughly: E2 ≈ AWS T/M-family burstable-to-balanced ≈ Azure B/D-series; C2 ≈ AWS C-family ≈ Azure F-series.

Spring Boot comparison

An Instance Template is conceptually a versioned Docker image plus a deployment spec rolled into one — "this exact JAR, this exact JVM flags, this exact service account" — and a MIG's rolling update with max-surge/max-unavailable is the same mechanics as a Kubernetes Deployment's rolling update, just one layer lower, operating on whole VMs instead of pods.

CIAM in production: The service account attached to an Instance Template is how a fleet of VMs authenticates to the rest of GCP — Cloud SQL, Secret Manager, Pub/Sub — without a single credential ever appearing in the startup script or baked into the image. The metadata server (http://metadata.google.internal/computeMetadata/v1/instance/service-accounts/default/token) hands back a short-lived OAuth token to whatever process asks from inside the VM, the same pattern Cloud Run and GKE use — see gcp-iam-secrets-visualizer.html for the full identity picture.

1. Instance Templates: one immutable, versioned source of truth

# v3 of the template — a new version, not an edit of v2
gcloud compute instance-templates create orders-tpl-v3 \
  --machine-type=e2-medium \
  --image-family=debian-12 --image-project=debian-cloud \
  --metadata-from-file=startup-script=deploy.sh \
  --tags=orders-api \
  --service-account=orders-sa@proj.iam.gserviceaccount.com --scopes=cloud-platform
Templates are immutable by design. You never edit orders-tpl-v3 in place — a config change means creating orders-tpl-v4 and pointing the MIG at it. This is exactly what makes rolling updates and canaries safe: the old template still exists untouched, so rollback is "point the MIG back at v3," not "hope you remember what v2 looked like."

2. Managed Instance Groups: autoscaling, health checks, rolling updates

# autoscale on CPU target
gcloud compute instance-groups managed set-autoscaling orders-mig \
  --zone=us-central1-a --max-num-replicas=10 --min-num-replicas=2 \
  --target-cpu-utilization=0.6

# health-check-driven auto-heal
gcloud compute instance-groups managed update orders-mig \
  --zone=us-central1-a --health-check=orders-health --initial-delay=120
Auto-healing and autoscaling are two independent mechanisms. The autoscaler decides how many instances should exist based on load; auto-healing decides whether an individual instance is still good, based on the health check, and recreates it if not — a healthy-count MIG can still be quietly replacing a sick instance one at a time in the background while the total size stays flat.

3. Spot VMs: steep discount, 30-second notice, no fixed lifetime cap

# provision spot VMs inside a MIG
gcloud compute instance-templates create batch-tpl-spot \
  --machine-type=e2-standard-4 --provisioning-model=SPOT \
  --instance-termination-action=STOP \
  --metadata-from-file=shutdown-script=checkpoint.sh
The shutdown script is your entire warning system. When GCP needs the capacity back, it sends a preemption notice and gives the instance roughly 30 seconds before terminating it — a shutdown script hooked to that signal is the only chance to checkpoint in-flight work. There's no fixed 24-hour cap like the older "preemptible VM" model had; a Spot VM can, in principle, run indefinitely until capacity is reclaimed.
