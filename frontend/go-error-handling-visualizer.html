Go Error Handling

The error interface, fmt.Errorf wrapping, errors.Is / errors.As, sentinel errors, custom error types, and panic/recover — Go error handling from basics to production patterns.

⚠️ What is Go's error handling philosophy — and why multiple return values instead of exceptions?

Go has no exceptions — errors are values returned alongside the result: result, err := doSomething(), and if err != nil the caller decides. This forces every error path to be visible in the code, the opposite of exceptions silently propagating. The error interface is one method (Error() string), so any type can be an error. Wrapping (Go 1.13+) with fmt.Errorf("...: %w", err) builds a causal chain; errors.Is checks for a sentinel (var ErrNotFound = errors.New(...)) anywhere in it, and errors.As unwraps to a custom type. panic/recover exists but is reserved for truly unrecoverable bugs — an HTTP server keeps a recover middleware so one panicking goroutine can't crash it.

  • Errors are returned values — if err != nil, every path explicit and visible.
  • error = one method (Error() string); any type can implement it.
  • %w wraps a chain — errors.Is finds a sentinel, errors.As a custom type.
  • panic/recover for bugs only — not the error channel; guard servers with recover.

Error return + wrapping

var ( ErrUserNotFound = errors.New("user not found") ErrUnauthorized = errors.New("unauthorized") ) func GetUser(ctx context.Context, id int) (*User, error) { row, err := db.QueryRowContext(ctx, "SELECT...", id) if err == sql.ErrNoRows { return nil, fmt.Errorf("GetUser %d: %w", id, ErrUserNotFound) } if err != nil { return nil, fmt.Errorf("GetUser %d: %w", id, err) } user := &User{} if err := row.Scan(&user.ID, &user.Name); err != nil { return nil, fmt.Errorf("scan: %w", err) } return user, nil } // Caller: user, err := GetUser(ctx, 42) if errors.Is(err, ErrUserNotFound) { http.Error(w, "not found", 404) return }

Custom error types + errors.As

// Custom error type with fields type IdpError struct { IDP string Code int Detail string } func (e *IdpError) Error() string { return fmt.Sprintf("[%s] HTTP %d: %s", e.IDP, e.Code, e.Detail) } // Wrapping: func createPingUser(req Req) (*User, error) { if resp.StatusCode == 409 { return nil, fmt.Errorf("create: %w", &IdpError{ IDP: "PING", Code: 409, Detail: "email taken", }) } } // errors.As: unwrap and type-assert var idpErr *IdpError if errors.As(err, &idpErr) { log.Printf("IDP: %s, Code: %d", idpErr.IDP, idpErr.Code) if idpErr.Code == 409 { return http.StatusConflict, "email already exists" } }

Java/Spring comparison

Go error → Java equivalent. err != nil → try { } catch { }. fmt.Errorf("...: %w", err) → throw new ServiceException("...", cause). errors.Is(err, ErrNotFound) → catch (UserNotFoundException e). errors.As(err, &idpErr) → catch (IdpException e) { e.getCode() }. var ErrNotFound = errors.New("...") → class UserNotFoundException extends RuntimeException {}. Spring's @ControllerAdvice → Go middleware that checks error types and writes the appropriate HTTP status. Key difference: Go errors are explicit in every function signature — you see every possible failure mode. Java exceptions can be thrown anywhere without appearing in the method signature (unchecked), making error paths invisible. Both valid approaches — Go trades verbosity for explicitness, Java trades terseness for potential surprise.

CIAM Go service: A handler maps wrapped errors to HTTP status: if errors.As(err, &idpErr) && idpErr.Code == 409 { http.Error(w, "email taken", 409) }, errors.Is(err, ErrUnauthorized) → 403, else log and 500. And a Recovery middleware (defer func() { if err := recover(); err != nil { log.Printf("panic: %v", err); http.Error(w, "internal error", 500) } }()) prevents one panicking request from crashing the server — the Go counterpart of Spring's @ControllerAdvice + a global error filter.

1. The error Interface

// error is a built-in interface
type error interface {
  Error() string
}

// Any type with Error() string satisfies error
result, err := os.Open("data.csv")
if err != nil {
  return nil, err
}
// err == nil → continue
// Create errors
err1 := errors.New("file not found") // simple
err2 := fmt.Errorf("open %s: %w", name, err1) // wrapped

// Propagate without wrapping
return nil, err // original error, no context added
// Propagate WITH context
return nil, fmt.Errorf("loadUser: %w", err) // adds stack context

Add context when propagating errors. "loadUser: open data.csv: no such file" is infinitely more debuggable than "no such file."

2. errors.Is and errors.As

// Sentinel errors: package-level variables
var ErrNotFound = errors.New("not found")

// errors.Is unwraps the chain to find target
err := fmt.Errorf("getUserByID: %w", ErrNotFound)
errors.Is(err, ErrNotFound) // true — unwraps chain
err == ErrNotFound // false — wrapped
// Custom error type
type ValidationError struct {
  Field, Message string
}
func (e *ValidationError) Error() string {
  return e.Field + ": " + e.Message
}

// errors.As finds the first matching type in chain
var ve *ValidationError
if errors.As(err, &ve) {
  fmt.Println(ve.Field) // access struct fields
}
errors.Is vs errors.As: Use errors.Is to check for a specific sentinel error value (e.g., sql.ErrNoRows, your package's ErrNotFound). Use errors.As to extract an error of a specific type (e.g., *ValidationError to read the Field). Both unwrap the error chain automatically.

3. Panic — When to Use

✅ Panic is appropriate for:

  • Programming errors: nil pointer, out-of-bounds index, type assertion without ok
  • Unrecoverable startup: config missing, DB unreachable at init
  • Package init: regexp.MustCompile panics on bad regex pattern — it is a code bug

❌ Do NOT panic for:

  • Expected errors: file not found, network timeout, invalid user input
  • Library code: libraries should never panic (except for programmer errors)
  • Control flow: return errors, not panics, for recoverable situations
