Python: itertools & functools

Lazy, memory-efficient iteration (itertools) and higher-order function tools (functools: reduce, partial, lru_cache, wraps) — the standard library's functional toolkit.

Two stdlib modules that make Python code shorter, lazier, and faster

itertools is a collection of building blocks for working with iterators — objects that produce values one at a time, on demand (lazily). Because they don't materialize a list, they use constant memory and can even be infinite. The toolkit covers three families: infinite generators (count, cycle, repeat), terminating combinators that reshape iterables (chain to concatenate, islice to slice without indexing, zip_longest, accumulate for running totals, groupby to group adjacent equal keys, takewhile/dropwhile), and combinatorics (product, permutations, combinations). functools is the higher-order-function companion. reduce(fn, iterable, init) folds a sequence to a single value. partial(fn, a) pre-binds arguments to make a new, specialized function. lru_cache / cache memoize a function — caching results so repeated calls with the same args are instant (turning exponential recursion into linear). cached_property memoizes a computed attribute. wraps is essential when you write decorators: it copies the wrapped function's name/docstring onto the wrapper so introspection and tooling still work. singledispatch gives you type-based function overloading. Together they push you toward a declarative, composable style: instead of manual loops with accumulator variables, you pipe lazy iterators through combinators and fold with reduce — less code, less memory, and often faster (the itertools internals are C). The one rule to remember: an iterator is consumed once — after you exhaust it, it's empty.

Lazy + infinite

from itertools import count, islice, chain # infinite, but lazy — take only what you need first5 = list(islice(count(1), 5)) # [1,2,3,4,5] # concatenate iterables without building a list for x in chain([1,2], (3,4), {5}): ... # accumulate = running totals list(accumulate([1,2,3,4])) # [1,3,6,10]

functools essentials

from functools import reduce, partial, lru_cache reduce(lambda a,b: a*b, [1,2,3,4], 1) # 24 add5 = partial(lambda x,y: x+y, 5) add5(10) # 15 @lru_cache(maxsize=None) def fib(n): return n if n<2 else fib(n-1)+fib(n-2) # exponential → linear (memoized)

vs Java Streams / JS

Java: Stream (lazy, map/filter/reduce, collect) ≈ itertools + comprehensions; @Cacheable ≈ lru_cache. JS: generators + lodash; no built-in lazy infinite combinators as rich as itertools. Python's edge: the itertools combinators are C-fast and compose with generator expressions, and functools.reduce/partial/lru_cache are one import away.

In a CIAM context: islice paginates a stream of audit events without loading them all into memory; groupby groups a sorted permission list by resource; lru_cache memoizes an expensive JWKS-key or role lookup so a burst of token validations hits the cache; partial pre-binds a config or tenant id to a handler; and functools.wraps is mandatory when you write an auth decorator (@require_role('ADMIN')) so the wrapped view keeps its name for routing and docs.

1. itertools — Lazy Combinators

ToolDoes
count(start) · cycle(it) · repeat(x)infinite generators (pair with islice to bound)
islice(it, stop)slice an iterator without indexing — paginate a stream
chain(a, b, …)concatenate iterables lazily (no intermediate list)
accumulate(it[, fn])running totals / scans
groupby(it, key)group adjacent equal keys — sort first!
product / permutations / combinationscombinatorics without nested loops
groupby groups only consecutive equal keys. Unlike SQL GROUP BY, it won't gather non-adjacent items — so you almost always sorted(data, key=...) by the same key first. Forgetting this is the #1 itertools bug.

2. functools.reduce — Fold a Sequence

from functools import reduce
import operator

reduce(operator.mul, [1, 2, 3, 4], 1) # 24
reduce(lambda acc, x: acc | x, perms, set()) # union

# often a comprehension / sum()/any() reads better:
sum([1, 2, 3, 4]) # prefer built-ins when they exist

reduce(fn, iterable, initial) applies fn(acc, item) left-to-right, threading the accumulator — the classic fold. Provide the initial value (it's also the result for an empty iterable, avoiding an error). The operator module (operator.mul, add, or_) gives picklable, fast function objects instead of lambdas. Prefer a built-in when one fits (sum, max, any, "".join) — they're clearer than a reduce.

Guido moved reduce out of builtins into functools on purpose — for many cases an explicit loop or a comprehension is more readable. Reach for reduce when the fold is genuinely the clearest expression (a running combine with no built-in), not reflexively.

3. functools.partial — Specialize a Function

from functools import partial

def connect(host, port, timeout): ...

# pre-bind the stable args → a simpler callable
connect_db = partial(connect, "db.internal", 5432)
connect_db(timeout=3) # connect("db.internal", 5432, timeout=3)

partial(fn, *args, **kwargs) returns a new callable with some arguments already filled in — a clean way to adapt a general function to a specific use (a callback that needs fewer params, a handler pre-bound to a tenant/config). It's lighter and more introspectable than a wrapping lambda, and the bound function is picklable (works across multiprocessing).

partial binds positionally from the left. To pin a later parameter, bind it by keyword (partial(fn, timeout=3)). It's the functional-programming "currying" you'll see in event handlers, CLI command tables, and dependency wiring.

4. Caching & Decorator Helpers

from functools import lru_cache, cache, wraps

@cache # == lru_cache(maxsize=None) (3.9+)
def jwks_key(kid): ... # fetched once per kid

# wraps: preserve identity when writing a decorator
def require_role(role):
  def deco(fn):
    @wraps(fn)
    def inner(*a, **k): ...
    return inner
  return deco

lru_cache(maxsize=N) / cache memoize by arguments (which must be hashable) — instantly turning naive recursion linear and deduping expensive lookups; inspect with fn.cache_info(), clear with fn.cache_clear(). cached_property memoizes a computed attribute. wraps copies __name__/__doc__/__wrapped__ onto your wrapper so the decorated function still introspects correctly. singledispatch adds type-based overloads.

Don't lru_cache on instance methods carelessly — the cache holds a reference to self, keeping every instance alive (a memory leak) and keying on the (often unhashable / always-distinct) instance. Use cached_property for per-instance memoization, or cache a module-level function keyed by an id.
