React State Management

useState for local state, useReducer for complex logic, Context for shared state, and Zustand for global app state — picking the right tool for each layer.

🧱 What are the layers of React state management — and which tool belongs at which layer?

React has no built-in global store, so think in layers. Local (useState): state one component needs — toggles, fields, loading flags; never lift higher than necessary. Complex local (useReducer): many related variables or update paths, centralized in (state, action) => newState — Redux-style without the global store. Tree (Context): state a subtree shares (user, theme, locale) — but every consumer re-renders on change, so split large contexts. Global (Zustand/Redux Toolkit): truly app-wide state (auth, notifications). And server state belongs to TanStack Query — caching, dedup, background refresh, stale-while-revalidate, which none of the others do.

  • Local → useState; complex local → useReducer (one reducer, many actions).
  • Subtree → Context — stable values; consumers re-render, so keep it small.
  • Global → Zustand / RTK — auth, notifications, cart.
  • Server data → TanStack Query — not any of the above.

useReducer pattern

// State shape type UserState = { users: UserDto[]; loading: boolean; error: string | null; }; // Actions as discriminated union type Action = | { type: 'LOAD' } | { type: 'LOAD_SUCCESS'; payload: UserDto[] } | { type: 'LOAD_ERROR'; payload: string }; // Reducer: pure function, no side effects function reducer(state: UserState, action: Action): UserState { switch (action.type) { case 'LOAD': return { ...state, loading: true, error: null }; case 'LOAD_SUCCESS': return { ...state, loading: false, users: action.payload }; case 'LOAD_ERROR': return { ...state, loading: false, error: action.payload }; } } // Usage: const [state, dispatch] = useReducer(reducer, initialState);

Zustand global store

// Define store const useAuthStore = create<AuthStore>()((set) => ({ user: null as UserDto | null, isAuthenticated: false, login: (user: UserDto) => set({ user, isAuthenticated: true }), logout: () => set({ user: null, isAuthenticated: false }), })); // Use in any component — no Provider needed function NavBar() { const user = useAuthStore(s => s.user); // selector const logout = useAuthStore(s => s.logout); return <button onClick={logout}>{user?.name}</button>; } // Only re-renders when selected slice changes (user or logout)

State layer decision tree

Is this data from a server? → TanStack Query (handles caching, freshness, background refresh). Is this state needed by only one component? → useState. Complex local state with many update paths? → useReducer. State needed by 2-5 components in a subtree? → Context + useReducer. State needed globally or by deeply unrelated components? → Zustand or Redux Toolkit. Angular equivalent of Zustand: an @Injectable({providedIn:'root'}) service with BehaviorSubjects or Signals — a singleton shared store. Angular equivalent of Context: a service provided at a specific module or component level (not root).

CIAM React app: Auth → Zustand useAuthStore (user, JWT, IDP type, no prop-drilling); user list → TanStack Query useQuery(['users', filters], fetchUsers) (cached, stale-after-60s); forms → React Hook Form; a role-assignment dialog → local useReducer (selected roles, validation, submit status); theme → Context. The Angular mirror: an AuthService with currentUser$ = new BehaviorSubject<UserDto|null>(null) ≈ the Zustand store, and HttpClient.get + async pipe ≈ TanStack Query (minus caching out of the box).

2. useReducer Pattern

// 1. Define state shape + action types
const init = { status: 'idle', data: null, error: null };

// 2. Pure reducer (no side effects!)
function reducer(state, action) {
  switch(action.type) {
    case 'FETCH_START': return {...state, status:'loading'};
    case 'FETCH_OK': return { status:'ok', data: action.payload, error: null };
    case 'FETCH_ERR': return { status:'error', data: null, error: action.error };
    default: return state;
  }
}
// 3. Use in component
function UserProfile({ id }) {
  const [state, dispatch] = useReducer(reducer, init);

  useEffect(() => {
    dispatch({ type: 'FETCH_START' });
    fetchUser(id)
      .then(data => dispatch({ type: 'FETCH_OK', payload: data }))
      .catch(err => dispatch({ type: 'FETCH_ERR', error: err.message }));
  }, [id]);
}

Advantages: all state transitions are visible in the reducer, easily unit-testable with (state, action) input/output, no impossible states.

3. Context API Pitfalls

Context re-renders ALL consumers when the value changes. If your context value is {"{ user, cart }"} and only user changes, every component subscribed to this context re-renders — even cart-only components. Split contexts by update frequency or use a state manager with selector support.

⚠️ One fat context (anti-pattern)

const ctx = { user, cart, theme, locale, notifications };
// User updates → ALL 50 subscribed components re-render

✅ Split by update frequency

const AuthCtx = { user }; // rarely changes
const ThemeCtx = { theme }; // rarely changes
const CartCtx = { cart }; // changes often
// User updates → only AuthCtx consumers re-render
