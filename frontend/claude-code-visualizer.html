Claude Code — Plan, Act, Verify

The differentiator isn't the model — it's the harness: a real tool-calling loop that reads and edits actual files, a Plan Mode gate for risky changes, subagents that keep noisy exploration out of the main conversation, and hooks that enforce policy outside the model's judgment entirely.

⚙️ What makes a terminal-native agent different?

Claude Code runs as a CLI process, not an editor plugin, and that one architectural choice unlocks everything else about how it behaves. Because it's a real process with real file-system and shell access, it doesn't have to guess what a file contains or whether a build passes — it can Read the actual bytes, Grep for the actual pattern, run the actual test command via Bash, and read the actual exit code and output before saying anything is done. That tool-calling loop — read, act, verify, repeat — is the foundation everything else builds on. Plan Mode is a restricted version of that same loop: for changes that are large, ambiguous, or risky, the agent is limited to read-only tools (Read/Grep/Glob, no Edit/Write/Bash-with-side-effects) until it presents a plan and a human explicitly approves it — so research can happen freely while the ability to change anything stays gated. Subagents let the same loop run inside an isolated child conversation: a fork inherits the parent's full context and shares its cache, while a fresh subagent starts cold with just the prompt it's given — either way, the raw tool output from a long exploration stays inside the subagent, and only a distilled summary returns to the main thread. Hooks sit outside all of this: a hook is a deterministic shell command the harness runs at a fixed point (before or after a tool call), and because it runs whether or not the model "agrees," it's the one guardrail that can't be reasoned around by a sufficiently persuasive prompt.

  • Tool loop — Read/Grep/Glob to explore, Edit/Write to change, Bash to run and verify; the same four-step cycle (explore → act → verify → report) repeats for tasks of any size.
  • Plan Mode — a read-only research phase that ends in a written plan; zero files can change until a human explicitly exits plan mode and approves it.
  • Subagents (Task tool) — a fork shares the parent's context and cache; a fresh subagent starts with none of it. Both keep their tool-call noise out of the parent's context window.
  • Hooks — shell commands wired to lifecycle events (e.g. PreToolUse) that can block a specific tool call deterministically, before the model's own judgment is ever consulted.

Verification is the load-bearing step

"I fixed it" and "I ran mvn test and it now exits 0" are different claims. Only a tool loop with real shell access can make the second one — and it's the one worth trusting.

Plan Mode is a permission boundary, not a suggestion

While in plan mode, Edit/Write/side-effecting Bash calls aren't just discouraged — the harness itself refuses to run them until the mode is explicitly exited.

Hooks run outside the model

A hook is a fixed shell command, not a prompt. It can't be argued with, distracted, or convinced to make an exception — which is exactly the point.

In a CIAM codebase specifically: a CLAUDE.md that encodes "JDBC not JPA, ResponseEntity<HttpResponse> on every controller, constructor injection, never hardcode secrets" turns every one of these four capabilities toward the same house rules — Plan Mode research reads the real CustomAuthFilter instead of guessing, a verifying tool loop runs the real mvn test against the real security config, and a pre-commit hook can deterministically block a commit that contains a literal JWT secret, independent of whether the model noticed it.

Four capabilities, one harness

All four scenarios share the same underlying tool loop — what changes is which tools are available, whether a human gate sits in the middle, and whether the work happens in the main conversation or an isolated one. Scenario ④ is the odd one out on purpose: it's the only scenario where the model's own judgment is never even consulted before the block happens.

A few things worth knowing

  • A fork is not a fresh agent — a fork inherits the parent's full conversation and shares its prompt cache, so it's cheap and fast for "go figure this out without cluttering my context." A fresh subagent starts cold and needs the whole situation explained in its prompt, which costs more but guarantees no stale assumptions carry over.
  • Plan Mode changes which tools exist, not just what the model intends — this is enforced by the harness, the same category of guarantee a hook provides, just scoped to a mode rather than a specific command pattern.
  • Hooks and CLAUDE.md solve different problems — CLAUDE.md steers what the model is inclined to do; a hook constrains what the harness will actually let happen even if the model tries anyway. Defense in depth, not redundancy.
