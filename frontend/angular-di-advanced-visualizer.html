Angular DI Advanced — InjectionToken, Hierarchical Injectors & Providers

The complete dependency injection system: typed tokens, provider recipes, injector hierarchy, and modern inject().

💉 What is Angular DI — and why can't you just use new MyService()?

If every component called new UserService(new HttpClient(...)), you'd get a different instance per component (no shared cache or auth state), tight coupling to concrete classes (no swapping a mock in tests), and no control over lifetime. Dependency Injection inverts that: you declare what you need (inject(UserService)) and Angular's injector decides how to supply it — a shared singleton, a scoped instance, or a mock under test. The component neither knows nor cares which implementation it gets.

  • You ask for a token (usually a class); the injector resolves it through a tree of providers and hands back the instance.
  • inject() (14+) works in fields, factories, interceptors, and guards — anywhere in an injection context, not just constructors.
  • Non-class values (config, flags, URLs) come from an InjectionToken so they're injectable too.
  • Provider recipes decide what a token yields: useClass, useValue, useFactory (with its own deps), useExisting (alias).
  • Because dependencies are declared, tests swap a real service for a mock with one provider — no change to the component.

inject() — modern field injection

Old: constructor(private svc: UserService) {}. Modern: private svc = inject(UserService) as a field. Same singleton result; inject() also works in factories, interceptors, and guards — no decorator metadata needed.

InjectionToken — non-class values

const API_URL = new InjectionToken<string>('API_URL'); provide { provide: API_URL, useValue: environment.apiUrl }; inject(API_URL). For config, flags, environment settings — different envs provide different values with no code change.

Provider recipes

useClass (swap Real for Mock), useValue (a static value), useFactory (a function + its own deps), useExisting (alias to an already-provided instance). Combine them for flexible service config.

In CIAM:AuthStore is providedIn: 'root' (one singleton); a PING_URL = new InjectionToken('PING_URL') is provided from environment.pingBaseUrl; and tests do TestBed.configureTestingModule({ providers: [{ provide: AuthStore, useClass: MockAuthStore }] }) so every injector of AuthStore gets the mock — zero test-specific code in components.

or, providers: [UserService] doesn't share your service with the app — it hides the app's copy from everyone inside that box

The problem

The nav bar showed the badge count. The page it navigated to reset back to zero.

Same @Injectable, same providedIn: 'root' — and two different instances of it, alive at once

NotificationService is @Injectable({ providedIn: 'root' }) and increments an in-memory unread count as events arrive. NavComponent injects it and shows a badge. Someone adds providers: [NotificationService] to PageComponent — "just to be explicit about what this page depends on" — and everything keeps compiling, keeps working in every manual test. Weeks later someone notices the badge count resets to zero every time you navigate into a page, then climbs again, independent of the nav bar's own count. Nobody touched NotificationService's code. Nobody removed providedIn: 'root'.

NotificationService still says providedIn: 'root' ✓ NavComponent's badge injects it exactly the same way it always did ✓ PageComponent's providers array creates a second instance ⚠ everything inside PageComponent now talks to that copy, forever ⚠

providedIn: 'root' is a promise about where a service is registered, not a guarantee about which instance a given component actually receives — that part depends entirely on what sits between it and the root.

Only add a provider where you actually mean to start a new instance
providers: [NotificationService] on PageComponent → remove it entirely ↓ with nothing shadowing it, PageComponent's injector has no local recipe, so resolution walks up to the root singleton like everything else does If a scoped instance really was the goal (a per-page draft, a per-dialog form), keep the provider — but name it so the next reader knows it's deliberate ↓ shadowing isn't wrong, it's a real, useful tool — it's only a bug when nobody meant to reach for it One array entry, and it's the difference between "the badge" and "a badge"
A provider doesn't add to where a service lives — it changes which injector answers first. Every component sits at the bottom of a chain of injectors, and DI resolution asks each one in turn, starting at that component, "do you have a recipe for this token?" — stopping at the very first yes. providedIn: 'root' only matters if nothing closer already said yes. That's why an unrelated providers: [NotificationService] three components down doesn't override the root service so much as it never lets the question reach the root at all.
Think of injector resolution as asking a question up a chain of managers, stopping at the first one who answers. If your direct manager happens to know the answer — even if they made it up five minutes ago, unaware the CEO already had an official one — you get your manager's answer, and the question never reaches the CEO's desk at all. providedIn: 'root' is the CEO's official policy; a component providers array is a manager quietly deciding to run things their own way for their own team. Nothing forwards the question past the first "yes."

Because I was never asked to check with root at all. I was configured with my own provider for that exact token — my own recipe, my own instance — so when anything inside me asks for NotificationService, I already have an answer. I don't consult anyone above me; I don't need to.

The mechanism

One array entry on one component changes who answers a question that never reaches the root at all.

  1. NotificationService is registered once, in the root environment injector, via providedIn: 'root'the only instance, until something shadows it
  2. PageComponent is decorated with providers: [NotificationService] — a second, independent recipe for the identical token, registered in PageComponent's own node injectora new injector level now has an opinion
  3. PageComponent is instantiated. Angular builds it a fresh node injector, sees the local providers entry, and has a recipe ready before anything even asksset up in advance, not on demand
  4. A child inside PageComponent calls inject(NotificationService). Resolution starts at that child's own injector and walks upward — and hits PageComponent's injector first, which already has a matchthe walk stops at the first yes
  5. PageComponent's local instance is returned. The root's instance — the one NavComponent is holding onto — is never even considered, because the walk never got that farnot overridden — never reached
  6. Two live instances of NotificationService now exist for the lifetime of PageComponent: the root's, still ticking along for NavComponent, and PageComponent's own, starting from zero and known to nothing outside its subtreethe whole bug in one sentence

Step 4 is the lesson. Nothing about the root's NotificationService broke, and nothing explicitly "overrode" it — the walk that would have found it simply never made it past the first injector that had an answer. That's the entire mental model hierarchical DI runs on: resolution is a walk that stops at the first match, not a merge of every provider in the tree.

Root injector — providedIn: 'root' NotificationService lives here, untouched
PageComponent's injector — providers: [NotificationService], a second recipe for the same token
A child inside PageComponent calls inject(NotificationService)the walk starts here and looks outward, ring by ring, stopping at the first yes

The walk never reaches the outer ring — not because anything blocks it, but because the inner ring already answered. Move PageComponent's providers array away and the exact same walk keeps going one ring further out, straight to root, and NavComponent's instance is the one everyone gets again.

AuthStore is @Injectable({ providedIn: 'root' }). LoginPageComponent has providers: [AuthStore] in its decorator "to be explicit about what this page depends on." A child of LoginPageComponent calls inject(AuthStore). Which instance does it get?

Right, and "to be explicit" is exactly how this mistake gets written — the intent was documentation, not a second instance, but the injector can't tell the difference between "I'm restating this for clarity" and "I'm establishing a new recipe here." Both look identical: an entry in a providers array.

A completely reasonable mental model — "DI is basically one big registry, so pointing at the same class twice should be a no-op" — and it's the mental model this exact bug relies on being wrong. Every providers array creates a real, independent recipe local to that injector; there's no dedup against what root already has.

There's no cross-level deduplication in Angular's DI — each injector that has a matching recipe creates and owns its own instance the first time something asks. Two injectors with a recipe for the same token during the same app run means two separate live objects, full stop, with no mechanism checking whether one already exists somewhere else in the tree.

Where you've seen this before

"Nearest answer wins" is a rule you already rely on somewhere else in your stack.

CSS specificity — closest rule wins, not "most official" rule

The identical resolution shape: a browser applies whichever matching CSS rule wins by specificity and source order, not whichever one lives in the most authoritative-sounding stylesheet. A component-scoped style overriding a global one isn't the global rule being broken — it's the same "nearest match wins, full stop" logic DI resolution runs, just for pixels instead of service instances.

nearest matching rule / nearest matching injector — same algorithm

Java's classloader shadowing — the same class, loaded twice

A Java app with two classloaders (an app server's shared lib folder plus a WAR's own WEB-INF/lib) can load the same class twice as two distinct Class objects — a static field on one is invisible to code holding the other loader's version, and instanceof checks between them mysteriously fail. Same root cause as this page: nothing merges two things registered under the same name at different levels of a hierarchy; whichever level answers your specific lookup is the only one you get.

two classloaders, two "singletons" — same shape as two injectors

A CIAM step-up-auth dialog re-providing AuthStore on purpose

A step-up MFA dialog is one of the rare, legitimate uses of this exact mechanism: providers: [{ provide: AuthStore, useClass: StepUpAuthStore }] deliberately shadows the root store for everything inside that dialog, so a half-completed step-up flow can hold its own draft session state without corrupting the real, already-authenticated AuthStore the rest of the app is reading. Same shadowing behavior that broke NotificationService above — the only difference is that here, somebody meant it and named the class to say so.

shadowing is the same feature, used on purpose this time
Questions from the back row

If shadowing is this easy to trigger by accident, why does Angular allow component-level providers at all?

Because scoped instances are genuinely necessary, not a mistake waiting to happen — a form-wizard step, a modal with its own draft state, a list item that needs its own selection state, all want an instance that dies with the component instead of leaking into a singleton that outlives it. The feature isn't the problem; the problem is that "shadow the root on purpose" and "accidentally re-list a root service out of habit" produce byte-for-byte identical code. The fix is a habit, not a language change: only add a component to a providers array when you can say out loud why this component needs its own instance.

Does @Self or @SkipSelf help catch or prevent this kind of bug?

They help at the injection site, not the provider site — @Self() on an inject() call says "only look in my own component's injector, fail if it's not there," which would at least make a missing local provider loud instead of silently falling through to root. @SkipSelf() does the opposite: "start looking one level up, ignore anything provided right here" — useful for a component that wants its parent's instance specifically even though it also happens to provide its own for its children. Neither one stops someone from adding an accidental providers: [X] in the first place; they just change how loudly the next injection point complains about the hierarchy it finds.

Is providedIn: 'root' ever actually a lie, then — does the service really live in "one" place?

No, providedIn: 'root' is accurate as far as it goes: it registers exactly one recipe, in the root environment injector, and that's the only registration that exists unless something else adds a competing one. It was never a claim that no other injector could ever shadow it — it's closer to "this is the fallback everyone gets, absent a closer answer." The mental slip is reading "providedIn: 'root'" as "there is exactly one instance for the life of the app," when the accurate reading is "there is exactly one instance for any injector that doesn't have a closer recipe of its own."

1. DI System Recap: Tokens, Providers, Injectors

Token

The key used to look up a dependency. Can be a class (most common), an InjectionToken, or a string (avoid strings — use tokens).

Provider

The recipe that tells the injector how to create the value. Types: useValue, useClass, useExisting, useFactory.

Injector

The container that holds token→value mappings. Multiple injectors form a tree. Resolution walks up the tree until found.

// The DI lookup process in pseudo-code:
function inject(Token) {
  let injector = getCurrentElementInjector();  // starts at the injector CLOSEST to where inject() was called
  while (injector !== null) {  // keeps going until it either finds the token or runs out of tree
    if (injector.has(Token)) return injector.get(Token);  // first match wins — a closer provider always shadows a farther one
    injector = injector.parent; // walk up
  }
  throw new NullInjectorError(`No provider for ${Token}`);  // reached the root with nothing found — this is the real error behind "NullInjectorError"
}

2. InjectionToken<T> — Typed Tokens for Non-Class Values

Use InjectionToken when you need to inject a primitive value, configuration object, or function — anything that isn't a class.

import { InjectionToken } from '@angular/core';  // a class that manufactures unique, typed tokens — the string is just a debug label

// Basic string token
export const API_URL = new InjectionToken<string>('apiUrl');  // <string> is what makes inject(API_URL) come back typed as string, not any

// With inline factory + providedIn — no need to add to providers array
export const BASE_URL = new InjectionToken<string>('baseUrl', {
  providedIn: 'root',  // same tree-shakable-singleton idea as an @Injectable service
  factory: () => 'https://api.example.com'  // runs once, lazily, the first time something injects this token
});

// Complex type token
interface AppConfig {  // tokens aren't limited to primitives — any shape works
  apiUrl: string;
  maxRetries: number;
  debugMode: boolean;
}
export const APP_CONFIG = new InjectionToken<AppConfig>('appConfig');  // no factory this time — must be registered explicitly, see providers below

// Register in providers (bootstrapApplication or component)
providers: [
  { provide: API_URL, useValue: 'https://prod.api.example.com' },  // useValue — the simplest case, just hand over a literal
  {
    provide: APP_CONFIG,
    useFactory: () => ({  // useFactory — computed at registration time, can read other values
      apiUrl: environment.apiUrl,
      maxRetries: 3,
      debugMode: !environment.production
    })
  }
]

// Inject using inject() function (recommended, modern)
@Injectable({ providedIn: 'root' })
export class ApiService {
  private readonly apiUrl = inject(API_URL);  // same inject() function used for class-based services — tokens aren't special-cased
  private readonly config = inject(APP_CONFIG);  // fully typed as AppConfig — TS knows config.maxRetries is a number
}
Token TypeWhen to UseExample
classWhen the value is an instance of a classinject(UserService)
InjectionToken<string>Strings, numbers, URLs, API keysinject(API_URL)
InjectionToken<Config>Configuration objectsinject(APP_CONFIG)
InjectionToken<Function>Inject a function/factoryinject(LOCALE_FACTORY)

3. All Four Provider Types

useValue — Constant

{ provide: API_URL,
  useValue: 'https://api.example.com' }

{ provide: ENVIRONMENT,
  useValue: { production: false } }

Provides a static, already-constructed value. The value is never instantiated — it's given as-is. Good for config, flags, constants.

useClass — New Instance

{ provide: UserService,
  useClass: MockUserService }

// Provide a different impl in tests
// or for feature flags

Angular creates a new instance of the given class when the token is first requested. Useful for swapping implementations (e.g., mock in tests).

useExisting — Alias

{ provide: AbstractLogger,
  useExisting: ConsoleLogger }

// Both tokens resolve to the SAME
// ConsoleLogger instance — no duplication

Maps one token to an already-registered token. Unlike useClass, it reuses the existing singleton — no second instance created.

useFactory — Computed

{ provide: DbConnection,  // the token being provided — here it's a class, but could be an InjectionToken too
  useFactory: (config: AppConfig,  // factory arguments are positional — their ORDER must match the deps array below
               http: HttpClient) => {
    return new DbConnection(config.dbUrl, http);  // build the real value using whatever the factory needs
  },
  deps: [APP_CONFIG, HttpClient]  // Angular resolves each of these first, then passes them as the factory's args, in this order
}

Runs a function to produce the value. Deps array lists what the factory needs — Angular injects them and passes as args.

Multi-Providers — Collecting Multiple Values

// Register multiple interceptors — all use the SAME token, multi:true
{ provide: HTTP_INTERCEPTORS, useClass: AuthInterceptor, multi: true }
{ provide: HTTP_INTERCEPTORS, useClass: LoggingInterceptor, multi: true }
{ provide: HTTP_INTERCEPTORS, useClass: RetryInterceptor, multi: true }

// inject(HTTP_INTERCEPTORS) returns [AuthInterceptor, LoggingInterceptor, RetryInterceptor]

// Custom multi-provider token
export const APP_INITIALIZER_TOKEN = new InjectionToken<AppInitFn[]>('appInit');
{ provide: APP_INITIALIZER_TOKEN, useValue: loadUserFn, multi: true }
{ provide: APP_INITIALIZER_TOKEN, useValue: loadConfigFn, multi: true }

4. DI Decorators: @Optional, @Self, @SkipSelf, @Host

DecoratorBehaviorUse Case
@Optional() Returns null instead of throwing if token not found Optional feature modules, plugins, optional configuration
@Self() Only looks in the current element injector — does not walk up the tree Ensure a dep is provided locally, fail if not
@SkipSelf() Skips the current injector — starts search at the parent Module forChild pattern, avoid circular self-reference
@Host() Stops search at the host component (won't go past view boundary) Directive accesses a service from its host component only 
// @Optional — won't throw
readonly logger = inject(LogService, {
  optional: true  // inject() syntax
});

// Or decorator syntax
constructor(
  @Optional() private logger: LogService
) {}
// @Self — component-local only
constructor(
  @Self() private ctrl: NgControl  // must be provided on THIS element — a parent's NgControl doesn't satisfy it
) {}

// @SkipSelf — parent's injector
constructor(
  @SkipSelf() private parentSvc: SomeService  // the exact opposite of @Self — deliberately ignores a local provider, if one exists
) {}

// @Host — stops at host boundary
constructor(
  @Host() @Optional() private form: FormGroupDirective  // stacking decorators — stop at the host, AND don't throw if nothing's found
) {}

import { inject, PLATFORM_ID, DOCUMENT } from '@angular/core';  // both are built-in InjectionTokens, same mechanism as APP_CONFIG above
import { isPlatformBrowser } from '@angular/common';  // a helper that reads PLATFORM_ID's value for you

export class ThemeService {
  private readonly platformId = inject(PLATFORM_ID);  // tells you whether this code is running in the browser or on the server (SSR)
  private readonly document = inject(DOCUMENT);  // injecting DOCUMENT instead of using the global `document` keeps this service SSR-safe

  setTheme(theme: string) {
    if (isPlatformBrowser(this.platformId)) {  // guards against touching the DOM during server-side rendering, where there isn't one
      this.document.documentElement.setAttribute('data-theme', theme);
    }
  }
}

6. The inject() Function — Modern DI

The inject() function is the modern way to resolve dependencies in Angular. It can be called in class fields, constructors, and factory functions — anywhere Angular's injection context is active.

Old: constructor injection

@Component({...})
export class UserComponent {  // three services means three field declarations, three constructor params, three assignments
  private readonly userService: UserService;  // declared here...
  private readonly router: Router;
  private readonly http: HttpClient;

  constructor(
    userService: UserService,  // ...typed again here, as a constructor parameter Angular resolves by type
    router: Router,
    http: HttpClient
  ) {
    this.userService = userService;  // ...and assigned a THIRD time, manually, in the body
    this.router = router;
    this.http = http;
  }
}

New: inject() as class fields

@Component({...})
export class UserComponent {
  private readonly userService = inject(UserService);
  private readonly router = inject(Router);
  private readonly http = inject(HttpClient);

  // No constructor needed!
  // TypeScript infers the types automatically.
  // Works in directives, services, pipes too.
}

inject() in Functions (injection context required)

// Guards — standalone functional style (Angular 15+)
export const authGuard: CanActivateFn = (route, state) => {
  const auth = inject(AuthService);      // inject() inside guard function
  const router = inject(Router);
  return auth.isLoggedIn() || router.navigate(['/login']);
};

// Resolvers
export const userResolver: ResolveFn<User> = (route) => {
  return inject(UserService).getUser(route.params['id']);
};

// Class field with computed token
readonly config = inject(APP_CONFIG, { optional: true }) ?? defaultConfig;

8. forwardRef — Resolving Circular References

When you need forwardRef: TypeScript evaluates class definitions in order. If class A references class B that's defined after A (circular or forward reference), the value is undefined at definition time. forwardRef wraps it in a function that's resolved lazily. 
import { forwardRef } from '@angular/core';
import { NG_VALUE_ACCESSOR } from '@angular/forms';

// Custom form control — classic forwardRef use case
@Component({
  selector: 'app-custom-input',
  standalone: true,
  providers: [{
    provide: NG_VALUE_ACCESSOR,
    useExisting: forwardRef(() => CustomInputComponent),
    multi: true
  }]
})
export class CustomInputComponent implements ControlValueAccessor {
  // ... the class body
}
// forwardRef needed because CustomInputComponent is used in its OWN decorator,
// before the class definition is complete.
