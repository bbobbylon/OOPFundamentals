🪪 What is a JWT — and why can everyone read one?

A JWT is three Base64-encoded chunks glued with dots: header.payload.signature. The header and payload are just JSON — anyone can paste a token into this page (or jwt.io) and read every claim, no key required. What makes it trustworthy isn't secrecy, it's the signature: a cryptographic proof that only whoever holds the signing key could have produced that exact header+payload combination.

  • Header — algorithm (HS256, RS256…) and token type.
  • Payload — the claims: sub (who), exp (expiry), roles/scope (what they can do), plus whatever else the issuer put there.
  • Signature — HMAC or RSA/ECDSA over the first two parts. Change one byte of the payload and the signature no longer matches — that's what "tamper → Verify ✗" proves.
  • The rule the whole system rests on: anyone can read (and edit) a JWT; only the key holder can make a valid one.
  • A server never "looks up" a session for a JWT — it just re-checks the signature and trusts the claims inside. That's what makes JWTs stateless.

or, the one JWT field you should never let the token itself decide

The problem

The header field that names the signing algorithm lives INSIDE the token — which means whoever forges a token also gets to write that field.

Your verifier let a forged Admin token through, using nothing but a public key

Your resource server verifies tokens from your IdP with real RS256: it fetches the IdP's public key from /oauth2/jwks and hands it, plus the token, to a verify function. Some JWT libraries — this is a real, documented weakness several popular ones shipped historically — accept a bare key and read the token's own alg header to decide HOW to use it: RSA public key for RS256, or plain HMAC secret for HS256. Convenient. Also fatal.

An attacker fetches your public JWKS — it's meant to be public, that's the whole point of RS256 — and builds a token by hand: header {"alg":"HS256"}, payload {"sub":"attacker","roles":["Admin"]}, then computes the signature as HMAC-SHA256(header.payload, publicKeyBytes) — using your RSA public key's raw bytes as if they were a shared HMAC secret. Your verifier reads alg: HS256 off the token, reaches for the exact same public key it already had loaded for RS256, and runs it through HMAC instead. The attacker computed that same HMAC using that same public key. The two match. The forged token verifies — the IdP's actual private key was never touched, and never needed to be.

JWKS correctly serving the public key ✓ the IdP's private key never left the IdP ✓ the signature check ran, and technically matched ✓ the TOKEN got to choose which algorithm/key-type verified it ⚠

The alg header is a claim like any other — the same untrusted, attacker-editable JSON you've been tampering with all through this page. Trusting it to decide how you check the signature hands the attacker the one decision that was supposed to be yours.

Pin the algorithm on the server — never read it off the token
Configure your verifier with an explicit allow-list, e.g. algorithms: ["RS256"] ↓ modern libraries (jjwt, jose, a patched PyJWT) require this and refuse to verify at all if the token's own header names anything outside it — the token no longer gets a vote Never let one code path accept both HMAC and RSA/EC verification ↓ HMAC wants a plain secret, RSA wants a public/private keypair; a verifier willing to take either based on the token's own say-so is exactly the ambiguity this attack lives in Reject alg: none outright, not just fail to specifically support it ↓ none means "no signature at all" — technically spec-legal, but a hardened verifier should treat it as an attack signal, never a valid choice to fall back to
The one-sentence rule. A cryptographic verifier has to decide, independently of the message it's checking, which algorithm and which key that check is allowed to use — the moment the message itself gets a vote in that decision, the message can simply lie its way into passing.
It's like a bouncer who asks the guest which ID-checking method to use before looking at the ID. Of course the fake ID says "just glance at the photo, don't scan the barcode." The guest should never be the one setting the rules for their own inspection.

The mechanism

Follow a forged Admin token all the way through a verifier that lets the alg header make the call.

  1. Your server publishes its RSA public key at /oauth2/jwks — public by design, meant for anyone to fetchpublic by design
  2. An attacker downloads that key the same way any legitimate resource server wouldno secret needed
  3. Attacker builds a token: header {"alg":"HS256"}, payload {"sub":"attacker","roles":["Admin"]}forged claims
  4. Attacker signs it: HMAC-SHA256(header.payload, publicKeyBytes) — the public key standing in as a shared secretthe trick
  5. Your verifier reads alg: HS256 off the token and reruns HMAC using the same public key it already had loadedtrusts the header
  6. Both HMACs were computed from the exact same bytes — they match, and the forged Admin token verifies "successfully"forgery accepted

Step 5 is the whole bug, and there's nothing broken about the cryptography anywhere in this chain — HMAC and RSA are both doing precisely what they're built to do. The mistake was made once, early, in how the verifier was wired: "read the token's alg field, and use whatever it says." Everything downstream of that one decision worked flawlessly toward the wrong outcome.

an HTTP request arrives, carrying a JWT
the JWT's own header self-declares alg: HS256
the verifier's algorithm-selection logic defers to that header
an RSA PUBLIC key, doing an HMAC SECRET's jobmeant to be shared with the world, now protecting a forged "Admin" claim instead

Trace the nesting from the outside in: each layer trusted the one just inside it a little further than it should have, and by the time you reach the center, a key that was DESIGNED to be public is standing guard over a decision that needed a secret. Nothing in any single ring looks wrong — the request is real, the header parses fine, the key really is the IdP's key. The vulnerability only exists in the accumulated trust between the rings.

Your resource server reads the alg field out of the token itself, then verifies using whatever type that field names. An attacker downloads your IdP's PUBLIC RSA key from your own JWKS endpoint, crafts a token with alg: HS256 and roles: ["Admin"], and signs it with HMAC using that public key's bytes as the secret. What happens?

Right. HMAC's secret can be any bytes at all — including a supposedly public RSA key. Because the verifier let the token's own alg header pick the algorithm, it reused the RSA public key as an HMAC secret, and since the attacker used that exact same public key, the HMAC matches perfectly.

HMAC doesn't know or care where its secret came from or what it "means" elsewhere — it's just bytes in, hash out. An RSA public key is, at the byte level, just as usable as any other string of bytes, which is exactly the problem.

A JWKS endpoint's only job is serving public keys to anyone who asks — it has no visibility into what algorithm some later, unrelated request decides to use those keys with, and no role in verification at all. The vulnerability lives entirely inside the verifier's own logic.

Where you have seen this before

"Let the untrusted input decide how it gets interpreted" is the same root mistake behind some of the oldest bug classes in software.

SQL injection

Concatenating user input directly into a query string lets the attacker's input decide what's code and what's data — a string that was supposed to be a value for WHERE name = ? gets treated as SQL syntax instead. Parameterized queries fix it the same way pinning alg does: the interpretation is fixed by the server, never negotiated with the input.

the original "let input choose the rules" bug

XXE — untrusted XML declaring its own parsing rules

An XML document's <!DOCTYPE> can declare external entities that a naive parser will dutifully resolve — including reading local files or making outbound requests — because the document itself is allowed to configure how it gets parsed. A hardened parser disables external entity resolution by server-side policy, not by trusting the document to behave.

the document telling the parser how to read it

Unsafe polymorphic deserialization (Jackson @class, Java's ObjectInputStream)

Enabling default typing lets an incoming JSON payload include a @class field naming exactly which Java class to instantiate — attacker-controlled data choosing its own deserialization target, which is how a crafted payload turns into remote code execution. Same shape: the data names its own interpretation, and the deserializer obeys.

a JVM-native version of the identical trap

3 — The one rule: read ≠ trust

A JWT is signed, not encrypted

The header and payload are just base64url — anyone can decode and read them (you just did). They are not secret: never put a password or anything sensitive in a token. The signature is the only protection — it proves the payload hasn't changed since the issuer signed it.

Tampering is trivial — and caught

Edit roles to ["Admin"] and keep the signature → Verify fails. To forge a token that verifies, you'd need the issuer's secret (HS256) or private key (RS256) — which never leaves the IdP. That's why a resource server must verify the signature on every request and never trust an unverified token. See JWTs: decode & diagnose.

HS256 vs RS256. HS256 uses one shared secret to sign and verify (fine when the same party does both). Real IdPs use RS256: the IdP signs with a private key, and your API verifies with the matching public key fetched from the IdP's JWKS endpoint — so your API can validate tokens without ever holding a secret. This playground verifies HS256 locally; the principle is identical. Walk a real validation in JWT Tokens (Entra) and the mapping in Multi-IDM Claim Mapping.

4 — Recap

🎫 A JWT is three base64url parts: header (alg, kid), payload (the claims — iss/aud/sub/exp/scope/roles), and a signature. The payload is readable by anyone and means nothing on its own — only a valid signature (made with the issuer's secret/key) makes it trustworthy, and your API re-checks it every request. Authorization is a separate step: claims are mapped to authorities (the mapping is per-IdP, and the default ignores roles), then @PreAuthorize decides. Authentication ≠ authorization; readable ≠ trustworthy.
