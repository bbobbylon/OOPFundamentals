3 — The one rule: read ≠ trust

A JWT is signed, not encrypted

The header and payload are just base64url — anyone can decode and read them (you just did). They are not secret: never put a password or anything sensitive in a token. The signature is the only protection — it proves the payload hasn't changed since the issuer signed it.

Tampering is trivial — and caught

Edit roles to ["Admin"] and keep the signature → Verify fails. To forge a token that verifies, you'd need the issuer's secret (HS256) or private key (RS256) — which never leaves the IdP. That's why a resource server must verify the signature on every request and never trust an unverified token. See JWTs: decode & diagnose.

HS256 vs RS256. HS256 uses one shared secret to sign and verify (fine when the same party does both). Real IdPs use RS256: the IdP signs with a private key, and your API verifies with the matching public key fetched from the IdP's JWKS endpoint — so your API can validate tokens without ever holding a secret. This playground verifies HS256 locally; the principle is identical. Walk a real validation in JWT Tokens (Entra) and the mapping in Multi-IDM Claim Mapping.

4 — Recap

🎫 A JWT is three base64url parts: header (alg, kid), payload (the claims — iss/aud/sub/exp/scope/roles), and a signature. The payload is readable by anyone and means nothing on its own — only a valid signature (made with the issuer's secret/key) makes it trustworthy, and your API re-checks it every request. Authorization is a separate step: claims are mapped to authorities (the mapping is per-IdP, and the default ignores roles), then @PreAuthorize decides. Authentication ≠ authorization; readable ≠ trustworthy.
