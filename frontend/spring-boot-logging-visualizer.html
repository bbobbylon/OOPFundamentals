1. SLF4J + Logback Architecture

SLF4J (Simple Logging Facade for Java) is just an API — a set of interfaces your code calls. Logback is the default implementation that Spring Boot wires in automatically via spring-boot-starter-logging. Because your code only ever talks to the SLF4J API, you can swap Logback for Log4j2 by changing a single Maven exclusion — zero code changes.

Your Codecalls log.info()
→
SLF4J APILogger / LoggerFactory
→
Logbackdefault impl
→
Console / Fileformatted output
Why the abstraction? If Logback has a CVE, or your team switches to Log4j2 for async performance, you add one exclusion + one dependency in pom.xml. Every log.info() call in your service layer stays identical.
/* Maven — Logback is included transitively by spring-boot-starter-web. You don't need to declare it. To switch to Log4j2: */ <dependency> <groupId>org.springframework.boot</groupId> <artifactId>spring-boot-starter-web</artifactId> <exclusions> <exclusion> <groupId>org.springframework.boot</groupId> <artifactId>spring-boot-starter-logging</artifactId> <!-- remove Logback --> </exclusion> </exclusions> </dependency> <dependency> <groupId>org.springframework.boot</groupId> <artifactId>spring-boot-starter-log4j2</artifactId> <!-- add Log4j2 --> </dependency>

3. Logger Setup

You need a Logger instance in each class. The Lombok way eliminates the boilerplate entirely.

Lombok @Slf4j PREFERRED
// Add Lombok to pom.xml: // <dependency> // <artifactId>lombok</artifactId> // </dependency> @Slf4j // Lombok generates the log field @Service public class UserService { public User getUserById(Long id) { log.debug("Fetching user {}", id); User user = repo.findById(id) .orElseThrow(() -> { log.warn("User {} not found", id); return new UserNotFoundException(id); }); log.info("User {} loaded", id); return user; } }
Manual LoggerFactory VERBOSE
// No Lombok dependency needed, // but you write this in every class. @Service public class UserService { // Must match the enclosing class exactly private static final Logger log = LoggerFactory.getLogger(UserService.class); public User getUserById(Long id) { log.debug("Fetching user {}", id); return repo.findById(id) .orElseThrow(...); } }
The logger name matters. Logback uses the fully-qualified class name (com.example.UserService) to match logging level rules in application.properties. Always pass MyClass.class so the hierarchy works correctly — never a string literal.

4. Logging in application.properties

Spring Boot maps logging.level.<package> directly to Logback logger names. The key is always the fully-qualified package or class name.

# application.properties # Root level — applies to everything not matched by a more specific rule logging.level.root=WARN # Spring framework internals — set to DEBUG to see request mapping, beans, etc. logging.level.org.springframework.web=INFO logging.level.org.springframework.security=DEBUG # Your application packages — DEBUG in dev, INFO in prod logging.level.com.example=DEBUG logging.level.com.example.service=INFO # override a sub-package # Print ALL SQL queries executed by Hibernate logging.level.org.hibernate.SQL=DEBUG # Print the actual bind parameter values (careful in prod!) logging.level.org.hibernate.orm.jdbc.bind=TRACE # Output format — writes to a file as well as console logging.file.name=logs/application.log # Custom console pattern (optional — logback-spring.xml overrides this) logging.pattern.console=%d{HH:mm:ss.SSS} %-5level [%X{requestId}] %logger{36} - %msg%n
Key pattern Example value Effect
logging.level.root WARN Default for all loggers not matched below
logging.level.<package> DEBUG All classes inside that package and sub-packages
logging.level.<class> TRACE One specific class only
logging.level.org.hibernate.SQL DEBUG Prints every SQL statement — essential when debugging JPA
logging.file.name logs/app.log Also write logs to this file (default: console only)

5. MDC — Mapped Diagnostic Context

The most underrated logging feature. MDC lets you attach key-value pairs (requestId, userId, traceId) to the current thread. Every log line from that thread automatically includes those values — without passing them through every method signature.
1
Request arrives. A Filter or HandlerInterceptor runs before your controller. It calls MDC.put("requestId", UUID.randomUUID().toString()) to tag the thread.
2
Your code runs normally. Every call to log.info(), log.debug(), etc. automatically includes the MDC map — no extra parameters needed.
3
Log pattern outputs the value. Use %X{requestId} in your Logback pattern to interpolate MDC values into every log line.
4
Request completes. The filter calls MDC.clear() in a finally block to prevent MDC leaking to the next request on thread-pool reuse.
MDC Filter (recommended)
@Component public class MdcFilter implements Filter { @Override public void doFilter( ServletRequest req, ServletResponse res, FilterChain chain) throws IOException, ServletException { try { String reqId = UUID.randomUUID().toString() .substring(0, 8); MDC.put("requestId", reqId); // Add to response header so // caller can correlate errors ((HttpServletResponse) res) .setHeader( "X-Request-Id", reqId); chain.doFilter(req, res); } finally { MDC.clear(); // always! } } }
Logback pattern with %X{}
# application.properties logging.pattern.console=\ %d{HH:mm:ss.SSS} \ %-5level \ [%X{requestId:-no-mdc}] \ %logger{30} \ - %msg%n /* What a log line looks like: */ 14:23:01.442 INFO [req-a1b2c3d4] c.e.s.UserService - User 42 loaded /* %X{key:-default} means: print MDC "key", or "default" if it is not set (handy for background threads). */ /* You can put multiple values: %X{requestId} %X{userId} */

7. Logback Configuration (logback-spring.xml)

logback-spring.xml vs logback.xml: Always use logback-spring.xml. Spring Boot loads it after its own auto-configuration, which means you get <springProfile> tags to activate different appenders per profile (dev / prod).
<?xml version="1.0" encoding="UTF-8"?> <configuration> <!-- Pull in Spring Boot's defaults (color, base pattern) --> <include resource="org/springframework/boot/logging/logback/defaults.xml"/> <!-- ── Console Appender ───────────────────────────────────────── --> <appender name="CONSOLE" class="ch.qos.logback.core.ConsoleAppender"> <encoder> <pattern> %d{HH:mm:ss.SSS} %highlight(%-5level) [%X{requestId:- }] %cyan(%logger{36}) - %msg%n </pattern> </encoder> </appender> <!-- ── Rolling File Appender ─────────────────────────────────── --> <appender name="FILE" class="ch.qos.logback.core.rolling.RollingFileAppender"> <file>logs/application.log</file> <rollingPolicy class="ch.qos.logback.core.rolling.TimeBasedRollingPolicy"> <!-- Roll over daily; gzip the archived file --> <fileNamePattern>logs/application.%d{yyyy-MM-dd}.log.gz</fileNamePattern> <maxHistory>30</maxHistory> <!-- keep 30 days of archives --> <totalSizeCap>3GB</totalSizeCap> <!-- hard cap on disk usage --> </rollingPolicy> <encoder> <!-- Plain text in file (no ANSI codes) --> <pattern>%d{yyyy-MM-dd HH:mm:ss.SSS} %-5level [%X{requestId:- }] %logger{50} - %msg%n</pattern> </encoder> </appender> <!-- ── Profile-specific activation ───────────────────────────── --> <springProfile name="dev"> <root level="DEBUG"> <appender-ref ref="CONSOLE"/> </root> </springProfile> <springProfile name="prod"> <root level="WARN"> <appender-ref ref="CONSOLE"/> <appender-ref ref="FILE"/> </root> <!-- Keep DEBUG for your own code even in prod --> <logger name="com.example" level="DEBUG"/> </springProfile> </configuration>

8. Structured JSON Logging

Plain-text logs are for humans. JSON logs are for machines — ELK Stack, Splunk, CloudWatch Logs Insights, Datadog. One log line becomes a fully-indexed document where every field is searchable without regex.

<!-- pom.xml: logstash-logback-encoder --> <dependency> <groupId>net.logstash.logback</groupId> <artifactId>logstash-logback-encoder</artifactId> <version>7.4</version> </dependency>
<!-- logback-spring.xml: replace the encoder in your FILE appender --> <encoder class="net.logstash.logback.encoder.LogstashEncoder"> <!-- include all MDC fields automatically --> <includeMdc>true</includeMdc> <!-- shorten the logger name field --> <shortenedLoggerNameLength>36</shortenedLoggerNameLength> </encoder>

What one JSON log line looks like:

{ "@timestamp": "2026-05-29T14:23:01.442Z", "level": "INFO", "logger_name": "com.example.service.UserService", "thread_name": "http-nio-8080-exec-3", "message": "User 42 loaded, returning DTO", "requestId": "a1b2c3d4", // from MDC — automatic "userId": "42", // from MDC — if you added it "stack_trace": null }
Why this matters: In CloudWatch Logs Insights you can run fields @timestamp, message | filter requestId = "a1b2c3d4" and instantly see every log line from that one HTTP request across all your service instances. With plain text you would need a regex and a lot of luck.

9. Log File Rolling Policies

Never let a log file grow forever. Logback supports two rolling strategies, and you can combine them.

TimeBasedRollingPolicy
<!-- Roll at midnight, keep 30 days --> <rollingPolicy class= "...TimeBasedRollingPolicy"> <fileNamePattern> logs/app.%d{yyyy-MM-dd}.log.gz </fileNamePattern> <<!-- delete files older than this many periods --> <maxHistory>30</maxHistory> <!-- total archive cap --> <totalSizeCap>5GB</totalSizeCap> </rollingPolicy>
SizeAndTimeBasedRollingPolicy
<!-- Roll daily OR when file hits 100MB --> <rollingPolicy class= "...SizeAndTimeBasedRollingPolicy"> <fileNamePattern> logs/app.%d{yyyy-MM-dd}.%i.log.gz </fileNamePattern> <!-- max size per file --> <maxFileSize>100MB</maxFileSize> <maxHistory>30</maxHistory> <totalSizeCap>10GB</totalSizeCap> </rollingPolicy>
SettingRecommended valueNotes
maxHistory 30 30 days of daily archives — enough for incident post-mortems
maxFileSize 100MB Only used with SizeAndTimeBasedRollingPolicy
totalSizeCap 5–10GB Hard ceiling — oldest archives deleted first when reached
fileNamePattern .gz use it Logback gzips automatically — typical 10:1 compression on log text
%i in pattern required with size policy Index counter: app.2026-05-29.0.log.gz, app.2026-05-29.1.log.gz …

10. Best Practices

Rule Wrong Right Why
Parameterized logging log.debug("User " + id) log.debug("User {}", id) String concat happens even if DEBUG is disabled. Params are lazy — toString() only called if the message is actually logged.
Never log secrets log.info("Password: {}", pw) log.info("Login attempt: {}", user) Passwords, tokens, credit cards, and SSNs must never appear in log files. Compliance (SOC2, PCI-DSS, GDPR) requires this.
Correlation IDs via MDC log.info("req " + reqId + " done") MDC.put("requestId", id);
log.info("done")		 Manual injection in every log call is error-prone and verbose. MDC does it once per thread.
Correct level for normal flow log.error("User not found") log.warn("User not found") ERROR should mean "a human needs to act". A 404 is handled by design — it is WARN at most.
Log exceptions with cause log.error(e.getMessage()) log.error("Save failed", e) The second arg to SLF4J is the Throwable. Logback then prints the full stack trace. Logging only the message loses the stack.
MDC in filter, not services MDC.put() inside UserService MDC.put() inside a Filter Filters run for every request automatically. Putting MDC setup in business logic is fragile and easily missed.
Always MDC.clear() in finally MDC.put(...); chain.doFilter(...) try { MDC.put(...); } finally { MDC.clear(); } Thread-pool threads are reused. Skipping clear() leaks the previous request's MDC into the next request.
Structured logs in production pattern encoder, plain text LogstashEncoder, JSON output JSON logs are directly queryable in CloudWatch, Datadog, Kibana. Plain text requires slow regex parsing.
