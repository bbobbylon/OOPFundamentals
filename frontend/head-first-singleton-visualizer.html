The Singleton Pattern — the Chocolate Boiler

or, the one object — and the race that quietly makes it two

Chapter 5. The chocolate factory's boiler must never have two instances — a second one while the first holds 500 gallons of boiling chocolate is a very bad day. Singleton guarantees exactly one instance with one global access point. Simple… until two threads call getInstance() at the same time.

The problem

"There is only one" is a promise the naive version breaks.

The version in every tutorial

Single-threaded, it is perfect. Add a second thread and the guarantee evaporates.

Thread A: instance == null ✓ Thread B: instance == null ✓ A: new Singleton() B: new Singleton() ⚠ two instances

Both threads read null before either wrote. Nothing in that code is atomic, and nothing said it had to be.

In Spring, you rarely write this at all. Every @Bean is a singleton within the container by default — one instance, managed, injected where needed. Double-checked locking without volatile — what actually goes wrong?

volatile is a visibility and ordering guarantee, not a hint. Without it the compiler and CPU are free to reorder the write.

The lock does prevent two instances. The bug is subtler and nastier than duplication.

The reference can be published before the constructor finishes, so another thread passes the null check and uses an object whose fields are not initialised yet. That is worse than having two, because it fails intermittently and far from the cause.

Key terms

Private constructor

The part people forget. Without it the class is not a singleton, it is a suggestion.

Lazy vs eager

Build on first use, or build at class load. Eager is simpler and correct; choose lazy only when the object is genuinely expensive and often unused.

Double-checked locking

Check, lock, check again. The outer check skips the lock once initialised; the inner one stops the race. Needs volatile to be correct.

Questions from the back row

Why check twice? Isn't the synchronised block enough on its own?

It is correct on its own — just slow. Every single call would take the lock forever after, for a field that will never be null again. The outer check exists purely so the lock is paid once rather than a million times.

Why is Singleton so often called an anti-pattern?

Because it is global mutable state with a friendly name. It hides dependencies (nothing in a signature says a class reached for it), and it is hard to swap in a test. Dependency injection gives you "one instance" without those two costs, which is why Spring beans are the better default.

Is one instance per JVM, or per application?

Per classloader — which is not always per JVM. In a container with several classloaders you can genuinely get several "singletons", and that surprise has cost people entire afternoons.

🎯 What is the Singleton pattern — and why is the double-checked lock needed in multi-threaded code?

The Singleton pattern ensures a class has only one instance and provides a global access point to it. The naive implementation: private static Singleton instance; public static Singleton getInstance() { if (instance == null) instance = new Singleton(); return instance; }. Works fine single-threaded. Multi-threaded problem: Thread A and Thread B both check instance == null, both find it null, both create a new instance — now you have two. Double-checked locking: if (instance == null) { synchronized(Singleton.class) { if (instance == null) instance = new Singleton(); } }. First check (unsynchronised, fast) avoids locking after initialisation. Inner check (synchronised, slow) prevents double-instantiation when two threads both pass the first check. Requires volatile on the field: private static volatile Singleton instance — ensures the instance is flushed to main memory before it's visible to other threads. Modern Java alternative: use enum: enum Singleton { INSTANCE; } — thread-safe by the JVM, serialisation-safe, and one line of code. Or rely on Spring — every @Bean is a Singleton by default.

Thread-safe implementations

Eager init: private static final Singleton INSTANCE = new Singleton(). Simple, thread-safe (class loading is thread-safe), no lazy loading. Use when the instance is always needed. Bill Pugh (Holder idiom): private static class SingletonHolder { static final Singleton INSTANCE = new Singleton(); } public static Singleton getInstance() { return SingletonHolder.INSTANCE; }. Lazy + thread-safe without synchronisation — the holder class is only loaded when getInstance() is first called. Enum: enum Singleton { INSTANCE; void doThing() { ... } }. JVM guarantees one instance, even during serialisation/deserialisation.

Spring Singletons

Every @Component, @Service, @Repository, @Controller is a Singleton bean by default — one instance per ApplicationContext. Spring manages the lifecycle: creates it once, reuses it for all requests. You don't write the Singleton pattern manually — Spring handles it. But you must be careful: singleton beans are shared across all threads. If a bean has mutable state (a counter, a HashMap), you need thread safety. @RequestScope: one instance per HTTP request. @SessionScope: one instance per user session. @Prototype: new instance every time — anti-Singleton.

When NOT to use Singleton

Singleton is sometimes called an anti-pattern because: global state makes testing hard (tests share state), it couples code to the concrete class (no easy substitution in tests), and it hides dependencies (callers don't declare the Singleton as a parameter — they reach for it globally). In modern code: use dependency injection instead. Instead of Singleton.getInstance().doThing(), inject the class: class MyService { MyService(ThingThatShouldBeSingleton t) { ... } }. Spring's DI makes this trivial and the injection framework handles the single-instance guarantee.

In CIAM / Spring Boot: Every Spring bean is a managed Singleton: JwtService, UserService, PingClient, UserRepository — all single instances shared across all HTTP request threads. Because they're singletons, they must be stateless (or use thread-safe state). JwtService holds a cached JWKS (JSON Web Key Set) for JWT signature verification — singleton with a cached key set. ConcurrentHashMap<String, JWKSet> jwksCache — thread-safe because ConcurrentHashMap handles concurrent access. Never hold request-specific data in a singleton — it would leak between requests. Use ThreadLocal (SecurityContextHolder) or method parameters instead.

Act 1 — why not a global variable?

You could make a global ChocolateBoiler. But a global is eagerly created at startup whether or not you ever use it, and — crucially — nothing stops anyone from calling new ChocolateBoiler() again. Singleton makes a second instance impossible by hiding the constructor.

class ChocolateBoiler {
  private ChocolateBoiler() { }   // private — no outside "new"
  private static ChocolateBoiler instance;
}
Brain Power. A private constructor looks like a contradiction — how do you ever create the object? The trick: the class creates itself, from inside, in a static method. Only ChocolateBoiler's own code can call its private constructor.

Act 2 — the classic (lazy) Singleton

public static ChocolateBoiler getInstance() {
  if (instance == null) {        // first call only
    instance = new ChocolateBoiler();
  }
  return instance;          // every later call returns the SAME object
}

"Lazy" = the instance isn't built until the first getInstance(). Great for an object that's expensive and maybe never needed. In a single-threaded program this is perfect.

Act 3 — two threads, two boilers

Add threads and the lazy version breaks. Thread A checks instance == null (true) and — before it runs new — Thread B checks the same field (still null, true). Now both create a boiler. The hero's scene ③ animates exactly this interleaving.

Q: How often does that actually happen?

A: Rarely — which is what makes it vicious. It only triggers when two threads hit the null window simultaneously, so it passes every test and then corrupts production once a week. "Rare" is not "safe."

The four fixes

1 · synchronize getInstance()

public static synchronized ChocolateBoiler getInstance() {
  if (instance == null) instance = new ChocolateBoiler();
  return instance;
}

Correct, but locks on every call — slow if getInstance() is hot.

2 · eager initialization

private static ChocolateBoiler instance =
    new ChocolateBoiler();  // JVM builds it once, safely

Thread-safe for free. Use it when the object is cheap or always needed.

3 · double-checked locking (volatile)

private static volatile ChocolateBoiler instance;
if (instance == null) synchronized(...) {
  if (instance == null) instance = new ...;
}

Locks only on first creation. volatile is mandatory.

4 · the enum Singleton (preferred)

enum ChocolateBoiler { INSTANCE;
  void fill() { ... }
}

Thread-safe, lazy, and immune to reflection & serialization attacks. Josh Bloch's recommended way.

The Singleton Pattern, defined

The Singleton Pattern ensures a class has only one instance, and provides a global point of access to it.
Reality check. Singleton is the most overused (and abused) pattern — a global in a nicer suit, and hard to unit-test because of the hidden static state. In modern apps, prefer letting a DI container own the single instance: a Spring @Component is singleton-scoped by default, and Angular's providedIn: 'root' service is one instance per app — same guarantee, testable, no static. Singleton in the wild — let the DI container own it

In modern application code you rarely write a Singleton from scratch. Spring beans are singleton-scoped by default; Angular root-level services are one instance per app. Same guarantee — one instance — managed by a container you can swap for a mock in tests.

Spring — @Component is singleton by default

@Component  // one instance per ApplicationContext
public class BoilerService {
  // injected anywhere with @Autowired or constructor
}
// need a fresh instance per call? @Scope("prototype")

Angular — providedIn: 'root' service

@Injectable({ providedIn: 'root' })
export class BoilerService {
  // Angular creates exactly one at root level
  // swap with TestBed.inject() in tests
}
Classification — Creational patternSingleton controls how a class is instantiated, not what it does. Use it for objects that are expensive to create, must be shared, and have no per-caller state. For anything you need to test in isolation, prefer DI over a static accessor.

Why the static Singleton is a testing trap

The static instance survives between test methods in the same JVM run. Tests that run in the wrong order fail unpredictably — the classic "passes in isolation, fails in the suite" mystery:

void testFill() {
  ChocolateBoiler.getInstance().fill();   // sets full=true
}
void testFillAgain() {
  // static instance still full from testFill!
  ChocolateBoiler.getInstance().fill();   // throws "already full"
}
The DI fix. Inject BoilerService as a constructor parameter instead of accessing the static field. In tests, pass a @Mock — created fresh per test, isolated by default. Same one-instance-per-container guarantee, zero shared static state, full testability.
