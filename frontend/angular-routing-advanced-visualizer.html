Advanced Routing

Guards, resolvers, router events, named outlets, scroll restoration, query params, and the full navigation lifecycle — all in one place.

🧭 What happens during an Angular route navigation — step by step?

Click a routerLink or call router.navigate() and Angular runs a precise 10-step pipeline before the new component renders. Understanding it explains why guards run in a set order, why resolvers block rendering, why query params survive navigation, and why programmatic navigation sometimes surprises you. Each step emits a RouterEvent — subscribe to router.events to observe the whole lifecycle for analytics, loading bars, and debugging.

  • Order: NavigationStart → URL match → canMatch → canActivate(Child) → resolvers → lazy chunk → canDeactivate → activate → NavigationEnd.
  • Any guard returning false/UrlTree or any error cancels the navigation (a NavigationCancel/Error event).
  • Resolvers run before activation, so the component renders with data already in hand (no loading flash).
  • Query params + fragments survive navigation; queryParamsHandling: 'merge'|'preserve' controls how.
  • Subscribing to router.events powers a global loading indicator, route analytics, and slow-resolver debugging.

Navigation pipeline

1 NavigationStart · 2 URL match · 3 canMatch · 4 canActivate · 5 canActivateChild · 6 resolvers · 7 lazy download · 8 canDeactivate (old) · 9 activate · 10 NavigationEnd. Any false/error cancels it.

Query params + fragments

router.navigate(['/users'], { queryParams: { page: 1, filter: 'active' } }) → /users?page=1&filter=active. Read via route.queryParams; persist with queryParamsHandling: 'merge' — ideal for shareable filtered views.

Router events for analytics

router.events.pipe(filter(e => e instanceof NavigationEnd)).subscribe(e => analytics.track(e.url)). Drive a loading bar off NavigationStart; log ResolveStart → ResolveEnd to catch slow resolvers blocking render.

In CIAM:the user-management table keeps all state in the URL — /admin/users?page=2&size=20&sort=email&filter=active — so links are shareable and back/forward works. Subscribe to NavigationEnd to reset the loading signal and dismiss error toasts; time NavigationStart→NavigationEnd to spot slow resolvers.

Route Guards — the four interfaces

Guards are hooks that run during navigation. They let you allow, block, or redirect navigations based on conditions like auth state, unsaved changes, or feature flags.

GuardRuns whenReturn value meaningCommon use
CanActivate / CanActivateFnBefore a route's component is activatedtrue=allow, false=block, UrlTree=redirectAuth check — redirect to /login
CanActivateChildBefore any child route activatesSame as CanActivateProtect entire feature subtree
CanDeactivateBefore leaving the current routetrue=allow leave, false=stay"Unsaved changes" dialogs
CanMatchBefore deciding if a route matches at alltrue=consider this route, false=skip to nextFeature flags, role-based routes
ResolveBefore component activates (fetches data)Observable/Promise that resolves the dataPre-fetch required data

Functional guards (Angular 14+) vs class-based — migration

Old style: class-based (still works)

// auth.guard.ts
@Injectable({ providedIn: 'root' })
export class AuthGuard
    implements CanActivate {
  constructor(private auth: AuthService,
              private router: Router) {}

  canActivate(
    route: ActivatedRouteSnapshot,
    state: RouterStateSnapshot
  ): boolean | UrlTree {
    return this.auth.isLoggedIn
      ? true
      : this.router.createUrlTree(['/login']);
  }
}

// In routes:
{ path: 'dashboard',
  canActivate: [AuthGuard], ... }

New style: functional (Angular 14+, recommended)

// auth.guard.ts
export const authGuard: CanActivateFn =
  (route, state) => {
    const auth   = inject(AuthService);
    const router = inject(Router);

    return auth.isLoggedIn()
      ? true
      : router.createUrlTree(['/login'], {
          queryParams: { returnUrl: state.url }
        });
  };

// In routes:
{ path: 'dashboard',
  canActivate: [authGuard], ... }
Why functional guards are better: no class boilerplate, no decorator, no DI registration. inject() works at the call site. Easier to compose — combine multiple guard functions with && or as an array.

CanActivate — AuthGuard pattern

The most common guard: check if the user is authenticated. If not, redirect to the login page, preserving the intended URL so you can redirect back after login.

Complete AuthGuard example

// auth.service.ts
@Injectable({ providedIn: 'root' })
export class AuthService {
  private _loggedIn = signal(false);
  isLoggedIn = this._loggedIn.asReadonly();

  login(token: string) {
    localStorage.setItem('token', token);
    this._loggedIn.set(true);
  }
  logout() {
    localStorage.removeItem('token');
    this._loggedIn.set(false);
  }
  checkStoredToken() {
    this._loggedIn.set(!!localStorage.getItem('token'));
  }
}
// auth.guard.ts — functional guard
import { inject } from '@angular/core';
import { CanActivateFn, Router } from '@angular/router';

export const authGuard: CanActivateFn = (route, state) => {
  const auth   = inject(AuthService);
  const router = inject(Router);

  if (auth.isLoggedIn()) {
    return true;                               // ✅ allow navigation
  }

  // ↓ redirect to /login, preserve the URL they tried to visit
  return router.createUrlTree(['/login'], {
    queryParams: { returnUrl: state.url }
  });
};

// Role-based guard — check user role
export const adminGuard: CanActivateFn = (route, state) => {
  const auth = inject(AuthService);
  const router = inject(Router);

  return auth.hasRole('admin')
    ? true
    : router.createUrlTree(['/forbidden']);
};
// app.routes.ts — apply guards to routes
export const routes: Routes = [
  { path: '',          component: HomeComponent },
  { path: 'login',     component: LoginComponent },
  {
    path: 'dashboard',
    canActivate: [authGuard],           // ← apply to this route
    component: DashboardComponent
  },
  {
    path: 'admin',
    canActivate: [authGuard, adminGuard], // ← both must pass (AND logic)
    component: AdminComponent
  },
  {
    path: 'settings',
    canActivateChild: [authGuard],       // ← protects ALL children
    children: [
      { path: 'profile', component: ProfileComponent },
      { path: 'security', component: SecurityComponent }
    ]
  }
];

CanMatch — guard before route matching

CanMatch runs even earlier than CanActivate — it decides whether a route is even considered in the matching algorithm. This lets you have multiple routes at the same path that render different components based on conditions.

// Two routes for the same path — different components based on feature flag
{ path: 'checkout',
  canMatch: [newCheckoutGuard],    // only matches if new checkout is enabled
  component: NewCheckoutComponent },
{ path: 'checkout',
  component: LegacyCheckoutComponent  // fallback if first route didn't match
}

// guard
export const newCheckoutGuard: CanMatchFn = () =>
  inject(FeatureFlagService).isEnabled('new-checkout');

CanDeactivate — "Unsaved Changes" dialogs

CanDeactivate runs when the user tries to navigate away from the current route. Return false (or a Promise/Observable of false) to block navigation.

Pattern 1: Interface-based (generic)

// can-deactivate.guard.ts
export interface CanComponentDeactivate {
  canDeactivate(): boolean | Observable<boolean> | Promise<boolean>;
}

export const unsavedChangesGuard: CanDeactivateFn<CanComponentDeactivate>
  = (component) => component.canDeactivate();
// edit-profile.component.ts
export class EditProfileComponent
    implements CanComponentDeactivate {

  isDirty = signal(false);

  canDeactivate(): boolean | Observable<boolean> {
    if (!this.isDirty()) return true;

    // Show a dialog, return its result as an Observable
    return this.dialogService
      .confirm('You have unsaved changes. Leave anyway?');
  }
}

// app.routes.ts
{ path: 'profile/edit',
  component: EditProfileComponent,
  canDeactivate: [unsavedChangesGuard] }

Pattern 2: Inline functional guard

// Simple version — just a browser confirm dialog
{ path: 'editor',
  component: EditorComponent,
  canDeactivate: [
    (component: EditorComponent) =>
      component.isSaved || confirm('Leave without saving?')
  ]
}
Note: CanDeactivate only works for in-app navigation (RouterLink / Router.navigate). It does NOT intercept browser back button or closing the tab — for that you need the beforeunload DOM event separately.

Route Resolvers — fetch data before activating

A resolver runs after guards pass but before the component activates. The component receives pre-fetched data via route.snapshot.data — no loading state needed in the component itself.

Functional resolver (Angular 14+ — preferred)

// product.resolver.ts
import { ResolveFn } from '@angular/router';

export const productResolver: ResolveFn<Product> =
  (route, state) => {
    const productService = inject(ProductService);
    const id = route.paramMap.get('id')!;
    return productService.getById(id);   // Observable<Product>
    // Angular subscribes, waits for completion, then activates
  };
// app.routes.ts — attach resolver to the route
{ path: 'products/:id',
  component: ProductDetailComponent,
  resolve: {
    product: productResolver   // key name used in component
  }
}
// product-detail.component.ts — read resolved data
export class ProductDetailComponent {
  private route = inject(ActivatedRoute);

  // Snapshot — available immediately, no async
  product = this.route.snapshot.data['product'] as Product;

  // Or as an observable (updates if resolver re-runs on same route)
  product$ = this.route.data.pipe(map(d => d['product']));
}
Resolver vs Component loading state: resolvers make the transition "slower" but the component "instant". Choose resolvers when you MUST have data for the initial render. For optional/progressive data, just load in ngOnInit with a loading spinner.

Class-based resolver (legacy — still works)

@Injectable({ providedIn: 'root' })
export class ProductResolver implements Resolve<Product> {
  constructor(private ps: ProductService) {}

  resolve(route: ActivatedRouteSnapshot): Observable<Product> {
    return this.ps.getById(route.params['id']);
  }
}

Multiple resolvers on one route

{ path: 'products/:id',
  component: ProductDetailComponent,
  resolve: {
    product:  productResolver,    // runs in PARALLEL
    reviews:  reviewsResolver,    // runs in PARALLEL
    related:  relatedResolver,    // runs in PARALLEL
  }
}
// Angular runs all resolvers in parallel and waits for ALL to complete

Router Events Lifecycle

Every navigation emits a sequence of events. Subscribe to router.events to build loading indicators, analytics tracking, scroll management, and more.

Animated event pipeline — step through a full navigation

NavigationStart
Navigation begins. Show global loading indicator here.
RouteConfigLoadStart
Lazy-loaded route module begins fetching. (Only for lazy routes.)
RouteConfigLoadEnd
Lazy route module loaded. Proceeds to recognition.
RoutesRecognized
URL matched to a route config. Route tree built.
GuardsCheckStart
All guards begin executing (CanMatch, CanActivate, CanActivateChild).
ChildActivationStart
Guards passed. Child routes begin activating.
ActivationStart
A specific route component is about to be activated.
GuardsCheckEnd
All guards completed. shouldActivate=true means proceed.
ResolveStart
Resolvers begin executing in parallel.
ResolveEnd
All resolvers completed. Data available in route.snapshot.data.
ActivationEnd
Component fully activated. Component is in the DOM.
NavigationEnd
Navigation complete. Hide loading indicator here. URL updated.
NavigationCancel (if guard blocked)
A guard returned false or a UrlTree redirect. Navigation aborted.
NavigationError (if error occurred)
Resolver threw, component failed to load, etc. Show error state.

Common usage patterns

// Global loading indicator
export class AppComponent {
  loading = signal(false);
  private router = inject(Router);

  constructor() {
    this.router.events.pipe(
      filter(e => e instanceof NavigationStart
                || e instanceof NavigationEnd
                || e instanceof NavigationCancel
                || e instanceof NavigationError)
    ).subscribe(event => {
      this.loading.set(event instanceof NavigationStart);
    });
  }
}

<!-- template -->
<app-progress-bar *ngIf="loading()" />
// Page title updates on navigation
export class AppComponent {
  constructor() {
    inject(Router).events
      .pipe(filter(e => e instanceof NavigationEnd))
      .subscribe(() => {
        const title = inject(ActivatedRoute)
          .firstChild?.snapshot.data['title'] ?? 'My App';
        inject(Title).setTitle(title);
      });
  }
}

Named Router Outlets — secondary outlets

Angular supports multiple <router-outlet> elements in one template. Secondary outlets have names and are navigated independently from the primary outlet. The URL encodes both outlet states simultaneously.

Setup: add a named outlet in the template

<!-- app.component.html -->
<nav>...</nav>

<div class="layout">
  <main>
    <router-outlet></router-outlet>          <!-- primary outlet -->
  </main>

  <aside>
    <router-outlet name="sidebar"></router-outlet>  <!-- secondary -->
  </aside>
</div>

Routes for secondary outlets

export const routes: Routes = [
  { path: 'home',    component: HomeComponent },
  { path: 'products', component: ProductsComponent },

  // Secondary outlet routes — must specify outlet name
  { path: 'help',   outlet: 'sidebar', component: HelpComponent },
  { path: 'chat',   outlet: 'sidebar', component: ChatComponent },
];

Navigating to a secondary outlet

<!-- RouterLink -->
<a [routerLink]="[{ outlets: { sidebar: ['help'] } }]">
  Open Help
</a>

<!-- Navigate primary AND secondary at the same time -->
<a [routerLink]="[{ outlets: { primary: ['products'], sidebar: ['chat'] } }]">
  Products + Chat
</a>

// Programmatic navigation
router.navigate([{ outlets: { sidebar: ['help'] } }]);

// Close a secondary outlet (set to null)
router.navigate([{ outlets: { sidebar: null } }]);

What the URL looks like

http://localhost:4200 /products (sidebar:chat)

Secondary outlets are useful for: persistent sidebars, modals, notification panels, chat windows — anything that needs its own navigation state independent of the main view.

Query Params, Route Params, and Fragments

Three ways to carry data in a URL — each with a different scope and lifecycle.

TypeURL formatDefined in route?When to use
Route params/products/:id → /products/42Yes — part of pathRequired data that identifies the resource
Query params/search?q=shoes&page=2No — appendedOptional filter/pagination that doesn't change the route
Fragment/docs#getting-startedNoIn-page anchor / section links
State (history)Not visible in URLNoTransient data between routes (e.g. from-page breadcrumb)

Query params — passing and preserving

<!-- Pass query params via RouterLink -->
<a [routerLink]="['/search']"
   [queryParams]="{ q: 'shoes', page: 1, sort: 'price' }">
  Search shoes
</a>
<!-- URL: /search?q=shoes&page=1&sort=price -->

<!-- Preserve existing query params when navigating -->
<a [routerLink]="['/search']"
   queryParamsHandling="preserve">
  Next page (keeps all current params)
</a>

<!-- Merge — keeps existing, merges in new ones -->
<a [routerLink]="['/search']"
   [queryParams]="{ page: currentPage + 1 }"
   queryParamsHandling="merge">
  Next page (merges page param)
</a>
// Reading query params in a component
export class SearchComponent {
  private route = inject(ActivatedRoute);

  // snapshot — current value, doesn't update
  query = this.route.snapshot.queryParams['q'];

  // observable — updates when params change (same component, new params)
  query$ = this.route.queryParams.pipe(map(p => p['q']));

  // Signal-based (Angular 17.2+)
  querySignal = toSignal(this.route.queryParams.pipe(map(p => p['q'])));
}

Fragments

<!-- Navigate with a fragment -->
<a [routerLink]="['/docs']" fragment="getting-started">
  Getting Started
</a>
<!-- URL: /docs#getting-started -->

// Programmatic
router.navigate(['/docs'], { fragment: 'getting-started' });

// Read it back
route.fragment.subscribe(frag => document.getElementById(frag)?.scrollIntoView());

Router state — passing invisible data

// Navigate with hidden state
router.navigate(['/checkout'], {
  state: { orderId: 'ORD-123', fromCart: true }
});

// Read it in the target component
const nav = router.getCurrentNavigation();
const state = nav?.extras.state as { orderId: string; fromCart: boolean };

// Or via history (after navigation completes)
const state = history.state;

RouterLink, routerLinkActive, relativeTo, Scroll, Wildcards

RouterLink and routerLinkActive

<!-- Basic navigation -->
<a routerLink="/products">Products</a>

<!-- With params -->
<a [routerLink]="['/products', product.id]">{{ product.name }}</a>

<!-- Active class — applies 'active-link' when URL matches -->
<a routerLink="/home"
   routerLinkActive="active-link"
   [routerLinkActiveOptions]="{ exact: true }">Home</a>
<!-- exact: true prevents /home from matching on /home/settings -->

<!-- Relative navigation (inside a child route) -->
constructor(private router: Router, private route: ActivatedRoute) {}

goToEdit() {
  this.router.navigate(['edit'], { relativeTo: this.route });
  // Navigates to: current-path/edit
}

Scroll restoration

// app.config.ts — enable scroll restoration globally
export const appConfig: ApplicationConfig = {
  providers: [
    provideRouter(routes,
      withInMemoryScrolling({
        scrollPositionRestoration: 'enabled',  // restore scroll on back/forward
        anchorScrolling: 'enabled'              // scroll to #fragment targets
      }),
      withRouterConfig({
        onSameUrlNavigation: 'reload'           // optional: re-run guards on same URL
      })
    )
  ]
};

Wildcard routes and 404 handling

export const routes: Routes = [
  { path: '',          redirectTo: '/home', pathMatch: 'full' },
  { path: 'home',      component: HomeComponent },
  { path: 'products',  component: ProductsComponent },

  // Catch-all — MUST be last
  { path: '**', component: NotFoundComponent }
];

// Or redirect unknowns to home
{ path: '**', redirectTo: '/home' }
Order matters: Angular matches routes from top to bottom. Put ** last. If it comes before other routes, it swallows all navigations.

Lazy loading with CanMatch

// Lazy-load a feature route ONLY if the user has a specific role
{ path: 'admin',
  canMatch: [adminRoleGuard],
  loadChildren: () => import('./admin/admin.routes').then(m => m.adminRoutes)
}

// If canMatch returns false, Angular NEVER downloads the chunk.
// Perfect for role-based lazy loading — non-admins don't download admin code.
