LLM API Integration

Every AI feature you build talks to an LLM provider over plain HTTPS — the same request/response mechanics as any REST API, plus three things that are new: streaming tokens, paying per-token, and providers that rate-limit and fail more often than your average backend.

🔌 What is "LLM API integration" — and why isn't it just another REST call?

Calling OpenAI, Anthropic, or any hosted model provider is, at the wire level, a POST request with a JSON body and a Bearer token — nothing exotic. What's different from a typical CRUD API: responses can take seconds to generate (so you usually stream tokens back instead of waiting for the whole thing), every request and response costs real money billed per token, the API is stateless (you resend the whole conversation every turn), and providers rate-limit aggressively — so retry-with-backoff isn't optional polish, it's required for a production integration.

  • It's just HTTP. POST a JSON body of messages, get JSON (or a stream of JSON chunks) back.
  • Streaming = perceived speed. Server-Sent Events deliver tokens as they're generated, not after.
  • Stateless & token-metered. You resend history every call; every token in and out costs money.
  • Rate limits are normal. 429s happen in production — exponential backoff + jitter is required, not optional.

A minimal request

POST https://api.openai.com/v1/chat/completions Authorization: Bearer sk-... Content-Type: application/json { "model": "gpt-4o", "messages": [ {"role":"system","content":"You are concise."}, {"role":"user","content":"What is a closure?"} ], "temperature": 0.7, "max_tokens": 300 }

Streaming with fetch()

const res = await fetch(url, { method: "POST", headers, body: JSON.stringify({...body, stream: true}) }); const reader = res.body.getReader(); const decoder = new TextDecoder(); while (true) { const {done, value} = await reader.read(); if (done) break; const chunk = decoder.decode(value); // parse "data: {...}\n\n" lines render(chunk); }

Never call from the browser

// ❌ Browser JS → OpenAI directly // exposes your API key in devtools/network tab // within minutes it's scraped and abused // ✅ Browser → your backend → LLM provider // key lives ONLY in server env vars // backend can also enforce per-user // rate limits, auth, and cost caps

Vs. a typical internal REST call: Compare this to Spring's RestClient — same fluent-request, parse-response shape, but an LLM call trades a <50ms round trip for a multi-second one, trades a fixed response shape for a token stream, and trades "retry is a nice-to-have" for "retry is required because 429s are routine." If you've built a resilient internal REST client with timeouts and backoff already, you have 80% of what you need here.

or, the 200 OK that lied to you three seconds into the response

The problem

Your callWithRetry function up above checks res.status once, right after the headers come back. For a streaming call, that check has already finished its job before the failure you actually care about even happens.

The response says 200 OK. The answer on screen is half a sentence, forever.

You wire up streaming exactly like Section 3 above: open the connection, get back HTTP 200, start reading data: chunks and appending delta.content to the UI. Three seconds in, on a long generation, the provider hits an internal overload, trips a content filter, or the connection drops — and the stream just stops. No exception. No non-2xx status you can catch. res.ok was true the entire time, because it was checked once, at the start, before any of this happened.

That's the trap: HTTP status codes describe the response you got when you FIRST connected. A stream is a promise to keep sending you more — and once that promise is made, the status line can't be un-sent to tell you it broke. Real streaming APIs handle a mid-stream failure by sending an in-band signal instead: an error-typed SSE event, a finish_reason other than "stop", or simply closing the connection without ever sending [DONE]. If your client only ever inspects res.status, none of those are visible to it.

connection opened ✓ 200 OK received ✓ retry logic never triggers, because nothing ever returned non-2xx ⚠

You built retry logic for the failure that happens before the stream starts. The failure that actually bit you happens after.

Treat the stream itself as the thing that can fail, not just the handshake
Check res.ok once, for connection-level failures only ↓ this still matters — a 429 or 401 arrives as a real status code before any chunk is sent, and your existing retry-with-backoff handles that correctly Parse every chunk for an in-band error, not just for content ↓ look for an error field or event type on each SSE message, the same way you already look for delta.content Track whether you ever received a clean terminator ([DONE] / a stop finish_reason) ↓ a stream that just goes silent without one is a failure, even though nothing ever threw and the status was 200 the whole time
The one-sentence rule. An HTTP status code is a snapshot taken at connection time, not a running health check — the moment a response becomes a stream, the only place left to report a failure is inside the stream itself.
Think of a streaming response like a phone call, not a letter: the letter either arrives or it doesn't (that's your status code), but the call can be answered fine and still drop mid-sentence — and the only way to know is to keep listening, not to check that someone picked up.

The mechanism

Follow one streaming request from connection to its silent death and see exactly where a status-code check would have to be looking, and isn't.

  1. Client opens the connection, provider responds 200 OK with headersconnect
  2. res.ok is checked once here — this is the only status-code check that will ever runhandshake check
  3. Chunks of delta.content stream in and get appended to the rendered texthappy path
  4. Three seconds in, the provider's backend hits an overload conditionfailure occurs
  5. The provider sends an error-typed event on the SAME open connection — the status line can't change nowin-band signal
  6. A client only watching res.status sees nothing wrong; a client parsing every chunk sees the error eventdetection gap

Step 5 is the part that trips people up: the failure is real and the provider DID report it — just not in the one place (res.status) that every non-streaming error-handling habit trained you to look.

Connecting server responds → 200 OK, status check passes once
Streaming each chunk arrives → append delta.content, OR receive an in-band error event
Terminated [DONE] received → success — but silence with no [DONE] means failure too

The status code only ever exists in the "Connecting" state. Everything that can go wrong in "Streaming" has to be detected by watching the stream's content, because there's no HTTP status left to check — the response already committed to 200 and can't take it back.

Retrying a genuinely successful 200 response would just re-run a fine request for no reason — the problem isn't that 200 needs retry logic, it's that a 200 doesn't cover the whole lifetime of a stream.

That's true for a normal request/response call, but not for a stream — the 200 only certifies the connection opened, not that every chunk that follows will complete cleanly.

Where you have seen this before

"The connection succeeded" and "the thing I asked for actually finished" are two different claims in more places than just LLM streaming.

A WebSocket that stays open after the backend dies

The TCP handshake and the WebSocket upgrade both succeeded — the connection is technically "up." That tells you nothing about whether the process on the other end is still alive and sending real messages versus silently hung.

a connected socket isn't the same as a healthy one

A 202 Accepted from an async job endpoint

Kick off a long-running export job and the API correctly returns 202 Accepted — meaning "I received your request," not "your job succeeded." You still have to poll a status endpoint or listen for a webhook to learn how the job actually ended.

accepted is not the same as completed

A SAML/OIDC redirect that lands on your callback URL

The browser successfully redirecting back to your /callback route just means the identity provider sent something — it says nothing about whether the assertion or code inside that redirect is valid until you actually validate the signature and claims.

arriving at the endpoint isn't the same as passing validation

The one new sentence this block adds: once a response starts streaming, HTTP status can no longer report a failure — you have to watch the chunks themselves for an in-band error or a missing terminator, because the status line already committed to 200 and it isn't coming back to tell you otherwise.

1. The Request Shape

Nearly every chat-completions API — OpenAI, Anthropic, Azure OpenAI, local servers speaking the OpenAI-compatible format — shares the same four ingredients.

model
which model, e.g. "gpt-4o" / "claude-sonnet-5"
messages[]
role: system/user/assistant + content
temperature
0 = deterministic, 1+ = creative
max_tokens
hard cap on response length (and cost)
// The system message sets behavior; it isn't shown to the end user
{
  "model": "gpt-4o",
  "messages": [
    {"role": "system", "content": "You are a terse Python tutor."},
    {"role": "user", "content": "Explain list comprehensions."}
  ],
  "temperature": 0.3,
  "max_tokens": 400
}
The system message is the single highest-leverage lever you control: it sets tone, format, and constraints for every reply in the conversation. Put stable instructions there, not repeated in every user message.

2. API Key Security

An LLM API key is a bearer credential billed per token — leak one and someone else spends your money. The rule is absolute: the key never reaches the browser.

❌ Wrong: browser calls the provider directly

// api key baked into client JS or fetched at runtime
const res = await fetch("https://api.openai.com/v1/...", {
  headers: { Authorization: `Bearer ${apiKey}` }
});
// key is visible in devtools → Network tab → Headers
// scraped within minutes by bots that crawl public JS bundles

✅ Right: browser calls YOUR backend

const res = await fetch("/api/chat", {
  method: "POST",
  body: JSON.stringify({ message: userInput })
});
// your backend (holding the key in an env var)
// forwards the request to the LLM provider server-side
// and can enforce per-user rate limits + cost caps

3. Streaming Responses (SSE)

A full response can take several seconds to generate. Streaming sends each token as it's produced, over a long-lived HTTP connection using the Server-Sent Events format — dramatically better perceived latency even though total time is the same.

// Raw SSE wire format — one JSON chunk per "data:" line
data: {"choices":[{"delta":{"content":"List"}}]}

data: {"choices":[{"delta":{"content":" comprehensions"}}]}

data: {"choices":[{"delta":{"content":" let you"}}]}

data: [DONE]
You must accumulate delta.content fragments yourself — each chunk is a partial update, not a full message. Concatenate them client-side to build the rendered text as it streams in.

4. Context Window & Token Costs

The API is stateless — the provider has no memory between calls. Every turn, you resend the entire conversation history, and you pay for every token you send AND receive.

input tokensevery token in system + all prior messages you resendbilled per call, every turn
output tokensevery token the model generates backusually priced higher than input
context windowmax tokens (in + out) a model can handle at oncee.g. 128k, 200k tokens
unbounded historya long chat resent every turn grows cost quadraticallytruncate / summarize old turns
Mitigation strategies: cap history to the last N turns, summarize older turns into a compact system note, or (forward pointer) use prompt caching so a provider can reuse the unchanged prefix of a long system prompt across calls instead of re-processing it every time.

5. Error Handling & Resilience

LLM providers fail and rate-limit far more often than a typical internal service. A production integration treats retry logic as a requirement, not an edge case.

429rate limited — read Retry-After, back off
500/503provider overloaded — retry with backoff
timeoutgeneration is slow — set a generous but finite timeout
400bad request — don't retry, fix the payload
async function callWithRetry(body, attempt = 1) {
  const res = await fetch(url, { method: "POST", headers, body });
  if (res.status === 429 && attempt <= 5) {
    const retryAfter = Number(res.headers.get("retry-after")) || (2 ** attempt);
    const jitter = Math.random() * 0.3 * retryAfter;
    await sleep((retryAfter + jitter) * 1000);
    return callWithRetry(body, attempt + 1);
  }
  if (!res.ok) throw new Error(`LLM call failed: ${res.status}`);
  return res.json();
}
