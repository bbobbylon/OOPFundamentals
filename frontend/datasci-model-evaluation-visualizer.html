Model Evaluation — Precision, Recall, F1, ROC-AUC & Cross-Validation

Accuracy alone lies to you on real-world data. The confusion matrix, precision/recall, F1, ROC-AUC, and k-fold cross-validation — the actual toolkit for knowing whether a model works.

📐 What is model evaluation — and why does "accuracy" lie to you?

Model evaluation is the discipline of measuring whether a trained model is actually good — and the single most important lesson is that accuracy alone can be dangerously misleading. On an imbalanced dataset (99% of transactions are legitimate, 1% are fraud), a model that predicts "not fraud" for every single transaction scores 99% accuracy while catching exactly zero fraud. That's why real evaluation starts with the confusion matrix — the four raw counts (true positive, true negative, false positive, false negative) every other metric is built from — and derives precision (how many of my positive predictions were right?) and recall (how many actual positives did I catch?), which trade off against each other as you move the decision threshold. ROC-AUC summarizes that tradeoff across every threshold into one number, and k-fold cross-validation makes sure your score isn't just a lucky (or unlucky) single train/test split.

  • Accuracy hides failure on imbalanced data — a dumb "always predict negative" model can score 99%+.
  • Precision = of what I flagged positive, how much was real? Recall = of what was real, how much did I catch?
  • Precision and recall trade off against each other by moving the classification threshold — F1 balances both into one number.
  • ROC-AUC is threshold-independent; k-fold CV protects you from trusting one lucky data split.

Confusion matrix cheat sheet

# Binary classification, 4 outcomes: # TP — predicted positive, WAS positive # TN — predicted negative, WAS negative # FP — predicted positive, was actually negative # (a "false alarm") # FN — predicted negative, was actually positive # (a "miss") from sklearn.metrics import confusion_matrix tn, fp, fn, tp = confusion_matrix(y_true, y_pred).ravel() # Every metric below is arithmetic on these 4 ints.

Precision vs recall — when each matters

precision = TP / (TP + FP) # "Of what I called positive, how much was real?" # High precision matters when false POSITIVES # are costly — e.g. blocking a real customer's # legit transaction as "fraud". recall = TP / (TP + FN) # "Of what was real, how much did I catch?" # High recall matters when false NEGATIVES # are costly — e.g. missing actual fraud, # missing an actual cancer diagnosis.

k-fold cross-validation

from sklearn.model_selection import cross_val_score scores = cross_val_score(model, X, y, cv=5) # Splits data into 5 folds. Trains on 4, # validates on the 5th — 5 times, rotating # which fold is held out. Averages the 5 scores. print(scores.mean(), scores.std()) # A robust estimate, not one lucky split.

CIAM angle: An adaptive-auth risk engine deciding "trigger step-up MFA or not" is exactly this precision/recall tradeoff. A low risk-score threshold favors recall — it catches more real account-takeover attempts, but forces more legitimate users through extra MFA friction (more false positives, worse UX). A high threshold favors precision — fewer legitimate users get bothered, but more real attacks slip through as false negatives. Tuning that threshold is a business risk-tolerance decision, not a data-science one — the same lever Ping/Entra adaptive-auth policies expose as a risk-score cutoff.

or, why a 0.93 ROC-AUC didn't stop your reviewers from drowning in false alarms

The problem

You can post a genuinely excellent ROC-AUC and still ship a model that turns every fraud-review queue into 93% noise.

0.93 AUC, 7% precision, the exact same model

You've got 10,000 transactions, 100 of them real fraud (1%). You train a classifier, check roc_auc_score(y_test, y_proba), and get 0.93 — comfortably "good" on the usual 0.5=random / 1.0=perfect scale. You pick an operating threshold tuned to catch 70% of the fraud (recall = 0.70), which is the business's stated target.

At that threshold, the confusion matrix comes out TP=70, FN=30, FP=900, TN=9000. Precision = 70/(70+900) ≈ 7.2% — of every 100 transactions your model flags as fraud, roughly 93 are innocent customers getting reviewed or blocked for nothing.

ROC-AUC = 0.93 ✓ ("good" by the textbook scale) recall hit its 70% target ✓ 93 of every 100 flags are false alarms ⚠

The AUC never lied about ranking quality — it just was never answering the question "will my reviewers drown."

Check precision at your actual threshold, not just AUC across all of them
Compute precision_score(y_test, y_pred) at the exact threshold you plan to deploy ↓ AUC averages ranking quality across every possible threshold, including ones you'll never use in production On badly imbalanced data, check a precision-recall curve or average_precision_score alongside ROC-AUC ↓ precision's denominator (TP+FP) is dominated by the tiny positive class, so a PR curve is far more sensitive to false positives than ROC's FPR ever is Report precision AND recall AT the operating threshold you'll actually ship ↓ never AUC alone — it's the only number your reviewers never actually experience
The one-sentence rule. ROC-AUC measures how well a model ranks positives above negatives across every possible threshold, which makes it insensitive to class imbalance in a way that precision — the metric your reviewers actually feel — is not; a great AUC and a terrible precision at your chosen cutoff can both be true about the exact same model.
ROC-AUC is graded on a curve most of your reviewers never took — because most of it describes thresholds you're never going to deploy. Always check precision at the ONE threshold you actually ship.

The mechanism

Walk through why the false-positive rate feeding ROC-AUC stays calm while precision panics, using the SAME 900 false positives both times.

  1. Dataset: 9,900 legitimate transactions, 100 fraud1% positive
  2. Threshold chosen to hit 70% recallbusiness target
  3. Confusion matrix at that threshold: TP=70, FN=30, FP=900, TN=9000the real counts
  4. FPR = FP/(FP+TN) = 900/9900 ≈ 9.1%ROC's x-axis
  5. Precision = TP/(TP+FP) = 70/970 ≈ 7.2%reviewers' reality
  6. Same 900 false positives; FPR reads "mildly elevated," precision reads "mostly noise"same number, two verdicts

The step that matters most is #4 versus #5 — both use the exact same 900 false positives, but FPR divides them by 9,900 (nearly the whole dataset) while precision divides them by 970 (a number close to how many positives even exist). The identical mistake looks almost invisible through one denominator and catastrophic through the other.

900 false positives at your chosen thresholdsame number, judged two different ways
how each metric reacts ↓
Recall (70/100 = 70%) — unaffected, FP isn't even in its formula FPR (900/9900 ≈ 9%) — the surprising reactor: barely moves Precision (70/970 ≈ 7%) — collapses

Recall doesn't even have false positives in its formula, so it's a bystander here. FPR technically reacts, but its enormous denominator — nearly the whole dataset, since negatives vastly outnumber positives — absorbs 900 false positives almost without flinching. Precision, whose denominator is only true-plus-false positives, has nowhere to hide the same 900 — that's the one your reviewers actually experience.

A fraud model reports ROC-AUC = 0.95 on a dataset that's 2% positive. At the threshold your team deploys, the model has 200 false positives and 40 true positives. What does the 0.95 AUC guarantee about precision at THAT threshold?

AUC and precision measure different things and aren't linked by a fixed ratio — AUC summarizes ranking quality across every threshold, while precision is computed at exactly one.

There's no such guarantee in the metric's definition — AUC contains no information about the false-positive COUNT at any specific threshold, which is exactly what precision needs.

Correct. Precision is arithmetic on the confusion matrix at the threshold you actually deploy — 40/(40+200) ≈ 16.7% — and AUC, a threshold-independent ranking summary, has no bearing on that specific number.

Where you have seen this before

A great aggregate score hiding a bad result at the one operating point you actually use shows up everywhere metrics get averaged.

p99 latency hiding behind a good average

A service's mean response time looks great (120ms) while its p99 is 4 seconds — the average is dragged down by the vast majority of fast, boring requests, exactly like FPR gets diluted by the vast majority of true negatives.

the compressed lesson: the summary number and the number your users feel can point in opposite directions

Integration tests that "pass" while the endpoint that matters is broken

A Spring Security test suite covering 50 endpoints reports 98% pass while the ONE endpoint hit 90% of the time in production — say, /login — is the failing 2%. An aggregate pass rate says nothing about whether the endpoint that matters is fine.

the compressed lesson: a pass rate is an average across tests you don't weight by how much you'll actually hit them

An A/B test's overall lift masking a harmed segment

A feature ships because the overall conversion metric improved 3%, while it quietly tanked conversion for mobile users by 15% — the number that shipped it wasn't computed on the population you actually cared about.

the compressed lesson: an aggregate metric can improve while the segment you depend on gets worse

1. The Confusion Matrix — the Foundation of Every Metric

For binary classification, every prediction lands in exactly one of 4 buckets. Every metric on this page is arithmetic performed on these 4 counts — nothing more.

Actual: Positive
Actual: Negative
Predicted: Positive
TPTrue Positive — correctly caught
FPFalse Positive — false alarm
Predicted: Negative
FNFalse Negative — a miss
TNTrue Negative — correctly cleared
from sklearn.metrics import confusion_matrix, classification_report

tn, fp, fn, tp = confusion_matrix(y_true, y_pred).ravel()
print(f"TP={tp} FP={fp} FN={fn} TN={tn}")
# TP=40 FP=10 FN=15 TN=935 — a 1000-row imbalanced dataset
Accuracy on this matrix: (TP+TN)/total = (40+935)/1000 = 97.5% — looks great. But recall = 40/(40+15) = 73% — the model missed over a quarter of the real positives. Accuracy alone would never have told you that.

2. Precision, Recall & F1 — the Tradeoff

Precision and recall answer two different questions, and improving one by moving the classification threshold usually costs you the other.

PrecisionOf everything predicted positive, how much was actually positive?TP / (TP + FP)
RecallOf everything actually positive, how much did I catch?TP / (TP + FN)
F1 ScoreHarmonic mean — balances precision and recall into one number2·P·R / (P + R)
from sklearn.metrics import precision_score, recall_score, f1_score

precision_score(y_true, y_pred)  # 40 / (40+10) = 0.80
recall_score(y_true, y_pred)     # 40 / (40+15) = 0.727
f1_score(y_true, y_pred)         # 2·0.80·0.727 / (0.80+0.727) = 0.762

# Full breakdown per class:
print(classification_report(y_true, y_pred))
There is no single "correct" threshold — it's a business decision. Fraud detection usually favors recall (missing fraud is expensive); spam filtering usually favors precision (flagging a real email as spam is more annoying than one spam email slipping through).

3. ROC-AUC & k-Fold Cross-Validation

Precision/recall/F1 all depend on which threshold you chose. ROC-AUC and cross-validation answer two different, threshold-independent questions.

from sklearn.metrics import roc_auc_score
from sklearn.model_selection import cross_val_score

# ROC-AUC: plots True Positive Rate vs False Positive Rate
# across EVERY possible threshold, then measures area under it
roc_auc_score(y_true, y_proba)  # 0.5 = random guess, 1.0 = perfect

# k-fold CV: don't trust one train/test split
scores = cross_val_score(model, X, y, cv=5, scoring='f1')
print(f"F1: {scores.mean():.3f} ± {scores.std():.3f}")

A model's F1 score from a single train/test split can be misleadingly high or low just from which rows landed in the test set — especially on small datasets. 5-fold CV runs the whole train/validate cycle 5 times, rotating the held-out fold, and reports mean ± std so you know how stable the score actually is.
