Go: Runtime — Scheduler & GC

The GMP scheduler that multiplexes millions of goroutines onto a few OS threads, growable goroutine stacks, the concurrent garbage collector, and escape analysis.

⚙️ How one Go process runs hundreds of thousands of goroutines on a handful of threads

Go's runtime is a small OS bundled into your binary. Concurrency rides the GMP scheduler: a G is a goroutine, an M is an OS thread, a P is a logical processor with a local run queue (capped at GOMAXPROCS). It multiplexes many G onto few M through the P's — idle P's steal work, and a blocking syscall hands off the M so the P keeps running others. Goroutines are cheap because stacks start at ~2KB and grow by copying (vs ~1MB threads), and since 1.14 the scheduler is preemptible so a tight loop can't starve neighbors. Memory is a concurrent tri-color mark-sweep GC with sub-ms pauses, tuned by GOGC and bounded by GOMEMLIMIT. The compiler's escape analysis decides stack vs heap — keeping allocations on the stack is the biggest GC-pressure lever.

  • GMP scheduler — many goroutines (G) on few threads (M) via processors (P).
  • Work-stealing + syscall handoff — P's stay busy; blocking doesn't stall them.
  • ~2KB growable stacks — 100k+ goroutines routine; preemptible since 1.14.
  • Concurrent low-pause GC — tune GOGC/GOMEMLIMIT; escape analysis keeps allocs on stack.

G, M, P

G = goroutine (~2KB stack, millions of them) M = OS thread (the "machine" that runs code) P = processor (run queue; count = GOMAXPROCS) // many G ⇄ P (= cores) ⇄ M (threads) runtime.GOMAXPROCS(0) // # of P's runtime.NumGoroutine() // live G count

Tuning the GC

GOGC=100 // default: GC when heap grows 100% GOGC=200 // less often, more RAM, less CPU GOGC=off // disable (batch jobs only) GOMEMLIMIT=512MiB // soft memory ceiling // the GC works harder as you near it — // prevents OOM on a fixed-memory container

Go runtime vs the JVM

JVM: OS threads (~1MB each), a generational compacting GC (G1/ZGC), JIT warm-up. Go: goroutines (~2KB) on a userspace scheduler, a non-generational non-compacting concurrent collector tuned for low pause over throughput, AOT-compiled (no warm-up). Result: Go starts in milliseconds and holds tens of thousands of cheap concurrent connections — great for gateways/sidecars; the JVM often wins raw throughput on long-lived CPU-bound work.

CIAM context: This is why a Go auth gateway shrugs off 10k+ simultaneous connections — a goroutine-per-connection at ~2KB is feasible where a thread-per-request model (classic Spring MVC at ~1MB/thread) would exhaust memory. For predictable token-validation p99, set GOMEMLIMIT to the container's memory and consider a higher GOGC to trade RAM for fewer GC cycles. Cutting per-request heap allocations (reuse buffers, avoid pointers that escape) directly shrinks GC pauses under load.

Or: the most harmless-looking log line in your handler is also its biggest allocator.

The problem

Nobody took the address of that int. It escapes to the heap anyway.

A hot path that allocates on every request, from a log line nobody suspects

A token-validation handler is otherwise allocation-free — no pointers escape, everything's plain ints and strings staying on the stack, exactly per the escape-analysis advice earlier on this page. Then someone adds one debug line: log.Printf("validated user %d in %v", userID, elapsed).

go build -gcflags=-m now reports userID escapes to heap and elapsed escapes to heap — for two plain, unaddressed local values that are only ever read, never pointed to. Under load, pprof shows thousands of small heap allocations per second, all traced back to that one log line, and GC pause time climbs to match.

no explicit pointers anywhere in the handler ✓ userID and elapsed never addressed with & ✓ both passed to a ...any parameter ⚠

Passing an argument to an interface parameter almost always forces it to escape, because the interface has to carry a type descriptor plus a pointer to the value, and the compiler can't prove how long that interface might live.

Keep hot-path logging typed, not interface-boxed
Reach for a structured logger with typed field constructors (zap.Int, zap.Duration) instead of %v ↓ a typed field API can often avoid the interface conversion entirely on the hot path — that's the whole reason those APIs exist Gate expensive Printf-style debug logging behind a level check ↓ if logger.Enabled(Debug) { log.Printf(...) } means the allocation only happens when the line actually prints And verify with go build -gcflags=-m or a benchmark's -benchmem, not intuition
Boxing into an interface — not taking an address — is escape analysis's other trigger. The page's earlier examples (returning &User{}) are the obvious case: a pointer visibly escapes. Converting a plain value to interface{}/any is the invisible case: no & appears anywhere in your source, yet the compiler must still heap-allocate so the interface's type-and-pointer pair has something stable to point at.
An interface value is a claim ticket, not the coat. Handing fmt.Println a plain int is like checking your coat at a counter that only accepts claim tickets — the counter can't hold the coat directly, so it has to put YOUR coat on a hook somewhere (the heap) and hand back a ticket (the interface) pointing at it, even if you were only ever going to glance at it and walk away.

The mechanism

Follow one int from "clearly stack-safe" to "heap allocation" with nothing but a log line in between.

  1. func handle(userID int) { ... } — userID is a plain value parameterstack candidate
  2. validate(userID) — a typed function call, no interface involvedstill on stack
  3. log.Printf("user %d ok", userID) — Printf's signature is (format string, args ...any)any parameter
  4. The compiler must convert userID into an any to build that variadic sliceboxing required
  5. That any needs a type descriptor + a pointer to the int's value — a stack address won't doneeds a stable address
  6. go build -gcflags=-m: "userID escapes to heap" — one log line changed where it livesheap allocation

Nothing structural changed about userID between steps 2 and 3 — it's the exact same int. Only its DESTINATION changed, from a typed parameter to a variadic ...any slot, and that alone is what flips the compiler's decision from stack to heap.

log.Printf("...%d...", userID) looks like a read-only call
userID is converted to any to build the ...args slice
that any needs a type descriptor + a pointer to the value
userID escapes to the heapeven though nothing in the source ever wrote &userID

Peel the log line back one layer at a time and the heap allocation is at the center the whole time — just never visible from the outside, because every layer around it looks like ordinary, harmless value-passing.

A hot-path handler is allocation-free per -gcflags=-m until someone adds log.Printf("lat=%v", elapsed) where elapsed is a plain time.Duration local variable, never addressed with &. What does escape analysis do with elapsed now?

That's the rule for the OTHER, more obvious escape trigger (returning or storing a pointer) — but it's not the only one. Converting a value to an interface parameter is a second, separate trigger that needs no & anywhere in the source.

Printf's signature ends in ...any. Building that variadic slice means converting elapsed into an interface{} value, which needs a type descriptor plus a pointer to elapsed's data — a pointer the compiler can't safely leave on the stack, so elapsed moves to the heap.

String literals are typically placed in read-only data at compile time, not the heap, and that's not what changes here anyway — the argument being boxed into the interface is what escapes, not the format string.

Where you have seen this before

"Boxing a value forces it off the fast path" is a cost that shows up wherever a language erases a concrete type into a generic one.

Java's autoboxing into Object

Passing an int to a method expecting Object (or into a pre-generics Collection) autoboxes it into an Integer on the heap — the same "concrete value forced into a generic box that needs heap-backed identity" cost, just with the JVM doing the boxing instead of the Go compiler.

same cost, different compiler doing the boxing

C#'s value types boxed into object

A struct or int passed where object is expected gets heap-boxed in .NET too — .NET's own docs use the word "boxing" for this and recommend generic methods over object-typed ones for exactly this reason, the same fix idiomatic Go reaches for with typed logging fields.

the vocabulary ("boxing") even matches across languages

Python's everything-is-an-object model

Python sidesteps this specific surprise by making everything heap-allocated from the start — there's no stack-resident int to escape, because Python never offered the fast path Go and Java are giving up here.

you can't lose a fast path a language never gave you

1. The GMP Scheduler

PartIsCount
Ga goroutine — task + its own growable stackthousands to millions
Man OS thread (a "machine") that executes codeas needed (blocking syscalls add more)
Pa logical processor with a local run queue; the right to run Go codeGOMAXPROCS (default = CPU cores)
Work stealing + syscall handoff keep cores busy. Each P runs goroutines from its local queue; an idle P steals half of another's queue rather than sitting idle. When a goroutine blocks in a syscall, the runtime detaches its P onto a fresh/idle M so the remaining goroutines keep running — your CPU is never parked just because one goroutine is waiting on disk or network.

2. Goroutine Stacks: Small and Growable

// 100k goroutines? ~200MB of stack — fine.
for i := 0; i < 100_000; i++ {
  go handle(conn[i])
}
// each G starts at ~2KB, grows on demand,
fmt.Println(runtime.NumGoroutine())

A goroutine's stack begins at about 2 KB. When it needs more, the runtime allocates a bigger stack and copies the frames over (updating pointers); it shrinks during GC when over-sized. An OS thread, by contrast, reserves ~1 MB up front. That 500× difference is why "one goroutine per connection/request" is idiomatic in Go and would be reckless with threads.

Cheap to start, but not free to leak. A goroutine blocked forever (on a channel nobody sends to, or a request with no timeout) lives until the process dies — a goroutine leak. Watch runtime.NumGoroutine() climbing without bound, and always give blocking operations a context deadline so they can exit.

3. The Garbage Collector

PropertyGo's GC
Algorithmconcurrent tri-color mark-sweep — runs alongside your code
Pausestwo brief stop-the-world points; total pause typically sub-millisecond
Generational?No (tuned for low latency, not throughput) — and non-compacting
TuningGOGC (default 100 = collect at 2× live heap) · GOMEMLIMIT (soft ceiling)
GOMEMLIMIT is the fix for OOM-killed containers. Set it to (a bit under) the container's memory limit and the GC runs more aggressively as the heap approaches it, trading CPU to avoid the kill. Pair with a higher GOGC to reduce routine cycles while still being protected by the hard ceiling. A write barrier lets the collector mark concurrently while your goroutines keep mutating pointers.

4. Escape Analysis: Stack vs Heap

# see what escapes:
go build -gcflags='-m' ./...

// stays on the stack (no escape) — free
func sum(a, b int) int { return a + b }

// escapes to the heap → GC work
func newUser() *User { return &User{} } // addr outlives the call

The compiler proves whether a value's lifetime stays within its function. If it does, the value lives on the stack (freed automatically when the function returns — zero GC cost). If a pointer to it escapes (returned, stored in a heap structure, captured by a closure that outlives the call), it must go on the heap, creating future GC work. -gcflags=-m prints each decision ("moved to heap", "does not escape").

Fewer heap allocations = shorter GC pauses. The biggest wins: reuse buffers (sync.Pool, or pass a []byte in rather than returning a fresh one), avoid returning pointers to short-lived values, and pre-size slices/maps. Profile allocations with go test -benchmem and pprof (-memprofile) before optimizing — measure, don't guess.
