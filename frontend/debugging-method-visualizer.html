The Debugging Method

Debugging isn't poking until it works — it's the scientific method on a deadline: reproduce → hypothesize → predict → test one thing → narrow. The single biggest speed-up is bisecting: instead of reading 1,000 lines or 30 commits, you halve the search space each step and corner the bug in a handful of checks.

🐛 What is the debugging method — and why is random "poking" the worst way to fix a bug?

Most developers debug by making changes and hoping — "maybe it's the null check, let me add one," "maybe it's the cache, let me clear it," "maybe I need to restart." This random approach wastes enormous time because each change reveals nothing about why the bug exists. The scientific method applied to debugging: (1) Reproduce — you can't fix what you can't reproduce. Make the bug happen reliably, locally if possible. Document the exact steps, input, and environment. "It only happens sometimes" is not reproducible yet. (2) Hypothesize — form a testable belief about what's wrong. Not "the auth is broken" but "the Ping client is receiving a null response when the redirect URI doesn't match." (3) Predict — if your hypothesis is correct, what SPECIFIC observable thing should be true? "The Ping debug log should show a redirect_uri_mismatch error." (4) Test ONE thing — check the specific prediction. Don't change multiple things simultaneously. If you change three things at once and the bug disappears, you don't know which change fixed it. (5) Narrow — your test either confirms or eliminates the hypothesis. Either way, you've reduced the search space. If your prediction was wrong, what does that tell you about the real cause? Bisecting: binary search for bugs. Works in two forms: (1) Code bisect — "the bug is somewhere in this 500-line function." Add a log/breakpoint at the midpoint. Does the bug manifest before or after that line? Eliminate half. Repeat 9 times → found the bug. (2) Commit bisect — "the bug appeared after last Tuesday's deploy." git bisect binary searches through 50 commits in ~6 tests. Rubber duck debugging: explain your code to an inanimate object (or a colleague who stays silent). The act of articulating the problem forces you to think through assumptions you've been skipping.

1. The loop

  1. Reproduce — reliably and minimally. A bug you can't trigger on demand, you can't fix. Pin down the exact input/steps first.
  2. Hypothesize — form one falsifiable guess ("the token's aud is wrong"), not five.
  3. Predict — "if that's it, the decoded token shows aud=other-api."
  4. Test one thing — change a single variable so the result is unambiguous.
  5. Narrow — confirmed or refuted, you've halved the space. Repeat.

Skipping step 1 (or changing many things at once) is where hours vanish. Hold everything constant except the one thing you're testing.

or, bisect will name a commit with total confidence even when the bug was never in the range it searched

The problem

Binary search cannot tell that one of your answers was wrong. It just returns a different answer, with the same straight face.

d4e5f6 is the first bad commit — and the diff is a typo fix in the README

The bug reproduces "most of the time" — call it seven runs in ten. That felt reproducible enough, so you started bisecting 32 commits. Five probes, five verdicts, and git names the culprit. You open the diff expecting an auth change and find a one-word fix to a markdown file. So you stare harder, because git said so, and start inventing mechanisms by which a README could break token exchange.

Here is what happened instead. On probe two you ran the test once, it passed, you typed git bisect good, and in that moment every commit older than the midpoint was removed from the search — permanently, and without a record. The bug was in that half. Everything after was a perfectly executed binary search over a range that no longer contained the answer, and the algorithm terminated the way it always does: by naming whatever commit was left. Notice the asymmetry that makes this specifically dangerous: a bad verdict is proof, because the bug actually appeared. A good verdict is only ever as reliable as your reproduction, and with a 70% repro a single clean run is a coin-flip you called wrong three times out of ten.

every probe ran correctly ✓ git's search was flawless ✓ the range was halved five times exactly as advertised ✓ one "good" verdict was a lie ⚠ and the answer is presented with no uncertainty at all ⚠

Step one of this page's loop is "reproduce reliably". Bisect is the technique that punishes skipping it, and it punishes you silently.

Measure your repro rate before you spend it as evidence

Every narrowing technique converts answers into eliminated territory, and eliminated territory never comes back. That is exactly why bisection is so fast — five probes across a thousand commits — and exactly why it has no tolerance for a wrong answer. There is no consistency check at the end, no confidence interval, no "this result disagrees with probe two"; the algorithm has already discarded the evidence that would have contradicted it. So the quality of a bisect is set entirely before the first probe, by how reliably you can tell good from bad. Improving the test is not preparation for the search. It is the search.

A binary search cannot smell a lie.

Think of "guess my number, higher or lower". Play it perfectly against someone who answers wrong just once and you will end up on a confidently wrong number — and neither of you will ever find out, because the game ends when you commit, not when you're right. The algorithm is only as honest as the answers you feed it.

The mechanism

One flaky verdict, and watch the search become perfectly efficient at finding the wrong thing.

  1. 32 commits. v1.2.0 is known good, HEAD is known bad. The real culprit is commit 7, which nobody knows yetthe search space
  2. Probe 1 — commit 16. The bug shows. bad. This verdict is proof: a bug that appeared cannot un-appeartrustworthy by construction
  3. Probe 2 — commit 8. One run, and it happens to pass. You type good. Commits 1-8 leave the search forever — including commit 7the only wrong step in the whole process
  4. Probes 3, 4, 5 — all correct, all rigorous, all inside a range that no longer contains the bug. Every one of them reports bad, because the bug is still present in all of themflawless work, wrong room
  5. git prints d4e5f6 is the first bad commit. No caveat, no confidence score — the algorithm has no notion that a verdict could have been wrongcertainty is part of the output format
  6. You spend the next hour reconciling a README change with an auth failure, because the tool's confidence is more persuasive than your own reading of the diffthe real cost of the bad probe

Step 3 is the whole story, and notice it is the one step you can make almost free: running the repro twenty times instead of once at each probe costs minutes, and it converts every "good" from a guess into something close to proof. Compare that with the hour in step 6, plus the chance that you "fix" the innocent commit and ship a change that does nothing at all.

Range: commits 1-32 probe 16, it fails → verdict bad, and this one is real — the bug genuinely appeared
Range: commits 1-16 probe 8, one run, passes by luck → verdict good, and the true culprit at commit 7 is now outside the search
Range: commits 9-16 two more flawless probes → the range shrinks correctly around a bug that is not in it
Verdict: commit 12 git prints "first bad commit" → stated with the same certainty it would state a correct answer

Follow the loop and you can see the moment the process stopped being able to succeed — and that nothing after it could possibly have detected the problem. That is the property worth carrying to every other narrowing technique on this page: halving your input, disabling half your config, commenting out half a function. Each of them converts one observation into a permanent elimination, so each of them inherits the reliability of that observation and quietly amplifies it.

A bug reproduces about seven times in ten. You bisect 32 commits, running the repro once per probe, and git reports d4e5f6 is the first bad commit. The diff is a typo fix in the README. What is the most likely explanation?

Bisect handles merges fine — it walks the commit graph and picks testable ancestors, and a merge commit is a perfectly legitimate thing for it to check out. Topology does cause a different, real headache: commits that won't build. The answer there is git bisect skip (or exit code 125 from a bisect run script), because marking an unbuildable commit "bad" corrupts the search in exactly the same way a flaky "good" does.

This phenomenon is real — a commit that merely changes timing or ordering can expose a latent race that has been sitting there for months — which is what makes it such a comfortable story to reach for. But it has to be plausible: a race exposed by a scheduling change is a mechanism, and a README typo fix is not one. When the named commit cannot physically influence the symptom, the likeliest explanation is that a verdict was wrong, not that you've found an exotic interaction.

Right, and the asymmetry is the thing to remember: a bad verdict is proof, because a bug that manifests is definitely present; a good verdict is only as strong as your reproduction rate, and at 70% a single clean run is wrong roughly a third of the time. So make the test asymmetric — fail fast on one failure, require twenty clean runs before saying good — and measure the rate before you start, by running the known-bad commit ten times and counting.

Where you have seen this before

Three other places where a single unreliable observation gets promoted into a permanent fact.

The intermittent auth bug that was really two pods

Logins fail "sometimes" — and the load balancer is round-robining between two instances, one of which has a stale JWKS cache or points at the wrong tenant. Every "good" run is simply a run that landed on the healthy pod. No amount of bisecting the code will find that, because the variable that decides the outcome isn't in the repository. Before you binary-search anything, pin down what you are actually varying: same instance, same environment, same account, same clock.

if the verdict depends on which pod answered, you are not testing commits

"Just re-run the pipeline"

A flaky test fails, someone hits retry, it goes green, the PR merges. That ritual is the same fallacy with a nicer UI: a pass is treated as evidence of correctness when it is only evidence that this particular run passed. The difference is that CI gives you a rerun button and bisect gives you nothing — the eliminated half of history has no retry.

green once is not green

The commit that doesn't build

git bisect run reads your script's exit code: 0 is good, 1-127 is bad, and 125 means "I could not test this one" — which is why 125 exists as its own value. Mark an unbuildable commit as bad and you have poisoned the search precisely as thoroughly as a flaky good, just in the opposite direction. The tool gave you a way to say "I don't know"; use it, and git will route around it and tell you if the answer becomes ambiguous.

"I don't know" is a valid answer and the only honest one

2. Interactive: bisect to the culprit commit

32 commits. It worked at the start, it's broken now — somewhere a commit introduced the bug. Binary-search it: test the midpoint, mark it good/bad, halve the range. (This is exactly what git bisect automates.)

known good known bad candidate probe / culprit

32 commits → found in ~5 probes (log₂32). 1,000 commits would take ~10. That's the power of halving instead of scanning.

3. Bisecting beyond git

git bisect (find the commit)

git bisect start
git bisect bad             # now is broken
git bisect good v1.2.0     # this tag worked
# git checks out the midpoint; you test & mark:
git bisect good   # …or…  git bisect bad
# repeat ~log2(N) times → it names the commit
git bisect reset

The same idea, everywhere

  • Input: half the rows / payload still break it? Keep halving to a minimal repro.
  • Config: disable half the flags/modules; which half carries the bug?
  • Code: comment out half a function; binary-search the offending block.
  • Time: "when did it start?" → bisect deploys/releases.

4. Anti-patterns

  • Shotgun debugging — changing several things at once. Now a "fix" has ambiguous cause; you've learned nothing.
  • Not reproducing first — "fixing" a bug you can't trigger means you can't confirm the fix either.
  • Treating symptoms — a null check that hides why it was null just moves the crash.
  • No hypothesis — stepping aimlessly through a debugger. Decide what you expect before you look.

5. One-sentence recap

🔬 Debug like a scientist: reproduce reliably, form one falsifiable hypothesis, change one variable, and above all bisect — halve the search space each step (git bisect for commits, the same binary search for inputs, config, code blocks, and deploys) so you corner the bug in ~log₂(N) checks instead of scanning it all — and avoid shotgun changes, symptom-patching, and looking before you have a hypothesis.
