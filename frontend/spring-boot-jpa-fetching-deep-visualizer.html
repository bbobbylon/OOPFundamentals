The N+1 Query Problem & How to Kill It

The most common JPA performance bug, and the five ways to fix it. Pick a fetch strategy and watch the exact SQL Hibernate fires — and how the query count explodes or collapses.

🪤 What is the N+1 query problem — and why does it destroy performance at scale?

userRepository.findAll() fires one query for 200 users. Then your code reads user.getRoles() per user — and because roles is lazy, JPA fires another query each time: 200 × SELECT … WHERE user_id = ?. That's 201 queries where 1 would do — the N+1 problem. At 200 users it's ~200ms; at 20,000 the endpoint times out. The trap is that lazy loading is invisible — getRoles() looks like a list access but is secretly a query. The fix: load what you need upfront in one (or a few) queries.

  • 1 parent query + N child queries. The cost grows linearly with the result set.
  • Lazy access hides queries. A getter that triggers SQL is the whole problem.
  • Fix by fetching together — JOIN FETCH or @EntityGraph in one round trip.
  • Paginated list endpoints are the danger zone — always fetch-join their associations.

Fix 1: JOIN FETCH (JPQL)

@Query("SELECT u FROM User u LEFT JOIN FETCH u.roles WHERE …") loads users + roles in one query. Caveats: it duplicates rows for multi-role users (use DISTINCT), and JOIN FETCH + @OneToMany can't paginate in SQL — Hibernate pages in memory (logs warn).

Fix 2: @EntityGraph

@EntityGraph(attributePaths={"roles"}) Optional<User> findById(Long id) — Spring Data emits the fetch join, cleaner than JPQL for simple cases. Multiple paths ({"roles","addresses"}) load several eagerly, overriding the entity's own fetch type for this query.

Detecting N+1

Turn on show-sql + logging.level.org.hibernate.SQL=DEBUG and watch for the same query repeated. Better: hibernate.generate_statistics=true ("Queries executed: 201"). Best: alert in Datadog/Grafana when an endpoint exceeds ~10 queries/request.

CIAM: GET /api/users with role names is 1 + 100 = 101 queries without a fix, 1 with @EntityGraph(attributePaths={"roles"}). Audit queries like findAllByTargetUserId(userId) have lazy actor/targetUser — load with an entity graph. Rule: any list endpoint that touches associations must fetch-join or project, paginated ones above all (N+1 × 20/page × thousands of pages is catastrophic).

1. What is N+1?

You load a list of Authors (1 query), then loop and touch each author's books collection. If books are lazy, Hibernate fires one more query per author to load them — N extra queries. For 100 authors that's 101 round-trips to the database to render one page. Each round-trip has network + parse + planning cost; the latency stacks up fast.

@Entity class Author {
  @OneToMany(mappedBy="author") // LAZY by default
  List<Book> books;
}

// the innocent-looking loop that triggers N+1:
for (Author a : authorRepo.findAll())   // 1 query
    total += a.getBooks().size();      // +1 query EACH time

3. LAZY vs EAGER — and why EAGER is not the fix

The defaults you must memorize

AssociationDefault fetch
@OneToManyLAZY
@ManyToManyLAZY
@ManyToOneEAGER ⚠️
@OneToOneEAGER ⚠️

Best practice: make everything LAZY (@ManyToOne(fetch = LAZY) too) and fetch what you need explicitly per query. EAGER is a global decision that's wrong most of the time.

EAGER just moves the problem

Switching the collection to EAGER does not merge the queries — when you findAll() a list, Hibernate still fires one SELECT per association (it can't put a collection join into a "load by id" plan safely). You get the same N+1, just eagerly and everywhere, even when you didn't need the books at all.

Try it in the demo: EAGER and LAZY + loop produce the same query count. The fix is never the fetch type — it's fetching via a join at query time.

4. The real fixes — at query time

JOIN FETCH (JPQL)

@Query("""
  select distinct a from Author a
  join fetch a.books
""")
List<Author> findAllWithBooks();

One SQL join, one round-trip. Use distinct to collapse duplicate author rows the join produces.

@EntityGraph (declarative)

@EntityGraph(attributePaths = "books")
List<Author> findAll();

Same effect as join fetch but reusable and composable with derived queries. The cleanest default for "load this with its children."

Batch fetching (the pagination-safe one)

# application.yml
spring.jpa.properties.hibernate
  .default_batch_fetch_size: 25

// or per-collection: @BatchSize(size = 25)

Turns N queries into 1 + ceil(N/size) using WHERE author_id IN (?,?,…). Crucially, it works with pagination, unlike join fetch.

DTO projection (fetch only what you show)

@Query("""
  select new com.app.AuthorView(
    a.name, count(b))
  from Author a left join a.books b
  group by a.name
""")
List<AuthorView> summaries();

No entities, no lazy loading at all — the DB does the aggregation. Often the fastest for read-only views.

5. The pagination trap

Combining JOIN FETCH a collection with Pageable (or setMaxResults) triggers this warning:

HHH000104: firstResult/maxResults specified with collection fetch;
applying in memory!

Because the join multiplies rows, the database can't paginate correctly, so Hibernate fetches everything and paginates in memory — a hidden OOM risk on large tables. Fix: use @BatchSize / default_batch_fetch_size for paginated queries, or do it in two steps (page the IDs first, then fetch the collection for those IDs).

7. One-sentence recap

🐘 N+1 is "1 query for the parents + 1 per parent for a lazy child collection"; switching to EAGER doesn't fix it (same count, always paid) — the cure is fetching via a join at query time with JOIN FETCH or @EntityGraph (1 query), @BatchSize when you also need pagination (1 + N/size), or a DTO projection when you only need a summary.
