Go: database/sql

The standard database layer: sql.DB is a connection pool (not a connection), parameterized queries that defeat SQL injection, scanning rows, and transactions.

🗃️ sql.Open doesn't open a connection — and other things that surprise newcomers

database/sql is Go's driver-agnostic DB interface — import a driver (pgx, mysql) for its side effects, program against the stdlib. First surprise: sql.Open returns a *sql.DB that's a lazy connection pool — it doesn't connect until the first query, so db.PingContext(ctx) verifies at startup. Keep one *sql.DB for the app's lifetime (concurrency-safe), not one per request. QueryContext reads many rows, QueryRowContext one, ExecContext writes. The cardinal rule: always use placeholders ($1/?) and pass values as args — never fmt.Sprintf SQL. The driver sends query and data separately, so input can't be parsed as SQL — the definitive SQL-injection defense. rows.Scan(&a, &b) reads into typed vars, and multi-statement work goes in a BeginTx → Commit/Rollback transaction.

  • sql.Open = lazy pool — PingContext to verify; keep ONE for the whole app.
  • Query/QueryRow/Exec — many rows / one row / writes; loop+Close+check rows.Err().
  • Always placeholders ($1/?) — never Sprintf; the injection defense.
  • Scan into typed vars; wrap multi-statement units in a transaction.

Open the pool once

import _ "github.com/jackc/pgx/v5/stdlib" db, err := sql.Open("pgx", dsn) // no connection yet — it's a lazy pool if err := db.PingContext(ctx); err != nil { log.Fatal(err) // verify at startup } db.SetMaxOpenConns(25) // keep ONE *sql.DB for the whole app

Placeholders, never Sprintf

// ✅ safe — value sent separately row := db.QueryRowContext(ctx, "SELECT id,roles FROM users WHERE email=$1", email) // ❌ SQL INJECTION db.Query("SELECT * FROM users WHERE email='" + email + "'") // email = "' OR '1'='1" → returns everyone

database/sql vs JPA/Hibernate

JPA: an ORM — entities, a session/EntityManager, lazy loading, dirty checking, generated SQL. Go's database/sql: deliberately not an ORM — you write SQL and Scan into structs yourself. More boilerplate, zero hidden queries (no N+1 surprises), full control. Libraries like sqlx (struct scanning), sqlc (generate type-safe Go from SQL), or GORM (a real ORM) build on top, but the stdlib is explicit by design.

CIAM context: The login lookup is the highest-value injection target in the system — QueryRowContext(ctx, "SELECT id, password_hash, roles FROM users WHERE email=$1", email) with a placeholder makes a malicious ' OR '1'='1 a literal string that matches no user, not an auth bypass. Pass the request ctx so a cancelled login cancels the query, and wrap "insert user + assign default role" in a transaction so a half-created account can never exist.

1. sql.Open Is a Lazy Pool

// blank import = register the driver for its side effects
import _ "github.com/jackc/pgx/v5/stdlib"

db, err := sql.Open("pgx", dsn) // no connection yet!
if err != nil { log.Fatal(err) }
if err := db.PingContext(ctx); err != nil { // now it connects
  log.Fatal(err)
}
defer db.Close() // at shutdown, not per request

sql.Open only validates arguments and builds a pool; the first real connection happens on first use, which is why Ping is the way to fail fast at startup. The _ blank import runs the driver's init() to register itself under a name ("pgx", "mysql"). Crucially, *sql.DB is safe for concurrent use and is meant to live for the program's lifetime — store it once (in a struct or package var), never open one per request.

One *sql.DB for the whole app. It manages a pool of underlying connections for you. Opening a new sql.DB per request is the classic performance bug — you lose pooling entirely and exhaust the database's connection limit under load.

2. Parameterized Queries + Scan

// many rows
rows, err := db.QueryContext(ctx,
  "SELECT id, email FROM users WHERE active=$1", true)
if err != nil { return err }
defer rows.Close()
for rows.Next() {
  var id int; var email string
  if err := rows.Scan(&id, &email); err != nil { return err }
}
return rows.Err() // check after the loop!

QueryContext → many rows (loop Next/Scan, defer Close, then rows.Err()). QueryRowContext → exactly one (.Scan returns sql.ErrNoRows if none). ExecContext → writes (returns a Result with RowsAffected()). Scan maps columns to typed pointers in order; nullable columns need sql.NullString/NullInt64 (or pointers), because scanning a SQL NULL into a plain string errors.

Forgetting rows.Close() or rows.Err() are the two classic leaks/bugs. An unclosed Rows holds a pooled connection until GC — exhausting the pool. And the for rows.Next() loop also ends on error, not just end-of-data, so you must check rows.Err() afterward or you'll silently treat a mid-iteration failure as success.

3. Tuning the Connection Pool

SettingControls
SetMaxOpenConns(n)max simultaneous open connections (cap it below your DB's limit ÷ instances)
SetMaxIdleConns(n)connections kept idle for reuse (avoids reconnect churn)
SetConnMaxLifetime(d)recycle a connection after d (plays nice with load balancers / DB restarts)
SetConnMaxIdleTime(d)close a connection idle longer than d
Size the pool to the database, not the app. If Postgres allows 100 connections and you run 5 instances, SetMaxOpenConns(20) per instance keeps you under the limit. An unbounded pool (the default MaxOpenConns is 0 = unlimited) can open hundreds of connections under a traffic spike and take the database down.

4. Transactions

tx, err := db.BeginTx(ctx, nil)
if err != nil { return err }
defer tx.Rollback() // no-op if already committed — safety net

if _, err := tx.ExecContext(ctx,
  "INSERT INTO users(email) VALUES($1)", email); err != nil {
  return err // deferred Rollback undoes everything
}
if _, err := tx.ExecContext(ctx,
  "INSERT INTO user_roles(user_id,role) VALUES($1,$2)", id, "ROLE_USER"); err != nil {
  return err
}
return tx.Commit() // both inserts land, or neither
The defer tx.Rollback() idiom is the safety net. Defer the rollback right after Begin; if any step returns early, the rollback fires and undoes partial work. On the happy path you reach tx.Commit(), and the deferred Rollback becomes a harmless no-op (it returns sql.ErrTxDone, which you ignore). Run all statements through tx, never the original db, or they won't be in the transaction.
