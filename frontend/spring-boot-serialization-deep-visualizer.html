JSON Serialization & Content Negotiation

An API response body is just text. Spring uses Jackson to turn your Java object into JSON (and a request body back into an object), guided by Content-Type/Accept negotiation. The exact field names, date format, and null handling on the wire are decisions — and your Angular interface has to mirror them precisely. Let's make those decisions visible.

📦 What does Jackson do — and why doesn't the JSON field name always match the Java field?

When a controller returns an object, Spring calls Jackson to serialize it to JSON. Naming strategy, annotations, and visibility rules decide which fields appear, what they're named (camelCase by default, optionally snake_case), how dates render (ISO-8601 string vs epoch), and whether nulls are included. The Angular interface must match exactly — serialize a LocalDateTime as epoch ms while Angular expects a string and the field is undefined; use snake_case while Angular uses camelCase and every field is undefined. These are API-contract decisions: once Angular consumes the API, changing them is breaking.

  • Jackson is the JSON translator in both directions — response out, request body in.
  • Config = contract. Naming, date format, and null-inclusion must match the client exactly.
  • Deserialization is by field name (case-insensitive); unknown fields are ignored by default.
  • Type info enables polymorphism — but never expose raw @class names (info leak).

Key configuration

property-naming-strategy=SNAKE_CASE, serialization.write-dates-as-timestamps=false (ISO-8601), default-property-inclusion=NON_NULL. Per-field: @JsonProperty("given_name"), @JsonIgnore, @JsonFormat(pattern="yyyy-MM-dd").

Deserialization

Jackson maps request JSON to Java fields by name. fail-on-unknown-properties=false (Boot default) ignores extras; set true for strict contract checks. Jackson doesn't enforce "required" — that's Bean Validation via @Valid @RequestBody.

Polymorphism

@JsonTypeInfo(use=NAME, property="type") + @JsonSubTypes(...) emits "type":"PING" and reads it back to pick the subclass — good for event payloads. Never return raw Object with default typing; Jackson leaks "@class" names.

CIAM: Standardize early — camelCase, ISO-8601 dates, NON_NULL — so interface UserResponse { id; email; displayName; roleNames: string[]; createdAt: string } matches the wire exactly. Parse createdAt to Date in an Angular interceptor, and never return ZonedDateTime/Instant without a configured timezone (Angular needs UTC or an explicit offset).

The problem

You wrote private boolean isActive;, Lombok generated the getter, Jackson serialized the DTO — and the JSON key isn't isActive. It's active.

"isActive" vanishes into "active" — and Angular reads undefined

Your AccountDto has one field: private boolean isLocked;. @Data (or a hand-written getter) gives you public boolean isLocked() { return isLocked; }. It compiles clean, nothing warns, and the field is right there in the class, spelled exactly the way you want the JSON key spelled.

Jackson doesn't serialize fields — it serializes properties, and it derives a property's name from its getter using the same rule the JDK's own java.beans.Introspector has used for decades: a getter named isXxx() names the property xxx, first letter lowercased, full stop. It never checks whether your FIELD already happened to be spelled isLocked — it just strips the leading is off the METHOD name it sees. So isLocked() maps to the property locked, not isLocked — even though the field, the getter, and the constructor parameter are ALL literally spelled isLocked.

field is named isLocked ✓ getter compiles as isLocked() ✓ the thing that is not ⚠ JSON key is "locked"

Your Angular interface AccountDto { isLocked: boolean } isn't wrong syntax — it's just reading a key that was never on the wire.

The one-sentence rule. Jackson names a property after what its accessor method is called, not what your field is called — and for a boolean, an "is"-shaped getter always drops the "is". This is the exact same JavaBeans Introspector rule the whole JDK uses, so it isn't a Jackson bug — it's Jackson faithfully doing what a beans-aware framework has always done. Lombok doesn't fight it either: for a field already spelled isXxx, Lombok emits the getter as isXxx() verbatim instead of doubling it to isIsXxx(), which is the right call for Lombok and the trigger for Jackson's stripping. The bug only becomes visible once a client mirrors the field name instead of the wire.
"Jackson reads the getter's lips, not the field's name tag." If the getter says isActive(), Jackson hears "active" — every single time, no exceptions.
You

I named the field isLocked so the JSON would obviously say isLocked. Why is it "locked"?

Jackson, personified

I never looked at your field. I looked at the getter, saw isLocked(), and did what every is-getter has taught me to do since JavaBeans existed: strip the "is", lowercase the rest.

You

So if I'd called the field enabled and generated isEnabled(), I'd have gotten... "enabled"?

Jackson, personified

Exactly — and you'd never have noticed a mismatch, because that time the strip happened to match what you wanted.

The mechanism

Walk the exact path from your field declaration to the byte on the wire.

  1. Field declared: private boolean isLocked;your code
  2. Lombok/IDE emits public boolean isLocked() {...}no double "is"
  3. Jackson's bean introspector scans the class's public gettersreflection
  4. It sees isLocked() — matches the is-getter pattern (is + capitalized word)pattern match
  5. Strips "is", decapitalizes "Locked" → property name lockedthe rule
  6. ObjectMapper writes "locked": true to the response bodyon the wire

Step 4 is the one to memorize: Jackson doesn't care that your FIELD is already named isLocked — it only ever looks at the accessor method's name, and isLocked() is indistinguishable to Jackson from a getter Lombok would have generated for a field named just locked. Two totally different field names produce the identical wire output, because Jackson's introspection only sees the getter's shape, never your source code.

Right — isLocked() matches the classic is-getter pattern, so Jackson strips "is" and decapitalizes the rest, giving the property name "locked," identically to how it would for a field just named "locked." The deeper point: a getter's spelling is the only input to this rule; your source field name is invisible to Jackson entirely.

That's what most people guess because it's what the field AND the getter method are literally spelled — but Jackson never reads either of those; it only applies the is-getter stripping rule to the getter's name, so this spelling never survives to the wire.

Jackson always decapitalizes the first letter of the remainder before using it as a property name — the same lowercase-first-letter convention the JDK's own Introspector uses — so a capital-I property name never comes out of this path.

1. The body is text; Jackson is the translator

A @RestController returns a Java object, not JSON. Spring picks an HttpMessageConverter based on the request's Accept header (content negotiation) — for application/json that's MappingJackson2HttpMessageConverter, which runs Jackson's ObjectMapper. Inbound, @RequestBody + Content-Type does the reverse.

User object→ Jackson serialize → JSON text→ wire → TS object

Boot auto-configures the ObjectMapper; you tune it with application.yml (spring.jackson.*), a Jackson2ObjectMapperBuilderCustomizer, or per-field annotations.

3. Field naming — the multi-IDM reality

Jackson defaults to the Java field name (camelCase). But you'll consume IDMs and partners that use snake_case (and Entra mixes both). Three levers:

  • @JsonProperty("user_name") — rename one field explicitly (wins over any strategy).
  • @JsonNaming(SnakeCaseStrategy.class) on the type, or globally spring.jackson.property-naming-strategy: SNAKE_CASE.
  • For inbound only, @JsonAlias({"user_name","userName"}) accepts several spellings.

Key point: whatever name is on the wire is the name your TypeScript interface must use — or you map it on the way in. There's no automatic camelCasing in Angular's HttpClient.

4. Dates & times — the #1 gotcha

Spring side

  • Use Instant/OffsetDateTime for timestamps. Boot registers the JavaTimeModule so they serialize as ISO-8601 strings by default.
  • spring.jackson.serialization.write-dates-as-timestamps: true flips them to epoch numbers — rarely what you want for an API.
  • @JsonFormat(pattern="yyyy-MM-dd") for a specific shape on one field.

Angular side

  • JSON has no date type — createdAt arrives as a string (or number). HttpClient does not revive it to a Date.
  • Type it as string in your interface and parse where needed: new Date(dto.createdAt) or a date lib.
  • Pretending it's a Date in the interface is a lie that bites at runtime.

5. Nulls & unknown properties

SettingDirectionEffect
@JsonInclude(NON_NULL)outomit null fields entirely (smaller, but the key is absent — TS field must be optional)
FAIL_ON_UNKNOWN_PROPERTIESindefault true: an extra field in the incoming JSON throws. Often disabled for forward-compat
@JsonIgnoreProperties(ignoreUnknown=true)intolerate extra fields on one type (e.g., evolving IDM tokens)
@JsonIgnorebothdrop a field from serialization & deserialization (e.g., never expose it)

Forward-compatibility tip: when you consume an IDM/partner whose payload grows over time, disable FAIL_ON_UNKNOWN_PROPERTIES (or annotate) so a new claim/field they add doesn't break your deserialization.

6. Keeping the TS model in sync

  • The interface is a hand-written mirror of the JSON contract — names, optionality, and types must match the wire, not your Java field names.
  • NON_NULL / nullable columns → optional (field?: T) in TS.
  • Dates/Instants → string (parse on use); enums → string-literal unions.
  • Best of all: generate the model from the API's OpenAPI spec (openapi-generator) so it can never drift — see the Spring OpenAPI / Swagger page.

7. One-sentence recap

🔤 Spring negotiates on Accept/Content-Type and uses Jackson to (de)serialize your DTO, where naming (camelCase default vs @JsonProperty/snake_case), dates (ISO-8601 strings by default — and just string in TS, never a real Date), and nulls/unknowns (@JsonInclude(NON_NULL), FAIL_ON_UNKNOWN_PROPERTIES) are all explicit contract decisions your Angular interface must mirror exactly — so type it to the wire, mark omitted fields optional, and generate it from OpenAPI when you can.
