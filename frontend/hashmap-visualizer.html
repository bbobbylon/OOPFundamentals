HashMap — Buckets, Chaining & Auto-Resize

Hash a key, pick a bucket, store there. When too full, double the array and re-hash everything.

🧩 What is a HashMap — and how does hashing achieve O(1) average lookups regardless of how many entries are stored?

A HashMap is the most important data structure for day-to-day programming: it maps arbitrary keys to values and delivers O(1) average time for get, put, and remove — regardless of whether you have 10 or 10 million entries. This seems impossible, but the mechanism is elegant. How hashing works: to store key K, call K.hashCode() to get an integer (the hash), then compute index = Math.abs(hash) % bucketArrayLength. That index is the "bucket" where the entry is stored in an internal array. To retrieve, hash the key again, jump directly to that bucket — no linear scan. Collisions: two different keys can hash to the same bucket (pigeonhole principle — infinite keys, finite buckets). Java resolves this with separate chaining: each bucket holds a linked list (or, since Java 8, a Red-Black tree when the chain exceeds 8 entries). A get() must scan the chain at the target bucket, comparing each entry's key via equals(). Load factor: the ratio of entries to buckets. Java's default load factor is 0.75 — when 75% full, the bucket array is doubled and every entry is re-hashed (rehashing). This keeps chain lengths short and maintains O(1) average. Rehashing is O(n) but happens so infrequently that the amortized cost per operation is O(1). The equals()/hashCode() contract: if two objects are equal (equals() returns true), they MUST have the same hashCode(). Breaking this contract silently destroys HashMap correctness — you'd be able to put an entry, then get() with the equal key finds nothing because the hash sends it to a different bucket. HashMap vs LinkedHashMap vs TreeMap: HashMap has O(1) operations, no order. LinkedHashMap maintains insertion order (O(1) operations, O(n) space overhead per entry). TreeMap maintains sorted order (O(log n) operations). For cache implementations (LRU cache = LinkedHashMap with accessOrder=true + removeEldestEntry), LinkedHashMap is the standard choice.

HashMap internals

// Java HashMap simplified internals class SimpleHashMap<K,V> { Node[] buckets = new Node[16]; // starts with 16 buckets int size = 0; float loadFactor = 0.75f; void put(K key, V value) { int idx = Math.abs(key.hashCode()) % buckets.length; Node cur = buckets[idx]; // scan existing chain while (cur != null) { if (cur.key.equals(key)) { cur.value=value; return; } // update cur = cur.next; } buckets[idx] = new Node(key, value, buckets[idx]); // prepend size++; // if load factor exceeded → resize() doubles array and re-hashes all if ((float)size/buckets.length > loadFactor) resize(); } V get(K key) { int idx = Math.abs(key.hashCode()) % buckets.length; Node cur = buckets[idx]; while (cur != null) { if (cur.key.equals(key)) return cur.value; // found cur = cur.next; } return null; // not found } } // O(1) average — O(n) worst case (all keys hash to same bucket)

equals() + hashCode() contract

// RULE: equals() → same hashCode() // (not the other way: same hashCode() does NOT mean equals) // CORRECT custom key class class UserId { String tenant; String userId; @Override public boolean equals(Object o) { if (!(o instanceof UserId)) return false; UserId other = (UserId) o; return tenant.equals(other.tenant) && userId.equals(other.userId); } @Override public int hashCode() { return Objects.hash(tenant, userId); // MUST include same fields as equals } } // BROKEN: if you override equals but NOT hashCode, // two "equal" objects get different bucket indices → // map.put(id1, user); map.get(id2); // returns NULL even if id1.equals(id2)! // Java records auto-implement both correctly

HashMap variants comparison

// HashMap — no ordering, O(1) Map<String,User> cache = new HashMap<>(); cache.put("user123", user); cache.get("user123"); // O(1) // LinkedHashMap — insertion order preserved Map<String,User> ordered = new LinkedHashMap<>(); // or access order (LRU cache!): Map<String,User> lruCache = new LinkedHashMap<String,User>( 16, 0.75f, true /*accessOrder*/) { protected boolean removeEldestEntry(Map.Entry e) { return size() > 1000; // evict LRU when over 1000 entries } }; // TreeMap — sorted by key, O(log n) TreeMap<Long,Session> byExpiry = new TreeMap<>(); byExpiry.put(expiryTimestamp, session); // Efficiently find + evict the soonest-to-expire session: byExpiry.firstEntry(); // O(log n)

In CIAM / Context: HashMaps are ubiquitous in CIAM: in-memory token caches (HashMap<String, TokenInfo> keyed by token hash), user session stores (HashMap<String, Session> keyed by sessionId), OAuth client registrations (HashMap<String, ClientDetails> keyed by clientId), and JWT claim extraction (the decoded JWT payload IS a Map<String, Object>). The LinkedHashMap LRU pattern is standard for a bounded in-memory token validation cache — add tokens as they arrive, auto-evict the oldest when the cache exceeds N entries, preventing unbounded memory growth between Redis refreshes. Always override equals() + hashCode() when using composite keys (tenantId + userId) — failing to do so causes silent cache misses that are notoriously hard to debug in production.

How the magic happens

1. hash(key)

Run the key through hashCode() — a function that turns any object into an int. For strings, Java does h = 31*h + char for each character. Two equal keys ALWAYS produce the same hash. The reverse is not true: different keys can collide.

// java.lang.String#hashCode
int h = 0;
for (int i = 0; i < length(); i++)
    h = 31 * h + charAt(i);

2. (hash & 0x7FFFFFFF) % cap

Force the hash positive (drop the sign bit) and mod by capacity. That gives a bucket index in [0, capacity). Real HashMap uses hash & (cap - 1) — same result when capacity is a power of two, but a single AND instead of a divide.

3. Walk the chain

Each bucket holds a linked list (or, in Java 8+, a tree if it gets long). To find a key you compare it against each entry in the chain with .equals(). That's why keys MUST implement equals and hashCode consistently.

4. Resize when full

When size / capacity exceeds the load factor (Java default 0.75), the map allocates a new array twice as big and re-hashes every entry into it. That's an O(n) operation, but it happens rarely enough that put is amortized O(1).

Where you actually use HashMap

🗂️ Caches

Memoization, web caches, image caches, Redis lookups. Key = the URL or request signature, value = the cached result. O(1) lookup is what makes a cache faster than recomputing.

🔐 Session store

Web servers map a session ID cookie to a session object in memory. Every request does a HashMap lookup before your code even runs.

🏷️ Counting / tallying

"How many times did each word appear?" → Map<String,Integer>. "Group orders by customer" → Map<Customer,List<Order>>. Bread and butter of data processing.

🔍 Indexes

Database indexes, search inverted indexes, the JVM's own symbol tables. Anywhere you need "given an ID, find the row" without scanning.

🎯 De-dup (HashSet)

HashSet is a HashMap that throws away the value. "Have I seen this user-agent before?" — add to a HashSet and check existence in O(1).

🌐 DNS / routing tables

"Given this hostname, which server?" / "Given this URL pattern, which controller?" Routing layers everywhere are HashMap-shaped.

Why not just use an array?

Operation ArrayList (unsorted) ArrayList (sorted) + binary search HashMap
find by key O(n) scan O(log n) O(1) avg
insert O(1) at end O(n) shift O(1) amortized
remove by key O(n) O(n) O(1) avg
iterate in order insertion order sorted no order (use TreeMap for sorted, LinkedHashMap for insertion)
memory overhead low low ~33% extra (the empty buckets)

Use HashMap when you'll do many lookups by key and don't need order. Use TreeMap when you need keys sorted (e.g. range queries). Use LinkedHashMap when you want HashMap speed but iteration in insertion order (LRU caches).

The danger of a bad hashCode

If you override equals but not hashCode, you break the contract: equal objects can end up in different buckets, and the map can't find them. If every key returns the same hash, ALL entries chain in one bucket and lookup degenerates to O(n) — the map becomes a linked list. That's why IDEs nag you to generate them together. 

// The contract — break this and your map breaks.
if (a.equals(b)) then a.hashCode() == b.hashCode()

// Good: derive both from the same fields
public boolean equals(Object o) {
    return o instanceof Person p && id == p.id;
}
public int hashCode() {
    return Objects.hash(id);
}
