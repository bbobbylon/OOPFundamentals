AWS-Native IaC — CloudFormation & CDK

Terraform is cloud-agnostic; CloudFormation is AWS's own IaC engine, and the state file you'd manage yourself in Terraform is instead tracked for you inside every stack. CDK doesn't replace CloudFormation — it generates it, letting you write real TypeScript or Python instead of YAML.

🧱 If Terraform already does IaC, why does AWS have its own version?

CloudFormation is AWS's native, declarative IaC service: you write a template (YAML or JSON) describing resources, and CloudFormation manages the entire lifecycle as a named stack — creating, updating, and rolling back resources as one atomic unit. The key difference from Terraform is who owns the state: Terraform's state file is your responsibility (stored remotely, must be locked, can drift out of sync); a CloudFormation stack's state lives inside AWS itself — there's no file to lose, back up, or corrupt. Where Terraform's plan shows a diff, CloudFormation's equivalent is a change set: a preview of exactly what an update will create, modify, or replace, which you review and then execute — nothing happens until you do. CloudFormation also runs drift detection: since it knows the exact template that created each resource, it can compare that record against the resource's actual current state in AWS and flag anything changed outside the stack (someone editing a security group rule by hand in the console, for example). CDK (Cloud Development Kit) sits on top of CloudFormation rather than replacing it: you write actual TypeScript, Python, Java, or C# — with loops, conditionals, functions, and reusable classes called constructs — and running cdk synth compiles that code down into a plain CloudFormation template. cdk deploy then synthesizes and hands that template to CloudFormation exactly as if you'd written the YAML by hand. CDK's real value is abstraction: a single new Bucket(this, 'Uploads') construct expands into dozens of lines of CloudFormation (bucket policy, encryption config, public-access block) with secure defaults already applied.

  • Stack, not state file — CloudFormation tracks what it manages internally; there's no state file for you to store, lock, or lose.
  • Change set = plan — a change set previews create/modify/replace before anything executes, same safety idea as terraform plan.
  • Drift detection — CloudFormation can compare a resource's live AWS state against what the template says it should be, and flag manual out-of-band edits.
  • CDK compiles to CloudFormation — cdk synth turns real code (constructs) into a template; CDK never talks to AWS directly, CloudFormation still executes everything.

"Replace" is the change set outcome to fear

Some property changes (like an RDS instance's engine version, or renaming certain resources) can't be updated in place — CloudFormation must delete and recreate. A change set always tells you up front which resources are Modify (safe, in-place) vs Replace (destructive) before you execute it.

CDK constructs have three abstraction levels (L1/L2/L3)

L1 (CfnBucket) is a 1:1 mirror of a raw CloudFormation resource. L2 (Bucket) adds sane defaults and helper methods. L3 "patterns" (like ApplicationLoadBalancedFargateService) wire together many resources — a whole VPC, ALB, and ECS service — from one construct call.

A stack rollback is automatic on failure

If any resource in a CloudFormation update fails to create or update, the entire stack automatically rolls back every resource to its pre-update state — you never end up with half the change applied, unlike a script that fails partway through.

The CIAM parallel: a CDK Stack that provisions a Cognito user pool, an API Gateway with a JWT authorizer, and the Lambda functions behind it is the AWS-native version of provisioning this codebase's own identity infrastructure — the same "app registration, secrets, redirect URIs" concerns from the Terraform page's CIAM note, just expressed as real code with type-checked resource references instead of HCL string interpolation.

The problem

Knowing a resource is about to be replaced is only half the warning. Whether the resource losing that identity gets deleted or kept is a completely separate decision, made somewhere else entirely.

The DynamoDB table that vanished during an "expected" replace

The team needs to change a DynamoDB table's partition key — UserSessions moves from a plain sessionId key to a composite key. They already know the rule this page's own intro warns about: a partition key is immutable, so this will be a Replace, not a Modify. They open the change set, see Replace next to UserSessions, recognize exactly what that means, and approve it.

CloudFormation creates the new table first, the application gets repointed at its ARN — and then CloudFormation deletes the OLD UserSessions table, instantly, along with every session record that hadn't yet been migrated into the new one. Nobody had ever added an UpdateReplacePolicy to that resource, and when none is set, CloudFormation's documented default is to delete the old resource the moment the replacement succeeds.

Knowing a resource will be replaced tells you nothing about what happens to the one it's replacing — that's a second, separate setting, and its default is gone.

Set UpdateReplacePolicy wherever Replace is possible
On any resource where a change set might ever say Replace, add an explicit UpdateReplacePolicy ↓ without it, CloudFormation silently assumes Delete — there's no extra warning at execute time beyond the word "Replace" you already saw Set it to Retain, or Snapshot where the resource type supports it ↓ Retain keeps the old physical resource alive in your account, orphaned from the stack but not destroyed — the same idea as DeletionPolicy on a full stack deletion Re-check the change set for "Replacement: True" alongside your intended policy before executing ↓ this is the last checkpoint — the change set can tell you what policy it sees, but only if you look for it instead of stopping at the word Replace
The one-sentence rule. A change set's Replace flag answers "will this resource's physical identity change" — it says nothing about what happens to the resource whose identity is changing, and that second question belongs entirely to UpdateReplacePolicy. That attribute defaults to Delete on every resource type that doesn't explicitly override it, and it lives nowhere near the change-set review that told you Replace was coming, which is exactly why a team can correctly understand one fact and still never learn the other.
Replace tells you WHO's changing. UpdateReplacePolicy tells you what happens to the one left behind.

The mechanism

Here's the actual order of operations for a Replace update, and the exact step with no confirmation dialog attached to it.

  1. A partition-key change is submitted; the change set computes UserSessions: Replacechange set
  2. The team reviews the change set, recognizes Replace, and approves it — exactly the check this page recommendsreview
  3. CloudFormation creates the NEW UserSessions table first, under a new physical IDcreate-first
  4. The application's connection is repointed to the new table's ARNcutover
  5. CloudFormation checks the OLD table's UpdateReplacePolicy attribute — none was ever setthe missing setting
  6. The default applies: the old table, and every item still sitting in it, is deletedgone

Step 5 is the one worth sitting with — there is no UI equivalent to step 2's change-set review for it. No dialog pops up asking "delete the old table too?" The policy, or the absence of one, was already baked into the template long before anyone opened a change set for this particular update.

Where you have seen this before

"The destructive thing already happened; whether it took your data with it was decided somewhere else" shows up constantly once you start looking for it.

ON DELETE CASCADE on a users table

A CIAM schema migration swaps the users table's primary key from a Long ID to a UUID — an immutable-style change that forces dropping and recreating the table. Every sessions, refresh_tokens, and audit_log row with a foreign key configured ON DELETE CASCADE against that old table vanishes the instant it's dropped, because the cascade behavior was decided in the schema, months earlier, not at migration time.

the cascade was already decided

Terraform's prevent_destroy

A resource forced to replace because of an immutable attribute change can still be blocked from actually being destroyed — but only if a lifecycle { prevent_destroy = true } block was added to that resource ahead of time. It's the exact same shape as UpdateReplacePolicy: a separate, easy-to-skip setting that has to exist before the triggering change ever shows up in a plan.

same idea, different IaC engine

Kubernetes PersistentVolume reclaimPolicy

Delete a PersistentVolumeClaim and whether the underlying storage volume is actually destroyed or kept around depends on the StorageClass's reclaimPolicy — Delete or Retain — a setting chosen when the StorageClass was created, possibly years before anyone ran the kubectl delete that triggered it.

the policy predates the trigger

A few things worth knowing

  • A change set doesn't execute itself — creating one is always a separate step from executing it; you (or a CI pipeline gated by manual approval) explicitly choose to execute, exactly like reviewing a Terraform plan before apply.
  • Drift detection is on-demand, not continuous — CloudFormation doesn't watch resources in real time; you (or a scheduled job) trigger a drift detection run, and it reports per-resource IN_SYNC / MODIFIED / DELETED.
  • cdk bootstrap is a one-time per-account/region setup — CDK needs an S3 bucket and IAM roles of its own to stage synthesized assets before it can deploy; this runs once, not per deployment.
