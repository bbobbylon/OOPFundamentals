AWS-Native IaC — CloudFormation & CDK

Terraform is cloud-agnostic; CloudFormation is AWS's own IaC engine, and the state file you'd manage yourself in Terraform is instead tracked for you inside every stack. CDK doesn't replace CloudFormation — it generates it, letting you write real TypeScript or Python instead of YAML.

🧱 If Terraform already does IaC, why does AWS have its own version?

CloudFormation is AWS's native, declarative IaC service: you write a template (YAML or JSON) describing resources, and CloudFormation manages the entire lifecycle as a named stack — creating, updating, and rolling back resources as one atomic unit. The key difference from Terraform is who owns the state: Terraform's state file is your responsibility (stored remotely, must be locked, can drift out of sync); a CloudFormation stack's state lives inside AWS itself — there's no file to lose, back up, or corrupt. Where Terraform's plan shows a diff, CloudFormation's equivalent is a change set: a preview of exactly what an update will create, modify, or replace, which you review and then execute — nothing happens until you do. CloudFormation also runs drift detection: since it knows the exact template that created each resource, it can compare that record against the resource's actual current state in AWS and flag anything changed outside the stack (someone editing a security group rule by hand in the console, for example). CDK (Cloud Development Kit) sits on top of CloudFormation rather than replacing it: you write actual TypeScript, Python, Java, or C# — with loops, conditionals, functions, and reusable classes called constructs — and running cdk synth compiles that code down into a plain CloudFormation template. cdk deploy then synthesizes and hands that template to CloudFormation exactly as if you'd written the YAML by hand. CDK's real value is abstraction: a single new Bucket(this, 'Uploads') construct expands into dozens of lines of CloudFormation (bucket policy, encryption config, public-access block) with secure defaults already applied.

  • Stack, not state file — CloudFormation tracks what it manages internally; there's no state file for you to store, lock, or lose.
  • Change set = plan — a change set previews create/modify/replace before anything executes, same safety idea as terraform plan.
  • Drift detection — CloudFormation can compare a resource's live AWS state against what the template says it should be, and flag manual out-of-band edits.
  • CDK compiles to CloudFormation — cdk synth turns real code (constructs) into a template; CDK never talks to AWS directly, CloudFormation still executes everything.

"Replace" is the change set outcome to fear

Some property changes (like an RDS instance's engine version, or renaming certain resources) can't be updated in place — CloudFormation must delete and recreate. A change set always tells you up front which resources are Modify (safe, in-place) vs Replace (destructive) before you execute it.

CDK constructs have three abstraction levels (L1/L2/L3)

L1 (CfnBucket) is a 1:1 mirror of a raw CloudFormation resource. L2 (Bucket) adds sane defaults and helper methods. L3 "patterns" (like ApplicationLoadBalancedFargateService) wire together many resources — a whole VPC, ALB, and ECS service — from one construct call.

A stack rollback is automatic on failure

If any resource in a CloudFormation update fails to create or update, the entire stack automatically rolls back every resource to its pre-update state — you never end up with half the change applied, unlike a script that fails partway through.

The CIAM parallel: a CDK Stack that provisions a Cognito user pool, an API Gateway with a JWT authorizer, and the Lambda functions behind it is the AWS-native version of provisioning this codebase's own identity infrastructure — the same "app registration, secrets, redirect URIs" concerns from the Terraform page's CIAM note, just expressed as real code with type-checked resource references instead of HCL string interpolation.

A few things worth knowing

  • A change set doesn't execute itself — creating one is always a separate step from executing it; you (or a CI pipeline gated by manual approval) explicitly choose to execute, exactly like reviewing a Terraform plan before apply.
  • Drift detection is on-demand, not continuous — CloudFormation doesn't watch resources in real time; you (or a scheduled job) trigger a drift detection run, and it reports per-resource IN_SYNC / MODIFIED / DELETED.
  • cdk bootstrap is a one-time per-account/region setup — CDK needs an S3 bucket and IAM roles of its own to stage synthesized assets before it can deploy; this runs once, not per deployment.
