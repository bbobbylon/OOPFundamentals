From git push to Production

This hub teaches CI/CD, Docker, Kubernetes, and cloud compute as separate, deep tracks. This page is the capstone that ties them together: which combination do you actually pick, for a given kind of app, and what does the real end-to-end path from a commit to a live URL look like? docs/DEPLOYMENT.md documents deploying this specific repo — this page teaches the general decision underneath it.

🚀 "Deploy it" is really four separate decisions

Every deploy path — no matter the app — answers the same four questions in order, and the tracks in this hub each cover one of them in depth without necessarily showing how they chain together. (1) What builds and validates the code? A CI pipeline (GitHub Actions) runs on every push — compile, test, lint — and fails fast before anything gets near production. (2) What format does the built app ship as? A container image (Dockerfile), a static asset bundle, or a deployment-specific zip — the choice depends entirely on what runs it next. (3) What actually runs it? A container orchestrator (Kubernetes, ECS), a serverless platform (Lambda), a CDN for static files, or a PaaS that hides all of this — each with very different operational cost. (4) How does new code become live traffic, safely? Rolling, blue-green, canary, or a feature flag (Deployment Strategies) — the last-mile decision this page's scenarios each end on.

  • The artifact format follows from the runtime, not the other way around — you don't pick "Docker" first; you pick "Kubernetes" first, and Docker follows because that's what Kubernetes runs.
  • A static SPA doesn't need a server at all — Angular's production build is just files; a CDN can serve it directly, with no container, no orchestrator, no compute to manage.
  • Serverless inverts the capacity question — instead of provisioning instances for peak load, a function runs only when invoked, and scales to zero when it isn't.
  • A PaaS collapses steps 2 and 3 into one — git push to a platform like Render/Railway builds AND runs the app, trading control for near-zero operational overhead.

CIAM angle — secrets never travel through the artifact

A Docker image, a Lambda zip, or a static bundle should never contain a JWT signing key, a database password, or an OAuth client secret baked in — those are injected at the TARGET (Kubernetes Secret, ECS task definition environment, Lambda environment variables, App Runner/Container Apps config) at deploy or runtime, never committed into the artifact that CI produced. The problem

You wire the Angular SPA pipeline exactly like the Docker/Kubernetes one above — build once, promote the same files everywhere — and staging starts silently calling production's API.

Angular's own environment files quietly break "build once, promote everywhere"

Section 2 above says environments should differ only in config injected at the TARGET, never in the artifact itself — and the Spring Boot/Kubernetes scenario proves it works: the same Docker image runs in staging and prod, with only a Kubernetes Secret changing between them. You apply the identical discipline to the Angular pipeline: run ng build --configuration production once in CI, sync dist/browser/ to the staging bucket, run smoke tests, then sync those exact same files to the prod bucket with no rebuild.

But ng build never produced an environment-agnostic artifact. Angular's angular.json uses fileReplacements to swap environment.ts for environment.prod.ts BEFORE compilation, and every value inside it — apiUrl, feature flags, an OAuth client ID — gets inlined as a literal string directly into main.[hash].js. There is no separate config file sitting next to index.html for a deploy target to inject values into afterward; the only artifact you built already has "https://api.prod.example.com" compiled into its source, indistinguishable from any other string in the bundle. Promoting that exact build to staging doesn't make staging test itself — it makes staging silently call production's API.

ng build ran clean, dist/browser/ produced correctly ✓ the exact same files synced to both buckets ✓ assumed config lives outside the bundle, like it does for a container ⚠

"Promotable unchanged across environments" holds for anything that reads its config at START-UP — a static SPA's default build reads it at BUILD time, and once the bundle exists, that door is already closed.

Give the SPA a config it reads at runtime, not build time
Stop treating environment.prod.ts as your deploy-time config ↓ it's Angular's build-time seam, genuinely useful for build-only differences like enabling production optimizations — the wrong tool for anything that must differ per deployed environment Fetch a small config.json (or read a window.__env global) at app bootstrap ↓ a plain static file living next to index.html, fetched before the app renders, restores exactly the "same artifact, different config per target" property Section 2 promised — because the value is now genuinely injected at the target Or accept the rebuild, and stop calling it "the same artifact" ↓ building one bundle per environment is a legitimate choice, but staging and prod are now honestly two different artifacts — the "never test what you're not about to ship" promise needs its own story for that
The one-sentence rule. The mechanism

Follow one apiUrl value from a TypeScript file into a compiled bundle that can never be told anything different again.

  1. CI runs ng build --configuration productionbuild
  2. angular.json's fileReplacements swaps environment.ts for environment.prod.ts BEFORE compilation — this happens once, at build timefile swap
  3. The bundler inlines environment.prod.ts's exported object directly into main.[hash].js as literal valuesinlined
  4. dist/browser/ is synced to the staging bucket unchanged, exactly like "one artifact, many targets" recommendspromote
  5. The browser loads main.[hash].js on staging — apiUrl is still the production string, because copying files doesn't rewrite JS sourceno rewrite
  6. Every request from "staging" now silently hits the production API — no build error, no runtime warning, nothing obviously wrong in the network tabsilent

Step 3 is the whole trap. Nothing about steps 1, 2, or 4 is a mistake — this is exactly how Angular's environment files are documented to work, and exactly how "promote the same artifact everywhere" is documented to work elsewhere on this page. The two documented behaviors just can't both be true for a static SPA at the same time.

"Promote the same artifact, unchanged, to every environment" — applied to three different TARGET typesSection 2's rule, tested against reality
each target's config model reacts differently ↓
Docker image (Kubernetes) — config injected as env vars at container start, artifact never touched Static bundle (CDN) — apiUrl already compiled into main.js at build time, nothing left to inject Lambda zip — config set on the function's environment variables, read at invocation, artifact never touched

Two of these three targets read their configuration when they start running, which is exactly what makes "the same artifact everywhere" true for them. The static bundle is the surprising reactor — its configuration was decided the moment ng build finished, long before any target ever sees it.

Where you have seen this before

"Config decided at build time instead of start-up time" is a trap waiting in nearly every static-site toolchain, and even inside Docker itself.

React and Vue hit the identical wall — this isn't an Angular quirk

Create React App's process.env.REACT_APP_* variables and Vite's import.meta.env.VITE_* variables are ALSO inlined into the bundle at build time by the bundler's define/replace step. Any static-site framework's default build-time environment approach hits this exact limitation — and the runtime-config-fetch workaround is the same fix across all of them, not something specific to Angular.

the same gap, three different frontend frameworks

Spring Boot's config model is exactly why the Kubernetes scenario above never hits this

Spring reads application.properties and environment variables at process START-UP through its Environment abstraction, not at compile time — the identical .jar can run against a different DATABASE_URL in staging vs. prod because nothing about that value was ever baked into a .class file. This is precisely why "one artifact, config injected at the target" works cleanly for the Spring/K8s scenario at the top of this page, and needs a workaround for the CDN one.

the reason this page's own first scenario is immune

A Dockerfile's ARG instead of ENV can reintroduce the identical bug

Dockerfile ARG values are baked in at image BUILD time and disappear from the running container, unlike ENV, which stays readable and overridable at runtime. Using ARG for something like a database URL bakes it into the image the exact same way ng build bakes apiUrl into main.js — the same mistake, hiding inside the container path this page treats as the safe one.

The "TARGET" decision drives everything upstream of it. Picking Kubernetes means you need a Docker image, which means you need a registry, which means CI needs a build+push step. Picking a static CDN means none of that exists — the artifact IS the deploy. Decide the target first; the rest of the pipeline follows from it.

2. Where secrets enter — and where they must NOT

✗ Baked into the artifact

# Dockerfile — NEVER do this
ENV JWT_SECRET="prod-secret-abc123"
# now it's in the image, the registry,
# and every layer's history, forever

✓ Injected at the target, at deploy/runtime

# Kubernetes Secret, mounted as an env var —
# the IMAGE is identical across dev/staging/prod
env:
  - name: JWT_SECRET
    valueFrom:
      secretKeyRef: { name: app-secrets, key: jwt }
The same built artifact should be promotable across every environment unchanged — dev, staging, and prod differ only in the config/secrets injected at the TARGET, never in the artifact itself. If the Docker image (or zip, or bundle) differs between staging and prod, you're no longer testing what you're about to ship.
