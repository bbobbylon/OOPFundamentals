From git push to Production

This hub teaches CI/CD, Docker, Kubernetes, and cloud compute as separate, deep tracks. This page is the capstone that ties them together: which combination do you actually pick, for a given kind of app, and what does the real end-to-end path from a commit to a live URL look like? docs/DEPLOYMENT.md documents deploying this specific repo — this page teaches the general decision underneath it.

🚀 "Deploy it" is really four separate decisions

Every deploy path — no matter the app — answers the same four questions in order, and the tracks in this hub each cover one of them in depth without necessarily showing how they chain together. (1) What builds and validates the code? A CI pipeline (GitHub Actions) runs on every push — compile, test, lint — and fails fast before anything gets near production. (2) What format does the built app ship as? A container image (Dockerfile), a static asset bundle, or a deployment-specific zip — the choice depends entirely on what runs it next. (3) What actually runs it? A container orchestrator (Kubernetes, ECS), a serverless platform (Lambda), a CDN for static files, or a PaaS that hides all of this — each with very different operational cost. (4) How does new code become live traffic, safely? Rolling, blue-green, canary, or a feature flag (Deployment Strategies) — the last-mile decision this page's scenarios each end on.

  • The artifact format follows from the runtime, not the other way around — you don't pick "Docker" first; you pick "Kubernetes" first, and Docker follows because that's what Kubernetes runs.
  • A static SPA doesn't need a server at all — Angular's production build is just files; a CDN can serve it directly, with no container, no orchestrator, no compute to manage.
  • Serverless inverts the capacity question — instead of provisioning instances for peak load, a function runs only when invoked, and scales to zero when it isn't.
  • A PaaS collapses steps 2 and 3 into one — git push to a platform like Render/Railway builds AND runs the app, trading control for near-zero operational overhead.

This repo's own real path

docs/DEPLOYMENT.md + deploy/aws/* and deploy/azure/* show this exact decision made concretely for this app: Spring Boot backend → Docker image → AWS App Runner or Azure Container Apps (both PaaS-like container runtimes — no Kubernetes cluster to operate), Angular frontend → static build → served alongside or from a CDN.

"Environment" means more than one thing

dev → staging → prod as environments is a separate axis from the deploy MECHANISM covered here — the same CI→package→target→traffic-cutover path typically runs once per environment, usually gated so staging deploys automatically and prod requires an approval step.

CIAM angle — secrets never travel through the artifact

A Docker image, a Lambda zip, or a static bundle should never contain a JWT signing key, a database password, or an OAuth client secret baked in — those are injected at the TARGET (Kubernetes Secret, ECS task definition environment, Lambda environment variables, App Runner/Container Apps config) at deploy or runtime, never committed into the artifact that CI produced. This scaffold's own .env.example + real secrets manager convention follows exactly this rule.

The "TARGET" decision drives everything upstream of it. Picking Kubernetes means you need a Docker image, which means you need a registry, which means CI needs a build+push step. Picking a static CDN means none of that exists — the artifact IS the deploy. Decide the target first; the rest of the pipeline follows from it.

2. Where secrets enter — and where they must NOT

✗ Baked into the artifact

# Dockerfile — NEVER do this
ENV JWT_SECRET="prod-secret-abc123"
# now it's in the image, the registry,
# and every layer's history, forever

✓ Injected at the target, at deploy/runtime

# Kubernetes Secret, mounted as an env var —
# the IMAGE is identical across dev/staging/prod
env:
  - name: JWT_SECRET
    valueFrom:
      secretKeyRef: { name: app-secrets, key: jwt }
The same built artifact should be promotable across every environment unchanged — dev, staging, and prod differ only in the config/secrets injected at the TARGET, never in the artifact itself. If the Docker image (or zip, or bundle) differs between staging and prod, you're no longer testing what you're about to ship.

3. One-sentence recap

🚀 Every deploy answers the same four questions in order — what builds it (CI), what format it ships as (Docker image / static bundle / zip), what runs it (orchestrator / CDN / serverless / PaaS) — and how new code safely becomes live traffic, which is exactly what Deployment Strategies covers next.
