Python Async / Await & asyncio

Coroutines, the event loop, asyncio.gather(), task cancellation, and the #1 gotcha: blocking the event loop with synchronous calls.

⚡ What is Python async/await — and how does it differ from Java threads or Angular Observables?

Python's async/await is cooperative concurrency — many I/O-bound operations on a single thread, no OS-thread overhead. An async def coroutine doesn't run when called; you await it, which suspends it and hands control to the event loop to run other coroutines until the I/O completes (the same model as JavaScript's loop). asyncio.gather() runs coroutines concurrently — three sequential 300ms calls become ~300ms. The fatal trap: a blocking call (time.sleep, requests.get) freezes the whole loop — use asyncio.sleep/httpx instead.

  • Cooperative, single-threaded concurrency — great for I/O, not CPU.
  • await suspends to the event loop — other coroutines run during the wait.
  • gather() overlaps awaits — N sequential calls collapse to ~the slowest.
  • Never block the loop — await asyncio.sleep/httpx, never time.sleep/requests.

or, the exception that stops you without stopping anything else

The problem

gather() raised. You caught it, logged it, and moved on. Two more coroutines kept running behind your back for as long as they felt like it.

except ValueError: looked like it caught everything gather() was doing

Provisioning a new user fans out to three IDPs at once: await asyncio.gather(create_in_ping(user), create_in_entra(user), create_in_keycloak(user)), wrapped in a try/except. create_in_ping raises — duplicate email — almost immediately. You catch it, log "provisioning failed," and tell the caller no account was created.

create_in_entra and create_in_keycloak were never told any of that happened. A second later — after your response already went out — they finish on their own and create real accounts in Entra and Keycloak for a user your own API just told everyone does not exist.

gather() raises the FIRST exception ✓ — exactly as documented the other two coroutines get cancelled ⚠ — they do not they keep running, unobserved, until they finish on their own ✓

Your except block was never lying to you — create_in_ping really did fail. It just wasn't the whole story, and gather() never promised to tell you the rest.

Ask for cancel-on-failure explicitly — or stop assuming it's automatic
Swap gather() for asyncio.TaskGroup() (3.11+) ↓ the instant one task in the group raises, TaskGroup cancels every other task in it — structured concurrency, not opt-in Or track the tasks yourself and cancel on failure ↓ asyncio.create_task() each call, catch the exception, then call .cancel() on whatever is left running Or pass return_exceptions=True and check every result yourself — nothing gets cancelled, but nothing surprises you either
asyncio.gather()'s job is to propagate the first exception — not to stop the others. With its default return_exceptions=False, the moment one awaited coroutine raises, that exception is thrown into whatever is awaiting gather(), immediately. The remaining coroutines are left exactly as they were: scheduled, running, and completely unaware that a sibling failed, because nothing in gather()'s contract ever cancels them for you.
asyncio.gather() raising is a fire alarm that gets you out of the building. It does not lock the doors behind you. Everyone else you left inside keeps working until they're done, or until they hit something on fire themselves — and nobody who left with you will ever know which.

The event loop

The mechanism

Watch what gather() actually does the moment one coroutine raises.

  1. gather(a(), b(), c()) wraps each coroutine in its own Task and starts all threeall scheduled
  2. Your await gather(...) suspends, waiting for every Task to finishwaiting
  3. a() raises first — gather immediately re-raises that exception to your awaiting codefirst failure wins
  4. gather does NOT call .cancel() on b()'s or c()'s Taskno cancellation — default
  5. Your except block runs, and your function returns or moves onyou've moved on
  6. b() and c() are still live on the same event loop — they run to completion, or fail, entirely on their ownstill running

Step 4 is the one line of behavior nowhere in your code. You never told gather to leave the others running, and you never told it to cancel them either — you just never had to, because Python defaults to leaving them alone. Structured concurrency (TaskGroup) exists specifically to flip that default.

All three launched await gather(ping(), entra(), keycloak()) → three Tasks start running concurrently
One fails ping() raises ValueError → gather re-raises it to your await, immediately
The rest keep going (no signal sent to them at all) → entra() and keycloak() run to completion, unseen, after you've already told the caller it failed

Read the middle state again: the trigger for "the rest keep going" is nothing — no cancellation, no notification, not even a log line. That blank is the entire bug. Everything gather() does is correct and documented; the missing state transition is the one you assumed existed and nobody wrote.

A checkout handler wraps asyncio.gather(charge_card(order), reserve_inventory(order), send_confirmation(order)) in a try/except. reserve_inventory raises OutOfStockError almost immediately; charge_card needs two more seconds to finish. You catch the error and tell the customer "out of stock, nothing was charged." What is actually true two seconds later?

This is the exact assumption gather() doesn't back up. No cancellation is sent to any sibling coroutine when one of them raises — not by default, and not automatically.

Right. charge_card() has no idea reserve_inventory() failed, and gather() never told it to stop. It keeps running on the event loop and completes on its own two seconds later — after the customer already heard "nothing was charged."

Your except block already ran and finished by the time charge_card() completes — there is nothing left awaiting gather() to receive a second exception into. If charge_card() also raises, asyncio just logs "Task exception was never retrieved" — silently, in a place nobody is looking.

Where you have seen this before

"The group fails fast, but the group doesn't stop" is not an asyncio quirk — it shows up anywhere concurrent work is fanned out and joined.

Java's CompletableFuture.allOf(...)

If one future in the set completes exceptionally, the combined future returned by allOf also completes exceptionally — but the other futures are not cancelled. They keep executing on their own executor threads to whatever result they were going to reach anyway.

allOf fails fast ✓sibling futures cancelled ⚠ — they are not

Several Spring @Async calls fired in parallel

Kick off three @Async methods from one service call and each returns its own independent CompletableFuture. One throwing does nothing to the others — there is no shared cancellation unless you wire an ExecutorService and cancel the rest yourself.

independent futures ⚠ one failing touches nothing else

JavaScript's Promise.all()

Rejects the instant one promise rejects — but JS promises cannot be cancelled at all. The other promises keep running to whatever they were going to resolve or reject to, and an unhandled rejection from one of them shows up later as a console warning nobody connects back to the request that already finished.

Promise.all rejects fast ✓the losing promises ⚠ — un-cancellable, keep running
The whole page on a napkin: the event loop runs many coroutines on one thread, suspending each at its await points so others can make progress, and gather/TaskGroup/queues give you patterns for running several at once. The one new sentence this block adds: gather()'s default behavior fails fast for YOU but does not fail fast for the group — the siblings of a raised exception keep running, unseen, unless you reach for TaskGroup or cancel them yourself.

1. The Event Loop Mental Model

Single thread, multiple coroutines

One thread runs the event loop. Coroutines voluntarily yield at await points, letting others run. No true parallelism — but I/O-bound tasks overlap perfectly because they spend most of their time waiting, not computing.

import asyncio

async def fetch(url):  # a coroutine function — calling it doesn't run the body yet
    await asyncio.sleep(1)  # yields control
    return f"data from {url}"

async def main():
    # Both run "concurrently" — total ~1s
    a, b = await asyncio.gather(  # runs BOTH coroutines concurrently, waits for both to finish
        fetch("api-1"),
        fetch("api-2")
    )

asyncio.run(main())  # the ONE entry point from sync code — creates the loop, runs, closes it

Concurrency vs Parallelism

asyncio: 1 thread, concurrent I/O (network, disk). Best for I/O-bound tasks.

threading: multiple threads, the GIL limits true CPU parallelism. OK for I/O-bound.

multiprocessing: multiple processes, true parallelism, bypasses GIL. Best for CPU-bound.

asyncio.to_thread(): run sync blocking code in a thread pool without blocking the event loop.

2. async / await Rules

You can only await awaitables

async def good():
    # ✓ await a coroutine
    result = await fetch_data()
    # ✓ await asyncio primitives
    await asyncio.sleep(0)  # yield once
    # ✓ await asyncio.Task / Future
    task = asyncio.create_task(work())
    await task

The blocking trap

⚠️ NEVER do this in async code:
time.sleep(5) — blocks the ENTIRE thread
requests.get(url) — synchronous HTTP
open(file).read() — synchronous file I/O

Use instead:
await asyncio.sleep(5)
await httpx.get(url) or aiohttp
await asyncio.to_thread(open(f).read)

3. Task Patterns

import asyncio

# gather: run all, wait for all, return list of results
results = await asyncio.gather(task1(), task2(), task3())

# create_task: fire and not necessarily wait (runs in background)
task = asyncio.create_task(background_sync())
await other_work()
await task  # collect result later

# TaskGroup (Python 3.11+): structured concurrency
async with asyncio.TaskGroup() as tg:
    t1 = tg.create_task(fetch("api-1"))
    t2 = tg.create_task(fetch("api-2"))
# both tasks done here — any exception cancels the group

# Timeout (Python 3.11+)
async with asyncio.timeout(5.0):
    result = await slow_fetch()  # TimeoutError if > 5s
