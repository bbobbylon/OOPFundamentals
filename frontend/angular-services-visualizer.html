Services & Dependency Injection

A service is just a class. Dependency injection is Angular handing you instances of that class instead of you saying new Service(). The whole DI system exists to make code testable, swappable, and shareable.

Why services exist — the "before/after"

❌ Without a service — duplication everywhere

export class HeaderComponent {
  getUser() {
    return fetch('/api/me').then(r => r.json());
  }
}

export class ProfileComponent {
  getUser() {
    return fetch('/api/me').then(r => r.json());
  }
}

export class SidebarComponent {
  getUser() {
    return fetch('/api/me').then(r => r.json());
  }
}

// 3× the code, 3× the bugs, untestable.

✅ With a service — one source of truth

@Injectable({ providedIn: 'root' })
export class UserService {
  getUser() {
    return fetch('/api/me').then(r => r.json());
  }
}

export class HeaderComponent {
  private userSvc = inject(UserService);
  user$ = this.userSvc.getUser();
}
export class ProfileComponent {
  private userSvc = inject(UserService);
  user$ = this.userSvc.getUser();
}
// All 3 components get the SAME instance
// → if one caches the user, the others see it too.

The two ways to inject — constructor vs inject()

Old way — constructor injection

export class ProfileComponent {
  constructor(
    private userSvc: UserService,
    private router: Router
  ) {}
}

Works in all Angular versions. Verbose but explicit.

Modern way — inject() function (v14+)

export class ProfileComponent {
  private userSvc = inject(UserService);
  private router  = inject(Router);
}

Cleaner. Required for standalone route guards & functional guards. Cannot be called inside callbacks — only in constructors, field initializers, factory functions.

Both produce identical behavior. New code should prefer inject(). Don't mix them in the same class — pick one style per component.

Where the service lives — provider scope

The providedIn option controls how many instances exist and who can inject it. Pick the smallest scope you can — services that don't need to be global shouldn't be.

Where providedHow many instancesTree-shaken if unused?Use for
providedIn: 'root'One — singleton for the whole app✅ YesMost services. HTTP services, auth, app state.
providedIn: 'platform'One per page/iframe — shared across multiple Angular apps on the same page✅ YesRare. Micro-frontends.
providedIn: 'any'One per lazy-loaded module✅ YesPer-feature isolation.
providers: [Svc] on a componentOne per component instance + its children—Per-component state (a service for ONE form, etc).
providers: [Svc] on a moduleOne per module (old NgModule style)—Legacy code. Modern: use providedIn.
 
// Singleton — one instance app-wide. Default for 99% of services.
@Injectable({ providedIn: 'root' })
export class UserService { ... }

// Component-scoped — each <app-cart> gets its OWN CartStore instance.
@Component({
  selector: 'app-cart',
  providers: [CartStore],             // new instance per <app-cart> on the page
  template: `...`
})
export class CartComponent {
  store = inject(CartStore);
}

The injector tree — how Angular finds your service

Every component has its own injector. When you ask for a service, Angular walks UP the component tree, then to the module / root injector, until it finds a provider. If nothing provides it, you get the dreaded NullInjectorError.

📦 Root injector ← providedIn: 'root' services live here
└─ UserService, AuthService, ApiService ...
   └─ <app-root> injector
      └─ <app-shell> injector
         ├─ <app-header>
         └─ <app-main> injector
              └─ <app-cart> injector providers: [CartStore]
                   └─ CartStore ← lives HERE, not in root
                       └─ <app-cart-item> → asks for CartStore
                            ↑ walks up, finds it at <app-cart>

Walking up means: child components get the same instance as their parent provided. If <app-cart-item> asks for CartStore, it gets the one from its parent <app-cart>. If a SECOND <app-cart> exists on the page, IT has its own CartStore — completely independent.

Swapping implementations — the real power of DI

Code depends on the abstraction, not the implementation. In tests or different environments, swap which concrete class gets injected without touching component code. 

// Abstract API the rest of the app depends on
export abstract class Logger {
  abstract log(msg: string): void;
}

// Real implementation
export class ConsoleLogger extends Logger {
  log(msg: string) { console.log(msg); }
}

// Test implementation
export class FakeLogger extends Logger {
  logs: string[] = [];
  log(msg: string) { this.logs.push(msg); }
}

// In your main.ts — register the real one for the app
bootstrapApplication(AppComponent, {
  providers: [
    { provide: Logger, useClass: ConsoleLogger }
  ]
});

// In a test — register the fake
TestBed.configureTestingModule({
  providers: [{ provide: Logger, useClass: FakeLogger }]
});

// Components don't change — they just ask for Logger
export class LoginComponent {
  private log = inject(Logger);   // gets ConsoleLogger in prod, FakeLogger in tests
}

Provider recipes — the four ways to register

// 1. useClass — instantiate this class (default)
{ provide: Logger, useClass: ConsoleLogger }

// 2. useValue — use this exact value (great for config)
{ provide: API_URL, useValue: 'https://api.example.com' }

// 3. useFactory — call this function to produce the value
{
  provide: ApiClient,
  useFactory: (config: AppConfig) => new ApiClient(config.url),
  deps: [AppConfig]   // what the factory needs injected
}

// 4. useExisting — alias one token to another
{ provide: OldLogger, useExisting: NewLogger }   // backwards compat

InjectionToken — for things that aren't classes

Want to inject a string, a number, or a config object? You can't use the value as the token (it'd collide with everyone else's). Create an InjectionToken: 

// tokens.ts
export const API_URL = new InjectionToken<string>('API_URL');

// main.ts — provide a value
bootstrapApplication(AppComponent, {
  providers: [
    { provide: API_URL, useValue: 'https://api.example.com' }
  ]
});

// somewhere — inject it
export class UserService {
  private apiUrl = inject(API_URL);   // → 'https://api.example.com'
  private http   = inject(HttpClient);

  getUsers() { return this.http.get(`${this.apiUrl}/users`); }
}

The three injector trees

Modern Angular actually has three distinct injector hierarchies — knowing which is which makes the resolution rules far less mysterious. They form a chain: an ElementInjector first asks itself and its component-tree ancestors, then falls back to the EnvironmentInjector (route- or app-level), then to the root ModuleInjector.

InjectorCreated byHoldsLifetime
ModuleInjectorBootstrap + NgModulesprovidedIn: 'root' services, app-wide providersWhole app
EnvironmentInjectorbootstrapApplication, route providers, createEnvironmentInjectorRoute-scoped services, lazy feature providersRoute / feature lifetime
ElementInjectorEvery component & directive instanceComponent-level providers: [...]Component instance lifetime
 
// Lookup order when you do inject(MyService):
  ElementInjector chain (this component → parent → grandparent → ...)
      ↓
  EnvironmentInjector chain (route → parent route → app-level)
      ↓
  Platform / NullInjector  → if still not found → NullInjectorError

Route-level providers in the new provideRouter world create their own EnvironmentInjector — that's how a feature route can have its own state without polluting the root.

Resolution modifiers — control where Angular looks

By default, inject(X) walks up the whole chain. Four modifiers let you change that — pass them as options to inject() or use the legacy decorator form on constructor params.

ModifierMeaningUse when
{ optional: true } / @Optional()Return null instead of throwing if not providedOptional dependency, multi-tenant configs
{ self: true } / @Self()Only look in the current injector — don't walk upForms (NgControl on the host element only)
{ skipSelf: true } / @SkipSelf()Skip the current injector, start from parentRecursive directives finding the parent's instance
{ host: true } / @Host()Walk up only until the host component boundaryContent-projected components avoiding the outer app
 
// Modern inject() with options
export class ThemeAwareWidget {
  // Try to find a Theme; if nothing provides one, get null and use defaults.
  private theme = inject(Theme, { optional: true });

  // Only my OWN element-injector — error if I forgot providers: [Logger]
  private log = inject(Logger, { self: true });

  // Skip my own injector — get the PARENT's instance even if I provide my own
  private parentBus = inject(EventBus, { skipSelf: true });
}

// Combined — common with directive-on-form-control pattern
@Directive({ selector: '[appHighlight]' })
export class HighlightDirective {
  private ctrl = inject(NgControl, { optional: true, self: true });
}

Multi providers — many implementations under one token

With multi: true, multiple providers can register against the same token. Injecting that token gives you the array of all registered values — Angular itself uses this for HTTP_INTERCEPTORS, validators, and route guards. 

// Define a multi token
export const ANALYTICS_PLUGIN =
  new InjectionToken<AnalyticsPlugin[]>('ANALYTICS_PLUGIN');

// Register many implementations across the app
bootstrapApplication(AppComponent, {
  providers: [
    { provide: ANALYTICS_PLUGIN, useClass: GooglePlugin, multi: true },
    { provide: ANALYTICS_PLUGIN, useClass: AmplitudePlugin, multi: true },
    { provide: ANALYTICS_PLUGIN, useClass: ConsolePlugin, multi: true },
  ]
});

// Consume — you get the array, not one instance
export class Analytics {
  private plugins = inject(ANALYTICS_PLUGIN);   // AnalyticsPlugin[]
  track(event: string) {
    this.plugins.forEach(p => p.track(event));
  }
}

Circular dependencies — forwardRef

Two services referencing each other, or a class that refers to itself in a provider definition, hits a "Class not defined yet" error at module-load time. forwardRef(() => X) defers the lookup until injection time, by which point both classes exist. 

// ⚠ Without forwardRef — error: 'TreeNode is used before its declaration'
@Directive({
  selector: '[tree-node]',
  providers: [{ provide: PARENT, useExisting: TreeNode }]
})
export class TreeNode {}

// ✅ With forwardRef
@Directive({
  selector: '[tree-node]',
  providers: [{ provide: PARENT, useExisting: forwardRef(() => TreeNode) }]
})
export class TreeNode {}

If you're reaching for forwardRef in normal services, it's usually a sign two services should be merged or a third extracted. The legitimate uses are mostly with recursive directives and self-referential providers.

APP_INITIALIZER & ENVIRONMENT_INITIALIZER

Sometimes you need to run code before Angular bootstraps any component — load config from a server, hydrate a feature flag SDK, register a service worker. Two multi-tokens let you hook in. 

// APP_INITIALIZER — runs once; if it returns a Promise, bootstrap waits.
bootstrapApplication(AppComponent, {
  providers: [
    {
      provide: APP_INITIALIZER,
      multi: true,
      useFactory: () => {
        const config = inject(ConfigService);
        return () => config.load();   // Promise<void> — bootstrap waits
      }
    }
  ]
});

// ENVIRONMENT_INITIALIZER — fires the first time an EnvironmentInjector is created.
// Great for feature-route setup.
export const FEATURE_ROUTES: Routes = [{
  path: 'admin',
  providers: [
    {
      provide: ENVIRONMENT_INITIALIZER,
      multi: true,
      useValue: () => inject(AdminAnalytics).enable()
    }
  ],
  loadChildren: () => import('./admin/routes').then(m => m.routes)
}];

Functional DI — guards, resolvers, interceptors

Modern Angular replaced class-based guards/resolvers/interceptors with plain functions. inject() works inside them because they execute in an injection context. Far less boilerplate than the old class form. 

// Functional guard — was a class implementing CanActivate
export const authGuard: CanActivateFn = (route, state) => {
  const auth = inject(AuthService);
  const router = inject(Router);
  return auth.isLoggedIn() || router.createUrlTree(['/login']);
};

// Functional resolver
export const userResolver: ResolveFn<User> = (route) => {
  const users = inject(UserService);
  return users.byId(route.params['id']);
};

// Functional HTTP interceptor (v15+)
export const authInterceptor: HttpInterceptorFn = (req, next) => {
  const auth = inject(AuthService);
  const cloned = req.clone({ setHeaders: { Authorization: `Bearer ${auth.token}` } });
  return next(cloned);
};

// Wire them up
bootstrapApplication(AppComponent, {
  providers: [
    provideRouter([{ path: 'profile', component: ProfileComponent, canActivate: [authGuard] }]),
    provideHttpClient(withInterceptors([authInterceptor]))
  ]
});

Testing with TestBed & provider overrides

TestBed is the testing-time injector — it configures providers per test, then TestBed.inject(X) grabs the instance the same way inject(X) would in production. 

describe('CartService', () => {
  beforeEach(() => {
    TestBed.configureTestingModule({
      providers: [
        CartService,
        { provide: ApiClient, useClass: FakeApiClient },   // swap the dependency
        { provide: API_URL, useValue: 'http://test' }
      ]
    });
  });

  it('sums items', () => {
    const cart = TestBed.inject(CartService);
    cart.add({ price: 10 });
    cart.add({ price: 15 });
    expect(cart.total).toBe(25);
  });
});

// To override a provider for ONE test:
TestBed.overrideProvider(Logger, { useValue: new SilentLogger() });

Common services you'll meet

HttpClient

From @angular/common/http. Returns Observables. Wrap in your own service so components don't talk to HTTP directly.

inject(HttpClient).get<User>('/api/me')

Router

Programmatic navigation when a template [routerLink] isn't enough.

inject(Router).navigate(['/users', id])

ActivatedRoute

Current route's params, queryParams, data. Inject in the routed component itself.

route = inject(ActivatedRoute);
id = this.route.snapshot.params['id'];

FormBuilder

Concise FormGroup/FormControl construction (covered in Reactive Forms).

fb = inject(FormBuilder);
form = this.fb.group({ ... });

Common mistakes

❌ new MyService()

Never instantiate services manually. You lose the singleton guarantee and break test mocking. Always inject.

❌ Putting state in providedIn: 'root' for a feature

Singletons hold state for the app's whole lifetime. If you provide a "CartService" in root, it survives navigating away from the cart — possibly stale. For feature-scoped state, scope the provider to the route or component.

❌ Calling inject() in a method

inject() only works in an "injection context" — constructors, field initializers, factory functions, route resolvers/guards/interceptors. In other places, capture it once in a field, then use that field.

❌ Circular dependencies between services

If A needs B and B needs A, you have a design smell. Extract the shared logic into a third service, or use an Observable / event bus instead. forwardRef is a band-aid, not a fix.

Bug table — DI symptoms & fixes

SymptomLikely causeFix
NullInjectorError: No provider for X X isn't providedIn: 'root' and no ancestor provides it Add providedIn: 'root', or list it in route/component providers
inject() must be called from an injection context Called inside setTimeout, a class method, or an event handler Inject in a field initializer/constructor; store the reference; use it later
"Class X is used before its declaration" Provider definition references its own class or a not-yet-loaded class forwardRef(() => X)
Two component instances unexpectedly share state Service is providedIn: 'root' (singleton) Move to providers: [] on the component for per-instance state
Lazy route's service is a new instance every navigation Service is provided on the route, not in root Decide intentionally: feature-scoped vs app-scoped
Interceptor never runs Old HTTP_INTERCEPTORS + new provideHttpClient() mix Use withInterceptors([fn]) with functional interceptors, or withInterceptorsFromDi() for the class form

Two instances of what should be a singleton Service imported via two different paths (case sensitivity, barrel mismatch) Unify import paths; check tsconfig.paths
inject(Token, { optional: true }) returns null unexpectedly Token isn't provided at this injector or above Provide it; or accept the fallback gracefully

Mental model

1. A service is just a class

Plain TS. The only Angular-specific thing is the @Injectable decorator that lets Angular's injector instantiate it.

2. DI is a container

You ask for a type, Angular hands you an instance. The container decides whether to create a new one or reuse an existing one, based on the provider scope.

3. Components depend on abstractions

Components shouldn't know how a service does its job — only its interface. This is what makes Angular code testable.

4. Smallest scope that works

providedIn: 'root' is the safe default for stateless services. For state, scope to the route or component so it's destroyed when the user leaves.
