Docker Networking

How containers talk to each other, to the host, and to the internet. Port mapping, user-defined networks, and DNS resolution.

What is Docker networking — and how do containers communicate with each other and the outside world?

Each Docker container gets its own network namespace — its own virtual network interface, IP address, and routing table. By default, containers are isolated from each other and from the host. Docker provides several network drivers to connect them. Bridge network (default): Docker creates a virtual switch (docker0) on the host. Containers on the same bridge can communicate by IP. User-defined bridge networks are better than the default — they provide automatic DNS resolution by container name. On the default bridge, you must use IP addresses; on a user-defined bridge, http://ciam-auth:8080 works because Docker's embedded DNS resolves container names. Port mapping: containers are isolated by default — no external access. -p 8080:8080 (host-port:container-port) punches a hole: traffic hitting the host's port 8080 is forwarded to the container's port 8080. -p 127.0.0.1:8080:8080 restricts to localhost only (more secure). Without -p, the container is only accessible from other containers on the same network. Host network: --network host — container shares the host's network stack. Container port 8080 IS host port 8080 — no port mapping needed, no isolation. Faster but loses container network isolation. Linux only (not available on Docker Desktop for Mac/Windows). None network: complete network isolation. No network interface. For containers that should never make network calls (batch processors, compilers). DNS resolution: on user-defined bridge networks, Docker's embedded DNS server (running at 127.0.0.11 inside containers) resolves container names. ciam-auth resolves to that container's IP. This is the mechanism Docker Compose uses — service names in compose.yaml become DNS names. overlay network: for Docker Swarm or multi-host networking — spans multiple Docker hosts. Kubernetes handles its own networking (doesn't use Docker networks).

User-defined bridge

# Create user-defined network: docker network create ciam-net # Run containers on same network: docker run -d --name postgres \ --network ciam-net \ -e POSTGRES_PASSWORD=secret \ postgres:16 docker run -d --name ciam-auth \ --network ciam-net \ -p 8080:8080 \ -e DB_URL=jdbc:postgresql://postgres:5432/ciam \ myregistry/ciam:1.0 # ciam-auth CAN reach postgres by name: # jdbc:postgresql://postgres:5432/ciam # "postgres" resolves via Docker DNS! # External traffic can reach ciam-auth via port 8080 # External traffic CANNOT reach postgres # (no -p flag = port not exposed)

Kubernetes networking

Docker networking vs Kubernetes. Docker user-defined bridge → K8s Pod network (every pod gets an IP, pods can talk directly). Docker --network host → K8s hostNetwork: true. Docker -p 8080:8080 → K8s Service of type NodePort or LoadBalancer. Docker container name DNS (http://postgres) → K8s Service DNS (http://postgres.ciam-prod.svc.cluster.local). Docker Compose service: name → K8s: Service name. Docker doesn't manage multi-host networking in production — Kubernetes handles all of that with CNI plugins (Calico, Flannel, Cilium). Kubernetes NetworkPolicy is the equivalent of Docker firewall rules. Key difference: in Docker you control networking at container runtime with flags. In Kubernetes you declare it in YAML manifests and the CNI plugin implements it. For local dev, Docker networking is fine. For production multi-pod deployments, Kubernetes networking takes over.

CIAM local dev networking: Docker Compose creates a user-defined network automatically (named projectname_default) — all services on the same network, reachable by service name. Your ciam-auth Spring Boot container connects to postgres container via: spring.datasource.url=jdbc:postgresql://postgres:5432/ciam — "postgres" resolves via Docker DNS. It connects to Redis cache via spring.redis.host=redis. It connects to Ping Identity container via https://ping-server:9031. External traffic reaches only what you expose with ports: in compose.yaml. Best practice: expose only the Spring Boot port (8080) and the Ping admin UI port if needed — don't expose postgres (5432) externally in compose unless you're using a DB tool. Common debugging: docker exec -it ciam-auth curl http://postgres:5432 — if this fails with "connection refused" not "host not found", the network is fine but postgres isn't listening on that port in the container.

On the default bridge, containers can reach each other by IP but not by name. Use a user-defined bridge for DNS-based name resolution.

host — removes network isolation. Container shares the host's network stack directly. Port 8080 in the container IS port 8080 on the host — no mapping needed.

✓ Best performance (no NAT overhead). ✗ Container can conflict with host ports. Linux only — does not work on Docker Desktop for Mac/Windows (which uses a Linux VM).

none — completely disables networking. Container has no network interface except loopback (127.0.0.1). Completely isolated.

Use for batch jobs or security-sensitive workloads that must not make outbound calls, or for containers that communicate only via mounted volumes.

3 — Container DNS and Service Discovery

Default bridge — IP only ✗

# On default bridge, containers # can only reach each other by IP: docker run --name api myapp:1.0 docker run --name db postgres:16 # Inside 'api', you'd need: jdbc:postgresql://172.17.0.3:5432/db # Fragile! IPs change on restart.

User-defined bridge — DNS names ✓

# Create a named network first: docker network create app-net docker run --name api \ --network app-net myapp:1.0 docker run --name postgres \ --network app-net postgres:16 # Inside 'api', use the container name: jdbc:postgresql://postgres:5432/db # Docker DNS resolves "postgres" → IP

4 — Networking Command Reference

CommandWhat it does
docker network lsList all networks (bridge, host, none, and user-defined)
docker network create my-netCreate a user-defined bridge network
docker network inspect my-netShow connected containers and their IPs
docker network connect my-net containerAdd a running container to a network
docker network disconnect my-net containerRemove a container from a network
docker network rm my-netDelete a network (containers must be disconnected first)
docker run --network my-netStart container attached to a specific network
docker run -p 8080:8080Map host port 8080 to container port 8080
docker run --network hostShare host network stack (Linux only)
docker run --network noneNo network connectivity

Start Spring Boot on the SAME network docker run -d \ --name spring-api \ --network spring-net \ -p 8080:8080 \ -e SPRING_DATASOURCE_URL=jdbc:postgresql://postgres:5432/mydb \ -e SPRING_DATASOURCE_PASSWORD=secret \ myapp:1.0 # spring-api resolves "postgres" to the DB container's IP via Docker DNS. # No hard-coded IPs.
