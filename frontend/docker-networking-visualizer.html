Docker Networking

How containers talk to each other, to the host, and to the internet. Port mapping, user-defined networks, and DNS resolution.

🕸️ What is Docker networking — and how do containers communicate with each other and the outside world?

Each container gets its own network namespace (interface, IP, routing), isolated by default. Docker's drivers connect them. The default bridge is a virtual switch (docker0); a user-defined bridge is better because it adds automatic DNS — http://ciam-auth:8080 resolves by container name. Port mapping -p 8080:8080 punches a hole from the host into the container (without it, only same-network containers can reach it; bind to 127.0.0.1 to restrict to localhost). Host network shares the host stack (fast, no isolation, Linux-only); none gives total isolation. Compose builds a user-defined bridge automatically, which is why service names work as DNS — and Kubernetes replaces all of this with its own CNI networking in production.

  • Each container has its own net namespace — isolated by default.
  • User-defined bridge adds DNS — reach others by container name.
  • -p host:container exposes a port; bind 127.0.0.1 for localhost-only.
  • Compose auto-creates a bridge; K8s CNI takes over in production.

User-defined bridge

# Create user-defined network: docker network create ciam-net # Run containers on same network: docker run -d --name postgres \ --network ciam-net \ -e POSTGRES_PASSWORD=secret \ postgres:16 docker run -d --name ciam-auth \ --network ciam-net \ -p 8080:8080 \ -e DB_URL=jdbc:postgresql://postgres:5432/ciam \ myregistry/ciam:1.0 # ciam-auth CAN reach postgres by name: # jdbc:postgresql://postgres:5432/ciam # "postgres" resolves via Docker DNS! # External traffic can reach ciam-auth via port 8080 # External traffic CANNOT reach postgres # (no -p flag = port not exposed)

Network debugging

# List networks: docker network ls # bridge, host, none (defaults) + user-defined # Inspect network (see connected containers): docker network inspect ciam-net # Test connectivity from inside container: docker exec -it ciam-auth sh # Inside container: curl http://postgres:5432 # test DNS + TCP wget -O- http://ciam-auth:8080/actuator/health nslookup postgres # DNS lookup # Port mapping verification: docker port ciam-auth # 8080/tcp → 0.0.0.0:8080 # Connect running container to another network: docker network connect second-net ciam-auth # Remove container from network: docker network disconnect ciam-net ciam-auth

Kubernetes networking

Docker networking vs Kubernetes. Docker user-defined bridge → K8s Pod network (every pod gets an IP, pods can talk directly). Docker --network host → K8s hostNetwork: true. Docker -p 8080:8080 → K8s Service of type NodePort or LoadBalancer. Docker container name DNS (http://postgres) → K8s Service DNS (http://postgres.ciam-prod.svc.cluster.local). Docker Compose service: name → K8s: Service name. Docker doesn't manage multi-host networking in production — Kubernetes handles all of that with CNI plugins (Calico, Flannel, Cilium). Kubernetes NetworkPolicy is the equivalent of Docker firewall rules. Key difference: in Docker you control networking at container runtime with flags. In Kubernetes you declare it in YAML manifests and the CNI plugin implements it. For local dev, Docker networking is fine. For production multi-pod deployments, Kubernetes networking takes over.

CIAM local dev networking: Compose auto-creates a projectname_default network, so ciam-auth reaches postgres via jdbc:postgresql://postgres:5432/ciam, Redis via spring.redis.host=redis, and Ping via https://ping-server:9031 — all by service-name DNS. Only what you list under ports: is externally reachable; expose 8080 (and Ping admin if needed) but not postgres (5432). Debug tip: docker exec -it ciam-auth curl http://postgres:5432 — "connection refused" (not "host not found") means DNS is fine but the port isn't listening.

or, why the exact same connection string works in your terminal and fails in your container

The problem

"localhost" is not one address. It's a different address depending on which network namespace asks for it.

The JDBC URL didn't change. The result did.

Postgres runs natively on your Windows machine — not in Docker at all — listening on 127.0.0.1:5432. From PowerShell, psql -h localhost -p 5432 connects instantly. You containerize the Spring Boot app and leave SPRING_DATASOURCE_URL=jdbc:postgresql://localhost:5432/mydb exactly as it was, because why would it need to change — Postgres hasn't moved.

The container logs show Connection refused. Same host string, same port number, same driver. The only thing that changed is which process is asking "where is localhost," and that turns out to matter completely.

They are never the same thing Use the DNS name built for exactly this ↓ host.docker.internal resolves to the host machine from inside a container — built in on Docker Desktop; on Linux (20.10+) add --add-host=host.docker.internal:host-gateway Or skip reaching out to the host entirely ↓ containerize Postgres too and put both containers on the same user-defined network (Section 5 above) — then it's ordinary container-name DNS, no host boundary to cross at all
"localhost" is relative to whoever asks. It always means "my own loopback interface" — but a container's network namespace has its own loopback, completely separate from the host's, created fresh before the container's first line of code even runs. The string never crosses that boundary by itself, no matter how correct it looked a second ago in a terminal that wasn't inside a container.
Every container is a stranger in their own studio apartment, and every apartment's front door is labeled "localhost." Knocking on your own door doesn't reach the neighbor's apartment just because the labels match.

The mechanism

Trace the exact connection attempt from a terminal that works to a container that doesn't.

  1. Postgres runs directly on the host machine, bound to 127.0.0.1:5432not containerized
  2. psql -h localhost -p 5432 from a normal terminal connects immediatelyhost's own loopback
  3. Spring Boot container starts with the identical connection string, unchangedlooks correct
  4. Inside the container, "localhost" resolves to 127.0.0.1 — but that address now lives in the container's own namespacea different 127.0.0.1
  5. Nothing is listening on port 5432 inside the container's own loopback — the OS refuses the connectionrefused, not "host unreachable"
  6. Switching to host.docker.internal:5432, or containerizing Postgres onto a shared network, actually crosses the boundarythe real fix

Step 5 is worth sitting with: the error is "connection refused," not "host not found" or "timed out." That's the tell. A DNS failure or an unreachable host times out or says unknown host; "refused" means the connection reached a real network stack and a real (if empty) port — just the wrong stack's port.

Docker's network layer — bridge networks and container-name DNS live here

Three layers, three different answers to "what does localhost mean here." Section 1 above already showed you that container-to-container traffic needs a shared Docker network to resolve names — this is the same idea one layer further out: reaching the HOST from inside a container needs its own explicit bridge, because the innermost ring never automatically sees past its own walls.

Postgres runs directly on your Windows machine (not in Docker), and psql -h localhost -p 5432 connects fine from PowerShell. You containerize your Spring Boot app with SPRING_DATASOURCE_URL=jdbc:postgresql://localhost:5432/mydb left unchanged. The container logs show Connection refused. Why?

DNS isn't what fails here. "localhost" resolves to 127.0.0.1 instantly, every time, inside a container or out — there's no lookup to break. The problem is what 127.0.0.1 points to once you're inside the container's own namespace, not whether the name resolves.

Right. Every container gets its own private loopback interface, sealed off from the host's before the container even starts. The container asks its OWN 127.0.0.1 for something on port 5432, finds nothing, and refuses the connection. host.docker.internal, or containerizing Postgres onto the same network as Section 5 above, is what actually crosses that boundary.

There's no subnet access-control rule involved — the real story is simpler and stranger. The container isn't being blocked from reaching 127.0.0.1; it successfully reaches its OWN 127.0.0.1, which just has nothing running on port 5432.

Where you have seen this before

"My own namespace's localhost isn't the one I meant" shows up anywhere namespaces stack.

Kubernetes pods flip the rule

Inside a single Kubernetes pod, ALL containers (your app plus any Ping/Envoy sidecar) share ONE network namespace — so localhost genuinely DOES cross container boundaries there. That's the opposite rule from plain docker run, which is exactly why engineers moving between Compose locally and pods in production get bitten switching directions.

same word, opposite rule, one layer of infrastructure apart

WSL2's own loopback

WSL2 runs Linux inside a lightweight VM, so historically a service bound to localhost inside a WSL2 distro lived in a separate network namespace from Windows' own localhost — a Windows tool and a WSL2 tool couldn't just assume they shared the word, until Microsoft added explicit localhost-forwarding to paper over exactly this gap.

a VM boundary, not a container boundary, same confusion

SSH local port forwarding

ssh -L 5432:localhost:5432 jumphost is famous for tripping people up the first time: the localhost inside that command means the JUMP HOST's loopback once the tunnel lands, not your own laptop's — the same word resolving relative to wherever the connection actually terminates.

the tunnel's far end has its own "localhost" too

bridge — default driver. Creates an isolated virtual network. Containers communicate via IP, but must use port mapping (-p) to be reachable from the host or internet.

docker host (your machine)

Host: localhost:8080 → -p 8080:8080 → container A port 8080

On the default bridge, containers can reach each other by IP but not by name. Use a user-defined bridge for DNS-based name resolution.

host — removes network isolation. Container shares the host's network stack directly. Port 8080 in the container IS port 8080 on the host — no mapping needed.

docker host — container shares this network stack
container (host mode)
ports = host ports
No -p mapping needed.
localhost:8080 reaches the container directly.

✓ Best performance (no NAT overhead). ✗ Container can conflict with host ports. Linux only — does not work on Docker Desktop for Mac/Windows (which uses a Linux VM).

none — completely disables networking. Container has no network interface except loopback (127.0.0.1). Completely isolated.

container (none mode)
No network access

Use for batch jobs or security-sensitive workloads that must not make outbound calls, or for containers that communicate only via mounted volumes.

3 — Container DNS and Service Discovery

Default bridge — IP only ✗

# On default bridge, containers # can only reach each other by IP: docker run --name api myapp:1.0 docker run --name db postgres:16 # Inside 'api', you'd need: jdbc:postgresql://172.17.0.3:5432/db # Fragile! IPs change on restart.

User-defined bridge — DNS names ✓

# Create a named network first: docker network create app-net docker run --name api \ --network app-net myapp:1.0 docker run --name postgres \ --network app-net postgres:16 # Inside 'api', use the container name: jdbc:postgresql://postgres:5432/db # Docker DNS resolves "postgres" → IP
