WebSocket & Real-time Communication

Move beyond request/response. WebSocket gives you a persistent, bidirectional channel — the server can push data any time without the client asking.

🔌 What is a WebSocket — and when does real-time push beat polling?

Plain HTTP is half-duplex: the client asks, the server answers, the connection closes. To push data to the browser (live audit logs, provisioning progress, a live user count) the old approach is polling — call GET /api/status every 2s, where 99% of responses say "nothing changed." A WebSocket is full-duplex: after an HTTP Upgrade handshake the connection becomes a persistent TCP channel either side can write to anytime. STOMP over WebSocket is Spring's recommended layer — topics and queues on top of raw frames, so SimpMessagingTemplate can broadcast or target one user. Choose WebSocket when latency (<1s) and frequency matter; stick with polling for rare updates or firewall-restricted clients.

  • Full-duplex & persistent. The server pushes without the client asking — no polling waste.
  • STOMP adds structure — /topic/* broadcasts, /queue/* private — over the raw socket.
  • Secure the CONNECT frame. WebSocket skips the HTTP filter chain post-handshake; validate the token in a ChannelInterceptor.
  • SSE is the simpler cousin for one-way server→client streams — plain HTTP, auto-reconnect.

Spring STOMP setup

@EnableWebSocketMessageBroker with enableSimpleBroker("/topic","/queue") and an /ws endpoint. Push with simpTemplate.convertAndSend("/topic/users", event); Angular does client.subscribe('/topic/users', msg => …).

WebSocket security

After the handshake the HTTP filter chain is bypassed. A ChannelInterceptor.preSend validates the JWT on the CONNECT frame and rejects bad tokens. Also restrict subscriptions — an ordinary user can't subscribe to /topic/admin-audit-log; use private /queue/user-{id} channels.

SSE alternative

@GetMapping(produces=TEXT_EVENT_STREAM_VALUE) SseEmitter stream() — server→client only, plain HTTP, browser auto-reconnect, no special config (cap ~6 per domain). Great for progress bars and log tails; use WebSocket only when you truly need bidirectional.

CIAM: An admin bulk-imports 500 users from CSV. Polling GET /api/jobs/{id} every 2s wastes ~250 requests; instead GET /api/jobs/{id}/progress streams data:{"processed":50,"total":500} via SSE so Angular updates a live progress bar, then data:{"status":"COMPLETE","created":498,"failed":2} and closes. SSE fits because it's one-way over plain HTTP — WebSocket would be overkill.

The problem

The login worked. The handshake succeeded. An anonymous SUBSCRIBE still got through.

/ws sat behind Spring Security the whole time — and it didn't matter

Someone wires up registry.addEndpoint("/ws").withSockJS() and reasonably assumes that because /ws sits behind the same SecurityFilterChain as every REST controller — session cookie checked, the works — a connection that makes it past the handshake is "logged in" for the rest of its life. They add @MessageMapping("/admin/broadcast") for an admin-only feature and don't think twice about it — it's just another controller method, in the same app, under the same security config. Except the moment the upgrade to WebSocket completes, every STOMP frame that flows over that socket — CONNECT, SUBSCRIBE, SEND — travels through Spring's message-handling pipeline, not the HTTP filter chain. Nothing about @EnableWebSocketMessageBroker or a @MessageMapping method re-runs @PreAuthorize-style checks by default. Anyone who can open a socket to /ws at all can SEND to /app/admin/broadcast.

/ws sits behind the security filter chain ✓ the handshake correctly required a valid session ✓ every STOMP frame after that rides the same open socket ⚠ the HTTP filter chain never sees another one of them ⚠

The wrong assumption: that "an authenticated connection" means "every message on it is authorized." The handshake proves who opened the door. It says nothing about what walks through it afterward.

Authenticate the CONNECT frame, then authorize each destination on its own
Add a ChannelInterceptor.preSend() that reads the JWT off the STOMP CONNECT frame's headers and validates it — the same JwtDecoder the REST controllers already use ↓ this is the one place a WebSocket connection gets checked, so it has to happen explicitly Set the resulting Principal on the STOMP session, then restrict destinations — an ordinary user can't SUBSCRIBE to /topic/admin-audit-log or SEND to /app/admin/* ↓ authentication (who is this) and authorization (what can they reach) are still two separate steps, same as REST Now a valid handshake only ever gets you as far as your own role allows, frame by frame
A WebSocket handshake authenticates a connection. It does not authorize every frame that ever travels over it. That's why the HTTP filter chain protecting /ws is necessary but not sufficient, why @PreAuthorize inside a @MessageMapping method needs its own wiring to mean anything, and why "the user was logged in when they connected" is a different claim from "this specific SEND is something they're allowed to do."
Think of the handshake like showing ID to get a wristband at a festival gate. The wristband proves you got checked once, at the door. It does not, by itself, mean every tent you walk into afterward has its own bouncer confirming you belong there — if the VIP tent doesn't post someone at its own entrance checking for a different wristband color, showing up with any wristband at all gets you in. The gate's check and the VIP tent's check are two separate jobs, done by two separate people.
You

The user already logged in to open this socket. Why would I need to check anything again?

The HTTP filter chain

Because I only ever see ONE request from this connection — the handshake. The moment it upgrades to a WebSocket, I'm out of the picture. Everything that happens on that socket after that, I never see.

A STOMP frame

And I'm not an HTTP request. I don't carry a session cookie the way the handshake did — I'm just bytes on an already-open pipe. If nobody's inspecting me specifically, nobody's checking who sent me.

ChannelInterceptor

Which is the job nobody assigns by default. I sit in the one spot that DOES see every frame — CONNECT, SUBSCRIBE, SEND, all of it. That's exactly why the fix lives here, and nowhere else.

The mechanism

One HTTP request gets filtered. Every frame after it rides the pipe that request built.

  1. The client opens new SockJS('/ws') — a normal HTTP request, and it DOES go through Spring Security's filter chainthe one moment HTTP security applies
  2. The 101 Switching Protocols response completes the upgrade — from here it's a raw bidirectional channel, not HTTP requests anymorethe filter chain's last look at this connection
  3. The STOMP client sends a CONNECT frame over that channel — Spring's message-handling pipeline picks it up, not DispatcherServleta different pipeline entirely
  4. Without a ChannelInterceptor, that CONNECT frame — and every SUBSCRIBE/SEND after it — has no Principal attachedsilently, not with an error
  5. A registered ChannelInterceptor.preSend() reads the Authorization header off the CONNECT frame specifically, validates the JWT, and sets the STOMP session's Principalthe fix runs exactly once, at CONNECT
  6. Every later frame on that session carries the Principal the interceptor set — but only destinations you've explicitly restricted actually check it against anythingauthentication ≠ authorization, still

Step 4 is the lesson. Nothing throws, nothing 403s, nothing logs a warning when a @MessageMapping method runs with no Principal attached — Spring just calls it with whatever an unauthenticated session's getPrincipal() returns, and if that method never checks, it never notices. Every other step here — the handshake, the upgrade, the interceptor — is infrastructure built to make sure step 4's silence isn't the last word.

HTTP handshake GET /ws with an Upgrade header — the filter chain runs HERE, exactly once → 101 Switching Protocols
STOMP CONNECT JWT read from the CONNECT frame's headers by ChannelInterceptor, not by the filter chain → a Principal attached to the STOMP session
SUBSCRIBE / SEND frames flow each destination checked against what THIS Principal is allowed to reach → MESSAGE frames delivered
DISCONNECT — or the socket just drops SessionDisconnectEvent fires → back to nothing connected, nothing authenticated

Notice what does not carry over the loop: the filter chain's work in step 1 never reaches step 3 on its own — every reconnect restarts the cycle with a fresh handshake and a fresh ChannelInterceptor check. That's the safe half of the design. The other half is a real design question this diagram doesn't answer for you: a connection that authenticated hours ago and never disconnected is still trusted on whatever it authenticated with then, because nothing about a long-lived socket re-runs step 2 on a timer.

/ws sits behind Spring Security's normal filter chain, requiring a valid session to complete the handshake. No ChannelInterceptor is configured. A logged-in ordinary user's browser opens a STOMP connection and sends a SUBSCRIBE frame for /topic/admin-audit-log. What happens?

Right. The handshake required a valid session, but that's the only check that ran. Without a ChannelInterceptor — or message-level authorization rules configured separately — nothing at the STOMP layer ever asks "should THIS Principal see THIS destination," so an ordinary logged-in user reaches an admin-named topic just by asking for it.

@EnableWebSocketMessageBroker turns on STOMP support — routing, the broker, @MessageMapping dispatch. It does not turn on authorization checks for destinations; that's separate config you add yourself, the same way @EnableWebSocketMessageBroker doesn't make @PreAuthorize start working inside a @MessageMapping method on its own.

There's no such convention. The simple in-memory broker (enableSimpleBroker("/topic","/queue")) just routes messages to whoever subscribed to a destination string — it has no idea "admin" in a topic name is supposed to mean anything. Naming a destination defensively doesn't defend it.

Where you've seen this before

Three connections, one rule: check once at the door, and the door doesn't check again for you.

A gRPC bidirectional stream

Opening a gRPC stream sends auth metadata (a token) once, at the start. Everything sent over that stream afterward is trusted based on that first check unless you deliberately add interceptors that re-validate per message — the exact same "checked at open, not per-frame" shape as a STOMP session's Principal.

stream metadata ≈ the CONNECT frame

An SSH session after key authentication

You authenticate once with your key when the connection opens. The shell session that follows doesn't re-prompt for your key on every command you type — the connection itself becomes the trust boundary, not each thing sent over it.

the connection is the trust boundary

Questions from the back row

If the JWT expires while the socket is still open, does the connection get kicked?

Not automatically. The Principal was set once, at CONNECT time, and nothing about a long-lived WebSocket connection re-runs that check on a timer. If expired tokens need to actually disconnect live sessions, you have to build that — a scheduled check against stored connection-start times, or having the client proactively reconnect with a fresh token before expiry and letting the ordinary CONNECT cycle handle re-validation. It's a real operational gap worth deciding on purpose, not by default.

The intro says SSE is simpler for one-way updates — could the admin audit-log dashboard have used SSE instead?

For read-only monitoring, quite possibly — and it would sidestep this entire CONNECT-frame question. An SseEmitter endpoint is a normal @GetMapping, so it's protected by the exact same SecurityFilterChain and @PreAuthorize as any other REST endpoint, re-checked the ordinary way, on every request. WebSocket earns its extra complexity when the dashboard also needs to send something back — revoke a session, push a config change. One-way monitoring alone doesn't need full duplex.

Why not just put the JWT in a query parameter on the /ws URL — wouldn't the HTTP filter chain see that?

It would see it, which is exactly the problem — tokens in URLs get written to proxy logs, load balancer logs, and access logs by default, and browsers can leak them through the Referer header. The reason to validate the token in the STOMP CONNECT frame instead is that STOMP frames aren't HTTP requests, so they don't land in any of those logs the same way. It's a real, if second-order, reason to keep the token out of the handshake URL entirely.

3 — STOMP Protocol

Raw WebSocket is just bytes. STOMP (Simple Text Oriented Messaging Protocol) adds structure: named destinations, typed commands, and headers — like HTTP but for messaging.

STOMP Commands
CONNECT Client opens session, sends credentials
SUBSCRIBE Client listens to a destination
SEND Client sends a message to server
MESSAGE Server delivers to subscriber
DISCONNECT Clean session close

4 — Spring Boot WebSocket Config

Two things to configure: where clients connect (endpoint) and how messages route (broker). The @EnableWebSocketMessageBroker annotation activates the whole machinery.

@Configuration @EnableWebSocketMessageBroker // activates STOMP WebSocket support public class WebSocketConfig implements WebSocketMessageBrokerConfigurer { @Override public void registerStompEndpoints(StompEndpointRegistry registry) { registry .addEndpoint("/ws") // clients connect to ws://host/ws .withSockJS(); // enable SockJS fallback } @Override public void configureMessageBroker(MessageBrokerRegistry registry) { // messages prefixed /topic or /queue go straight to the in-memory broker registry.enableSimpleBroker("/topic", "/queue"); // messages prefixed /app are routed to @MessageMapping methods first registry.setApplicationDestinationPrefixes("/app"); // for convertAndSendToUser() — builds /queue/reply-user{id} registry.setUserDestinationPrefix("/user"); } }
registerStompEndpoints
Defines where the WebSocket handshake happens. Clients hit /ws to open the connection. .withSockJS() adds automatic fallback for old browsers.
configureMessageBroker
enableSimpleBroker — built-in broker for pub/sub. In production, swap for enableStompBrokerRelay to point at RabbitMQ or ActiveMQ.

5 — @MessageMapping Controllers

@MessageMapping is the WebSocket equivalent of @RequestMapping. It handles incoming STOMP SEND frames routed via the /app prefix.

@Controller public class ChatController { @Autowired private SimpMessagingTemplate messagingTemplate; // ── Broadcast to ALL subscribers of /topic/messages ────────────────── @MessageMapping("/chat") // client sends to /app/chat @SendTo("/topic/messages") // return value broadcast to topic public ChatMessage handleChat(ChatMessage incoming) { incoming.setTimestamp(Instant.now()); return incoming; // delivered to every subscriber } // ── Private message to ONE specific user ───────────────────────────── @MessageMapping("/private") // client sends to /app/private public void handlePrivate(Principal user, PrivateMessage msg) { messagingTemplate.convertAndSendToUser( msg.getRecipient(), // target username "/queue/reply", // routed to /user/{name}/queue/reply msg ); } }
@SendTo — Broadcast
The return value is serialised to JSON and delivered to every client subscribed to /topic/messages. Perfect for chat rooms and live feeds.
convertAndSendToUser — Private
Delivers to one specific user's private queue. Spring maps the username to a session-specific destination automatically.

7 — Server-Initiated Push with SimpMessagingTemplate

Sometimes the server needs to push data without a client sending a message first — think stock prices updating every second or system health dashboards. Inject SimpMessagingTemplate anywhere in your beans and call it.

@Component public class StockPricePusher { @Autowired private SimpMessagingTemplate messagingTemplate; // auto-configured by Spring @Autowired private StockService stockService; @Scheduled(fixedRate = 1000) // runs every 1 second public void pushPrices() { List<StockPrice> prices = stockService.getLatestPrices(); // broadcast to ALL subscribers — no client request needed messagingTemplate.convertAndSend("/topic/stocks", prices); } // Can also be called from an @EventListener, HTTP endpoint, etc. public void sendUserAlert(String username, String message) { messagingTemplate.convertAndSendToUser( username, "/queue/alerts", message ); } }
Key insight: SimpMessagingTemplate decouples the push from the WebSocket layer. You can trigger a push from a scheduled job, a Kafka consumer, an HTTP webhook handler — anything. The messaging template handles routing to connected clients.

9 — SockJS Fallback

WebSocket is blocked by some corporate firewalls and older browsers. SockJS is a JavaScript library that emulates WebSocket with automatic fallback. One line of config covers everyone.

SockJS negotiation order (tries each until one works):
1
WebSocket (native, fastest)
2
xhr-streaming (chunked HTTP, near-realtime)
3
xhr-polling (last resort, works everywhere)
Server — one line
// WebSocketConfig.java registry .addEndpoint("/ws") .withSockJS(); // ← that's it
Client — JavaScript
// browser const socket = new SockJS('/ws'); const stomp = StompJs.over(socket); stomp.connect({}, frame => { stomp.subscribe('/topic/chat', msg => { console.log(msg.body); }); });

10 — When to Use WebSocket

WebSocket adds complexity — connection management, scaling across multiple servers (need a message broker), session handling. Only reach for it when the use case genuinely needs real-time push.

Use Case WebSocket? Why
Real-time chat Yes Messages must appear instantly for all participants
Live notifications / alerts Yes Server needs to push without a client request
Stock / crypto price feed Yes High-frequency updates; polling would be way too expensive
Collaborative editing (Google Docs style) Yes Bidirectional, low-latency sync between many clients
Live game state Yes Sub-100ms delivery matters; persistent connection avoids overhead
Regular CRUD (create user, fetch list…) No — use REST Request/response pattern is natural; REST is simpler and cacheable
File upload / download No — use REST HTTP multipart handles binary efficiently; WebSocket is for messages
Occasional background refresh (every 30s) No — use polling Keeping a persistent socket open for 30-second updates is wasteful
Production tip: Running multiple server instances? The in-memory broker only works on one node. Switch to enableStompBrokerRelay pointing at RabbitMQ or ActiveMQ so all nodes share the same message bus and any server can deliver to any connected client.
