Signals — Deep Dive

Beyond the basics: linkedSignal, resource, untracked, equality functions, signal-based queries, the reactive graph, and the gotchas.

⚡ What are Angular Signals — and why are they replacing RxJS for state?

A signal is a reactive value container: a box that holds a value and tells Angular exactly which component or effect reads it, so Angular can surgically update just those consumers when the value changes — no dirty-checking the whole tree. Introduced in Angular 16 (stable 17+), signals replace a common RxJS antipattern: using a BehaviorSubject to hold synchronous UI state and manually subscribing/unsubscribing everywhere.

  • Three primitives: signal() (writable), computed() (derived + cached), effect() (side effects).
  • Reading a signal inside a reactive context registers a dependency; writing it notifies exactly those readers.
  • computed is lazy and memoized — it doesn't recompute until read, and only when a dependency actually changed.
  • effect is for I/O (logging, localStorage) — don't use it to set other signals (that's what computed is for).
  • Use signals for synchronous state; keep RxJS for true async streams (HTTP, WebSocket, debounced input).

signal() — writable state

const count = signal(0). Read count(), write count.set(1) or count.update(n => n + 1). Angular tracks every template that reads it.

computed() — derived state

const isAdmin = computed(() => user().roles.includes('ADMIN')). Re-evaluates only when a dependency changes, and lazily — not until something reads it.

effect() — side effects

effect(() => console.log(user())) runs when its dependencies change. For logging, analytics, syncing to localStorage — not for updating other signals (use computed).

In CIAM:the auth store — user = signal<User|null>(null), isAuthenticated = computed(() => user() !== null), roles = computed(() => user()?.roles ?? []) — and every guard, interceptor, and nav bar reads the same reactive derivations with no subscriptions to manage.

1. The reactive graph — how dependency tracking actually works

    
Signals build a directed graph at runtime. When you call count() inside a computed, Angular registers an edge: "this computed depends on this signal." When the signal changes, only the things that depend on it get marked dirty — and they're only re-evaluated when read. This is called lazy evaluation.


    

      

        

          
Signals (sources)

          
a()
= 2

          
b()
= 3

= 10

        

        

          
Computed (derived)

          
sum = a + b
= 5

          
double = c * 2
= 20

last: 5

        

      


      

        
        
        
        
        
        
      


      

        Click c.set — double goes dirty but doesn't recompute until you read it. Click "read double" — it evaluates and goes clean again. This is the entire trick.
      


      

    


    

      The lazy-evaluation rule: a computed only runs when read. Marking dirty is cheap; computing is not. This is why signals can be 10× faster than zone-based change detection on big trees.
    


    
// Behind the scenes, every signal/computed tracks two sets:
// - producers: signals it READ during its last computation
// - consumers: things that depend on it
// On .set(), Angular walks the consumer graph marking nodes "dirty",
// then schedules effects to re-run. Computeds are pulled, not pushed.


    
    
2. Equality functions — when changes propagate

    
A signal only notifies dependents when the new value is not equal to the old. Default: Object.is (strict equality with NaN fix). You can override per signal.


    

      

        signal({ x: 1 }).set({ x: 1 })
        NOTIFIES
        — new object reference, default Object.is fails
      

      

        signal(1).set(1)
        SKIPS
        — same primitive value
      

      

        signal(NaN).set(NaN)
        SKIPS
        — Object.is(NaN, NaN) is true (vs === which is false)
      

      

        signal([1], { equal: _.isEqual }).set([1])
        SKIPS
        — custom deep equality
      

    


    
import { signal } from '@angular/core';
import _ from 'lodash-es';

// Default — Object.is (reference equality for objects)
const user = signal({ name: 'Ada' });
user.set({ name: 'Ada' });                      // NOTIFIES — different object reference

// Custom equality — only notify when *value* changes
const coords = signal({ x: 0, y: 0 }, {
  equal: (a, b) => a.x === b.x && a.y === b.y
});
coords.set({ x: 0, y: 0 });                  // SKIPS — values match, no notify


    

      Practical impact: if you store objects/arrays in signals without a custom equality, every .set() from a server response triggers re-renders even if the data didn't change. Add { equal: _.isEqual } for HTTP-backed signals if perf matters.
    


    
    
3. update vs set vs mutate (RIP)

    

      
APIUse forNotes

      
        
sig.set(value)Replace with a new valueMost common

        
sig.update(v => v + 1)Derive new value from oldCleaner than set(sig() + 1)

        
sig.mutate(v => v.push(x))—❌ Removed in v17. Always return a new reference for arrays/objects.

      
    

    
// ❌ DON'T mutate
const items = signal(['a']);
items().push('b');                              // no notify, dependents won't update

// ✅ DO immutable update
items.update(arr => [...arr, 'b']);

// ✅ Or with structuredClone for deep objects
state.update(s => ({ ...s, user: { ...s.user, name: 'Ada' } }));


    
    
4. untracked() — break the dependency edge

    
Sometimes you want to read a signal inside a computed/effect without subscribing to it. Wrap the read in untracked().


    

      
Two counters. Both have effects that log when they run. The first effect tracks both counters. The second tracks only tracked — read is wrapped in untracked() so changes don't trigger it.

      

        

          
tracked

          
0

          
          
effect A ran: 0×   effect B ran: 0×

        

        

          
read (wrapped in untracked)

          
0

          
          
effect A ran: 0×   effect B ran: 0×

        

      

    


    
import { signal, effect, untracked } from '@angular/core';

const tracked = signal(0);
const read = signal(0);

// Effect A — tracks BOTH (re-runs when either changes)
effect(() => console.log(tracked(), read()));

// Effect B — only tracks `tracked`. `read` is read but NOT subscribed.
effect(() => {
  const t = tracked();
  const r = untracked(() => read());     // peek without subscribing
  console.log(`tracked=${t} (read was ${r})`);
});


    

      Real use case: logging side effects ("user with id userId() clicked on item itemId()"). You want the effect to fire when itemId changes but not every time userId changes (the user staying the same shouldn't fire it). Wrap userId() in untracked.
    


    
    
5. linkedSignal() — writable computed (v19+)

    
A read-only computed can't be written to. A signal can be written to but doesn't react to other signals. linkedSignal is both — a writable signal that resets when its source changes.


    
import { signal, linkedSignal } from '@angular/core';

const options = signal(['red', 'green', 'blue']);

// Selected color — defaults to options[0], BUT user can override
// When options changes, selected resets to the new options[0]
const selected = linkedSignal(() => options()[0]);

console.log(selected());                // 'red'
selected.set('green');                   // user picks green — writable
console.log(selected());                // 'green'
options.set(['cyan', 'magenta']);      // options changed → selected RESETS
console.log(selected());                // 'cyan' (back to options[0])


    
// Advanced form: choose how to compute new value from old
const selected = linkedSignal({
  source: options,
  computation: (newOptions, previous) => {
    // Preserve the previous selection if still in the new options
    if (previous && newOptions.includes(previous.value)) return previous.value;
    return newOptions[0];
  }
});


    

      Killer use case: form dropdowns where the available options can change (e.g. State select depends on Country). Without linkedSignal you have to manually effect() to reset State when Country changes — error-prone. With it: one line.
    


    
    
6. resource() & rxResource() — async data as a signal (v19+)

    
The reactive way to load data. A resource bundles status (loading/error/success), value, and reload — all as signals you can read directly in templates.


    
import { resource, signal } from '@angular/core';

const userId = signal(1);

const userRes = resource({
  request: () => ({ id: userId() }),               // reactive request — re-fetches on change
  loader: async ({ request, abortSignal }) => {
    const res = await fetch(`/api/users/${request.id}`, { signal: abortSignal });
    return res.json();
  }
});

// In a template — everything is signal-based:
@if (userRes.isLoading()) { <spinner/> }
@else if (userRes.error()) { <error-msg [error]="userRes.error()"/> }
@else if (userRes.value(); as user) { <user-card [user]="user"/> }

// Programmatic:
userId.set(2);                     // auto-cancels in-flight, re-fetches
userRes.reload();                  // force refresh with same request
userRes.set({ name: 'optimistic' }); // optimistic local update


    
The full API surface

    

      
SignalTypePurpose

      
        
res.value()T | undefinedThe loaded data

        
res.status()'idle'|'loading'|'reloading'|'resolved'|'error'|'local'Current state

        
res.isLoading()booleanShortcut for status checks

        
res.error()unknownError if rejected

        
res.hasValue()booleanType guard for value()

        
res.reload()methodRefresh with current request

      
    


    
// rxResource — for RxJS-based loaders (HttpClient returns Observables)
import { rxResource } from '@angular/core/rxjs-interop';

const userRes = rxResource({
  request: () => ({ id: userId() }),
  loader: ({ request }) => this.http.get<User>(`/api/users/${request.id}`)
});


    
    
7. Signal-based queries (viewChild, contentChild)

    
The v17+ replacement for @ViewChild decorators. Returns a signal you can read in computed/effect.


    
import { viewChild, viewChildren, contentChild, contentChildren, ElementRef } from '@angular/core';

export class MyComp {
  // Single element — returns signal<ElementRef | undefined>
  inputRef = viewChild<ElementRef<HTMLInputElement>>('myInput');

  // Required version — returns signal<ElementRef> (no undefined)
  inputRef = viewChild.required<ElementRef<HTMLInputElement>>('myInput');

  // Multiple — returns signal<readonly ElementRef[]>
  items = viewChildren(ItemComponent);

  // Use it in a computed
  itemCount = computed(() => this.items().length);

  // Or in an effect
  constructor() {
    effect(() => {
      const el = this.inputRef()?.nativeElement;
      if (el) el.focus();                  // auto-focus when available
    });
  }
}


    

      Why this is better than the decorator: with @ViewChild you had to wait for ngAfterViewInit and remember the timing. With the signal version, it's just a signal — read it whenever, computed/effect handle the timing.
    


    
    
8. Effect gotchas — the rules

    

      
RuleWhy

      
        
No signal writes in an effect by defaultCauses infinite loops. Use allowSignalWrites: true opt-in if you must.

        
Effects are asyncThey run after the current microtask, in the next CD cycle. Don't expect immediate execution.

        
Effects need an injection contextCall effect() in constructor or use injector option.

        
Effects auto-clean on destroyInside a component, they tie to the component's lifecycle. Outside, you get an EffectRef with .destroy().

        
Use onCleanup for teardownCancel timers, unsubscribe, abort fetches before the next run.

      
    


    
// onCleanup pattern — like useEffect's return in React
effect((onCleanup) => {
  const id = setInterval(() => console.log(time()), 1000);
  onCleanup(() => clearInterval(id));
});

// allowSignalWrites — escape hatch, use sparingly
effect(() => {
  if (count() > 10) cappedCount.set(10);
}, { allowSignalWrites: true });
// Better: use computed instead — almost always
const cappedCount = computed(() => Math.min(count(), 10));


    
    
9. afterNextRender & afterRender

    
For DOM-touching logic that needs to run AFTER Angular has rendered. Useful for measuring element sizes, focusing inputs, integrating non-Angular libraries.


    
import { afterNextRender, afterRender } from '@angular/core';

export class ChartComponent {
  constructor() {
    // Runs ONCE after the next render
    afterNextRender(() => {
      const el = document.getElementById('chart');
      new Chart(el, chartOptions);
    });

    // Runs after EVERY render — careful with perf
    afterRender(() => {
      console.log('measured height:', this.el.offsetHeight);
    });
  }
}

    

      Don't use these for state changes — they don't auto-track signals. They run on render, not on reactivity. Use effect for reactive things; afterRender for "the DOM exists now" things.
    


    
    
10. Signal-based input/output/model (recap)

    
import { input, output, model } from '@angular/core';

export class SearchBox {
  // Optional input — returns Signal<string | undefined>
  placeholder = input<string>();

  // With default — returns Signal<number>
  minLen = input(3);

  // Required — returns Signal<User> (no undefined)
  user = input.required<User>();

  // Transform on input — string → number
  count = input(0, { transform: numberAttribute });

  // Output — emit(value)
  search = output<string>();
  onType(q: string) { this.search.emit(q); }

  // model — two-way binding (input + output combined)
  query = model('');
  clear() { this.query.set(''); }    // notifies parent via [(query)]="..."
}


    
    
11. Building a SignalStore by hand (no library)

    
Most apps don't need NgRx. A plain service holding signals = a complete state store. Here's the pattern.


    
@Injectable({ providedIn: 'root' })
export class CartStore {
  // --- private writable state ---
  private _items = signal<CartItem[]>([]);
  private _coupon = signal<string | null>(null);

  // --- public read-only views ---
  items = this._items.asReadonly();
  coupon = this._coupon.asReadonly();

  // --- derived ---
  count    = computed(() => this._items().reduce((n, i) => n + i.qty, 0));
  subtotal = computed(() => this._items().reduce((s, i) => s + i.price * i.qty, 0));
  discount = computed(() => this._coupon() === 'SAVE10' ? this.subtotal() * 0.1 : 0);
  total    = computed(() => this.subtotal() - this.discount());

  // --- methods (the "actions") ---
  add(item: CartItem) {
    this._items.update(arr => {
      const idx = arr.findIndex(i => i.id === item.id);
      if (idx >= 0) {
        return arr.map((x, i) => i === idx ? { ...x, qty: x.qty + 1 } : x);
      }
      return [...arr, { ...item, qty: 1 }];
    });
  }
  remove(id: string) { this._items.update(arr => arr.filter(i => i.id !== id)); }
  applyCoupon(code: string) { this._coupon.set(code); }
  clear() { this._items.set([]); this._coupon.set(null); }
}


    

      That's it. No actions, no reducers, no boilerplate. Components inject CartStore and read store.total() in templates. This pattern scales surprisingly far — many production apps never need more.
    


    
    
12. Going fully zoneless (v18+ stable)

    
// app.config.ts
import { provideZonelessChangeDetection } from '@angular/core';

export const appConfig: ApplicationConfig = {
  providers: [provideZonelessChangeDetection()]
};

// And in main.ts — remove zone.js from the polyfills
// In angular.json:
"polyfills": [/* drop "zone.js" */]


    
What changes

    

      
Was triggered by zoneNow triggered by

      
        
Any browser event (click, input)Signal writes only

        
setTimeout / setInterval(nothing — must use signals)

        
Promise resolutions(nothing)

        
HTTP responses(nothing — use toSignal or HttpClient auto-bridge)

      
    


    

      Migration reality: third-party libraries (calendars, charts, drag-drop) often relied on zone-triggered CD. Going zoneless can mean wrapping those calls in ngZone.run() or ChangeDetectorRef.markForCheck(). Audit before flipping the switch.
    


    
    
13. Performance — signal granularity

    
Coarse signals (one big object) are easy. Fine-grained signals (one per field) are fast. Pick based on what changes together.


    
// ❌ Coarse — every field change triggers all consumers
const user = signal({ name: 'Ada', age: 30, email: 'ada@ex.com' });
// Anything that reads user() re-runs even if only age changed

// ✅ Fine-grained — only the consumers of the changed field re-run
const name  = signal('Ada');
const age   = signal(30);
const email = signal('ada@ex.com');

// ✅ Or: coarse + custom equality (best of both)
const user = signal({ name: 'Ada', age: 30 }, { equal: _.isEqual });
// Only notifies if value actually changed


    
    
Anti-patterns

    

      
❌ Don't✅ Do

      
        
Use effect for derived stateUse computed

        
Mutate signal contentsupdate(v => new value) — return new ref

        
Read signals outside Angular contextPass an injector option or call in runInInjectionContext

        
Call signals in non-reactive hot pathsReading is cheap, but DOM-heavy loops should cache: const v = sig(); for ...

        
Use signals for transient UI state in shared servicesKeep transient state local to the component

        
Mix Subject + signal randomlyPick one for the boundary. Use toSignal / toObservable at API edges only.

      
    


    

      The full signals mental model: a graph where writes mark dirty (cheap), reads pull values (lazy). signal = source. computed = lazy derived. effect = side effect to the outside world. linkedSignal = writable+reactive. resource = async loader bundled with status. Pick the right primitive and the framework does the rest.
