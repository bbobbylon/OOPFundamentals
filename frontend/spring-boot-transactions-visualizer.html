Transaction Management

Guarantee that a group of database operations either ALL succeed or ALL fail — no half-written data. @Transactional is one of the most critical and most misunderstood annotations in Spring.

🔁 What is a database transaction — and why do you need @Transactional?

Creating an account writes to users, then to user_roles. If the server crashes between those writes you get an orphaned user with no roles. A transaction bundles multiple operations into one atomic unit: either all commit or none do (the DB rolls back to the pre-transaction state) — the ACID "Atomicity" guarantee. @Transactional on a service method opens a connection at the start, groups every DB operation inside it into one transaction, and commits at the end; throw an exception and it all rolls back. The classic bug: calling a @Transactional method from within the same class (this.method()) bypasses the proxy, so no transaction is created.

  • It's proxy-based. Spring wraps the bean; the proxy opens the tx, calls your method, then commits or rolls back.
  • Only unchecked exceptions roll back by default. For checked exceptions add @Transactional(rollbackFor=Exception.class).
  • Put it on the service layer — not the controller, not the repository (repos already run per-method transactions).
  • Self-invocation defeats it. An internal call skips the proxy; fix by injecting self or extracting another bean.

How it works

Spring wraps the service in a CGLIB proxy. service.createUser() hits the proxy → opens a connection & starts a tx → calls the real method → no exception commits; a RuntimeException rolls back and rethrows. Class-level @Transactional applies to all public methods.

readOnly = true

On query methods, @Transactional(readOnly=true) tells the driver no writes happen — skips dirty-check overhead, can route to read replicas. The first-level cache still dedupes repeated findById in one tx. Don't use it on writers — Hibernate skips dirty checking and you get silent data loss.

Diagnosing

Set logging.level.org.springframework.transaction=DEBUG to see "Creating new transaction", "Participating in existing transaction", "Initiating transaction rollback", "Committing JPA transaction". "No existing transaction found" where you expected one = self-invocation bypass.

CIAM: @Transactional on createUser(...) inserts the user, the default role assignment, and an audit log entry as one unit — if the role insert violates a constraint, the user insert rolls back too (no orphans). @Transactional(readOnly=true) on searchUsers(criteria, pageable). Rule: transactions live on the service layer.

1 — ACID: What a Transaction Guarantees

Click each letter to understand what the database promises:

A
Atomicity
All operations in the transaction succeed together, or none of them do. If any step fails, every prior change is rolled back. You never end up with money debited but not credited.
C
Consistency
The database moves from one valid state to another. Constraints, foreign keys, and triggers are enforced. A transfer can't produce a negative balance if the schema prevents it.
I
Isolation
Concurrent transactions don't see each other's in-progress changes (unless you explicitly allow it via isolation level). Protects against dirty reads, phantom reads, and non-repeatable reads.
D
Durability
Once a transaction commits, the data is permanently saved — even if the server crashes a millisecond later. Achieved via write-ahead logging (WAL) in the database.

2 — How @Transactional Works Under the Hood

Spring wraps your service bean in a proxy. The proxy intercepts the call, opens a transaction, calls your real method, then commits or rolls back:

// What you write: @Service public class AccountService { @Transactional // triggers proxy generation at startup public void transfer(Long fromId, Long toId, BigDecimal amount) { accountRepo.debit(fromId, amount); // SQL UPDATE accountRepo.credit(toId, amount); // SQL UPDATE } } // What Spring generates at runtime (simplified CGLIB proxy): class AccountService$$SpringProxy extends AccountService { public void transfer(Long fromId, Long toId, BigDecimal amount) { txManager.begin(); // open transaction, grab Connection from pool try { super.transfer(fromId, toId, amount); // call YOUR real code txManager.commit(); // flush all changes to DB } catch (RuntimeException ex) { txManager.rollback(); // undo EVERYTHING since begin() throw ex; } } }
Key rule: @Transactional only works when the call goes through the proxy. Calling a @Transactional method from another method in the same class bypasses the proxy — no transaction! (See Section 7.)

5 — Rollback Rules — What Triggers a Rollback

Default: rolls back on RuntimeException & Error
@Transactional public void process() { save(record); throw new IllegalStateException(); // ↑ RuntimeException → ROLLBACK ✓ } @Transactional public void processChecked() throws IOException { save(record); throw new IOException(); // ↑ Checked exception → COMMITS! ✗ }
Override rollback rules explicitly
// Roll back on a checked exception too @Transactional( rollbackFor = IOException.class ) public void processChecked() throws IOException { ... } // Commit EVEN IF this runtime exception is thrown @Transactional( noRollbackFor = OptimisticLockException.class ) public void tryUpdate() { ... }

RuntimeException (unchecked)ROLLBACKnoRollbackFor=RuntimeException.class

7 — The Three Pitfalls That Silently Break Transactions

Pitfall 1 — Self-invocation (the proxy bypass)

When method A in the same class calls @Transactional method B, the call goes directly to this, bypassing the proxy. B's transaction annotation is ignored entirely.

// BROKEN — both methods in same class public void doWork() { saveAudit(); // direct call, no proxy → no transaction! } @Transactional public void saveAudit() { ... } // FIX — inject the service into itself, OR extract saveAudit to a separate @Service bean @Autowired private AuditService auditService; public void doWork() { auditService.saveAudit(); } // goes through proxy ✓

Pitfall 2 — @Transactional on private methods

CGLIB proxies can only override public methods. @Transactional on a private or package-private method is silently ignored — no error, no transaction.

@Transactional // SILENTLY IGNORED — method is private private void persistInternal() { ... } // Fix: make it public, or move it to a separate @Service bean

Pitfall 3 — Checked exceptions not rolling back

Spring only rolls back on RuntimeException by default. If your method throws a checked exception (e.g. IOException) and you don't specify rollbackFor, Spring will COMMIT the partial changes.

@Transactional // COMMITS even if IOException is thrown — likely a bug public void sendAndSave() throws IOException { repo.save(entity); emailService.send(email); // throws IOException // save is committed! email failed! inconsistent state! } // Fix: @Transactional(rollbackFor = Exception.class) // rolls back on any exception public void sendAndSave() throws IOException { ... }
