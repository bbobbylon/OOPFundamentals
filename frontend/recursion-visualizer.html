Recursion — A Function That Calls Itself

Three classic recursive problems, side by side. Watch the call stack grow, unwind, and (sometimes) explode.

What is recursion — and how does a function calling itself eventually produce a result instead of running forever?

Recursion is when a function solves a problem by calling itself on a smaller version of the same problem. It sounds circular, but it terminates because every recursive call moves toward a base case — a simple version of the problem with a known answer that requires no further recursion. Without a base case (or with a broken one), recursion runs forever until Java throws a StackOverflowError. Two required ingredients: (1) Base case — the stopping condition; handles the simplest input directly without recursion. (2) Recursive case — calls itself with a strictly simpler input, making progress toward the base case. The call stack is how recursion works mechanically. Each function call creates a new stack frame containing the local variables and parameters for that call. The frame is pushed onto the call stack. When the function returns, the frame is popped. Recursive calls stack up frames one on top of another — you can visualize the call stack as a literal tower of function calls. All those frames are held in memory simultaneously until the base case is reached and the tower starts collapsing (unwinding). Recursion vs iteration: any recursive algorithm can be converted to an iterative one (sometimes you need an explicit stack, but it's always possible). The recursive version is often more readable because it mirrors the mathematical definition. The iterative version avoids stack frame overhead and stack overflow risk for very deep inputs. Tail recursion: when the recursive call is the very last operation in the function (nothing happens after the recursive call returns). Some languages (not Java) optimize this to reuse the same stack frame — O(1) stack space instead of O(n). In Java, there's no tail call optimization, so deep recursion always risks StackOverflowError. When to use recursion: problems with a naturally recursive structure (trees, graphs, divide-and-conquer, dynamic programming, backtracking). Never use raw recursion for simple loops; use it when the problem decomposes naturally into "solve a smaller version of itself."

Factorial — textbook recursion

// factorial(n) = n × (n-1) × ... × 1 // factorial(0) = 1 ← BASE CASE // factorial(n) = n × factorial(n-1) ← RECURSIVE CASE int factorial(int n) { if (n == 0) return 1; // base case: stop here! return n * factorial(n - 1); // recursive: call with n-1 } // Call stack trace for factorial(4): // factorial(4) calls factorial(3) // factorial(3) calls factorial(2) // factorial(2) calls factorial(1) // factorial(1) calls factorial(0) // factorial(0) returns 1 ← base case reached! // factorial(1) returns 1×1 = 1 // factorial(2) returns 2×1 = 2 // factorial(3) returns 3×2 = 6 // factorial(4) returns 4×6 = 24 // Stack grew 5 frames deep, then collapsed

Binary search — recursive

// Binary search: find target in SORTED array // Base cases: // lo > hi → not found (-1) // arr[mid] == target → found (return mid) // Recursive: eliminate half the array int binarySearch(int[] arr, int target, int lo, int hi) { if (lo > hi) return -1; // BASE CASE: empty range int mid = lo + (hi - lo) / 2; // avoid int overflow if (arr[mid] == target) return mid; // BASE CASE: found it if (arr[mid] > target) return binarySearch(arr, target, lo, mid-1); // go LEFT else return binarySearch(arr, target, mid+1, hi); // go RIGHT } // Each call halves the search space: O(log n) depth // Call stack grows O(log n) deep — very safe // For n=1,000,000: only 20 frames deep!

Tree traversal — recursion shines

// Tree traversals are naturally recursive // because every subtree IS a smaller tree // In-order (left → root → right) = sorted output for BST void inOrder(TreeNode node) { if (node == null) return; // BASE CASE: leaf's child inOrder(node.left); // recurse into left subtree process(node.val); // process THIS node inOrder(node.right); // recurse into right subtree } // Pre-order (root → left → right) = copy/serialize tree // Post-order (left → right → root) = delete tree safely // Count nodes in tree: int countNodes(TreeNode node) { if (node == null) return 0; // base: null contributes 0 return 1 + countNodes(node.left) + countNodes(node.right); } // Why recursion? Tree has no "index" — // recursion mirrors the structure of the data itself

In CIAM / Context: Recursion appears throughout CIAM systems in non-obvious ways. Spring's ApplicationContext builds the bean dependency graph recursively — resolving A requires B requires C (and detects circular dependencies that would infinite-loop). Angular's component tree rendering is recursive — each component renders its children recursively. OAuth scope inheritance in Ping AM uses recursive group membership resolution (is user in group X? → is group X a member of group Y? → recurse). JWT claim transformation chains in Ping AM scripted decision nodes traverse claim objects recursively. Understanding recursion and call stacks also helps debug StackOverflowError in production — always means infinite or too-deep recursion.

The two ingredients of recursion

Every recursive function has exactly two parts:

  1. Base case — the smallest version of the problem you can answer directly, with NO more recursion. Without this, recursion runs forever (and you get StackOverflowError).
  2. Recursive step — reduce the problem to a smaller version and call yourself.

2. The Fibonacci catastrophe — naive vs memoized

Naive fib(n) = fib(n-1) + fib(n-2) recomputes the same sub-problems over and over. fib(5) calls fib(3) twice, fib(2) three times, fib(1) five times. Memoization caches each answer the first time we compute it, dropping the complexity from O(2ⁿ) to O(n). Click the button to see the difference.

3. Tower of Hanoi — recursion that solves a physical puzzle

Move all the disks from peg A to peg C, one at a time, never placing a larger disk on a smaller one. The recursive solution is elegant: move (n-1) disks to peg B, move the biggest disk to C, then move the (n-1) disks from B to C. It takes exactly 2ⁿ - 1 moves — so n=10 needs 1023 moves; n=64 (the legend) needs ~18 quintillion.

Big picture

  • Recursion's strength: mirrors the structure of the problem. Tree traversal, file-system walks, divide-and-conquer all become elegant.
  • Recursion's cost: each call takes stack space. Deep recursion (n=100,000+) blows the stack.
  • Always check: do I have a base case? Will the recursive step actually get me closer to it?
  • Memoization turns an exponential recursive solution into a linear one when sub-problems overlap (like Fibonacci). This is the gateway to dynamic programming.
