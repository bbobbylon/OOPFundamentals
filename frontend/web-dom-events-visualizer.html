The DOM & Events — Selecting, Manipulating & Event Delegation

Every framework you'll ever use — Angular, React, Vue — compiles down to plain calls against the Document Object Model: find a node, change it, listen for something the user did. This page is what's actually happening underneath the template syntax.

🌳 What is the DOM, and why does every framework boil down to it?

When a browser parses HTML, it doesn't keep the text around — it builds a live, tree-shaped, in-memory object representing every element, attribute, and piece of text: the Document Object Model (DOM). JavaScript's whole job in the browser is reading and mutating that tree. Change a node's .textContent in DevTools and the page visibly updates immediately, even though the original HTML file on disk never changed — because the browser renders the live tree, not the source. Two capabilities sit on top of that tree: selecting nodes (find the element(s) you care about) and manipulating them (change their text, attributes, classes, or children), plus a separate but related system for events — code that runs in response to something the user did (a click, a keystroke, a form submit). Here's the payoff for anyone coming to this page from Angular or React: when you write {{ user.name }} in an Angular template or {user.name} in JSX, the framework is not doing anything magical — it is generating exactly the querySelector + .textContent + addEventListener calls this page teaches, just automatically, efficiently, and without you writing them by hand. Understanding this page means you can read what your framework's compiled output is actually doing, and it's the only way to debug a "why isn't my click handler firing" bug that a framework's abstraction can't fully hide.

  • The DOM is live and separate from the HTML source — mutate it, and the source file is untouched but the page updates.
  • Selecting — querySelector/querySelectorAll (CSS selectors, the modern default) vs the older getElementById/getElementsByClassName.
  • Manipulating — .textContent is always safe; .innerHTML parses raw HTML and is a real XSS vector with untrusted input.
  • Events bubble upward by default from the exact element clicked, through every ancestor, unless stopPropagation() halts them.
  • Event delegation — one listener on a parent handles clicks on any child, including children added later — the pattern every framework's own event system is built on.

The vanilla-JS happy path

// find it const card = document.querySelector('.card'); // change it safely card.textContent = user.name; // react to clicks on it card.addEventListener('click', e => {   console.log('clicked', e.target); });

What Angular/React do for you

Angular's change detector diffs your component's data and calls the exact same .textContent/.setAttribute APIs shown here to patch only what changed. React's synthetic event system attaches one real listener at the root and uses event bubbling — the same delegation pattern taught in scenario 3 — to route every click to the right component handler.

Spring Boot / CIAM comparison

Treat innerHTML the way you treat string-concatenated SQL on the backend: both take untrusted input and hand it to a parser that executes structure, not just data. NamedParameterJdbcTemplate avoids SQL injection by binding parameters instead of concatenating; .textContent avoids DOM-based XSS the same way, by writing data as text instead of parsing it as markup.

Security in production: DOM-based XSS happens entirely client-side — no backend involved. If you ever write el.innerHTML = someValue where someValue came from a URL query param, a form field, or an API response you don't fully trust, an attacker who controls that string can inject a <script> or an onerror-bearing <img> tag that runs in your page's origin — reading cookies, forging requests with the logged-in user's session. See appsec-injection-xss-visualizer.html for the full attack trace. The fix here is almost always the same one line: use .textContent instead of .innerHTML unless you specifically need to render trusted, sanitized markup.

1. Selecting elements — CSS selectors vs the older DOM methods

// modern default — any CSS selector, returns a static NodeList
const cards = document.querySelectorAll('.card.active');
const first = document.querySelector('#main .card');

// older, narrower, but still used — and a real gotcha
const byId = document.getElementById('main'); // fastest single-element lookup
const live = document.getElementsByClassName('card'); // ⚠️ LIVE HTMLCollection
// live.length changes automatically as .card elements are added/removed —
// a querySelectorAll() NodeList does NOT update after the call.
Live vs static is the gotcha. getElementsByClassName and getElementsByTagName return a live HTMLCollection — iterate it while adding matching elements and you can skip items or loop unexpectedly, because the collection's length is changing under you. querySelectorAll returns a static NodeList snapshot taken at call time — the safer default for almost every case, which is why it's the one shown first above.

2. Manipulating safely — textContent vs innerHTML

// SAFE — always treats the value as plain text, never parsed as markup
card.textContent = userSuppliedName; // "<b>hi</b>" renders as the literal text <b>hi</b>

// UNSAFE with untrusted input — parses and executes markup
card.innerHTML = userSuppliedName; // "<img src=x onerror=alert(1)>" RUNS as HTML

// other common mutations
card.classList.toggle('active');
card.setAttribute('aria-expanded', 'true');
const li = document.createElement('li');
li.textContent = 'New item';
list.appendChild(li);
innerHTML is not "wrong" — it's scope-limited. It's the right tool when you're rendering markup you wrote (a static template string with no user data inside it) or content you've explicitly sanitized. The rule that keeps you safe: never let a value that came from a URL, a form field, or an API response reach innerHTML unsanitized. That's DOM-based XSS, and it's the same class of bug as SQL injection — untrusted data got interpreted as executable structure instead of inert data.

3. Events — the object, bubbling, and delegation

// listen for a click, inspect the event object
button.addEventListener('click', (event) => {
  event.target; // the EXACT element that was clicked (could be a child)
  event.currentTarget; // the element the listener is ATTACHED to
  event.preventDefault(); // cancel the browser's default action (e.g. form submit)
  event.stopPropagation();// stop the event bubbling further up the tree
});

// delegation — ONE listener handles every <li>, even ones added later
list.addEventListener('click', (event) => {
  if (event.target.matches('li')) handleItemClick(event.target);
});
Bubbling is why delegation works. A click on a deeply nested <span> doesn't just fire a listener on the span — it fires on the span, then bubbles up and fires listeners on every ancestor in turn, all the way to document, unless something calls stopPropagation(). That means one listener on a parent container can catch clicks from any descendant, present now or added to the DOM later — you never have to re-attach listeners to new items. This is exactly how React's synthetic event system and Angular's event binding are implemented internally: one real listener near the root, routed by inspecting event.target.
