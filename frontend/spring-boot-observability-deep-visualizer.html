Micrometer, Metrics & Distributed Tracing

See inside your running application. Metrics tell you how fast, how many, and how full. Traces tell you why a specific request was slow.

What is observability — metrics vs logs vs traces, and when do you need each?

Observability is the ability to understand what your system is doing from the outside — without having to modify the code and redeploy. It has three pillars: Metrics answer "how much, how often, how full?" — request rate, error rate, DB pool size, JVM heap. They're numeric, time-series, good for alerts and dashboards. Logs answer "what happened?" — discrete events with context. Good for debugging specific failures. Traces answer "why was this request slow?" — a trace follows one request through every service and shows where time was spent (5ms in Spring Security filter, 20ms in UserService, 100ms in DB query). Together they answer: "API latency spiked (metric) → find the slow request (trace) → read the logs for that request (log)" — three pillars, one answer.

Micrometer metrics

Spring Boot Actuator includes Micrometer — a metrics facade (like SLF4J for logging). Add dependency: micrometer-registry-prometheus. Spring auto-instruments: HTTP requests (count, latency by endpoint + status), JVM (heap, GC, threads), HikariCP (pool active/idle/wait). Custom: @Timed("user.create") or registry.timer("user.search").record(() -> searchUsers()). Prometheus scrapes /actuator/prometheus every 15s; Grafana displays dashboards.

Distributed tracing

Spring Boot 3 + Micrometer Tracing: auto-instruments HTTP requests and RestClient calls. Add: micrometer-tracing-bridge-otel + opentelemetry-exporter-zipkin (or Tempo). Each request gets a traceId (same across all services) and spanId (per operation). MDC automatically includes traceId and spanId in log lines — correlation between traces and logs is automatic. Grafana Tempo + Loki: click a slow span → see its logs immediately.

Key alerts for Spring Boot

HTTP 5xx error rate > 1% for 5 minutes → page on-call. P99 latency > 2 seconds → investigate. HikariCP active connections = max pool size → DB pool exhaustion imminent. JVM heap > 85% for 10 minutes → likely memory leak. Circuit breaker open state → downstream service failing. These five metrics cover 90% of production incidents. Build dashboards before you need them — you won't have time to configure Grafana while users report errors.

In CIAM: Custom metrics: Counter loginAttempts = registry.counter("ciam.login.attempts", "result", "success"/"failure") — track login success/failure rate. Alert: failure rate > 20% for 5 minutes could be a credential-stuffing attack. Trace the JWT validation path: how long does JWKS fetch take? Is it hitting cache or Ping on every request? A trace shows: Spring Security filter = 2ms (cached JWKS), UserService = 5ms, DB query = 3ms, total = 10ms. Remove JWKS caching accidentally and the trace shows: Spring Security filter = 150ms (Ping API call on every request).

1. The Three Pillars of Observability

📊
Metrics
Aggregated numbers over time. How many requests/sec? What's the 99th percentile latency? CPU %, error rate. Tells you: something is wrong.
Tools: Micrometer → Prometheus → Grafana
📝
Logs
Discrete events with context. Stacktraces, user actions, business events. Tells you: what happened. Best with structured JSON + correlation IDs.
Tools: SLF4J + Logback → ELK / CloudWatch
🔍
Traces
End-to-end journey of a single request across services. Spans show each operation's duration. Tells you: why it was slow.
Tools: Micrometer Tracing → Zipkin / Jaeger
The typical workflow: Metrics alert you that p99 latency spiked. You open Grafana, identify which endpoint. You correlate a TraceId in logs, open Zipkin to see the trace waterfall, and find the slow DB query in the OrderService span.

2. Core Meter Types

Micrometer is a metrics facade — like SLF4J but for metrics. Your code uses the Micrometer API; the actual backend (Prometheus, Datadog, CloudWatch) is a pluggable implementation.

Counter
Monotonically increasing number. Never decreases.
Use for: total requests, total errors, total items processed, login attempts.

private final Counter loginAttempts; UserService(MeterRegistry registry) { // Tags are key-value dimensions for filtering loginAttempts = Counter.builder("user.login.attempts") .description("Number of login attempts") .tag("service", "user-service") .register(registry); } public void login(String username) { loginAttempts.increment(); // or .increment(n) } // Prometheus query: rate(user_login_attempts_total[5m]) // NEVER alert on counter value — always use rate()
Gotcha: Counters only make sense as rates. "123456 logins" is useless. "42 logins/second" is actionable.
Timer
Measures duration + count + throughput. Most useful meter.
Use for: HTTP request duration, DB query time, method execution time, external API call latency.

private final Timer dbTimer; OrderRepository(MeterRegistry registry) { dbTimer = Timer.builder("db.query.duration") .description("Time to execute DB queries") .tag("table", "orders") .publishPercentiles(0.5, 0.95, 0.99) // p50/p95/p99 .publishPercentileHistogram() // for Grafana heatmaps .register(registry); } public List<Order> findAll() { return dbTimer.record(() -> orderRepo.findAll()); } // Prometheus: db_query_duration_seconds_bucket, _count, _sum // histogram_quantile(0.99, rate(db_query_duration_seconds_bucket[5m])) // Spring's @Timed annotation (on @RestController/@Service) @Timed(value = "orders.list", percentiles = {0.5, 0.95})
Gauge
Current value — can go up or down.
Use for: queue depth, active sessions, cache size, thread pool usage, DB connection pool size.

// Gauge tracks a supplier function's current value Gauge.builder("queue.depth", orderQueue, Queue::size) .description("Number of orders in processing queue") .tag("type", "high-priority") .register(registry); // Active HTTP sessions Gauge.builder("http.sessions.active", sessionManager, SessionManager::getActiveCount) .register(registry); // Prometheus: alert if queue.depth > 1000 // alert: expr: queue_depth > 1000 // for: 5m // severity: warning // Gotcha: Gauge holds a weak reference to your object! // Keep a strong reference or the gauge becomes NaN.
DistributionSummary
Like Timer but for sizes, not time. Request payload size, batch size.
DistributionSummary summary = DistributionSummary .builder("http.request.size") .description("HTTP request payload size in bytes") .baseUnit("bytes") .publishPercentiles(0.5, 0.95) .register(registry); summary.record(requestSize); // in a filter // Prometheus: http_request_size_bytes_sum / http_request_size_bytes_count // = average request size
LongTaskTimer
Tracks duration of CURRENTLY RUNNING tasks. Unlike Timer which records after completion.
Use for: batch jobs, report generation, long-running background tasks — see how long they've been running while still active.

LongTaskTimer ltt = LongTaskTimer .builder("report.generation.active") .register(registry); void generateMonthlyReport() { LongTaskTimer.Sample sample = ltt.start(); try { doHeavyWork(); // visible in metrics WHILE running } finally { sample.stop(); } } // ltt.activeTasks() — how many currently running // ltt.duration(SECONDS) — how long the longest has run

Observation API (Micrometer 1.10+ / Spring Boot 3)

// Modern API: one @Observed creates both metrics AND traces @Configuration public class ObservabilityConfig { @Bean public ObservedAspect observedAspect(ObservationRegistry reg) { return new ObservedAspect(reg); // enables @Observed } } @Service public class OrderService { // Creates Timer + Trace span automatically @Observed(name = "order.create", contextualName = "creating-order") public Order createOrder(CreateOrderRequest req) { ... } // Programmatic Observation API public Order processOrder(Long id) { return Observation.createNotStarted("order.process", registry) .lowCardinalityKeyValue("service", "order-svc") .observe(() -> actualProcessing(id)); } }

Dependencies & Config

Tags — the key to useful metrics

// BAD — no dimensions, can't filter by endpoint Counter.builder("api.requests").register(registry); // GOOD — low-cardinality tags for dashboarding Counter.builder("api.requests") .tag("endpoint", "/api/orders") // low cardinality .tag("method", "GET") .tag("status", "200") .register(registry); // CRITICAL: never use user IDs or order IDs as tags! // High cardinality = millions of time series = OOM Prometheus // Use low-cardinality tags: status codes, HTTP methods, // service names, environment names

Useful Prometheus PromQL queries

# Request rate (req/sec) over 5-min window rate(http_server_requests_seconds_count[5m]) # Error rate (5xx only) rate(http_server_requests_seconds_count{status=~"5.."}[5m]) / rate(http_server_requests_seconds_count[5m]) # 99th percentile latency histogram_quantile(0.99, rate(http_server_requests_seconds_bucket[5m])) # JVM heap usage % jvm_memory_used_bytes{area="heap"} / jvm_memory_max_bytes{area="heap"}
Counters always go up — use rate() in PromQL to get per-second rates. Gauges can be used directly. Never alert on raw counter values.

4. Distributed Tracing — TraceId, SpanId & Propagation

Core concepts

Trace
One end-to-end request journey across all services. Identified by a single TraceId. Contains all spans from all services.
Span
One unit of work within a trace — a service call, a DB query, an external HTTP call. Has its own SpanId and a parent SpanId. Has start/end timestamps.
Context Propagation
TraceId + SpanId passed between services via HTTP headers. Each service creates a child span with a new SpanId but the same TraceId.

B3 vs W3C TraceContext headers

# B3 propagation (Zipkin native) X-B3-TraceId: 4bf92f3577b34da6a3ce929d0e0e4736 X-B3-SpanId: 00f067aa0ba902b7 X-B3-ParentSpanId: a3ce929d0e0e4736 (if child span) X-B3-Sampled: 1 (1=trace this request, 0=don't) # W3C TraceContext (newer standard, OTEL default) traceparent: 00-4bf92f3577b34da6a3ce929d0e0e4736-00f067aa0ba902b7-01 # format: version-traceId-spanId-flags

Sampling

# application.yml — sample 10% of requests management: tracing: sampling: probability: 0.1 # 0.0=off, 1.0=100% # Production: 1-10% sampling (millions of requests) # Dev/staging: 1.0 (100% — easier debugging)

Micrometer Tracing setup

<!-- pom.xml — Brave bridge (Zipkin) --> <dependency> <groupId>io.micrometer</groupId> <artifactId>micrometer-tracing-bridge-brave</artifactId> </dependency> <dependency> <groupId>io.zipkin.reporter2</groupId> <artifactId>zipkin-reporter-brave</artifactId> </dependency> # application.yml management: zipkin: tracing: endpoint: http://zipkin:9411/api/v2/spans // Custom span in your code @Autowired private Tracer tracer; public Order processOrder(Long id) { Span span = tracer.nextSpan() .name("order.process") .tag("orderId", id.toString()) .start(); try(var ws = tracer.withSpan(span)) { return doProcess(id); } finally { span.end(); } } // MDC integration — TraceId in logs automatically // Pattern: %d{HH:mm:ss} [%X{traceId}] [%X{spanId}] %-5level %logger - %msg // Log output: 14:23:11 [4bf92f35] [00f067aa] INFO OrderService - Order saved

Baggage — propagate custom data

// Baggage travels with the trace through all services // Perfect for: tenantId, userId, correlationId, feature flags BaggageField tenantField = BaggageField.create("tenant-id"); // In service A — set baggage tenantField.updateValue("tenant-acme"); // In service B — read baggage (from propagation headers) String tenantId = tenantField.getValue();
