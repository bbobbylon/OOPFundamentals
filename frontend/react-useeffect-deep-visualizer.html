useEffect In Depth

Effects synchronize your component with an external system — and most of the time you don't need one. Deps comparison, the fetch race condition + cleanup, infinite-loop dependency traps, and the cases where an effect is the wrong tool.

What is useEffect really doing — and when should you NOT use it?

useEffect is a hook that synchronizes your React component with something outside of React — a browser API, a subscription, a timer, or a network request. The definition: useEffect(setup, dependencies?). React calls setup after every render where any dependency changed. If setup returns a cleanup function, React calls it before the next setup run and on unmount. Dependency array rules: empty array [] = run once on mount only; no array = run after every render (dangerous); array with values = run when those values change (shallow comparison with Object.is). The fetch race condition: if userId changes quickly (say, user clicks user 1 then user 2), two fetches are in-flight. The response for user 1 might arrive AFTER user 2's response, displaying the wrong user. The fix: use the cleanup function to cancel the previous fetch with an AbortController. Infinite loop trap: useEffect(() => { setUser({...}); }, [user]) — effect updates user, which triggers the effect again, forever. Break cycles by using a ref or a different dep. When NOT to use useEffect: don't use it to transform data for rendering (use useMemo instead); don't use it to reset state when props change (derive the state instead); don't use it to notify a parent of a change (do that during the event handler). React's official docs say: "If you're not synchronizing with an external system, you probably don't need an effect."

Deps comparison

// Object.is comparison (same as ===) useEffect(() => { /* runs */ }, [42]); // number: stable ✓ useEffect(() => { /* runs */ }, ['hello']); // string: stable ✓ useEffect(() => { /* runs */ }, [true]); // boolean: stable ✓ // ⚠ New object/array each render = always runs useEffect(() => {}, [{ id: 1 }]); // new ref every render useEffect(() => {}, [[1, 2, 3]]); // new ref every render useEffect(() => {}, [() => {}]); // new ref every render // Fix: stabilize with useMemo / useCallback const options = useMemo(() => ({ id: userId }), [userId]); useEffect(() => { fetch('/api', options); }, [options]); // Or just use the primitive: useEffect(() => { const opts = { id: userId }; // create inside fetch('/api', opts); }, [userId]); // ← userId is a stable primitive

Fetch + AbortController cleanup

useEffect(() => { // Create a cancel token for this fetch const controller = new AbortController(); fetch(\`/api/users/${userId}\`, { signal: controller.signal, // attach to fetch headers: { Authorization: \`Bearer ${token}\` } }) .then(r => r.json()) .then(setUser) .catch(err => { if (err.name !== 'AbortError') setError(err); // AbortError = cleanup called, ignore it }); // Cleanup: cancel the fetch if userId changes // or component unmounts return () => controller.abort(); }, [userId, token]); // If userId changes before fetch resolves: // cleanup calls controller.abort() → fetch cancels // new effect starts with new userId → fresh fetch

Angular ngOnInit comparison

React useEffect → Angular lifecycle equivalent: useEffect(fn, []) → ngOnInit() (mount). Cleanup function return → ngOnDestroy(). useEffect(fn, [id]) → no direct equivalent — Angular would use a Setter on the @Input() or ngOnChanges. Data fetching in useEffect → Angular's ngOnInit() { this.service.getUser(id).subscribe(u => this.user = u); }. Race condition fix in Angular: RxJS switchMap automatically cancels the previous inner observable: this.route.paramMap.pipe(switchMap(p => this.service.getUser(+p.get('id')!))).subscribe(). The AbortController pattern in React is the manual equivalent of RxJS's switchMap cancellation. RxJS is more ergonomic for complex async sequences; useEffect + AbortController is simpler for straightforward fetches.

In a CIAM React app: Token refresh on interval — useEffect + cleanup: useEffect(() => { const id = setInterval(() => refreshAccessToken(), 4 * 60 * 1000); return () => clearInterval(id); }, []) — without the cleanup, if the component unmounts (user logs out), the interval keeps running, calling refreshToken on a dead session forever. WebSocket connection for real-time user status: useEffect(() => { const ws = new WebSocket(url); ws.onmessage = e => dispatch(parseEvent(e)); return () => ws.close(); }, [url]). Race condition guard matters here too — if url changes (multi-tenant IDP switching), the old socket must be closed before opening a new one. In contrast, TanStack Query handles all this automatically for HTTP requests — prefer it over manual useEffect fetching for user data.

1. The three dependency-array shapes

FormRunsUse for
useEffect(fn) — no arrayafter every commitalmost never — usually a mistake
useEffect(fn, []) — emptyonce after mount; cleanup on unmountone-time setup: subscribe, connect
useEffect(fn, [a, b])after mount + whenever a or b changere-sync when an input changes
Deps are compared with Object.is, shallowly. Primitives compare by value, but objects/arrays/functions compare by reference. A fresh {}, [], or inline () => {} created during render is a new reference every time — so an effect that depends on it re-runs every render. That is the root of most "infinite loop" and "effect won't stop firing" bugs.

2. Effects are for synchronizing with external systems

The mental model from the React docs: an effect synchronizes your component with something outside React — a server, the browser DOM/APIs, a non-React widget, a subscription. If you are not synchronizing with an external system, you probably do not need an effect.

useEffect(() => {
  const conn = createConnection(roomId); // connect (setup)
  conn.connect();
  return () => conn.disconnect(); // disconnect (cleanup)
}, [roomId]); // re-sync when the room changes

3. You Might Not Need an Effect

Tempting effectDo this instead
Transform data for rendering (setFiltered in effect)Compute it during render: const filtered = items.filter(...)
Handle a button click / form submit in an effectPut the logic in the event handler
Reset state when a prop changesGive the component a key so React remounts it
"Cache" an expensive calc in state + effectuseMemo(() => calc(a), [a])
Chain effects that each setStateCalculate everything in one place; avoid effect waterfalls
Effect → render → effect waterfalls are slow. Each effect that calls setState forces another render + paint before the user sees the final result. Deriving values during render (or in an event handler) collapses that into a single pass.
