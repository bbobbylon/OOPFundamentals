useReducer & useContext

useReducer centralizes state transitions in a pure function; useContext beams a value down the tree without prop drilling. Together they are React's built-in, dependency-free state manager.

What are useReducer and useContext — and how do they replace Redux for mid-sized apps?

useReducer is a state hook for complex state. Instead of calling setX with the new value directly, you call dispatch({ type: 'ACTION', payload: data }) and a pure reducer function decides what the next state is: (currentState, action) => nextState. Benefits: (1) all state transitions are in ONE place (the reducer), easy to read, easy to test — the reducer is just a plain function with no side effects. (2) dispatch is stable (never changes reference), so you can pass it to children without useCallback. (3) complex state with many fields stays coherent — you can't accidentally update only half the state. useContext: React's built-in way to share data through the component tree without passing it as props through every intermediate component ("prop drilling"). Create a context with React.createContext(defaultValue). Provide it high in the tree with <MyContext.Provider value={{ state, dispatch }}>. Consume it anywhere below with const { state, dispatch } = useContext(MyContext). Combined pattern: useReducer defines the state + all transitions. Context distributes both state and dispatch to the tree. This is the "poor man's Redux" — no extra dependencies needed. The key limitation vs Zustand/Redux: when context value changes, every consumer re-renders (no selector optimization). For large apps with frequent global updates, Zustand or Redux Toolkit perform better. For small-to-medium shared state (auth, theme, a wizard flow), useReducer + Context is perfect.

useReducer anatomy

// State shape interface AuthState { user: UserDto | null; loading: boolean; error: string | null; } // Action discriminated union type AuthAction = | { type: 'LOGIN_START' } | { type: 'LOGIN_SUCCESS'; payload: UserDto } | { type: 'LOGIN_ERROR'; payload: string } | { type: 'LOGOUT' }; // Reducer: pure, testable function authReducer(s: AuthState, a: AuthAction): AuthState { switch (a.type) { case 'LOGIN_START': return {...s, loading:true, error:null}; case 'LOGIN_SUCCESS': return {user:a.payload, loading:false, error:null}; case 'LOGIN_ERROR': return {...s, loading:false, error:a.payload}; case 'LOGOUT': return {user:null, loading:false, error:null}; } } const [state, dispatch] = useReducer(authReducer, {user:null,loading:false,error:null});

Context provider + consumer

// 1. Create typed context const AuthCtx = React.createContext<{ state: AuthState; dispatch: React.Dispatch<AuthAction>; } | null>(null); // 2. Provider component (wraps the app) function AuthProvider({ children }: { children: ReactNode }) { const [state, dispatch] = useReducer(authReducer, initial); return <AuthCtx.Provider value={{state, dispatch}}>{children}</AuthCtx.Provider>; } // 3. Custom hook for consumers function useAuth() { const ctx = useContext(AuthCtx); if (!ctx) throw new Error('useAuth must be inside AuthProvider'); return ctx; } // 4. Consume anywhere in the tree function NavBar() { const { state, dispatch } = useAuth(); return <button onClick={() => dispatch({type:'LOGOUT'})}> Log out {state.user?.name} </button>; }

Angular BehaviorSubject comparison

React pattern → Angular equivalent. authReducer pure function → methods on AuthService that call this.userSubject.next(newValue). AuthCtx.Provider → @Injectable({providedIn:'root'}) singleton service (globally available). useContext(AuthCtx) → constructor(private auth: AuthService){} + this.auth.user$. dispatch({type:'LOGOUT'}) → this.auth.logout(). The discriminated union of actions maps to methods on the Angular service — both centralize state transitions in one place. The key difference: Angular's state changes don't re-render the whole component tree; only components subscribed to the specific Observable update. React's Context re-renders all consumers whenever value changes. For this reason, split contexts: AuthUserCtx (changes rarely) and AuthLoadingCtx (changes often) separately.

In a CIAM React app: Auth context wraps the whole app in main.tsx: <AuthProvider><RouterProvider router={router} /></AuthProvider>. The useAuth() hook is used in: NavBar (display user name + roles), login page (dispatch LOGIN_SUCCESS after OAuth callback), router loaders (get token for API headers), every protected route. Actions map directly to the CIAM auth flow: OAUTH_CALLBACK_START → OAUTH_CALLBACK_SUCCESS { user, token, idpType } → TOKEN_REFRESHED { newToken } → LOGOUT. The reducer ensures these state transitions are atomic — you can never be in a state where user is set but token is null, because the reducer sets them together in one transition. Test the reducer in isolation: expect(authReducer(initial, {type:'LOGOUT'})).toEqual({user:null,...}).

1. useReducer vs useState

Reach for useStateReach for useReducer
One or two independent valuesSeveral values that change together
Simple set/replace updatesMany actions / complex transition logic
Logic lives in the componentLogic worth extracting + unit-testing (it is a plain function)
Next state rarely depends on prevNext state derived from prev + an action
const [state, dispatch] = useReducer(reducer, { count: 0 });
// dispatch is a STABLE reference — safe to omit from deps & pass down
dispatch({ type: 'increment', by: 5 });
dispatch never changes identity. Like setState, React guarantees a stable dispatch across renders. You can pass it through context or to memoized children without it triggering re-renders, and you can safely leave it out of effect dependency arrays.

2. A reducer is a pure function

function reducer(state, action) {
  switch (action.type) {
    case 'increment': return { ...state, count: state.count + action.by };
    case 'reset': return { count: 0 };
    default: throw new Error('unknown action ' + action.type);
  }
}
Rules: Always return a new object (never mutate state) so React's Object.is check detects the change. No side effects, no async, no fetching — a reducer takes (state, action) and returns the next state, deterministically. That purity is exactly what makes it trivially unit-testable and replayable.

3. The context re-render gotcha

Every component that calls useContext(X) re-renders whenever X's Provider value changes by Object.is — even React.memo cannot stop it. Passing a fresh object value={{ state, dispatch }} every render re-renders all consumers.

ProblemFix
New value object each renderuseMemo(() => ({ state, dispatch }), [state])
Dispatch-only components re-render on state changeSplit into a state context and a dispatch context
One huge context for everythingMultiple focused contexts so changes are scoped
