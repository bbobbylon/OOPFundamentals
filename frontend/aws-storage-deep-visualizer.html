Storage Deep Dive — EBS vs EFS vs S3 Storage Classes

Three storage services that solve three different problems: EBS is a disk for one instance, EFS is a shared filesystem for many, and S3 isn't a filesystem at all — it's an object store with storage classes built for cost, not access speed.

💾 Block, file, or object — which storage model actually fits the job?

EBS (Elastic Block Store) is block storage: a virtual hard drive that attaches to exactly one EC2 instance at a time (with the narrow exception of Multi-Attach io2 volumes for cluster-aware filesystems). It behaves like a real disk — you format it, mount it, and the OS sees raw blocks. gp3 is the default general-purpose SSD: a flat 3,000 IOPS and 125 MB/s baseline that you can provision independently of size (unlike its predecessor gp2, where IOPS scaled with volume size). io2 is the high-performance tier for latency-sensitive, high-IOPS workloads (databases) — provisioned IOPS up to 64,000 with 99.999% durability. EFS (Elastic File System) is file storage: a managed, POSIX-compliant NFS filesystem that many instances (or Lambda functions) can mount concurrently, all reading and writing the same shared files — something EBS fundamentally can't do. EFS has two throughput modes: Bursting (throughput scales with the amount of data stored, with a burst credit balance for spikes) and Provisioned (you set a fixed throughput regardless of size, for workloads that need consistent high throughput on a small dataset). S3 (Simple Storage Service) is object storage — not a filesystem at all. There's no mounting, no POSIX semantics, no partial-file edits: you PUT a whole object under a key and GET it back. What S3 has instead is storage classes — the same durability, different price-vs-retrieval-speed tradeoffs: Standard (frequent access, millisecond retrieval), Standard-IA (infrequent access, cheaper storage, a per-GB retrieval fee, still millisecond access), Glacier Instant Retrieval (archive pricing, still millisecond access), Glacier Flexible/Deep Archive (cheapest, but retrieval takes minutes to hours), and Intelligent-Tiering, which watches access patterns and moves objects between tiers automatically. A lifecycle rule automates the Standard → IA → Glacier progression based on an object's age, with zero application code involved.

  • EBS = block, one instance — a virtual disk; gp3 for general purpose, io2 for high-IOPS databases.
  • EFS = file, many instances — a shared NFS filesystem; Bursting throughput scales with size, Provisioned is a fixed rate you set.
  • S3 = object, no filesystem semantics — whole-object PUT/GET; storage classes trade retrieval speed for cost, not access pattern.
  • Lifecycle rules automate the tradeoff — age-based transitions move objects to cheaper classes with no application code required.

EBS snapshots are incremental, but restores are full

Each EBS snapshot only stores the blocks changed since the last one (cheap, fast to create) — but restoring ANY snapshot to a new volume reconstructs the entire disk, not just the delta, because S3 (where snapshots live) has to replay the full chain.

EFS bills for storage AND throughput mode separately

Provisioned Throughput mode has its own hourly charge on top of per-GB storage — sized for a small, hot dataset that needs more throughput than Bursting mode's size-proportional formula would ever grant it.

Glacier retrieval has three speed tiers, each priced differently

Flexible Retrieval alone offers Expedited (1-5 min), Standard (3-5 hrs), and Bulk (5-12 hrs) — picking Bulk for a large restore can be 10x cheaper than Expedited for the same data, if you can tolerate the wait.

The CIAM parallel: a shared session-cache or a Spring Boot app's uploaded profile-photo store both illustrate the block-vs-file-vs-object choice directly: an app server's own OS/app binaries live on EBS (one instance, one disk); a directory of files that MULTIPLE app server instances behind a load balancer need to read and write concurrently (like a shared temp-upload staging area) needs EFS, not EBS; and the final, durable copy of an uploaded profile photo belongs in S3, with a lifecycle rule quietly moving photos nobody's viewed in 90 days into IA to cut storage cost.

A few things worth knowing

  • gp3 decouples size from performance — unlike gp2, you can provision 3,000+ IOPS on a small gp3 volume without over-provisioning capacity you don't need, just to buy more IOPS.
  • EFS access points scope permissions per-application — rather than every mounting instance sharing one root, an access point enforces a specific POSIX user/group and a restricted root directory, so multiple apps sharing one EFS filesystem can't see each other's files.
  • Intelligent-Tiering has no retrieval fee — unlike manually chosen IA/Glacier classes, Intelligent-Tiering moves objects automatically based on observed access and never charges a retrieval fee, at the cost of a small monthly monitoring fee per object.
