Lazy Loading & Preloading

Ship a small app, not a monolith. Lazy routes code-split each feature into its own chunk that downloads only when needed — so the initial bundle stays tiny. Preloading then fetches likely-next chunks quietly in the background, and canMatch can stop a chunk (say, the admin bundle) from ever downloading for users who can't use it.

🔒 canMatch — the hidden security feature of lazy loading

A standard canActivate guard stops a user from seeing a route — but the chunk still downloads. A non-admin hitting /admin gets redirected to /403, yet Angular already fetched the admin bundle before the guard ran. canMatch (Angular 14+) runs before the route even matches: return false and the chunk is never downloaded, the route is skipped, and Angular tries the next one. For admin features with sensitive UI logic, canMatch means non-admins never receive that JavaScript at all.

  • canActivate: match → download chunk → guard → redirect. canMatch: guard first → if false, skip route, no download.
  • Use canMatch when the denied user should hit a different route, or to keep a sensitive chunk off their machine.
  • Preloading fetches likely-next chunks after first paint — PreloadAllModules, a custom data:{preload:true} strategy, or Quicklink.
  • ng build --named-chunks gives readable chunk names in dev — but never in prod (route names leak structure).
  • Combine: canMatch for security + a preload strategy for speed on routes the user will likely visit.

canActivate vs canMatch

canActivate: route matches, chunk downloads, guard runs, redirect if denied. canMatch: guard runs first — if false, the route is skipped, the chunk never downloads, and the next route is tried.

Preloading strategies

withPreloading(PreloadAllModules) silently fetches all lazy chunks after load; a custom strategy preloads only data:{preload:true} routes; Quicklink preloads chunks for routes linked on the current page.

Chunk naming in angular.json

Default chunk names are hashes (chunk-ABCDE.js). ng build --named-chunks yields admin-dashboard-component.js — easy to spot in Network. Never in prod: the route name reveals app structure.

In CIAM:{ path: 'admin', canMatch: [() => inject(AuthStore).hasRole('SYSTEM_ADMIN')], loadChildren: () => import('./admin/routes') } — non-admins never download the admin chunk. Login/callback stay eager; user-management is lazy with data:{preload:true} so it loads after login when the user will likely go there next.

The problem

You deployed twenty minutes ago. Half the open tabs don't know it yet.

The user did nothing wrong, and the app still went blank

Someone's had the app open since this morning. You ship a deploy at lunch. At 2pm they click into "Reports" for the first time this session — a route they haven't visited yet, so it hasn't been downloaded. The router calls import('./reports/reports.component'), which resolves to a specific hashed filename baked into the JavaScript their tab already has — reports.abc1.js. Your new deploy replaced that file with reports.xyz9.js and deleted the old one. The import rejects. The screen goes blank, or nothing happens at all, depending on what (if anything) is listening.

app worked fine 20 minutes ago ✓ user changed nothing ✓ reports.abc1.js no longer exists on the server ⚠ Angular does not retry by default ⚠

The bug isn't in the code the user is running. It's that the code they're running doesn't exist on the server anymore.

A deployed bundle is a promise about files that might not exist anymore. Every import() the router does is a bet that the chunk map baked into whatever index.html this tab loaded is still an accurate map of what's on the server — and that bet loses the instant you deploy while someone has a tab open to a route they haven't visited yet.
Think of a running SPA tab as a restaurant menu photographed at 6pm and handed to a customer who doesn't order until 9. By 9 the kitchen's swapped the salmon for something else — the photo doesn't know that, because photos don't refresh themselves. Ordering the salmon (clicking into a route this tab has never fetched) sends the order to a dish that no longer exists. Reloading the page is asking for a fresh menu; nothing less actually fixes it, because nothing less makes the tab look at the kitchen again.

The user says the app just went blank when they clicked a nav link. Nothing in my code changed today.

I tried. I called import('./reports/reports.component') exactly like the route config told me to, bundled as reports.abc1.js when this tab's index.html first loaded. That file 404'd. I don't retry failed imports — I raised a NavigationError and stopped there.

The server

window.location.reload()

I'm the only one of us who can actually fix this. Everything else in this conversation is still working from the old map. I'm the one action that throws the map away and asks for a new one.

The mechanism

The chunk map isn't reloaded per click. It's frozen the moment the tab opened.

  1. This morning, the tab loads index.html — it references reports.abc1.js by that exact hashed name, wherever that route is first neededa map frozen at load time
  2. At lunch you deploy. The build re-hashes what changed; reports.abc1.js is gone from the server, replaced by reports.xyz9.jsthe open tab has no way to know
  3. At 2pm the user clicks into Reports for the first time this session — the router resolves the lazy route and calls import(...)using the OLD filename, because that's all this tab has ever known
  4. The dynamic import rejects — a clean 404 against a hashed filename, or a CDN edge that already evicted the asset — Angular surfaces it as ChunkLoadErrornot a bug in your TypeScript
  5. Angular does not auto-retry. The router emits NavigationError { error: ChunkLoadError } and the navigation simply failsby default: no message, no recovery
  6. A Router.events listener catching that error is the only thing standing between this and a reload that actually fixes ityour code has to opt in — Angular won't do it for you

Step 1 is the lesson, and everything after it is that one fact playing out. The chunk map isn't something Angular reconsults on every click — it's baked into the JavaScript the browser already has, fixed at the moment index.html loaded. A deploy doesn't just ship new code to new visitors; it quietly invalidates the map every already-open tab is still using, and nothing forces one of those tabs to notice until it reaches for a file that's gone.

Swap the strategy and nothing about the route table changes — same canMatch guards, same lazy chunks, same components. All that moves is when the download happens: never, always shortly after load, or only for the routes you've flagged. That's the entire surface of withPreloading() — one strategy object, plugged in once, and every route defers to it.

A route config lists { path: 'admin', canMatch: [isAdmin], loadChildren: ... } immediately followed by a wildcard { path: '**', component: NotFoundComponent }. A non-admin user navigates to /admin. What happens?

Exactly — this is the actual point of canMatch over the older canActivate-only approach: a false return doesn't reject the navigation, it makes the router treat that route definition as though it were never there, so matching just keeps walking the config. Put a wildcard after the guarded route and a denied user gets a normal "not found," with zero bytes of the admin bundle ever requested.

That's the mental model canActivate trains you into — match first, download, guard, then redirect-or-error on denial. canMatch works one step earlier: a false result means the route is treated as not matching in the first place, so there's nothing here for a NavigationError to be about. The config simply moves on to the next candidate.

Reasonable if you're picturing canMatch as leaving a hole in the route table — but the wildcard route is still sitting right there as the next candidate. The router doesn't stop at the first denial; it keeps evaluating routes in order until one matches, and a trailing ** exists specifically to always match.

Where you've seen this before

Three systems, one shared problem: a client holding a map the server already redrew.

React.lazy() hits the identical ChunkLoadError

This isn't an Angular quirk — React.lazy(() => import('./Reports')) uses the exact same browser-level dynamic import(), so a React SPA deployed behind the same kind of hashed build gets the exact same stale-chunk failure after a deploy, under the name ChunkLoadError in webpack or a fetch failure in Vite. The fix people reach for is the same one, too: catch the error at the top of the tree and prompt a reload.

framework-agnostic — it's an import() problem

Mobile "force update" banners are the same fix, without a reload button

A native app can't just refetch index.html — the binary is installed. So when a backend makes a breaking API change, mobile teams ship a minimum-supported-version check that the server enforces, forcing a blocking "update required" screen. Same root cause as your open tab (client is running a contract the server has moved past), and a much heavier fix, because reloading a webpage is free and forcing an app-store update is not.

no reload() equivalent on mobile

Your CIAM job: a cached JWKS pointing at rotated signing keys

An OIDC client caches the issuer's .well-known/openid-configuration and its JWKS (signing keys) rather than fetching them on every request. Ping or Entra rotates signing keys, and a client still holding the old JWKS starts failing token validation for tokens signed with a key it doesn't recognize — until it re-fetches. Same shape as the chunk map: a cached "here's where things are" going stale the moment the source of truth moves.

cached contract, source of truth moved
Questions from the back row

Does hashing the filenames actually fix the ChunkLoadError, or just make it less confusing?

Just the second one, and that's still worth a lot. Hashing doesn't stop the old file from being gone after a deploy — it makes that failure immediate and detectable: a stale hashed reference 404s cleanly, instead of a stable filename silently serving whatever new (mismatched) content now lives at that URL, which is a far worse failure mode because nothing throws. The actual fix is still the NavigationError-triggered reload. Hashing just keeps the failure honest.

If PreloadAllModules downloads every lazy chunk right after load anyway, doesn't that defeat the point of lazy loading?

It defeats deferring the download, but keeps the part that actually matters for perceived speed: the initial bundle — the one blocking first paint — stays small, because none of the lazy chunks are in it. Everything else streams in during idle time after the app is already interactive. For most apps that trade is worth it. Where it isn't — one genuinely huge module (a reporting dashboard, a rich admin panel) that most users never open — is exactly the case for a custom strategy that only preloads routes flagged data:{preload:true}, or no preloading at all for that one route.

Why doesn't Angular just retry the failed import() automatically?

Because a failed import() after a deploy usually isn't a transient network blip — it's a stale reference to a file that no longer exists at that URL, full stop. Retrying the identical request fails the identical way every time; a blind retry loop just spins forever. The only thing that changes the outcome is fetching a new index.html, which is what a reload does and a retry, by definition, does not.

1. Split at the route

export const routes: Routes = [
  { path: '',          component: HomeComponent },                  // eager → in the initial bundle
  { path: 'dashboard', loadComponent: () => import('./dashboard') }, // lazy → its own chunk
  { path: 'admin',     canMatch: [adminGuard],
                  loadComponent: () => import('./admin') },     // lazy + gated: chunk only loads if guard passes
  { path: 'reports',   loadChildren: () => import('./reports.routes'),
                  data: { preload: true } },                       // flagged for custom preloading
];

loadComponent (a standalone component) or loadChildren (a sub-route file) both produce a separate chunk. canMatch runs during matching, so a failed guard means the import never even fires.

3. Choosing a preloading strategy

provideRouter(routes,
  withPreloading(PreloadAllModules));      // or a custom PreloadingStrategy

export class FlaggedPreload implements PreloadingStrategy {
  preload(route: Route, load: () => Observable<any>) {
    return route.data?.['preload'] ? load() : of(null);  // only flagged routes
  }
}
  • NoPreloading — smallest first load; every feature pays on first visit.
  • PreloadAllModules — snappy navigation; fetches everything after the app boots (fine for small/medium apps).
  • Custom — preload only likely-next routes (flag them) — the usual sweet spot.

4. Tips

  • Split by feature/route, not by tiny component — too many micro-chunks add request overhead.
  • Measure with source-map-explorer on the build to see what's actually in each chunk (and what bloats the initial one).
  • Gate, don't just hide. canMatch keeps an admin chunk off non-admins' machines entirely — better than shipping it and hiding the link.
  • In-view laziness for big components within a page → @defer (different tool, same goal of "load it when needed").

5. One-sentence recap

📦 Lazy-load features with loadComponent/loadChildren so each becomes a chunk fetched on demand (tiny initial bundle), choose a preloading strategy — none, PreloadAllModules, or a custom one that preloads only flagged likely-next routes — to hide navigation latency, and use canMatch to stop gated chunks (like admin) from ever downloading for users who can't use them; split by feature, measure the bundles, and reach for @defer for in-view component laziness.
