Context API Deep Dive

Context is a wormhole through the tree — but every consumer re-renders when the value changes, and React.memo can't stop it. The propagation model, the re-render storm, selector workarounds, and the values you should never put in context.

What is React Context — and why does it cause re-render storms if misused?

Context is React's mechanism for passing data down the component tree without threading it through every intermediate component as props. It works like a broadcast channel: a Provider broadcasts a value; any component below that Provider in the tree can tune in with useContext and receive the value directly. No prop drilling. The critical rule: when the context value changes, EVERY component that calls useContext(MyCtx) re-renders — regardless of whether the specific part of the value they use changed. React.memo cannot prevent this — memo only stops re-renders caused by prop changes, not context changes. This causes "re-render storms." Example: if you put { user, notifications, theme, locale } all in one context, every component using this context re-renders whenever notifications update — even components that only care about the user. Solutions: (1) split contexts by update frequency — UserContext (changes rarely), NotificationContext (changes often) separately. (2) Use useMemo on the context value to stabilize object references. (3) Move to Zustand with selectors for high-frequency global state. What belongs in context: stable, infrequently-changing values — the current user, the active theme, the current locale, i18n translations. What does NOT belong in context: the full user list (changes constantly), loading states, form data, any frequently-updating server state.

Re-render storm example

// ❌ BAD: everything in one context const AppCtx = createContext<{ user: UserDto | null; notifications: Notification[]; // changes every second theme: 'light' | 'dark'; locale: string; }>(...); // NavBar only uses user and theme // but re-renders every second when notifications update function NavBar() { const { user, theme } = useContext(AppCtx); // ← re-renders every time notifications changes // React.memo on NavBar doesn't help } // ✓ GOOD: split by update frequency const UserCtx = createContext<UserDto | null>(null); const ThemeCtx = createContext<'light'|'dark'>('light'); const NotifCtx = createContext<Notification[]>([]); // NavBar uses UserCtx + ThemeCtx only // → never re-renders on notification changes

useMemo stabilization

// Stabilize context value with useMemo function AuthProvider({ children }: { children: ReactNode }) { const [user, setUser] = useState<UserDto | null>(null); const [token, setToken] = useState(''); // Without useMemo: new object every render // → all consumers re-render on every parent render // With useMemo: only new object when user/token changes const value = useMemo(() => ({ user, token, login: (u: UserDto, t: string) => { setUser(u); setToken(t); }, logout: () => { setUser(null); setToken(''); }, }), [user, token]); // login/logout are re-created but that's ok — // they only change when user/token changes return <AuthCtx.Provider value={value}>{children}</AuthCtx.Provider>; }

Context vs Zustand

Context: built-in, no deps. Best for stable values (auth user, theme). All consumers re-render on any change — no selectors. Needs Provider in tree. Zustand: external library (<1KB). Selector-based: const user = useStore(s => s.user) — only re-renders when user changes, even if other store fields update. No Provider needed. Better for high-frequency global state. Angular equivalent of Context: a service provided at a component or module level (not root) creates a scoped singleton — same idea as a Context that only provides to a subtree. Angular equivalent of Zustand: @Injectable({providedIn:'root'}) service with Signals: const user = signal<UserDto|null>(null) — only components that reference user() in their template re-render when user changes. Signals in Angular solve the same "granular subscription" problem Zustand selectors solve in React.

In a CIAM React app: Well-designed context structure: AuthContext → { user: UserDto | null, idpType: 'PING' | 'ENTRA' | null, logout: () => void } (changes only on login/logout — rare). ThemeContext → 'light' | 'dark' (stable). ToastContext → { toasts: Toast[], addToast, removeToast } (but move to Zustand if toasts update frequently). What NOT to put in Context: the user list from /api/users (use TanStack Query instead); pagination cursors (local state per page); search query (local state). The test: "how often does this value change, and how many components consume it?" If the value changes more than a few times per minute and many components consume it, use Zustand with selectors instead of Context.

1. Context solves prop drilling, not state management

Context is a transport mechanism: it lets a deep component read a value without every component in between forwarding it as a prop. It is not a store — it has no reducers, no selectors, no devtools. Pair it with useState/useReducer (which hold the state) to manage state.

The default value is a footgun. createContext(defaultValue)'s default is used only when a consumer has no Provider above it. Forget to wrap a subtree in the Provider and consumers silently read the default instead of erroring — which is why a custom hook that throws when the value is the sentinel default is the recommended guard.

2. Who re-renders when the value changes?

ComponentRe-renders on value change?
Consumers (useContext)Yes — always, even if wrapped in React.memo
Non-consumers between Provider and consumerNo (unless they re-render for other reasons)
The Provider's own parentNo — it is the parent that usually causes the value change
Children passed as {children} to the ProviderNo — they were created by the parent, so they're reused (key trick!)
The children escape hatch: A Provider component that renders {props.children} does not re-render those children when its own state changes — they were created in the parent's render, so React reuses the same element references. This lets a stateful Provider update without re-rendering the entire app it wraps.

3. Context has no built-in selector

Redux lets you useSelector(s => s.user.name) and only re-render when that slice changes. Context cannot — a consumer subscribes to the whole value. The mitigations:

TechniqueEffect
Split into multiple contextsChanging one context doesn't re-render the others' consumers
Memoize the value (useMemo)Stops a new object reference re-rendering consumers every render
use-context-selector librarySubscribe to a slice; skip re-renders when other slices change
Reach for Zustand/Jotai/ReduxFirst-class selectors + devtools when state grows
