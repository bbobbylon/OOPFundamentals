1. Context solves prop drilling, not state management

Context is a transport mechanism: it lets a deep component read a value without every component in between forwarding it as a prop. It is not a store — it has no reducers, no selectors, no devtools. Pair it with useState/useReducer (which hold the state) to manage state.

The default value is a footgun. createContext(defaultValue)'s default is used only when a consumer has no Provider above it. Forget to wrap a subtree in the Provider and consumers silently read the default instead of erroring — which is why a custom hook that throws when the value is the sentinel default is the recommended guard.

2. Who re-renders when the value changes?

ComponentRe-renders on value change?
Consumers (useContext)Yes — always, even if wrapped in React.memo
Non-consumers between Provider and consumerNo (unless they re-render for other reasons)
The Provider's own parentNo — it is the parent that usually causes the value change
Children passed as {children} to the ProviderNo — they were created by the parent, so they're reused (key trick!)
The children escape hatch: A Provider component that renders {props.children} does not re-render those children when its own state changes — they were created in the parent's render, so React reuses the same element references. This lets a stateful Provider update without re-rendering the entire app it wraps.

3. Context has no built-in selector

Redux lets you useSelector(s => s.user.name) and only re-render when that slice changes. Context cannot — a consumer subscribes to the whole value. The mitigations:

TechniqueEffect
Split into multiple contextsChanging one context doesn't re-render the others' consumers
Memoize the value (useMemo)Stops a new object reference re-rendering consumers every render
use-context-selector librarySubscribe to a slice; skip re-renders when other slices change
Reach for Zustand/Jotai/ReduxFirst-class selectors + devtools when state grows
