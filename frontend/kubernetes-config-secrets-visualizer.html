ConfigMaps & Secrets

Decouple configuration from container images. ConfigMaps for plain config, Secrets for credentials.

🗝️ What are ConfigMaps and Secrets — and why should config never live inside your container image?

12-Factor says config that varies per environment must live outside the image — never bake config (or worse, prod credentials) into a container. A ConfigMap holds non-sensitive key-values (an environment-specific application.properties in K8s), consumed as env vars or mounted files — feature flags, base URLs, log levels, CORS. A Secret holds sensitive data as base64 (encoding, not encryption); it sits in etcd, so enable encryption-at-rest and prefer mounting as a tmpfs volume over env vars. For real protection, sync from AWS Secrets Manager / Azure Key Vault (External Secrets, the CSI driver) or use Sealed Secrets / Vault — keeping zero plaintext secrets in etcd or git.

  • Config lives outside the image — same image, per-env config (12-Factor).
  • ConfigMap = non-sensitive key-values; env vars or mounted files.
  • Secret = base64, not encryption — enable etcd encryption; prefer tmpfs mounts.
  • Sync from Key Vault / Secrets Manager (CSI/External Secrets) — none in etcd or git.

Production secret management

Problem: K8s Secrets stored in etcd are base64, not encrypted. If etcd is compromised, all secrets leak. Solutions: (1) Etcd encryption at rest — encrypt etcd data with AES-GCM, keys managed by KMS. (2) External Secrets Operator: CRD that syncs from AWS Secrets Manager / Azure Key Vault / GCP Secret Manager into K8s Secrets automatically: kind: ExternalSecret; spec: { secretStoreRef: { name: aws-secrets-manager }; data: [{ secretKey: PING_CLIENT_SECRET; remoteRef: { key: prod/ciam/ping, property: clientSecret }}] }. (3) Sealed Secrets (Bitnami): encrypt Secret manifest with a cluster public key — safe to commit to git. (4) HashiCorp Vault with Vault Agent sidecar: fetches secrets from Vault's secure storage at pod startup, writes to tmpfs volume. In Azure/AWS environments: use the cloud-native options (Key Vault + Azure Key Vault Provider for Secrets Store CSI Driver, or AWS Secrets Manager CSI driver) — zero secrets in etcd at all.

CIAM secrets management: Your app needs PING_CLIENT_SECRET, ENTRA_CLIENT_SECRET, DB_PASSWORD, JWT_SIGNING_KEY, etc. In Azure AKS, use Azure Key Vault + the Secrets Store CSI Driver — secrets stay in Key Vault, mounted via a SecretProviderClass (none in etcd or git, automated rotation). Spring reads them with @Value("${PING_CLIENT_SECRET}") regardless of file vs env-var source. Put non-secret config (SPRING_PROFILES_ACTIVE, PING_BASE_URL, CORS_ORIGINS) in a ConfigMap — a different one per namespace, same image.

or, the day you find out base64 -d is not a password prompt

The problem

Kubernetes called it a Secret, and you believed it.

"It's in a Secret, so it's protected"

You moved PING_CLIENT_SECRET out of the image and into a kind: Secret, and it felt like you locked something. You didn't. base64 is a transport encoding, not a cipher — it exists so a YAML file can carry the raw bytes of a TLS key, and it has no key, no salt and nothing to crack. Anyone who can get secrets in that namespace reads your Ping client secret in one line, and it does not even feel like an attack:

kubectl get secret ciam-secrets -o jsonpath='{.data.PING_CLIENT_SECRET}' | base64 -d → the plaintext ⚠ etcd stores it unencrypted by default ⚠ an etcd backup on S3 is a credential file ⚠ anyone with pod/exec reads the env ⚠

And the sting: the developer who wrote view-level RBAC for the support team just handed them production's signing key, because view once included secrets and nobody read that far down the ClusterRole.

Three real locks, none of which is base64
RBAC — who may get secrets in this namespace ↓ because this, not encoding, is the actual boundary EncryptionConfiguration — AES-GCM at rest in etcd, KMS-backed ↓ because a stolen etcd snapshot should be noise, not a wallet Key Vault / Secrets Manager via CSI or ESO — nothing in etcd at all
A Secret is not encrypted. It is a ConfigMap that Kubernetes agrees not to print in logs. What actually protects it is RBAC plus encryption at rest — and the second one is off by default on a cluster you did not configure yourself.

The mechanism

Follow one value from etcd to your process, and watch exactly where it freezes.

  1. the ConfigMap/Secret sits in etcd — it is an API object, not a filesource of truth
  2. you create a pod; the kubelet resolves every configMapKeyRef/secretKeyRef right nowat admission
  3. the values are copied into the container's environment as it startsa snapshot
  4. your JVM reads them once into System.getenv(); Spring binds @Value at startupfrozen twice
  5. you edit the ConfigMap. Nothing moves. Nothing will ever move.needs a new pod

Step 3 is the part everyone re-learns the hard way. An env var is a copy taken at container creation, and there is no wire back to etcd — no watch, no sync, no eventual anything. A mounted volume takes the other road: the kubelet keeps watching the object and re-projects the directory (atomically, by swapping a symlink) roughly every minute, so the file on disk really does change under a running process.

"Mounted files update live" is true about the file and a lie about your app. The kubelet changes the bytes at /app/config/LOG_LEVEL; your Spring app read that value into a final field at 09:14 and will keep using it until it dies. Live-updating config needs someone to re-read — Spring Cloud Kubernetes' reload watcher, an Actuator /refresh with @RefreshScope, or your own WatchService. Two footnotes that eat afternoons: a subPath mount never updates (you get a plain file, not a symlink into the projected directory), and a ConfigMap marked immutable: true cannot be edited at all — which sounds like a downside until you learn it also stops the kubelet watching it, cutting a real chunk of API-server load on a big cluster. The immutable workflow is the honest one anyway: new name, new rollout, instant rollback. For the mutable case the standard trick is a checksum/config annotation on the pod template — change the ConfigMap, the checksum changes, the Deployment sees a different pod spec and rolls. Otherwise: kubectl rollout restart deployment/ciam-auth.

Prod is drowning in logs. You run kubectl edit cm ciam-config and change LOG_LEVEL from INFO to WARN. The pod consumes that ConfigMap with envFrom: configMapRef. Five minutes later the logs are unchanged. Why?

This is true — for volume mounts, which is exactly why it is the tempting answer. The kubelet does watch the object and re-project mounted files. It does not, and cannot, reach into a running process and rewrite its environment block.

Right. The kubelet resolved the ConfigMap once, at container creation, and handed the values to the container as its environment. There is no watch and no sync. Roll the pods — kubectl rollout restart deployment/ciam-auth — or add a checksum/config annotation so the ConfigMap edit changes the pod template and rolls them for you.

ConfigMaps are mutable by default; immutable: true is opt-in, and had it been set the API server would have rejected your edit loudly rather than accepting it silently. Your edit landed fine — it just landed in etcd, not in the pod.

Questions from the back row

If base64 buys nothing, why does Kubernetes use it at all?

Because Secret values are []byte, not strings — a TLS private key, a PKCS#12 keystore, a binary licence blob. JSON and YAML cannot carry arbitrary bytes, so the API encodes them. That is the entire reason, and it is a serialization decision wearing a security-sounding word. When your value is text, use stringData: and write it in the clear — the API server base64s it on the way in, and your manifest stays reviewable.

Env var or mounted file — which should I actually use for a secret?

Mount it. An env var is copied into every child process, appears in /proc/<pid>/environ, gets scooped up by crash dumps and APM agents that snapshot the environment, and shows up in plain text under kubectl describe pod if anyone ever writes a literal env: value: instead of a secretKeyRef. A mounted secret lands in tmpfs (RAM, never the node's disk), can be given file permissions, and rotates without a new pod. Use env vars for ConfigMap-grade config; mount the things that would end a quarter if they leaked.

So can I rotate the Ping client secret with no downtime, since mounts update live?

Only if your code re-reads the file. The kubelet will happily replace the bytes within about a minute; Spring's @Value("${PING_CLIENT_SECRET}") was bound once at startup and never looks again. Either re-read on use (a Supplier<String> that reads the file, cached for seconds), or accept a rolling restart — and either way overlap the old and new secret at the IdP during the swap, because pods do not all roll at the same instant.

Grab a napkin

Predict it before you run it.

One ConfigMap, ciam-config, is consumed by the same pod twice: LOG_LEVEL comes in through envFrom: configMapRef, and the whole map is also mounted at /app/config. You kubectl apply a change setting LOG_LEVEL: DEBUG and wait two minutes. Write down both answers before you look: what does kubectl exec pod -- printenv LOG_LEVEL print, and what does kubectl exec pod -- cat /app/config/LOG_LEVEL print? Then the one that matters — is the application logging at DEBUG?

1 — ConfigMap




apiVersion: v1
kind: ConfigMap
metadata:
  name: app-config
data:
  SPRING_PROFILES_ACTIVE: prod
  LOG_LEVEL: INFO
  application.yml: |
    server.port: 8080
    spring.datasource.url: jdbc:postgresql://postgres-svc:5432/mydb
---
# Reference it in a Deployment
envFrom:
- configMapRef:
    name: app-config   # all keys become env vars









2 — Secret




apiVersion: v1
kind: Secret
metadata:
  name: db-secret
type: Opaque
data:  # values MUST be base64-encoded
  DB_PASSWORD: cGFzc3dvcmQxMjM=   # echo -n "password123" | base64
  JWT_SECRET: c3VwZXJzZWNyZXQ=
---
# Mount as env var
env:
- name: DB_PASSWORD
  valueFrom:
    secretKeyRef:
      name: db-secret
      key: DB_PASSWORD


⚠ Secrets are base64, NOT encrypted. Anyone with kubectl access can decode them. In production use Sealed Secrets (Bitnami) or External Secrets Operator pulling from AWS Secrets Manager, Azure Key Vault, or HashiCorp Vault.









3 — Volume Mount (file-based config)




For Spring Boot, mount application.yml from a ConfigMap — Spring picks it up automatically from the working directory.


volumes:
- name: config
  configMap:
    name: app-config
    items:
    - key: application.yml
      path: application.yml

volumeMounts:
- name: config
  mountPath: /app/config
  readOnly: true
# Spring Boot finds /app/config/application.yml
# because it searches config/ subdirectory first









4 — Spring Boot Active Profile via K8s




# Set Spring profile from ConfigMap
env:
- name: SPRING_PROFILES_ACTIVE
  valueFrom:
    configMapKeyRef:
      name: app-config
      key: SPRING_PROFILES_ACTIVE
- name: SPRING_DATASOURCE_PASSWORD
  valueFrom:
    secretKeyRef:
      name: db-secret
      key: DB_PASSWORD


Spring Boot reads environment variables using relaxed binding: SPRING_DATASOURCE_URL maps to spring.datasource.url automatically. No code changes needed to move from local to K8s.
