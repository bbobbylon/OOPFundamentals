E2E Testing — Playwright & Cypress: What Unit Tests Can't Catch

The top tier of the test pyramid: driving a real browser through a real user flow against a real (or realistically mocked) backend. Unit and component tests already cover this hub's Angular Testing and Spring Boot Testing pages — this page is what happens one layer up, where the thing under test is the whole app wired together.

🎭 What does an E2E test actually verify, and why is it the tier everyone gets wrong first?

An end-to-end test opens a real browser, navigates to a real URL, and interacts with the page the exact way a user would — click a button by its visible role, type into a field, wait for a network call to resolve, assert something rendered. It's the only tier that can catch bugs living between the pieces unit tests mock away: a route guard that redirects wrong, a CORS header missing in prod config, a CSS change that hides the submit button behind a modal. The trade-off is cost — E2E tests are slow (seconds, not milliseconds), expensive to write, and the tier most prone to flakiness: a test that passes 98% of the time and fails the other 2% for reasons that have nothing to do with the code being wrong. Almost all flakiness traces back to one root cause: the test asserted before the browser was actually ready, because it used a fixed delay instead of waiting for a real condition.

  • Locate by role/test-id, never by CSS class — a class rename shouldn't break a test that never claimed to care about styling.
  • Auto-waiting is the whole point — Playwright/Cypress re-check a condition until it's true (or times out); a hardcoded sleep(2000) is either wastefully slow or a flaky bug waiting to happen.
  • Page Object Model keeps selectors in one place per page, so a UI refactor means editing one file, not every spec that touches that page.
  • Mock the network at the edge, not the code — page.route()/cy.intercept() intercept real HTTP calls, so the app under test never knows it's not talking to a real backend.

Playwright vs Cypress, in one line

Playwright drives real browser engines (Chromium/Firefox/WebKit) out-of-process via CDP-like protocols and supports multiple tabs/origins natively. Cypress runs inside the browser alongside your app (historically Chromium-family only, though WebKit/Firefox support has matured) — that in-browser position is why its API feels so synchronous, and why cross-origin/multi-tab scenarios needed workarounds for years.

Where this fits the pyramid

The spring-boot-testing-visualizer.html pyramid labels its top tier "E2E / Integration Tests" — this page is what actually goes there: a handful of critical happy-path flows (login, checkout, "create X"), not exhaustive coverage. Push everything that can live lower in the pyramid down to unit/component tests, which are orders of magnitude cheaper to run and debug.

CIAM angle

Login is the single highest-value E2E flow in an identity-heavy app: it's the one path that genuinely can't be faithfully unit-tested (real redirect, real token issuance/storage, real guard evaluation) and the one path where a silent regression locks out every user. A minimal E2E suite that only covers "log in as a normal user" and "log in as an admin and see the admin nav" already captures most of the ROI.

The problem

The test is right. The assertion is right. It fails one CI run in ten anyway.

The suite is "flaky" again — except this flakiness has nothing to do with waiting

A spec seeds five orders for a test user, then asserts expect(ordersTable.rows).toHaveCount(5). Run it alone — npx playwright test order.spec.ts — and it passes every single time, instantly. Push it to CI, where the pipeline runs --shard=2/4 across four parallel workers against the one Postgres container the pipeline spins up for the whole job, and it fails roughly one run in ten with a count of 6, 7, or 8. Nobody touched a fixed delay. getByRole is auto-waiting exactly like it should. The test is reading the DOM correctly — the DOM is correctly reflecting a database table that a completely different shard's test, committing at that exact moment, also just inserted a row into.

passes locally, every time ✓ no waitForTimeout anywhere in the spec ✓ 4 shards, 1 shared Postgres container ⚠ count assertion reads rows another shard just wrote ⚠

The wrong assumption underneath: that "fresh, seeded database" (true once, at pipeline start) means "isolated database, per test" — sharding parallelizes the browsers; nobody parallelized the data.

Give every test its own slice of data, not just its own browser
First move: scope every assertion to data THIS test created — count orders WHERE user_id = testUser.id, not the whole table ↓ a concurrent shard inserting unrelated rows can no longer move your number Better: one throwaway schema (or database) per shard, instead of one shared instance for the whole job ↓ parallel workers stop being able to see each other's writes at all, which is what "parallel" was supposed to mean The result: 4 shards run 4x faster AND stop being able to interfere with each other's data
Parallel workers and a shared database are two different kinds of "isolated" pretending to be one. Sharding genuinely gives every worker its own browser, its own process, its own test run — but if all four still point at the one Postgres container the pipeline spun up, the data underneath every one of those "isolated" tests is the same table, being written to by strangers, at the same time. It's the same shape of bug as a previous test's toast still fading over a button — leftover state colliding with this run — just one layer down, in the database instead of the DOM.
Think of CI sharding as four cashiers ringing up four different customers at four different registers, sharing one stockroom shelf in the back. Each register really is independent — separate line, separate customer, separate receipt. But if two cashiers both grab from the same shelf of "5 remaining blue shirts" at the same moment, neither sale waits for the other, and both cashiers walk away confident there are still shirts left. The registers were never the problem. The shelf was never split.

The mechanism

Four shards. One database. Zero coordination between them — by design, until you add it.

  1. CI starts one Postgres service container and seeds it once, before any shard begins"fresh" happens once per pipeline run, not once per test
  2. The pipeline launches 4 parallel workers, each running --shard=N/4 — separate processes, separate browsers, the same database connection stringthis line is what creates the sharing
  3. Shard 2's test inserts 5 rows for its own test user and asserts toHaveCount(5) against the whole tablecorrect, in isolation
  4. At nearly the same instant, Shard 3's completely unrelated test inserts 2 rows of its own into the same table, for a different test useralso correct, also in isolation
  5. Shard 2's SELECT count(*) FROM orders has no WHERE clause narrowing it to its own user — it counts every row that exists at that instant, from anyonethe actual defect
  6. The count lands on 5, 7, or somewhere else entirely, purely by scheduling luck — the test is flaky not because anything raced a clock, but because it raced other tests' datatiming-flaky and data-flaky look identical in a CI log

Step 5 is the lesson. Steps 1 through 4 are the pipeline working exactly as configured — a shared service container, four honest parallel workers, two tests that are each individually correct. The only line that's actually wrong is the query with no WHERE clause, silently counting the whole table instead of the slice this test owns. Fix step 5 alone and steps 1-4 stop mattering, because nothing about them was ever the bug.

Sharding drew four separate lanes for the browsers and never touched the table at the bottom — that was never sharding's job. Every one of those four specs is, individually, a well-written test. Put one unscoped count assertion in any of them and this diagram is the whole explanation for why it only fails when the other three lanes happen to be busy at the same moment.

You fix the flaky toHaveCount(5) assertion by scoping it to WHERE user_id = testUser.id instead of counting the whole table. Later, someone disables sharding entirely — the whole suite now runs sequentially, one worker, --shard=1/1 — reasoning that "there's no concurrency left, so the scoping fix doesn't matter anymore." Are they right to revert it?

Right — concurrency made this bug fail loudly and often, but it was never the actual cause. The cause is an assertion that counts rows it doesn't own. Any earlier spec file in the same sequential run that seeds an order and doesn't clean up leaves rows sitting in that same table, and the very next spec's unscoped count reads them too — just less often, and more confusingly, because now it depends on test order instead of shard timing.

This is the reasonable-sounding trap: "no parallelism" does feel like "no shared state." But every spec file in that one sequential run still shares the same database instance and the same tables across the whole run — order.spec.ts running before checkout.spec.ts and leaving rows behind reproduces the identical symptom, just triggered by test order instead of two shards landing on the same millisecond.

By the time this assertion runs, Playwright has already auto-waited for the DOM to reflect whatever the database actually contains — that part genuinely isn't racing anything. The bug isn't about WHEN the count becomes visible, it's about WHICH rows are in it. That's a scope problem, not a timing problem, which is exactly why the fixed-delay fix from earlier doesn't apply here.

Where you've seen this before

Many workers, one shared thing, nobody coordinating — the oldest bug shape in concurrent systems.

Your shared CIAM test tenant has the exact same disease

A throwaway Postgres container at least gets destroyed every pipeline run. A shared Entra ID or PingOne test tenant usually doesn't — it's one long-lived environment the whole team's local runs and every CI pipeline point at together. Two engineers' E2E suites both trying to register the same e2e-test-user@… email at the same moment collide exactly like the orders table did, except the fix is harder: you can't spin up a fresh throwaway IdP tenant per shard the way you can spin up a fresh database.

same disease, harder to reset

Two threads incrementing one counter — the original version of this bug

This is the same shape as the classic "two threads, one shared counter, no lock" race from every concurrency textbook: each thread reads the current value, computes current+1, and writes it back, and if both read before either writes, one increment is silently lost. Sharded Playwright workers aren't threads and Postgres isn't a bare int in memory, but the shape is identical — independent actors mutating one shared piece of state with nothing coordinating the order.

read-modify-write, no lock, shared state ⚠

Why Spring's @Transactional has an isolation level at all

Postgres's default READ_COMMITTED isolation is exactly why Shard 2's SELECT can see Shard 3's just-committed INSERT — that's not a Postgres bug, it's the whole point of READ_COMMITTED. A SERIALIZABLE transaction would prevent that phantom read, at the cost of throwing serialization failures under real contention instead. E2E tests don't reach for isolation levels, though — scoping every query to data the test actually owns is cheaper and doesn't need a database expert to tune.

READ_COMMITTED allows phantom reads by design
Questions from the back row

Why not just give every shard its own database instead of scoping every query?

That works too, and for a big suite it's often the better long-term fix — a throwaway schema (or a full ephemeral container) per shard makes cross-shard interference structurally impossible instead of relying on every author remembering to scope every assertion. The trade-off is setup cost: spinning up N database instances instead of one is more pipeline configuration, and it doesn't retroactively fix a spec someone runs locally against a shared dev database anyway. Scoping the query is the cheaper fix that also protects you outside CI.

How would I even notice this kind of flakiness, versus the fixed-delay kind?

Look at what changes between the passing run and the failing one. Timing-flakiness (the fixed-delay kind) correlates with load — it gets worse on a slow or busy runner and often clears up on an immediate rerun. Data-flakiness like this correlates with what ELSE was running at the same time — it gets worse with MORE parallel shards, not a slower one, and a trace replay will show the assertion reading a row count that includes data your test never created. The DOM was never wrong; the table was.

Does this affect the network-interception scenario too, since that mocks the backend entirely?

No, and that's worth noticing: a fully-mocked backend (page.route() returning canned JSON) has no shared database at all, so it can't have this exact bug — each test's mock is scoped to that test by construction. This is specifically a hazard of the CI scenario's other approach — a real, shared, ephemeral backend — which is the trade-off you take on for testing against something real instead of a fake.

1. Playwright vs Cypress, side by side

AxisPlaywrightCypress
ArchitectureOut-of-process, drives real browser engines via a devtools-protocol-style bridgeRuns inside the browser, in the same run-loop as your app
BrowsersChromium, Firefox, WebKit — one API, three enginesChromium-family primary; Firefox/WebKit support exists but is newer
Multi-tab / multi-originNative — context.newPage(), cross-origin navigation just worksHistorically required workarounds; has improved but is still Cypress's rougher edge
ParallelismBuilt-in test sharding, no paid add-on requiredFree parallelization requires the Cypress Cloud dashboard (paid at scale)
Debugging--trace on records a full timeline (DOM snapshots, network, console) replayable in the Trace ViewerTime-travel debugger in the interactive Test Runner UI — arguably the friendlier live-debugging experience
Neither is strictly "better" — Playwright's out-of-process model wins on true cross-browser + multi-origin coverage and free CI parallelism; Cypress's in-browser model wins on the interactive debugging feel while you're first writing a test. Both auto-wait, both intercept network calls, both support a Page Object Model — the concepts on this page transfer directly between them.

2. Locate by role/test-id — Page Object Model keeps it in one place

✗ Brittle — CSS-class selector, inline in the spec

// breaks the instant a designer renames a class
await page.click('.btn.btn-primary.submit-v2');
await page.fill('#email-input-field', 'a@b.com');
// this selector says nothing about WHY it's being clicked

✓ Resilient — role/test-id, behind a Page Object

// login.page.ts — one file owns every selector for this page
export class LoginPage {
  constructor(private page: Page) {}  // wraps the one Playwright Page handle the spec already has
  emailInput = this.page.getByTestId('login-email');  // stable hook, survives a redesign
  submitBtn  = this.page.getByRole('button', { name: 'Sign in' });  // found the way a screen reader finds it
  async loginAs(email: string) {  // the ONE method every spec calls to log in
    await this.emailInput.fill(email);  // types into the field located above
    await this.submitBtn.click();  // submits — a redesign only ever touches this file
  }
}
A CSS class is a styling concern, not an identity contract — getByTestId/getByRole selectors survive a full redesign because they describe what the element is for, not how it currently looks. The Page Object Model is the same idea applied at the file level: every spec that logs in calls loginPage.loginAs(email), so a login-page redesign means editing login.page.ts once, not every spec file that happens to log in first.

3. Auto-waiting vs. fixed delays — the #1 cause of flaky tests

✗ Flaky — a fixed delay guesses how long is "enough"

await page.click('#save-btn');
await page.waitForTimeout(2000); // hope 2s is enough
const toast = await page.textContent('.toast');
// fails ~2% of the time under CI load, when the API takes 2.3s
// OR wastes 1.9s of real time when it resolves in 100ms

✓ Stable — assert on the condition itself

await page.click('#save-btn');
await expect(page.getByRole('status')).toHaveText('Saved!');
// Playwright retries this assertion internally until it passes
// or the timeout elapses — takes exactly as long as it needs to
waitForTimeout/cy.wait(2000) is a code smell, not a tool — it's either too short (flaky under real-world CI load, where a shared runner is slower than your laptop) or too long (a fast test suite becomes a slow one, multiplied by every spec that does it). expect(...).toHaveText(...) and cy.get(...).should(...) both poll-and-retry against the real DOM until the assertion is true or a timeout is hit — they're the auto-waiting mechanism working for you instead of you guessing against it.

4. One-sentence recap

🎭 E2E tests are the only tier that verifies the whole app wired together the way a user actually experiences it — worth the cost only for a handful of critical flows, kept fast and stable by locating elements through role/test-id behind a Page Object, asserting on real conditions instead of fixed delays, and mocking the network at the HTTP boundary instead of the application code.
