SOLID — Five Principles That Make Code Last

Coined by Robert C. Martin. They aren't laws — they're heuristics that keep codebases changeable as they grow. Each tab shows the principle, broken code, the fix, and where you'll see it.

📐 What are the SOLID principles — and do you actually need to follow them?

SOLID is five OO design heuristics that make code easier to maintain and extend — not laws; over-applying them over-engineers. Single Responsibility (one reason to change), Open/Closed (extend without modifying), Liskov Substitution (subtypes honor the supertype's contract), Interface Segregation (small, focused interfaces), and Dependency Inversion (depend on abstractions, not concretions). Spring's dependency injection is literally DIP in action.

  • S — one reason to change per class.
  • O — extend, don't modify existing code (interfaces + polymorphism).
  • L — subtypes must substitute without breaking the supertype's contract.
  • I & D — small interfaces; depend on abstractions — every @Autowired is DIP.

SRP and OCP in Spring

SRP violation: a UserService that creates users, sends emails, generates reports, AND validates JWTs — four reasons to change. Fix: UserService (create/update/delete), EmailService (notifications), ReportService (reports), JwtService (token handling). Each class has one reason to change. OCP in action: adding a new IDP (Keycloak) shouldn't require modifying AuthService. Instead: AuthService depends on AuthStrategy interface. Add KeycloakStrategy implements AuthStrategy. Register it. AuthService unchanged — it's closed for modification but open for extension.

LSP and ISP

LSP violation: Square extends Rectangle. Rectangle has setWidth(w) and setHeight(h) independently. Square overrides both to set both dimensions (a square's sides are equal). Code that calls rect.setWidth(5); rect.setHeight(10) expects area 50 — gets 100 with a Square. The subclass broke the superclass's contract. Fix: use composition, not inheritance. ISP violation: a fat interface UserManager { createUser(); deleteUser(); generateReport(); sendEmail(); }. ReportingModule implements UserManager but only needs generateReport() — forced to implement empty stubs. Fix: split into UserCrud, UserReporting, UserNotification.

DIP is Spring's core

Without DIP: class UserService { UserRepository repo = new JpaUserRepository(); } — tightly coupled to JPA. Can't test without a real DB. Can't swap to a different storage. With DIP: class UserService { final UserRepository repo; UserService(UserRepository r) { this.repo=r; } } — depends on the interface. Spring injects JpaUserRepository at runtime. Test with a @MockBean. Swap to MongoUserRepository without changing UserService. Every @Autowired in Spring is DIP in action. The DIP is why Spring Boot is so testable: every dependency is injectable.

CIAM / Spring Boot: SRP splits JwtService/ClaimsMapper/UserService by reason-to-change; OCP adds a new permission check via a fresh annotation + aspect, not edits to existing @PreAuthorize; LSP means every IdpAuthStrategy (Ping/Entra/Keycloak) returns a UserPrincipal and never throws on a valid token; ISP splits UserReader vs UserWriter; and DIP lets UserService swap H2→Postgres by config with zero code changes.

S — Single Responsibility

A class should have one, and only one, reason to change.

If marketing changes the email template, the finance code shouldn't risk breaking. Group code by who needs to change it together — not by what's convenient to type.

❌ Bad — one class doing everything

class Invoice {
    private List<Item> items;

    public BigDecimal total() { ... }       // 💰 business rules

    public void saveToDb(Connection c) { ... }  // 🗄️ persistence

    public String renderHtml() { ... }      // 🎨 presentation

    public void emailTo(String addr) { ... } // 📧 delivery
}

✅ Good — one role per class

class Invoice {                // just the data + business rules
    private List<Item> items;
    public BigDecimal total() { ... }
}

class InvoiceRepository { void save(Invoice i) { ... } }

class InvoiceRenderer   { String renderHtml(Invoice i) { ... } }

class InvoiceMailer     { void email(Invoice i, String to) { ... } }
Smell: a class with "and" in its job description — "User and notification and permissions." Or a file 800+ lines long that you keep scrolling around in.
Fix: ask "if X changes, do I touch this class?" Make a list of X's. If it has more than one, split.

O — Open / Closed

Open for extension, closed for modification. Add new behavior by adding new code, not editing existing code.

Every switch on a type is a code-smell. Every time you add a new case, you risk breaking the existing ones. Use polymorphism to make new types extend the system from outside.

❌ Bad — switch on type

double area(Shape s) {
    switch (s.kind) {
        case CIRCLE:    return Math.PI * s.r * s.r;
        case RECTANGLE: return s.w * s.h;
        case TRIANGLE:  return s.b * s.h / 2;
    }
    throw new IllegalArgumentException();
}
// Adding HEXAGON requires editing this method.
// Forget a case? Silent bug in production.

✅ Good — each shape owns its formula

interface Shape { double area(); }

class Circle    implements Shape { public double area() { ... } }
class Rectangle implements Shape { public double area() { ... } }

// To add Hexagon — write a NEW class. Touch zero existing code.
class Hexagon implements Shape { public double area() { ... } }
Smell: long if/else chains or switches on type, instanceof ladders, "case X" sprinkled across multiple files for the same enum.
Fix: introduce an interface; let each variant implement its own version. Or use the Strategy pattern.

L — Liskov Substitution

Subtypes must be usable wherever their parent type is expected — without surprises.

If S extends T, code written for T should still work when given an S. If a subclass throws when the parent doesn't, or weakens the contract, it's not really an "is-a".

❌ Bad — Square breaks Rectangle's contract

class Rectangle {
    public void setWidth(int w)  { this.w = w; }
    public void setHeight(int h) { this.h = h; }
}

class Square extends Rectangle {  // "a square IS-A rectangle, right?"
    public void setWidth(int w)  { this.w = w; this.h = w; }
    public void setHeight(int h) { this.w = h; this.h = h; }
}

// Tests written against Rectangle break when handed a Square:
r.setWidth(5); r.setHeight(10);
assert r.area() == 50;   // fails — Square made it 100!

✅ Good — model the difference honestly

interface Shape { int area(); }

class Rectangle implements Shape {
    private final int w, h;
    // no setters — immutable; can't be subverted
}

class Square implements Shape {  // sibling, not child
    private final int side;
    public int area() { return side * side; }
}
Smell: overrides that throw UnsupportedOperationException, instanceof checks before using a "subtype", subclasses that disable parent behavior.
Fix: if a subtype can't honor the parent's contract, it's not really an "is-a". Use composition or sibling types instead of inheritance.

I — Interface Segregation

No client should be forced to depend on methods it doesn't use.

One fat interface forces every implementer to deal with every method. Break it into smaller role-based interfaces so each implementer says yes only to what it actually does.

❌ Bad — the kitchen-sink interface

interface Worker {
    void work();
    void eat();
    void sleep();
}

class RobotWorker implements Worker {
    public void work()  { ... }
    public void eat()   { throw new UnsupportedOperationException(); }
    public void sleep() { throw new UnsupportedOperationException(); }
}

✅ Good — small, role-based interfaces

interface Workable  { void work(); }
interface Eater     { void eat();     }
interface Sleeper   { void sleep();   }

class RobotWorker implements Workable { ... }
class HumanWorker implements Workable, Eater, Sleeper { ... }

// Code that runs work() doesn't care if the worker also eats.
Smell: implementations stubbing methods with empty bodies, returning null, or throwing UnsupportedOperationException.
Fix: split the interface along usage lines. Look at the standard library: Comparable, Comparator, Iterable, Iterator, Closeable — each is small and focused.

D — Dependency Inversion

Depend on abstractions, not concretions. High-level modules shouldn't reach down into low-level ones.

A service that news its own database client is welded to that database forever. Inject the dependency through the constructor (or DI container) and depend on an interface instead. Now you can swap Postgres for Mongo, or a fake for tests, without changing the service.

❌ Bad — wired directly to MySQL

class OrderService {
    private final MySQLDatabase db = new MySQLDatabase();

    public void place(Order o) {
        db.runMySqlInsert("INSERT INTO orders ...");
    }
}
// Switching to Postgres? Touch this class.
// Unit tests? Spin up a real MySQL. Slow, brittle.

✅ Good — depend on an interface

interface OrderRepository { void save(Order o); }

class OrderService {
    private final OrderRepository repo;   // any impl

    public OrderService(OrderRepository repo) { this.repo = repo; }

    public void place(Order o) { repo.save(o); }
}

// Spring/Guice wires up MySqlOrderRepository in prod,
// InMemoryOrderRepository in tests, MongoOrderRepository tomorrow.
Smell: business logic doing new SomeDatabase() or new HttpClient(), hardcoded paths and URLs, tests that need real infrastructure to run.
Fix: constructor injection. Pass dependencies in. The class shouldn't know how to build its collaborators — only how to use them.

▶ D — Dependency Injection in action

The same OrderService, two environments. In prod Spring wires the real database; in tests you pass a fake. The service code doesn't change. Watch how the dependency flows in.

Putting it all together

SOLID isn't a checklist to chase. It's a way of recognizing when code is becoming hard to change. Codebases drift toward chaos by default; SOLID is the constant pressure pushing back. Apply it when you feel friction — not preemptively, not absolutely.

SRP

"This class has one reason to change."

OCP

"I can add a new variant without editing existing code."

LSP

"Subtypes don't surprise their parent's callers."

ISP

"No client implements methods it doesn't use."

DIP

"Code depends on interfaces; concretions are wired in from outside."
