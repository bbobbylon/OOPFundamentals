Python Exceptions & Error Handling

When something goes wrong, Python raises an exception — an object that travels up the call stack until a matching except catches it, or it reaches the top and prints a traceback. This page walks the four-part try / except / else / finally block, how exceptions propagate, custom exception hierarchies, and the Pythonic EAFP style ("easier to ask forgiveness than permission"). What are Python exceptions — and what is EAFP vs LBYL?

In Python, errors are represented as exceptions — objects that inherit from BaseException. When something goes wrong (KeyError, ValueError, HTTPError, etc.), Python raises an exception object that travels UP the call stack until it finds a matching except clause — or reaches the top and prints a traceback. The four-part try block: try (the protected block), except ExcType as e (catches specific exceptions), else (runs if NO exception was raised — often misunderstood), finally (ALWAYS runs, for cleanup). The else clause is rare but powerful: it separates "this is the happy path" code from the error handlers. Exception hierarchy: all exceptions inherit from BaseException. Exception is the base for most user-facing errors. Best practice: catch the most specific exception possible, not bare except: or except Exception:. Custom exceptions: create exception hierarchies for your domain. class CiamError(Exception): pass; class UserNotFoundError(CiamError): pass. Now callers can catch CiamError (broad) or UserNotFoundError (specific). EAFP vs LBYL: Python strongly prefers EAFP ("Easier to Ask Forgiveness than Permission") over LBYL ("Look Before You Leap"). LBYL: check first, then do. EAFP: just do it, handle errors if they arise. LBYL has race conditions (state can change between check and use) and is verbose. EAFP is faster (one operation) and idiomatic Python. try: return d[key]; except KeyError: return default vs if key in d: return d[key]; return default.

async def fetch_user(user_id: int) -> UserDto: try: # Protected block: may raise response = await client.get(f'/users/{user_id}') response.raise_for_status() # raises on 4xx/5xx data = response.json() except httpx.HTTPStatusError as e: if e.response.status_code == 404: raise UserNotFoundError(user_id) from e raise # re-raise other HTTP errors except httpx.RequestError as e: raise NetworkError(f'Connection failed: {e}') from e else: # Only runs if NO exception: post-success logic log_audit('USER_FETCHED', user_id=user_id) return UserDto(**data) finally: # ALWAYS runs: cleanup metrics.increment('api.user.fetch.attempts')

EAFP vs LBYL + Java comparison

# LBYL (Look Before You Leap): if 'email' in user_dict: # check first email = user_dict['email'] # then use # Problem: verbose, possible race conditions # EAFP (Easier to Ask Forgiveness): try: email = user_dict['email'] except KeyError: email = None # Idiomatic Python. Often use .get() shortcut: email = user_dict.get('email') # None if missing # Java comparison: # Java: checked exceptions (must declare or catch) # void foo() throws IOException { } # Python: unchecked exceptions (can catch or not) # def foo(): raise ValueError('...') ← no declaration # Spring @ControllerAdvice = centralized exception handler # FastAPI equivalent: # @app.exception_handler(UserNotFoundError) # async def handle(req, exc): return JSONResponse(404, ...)

In a CIAM Python context: Global exception handler in FastAPI (≈ Spring's @ControllerAdvice): @app.exception_handler(UserNotFoundError) async def user_not_found(req, exc): return JSONResponse(status_code=404, content={"error": str(exc), "type": "USER_NOT_FOUND"}). Exception chaining for clear error trails: raise IdpSyncError('PING', f'Failed to create user') from original_exception — the from clause attaches the original cause, visible in tracebacks. Context manager for transactions: async with db.transaction(): await create_user(req) — if any exception is raised inside the async with block, the transaction rolls back (the __aexit__ dunder handles it). This is exactly Spring Boot's @Transactional — any RuntimeException triggers a rollback.

1. The four blocks — and exactly when each runs

try:
    data = load(path)          # the risky code
except FileNotFoundError as e:
    log(e); data = {}          # runs ONLY if that error fired
except (ValueError, KeyError):
    raise                      # catch several; re-raise
else:
    print("loaded OK")         # runs ONLY if try had NO error
finally:
    cleanup()                  # ALWAYS runs — error or not

Catch narrow, not bare

# ❌ swallows EVERYTHING, even bugs
try: risky()
except: pass

# ✅ name the exceptions you expect
except (TimeoutError, ConnectionError) as e:
    retry()

Chaining — keep the cause

try:
    parse(raw)
except ValueError as e:
    raise ConfigError("bad config") from e
# traceback shows BOTH: "direct cause"
Brain Power. Why have else when you could put "loaded OK" at the end of try? Because code in try is protected — if print("loaded OK") itself raised, the except above could catch it by accident. else runs only when try succeeded, and is not protected by these handlers. Precision.

2. The exception hierarchy — catch by base class

BaseException ├─ SystemExit, KeyboardInterrupt ← don't catch these by accident └─ Exception ← catch THIS, never BaseException ├─ ArithmeticError → ZeroDivisionError ├─ LookupError → KeyError, IndexError ├─ OSError → FileNotFoundError, PermissionError, TimeoutError ├─ ValueError, TypeError, AttributeError └─ YourAppError → NotFoundError, ValidationError ← your own subtree

Catching a base class catches all its subclasses. except LookupError handles both KeyError and IndexError. This is why a custom hierarchy is powerful: callers can catch your AppError base and handle every error your library raises.

EAFP (scenario ④) is the Pythonic default: just do the thing and handle the exception if it fails — try: d[k] except KeyError — instead of LBYL ("look before you leap": if k in d: d[k]). EAFP avoids the race where the key disappears between the check and the use, and it's usually faster on the happy path because there's no pre-check.
