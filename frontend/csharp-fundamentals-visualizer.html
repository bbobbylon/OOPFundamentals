C# Fundamentals for a Java Developer

C# and Java are siblings — managed runtime, GC, classes, generics, interfaces. This page focuses on what is genuinely different: value vs reference types, properties, records, LINQ, and pattern matching — the things that trip up a Java developer reading C#.

🟣 What is C# — and what does a Java developer actually need to relearn?

C# runs on .NET (the CLR — a managed runtime with JIT and a garbage collector, like the JVM) and is, at the syntax level, the language closest to Java. If you know Java you can read most C# immediately. The differences that matter: C# has true value types — a struct is copied by value and can live on the stack, unlike Java where everything except primitives is a heap reference. C# replaces getter/setter boilerplate with properties (public string Name { get; set; }). It has records for concise immutable data with value equality (Java got these later). LINQ is a built-in, composable query language over any collection — users.Where(u => u.Age > 18).Select(u => u.Name) — with deferred execution, and over a database it translates to SQL. And C# leans hard on pattern matching and switch expressions. Add nullable reference types, async/await as a first-class language feature, and you have the toolkit. The ecosystem — ASP.NET Core, Entity Framework — maps almost one-to-one onto Spring Boot and JPA.

  • Value vs reference types — struct copies; class references. Java has no struct.
  • Properties replace getters/setters; init and record give immutability + value equality.
  • LINQ — composable, deferred queries over collections and databases (→ SQL).
  • Pattern matching + switch expressions are everyday tools, not an afterthought.

Java comparison

C# struct = value type (no Java equivalent — Java is adding them as "value classes" via Valhalla). C# properties = Java getters/setters but built into the language. C# record ≈ Java record (C# had it first, and adds with expressions). C# LINQ ≈ Java Streams (.Where≈.filter, .Select≈.map, .ToList()≈.collect()) — but LINQ also runs against databases via Entity Framework. C# async/await ≈ Java's CompletableFuture/virtual threads but as language syntax. C# namespaces ≈ Java packages; PascalCase methods are the C# convention.

CIAM .NET service: A Java/Spring developer dropped into a .NET CIAM service will recognize everything: DTOs become records (immutable, value-equal — ideal for token claims), claim filtering is LINQ over ClaimsPrincipal.Claims, and authorization checks read naturally as pattern-matching switch expressions over a role enum. The mental shift is small; the productivity transfer is large.

2. Why value vs reference matters

// struct = value type → copied on assignment
struct Point { public int X, Y; }
Point p1 = new() { X = 1 };
Point p2 = p1; // COPY — independent
p2.X = 99; // p1.X is still 1

// class = reference type → shared
class Person { public string Name; }
Person a = new();
Person b = a; // same object
b.Name = "X"; // a.Name is now "X" too
This is the #1 surprise for Java developers. In Java, every object is a reference. In C#, a struct is a value — assigning it copies the whole thing, and passing it to a method copies it (unless ref). Use structs for small, immutable, frequently-allocated data (points, money) to avoid GC pressure; use classes for everything with identity.

3. LINQ is deferred

var query = users.Where(u => u.Age > 18); // nothing runs yet!
users.Add(new User { Age = 25 }); // added before execution
var list = query.ToList(); // executes NOW, includes the new user

Where/Select/OrderBy build a query object; iteration (ToList, foreach, Count) runs it. Over Entity Framework, the whole chain becomes a single SQL statement — the filtering happens in the database, not in memory.
