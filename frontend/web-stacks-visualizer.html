Full-Stack Web Stacks Compared

Every track in this hub is a layer; a stack is a specific combination of them. This page traces one request through the four shapes you'll actually meet: a SPA + REST API (Angular + Spring — the CIAM stack), MERN (JS top-to-bottom), a server-rendered monolith (Rails / Laravel), and a compiled API + SPA (Go / Rust). Once you've picked a stack, see From git push to Production for how it actually gets deployed.

🏗️ What is a "stack" — and how do the pieces fit together?

A full-stack application is the whole vertical slice: the code in the browser, the network protocol between, the server that handles requests, and the database that stores state — plus, increasingly, an identity provider for auth. A "stack" is just a named, conventional combination of those layers. The big architectural fork is where the HTML is built. In a SPA + API stack (React/Angular talking to a JSON API), the browser downloads a JavaScript app once, and from then on the client renders the UI and the server only ships data (JSON) — usually authenticated with a bearer JWT. This is the dominant shape for app-like products and is exactly the Angular + Spring Boot + OIDC stack used in CIAM work. MERN (MongoDB, Express, React, Node) is that same SPA + API shape but with JavaScript/TypeScript at every layer — one language, one mental model. A server-rendered monolith (Rails, Laravel, Django) takes the older, still-excellent path: the server queries the database and renders complete HTML per request, with libraries like Hotwire/Livewire sprinkling interactivity on top — fewer moving parts, no API to design. A compiled API + SPA swaps the backend for a Go or Rust service (Gin/Axum) when you need raw throughput, low latency, or memory safety on the hot path. Underneath every stack the request path rhymes: client → (frontend) → network → backend → data → back. Learning the layers once lets you read any stack.

  • The fork that matters — does the server render HTML (monolith) or does the client render and the server ship JSON (SPA + API)?
  • SPA + API — Angular/React ↔ JSON/JWT ↔ Spring/Express/Go/Rust; the modern app default.
  • Monolith — Rails/Laravel/Django render HTML server-side; fewer parts, no API contract.
  • Same skeleton — client → frontend → network → backend → database → response, every time.

How this maps to the other tracks

Each layer has its own track: 🅰️ Angular / ⚛️ React (frontend), 🍃 Spring · 🟢 Node · 🟣 C# · 🐿️ Go · 🐘 PHP · 💎 Ruby · 🦀 Rust (backend), 🗄️ SQL (data), 🔐 Identity (auth), 🛠️ Docker / ⎈ Kubernetes (deploy). A stack is a path through them — this page is the map; the tracks are the territory.

The CIAM stack in focus: a customer identity app is the canonical SPA + API stack — an Angular SPA served from a CDN, login delegated to an OIDC provider (Entra External ID / Ping) via Authorization Code + PKCE, and every API call to Spring Boot carrying a bearer JWT that the Spring Security filter chain validates against the provider's JWKS before any controller runs. The frontend guards are UX; the Spring @PreAuthorize checks are the real gate. The data layer (Postgres) never trusts the client. Knowing the whole path — who renders, where the token is verified, which layer is authoritative — is what lets you debug a 401 vs a 403 vs a CORS failure in seconds.

The problem

Ditching cookies for a bearer JWT really does kill CSRF. It also means your token is one XSS bug away from sitting in an attacker's browser tab.

Your "CSRF-immune" token is one localStorage.getItem() away from an attacker

Following the CodeWalk above, your Angular interceptor reads a JWT and attaches it as Authorization: Bearer ${token}. To survive a page refresh, token has to come from somewhere — the standard, extremely common pattern is localStorage.setItem('access_token', token) right after login, then localStorage.getItem('access_token') inside the interceptor. The page's claim above is completely correct: a forged cross-site form or <img> tag cannot set a custom Authorization header, so classic CSRF genuinely cannot steal or replay this token.

But localStorage has no origin-internal access control. Every script running on your page — including a malicious one — can read it with one line: localStorage.getItem('access_token'). A vulnerable npm dependency, an unsanitized comment field rendered without escaping, a compromised third-party analytics snippet — any single XSS foothold reads the token directly and ships it to an attacker's server with a plain fetch() call. An HttpOnly cookie holding a session id is invisible to JavaScript entirely, even to a successful XSS payload; localStorage has no equivalent protection at all.

You didn't remove a vulnerability by switching from cookies to bearer tokens — you traded CSRF for XSS-based token theft, and XSS is usually the easier bug to find.

Stop letting JavaScript-readable storage hold the raw token
Never persist the raw token in localStorage or sessionStorage if you can avoid it ↓ both are just JS-readable key/value stores with zero built-in protection against script access — exactly the surface an XSS payload targets first Keep the access token in memory only, and re-authenticate silently on reload ↓ a variable inside an Angular service (never persisted) disappears on refresh; pair it with a silent OIDC re-authentication so the user doesn't have to log in again, without ever writing the token to disk Or move to the Backend-for-Frontend pattern entirely ↓ the browser never sees the raw JWT at all — your own backend holds it server-side and issues an HttpOnly, Secure, SameSite cookie instead, so even a successful XSS payload has nothing to steal
The one-sentence rule. "Bearer token, not a cookie" answers the CSRF question, not the security question — anywhere your own JavaScript can read the token to attach it, any other JavaScript that ends up running on your page can read it too.
A key you keep in your own pocket instead of leaving in the mailbox is safe from the mailman — it's not safe from someone who's already inside your house.

The mechanism

Follow one XSS payload as it walks straight past every CSRF defense you just built.

  1. An unsanitized comment field renders a <script> tag verbatim on your page — the classic stored-XSS entry pointxss injected
  2. That script runs with the exact same JS privileges as your Angular app — same origin, same DOM, same storagesame origin
  3. It calls localStorage.getItem('access_token') — one line, no special permission neededtoken read
  4. The script POSTs that value to an attacker-controlled endpoint over a normal fetch() callexfiltrated
  5. The attacker now holds a valid, unexpired bearer token and can call your API as you, from anywhereimpersonation
  6. None of this touched a cookie, a form, or cross-site request forgery at any point — CSRF defenses were never even in the picturecsrf irrelevant

Step 3 is the whole trap. Your interceptor, your Authorization header, your Spring filter chain — every piece from the CodeWalk above works exactly as designed. The attacker didn't break any of it; they just read the token off the shelf before your own code ever got to use it.

SameSite and CSRF tokens are the right tool for a cookie-based session — they have nothing to say about a value sitting in localStorage. The only real defense against this attack is keeping the token somewhere a script can't casually reach, or not letting the browser hold the raw token at all.

Where you have seen this before

"Fixing one attack surface can open a different one" is a lesson worth hearing from more than one direction.

OWASP and the OAuth-for-browsers guidance say the same thing

Industry guidance for OAuth 2.0 in browser-based apps explicitly recommends against persisting tokens in localStorage and instead recommends the Backend-for-Frontend pattern — the browser gets an HttpOnly session cookie, and the actual access token never leaves the server. The fix above isn't a personal opinion; it's the standard answer the identity industry has already converged on.

the same lesson, as a published standard

Angular's own sanitizer is the safety net you have to defeat first

Angular auto-escapes interpolated bindings ({{ userComment }}) by default — this class of vulnerability usually requires a developer to explicitly bypass that protection, most often via an [innerHTML] binding fed unsanitized content, or bypassSecurityTrustHtml(). The same framework holding your token in a service is also the one whose guardrail has to be actively defeated to open the door in the first place.

the framework you already use, both the risk and the guardrail

Third-party script tags are functionally identical to an XSS payload

Any third-party <script> loaded onto your page — an analytics SDK, an ad script, a chat widget — executes with the exact same origin privileges as your own app code, with no sandboxing by default. A compromised or malicious third-party script can read localStorage just as easily as an injected payload can. Adding a customer-facing SDK to a CIAM app is adding code with full read access to anything your app stored there.

the same gap, opened by a vendor instead of an attacker

Everything else is a variation on these two. MERN is SPA + API with one language (JS). A "compiled API + SPA" is SPA + API with a Go/Rust backend for throughput. Next.js/SSR blurs the line by rendering on the server and hydrating on the client. Pick the row that matches your team and product, not the trendiest logo.

2. The skeleton is always the same

// every stack, abstracted
CLIENT (browser)
  → FRONTEND // SPA in the browser, OR server-side templates
  → [ AUTH ] // verify a token / session (who are you?)
  → BACKEND // routing → controller → service/business logic
  → DATA // SQL or NoSQL query
  ◄ RESPONSE // JSON (SPA) or HTML (monolith), back up the chain

Learn this skeleton once and every framework slots in: Spring's filter chain, Express middleware, Rails' Rack stack, Laravel's kernel, Axum's tower layers are all the same position in the path. The differences are language, where rendering happens, and how auth is carried.
