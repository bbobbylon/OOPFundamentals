Narrowing — Control-Flow Analysis Internals

The Narrowing page walks the happy path. This companion shows the machinery underneath — the flow graph, aliased guards, and the spots where a narrowing you "earned" gets quietly thrown away: across closures and after a function call touches a property.

🔬 What is control-flow analysis (CFA) — and why do some narrowings disappear across calls?

TypeScript runs control-flow analysis (CFA) — it builds a flow graph of your code and tracks what's provably true at each point. if (typeof x === 'string') narrows x to string inside the block; an early return/throw marks the rest unreachable. That's narrowing. The gotcha is invalidation: a function call (or a deferred closure like setTimeout) could have changed a mutable variable, so TypeScript forgets the narrowing of a let across that boundary. Capture the value in a const first to keep it.

  • CFA tracks what's true per branch — typeof/null checks narrow the type.
  • Early return/throw prunes unreachable paths.
  • Aliased guards work (TS 4.4+) — const ok = typeof x === 'string'; if (ok) ….
  • Calls & closures invalidate let narrowing — copy to a const to preserve it.

Narrowing is a fact about a place in the code, not about a variable. The compiler holds it only as long as it can prove nothing invalidated it — and a callback runs later, where that proof no longer holds.

The mechanism

Every branch is a fork in what the compiler knows.

  1. let x: string | number | null3 possibilities
  2. if (x === null) return; — the early return removes onestring | number
  3. if (typeof x === "string") — inside, one remainsstring
  4. the else gets the complement, not "the rest of the union"number
  5. a function call, a reassignment, or a closure boundary RESETS itback to 3

Step 4 is the part worth internalising: the else branch is narrowed too, automatically, which is what makes an exhaustive switch work. Step 5 is why the same expression can be an error one line after it was fine.

The most useful narrowing tool is a discriminated union, because it needs no runtime cleverness at all. Give every member a shared literal field — { kind: "ok", data: T } | { kind: "err", error: E } — and switch (r.kind) narrows each branch exactly. Add const _never: never = r in the default and the compiler will refuse to build the day someone adds a third variant without handling it. That is exhaustiveness checking, and it is three words of code.

Right. A const cannot be reassigned, so the narrowing the guard established is still provable inside the closure. No assertion, and the compiler is doing real work rather than being told to look away.

This works and it is honest, but it is a runtime check for a situation the type system can settle at compile time — and it forces you to invent something to do in a branch that should be impossible.

Questions from the back row

Why does narrowing vanish after I call a function?

Because the compiler cannot see what that function did. If the narrowed thing is a mutable property like this.user, any call might have reassigned it, so the assumption is dropped. Local consts survive; object properties and lets do not. Copying to a local before the call is the standard fix, and it is not a workaround — it is you telling the truth about what is immutable.

Is as ever safe?

as and ! both mean "stop checking, I promise". They are appropriate at a boundary you genuinely know more about than the compiler does — a parsed JSON payload you have just validated, a DOM query you control. They are not appropriate as a way to make an error message go away, which is where most of them come from. A type predicate is the honest version of the same intent.

What is never actually for?

It is the empty type — no value has it — so it means "this cannot happen". That makes it the perfect exhaustiveness tool: if narrowing has eliminated every case, the remainder is never, and assigning a non-never to it is a compile error naming the case you forgot. Seeing never in an error is usually good news badly phrased.

1. The flow graph mental model

TS builds a control-flow graph of your function. At each node, every variable has a flow type — the narrowest type still possible given the path taken to get there. "Narrowing" is just reading that flow type; an if splits the graph and each branch carries a different flow type.

function f(x: string | number | null) {
  // node A — flow type: string | number | null
  if (x == null) return;
  // node B — flow type: string | number   (null path left the graph)
  if (typeof x === "string") {
    // node C — flow type: string
  } else {
    // node D — flow type: number
  }
}

2. Aliased guards — narrowing through a const

✅ Store the check in a const

Since TS 4.4, a guard saved in a const still narrows where it's used — the compiler tracks that the const is that condition.

function f(x: string | number) {
  const isStr = typeof x === "string";
  if (isStr) {
    x.toUpperCase();  // ✅ x: string
  }
}

❌ …but only with const

A let could be reassigned between the check and the use, so the link is dropped. Same for a discriminant copied into a let.

function f(x: string | number) {
  let isStr = typeof x === "string";
  if (isStr) {
    x.toUpperCase();  // ❌ x is still string | number
  }
}

4. The other re-widener: a call between guard and use

    

      
Narrowing a property access (obj.x) is fragile: any function call in between could have reassigned that property, so TS resets it to the declared type. (Narrowing of a plain local variable is not reset by a call — only by reassigning the variable itself.)

      
type Box = { val: string | null };

function use(b: Box) {
  if (b.val !== null) {
    // here b.val: string
    doStuff();          // 💥 could have set b.val = null
    b.val.toUpperCase();  // ❌ Object is possibly 'null'
  }
}

// ✅ pin it in a local — locals aren't reset by calls
function use2(b: Box) {
  const v = b.val;
  if (v !== null) {
    doStuff();
    v.toUpperCase();    // ✅ v is string, immune to the call
  }
}

      
This is why "copy to a const first" is the universal fix for both the closure case and the property case.

    

  


  
  

    
5. Discriminants & assertion flow

    

      

        
Discriminant must be a stable reference

        
Switching on shape.kind narrows shape only while it's read as the same reference. Destructure the tag into a const and the link to the object's other fields is lost.

        
function area(s: Shape) {
  const { kind } = s;     // kind copied out…
  if (kind === "circle")
    s.radius;             // ❌ s not narrowed — narrow on s.kind instead
}

      

      

        
Assertions cut the graph

        
A call to an asserts function narrows for the rest of the scope (it either threw or the fact holds). A function returning never marks code after it unreachable.

        
function f(x: unknown) {
  assert(typeof x === "string");
  x.toUpperCase();   // ✅ x: string from here down
}

        
Assertion signatures only work on function declarations — not arrow consts (the flow effect isn't carried).

7. One-sentence recap

    

      
Narrowing is the flow type a variable carries at each node of the control-flow graph; it survives in straight-line code (and through a const-aliased guard), but the compiler conservatively re-widens when a value could have changed out from under it — a let captured in a callback, or a obj.x property read after any function call — and the one fix for both is to copy the value into a local const before you rely on it.
