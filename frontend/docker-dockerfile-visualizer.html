Dockerfile Syntax

Every instruction, what it does, and a production-ready Spring Boot Dockerfile. Click any instruction to expand details.

What is a Dockerfile — and what does each instruction actually do?

A Dockerfile is a text file containing a sequence of instructions that Docker reads to build an image. Each instruction creates a new layer in the image. Understanding what each instruction does — and the ORDER in which you write them — directly impacts how fast your CI builds run (layer caching) and how secure and small your final image is. FROM: must be the first instruction. Sets the base image — the starting point your layers build on. Always use specific tags (eclipse-temurin:21-jre-alpine), never :latest. Choose the smallest base that works: alpine variants are ~10x smaller than full Debian/Ubuntu. JRE vs JDK: production images only need JRE (runtime), not JDK (compiler). WORKDIR: sets the working directory for all subsequent instructions. Creates the directory if it doesn't exist. Best practice: use /app consistently. COPY vs ADD: COPY copies files from host into the image. ADD does the same but ALSO supports URLs and auto-extracts tar files — use COPY unless you specifically need those extras (ADD is surprising). RUN: executes a shell command and creates a new layer. Chain commands with && and \ to keep related changes in ONE layer (vs multiple RUN = multiple layers). ENV: sets environment variables in the container. Visible in docker inspect — never store secrets here. Use them for non-secret config: ENV JAVA_OPTS="-Xmx512m". EXPOSE: documents which port the app listens on. Does NOT actually publish the port — that happens with -p at runtime. ENTRYPOINT vs CMD: ENTRYPOINT is the command that always runs. CMD provides default arguments to ENTRYPOINT. Use ENTRYPOINT ["java","-jar","app.jar"] + CMD ["--spring.profiles.active=prod"] — the profile can be overridden at runtime while java always runs. Multi-stage builds: use multiple FROM instructions. The first stage (builder) has the JDK and compiles. The final stage starts fresh from a minimal JRE base — copies only the compiled output. The final image has NO JDK, NO source code, NO Maven. Only what's needed to run.

Production Dockerfile

# Stage 1: BUILD (has JDK + Maven) FROM eclipse-temurin:21-jdk-alpine AS build WORKDIR /app # Copy pom.xml FIRST (layer caching trick): COPY pom.xml . # changes rarely RUN mvn dependency:go-offline # cache deps # THEN copy source: COPY src ./src # changes often RUN mvn package -DskipTests # compile + jar # Stage 2: RUN (minimal JRE only) FROM eclipse-temurin:21-jre-alpine WORKDIR /app # Non-root user (security best practice): RUN addgroup -S appgroup && adduser -S appuser -G appgroup USER appuser # Copy only the jar from build stage: COPY --from=build /app/target/*.jar app.jar EXPOSE 8080 ENTRYPOINT ["java", \ "-XX:MaxRAMPercentage=75", \ "-XX:+ExitOnOutOfMemoryError", \ "-jar", "app.jar"]

Layer caching strategy

# BAD: COPY everything first → cache miss every build COPY . . # any file change = redo everything RUN mvn package # deps re-downloaded every build! # GOOD: copy dep files first (stable), source last COPY pom.xml . # rarely changes RUN mvn dependency:go-offline # cache miss only when pom changes COPY src ./src # changes on every commit RUN mvn package -DskipTests # only recompile, deps cached # Spring Boot layered JAR (even better caching): # Split the fat JAR into layers: # 1. dependencies (stable, cached) # 2. spring-boot-loader (stable) # 3. snapshot-dependencies (changes rarely) # 4. application (changes every commit) # Enable: <configuration><layers><enabled>true</enabled></layers></configuration> # in spring-boot-maven-plugin

.dockerignore + security

# .dockerignore (like .gitignore for COPY): .git .gitignore target/ # don't copy compiled output *.md .env # NEVER copy .env into image! node_modules # if mixed project # Security best practices: # 1. Never RUN apt-get without clearing cache: RUN apt-get update && apt-get install -y curl \ && rm -rf /var/lib/apt/lists/* # clear cache # 2. Non-root user (prevents container escape): USER 1000:1000 # 3. Read-only filesystem: docker run --read-only \ --tmpfs /tmp \ myapp:1.0 # 4. Drop capabilities: docker run --cap-drop ALL myapp:1.0 # 5. Scan image for vulnerabilities: docker scout cves myapp:1.0 # or: trivy image myapp:1.0

CIAM Dockerfile patterns: Multi-stage Dockerfile for your Spring Boot CIAM service: Stage 1 (AS build): eclipse-temurin:21-jdk-alpine, copies pom.xml, runs mvn dependency:go-offline, copies src/, runs mvn package -DskipTests. Stage 2: eclipse-temurin:21-jre-alpine, non-root user (adduser appuser), copies ONLY the JAR from Stage 1 (COPY --from=build /app/target/*.jar app.jar). JVM flags: -XX:MaxRAMPercentage=75 (use 75% of container memory limit for heap — Kubernetes-aware), -XX:+ExitOnOutOfMemoryError (crash-and-restart is safer than hanging OOM). ADO pipeline: docker build -t $(acrLoginServer)/ciam-auth:$(Build.BuildId) . && docker push $(acrLoginServer)/ciam-auth:$(Build.BuildId). Image size target: <250 MB (JRE alpine ~190 MB + fat JAR ~50 MB). Never include: source code, test classes, .env files, private keys.

1 — Annotated Spring Boot Dockerfile

Click any line to see a detailed explanation:

FROM eclipse-temurin:21-jre-alpine
FROM sets the base image — the starting point. Every Dockerfile must begin with FROM.

eclipse-temurin:21-jre-alpine is the official OpenJDK image built on Alpine Linux (tiny base OS, ~5MB). 21 = Java version. jre = Java Runtime only (not JDK — we don't need javac in production). alpine = minimal OS, small image size (~190MB total).

Tip: Always pin to a specific version tag — never use :latest in production (it changes without warning).
WORKDIR /app
WORKDIR sets the working directory inside the container for all subsequent instructions (COPY, RUN, CMD, ENTRYPOINT).

If /app doesn't exist, Docker creates it. Think of it as mkdir -p /app && cd /app. All relative paths in later instructions are relative to this directory.
COPY target/app.jar app.jar
COPY copies files or directories from the build context (your local machine) into the image.

Syntax: COPY <source> <destination>
target/app.jar = the JAR file Maven built (via mvn package)
app.jar = destination inside the container (relative to WORKDIR /app)

Note: COPY only works with local files. For URLs or tar extraction, use ADD (but prefer COPY whenever possible).
EXPOSE 8080
EXPOSE documents that the container listens on port 8080. It is documentation only — it does NOT actually publish the port.

To actually make the port accessible from your host machine, you still need: docker run -p 8080:8080 myapp

Without EXPOSE it still works — it just makes intent clear to developers and tools like docker-compose.
ENV JAVA_OPTS="-Xmx512m"
ENV sets environment variables in the image. These are available to every RUN, CMD, and ENTRYPOINT instruction AND to the running container process.

For Spring Boot config: ENV SPRING_PROFILES_ACTIVE=prod activates the prod profile. ENV SPRING_DATASOURCE_URL=jdbc:postgresql://db:5432/myapp overrides application.properties.

You can also pass env vars at runtime: docker run -e SPRING_PROFILES_ACTIVE=dev myapp (overrides ENV in the image).
ENTRYPOINT ["java", "-jar", "app.jar"]
ENTRYPOINT defines the main command that always runs when the container starts. Use the exec form (JSON array) — NOT shell form — to avoid shell wrapping (which causes SIGTERM not to propagate to Java).

["java", "-jar", "app.jar"] runs: java -jar /app/app.jar

ENTRYPOINT is not easily overridden by docker run args (unlike CMD). Use it for the "main" command of your container.

2 — COPY vs ADD

✅ COPY — Use This

Simple, predictable. Copies files/directories from host to image. Nothing more.

Use for: source code, config files, JARs, certificates.

COPY src/ ./src/
COPY pom.xml .

⚠️ ADD — Special Cases Only

Like COPY but with extras: auto-extracts .tar.gz archives, can fetch URLs.

Use only when you need these extras. ADD with a URL bypasses build cache unpredictably.

ADD app-v1.tar.gz /app/

Rule: Use COPY for everything unless you specifically need ADD's tar-extraction or URL features.

3 — RUN vs CMD vs ENTRYPOINT

RUN

Runs at BUILD time. Creates a new image layer. Used for: installing packages, running build commands, creating directories.

RUN apt-get install -y curl
RUN mvn dependency:resolve

CMD

Default command at RUNTIME. Overridable by docker run arguments.

If both CMD and ENTRYPOINT exist, CMD provides default arguments to ENTRYPOINT.

CMD ["--server.port=9090"]

ENTRYPOINT

Main command at RUNTIME. Not easily overridden.

This is the "identity" of the container — what it is. Use exec form (JSON array) always.

ENTRYPOINT ["java","-jar","app.jar"]

# What happens with both ENTRYPOINT + CMD: ENTRYPOINT ["java", "-jar", "app.jar"] CMD ["--spring.profiles.active=prod"] # docker run myapp → runs: java -jar app.jar --spring.profiles.active=prod # docker run myapp --spring.profiles.active=dev → replaces CMD: # java -jar app.jar --spring.profiles.active=dev

4 — Layer Caching — Order Matters

Put slow, rarely-changing steps first. Put fast, frequently-changing steps last.

❌ Bad — slow rebuilds
# COPY everything first # Any source change = re-download ALL deps FROM maven:3.9-eclipse-temurin-21 WORKDIR /app COPY . . # ← changed? invalidates all below RUN mvn package -DskipTests # ← always re-downloads
✅ Good — deps cached separately
# Copy pom.xml first, download deps # Only re-download when pom.xml changes FROM maven:3.9-eclipse-temurin-21 WORKDIR /app COPY pom.xml . # ← stable, stays cached RUN mvn dependency:go-offline COPY src ./src # ← changes often, fast layer RUN mvn package -DskipTests

Result: when only your Java source changes, the mvn dependency:go-offline layer is cached. Rebuild time drops from ~3 minutes to ~20 seconds.
