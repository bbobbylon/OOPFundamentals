Debugging Auth: 401 vs 403

These two status codes get blamed on each other constantly, but they answer different questions. 401 = authentication ("I don't know who you are") — fixable by getting a valid credential. 403 = authorization ("I know who you are, and you can't do this") — not fixable by refreshing a token. Knowing which one you have tells you exactly where to look.

🐛 What is the difference between 401 and 403 — and what does each one tell you to look for?

These two HTTP error codes are the most confused in the entire auth space — developers and even frameworks get them backwards. The distinction is conceptually clean but easy to muddle in practice. 401 Unauthorized: the name is misleading — it actually means unauthenticated. The server doesn't know who you are. Either: no credentials were provided (missing Authorization header), the credentials are invalid (bad token, expired token, signature check failed, wrong issuer), or the credentials can't be verified (JWKS endpoint unreachable). The HTTP spec says a 401 response SHOULD include a WWW-Authenticate header telling the client what auth scheme to use: WWW-Authenticate: Bearer realm="ciam", error="invalid_token". Key insight: getting a fresh token WILL fix a 401 (assuming the fresh token is valid). If refreshing the token still gives 401, the token is structurally wrong (wrong issuer, wrong audience, wrong algorithm). 403 Forbidden: the server knows exactly who you are (authentication succeeded) — but this identity doesn't have permission to perform the requested action. A 403 cannot be fixed by getting a new token (unless the new token includes additional scopes/roles). You need different permissions: a role change in the IDP, a scope added to the OAuth client, or a resource access policy change. Spring Security causes: 401 from Spring → AuthenticationException caught by AuthenticationEntryPoint. 403 from Spring → AccessDeniedException caught by AccessDeniedHandler. Both configurable via http.exceptionHandling().authenticationEntryPoint(...).accessDeniedHandler(...). Debugging 403s: decode the JWT — does it have the required role/scope? Check Spring Security's @PreAuthorize("hasRole('CIAM_ADMIN')") — does the role in the JWT match exactly? Case sensitivity? Spring adds "ROLE_" prefix automatically — hasRole('ADMIN') checks for authority ROLE_ADMIN.

The problem

You can spend a whole afternoon comparing authorities against a rule that was never evaluated.

GET /api/customers returns 200. POST /api/customers returns 403. Same token, same user, same minute.

So you do the sensible thing this page just taught you: it's a 403, therefore it's authorization, therefore compare the token's authorities against the endpoint's rule. You decode the token — "roles":["CIAM_ADMIN"]. You check the converter — it prefixes correctly, so the principal carries ROLE_CIAM_ADMIN. You check the annotation — @PreAuthorize("hasRole('CIAM_ADMIN')"). It matches. You add a breakpoint in the controller method to print the authorities, hit POST again, and the breakpoint never fires.

It never fires because Spring Security turns CSRF protection on by default, and the default matcher exempts exactly GET, HEAD, TRACE and OPTIONS. Every read sails through; every write hits CsrfFilter, which sits near the front of the filter chain — ahead of the bearer-token authentication filter and far ahead of method security. Finding no CSRF token, it hands the request to an access-denied handler and writes 403 itself. Your rule was never consulted. Your controller was never reached. The status code you spent the afternoon interpreting was produced by a filter that had not yet looked at your token at all.

token valid and unexpired ✓ ROLE_CIAM_ADMIN present ✓ @PreAuthorize expression correct ✓ CsrfFilter rejected the POST before any of that ⚠ identical 403 either way ⚠

403 means "a component refused this request". It does not promise the component was your authorization rule.

A status code names the outcome, never the component. 401 and 403 are honest about what the server decided and silent about who decided it — and on a Spring app there are a dozen candidates, most of them filters running before your code exists to the request. The fastest way to shorten an auth investigation is not a better reading of the number; it is one experiment that changes which components can possibly be involved. Drop the credential. Change the verb. Call a permitAll route. Each one rules out a whole stretch of the chain, which a second look at the same three-digit number never will.

The mechanism

Walk one POST down the filter chain and watch it die three filters before the code you were debugging.

  1. The browser sends POST /api/customers with Authorization: Bearer eyJ… and a JSON bodyeverything the endpoint needs
  2. Early in the chain, CsrfFilter asks one question: is this verb exempt? GET/HEAD/TRACE/OPTIONS are; POST is notwhy reads "work" and writes don't
  3. Not exempt → it looks for the expected CSRF token in the request. A stateless SPA sending only a bearer token has noneno header, no cookie, no match
  4. CsrfFilter calls the access-denied handler itself and returns. The chain stops here — the bearer-token filter downstream never runsthe token is never even parsed
  5. So there is no Authentication in the context, no authorities list, no @PreAuthorize evaluation, and no entry in your controller's logevery clue you'd look for is absent
  6. The browser shows 403 Forbidden — the same three digits a genuine missing-role failure produces, and with no WWW-Authenticate header to hint otherwisetwo very different bugs, one identical symptom

Step 4 is the one to hold on to, and it generalises well past CSRF: a filter that writes the response itself ends the request, so every downstream component you were mentally debugging did not participate. This is also why the same misconfiguration 403s a route you marked permitAll — "public" is an authorization decision, and the request never got as far as authorization to have it applied.

Two of those causes are settled by comparing authorities against a rule. The third is settled by looking at the HTTP verb, and no amount of staring at the token will get you there. That is what makes the 403 family harder to debug than the 401 family: 401 at least tells you the credential is the problem, while 403 only tells you that something said no.

POST /api/customers returns 403. The decoded token carries CIAM_ADMIN, the converter prefixes it, and the endpoint asks for exactly hasRole('CIAM_ADMIN'). GET /api/customers with the same token returns 200. You resend the POST from curl with no Authorization header at all — and get 403 again. What has that last experiment told you?

Exactly, and it is the cheapest experiment in auth debugging: removing the credential should change the answer, and when it doesn't, the components that read credentials are not involved. On a Spring Security 6 app whose CSRF protection is still at its default, this is the signature of CsrfFilter — it runs ahead of the bearer-token filter, exempts only GET/HEAD/TRACE/OPTIONS, and answers the request itself. Confirm it in the DEBUG log, then decide deliberately: disable CSRF for a genuinely stateless bearer-token API (there is no ambient credential for a hostile page to ride on), or keep it and send the token if your auth travels in a cookie.

permitAll is worth understanding precisely: it means the authorization step allows anyone, so a credential-less request to such a route should return 200, not 403. Anonymous authentication is a real thing in Spring Security — an unauthenticated request does get an AnonymousAuthenticationToken — but a denial against an anonymous principal is specifically translated into a 401 challenge, because the right thing to tell someone with no credential is "authenticate", not "you may not". A 403 here means the decision was made somewhere that translation never reaches.

This is the assumption that costs the afternoon. A missing credential is the textbook 401: the server cannot identify you, so it challenges you, and it is required to say how in a WWW-Authenticate header. 403 is reserved for "I understood the request and I am refusing it anyway" — so a credential-less 403 is genuinely surprising information, not noise, and it points at something in front of authentication rather than at your roles.

Where you have seen this before

Anything sitting in front of your app can answer for it — and it never says so.

Angular's XSRF interceptor and the absolute URL

Angular's HttpClient reads the XSRF-TOKEN cookie and attaches X-XSRF-TOKEN automatically — but only on mutating requests to relative URLs, never on absolute ones, because it will not leak your token to another origin. So the identical code that passes against a dev proxy (/api/…) starts 403-ing in production the day someone switches the base URL to https://api.example.com. Nothing about your Spring config changed; the header simply stopped being sent.

the client silently changed the request, not the server

The 403 your application logs have never heard of

A WAF rule, an API gateway authorizer, or an ingress controller can refuse a request and write a 403 without your app receiving anything. The tell is the same one as here: you grep the application log for the request and find no entry at all. An absent log line is evidence — it means the responder is upstream of whatever writes that log.

no log line means it never arrived

SameSite=Lax, the browser's own CSRF defence

Modern browsers default cookies to SameSite=Lax, which withholds them on cross-site POSTs while still sending them on top-level GET navigations — the same verb split, for the same threat, one layer lower. It is also a famous source of mystery failures in federated login flows, where the IdP POSTs back to your app and the session cookie you were relying on quietly isn't there. Same lesson: the request that arrived is not always the request you sent.

the browser edits your request too

2. Interactive: walk the decision tree to the verdict

What's the situation?

The tree is always the same three gates: credential present? → credential valid? → has the required authority? The first gate that fails decides 401 vs 403.

3. How to confirm each, fast

  • 401? Decode the token and check it — is it present, unexpired, signed by the right key, with the right aud/iss? (Decode in the JWTs page or with the runbook snippet.)
  • 403? The token is fine — compare its authorities (scope/roles) against what the endpoint's @PreAuthorize demands.
  • Reproduce server-side (bypasses the browser/CORS) to see the true status:
curl -i https://your-api/api/progress -H "Authorization: Bearer $TOKEN"
# 401 → credential problem · 403 → permission problem · 200 → it's the client

4. Traps that send you the wrong way

  • A "401 after every deploy" usually means JWT_SECRET changed — old tokens fail signature checks. Sign out/in.
  • Endless refresh loop on a 403. If your interceptor refreshes on any error, a 403 triggers a pointless refresh-and-retry. Only refresh on 401.
  • A CORS error is neither. If the browser shows a CORS message, the status you imagine may never have reached your JS — debug CORS first.
  • Clock skew → 401. A fast/slow server clock makes a fresh token look expired/not-yet-valid. Allow a little leeway.
  • 403 for unauthenticated. A misconfigured entry point can return 403 where you'd expect 401 — check what's actually missing, not just the number.

5. One-sentence recap

🔑 Read the number as a question: 401 = "who are you?" — the filter chain found no valid credential (missing/expired/bad-signature/wrong-audience), usually fixable by re-auth or refresh; 403 = "you, but no" — you're authenticated but @PreAuthorize said the token lacks the scope/role (or failed an ownership rule), which a refresh can't fix — so confirm by decoding the token for 401s and comparing authorities vs the endpoint's rule for 403s, and reproduce with curl to step around the browser.
