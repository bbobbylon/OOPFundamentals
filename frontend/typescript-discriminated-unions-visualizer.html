Discriminated Unions & Exhaustiveness

The single most useful pattern in TypeScript — model "one of several shapes" safely, and let the compiler force you to handle every case

What are discriminated unions — and why are they the most useful pattern in TypeScript for modelling states?

A discriminated union (also called a tagged union or algebraic data type) is a union type where every variant shares a common discriminant property — a literal type that uniquely identifies which variant you have. Example: type AuthState = { status: 'unauthenticated' } | { status: 'loading' } | { status: 'authenticated'; user: UserDto; token: string } | { status: 'error'; message: string }. The discriminant is status. When you check if (state.status === 'authenticated'), TypeScript narrows the type inside that branch to { status: 'authenticated'; user: UserDto; token: string } — you can access state.user safely. Outside that branch: state.user is a compile error (it might be the unauthenticated variant). This is fundamentally different from having user?: UserDto on one big object — that approach allows impossible states like status: 'unauthenticated' AND user: someUser set simultaneously. Discriminated unions make impossible states unrepresentable. Exhaustiveness: use never to make the compiler error if you miss a case: const _: never = state in the default branch — if every case is handled, TypeScript narrows to never and the assignment succeeds; if you add a new variant and forget to handle it, TypeScript errors on this line.

Structure + narrowing

type Shape = | { kind: 'circle'; radius: number } | { kind: 'rectangle'; w: number; h: number } | { kind: 'triangle'; base: number; height: number }; function area(shape: Shape): number { switch (shape.kind) { case 'circle': return Math.PI * shape.radius ** 2; // narrowed case 'rectangle': return shape.w * shape.h; // narrowed case 'triangle': return 0.5 * shape.base * shape.height; // narrowed default: const _: never = shape; // exhaustiveness check throw new Error('Unknown shape'); } }. Adding a new shape variant = compile error on the never line until you handle it.

Impossible states

1. The problem — a "type" field and a tower of ifs

Without discriminated unions — fragile

// one interface trying to be everything
interface Shape {
  kind: string;
  radius?: number;   // only for circles
  side?: number;     // only for squares
  width?: number;    // only for rectangles
  height?: number;
}

function area(s: Shape): number {
  if (s.kind === 'circle') {
    // 😖 radius might be undefined — TS can't be sure
    return Math.PI * s.radius! ** 2; // forced ! everywhere
  }
  return 0;
}

// nothing stops this nonsense:
const bad: Shape = { kind: 'circle', side: 5 }; // ✗ allowed!

Every optional field is a lie waiting to crash. You litter the code with ! and ?., and impossible combinations compile fine.

With a discriminated union — bulletproof

// each shape is its OWN type with a shared literal tag
interface Circle    { kind: 'circle';    radius: number; }
interface Square    { kind: 'square';    side: number; }
interface Rectangle { kind: 'rectangle'; width: number;
                                       height: number; }

// the union — "a Shape is ONE of these"
type Shape = Circle | Square | Rectangle;

function area(s: Shape): number {
  switch (s.kind) {
    case 'circle':    return Math.PI * s.radius ** 2; // ✓ no !
    case 'square':    return s.side ** 2;
    case 'rectangle': return s.width * s.height;
  }
}

// impossible combos rejected at compile time:
const bad: Shape = { kind: 'circle', side: 5 }; // ✗ error ✓

☕ Coming from Java? A discriminated union is TypeScript's version of a sealed interface + switch pattern matching. The kind literal plays the role of the runtime type, and TS narrows exactly like Java's pattern switch narrows a sealed hierarchy.

2. The three ingredients

① a common discriminant property + ② a literal type for it in each member + ③ a union of those members
IngredientWhat it meansExample
DiscriminantOne property present in every member, with the same namekind (or type, tag, status…)
Literal typeEach member sets the discriminant to a unique literal, not string'circle', 'square'
UnionCombine members with |Circle | Square | Rectangle

⚠ The discriminant must be a literal type (kind: 'circle'), not string. If you write kind: string, narrowing breaks — TS can't tell the members apart.

4. Exhaustiveness — the never trick

Force the compiler to catch missing cases

Add a default branch that assigns the value to never. If you ever add a new union member and forget to handle it, this line becomes a compile error — a to-do list the compiler maintains for you.

function area(s: Shape): number {
  switch (s.kind) {
    case 'circle':    return Math.PI * s.radius ** 2;
    case 'square':    return s.side ** 2;
    case 'rectangle': return s.width * s.height;
    default:
      // if every case is handled, s is 'never' here
      const _exhaustive: never = s;
      return _exhaustive;
  }
}

✓ Why it works: once all known cases return, the only type left is never. Assigning a real leftover type to never fails to compile.

API request state — the killer use case

        
type RequestState<T> =
  | { status: 'idle' }
  | { status: 'loading' }
  | { status: 'success'; data: T }
  | { status: 'error';   message: string };

// data only exists when status is 'success' —
// no "loading but also has data?" impossible states
function render(s: RequestState<User>) {
  switch (s.status) {
    case 'idle':    return 'Press load';
    case 'loading': return 'Spinner…';
    case 'success': return s.data.name; // ✓ data exists
    case 'error':   return s.message;  // ✓ message exists
  }
}

🌱 New here? A shared "tag" lets TypeScript tell shapes apart.

  

    
Sometimes a value is "one of several shapes." A discriminated union gives each shape a common literal tag field so TypeScript can figure out which one you have:

    
type Shape =
  | { kind: "circle"; r: number }
  | { kind: "rect"; w: number; h: number };

    
Now switch (shape.kind) and inside case "circle" TypeScript knows there's an r (and no w/h) — autocomplete and type-checks adjust per branch. It's the type-safe way to model "this is one of a fixed set of variants," and it reads naturally.

  

  
🧠 Expert corner — exhaustiveness and "impossible states impossible"

  

    
    
      
  • The discriminant must be a literal type (a string/number literal like "circle", not string). That's what lets the compiler narrow on it.
    • 
      
  • Exhaustiveness checking. In the default case, assign the value to const _: never = shape — if you later add a variant and forget to handle it, that line becomes a compile error. The compiler maintains your switch for you.
    • 
      
  • Model state machines & API results: {status:"loading"} | {status:"ok"; data: T} | {status:"error"; msg: string}. Now data only exists when status === "ok" — you literally cannot read data while loading. That's "make impossible states impossible."
    • 
      
  • Pairs with as const to lock literal tags, and with narrowing (the switch is the narrowing mechanism).
    • 
      
  • CIAM tie-in. An auth state union — { status: "anonymous" } | { status: "authenticating" } | { status: "authenticated"; user: User; token: string } — means user/token are only accessible once authenticated. No more "is user maybe null here?" guesswork.
