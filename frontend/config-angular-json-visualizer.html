angular.json

⚙️ What is angular.json — and how does it control every ng command you run?

angular.json is the workspace configuration file for the Angular CLI. It lives at the project root alongside package.json and is the first file the CLI reads whenever you run ng serve, ng build, ng test, or ng lint. Think of it as the blueprint that maps CLI commands to specific build toolchains with specific options. The file uses a project → architect → targets hierarchy. Each project (there can be multiple in a monorepo) has an architect section. Each key under architect is a target (build, serve, test, lint, extract-i18n). Each target specifies a builder (a plugin that does the work: @angular-devkit/build-angular:application is the default esbuild-based builder for Angular 17+) and options (the configuration passed to that builder). A critical feature: targets have configurations that override the base options. The production configuration enables minification, tree-shaking, AOT compilation, hashed filenames, and disables source maps. The development configuration keeps source maps, disables optimization, and enables HMR (Hot Module Replacement). When you run ng build without flags, it uses the production configuration by default (Angular 17+). When you run ng serve, it uses development. You can switch: ng build --configuration staging to use a custom staging configuration you define. File replacements in configurations let you swap environment.ts with environment.prod.ts at build time — the classic pattern for environment-specific API URLs.

Targets → builders

// angular.json excerpt: "architect": { "build": { "builder": "@angular-devkit/build-angular:application", "options": { "outputPath": "dist/my-app", "index": "src/index.html", "browser": "src/main.ts", "tsConfig": "tsconfig.app.json", "assets": ["src/favicon.ico", "src/assets"], "styles": ["src/styles.scss"], "scripts": [] }, "configurations": { "production": { "optimization": true, "outputHashing": "all", "sourceMap": false, "namedChunks": false, "aot": true, "budgets": [...] }, "development": { "optimization": false, "sourceMap": true, "hmr": true } } }, "serve": { "builder": "@angular-devkit/build-angular:dev-server", "options": { "buildTarget": "my-app:build:development", "port": 4200 } } }

File replacements (env switching)

// Switch files at build time: "configurations": { "production": { "fileReplacements": [{ "replace": "src/environments/environment.ts", "with": "src/environments/environment.prod.ts" }] } } // environment.ts (development): export const environment = { production: false, apiUrl: 'http://localhost:8080', pingIssuer: 'https://ping-dev.myco.com' }; // environment.prod.ts (production): export const environment = { production: true, apiUrl: 'https://api.myco.com', pingIssuer: 'https://ping.myco.com' }; // Angular service uses: import { environment } from '../environments/environment'; // ng build → uses environment.prod.ts automatically // ng serve → uses environment.ts

Custom configurations

# Add a custom "staging" config: # In angular.json under "configurations": "staging": { "fileReplacements": [{ "replace": "src/environments/environment.ts", "with": "src/environments/environment.staging.ts" }], "optimization": true, "sourceMap": false } # Use it: ng build --configuration staging # Angular 17+ generates this automatically if you: ng generate environments # ADO pipeline: # Build for staging: - task: Npm@1 inputs: command: custom customCommand: 'run build:staging' # package.json script: # "build:staging": "ng build --configuration staging"

In CIAM / Context: The CIAM Angular app's angular.json has three configurations: development (local, hits localhost:8080 Spring Boot), staging (hits staging API, real Ping staging tenant), production (hits prod API, real Ping prod tenant). File replacements swap environment.ts per config. The ADO build pipeline runs ng build --configuration production and deploys the dist/ folder to the S3 bucket behind CloudFront.

or, ng build does not know how to build anything

The problem

You type a command. Nothing in the CLI knows what it means.

Reading it as a settings file makes every error confusing

Treat angular.json as "the config" and its errors are noise: Cannot find target "serve", Project does not support the "test" target, Unknown option "browser". Each of those is a lookup miss, and none of them says so — which is why people go hunting through their source for a problem that lives entirely in one JSON path.

ng build ⚠ Cannot find target "build" ⚠ source is fine ⚠ the map has no entry ⚠

Nothing is broken in your app. The CLI asked a question of a JSON file and got no answer back.

Read it as a lookup table and the errors read themselves
ng <target> <project> is a path, not a command ↓ projects.<project>.architect.<target> What it finds there names a builder — the code that does the work ↓ and hands it the options object sitting beside it So swapping the builder changes the build without changing any command
ng build is a lookup, not a command. The CLI has no idea how to compile anything — it reads projects.<name>.architect.build.builder, loads that package, and hands it the options next door. Every "unknown target" error is a missing key, and every build behaviour you want to change is an option in that one object.
You

ng test says the project doesn't support that target. I have tests.

The CLI

I am sure you do. I looked up projects.my-app.architect.test and there is no such key, so I have no builder to run and no options to give it. Your spec files were never part of the question.

The builder

And I am an ordinary npm package. Point that key at @angular/build:application instead of the old browser builder and you have switched the whole project to esbuild — same command, entirely different machinery.

The mechanism

Follow ng build my-app --configuration production to the code that runs.

each level is one key deeper into the file ↘

projects — every app and library in the workspace
my-app — the one you named (or defaultProject)
architect — the map of target name → what to run
build — the target you typed
builder + options@angular/build:application, plus the options it receives

And --configuration production is the last step, layered on top: its object under configurations is merged over the base options, not used instead of them. That single word — merged — is why a setting can be right in options and still wrong in prod, and why reading only one of the two objects tells you almost nothing about what the build actually did.

Which makes one command more useful than reading the file. Because the effective options are a merge you performed in your head, the reliable way to know what a build received is to ask: ng build --configuration production --verbose, or simply to check whether the option you are editing is being overridden one level down. This is also the honest answer to why ng serve and ng build disagree — they are different targets, with different builders and different merged options. They were never the same operation with a flag.

Your build target sets "sourceMap": true in options, and its configurations.production block sets "sourceMap": false. You run ng build --configuration production. What do you get?

Right, and "merged over" is the exact mental model to keep. The configuration block is not a separate set of options, it is a patch applied on top — so reading options alone tells you what happens in a build with no configuration, which is a build you probably never run.

It is the other way round: options is the base and the configuration is the override. If it worked as described, fileReplacements could never swap your environment file, which is the single most-used thing configurations do.

Declaring the same key in both is not just legal, it is the entire point — that is how you say "this in general, that in production." A build error here would make configurations useless.

Where you've seen this before

Three familiar versions of the same lookup.

Maven's plugin goals

mvn spring-boot:run is the identical shape — a plugin name, a goal, and a configuration block, resolved from a POM. Neither Maven nor the Angular CLI contains the logic; both look up who does and hand over the settings.

a name, resolved to code

npm scripts

npm run build is the same lookup, one level simpler: a key in a JSON object whose value is what actually runs. Same reason its error is "missing script" rather than anything about your code.

missing script = missing key

A CIAM workspace with three apps

Admin console, customer portal, shared lib — three entries under projects, each with its own architect map. Which is why ng build with no project name is ambiguous, and why naming it explicitly in CI scripts is worth the extra word.

name the project in CI
Questions from the back row

What does a bundle budget actually do?

Fails your build on size, deliberately. A budgets entry with "type": "initial" and a maximumError turns "the bundle grew again" from something nobody notices into a red CI run on the pull request that did it. That is the whole value — it is a ratchet, not a report. Set maximumWarning a little under where you are now and maximumError where it would genuinely hurt, then treat a raise as a decision someone has to make on purpose.

Why did my new global stylesheet not apply?

Because global styles are not discovered, they are listed. The styles array in the build target's options is the complete set — a file that is not in it is simply not part of the bundle, no matter where it sits in src/. Same for scripts and for assets, which is the usual reason a folder of images 404s in production and works in dev, where a leftover path happened to resolve.

Should I edit this file by hand?

For options, yes — that is what it is for. For structural changes, prefer the CLI: ng generate application and ng generate library add a projects entry with every target wired correctly, and ng update migrates builder names when they change. Hand-editing structure is how you end up with a builder string that no longer exists after an upgrade, producing an error about a package rather than about the key that named it.

angular.json Anatomy

The Angular CLI workspace configuration. One file controls how your app is built, served, tested, and linted. It lives in the project root alongside package.json.

{
  "$schema": "./node_modules/@angular/cli/lib/config/schema.json",
  "version": 1,
  "newProjectRoot": "projects",       // where `ng generate library` goes

  "projects": {

    "my-app": {                         // project name (matches package.json name)
      "projectType": "application",     // "application" | "library"
      "root": "",                        // root of project relative to workspace
      "sourceRoot": "src",              // where source files live
      "prefix": "app",                  // default component selector prefix (app-xxx)

      "architect": {                    // ← "targets" in CLI v17+ terminology

        /* ── build ──────────────────────────────────────────── */
        "build": {
          "builder": "@angular-devkit/build-angular:application",
          "options": {
            "outputPath": "dist/my-app",
            "index": "src/index.html",
            "browser": "src/main.ts",
            "polyfills": ["zone.js"],
            "tsConfig": "tsconfig.app.json",
            "assets": ["src/favicon.ico", "src/assets"],
            "styles": ["src/styles.scss"],
            "scripts": []
          },
          "configurations": {             // ← environment overrides
            "production": {
              "budgets": [...],
              "outputHashing": "all",
              "optimization": true
            },
            "development": {
              "optimization": false,
              "extractLicenses": false,
              "sourceMap": true
            }
          },
          "defaultConfiguration": "production"
        },

        /* ── serve ───────────────────────────────────────────── */
        "serve": {
          "builder": "@angular-devkit/build-angular:dev-server",
          "configurations": {
            "production": { "buildTarget": "my-app:build:production" },
            "development": { "buildTarget": "my-app:build:development" }
          },
          "defaultConfiguration": "development"
        },

        /* ── extract-i18n ─────────────────────────────────────── */
        "extract-i18n": {
          "builder": "@angular-devkit/build-angular:extract-i18n"
        },

        /* ── test ────────────────────────────────────────────── */
        "test": {
          "builder": "@angular-devkit/build-angular:karma",
          "options": {
            "tsConfig": "tsconfig.spec.json",
            "polyfills": ["zone.js", "zone.js/testing"],
            "assets": ["src/favicon.ico", "src/assets"],
            "styles": ["src/styles.scss"],
            "scripts": []
          }
        },

        /* ── lint ────────────────────────────────────────────── */
        "lint": {
          "builder": "@angular-eslint/builder:lint",
          "options": {
            "lintFilePatterns": ["src/**/*.ts", "src/**/*.html"]
          }
        }
      }
    }
  }
}

Build Targets — architect

Each key under architect is a target. Run any target with ng run <project>:<target>[:<configuration>].

Running targets

# Shorthand commands
ng serve                     = ng run my-app:serve:development
ng build                     = ng run my-app:build:production
ng test                      = ng run my-app:test
ng lint                      = ng run my-app:lint

# Specify a configuration explicitly
ng build --configuration staging
ng serve --configuration production

# Override a single option on the command line
ng serve --port 4300
ng build --output-path custom-dist
ng test --code-coverage

Environments & Configurations

Angular's environment system replaces files at build time. You don't use Node's NODE_ENV — you use fileReplacements to swap out environment-specific constants.

File structure

src/
├── environments/
│   ├── environment.ts          // development (default)
│   ├── environment.staging.ts  // staging
│   └── environment.prod.ts     // production

environment.ts — development defaults

export const environment = {
  production: false,
  apiUrl: 'http://localhost:8080/api',
  logLevel: 'debug',
  featureFlags: {
    newDashboard: true   // enabled in dev, maybe not prod
  }
};

environment.prod.ts — production overrides

export const environment = {
  production: true,
  apiUrl: 'https://api.myapp.com',
  logLevel: 'error',
  featureFlags: {
    newDashboard: false
  }
};

angular.json — fileReplacements

"configurations": {
  "production": {
    "fileReplacements": [
      {
        "replace": "src/environments/environment.ts",
        "with":    "src/environments/environment.prod.ts"
      }
    ],
    "optimization": true,
    "outputHashing": "all",
    "sourceMap": false,
    "extractLicenses": true
  },
  "staging": {
    "fileReplacements": [
      {
        "replace": "src/environments/environment.ts",
        "with":    "src/environments/environment.staging.ts"
      }
    ],
    "optimization": true,
    "sourceMap": true          // keep source maps for staging debugging
  }
}

Using environments in code

// Always import the development path — fileReplacements swap it at build time
import { environment } from '../environments/environment';

@Injectable({ providedIn: 'root' })
export class ApiService {
  private baseUrl = environment.apiUrl;

  getData() {
    return this.http.get(`${this.baseUrl}/data`);
  }
}

Building for a specific environment

# Development (default for ng serve)
ng serve

# Production
ng build --configuration production
ng build  # same — production is the defaultConfiguration

# Staging
ng build --configuration staging
ng serve --configuration staging

# Combine configurations (comma-separated)
ng build --configuration production,fr   # production + French i18n

Bundle Budgets

Budgets enforce size limits on your built assets. The CLI warns or errors during ng build if any bundle exceeds the threshold. This keeps bundle bloat visible as the project grows.

Budget configuration

"budgets": [
  {
    "type": "initial",          // total initial download (all bundles loaded at startup)
    "maximumWarning": "500kb", // warn at 500kB
    "maximumError": "1mb"      // build fails at 1MB
  },
  {
    "type": "anyComponentStyle", // any single component's styles
    "maximumWarning": "4kb",
    "maximumError": "8kb"
  },
  {
    "type": "any",               // any individual file
    "maximumWarning": "750kb",
    "maximumError": "2mb"
  }
]

Budget types

TypeWhat it measures
initialTotal size of all bundles loaded before user interaction — main, polyfills, styles
anyAny single output file (any bundle or chunk)
allScriptTotal of all JS bundles
allTotal of every output file including CSS
anyScriptAny single JS file
anyComponentStyleAny component's encapsulated styles (ViewEncapsulation.Emulated)

Typical Angular bundle sizes (production)

Example bundle breakdown for a medium Angular 17 app:
main.js (app code)
180kB
polyfills.js (zone.js)
32kB
styles.css (global + Angular Material)
76kB
vendor / lazy-loaded routes (loaded on demand)
128kB
Initial total: ~288kB gzipped. Budget warning at 500kB.

When you exceed the budget

✗  Error: bundle initial exceeded maximum budget. Budget 1.00 MB was not met by 234 kB with a total of 1.23 MB.

Solutions:
1. Lazy load more routes (dynamic import())
2. Remove or replace large dependencies (lodash → lodash-es or native)
3. Use @defer for below-the-fold components
4. Increase the budget threshold (last resort)
5. Run: ng build --stats-json then analyze with webpack-bundle-analyzer

Assets, Styles & Scripts

These three arrays in the build options control what gets copied to the output folder and what's globally injected into every page.

assets — copied verbatim

"assets": [
  "src/favicon.ico",              // single file at output root
  "src/assets",                   // entire directory → dist/assets/
  {
    "glob": "**/*",
    "input": "src/assets/",
    "output": "/assets/"          // served at: /assets/...
  },
  {
    "glob": "manifest.webmanifest",
    "input": "src/",
    "output": "/"                 // at dist root (for PWA)
  },
  {
    "glob": "**/*.{woff2,woff,ttf}",
    "input": "node_modules/@fontsource/inter",
    "output": "/fonts/"          // self-host fonts
  }
]

styles — global CSS / SCSS

"styles": [
  "src/styles.scss",              // your global styles
  "node_modules/@angular/material/prebuilt-themes/indigo-pink.css",
  {
    "input": "src/styles/print.scss",
    "inject": false,             // don't auto-inject — load on demand
    "bundleName": "print"        // outputs print.css
  }
]

// Note: component styles defined in @Component.styles are NOT here.
// They go through Angular's ViewEncapsulation and are scoped automatically.

scripts — legacy global scripts

"scripts": [
  "node_modules/jquery/dist/jquery.min.js",  // rare: legacy libs
  {
    "input": "src/scripts/analytics.js",
    "inject": false,
    "bundleName": "analytics"
  }
]
// Modern approach: use npm packages and import them in TypeScript instead

Serving static assets in Angular

// Access at runtime — path is relative to the app root, not the component
// ✓ Asset at src/assets/images/logo.png
<img src="/assets/images/logo.png" />         // absolute — always works
<img src="assets/images/logo.png" />          // relative — only from root

// In TypeScript — use environment to switch between CDN and local
import { environment } from '../environments/environment';
const logo = environment.production
  ? 'https://cdn.myapp.com/logo.png'
  : 'assets/images/logo.png';

Builders — esbuild vs Webpack

A "builder" is the Angular CLI plugin that does the actual compilation. Angular 17+ defaults to esbuild (via Vite for dev server). Prior versions used Webpack.

@angular-devkit/build-angular:application

Angular 17+ defaultesbuild
  • 2–10× faster production builds
  • Vite dev server with native HMR
  • Supports SSR ("server" option)
  • Bundle splitting / code splitting
  • JSON imports, CSS modules

@angular-devkit/build-angular:browser

Angular 12–16 (webpack)
  • Webpack-based — slower, well-understood
  • Uses "main" key (not "browser")
  • Custom webpack via @angular-builders/custom-webpack
  • No built-in SSR support
  • Required by older third-party schematics

Migrating from browser to application builder

# Angular CLI migration schematic — updates angular.json automatically
ng update @angular/cli --name use-application-builder

// angular.json changes:
"builder": "@angular-devkit/build-angular:browser"
"builder": "@angular-devkit/build-angular:application"

// Key option name change:
"main": "src/main.ts"
"browser": "src/main.ts"

Custom builders

// Third-party builders — install and reference in angular.json
"@nrwl/angular:webpack-browser"      // Nx workspace builder
"@nguniversal/builders:ssr-dev-server"// SSR dev server (legacy)
"@angular-builders/jest:run"          // Jest instead of Karma
"@angular-builders/custom-webpack:browser" // extend webpack config
