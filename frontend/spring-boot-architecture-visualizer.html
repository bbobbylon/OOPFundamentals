Spring Boot Architecture

How Spring Boot starts up, wires your beans, and configures itself from the classpath.

🌱 What is Spring Boot? What does it actually do when you run it?

Spring Boot is a framework for building Java apps — most commonly REST APIs. It wraps the older, more verbose Spring Framework and adds auto-configuration: instead of dozens of XML files or @Bean factory methods, it inspects what's on the classpath (the libraries in your pom.xml) and wires sensible defaults for you. Running the app kicks off a startup sequence — scan packages for @Component/@Service/@Repository/@Controller, apply auto-config, build the ApplicationContext (the bean container), start an embedded Tomcat, and begin serving — all in seconds.

  • Convention over configuration. Classpath presence drives defaults; you override only what you need.
  • Component scanning finds your beans by their stereotype annotations and registers them in the context.
  • The server is embedded. Tomcat (or Netty for reactive) ships inside the jar — java -jar just runs.
  • The ApplicationContext is the runtime — it holds every bean and resolves the dependency graph.

Startup sequence

1. JVM loads your classes. 2. Spring scans for @Component beans. 3. Auto-configuration applies. 4. ApplicationContext (IoC container) is created. 5. Embedded Tomcat starts on port 8080.

What auto-config does

Add spring-security → a security filter chain is set up automatically. Add spring-data-jpa + a driver → a datasource + EntityManager appear. You override these defaults only when you actually need to.

CIAM backend: Your API boots with Tomcat (or Netty), Spring Security auto-configured, a JPA datasource on your database, and your @RestController endpoints registered. The Angular frontend calls them with Bearer tokens that Spring Security validates.

"On the classpath" and "known to Spring" are not the same claim. Component scanning only finds classes wearing a stereotype annotation — everything else is a .class file Spring never looks at twice.

Spring never goes looking for classes — it only ever finds the ones that raised a hand. Component scanning isn't "search everything and figure out what looks useful"; it's "check every class for one of a handful of specific annotations." A perfectly good class with no annotation on it is, to Spring, indistinguishable from a class that doesn't exist.
Think of component scanning like a school taking attendance by roll call, not a headcount. A student sitting quietly in the back who never says "here" is marked absent — not because the teacher can't see them, but because attendance is taken by who answers, not by who's physically present. @Service is your class raising its hand.

Component scanning

I don't inspect every .class file on your classpath for "does this look useful." I look specifically for @Component and the annotations built on top of it — @Service, @Repository, @Controller. No annotation, no candidate. I walked right past that file and had no reason to stop.

The ApplicationContext

And I only know what component scanning hands me. By the time OrderService asks for an EmailService, I'm not searching your source folders — I'm searching a bean registry that was already finalized. Not in the registry means it doesn't exist, as far as I'm concerned, compiled class or not.

The mechanism

Five steps, and only one of them decides whether your class ever gets a vote.

  1. The JVM loads OopFundamentalsApplication and every class it can reach — plain Java classloading, nothing Spring-specific yetcompiling and loading aren't "registered"
  2. SpringApplication.run() starts, and @ComponentScan (bundled inside @SpringBootApplication) walks the main class's package and every sub-packagea directory walk, not a classpath-wide search
  3. For each class found, it checks for @Component or any annotation itself meta-annotated with it — @Service, @Repository, @Controller, @Configurationthe actual filter
  4. Matching classes become BeanDefinitions — metadata describing how to construct them, not yet actual objectsa blueprint, not an instance
  5. @EnableAutoConfiguration separately adds its own conditional BeanDefinitions based on what's on the classpath — a DataSource bean only if a JDBC driver is present, saya parallel source of beans, same registry
  6. The ApplicationContext resolves the whole dependency graph, instantiating beans in order — a constructor asking for a type with zero matching BeanDefinitions fails right here, before Tomcat ever startsthis is where "no bean of type X" gets thrown

Step 3 is the lesson. Everything upstream — the JVM loading your class, the file compiling cleanly — is necessary but nowhere near sufficient. A class only enters Spring's world the moment component scanning recognizes one specific kind of annotation on it. Skip that annotation and every later step proceeds as if the file were simply absent.

Four classes, one sweep, one skipped — and the skip is silent. Component scanning never warns "I found a class that looks like it should probably be a bean." It simply doesn't register it, and the first sign of trouble is a constructor somewhere else failing to find what it asked for.

EmailServiceImpl lives in com.bob.oopfundamentals.integrations.email and is correctly annotated @Service. The main class, OopFundamentalsApplication, lives in com.bob.oopfundamentals.app — a sibling package, not a parent of integrations.email. Startup still fails with "no bean of type EmailService found." What's actually wrong?

A reasonable first guess, since a missing or misspelled @Service is the single most common cause of this message — but the scenario already states the annotation is present and correct. The same error message can have more than one cause, and "check the annotation again" stops being useful once you've actually checked it.

Right — @ComponentScan (bundled into @SpringBootApplication) defaults to scanning the main class's package and everything beneath it, never upward and never sideways. A sibling package sits completely outside that tree, so the class stays invisible no matter how correctly it's annotated. The fix is moving the main class to the shared top-level package, or adding an explicit @ComponentScan(basePackages="com.bob.oopfundamentals") to widen the search.

@ComponentScan is configured on the class doing the scanning — your @SpringBootApplication main class — to say where to look. It's never placed on the class being found, which has no say in whether it gets scanned. This answer has the direction of control backwards.

Where you've seen this before

"On the classpath" has never meant "known to the framework" — you've hit this exact shape before.

Angular's @Injectable() — the identical two-step requirement

Angular's dependency injection has almost the exact same rule: a class needs @Injectable() (or to be registered as a provider some other way) before Angular's injector will construct and inject it. A plain, correctly written TypeScript class sitting in the same folder, undecorated, is exactly as invisible to Angular's injector as an unannotated POJO is to Spring's component scan — both throw a "no provider found" error that points at the missing decorator, not at anything wrong with the class itself.

@Injectable() ≈ @Service

Flask/FastAPI routes that are never registered

A route function decorated correctly but never passed to app.include_router(...) (or an un-registered Flask blueprint) is dead code, no matter how correctly it's written — the framework only knows about routes explicitly handed to it. Different mechanism from annotation-driven scanning, but the same underlying lesson: "written correctly" and "known to the framework" are separate facts, and the second one is never assumed for free.

registered explicitly, or it's dead code

Add spring-boot-starter-security and everything locks, on purpose

The first time most people add the security starter to a CIAM project, every endpoint suddenly demands a login — including ones nobody secured yet — because Spring Security's auto-configuration default posture is "require authentication for everything" the moment it detects itself on the classpath, until you supply your own SecurityFilterChain. It's the same "presence changes behavior automatically" theme as component scanning, aimed at the opposite failure mode: too much locked down by default, instead of too little discovered.

Questions from the back row

Why does Spring even need @Service/@Component — why not scan every class and guess which ones look like services?

Because "looks like a service" isn't decidable in general — plenty of classes are plain data holders, static-method utility classes, or DTOs that should never be instantiated by a DI container. An explicit annotation is a contract: "yes, construct me, manage my lifecycle, wire my dependencies." Guessing would mean Spring occasionally deciding to manage a class you never intended as a bean — a far stranger failure mode than "I forgot one annotation."

Does component scanning slow down startup on a big codebase?

A little, but it's a one-time cost paid once at boot, and it's rarely the actual bottleneck people assume — the classpath walk itself is fast compared to instantiating beans, running auto-configuration's conditionals, and opening a database connection pool. If startup time genuinely matters (serverless cold starts, for instance), the bigger lever is usually lazy initialization (spring.main.lazy-initialization=true) or AOT/native compilation, not narrowing the scan.

What's the actual difference between @Component, @Service, and @Repository, if they all register the same way?

Functionally, almost nothing for basic wiring — all three ARE @Component underneath, and component scan treats them identically. The difference is meaning plus one real behavior: @Repository additionally enables Spring's exception translation, turning a driver-specific SQLException into a consistent DataAccessException. @Service and @Controller exist mainly to document intent — business logic versus web layer. Using the specific one over the generic one costs nothing and tells the next reader exactly what the class is for.

2 — @SpringBootApplication Breakdown

@SpringBootApplication is a convenience annotation that combines three annotations. Click each to see what it does.

@SpringBootApplication
Shorthand for: @SpringBootConfiguration + @EnableAutoConfiguration + @ComponentScan.
Put this on your main class — the one with public static void main().
@SpringBootConfiguration
Marks this class as a configuration source (like @Configuration). Spring Boot can use it to define additional @Bean methods. Usually you just inherit this via @SpringBootApplication.
@EnableAutoConfiguration
Tells Spring Boot to automatically configure your app based on what's on the classpath. This is the "magic" — it reads spring.factories / AutoConfiguration.imports files inside every starter JAR and activates relevant configurations conditionally.
@ComponentScan
Scans the package of the annotated class (and all sub-packages) for Spring-managed beans: @Component, @Service, @Repository, @Controller, @RestController, and any custom stereotype annotations. Tip: put your main class at the top-level package so it scans everything.

🌱 New to Spring Boot? It's "Spring with the wiring already done."

Plain Spring made you configure everything by hand. Spring Boot looks at what libraries are on your classpath and auto-configures sensible defaults — an embedded web server, JSON handling, a database connection — so a running web app is one main() away. The idea you'll meet over and over: you write plain classes and annotate them (@RestController, @Service, @Repository), and Spring creates and connects them for you in a "container." You write the logic; the framework does the plumbing. That's why a tiny Boot app does so much with so little code.

🧠 Expert corner — layers, the container, and the auto-config magic

  • The standard shape is layered: @RestController (HTTP) → @Service (business logic + @Transactional) → @Repository (data). Keep controllers thin and rules in the service.
  • @SpringBootApplication is three annotations — @Configuration + @EnableAutoConfiguration + @ComponentScan. Component-scan finds your beans; auto-config supplies the framework ones.
  • Auto-configuration is conditional. Starters (spring-boot-starter-web, …) put libraries on the classpath; auto-config classes use @ConditionalOnClass/@ConditionalOnMissingBean to wire defaults you can always override. (See Auto-Configuration Magic.)
  • The IoC container owns object creation. Beans are wired by dependency injection — you ask for collaborators in the constructor, Spring provides them.
  • Config is externalized via application.yml + profiles, and ops via Actuator — so the same jar runs in dev and prod.
  • CIAM tie-in. Adding spring-boot-starter-oauth2-resource-server + an issuer-uri auto-configures JWT validation — no manual filter wiring. See Security.
