Dynamic Components — createComponent & ViewContainerRef

Dynamic components let you create and insert Angular components at runtime — no static template references required. This is the foundation of modals, notifications, plugin systems, and low-code builders.

🧩 What are dynamic components — and why do modals, toasts, and plugins need them?

Most components are statically declared in a template — <app-user-detail [user]="u"> — so Angular knows at compile time what goes where. Dynamic components are created at runtime in response to events: you can't pre-declare 0…N toasts, every possible modal, or unknown plugin UIs in a template. The API is ViewContainerRef.createComponent(ComponentClass) — it builds the component, inserts it into the DOM, attaches it to change detection, and returns a ComponentRef to talk to it. Call ref.destroy() and Angular cleans it up.

  • Use them when the number or type of components isn't known at compile time — toasts, modals, wizards, plugin slots.
  • ViewContainerRef is a DOM insertion point; an empty <ng-container> read via @ViewChild(..., { read: ViewContainerRef }) is the usual host.
  • createComponent(C) returns a ComponentRef<C>; pass data with ref.setInput('x', v) (signal-friendly), read outputs via ref.instance.event.subscribe(...).
  • createEmbeddedView(templateRef, ctx) stamps an <ng-template> instead — exactly how *ngIf/*ngFor work internally.
  • Always destroy() when done — it runs ngOnDestroy, unsubscribes, and removes the DOM; forgetting leaks.

createComponent API

A root ModalService holds a ViewContainerRef and exposes open(C, data?) → const ref = vcr.createComponent(C); Object.assign(ref.instance, data); return ref; and close(ref) → ref.destroy(). Call: modal.open(ConfirmDialogComponent, { message: 'Delete user?' }).

ng-container + ViewContainerRef

<ng-container #hostEl></ng-container> renders no element — a pure placeholder. Inject it via @ViewChild('hostEl', { read: ViewContainerRef }). createComponent() appends; call clear() first to replace.

ComponentRef communication

Set inputs with ref.setInput('title', '…') (preferred in 17+; tracks signals). Listen: ref.instance.confirmed.subscribe(ok => { … }). In zoneless, nudge with ref.changeDetectorRef.detectChanges(). Tear down with ref.destroy().

In CIAM / Angular:a confirm-before-delete modal opened on demand (modal.open(ConfirmUserDeleteComponent); ref.setInput('user', selected); ref.instance.confirmed.subscribe(ok => ok && userService.delete(selected.id))); toast notifications for API results (auto-destroy after 3s); a bulk-import progress component wired to Spring's SSE /api/import/progress — none of which belong in a static template.

What are dynamic components?

  

    
In most Angular code you reference components statically in templates: <app-user-card />. Angular knows at compile time exactly which component to render. Dynamic components flip this: you decide which component class to instantiate and where to put it entirely at runtime, in TypeScript code.

    
The host element for a dynamic component is usually an <ng-container> or a dedicated anchor element — a placeholder that Angular can reach via ViewContainerRef.

    

      Key insight: Angular's rendering engine treats dynamic components identically to static ones. They participate in change detection, they have the same full lifecycle (ngOnInit, ngOnDestroy …), they can use dependency injection, and they emit events just like any other component. The only difference is how they are created.
    

    
// Static — Angular handles creation at compile time
<app-alert message="Hello" />

// Dynamic — YOU create it at runtime in TypeScript
const ref = this.viewContainerRef.createComponent(AlertComponent);
ref.setInput('message', 'Hello');

  


  
  
When do you need dynamic components?

  

    

      
Modal dialogs

      
A DialogService.open(MyFormComponent) call creates any component inside a modal overlay without pre-declaring it in a template.

    

    

      
Toast / notifications

      
A ToastService.show('Saved!') appends a toast component to a top-level container and destroys it after a timeout.

    

    

      
Plugin systems

      
Load a component class lazily from a route or feature module, then render it without knowing its type at compile time.

    

    

      
Drag-and-drop builders

      
A visual page builder drops different widget components (cards, charts, forms) into a canvas based on the user's actions.

    

    

      
Tooltip / popover systems

      
A directive creates a tooltip component next to the host element, positions it, then destroys it on mouse-leave.

    

    

      
Tab systems

      
Each tab renders a different component class. Switching tabs destroys the old component and creates a new one, controlling memory carefully.

    

  


  
  
The old way: ComponentFactoryResolver (Angular ≤12)

  

    
Before Angular 13, creating a dynamic component required asking ComponentFactoryResolver to produce a factory for your component class, then calling viewContainerRef.createComponent(factory). This was verbose and required the component to be listed in entryComponents in the module (removed in Ivy).

    
Deprecated. Do not use this pattern in new code. It is shown here only for maintaining legacy codebases.

    
// LEGACY — Angular 12 and below (do not use in new code)
@Component({ ... })
export class HostComponent {
  @ViewChild('anchor', { read: ViewContainerRef })
  anchor!: ViewContainerRef;

  constructor(private cfr: ComponentFactoryResolver) {}

  createAlert() {
    // Step 1: resolve a factory for the component class
    const factory = this.cfr.resolveComponentFactory(AlertComponent);
    // Step 2: create via the factory — verbose!
    const ref = this.anchor.createComponent(factory);
    // Step 3: set inputs directly on the instance
    ref.instance.message = 'Hello from legacy';
    ref.instance.ngOnChanges(); // had to trigger change detection manually!
  }
}

  


  
  
Modern way: ViewContainerRef.createComponent() (Angular 13+)

  

    
Angular 13 introduced the ability to pass the component class directly to createComponent(). No factory resolver needed. Combined with standalone components, this is clean and minimal.


    
Getting a ViewContainerRef

    
There are two ways to get a ViewContainerRef:

    

      

        
Option A — inject in constructor

        
The injected VCR is scoped to the component's host element. Dynamic children appear inside the host.

        
constructor(private vcr: ViewContainerRef) {}

      

      

        
Option B — @ViewChild on ng-container

        
Use a template anchor for precise placement. read: ViewContainerRef is required.

        
<ng-container #anchor />

@ViewChild('anchor', { read: ViewContainerRef })
anchor!: ViewContainerRef;

      

    


    
Full createComponent() workflow

    
import { ViewContainerRef, ComponentRef } from '@angular/core';
import { AlertComponent } from './alert.component';

@Component({
  selector: 'app-host',
  template: `<ng-container #anchor />`,
  standalone: true,
})
export class HostComponent {
  @ViewChild('anchor', { read: ViewContainerRef, static: true })
  anchor!: ViewContainerRef;

  alertRef?: ComponentRef<AlertComponent>;

  showAlert(msg: string) {
    // 1. Create the component — Angular handles everything
    this.alertRef = this.anchor.createComponent(AlertComponent);

    // 2. Pass inputs using setInput() — triggers change detection
    this.alertRef.setInput('message', msg);
    this.alertRef.setInput('type', 'warning');

    // 3. Access the instance directly if needed
    this.alertRef.instance.dismissed.subscribe(() => this.dismiss());
  }

  dismiss() {
    this.alertRef?.destroy(); // removes from DOM + calls ngOnDestroy
  }
}

  


  
  
ComponentRef<T> API

  

    

      
MemberTypeDescription

      
        
.instanceTDirect reference to the component class instance. Use to call methods or access properties.

        
.setInput(name, value)voidPasses a value to an @Input(). Preferred over .instance.prop = x because it triggers OnPush change detection correctly.

        
.hostViewViewRefThe view that wraps the component. Can be attached/detached from the application's change detection tree.

        
.locationElementRefReference to the host DOM element. Useful for positioning (tooltips, popovers).

        
.destroy()voidDestroys the component: calls ngOnDestroy, removes from the DOM, detaches from change detection. Always call this to prevent memory leaks.

        
.changeDetectorRefChangeDetectorRefManually trigger change detection on this component's subtree (useful for OnPush components).

      
    

    

      setInput() vs instance.prop: When using OnPush change detection, ref.instance.prop = x does not trigger a re-render. Always use ref.setInput('prop', x) — it correctly marks the component as dirty.
    

  


  
  
NgComponentOutlet — declarative dynamic components

  

    
NgComponentOutlet is a directive that wraps the createComponent API in a declarative template syntax. When the bound class changes, Angular destroys the old instance and creates a new one automatically.

    

      

        
Basic usage

        
<ng-container
  [ngComponentOutlet]="activeComponent"
/>

// In the component class:
activeComponent = AlertComponent;

switchToForm() {
  this.activeComponent = FormComponent;
}

      

      

        
With inputs (Angular 16+)

        
<ng-container
  [ngComponentOutlet]="activeComponent"
  [ngComponentOutletInputs]="{ message: 'Hi!', type: 'info' }"
/>

        
The inputs object is passed to setInput() for each key. Automatically updated when the object changes.

      

    

    
Content projection with NgComponentOutlet

    
<ng-container
  [ngComponentOutlet]="modalComponent"
  [ngComponentOutletContent]="projectedContent"
/>

// projectedContent is an array of TemplateRef[] or Node[][]
// Passed to the component's ng-content slots in order

  


  
  
Dynamic components with Signals & setInput()

  

    
When a component uses signal-based inputs (the input() function from Angular 17+), ComponentRef.setInput() still works exactly the same — Angular bridges the gap. The component's input() signal updates reactively.

    
// The dynamic component uses signal inputs
@Component({ standalone: true, ... })
export class AlertComponent {
  message = input<string>('');        // signal input
  type    = input<string>('info');   // signal input with default
  upper   = computed(() => this.message().toUpperCase());
}

// The host creates it and pushes values via setInput()
const ref = vcr.createComponent(AlertComponent);
ref.setInput('message', 'Operation complete');  // updates the signal!
ref.setInput('type', 'success');

// Later, update reactively:
ref.setInput('message', 'Still processing…'); // computed 'upper' updates too

  


  
  
Injector context: scoped providers

  

    
By default, a dynamically created component inherits the parent's injector. You can pass a custom injector to provide different (or scoped) services to the dynamic component — without polluting the global provider tree.

    
import { Injector, createEnvironmentInjector } from '@angular/core';

@Component({ ... })
export class HostComponent {
  constructor(
    private vcr: ViewContainerRef,
    private envInjector: EnvironmentInjector
  ) {}

  openScopedDialog() {
    // Create a child injector that overrides a service for this instance
    const scopedInjector = createEnvironmentInjector(
      [{ provide: ThemeService, useValue: new ThemeService('dark') }],
      this.envInjector
    );

    const ref = this.vcr.createComponent(DialogComponent, {
      environmentInjector: scopedInjector,  // scoped providers!
    });
  }
}

    
Use case: A multi-tenant SaaS where each dynamically opened panel needs its own isolated TenantService instance.

  


  
  
Content projection in dynamic components

  

    
You can project DOM nodes into a dynamic component's ng-content slots by passing a projectableNodes array to createComponent(). Each element in the array corresponds to one <ng-content> slot.

    
// The dynamic component has two content slots
@Component({
  template: `
    <div class="header"><ng-content select="[slot=header]" /></div>
    <div class="body"><ng-content /></div>
  `
})
export class PanelComponent {}

// The host creates projected nodes from a template
@ViewChild('headerTpl') headerTpl!: TemplateRef<any>;

open() {
  const headerView = this.headerTpl.createEmbeddedView({});
  const ref = this.vcr.createComponent(PanelComponent, {
    projectableNodes: [headerView.rootNodes],   // → first ng-content
  });
}

  


  
  
Real-world pattern: Modal Service

  

    
The most common use of dynamic components. A DialogService injectable holds a reference to a top-level ViewContainerRef (set by the root app component) and creates any component inside an overlay.

    
// dialog.service.ts
@Injectable({ providedIn: 'root' })
export class DialogService {
  private vcr!: ViewContainerRef;
  private overlayRef?: ComponentRef<OverlayComponent>;

  registerContainer(vcr: ViewContainerRef) { this.vcr = vcr; }

  open<T>(component: Type<T>, inputs?: Partial<T>): ComponentRef<T> {
    // 1. Create the backdrop overlay
    this.overlayRef = this.vcr.createComponent(OverlayComponent);

    // 2. Create the content component inside the overlay
    const dialogRef = this.overlayRef.instance.innerVCR.createComponent(component);

    // 3. Set inputs
    if (inputs) {
      Object.entries(inputs).forEach(([k, v]) => dialogRef.setInput(k, v));
    }
    return dialogRef;
  }

  close() { this.overlayRef?.destroy(); }
}

// Usage anywhere in the app:
this.dialogService.open(UserEditFormComponent, { userId: 42 });

  


  
  
Real-world pattern: Toast / Notification Service

  

    
@Injectable({ providedIn: 'root' })
export class ToastService {
  private containerVCR!: ViewContainerRef;

  show(message: string, type: 'success' | 'error' = 'success') {
    const toastRef = this.containerVCR.createComponent(ToastComponent);
    toastRef.setInput('message', message);
    toastRef.setInput('type', type);

    // Auto-destroy after 3 seconds
    setTimeout(() => toastRef.destroy(), 3000);
  }
}

  


  
  
Real-world pattern: Tab System

  

    
@Component({
  template: `
    <div class="tab-bar">
      <button *ngFor="let tab of tabs" (click)="activate(tab)">{{ tab.label }}</button>
    </div>
    <ng-container #tabAnchor />
  `
})
export class TabContainerComponent {
  @ViewChild('tabAnchor', { read: ViewContainerRef }) anchor!: ViewContainerRef;

  tabs = [
    { label: 'Overview',  component: OverviewComponent  },
    { label: 'Settings',  component: SettingsComponent  },
    { label: 'Analytics', component: AnalyticsComponent },
  ];

  currentRef?: ComponentRef<any>;

  activate(tab: typeof this.tabs[0]) {
    this.currentRef?.destroy();        // destroy previous tab
    this.anchor.clear();               // clear the container
    this.currentRef = this.anchor.createComponent(tab.component);
  }
}

Interactive Demo: Dynamic Component Lifecycle

  

    
Step through the lifecycle of a dynamic component — from calling createComponent() to destroy(). Each step shows what Angular does internally and what you can do as the host.

    
    
    

      

        
1

        

          
createComponent(AlertComponent) called

          
Angular instantiates the component class, creates its host element, sets up change detection.

          
const ref = vcr.createComponent(AlertComponent);

        

      

      

        
2

        

          
Constructor & inject() run

          
Angular resolves all dependencies via the injector and calls the constructor.

          
constructor(private http: HttpClient) { ... }

        

      

      

        
3

        

          
setInput() — inputs are delivered

          
Host calls setInput() for each @Input. ngOnChanges fires for each change.

          
ref.setInput('message', 'Hello!'); // → ngOnChanges

        

      

      

        
4

        

          
ngOnInit runs

          
The component's ngOnInit lifecycle hook fires. Initial data fetching typically happens here.

          
ngOnInit() { this.loadData(); }

        

      

      

        
5

        

          
Component is visible — inserted into ViewContainerRef

          
The component's host element is inserted into the DOM at the ViewContainerRef anchor position. The user can now see and interact with it.

          
// Angular inserts ref.hostView into the DOM

        

      

      

        
6

        

          
Change detection runs normally

          
The dynamic component participates in Angular's change detection like any static component. setInput() or signals trigger re-renders.

          
ref.setInput('count', 99); // triggers re-render

        

      

      

        
7

        

          
ref.destroy() — cleanup

          
Host calls destroy(). Angular runs ngOnDestroy, unsubscribes all internal observables, removes the element from the DOM, and releases memory.

          
ref.destroy(); // ngOnDestroy → DOM removal → GC
