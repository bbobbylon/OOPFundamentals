SQL — Joins, Transactions & Indexes

Tables hold rows. Joins combine rows from multiple tables. Indexes are how databases find anything fast. Transactions are how you stay consistent under failure.

What is SQL — Joins, Transactions & Indexes at a glance?

SQL (Structured Query Language) is the universal language for interacting with relational databases. Every web application stores its persistent data — users, orders, sessions, audit logs — in relational database tables, and SQL is how you get that data in and out. This visualizer focuses on three fundamental pillars. Joins: the mechanism for combining rows from multiple tables. Data is split across tables for normalization (reducing redundancy), but queries often need data from several tables simultaneously. INNER JOIN returns rows that match in BOTH tables. LEFT JOIN returns ALL rows from the left table and NULLs where the right has no match — essential when you want "all users, even those with no orders." RIGHT JOIN is the mirror. FULL OUTER JOIN returns everything. The join condition (ON users.id = orders.user_id) is the foreign key relationship. Indexes: database indexes are like a book's index — instead of reading every row (sequential scan), the database jumps directly to matching rows. A B-tree index on email makes WHERE email = 'bob@eg.com' go from scanning 10 million rows to reading ~3 B-tree nodes. The cost: every INSERT/UPDATE/DELETE must also update all indexes — so over-indexing slows writes. Transactions: a transaction groups multiple SQL statements that must ALL succeed or ALL fail together. BEGIN...COMMIT. If any statement fails mid-transaction, ROLLBACK undoes everything. This is ACID guarantees: Atomicity (all-or-nothing), Consistency (constraints enforced), Isolation (concurrent transactions don't interfere), Durability (committed data survives crashes). Spring Boot's @Transactional annotation manages transactions automatically.

JOIN types

-- INNER JOIN: only matching rows SELECT u.email, o.total FROM users u INNER JOIN orders o ON u.id = o.user_id; -- users with NO orders: excluded -- LEFT JOIN: all users, even with no orders SELECT u.email, o.total FROM users u LEFT JOIN orders o ON u.id = o.user_id; -- users with no orders: total = NULL -- Multi-table JOIN: SELECT u.email, r.role_name FROM users u JOIN user_roles ur ON u.id = ur.user_id JOIN roles r ON ur.role_id = r.id WHERE r.role_name = 'CIAM_ADMIN';

Indexes

-- Without index: FULL TABLE SCAN -- With 10M rows: ~500ms SELECT * FROM users WHERE email = 'bob@eg.com'; -- Add index: CREATE UNIQUE INDEX ON users (email); -- With index: B-tree lookup -- ~3 node reads: <1ms SELECT * FROM users WHERE email = 'bob@eg.com'; -- Check what the planner does: EXPLAIN ANALYZE SELECT * FROM users WHERE email = 'bob@eg.com'; -- Look for: Index Scan using idx_users_email -- Not: Seq Scan on users (bad!) -- Composite index for multi-column filter: CREATE INDEX ON sessions (user_id, expires_at);

Transactions

-- Explicit transaction: BEGIN; INSERT INTO users (email) VALUES ('bob@eg.com'); INSERT INTO user_roles (user_id, role_id) VALUES (lastval(), 1); -- If role insert fails → ROLLBACK -- No orphaned user without a role COMMIT; -- Spring @Transactional: @Transactional public User createUser(CreateUserRequest req) { User user = userRepo.save(new User(req.email())); // Spring starts BEGIN here (via proxy) roleRepo.save(new UserRole(user, defaultRole)); auditRepo.save(new AuditEvent(user, "CREATED")); return user; // COMMIT when method returns normally // ROLLBACK if RuntimeException thrown }

In your CIAM stack: JOINs are used constantly in CIAM: get a user's roles (JOIN users → user_roles → roles), get a user's active sessions (JOIN users → sessions WHERE expires_at > NOW()), get audit trail with user details (JOIN audit_events → users). Indexes are critical: index on users.email (login lookup), sessions.token_hash (token validation on every API call — must be milliseconds), user_roles.user_id (load roles on every auth check). Transactions prevent partial state: user provisioning (create user + assign roles + log audit event), role assignment (update user + log who changed what), session creation (create session + invalidate old sessions atomically). Spring Boot's @Transactional on your service methods handles all of this — but understanding the underlying SQL is essential for debugging, performance tuning, and writing complex queries that JPA can't express.

The five basic JOINs explained

JOIN typeWhat you getWhen you use it
INNER JOIN Only rows that match in BOTH tables. Drops anything without a partner. "Show orders along with their user" — only complete pairs.
LEFT JOIN All rows from LEFT table; NULL on the right where no match. "Show all users, with orders if any" — keep users with zero orders.
RIGHT JOIN All rows from RIGHT table; NULL on the left where no match. Rare — usually rewritten as LEFT JOIN with tables swapped.
FULL OUTER JOIN All rows from BOTH tables; NULLs where no match on either side. "Find users without orders AND orders without users (orphans)."
CROSS JOIN Every row of A paired with every row of B (cartesian product). Generating combinations, calendar × users, sparse → dense reports.

The Big Three SQL clauses, in execution order

SQL is written in one order, but the database executes it in a different order. Memorizing this fixes 90% of beginner confusion. 

// Written like this:
SELECT   name, COUNT(o.id)         // 6th
FROM     users u                  // 1st — source tables
LEFT JOIN orders o ON u.id = o.user_id  // 2nd — join
WHERE    u.country = 'US'          // 3rd — filter rows BEFORE grouping
GROUP BY u.id, u.name             // 4th — group
HAVING   COUNT(o.id) > 0          // 5th — filter GROUPS
ORDER BY name                     // 7th — sort the result
LIMIT    10;                      // 8th — slice

Common gotcha: aliases defined in SELECT (the 6th step) aren't usable in WHERE (3rd step). Use the full expression in WHERE, or filter in a subquery / CTE.

Indexes — how databases find things fast

Without an index, WHERE email = 'b@b.com' on a million-row table is a full table scan — read every row. With a B-tree index on email, it's a few hops, like binary search. 

CREATE INDEX idx_users_email ON users(email);  // O(log n) lookup

// composite index — order matters!
CREATE INDEX idx_user_status_created ON users(status, created_at);
//   ↑ helps WHERE status=X, WHERE status=X AND created_at>Y, NOT WHERE created_at>Y alone

✅ Index when

Column is in WHERE / JOIN / ORDER BY of frequent queries. Foreign keys (most databases don't auto-index those).

🚫 Don't index when

Table is small (<1000 rows — scan is faster than index lookup). Column has low cardinality (boolean, status enum — index is barely better than scan). Write-heavy and read-rare.

⚖️ The cost

Indexes take disk space and slow down INSERT / UPDATE / DELETE (every change updates every index on the table). Don't add them just because you can.

🔍 EXPLAIN is your friend

EXPLAIN SELECT ... shows whether your query uses an index or does a sequential scan. Look for "Seq Scan" on big tables — usually a missed index.

ACID — what databases promise you

🅰️ Atomicity

A transaction either fully commits or fully rolls back. No partial state. Transfer $100 from A to B: both debit and credit happen, or neither does.

🅒 Consistency

Constraints (PK, FK, CHECK) hold before and after. If the schema says "balance ≥ 0", no transaction leaves the DB in a state that violates it.

🅘 Isolation

Concurrent transactions don't see each other's half-done work. Levels exist (READ COMMITTED, REPEATABLE READ, SERIALIZABLE) — higher = safer = slower.

🅓 Durability

Once committed, the data survives crashes. Achieved by writing to a Write-Ahead Log (WAL) before acknowledging the commit. fsync'd to disk.

The N+1 query problem (kill it on sight)

// ❌ N+1 — one query to load users, then ONE query PER USER to load orders
List<User> users = userRepo.findAll();        // 1 query
for (User u : users) {
    u.getOrders().size();                  // N queries — one per user!
}
// 100 users? 101 queries. 1000 users? 1001 queries. Production-killer.

// ✅ FIX 1 — JOIN FETCH in the query
@Query("SELECT u FROM User u LEFT JOIN FETCH u.orders")
List<User> findAllWithOrders();

// ✅ FIX 2 — explicit IN query
SELECT * FROM orders WHERE user_id IN (1, 2, 3, ...);  // 1 query for all

SQL injection — never concatenate user input

// ❌ String concatenation — RCE waiting to happen
String sql = "SELECT * FROM users WHERE name = '" + name + "'";
// caller sends name = "'; DROP TABLE users; --"  →  💀

// ✅ Prepared statement — parameter is data, not code
PreparedStatement ps = conn.prepareStatement(
    "SELECT * FROM users WHERE name = ?");
ps.setString(1, name);   // driver escapes it safely
ResultSet rs = ps.executeQuery();

Always use parameterized queries. Frameworks (Hibernate, JOOQ, Spring Data) do this for you — but if you ever drop down to raw JDBC, make sure to use ? placeholders, never string concatenation.

The Java side — JDBC in 60 seconds

try (Connection c = DriverManager.getConnection(url, user, pw);
     PreparedStatement ps = c.prepareStatement(
         "INSERT INTO orders (user_id, amount) VALUES (?, ?)",
         Statement.RETURN_GENERATED_KEYS)) {

    c.setAutoCommit(false);                 // start a transaction
    try {
        ps.setLong(1, userId);
        ps.setBigDecimal(2, amount);
        ps.executeUpdate();

        try (ResultSet keys = ps.getGeneratedKeys()) {
            keys.next();
            long orderId = keys.getLong(1);
        }

        c.commit();
    } catch (SQLException e) {
        c.rollback();                          // undo everything
        throw e;
    }
}  // connection auto-closed by try-with-resources
