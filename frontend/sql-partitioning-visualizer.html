Partitioning & Sharding

Splitting one giant table into manageable pieces — and the point where "pieces of one table" becomes "pieces on different machines."

🧩 Same table, split how — and split across what?

Partitioning splits one logical table into multiple physical storage units (partitions) that still live on the same database server and are queried through the same parent table name — Postgres' planner decides which partitions a given query actually needs to touch, a step called partition pruning. Split by a range (dates, IDs) and a query with a matching filter can skip nearly every partition it doesn't need; split by a hash of some column and rows spread evenly, but pruning only works if the query filters on that exact hash key — filter on anything else and every partition gets scanned, which is strictly worse than not partitioning at all. Partitioning solves an I/O and maintenance problem on a single box (smaller indexes, cheap bulk-drop old partitions, targeted vacuum); it does nothing for a table that has simply outgrown what one machine's CPU, RAM, or disk throughput can serve. Sharding is the answer to that: the same "split by a key" idea, but the pieces live on entirely separate database instances, with a routing layer deciding which shard owns a given row. The two combine in practice — each shard is usually partitioned internally too — but sharding introduces a cost partitioning never has: a query that can't be answered from a single shard has to fan out to all of them and merge results in the application, which is exactly the trade you're making when you pick a shard key.

  • Partitioning — one table, many physical pieces, still one server; the planner prunes irrelevant pieces automatically if the query filters on the partition key.
  • Partition pruning — the whole performance win; lose the partition-key filter and you're scanning every partition, worse than an unpartitioned table.
  • Sharding — the same idea across servers, not just files; solves capacity, not just I/O.
  • Cross-shard queries — anything that can't be answered by one shard requires a scatter-gather fan-out; the shard key you choose decides how often that happens.

Declarative range partitioning

CREATE TABLE orders ( id bigint, customer_id bigint, created_at date, total numeric ) PARTITION BY RANGE (created_at); CREATE TABLE orders_2026_01 PARTITION OF orders FOR VALUES FROM ('2026-01-01') TO ('2026-02-01'); CREATE TABLE orders_2026_02 PARTITION OF orders FOR VALUES FROM ('2026-02-01') TO ('2026-03-01'); -- old data ages out in O(1): DROP TABLE orders_2024_01;

Hash partitioning

CREATE TABLE events ( id bigint, customer_id bigint, payload jsonb ) PARTITION BY HASH (customer_id); CREATE TABLE events_p0 PARTITION OF events FOR VALUES WITH (MODULUS 4, REMAINDER 0); CREATE TABLE events_p1 PARTITION OF events FOR VALUES WITH (MODULUS 4, REMAINDER 1); -- ...p2, p3 -- pruned (filters the hash key): SELECT * FROM events WHERE customer_id = 88; -- NOT pruned (no hash-key filter): SELECT * FROM events WHERE payload->>'type'='login';

Shard routing (application layer)

int shardCount = 8; int shardFor(long customerId) { return (int) Math.floorMod( Long.hashCode(customerId), shardCount); } DataSource ds = shardDataSources .get(shardFor(customerId)); // a query keyed on customer_id hits ONE // shard; a query NOT keyed on it (e.g. // "top orders this week, all customers") // must fan out to all 8 and merge

Partitioning in a CIAM stack: a login_events or audit_log table is the textbook range-partitioning case — partition by month, keep 90 days queryable, and DROP (not DELETE) the partitions older than your retention policy in O(1) instead of a table-locking bulk delete. If you ever shard users across tenants, shard by tenant_id, not by user_id — nearly every CIAM query (login, session list, permission check) is scoped to one tenant, so tenant_id as the shard key keeps almost everything single-shard; user_id as the shard key would force cross-shard fan-out on routine tenant-wide admin queries.

or, the id column that stopped meaning what everyone assumed

The problem

Postgres won't even let you keep your old primary key once you partition the table.

ERROR: unique constraint on partitioned table must include all partitioning columns

You take an existing orders(id bigserial PRIMARY KEY, customer_id, created_at, total) table and add PARTITION BY RANGE (created_at) because this page already sold you on it — range partitioning by date, drop old partitions in O(1). You try to keep the schema otherwise identical: PRIMARY KEY (id), same as before. Postgres refuses to create it. Not a warning — a hard error at CREATE TABLE time.

The fix everyone reaches for is obvious: make the key composite, PRIMARY KEY (id, created_at). Postgres accepts it immediately, and it feels like you're done. But that fix quietly changes what "unique" means: uniqueness is only enforced within each partition's own local index, never across the whole table. Nothing stops id = 42 from existing in both orders_2026_01 and orders_2026_03 at once — two completely different orders, same id, and Postgres considers both perfectly valid.

added the partition key to the primary key, as required ✓ CREATE TABLE succeeds, no more errors ✓ id alone no longer identifies a unique row anywhere in the table ⚠

Every step here was forced on you by Postgres's own rule, followed correctly. The surprise is what the rule quietly gives up in exchange: your "primary key" moved from guaranteeing one thing (id is globally unique) to guaranteeing a weaker one (id is unique per date range) without changing its name.

Decide where global uniqueness actually has to live
Generate ids that are unique by construction, not by index ↓ a UUID, or a Snowflake-style id that encodes a timestamp/shard bit, is globally unique whether or not any single index ever sees every row — the partitioned composite key becomes a performance detail, not your only defense If you must keep a bigserial id, treat (id, created_at) as the real key everywhere ↓ every foreign key, every API lookup, every cache key has to carry BOTH columns from then on — "just look it up by id" quietly stopped being true the moment the table was partitioned Add an application-level or trigger-based global-uniqueness check only if you truly can't change either ↓ this reintroduces exactly the cross-partition coordination cost that made partitioning attractive in the first place — worth naming as a deliberate trade-off, not something you discover in an incident
The one-sentence rule. A unique or primary-key index on a partitioned table can only be enforced inside each partition's own local B-tree, so Postgres forces you to add the partition key to it — and that same forcing function quietly downgrades "globally unique" to "unique within one partition," under the identical constraint name.
Partitioning a table doesn't just split its ROWS across files — it can silently split what your primary key even means. The column is still called id. It stopped being a single source of truth the moment created_at joined it in the key.
You

I added created_at to the primary key like Postgres demanded. Why do I now have two rows with id=42?

Postgres

I never promised id=42 was unique across the whole table — only within whichever partition each row landed in. That was true the moment you made the key composite; it just wasn't obvious.

You

So the "primary key" on this table means something different now than it did before I partitioned it?

The composite index, per partition

Same name, smaller promise. I guard my own partition's rows. Nobody's watching across the boundary.

The mechanism

Follow one attempt to insert a duplicate id into two different partitions.

  1. orders is partitioned by range on created_at, key is (id, created_at)schema
  2. Row A: id=42, created_at='2026-01-15' lands in partition orders_2026_01insert 1
  3. That partition's own local unique index accepts it — no conflict therelocal check
  4. Row B: id=42, created_at='2026-03-02' is inserted later, months apartinsert 2
  5. Postgres routes it to a DIFFERENT partition, orders_2026_03, based on created_atrouting
  6. That partition has its OWN separate local index — it has never heard of the id=42 sitting in January's partition — so the insert succeedssilent duplicate

Step 6 is the whole gotcha. Nothing crashed, nothing warned — two genuinely different physical B-tree indexes, one per partition, each faithfully enforced uniqueness within its own file and had no way to know about the other one's contents.

All three attempts — a plain primary key, a plain unique constraint, a foreign key target — run into the identical wall from three different angles, because they all reduce to "can one index enforce a rule across every partition," and a partitioned table's indexes are local by construction. There's no version of "just add a constraint" that sidesteps this.

You partition orders by range on created_at. Postgres refuses PRIMARY KEY (id) alone, so you change it to PRIMARY KEY (id, created_at) and the table creates successfully. What does that composite key actually guarantee now?

This is the trap — the syntax accepting your change reads as "problem solved," but a partitioned table's unique/PK indexes are built per-partition. Adding created_at to the key didn't preserve the old global guarantee; it's what let Postgres accept a constraint that only checks each partition on its own.

Right. Each partition maintains its own local B-tree for that composite key. Two rows with the same id but different created_at values route to different partitions, and neither partition's index has any visibility into the other's contents — so the same id can exist more than once in the table as a whole.

Postgres does not maintain any hidden cross-partition index for you. If you need a table-wide uniqueness guarantee on just id, you have to build it yourself — a globally-unique id generation scheme, or accept that "unique" now means "unique per partition" and design around it.

Where you have seen this before

"The same constraint name, a smaller guarantee" turns up anywhere data gets split.

Sharded databases and auto-increment ids

This page's own sharding section already warns that a query without the shard key has to fan out — the same root cause shows up here one level down: an auto-increment id generated independently per shard is unique per shard, never across shards, unless you switch to UUIDs or a Snowflake-style scheme up front.

partition-local uniqueness and shard-local uniqueness are the same bug at two different scales

Distributed CIAM identity — the same user_id across IDPs

Ping's internal id for a user and Entra's internal id for the "same" human are both locally unique within their own IDP and mean nothing across the boundary — which is exactly why a CIAM schema needs its own globally unique users.id plus an external_id per IDP link, rather than trusting either provider's id to be unique on its own.

"unique within my system" was never the same claim as "unique, period"

Kubernetes pod names versus deployment identity

A pod name is unique within its node/namespace at a point in time, but two different deployments can produce pods that look interchangeable from outside — the label selector, not the pod name, is the thing that's actually globally meaningful. Same pattern: the locally-unique identifier isn't automatically the globally-unique one.

always ask which scope a "unique" guarantee was actually checked at
The whole page on a napkin: partitioning splits one logical table into physical pieces on one server, with the planner pruning irrelevant pieces when a query filters on the partition key — lose that filter and every partition gets scanned, which sharding then repeats one level up across separate machines. The one new sentence this block adds: a unique or primary-key constraint on a partitioned table must include the partition key too, and that requirement quietly turns "globally unique" into "unique per partition" — the same id value can legally exist more than once in the table as a whole.

2 — Checking That Pruning Actually Happened




EXPLAIN SELECT * FROM orders
WHERE created_at >= '2026-01-01' AND created_at < '2026-02-01';

--                    QUERY PLAN
-- Append
--   ->  Seq Scan on orders_2026_01 orders
--         Filter: (created_at >= ... AND created_at < ...)
-- (1 partition touched out of 24 — the other 23 never opened)


If EXPLAIN shows every partition listed under Append, pruning did not happen — the filter doesn't match the partition key, or is wrapped in a function/cast the planner can't reason about at plan time.









3 — Sharding: the Router Owns the Decision




-- logical view: one "orders" table
-- physical reality: 8 independent Postgres instances

shard 0: customers where hash(customer_id) % 8 == 0
shard 1: customers where hash(customer_id) % 8 == 1
-- ... shard 7

-- a query WITH the shard key: 1 shard, fast
SELECT * FROM orders WHERE customer_id = 42;

-- a query WITHOUT it: fan out to all 8, merge in the app
SELECT * FROM orders WHERE total > 1000
ORDER BY created_at DESC LIMIT 10;
