Partitioning & Sharding

Splitting one giant table into manageable pieces — and the point where "pieces of one table" becomes "pieces on different machines."

🧩 Same table, split how — and split across what?

Partitioning splits one logical table into multiple physical storage units (partitions) that still live on the same database server and are queried through the same parent table name — Postgres' planner decides which partitions a given query actually needs to touch, a step called partition pruning. Split by a range (dates, IDs) and a query with a matching filter can skip nearly every partition it doesn't need; split by a hash of some column and rows spread evenly, but pruning only works if the query filters on that exact hash key — filter on anything else and every partition gets scanned, which is strictly worse than not partitioning at all. Partitioning solves an I/O and maintenance problem on a single box (smaller indexes, cheap bulk-drop old partitions, targeted vacuum); it does nothing for a table that has simply outgrown what one machine's CPU, RAM, or disk throughput can serve. Sharding is the answer to that: the same "split by a key" idea, but the pieces live on entirely separate database instances, with a routing layer deciding which shard owns a given row. The two combine in practice — each shard is usually partitioned internally too — but sharding introduces a cost partitioning never has: a query that can't be answered from a single shard has to fan out to all of them and merge results in the application, which is exactly the trade you're making when you pick a shard key.

  • Partitioning — one table, many physical pieces, still one server; the planner prunes irrelevant pieces automatically if the query filters on the partition key.
  • Partition pruning — the whole performance win; lose the partition-key filter and you're scanning every partition, worse than an unpartitioned table.
  • Sharding — the same idea across servers, not just files; solves capacity, not just I/O.
  • Cross-shard queries — anything that can't be answered by one shard requires a scatter-gather fan-out; the shard key you choose decides how often that happens.

Declarative range partitioning

CREATE TABLE orders ( id bigint, customer_id bigint, created_at date, total numeric ) PARTITION BY RANGE (created_at); CREATE TABLE orders_2026_01 PARTITION OF orders FOR VALUES FROM ('2026-01-01') TO ('2026-02-01'); CREATE TABLE orders_2026_02 PARTITION OF orders FOR VALUES FROM ('2026-02-01') TO ('2026-03-01'); -- old data ages out in O(1): DROP TABLE orders_2024_01;

Hash partitioning

CREATE TABLE events ( id bigint, customer_id bigint, payload jsonb ) PARTITION BY HASH (customer_id); CREATE TABLE events_p0 PARTITION OF events FOR VALUES WITH (MODULUS 4, REMAINDER 0); CREATE TABLE events_p1 PARTITION OF events FOR VALUES WITH (MODULUS 4, REMAINDER 1); -- ...p2, p3 -- pruned (filters the hash key): SELECT * FROM events WHERE customer_id = 88; -- NOT pruned (no hash-key filter): SELECT * FROM events WHERE payload->>'type'='login';

Shard routing (application layer)

int shardCount = 8; int shardFor(long customerId) { return (int) Math.floorMod( Long.hashCode(customerId), shardCount); } DataSource ds = shardDataSources .get(shardFor(customerId)); // a query keyed on customer_id hits ONE // shard; a query NOT keyed on it (e.g. // "top orders this week, all customers") // must fan out to all 8 and merge

Partitioning in a CIAM stack: a login_events or audit_log table is the textbook range-partitioning case — partition by month, keep 90 days queryable, and DROP (not DELETE) the partitions older than your retention policy in O(1) instead of a table-locking bulk delete. If you ever shard users across tenants, shard by tenant_id, not by user_id — nearly every CIAM query (login, session list, permission check) is scoped to one tenant, so tenant_id as the shard key keeps almost everything single-shard; user_id as the shard key would force cross-shard fan-out on routine tenant-wide admin queries.

2 — Checking That Pruning Actually Happened




EXPLAIN SELECT * FROM orders
WHERE created_at >= '2026-01-01' AND created_at < '2026-02-01';

--                    QUERY PLAN
-- Append
--   ->  Seq Scan on orders_2026_01 orders
--         Filter: (created_at >= ... AND created_at < ...)
-- (1 partition touched out of 24 — the other 23 never opened)


If EXPLAIN shows every partition listed under Append, pruning did not happen — the filter doesn't match the partition key, or is wrapped in a function/cast the planner can't reason about at plan time.









3 — Sharding: the Router Owns the Decision




-- logical view: one "orders" table
-- physical reality: 8 independent Postgres instances

shard 0: customers where hash(customer_id) % 8 == 0
shard 1: customers where hash(customer_id) % 8 == 1
-- ... shard 7

-- a query WITH the shard key: 1 shard, fast
SELECT * FROM orders WHERE customer_id = 42;

-- a query WITHOUT it: fan out to all 8, merge in the app
SELECT * FROM orders WHERE total > 1000
ORDER BY created_at DESC LIMIT 10;









4 — Spring Boot: Range-Partitioned Retention Job




@Scheduled(cron = "0 0 3 1 * *") // monthly, 3am
public void dropExpiredAuditPartitions() {
  LocalDate cutoff = LocalDate.now().minusMonths(RETENTION_MONTHS);
  String partition = "audit_log_" + cutoff.format(YYYYMM);
  jdbcTemplate.execute(
      "DROP TABLE IF EXISTS " + partition);
  // O(1) metadata operation — NOT a row-by-row DELETE,
  // no table bloat, no long-held locks on the live table
}
