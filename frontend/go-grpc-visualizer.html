Go: gRPC & Protocol Buffers

A typed contract in a .proto file, code generation into Go client + server stubs, the four RPC styles over HTTP/2, and interceptors + metadata for cross-cutting concerns like auth. See also: gRPC & Protocol Buffers (Spring) for the same protocol wired into a Spring Boot service with grpc-spring-boot-starter.

📡 What gRPC is, and why service-to-service calls use it instead of REST

gRPC is a contract-first RPC framework. You describe a service in a Protocol Buffers (.proto) file — the service, its methods, and message shapes with stable field numbers — and a generator (protoc/buf) turns it into a ready client and a server interface you implement. The wire format is binary protobuf over HTTP/2 (compact, multiplexed, streaming-capable). Four call types: unary, server-streaming, client-streaming, bidirectional. Cross-cutting concerns ride on interceptors (gRPC's middleware) and per-call metadata (its headers, carrying tokens/trace IDs); errors are typed status codes, not HTTP numbers. The payoff over REST: one source-of-truth contract, generated type-safe stubs that can't drift, smaller payloads, and first-class streaming — which is why it dominates internal traffic even when the public edge stays REST.

  • Contract-first .proto — generates client + server stubs that can't drift.
  • Binary protobuf over HTTP/2 — compact, multiplexed, streaming.
  • Four call types — unary + server/client/bidirectional streaming.
  • Interceptors + metadata + status codes — middleware, headers, typed errors.

The .proto contract

syntax = "proto3"; package auth.v1; service UserService { rpc GetUser(GetUserRequest) returns (User); } message GetUserRequest { string id = 1; } message User { string id = 1; string email = 2; repeated string roles = 3; }

Generated client call

conn, _ := grpc.NewClient(addr, grpc.WithTransportCredentials(creds)) client := authv1.NewUserServiceClient(conn) u, err := client.GetUser(ctx, &authv1.GetUserRequest{Id: "u1"}) // u is a typed *User — no JSON parsing if status.Code(err) == codes.NotFound { ... }

gRPC vs REST/JSON

REST/JSON: human-readable, browser-native, no codegen needed, loose contract (OpenAPI optional). gRPC: binary + HTTP/2 (faster, smaller), a required typed contract with generated stubs, native streaming, typed status codes. Browsers can't speak raw gRPC (need grpc-web/a gateway), so the usual split is REST at the public edge, gRPC between internal services. Same idea as Spring's @GrpcService + generated stubs, or a Feign client — but the contract is the proto, not Java interfaces.

CIAM context: Internal auth calls — token introspection, user/role lookup, session checks — are a perfect gRPC fit: typed, HTTP/2-multiplexed, low-latency. Carry the caller's bearer token and trace ID in metadata, and put one auth interceptor in front of every method to validate the JWT and inject the principal into the context — Spring Security's filter chain, but for RPCs. Map codes.Unauthenticated (16) → 401 and codes.PermissionDenied (7) → 403 at the edge gateway.

The problem

The client set a deadline. The server respected it perfectly. And a downstream call the handler made kept burning CPU for another eight seconds after that deadline passed.

A 2-second deadline that a downstream lookup never heard about

Your GetUser RPC handler needs to enrich the response with data from a second internal service, so it calls enrichmentClient.Lookup(context.Background(), req) instead of forwarding the ctx the RPC handler was actually given. The client called GetUser with a 2-second deadline via context.WithTimeout. At 2 seconds, gRPC correctly cancels the CLIENT's wait and returns codes.DeadlineExceeded — the caller moves on immediately.

The Lookup call, though, was handed context.Background() — a context that is never cancelled and carries no deadline at all. It keeps running: still holding a database connection, still consuming a goroutine, still doing work, for however long Lookup naturally takes — 8 seconds, in this case — for a response nobody is waiting for anymore. Under load, this is exactly how a slow downstream dependency turns into a resource leak: every timed-out client just adds one more orphaned call that outlives it.

the client's context.WithTimeout(2*time.Second) ✓ gRPC returning DeadlineExceeded to the client on time ✓ what the SERVER did with that deadline internally ⚠

The deadline worked exactly where you could see it — at the client — and silently stopped existing exactly where you couldn't.

Forward the context you were given — always
Pass the handler's own ctx to every downstream call: enrichmentClient.Lookup(ctx, req) ↓ gRPC clients read the deadline off the context you pass in and stop the call automatically once it's exceeded — no manual timer needed Never use context.Background() or context.TODO() inside a request handler ↓ both create a fresh context with no deadline and no cancellation — reserve them for main(), service startup, and background jobs that genuinely have no caller to inherit from If a downstream call needs its OWN shorter budget, derive it: ctx, cancel := context.WithTimeout(ctx, 500*time.Millisecond) ↓ deriving from the incoming ctx keeps the parent deadline as a hard ceiling — the derived context can only be stricter, never looser
A context you don't forward is a promise you don't keep. The whole point of Go's context.Context is that cancellation and deadlines propagate down a call chain automatically — but only along edges where the code actually passes the context forward. Swap in a fresh one anywhere in that chain and every promise upstream made about "stop when the caller stops" ends at that line.
Think of the incoming ctx as a relay baton, not a starting gun. Every downstream call needs the SAME baton passed into its hand — hand it a brand-new baton (context.Background()) instead, and it has no idea the race was ever supposed to end.
You

The client's deadline fired and it moved on. Why is my enrichment lookup still running?

context.Background()

Because that's what I am — a context with no deadline, no parent, no cancellation signal. I don't know a client existed, let alone that it gave up two seconds ago. Nobody told me to stop, so I don't.

You

But the handler DID have a ctx with the deadline on it.

The handler's real ctx

I did, and I was sitting right there in scope. The code just called Lookup with context.Background() instead of me — a completely valid Go value, so nothing warned anyone at compile time.

The mechanism

Trace the same 2-second deadline through a handler that does — and doesn't — forward it.

  1. The client calls GetUser with ctx, _ := context.WithTimeout(ctx, 2*time.Second)deadline set
  2. gRPC transmits that deadline to the server; the server's handler receives a ctx already carrying itpropagated
  3. The handler calls enrichmentClient.Lookup(context.Background(), req) — a fresh context, not the one it was givendropped
  4. At the 2-second mark, the CLIENT's original call unblocks with codes.DeadlineExceeded — that part of the contract still worksclient returns
  5. The Lookup call, riding on context.Background(), has no idea a deadline ever existed and keeps executingstill running
  6. It finishes 6 seconds later, holding a DB connection and a goroutine the whole time, and writes a result nothing will ever readwasted work

Step 3 is the entire bug in one function call. Everything before it and after it behaves exactly as documented — context.Background() is doing precisely what it's supposed to do: nothing. The mistake is calling it there at all.

Every one of these looks like an unrelated, small decision made under time pressure. All three throw away the same thing: the one piece of information — "someone is still waiting, and here's until when" — that only exists on the context you were actually handed.

A unary interceptor authenticates the caller, then calls handler(context.WithValue(ctx, userKey, principal), req) — the exact pattern from this page's own interceptor code. The wrapped handler internally makes a downstream call using this new context. Does the ORIGINAL client's deadline still apply to that downstream call?

This is the wrong instinct built from today's lesson — but WithValue isn't Background(). It derives a child context that still has the original as its parent, so cancellation and the deadline are inherited, not discarded. Only creating a genuinely NEW root context throws them away.

Deadlines aren't windowed like that — a context either carries a specific deadline (checked against `time.Now()`) or it doesn't. There's no "first half only" behavior in `context.Context`; this answer invents a rule that doesn't exist.

Correct — every context.With* function (WithValue, WithTimeout, WithCancel) returns a CHILD of the context you pass in, and a child always inherits its parent's deadline and cancellation. This is exactly why forwarding the real ctx — even after attaching values to it — keeps the whole chain intact.

Where you have seen this before

"The caller stopped waiting, but the work kept happening anyway" is a resource-leak shape that shows up anywhere cancellation has to be threaded through by hand.

An Angular HTTP call that isn't unsubscribed

Navigate away from a component mid-request and an HttpClient call with no takeUntilDestroyed()/manual unsubscribe keeps running, then tries to update a component that no longer exists. Same shape as the orphaned gRPC call: the "caller" (the component) is gone, but nothing told the in-flight work to stop.

an in-flight call outliving its own caller is a pattern, not a one-off bug

A Spring @Async method that ignores the caller's timeout

A CompletableFuture from an @Async method keeps executing on its own thread-pool thread even after the caller times out waiting on it (future.get(2, TimeUnit.SECONDS) throwing just stops the CALLER from waiting — it doesn't cancel the work) unless you explicitly call future.cancel(true) and the underlying task actually checks for interruption.

a caller giving up is not the same event as the work actually stopping

A database query that keeps running after the API request times out

An HTTP framework returning a 504 to the client doesn't automatically send a query-cancellation signal down to Postgres/MySQL unless the driver is wired to the request's cancellation (e.g. passing ctx into sql.QueryContext, or a JDBC statement's setQueryTimeout). Skip that wiring and the database keeps grinding on a query whose answer will be thrown away.

the response timing out and the underlying work stopping are two separate things you have to wire together
The whole page on a napkin: gRPC is a contract-first RPC framework — a .proto generates typed client/server stubs, calls travel as binary protobuf over HTTP/2 in four shapes (unary and three streaming styles), and cross-cutting concerns ride on interceptors, metadata, and typed status codes. The one new sentence this block adds: the ctx your handler receives carries the caller's real deadline and cancellation, but only for as long as your code keeps passing that SAME context forward — swap in context.Background() for even one downstream call, and that call becomes deaf to a client that already left.

1. The .proto Contract (proto3)

syntax = "proto3";
package auth.v1;
option go_package = "acme/gen/authv1";

service UserService {
  rpc GetUser(GetUserRequest) returns (User);
}
message User {
  string id = 1;
  string email = 2;
  repeated string roles = 3;
}

The .proto is the single source of truth shared by every language. Field numbers (= 1, = 2) are the real identity on the wire — names can change but numbers must stay stable forever. Adding a field is backward-compatible (old code ignores unknown fields); removing or renumbering a field is a breaking change. repeated = a list; proto3 scalars have no "null" (a zero value), so optionality is modeled with optional or wrapper types.

Never reuse or renumber a field number. Two messages that disagree on what field 3 means will silently mis-decode each other's data. When you delete a field, mark its number reserved so no future edit can recycle it.

2. Code Generation: One Proto → Both Sides

# buf (modern) or protoc generate Go from the proto
buf generate # → user.pb.go (messages) + user_grpc.pb.go (service)

// SERVER: implement the generated interface
type server struct { authv1.UnimplementedUserServiceServer }
func (s *server) GetUser(ctx context.Context, r *authv1.GetUserRequest) (*authv1.User, error) { ... }

// CLIENT: use the generated stub — a typed method call
client := authv1.NewUserServiceClient(conn)
u, err := client.GetUser(ctx, &authv1.GetUserRequest{Id: id})
Embed UnimplementedXxxServer in your server struct. It provides default "unimplemented" methods so adding a new RPC to the proto doesn't break compilation of existing servers — they keep building until you implement the new method. Forgetting it makes every proto addition a compile error.

3. The Four RPC Types (all over one HTTP/2 connection)

TypeSignature shapeUse for
Unaryrpc Get(Req) returns (Resp)ordinary request/response (most calls)
Server streamreturns (stream Resp)large result sets, live feeds, progress
Client streamrpc Up(stream Req) returns (Resp)uploads, batched ingestion
Bidirectionalrpc Chat(stream Req) returns (stream Resp)chat, real-time sync, long-lived sessions
HTTP/2 is what makes streaming cheap. One TCP connection multiplexes many concurrent RPCs and streams as independent frames — no head-of-line blocking between calls, no connection-per-request. This is also why a single grpc.ClientConn is shared across goroutines, like a *sql.DB.

4. Interceptors & Metadata (auth, the gRPC way)

// a unary auth interceptor = middleware for every RPC
func authUnary(ctx context.Context, req any, info *grpc.UnaryServerInfo,
  handler grpc.UnaryHandler) (any, error) {
  md, _ := metadata.FromIncomingContext(ctx) // gRPC "headers"
  tokens := md.Get("authorization")
  principal, err := validateJWT(tokens)
  if err != nil {
    return nil, status.Error(codes.Unauthenticated, "invalid token")
  }
  ctx = context.WithValue(ctx, userKey, principal)
  return handler(ctx, req) // call the real method
}
grpc.NewServer(grpc.ChainUnaryInterceptor(authUnary, loggingUnary))
Metadata is gRPC's header map; status codes are its errors. Carry the bearer token / trace ID in metadata, validate it once in an interceptor (chained like middleware), and return typed status.Error(codes.X, msg) — never a bare errors.New, or the client loses the code. codes.Unauthenticated → 401 and codes.PermissionDenied → 403 at your REST gateway.
