Go: gRPC & Protocol Buffers

A typed contract in a .proto file, code generation into Go client + server stubs, the four RPC styles over HTTP/2, and interceptors + metadata for cross-cutting concerns like auth.

📡 What gRPC is, and why service-to-service calls use it instead of REST

gRPC is a contract-first RPC framework. You describe a service in a Protocol Buffers (.proto) file — the service, its methods, and message shapes with stable field numbers — and a generator (protoc/buf) turns it into a ready client and a server interface you implement. The wire format is binary protobuf over HTTP/2 (compact, multiplexed, streaming-capable). Four call types: unary, server-streaming, client-streaming, bidirectional. Cross-cutting concerns ride on interceptors (gRPC's middleware) and per-call metadata (its headers, carrying tokens/trace IDs); errors are typed status codes, not HTTP numbers. The payoff over REST: one source-of-truth contract, generated type-safe stubs that can't drift, smaller payloads, and first-class streaming — which is why it dominates internal traffic even when the public edge stays REST.

  • Contract-first .proto — generates client + server stubs that can't drift.
  • Binary protobuf over HTTP/2 — compact, multiplexed, streaming.
  • Four call types — unary + server/client/bidirectional streaming.
  • Interceptors + metadata + status codes — middleware, headers, typed errors.

The .proto contract

syntax = "proto3"; package auth.v1; service UserService { rpc GetUser(GetUserRequest) returns (User); } message GetUserRequest { string id = 1; } message User { string id = 1; string email = 2; repeated string roles = 3; }

Generated client call

conn, _ := grpc.NewClient(addr, grpc.WithTransportCredentials(creds)) client := authv1.NewUserServiceClient(conn) u, err := client.GetUser(ctx, &authv1.GetUserRequest{Id: "u1"}) // u is a typed *User — no JSON parsing if status.Code(err) == codes.NotFound { ... }

gRPC vs REST/JSON

REST/JSON: human-readable, browser-native, no codegen needed, loose contract (OpenAPI optional). gRPC: binary + HTTP/2 (faster, smaller), a required typed contract with generated stubs, native streaming, typed status codes. Browsers can't speak raw gRPC (need grpc-web/a gateway), so the usual split is REST at the public edge, gRPC between internal services. Same idea as Spring's @GrpcService + generated stubs, or a Feign client — but the contract is the proto, not Java interfaces.

CIAM context: Internal auth calls — token introspection, user/role lookup, session checks — are a perfect gRPC fit: typed, HTTP/2-multiplexed, low-latency. Carry the caller's bearer token and trace ID in metadata, and put one auth interceptor in front of every method to validate the JWT and inject the principal into the context — Spring Security's filter chain, but for RPCs. Map codes.Unauthenticated (16) → 401 and codes.PermissionDenied (7) → 403 at the edge gateway.

1. The .proto Contract (proto3)

syntax = "proto3";
package auth.v1;
option go_package = "acme/gen/authv1";

service UserService {
  rpc GetUser(GetUserRequest) returns (User);
}
message User {
  string id = 1;
  string email = 2;
  repeated string roles = 3;
}

The .proto is the single source of truth shared by every language. Field numbers (= 1, = 2) are the real identity on the wire — names can change but numbers must stay stable forever. Adding a field is backward-compatible (old code ignores unknown fields); removing or renumbering a field is a breaking change. repeated = a list; proto3 scalars have no "null" (a zero value), so optionality is modeled with optional or wrapper types.

Never reuse or renumber a field number. Two messages that disagree on what field 3 means will silently mis-decode each other's data. When you delete a field, mark its number reserved so no future edit can recycle it.

2. Code Generation: One Proto → Both Sides

# buf (modern) or protoc generate Go from the proto
buf generate # → user.pb.go (messages) + user_grpc.pb.go (service)

// SERVER: implement the generated interface
type server struct { authv1.UnimplementedUserServiceServer }
func (s *server) GetUser(ctx context.Context, r *authv1.GetUserRequest) (*authv1.User, error) { ... }

// CLIENT: use the generated stub — a typed method call
client := authv1.NewUserServiceClient(conn)
u, err := client.GetUser(ctx, &authv1.GetUserRequest{Id: id})
Embed UnimplementedXxxServer in your server struct. It provides default "unimplemented" methods so adding a new RPC to the proto doesn't break compilation of existing servers — they keep building until you implement the new method. Forgetting it makes every proto addition a compile error.

3. The Four RPC Types (all over one HTTP/2 connection)

TypeSignature shapeUse for
Unaryrpc Get(Req) returns (Resp)ordinary request/response (most calls)
Server streamreturns (stream Resp)large result sets, live feeds, progress
Client streamrpc Up(stream Req) returns (Resp)uploads, batched ingestion
Bidirectionalrpc Chat(stream Req) returns (stream Resp)chat, real-time sync, long-lived sessions
HTTP/2 is what makes streaming cheap. One TCP connection multiplexes many concurrent RPCs and streams as independent frames — no head-of-line blocking between calls, no connection-per-request. This is also why a single grpc.ClientConn is shared across goroutines, like a *sql.DB.

4. Interceptors & Metadata (auth, the gRPC way)

// a unary auth interceptor = middleware for every RPC
func authUnary(ctx context.Context, req any, info *grpc.UnaryServerInfo,
  handler grpc.UnaryHandler) (any, error) {
  md, _ := metadata.FromIncomingContext(ctx) // gRPC "headers"
  tokens := md.Get("authorization")
  principal, err := validateJWT(tokens)
  if err != nil {
    return nil, status.Error(codes.Unauthenticated, "invalid token")
  }
  ctx = context.WithValue(ctx, userKey, principal)
  return handler(ctx, req) // call the real method
}
grpc.NewServer(grpc.ChainUnaryInterceptor(authUnary, loggingUnary))
Metadata is gRPC's header map; status codes are its errors. Carry the bearer token / trace ID in metadata, validate it once in an interceptor (chained like middleware), and return typed status.Error(codes.X, msg) — never a bare errors.New, or the client loses the code. codes.Unauthenticated → 401 and codes.PermissionDenied → 403 at your REST gateway.
