A Angular v14–v19: New Features

Every meaningful change from v14 to v19 — standalone, signals, control flow, defer, typed forms, inject(), and zoneless

📈 Why Angular changed so much between v14 and v19 — and what you need to know

v14–v19 was the most significant period of change in Angular's history — the team rewrote three fundamentals: the component model (standalone, no NgModules), the reactivity system (signals, no Zone.js tree walks), and the template syntax (built-in control flow, no *ngIf/*ngFor). These were architectural pivots, not tweaks. If you learned Angular before v14, most tutorials you'll find use the old APIs — this page maps each version to the feature it introduced so you know what's available at your version and what's now legacy.

  • Three pivots: standalone components, signals, and built-in @if/@for/@switch.
  • v14: standalone (opt-in), typed reactive forms, inject(), protected template members.
  • v16–17: signals (stable in 17), built-in control flow, @defer, standalone-by-default, Vite/esbuild builds.
  • v18–19: zoneless mode, signal input()/output()/viewChild(), resource(), linkedSignal(), incremental hydration.
  • The direction is clear: signals + standalone + zoneless. Old patterns still work but aren't where Angular is going.

v14 (2022) — foundations

Standalone (opt-in standalone: true); typed reactive forms (FormControl<string>); inject() in any function; protected members usable in templates.

v16–17 (2023) — signals + control flow

Signals (preview → stable in 17); built-in @if/@for (mandatory track)/@switch; @defer; standalone the CLI default; Vite + esbuild (3–8× faster builds).

v18–19 (2024) — zoneless

Zoneless mode; signal input()/output()/viewChild() replacing decorators; resource() for async data; linkedSignal(); incremental hydration; afterRenderEffect().

Practical rule:on 17+? Use standalone, @if/@for, signals for state, inject() for DI — the current defaults. Seeing @NgModule, *ngIf, BehaviorSubject in new code means the old pattern. For a CIAM app, target 17+ and use the new APIs from day one — signal-based forms and resource() will be much smoother.

Angular Release Timeline: v14 → v19

      
Angular follows a 6-month release cadence with LTS (Long-Term Support) versions receiving bug/security fixes for 18 months. v17+ is the modern baseline for new projects.


      

        

          
v14 — June 2022

          

            
stableStandalone components (developer preview) — Components without NgModule declarations. standalone: true in @Component.

            
stableStrictly typed reactive forms — FormControl<string>, FormGroup<{name: FormControl<string>}>. No more any.

            
stableinject() function — Call DI outside of constructor: const svc = inject(MyService).

            
stableExtended template diagnostics — Compiler catches unsafe nullability, missing imports at build time.

          

        


        

          
v15 — November 2022

          

            
stableStandalone components — STABLE — bootstrapApplication(), provideRouter(), provideHttpClient(). NgModule optional.

            
stableDirective composition API — hostDirectives: compose directives onto components without inheritance.

            
stableNgOptimizedImage — [ngSrc] auto-adds width/height, priority attribute, CDN integration. Dramatically improves LCP.

            
stableFunctional guards & resolvers — canActivate: [() => inject(AuthGuard).canActivate()] — no class needed.

            
stableStable MDC-based Material — Angular Material rebuilt on Google's MDC foundation.

          

        


        

          
v16 — May 2023

          

            
developer previewSignals (developer preview) — signal(), computed(), effect(). Reactive primitives without RxJS or Zone.js.

            
stableRequired inputs — @Input({ required: true }) — compile-time error if not bound.

            
stableRouter inputs — withComponentInputBinding() — route params auto-injected as @Input() on component.

            
stabletakeUntilDestroyed() — RxJS operator that auto-unsubscribes when component destroys.

            
stableJest support (experimental) — Builder for running Jest instead of Karma.

            
stableSSR improvements — Non-destructive hydration preview. Server renders, client hydrates without re-rendering.

          

        


        

          
v17 — November 2023 ⭐ Major

          

            
stableBuilt-in control flow — @if, @else, @for, @empty, @switch, @case, @default. Replaces *ngIf/*ngFor.

            
stable@defer blocks — Declarative lazy loading with loading/placeholder/error states and viewport/hover/interaction triggers.

            
stableSignals — STABLE — signal(), computed(), effect() fully stable and ready for production.

            
stableHydration — STABLE — Full client hydration without flicker. withEventReplay() coming in v18.

            
stableEsbuild + Vite for dev server — 67% faster cold builds, HMR with Vite (replaces webpack-based dev server).

            
stableNew Angular.dev — Redesigned docs site with interactive tutorials.

          

        


        

          
v18 — May 2024

          

            
developer previewZoneless change detection (experimental) — provideExperimentalZonelessChangeDetection(). Renamed provideZonelessChangeDetection() in v20 and stable in v20.2; the old name is gone.

            
stableEvent replay — SSR: events during hydration are captured and replayed. No missed clicks.

            
stableMaterial 3 stable — Angular Material 3 (full Material Design 3 compliance).

            
stableRoute redirects as functions — redirectTo: (info) => '/new/path/' + info.params.id.

            
stableinput() signal API — input(), input.required(), output(), model() — signal-based alternatives to @Input/@Output.

          

        


        

          
v19 — November 2024

          

            
stableIncremental hydration — Hydrate individual @defer blocks on-demand. Dramatically reduces time-to-interactive.

            
developer previewZoneless — still the experimental provider in v19 — Signal-based rendering without Zone.js. Renamed and stabilised in v20 (stable as of v20.2), not here.

            
stablelinkedSignal() — Writable signal derived from another signal. Resets when source changes.

            
stableresource() / rxResource() — Signal-based async data fetching. Replaces common subscribe patterns.

            
stableStandalone by default — ng new generates standalone apps by default. NgModule still supported.

            
stableHot module replacement (HMR) — Styles and components hot-reload without full page refresh.

          

        

      

    

  


  
  

    

      
Standalone Components — No NgModule Required

      
Before v14, every component had to be declared in an NgModule. Standalone components declare their own dependencies inline — simpler, more tree-shakeable, and compatible with vite/esbuild.

      

        

          
Before: NgModule-based

          
// app.module.ts — required before v14
@NgModule({
  declarations: [AppComponent, UserCardComponent],
  imports: [BrowserModule, HttpClientModule],
  providers: [UserService],
  bootstrap: [AppComponent]
})
export class AppModule {}

// user-card.component.ts
@Component({ selector: 'app-user-card' })
export class UserCardComponent {
  // Must be in declarations[] to use
}

        

        

          
After: Standalone (v15+)

          
// main.ts — bootstrapApplication replaces AppModule
bootstrapApplication(AppComponent, {
  providers: [
    provideRouter(routes),
    provideHttpClient(),
    provideAnimations()
  ]
});

// user-card.component.ts
@Component({
  selector: 'app-user-card',
  standalone: true,
  imports: [CommonModule, RouterLink], // own imports!
  template: `<a [routerLink]="['/user', id]">...</a>`
})
export class UserCardComponent { ... }

        

      

      

        v19+: ng new generates standalone by default. NgModule still fully supported — you don't need to migrate existing apps.
      

    


    

      
Bootstrapping & Providers

      
// Standalone app bootstrap (replaces platformBrowserDynamic().bootstrapModule(AppModule))
bootstrapApplication(AppComponent, {
  providers: [
    provideRouter([
      { path: '', component: HomeComponent },
      { path: 'users', loadComponent: () => import('./users.component').then(m => m.UsersComponent) }

    provideHttpClient(withInterceptors([authInterceptor])), // functional interceptors!

    provideAnimations(),

    importProvidersFrom(SomeThirdPartyModule), // migrate NgModule providers
  ]
}).catch(console.error);

    

  


  
  

    

      
Signals — Reactive Primitives (v16 dev preview → v17 stable)

      
Signals are reactive value containers. When a signal changes, Angular knows exactly which components to re-render — no dirty-checking the whole tree. The future of Angular change detection.

      

        
// signal() — writable reactive value
import { signal, computed, effect } from '@angular/core';

@Component({ template: `
  <p>Count: {{ count() }}</p>         <!-- call to read! -->
  <p>Double: {{ double() }}</p>
  <button (click)="increment()">+</button>
` })
export class CounterComponent {
  count = signal(0);                         // WritableSignal<number>
  double = computed(() => this.count() * 2); // auto-recomputes

  constructor() {
    effect(() => {
      console.log('count changed:', this.count()); // runs on change
    });
  }

  increment() { this.count.update(c => c + 1); }
  reset()     { this.count.set(0); }
}

        
// input() — signal-based @Input (v17.1+)
import { input, output, model } from '@angular/core';

@Component({...})
export class UserCardComponent {
  // Replaces @Input() name: string
  name = input('Guest');           // with default
  userId = input.required<number>(); // required, no default

  // Replaces @Output() selected = new EventEmitter()
  selected = output<number>();
  select() { this.selected.emit(this.userId()); }

  // model() = two-way bindable signal
  // Replaces @Input() + @Output() value/valueChange pair
  value = model(''); // [(value)]="parentProp" works!
}

// linkedSignal (v19) — writable, resets when source changes
selectedPage = linkedSignal(() => this.currentTab() === 'list' ? 1 : 0);

      

    


    

      
resource() — Signal-Based Async Data (v19)

      
// resource() replaces common subscribe-in-constructor patterns
import { resource, signal } from '@angular/core';

@Component({
  template: `
    @if (userResource.isLoading()) { <spinner/> }
    @else if (userResource.error()) { <p>Error!</p> }
    @else { <user-card [user]="userResource.value()"/> }
  `
})
export class UserPageComponent {
  userId = signal(1);

  userResource = resource({
    request: () => this.userId(), // re-fetches when userId changes
    loader: async ({ request: id }) => {
      const res = await fetch(`/api/users/${id}`);
      return res.json();
    }
  });

  // rxResource: same but with Observables
  // rxResource({ request: () => id, loader: ({request}) => this.http.get('/users/' + request) })
}

      

        resource() states: .isLoading(), .value(), .error(), .reload() — all signals. Automatically re-fetches when the request signal changes, handles race conditions, and cancels in-flight requests.
      

    


    

      
toSignal() & toObservable() — Bridge RxJS ↔ Signals

      

        
// Convert Observable → Signal
import { toSignal } from '@angular/core/rxjs-interop';

@Component({...})
export class SearchComponent {
  searchTerm = signal('');

  // Convert Observable to Signal
  results = toSignal(
    toObservable(this.searchTerm).pipe(
      debounceTime(300),
      switchMap(term => this.http.get(`/search?q=${term}`))
    ),
    { initialValue: [] }
  );

  // Now template can use results() directly — no async pipe!
}

        
// Convert Signal → Observable
import { toObservable } from '@angular/core/rxjs-interop';

@Component({...})
export class RealtimeComponent {
  count = signal(0);

  // Convert Signal → Observable for RxJS operators
  count$ = toObservable(this.count);

  // Then pipe it like any Observable
  doubled$ = this.count$.pipe(map(c => c * 2));

  // takeUntilDestroyed() — v16+
  // auto-unsubscribes when component is destroyed
  ngOnInit() {
    someObservable$.pipe(
      takeUntilDestroyed(this.destroyRef) // inject(DestroyRef)
    ).subscribe(v => this.count.set(v));
  }
}

      

    

  


  
  

    

      
Built-in Control Flow (v17)

      
New block syntax replaces structural directives (*ngIf, *ngFor, *ngSwitch). Faster (no Directive overhead), type-narrowing works inside blocks, and @for requires track — preventing bugs.

      

        

          
@if / @else if / @else

          
<!-- Old: *ngIf -->
<div *ngIf="user; else loading">...</div>
<ng-template #loading><spinner/></ng-template>

<!-- New: @if (v17+) -->
@if (user) {
  <user-profile [user]="user"/>
} @else if (isLoading) {
  <spinner/>
} @else {
  <p>Not found</p>
}

<!-- Type narrowing works inside @if! -->
@if (item instanceof Admin) {
  <admin-panel [admin]="item"/>  <!-- item is Admin here -->
}

        

        

          
@for / @empty

          
<!-- Old: *ngFor -->
<li *ngFor="let item of items; trackBy: trackId">
  {{ item.name }}
</li>

<!-- New: @for (requires track!) -->
@for (item of items; track item.id) {
  <li>{{ item.name }}</li>
} @empty {
  <p>No items found.</p>
}

<!-- Loop variables: $index, $first, $last, $even, $odd, $count -->
@for (item of items; track item.id; let i = $index) {
  <li [class.last]="$last">{{ i }}: {{ item }}</li>
}

        

      

      

        

          
@switch / @case / @default

          
<!-- Old: [ngSwitch] -->
<div [ngSwitch]="status">
  <span *ngSwitchCase="'active'">Active</span>
  <span *ngSwitchDefault>Inactive</span>
</div>

<!-- New: @switch -->
@switch (status) {
  @case ('active')   { <span class="green">Active</span> }
  @case ('pending')  { <spinner/> }
  @case ('inactive') { <span class="red">Inactive</span> }
  @default           { <span>Unknown</span> }
}

        

        

          

            @for track is required — unlike *ngFor's optional trackBy, @for requires a track expression. This prevents the #1 performance mistake where Angular destroys and recreates all DOM nodes on every change.
          

          

            Migration: Run ng generate @angular/core:control-flow to automatically migrate your templates from *ngIf/*ngFor to @if/@for.
          

        

      

    

  


  
  

    

      
Strictly Typed Reactive Forms (v14)

      
Before v14, FormControl.value was typed as any — no autocomplete, no type safety. v14 added generics to all form types.

      

        

          
Before v14 (untyped)

          
// FormControl was untyped — value: any
const ctrl = new FormControl('');
const val = ctrl.value; // type: any 😢

const form = new FormGroup({
  name:  new FormControl(''),
  email: new FormControl('')
});
form.value.somethingThatDoesntExist; // no error!
form.value.name; // type: any

          
Typos in .value.propertyName compile silently. Runtime bugs hard to track.

        

        

          
v14+: Typed forms

          
// FormControl<string | null> — null when reset()
const ctrl = new FormControl('');
const val = ctrl.value; // type: string | null ✓

interface LoginForm {
  name: FormControl<string>;
  age:  FormControl<number | null>;
}
const form = new FormGroup<LoginForm>({
  name: new FormControl('', { nonNullable: true }),
  age:  new FormControl<number | null>(null)
});
form.value.name; // type: string ✓
form.value.somethingBad; // TypeScript ERROR ✓

        

      

    


    

      
FormBuilder & nonNullable

      
import { NonNullableFormBuilder } from '@angular/forms';

@Component({...})
export class LoginComponent {
  private fb = inject(NonNullableFormBuilder); // never returns null on reset()

  form = this.fb.group({
    email:    ['', [Validators.required, Validators.email]],
    password: ['', Validators.minLength(8)],
    remember: [false]
  });

  // form.value.email is string (not string | null) because NonNullableFormBuilder

  onSubmit() {
    if (this.form.valid) {
      const { email, password } = this.form.getRawValue(); // typed!
    }
  }
}

// FormArray<FormControl<string>> — typed arrays
tags = new FormArray<FormControl<string>>([
  new FormControl('angular', { nonNullable: true })
]);

    

  


  
  

    

      
inject() Function (v14)

      
The inject() function lets you access Angular's DI system outside of constructor parameters — in field initializers, service factories, functional guards, and interceptors. Must be called in an injection context.

      

        
// inject() in component field (no constructor needed!)
@Component({...})
export class UserComponent {
  private userService = inject(UserService);
  private router = inject(Router);
  private destroyRef = inject(DestroyRef); // for takeUntilDestroyed

  users = toSignal(this.userService.getAll());

  // No constructor() at all! Cleaner class
}

// inject() in functional guard (v15+)
export const authGuard: CanActivateFn = (route) => {
  const auth = inject(AuthService);
  const router = inject(Router);
  return auth.isLoggedIn() || router.parseUrl('/login');
};

// inject() in functional interceptor (v15+)
export const authInterceptor: HttpInterceptorFn = (req, next) => {
  const auth = inject(AuthService);
  const token = auth.getToken();
  return next(req.clone({ setHeaders: { Authorization: `Bearer ${token}` } }));
};

        
// Injection Tokens — type-safe DI of non-class values
const API_URL = new InjectionToken<string>('API_URL');
const MAX_RETRIES = new InjectionToken<number>('MAX_RETRIES', {
  factory: () => 3 // default value
});

// Provide at app level:
bootstrapApplication(AppComponent, {
  providers: [
    { provide: API_URL, useValue: 'https://api.example.com' },
    { provide: MAX_RETRIES, useValue: 5 }
  ]
});

// Consume with inject():
const apiUrl = inject(API_URL);         // type: string
const retries = inject(MAX_RETRIES);    // type: number
const optional = inject(API_URL, { optional: true }); // string | null

// Component-scoped providers — fresh instance per component
@Component({

@defer — Declarative Lazy Loading (v17)

      
@defer lazily loads a component or block of template only when needed. Unlike route-level lazy loading, it works at the template level — you can defer any part of a component's template.

      

        

          
Basic @defer Structure

          
<!-- Full @defer anatomy -->
@defer (when isVisible) {
  <!-- Lazy-loaded. Bundle split here -->
  <heavy-chart [data]="chartData"/>

} @loading (minimum 200ms) {
  <!-- Shown while chunk downloads -->
  <skeleton-loader/>

} @placeholder (minimum 100ms) {
  <!-- Shown before trigger fires -->
  <p>Chart will load here</p>

} @error {
  <!-- Shown if chunk fails to load -->
  <p>Failed to load chart.</p>
}

        

        

          
Triggers

          
<!-- Trigger on viewport intersection -->
@defer (on viewport) { <comments/> }

<!-- Trigger on user interaction -->
@defer (on interaction) { <chat-widget/> }
@defer (on hover)       { <preview-card/> }
@defer (on focus)       { <search-dropdown/> }

<!-- Trigger when signal condition is true -->
@defer (when userLoggedIn()) { <dashboard/> }

<!-- Prefetch in background, render later -->
@defer (on viewport; prefetch on idle) {
  <heavy-analytics/>
}

<!-- Multiple triggers -->
@defer (on hover; on interaction) {
  <modal/>
}

        

      

    


    

      
@defer + Incremental Hydration (v19)

      
// app.config.ts — enable incremental hydration
bootstrapApplication(AppComponent, {
  providers: [
    provideClientHydration(withIncrementalHydration())
  ]
});

<!-- Template: SSR renders full page, client hydrates @defer blocks on demand -->
@defer (hydrate on viewport) {
  <product-reviews/>   <!-- Hydrates only when user scrolls near it -->
}

@defer (hydrate on interaction) {
  <shopping-cart/>     <!-- Hydrates only when user clicks/taps -->
}

<!-- Result: full SSR HTML, interactive parts hydrate on demand
     → Dramatically lower Time to Interactive
     → Less JavaScript executed on page load -->

      

        Real impact: A typical e-commerce page defers product recommendations, reviews, and chat widget. Only the above-the-fold add-to-cart button hydrates immediately. Time-to-interactive drops from 4s to <1s.
      

    


    

      
Router Input Binding (v16) & Functional Resolvers (v15)

      

        
// v16: withComponentInputBinding()
// Route params auto-inject as @Input()

// router config:
provideRouter([
  { path: 'users/:id', component: UserDetailComponent }
], withComponentInputBinding())

// component — no need to inject ActivatedRoute!
@Component({...})
export class UserDetailComponent {
  @Input() id!: string; // ← auto-injected from :id param
  // or with signals:
  id = input.required<string>();
}

        
// v15: Functional resolvers & guards

// OLD: class-based guard
@Injectable({ providedIn: 'root' })
class AuthGuard implements CanActivate {
  canActivate() { return inject(AuthService).isLoggedIn(); }
}

// NEW: functional guard (v15+)
export const canActivate: CanActivateFn = () =>
  inject(AuthService).isLoggedIn();

// Functional resolver:
export const userResolver: ResolveFn<User> = (route) =>
  inject(UserService).getUser(+route.params['id']);

// Route config:
{ path: 'user/:id', component: ..., canActivate: [canActivate],
  resolve: { user: userResolver } }
