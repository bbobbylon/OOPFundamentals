Go: Packages & Modules

How Go code is organized and shared: packages and exported names, the go.mod module, import paths, SemVer + minimal version selection, and the internal/ visibility rule.

📚 Package, module, import path — what each one actually is

A package is one directory of .go files sharing a package X declaration — the unit of compilation and visibility, where an uppercase identifier is exported and lowercase is package-private. A module is packages versioned together, defined by go.mod; the module path (github.com/acme/app) is also the import prefix. Add deps by importing and running go mod tidy (writes require + checksums in go.sum). Versions are SemVer git tags, resolved by Minimal Version Selection — Go picks the lowest version satisfying everyone, so adding a dep can't silently upgrade another. A breaking major version lives at a distinct path (.../app/v2), and an internal/ directory is compiler-enforced private to its parent tree.

  • Package = directory + visibility — uppercase exported, lowercase private.
  • Module = go.mod — module path doubles as the import prefix.
  • MVS picks the lowest satisfying version — reproducible, no surprise upgrades.
  • /v2 paths + internal/ — majors coexist; internals stay private.

go.mod + import path

// go.mod module github.com/acme/gateway go 1.23 require ( github.com/golang-jwt/jwt/v5 v5.2.1 github.com/jackc/pgx/v5 v5.6.0 ) // import a local package: import "github.com/acme/gateway/internal/token"

Exported vs unexported

package token // Exported — visible to importers func Parse(s string) (*Claims, error) {...} type Claims struct { Subject string // exported field secret []byte // package-private } // unexported — internal helper func validate(c *Claims) error {...}

Go modules vs Maven/npm

Maven/npm: a central registry, a manifest (pom.xml / package.json), a lockfile, and a SAT-ish resolver that often picks the highest compatible version. Go: no central registry — the import path IS the URL (github.com/...); go.mod + go.sum replace manifest + lockfile; and MVS picks the lowest version that satisfies everyone, so adding a dep can't silently upgrade an unrelated one. Major versions live at distinct import paths (/v2), sidestepping "diamond" conflicts.

CIAM context: Lay out an auth service as one module github.com/acme/ciam-gateway with internal/token, internal/idm, internal/store — the internal/ rule makes those compiler-enforced private, so no other team can couple to your token internals; the binary lives in cmd/gateway. Pin the JWT lib exactly (jwt/v5 v5.2.1) and let go.sum guarantee the bytes never change — supply-chain hygiene for a security-critical dependency. A breaking v2 of a shared SDK imports as .../sdk/v2 so consumers upgrade deliberately.

or, the init() ordering rule that has nothing to do with imports, edits, or declarations — just filenames, sorted alphabetically

The problem

Multiple files in the same package don't run their init() functions in the order you wrote them, imported them, or last touched them. They run in the order cmd/go happens to hand the files to the compiler — alphabetically, by filename.

Adding a new file silently changes which init() "wins"

A metrics package registers exporters by name, and two files each try to claim the same key during startup:

// exporters.go
func init() { registry["default"] = jsonExporter{} }

// prometheus.go
func init() { registry["default"] = prometheusExporter{} }

Neither file imports the other; neither declares any dependency between them. A developer reading top-to-bottom assumes declaration order, or import order in main.go, or maybe "whichever file was edited most recently" decides which init() runs last and therefore wins the "default" key. None of those are the actual rule. The Go spec is explicit: within a package, cmd/go presents multiple source files to the compiler in lexical (alphabetical) filename order, and package-level variable initialization plus init() functions across files run in that same order when there's no explicit dependency forcing otherwise. exporters.go sorts before prometheus.go, so prometheus.go's init() runs second and silently overwrites the "default" entry.

Six months later, someone adds a third exporter and, out of habit, names the file zz_datadog.go so it "sorts to the bottom, out of the way." That single filename choice — nothing about the code inside it — makes the Datadog exporter win "default" instead of Prometheus, with no import changed and no line of existing code touched.

no import cycle, no explicit dependency between the files ✓ both init() functions compile and run correctly ✓ which one "wins" depends only on filename sort order ⚠ adding zz_datadog.go changes the winner with zero code review flag ⚠

Nothing here is a bug in either file — it's a bug in the assumption that anything other than alphabetical filename order was ever deciding the outcome.

Make the ordering explicit instead of leaning on filenames
Never let two init() functions race for the same side effect ↓ if two files can both write registry["default"], that's a design smell independent of which one currently wins — make the registration itself detect and reject the collision Prefer an explicit registration call from main(), in a visible order, over implicit init() magic ↓ RegisterExporter("prometheus", prometheusExporter{}) called deliberately from main.go makes the order a line of code you can read, not a filename you have to alphabetize in your head If init() order truly matters, say so with a comment AND a naming convention you enforce on purpose ↓ treat filename-driven ordering as something you're choosing deliberately (and documenting), not something that fell out of whatever you happened to name the file
The one-sentence rule. Without an explicit dependency between them, multiple files' package-level init() functions run in alphabetical-by-filename order — not import order, not edit order, not the order they appear in your editor's file tree.
Two init() functions racing for the same key is like two people writing on the same whiteboard slot, in an order decided entirely by the alphabetical position of their name tags — not who spoke first, not who has seniority, just spelling.

The mechanism

Follow one package from three source files on disk to one line deciding which init() runs last.

  1. Package metrics/ contains exporters.go, prometheus.go, and (later) zz_datadog.gofiles
  2. go build invokes cmd/go, which lists this package's files in lexical (alphabetical) filename order: exporters.go, prometheus.go, zz_datadog.gosorted
  3. The compiler processes package-level variable initializers and init() functions across these files in that exact sorted order, since none of them declares a dependency on anotherin order
  4. exporters.go's init() runs first, setting registry["default"] = jsonExporter{}1st
  5. prometheus.go's init() runs second, overwriting registry["default"] = prometheusExporter{}2nd
  6. zz_datadog.go's init() runs last, overwriting registry["default"] a third time — purely because "zz_" sorts last, not because Datadog is somehow the "final" or "most important" exporter3rd, wins

Step 2 is the entire mechanism, and it happens before a single line of your code executes — the file order is decided by cmd/go reading directory entries and sorting names, a step most Go developers never learn exists because it almost never matters, right up until two init() functions quietly disagree about the same piece of state.

Package directory: metrics/ — three .go files, no explicit dependency declared between them

Reading inward: the outer ring is just files sitting in a folder, indistinguishable in importance; the middle ring is the one invisible step — a plain alphabetical sort — that most Go code never needs to know exists; the core is where that sort quietly becomes a business decision, deciding which exporter, which config default, which registered handler "wins."

Package metrics has two files, exporters.go and prometheus.go, each with an init() that writes to registry["default"]. Neither file imports the other or declares any dependency between them. What determines which one's write wins?

Right. With no explicit dependency between the files, the Go spec has cmd/go hand them to the compiler in lexical filename order, and init() functions run in that same order — exporters.go first, prometheus.go second and therefore last-write-wins on the shared key.

Declaration position only controls order WITHIN a single file — multiple init() functions in the same file do run top-to-bottom. Across separate files, filename order is what governs it, not where each function sits inside its own file.

Which symbol main.go happens to reference first has no effect on init() ordering between sibling files in the same package — imports control which packages get initialized before which, not the file order inside one package.

Where you have seen this before

"An invisible sort step decides execution order, until two things collide" shows up anywhere a language or tool discovers files instead of being told their order explicitly.

CSS load order for colliding selectors

Two stylesheet <link> tags with equal specificity resolve a conflicting rule by whichever one appears LAST in the compiled HTML — often decided by a bundler's own file-discovery order, not by which rule a developer intended to "win." A renamed file, sorted differently by the bundler, can flip which style applies with no visual diff in either file's own contents.

the same last-one-wins collision, in the browser's cascade

Python's __init__.py import side effects across a package

When a Python package's submodules each register a plugin via a module-level side effect, and nothing pins their import order explicitly, the actual order can hinge on directory listing order or import-statement placement — an implicit ordering rule most developers never examine until two plugins claim the same registry key.

the same implicit-discovery-order trap, one ecosystem over

Spring's component scan with ambiguous bean priority

Two @Component classes both implementing the same interface, with no explicit @Primary or @Order, get a winner decided by Spring's own internal bean-definition ordering — effectively classpath scan order — rather than anything a developer wrote on purpose. It compiles fine right up until a new class is added and the "wrong" bean becomes primary.

1. Packages: One Directory, Exported by Capitalization

// every file in ./token starts with:
package token

// Exported (Capitalized) — importers can use these
func Parse(s string) (*Claims, error) { ... }
type Claims struct { Subject string }

// unexported — only this package sees these
func validate(c *Claims) error { ... }
const secretKey = "..."

A package is exactly one directory; all its files share the package name (usually matching the folder). The only visibility control is the first letter — uppercase exports, lowercase hides. package main with func main() produces an executable; any other name produces an importable library. An init() function (you don't call it) runs once at package load, after variable initialization — useful for registering drivers, before main.

Package name, not path, is what you type. You import "github.com/acme/app/token" but refer to its contents as token.Parse — the last path element is usually the package name, but not always. Rename on import to disambiguate: import jwttoken "github.com/acme/app/token".

2. The Module: go.mod and Import Paths

# create a module — path becomes the import prefix
go mod init github.com/acme/gateway

# add/remove deps to match your imports + write go.sum
go mod tidy

# go.mod now lists requires; go.sum has checksums

go.mod declares the module path, the go language version, and require directives for dependencies. The module path is the import prefix for every package inside it. You don't hand-edit requires — you import what you need and run go mod tidy, which adds missing deps, drops unused ones, and records exact checksums in go.sum. Commit both files.

go.sum is a checksum database, not a lockfile. It records the cryptographic hash of each dependency version so a tampered or swapped release fails the build. Exact versions are pinned in go.mod's require lines; together they make builds reproducible and tamper-evident.

3. Versioning: SemVer + Minimal Version Selection

ActionWhat happens
go get pkg@v1.4.2pin an exact version; @latest, @v1.4.0, a branch, or a commit also work
build resolves versionsMVS: pick the lowest version that satisfies every module's requirement — deterministic, no solver
major bump (v1 → v2)breaking change → import path gains /v2; v1 and v2 are different modules and coexist
go get -uopt-in upgrade to newer minor/patch versions
The /v2 rule (Semantic Import Versioning): a module at v2.0.0+ must end its module path in /v2, and importers write import "github.com/acme/sdk/v2". This is why a breaking upgrade is always a deliberate code change, never a silent one — the old and new majors are literally different import paths that can both be in the build.

4. internal/ and Project Layout

github.com/acme/gateway/
├── go.mod
├── cmd/
│   └── gateway/main.go // the binary
├── internal/
│   ├── token/ // private to this module
│   ├── idm/
│   └── store/
└── pkg/
    └── apiclient/ // meant for external reuse

A package under internal/ can be imported only by code whose import path is rooted at internal/'s parent. So gateway/internal/token is usable anywhere in the gateway module but is a hard compile error for anyone outside it — a compiler-enforced private API. Convention: cmd/ holds main packages (one per binary), internal/ holds private implementation, and pkg/ (optional) holds code you intend others to import.

For local multi-module development, use a replace directive (or a go.work workspace): replace github.com/acme/sdk => ../sdk points an import at a local checkout so you can edit a dependency and your service together before publishing a tag.
