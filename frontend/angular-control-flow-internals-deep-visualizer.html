@for, track & Control-Flow Internals

The new built-in control flow isn't just nicer syntax — @for makes track mandatory because that key drives DOM reconciliation. Pick a wrong key and Angular destroys and rebuilds nodes you meant to keep. Watch it happen, node by node.

🔑 What is DOM reconciliation — and why does the track key matter so much?

When a @for list changes (an item added, removed, or reordered), Angular doesn't rebuild every DOM node — that'd be brutal for a 200-row table. It reconciles: diff old vs new and make the minimal DOM changes. The track expression is the key that matches old nodes to new items. track user.id — user 42 moving from row 5 to row 1 moves its existing node (keeping focus, animations, input values). track $index — Angular matches by position, so the same move destroys and rebuilds nodes. Wrong key = 10× the DOM work.

  • Reconciliation = diff + minimal patch; the track key decides which old node maps to which new item.
  • Stable id (track user.id): reorders move nodes — focus, animation, and inline-edit state survive.
  • Position (track $index): a sort destroys + recreates every moved row — slow, and it wipes focus/state.
  • $index is fine only for non-reordering lists with no stable id (primitive strings, fixed steps).
  • For object lists that sort/filter/edit, always track a unique stable field.

track user.id — correct

Items identified by stable id. Add → one new node; remove 42 → its node destroyed; sort → nodes reordered with insertBefore. A focused input inside a row stays focused through a sort — its node moved, not recreated.

track $index — common mistake

Items identified by position. After a sort, position 0 holds a different user, so Angular destroys node 0 and creates a new one — for every moved row. A 200-row sort = up to 200 destroy+create ops; animations reset, focus lost, fields cleared.

When track $index is ok

Items never reorder and have no stable id — a list of primitive strings, a read-only message list, fixed steps. If items are objects, always track item.id. Never use $index on a sortable/filterable/editable list.

In CIAM:the user table is @for (user of users(); track user.id) — sorting by email moves nodes (~5ms). With $index instead, Angular destroys + recreates all 200 rows (~50ms) and inline-edit fields lose their values. Invisible at 5 rows; critical at 200.

or, track isn't a performance knob — it's the answer to "is this the same row, or a new one?"

The problem

You typed into a row's edit field, someone sorted the table, and your text is now attached to a stranger.

Nothing crashed. The sort even landed in the right order. The text moved anyway.

Your @for (user of users(); track $index) renders an editable table — click a name, an <input> appears inline. You wire up a "sort by email" button and test it: add a user, it appears; remove one, it's gone; sort a clean table, the order is right. Every case looks fine. Then QA reports that if you start typing a rename and someone else's click re-sorts the table mid-edit, the half-typed text reappears next to a completely different person. You re-read the loop. The array is sorted correctly. The rendered names are correct. Nothing threw. So you go looking for a bug in the sort function, when the sort function was never the problem.

adding and removing a row works fine ✓ the sorted order on screen is correct ✓ track $index ties identity to a slot, not a person ⚠ the input's typed text stayed in that slot — now next to someone else ⚠

The bug isn't in the sort, and it isn't in the render. It's in the one word you didn't think mattered: track.

Track the thing that identifies the person, not the thing that counts them
track $index → track user.id ↓ identity now travels with the user, so the differ can tell "this row moved" from "this slot has new content" Same fix covers any per-row state — a checkbox, an open menu, scroll position ↓ all of it lives on the DOM node, and track is what decides whether that node follows its data or stays put One word in the @for, not a rewrite of the table
track doesn't decide what gets rendered — it decides which DOM node renders it. That one distinction is the whole page: it's why track user.id carries a focused input, a checkbox, or a mid-animation row through a reorder unharmed, why track $index looks perfect on a list that only ever grows and falls apart the moment a row gets stateful, and why Angular stopped letting @for skip the question — old *ngFor let you forget trackBy; the new syntax won't compile without an answer.
Think of track as a coat-check ticket, not a coat-hook number. Hand over ticket #42 and you get your coat, wherever the attendant rehung it. Ask for "whatever's on hook 3" and after the coats get shuffled, hook 3 belongs to a stranger. track user.id is the ticket. track $index is the hook — and the analogy only breaks down for a coat rack nobody ever reshuffles, which is exactly the one case where the hook number was fine all along.

The IterableDiffer

I never saw "your half-typed text" — I only see two arrays, old and new, and whatever key you told me to match them by. You told me to match by position. Position 0 held Ada before the sort and Grace after it, so as far as I'm concerned that's the same slot with new content, not a move.

The DOM node

And I did exactly what it told me to do — I stayed exactly where I was and let my label get rewritten from Ada to Grace. Nobody told me to hand off my input's value to Ada's new node, because nobody told me Ada had a new node. I don't have one. I'm just wearing a different name now.

The mechanism

Same array, same .sort() call — one track key produces a move, the other produces a relabel.

  1. .sort() gives @for a new array reference holding the same three user objects in a new ordernot a fetch — a resort
  2. Angular's differ walks the old array and the new array together, computing each item's key with your track expressionthis is the IterableDiffer
  3. track user.id: id 7 was at old index 2, now at new index 0 — the differ records that as a moveidentity survived the reorder
  4. track $index: the key set is just {0,1,2} both times — nothing about the key set changed, so the differ records zero moves, zero creates, zero destroysas far as the differ can tell, nothing happened
  5. Angular applies the diff: an identity-tracked move relocates the whole node — DOM position, input value, focus, running animation, all of itthe input rides along for free
  6. An index-tracked "no change" still lets ordinary change detection re-check every binding inside each retained node — {{ user.name }} updates, but nothing not bound to Angular gets touched at allcorrect text, wrong everything else

Step 4 is the lesson, and it isn't a bug — the differ is doing exactly what its key told it to do. Handing it $index as an identity is a legitimate choice for a list that never reorders; the mistake is that nothing stops you from making that choice on a list that later grows a sort button, an inline edit, or a checkbox, at which point the differ is still honoring a promise ("position is identity") that your UI broke months ago.

A @for (user of users(); track $index) table has row 2's <input> mid-edit — you've typed "Sr." into the name field but haven't saved it. Elsewhere on the page, an unrelated click runs users.update(list => [...list].reverse()). What happens to your unsaved "Sr."?

A reasonable guess if you think of the reorder as something happening "over there," to the array, separate from anything already on screen. But the reorder's whole effect is on-screen: every retained node gets re-checked, and the ones bound to Angular (the name, the id badge) get rewritten to match whichever user now maps to that index — your row is one of them, it just doesn't look like it moved.

Right — and the unsettling part is that everything Angular touched is correct. It rewrote the bindings it owns exactly the way it's supposed to. Your "Sr." was never one of those bindings, so it stayed exactly where you left it: physically inside a node that now belongs, as far as its label is concerned, to someone else.

There's no reset step here to trigger — track $index doesn't create a new input or a new form control for that slot, it keeps the one that's already there. Nothing in this path clears a value; the surprising part is the opposite of a reset — everything you typed survives, just misattached.

Where you've seen this before

Three stacks, one rule: identity travels with the thing, never with the slot it's currently sitting in.

React's key prop — same rule, different framework

React's reconciler runs the identical algorithm: diff the old children against the new ones, matched by key. .map((item, i) => <Row key={i} />) is React's track $index, and it produces the exact same "typed text ends up on the wrong row" bug that's been a React footgun for years before Angular made the equivalent mandatory.

track ≈ key — same job, same failure mode

A SQL primary key vs. ORDER BY position

A row's identity is its primary key, never the slot it occupies in a result set. ORDER BY email can put row 42 in position 0 today and position 3 tomorrow without a single column of row 42 changing. Code that caches or keys UI state off "the row at index 3" instead of the primary key has the identical bug as track $index, just one layer further from the browser.

primary key ≠ row position, ever

Linked-identity chips on a CIAM account page

A profile screen lists every IdP a user has linked — Ping, Entra, a social login — as @for (link of links(); track link.subjectId). An admin clicks "revoke" on one chip from a support console at the same moment a background refresh re-sorts the list by last-used. Track by subjectId and the revoke click stays glued to the identity it was aimed at, mid-reorder or not. Track by $index and there's a real window where that click lands on whichever provider the reorder just slid into that slot instead.

subjectId, never position, is the only safe key on this screen
Questions from the back row

If track user.id is always safer, why does @for even allow track $index?

Because for the right list, $index isn't wrong — it's just narrower than habit assumes. A read-only list of primitive values, or one that only ever appends at the tail, has no identity worth tracking beyond position, and $index is one less field to maintain. The real mistake is reaching for it by default and then adding a sort button, an inline edit, or a checkbox to that same list six months later without revisiting the track clause you wrote when none of that existed yet.

Does track user — the whole object, no .id needed — fix this without adding an id field?

Only if the same object reference survives between renders. If a signal is updated with users.set([...draft]) reusing the original objects, track user works, because Angular is tracking by reference and the references didn't change. But the moment users() comes from a fresh HTTP response, or a .map() that builds new object literals, every item is a "new" reference even when nothing about the person changed — and you get a full destroy-and-recreate of the whole list on every refresh, which is worse than either $index or an id. A real field beats a reference every time you don't fully control where the array comes from.

Does identity matter for @if and @switch too, or is this only a @for problem?

It's specifically a @for problem, because @if/@switch never have more than one instance of a branch alive at once — there's no "which of several nodes is this" question to answer, only "does this one exist or not." What they do inherit from being compiler-native rather than directive-based (the old *ngIf) is that a branch is always fully created or fully torn down on a flip, never patched in place — the same "no ambiguity" property track is trying to buy you for a list, arrived at from the opposite direction.

1. Why track is required (and what it does)

When a list changes, Angular doesn't blindly rebuild it. It reconciles: it matches each new item to an existing DOM node using the track expression as the identity key, then reuses, moves, creates, or destroys nodes accordingly. The right key means existing nodes (and their component state, focus, animations) are preserved.

@for (item of items(); track item.id) {   // ✅ stable identity
  <app-card [item]="item" />
} @empty {
  <p>No items.</p>
}

It's mandatory now: a bare @for (item of items()) won't compile — the framework forces you to think about identity. (In the old *ngFor, trackBy was optional and usually forgotten, defaulting to object-identity.)

3. The takeaways

track by stable id → reuse

  • Existing rows keep their exact DOM nodes — component instances, <input> values, focus, scroll position, and running animations all survive.
  • Reorders become moves, not rebuilds.
  • Minimal DOM work = best performance on big or frequently-changing lists.

track $index → content rewrites

  • Identity = position, so any insert/remove/reorder makes slots hold different items — Angular keeps the node but rewrites its bindings.
  • For plain text it looks fine; but per-row state (a typed input, a checkbox, focus) is now on the wrong row.
  • Only safe when the list is static or append-only, or items have no identity.

Rule: track by a stable, unique business id (item.id). Use $index only for primitive lists with no identity (e.g. @for (n of [1,2,3]; track $index)). Angular also special-cases identity-tracking when you write track item for objects that are themselves stable references.

4. @for's contextual variables & @empty

@for (user of users(); track user.id; let i = $index, isLast = $last) {  // track by stable id, alias $index/$last to i/isLast
  <div [class.first]="$first" [class.even]="$even">  // $first/$even are built in — no manual index math
    {{ i + 1 }}. {{ user.name }} {{ isLast ? '(last)' : '' }}  // i is 0-based, so +1 here just for display
  </div>
} @empty {  // runs ONLY when the collection has zero items
  <p>No users yet.</p>
}

5. @if / @switch internals

@if with binding & narrowing

@if (user(); as u) {        // alias the truthy value
  {{ u.name }}              // u is narrowed, non-null
} @else if (loading()) {
  <app-spinner/>
} @else {
  <p>Not found.</p>
}
  • Real @else if/@else — no nested ng-template wiring.
  • as u binds and type-narrows the expression inside the block.
  • Built into the compiler (not a structural directive), so it's eager and a touch faster.

@switch

@switch (status()) {
  @case ('loading') { <app-spinner/> }
  @case ('error')   { <app-error/> }
  @default          { <app-list/> }
}
  • Strict equality (===), no fall-through, no ngSwitchCase directives.
  • Only the matching branch is created; switching cases destroys the old branch and creates the new one.
  • Pairs perfectly with a discriminated-union status signal.

6. Why the new control flow is also faster

  • No structural directives: @if/@for/@switch are compiled into the template's instructions directly, instead of going through *ngIf/*ngFor directive instances and ng-templates.
  • Mandatory track: the optimal-by-default reconciliation that *ngFor only got when you remembered trackBy.
  • Smaller bundles: the control-flow directives no longer need to be imported (CommonModule/NgIf/NgFor drop out).
  • Better ergonomics: @empty, real @else if, and aliasing remove the old template boilerplate.

Migrate automatically with ng generate @angular/core:control-flow.

7. One-sentence recap

🔑 @for makes track mandatory because that key is the identity Angular uses to reconcile the list — track item.id preserves existing DOM nodes (and their state/focus) across inserts and reorders, while track $index ties identity to position and rewrites node content when the structure shifts; combine it with @empty, the $index/$first/$last contextuals, and compiler-native @if/@switch for faster, boilerplate-free templates.
