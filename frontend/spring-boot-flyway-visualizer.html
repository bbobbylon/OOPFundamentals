Database Migrations with Flyway

Version-control your database schema the same way you version-control your code — reproducibly, collaboratively, and automatically on startup.

What is Flyway — and why is running raw SQL scripts against production databases dangerous without it?

Without database migration tooling, schema changes are managed manually: someone SSHes into the server, runs a ALTER TABLE script, crosses their fingers. Problems: "Did this run in staging? Did it run in prod? What order did we apply them? Can a new developer reproduce the DB from scratch?" Flyway solves this by treating your database schema exactly like source code: versioned SQL files (V1__create_users.sql, V2__add_roles.sql) committed to Git. On startup, Spring Boot automatically runs Flyway, which checks which migrations have already run (stored in the flyway_schema_history table), and runs only the new ones in order. New developer joins? They clone the repo and run the app — the DB is created automatically. Staging vs prod? Same migrations, same order, guaranteed.

File naming convention

V{version}__{description}.sql in src/main/resources/db/migration/. Examples: V1__create_users_table.sql, V2__add_roles.sql, V3__add_user_status_column.sql. Version must increase monotonically. Flyway checks the checksum of each applied migration — if you modify an already-applied migration file, startup fails with a checksum error. Never modify a migration that's been run. Add a new migration instead: V4__fix_users_email_index.sql.

Repeatable and undo migrations

R__{description}.sql — repeatable migrations (prefix R, two underscores). Re-applied every time their checksum changes. Use for: views, stored procedures, seed reference data that you update regularly. U{version}__{description}.sql — undo migration (Flyway Teams/Pro): rolls back a specific version. Free Flyway doesn't support undo — you write a new forward migration that reverts the change. This is fine for most use cases.

Production safety

Risky migrations (DROP COLUMN, rename column) need care. Adding a column with a default value: safe (non-locking in most DBs). DROP TABLE: needs a two-step deploy (first make app ignore the column, then drop it in a later migration). For large tables, use pg_repack or online DDL to avoid table locks. Test every migration against a production-size dataset in staging before applying. Use flyway.validateOnMigrate=true (default) to detect corrupt migrations.

In CIAM: V1__create_users.sql: CREATE TABLE users (id BIGSERIAL, email VARCHAR(255) UNIQUE NOT NULL, display_name VARCHAR(255), status VARCHAR(50) DEFAULT 'PENDING', created_at TIMESTAMP, created_by VARCHAR(255)). V2__create_roles.sql: roles + user_roles join table. V3__create_refresh_tokens.sql: token family, token hash, expires_at, revoked. V4__create_audit_log.sql: actor, action, target_user_id, occurred_at, ip_address. Every new feature that needs schema changes = a new versioned migration file committed alongside the code change.

1 — The Problem Without Migrations

Many tutorials show spring.jpa.hibernate.ddl-auto=create-drop or a plain schema.sql to bootstrap a database. This is fine in a demo, but it causes serious problems in real projects.

WITHOUT migrations (schema.sql)
-- schema.sql runs on EVERY startup DROP TABLE IF EXISTS users; CREATE TABLE users ( id BIGINT PRIMARY KEY, name VARCHAR(255) );
Every restart drops all production data. Adding a column means manually running SQL on every developer machine and every environment. There is no record of what changed or when.
WITH Flyway migrations
-- V1__create_users.sql (runs once, ever) CREATE TABLE users ( id BIGINT PRIMARY KEY, name VARCHAR(255) ); -- V2__add_email_column.sql (added later) ALTER TABLE users ADD COLUMN email VARCHAR(255);
Flyway tracks which scripts have already run. Each script runs exactly once, in order, on every environment automatically. Schema and code ship together.
Four real pains solved by Flyway
1. Data destruction — schema.sql drops tables on every restart.
2. Team drift — "works on my machine" because Alice's DB has a column Bob's doesn't.
3. Prod vs dev gap — production diverges from development over months of manual patches.
4. Manual rollbacks — no record of what was applied, so undoing is guesswork.

2 — Flyway vs Liquibase

Both tools solve the same problem. Flyway favours plain SQL and simplicity; Liquibase favours a database-agnostic XML/YAML changelog with more features. For most Spring Boot projects, Flyway is the better default.

Feature Flyway Liquibase
Migration format Plain SQL (or Java) XML / YAML / JSON / SQL
Learning curve Low — just write SQL Medium — XML changeset syntax
Spring Boot auto-config Full — zero config to start Full — zero config to start
Checksum enforcement Yes — SHA-256 per file Yes — MD5 per changeset
Undo / rollback Teams tier only (paid) Free with <rollback> tags
Conditional migrations Limited (Java migrations) Rich (preconditions XML)
Dry run / diff Enterprise only Free CLI diff
Best for Most Spring Boot projects Complex multi-DB enterprise projects
Verdict: Use Flyway unless you need database-agnostic migrations or complex rollback scripting. Its plain-SQL approach means any DBA can read, review, and write migrations without learning a new format.

4 — Project Structure

src/ └── main/ └── resources/ ├── application.properties └── db/ └── migration/ ← default location Flyway scans ├── V1__create_users.sql ← runs first ├── V2__add_email_index.sql ← runs second ├── V3__create_orders.sql ← runs third ├── V4__add_order_status.sql ← runs fourth └── R__seed_countries.sql ← repeatable, runs if checksum changes
The default scan path is classpath:db/migration. You can override it with spring.flyway.locations — for example to scan multiple directories (classpath:db/migration,filesystem:/opt/sql), or to use different paths per Spring profile.

5 — Maven Dependency & application.properties

pom.xml
<!-- Spring Boot manages the version --> <dependency> <groupId>org.flywaydb</groupId> <artifactId>flyway-core</artifactId> </dependency> <!-- If using MySQL, also add: --> <dependency> <groupId>org.flywaydb</groupId> <artifactId>flyway-mysql</artifactId> </dependency>
application.properties
# Flyway is enabled by default when # flyway-core is on the classpath spring.flyway.enabled=true # Custom location (optional) spring.flyway.locations=classpath:db/migration # For existing databases (see §6) spring.flyway.baseline-on-migrate=false # Fail if migration scripts are # missing from the DB (default true) spring.flyway.validate-on-migrate=true # Allow out-of-order migration runs spring.flyway.out-of-order=false
Spring Boot autoconfigures Flyway completely. Just add the dependency and put your SQL files in src/main/resources/db/migration/. On the next startup Flyway runs before Hibernate initialises, so your schema is always ready before the app takes requests.

6 — The flyway_schema_history Table

The first time Flyway runs it creates a bookkeeping table called flyway_schema_history in your database. Every migration it applies gets a row. This is the source of truth for "what has already been run".

installed_rank version description type script checksum installed_by installed_on execution_time success
1 1 create users SQL V1__create_users.sql -1283447128 sa 2024-05-01 09:12:34 42ms true
2 2 add email index SQL V2__add_email_index.sql 872634901 sa 2024-05-08 14:03:11 18ms true
3 3 create orders SQL V3__create_orders.sql -2047832910 sa 2024-05-15 10:44:02 61ms true
4 4 add order status SQL V4__add_order_status.sql 1473920845 sa 2024-05-22 16:01:59 9ms true
The Checksum Trap. Flyway computes a checksum (CRC32) for every applied migration file. If you edit V2__add_email_index.sql after it has already been applied to any environment, the next startup will throw:

Migration checksum mismatch for migration version 2

This is intentional — it prevents silent schema drift. Never modify an applied migration. Create a new V5__... instead.

8 — Migration States

Pending
File exists on disk but has not been applied to this database yet. Will run on the next migrate.
Success
Applied cleanly with no errors. Recorded in flyway_schema_history with success=true.
Failed
Script threw an error mid-run. Row is recorded with success=false. Only databases with transactional DDL (PostgreSQL) auto-roll back. MySQL does not — the schema may be half-applied.
Ignored
Version is lower than the current baseline version, or out-of-order is disabled and a lower-version file appeared after higher ones were already applied.
Repeatable
R__ prefixed files have no version. They re-run whenever their checksum changes. Always run after all versioned migrations.
What to do with a Failed migration on MySQL/MariaDB: Fix the SQL, then run flyway repair to remove the failed row from the history table. Then rerun flyway migrate. On PostgreSQL the DDL rolls back automatically, so just fix and rerun.

9 — Repeatable Migrations

Versioned migrations run once. Repeatable migrations (R__ prefix) run every time their checksum changes. They are always applied after all versioned migrations, in alphabetical order.

R__seed_countries.sql
-- Repeatable: safe to re-run TRUNCATE TABLE countries; INSERT INTO countries (code, name) VALUES ('AU', 'Australia'), ('US', 'United States'), ('GB', 'United Kingdom'), ('DE', 'Germany'); -- add 'CA' here → checksum changes -- → Flyway re-runs this file
Good uses for R__ files
R__seed_countries.sqlReference / lookup data
R__seed_test_users.sqlDev/test fixture data
R__update_views.sqlRecreate database views
R__update_procedures.sqlStored procedures
Rule: Every statement in a repeatable migration must be safe to run multiple times (use TRUNCATE + INSERT or CREATE OR REPLACE, not plain INSERT which will duplicate rows).

10 — Best Practices

PracticeWhy
🚫 Never modify an applied migration Flyway stores a checksum. Editing an applied file causes a checksum mismatch error on the next startup. Create a new versioned migration instead.
🧪 Test migrations in staging first A migration that drops a column or renames a table is irreversible on MySQL. Always run against a staging environment with production-like data before deploying to prod.
✂️ Keep migrations small and focused One migration, one concern. A 500-line migration that creates tables, adds indexes, and back-fills data is hard to debug when one statement fails.
☕ Use Java migrations for complex data transforms Implement JavaMigration when you need to read existing rows, transform them in Java, and write them back. SQL alone can't call business logic.
📦 Store migrations in version control with the code A feature branch that adds a new column should contain both the Java code that uses it and the migration that creates it. They ship together, they review together.
🏷️ Use date-based versions in teams V20240521001__... avoids version conflicts when multiple developers create migrations in parallel branches. Sequential integers clash when branches merge.
⚠️ Never run flyway clean in production clean drops every object in the schema. Disable it with spring.flyway.clean-disabled=true (default in Spring Boot 3+) so it can never be triggered accidentally.

11 — Common Flyway CLI Commands

These same operations are available via the Flyway CLI, Maven plugin (mvn flyway:migrate), Gradle plugin, or the Flyway Java API. In Spring Boot, migrate runs automatically on startup.

CommandWhat it does
migrate Apply all pending versioned migrations in order, then run repeatable migrations whose checksums changed. The one you use all the time.
info Print the status of every migration — Pending, Success, Failed, Ignored. Useful before deploying to see what will run. Does not change the database.
validate Verify that the checksums of all applied migrations still match the files on disk. Fails fast if someone edited a migration after it was applied. Runs automatically before migrate by default.
repair Remove failed migration rows from flyway_schema_history and realign checksums after you have fixed a broken migration file. Use this to recover from a Failed state on MySQL.
baseline Mark an existing database (that predates Flyway) as already at a given version. Flyway will then only apply migrations newer than the baseline. Needed when adopting Flyway on a live project. Set spring.flyway.baseline-on-migrate=true to automate this.
clean DANGER — drops every table, view, index, and stored procedure in the schema. Useful in development to reset a local database to scratch. Blocked by default in Spring Boot 3+. Never use in production. Enable only with spring.flyway.clean-disabled=false and only in dev profiles.

Bonus — Java-Based Migration

When a migration needs to call Spring beans, transform data row-by-row, or use libraries, implement JavaMigration directly. Spring Boot's Flyway auto-configuration picks up these beans automatically.

@Component public class V5__BackfillUserSlugs implements JavaMigration { @Autowired private JdbcTemplate jdbc; @Override public MigrationVersion getVersion() { return MigrationVersion.fromVersion("5"); } @Override public String getDescription() { return "Backfill user slugs from display names"; } @Override public void migrate(Context context) { // Query with JDBC — can call any Java / Spring logic List<Map<String, Object>> rows = jdbc.queryForList("SELECT id, name FROM users WHERE slug IS NULL"); for (Map<String, Object> row : rows) { String slug = toSlug((String) row.get("name")); jdbc.update("UPDATE users SET slug = ? WHERE id = ?", slug, row.get("id")); } } private String toSlug(String name) { return name.toLowerCase().replaceAll("[^a-z0-9]+", "-").trim(); } }
