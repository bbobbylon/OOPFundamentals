Concurrent Hooks

React 18's concurrent renderer can prioritize, pause, and discard work. These hooks are how you tap into it: useTransition and useDeferredValue for responsiveness, useId for SSR-safe IDs, useSyncExternalStore for tear-free external state.

⚡ What is React 18 concurrent rendering — and what problem do the new hooks solve?

React 18's concurrent renderer (default with createRoot) can work on several updates at once, prioritize some over others, and discard stale work. It introduces lanes — priority levels — so typing/clicking stays high-priority while a big list filter runs low-priority. Four hooks expose it: useTransition marks an update non-urgent (shows old UI, returns [isPending, startTransition]); useDeferredValue does the same for a value you receive but can't set; useId makes a stable SSR-safe id (no hydration mismatch on <label htmlFor>); and useSyncExternalStore subscribes to external stores (Zustand/Redux) without "tearing."

  • Lanes = priority levels — urgent input beats background re-render.
  • useTransition marks updates non-urgent; isPending drives a spinner.
  • useDeferredValue defers a value you don't own (parent-supplied query).
  • useId SSR-safe ids; useSyncExternalStore tear-free external state.

useTransition

function RoleFilter() { const [selectedRole, setSelectedRole] = useState('ALL'); const [filteredUsers, setFilteredUsers] = useState(allUsers); const [isPending, startTransition] = useTransition(); const handleRoleChange = (role: string) => { // Urgent: update the dropdown immediately setSelectedRole(role); // Non-urgent: filter might be slow (10k users) startTransition(() => { // React can interrupt this if user clicks again setFilteredUsers(allUsers.filter(u => role === 'ALL' || u.roles.includes(role) )); }); }; return ( <> <select value={selectedRole} onChange={e => handleRoleChange(e.target.value)}> <option value="ALL">All roles</option> </select> {isPending && <span>Filtering…</span>} <UserList users={filteredUsers} /> </> ); }

useDeferredValue

// useDeferredValue: when you can't control the setter // (e.g., search query comes from a parent) function UserList({ query }: { query: string }) { // deferredQuery lags behind query during rendering const deferredQuery = useDeferredValue(query); // isStale: true when query !== deferredQuery // (React is still working on the update) const isStale = deferredQuery !== query; const filtered = useMemo( () => allUsers.filter(u => u.name.includes(deferredQuery)), [deferredQuery] ); return ( <ul style={{ opacity: isStale ? 0.5 : 1 }}> {filtered.map(u => <UserRow key={u.id} user={u} />)} </ul> ); } // While new query is being processed, list shows // old results at 50% opacity (stale indicator)

useId + useSyncExternalStore

// useId: stable SSR-safe IDs function EmailField() { const id = useId(); // e.g., ':r3:' (stable on server+client) return ( <> <label htmlFor={id}>Email</label> <input id={id} type="email" /> </> ); } // Never use Math.random() or a counter for IDs — // they differ between server and client render // → hydration mismatch error // useSyncExternalStore: subscribe to external state // (Zustand uses this internally) const users = useSyncExternalStore( userStore.subscribe, // subscribe(callback): void userStore.getSnapshot, // getSnapshot(): UsersState userStore.getServerSnapshot // optional: for SSR );

Angular equivalent & CIAM: useTransition ≈ @defer (on interaction) / OnPush; useDeferredValue ≈ RxJS debounceTime()+distinctUntilChanged(); useId ≈ CDK-generated ARIA ids; useSyncExternalStore ≈ Angular Signals' fine-grained subscriptions. In a CIAM app: useTransition for role-filtering a large user table, useDeferredValue for search-while-typing, and useId for accessible labels in the create-user dialog.

1. The four concurrent hooks at a glance

HookProblem it solvesReturns
useTransitionAn expensive state update freezes the UI[isPending, startTransition]
useDeferredValueRe-rendering on every keystroke is jankya lagging copy of the value
useIdUnique IDs that match across SSR + clienta stable string id
useSyncExternalStoreExternal stores can "tear" in concurrent modethe current store snapshot
"Urgent" vs "transition" updates. Typing, clicking, and pressing keys are urgent — they must feel instant. Re-rendering a 10,000-row filtered list is a transition — it can lag a frame or two. Concurrent React lets you label the slow update so it never blocks the fast one.

2. useTransition vs useDeferredValue

useTransition — you own the setter

const [isPending, startTransition] = useTransition();

function onChange(e) {
 setQuery(e.target.value); // urgent
 startTransition(() => {
  setResults(filter(big, e.target.value)); // deferred
 });
}

useDeferredValue — you only have the value

const query = props.query; // can't wrap the setter
const deferred = useDeferredValue(query);

// list re-renders at low priority using `deferred`
<List query={deferred} />
Pick by what you control. Use useTransition when you trigger the update yourself (you can wrap the setState). Use useDeferredValue when the value arrives as a prop you cannot wrap — you defer the value instead of the setter. Both keep urgent input snappy.

3. useId — and what it is NOT for

const id = useId();
<label htmlFor={id}>Email</label>
<input id={id} /> // e.g. ":r3:" — matches on server + client
useId is for accessibility attributes, not list keys. It produces IDs derived from the component's position in the tree so the server-rendered HTML and the client hydration generate the same string — eliminating hydration mismatches. Never use it as a key in a list (keys need to come from your data), and never use Math.random() for IDs (it differs between server and client → hydration error).
