Dependency Injection & the IoC Container

The idea the whole framework is built on: you don't create your objects — Spring does, and hands them their dependencies

1. The problem — wiring objects by hand

Without DI — you new everything

class OrderService {
  // OrderService must KNOW how to build its deps
  private OrderRepository repo =
      new OrderRepository(
          new DataSource("jdbc:...", "user", "pw"));
  private EmailClient email = new SmtpEmailClient();
}

Problems:

✗ Tightly coupled to SmtpEmailClient — can't swap for tests
✗ Knows DB credentials — leaky responsibility
✗ Every object rebuilt everywhere — no sharing
✗ Change a constructor → edit dozens of call sites

With DI — you declare what you need

@Service
class OrderService {
  private final OrderRepository repo;
  private final EmailClient email;

  // "I need these" — Spring provides them
  OrderService(OrderRepository repo, EmailClient email) {
    this.repo = repo;
    this.email = email;
  }
}
✓ Depends on the EmailClient interface — swap freely
✓ Knows nothing about DB setup
✓ One shared instance, wired once
✓ Trivial to unit-test (pass mocks to the constructor)

2. "Inversion of Control" — who's in charge?

Normally your code calls libraries and builds its own objects. With IoC, you hand control to the framework: Spring builds your objects and injects their dependencies. That inversion — the container calling you, not you calling it — is where the name comes from.

Traditional: your code → new Dependency() vs IoC: container creates & injects → your code receives

Dependency Injection is the specific technique that implements IoC: dependencies are injected from outside rather than created inside. The IoC container (Spring's ApplicationContext) is the thing that does the injecting.

3. The container & how beans get in it

Component scanning finds your beans

On startup, Spring scans your packages for stereotype annotations and registers each class as a bean (a managed object) in the ApplicationContext.

@SpringBootApplication // enables scanning of this pkg + below
public class App {
  public static void main(String[] args) {
    SpringApplication.run(App.class, args);
    // → container starts, scans, creates & wires all beans
  }
}
AnnotationMarks a…
@Componentgeneric Spring-managed bean
@Servicebusiness-logic bean (a @Component)
@Repositorydata-access bean (+ exception translation)
@Controller / @RestControllerweb endpoint bean

@Service/@Repository/@Controller are all specialized @Components — same registration, clearer intent (and a few extras).

For classes you don't own: @Bean

You can't put @Component on a third-party class. Instead, declare a factory method in a @Configuration class.

@Configuration
public class AppConfig {

  @Bean // the return value becomes a bean
  public RestClient restClient() {
    return RestClient.builder()
        .baseUrl("https://api.example.com")
        .build();
  }

  @Bean
  public ObjectMapper objectMapper() {
    return new ObjectMapper().findAndRegisterModules();
  }
}
@Component scan + @Bean methods → ApplicationContext

5. Three injection styles — and why constructor wins

Constructor injection recommended

@Service
class OrderService {
  private final OrderRepository repo;

  // no @Autowired needed for a single constructor
  OrderService(OrderRepository repo) {
    this.repo = repo;
  }
}
✓ Fields can be final → truly immutable
✓ Impossible to construct in an invalid state
✓ Dependencies obvious & testable (just call new)
✓ Fails fast at startup if a dependency is missing

Pair with Lombok @RequiredArgsConstructor to skip the boilerplate constructor (it generates one for all final fields).

Field & setter injection — avoid

// FIELD injection — looks clean, hides problems
@Service
class OrderService {
  @Autowired OrderRepository repo; // not final!
}
✗ Can't be final — mutable, nullable
✗ Hidden deps — easy to pile on 10 of them
✗ Hard to unit-test without Spring/reflection
✗ Can hide circular-dependency bugs until runtime
// SETTER injection — only for true optionals
@Autowired(required = false)
void setMetrics(MetricsClient m) { this.metrics = m; }

6. Two beans of the same type? Resolve the ambiguity

@Primary and @Qualifier

// two EmailClient implementations exist
@Component @Primary           // the default choice
class SmtpEmailClient implements EmailClient {}

@Component("sesClient")
class SesEmailClient implements EmailClient {}

@Service
class Notifier {
  // gets SmtpEmailClient (the @Primary)
  Notifier(EmailClient email) { … }

  // …or ask for a specific one by name
  Notifier(@Qualifier("sesClient") EmailClient e) { … }
}

Without one of these, Spring throws NoUniqueBeanDefinitionException at startup — a good fail-fast.

Conditional beans by environment

// pick an implementation per profile
@Component @Profile("prod")
class RealPaymentGateway implements Gateway {}

@Component @Profile("dev")
class FakePaymentGateway implements Gateway {}

// only the matching one is registered as a bean
// → inject Gateway, get the right impl per env

Also: @ConditionalOnProperty, @ConditionalOnMissingBean (how Spring Boot auto-config backs off when you define your own bean).

7. Bean scopes — how many instances?

Singleton (default) vs prototype

@Service // singleton: ONE instance for the whole app
class OrderService {}

@Component
@Scope("prototype") // NEW instance every injection/lookup
class ShoppingCart {}
ScopeInstances
singleton (default)one per container
prototypenew each time requested
requestone per HTTP request
sessionone per HTTP session

⚠ Singletons must be stateless — they're shared across all threads. Storing per-request data in a singleton field is a classic concurrency bug.

call context.getBean(...) repeatedly
Singletons return the SAME object hash each call; prototypes return a NEW one.

8. Circular dependencies — the startup error you'll hit

The problem

@Service class A { A(B b) {} }
@Service class B { B(A a) {} }

// A needs B to be built, B needs A to be built…
// → BeanCurrentlyInCreationException at startup
A → needs B & B → needs A = 🔁 deadlock

The fix — usually a design smell

✓ Best: extract the shared logic into a third bean both depend on
✓ Rethink responsibilities — a cycle means A and B are too entangled
○ Last resort: @Lazy on one dependency (breaks the cycle by deferring creation)
✗ Field injection "fixes" it by hiding it — the cycle is still there
// @Lazy escape hatch (prefer redesign)
A(@Lazy B b) { this.b = b; }
