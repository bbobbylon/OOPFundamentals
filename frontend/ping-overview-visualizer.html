IDM & Ping Identity Overview

What Identity Management is, why enterprises need it, and how the Ping Identity product suite fits together.

What is Ping Identity / ForgeRock — and why does every enterprise CIAM build use this suite of four interconnected engines?

Ping Identity (which acquired ForgeRock in 2023) is an enterprise CIAM (Customer Identity and Access Management) platform. The suite is organized around four specialized engines that together handle every aspect of digital identity: who someone is, how they prove it, how their account is managed over time, and how access to protected resources is enforced. PingAM (formerly ForgeRock AM / OpenAM): the authentication and authorization engine. The "front door." Handles login journeys (declarative trees of authentication nodes), SSO (Single Sign-On), OAuth2/OIDC token issuance, SAML federation, MFA (push, TOTP, biometrics), adaptive risk-based authentication, and the policy engine (who can access what resource). PingIDM (formerly ForgeRock IDM / OpenIDM): the identity lifecycle engine. Manages the full Joiner-Mover-Leaver cycle — creating accounts when someone is hired, updating them when roles change, deprovisioning them when they leave. Connects to HR systems, Active Directory, Salesforce, Workday via connectors. Handles self-service registration, profile management, sync, and reconciliation. PingDS (formerly ForgeRock DS / OpenDJ): the identity store — a hardened LDAP directory built for hundreds of millions of consumer identities with microsecond read latency and multi-site replication. Often the system of record for CIAM user profiles. PingGateway (formerly ForgeRock IG / OpenIG): the enforcement point. A reverse proxy that fronts APIs and applications, validates tokens, enforces AM policy, and retrofits SSO onto legacy apps that can't speak OIDC. The cloud version — PingOne Advanced Identity Cloud — delivers the entire stack as a SaaS service. PingOne DaVinci is the no-code flow orchestration (equivalent to AM journeys). Understanding which box does what is the foundation of every Ping/ForgeRock interview and every production CIAM build.

Joiner-Mover-Leaver lifecycle

// JOINER: new employee hired // HR system → PingIDM connector // IDM creates: PingDS account, AD account, Salesforce user // AM notified: user can now authenticate // Welcome email sent with self-service activation link // MOVER: employee changes department // HR updates title/department → IDM reconciliation picks up delta // IDM updates: AD group memberships (remove old, add new) // AM: policy now grants access to new org's resources // IDM: revokes old entitlements (Salesforce role change) // LEAVER: employee terminated // HR sets status=TERMINATED → IDM connector detects // IDM (in order!): // 1. Invalidate all AM SSO sessions immediately // 2. Revoke all OAuth2 access + refresh tokens // 3. Disable AD account // 4. Disable PingDS account // 5. Log audit event (compliance) // Order matters: if you disable AD first, IDM connector may lose access

Self-managed vs PingOne cloud

// SELF-MANAGED (the ForgeRock stack) // Deploy AM/IDM/DS/IG on your own infra (VMs or Kubernetes) // Typical ports: // AM: https://am.example.com:8443/openam // IDM: https://idm.example.com:8080/openidm // DS: ldap://ds.example.com:1389 // IG: https://ig.example.com:8080 // You control upgrades, scaling, HA, customization // PINGONE (cloud SaaS) // Advanced Identity Cloud = managed ForgeRock stack // Lower-env domains: *.forgeblocks.com // DaVinci = no-code flow builder (cloud AM journeys) // PingOne MFA/Risk/Verify = standalone cloud services // REST-only: no SSH access, config via APIs // HYBRID // On-prem IDM syncs with cloud PingOne // PingGateway fronts on-prem legacy apps // AM/IG in cloud, DS on-prem for data sovereignty

In CIAM / Your Job: This is literally your day job — building and maintaining the Ping/ForgeRock CIAM stack at your organization. In your role, you're most heavily involved with PingAM (OAuth2/OIDC token flows that your Angular frontend and Spring Boot APIs consume), PingIDM (SCIM provisioning to sync identities from HR systems), and PingFederate (the OAuth2 Authorization Server that issues the JWTs your Spring Boot APIs validate with spring-security-oauth2-resource-server). Understanding the platform boundary — which engine owns which concern — prevents the classic mistake of trying to do lifecycle management inside AM journey nodes or putting authorization policy inside your Spring Boot code instead of AM.

Hire event in Workday/SAP HR:
PingIDM detects new employee via HR connector → creates Active Directory account → creates email (Microsoft 365) → provisions Jira seat → grants access to Salesforce based on department → sends welcome email with credentials.
Without IDM: 5 different IT tickets, 2-3 days delay. With IDM: automated, 15 minutes.
Day 1 access:
Employee's badge/email is active. PingIDM assigned application entitlements based on job role. Role-based access: "Software Engineer in Platform team" → gets access to GitHub org, AWS dev account, Confluence, Slack, and dev Kubernetes cluster automatically.
Promotion or department transfer:
HR updates job title in Workday → PingIDM reconciles the change → removes old team's Slack channels + Jira projects → grants new team's access → escalates AD group memberships. All within minutes of the HR change, with a full audit trail.
Termination event:
HR marks employee inactive → PingIDM fires within minutes: disables AD account (blocks all SSO) → revokes all application tokens → removes Salesforce license → archives email → suspends GitHub membership. Meets regulatory requirement: access revoked within 4 hours. Without IDM: orphaned accounts can persist for months.

2 — Ping Identity Product Portfolio

Ping Identity acquired ForgeRock in 2023. Click each product for details:

PingOne

Cloud SaaS

Cloud IDaaS: SSO, MFA, user directories, workforce + customer identity. Quickest to deploy, least customizable.

Use when: you need identity fast, you're cloud-first, you don't need deep customization. Competitors: Okta, Entra ID.

PingFederate

On-prem / cloud

Enterprise federation server. OAuth2/OIDC Authorization Server + SAML Identity Provider. Bridges identity between systems.

Use when: you need fine-grained token customization, you're bridging multiple IdPs, or you have complex enterprise federation requirements. Highly configurable via policies, adapters, and plugins.

PingIDM

formerly ForgeRock Identity Management

Identity lifecycle management. Connectors to LDAP/AD, databases, HR systems, REST APIs. Provisioning + reconciliation.

Use when: you need to automate user lifecycle across many systems. Configuration stored as JSON. Customizable with JavaScript. REST API for everything.

PingDirectory

formerly ForgeRock Directory Services

High-performance LDAP directory + REST API. Stores millions of identity records at scale with low latency.

Use when: you need a high-scale, high-availability identity data store. Often sits behind PingFederate and PingIDM as the authoritative user store.

PingAccess

Policy enforcement proxy

Fine-grained authorization proxy. Enforce access policies before requests reach your apps — at the perimeter.

Works as a reverse proxy or Apache/Nginx plugin. Validates tokens, checks policies, passes authorized requests. Apps don't need their own auth logic.

PingAM

formerly ForgeRock Access Management

Intelligent authentication trees. MFA, risk-based auth, social login, progressive profiling. Replaces PingFederate in newer deployments.

Highly scriptable authentication journeys. Drag-and-drop "authentication trees" to build: if device is trusted AND risk is low → allow; else → MFA challenge.
