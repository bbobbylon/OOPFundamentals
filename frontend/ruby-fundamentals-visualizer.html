Ruby Fundamentals & the Object Model

Ruby is purely object-oriented and unusually consistent: everything is an object, every operation is a message sent to a receiver, and method lookup walks a predictable ancestor chain. Blocks, modules/mixins, and duck typing are the levers that make it so expressive.

💎 What is Ruby — and why does it feel so different from Java?

Ruby is a dynamic, purely object-oriented language designed for programmer happiness. The single biggest mental shift from Java is that everything is an object — 5, true, nil, even a class — and every operation is a message sent to a receiver. 5 + 3 is really 5.+(3): you are calling the + method on the integer object 5. When you call a method, Ruby looks it up by walking the receiver's ancestor chain — its singleton class, then its class, then any modules mixed in, then the superclass, and so on up to BasicObject — and runs the first match (or fires method_missing). Because dispatch is dynamic and based on whether an object responds to a message, Ruby uses duck typing instead of interfaces: if it quacks like a duck, it is one — no shared base class required. Blocks (chunks of code you pass to methods, like [1,2,3].map { |x| x*2 }) are everywhere and are Ruby's answer to lambdas, made first-class as Proc/lambda. Modules serve double duty: namespaces and mixins (include Comparable grants behavior without inheritance). The result is terse, readable code — at the cost of compile-time type checking, which Ruby trades away for flexibility.

  • Everything is an object — integers, nil, classes; 5 + 3 ≡ 5.+(3).
  • Method = message — dispatch walks the ancestor chain; miss → method_missing.
  • Blocks/Procs/lambdas — code passed to methods; the heart of Ruby's iteration.
  • Modules + duck typing — mixins grant behavior; respond-to, not inheritance, defines a type.

Java / Spring comparison

Ruby has no primitives — 5 is a full object, unlike Java's int. A method call is a dynamic message send, so there is no compile-time overload resolution. Mixins (include Module) are how Ruby shares behavior — closer to Java default methods on interfaces than to class inheritance. Duck typing replaces interfaces: you check respond_to?(:save), not instanceof. Blocks ≈ lambdas / functional interfaces, but baked into nearly every collection method. There is no static type checker (though sorbet/RBS add optional types).

Ruby in a CIAM world: Ruby's strength is gluing identity systems together quickly — a few lines to call an OAuth2/OIDC provider, decode a JWT, and map claims to roles. Duck typing means a "token verifier" is just any object that respond_to?(:verify), so swapping Ping for Entra is a config change, not a refactor. The same object model that makes 5.+(3) a message send makes it trivial to wrap an identity client in a decorator or mixin. In Rails (next page) this becomes Devise/OmniAuth for login and before_action filters for auth — Ruby's equivalent of a Spring Security filter chain.

1. A method call is a message send

# these two lines are identical — operators are methods
5 + 3
5.+(3) # => 8 — calling :+ on the object 5

# send the message dynamically by name
5.send(:+, 3) # => 8
5.respond_to?(:+) # => true
There are no operators, only methods. a + b is sugar for a.+(b); a[i] is a.[](i). This is why you can define + on your own class. Method calls are messages — Ruby finds the method at runtime by walking the receiver's ancestor chain, so dispatch is fully dynamic (no compile-time binding).

2. Blocks are the heart of Ruby

# a block is a chunk of code passed to a method
[1, 2, 3].map { |x| x * 2 } # => [2, 4, 6]

# your own method can yield to a block
def twice
  yield
  yield
end
twice { puts "hi" } # prints hi twice

A block is an anonymous closure attached to a method call. yield runs it. Capture it as a Proc with &block, or build one explicitly with proc { } / ->(x){ } (a lambda — stricter arity, and return exits only the lambda).

3. Modules: namespaces and mixins

module Walkable
  def walk = "#{name} is walking"
end

class Person
  include Walkable # mix the behavior in
  attr_reader :name
end
Person.ancestors # => [Person, Walkable, Object, Kernel, BasicObject]
Mixins beat single inheritance. Ruby classes have one superclass, but a class can include many modules. The included module is spliced into the ancestor chain just above the class, so its methods are found during lookup. This is how Comparable, Enumerable, etc. grant whole bundles of behavior from a couple of methods you implement.
