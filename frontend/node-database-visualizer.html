Node — Talking to a Database

Two ways a Node backend reaches a database: a raw parameterized query through a connection pool (pg), and a typed ORM query (Prisma). Same round trip either way — the difference is who builds the SQL, and whether a stray string can become an attacker's SQL.

🗄️ What is a query round trip in Node — and why does the placeholder matter more than the library?

Every Node request that needs data does the same three things: borrow a connection from a pool (opening a fresh TCP connection per request is too slow to do 1,000 times a second), send a query, and give the connection back. The library you pick — pg for raw SQL, Prisma or TypeORM for an ORM — only changes how you write the query, not that round trip. What actually matters is never building SQL by concatenating a string with user input. pool.query('SELECT * FROM users WHERE email = ' + email) lets an attacker send email = "x' OR '1'='1" and turn your WHERE clause into WHERE '1'='1' — every row matches. The fix is a parameterized query: pool.query('SELECT * FROM users WHERE email = $1', [email]) sends the SQL text and the value separately over the wire — the driver never lets the value be interpreted as SQL, no matter what it contains. An ORM like Prisma parameterizes for you by construction: prisma.user.findUnique({ where: { email } }) can't concatenate a string because there is no string to build — you never touch raw SQL at all. Multi-step writes (like transferring money between two rows) need a third idea, a transaction: wrap several statements in BEGIN … COMMIT (or Prisma's $transaction) so they commit together or not at all — a crash between the debit and the credit rolls both back, instead of leaving money gone from one account and never credited to the other.

  • Pool, not a connection per request — new Pool() keeps a small set of live connections and hands them out.
  • Parameterize, never concatenate — $1/$2 placeholders + a values array; the driver escapes for you.
  • An ORM parameterizes by construction — Prisma's query builder has no string to concatenate into.
  • Transactions — BEGIN/COMMIT/ROLLBACK (or $transaction) make several writes succeed or fail as one unit.

Raw, parameterized (pg)

const { rows } = await pool.query( 'SELECT id, roles FROM users WHERE email = $1', [email] ); return rows[0] ?? null;

Typed ORM (Prisma)

const user = await prisma.user.findUnique({ where: { email } }); // user is fully typed — .roles autocompletes

Spring Boot comparison

A pg.Pool ≈ Spring's DataSource connection pool (HikariCP). pool.query(sql, [params]) ≈ NamedParameterJdbcTemplate.queryForObject(sql, params, rowMapper) — the exact same "named/positional placeholders, never string-build SQL" rule this app's own backend recipe follows. Prisma's typed client ≈ Spring Data JDBC's repository — both trade raw SQL control for compile-time-checked queries. prisma.$transaction([...]) ≈ Spring's @Transactional.

CIAM in production: a query built from unsanitized input is exactly how a CIAM system leaks credentials — a login form is the highest-value SQL-injection target on the whole site, because success returns "you are this user." Parameterized queries and ORMs both close that door by construction; the mistake to watch for in review is a stray `WHERE email = '${email}'` template literal that looks fine in a demo and is a full account-takeover in production. The same discipline applies to Spring's JdbcTemplate — queryForObject("... = '" + email + "'", ...) is the identical bug in Java.

The problem

Your queries are all parameterized. Injection isn't the bug that takes this app down.

The return statement that quietly keeps a connection forever

An endpoint checks out a connection, looks up a row, and — if nothing matched — returns a 404 straight away. Perfectly reasonable code. It passes every test, because every test either finds a row or doesn't care what happens next. In production, the app runs fine for hours, then every single request — not just this endpoint — starts hanging with no error, no stack trace, no crash. Nobody touched the SQL. Nobody touched the schema. The queries were never the problem.

every query is parameterized ✓ 404 is the correct status code here ✓ client.release() sits right after the happy path ⚠ the early return skips straight past it ⚠

"The code runs" and "the code always returns the connection it borrowed" are two different claims — this bug is what happens when only the first one gets checked.

Make release() unconditional, not a step in the happy path
client.release() as the last line of the function ↓ any early return, throw, or middleware short-circuit skips right past it client.release() inside a finally block ↓ finally runs on every exit from try — return, throw, or falling off the end The connection always goes back, no matter which path the code takes out
A connection you forgot to release isn't lost — it's permanently "in use." Nothing crashes, nothing throws, nothing logs an error, because from the pool's point of view nothing went wrong: a client asked for a connection, and simply hasn't given it back yet. Section 4 of this page already shows the fix — client.release() inside finally — for the transaction code. The exact same rule has to apply to every plain pool.connect() call too, including ones that never touch BEGIN at all.
Think of the pool as a car-rental counter with exactly ten cars. Each renter must return the keys before the next customer can drive. If a renter parks in their own garage and just keeps the keys — even though their trip is long over — the counter still lists that car as "out." Ten renters like that and the counter has zero cars for an eleventh customer, who waits at the desk not because there are no cars in the city, only because none of this counter's ten ever came back. Where the analogy stops: a real rental company eventually writes off a no-show car. pg.Pool never does — a leaked connection stays "checked out" forever, with nothing watching the clock on it.

The app ran fine for six hours, then every request just hangs — not only the endpoint I touched today. No errors anywhere. What broke?

Nothing broke, from where I sit. I have exactly ten connections. Ten requests checked one out from me, hit a 404 branch that returns before release(), and never told me they were done. I have no idea those ten are never coming back — I'm just out of connections for everyone else.

One of the leaked clients

I'm still marked "checked out." The variable holding me went out of scope the moment that request handler returned — nobody called anything on me again, ever. I'm not running a query. I'm not doing anything. I'm also not available to anyone else. I'm just... open.

Pool

And request eleven, whatever it needs, calls pool.connect() and asks me for one. I don't have one. I don't reject the request — I queue it and wait for a release that is never going to happen. That "hang with no error" you're seeing? That's request eleven, still waiting.

The mechanism

One skipped line, repeated ten times, is indistinguishable from a production outage.

  1. new Pool({ max: 10 }) — ten live connections is the WHOLE budget for this process, forevernot a soft suggestion
  2. A handler calls pool.connect(), gets connection #7, queries, finds no row, and returns a 404 — before the client.release() linethe lesson
  3. Connection #7 is still marked checked out in Pool's bookkeeping — nothing ever told Pool otherwiseleaked, not lost — the object still exists
  4. Over the next few hours, nine more requests hit that same 404 branchone leak looks like nothing; ten is the whole pool
  5. Pool now has zero free connections; a completely unrelated, correctly-written request calls pool.connect()not an error yet — a pending promise
  6. node-postgres has no connection-acquire timeout configured by default — the call just waits, because none of the ten checked-out clients will ever be releasedthis is the "random hang," fully explained

Step 2 is the entire lesson. Every step after it is just arithmetic — how many leaks it takes to reach max — and a default (no acquire timeout) doing exactly what it's documented to do. Fix step 2 with a finally block and steps 3 through 6 never get a chance to happen, no matter how many requests hit that 404 branch.

FREE — sitting in the pool a request calls pool.connect() → CHECKED OUT
CHECKED OUT — doing work handler finishes, calls client.release() → back to FREE
CHECKED OUT — forgotten an early return skips release() → nowhere. ever.

The top two rows are the entire healthy lifecycle — a connection cycles between FREE and CHECKED OUT for as long as the process runs. The third row isn't a third state in that cycle at all; it's a connection that left the cycle and never came back. Ten connections stuck in row three is the same as having a pool of size zero.

A route handler does const client = await pool.connect(), runs a query, and on a "not found" result does return res.status(404).json(...) — before its client.release() line. The pool was created with new Pool({ max: 10 }). This 404 branch gets hit 10 times over the next hour. What happens when the 11th request — to any endpoint sharing this pool — calls pool.connect()?

A reasonable guess if you picture the pool as a dumb round-robin list. It isn't — the pool tracks per-connection state (free vs. checked-out) precisely so it never hands the same physical connection to two callers at once. A checked-out connection is simply unavailable, not reused.

This describes max as a soft cap that gets exceeded under pressure — the opposite of what it is. max is a hard ceiling on how many physical connections the pool will ever open; node-postgres will not create an 11th to relieve pressure, no matter how many callers are waiting.

Right. All 10 connections are marked "in use," and node-postgres has no connection-acquire timeout configured out of the box, so pool.connect() queues the request and waits for a release. Since the 10 leaked connections were never released — and never will be — that wait has no end. This is exactly what "the app just hangs" looks like from the outside.

Where you've seen this before

Three different pools, the exact same failure mode: a resource that isn't returned isn't available.

Spring's HikariCP has a feature for this exact bug

This page's own intro already calls pg.Pool the equivalent of Spring's DataSource pool, HikariCP — and HikariCP ships a setting node-postgres simply doesn't have: leakDetectionThreshold. Set it, and HikariCP logs a full stack trace the moment any connection has been checked out longer than that threshold without being returned — turning this exact bug from a silent multi-hour production mystery into a log line pointing at the offending code, often within seconds of the leak happening.

HikariCP can tell you it's leaking; pg.Pool cannot

"Too many open files" is the OS-level version

Every process has a fixed limit on open file descriptors (often 1024 by default on Linux). An fs.createReadStream that never gets closed on an error path leaks a descriptor the exact same way a forgotten client.release() leaks a connection — one leak is invisible, and the process throws EMFILE only once enough of them have piled up to exhaust the limit. Same shape, different fixed-size pool.

a fixed pool + one unclosed handle per request = eventual exhaustion

Your browser does this to itself on purpose

Chrome and Firefox cap plain HTTP/1.1 connections at six per origin. Open a page that fires eight simultaneous requests to the same API and you'll watch two of them sit as (pending) in the Network tab — not failed, not slow, just queued behind the other six exactly the way request 11 queues behind Pool's ten. The difference is those six connections DO eventually free up; that's what makes this a size limit instead of a leak.

same queueing behavior, no leak — just a small number
Questions from the back row

Doesn't idleTimeoutMillis eventually clean up a leaked connection for me?

No, and this is the misconception that costs people the most debugging time. idleTimeoutMillis only closes connections sitting idle inside the pool — ones that were properly released and are just waiting for the next caller. A leaked connection was never released, so it never re-enters the pool's free list in the first place; there's no idle clock running on it at all. The pool has nothing to time out, because as far as its bookkeeping goes, that connection is still busy doing legitimate work.

If I use pool.query() everywhere instead of pool.connect(), am I immune to this?

For single statements, yes — pool.query() checks a connection out AND releases it back automatically around that one call, so there's no manual release() for you to forget. The risk in this lesson is specific to the manual pool.connect() / client.release() pattern, which section 4 of this page shows you actually need — a multi-statement transaction has to pin every statement to the same connection, and pool.query() gives you no way to guarantee that.

Would just raising max to, say, 50 fix this?

It buys you time, not a fix — a bigger pool just takes longer to leak down to zero. The exact same 404 branch, hit 50 times instead of 10, produces the identical outage; you've only changed how many hours of uptime it takes to get there. The only real fix is making release() unconditional with finally, so the leak never happens at any pool size.

1. A parameterized query, end to end

import { Pool } from 'pg';

const pool = new Pool({ connectionString: process.env.DATABASE_URL });

async function getUserByEmail(email) {
  const { rows } = await pool.query(
    'SELECT id, email, roles FROM users WHERE email = $1',
    [email] // bound separately from the SQL text
  );
  return rows[0] ?? null;
}
$1 is not string substitution. The driver sends the SQL text SELECT ... WHERE email = $1 and the values array [email] as two separate parts of the wire protocol. Postgres itself substitutes the placeholder after parsing the query as SQL — so a value of "x' OR '1'='1" is bound as one literal string to compare against, never as SQL syntax. This is why parameterizing defeats injection completely, while "escaping quotes yourself" is a losing arms race.

2. What NOT to do: building SQL with a template literal

// DO NOT DO THIS
async function getUserByEmailUNSAFE(email) {
  const { rows } = await pool.query(
    `SELECT id, email, roles FROM users WHERE email = '${email}'` // email is now PART of the SQL
  );
  return rows[0] ?? null;
}

// attacker sends: email = "x' OR '1'='1"
// query becomes: ...WHERE email = 'x' OR '1'='1' -- matches every row
The bug is invisible in the happy path. With a normal email this runs identically to the safe version — same result, same speed. It only breaks when someone deliberately sends a quote character, which is exactly why it survives code review and a demo: nobody tests with an apostrophe in the input. Anywhere you see a template literal or + building a SQL string around a variable, treat it as a finding.

3. The same query through Prisma

import { PrismaClient } from '@prisma/client';
const prisma = new PrismaClient();

async function getUserByEmail(email) {
  return prisma.user.findUnique({
    where: { email }, // generated client, no string to build
    select: { id: true, email: true, roles: true },
  });
  // user.roles is typed as string[] at compile time — a typo in "rols" fails the build
}
You cannot inject what you never build. where: { email } is a plain JS object; Prisma's generated client turns it into a parameterized query behind the scenes, the same $1 mechanism as section 1. The win isn't "safer than pg" — a correctly parameterized pg query is equally safe — it's that there is no string-building step for a future edit to accidentally reintroduce, plus compile-time checked columns.

4. A transaction: two writes that must succeed together

async function transferFunds(fromId, toId, amount) {
  const client = await pool.connect(); // one connection for the whole transaction
  try {
    await client.query('BEGIN');
    await client.query('UPDATE accounts SET balance = balance - $1 WHERE id = $2', [amount, fromId]);
    await client.query('UPDATE accounts SET balance = balance + $1 WHERE id = $2', [amount, toId]);
    await client.query('COMMIT');
  } catch (e) {
    await client.query('ROLLBACK'); // undo the debit too
    throw e;
  } finally {
    client.release(); // back to the pool either way
  }
}
Same connection, or it isn't one transaction. pool.query(...) can silently hand two calls two different connections — BEGIN on one and the UPDATE on another share nothing. pool.connect() checks out a single connection that every statement in the transaction reuses, and client.release() in finally returns it to the pool whether it committed or rolled back. Prisma's equivalent, prisma.$transaction([update1, update2]), does the same BEGIN/COMMIT/ROLLBACK dance for you.
