Node — Talking to a Database

Two ways a Node backend reaches a database: a raw parameterized query through a connection pool (pg), and a typed ORM query (Prisma). Same round trip either way — the difference is who builds the SQL, and whether a stray string can become an attacker's SQL.

🗄️ What is a query round trip in Node — and why does the placeholder matter more than the library?

Every Node request that needs data does the same three things: borrow a connection from a pool (opening a fresh TCP connection per request is too slow to do 1,000 times a second), send a query, and give the connection back. The library you pick — pg for raw SQL, Prisma or TypeORM for an ORM — only changes how you write the query, not that round trip. What actually matters is never building SQL by concatenating a string with user input. pool.query('SELECT * FROM users WHERE email = ' + email) lets an attacker send email = "x' OR '1'='1" and turn your WHERE clause into WHERE '1'='1' — every row matches. The fix is a parameterized query: pool.query('SELECT * FROM users WHERE email = $1', [email]) sends the SQL text and the value separately over the wire — the driver never lets the value be interpreted as SQL, no matter what it contains. An ORM like Prisma parameterizes for you by construction: prisma.user.findUnique({ where: { email } }) can't concatenate a string because there is no string to build — you never touch raw SQL at all. Multi-step writes (like transferring money between two rows) need a third idea, a transaction: wrap several statements in BEGIN … COMMIT (or Prisma's $transaction) so they commit together or not at all — a crash between the debit and the credit rolls both back, instead of leaving money gone from one account and never credited to the other.

  • Pool, not a connection per request — new Pool() keeps a small set of live connections and hands them out.
  • Parameterize, never concatenate — $1/$2 placeholders + a values array; the driver escapes for you.
  • An ORM parameterizes by construction — Prisma's query builder has no string to concatenate into.
  • Transactions — BEGIN/COMMIT/ROLLBACK (or $transaction) make several writes succeed or fail as one unit.

Raw, parameterized (pg)

const { rows } = await pool.query( 'SELECT id, roles FROM users WHERE email = $1', [email] ); return rows[0] ?? null;

Typed ORM (Prisma)

const user = await prisma.user.findUnique({ where: { email } }); // user is fully typed — .roles autocompletes

Spring Boot comparison

A pg.Pool ≈ Spring's DataSource connection pool (HikariCP). pool.query(sql, [params]) ≈ NamedParameterJdbcTemplate.queryForObject(sql, params, rowMapper) — the exact same "named/positional placeholders, never string-build SQL" rule this app's own backend recipe follows. Prisma's typed client ≈ Spring Data JDBC's repository — both trade raw SQL control for compile-time-checked queries. prisma.$transaction([...]) ≈ Spring's @Transactional.

CIAM in production: a query built from unsanitized input is exactly how a CIAM system leaks credentials — a login form is the highest-value SQL-injection target on the whole site, because success returns "you are this user." Parameterized queries and ORMs both close that door by construction; the mistake to watch for in review is a stray `WHERE email = '${email}'` template literal that looks fine in a demo and is a full account-takeover in production. The same discipline applies to Spring's JdbcTemplate — queryForObject("... = '" + email + "'", ...) is the identical bug in Java.

1. A parameterized query, end to end

import { Pool } from 'pg';

const pool = new Pool({ connectionString: process.env.DATABASE_URL });

async function getUserByEmail(email) {
  const { rows } = await pool.query(
    'SELECT id, email, roles FROM users WHERE email = $1',
    [email] // bound separately from the SQL text
  );
  return rows[0] ?? null;
}
$1 is not string substitution. The driver sends the SQL text SELECT ... WHERE email = $1 and the values array [email] as two separate parts of the wire protocol. Postgres itself substitutes the placeholder after parsing the query as SQL — so a value of "x' OR '1'='1" is bound as one literal string to compare against, never as SQL syntax. This is why parameterizing defeats injection completely, while "escaping quotes yourself" is a losing arms race.

2. What NOT to do: building SQL with a template literal

// DO NOT DO THIS
async function getUserByEmailUNSAFE(email) {
  const { rows } = await pool.query(
    `SELECT id, email, roles FROM users WHERE email = '${email}'` // email is now PART of the SQL
  );
  return rows[0] ?? null;
}

// attacker sends: email = "x' OR '1'='1"
// query becomes: ...WHERE email = 'x' OR '1'='1' -- matches every row
The bug is invisible in the happy path. With a normal email this runs identically to the safe version — same result, same speed. It only breaks when someone deliberately sends a quote character, which is exactly why it survives code review and a demo: nobody tests with an apostrophe in the input. Anywhere you see a template literal or + building a SQL string around a variable, treat it as a finding.

3. The same query through Prisma

import { PrismaClient } from '@prisma/client';
const prisma = new PrismaClient();

async function getUserByEmail(email) {
  return prisma.user.findUnique({
    where: { email }, // generated client, no string to build
    select: { id: true, email: true, roles: true },
  });
  // user.roles is typed as string[] at compile time — a typo in "rols" fails the build
}
You cannot inject what you never build. where: { email } is a plain JS object; Prisma's generated client turns it into a parameterized query behind the scenes, the same $1 mechanism as section 1. The win isn't "safer than pg" — a correctly parameterized pg query is equally safe — it's that there is no string-building step for a future edit to accidentally reintroduce, plus compile-time checked columns.

4. A transaction: two writes that must succeed together

async function transferFunds(fromId, toId, amount) {
  const client = await pool.connect(); // one connection for the whole transaction
  try {
    await client.query('BEGIN');
    await client.query('UPDATE accounts SET balance = balance - $1 WHERE id = $2', [amount, fromId]);
    await client.query('UPDATE accounts SET balance = balance + $1 WHERE id = $2', [amount, toId]);
    await client.query('COMMIT');
  } catch (e) {
    await client.query('ROLLBACK'); // undo the debit too
    throw e;
  } finally {
    client.release(); // back to the pool either way
  }
}
Same connection, or it isn't one transaction. pool.query(...) can silently hand two calls two different connections — BEGIN on one and the UPDATE on another share nothing. pool.connect() checks out a single connection that every statement in the transaction reuses, and client.release() in finally returns it to the pool whether it committed or rolled back. Prisma's equivalent, prisma.$transaction([update1, update2]), does the same BEGIN/COMMIT/ROLLBACK dance for you.
