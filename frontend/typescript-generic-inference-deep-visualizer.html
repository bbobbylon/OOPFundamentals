Generic Inference — How T Gets Its Type

The Generics page shows you how to write <T>. This companion shows how the compiler figures out what T is: collecting candidates from the call, letting context flow inward, and the cases where inference gives up and you have to annotate.

🧩 How does TypeScript infer what T is — and why does it sometimes ask you to annotate?

When you call map(arr, fn), TypeScript works out T for you instead of making you write map<string>(...) — that's type-argument inference. It gathers inference candidates (every place T appears in the call), flows context inward to lambdas, and picks the best common type; conflicting candidates become a union. It gives up when T appears only in the return position — falling back to unknown — at which point you annotate explicitly. Constraints (T extends keyof U) keep inference within bounds.

  • Candidates come from arguments, then resolve to a best common type.
  • Context flows inward — a lambda's parameter type is inferred from where it's used.
  • Inference fails when T is return-only → unknown; annotate fn<string>(...).
  • Constraints bound inference — K extends keyof T rejects unknown keys.

Inference candidates

function identity<T>(x: T): T { return x; } const s = identity('hello'); // T = 'hello' (literal) const n = identity(42); // T = 42 (literal) // Widened inference with let: let str = 'hello'; const ws = identity(str); // T = string (widened) // Multiple candidates: function pair<T>(a: T, b: T): [T, T] { return [a, b]; } pair('a', 'b'); // T = string ✓ pair('a', 1); // T = string | number — union inference pair<string>('a', 1); // Error: 1 is not string // Contextual typing (inward flow): const fn: (x: number) => string = x => x.toString(); // TypeScript infers x: number from the context

Constraints narrow inference

// T extends keyof U: constrain to known keys function getProperty<T, K extends keyof T>(obj: T, key: K): T[K] { return obj[key]; } const user: UserDto = { id: 1, name: 'Bob' }; getProperty(user, 'name'); // T=UserDto, K='name', returns string getProperty(user, 'id'); // T=UserDto, K='id', returns number getProperty(user, 'xyz'); // Error: 'xyz' is not a key of UserDto // T extends object: prevent primitives function deepClone<T extends object>(obj: T): T { return JSON.parse(JSON.stringify(obj)); } deepClone({ a: 1 }); // OK deepClone('hello'); // Error: string not assignable to object

1. The model: collect candidates, then pick

At a generic call, TS looks at each argument, matches it against the parameter type, and records a candidate for each type parameter. With one candidate it just uses it. With several, it computes a best common type — often a union.

function identity<T>(x: T): T { return x; }
identity(42);      // candidate for T: number  → T = number  → returns number
identity("hi");    // candidate for T: string  → T = string

function pair<T>(a: T, b: T): [T, T] { return [a, b]; }
pair(1, "x");    // candidates: number AND string → T = string | number

3. Context flows inward — contextual typing

Callbacks get typed from the outside

Inference isn't only bottom-up. When a value has an expected type, that type flows into the expression — so callback parameters get types without annotations.

const nums = [1, 2, 3];
nums.map(x => x.toFixed(2));
// x: number — inferred from number[].map, not annotated

const fn: (n: number) => void = x => {
  x.toFixed(0);   // x: number — flowed in from the annotation
};

Default type parameters

When nothing pins a type parameter down, a = Default fills the gap (instead of falling back to unknown/{}).

function make<T = string>(): T[] { return []; }
const a = make();          // T = string (default) → string[]
const b = make<number>();  // T = number → number[]

Order matters: a parameter's default can reference type params declared before it.

4. NoInfer<T> — telling a site not to vote

Sometimes one argument shouldn't influence inference — it should only be checked against what the other arguments already determined. NoInfer<T> (built in since TS 5.4) removes that position from candidate collection.

// 🟥 without NoInfer: 'green' widens the union you didn't want
function paint<C>(palette: C[], chosen: C): C { return chosen; }
paint(["red", "blue"], "green");
// C = "red" | "blue" | "green"  ← 'green' snuck into the type 😬

// ✅ with NoInfer: 'chosen' must be one of the palette, can't expand it
function paint<C>(palette: C[], chosen: NoInfer<C>): C { return chosen; }
paint(["red", "blue"], "green");
// ❌ 'green' is not assignable to "red" | "blue" — exactly the guard we wanted

// return-only T — nothing to infer from, so it falls back:
function parse<T>(json: string): T { return JSON.parse(json); }
const u = parse("{}");        // u: unknown (TS 5.x) — T never got a candidate
const v = parse<User>("{}"); // v: User ✅ — supplied explicitly

A constraint also shapes inference: <T extends object> stops the literal from widening to a primitive and gives better errors.

6. Inference priority — a quick intuition

  • More arguments = more candidates. Each site that mentions T adds a candidate; the result is their best common type (often a union).
  • Some sites outrank others. A naked T argument is a stronger signal than T buried inside a type the compiler has to peel (e.g. a return-position or a wrapped generic).
  • Contextual type wins for callbacks. If an outer expected type exists, callback params get it before bottom-up inference runs.
  • Constraints don't supply the type — <T extends string> doesn't make T = string; it limits candidates and is the fallback default only when nothing is inferred.

7. One-sentence recap

TypeScript infers a type parameter by collecting a candidate at every argument site that mentions it and taking their best common type (a union when they differ), while an outer expected type can flow inward to type callbacks; use NoInfer<T> to stop a position from voting, <T = Default> when nothing pins it down, and explicit type arguments or annotations for the cases inference can't reach — return-only T, empty literals, and over-widened primitives.
