Python: Descriptors & Metaclasses

The machinery behind property, bound methods, ORMs, and enums: the descriptor protocol, how classes are themselves objects, metaclasses — and the lighter hooks that replace most of them.

🧙 The "deep magic" that powers the features you already use

Two advanced mechanisms explain a lot of Python's "magic." A descriptor is a class attribute defining __get__/__set__/__delete__, so accessing instance.attr routes through those methods — it's the protocol behind @property, classmethod, and even plain methods (a function's __get__ returns a bound method, which is how self is injected). The second: classes are objects too — class is sugar for type(name, bases, ns), and a class's class is its metaclass, which can intercept class creation. But metaclasses are rarely needed: prefer __init_subclass__, __set_name__, or a class decorator.

  • Descriptors route attribute access — the engine under @property, methods, ORM columns.
  • A function is a descriptor — its __get__ binds self automatically.
  • Classes are objects; their class is the metaclass — it can intercept class creation.
  • Use these constantly, write them rarely — prefer __init_subclass__/class decorators.

A validating descriptor

class Positive: def __set_name__(self, owner, name): self.attr = "_" + name def __get__(self, obj, owner): return getattr(obj, self.attr) def __set__(self, obj, val): if val <= 0: raise ValueError(">0") setattr(obj, self.attr, val) class Account: balance = Positive() # reusable

A class IS an object

class User: pass type(User) # <class 'type'> — its metaclass User2 = type("User2", (), {"x": 1}) # class made at runtime # class X(metaclass=Meta): ... # Meta.__new__ intercepts creation

vs Java reflection / annotations

Java: annotation processors + reflection at build/runtime do what metaclasses do at class-definition time; getters/setters are explicit (no descriptor equivalent). Python: descriptors make obj.x run code transparently, and metaclasses hook class creation — which is why Python ORMs need far less boilerplate than their Java counterparts.

CIAM context: You rarely write these but they demystify your stack — SQLAlchemy/Django models use a metaclass to collect column descriptors, @property computes user.is_admin, and a custom descriptor could mask a secret on repr. For "register every auth-provider subclass," reach for __init_subclass__ (auto-register on definition), not a hand-rolled metaclass.

Or: the descriptor you wrote perfectly, that Python never once calls.

The problem

You copy-paste a validated-attribute descriptor into __init__ instead of the class body — one line of difference — and every validation check inside it just... never runs, with no error, ever.

The validator that silently stops validating

Your Positive descriptor from earlier in this lesson works fine as a class attribute: class Account: balance = Positive(). But in a different class, written under deadline, you build the object inside __init__ instead: class Account: def __init__(self, balance): self.balance = Positive(); self.balance = balance — one statement assigns the descriptor, the next assigns the actual value, both look like ordinary attribute assignment.

account.balance = -500 now succeeds. No ValueError, ever, for any value. The descriptor protocol only activates when Python finds a descriptor object on the class — via type(obj).__mro__ — not when it finds one sitting in instance.__dict__. self.balance = Positive() just stores a plain Positive instance as a normal attribute VALUE. The very next line, self.balance = balance, then overwrites that value entirely — the descriptor object is garbage before the constructor even returns.

You built a lock. You just left it sitting on the floor instead of bolting it to the door.

Descriptors are declared on the class, never assigned in __init__
Move the descriptor to a class-level assignment: class Account: balance = Positive() ↓ this runs once, when the class itself is being built, so Positive() becomes part of Account's own namespace — exactly where type.__getattribute__ looks In __init__, only ever ASSIGN a value through it — never re-assign the descriptor itself: def __init__(self, balance): self.balance = balance ↓ this now goes through Positive.__set__, because Python finds the descriptor on the class first and routes the assignment through it If you need per-instance validators with different bounds, parameterize the descriptor's __init__, not its placement — balance = Bounded(0, 10_000) on the class, still ↓ the descriptor OBJECT lives on the class either way; only the bounds it enforces vary
The one-sentence rule. A descriptor only works when it is found on the class, via the normal class attribute lookup Python already does for you — put the exact same object on an instance instead, and it's just an inert value sitting in __dict__, indistinguishable to Python from any other attribute.
Think of a descriptor like a house rule posted on the FRONT DOOR of the building (the class) — every tenant (instance) who walks through automatically obeys it. Taping that exact same rule to the inside of one apartment's fridge (an instance's __dict__) means nobody walking through the front door ever sees it — it's real paper, it says the right words, and it governs nothing.

The mechanism

Trace exactly where Python looks, and why the instance-assigned descriptor is invisible to it.

  1. class Account: body executes; if balance = Positive() is HERE, it's stored in Account.__dict__["balance"]class-level path
  2. __init__ runs; self.balance = Positive() instead stores it in instance.__dict__["balance"]instance-level path
  3. self.balance = balance (the very next line) OVERWRITES that entry with a plain intdescriptor discarded
  4. Later: account.balance = -500 triggers object.__setattr__assignment
  5. Python checks type(account).__mro__ for a data descriptor named balance — finds none, because it was never placed therelookup misses
  6. Falls back to plain instance.__dict__["balance"] = -500 — ordinary assignment, no validation, no errorsilent success

Step 3 is the trap within the trap: even someone who catches "wait, I put the descriptor in __init__" and fixes only the SECOND line still has a bug, because the descriptor object from line 2 is already gone by the time line 3 runs. The fix has to move the descriptor itself up to the class body — nothing you do later in __init__ can resurrect it.

The descriptor protocol is nested lookup, outside-in: class hierarchy first, instance dict second, and only for a NAME Python is already resolving via ordinary attribute access. An object assigned in __init__ never enters that outer ring at all — it lands directly in the instance __dict__, the innermost, last-resort layer, where a descriptor object is just inert data.

You refactor class User: role = RoleField() (a working class-level descriptor) into a factory function: def make_user(name): u = User.__new__(User); u.role = RoleField(); return u, trying to set a default role per instance. What happens when code later does u.role = "admin"?

Right — u.role = RoleField() inside the factory function is an instance assignment, indistinguishable to Python from assigning any other value. The descriptor protocol never engages because Python never finds a descriptor on type(u) — User itself has no role attribute here at all.

Python raises no error for this — it's syntactically identical to any other attribute assignment. That's exactly what makes it dangerous: nothing warns you at the moment you make the mistake.

It does NOT work like the class-level version. On the class, role = RoleField() lives in User.__dict__, where the protocol looks. On the instance, that same object sits in u.__dict__, which the protocol never checks for descriptors — the object being a RoleField is irrelevant once it's in the wrong dictionary.

Where you have seen this before

"Put it in the wrong scope and the mechanism that would have used it never sees it" repeats across languages.

Java: an @Overrided method with the wrong signature

Add an extra parameter to what you meant as an override and Java silently treats it as a brand-new overload instead — the base class's dispatch never routes to your method, with no compiler error unless you remembered @Override (which catches only THIS specific mismatch). A descriptor in the wrong dict is the same shape of "looks connected, isn't" failure.

the right code, filed under the wrong lookup key

Spring: a @Bean method that isn't inside a @Configuration class

Write a perfectly correct @Bean public DataSource ds() {...} method on a plain class instead of one annotated @Configuration, and Spring's component scan never registers it — the method is 100% valid Java, it just isn't in a place Spring's mechanism looks for bean definitions.

correct code that the framework's scan never reaches

Angular: a provider registered on a component instead of the module/root

Registering a service in a child component's providers array (instead of at the module or root level) gives that component and its children their OWN instance, invisible to the rest of the app that expected a shared singleton via DI — the service works, injection succeeds, and it's still silently the wrong instance because of where it was declared.

DI resolves scope by declaration site, not by intention
The whole page on a napkin: descriptors (__get__/__set__) power @property, methods, and ORM fields by intercepting attribute access declared on a class, and metaclasses control class creation itself — with lighter hooks like __init_subclass__ covering most everyday needs. The one new sentence this block adds: a descriptor only works from the class's own namespace — assign the exact same object to an instance instead, and it becomes an inert value the protocol never looks at.

1. The Descriptor Protocol

class Positive: # a reusable, validated attribute
  def __set_name__(self, owner, name): self.n = "_" + name
  def __get__(self, obj, owner):
    return None if obj is None else getattr(obj, self.n)
  def __set__(self, obj, val):
    if val <= 0: raise ValueError("must be > 0")
    setattr(obj, self.n, val)

class Account: balance = Positive() # class attr

A descriptor is an object (stored as a class attribute) that implements __get__/__set__/__delete__. When you read or assign account.balance, Python invokes the descriptor's methods instead of plain attribute access. __set_name__(owner, name) tells the descriptor which attribute it was assigned to, so one descriptor class is reusable across fields. This is how you factor out validation/computation that would otherwise be repeated in many @property pairs.

Data vs non-data descriptors decide precedence. A descriptor with __set__ (or __delete__) is a data descriptor and takes priority over an instance's __dict__; one with only __get__ is non-data and is shadowed by an instance attribute of the same name. That precedence rule is exactly why @property (data) can't be accidentally overwritten on an instance, but a method (non-data) can.

"How does self get passed automatically?" — descriptors. A function defined in a class is a non-data descriptor; accessing obj.method calls the function's __get__(obj, Cls), which returns a bound method with obj pre-filled as the first argument. So the self "magic" is just the descriptor protocol you saw in §1, applied to functions.

3. Metaclasses — Classes Creating Classes

# `class` is sugar for a call to type(...)
User = type("User", (Base,), {"role": "user"})

# a custom metaclass intercepts class creation
class Meta(type):
  def __new__(mcs, name, bases, ns):
    ns["created_by"] = "Meta" # transform the class
    return super().__new__(mcs, name, bases, ns)

class Service(metaclass=Meta): ...

A class statement actually calls its metaclass — type by default — as type(name, bases, namespace), which is why type(SomeClass) is type. A custom metaclass (subclass of type) overrides __new__/__init__ to inspect, validate, register, or transform a class as it's defined. This runs once per class (not per instance). It's the mechanism behind ORM model bases (collecting field descriptors), abc.ABCMeta, and Enum.

"Metaclasses are deeper magic than 99% of users should ever worry about" — Tim Peters. They're powerful but make code hard to follow and can conflict (a class can have only one metaclass, so combining libraries that each use one breaks). Understand them to read framework internals; write one only when you genuinely must hook class creation across a whole hierarchy.

4. Prefer the Lighter Hooks

# __init_subclass__: auto-register every subclass (no metaclass!)
class AuthProvider:
  registry = {}
  def __init_subclass__(cls, *, key, **kw):
    super().__init_subclass__(**kw)
    AuthProvider.registry[key] = cls

class Entra(AuthProvider, key="entra"): ... # auto-registered
class Ping(AuthProvider, key="ping"): ...

Most things people once needed a metaclass for now have a simpler tool: __init_subclass__ runs whenever a class is subclassed (perfect for plugin/auto-registration); __set_name__ gives descriptors their attribute name; and a class decorator (@dataclass, @final) transforms a class after creation. These are easier to read, compose without the single-metaclass conflict, and cover the vast majority of real needs.

Decision order: descriptor / class decorator / __init_subclass__ → then metaclass. Need a smart attribute? Descriptor. Need to transform one class? Class decorator. Need to react when a class is subclassed (registration, validation)? __init_subclass__. Only when you must control the actual creation of an entire class hierarchy (building a framework like an ORM) do you reach for a metaclass.
