Python: Descriptors & Metaclasses

The machinery behind property, bound methods, ORMs, and enums: the descriptor protocol, how classes are themselves objects, metaclasses — and the lighter hooks that replace most of them.

🧙 The "deep magic" that powers the features you already use

Two advanced mechanisms explain a lot of Python's "magic." A descriptor is a class attribute defining __get__/__set__/__delete__, so accessing instance.attr routes through those methods — it's the protocol behind @property, classmethod, and even plain methods (a function's __get__ returns a bound method, which is how self is injected). The second: classes are objects too — class is sugar for type(name, bases, ns), and a class's class is its metaclass, which can intercept class creation. But metaclasses are rarely needed: prefer __init_subclass__, __set_name__, or a class decorator.

  • Descriptors route attribute access — the engine under @property, methods, ORM columns.
  • A function is a descriptor — its __get__ binds self automatically.
  • Classes are objects; their class is the metaclass — it can intercept class creation.
  • Use these constantly, write them rarely — prefer __init_subclass__/class decorators.

A class IS an object

class User: pass type(User) # <class 'type'> — its metaclass User2 = type("User2", (), {"x": 1}) # class made at runtime # class X(metaclass=Meta): ... # Meta.__new__ intercepts creation

vs Java reflection / annotations

Java: annotation processors + reflection at build/runtime do what metaclasses do at class-definition time; getters/setters are explicit (no descriptor equivalent). Python: descriptors make obj.x run code transparently, and metaclasses hook class creation — which is why Python ORMs need far less boilerplate than their Java counterparts.

CIAM context: You rarely write these but they demystify your stack — SQLAlchemy/Django models use a metaclass to collect column descriptors, @property computes user.is_admin, and a custom descriptor could mask a secret on repr. For "register every auth-provider subclass," reach for __init_subclass__ (auto-register on definition), not a hand-rolled metaclass.

1. The Descriptor Protocol

class Positive: # a reusable, validated attribute
  def __set_name__(self, owner, name): self.n = "_" + name
  def __get__(self, obj, owner):
    return None if obj is None else getattr(obj, self.n)
  def __set__(self, obj, val):
    if val <= 0: raise ValueError("must be > 0")
    setattr(obj, self.n, val)

class Account: balance = Positive() # class attr

A descriptor is an object (stored as a class attribute) that implements __get__/__set__/__delete__. When you read or assign account.balance, Python invokes the descriptor's methods instead of plain attribute access. __set_name__(owner, name) tells the descriptor which attribute it was assigned to, so one descriptor class is reusable across fields. This is how you factor out validation/computation that would otherwise be repeated in many @property pairs.

Data vs non-data descriptors decide precedence. A descriptor with __set__ (or __delete__) is a data descriptor and takes priority over an instance's __dict__; one with only __get__ is non-data and is shadowed by an instance attribute of the same name. That precedence rule is exactly why @property (data) can't be accidentally overwritten on an instance, but a method (non-data) can.

"How does self get passed automatically?" — descriptors. A function defined in a class is a non-data descriptor; accessing obj.method calls the function's __get__(obj, Cls), which returns a bound method with obj pre-filled as the first argument. So the self "magic" is just the descriptor protocol you saw in §1, applied to functions.

3. Metaclasses — Classes Creating Classes

# `class` is sugar for a call to type(...)
User = type("User", (Base,), {"role": "user"})

# a custom metaclass intercepts class creation
class Meta(type):
  def __new__(mcs, name, bases, ns):
    ns["created_by"] = "Meta" # transform the class
    return super().__new__(mcs, name, bases, ns)

class Service(metaclass=Meta): ...

A class statement actually calls its metaclass — type by default — as type(name, bases, namespace), which is why type(SomeClass) is type. A custom metaclass (subclass of type) overrides __new__/__init__ to inspect, validate, register, or transform a class as it's defined. This runs once per class (not per instance). It's the mechanism behind ORM model bases (collecting field descriptors), abc.ABCMeta, and Enum.

"Metaclasses are deeper magic than 99% of users should ever worry about" — Tim Peters. They're powerful but make code hard to follow and can conflict (a class can have only one metaclass, so combining libraries that each use one breaks). Understand them to read framework internals; write one only when you genuinely must hook class creation across a whole hierarchy.

4. Prefer the Lighter Hooks

# __init_subclass__: auto-register every subclass (no metaclass!)
class AuthProvider:
  registry = {}
  def __init_subclass__(cls, *, key, **kw):
    super().__init_subclass__(**kw)
    AuthProvider.registry[key] = cls

class Entra(AuthProvider, key="entra"): ... # auto-registered
class Ping(AuthProvider, key="ping"): ...

Most things people once needed a metaclass for now have a simpler tool: __init_subclass__ runs whenever a class is subclassed (perfect for plugin/auto-registration); __set_name__ gives descriptors their attribute name; and a class decorator (@dataclass, @final) transforms a class after creation. These are easier to read, compose without the single-metaclass conflict, and cover the vast majority of real needs.

Decision order: descriptor / class decorator / __init_subclass__ → then metaclass. Need a smart attribute? Descriptor. Need to transform one class? Class decorator. Need to react when a class is subclassed (registration, validation)? __init_subclass__. Only when you must control the actual creation of an entire class hierarchy (building a framework like an ORM) do you reach for a metaclass.
