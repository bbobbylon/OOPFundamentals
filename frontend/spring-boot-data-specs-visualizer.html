Spring Data JPA — Specifications, Projections & Advanced Queries

Build type-safe dynamic queries, avoid N+1 problems, load only the fields you need, and add auditing automatically.

🔎 What is a Spring Data Specification — and why do user search/filter APIs need it?

A user API needs flexible, optional filtering: "status=ACTIVE and role=ADMIN and email contains '@contoso.com'", where any combination might be sent. Writing a method per combination (findByStatusAndRole, findByStatus, …) doesn't scale. Spring Data Specifications fix this: a Specification<User> is a small predicate you compose with and()/or(). Write one per criterion, chain only the non-null ones, and a single dynamic query is built at runtime — userRepository.findAll(spec, pageable) handles every combination. Type-safe (compile errors, not SQL string bugs), composable, and readable.

  • One method, every filter combo. Compose predicates instead of multiplying query methods.
  • Null specs drop out — only the filters actually supplied join the query.
  • Projections cut the payload — select just the columns a view needs, no entity/lazy loads.
  • JPA auditing stamps who/when automatically — essential for CIAM compliance.

Writing a Specification

hasStatus(status) returns (root,query,cb) -> status==null ? null : cb.equal(root.get("status"), status). Compose: Specification.where(hasStatus(...)).and(hasRole(...)).and(emailContains(...)) — nulls ignored. The repo extends JpaSpecificationExecutor<User> for findAll(spec, pageable).

Projections

Loading a 30-field User with lazy roles for a name+email dropdown is wasteful. A projection interface (UserSummary { getEmail(); getDisplayName(); }) with List<UserSummary> findAllProjectedBy() emits SELECT email, display_name — no entity, no lazy loading.

JPA auditing

@CreatedDate/@LastModifiedDate/@CreatedBy on entity fields, plus @EntityListeners(AuditingEntityListener.class) and @EnableJpaAuditing, auto-populate on insert/update. An AuditorAware<String> supplies the current user for the *By fields.

CIAM: GET /api/users?status=ACTIVE&role=ADMIN&email=contoso → the controller binds the params into a filter record, builds Specification.where(hasStatus(...)).and(hasRole(...)).and(emailContains(...)), and returns Page<UserSummary>. Every User carries @CreatedBy/@LastModifiedBy — who provisioned and last changed each user, exactly what compliance needs.

The problem

You copied the exact "skip when null" trick this page just taught you. This time it isn't AND — and now it matches everything.

Filtering by department alone quietly returns the entire user table

You need "role X OR department Y," so you write hasRole(role) and hasDepartment(dept) using the exact null-guard idiom above: role == null ? cb.conjunction() : cb.equal(...). Then you compose them with Specification.where(hasRole(role)).or(hasDepartment(dept)) instead of .and(), because this search really is an OR. The caller leaves role blank and passes department="Sales", expecting Sales employees only. Every user in the table comes back — including engineering, finance, everyone. The department predicate is sitting right there in the generated SQL. It just isn't doing anything.

hasDepartment("Sales") correctly built ✓ role left blank, hasRole(null) called ✓ hasRole(null) returns cb.conjunction() — "always true" ⚠ TRUE OR anything is always TRUE ⚠

The null-guard isn't wrong. It's wrong for OR — the same line of code means "skip me" under AND and "match everything" under OR.

Match the identity element to the operator, not just to "null means skip"
Under AND: missing filter → cb.conjunction() (TRUE) ↓ TRUE AND x always equals x — the missing filter genuinely drops out Under OR: missing filter → cb.disjunction() (FALSE) ↓ FALSE OR x always equals x — here, FALSE is the one that actually drops out Same helper method family, opposite identity element
cb.conjunction() means "true," not "skip this." Under AND, true is harmless — it looks exactly like an ignored filter, because TRUE AND x is x. Under OR, true is catastrophic — TRUE OR x is always true, so it silently swallows every other condition in the chain. The bug was never in the null check itself; it was in reusing an AND-shaped idiom inside an OR-shaped composition without asking which identity element that operator actually needs.
Think of cb.conjunction() as a blank ballot that always counts as "yes." In a vote where EVERY ballot has to say yes to pass (AND), a blank-counts-as-yes abstention is harmless — it just steps out of the way and lets the real ballots decide. In a vote where a SINGLE yes is enough to pass (OR), that exact same blank ballot passes the motion all by itself, no matter what anyone else voted. The rule for the abstention never changed. The voting system around it did.
You

hasRole(null) returns cb.conjunction() — that's the exact pattern taught above for skipping a filter. Why did OR-ing it in return every single row?

CriteriaBuilder

Because conjunction() isn't a "skip me" signal — I don't have one of those. It's a predicate that evaluates to TRUE, full stop. Hand me cb.or(TRUE, anything) and I have no way to know you meant "ignore my left side." As far as I'm concerned, you asked for TRUE OR anything, and that's always TRUE.

cb.disjunction()

I'm the one you actually wanted here. I'm FALSE, full stop — the mirror image of conjunction(). OR me in with a real predicate and I vanish the same way conjunction() vanishes under AND, because FALSE OR x really does just equal x.

The mechanism

AND's blank vote is TRUE. OR's blank vote is FALSE. Reach for the wrong one and the search stops filtering — silently.

  1. The caller submits role=null, department="Sales" to a search built around .or() — "match role OR department"an OR-shaped search
  2. hasRole(null) runs its null guard — copied straight from this page's AND example — and returns cb.conjunction()TRUE, not "skip"
  3. hasDepartment("Sales") returns a real predicate: department = 'Sales'the one honest condition in the chain
  4. The composition evaluates cb.or(conjunction(), departmentPredicate)TRUE OR anything
  5. By the rules of boolean OR, the result is unconditionally TRUE — the department check is still IN the SQL, it's just logically irrelevant nowthe WHERE clause is real; its effect isn't
  6. Every row in the table satisfies TRUE, so every user comes back, regardless of departmentthe filter UI looks like it worked — the query didn't

Step 4 is the lesson. The instant a TRUE predicate enters an OR chain, every predicate after it becomes provably irrelevant, no matter how correct it is. department = 'Sales' is a perfectly valid SQL fragment sitting right there in the query — it just no longer affects which rows match, because ORing anything with TRUE was always going to be TRUE.

cb.or(?, department = 'Sales')the OR chain needs a neutral left side
null role plugs in →
cb.conjunction() — TRUE, swallows the whole OR cb.disjunction() — FALSE, the actual neutral value for OR

The slot is identical in both cases — "what do I return when the filter is absent" — but which value is safe to plug into it depends entirely on the operator waiting on the other side. Swap the composition back to .and() and the correct option flips again: conjunction() becomes safe, and disjunction() would be the one quietly breaking everything.

hasRole(null) returns cb.conjunction() — the exact null-guard pattern taught above for AND. A search screen chains it with .or(hasDepartment(dept)) instead, because the query should mean "role X OR department Y." The caller leaves role blank and passes department="Sales". What comes back?

A reasonable instinct — plenty of Spring Data's own null-handling really does fail safe by quietly dropping out. But cb.conjunction() isn't a null and isn't a skip signal; it's a fully valid, always-true Predicate, and CriteriaBuilder happily ORs it with anything you hand it. Nothing here throws.

Exactly — TRUE OR (department = 'Sales') is TRUE no matter what department equals, by ordinary boolean logic. The department predicate is still sitting right there in the generated SQL; it just has no power left to exclude a row, because the other side of the OR already guarantees a match.

This is exactly true under AND — it's the page's own example above — which is precisely why it's so easy to assume it carries over unchanged. TRUE is the identity element for AND (harmless), but it's the absorbing element for OR (it wins outright, every time). Same value, opposite effect, entirely depending on which operator it's plugged into.

Where you've seen this before

Three systems, one trap: an always-true clause is only harmless next to AND.

Hand-written SQL's classic WHERE 1=1

Any developer who's built a dynamic WHERE clause by string concatenation knows the WHERE 1=1 trick — it lets every real condition start with a clean AND instead of special-casing the first one. Accidentally concatenate an OR condition onto that same string instead of an AND, and 1=1 silently swallows the entire clause — the exact same failure, with zero ORM anywhere in sight. cb.conjunction() is 1=1 wearing a Criteria API costume.

WHERE 1=1 OR … ≈ cb.or(conjunction(), …)

MongoDB's empty filter inside $or

An empty filter document {} matches every document in MongoDB — it's Mongo's version of "always true." Put one inside $or: [{}, {department: "Sales"}] and the whole query matches every document in the collection, for the identical reason: one branch of an OR that's unconditionally true makes the other branch's condition irrelevant, regardless of query language.

{} in $or ≈ conjunction() in cb.or()

Your CIAM authorization check

An endpoint gated by hasScope(requiredScope).or(isSuperAdmin()), where a route with no required scope is coded as hasScope(null) → cb.conjunction() "to skip the scope check." The moment scope is optional for that endpoint, every caller becomes a super-admin — not a search bug anymore, but an authorization bypass, from the identical always-true-in-an-OR mistake.

same bug, now it's a CVE instead of a wrong search result
Questions from the back row

Does Specification.where(null) have this same problem?

No — that one's genuinely safe, for a different reason. It's the seed of an .and() chain, always paired with more real .and() calls layered on top, and each filter you add narrows the result exactly like you'd expect. The trap above is about plugging an always-true predicate into .or(), not about Specification.where(null) itself — the danger lives in the operator on the other side, not in the null-guard convention by itself.

Why doesn't Spring Data just skip null filters automatically instead of making me guard them?

Because it can't know what your null means. It might mean "no filter requested," or it might mean "search for rows where this column IS NULL" — an unassigned department, say. Spring Data can't guess which one you intend, so your own spec has to decide, and it only looks uniform because most search screens happen to mean the first one.

Is there a way to make this mistake structurally impossible, not just something to remember?

Yes — stop seeding an identity element at all. Collect only the non-null predicates into a plain List<Predicate>, and if that list ends up empty, decide explicitly what "no filters supplied" should mean for this endpoint — everything, nothing, or a required 400. It's more code than cb.conjunction(), but it forces you to name the decision instead of burying it inside an algebraic identity trick that only one operator agrees with.

1. JPA Specifications — Dynamic, Composable Queries

Spring Data's Specification API wraps the JPA Criteria API. Instead of one giant "search" JPQL query with every possible filter, you build small, named, testable predicates and combine them.

Repository setup

// Extend JpaSpecificationExecutor to unlock // findAll(Specification), findOne(Specification), count(Spec) public interface ProductRepository extends JpaRepository<Product, Long>, JpaSpecificationExecutor<Product> { }

Specification interface

// interface Specification<T>: // Predicate toPredicate(Root<T> root, // CriteriaQuery<?> query, // CriteriaBuilder cb); // Static factory methods on a Specifications class public class ProductSpecs { public static Specification<Product> hasCategory( String category) { return (root, query, cb) -> category == null ? cb.conjunction() // "1=1" — always true : cb.equal(root.get("category"), category); } public static Specification<Product> nameLike( String name) { return (root, query, cb) -> name == null ? cb.conjunction() : cb.like(cb.lower(root.get("name")), "%" + name.toLowerCase() + "%"); } public static Specification<Product> priceBetween( BigDecimal min, BigDecimal max) { return (root, query, cb) -> { if(min == null && max == null) return cb.conjunction(); if(min == null) return cb.lessThanOrEqualTo(root.get("price"), max); if(max == null) return cb.greaterThanOrEqualTo(root.get("price"), min); return cb.between(root.get("price"), min, max); }; } public static Specification<Product> inStock() { return (root, query, cb) -> cb.greaterThan(root.get("stockQuantity"), 0); } }

Composing and using specifications

// Service layer — build spec from non-null filters @Service public class ProductSearchService { public Page<Product> search( String name, String category, BigDecimal minPrice, BigDecimal maxPrice, boolean inStockOnly, Pageable pageable) { // Specification.where creates a null-safe starting point Specification<Product> spec = Specification.where(ProductSpecs.nameLike(name)) .and(ProductSpecs.hasCategory(category)) .and(ProductSpecs.priceBetween(minPrice, maxPrice)); if(inStockOnly) { spec = spec.and(ProductSpecs.inStock()); } return productRepo.findAll(spec, pageable); } } // CriteriaBuilder predicates reference cb.equal(root.get("field"), value) // WHERE field = :val cb.notEqual(root.get("field"), value) // WHERE field <> :val cb.like(root.get("name"), "%str%") // WHERE name LIKE '%str%' cb.between(root.get("price"), lo, hi) // WHERE price BETWEEN cb.greaterThan(root.get("x"), val) // WHERE x > :val cb.isNull(root.get("deletedAt")) // WHERE deleted_at IS NULL root.get("tags").in(List.of("a","b")) // WHERE tag IN ('a','b') // Join in specification var join = root.join("categories", JoinType.INNER); return cb.equal(join.get("name"), categoryName);

3. Projections — Load Only What You Need

Interface Projection (closed)

// Spring Data generates a proxy implementing this public interface ProductSummary { Long getId(); String getName(); BigDecimal getPrice(); // Only these 3 fields loaded — no @Lob images! } public interface ProductRepository extends JpaRepository<Product, Long> { // Returns a projection, not a full entity List<ProductSummary> findAllProjectedBy(); ProductSummary findSummaryById(Long id); } // SQL: SELECT p.id, p.name, p.price FROM products p // No lazy loading of associations, no extra columns

Open Projection (computed)

public interface ProductLabel { String getName(); BigDecimal getPrice(); // @Value computes from multiple fields with SpEL @Value("#{target.name + ' ($' + target.price + ')'}") String getDisplayLabel(); } // "Open" = must load full entity for SpEL evaluation // Less efficient than closed projections

Dynamic Projection

// Single generic method serves multiple projections interface ProductRepository ... { <T> List<T> findByCategory( String cat, Class<T> type); } // Callers choose the shape they need: repo.findByCategory("BOOKS", ProductSummary.class); repo.findByCategory("BOOKS", ProductLabel.class); repo.findByCategory("BOOKS", Product.class); // full entity

DTO Projection (class/record)

// Record DTO — immutable, compact public record ProductDto( Long id, String name, BigDecimal price ) {} // JPQL constructor expression @Query("SELECT new com.myapp.dto.ProductDto(p.id, p.name, p.price) " + "FROM Product p WHERE p.active = true") List<ProductDto> findActiveProductDtos(); // Or Spring Data native projection query @Query(value = "SELECT id, name, price FROM products WHERE active = 1", nativeQuery = true) List<ProductDto> findActiveNative();

When to use each

Closed interface projection
Best performance — Spring generates targeted SELECT. Use for list endpoints returning many records.
DTO record + constructor expression
Explicit, type-safe, easy to test. Good when you need computed/joined fields in the DTO.
Open interface projection
Use only when SpEL computation is necessary. Loads full entity — same as no projection.
Full entity
Use when you'll modify and save the entity. Unnecessary for read-only operations.

4. N+1 Problem & @EntityGraph Fix

The N+1 Problem

Load 50 orders, then access order.getItems() on each. Because items are LAZY, Hibernate fires one SELECT per order = 51 queries total (1 + 50). At 50ms each, that's 2.55 seconds for a simple list.

// N+1 BAD — 1 query for orders, N for items List<Order> orders = orderRepo.findAll(); orders.forEach(o -> { // Each call fires: SELECT * FROM order_items WHERE order_id=? o.getItems().size(); // 💥 N queries! }); // Same problem in @RestController with @JsonProperty on lazy collection

Fix 1 — @EntityGraph

// On the repository method @EntityGraph(attributePaths = {"items", "items.product"}) List<Order> findAllWithItems(); // SQL: SELECT o.*, i.*, p.* FROM orders o // LEFT JOIN order_items i ON i.order_id=o.id // LEFT JOIN products p ON p.id=i.product_id // Named entity graph on the entity class @Entity @NamedEntityGraph(name = "Order.withItems", attributeNodes = { @NamedAttributeNode(value = "items", subgraph = "items.product") }, subgraphs = { @NamedSubgraph(name = "items.product", attributeNodes = @NamedAttributeNode("product")) } ) public class Order { ... } // Reference named graph in repository @EntityGraph("Order.withItems") List<Order> findByStatus(String status);

Fix 2 — @BatchSize

@Entity public class Order { // Instead of 50 individual SELECTs, // Hibernate batches into groups of 25 // Result: 2 queries instead of 50 @OneToMany(fetch = FetchType.LAZY) @BatchSize(size = 25) private List<OrderItem> items; } // Or globally in application.yml: # spring.jpa.properties.hibernate.default_batch_fetch_size: 25

Fix 3 — JOIN FETCH in JPQL

@Query("SELECT DISTINCT o FROM Order o " + "JOIN FETCH o.items i " + "JOIN FETCH i.product " + "WHERE o.status = :status") List<Order> findWithItemsByStatus( @Param("status") String status);
Detect N+1: Add spring.jpa.show-sql=true and spring.jpa.properties.hibernate.format_sql=true. If you see the same table queried repeatedly with different IDs, you have N+1. Also consider a library like Hypersistence (Vlad Mihalcea's) that logs query counts per test.

5. JPA Auditing — Automatic Timestamps & Users

Enable Auditing

// Enable JPA auditing on any @Configuration @Configuration @EnableJpaAuditing(auditorAwareRef = "auditorProvider") public class JpaConfig { @Bean public AuditorAware<String> auditorProvider() { // Returns current authenticated user name return () -> Optional.ofNullable( SecurityContextHolder.getContext() .getAuthentication()) .filter(a -> a.isAuthenticated() && !(a instanceof AnonymousAuthenticationToken)) .map(Authentication::getName); } }

@MappedSuperclass BaseEntity

@MappedSuperclass @EntityListeners(AuditingEntityListener.class) public abstract class BaseEntity { @CreatedDate @Column(updatable = false) private LocalDateTime createdAt; @LastModifiedDate private LocalDateTime updatedAt; @CreatedBy @Column(updatable = false) private String createdBy; @LastModifiedBy private String updatedBy; } @Entity public class Product extends BaseEntity { // Inherits all 4 audit fields automatically @Id @GeneratedValue private Long id; private String name; // ... }

Soft Delete pattern

@Entity @SQLDelete(sql = "UPDATE products SET deleted_at = NOW() WHERE id = ?") @FilterDef(name = "notDeleted", defaultCondition = "deleted_at IS NULL") @Filter(name = "notDeleted") // auto-applies WHERE filter public class Product extends BaseEntity { @Column private LocalDateTime deletedAt; public boolean isDeleted() { return deletedAt != null; } } // Enable the filter per session/transaction @Autowired private EntityManager em; public void enableSoftDeleteFilter() { Session session = em.unwrap(Session.class); session.enableFilter("notDeleted"); }
