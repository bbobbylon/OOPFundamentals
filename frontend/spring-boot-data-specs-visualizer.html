Spring Data JPA — Specifications, Projections & Advanced Queries

Build type-safe dynamic queries, avoid N+1 problems, load only the fields you need, and add auditing automatically.

1. JPA Specifications — Dynamic, Composable Queries

Spring Data's Specification API wraps the JPA Criteria API. Instead of one giant "search" JPQL query with every possible filter, you build small, named, testable predicates and combine them.

Repository setup

// Extend JpaSpecificationExecutor to unlock // findAll(Specification), findOne(Specification), count(Spec) public interface ProductRepository extends JpaRepository<Product, Long>, JpaSpecificationExecutor<Product> { }

Specification interface

// interface Specification<T>: // Predicate toPredicate(Root<T> root, // CriteriaQuery<?> query, // CriteriaBuilder cb); // Static factory methods on a Specifications class public class ProductSpecs { public static Specification<Product> hasCategory( String category) { return (root, query, cb) -> category == null ? cb.conjunction() // "1=1" — always true : cb.equal(root.get("category"), category); } public static Specification<Product> nameLike( String name) { return (root, query, cb) -> name == null ? cb.conjunction() : cb.like(cb.lower(root.get("name")), "%" + name.toLowerCase() + "%"); } public static Specification<Product> priceBetween( BigDecimal min, BigDecimal max) { return (root, query, cb) -> { if(min == null && max == null) return cb.conjunction(); if(min == null) return cb.lessThanOrEqualTo(root.get("price"), max); if(max == null) return cb.greaterThanOrEqualTo(root.get("price"), min); return cb.between(root.get("price"), min, max); }; } public static Specification<Product> inStock() { return (root, query, cb) -> cb.greaterThan(root.get("stockQuantity"), 0); } }

Composing and using specifications

// Service layer — build spec from non-null filters @Service public class ProductSearchService { public Page<Product> search( String name, String category, BigDecimal minPrice, BigDecimal maxPrice, boolean inStockOnly, Pageable pageable) { // Specification.where creates a null-safe starting point Specification<Product> spec = Specification.where(ProductSpecs.nameLike(name)) .and(ProductSpecs.hasCategory(category)) .and(ProductSpecs.priceBetween(minPrice, maxPrice)); if(inStockOnly) { spec = spec.and(ProductSpecs.inStock()); } return productRepo.findAll(spec, pageable); } } // CriteriaBuilder predicates reference cb.equal(root.get("field"), value) // WHERE field = :val cb.notEqual(root.get("field"), value) // WHERE field <> :val cb.like(root.get("name"), "%str%") // WHERE name LIKE '%str%' cb.between(root.get("price"), lo, hi) // WHERE price BETWEEN cb.greaterThan(root.get("x"), val) // WHERE x > :val cb.isNull(root.get("deletedAt")) // WHERE deleted_at IS NULL root.get("tags").in(List.of("a","b")) // WHERE tag IN ('a','b') // Join in specification var join = root.join("categories", JoinType.INNER); return cb.equal(join.get("name"), categoryName);

3. Projections — Load Only What You Need

Interface Projection (closed)

// Spring Data generates a proxy implementing this public interface ProductSummary { Long getId(); String getName(); BigDecimal getPrice(); // Only these 3 fields loaded — no @Lob images! } public interface ProductRepository extends JpaRepository<Product, Long> { // Returns a projection, not a full entity List<ProductSummary> findAllProjectedBy(); ProductSummary findSummaryById(Long id); } // SQL: SELECT p.id, p.name, p.price FROM products p // No lazy loading of associations, no extra columns

Open Projection (computed)

public interface ProductLabel { String getName(); BigDecimal getPrice(); // @Value computes from multiple fields with SpEL @Value("#{target.name + ' ($' + target.price + ')'}") String getDisplayLabel(); } // "Open" = must load full entity for SpEL evaluation // Less efficient than closed projections

Dynamic Projection

// Single generic method serves multiple projections interface ProductRepository ... { <T> List<T> findByCategory( String cat, Class<T> type); } // Callers choose the shape they need: repo.findByCategory("BOOKS", ProductSummary.class); repo.findByCategory("BOOKS", ProductLabel.class); repo.findByCategory("BOOKS", Product.class); // full entity

DTO Projection (class/record)

// Record DTO — immutable, compact public record ProductDto( Long id, String name, BigDecimal price ) {} // JPQL constructor expression @Query("SELECT new com.myapp.dto.ProductDto(p.id, p.name, p.price) " + "FROM Product p WHERE p.active = true") List<ProductDto> findActiveProductDtos(); // Or Spring Data native projection query @Query(value = "SELECT id, name, price FROM products WHERE active = 1", nativeQuery = true) List<ProductDto> findActiveNative();

When to use each

Closed interface projection
Best performance — Spring generates targeted SELECT. Use for list endpoints returning many records.
DTO record + constructor expression
Explicit, type-safe, easy to test. Good when you need computed/joined fields in the DTO.
Open interface projection
Use only when SpEL computation is necessary. Loads full entity — same as no projection.
Full entity
Use when you'll modify and save the entity. Unnecessary for read-only operations.

4. N+1 Problem & @EntityGraph Fix

The N+1 Problem

Load 50 orders, then access order.getItems() on each. Because items are LAZY, Hibernate fires one SELECT per order = 51 queries total (1 + 50). At 50ms each, that's 2.55 seconds for a simple list.

// N+1 BAD — 1 query for orders, N for items List<Order> orders = orderRepo.findAll(); orders.forEach(o -> { // Each call fires: SELECT * FROM order_items WHERE order_id=? o.getItems().size(); // 💥 N queries! }); // Same problem in @RestController with @JsonProperty on lazy collection

Fix 1 — @EntityGraph

// On the repository method @EntityGraph(attributePaths = {"items", "items.product"}) List<Order> findAllWithItems(); // SQL: SELECT o.*, i.*, p.* FROM orders o // LEFT JOIN order_items i ON i.order_id=o.id // LEFT JOIN products p ON p.id=i.product_id // Named entity graph on the entity class @Entity @NamedEntityGraph(name = "Order.withItems", attributeNodes = { @NamedAttributeNode(value = "items", subgraph = "items.product") }, subgraphs = { @NamedSubgraph(name = "items.product", attributeNodes = @NamedAttributeNode("product")) } ) public class Order { ... } // Reference named graph in repository @EntityGraph("Order.withItems") List<Order> findByStatus(String status);

Fix 2 — @BatchSize

@Entity public class Order { // Instead of 50 individual SELECTs, // Hibernate batches into groups of 25 // Result: 2 queries instead of 50 @OneToMany(fetch = FetchType.LAZY) @BatchSize(size = 25) private List<OrderItem> items; } // Or globally in application.yml: # spring.jpa.properties.hibernate.default_batch_fetch_size: 25

Fix 3 — JOIN FETCH in JPQL

@Query("SELECT DISTINCT o FROM Order o " + "JOIN FETCH o.items i " + "JOIN FETCH i.product " + "WHERE o.status = :status") List<Order> findWithItemsByStatus( @Param("status") String status);
Detect N+1: Add spring.jpa.show-sql=true and spring.jpa.properties.hibernate.format_sql=true. If you see the same table queried repeatedly with different IDs, you have N+1. Also consider a library like Hypersistence (Vlad Mihalcea's) that logs query counts per test.

5. JPA Auditing — Automatic Timestamps & Users

Enable Auditing

// Enable JPA auditing on any @Configuration @Configuration @EnableJpaAuditing(auditorAwareRef = "auditorProvider") public class JpaConfig { @Bean public AuditorAware<String> auditorProvider() { // Returns current authenticated user name return () -> Optional.ofNullable( SecurityContextHolder.getContext() .getAuthentication()) .filter(a -> a.isAuthenticated() && !(a instanceof AnonymousAuthenticationToken)) .map(Authentication::getName); } }

@MappedSuperclass BaseEntity

@MappedSuperclass @EntityListeners(AuditingEntityListener.class) public abstract class BaseEntity { @CreatedDate @Column(updatable = false) private LocalDateTime createdAt; @LastModifiedDate private LocalDateTime updatedAt; @CreatedBy @Column(updatable = false) private String createdBy; @LastModifiedBy private String updatedBy; } @Entity public class Product extends BaseEntity { // Inherits all 4 audit fields automatically @Id @GeneratedValue private Long id; private String name; // ... }

Soft Delete pattern

@Entity @SQLDelete(sql = "UPDATE products SET deleted_at = NOW() WHERE id = ?") @FilterDef(name = "notDeleted", defaultCondition = "deleted_at IS NULL") @Filter(name = "notDeleted") // auto-applies WHERE filter public class Product extends BaseEntity { @Column private LocalDateTime deletedAt; public boolean isDeleted() { return deletedAt != null; } } // Enable the filter per session/transaction @Autowired private EntityManager em; public void enableSoftDeleteFilter() { Session session = em.unwrap(Session.class); session.enableFilter("notDeleted"); }
