Why TypeScript? — The Case for Static Types

JavaScript is expressive and ubiquitous, but its dynamic nature lets entire classes of bugs slip through to production. TypeScript layers a compile-time type system on top, catching errors before your code ever runs — while compiling away to plain JavaScript with zero runtime overhead.

1. TypeScript is a JavaScript superset

Every valid JavaScript file is already valid TypeScript. You can rename app.js to app.ts and it compiles — no rewrite required. TypeScript only adds syntax on top of JavaScript: type annotations, interfaces, access modifiers, enums, and a handful of decorators. When you compile, all those additions are erased and you get clean JavaScript.

Valid JavaScript (also valid TypeScript)

function greet(name) {
  return "Hello, " + name;
}

const result = greet("World");
console.log(result);

TypeScript — types added

function greet(name: string): string {
  return "Hello, " + name;
}

const result: string = greet("World");
console.log(result);

The type annotations (: string) are the only difference. They are completely invisible at runtime — the compiled output of the TypeScript version is byte-for-byte identical to the JavaScript version.

The superset relationship means: adopting TypeScript in an existing project is incremental. You can start by renaming .js files to .ts one at a time, loosening strictness settings until you're ready to tighten them. There is no "all-or-nothing" migration cliff.

3. Type erasure — zero runtime overhead

TypeScript's type system is entirely a compile-time construct. The TypeScript compiler (tsc) performs two jobs: type-check your code, then strip every type annotation to produce plain JavaScript. This process is called type erasure. The output contains no traces of your types — not as objects, not as checks, not as metadata.

TypeScript source

interface User {
  id: number;
  name: string;
}

function formatUser(u: User): string {
  return `#${u.id} — ${u.name}`;
}

const user: User = { id: 1, name: "Alice" };
console.log(formatUser(user));

Compiled JavaScript output

// interface User { ... }  ← erased entirely

function formatUser(u) {   // : User erased
  return `#${u.id} — ${u.name}`;
}

const user = { id: 1, name: "Alice" };
console.log(formatUser(user));

This is why TypeScript has no performance cost at runtime: the JavaScript engine never sees your type annotations. There are no hidden instanceof checks or type guards injected by the compiler.

Consequence of erasure: you cannot use TypeScript types for runtime decisions. if (x instanceof MyInterface) is illegal because interfaces don't exist at runtime. For runtime type checking you need type guards, class checks, or a library like Zod. TypeScript types are a developer tool, not a runtime feature.

4. Structural typing — "duck typing" with a compiler

TypeScript uses structural typing: a value's type is determined by its shape (what properties and methods it has), not by what class it was constructed from or what type name was declared. If two objects have the same structure, they are mutually assignable — even if they were created from completely different classes.

Structural TS — compatible by shape

interface Point { x: number; y: number; }

class CartesianPoint {
  x: number; y: number;
  constructor(x: number, y: number) {
    this.x = x; this.y = y;
  }
}

function distance(p: Point): number {
  return Math.sqrt(p.x**2 + p.y**2);
}

// CartesianPoint has {x, y} — it satisfies Point
distance(new CartesianPoint(3, 4)); // ✅
distance({ x: 3, y: 4 });         // ✅ also fine

Nominal Java — incompatible by name

// Java equivalent (nominal typing)
interface Point { ... }
class CartesianPoint {
  // Does NOT declare "implements Point"
  double x, y;
}

// In Java this would FAIL at compile time
// because CartesianPoint doesn't nominally
// implement Point, even though the shape
// matches exactly. Name is what counts.
// distance(new CartesianPoint(3, 4)); ❌
SystemLanguagesCompatibility rule
StructuralTypeScript, Go, ElmSame shape → assignable, regardless of class name
NominalJava, C#, Kotlin, SwiftMust explicitly declare type relationship (extends / implements)
Why structural typing fits JavaScript: JS objects are just property bags. You never declare "this object implements IFoo" — you just put the right properties on it. Structural typing mirrors this reality. It also makes TypeScript play nicely with libraries that use plain objects as configuration or data transfer objects.

5. The compile step and modern toolchains

TypeScript requires a build step before the code can run in a browser or Node. This step is handled by different tools depending on your context:

ToolWhat it doesUse case
tscThe official TypeScript compiler. Full type checking + emit.Library builds, CI type-check, declaration files
ts-nodeRuns .ts files directly in Node without a separate compile step.Scripts, REPL, rapid prototyping
esbuildStrips types (no type checking) and bundles. Extremely fast.Production bundling when tsc runs separately in CI
ViteUses esbuild for dev, Rollup for production. Instant HMR.Frontend apps (React, Vue, Svelte + TypeScript)
swcRust-based transpiler. Strips types only, no checking.Next.js, Jest transforms, fast CI builds
Babel @babel/preset-typescriptStrips types (no checking) as a Babel transform.Projects already using Babel
Type stripping vs. type checking: esbuild, swc, and Babel only strip types — they never report type errors. They are fast because they skip the analysis phase. Always run tsc --noEmit in CI to catch type errors, even if your build tool strips types without checking.

Minimal tsconfig.json

{
  "compilerOptions": {
    "target":     "ES2022",      // JS version to emit
    "module":     "ESNext",      // module system
    "moduleResolution": "Bundler", // for Vite/esbuild
    "strict":     true,          // all strict checks on
    "outDir":     "./dist",      // where to emit
    "rootDir":    "./src"        // where source lives
  },
  "include": ["src/**/*"]
}

6. Type inference — annotations you don't have to write

TypeScript can usually work out the type of a variable from its initial value. You only need to annotate when inference can't figure it out, or when you want to be explicit for documentation purposes. Hover over the underlined variables below to see what TypeScript infers.

Hover to see inferred types

let x = 42inferred: number; let name = "Alice"inferred: string; let flags = [true, false]inferred: boolean[]; const user = { id: 1, name: "Bob" }inferred: { id: number; name: string }; function double(n: number)return type inferred: number { return n * 2; // TS sees: n*2 must be number } const doubled = double(5)inferred: number (from double's return type); const mapped = [1, 2, 3].map(n => n.toString())inferred: string[];

Inference chains through expressions: TypeScript knows [1,2,3] is number[], so the callback parameter n is number, so n.toString() is string, so the result is string[] — all without a single annotation.

Best practice: annotate function parameters (inference can't read your mind about inputs), and return types on public API functions (makes intent explicit and catches mistakes). Skip annotations on local variables and intermediate values — let inference work.

8. Safety levels: any → unknown → never

TypeScript has three special types that represent different points on the safety spectrum. Understanding them is key to writing robust code.

TypeAssignable FROMAssignable TOUse when
any Everything Everything Escape hatch — you're telling TS "trust me, I know what this is." Turns off all checking for that value. Avoid except for incremental migration.
unknown Everything Only unknown and any Truly unknown input (API responses, JSON.parse, caught errors). You must narrow it before use — TS forces you to check the shape first.
never Nothing (the empty set) Everything Code that can never be reached (exhaustive switch arms, functions that always throw). TS uses this to ensure you've handled all cases. 
// any — dangerous, spreads unsafety
const a: any = JSON.parse('...');
a.nonexistentProperty;      // ✅ TS doesn't complain (bug waiting to happen)
a.toUpperCase();            // ✅ TS doesn't complain (might crash at runtime)

// unknown — safe, forces you to narrow
const u: unknown = JSON.parse('...');
u.nonexistentProperty;      // ❌ Error: Object is of type 'unknown'
if (typeof u === 'string') {
  u.toUpperCase();          // ✅ now TS knows it's a string
}

// never — exhaustive checking
type Shape = 'circle' | 'square' | 'triangle';
function area(s: Shape): number {
  switch (s) {
    case 'circle':   return Math.PI;
    case 'square':  return 1;
    case 'triangle': return 0.5;
    default:
      const _: never = s; // if you add a 4th Shape, this line errors ✅
      throw new Error(`Unhandled shape: ${_}`);
  }
}

9. JS ecosystem interop — @types and DefinitelyTyped

Most popular JavaScript libraries were written before TypeScript existed. They ship plain .js files with no type information. TypeScript handles this through two mechanisms:

@types packages (DefinitelyTyped)

The DefinitelyTyped repository contains community-maintained type declaration files for thousands of JavaScript packages. Install them alongside the library:

npm install lodash          # install the library
npm install -D @types/lodash  # install its type declarations

TypeScript automatically finds @types/* packages in node_modules. Once installed, you get full IntelliSense and type checking for the library — without the library itself changing at all.

Writing types for untyped packages

If no @types package exists, you can write a declaration file yourself:

// types/some-old-lib.d.ts
declare module 'some-old-lib' {
  export function doThing(x: string): void;
  export const version: string;
}

// Or the "I'll type it properly later" escape hatch:
declare module 'some-old-lib'; // everything from it is: any
Many modern packages now ship their own types. React, Vue, Zod, Prisma, tRPC, and most actively maintained libraries include .d.ts files in their npm package. You don't need a separate @types install — TypeScript finds declarations automatically if the package's package.json points to them.
