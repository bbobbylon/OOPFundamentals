React: Next.js App Router & RSC

File-based routing, React Server Components (default) vs Client Components, server-side data fetching, and Server Actions — the Next.js App Router model.

🚀 From "React in the browser" to "React that runs on the server first"

Next.js's App Router (the app/ directory) makes routing file-based and components server-rendered by default. A folder is a route segment; page.tsx, layout.tsx, loading.tsx, error.tsx and [id] give it meaning. Components are React Server Components unless you opt out — they run only on the server, ship zero JS, and await data directly (DB, secrets, cached fetch) with no API round-trip. Add "use client" for interactivity (state, effects, handlers) — a Client Component that hydrates. The boundary is one-way: server can render client, not vice-versa. Server Actions ("use server") let a form call a server function that mutates and revalidatePath()s. Less client JS, co-located data, secrets that never reach the browser — at the cost of always asking "where does this run?"

  • Server-rendered by default — RSCs ship 0 KB JS and await data directly.
  • File-based routing — page/layout/loading/error/[id] per segment.
  • "use client" opts into the browser — state/effects/handlers; one-way boundary.
  • Server Actions mutate on the server with progressive enhancement.

Server Component (default)

// app/users/page.tsx — runs on the server export default async function Users() { const res = await fetch( 'https://api/users', { next: { revalidate: 60 } }) const users = await res.json() return <ul>{users.map(u => <li key={u.id}>{u.email}</li>)}</ul> } // 0 KB JS shipped for this component

Client Component (opt-in)

'use client' import { useState } from 'react' export function Counter() { const [n, setN] = useState(0) return <button onClick={() => setN(n+1)}> {n}</button> } // hooks + handlers → must be a Client Component

App Router vs Angular/SPA

SPA (CRA/Vite): everything ships to and runs in the browser; data via useEffect + an API. Angular: a client framework (SSR via Angular Universal is opt-in). Next App Router: server-first — components render on the server, only interactive leaves ship JS. Closer to a full-stack framework (routes + data + mutations) than a view library. The trade is the RSC/Client split you must reason about.

CIAM context: The App Router is a natural BFF: the root layout reads the session from an httpOnly cookie on the server, Server Components render user-specific data without exposing the token to client JS, and a Server Action performs the login — calling your Spring API, then setting the httpOnly cookie — so the access token never touches the browser (no XSS token theft). A small Client Component handles the interactive form. The "keep tokens off the browser" pattern, built into the framework.

1. The app/ Directory — Routing by File Convention

FileRole
app/page.tsxthe UI for that route segment (/)
app/layout.tsxshared shell wrapping children; persists across navigation (no re-render)
app/loading.tsxinstant Suspense fallback while the segment streams
app/error.tsxerror boundary for the segment (a Client Component)
app/users/[id]/page.tsxdynamic segment → params.id
app/(marketing)/…route group — organize without affecting the URL
Layouts nest and persist. Navigating between sibling pages re-renders the page but keeps the surrounding layout mounted (preserving its state/scroll) — the App Router's version of nested routing. loading.tsx wrapping a segment is just sugar for a React <Suspense> boundary.

2. Server Components (default) vs Client Components

Server Component (default)Client Component ('use client')
Runsonly on the serverserver (SSR) then hydrates in the browser
Ships JS?no (0 KB)yes
Canawait data, read secrets/DB, env varsuseState/useEffect, events, browser APIs
Cannotuse hooks or event handlersbe async / directly access server-only resources
The boundary is one-way: Server can render Client, not vice-versa. A Server Component imports and renders a Client Component and passes serializable props (no functions). Keep 'use client' at the leaves (a button, a form) so most of the tree stays server-rendered and JS-free. Putting 'use client' at the top of the tree drags everything below it to the client.

3. Data Fetching on the Server

// async Server Component — no useEffect, no loading state
export default async function Page() {
  const res = await fetch(url, {
    next: { revalidate: 60 } // ISR: cache 60s
  })
  const data = await res.json()
  return <List items={data} />
}

Server Components fetch by awaiting directly — no client round-trip, no useEffect, no loading flag (wrap in <Suspense>/loading.tsx for streaming). Next extends fetch with caching: cache: 'force-cache' (default, static), no-store (dynamic, per request), or next: { revalidate: N } (ISR — regenerate every N seconds). On-demand: revalidatePath() / revalidateTag().

For client-side server-state, still use TanStack Query. RSC data fetching covers the initial server render beautifully; for interactive client refetching/mutations after hydration, a Client Component + TanStack Query (or SWR) is the complement. The two layers coexist.

4. Server Actions — Mutations Without an API Route

// a Server Action: runs on the server, callable from a form
async function createUser(formData: FormData) {
  'use server'
  await db.users.create({ email: formData.get('email') })
  revalidatePath('/users') // refresh the cached list
}
<form action={createUser}>…</form> // works before JS loads (progressive enhancement)
Server Actions replace many hand-written API routes for mutations. The form posts directly to the server function; you mutate, then revalidatePath/redirect. Because it degrades to a native form POST, it works without client JS. Treat the input as untrusted — validate inside the action (it's a public endpoint under the hood), and never trust client-passed identity; read the session server-side.
