Recipe — Batch File Upload with Progress

Upload several files at once and show real progress: select multiple files, validate each (type & size) before sending, pack them into FormData, POST with HttpClient progress events for a live bar, and handle partial failures when the server accepts some and rejects others.

📤 The pattern: pick → validate → FormData → POST with progress

File upload is just a multipart POST, but a good one has four moving parts. (1) Select: an <input type="file" multiple accept="…"> gives you a FileList; you turn it into an array of File objects (each has name, size, type). (2) Validate client-side: before sending anything, reject files that are the wrong type or over a size limit — fail fast so the user fixes it without a wasted round trip. (3) Pack into FormData: you can't JSON-encode a binary file, so you build a FormData and append('files', file, file.name) for each — the browser sends it as multipart/form-data with a boundary, and you must not set the Content-Type header yourself (the browser adds the boundary). (4) POST with progress: call http.post(url, formData, { reportProgress: true, observe: 'events' }). Instead of one response, you get a stream of HttpEvents: Sent, then repeated UploadProgress events carrying loaded/total (compute the percentage for a live bar), then the final Response. For multiple files the server typically returns a per-file result so you can show that 2 succeeded and 1 was rejected (too large, wrong type, or failed a virus scan) — a partial success, not all-or-nothing. As always, client validation is UX; the server independently enforces size/type/scan limits, because a crafted request can skip the browser entirely.

  • Select — <input type="file" multiple> → an array of File (name/size/type).
  • Validate — reject wrong type / over-size client-side before uploading; fail fast.
  • FormData — append('files', file, name); let the browser set multipart/form-data (don't set it yourself).
  • Progress — {reportProgress:true, observe:'events'} streams UploadProgress (loaded/total) → a live bar; handle partial failures.

The problem

You set Content-Type "properly." The server couldn't parse a single file out of the request.

You set the header correctly, and that's exactly what broke it

Every other POST in your app sets Content-Type: application/json, so setting the header explicitly feels like the responsible habit — for a file upload, that instinct becomes headers: { 'Content-Type': 'multipart/form-data' }. It compiles. It even names the right format. Then every upload fails server-side with something like "no multipart boundary found." Nothing about the FormData itself is wrong. The problem is that multipart/form-data on its own is an incomplete value — it needs a boundary=… parameter naming the exact separator string used between files and fields in the body, and that string has to be generated fresh, from the real bytes, specifically so it can never collide with anything inside your actual files. Set the header yourself and you've told the browser "I've got this" — so it doesn't add the boundary either, and the body becomes unparseable.

FormData built correctly ✓ files attached under the right field name ✓ Content-Type set to 'multipart/form-data' ⚠ no boundary parameter anywhere in that header ⚠

The wrong assumption: setting the header yourself is being thorough. Here it's the one thing standing between the browser and the one piece of information — the boundary — only the browser can safely generate.

Let the one party who can compute the boundary write the header
Don't set Content-Type on a FormData request at all — omit the headers option for this call ↓ FormData already tells HttpClient exactly what it's sending; the browser computes the boundary and writes the full header itself If a global interceptor force-sets Content-Type on every request, special-case it: skip when the body is a FormData instance ↓ a one-line "is this a FormData?" check saves this exact bug from recurring app-wide The browser owns the one header it's uniquely positioned to get right
The browser knows something about this request that you don't: the boundary. It's a string generated at send time, from the real body, chosen specifically so it can't collide with anything inside your files. That's why a FormData upload is the one case in this whole app where not setting a header is the more correct, more deliberate choice than setting it yourself.
Think of the multipart boundary like a courier sealing several packages into one crate with a sticker that reads "use the phrase XQ7-PRT9 to know where one package ends and the next begins" — a phrase picked fresh, at packing time, specifically because it's guaranteed not to already appear inside anyone's box. Pre-print your own sticker before packing and you have no way to know whether that phrase happens to show up inside someone's contents already — and whoever unpacks the crate has no reliable way to find the seams.

Which is exactly why I exist as my own type instead of you building a plain object. Hand me to HttpClient without touching Content-Type, and the browser recognizes me and writes the entire header — type, boundary, and all — correctly, every time.

The mechanism

One POST. Several events. Watch what subscribe actually receives, over time.

  1. http.post(url, formData, { reportProgress: true, observe: 'events' }) returns an Observable of HttpEvent, not a single responseone call, a stream — not a value
  2. The browser builds the real request headers itself, computing a fresh boundary and writing the full Content-Type — because you didn'tthe payoff of leaving the header alone
  3. The first event to arrive is typically HttpEventType.Sent — confirms the request left, nothing about the response yetstep zero of the stream
  4. As bytes actually leave the network interface, repeated UploadProgress events arrive, each carrying loaded/total — divide them for the percentage your bar readsthe whole reason observe:'events' exists
  5. The server finishes and returns its result, delivered as one final HttpResponse event carrying the per-file outcome arraythe payload you actually wanted, arriving last
  6. Your subscribe handler has to branch on event.type for every one of these, because "the response" is really the last of several different event shapes sharing one streamthe shape-switch every upload handler needs

Step 1 is the one to remember, because everything after it follows from that single choice. observe:'events' trades a normal single-value Observable for a stream of several different event shapes across the life of one request. A plain http.post() call only ever hands you the last of these. Ask for events and you get to watch the request happen instead of only learning how it ended — the entire point when what you're building is a progress bar.

A normal http.post() throws away everything except the box marked "new" here — it only ever gives you the final response. Asking for events turns the same request into a stream you can watch happen, which is the only way a progress bar has anything to draw before the upload finishes.

Your batch upload sends 3 files in one request. The server successfully processes all 3 but rejects file #2 (it failed a virus scan). What should the HTTP response look like, and how does your Angular code find out which file was rejected?

A completely fair instinct — something did go wrong, so a 4xx feels right. But the request itself — three files, correctly formed, correctly authenticated — was valid and was fully processed; the server understood it perfectly and made a per-file decision. A 4xx on the whole batch would incorrectly tell files #1 and #3 they failed too, when they didn't.

Right — this is the "partial success" shape this recipe's own section 4 is built around. The HTTP status describes whether the server could process the request; the per-file result array in the body is the only place a per-item outcome can live, because HTTP has no status code that means "mostly worked."

That mixes up two different streams. observe:'events' gives you UploadProgress events while bytes are still going out over the wire — that's about the upload, not the server's verdict. However many files ride in one FormData, the server still sends back exactly one final HttpResponse for the whole POST; a per-file breakdown has to live inside that single response body, not as additional HTTP responses.

Where you've seen this before

GraphQL formalized this exact shape, AWS's own batch APIs live by it, and a KYC pipeline can't stop at the header this recipe already checks.

GraphQL's "200 OK with an errors array" is the same idea, standardized

GraphQL treats "the request was processed" and "every field resolved successfully" as two separate facts from the spec up: a response can be 200 OK and still carry a top-level errors array alongside partial data. This upload endpoint's per-file result array is a smaller, ad hoc version of the identical idea.

200 + errors[] ≈ 200 + perFileResults[]

AWS's SQS SendMessageBatch does this at much larger scale

Send 10 messages in one call, get one 200 response back — and the body separates a Successful array from a Failed array by message ID. A batch API succeeding as a request and every item inside it succeeding are treated as two separate questions industry-wide, not just in this one Angular recipe.

SendMessageBatch: one 200, two arrays

A KYC document upload can't stop at "is the Content-Type image/jpeg"

An identity-verification upload (driver's license front/back) is exactly where "the server re-validates type" has to mean something stricter than trusting the multipart part's declared Content-Type — that value is still just a client-supplied string, trivially set to image/jpeg on a file that isn't one. A real verification pipeline sniffs the actual file's magic bytes server-side (or hands it to a vendor that does) before it's ever stored or forwarded for identity matching, because a spoofed file type is the one thing this particular upload can least afford to let through.

Questions from the back row

Why not just base64-encode the files and JSON.stringify the whole thing, like every other POST?

You could, but you'd pay for it twice: base64 inflates binary data by roughly a third, and the payload becomes one giant string you can't get meaningful upload-progress events for, since HttpClient's progress tracking follows raw bytes leaving the wire, not a JSON parser's position inside a string. FormData plus multipart is the format HTTP was actually built to carry binary payloads in — it isn't legacy ceremony, it's the option with fewer tradeoffs.

Can I show progress for each file individually, or only for the whole batch?

Only the whole batch, if every file rides in one FormData and one request — reportProgress gives you loaded/total for the entire request body, with no visibility into which file's bytes are crossing the wire at any moment. True per-file bars mean one HTTP request per file, each with its own Observable and its own progress stream — at the cost of managing several concurrent requests instead of one.

Does reportProgress slow the upload down?

Negligibly — it tells HttpClient to surface progress events it can already see from the underlying request, not to add network round trips or re-read the file. The real cost is on your end: firing a change-detection cycle or a signal update on every UploadProgress event, which can arrive quite often for a large file. Throttle how frequently you actually update the visible percentage if a huge upload feels janky, rather than blaming reportProgress itself.

1. Select multiple files & validate each

onPick(e: Event) {
  const files = Array.from((e.target as HTMLInputElement).files ?? []);
  const MAX = 5_000_000; // 5 MB per file
  this.batch = files.map(f => ({
    file: f,
    error: f.size > MAX ? 'Too large (max 5 MB)'
         : !f.type.startsWith('image/') ? 'Images only'
         : null, // null = valid
  }));
}
A FileList isn't an array — spread it first. input.files is a FileList; Array.from (or [...]) gives you real array methods. Each File exposes name, size (bytes), and type (MIME). Validate up front so the user sees per-file problems immediately and you never waste bandwidth uploading a file the server will reject anyway. The accept="image/*" attribute on the input is a hint/filter for the picker — not enforcement — so you still check type and size in code.

2. Pack into FormData & POST with progress

upload() {
  const valid = this.batch.filter(b => !b.error).map(b => b.file);
  const fd = new FormData();
  valid.forEach(f => fd.append('files', f, f.name)); // same key → a list server-side

  this.http.post<UploadResult>('/api/files', fd, {
    reportProgress: true, // emit UploadProgress events
    observe: 'events', // stream events, not just the body
  }).subscribe(ev => this.handle(ev));
}
Don't set Content-Type — the browser must. Appending each file under the same key ('files') makes the server see a list. When you pass a FormData body, the browser sets Content-Type: multipart/form-data; boundary=… automatically; if you set it yourself you'll clobber the boundary and the server can't parse the parts. reportProgress:true + observe:'events' changes the Observable from "emit once with the body" to "emit a stream of HttpEvents," which is what powers the progress bar.

3. Handle the event stream & partial results

handle(ev: HttpEvent<UploadResult>) {
  if (ev.type === HttpEventType.UploadProgress) {
    this.percent = Math.round(100 * ev.loaded / (ev.total ?? 1)); // live bar
  } else if (ev.type === HttpEventType.Response) {
    this.results = ev.body!.files; // per-file [{name, status}]
    this.failed = this.results.filter(r => r.status !== 'stored');
  }
}
One request, many events — switch on ev.type. The stream goes Sent → UploadProgress×N → Response. On each UploadProgress you compute loaded/total for the bar (total can be undefined early, so guard it). On Response you read the body — and because batch uploads are partial by nature, the server returns a per-file outcome so you can show "2 stored, 1 rejected (too large)" and offer to retry just the failures. Treat the upload as a set of independent results, not a single success/failure.
