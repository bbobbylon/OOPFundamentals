The Command Pattern — the Remote Control

or, why the remote control has no idea what it's turning on

Chapter 6. You're handed a programmable remote with seven slots, and a pile of vendor classes — Light, GarageDoor, Stereo — each with its own weird API. The remote must drive all of them without knowing any of their methods. Command turns "do this request" into an object you can store in a slot, queue, log, and undo.

The problem

A remote that knows every device is a remote you rewire constantly.

Wire the buttons to the devices

Seven slots, and the remote has to know what each one is attached to — and how that particular thing is switched on.

if slot==0 light.on() else if slot==1 garage.up() else if slot==2 stereo.setCd() …and stereo needs 3 calls ⚠

And undo? The remote would need to know how to reverse every one of them.

That last slot is worth a second look. A MacroCommand is just a Command holding a list of Commands, and its execute() runs them all. The invoker cannot tell the difference — which is the same trick Composite plays two chapters later.

Why does Command give you undo almost for free, when a lambda doesn't?

LightOnCommand holds the Light and knows it called on(). That is exactly the knowledge needed to write undo() as off(). The reversal lives with the thing that caused the change.

The invoker deliberately knows nothing. If it had to record effects, it would need to understand every device — which is the coupling the pattern removes.

The stack gives you multi-level undo, but it only works because each command can already reverse itself. A stack of lambdas would have nothing to call.

Key terms

Invoker

Triggers the command and knows nothing else. RemoteControl, a menu item, a thread pool.

Receiver

The object that does the actual work. Light. It needs no changes to be commanded.

Null Object

A NoCommand in the empty slots, so the remote never checks for null. A tiny pattern that removes a whole class of guard clause.

Questions from the back row

Why not just pass a lambda? () -> light.on() does the same thing.

For execute alone, it does — and in modern Java that is often the right call. A class earns its keep the moment you need a second method: undo, a description for the log, a serialisable form to queue. A lambda gives you one method; Command gives you an object with a memory.

How does undo work for something that isn't a simple toggle?

The command stores whatever state it needs to reverse itself. A stereo command records the previous volume before changing it, then restores that on undo. The invoker still knows nothing — the knowledge stays with the thing that caused the change.

Isn't the Command just a Strategy with a different name?

The wiring rhymes; the intent does not. A Strategy answers "how should this be done" and is usually swapped once. A Command is a request — you queue them, keep a history of them, and reverse them. Strategy varies an algorithm; Command captures an action.

🎯 What is the Command pattern — and how does "encapsulating a request as an object" enable undo/redo and queuing?

The Command pattern encapsulates a request as an object, allowing you to parameterise clients with different requests, queue them, log them, and support undo. The story: the remote control (Invoker) has 7 slots. Each slot holds a Command object. When you press a button, the remote calls command.execute(). The remote doesn't know if it's turning on a light or opening a garage — it just calls execute(). The LightOnCommand knows it wraps a Light and calls light.on(). This decouples the invoker (remote) from the receiver (Light, GarageDoor, Stereo). The key benefit: undo. Add void undo() to the Command interface. LightOnCommand.undo() calls light.off(). Store the last executed command in the remote — pressing Undo calls lastCommand.undo(). The Invoker never needs to know how to undo anything — each Command undoes itself. This is why text editors have Ctrl-Z — every edit operation is a Command object stored in a history stack.

The structure

interface Command { void execute(); void undo(); } // Concrete commands class LightOnCommand implements Command { Light light; LightOnCommand(Light l) { this.light=l; } public void execute() { light.on(); } public void undo() { light.off(); } } // Invoker class RemoteControl { Command[] slots; Command lastCmd; void setCommand(int slot, Command c) { slots[slot]=c; } void onPressed(int slot) { slots[slot].execute(); lastCmd=slots[slot]; } void undoPressed() { lastCmd.undo(); } } // Receiver class Light { void on() { ... } void off() { ... } }

Macro commands + queuing

Macro commands: class MacroCommand implements Command { Command[] commands; void execute() { for (Command c : commands) c.execute(); } } — one button triggers multiple commands. Queuing: store Commands in a queue, execute asynchronously. Job scheduler: queue.add(new SendEmailCommand(user)) — worker thread calls command.execute(). Command objects are self-contained requests — all information needed to execute is inside the object. Logging: before execute(), serialise the command to disk — if the system crashes, replay the logged commands on restart. This is how database transaction logs work.

Lambda as Command

Since Command is a functional interface (one method), lambdas replace concrete Command classes: remote.setCommand(0, () -> light.on()). Same effect, less boilerplate. Without undo: Runnable cmd = () -> light.on(); cmd.run(). With undo: keep the Runnable pair: record CommandPair(Runnable execute, Runnable undo) {}. remote.setCommand(0, new CommandPair(() -> light.on(), () -> light.off())). Java's Executor.submit(Runnable r) is the Command pattern — the Executor is the Invoker, the Runnable is the Command, the thread is the Receiver.

In CIAM / Spring Boot: Admin role assignment with undo: interface UserCommand { void execute(); UserCommand reverse(); } class AssignRoleCommand implements UserCommand { Long userId; Long roleId; void execute() { roleService.assign(userId, roleId); auditLog.record("ASSIGN_ROLE", userId, roleId); } UserCommand reverse() { return new RemoveRoleCommand(userId, roleId); } }. Admin UI: "Assign Role" calls cmd.execute(). "Undo" calls cmd.reverse().execute(). History: stack of executed commands for "What changed?" audit trail. Spring Batch: each ItemProcessor step is a Command; JobLauncher.run(job, params) is the Invoker. Spring @Async/ThreadPoolTaskExecutor: submits Runnable Commands to a queue.

Act 1 — the remote that knew too much

The naive remote hard-codes each vendor's API into its button handlers — an if/else per device, calling light.on() here, garageDoor.up() there, stereo.setCd() over there.

void onButtonPressed(int slot) {
  if (slot == 0) light.on();  // to add a new device, you reopen THIS method and add another branch
  else if (slot == 1) garageDoor.up();
  else if (slot == 2) { stereo.on(); stereo.setCd(); stereo.setVolume(11); }
  // … the remote is welded to every device's API …
}
Brain Power. Every new gadget reopens the remote and adds another branch. The remote — which should just be seven buttons — depends on Light, GarageDoor, Stereo, and their exact method names. We want the remote to invoke a request without knowing a thing about the receiver or the action.

Act 2 — wrap the request in an object

A Command packages a receiver and an action behind one method, execute(). The light command holds a light and calls on() — nobody outside needs to know that.

The Command interface

interface Command {
  void execute();
  void undo();
}

A concrete command wraps a receiver

class LightOnCommand implements Command {
  private Light light;   // the receiver
  LightOnCommand(Light l) { light = l; }  // the receiver is handed in once, at construction — the invoker never sees Light directly
  public void execute() { light.on(); }
  public void undo()    { light.off(); }
}
Design Principle — Encapsulate What VariesThe request is what varies — button actions change, device APIs get added. Package the request as a Command object and the invoker never needs editing when requests change.

Act 3 — invoker, command, receiver

The remote (the invoker) just holds Command objects in slots and calls execute(). It never references a single device class.

// setup: load a slot with a command
remote.setCommand(0, new LightOnCommand(livingRoomLight));

// runtime: a button press is the same line for every device
void onButtonPressed(int slot) {
  commands[slot].execute();   // remote knows only "Command"
}

Q: The remote does almost nothing now — isn't that a waste of a class?

A: That "almost nothing" is the point. The invoker is deliberately dumb so it can drive any request. The same remote can fire a light, a garage door, or a whole "party mode" macro — because all it ever calls is execute().

Act 4 — undo, queues, and macros

Because a request is now an object, you can do things you never could with a method call:

Undo — remember the last command

Command last = commands[slot];
last.execute();
undoStack.push(last);
// undo button:
undoStack.pop().undo();   // reverse it

Macro — a command of commands

class MacroCommand implements Command {
  Command[] commands;  // a MacroCommand IS a Command, made of other Commands — the same interface, recursively
  public void execute() {
    for (Command c : commands) c.execute();  // runs every wrapped command in order, with no idea what any of them actually do
  }
}

Same idea powers job queues (put commands on a thread pool), logging (record executes, replay after a crash), and transactional request objects.

The Command Pattern, defined

The Command Pattern encapsulates a request as an object, thereby letting you parameterize other objects with different requests, queue or log requests, and support undoable operations.
You've used it. A Runnable handed to an ExecutorService is a Command on a queue. Angular's reactive actions and an event handler bound to (click)="save()" are requests-as-objects. Next in the track: Adapter & Facade.

NoCommand — the Null Object for empty slots

What sits in a slot that hasn't been programmed? A NoCommand — the Null Object pattern. Every slot starts with one, so commands[slot].execute() is always safe. No null check needed in the invoker.

class NoCommand implements Command {
  public void execute() { }   // do nothing, safely
  public void undo()    { }
}
// initialize every slot at construction:
for (int i = 0; i < 7; i++) commands[i] = new NoCommand();
// now commands[slot].execute() never NPEs

You'll see Null Object everywhere: Collections.emptyList(), SLF4J's no-op logger, Spring's NoOpPasswordEncoder. Replace "do nothing if null" with an object that does nothing.

Command in your stack

Java — Runnable on a thread pool

ExecutorService pool = Executors.newFixedThreadPool(4);
// Runnable IS-A Command: execute = run()
pool.submit(() -> emailService.send(user));
pool.submit(() -> reportService.generate(id));
// invoker = pool · receiver = lambda body

Spring — ApplicationEvent

class UserRegisteredEvent { String email; }
// publisher = Invoker
publisher.publishEvent(new UserRegisteredEvent(email));
// listener = Command — decoupled, swappable
@EventListener
void onRegister(UserRegisteredEvent e) { ... }
You live in it. Every Runnable on a thread pool, Spring ApplicationEvent, NgRx Action, or CQRS command-bus message is the Command pattern. The common thread: a request packaged as an object so it can be queued, logged, replayed, or handed off between threads without the sender knowing anything about the receiver.
