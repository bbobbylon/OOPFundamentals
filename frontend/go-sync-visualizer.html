Go: sync & Worker Pools

Mutex and RWMutex, WaitGroup and Once, the lock-free sync/atomic package, and the bounded worker-pool pattern — coordinating goroutines without data races.

"Don't communicate by sharing memory" — so when do you reach for sync?

Go's motto is share memory by communicating (use channels), but plenty of real code does need to guard shared state, and that's what the sync and sync/atomic packages are for. A sync.Mutex gives mutual exclusion: mu.Lock(); defer mu.Unlock() ensures one goroutine at a time touches the protected data — the fix for the data race the race detector catches. A sync.RWMutex splits that into RLock (many concurrent readers) and Lock (one exclusive writer) — a big win for read-heavy state like a cache. A sync.WaitGroup lets one goroutine wait for a set of others: wg.Add(n), each worker defer wg.Done(), then wg.Wait() blocks until the count hits zero. sync.Once runs an initializer exactly once even under concurrency — the idiom for lazy singletons. When the shared state is a single number or pointer, sync/atomic (atomic.AddInt64, CompareAndSwap, atomic.Value) is lock-free and faster than a mutex. And the capstone pattern, the worker pool, bounds concurrency: instead of spawning a goroutine per task (which can exhaust memory or hammer a downstream), you start a fixed number of workers that pull from a jobs channel and push to a results channel. The two rules that prevent most bugs: always pair Lock with a deferred Unlock, and never copy a sync type after first use (pass *T, not T) — go vet flags a copied lock.

RWMutex-guarded cache

type Cache struct { mu sync.RWMutex m map[string]*JWKS } func (c *Cache) Get(k string) *JWKS { c.mu.RLock() defer c.mu.RUnlock() return c.m[k] // many readers } func (c *Cache) Put(k string, v *JWKS) { c.mu.Lock() defer c.mu.Unlock() c.m[k] = v // one writer }

Bounded worker pool

jobs := make(chan Job) results := make(chan Result) var wg sync.WaitGroup for i := 0; i < 8; i++ { // 8 workers wg.Add(1) go func() { defer wg.Done() for j := range jobs { // drain results <- handle(j) } }() } // feed jobs, close(jobs), wg.Wait()

Go sync vs Java concurrency

Java: synchronized blocks / ReentrantLock (Mutex), ReadWriteLock (RWMutex), CountDownLatch (WaitGroup), AtomicInteger (atomic), ExecutorService thread pools (worker pool). Go: same toolbox, but note sync.Mutex is not reentrant — a goroutine that re-locks a mutex it already holds deadlocks (Java's synchronized is reentrant). And Go favors goroutines + channels over an executor; a worker pool is a handful of plain goroutines, not a framework.

In a CIAM context: A JWKS / token cache is the textbook RWMutex case — thousands of concurrent token validations read the keys while a background refresh occasionally writes them. Lazy-load the signing keys exactly once with sync.Once so a burst of first requests doesn't fetch the JWKS five times. And when you must validate a batch of tokens against an external IdP, a bounded worker pool (say 16 workers) keeps you from opening 10,000 simultaneous connections and getting rate-limited or OOM-killed.

1. Mutex & RWMutex

// Mutex: exactly one goroutine in the critical section
var mu sync.Mutex
mu.Lock()
defer mu.Unlock()
balance += amount

// RWMutex: concurrent reads, exclusive writes
var rw sync.RWMutex
rw.RLock(); v := m[k]; rw.RUnlock() // reader
rw.Lock(); m[k] = v; rw.Unlock() // writer

Use a plain Mutex by default; reach for RWMutex only when reads vastly outnumber writes (its bookkeeping is heavier, so it loses on write-heavy or low-contention data). Keep critical sections small — hold the lock only around the shared access, not around slow I/O. defer Unlock() guarantees release even on a panic or early return.

Go mutexes are not reentrant. If a function holding the lock calls another that also locks the same mutex, it deadlocks. Structure code so the locked region doesn't call back into locking code — or split into a public method that locks and a private one that assumes the lock is held.

2. WaitGroup & Once

// WaitGroup: wait for N goroutines to finish
var wg sync.WaitGroup
for _, u := range urls {
  wg.Add(1)
  go func(u string) {
    defer wg.Done()
    fetch(u)
  }(u)
}
wg.Wait() // blocks until count == 0

Call wg.Add before launching the goroutine, not inside it — otherwise Wait can race past before the goroutine registers. defer wg.Done() in the worker keeps the count correct even on panic. sync.Once is the companion for one-time work: var once sync.Once; once.Do(initFn) runs initFn exactly once no matter how many goroutines call it concurrently — the standard lazy-singleton / lazy-init idiom.

A negative WaitGroup counter panics. More Done() calls than Add() (a stray defer, double-Done) crashes with "negative WaitGroup counter." Match every Add(1) with exactly one Done().

3. sync/atomic — Lock-Free for Single Values

OperationUse
atomic.AddInt64(&n, 1)concurrent counter without a mutex
atomic.LoadInt64 / StoreInt64safe read/write of a shared int
atomic.CompareAndSwap... (CAS)lock-free state machines / flags
atomic.Value / atomic.Pointer[T]atomically swap a whole config/snapshot pointer
Atomics are for one variable, not an invariant across several. If two fields must change together (e.g. balance and a log entry), atomics can't keep them consistent — you need a mutex. Reach for atomic only when the entire shared state is a single number or pointer.

4. The Worker Pool: Bounded Concurrency

jobs := make(chan Job)
results := make(chan Result)
var wg sync.WaitGroup

// start a FIXED number of workers
for w := 0; w < 8; w++ {
  wg.Add(1)
  go func() {
    defer wg.Done()
    for j := range jobs { results <- handle(j) } // drain until closed
  }()
}
go func() { for _, j := range allJobs { jobs <- j }; close(jobs) }() // feed, then close
go func() { wg.Wait(); close(results) }() // close results when workers done
for r := range results { collect(r) } // consume
Closing in the right order is the whole trick. Close jobs after feeding so the range loops end and workers exit; then a separate goroutine does wg.Wait() and closes results, so the consumer's range terminates. Close too early and you send on a closed channel (panic); never close and the consumer blocks forever.
