Go: defer, panic & recover

Deferred calls run LIFO at return, panic unwinds the stack running those defers, and recover — only inside a deferred function — turns a panic back into an error at a boundary.

🧹 Go has no try/catch — so how do defer, panic, and recover handle cleanup and failure?

Go splits try/catch/finally into three precise tools. defer schedules a call to run when the function returns (even on panic), in LIFO order, with arguments evaluated immediately — the idiomatic acquire/release pairing (f, _ := os.Open(p); defer f.Close()). panic stops normal flow and unwinds the stack, running every already-scheduled defer on the way; uncaught, it crashes with a stack trace and exit status 2. recover is the only thing that stops a panic, and only directly inside a deferred function — it returns the panic value and lets the function return normally. The idiom: ordinary error returns for expected failures, panic only for unrecoverable bugs, and recover only at a boundary (HTTP middleware, worker loop) to keep one bad request from killing the process.

  • defer = LIFO cleanup on return — args captured at the defer statement.
  • Pairs acquire/release — Open/Close, Lock/Unlock sit together.
  • panic unwinds running defers; uncaught it crashes with exit 2.
  • recover only in a deferred func — use at a boundary, not as error handling.

defer is LIFO + args eval now

func demo() { defer fmt.Println("1") defer fmt.Println("2") defer fmt.Println("3") fmt.Println("body") } // body // 3 // 2 // 1 (LIFO) // args captured at defer time: i := 0 defer fmt.Println(i) // captures 0 i = 99 // → still prints 0

panic / recover boundary

func safe() (err error) { defer func() { if r := recover(); r != nil { err = fmt.Errorf("recovered: %v", r) } }() risky() // may panic return nil } // panic in risky() → unwinds → deferred // func runs → recover() returns the value // → err is set, safe() returns normally

Go vs Java try/catch/finally

Java: try { risky(); } catch (E e) { handle(e); } finally { cleanup(); } — exceptions are the normal error channel. Go: errors are ordinary return values (v, err := risky()), finally → defer cleanup(), and catch → a deferred recover() used sparingly. Panics are NOT Go's error handling — they signal "this should never happen." A library that panics across its API boundary is considered badly behaved; it should return an error instead.

CIAM context: Every production HTTP server wraps handlers in a recover middleware so a nil-pointer panic in one token-validation request returns a clean 500 instead of crashing the auth service for every other user: defer func() { if r := recover(); r != nil { log.Error(r); http.Error(w, "internal error", 500) } }(). That's exactly what Go's net/http does per-connection and what Gin's Recovery() middleware does — one panic-safe boundary protecting the process.

1. defer: LIFO, and Arguments Evaluated Immediately

// LIFO: last deferred runs first
defer fmt.Println("1")
defer fmt.Println("2")
defer fmt.Println("3")
// prints: 3, 2, 1 at return

// pair acquire + release
mu.Lock()
defer mu.Unlock()
f, _ := os.Open(p)
defer f.Close()

Arguments are evaluated at the defer line, then the call is queued. So defer fmt.Println(i) captures the value of i right now; reassigning i later does not change what prints. A defer func(){ ... i ... }() closure, by contrast, reads i when it runs — so it sees the final value. This single distinction is the most common defer surprise.

defer in a loop runs at function return, not loop-iteration end. for _, p := range paths { f, _ := os.Open(p); defer f.Close() } keeps every file open until the function returns — a file-descriptor leak. Fix: wrap the body in a closure called each iteration, or close explicitly inside the loop.

2. panic Unwinds the Stack — Running Defers as It Goes

A panic stops normal execution and walks back up the call stack. At each frame it runs that frame's already-scheduled deferred calls (so cleanup still happens), then continues unwinding. If nothing recovers, the runtime prints the panic value + a stack trace and the process exits with code 2.

3. recover: Only Inside a Deferred Function

// convert a panic into an error return
func Safe() (err error) {
  defer func() {
    if r := recover(); r != nil {
      err = fmt.Errorf("recovered: %v", r)
    }
  }()
  risky() // may panic
  return nil
}

recover() returns the panic value, or nil when there is no panic — so the if r != nil check is mandatory. It only works when called directly by a deferred function (not in a helper the deferred function calls). Using a named return value (err error) lets the deferred recover set the function's return. Execution does not resume where the panic happened — it continues in the caller, as if Safe() returned normally with the error you set.

recover only catches panics in the same goroutine. A go func(){ panic("x") }() with no recover inside that goroutine crashes the whole program — the parent's recover can't see it. Every goroutine that might panic needs its own deferred recover.

4. The Production Idiom: a Panic-Safe Boundary

// HTTP middleware: one panic → one 500, process stays up
func Recovery(next http.Handler) http.Handler {
  return http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
    defer func() {
      if rec := recover(); rec != nil {
        log.Printf("panic: %v\n%s", rec, debug.Stack())
        http.Error(w, "internal error", http.StatusInternalServerError)
      }
    }()
    next.ServeHTTP(w, r)
  })
}
Log the stack at the boundary with runtime/debug.Stack() before responding — once you recover, the original stack trace is gone, and a bare "recovered: nil pointer" with no location is nearly useless for debugging.
