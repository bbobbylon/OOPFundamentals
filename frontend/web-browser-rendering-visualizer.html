How Browsers Work — Parsing, Render Tree, Layout & Paint

Every page you write in this track — HTML, CSS, JavaScript, the DOM — ends up funneled through one pipeline: parse → style → layout → paint → composite. This page is the payoff: it shows exactly what the browser does with your markup, and why Angular's change detection and React's virtual DOM exist as optimizations layered on top of it.

🖥️ What actually happens between "the server sends HTML" and "pixels are on screen"?

When a browser receives an HTML response, it doesn't just "show" it — it runs a fixed pipeline called the critical rendering path. First, the HTML parser reads the bytes and builds the DOM tree (a tree of objects representing every tag). In parallel, any CSS it encounters gets parsed into the CSSOM tree (every selector's computed styles). The browser then merges DOM + CSSOM into the render tree — but only the nodes that are actually visible; an element with display: none is left out entirely, as if it were never there. Next comes layout (also called reflow): the browser walks the render tree and computes the exact pixel size and position of every box, top to bottom, left to right. Then paint fills in the actual pixels — colors, borders, shadows, text — onto one or more layers. Finally compositing stitches those layers together and hands the result to the GPU to draw on screen. Every one of your HTML/CSS/JS pages in this track feeds this exact pipeline; this page is the "zoom out" that explains why script placement, `display` vs `visibility`, and CSS `transform` all behave the way they do — and it's the literal mechanism that Angular's change detection and React's virtual DOM are built to minimize calls into, because layout and paint are the expensive parts.

  • Fixed pipeline — parse HTML → parse CSS → render tree → layout → paint → composite, always in that order.
  • display:none vs visibility:hidden — one is excluded from the render tree entirely; the other still costs a full layout pass.
  • Scripts can block parsing — a plain <script src> halts the HTML parser until it downloads and runs; defer/async fix that.
  • Not all CSS changes cost the same — layout-affecting properties trigger reflow+repaint; transform/opacity can skip both and go straight to the GPU.

Why this page exists

Every other page in this track teaches a piece — HTML tags, CSS selectors, JS/DOM APIs — in isolation. This page is the assembly line those pieces run on. Once you've seen the pipeline, "why does animating left feel janky but transform doesn't" stops being folklore and becomes a fact you can predict.

Angular / React comparison

Angular's change detection and React's virtual DOM diffing exist to answer one question cheaply: did anything that affects the render tree actually change? Both frameworks batch DOM writes and try to touch layout-affecting properties as few times as possible per frame — because layout and paint, not JS execution, are usually the actual bottleneck.

Interview-relevant traps

display:none element = zero layout cost, siblings collapse into its space. visibility:hidden = still occupies its box, still costs a layout pass, just isn't painted. Reading `.offsetHeight` in a loop after writing styles is the classic "layout thrashing" bug — each read forces a synchronous reflow.

Where this shows up on the job: a login form that flashes unstyled content, a spinner that never smoothly fades, a mega-menu that stutters on hover — these are almost always critical-rendering-path problems: a blocking script delaying first paint, an animation driving reflow every frame, or a visibility:hidden element silently eating layout cost on every page render. 1. The critical rendering path — six steps, always this order

// what the browser does with one HTML response
1. Parse HTML bytes → DOM tree // every tag becomes a node
2. Parse CSS bytes → CSSOM tree // every selector's computed styles
3. DOM + CSSOM → Render Tree // visible nodes only — display:none is dropped
4. Render Tree → Layout / Reflow // exact size + position of every box
5. Layout → Paint // fill in pixels: color, text, borders, shadows
6. Paint layers → Composite // GPU stitches layers onto the screen
The render tree is not the DOM. It's a filtered, styled projection of it. Nodes with display:none, <head>, <script>, and HTML comments never enter the render tree at all — they exist in the DOM (JavaScript can still query them) but the layout/paint/composite stages never see them, so they cost nothing. This is the single fact that explains most of the "hidden element" gotchas below.

2. Parser-blocking scripts — why script placement and defer/async matter

<!-- BLOCKS parsing: browser stops, fetches, executes, THEN continues -->
<head>
  <script src="analytics.js"></script>
</head>

<!-- fetches in parallel with parsing, runs in order, after parse -->
<script src="app.js" defer></script>

<!-- fetches in parallel, runs the instant it's ready — order NOT guaranteed -->
<script src="widget.js" async></script>
CSS blocks rendering, not parsing. A <link rel="stylesheet"> in <head> does not stop the HTML parser from building the DOM — but the browser refuses to paint until the CSSOM is ready, because painting unstyled content and then re-painting it styled would cause a visible flash. Scripts are the opposite: a plain <script> genuinely halts the parser itself, because the script might call document.write() and change what comes next.

3. Reflow vs repaint vs composite — not all style changes cost the same

// EXPENSIVE — triggers layout (reflow) + paint + composite
el.style.width = '400px'; // size changed → everything downstream re-measured
el.style.left = '20px'; // position changed → reflow

// CHEAPER — skips layout, still repaints
el.style.backgroundColor = 'red'; // no size/position change

// CHEAPEST — skips layout AND paint, goes straight to the GPU compositor
el.style.transform = 'translateX(20px)';
el.style.opacity = '0.5';
This is why animation libraries prefer transform. Changing left/width/font-size forces the browser to recompute layout for that element and everything that depends on it — on every single animation frame, that's up to 60 expensive reflows a second. transform and opacity can be handled entirely on the GPU compositor thread, bypassing layout and paint completely — the same visual motion, none of the cost.
