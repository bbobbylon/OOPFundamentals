CSRF Protection — and when you need it

Cross-Site Request Forgery tricks a logged-in user's browser into firing an authenticated request to your app from a malicious page. The crucial insight: it only works when the credential is something the browser attaches automatically — a cookie. A token your JavaScript explicitly puts in an Authorization header can't be forged this way, which is exactly why this app safely turns CSRF off.

What is a CSRF attack — and why are bearer-token APIs immune to it?

Imagine you're logged into your bank at bank.com (authenticated via cookie). You visit a malicious page at evil.com. That page has a hidden form: <form action="https://bank.com/transfer" method="POST"><input name="amount" value="10000"></form>. When the page loads, JavaScript submits the form. The browser sends the request to bank.com — and automatically includes your bank.com authentication cookie, because that's what browsers do with cookies. The bank's server sees a valid, authenticated request to transfer $10,000. This is Cross-Site Request Forgery (CSRF). The key: it only works because the credential (cookie) was attached automatically by the browser. If your Angular app puts a Bearer token in the Authorization header explicitly, evil.com can't forge that — it doesn't have the token. This is why Spring Security's CSRF protection can be safely disabled for pure API backends that use Bearer tokens.

When to disable CSRF

Safe to disable when: your API uses Bearer tokens in the Authorization header (Angular does this). The browser never auto-attaches the credential. In Spring Security: http.csrf(csrf -> csrf.disable()). This is correct and safe for REST APIs consumed by Angular with bearer tokens. Disabling CSRF on an API that uses httpOnly cookies (BFF pattern) is dangerous — see BFF page.

When you MUST keep CSRF on

If you use session cookies or httpOnly cookies for authentication (BFF pattern, traditional MVC apps), CSRF protection is mandatory. Spring Security default: CSRF on, requires X-CSRF-TOKEN header or form parameter on state-changing requests. Use CookieCsrfTokenRepository.withHttpOnlyFalse() — Angular reads the XSRF-TOKEN cookie and sends it back as X-XSRF-TOKEN header automatically.

SameSite cookie attribute

Modern browsers support SameSite=Lax or SameSite=Strict on cookies, which prevents the browser from sending the cookie on cross-site requests. SameSite=Lax (browser default) blocks cookies on cross-site POST/DELETE/PATCH but allows on top-level navigations. This makes CSRF much harder even without a CSRF token. But don't rely on SameSite alone — CSRF tokens remain best practice when using cookies.

In CIAM: Standard Angular + Bearer token setup: http.csrf(c -> c.disable()) — safe. BFF setup (Angular + httpOnly session cookie): CSRF protection must be on. Use CookieCsrfTokenRepository.withHttpOnlyFalse() and ensure Angular's HttpClient is configured to send X-XSRF-TOKEN header (it does automatically when you set withCredentials: true on requests and the XSRF-TOKEN cookie is present). Confusion point: devs often disable CSRF in the BFF app because it "seems like a REST API" — then they're vulnerable to CSRF attacks because the session cookie IS auto-attached.

1. Why CSRF works (when it works)

victim logged into your-app.com  (has a session cookie)
victim visits evil.com  →  it auto-submits a form to your-app.com
browser auto-attaches the cookie  →  your app sees a "valid" request 💥

The attacker never sees the cookie — they just rely on the browser sending it. So the question is always: does the auth credential ride along automatically? Cookie = yes (forgeable). Custom header = no (safe).

3. Why this app disables CSRF (correctly)

// SecurityConfig — stateless + JWT in a header ⇒ CSRF off is correct
http.csrf(AbstractHttpConfigurer::disable)
    .sessionManagement(s -> s.sessionCreationPolicy(STATELESS));

No session cookie carries auth here — the SPA reads the JWT and explicitly sets Authorization: Bearer …. A forged cross-site request can't set that header (and can't read your token to copy it), so there's nothing to forge. Disabling CSRF on a stateless JWT API is right, not a shortcut.

4. When you DO need it: cookies / BFF

The moment auth rides on a cookie — a classic server session, or a BFF using an httpOnly session cookie — CSRF is back on the table. Enable it:

// BFF / cookie-session mode — double-submit cookie token
http.csrf(c -> c.csrfTokenRepository(
        CookieCsrfTokenRepository.withHttpOnlyFalse()));
// + set the session cookie SameSite=Lax/Strict
  • Synchronizer token — server stores a per-session token; the form/request must echo it. Stateful, strongest.
  • Double-submit cookie — token in a cookie + the same value in a header; the server checks they match. Stateless-friendly (SPA reads the cookie, sends the header).
  • SameSite cookies are the first line — the browser won't send the cookie cross-site (Strict) or on cross-site sub-requests (Lax).
  • Also check Origin/Referer on state-changing requests.

5. One-sentence recap

🛡️ CSRF abuses credentials the browser sends automatically (cookies), so a stateless API with a JWT in the Authorization header is not vulnerable — which is why this app correctly csrf().disable()s — but the instant you authenticate with a cookie (classic session or a BFF), turn CSRF back on with a synchronizer or double-submit token plus SameSite cookies (and Origin checks); and don't confuse CSRF with CORS — different attacks, different defenses.
