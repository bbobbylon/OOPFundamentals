CSRF Protection — and when you need it

Cross-Site Request Forgery tricks a logged-in user's browser into firing an authenticated request to your app from a malicious page. The crucial insight: it only works when the credential is something the browser attaches automatically — a cookie. A token your JavaScript explicitly puts in an Authorization header can't be forged this way, which is exactly why this app safely turns CSRF off.

1. Why CSRF works (when it works)

victim logged into your-app.com  (has a session cookie)
victim visits evil.com  →  it auto-submits a form to your-app.com
browser auto-attaches the cookie  →  your app sees a "valid" request 💥

The attacker never sees the cookie — they just rely on the browser sending it. So the question is always: does the auth credential ride along automatically? Cookie = yes (forgeable). Custom header = no (safe).

2. Interactive: is this app vulnerable?

How does the app authenticate requests?

Watch what credential the forged cross-site request carries — that's the whole verdict.

3. Why this app disables CSRF (correctly)

// SecurityConfig — stateless + JWT in a header ⇒ CSRF off is correct
http.csrf(AbstractHttpConfigurer::disable)
    .sessionManagement(s -> s.sessionCreationPolicy(STATELESS));

No session cookie carries auth here — the SPA reads the JWT and explicitly sets Authorization: Bearer …. A forged cross-site request can't set that header (and can't read your token to copy it), so there's nothing to forge. Disabling CSRF on a stateless JWT API is right, not a shortcut.

4. When you DO need it: cookies / BFF

The moment auth rides on a cookie — a classic server session, or a BFF using an httpOnly session cookie — CSRF is back on the table. Enable it:

// BFF / cookie-session mode — double-submit cookie token
http.csrf(c -> c.csrfTokenRepository(
        CookieCsrfTokenRepository.withHttpOnlyFalse()));
// + set the session cookie SameSite=Lax/Strict
  • Synchronizer token — server stores a per-session token; the form/request must echo it. Stateful, strongest.
  • Double-submit cookie — token in a cookie + the same value in a header; the server checks they match. Stateless-friendly (SPA reads the cookie, sends the header).
  • SameSite cookies are the first line — the browser won't send the cookie cross-site (Strict) or on cross-site sub-requests (Lax).
  • Also check Origin/Referer on state-changing requests.

↪ The cookie-based architecture this matters for: Spring · BFF & Token Relay. CORS is a different control: Debugging · CORS Failures.

5. One-sentence recap

🛡️ CSRF abuses credentials the browser sends automatically (cookies), so a stateless API with a JWT in the Authorization header is not vulnerable — which is why this app correctly csrf().disable()s — but the instant you authenticate with a cookie (classic session or a BFF), turn CSRF back on with a synchronizer or double-submit token plus SameSite cookies (and Origin checks); and don't confuse CSRF with CORS — different attacks, different defenses.
