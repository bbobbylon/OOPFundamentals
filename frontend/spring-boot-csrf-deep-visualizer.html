CSRF Protection — and when you need it

Cross-Site Request Forgery tricks a logged-in user's browser into firing an authenticated request to your app from a malicious page. The crucial insight: it only works when the credential is something the browser attaches automatically — a cookie. A token your JavaScript explicitly puts in an Authorization header can't be forged this way, which is exactly why this app safely turns CSRF off.

🛡️ What is a CSRF attack — and why are bearer-token APIs immune to it?

You're logged into bank.com via a cookie. You open evil.com, which has a hidden <form action="https://bank.com/transfer" method="POST"> that auto-submits. The browser sends the request to bank.com and automatically attaches your bank cookie — so the server sees a valid, authenticated $10,000 transfer. That's Cross-Site Request Forgery, and it only works because the credential rides along automatically. A Bearer token set explicitly in the Authorization header can't be forged by evil.com — it doesn't have the token. That's why Spring's CSRF protection can be safely disabled for pure Bearer-token APIs, and why it's mandatory the moment you use cookies.

  • CSRF rides on auto-attached credentials — cookies, not explicit headers.
  • Bearer tokens are immune. The attacker can't read or set your Authorization header.
  • Cookie/session auth needs CSRF on — a token header (or SameSite) re-introduces intent.
  • The BFF trap: "it looks like a REST API" so devs disable CSRF — but the session cookie auto-attaches.

When to disable

Safe when the API authenticates via Bearer tokens in the Authorization header (standard Angular): http.csrf(csrf -> csrf.disable()). The browser never auto-attaches the credential, so there's nothing to forge.

When you MUST keep it on

Session/httpOnly-cookie auth (BFF, classic MVC) requires CSRF. Spring's default expects an X-CSRF-TOKEN on state-changing requests; CookieCsrfTokenRepository.withHttpOnlyFalse() lets Angular echo the XSRF-TOKEN cookie as X-XSRF-TOKEN automatically.

SameSite cookies

SameSite=Lax (the browser default) blocks cookies on cross-site POST/DELETE/PATCH while allowing top-level navigation; Strict blocks more. It makes CSRF much harder — but don't rely on it alone; keep CSRF tokens when using cookies.

CIAM: Standard Angular + Bearer: http.csrf(c -> c.disable()) is safe. BFF (Angular + httpOnly session cookie): CSRF must stay on — use CookieCsrfTokenRepository.withHttpOnlyFalse() and send requests with withCredentials:true so Angular returns the X-XSRF-TOKEN automatically. The common mistake is disabling CSRF in the BFF because it "feels like a REST API" — then the auto-attached session cookie makes it vulnerable.

Brain Power

This BFF has CSRF properly enabled — CookieCsrfTokenRepository, Angular echoing X-XSRF-TOKEN, every POST/PUT/DELETE tested and confirmed to reject a forged request. A teammate ships a one-click "close my account" link as a plain GET /account/close?confirm=true. Before you look at the fork below: does CsrfFilter even look at this request?

GET /account/close?confirm=truesame session cookie as every other request
↓ CsrfFilter checks the method first
GET / HEAD / OPTIONS / TRACE → "safe" → no token required ← this request POST / PUT / PATCH / DELETE → "unsafe" → token required, checked here
The fork runs on every request, safe method or not — CsrfFilter never skips itself, it only skips the token check.
What decides which lane a request lands in is one thing, and one thing only: the verb sitting at the front of the request line. Not the path. Not what the endpoint actually does to your database.
GET is HTTP's own promise that nothing changes — CsrfFilter takes that promise on faith and waves every GET through untouched. Break the promise anywhere in the app and the fork doesn't weaken or bend. It just finishes answering a question this request was never going to be asked.

So: the picture answers the Brain Power question. CookieCsrfTokenRepository, the X-XSRF-TOKEN wiring, every POST/PUT/DELETE endpoint tested — none of it is broken, and none of it is even consulted. /account/close took the left lane, and the left lane has no checkpoint.

Spring's CsrfFilter doesn't protect your application — it protects four HTTP methods. Everything except GET, HEAD, OPTIONS, and TRACE gets a token check; those four are waved through by design, because HTTP's own spec calls them "safe" and promises they never change anything. Enabling CSRF is necessary but nowhere near sufficient — the moment one of your endpoints breaks that promise, the filter's coverage of it isn't weakened, it's zero.
Think of CsrfFilter as a bouncer posted at a revolving door, checking IDs on everyone who spins through it. There's a side door marked EXIT ONLY a few feet away, and he doesn't watch it at all — nobody's supposed to enter that way, so why would he? The revolving door is every POST/PUT/DELETE in your app. The exit door is GET. It works perfectly until someone quietly wires the exit door to also let people into the vault.
The mechanism

Every request meets the same filter. Only some of them get asked for proof.

  1. CsrfFilter sits early in the chain and runs on every request, safe method or notnothing skips the filter itself
  2. It checks the request's HTTP method against its "requires CSRF" matcherthe one decision that matters
  3. GET, HEAD, OPTIONS, TRACE → matcher says "not required" → the request passes through untouchedthe "safe methods" HTTP already promised
  4. Any other method — POST, PUT, PATCH, DELETE → matcher says "required" → the filter looks for a tokeneverything meant to change data
  5. Token present and matching the one tied to the session → request continues to authentication/authorizationthe happy path
  6. Token missing or mismatched on a required method → 403 immediately, before your controller ever runsthis is the protection actually firing

Step 3 is the lesson. CSRF's entire value depends on a promise your own endpoints have to keep — that a GET never changes anything. Break that promise anywhere in the app and step 3 waves the attack straight through, with the filter behaving exactly as designed the whole time. Nothing is misconfigured. The filter did its job; the job just didn't cover this request.

and here's the fix, as one rule: route state-changing actions onto a state-changing verb, no exceptions for convenience. POST /account/close (or DELETE) falls under the four methods CsrfFilter actually inspects. A one-click email link can still land on a tiny confirmation page with a real button instead of a bare href — one tap, same feel, but it goes out as a real POST carrying the token. GET stays exactly what HTTP promises it is: safe to click, cache, and prefetch.

A BFF has CSRF fully enabled and every mutating endpoint verified to require X-XSRF-TOKEN. A teammate ships a one-click "unsubscribe" feature as a plain GET /notifications/unsubscribe link, meant to be pasted straight into emails. An attacker posts that same URL as a clickable link in a public forum thread. A logged-in victim clicks it out of curiosity. What happens?

A reasonable guess, because SameSite=Lax does block plenty of cross-site requests. But it carves out exactly one exception: a top-level navigation using a safe method — precisely what a clicked link produces. That carve-out exists so ordinary links, bookmarks, and shares keep working across sites; it also means a clicked GET link still carries the cookie.

This is exactly what would happen to a forged POST — which is why "CSRF is on" feels like it should cover this too. But CsrfFilter's token requirement only applies to unsafe methods. A GET is never asked for a token in the first place, so there's no missing token here for it to catch.

Right — two separate, correctly configured defenses, both irrelevant here because the vulnerable action is wearing a GET's clothing. Neither SameSite nor CSRF tokens were ever designed to stop a GET from doing something a GET is promised not to do.

Where you've seen this before

"GET must be safe" is a promise the whole web relies on, and CSRF is only one of the things that breaks when an endpoint doesn't keep it. A search-engine crawler, or a browser prefetching links it predicts you'll click, treats "it's a GET" as "safe to follow automatically" — sites that once exposed a "delete this page" or "log out" action as a plain GET link have had a well-behaved bot walk every link on the site and trigger every one of them, no attacker required. Browsers, proxies, and CDNs lean on the identical contract to cache and retry GET requests, so a mutating GET can get silently re-executed by infrastructure that's behaving exactly as designed. Even OAuth2's state parameter is this same shape of protection aimed at a different door: without it, an attacker can start their own login, capture the resulting code, and trick a victim's browser into finishing your callback with the attacker's code — CSRF guarding your login flow instead of your data.

Questions from the back row

Why doesn't Spring just require a CSRF token on every request, GET included, and remove the exception entirely?

Because that would break ordinary browsing. A clicked link, a bookmark, an <img> tag pointing at your own site, a search engine indexing your pages — all of those are GET requests with no mechanism to attach a custom header, and the entire read side of the web depends on GET working without extra ceremony. The fix was never "protect GET too" — it's "never let GET do something that needs protecting" in the first place.

Does SameSite=Lax help here at all, since this page already recommends it?

Only partly, and the edge is sharp: Lax withholds the cookie on cross-site subrequests — an <img>, an iframe, a fetch() call — but deliberately still sends it on a top-level navigation using a safe method, because that's exactly what happens when someone clicks an ordinary link. A forged image tag gets blocked by Lax. A forged link the victim actually clicks does not, and a GET-based mutation is exposed to precisely that second case. Strict closes the gap but breaks normal links into your app from anywhere else — which is why real apps combine Lax, CSRF tokens, and "never mutate on GET," rather than picking just one.

How would code review even catch this — the endpoint looks exactly like every other read?

It doesn't look like a read — that's the actual failure. Review the verb, not the security annotations near it: any @GetMapping (or anything reachable by a bare URL) that writes to a database, sends an email, or changes account state is the bug, regardless of how perfectly CSRF, SameSite, and authentication are configured everywhere else. The fix is never more security configuration — it's moving the action off a method that was never supposed to cover it.

1. Why CSRF works (when it works)

victim logged into your-app.com  (has a session cookie)
victim visits evil.com  →  it auto-submits a form to your-app.com
browser auto-attaches the cookie  →  your app sees a "valid" request 💥

The attacker never sees the cookie — they just rely on the browser sending it. So the question is always: does the auth credential ride along automatically? Cookie = yes (forgeable). Custom header = no (safe).

2. Interactive: is this app vulnerable?

How does the app authenticate requests?

Watch what credential the forged cross-site request carries — that's the whole verdict.

3. Why this app disables CSRF (correctly)

// SecurityConfig — stateless + JWT in a header ⇒ CSRF off is correct
http.csrf(AbstractHttpConfigurer::disable)
    .sessionManagement(s -> s.sessionCreationPolicy(STATELESS));

No session cookie carries auth here — the SPA reads the JWT and explicitly sets Authorization: Bearer …. A forged cross-site request can't set that header (and can't read your token to copy it), so there's nothing to forge. Disabling CSRF on a stateless JWT API is right, not a shortcut.

4. When you DO need it: cookies / BFF

The moment auth rides on a cookie — a classic server session, or a BFF using an httpOnly session cookie — CSRF is back on the table. Enable it:

// BFF / cookie-session mode — double-submit cookie token
http.csrf(c -> c.csrfTokenRepository(
        CookieCsrfTokenRepository.withHttpOnlyFalse()));
// + set the session cookie SameSite=Lax/Strict
  • Synchronizer token — server stores a per-session token; the form/request must echo it. Stateful, strongest.
  • Double-submit cookie — token in a cookie + the same value in a header; the server checks they match. Stateless-friendly (SPA reads the cookie, sends the header).
  • SameSite cookies are the first line — the browser won't send the cookie cross-site (Strict) or on cross-site sub-requests (Lax).
  • Also check Origin/Referer on state-changing requests.

5. One-sentence recap

🛡️ CSRF abuses credentials the browser sends automatically (cookies), so a stateless API with a JWT in the Authorization header is not vulnerable — which is why this app correctly csrf().disable()s — but the instant you authenticate with a cookie (classic session or a BFF), turn CSRF back on with a synchronizer or double-submit token plus SameSite cookies (and Origin checks); and don't confuse CSRF with CORS — different attacks, different defenses.
