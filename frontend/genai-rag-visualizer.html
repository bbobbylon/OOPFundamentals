RAG — Retrieval-Augmented Generation

How to make an LLM answer questions grounded in YOUR documents instead of guessing from stale training data — embed, retrieve, augment, generate.

📚 What is RAG — and why can't the model just "know" this already?

An LLM's knowledge is frozen at training time and lives entirely inside its weights — it has never seen your company's PTO policy, this week's ticket queue, or a document uploaded five minutes ago. Retrieval-Augmented Generation (RAG) fixes this without retraining anything: at request time, you take the user's question, turn it into an embedding, use that embedding to search a vector database for the most relevant chunks of your own documents, and paste those chunks into the prompt as context before the LLM ever generates a word. The model isn't smarter — it's just been handed the right page of the textbook right before the exam. This is why RAG is the default architecture for internal knowledge bots, customer-support assistants, and "chat with your docs" products: it's cheaper than fine-tuning, it updates the instant a source document changes, and — critically — a grounded answer can be traced back to a specific source chunk, which a purely generated answer never can. The parts worth mastering are the same four this page walks through: how the pipeline actually moves data end to end, why it beats raw generation on hallucination and staleness, how chunk size and hybrid search change retrieval quality, and the one mistake that turns a helpful RAG bot into a data-leak machine — forgetting that retrieval is still a data access, and every data access needs an authorization check.

  • Embed → Retrieve → Augment → Generate — the four-stage pipeline, run fresh on every request.
  • No retraining — swap or update source documents and the next query sees the change immediately.
  • Grounding reduces (not eliminates) hallucination — and gives you a citation trail generation alone can't.
  • Retrieval is a data access — skip the permission check and RAG becomes a very articulate way to leak other people's data.

Chunking & retrieval quality

# Too coarse: whole 40-page doc as 1 chunk chunk_size = 40_000 # tokens # → embedding averages the whole doc, # the one relevant paragraph gets diluted # Too fine: every sentence its own chunk chunk_size = 20 # tokens # → loses surrounding context, e.g. # "employees with >2 years" separated # from "get 15 days" # Sweet spot: paragraph-ish, with overlap chunk_size = 400 # tokens chunk_overlap = 50 # tokens # → chunk IS the relevant unit of meaning # See also: genai-embeddings-vector-db-visualizer.html

CIAM angle — retrieval is a data access: A naive RAG bot embeds a query and searches the ENTIRE vector index with no filter — which means it will happily retrieve and quote chunks from documents the asking user has no right to see. The fix is the same one you'd apply to any other read path: scope the query with a tenant_id/owner_id metadata filter (or a separate per-tenant index) BEFORE the search runs, and treat retrieved chunks as untrusted, permission-checked data — not a shortcut around the authorization layer. "The LLM only said what was in the context" is not a defense if the context itself was fetched without checking who's asking.

1. The RAG Pipeline: Embed, Retrieve, Augment, Generate

RAG is not a model — it's an architecture wrapped around a model. Every request runs the same four stages before the LLM generates a single token.

Query
user's raw question
Embed
text → vector (same model as indexing)
Retrieve
top-k nearest chunks by similarity
Augment
chunks + query → one prompt
Generate
LLM answers from the prompt
# Minimal RAG pipeline
def answer_question(user_query, current_user):
    # 1. Embed — same embedding model used when indexing docs
    q_vec = embed_model.encode(user_query)

    # 2. Retrieve — nearest neighbors in the vector store
    chunks = vector_db.search(
        vector=q_vec, top_k=4,
        filter={"tenant_id": current_user.tenant_id}
    )

    # 3. Augment — build one prompt: instructions + context + question
    context = "\n---\n".join(c.text for c in chunks)
    prompt = f"""Answer using ONLY the context below.
If the answer isn't in the context, say you don't know.

Context:
{context}

Question: {user_query}"""

    # 4. Generate — grounded in retrieved context, not raw parametric memory
    return llm.generate(prompt, sources=[c.doc_id for c in chunks])
The embedding model used at query time MUST be the same one used to embed the documents when they were indexed — mixing embedding models produces vectors that live in different coordinate spaces, so "similar" comparisons become meaningless. See genai-embeddings-vector-db-visualizer.html for how the vector store itself works.

2. Why RAG Exists: Knowledge Cutoff & Hallucination

Two problems that pure generation can't solve on its own, because both come from the same root cause: the model only knows what was baked into its weights at training time.

Knowledge cutoffThe model was trained on data up to some date and has zero awareness of anything after — a new pricing page, this morning's incident, or a policy that changed last week. RAG re-supplies current facts at request time without retraining.
HallucinationWhen the model doesn't know an answer, it doesn't reliably say "I don't know" — it produces a fluent, confident-sounding guess. Without a grounding source, a wrong answer and a right one are equally fluent, so users can't tell them apart.
Grounding (fix)Retrieved chunks give the model something concrete to paraphrase and cite instead of inventing facts from scratch — and give the application a source to show the user ("according to pto-policy.pdf §3.2").
Still imperfectRAG reduces hallucination, it doesn't eliminate it — a model can still misread retrieved context, blend it with parametric memory, or answer confidently when retrieval returned nothing relevant. Grounded ≠ guaranteed correct.
# No retrieval — the model fills the gap with a plausible guess
llm.generate("What's our current parental-leave policy?")
# "Most companies offer around 12 weeks..." — generic, not OUR policy, no source

# With retrieval — the model paraphrases what was actually found
chunks = vector_db.search(embed("parental leave policy"), top_k=3)
llm.generate(prompt_with_context(chunks))
# "16 weeks paid, per parental-leave-policy.pdf §1" — specific, sourced, current
A RAG bot that retrieves NOTHING relevant (empty or off-topic results) can still hallucinate a confident answer if the prompt doesn't explicitly instruct it to refuse — always include a "if the answer isn't in the context, say you don't know" instruction, and check that at least one chunk cleared a similarity threshold before generating.

3. Chunking, Hybrid Search, Re-ranking — and the Authorization Gap

Retrieval quality is won or lost before generation ever happens: how you split documents into chunks, how you search, and — the part teams skip — who's allowed to see what you retrieve.

too bigwhole doc/page → averaged embedding, diluted relevance
too smallsingle sentence → loses the surrounding context it needs
~300-500 tokparagraph-sized, with ~10-15% overlap between chunks
# Chunking with overlap (so an answer split across a boundary isn't lost)
def chunk_document(text, size=400, overlap=50):
    chunks, start = [], 0
    while start < len(text):
        chunks.append(text[start:start+size])
        start += size - overlap  # step forward, but re-include the tail
    return chunks

# Hybrid search: combine keyword (BM25) + vector similarity, then re-rank
keyword_hits = bm25_index.search(user_query, top_k=20)
vector_hits  = vector_db.search(embed(user_query), top_k=20)
candidates   = merge_dedupe(keyword_hits, vector_hits)
top_chunks   = reranker.rerank(user_query, candidates, top_k=4)
# Vector search alone misses exact terms (IDs, error codes); BM25 alone misses paraphrase.
# A re-ranker (cross-encoder) then scores query+chunk pairs directly — slower, but far more precise.

# The authorization gap — retrieval MUST be scoped, same as any other read
def search_docs(query_vec, current_user):
    return vector_db.search(
        vector=query_vec, top_k=4,
        filter={"tenant_id": current_user.tenant_id,
                "allowed_roles": {"$in": current_user.roles}}
    )  # without this filter, ANY indexed chunk is fair game for ANY asker
The most common production RAG bug isn't a hallucination — it's a permission bug wearing a hallucination costume. A vector index built by dumping every internal doc into one collection with no tenant/role metadata will retrieve confidential chunks for anyone whose query happens to be semantically close to them. Fix it the same way you'd fix an unscoped SQL query: filter at the data layer (metadata filter or separate per-tenant index), not by hoping the prompt's phrasing keeps the model from repeating what it was handed.
