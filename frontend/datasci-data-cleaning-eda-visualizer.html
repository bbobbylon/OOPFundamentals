Data Cleaning & EDA

Missing data, outliers, duplicates, type coercion, and the first-look exploratory pass — the unglamorous 80% of a real data science project that determines whether any model built afterward can be trusted.

🧹 Why data cleaning is most of the job, not a footnote before it

"Garbage in, garbage out" isn't a cliché in data science — it's the single biggest determinant of whether a model works. Real datasets arrive with missing values, outliers that might be errors or might be the whole point, near-duplicate records that exact matching misses, and columns silently mis-typed by whatever exported them. Exploratory Data Analysis (EDA) is the disciplined first pass — .info(), .describe(), .isna().sum(), .corr() — that builds intuition and catches these problems before a single model is trained, not after a model quietly learns the wrong thing from bad data. Most practitioners report spending 60-80% of a real project here, not in the notebook cell that calls .fit().

  • Missing data isn't one problem — MCAR/MAR/MNAR determine whether dropping or imputing introduces bias.
  • An outlier isn't automatically wrong — it might be the fraud case you're trying to catch.
  • Exact-match dedup misses near-duplicates — "NY" / "New York" / "ny" need normalization first.
  • .info() + .describe() before anything else — the fastest way to catch bad dtypes and nulls.

Where this shows up beyond ML: the exact same discipline applies to identity/auth data — deduplicating near-duplicate user accounts ("Bob O." vs "Bobby Oliver" vs a stray whitespace typo), imputing a missing signup timestamp before it feeds an analytics pipeline, or flagging an outlier login-rate as a possible credential-stuffing attack rather than deleting it as "bad data." Data cleaning is a CIAM discipline too, not just an ML one.

1. Missing Data — Detection & Strategy

Not all missingness is equal. Why a value is missing determines whether dropping or imputing it introduces bias into everything downstream.

MCARMissing Completely At Random — safe to drop or impute, no systematic biassensor glitch drops random rows
MARMissing At Random — missingness depends on OTHER observed columnsolder survey forms lack a field added later
MNARMissing Not At Random — missingness depends on the value itself; naive imputation biases the resulthigh earners disproportionately skip "income"
# Detect
df.isna().sum()             # per-column missing count
df.isna().mean() * 100       # % missing per column

# Strategies, in order of how much they trust the data
df.dropna()                        # only if missingness is small & MCAR
df['age'].fillna(df['age'].median())   # robust to skew — prefer over mean
df['sensor'].ffill()               # time series: carry the last known value
Mean imputation is fragile: one huge outlier drags the mean far from where most values actually sit. Median imputation ignores extreme values entirely — it's the safer default unless you've already confirmed the column is roughly symmetric.

2. Outlier Detection — IQR & Z-Score

The IQR method draws the same fence a box plot's whiskers draw. A flagged value is a question, not an automatic deletion.

Q1
25th percentile
Q3
75th percentile
IQR
Q3 − Q1
Lower fence
Q1 − 1.5×IQR
Upper fence
Q3 + 1.5×IQR
import pandas as pd
q1 = df['amount'].quantile(0.25)
q3 = df['amount'].quantile(0.75)
iqr = q3 - q1
lower, upper = q1 - 1.5*iqr, q3 + 1.5*iqr
outliers = df[(df['amount'] < lower) | (df['amount'] > upper)]

# z-score alternative: values beyond ±3 std deviations
z = (df['amount'] - df['amount'].mean()) / df['amount'].std()
outliers_z = df[z.abs() > 3]
In fraud detection or rare-disease screening, the outliers ARE the target — "clean" there means flag and keep, not delete. Deleting them would delete the exact signal the model needs to learn.

3. Duplicates, Type Coercion & the First-Look EDA Pass

Exact-match dedup only catches literal repeats. Type mismatches from a CSV import fail silently until arithmetic on them breaks.

# Exact duplicates
df.duplicated().sum()
df = df.drop_duplicates()

# Near-duplicates need normalization FIRST
df['city'] = df['city'].str.strip().str.lower()
df['city'] = df['city'].replace({'ny': 'new york', 'nyc': 'new york'})

# Type coercion — CSV often reads numbers/dates as strings
df['price'] = pd.to_numeric(df['price'], errors='coerce')  # bad parses → NaN, not a crash
df['signup_date'] = pd.to_datetime(df['signup_date'])

# The first-look pass, in order:
df.info()                    # dtypes + non-null counts — spot bad types & nulls at a glance
df.describe()                # count/mean/std/min/quartiles/max — spot implausible values
df.corr(numeric_only=True)   # pairwise correlation — first pass at what predicts the target
errors='coerce' on pd.to_numeric/pd.to_datetime silently turns unparseable values into NaN instead of crashing — convenient, but it means you must re-run .isna().sum() AFTER coercion, since coercion itself can create new missing data.
