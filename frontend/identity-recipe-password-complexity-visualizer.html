Recipe — Password Complexity, Strength & Enforcement

How to actually validate a password: a live rule checklist and strength meter for UX, a breach check against known-leaked passwords, and — the part that matters — server-side enforcement plus a slow hash (bcrypt/argon2). Modern guidance: length beats silly symbol rules.

🔐 What makes a password strong — and where do you enforce it?

Two ideas: complexity rules (what characters/length you require) and strength (how hard the password is to actually guess) — they are not the same thing. Classic composition rules ("≥8 chars, an upper, a lower, a digit, a symbol") are easy to check but produce weak, predictable passwords like Password1!. Modern guidance (NIST SP 800-63B) flips the emphasis: require a generous minimum length (≥8, ideally ≥12), allow all characters including spaces, screen against known-breached passwords, and drop forced periodic rotation and arbitrary composition rules — because length and unpredictability, not symbol soup, are what defeat guessing. Strength is best estimated with an entropy/pattern model (like zxcvbn) that knows P@ssw0rd is weak despite "passing" composition. On the client you give instant feedback: a rule checklist that ticks off as the user types and a strength meter (weak→strong). You can even check the password against the HaveIBeenPwned breach corpus using k-anonymity — hash the password with SHA-1, send only the first 5 hex chars of the hash, and compare the returned suffixes locally, so the password (and even its full hash) never leaves the browser. But all of that is UX. The authoritative gate is the server: it must re-validate the policy (never trust the client), reject breached passwords, and store only a slow salted hash — bcrypt (cost ≥12) or argon2 — never the plaintext, never a fast hash like MD5/SHA-256. In a CIAM setup the IdP (Entra/Ping) typically owns and enforces this policy.

  • Length > composition — NIST 800-63B: long minimum, allow all chars, screen breaches, no forced rotation.
  • Strength ≠ rules — P@ssw0rd passes composition but a zxcvbn-style model rates it weak.
  • Breach check — HaveIBeenPwned via k-anonymity: send a 5-char SHA-1 prefix, compare suffixes locally.
  • Server is the gate — re-validate policy server-side; store a slow salted hash (bcrypt cost ≥12 / argon2), never plaintext.

The problem

Same status code. Same JSON. Two hundred and fifty milliseconds apart.

You did the enumeration fix correctly — and the login endpoint still tells an attacker who banks with you

You already know not to say "no account with that email." So both failures return the exact same thing: 401, body {"error":"Invalid credentials"}, byte for byte. A reviewer reading the response cannot tell the cases apart, and neither can a user.

Now time it. When the email does exist, your code loads the hash and calls BCryptPasswordEncoder(12).matches(...) — which is deliberately expensive, around a quarter of a second, because that slowness is what makes an offline crack of your database impractical. When the email does not exist, there is no hash to compare against, so the method returns in about two milliseconds. Same words, a hundred times the work. An attacker with a list of a million emails does not need to read your response at all; they need a clock.

status: 401 both ✓ body: identical ✓ known user: ~250 ms ⚠ unknown user: ~2 ms ⚠ a 100x tell, in one request ⚠

The property that makes your hashing strong is the property that makes this leak loud. Those are the same design decision seen from two sides.

An identical message is not an identical answer. If two outcomes cost different amounts of work, the duration is a third channel you never meant to open. This is why "don't reveal whether the account exists" is an incomplete instruction — it describes the response body and stops there. The real requirement is that an observer cannot distinguish the two cases by any means available to them, and timing is always available.

The mechanism

Six steps, and the leak is in the one you skipped.

  1. Request arrives: POST /login with an email and a password guessno secrets yet
  2. Look the user up. A miss here is the fork — and a database miss is fast, often sub-millisecond on an indexed columnthe branch that costs nothing
  3. User found → load the stored hash and run matches(). Cost 12 means ~250 ms of deliberate work before you know anythingthe branch that costs everything
  4. Both branches converge on the same 401 and the same body. On paper, indistinguishablewhere most reviews stop
  5. The attacker measures wall-clock time per request. The two branches differ by ~100x — far outside any plausible network jitterthe tell
  6. The fix restores the symmetry: on a miss, hash against a dummy anyway, so step 2's cheap branch becomes just as expensive as step 3'spay the cost you do not need

Notice the shape of the fix, because it generalises: you are not hiding information by removing work, you are hiding it by adding work to the cheap path until both cost the same. That is the same reason a password comparison uses a constant-time equals rather than String.equals, which returns early on the first differing character and leaks how much of a token you guessed correctly. Same family of bug, two different layers.

Add the fourth row to your test plan too — "account locked" is the one teams forget, and it is often implemented as an early return before the hash comparison, which puts the timing leak straight back in through a different door. The rule to hold onto: an observer should be able to distinguish exactly one outcome, success, and nothing else.

Your login endpoint returns a byte-identical 401 {"error":"Invalid credentials"} for both a wrong password and an unknown email. Password verification uses BCryptPasswordEncoder at strength 12 (~250 ms), and an unknown email short-circuits before any hashing. What can an attacker learn?

Identical bodies close one channel and leave another wide open. The guidance "never reveal whether the account exists" is usually written as advice about error messages, so it is easy to implement it exactly as written and still be enumerable — what an attacker observes is the whole response, and duration is part of that whether you intended it or not.

Exactly. Two milliseconds versus two hundred and fifty is not a subtle statistical signal; it is legible in a single request. And the irony is worth keeping: the gap exists because you chose a strong work factor, so weakening bcrypt would shrink the leak and weaken the system. The fix goes the other way — hash the submitted password against a dummy hash on the not-found path so both branches pay the same cost.

This would be a fair objection to a timing leak of a few microseconds — those genuinely do need thousands of samples and careful statistics. But a deliberate work factor puts the difference in the hundreds of milliseconds, which is one to two orders of magnitude above ordinary jitter. Network noise adds variance around both means; it does not move a 2 ms mean anywhere near a 250 ms one.

Where you have seen this before

Anywhere a shortcut exists, the shortcut is the signal.

MessageDigest.isEqual, and why String.equals is banned for tokens

Comparing a submitted HMAC or reset token with equals returns on the first differing byte, so a correct first character measurably takes longer than a wrong one — enough to reconstruct a token byte by byte. The constant-time comparison exists for precisely this reason, and it is the same fix: refuse the shortcut, always do the full work.

early return = a progress bar for the attacker

Password reset — the same leak, on the endpoint everyone forgets

"If an account exists, we have sent an email" is the right message, and then the handler sends the mail synchronously for real accounts and returns immediately for the rest. Same tell, lower-traffic endpoint, and usually no rate limit. Queue the send, or fake the delay.

every identity endpoint, not just login

Why enumeration matters even though the password still holds

Knowing an address has an account here is not access — it is targeting. It turns credential stuffing from a broad sweep into a precise list, makes phishing credible ("we noticed a login on your account"), and on some services the mere existence of an account is itself sensitive. That is why the mitigation is worth a quarter-second of wasted CPU on every failed login.

existence is information
The whole page on a napkin: composition rules produce Password1!, so follow NIST — long minimum, every character allowed, screen against breach lists, and no forced rotation; measure real strength with a pattern model, and re-enforce everything server-side before BCryptPasswordEncoder(12) persists it. And the extra sentence most implementations miss: identical error messages are only half of not leaking who has an account — the two paths have to take the same amount of time as well.

1. The rules — a live checklist

function checkRules(pw, email) {
  return {
    length: pw.length >= 12, // length is the big lever
    letter: /[a-z]/i.test(pw),
    number: /[0-9]/.test(pw),
    notUser: pw.length > 0 && !pw.toLowerCase().includes(email.split('@')[0]), // not your own name
  };
}
// render each rule as ✓ / ✗ so the user sees exactly what's missing
Show the rules, don't just reject. A live checklist that ticks each requirement as the user types is far better UX than a single "password too weak" error after submit. Modern policy leans on length (≥12 here) and a couple of light requirements rather than a wall of composition rules — and crucially a contextual check that the password doesn't contain the user's own email/username. Keep the rule set short and meaningful; symbol-soup mandates mostly push users toward predictable substitutions.

2. Strength is not the same as passing the rules

// composition rules say "valid", but guessability says "weak"
estimate("P@ssw0rd") // → score 1 (weak): a top-1000 password + leet substitution
estimate("correct horse battery staple") // → score 4 (strong): long, high entropy

// entropy ≈ log2(poolSize ^ length); LENGTH dominates.
// real estimators (zxcvbn) also penalize dictionary words, dates, keyboard runs.
Measure guessability, not character classes. P@ssw0rd satisfies every composition rule yet is one of the first things an attacker tries — common base word + predictable leet swaps. A pattern-aware estimator like zxcvbn scores it ~1/4. Meanwhile a long passphrase scores 4/4 with no symbols at all, because entropy grows with length far faster than with adding one symbol. Drive your strength meter from an estimator, and treat low scores as a warning even when the rules technically pass.

3. Breach check, then enforce on the server

// HaveIBeenPwned k-anonymity: the password never leaves the browser
const hash = sha1(pw).toUpperCase(); // e.g. "21BD1...A0F3"
const body = await fetch(`https://api.pwnedpasswords.com/range/${hash.slice(0,5)}`)
  .then(r => r.text()); // send only the 5-char prefix
const pwned = body.includes(hash.slice(5)); // match the suffix locally

// ── SERVER (the real gate) — Spring ──
if (!passwordPolicy.isValid(pw) || breachList.contains(pw))
  throw new ApiException("Choose a stronger password");
user.setPassword(passwordEncoder.encode(pw)); // BCrypt(strength 12) — store the HASH
The client meter is courtesy; the server is the law. The breach check uses k-anonymity — only the first 5 hex chars of the SHA-1 hash go over the wire, the API returns all matching suffixes, and you compare locally, so neither the password nor its full hash is ever exposed. But none of the client checks are trusted: the server must re-validate the policy and breach screen, then store only a slow salted hash via BCryptPasswordEncoder (cost ≥12) or argon2 — never plaintext, never a fast hash. bcrypt's deliberate slowness is what makes a stolen hash dump expensive to crack.
