Recipe — Password Complexity, Strength & Enforcement

How to actually validate a password: a live rule checklist and strength meter for UX, a breach check against known-leaked passwords, and — the part that matters — server-side enforcement plus a slow hash (bcrypt/argon2). Modern guidance: length beats silly symbol rules.

🔐 What makes a password strong — and where do you enforce it?

Two ideas: complexity rules (what characters/length you require) and strength (how hard the password is to actually guess) — they are not the same thing. Classic composition rules ("≥8 chars, an upper, a lower, a digit, a symbol") are easy to check but produce weak, predictable passwords like Password1!. Modern guidance (NIST SP 800-63B) flips the emphasis: require a generous minimum length (≥8, ideally ≥12), allow all characters including spaces, screen against known-breached passwords, and drop forced periodic rotation and arbitrary composition rules — because length and unpredictability, not symbol soup, are what defeat guessing. Strength is best estimated with an entropy/pattern model (like zxcvbn) that knows P@ssw0rd is weak despite "passing" composition. On the client you give instant feedback: a rule checklist that ticks off as the user types and a strength meter (weak→strong). You can even check the password against the HaveIBeenPwned breach corpus using k-anonymity — hash the password with SHA-1, send only the first 5 hex chars of the hash, and compare the returned suffixes locally, so the password (and even its full hash) never leaves the browser. But all of that is UX. The authoritative gate is the server: it must re-validate the policy (never trust the client), reject breached passwords, and store only a slow salted hash — bcrypt (cost ≥12) or argon2 — never the plaintext, never a fast hash like MD5/SHA-256. In a CIAM setup the IdP (Entra/Ping) typically owns and enforces this policy.

  • Length > composition — NIST 800-63B: long minimum, allow all chars, screen breaches, no forced rotation.
  • Strength ≠ rules — P@ssw0rd passes composition but a zxcvbn-style model rates it weak.
  • Breach check — HaveIBeenPwned via k-anonymity: send a 5-char SHA-1 prefix, compare suffixes locally.
  • Server is the gate — re-validate policy server-side; store a slow salted hash (bcrypt cost ≥12 / argon2), never plaintext.

1. The rules — a live checklist

function checkRules(pw, email) {
  return {
    length: pw.length >= 12, // length is the big lever
    letter: /[a-z]/i.test(pw),
    number: /[0-9]/.test(pw),
    notUser: pw.length > 0 && !pw.toLowerCase().includes(email.split('@')[0]), // not your own name
  };
}
// render each rule as ✓ / ✗ so the user sees exactly what's missing
Show the rules, don't just reject. A live checklist that ticks each requirement as the user types is far better UX than a single "password too weak" error after submit. Modern policy leans on length (≥12 here) and a couple of light requirements rather than a wall of composition rules — and crucially a contextual check that the password doesn't contain the user's own email/username. Keep the rule set short and meaningful; symbol-soup mandates mostly push users toward predictable substitutions.

2. Strength is not the same as passing the rules

// composition rules say "valid", but guessability says "weak"
estimate("P@ssw0rd") // → score 1 (weak): a top-1000 password + leet substitution
estimate("correct horse battery staple") // → score 4 (strong): long, high entropy

// entropy ≈ log2(poolSize ^ length); LENGTH dominates.
// real estimators (zxcvbn) also penalize dictionary words, dates, keyboard runs.
Measure guessability, not character classes. P@ssw0rd satisfies every composition rule yet is one of the first things an attacker tries — common base word + predictable leet swaps. A pattern-aware estimator like zxcvbn scores it ~1/4. Meanwhile a long passphrase scores 4/4 with no symbols at all, because entropy grows with length far faster than with adding one symbol. Drive your strength meter from an estimator, and treat low scores as a warning even when the rules technically pass.

3. Breach check, then enforce on the server

// HaveIBeenPwned k-anonymity: the password never leaves the browser
const hash = sha1(pw).toUpperCase(); // e.g. "21BD1...A0F3"
const body = await fetch(`https://api.pwnedpasswords.com/range/${hash.slice(0,5)}`)
  .then(r => r.text()); // send only the 5-char prefix
const pwned = body.includes(hash.slice(5)); // match the suffix locally

// ── SERVER (the real gate) — Spring ──
if (!passwordPolicy.isValid(pw) || breachList.contains(pw))
  throw new ApiException("Choose a stronger password");
user.setPassword(passwordEncoder.encode(pw)); // BCrypt(strength 12) — store the HASH
The client meter is courtesy; the server is the law. The breach check uses k-anonymity — only the first 5 hex chars of the SHA-1 hash go over the wire, the API returns all matching suffixes, and you compare locally, so neither the password nor its full hash is ever exposed. But none of the client checks are trusted: the server must re-validate the policy and breach screen, then store only a slow salted hash via BCryptPasswordEncoder (cost ≥12) or argon2 — never plaintext, never a fast hash. bcrypt's deliberate slowness is what makes a stolen hash dump expensive to crack.
