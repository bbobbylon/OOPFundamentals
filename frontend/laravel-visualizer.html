Laravel — Lifecycle, Eloquent & Middleware

PHP's most popular framework and a genuine joy for rapid web apps: a DI container, an expressive Active-Record ORM (Eloquent), a middleware pipeline, routing, validation, and the Artisan CLI — convention-driven, batteries included.

🔴 What is Laravel — and why do teams ship so fast with it?

Laravel is PHP's flagship full-stack framework. Each request enters through public/index.php, boots the framework, and is passed to the HTTP kernel, which runs it through a middleware pipeline (≈ a servlet filter chain) to the router, which dispatches to a controller resolved from the service container (Laravel has full dependency injection). The controller talks to the database through Eloquent — an expressive Active Record ORM where models are the query interface (User::where(...)->get(), $user->save()) and relationships are first-class. Input is checked with validation (inline rules or a FormRequest), responses are return response()->json(...) or a Blade template, and the Artisan CLI scaffolds models, runs migrations, and clears caches. The reason teams move fast: strong conventions, a huge first-party ecosystem (auth, queues, mail, Sanctum/Passport for tokens), and an ergonomic API that makes the common path short. The trade compared to Spring: Active Record couples models to persistence, where Spring/JPA separates entities from repositories.

  • Lifecycle — index.php → HTTP kernel → middleware → router → controller → response.
  • Eloquent — Active-Record ORM: the model is the query API; relationships are built in.
  • Service container — real DI; controllers and dependencies are auto-resolved.
  • Artisan + conventions — scaffolding, migrations, queues, auth — batteries included.

Route → controller → Eloquent

// routes/api.php Route::middleware("auth:sanctum") ->get("/users/{user}", [UserController::class, "show"]); // app/Http/Controllers/UserController.php public function show(User $user) { // route-model binding return response()->json($user->load("orders")); } // app/Models/User.php — Eloquent model class User extends Model { public function orders() { return $this->hasMany(Order::class); } }

Spring Boot comparison

The middleware pipeline ≈ the Servlet/Security filter chain. Routes → controllers ≈ @RequestMapping → @RestController; route-model binding (show(User $user)) auto-loads the entity by id — Spring needs an explicit repository call. Eloquent is Active Record (model = persistence), where Spring Data/JPA uses the Data Mapper pattern (entity + repository). ->with("orders") ≈ JOIN FETCH and the N+1 trap is identical. $request->validate() ≈ @Valid + a DTO. The service container ≈ the Spring bean container. Artisan ≈ Spring Boot CLI + Flyway.

CIAM with Laravel: Laravel Sanctum/Passport handle token auth; for a Ping/Entra bearer token you add a middleware that verifies the RS256 JWT against the JWKS and sets the authenticated user, then gate routes with ->middleware("auth") and policies (≈ @PreAuthorize) for role checks. $request->validate() rejects bad input with a 422 before the controller runs. Eloquent\'s relationships make a consent/user model expressive — $user->consents()->where("granted", true)->get() — and ->with() avoids N+1 across scopes. The shared-nothing model means each request re-verifies the token independently, which suits stateless JWT auth.

The problem

You set a value on an Eloquent model, hand that same model to a queued job, and the job runs with a version of it that never heard about the value at all.

Your queued job doesn't know about the property you just set

Say a controller saves a user, then sets one more thing in memory before handing the model to a job: $user->save(); $user->referral_bonus = 10; ProcessSignup::dispatch($user);. referral_bonus isn't a column — it's a value you want the job to use while sending a welcome email. It looks completely safe: the job type-hints User $user in its constructor, and Laravel's queue system is built specifically to carry Eloquent models across the wire.

Here's what actually happens. Every queued job that holds an Eloquent model uses Laravel's SerializesModels trait, and that trait does not serialize the object you handed it. It serializes exactly two things: the model's class name and its primary key. When a queue worker — a separate PHP process, quite possibly on a separate machine, picked up seconds or minutes later — unserializes the job, it does not restore your in-memory object. It runs User::find(42) against the database, right then, and builds a brand-new model from whatever is actually in the row. referral_bonus was never a column, so it was never in that row, so the fresh model simply doesn't have it. Not an error — just gone.

job dispatched with the model ✓ property spelled correctly ✓ queue driver delivered the job ✓ the value was never saved to a column ⚠

The job didn't lose your data. It never had it — all it was ever given was your user's id.

Persist it, or pass it separately — don't bolt it onto the model
Save the value first if it truly belongs on the model ↓ the worker's fresh User::find($id) then includes it, because it's really a column value now, not a memory-only guess Or pass it as its own constructor argument, not a property tacked onto the model ↓ ProcessSignup::dispatch($user, $bonus) serializes $bonus by its actual value — a plain int survives the trip on its own, independent of the model And re-load any relationship the job actually needs inside handle() ↓ a ->load('orders') you did before dispatch doesn't ride along either — the worker's re-fetch is a bare model, so eager-load again inside the job if it needs the relation
The one-sentence rule. A queued Eloquent model is a promise to re-fetch by id later, not a snapshot of the object you dispatched — anything that isn't already sitting in a database column by the time the worker runs simply does not make the trip.
Queuing a model is like mailing someone your library card instead of the book. They don't get your dog-eared page or the note you scribbled in the margin — just the card. When they get to the library, they check out a fresh copy.
You

I set $user->referral_bonus = 10 right before I dispatched the job — why does the job see null?

SerializesModels

I never touched referral_bonus. What I stored in the queue payload was "App\Models\User" and the number 42. That's the entire package.

You

But the job ran on the same request, practically the same millisecond. Nothing could have changed in the database in that time.

Queue worker

I don't know that, and I don't assume it. I'm a separate PHP process — maybe even a separate server. All you gave me was an id, so I ran the query myself. Whatever wasn't saved by the time I ran it never existed, as far as I'm concerned.

The mechanism

Follow $user from the controller, through the queue, to the worker — and watch exactly which parts of it survive the trip.

  1. Controller sets $user->referral_bonus = 10 in memory, then calls ProcessSignup::dispatch($user)dispatch
  2. The job's constructor stores $user as a public property; SerializesModels intercepts how that property gets serializedintercept
  3. Instead of the object graph, it records only get_class($user) and $user->getKey() — 42 — into the payloadid only
  4. That small payload is pushed onto the queue driver (database, Redis, SQS). referral_bonus was never part of itenqueued
  5. A queue worker process — started later, maybe on a different box — pops the payload and unserializes the jobdequeue
  6. Unserializing runs User::find(42) fresh against the database to rebuild $this->user — a real query, not a memory restorerefetched

Step 6 is where the assumption quietly breaks. "Unserialize" sounds like restoring exactly what you had — but for a queued Eloquent model it means running a brand-new SELECT. Whatever was true about $user only inside the controller's memory in step 1, and never reached a save() call, simply isn't part of that new row. There was nowhere for it to survive.

Nothing in this path raises an error — not PHP, not Laravel. There's no exception because there's no missing column being demanded; the slot just resolves to whatever the fresh row actually holds, which for a value that was never saved is nothing. Silence, not failure, is exactly what makes this one easy to ship.

A controller does $user->save(), then sets $user->last_login_ip = $request->ip() (never a real column, never saved), then calls ProcessLogin::dispatch($user). Inside the queued job's handle(), what does $this->user->last_login_ip contain?

The job never receives the same PHP object. SerializesModels only records the model's class and primary key, not any in-memory state, so anything not already saved never crosses the queue boundary.

Right. When the worker unserializes the job, it rebuilds $user by running a fresh User::find($id) query. Since last_login_ip was set only in memory and never saved, the fresh row simply doesn't have it — no error, just an absent value.

Serialization doesn't fail here — it succeeds completely, just not the way you'd expect: it silently keeps only the model's identity and drops everything else. That quiet success, not a thrown exception, is exactly what lets this ship unnoticed.

Where you have seen this before

A snapshot that quietly goes stale is the same shape of bug wearing a different costume, all over a CIAM stack.

A JWT's role claim, minted at login

An access token bakes in the roles a user had at the moment it was issued. Promote that user to admin five minutes into their session and the token they're still using doesn't lie exactly — it's just describing a moment that has already passed. It stays wrong until it's refreshed or re-issued, the same way a queued model stays stuck on whatever the database said at dispatch time.

a snapshot presented as if it were still live

A detached JPA entity crossing an @Async boundary

Pass a @Transactional-loaded entity into an @Async method and by the time that method's thread touches it, the persistence context that loaded it has already closed. The entity is detached: set a field on it afterward without an explicit merge() and you've changed an orphaned in-memory copy — the database never hears about it, exactly like the unsaved property that never reaches the queue worker's fresh copy.

the same trap, one layer down in Spring's own persistence context

A stale closure in a UI event handler

An event handler built during one render captures whatever the surrounding values were at that instant. Change that value a moment later, before the user clicks, and the handler still acts on the number it closed over — because a closure is a snapshot taken once, not a live wire back to the variable's current state.

a captured moment mistaken for a live connection

1. Eloquent is Active Record

// the model IS the query interface and the row
$user = User::find(42); // SELECT … WHERE id=42
$user->email = "new@x.com";
$user->save(); // UPDATE … (only changed columns)

$user->orders()->create([...]); // INSERT a related row
User::where("active", true)->get(); // query builder
Active Record vs Data Mapper. In Eloquent the model both represents a row and is the query API — $user->save() persists itself. Spring/JPA splits these: an entity holds data, a repository does persistence. Active Record is terser for CRUD; Data Mapper separates concerns better for complex domains. Same N+1 trap in both — use ->with() to eager-load.

2. FormRequest — validation as a class

class StoreUserRequest extends FormRequest {
  public function authorize(): bool { return $this->user()->can("create", User::class); }
  public function rules(): array {
    return ["email" => "required|email|unique:users"];
  }
}
// inject it; validation + authorization run BEFORE the controller body
public function store(StoreUserRequest $request) { ... }

A FormRequest bundles authorization + validation into a type you inject — failures auto-return 403 / 422. It is Laravel's answer to a validated DTO plus a method-security check, in one class.
