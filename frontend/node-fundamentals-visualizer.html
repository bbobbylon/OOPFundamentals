Node.js Runtime & the Event Loop

One thread, never blocked: the call stack, libuv, the macrotask & microtask queues, and the event loop that ties them together — why Node handles thousands of concurrent connections without a thread per request.

🟢 What is Node.js — and how does one thread serve thousands of requests?

Node.js runs JavaScript outside the browser on Google's V8 engine, plus libuv — a C library that gives Node a thread pool and an OS-level event notification system. Your JS runs on a single thread with one call stack. When you call something asynchronous (a timer, a file read, a DB query), Node hands the work to libuv and immediately moves on — the thread is never blocked waiting. When the work finishes, its callback is parked in a queue. The event loop is the heartbeat: whenever the call stack is empty, it pulls the next callback and runs it. Promises and queueMicrotask go in a higher-priority microtask queue that fully drains after every task. That non-blocking model — not threads — is how a single Node process serves huge concurrency. This is the opposite of Spring Boot's thread-per-request model, and the thing that surprises Java developers most.

  • Single-threaded JS on V8 — one call stack, run-to-completion.
  • libuv does async I/O & timers off the main thread (a small thread pool).
  • Event loop moves queued callbacks onto the stack only when it is empty.
  • Microtasks (promises) beat macrotasks (timers/I/O) — drained first, every time.

The non-blocking model

console.log("1: start"); setTimeout(() => { console.log("4: timeout (macrotask)"); }, 0); Promise.resolve().then(() => { console.log("3: promise (microtask)"); }); console.log("2: end"); // Output: 1, 2, 3, 4 // All sync code runs first (1,2), // then microtasks (3), then macrotasks (4).

Async I/O without threads

import { readFile } from "node:fs/promises"; // Non-blocking: the thread is FREE while // libuv reads the file on its thread pool. const data = await readFile("big.json", "utf8"); // Thousands of these can be in flight at once // on ONE thread — each just parks a callback. // Contrast: blocking readFileSync() freezes // the whole process until the disk responds.

Spring Boot comparison

Spring Boot (classic MVC) uses a thread per request from a Tomcat pool — a blocking jdbcTemplate.query() just parks that thread; concurrency = pool size (e.g. 200). Node uses one thread + an event loop: a blocking-looking await db.query() actually frees the thread to serve other requests, so one process handles far more concurrent I/O-bound work. The trade-off flips for CPU-bound work: a heavy computation blocks Node's single loop (starving everyone), while Spring just uses another thread. Node's answer is worker_threads or offloading. Spring WebFlux (Reactor) is the JVM's event-loop equivalent.

CIAM Node gateway: A Node BFF validating Ping/Entra JWTs is almost all I/O — verify a signature (CPU-cheap), call /userinfo, hit a session store, proxy to a downstream API. The event loop shines here: thousands of in-flight token validations and upstream calls share one thread because each is just a parked callback awaiting I/O. The one rule: never do something CPU-heavy (a giant JSON transform, synchronous crypto over megabytes) on the main loop, or every other request stalls behind it.

The problem

Your retry helper uses 0% CPU. The server still can't answer a health check.

Nothing is slow — nothing else is running

You wrote a small helper that retries a not-quite-ready operation by calling process.nextTick(retry) at the end of itself — it felt like the fast choice, since nextTick beats every timer and every promise to the front of the queue. Under load, the health check starts timing out and the load balancer restarts the instance. You check CPU usage: idle. You check for a runaway loop: there isn't one. Every symptom says "the process died," but the process is still running — it just never gets past this one function.

CPU usage: ~0% ✓ no runaway loop anywhere ✓ nextTick queue: never empty ⚠ poll phase (sockets, health checks): never runs ⚠

The bug isn't that something is doing too much work. It's that the loop is never being handed back.

Scheduling a callback is also a decision about who has to wait for it. process.nextTick and promise microtasks fully drain before the loop is allowed to advance a single phase, so a callback that keeps re-adding itself to either queue can hold up every timer, every socket read, and every health check on the process. That is the same rule that orders the A/B/C/D interview question below, the same rule "don't block the loop" leans on, and the reason setImmediate exists at all — it is the "run soon" that still lets I/O go first.
Think of process.nextTick as a bank customer who's allowed to say "actually, one more thing" and jump straight back to the front of the line — as many times as they want, with no rule stopping them. The teller can't call the next number until that customer finally stops. It stops being a fair comparison the moment you remember a real customer eventually runs out of one-more-things; a recursive nextTick callback might not.

The mechanism

Zero re-scheduled callbacks — that's the only number that decides when the loop moves on.

  1. A request needs to retry, so its handler calls process.nextTick(retry) once, right before returningfeels instant
  2. The current turn finishes, so Node applies its rule: the nextTick queue must run completely empty before the loop can advance to the next phasethe rule that matters
  3. retry() runs. Still not ready, so it calls process.nextTick(retry) again before returningthe same trick, again
  4. The queue is non-empty again, so step 2's rule fires again — the loop still hasn't movedthis is the trap
  5. Meanwhile a client's socket has data waiting, and the health check has an open connection — both sit in the poll phase queue, unservicedyour users are here
  6. Only once retry() finally stops re-queuing itself does the nextTick queue empty — every stalled socket then fires at once, however late it isthe pileup

Step 2 is the lesson. The loop doesn't advance because enough time has passed or because the CPU is busy — it advances only when one specific queue hits zero. A callback that re-adds itself before returning keeps that number above zero indefinitely, and every phase after it — poll, check, close — simply never gets a turn. That's a starvation bug with no exception thrown and no CPU spike to find it by.

RETRY(): not ready yet calls process.nextTick(retry) again before returning → RETRY(): not ready yet
RETRY(): finally ready returns WITHOUT re-scheduling itself → QUEUE EMPTY
QUEUE EMPTY only now can the loop advance a phase → POLL PHASE RUNS
POLL PHASE RUNS every socket that arrived during the retry fires at once → RETRY(): not ready yet, next time

The top row is the trap, drawn as what it really is: a cycle that only ever points back at itself. Nothing here is slow in the CPU sense — it's slow in the "nobody else gets a turn" sense, which is exactly why a profiler shows idle time while the server looks dead.

A handler runs, in this exact order: console.log('1'), then setTimeout(() => console.log('2'), 0), then process.nextTick(() => console.log('3')), then Promise.resolve().then(() => console.log('4')), then process.nextTick(() => console.log('5')), then console.log('6'). What prints, in order?

Reasonable guess if nextTick and the promise shared one FIFO line — plenty of casual explanations lump both together as "microtasks." They don't share a line. Node empties the nextTick queue completely, including anything added while it drains, before the promise microtask queue gets a single turn — so both nextTicks (3 and 5) finish before 4 runs, even though 4 was scheduled in between them.

Right. Sync code finishes first: 1, 6. Then the nextTick queue drains completely, in call order: 3, then 5. Only once it's empty does the promise microtask queue get its turn: 4. Only once that's empty does a single macrotask run: the timer, 2. Notice 4 was scheduled before 5 finished being declared, and still runs after it — queue identity beats scheduling order.

This is what the name suggests if you take "next tick" literally — but run-to-completion doesn't bend for it. No queued callback of any kind, from any queue, runs until the currently executing synchronous code returns, so console.log('6') always happens before Node even glances at a queue.

Where you've seen this before

Three systems, one trap: a queue that never lets go doesn't need a big computation to hurt you.

The browser has this too — with one fewer queue

Every JS engine, browser or Node, drains its microtask queue (promises, queueMicrotask) completely between every macrotask — that's the ECMAScript spec, not a Node feature. The browser just doesn't have process.nextTick: that third, even-higher-priority queue is a Node-only API stacked on top of the same rule. A recursive queueMicrotask() loop starves a browser tab's rendering exactly the way a recursive nextTick starves a Node server's sockets.

same trap, one browser API lighter

Java: a starved thread needs no queue at all

Java has no single-threaded loop to starve, but it produces the identical symptom from a different cause: a thread holding a synchronized lock, or a pool sized too small for the load, makes every other thread wait indefinitely while the CPU itself sits barely busy. Same diagnosis either way — "nothing is slow, but nothing else is running" — and the same first instinct fails: a profiler shows near-idle time in both cases, because the problem is scheduling, not computation.

lock contention ≈ nextTick starvation

Your CIAM gateway, retrying a flaky /userinfo call

A Node backend-for-frontend validates a Ping or Entra JWT, then calls the identity provider's /userinfo endpoint to hydrate the session. Write the retry-on-timeout logic as process.nextTick(retry) instead of a real backoff, and one slow identity call can pin the nextTick queue busy — every other tenant's login request queues up behind it on the same process, because of a helper function nobody thought was "doing work."

Questions from the back row

If nextTick is higher priority, why does everyone say to use async/await instead?

Because priority isn't the same as safety. nextTick's priority is exactly what makes it dangerous to reach for casually — it queue-jumps everything, including I/O, and Node's own documentation warns against building recursive logic on top of it. Promises get the priority benefit (microtasks still beat timers) without the ability to fully monopolize the loop the way an ill-behaved recursive nextTick chain can. Let async/await be your default, and let nextTick stay the internal plumbing detail it was designed to be.

Does setImmediate actually mean "immediately"?

No — it might be the most misleading name in the API. setImmediate doesn't jump any queue; it schedules a callback for the check phase, which runs after the poll (I/O) phase of the current loop iteration. Inside an I/O callback it reliably beats a setTimeout(fn, 0) scheduled at the same moment, because poll already happened this tick and check comes right after. At the very top level of a script, the order between the two isn't guaranteed. "Immediate" here means "next available check phase," not "right now."

CPU usage looks fine — how would I even notice this happening in production?

Watch event-loop lag, not CPU. perf_hooks.monitorEventLoopDelay() (or a package like blocked-at) measures the gap between when a timer or I/O callback should run and when it actually does. A process stuck draining nextTick shows near-zero CPU load but climbing event-loop-delay numbers, plus connections that time out even though nothing in top looks busy. Idle CPU paired with an unresponsive server is the fingerprint of a scheduling starvation, not a computation problem.

1. The event loop phases

// libuv runs the loop in ordered phases, each with its own queue:
┌─> timers // setTimeout / setInterval callbacks
│ pending // deferred I/O callbacks
│ poll // retrieve new I/O events; run I/O callbacks
│ check // setImmediate callbacks
└── close // 'close' events (socket.on('close'))

// After EACH callback, the microtask queue (promises,
// process.nextTick) is drained completely before moving on.
Run-to-completion. A callback runs start to finish with nothing interrupting it — JavaScript is never pre-empted mid-function. That is why a long synchronous loop is so dangerous: until it returns, the event loop cannot run any other callback, and the whole server appears frozen.

2. nextTick & microtasks beat the rest

setTimeout(() => console.log("timeout"), 0); // macrotask (timers phase)
setImmediate(() => console.log("immediate")); // macrotask (check phase)
Promise.resolve().then(() => console.log("promise")); // microtask
process.nextTick(() => console.log("nextTick")); // runs before other microtasks

// Order: nextTick → promise → (timeout / immediate)

process.nextTick runs before the Promise microtask queue; both run before any macrotask. Overusing nextTick can starve the loop (it keeps cutting in line).

3. Don't block the loop

// ❌ BAD — freezes every other request for ~2s
app.get("/hash", (req, res) => {
  const h = crypto.pbkdf2Sync(pw, salt, 1_000_000, 64, "sha512"); // sync!
  res.json({ h });
});

// ✅ GOOD — async variant runs on libuv's thread pool
app.get("/hash", (req, res) => {
  crypto.pbkdf2(pw, salt, 1_000_000, 64, "sha512", (e, h) => {
    res.json({ h: h.toString("hex") }); // loop stayed free
  });
});
