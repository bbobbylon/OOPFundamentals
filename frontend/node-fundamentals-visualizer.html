Node.js Runtime & the Event Loop

One thread, never blocked: the call stack, libuv, the macrotask & microtask queues, and the event loop that ties them together — why Node handles thousands of concurrent connections without a thread per request.

🟢 What is Node.js — and how does one thread serve thousands of requests?

Node.js runs JavaScript outside the browser on Google's V8 engine, plus libuv — a C library that gives Node a thread pool and an OS-level event notification system. Your JS runs on a single thread with one call stack. When you call something asynchronous (a timer, a file read, a DB query), Node hands the work to libuv and immediately moves on — the thread is never blocked waiting. When the work finishes, its callback is parked in a queue. The event loop is the heartbeat: whenever the call stack is empty, it pulls the next callback and runs it. Promises and queueMicrotask go in a higher-priority microtask queue that fully drains after every task. That non-blocking model — not threads — is how a single Node process serves huge concurrency. This is the opposite of Spring Boot's thread-per-request model, and the thing that surprises Java developers most.

  • Single-threaded JS on V8 — one call stack, run-to-completion.
  • libuv does async I/O & timers off the main thread (a small thread pool).
  • Event loop moves queued callbacks onto the stack only when it is empty.
  • Microtasks (promises) beat macrotasks (timers/I/O) — drained first, every time.

The non-blocking model

console.log("1: start"); setTimeout(() => { console.log("4: timeout (macrotask)"); }, 0); Promise.resolve().then(() => { console.log("3: promise (microtask)"); }); console.log("2: end"); // Output: 1, 2, 3, 4 // All sync code runs first (1,2), // then microtasks (3), then macrotasks (4).

Async I/O without threads

import { readFile } from "node:fs/promises"; // Non-blocking: the thread is FREE while // libuv reads the file on its thread pool. const data = await readFile("big.json", "utf8"); // Thousands of these can be in flight at once // on ONE thread — each just parks a callback. // Contrast: blocking readFileSync() freezes // the whole process until the disk responds.

Spring Boot comparison

Spring Boot (classic MVC) uses a thread per request from a Tomcat pool — a blocking jdbcTemplate.query() just parks that thread; concurrency = pool size (e.g. 200). Node uses one thread + an event loop: a blocking-looking await db.query() actually frees the thread to serve other requests, so one process handles far more concurrent I/O-bound work. The trade-off flips for CPU-bound work: a heavy computation blocks Node's single loop (starving everyone), while Spring just uses another thread. Node's answer is worker_threads or offloading. Spring WebFlux (Reactor) is the JVM's event-loop equivalent.

CIAM Node gateway: A Node BFF validating Ping/Entra JWTs is almost all I/O — verify a signature (CPU-cheap), call /userinfo, hit a session store, proxy to a downstream API. The event loop shines here: thousands of in-flight token validations and upstream calls share one thread because each is just a parked callback awaiting I/O. The one rule: never do something CPU-heavy (a giant JSON transform, synchronous crypto over megabytes) on the main loop, or every other request stalls behind it.

1. The event loop phases

// libuv runs the loop in ordered phases, each with its own queue:
┌─> timers // setTimeout / setInterval callbacks
│ pending // deferred I/O callbacks
│ poll // retrieve new I/O events; run I/O callbacks
│ check // setImmediate callbacks
└── close // 'close' events (socket.on('close'))

// After EACH callback, the microtask queue (promises,
// process.nextTick) is drained completely before moving on.
Run-to-completion. A callback runs start to finish with nothing interrupting it — JavaScript is never pre-empted mid-function. That is why a long synchronous loop is so dangerous: until it returns, the event loop cannot run any other callback, and the whole server appears frozen.

2. nextTick & microtasks beat the rest

setTimeout(() => console.log("timeout"), 0); // macrotask (timers phase)
setImmediate(() => console.log("immediate")); // macrotask (check phase)
Promise.resolve().then(() => console.log("promise")); // microtask
process.nextTick(() => console.log("nextTick")); // runs before other microtasks

// Order: nextTick → promise → (timeout / immediate)

process.nextTick runs before the Promise microtask queue; both run before any macrotask. Overusing nextTick can starve the loop (it keeps cutting in line).

3. Don't block the loop

// ❌ BAD — freezes every other request for ~2s
app.get("/hash", (req, res) => {
  const h = crypto.pbkdf2Sync(pw, salt, 1_000_000, 64, "sha512"); // sync!
  res.json({ h });
});

// ✅ GOOD — async variant runs on libuv's thread pool
app.get("/hash", (req, res) => {
  crypto.pbkdf2(pw, salt, 1_000_000, 64, "sha512", (e, h) => {
    res.json({ h: h.toString("hex") }); // loop stayed free
  });
});
