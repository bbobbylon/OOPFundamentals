Components & Templates

Angular apps are trees of components. A component is just a TypeScript class with a decorator that says "here's my HTML and my CSS" — plus a public API of inputs (data in) and outputs (events out). That's the whole job.

🧩 What is an Angular component? Why is everything a component?

An Angular app is built from components — self-contained pieces of UI, each a TypeScript class with its own HTML template and scoped styles. A component behaves like a custom HTML element: <app-user-card> renders a card; inside it, <app-avatar> renders the photo. The whole app is a tree of nested components, from the root AppComponent down to the smallest button. The @Component decorator is what ties the class to its template, its CSS, and the tag name (selector) Angular registers.

  • Three pieces in one unit: the class (logic + state), the template (HTML with Angular syntax), and styles (CSS scoped to just this component).
  • Data flows down via inputs (@Input() / the modern input()) and up via outputs (@Output() / output() events).
  • model() gives two-way binding; <ng-content> projects child markup in; the selector decides the tag a parent uses to place it.
  • Angular drives each one through lifecycle hooks — ngOnInit (setup), ngOnChanges (an input changed), ngOnDestroy (clean up / unsubscribe).
  • You build features by composing small components, not by writing one giant page — each owns and renders its own slice of state.

Anatomy of a component

  • Class — TypeScript logic, properties, methods
  • Template — HTML + bindings ({{ }}, [ ], ( ))
  • Styles — CSS scoped to this component only
  • selector — the tag, e.g. app-user-card

Talking to other components

  • input() — parent passes data IN
  • output() — emit events OUT to the parent
  • model() — two-way [(x)] binding
  • <ng-content> — project child markup

Lifecycle hooks

  • ngOnInit — first-render setup
  • ngOnChanges — an @Input changed
  • ngAfterViewInit — view + @ViewChild ready
  • ngOnDestroy — cleanup (unsubscribe!)
In a CIAM Angular app:the login form, the user-profile page, and the "logged in as" banner are each components. Each renders its own slice of auth state, and the whole OIDC login flow is orchestrated by components communicating through services and inputs/outputs.

The problem

Angular builds your class before it has anything to put in it.

The admin button nobody ever saw

You write an <app-admin-tools> that takes the signed-in user and decides, once, whether to show the "Edit roles" control. You put that decision in the constructor, because that is where initialisation goes in every other language you have ever used. Angular calls new AdminTools() before it assigns a single input — so this.user is undefined, the ?. you added quietly swallows it, and canEdit is computed as false and never computed again.

constructor runs firstuser = undefined canEdit = false ⚠nothing throws ⚠ ships to prod ⚠

The version that crashes gets fixed on Tuesday. This version renders perfectly, for everybody, forever — and turns up in March as a ticket titled "admins can't edit anything".

Read inputs where inputs exist
constructor() — inject services, and stop there ↓ the object exists, but Angular has not touched its inputs yet Angular assigns every bound input, then calls ngOnChanges() ↓ the values are really there now, for the first time ngOnInit() — the first moment this.user is a user ↓ so fetches, subscriptions and derived flags all live here ngOnDestroy() — hand back everything you took
The constructor belongs to TypeScript. ngOnInit belongs to Angular. new is a language feature and it fires the instant the class is created; inputs are a framework feature and they arrive later, in a separate pass. Every "why is this undefined" question in Angular is that one sentence, asked again.
constructor()

I run the microsecond the class is created. Ask me for a service and I will hand it over. Ask me for user and I will hand you undefined with a completely straight face.

Angular

Correct, and not my fault. I cannot bind [user]="me()" onto an object that does not exist yet. Build first, bind second — there is no other order available.

ngOnInit()

Which is the entire reason I exist. I am the phone call that says "everything the parent promised has arrived." Start your HTTP call on my line, not one step earlier.

The mechanism

Seven beats, and each one only makes sense after the one before it.

  1. new YourComponent() — DI runs, field initialisers run, inputs are still emptyconstructor
  2. Angular writes every bound input onto the instancebinding
  3. ngOnChanges(changes) — a map keyed by input name, each entry carrying previousValue, currentValue and firstChangeinputs arrived
  4. ngOnInit() — runs exactly once, and is the first hook where the inputs are realset up here
  5. the template is evaluated and the DOM is patchedrender
  6. in dev mode only, Angular re-checks every binding and shouts if one movedverify
  7. ngOnDestroy() — the component leaves the DOM; the things it subscribed to do notclean up

Step 6 is the one everybody re-learns. ExpressionChangedAfterItHasBeenCheckedError is not Angular being fussy — it is Angular telling you that a value it had already verified changed again inside the same cycle, so the number on the screen is no longer the number in your component.

That the error exists only in development is the entire point of it. Dev mode runs change detection twice per cycle: once to render, once to compare. If ngAfterViewInit measured a table and wrote rowCount = 12 after the first pass, the second pass finds the binding saying 12 while the DOM still says 0 — mismatch, throw. Production runs that pass once, notices nothing, and shows you 0: a stale number, silently, with no error anywhere on the page. The exception is not the bug — it is the only thing that ever told you about the bug. Fix it by moving the write out of the checked window (afterNextRender(), a signal Angular will re-read, or simply computing the value earlier), not by pasting in detectChanges() until the shouting stops.

In ngAfterViewInit you set this.rowCount from a measured table, and {{ rowCount }} is in the template. Dev mode throws ExpressionChangedAfterItHasBeenCheckedError. What does that actually mean?

A double subscription gives you duplicate work, not this error. Angular is not complaining about how many times the value arrived; it is complaining about when. One assignment, made after the check, is enough on its own.

Right. First pass: rowCount is 0, the DOM says 0, checked and done. Then ngAfterViewInit sets it to 12. The verification pass reads 12, sees 0 painted, and refuses to pretend that is fine.

This is the trap. Production skips the verification pass, so nothing throws — and the screen keeps showing the stale 0 until something else happens to trigger a check. Dev mode is the only thing standing between you and a number that is quietly wrong in front of a customer.

Questions from the back row

If ngOnChanges already fires before ngOnInit, why do I need both?

Because they answer different questions. ngOnChanges fires on every input update — and never fires at all for a component that has no inputs. ngOnInit runs exactly once either way. "Do this once, with the first values" belongs in ngOnInit; "react to this changing" belongs in ngOnChanges. And the trap: with decorator inputs the hook only fires when the reference changes. Do user.roles.push('admin') in the parent and the reference is identical, so the hook never fires and you will swear Angular is broken.

What is firstChange actually for?

changes['user'].firstChange is true only on the very first delivery, which lets one handler do two jobs: initialise on the first call, diff against previousValue on every call after it — no hand-rolled boolean flag. Note that SimpleChanges is a map, not a record of all your inputs: if a different input changed, changes['user'] is simply absent, so guard the key before you read it.

Is ngOnDestroy dead now that takeUntilDestroyed exists?

For RxJS, mostly — takeUntilDestroyed() in a field initialiser, or takeUntilDestroyed(inject(DestroyRef)) anywhere else, and the subscription ends with the component. But it only knows about observables. A setInterval, a chart instance, a listener you added to window, an open socket — those still need ngOnDestroy or a DestroyRef.onDestroy() callback, and a leaked one keeps a whole component tree alive in memory.

Connecting them — selector + parent template

    

      

        The selector: 'app-counter' line tells Angular: "wherever you see <app-counter></app-counter> in HTML, instantiate this component there." A parent component uses it by importing it (standalone) and referencing the tag.
      

      
// app.component.ts — the root component
import { Component } from '@angular/core';
import { CounterComponent } from './counter.component';

@Component({
  selector: 'app-root',
  imports: [CounterComponent],                  // must import to use the tag
  template: `
    <h1>My App</h1>
    <app-counter />                              // ← use it here!
    <app-counter />                              // ← use it as many times as you want
  `
})
export class AppComponent {}

      

        Each tag is a fresh instance with its own count. Two counters on the page = two completely independent instances, just like new CounterComponent() twice.

A component's public API — input() & output()

    

      

        Here's the code behind the animation. In modern Angular (v17.3+), you declare a component's public surface with two functions that return signals: input() for data coming in, output() for events going out. This is the form to reach for in new code.
      

      
// product.component.ts — the modern, signal-based public API
import { Component, input, output, computed } from '@angular/core';
import { numberAttribute } from '@angular/core';

@Component({
  selector: 'app-product',
  template: `
    <h3>{{ name() }}</h3>             <!-- read an input like a function -->
    <p>{{ blurb() }}</p>             <!-- derived state, for free -->
    <button (click)="like()">♥ Like</button>
  `
})
export class ProductComponent {
  // ── INPUTS: data the parent passes DOWN ──
  name     = input.required<string>();                  // must be provided, or compile error
  discount = input(0, { transform: numberAttribute });      // optional, has a default, coerced

  // ── OUTPUTS: events this component sends UP ──
  liked = output<void>();                                  // OutputEmitterRef<void> — no payload

  // ── derived state: ngOnChanges? 404 — computed() already tracked it ──
  blurb = computed(() => `${this.name()} — ${this.discount()}% off`);

  like() { this.liked.emit(); }                            // → fires the parent's (liked) handler
}

      
And the parent wires both ends in its template — square brackets for input (down), parentheses for output (up):

      
<!-- app.component.html -->
<app-product
  [name]="product"          <!-- input  → DOWN -->
  [discount]="10"
  (liked)="likes++"          <!-- output → UP -->
/>


      
Reading a signal input: name vs name()

      

        this.name is the signal itself; this.name() calls it to get the current value. In templates you write {{ name() }}. Drop that call inside a computed() or effect() and Angular tracks the dependency automatically — no ngOnChanges lifecycle hook to react to input changes.
      


      
You'll still see the older decorator form everywhere

      
It isn't deprecated and most existing codebases use it. Same idea — data down, events up — just expressed with decorators instead of functions:

      
// the legacy form — recognize it, but prefer input()/output() in new code
export class ProductComponent {
  @Input({ required: true }) name!: string;          // down
  @Output() liked = new EventEmitter<void>();      // up

  like() { this.liked.emit(); }
}

Two-way binding with model()

    

      

        Sometimes a child both receives a value and changes it — a stepper, a toggle, a custom input. model() is an input and its matching output bundled together, so a parent can two-way bind with [(value)]. (That banana-in-a-box [(ngModel)] you've seen? Same mechanism.)
      

      
// stepper.component.ts
import { Component, model } from '@angular/core';

@Component({
  selector: 'app-stepper',
  template: `
    <button (click)="dec()">−</button>
    {{ value() }}
    <button (click)="inc()">+</button>
  `
})
export class StepperComponent {
  value = model(0);                       // ModelSignal<number> = input + matching output

  inc() { this.value.update(v => v + 1); }   // auto-emits the new value upward
  dec() { this.value.update(v => v - 1); }
}

      
<!-- parent — true two-way binding, no (valueChange) to wire up -->
<app-stepper [(value)]="quantity"/>

<!-- exactly equivalent to the long form: -->
<app-stepper [value]="quantity" (valueChange)="quantity = $event"/>

    


    
Inline vs external — pick your style

    

      

        
External files (good for big components)

        
@Component({
  selector: 'app-counter',
  templateUrl: './counter.component.html',
  styleUrl:    './counter.component.css'
})

        
Separate files. Best when HTML > 20 lines or CSS is non-trivial. Editor gets full syntax highlighting per file.

      

      

        
Inline (good for tiny components)

        
@Component({
  selector: 'app-badge',
  template: `<span class="badge">{{ text() }}</span>`,
  styles: `.badge { padding: 4px 8px; }`
})

        
All-in-one. Best for trivial components — badges, icons, dumb display components. Easier to read at a glance.

      

    


    
Standalone components — the modern default (Angular 14+, default since 19)

    

      

        For years, every component had to be declared in an NgModule. Then standalone: true arrived; as of Angular 19 it's the default — you don't even write the flag. Components import what they need directly, no boilerplate module file required.
      

      

        

          
❌ Old way — NgModule (still works, but verbose)

          
@NgModule({
  declarations: [CounterComponent],
  imports: [CommonModule, FormsModule],
  exports: [CounterComponent]
})
export class CounterModule {}

        

        

          
✅ New way — standalone (the default)

          
@Component({
  selector: 'app-counter',
  imports: [CommonModule, FormsModule],      // import deps right here
  template: `...`
})
export class CounterComponent {}

        

      

      

        New apps (ng new my-app) generate standalone by default. Use them. The NgModule world isn't going away — old codebases still have it everywhere — but you don't need to learn it to start building today. (You can still write standalone: true explicitly; it's just redundant now.)
      

    


    
The host element — your component's own tag

    

      

        Every component renders into its selector tag — for <app-product>, that outer tag is the component's host element. You don't need a wrapper <div>: style the host with :host in CSS, and bind to it from the host metadata in TS. This keeps a component self-contained — it decorates its own tag.
      

      
@Component({
  selector: 'app-product',
  host: {
    'class': 'card',                    // always render class="card" on the host
    '[class.is-liked]': 'liked()',       // toggle a class from component state
    '[attr.role]': '"listitem"',         // set an ARIA attribute
    '(click)': 'select()'              // listen for clicks on the host itself
  },
  template: `...`
})

      
/* product.component.css — :host targets the <app-product> tag */
:host { display: block; border: 1px solid #334155; border-radius: 8px; }
:host(.is-liked) { border-color: #f472b6; }     /* when the host has .is-liked */
:host-context(.dark) h3 { color: white; }      /* react to an ancestor's class */

View encapsulation — why your CSS doesn't leak

    

      

        Define .title { color: red; } in counter.component.css and it ONLY affects .title elements inside <app-counter> — not any other .title on the page. Angular does this by attaching a unique attribute to your elements and rewriting your CSS.
      

      
<!-- What you write -->
<h3 class="title">Hi</h3>

<!-- What Angular renders -->
<h3 class="title" _ngcontent-abc-1>Hi</h3>

/* What you wrote */
.title { color: red; }

/* What Angular generates */
.title[_ngcontent-abc-1] { color: red; }

      

        Three modes: Emulated (default — the attribute trick above), ShadowDom (real browser Shadow DOM), None (global — escape hatch).

Mental model — the things that make a component

    

      

        
1. A class

        
Plain TypeScript. Holds state (properties) and behavior (methods). Nothing Angular-specific about the class itself.

      

      

        
2. A decorator

        
@Component({...}) attached above the class. Tells Angular "this is a component" and provides the metadata: selector, template, styles, host.

      

      

        
3. A template

        
HTML, possibly with Angular's binding syntax ({{ }}, [prop], (event)). Angular compiles it into rendering instructions.

      

      

        
4. A public API

        
Its input()s (data in) and output()s (events out) — the contract every parent relies on. Plus optional scoped styles.

🌱 Brand-new to all this? The plain-English version

    

      
Forget the jargon for a second. A component is one reusable piece of the screen — a navbar, a product card, a login form. Each piece bundles three things that belong together:

      
    
        
  • a template (HTML) — what you see;
    • 
        
  • styles (CSS) — how it looks (and they're scoped, so they can't leak out and wreck other components);
    • 
        
  • a class (TypeScript) — the data and logic behind it.
    • 
      

      
You give that bundle a tag name — say <app-product> — and now you can drop it into a page like a LEGO brick, as many times as you like. A whole Angular app is just components nested inside components, all the way up to a single root <app-root>. The @Component({...}) line on top of the class is nothing scary — it's a label that tells Angular "this class is a component; here's its tag and its template." That's the entire idea. Everything else on this page is detail layered on top of it.

    


    
🧠 Expert corner — what's really happening underneath

    

      
    
        
  • It's standalone now. Modern Angular components set standalone: true (the default since v17) and list their own imports — no NgModule boilerplate. The old module system still works, but greenfield code is standalone.
    • 
        
  • The template is compiled, not interpreted. Angular's compiler turns your HTML into imperative render instructions plus a per-component change detector. There's no live DOM diffing like React's virtual DOM — each component knows exactly which bindings to re-check.
    • 
        
  • OnPush is the performance lever. changeDetection: ChangeDetectionStrategy.OnPush tells that detector to skip the component unless an @Input/input() reference changes, an event fires inside it, or a bound signal/async pipe emits. On a big tree this turns O(everything) into O(what-actually-changed).
    • 
        
  • The host element is real. The <app-product> tag is an actual DOM node you can style and bind to via the host property or @HostBinding/@HostListener — the component is a custom element in the tree, not an invisible wrapper.
    • 
        
  • Inputs/outputs are signals (v17+). input(), output(), and model() are the signal-based API — reading name() participates in reactivity, so a template that reads it updates automatically. (The decorator forms @Input()/@Output() still exist.)
    • 
        
  • CIAM tie-in. A <user-menu> takes the signed-in user as an input() and emits a logout output(); a route guard decides whether the page renders, but the component stays a small, isolated unit you can test on its own with TestBed. Keep components dumb about auth policy — pass them the already-decided state.
    • 
      

      
Rule of thumb that scales from day one to senior: a component should do one job and own a small amount of state. When a component starts coordinating many others or holding app-wide data, that's the signal to push logic into a service.
