Components & Templates

Angular apps are trees of components. A component is just a TypeScript class with a decorator that says "here's my HTML and my CSS" — plus a public API of inputs (data in) and outputs (events out). That's the whole job.

Live demo — a real component in action

In Angular, this entire box below is one component called <app-counter>. Click the buttons — the click handler is wired through Angular's event binding (see the Data Binding visualizer).

</app-counter>

The four pieces of every component

// counter.component.ts
import { Component } from '@angular/core';

@Component({                                  // 1️⃣ DECORATOR — metadata
  selector: 'app-counter',                   //    the HTML tag to use this with
  templateUrl: './counter.component.html',    // 2️⃣ TEMPLATE — what you see (HTML)
  styleUrl: './counter.component.css'         // 3️⃣ STYLES — how it looks (CSS)
})                                              //    (standalone is the default since v19 — no NgModule)
export class CounterComponent {              // 4️⃣ CLASS — state & behavior (TS)
  title = 'My first Angular component';
  count = 0;

  increment() { this.count++; }
  decrement() { this.count--; }
  reset()     { this.count = 0; }
}

2️⃣ Template — counter.component.html

<h3>{{ title }}</h3>
<div class="count">{{ count }}</div>
<button (click)="decrement()">−</button>
<button (click)="reset()">reset</button>
<button (click)="increment()">+</button>

3️⃣ Styles — counter.component.css

/* SCOPED — only affect this component */
:host {
  display: block;
  text-align: center;
}
.count {
  font-size: 48px;
  color: #4ade80;
}

Connecting them — selector + parent template

The selector: 'app-counter' line tells Angular: "wherever you see <app-counter></app-counter> in HTML, instantiate this component there." A parent component uses it by importing it (standalone) and referencing the tag. 

// app.component.ts — the root component
import { Component } from '@angular/core';
import { CounterComponent } from './counter.component';

@Component({
  selector: 'app-root',
  imports: [CounterComponent],                  // must import to use the tag
  template: `
    <h1>My App</h1>
    <app-counter />                              // ← use it here!
    <app-counter />                              // ← use it as many times as you want
  `
})
export class AppComponent {}

Each tag is a fresh instance with its own count. Two counters on the page = two completely independent instances, just like new CounterComponent() twice.

▶ Watch data flow — input down, output up

Once components nest, they need to talk. The contract is simple and one-directional: the parent owns the data and passes it DOWN through an input; the child announces things by sending an event UP through an output. Press play and watch one round-trip.

…or click ♥ Like on the child yourself.

Press ▶ Play the data flow to send the product name down into the child, then watch a “like” event travel back up to the parent.

The golden rule you just watched: the child never reaches up and changes the parent's data. It can only ask by emitting an event — and the parent, the owner, decides what that event means. That one constraint is what keeps a thousand-component app understandable.

A component's public API — input() & output()

Here's the code behind the animation. In modern Angular (v17.3+), you declare a component's public surface with two functions that return signals: input() for data coming in, output() for events going out. This is the form to reach for in new code. 

// product.component.ts — the modern, signal-based public API
import { Component, input, output, computed } from '@angular/core';
import { numberAttribute } from '@angular/core';

@Component({
  selector: 'app-product',
  template: `
    <h3>{{ name() }}</h3>             <!-- read an input like a function -->
    <p>{{ blurb() }}</p>             <!-- derived state, for free -->
    <button (click)="like()">♥ Like</button>
  `
})
export class ProductComponent {
  // ── INPUTS: data the parent passes DOWN ──
  name     = input.required<string>();                  // must be provided, or compile error
  discount = input(0, { transform: numberAttribute });      // optional, has a default, coerced

  // ── OUTPUTS: events this component sends UP ──
  liked = output<void>();                                  // OutputEmitterRef<void> — no payload

  // ── derived state: ngOnChanges? 404 — computed() already tracked it ──
  blurb = computed(() => `${this.name()} — ${this.discount()}% off`);

  like() { this.liked.emit(); }                            // → fires the parent's (liked) handler
}

And the parent wires both ends in its template — square brackets for input (down), parentheses for output (up):

<!-- app.component.html -->
<app-product
  [name]="product"          <!-- input  → DOWN -->
  [discount]="10"
  (liked)="likes++"          <!-- output → UP -->
/>

Reading a signal input: name vs name()

this.name is the signal itself; this.name() calls it to get the current value. In templates you write {{ name() }}. Drop that call inside a computed() or effect() and Angular tracks the dependency automatically — no ngOnChanges lifecycle hook to react to input changes.

You'll still see the older decorator form everywhere

It isn't deprecated and most existing codebases use it. Same idea — data down, events up — just expressed with decorators instead of functions:

// the legacy form — recognize it, but prefer input()/output() in new code
export class ProductComponent {
  @Input({ required: true }) name!: string;          // down
  @Output() liked = new EventEmitter<void>();      // up

  like() { this.liked.emit(); }
}
🔎 The deep dive lives next door. Required inputs, transform, aliases, two-way [(banana)] binding, talking to siblings via services, viewChild(), and content projection all get the full treatment on the Component Communication page. Here we just meet the API a component exposes.

Two-way binding with model()

Sometimes a child both receives a value and changes it — a stepper, a toggle, a custom input. model() is an input and its matching output bundled together, so a parent can two-way bind with [(value)]. (That banana-in-a-box [(ngModel)] you've seen? Same mechanism.) 

// stepper.component.ts
import { Component, model } from '@angular/core';

@Component({
  selector: 'app-stepper',
  template: `
    <button (click)="dec()">−</button>
    {{ value() }}
    <button (click)="inc()">+</button>
  `
})
export class StepperComponent {
  value = model(0);                       // ModelSignal<number> = input + matching output

  inc() { this.value.update(v => v + 1); }   // auto-emits the new value upward
  dec() { this.value.update(v => v - 1); }
}
<!-- parent — true two-way binding, no (valueChange) to wire up -->
<app-stepper [(value)]="quantity"/>

<!-- exactly equivalent to the long form: -->
<app-stepper [value]="quantity" (valueChange)="quantity = $event"/>

Inline vs external — pick your style

External files (good for big components)

@Component({
  selector: 'app-counter',
  templateUrl: './counter.component.html',
  styleUrl:    './counter.component.css'
})

Separate files. Best when HTML > 20 lines or CSS is non-trivial. Editor gets full syntax highlighting per file.

Inline (good for tiny components)

@Component({
  selector: 'app-badge',
  template: `<span class="badge">{{ text() }}</span>`,
  styles: `.badge { padding: 4px 8px; }`
})

All-in-one. Best for trivial components — badges, icons, dumb display components. Easier to read at a glance.

Standalone components — the modern default (Angular 14+, default since 19)

For years, every component had to be declared in an NgModule. Then standalone: true arrived; as of Angular 19 it's the default — you don't even write the flag. Components import what they need directly, no boilerplate module file required.

❌ Old way — NgModule (still works, but verbose)

@NgModule({
  declarations: [CounterComponent],
  imports: [CommonModule, FormsModule],
  exports: [CounterComponent]
})
export class CounterModule {}

✅ New way — standalone (the default)

@Component({
  selector: 'app-counter',
  imports: [CommonModule, FormsModule],      // import deps right here
  template: `...`
})
export class CounterComponent {}

New apps (ng new my-app) generate standalone by default. Use them. The NgModule world isn't going away — old codebases still have it everywhere — but you don't need to learn it to start building today. (You can still write standalone: true explicitly; it's just redundant now.)

The host element — your component's own tag

Every component renders into its selector tag — for <app-product>, that outer tag is the component's host element. You don't need a wrapper <div>: style the host with :host in CSS, and bind to it from the host metadata in TS. This keeps a component self-contained — it decorates its own tag. 

@Component({
  selector: 'app-product',
  host: {
    'class': 'card',                    // always render class="card" on the host
    '[class.is-liked]': 'liked()',       // toggle a class from component state
    '[attr.role]': '"listitem"',         // set an ARIA attribute
    '(click)': 'select()'              // listen for clicks on the host itself
  },
  template: `...`
})
/* product.component.css — :host targets the <app-product> tag */
:host { display: block; border: 1px solid #334155; border-radius: 8px; }
:host(.is-liked) { border-color: #f472b6; }     /* when the host has .is-liked */
:host-context(.dark) h3 { color: white; }      /* react to an ancestor's class */

Bootstrapping — how the app actually starts

// main.ts — the entry point
import { bootstrapApplication } from '@angular/platform-browser';
import { AppComponent } from './app/app.component';

bootstrapApplication(AppComponent)
  .catch(err => console.error(err));
<!-- index.html — the only hand-written HTML -->
<html>
  <body>
    <app-root></app-root>                  <!-- ← Angular replaces this with the rendered AppComponent -->
  </body>
</html>

Angular finds <app-root> in the DOM, mounts AppComponent there, and from that point on the entire UI is rendered by Angular's component tree.

View encapsulation — why your CSS doesn't leak

Define .title { color: red; } in counter.component.css and it ONLY affects .title elements inside <app-counter> — not any other .title on the page. Angular does this by attaching a unique attribute to your elements and rewriting your CSS. 

<!-- What you write -->
<h3 class="title">Hi</h3>

<!-- What Angular renders -->
<h3 class="title" _ngcontent-abc-1>Hi</h3>

/* What you wrote */
.title { color: red; }

/* What Angular generates */
.title[_ngcontent-abc-1] { color: red; }

Three modes: Emulated (default — the attribute trick above), ShadowDom (real browser Shadow DOM), None (global — escape hatch).

The file convention you'll see everywhere

Run ng generate component counter (shorthand: ng g c counter) and Angular CLI creates this:

📁 counter/
  ├── counter.component.ts← the class + @Component decorator
  ├── counter.component.html← the template
  ├── counter.component.css← scoped styles
  └── counter.component.spec.ts← unit tests (auto-generated)

Every component lives in its own folder with these (up to) 4 files. The CLI also wires it into the nearest imports for you. Don't fight the convention — every Angular codebase looks the same, which is a feature, not a bug.

Component-tree mental model

         <app-root>                       // root component (mounted in index.html)
       /     |     \
 <app-header> <app-sidebar> <app-main>     // three children
                          /        \
                <app-product-list>  <app-cart>
                       |
              <app-product-card> × N        // looped with @for

Your whole app is a tree of components. Data flows down via input(), events bubble up via output() — exactly the round-trip you played above. For deep trees and siblings, a shared service is the escape hatch (see Component Communication).

Mental model — the things that make a component

1. A class

Plain TypeScript. Holds state (properties) and behavior (methods). Nothing Angular-specific about the class itself.

2. A decorator

@Component({...}) attached above the class. Tells Angular "this is a component" and provides the metadata: selector, template, styles, host.

3. A template

HTML, possibly with Angular's binding syntax ({{ }}, [prop], (event)). Angular compiles it into rendering instructions.

4. A public API

Its input()s (data in) and output()s (events out) — the contract every parent relies on. Plus optional scoped styles.
